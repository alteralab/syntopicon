하나의 질문: **크기가 제각각인 레코드를 고정 크기 페이지에 어떻게 놓고, 지워진 자리를 어떻게
되쓰는가.**

## 페이지라는 단위

- **데이터베이스 시스템은 데이터 레코드를 데이터 파일과 인덱스 파일에 저장한다. 이 파일들은
  페이지(pages)라 불리는 고정 크기 단위로 분할되며, 페이지는 흔히 파일시스템 블록 여러 개의
  크기다. 페이지 크기는 보통 4에서 16Kb 범위다** (3장, p.52).[^petrov2019]
- 이름이 겹치는 이유도 여기 있다 — **구조 관점에서 [B-트리](../concepts/b-tree-structure.md)는
  키와 데이터 레코드 쌍을 담는 리프 노드(leaf nodes)와, 키와 다른 노드로 가는 포인터를 담는
  논리프 노드(nonleaf nodes)를 구분한다. 각 B-트리 노드는 페이지 하나 또는 서로 연결된 여러
  페이지를 차지하므로, B-트리 맥락에서 노드(node)·페이지(page)·심지어 블록(block)이라는 말이
  자주 바꿔 쓰인다** (3장, p.52).[^petrov2019]

## 고정 크기 레코드가 막히는 곳

- **원래 B-트리 논문은 고정 크기 데이터 레코드를 위한 단순한 페이지 조직을 서술하는데, 각
  페이지가 삼중항의 연접일 뿐이다** — 키를 k, 딸린 값을 v, 자식 페이지로 가는 포인터를 p로
  적으면 `p₀ k₁ v₁ p₁ k₂ v₂ … kₙ vₙ pₙ` 뒤에 쓰이지 않은 공간이 남는 모양이다 (3장,
  p.52).[^petrov2019]
- **이 접근법은 따라가기 쉽지만 단점이 있다** (3장, p.52):[^petrov2019]
  - **오른쪽 끝이 아닌 곳에 키를 덧붙이려면 요소를 재배치해야 한다.**
  - **가변 크기 레코드를 효율적으로 관리하거나 접근하는 것을 허용하지 않으며 고정 크기
    데이터에만 작동한다.**
- 가변 크기로 가면 새 문제가 나온다 — **가변 크기 레코드를 저장할 때 주된 문제는 자유 공간
  관리(free space management), 곧 제거된 레코드가 차지하던 공간을 회수하는 일이다. 크기가
  `n`인 레코드를 이전에 크기 `m`인 레코드가 차지했던 공간에 넣으려 하면, `m == n`이거나
  크기가 정확히 `m - n`인 다른 레코드를 찾을 수 있지 않은 한 그 공간은 쓰이지 않은 채로 남는다.
  마찬가지로 크기 `m`인 세그먼트는 `k`가 `m`보다 크면 크기 `k`인 레코드를 저장하는 데 쓸 수
  없고, 그래서 쓰이지 않은 공간을 회수하지 않은 채 레코드가 삽입된다** (3장,
  p.52).[^petrov2019]
- 고정 크기 세그먼트로 쪼개는 우회도 값을 치른다 — **가변 크기 레코드의 공간 관리를
  단순화하려고 페이지를 고정 크기 세그먼트로 쪼갤 수 있다. 그러나 그렇게 해도 공간을 낭비하게
  된다. 예컨대 세그먼트 크기를 64바이트로 쓰면 레코드 크기가 64의 배수가 아닌 한
  `64 - (n modulo 64)` 바이트를 낭비한다**(`n`은 삽입된 레코드의 크기). **다시 말해 레코드가
  64의 배수가 아니면 블록 중 하나는 부분적으로만 채워진다** (3장, p.52).[^petrov2019]
- **공간 회수는 그냥 페이지를 다시 쓰고 레코드를 옮기는 것으로도 할 수 있지만, 레코드
  오프셋은 보존해야 한다 — 페이지 밖의 포인터가 이 오프셋을 쓰고 있을 수 있기 때문이다.
  그리고 그 일을 공간 낭비를 최소화하면서 하는 것이 바람직하다** (3장, p.53).[^petrov2019]

## 페이지 형식의 세 요구

- 여기까지를 요약하면 **우리에게 필요한 것은 다음을 할 수 있게 해 주는 페이지 형식**이다
  (3장, p.53):[^petrov2019]
  - **최소한의 오버헤드로 가변 크기 레코드를 저장한다.**
  - **제거된 레코드가 차지한 공간을 회수한다.**
  - **페이지 안의 레코드를 그 정확한 위치와 무관하게 참조한다.**
- **문자열·이진 대형 객체(BLOBs) 같은 가변 크기 레코드를 효율적으로 저장하려면 슬롯
  페이지(slotted page, 곧 슬롯이 있는 페이지) 또는 슬롯 디렉터리(slot directory)라 불리는
  조직 기법을 쓸 수 있다. 이 접근법은 많은 데이터베이스가 쓰며, 예로 PostgreSQL이 있다**
  (3장, p.53).[^petrov2019]

## 슬롯 페이지

- 착상은 **페이지를 슬롯(slots) 또는 셀(cells)의 모음으로 조직하고, 포인터와 셀을 페이지의
  서로 다른 쪽에 자리 잡은 두 개의 독립된 메모리 영역으로 갈라 두는 것**이다. **그래서 순서를
  보존하려면 셀을 주소 지정하는 포인터만 재조직하면 되고, 레코드를 삭제하는 일은 그 포인터를
  무효화하거나 제거하는 것으로 할 수 있다** (3장, p.53).[^petrov2019]
- **슬롯 페이지는 페이지와 셀에 관한 중요한 정보를 담는 고정 크기 헤더를 갖는다. 셀은 크기가
  서로 다를 수 있고 임의의 데이터 — 키·포인터·데이터 레코드 등 — 를 담을 수 있다. 곧 모든
  페이지가 유지 영역(헤더)과 셀들과 그것들을 가리키는 포인터를 갖는 모양이다** (3장,
  p.53).[^petrov2019]
- 앞의 세 요구가 이렇게 풀린다 (3장, p.54):[^petrov2019]
  - **최소 오버헤드** — **슬롯 페이지가 초래하는 유일한 오버헤드는 레코드가 저장된 정확한
    위치의 오프셋을 담는 포인터 배열이다.**
  - **공간 회수** — **페이지를 조각 모음(defragmenting)하고 다시 쓰는 것으로 공간을 회수할
    수 있다.**
  - **동적 배치** — **페이지 밖에서 볼 때 슬롯은 그 ID로만 참조되므로 정확한 위치는 페이지의
    내부 사정이다.**

## 셀 레이아웃

- **플래그·열거형·프리미티브 값을 써서 셀 레이아웃을 설계한 뒤 셀을 페이지로 묶고 페이지로
  트리를 구성할 수 있다. 셀 수준에서는 키 셀(key cell)과 키-값 셀(key-value cell)의 구분이
  있다. 키 셀은 구분 키와, 이웃한 두 포인터 사이에 있는 페이지로 가는 포인터를 담는다. 키-값
  셀은 키와 그에 딸린 데이터 레코드를 담는다** (3장, p.54).[^petrov2019]
- 단순화 가정이 하나 있다 — **페이지 안의 모든 셀이 균일하다고 가정한다**(예컨대 모든 셀이
  키만 담거나 키와 값을 둘 다 담고, 마찬가지로 모든 셀이 고정 크기 데이터 또는 가변 크기
  데이터를 담되 둘을 섞지 않는다). **그러면 셀을 서술하는 메타데이터를 셀마다 복제하지 않고
  페이지 수준에 한 번만 저장할 수 있다** (3장, p.54).[^petrov2019]
- **키 셀을 구성하려면 다음을 알아야 한다** (3장, p.54):[^petrov2019] **셀 타입**(페이지
  메타데이터에서 추론할 수 있다)**·키 크기·이 셀이 가리키는 자식 페이지의 ID·키 바이트.**
- 가변 크기 키 셀의 배치는 이런 모양이다(고정 크기라면 셀 수준에 크기 지정자가 없다) (3장,
  p.54):[^petrov2019]

  ```text
  0               4              8
  +---------------+--------------+------------+
  | [int] key_size | [int] page_id | [bytes] key |
  +---------------+--------------+------------+
  ```

- 고정 크기 필드를 앞에 모은 이유가 명시된다 — **고정 크기 데이터 필드를 함께 묶고 그 뒤에
  `key_size` 바이트를 뒀다. 엄격히 필요한 것은 아니지만 오프셋 계산을 단순화할 수 있다 —
  모든 고정 크기 필드는 정적인 미리 계산된 오프셋으로 접근할 수 있고 가변 크기 데이터에
  대해서만 오프셋을 계산하면 되기 때문이다** (3장, p.54).[^petrov2019]
- **키-값 셀은 자식 페이지 ID 대신 데이터 레코드를 담는다. 그 밖에는 구조가 비슷하다** —
  **셀 타입**(페이지 메타데이터에서 추론 가능)**·키 크기·값 크기·키 바이트·데이터 레코드
  바이트** (3장, p.55).[^petrov2019]
- 오프셋과 페이지 ID를 가르는 이유 — **페이지는 고정 크기이고 페이지 캐시가 관리하므로 우리는
  페이지 ID만 저장하면 되고, 그것이 나중에 룩업 테이블로 파일 안의 실제 오프셋으로 번역된다.
  셀 오프셋(cell offsets)은 페이지 로컬이고 페이지 시작 오프셋에 상대적이다 — 이렇게 하면 더
  작은 카디널리티의 정수로 표현을 더 압축적으로 유지할 수 있다** (3장, p.55).[^petrov2019]
- 가변 크기가 양쪽에 걸려도 된다 — **셀 안의 키와 값이 고정 크기여야 할 필요는 없다. 키와 값
  둘 다 가변 크기일 수 있고, 그 위치는 오프셋을 써서 고정 크기 셀 헤더로부터 계산할 수 있다.
  키를 찾으려면 헤더를 건너뛰고 `key_size` 바이트를 읽는다. 값을 찾으려면 헤더에 `key_size`
  바이트를 더 건너뛰고 `value_size` 바이트를 읽는다** (3장, p.55).[^petrov2019]
  - **같은 일을 하는 다른 방법도 있다 — 예컨대 총 크기를 저장하고 값 크기를 뺄셈으로 계산하는
    것이다. 결국 셀을 부분들로 잘라 인코딩된 데이터를 재구성할 만큼의 정보를 갖는 문제로
    귀착한다** (3장, p.55).[^petrov2019]

## 셀을 페이지에 넣기

- **셀을 페이지로 조직하려면 슬롯 페이지 기법을 쓸 수 있다. 셀을 페이지의 오른쪽(끝 방향)에
  덧붙이고 셀 오프셋/포인터는 페이지의 왼쪽에 둔다** (3장, p.56).[^petrov2019]
- 그래서 정렬이 공짜가 된다 — **키는 순서 없이 삽입될 수 있고, 그 논리적 정렬 순서는 셀 오프셋
  포인터를 키 순서로 정렬함으로써 유지된다. 이 설계는 최소한의 노력으로 셀을 페이지에 덧붙이게
  해 주는데, 삽입·갱신·삭제 연산 중에 셀을 재배치하지 않아도 되기 때문이다** (3장,
  p.56).[^petrov2019]
- 저자가 든 예 — **이름을 담는 페이지에 Tom과 Leslie를 그 순서로 더하면, 그 논리적
  순서**(여기서는 알파벳순)**가 삽입 순서**(페이지에 덧붙여진 순서)**와 맞지 않는다. 셀은 삽입
  순서로 배치되지만 오프셋은 이진 탐색이 가능하도록 다시 정렬된다** (3장,
  p.56).[^petrov2019]
- **여기에 이름 Ron을 더하면 새 데이터는 페이지 자유 공간의 상단 경계에 덧붙지만, 셀 오프셋은
  사전순 키 순서 Leslie, Ron, Tom을 보존해야 한다. 그러려면 셀 오프셋을 재정렬해야 한다 —
  삽입 지점 뒤의 포인터들이 오른쪽으로 밀려 Ron 셀을 가리키는 새 포인터의 자리를 만든다**
  (3장, p.56).[^petrov2019]
- 요약하면 — **B-트리 레이아웃을 단순화하기 위해 각 노드가 페이지 하나를 차지한다고 가정한다.
  페이지는 고정 크기 헤더·셀 포인터 블록·셀로 이뤄진다. 셀은 키와, 자식 노드를 나타내는
  페이지로 가는 포인터 또는 딸린 데이터 레코드를 담는다. B-트리는 단순한 포인터 계층을 쓴다 —
  트리 파일 안에서 자식 노드를 찾는 데 페이지 식별자를, 페이지 안에서 셀을 찾는 데 셀 오프셋을
  쓴다** (3장, p.58).[^petrov2019]

## 지워진 자리를 되쓰기

- **페이지에서 항목을 제거한다고 실제 셀을 제거하고 다른 셀을 옮겨 해제된 공간을 다시 차지하게
  해야 하는 것은 아니다. 대신 셀을 삭제됐다고 표시하고, 인메모리 가용성 목록(availability
  list)을 해제된 메모리 양과 해제된 값을 가리키는 포인터로 갱신할 수 있다. 가용성 목록은
  해제된 세그먼트의 오프셋과 그 크기를 저장한다. 새 셀을 삽입할 때는 먼저 가용성 목록을 확인해
  들어갈 만한 세그먼트가 있는지 찾는다** (3장, p.57).[^petrov2019]
- 실물 이름 — **SQLite는 점유되지 않은 세그먼트를 프리블록(freeblocks)이라 부르고 페이지
  헤더에 첫 프리블록을 가리키는 포인터를 저장한다. 추가로 페이지 안의 총 가용 바이트 수를
  저장해, 조각 모음 뒤에 새 요소가 페이지에 들어갈 수 있는지 빠르게 확인한다** (3장,
  p.57).[^petrov2019]
- **들어갈 자리는 전략(strategy)에 따라 계산된다** (3장, pp.57–58):[^petrov2019]
  - **최초 적합(First fit)** — **첫 번째로 알맞은 세그먼트를 재사용한 뒤 남는 공간이 다른 어떤
    셀에도 너무 작아 사실상 낭비될 수 있으므로 오버헤드가 더 클 수 있다.**
  - **최적 적합(Best fit)** — **삽입 후 남는 나머지가 가장 작은 세그먼트를 찾으려 한다.**
- 그래도 안 되면 두 단계가 더 있다 — **새 셀이 들어갈 만큼의 연속된 바이트를 찾지 못했지만
  단편화된 바이트는 충분히 있으면, 살아 있는 셀을 읽어 다시 씀으로써 페이지를 조각 모음하고 새
  쓰기를 위한 공간을 회수한다. 조각 모음 뒤에도 자유 공간이 부족하면 오버플로
  페이지(overflow page)를 만들어야 한다** (3장, p.58).[^petrov2019]
- 지역성을 위한 변형도 있다 — **지역성을 개선하려고(특히 키의 크기가 작을 때) 일부 구현은 리프
  레벨에서 키와 값을 따로 저장한다. 키를 함께 두면 탐색 중의 지역성이 좋아진다. 찾는 키를 찾고
  나면 그 값은 대응하는 인덱스를 가진 값 셀에서 찾을 수 있다. 가변 크기 키에서는 추가 값 셀
  포인터를 계산해 저장해야 한다** (3장, p.58).[^petrov2019]
