# 차원 설계 프로세스 운영

이 페이지의 질문: **차원 모델링 작업을 조직에서 누구와, 어떤 절차와 산출물로 운영하는가?** 설계의 4단계 결정(비즈니스 프로세스 → grain → 차원 → 팩트) 자체는 [4단계 차원 설계](four-step-dimensional-design.md), 전체 프로젝트 맥락은 [Kimball DW/BI 라이프사이클](kimball-lifecycle.md), 모델링 기법은 [차원 모델링](../concepts/dimensional-modeling.md) 참고.

## 왜 버스 매트릭스에서 출발하는가

- 차원 모델링 프로세스의 핵심 입력은 **예비 버스 매트릭스와 상세 비즈니스 요구** 두 가지다. 핵심 산출물은 high-level 차원 모델, 상세 차원·팩트 테이블 설계, 이슈 로그다 (18장, p.430).[^kimball2013]
- 어느 행(row)을 모델링할지는 모델링 팀이 정하지 않는다 — 요구정의 마무리의 우선순위 결정 활동이 어떤 버스 매트릭스 행(= 비즈니스 프로세스)을 모델링할지 확정하고, 그 기반 위에서 설계를 시작한다 (18장, p.434).[^kimball2013]
- 첫 초안 작성이 수월한 이유도 버스 매트릭스 덕분이다 — 매트릭스가 이미 설계 범위와 후보 차원을 담고 있어, 초기 그래픽 모델을 매트릭스에서 유도한다 (18장, pp.429, 435).[^kimball2013]
- 버스 매트릭스는 출발점이면서 **살아 있는 산출물**이다. 상세 모델링 중 새 팩트 테이블·새 차원·차원의 분할/통합이 발견되면 매트릭스를 계속 갱신해야 한다 — 핵심 소통·계획 도구이기 때문이다. 상세 버스 매트릭스는 팩트 테이블별 grain과 지표 정보까지 담는다 (18장, p.439).[^kimball2013]

## 참여자와 워크숍 운영

- 최고의 차원 모델은 협업의 결과다 — 비즈니스 요구와 소스 시스템의 특이점 양쪽을 혼자 아는 사람은 없다. 데이터 모델러가 프로세스를 진행(facilitate)하고 산출물의 1차 책임을 지되, **비즈니스 대표와 데이터 스튜어드의 참여**가 결정적이다. 인원이 늘면 속도는 느려지지만 설계의 풍부함·완전성이 그 비용을 정당화한다 (18장, pp.429, 431).[^kimball2013]
- 소스 시스템 현실을 아는 사람을 반드시 포함하고, 물리 DBA·ETL 팀 대표도 참여시킨다 — ETL 처리를 줄이려고 3NF 개념을 들이대거나 복잡성을 BI 앱으로 미루려는 유혹을 현장에서 차단하기 위해서다. 목표는 ETL 처리 복잡성을 감수하고 BI 표현 계층의 단순성·예측 가능성을 얻는 교환이다 (18장, p.431).[^kimball2013]
- 외부 전문가를 쓴다면 몇 주 사라졌다 완성 설계를 들고 돌아오게 두지 말고 **팀과 함께 퍼실리테이션하게** 하라 — 팀 전체가 설계와 트레이드오프를 이해하고 다음 모델을 자력으로 다룰 수 있어야 한다 (18장, p.431).[^kimball2013]
- 사전 준비: 요구 문서 정독(건너뛰면 소스 데이터에만 끌려가는 모델이 나온다), 초기 문서화 도구는 스프레드시트(반복 수정이 빠르다; 모델이 굳으면 모델링 툴로 이관), 데이터 프로파일링(data profiling) 도구로 소스의 실제 내용·관계를 검증, 명명 규약(prime word–qualifier–class word 3부 구조가 흔하다) 확보 (18장, pp.432–433).[^kimball2013]
- 일정 운영: 종일 세션 대신 **주 3–4일, 2–3시간짜리 오전/오후 세션**이 현실적이다 — 세션 사이 시간에 소스 조사·요구 확인·문서 갱신을 한다. 설계 기간 전체 동안 전용 회의실을 확보한다 (18장, pp.433–434).[^kimball2013]
- 단일 비즈니스 프로세스의 모델링에 통상 **3–4주**가 걸린다. 기존 conformed dimension을 재사용할 수 있으면 노력이 팩트 테이블 지표에 집중되어 기간이 크게 준다 (18장, pp.430, 434).[^kimball2013]

## 프로세스 흐름: high-level 모델 → 상세 모델 → 검증 → 확정

- 전체 흐름(Figure 18-1): 준비 → high-level 차원 모델 → 상세 모델 개발 ⇄ 리뷰·검증(반복) → 최종 설계 문서화. 그림은 직선이지만 실제로는 고도로 반복적(iterative)이어서, 높은 수준에서 시작해 테이블·컬럼 단위로 파고들며 여러 번 왕복한다 (18장, p.430).[^kimball2013]
- **1단계 — high-level 모델(버블 차트)**: 대상 비즈니스 프로세스의 팩트·차원 테이블을 엔터티 수준 다이어그램으로 그려 grain과 차원을 비기술 청중에게도 명확히 보인다. 숙련 설계자가 혼자 만들어 와서 발표하는 방식은 권하지 않는다 — 팀 전체의 참여를 막기 때문이다 (18장, p.435).[^kimball2013]
- 버블 차트는 물리적 데이터 소스의 현실에 뿌리내려야 하며, 버스 매트릭스 한 행이 고유 grain의 팩트 테이블별로 **여러 장의 버블 차트**가 될 수 있다. grain을 선언하면 대부분의 주요 차원이 자연히 따라 나오고, 차원 선택이 역으로 grain 재선언을 유발하기도 한다 (18장, p.436).[^kimball2013]
- **2단계 — 상세 모델**: 테이블별·컬럼별로 정의한다. 차원 테이블부터 시작하고, 그중에서도 쉬운 것(날짜 차원이 단골 출발점)부터 — 이른 성공으로 팀이 프로세스를 익히고 협업을 배우게 하기 위해서다. 그다음 팩트 테이블로 간다 (18장, p.436).[^kimball2013]
- 상세 설계에서 정하는 것: 각 차원의 속성·정의·도메인 값·소스·변환 규칙, conformed dimension의 전사 합의(명명은 기술이 아니라 정치의 문제 — 거버넌스 스티어링 커미티가 개입할 수도 있다), grain에 충실한 팩트와 파생 지표, 그리고 **속성별 SCD(slowly changing dimension) 유형** (18장, pp.436–437, 442).[^kimball2013]
- 설계 중 발견되는 정의·변환 규칙·데이터 품질 이슈는 **이슈 추적 로그**에 담당자를 지정해 기록하고, 매 세션 끝에 퍼실리테이터가 신규 이슈를 검토·배정할 시간을 확보한다 (18장, p.439).[^kimball2013]
- 프로세스의 목표와 완료 조건은 원문으로:

> The primary goals are to create a model that meets the business requirements, verify that data is available to populate the model, and provide the ETL team with a solid starting source-to-target mapping. (18장, p.430)[^kimball2013]

## 검증: 3중 리뷰

- **IT 리뷰**: 통상 첫 리뷰. 참가자 다수가 3NF 사고로 차원 모델을 재단하려 들므로, 모델링 유파 논쟁에 시간을 쓰지 말고 리뷰 절차에 차원 모델링 교육을 선제적으로 포함한다. 버스 매트릭스 → 해당 행의 high-level 다이어그램 → 워크시트 상세 순으로 진행한다 (18장, p.440).[^kimball2013]
- **핵심 사용자 리뷰**: 핵심 비즈니스 사용자가 이미 모델링 팀원이면 생략 가능. 작은 조직에서는 IT 리뷰와 통합하기도 한다 (18장, p.440).[^kimball2013]
- **일반 비즈니스 사용자 리뷰**: 설계 리뷰인 만큼 교육이기도 하다. 버스 매트릭스 → 버블 차트 → 핵심 차원(고객·제품 등) 순으로 소개하고, 요구 문서에서 실제 질문을 뽑아 모델이 어떻게 답하는지 시연할 시간을 반드시 배정한다 (18장, pp.440–441).[^kimball2013]

## 확정 산출물

- 상세 모델링의 핵심 산출물은 **테이블별 설계 워크시트**다: 속성/팩트별 이름·설명·예시 값·SCD 유형, 팩트 테이블의 외래 키 관계·퇴화 차원(degenerate dimension), 팩트별 합산 가능/부분 합산 가능/합산 불가 규칙까지 담는다 (18장, pp.437–439).[^kimball2013]
- 워크시트는 **소스-투-타깃 매핑 문서의 첫걸음**이다 — 물리 설계 팀이 물리 테이블·컬럼명·데이터 타입·키 선언으로 살을 붙이고, 최종 소비자는 이 설계를 적재할 ETL 개발자다 (18장, pp.437, 439).[^kimball2013]
- 최종 설계 문서 구성: 프로젝트 개요, high-level 데이터 모델 다이어그램, 팩트·차원 테이블별 상세 설계 워크시트, 미해결 이슈 목록 (18장, p.441).[^kimball2013]
- 종착점: 비즈니스 요구와 데이터 현실 **양쪽에 대해 검증을 통과한** 차원 모델 (18장, p.442).[^kimball2013]

[^kimball2013]: Kimball & Ross 2013, 18장 "Dimensional Modeling Process and Tasks"
