하나의 질문: **저장된 데이터를 다시 조직하지 않고, 읽기 경로에서 할 일을 어떻게 덜어낼
것인가.**

Konieczny 8장의 셋째 범주인 **읽기 성능 최적화**(Read Performance Optimization)는
[데이터 저장 레이아웃 패턴](../concepts/data-storage-layout-patterns.md)의 넷과 짝을 이룬다 — 저쪽이
데이터를 **어디에 두느냐**를 고치고, 이쪽은 데이터를 그대로 둔 채 **읽기 전에 무엇을 알 수
있느냐**를 고친다. 저자의 표현으로 **이 절의 패턴들은 지금까지 제시한 데이터 조직 기법을
데이터 접근을 최적화하도록 확장한다** (8장, p.251).[^konieczny2025]

## 세 패턴이 공유하는 발상

- 장 도입부가 이 셋을 한 목록으로 예고한다 — 데이터 조직 말고 사용자 경험을 개선하는 다른
  접근들 (8장, p.234):[^konieczny2025]
  - **불필요한 데이터 관련 연산을 피하기 위해 메타데이터 계층을 활용하는 것** — Metadata Enhancer.
  - **비싼 연산을 한 번만 돌리고, 따라서 그것을 이후 독자를 위해 구체화하는 것** —
    Dataset Materializer.
  - **비싼 나열 연산을 피해 데이터 준비 단계를 단순화하는 것** — Manifest.
- 셋 다 **읽는 쪽의 일을 쓰는 쪽으로 옮긴다**는 점에서 같고, 옮기는 대상이 각각 통계·계산 결과·
  파일 목록이라는 점에서 다르다.

## Metadata Enhancer — 파일을 열기 전에 거른다

- 자리매김 — **읽기 성능 최적화를 위해 활용할 수 있는 첫 기법은 메타데이터를 쓴다. 이것이 Apache
  Parquet 같은 열 지향 파일 형식이 여러 해 동안 데이터 엔지니어링 분야에서 파괴적 변화로 여겨져
  온 이유 중 하나다** (8장, p.251).[^konieczny2025]
- 문제의 실물 — JSON 데이터셋을 이벤트 시각으로 수평 파티션해 배치 잡 시간을 줄였는데, 새로 합류한
  데이터 분석가들이 **같은 파티션된 데이터셋에서 한 파티션의 아주 작은 행 부분집합만 겨냥한다.
  파티션이 크므로 분석가들은 질의 실행 지연과, 사용한 만큼 내는 질의 서비스에 기대고 있어 늘어난
  클라우드 청구서를 불평한다** (8장, p.251).[^konieczny2025]
  - 진단이 순서 문제로 정리된다 — **첫 분석 뒤에 분석가들의 질의가 언제나 전체 데이터셋을 적재한
    다음에야 필터링 로직을 적용한다는 것을 알아냈다. 이 두 연산을 뒤집어 데이터셋을 질의 엔진에
    적재하기 전에 필터링 로직을 적용하고 싶다** (8장, p.251).[^konieczny2025]
- 해법 — **질의 실행 시간과 비용을 최적화하는 쉬운 방법은 무관한 데이터 파일 전부를 처리를 위해
  적재하기 전에 건너뛰는 것이다. 구현은 파일이나 데이터베이스에 저장된 레코드에 대한 통계를 수집하고
  영속화하는 것으로 이뤄진다** (8장, p.251).[^konieczny2025]
- 파일 쪽 구현의 성립 조건이 형식에 매인다 — **파일에 대한 Metadata Enhancer 구현은 Apache Parquet
  같은 열 지향 파일 형식에 적용되는데, 거기서는 각 데이터 파일이 추가 메타데이터를 담은 푸터(footer)를
  포함한다. 이름 그대로 열 지향 파일 형식은 각 파일에 열을 저장한다. 통계는 파일에 국소적이다
  (즉 그 파일의 값만 서술한다)** (8장, p.251).[^konieczny2025] 저자의 그림 8-7 예는 age 열에
  `min=19`·`max=50`·`nulls=0`이 붙은 것이다.
- 왜 싸지는지가 크기 비교로 주어진다 — **푸터는 파일이 생성될 때 데이터 생산자에 의해 자동으로
  계산되는 가능한 값의 범위를 포함한다. 사용자가 age 열을 술어의 일부로 질의할 때(예컨대
  `SELECT ... FROM table WHERE age > 50`) 질의 실행 엔진은 요청된 age가 파일 안에 있는지를
  메타데이터 푸터에서 간단히 확인할 수 있다. 푸터는 데이터 블록보다 작으므로 필터링 연산은 축소된
  데이터셋에 기대고 결과적으로 각 항목을 분석하려고 데이터의 더 큰 부분을 여는 것보다 훨씬 빠르다**
  (8장, p.252).[^konieczny2025]
  - 저자가 오버헤드를 숨기지 않는다 — **그렇다고는 해도 관련 레코드가 어디 있는지 알기 위해 모든
    푸터를 읽는 오버헤드는 여전히 있다. 그러나 그 오버헤드는 모든 데이터 파일을 읽는 것보다
    비교할 수 없이 작다** (8장, p.252).[^konieczny2025]
- 통계를 실제로 들여다보는 명령이 이 패턴의 대표 코드다 — Spark가 Parquet을 쓰고 나면
  **통계는 내부에서 만들어지고**, 그 내용은 Docker 이미지의 parquet-tools로 볼 수 있다 (8장,
  p.253):[^konieczny2025]

  ```sh
  docker run --rm -v "./output-parquet:/tmp/parquet" \
    hangxie/parquet-tools:v1.20.7 meta \
    /tmp/parquet/part-00001-3c52ae6f-aeea-4364-aac3-7fc69d63e898-c000.snappy.parquet
  ```

  - 출력은 열별 통계다 — `NumRowGroups`·`Type`·`Encodings`·`CompressedSize`·
    `UncompressedSize`·`NumValues`·`NullCount`·`MinValue`·`MaxValue`·`CompressionCodec`이
    한 항목으로 나온다 (8장, p.254, 예제 8-15).[^konieczny2025]

## 테이블 형식이 푸터 위에 더 얹는 것

- **Apache Parquet이 테이블 파일 형식이 쓰는 저장 형식이므로 이 패턴은 Delta Lake·Apache
  Iceberg·Apache Hudi에서 자동으로 가용하다. 그러나 Apache Parquet 통계에 더해 이 형식들은
  독자를 최적화할 수 있는 추가 메타데이터를 커밋 로그에 저장한다** (8장,
  p.252).[^konieczny2025]
- 그 추가분이 무엇인지 — **이 메타데이터 일부는 숫자로 이뤄지는데, 커밋에서 생성된 행 개수, 열별
  최소·최대값, 심지어 주어진 열의 `NULL` 개수 같은 것이다. 그 덕에 사용자는 원소 개수를 세거나
  존재하지 않는 값으로 필터하는 질의를 꽤 빠르게 수행할 수 있다** (8장,
  p.252).[^konieczny2025] Delta Lake 커밋 로그에서는 `numRecords`·`minValues`·`maxValues`·
  `nullCount`가 `add` 항목의 `stats`로 나온다 (8장, p.254, 예제 8-16).[^konieczny2025]
- 파일만의 이야기가 아니다 — **그러나 파일이 Metadata Enhancer가 적용되는 유일한 자리는 아니다.
  관계형 데이터베이스와 데이터 웨어하우스의 테이블에서도 같은 종류의 통계를 찾을 수 있다. 그
  맥락에서 통계는 흔히 별도 테이블에 위치하며, 질의 플래너가 그것을 활용해 가장 효율적인 실행
  계획을 만든다** (8장, pp.252–253).[^konieczny2025]

## 통계는 공짜가 아니고, 낡는다

- 저자의 총평 — **Metadata Enhancer의 단점을 찾기는 어렵지만, 이 추가 계층의 비용과 관련해 작은
  것이 하나 있다** (8장, p.253).[^konieczny2025]
- **오버헤드**(overhead) — **열 지향 파일 형식이라면 쓰기 시간에 통계를 만드는 것은 잡이 수행해야
  하는 추가 연산이다. 각 처리 열에 대해 잡이 설정된 통계를 유지해야 하므로 처리 시간에 약간 영향을
  줄 수 있다** (8장, p.253).[^konieczny2025]
  - 관계형 쪽은 성질이 다르다 — **추가로 관계형 데이터베이스와 데이터 웨어하우스에서는 데이터
    저장소가 통계를 최신으로 유지해야 한다. 그러지 않으면 실행 계획이 최적과 거리가 멀 수 있다.
    통계가 낡았을 때 이 문제를 다루려면 그것을 갱신하는 명령을 돌릴 수 있다** (8장,
    p.253).[^konieczny2025]
- **낡은 통계**(out-of-date statistics) — **관계형 데이터베이스와 데이터 웨어하우스에서 통계가
  자동으로 갱신되더라도 갱신 프로세스가 즉시는 아닐 수 있다. 흔히 그 실행은 마지막 갱신 이후
  수정된 행 개수 같은 특정 임계값에 의해 통제된다. 결과적으로 테이블이 임계값에 닿지 않는 작은
  변경을 이따금 겪는다면 통계는 시간이 지나며 낡을 수 있다** (8장,
  p.253).[^konieczny2025]
  - 수동 갱신에도 값이 붙는다 — **이 문제를 완화하려면 `ANALYZE TABLE` 같은 명령으로 통계를 수동
    갱신할 수 있다. 그러나 이것이 테이블을 처리하고 갱신된 통계를 생성하기 위해 데이터베이스에
    일시적 읽기 오버헤드를 더할 수 있음을 명심하라** (8장, p.253).[^konieczny2025]

## Dataset Materializer — 비싼 질의를 한 번만 계산한다

- 도입이 직관에 반한다 — **비싼 연산은 데이터 접근 개선에 또 다른 도전을 제기한다. 어떤 셔플과
  CPU 집약적 변환을 수반하는 질의를 써야 하고 같은 질의를 반복해서 돌려야 한다면 성능이 나빠질 수
  있다. 놀랍게도 데이터 읽기 성능을 개선하기 위해 데이터 중복에서 이득을 얻을 수 있다** (8장,
  p.254).[^konieczny2025]
- 문제의 실물 — 같은 데이터셋의 여러 파티션된 테이블을 질의해 지난 3주를 얻는 과정을 단순화하려고
  뷰를 만들었는데 **소비자들이 완전히 만족하지 못했다. 그들은 지연을 불평했고, 뷰가 매번 하부
  질의를 돌리므로 그럴 만하다** (8장, pp.254–255).[^konieczny2025]
- 해법 — **결과 계산이 느릴 때 가장 단순한 해법은 데이터를 구체화(materializing)해 문제를 피하는
  것이다. 그것이 Dataset Materializer 패턴이 하는 일이다** (8장,
  p.255).[^konieczny2025]
  - 구현 — **구체화해야 할 데이터셋을 식별하는 것으로 시작한다. 식별 단계 뒤에는 구체화를 구현해야
    한다. 전형적으로 이는 적절한 `SELECT` 문으로 데이터를 질의하고 어쩌면 `UNION`이나 `JOIN` 연산으로
    여러 데이터셋을 결합하는 것을 수반한다. 그렇게 만들어진 질의가 나중에 데이터셋을 구체화 뷰나
    데이터베이스의 테이블로 구체화하는 데 쓰인다** (8장, p.255).[^konieczny2025]

## 구체화 뷰냐 테이블이냐 — 자동 갱신과 저장 최적화의 갈림

- 저자가 세우는 판정 기준은 하나다 — **구체화 뷰와 테이블 기법 중 무엇을 골라야 하는가? 둘 사이의
  가장 큰 차이는 갱신(refresh)과 관련된다** (8장, p.255).[^konieczny2025]
- 구체화 뷰 쪽 — **구체화 뷰의 수동 갱신도 가능하지만, 현대적 데이터 웨어하우징 솔루션은 어떤
  기준 아래 자동 갱신도 지원한다. 예컨대 Amazon Redshift는 `CREATE MATERIALIZED VIEW` 문에
  정의된 `AUTO REFRESH YES` 옵션으로 이 기능을 지원한다** (8장, p.255).[^konieczny2025]
  - 자동의 대가는 예측 불가능성이다 — **그러나 그 갱신은 하부 테이블을 바꾼 직후 돌도록 되어 있지
    않다. 그 실행은 데이터베이스의 현재 작업부하나 갱신할 데이터의 크기에 달렸다. 그러므로 그
    로직은 자동화돼 있음에도 덜 예측 가능하다** (8장, p.255).[^konieczny2025]
  - BigQuery의 실물이 그 예측 불가능성을 수치로 준다 — 15분 갱신 간격을 옵션으로 준 구체화 뷰에
    대해 **주의할 점이 하나 있는데, 자동 갱신은 기반 테이블을 수정한 직후에 도는 것이 좀처럼
    보장되지 않는다는 것이다. BigQuery도 그러한데, 변경 후 5분 안에 갱신을 돌려야 하지만 용량이
    충분하지 않으면 갱신이 지연될 것이다** (8장, p.256).[^konieczny2025]
- 테이블 쪽 — **반면 구체화된 데이터셋의 저장으로 테이블을 쓰면 갱신에 대한 책임을 당신이 지게
  되고, 어떤 자동 갱신 기능도 활용할 가능성이 없다. 그 추가 작업의 대가로 추가 유연성을 얻는데,
  테이블은 파티션·버킷·정렬을 포함한 다른 저장 최적화 기법의 혜택을 받을 수 있고 그것들은 구체화
  뷰에는 가용하지 않을 수 있기 때문이다. 이 모두가 할 일을 늘리지만 더 많은 운영 유연성과 최적화
  기법도 준다** (8장, p.255).[^konieczny2025]
  - **이 갈림이 앞 페이지와 맞물린다** — 테이블을 고르면
    [저장 레이아웃 패턴](../concepts/data-storage-layout-patterns.md) 넷을 그 위에 얹을 수 있고, 구체화 뷰를
    고르면 자동 갱신을 얻는 대신 그 넷을 포기한다.

## 갱신 비용과 증분 갱신

- **갱신 비용**(refresh cost) — **뷰를 갱신해야 할 때마다 생성 질의를 다시 돌려야 한다. 이 설정
  질의가 비싸다면, 어쩌면 데이터 볼륨이나 연산 유형 때문에, 그것은 데이터베이스의 자원에 영향을
  주며 여기에는 다른 테이블과 상호작용하는 일반 사용자에게 가용한 자원도 포함된다** (8장,
  p.255).[^konieczny2025]
- 완화책과 그 성립 조건 — **이 문제를 넘어서려면 증분 갱신을 쓸 수 있다(즉 가장 최근의 변경만
  뷰에 통합하는 것). 이는 과거 데이터가 바뀌지 않고 갱신이 새 레코드만 덧붙이는 삽입 전용
  작업부하에 완벽히 들어맞는다** (8장, p.256).[^konieczny2025]
  - 제품 지원에 단서가 붙는다 — **현대적 데이터 웨어하우징 솔루션은 증분 갱신을 기본 제공한다.
    Databricks와 GCP BigQuery가 그렇다. 그러나 그들의 증분 갱신은 모든 SQL 연산을 지원하지 않고,
    때때로 여전히 데이터셋 전체를 갱신할 것이다** (8장, p.256).[^konieczny2025]
- 증분 판을 손으로 짜면 **두 패턴의 합성**이 된다 — 입력 테이블의 `insertion_time` 열이 각 행의
  쓰기 시각에 대응하고, **그 열로 이전 실행 이후 추가된 행만 질의해 기존 데이터셋과 결합한다는
  것이 발상이다. 보다시피 이 해법은 Incremental Loader 패턴과 Merger 패턴을 결합한다** (8장,
  p.257):[^konieczny2025]

  ```sql
  MERGE INTO dedp.visits_counter AS target
  USING (
   -- 2024-11-09T03:27:32 is the time after the previous insertion_time
   SELECT user_id, COUNT(*) AS visits FROM dedp.visits
    WHERE insertion_time > '2024-11-09T03:27:32' GROUP BY user_id
  ) AS input
  ON target.user_id = input.user_id
  WHEN MATCHED THEN UPDATE SET count = count + input.visits
  WHEN NOT MATCHED THEN INSERT (user_id, count) VALUES (input.user_id, input.visits)
  ```

  - 수동 갱신 쪽 대표는 PostgreSQL의 `REFRESH MATERIALIZED VIEW ... WITH DATA` 한 줄이다 (8장,
    p.256).[^konieczny2025]

## 구체화가 뚫는 접근 통제 구멍

- **데이터 접근**(data access) — **구체화된 데이터셋이 여러 테이블을 결합하므로 보존이나 접근
  설정을 포함한 일관된 데이터 관리를 적용하기가 어려울 수 있다. 전형적으로 사용자가 구성 테이블 중
  하나에 접근 권한이 없다면 그 뷰에 대한 접근도 계속 거부해야 하거나, 가능하다면 Fine-Grained
  Accessor 패턴의 선택지 중 하나를 구현해야 한다** (8장, p.256).[^konieczny2025]
  - 그 패턴 쪽 정본은
    [세밀한 접근과 자격 증명 패턴](../concepts/fine-grained-access-and-credential-patterns.md)이다.
    **구체화는 접근 통제를 무효로 만들 수 있는 조작이라는 것**이 이 결과 항목의 요지다 — 여러
    테이블의 값이 한 객체로 합쳐지는 순간, 원래 테이블에 걸려 있던 권한은 따라오지 않는다.
- **데이터 저장 오버헤드**(data storage overhead) — **구체화는 접근을 최적화하지만 저장과
  최적화를 맞바꾼다. 저장이 걱정이라면 뷰의 데이터셋 중 일부만 구체화되고 나머지는 일반적인
  재계산 가능한 부분으로 남는 혼합 구현을 택할 수 있다** (8장, p.256).[^konieczny2025]

## Manifest — 나열을 파일 하나로 대체한다

- 문제의 성질이 API 호출 수다 — **마지막 읽기 접근 성능 도전은 데이터 나열(listing)에 관한
  것인데, 특히 파일이 많은 오브젝트 스토어에서 느릴 수 있다. 많은 API 호출로 이어지기 때문이다.
  나열 연산을 병렬화해 이 문제를 완화하려 할 수도 있지만, 더 나은 방법이 있다** (8장,
  p.257).[^konieczny2025]
- 문제의 실물 — 오브젝트 스토어의 Parquet 데이터셋으로 배치 잡이 잘 돌고 클라우드 청구서도 줄었는데,
  회사가 데이터 웨어하우스 계층을 요구했다. 분석가 팀에 그 데이터셋을 노출했더니 **첫 테스트에서
  실행 시간이 배치 잡 생산자만큼 좋지 않았다. 가장 느린 연산이 오브젝트 스토어에서 적재할 파일을
  나열하는 것임을 알아냈고, 이 비싼 단계를 피하고 싶다** (8장, p.257).[^konieczny2025]
- 해법의 한 줄 — **반복되는 나열 연산 문제를 넘어서려면 파일을 한 번만 나열하거나, 데이터
  생산자가 파일명을 미리 기록할 수 있다면 아예 나열하지 않는 편이 낫다. 그것이 Manifest 패턴의
  전제다** (8장, p.257).[^konieczny2025]
- 첫 구현이 이미 우리가 쓰는 것들이다 — **Delta Lake·Apache Iceberg·Apache Hudi 같은 테이블 파일
  형식이 이 패턴의 첫 구현이다. 그것들은 주어진 트랜잭션 안에서 생성된 파일 목록을 메타데이터
  위치에 저장된 커밋 로그에 쓴다. 그 덕에 독자가 데이터 파일에 접근해야 할 때 하부 저장소를 전혀
  나열하지 않고 커밋 파일에서 그것들을 간단히 가져올 수 있다. Manifest 패턴의 맥락에서 이 커밋
  로그 파일은 매니페스트 파일로 작용하는데, 데이터에 대해 필요하고 중요한 모든 정보를 제공하는
  파일이라는 뜻이다** (8장, p.258).[^konieczny2025]
- 손으로 만드는 쪽도 자리가 있다 — **자동 관리되는 매니페스트의 대안은 사전 나열 연산을 요구할 수
  있는 수동 생성 매니페스트다. 여러 다른 독자가 같은 데이터셋에서 동작한다면 특히 유용할 수 있는데,
  예컨대 6장의 팬아웃 패턴의 일부로서 그렇다** (8장, p.258).[^konieczny2025] 팬아웃 쪽은
  [데이터 흐름 의존 패턴](../concepts/data-flow-dependency-patterns.md)에 있다.
- Delta Lake에서 매니페스트를 뽑는 것은 함수 하나다 — **생성된 매니페스트는 Delta Lake 테이블의
  가장 최근 버전(스냅샷)이 쓰는 모든 파일을 담는다** (8장, p.259):[^konieczny2025]

  ```python
  devices_table = DeltaTable.forPath(spark_session, DemoConfiguration.DEVICES_TABLE)
  devices_table.generate('symlink_format_manifest')
  ```

  - 그 다음이 두 제품을 잇는 자리다 — BigQuery의 `CREATE EXTERNAL TABLE`에서
    `file_set_spec_type = 'NEW_LINE_DELIMITED_MANIFEST'`로 그 매니페스트를 가리켜
    **Delta Lake 데이터셋에 대한 이른바 외부 테이블을 만든다** (8장,
    p.259).[^konieczny2025]

## 매니페스트는 읽기만이 아니라 쓰기에서도 일한다

- **데이터 읽기에서의 유용성에 더해 매니페스트는 쓰기에서도 결정적 역할을 할 수 있다. Amazon
  Redshift는 새 데이터를 테이블에 적재하는 `COPY` 명령에서 매니페스트 파일을 쓴다. 각 적재
  연산마다 업로드할 파일의 전용 목록을 담은 다른 매니페스트 파일을 정의할 수 있다. 이 구체화는
  4장에 있는 것 같은 멱등적 파이프라인을 구현하는 데 엄청나게 도움이 될 수 있다** (8장,
  p.258).[^konieczny2025]
  - 곧 **`COPY`가 무엇을 적재할지를 목록 파일로 고정하면 재생해도 같은 파일만 적재된다** — 저자는
    이를 **적재 전에 매니페스트를 만들어 잡의 실행에 결부시키면 재생되는 잡의 어느 실행에서도 같은
    매니페스트 파일을 쓸 수 있다**고 적는다 (8장, p.259).[^konieczny2025] 멱등성 쪽 정본은
    [멱등적 쓰기 패턴](../concepts/idempotent-write-patterns.md)이다.
  - 클라우드 간 복사에도 같은 것이 쓰인다 — **GCP의 Storage Transfer Service에도 비슷한 구현이
    있다. 이 서비스는 다른 클라우드 저장소에서 GCS로 파일을 복사하기 위해 매니페스트 나열에
    기댄다** (8장, p.258).[^konieczny2025]

## 매니페스트가 기가바이트로 자랄 때

- **복잡성**(complexity) — **매니페스트 생성 단계를 더해야 한다면 실행 흐름에 약간의 추가 복잡성을
  더하게 된다. 그러나 매니페스트 생성은 최근에 쓰인 파일을 나열하는 것으로 이뤄지는 다소 단순한
  연산이다. 파이프라인에 이 추가 복잡성을 두는 것이 느리고 예측 불가능한 나열 액션을 여러 번 돌리는
  것보다 받아들이기 쉬울 것이다** (8장, p.258).[^konieczny2025]
- **크기**(size) — **매니페스트는 정말 커질 수 있다. 입력 위치에 작은 파일이 많거나 데이터
  생산자가 연속적인 스트리밍 잡이라면 특히 그렇다. 그 경우 수 기가바이트 크기의 매니페스트를 보는
  것이 흔하다. 어떤 구현은 매니페스트 파일에 최대 크기 한계를 두거나 파일에 있는 항목에 대한 보존
  설정을 둘 수 있다** (8장, p.258).[^konieczny2025]
- 저자가 드는 실제 사고 — **크기 문제는 Apache Spark Structured Streaming 초기에 존재했다.
  프레임워크로 파일을 쓸 때 출력 위치에 새 파일을 만드는 것에 더해 잡이 그 이름을 매니페스트 파일에
  더하고 있었다. 시간이 지나며 매니페스트가 계속 자랐고, 때때로 잡이 아예 재시작할 수 없었는데
  매니페스트가 너무 커서 복원할 수 없었기 때문이다. 그 뒤 이 문제는 수정됐다(SPARK-27188 참조)**
  (8장, p.258).[^konieczny2025]
  - **이 사고가 이 패턴의 성질을 드러낸다** — 매니페스트는 나열 비용을 없애는 대신 **상태를 하나
    더 만든다**. 그 상태는 데이터와 함께 자라고, 자란 상태가 복구 경로에 놓이면 나열보다 나쁜
    실패가 된다.
