## 추론 서버와 추론 서비스

- 두 이름의 경계 — **프로덕션에서 모델 추론을 돌리는 구성 요소를 추론 서버(inference server)라
  부른다. 그것은 이용 가능한 모델들을 호스팅하고 필요한 하드웨어에 접근한다. 애플리케이션의
  요청(예: 사용자 프롬프트)에 근거해 그것은 적절한 모델을 실행하도록 자원을 배분하고 응답을
  사용자에게 돌려준다. 추론 서버는 더 넓은 추론 서비스(inference service)의 일부이고, 추론
  서비스는 요청이 추론 서버에 닿기 전에 그것을 받고 라우팅하고 어쩌면 전처리하는 것도
  책임진다** (9장, p.406, Figure 9-1).[^huyen2025]
- 누가 이 일을 하는가 — **OpenAI와 구글이 제공하는 것 같은 모델 API가 추론 서비스다. 이런 서비스
  중 하나를 쓴다면 이 장에서 논의되는 기법의 대부분을 직접 구현하지 않을 것이다. 그러나 모델을 직접
  호스팅한다면 그 추론 서비스를 만들고 최적화하고 유지하는 것을 책임지게 된다** (9장,
  p.407).[^huyen2025]

## 최적화는 병목을 찾는 일이다

- **최적화는 병목을 식별하고 그것을 다루는 일이다. 예컨대 교통을 최적화하려고 도시 계획가는 정체
  지점을 식별하고 정체를 완화할 조치를 취할 수 있다. 마찬가지로 추론 서버는 그것이 서빙하는 추론
  워크로드의 계산 병목을 다루도록 설계되어야 한다. 주된 계산 병목은 둘인데, 컴퓨트 바운드
  (compute-bound)와 메모리 대역폭 바운드(memory bandwidth-bound)다** (9장, p.407).[^huyen2025]

## 두 병목의 정의

- 정의 두 개 (9장, p.407):[^huyen2025]
  - **컴퓨트 바운드 — 완료까지의 시간이 그 과업에 필요한 계산으로 정해지는 과업을 가리킨다. 예컨대
    비밀번호 복호화는 암호 알고리즘을 깨는 데 요구되는 집중적인 수학 계산 때문에 통상 컴퓨트
    바운드다.**
  - **메모리 대역폭 바운드 — 이 과업들은 시스템 안의 데이터 전송률, 예컨대 메모리와 프로세서 사이의
    데이터 이동 속도로 제약된다. 예컨대 데이터를 CPU 메모리에 저장하고 모델을 GPU에서 훈련한다면
    CPU에서 GPU로 데이터를 옮겨야 하고 이는 오래 걸릴 수 있다. 이는 대역폭 바운드
    (bandwidth-bound)로 줄여 쓸 수 있다. 문헌에서 메모리 대역폭 바운드는 흔히 메모리 바운드
    (memory-bound)라고 불린다.**

## 메모리 바운드라는 말이 두 가지를 가리킨다

- 저자가 상자로 떼어 둔 용어 모호성이다 — **메모리 바운드는 어떤 사람들이 메모리 대역폭 대신 메모리
  용량으로 완료까지의 시간이 제약되는 과업을 가리키는 데도 쓴다. 이는 하드웨어가 그 과업을 감당할
  충분한 메모리를 갖지 못할 때 일어나는데, 예컨대 기계가 인터넷 전체를 저장할 메모리를 갖지 못할
  때다. 이 메모리는 어디서나 엔지니어가 알아보는 오류로 흔히 드러난다: OOM, out-of-memory** (9장,
  p.408).[^huyen2025]
- 그런데 용량 제약도 결국 대역폭 문제라는 것이 저자의 결론이다 — **그러나 이 상황은 흔히 과업을 더
  작은 조각으로 쪼개 완화할 수 있다. 예컨대 GPU 메모리에 제약되어 모델 전체를 GPU에 넣을 수 없다면
  모델을 GPU 메모리와 CPU 메모리에 걸쳐 쪼갤 수 있다. 이 쪼개기는 CPU와 GPU 사이의 데이터 전송에
  걸리는 시간 때문에 계산을 느리게 만들 것이다. 그러나 데이터 전송이 충분히 빠르면 이는 덜 문제가
  된다. 따라서 메모리 용량 제한은 실은 메모리 대역폭에 더 가까운 문제다** (9장,
  p.408).[^huyen2025]
- 각주가 짚는 출신별 용법 — **일화적으로 저자는 시스템 배경에서 온 사람들(예: 최적화 엔지니어와
  GPU 엔지니어)이 memory-bound를 bandwidth-bound를 가리키는 데 쓰고, AI 배경에서 온 사람들(예:
  ML·AI 엔지니어)이 memory-bound를 메모리 용량 바운드를 가리키는 데 쓴다는 것을 발견한다** (9장,
  p.408 각주 3).[^huyen2025] 이 각주는 원문에 `use to memory-bound to refer to memory
  capacity-bound`로 인쇄되어 있다 — 앞 절의 `use memory-bound to refer to`와 대구가 되어야 할
  자리라 `to`가 잘못 들어간 것으로 보이나 책 안에 확인할 근거가 없다. #hypothesis

## 산술 강도와 루프라인

- 개념의 출처와 기준 — **컴퓨트 바운드 또는 메모리 대역폭 바운드라는 개념은 논문 "Roofline"
  (Williams et al., 2009)에서 도입되었다. 수학적으로 연산은 그것의 산술 강도(arithmetic intensity)에
  근거해 컴퓨트 바운드인지 메모리 대역폭 바운드인지 분류될 수 있는데, 산술 강도란 메모리 접근
  바이트당 산술 연산의 수다. NVIDIA Nsight 같은 프로파일링 도구가 워크로드가 컴퓨트 바운드인지 메모리
  대역폭 바운드인지 알려 주는 루프라인 차트를 보여 줄 것이다. 이 차트는 지붕을 닮았기 때문에
  루프라인(roofline) 차트다. 루프라인 차트는 하드웨어 성능 분석에서 흔하다** (9장,
  p.408).[^huyen2025]
  - 각주 — **Roofline 논문은 memory-bound라는 용어를 메모리 대역폭 바운드를 가리키는 데
    쓴다** (9장, p.408 각주 4).[^huyen2025]
  - 도판 설명 — **루프라인 차트는 연산이 컴퓨트 바운드인지 메모리 대역폭 바운드인지 시각화하는 데
    도움이 될 수 있다. 이 그래프는 로그 척도다** (9장, p.409, Figure 9-2 설명).[^huyen2025] 가로축은
    산술 강도(FLOP/byte), 세로축은 성능(FLOP/s)이고 왼쪽이 memory bound region, 오른쪽이 compute
    bound region이다 (9장, p.409, Figure 9-2).[^huyen2025]

## 병목이 다르면 처방이 다르다

- **서로 다른 최적화 기법은 서로 다른 병목을 완화하는 것을 목표로 한다. 예컨대 컴퓨트 바운드
  워크로드는 그것을 더 많은 칩에 펼치거나 더 많은 계산력(예: 더 높은 FLOP/s 수)을 가진 칩을 활용해
  빨라질 수 있다. 메모리 대역폭 바운드 워크로드는 더 높은 대역폭을 가진 칩을 활용해 빨라질 수
  있다** (9장, p.408).[^huyen2025]
- 구조와 워크로드가 병목을 가른다 — **서로 다른 모델 구조와 워크로드는 서로 다른 계산 병목을 낳는다.
  예컨대 Stable Diffusion 같은 이미지 생성기의 추론은 통상 컴퓨트 바운드인 반면, 자기회귀 언어
  모델의 추론은 통상 메모리 대역폭 바운드다** (9장, p.409).[^huyen2025]

## 프리필은 컴퓨트, 디코드는 대역폭

- 2장의 두 단계에 병목을 붙인다 (9장, p.409):[^huyen2025]
  - **프리필(Prefill) — 모델이 입력 토큰을 병렬로 처리한다. 한 번에 몇 개의 토큰이 처리될 수
    있는지는 하드웨어가 주어진 시간에 실행할 수 있는 연산의 수로 제한된다. 따라서 프리필은 컴퓨트
    바운드다.**
  - **디코드(Decode) — 모델이 한 번에 출력 토큰 하나를 생성한다. 높은 수준에서 이 단계는 통상 큰
    행렬(예: 모델 가중치)을 GPU로 적재하는 것을 수반하고, 이는 하드웨어가 얼마나 빨리 데이터를
    메모리로 적재할 수 있는지로 제한된다. 따라서 디코딩은 메모리 대역폭 바운드다.**
  - 각주 — **프리필은 사실상 트랜스포머 모델을 위한 초기 KV 캐시를 채운다** (9장, p.409 각주
    5).[^huyen2025]
  - 도판 설명 — **자기회귀 언어 모델은 추론에 두 단계를 따른다: 프리필과 디코드. `<eos>`는 시퀀스
    끝 토큰을 나타낸다** (9장, p.410, Figure 9-3 설명).[^huyen2025]
- 그래서 프로덕션에서 갈라 둔다 — **프리필과 디코드는 계산 프로파일이 다르기 때문에 프로덕션에서
  흔히 별도 기계로 분리된다** (9장, p.410).[^huyen2025]

## 무엇이 그 양을 정하는가

- **LLM 추론 서버에서 프리필과 디코딩 계산의 양에 영향을 주는, 따라서 그 병목에 영향을 주는 요인에는
  컨텍스트 길이·출력 길이·요청 배칭 전략이 포함된다. 긴 컨텍스트는 통상 메모리 대역폭 바운드
  워크로드를 낳지만, 이 장에서 나중에 논의되는 것 같은 영리한 최적화 기법이 이 병목을 없앨 수
  있다** (9장, p.410).[^huyen2025]
- 지금의 판세 — **집필 시점 기준 트랜스포머 구조의 만연과 기존 가속기 기술의 한계 때문에 많은 AI와
  데이터 워크로드가 메모리 대역폭 바운드다. 그러나 미래의 소프트웨어와 하드웨어 발전이 AI와 데이터
  워크로드를 컴퓨트 바운드로 만들 수 있을 것이다** (9장, p.410).[^huyen2025]
