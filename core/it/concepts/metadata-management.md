## 메타데이터란 무엇인가

- "데이터에 관한 데이터"라는 통상 정의는 쓸모가 적다. 대안 정의는 원문을 직인용한다 (§10.1, pp.316–317).[^linstedt2016]

> metadata is all data about other data that is *"needed to promote its administration and use"*

- 데이터 웨어하우징에서 자주 쓰는 다른 분류는 백룸/프런트룸 구분이다: 백룸 메타데이터(back room metadata)는 프로세스 관련으로 추출·정제·적재 과정을 기술하며 DBA·웨어하우스 팀의 적재를 돕고, 프런트룸 메타데이터(front room metadata)는 기술적(descriptive) 성격으로 쿼리·리포트 도구에서 최종 사용자를 돕는다 (§10.1, p.317).[^linstedt2016]
- 메타데이터 관리의 궁극 목표는 데이터 웨어하우스의 모든 산출물(artifact)을 기술하는 것이다. 관계형 테이블 하나만 해도 레코드 레이아웃, 볼륨(volumetric), 인덱스, 적재 일정, 사용처·의존성, 참조 무결성, 일반 문서 등이 캡처 대상이다 (§10.1, p.317).[^linstedt2016]
- 메타데이터는 시간이 지나며 변한다 — 비즈니스 의미가 바뀌고(business), 원천 시스템이 바뀌고(technical), 데이터 웨어하우스 자체가 바뀐다(process execution). 추적할 메타데이터 목록은 각 팀이 조직·프로젝트의 필요에 맞게 조정해야 한다 (§10.1, p.318).[^linstedt2016]

## 메타데이터 3종 분류

- Data Vault 2.0 아키텍처가 채택하는 분류는 세 범주다 (§10.1, p.317):[^linstedt2016]
  - 비즈니스 메타데이터(business metadata): 데이터가 비즈니스에 갖는 의미를 기술한다. Meta Mart가 담는다.
  - 기술 메타데이터(technical metadata): 데이터 타입, 리니지(lineage), 프로파일링 결과 등 데이터의 기술적 측면을 기술한다. 역시 Meta Mart가 담는다.
  - 프로세스 실행 메타데이터(process execution metadata): 실행 중인 ETL 프로세스의 통계 — 원천에서 읽고 목적지에 쓴 레코드 수, 거부된 행 수, 적재 소요 시간을 제공한다. Metrics Vault가 담고, 오류 정보는 Error Mart가 추적한다.

### 비즈니스 메타데이터

- 비즈니스 정의 관련: 비즈니스 컬럼 이름(약어 풀이 포함), 속성·테이블·객체별 비즈니스 정의, 온톨로지·택소노미(비즈니스 객체 간 관계·계층·분류 — 보통 MDM 시스템에 저장), 물리 테이블·컬럼 이름과 비즈니스 이름의 대응, 기술 번호 체계 (§10.1.1, p.318).[^linstedt2016]
- 비즈니스 정의를 제공할 수 없는 항목은 비즈니스에 분석 가치가 없다는 신호이며 정보 마트에서 제거할 수 있다 (§10.1.1, p.318).[^linstedt2016]
- 원천 시스템 관련: 비즈니스 용어로 된 레코드 소스 기술(서버·인스턴스 참조가 아니라 "Flight Tracking Database"처럼, 가능한 한 상세하게), 테이블 명세(목적·볼륨·컬럼·키), 하드 예외 처리 규칙(hard rule — 기술적 이슈 대응), 원천 속성의 비즈니스 의미, 소프트 비즈니스 규칙(soft rule — 원천 시스템이 데이터를 수정·생성·정제하는 규칙) (§10.1.1, p.319).[^linstedt2016]
- 누가 비즈니스 메타데이터를 책임질지(요구사항 분석가, 원천 시스템 분석가, 데이터 모델러)는 논쟁거리지만, 어떤 비즈니스 메타데이터를 어디서 관리할지는 웨어하우스 팀이 반드시 결정해야 한다 (§10.1.1, p.318).[^linstedt2016]

### 기술 메타데이터

- 웨어하우스 팀이 만들고 유지하며 가장 많이 혜택을 보는 메타데이터로, 대상은 원천 시스템(데이터베이스·플랫 파일 위치, 스테이징 테이블), 데이터 모델(물리·논리 — 엄밀히는 메타데이터가 아니지만 귀중한 자산), 데이터 정의(테이블·컬럼·타입·도메인·참조 무결성·제약·기본값·트리거), 비즈니스 규칙의 기술적 정의(하드/소프트 구분 유지, 암복호화 요구 포함), 볼류메트릭스(테이블 크기·성장 패턴 — 6–12개월 하드웨어 조달 주기 예측), 온톨로지·택소노미(약어, 비즈니스 키 지정, 계층, 구조 수준의 온톨로지 간 매칭), 데이터 품질(표준화·품질 지표) (§10.1.2, pp.319–320).[^linstedt2016]
- 명명 규약도 메타데이터의 한 형태다: 테이블 이름의 접두사·접미사(예: 허브·링크·새틀라이트별 약어, 새틀라이트의 원천 시스템 약어)는 엔터티 타입 정보를 이름에 부호화해 모든 SQL 도구에서 보이게 한다. 단점은 이 메타데이터가 엔터티에 부착된 전용 메타데이터로는 쉽게 조회되지 않는다는 것이다 (§10.2.2, pp.325, 328).[^linstedt2016]

### 프로세스 실행 메타데이터

- 비즈니스·기술 메타데이터가 비즈니스나 원천 애플리케이션에서 제공되는 것과 달리, 프로세스 실행 메타데이터는 웨어하우스 팀이 생성하며 유지보수를 위한 ETL 처리 통찰을 제공한다. 네 유형: 제어 흐름(control flow) 메타데이터(데이터 리니지 파악·디버깅), 데이터 흐름(data flow) 메타데이터(변환별 처리·거부 레코드 수와 성능), 패키지 메타데이터(실행 시간 요약), 프로세스 메타데이터(패키지를 기동한 스케줄러 프로세스 정보) (§10.1.3, p.320).[^linstedt2016]
- 이 메타데이터는 프로세스 실행 시 Metrics Vault에 담기며, Meta Mart의 비즈니스·기술 메타데이터와는 통상 분리된다 (§10.1.3, p.320).[^linstedt2016]

### DMBOK의 네 범주 — 나란히 놓기

Data Vault 2.0의 3종 분류와 층위가 다른 분류가 하나 더 있다. Reis & Housley는 DMBOK을 따라
넷으로 가르는데, 앞의 셋은 위 분류와 대체로 겹치고 **참조 메타데이터**가 추가된다.

- 저자들이 데이터 엔지니어에게 유용하다고 꼽는 네 범주는 **비즈니스 메타데이터·기술
  메타데이터·운영 메타데이터·참조 메타데이터**다 (2장, p.53).[^reis2022]
- **비즈니스 메타데이터(business metadata)는 데이터가 업무에서 쓰이는 방식과 관련되며, 업무·
  데이터 정의, 데이터 규칙과 로직, 데이터가 어디서 어떻게 쓰이는지, 그리고 데이터 소유자를
  포함한다** (2장, p.53).[^reis2022]
  - 쓰임의 실물 — **데이터 엔지니어는 비즈니스 메타데이터로 누가·무엇을·어디서·어떻게라는
    비기술적 질문에 답한다. 고객 판매 분석용 파이프라인을 만들라는 과업을 받았다 하자.
    그런데 고객이란 무엇인가? 지난 90일 안에 구매한 사람인가? 사업이 열려 있던 어느 때든
    구매한 사람인가? 데이터 엔지니어는 "고객"이 어떻게 정의되는지 찾아보려고 비즈니스
    메타데이터(데이터 사전이나 데이터 카탈로그)를 참조한다** (2장, p.53).[^reis2022]
- **기술 메타데이터(technical metadata)는 데이터 엔지니어링 수명 주기 전반의 시스템이 만들고
  쓰는 데이터를 서술한다. 데이터 모델과 스키마, 데이터 계보, 필드 매핑, 파이프라인 워크플로가
  여기 든다** (2장, pp.53–54).[^reis2022] 저자들이 꼽는 흔한 세 유형 (2장, p.54):[^reis2022]
  - **파이프라인 메타데이터(흔히 오케스트레이션 시스템에서 생산된다)** — **오케스트레이션은
    여러 시스템에 걸쳐 워크플로를 조율하는 중심 허브다. 오케스트레이션 시스템에서 포착된
    파이프라인 메타데이터는 워크플로 스케줄, 시스템·데이터 의존, 설정, 연결 상세 등을
    제공한다.**
  - **데이터 계보(data lineage)** — **시간에 따른 데이터의 기원과 변경, 그 의존을 추적한다.**
  - **스키마(schema)** — **데이터베이스·데이터 웨어하우스·데이터 레이크·파일시스템 같은
    시스템에 저장된 데이터의 구조를 서술하며, 서로 다른 저장 시스템을 가르는 핵심 차별점
    중 하나다. 예컨대 객체 저장소는 스키마 메타데이터를 관리하지 않으므로 이것은 메타스토어
    (metastore)에서 관리돼야 한다. 반면 클라우드 데이터 웨어하우스는 스키마 메타데이터를
    내부에서 관리한다.**
- **운영 메타데이터(operational metadata)는 여러 시스템의 운영 결과를 서술하며 프로세스에 관한
  통계, 잡 ID, 애플리케이션 런타임 로그, 프로세스에 쓰인 데이터, 오류 로그를 포함한다. 데이터
  엔지니어는 운영 메타데이터로 프로세스가 성공했는지 실패했는지, 그 프로세스에 관련된 데이터가
  무엇인지 판단한다** (2장, p.54).[^reis2022] 위 [프로세스 실행 메타데이터](#프로세스-실행-메타데이터)와
  같은 것을 가리킨다.
  - 남은 문제 — **오케스트레이션 시스템은 운영 메타데이터의 제한된 그림만 줄 수 있고, 그것은
    여전히 여러 시스템에 흩어지는 경향이 있다. 더 나은 품질의 운영 메타데이터와 더 나은
    메타데이터 관리에 대한 필요가 차세대 오케스트레이션·메타데이터 관리 시스템의 주요
    동기다** (2장, p.54).[^reis2022]
- **참조 메타데이터(reference metadata)는 다른 데이터를 분류하는 데 쓰이는 데이터다. 룩업
  데이터(lookup data)라고도 한다. 표준 예는 내부 코드, 지리 코드, 측정 단위, 내부 달력
  표준이다. 참조 데이터의 상당수는 전적으로 내부에서 관리되지만 지리 코드 같은 항목은 표준
  외부 참조에서 올 수 있다. 참조 데이터는 본질적으로 다른 데이터를 해석하는 표준이므로,
  바뀐다면 그 변경은 시간에 걸쳐 천천히 일어난다** (2장, p.54).[^reis2022]

### 자동 생성과 사람 생성

- 또 하나의 축 — **메타데이터를 자동 생성(autogenerated)과 사람 생성(human generated)이라는
  두 주요 범주로 나눈다. 2022년 저술 시점의 데이터 엔지니어링은 자동화를 중심으로 돌지만, 메타데이터 수집은
  흔히 수동이고 오류가 나기 쉽다** (2장, p.52).[^reis2022]
- 도구가 하는 일 — **데이터 카탈로그, 데이터 계보 추적 시스템, 메타데이터 관리 도구의 확산이
  보인다. 도구는 데이터베이스를 크롤해 관계를 찾고, 데이터 파이프라인을 모니터링해 데이터가
  어디서 와서 어디로 가는지 추적할 수 있다** (2장, p.52).[^reis2022]
- 남는 한계 — **핵심 도전은 남아 있다. 특히 상호운용성과 표준이 여전히 부족하다. 메타데이터
  도구는 데이터 시스템에 대한 커넥터와 메타데이터를 공유하는 능력만큼만 좋다** (2장,
  pp.52–53).[^reis2022]
- 사람을 빼면 안 되는 이유 — **자동화된 메타데이터 도구가 사람을 완전히 루프 밖으로 내보내서는
  안 된다. 데이터에는 사회적 요소가 있다. 각 조직은 프로세스·데이터셋·파이프라인을 둘러싼
  사회적 자본과 지식을 축적한다. 사람 지향 메타데이터 시스템은 메타데이터의 사회적 측면에
  초점을 둔다. 그런 도구는 데이터 소유자·데이터 소비자·도메인 전문가를 드러낼 자리를 제공해야
  한다. 문서와 내부 위키 도구가 메타데이터 관리의 핵심 토대를 제공하지만, 이 도구들은
  자동화된 데이터 카탈로깅과도 통합돼야 한다** (2장, p.53).[^reis2022]

## 저장소별 역할 구분: 무엇을 재고 어디에 두나

[데이터 볼트 아키텍처](../concepts/data-vault-architecture.md)에는 Raw Data Vault 경유가 아닌 독립 구성 요소가 여럿 있고, 각자 담는 것이 다르다.

| 구성 요소 | 담는 것 | 위치·원천 | 모델 |
|---|---|---|---|
| Meta Mart | 비즈니스·기술 메타데이터 | 독립 정보 마트 — Raw Data Vault에서 조달하지 않음 | 차원 모델 또는 3정규형, 항상 실체화 |
| Metrics Vault | 프로세스 실행 메타데이터 원시 데이터(ETL 지표) | EDW 계층, Data Vault 모델의 통합된 일부 | Data Vault 2.0 모델 |
| Metrics Mart | 성능 분석용으로 가공된 지표 정보 | 정보 전달 계층, 주로 Metrics Vault에서 조달 | 분석 필요에 맞는 모델(차원 등), 가상화 선호 |
| Error Mart | 거부·미처리 레코드의 원시 데이터 | 독립 정보 마트 — Raw Data Vault에서 조달하지 않음 | 주로 차원 모델 |

### Meta Mart

- Meta Mart는 Data Vault 2.0 아키텍처에서 비즈니스·기술 메타데이터 수집의 중심이다. Raw Data Vault에서 조달되지 않는 독립 정보 마트이므로 가상 Meta Mart의 원천이 될 Meta Vault는 존재하지 않는다 — 메타데이터를 실제로 저장하므로 항상 실체화된다 (§10.2, p.321).[^linstedt2016]
- 다른 정보 마트처럼 비즈니스가 가장 잘 쓸 수 있는 형태로 모델링한다: 차원 모델일 수도, 3정규형일 수도 있고, 메타데이터 도구가 있으면 그 도구의 백엔드 데이터베이스가 Meta Mart가 된다. 관계형일 필요도 없다 — 상용 모델링·ETL 도구의 메타데이터 모델을 확장해 Data Vault용 리니지(허브·링크·새틀라이트의 원천 테이블 정의 등)를 담을 수도 있다 (§10.2, p.321).[^linstedt2016]

- 물리 설계 장이 이 마트의 내용 목록을 다시 준다. 최종 사용자(대개 관리자·파워 유저·웨어하우스 이니셔티브 팀원)에게 제시되는 것은 일곱 항목이다: **전 계층의 데이터·정보에 관한 메타데이터**, **프로세스에 관한 메타데이터**(주로, 그러나 ETL 적재 프로세스에 한정되지 않는다), **수행된 백업에 관한 메타데이터**, **원천 시스템과 타 시스템 인터페이스**(정보 소비자 등)**에 관한 메타데이터**, **하드·소프트 업무 규칙의 정의**, **접근 제어 목록(ACL) 등 보안 조치의 정의**, **프라이버시 관련 데이터의 보존 기간 정의**. 이 목록은 완결적이지 않다 — Meta Mart는 업무 사용자가 직접 쓰지는 않지만 **어떤 데이터·정보가 있는지, 어디서 왔는지, 어떻게 처리되는지, 누가 무슨 목적으로 쓰는지**를 기술하는 모든 정보를 접근 가능하게 만든다. 더 정교한 환경에서는 Meta Mart가 메타데이터 웨어하우스 솔루션으로 대체되기도 한다 (§8.6.4, p.257).[^linstedt2016]
- 이 마트를 **OLAP 도구로 질의한다면 차원 모델이 이 마트를 모델링하는 최선의 접근**이다 (§8.6.4, p.257).[^linstedt2016] 위 §10.2의 "차원 모델일 수도, 3정규형일 수도"를 소비 도구 기준으로 좁힌 진술이다.
- Meta Mart와 Error Mart는 **재구축할 수 없는 마트**다. Metrics Mart가 Metrics Vault에서 조달되는 것과 달리 이 둘은 데이터의 단일 지점이므로, 신뢰성 요구가 다른 정보 마트보다 높고 Raw Data Vault 계층에 준한다. 백업에도 반드시 포함해야 하며 Metrics Mart의 백업만 선택이다 (§8.6.4.1, pp.257–258).[^linstedt2016] 계층별 물리 설계는 [Data Vault 아키텍처](../concepts/data-vault-architecture.md)와 [물리 데이터 웨어하우스 설계](../concepts/physical-data-warehouse-design.md) 참조.

### Metrics Vault

- Metrics Vault는 ETL 제어·데이터 흐름의 프로세스 지표를 캡처한다. 선택적 구성 요소지만 오류 검사(ETL 재기동에 필요한 오류·원인 식별), 근본 원인 분석(같은 오류의 재발 방지), 성능 지표(데이터 크기·성장률을 관찰해 부정적 추세를 장애 전에 대응)에 유용하다 (§10.3, p.351).[^linstedt2016]
- 최고 수준의 상세로 캡처할 지표 영역: 타이밍(시작·종료·경과 시간), 성능(초당 읽기/쓰기 행 수), 볼륨(읽은·쓴·거부된 총 행 수), 오류(원천·목적지별 거부/오류 레코드 수 — 원시 데이터 자체는 Error Mart 몫), 빈도(원천의 데이터 제공·ETL 실행 주기), 의존 체인(의존 ETL 프로세스의 대기 시간) (§10.3, pp.351–352).[^linstedt2016]
- Metrics Vault는 Data Vault 2.0 모델로 모델링해야 한다 — ETL 도구 외에 서버·네트워크 인프라 등 다양한 원천의 지표를 통합하기 위해서다. 근본 원인 분석이 진행될수록 더 많은 잠재 장애 원천이 분석 대상이 되므로, 웨어하우스 자체처럼 애자일하게 원천을 늘려 간다 (§10.3, p.352).[^linstedt2016]

### Metrics Mart

- Metrics Vault에 원시 성능 데이터를 캡처한 다음 단계는 분석용 가공이다. Metrics Mart는 그 데이터 모델이 구현되는, 사용자 쪽 하류(downstream)에 위치한 정보 마트다. 표준 아키텍처를 그대로 따른다: Metrics Vault는 EDW의 Data Vault 모델에 통합된 일부로 구현되고 Metrics Mart 구축에만 배타적으로 쓰인다 (§10.4, p.363).[^linstedt2016]
- Metrics Mart는 특수 목적 정보 마트로 주로 Metrics Vault에서 조달되지만(Raw Data Vault·Business Vault 대신), 고객·제품 관련 기술 성능 지표처럼 비즈니스 객체를 포함하려면 Raw Data Vault나 Business Vault에서도 조달할 수 있다. ETL 실체화와 SQL 뷰 가상화 모두 가능하며 배포 속도가 빨라지는 가상화가 선호된다 (§10.4, p.363).[^linstedt2016]
- 모델은 최종 사용자의 분석 필요에 맞춘다 — OLAP 큐브를 올릴 거면 차원 모델, 모니터링 소프트웨어가 기대하는 형식이 따로 있으면 그 형식. 원시 데이터(Metrics Vault)와 정보(Metrics Mart)를 분리하는 이점은 Raw Data Vault와 정보 마트의 관계와 같다: 다른 원천을 쉽게 통합하면서 필요한 구조를 가상으로 구축할 수 있다 (§10.4, pp.363–364).[^linstedt2016]

### Error Mart

- Error Mart도 정보 마트지만 Meta Mart처럼 Raw Data Vault나 다른 원천에서 조달되지 않는다. 오류 정보를 저장하는 일차 장소이며, 대부분은 ETL 엔진에서 온다 (§10.5, p.364).[^linstedt2016]
- 캡처하는 레코드 유형 네 가지 (§10.5, p.365):[^linstedt2016]
  - 스테이징 영역이 거부한 레코드: 전송 오류 등으로 관계형 구조에 맞지 않는 데이터.
  - Raw Data Vault가 거부한 레코드: 적재 목표는 좋은 것·나쁜 것·못난 것(the good, the bad, and the ugly) 전부지만, 관계형 구조에 맞지 않으면 캡처 불가.
  - Business Vault가 처리하지 못한 레코드: 비즈니스가 정의한 소프트 규칙에 부합하지 않은 레코드.
  - 정보 마트가 처리하지 못한 레코드: Business Vault는 비즈니스 규칙을 부분적으로만 구현하므로 정보 마트의 소프트 규칙이 추가로 거부한 레코드도 Error Mart로 보낸다.
- 소프트 규칙은 시간이 지나며 바뀌므로 Error Mart가 캡처하는 데이터도 바뀐다. 거부된 레코드가 모두 나쁜 데이터는 아니다 — 소프트 규칙이 예상하지 못한 데이터(Data Vault 용어로 ugly data)도 포함되며, Error Mart는 이를 식별해 비즈니스 규칙 구현을 개선하고, 궁극적으로는 왜 그 레코드가 Raw Data Vault에 적재되지 못했는지를 찾아 고쳐서 적재하는 것이 목표다 (§10.5, p.365).[^linstedt2016]
- 최종 사용자가 선호하는 모델로 구현할 수 있지만 대부분 차원 모델로 짓는다: 오류 데이터를 팩트 테이블에, 부수 정보를 차원에 둔다. 오류 출력마다 별도 팩트 테이블을 만드는 쪽이 원시 데이터를 보존해 상세 오류 분석에 유리하다 — 단순 통계 산출은 Metrics Mart에 맡긴다 (§10.5, pp.365–366).[^linstedt2016]

## 데이터 카탈로그

데이터 엔지니어링 개론은 위 메타데이터 저장소들을 하나의 제품 범주로 묶어 **데이터 카탈로그**라
부른다.

- 정의와 지위 — **데이터 카탈로그(data catalog)는 조직 전반의 모든 데이터를 위한 중앙집중식
  메타데이터 저장소다. 엄밀히 말하면 데이터 카탈로그는 최상위 데이터 저장 추상이 아니지만 다양한
  시스템·추상과 통합된다. 데이터 카탈로그는 일반적으로 운영·분석 데이터 소스에 걸쳐 작동하고,
  데이터 계보와 데이터 관계의 제시를 통합하고, 사용자가 데이터 서술을 편집하도록 허용한다** (6장,
  p.218).[^reis2022]
- 무엇에 쓰는가와 데이터 엔지니어의 몫 — **데이터 카탈로그는 흔히 사람들이 자기 데이터·질의·데이터
  저장을 볼 수 있는 중앙 장소를 제공하는 데 쓰인다. 데이터 엔지니어로서 당신은 데이터 카탈로그와
  통합될 데이터 파이프라인·저장 시스템의 다양한 데이터 통합을 세우고 유지하는 것, 그리고 데이터
  카탈로그 자체의 무결성을 책임질 가능성이 크다** (6장, p.218).[^reis2022]
- **카탈로그 애플리케이션 통합** — **이상적으로 데이터 애플리케이션은 자기 메타데이터와 갱신을 직접
  다루기 위해 카탈로그 API와 통합되도록 설계된다. 카탈로그가 조직에서 더 널리 쓰일수록 이 이상에
  접근하기 쉬워진다** (6장, p.218).[^reis2022]
- **자동 스캐닝** — **실무에서 카탈로깅 시스템은 일반적으로 데이터 레이크·데이터 웨어하우스·운영
  데이터베이스 같은 다양한 시스템에서 메타데이터를 수집하는 자동 스캐닝 계층에 의존해야 한다. 데이터
  카탈로그는 기존 메타데이터를 수집할 수 있고, 키 관계나 민감 데이터의 존재 같은 메타데이터를
  추론하기 위해 스캐닝 도구를 쓸 수도 있다** (6장, p.218).[^reis2022]
- **데이터 포털과 소셜 계층** — **데이터 카탈로그는 일반적으로 웹 인터페이스를 통한 사람 접근
  계층도 제공하며 거기서 사용자는 데이터를 검색하고 데이터 관계를 볼 수 있다. 데이터 카탈로그는
  위키 기능을 제공하는 소셜 계층으로 향상될 수 있다. 이는 사용자가 자기 데이터셋에 대한 정보를
  제공하고, 다른 사용자에게 정보를 요청하고, 가용해지는 대로 갱신을 게시하도록 허용한다** (6장,
  p.218).[^reis2022]
- 유스케이스가 둘로 갈린다 — **데이터 카탈로그는 조직적 유스케이스와 기술적 유스케이스를 둘 다
  갖는다. 데이터 카탈로그는 메타데이터를 시스템이 쉽게 이용할 수 있게 만든다. 예컨대 데이터
  카탈로그는 데이터 레이크하우스의 핵심 재료로, 질의를 위한 테이블 발견 가능성을 허용한다** (6장,
  p.219).[^reis2022] 그 레이크하우스 쪽은
  [데이터 레이크](../concepts/data-lake.md)에 있다.
  - **조직적으로 데이터 카탈로그는 업무 사용자·분석가·데이터 과학자·엔지니어가 질문에 답할 데이터를
    검색하도록 허용한다. 데이터 카탈로그는 조직 간 소통과 협업을 매끄럽게 한다** (6장,
    p.219).[^reis2022]
- 저장 저류에서의 자리 — **데이터는 견고한 메타데이터로 향상된다. 카탈로깅은 데이터 발견을 가능하게
  해 데이터 과학자·분석가·ML 엔지니어를 돕는다. 데이터 계보는 데이터 문제를 추적하는 시간을
  가속하고 소비자가 상류 원시 소스를 찾도록 허용한다. 저장 시스템을 지어 나가면서 메타데이터에
  투자하라** (6장, p.228).[^reis2022]

## 카탈로그를 데이터 쪽으로 미는 반대 배치

위 [데이터 카탈로그](#데이터-카탈로그) 절이 전제하는 것은 **중앙 등록부**다. 데이터 메시는 그
배치를 뒤집는다 — 메타데이터를 모으는 주체를 카탈로그가 아니라 데이터 자신으로 옮긴다.

- 기존 배치의 서술 — **발견 가능성의 전통적 구현은 이용 가능한 데이터셋을 나열하는 중앙
  레지스트리나 카탈로그이며, 각 데이터셋에 대한 소유자·위치·샘플 데이터 등의 부가 정보를 담는다.
  이 정보는 흔히 중앙 데이터 팀이나 거버넌스 팀이 사후에 큐레이션한다** (3장,
  p.34).[^dehghani2022] 위 절이 서술하는 카탈로그가 정확히 이것이다.
- 뒤집는 방향 — **데이터 메시의 데이터 프로덕트 발견 가능성은 데이터 프로덕트 스스로가 발견
  가능성 정보를 의도적으로 제공하는 시프트 레프트 해법을 받아들인다. 개별 데이터 프로덕트가 자기
  수명 주기의 여러 지점 — 빌드·배포·실행 — 에서 표준화된 방식으로 그 정보를 제공하는 데
  의존한다** (3장, p.34).[^dehghani2022]
  - 무엇을 스스로 내놓는가 — **원천, 소유자, 적시성·품질 지표 같은 런타임 정보, 샘플 데이터셋,
    그리고 가장 중요하게는 소비자가 기여한 정보(그 데이터가 가능하게 한 상위 용법과
    애플리케이션)** (3장, p.34).[^dehghani2022] 마지막 항이 특히 이 페이지의 3종 분류에 없는
    것이다 — **소비 쪽에서 역류하는 메타데이터**다.
- **계보의 지위가 낮아진다.** 위 저장 저류 인용이 "데이터 계보는 데이터 문제를 추적하는 시간을
  가속한다"고 적는 자리에서, 데이터 메시는 계보 **의존**을 줄이는 것을 목표로 삼는다 — **각
  데이터 프로덕트에 신뢰성을 짓는 규율이 자리 잡으면, 조사 프로세스와 계보 트리를 훑는 탐지
  기법으로 신뢰를 확립할 필요가 줄어든다는 것이 내 의견이다** (3장, p.37).[^dehghani2022]
  - 다만 계보를 없애자는 것은 아니다 — **데이터 계보(data lineage)는 사후 근본 원인 분석,
    디버깅, 데이터 컴플라이언스 감사, ML 훈련을 위한 데이터 적합성 평가 같은 몇몇 시나리오에서
    중요한 요소로 남는다** (3장, p.37).[^dehghani2022] 그리고 계보는 데이터 프로덕트가 공표해야
    할 SLO 일곱 항 중 하나로 남는다 (3장, p.37).[^dehghani2022] 낮아지는 것은 계보의 제공
    의무가 아니라 **신뢰 확립 수단으로서의 일차성**이다.
- 상호운용을 위해 표준화해야 하는 메타데이터도 지목된다 — **공통 메타데이터 필드, 예컨대
  데이터가 발생한 시각과 기록된 시각의 표현** (3장, p.39).[^dehghani2022] 이는 위 3종 분류의
  **기술 메타데이터** 항목이 도메인 경계를 넘을 때 전역 합의를 요구한다는 뜻이다.

**두 배치는 어떤 문제에 답하는가.** 중앙 카탈로그는 흩어진 자산의 존재를 한자리에서 알게 하는
문제에, 데이터 프로덕트의 자기 서술은 그 카탈로그가 실물보다 낡는 문제에 답한다. 후자는 모든
데이터 자산이 표준 배포 단위로 만들어진다는 전제 위에서만 성립한다 — 레거시 저장소가 섞인
자리에서는 카탈로그가 여전히 유일한 진입점이다. 데이터 메시 쪽 정본은
[데이터 메시 원칙](../synthesis/data-mesh-principles.md) 허브가 받는다.

## 조회의 대상이 아니라 실행의 입력으로 쓰는 배치

위 절들과 데이터 카탈로그가 메타데이터를 **사람과 도구가 찾아 읽는 대상**으로 다룬다면, 레이크하우스
쪽에는 같은 저장소를 **파이프라인이 실행 시점에 읽는 입력**으로 쓰는 배치가 있다. 소비자가 다르므로
두 배치는 겨루지 않고, 실은 같은 저장소 하나가 둘 다 감당할 수 있다.

- 규정 — **메타데이터 주도 접근(metadata-driven approach)은 스키마 정의를 데이터베이스나 데이터
  카탈로그 같은 중앙화된 메타데이터 저장소에 두는 것**이고, 그 저장소가 **컬럼 이름·데이터 타입·
  제약·데이터 요소 사이의 관계**를 담는다 (5장 §"Schema Management" ▸ "Metadata-Driven
  Approach").[^strengholt2025]
- **차이는 시점이다** — 이 메타데이터로 **실행 시점에 스키마 정의를 동적으로 생성**할 수 있고,
  그래서 서로 다른 원천과 목적지에 맞춰 스키마를 적응시킬 수 있다 (같은 소절).[^strengholt2025]
  카탈로그가 "무엇이 있는가"에 답한다면 이쪽은 "이번 실행에서 무엇을 만들 것인가"에 답한다.
- 같은 배치가 파이프라인 전체로도 확장된다 — 데이터 유형마다 별도 파이프라인을 만드는 대신
  메타데이터 주도 프레임워크로 **주어진 메타데이터에 따라 스스로 조정되는 범용 파이프라인**을
  구성하면 방대한 코드를 쓰고 유지할 필요가 크게 준다 (5장 §"Building the Data Pipeline" ▸
  "Additional Considerations").[^strengholt2025]
  - 같은 저자가 앞 장에서 **메타데이터 통제 표(metadata control table)**를 권고한 것도 이 갈래다 —
    처리된 레코드를 추적해 복잡한 시스템에서 데이터 흐름 관리와 일관성 보장을 돕는다 (3장
    §"Bronze Layer" ▸ "Processing Incremental Data Loads").[^strengholt2025]
  - 검증 규칙도 같은 저장소에 얹힌다 — 많은 회사가 원천의 기술 스키마 상세를 담은 메타데이터
    저장소를 유지해 **검증 규칙을 선언적으로도 동적으로도 자동 강제**하게 한다 (3장 §"Bronze
    Layer" ▸ "Technical Validation Checks").[^strengholt2025]
- **대가는 구축 비용**이고 저자가 명시한다 — 메타데이터 주도 프레임워크의 구현이 **복잡하고 시간이
  많이 들 수 있다** (5장 §"Schema Management" ▸ "Metadata-Driven Approach").[^strengholt2025]

- **프레임워크의 뼈대는 부품 셋이다** — 이 데이터가 저장되는 **메타데이터 저장소**, 메타데이터를
  읽어 **잡과 검증과 변환을 동적으로 만들어 내는 오케스트레이터**, 그리고 여러 잡의 상태를
  **감시하고 추적하는 장치**다 (6장 §"Implementation of a Metadata-Driven Approach" ▸ "Improvement
  Areas").[^strengholt2025] 앞 절들의 저장소 하나만으로는 이 배치가 서지 않는다는 뜻이다.
- 저장소에 무엇을 넣을지의 확장 축도 함께 주어진다 — 도메인 고유 정보, 여러 원천의 메타데이터,
  민감도 라벨이나 행 필터링 같은 보안 메타데이터, 원천에서 대상으로의 컬럼 개명이나 단순 조인·
  유니온이나 무관 데이터 필터링 같은 처리 로직, 그리고 CI/CD를 위한 환경·배포·버전 정보다.
  **결국 메타데이터 프레임워크의 범위는 요구사항에 달렸다** (같은 소절).[^strengholt2025]
- 이 배치가 코드 기반 전략 대비 갖는 이점으로 저자가 넷을 센다 — 형식·스키마·주기가 다른 여러
  원천과 목적지를 감당하는 **다재다능함**, 노트북 여럿 대신 **범용 파이프라인 한 벌**만 유지하게
  되는 코드량 감소, 코드 수정이나 재배포 없이 메타데이터만으로 검증과 수정을 더하는 **개발·배포의
  단순화**, 그리고 여러 활동을 동시에 돌리는 **병렬성**이다 (같은 소절).[^strengholt2025]
  - 앞 셋은 같은 뿌리다. **무엇을 할지가 코드가 아니라 데이터에 적혀 있으면 코드를 고치지 않고
    무엇을 할지를 바꿀 수 있다**는 것이다.
- 같은 저자가 이 배치를 실물로 구현해 보이는 자리는
  [Silver 계층의 기술 검증과 데이터 정제](../concepts/silver-layer-validation-and-cleansing.md)다.
  메타데이터 저장소의 컬럼 구성과 그것을 파이프라인에 거는 부품 셋, 그리고 확장 방향 아홉이 거기
  있다.
