이 페이지의 질문: **관계형 데이터 웨어하우스가 이미 있는데 왜 파일 저장소가 또
필요해졌고, 그 선택이 무엇을 바꾸는가.**

## 웨어하우스가 감당하지 못한 수요

- 데이터 웨어하우스는 보통 SQL로 질의하는 **관계형** 데이터 모델을 쓰고 전용 BI
  소프트웨어를 얹는다. 업무 분석가가 던지는 종류의 질의에는 잘 맞지만, 데이터
  과학자가 하는 작업에는 덜 맞는다 (1장, p.9).[^kleppmann2026]
  - ML 모델 학습용 형태로의 변환: 테이블의 행과 열을 특징(feature)이라 불리는 수치
    벡터·행렬로 바꾸는 일이며, 학습 성능을 최대화하도록 이 변환을 수행하는 과정을
    특징 공학(feature engineering)이라 부른다. SQL로 표현하기 어려운 커스텀 코드가
    흔히 필요하다.
  - 텍스트에 자연어 처리(NLP)를 적용해 구조화된 정보를 뽑는 일(예: 리뷰의 감성,
    언급된 주제), 사진에서 컴퓨터 비전으로 정보를 뽑는 일.
- SQL 데이터 모델에 ML 연산자를 더하려는 시도도, 관계형 기반 위에 효율적 ML
  시스템을 짓는 시도도 있었지만, 많은 데이터 과학자는 데이터 웨어하우스 같은
  관계형 데이터베이스 안에서 일하기를 선호하지 않는다 — Pandas·scikit-learn 같은
  파이썬 라이브러리, R, Spark 같은 분산 분석 프레임워크를 쓴다 (1장,
  p.9).[^kleppmann2026]

## 정의와 웨어하우스와의 차이

- 정의는 원문 그대로 (1장, pp.9–10):[^kleppmann2026]

> The answer is a *data lake*: a centralized data repository that holds a copy
> of any data that might be useful for analysis, obtained from operational
> systems via ETL processes. The difference from a data warehouse is that a data
> lake simply contains files, without imposing any particular file format, data
> model, or schema.

- 레이크 안의 파일은 Avro·Parquet 같은 파일 형식으로 인코딩된 데이터베이스 레코드
  모음일 수도 있지만, 텍스트·이미지·비디오·센서 판독값·희소 행렬·특징 벡터·게놈
  서열 등 **어떤 종류의 데이터든** 똑같이 담을 수 있다 (1장, p.10).[^kleppmann2026]
- 유연성만이 아니라 값도 싸다. 오브젝트 스토어 같은 범용 파일 저장(commoditized
  file storage)을 쓸 수 있기 때문이다 (1장, p.10).[^kleppmann2026] 그 저장 계층의
  성질은 [클라우드 네이티브 아키텍처](../concepts/cloud-native-architecture.md)
  참조.

## 스시 원칙 — 원시 데이터가 낫다

- ETL 프로세스는 **데이터 파이프라인(data pipeline)** 으로 일반화됐고, 어떤 경우에는
  데이터 레이크가 운영계에서 웨어하우스로 가는 경로의 **중간 기착지**가 됐다 (1장,
  p.10).[^kleppmann2026]
- 데이터 레이크는 운영계가 만들어 낸 "원시(raw)" 형태의 데이터를 관계형 웨어하우스
  스키마로 변환하지 않은 채 담는다. 그러면 데이터의 **소비자마다 자기에게 가장 맞는
  형태로** 원시 데이터를 변환할 수 있다는 이점이 생긴다. 이를 스시 원칙(sushi
  principle)이라 부르기도 한다 — "원시 데이터가 낫다(raw data is better)" (1장,
  p.10).[^kleppmann2026]
- 이 원칙은 KB 안에서 정면으로 부딪히는 자리가 있다. Kimball은 ETL의 부가가치가
  **적재 전** 정제·통합에서 나온다고 보고, 정규화 구조를 사용자 질의에서 차단하라고
  요구한다(→ [ETL 34 서브시스템](../concepts/etl-subsystems.md),
  [Kimball DW/BI 아키텍처](../concepts/kimball-dwbi-architecture.md)). 반면 Linstedt의
  Raw Data Vault는 원천 그대로의 보존을 우선한다(→
  [데이터 품질 관리](../concepts/data-quality-management.md)의 "나쁜 데이터의 가치").
  세 관점을 지우지 말고 병기해 둔다.

## 이 선택의 이름 — 읽기 스키마

같은 책 3장이 이 선택에 이름을 붙인다. 레이크는 저장소 층위의 사례이고, 그 층위를 가리지 않는
일반 어휘가 3장에 있다.

- 두 이름의 정의 — **읽기 스키마(schema-on-read)는 데이터의 구조가 암묵적이며 데이터를 읽을 때만
  해석되는 것이고, 쓰기 스키마(schema-on-write)는 스키마가 명시적이고 데이터가 쓰일 때
  데이터베이스가 모든 데이터가 그것에 부합하도록 보장하는 관계형 데이터베이스의 전통적
  접근이다** (3장, p.80).[^kleppmann2026]
- "스키마가 없다"는 표현에 대한 경고도 그대로 적용된다 — **스키마리스(schemaless)라는 말은
  오해를 부른다. 데이터를 읽는 코드가 대개 어떤 종류의 구조를 가정하기 때문이다 — 즉 암묵적
  스키마가 있으나 강제되지 않을 뿐이다** (3장, p.80).[^kleppmann2026] 레이크에서도 마찬가지로,
  파일 형식을 강제하지 않는다는 것이 소비자가 아무 구조도 가정하지 않는다는 뜻은 아니다.
- 언제 이 쪽이 유리한지에 대한 조건도 레이크의 논거와 겹친다 — **읽기 스키마 접근은 컬렉션의
  항목들이 전부 같은 구조를 갖지 않을 때 유리하다. 객체의 종류가 많아 각 종류를 자기 테이블에
  두는 것이 실용적이지 않을 때, 그리고 데이터의 구조가 내가 통제할 수 없고 언제든 바뀔 수 있는
  외부 시스템에 의해 결정될 때다** (3장, p.81).[^kleppmann2026] 전문은
  [읽기 스키마와 쓰기 스키마](../concepts/schema-on-read-and-schema-on-write.md)에 있다.

## 레이크 다음에 온 것들

- 분석 실무가 성숙하면서 조직은 분석 시스템과 데이터 파이프라인의 **관리·운영**에
  점점 더 주의를 기울이게 됐고, 그것이 예컨대 DataOps 선언(DataOps Manifesto)에
  담겼다. 이 흐름을 민 것은 부분적으로 거버넌스·프라이버시, 그리고 GDPR·CCPA 같은
  규제 준수 문제였다 (1장, p.10).[^kleppmann2026]
- 분석용 데이터가 파일과 관계형 테이블만이 아니라 **이벤트 스트림**으로도 제공되는
  일이 늘고 있다. 파일 기반 분석은 데이터 변화에 대응하려면 분석을 주기적으로(예:
  일 단위) 다시 돌려야 하지만, 스트림 처리는 분석 시스템이 **초 단위**로 이벤트에
  반응하게 해 준다 — 예컨대 사기·악용 활동을 식별하고 차단하는 데 값어치가 있다
  (1장, p.10).[^kleppmann2026] 운반 계층 쪽은
  [데이터 생태계와 유스케이스](../concepts/kafka-data-ecosystem-and-use-cases.md)
  참조.
- 분석 시스템의 산출물을 거꾸로 운영계에 되돌리는 경우도 있고, 이를 리버스
  ETL(reverse ETL)이라 부르기도 한다. 예: 분석 시스템에서 학습한 ML 모델을
  프로덕션에 배포해 최종 사용자에게 추천을 내보내는 것 — TFX·Kubeflow·MLflow 같은
  전용 도구를 쓴다 (1장, p.10).[^kleppmann2026]

## 한 덩어리였던 웨어하우스가 넷으로 쪼개진다

같은 책 4장이 이 흐름의 **구조적 결과**를 적는다. 레이크가 오브젝트 스토리지 위로 옮겨 가면서
예전에 하나의 시스템이던 것이 교체 가능한 구성 요소로 나뉜다.

- 먼저 클라우드 쪽 배경 — **테라데이터·버티카·SAP HANA 같은 기성 데이터 웨어하우스 벤더는 상용
  라이선스의 온프레미스 배포와 클라우드 기반 솔루션을 함께 제공한다. 그러나 더 많은 고객이
  클라우드로 옮겨 가면서 구글 클라우드의 BigQuery, 아마존 Redshift, 스노우플레이크 같은 클라우드
  전용 데이터 웨어하우스도 널리 채택됐다. 전통적 데이터 웨어하우스와 달리 클라우드 데이터
  웨어하우스는 오브젝트 스토리지나 서버리스 계산 플랫폼 같은 확장 가능한 클라우드 인프라를 활용할
  수 있다** (4장, p.135).[^kleppmann2026]
- 그것이 주는 것 — **클라우드 웨어하우스는 다른 클라우드 서비스와 더 잘 통합되는 경향이 있다.
  예컨대 많은 클라우드 웨어하우스가 자동 로그 반입을 지원하고 구글 클라우드 Dataflow나 AWS Kinesis
  같은 데이터 처리 프레임워크와의 쉬운 통합을 제공한다. 이 웨어하우스들은 질의 계산을 저장 계층과
  분리하기 때문에 더 탄력적이기도 하다. 데이터가 로컬 디스크가 아니라 오브젝트 스토리지에
  영속화되므로 저장 용량과 질의용 계산 자원을 독립적으로 조정하기 쉽다** (4장,
  p.135).[^kleppmann2026]
- 오픈 소스 쪽에서 일어난 일 — **Apache Hive·Trino·Apache Spark 같은 오픈 소스 데이터 웨어하우스도
  클라우드와 함께 진화했다. 분석용 데이터 저장이 오브젝트 스토리지의 데이터 레이크로 옮겨 가면서
  오픈 소스 웨어하우스는 쪼개지기 시작했다. 예전에는 Hive 같은 단일 시스템에 통합돼 있던 다음
  구성 요소들이 이제는 흔히 별개 구성 요소로 구현된다** (4장, p.135).[^kleppmann2026]
  - **질의 엔진(query engine)** — **Trino·Apache DataFusion·Presto 같은 질의 엔진은 SQL 질의를
    파싱하고, 실행 계획으로 최적화하고, 데이터에 대해 실행한다. 실행은 대개 병렬 분산 데이터 처리
    태스크를 요구한다. 어떤 질의 엔진은 내장 태스크 실행을 제공하고 다른 것들은 Spark나 Flink 같은
    서드파티 실행 프레임워크를 쓰기로 고른다** (4장, pp.135–136).[^kleppmann2026]
  - **저장 형식(storage format)** — **저장 형식은 테이블의 행이 파일에서 어떻게 바이트로
    인코딩되는지를 정하며, 그 파일은 보통 오브젝트 스토리지나 분산 파일시스템에 저장된다. 이
    데이터는 질의 엔진뿐 아니라 데이터 레이크를 쓰는 다른 애플리케이션도 접근할 수 있다.
    Parquet·ORC·Lance·Nimble이 그런 저장 형식의 예다** (4장, p.136).[^kleppmann2026]
  - **테이블 형식(table format)** — **Parquet과 비슷한 저장 형식으로 쓰인 파일은 한 번 쓰이면 보통
    불변이다. 행 삽입과 삭제를 지원하려고 Apache Iceberg나 데이터브릭스의 Delta 형식 같은 테이블
    형식을 쓸 수 있다. 테이블 형식은 어떤 파일이 테이블을 구성하는지를 정의하는 파일 형식을 테이블
    스키마와 함께 명시한다. 그런 형식은 시간 여행(time travel, 테이블을 과거 시점의 모습으로 질의할
    수 있는 능력)·GC·심지어 트랜잭션 같은 고급 기능도 제공한다** (4장, p.136).[^kleppmann2026]
  - **데이터 카탈로그(data catalog)** — **테이블 형식이 어떤 파일이 테이블을 이루는지 정의하듯,
    데이터 카탈로그는 어떤 테이블이 데이터베이스에 담기는지 정의한다. 카탈로그는 테이블을 만들고
    이름을 바꾸고 지우는 데 쓰인다. 저장 형식·테이블 형식과 달리 스노우플레이크의 Polaris나
    데이터브릭스의 Unity Catalog 같은 데이터 카탈로그는 보통 REST 인터페이스로 질의할 수 있는
    독립 서비스로 돈다. Apache Iceberg도 카탈로그를 제공하며 클라이언트 안에서 또는 별도 프로세스로
    돌 수 있다. 질의 엔진은 테이블을 읽고 쓸 때 카탈로그 정보를 쓴다. 전통적으로 카탈로그와 질의
    엔진은 통합돼 있었지만, 그것들을 분리한 덕분에 데이터 발견·데이터 거버넌스 시스템도 카탈로그의
    메타데이터에 접근할 수 있게 됐다** (4장, p.136).[^kleppmann2026]

## 반대 압력 — 데이터 최소화

- 우리가 데이터를 저장하는 이유는 그 가치가 저장 비용보다 크다고 보기 때문이다.
  그러나 **저장의 비용은 청구서를 넘어선다** — 데이터가 유출·탈취됐을 때의 책임과
  평판 손상, 저장·처리가 법을 어긴 것으로 판명될 때의 법적 비용과 과징금까지
  비용편익 계산에 넣어야 한다 (1장, p.25).[^kleppmann2026]
- 정부나 경찰이 데이터 제출을 강제할 수도 있다. 데이터가 범죄화된 행위를 드러낼 수
  있는 곳에서는(저자들이 든 예는 여러 중동·아프리카 국가의 동성애, 미국 여러 주의
  낙태) 그런 데이터를 저장하는 것 자체가 사용자에게 실제 안전 위험을 만든다 —
  위치 데이터나 시간에 따른 IP 주소 로그만으로도 드러날 수 있다 (1장,
  p.25).[^kleppmann2026]
- 위험을 다 계산에 넣고 나면 **어떤 데이터는 아예 저장할 가치가 없고 따라서 지워야
  한다**는 판단이 합리적일 수 있다. 이 원칙을 데이터 최소화(data minimization,
  독일어로 Datensparsamkeit)라 부르며, 나중에 쓸모 있을지 모른다는 이유로 데이터를
  투기적으로 잔뜩 쌓는 "빅데이터" 철학과 **정면으로 어긋난다** (1장,
  p.25).[^kleppmann2026]
- 데이터 최소화는 GDPR과는 맞는다: 개인 데이터는 명시된 명확한 목적으로만 수집할 수
  있고, 이후 다른 목적으로 쓸 수 없으며, 수집 목적에 필요한 기간보다 오래 보관해서는
  안 된다 (1장, p.25).[^kleppmann2026]
- **반대편 처방**: [EDW](../concepts/enterprise-data-warehouse.md)의 "단일 사실
  버전"은 컴플라이언스를 근거로 **모든 원시 데이터를 항상 보관**하자고 말한다. 위의
  데이터 최소화는 같은 컴플라이언스를 근거로 **덜 저장하고 지우자**고 말한다. 다만
  두 처방의 대상이 온전히 같지는 않다 — 전자는 감사 가능성을 위한 업무 데이터,
  후자는 GDPR이 규율하는 개인 데이터다. 겹치는 구간(웨어하우스가 개인 데이터를
  담을 때)에서만 실제로 부딪히며, 그때도 어느 쪽이 참인지가 아니라 어떤 데이터에
  어느 정책을 걸지의 설계 판단이다. 사실 주장의 충돌이 아니므로 `contradicts`는
  달지 않는다(PLAN §2.1).
- 같은 책 14장이 이 원칙을 규제 조문으로 되받고 그 대립을 명시한다 — **GDPR은 개인 데이터가
  "구체적이고 명시적이며 정당한 목적을 위해 수집되고 그 목적과 양립할 수 없는 방식으로 추가
  처리되지 않아야" 하며 "처리되는 목적과 관련해 적절하고 관련성 있으며 필요한 것으로 제한되어야"
  한다고 규정한다** (14장, p.596).[^kleppmann2026] 그리고 **이 데이터 최소화 원칙은 빅데이터의
  철학 — 데이터 수집을 최대화하고, 수집된 데이터를 다른 데이터셋과 결합하고, 새로운 통찰을 생성하기
  위해 실험하고 탐색하는 것 — 과 정면으로 어긋난다. 탐색은 예견되지 않은 목적으로 데이터를 쓰는
  것을 뜻하는데, GDPR은 그것이 데이터가 수집됐어야 하는 "구체적이고 명시적인" 목적의 반대라고
  규정한다** (14장, p.596).[^kleppmann2026] 레이크의 "일단 원시 데이터를 다 모아 두고 나중에
  해석한다"는 전제가 바로 그 탐색이다.
- 14장은 실행 지침도 한 줄 더 준다 — **첫걸음으로 우리는 데이터를 영원히 보관하지 말고 더 이상
  필요 없어지는 즉시 파기하며 애초에 수집하는 것을 최소화해야 한다. 여러분이 갖고 있지 않은
  데이터는 유출되거나, 도난당하거나, 정부에 의해 넘기도록 강제될 수 없는 데이터다** (14장,
  p.597).[^kleppmann2026] 그 논거의 전문은
  [위험 자산으로서의 데이터](../concepts/data-as-a-hazardous-asset.md)에 있다.
