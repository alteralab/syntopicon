## 하나의 질문

**데이터 메시 채택의 장기 이정표를 무엇으로 나누는가.**

[데이터 메시 실행 프레임워크](../concepts/data-mesh-execution-framework.md)의 네 성격 중
넷째인 **진화적(evolutionary)**을 저자는 거시·미시 두 도구로 나눈다 — **이 절에서 나는
진화적 실행을 항해하도록 돕는 두 도구를 공유한다: 장기 지평의 이정표를 보며 거시 수준에서
실행을 안내하는 **다단계 채택 모델**과, 각 이터레이션의 미시 수준에서 진화를 안내하는 **목적
함수 집합**이다** (15장, p.286).[^dehghani2022] 뒤엣것은
[데이터 메시의 적합성 함수](../concepts/data-mesh-fitness-functions.md)가 받는다.

## 사전 계획을 거부하는 이유

- 저자는 상세 계획을 명시적으로 권하지 않는다 — **나는 신중히 설계된 과업과 이정표의 경직된
  사전 계획을 권하지 않는다. 경험상 나는 그런 계획이 대규모 비즈니스의 실행과 휘발성 환경과의
  첫 조우에서 살아남으리라고 그냥 믿지 않는다** (15장, p.286).[^dehghani2022]
- 대신 열어 두는 것 — **그렇게 말했지만, 결과를 얻는 것·가벼운 계획·지속적 학습·실험을
  우선시하는 EDGE — 가치 주도 디지털 전환 — 같은, 애자일 원칙에 기초한 프레임워크는 전환의
  운영 모델을 정의하는 데 매우 유용할 수 있다** (15장, p.286).[^dehghani2022]
- 프레임워크 선택과 무관한 요구사항 — **어떤 전환 프레임워크를 고르든 데이터 메시를 실행하는
  과정은 진화적인 것으로 다뤄진다. 진화적 과정은 구현 성숙도의 서로 다른 단계를 인식하고
  감당하며, 실행을 최적 결과와 더 높은 성숙도로 지속적으로 안내하는 테스트와 지표의 집합을
  갖는다** (15장, p.286).[^dehghani2022]

## s 곡선과 세 단계

- 도구의 출처가 명시된다 — **나는 혁신 채택의 s 곡선(s-curve of innovation adoption)이
  데이터 메시 구성 요소의 진화를 틀 지우는 데 꽤 유용한 도구임을 발견했다. 곡선의 모양은
  조직마다 다를 수 있지만 — 어떤 것은 더 가파르거나 완만한 기울기, 어떤 것은 더 짧거나 긴
  꼬리 — 곡선의 일반 단계들은 진화 접근을 안내하는 데 성공적으로 쓰일 수 있다** (15장,
  p.286).[^dehghani2022] 각주는 Rogers, *Diffusion of Innovations*, p.1을 든다 (15장,
  p.286, 각주 5).[^dehghani2022]
- 두 축의 매핑이 겹쳐진다 — **그림 15-5는 데이터 메시의 성장 s 곡선을 보인다. 곡선의 각
  단계는 조직 안의 서로 다른 채택자 집단 — 혁신자(innovators)·얼리 어답터(early adopters)·
  다수 채택자(majority adopters)·후기 채택자(late adopters)·지각자(laggards) — 에 매핑된다.
  그리고 곡선의 각 단계는 대응하는 개발 양식 — 부트스트래핑할 때의 **탐색(exploration)**,
  규모를 키울 때의 **확장(expanding)**, 규모에서 운영을 지속할 때의 **추출(extracting)** —
  에 매핑된다** (15장, p.286).[^dehghani2022]
  - 개발 양식 셋의 출처도 명시된다 — 각주는 Kent Beck의 "Explore, Expand, and Extract,
    3X"를 들며 **그는 제품 전달의 세 단계에 이름을 붙였다. 그는 각 단계 동안 제품 개발에 대한
    서로 다른 기법과 태도를 식별했다. 나는 그것들을 데이터 메시 실행에 적응시켰다**고 적는다
    (15장, p.286, 각주 6).[^dehghani2022]
- 예시가 플랫폼으로 주어진다 — **플랫폼 구현은 초기 기능이 혁신자와 얼리 어답터 — 위험
  감수자와 전문가 사용자 — 를 섬기며 지어지는 **탐색 마음가짐의 부트스트래핑** 단계를 거칠
  것이다. 플랫폼이 성숙하면서, 손을 잡아 주지 않아도 되는 도메인의 제너럴리스트 기술자라는 더
  큰 사용자 집단을 섬기도록 셀프서브 능력을 확장하고 넓힌다. 확장 단계 동안 플랫폼은 플랫폼
  사용의 마찰을 줄이고 후기 플랫폼 채택자라는 더 다양한 페르소나를 만족시키도록 지원 서비스를
  성숙시킨다. 사용자 다수와 그들의 필요가 다뤄지고 나면 플랫폼 변경은 최소로 남고, 조직은 현재
  자리 잡은 기능을 규모에서 **추출**하고 활용한다. 이 단계 동안 플랫폼 API와 서비스는 새 데이터
  프로덕트와 유스케이스에 재사용된다** (15장, p.287).[^dehghani2022]
- 곡선은 한 번으로 끝나지 않는다 — **데이터 관리에 주요 산업 혁신이 도래하거나, 조직이 플랫폼을
  새롭고 신기한 방식으로 쓰려 시도하거나, 벤더가 기반 기술을 바꾸면, 플랫폼은 다음 s 곡선의
  진화로 들어가고 과정이 반복된다** (15장, p.288).[^dehghani2022]
- 같은 곡선이 도메인 온보딩 순서에도 쓰인다 — **비슷하게 이 곡선을 도메인 소유권 실행을 계획하는
  데 쓸 수 있다. 진화 단계에 따라 대응하는 도메인 계층 — 혁신자·선도 채택자·후기 채택자·지각자 —
  을 식별하고 어느 것이 먼저 메시에 합류할지 우선순위를 매긴다. 예컨대 다수 채택자 도메인으로
  옮기기 전에 데이터 전문성이 더 많은 도메인을 혁신 채택자로 고른다. 얼리 어답터 도메인을 써서
  다른 도메인을 위한 길을 닦는다** (15장, p.288).[^dehghani2022]
- 그리고 단계마다 팀의 태도까지 달라야 한다고 못 박는다 — **진화의 각 단계에 대해, 개발되는
  능력과 팀의 행동을 의도적으로 달리하라. 예컨대 초기 단계에서 팀은 정책·플랫폼·데이터 프로덕트를
  세우는 데 더 탐색적인 태도를 채택해야 하고, 견딜 만한 수준의 수동 개입을 허용해야 한다. 확장
  단계에서 메시는 수동 활동을 최소화하고, 부하를 모니터링할 광범위한 관측 가능성을 갖추고, 큰
  정책 커버리지로 사용을 확장하도록 성숙해야 한다** (15장, p.288).[^dehghani2022]

## ① 도메인 소유권의 단계별 특성

그림 15-6이 네 차원으로 나눈다 (15장, p.288):[^dehghani2022]

| 차원 | 탐색·부트스트랩 | 확장·규모 | 추출·지속 |
|---|---|---|---|
| 도메인 수 | 적은 수의 도메인 | 도메인 다수로 가속 | 지속되는 도메인 수 |
| 도메인의 계층 | 데이터 제공자이자 소비자 | 데이터 제공자 다수 | 데이터 소비자 다수 |
| 도메인의 초점 | 길을 닦고 실무를 확립 | 온보딩 가속 | 프로세스 최적화 |
| 도메인의 원형 | 현대적 기술 스택을 갖춘 데이터 전문가 | 레거시 시스템을 가진 다수 중간층 | 지각자 |

- 탐색 단계에서 **초기 도메인은 최소 의존으로 종단 가치 전달에 참여하기 위해 데이터의 제공자와
  소비자 **둘 다**로 흔히 행동한다. 그럼에도 두 역할 모두 이 단계의 일부여야 한다** (15장,
  p.289).[^dehghani2022] 이 단계의 초기 도메인이 하는 일은 **데이터 프로덕트 소유자 역할을
  정의하고 도메인 팀 구조를 세우는 관점에서 합리적 실무를 세우는 것**이고, **애플리케이션의 운영
  데이터를 소스 정렬 데이터 프로덕트로 통합하는 도구와 프로세스를 만들어 길을 닦는다** (15장,
  p.289).[^dehghani2022]
- 확장 단계 — **빠른 증분으로 점점 더 많은 도메인이 메시에 합류한다. 다수 중간층이다. 초기
  다수는 계속 길을 닦고 기술적·조직적으로 반복 가능한 패턴 집합을 확립해, 실행이 도메인 다수로
  빠르게 규모 확장할 수 있게 한다. 도메인들은 다양한 기술 스택을 갖고, 아주 높은 확률로 메시에
  통합되거나 이관되어야 할 오래된 시스템과 레거시 시스템을 가진다. 그들은 레거시 통합을 다룰 새
  실무와 도구를 도입한다** (15장, p.289).[^dehghani2022]
- 추출 단계 — **대부분의 도메인이 자율적 데이터 소유 모델로 옮겨 갔고 도메인 수가 안정된다.
  데이터 소유 모델의 최적화 때문에 도메인의 요동이 예상된다. **많은 데이터 프로덕트 수 때문에
  병목이 된 도메인은 여럿으로 쪼개질 수 있고, 사용자가 최소한으로만 의존하는 도메인은 다른
  도메인과 합쳐질 수 있다.** 이 단계에서 제공자 도메인은 계속 자기 데이터 프로덕트를 수정·진화·
  최적화하지만, 활동의 다수는 재사용 가능한 큰 데이터 프로덕트 집합을 활용해 새 시나리오를 짓는
  소비자 도메인에서 일어난다** (15장, p.289).[^dehghani2022]

## ② 제품으로서의 데이터의 단계별 특성

그림 15-7이 다섯 차원으로 나눈다 (15장, p.290):[^dehghani2022]

| 차원 | 탐색·부트스트랩 | 확장·규모 | 추출·지속 |
|---|---|---|---|
| 데이터 프로덕트 수 | 적은 수 | 빠르게 커지는 큰 수 | 안정화 |
| 데이터 프로덕트의 어포던스 | 필수 어포던스 | 빠른 개발에 필요한 어포던스 대부분 | 회복력을 위한 전 어포던스 |
| 개발 초점 | 표준·합리적 실무의 확립 | 다양성 지원 | 데이터 프로덕트 최적화 |
| 데이터 프로덕트의 원형 | 낮은 위험(보안·신뢰성) | 높은 위험 | 레거시 |
| 데이터 프로덕트의 역할 | 소스 정렬 다수 | 집계 포함 전부 | 소비자 정렬 다수 |

- 어포던스의 부분 집합만 지원한다는 것이 구체적이다 — **초기 데이터 프로덕트는 11장에서 도입한
  어포던스의 필수 부분 집합을 지원한다. 예컨대 출력 포트 양식의 일부만 가용하고, 최신 스냅샷만
  공유하는 제한된 보존 기간이거나, 제한된 발견 가능성 능력일 수 있다** (15장,
  p.290).[^dehghani2022] 그 어포던스 목록이
  [데이터 프로덕트 어포던스](../concepts/data-product-affordances.md)의 표 11-1이다.
- 초기 선택의 기준 — **이 단계 동안 선택된 데이터 프로덕트는 보안·신뢰성 관점에서 위험이 낮은
  것들이고, 최소한의 표준화를 견딘다. 초기 데이터 프로덕트는 개발 모델과 기술 요구사항 면에서
  서로 다르되 보완적이도록 선택된다. 이것이 플랫폼 의존을 집중시킨다** (15장,
  p.290).[^dehghani2022]
- 확장 단계 — **얼리 어답터가 데이터 프로덕트의 표준화된 패턴을 확립해 두었으므로 데이터
  프로덕트가 빠르게 개발될 수 있다. 데이터 프로덕트는 큰 수의 사용자가 손을 잡아 주지 않아도
  관측하고·발견하고·규모에서 쓰는 데 필요한 어포던스를 만든다. 이 단계에서 개발되는 데이터
  프로덕트는 프라이버시·업타임·회복력 등에 관해 더 높은 위험 범주에 들 수 있다** (15장,
  p.291).[^dehghani2022]
- 추출 단계 — **데이터 프로덕트 수가 더 느린 변화 속도로 안정될 가능성이 크다. (…) 변환
  복잡도 때문에 변경 리드 타임이 긴 데이터 프로덕트는 더 작고 효율적인 데이터 프로덕트로 쪼개진다.
  이 단계에서 데이터 프로덕트 개발의 초점은 앞선 데이터 프로덕트 개발 투자에 대한 대규모 수익을
  내는 것이다. 많은 지능형 비즈니스 이니셔티브가 기존 데이터 프로덕트를 있는 그대로 쓸 수 있다.
  이 단계에서 지각 레거시 데이터 저장소나 시스템이 데이터 프로덕트로 전환된다** (15장,
  p.291).[^dehghani2022]

## ③ 셀프서브 플랫폼의 단계별 특성

그림 15-8이 네 차원으로 나눈다 (15장, p.291):[^dehghani2022]

| 차원 | 탐색·부트스트랩 | 확장·규모 | 추출·지속 |
|---|---|---|---|
| 플랫폼 서비스 | 필수·다수 유틸리티 플레인 | 경험 플레인 다수 | 자동 복구 |
| 셀프서브 수준 | 제한적 셀프서브 (예: 풀 리퀘스트) | 성숙한 셀프서브 | 소수 지각자를 위해 최적화 |
| 플랫폼 사용자 | 고급 사용자 | 제너럴리스트 기술자 다수 | 소수 지각자 |
| 플랫폼 개발 | 견해 있는(opinionated) 기반에 집중 | 서비스 다양성에 집중 | 경험 최적화, 위험 낮추기 |

- 초기 단계의 유틸리티 플레인 편중이 명시된다 — **플랫폼은 주로 유틸리티 플레인의 필수 기반
  능력 — 저장·연산·계정·접근 통제·변환 — 을 확립하고 있다. 기본 데이터 프로덕트 수명 주기
  관리와 전역 주소 지정 가능성 같은 원시적 데이터 프로덕트 경험 서비스 집합이 개발된다. 기본
  발견 가능성 같은 메시 경험 플레인 능력은 아주 적다** (15장, p.292).[^dehghani2022]
  세 플레인이 [멀티플레인 데이터 플랫폼](../concepts/multiplane-data-platform.md)에 있다.
- 셀프서브를 초기에 짓는 것을 명시적으로 이르다고 판정한다 — **이 단계에서 플랫폼 셀프서브
  구현은 시기상조이며, 풀 리퀘스트 기반 스크립트 공유만큼 단순할 수 있다** (15장,
  p.292).[^dehghani2022]
- 초기 플랫폼은 좁은 것이 미덕이다 — **초기 단계에서 플랫폼은 견해가 있고, 추진력을 얻는 데
  필요한 것에 집중하기 위해 지원 기술의 집합이 제한된다** (15장, p.292).[^dehghani2022]
- 확장 단계에서 플랫폼 밖에 남는 팀을 허용하되 대가를 지운다 — **플랫폼이 제공하는 것과 다른
  기술 집합을 쓰고자 하는 팀은 플랫폼 밖에 남게 되며 메시 거버넌스와 호환성 요구사항을 충족할
  종단 책임을 지게 된다. 이 범주에 드는 팀은 소수여야 한다** (15장, p.292).[^dehghani2022]
- 추출 단계 — **플랫폼은 자동 관측 가능성·자동 치유·규모에서의 높은 회복력이라는 성숙 상태에
  있다. 메시의 어떤 다운타임도 대규모 결과를 낳을 수 있다** (15장, p.292).[^dehghani2022]

## ④ 연합 컴퓨테이셔널 거버넌스의 단계별 특성

그림 15-9가 네 차원으로 나눈다 (15장, p.293):[^dehghani2022]

| 차원 | 탐색·부트스트랩 | 확장·규모 | 추출(Exploit)·지속 |
|---|---|---|---|
| 도메인 수 | 제한된 수 | 도메인이 빠르게 온보딩 | 도메인 수 안정화 |
| 운영 모델 성숙도 | 기본: 원칙·유인 | 확립: 온보딩·구조·프로세스 | 자동화된 관측 가능성·복구 |
| 개발 초점 | 운영 모델, 필수 정책 | 정책 커버리지와 다양성 | 정책 최적화 |
| 정책 커버리지 | 필수: 보안·프라이버시 표준화 등 | 폭 우선 커버리지 | 향상된 기능 |

- 그림 15-9의 셋째 단계 라벨은 다른 세 그림의 "Extract | Sustain"과 달리 **"Exploit |
  Sustain"**으로 적혀 있다 (15장, p.293).[^dehghani2022] 본문은 이 단계를 계속 "extract
  and sustain"으로 부르므로 도판의 표기 흔들림으로 보인다. #hypothesis
- 초기 거버넌스가 하는 일 — **거버넌스 운영은 의사 결정 과정을 안내하는 원칙을 확립하고, 조직이
  무엇을 전역적으로 구현해야 하고 무엇을 도메인에 맡길 수 있는지를 결정한다. 도메인 데이터
  프로덕트 팀의 전역 유인이 정의되어 그들의 지역 도메인 유인을 증강한다** (15장,
  p.293).[^dehghani2022]
- **기존 거버넌스 조직이 해체되는 경로가 구체적으로 적혀 있다** — **이 단계 동안 기존 거버넌스
  구조가 연합 모델로 재편된다. 기존 거버넌스 그룹의 구성원은 주제 전문가(subject matter
  expert) 역할을 맡거나, 교차 기능 정책 자동화의 제품 관리를 도우러 플랫폼 팀에 합류하거나,
  데이터 프로덕트 소유자로서 도메인에 합류한다** (15장, p.293).[^dehghani2022]
- 정책 구현의 초기 경로도 명시된다 — **초기에는 데이터 프로덕트 개발자가 자기 정책 구현을 지을
  수 있고, 플랫폼은 나중에 그것을 셀프서브 능력으로 수확한다. 초기 정책 구현 일부에 대한 일종의
  크라우드소싱이다** (15장, p.293).[^dehghani2022]
- 확장 단계 — **새 도메인을 메시에 온보딩하는 과정이 마찰 없다. 연합 거버넌스 팀의 구성원 수가
  조직 내 도메인 다수를 포함하도록 늘어난다. (…) 이 시기에 정책 다수가 자동화되어 상호운용 가능하고
  안전한 데이터 프로덕트가 많은 메시를 뒷받침한다. 정책의 기본 모니터링이 자리 잡는다** (15장,
  pp.293–294).[^dehghani2022]
- 추출 단계 — **메시 위 모든 데이터 프로덕트가 자동화된 정책을 내장하고 있다. 정책 위험과 준수
  결여를 **탐지**해 데이터 프로덕트 팀에 알리는 자동화된 프로세스가 자리 잡아, 플랫폼이 제공하는
  자동화 도구로 우려를 다루게 한다** (15장, p.294).[^dehghani2022]
  이 "정책을 데이터 프로덕트 안에 심는다"가
  [내장 정책과 코드로서의 정책](../concepts/embedded-policies-as-code.md)의 종착 상태다.

## 단계마다 가치가 나오는 곳이 다르다

저자는 도메인 소유권 서술에서 단계마다 가치의 출처를 명시적으로 갈라 적는다 (15장,
p.289):[^dehghani2022]

- 탐색·부트스트랩 — **이 단계에서 가치는 적은 수의 고가치 유스케이스를 막힘에서 풀어 주는
  데서 온다.**
- 확장·규모 — **이 단계에서 가치는 긍정적 네트워크 효과(positive network effect)에서 온다.**
- 추출·지속 — **이 단계에서 가치는 조직 전반의 일관성과 완전성 효과(consistency and
  completeness effects)에서 온다.**

- 이 세 줄이 실무적으로 중요한 이유: **같은 지표로 세 단계를 평가하면 안 된다**는 뜻이기
  때문이다. 초기에 네트워크 효과를 요구하거나 후기에 "막힘 해소"를 세면 판정이 어긋난다. 무엇을
  재는가는 [데이터 메시의 적합성 함수](../concepts/data-mesh-fitness-functions.md)가 받는다.
- 네트워크 효과라는 낱말은 프롤로그에서 이미 나온다 — [데이터 메시](../concepts/data-mesh.md)가
  그 자리다.
