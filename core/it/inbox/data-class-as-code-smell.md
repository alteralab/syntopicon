하나의 질문: **필드만 담고 행동이 없는 클래스를 만들었다. 이것은 언제 문제이고 언제
정당한가.**

## 이 절이 옮겨 온 것

- 이 장은 도구를 먼저 소개하고 그 뒤에 경고를 단다 — **데이터 클래스는 편리하지만 그것을
  남용하면 당신의 프로젝트가 고생할 수 있다** (5장 §"@dataclass Example: Dublin Core
  Resource Record" 맺음, p.189).[^ramalho2022]
- 경고의 형식이 특이하다. **저자가 마틴 파울러의 글 "Code Smell"을 전문 그대로
  재수록한다.** 각주에 사정이 적혀 있다 — **나는 마틴 파울러를 Thoughtworks의 동료로 둔
  행운이 있어서, 그의 허락을 얻는 데 20분밖에 걸리지 않았다** (5장 각주 9,
  p.190).[^ramalho2022]
- 장 머리의 제사(epigraph)도 같은 계보다 (5장 제사, p.163):[^ramalho2022]
  > Data classes are like children. They are okay as a starting point, but to
  > participate as a grownup object, they need to take some responsibility.
  >
  > — Martin Fowler and Kent Beck
  - 출처가 각주에 적혀 있다 — **Refactoring 초판, 3장 "Bad Smells in Code", Data Class
    절, 87쪽** (5장 각주 1, p.163).[^ramalho2022] 그리고 저자가 **이 최신판에는 이 장의
    제사에 쓴 "Data classes are like children…" 인용이 빠져 있다**고 적는다
    (5장 §"Further Reading", p.197).[^ramalho2022] 이 KB에 들어와 있는
    [코드 냄새](code-smells.md)는 그 2판이므로, 이 제사는 그쪽에서 찾을 수 없다.

## 냄새라는 말의 정의

파울러의 글이 이 페이지에 정의를 공급한다 (5장 §"Data Class as a Code Smell" 안에
재수록된 Martin Fowler, "Code Smell", pp.190–191).[^ramalho2022]

- 정의 — **코드 냄새는 보통 시스템의 더 깊은 문제에 대응하는 표면적 징후다. 그 용어는 켄트
  벡이 내 Refactoring 책을 도와주는 동안 처음 만들었다.**
- 미세한 점 둘이 따라온다.
  - **첫째로 냄새는 정의상 빨리 알아챌 수 있는 것 — 내가 최근에 표현한 대로 "코를 킁킁댈 수
    있는(sniffable)" 것이다. 긴 메서드가 좋은 예다 — 그저 코드를 보다가 자바 열 줄 남짓을
    넘기면 내 코가 실룩거린다.**
  - **둘째는 냄새가 언제나 문제를 가리키지는 않는다는 것이다. 어떤 긴 메서드는 그냥 괜찮다.
    거기 밑에 깔린 문제가 있는지 보려면 더 깊이 들여다봐야 한다 — 냄새는 그 자체로 본질적으로
    나쁜 것이 아니다. 그것들은 흔히 문제 자체라기보다 문제의 지표다.**
- 데이터 클래스가 좋은 냄새의 예로 지목된다 — **가장 좋은 냄새는 알아채기 쉬우면서 대부분의
  경우 정말로 흥미로운 문제로 인도하는 것이다. 데이터 클래스(전부 데이터이고 행동이 없는
  클래스)가 그 좋은 예다. 그것들을 보면서 스스로에게 물어라, 이 클래스에 어떤 행동이 있어야
  하는가? 그러고 나서 그 행동을 거기로 옮기는 리팩터링을 시작한다.**
- 그리고 냄새의 조직적 쓰임 하나가 붙는다 — **냄새의 좋은 점 하나는 경험이 부족한 사람도
  알아채기 쉽다는 것이다. (…) 나는 "이번 주의 냄새"를 골라 사람들에게 그 냄새를 찾아 팀의
  선임에게 가져오라고 하는 리드 개발자들 이야기를 들었다. 한 번에 냄새 하나씩 하는 것은
  팀 사람들을 더 나은 프로그래머로 점진적으로 가르치는 좋은 방법이다.**
  - 이것이 [코드 냄새](code-smells.md)의 "왜 냄새인가 — 계측을 포기한 자리"와 같은 논지의
    다른 각도다. 그쪽이 **정확한 계측을 포기한 대가로 얻는 것**을 말한다면, 여기서는
    **가르치기 쉬움**을 그 이득으로 든다.

## 왜 데이터만 있는 클래스가 문제인가

- 근거가 객체 지향의 정의로 소급된다 — **객체 지향 프로그래밍의 주된 생각은 행동과 데이터를
  같은 코드 단위, 즉 클래스에 함께 놓는 것이다. 어떤 클래스가 널리 쓰이는데 자기 자신의
  유의미한 행동이 없다면, 그 인스턴스를 다루는 코드가 시스템 전체의 메서드와 함수에 흩어져
  있고 심지어 중복돼 있을 가능성이 있다 — 유지보수 두통의 처방전이다. 그래서 파울러가 데이터
  클래스를 다루는 리팩터링들이 책임을 그 안으로 되가져오는 것이다**
  (5장 §"Data Class as a Code Smell", p.191).[^ramalho2022]
- 장 요약이 그것을 한 줄로 다시 적는다 — **그다음 우리는 데이터 클래스의 오용이 객체 지향
  프로그래밍의 기본 원리 — 데이터와 그것을 만지는 함수는 같은 클래스 안에 함께 있어야
  한다 — 를 무너뜨릴 수 있다고 경고했다. 논리가 없는 클래스는 잘못 놓인 로직의 신호일 수
  있다** (5장 §"Chapter Summary", p.196).[^ramalho2022]
- **진단의 대상이 클래스가 아니라 흩어진 코드라는 점이 이 절의 정확한 지점이다.** 문제는
  "필드만 있는 클래스가 존재한다"가 아니라 "그 필드를 만지는 코드가 다른 곳에 흩어져
  있다"이다. 그래서 처방이 클래스를 없애는 것이 아니라 **행동을 그 안으로 옮기는
  것**이 된다.

## 정당한 두 경우

**저자는 냄새를 인정한 뒤 예외를 명시한다** — **그것을 고려하더라도, 행동이 거의 또는 전혀
없는 데이터 클래스를 갖는 것이 말이 되는 흔한 시나리오가 두어 개 있다**
(5장 §"Data Class as a Code Smell", p.191).[^ramalho2022]

- **① 비계로서의 데이터 클래스** (5장 §"Data Class as Scaffolding", p.191):[^ramalho2022]
  - **이 시나리오에서 데이터 클래스는 새 프로젝트나 모듈을 띄우기 위한 초기의 단순한 클래스
    구현이다. 시간이 지나면 그 클래스는 자기 인스턴스를 다루기 위해 다른 클래스의 메서드에
    기대는 대신 자기 자신의 메서드를 가져야 한다. 비계는 임시적이다. 결국 당신의 맞춤
    클래스는 그것을 시작하는 데 쓴 빌더로부터 완전히 독립적이 될 수 있다.**
  - **단서가 파이썬 특유다** — **파이썬은 빠른 문제 해결과 실험에도 쓰이며, 그럴 때는 비계를
    그대로 두어도 괜찮다.**
- **② 중간 표현으로서의 데이터 클래스** (5장 §"Data Class as Intermediate
  Representation", p.191):[^ramalho2022]
  - **데이터 클래스는 JSON이나 다른 교환 형식으로 내보내려는 레코드를 짓거나, 어떤 시스템
    경계를 막 넘어 들어온 데이터를 담는 데 유용할 수 있다. 파이썬의 데이터 클래스 빌더들은
    전부 인스턴스를 평범한 `dict`로 변환하는 메서드나 함수를 제공하며, `**`로 펼친 `dict`를
    키워드 인자로 써서 언제든 생성자를 부를 수 있다. 그런 `dict`는 JSON 레코드에 매우
    가깝다.**
  - **이 경우에 붙는 단서가 이 절의 실무 조문이다** — **이 시나리오에서 데이터 클래스
    인스턴스는 불변 객체로 다뤄져야 한다 — 필드가 가변이더라도 그것들이 이 중간 형태에 있는
    동안에는 바꾸지 말아야 한다. 그렇게 하면 데이터와 행동을 가까이 두는 핵심 이득을 잃게
    된다. 가져오기·내보내기에서 값을 바꿔야 한다면, 주어진 "as dict" 메서드나 표준 생성자를
    쓰는 대신 자기만의 빌더 메서드를 구현해야 한다.**
- **이 두 경우가 이 KB의 소비 맥락과 정확히 겹친다.** "함수 사이로 데이터를 딕셔너리가 아니라
  구조체로 넘긴다"는 규약은 ②에 해당한다 — 시스템 경계나 함수 경계를 넘는 중간 표현이다.
  그러므로 그 규약을 채택할 때 함께 오는 조건이 위 단서다: **그 구조체는 넘어가는 동안
  불변으로 다뤄야 하고, 값을 바꿔야 하는 순간이 오면 그것은 구조체가 아니라 객체가 되어야
  한다는 신호다.**

## 파울러의 냄새 항목과 갈리는가 — 갈리지 않는다

이 KB에는 [코드 냄새](code-smells.md)가 먼저 들어와 있고 그 안에 *Data Class* 항목이 있다.
겉보기에는 "데이터 클래스는 냄새다"(파울러)와 "데이터 클래스 빌더를 쓰라"(라말류)가 부딪히는
것처럼 보인다. **실측 판정은 모순이 아니다.** 근거 셋이다.

- **① 라말류가 파울러를 인용하고 지지한다.** 이 절은 반박이 아니라 재수록이다. 저자는
  파울러의 정의를 그대로 옮기고 **그래서 파울러가 데이터 클래스를 다루는 리팩터링들이 책임을
  그 안으로 되가져오는 것이다**라고 그 처방까지 승인한다 (5장 §"Data Class as a Code
  Smell", p.191).[^ramalho2022]
- **② 파울러 쪽이 이미 같은 예외를 명시한다.** 2판의 *Data Class* 항목이 그것을 적는다 —
  **그러나 예외가 있고, 최선의 예외 중 하나가 별개의 함수 호출에서 나온 결과 레코드로 쓰이는
  레코드다. (…) 그런 결과 레코드의 핵심 특성은 그것이 (적어도 실제로는) 불변이라는 것이다**
  (Fowler 2018, 3장 §"Data Class", p.83 — 전문은 [코드 냄새](code-smells.md)에 있다).
  이것이 라말류의 **② 중간 표현**과 같은 것이고, **불변**이라는 단서까지 일치한다.
- **③ 갈리는 것은 명제가 아니라 대상이다.** 파울러가 겨냥하는 것은 **널리 쓰이면서 행동이
  없는 도메인 클래스**이고, 라말류가 권하는 것은 **보일러플레이트를 대신 써 주는 도구**다.
  도구가 만드는 클래스가 냄새가 되는지는 그 클래스가 무엇으로 쓰이느냐가 정한다 — 그리고
  그 판정 기준을 라말류가 파울러에게서 그대로 빌려 온다.
- 그래서 **`contradicts`를 걸지 않는다.** 대신 두 쪽을 서로 가리키게 두었다. 남는 실무
  지침은 하나로 합쳐진다: **빌더를 쓰되, 그 클래스가 중간 표현이나 비계의 자리를 벗어나
  도메인의 중심으로 자라기 시작하면 행동을 그 안으로 옮겨라.**
  - 같은 지점을 [값 객체와 엔티티](value-objects-and-entities.md)가 다른 낱말로 말한다 —
    **정체성이 없다는 것과 행동이 없다는 것은 다른 말이다.** 값 객체는 `frozen`
    데이터클래스로 만들어지지만 화폐 연산 같은 행동을 갖는다. 즉 데이터 클래스 빌더로 만든
    것이 곧 "데이터 클래스 냄새"인 것은 아니다.

## 셋째 소스가 대는 일반 조건

논쟁 중인 소스([소스 메타](../sources/martin2008.md))의 6장이 이 물음에 셋째 근거를
댄다. **위 판정을 뒤집지 않고 그 정당성의 일반 조건을 준다.**

- 그쪽의 정의는 객체와 자료 구조를 **서로의 반대**로 놓는다 — **객체는 데이터를 추상 뒤에
  감추고 그 데이터에 작용하는 함수를 노출한다. 자료 구조는 데이터를 노출하고 의미 있는
  함수를 갖지 않는다** (6장 §"Data/Object Anti-Symmetry", p.95).[^martin2008]
- 그리고 그 반대칭이 변경 용이성의 교환으로 정식화된다 (6장 §"Data/Object Anti-Symmetry",
  p.97):[^martin2008]

> Procedural code (code using data structures) makes it easy to add new functions without
> changing the existing data structures. OO code, on the other hand, makes it easy to add
> new classes without changing existing functions.

- **그래서 판단 기준이 나온다** — 새 데이터 타입을 더하는 일이 잦은 부분에서는 객체가,
  **새 함수를 더하는 일이 잦은 부분에서는 절차적 코드와 자료 구조가 더 적절하다** (6장
  §"Data/Object Anti-Symmetry", p.97).[^martin2008] 그리고 조문 (6장, p.97):[^martin2008]

> Mature programmers know that the idea that everything is an object *is a myth*.

- **위 [정당한 두 경우](#정당한-두-경우)와의 관계.** 그쪽이 "비계"와 "중간 표현"이라는
  **용례**로 정당성을 좁혔다면, 이 소스는 **변경 축의 방향**이라는 일반 조건을 댄다. 두
  설명이 어긋나지 않는다 — 중간 표현은 새 함수(파싱·변환·직렬화)가 새 타입보다 자주 붙는
  자리다.
- 그리고 **이름 붙은 실물 둘**을 더한다 — DTO(**공개 변수를 갖고 함수가 없는 클래스**,
  6장 §"Data Transfer Objects", p.100)와 액티브 레코드(**save·find 같은 항해 메서드를 가진
  자료 구조**, 6장 §"Active Record", p.101).[^martin2008]
- **잡종에 대한 판정은 세 소스가 같다** — **그런 잡종은 새 함수를 더하기도 어렵게 만들고
  새 자료 구조를 더하기도 어렵게 만든다. 그것들은 두 세계의 최악이다. 만들지 마라** (6장
  §"Hybrids", p.99).[^martin2008] 이 페이지가 냄새로 보는 것과 같은 대상이다.
- **`contradicts`를 걸지 않는다.** 어느 소스도 "모든 데이터 클래스는 나쁘다"나 "모든
  데이터 클래스는 좋다"는 전칭 주장을 하지 않는다. 전문은
  [객체와 자료 구조](objects-versus-data-structures.md)에 있다.
