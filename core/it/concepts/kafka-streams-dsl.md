하나의 질문: **카프카 스트림즈로 스트림 처리 토폴로지를 어떻게 정의하고 실행하는가.**

- 버전 조건: Kafka 0.10.0 이상 — **카프카는 인기 있는 모든 스트림 처리 프레임워크에
  신뢰성 있는 데이터 스트림 원천을 제공하는 것 이상을 한다. 이제 카프카는 클라이언트
  라이브러리 모음의 일부로 카프카 스트림즈(Kafka Streams, 때로 Streams API)라 불리는
  강력한 스트림 처리 라이브러리를 포함**하며, 이로써 **개발자는 외부 처리 프레임워크에
  의존하지 않고 자기 앱 안에서 이벤트를 소비·처리·생산할 수 있다** (14장,
  p.381).[^shapira2021]

## 버전 조건

> **버전 조건**: Kafka 2.8 기준. **카프카 스트림즈는 아직 진화 중인 프레임워크이고 주요
> 릴리스마다 API를 폐기하고 의미론을 수정한다**고 책이 밝힌다. 이 장은 **아파치 카프카
> 2.8 시점의 API와 의미론을 문서화**했고 **3.0에서 폐기 예정이던 API는 쓰지 않았으나**,
> **조인 의미론과 타임스탬프 처리에 대한 3.0 예정 변경은 반영돼 있지 않다** (14장,
> p.382).[^shapira2021]

## 두 개의 스트림 API

- **아파치 카프카에는 스트림 API가 둘 있다 — 저수준 Processor API와 고수준 Streams DSL**이며
  책의 예제는 DSL을 쓴다. **DSL은 스트림의 이벤트에 적용될 변환의 사슬을 정의함으로써
  스트림 처리 애플리케이션을 정의하게 해 준다. 변환은 필터처럼 단순할 수도, 스트림 대 스트림
  조인처럼 복잡할 수도 있다. 저수준 API는 우리 자신의 변환을 만들게 해 준다** (14장,
  p.402).[^shapira2021]
- **DSL API를 쓰는 애플리케이션은 언제나 `StreamsBuilder`로 처리 토폴로지 — 스트림의
  이벤트에 적용되는 변환의 유향 비순환 그래프(DAG) — 를 만드는 것으로 시작한다. 그다음
  토폴로지로부터 `KafkaStreams` 실행 객체를 만든다. `KafkaStreams` 객체를 시작하면 여러
  스레드가 시작되고 각각이 스트림의 이벤트에 처리 토폴로지를 적용한다. 처리는
  `KafkaStreams` 객체를 닫을 때 끝난다** (14장, p.402).[^shapira2021]
- 예제로 특정 API를 고른 이유도 밝혀 둔다 — **쓰기가 비교적 단순하고 아파치 카프카에
  딸려 오기 때문**이며, **패턴은 보편적이고 예제만 특정적이라는 것을 기억하는 것이
  중요하다** (14장, p.402).[^shapira2021]

## 모든 앱이 먼저 정하는 것

- 카프카 스트림즈 앱을 만들 때 **가장 먼저 하는 일은 카프카 스트림즈를 설정하는 것**이며,
  **카프카 스트림즈에 딸린 프로듀서·컨슈머는 `Properties` 객체에 프로듀서·컨슈머 설정을
  추가해 설정**할 수 있다 (14장, p.402).[^shapira2021] 그 설정들의 의미는
  [프로듀서 설정](../concepts/kafka-producer-configuration.md)과
  [컨슈머 설정](../concepts/kafka-consumer-configuration.md).
- 반드시 정하는 것 셋 — `StreamsConfig.APPLICATION_ID_CONFIG`,
  `StreamsConfig.BOOTSTRAP_SERVERS_CONFIG`, 그리고 기본 Serde 두 개
  (`DEFAULT_KEY_SERDE_CLASS_CONFIG`·`DEFAULT_VALUE_SERDE_CLASS_CONFIG`) (14장,
  p.403):[^shapira2021]
  - **모든 카프카 스트림즈 애플리케이션은 애플리케이션 ID를 가져야 한다. 애플리케이션의
    인스턴스들을 조율하는 데, 그리고 내부 로컬 저장소와 그에 관련된 토픽의 이름을 짓는 데
    쓰인다. 같은 카프카 클러스터를 쓰는 카프카 스트림즈 애플리케이션마다 이 이름은
    유일해야 한다.**
  - **카프카 스트림즈 애플리케이션은 언제나 카프카 토픽에서 데이터를 읽고 카프카 토픽으로
    출력을 쓰며, 조율에도 카프카를 쓴다. 그러니 카프카를 어디서 찾는지 알려 주는 편이
    낫다.**
  - **데이터를 읽고 쓸 때 직렬화·역직렬화가 필요하므로 기본 Serde 클래스를 제공한다.
    필요하면 스트림 토폴로지를 짓는 시점에 이 기본값을 재정의할 수 있다.**
- Serde를 만드는 법에 대한 권고 — **카프카에 저장하고 싶은 모든 객체(입력·출력, 경우에
  따라 중간 결과)에 대해 Serde 객체를 제공해야 함을 기억하라. 이를 쉽게 하려면 Gson·
  에이브로·프로토버프 같은 라이브러리로 Serde를 생성하기를 권한다** (14장,
  p.405).[^shapira2021] 스키마와 직렬화의 지형은
  [카프카 직렬화와 스키마 레지스트리](../concepts/kafka-serialization-and-schema-registry.md).

## 단어 개수 세기

- 첫 예제는 **단어 개수 세기(word count)** 로 **맵/필터 패턴과 단순 집계를 보인다** (14장,
  pp.402–404).[^shapira2021] 토폴로지는 한 줄의 사슬이다 —
  `builder.stream("wordcount-input")`으로 입력 토픽을 가리켜 스트림을 정의하고,
  `flatMapValues`로 정규식을 써서 한 줄을 개별 단어들로 쪼개고, `map`으로 **각 단어를
  이벤트 레코드의 키에 넣어 그룹별 연산에 쓸 수 있게** 하고, `filter`로 단어 `the`를
  걸러 내고(**필터가 얼마나 쉬운지 보이려고 넣었다**), `groupByKey`로 **유일한 단어마다
  이벤트의 모음**을 만들고, `count`로 세고, `mapValues`로 **세기 결과인 `Long`을 사람이
  읽기 쉽게 `String`으로 바꾸고**, `counts.to("wordcount-output")`로 결과를 카프카에 되쓴다.
- 이것이 보여 준 것을 책이 정리한다 — **몇 줄 안 되는 코드로 단일 이벤트 처리 패턴(맵과
  필터)을 구현했고, 그룹별 연산자를 더해 데이터를 리파티션했으며, 각 단어를 키로 갖는
  레코드 수를 셀 때 단순한 로컬 상태를 유지했다** (14장, p.404).[^shapira2021] 그 패턴들의
  이름은 [스트림 처리 설계 패턴](../concepts/stream-processing-design-patterns.md).

## 주식 시장 통계

- 둘째 예제는 **주식 종목·매도 호가(ask price)·매도 물량(ask size)을 담은 주식 거래
  이벤트 스트림을 읽는다.** **매도 호가는 파는 쪽이 부르는 값이고 매수 호가(bid price)는
  사는 쪽이 제안하는 값이며, 매도 물량은 파는 쪽이 그 가격에 팔 의향이 있는 주식 수**다.
  예제의 단순화를 위해 **매수는 완전히 무시하고, 데이터에 타임스탬프를 넣지 않고 카프카
  프로듀서가 채우는 이벤트 시간에 의존**한다 (14장, p.405).[^shapira2021]
- 만드는 출력은 **5초 윈도우마다의 최저(최선) 매도 호가, 5초 윈도우마다의 거래 수, 5초
  윈도우마다의 평균 매도 호가**이고 **모든 통계는 매초 갱신**된다 (14장,
  p.405).[^shapira2021]
- 앞 예제와의 주된 차이는 **쓰이는 Serde 클래스**다 — **단어 개수에서는 키·값 모두
  문자열이라 `Serdes.String()`을 썼지만, 여기서는 키는 여전히 문자열이되 값이 종목 기호·
  매도 호가·매도 물량을 담은 `Trade` 객체**다. 책은 **구글의 Gson 라이브러리로 자바 객체에서
  JSON 시리얼라이저·디시리얼라이저를 생성하고 그것들로 `Serde` 객체를 만드는 작은 감싸개**를
  만들었다 (14장, pp.405–406).[^shapira2021]
- 아래가 그 토폴로지이며 — `windowedBy`·`TimeWindows.of`·`advanceBy`·`aggregate`·
  `Materialized`로 찾는다 — 윈도우 집계를 하는 스트림 앱의 뼈대다 (14장,
  p.406):[^shapira2021]

  ```java
  KStream<Windowed<String>, TradeStats> stats = source
      .groupByKey()
      .windowedBy(TimeWindows.of(Duration.ofMillis(windowSize))
                             .advanceBy(Duration.ofSeconds(1)))
      .aggregate(
          () -> new TradeStats(),
          (k, v, tradestats) -> tradestats.add(v),
          Materialized.<String, TradeStats, WindowStore<Bytes, byte[]>>
              as("trade-aggregates")
              .withValueSerde(new TradeStatsSerde()))
      .toStream()
      .mapValues((trade) -> trade.computeAvgPrice());

  stats.to("stockstats-output",
      Produced.keySerde(
        WindowedSerdes.timeWindowedSerdeFrom(String.class, windowSize)));
  ```

- 책이 각 단계에 붙인 설명 (14장, pp.406–407):[^shapira2021]
  - **`groupByKey()`는 이름과 달리 아무 그룹화도 하지 않는다. 오히려 이벤트 스트림이 레코드
    키에 기반해 파티션되도록 보장한다.** 예제는 **키와 함께 데이터를 토픽에 썼고
    `groupByKey()` 호출 전에 키를 수정하지 않았으므로 데이터는 여전히 키로 파티션돼 있고
    이 메서드는 이 경우 아무것도 하지 않는다.**
  - **윈도우를 정의한다 — 이 경우 5초짜리 윈도우가 매초 전진한다.**
  - **올바른 파티셔닝과 윈도우를 확보한 뒤 집계를 시작한다. `aggregate` 메서드는 스트림을
    서로 겹치는 윈도우(매초마다 5초 윈도우)로 쪼갠 뒤 윈도우 안의 모든 이벤트에 집계
    메서드를 적용한다.** 첫 파라미터는 **집계 결과를 담을 새 객체(여기서는 `TradeStats`)** 이고,
    이는 **각 시간 윈도우에 대해 관심 있는 통계 전부 — 최저가·평균가·거래 수 — 를 담도록
    만든 객체**다.
  - 그다음 **레코드를 실제로 집계하는 메서드를 공급한다 — 여기서는 `TradeStats` 객체의
    `add` 메서드가 새 레코드로 윈도우의 최저가·거래 수·가격 총합을 갱신한다.**
  - **윈도우 집계는 상태와 그 상태를 담을 로컬 저장소의 유지를 요구하므로 `aggregate`
    메서드의 마지막 파라미터가 상태 저장소의 설정이다. `Materialized`가 저장소 설정 객체이고
    저장소 이름을 `trade-aggregates`로 설정했다. 어떤 유일한 이름이든 된다.** 상태 저장소가
    무엇을 떠안는지는 [스트림 처리의 상태](../concepts/stream-processing-state.md).
  - **상태 저장소 설정의 일부로 집계 결과(`TradeStats` 객체)를 직렬화·역직렬화할 `Serde`
    객체도 제공한다.**
  - **집계의 결과는 종목과 시간 윈도우를 기본 키로, 집계 결과를 값으로 갖는 테이블이다.
    그 테이블을 다시 이벤트의 스트림으로 되돌린다.**
  - **마지막 단계는 평균가를 갱신하는 것** — **지금 집계 결과에는 가격의 합과 거래 수가
    들어 있으므로, 이 레코드들을 훑으며 기존 통계로 평균가를 계산해 출력 스트림에
    포함시킨다.**
  - **끝으로 결과를 `stockstats-output` 스트림에 되쓴다. 결과가 윈도우 연산의 일부이므로
    윈도우 타임스탬프를 포함하는 윈도우 데이터 형식으로 결과를 저장하는 `WindowedSerde`를
    만든다. 윈도우 크기는 직렬화에 쓰이지 않는데도 Serde의 일부로 넘겨진다 — 역직렬화에
    윈도우 크기가 필요하기 때문이며, 출력 토픽에는 윈도우의 시작 시각만 저장되기
    때문이다.**
- 이 예제가 보인 것 — **스트림에 대한 윈도우 집계를 수행하는 법이며, 아마 스트림 처리의
  가장 인기 있는 유스케이스**다. **주목할 것은 집계의 로컬 상태를 유지하는 데 얼마나 적은
  일이 필요했는가 — Serde를 주고 상태 저장소의 이름을 지은 것이 전부**다. 그런데도 **이
  애플리케이션은 여러 인스턴스로 확장되고, 각 인스턴스 장애에서 일부 파티션의 처리를 살아
  있는 인스턴스로 옮겨 자동으로 복구**된다 (14장, p.407).[^shapira2021] 그 기제는
  [카프카 스트림즈 아키텍처](../concepts/kafka-streams-architecture.md).

## 클릭 스트림 보강

- 셋째 예제는 **웹사이트 클릭 스트림을 보강해 스트리밍 조인을 보인다.** **시뮬레이션된
  클릭 스트림, 가상의 프로필 데이터베이스 테이블에 대한 갱신 스트림, 웹 검색 스트림을
  생성한 뒤 세 스트림을 모두 조인해 각 사용자 활동에 대한 360도 뷰를 얻는다** —
  **사용자가 무엇을 검색했는가, 그 결과로 무엇을 클릭했는가, 프로필의 "관심사"를 바꿨는가.**
  **이런 조인은 분석을 위한 풍부한 데이터 수집을 제공하며, 상품 추천이 흔히 이런 정보에
  기반**한다 (14장, p.408).[^shapira2021]
- 토폴로지에서 갈리는 자리는 셋이다 (14장, pp.408–409):[^shapira2021]
  - 클릭과 검색은 `builder.stream(...)`으로 스트림 객체를 만들고, **사용자 프로필은
    `builder.table(...)`로 `KTable`을 정의**한다 — **`KTable`은 변경의 스트림으로 갱신되는
    구체화된 저장소**다.
  - **클릭 스트림을 프로필 테이블과 조인해 사용자 프로필 정보로 보강**한다. **스트림-테이블
    조인에서 스트림의 각 이벤트는 캐시된 프로필 테이블 사본에서 정보를 받는다. 여기서는
    left join을 하므로 알려지지 않은 사용자의 클릭도 보존된다.** 조인 메서드는
    **스트림에서 하나, 레코드에서 하나 두 값을 받아 세 번째 값을 반환**하며 —
    **데이터베이스와 달리 두 값을 하나의 결과로 어떻게 결합할지 우리가 정한다.**
  - **흥미로운 부분은 스트림 대 스트림 조인이 시간 윈도우를 갖는 조인이라는 점**이다.
    **사용자별 모든 클릭과 검색을 조인하는 것은 별 의미가 없고, 각 검색을 그와 관련된
    클릭 — 검색 직후 짧은 시간 안에 일어난 클릭 — 과 조인하고 싶다.** 그래서 **1초짜리
    조인 윈도우를 정의한다.** `JoinWindows.of`로 **각 검색의 전후 1초 윈도우를 만들고**,
    `before`에 **0초 간격을 주어 검색 뒤 1초 안에 일어난 클릭만 조인하고 앞선 것은 조인하지
    않게** 한다.
- 이 예제가 보인 두 조인 패턴을 책이 정리한다 — **하나는 스트림을 테이블과 조인해 모든
  스트리밍 이벤트를 테이블의 정보로 보강하는 것이며, 이는 데이터 웨어하우스에서 질의를
  돌릴 때 팩트 테이블을 차원과 조인하는 것과 비슷하다. 둘째 예는 시간 윈도우에 기반해 두
  스트림을 조인하며, 이 연산은 스트림 처리에 고유하다** (14장, p.410).[^shapira2021]
  조인의 종류별 성질은
  [스트림-테이블 이중성과 조인](../concepts/stream-table-duality.md).

## 설치 없이 클러스터가 된다

- **아파치 카프카 말고는 아무것도 설치하지 않고 예제 전체를 자기 기계에서 돌릴 수 있다.
  입력 토픽에 파티션이 여럿이면 `WordCount` 애플리케이션의 인스턴스를 여럿 돌릴 수 있고
  (여러 터미널 탭에서 앱을 돌리기만 하면 된다) 그것이 첫 카프카 스트림즈 처리 클러스터**다.
  **인스턴스들은 서로 대화하며 작업을 조율**한다 (14장, pp.404–405).[^shapira2021]
- 이것이 진입 장벽에서 갈리는 지점이라고 책이 말한다 — **어떤 스트림 처리 프레임워크는
  로컬 모드는 아주 쉽지만 프로덕션 클러스터를 돌리려면 YARN이나 메소스를 설치하고 모든
  머신에 처리 프레임워크를 설치한 뒤 앱을 클러스터에 제출하는 법을 배워야 한다. 카프카의
  Streams API로는 앱 인스턴스를 여럿 시작하기만 하면 클러스터가 되고, 개발 기계와
  프로덕션에서 정확히 같은 앱이 돈다** (14장, p.405).[^shapira2021]

## 미해소

- 저수준 Processor API의 상세는 이 장이 외부로 넘긴다 — 책이 지목한 곳은 **카프카 스트림즈
  개발자 가이드(공식 문서)** 와 **발표 "Beyond the DSL"** 이다 (14장,
  p.402).[^shapira2021]
- 카프카 스트림즈의 설정 항목 전체도 **여기서 논의하지 않는다고 책이 명시**하고 문서로
  넘긴다 (14장, p.402).[^shapira2021] **카프카 스트림즈 공식 문서(Configuring a Streams
  Application)** 가 필요하다.
- 세 예제의 전체 코드는 **깃허브 저장소**에 있다고만 적혀 있다 (14장, pp.402·407·410).
  [^shapira2021]
