하나의 질문: **배치 처리가 실제로 쓰이는 자리는 어디이고 왜 거기인가.**

## 어디에 있는가

- 기준 — **배치 잡은 큰 데이터셋을 대량으로 처리하는 데 훌륭하지만 낮은 지연 유스케이스에는 좋지
  않다. 따라서 데이터가 많고 데이터 신선도가 중요하지 않은 곳이라면 어디서든 배치 잡을 발견하게 된다.
  이는 제약처럼 들릴지 모르지만, 알고 보면 상당한 양의 데이터 처리 작업이 이 모델에 들어맞는다**
  (11장, p.476).[^kleppmann2026]
- 책이 드는 실물 (11장, p.476):[^kleppmann2026]
  - **기업이 거래가 자기 은행 계좌·재고와 맞는지 검증하는 회계와 재고 대사(reconciliation)는 흔히
    배치 잡으로 수행된다.**
  - **제조업에서 수요 예측(demand forecasting)은 흔히 주기적 배치 잡으로 돈다.**
  - **이커머스·미디어·소셜 미디어 기업은 배치 잡으로 추천 모델을 훈련한다.**
  - **많은 금융 시스템이 배치 기반이다; 예컨대 미국 은행 네트워크는 거의 전부 배치 잡으로 돈다.**

## ETL

- 무엇이 배치와 맞는가 — **배치 잡의 병렬적 성격은 데이터 변환에 훌륭한 궁합이며, 그 대부분은
  "부끄러울 만큼 병렬적인(embarrassingly parallel)" 워크로드다. 데이터 필터링, 필드 투영, 그 밖의 많은
  흔한 데이터 웨어하우스 변환이 전부 병렬로 수행될 수 있다** (11장, p.476).[^kleppmann2026]
  ETL 자체의 뼈대는 [ETL 34 서브시스템](../concepts/etl-subsystems.md)이 담당한다.
- 고치기 쉽다는 성질이 여기서 값을 한다 — **배치 잡은 일이 잘못됐을 때 문제를 진단하고 고치기 쉽다는
  것도 보았다. 이 기능은 데이터 파이프라인을 디버깅할 때 값을 헤아릴 수 없다. 실패한 파일을 쉽게 살펴
  무엇이 잘못됐는지 볼 수 있고, ETL 배치 잡은 고쳐서 다시 돌릴 수 있다. 예컨대 입력 파일이 변환 배치
  잡이 쓰려는 필드를 담고 있지 않으면, 데이터 엔지니어는 그 필드가 없다는 것을 쉽게 짚어 내고 변환
  로직이나 입력을 생산한 잡을 갱신할 수 있다** (11장, p.477).[^kleppmann2026]
- 소유권이 옮겨 간다 — **데이터 파이프라인은 예전에 단일 데이터 엔지니어링 팀이 관리했는데, 제품 기능을
  다루는 다른 팀에 복잡한 배치 데이터 파이프라인을 쓰고 관리하라고 요구하는 것이 부당하게 여겨졌기
  때문이다. 최근 배치 처리 모델과 메타데이터 관리의 개선으로 조직 전체의 엔지니어가 자기 데이터
  파이프라인에 기여하고 관리하기가 훨씬 쉬워졌다. 데이터 메시(data mesh)·데이터 컨트랙트(data
  contract)·데이터 패브릭(data fabric) 관행이 팀들이 조직 내 누구든 소비할 수 있도록 자기 데이터를
  안전하게 발행하는 것을 돕는 표준과 도구를 제공한다** (11장, p.477).[^kleppmann2026]
- 경계가 더 흐려진다 — **데이터 파이프라인과 분석 질의는 처리 모델뿐 아니라 실행 엔진까지 공유하기
  시작했다. 이제 많은 배치 ETL 잡이 그 출력을 읽는 분석 질의와 같은 시스템에서 돈다. 데이터 파이프라인
  변환과 분석 질의가 둘 다 SparkSQL·Trino·DuckDB 질의로 도는 것을 보는 일이 드물지 않다. 그런 아키텍처는
  애플리케이션 엔지니어링·데이터 엔지니어링·애널리틱스 엔지니어링·비즈니스 분석 사이의 선을 더욱
  흐린다** (11장, p.477).[^kleppmann2026]

## 분석 — 레이크하우스

- **"운영 시스템 대 분석 시스템"에서 우리는 분석 질의(OLAP)가 흔히 많은 수의 레코드를 훑으며 그룹핑과
  집계를 수행하는 것을 보았다. 그런 워크로드를 다른 배치 처리 워크로드와 나란히 배치 처리 시스템에서
  돌리는 것이 가능하다. 분석가는 질의 엔진 위에서 실행되는 SQL 질의를 쓰고, 그 엔진은 분산 파일시스템이나
  오브젝트 스토어에서 읽고 쓴다. 테이블-파일 매핑·이름·타입 같은 테이블 메타데이터는 Apache Iceberg
  같은 테이블 형식과 Unity 같은 카탈로그로 관리된다. 이 아키텍처는 데이터 레이크하우스(data
  lakehouse)로 알려져 있다** (11장, p.477).[^kleppmann2026] 그 네 부품이 어떻게 쪼개졌는지는
  [데이터 레이크](../concepts/data-lake.md)에 있다.
- **ETL과 마찬가지로 SQL 질의 인터페이스의 개선은 많은 조직이 이제 분석에 Spark 같은 배치 프레임워크를
  쓴다는 뜻이다. 그런 질의 패턴은 두 스타일로 온다** (11장, pp.477–478):[^kleppmann2026]
  - **사전 집계 질의(pre-aggregation queries)** — **질의를 빠르게 하려고 데이터가 OLAP 큐브나 데이터
    마트로 롤업된다. 사전 집계된 데이터는 웨어하우스에서 질의되거나 Apache Druid나 Apache Pinot 같은
    전용 실시간 OLAP 시스템으로 밀어진다. 사전 집계는 보통 정해진 간격으로 일어난다.** 그 롤업의 구조는
    [데이터 큐브와 구체화 뷰](../concepts/data-cubes-and-materialized-views.md)에 있다.
  - **애드혹 질의(ad hoc queries)** — **사용자는 특정 비즈니스 질문에 답하고, 사용자 행동을 조사하고,
    운영 문제를 디버깅하는 등을 위해 이것을 돌린다. 이 유스케이스에서는 응답 시간이 중요하다. 분석가는
    응답을 받고 조사 중인 데이터에 대해 더 알아 가며 반복적으로 질의를 돌린다. 빠른 질의 실행을 갖춘 배치
    처리 프레임워크는 분석가의 대기 시간을 줄이는 데 도움이 된다.**
- 도구가 붙는다 — **SQL 지원은 배치 처리 프레임워크가 Tableau·Power BI·Looker·Apache Superset 같은
  스프레드시트와 데이터 시각화 도구와 통합될 수 있게 한다** (11장, p.478).[^kleppmann2026]

## 기계 학습

- **기계 학습(ML)은 배치 처리를 자주 쓴다. 데이터 과학자·ML 엔지니어·AI 엔지니어는 데이터 패턴을
  조사하고, 데이터를 변환하고, ML 모델을 훈련하는 데 배치 처리 프레임워크를 쓴다. 흔한 용도는 다음과
  같다** (11장, p.478):[^kleppmann2026]
  - **특징 공학(feature engineering)** — **원시 데이터가 모델을 훈련할 수 있는 데이터로 필터링되고
    변환된다. 예측 모델은 흔히 수치 데이터를 필요로 하므로 엔지니어는 (텍스트나 이산값 같은) 다른 형태의
    데이터를 요구되는 형식으로 변환해야 한다.**
  - **모델 훈련(model training)** — **훈련 데이터가 배치 프로세스의 입력이고 훈련된 모델의 가중치가
    출력이다.**
  - **배치 추론(batch inference)** — **데이터셋이 크고 실시간 결과가 필요하지 않으면 훈련된 모델로
    대량 예측을 할 수 있다. 여기에는 테스트 데이터셋에 대한 모델 예측 평가가 포함된다.**
- 그래프 알고리즘도 여기 붙는다 — **추천 엔진과 랭킹 시스템 같은 ML 애플리케이션도 그래프 처리를 많이
  쓴다. 많은 그래프 알고리즘은 한 번에 한 간선을 순회하며 어떤 정보를 전파하기 위해 한 정점을 인접
  정점과 조인하고, 어떤 조건이 충족될 때까지 반복하는 것으로 표현된다 — 예컨대 더 따라갈 간선이 없을
  때까지, 혹은 어떤 지표가 수렴할 때까지** (11장, p.478).[^kleppmann2026]
- 그 계산 모델의 이름 — **계산의 벌크 동기 병렬(bulk synchronous parallel, BSP) 모델이 그래프의 배치
  처리에 인기를 얻었다; 그것은 Apache Giraph, Spark의 GraphX API, Flink의 Gelly API 등이 구현한다.
  구글의 Pregel 논문이 그래프 처리에 이 접근을 대중화했기에 Pregel 모델로도 알려져 있다** (11장,
  pp.478–479).[^kleppmann2026] 그래프 데이터 모델 자체는
  [그래프 데이터 모델](../concepts/graph-data-models.md)에 있다.
- LLM도 여기 있다 — **배치 처리는 대규모 언어 모델 데이터 준비와 훈련의 필수적 부분이기도 하다.
  웹사이트 내용 같은 원시 텍스트 입력 데이터는 통상 DFS나 오브젝트 스토어에 있다. 이 데이터는 훈련에
  적합하게 만들기 위해 전처리돼야 한다** (11장, p.479).[^kleppmann2026] 배치에 잘 맞는 전처리
  단계로 **HTML에서 평문을 뽑고 잘못된 형식의 텍스트를 고치는 것**, **저품질·무관·중복 문서를 감지해
  제거하는 것**, **텍스트를 토큰화(단어로 쪼개기)하고 임베딩, 즉 각 단어의 수치 표현으로 변환하는 것**이
  꼽힌다 (11장, p.479).[^kleppmann2026]
- 그 워크로드 전용 프레임워크가 따로 있다 — **Kubeflow·Flyte·Ray 같은 배치 처리 프레임워크가 그런
  워크로드를 위해 특별히 만들어졌다. 예컨대 OpenAI는 ChatGPT 훈련 과정의 일부로 Ray를 쓴다. 이
  프레임워크들은 PyTorch·TensorFlow·XGBoost 등 LLM·AI 라이브러리를 위한 내장 통합을 갖는다. 그들은 또한
  특징 공학·모델 훈련·배치 추론·파인 튜닝(기반 모델을 특정 유스케이스에 맞게 조정하는 것)에 대한 내장
  지원을 제공한다** (11장, p.479).[^kleppmann2026]
- 마지막으로 노트북 — **데이터 과학자는 흔히 Jupyter나 Hex 같은 대화형 노트북에서 데이터를 실험한다.
  노트북은 마크다운·파이썬·SQL의 작은 덩어리인 셀로 이뤄진다. 셀은 순차적으로 실행돼 스프레드시트·그래프·
  데이터를 만든다. 많은 노트북이 DataFrame API를 통해 배치 처리를 쓰거나 SQL로 그런 시스템에 질의한다**
  (11장, p.479).[^kleppmann2026]
