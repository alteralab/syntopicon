하나의 질문: **무엇을 배치 처리라 부르고, 그 구분이 무엇을 바꾸는가.**

## 온라인 시스템과 오프라인 시스템

- 이 책이 여기까지 다룬 것의 성격부터 정리한다 — **이 책이 지금까지 이야기한 많은 것은 요청과
  질의, 그리고 그에 대응하는 응답과 결과였다. 이 스타일의 데이터 처리는 많은 현대 데이터
  시스템에서 가정된다: 무언가를 요청하거나 명령을 보내면 시스템이 가능한 한 빨리 답을 주려
  한다** (11장, p.451).[^kleppmann2026]
- 그 계열의 이름 — **웹 브라우저가 페이지를 요청하는 것, 서비스가 원격 API를 호출하는 것,
  데이터베이스·캐시·검색 색인, 그 밖의 많은 시스템이 이렇게 동작한다. 우리는 이것을 온라인
  시스템(online systems)이라 부른다. 응답 시간이 보통 이들의 주된 성능 척도이고, 높은
  가용성을 보장하기 위해 흔히 결함 내성을 요구한다** (11장, p.451).[^kleppmann2026]
- 반대편 — **그러나 때로는 대화형 요청 안에서 할 수 있는 것보다 더 큰 계산을 돌리거나 더 많은
  양의 데이터를 처리해야 한다. AI 모델을 훈련해야 할 수도, 많은 데이터를 한 형태에서 다른
  형태로 변환해야 할 수도, 아주 큰 데이터셋 위에서 분석을 계산해야 할 수도 있다. 우리는 이런
  작업을 배치 처리 잡(batch processing jobs)이라 부르고, 그것을 다루는 시스템을 때로 오프라인
  시스템(offline systems)이라 일컫는다** (11장, p.451).[^kleppmann2026]
- 재는 것이 다르다 — **배치 잡은 도는 데 오랜 시간이 걸릴 수 있다: 몇 분, 몇 시간, 심지어 며칠.
  잡은 주기적으로(예: 하루 한 번) 돌도록 일정이 잡힐 수 있다. 성능의 주된 척도는 보통
  처리량(throughput)이다 — 단위 시간당 잡이 처리할 수 있는 데이터의 양** (11장,
  p.452).[^kleppmann2026] 그 두 척도의 정의는
  [응답 시간과 처리량](../concepts/response-time-and-throughput.md)에 있다.
- 결함을 다루는 방식도 갈린다 — **어떤 배치 시스템은 그냥 잡 전체를 중단하고 재시작하는 것으로
  결함을 다루고, 다른 것들은 노드 일부가 크래시해도 잡이 성공적으로 완료될 수 있도록 결함
  내성을 갖는다** (11장, p.452).[^kleppmann2026]

## 배치 잡의 정의

- 원문 그대로 — **배치 처리 잡은 입력 데이터(읽기 전용이다)를 받아 출력 데이터(잡이 돌 때마다
  처음부터 생성된다)를 만든다. 그것은 통상 읽기/쓰기 트랜잭션이 하듯 데이터를 변이시키지
  않는다. 따라서 출력은 입력에서 유도된다. 출력이 마음에 들지 않으면 그것을 지우고 잡의 로직을
  조정한 뒤 잡을 다시 돌리면 된다** (11장, p.451).[^kleppmann2026] 유도된다는 말의 정의는
  [기록 시스템과 파생 데이터](../concepts/system-of-record-and-derived-data.md)에 있다.

## 불변 입력이 주는 것

- **입력을 불변으로 취급하고 (외부 데이터베이스에 쓰는 것 같은) 부수 효과를 피함으로써 배치
  잡은 좋은 성능뿐 아니라 다른 이득도 얻는다** (11장, p.452):[^kleppmann2026]
  - **코드에 버그를 집어넣어 출력이 틀리거나 손상되면, 그냥 이전 버전의 코드로 롤백하고 잡을
    다시 돌리면 출력이 다시 올바르게 된다. 혹은 더 간단하게, 옛 출력을 다른 디렉터리에 두고
    거기로 되돌릴 수 있다. 대부분의 오브젝트 스토어와 열린 테이블 형식이 이 기능을 지원하며,
    이것은 타임 트래블(time travel)로 알려져 있다. 읽기/쓰기 트랜잭션을 갖는 대부분의
    데이터베이스에는 이 속성이 없다: 나쁜 데이터를 데이터베이스에 쓰는 버그 있는 코드를
    배포하면, 코드를 롤백해도 그 데이터를 고치는 데에는 아무 소용이 없다. 버그 있는 코드에서
    회복할 수 있다는 발상은 인간 장애 내성(human fault tolerance)이라 불려 왔다.**
  - **이렇게 롤백이 쉬운 결과로, 실수가 되돌릴 수 없는 손상을 뜻할 수 있는 환경에서보다 기능
    개발이 더 빠르게 진행될 수 있다. 되돌릴 수 없음을 최소화한다는 이 원칙은 애자일 소프트웨어
    개발에 이롭다.** 되돌릴 수 없음이 왜 비용인지는
    [유지보수성](../concepts/maintainability.md)에 있다.
  - **같은 파일 집합이 여러 종류의 잡에 입력으로 쓰일 수 있다. 지표를 계산하고 잡의 출력이
    기대한 특성을 갖는지 평가하는 모니터링 잡도 그중 하나다(예컨대 이전 실행의 출력과 비교해
    불일치를 재는 식으로).**
  - **배치 처리 프레임워크는 컴퓨팅 자원을 효율적으로 쓴다. OLTP 데이터베이스와 애플리케이션
    서버 같은 온라인 데이터 시스템으로 데이터를 배치 처리하는 것도 가능하지만, 그렇게 하면
    요구되는 자원 면에서 훨씬 비쌀 수 있다.**

## 대가

- **그러나 그것은 도전 과제도 제시한다. 대부분의 프레임워크에서 출력은 잡 전체가 끝난 뒤에야
  다른 잡에 의해 처리될 수 있다. 배치 처리는 비효율적일 수도 있다; 입력 데이터의 어떤 변경도 —
  단 1바이트라도 — 배치 잡이 입력 데이터셋 전체를 재처리하게 만든다** (11장,
  p.452).[^kleppmann2026]

## 경계는 뚜렷하지 않다

- **온라인 시스템과 배치 처리 시스템 사이의 경계가 언제나 분명한 것은 아니다; 오래 도는
  데이터베이스 질의는 배치 프로세스와 꽤 비슷해 보인다. 그러나 배치 처리에는 신뢰할 수 있고
  확장 가능하며 유지보수 가능한 애플리케이션을 만드는 데 쓸모 있는 구성 요소가 되게 하는 특유의
  성격도 있다. 예컨대 그것은 흔히 데이터 통합(data integration)에서 역할을 한다 — 여러 데이터
  시스템을 조합해 한 시스템만으로는 할 수 없는 일을 이루는 것이다** (11장,
  pp.452–453).[^kleppmann2026]
- 스트림 처리와의 관계도 한 문장으로 못박는다 — **배치 처리의 대안은 스트림
  처리(stream processing)로, 여기서는 잡이 입력을 다 처리했다고 끝나지 않고 계속 입력을
  지켜보며 입력의 변화를 그것이 일어난 직후에 처리한다** (11장, p.453).[^kleppmann2026]
  그쪽의 진입점은 [스트림 처리](../synthesis/stream-processing.md) 허브다.

## MapReduce에서 지금까지

- 출발점 — **현대 배치 처리는 MapReduce에 크게 영향받았다. MapReduce는 2004년 구글이 발표하고
  이후 Hadoop·CouchDB·MongoDB를 포함한 여러 오픈 소스 데이터 시스템에 구현된 배치 처리
  알고리즘이다. MapReduce는 꽤 저수준의 프로그래밍 모델이고, 예컨대 데이터 웨어하우스에서
  발견되는 병렬 질의 실행 엔진보다 덜 정교하다** (11장, p.453).[^kleppmann2026]
- 그 지위의 현재 — **새것이었을 때 MapReduce는 범용 하드웨어로 달성할 수 있는 처리 규모 면에서
  한 걸음 전진이었지만, 지금은 대체로 한물갔고 구글에서 더 이상 쓰이지 않는다** (11장,
  p.453).[^kleppmann2026]
- 지금의 지형 — **오늘날 배치 처리는 Spark나 Flink 같은 프레임워크, 또는 데이터 웨어하우스 질의
  엔진으로 하는 경우가 더 많다. MapReduce처럼 그것들도 샤딩과 병렬 실행에 크게 기대지만, 훨씬
  더 정교한 캐싱과 실행 전략을 갖는다. 이 시스템들이 성숙하면서 운영상의 관심사는 대체로
  해결됐고, 초점은 사용성으로 옮겨 갔다. 데이터플로 API·질의 언어·DataFrame API 같은 새 처리
  모델이 이제 널리 지원된다** (11장, p.453).[^kleppmann2026]
- 오케스트레이션도 세대가 바뀌었다 — **잡과 워크플로 오케스트레이션도 성숙했다. Oozie와 Azkaban
  같은 Hadoop 중심 워크플로 스케줄러는 Airflow·Dagster·Prefect 같은 더 일반화된 해법으로
  대체됐고, 이들은 다양한 배치 처리 프레임워크와 클라우드 데이터 웨어하우스를 지원한다** (11장,
  p.453).[^kleppmann2026]
- 저장 계층도 옮겨 갔다 — **클라우드 컴퓨팅이 어디에나 있게 됐다. 배치 저장 계층은 HDFS(Hadoop
  Distributed File System)·GlusterFS·CephFS 같은 분산 파일시스템(DFSs)에서 S3 같은 오브젝트
  스토리지 시스템으로 옮겨 가고 있다. BigQuery와 Snowflake 같은 확장 가능한 클라우드 데이터
  웨어하우스는 데이터 웨어하우스와 배치 처리 사이의 선을 흐리고 있다** (11장,
  p.453).[^kleppmann2026]

## 분산 운영체제라는 비유

- 이 장이 쓰는 뼈대 — **배치 처리가 무엇에 관한 것인지 직관을 세우기 위해, 단일 기계에서 표준
  Unix 도구를 쓰는 예로 이 장을 시작한다. 그다음 데이터 처리를 분산 시스템의 여러 기계로 어떻게
  확장할 수 있는지 살핀다. 우리는 운영체제와 아주 비슷하게 분산 배치 처리 프레임워크에도
  스케줄러와 파일시스템이 있음을 보게 될 것이다** (11장, p.453).[^kleppmann2026]
- 비유가 성립하는 근거를 부품으로 나열한다. 단일 기계에서 Unix 예제를 돌리는 요소는 **운영체제의
  파일시스템 인터페이스로 접근되는 저장 장치**, **프로세스가 언제 돌고 CPU 자원을 어떻게 배분할지
  정하는 스케줄러**, **표준 입력과 표준 출력(stdin·stdout)이 파이프로 이어진 일련의 Unix
  프로그램**이다 (11장, p.457).[^kleppmann2026]
- 결론 — **바로 이 부품들이 분산 데이터 처리 프레임워크에도 존재한다. 사실 이 프레임워크들을
  분산 운영체제(distributed operating systems)로 생각할 수 있다; 그들에게는 파일시스템, 잡
  스케줄러, 그리고 파일시스템이나 다른 통신 채널을 통해 서로에게 데이터를 보내는 프로그램이
  있다** (11장, p.457).[^kleppmann2026]
