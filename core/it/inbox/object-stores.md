하나의 질문: **오브젝트 스토어는 분산 파일시스템과 무엇이 다르고, 그 차이가 배치 잡에 무엇을
요구하는가.**

## 경계가 흐리다

- **아마존 S3, 구글 클라우드 스토리지, 애저 블롭 스토리지, 오픈스택 스위프트 같은 오브젝트
  저장(object storage) 서비스는 배치 처리 잡을 위해 분산 파일시스템의 인기 있는 대안이 됐다.
  사실 둘 사이의 선은 다소 흐릿하다. FUSE 드라이버는 사용자가 S3 같은 오브젝트 스토어를
  파일시스템으로 다룰 수 있게 한다. JuiceFS와 Ceph 같은 어떤 DFS 구현은 오브젝트 저장과
  파일시스템 API를 둘 다 제공한다** (11장, p.460).[^kleppmann2026]
- 그래도 갈아 끼울 수 있다는 뜻은 아니다 — **그러나 그들의 API·성능·일관성 보장은 매우 다르다.
  그런 시스템을 채택할 때는 필요한 API를 구현하는 것처럼 보이더라도 기대대로 동작하는지 확인하는
  주의가 필요하다** (11장, p.460).[^kleppmann2026]

## 주소 — 버킷과 키

- **오브젝트 스토어의 각 객체는 `s3://my-photo-bucket/2025/04/01/birthday.png` 같은 URL을 갖는다.
  URL의 호스트 부분(`my-photo-bucket`)은 객체가 저장된 버킷(bucket)을 서술하고, 그 뒤에 오는
  부분이 객체의 키(key)다(우리 예에서는 `/2025/04/01/birthday.png`). 버킷은 전역적으로 유일한
  이름을 갖고, 각 객체의 키는 그 버킷 안에서 유일해야 한다** (11장, p.460).[^kleppmann2026]

## 불변 객체

- **객체는 get 호출로 읽고 put 호출로 쓴다. 파일시스템의 파일과 달리 객체는 한 번 쓰이면
  불변이다. 객체를 갱신하려면 키-값 저장소와 비슷하게 put 호출로 전체를 다시 써야 한다. 애저 블롭
  스토리지와 S3 Express One Zone은 덧붙이기를 지원하지만 대부분의 다른 스토어는 그렇지 않다.
  `fopen`과 `fseek` 같은 함수를 갖는 파일 핸들 API는 없다** (11장, p.460).[^kleppmann2026]

## 디렉터리가 없다

- **객체가 디렉터리로 조직된 것처럼 보일 수 있는데, 오브젝트 스토어에는 디렉터리라는 개념이
  없으므로 이는 다소 혼란스럽다. 경로 구조는 그저 관례이고 슬래시는 객체 키의 일부다. 이 관례는
  특정 프리픽스를 가진 객체 목록을 요청함으로써 디렉터리 목록과 비슷한 무언가를 수행할 수 있게
  한다** (11장, p.460).[^kleppmann2026]
- 그러나 **프리픽스로 객체를 나열하는 것은 두 가지 면에서 파일시스템 디렉터리 목록과 다르다**
  (11장, pp.460–461):[^kleppmann2026]
  - **프리픽스 목록 연산은 Unix 시스템의 재귀적 `ls -R` 호출처럼 동작한다. 그것은 프리픽스로
    시작하는 모든 객체를 돌려주며 하위 경로의 객체도 포함된다.**
  - **빈 디렉터리는 불가능하다. `s3://my-photo-bucket/2025/04/01` 아래의 모든 객체를 지우면,
    `s3://my-photo-bucket/2025/04`에 list를 호출할 때 `01`이 더 이상 나타나지 않는다. 빈
    디렉터리를 표현하는 방법으로 0바이트 객체를 만드는 것이 흔한 관행이다(예: 모든 자식 객체가
    삭제될 때 유지하기 위해 빈 `s3://my-photo-bucket/2025/04/01` 파일을 만드는 것).**

## 없는 연산들

- **DFS 구현은 흔히 하드 링크, 심볼릭 링크, 파일 잠금, 원자적 이름 변경 같은 흔한 파일시스템
  연산을 지원한다. 그런 기능은 오브젝트 스토어에 없다. 링크와 잠금은 통상 지원되지 않고, 이름
  변경은 원자적이지 않다; 그것은 객체를 새 키로 복사한 뒤 옛 객체를 지우는 것으로 이뤄진다.
  디렉터리 이름을 바꾸고 싶다면 디렉터리 이름이 키의 일부이므로 그 안의 모든 객체 이름을 개별로
  바꿔야 한다** (11장, p.461).[^kleppmann2026]

## 무엇에 최적화돼 있나

- **4장에서 논의한 키-값 저장소는 작은 값(통상 킬로바이트)과 잦고 낮은 지연의 읽기/쓰기에
  최적화돼 있다. 반면 분산 파일시스템과 오브젝트 스토어는 일반적으로 큰 객체(메가바이트에서
  기가바이트)와 덜 잦고 더 큰 읽기에 최적화돼 있다. 그러나 최근 오브젝트 스토어는 잦고 더 작은
  읽기/쓰기 지원을 더하기 시작했다. 예컨대 S3 Express One Zone은 이제 한 자릿수 밀리초 지연과
  키-값 저장소에 더 가까운 가격 모델을 제공한다** (11장, p.461).[^kleppmann2026]

## 데이터 지역성을 포기한 대가

- **분산 파일시스템과 오브젝트 스토어의 또 다른 차이는 HDFS 같은 DFS가 특정 파일의 사본을
  저장하는 기계에서 컴퓨팅 태스크를 돌릴 수 있게 한다는 것이다. 이는 태스크가 그 파일을 네트워크로
  보내지 않고 읽을 수 있게 해, 태스크의 실행 코드가 읽어야 할 파일보다 작으면 대역폭을 아낀다.
  반면 오브젝트 스토어는 보통 저장과 연산을 분리해 둔다. 그렇게 하면 대역폭을 더 쓸 수 있지만
  현대 데이터센터 네트워크는 매우 빠르므로 이는 흔히 받아들일 만하다. 이 아키텍처는 또한 CPU와
  메모리 같은 기계 자원이 저장과 무관하게 확장될 수 있게 하는데, 둘이 분리돼 있기 때문이다**
  (11장, p.461).[^kleppmann2026] 그 분리가 데이터베이스 쪽에서 어디까지 갔는지는
  [클라우드 네이티브 아키텍처](../concepts/cloud-native-architecture.md)에 있다.

## 왜 클라우드 저장의 기본값이 되었는가

앞 절들이 오브젝트 스토어를 **배치 처리의 저장 계층**으로 서술한다면, 데이터 엔지니어링 개론은
같은 것을 **클라우드 데이터 아키텍처의 기본값**으로 놓고 그 이유를 편다.

- 무엇을 담는가 — **오브젝트 저장은 온갖 모양과 크기의 객체를 담는다. 오브젝트 저장이라는 용어는
  다소 혼란스러운데 컴퓨터 과학에서 객체(object)가 여러 뜻을 갖기 때문이다. 이 맥락에서 우리는
  특화된 파일 비슷한 구성물을 말하고 있다. 그것은 어떤 유형의 파일이든 될 수 있다 —
  TXT·CSV·JSON·이미지·비디오·오디오** (6장, p.205).[^reis2022]
- 어디에 얹혀 있는가 — **오브젝트 스토어는 빅데이터와 클라우드의 부상과 함께 중요성과 인기가
  커졌다. Amazon S3·Azure Blob Storage·Google Cloud Storage(GCS)가 널리 쓰이는 오브젝트 저장이다.
  덧붙여 많은 클라우드 데이터 웨어하우스(그리고 점점 늘어나는 데이터베이스)가 오브젝트 저장을
  자기 저장 계층으로 활용하며, 클라우드 데이터 레이크는 일반적으로 오브젝트 스토어 위에 앉는다**
  (6장, p.206).[^reis2022]
- 운영 관점에서의 매력 — **많은 온프레미스 오브젝트 저장 시스템이 서버 클러스터에 설치될 수
  있지만, 우리는 대부분 완전 관리형 클라우드 오브젝트 스토어에 초점을 맞출 것이다. 운영 관점에서
  클라우드 오브젝트 저장의 가장 매력적인 특성 중 하나는 관리하고 쓰기가 직설적이라는 것이다.
  오브젝트 저장은 틀림없이 최초의 "서버리스" 서비스 중 하나였다 — 엔지니어는 하부 서버 클러스터나
  디스크의 특성을 고려할 필요가 없다** (6장, p.206).[^reis2022]
- 무엇을 잃는가 — **오브젝트 스토어는 불변 데이터 객체를 위한 키-값 저장이다. 우리는 로컬 디스크의
  파일 저장에서 기대하는 쓰기 유연성의 상당 부분을 오브젝트 스토어에서 잃는다. 객체는 임의 쓰기나
  추가 연산을 지원하지 않는다 — 대신 바이트 스트림으로 한 번 쓰인다. 이 최초 쓰기 뒤에 객체는
  불변이 된다. 객체의 데이터를 바꾸거나 데이터를 덧붙이려면 전체 객체를 다시 써야 한다. 오브젝트
  스토어는 일반적으로 범위 요청을 통한 임의 읽기를 지원하지만 이 조회는 SSD에 저장된 데이터의
  임의 읽기보다 훨씬 나쁘게 수행될 수 있다** (6장, p.206).[^reis2022]
- 무엇을 얻는가 — **로컬 임의 접근 파일 저장을 활용하는 데 익숙한 소프트웨어 개발자에게 객체의
  특성은 제약처럼 보일 수 있지만 적을수록 낫다 — 오브젝트 스토어는 잠금이나 변경 동기화를 지원할
  필요가 없어 방대한 디스크 클러스터에 걸쳐 데이터 저장을 허용한다. 오브젝트 스토어는 많은 디스크에
  걸친 극도로 성능 좋은 병렬 스트림 쓰기와 읽기를 지원하며, 이 병렬성은 엔지니어에게 숨겨져 있어
  개별 디스크와 통신하는 대신 그냥 스트림을 다룰 수 있다** (6장, p.206).[^reis2022]
- 확장의 축이 여럿이다 — **클라우드 환경에서 쓰기 속도는 벤더가 정한 할당량 한계까지 쓰이는 스트림
  수와 함께 확장된다. 읽기 대역폭은 병렬 요청 수, 데이터를 읽는 데 채용된 가상 머신 수, CPU 코어
  수와 함께 확장될 수 있다. 이 특성이 오브젝트 저장을 대량 웹 트래픽 서빙이나 고도로 병렬적인
  분산 질의 엔진에 데이터를 인도하는 데 이상적으로 만든다** (6장, p.206).[^reis2022]
- 내구성과 가용성 — **전형적 클라우드 오브젝트 스토어는 데이터를 여러 가용 영역에 저장해 저장이
  완전히 오프라인이 되거나 복구 불가능하게 손실될 확률을 극적으로 줄인다. 이 내구성과 가용성은
  비용에 내장돼 있다 — 클라우드 저장 벤더는 줄어든 내구성이나 가용성과 맞바꿔 할인된 가격의 다른
  저장 클래스를 제공한다** (6장, p.206).[^reis2022]
- 저장 공간의 실질 한계 — **오브젝트 저장에서 가용 저장 공간도 고도로 확장 가능하며, 이는 빅데이터
  시스템에 이상적인 특성이다. 저장 공간은 저장 제공자가 소유한 디스크 수에 제약되지만 이 제공자들은
  엑사바이트의 데이터를 다룬다. 클라우드 환경에서 가용 저장 공간은 사실상 무한하다 — 실무에서 퍼블릭
  클라우드 고객의 저장 공간에 대한 주요 한계는 예산이다. 실용적 관점에서 엔지니어는 필요한 서버와
  디스크를 몇 달 앞서 계획하지 않고도 프로젝트를 위해 방대한 양의 데이터를 빠르게 저장할 수 있다**
  (6장, p.207).[^reis2022]

## 데이터 엔지니어링 응용에서의 성능 프로필

- 무엇을 잘하는가 — **데이터 엔지니어링의 관점에서 오브젝트 스토어는 큰 배치 읽기와 배치 쓰기에
  훌륭한 성능을 제공한다. 이는 대규모 OLAP 시스템의 유스케이스와 잘 대응한다** (6장,
  p.207).[^reis2022]
- 흔한 통념의 교정 — **데이터 엔지니어링 민담 한 조각은 오브젝트 스토어가 갱신에 좋지 않다고
  말하지만 이는 부분적으로만 참이다. 오브젝트 스토어는 초당 많은 작은 갱신이 있는 트랜잭션
  워크로드에는 열등한 적합이다 — 이 유스케이스는 트랜잭션 데이터베이스나 블록 저장 시스템이
  훨씬 잘 서빙한다. 오브젝트 스토어는 각 연산이 큰 데이터 볼륨을 갱신하는 낮은 비율의 갱신
  연산에는 잘 작동한다** (6장, p.207).[^reis2022]
- 데이터 레이크의 표준이 된 경로 — **오브젝트 스토어는 이제 데이터 레이크 저장의 금본위다. 데이터
  레이크 초기에는 한 번 쓰고 여러 번 읽는(WORM)이 운영 표준이었지만, 이는 HDFS와 오브젝트 스토어의
  한계보다는 데이터 버전과 파일 관리의 복잡성과 더 관련이 있었다. 그 이후 Apache Hudi와 Delta
  Lake 같은 시스템이 이 복잡성을 관리하기 위해 등장했고, GDPR·CCPA 같은 프라이버시 규제가 삭제·갱신
  능력을 필수로 만들었다. 오브젝트 저장의 갱신 관리가 3장에서 소개한 데이터 레이크하우스 개념 뒤의
  중심 아이디어다** (6장, p.207).[^reis2022] 상세는
  [데이터 레이크](../concepts/data-lake.md).
- 비정형 데이터의 저장소 — **오브젝트 저장은 이 구조화된 데이터 응용을 넘어 어떤 형식의 비정형
  데이터에도 이상적인 저장소다. 오브젝트 저장은 타입이나 구조에 제약 없이 어떤 이진 데이터든
  수용할 수 있고, 원시 텍스트·이미지·비디오·오디오를 위해 ML 파이프라인에서 자주 역할을 한다**
  (6장, p.207).[^reis2022]
- 조회는 디렉터리 순회가 아니다 — **오브젝트 스토어는 키-값 저장이다. 이것이 엔지니어에게 무슨
  뜻인가? 파일 스토어와 달리 오브젝트 스토어는 객체를 찾기 위해 디렉터리 트리를 활용하지 않는다는
  것을 이해하는 것이 결정적이다. 오브젝트 스토어는 최상위 논리 컨테이너(S3와 GCS에서는 버킷)를
  쓰고 객체를 키로 참조한다** (6장, p.207).[^reis2022]
  - 그래서 접두사 연산이 비싸다 — **표면적으로 이것은 일반 파일 폴더 시스템에서 볼 하위 디렉터리처럼
    보인다. 많은 클라우드 콘솔 인터페이스가 사용자에게 "디렉터리" 안의 객체를 보게 하고 클라우드
    명령줄 도구는 흔히 오브젝트 스토어 디렉터리에서 `ls` 같은 Unix 스타일 명령을 지원한다. 그러나
    무대 뒤에서 객체 시스템은 객체에 도달하기 위해 디렉터리 트리를 순회하지 않는다. 대신 그것은
    그냥 디렉터리 의미론과 일치하게 된 키를 볼 뿐이다. 이는 사소한 기술적 세부로 보일 수 있지만
    엔지니어는 오브젝트 스토어에서 특정 "디렉터리" 수준 연산이 비싸다는 것을 이해할 필요가 있다.
    버킷이 수백만 객체를 담고 있으면 "하위 디렉터리"에 객체가 몇 개뿐이더라도 이 연산은 시간이 걸릴
    수 있다** (6장, p.208).[^reis2022] 같은 성질을 자료 구조 쪽에서 말한 것이 위
    [디렉터리가 없다](#디렉터리가-없다) 절이다.

## 일관성과 버저닝

- 갱신이 곧 재기록이다 — **언급했듯 오브젝트 스토어는 일반 규칙으로 제자리 갱신이나 추가를 지원하지
  않는다. 우리는 객체를 갱신하기 위해 같은 키 아래 새 객체를 쓴다. 데이터 엔지니어가 데이터
  프로세스에서 갱신을 활용할 때 자기가 쓰는 오브젝트 스토어의 일관성 모델을 알고 있어야 한다.
  오브젝트 스토어는 최종 일관적일 수도 강하게 일관적일 수도 있다. 예컨대 최근까지 S3는 최종
  일관적이었다 — 같은 키 아래 객체의 새 버전이 쓰인 뒤에도 오브젝트 스토어가 때때로 객체의 옛
  버전을 돌려줄 수 있었다** (6장, p.208).[^reis2022] 두 모델의 정의는
  [일관성 모델](../concepts/consistency-models.md)에 있다.
- 강한 일관성을 얹는 표준 방법 — **다양한 이유로 오브젝트 스토어에 강한 일관성을 부과하는 것이
  바람직할 수 있고, 이를 달성하기 위해 표준 방법이 쓰인다. 한 가지 접근은 강하게 일관적인
  데이터베이스(예: PostgreSQL)를 섞는 것이다. 객체를 쓰는 것은 이제 2단계 과정이 된다** (6장,
  p.208):[^reis2022]
  1. **객체를 쓴다.**
  2. **객체 버전에 대해 돌려받은 메타데이터를 강하게 일관적인 데이터베이스에 쓴다.**
  - 읽기는 3단계다 (6장, p.209):[^reis2022]
    1. **강하게 일관적인 데이터베이스에서 최신 객체 메타데이터를 가져온다.**
    2. **객체 키를 써서 객체 메타데이터를 질의한다. 일관적인 데이터베이스에서 가져온 메타데이터와
       일치하면 객체 데이터를 읽는다.**
    3. **객체 메타데이터가 일치하지 않으면 객체의 최신 버전이 돌아올 때까지 2단계를 반복한다.**
  - 그 대가 — **실용적 구현에는 이 질의 과정 중에 객체가 다시 쓰이는 경우 같은 예외와 엣지 케이스가
    고려돼야 한다. 이 단계들은 API 뒤에서 관리될 수 있어, 객체 접근의 더 높은 지연을 대가로 객체
    읽는 쪽이 강하게 일관적인 오브젝트 스토어를 보게 된다** (6장, p.209).[^reis2022]
- 버저닝이 일관성 문제와 얽히는 이유 — **객체 버저닝은 객체 일관성과 밀접하게 관련돼 있다.
  오브젝트 스토어에서 기존 키 아래 객체를 다시 쓸 때 우리는 본질적으로 완전히 새 객체를 쓰고,
  기존 키에서 객체로의 참조를 설정하고, 옛 객체 참조를 지우고 있다. 클러스터 전체에서 모든 참조를
  갱신하는 데는 시간이 걸리고, 그래서 낡은 읽기의 가능성이 생긴다. 결국 저장 클러스터 가비지
  컬렉터가 역참조된 데이터에 바쳐진 공간을 해제하고 새 객체가 쓸 수 있도록 디스크 용량을
  재활용한다** (6장, p.209).[^reis2022]
- 버저닝을 켜면 — **객체 버저닝을 켜면 버전을 규정하는 추가 메타데이터를 객체에 더한다. 기본 키
  참조는 새 객체를 가리키도록 갱신되지만 우리는 이전 버전에 대한 다른 포인터를 유지한다. 또한
  버전 목록을 유지해 클라이언트가 모든 객체 버전의 목록을 얻은 뒤 특정 버전을 끌어올 수 있게 한다.
  객체의 옛 버전이 여전히 참조되므로 가비지 컬렉터가 그것을 청소하지 않는다** (6장,
  p.209).[^reis2022]
- 버전을 지정하면 일관성 문제가 사라진다 — **객체를 버전과 함께 참조하면 어떤 오브젝트 저장
  시스템의 일관성 문제가 사라진다: 키와 버전 메타데이터가 함께 특정 불변 데이터 객체에 대한 유일한
  참조를 이룬다. 이 쌍을 쓰면 우리가 지우지 않은 한 늘 같은 객체를 돌려받을 것이다. 클라이언트가
  객체의 "기본" 또는 "최신" 버전을 요청할 때는 여전히 일관성 문제가 존재한다** (6장,
  p.209).[^reis2022]
- 비용이 주요 오버헤드다 — **엔지니어가 객체 버저닝에서 고려해야 할 주요 오버헤드는 저장 비용이다.
  객체의 과거 버전은 일반적으로 현재 버전과 같은 결부 저장 비용을 갖는다. 객체 버전 비용은 다양한
  요인에 따라 거의 무의미할 수도, 파국적으로 비쌀 수도 있다. 데이터 크기가 문제이고 갱신 빈도도
  그렇다 — 더 많은 객체 버전은 유의하게 더 큰 데이터 크기로 이어질 수 있다. 우리는 무차별 대입
  객체 버저닝을 말하고 있음을 유념하라. 오브젝트 저장 시스템은 일반적으로 각 버전에 대해 차등
  스냅샷이 아니라 전체 객체 데이터를 저장한다** (6장, p.209).[^reis2022]
- 수명 주기 정책 — **엔지니어는 저장 수명 주기 정책을 배치할 선택지도 갖는다. 수명 주기 정책은
  특정 조건이 충족될 때(예: 객체 버전이 특정 나이에 도달하거나 훨씬 새로운 버전이 많이 존재할 때)
  옛 객체 버전의 자동 삭제를 허용한다. 클라우드 벤더는 크게 할인된 가격의 다양한 아카이브 데이터
  계층도 제공하며 아카이브 과정은 수명 주기 정책으로 관리될 수 있다** (6장, p.210).[^reis2022]

## 저장 클래스와 계층

- 무엇을 파는가 — **클라우드 벤더는 이제 줄어든 접근이나 줄어든 내구성과 맞바꿔 데이터 저장 가격을
  할인하는 저장 클래스를 제공한다. 여기서 줄어든 접근(reduced access)이라는 용어를 쓰는데, 이
  저장 계층 중 다수는 여전히 데이터를 고도로 가용하게 유지하되 줄어든 저장 비용과 맞바꿔 높은
  회수 비용을 물리기 때문이다** (6장, p.210).[^reis2022]
- S3의 사례 — **S3 Standard-Infrequent Access 저장 클래스는 늘어난 데이터 회수 비용과 맞바꿔
  월 저장 비용을 할인한다. Amazon은 Amazon S3 One Zone-Infrequent Access 계층도 제공하는데 이는
  단일 존에만 복제한다. 존 단위 중단의 가능성을 반영해 예상 가용성이 99.9%에서 99.5%로 떨어진다.
  Amazon은 데이터 내구성이 여전히 극히 높다고 주장하지만, 가용 영역이 파괴되면 데이터가 손실될
  것이라는 단서가 붙는다** (6장, p.210).[^reis2022]
- 아카이브 계층 — **줄어든 접근 계층 아래로 더 내려가면 S3 Glacier의 아카이브 계층이 있다.
  S3 Glacier는 훨씬 높은 접근 비용과 맞바꿔 장기 저장 비용의 극적인 감소를 약속한다. 사용자는
  분에서 시간까지 다양한 회수 속도 선택지를 가지며 빠른 접근에는 더 높은 회수 비용이 붙는다. 예컨대
  이 글을 쓰는 시점에 S3 Glacier Deep Archive는 저장 비용을 더 할인한다 — Amazon은 저장 비용이
  테라바이트당 월 1달러에서 시작한다고 광고한다. 그 대가로 데이터 복원에는 12시간이 걸린다. 덧붙여
  이 저장 클래스는 7–10년 저장되고 1년에 한두 번만 접근될 데이터를 위해 설계됐다** (6장,
  p.210).[^reis2022]
- 경고 — **아카이브 저장을 어떻게 활용할 계획인지 알고 있으라. 들어가기는 쉽고 나중에 데이터에
  접근하는 것은 흔히 비싸며, 특히 예상보다 자주 필요하면 그렇다** (6장, p.210).[^reis2022]
  같은 축의 판단은
  [수명 주기의 저장 단계](../concepts/storage-in-the-lifecycle.md)의 온도·보존 절에 있다.

## 오브젝트 스토어를 파일시스템으로 마운트하기

- 도구와 그 한계 — **오브젝트 스토어 동기화 해법이 점점 인기를 얻고 있다. s3fs와 Amazon S3 File
  Gateway 같은 도구는 사용자가 S3 버킷을 로컬 저장으로 마운트하도록 허용한다. 이 도구의 사용자는
  파일시스템에 대한 쓰기의 특성과, 그것이 오브젝트 저장의 특성·가격과 어떻게 상호작용할지 알고
  있어야 한다. 예컨대 File Gateway는 S3의 고급 능력을 써서 객체의 일부를 새 객체로 결합함으로써
  파일 변경을 꽤 효율적으로 처리한다. 그러나 고속 트랜잭션 쓰기는 오브젝트 스토어의 갱신 능력을
  압도할 것이다. 오브젝트 저장을 로컬 파일시스템으로 마운트하는 것은 자주 갱신되지 않는 파일에
  잘 작동한다** (6장, pp.210–211).[^reis2022]
