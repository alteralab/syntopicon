따져야 하는가.**

## 로그란 무엇이고 어디서 나오는가

- 정의 — **로그(log)는 시스템에서 일어나는 이벤트에 대한 정보를 포착한다. 예컨대 로그는 웹
  서버의 트래픽과 사용 패턴을 포착할 수 있다. 데스크톱 컴퓨터의 운영 체제(Windows·macOS·
  Linux)는 시스템이 부팅될 때, 그리고 애플리케이션이 시작하거나 크래시할 때 이벤트를 로그로
  남긴다** (5장, p.160).[^reis2022]
- 왜 데이터 엔지니어의 관심사인가 — **로그는 풍부한 데이터 원천이며 하류 데이터 분석·ML·자동화에
  잠재적으로 가치가 있다** (5장, p.160).[^reis2022]
- 친숙한 로그 원천 여섯 (5장, p.160):[^reis2022] **운영 체제 · 애플리케이션 · 서버 ·
  컨테이너 · 네트워크 · IoT 장치.**

## 최소한 담아야 할 세 가지

- **모든 로그는 이벤트와 이벤트 메타데이터를 추적한다. 최소한 로그는 누가·무엇을·언제를
  포착해야 한다** (5장, p.160):[^reis2022]
  - **누가(Who)** — **이벤트에 연결된 사람·시스템·서비스 계정(예: 웹 브라우저 사용자
    에이전트나 사용자 ID).**
  - **무엇이 일어났는가(What happened)** — **이벤트와 관련 메타데이터.**
  - **언제(When)** — **이벤트의 타임스탬프.**

## 로그 인코딩의 세 갈래

**로그는 몇 가지 방식으로 인코딩된다** (5장, pp.160–161):[^reis2022]

- **이진 인코딩 로그(binary-encoded logs)** — **공간 효율과 빠른 I/O를 위해 데이터를 맞춤
  압축 형식으로 인코딩한다. 데이터베이스 로그가 표준적 예다.**
- **반구조화 로그(semistructured logs)** — **객체 직렬화 형식(대개 JSON)의 텍스트로 인코딩된다.
  반구조화 로그는 기계가 읽을 수 있고 이식성이 있다. 그러나 이진 로그보다 훨씬 덜 효율적이다.
  그리고 명목상 기계가 읽을 수 있다지만 거기서 가치를 뽑으려면 흔히 상당한 맞춤 코드가
  필요하다.**
- **평문(비구조화) 로그(plain-text (unstructured) logs)** — **본질적으로 소프트웨어의 콘솔
  출력을 저장한다. 그런 만큼 범용 표준이 존재하지 않는다. 이 로그는 데이터 과학자와 ML
  엔지니어에게 유용한 정보를 제공할 수 있지만, 원시 텍스트 데이터에서 유용한 정보를 뽑는
  것은 복잡할 수 있다.**

## 해상도와 로그 레벨은 다른 축이다

- **로그는 다양한 해상도와 로그 레벨로 만들어진다. 로그 해상도(resolution)는 로그에 포착되는
  이벤트 데이터의 양을 가리킨다. 예컨대 데이터베이스 로그는 데이터베이스 이벤트로부터 어느
  시점의 데이터베이스 상태든 재구성할 수 있을 만큼 충분한 정보를 포착한다** (5장,
  p.161).[^reis2022]
- 전부를 담는 것이 늘 가능하지는 않다 — **반면 빅데이터 시스템에서 모든 데이터 변경을 로그에
  포착하는 것은 흔히 실용적이지 않다. 대신 이 로그들은 특정 유형의 커밋 이벤트가 일어났다는
  것만 기록할 수 있다** (5장, p.161).[^reis2022]
- 다른 축 — **로그 레벨(log level)은 로그 항목을 기록하는 데 요구되는 조건, 특히 오류와
  디버깅에 관한 조건을 가리킨다. 소프트웨어는 흔히 모든 이벤트를 로그로 남기거나 오류만 로그로
  남기도록 설정 가능하다** (5장, p.161).[^reis2022]
  - 그래서 두 축은 독립이다 — 해상도는 **한 이벤트를 얼마나 자세히 적는가**이고, 로그 레벨은
    **어떤 이벤트를 적기로 하는가**다. 같은 로그 레벨에서도 해상도가 다를 수 있다.

## 지연 — 배치인가 실시간인가

- **배치 로그는 흔히 파일에 연속적으로 쓰인다. 개별 로그 항목은 실시간 애플리케이션을 위해
  카프카나 펄사 같은 메시징 시스템에 쓰일 수 있다** (5장, p.161).[^reis2022]

## 데이터베이스 로그

- 왜 따로 떼는가 — **데이터베이스 로그는 더 상세한 취급을 받을 만큼 충분히 필수적이다**
  (5장, p.161).[^reis2022]
- 정체 — **쓰기 전 로그(write-ahead logs) — 보통 데이터베이스 고유 형식의 특정 이진 파일 —
  는 데이터베이스 보증과 복구 가능성에 결정적인 역할을 한다. 데이터베이스 서버는 데이터베이스
  테이블에 대한 쓰기·갱신 요청을 받아 요청을 확인 응답하기 전에 각 연산을 로그에 저장한다.
  확인 응답에는 로그와 결부된 보증이 딸려 온다 — 서버가 실패하더라도 재부팅 시 로그에서 끝나지
  않은 작업을 완료함으로써 상태를 복구할 수 있다** (5장, p.161).[^reis2022] 이 기제의
  전문은 [쓰기 전 로그와 ARIES 복구](../concepts/write-ahead-log-and-aries.md)에 있다.
- 데이터 엔지니어링에서의 쓸모 — **데이터베이스 로그는 데이터 엔지니어링에서 극도로 유용하며,
  특히 데이터베이스 변경에서 이벤트 스트림을 생성하는 CDC에 그렇다** (5장, p.161).[^reis2022]
  - 그래서 CDC의 구현이 데이터베이스 기술마다 갈린다 — **관계형 데이터베이스는 흔히
    데이터베이스 서버에 직접 저장된 이벤트 로그를 생성하며 이것을 처리해 스트림을 만들 수
    있다. 많은 클라우드 NoSQL 데이터베이스는 로그나 이벤트 스트림을 대상 저장 위치로 보낼 수
    있다** (5장, p.160).[^reis2022] 상세는
    [변경 데이터 캡처](../concepts/change-data-capture.md).
