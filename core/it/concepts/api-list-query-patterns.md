하나의 질문: **큰 데이터셋을 목록으로 내줄 때 무엇으로 골라내고, 세고, 잘라 주는가.**

## 필터링의 두 방식

- 규정은 한 문장이다 (2장 §"Filtering", p.57).[^dynowski2025]

  > Filtering allows you to retrieve specific data from a larger dataset based on
  > selection conditions.

- **REST API에서 필터링은 URI에 기준을 질의 매개변수로 붙이는 방식으로 가장 흔히 구현된다**
  (2장, p.57).[^dynowski2025] 저자들이 드는 예가
  `https://example.com/api/v1/books?order_by=published_date&language=en`이다.
- **기준을 API로 옮기는 접근은 둘이고 둘 다 질의 매개변수를 쓴다** (2장, p.57).[^dynowski2025]

## 필터 문자열

- 첫째 방식은 **필터 문자열(filter string)** 을 질의 매개변수로 API에 넘기는 것이고,
  **그 문자열의 형식은 밑에 깔린 저장 기술에 달려 있다** (2장, p.57).[^dynowski2025] SQL
  데이터베이스를 쓴다면 **백엔드가 정제하고 통제하고 해석하는 SQL 질의의 일부**를 담은 필터
  문자열을 만들 수 있다 — `country='Denmark' AND snowfall >= 0.5 AND rain >= 0.1`.
- 곧바로 경계가 그어진다 — **질의 전체를 넘기지 말라**(`SELECT * FROM weather WHERE …`).
  그러지 않으면 **SQL 주입 공격의 위험을 지게 되는데, 그것은 악의적 SQL 문장이 실행 가능한
  질의의 문맥 안으로 끼워 넣어지는 것**이다. `DROP` 문 주입이 그 예다 (2장,
  p.57).[^dynowski2025]
- 이점은 변경을 흡수하는 자리에 있다 — **API를 고치지 않고도 데이터 형식과 관련된 변경에
  대응하기 쉽다.** API가 파싱과 정제와 검증을 책임지므로 **클라이언트는 질의 매개변수의 필터
  문자열만 갱신하면 된다** (2장, p.57).[^dynowski2025]
  - 저자들이 드는 실물 — 밑에 깔린 모델이 데이터베이스 컬럼을 `snowfall`에서
    `snowfall_amount`로 개명하면 **클라이언트는 필터 문자열을 갱신해야 하지만, API가 질의
    문자열을 전과 다르게 다뤄야 하는 것은 아니다.** 곧 **API가 코드베이스를 고치지 않고 새
    스키마를 쓸 수 있다.**
- 대가는 클라이언트와 파서에 있다 — **클라이언트가 데이터셋의 스키마에 맞게 이 문자열을 구성할
  줄 알아야 하고**, 이 방법은 **필터 문자열을 이해하는 맞춤 파서를 요구한다** (2장,
  p.57).[^dynowski2025]

## 필드 기반 필터링

- 둘째 방식은 **필드 기반 필터링(field-based filtering)** 으로, 필터링 데이터를 질의 매개변수로
  API에 공급한다 — `country=Denmark&snowfall>=0.5&rain>=0.1`. **API가 필터링 로직과 구조를
  정의하고 관리하므로 더 통제되지만 덜 유연하다** (2장, p.58).[^dynowski2025]
- 이점이 셋이다 (2장, p.58).[^dynowski2025]
  - **입력 직렬화와 검증 덕분에 SQL 주입의 위험이 줄어든다.**
  - **API의 백엔드 프레임워크와 통합하기 쉽다.**
  - **어느 필드가 검증되고 있는지 정확히 알기 때문에 오류 메시지가 더 정밀하다.**
- 단점은 하나다 — **새 변경에 적응하는 유연성이 덜해 API를 계속 작동하게 하는 데 일이 든다.**
  그리고 저자들이 한 줄을 덧붙인다: **이것이 가장 흔한 접근이다** (2장, p.58).[^dynowski2025]
- 선택은 열려 있다 — **어느 필터링 접근을 따를지는 당신에게 달렸고, 프레임워크를 쓰고 있다면 그
  프레임워크의 권고를 따르라** (2장, p.58).[^dynowski2025]

## 응답의 모양을 깎는 필터링

- 필터링의 둘째 쓰임이 있다 — **응답 데이터의 모양을 잡는 데도 쓸 수 있다** (2장,
  p.58).[^dynowski2025]
  - **GraphQL은 클라이언트가 세밀한 수준에서 특정 데이터를 요청하게 한다**(질의에 적힌 대로).
  - **REST API도 원치 않는 데이터를 걸러낼 수 있지만 API 쪽 구현이 더 든다.** 저자들이 드는
    수단이 `exclude_fields` 질의 매개변수이고, 그것으로 클라이언트가 돌려받는 데이터의 모양을
    통제할 수 있다.

## 세기와 정렬

- 규정과 자리 — **레코드를 세고 정렬하는 것은 프런트엔드 애플리케이션이 흔히 바라는 기능**이다.
  **세기(counting)는 질의에 맞는 전체 레코드 수를 정하며 페이지네이션에 자주 쓰이고**,
  **정렬(sorting)은 시간·이름·수 같은 속성으로 정렬 가능한 데이터를 오름차순이나 내림차순으로
  줄 세우는 것**이다. 그리고 곧바로 단서가 붙는다 — **이 기능은 성능에 부정적 영향을 줄 수
  있다** (2장 §"Counting and Sorting", p.58).[^dynowski2025]
- 그 영향이 늦게 나타나는 것이 함정이다 — **소규모 체계에서는 세기와 정렬이 대체로 잘 수행되어
  체계가 최적화되어 있다는 인상을 만든다.** 그러나 **데이터 양이 자라면 데이터베이스 인덱스
  누락이나 1+n 문제(n+1이라고도 한다) 때문에 성능 문제가 드러날 수 있다** (2장,
  p.58).[^dynowski2025]
- **1+n 문제는 관련 데이터를 질의 하나 대신 여러 질의로 가져올 때 생기는 성능 문제**이고,
  **관계형 데이터베이스에서는 대개 SQL `JOIN`을 쓰지 않아서 생긴다** (2장,
  p.58).[^dynowski2025]

## 분산이 더하는 것

- **분산 체계는 복잡성을 더 들여온다** — **데이터가 여러 노드에 분할되면 세기와 정렬 같은
  연산이 조율을 요구할 수 있고 그것이 응답 시간을 느리게 만든다.** 밑의 데이터베이스가 그런
  집계 연산에 명시적으로 최적화되어 있지 않은 한 **API의 반응성에 부정적 영향을 줄 수 있다**
  (2장, p.58).[^dynowski2025]
- 그래서 판정이 저장 계층으로 내려간다 (2장, p.58).[^dynowski2025]
  - **백엔드가 비분산 데이터베이스에 기대고 있다면 세기와 정렬의 구현은 대체로 실행 가능하고
    권장된다.**
  - **분산 체계에서는 이 연산들이 분산 데이터 처리를 지원하는 기능을 요구한다.**
  - **어떤 경우에는 큰 데이터셋에 대해 세기와 정렬을 제한하거나 끄는 것, 또는 근사
    카운트(approximate counts)·캐시된 메타데이터·지연 처리 같은 대안을 탐색하는 것이 최선일 수
    있다.**

## 페이지네이션이라는 창

- 규정이 창의 비유로 되어 있다 (2장 §"Pagination", p.59).[^dynowski2025]
  - **페이지네이션(pagination), 또는 페이징(paging)은 큰 데이터셋을 페이지(덩어리) 단위로 읽는
    문제를 다루는 설계 패턴이다.**
  - **각 페이지는 페이지 크기(항목 수)로 정해지는 데이터의 부분집합을 담고, 데이터셋으로 난
    창처럼 작동해 어느 시점에도 전체 데이터셋의 일부만 제공한다.**
  - **사용자나 체계는 이 페이지들을 앞뒤로 미끄러지며 전체 데이터셋을 오갈 수 있고**, 다음이나
    이전 페이지로 가거나 특정 페이지로 뛸 수 있다.
- **구현 접근은 여럿이지만 가장 흔한 것이 오프셋 기반과 커서 기반** 둘이다 (2장,
  p.59).[^dynowski2025]

## 오프셋 기반

- **오프셋 기반 페이지네이션은 흔히 쓰이고 여러 결로 나뉜다** (2장 §"Offset-based pagination",
  pp.59–60).[^dynowski2025]
  - 첫째 결은 **요청의 질의 매개변수에 페이지 번호를 쓰는 것**이다(`?page=2&page_size=100`).
    응답의 `next`와 `previous` 필드에 담긴 `page` 값이 각각 하나 늘고 하나 줄며, `count`
    필드가 데이터셋의 객체 수를 가리킨다.
  - 둘째 결은 **`limit`과 `offset` 질의 매개변수를 쓰는 것**이다. **`limit`은 돌아오는 항목의
    총수를 통제하고, `offset`은 페이지로 나뉘지 않은 전체 항목 집합에 대해 결과가 어디서
    시작해야 하는지를 가리킨다.**
- 이점은 클라이언트가 얻는 앎에 있다 — **레코드 수와 페이지 크기로 전체 페이지 수를 추정할 수
  있고, 특정 페이지로 뛸 수 있다** (2장, p.60).[^dynowski2025]
- 첫째 단점은 규모다 — **방대한 데이터셋에서 비효율적이 되어 응답이 느려질 수 있다.**
  이유는 **데이터베이스가 그 페이지의 결과를 돌려주기 전에 원하는 오프셋에 닿기까지 많은
  레코드를 스캔하거나 건너뛰어야 하기 때문**이다. **데이터셋에서 1000번째 페이지를 요청하면
  데이터베이스는 앞선 999페이지의 레코드를 지나쳐야 한다** (2장, p.60).[^dynowski2025]

## 삭제와 삽입이 오프셋을 어긋나게 한다

- 둘째 단점은 데이터가 움직일 때 나타난다 (2장, p.60).[^dynowski2025]
  - **앞 페이지에서 항목을 지우면 뒤따르는 항목들이 한 자리씩 뒤로 밀려**, 다음 페이지에
    나왔어야 할 **항목 일부를 건너뛰는 결과**가 될 수 있다.
  - **반대로 앞 페이지에 항목을 끼워 넣으면 뒤따르는 항목들이 한 자리씩 앞으로 밀려**, 항목들이
    현재나 이전 페이지와 겹치는 자리로 밀려나며 **중복**으로 이어질 수 있다.
- 저자들이 표로 보이는 효과다 — 세 페이지에 A부터 I까지 셋씩 담긴 상태에서 **B를 지우면 마지막
  페이지의 항목이 하나 줄고**, **Z를 끼워 넣으면 페이지들이 앞으로 밀려 항목 하나가 다음
  페이지로 넘어간다** (2장 표 2-7, p.60).[^dynowski2025]
- 원인의 진술은 한 줄이다 — **오프셋 기반 페이지네이션은 고정된 수의 항목을 건너뛰는 데
  기댄다. 클라이언트가 페이지를 넘기는 동안 현재 오프셋보다 앞에서 항목이 지워지거나 끼워지면
  데이터셋이 밀린다** (2장, p.60).[^dynowski2025]

## 커서 기반

- 규정 (2장 §"Cursor-based pagination", p.60).[^dynowski2025]
  - **커서 기반 페이지네이션은 커서(포인터)를 써서 데이터셋 안의 위치를 가리킨다.**
  - **커서는 정렬 가능하도록 유일하고 순차적인 값이어야 한다** — 데이터베이스 기본 키 같은 것.
  - **커서는 인코딩되어 클라이언트는 이해하지 못하고 API는 이해하는 토큰으로 나타난다.
    API는 그 커서를 디코딩해 데이터베이스를 오가는 데 쓸 줄 안다.**
- 만드는 법이 하나 적힌다 — **흔히 쓰이는 기법은 기반 커서 값에 논스(nonce — 한 번만 쓰이는
  수로, 목적은 무작위성을 보장하는 것)를 결합하고 그 결과를 Base64로 인코딩하는 것**이다
  (2장, p.60).[^dynowski2025]
- 오가는 모양 — 첫 요청에서 클라이언트가 `limit`으로 크기를 통제하면 응답이 다음 페이지를
  가져오는 법을 가리키는 `next` 커서를 담고, 클라이언트는 그 값으로 이어서 가져온다.
  **`next`가 비어 있으면 더 이상 결과가 없다는 뜻**이다 (2장 예제 2-8, p.61).[^dynowski2025]
- 필드 이름은 규범이 아니다 — **Slack API 문서에 서술된 한 구현은 다른 필드 이름을 쓴다.
  응답은 `next_cursor`를 담고 클라이언트 요청은 `cursor`를 쓴다** (2장,
  p.61).[^dynowski2025]

## 커서가 더 일관된 이유와 그 대가

- 성능 쪽 — **커서 기반은 큰 데이터셋에서 잘 수행된다. 커서가 데이터셋의 특정 항목을
  식별하므로 체계가 다음 결과 집합을 효율적으로 가져올 수 있기 때문**이다. 그래서
  **라이브 피드처럼 데이터가 자주 바뀌는 동적 환경에 특히 알맞다** (2장, p.61).[^dynowski2025]
- 일관성 쪽 — **항목이 지워지거나 끼워질 때 레코드를 건너뛰거나 중복시킬 수 있는 오프셋 기반과
  달리 커서 기반은 더 일관되게 행동한다.** 이유는 **커서가 알려진 항목에 상대적인 위치를
  나타내므로 주변 데이터가 바뀌어도 페이지 넘김을 안정적으로 이어 갈 수 있기 때문**이다
  (2장, p.61).[^dynowski2025]
- 대가는 항해다 — **커서 기반의 단점은 특정 페이지로 뛰거나 페이지들 사이를 임의로 오가는
  로직을 구현하는 복잡성**이다 (2장, p.61).[^dynowski2025] 곧 오프셋 기반이 주던 이점이
  그대로 빠진다.

## 이 KB의 다른 자리에서 페이지와 커서가 뜻하는 것

- **같은 낱말이 이 KB에서 다른 것을 가리킨다.** 겹쳐 읽으면 어긋나므로 적어 둔다.
  - 여기서 **페이지**는 결과 집합을 자른 덩어리이고, 그 크기는 API가 정한다. 저장 엔진 쪽에서
    **페이지**는 디스크에 고정 크기로 쓰이고 읽히는 블록이며 그 전문은
    [B-트리](../concepts/b-tree-structure.md)에 있다. 두 뜻은 겨루지 않는다 — 층이 다르다.
  - 여기서 **커서**는 클라이언트가 해독하지 못하는 불투명 토큰이다. 데이터베이스 쪽에서 커서는
    서버가 들고 있는 결과 집합의 위치를 가리키는 핸들이다. 이 책의 커서는 **클라이언트가 들고
    다니고 서버는 상태를 남기지 않는다**는 점에서 그쪽과 다르다.
