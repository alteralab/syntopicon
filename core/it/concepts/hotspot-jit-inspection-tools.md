이 페이지의 질문: **가상 머신이 '무엇을 하는가'가 아니라 '어떻게 하고 성능은 어떠한가'를 보려
할 때 무엇으로 보는가.**

## 명세는 개념 모델이 되었다

- **《자바 가상 머신 명세》에는 가상 머신 명령어 세트에 속한 명령어의 의미가 각각 정의되어
  있다. 특히 실행 전후에 피연산자 스택과 지역 변수 테이블이 어떻게 변하는지 자세히 알 수
  있다.** 그런데 **기술이 발전하면서 고성능 가상 머신의 실제 구현은 《자바 가상 머신 명세》의
  정의와 조금씩 차이가 생기기 시작했다** (4장, p.245).[^zhou2024]
- 그 결과가 명세의 지위 변화다 — **《자바 가상 머신 명세》의 조항은 점차 실제 자바 가상 머신을
  구현하기 위한 '개념 모델'이 되어 갔다. 다시 말해 결과가 명세의 설명과 똑같다면 실행 방식은
  달라도 된다는 뜻**이다 (4장, p.245).[^zhou2024]
  - 같은 사정이 메서드 영역의 구현에서도 관측된다 —
    [JHSDB와 서비스 에이전트](../concepts/jhsdb-serviceability-agent.md)의 실험이 그 실물이다.
- 그래서 분석 층이 갈린다 — **프로그램 실행의 '의미(가상 머신이 무엇을 하는지)'를 논할 때는
  바이트코드 수준에서 분석하는 게 완전히 합리적이다. 하지만 프로그램 실행의 '동작(가상 머신이
  어떻게 하고 성능은 어떠한지)'을 논할 때는 바이트코드 수준의 분석이 무의미하다. 따라서 다른
  수단을 찾아야 한다** (4장, p.245).[^zhou2024]
- 일반적인 디버거로는 안 되는 이유도 명확하다 — **JIT 컴파일러가 엄청난 양의 실행 코드를
  동적으로 생성해 코드 캐시에 추가하는데, 이런 혼재된 환경에서 쉽게 디버깅할 간단한 방법은
  없다** (4장, p.245).[^zhou2024]

## 핫스팟 소스가 품고 있는 도구들

- **핫스팟 소스 코드를 깊게 들여다보면 핫스팟 개발 과정에서 많은 플러그인과 보조 도구가
  제작(또는 수집)되어 왔음을 알 수 있다.** `JDK_SRC_HOME/src/utils/` 디렉터리에서 다음을 찾아볼
  수 있다 (4장, pp.244–245):[^zhou2024]
  - **IGV** — **C2 JIT 컴파일러가 바이트코드를 아이디얼 그래프(ideal graph)로 변환한 후 다시
    기계어 코드로 변환하는 과정을 시각화해 준다.**
  - **CCV** — **C1 JIT 컴파일러가 HIR을 생성하고 저수준 중간 표현(이하 LIR)으로 변환한 후 물리
    레지스터를 할당하는 과정을 보여 준다.** 다만 **IGV와 달리 CCV는 핫스팟 코드 저장소에 포함된
    적은 없다.**
  - **프로젝트 크리에이터(Project Creator)** — **비주얼 스튜디오용 `.project` 파일 생성을
    도와준다**(JDK 9 때 제거).
  - **LogCompilation** — **`-XX:+LogCompilation` 옵션으로 출력된 로그를 더 읽기 편한 포맷으로
    변환한다.**
  - **HSDIS** — **JIT 컴파일러용 디스어셈블러**다.
  - 위치가 한 번 옮겨졌다 — **JDK 9까지는 `JDK_SRC_HOME/hotspot/src/share/tools/`
    디렉터리였다** (4장, p.244).

## 관찰용 매개 변수를 쓰기 전에

- 원래는 보이지 않는 것이 정상이다 — **일반적으로 자바 가상 머신의 JIT 컴파일 과정은 사용자와
  애플리케이션 모르게 진행된다. 가상 머신이 코드를 인터프리터로 실행하든 컴파일해서 실행하든
  사용자에게는 영향이 없으며(성능 차이는 크지만 실행 결과는 같음), 대부분의 경우 사용자는 알
  필요조차 없다. 하지만 핫스팟 가상 머신은 디버깅과 최적화용으로 JIT 컴파일과 일부 최적화 동작
  상태를 출력해 주는 매개 변수를 제공한다** (11장, p.529).[^zhou2024]
- 대신 빌드 조건이 붙는다 — **이번 절에서 소개하는 매개 변수 일부는 FastDebug나 SlowDebug
  모드로 빌드된 핫스팟 가상 머신에서만 효과가 있다** (11장, p.529).[^zhou2024]
  - 버전 조건: JDK 6 업데이트 25 이상에서는 받아 쓸 수 없다 — **예전에는 FastDebug로 빌드된
    JDK도 따로 제공되었지만, JDK 6 업데이트 25부터는 오라클과 OpenJDK 웹 사이트 모두 제공을
    중단했다. 따라서 이번 절의 테스트를 완벽하게 수행해 보려면 JDK를 직접 빌드하는 수밖에 없다**
    (11장, p.529). 빌드 절차는
    [OpenJDK 직접 빌드하기](../concepts/building-openjdk-from-source.md)에 있다.
- 이하 관찰의 대상은 메서드 두 개짜리 코드 하나다 (11장, pp.529–530, 코드 11-2):[^zhou2024]

  ```java
  package org.fenixsoft.jvm.chapter11;

  public class Test {
      public static final int NUM = 15000;

      public static int doubleValue(int i) {
          for (int j = 0; j < 100000; j++);  // JIT 코드 최적화 과정 시연용 빈 순환문
          return i * 2;
      }

      public static long calcSum() {
          long sum = 0;
          for (int i = 1; i <= 100; i++) {   // doubleValue()를 100번 호출
              sum += doubleValue(i);
          }
          return sum;
      }

      public static void main(String[] args) {
          for (int i = 0; i < NUM; i++) {    // calcSum()을 1만 5000번 호출
              calcSum();
          }
      }
  }
  ```

## 무엇이 컴파일되었는가 — PrintCompilation

- 매개 변수 하나가 컴파일된 메서드 이름을 준다 — **가상 머신에 `-XX:+PrintCompilation` 매개
  변수를 지정하면 JIT 컴파일러가 네이티브 코드로 컴파일한 메서드의 이름을 출력해 준다** (11장,
  p.530).[^zhou2024] 코드 11-2로 실행하면 **`calcSum()`과 `doubleValue()` 메서드가
  컴파일되었다**는 것과, **컴파일이 여러 번 된 것처럼 보인다는 점**이 함께 나온다. 그리고
  **실제로 여러 번 컴파일된 것이다** (11장, p.530).
- 출력이 네 열이다 (11장, pp.530–531):[^zhou2024]

  | 열 | 무엇 |
  |---|---|
  | 1 | **타임스탬프** |
  | 2 | **컴파일 아이디. 핫스팟 컴파일에서 모든 컴파일 단위에는 고유한 아이디가 부여된다. 단, 표준 JIT 컴파일과 OSR 컴파일은 아이디가 서로 독립적으로 증가한다. 숫자 뒤의 `%`가 온스택 치환을 의미한다** |
  | 3 | **계층형 컴파일에서 계층 단계를 뜻한다. 0은 인터프리터, 1~3은 클라이언트 컴파일러, 4는 서버 컴파일러에 의해 컴파일됐다는 뜻이다** |
  | 4 | **컴파일 대상 메서드의 이름과 몇 가지 추가 정보** — 컴파일된 메서드, 컴파일 단위의 바이트코드 크기(컴파일 전 크기), 그리고 OSR이라면 OSR BCI |

  - 네 번째 열의 추가 정보 하나가 OSR 전용이다 — **온스택 치환의 경우 OSR BCI라는 추가 정보가
    제공된다. 여기서 BCI는 온스택 치환을 촉발한 바이트코드의 위치를 뜻한다. 코드 11-2에서는
    순환문의 위치를 가리킨다** (11장, p.531). 그 촉발 조건은
    [핫스팟 탐지와 온스택 치환](../concepts/hotspot-detection-and-osr.md)에 있다.

## 그 출력을 시간순으로 읽으면

- 저자가 붙인 해석은 여덟 줄이다 (11장, pp.531–532):[^zhou2024] **클라이언트 컴파일러가
  `doubleValue()` 최적화(OSR) → 서버 컴파일러가 `doubleValue()` 최적화(OSR) → 클라이언트
  컴파일러의 최적화 취소(OSR) → 서버 컴파일러가 `doubleValue()` 추가 최적화 → 클라이언트
  컴파일러가 `calcSum()` 최적화 → 서버 컴파일러가 `calcSum()` 최적화(OSR) → 서버 컴파일러가
  `calcSum()` 추가 최적화 → 클라이언트 컴파일러의 최적화 취소**. 취소된 줄에는 `made not
  entrant`가 찍힌다.
- 이 순서가 계층형 컴파일의 설계를 그대로 보여 준다 — **클라이언트 컴파일러는 간단한 최적화만
  적용하여 속도가 빠른 반면, 서버 컴파일러는 더 많은 최적화를 적용하는 만큼 더 느리다. 그래서
  우선 클라이언트 컴파일러를 수행해 급한 불을 끄고, 백그라운드에서 서버 컴파일러를 수행한다.
  서버 컴파일러가 일을 끝마치면 클라이언트 컴파일 결과는 더 이상 필요 없으니 취소한다** (11장,
  p.532).[^zhou2024] 그 구조는
  [JIT 컴파일러와 계층형 컴파일](../concepts/jit-compilers-and-tiered-compilation.md)에 있다.
- 끝난 뒤에도 감시가 이어진다 — **또한 최적화를 수행한 후에도 지속해서 상황을 모니터링하다가,
  더 적극적인 최적화가 필요하다고 판단되면 추가 최적화를 시도할 수 있다** (11장,
  p.532).[^zhou2024]

## 인라인 여부 — PrintInlining

- 매개 변수를 하나 더 얹으면 인라인 판정이 보인다 — **`-XX:+PrintInlining` 매개 변수까지
  지정하면 메서드 인라인 정보도 출력해 준다** (11장, p.532).[^zhou2024] 출력의 판정 문구는
  `inlining prohibited by policy`(인라인 거부)와 `inline (hot)`(인라인 수행)으로 갈린다 (11장,
  p.533).
- 결과가 호출 자체를 없앤다 — **출력 결과에서 알 수 있듯이 `doubleValue()`가 `calcSum()`
  메서드로 인라인되었다. 인라인 후 가상 머신이 `calcSum()` 메서드를 실행할 때는
  `doubleValue()`가 다시 호출되지 않는다. 이처럼 코드 로직이 모두 `calcSum()`에 직접
  삽입(인라인)되어 메서드 디스패치 부하가 없어진다** (11장, p.533).[^zhou2024] 인라인이 왜
  최적화의 관문인지는
  [JIT 컴파일러의 최적화 기법](../concepts/jit-optimization-techniques.md)에 있다.

## HSDIS: 네이티브 코드를 되돌려 읽기

- **HSDIS는 오라클이 권장하는 핫스팟 가상 머신 JIT 컴파일 코드용 디스어셈블리 플러그인이다.
  OpenJDK에 소스가 포함되어 있어 직접 빌드할 수도 있고, 인터넷에서 미리 빌드한 바이너리(`.so`
  또는 `.dll` 파일 형태)도 찾을 수 있다** (4장, p.245).[^zhou2024]
- 설치는 경로에 놓는 것이 전부다 — **바이너리 파일을 리눅스·맥OS는 `JDK_HOME/lib`, 윈도우는
  `JDK_HOME\bin`에 넣으면 핫스팟이 실행될 때 자동으로 찾는다** (4장, pp.245–246).[^zhou2024]
  - 옮긴이의 실측이 붙어 있다 — **문서상으로는 윈도우에서도 `JDK_HOME\lib` 디렉터리에 넣으면
    된다고 하는데, 직접 실행해 보니 무슨 이유에서인지 해당 바이너리 파일을 찾지 못했다** (4장,
    p.246, 옮긴이 주).
- **실행은 핫스팟에 `-XX:+PrintAssembly` 매개 변수를 추가하면 된다. 그러면 핫스팟의 JIT
  컴파일러가 동적으로 생성한 네이티브 코드를 HSDIS가 어셈블리 코드로 복원해 출력한다. 유용한
  주석도 달아 준다. 프로그램을 가장 낮은 수준에서 들여다볼 수 있게 되는 것**이다 (4장,
  p.246).[^zhou2024]
  - 빌드 모드에 따라 조건이 하나 붙는다 — **SlowDebug나 FastDebug 모드로 컴파일한 핫스팟에서는
    `-XX:+PrintAssembly` 매개 변수만으로 HSDIS를 곧바로 이용할 수 있다. 반면 Product 모드의
    핫스팟이라면 `-XX:+UnlockDiagnosticVMOptions` 매개 변수도 추가해야 한다** (4장, p.246).
    빌드 모드를 고르는 자리는
    [OpenJDK 직접 빌드하기](../concepts/building-openjdk-from-source.md)다.
- 필드 하나와 정적 변수 하나, 매개 변수 하나를 더하는 `sum()` 메서드만 컴파일해 보는 실행 예다
  (4장, pp.246–247):[^zhou2024]

  ```sh
  java -XX:+UnlockDiagnosticVMOptions -XX:+PrintAssembly -Xcomp -XX:CompileCommand=dontinline,*Bar.sum -XX:CompileCommand=compileonly,*Bar.sum test.Bar
  ```

  - **`-XX:+PrintAssembly`** — **디스어셈블된 코드 출력.**
  - **`-Xcomp`** — **가상 머신이 코드를 컴파일 모드로 실행한다. 핫 코드가 될 때까지 오래
    기다리지 않아도 JIT 컴파일이 바로 이루어진다.**
  - **`-XX:CompileCommand=dontinline,*Bar.sum`** — **`sum()` 메서드 인라인 방지.**
  - **`-XX:CompileCommand=compileonly,*Bar.sum`** — **`sum()` 메서드만 컴파일.**

## 디스어셈블 결과에서 읽히는 것

- 출력의 머리에서 레지스터 배정이 먼저 확인된다 — **`rsi` 레지스터는 `this` 객체를 가리키는
  포인터이고 `rdx` 레지스터는 첫 번째 매개 변수**다. **`rdx`는 64비트 레지스터이며 `edx`는
  `rdx`의 첫 32비트 부분**이다 (4장, pp.247–248).[^zhou2024]
- Verified Entry Point 이후의 코드는 이렇게 읽힌다 (4장, pp.248–249):[^zhou2024]

  | 명령 | 무엇을 하는가 |
  |---|---|
  | `mov %eax,-0x14000(%rsp)` | 스택 오버플로 여부를 확인한다 |
  | `push %rbp` | 이전 스택 프레임의 기저 주소를 저장한다 |
  | `sub $0x30,%rsp` | 새 프레임을 위한 공간을 할당한다 |
  | `mov 0xc(%rsi),%eax` | **인스턴스 변수 `a`를 얻는다.** 오프셋 `0xc`는 `this` 객체의 객체 헤더를 지나 인스턴스 변수 `a`의 메모리 위치를 담고 있다 — **자바 힙의 데이터에 접근하는 코드다** |
  | `movabs $0x8b918bc8,%rsi` | **메서드 영역에 있는 `test.Bar`의 포인터를 얻어 `rsi` 레지스터에 저장한다** |
  | `mov 0x70(%rsi),%esi` | **`test.Bar`에 선언된 클래스 변수(정적 변수) `b`의 값을 얻어 `esi` 레지스터에 저장한다 — 메서드 영역에 있는 데이터에 접근하는 코드다** |
  | `add %esi,%eax` · `add %edx,%eax` | `a + b + c`를 계산하기 위해 더하기 연산을 두 번 수행한다 |
  | `add $0x30,%rsp` | 스택 프레임을 되돌린다 |
  | `pop %rbp` | 이전 스택 프레임을 복구한다 |
  | (폴링 명령) | **폴링 메서드가 반환되는 안전 지점이다** |
  | `ret` | 메서드가 실행을 마치고 반환된다 |

  - 마지막에서 두 번째 줄이 이 KB의 다른 페이지와 만난다 — 메서드 반환 직전에 놓인 안전 지점
    폴링이 [핫스팟의 가비지 컬렉션 구현 상세](../concepts/hotspot-gc-implementation.md)가
    설명하는 **자발적 멈춤**의 실물이다.
  - 객체 헤더를 지나 필드가 놓이는 배치는
    [객체 생성과 메모리 레이아웃](../concepts/object-creation-and-memory-layout.md)에 있다.
- 출력이 두 벌 나오는 이유도 적혀 있다 — **C1 컴파일러가 컴파일한 버전에 이어 C2 컴파일러가
  컴파일한 버전도 등장한다. 이는 핫스팟이 계층형 컴파일을 한 결과**다 (4장,
  p.249).[^zhou2024]
- 규모에 대한 경고 — **이번 예는 워낙 간단해서 맨눈으로도 디스어셈블된 코드를 해석하는 데 큰
  무리가 없다. 하지만 일반적으로는 너무 거대한 코드가 쏟아져 나온다. 그럴 때는 도구의 힘을
  빌려야 한다** (4장, p.249).[^zhou2024]

## 중간 표현까지 꺼내기

- 네이티브 코드 앞 단계도 출력된다 — **`-XX:+PrintOptoAssembly`(서버 모드 가상 머신용)나
  `-XX:+PrintLIR`(클라이언트 모드 가상 머신용) 매개 변수를 지정해 최종 결과에 더 가까운 중간
  표현을 출력할 수도 있다** (11장, p.533).[^zhou2024] 저자는 **OpenJDK 17을 서버 모드로
  빌드했으므로 `-XX:+PrintOptoAssembly`를 사용했다**고 밝히며, 그 출력에는 **조금 전보다 많은
  정보(주로 주석)가 포함되어 있어서 사람이 JIT 컴파일러의 최적화 결과를 읽고 이해하는 데 도움이
  된다**고 적는다 (11장, p.533).
  - 그 주석에 실제로 무엇이 실리는지가 출력에 드러난다 — 프레임 생성·파괴(`# Create frame`·
    `# Destroy frame`), 레지스터 스필(`# spill`), 스택 뱅(`# stack bang`), 그리고 **`# Safepoint:
    poll for GC`** 라는 안전 지점 폴링 주석과 소스 줄 번호(`bci`·`line`)가 함께 나온다 (11장,
    pp.533–534).
- 결과가 아니라 과정을 파일로 받을 수도 있다 — **네이티브 코드 생성 결과에 더해 네이티브 코드
  생성 과정까지 추적하려면 `-XX:+PrintCFGToFile`(클라이언트 컴파일러용)이나
  `-XX:PrintIdealGraphFile` 계열(서버 컴파일러용)을 지정한다. 그러면 자바 가상 머신이 컴파일
  과정의 다양한 단계에서 생성한 결과물을 파일로 출력해 준다. 예를 들어 클라이언트 컴파일러의
  경우 바이트코드, HIR, LIR, 레지스터 할당 처리, 네이티브 코드 등을 출력한다** (11장,
  p.534).[^zhou2024] 그 단계들의 정체는
  [JIT 컴파일러의 컴파일 과정](../concepts/jit-compilation-process.md)에 있다.
- 그 파일을 여는 도구가 앞에서 이름만 나온 둘이다 — **이렇게 얻은 데이터 파일은 클라이언트
  컴파일러용인 CCV나 서버 컴파일러용인 IGV로 열어 분석할 수 있다** (11장, p.534).[^zhou2024]

## IGV로 최적화 단계를 따라가기

- 서버 컴파일러의 중간 표현에 이름이 있다 — **서버 컴파일러의 중간 코드 표현은 아이디얼
  그래프라고 하는 프로그램 의존성 그래프다** (11장, p.534).[^zhou2024]
- 뽑는 방법은 매개 변수 두 개다 — **FastDebug나 SlowDebug로 빌드된 가상 머신에**
  `-XX:PrintIdealGraphLevel=2 -XX:PrintIdealGraphFile=ideal.xml`을 지정해 실행하면 된다 (11장,
  p.534):[^zhou2024]

  ```sh
  java -XX:PrintIdealGraphLevel=2 -XX:PrintIdealGraphFile=ideal.xml org.fenixsoft.jvm.chapter11.Test
  ```

  - 상세도는 눈금이 다섯이다 — **`-XX:PrintIdealGraphLevel`의 값은 0~4 사이로 지정하면 된다.
    0은 아무런 값도 출력하지 않고, 숫자가 커질수록 더 자세한 정보를 출력한다.
    `-XX:PrintIdealGraphFile` 매개 변수로는 생성할 파일의 이름을 지정한다** (11장, p.534).
- 도구 자체도 빌드해야 한다 — IGV는 `JDK_SRC_HOME/src/utils/IdealGraphVisualizer`에 있고
  메이븐으로 `mvn install` 한 뒤 `igv.sh`를 실행한다 (11장, p.535).[^zhou2024] 옮긴이의 실측이
  붙어 있다 — 그대로 실행하면 **아무것도 할 수 없는 빈 화면과 함께 오류 창이 뜬다. 오류 메시지는
  'Cannot load even default layout, using internally predefined configuration'인데, 문제를
  해결하는 데 별다른 도움을 주지 못한다.** 해결책은 **JDK 11 버전으로 실행**하는 것이며,
  `JAVA_HOME`을 OpenJDK 11로 바꾸면 **드디어 IGV가 제대로 실행된다** (11장, p.535).
- 열면 컴파일된 메서드 목록과 그 아래 단계들이 나온다 — **이 패널에서 메서드를 확장하면 파싱
  직후부터 최종 코드까지 최적화의 다양한 단계가 펼쳐진다. 적용된 최적화에 따라 각 메서드가 거쳐
  가는 단계가 달라진다** (11장, p.536).[^zhou2024]
  - 메서드가 두 개씩 보이는 이유가 앞 절의 결론과 맞물린다 — **`doubleValue()`와 `calcSum()`
    메서드가 각각 두 개씩이다. 하나는 표준 컴파일의 결과이고 다른 하나는 OSR 컴파일의 결과다.
    (…) 두 메서드 모두 3번씩 컴파일되었으나 그중 클라이언트 컴파일러의 결과는 취소되었다. 그래서
    최종적으로 2개씩 남아 있는 것이다** (11장, p.536).

## 빈 순환문은 어디서 사라지는가

- 컴파일의 첫 스냅숏이 무엇인지가 정의된다 — **JIT 컴파일러는 자바 메서드를 컴파일할 때 먼저
  바이트코드를 파싱하여 중간 표현으로 변환한다. 그런 다음 분석과 최적화를 수행하고 마지막으로
  네이티브 코드를 생성한다. After Parsing은 서버 컴파일러가 '파싱을 막 끝내고 아직 아무런
  최적화도 적용하지 않은 상태'를 아이디얼 그래프로 표현한 결과다. 각 사각형이 프로그램의 기본
  블록이다. 기본 블록은 프로그램을 제어 흐름에 따라 나눈 가장 작은 코드 블록을 말한다** (11장,
  p.538).[^zhou2024]
- 두 줄짜리 메서드가 왜 복잡한지도 설명된다 — **`doubleValue()`는 겨우 두 줄짜리 단순한
  메서드지만 기본 블록으로 구성된 그래프는 생각보다 훨씬 복잡하다. 자바 언어가 규정하는 타입
  안전성, 널 포인터 검사 같은 안전성 요구 사항과 안전 지점 폴링 등 자바 가상 머신의 동작에
  필요한 로직이 추가되기 때문이다. 또한 순환문과 같은 일부 프로그램 코드는 그 자체가 기본 블록
  여러 개로 구성되기 때문이기도 하다** (11장, p.538).[^zhou2024]
- 관찰 방법이 곧 판정 방법이다 — **컴파일 과정에서 빈 순환문이 언제 최적화되는지 알아보고
  싶다면, 해당 기본 블록이 언제 없어지는지 확인하면 된다.** 단계를 넘겨 보면 **PhaseIdealLoop 1
  단계에서 순환문 관련 블록들이 사라진다** (11장, p.538).[^zhou2024]
  - 두 단계를 직접 비교하는 기능도 있다 — Outline 패널에서 비교할 단계를 고르고 우클릭 →
    **Difference to current graph** 메뉴를 실행하면 **두 단계의 차이를 분석해 보여 준다(제거된
    블록과의 연결은 점선으로 표시)** (11장, p.539).
  - 그래서 결론이 나온다 — **PhaseIdealLoop 1 단계에서 순환문 작업이 제거됐음을 확인할 수 있다.
    최종 네이티브 코드에서도 빈 순환문이 실행되지 않는다는 뜻이다** (11장, p.539). 저자가 이
    실험을 붙인 이유는 통념 하나를 깨기 위해서다 — **아직까지도 빈 순환문으로 프로그램 실행을
    약간 지연시킬 수 있다고 소개하는 프로그래밍 입문서가 보인다** (11장, p.536).
- 사라지는 것은 순환문만이 아니다 — **After Parsing 단계부터 최종 Final Code 단계까지 차례로
  비교해 보면 `doubleValue()`의 아이디얼 그래프가 전반적으로 단순하게 변해 감을 확인할 수 있다.
  (…) 최종 코드에서는 빈 순환문이 주던 부하가 사라질 뿐 아니라 불필요한 안전성 요구 사항 관련
  작업과 안전 지점 폴링 등도 사라져 있을 것이다. 컴파일러는 이러한 보호 장치 없이도 프로그램이
  똑같은 결과를 내고, 관찰 가능한 부작용이 없으며, 가상 머신이 보안 위협도 받지 않을 것이라고
  판단하기 때문이다** (11장, p.539).[^zhou2024] 그 판단을 안전 지점 쪽에서 보면
  [핫스팟의 가비지 컬렉션 구현 상세](../concepts/hotspot-gc-implementation.md)가 말하는 폴링이
  줄어드는 것이다.

## JITWatch

- **JITWatch는 핫스팟 JIT 컴파일러용 로그 분석 및 시각화 도구로, HSDIS와 자주 함께 쓰인다.
  홈페이지에서 소스 코드뿐 아니라 빌드된 바이너리도 플랫폼별로 제공한다** (4장,
  p.249).[^zhou2024]
- 입력은 컴파일 로그다 — **매개 변수에 `-XX:+LogCompilation -XX:LogFile=logfile.log`를 추가해
  실행하면 JITWatch가 읽어 들일 로그가 저장된다** (4장, p.249).[^zhou2024]
- 쓰는 순서는 **Config 버튼으로 소스 코드와 클래스 파일의 경로를 설정한 뒤, Open Log로 로그
  파일을 읽고 Start를 눌러 분석하는 것**이며, **메서드를 선택하면 해당하는 자바 소스 코드,
  바이트코드, JIT 컴파일러가 생성한 어셈블리 코드를 동시에 확인할 수 있다** (4장,
  pp.250–251).[^zhou2024]
- 마무리에 붙는 경계 — **《자바 가상 머신 명세》 자체는 모니터링이나 문제 해결 방법을 정의하고
  있지 않으므로 도구에 따라 지원하는 가상 머신과 기능 범위가 다를 수 있다. 따라서 핫스팟 외의
  가상 머신을 이용하는 독자라면 적합한 분석 도구를 선택하는 게 특히 중요하다** (4장,
  p.252).[^zhou2024]
  - 그래서 책은 **IBM J9·OpenJ9용(IBM Support Assistant, Heap Analyzer, Thread and Monitor Dump
    Analyzer, Pattern Modeling and Analysis Tool for Java Garbage Collector, 이클립스 Memory
    Analyzer Tool + IBM DTFJ 플러그인)** 과 **HP-UX·SAP·핫스팟 VM용(HP의 HPjmeter와 HPjtune)**
    목록을 따로 싣고 있다 (4장, p.252).
