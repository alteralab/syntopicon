하나의 질문: **코드가 뻔하다는 것은 무엇이며, 무엇이 그것을 만들고 무엇이 그것을 깨뜨리는가.**

## 뻔함의 정의

- 이 장의 자리 — **불명료(obscurity)는 §2.3에서 서술한 복잡성의 두 주요 원인 중 하나다.
  불명료는 시스템에 대한 중요한 정보가 새 개발자에게 뻔하지 않을 때 일어난다. 불명료 문제의
  해법은 코드를 뻔하게 만드는 방식으로 쓰는 것이다** (18장, p.147).[^ousterhout2021]
  두 원인의 정의는 [복잡성의 정의와 증상](software-complexity-defined.md)에 있다.
- 뻔함(obviousness)의 조작적 정의 (18장, p.147):[^ousterhout2021]

> If code is obvious, it means that someone can read the code quickly, without much thought,
> and their first guesses about the behavior or meaning of the code will be correct.

- 뻔하지 않을 때의 대가 — **코드가 뻔하면 독자는 그 코드로 일하는 데 필요한 정보를 모으는 데
  많은 시간이나 노력을 들일 필요가 없다. 코드가 뻔하지 않으면 독자는 그것을 이해하는 데 많은
  시간과 기운을 써야 한다. 이것은 그들의 효율을 떨어뜨릴 뿐 아니라 오해와 버그의 가능성도
  높인다** (18장, p.147).[^ousterhout2021]
- 그리고 주석과의 관계 — **뻔한 코드는 뻔하지 않은 코드보다 주석이 덜 필요하다** (18장,
  p.147).[^ousterhout2021]

## 판정자는 읽는 사람이다

- 조문 (18장, p.147):[^ousterhout2021]

> "Obvious" is in the mind of the reader: it's easier to notice that someone else's code is
> nonobvious than to see problems with your own code. Thus, the best way to determine the
> obviousness of code is through code reviews.

- 그리고 논쟁 금지 규칙이 다시 나온다 — **당신의 코드를 읽는 누군가가 뻔하지 않다고 말하면
  그것은 뻔하지 않은 것이다. 당신에게 아무리 명료해 보이더라도. 무엇이 그 코드를 뻔하지 않게
  만들었는지 이해하려 함으로써 당신은 미래에 더 나은 코드를 쓰는 법을 배울 것이다** (18장,
  p.147).[^ousterhout2021]
  - 같은 규칙이 주석에 대해
    [주석은 코드에서 뻔하지 않은 것을 서술한다](../concepts/comments-describe-the-nonobvious.md)의 맺음
    절에 있다. **두 장이 같은 판정 절차를 공유한다** — 기준은 쓴 사람의 자기 평가가 아니라
    첫 독자의 반응이고, 그 반응은 반박 대상이 아니라 데이터다.

## 뻔하게 만드는 것 — 이름과 일관성

- 앞 장들이 이미 두 기법을 다뤘다 — **첫째는 좋은 이름을 고르는 것이다(14장). 정밀하고
  유의미한 이름은 코드의 동작을 명료하게 하고 문서화의 필요를 줄인다. 이름이 모호하거나
  중의적이면 독자는 이름 붙은 실체의 의미를 연역하려고 코드를 읽어야 한다; 이것은 시간이
  걸리고 오류를 부른다. 둘째 기법은 일관성이다(17장). 비슷한 것이 언제나 비슷하게 되어
  있으면 독자는 전에 본 패턴을 알아보고 코드를 상세히 분석하지 않고도 즉시 (안전한) 결론을
  내릴 수 있다** (18장 §18.1, pp.147–148).[^ousterhout2021]
  전문은 [이름 짓기](../concepts/naming-things.md)와 [코드의 일관성](../concepts/consistency-in-code.md)에 있다.

## 뻔하게 만드는 것 — 여백

- 조문 — **코드가 서식되는 방식은 그것을 이해하기가 얼마나 쉬운지에 영향을 줄 수 있다**
  (18장 §18.1, p.148).[^ousterhout2021]
- **실물 ① 매개변수 문서화** — 저자는 여백을 짜낸 Javadoc `@param` 블록을 보이고 이렇게
  판정한다 — **한 매개변수의 문서화가 어디서 끝나고 다음이 어디서 시작하는지 보기 어렵다.
  매개변수가 몇 개인지, 그 이름이 무엇인지조차 뻔하지 않다. 여백을 조금 더하면 구조가 갑자기
  명료해지고 문서화를 훑기 쉬워진다** (18장 §18.1, p.148).[^ousterhout2021] 고친 판은 각
  `@param` 이름을 자기 줄에 두고 설명을 들여쓴다.
- **실물 ② 블록 구분** — **빈 줄은 메서드 안의 주요 코드 블록을 분리하는 데도 쓸모 있다**
  (18장 §18.1, p.148).[^ousterhout2021] 저자가 든 버퍼 할당 메서드는 정렬 계산·기존 공간
  사용·마지막 청크 뒤 여유 사용·새 할당 생성 네 블록이 빈 줄로 갈려 있고, 각 블록이 주석으로
  시작한다. 그 상승 효과 — **이 접근은 각 빈 줄 다음 첫 줄이 다음 코드 블록을 서술하는
  주석일 때 특히 잘 동작한다: 빈 줄이 주석을 더 눈에 띄게 만든다** (18장 §18.1,
  p.149).[^ousterhout2021]
- **실물 ③ 문장 안의 여백** — **문장 안의 여백은 문장의 구조를 명료하게 하는 데 도움이 된다**
  (18장 §18.1, p.149).[^ousterhout2021] 저자가 대비하는 것은 `for(int pass=1;pass>=0&&!empty;pass--)`와
  `for (int pass = 1; pass >= 0 && !empty; pass--)` 두 줄이다.
- 그리고 마지막 수단으로 주석 — **때로는 뻔하지 않은 코드를 피할 수 없다. 그럴 때는 빠진
  정보를 제공해 보상하도록 주석을 쓰는 것이 중요하다. 이것을 잘하려면 독자의 자리에 서서
  무엇이 그들을 혼란시킬 가능성이 높은지, 어떤 정보가 그 혼란을 걷어 낼지 알아내야 한다**
  (18장 §18.1, p.149).[^ousterhout2021]

## 덜 뻔하게 만드는 것 — 이벤트 구동 프로그래밍

- 저자의 단서가 먼저 붙는다 — **코드를 뻔하지 않게 만드는 것은 많다; 이 절은 몇 가지 예를
  제공한다. 그중 어떤 것, 이를테면 이벤트 구동 프로그래밍은 어떤 상황에서 쓸모 있으므로
  당신은 어쨌든 그것을 쓰게 될 수도 있다. 그럴 때는 추가 문서화가 독자의 혼란을 최소화하는
  데 도움이 될 수 있다** (18장 §18.2, p.150).[^ousterhout2021]
- 왜 뻔하지 않은가 — **이벤트 구동 프로그래밍은 제어 흐름을 따라가기 어렵게 만든다. 이벤트
  처리기 함수는 결코 직접 호출되지 않는다; 그것들은 통상 함수 포인터나 인터페이스를 써서
  이벤트 모듈에 의해 간접적으로 호출된다. 이벤트 모듈에서 호출 지점을 찾아도 어느 특정 함수가
  호출될지는 여전히 알 수 없다: 이것은 실행 시간에 어떤 처리기가 등록됐는지에 달렸다. 이
  때문에 이벤트 구동 코드를 추론하거나 그것이 동작한다고 스스로를 납득시키기 어렵다** (18장
  §18.2, p.150).[^ousterhout2021]
- **보상책이 인터페이스 주석이다** — **이 불명료를 보상하려면 각 처리기 함수의 인터페이스
  주석을 써서 그것이 언제 호출되는지 가리켜라** (18장 §18.2, p.150).[^ousterhout2021]
  저자가 든 형태가 이것이고, 이 장이 복사해 쓸 것으로 내놓는 물건이다 (18장 §18.2,
  p.150):[^ousterhout2021]

  ```c
  /**
   * This method is invoked in the dispatch thread by a transport if a
   * transport-level error prevents an RPC from completing.
   */
  ```

## 붉은 깃발 — 뻔하지 않은 코드

조문 (18장 §18.2, pp.150–151):[^ousterhout2021]

> **Red Flag: Nonobvious Code**
>
> If the meaning and behavior of code cannot be understood with a quick reading, it is a red
> flag. Often this means that there is important information that is not immediately clear to
> someone reading the code.

## 덜 뻔하게 만드는 것 — 범용 컨테이너

- 유혹의 구조 — **많은 언어가 두 개 이상의 항목을 한 객체로 묶는 범용 클래스를 제공한다.
  자바의 `Pair`나 C++의 `std::pair` 같은 것이다. 이 클래스들은 여러 객체를 변수 하나로
  넘기기 쉽게 만들기 때문에 솔깃하다. 가장 흔한 용도 중 하나는 메서드에서 여러 값을 반환하는
  것이다** (18장 §18.2, p.151).[^ousterhout2021]
- 진단 — **불행히도 범용 컨테이너는 뻔하지 않은 코드를 낳는데, 묶인 원소가 그 의미를 가리는
  범용 이름을 갖기 때문이다. 위 예에서 호출자는 두 반환값을 `result.getKey()`와
  `result.getValue()`로 참조해야 하는데, 이것은 그 값들의 실제 의미에 대한 아무 단서도 주지
  않는다** (18장 §18.2, p.151).[^ousterhout2021]
- 처방 — **따라서 범용 컨테이너는 쓰지 않는 편이 낫다. 컨테이너가 필요하면 특정 용도에
  특수화된 새 클래스나 구조체를 정의하라. 그러면 원소에 유의미한 이름을 쓸 수 있고, 선언에
  추가 문서화를 제공할 수 있다. 이것은 범용 컨테이너로는 불가능하다** (18장 §18.2,
  p.151).[^ousterhout2021]
- **그리고 이 예에서 일반 규칙이 뽑힌다** (18장 §18.2, p.151):[^ousterhout2021]

> This example illustrates a general rule: software should be designed for ease of reading,
> not ease of writing.

  **범용 컨테이너는 코드를 쓰는 사람에게는 편의적이지만 뒤따르는 모든 독자에게 혼란을
  만든다. 코드를 쓰는 사람이 몇 분을 더 들여 특정 컨테이너 구조를 정의하는 편이 나으며,
  그러면 결과 코드가 더 뻔해진다** (18장 §18.2, p.151).[^ousterhout2021]
  - 이 규칙이 [복잡성을 아래로 끌어내리기](pull-complexity-downwards.md)의 셈법과 같은
    형태다 — **한 사람의 불편으로 여러 사람의 불편을 사는 거래**이고, 다만 그쪽은 모듈
    사용자와 개발자를, 이쪽은 코드의 독자와 저자를 센다.

## 덜 뻔하게 만드는 것 — 선언과 할당의 타입이 다를 때

- 저자가 든 자바 예는 변수를 `List<Message>`로 선언하고 실제로는 `ArrayList<Message>`를
  할당하는 것이다. 판정 — **변수는 `List`로 선언됐지만 실제 값은 `ArrayList`다. 이 코드는
  합법인데 `List`가 `ArrayList`의 상위 클래스이기 때문이다. 그러나 선언은 보고 실제 할당은
  보지 못한 독자를 오도할 수 있다. 실제 타입은 그 변수가 어떻게 쓰이는지에 영향을 줄 수 있으므로
  (`ArrayList`는 `List`의 다른 하위 클래스와 다른 성능·스레드 안전성 성질을 가진다) 선언을
  할당과 맞추는 편이 낫다** (18장 §18.2, p.151).[^ousterhout2021]

## 덜 뻔하게 만드는 것 — 독자의 기대를 어기는 코드

- 저자가 든 예는 자바 애플리케이션의 `main`이 `new RaftClient(...)` 한 줄만 실행하고 반환하는
  것이다. 진단 — **대부분의 애플리케이션은 main 프로그램이 반환할 때 종료하므로 독자는 여기서도
  그럴 것이라고 가정할 가능성이 높다. 그러나 그렇지 않다. `RaftClient`의 생성자가 추가 스레드를
  만들고, 그 스레드들은 애플리케이션의 메인 스레드가 끝나도 계속 동작한다** (18장 §18.2,
  pp.151–152).[^ousterhout2021]
- 처방과 그 이중 배치 — **이 동작은 `RaftClient` 생성자의 인터페이스 주석에 문서화돼야 하지만,
  그 동작이 충분히 뻔하지 않으므로 `main` 끝에도 짧은 주석을 두는 것이 값어치가 있다. 그
  주석은 애플리케이션이 다른 스레드에서 계속 실행될 것임을 가리켜야 한다** (18장 §18.2,
  p.152).[^ousterhout2021]
- 일반 규칙 — **코드는 독자가 기대할 관례를 따를 때 가장 뻔하다; 그렇지 않다면 독자가
  혼란스럽지 않도록 그 동작을 문서화하는 것이 중요하다** (18장 §18.2,
  p.152).[^ousterhout2021]

## 정보를 보장하는 세 가지 방법

- 뻔함을 정보의 언어로 다시 적는다 — **뻔함을 생각하는 또 다른 방법은 정보의 관점이다. 코드가
  뻔하지 않다면 그것은 보통 독자가 갖고 있지 않은 중요한 정보가 코드에 있다는 뜻이다**
  (18장 §18.3, p.152).[^ousterhout2021]
- **세 방법이 우선순위와 함께 제시된다** (18장 §18.3, p.152):[^ousterhout2021]
  - **가장 좋은 방법은 필요한 정보의 양 자체를 줄이는 것이다. 추상과 특수 사례 제거 같은
    설계 기법을 써서다.**
  - **둘째, 독자가 다른 맥락에서 이미 얻은 정보를 활용할 수 있다(예컨대 관례를 따르고 기대에
    부응함으로써). 그러면 독자가 당신의 코드를 위해 새 정보를 배울 필요가 없다.**
  - **셋째, 좋은 이름과 전략적 주석 같은 기법을 써서 중요한 정보를 코드에서 그들에게 제시할
    수 있다.**
  - **순서가 우연이 아니다.** 첫째는 설계로 푸는 것(4·10장), 둘째는 일관성으로 푸는 것(17장),
    셋째는 이름과 주석으로 푸는 것(13·14장)이다. **문서화가 마지막 수단이라는 배치**이고,
    이것이 [주석을 왜 쓰는가](why-write-comments.md)의 "좋은 설계가 주석의 필요를 줄인다는
    데는 동의한다"와 정확히 같은 자리다.

## 둘째 소스 — 뻔하지 않아도 코드가 도는 경우

이 장은 뻔하지 않음의 대가를 **읽는 사람의 시간과 버그 가능성**으로 잰다. 도메인 주도 설계
쪽 원전은 같은 진단에 한 가지를 더한다 — **버그가 나지 않는 경우**의 대가다.

- 인터페이스가 말해 주지 않을 때 무엇이 사라지는가 (10장, p.246):[^evans2003]

> If a developer must consider the implementation of a component in order to use it, the value
> of encapsulation is lost.

- 그리고 그다음 문장이 이 페이지에 없던 실패 유형이다 — **원래 개발자가 아닌 누군가가 객체나
  연산의 목적을 그 구현에 기반해 유추해야 한다면, 그 새 개발자는 그 연산이나 클래스가
  우연히만 충족하는 목적을 유추할 수 있다. 그것이 의도가 아니었다면 그 코드는 당장은 작동할 수
  있지만 설계의 개념적 기반은 훼손되었을 것이고, 두 개발자는 서로 어긋난 목적으로 일하게 될
  것이다** (10장, p.246).[^evans2003]
  - 위 [뻔함의 정의](#뻔함의-정의)는 **첫 짐작이 맞는가**로 뻔함을 판정한다. 이 소스가 더하는
    것은 **첫 짐작이 우연히 맞는 경우**다. 그때 테스트는 통과하고 코드는 돌지만 두 사람의
    모델이 갈라지므로, 이 실패는 나중에 설계가 어긋나는 것으로만 드러난다. 두 소스가 서로를
    참조한 적은 없다.
- 인지 부하의 셈법은 이 페이지와 같다 — **우리는 늘 인지 과부하와 싸우고 있다: 클라이언트
  개발자의 머리가 어떤 구성 요소가 어떻게 자기 일을 하는지에 대한 세부로 넘치면, 그의 머리는
  클라이언트 설계의 복잡한 문제를 풀 여유가 없다** (10장, p.246).[^evans2003] 다만 단서 하나가
  이 페이지의 [판정자는 읽는 사람이다](#판정자는-읽는-사람이다) 절을 옆에서 받친다 —
  **같은 사람이 자기 코드를 개발하고 쓰는 두 역할을 다 맡을 때조차 이것은 참인데, 그가 그
  세부를 배울 필요가 없다 해도 한 번에 고려할 수 있는 요인의 수에는 한계가 있기 때문이다**
  (10장, p.246).[^evans2003]
- **정보를 줄이는 방법에 대한 처방도 층이 다르다.** 위
  [정보를 보장하는 세 가지 방법](#정보를-보장하는-세-가지-방법)의 셋째가 "좋은 이름"이라면,
  이 소스는 그 이름의 정본을 개인의 판단이 아니라 팀이 합의한 모델에 둔다 — 이름은 **팀원이
  그 의미를 빠르게 유추할 수 있도록 유비쿼터스 언어(ubiquitous language)를 따라야 한다**
  (10장, p.247).[^evans2003] 그러면 둘째 방법(독자가 이미 가진 정보의 활용)과 셋째 방법이
  한 장치로 합쳐진다 — 모델을 아는 독자에게 이름은 이미 아는 정보이기 때문이다.
  전문은 [의도를 드러내는 인터페이스](../concepts/intention-revealing-interfaces.md)에 있다.
