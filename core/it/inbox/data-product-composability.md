## 하나의 질문

**단일 스키마도 중앙 타입 레지스트리도 없이, 서로 다른 데이터 프로덕트의 데이터를 어떻게
잇는가.**

- 13장 도입이 문제를 세운다 — **여러 기존 데이터의 교차와 집계로 새 데이터를 조합하는 것은 모든
  데이터 작업에 필요한 기본 기능이다. 데이터 메시는 **변화의 병목이 되는 단단히 결합된 데이터
  모델을 만들지 않고** 여러 데이터 프로덕트를 탈중앙적으로 조합하는 능력을 도입한다** (13장,
  p.233).[^dehghani2022]
- 절 머리의 제사 — **Learn how to see. Realize that everything connects to everything
  else. — Leonardo da Vinci** (13장, p.244).[^dehghani2022]
- 저자의 예 — **강력한 분석 사용 사례는 여러 데이터 프로덕트와 서로 다른 도메인에 걸쳐 데이터를
  상관시키고 연결하기를 요구한다. 예컨대 **emerging artists**를 식별하는 사용 사례는 아티스트가
  일정 기간 인기를 얻고 있는지를 분류하는 기계 학습 모델의 훈련을 요구한다. 이 모델을 훈련하려면
  메시의 다양한 데이터 프로덕트 — 아티스트의 곡이 들어 있는 **playlists**, 청취자가 아티스트의
  음악을 재생한 **play sessions**, 아티스트의 언급이 나타나는 **social media** 콘텐츠 — 를
  상관시켜야 한다. 모델은 각 아티스트에 대해, 그리고 특정 시간 윈도우에 대해 이 데이터
  프로덕트들을 상관시켜야 한다** (13장, p.244).[^dehghani2022]

## 무엇을 조합이라 부르는가

- 조합하는 주체 — **메시를 가로질러 데이터를 연결해야 하는 데이터 사용자는 여러 소스에 변환을
  수행하는 **메시 위(on-the-mesh)** 데이터 프로덕트이거나, 분석 리포트 같은 **메시 밖(off-the-mesh)**
  분석 애플리케이션이다** (13장, p.245).[^dehghani2022]
- 낱말의 범위 — **나는 상관(correlation) 또는 조합(composition)이라는 총칭을 둘 이상의 데이터
  프로덕트에 수행될 수 있는 연산 — 조인·합집합·필터·교집합·검색(순회) 등 — 의 자리표시자로
  쓴다** (13장, p.245).[^dehghani2022]

## 탈중앙화가 부과하는 네 요구

- **데이터 프로덕트의 탈중앙화는 데이터 메시 구현에서 데이터 조합 가능성이 어떻게 설계되는지에
  다음 요구를 부과한다** (13장, p.245):[^dehghani2022]

**① 서로 다른 접근 양식과 토폴로지에 걸쳐 데이터를 조합할 수 있어야 한다** — **12장의 소비·변환·
서빙 어포던스를 회상하면, 데이터는 파일·데이터베이스 테이블·스트림 등 서로 다른 양식으로 서빙될
수 있다. 따라서 데이터를 조합하는 능력은 데이터의 구문·기저 스토리지 타입·접근 양식에 불가지여야
한다** (13장, p.245).[^dehghani2022]

- 저자의 예 — **앞 예에 **play events**를 더하면 emerging artists 모델의 훈련은 이벤트 스트림으로
  서빙되는 데이터와 열 지향 파일에 걸쳐 아티스트에 대한 정보를 조합할 수 있어야 한다** (13장,
  p.245).[^dehghani2022]
- **그 귀결이 기존 기법의 탈락이다** — **결과적으로 단일 스키마의 테이블 사이 기본 키·외래 키
  관계를 정의하는 것처럼 **동질 데이터를 가정하는 많은 기존 조합 가능성 기법은 작동하지 않는다**
  (13장, p.245).[^dehghani2022]

**② 무엇이 연결 가능한지를 탈중앙으로 발견하고 배울 수 있어야 한다** — **서로 다른 데이터
프로덕트에 걸쳐 데이터를 조합하기 전에, 데이터 사용자는 무엇이 연결 가능한지를 발견해야 한다.
앞 예에서 emerging artists 데이터 프로덕트 개발자는 아티스트에 대한 정보가 playlists·social
media mentions·artist profiles 데이터 프로덕트에 존재하고 연결 가능하다는 지식을 가져야 한다**
(13장, p.245).[^dehghani2022]

- **전통적으로 이것은 공유되고 중앙집중된 타입 시스템이나 스키마로 달성된다. 대조적으로 데이터
  메시는 **분산 데이터 모델링 접근**을 채택해야 한다** (13장, p.245).[^dehghani2022]

**③ 연결 가능한 데이터를 매끄럽게 이을 수 있어야 한다** — **데이터 사용자가 아티스트 정보가
social media mentions·playlists·artist profiles에 있음을 발견하고 나면, 이 데이터 프로덕트들에
걸쳐 같은 아티스트의 개별 개체를 매핑하고 상관시킬 수 있어야 한다. 각 데이터 프로덕트에서 어느
필드가 아티스트를 표현하는지, 그리고 그것들이 어떻게 매핑될 수 있는지 — 예컨대 모든 데이터
프로덕트가 아티스트 식별에 일관되게 쓰는 전역 고유 **artist identifier**의 매핑 — 를 알아야 한다**
(13장, p.245).[^dehghani2022]

**④ 데이터를 시간적으로 관계 지을 수 있어야 한다** — **데이터 프로덕트는 처리 시간과 실제 시간
(또는 시간 윈도우)이라는 두 시간 차원에 걸쳐 데이터를 서빙한다. 내재적으로 시간은 두 데이터 개체를
관계 짓는 파라미터다. 예컨대 emerging artists를 발견할 때, social media mentions와 playlists에
걸쳐 데이터를 변환·상관하는 코드(또는 질의)는 아티스트의 언급이 일어난 실제 시간과 아티스트가
재생 목록에 더해진 실제 시간을 포함한다. 시간을 기본으로 편입하는 것의 아름다움은 **다른 모든
연산이 자연스럽게 시간의 함수가 된다**는 것이다** (13장, p.246).[^dehghani2022]

- [바이템포럴 데이터](../concepts/bitemporal-data.md)의 두 축이 조합의 **조인 키 일부**가 되는
  자리다 — 이것이 저자가 시간을 "늘 존재하는 파라미터"로 둔 실용적 이유다.

## 기존 접근 ① 팩트 테이블의 외래 키

- 저자가 세 접근을 먼저 훑는다 — **기존 데이터 기술 지형을 보면 데이터 조합 가능성에 대한 몇
  주목할 접근을 발견한다. 집필 시점 이 접근들은 데이터 메시에 그대로는 작동하지 않지만, 배울
  흥미로운 교훈이 있다. 이 접근들 전부에서 조합 가능성은 관계의 **명시적 정의**와 **공유 타입
  시스템**을 통해 가능해진다** (13장, p.246).[^dehghani2022]
- 서술 — **관계형 스키마, 특히 데이터 웨어하우징 시스템이 채택한 스타·스노플레이크 스키마는 서로
  다른 데이터 타입 사이의 명시적 관계를 정의한다. 예컨대 emerging artist 모델 훈련용 데이터에
  접근하기 위해 스키마는 artist profiles·social media mentions·playlists에 대한 세 차원 테이블을
  정의한다. 이 데이터 프로덕트들을 조합하고 관계 지으려면 각 아티스트에 대해 네 번째 테이블 —
  팩트 테이블 — 이 만들어져 이 각각을 가리키는 아티스트의 외래 키를 갖는다** (13장,
  p.246).[^dehghani2022]
  - 각주 — **스노플레이크 스키마는 모든 엔티티를 차원 테이블로 정규화하고 그 관계를 별도 테이블,
    곧 차원 테이블에 대한 외래 키를 담는 팩트 테이블에 정의하는 다차원 데이터베이스 스키마다.
    스타 스키마는 스노플레이크 스키마의 특수한 경우다** (13장, p.246, 각주 6).[^dehghani2022]
- **판정** — **이 데이터 조합 방법은 중앙집중 시스템에서 질의를 돌리는 데 성능이 좋고 유연하지만
  데이터 메시에 맞지 않는다. 그것은 데이터 프로덕트 사이에 **단단하고 깨지기 쉬운 결합(tight and
  fragile coupling)**을 만든다. 각 데이터 프로덕트의 스키마는 같은 스키마 안에서 다른 것들과
  단단히 연결되므로 독립적으로 바뀔 수 없다. 그것은 데이터 프로덕트에 걸쳐 동질적인 데이터
  구문(표 형식)을 가정하고, 내부 스토리지 시스템 식별자는 특정 구현에 대한 단단한 결합을 만든다**
  (13장, p.246).[^dehghani2022]
- 한 줄 결론 — **데이터 메시는 팩트를 명시적으로 정의하거나 테이블을 조인하는 것에서 멀어진다**
  (13장, p.247).[^dehghani2022]
  - [차원 모델링](../concepts/dimensional-modeling.md)·[팩트 테이블](../concepts/fact-table.md)·
    [통합 팩트 테이블](../concepts/consolidated-fact-table.md)·[표준 차원](../concepts/conformed-dimension.md)
    전체와 정면으로 갈리는 자리다. **대립은 처방이고, 조건은 조합의 주체가 단일 시스템 안인가
    자율 프로덕트들 사이인가이다** — 저자도 중앙집중 시스템 안에서는 이 방법이 "성능이 좋고
    유연하다"고 인정한다. 사실 충돌이 아니라 **적용 범위의 대립**이다.

## 기존 접근 ② 분산 타입 시스템

- 서술 — **연결 가능한 데이터를 발견하는 또 다른 접근은 타입 시스템을 쓰는 것이다. 예컨대
  GraphQL의 Apollo federation은 개별 서비스가 서브그래프 — 서비스가 해결하고 데이터를 제공할 수
  있는 데이터 타입 집합의 스키마 — 를 정의하게 한다. 각 서브그래프는 자기 스키마를 가지며 타입·
  객체·그 성질의 집합을 정의한다. 각 서브그래프 스키마는 다른 서브그래프 스키마에 정의된 다른
  타입을 참조하고 확장할 수 있다. 그러면 게이트웨이가 서로 다른 서브그래프를 조합할 책임을 진다.
  게이트웨이는 연합 타입 시스템을 써서 서브그래프들을 상관시키고 슈퍼그래프를 만든다** (13장,
  p.247).[^dehghani2022]
- 저자가 GraphQL 스키마 예를 원문 코드로 든다 — `ArtistProfile` 타입이 `Artist`를 참조하고,
  다른 스키마의 `Playlist`·`Track`이 그 공유 타입 `Artist`를 재사용하는 모양이다 (13장, p.248,
  코드 예).[^dehghani2022]
- **판정** — **분산 타입 시스템은 느슨한 결합과 재사용 가능한 타입의 명확한 소유권을 존중하므로
  데이터 메시에 적합하다. 그러나 타입(스키마)의 **독립적 변경**과 **시간 차원(타입의 버전)**을
  고려하면서 타입 재사용을 허용하도록 더 정련되어야 한다** (13장, p.248).[^dehghani2022]
  - 세 접근 중 유일하게 **적합** 판정을 받는다. [GraphQL](../concepts/graphql.md) 페이지가
    받는 계열이 여기서 데이터 조합의 후보로 승격된다.

## 기존 접근 ③ 하이퍼링크와 중앙 타입 시스템

- 서술 — **연결 가능한 관계를 정의하는 또 다른 방법은 스키마 안에 공유 데이터 타입에 대한 명시적
  HTTP 하이퍼링크를 쓰는 것이고, 그 스키마는 흔히 중앙집중·공유 스키마 레지스트리(예:
  schema.org)를 통해 가용하다. 스키마에 대한 직접 하이퍼링크는 흔히 서로 다른 집합에 걸친 개별
  데이터 인스턴스에 대한 직접 하이퍼링크를 동반한다** (13장, p.248).[^dehghani2022]
- 계열 — **예컨대 이 접근은 Linked Data와, 전역 규모의 데이터 웹인 시맨틱 웹을 중심으로 개발된
  표준화들이 채택한다. Linked Data 채택이 기업의 분석 데이터 관리에 널리 침투하지는 않았지만,
  분산 데이터 연결과 조합 가능성을 전역 규모에서, 웹 링크를 통한 관련 데이터 연결에 방점을 두고
  다루려 했다는 점에서 흥미로운 영감의 원천이다** (13장, p.248).[^dehghani2022]
- 저자가 JSON-LD 예를 든다 — `@context`가 용어를 중앙 스키마 정의로 가리키고, 각 개체가
  `@id`·`@type`을 갖는 모양이다 (13장, p.249, 코드 예).[^dehghani2022]
- 무엇이 성립하는가 — **이 모델에서 모든 개별 엔티티와 데이터 타입은 스키마 URI로 식별되는
  명시적으로 정의된 스키마를 가지며, 정의된 **온톨로지와 어휘(ontologies and vocabularies)**로
  다른 스키마에 연결할 수 있다. 온톨로지는 한 도메인의 용어들과 그 사이 관계, 그리고 다른
  도메인과의 관계에 대한 명시적이고 형식적인 명세다** (13장, p.249).[^dehghani2022] 각주는
  Ontology Development 101을 든다 (13장, p.249, 각주 7).[^dehghani2022]
- 그리고 그래프가 창발한다 — **추가로 식별 가능한 모든 엔티티는 고유 URI를 갖는다. 예컨대 artist
  profiles의 각 아티스트는 다른 연결 가능한 엔티티가 링크할 수 있는 고유 URI를 갖는다. 이
  데이터 연결은 그래프를 만들고, 거기서 기존 관계를 순회함으로써 **새 관계가 추론될 수 있다**
  (13장, p.250).[^dehghani2022]
- **판정** — **이 모델은 분산 데이터 모델링과 조합 가능성에 맞지만, 시간이 지나면서 유지하고
  바꾸기 어려울 **공유되고 중앙에서 관리되는 스키마**를 쓰지 않도록 더 정련되어야 한다** (13장,
  p.250).[^dehghani2022]
  - 세 접근에 대한 판정 축이 하나로 정리된다: **관계를 명시적으로 정의하는 것 자체는 문제가
    아니고, 그 정의가 어디에 사는가가 문제다.** 팩트 테이블은 하나의 스키마에, schema.org는
    중앙 레지스트리에, Apollo federation은 각 서브그래프에 산다.

## 데이터 메시의 설계 요소 다섯

- 설계 원칙 — **설계는 데이터 프로덕트 사이의 **느슨한 결합**과 **중앙집중 동기화 지점의 최소화**를
  우선한다. 메시 전반의 데이터 조합 가능성은 **분산 타입 시스템(스키마)**에 의존하며, 거기서 각
  데이터 프로덕트가 자기 스키마의 수명 주기를 소유하고 통제한다. 한 데이터 프로덕트는 다른 데이터
  프로덕트의 스키마와 데이터를 쓰고 참조할 수 있으며, 한 데이터 프로덕트에서 이웃으로의 매핑을 써서
  무엇이 연결 가능하고 어떻게인지를 식별한다** (13장, p.250).[^dehghani2022]
- 지위를 낮춘다 — **집필 시점 데이터 메시의 조합 가능성 접근은 **개발 중인 영역**임에 유의하라**
  (13장, p.250).[^dehghani2022]

**① 분산 타입 시스템** — **각 데이터 프로덕트가 **독립적으로** 자기가 서빙하는 데이터의 시맨틱
타입을 정의한다. 그런 시맨틱 정의, 곧 스키마는 데이터 사용자가 고유하게 주소 지정할 수 있다.
한 데이터 프로덕트의 시맨틱은 다른 데이터 프로덕트의 시맨틱에 정의된 타입을 참조하고 확장할 수
있다 — **시맨틱 연결(semantic linking)**이다. 참조 시스템이 URI라는 인터넷 주소 지정 체계를 쓰면,
그것은 단순히 여러 호스팅 환경과 조직으로 범위를 확장한 분산 타입 시스템을 가능하게 한다**
(13장, p.250).[^dehghani2022]

- 중앙 색인은 허용되되 지위가 낮다 — **메시 경험 플레인이 메시의 모든 데이터 프로덕트가 정의한
  모든 타입의 중앙집중 색인을 만들 가능성이 크다. 그 색인은 단순히 개별 데이터 프로덕트로의
  **읽기 전용 재유도 기제(read-only redirection mechanism)**다. 새 데이터 프로덕트가 만들어지거나
  기존 것이 갱신·삭제되면서 계속 갱신될 수 있다** (13장, p.250).[^dehghani2022]
  - **중앙 색인 자체는 금지되지 않는다** — 금지되는 것은 그것이 **정본이 되는 것**이다. 이
    구분이 [메타데이터 관리](../concepts/metadata-management.md)의 중앙 카탈로그와 갈리는
    정확한 지점이다.

**② 데이터 프로덕트 전역 URI** — **각 데이터 프로덕트는 이상적으로 URI 형태의 고유 주소를 가지며,
서로 다른 데이터 메시 인스턴스 안에서도 사이에서도 프로그램적으로 접근될 수 있다. 이 주소는
데이터 프로덕트의 다른 모든 공유 가능한 성질 — 시맨틱 스키마·출력 포트·데이터 개체 등 — 에
접근하는 루트다** (13장, p.250).[^dehghani2022]

**③ 데이터 개체 URI** — **여러 데이터 프로덕트에 나타나는 엔티티는 전역 고유 식별자로 식별되어야
한다. 식별자는 궁극적으로 특정 개체의 주소를 해석할 수 있는 특정 데이터 프로덕트를 가리키는 URI
형태일 수 있다. 앞서 공유한 예에서 "아티스트"라는 개념은 playlists·artist profiles 같은 여러
데이터 프로덕트에 나타나는 **다의어(polyseme)**다. 한 데이터 프로덕트가 이 URI들을 생성하는 소스가
된다. 이 예에서 **artist profiles**가 아티스트 온보딩 시점에 URI를 할당한다** (13장,
p.251).[^dehghani2022]

- 해석은 쉽지 않다 — **전역 식별자가 어떻게 할당되고, 데이터 프로덕트가 그것을 어떻게 해석해
  특정 아티스트에 대한 정보를 가리키는지는 정교한 검색과 패턴 매칭 능력을 요구한다. 예컨대
  **social media mentions** 데이터 프로덕트는 트위터 코멘트에서 언급된 이름을 찾는다. 그 언급을
  알려진 아티스트와 아티스트 URI로 매핑하는 것은 앨범·트랙·이벤트 언급 등 많은 서로 다른 맥락
  파라미터를 살피는 정교한 패턴 매칭이다. **artist** 도메인이 이 목적을 위해 ML 모델을 쓰는
  아티스트 해석 서비스를 제공할 수 있다** (13장, p.251).[^dehghani2022]
  - [마스터 데이터 관리](../concepts/master-data-management.md)의 개체 해석(entity resolution)이
    여기서 **중앙 MDM 허브가 아니라 소유 도메인의 서비스**로 재배치된다. 기법은 같고 소유가
    다르다.
  - `polyseme`(다의어)는 [도메인 소유권 원칙](../concepts/domain-ownership-principle.md)이
    DDD에서 가져온 어휘다 — 같은 낱말이 컨텍스트마다 다른 뜻을 갖는 상태를 없애지 않고
    매핑으로 잇는다.

**④ 기계보다 사람 쪽 최적화** — **데이터 프로덕트 설계는 논리 수준에서 기계뿐 아니라 사람과 조직
양쪽에 최적화된다. 예컨대 단단히 결합된 외래 키–기본 키 표 형식 관계 대신 느슨하게 결합된
하이퍼링크를 쓰는 것은 **기계의 최적화보다 조직의 최적화를 선호**한다. 예컨대 URI는 그대로 남을 수
있는 반면 데이터 프로덕트는 시간이 지나면서 바뀌고 다른 위치에 배포될 수 있다** (13장,
p.251).[^dehghani2022]

- 성능은 아래층에서 회복된다 — **플랫폼이 질의 속도 최적화를 요구하면, 연합 질의 엔진(federated
  query engines)이 서로 다른 데이터 프로덕트에 걸쳐 서빙되는 데이터에 대한 내부 색인을 만들 수
  있다. 더 단단히 결합된 이 내부 색인들은 계속 갱신되고 데이터 프로덕트 개발자에게서 감춰진다.
  질의 엔진이 내부적으로 쓴다. 유사한 시나리오는 웹 링크를 순회하며 구글이 유지하는 웹 색인이다.
  검색 사용자로서 우리는 사람이 접근 가능한 URI만 다루는 반면, 구글 검색 엔진은 내부적으로 최적화된
  해시 색인을 쓴다** (13장, p.251).[^dehghani2022]
- 한 줄 요약 — **요컨대 논리 수준에서 데이터의 표현은 사용자에게 더 친화적이고, 물리 수준에서는
  기계 작동에 더 친화적이다** (13장, p.251).[^dehghani2022]
  - **성능을 포기하는 것이 아니라 성능 최적화의 자리를 물리 층으로 내린다**는 판정이다. 같은
    분업이 [질의 수명 주기와 성능](../concepts/query-lifecycle-and-performance.md)의 논리
    계획과 물리 계획의 분리다.

**⑤ 사람이라는 요소** — **합의된 ID 체계와 표준화된 데이터 형식·모델링처럼 조합을 뒷받침하는
기술적 조치가 중요하지만, 데이터 조합은 **사람이라는 요소(human element)**도 요구한다. 데이터
프로덕트 소유자는 관련 데이터를 인지하고 데이터 사용자가 의미 있는 관계를 짓기 쉽게 만들 동기를
가져야 한다. 다른 제품 소유자와 마찬가지로 그들은 고객의 필요를 듣고 조합을 촉진할 방법을 찾아야
한다** (13장, p.251).[^dehghani2022]

- 그림 13-6이 이 요소들을 한 장에 그린다 — 메시 경험 플레인이 `/types`·`/search`를 노출하고,
  각 데이터 프로덕트가 **지역 정의 시맨틱과 링크**를 갖고, `https://artist-profiles.daff.com`
  같은 데이터 프로덕트 URI와
  `https://artist-profiles.daff.com/artists/43234?processing_time="2021/09/08"` 같은
  **(다의어) 데이터 URI**가 붙는다 (13장, p.252, 그림 13-6).[^dehghani2022]
  - 데이터 URI에 처리 시간이 질의 파라미터로 붙어 있는 것이 요점이다 — 조합의 대상은
    개체가 아니라 **특정 처리 시간의 개체**다.

## 13장이 스스로 정리한 것

- **개별 데이터 프로덕트에서 더 높은 차원의 지능과 지식을 끌어내려면 데이터 사용자가 그것들을
  상관시키고 조합해야 한다. 데이터를 꿰매는 능력은 중앙집중 모델에서는 꽤 단순하다 — 스키마 하나가
  모든 엔티티와 그 관계를 정의할 수 있다. 데이터 메시에는 이것이 몇 가지 설계 고려사항을
  요구한다. 이 고려사항들은 하나의 주된 목표에서 나온다: **단단히 결합되거나 중앙집중된 모델을
  만들지 않고 빠르게 진화할 수 있는 데이터 조합 가능성을 가능하게 하는 분산 데이터 모델 시스템을
  정의하는 것**이다** (13장, p.253).[^dehghani2022]
- 도입된 개념의 목록 — **데이터 프로덕트가 시간 가변이고·공유 가능하고·참조 가능한 시맨틱 데이터
  모델을 소유한다는 것, 시맨틱 모델 연결, 데이터 프로덕트에 걸쳐 데이터를 매핑하는 전역 식별
  시스템, 그리고 가장 중요하게는 다른 데이터 프로덕트와 의미 있는 관계를 발견하고 만들 기회를
  계속 찾을 데이터 프로덕트 소유자의 책임이다** (13장, p.253).[^dehghani2022]
- 미래에 넘기는 것 — **나는 이 장이 미래의 데이터 메시 구현자들이 기저 데이터 스토리지·형식화
  기술에 불가지인 **열린 데이터 모델링·조합 가능성 언어**를 만들도록 영감을 주기를 바란다** (13장,
  p.253).[^dehghani2022]
