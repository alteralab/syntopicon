이 페이지의 질문: **메달리온 계층 셋을 올리기 전에 플랫폼 층에서 무엇을 정해야 하고, 그 경계를
어디에 긋는가.**

[메달리온 아키텍처의 정의와 계보](../concepts/medallion-architecture-origins.md)부터
[메달리온 Gold 계층](../concepts/medallion-gold-layer.md)까지가 계층 안의 설계를 다룬다면, 이
페이지는 계층이 **놓일 자리**를 다룬다. 저자가 이 장을 제품 하나(Microsoft Fabric)로 끌고 가므로
제품에 묶인 것과 옮길 수 있는 것을 갈라 옮긴다 — 클릭 절차는 옮기지 않고, 경계의 규정과 그것을
가르는 판단만 남긴다.

## II부가 여는 것

- 부의 자리 규정 — II부에서 초점이 **이론적 기초에서 실천적 적용으로** 옮겨 가며, 이 부는 이론을
  실행 가능하게 만드는 데 관한 것이다. 메달리온 아키텍처를 짓는 처음부터 끝까지의 과정을 훑는
  실습 형태로 설계됐고, 도구와 기법에 직접 관여함으로써 견고한 데이터 아키텍처를 구현하는 실무의
  도전과 보상을 얻게 한다는 것이 부의 주장이다 (II부 도비라).[^strengholt2025]
- 부의 장 배치 — 4장이 인프라를 세우고, 5장이 Bronze를, 6장이 Silver를(데이터 검증과 정제, 그리고
  Apache Airflow를 통한 파이프라인 오케스트레이션을 다룬다), 7장이 Gold를 짓는다 (II부
  도비라).[^strengholt2025]
- **실습을 따라 하지 않아도 II부에 값어치가 있다**는 것이 저자의 주장이다 — 본문 전반에 짜여 들어간
  고려 사항·모범 사례·패턴의 탐색이 그 값어치다 (4장 도입 곁줄).[^strengholt2025]
- **왜 벤더 중립적이고 이식 가능한 해법을 주로 쓰는가**에도 저자가 답을 단다 — 처음부터 끝까지의
  메달리온 아키텍처 구현에 관한 실용적이고 공개된 예제가 부족하고, 자료 다수가 너무 이론적이거나
  너무 고수준이거나 한 측면에만 집중해 실무자가 실제 시나리오에 적용하기 어렵다는 진단이다. 저자는
  **혁신이 빠르게 움직이며 서비스와 기능을 계속 바꾸므로 성숙한 서비스와 이식 가능한 역량에
  초점을 둔다**고 적고, 그 예로 Apache Airflow·(Azure) Data Factory·Spark·PySpark·메타데이터 주도
  접근을 든다 (4장 도입).[^strengholt2025]
  - 자기 검증도 붙인다 — 이 책의 코드 조각 전부를 다른 Spark·Delta Lake 기반 서비스에서
    시험했고 똑같이 동작한다는 진술이다 (4장 도입).[^strengholt2025]
  - 이음줄은 메달리온 아키텍처 자체라는 것이 저자의 정리다. 그것이 공통의 기초로 작동하므로
    원칙·모범 사례·코드 조각이 Spark와 Delta Lake를 쓰는 다른 벤더에도 적용된다 (4장 도입
    곁줄).[^strengholt2025]

## Oceanic Airlines라는 가상 회사

- **이 책 II부와 뒤 장들의 사례는 가상의 항공사 Oceanic Airlines 하나**다. 넓은 운항망으로 알려진
  이 회사가 최첨단 데이터 레이크하우스 아키텍처를 지어 데이터 관리 시스템을 개편하는 임무에
  나섰다는 설정이다 (4장 §"Our Case Study: Oceanic Airlines").[^strengholt2025]
- **착수 방식이 사례의 전제다** — 그 일은 IT·운영·고객 서비스·재무를 포함한 여러 부서의 이해관계자가
  참여하는 일련의 업무 워크숍으로 시작했고, 그 워크숍이 새 아키텍처에 대한 구체적인 데이터 관련
  필요와 기대를 식별하는 데 도움이 되었다. 여러 선택지를 신중히 저울질한 뒤 회사가 Microsoft
  Fabric을 제안된 설계에 구현하기로 정했다 (4장 §"Our Case Study: Oceanic
  Airlines").[^strengholt2025]
- 회사의 조직 단위도 뒤 절에서 예로 쓰인다 — Airport Management·Baggage Handling Management·
  Sales·Finance·Marketing·Operations 같은 여러 업무 단위에 걸친 팀이 많을 법한 회사이고, 실습에서
  만드는 도메인은 그중 Sales 하나다 (4장 §"Setting Up the Foundation" ▸ "Domain
  Considerations").[^strengholt2025]
- 제안된 아키텍처의 전체 모양은 그림 4-1이 그리고, **그 배치는 본문이 아니라 그림에만 있다**
  (4장 §"Our Case Study: Oceanic Airlines", 그림 4-1):[^strengholt2025]

> Operational systems · Blob landing zone → Ingest data with Data Factory →
> Bronze (Lakehouse) · Silver (Lakehouse) · Gold (Lakehouse) → Serve →
> Reporting · Data science. 위를 가로지르는 띠가 Governance with Microsoft Purview,
> 아래를 가로지르는 띠가 Orchestrate using Airflow. 바깥에서 들어오는 상자가 SQL Metastore이고,
> 계층 셋 위에 Synapse data engineering (Spark)이 놓여 각 계층과 양방향 화살표로 이어진다.

  - 곧 그림이 배치하는 것은 **계층 셋이 아니라 계층 셋을 감싸는 다섯 가지**다 — 랜딩, 반입 도구,
    처리 엔진, 메타스토어, 그리고 계층 전체를 세로로 가로지르는 거버넌스와 오케스트레이션이다.
    이 다섯이 이 페이지가 다루는 플랫폼 층이다.

## 플랫폼 층의 경계 넷

저자가 제품 설명에 앞서 규정하는 개념 넷이다. 이름은 제품의 것이되 **규정 자체는 다른 플랫폼으로
옮길 수 있다**고 저자가 명시한다 — Azure Databricks와 Synapse Analytics도 비슷한 개념을 쓰므로
여기서 얻는 지식이 다른 데이터 플랫폼 서비스로 이전된다는 것이다 (4장 §"Setting Up the
Foundation" ▸ "Creating Lakehouses").[^strengholt2025]

- **도메인(domain)** — 관련 산출물과 데이터 전부를 묶는 단위이고, 부서나 업무 프로젝트처럼 구체적인
  조직 단위에 맞추는 것이 통상이다. 판매·재무·마케팅에 별도 도메인을 두고 각각 격리를 유지해
  데이터 무결성과 보안을 확보하는 식이다. 저자는 이 묶기를 **중앙집중 데이터 관리에서 탈중앙
  데이터 관리로의 이동**을 돕는 장치로 규정한다 (4장 §"Introducing Microsoft Fabric" ▸
  "Domains").[^strengholt2025]
  - **도메인은 가장 높은 추상 계층이고 위임 모델 아래에서 작동한다.** 이 모델이 각 업무 단위가
    자기 필요에 맞춘 규칙과 제약을 스스로 정하게 한다 (같은 소절).[^strengholt2025]
  - **경계의 성격이 이 절의 규정**이다 — 도메인은 **주로 관리·행정 관심사를 가르기 위한 것이지
    누가 데이터나 산출물에 접근하는지를 정하지 않는다.** 보안과 접근 관리는 다른 계층이 다룬다
    (4장 §"Setting Up the Foundation" ▸ "Domain Considerations").[^strengholt2025]
- **워크스페이스(workspace)** — 데이터 실무자가 레이크하우스·웨어하우스·노트북·리포트 같은 여러
  항목을 만들고 공유하도록 설계된 협업 환경이다. **각 워크스페이스는 도메인 하나에 연결된다**
  (4장 §"Introducing Microsoft Fabric" ▸ "Workspaces and Capacities").[^strengholt2025]
- **용량(capacity)** — 인프라 쪽에서 각 워크스페이스가 연결되는 것으로, **컴퓨트의 보편적 양동이
  또는 풀**이다. 용량은 동시에 라이선스로도 작동해 그 자원 묶음을 여러 활동에 배분한다. 곧 일정한
  양의 컴퓨트 파워를 사들이는 것이다 (같은 소절).[^strengholt2025]
  - 관계의 방향이 대칭이 아니다 — **하나의 용량을 여러 워크스페이스에 배정할 수 있다** (같은
    소절).[^strengholt2025]
  - 포함 관계의 실물은 그림 4-3이고, **본문이 말하지 않는 배치가 그림에 있다** (같은 소절, 그림
    4-3):[^strengholt2025]

> Azure tenant 아래에 Fabric capacity 둘이 놓이고, 왼쪽 용량이 워크스페이스 하나를,
> 오른쪽 용량이 워크스페이스 둘을 받는다. **Fabric domain 상자는 용량이 아니라 워크스페이스
> 셋만을 감싼다.**

  - 곧 그림이 못 박는 것은 **도메인이 워크스페이스를 묶고 용량은 그 묶음과 직교한다**는 것이다.
    한 도메인 안의 워크스페이스들이 서로 다른 용량 위에 놓일 수 있고, 한 용량이 도메인 경계를
    가로질러 여러 워크스페이스를 받칠 수 있다. 관리 경계와 과금·컴퓨트 경계가 따로 논다는 뜻이다.
- **공유 저장 계층** — 테넌트 수준에서 켜지면 모든 워크스페이스에 자동으로 쓸 수 있게 되어 여러
  워크로드가 같은 데이터에 쉽게 접근하게 한다. **데이터 엔지니어가 만든 테이블을 리포트 개발자가
  즉시 쓸 수 있다**는 것이 저자가 드는 효과다 (4장 §"Introducing Microsoft Fabric" ▸
  "OneLake").[^strengholt2025]
  - 이 계층이 되사는 것도 규정한다 — 저장에 앞서 **저장 계정·컨테이너·폴더 구조를 세우는 과정이
    사라진다.** 레이크하우스를 만들고 곧장 데이터를 다루기 시작하면 플랫폼이 뒤에서 필요한 자원과
    SQL 엔드포인트를 준비하고 인프라를 관리한다 (4장 §"Introducing Microsoft Fabric" ▸ "Data
    Engineering with Spark").[^strengholt2025]

## 2025년 저술 시점의 Microsoft Fabric

제품에 묶인 서술을 이 절 하나로 몬다. 아래는 **2025년 저술 시점의 기능**이고 가장 빨리 낡는다.

- 플랫폼의 성격 — SaaS 모델에 기반한 데이터·분석 플랫폼으로, 엔지니어·데이터 과학자·업무 분석가를
  위한 협업 환경을 제공하고 Apache Spark와 Delta Lake 같은 알려진 기술을 지원한다 (4장
  §"Introducing Microsoft Fabric").[^strengholt2025]
- 용량의 규격과 과금 — Fabric SKU라 불리는 여러 크기와 구성(F2·F16·F64 등)으로 오고, 구독형과
  종량형(용량을 만들어 워크로드를 돌린 뒤 멈추는 방식) 같은 서로 다른 구독 모델을 따른다. 이
  용량들은 사용자의 Azure 테넌트 안에 놓이되 Microsoft가 완전히 관리하므로 **아래의 가상 머신은
  사용자에게 보이지 않는다** (4장 §"Introducing Microsoft Fabric" ▸ "Workspaces and
  Capacities").[^strengholt2025] 실습이 고르는 것은 F4이고, 저자는 그것을 **넓은 변환을 요구하지
  않고 소수 사용자를 상대하는 단순한 배치 ETL 잡에 이상적**이라 평한다 (4장 §"Setting Up the
  Foundation" ▸ "Capacity Considerations").[^strengholt2025]
- 저장 계층 — Azure Data Lake Storage Gen2를 저장에 쓰고 **기본값으로 Delta 테이블 형식**을 쓴다
  (4장 §"Introducing Microsoft Fabric" ▸ "OneLake").[^strengholt2025]
- 외부 데이터를 끌어오는 두 길과 그 분업 (같은 소절):[^strengholt2025]
  - **바로가기(shortcut)** — 경량 데이터 가상화 계층이 다른 저장 위치로의 바로가기를 만들게 한다.
    그 위치는 같은 저장 계층 안일 수도 있고 Azure나 Amazon Web Services 같은 바깥일 수도 있다.
  - **미러링(mirroring)** — 데이터베이스 스냅샷을 실시간으로 복제한다. 복제본이 거의 즉시
    동기화되고 Delta 형식으로 저장되어 곧바로 쓸 수 있다. 저자는 **이 접근이 변경 데이터 캡처
    기술과 비슷하다**고 적는다.
  - **가르는 기준은 형식이다** — 바로가기는 Delta Lake·Iceberg 같은 형식의 데이터 연결을 돕고,
    미러링은 Azure SQL 같은 독점 형식에 최적이다.
- 워크로드 유형의 분업 (4장 §"Introducing Microsoft Fabric" ▸ "Data Engineering with Spark",
  "Data Warehousing with T-SQL", "Other Fabric Workload Types"):[^strengholt2025]
  - **레이크하우스 엔티티와 레이크하우스 아키텍처는 같은 것이 아니다**라고 저자가 곁줄에서 못
    박는다. 레이크하우스는 데이터 레이크와 데이터 웨어하우스의 요소를 결합한 데이터 아키텍처이고,
    이 제품의 레이크하우스 엔티티는 저장·SQL 엔드포인트·그 밖의 설정 항목을 포함하는 **구체적
    구현**이다. 곧 엔티티는 아키텍처를 짓는 데 쓰는 벽돌이다.
  - **레이크하우스와 웨어하우스를 가르는 핵심 차이는 처리 엔진**이다. 웨어하우스는 T-SQL을 통해
    다중 테이블 트랜잭션을 지원하는 분산 처리 엔진으로 동작하고, T-SQL은 Apache Spark에서 쓸 수
    없다. 선택 기준도 그래서 갈린다 — 처리 요구가 복잡한 트랜잭션을 포함하거나 엔지니어가 T-SQL에
    능숙하면 웨어하우스가, 팀이 Spark에 더 익숙하거나 **상호운용성과 개방 표준이 결정적이면**
    레이크하우스가 낫다.
  - 워크로드 유형이 여럿이어도 **모든 처리 엔진이 같은 저장 아키텍처와 통합되고 그 기본 형식이
    Delta 테이블**이라는 것이 통합의 근거다. 이 통합 덕에 데이터를 복제하지 않고 워크로드를
    가로질러 쓸 수 있고, 저자는 이 방식을 **제로 ETL 접근**이라 부르기도 한다고 적는다.
- **"플랫폼 인스턴스"라는 말의 뜻도 제품마다 다르다.** 각주 하나가 그것을 Synapse Analytics나
  Azure Databricks 같은 플랫폼을 한 지역 안에 구체적으로 설치한 것으로 규정하고 지역화된 설정을
  허용한다고 적은 뒤, **이 제품은 다르다**고 갈라 놓는다 — 통합 SaaS 플랫폼으로 작동해 사용자가
  같은 플랫폼 아키텍처 안의 워크스페이스 묶음으로 운영을 관리하며 **명확히 구분되는 인스턴스가
  없다** (4장 각주 3).[^strengholt2025]

## 용량을 가르는 기준

- **하나로 시작하되 요구가 자라면 여러 용량을 배치하라**는 것이 저자의 권고다. 서로 다른 유형의
  워크로드를 더 효율적으로 다루기 위해서다 (4장 §"Setting Up the Foundation" ▸ "Capacity
  Considerations").[^strengholt2025]
- 가르는 축은 **워크로드의 탄력성**이다 — 일상 작업에는 표준 예약 용량을, 임시적이거나 가벼운
  잡에는 더 작고 비용 효율적인 종량 용량을 두는 식이다. 워크로드를 여러 클러스터에 분산하는 이
  전략이 비용과 성능을 함께 최적화하고 아키텍처가 변하는 요구에 더 잘 적응하게 한다 (같은
  소절).[^strengholt2025]

## 도메인을 가르는 기준

- 도메인은 조직의 특정 영역 안에 있는 모든 관련 데이터와 산출물의 **논리적 묶음**으로 작동하고,
  이 기능이 **큰 조직에 특히 유용**하다. 데이터를 업무 역량·기능 영역·부서로 묶게 해 주어 사용자가
  자기 규정과 제약과 필요에 따라 데이터를 관리하도록 돕기 때문이다 (4장 §"Setting Up the
  Foundation" ▸ "Domain Considerations").[^strengholt2025]
- 위임의 실물 — 사용자와 워크스페이스를 관리하는 책임과 권한을 **지정된 도메인 관리자나
  기여자에게 위임**할 수 있고, 도메인은 하위 도메인도 가질 수 있다. 저자의 예는 Sales 도메인
  아래의 Sales Consumers와 Sales Businesses다 (같은 소절).[^strengholt2025]
- **도메인의 개수에 정답이 없다**는 것이 저자의 답이다 — 다양한 업무 도메인을 많이 가진 회사도
  있고, 더 작거나 대규모 데이터 관리에 덜 성숙한 회사는 **도메인을 적게 두되 더 큰 팀이 더 많은
  데이터셋을 다루는 쪽**을 고를 수 있다. 상세는 저자가 11장으로 미룬다 (같은
  소절).[^strengholt2025]

## 워크스페이스를 가르는 기준

워크스페이스는 반입·엔지니어링·기계 학습·데이터 발견·리포팅에 이르는 활동이 벌어지는 협업 허브이고,
저자는 이 산출물 관리 방식이 이 제품 고유의 것이 아니라고 적는다 — Synapse Analytics와 Azure
Databricks도 비슷하게 쓴다 (4장 §"Setting Up the Foundation" ▸ "Workspace
Considerations").[^strengholt2025] 개수를 정하는 이유가 다섯이다.

- **지리적 분리**. 워크스페이스는 사용자를 특정 지역·용량·버전 관리 시스템에 잇는다. 특정 용량에
  이으면 그 용량이 이어진 지역 안에 모든 저장이 놓이므로, **엄격한 지리적 데이터 분리 법규를
  지켜야 하는 글로벌 회사**에 특히 이롭다. 유럽과 미국 사이에 데이터를 나눠야 하는 업무 단위라면
  여러 워크스페이스로 요구를 채운다. 그 결과 **업무 도메인 하나가 여러 지역화된 플랫폼 인스턴스를
  거느리며 워크스페이스를 다수 운영**할 수 있다 (같은 소절).[^strengholt2025]
- **컴퓨트 정렬**. 용량 하나가 여러 팀의 개발 워크스페이스 전부를 상대할 수도 있고, 수요가 높은
  운영 환경이 전용 용량을 가질 수도 있다. 워크스페이스를 더 쓰는 것이 도메인 안에서 컴퓨트 집약적
  워크로드를 분리하고 최적화하는 효과적인 방법이 된다 (같은 소절).[^strengholt2025]
- **CI/CD**. 워크스페이스는 버전 관리 시스템과 통합해 배포 과정을 관리하고 개발·테스트·운영의
  관심사를 가른다. **각 단계가 자기 전용 워크스페이스를 갖기를 권고**하고, 이것이 CI/CD 과정의
  관리에 필수적이다 (같은 소절).[^strengholt2025]
  - **메달리온 아키텍처에 대해서는 반대 방향의 권고가 붙는다** — 레이크하우스를 포함한 모든 코드와
    산출물을 **단일 워크스페이스 안에** 저장하기를 권고한다. 계층별로 워크스페이스를 나눌 수도
    있으나 그러면 여러 워크스페이스와 그 산출물을 관리해야 해 **CI/CD 과정이 복잡해질 수 있다**
    (같은 소절).[^strengholt2025] 곧 **배포 단계로는 가르고 계층으로는 가르지 말라**는 것이 이
    절의 판정이다.
- **보안 경계**. 워크스페이스는 권한 관리의 보안 경계로 작동하고 admin·member·contributor·viewer
  같은 역할을 각기 다른 권리와 제약으로 수용한다. 운영 환경에서 다른 워크스페이스로의 **읽기 전용
  바로가기만 가진 새 워크스페이스**를 세우면 일부 사용자에게 탐색 목적의 제한된 접근을 줄 수 있다.
  워크스페이스에 딸린 관리형 아이덴티티가 다른 서비스로의 안전한 접근을 맡는다 (같은
  소절).[^strengholt2025]
- **팀 경계**. 팀마다 워크스페이스를 두면 격리된 환경으로 집중과 보안이 좋아진다. 저자가 자주 보는
  구도는 **복잡성 때문에 한 팀이 모든 데이터 온보딩과 반입을 맡고**, 반입·정제·큐레이션이 끝난
  데이터를 다른 팀들이 자기 워크스페이스에서 쓰는 것이다 (같은 소절).[^strengholt2025]
  - 그 구도의 실물이 그림 4-9이고, **본문에 없는 배치가 그림에 있다** (같은 소절, 그림
    4-9):[^strengholt2025]

> Source systems → 중앙 팀이 소유한 Workspace 상자 안의 Bronze → Silver → 그 밖으로 뻗는
> Gold 상자 여럿. Gold 상자들은 각각 다른 팀 아이콘이 붙은 별도의 점선 상자 안에 있고,
> **Gold 하나가 다시 Gold 둘을 낳는 가지도 있다.**

  - 곧 그림이 더하는 것은 **중앙 팀의 경계가 Silver에서 끝난다**는 것과 **Gold가 팀마다 갈라지며
    Gold에서 Gold로 이어지는 층도 허용된다**는 것이다.
- 사례의 진행 — Oceanic Airlines는 처음에 모든 데이터 처리 잡을 **단일 워크스페이스** 안에서
  관리하고 엔지니어들이 개발과 협업에 쓴다. 조직이 자라고 프로젝트가 늘면 테스트와 운영을 담기
  위해 워크스페이스를 여럿 만드는 것이 이로울 수 있다 (같은 소절).[^strengholt2025]

## 계층마다 저장 엔티티를 따로 두는 이유

- **권고는 계층마다 별도 엔티티**다. 계층 전부를 스키마로만 가른 단일 엔티티보다 낫다는 것이고,
  이유는 **엔티티마다 전용 SQL 엔드포인트가 딸려 와 누가 어느 엔드포인트에 접근하는지를 더 세밀히
  통제**할 수 있기 때문이다. 표준 메달리온이라면 최소 셋을 만든다 (4장 §"Setting Up the
  Foundation" ▸ "Lakehouse Entities Considerations").[^strengholt2025]
- **그 권고가 배포 환경으로 곱해진다** — 개발·테스트·운영(DTP) 사이의 배포 작업 흐름이 흔히
  워크스페이스 복제를 수반하고 환경마다 최소 셋을 가지므로, **워크스페이스 셋에 걸쳐 총 아홉**이
  된다. 저자는 많아 보여도 감당할 만하다고 평하는데, **환경별 계층마다 다른 용량을 배정할 수 있기
  때문**이다 (같은 소절).[^strengholt2025]
- 세밀한 접근 통제의 쓸모 — 일부 사용자에게 SQL 엔드포인트를 통한 읽기 전용 접근을 계층 단위로
  줄 수 있다. **Gold의 고품질 데이터만 열고 싶을 때**, 또는 **운영 Bronze에서 문제를 해결해야
  하지만 다른 계층은 볼 필요가 없는 개발자**에게 특히 쓸모 있다 (같은 소절).[^strengholt2025]
- 계층 하나를 다시 여럿으로 쪼개는 것도 허용된다 — 큰 도메인 팀이 여러 애플리케이션을 관리하되
  구성원 전부가 모든 원시 데이터에 접근해서는 안 되는 경우, 또는 여러 작은 팀이 반입하면서 **같은
  위치에 쓰는 것을 막고 싶은 경우**에 엔티티를 더 두어 팀마다 자기 데이터를 독립적으로 관리하게
  한다. Bronze나 Gold가 접두나 식별자로 구분되는 여러 엔티티로 이루어질 수 있다 (같은
  소절).[^strengholt2025]
- **표준 정렬이 성공의 조건**이라는 것이 이 절의 맺음이다 — 새 팀을 빠르고 효율적으로 온보딩하게
  하기 때문이다. 모든 워크스페이스가 엔티티의 특정 배치 설계를 따르게 하고, 연결된 워크스페이스나
  프로젝트를 반영하는 **서술적 명명 규약**을 채택하며, 워크스페이스와 엔티티 같은 필수 항목이
  **함께 묶여 배포되도록 배포 과정을 스크립트로 만드는 것**이 도움이 되는 전략이다 (같은
  소절).[^strengholt2025]

## 저장 계정을 가르는 기준

계정 수준의 저장을 직접 다루는 다른 Spark 기반 서비스가 있으므로 저자가 절을 따로 둔다. 배치가
세 갈래다 (4장 §"Setting Up the Foundation" ▸ "Storage Account Considerations").[^strengholt2025]

- **단일 계정 + 컨테이너 셋**이 기본형이다. 저장 계정 하나를 Bronze·Silver·Gold 컨테이너 셋으로
  나누어 모든 데이터를 한 자리에 두되 컨테이너로 조직하는 배치다. **단순한 데이터 관리를 하는 작은
  프로젝트에는 흔히 이것으로 충분**하다 — 관리와 접근이 쉽기 때문이다.[^strengholt2025]
- **팀별 계정**이 다음이다. 더 큰 프로젝트에서 조직적·보안적 목적으로 데이터를 가르려면 여러 저장
  계정이 필요할 수 있고, 그러면 데이터 엔지니어링 팀마다 계층별 컨테이너를 여럿 가진 자기 저장
  계정을 갖는다. 접근 통제와 데이터 거버넌스를 더 효과적으로 관리하게 돕는다.[^strengholt2025]
- **혼합 모델**이 셋째다. 지역 정렬과 중앙 정렬의 균형을 잡는 배치로, **도메인 내부 전용 계정과
  중앙 공유 계정을 함께 둔다.** 각 도메인은 내부 처리용 전용 계정을 쓰고(Bronze·Silver·Gold 활동을
  포함할 수 있다) 이 계정은 순수 내부용이라 다른 도메인에 노출되지 않는다. 그 위에 중앙 공유 계정이
  있어 **데이터 산물의 최종판을 다른 도메인에 배포**하는 데 쓰인다. 저자는 그 최종판이 보통
  **Silver(원천 정렬 데이터 산물)나 Gold(집계 또는 소비자 정렬 데이터 산물)**에 놓인다고 적고, 이
  공유 계정은 흔히 중앙 부서가 관리한다. **도메인에 유연성을 주면서 모든 데이터 교환을 조망하게
  하는 설계**라는 것이 저자의 평이다. 실물 예는 11장으로 미룬다.[^strengholt2025]
- 기본 배치를 벗어나는 이유를 저자가 열둘로 나열한다 (같은 소절):[^strengholt2025] 부서가 자기
  데이터의 소유권을 유지하는 **조직 구조**, 지역 데이터 레지던시 요건을 지키는 **다지역 배치**,
  구독·서비스 제약을 넘는 **클라우드 한도 회피**, 레이크마다 정책을 달리하는 **정책 분리**, 레이크마다
  구독을 두어 과금을 단순화하는 **비용 추적**, 더 엄격한 통제를 적용하는 **민감 데이터 분리**, 개발·
  테스트·운영에 다른 레이크를 쓰는 **환경 분리**, 레이크를 사용자·애플리케이션에 가까이 두는 **지연
  개선**, 상승된 권한을 필요한 자산으로 제한하는 **권한 제한**, 다양한 규제를 맞추는 **거버넌스와
  컴플라이언스**, 전용 레이크를 요구하는 **부서별 필요**, 지역에 걸쳐 분산해 가용성을 확보하는
  **재해 복구**, 데이터 유형마다 비용과 성능을 최적화하는 **서비스 수준 분리**다.

## 이 도메인은 데이터 메시의 도메인과 같은 낱말인가

**같은 낱말의 다른 층이라는 것이 이 런의 판정이고, `contradicts`는 걸지 않았다.**

- [도메인 소유권 원칙](../concepts/domain-ownership-principle.md)과
  [데이터 메시](../concepts/data-mesh.md)의 도메인은 **조직의 책임 단위**다. 누가 데이터를 소유하고
  누가 그 품질에 책임지는가를 정하고, 그 결과로 데이터 산물의 경계가 정해진다.
- 이 소스의 도메인은 **플랫폼의 관리 경계**다. 저자 자신이 "주로 관리·행정 관심사를 가르기 위한
  것이지 누가 데이터에 접근하는지를 정하지 않는다"고 못 박고, 접근은 워크스페이스와 저장 엔티티가
  맡는다 (4장 §"Setting Up the Foundation" ▸ "Domain Considerations").[^strengholt2025]
- 곧 두 도메인은 **겹치되 같지 않다.** 저자가 도메인을 "중앙집중에서 탈중앙 데이터 관리로의 이동"을
  돕는 장치라 규정하는 자리에서 둘이 같은 방향을 가리키지만, 데이터 메시 쪽의 도메인은 **조직이
  먼저 있고 플랫폼이 뒤따르는** 배치이고 이 소스의 도메인은 **플랫폼이 제공하는 상자에 조직을 맞춰
  넣는** 배치다. 최대 하나만 참일 수 있는 사실 충돌이 아니다.
- 이 소스가 데이터 메시 쪽으로 실제로 다가서는 자리는 도메인이 아니라 **저장 계정의 혼합 모델**이다
  — 도메인 전용 저장과 중앙 공유 저장을 나누고 공유되는 것을 "원천 정렬 데이터 산물"과 "소비자 정렬
  데이터 산물"로 부르는 대목이 [데이터 산물](../concepts/data-products.md)의 어휘를 그대로 쓴다.
