하나의 질문: **저장 아키텍처의 트레이드오프는 결국 어떤 물리 수치에서 나오는가.**

## 수치의 측정 시점

> **측정 시점**: 아래 성능·가격 수치는 모두 **2022년 초판 집필 시점의 상용 제품 기준**이다.
> 책이 여러 곳에서 "at the time of this writing"이라고 스스로 밝힌다(예: RAM 가격, EBS 볼륨
> 한계). 매체 가격과 대역폭은 해마다 움직이므로 **비율과 자릿수는 오래 가고 절대값은 그렇지
> 않다** — 아래 [기존 수치와의 대조](#기존-수치와의-대조) 절이 그 비율을 다른 소스와 맞춰 본다.
> 이것은 릴리스 번호 경계가 아니라 측정 시점이므로 `버전 조건:` 형식을 쓰지 않는다.

## 세 층위 — 원료·저장 시스템·저장 추상

- 저장이 초석이다 — **저장은 데이터 엔지니어링 수명 주기의 초석이며 그 주요 단계들 — 반입·변환·
  서빙 — 을 떠받친다. 데이터는 수명 주기를 지나며 여러 번 저장된다. 오래된 말을 바꿔 말하면
  아래까지 죽 저장이다(it's storage all the way down). 데이터가 몇 초 뒤에 필요하든, 몇 분,
  며칠, 몇 년 뒤에 필요하든, 시스템이 추가 처리와 전송을 위해 소비할 준비가 될 때까지 그것은
  저장에 영속해야 한다. 데이터의 유스케이스와 미래에 그것을 회수할 방식을 아는 것이 데이터
  아키텍처에 알맞은 저장 해법을 고르는 첫걸음이다** (6장, p.189).[^reis2022]
- 5장과 무엇이 다른가 — **5장에서도 저장을 논했지만 초점과 통제 영역이 다르다. 원천 시스템은
  일반적으로 데이터 엔지니어가 유지하거나 통제하지 않는다. 데이터 엔지니어가 직접 다루는 저장,
  이 장에서 초점을 맞출 저장은 원천 시스템에서 데이터를 반입하는 것부터 분석·데이터 과학 등으로
  가치를 인도하기 위해 데이터를 서빙하는 것까지의 수명 주기 단계를 아우른다** (6장,
  p.190).[^reis2022]
- 층이 셋이다 (6장, p.190, 그림 6-2):[^reis2022]
  - **원료(raw ingredients)** — **HDD·SSD·RAM·네트워킹·직렬화·압축·CPU.**
  - **저장 시스템(storage systems)** — **HDFS·오브젝트 저장·RDBMS·캐시/메모리 기반 저장·
    스트리밍 저장.**
  - **저장 추상(storage abstractions)** — **데이터 레이크·데이터 레이크하우스·데이터 플랫폼·
    클라우드 데이터 웨어하우스.**
- 왜 이렇게 층을 나누는가 — **다음으로 저장 시스템을 볼 것이다. 실무에서 우리는 시스템 메모리나
  하드 디스크에 직접 접근하지 않는다. 이 물리 저장 구성 요소는 다양한 접근 패러다임으로 데이터를
  반입하고 회수할 수 있는 서버와 클러스터 안에 존재한다** (6장, p.191).[^reis2022]
  - **마지막으로 저장 추상을 볼 것이다. 저장 시스템은 클라우드 데이터 웨어하우스, 데이터 레이크
    등으로 조립된다. 데이터 파이프라인을 지을 때 엔지니어는 데이터가 반입·변환·서빙 단계를 지나며
    저장될 적절한 추상을 고른다** (6장, p.191).[^reis2022]

## 왜 원료를 알아야 하는가

- 문제의 진단 — **저장은 너무 흔해서 당연하게 여기기 쉽다. 매일 저장을 쓰면서도 그것이 무대 뒤에서
  어떻게 작동하는지, 다양한 저장 매체에 내재한 트레이드오프가 무엇인지는 거의 모르는 소프트웨어·
  데이터 엔지니어의 수에 우리는 자주 놀란다. 그 결과 저장이 꽤… 흥미로운 방식으로 쓰이는 것을
  본다** (6장, p.191).[^reis2022]
- 관리형 서비스가 있어도 남는 것 — **현재의 관리형 서비스가 데이터 엔지니어를 서버 관리의
  복잡성에서 잠재적으로 해방시켜 주지만, 데이터 엔지니어는 여전히 하부 구성 요소의 본질적 특성·
  성능 고려사항·내구성·비용을 알아야 한다** (6장, p.191).[^reis2022]
- 그리고 데이터는 실제로 이 셋을 다 통과한다 — **대부분의 데이터 아키텍처에서 데이터는 파이프라인의
  다양한 처리 단계를 거치며 마그네틱 저장·SSD·메모리를 자주 통과한다. 데이터 저장과 질의 시스템은
  일반적으로 분산 시스템·다수의 서비스·여러 하드웨어 저장 계층을 포함하는 복잡한 레시피를 따른다.
  이 시스템은 올바로 기능하기 위해 올바른 원료를 요구한다** (6장, p.191).[^reis2022]

## 마그네틱 디스크 드라이브

- 기제 — **마그네틱 디스크(magnetic disks)는 강자성 필름을 입힌 회전 플래터를 활용한다. 이
  필름은 쓰기 연산 동안 읽기/쓰기 헤드에 의해 자화되어 이진 데이터를 물리적으로 인코딩한다.
  읽기/쓰기 헤드는 읽기 연산 동안 자기장을 감지해 비트스트림을 출력한다** (6장,
  p.191).[^reis2022]
- 왜 아직 쓰는가 — **마그네틱 디스크 드라이브는 오래전부터 있었다. 저장된 데이터 기가바이트당
  SSD보다 유의하게 싸기 때문에 여전히 대량 데이터 저장 시스템의 등뼈를 이룬다** (6장,
  p.191).[^reis2022]
  - 가격 — **현재 상용 마그네틱 디스크 드라이브는 용량 기가바이트당 대략 3센트다** (6장,
    p.191).[^reis2022]
- 용량은 계속 늘었다 — **IBM이 1950년대에 마그네틱 디스크 드라이브 기술을 개발했다. 그 이후
  마그네틱 디스크 용량은 꾸준히 늘었다. 첫 상용 마그네틱 디스크 드라이브인 IBM 350은 용량이
  3.75메가바이트였다. 이 글을 쓰는 시점에 20TB를 저장하는 마그네틱 드라이브가 상용으로 이용
  가능하다. 사실 마그네틱 디스크는 열 보조 자기 기록(HAMR)·기와식 자기 기록(SMR)·헬륨 충전
  디스크 인클로저 같은 방법으로 계속 빠른 혁신을 보며 점점 더 큰 저장 밀도를 실현하고 있다**
  (6장, p.192).[^reis2022]
- **그런데도 물리가 발목을 잡는다 — 드라이브 용량의 지속적 개선에도 불구하고 HDD 성능의 다른
  측면은 물리에 의해 방해받는다** (6장, p.192).[^reis2022] 저자들이 드는 한계는 넷이다.
- **첫째, 디스크 전송 속도(disk transfer speed) — 데이터를 읽고 쓸 수 있는 속도는 디스크 용량에
  비례해 확장되지 않는다. 디스크 용량은 면 밀도(areal density, 제곱인치당 저장되는 기가비트)로
  확장되는 반면 전송 속도는 선 밀도(linear density, 인치당 비트)로 확장된다. 이는 디스크 용량이
  4배로 늘면 전송 속도는 2배만 는다는 뜻이다. 결과적으로 현재 데이터센터 드라이브는 최대
  200–300MB/s의 데이터 전송 속도를 지원한다. 이것을 다르게 표현하면, 300MB/s 전송 속도를 가정할
  때 30TB 마그네틱 드라이브의 전체 내용을 읽는 데 20시간 넘게 걸린다** (6장,
  p.192).[^reis2022]
- **둘째, 탐색 시간(seek time)이다. 데이터에 접근하려면 드라이브가 읽기/쓰기 헤드를 디스크의
  적절한 트랙으로 물리적으로 재배치해야 한다** (6장, p.192).[^reis2022]
- **셋째, 디스크에서 특정 데이터 조각을 찾으려면 디스크 컨트롤러가 그 데이터가 읽기/쓰기 헤드
  아래로 회전해 오기를 기다려야 한다. 이것이 회전 지연(rotational latency)으로 이어진다.
  분당 7,200회전(RPM)으로 도는 전형적 상용 드라이브에서 탐색 시간과 회전 지연은 전체 평균
  지연 4밀리초 초과로 이어진다(선택한 데이터 조각에 접근하는 시간)** (6장,
  pp.192–193).[^reis2022]
- **넷째 한계는 트랜잭션 데이터베이스에 결정적인 초당 입출력 연산(IOPS)이다. 마그네틱 드라이브는
  50에서 500 IOPS 범위다** (6장, p.193).[^reis2022]
- 트릭이 있지만 판을 뒤집지는 못한다 — **다양한 트릭이 지연과 전송 속도를 개선할 수 있다. 더 높은
  회전 속도를 쓰면 전송률을 올리고 회전 지연을 낮출 수 있다. 디스크 플래터의 반지름을 제한하거나
  디스크의 좁은 대역에만 데이터를 쓰면 탐색 시간이 줄어든다. 그러나 이 기법들 중 어느 것도 임의
  접근 조회에서 마그네틱 드라이브를 SSD와 원격으로라도 경쟁하게 만들지 못한다** (6장,
  p.193).[^reis2022]
- 그럼에도 남는 강점이 병렬성이다 — **마그네틱 드라이브는 병렬성을 통해 대단히 높은 전송률을
  유지할 수 있다. 이것이 클라우드 오브젝트 저장 뒤의 결정적 아이디어다 — 데이터가 클러스터의 수천
  디스크에 걸쳐 분산될 수 있다. 데이터 전송률은 수많은 디스크에서 동시에 읽음으로써 극적으로
  올라가며, 주로 디스크 전송률이 아니라 네트워크 성능에 의해 제한된다. 따라서 네트워크 구성 요소와
  CPU도 저장 시스템의 핵심 원료다** (6장, p.193).[^reis2022]

## 솔리드 스테이트 드라이브

- 기제와 성능 — **솔리드 스테이트 드라이브(SSDs)는 데이터를 플래시 메모리 셀의 전하로 저장한다.
  SSD는 마그네틱 드라이브의 기계 부품을 없앤다 — 데이터는 순수하게 전자적 수단으로 읽힌다. SSD는
  0.1ms(100마이크로초) 미만에 임의 데이터를 조회할 수 있다. 게다가 SSD는 저장을 병렬로 도는
  다수의 저장 컨트롤러가 있는 파티션으로 잘라 데이터 전송 속도와 IOPS를 둘 다 확장할 수 있다.
  상용 SSD는 초당 수 기가바이트의 전송 속도와 수만 IOPS를 지원할 수 있다** (6장,
  p.193).[^reis2022]
- OLTP를 바꿨다 — **이 예외적 성능 특성 때문에 SSD는 트랜잭션 데이터베이스를 혁명적으로 바꿨고
  OLTP 시스템의 상용 배치에서 받아들여진 표준이다. SSD는 PostgreSQL·MySQL·SQL Server 같은
  관계형 데이터베이스가 초당 수천 트랜잭션을 감당하도록 허용한다** (6장, p.193).[^reis2022]
- 그런데 분석 저장의 기본은 아니다 — **그러나 SSD는 현재 고규모 분석 데이터 저장의 기본 선택지가
  아니다. 다시 이는 비용으로 귀결된다. 상용 SSD는 일반적으로 용량 기가바이트당 20–30센트(USD)로,
  마그네틱 드라이브의 용량당 비용의 거의 10배다. 따라서 마그네틱 디스크 위의 오브젝트 저장이
  데이터 레이크와 클라우드 데이터 웨어하우스에서 대규모 데이터 저장의 선도적 선택지로 부상했다**
  (6장, p.193).[^reis2022]
- 그래도 OLAP에서 역할이 있다 — **SSD는 여전히 OLAP 시스템에서 상당한 역할을 한다. 어떤 OLAP
  데이터베이스는 자주 접근되는 데이터에 대한 고성능 질의를 지원하기 위해 SSD 캐싱을 활용한다.
  낮은 지연의 OLAP가 더 인기를 얻으면서 우리는 이 시스템들에서 SSD 사용이 뒤따를 것으로
  기대한다** (6장, p.194).[^reis2022]

## 랜덤 액세스 메모리

- 왜 별도 낱말인가 — **우리는 흔히 랜덤 액세스 메모리(RAM)와 메모리라는 용어를 서로 바꿔 쓴다.
  엄밀히 말하면 마그네틱 드라이브와 SSD도 나중의 임의 접근 회수를 위해 데이터를 저장하는 메모리
  역할을 하지만, RAM에는 몇 가지 구체적 특성이 있다** (6장, p.194).[^reis2022] 저자들이 드는
  성질은 일곱이다 (6장, p.194):[^reis2022]
  - **CPU에 붙어 있고 CPU 주소 공간에 매핑된다.**
  - **CPU가 실행하는 코드와 그 코드가 직접 처리하는 데이터를 저장한다.**
  - **휘발성(volatile)이다. 마그네틱 드라이브와 SSD는 비휘발성(nonvolatile)이다. 이따금 실패하고
    데이터를 손상하거나 잃을 수 있지만 드라이브는 일반적으로 전원이 꺼져도 데이터를 유지한다.
    RAM은 전원이 끊기면 1초도 안 되어 데이터를 잃는다.**
  - **SSD 저장보다 유의하게 높은 전송 속도와 빠른 회수 시간을 제공한다. DDR5 메모리 — RAM의
    최신 광범위 사용 표준 — 는 100나노초 정도의 데이터 회수 지연을 제공하며 이는 SSD보다 대략
    1,000배 빠르다. 전형적 CPU는 붙어 있는 메모리에 대해 100GB/s 대역폭과 수백만 IOPS를 지원할
    수 있다. (통계는 메모리 채널 수와 다른 설정 세부에 따라 극적으로 다르다.)**
  - **SSD 저장보다 유의하게 비싸다 — 이 글을 쓰는 시점에 대략 GB당 10달러.**
  - **개별 CPU와 메모리 컨트롤러에 붙일 수 있는 RAM의 양에 제한이 있다. 이는 복잡성과 비용을 더
    더한다. 고메모리 서버는 일반적으로 한 보드에 상호 연결된 다수의 CPU를 활용하며 각각이 붙어
    있는 RAM 블록을 갖는다.**
  - **여전히 CPU 캐시보다 유의하게 느리다. CPU 캐시는 CPU 다이 위나 같은 패키지 안에 직접 위치한
    메모리 유형이다. 캐시는 처리 중 초고속 회수를 위해 자주·최근에 접근된 데이터를 저장한다. CPU
    설계는 크기와 성능 특성이 다양한 여러 층의 캐시를 담는다.**
- 시스템 메모리라 할 때의 실물 — **시스템 메모리를 말할 때 우리는 거의 언제나 동적 RAM(dynamic
  RAM)을 뜻한다 — 고밀도·저비용 형태의 메모리다. 동적 RAM은 데이터를 커패시터의 전하로 저장한다.
  이 커패시터는 시간에 따라 누설되므로 데이터 손실을 막기 위해 메모리를 자주 리프레시(읽고 다시
  쓰기)해야 한다. 하드웨어 메모리 컨트롤러가 이 기술적 세부를 다룬다. 데이터 엔지니어는 그냥
  대역폭과 회수 지연 특성만 걱정하면 된다. 정적 RAM(static RAM) 같은 다른 형태의 메모리는 CPU
  캐시 같은 특화된 응용에 쓰인다** (6장, p.194).[^reis2022]
- 아키텍처에 대한 여담 — **현재 CPU는 사실상 언제나 폰 노이만 아키텍처(von Neumann architecture)
  를 채용하며 코드와 데이터가 같은 메모리 공간에 함께 저장된다. 그러나 CPU는 일반적으로 강화된
  보안을 위해 메모리의 특정 페이지에서 코드 실행을 비활성화하는 선택지도 지원한다. 이 기능은 코드와
  데이터를 분리하는 하버드 아키텍처(Harvard architecture)를 연상시킨다** (6장,
  p.195).[^reis2022]
- 데이터 엔지니어가 잊으면 안 되는 것 — **RAM은 다양한 저장·처리 시스템에서 쓰이며 캐싱·데이터
  처리·인덱스에 쓰일 수 있다. 여러 데이터베이스가 RAM을 주 저장 계층으로 취급해 초고속 읽기·쓰기
  성능을 허용한다. 이런 응용에서 데이터 엔지니어는 RAM의 휘발성을 늘 염두에 둬야 한다. 메모리에
  저장된 데이터가 클러스터에 걸쳐 복제되더라도 여러 노드를 내리는 정전은 데이터 손실을 일으킬 수
  있다. 데이터를 내구적으로 저장하려는 아키텍처는 배터리 백업을 쓰고 정전 시 모든 데이터를 자동으로
  디스크에 덤프할 수 있다** (6장, p.195).[^reis2022] 그 선택의 전문은
  [저장 엔진의 분류](../concepts/storage-engine-classification.md)의 인메모리 절에 있다.

## 네트워킹과 CPU

- 왜 저장의 원료로 세는가 — **왜 네트워킹과 CPU를 데이터 저장의 원료로 언급하는가? 점점 저장
  시스템은 성능·내구성·가용성을 높이기 위해 분산된다. 개별 마그네틱 디스크는 상대적으로 낮은 전송
  성능을 제공하지만 디스크 클러스터는 읽기를 병렬화해 상당한 성능 확장을 낸다고 구체적으로 언급했다.
  독립 디스크 중복 배열(RAID) 같은 저장 표준이 단일 서버에서 병렬화하는 반면, 클라우드 오브젝트
  저장 클러스터는 훨씬 더 큰 규모로 작동하며 디스크가 네트워크에, 심지어 여러 데이터센터와 가용
  영역에 걸쳐 분산된다** (6장, p.195).[^reis2022]
- 가용 영역 — **가용 영역(availability zones)은 독립적인 전력·물·기타 자원을 가진 컴퓨트 환경으로
  이뤄진 표준 클라우드 구성물이다. 다중 영역 저장은 데이터의 가용성과 내구성을 둘 다 높인다**
  (6장, p.195).[^reis2022]
- CPU가 하는 일 — **CPU는 요청을 서빙하고 읽기를 집계하고 쓰기를 분배하는 세부를 다룬다. 저장은
  API·백엔드 서비스 구성 요소·로드 밸런싱을 갖춘 웹 애플리케이션이 된다. 네트워크 장치 성능과
  네트워크 토폴로지가 높은 성능을 실현하는 데 핵심 요인이다** (6장, p.195).[^reis2022]
- 그래서 데이터 엔지니어가 저울질하는 축 — **데이터 엔지니어는 네트워킹이 자기가 짓고 쓰는 시스템에
  어떤 영향을 줄지 이해해야 한다. 엔지니어는 데이터를 지리적으로 펼침으로써 얻는 내구성·가용성과,
  저장을 작은 지리 영역 안에 데이터 소비자·기록자 가까이에 두는 것의 성능·비용 이득 사이에서 끊임없이
  균형을 잡는다** (6장, p.195).[^reis2022]

## 직렬화

- 왜 저장의 원료인가 — **직렬화(serialization)는 또 하나의 원시 저장 재료이자 데이터베이스 설계의
  결정적 요소다. 직렬화를 둘러싼 결정은 질의가 네트워크 너머로 얼마나 잘 수행되는지, CPU 오버헤드,
  질의 지연 등에 영향을 준다. 예컨대 데이터 레이크를 설계하는 것은 기반 저장 시스템(예: Amazon
  S3)과 상호운용성과 성능 고려사항의 균형을 맞추는 직렬화 표준을 고르는 일을 수반한다** (6장,
  pp.195–196).[^reis2022]
- 정의 — **직렬화란 정확히 무엇인가? 소프트웨어가 시스템 메모리에 저장한 데이터는 일반적으로
  디스크 저장이나 네트워크 전송에 적합한 형식이 아니다. 직렬화는 데이터를 읽는 쪽이 디코딩할 수
  있는 표준 형식으로 평탄화하고 포장하는 과정이다. 직렬화 형식은 데이터 교환의 표준을 제공한다.
  데이터를 XML·JSON·CSV 파일로 행 기반 방식으로 인코딩하고 다른 사용자에게 넘기면 그가 표준
  라이브러리로 디코딩할 수 있다** (6장, p.196).[^reis2022]
- 알고리즘이 담는 것 — **직렬화 알고리즘은 타입을 다루는 로직을 갖고, 데이터 구조에 규칙을
  부과하고, 프로그래밍 언어와 CPU 사이의 교환을 허용한다. 직렬화 알고리즘은 예외를 다루는 규칙도
  갖는다. 예컨대 파이썬 객체는 순환 참조를 담을 수 있다 — 직렬화 알고리즘은 순환을 만나면 오류를
  던지거나 중첩 깊이를 제한할 수 있다** (6장, p.196).[^reis2022]
- 저수준 저장도 직렬화다 — **저수준 데이터베이스 저장도 직렬화의 한 형태다. 행 지향 관계형
  데이터베이스는 빠른 조회와 제자리 갱신을 지원하기 위해 데이터를 디스크에 행으로 조직한다. 컬럼
  데이터베이스는 매우 효율적인 압축을 위해 데이터를 컬럼 파일로 조직하고 큰 데이터 볼륨의 빠른
  스캔을 지원한다. 각 직렬화 선택은 트레이드오프 집합과 함께 오며, 데이터 엔지니어는 요구사항에
  맞춰 성능을 최적화하기 위해 이 선택을 튜닝한다** (6장, p.196).[^reis2022] 형식의 카탈로그는
  [데이터 인코딩 형식](../concepts/data-encoding-formats.md)에 있다.

## 압축

- 왜 결정적인가 — **압축(compression)은 저장 공학의 또 하나의 결정적 구성 요소다. 기본 수준에서
  압축은 데이터를 더 작게 만들지만, 압축 알고리즘은 저장 시스템의 다른 세부와 복잡한 방식으로
  상호작용한다** (6장, p.196).[^reis2022]
- **고도로 효율적인 압축은 저장 시스템에서 세 가지 주요 이점을 갖는다** (6장, p.196):[^reis2022]
  - **첫째, 데이터가 더 작아 디스크에서 공간을 덜 차지한다.**
  - **둘째, 압축은 디스크당 실용 스캔 속도를 높인다. 10:1 압축률이면 마그네틱 디스크당 200MB/s를
    스캔하던 것에서 디스크당 실효 2GB/s로 간다.**
  - **셋째 이점은 네트워크 성능에 있다. Amazon EC2 인스턴스와 S3 사이의 네트워크 연결이 초당
    10기가비트(Gbps) 대역폭을 제공한다면 10:1 압축률은 실효 네트워크 대역폭을 100Gbps로 높인다.**
- 대가 — **압축에는 단점도 따라온다. 데이터를 압축·해제하는 것은 데이터를 읽거나 쓰는 데 추가
  시간과 자원 소비를 수반한다** (6장, p.197).[^reis2022]

## 캐싱과 캐시 계층

- 핵심 아이디어 — **캐싱의 핵심 아이디어는 자주 또는 최근에 접근된 데이터를 빠른 접근 계층에
  저장하는 것이다. 캐시가 빠를수록 비용이 높고 가용 저장 공간이 적다. 덜 자주 접근되는 데이터는
  더 싸고 느린 저장에 저장된다. 캐시는 데이터 서빙·처리·변환에 결정적이다** (6장,
  p.197).[^reis2022]
- 캐시 계층이라는 틀 — **저장 시스템을 분석할 때 우리가 활용하는 모든 유형의 저장을 캐시 계층
  (cache hierarchy) 안에 놓는 것이 도움이 된다. 대부분의 실용적 데이터 시스템은 성능 특성이 다양한
  저장으로 조립된 많은 캐시 층에 의존한다. 이는 CPU 안에서 시작한다 — 프로세서는 최대 네 개의 캐시
  계층을 배치할 수 있다. 우리는 계층을 따라 RAM과 SSD로 내려간다. 클라우드 오브젝트 저장은 데이터
  서빙과 파이프라인 안의 동적 데이터 이동을 허용하면서 장기 데이터 보존과 내구성을 지원하는 더 낮은
  계층이다** (6장, p.197).[^reis2022]
- 저자들이 제시하는 발견적 계층 (6장, p.197, 표 6-1):[^reis2022]

  | 저장 유형 | 데이터 인출 지연 | 대역폭 | 가격 |
  |---|---|---|---|
  | CPU 캐시 | 1나노초 | 1TB/s | N/A |
  | RAM | 0.1마이크로초 | 100GB/s | $10/GB |
  | SSD | 0.1밀리초 | 4GB/s | $0.20/GB |
  | HDD | 4밀리초 | 300MB/s | $0.03/GB |
  | 오브젝트 저장 | 100밀리초 | 10GB/s | 월 $0.02/GB |
  | 아카이브 저장 | 12시간 | 데이터가 가용해진 뒤로는 오브젝트 저장과 같음 | 월 $0.004/GB |

  - 단위 확인은 표의 각주가 붙어 있다 — **마이크로초는 1,000나노초이고 밀리초는 1,000
    마이크로초다** (6장, p.197).[^reis2022]
  - 이 표에서 **오브젝트 저장의 대역폭이 SSD보다 크다**(10GB/s 대 4GB/s)는 점이 눈에 띈다.
    앞의 [마그네틱 디스크 드라이브](#마그네틱-디스크-드라이브) 절이 말한 **병렬성** 때문이다 —
    수천 디스크에서 동시에 읽으면 개별 매체보다 빨라진다. 지연은 100밀리초로 가장 나쁘다.
    즉 대역폭과 지연이 같은 방향으로 움직이지 않는다.
- 아카이브는 역방향 캐시다 — **우리는 아카이브 저장을 역캐시(reverse cache)로 생각할 수 있다.
  아카이브 저장은 낮은 비용으로 열등한 접근 특성을 제공한다. 아카이브 저장은 일반적으로 데이터
  백업과 데이터 보존 규제 준수 요구를 충족하는 데 쓰인다. 전형적 시나리오에서 이 데이터는 비상시
  에만 접근된다(예: 데이터베이스의 데이터가 손실되어 복구가 필요하거나, 회사가 법적 증거 개시를
  위해 과거 데이터를 되돌아봐야 할 수 있다)** (6장, p.197).[^reis2022]

## 기존 수치와의 대조

이 KB에는 저장 매체의 물성을 다루는 소스가 이미 둘 있다. 수치가 어긋나는지 맞춰 본다.

- **블록·섹터 크기 — 일치한다.** 저자들은 **블록이 "옛 디스크에서 흔히 사용 가능 데이터 512
  바이트였으나 이제 대부분의 현행 디스크에서 4,096바이트로 커졌다"** 고 적는다 (6장,
  p.202).[^reis2022] 페트로프는 **"섹터 크기는 보통 512바이트에서 4KB 사이"** 라고 적는다 (2장,
  p.30).[^petrov2019] 범위가 같고, reis 쪽이 그 범위 안에서 시간에 따른 이동을 밝힌 것이다.
  상세는 [디스크 기반 저장의 제약](../concepts/disk-based-storage-constraints.md).
- **HDD 임의 접근 지연 — 일치한다.** reis는 7,200 RPM 드라이브에서 탐색 시간과 회전 지연을 합쳐
  평균 4밀리초 초과라 적고, 위 캐시 계층 표도 HDD를 4밀리초로 놓는다 (6장, pp.192–193, 197).
  [^reis2022] 페트로프는 수치 없이 **"헤드 위치 잡기가 HDD 연산에서 가장 비싼 부분"** 이라는
  정성 서술만 한다 (2장, p.30).[^petrov2019] 충돌이 아니라 정량화다.
- **SSD 임의 조회 — 서술이 두 곳에서 미세하게 다르다.** 본문은 **"0.1ms(100마이크로초)
  미만"** 이라 하고 (6장, p.193), 표 6-1은 SSD 인출 지연을 **"0.1밀리초"** 로 적는다 (6장,
  p.197).[^reis2022] 같은 자릿수를 각각 상한과 대표값으로 쓴 것으로 보인다 — 표는 발견적
  (heuristic)이라고 제목이 스스로 밝힌다. #hypothesis
- **순차 대 임의의 강조가 다르다.** 페트로프는 SSD에서 **"임의 대 순차 I/O의 강조가 HDD만큼
  세지 않다"** 고 적고 그 이유를 FTL·가비지 컬렉션에서 찾는다 (2장, pp.31–32).[^petrov2019]
  reis는 SSD의 구조적 세부(지우기 블록·FTL)를 다루지 않고 성능 수치와 가격만 다룬다. 층위가
  다르지 충돌은 아니다 — 저장 엔진 설계자와 저장 시스템 선택자의 관심이 갈리는 지점이다.
- **가격 비율이 이 페이지의 실질 정보다.** SSD가 HDD의 약 10배, RAM이 SSD의 약 50배(GB당 $10
  대 $0.20), 오브젝트 저장이 HDD 구매가보다 싼 월 임대료. 절대 가격은 위 [측정
  시점](#수치의-측정-시점)이 밝힌 대로 낡지만, **왜 분석 저장이 마그네틱 위의 오브젝트 저장으로
  수렴했는가**라는 결론은 이 비율에서 나온다.
