# Kimball DW/BI 라이프사이클

이 페이지의 질문: **DW/BI 프로젝트는 전체적으로 어떤 순서와 의존 관계로 진행되며, 무엇 때문에 실패하는가?** 차원 모델링 기법 자체가 아니라, 프로젝트 착수부터 유지보수까지의 로드맵을 다룬다. 아키텍처 구성 요소는 [Kimball DW/BI 아키텍처](../concepts/kimball-dwbi-architecture.md), 모델링 작업의 운영 방식은 [차원 설계 프로세스 운영](../concepts/dimensional-design-process.md) 참고.

## 로드맵 구조: 계획 → 요구정의 → 3트랙 → 배포

- 라이프사이클은 1998년 "Business Dimensional Lifecycle"로 처음 발표됐고, 핵심 신조는 세 가지다 — 비즈니스 요구에 집중, 차원 구조로 데이터 제공, 관리 가능한 반복(iterative) 프로젝트 수행 (17장, p.404).[^kimball2013]
- 로드맵 다이어그램(Figure 17-1)은 작업의 순서·의존성·동시성을 나타내며, 절대적 시간축이 아니다 — 상자 크기는 같아도 실제 노력은 크게 다르다(예: 물리 설계 대비 ETL 작업의 부하 차이) (17장, pp.404–406).[^kimball2013]
- 전체 흐름: 프로그램/프로젝트 계획 → 비즈니스 요구정의 → **3개 병렬 트랙**(기술: 아키텍처 설계→제품 선정 / 데이터: 차원 모델링→물리 설계→ETL / BI 앱: 설계→개발) → 배포 → 유지보수 → 성장(다음 반복으로 라이프사이클 재진입). 프로그램/프로젝트 관리가 전 구간을 받친다 (17장, pp.404–406).[^kimball2013]
- 계획과 요구정의 사이에는 양방향 화살표가 있다 — 두 활동은 상호작용하며, 요구를 모른 채 계획을 확정할 수 없다 (17장, p.405).[^kimball2013]
- 제품 선정이 로드맵의 첫 상자가 아니라는 점이 의도적이다. 초보 팀의 가장 흔한 실수가 목표를 이해하기 전에 제품부터 고르는 것이다 (17장, p.405).[^kimball2013]
- 애자일과의 관계: 비즈니스 가치 집중·협업·점진 개발이라는 신조는 공유하지만, 버스 아키텍처가 이끄는 데이터 아키텍처·거버넌스 기반 위에서 개발해야 하며, 여러 애자일 산출물을 묶어 충분한 기능의 릴리스로 배포하는 편이 대개 낫다고 본다 (17장, p.405).[^kimball2013]

## 착수: 준비도 평가·범위·인력

- 준비도(readiness) 3요인 — 중요도 순위가 있다: (1) **강력한 경영진 비즈니스 스폰서**(가장 결정적; CIO가 스폰서인 경우는 더 위험하다), (2) 절박한 비즈니스 동기, (3) 타당성(feasibility) — 그중 **데이터 타당성이 가장 치명적**이다. 필요한 grain(grain)으로 깨끗한 데이터를 수집하고 있지 않다면 단기 해결책이 없기 때문이다 (17장, pp.406–407).[^kimball2013]
- 범위 설정: 처음에는 **단일 비즈니스 프로세스**의 데이터에 집중하고, 프로세스 횡단 프로젝트는 뒤로 미룬다. "Law of Too"를 피하라 — 너무 많은 소스·사용자·지역·요구를 너무 짧은 일정에 (17장, p.407).[^kimball2013]
- 정당화(justification): 비용은 IT가, 재무 편익은 비즈니스가 산정할 책임을 진다. "단일 진실"이나 "유연한 정보 접근" 같은 구호는 재무적 정당화가 못 된다 — 의사결정 개선의 정량 효과까지 파고들어야 하고, 그게 안 되면 스폰서나 문제 자체를 잘못 골랐다는 징후다 (17장, p.407).[^kimball2013]
- 인력은 "역할이지 사람 수가 아니다". 비즈니스 측(스폰서·드라이버·리드·사용자), 경계 역할(비즈니스 분석가·데이터 스튜어드·BI 앱 설계/개발자), IT 측(프로젝트 관리자·기술 아키텍트·데이터 아키텍트/모델러·DBA·메타데이터 코디네이터·ETL 아키텍트·ETL 개발자)로 구성되며, 작은 조직에서는 한 사람이 여러 역할을 겸한다 (17장, pp.408–409).[^kimball2013]
- 범위 변경(scope creep) 대응은 셋 중 하나 — 범위 확대(시간·자원·예산 추가), 제로섬 교환, 개선 요청으로 유예 — 이며, 어느 쪽이든 IT 단독으로 결정하지 말고 비즈니스와 함께 정한다 (17장, p.410).[^kimball2013]

## 요구정의 전술

- 수집 기법은 인터뷰와 퍼실리테이션 세션(facilitated session) 두 가지가 기본이고, 저자들은 인터뷰로 상세를 모으고 퍼실리테이션으로 합의를 만드는 혼합 방식을 쓴다. 설문은 평면적이고 심층 탐색이 불가능해 부적합하다 (17장, pp.410–411).[^kimball2013]
- 비즈니스 대표에게 데이터의 grain이나 차원성을 직접 묻지 않는다 — 무엇을 하고, 왜 하며, 어떻게 의사결정하는지를 묻는다. 핵심 성과 지표 추적 방식이 곧 비즈니스 프로세스와 팩트로 번역된다 (17장, pp.410, 412).[^kimball2013]
- 커버리지 원칙: 조직을 **수평으로**(부서 횡단 — 버스 매트릭스 청사진 수립에 필수) 그리고 **수직으로**(경영진~실무 — 파워 유저에게만 쏠리면 전략 방향을 놓친다) 커버한다 (17장, p.411).[^kimball2013]
- 사용자의 상위 5개 리포트에 합의시키는 것만으로는 확장 가능한 분석 환경을 설계할 수 없다 — 질문은 반드시 바뀐다 (17장, p.413).[^kimball2013]
- 인터뷰 마무리에 각자의 **측정 가능한 성공 기준**을 묻고, 논의된 기능이 1차 범위에 포함된다는 보장은 없다는 면책을 반드시 남긴다 (17장, p.413).[^kimball2013]
- 비즈니스 인터뷰와 병행해 소스 시스템 전문가와 **데이터 중심 인터뷰**를 끼워 넣어 핵심 데이터의 존재 여부를 확인한다 — 기대가 커지기 전에. 정밀 데이터 감사는 모델링 단계에서 한다 (17장, pp.413–414).[^kimball2013]
- 산출 문서는 개별 인터뷰 기록보다 **비즈니스 프로세스 단위로 구조화한 통합 findings 문서**가 더 중요하다 — 프로세스가 곧 구현 단위가 되기 때문이다 (17장, p.414).[^kimball2013]
- 우선순위는 **우선순위 그리드**(Figure 17-2: 세로축 = 잠재 비즈니스 영향, 가로축 = 타당성)로 비즈니스와 함께 정한다. 우선 착수는 우상단(고영향·고타당성), 좌하단은 회피, 우하단(쉽지만 안 중요)은 팀이 쏠리기 쉬우나 단기 착수 정당화가 안 되고, 좌상단(중요하나 현재 불가)은 다른 IT 팀이 타당성 제약을 해소해야 할 대상이다 (17장, pp.414–415).[^kimball2013]

## 기술 트랙: 아키텍처 8단계와 제품 선정 6작업

- 기술 아키텍처는 집 짓기의 청사진 유비 — 종이 위에서 문제를 잡아내고, 병렬 작업을 조율하며, 무엇보다 소통 도구다. 모든 DW/BI 시스템에는 아키텍처가 있다; 문제는 그것이 계획되고 명시적인가, 암묵적인가일 뿐이다 (17장, pp.416–417).[^kimball2013]
- 양극단 모두 병폐다 — 아키텍처를 건너뛰고 임시변통으로 잇다가 재구축하게 되는 팀과, 2년간 아키텍처만 설계하는 팀. 8단계 프로세스가 중간 지대다: 태스크포스 구성(2–3인) → 아키텍처 관련 요구 수집(비즈니스 요구를 다른 필터로 듣기 + IT 인터뷰) → 요구 문서화 → 아키텍처 모델 작성 → 구현 단계 결정 → 서브시스템 상세 정의 → 아키텍처 계획 문서화 → 리뷰·확정 (17장, pp.416–418).[^kimball2013]
- 제품 선정 6작업: 구매 프로세스 이해 → 평가 매트릭스 작성(기준이 구체적일수록 좋다) → 시장 조사(RFP는 가능하면 피하라 — 비용 대비 미인기 대회에 가깝다) → 후보 축소·상세 평가(평가자가 주도권을 쥐어야 한다) → 필요시 프로토타입(최대 2개 제품) → 선정 후 **비공개 단독 후보로 시험 도입**하며 협상력을 보존한다 (17장, pp.418–420).[^kimball2013]

## 데이터 트랙과 BI 앱 트랙

- 데이터 트랙 = 차원 모델링 → 물리 설계 → ETL 설계·개발. 물리 설계에서 논리 설계와 물리 설계는 거의 닮아야 한다 — DBA가 차원 스키마를 정규화 구조로 되돌리게 두지 마라 (17장, p.420).[^kimball2013]
- 물리 설계 활동: 명명·DB 표준 수립, 물리 모델 개발(스테이징·감사 테이블 포함), 초기 인덱스 계획(차원 테이블은 대리 키에 유일 인덱스 + 필터링 속성에 비트맵, 팩트 테이블은 날짜 외래 키를 선두로 한 기본 키 인덱스), 집계 설계, 물리 저장 상세(대형 팩트 테이블은 날짜 파티셔닝) (17장, pp.420–422).[^kimball2013]
- 성능 튜닝에서 하드웨어 증설보다 **집계 테이블**이 훨씬 비용 효율적이다. 모든 집계를 만들 수는 없으므로 사용자 접근 패턴과 데이터의 통계적 분포 두 가지로 지점을 고른다. 초기 배포부터 적절한 인덱스·집계를 갖춰야 한다 (17장, pp.421–422).[^kimball2013]
- BI 앱 트랙: 완전 애드혹 환경보다 **파라미터 구동 템플릿** 형태의 BI 앱이 사용자 요구의 대부분을 채운다 — 다수 사용자에게 "애드혹"이란 리포트의 파라미터를 바꾸는 것이다. 요구정의에서 10–15개의 시작 앱을 선별한다 (17장, pp.422–423).[^kimball2013]
- BI 앱 개발을 ETL "완료" 전에 시작하는 것을 권한다 — BI 개발자가 데이터 문제를 가장 빨리 찾아내고 쿼리 응답 시간을 처음으로 현실적으로 시험하기 때문이다 (17장, p.423).[^kimball2013]

## 배포·유지보수·성장

- 세 트랙은 배포에서 수렴하지만 자연히 합쳐지지 않는다 — 상당한 사전 계획과, 준비 안 된 배포를 미룰 용기가 필요하다. 명절 만찬 유비: 데이터가 메인 요리인데, 덜 익었어도 예고한 날짜 때문에 배포를 강행하면 사용자는 다시 오지 않는다 (17장, p.424).[^kimball2013]
- 배포 전 **엔드투엔드 시스템 테스트**(데이터 품질 보증·운영 처리·성능·사용성)와 교육·지원 패키징이 필요하다. 지원은 셀프서비스 → 현업 파워 유저 → DW/BI 팀 중앙 지원의 계층 구조가 일반적이다 (17장, p.424).[^kimball2013]
- 배포 후 관리 4영역: 지원(소식이 없으면 좋은 소식이 아니라 아무도 안 쓰는 것이다), 교육(신규·심화·재수강 커리큘럼), 기술 지원(SLA를 갖춘 운영 환경으로 취급, 성능 추세 선제 모니터링), 프로그램 지원(성공을 측정하고 마케팅) (17장, p.425).[^kimball2013]
- 성장 요구는 실패가 아니라 **성공의 신호**다. 우선순위 그리드로 비즈니스와 함께 다음 단계를 정하고, 이미 구축된 기반 위에서 라이프사이클의 처음으로 되돌아간다 (17장, pp.425–426).[^kimball2013]

## 실패 원인 상위 요인 (Top 10 Pitfalls)

- 저자들이 꼽는 치명적 오류 10가지 — "하나만으로도 이니셔티브를 무너뜨리기에 충분하다" (17장, p.426).[^kimball2013] 번호는 원문의 카운트다운(10 → 1, 1이 가장 치명적):
  - 10: 비즈니스 요구·목표 대신 기술과 데이터 자체에 심취.
  - 9: 영향력 있고 접근 가능한 경영진 비즈니스 스폰서 영입 실패.
  - 8: 관리 가능한 반복 개발 대신 은하계급 다년 프로젝트 착수.
  - 7: 정규화 구조 구축에 에너지를 쏟다가 차원 모델 기반 표현 영역을 만들기 전에 예산 소진.
  - 6: 프런트 룸의 쿼리 성능·사용 편의보다 백 룸 운영 성능·개발 편의를 우선.
  - 5: 조회 대상인 표현 영역 데이터를 과도하게 복잡하게 만듦.
  - 4: 공유 conformed dimension으로 묶는 데이터 아키텍처 없이 차원 모델을 각개 구축.
  - 3: 표현 영역에 요약 데이터만 적재.
  - 2: 비즈니스·요구·데이터·기술이 정적이라고 가정.
  - 1: DW/BI 성공이 비즈니스 수용(business acceptance)에 직결됨을 부정 (17장, p.426).[^kimball2013]
- 1번은 왜곡 없이 원문으로:

> **Pitfall 1**: Neglect to acknowledge that DW/BI success is tied directly to business acceptance. If the users haven't accepted the DW/BI system as a foundation for improved decision making, your efforts have been exercises in futility. (17장, p.426)[^kimball2013]

[^kimball2013]: Kimball & Ross 2013, 17장 "Kimball DW/BI Lifecycle Overview"
