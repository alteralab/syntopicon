하나의 질문: **저장소에서 꺼낸 데이터로 객체를 다시 세우는 일이 새 객체를 만드는 일과 무엇이
다르고, 그 차이를 설계에서 어떻게 표시하는가.**

## 왜 되살리는 데 조립이 필요한가

- 전제가 저장 기술의 성질이다 — 어느 시점에서 대부분의 객체는 데이터베이스에 저장되거나 네트워크로
  전송되는데, **2003년 저술 시점의 데이터베이스 기술 중 자기 내용물의 객체적 성격을 보존하는 것은 거의 없다.
  전송 방식 대부분은 객체를 그보다 더 제한된 표현으로 납작하게 만든다. 그러므로 검색은 부품들을
  살아 있는 객체로 재조립하는, 잠재적으로 복잡한 과정을 요구한다** (6장, p.145).[^evans2003]
- 그래서 팩토리(FACTORY)의 몫이 생애 주기의 맨 앞에서 한 칸 더 나아간다. 여기까지 팩토리는 객체
  생애의 시작에서만 제 역할을 했다 (6장, p.145).[^evans2003] 그 패턴의 본체는
  [팩토리 패턴](../concepts/factories-pattern.md)에 있다.
- 도구가 대신해 주는 구간도 명시된다 — **객체 매핑 기술이 데이터베이스 재구성(reconstitution)의
  경우에 이 서비스의 일부나 전부를 제공할 수 있고, 그것은 편리하다. 다른 매체에서 객체를
  재구성하는 데 드러난 복잡성이 있을 때면 언제나 팩토리가 좋은 선택지다** (6장,
  p.145).[^evans2003]

## 재구성 팩토리가 생성 팩토리와 다른 두 자리

- **재구성에 쓰이는 팩토리는 생성에 쓰이는 팩토리와 아주 비슷하되 두 가지 큰 차이가 있다** (6장,
  p.145):[^evans2003]
  1. **재구성에 쓰이는 엔티티(ENTITY) 팩토리는 새 추적 식별자를 부여하지 않는다.** 그렇게 하면
     객체의 이전 화신과의 연속성을 잃을 것이기 때문이다. **그래서 저장된 객체를 재구성하는
     팩토리에서는 식별 속성이 입력 매개변수의 일부여야 한다.**
  2. **객체를 재구성하는 팩토리는 불변식(invariant) 위반을 다르게 다룰 것이다.** 새 객체를 만들
     때 팩토리는 불변식이 충족되지 않으면 그냥 멈춰 서야 하지만, **재구성에서는 더 유연한 대응이
     필요할 수 있다.** 객체가 이미 시스템 어딘가(예컨대 데이터베이스)에 존재한다면 그 사실을
     무시할 수 없다. **그렇다고 규칙 위반을 무시할 수도 없다. 그런 불일치를 고칠 전략이 있어야
     하고, 그것이 재구성을 새 객체의 생성보다 더 까다롭게 만들 수 있다.**
- 둘째 차이가 이 페이지에서 가장 실무적인 대목이다. 생성 쪽 규칙은
  [팩토리 패턴](../concepts/factories-pattern.md)의 "원자적이고 모든 불변식을 강제한다"인데, 재구성에는 그
  규칙을 그대로 적용할 수 없다 — 이미 저장된 데이터는 규칙보다 먼저 존재한다. 무엇을 고치고
  무엇을 거부할지가 설계 결정으로 남는다.
- 저자가 재구성의 두 갈래를 도해로 보인다. 하나는 관계형 데이터베이스에서 꺼낸 엔티티로, SQL 결과
  집합을 받은 팩토리가 객체-관계 매핑 기술에 위임해 객체를 만든다. 다른 하나는 XML로 전송된
  엔티티로, XML을 받은 팩토리가 파서에 위임한 뒤 객체를 만든다 (6장, p.146, Figure
  6.16·6.17).[^evans2003] 두 경우 모두 **팩토리가 매체별 복잡성을 받아 내고 산물은 같은 모양으로
  나온다**는 구조가 같다.
- 절을 닫는 요약이 팩토리 전체의 범위를 정한다 (6장, pp.145–146):[^evans2003]
  - **요약하면, 인스턴스 생성의 접근점이 식별되어야 하고 그 범위가 명시적으로 정의되어야 한다.
    그것들은 그냥 생성자일 수도 있지만, 더 추상적이거나 정교한 인스턴스 생성 기제가 필요한 경우가
    흔하다.**
  - **팩토리는 대개 모델의 어떤 부분도 표현하지 않지만, 모델을 표현하는 객체들을 날카롭게
    유지하도록 돕는 도메인 설계의 일부다.**
  - **팩토리는 생성과 재구성이라는 생애 주기 전이를 캡슐화한다.**

## 기술적으로는 생성, 개념적으로는 중간

- 이 낱말의 유래가 리포지터리(REPOSITORY) 절에 있다. 기술적 관점에서 보면 **저장된 객체의 검색은
  실제로 생성의 부분집합이다. 데이터베이스에서 온 데이터가 새 객체를 조립하는 데 쓰이기 때문이다.
  실제로 흔히 써야 하는 코드가 이 현실을 잊기 어렵게 만든다** (6장, p.149).[^evans2003]
- **그런데 개념적으로는 다르다** — **그러나 개념적으로 이것은 엔티티 생애 주기의 *중간*이다.
  고객(Customer) 객체는 우리가 그것을 데이터베이스에 저장했다가 검색해 왔다는 이유만으로 새
  고객을 표상하지 않는다. 이 구분을 염두에 두려고, 나는 저장된 데이터에서 인스턴스를 만드는 것을
  *재구성*이라 부른다** (6장, p.149).[^evans2003]
  - **이름 하나가 설계 판정을 나른다.** 같은 코드 경로를 무엇이라 부르느냐가 식별자를 새로 줄지,
    불변식 위반에 어떻게 대응할지를 정한다. 이것이 이 소스가
    [유비쿼터스 언어](ubiquitous-language.md)에서 요구하는 것의 좁은 실례다 — 이름을 바꾸면
    모델이 바뀐다.

## 팩토리는 만들고 리포지터리는 찾는다

- 두 패턴의 분담이 한 줄로 정해진다 — **팩토리는 객체 생애의 시작을 다루고, 리포지터리는 중간과
  끝을 관리하도록 돕는다** (6장, p.157).[^evans2003] 객체가 메모리에 있거나 객체 데이터베이스에
  저장될 때는 이것이 단순하지만, 관계형 데이터베이스·파일·다른 비객체 지향 시스템에 저장된
  것이라면 **검색된 데이터가 객체 형태로 재구성되어야 한다** (6장, p.157).[^evans2003]
- **그래서 둘을 합치자는 유혹이 생긴다** — 리포지터리가 데이터에 기반해 객체를 만들고 있으므로
  **많은 사람이 리포지터리를 팩토리*라고* 여긴다 — 기술적 관점에서는 실제로 그렇다** (6장,
  p.157).[^evans2003]
- 저자는 그 합침을 기각한다 — **그러나 모델을 전면에 두는 쪽이 더 쓸모 있고, 앞서 말했듯 저장된
  객체의 재구성은 새로운 개념적 객체의 생성이 아니다. 이 도메인 주도의 설계관에서 팩토리와
  리포지터리는 별개의 책임을 갖는다. 팩토리는 새 객체를 만들고, 리포지터리는 옛 객체를 찾는다.
  리포지터리의 클라이언트에게는 객체들이 메모리에 있다는 착시가 주어져야 한다. 객체가 재구성되어야
  할 수도 있지만(그렇다, 새 인스턴스가 만들어질 수도 있다) 그것은 같은 개념적 객체이고 여전히
  생애 주기의 중간에 있다** (6장, pp.157–158).[^evans2003]
- 화해의 배치가 위임이다 — **이 두 관점은 리포지터리가 객체 생성을 팩토리에 *위임*하게 만들어
  조화될 수 있으며, 그 팩토리는 (이론상으로는, 실무에서는 드물지만) 맨바닥에서 객체를 만드는 데도
  쓰일 수 있다** (6장, p.158, Figure 6.22).[^evans2003]
- **이 분담이 팩토리 쪽에서도 값을 한다** — **이 명확한 분리는 팩토리에서 영속성에 대한 모든 책임을
  덜어 내는 데도 도움이 된다. 팩토리의 일은 데이터로부터 잠재적으로 복잡한 객체를 인스턴스화하는
  것이다. 산물이 새 객체라면 클라이언트가 그것을 알고 리포지터리에 더할 수 있으며, 리포지터리가
  그 객체의 데이터베이스 저장을 캡슐화할 것이다** (6장, p.158, Figure 6.23).[^evans2003]
  - 즉 새 객체는 `팩토리 → 클라이언트 → 리포지터리.add` 순으로 흐르고, 옛 객체는
    `클라이언트 → 리포지터리 → 팩토리` 순으로 흐른다. 두 흐름이 팩토리를 공유하되 방향이 반대다.

## "찾거나 만들기"를 기각하는 근거

- 합침을 부르는 마지막 동기가 편의 기능이다 — **팩토리와 리포지터리를 합치도록 사람들을 몰아가는
  또 다른 경우는 "찾거나 만들기"(find or create) 기능에 대한 욕구다. 클라이언트가 원하는 객체를
  서술하면 그런 객체가 없을 때 새로 만들어진 것을 받는 기능이다** (6장, p.158).[^evans2003]
- 판정이 단호하다 — **이 기능은 피해야 한다. 그것은 잘해야 사소한 편의다. 쓸모 있어 보이는 경우의
  많은 수가 엔티티와 값 객체(VALUE OBJECT)를 구분하면 사라진다. 값 객체를 원하는 클라이언트는
  곧장 팩토리로 가서 새것을 요청하면 된다** (6장, pp.158–159).[^evans2003]
- 근거가 도메인 쪽에 있다 — **보통 새 객체와 기존 객체의 구분은 도메인에서 중요하고, 둘을 투명하게
  합치는 프레임워크는 실제로 상황을 흐려 놓을 것이다** (6장, p.159).[^evans2003]
  - **이 판정이 앞 절의 재구성 규정에 직접 기댄다.** "이것이 새것인가 옛것인가"가 도메인의 물음이면,
    그 물음을 지우는 편의 메서드는 모델을 지우는 것이 된다. 엔티티와 값 객체의 구분 자체는
    [값 객체와 엔티티](value-objects-and-entities.md)에 있다.
