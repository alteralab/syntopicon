## 하나의 질문

**플랫폼이 노출할 인터페이스를 무엇을 기준으로 고르는가.**

[멀티플레인 데이터 플랫폼](../concepts/multiplane-data-platform.md)이 플랫폼의 **구조**를
정한다면, 원전 10장의 본체는 그 구조의 **표면을 도출하는 절차**다. 저자의 답은 능력 목록이
아니라 사용자의 여정이다.

## 왜 여정에서 시작하는가

- 목적에서 방법이 따라 나온다 — **플랫폼의 궁극적 목적은 교차 기능 도메인 팀을 서빙해 그들이
  데이터 프로덕트를 전달하거나 소비할 수 있게 하는 것이다. 따라서 플랫폼 설계를 시작하는 가장
  좋은 방법은 당신 플랫폼 사용자의 주요 여정(journeys)을 이해하고, 플랫폼을 써서 그들이 여정을
  성공적으로 완수하기 쉽게 만들 방법을 평가하는 것이다** (10장, p.174).[^dehghani2022]
- 10장 전체가 그 방법의 시연이다 — **이 장에서 나는 플랫폼의 설계에 어떻게 접근하는지를 두 예시
  역할 — 데이터 프로덕트 개발자와, 데이터 프로덕트 소비자로서의 데이터 과학자 — 을 써서 보인다**
  (10장, p.175).[^dehghani2022]
- 표기에 단서가 붙는다 — **인터페이스의 표기와 표현은 최종 구현을 대표하지 않는다. 명령형 언어는
  기능성에 집중하기 위해 고른 것이고, 실제로는 API의 선언적 형태가 더 바람직하다. 예컨대
  `/deploy` 인터페이스는 배포된 데이터 프로덕트를 위한 선언적 자원인 `/deployments`로 구현될
  가능성이 아주 크다** (10장, p.176).[^dehghani2022] 그림 10-3은 표기 규약도 정한다 — `/`는
  플레인 수준 API, `/{dp}`는 특정 데이터 프로덕트의 API, `/{dp}/{output}`은 특정 데이터
  프로덕트의 특정 출력 포트의 API다 (10장, p.177, 그림 10-3).[^dehghani2022]

## 여섯 페르소나

- 저자가 데이터 메시 생태계의 고수준 페르소나로 드는 것은 여섯이다 (10장,
  pp.174–175):[^dehghani2022]

| 페르소나 | 원어 | 무엇을 하는가 |
|---|---|---|
| 데이터 프로덕트 개발자 | data product developers | 일반 프로그래밍 기술을 가진 제너럴리스트부터 기존 분석 데이터 처리 기술에 정통한 전문 데이터 엔지니어까지 넓은 스펙트럼을 포괄한다 |
| 데이터 프로덕트 소비자 | data product consumers | 일하기 위해 데이터에 접근해 써야 한다는 공통점을 갖는 여러 역할 |
| 데이터 프로덕트 소유자 | data product owners | 자기 도메인에 대해 성공적인 데이터 프로덕트를 전달하고 전도한다 |
| 데이터 거버넌스 구성원 | data governance members | 연합 구조라 단일 거버넌스 역할은 없고, 메시 전체의 최적·안전한 운영을 보증하는 집합적 책임을 진다 |
| 데이터 플랫폼 프로덕트 소유자 | data platform product owner | 플랫폼 서비스를 최고의 사용자 경험을 갖는 제품으로 전달할 책임을 진다 |
| 데이터 플랫폼 개발자 | data platform developer | 플랫폼을 짓고 운영하며 동시에 쓴다 |

- 소비자 페르소나가 특히 넓다 — 그들의 일은 **데이터 과학자로서 ML 모델을 훈련하거나 추론하는
  것, 데이터 분석가로서 리포트와 대시보드를 개발하는 것, 데이터 프로덕트 개발자로서 기존 것을
  소비하는 새 데이터 프로덕트를 개발하는 것, 애플리케이션 개발자로서 운영 도메인에서 데이터 주도
  서비스와 애플리케이션을 짓는 것**일 수 있다 (10장, p.174).[^dehghani2022] 그래서 **플랫폼
  인터페이스와 서비스는 정확한 역할에 따라 달라질 수 있다** (10장, p.174).[^dehghani2022]
- 플랫폼 개발자가 페르소나에 드는 이유가 재귀적이다 — **데이터 프로덕트 경험 플레인에서 일하는
  플랫폼 개발자는 유틸리티 플레인 서비스의 사용자다. 따라서 그들의 기술 집합과 여정은 유틸리티
  플레인 서비스의 설계에 중요하다** (10장, p.175).[^dehghani2022]

## 데이터 프로덕트 개발자 여정 — 세 단계

- 여정의 성격이 먼저 규정된다 — **데이터 프로덕트 개발자의 핵심 여정 하나는 데이터 프로덕트를
  만들고 운영하는 것이다. 이는 "모두가 책임진다"는 지속적 전달 원칙을 받아들이는 종단 간
  장기적 책임이다. 데이터 프로덕트를 짓고 운영하는 것은 다른 누군가의 문제가 아니다** (10장,
  p.175).[^dehghani2022]
- 단계는 셋으로 그린다 — **착상(Incept)·탐색(Explore)·부트스트랩(Bootstrap)·소스(Source)**,
  **빌드(Build)·테스트(Test)·배포(Deploy)·실행(Run)**, **모니터(Monitor)·진화(Evolve)·
  [은퇴(Retire)]** (10장, p.176, 그림 10-2).[^dehghani2022]
  - 단선이 아님을 저자가 명시한다 — **이 단계들은 지속적 피드백 루프를 갖고 반복적이다. 시연의
    단순함을 위해 나는 여정을 단계들의 선형 연속으로 그렸다** (10장, p.175).[^dehghani2022]
- 이 여정은 고립되지 않는다 — **원천 정렬 데이터 프로덕트의 경우 데이터 프로덕트 개발자는 원천
  애플리케이션 개발자와 긴밀히 일한다. 그들은 애플리케이션이 자기 운영 데이터를 데이터 프로덕트에
  대한 입력으로 어떻게 공유할지를 공동 설계하고 구현한다. 이 사람들은 같은 도메인 팀에 속함에
  유의하라** (10장, p.175).[^dehghani2022] 소비자 정렬 쪽도 대칭이다 — **소비자 정렬 데이터
  프로덕트의 경우 데이터 프로덕트 개발자와 분석 애플리케이션 개발자 사이에 협업이 있다. 데이터
  프로덕트 개발자는 분석 애플리케이션의 목표와, 데이터 필드 및 데이터 프로덕트가 지원해야 할
  보증의 면에서 그 필요를 이해해야 한다** (10장, p.176).[^dehghani2022]

## ① 착상·탐색·부트스트랩·소스

- 착상의 근거가 실제 용법이어야 한다 — **데이터 프로덕트는 흔히 자기 데이터를 필요로 하는 하나
  또는 여러 잠재적 분석 용법을 우리가 발견하기 때문에 존재하게 된다. 데이터 프로덕트, 특히 원천
  정렬인 것은 오늘 우리 상상 너머를 포함해 많은 다양한 용법을 갖지만, 그럼에도 우리는 실세계
  맥락에서 데이터 프로덕트의 가치를 보여 주는 실제 용법에서 착상 — 창조 — 을 시작해야 한다**
  (10장, pp.177–178).[^dehghani2022]
- 탐색 단계에서 개발자가 하는 일 — **데이터 프로덕트의 착상 동안 개발자는 데이터 프로덕트를 위한
  잠재 소스를 찾는 탐색적(exploratory) 국면에 있다. 소스는 상류 데이터 프로덕트, (조직에 대한)
  외부 시스템, 또는 (조직 안의) 운영 시스템으로 발견될 수 있다. 탐색 동안 개발자는 상류 소스의
  발견 정보를 연구해 소스의 적합성·데이터 보증·문서·데이터 프로파일링·기존 사용자 등을 평가할 수
  있다** (10장, p.178).[^dehghani2022]
- 부트스트랩의 실질 — **잠재적 소스가 지명되면 개발자는 hello world 데이터 프로덕트를 빠르게
  부트스트랩할 수 있다. 플랫폼이 필요한 인프라를 프로비저닝한다. 그것은 데이터 프로덕트 개발자가
  소스에 연결하고 데이터를 소비할 수 있게 한다 — 합성 데이터(synthesized data)의 형태로든,
  난독화된 것이든, 실제 데이터든이다** (10장, p.178).[^dehghani2022]
- 이 국면이 요구하는 플랫폼 능력이 네 가지로 정리된다 — **빠른 발견, 소스 출력 데이터에 대한
  접근, 데이터 프로덕트의 빠른 스캐폴딩, 인프라 프로비저닝이 전부 착상·부트스트랩 국면의 필수
  조각이다** (10장, p.178).[^dehghani2022]
- 표 10-1이 이 국면의 인터페이스 예다 (10장, pp.179–180):[^dehghani2022]

| 플레인 | 인터페이스 | 하는 일 |
|---|---|---|
| 메시 경험 | `/search` | 적합한 소스를 찾기 위해 기존 데이터 프로덕트의 메시를 검색한다. 원천 운영 시스템·도메인·데이터 종류 같은 다양한 매개변수로 검색할 수 있다 |
| 메시 경험 | `/knowledge-graph` | 관련 데이터 프로덕트의 의미 모델의 메시를 브라우징한다. 의미 관계를 순회해 원하는 데이터 소스를 식별한다 |
| 메시 경험 | `/lineage` | 데이터의 기원과 데이터가 거친 변환에 근거해, 메시 위 데이터 프로덕트 사이의 입력–출력 데이터 계보를 순회한다 |
| 데이터 프로덕트 경험 | `/{dp}/discover` | 소스가 식별되면 문서·데이터 모델·가용한 출력 포트 등 데이터 프로덕트의 발견 가능성 정보 전부에 접근한다 |
| 데이터 프로덕트 경험 | `/{dp}/observe` | 데이터가 얼마나 자주 릴리스되는지, 마지막 릴리스 날짜, 데이터 품질 메트릭 등 데이터 프로덕트의 보증과 메트릭에 실시간으로 접근한다 |
| 데이터 프로덕트 경험 | `/init` | 소스에 연결하고 변환을 돌리고 단일 접근 양식으로 출력을 서빙할 만큼의 인프라를 갖춘 뼈대 데이터 프로덕트를 부트스트랩한다. 이것이 데이터 프로덕트 수명 주기의 시작을 표시한다 |
| 메시 경험 | `/register` | 새 데이터 프로덕트의 초기화 동안 자동으로 메시에 등록된다. 유일한 전역 식별자와 주소를 부여받고 메시와 거버넌스 프로세스에 보이게 된다 |
| 데이터 프로덕트 경험 | `/connect` | 소스가 발견되면 데이터 프로덕트가 그것에 연결해 접근을 얻는다. 이 단계는 소스를 규율하는 접근 통제 정책을 검증한다 |
| 데이터 프로덕트 경험 | `/{dp}/{output}/query`, `/{dp}/{output}/subscribe` | 원천 데이터 프로덕트의 특정 출력 포트에서 데이터를 읽는다 — 풀 기반 질의 모델이든 변경 구독이든 |

## ② 빌드·테스트·배포·실행

- 이 단계의 성격 — **데이터 프로덕트 개발자는 자기 데이터 프로덕트를 짓고·테스트하고·배포하고·
  운영하는 종단 간 책임을 진다. 내가 단순히 "빌드·테스트·배포·실행"이라 부른 단계는 성공적인
  데이터 프로덕트의 모든 필요 구성 요소를 전달하기 위해 데이터 프로덕트 개발자가 수행하는
  연속적이고 반복적인 활동의 계열이다** (10장, p.180).[^dehghani2022]
- 그 산물의 조건이 3장의 여덟 속성으로 되돌려진다 — **이 데이터 프로덕트는 자율적으로 발견
  가능하고·이해 가능하고·신뢰할 만하고·주소 지정 가능하고·상호운용 가능하고·조합 가능하고·
  안전하고·그 자체로 가치 있다** (10장, p.180).[^dehghani2022]
- 표 10-2가 이 단계의 인터페이스 예다 (10장, pp.180–181):[^dehghani2022]

| 플레인 | 인터페이스 | 하는 일 |
|---|---|---|
| 데이터 프로덕트 경험 | `/build` | 데이터 프로덕트의 모든 구성 요소를 컴파일·검증·조합해, 여러 배포 환경에서 돌릴 수 있는 배포 가능 아티팩트로 만든다 |
| 데이터 프로덕트 경험 | `/test` | 데이터 변환의 기능성, 출력 데이터의 무결성, 데이터 버저닝·업그레이드 프로세스에 대한 기대, 데이터 프로파일(기대되는 통계적 특성)에 대한 기대, 테스트 편향 등을 테스트한다 |
| 데이터 프로덕트 경험 | `/deploy` | 지어진 개정본을 한 환경 — 개발자의 로컬 머신, 대상 호스팅 환경의 개발 샌드박스, 프리프로덕션 또는 프로덕션 — 에 배포한다 |
| 데이터 프로덕트 경험 | `/start`, `/stop` | 특정 환경에서 데이터 프로덕트 인스턴스를 돌리거나 멈춘다 |
| 데이터 프로덕트 경험 | `/local-policies` | 암호화·접근·보존·지역성·프라이버시 등 데이터 프로덕트를 규율하는 정책을 지역에서 설정·저작하고, 테스트 동안 검증하고, 데이터 접근 동안 실행하는 것을 플랫폼이 돕는다 |
| 메시 경험 | `/global-policies` | 많은 조직에서 데이터 프로덕트를 규율하는 정책은 전역(연합) 거버넌스 팀이 저작한다. 플랫폼이 전역 정책의 저작과 모든 데이터 프로덕트에 의한 그 적용을 가능하게 한다 |

## 인프라 플레인으로의 위임 경계

- 개발자가 실제로 상대하는 플레인은 하나다 — **데이터 프로덕트 개발자는 대다수의 경우 단순히
  데이터 프로덕트 경험 플레인과 상호작용한다: 단일 데이터 퀀텀을 짓고·배포하고·테스트하는
  것이다. 데이터 프로덕트 경험 플레인은 데이터 프로덕트 구성 요소의 구현을 데이터 인프라
  플레인에 위임한다** (10장, p.181).[^dehghani2022]
- 그럼에도 아래를 알아야 하는 지점이 있다 — **개발자는 데이터 인프라 플레인이 제공하는 것을 감안해
  데이터 프로덕트의 서로 다른 측면과 구성 요소를 이해하고·코딩하고·설정해야 한다. 예컨대 데이터
  프로덕트의 변환 측면을 어떻게 코딩할지의 선택은 데이터 인프라 플레인이 어떤 연산 엔진을
  지원하는지에 달렸다** (10장, p.181, 각주 1은 인프라 플레인이 Prefect나 서버리스 함수로
  오케스트레이션되는 Apache Spark 또는 Apache Beam 태스크를 제공할 수 있다고 예를
  든다).[^dehghani2022]
- 그럼에도 분업의 선은 분명하다 — **그럼에도 데이터 프로덕트 개발자는 자기에게 가용해진 기술을
  써서 변환을 코딩하는 데 집중하고, 다른 모든 구성 요소와 함께 변환의 빌드·배포·실행을 관리하는
  것은 데이터 프로덕트 경험 플레인에 맡긴다. 이 과정에서 데이터 프로덕트 경험 플레인은 변환 실행의
  세부를 데이터 인프라 플레인에 위임한다** (10장, p.181).[^dehghani2022]
- 표 10-3이 그 아래층 인터페이스 예다 (10장, p.183):[^dehghani2022]

| 인터페이스 | 하는 일 |
|---|---|
| `/input-ports` | 데이터 프로덕트의 설계에 따라 데이터를 소비하는 여러 기제 — 이벤트 스트리밍 입력, 원격 데이터베이스 질의, 파일 읽기 등 — 를 제공한다. 데이터가 가용해지면 변환 실행을 촉발한다. 입력 포트 기제는 새 데이터가 가용해질 때 소비 진행을 추적한다 |
| `/output-ports` | 데이터 프로덕트가 제공하는 접근 양식 — 스트림·파일·테이블 등 — 에 따라 데이터를 서빙하는 여러 기제를 제공한다 |
| `/transformations` | 데이터를 변환하는 데 필요한 모든 계산을 돌리는 여러 실행 기제를 제공한다 |
| `/containers` | 데이터 프로덕트와 그것이 요구하는 모든 인프라 자원의 수명 주기를 자율적 단위로 관리한다 |
| `/controls` | 접근 통제·암호화·프라이버시·보존·지역성 같은 다양하고 진화하는 정책을 코드로 설정하고 실행할 수 있게 하는 넓은 범위의 기술을 제공한다 |
| `/storage` | 입력 포트·출력 포트·변환 모두가 데이터와 그 메타데이터(SLO·스키마 등)를 위한 영구·임시 스토리지에 대한 접근을 요구한다. 플랫폼은 서로 다른 스토리지 타입(블롭·관계형·그래프·시계열 등)과 페일오버·복구·복원 같은 모든 운영 능력에 대한 접근을 공급해야 한다 |
| `/models` | 데이터의 의미·구문 스키마 모델을 서술하고·공유하고·연결하는 기제 |
| `/identities` | 메시 위에서 데이터 프로덕트를 유일하게 식별하고 주소 지정하는 기제 |

## ③ 유지·진화·은퇴

- 유지와 진화의 정의 — **데이터 프로덕트의 유지와 진화는 데이터 프로덕트에 대한 지속적 변경을
  포함한다: 변환 로직의 개선, 데이터 모델의 진화, 데이터에 대한 새 접근 양식의 지원, 정책의
  풍부화다. 데이터 프로덕트에 대한 변경은 중단 없는 처리와 데이터 공유를 유지하면서 빌드·테스트·
  배포·실행의 지속적 반복으로 귀결된다** (10장, p.183).[^dehghani2022]
- 플랫폼이 줄여야 할 것이 명시된다 — **플랫폼은 데이터 프로덕트가 **어떻게** 유지되는가의
  간접비를 줄여 **무엇이** 유지되어야 하는가로 옮겨야 한다. 예컨대 새 빌드의 결과가 의미와
  스키마의 변경이라면 데이터 프로덕트 개발자는 단순히 데이터 모델의 변경과 새 모델에 근거한
  데이터의 변환에 집중한다. 스키마의 서로 다른 버전(의미와 구문)이 어떻게 관리되고 데이터와
  연결되고 소비자에게 접근되는가의 복잡성은 플랫폼이 관리한다** (10장, p.183).[^dehghani2022]
  [하위·상위 호환성](../concepts/backward-and-forward-compatibility.md)의 문제를 플랫폼 책임으로
  배정하는 판정이다.
- 진화가 인프라에 닿는 경우와 아닌 경우가 갈린다 — **어떤 경우 데이터 프로덕트의 진화는 기저
  인프라 자원에 아무 영향이 없다. 예컨대 변환 코드의 버그 수정은 단순히 데이터 프로덕트를 다시
  짓고 다시 배포하고 생성된 데이터를 고치기를 요구한다. 다른 경우 진화는 기저 자원에 영향을 준다.
  예컨대 스토리지 벤더를 바꾸는 경우 데이터 프로덕트를 새 환경으로 이전하는 것은 스토리지 자원의
  재할당과 데이터 프로덕트 기저 데이터의 이전을 요구한다** (10장, p.183).[^dehghani2022]
- **모니터링의 대상이 개별과 전체로 갈린다** — 개별 쪽은 **각 데이터 프로덕트의 성능·신뢰성·
  SLO·계산적 정책의 효과성·자원 사용에 근거한 운영 비용을 모니터링하는 것**이고, 메시 쪽은
  **메시 경험 플레인이 메시 전체의 상태에 대한 통찰을 모아 모니터링해야 한다** (10장,
  p.184).[^dehghani2022]
  - 저자가 드는 메시 수준 탐지의 예가 자기 제안의 안티패턴이다 — **너무 많은 소스에서 데이터를
    집계해 많은 이가 쓰면서 병목이 되는 데이터 프로덕트, 곧 마스터 데이터 프로덕트(master data
    products)가 탐지되면 알람을 울리는 것** (10장, p.184).[^dehghani2022] 도메인 소유권 원칙이
    경고하는 집계 도메인 데이터의 비대화를 **플랫폼이 자동 탐지**하게 만드는 자리이고,
    [마스터 데이터 관리](../concepts/master-data-management.md)를 실패 선례로 지목하는 서술과
    같은 계열이다.
- 전역 제어의 경로도 여기서 완성된다 — **데이터 프로덕트의 생애 동안 메시 수준 관리 통제가
  호출되어야 할 때가 있다. 예컨대 잊힐 권리는 메시 수준 전역 통제(global controls)를 통해
  촉발되어, 낱낱의 데이터 프로덕트의 제어 인터페이스로 위임되고, 그 기저 스토리지의 데이터 축출
  기능을 통해 구현될 수 있다** (10장, p.184).[^dehghani2022]
- **데이터 프로덕트도 죽는다 — 그런데 두 가지 죽음이 있다.** 저자가 두 시나리오를 든다 —
  **데이터 프로덕트는 새 데이터 프로덕트로의 이전의 경우, 또는 그것이 생성한 모든 데이터 레코드가
  폐기되어야 하고 새 레코드가 결코 생성되지 않을 경우에 은퇴할 수 있다. 두 경우 모두 플랫폼은
  데이터 프로덕트 개발자가 데이터 프로덕트를 우아하게 은퇴시켜, 그 하류 소비자가 시간을 두고 새
  소스로 이전하거나 스스로 은퇴할 수 있게 한다** (10장, p.184).[^dehghani2022]
  - 그리고 **휴면**이라는 중간 상태가 정의된다 — **누군가 과거 데이터를 쓰고 있는 한 데이터
    퀀텀은 계속 존재한다. 다만 더 이상 어떤 변환도 실행하지 않고 새 데이터도 생산하지 않을 수
    있다. 휴면(dormant) 데이터 프로덕트는 자기 옛 데이터를 계속 서빙하고 자기 정책을 계속 강제하는
    반면, 완전히 은퇴한 데이터 프로덕트는 그저 소멸(extinct)한다** (10장,
    p.184).[^dehghani2022]
- 표 10-4가 이 단계의 인터페이스 예다 (10장, pp.184–185):[^dehghani2022]

| 플레인 | 인터페이스 | 하는 일 |
|---|---|---|
| 데이터 프로덕트 경험 | `/{dp}/status` | 데이터 프로덕트의 상태를 확인한다 |
| 데이터 프로덕트 경험 | `/{dp}/logs`, `/{dp}/traces`, `/{dp}/metrics` | 데이터 퀀텀의 관측 가능성 설계에 따라 로그·추적·메트릭 같은 런타임 관측 정보를 데이터 프로덕트가 내보내는 기제. 메시 계층 모니터링 서비스가 이 데이터를 활용한다 |
| 데이터 프로덕트 경험 | `/{dp}/accesses` | 데이터 프로덕트에 대한 모든 접근의 로그 |
| 데이터 프로덕트 경험 | `/{dp}/controls` | 특정 데이터 퀀텀에 대해 잊힐 권리 같은 고특권 관리 통제를 호출하는 능력 |
| 데이터 프로덕트 경험 | `/{dp}/cost` | 데이터 프로덕트의 운영 비용을 추적한다. 자원 할당과 사용에 근거해 계산할 수 있다 |
| 데이터 프로덕트 경험 | `/migrate` | 데이터 프로덕트를 새 환경으로 이전하는 능력. 데이터 프로덕트 개정을 갱신하는 것은 단순히 빌드와 배포의 함수다 |
| 메시 경험 | `/monitor` | 메시 수준의 여러 모니터링 능력 — 로그·상태·규정 준수 등 |
| 메시 경험 | `/notifications` | 탐지된 메시 이상에 대한 알림과 경보 |
| 메시 경험 | `/global-controls` | 메시 위 데이터 프로덕트 집합에 대해 잊힐 권리 같은 고특권 관리 통제를 호출하는 능력 |

- `/{dp}/cost`가 있다는 사실 자체가 판정이다 — 비용을 데이터 프로덕트 단위로 추적한다는 것은
  4장이 기존 플랫폼의 한계로 지목한 **모놀리식 비용 추정**의 반대편이고,
  [FinOps와 비용 최적화](../concepts/finops-and-cost-optimization.md)의 단위 경제를 데이터
  프로덕트로 잡는다는 뜻이다.

## 데이터 소비자 여정 — ML 모델을 데이터 프로덕트로

- 저자가 고른 예 — **이 절에서 나는 기존 데이터 프로덕트를 소비해 ML 모델을 훈련한 다음 그 ML
  모델을 데이터 프로덕트로 배포해 추론을 하고 새 데이터를 생성하는 예시 데이터 과학자 페르소나에
  집중한다** (10장, p.185).[^dehghani2022] 훈련된 모델은 **monday playlists라는 데이터 프로덕트로
  배포된다** (10장, p.185).[^dehghani2022]
- **ML 모델이 두 플레인의 경계를 흐린다** — **두 플레인의 실체 사이 경계를 명확히 하려는 시도에도
  불구하고 ML 모델은 이 경계를 흐린다. ML 모델은 어느 플레인에도 속할 수 있다** (10장,
  p.185).[^dehghani2022]
  - 운영 쪽 배치 — **ML 모델은 최종 사용자가 요청할 때 온라인으로 추론하기 위해 마이크로서비스로
    배포될 수 있다. 예컨대 새 리스너 등록 동안 리스너가 제공한 정보를 두고 분류기 ML 모델이
    호출되어 사용자 정보를 프로필 분류로 증강한다** (10장, pp.185–186).[^dehghani2022]
  - 분석 쪽 배치 — **대안으로 ML 모델은 데이터 프로덕트의 변환 로직으로 배포될 수 있다. 예컨대
    플레이리스트 추천 ML 모델은 매주 월요일 추론해 새 플레이리스트를 생성하는 데이터 프로덕트로
    배포된다. 그러면 이 데이터는 리스너에게 플레이리스트를 표시하는 운영 서비스로 다시 먹여질 수
    있다** (10장, p.186, 그림 10-5).[^dehghani2022] 저자는 이것을 **ML 모델의 양식적(bimodal)
    배포**라 부른다 (10장, p.186, 그림 10-5).[^dehghani2022]
  - 그럼에도 두 플레인의 차이는 유지된다 — **두 플레인 사이의 긴밀한 통합과 피드백 루프에도
    불구하고 데이터 메시는 각 플레인의 책임과 특성의 차이를 계속 존중한다. 곧 마이크로서비스는
    사업을 돌리기 위해 온라인 요청이나 이벤트에 응답하고, 데이터 프로덕트는 ML 모델 훈련이나
    통찰 생성 같은 하류 분석 용법을 위해 시간 데이터를 큐레이션·변환·공유한다** (10장,
    p.185).[^dehghani2022]
- 여정의 뼈대는 개발자 여정과 같고, 그 이유가 실천의 이름으로 붙는다 — **이 가치 흐름은 기계
  학습을 위한 지속적 전달(continuous delivery for machine learning, CD4ML)의 실천을 따라, 반복
  가능한 프로세스로 빠른 피드백 루프 속에서 모델을 지속적으로 가설화하고·훈련하고·배포하고·
  모니터링하고·개선한다** (10장, p.187, 각주 3은 이 프로세스가 MLOps로도 알려져 있지만 저자는
  소프트웨어·데이터 프로덕트의 지속적 전달과 겹치고 긴밀히 통합되므로 CD4ML 표기를 쓴다고
  밝힌다).[^dehghani2022]
- 갈리는 지점은 셋이다 (10장, p.188):[^dehghani2022]
  - **탐색에서 신경 쓰는 발견 정보의 종류** — **데이터 과학자가 신경 쓰는 발견 가능성 정보의
    종류가 아마도 주된 차이다. 그들은 데이터에 편향(bias)이 있는지와 데이터의 공정성(fairness)을
    평가해야 한다. 이는 원천 데이터 프로덕트 출력 포트를 표집하고 프로파일링해 평가할 수 있다.**
  - **피처가 그 자체로 데이터 프로덕트가 된다** — **훈련 동안 모델 개발자는 훈련 데이터셋이
    변경을 요구한다고 결정하고 상류 데이터 프로덕트 데이터를 피처(features)로 수정할 수 있다.
    이 경우 피처를 생성하는 데이터 변환 파이프라인 자체가 데이터 프로덕트가 된다. 예컨대 monday
    playlist features가 다른 어떤 것과도 마찬가지로 개발되는 데이터 프로덕트가 된다.**
  - **데이터 복사본 대신 처리 시각으로 버저닝한다** — **소스(훈련·테스트) 데이터의 버저닝은
    모든 데이터 프로덕트가 노출하는 처리 시각(processing time) 매개변수를 데이터의 개정으로 쓸 수
    있다 — 데이터의 상태에 유일하고 데이터가 언제 처리·발행되었는지를 가리키는 타임스탬프다.
    이는 모델의 미래 재사용과 재현성을 위해 데이터의 복사본을 유지할 필요를 없앤다. 원천 데이터
    프로덕트가 언제나 과거 데이터를 되찾을 수 있게 하기 때문이다** (각주 4는 오늘날 분석 데이터의
    네이티브 버저닝 부재가 DVC 같은 도구의 사용을 요구한다고 적는다).
- 배포와 실행의 실물 — **배포 동안 모델은 monday playlists 데이터 프로덕트의 변환 코드로 돌 수
  있는 형식으로 패키징되어야 한다(각주 5는 파이썬 모델이 pickle 이진 파일 형식으로 직렬화되는
  예를 든다). 모델 실행 동안 인프라 플레인 변환 엔진은 GPU나 TPU 같은 표적 하드웨어에서 ML
  모델을 실행하는 고유한 필요를 다룰 수 있다** (10장, p.189).[^dehghani2022]
- 모델 모니터링에만 있는 요구도 명시된다 — **모델 모니터링의 고유한 필요 하나는 모델의 효능
  (efficacy)과 리스너가 취하는 모니터링 행동을 관측하는 것이다. 예컨대 모델의 개정이 플레이리스트
  청취 시간 증가, 더 많은 재생, 더 많은 리스너로 이어지는가? 그런 매개변수를 모니터링하는 것은
  운영 플레인의 메트릭 모니터링 능력을 활용할 수 있다** (10장, p.189).[^dehghani2022]
- ML 플랫폼은 별도로 남는다 — **모델 훈련과 추적 과정은 ML 플랫폼 — ML 모델 훈련 파이프라인의
  고유한 필요를 만족시키는 기술과 도구의 플랫폼 — 이 다룰 수 있다. 이 서비스들은 데이터 플랫폼과
  긴밀히 협력하고 통합된다** (10장, p.189).[^dehghani2022] 데이터 메시 플랫폼이 모든 것을 삼키지
  않는다는 경계 선언이다.
