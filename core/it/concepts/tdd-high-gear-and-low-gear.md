하나의 질문: **같은 행동을 도메인 계층에서도 서비스 레이어에서도 테스트할 수 있을 때,
어느 쪽에 쓸 것인가.**

## 물음 — 도메인 테스트를 서비스 레이어로 올려야 하는가

- 물음이 정면이다 — **서비스 레이어를 상대로 소프트웨어를 테스트할 수 있으므로 우리는
  도메인 모델에 대한 테스트가 더 이상 정말로 필요하지 않다. 대신 1장의 도메인 수준 테스트를
  전부 서비스 레이어의 관점에서 다시 쓸 수 있다**
  (5장 §"Should Domain Layer Tests Move to the Service Layer?").[^percival2020]
- 왜 그러고 싶은지가 실무 관찰에서 나온다 — **테스트는 우리가 두려움 없이 시스템을 바꾸도록
  돕기로 되어 있지만, 팀이 도메인 모델을 상대로 너무 많은 테스트를 쓰는 것을 우리는 자주
  본다. 이것은 코드베이스를 바꾸러 왔을 때 수십 개, 심지어 수백 개의 단위 테스트를 갱신해야
  한다는 것을 발견하며 문제를 일으킨다**
  (5장 §"Should Domain Layer Tests Move to the Service Layer?").[^percival2020]
- 테스트의 목적이 재규정된다 — **우리는 우리가 작업하는 동안 시스템의 어떤 성질이 바뀌지
  않도록 강제하는 데 테스트를 쓴다. API가 계속 200을 돌려주는지, 데이터베이스 세션이 계속
  커밋하는지, 주문이 여전히 할당되고 있는지를 확인하는 데 테스트를 쓴다**
  (5장 §"Should Domain Layer Tests Move to the Service Layer?").[^percival2020]
- **그리고 그 목적의 이면이 문제다** — **뒤집힌 면은, 우리가 코드의 설계를 바꾸고 싶으면
  그 코드에 직접 기대는 어떤 테스트든 함께 실패하리라는 것이다**
  (5장 §"Should Domain Layer Tests Move to the Service Layer?").[^percival2020]
- 그래서 서비스 레이어를 상대로 테스트하면 — **이 API를 상대로 테스트하는 것은 우리가
  도메인 모델을 리팩터링할 때 바꿔야 하는 코드의 양을 줄인다. 서비스 레이어만 상대로
  테스트하기로 스스로를 제한하면 우리는 모델 객체의 "비공개" 메서드나 속성과 직접
  상호작용하는 테스트를 하나도 갖지 않게 되고, 그것이 우리를 그것들을 리팩터링하는 데
  더 자유롭게 만든다** (5장 §"Should Domain Layer Tests Move to the Service
  Layer?").[^percival2020]

## 테스트 한 줄은 접착제 한 방울이다

이 장에서 가장 짧은 조문이다 (5장 §"Should Domain Layer Tests Move to the Service
Layer?"):[^percival2020]

> Every line of code that we put in a test is like a blob of glue, holding the system in a
> particular shape. The more low-level tests we have, the harder it will be to change things.

- 이 비유가 이 페이지의 절충을 성립시킨다. 테스트는 자산이자 제약이고, **어느 수준에
  붙이는가**가 무엇을 굳히고 무엇을 남길지를 정한다.
- 같은 진단이 이 KB의 다른 소스에도 있다 —
  [자기 테스트 코드](../concepts/self-testing-code.md)는 테스트를 리팩터링의 담보로 두고 그 담보가
  갖춰야 할 성질을 다루며, [테스트가 코딩을 이끈다](test-to-code.md)는 테스트를 코드의 첫
  사용자로 둔다. **이 소스가 더해 주는 것은 담보에도 층이 있고 층마다 굳히는 것이 다르다는
  것이다.** #hypothesis 세 소스가 서로를 참조한 적은 없다.

## 스펙트럼 — 결합과 설계 피드백의 절충

- 규정 — **"그러면 내 단위 테스트를 전부 다시 써야 하나? 도메인 모델을 상대로 테스트를
  쓰는 것이 잘못인가?"라고 스스로에게 묻고 있을지 모른다. 그 질문에 답하려면 결합과 설계
  피드백 사이의 절충을 이해하는 것이 중요하다**
  (5장 §"On Deciding What Kind of Tests to Write").[^percival2020]
- 그림 5-1이 그 스펙트럼이고, 원본 ditaa 소스에 축의 이름이 그대로 있다
  (5장 §"On Deciding What Kind of Tests to Write"):[^percival2020]

  | | API 테스트 ← | → 도메인 테스트 |
  |---|---|---|
  | 피드백 | 낮음 | 높음 |
  | 변경의 장벽 | 낮음 | 높음 |
  | 커버리지 | 시스템 전반 | 초점이 맞음 |

  가운데가 서비스 레이어 테스트다.
- 높은 피드백이 왜 필요한지 — **익스트림 프로그래밍(XP)은 우리에게 "코드에 귀 기울이라"고
  권한다. 테스트를 쓸 때 우리는 코드가 쓰기 어렵다는 것을 발견하거나 코드 냄새를 알아챌 수
  있다. 이것이 우리에게 리팩터링하고 설계를 재고하라는 방아쇠다**
  (5장 §"On Deciding What Kind of Tests to Write").[^percival2020]
- 그리고 그 피드백이 거리에 반비례한다 — **그러나 우리는 대상 코드와 밀접하게 작업할 때만
  그 피드백을 얻는다. HTTP API에 대한 테스트는 우리 객체의 세밀한 설계에 대해 아무것도
  말해 주지 않는데, 그것이 훨씬 높은 추상 수준에 앉아 있기 때문이다**
  (5장 §"On Deciding What Kind of Tests to Write").[^percival2020]
- 반대쪽 이득 — **반면 우리는 애플리케이션 전체를 다시 쓸 수 있고, URL이나 요청 형식을
  바꾸지 않는 한 우리 HTTP 테스트는 계속 통과할 것이다. 이것은 데이터베이스 스키마 변경
  같은 대규모 변경이 우리 코드를 깨뜨리지 않았다는 확신을 준다**
  (5장 §"On Deciding What Kind of Tests to Write").[^percival2020]

## 도메인 테스트는 살아 있는 문서다

- 스펙트럼의 다른 끝이 주는 것 — **스펙트럼의 다른 끝에서, 1장에서 쓴 테스트는 우리가
  필요로 하는 객체에 대한 이해를 살찌우는 데 도움이 됐다. 그 테스트들은 우리를 말이 되고
  도메인 언어로 읽히는 설계로 안내했다. 우리 테스트가 도메인 언어로 읽힐 때 우리는 우리
  코드가 우리가 풀려는 문제에 대한 직관과 맞는다는 데 편안함을 느낀다**
  (5장 §"On Deciding What Kind of Tests to Write").[^percival2020]
- 그 부산물이 문서다 — **테스트가 도메인 언어로 쓰였기 때문에 그것들은 우리 모델에 대한
  살아 있는 문서로 작용한다. 새 팀원은 이 테스트를 읽고 시스템이 어떻게 작동하는지, 핵심
  개념들이 어떻게 서로 관계되는지 빠르게 이해할 수 있다**
  (5장 §"On Deciding What Kind of Tests to Write").[^percival2020]
  - 1부 맺음에서 같은 말이 반복된다 — **우리 테스트는 살아 있는 문서다: 그것들은 시스템의
    행동을, 우리가 업무 이해관계자와 합의한 규칙들을, 읽기 좋은 코드로 서술한다**
    (7장 §"Part I Recap").[^percival2020]
- **그리고 그 문서는 버려질 수 있다** — **코드의 설계를 개선하고 싶을 때 우리는 이
  테스트들을 대체하거나 지워야 할 것인데, 그것들이 특정 구현에 단단히 결합돼 있기 때문이다**
  (5장 §"On Deciding What Kind of Tests to Write").[^percival2020]
  - 이 문장이 위 [테스트 한 줄은 접착제 한 방울이다](#테스트-한-줄은-접착제-한-방울이다)와
    맞물린다. 접착제를 붙였으면 떼는 것도 정상 절차다. 같은 태도가 어림 규칙 셋째에
    다시 나온다.

## 기어 비유

- 언제 어느 쪽인지가 정해진다 — **대부분의 경우 새 기능을 더하거나 버그를 고칠 때 우리는
  도메인 모델에 광범위한 변경을 할 필요가 없다. 이런 경우에 우리는 더 낮은 결합과 더 높은
  커버리지 때문에 서비스를 상대로 테스트 쓰기를 선호한다**
  (5장 §"High and Low Gear").[^percival2020] 예가 `add_stock` 함수나 `cancel_order`
  기능이다.
- 반대 경우 — **새 프로젝트를 시작할 때나 특별히 고약한 문제에 부딪혔을 때 우리는 더 나은
  피드백과 우리 의도의 실행 가능한 문서를 얻으려고 도메인 모델을 상대로 테스트 쓰기로
  내려간다** (5장 §"High and Low Gear").[^percival2020]
- 비유 — **우리가 쓰는 은유는 기어를 바꾸는 것이다. 여정을 시작할 때 자전거는 관성을
  이길 수 있도록 낮은 기어에 있어야 한다. 일단 출발해 달리기 시작하면 높은 기어로 바꿔 더
  빠르고 효율적으로 갈 수 있다; 그러나 갑자기 가파른 언덕을 만나거나 위험 때문에 속도를
  줄여야 하면 우리는 다시 낮은 기어로 내려가고 속도를 되찾을 수 있을 때까지 그렇게 간다**
  (5장 §"High and Low Gear").[^percival2020]
  - **기어가 방향이 아니라 상태라는 점이 이 비유의 값이다.** 도메인 테스트를 "졸업"하는
    것이 아니라 필요할 때 되돌아간다. 그래서 아래 어림 규칙 셋째가 "작은 핵심을 유지하라"가
    된다.

## 테스트 종류별 어림 규칙 넷

**5장이 남기는 요약이다** (5장 §"Recap: Rules of Thumb for Different Types of Test"
곁글):[^percival2020]

- **기능당 종단 간 테스트 하나를 목표로 하라.** 예컨대 HTTP API를 상대로 쓸 수 있다.
  **목적은 그 기능이 작동한다는 것과 모든 움직이는 부품이 옳게 붙어 있다는 것을 보이는
  것이다.**
- **테스트의 대부분은 서비스 레이어를 상대로 써라.** **이 가장자리에서 가장자리까지
  테스트는 커버리지·실행 시간·효율 사이의 좋은 절충을 제공한다. 각 테스트는 한 기능의
  코드 경로 하나를 다루고 I/O에는 가짜를 쓰는 경향이 있다. 여기가 모든 엣지 케이스와
  업무 로직의 구석구석을 남김없이 다룰 자리다.**
  - 단서가 각주에 있다 — **더 높은 수준에서 테스트를 쓰는 것에 대한 타당한 우려 하나는
    더 복잡한 사용 사례에서 조합 폭발로 이어질 수 있다는 것이다. 이런 경우에는 협력하는
    여러 도메인 객체의 더 낮은 수준 단위 테스트로 내려가는 것이 쓸모 있을 수 있다**
    (5장 각주 1).[^percival2020]
- **도메인 모델을 상대로 쓴 작은 핵심 테스트 모음을 유지하라.** **이 테스트들은 아주 초점이
  맞은 커버리지를 갖고 더 잘 깨지지만, 가장 높은 피드백을 갖는다. 나중에 서비스 레이어의
  테스트가 그 기능을 다루게 되면 이 테스트들을 지우기를 두려워하지 마라.**
- **오류 처리는 기능으로 친다.** **이상적으로 당신 애플리케이션은 진입점(예컨대 Flask)까지
  올라오는 모든 오류가 같은 방식으로 처리되도록 구조화될 것이다. 이것은 기능마다 정상 경로만
  테스트하면 되고, 모든 비정상 경로에 대해 종단 간 테스트 하나를 남겨 두면 된다는 뜻이다
  (그리고 물론 비정상 경로 단위 테스트는 많이).**

## 피라미드가 실제로 뒤집히는 것을 본 경험

- 저자 하나의 회고가 곁글로 있다 — **나는 처음에 Bob의 아키텍처 패턴 전부에 회의적이었지만
  실제 테스트 피라미드를 보고 전향자가 됐다. 도메인 모델링과 서비스 레이어를 구현하고 나면
  단위 테스트가 통합·종단 간 테스트보다 자릿수 하나만큼 많은 단계에 정말로 실제로 도달할 수
  있다. E2E 테스트 빌드가 몇 시간씩 걸리는(사실상 "내일까지 기다려") 곳에서 일해 본 적이
  있는데, 모든 테스트를 몇 분이나 몇 초 안에 돌릴 수 있다는 것이 얼마나 큰 차이를 만드는지
  이루 말할 수 없다** (5장 §"Harry Says: Seeing a Test Pyramid in Action Was a Light-Bulb
  Moment" 곁글).[^percival2020]
- 실제 계수 방법도 함께 인쇄돼 있다. 저자들이 `grep -c test_ test_*.py`로 세어 보인 값이
  단위 15, 통합 8, E2E 2였다 — **나쁘지 않다! 우리는 단위 테스트 15개, 통합 테스트 8개,
  종단 간 테스트 딱 2개를 갖고 있다. 이미 건강해 보이는 테스트 피라미드다**
  (5장 §"How Is Our Test Pyramid Looking?").[^percival2020]
  - 계수 명령이 셸 한 줄이라는 것이 이 관측의 값이다. 계측 도구가 필요 없다.
- 5장의 맺음 — **서비스 레이어가 자리를 잡고 나면 당신은 정말로 테스트 커버리지의 대부분을
  단위 테스트로 옮기고 건강한 테스트 피라미드를 개발할 수 있다**
  (5장 §"Wrap-Up").[^percival2020]
