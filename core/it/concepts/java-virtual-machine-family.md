이 페이지의 질문: **'자바 가상 머신'이라 부르는 자리에 실제로 어떤 제품들이 있었고, 각각
무엇으로 갈렸는가.**

- 출발점의 관찰 — **많은 자바 개발자가 자바 가상 머신을 오라클 JDK의 핫스팟 가상 머신과
  동일시한다.** 그러나 **1996년 초에 JDK 1.0과 함께 등장한 썬 클래식 VM을 시작으로 지금까지
  수많은 전통적이고 훌륭하고 독특한(또는 논란의 여지가 있는) 가상 머신이 나타나고 사라졌다**
  (1장, p.19).[^zhou2024]

## 조상: 클래식 VM과 이그잭트 VM

- 썬 클래식 VM은 **'세계 최초의 상용 자바 가상 머신'** 이며 **자바 코드를 순전히 인터프리터
  방식으로 실행했다** (1장, p.19).[^zhou2024]
  - 구조상의 결정적 제약 — **JIT 컴파일러를 사용하려면 플러그인을 추가하면 됐는데, 플러그인하는
    순간 가상 머신의 실행 시스템 전체가 JIT 컴파일러에 넘어가는 구조였다. 즉, 인터프리터는 더
    이상 동작하지 않았다** (1장, pp.19–20).
  - 그 대가가 자바의 평판을 만들었다 — **당시 인터프리터와 컴파일러는 함께 구동되지 않았기
    때문에 컴파일러를 사용하기 시작하면 실행 빈도 등 컴파일에 따른 득실과 상관없이 '코드
    전체'를 컴파일해야 했다. 그래서 자칫하면 프로그램 응답 속도가 너무 느려지므로 오래 걸리는
    최적화 기법은 적용할 수 없었다.** **'자바 언어는 느리다'는 인상이 개발자들 머릿속에 자리
    잡기 시작한** 이유다 (1장, p.20).
- 이그잭트 VM은 **JDK 1.2와 함께 솔라리스 플랫폼용으로 공개**되었고, **핫스팟 검출, 2단계 JIT
  컴파일러, 컴파일러와 인터프리터 혼합 모드 등을 갖추고 있어 현대적인 고성능 가상 머신의
  프로토타입이라 할 수 있다** (1장, p.20).[^zhou2024]
- 이름의 뜻이 곧 기술이다 — **'정확한 메모리 관리(exact memory management)'** 란 **가상 머신이
  메모리의 특정 위치에 있는 데이터의 구체적인 자료형을 알 수 있다는 뜻**이다. **메모리에
  32비트 정수 123456이 담겨 있다면, 이 데이터가 메모리 주소 123456번지를 가리키는 참조형인지
  또는 값이 123456인 정수형인지 정확하게 구분할 수 있다**는 것이며, **이 정보는 가비지 컬렉션
  시 힙에 존재하는 데이터(객체)가 여전히 사용 중인지 판단하는 전제 조건**이다 (1장,
  p.20).[^zhou2024]
  - 그래서 얻은 것 — **정확한 메모리 관리 덕분에 이그잭트 VM은 핸들에 기초한 클래식 VM의 객체
    검색 방식에서 벗어날 수 있었고, 그 결과 핸들을 거쳐야 하는 간접 검색 부하가 줄어서 실행
    성능이 크게 개선되었다** (1장, p.20).
  - 핸들을 쓸 수밖에 없었던 이유도 적혀 있다 — **가비지 컬렉션 후 객체가 옮겨질 수 있었기
    때문**이며, **이 데이터가 참조형인지 알려 주는 명확한 정보가 없다면 가상 머신은 값이
    123456인 모든 메모리를 654321로 섣불리 변경할 수 없다** (1장, p.20). 핸들과 다이렉트
    포인터의 대비는
    [객체 생성과 메모리 레이아웃](../concepts/object-creation-and-memory-layout.md)에 있다.
- 세 가상 머신의 교대는 이렇게 끝났다 — **이그잭트 VM은 상용으로 활용되기 시작한 지 얼마 안
  되어 썬 외부에서 개발된 핫스팟 VM으로 대체**되었고 **윈도우용과 리눅스용으로는 상용 버전을
  출시조차 하지 못했다.** 반면 **클래식 VM은 JDK 1.2에서도 기본이었고**(핫스팟을 쓰려면
  `-hotspot`), **JDK 1.3에서 기본 자리를 핫스팟에 내주었으며**(클래식을 쓰려면 `-classic`),
  **JDK 1.4부터는 함께 배포되지 못했다** (1장, p.21).[^zhou2024]

## 일인자: 핫스팟

- 핫스팟은 **썬·오라클 JDK와 OpenJDK의 기본 가상 머신이자 가장 널리 사용되는 자바 가상
  머신**이지만 **썬의 순수 혈통이 아니라 롱뷰 테크놀러지스라는 작은 회사에서 태어났고, 심지어
  처음에는 자바 언어용으로 개발된 것도 아니었다** (1장, p.21).[^zhou2024]
  - 계보는 이렇다 — **핫스팟의 선조는 셀프(Self)라는 언어의 실행 효율을 C 언어의 50% 수준까지
    높이고자 개발된 스트롱토크(Strongtalk) 가상 머신**이었고, **이 셀프 언어용 가상 머신의
    역사는 1980년대 중반에 개발된 버클리 스몰토크(Berkeley Smalltalk)까지 거슬러 올라간다.**
    **썬은 1997년 롱뷰 테크놀러지스를 인수하여 핫스팟 VM을 손에 넣었다** (1장, p.21).
- 이름을 만든 기술이 **핫 코드 감지(hot code detection)** 다 — **'컴파일했을 때 효과를 가장 크게
  볼 수 있는 코드 영역'을 런타임에 알아내어 JIT 컴파일러에 알려 주고, JIT 컴파일러가 해당
  코드를 메서드 단위로 컴파일한다** (1장, pp.21–22).[^zhou2024]
  - **메서드가 자주 호출되거나 메서드 안에 시간을 많이 잡아먹는 순환문이 있다면 JIT 컴파일을
    수행해 스택을 치환**하는데, **이처럼 런타임에 스택을 치환하는 기술을 온스택 치환(OSR)**
    이라고 한다 (1장, p.22).
  - 얻는 것은 균형이다 — **컴파일러와 인터프리터가 조화롭게 협력해 프로그램 응답 속도와 실행
    성능 사이의 균형을 잡아 주며**, **JIT 컴파일을 빨리 끝내야 한다는 압박이 크게 줄어든 덕분에
    더 복잡한 최적화 기법을 도입하여 고품질 네이티브 코드를 만들어 낼 수 있게 되었다** (1장,
    p.22).
- 인수 이후의 합병 결과도 기록되어 있다 — **오라클은 썬 인수 후 BEA JRockit의 뛰어난 기능을
  핫스팟에 통합하는 HotRockit 프로젝트를 가동했고, 2014년에 출시된 JDK 8의 핫스팟에는 두 VM이
  이미 통합된 상태였다. 이 과정에서 핫스팟에서 영구 세대가 제거되었고, JRockit의 JMC 모니터링
  도구 등의 기능이 흡수됐다** (1장, p.22).[^zhou2024]

## 모바일과 임베디드

- **자바 ME용 가상 머신의 이름은 CDC-HI(CVM)와 CLDC-HI(몬티 VM)** 이며 **각각 JSR 139와
  JSR 218 명세와 함께 제공되는 참조 구현**이다. **여기서 HI는 HotSpot Implementation의
  약자지만 핫스팟 VM을 직접 계승한 것은 아니다** (1장, pp.22–23).[^zhou2024]
- **자바 ME용 자바 가상 머신은 현재 죽어 있다고 봐도 무방하다 — 자바 ME의 가장 큰 시장인
  스마트폰은 안드로이드와 iOS가 양분해 버렸다.** 임베디드 쪽에서도 **형제뻘인 자바 SE
  임베디드(eJDK)와 직접 경쟁하다가 설 자리를 빼앗겼고**, **오라클은 CDC-HI 프로젝트를 모두
  취소하고 자바 SE 임베디드로 편입시켰다** (1장, p.23).[^zhou2024]
- 그 임베디드용 핫스팟이 무엇을 뺐는지가 흥미롭다 — **자바 SE 임베디드용 자바 가상 머신은
  핫스팟이되 임베디드 환경에 특화되어 클라이언트 컴파일러(C1)와 서버 컴파일러(C2)를 제거했고,
  가비지 컬렉터도 시리얼 컬렉터만 남기고 모두 삭제했다** (1장, p.23).[^zhou2024]
- **CLDC 중 가장 성공적으로 살아남은 제품은 KVM**이며, **효도폰이나 가난한 국가에 수출되는
  피처폰에서는 KVM을 꽤 오래 사용했다. 더 단순하고 자원을 적게 썼기 때문**이다 (1장,
  p.23).[^zhou2024]

## 이인자: JRockit과 J9

- **한때 핫스팟과 함께 '세계 3대 상용 자바 가상 머신'이라 불리던 두 경쟁자가 BEA 시스템의
  JRockit과 IBM의 J9** 이며, **세 가상 머신의 전반적인 성능은 앞서거니 뒤서거니 하며
  발전했다** (1장, pp.23–24).[^zhou2024]
- JRockit은 **2002년 BEA가 어필 버추얼 머신스(Appeal Virtual Machines)로부터 사들인 뒤 서버
  하드웨어와 애플리케이션 동작 시나리오에 중점을 두고 최적화**했다. 그 결과 **프로그램 구동
  시간(startup time)은 우선순위에서 밀렸고, 같은 이유로 JRockit은 인터프리터를 완전히 제거하고
  모든 코드를 JIT 컴파일러로 컴파일하게 했다.** **JRockit의 가비지 컬렉터와 JMC 실패 처리
  스위트 구현은 당시 자바 가상 머신 중 최고 수준**이었으며, **오라클이 BEA를 인수하면서 추가
  개발은 중단되었고 최종 버전은 JDK 6용의 코드명 R28**이다 (1장, p.24).[^zhou2024]
- J9은 **원래 개발 코드명**이었고 **처음 선택된 공식 이름은 'IBM Technology for Java Virtual
  Machine', 줄여서 IT4J**였다. **BEA의 JRockit이 서버 애플리케이션에만 신경 쓴 데 반해 J9의
  목표 시장은 핫스팟과 비슷해 서버와 데스크톱을 모두 고려해 설계된 다용도 가상 머신**이었다
  (1장, p.24).[^zhou2024]
- J9의 특징은 모듈화다 — **핫스팟보다 역할별로 모듈화가 잘 이루어져 있어 가비지 컬렉터, JIT
  컴파일러, 진단 모니터 등의 핵심 구성 요소들이 잘 추상화·캡슐화되어 있고 다른 언어 플랫폼에서
  사용할 수도 있을 정도다.** **IBM은 공통 요소들을 OMR이라는 독립 프로젝트로 만들었고**,
  **2016년부터 OMR과 J9을 점차 오픈 소스로 전환해 현재는 '이클립스 OMR'과 'OpenJ9'이라는
  이름으로 관리되고 있다** (1장, pp.24–25).[^zhou2024]
  - 실용적 권고도 붙는다 — **가상 머신 기술을 공부할 목적으로 소스 코드를 살펴보려면 핫스팟보다
    모듈화가 잘된 OpenJ9이 나은 선택일지도 모르겠다**는 것, 그리고 **OpenJDK 라이브러리들에
    OpenJ9을 결합한 완전한 형태의 JDK가 이클립스 테무린**이라는 것 (1장, p.25).
- 나머지 대기업의 'JDK'에는 선을 긋는다 — **자사 제품을 독자적인 JDK와 가상 머신이라고 주장하는
  거대 기업이 몇 개 있지만, 썬·오라클로부터 라이선스를 구입했거나(HP, SAP 등) OpenJDK
  프로젝트를 개선했을 뿐(알리바바, 트위터 등) 독자적으로 개발하지는 않았다** (1장,
  p.25).[^zhou2024]

## 하드웨어와 통합된 가상 머신

- **리퀴드 VM은 JRockit VE(Virtual Edition)로도 불리며 BEA가 개발한 JRockit의 가상화된
  버전으로, 독자적인 하이퍼바이저 시스템 위에서 직접 실행된다. 다시 말해 리퀴드 VM을 돌리는
  데는 운영 체제가 필요 없다** — **스레드 스케줄링, 파일 시스템, 네트워크 통신 등 필요한 기능을
  제공하는 전용 운영 체제가 포함되어 있다고 봐도 된다** (1장, p.25).[^zhou2024]
  - 이득의 예 — **스레드 스케줄링 시 커널 모드와 사용자 모드 전환이 필요 없다.** 다만 **JRockit
    개발이 중단되면서 리퀴드 VM 프로젝트도 함께 중단되었다** (1장, p.25).
- **어줄 VM은 어줄 시스템스가 핫스팟에 기초해 개발한 자바 가상 머신으로 자사의 베가(Vega)라는
  하드웨어 시스템에서 구동**되며 **인스턴스당 최소 수십 개의 CPU와 수백GB의 메모리를
  관리한다.** **광대한 메모리에서 일시 정지 시간을 제어할 수 있는 가비지 컬렉터(흔히 PGC 또는
  C4 컬렉터라고 부름)** 가 특징이다 (1장, pp.25–26).[^zhou2024]
- **2010년부터 어줄은 무게 중심을 하드웨어에서 소프트웨어로 옮겨 범용 x86 플랫폼용 징
  VM(Zing VM)을 출시**했다. **징의 PGC와 C4 컬렉터(Concurrent Continuously Compacting
  Collector)는 수TB의 자바 힙 메모리를 지원하면서도 일시 정지 시간을 10밀리초 이하로 통제할 수
  있었고, 핫스팟은 JDK 11과 JDK 12에서 ZGC와 셰넌도어 컬렉터를 선보이기 전까지 이 수준에
  도달할 수 없었다** (1장, p.26).[^zhou2024]
  - 징의 다른 기능 둘 — **레디나우(ReadyNow!)는 이전 실행에서 얻은 성능 모니터링 데이터를
    활용해 가상 머신 재시작 후 빠르고 안정적으로 고성능을 내는 상태로 진입시켜 주고**,
    **ZVision·ZVRobot으로는 실행 중 핫스팟 찾기, 객체 할당 모니터링, 락 경합 모니터링 등을 할
    수 있다** (1장, p.26).
- 이 계열이 쇠퇴한 이유도 정리되어 있다 — **독자 하드웨어라서 오픈 소스 커뮤니티의 힘을 빌릴 수
  없었고 가격도 높은 경우가 많았다.** 그래서 **어줄 시스템스는 결국 베가 제품군을 포기하고
  범용 플랫폼용인 징과 줄루(Zulu) 제품군에 모든 노력을 쏟아부었다** (1장, p.26).[^zhou2024]

## 자바 가상 머신이 아닌 도전자들

- **아파치 하모니 가상 머신(정확하게는 하모니의 DRLVM)과 안드로이드 아트(ART) 가상 머신은
  '가상 머신'은 맞지만 '자바 가상 머신'은 아니다.** 그럼에도 **두 가상 머신과 이를 떠받드는
  기술 시스템은 자바 세계에 커다란 영향을 주며 강력한 도전자로 떠올랐다** (1장,
  p.27).[^zhou2024]
- 하모니는 **JDK 5~6과 호환되는 자바 프로그램 운영 플랫폼**이었지만 **TCK 인증을 통과하지
  못했기 때문에 '아파치 JDK'나 '아파치 자바 가상 머신'이라는 이름을 쓰지 못했다.** 규칙 자체가
  이것이다 — **어떤 운영 플랫폼을 "자바 기술 시스템과 호환된다"라고 내세우고 싶다면 TCK
  호환성 테스트를 통과해야 한다** (1장, p.27).[^zhou2024]
  - 뒷이야기 — **아파치 재단이 썬에 TCK 라이선스를 요청했으나 지연되었고, 대립이 첨예해져 화가
    난 아파치 재단이 결국 JCP에서 탈퇴했다. 자바 커뮤니티 역사상 상당히 큰 분열 사건 중
    하나**였다. 하모니는 널리 쓰이지 못했지만 **많은 코드(주로 자바 클래스 라이브러리의 코드)가
    IBM의 JDK 7과 구글 안드로이드 SDK로 흡수되었다** (1장, p.27).
- **달빅 VM(Dalvik VM)은 초기 안드로이드 플랫폼의 핵심 요소**였으며 **《자바 가상 머신 명세》를
  따르지 않아서 자바 클래스 파일을 직접 실행하지는 못한다. 또한 자바 가상 머신에서 흔히 쓰는
  스택 기반 아키텍처 대신 레지스터 기반 아키텍처를 사용한다** (1장, pp.27–28).[^zhou2024]
  - 그럼에도 자바와 뗄 수 없다 — **달빅용 실행 파일인 DEX 파일은 자바 클래스 파일로부터 변환해
    만들 수 있고, 앱 작성 시 자바 언어를 이용하고 자바 API 대부분을 그대로 사용하기도 한다**
    (1장, p.28).
  - 세대 교체 — **안드로이드 2.2부터 달빅에서도 JIT 컴파일러가 제공되어 성능이 크게 개선**
    되었고, **안드로이드 4.4부터는 AOT 컴파일을 지원하는 아트 VM이 달빅을 빠르게 대체**했으며
    **안드로이드 5.0부터는 아트가 달빅을 완전히 대체**했다. **당시 사양이 높지 못하던 모바일
    기기에서 AOT는 JIT보다 높은 성능을 쉽게 낼 수 있었다** (1장, p.28).
- **마이크로소프트가 개발해 인터넷 익스플로러에 탑재한 자바 가상 머신은 윈도우에서만 동작
  했다.** **"한 번 작성하면 어디서든 실행된다"라는 자바의 구호에 맞지는 않았지만, 당시
  윈도우에서 동작하는 가상 머신 중 가장 빨랐다.** **1997년 10월 썬이 상표권 침해와 불공정
  거래로 고소했고, 소송 결과 마이크로소프트는 썬에 2000만 달러를 지불하고 자바 가상 머신 개발을
  중단**했다 (1장, p.28).[^zhou2024]

## 연구용 가상 머신

- **애초부터 주류 시장에서 쓰이거나 상업적 용도로 이용되지 못할 운명을 타고난 자바 가상 머신도
  많다** — **연구 목적이나 특정 기능 또는 아이디어를 검증해 볼 목적으로 만들어졌거나 표준 제시
  목적 등으로 구현된 가상 머신**이다 (1장, p.29).[^zhou2024]
- 저자가 고른 것들 (1장, pp.29–30):[^zhou2024]
  - **KVM** — **K는 '킬로바이트(kilobyte)'를 뜻하며 엄격하고 가볍고 이식성이 좋음을 강조하기
    위해 선택된 단어**다. **하지만 성능은 낮았다.**
  - **JCVM** — **자바 가상 머신의 매우 작은 부분 집합**으로 **스마트카드, SIM 카드, 신용 카드,
    직불 카드 등에 들어갈 정도로 간소화되었고 자바 애플릿을 인터프리터 방식으로 실행한다.**
  - **스쿽 VM(Squawk VM)** — 썬이 개발했고 **상당 부분을 자바 코드로 구현한 임베디드 가상
    머신**이다. **클래스 로더, 바이트코드 검증기, 가비지 컬렉터, 인터프리터, 컴파일러, 스레드
    스케줄링을 모두 자바 언어로 구현**했다.
  - **자바 인 자바(JavaInJava)** — **자바 언어 자체를 자바 언어로 구현하려고 시도한, 이른바
    메타순환(meta-circular) 가상 머신**이다. **메타순환이란 언어 런타임 환경을 해당 언어 자체로
    구현한다는 뜻**이며, **또 다른 호스트 가상 머신에서 실행해야 했고 JIT 컴파일러가 없어서
    인터프리터로만 코드를 실행할 수 있었다.**
  - **맥신 VM(Maxine VM)** — 역시 메타순환이며 **자바 가상 머신을 시작하는 로더만 C 언어로
    작성**했다. **2005년에 시작되어 2019년 말까지 지속**되었고 **클라이언트 모드의 핫스팟 가상
    머신에 가까운 실행 효율을 보여 주었다.**
  - **자이크스 RVM(Jikes RVM)** — **IBM이 자바 가상 머신 기술을 연구하기 위해 시작한
    프로젝트**로 **할라페뇨라 부르기도 한다.**
  - **IKVM.NET** — **마이크로소프트 닷넷 프레임워크 기반으로 구현된 자바 가상 머신**이며
    **클래스 파일을 닷넷 어셈블리로 컴파일하여 어떤 CLI에서든 실행할 수 있게 해 준다.**
