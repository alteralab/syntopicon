이 페이지의 질문: **저장 엔진들은 무엇으로 갈리는가.**

이 책은 완전한 분류 체계를 세우려 하지 않는다. 대신 이후 논의에 실제로 쓰이는 축만 고른다 —
저장 매체와 레이아웃이 그 둘이고, 마지막에 모든 저장 구조를 셋으로 요약하는 변수가 나온다
(1장, pp.7–8).[^petrov2019]

## 메모리 기반과 디스크 기반

- 인메모리 데이터베이스 관리 시스템(때로 main memory DBMS)은 데이터를 주로 메모리에 두고
  디스크는 복구와 로깅에 쓴다. 디스크 기반 DBMS는 데이터 대부분을 디스크에 두고 메모리를
  디스크 내용의 캐시나 임시 저장소로 쓴다. 두 유형 모두 디스크를 어느 정도 쓰지만, 메인
  메모리 데이터베이스는 내용을 거의 전적으로 RAM에 둔다 (1장, p.10).[^petrov2019]
- 메모리 접근은 디스크 접근보다 여러 자릿수 빠르고 메모리 가격이 떨어지면서 주 저장소로
  쓰는 것이 경제적으로 타당해지고 있지만, RAM 가격은 SSD·HDD 같은 영속 저장 장치에 비하면
  여전히 높다 (1장, p.11).[^petrov2019]
- 메인 메모리 시스템이 디스크 기반과 다른 것은 주 저장 매체만이 아니다 — 쓰는 자료 구조,
  조직 방식, 최적화 기법이 함께 다르다 (1장, p.11).[^petrov2019]
- 메모리를 주 저장소로 쓰는 이유는 성능, 상대적으로 낮은 접근 비용, 접근 단위다. 프로그래밍도
  훨씬 단순하다 — 운영체제가 메모리 관리를 추상화해 임의 크기 청크의 할당과 해제로 생각하게
  해 주지만, **디스크에서는 데이터 참조·직렬화 형식·해제된 메모리·단편화를 손으로 관리해야
  한다** (1장, p.11).[^petrov2019]
- 인메모리 데이터베이스의 성장을 막는 주 요인은 RAM의 휘발성(곧 지속성의 부재)과 비용이다.
  RAM 내용은 영속적이지 않으므로 소프트웨어 오류·크래시·하드웨어 장애·정전이 데이터 손실로
  이어질 수 있다. 무정전 전원 장치나 배터리 백업 RAM으로 지속성(durability)을 확보할 수는
  있지만 추가 하드웨어 자원과 운영 전문성이 든다 — 결국 **디스크가 유지하기 쉽고 값이 훨씬
  싸다**는 사실로 귀착한다 (1장, p.11).[^petrov2019]
- 비휘발성 메모리(Non-Volatile Memory, NVM) 기술이 널리 퍼지면 상황이 바뀔 가능성이 있다.
  NVM 저장은 읽기와 쓰기 지연의 비대칭을 줄이거나 (기술에 따라) 아예 없애고, 읽기·쓰기 성능을
  더 끌어올리며, 바이트 단위 주소 지정을 가능하게 한다 (1장, p.11).[^petrov2019]
- 흔한 오해 하나를 저자가 직접 못 박는다. 원문 직인용 (1장, p.12):[^petrov2019]

> It is unfair to say that the in-memory database is the equivalent of an on-disk
> database with a huge page cache […]. Even though pages are cached in memory,
> serialization format and data layout incur additional overhead and do not permit the
> same degree of optimization that in-memory stores can achieve.

- 디스크 기반 데이터베이스는 디스크 접근에 최적화된 특수 저장 구조를 쓴다. 메모리에서는
  포인터를 따라가는 것이 비교적 빠르고 임의 메모리 접근이 임의 디스크 접근보다 훨씬 빠르므로,
  **디스크 기반 저장 구조는 넓고 낮은 트리 형태를 띠는 반면 메모리 기반 구현은 더 넓은 자료
  구조 풀에서 고를 수 있다** (1장, p.12).[^petrov2019]
- 어떤 용도에서는 데이터셋 전체가 메모리에 들어간다고 가정해도 된다 — 학교의 학생 기록, 기업의
  고객 기록, 온라인 상점의 재고처럼 현실 세계의 표현에 의해 크기가 묶이는 데이터셋이다. 각
  레코드가 수 KB를 넘지 않고 개수가 한정된다 (1장, p.12).[^petrov2019]

## 인메모리 저장소의 지속성

- 인메모리 시스템은 지속성을 제공하고 휘발성 데이터의 손실을 막기 위해 디스크에 백업을 둔다.
  지속성 보장 없이 오직 메모리에만 저장하는 데이터베이스도 있으나 이 책의 범위 밖이다 (1장,
  p.11).[^petrov2019]
- 연산이 완료로 간주되기 전에 결과가 **순차 로그 파일**에 쓰여야 한다. 시작 시나 크래시 후에
  로그 전체를 재생하는 일을 피하려고 인메모리 저장소는 백업 사본을 유지하는데, 이 사본은
  정렬된 디스크 기반 구조로 유지되고 그 변경은 대개 비동기(클라이언트 요청과 분리)이며
  I/O 연산 수를 줄이려고 배치로 적용된다 (1장, pp.11–12).[^petrov2019]
- 로그 레코드 배치가 처리되고 나면 백업은 특정 시점의 데이터베이스 스냅숏을 담게 되고, 그
  시점까지의 로그 내용은 버릴 수 있다. **이 과정을 체크포인팅(checkpointing)이라 한다** — 디스크에
  상주하는 데이터베이스를 로그 항목으로 최신에 가깝게 유지하면서도 백업이 갱신될 때까지
  클라이언트를 막지 않아 복구 시간을 줄인다 (1장, p.12).[^petrov2019]

## 행 지향과 열 지향

- 대부분의 데이터베이스는 열(column)과 행(row)으로 이뤄진 테이블에 데이터 레코드 집합을
  저장한다. 필드(field)는 열과 행의 교차점, 곧 어떤 타입의 값 하나다. 같은 열에 속한 필드는
  보통 같은 데이터 타입을 갖는다. 논리적으로 같은 레코드에 속하는(대개 키로 식별되는) 값들의
  모음이 행이다 (1장, p.12).[^petrov2019]
- 분류축은 디스크에 데이터를 어떻게 저장하는가다 — 행 단위인가 열 단위인가. 테이블은 수평
  분할(같은 행에 속한 값들을 함께 저장)될 수도, 수직 분할(같은 열에 속한 값들을 함께 저장)될
  수도 있다 (1장, pp.12–13).[^petrov2019]
- 행 지향(row-oriented)의 사례는 흔하다 — MySQL, PostgreSQL, 그리고 전통적 관계형 데이터베이스
  대부분이다. 열 지향(column-oriented)의 개척자 격 오픈소스 둘은 MonetDB와 C-Store(Vertica의
  오픈소스 전신)다 (1장, p.13).[^petrov2019]
- 행 지향은 레이아웃이 표 형태 표현에 가깝고, 여러 필드가 하나의 레코드를 이루며 키로 유일하게
  식별되는 경우에 잘 맞는다. 한 사용자 레코드를 이루는 모든 필드는 대개 함께 읽히고, 만들 때도
  함께 쓰인다. 동시에 각 필드는 개별적으로 수정할 수 있다 (1장, p.13).[^petrov2019]
- 행 단위로 접근할 때 유용하므로 행 전체를 함께 저장하면 **공간 지역성(spatial locality)** 이
  좋아진다. 디스크 같은 영속 매체는 보통 블록 단위로 접근되므로 블록 하나에 모든 열의 데이터가
  담긴다 — **사용자 레코드 전체가 필요할 때는 좋지만, 여러 레코드의 개별 필드만 읽는 질의(예:
  전화번호만 가져오는 질의)는 다른 필드까지 페이징되므로 더 비싸진다** (1장,
  pp.13–14).[^petrov2019]
- 열 지향은 같은 열의 값을 디스크에 연속으로 저장한다. 서로 다른 열의 값을 별도 파일이나 파일
  세그먼트에 두면 **행 전체를 읽고 질의되지 않은 열의 데이터를 버리는 대신 한 번의 패스로 열을
  읽을 수 있어** 열 단위 질의가 효율적이다 (1장, p.14).[^petrov2019]
- 열 지향은 추세 파악·평균 계산 같은 집계를 하는 분석 워크로드에 잘 맞는다. 논리 레코드에 여러
  필드가 있지만 그중 일부(예: 주가 시세)가 중요도가 다르고 함께 소비되는 경우에 유리하다
  (1장, p.14).[^petrov2019]
- 열 지향에는 비용이 따른다 — 조인·필터링·다중 행 집계에 쓸모 있는 튜플을 재구성하려면 어느
  열의 어느 데이터 지점끼리 연관되는지 식별할 메타데이터가 열 수준에 있어야 한다. 명시적으로
  하면 값마다 키를 들고 있어야 해서 중복이 생기고 저장량이 늘어난다. 일부 열 스토어는 대신
  **암시적 식별자(가상 ID)를 쓰고 값의 위치(오프셋)로 관련 값에 되짚어 매핑한다** (1장,
  p.14).[^petrov2019]
- 최근 몇 해 동안 커지는 데이터셋에 복잡한 분석 질의를 돌리려는 수요 때문에 Apache Parquet,
  Apache ORC, RCFile 같은 열 지향 파일 형식과 Apache Kudu, ClickHouse 같은 열 지향 스토어가
  많이 등장했다 (1장, pp.14–15).[^petrov2019]
- **행과 열의 차이가 저장 방식뿐이라고 말하는 것으로는 부족하다.** 데이터 레이아웃 선택은 열
  스토어가 노리는 일련의 최적화 중 한 단계일 뿐이다 (1장, p.15):[^petrov2019]
  - 같은 열의 여러 값을 한 번에 읽으면 캐시 활용과 계산 효율이 크게 좋아진다. 현대 CPU에서는
    벡터화 명령(SIMD)으로 하나의 명령이 여러 데이터 지점을 처리할 수 있다.
  - 같은 데이터 타입의 값을 함께 저장하면 압축률이 좋아진다. 데이터 타입에 따라 다른 압축
    알고리즘을 골라 각 경우에 가장 효과적인 방법을 쓸 수 있다.
- 선택 기준은 접근 패턴이다 — **읽는 데이터가 레코드 단위로 소비되고(대부분 또는 모든 열을
  요청) 워크로드가 대체로 포인트 질의와 범위 스캔이면 행 지향이 낫고, 스캔이 여러 행에 걸치거나
  열의 부분집합에 대한 집계를 계산하면 열 지향을 고려할 값어치가 있다** (1장,
  p.15).[^petrov2019]

## 와이드 칼럼 스토어는 다른 것이다

- 열 지향 데이터베이스를 BigTable·HBase 같은 **와이드 칼럼 스토어(wide column store)** 와 섞으면
  안 된다. 와이드 칼럼 스토어에서는 데이터가 다차원 맵으로 표현되고, 열들이 컬럼 패밀리(column
  family, 보통 같은 타입의 데이터를 저장)로 묶이며, **각 컬럼 패밀리 안에서는 데이터가 행 단위로
  저장된다.** 이 레이아웃은 키 또는 키의 순열로 조회되는 데이터에 가장 잘 맞는다 (1장,
  p.15).[^petrov2019]
- Bigtable 논문의 정본 예가 Webtable이다 — 특정 시각의 웹 페이지 내용 스냅숏과 속성, 그리고
  페이지들 사이의 관계를 저장한다. 페이지는 뒤집힌 URL로 식별되고, 페이지 내용과 앵커(페이지
  사이 링크) 같은 속성은 스냅숏을 찍은 타임스탬프로 식별된다 (1장, p.15).[^petrov2019]
- 물리 구조는 개념 구조와 다르다. 데이터는 계층형 인덱스를 가진 다차원 정렬 맵에 저장되며,
  각 행은 행 키로 인덱싱된다. 관련된 열들은 컬럼 패밀리로 묶여 **디스크에 따로 저장되고**,
  컬럼 패밀리 안의 각 열은 컬럼 패밀리 이름과 한정자의 조합인 컬럼 키로 식별된다. 컬럼
  패밀리는 타임스탬프별로 여러 버전을 저장한다 (1장, pp.16–17).[^petrov2019]

## 세 변수 — 버퍼링·불변성·순서

- 저장 엔진은 어떤 자료 구조 위에 서지만, 그 자료 구조는 캐싱·복구·트랜잭션성 같은 저장 엔진이
  얹는 것들의 의미를 서술하지 않는다 (1장, p.21).[^petrov2019]
- **저장 구조에는 공통 변수가 셋 있다** — 버퍼링을 쓰는가(쓰지 않는가), 불변 파일을 쓰는가(가변
  파일을 쓰는가), 값을 순서대로 저장하는가(순서 없이 저장하는가). 이 책에서 논의하는 저장
  구조의 구분과 최적화 대부분이 이 셋 중 하나와 관계있다 (1장, p.21).[^petrov2019]
- **버퍼링(buffering)** — 저장 구조가 디스크에 놓기 전에 일정량의 데이터를 메모리에 모으기로
  하는가. 물론 모든 온디스크 구조는 어느 정도 버퍼링을 쓴다(디스크 전송의 최소 단위가 블록이고
  꽉 찬 블록을 쓰는 편이 낫다). 여기서 말하는 것은 **회피 가능한 버퍼링**, 곧 구현자가 하기로
  선택하는 버퍼링이다 (1장, pp.21–22).[^petrov2019]
- **가변성(mutability, 또는 불변성)** — 저장 구조가 파일의 일부를 읽어 갱신한 뒤 같은 위치에 다시
  쓰는가. **불변 구조는 추가 전용(append-only)** 이며, 한 번 쓰인 파일 내용은 수정되지 않고 변경은
  파일 끝에 덧붙는다. 불변성을 구현하는 다른 방법으로 쓰기 시 복사(copy-on-write)가 있는데,
  갱신된 레코드를 담은 페이지를 원래 위치가 아니라 파일의 새 위치에 쓴다 (1장,
  p.22).[^petrov2019]
  - 흔히 LSM과 B-트리의 구분을 불변 대 인플레이스 갱신으로 그리지만, **B-트리에서 영감을 받았으면서
    불변인 구조(예: Bw-트리)도 있다.**
- **순서(ordering)** — 디스크 페이지 안에서 데이터 레코드가 키 순서로 저장되는가. 곧 가깝게 정렬되는
  키들이 디스크의 연속 세그먼트에 저장되는가. **순서는 개별 레코드를 찾는 것을 넘어 레코드 범위를
  효율적으로 스캔할 수 있는지를 결정하는 경우가 많다.** 순서 없이(대개 삽입 순서로) 저장하면 쓰기
  시점의 최적화 여지가 열린다 (1장, p.22).[^petrov2019]
