하나의 질문: **무엇이든 무엇과든 연결될 수 있는 데이터를 어떤 구조로 표현해야 하고, 그
표현의 두 계열은 무엇이 같고 무엇이 다른가.**

## 언제 그래프로 가는가

- 판정 기준이 관계의 종류에 있다 — **관계의 종류는 데이터 모델을 가르는 중요한 구별 특징이다.
  애플리케이션이 대부분 일대다 관계(트리 구조 데이터)를 갖고 레코드 사이의 다른 관계가 적으면
  문서 모델이 적절하다** (3장, p.84).[^kleppmann2026]
- **그러나 데이터에서 다대다 관계가 매우 흔하다면? 관계형 모델은 다대다 관계의 단순한 경우를
  다룰 수 있지만, 데이터 안의 연결이 더 복잡해질수록 그 데이터를 그래프(graph)로 모델링하기
  시작하는 것이 더 자연스러워진다** (3장, p.84).[^kleppmann2026]

## 정점과 간선

- **그래프는 두 종류의 객체로 이뤄진다 — 정점(vertices, 노드nodes 또는 엔티티entities라고도
  한다)과 간선(edges, 관계relationships 또는 아크arcs라고도 한다)이다** (3장,
  p.84).[^kleppmann2026]
- **많은 종류의 데이터를 그래프로 모델링할 수 있다.** 전형적 예 셋 (3장, p.84):[^kleppmann2026]
  - **소셜 그래프(social graphs)** — **정점은 사람이고, 간선은 어떤 사람들이 서로 아는지를
    가리킨다.**
  - **웹 그래프(the web graph)** — **정점은 웹 페이지이고, 간선은 다른 페이지로 가는 HTML
    링크를 가리킨다.**
  - **도로 또는 철도 네트워크** — **정점은 교차점이고, 간선은 그 사이의 도로나 철도 노선을
    나타낸다.**
- **잘 알려진 알고리즘이 이 그래프들 위에서 동작할 수 있다 — 예컨대 지도 내비게이션 앱은 도로
  네트워크에서 두 지점 사이의 최단 경로를 찾고, PageRank는 웹 그래프에서 웹 페이지의 인기도,
  따라서 검색 결과에서의 순위를 정하는 데 쓰일 수 있다** (3장, p.84).[^kleppmann2026]

## 인접 리스트와 인접 행렬

- **그래프는 여러 방식으로 표현될 수 있다. 인접 리스트(adjacency list) 모델에서는 각 정점이
  간선 하나 거리에 있는 이웃 정점들의 ID를 저장한다. 대안으로 인접 행렬(adjacency matrix), 즉
  각 행과 열이 정점에 대응하는 2차원 배열을 쓸 수 있는데, 행 정점과 열 정점 사이에 간선이 없으면
  값이 0이고 있으면 1이다** (3장, p.85).[^kleppmann2026]
- 용도가 갈린다 — **인접 리스트는 그래프 순회에 좋고, 행렬은 기계 학습에 좋다** (3장,
  p.85).[^kleppmann2026] 행렬 쪽 표현은
  [데이터프레임과 배열](../concepts/dataframes-and-arrays.md)이 다룬다.

## 한 그래프에 여러 종류를 담기

- **앞의 예에서는 그래프의 모든 정점이 같은 종류의 것(각각 사람·웹 페이지·도로 교차점)을
  나타낸다. 그러나 그래프는 그런 동질적 데이터에 국한되지 않는다. 그래프의 똑같이 강력한 용도는
  완전히 다른 종류의 객체들을 하나의 데이터베이스에 저장하는 일관된 방법을 제공하는 것이다**
  (3장, p.85).[^kleppmann2026]
- 실물 둘 (3장, p.85):[^kleppmann2026]
  - **페이스북은 여러 종류의 정점과 간선을 가진 단일 그래프를 유지한다. 정점은 사람·장소·
    이벤트·체크인·사용자가 남긴 댓글을 나타내고, 간선은 어떤 사람들이 서로 친구인지, 어떤
    체크인이 어느 장소에서 일어났는지, 누가 어떤 글에 댓글을 달았는지, 누가 어떤 이벤트에
    참석했는지 등을 가리킨다.**
  - **검색 엔진은 지식 그래프(knowledge graphs)를 써서 검색 질의에 자주 나타나는 엔티티 —
    조직·사람·장소 같은 것 — 에 관한 사실을 기록한다. 이 정보는 웹사이트의 텍스트를 크롤링하고
    분석해 얻으며, 위키데이터 같은 어떤 웹사이트는 구조화된 형태로 그래프 데이터를 발행하기도
    한다.**
- 이 장이 다루는 두 계열 — **그래프는 데이터를 구조화하고 질의하는 서로 다르지만 관련된 여러
  방법을 제공한다. 이 절에서 우리는 속성 그래프 모델(property graph model, Neo4j·Memgraph·
  KùzuDB 등이 구현한다)과 트리플 스토어 모델(triple store model, Datomic·AllegroGraph·
  Blazegraph 등이 구현한다)을 논한다. 이 모델들은 표현할 수 있는 것이 꽤 비슷하며, 어떤 그래프
  데이터베이스(아마존 넵튠 같은)는 둘 다 지원한다** (3장, p.85).[^kleppmann2026]
- 예시로 쓰는 그래프도 소개된다 — **소셜 네트워크나 계보 데이터베이스에서 가져왔을 법한 것으로,
  아이다호 출신 루시와 프랑스 생로 출신 알랭 두 사람을 보여 준다. 그들은 결혼해 런던에 살고
  있다. 각 사람과 각 장소가 정점으로, 그들 사이의 관계가 간선으로 표현된다** (3장, p.85, 그림
  3-6).[^kleppmann2026]

## 속성 그래프

- **속성 그래프(property graph, 레이블 속성 그래프labeled property graph라고도 한다) 모델에서
  각 정점은 다음으로 이뤄진다** (3장, p.86):[^kleppmann2026]
  - **고유 식별자**
  - **이 정점이 나타내는 객체의 종류를 서술하는 레이블(문자열)**
  - **나가는 간선의 집합**
  - **들어오는 간선의 집합**
  - **속성의 모음(키-값 쌍)**
- **각 간선은 다음으로 이뤄진다** (3장, p.86):[^kleppmann2026]
  - **고유 식별자**
  - **간선이 시작하는 정점(꼬리 정점tail vertex)**
  - **간선이 끝나는 정점(머리 정점head vertex)**
  - **두 정점 사이 관계의 종류를 서술하는 레이블**
  - **속성의 모음(키-값 쌍)**
- **그래프 저장소를 관계형 테이블 둘 — 정점용 하나와 간선용 하나 — 로 이뤄진 것으로 생각할 수
  있다.** 그 스키마는 이렇게 생겼다(PostgreSQL의 `jsonb` 데이터 타입으로 속성을 저장한다) (3장,
  p.87, 예제 3-3):[^kleppmann2026]

  ```sql
  CREATE TABLE vertices (
      vertex_id   integer PRIMARY KEY,
      label       text,
      properties  jsonb
  );

  CREATE TABLE edges (
      edge_id     integer PRIMARY KEY,
      tail_vertex integer REFERENCES vertices (vertex_id),
      head_vertex integer REFERENCES vertices (vertex_id),
      label       text,
      properties  jsonb
  );

  CREATE INDEX edges_tails ON edges (tail_vertex);
  CREATE INDEX edges_heads ON edges (head_vertex);
  ```

- **간선마다 머리 정점과 꼬리 정점이 저장된다. 어떤 정점의 들어오는 간선 집합이나 나가는 간선
  집합을 원하면 edges 테이블을 각각 head_vertex나 tail_vertex로 질의하면 된다** (3장,
  p.87).[^kleppmann2026]
- **이 모델의 중요한 측면들** (3장, p.87):[^kleppmann2026]
  - **어떤 정점이든 다른 어떤 정점과도 잇는 간선을 가질 수 있다. 어떤 종류의 것들이 연관될 수
    있는지 없는지를 제한하는 스키마가 없다.**
  - **어떤 정점이 주어지든 그 들어오는 간선과 나가는 간선을 효율적으로 찾을 수 있고, 따라서
    그래프를 앞뒤 양방향으로 순회할 수 있다(즉 정점 사슬을 따라 경로를 따라간다). 그래서 위
    예제가 tail_vertex와 head_vertex 열 양쪽에 인덱스를 갖는 것이다.**
  - **서로 다른 종류의 정점과 관계에 서로 다른 레이블을 씀으로써, 깔끔한 데이터 모델을 유지하면서
    여러 종류의 정보를 하나의 그래프에 저장할 수 있다.**
- 관계형 조인 테이블과의 관계 — **edges 테이블은 다대다 연관 테이블 또는 조인 테이블과 비슷하되,
  여러 종류의 관계가 같은 테이블에 저장될 수 있도록 일반화된 것이다. 레이블과 속성에 인덱스가
  있을 수도 있어 특정 속성을 가진 정점이나 간선을 효율적으로 찾을 수 있다** (3장,
  p.87).[^kleppmann2026] 조인 테이블 쪽은
  [정규화와 비정규화](../concepts/normalization-and-denormalization.md)에 있다.

## 그래프 모델의 한계와 유연성

- 저자들이 상자로 한계를 하나 명시한다 — **그래프 모델의 한계는 간선이 오직 두 정점만 서로
  연관 지을 수 있다는 것이다. 반면 관계형 조인 테이블은 한 행에 여러 외래 키 참조를 둠으로써
  3자 관계나 더 높은 차수의 관계를 표현할 수 있다. 그런 관계는 조인 테이블의 각 행에 대응하는
  추가 정점과 그 정점을 오가는 간선을 만들거나, 하이퍼그래프(hypergraph)를 씀으로써 그래프에서
  표현될 수 있다** (3장, p.88).[^kleppmann2026]
- 그 대신 얻는 것이 유연성이다 — 예시 그래프는 **전통적 관계형 스키마로 표현하기 어려울 몇 가지를
  보여 준다 — 나라마다 다른 종류의 지역 구조(프랑스에는 데파르트망과 레지옹이 있고 미국에는
  카운티와 주가 있다), 나라 안의 나라 같은 역사적 특이 사항, 그리고 데이터 세밀도의 차이(루시의
  현재 거주지는 도시로 특정되지만 출생지는 주 수준으로만 특정된다)** (3장,
  p.88).[^kleppmann2026]
- 확장 시나리오도 든다 — **루시와 알랭, 또는 다른 사람들에 대한 다른 많은 사실을 포함하도록
  그래프를 확장하는 것을 상상할 수 있다. 예컨대 그래프로 그들이 가진 음식 알레르기를 나타내고
  (알레르겐마다 정점을 하나씩 도입하고 사람과 알레르겐 사이에 간선을 두어), 알레르겐을 어떤
  음식이 어떤 물질을 담는지 보여 주는 정점 집합과 연결할 수 있다. 그러면 각 사람이 무엇을 먹어도
  안전한지 알아내는 질의를 쓸 수 있다** (3장, p.88).[^kleppmann2026]
- 그래서 판정이 이렇다 — **그래프는 진화성(evolvability)에 좋다. 애플리케이션에 기능을 더할 때
  그래프는 애플리케이션의 데이터 구조 변화를 수용하도록 쉽게 확장될 수 있다** (3장,
  p.88).[^kleppmann2026] 진화성이라는 요건 자체는
  [유지보수성](../concepts/maintainability.md)에 있다.

## 트리플 스토어

- **트리플 스토어 모델은 속성 그래프 모델과 대체로 동등하며, 같은 발상을 서술하는 데 다른 낱말을
  쓴다. 그럼에도 논할 가치가 있는데, 트리플 스토어를 위한 여러 도구와 언어가 애플리케이션을
  만드는 도구 상자에 값진 보탬이 될 수 있기 때문이다** (3장, p.92).[^kleppmann2026]
- **트리플 스토어에서 모든 정보는 매우 단순한 세 부분 진술 — (주어subject, 술어predicate,
  목적어object) — 의 형태로 저장된다. 예컨대 (Jim, likes, bananas)라는 트리플에서 Jim은 주어,
  likes는 술어(동사), bananas는 목적어다** (3장, p.92).[^kleppmann2026]
- 저자들이 정확성을 위해 상자를 단다 — **정확히 말하면, 트리플 유사 데이터 모델을 제공하는
  데이터베이스는 흔히 각 튜플에 추가 메타데이터를 저장해야 한다. 예컨대 AWS 넵튠은 각 트리플에
  그래프 ID를 더해 쿼드(quads, 4-튜플)를 쓰고, Datomic은 각 트리플을 트랜잭션 ID와 삭제를
  나타내는 불리언으로 확장한 5-튜플을 쓴다. 이 데이터베이스들이 기본적인 주어-술어-목적어 구조를
  유지하므로 이 책은 그럼에도 그것들을 트리플 스토어라 부른다** (3장, p.92).[^kleppmann2026]
- 속성 그래프와의 대응 — **트리플의 주어는 그래프의 정점에 해당한다. 목적어는 둘 중 하나다**
  (3장, pp.92–93):[^kleppmann2026]
  - **문자열이나 수 같은 원시 데이터 타입의 값.** 그 경우 **트리플의 술어와 목적어는 주어 정점에
    있는 속성의 키와 값에 해당한다.** 예컨대 **(lucy, birthYear, 1989)는 속성
    `{"birthYear": 1989}`를 가진 정점 lucy와 같다.**
  - **그래프의 다른 정점.** 그 경우 **술어는 그래프의 간선이고, 주어는 꼬리 정점, 목적어는 머리
    정점이다.** 예컨대 **(lucy, marriedTo, alain)에서 주어와 목적어 lucy와 alain은 둘 다 정점이고,
    술어 marriedTo는 그들을 잇는 간선의 레이블이다.**
- 트리플을 적는 표기 하나가 **Notation3(N3)의 부분집합인 Turtle** 이다. 세미콜론으로 같은
  주어에 대해 여러 가지를 말하면 꽤 읽기 좋아진다 (3장, p.93, 예제
  3-8):[^kleppmann2026]

  ```turtle
  @prefix : <urn:example:>.
  _:lucy     a :Person;   :name "Lucy";          :bornIn _:idaho.
  _:idaho    a :Location; :name "Idaho";         :type "state";   :within _:usa.
  _:usa      a :Location; :name "United States"; :type "country"; :within _:namerica.
  _:namerica a :Location; :name "North America"; :type "continent".
  ```

- 표기의 읽는 법 — **그래프의 정점은 `_:someName`으로 쓴다. 그 이름은 이 파일 바깥에서는 아무
  의미가 없다 — 어느 트리플이 같은 정점을 가리키는지 알 수 없기 때문에 존재할 뿐이다. 술어가
  간선을 나타낼 때 목적어는 정점이고(`_:idaho :within _:usa`처럼), 술어가 속성일 때 목적어는
  문자열 리터럴이다(`_:usa :name "United States"`처럼)** (3장, p.93).[^kleppmann2026]

## RDF와 시맨틱 웹

- **Turtle 언어는 사실 자원 기술 프레임워크(Resource Description Framework, RDF)로 데이터를
  인코딩하는 한 방법이며, RDF는 시맨틱 웹을 위해 설계된 데이터 모델이다. RDF 데이터는 (더 장황하게)
  XML을 포함한 다른 방식으로도 인코딩될 수 있다. Apache Jena 같은 도구가 서로 다른 RDF 인코딩
  사이를 자동으로 변환할 수 있다** (3장, p.94).[^kleppmann2026]
- **RDF에는 몇 가지 특이한 점이 있는데 인터넷 전역의 데이터 교환을 위해 설계됐기 때문이다.
  트리플의 주어·술어·목적어는 흔히 URI다. 예컨대 술어가 그냥 WITHIN이나 LIVES_IN이 아니라
  `<http://my-company.com/namespace#within>` 같은 URI일 수 있다** (3장,
  p.95).[^kleppmann2026]
- **이 설계의 근거는, 내 데이터를 다른 사람의 데이터와 결합할 수 있어야 하며, 그들이 within이나
  lives_in이라는 낱말에 다른 의미를 붙이더라도 그들의 술어는 실제로는
  `<http://other.org/foo#within>`과 `<http://other.org/foo#lives_in>`이므로 충돌이 나지
  않는다는 것이다** (3장, p.95).[^kleppmann2026]
- **URL `<http://my-company.com/namespace>`가 반드시 무언가로 해석돼야 하는 것은 아니다 —
  RDF의 관점에서 그것은 그저 네임스페이스일 뿐이다. `http://` URL과의 잠재적 혼동을 피하려고
  이 절의 예는 `urn:example:within` 같은 해석 불가능한 URI를 쓴다. 다행히 이 접두사는 파일
  맨 위에 한 번만 특정하고 그다음엔 잊어버리면 된다** (3장, p.95).[^kleppmann2026]
- 저자들이 상자로 시맨틱 웹의 결말을 정리한다 — **트리플 스토어에 대한 연구·개발 노력의 일부는
  시맨틱 웹(Semantic Web)에 자극받았다. 시맨틱 웹은 데이터를 사람이 읽을 수 있는 웹 페이지로만이
  아니라 표준화된 기계 판독 가능 형식으로도 발행함으로써 인터넷 전역의 데이터 교환을 촉진하려던
  2000년대 초의 노력이다** (3장, p.94).[^kleppmann2026]
  - 결말 — **원래 구상된 시맨틱 웹은 성공하지 못했지만, 그 프로젝트의 유산은 예컨대 JSON-LD 같은
    링크드 데이터 표준, 생의학에서 쓰이는 온톨로지, 페이스북의 오픈 그래프 프로토콜(링크 언펄링에
    쓰인다), 위키데이터 같은 지식 그래프, 그리고 Schema.org가 유지하는 구조화 데이터용 표준
    어휘에 살아 있다** (3장, p.94).[^kleppmann2026]
  - 저자들의 결론 — **트리플 스토어는 원래 유스케이스 바깥에서 쓰임새를 찾은 또 하나의 시맨틱 웹
    기술이다. 시맨틱 웹에 아무 관심이 없더라도 트리플은 애플리케이션의 좋은 내부 데이터 모델이 될
    수 있다** (3장, p.94).[^kleppmann2026]

## 원천 시스템이 그래프일 때

- 왜 문서 저장소로는 안 되는가 — **예컨대 문서 데이터베이스를 써서 각 사용자의 속성을 서술하는
  문서를 하나씩 저장할 수 있다. 소셜 미디어 맥락에서 직접 연결된 사용자의 ID를 담은 연결
  배열 요소를 더할 수 있다. 사용자가 가진 직접 연결의 수를 정하기는 꽤 쉽지만, 두 직접 연결을
  건너서 몇 명의 사용자에게 도달할 수 있는지 알고 싶다고 하자. 복잡한 코드를 써서 이 질문에
  답할 수 있지만 각 질의가 느리게 돌고 상당한 자원을 소비할 것이다. 문서 저장소는 그냥 이
  유스케이스에 최적화돼 있지 않다** (5장, p.172).[^reis2022]
- 그래서 데이터 엔지니어가 골라야 하는 것 셋 — **이는 구조화된 릴레이션·문서·비정형 데이터를
  다루는 데 더 익숙할 수 있는 데이터 엔지니어에게 고유한 도전을 제기한다. 엔지니어는 다음 중
  무엇을 할지 골라야 한다** (5장, p.173):[^reis2022]
  - **원천 시스템 그래프 데이터를 기존의 선호 패러다임 중 하나로 매핑한다**
  - **원천 시스템 안에서 그래프 데이터를 분석한다**
  - **그래프 특화 분석 도구를 채택한다**
- 재인코딩이라는 선택지 — **그래프 데이터는 관계형 데이터베이스의 행으로 다시 인코딩될 수 있고,
  이는 분석 유스케이스에 따라 적합한 해법일 수 있다. 트랜잭션 그래프 데이터베이스도 분석용으로
  설계돼 있지만 큰 질의는 프로덕션 시스템에 과부하를 줄 수 있다. 현대의 클라우드 기반 그래프
  데이터베이스는 방대한 양의 데이터에 대한 읽기 중심 그래프 분석을 지원한다** (5장,
  p.173).[^reis2022]
