하나의 질문: **두 트랜잭션이 같은 값을 읽고 고쳐 되쓸 때 한쪽 수정이 사라지는 것을 어떻게
막는가.**

## 갱신 손실이란 무엇인가

- **read-committed와 스냅샷 격리 수준의 논의는 주로 동시 쓰기가 있을 때 읽기 전용 트랜잭션이
  무엇을 볼 수 있는가에 대한 보장에 초점을 맞췄다. 두 트랜잭션이 동시에 쓰는 문제는 더티
  쓰기(dirty write)라는 한 종류의 쓰기-쓰기 충돌만 다뤘다** (8장,
  p.299).[^kleppmann2026]
- **동시에 쓰는 트랜잭션 사이에는 다른 흥미로운 종류의 충돌이 여럿 일어날 수 있다. 그중 가장
  잘 알려진 것이 갱신 손실(lost update) 문제이며, 그림 8-1의 두 동시 카운터 증가 예가
  그것**이다 (8장, p.299).[^kleppmann2026]
- 정의 — **갱신 손실 문제는 애플리케이션이 데이터베이스에서 값을 읽어 수정하고 수정된 값을
  되쓸 때(앞서 언급한 읽기-수정-쓰기 사이클) 일어날 수 있다. 두 트랜잭션이 이것을 동시에 하면
  두 번째 쓰기가 첫 수정을 포함하지 않으므로 수정 중 하나가 유실될 수 있다.**(나중 쓰기가 앞선
  쓰기를 뭉갠다(clobbers)고 말하기도 한다.) (8장, p.299).[^kleppmann2026]
- 이 패턴이 나타나는 시나리오 셋 (8장, p.299):[^kleppmann2026]
  - **카운터를 증가시키거나 계좌 잔액을 갱신하기**(현재 값을 읽고 새 값을 계산해 갱신된 값을
    되써야 한다)
  - **복잡한 값에 국소적 변경을 가하기** — 예컨대 **JSON 문서 안의 리스트에 원소를
    추가하기**(문서를 파싱하고 변경을 가하고 수정된 문서를 되써야 한다)
  - **두 사용자가 같은 위키 페이지를 동시에 편집하고 각자 페이지 전체 내용을 서버로 보내
    저장해 현재 데이터베이스에 있는 것을 무엇이든 덮어쓰기**

## 원자적 쓰기 연산

- **많은 데이터베이스가 원자적 갱신 연산을 제공해 애플리케이션 코드에서 읽기-수정-쓰기 사이클을
  구현할 필요를 없앤다. 코드를 그 연산으로 표현할 수 있다면 대개 최선의 해법이다.** 예컨대
  `UPDATE counters SET value = value + 1 WHERE key = 'foo';` 는 **대부분의 관계형
  데이터베이스에서 동시성에 안전하다** (8장, p.300).[^kleppmann2026]
- 비슷하게 **몽고DB(MongoDB) 같은 문서 데이터베이스는 JSON 문서의 일부를 국소적으로 수정하는
  원자적 연산을 제공하고, 레디스(Redis)는 우선순위 큐 같은 자료 구조를 수정하는 원자적 연산을
  제공한다. 모든 쓰기를 원자적 연산으로 쉽게 표현할 수 있는 것은 아니다** — 예컨대 **위키
  페이지 갱신은 임의의 텍스트 편집을 수반**하며 그것은 CRDT나 운영 변환 계열 알고리즘으로
  다룰 수 있다. **그러나 원자적 연산을 쓸 수 있는 상황에서는 대개 그것이 최선의 선택이다**
  (8장, p.300).[^kleppmann2026]
- 구현 — **원자적 연산은 보통 객체를 읽을 때 그 객체에 배타적 잠금을 걸어 갱신이 적용될
  때까지 다른 트랜잭션이 읽지 못하게 하는 방식으로 구현된다. 다른 선택지는 모든 원자적 연산을
  단일 스레드에서 실행하도록 강제하는 것**이다 (8장, p.300).[^kleppmann2026]
- 함정 — **ORM 프레임워크는 데이터베이스가 제공하는 원자적 연산 대신 안전하지 않은
  읽기-수정-쓰기 사이클을 수행하는 코드를 실수로 쓰기 쉽게 만든다. 이는 테스트로 찾기 어려운
  미묘한 버그의 원천일 수 있다** (8장, p.300).[^kleppmann2026]

## 명시적 잠금

- **데이터베이스의 내장 원자적 연산이 필요한 기능을 제공하지 않을 때 갱신 손실을 막는 또 다른
  선택지는 애플리케이션이 갱신할 객체를 명시적으로 잠그는 것이다. 그러면 애플리케이션이
  읽기-수정-쓰기 사이클을 수행할 수 있고, 다른 트랜잭션이 같은 객체를 동시에 갱신하거나 잠그려
  하면 첫 읽기-수정-쓰기 사이클이 완료될 때까지 기다리도록 강제된다** (8장,
  p.300).[^kleppmann2026]
- 책의 예는 **여러 플레이어가 같은 말을 동시에 움직일 수 있는 멀티플레이어 게임**이다.
  **이 경우 원자적 연산으로는 충분하지 않을 수 있는데, 애플리케이션이 플레이어의 이동이 게임
  규칙을 따르는지도 확인해야 하고 그 로직은 데이터베이스 질의로 온당하게 구현할 수 없기
  때문이다. 대신 두 플레이어가 같은 말을 동시에 움직이지 못하도록 잠금을 쓸 수 있다** (8장,
  p.300).[^kleppmann2026]
- 예제 8-1이 그 형태이며 — `FOR UPDATE`로 찾는다 — **이 절이 데이터베이스에게 이 질의가
  돌려준 모든 행을 잠그라고 지시한다** (8장, p.301):[^kleppmann2026]

  ```sql
  BEGIN TRANSACTION;

  SELECT * FROM figures
    WHERE name = 'robot' AND game_id = 222
    FOR UPDATE;

  -- Check whether move is valid, then update the position
  -- of the piece that was returned by the previous SELECT.
  UPDATE figures SET position = 'c4' WHERE id = 1234;

  COMMIT;
  ```

- 대가 둘 (8장, p.301):[^kleppmann2026]
  - **동작하기는 하지만 제대로 하려면 애플리케이션 로직을 신중히 생각해야 한다. 코드 어딘가에
    필요한 잠금을 추가하는 것을 잊어 경쟁 조건을 들이기 쉽다.**
  - **여러 객체를 잠그는 것은 교착 상태(deadlock)의 위험을 안고 있다 — 둘 이상의 트랜잭션이
    서로가 잠금을 놓기를 기다리는 상황이다. 많은 데이터베이스가 교착 상태를 자동으로 탐지해
    관련된 트랜잭션 중 하나를 중단시켜 시스템이 진전할 수 있게 한다. 애플리케이션 수준에서는
    중단된 트랜잭션을 재시도해 이 상황을 처리할 수 있다.**

## 갱신 손실 자동 탐지

- **원자적 연산과 잠금은 읽기-수정-쓰기 사이클을 순차적으로 일어나게 강제해 갱신 손실을 막는
  방법이다. 대안은 병렬 실행을 허용하되 트랜잭션 관리자가 갱신 손실을 탐지하면 문제의 트랜잭션을
  중단시켜 읽기-수정-쓰기 사이클을 재시도하게 강제하는 것이다** (8장,
  p.301).[^kleppmann2026]
- 이점 — **데이터베이스가 이 검사를 스냅샷 격리와 결합해 효율적으로 수행할 수 있다는 것**이다.
  **실제로 PostgreSQL의 repeatable read, 오라클의 serializable, SQL Server의 스냅샷 격리
  수준은 갱신 손실이 일어났을 때 자동으로 탐지하고 문제의 트랜잭션을 중단시킨다. 그러나
  MySQL/InnoDB의 repeatable read 격리 수준은 갱신 손실을 탐지하지 않는다. 어떤 저자들은
  데이터베이스가 스냅샷 격리를 제공한다고 인정받으려면 갱신 손실을 막아야 한다고 주장하므로,
  그 정의에 따르면 MySQL은 스냅샷 격리를 제공하지 않는다** (8장,
  p.301).[^kleppmann2026]
- **갱신 손실 탐지의 큰 이점은 애플리케이션 코드가 어떤 특별한 데이터베이스 기능도 쓰지 않아도
  된다는 것이다. 잠금이나 원자적 연산 쓰기를 잊어 버그를 들일 수 있지만, 갱신 손실 탐지는
  자동으로 일어나므로 오류 발생 가능성이 더 낮다. 다만 중단된 트랜잭션을 애플리케이션 수준에서
  재시도해야 한다** (8장, pp.301–302).[^kleppmann2026]

## 조건부 쓰기 — compare-and-set

- **트랜잭션을 제공하지 않는 데이터베이스에서는 마지막으로 읽은 이후 값이 바뀌지 않았을
  때에만 갱신이 일어나도록 허용하는 조건부 쓰기(conditional write) 연산을 볼 수 있고, 이것으로
  갱신 손실을 막을 수 있다. 현재 값이 이전에 읽은 것과 맞지 않으면 갱신은 효과가 없고
  읽기-수정-쓰기 사이클을 재시도해야 한다. 많은 CPU가 지원하는 원자적 CAS 명령의 데이터베이스
  대응물**이다 (8장, p.302).[^kleppmann2026]
- 예컨대 두 사용자가 같은 위키 페이지를 동시에 갱신하는 것을 막으려면
  `UPDATE wiki_pages SET content = 'new content' WHERE id = 1234 AND content = 'old content';`
  같은 것을 시도해 **사용자가 편집을 시작한 이후 페이지 내용이 바뀌지 않았을 때에만 갱신이
  일어나기를 기대할 수 있다**. 다만 원문의 주석대로 **이것은 데이터베이스 구현에 따라 안전할
  수도 안전하지 않을 수도 있다** (8장, p.302).[^kleppmann2026]
- **내용이 바뀌어 `old content`와 더는 맞지 않으면 이 갱신은 효과가 없으므로 갱신이 반영됐는지
  확인하고 필요하면 재시도해야 한다. 전체 내용을 비교하는 대신 갱신마다 증가시키는 버전 번호
  컬럼을 두고 현재 버전 번호가 바뀌지 않았을 때에만 갱신을 적용할 수도 있다. 이 접근법을
  때때로 낙관적 잠금(optimistic locking)이라 부른다** (8장, p.302).[^kleppmann2026]
- 주의할 상호작용 — **다른 트랜잭션이 `content`를 동시에 수정했다면 그 새 내용은 MVCC 가시성
  규칙 아래에서 보이지 않을 수 있다. MVCC의 많은 구현이 이 시나리오를 위해 가시성 규칙에 예외를
  두어, 다른 트랜잭션이 쓴 값이 스냅샷에서는 달리 보이지 않더라도 `UPDATE`와 `DELETE` 질의의
  `WHERE` 절 평가에는 보이게 한다** (8장, p.302).[^kleppmann2026]

## 복제된 데이터베이스에서는

- **복제된 데이터베이스에서 갱신 손실 방지는 또 다른 차원을 갖는다. 이 데이터베이스들은 여러
  노드에 데이터 사본을 두고 데이터가 서로 다른 노드에서 동시에 수정될 수 있으므로 추가 조치가
  필요하다** (8장, p.302).[^kleppmann2026]
- 전제가 깨지는 지점 — **잠금과 조건부 쓰기 연산은 데이터의 최신 사본이 하나라고 가정한다.
  그러나 다중 리더(multi-leader)나 리더리스(leaderless) 복제를 쓰는 데이터베이스는 보통 여러
  쓰기가 동시에 일어나 비동기로 복제되는 것을 허용하므로 데이터의 최신 사본이 하나임을 보장할 수
  없다. 따라서 잠금이나 조건부 쓰기에 기반한 기법은 이 맥락에 적용되지 않는다** (8장,
  p.302).[^kleppmann2026]
- 대신 쓰이는 접근 — **그런 복제된 데이터베이스에서 흔한 접근법은 동시 쓰기가 값의 충돌하는
  버전 여럿(형제, siblings)을 만들도록 허용하고, 애플리케이션 코드나 특수한 자료 구조로 사후에
  그 버전들을 해소하고 병합하는 것이다** (8장, p.303).[^kleppmann2026]
- **충돌하는 값의 병합은 갱신이 가환적(commutative)이면**(즉 서로 다른 레플리카에서 다른 순서로
  적용해도 같은 결과를 얻으면) **갱신 손실을 막을 수 있다. 예컨대 카운터를 증가시키는 것과 집합에
  원소를 추가하는 것은 가환 연산이며, 그것이 CRDT의 착상이다. 그러나 조건부 쓰기 같은 일부
  연산은 가환적으로 만들 수 없다** (8장, p.303).[^kleppmann2026]
- **덧붙여 많은 복제 데이터베이스의 기본값인 LWW(최종 쓰기 승리) 충돌 해소 방법은 갱신 손실에
  취약하다** (8장, p.303).[^kleppmann2026]

## 더티 쓰기와 나란히 놓인 정의

- 같은 이상이 쓰기 이상 셋 중 하나로 정의된 판이 있다 — **갱신 손실(lost update)은 트랜잭션 T₁과
  T₂가 둘 다 V의 값을 갱신하려 시도할 때 일어난다. T₁과 T₂가 V의 값을 읽는다. T₁이 V를 갱신하고
  커밋하고, T₂도 그 뒤 V를 갱신하고 커밋한다. 트랜잭션들이 서로의 존재를 알지 못하므로, 둘 다
  커밋되는 것이 허용되면 T₁의 결과가 T₂의 결과로 덮어써지고 T₁의 갱신은 유실된다** (5장,
  p.96).[^petrov2019]
- 바로 옆에 놓인 더티 쓰기의 정의도 옮겨 둔다 — **더티 쓰기(dirty write)는 트랜잭션 중 하나가
  커밋되지 않은 값(곧 더티 읽기)을 가져다 수정하고 저장하는 상황이다. 다시 말해 트랜잭션 결과가
  결코 커밋된 적 없는 값에 근거한다** (5장, p.96).[^petrov2019]
- 스냅샷 격리가 이것을 자동으로 막는지에 대한 판정은 두 정본이 갈린다. 조건과 함께 정리한 자리는
  [격리 수준과 이상 현상](../concepts/isolation-levels-and-anomalies.md)의 "두 표가 어긋나는 두
  칸" 절이다. 요지는 **먼저 커밋한 쪽이 이기고 나머지는 중단되는 커밋 규칙을 갖춘 구현에 한해**
  갱신 손실이 배제된다는 것이다 (5장, p.97).[^petrov2019]
- 락 없이 같은 문제를 다루는 반대 방향의 규칙도 있다 — 타임스탬프 순서화에서
  **`max_write_timestamp`보다 낮은 타임스탬프의 쓰기 연산은 허용되는데, 낡은 쓰인 값을 안전하게
  무시할 수 있기 때문이다. 이 추측을 흔히 토머스 쓰기 규칙(Thomas Write Rule)이라 한다** (5장,
  p.100).[^petrov2019] 곧 여기서는 덮어써진 갱신이 버그가 아니라 설계된 동작이다.
