# 객체 생존 판정

**목차**: [참조 카운팅과 순환 참조](#참조-카운팅과-순환-참조) · [도달 가능성 분석](#도달-가능성-분석) · [참조의 네 가지 세기](#참조의-네-가지-세기) · [두 번의 표시와 finalize](#두-번의-표시와-finalize) · [메서드 영역 회수하기](#메서드-영역-회수하기) · [이어지는 페이지](#이어지는-페이지)

이 페이지의 질문: **가비지 컬렉터는 어떤 객체가 '죽었다'고 판단하는가.** 여기서 죽었다는
말은 **프로그램 코드에서 어떤 식으로도 더는 사용될 수 없다는 뜻**이다 (3장,
p.94).[^zhou2024]

- 자리를 먼저 잡아 두자. 프로그램 카운터·가상 머신 스택·네이티브 메서드 스택은 스레드와
  함께 생성·소멸하고 **각 스택 프레임의 크기가 클래스가 만들어질 때 결정되므로, 이 영역의
  할당과 회수는 결정적이라 어떻게 회수할지 고민하지 않아도 된다.** 반면 자바 힙과 메서드
  영역은 **런타임에만 알 수 있는 것들**이라 할당·회수가 동적이며, 가비지 컬렉터는 바로
  이런 영역을 관리하는 데 집중한다 (3장, pp.93–94).[^zhou2024]

## 참조 카운팅과 순환 참조

- 많은 교재가 설명하는 **참조 카운팅(reference counting)** 알고리즘은 이렇다 (3장,
  p.94):[^zhou2024]
  1. 객체를 가리키는 **참조 카운터(reference counter)** 를 추가하고, 참조하는 곳이 하나
     늘어날 때마다 카운터를 1씩 증가시킨다.
  2. 참조하는 곳이 하나 사라질 때마다 1씩 감소시킨다.
  3. 카운터 값이 0이 된 객체는 더는 사용될 수 없다.
- 이 알고리즘은 **원리가 간단하고 판단에 드는 에너지도 적어 대다수 상황에서 좋은
  알고리즘**이며 마이크로소프트 COM, 파이썬, 러스트, 게임용 스크립트 언어 스퀄(Squirrel)이
  실제로 쓴다 (3장, p.95).[^zhou2024]
- **하지만 자바 가상 머신에서는 참조 카운팅을 쓰지 않는다.** 간결한 알고리즘임에도
  고려해야 할 특이 상황이 적지 않고, **모든 상황에서 문제없이 동작하게 하려면 계산할 것이
  상당히 늘어나기 때문**이다 (3장, p.95).[^zhou2024]
- 대표적 반례가 **순환 참조(circular reference)** 다. 두 객체가 서로를 필드로 참조한 뒤
  외부 참조를 끊으면 **외부에서 접근할 길이 사라졌는데도 카운터가 0이 아니어서 회수하지
  못한다** (3장, p.95).[^zhou2024]
  - 실제로 그 코드를 `-Xlog:gc*`로 돌려 보면 전체 GC 로그에 `10M->0M(16M)`가 찍혀
    **두 객체가 회수됐음**을 확인할 수 있다. 즉 **가상 머신은 생사 판단에 참조 카운팅을
    쓰지 않는다** (3장, p.96).

## 도달 가능성 분석

- 자바·C# 등 오늘날의 주류 언어는(그리고 거슬러 올라가 리스프까지) 모두 **도달 가능성
  분석(reachability analysis)** 을 쓴다. **GC 루트(GC Roots)** 라는 시작 노드 집합에서
  출발해 참조하는 객체들로 탐색해 들어가며, 이때 만들어지는 경로를 **참조 체인(reference
  chain)** 이라 한다 (3장, p.97).[^zhou2024]
- 판정 기준은 하나다 — **어떤 객체와 GC 루트 사이를 이어 주는 참조 체인이 없다면, 즉 GC
  루트로부터 도달 불가능한 객체는 더 이상 사용될 수 없는 게 확실해진다.** 서로 이어져
  있어도 루트에서 닿지 않으면 회수 대상이다 (3장, p.97).[^zhou2024]
- 자바에서 GC 루트로 쓰이는 객체는 정해져 있다 (3장, pp.97–98):[^zhou2024]
  - **가상 머신 스택**(스택 프레임의 지역 변수 테이블)에서 참조하는 객체 — 현재 실행 중인
    메서드의 매개 변수, 지역 변수, 임시 변수 등.
  - **메서드 영역에서 클래스가 정적 필드로 참조하는 객체** — 자바 클래스의 참조 타입 정적
    변수.
  - **메서드 영역에서 상수로 참조되는 객체** — 문자열 테이블 안의 참조.
  - **네이티브 메서드 스택에서 JNI가 참조하는 객체.**
  - **가상 머신 내부에서 쓰이는 참조** — 기본 데이터 타입에 해당하는 `Class` 객체, 일부
    상주 예외 객체(`NullPointerException`·`OutOfMemoryError` 등), 시스템 클래스 로더.
  - **동기화 락(`synchronized` 키워드)으로 잠겨 있는 모든 객체.**
  - 가상 머신 내부 상황을 반영하는 **JMXBean, JVMTI에 등록된 콜백, 로컬 코드 캐시** 등.
- 여기에 더해 **가비지 컬렉터 종류나 현재 회수 중인 메모리 영역에 따라 다른 객체들이
  '임시로' 추가**될 수 있다. 세대 단위 컬렉션과 부분 컬렉션에서는 힙의 일부 영역(전형적인
  컬렉터라면 신세대)부터 분석을 시작하는데, **영역들이 서로 완전히 격리되거나 닫혀 있지
  않으므로 연관된 영역의 객체들도 루트 집합에 포함시켜야 결과를 신뢰할 수 있다** (3장,
  p.98).[^zhou2024]

## 참조의 네 가지 세기

- 생사 판단과 '참조'는 떼어 생각할 수 없다. **JDK 1.2 전의 자바는 참조를 매우 전통적인
  의미로 정의했다** (3장, p.98):[^zhou2024]

  > "참조 타입 데이터에 저장된 값이 다른 메모리 조각의 시작 주소를 뜻한다면, 이 참조
  > 데이터를 해당 메모리 조각이나 객체를 참조한다고 말한다."

- 이 정의에서는 객체 상태가 '참조됐다'와 '참조되지 않았다' 딱 둘뿐이라 **'버리기는 아까운'
  객체를 표현할 방법이 없다.** 예컨대 '메모리가 여유롭다면 그냥 두고, 가비지 컬렉션을 하고
  나서도 메모리가 매우 부족하다면 그때 회수하는 객체'는 **많은 시스템의 캐시 기능에 딱
  맞는 시나리오**다 (3장, pp.98–99).[^zhou2024]
- 그래서 **JDK 1.2부터 참조를 넷으로 구분하며, 나열한 순서대로 강도가 약해진다** (3장,
  p.99):[^zhou2024]
  - **강한 참조(strong reference)** — `Object obj = new Object()`처럼 코드에서 참조를
    할당하는 것. **강한 참조 관계가 남아 있는 객체는 가비지 컬렉터가 절대 회수하지 않는다.**
  - **부드러운 참조(soft reference)** — 유용하지만 필수는 아닌 객체. **부드러운 참조만 남은
    객체는 메모리 오버플로가 나기 직전에 두 번째 회수를 위한 회수 목록에 추가되고, 두 번째
    회수 후에도 메모리가 부족하면 그때 오버플로 예외를 던진다.** JDK 1.2 때
    `SoftReference` 클래스로 추가됐다.
  - **약한 참조(weak reference)** — 부드러운 참조와 비슷하나 연결 강도가 더 약하다. **약한
    참조뿐인 객체는 다음번 가비지 컬렉션까지만 살아 있으며, 컬렉터가 동작하기 시작하면
    메모리가 넉넉하더라도 모두 회수된다.** `WeakReference`가 구현한다.
  - **유령 참조(phantom reference)** — 가장 약한 참조('ghost reference'라고도 한다).
    **객체 수명에 아무 영향을 주지 않으며, 유령 참조를 통해 인스턴스를 가져오는 것조차
    불가능하다. 유일한 목적은 대상 객체가 회수될 때 알림을 받는 것**이다.
    `PhantomReference`가 구현한다.
- JDK 내부에는 **파이널 참조(final reference)** 라는 유형도 쓰인다. 강도는 약한 참조와
  유령 참조 사이이며, **`finalize()`를 구현한 객체는 모두 파이널 참조의 대상이 되어 별도
  대기열(queue)에 등록된다** (3장, p.99).[^zhou2024]

## 두 번의 표시와 finalize

- 도달 가능성 분석이 '도달 불가능'으로 판단한 객체라고 해서 반드시 죽어야 하는 건 아니다.
  **확실한 사망 선고를 내리려면 두 번의 표시(marking) 과정을 거쳐야 한다** (3장,
  p.100).[^zhou2024]
- 첫 번째 표시 뒤에 **필터링**이 진행된다. 조건은 **종료자(finalizer), 즉 `finalize()`
  메서드를 실행해야 하는 객체인가**이며, `finalize()`가 필요 없거나 가상 머신이 이미
  호출한 경우 모두 '실행할 필요 없음'으로 처리한다 (3장, p.100).[^zhou2024]
- 실행해야 하는 객체는 **F-큐(F-Queue)** 라는 대기열에 추가되고, 가상 머신이 만든 **우선
  순위가 낮은 종료자 스레드**가 그 객체들의 `finalize()`를 실행한다. **가상 머신은 메서드를
  시작만 시킬 뿐 끝날 때까지 기다려 주지 않는다** — 어떤 객체의 `finalize()`가 너무
  오래 걸리거나 무한 루프에 빠지면 F-큐의 다른 객체들이 무작정 기다려야 하고, 최악의 경우
  **가비지 컬렉션 시스템 전체를 비정상 종료시킬 수도 있기 때문**이다 (3장,
  p.100).[^zhou2024]
- `finalize()`는 **죽음에 직면한 객체가 부활할 수 있는 마지막 기회**다. 참조 체인상의 아무
  객체와 다시 연결되면(예: `this`를 다른 객체의 인스턴스 변수에 할당) **두 번째 표시에서
  '회수 대상' 목록에서 제외된다** (3장, p.100).[^zhou2024]
  - 실험 결과가 이를 보여 준다 — **완전히 같은 코드가 두 번 반복되는데 첫 번째는 탈출에
    성공하고 두 번째는 실패한다. 시스템이 `finalize()`를 호출해 주는 건 객체마다 오직 한
    번뿐이기 때문**이다 (3장, pp.101–102).
- 저자의 권고는 단호하다 — **`finalize()`는 C·C++의 파괴자와 다르며, 자바가 막 탄생했을 때
  기존 C·C++ 개발자를 끌어들이려고 도입한 타협안일 뿐이다. 실행 비용이 높고 불확실성이
  크며 어느 객체부터 호출되는지도 보장하지 않는다.** 이런 이유로 **JDK 9부터 폐기 대상으로
  지정되었고**, `finalize()`로 할 수 있는 일은 전부 `try-finally` 등으로 더 잘 처리할 수
  있다 (3장, p.102).[^zhou2024]

## 메서드 영역 회수하기

- 메서드 영역(핫스팟의 메타스페이스나 영구 세대)은 **가비지 컬렉션 대상이 아니라고
  생각하는 사람도 있다.** 명세에 따르면 반드시 청소해야 하는 건 아니고, 실제로 타입
  언로딩을 구현하지 않거나 완벽히 수행하지 않는 가상 머신도 있다 — **JDK 11에 처음 탑재된
  시험 버전 ZGC는 클래스 언로딩을 지원하지 않았다(JDK 12부터 지원)** (3장,
  p.102).[^zhou2024]
- 이유는 **비용 효율**이다. 일반적인 애플리케이션에서 **자바 힙, 그중에서도 신세대는 가비지
  컬렉션 한 번으로 메모리 공간의 70~99%를 회수해 내는 반면, 메서드 영역은 회수 조건이
  까다로워 효율이 훨씬 떨어진다** (3장, p.102).[^zhou2024]
- 회수 대상은 크게 둘 — **더 이상 사용되지 않는 '상수'와 '클래스'** 다 (3장,
  p.102).[^zhou2024]
  - 상수 회수는 힙의 객체 회수와 매우 비슷하다. 상수 풀의 `"java"` 리터럴을 참조하는
    문자열 객체가 하나도 없고 이 리터럴을 쓰는 코드도 없다면, 컬렉터는 그 상수를 풀에서
    치워 버려도 된다고 판단한다. 다른 클래스·메서드·필드의 심벌 참조도 비슷하다 (3장,
    p.103).
- 반면 **더 이상 쓰이지 않는 '클래스'인지 판단하는 조건은 훨씬 까다로워 다음 셋을 동시에
  만족해야 한다** (3장, p.103):[^zhou2024]
  - 이 클래스의 인스턴스가 모두 회수됐다 — 자바 힙에 해당 클래스와 하위 클래스의
    인스턴스가 하나도 없다.
  - 이 클래스를 읽어 들인 **클래스 로더가 회수됐다.** OSGi나 JSP 리로딩처럼 세심하게
    설계한 대안 클래스 로더 없이는 충족하기 어렵다.
  - 이 클래스의 `java.lang.Class` 객체를 아무 곳에서도 참조하지 않고, **리플렉션으로 이
    클래스의 메서드를 이용하는 곳도 전혀 없다.**
- 세 조건에 부합하는 클래스를 가상 머신은 **회수하도록 '허용'할 뿐 반드시 회수한다고 하지는
  않는다.** 핫스팟은 `-Xnoclassgc`로 회수 여부를 제어하고,
  `-Xlog:class+load=info`·`-Xlog:class+unload=info`로 로딩·언로딩 정보를 볼 수 있다 (3장,
  p.103).[^zhou2024]
- **리플렉션, 동적 프락시, CGLib 같은 바이트코드 프레임워크를 많이 쓰거나 JSP를 동적
  생성하고 클래스 로더를 자주 자화하는 OSGi 환경**에서는 일반적으로 타입 언로딩을 지원해야
  메서드 영역이 과도한 압박에 시달리지 않는다 (3장, p.103).[^zhou2024]
