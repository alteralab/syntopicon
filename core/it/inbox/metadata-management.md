# 메타데이터 관리

## 메타데이터란 무엇인가

- "데이터에 관한 데이터"라는 통상 정의는 쓸모가 적다. 대안 정의는 원문을 직인용한다 (§10.1, pp.316–317).[^linstedt2016]

> metadata is all data about other data that is *"needed to promote its administration and use"*

- 데이터 웨어하우징에서 자주 쓰는 다른 분류는 백룸/프런트룸 구분이다: 백룸 메타데이터(back room metadata)는 프로세스 관련으로 추출·정제·적재 과정을 기술하며 DBA·웨어하우스 팀의 적재를 돕고, 프런트룸 메타데이터(front room metadata)는 기술적(descriptive) 성격으로 쿼리·리포트 도구에서 최종 사용자를 돕는다 (§10.1, p.317).[^linstedt2016]
- 메타데이터 관리의 궁극 목표는 데이터 웨어하우스의 모든 산출물(artifact)을 기술하는 것이다. 관계형 테이블 하나만 해도 레코드 레이아웃, 볼륨(volumetric), 인덱스, 적재 일정, 사용처·의존성, 참조 무결성, 일반 문서 등이 캡처 대상이다 (§10.1, p.317).[^linstedt2016]
- 메타데이터는 시간이 지나며 변한다 — 비즈니스 의미가 바뀌고(business), 원천 시스템이 바뀌고(technical), 데이터 웨어하우스 자체가 바뀐다(process execution). 추적할 메타데이터 목록은 각 팀이 조직·프로젝트의 필요에 맞게 조정해야 한다 (§10.1, p.318).[^linstedt2016]

## 메타데이터 3종 분류

- Data Vault 2.0 아키텍처가 채택하는 분류는 세 범주다 (§10.1, p.317):[^linstedt2016]
  - 비즈니스 메타데이터(business metadata): 데이터가 비즈니스에 갖는 의미를 기술한다. Meta Mart가 담는다.
  - 기술 메타데이터(technical metadata): 데이터 타입, 리니지(lineage), 프로파일링 결과 등 데이터의 기술적 측면을 기술한다. 역시 Meta Mart가 담는다.
  - 프로세스 실행 메타데이터(process execution metadata): 실행 중인 ETL 프로세스의 통계 — 원천에서 읽고 목적지에 쓴 레코드 수, 거부된 행 수, 적재 소요 시간을 제공한다. Metrics Vault가 담고, 오류 정보는 Error Mart가 추적한다.

### 비즈니스 메타데이터

- 비즈니스 정의 관련: 비즈니스 컬럼 이름(약어 풀이 포함), 속성·테이블·객체별 비즈니스 정의, 온톨로지·택소노미(비즈니스 객체 간 관계·계층·분류 — 보통 MDM 시스템에 저장), 물리 테이블·컬럼 이름과 비즈니스 이름의 대응, 기술 번호 체계 (§10.1.1, p.318).[^linstedt2016]
- 비즈니스 정의를 제공할 수 없는 항목은 비즈니스에 분석 가치가 없다는 신호이며 정보 마트에서 제거할 수 있다 (§10.1.1, p.318).[^linstedt2016]
- 원천 시스템 관련: 비즈니스 용어로 된 레코드 소스 기술(서버·인스턴스 참조가 아니라 "Flight Tracking Database"처럼, 가능한 한 상세하게), 테이블 명세(목적·볼륨·컬럼·키), 하드 예외 처리 규칙(hard rule — 기술적 이슈 대응), 원천 속성의 비즈니스 의미, 소프트 비즈니스 규칙(soft rule — 원천 시스템이 데이터를 수정·생성·정제하는 규칙) (§10.1.1, p.319).[^linstedt2016]
- 누가 비즈니스 메타데이터를 책임질지(요구사항 분석가, 원천 시스템 분석가, 데이터 모델러)는 논쟁거리지만, 어떤 비즈니스 메타데이터를 어디서 관리할지는 웨어하우스 팀이 반드시 결정해야 한다 (§10.1.1, p.318).[^linstedt2016]

### 기술 메타데이터

- 웨어하우스 팀이 만들고 유지하며 가장 많이 혜택을 보는 메타데이터로, 대상은 원천 시스템(데이터베이스·플랫 파일 위치, 스테이징 테이블), 데이터 모델(물리·논리 — 엄밀히는 메타데이터가 아니지만 귀중한 자산), 데이터 정의(테이블·컬럼·타입·도메인·참조 무결성·제약·기본값·트리거), 비즈니스 규칙의 기술적 정의(하드/소프트 구분 유지, 암복호화 요구 포함), 볼류메트릭스(테이블 크기·성장 패턴 — 6–12개월 하드웨어 조달 주기 예측), 온톨로지·택소노미(약어, 비즈니스 키 지정, 계층, 구조 수준의 온톨로지 간 매칭), 데이터 품질(표준화·품질 지표) (§10.1.2, pp.319–320).[^linstedt2016]
- 명명 규약도 메타데이터의 한 형태다: 테이블 이름의 접두사·접미사(예: 허브·링크·새틀라이트별 약어, 새틀라이트의 원천 시스템 약어)는 엔터티 타입 정보를 이름에 부호화해 모든 SQL 도구에서 보이게 한다. 단점은 이 메타데이터가 엔터티에 부착된 전용 메타데이터로는 쉽게 조회되지 않는다는 것이다 (§10.2.2, pp.325, 328).[^linstedt2016]

### 프로세스 실행 메타데이터

- 비즈니스·기술 메타데이터가 비즈니스나 원천 애플리케이션에서 제공되는 것과 달리, 프로세스 실행 메타데이터는 웨어하우스 팀이 생성하며 유지보수를 위한 ETL 처리 통찰을 제공한다. 네 유형: 제어 흐름(control flow) 메타데이터(데이터 리니지 파악·디버깅), 데이터 흐름(data flow) 메타데이터(변환별 처리·거부 레코드 수와 성능), 패키지 메타데이터(실행 시간 요약), 프로세스 메타데이터(패키지를 기동한 스케줄러 프로세스 정보) (§10.1.3, p.320).[^linstedt2016]
- 이 메타데이터는 프로세스 실행 시 Metrics Vault에 담기며, Meta Mart의 비즈니스·기술 메타데이터와는 통상 분리된다 (§10.1.3, p.320).[^linstedt2016]

## 저장소별 역할 구분: 무엇을 재고 어디에 두나

[데이터 볼트 아키텍처](../concepts/data-vault-architecture.md)에는 Raw Data Vault 경유가 아닌 독립 구성 요소가 여럿 있고, 각자 담는 것이 다르다.

| 구성 요소 | 담는 것 | 위치·원천 | 모델 |
|---|---|---|---|
| Meta Mart | 비즈니스·기술 메타데이터 | 독립 정보 마트 — Raw Data Vault에서 조달하지 않음 | 차원 모델 또는 3정규형, 항상 실체화 |
| Metrics Vault | 프로세스 실행 메타데이터 원시 데이터(ETL 지표) | EDW 계층, Data Vault 모델의 통합된 일부 | Data Vault 2.0 모델 |
| Metrics Mart | 성능 분석용으로 가공된 지표 정보 | 정보 전달 계층, 주로 Metrics Vault에서 조달 | 분석 필요에 맞는 모델(차원 등), 가상화 선호 |
| Error Mart | 거부·미처리 레코드의 원시 데이터 | 독립 정보 마트 — Raw Data Vault에서 조달하지 않음 | 주로 차원 모델 |

### Meta Mart

- Meta Mart는 Data Vault 2.0 아키텍처에서 비즈니스·기술 메타데이터 수집의 중심이다. Raw Data Vault에서 조달되지 않는 독립 정보 마트이므로 가상 Meta Mart의 원천이 될 Meta Vault는 존재하지 않는다 — 메타데이터를 실제로 저장하므로 항상 실체화된다 (§10.2, p.321).[^linstedt2016]
- 다른 정보 마트처럼 비즈니스가 가장 잘 쓸 수 있는 형태로 모델링한다: 차원 모델일 수도, 3정규형일 수도 있고, 메타데이터 도구가 있으면 그 도구의 백엔드 데이터베이스가 Meta Mart가 된다. 관계형일 필요도 없다 — 상용 모델링·ETL 도구의 메타데이터 모델을 확장해 Data Vault용 리니지(허브·링크·새틀라이트의 원천 테이블 정의 등)를 담을 수도 있다 (§10.2, p.321).[^linstedt2016]

- 물리 설계 장이 이 마트의 내용 목록을 다시 준다. 최종 사용자(대개 관리자·파워 유저·웨어하우스 이니셔티브 팀원)에게 제시되는 것은 일곱 항목이다: **전 계층의 데이터·정보에 관한 메타데이터**, **프로세스에 관한 메타데이터**(주로, 그러나 ETL 적재 프로세스에 한정되지 않는다), **수행된 백업에 관한 메타데이터**, **원천 시스템과 타 시스템 인터페이스**(정보 소비자 등)**에 관한 메타데이터**, **하드·소프트 업무 규칙의 정의**, **접근 제어 목록(ACL) 등 보안 조치의 정의**, **프라이버시 관련 데이터의 보존 기간 정의**. 이 목록은 완결적이지 않다 — Meta Mart는 업무 사용자가 직접 쓰지는 않지만 **어떤 데이터·정보가 있는지, 어디서 왔는지, 어떻게 처리되는지, 누가 무슨 목적으로 쓰는지**를 기술하는 모든 정보를 접근 가능하게 만든다. 더 정교한 환경에서는 Meta Mart가 메타데이터 웨어하우스 솔루션으로 대체되기도 한다 (§8.6.4, p.257).[^linstedt2016]
- 이 마트를 **OLAP 도구로 질의한다면 차원 모델이 이 마트를 모델링하는 최선의 접근**이다 (§8.6.4, p.257).[^linstedt2016] 위 §10.2의 "차원 모델일 수도, 3정규형일 수도"를 소비 도구 기준으로 좁힌 진술이다.
- Meta Mart와 Error Mart는 **재구축할 수 없는 마트**다. Metrics Mart가 Metrics Vault에서 조달되는 것과 달리 이 둘은 데이터의 단일 지점이므로, 신뢰성 요구가 다른 정보 마트보다 높고 Raw Data Vault 계층에 준한다. 백업에도 반드시 포함해야 하며 Metrics Mart의 백업만 선택이다 (§8.6.4.1, pp.257–258).[^linstedt2016] 계층별 물리 설계는 [Data Vault 아키텍처](../concepts/data-vault-architecture.md)와 [물리 데이터 웨어하우스 설계](../concepts/physical-data-warehouse-design.md) 참조.

### Metrics Vault

- Metrics Vault는 ETL 제어·데이터 흐름의 프로세스 지표를 캡처한다. 선택적 구성 요소지만 오류 검사(ETL 재기동에 필요한 오류·원인 식별), 근본 원인 분석(같은 오류의 재발 방지), 성능 지표(데이터 크기·성장률을 관찰해 부정적 추세를 장애 전에 대응)에 유용하다 (§10.3, p.351).[^linstedt2016]
- 최고 수준의 상세로 캡처할 지표 영역: 타이밍(시작·종료·경과 시간), 성능(초당 읽기/쓰기 행 수), 볼륨(읽은·쓴·거부된 총 행 수), 오류(원천·목적지별 거부/오류 레코드 수 — 원시 데이터 자체는 Error Mart 몫), 빈도(원천의 데이터 제공·ETL 실행 주기), 의존 체인(의존 ETL 프로세스의 대기 시간) (§10.3, pp.351–352).[^linstedt2016]
- Metrics Vault는 Data Vault 2.0 모델로 모델링해야 한다 — ETL 도구 외에 서버·네트워크 인프라 등 다양한 원천의 지표를 통합하기 위해서다. 근본 원인 분석이 진행될수록 더 많은 잠재 장애 원천이 분석 대상이 되므로, 웨어하우스 자체처럼 애자일하게 원천을 늘려 간다 (§10.3, p.352).[^linstedt2016]

### Metrics Mart

- Metrics Vault에 원시 성능 데이터를 캡처한 다음 단계는 분석용 가공이다. Metrics Mart는 그 데이터 모델이 구현되는, 사용자 쪽 하류(downstream)에 위치한 정보 마트다. 표준 아키텍처를 그대로 따른다: Metrics Vault는 EDW의 Data Vault 모델에 통합된 일부로 구현되고 Metrics Mart 구축에만 배타적으로 쓰인다 (§10.4, p.363).[^linstedt2016]
- Metrics Mart는 특수 목적 정보 마트로 주로 Metrics Vault에서 조달되지만(Raw Data Vault·Business Vault 대신), 고객·제품 관련 기술 성능 지표처럼 비즈니스 객체를 포함하려면 Raw Data Vault나 Business Vault에서도 조달할 수 있다. ETL 실체화와 SQL 뷰 가상화 모두 가능하며 배포 속도가 빨라지는 가상화가 선호된다 (§10.4, p.363).[^linstedt2016]
- 모델은 최종 사용자의 분석 필요에 맞춘다 — OLAP 큐브를 올릴 거면 차원 모델, 모니터링 소프트웨어가 기대하는 형식이 따로 있으면 그 형식. 원시 데이터(Metrics Vault)와 정보(Metrics Mart)를 분리하는 이점은 Raw Data Vault와 정보 마트의 관계와 같다: 다른 원천을 쉽게 통합하면서 필요한 구조를 가상으로 구축할 수 있다 (§10.4, pp.363–364).[^linstedt2016]

### Error Mart

- Error Mart도 정보 마트지만 Meta Mart처럼 Raw Data Vault나 다른 원천에서 조달되지 않는다. 오류 정보를 저장하는 일차 장소이며, 대부분은 ETL 엔진에서 온다 (§10.5, p.364).[^linstedt2016]
- 캡처하는 레코드 유형 네 가지 (§10.5, p.365):[^linstedt2016]
  - 스테이징 영역이 거부한 레코드: 전송 오류 등으로 관계형 구조에 맞지 않는 데이터.
  - Raw Data Vault가 거부한 레코드: 적재 목표는 좋은 것·나쁜 것·못난 것(the good, the bad, and the ugly) 전부지만, 관계형 구조에 맞지 않으면 캡처 불가.
  - Business Vault가 처리하지 못한 레코드: 비즈니스가 정의한 소프트 규칙에 부합하지 않은 레코드.
  - 정보 마트가 처리하지 못한 레코드: Business Vault는 비즈니스 규칙을 부분적으로만 구현하므로 정보 마트의 소프트 규칙이 추가로 거부한 레코드도 Error Mart로 보낸다.
- 소프트 규칙은 시간이 지나며 바뀌므로 Error Mart가 캡처하는 데이터도 바뀐다. 거부된 레코드가 모두 나쁜 데이터는 아니다 — 소프트 규칙이 예상하지 못한 데이터(Data Vault 용어로 ugly data)도 포함되며, Error Mart는 이를 식별해 비즈니스 규칙 구현을 개선하고, 궁극적으로는 왜 그 레코드가 Raw Data Vault에 적재되지 못했는지를 찾아 고쳐서 적재하는 것이 목표다 (§10.5, p.365).[^linstedt2016]
- 최종 사용자가 선호하는 모델로 구현할 수 있지만 대부분 차원 모델로 짓는다: 오류 데이터를 팩트 테이블에, 부수 정보를 차원에 둔다. 오류 출력마다 별도 팩트 테이블을 만드는 쪽이 원시 데이터를 보존해 상세 오류 분석에 유리하다 — 단순 통계 산출은 Metrics Mart에 맡긴다 (§10.5, pp.365–366).[^linstedt2016]
