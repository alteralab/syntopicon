## 버전 조건

> **버전 조건**: 이 페이지의 프레임워크와 제품 이름은 **2025년 저술 시점**의 것이다 — Starlette·
> uvicorn·ASGI·Redis·장고와 Simple JWT·`asyncapi/cli`와 HTML 템플릿·Nginx·AsyncAPI Studio다.
> AsyncAPI가 리눅스 재단 아래의 오픈 소스 프로젝트이고 비동기 API 문서화의 가장 널리 쓰이는
> 표준이라는 판정, Redis가 지금 벡터 검색과 트랜잭션까지 지원한다는 기능 목록, 그리고
> WebSocket API가 헤더를 넘기지 못한다는 브라우저 API의 제약도 그 시점의 것이다. WebSocket 닫기
> 상태 코드 1008(Policy Violation)이 RFC 6455의 것이라는 사실은 시점에 매이지 않는다.
> **저자들은 이 가운데 어느 것의 지원 종료일도 적지 않으므로 이 페이지는 `stale_after`를 적지
> 않는다.**

## 클라이언트가 거는 콜백 넷

- **구현에 필요한 것이 둘로 적힌다** — **WebSocket API는 클라이언트와 서버 두 컴포넌트를
  요구한다** (10장, p.310).[^dynowski2025]
- **브라우저 쪽 클라이언트는 객체 하나를 만들고 콜백 넷을 건다** (10장,
  pp.310–311):[^dynowski2025]
  - **객체를 만드는 줄이 여는 핸드셰이크를 개시한다.**
  - **`onopen()`은 WebSocket 연결이 성공적으로 세워졌을 때 촉발된다.** 저자들의 예에서
    클라이언트는 거기서 JSON으로 인코딩된 메시지를 서버로 보낸다.
  - **`onmessage()`는 클라이언트가 서버에서 메시지를 받았을 때 촉발된다.** 예제의 클라이언트는
    거기서 넷을 한다 — **메시지를 읽고, 웹 페이지의 태그를 갱신하고, 콘솔에 기록하고,
    WebSocket 연결을 닫는다.**
    - **저자들이 마지막 하나를 스스로 취소한다** — **보통은 메시지를 받은 뒤 클라이언트가 연결을
      닫지 않으며, 여기서는 오직 시연 목적으로 그렇게 한다** (10장, p.311).[^dynowski2025]
  - **`onclose()`는 WebSocket 연결이 닫힌 것을 탐지했을 때 촉발된다.**
  - **`onerror()`는 이미 세워진 연결 동안 오류 이벤트를 탐지하면 오류 메시지를 기록한다.**
- **곁주 하나가 로깅에 유보를 단다** — **클라이언트의 콘솔에 로그를 찍는 것은 불필요한 정보를
  노출하거나 애플리케이션 성능에 영향을 줄 수 있고**, 저자들은 **프로그램 흐름을 보이려고만 그렇게
  한다**고 적으며 **운영 환경에서는 콘솔 대신 로그 집계 서비스로 기록하라**고 적는다 (10장,
  p.311).[^dynowski2025]

## 서버 엔드포인트가 덮어쓰는 메서드 셋

- **서버 쪽은 프레임워크가 주는 클래스를 상속한다** — 저자들의 엔드포인트 클래스는 **Starlette의
  `WebSocketEndpoint`를 상속하고, 그 클래스는 WebSocket 연결을 다루는 덮어쓸 수 있는 메서드
  셋을 제공한다** — `on_connect()`·`on_receive()`·`on_disconnect()`다 (10장,
  p.311).[^dynowski2025]
- **`encoding` 속성이 검증을 맡는다** — 그 속성이 **`on_receive()`에서 데이터를 JSON으로
  검증한다** (10장, p.311).[^dynowski2025]
- **두 메서드가 하는 일** (10장, pp.311–312):[^dynowski2025]
  - **`on_connect()`는 클라이언트가 엔드포인트에 연결을 세울 때 촉발된다.** 저자들의 ECHO
    엔드포인트는 거기서 연결을 받아들이지만 **필요하면 거절할 수도 있다.**
  - **`on_receive()`는 클라이언트가 데이터 프레임(메시지)을 서버로 보낼 때 촉발된다.** ECHO
    서버는 **받은 데이터를 그대로 돌려준다.**
- **곧 이 스타일의 서버는 요청 핸들러가 아니라 연결 수명의 사건 처리기로 적힌다.** REST 쪽의
  뷰가 요청 하나에 대응한다면([REST API 구현 결정](rest-api-implementation-decisions.md)),
  여기서는 **연결의 열림·수신·닫힘이 각각 자리를 갖는다.**

## 프로세스가 둘이라 다리가 필요했다

- **저자들이 짓는 것이 도시별 기상 경보다** — **클라이언트가 도시의 UUID로 식별되는 도시의 기상
  경보를 받을 수 있게 하고**, **그 UUID가 경보 메시지를 보낼 도시를 식별하며**, **API에 연결된
  모든 WebSocket 클라이언트가 경보를 받는다** (10장, p.313).[^dynowski2025]
- **문제가 배포 구조에서 나온다** — 서비스가 **독립한 프로세스 둘**로 돈다. 웹 페이지를 내주는
  쪽이 한 포트에서, WebSocket 서버가 다른 포트에서 돈다. 그래서 **앞쪽에서 뒤쪽으로 메시지를
  넘길 방법을 찾아야 한다** (10장, p.314).[^dynowski2025]
- **고른 해법이 발행-구독이다** — **그 쓸 자리에 맞는 pub/sub 메시징 패턴을 구현하기로 했고,
  그 패턴이 앞쪽 애플리케이션에서 뒤쪽 애플리케이션으로 데이터를 보내게 해 준다** (10장,
  p.314).[^dynowski2025]
  - 저자들은 그 패턴의 전문을 같은 책 11장으로 미룬다. **그 자리가
    [브로커 기반 API 스타일과 RabbitMQ](broker-based-api-style-and-rabbitmq.md)의 패턴 절**이고,
    거기서 이 패턴은 **익스체인지가 큐마다 사본을 라우팅하는 것**으로 규정된다. **이 KB에서
    이름 층의 정본은 [발행/구독 메시징](../concepts/publish-subscribe-messaging.md)이고,** 그
    페이지는 다른 소스들로 이미 두껍다.
- **구현 기술이 Redis다** — **메모리 안에서 도는 키-값 데이터베이스이고 pub/sub 메시지 전달의
  가벼운 구현을 제공한다** (10장, p.314).[^dynowski2025]
  - **저자들이 그 제품의 범위가 자란 내력을 적는다** — **본래 Redis는 메모리 안 키-값
    데이터베이스였고, 시간이 지나며 캐시와 키-값 NoSQL 데이터베이스로 제공 범위를 넓혔으며,
    지금은 벡터 검색·트랜잭션·pub/sub 메시징 같은 기능을 더 지원한다** (10장,
    p.319).[^dynowski2025]
- **흐름이 셋으로 적힌다** — **명령줄 프로그램이 경보 메시지를 만들어 pub/sub에 발행하고**,
  **WebSocket 서버가 pub/sub에 구독해 도착하는 메시지를 소비하며**, **그것을 연결된 모든
  WebSocket 클라이언트에 경보로 보낸다** (10장, p.314).[^dynowski2025]
- **채널의 이름이 도메인 식별자다** — **도시의 UUID가 Redis pub/sub 채널로 쓰인다** (10장,
  p.315).[^dynowski2025] 곧 **구독의 단위가 기술의 단위가 아니라 도메인의 단위**다.
  - **이 KB에서 채널 세밀도를 물음으로 세운 자리**가
    [토픽과 파티션](../concepts/topics-and-partitions.md)과
    [메시징 채널 패턴](../concepts/messaging-channel-patterns.md)이다. #hypothesis 도시마다 채널
    하나라는 이 배치는 도시 수가 늘면 채널 수가 그만큼 는다 — 저자들은 그 한계를 적지 않는다.
- **도판에만 있는 것 하나** — 그림 10-5는 상자 넷을 놓고 **명령줄 쪽에 "Publisher", WebSocket
  서버 쪽에 "Subscriber"라는 역할 이름을 적고, Redis 상자에 "PUB/SUB (DB index 0)"이라 적는다**
  (10장 그림 10-5, p.314).[^dynowski2025] 본문에 없는 것은 **두 프로세스가 같은 Redis 데이터베이스
  번호를 써야 한다**는 배치다.

## ASGI가 하는 일

- **프레임워크를 고른 근거가 둘이다** — **WebSocket API를 지원하는 것**과 **비동기 서버 게이트웨이
  인터페이스(Asynchronous Server Gateway Interface, ASGI) 덕분에 요청을 비동기로 처리할 수 있는
  것**이다 (10장, p.315).[^dynowski2025]
- **ASGI의 규정이 곁주로 온다** — **ASGI는 파이썬 웹 서버가 요청을 비동기로 처리할 수 있게
  한다** (10장, p.315).[^dynowski2025]
- **이 KB에 논블로킹 서버 모형의 일반형이 이미 있다** —
  [NIO 셀렉터와 이벤트 루프](../concepts/nio-selector-event-loop.md)와
  [이벤트 루프 스레드를 막지 않는다는 규율](../concepts/event-loop-thread-discipline.md)이 그 자리이고, 그쪽은
  자바 쪽 소스다. **겨루지 않는다** — 이 책은 그 모형을 규정하지 않고 파이썬 생태계의 인터페이스
  이름 하나로만 적는다.

## 미들웨어의 규정

- 규정 문장이 실물 설명 안에 있다 (10장, p.316):[^dynowski2025]

  > Middleware is a class whose behavior is applied across the application request-response
  > cycle. Before the request arrives at the specific function within the application, it goes
  > through the stack of middleware in the order specified by the application. After the
  > application generates the response, it goes through the middleware stack in reverse order.

- **곧 순서가 두 번 쓰이고 방향이 반대다.** 들어갈 때는 선언 순서대로, 나올 때는 역순이다.
- **저자들이 쌓은 미들웨어가 셋이다** — **출처 검증 미들웨어**, **신뢰 호스트 미들웨어**, 그리고
  **사용자 정의 JWT 인증 백엔드로 확장된 인증 미들웨어**다 (10장, p.316).[^dynowski2025]
  - **설정 값 둘의 뜻** — **허용 출처 목록은 서버에 연결하도록 허락된 클라이언트 출처들을 담고,
    허용 호스트 목록은 허용된 서버 호스트를 지정한다** (10장, p.316).[^dynowski2025]
- **엔드포인트도 둘로 갈린다** — **하나는 브라우저가 웹 페이지를 가져오는 데 쓰는 HTTP
  엔드포인트**이고, **다른 하나는 그 페이지의 자바스크립트가 경보를 받으려고 WebSocket 연결을
  세우는 데 쓰는 엔드포인트**다 (10장, p.317).[^dynowski2025]
  - **JWT를 얻는 엔드포인트가 따로 하나 더 있다** (10장, p.317).[^dynowski2025] 그 구현이
    같은 책 5장의 것이고 [REST API 구현 결정](rest-api-implementation-decisions.md) §"JWT의 세
    부분"에 있다.

## 미들웨어와 8장의 인터셉터

**이 절의 대조는 이 KB가 세운 것이다** — 다만 **저자들 자신이 8장에서 그 둘을 이어 두었다.**

- [gRPC와 RPC 스타일](grpc-and-rpc-style.md) §"구현이 쓰는 기능들"이 옮긴 8장의 인터셉터 규정은
  **"미들웨어와 비슷하다"**로 시작하고, **모든 RPC를 가로채 기능을 수행한 다음 사슬의 다음으로
  넘기며, 클라이언트와 서버 양쪽에서 구현될 수 있고, 흔한 쓸 자리는 캐싱·로깅·인증**이라고
  적는다. **이 장의 미들웨어 규정이 그 "비슷하다"의 다른 쪽 항이다.**
- **같은 것** — 둘 다 **사슬이고, 요청이 본 처리에 닿기 전에 지나며, 인증이 흔한 쓸 자리다.**
- **갈리는 것 셋이다.**
  - **단위가 다르다.** 인터셉터가 가로채는 것은 **RPC 하나**이고, 여기의 미들웨어가 걸리는 것은
    **요청-응답 주기**다. WebSocket에서 그 주기는 **여는 핸드셰이크 한 번**이므로, 미들웨어는
    **연결마다 한 번만 돈다.**
  - **되돌아 나오는 경로가 이쪽에만 명시된다.** 이 장의 규정은 **응답이 역순으로 스택을
    되돌아 나온다**고 적고, 8장의 인터셉터 규정은 그 방향을 적지 않는다.
  - **그래서 보안의 자리가 다르다.** 인터셉터는 **RPC마다** 인증을 다시 볼 수 있지만, 여기서는
    아래 §"JWT는 핸드셰이크에서 한 번만 검사된다"가 그것을 못 하는 이유를 적는다.
- #hypothesis **두 이름이 다른 까닭은 계보이지 기제가 아니다** — 저자들은 어원을 적지 않는다.

## 알림 엔드포인트가 드는 상태

- **연결을 여는 순간 서버가 하는 일** — **연결을 받아들이고, 질의 파라미터에서 도시의 UUID를
  읽는다** (10장, p.319).[^dynowski2025]
  - **UUID가 없거나 그 도시가 없으면 연결을 닫는다** — **WebSocket 상태 코드
    1008(Policy Violation)로 닫고, 그것이 닫힘 이벤트를 촉발한다** (10장,
    p.319).[^dynowski2025] 각주가 상태 코드의 출처를 RFC 6455로 가리킨다 (10장, p.319 각주
    8).[^dynowski2025]
  - **UUID가 있고 도시가 있으면 구독한다** — 그 UUID로 **Redis pub/sub 채널을 만들고 클라이언트가
    거기 구독한다** (10장, p.320).[^dynowski2025]
- **서버가 클라이언트 집합을 들고 있다** — **도시마다 연결된 WebSocket 클라이언트 전부를 담는
  사전이 만들어지고**, **연결이 닫히면 그 집합에서 지운다** (10장, pp.318–320).[^dynowski2025]
  - **이것이 앞 페이지의 단점 항목이 말한 상태다.**
    [WebSocket과 양방향 스타일](websocket-and-bidirectional-style.md) §"되무는 것 일곱"의
    상태 관리와 제한된 확장성이 여기서 실물로 보인다 — **연결 수만큼 자라는 자료 구조가 서버
    프로세스 안에 있다.**
- **메시지를 지켜보는 일이 비동기 과업으로 돈다** — 비공개 메서드 하나가 **pub/sub 채널에서 새
  메시지를 듣고**, **메시지 종류가 맞고 채널 속성이 도시의 UUID와 맞으면 연결된 모든 클라이언트에
  방송한다** (10장, p.320).[^dynowski2025]
  - **폴링 간격이 있다** — **메시지를 가져오는 메서드가 1초 간격의 논블로킹 루프 안에서 돌기
    때문에 채널에 도착하는 메시지를 계속 듣는다** (10장, p.320).[^dynowski2025] 곧 **브로커에서
    꺼내는 쪽은 여전히 폴링이고, 밀어 주는 것은 그 뒤 구간뿐이다.**
  - **경쟁 조건을 막는 잠금이 있다** — **`asyncio.Lock`이 Redis pub/sub 채널에서 온 메시지를
    처리하는 동안 경쟁 조건을 막는다** (10장, p.320).[^dynowski2025]

## 클라이언트 쪽 흐름 넷

- **저자들이 클라이언트 코드를 싣지 않는다** — **100줄이 넘어 인쇄판에서 설명하기 어렵기
  때문**이고, 대신 **연결이 끊겼을 때 클라이언트를 다시 잇는 백오프 알고리즘의 구현이 그 파일에
  있다**고 적으며 읽어 보라고 권한다 (10장, p.321).[^dynowski2025]
- **대신 프로그램 흐름을 넷으로 적는다** (10장, pp.321–322):[^dynowski2025]
  1. **클라이언트가 기본 사용자를 위한 접근 토큰(JWT)을 얻는다.**
  2. **접근 토큰과 도시 UUID를 질의 파라미터로 WebSocket 엔드포인트에 넘긴다.** 앞의 것은
     사용자를 인증하는 데, 뒤의 것은 pub/sub 채널에 구독하는 데 쓰인다.
     - **헤더로 넘기지 않는 이유가 명시된다** — **WebSocket API가 헤더를 넘기는 것을 허용하지
       않기 때문**이다 (10장, p.322).[^dynowski2025] 각주가 MDN 문서를 가리킨다.
     - **이것이 이 스타일의 보안이 HTTP API와 갈리는 첫 자리다.** HTTP API에서 토큰은
       `Authorization` 헤더로 가는데([REST API 구현 결정](rest-api-implementation-decisions.md)
       §"짧은 수명 토큰과 남는 위험"), 여기서는 **URL 안으로 들어간다.** #hypothesis 질의
       파라미터는 서버 접근 로그와 중개자에 남기 쉬우므로 이 배치는 헤더보다 노출면이 넓다 —
       저자들은 이 귀결을 적지 않는다.
  3. **연결을 세운 뒤 경보 메시지를 기다리고, 오면 사용자에게 보인다.**
  4. **연결이 예기치 않게 끊긴 것을 탐지하면**(닫힘 콜백에서 닫기 상태 코드를 확인해서)
     **재연결 함수를 불러 다시 잇기를 시도한다.**

## 보안 넷

- **저자들이 범위를 먼저 넓힌다** — **이 방법들은 WebSocket의 맥락에서 논의되지만 대부분의 HTTP
  기반 API에도 적용된다** (10장, p.322).[^dynowski2025]
- **넷이 목록으로 온다** (10장, p.322):[^dynowski2025]
  - **Origin 검증(Origin validation)** — **WebSocket 명세는 클라이언트의 `Origin` 헤더를 보안
    수단으로 쓰는 것을 정의하며, 그것으로 서버가 여는 핸드셰이크 요청을 받아들일지 거절할지
    정하게 한다.**
  - **신뢰 호스트 보안(Trusted host security)** — **클라이언트의 요청을 신뢰하는 호스트로 가는
    것만으로 제한한다.**
  - **JWT를 쓰는 토큰 기반 인증** — **토큰, 특히 JWT는 클라이언트를 인증하고 인가하는 무상태
    방법을 준다.** **WebSocket 맥락에서 이 토큰들은 핸드셰이크 동안 질의 문자열의 일부로
    넘겨져 서버가 검증할 수 있다.**
  - **전송 계층 보안(TLS)** — **네트워크로 오가는 애플리케이션 데이터에 암호화 기밀성과 무결성과
    진정성을 준다.** **WebSocket에서 그것은 안전한 통신을 위해 `ws://` 대신 `wss://`를 쓰는
    것을 뜻한다.**

## Origin 검증

- **모형의 이름과 갈리는 자리가 함께 적힌다** — **WebSocket 명세가 서술하는 보안 모형은 출처
  기반(origin-based)이고 동일 출처 정책(same-origin policy, SOP)과 비슷하다. 그러나 검증은
  서버가 수행한다** (10장, p.322).[^dynowski2025]
- **막으려는 것** — **서로 다른 출처를 가로지르는 인가되지 않은 자원 접근을 막는 데 도움이
  된다** (10장, p.322).[^dynowski2025]
- **판정 기준** — **출처 검증 모형에서 클라이언트는 같은 출처(곧 스킴과 호스트 이름과 포트)를
  공유할 때만 서버와 통신할 수 있고, 서버는 클라이언트의 여는 핸드셰이크 HTTP 요청의 `Origin`
  헤더를 확인해 출처를 검사한다** (10장, p.322).[^dynowski2025]
- **한계가 앞 페이지의 단점 항목에 적혀 있다** — **악의적 사용자가 여는 핸드셰이크 동안 `Origin`
  헤더를 바꿔 이 모형을 우회할 수 있다** (10장, p.332).[^dynowski2025] 곧 **이 검증은 브라우저가
  규칙을 지킬 때만 효력이 있고 브라우저가 아닌 클라이언트에는 보증이 되지 않는다.**
  - **이 KB에는 동일 출처 정책을 다루는 페이지가 없다.** 위 서술은 이 책을 통한 2차 경유이고,
    브라우저 보안 모형 자체의 원전은 아직 들어와 있지 않다.

## 신뢰 호스트

- **기제** — **클라이언트의 여는 핸드셰이크 HTTP 요청에서 `host` 헤더를 확인하고, 이름이 말하듯
  그 값이 서버의 신뢰 호스트 목록에 든 요청만 받아들인다** (10장, p.323).[^dynowski2025]
- **막으려는 것** — **서버 호스트를 허용 목록의 호스트 이름이나 IP 주소로 제한함으로써 HTTP
  호스트 헤더 공격(HTTP host header attack)의 위험을 줄인다** (10장, p.323).[^dynowski2025]
- **`Host` 헤더가 무엇을 위해 생겼는가**는 같은 책 4장의 것이고
  [HTTP 초기 판들과 TCP의 한계](http-early-versions-and-tcp-limits.md) §"Host 헤더와 가상
  호스팅"에 있다. **가상 호스팅을 가능하게 한 필드가 여기서는 공격면**이다.

## JWT는 핸드셰이크에서 한 번만 검사된다

- **검증의 자리** — 저자들은 **여는 핸드셰이크에서 얻은 JWT의 서버 쪽 검증**을 구현하고, 그
  일을 맡는 것이 **인증 미들웨어를 확장한 사용자 정의 인증 백엔드**이며 그것이 **JWT를 검증하고
  사용자 신원을 제공하는 책임**을 진다 (10장, p.323).[^dynowski2025]
- **검사 순서가 적힌다** (10장, pp.323–324):[^dynowski2025]
  - **엔드포인트가 인증을 요구하는 집합에 드는지 먼저 본다.** 들지 않으면 **그 연결은 인증될
    의도가 아니므로 요청이 인증되지 않은 채 진행된다.**
  - **최초의 여는 핸드셰이크 요청에서 질의 파라미터에 접근 토큰이 있는지 확인한다.** 없으면
    거절한다.
  - **JWT의 인코딩된 적재물을 해독한다.** 해독 중에 무엇이든 잘못되면 거절한다.
  - **적재물에서 만료 시각을 뽑아 현재 시각과 견준다.** 만료되었으면 거절한다.
  - **적재물의 사용자 ID로 데이터베이스에서 사용자를 찾는다.** 없으면 거절한다.
  - **성공하면 인증 자격 객체와 사용자 객체를 돌려준다.**
- **왜 최초 핸드셰이크에서만 보는지를 저자들이 스스로 묻고 답한다** (10장,
  p.324):[^dynowski2025]

  > This is because after a WebSocket connection is established, it's assumed to be trusted.

- **이 한 문장이 이 스타일의 보안을 규정한다.** 앞 페이지의 단점 항목이 같은 사실의 귀결을
  적는다 — **연결 뒤의 보안이 더 필요하면 프레임마다 검증하는 애플리케이션 수준 인증을 구현해야
  한다**(10장, p.332).[^dynowski2025]
- **이 KB에 그 가정을 정면으로 치는 축이 있다.**
  [암묵적 신뢰와 제로 트러스트](../concepts/zero-trust-and-implicit-trust.md)가 **위치나 앞선
  검증에서 신뢰를 파생시키지 말라**고 적는다. **모순이 아니라 층이 다르다** — 이 책은 그
  가정을 **프로토콜이 준 성질**로 적고 그 대가를 단점 칸에 적으며, 그쪽은 그 가정 자체를
  **아키텍처 원칙으로 금지**한다. **두 서술을 겹쳐 읽으면 판정 하나가 나온다** — #hypothesis
  제로 트러스트를 지키려는 체계에서 WebSocket을 쓰려면 프레임 수준 인증이 선택이 아니라 요구가
  된다. 저자들은 그 결론까지 가지 않는다.
  - 토큰의 수명과 남는 위험은
    [서비스 사이 인증과 인가](../concepts/service-to-service-authentication-and-authorization.md)와
    [REST API 구현 결정](rest-api-implementation-decisions.md)이 갖는다.

## TLS와 wss

- **필요의 자리** — **WebSocket 같은 애플리케이션 계층 프로토콜을 다룰 때 필요한 방어선 하나가
  전송 중 데이터를 암호화하는 것**이고, **TLS 프로토콜이 전송하는 동안 암호화해 클라이언트와
  서버 사이에 오가는 데이터를 지킨다** (10장, p.325).[^dynowski2025]
- **저자들의 절차** — **환경 변수 하나가 자체 서명 SSL 인증서의 생성을 촉발하는 문지기 구실을
  하고**, 만들어진 **인증서와 비공개 키가 각각 두 플래그로 ASGI 웹 서버에 건네지며, 그 서버가
  WebSocket API를 노출하는 애플리케이션 앞에 선다** (10장, p.325).[^dynowski2025]
- **곁주가 한계를 적는다** — **자체 서명 인증서는 테스트에는 쓸 수 있으나 운영 환경에는
  권장되지 않으므로, 운영에서 WebSocket(이나 다른 어떤) 연결을 TLS로 암호화할 때는 신뢰받는
  CA가 발급한 인증서를 쓰라** (10장, p.325).[^dynowski2025]
  - **같은 책 5장이 그 저울을 절 하나로 다뤘고** 그 자리가
    [REST API 구현 결정](rest-api-implementation-decisions.md) §"자체 서명 인증서와 CA 서명
    인증서"다. **되풀이하지 않는다.**
- **눈에 보이는 결과가 스킴이다** — 암호화된 뒤 **WebSocket 프로토콜의 스킴이 `ws://`가 아니라
  `wss://`가 된다** (10장, p.325).[^dynowski2025]

## 문서화 — AsyncAPI

- **어느 범주에 드는가로 시작한다** — **대부분의 WebSocket 구현은 비동기 API 범주에 들고, 거기서
  데이터는 블로킹하지 않는 방식으로 교환된다** (10장, p.326).[^dynowski2025]
- **고른 명세와 그 사정거리** — **AsyncAPI 명세로 문서화하며, AsyncAPI가 이벤트 기반
  아키텍처(EDA)로 지어진 애플리케이션의 문서화에 초점을 두지만 WebSocket API도 지원한다**
  (10장, p.326).[^dynowski2025]
- **OpenAPI와의 관계** — **AsyncAPI는 OpenAPI를 보완하는 프로젝트이되 초점이 비동기 API에
  있고**, **AsyncAPI 명세는 비동기 API를 문서화하고 시험하고 시각화하는 데 가장 널리 쓰이는
  표준**이며, **AsyncAPI 계약은 이식 가능한 형식(YAML이나 JSON)으로 API 사용자(개발자·테스터·
  아키텍트 등)와 공유된다** (10장, p.326).[^dynowski2025]
- **프로젝트의 지위와 성격** (10장, p.326):[^dynowski2025]
  - **리눅스 재단 아래의 오픈 소스 프로젝트이고 EDA를 다루기 쉽게 만드는 것을 돕는다.**
  - **특정 기술에 매이지 않는다** — **애플리케이션이 비동기로 소통하는 방식을 서술하는 길과,
    이벤트 기반 체계를 시험하고 감시하고 관리하는 도구를 함께 준다.**
  - **AsyncAPI 명세는 OAS에서 영감을 받았고, OAS는 전에 Swagger로 알려져 있었다.**
- **문서가 담는 필드가 여섯으로 적힌다** (10장, pp.327–328):[^dynowski2025]
  - **`asyncapi`는 명세의 판을 지정한다.**
  - **`defaultContentType`은 메시지가 기본적으로 JSON으로 인코딩된다는 것을 알린다.**
  - **`operations`는 WebSocket API 엔드포인트에 수행할 수 있는 연산을 서술한다.** 저자들의
    연산 하나는 **경보 채널에서 메시지를 받는 책임**을 지고 `action: receive`로 서술된다.
  - **`channels`는 메시지를 받는 WebSocket 엔드포인트를 담는다.**
  - **`bindings`는 연결을 세우는 데 쓰이는 결속을 서술한다.** 저자들의 경우 **접근 토큰과 도시
    UUID라는 질의 파라미터 둘을 기대한다.**
  - **`messages`는 엔드포인트에서 받는 메시지의 스키마를 서술한다.**
- **낱말 하나에 경고가 붙는다** — **여기서 채널(channel)은 AsyncAPI가 서술하는 개념이지 Redis의
  것이 아니다** (10장, p.327).[^dynowski2025] 그리고 AsyncAPI 쪽에서 채널은 **서버가 노출하는
  주소 지정 가능한 컴포넌트**다.
  - **같은 낱말이 이 페이지 안에서 두 번 다른 것을 가리킨다** — 위 §"프로세스가 둘이라 다리가
    필요했다"의 채널은 Redis의 것이고, 여기의 채널은 문서 형식의 것이다. **저자들이 그 겹침을
    스스로 경고한다.**
- **HTML 문서로 바꿀 수 있다** — **AsyncAPI 스키마를 HTML 문서로 바꿔 사용자에게 노출하면 API의
  발견 가능성을 높일 수 있다** (10장, p.328).[^dynowski2025] 저자들은 CLI 도커 이미지로 생성하고
  웹 서버로 내주는 절차를 싣는다.
- **온라인 도구에 같은 유보가 붙는다** — **믿는 온라인 서비스에만 정보를 붙여 넣고 지역 대안을
  선호하라** (10장, p.328).[^dynowski2025] 같은 경고를 앞 장의 문서화 절도 달았다 —
  [웹훅과 콜백 스타일](webhooks-and-callback-style.md) §"문서화 — OpenAPI의 두 필드"다.
- **같은 명세가 AMQP 큐를 서술하는 자리는 같은 책 11장이다** —
  [RabbitMQ의 전달과 보안과 문서화](rabbitmq-delivery-security-and-documentation.md)가
  채널과 연산의 AMQP 바인딩과 메시지 버저닝을 담는다. **여기의 "채널은 Redis의 것이 아니다"라는
  경고와 같은 모양의 경고가 거기에도 있다** — 거기서는 AsyncAPI의 채널이 RabbitMQ의 채널이
  아니다.
- **이 KB에 AsyncAPI의 원전은 없었다.** 지금까지는 다른 소스들이 이름으로만 적었다 —
  [웹 서비스와 REST](../concepts/web-services-and-rest.md)가 이벤트 기반 인터페이스 문서화의
  선택지 둘 가운데 하나로, [후진 호환과 전진 호환](../concepts/backward-and-forward-compatibility.md)이
  CloudEvents와 나란히, [발행/구독 메시징](../concepts/publish-subscribe-messaging.md)이
  "OpenAPI의 메시징 판"으로 적었다. **이 절이 그 이름의 첫 구성 요소 서술이다.**

## 이 KB의 이웃과 맞대는 자리

**이 절의 대조는 이 KB가 세운 것이다** — 이 책은 아래 소스들을 인용하지 않는다.

- **이 구현이 실은 스타일 둘을 겹쳐 쓴다.** 밖으로 보이는 것은 WebSocket이고, 프로세스 둘 사이의
  안쪽은 브로커다. **곧 같은 책이 11장으로 미룬 발행-구독이 10장의 구현 안에 이미 들어와
  있다.** #hypothesis 이 겹침은 우연이 아니라 필연이다 — 연결을 든 프로세스와 사건을 만드는
  프로세스가 다르면 둘을 이을 것이 필요하고, 그 자리를 브로커가 메운다. 저자들은 그것을
  "쓸 자리에 맞아서"라고만 적는다.
- **알림의 세 길 가운데 둘이 한 체계 안에 있다.**
  [웹훅과 콜백 스타일](webhooks-and-callback-style.md) §"알림의 세 길"의 대조표에서 이 구현은
  **브로커 줄(안쪽)과 그 어느 줄도 아닌 지속 연결(바깥쪽)을 잇대어 쓴다.** 그리고 그 이음매에서
  **밖으로 미는 구간만 푸시이고 브로커에서 꺼내는 구간은 여전히 1초 폴링**이다.
- **상태를 어디에 둘 것인가가 이 KB의 오래된 물음이다.**
  [상태 있는 마이크로서비스와 상태 저장소](../concepts/stateful-microservices-and-state-stores.md)가
  그 자리인데, 여기서 서버가 드는 상태는 **연결 자체**라 저장소로 옮길 수 없다. **그것이 앞
  페이지의 §"제한된 확장성"이 서버마다 연결 수를 제한하라고 적는 이유**다.
- **판정 하나** — **이 페이지는 `contradicts`를 걸지 않았다.** 위 제로 트러스트와의 대조가 이
  런에서 가장 팽팽한 자리였으나, 한쪽은 프로토콜의 성질을 적고 다른 쪽은 아키텍처 원칙을
  적으므로 **같은 층위의 사실 충돌이 아니다.**
