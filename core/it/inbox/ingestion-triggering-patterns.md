하나의 질문: **반입할 데이터가 준비됐다는 것을 누가 어떻게 알리는가.**

## 질문 — 언제 시작하는가

- 저자가 반입 의미론(전체·증분·복제·컴팩션)을 다 다룬 뒤 남겨 둔 물음이다 — **지금까지 다룬
  다른 데이터 반입 의미론이 이 겉보기에 쉬운 데이터 반입 태스크에서 만날 수 있는 유일한 문제는
  아니다. 다음으로 확실히 스스로에게 묻게 될 문제적 질문은 "반입 프로세스를 언제 시작해야
  하는가?"다** (2장, p.30).[^konieczny2025]
- 문제 서술의 실물 — 매시간 메달리온 아키텍처의 Silver 계층 데이터를 준비하는 배치 잡이 있고
  다른 팀들이 그것으로 ML 모델과 BI 대시보드를 만드는데, **그들은 불완전한 데이터셋에 대해 자주
  불평하고, 언제 당신의 데이터를 소비하기 시작할 수 있는지 직접 또는 간접으로 알려 줄 기제를
  구현해 달라고 요청했다** (2장, p.30).[^konieczny2025]
- 왜 직접 호출로 못 푸는가 — **이 이슈는 논리적으로 의존하지만 물리적으로 격리된, 다른 팀들이
  유지하는 파이프라인에서 특히 두드러진다. 그 격리된 워크로드 때문에 당신의 잡이 하류
  파이프라인을 직접 촉발하는 것은 흔히 가능하지 않다** (2장, p.30).[^konieczny2025]
  **조직 경계가 기술 해법을 정한다** — 그래서 답이 호출이 아니라 **표시**가 된다.

## Readiness Marker — 소비자가 기다린다

- 정의 — **Readiness Marker는 가장 적절한 순간에 반입 프로세스를 촉발하도록 돕는 패턴이다.
  그 목표는 완전한 데이터셋의 반입을 보장하는 것이다** (2장, p.30).[^konieczny2025]
- 구현은 데이터 형식과 저장 조직에 달렸고, 저자가 둘을 든다 (2장, pp.30–31):[^konieczny2025]
  - **플래그 파일(flag file)** — 성공적 데이터 생성 뒤에 만들어지는 파일로 데이터셋의 완결을
    신호한다. **현대 데이터 아키텍처에서 오브젝트 저장과 분산 파일 시스템이 인기 있는 덕분에
    이 접근은 쉽게 구현된다.** 데이터 처리 계층에서 네이티브로 제공될 수도 있다 — Apache
    Spark는 원시 파일 형식에 `_SUCCESS` 파일을 쓰고, Delta Lake는 새 커밋 로그를 쓴다. 네이티브
    지원이 없으면 **데이터 오케스트레이션 계층에서 데이터 처리 성공 뒤 실행되는 별도 태스크로**
    플래그 파일을 구현한다.
  - **관례적 파티션(conventional)** — 시간 기반 테이블·위치를 생성한다면 Readiness Marker가
    관례일 수 있다. **잡이 매시간 돌며 시간 기반 파티션에 데이터를 쓴다면, 10:00 실행은 파티션
    10에, 11:00 실행은 11에 쓴다. 소비자가 파티션 10을 처리하고 싶다면 당신의 잡이 파티션 11에서
    작업하기를 기다리기만 하면 된다.**
- 결과 ① **강제력의 부재(lack of enforcement)** — **플래그 파일이나 다음 파티션 탐지에 기반한
  관례적 준비 상태를 강제할 쉬운 방법이 없다. 어느 쪽이든 소비자는 당신이 그것을 생성하는 중에
  데이터셋을 소비하기 시작할 수 있다** (2장, p.31).[^konieczny2025]
  - 그래서 완화책이 기술이 아니라 합의다 — **이 암묵성 때문에 소비자와 소통하고 그들 쪽 처리를
    촉발할 수 있는 조건에 합의하는 것이 매우 중요하다. 추가로 준비 상태 관례를 존중하지 않을
    때의 위험을 명확히 설명해야 한다** (2장, p.31).[^konieczny2025]
- 결과 ② **늦은 데이터에 대한 신뢰성** — **파티션이 이벤트 시각에 기반하면 파티션 기반 구현은
  늦은 데이터(late data) 이슈를 겪는다** (2장, p.31).[^konieczny2025]
  - 저자의 시나리오가 정확하다 — 8·9·10시 파티션을 닫았고 소비자들이 이미 그 셋을 처리했는데,
    **방금 9시에 대한 늦은 데이터를 탐지했다. 파티션이 이벤트 시각 기반이므로 이 데이터를 9시
    파티션에 통합하기로 정한다. 소비자들은 그 파티션을 닫힌 것으로 간주할 수 있으므로 아마
    같은 일을 하지 못할 것이다** (2장, p.31).[^konieczny2025]
  - 처방은 둘 중 하나를 **명시적으로 고르는 것**이다 — **파티션을 한 번 닫히면 결코 바뀌지 않는
    불변 부분으로 간주하거나, 가변성 조건을 명확히 정의해 소비자와 공유하라. 파티션 갱신을
    공유하는 것 외에 결국 처리해야 할 새 데이터를 그들에게 알려야 한다** (2장,
    p.31).[^konieczny2025] 늦은 데이터 자체는
    [스트림 반입 고려사항](stream-ingestion-considerations.md)이 받는다.
- 구현의 실물 — Spark는 Parquet·Avro 등 지원 형식을 생성할 때 **언제나 데이터 파일을 먼저 쓰고
  그 연산이 완료될 때만 마커 파일을 생성한다** (2장, p.31).[^konieczny2025] 소비자 쪽은 Airflow의
  `FileSensor`에 `_SUCCESS` 경로를 조건으로 걸고, `mode='reschedule'`을 준다 — **그 덕에 센서
  태스크가 중단 없이 워커 슬롯을 점유하지 않고, 대신 깨어나 설정된 파일이 존재하는지 검증한다.
  다른 태스크가 처리 준비가 됐는데도 오케스트레이션 계층이 데이터를 기다리느라 바쁜 것을 피하려면
  고려해야 할 중요한 지점이다** (2장, p.32).[^konieczny2025]
- 네이티브 지원이 없을 때 마커를 직접 만드는 형태가 이 패턴의 대표 코드다 (2장,
  p.32):[^konieczny2025]

  ```python
  @task
  def delete_dataset():
    shutil.rmtree(dataset_dir, ignore_errors=True)

  @task
  def generate_dataset():
    ...  # 처리 부분

  @task
  def create_readiness_file():
    with open(f'{dataset_dir}/COMPLETED', 'w') as marker_file:
      marker_file.write('')

  delete_dataset() >> generate_dataset() >> create_readiness_file()
  ```

  - **여기서 명심할 가장 중요한 것은 준비 마커가 언제나 파이프라인의 마지막 단계로, 즉 데이터셋의
    마지막 변환을 수행한 뒤에 생성돼야 한다는 것이다** (2장, p.33).[^konieczny2025]

## External Trigger — 생산자가 알린다

- 자리 — **이상적인 데이터 반입 시나리오에서는 새 데이터셋이 정규 일정으로 사용 가능하다.
  파이프라인을 촉발하고 처리 전에 Readiness Marker 패턴을 쓸 수 있다. 덜 이상적인 시나리오에서는
  들어오는 빈도를 예측하기 어렵다. 그 결과 정적 반입에서 이벤트 주도 반입으로 사고방식을 바꿔야
  한다** (2장, p.33).[^konieczny2025]
- 두 패턴의 대비를 저자가 한 문장으로 놓는다 (2장, p.33):[^konieczny2025]

  > The Readiness Marker pattern from the previous section relies on pull semantics, in
  > which the consumer is responsible for checking whether there is new data to process.
  > But the event-driven nature of a dataset favors push semantics, in which the producer
  > is in charge of notifying consumers about data availability.

- 문제 서술이 비용 논증이다 — 백엔드 팀이 주에 최대 한 번, 월요일과 목요일 사이에 새 기능을
  릴리스하는데 참조 데이터셋 갱신 잡은 하루 한 번 스케줄돼 있어 **변경이 없을 때도 데이터를
  다시 적재해 컴퓨트 자원을 낭비했다** (2장, p.33).[^konieczny2025] 저자의 판정 —
  **시간 스케줄된 잡으로 전체 데이터셋을 복사하거나 새 것이 있는지 아주 자주 확인하는 것으로 풀
  수 있지만, 이는 컴퓨트 자원을 낭비하고 불필요한 운영 부담을 더한다** (2장,
  p.33).[^konieczny2025]
- 패턴은 **세 주요 동작으로 구성된다** (2장, p.34):[^konieczny2025]
  1. **알림 채널 구독** — 외부 세계(이벤트 주도 생산자)와 당신의 파이프라인 사이의 연결을
     설정한다. 이제부터 새 일이 생길 때마다 그것을 다룰 능력을 갖는다.
  2. **알림에 반응** — 이벤트 핸들러다. **이벤트를 분석해 그것이 데이터 오케스트레이션 계층의
     파이프라인을 촉발하거나 데이터 처리 계층의 잡을 시작하는 결과를 낳아야 하는지 결정한다.**
     메시지 버스 기술에 따라 핸들러가 특정 이벤트(예: 주어진 테이블의 데이터 생성)를 구독할 수
     있고, **그 필터링 기능이 가능하지 않으면 핸들러가 스스로 구현해야 한다.**
  3. **반입 파이프라인 촉발** — **단순함을 위해 한 이벤트가 한 반입 파이프라인을 촉발해야 한다.
     그러나 같은 데이터셋이 여러 워크로드의 입력 데이터 원천일 때처럼 여럿을 시작하는 것도
     가능하다.**
- 결과 ① **푸시 대 풀** — External Trigger 구성 요소 자체가 둘 중 하나로 구현될 수 있다는 것이
  이 패턴의 미묘한 점이다 (2장, pp.34–35):[^konieczny2025]
  - **풀 기반 트리거는 처리할 새 이벤트가 있는지 연속적으로 확인하고, 푸시 기반 트리거는
    이벤트 생산자가 처리할 새 것을 알려 주지 않는 한 아무것도 하지 않는다.**
  - **풀 기반 트리거는 장기 실행 잡이라 짧고 규칙적인 간격으로 확인하며 떠 있는 프로세스다.
    기술적으로 유효한 구현이지만, 잡이 알림 원천에서 0개 메시지를 당기는 데 대부분의 시간을 쓸
    수 있으므로 가장 최적화된 것은 아니다.**
  - **더 나은 대안은 푸시 기반 트리거로, 데이터 원천이 버스에 있는 새 메시지에 대해 엔드포인트에
    알린다. 각 알림 메시지는 이벤트에 반응한 뒤 끝나는 새 컨슈머 인스턴스를 시작한다.**
- 결과 ② **실행 맥락(execution context)** — **외부 트리거가 데이터 오케스트레이터 엔드포인트를
  호출하는 **그냥 핑** 기제가 될 위험이 있다. 이 단순주의적 접근이 유혹적이지만, 촉발된 반입
  파이프라인도 다른 것과 마찬가지로 유지돼야 함을 명심해야 한다. 그저 촉발만 하면 그것이 왜
  촉발됐고 무엇을 처리해야 하는지 이해할 충분한 맥락이 없을 수 있다** (2장,
  p.35).[^konieczny2025]
  - 완화책 — **트리거 잡의 버전, 알림 봉투(envelope), 처리 시각, 이벤트 시각을 포함해 적절한
    메타데이터 정보로 촉발 호출을 풍부하게 하는 것이 중요하다. 결국 실패의 이유를 조사해야 할
    일상 모니터링에서 유용할 것이다** (2장, p.35).[^konieczny2025]
- 결과 ③ **오류 관리** — **여기서 이벤트가 핵심 요소이고, 그것 없이는 어떤 작업도 촉발할 수
  없다. 그런 이유로 무슨 일이 있어도 이벤트를 지키는 것을 목표로 실패를 염두에 두고 트리거를
  설계해야 한다. 전형적으로 여기서 데드레터(Dead-Letter) 패턴처럼 다음 장에 서술된 패턴에
  의존하게 될 것이다** (2장, p.35).[^konieczny2025]
- 구현 — **클라우드에서 구현하기 쉽다. AWS·Azure·GCP가 이 이벤트 주도 능력을 가능하게 하는
  서버리스 함수 서비스를 제공하므로 트리거의 훌륭한 후보다. 게다가 대부분의 데이터
  오케스트레이터가 파이프라인을 시작하는 데 쓸 수 있는 API를 노출한다** (2장,
  p.35).[^konieczny2025]
  - Airflow 쪽에서 촉발 대상이 되는 DAG는 `schedule_interval=None`을 갖는다 — **이는 Airflow
    스케줄러가 계획 단계에서 그것을 무시하고, 파이프라인을 시작하는 유일한 방법이 명시적 트리거
    액션이라는 뜻이다. 감시되는 S3 버킷에 새 객체가 나타날 때마다 도는 Lambda 함수의 책임이 될
    것이다** (2장, p.36).[^konieczny2025] 그 Lambda 핸들러는 이벤트·트리거 메타데이터(함수
    이름·버전·요청 ID)·적재할 파일 경로·DAG 실행 ID를 담은 페이로드를 만들어 Airflow의
    `dagRuns` API에 POST하고, 200이 아니면 예외를 던진다 (2장, p.36).[^konieczny2025]
  - 복원력은 코드가 아니라 인프라에 있다 — **AWS Lambda는 그것을 인프라 수준에서 실패 이벤트
    목적지(failed-event destinations)로 구현한다. 서비스가 실패한 함수 호출의 레코드를 보낸다.
    스트림 데이터 원천에 대해 배치 크기나 동시성 수준도 설정할 수 있다** (2장,
    p.36).[^konieczny2025]
  - 저자가 예제 코드의 지위를 여기서 못 박는다 — **코드 스니펫은 달리 명시되지 않는 한 가독성을
    염두에 두고 쓰였다.** 그래서 예제에 하드코딩된 자격 증명이 보이는데, **일반 규칙으로 코드에
    자격 증명을 직접 하드코딩하는 것은 쉽게 유출될 수 있으므로 나쁜 관행**이고 7장의 데이터 보안
    디자인 패턴이 그 완화책이다 (2장, p.36).[^konieczny2025] 이 KB가 그 예제를 펜스로 옮기지
    않은 이유도 같다.

## 두 패턴을 가르는 축

| | Readiness Marker | External Trigger |
|---|---|---|
| 의미론 | 풀 — 소비자가 확인한다 | 푸시 — 생산자가 알린다 |
| 전제 | 데이터가 정규 일정으로 도착한다 | 도착 빈도를 예측할 수 없다 |
| 신호의 실물 | 플래그 파일(`_SUCCESS`·`COMPLETED`) 또는 다음 파티션 | 메시지 버스의 알림 이벤트 |
| 강제력 | 없다 — 관례와 소통에 의존 | 이벤트 유실이 곧 미실행이라 오류 관리가 필수 |
| 대표 위험 | 이벤트 시각 파티션 + 늦은 데이터 | 맥락 없는 "그냥 핑"으로 퇴화 |

- 두 패턴이 배타적이지 않다는 것도 짚어 둘 만하다. External Trigger의 세 번째 동작(파이프라인
  촉발)이 촉발하는 그 파이프라인이 다시 Readiness Marker를 마지막 태스크로 갖는 구성이
  자연스럽다 — 저자의 Airflow 예제 둘이 실제로 그 모양이다.
