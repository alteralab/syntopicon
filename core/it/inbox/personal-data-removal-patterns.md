하나의 질문: **사용자가 자기 데이터를 지우라고 했을 때, 지워야 할 것을 어떻게 줄이거나 갈아
끼우는가.**

Konieczny의 7장은 데이터 보안을 네 범주로 가르는데(제거·접근 제어·데이터 보호·연결), 이 페이지는
첫 범주인 **데이터 제거**(Data Removal)의 두 패턴을 다룬다. 나머지 셋은
[세밀한 접근과 자격 증명 패턴](fine-grained-access-and-credential-patterns.md)과
[암호화와 익명화 패턴](data-encryption-and-anonymization-patterns.md)에 있다.

## 삭제 요청이라는 요구 사항

- 장 전체의 좌표 — **데이터 엔지니어링은 데이터 처리 잡을 쓰는 것에서 멈출 수 없다. 요즘 데이터
  엔지니어는 보안 측면도 생각해야 한다. 지난 몇 년간 막대한 견인력을 얻은 측면 하나가 컴플라이언스다.
  유럽의 GDPR이나 미국의 CCPA 같은 데이터 프라이버시 법은 당신(데이터 제공자)과 고객(데이터 소비자)
  사이의 경계를 정확히 정의한다** (7장, p.197).[^konieczny2025]
- 이 범주가 답하는 요구 하나 — **CCPA와 GDPR 같은 프라이버시 규제는 여러 중요한 컴플라이언스
  요구 사항을 정의한다. 그중 중요한 하나가 개인 데이터 제거 요청에 초점을 맞추는데, 사용자로부터
  제거 요청을 받으면 그 사용자의 데이터를 삭제해야 한다** (7장, p.197).[^konieczny2025]
- **두 패턴은 대안이 아니라 조건에 따라 갈린다** — 저자가 둘째 패턴의 도입부에서 그 조건을 명시한다.
  **Vertical Partitioner 패턴은 새 프로젝트를 시작하거나 기존 작업부하를 이전할 시간과 컴퓨트
  자원이 충분할 때 훌륭하다. 그러나 그 편안한 위치 중 하나에 있지 않다면, 검증된 덮어쓰기 전략에
  의존하는 것 말고 다른 선택지가 없을 수 있다** (7장, p.203).[^konieczny2025]

## Vertical Partitioner — 지울 것을 한 번만 쓴다

- 문제의 실물 — 개인 데이터 제거 파이프라인 설계 문서에 동료들이 저장 오버헤드를 지적했다.
  **데이터셋의 여러 열이 불변이다. 달리 말해 그것들은 결코 바뀌지 않으면서 동시에 모든 레코드에
  존재한다. 그런 속성의 예가 생일이나 개인 ID 번호다.** 그래서 동료들이 요구한 것은
  **각 불변 속성을 한 번만 저장하라는 것이다. 결과적으로 데이터 제거 요청이 있을 때 지울 데이터가
  더 적어진다** (7장, p.198).[^konieczny2025]
- 해법은 데이터셋을 **가변 부분과 불변 부분 둘로 나누는 것**이다 (7장, p.198).[^konieczny2025]
  - 저자가 먼저 낱말을 가른다 — **데이터 엔지니어링에서 데이터셋을 수평 또는 수직으로 분할할 수
    있다. 수평 분할(horizontal partitioning)은 관련 속성을 가진 모든 레코드를 함께 놓는다. 가장
    빈번한 예가 날짜 기반 분할로, 배치 잡의 증분 데이터 처리에 자주 쓰인다** (7장,
    p.198).[^konieczny2025]
  - **수평 분할의 대안이 수직 분할(vertical partitioning)이다. 이 접근은 각 행을 쪼개어 그
    부분들을 다른 곳에 쓴다. 속성 기반 분할은 효율적인 개인 데이터 제거 파이프라인을 구현하는 것을
    도울 수 있다** (7장, p.199).[^konieczny2025]
  - 상자 하나가 배타 관계가 아님을 못 박는다 — **수직 분할을 수평 분할과 결합해, 관련되지만 쪼개진
    레코드 부분을 같은 저장 존에 그룹지을 수 있다** (7장, p.199).[^konieczny2025]
- 구현의 첫 단계는 **쪼갤 열과, 쪼개진 행을 나중에 다시 합칠 때 쓸 속성을 식별하는 것**이다. 저자의
  그림에서 그 속성은 `user_id`이고, **값이 새 레코드마다 달라지는 이벤트 속성은 별도 저장으로
  전달되는 반면 변하지 않는 것과 개인 데이터 범위에 관련된 것은 다른 곳에 쓰인다** (7장,
  p.199).[^konieczny2025]
- 얻는 것 — **개인 데이터 제거 요청에 관해서라면 이 해법은 제거할 데이터의 양을 상당히 줄인다.
  각 레코드에서 반복되던 사적 속성이 이제 한 번만 쓰인다. 결과적으로 제거 프로세스가 처리할 데이터가
  더 적다. 비분할 저장에서의 제거보다 계산 관점에서도 금전 관점에서도 덜 비싸야 한다. 마지막으로,
  이 완전히 분리된 저장 계층 덕에 다른 데이터 접근이나 데이터 보존 규칙을 적용할 수 있다** (7장,
  p.200).[^konieczny2025]
- Spark의 `foreachBatch`가 이 패턴의 대표 코드다 — **들어오는 레코드를 쪼개는 잡의 첫 부분으로,
  두 데이터셋을 만들어 각각을 다른 카프카 토픽에 쓴다** (7장, p.201):[^konieczny2025]

  ```python
  def split_visit_attributes(visits_to_save: DataFrame, batch_number: int):
    visits_to_save.persist()

    visits_without_user_context = (visits_to_save
      .filter('user_id IS NOT NULL AND context.user.login IS NOT NULL')
      .withColumn('context', F.col('context').dropFields('user'))
      .select(F.col('visit_id').alias('key'), F.to_json(F.struct('*')).alias('value')))
    # save to visits_without_user_context

    user_context_to_save = (visits_to_save.selectExpr('context.user.*', 'user_id')
      .select(F.col('user_id').alias('key'), F.to_json(F.struct('*')).alias('value')))
    # save to user_context_to_save

    visits_to_save.unpersist()
  ```

  - 쪼갠 뒤의 흐름 — **분할된 user context 토픽은 나중에 다른 잡이 `MERGE` 연산으로 항목을 중복
    제거하며 Delta Lake 테이블로 변환할 수 있다** (7장, p.202).[^konieczny2025] 그 테이블에서
    제거는 `delete` 액션이고, **이 액션은 보존 기간을 넘긴 삭제된 사용자의 파일을 제거하기 위해
    추가 `VACUUM` 연산 실행을 요구한다. 그러지 않으면 테이블의 더 오래된 버전을 읽어 여전히 그
    사용자의 데이터를 가져올 수 있다** (7장, p.202).[^konieczny2025]

## 쓰기를 싸게 만든 값을 읽기가 치른다

- **질의 성능** — **수직 분할은 불변 속성이 가변 속성과 떨어져 사는 일종의 데이터 정규화를 들여온다.
  이는 볼륨을 줄여 쓰기 성능을 최적화하지만, 각 리더가 쪼개진 행을 조인해야 하므로 읽기 성능도
  떨어뜨린다. 그러면 어떤 읽기 연산이든 네트워크 트래픽을 수반하게 되는데, 보통 비분할 판에서는 행
  수준에서 읽기가 국소적으로 남는다** (7장, p.200).[^konieczny2025]
- **질의 복잡성** — **데이터 분리는 질의에 추가 복잡성도 가져온다. 소비자는 일부 속성이 다른 곳에
  있을 수 있음을 알아야 한다. 다행히 이 문제는 단일 진입점(뷰 같은)에서 데이터셋을 노출하거나,
  데이터 문서(예컨대 데이터 카탈로그)를 제공하거나, 데이터 리니지를 명확히 노출하는 것으로 꽤 쉽게
  완화할 수 있다** (7장, p.200).[^konieczny2025]
- **폴리글랏 세계의 복잡성** — **한 데이터셋이 여러 종류의 저장(NoSQL 데이터베이스와 관계형
  데이터베이스 같은)에 동시에 사는 폴리글랏 지속성(polyglot persistence) 세계에 걸리는 도전이다.
  폴리글랏 지속성은 리더에게 훌륭한데, 주어진 레코드를 소비자에 맞춘 기술로 노출하기 때문이다. 예컨대
  검색 엔진 기능은 검색 최적화 데이터베이스를 쓰고 싶어 하는 반면, 저지연 마이크로서비스는 같은
  레코드를 키-값 저장에서 매우 빠르게 얻어야 할 수 있다. 결과적으로 이 수직 분할을 여러 데이터 제거
  파이프라인을 포함해 여러 저장 시스템에 걸쳐 적용해야 할 수 있다** (7장,
  p.200).[^konieczny2025]
- **원시 데이터** — 이 패턴이 **닿지 않는 자리**를 밝히는 결과다. **쪼개지지 않은 원시 데이터를
  얼마간 보관해야 한다면 데이터 제거를 다룰 보완 해법이 필요하다. Vertical Partitioner 패턴은 첫
  데이터 변환 단계부터만 적용된다** (7장, p.201).[^konieczny2025]
  - 저자가 내놓는 손쉬운 답과 그 대가 — **쉬운 해법은 데이터 제거 요청 지연에 부합한다면 쪼개지지
    않은 데이터에 짧은 보존 기간을 쓰는 것이다. 그러나 그것은 백필 목적의 데이터 가용성을 줄일 수
    있다** (7장, p.201).[^konieczny2025]

## 카프카에서는 툼스톤이고, 그것이 통하지 않는 토픽이 있다

- **카프카에 관해서라면 정리 부분이 조금 다른데, 이른바 툼스톤 메시지(tombstone message)에
  의존하기 때문이다. 그것은 삭제된 행에 대한 특별한 마커 레코드다. 툼스톤 메시지는 제거된 레코드의
  키와 `null` 값으로 구성된다. 그것을 압착 정리 정책(`cleanup.policy`)을 가진 토픽에 보내면
  카프카가 배경 압착 프로세스를 돌려 모든 툼스톤 메시지를 삭제한다** (7장,
  p.202).[^konieczny2025]
- **이 기법이 통하는 조건이 좁다** — **이 접근은 우리의 수직 분할된 `user_context` 토픽에 대해서는
  작동하는데, 키마다 언제나 발생이 하나이기 때문이다. 그러나 여러 이벤트가 같은 방문 ID 키를 공유하는
  사용자 방문 같은 다른 유형의 레코드에는 작동하지 않을 것이다. 그 토픽에서 압착 프로세스를 돌리는
  것은 결국 마지막 방문 항목만 소비자에게 노출한다는 뜻이 된다** (7장, p.203).[^konieczny2025]
  - **즉 수직 분할이 툼스톤을 가능하게 만든 것이다.** 개인 속성을 `user_id` 키로 유일하게 만든
    토픽으로 옮겼기 때문에 압착이 삭제 기제가 될 수 있다. 두 패턴이 우연히 나란히 있는 것이 아니다.

## In-Place Overwriter — 자리에서 갈아 끼운다

- 문제의 실물 — **시간 기반 수평 파티션에 테라바이트 단위 데이터가 저장된 레거시 시스템을 물려받았고
  개인 데이터 관리 전략이 정의돼 있지 않다. 이 레거시적 성격에도 그 프로젝트는 조직 안에서 여전히
  널리 쓰이고, 그 때문에 정부의 새 프라이버시 규제를 준수해야 한다** (7장,
  p.203).[^konieczny2025]
- 구현은 **데이터 저장 기술에 크게 의존한다** — **데이터 저장이 자리 연산(in-place operations)을
  네이티브로 지원한다면 구현은 `WHERE` 조건으로 제거할 엔티티를 겨냥하는 `DELETE` 문을 돌리는
  것으로 이뤄진다** (7장, p.203).[^konieczny2025]
  - 그런데 그것으로 끝이 아니다 — **결국 이 삭제 질의를 데이터 정리 연산으로 완결해야 할 수 있다.
    이는 특히 Apache Iceberg와 Delta Lake 같은 오픈 테이블 파일 형식에 적용되는데, 그들은 잘못된
    액션의 경우 데이터셋을 이전 버전으로 복원하는 시간 여행 기능을 제공하는 일이 잦다. 개인 데이터를
    삭제했지만 제거된 행을 저장한 데이터 블록을 회수하지 않으면 그 개인 데이터는 여전히 거기 있을
    것이다** (7장, pp.203–204).[^konieczny2025]
- 저자가 상자로 갈라 둔 두 구현 — **테이블 파일 형식에서 삭제를 관리하는 두 접근이 있다. 첫째는
  제거된 행을 단순히 식별해 쓰기 발자국을 줄이려고 그것들을 더 작은 사이드 파일(side file)에 쓴다.
  이는 흔히 삭제 벡터(deletion vector)로 알려져 있다. 그 접근에서 소비자는 읽기 시각에 삭제된
  행을 제거해야 한다. 반대 접근은 소비자가 직접 쓸 수 있도록 제거된 항목을 뺀 전부를 파일에 쓰므로
  더 쓰기 과중이다** (7장, p.204).[^konieczny2025]
- 네이티브 삭제가 없는 형식이라면 **흉내 내야 한다** — **원시 파일 형식(JSON과 CSV)을 쓸 때 시뮬레이션
  잡이 데이터셋 전체를 처리해 제거된 사용자를 나타내는 모든 레코드를 걸러 낸다. 이것은 기존 데이터를
  필터링된 데이터셋으로 교체하는 컴퓨트 집약적 연산이다** (7장, p.204).[^konieczny2025]
- 압착 가능한 저장에도 쓸 수 있다 — **압착 전략이 활성화되고 키 기반 레코드가 쓰인 카프카 토픽 같은
  경우다. 구현은 ① 토픽에 저장된 레코드를 읽고 ② 레코드가 제거된 엔티티에 속하면 레코드 키를 써서
  `null` 페이로드와 함께 토픽에 보내는 단계를 따른다. 그러면 압착 프로세스가 각 키의 가장 최근 항목만
  유지하므로 개인 데이터를 가진 이전 레코드를 제거하고 빈 삭제 마커를 저장한다. 다만 구현은 키 기반
  레코드와 토픽에 정의된 압착 전략을 요구한다** (7장, pp.204–205).[^konieczny2025]
- 상자 하나가 **가장 값싼 선택지와 그 단서**를 함께 준다 — **데이터 보존 기간이 데이터 제거 액션을
  취하는 지연보다 짧다면 그것을 데이터 제거 압착 전략으로 간주할 수 있다. 결국 데이터는 법적 지연
  기간 안에 자동으로 제거될 것이다. 그러나 이것은 구현 제안일 뿐이고, 최종 해법으로 고려하기 전에
  최고데이터책임자(CDO)와 법무 부서에 반드시 재확인하라** (7장, p.205).[^konieczny2025]

## 스테이징 영역이 선택이 아닌 이유

- **부작용을 피하려면 데이터셋을 직접 교체해서는 안 되는데, 잡이 재시도하거나 심지어 실패해 데이터
  손실을 일으킬 수 있기 때문이다. 그렇다고 각 파일을 개별적으로 덮어써야 한다는 뜻은 아닌데, 그것은
  시간·컴퓨트 양쪽으로 집약적일 것이기 때문이다. 대안으로 스테이징 영역(staging area)이라고도
  알려진 내부 저장 영역에 데이터를 쓰는 잡에 기댈 수 있고, 거기서 결과는 잡이 완료되지 않는 한
  비공개로 유지된다. 데이터 제거가 성공하고 나서야 기존 공개 데이터셋을 덮어쓰는 데이터 승격 잡을
  돌릴 수 있다** (7장, p.204).[^konieczny2025]
  - 그 값과 얻는 것 — **중간 저장으로 약간의 추가 복잡성을 더하지만, 재시도된 데이터 제거 잡이
    들여올 수 있는 데이터 품질 문제를 피한다. 물론 데이터 승격 잡도 여전히 실패할 수 있지만, 그
    실패가 데이터 손실로 이어지지는 않는데 데이터셋이 스테이징 영역에 이미 완전히 계산돼 있기
    때문이다** (7장, p.204).[^konieczny2025]
- 처리 엔진의 성질이 이 요구를 강제한다 — **Apache Spark는 분산적이고 트랜잭션 없는(transactionless)
  처리 계층이므로 최종 위치의 파일을 그냥 덮어쓸 수 없는데, 실패의 경우 부분적으로 쓰인 결과를 남길
  수 있기 때문이다. 그런 이유로 라이터는 이 스테이징 위치에 데이터셋을 생성하고 나중에야 저장 계층에
  맞춘 이름 변경류(rename-like) 명령으로 최종 출력에 승격한다** (7장,
  p.206).[^konieczny2025]
  - 각주가 클라우드에서 그 "이름 변경류"의 실체를 밝힌다 — **클라우드 객체 저장소의 이름 변경은
    로컬 파일 시스템과 같은 트랜잭션 의미론을 따르지 않는다. 그것들은 흔히 복사-후-제거 연산으로
    구현되며, 실패의 경우 빈 유효 상태(empty valid states)를 남길 수 있다** (7장, p.206,
    각주 1).[^konieczny2025]
- 원시 파일 형식에서 행을 지우는 잡이 이 패턴의 대표 코드다 — 저자가 두 가지를 못 박는다.
  **첫째, 데이터셋을 변형하고 싶지 않으므로 가능한 가장 단순한 쓰기 API인 텍스트 API를 쓴다. 둘째,
  공간을 아끼려고 모든 속성을 추출하지 않고 필터에 쓰이는 것(우리 경우 `user_id`)만 추출한다**
  (7장, p.206):[^konieczny2025]

  ```python
  input_raw_data = spark_session.read.text(get_input_table_dir())
  df_w_user_column = input_raw_data.withColumn(
    'user', F.from_json('value', 'user_id STRING')
  )

  user_id = '139621130423168_029fba78-15dc-4944-9f65-00636566f75b'
  to_save = df_w_user_column.filter(f'user.user_id != "{user_id}"').select('value')
  to_save.write.mode('overwrite').format('text').save(get_staging_table_dir())
  ```

  - 승격은 저장 계층의 명령으로 한다 — S3에서는 `aws s3 rm ${BUCKET}/output --recursive` 뒤
    `aws s3 mv ${BUCKET}/staging ${BUCKET}/output --recursive`. **물론 복사도 실패할 수 있지만
    그 경우에도 스테이징 위치에 복사될 새 데이터셋이 여전히 준비돼 있다** (7장,
    p.206).[^konieczny2025]

## 읽고 다시 쓰는 값 — I/O와 비용

- **I/O 오버헤드** — **파일을 읽고 덮어쓰는 것은 심각한 I/O 오버헤드를 초래한다. 시간이 지나면
  저장 공간이 거의 두 배로 커지고 처리량 증가로 이어질 수 있다** (7장, p.205).[^konieczny2025]
  - 줄이는 자리 — **저장 계층이 필터 조건에 무관한 파일을 피할 수 있다면 이 오버헤드가 더 작아진다.
    Apache Parquet과 그것에 기대는 테이블 파일 형식(Delta Lake·Apache Iceberg)이 그렇다. Parquet은
    데이터 블록에 레코드를 저장하는 것에 더해 각 데이터 블록의 행에 대한 통계를 저장하는 메타데이터
    계층을 갖는다. 질의 엔진이 이 통계를 분석해 제거된 사용자에 일치하는 행이 없음을 보면 더 비싼
    데이터 블록 읽기 연산을 건너뛸 수 있다** (7장, p.205).[^konieczny2025]
- **비용** — **패턴이 모든 데이터를 읽기를 요구하므로 Vertical Partitioner 패턴보다 비싼 해법이다.
  제거된 엔티티 하나에 대해 레코드 2,000개가 있다면, Vertical Partitioner로는 항목 하나만 읽고
  드롭하면 되지만 In-Place Overwriter 패턴으로는 2,000개 레코드가 영향을 받는다** (7장,
  p.205).[^konieczny2025]
  - 완화 — **이 영향을 줄이려고 데이터 제거 요청을 묶어, 요구마다 파이프라인 하나를 돌리는 대신
    모든 요청에 대해 하나를 실행해 볼 수 있다** (7장, p.205).[^konieczny2025]

## 덮어쓰고 나면 되돌릴 수 없다

- 저자가 이 패턴에만 붙인 경고 상자다 — **스테이징 기반 접근이 우리 시나리오에는 작동하지만 그것도
  완벽하지는 않다. 데이터 제거 잡에 버그가 좀 있어서 그것을 재생해야 한다고 상상해 보라. 불행히도
  원본 데이터셋은 덮어써졌기 때문에 쓸 수 없을 것이다. 이 문제를 완화하려면 Proxy 패턴에 기대거나
  인프라 수준에서 데이터 버저닝을 활성화할 수 있다** (7장, p.207).[^konieczny2025]
  - 각주가 후자의 가용성을 밝힌다 — **비트랜잭션 파일 시스템을 저장하는 데 가장 자주 쓰이는 모든
    주요 객체 저장소가 버저닝을 지원한다. 여기에는 S3·Azure Storage·GCS가 포함된다** (7장,
    p.207, 각주 2).[^konieczny2025]
  - **여기서 4장의 멱등성 패턴이 그대로 다시 불린다** — Proxy는 매번 새 테이블에 쓰고 뷰로만
    노출해 원본을 덮어쓰지 않는 패턴이다([멱등적 쓰기 패턴](idempotent-write-patterns.md)).
    데이터 제거는 그 불변성이 값을 하는 자리다.
  - **다만 이 처방은 위 "원시 데이터" 결과와 긴장한다** — 되돌리려고 버전을 남기는 것과, 지우라고
    받은 요청을 이행하는 것은 같은 데이터를 두고 반대로 민다. 저자는 둘을 각각의 자리에서 말하고
    조정하지 않는다. #hypothesis 실무의 조정점은 보존 기간과 `VACUUM` 주기이며, 그것은
    이 장이 아니라 법무·CDO 쪽 결정으로 넘어간다.
