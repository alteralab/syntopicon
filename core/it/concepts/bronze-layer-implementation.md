이 페이지의 질문: **Bronze 계층을 실물로 세울 때 반입 파이프라인은 어떤 모양이고, 착지한 파일을
질의 가능하게 만드는 기법 다섯 중 무엇을 고르는가.**

[메달리온 Bronze 계층](../concepts/medallion-bronze-layer.md)이 이 계층의 규정과 설계 결정을
이론의 언어로 세운다면, 이 페이지는 같은 저자가 같은 것을 구현으로 되받는 자리다. 3장이 전체
적재와 증분 적재, MERGE, 스키마 관리, 기술 검증을 이론으로 나열하고 상세를 5장으로 미뤄 두었고,
그 미뤄진 것이 여기 온다. 스키마를 어디에 어떻게 두는가는 분량이 커서
[레이크하우스 스키마 정의 접근 여덟](../concepts/lakehouse-schema-definition-approaches.md)로
갈라 두었다.

저자가 이 장의 코드에 단서를 단다 — 예제들이 **교육 목적으로 간결하게 다듬어진 것**이므로 실제
시나리오에 적용할 때는 손봐야 할 수 있고, 일부는 학습용일 뿐이고 일부만 실습에 그대로 쓸 수 있다
(5장 도입).[^strengholt2025]

## 버전 조건

> **버전 조건**: 2025년 저술 시점. 아래 절들이 이름을 드는 제품(Data Factory·Azure SQL·
> Azure Event Hubs·Azure Databricks·Microsoft Fabric의 미러링)과 그 기능 유무는 그 시점의 것이다.
> 특히 [외부 테이블](#외부-테이블) 절의 제약은 저자가 스스로 "저술 시점"이라 못 박은 자리다.
> 파이프라인의 모양, 기법 다섯의 규정과 대가, 고르는 기준은 설계 판단이라 제품과 함께 낡지 않는다.
> 이 소스에 공표된 만료 날짜가 없어 `stale_after`는 걸지 않는다.

## 반입 파이프라인의 모양

- 실습의 원천은 **AdventureWorks 샘플 데이터베이스**다. 시연과 훈련에 널리 쓰이는 샘플이라 데이터
  반입, 데이터 품질 교정, 데이터 통합 활동을 공부하기에 좋은 선택이라는 것이 고른 이유다 (5장
  §"Building the Data Pipeline" ▸ "Deploying the AdventureWorks Sample
  Database").[^strengholt2025]
- 연결 설정에서 저자가 남기는 판단 하나는 인증 방식이다 — **서비스 주체(service principal) 계정을
  권고**하고, 그것이 반입 도구 계정을 클라우드 서비스에 인증시키는 가장 안전하고 확장 가능한 방법을
  제공하기 때문이다 (5장 §"Building the Data Pipeline" ▸ "Set Up an Azure SQL Database
  Connection").[^strengholt2025]
- **파이프라인의 구조가 이 절의 요지다.** 활동 넷이 두 겹으로 놓인다 (5장 §"Building the Data
  Pipeline" ▸ "Creating a New Data Pipeline", 그림 5-1):[^strengholt2025]

> Lookup(LookupTables) → ForEach(ForEachTable) ▸ 그 안에 CopyTable → CreateBronzeTables

  - **Lookup 활동**이 원천의 스키마 정보를 가져온다. 그 정보로 데이터베이스 테이블 목록을 순회해
    각각에 복사 연산을 수행하므로, **각 테이블이 동적으로 Bronze에 복사된다.**
  - **ForEach 활동**은 항목 모음을 특정 순서로 순회하며 각 항목에 연산을 수행하는 제어 흐름
    활동이다. 저자는 이것이 **파일이나 테이블 무리에 반복적 연산을 수행하려는 데이터 엔지니어링
    프로젝트에서 흔히 쓰인다**고 적는다 (5장 §"Building the Data Pipeline" ▸ "Creating a New Data
    Pipeline" ▸ "Building the ForEach loop").[^strengholt2025]
  - **CopyTable 활동**이 원천에서 목적지로 데이터를 복사하고, 원천 속성의 테이블명과 스키마명은
    Lookup이 가져온 메타데이터에 이어진 입력 매개변수다 (5장 §"Building the Data Pipeline" ▸
    "Creating a New Data Pipeline" ▸ "Configuring the CopyTable activity").[^strengholt2025]
- **목록을 얻는 방법이 이 파이프라인을 메타데이터 주도로 만드는 자리다.** 저자의 질의는 표준
  정보 스키마 뷰에서 기본 테이블 유형만 걸러 오는 SQL 한 문장이고(`INFORMATION_SCHEMA.TABLES`에서
  `TABLE_TYPE = 'BASE TABLE'`이고 대상 스키마에 속한 것), 고른 이유가 명시적이다 — 이 뷰가
  데이터베이스 메타데이터에 대한 **내부 시스템 테이블과 무관한 관점**을 주어 테이블·컬럼·도메인·
  검사 제약·권한 같은 객체 정보를 얻는 **더 표준화된 방법**을 제공하고, 대부분의 데이터베이스가
  시스템 테이블을 지원하므로 메타데이터 질의에 흔히 쓰인다는 것이다 (5장 §"Building the Data
  Pipeline" ▸ "Creating a New Data Pipeline").[^strengholt2025]
  - 곧 **파이프라인은 테이블 이름을 하나도 모른 채 작성된다.** 원천이 자기 카탈로그로 목록을
    답하고 반복자가 그 목록을 돈다. 이것이 아래
    [판단 열둘](#파이프라인-설계에-남는-판단-열둘)의 "범용 파이프라인" 항목과 6장의 메타데이터
    주도 구현으로 이어지는 씨앗이다.
- 곁줄 하나가 반복의 대안을 단다 — 다른 노트북에서 Spark 노트북을 돌리는 방식으로도 반복 활동을
  수행할 수 있고, **그 접근이 더 효율적이고 유지하기 쉬울 수 있다** (5장 각주 2).[^strengholt2025]

## 착지 경로를 날짜로 가르는 이유

- 착지 형식은 `Files/<원천>/YYYYMMDD/<테이블명>.parquet`이다. 이 방식의 이점을 저자가 넷으로
  적는다 — **모든 데이터를 일 단위 시간 창 안에 아카이빙**하여 구조화된 시간 기반 저장을 확보하고,
  체계적인 이력화로 **Spark 처리 잡에 잘 준비된 입력**을 만들며, **감사 요건**을 뒷받침하고,
  **오류 시 데이터 복구를 위한 이력 기록**을 제공한다 (5장 §"Building the Data Pipeline" ▸
  "Creating a New Data Pipeline" ▸ "Configuring the CopyTable activity").[^strengholt2025]
- 저자 자신이 이 실습 형식을 곧바로 고쳐 잡는다 — **평평한 `YYYYMMDD`에서 계층적 `YYYY/MM/DD`
  구조로 바꾸면** 데이터 관리와 질의 성능이 좋아진다. **정밀한 파티션 프루닝**을 가능하게 하고,
  **한 디렉터리에 많은 파일을 다루는 부담을 줄이며**, 데이터를 다루기 좋은 덩어리로 조직해 삭제와
  아카이빙 같은 연산을 단순하게 만든다 (5장 §"Building the Data Pipeline" ▸ "Additional
  Considerations").[^strengholt2025]

## 파이프라인 설계에 남는 판단 열둘

**저자는 실습이 쉬웠던 이유를 먼저 못 박는다** — 복잡한 네트워크 요건 없이 원천에 직접 접근할 수
있었기 때문이고, 다른 시나리오에서는 수집 방식이 크게 달라진다. 데이터가 임시 저장 영역에 먼저
도착할 수도, 기술적 변환을 요구하는 형식일 수도 있고, 접근에 통합 런타임 배치나 VPN 같은 추가
단계가 필요할 수도 있으며, API 엔드포인트에서 가져오려면 특화 도구가 필요할 수도 있다. **핵심
교훈은 반입 과정의 구체가 원천 시스템의 특성과 다뤄야 할 데이터의 성격에 크게 달렸다는 것이고,
은탄환은 없으며 시나리오마다 재단된 고유한 접근이 필요하다** (5장 §"Building the Data Pipeline" ▸
"Additional Considerations").[^strengholt2025]

그 위에서 저자가 남기는 판단이 열둘이다 (같은 소절).[^strengholt2025]

- **날짜 파티션 구조** — 위 [착지 경로](#착지-경로를-날짜로-가르는-이유) 절의 계층적 구조로의 전환.
- **로깅과 지표** — 반입 시 감사와 문제 해결 양쪽을 위해 과정을 감시하는 것이 결정적이다. 실용적
  방법은 Bronze에서 처리되는 데이터셋마다 지표를 남기는 것으로, 읽은 행 수·쓴 행 수·싱크 처리
  시간 같은 상세를 반입 도구의 실행 상태 지표에서 얻는다. 스트리밍이나 실시간이면 Spark Structured
  Streaming의 질의 진행 지표가 초당 입력·처리 행 수, 배치 지속 시간, 싱크 커밋 지연 같은 정보를
  준다.
  - **후처리 잡의 대조**도 권고된다 — 행 수와 합계를 원천 데이터와, 그리고 메달리온의 모든 계층에
    걸쳐 검증하는 잡이다. 이것이 불일치나 오류를 식별하는 데 도움이 되고, **증분 갱신마다 수행하는
    것이 바람직하다.**
- **로깅 프레임워크** — 실습 구성에는 폭넓은 로깅이 없다. 확장성과 처리 견고성을 높이려면 감시와
  문제 해결에 필요한 정보를 포착하는 프레임워크를 구현하기를 권고한다.
- **자동 트리거** — 새 데이터가 도착할 때 반입 파이프라인을 자동으로 발동시키는 기능으로
  오케스트레이션을 개선할 수 있다.
- **공유 라이브러리** — 문서와 테스트가 잘 갖춰진 공유 라이브러리가 전사에 걸친 데이터 팀의 효율을
  크게 높인다. 확장성을 위해 **기술적 파일 형식 변환, 복잡한 구조의 평탄화, append 연산**에 대한
  반복 가능한 스크립트를 개발하고 공유 코드 저장소에 두기를 권고한다.
- **메타데이터 기반 범용 파이프라인** — 데이터 유형마다 별도 파이프라인을 만드는 대신 메타데이터
  주도 프레임워크로 **주어진 메타데이터에 따라 스스로 조정되는 범용 파이프라인**을 구성한다. 이
  접근이 방대한 코드를 쓰고 유지할 필요를 크게 줄인다. 구체적 예는 6장으로 미룬다.
- **연결 서비스의 매개변수화** — 연결 서비스가 실행 시점에 동적 값을 받게 만든다. 같은 논리 SQL
  서버의 여러 데이터베이스에 붙으려면 연결 정의에서 데이터베이스 이름을 매개변수로 뽑는 식이다.
- **템플릿 활용** — 반입 도구에 딸린 템플릿이 미리 정의된 파이프라인을 제공해 빠른 시작을 돕는다.
- **통합 런타임 배치** — 네트워크 요건이 설정을 복잡하게 만들 수 있다. 온프레미스 원천이나 다른
  가상 네트워크 안의 서비스에 접근해야 하면 통합 런타임을 가상 네트워크에 배치해야 할 수 있다.
- **데이터 보안** — PII나 그 밖의 민감 데이터를 다룰 때 반입 과정이 복잡해질 수 있다. 민감 데이터를
  걸러 내거나 암호화나 동적 데이터 마스킹을 적용해야 할 수 있다.
- **성능을 위한 재설계** — 성능 문제가 반입 전략의 재설계를 요구할 수 있다. 복사 활동의 병렬 복사
  옵션으로 처리량을 높이거나, 전체 추출 대신 **증분 적재와 델타 처리 접근을 채택**하는 선택지가 있다.

## 관리형 Delta 테이블로 옮기기

- **파일을 받은 것만으로는 끝나지 않는다**는 것이 이 구간의 전제다 — Bronze는 파일을 위한 저장
  공간 이상이고 **데이터를 균일하고 쉽게 접근 가능하게 만드는 결정적 역할**을 하므로, 질의 가능하고
  이후 쓰임에 접근 가능하게 만드는 처리가 더 필요하다 (5장 §"Implementation of Lakehouse
  Tables").[^strengholt2025]
- Delta 테이블을 만드는 이유가 셋이다 — **ACID 준수**가 동시 읽기·쓰기 중 데이터 무결성과 신뢰성을
  보장하고, **타임 트래블**을 지원하며, **효율적인 upsert와 삭제**를 지원해 데이터 관리를 더 견고하고
  유연하게 만든다 (5장 §"Implementation of Lakehouse Tables" ▸ "Traverse Parquet Files to Managed
  Delta Tables").[^strengholt2025]
- 파이프라인이 노트북 활동을 하나 더 품고, 그 노트북이 하는 일이 순서대로 여섯이다 (같은
  소절):[^strengholt2025] 파이프라인이 넘긴 매개변수(스키마명·테이블명·파일 경로)를 받고, 없으면
  스키마를 만들고, 기존 테이블을 떨어뜨리고, Parquet 파일을 읽어 DataFrame에 싣고, **`loading_date`
  컬럼을 더한 뒤**, 덮어쓰기 모드로 Delta 테이블에 쓴다.
- **`loading_date` 컬럼의 근거가 이 절에서 가장 옮길 값어치가 있는 자리다** — Bronze의 데이터셋마다
  반입 시점의 날짜와 시각을 기록하는 컬럼이고, 이 타임스탬프가 **변경 추적과 감사를 돕고 SCD2 같은
  기능의 구현에 필수적**이다. 레코드 변경이나 추가의 정확한 시각 기록이 정확한 레코드 버전 유지에
  결정적이기 때문이다. 저자는 예제가 컬럼 하나만 더하지만 **실제 시나리오라면 `source_system`·
  `lineage_id` 같은 메타데이터 컬럼을 더 포함할 것**이라 적는다 (같은 소절).[^strengholt2025]
- **적용 범위의 경계를 저자가 곁줄로 긋는다** — 테이블을 떨어뜨리고 새 데이터로 덮어쓰는 이 방법은
  **전체 데이터 전달분을 다루는 데 특히 알맞다.** 낡은 정보를 걷어 내 깨끗한 판을 보장하지만
  **증분 갱신만 담는 델타 전달분에는 적용되지 않는다** (같은 소절 곁줄).[^strengholt2025]
- 각주 하나가 이 방식의 위험을 못 박는다 — 이 코드 조각은 **Parquet 파일이 폴백으로 남아 있다는
  전제 아래** 테이블을 떨어뜨리는 것이고, **그 전제가 참이 아니면 기존 테이블을 떨어뜨리는 것이
  심각한 결과를 낳을 수 있다.** 대안은 존재하지 않을 때만 만들고 있으면 덮어쓰지 않는 생성 방식이다
  (5장 각주 3).[^strengholt2025]

## 외부 테이블

- 외부 테이블은 **관리형 환경 바깥에 저장된 데이터를 질의하게 한다** — HDFS나 ADLS 같은 외부 저장
  시스템에 있는 데이터가 대상이다 (5장 §"Implementation of Lakehouse Tables" ▸ "Using External
  Tables").[^strengholt2025]
- 만드는 방법은 위치 지정이다 — 테이블 생성문에 위치 절을 붙여 테이블 위치를 저장소의 Parquet 파일
  경로로 지정한다 (같은 소절).[^strengholt2025]
- **이득은 단순함과 무복제**다. 설정이 간단하고 곧바르며 데이터 중복을 요구하지 않는다 (같은
  소절).[^strengholt2025]
- **대가가 둘이고 이것이 선택의 근거다** (같은 소절):[^strengholt2025]
  - 외부 Parquet 테이블에서 읽는 것이 **Delta 테이블에서 읽는 것보다 일반적으로 느리다.** 저자는
    그 원인을 데이터 접근·처리 방식에 영향을 주는 최적이 아닌 파티셔닝 같은 요인으로 돌린다.
  - 관리형 Delta 테이블과 달리 **스키마 강제와 타임 트래블 같은 고급 기능을 지원하지 않는다.**
- 저자의 판정은 단호하지 않다 — **틀린 것이 아니고 구체적 요건에는 잘 맞을 수 있으나 가장 최적화된
  방법은 아니다** (같은 소절).[^strengholt2025]
- 제품 제약 하나가 여기 붙는다 — **2025년 저술 시점에 Microsoft Fabric은 스키마가 켜진 레이크하우스
  엔티티 위에 외부 테이블을 만드는 것을 지원하지 않지만 다른 여러 Spark 기반 플랫폼에서는 된다**
  (같은 소절).[^strengholt2025]

## MERGE로 갱신하기

- 언제 필요한가 — 앞의 예들이 외부 테이블이나 데이터 복제였다면, **복잡한 필터로 변경분(갱신과 신규
  항목)만 다뤄야 하는 시나리오**에서 증분 적재 처리가 필요해지고 그때 병합 연산이 결정적이 된다
  (5장 §"Implementation of Lakehouse Tables" ▸ "Updating Tables with MERGE
  Operations").[^strengholt2025]
- Delta Lake의 MERGE는 새 데이터를 기존 테이블에 병합하게 하고, **테이블의 데이터를 갱신하거나
  upsert하는 데 특히 이롭다** (같은 소절).[^strengholt2025]
- **유연성의 실물은 조건절의 어휘 다섯이다** — `WHEN MATCHED`·`WHEN NOT MATCHED`·`WHEN MATCHED AND`·
  `WHEN NOT MATCHED BY TARGET`·`WHEN NOT MATCHED BY SOURCE`. 이 조건들이 일치 기준에 따른 구체적
  행동을 정의하게 해 증분 데이터 적재 관리의 강력한 도구가 된다 (같은 소절).[^strengholt2025]
- 같은 일을 SQL로도 Python API로도 쓸 수 있고, **Python 쪽의 이점은 코드를 인자로 매개변수화할 수
  있다는 것**이다 (같은 소절).[^strengholt2025] 저자의 SQL 예는 랜딩 테이블을 원천으로 Bronze
  테이블을 대상으로 두고 고객 식별자로 잇는 문장이며, 일치하면 이름·연락처·구매 이력을 갱신하고
  일치하지 않으면 삽입한다.
- **이 절의 판정이 KB의 멱등 쓰기 쪽과 맞닿는다** — 병합 연산은 데이터를 더 효율적으로 다루는 이점을
  주지만 **원천 데이터가 깨끗하지 않거나 조인 조건이 단순하지 않으면 복잡성이 생긴다.** 그런 상황에서는
  병합이 올바로 수행되도록 추가 정제나 변환 단계가 필요할 수 있고, 예컨대 데이터셋에 중복 항목이
  있으면 **병합 전에 중복을 제거해야 할 수 있다.** 그래서 **복잡한 병합 연산은 흔히 메달리온의 다음
  계층들에서 수행된다**는 것이 저자의 결론이고 구체적 예를 6·7장으로 미룬다 (같은
  소절).[^strengholt2025]

## Spark Structured Streaming

- 스트림 처리의 규정 — 큐나 파일에서 메시지를 소비하고 질의·필터·집계 같은 처리를 수행한 뒤 결과를
  **최소 지연으로** 싱크에 보내는 기법이고, 주기적으로 일어나는 배치나 마이크로배치 처리와 다르다
  (5장 §"Implementation of Lakehouse Tables" ▸ "Spark Structured Streaming").[^strengholt2025]
  - 각주가 마이크로배치의 접점을 단다 — Apache Spark의 `foreachBatch` 연산이 주로 Structured
    Streaming과 함께 **스트림의 각 마이크로배치에 처리 로직을 적용**하는 데 쓰인다 (5장 각주
    5).[^strengholt2025]
- 이 기법을 고르는 근거는 **다재다능함과 어느 Spark 기반 플랫폼과도 매끄럽게 통합된다는 것**이고,
  낮은 지연 응답이 필요한 시나리오에 특히 쓸모 있다. 저자가 드는 예는 IoT 기기, 엣지 기기, 금융
  거래, 기계 로그다 (같은 소절).[^strengholt2025]
- **복잡 이벤트 처리 지원**이 또 하나의 이점이다 — 복잡한 질의를 다루고 **스트림을 정적 데이터나
  다른 스트림과 조인**하게 한다. 추천이나 사용자 활동 추적처럼 고급 분석을 요구하는 애플리케이션에
  결정적이다 (같은 소절).[^strengholt2025]
- 사례로 든 구도는 항공기 편대의 실시간 감시다 — 각 항공기의 센서와 기기에서 나온 데이터를 이벤트
  허브로 반입해 Structured Streaming으로 실시간 처리하고, 악천후 같은 예기치 못한 상황이면 **이벤트
  스트림이 즉시 관련자에게 경보**해 항로 변경이나 안전 조치의 빠른 결정을 가능하게 한다 (같은
  소절).[^strengholt2025]
- 그 구도의 실물이 그림 5-10이고, **본문에 없는 연결 하나가 그림에 있다** (같은 소절, 그림
  5-10):[^strengholt2025]

> Real-time systems → *Real-time ingestion* → Azure Event Hubs → *Connector* →
> Microsoft Fabric 상자 안의 Process ▸ Spark Structured Streaming ⇄ Bronze (Lakehouse) →
> *DirectQuery* → Reporting

  - 곧 그림이 더하는 것은 **스트리밍 경로에서 Bronze가 리포팅에 직접 연결된다**는 것이다.
    Structured Streaming과 Bronze 사이 화살표가 양방향이고, Bronze에서 리포팅으로 나가는 화살표에
    `DirectQuery` 라벨이 붙는다. 저자가 3장에서 **Bronze를 업무 사용자에게 열지 말라**고 권고한
    것과 나란히 놓고 읽을 자리다 — 실시간 감시라는 목적이 그 권고를 되돌리는 예외로 그려진다.
- 구현에서 남는 것이 둘이다 — 연결 문자열은 **보안을 위해 암호화**하고, **체크포인트 위치**를
  지정해 스트리밍 질의의 메타데이터를 저장함으로써 내결함성을 확보하고 실패 시 질의를 재시작할 수
  있게 한다 (5장 §"Implementation of Lakehouse Tables" ▸ "Spark Structured Streaming" ▸ "Example
  with Azure Event Hubs").[^strengholt2025]
- **계층을 건너뛰는 선택지**도 여기서 열린다 — 스트리밍 데이터를 Bronze에 쓰는 것에 더해 같은
  DataFrame을 Structured Streaming으로 더 처리해 필터·정제·변환한 뒤 **정제된 출력을 곧바로
  Silver에 저장**할 수 있다. 상세는 6장으로 미룬다 (같은 소소절).[^strengholt2025]

## 변경 데이터 캡처

- 규정 — 데이터베이스의 변경을 추적하는 데 쓰이고, 삽입·갱신·삭제 같은 변경을 포착해 **별도의
  테이블에 저장**한다. 실시간 데이터 복제에 특히 쓸모 있고, 데이터의 변경을 추적하게 해 정확하고
  최신인 관점을 유지하게 한다 (5장 §"Implementation of Lakehouse Tables" ▸ "Using Change Data
  Capture").[^strengholt2025]
- 제품 쪽 구현으로 저자가 드는 것은 **미러링**이다 — 이 기능으로 데이터베이스를 레이크하우스 저장
  계층에 곧장 복제한다 (같은 소절).[^strengholt2025]
- 곁줄이 보완 기법을 단다 — Delta Lake와 Spark를 쓰는 레이크하우스 아키텍처에서 **change data
  feed를 함께 쓰면 데이터 복제의 효율이 크게 높아진다.** 삽입·갱신·삭제를 포함한 데이터 변경의 더
  세밀한 추적을 가능하게 해 변경 레코드 접근에 간소하고 확장 가능한 접근을 제공하기 때문이다
  (같은 소절 곁줄).[^strengholt2025]
- **대가가 다섯이고 이것이 CDC를 고르지 않을 근거다** (같은 소절):[^strengholt2025]
  - 강력하지만 **쓰기 복잡하다.** 신중한 구현과 **미러링 과정을 위한 기본 키**를 요구한다.
  - **스키마 변경이 있으면 바뀐 테이블의 전체 데이터 스냅샷이 다시 시작되고 모든 데이터가 재적재**된다.
  - **모든 컬럼 타입이 항상 지원되지는 않으므로** 원천과 대상 테이블 사이의 데이터 타입 호환을
    확인해야 한다.
  - **실시간 원천 데이터베이스 구조에 강하게 결합**된다.
  - 그 결합 때문에 **아카이빙과 메타데이터 추가 같은 가벼운 변환을 위한 별도 계층**이 흔히 필요해진다.

## 다섯 기법을 고르는 기준

**이 절이 이 장의 판정 정본이다.** 저자가 다섯을 한 줄씩 다시 규정한 뒤 고르는 규칙을 준다 (5장
§"Implementation of Lakehouse Tables" ▸ "Navigating Data Handling Techniques").[^strengholt2025]

| 기법 | 저자가 그것에 부여하는 값어치 |
|---|---|
| Parquet 파일에서 관리형 Delta 테이블로 | 향상된 성능과 데이터 버전 사이를 오가는 타임 트래블 능력 |
| 외부 테이블 | 즉각적인 데이터 노출 |
| MERGE 연산 | 필요한 변경(갱신과 신규 항목)만 처리해야 할 때의 효율 |
| Spark Structured Streaming | 실시간 데이터 변환의 수행 |
| CDC | 데이터베이스 변경을 실시간으로 미러링하거나 포착하는 **제로 ETL 패턴의 전형** |

- **고르는 규칙이 둘이다** (같은 소절):[^strengholt2025]
  - 각 패턴을 **눈앞의 구체적 시나리오와 데이터 획득에 얽힌 복잡성**에 비추어 저울질하는 것이
    중요하다.
  - **흔히 이 접근들의 혼합이 공존하게 된다** — 아키텍처의 고유한 요구에 맞춰 재단된 형태로.
    곧 저자의 기본값은 하나를 고르는 것이 아니라 **여럿을 동시에 두는 것**이다.
- 장의 맺음이 그 혼합의 예를 셋 준다 (5장 §"Conclusion"):[^strengholt2025] 큰 데이터 볼륨의 주기적
  배치 처리라면 오케스트레이션에 반입 도구를, 저장과 처리에 Delta 테이블을 쓰도록 팀을 안내하고,
  실시간 스트리밍이라면 Structured Streaming이 기본 선택이며, 배치와 실시간의 혼합이나 직접 데이터
  접근이 필요한 시나리오라면 **직접 질의용 외부 테이블과 반입·처리용 Structured Streaming을 결합**하는
  것이 최선일 수 있다.
- 패턴을 가르는 요인도 맺음이 나열한다 — **원천 유형, 데이터 볼륨, 원천 시스템의 스키마 변동,
  처리 요구**가 첫 묶음이고, **실시간 처리냐 배치 잡이냐 같은 프로젝트 요건**과 **델타 전달분이냐
  전체 적재냐 같은 전달 패턴**이 둘째 묶음이다 (같은 절).[^strengholt2025]

## Bronze를 세우고 남는 교훈 다섯

- 저자가 맺음에서 인정하는 것 — 질의 가능한 Bronze를 만드는 일은 **여러 면을 가진 도전**이었고,
  수많은 구성 요소와 서비스의 통합을 요구하며 각각이 고유한 도전과 요구를 제기한다. 데이터 수집은
  복잡성과 안정성·신뢰성 요구 때문에 **데이터 엔지니어링의 근본 문제로 남아 있고**, 그래서 많은
  조직이 다양한 원천을 다루는 파이프라인을 여럿 개발하며 각각이 맞춤 접근을 요구한다 (5장
  §"Conclusion").[^strengholt2025]
- 여러 엔지니어링 팀이 같은 조직 안에서 다른 플랫폼 인스턴스를 운영할 때 **철저한 지침과 훈련을
  제공하라**는 것이 저자의 권고다. 모두가 같은 모범 사례를 따르게 하기 위해서다 (같은
  절).[^strengholt2025]
- 견고한 Bronze를 위한 요점 다섯 (같은 절):[^strengholt2025]
  - **원천마다 구조적·네트워크적 제약 같은 고유한 도전이 있음을 인정하고** 온보딩 전략의 유연성을
    유지한다.
  - **원천마다 전용 파이프라인을 설계하되 공통 처리 단계는 템플릿을 써서** 일관성과 재사용성을
    유지한다.
  - **스키마 진화를 관리하고 기술 검증을 효과적으로 수행하는 전략을 개발한다.** 메타스토어 구현이
    이로울 수 있다.
  - **원천마다 별도 스키마나 별도 레이크하우스 엔티티로 데이터를 조직**해 대응하는 파이프라인과
    정렬시킨다.
  - **Bronze 데이터가 최종 사용자에게 이미 접근 가능한지 아닌지에 대한 지침을 낸다.**

## 이 KB의 원전과 맞대어 본 것

이 장의 소재는 이 KB에 이미 이름을 가진 것이 많다. 갈리는 자리만 적는다. **`contradicts`는 하나도
걸지 않았다** — 아래는 전부 층위가 다르거나 어휘가 다를 뿐, 최대 하나만 참일 수 있는 사실 충돌이
아니다.

- **MERGE와 멱등 쓰기.** [멱등적 쓰기 패턴](../concepts/idempotent-write-patterns.md)의 Merger
  패턴이 병합을 **재실행 안전성의 수단**으로 다루고 그 대가를 셋(성능, 삭제 처리, 상태)으로 센다면,
  이 소스는 병합을 **증분 적재의 수단**으로 다루고 대가를 **원천의 더러움**에 둔다. 목적이 달라
  겹치지 않되, 이 소스가 "중복이 있으면 병합 전에 제거해야 한다"고 적는 자리와 그 페이지가 병합의
  전제로 요구하는 것이 같은 것을 가리킨다. 이 소스가 더하는 것은 **그래서 복잡한 병합을 Bronze가
  아니라 다음 계층에서 하라는 배치 규칙**이다.
- **배치 반입의 구현.** [배치 반입 패턴](../concepts/batch-ingestion-patterns.md)이 Full Loader와
  Incremental Loader를 반입 잡의 패턴으로 서술한다면, 이 소스는 그 잡을 **오케스트레이터의 활동
  네 개**(조회·반복·복사·노트북)로 분해해 보인다. 이 소스가 더하는 것은 **원천 카탈로그를 질의해
  대상 목록을 얻는 메타데이터 주도 구조**다.
- **CDC의 대가.** [변경 데이터 캡처](../concepts/change-data-capture.md)가 CDC를 리더-팔로워 기제로
  규정하고 배치 CDC와 연속 CDC를 가른다면, 이 소스는 **운영 비용 다섯**(기본 키 요구, 스키마 변경
  시 전량 재적재, 타입 호환, 원천 구조와의 결합, 추가 계층의 필요)을 더한다. 2장이 CDC를 트랜잭션
  로그 기반으로만 규정해 그 페이지보다 좁았던 자리를 5장이 **미러링이라는 구현 이름과 change data
  feed의 보완 관계**로 채운다.
- **스트리밍 질의.** [스트리밍 질의와 변환](../concepts/streaming-queries-and-transformations.md)이
  마이크로배치와 진짜 스트리밍을 가르는 축을 세운다면, 이 소스는 Structured Streaming을 **레이크하우스
  계층 안의 반입 기법 하나**로 배치하고 체크포인트를 내결함성의 조건으로 못 박는다.
- **반입 트리거.** [반입 트리거 패턴](../concepts/ingestion-triggering-patterns.md)이 소비자가
  기다리는 쪽과 생산자가 알리는 쪽을 가른다면, 이 소스의 "자동 트리거" 항목은 **저장 이벤트에
  반응하는 발동**을 권고만 하고 상세를 바깥 문서로 넘긴다. 이 소스가 더하는 것은 없다.
- **저장 레이아웃.** [데이터 저장 레이아웃 패턴](../concepts/data-storage-layout-patterns.md)의
  Horizontal Partitioner가 파티션 키 선택과 스큐를 다룬다면, 이 소스는 **경로 문자열의 모양**이라는
  더 낮은 층에서 같은 것을 말한다 — 평평한 `YYYYMMDD` 대 계층적 `YYYY/MM/DD`. 프루닝 효과의 근거는
  같다.
- **Bronze의 개방.** [메달리온 Bronze 계층](../concepts/medallion-bronze-layer.md)이 "업무 사용자에게
  Bronze를 열지 말라"는 저자의 권고를 담는데, 이 장의 그림 5-10은 **실시간 경로에서 Bronze를 리포팅에
  직접 잇는다.** 같은 책 안에서 방향이 갈리는 유일한 자리다. 다만 이것도 사실 충돌이 아니다 — 3장의
  권고는 **원천 시스템 이해를 요구하는 업무 분석**을 겨냥하고, 5장의 그림은 **실시간 감시**라는 다른
  용도다. 저자 자신이 맺음의 요점 다섯에서 "Bronze 데이터가 최종 사용자에게 접근 가능한지 지침을
  내라"고 적어 **조직이 정할 일로 넘긴다.**
