하나의 질문: **API의 인터페이스에 어떤 이름을 붙이고, 그 계약이 바뀔 때 판을 어디에 어떤
형식으로 매기는가.**

## 버전 조건

> **버전 조건**: 이 페이지가 드는 제품 이름(Stripe Payment Intents·RabbitMQ)과 도구 조언은
> **2025년 저술 시점**의 것이다. 이름 짓기의 성질, 자원 지향과 의도 지향의 구별, 변경을
> 가르는 두 축, 버전 라벨을 놓는 네 자리와 세 형식은 시점에 매이지 않는다.

## API의 자연어

- 저자들이 먼저 답하는 것은 **어떤 자연어로 API를 지을 것인가**이고 답은 하나다 — **그 언어는
  여전히 영어이며, 미국과 영국이 컴퓨팅 발전에서 맡은 주도적 역할 때문에 정보기술의 언어가
  되었다** (2장 §"API Language", p.42).[^dynowski2025]
- 철자까지 내려간다 — 말해지는 영어는 여러 결로 나뉘지만 주된 철자는 미국식과 영국식 둘이고,
  **대상 독자에 대한 특정 요구가 없다면 보급 정도 때문에 미국식 영어가 권고된다** (2장,
  p.42).[^dynowski2025]
- 대상 사용자에게 닿을 수 없을 때의 조언이 하나 붙는다 (2장, p.42).[^dynowski2025]
  - **대부분의 경우 당신은 피드백을 줄 대상 사용자에게 접근하지 못한 채 API를 개발한다.
    그런 상황에서는 LLM에 당신의 API 설계나 쓰고 있는 패턴에 대한 피드백을 물어보라.**
  - 곧바로 단서가 붙는다 — **LLM은 텍스트를 생성하는 것이 목적인 도구이지 API 설계를 돕는 것이
    목적인 도구가 아니므로, 쓰되 그것이 생성한 정보의 정확성을 검증하라.**

## 이름이 갖춰야 할 것

- 저자들은 이름 짓기를 **API를 만드는 가장 어려운 부분의 하나**로 놓는다 — 인터페이스·스키마·
  필드·매개변수 무엇이든 그렇고, 이유는 뒤에 있다. **프로덕션에서 한 번 쓰이고 나면 기존
  클라이언트를 전부 갱신해야 하므로 이름을 바꾸기가 어려울 수 있다.** 그래서 인터페이스 이름에
  스스로를 묶기 전에 사용자에게 피드백을 구하라고 적는다 (2장 §"API Naming",
  p.42).[^dynowski2025]
- 좋은 이름의 성질이 열거된다 — 엔드포인트든 함수든 속성이든 질의 매개변수든, 고른 이름은
  **표현력 있고 직관적이고 발음 가능해야 하며, 자기 맥락에 맞고 의도를 표현해야 한다.**
  그리고 **좋은 이름은 오독으로 이어질 의심을 만들지 않는 방식으로 뜻을 전한다** (2장,
  p.42).[^dynowski2025]
- 일관성은 두 층에 걸린다 (2장, p.42).[^dynowski2025]
  - **고른 지침** — 복수화, 동사-명사 패턴, 스칼라 필드가 단위를 담게 하는 것 따위.
  - **표기 관례** — `hungarianNotation`·`CamelCaseNotation`·`snake_notation`.
- 이름이 고립돼 있지 않다는 경고가 붙는다 — **API 주위에는 언제나 맥락이 있다.** 저자들이 드는
  실물이 `channel`이고, 통신·방송·토목이라는 서로 다른 맥락에서 서로 다른 것을 뜻할 수 있다
  (2장, p.42).[^dynowski2025]
- 그럼에도 오독될 여지가 남으므로, **의심스러울 때 API 개발자가 쓸 수 있는 보조 문서를
  제공하라**고 적는다 (2장, p.42).[^dynowski2025]

## 단수인가 복수인가는 스타일이 정한다

- 자원 이름을 단수로 할지 복수로 할지는 **그 이름이 나타나는 API 스타일에 달려 있다** (2장,
  pp.42–43).[^dynowski2025]
  - **REST API에서는 자원 지향 이름과 복수형이 규범**이다 — `/orders/123`.
  - **GraphQL·gRPC·브로커 기반 API는 대체로 의도 지향 접근을 따르며**, 그래서 동작 이름에
    단수와 복수를 둘 다 허용하는 더 큰 자유를 준다.

## 자원 지향과 의도 지향

**저자들은 이 구별을 곁글로 둔다.** 곧 이름 짓기의 한 규칙이 아니라 API 전체를 가르는 두
범주다.

- **자원 지향 API는 데이터에 초점을 둔다.** 자원 이름에 명사를 쓰는 것이 흔하고 — `bookings`·
  `orders`·`users` — REST 아키텍처 스타일에서 유래했으며, `POST`·`GET`·`PUT`·`PATCH`·`DELETE`
  같은 HTTP 동사로 자원을 조작한다 (2장 곁글 §"Resource-Oriented Versus Intent-Oriented APIs",
  p.43).[^dynowski2025]
- **표준 HTTP 동사의 수가 제한된 것이 자원 지향의 약점이면서 동시에 강점**이라고 저자들은 같은
  문단에서 두 번 적는다 (2장, p.43).[^dynowski2025]
  - 약점 쪽 — `archive user`나 `backup server` 같은 **맞춤 동작에 대응하는 HTTP 동사가 없다.**
    우회로 자원 안에 동작 관련 필드를 두어 맞춤 동작을 구현하거나, 자원 지향을 벗어나 명사 대신
    맞춤 동사로 특정 엔드포인트의 이름을 짓는다.
  - 강점 쪽 — **모든 API가 같은 HTTP 동사를 공유하는 것이 예측 가능성이라는 요소를 들여온다.**
- **의도 지향 API는 데이터에 수행되는 연산의 목표에 초점을 둔다.** 인터페이스 이름에 대체로
  동사가 들어간다 — `createUser`·`archiveUser`·`backupServer`. Stripe의 Payment Intents가
  의도 지향 REST API의 예다 (2장, p.43).[^dynowski2025]
- 그 자유의 대가가 적혀 있다 — 의도 지향은 자원 지향보다 이름 짓기에 더 큰 자유를 주지만,
  **변이가 커지고 각 엔드포인트가 특정 동작 하나를 나타내는 엔드포인트가 많이 생길 위험**이
  있다 (2장, p.43).[^dynowski2025]

## 선언적과 명령적

- 구별을 더 밀면 다른 짝이 나온다 — **자원 지향 API는 선언적 API로, 의도 지향 API는 명령적
  API로 서술될 수 있다** (2장, p.43).[^dynowski2025]
- **선언적 API는 그 상태에 이르는 구체적 단계가 아니라 자원의 최종 상태에 초점을 둔다.**
  `GET`이나 `POST` 같은 표준 HTTP 동사가 **연산이 어떻게 수행되는지의 구현 세부를 추상해
  치우므로** REST API는 선언적으로 볼 수 있다 (2장, p.43).[^dynowski2025]
- **명령적 API는 동작 지향이고, 그 이름은 원하는 결과가 어떻게 달성되어야 하는지를 강조한다.**
  gRPC API는 동작과 프로시저에 초점을 두므로 명령적으로 생각할 수 있다. **GraphQL API는 선언적
  질의와 명령적 뮤테이션이 섞인 것**이다 (2장, p.43).[^dynowski2025]

## 같은 CRUD 다섯을 네 스타일이 이름 짓는 법

- 저자들은 같은 주문 CRUD 다섯을 네 스타일에 각각 옮겨 놓은 표 넷을 든다. 연산의 순서는
  **CRUD**(Create·Read·Update·Delete)를 따른다 (2장 표 2-1~2-4, p.44).[^dynowski2025]

| 연산 | REST(자원 지향) | gRPC(의도 지향) | GraphQL(혼합) | RabbitMQ(의도 지향·브로커) |
|---|---|---|---|---|
| 주문 하나 만들기 | `POST /api/orders` | `CreateOrder()` | Mutation `createOrder` | Command `orders.create` |
| 주문 전부 가져오기 | `GET /api/orders` | `ListOrders()` | Query `orders` | Query `orders.list` |
| 주문 하나 가져오기 | `GET /api/orders/{orderID}` | `GetOrder()` | Query `order` | Query `orders.get` |
| 주문 고치기 | `PUT /api/orders/{orderID}` | `UpdateOrder()` | Mutation `updateOrder` | Command `orders.update` |
| 주문 지우기 | `DELETE /api/orders/{orderID}` | `DeleteOrder()` | Mutation `deleteOrder` | Command `orders.delete` |

- 표를 가로로 읽으면 앞 절의 구별이 그대로 보인다. REST는 같은 명사에 동사를 갈아 끼우고,
  gRPC는 동사를 이름 안에 넣으며, GraphQL은 연산 종류(Query·Mutation)와 필드 이름으로 나누고,
  RabbitMQ는 메시지 종류(Command·Query)와 라우팅 키로 나눈다.

## 복수형의 예외

- 영어에서 규칙 명사의 복수는 `s`나 `es`를 붙여 만들어지지만 예외가 있다 — `die`·`person`·
  `louse`의 복수는 각각 `dice`·`people`·`lice`다. 그런 의심스러운 상황에서의 조언은
  **영문법을 따르거나 대체할 낱말을 찾으라**는 것이다 (2장, p.45).[^dynowski2025]

## 스칼라 이름에 단위를 담아라

- 문제의 진술이 이렇다 — API 응답 필드는 온도·속도·고도·압력·크기·지속·길이·무게 같은 스칼라
  값을 자주 담는데, **대부분의 API는 어떤 단위 체계가 쓰이는지에 대한 정보를 결여한다**(미터법
  국제단위계인지 야드파운드법인지). 그러면 **개발자는 자기에게 편한 단위를 가정하고, 그것이
  충돌로 이어질 수 있다** (2장, p.45).[^dynowski2025]
- 저자들이 대는 실물 둘이 **도쿄 디즈니랜드 롤러코스터 탈선**과 **NASA 화성 기후 궤도선의
  실패**다 (2장, p.45).[^dynowski2025] 이 KB는 두 사건의 원전을 갖고 있지 않으므로 이 책을
  통한 2차 경유로 둔다.
- 처방은 이름에 있다 — **단위 오류의 위험을 줄이려면 스칼라의 이름이 단위를 담을 수 있다.**
  `durationSeconds`·`lengthMeters`·`temperatureCelsius`·`weightGrams`·`widthPixels` (2장,
  p.45).[^dynowski2025]

## 변경의 두 축과 두 층위

- **API는 바뀌고 진화한다.** 그래서 변경이 일어나는 동안에도 API가 모든 사용자를 계속 섬기게
  해 주는 버저닝을 생각해야 한다 (2장 §"Evolving APIs", p.45).[^dynowski2025]
- 변경을 두 축으로 가른다 (2장, p.45).[^dynowski2025]
  - **더하기(additive)인가 빼기(subtractive)인가** — 더하기는 새 기능이 API에 더해지는 것,
    빼기는 기능이 API에서 없어지는 것이다. **기존 기능의 수정은 빼기 뒤에 더하기가 온 것으로
    볼 수 있다.**
  - **어느 층위에 나타나는가** — **인터페이스**(엔드포인트·프로시저·질의·뮤테이션)와
    **자원**(메시지) 둘이다.
- 그 변경이 체계에 미치는 효과는 **깨거나 안 깨거나** 둘이다 (2장, p.45).[^dynowski2025]

## 무엇이 깨고 무엇이 안 깨는가

- 저자들은 효과를 일반론으로 서술하는 대신 REST API 클라이언트에 대한 예로 보인다. 예의 전제는
  가상의 주사위 엔드포인트에 `GET`을 보내 JSON 응답(`data.message`와 `data.outcome`)을 받는
  것이고, **REST를 맥락으로 쓰지만 깨는·안 깨는 변경이라는 발상은 다른 API 스타일로 확장될 수
  있다**고 적는다 (2장, pp.45–46).[^dynowski2025]

| 변경 | 효과 | 예 |
|---|---|---|
| 엔드포인트 개명 | 깬다 | `/v1/roll/die`를 `/v1/roll-die`로 |
| API 판 제거 | 깬다 | `v1` 제거 |
| 콘텐츠 타입 변경 또는 미지원 | 깬다 | `application/json` 대신 `application/xml`을 요구하거나 `application/xml`을 `application/json`으로 바꿈 |
| 필드 제거 | 깬다 | `outcome` 필드 삭제 |
| 필드 개명 | 깬다 | `outcome` 필드를 `roll` 필드로 |
| 필드의 자료형 변경 | 깬다 | `int`(5)를 `string`("5")으로 |
| 새 필드·엔드포인트 추가 | 안 깬다 | `data`에 `sides` 필드 추가 |
| 기본값 있는 질의 매개변수 추가 | 안 깬다 | `sides` 질의 매개변수 추가 |
| 새 콘텐츠 타입 추가 | 안 깬다 | `application/xml` 콘텐츠 타입 추가 |
| 선택적 맞춤 헤더 추가 | 안 깬다 | 맞춤 헤더 추가 |

- 표 밖에 한 줄이 더 있다 — **REST API에서 데이터의 표현을 개명하거나 제거하거나 재정렬하면**
  그 변경에 걸린 기능을 쓰는 클라이언트에 깨는 변경이 된다. 각주에서 이유를 댄다:
  **클라이언트가 데이터가 특정 순서로 오기를 기대하면 데이터의 재정렬이 그 클라이언트에 영향을
  준다** (2장, p.46).[^dynowski2025]

## API가 그대로인데 깨지는 경우

- 이 절에서 가장 날 선 claim이 마지막에 온다 — **깨는 변경은 API에 대응하는 변경이 없이
  클라이언트 쪽 행동이 바뀌는 데서도 생길 수 있다.** 클라이언트가 API의 행동이나 구조에 대해
  **보장되지 않은 가정**을 할 때 그렇다 (2장, p.46).[^dynowski2025]
- 저자들이 드는 실물 — 클라이언트가 `status` 필드에 대해 API의 실제 값 `active` 대신
  `enabled`가 돌아오기를 기대하기 시작하면, **API 응답이 일관되게 유지되더라도 클라이언트
  로직이 깨진다** (2장, p.46).[^dynowski2025]
- 후진 호환과 전진 호환이라는 짝은 이 절 곁글의 몫이고, 그 전문은
  [후진 호환과 전진 호환](../concepts/backward-and-forward-compatibility.md)에 있다.

## 계약이라는 낱말

- 버저닝 절은 계약의 규정으로 연다 (2장 §"API Versioning", p.47).[^dynowski2025]
  - **흔히 API를 계약이라 부르는데, 그것은 API 클라이언트와 API 제공자 사이의 합의라는
    뜻**이다.
  - **API 계약은 API의 데이터 모양과 형식과 행동을 서술한다.**
  - **계약은 명세로 작동하며, 그로써 클라이언트와 서버가 공유된 이해를 갖는다.** 명세는 한편으로
    API가 무엇을 제공하는지를, 다른 편으로 클라이언트가 그 API로 무엇을 할 수 있는지를 말한다.
- 그리고 버저닝의 자리를 거기서 끌어낸다 — **현실은 계약이 자주 개정되고 API도 그렇다는
  것**이고, **API의 버저닝은 계약의 변경을 가리키며 옛 클라이언트가 옛 API를 계속 쓰게, 새
  클라이언트가 최신 판을 쓰게 한다** (2장, p.47).[^dynowski2025]

## 판을 어디에 둘 것인가

- 저자들은 판을 놓을 자리 넷을 표로 들고 각각을 따로 서술한다 (2장 표 2-6과 그 뒤 목록,
  pp.48–49).[^dynowski2025]

**경로 기반 버저닝** — 판이 경로의 일부로 명시적으로 열거된다(`/api/v1/resource`).

- 판의 변화를 클라이언트에 분명히 알리고, **깨는 변경이 있거나 자원이 독립적으로 진화하는
  API에 잘 맞는다.**
- **판이 API 전체에 걸리므로 이 방법은 거친 입도에서 작동한다.** 헤더 기반 같은 전략과 달리
  개별 엔드포인트에 대한 세밀한 통제를 허용하지 않는다.
- 제대로 된 리팩터링(공통 로직을 위한 공유 라이브러리 따위) 없이 여러 판을 유지하면 **중복 코드와
  늘어난 유지보수 노력**으로 이어질 수 있다.

**질의 매개변수 버저닝** — 판이 URL에 질의 매개변수로 주어진다(`?api-version=v1`).

- 이점은 **변경의 범위가 자원으로 한정된다**는 것이다. 그래서 **URL이 모든 클라이언트에 걸쳐
  일정하게 유지되고**, 엔드포인트가 개명되거나 제거되지 않는 한 기반 URL이 바뀔 필요가 없다.
- **버저닝이 자원 식별자에 묶이는 대신 요청 수준에 적용되므로 더 세밀하다.**
- 대가는 라우팅이다 — **라우팅이 URL 경로로 정해지지 않고 요청을 받는 함수 안에서 처리되므로**
  특정 판의 올바른 처리기로 요청을 보내는 보조 로직이 필요해 코드베이스가 커질 수 있다.
  게다가 **모든 자원이 질의 수준에서 문서화되어야 한다.**

**헤더 기반 버저닝** — 판이 요청 헤더에 담긴다(`Accept-Version: v1`, 또는 `Accept` 헤더의
미디어 타입 매개변수).

- 클라이언트가 **API가 진화해도 같은 URL을 쓸 수 있게** 한다.
- **URL 기반이나 경로 기반보다 덜 투명하다** — 판 정보가 곧바로 보이지 않기 때문이다. 그
  가시성 저하가 **디버깅과 로깅을 복잡하게 만든다.** 개발자와 테스터가 판을 알려면 요청 헤더를
  들여다봐야 한다.
- **RESTful 콘텐츠 협상 원칙을 따르기는 하지만 모호함을 들여오고 판 관리를 더 어렵게 만들 수
  있다.** 게다가 **프록시 같은 일부 중개 체계가 맞춤 헤더를 벗겨 내거나 막을 수 있다.**

**메시지 적재물 버저닝** — 판이 메시지 스키마의 필드로 들어간다(`{"version": "v1", "data": {...}}`).

- **이벤트 기반 아키텍처와 브로커 기반 API에 흔한 전략**이다. 그런 곳에서는 **메시지가
  오래 살아 있거나 나중 처리를 위해 저장될 수 있기 때문**이다.
- 이점은 **각각 다른 판을 가진 메시지 여럿을 체계에 배포할 수 있다**는 것이고, 단점은
  **메시지를 받는 쪽이 판마다 따로 다뤄야 하므로 소비자가 관리하기 더 어려워진다**는 것이다.

## 어떤 형식으로 매길 것인가

- 자리와는 별도로 **어떤 형식으로 판을 매길 것인가**라는 물음이 있고, 여러 접근과 그 조합이
  존재한다 (2장, p.50).[^dynowski2025]
  - **시맨틱 버저닝** — `MAJOR.MINOR.PATCH` 형식(`1.3.5`)으로, **MAJOR는 깨는 변경을, MINOR는
    후진 호환 변경을, PATCH는 후진 호환 버그 수정을 가리킨다.**
  - **캘린더 버저닝** — 판 이름에 달력 날짜를 쓴다(`2024-11-01`이나 `2024.47`).
  - **해시 버저닝** — 해시를 판 라벨로 쓴다. 예가 버전 관리의 커밋 해시(`237a2b4f`)다.

## 섞지 말라는 권고와 스타일별 관례

- **여러 버저닝 전략을 조합하는 것은 가능하다** — 경로 기반과 질의 매개변수 버저닝을 섞으면
  `/api/v1/orders/123?version=1.2.3` 같은 엔드포인트가 된다. 저자들은 **그 접근을 권하지
  않는다** (2장 곁주, p.49).[^dynowski2025] 이유가 셋이다.
  - 애플리케이션을 복잡하게 만든다.
  - **자원 식별과 우선순위 판정을 어렵게 만든다.**
  - **캐싱을 방해한다.**
- 스타일마다 관례가 다르다 (2장, p.49).[^dynowski2025]
  - **GraphQL 같은 의도 지향 API에서는 판이 필드 이름의 개명으로 표현된다**(`updateOrderV2`).
  - **gRPC는 패키지와 서비스 이름을 버저닝하는 쪽을 선호한다.** 메서드 이름에 판 접미를 붙이는
    것(`UpdateOrderV2`)도 가능하지만 덜 흔하다.

## 버저닝을 아예 피하라는 쪽

- 목록의 마지막 항목이 나머지를 부정한다 — **또 하나의 접근은 API의 버저닝을 아예 피하는
  것**이다 (2장, p.49).[^dynowski2025] 그 자리에 각주가 붙고, 각주가 근거를 댄다.

  > Roy Fielding's recommendation, given at the 2013 Evolve conference, is to avoid
  > introducing breaking changes: "DON'T—versioning an interface is a polite way to kill
  > deployed applications."

- 이 KB는 그 강연을 원전으로 갖고 있지 않으므로 **이 책을 통한 2차 경유**로 둔다. 같은 방향의
  조언을 다른 소스가 어떻게 적는지는
  [계약을 깨는 변경의 관리](../concepts/managing-breaking-api-changes.md)에 있고, 그쪽은
  "버저닝을 어떻게 하는가"라는 물음 자체를 **번호 체계의 물음이 아니라 계약 변경을 다루는
  물음**으로 고쳐 쓴다. 이 페이지가 답하는 것은 그 고쳐 쓴 물음이 아니라 **라벨을 어디에 어떤
  형식으로 놓는가**이고, 두 물음은 겨루지 않는다.

## 라벨 하나로는 전해지지 않는다

- 버저닝의 어려움이 한 문장으로 적힌다 — **잠재적으로 큰 API 변경 집합을 판 라벨 하나로
  전달하는 것**이다 (2장, p.50).[^dynowski2025]
- 그래서 라벨의 뜻을 설명하는 것에 더해 세 가지가 필요하다 — **새 기능을 알리는 능력**, **깨는
  변경을 알리는 능력**, 그리고 **변경에 적응할 시간을 주는 것**이다. 그 수단으로 드는 것이
  **API 문서 웹사이트의 변경 기록(changelog)**, **Atom 피드**, 그리고 **다가올 변경을 서술하는
  API 응답 안의 전용 메타데이터 절**이다 (2장, p.50).[^dynowski2025]
- 기계 쪽 수단도 하나 붙는다 — **JSON Schema가 JSON 인코딩 데이터의 모양을 서술하고 검증하는
  것을 돕고, 도입하려는 변경이 API를 깰지를 그 도구로 알아낼 수 있다.** 다만 **검증되었고
  신뢰할 수 있는 온라인 도구만 쓰라**는 단서가 붙는다 — 그러지 않으면 민감한 정보를 제3자와
  공유하는 위험을 지게 된다 (2장, p.50).[^dynowski2025]
