# 카프카 물리적 저장소

**목차**: [기본 단위와 그 상한](#기본-단위와-그-상한) · [파티션 할당](#파티션-할당) · [세그먼트 — 파일 관리](#세그먼트--파일-관리) · [파일 형식](#파일-형식) · [인덱스](#인덱스) · [계층화된 저장소](#계층화된-저장소) · [이어지는 페이지](#이어지는-페이지)

하나의 질문: **카프카는 파티션을 어느 디스크에 어떤 파일로 놓는가, 그리고 그 선택이
무엇을 제약하는가.**

## 기본 단위와 그 상한

- 카프카의 기본 저장 단위는 **파티션 레플리카**다 (6장, p.149).[^shapira2021]
- 결정적 제약: **파티션은 브로커 사이에 쪼갤 수 없고, 같은 브로커의 여러 디스크 사이에도
  쪼갤 수 없다. 그래서 파티션 크기는 하나의 마운트 포인트에서 쓸 수 있는 공간으로
  제한된다** (6장, p.149).[^shapira2021]
  - 마운트 포인트는 JBOD 구성이면 디스크 한 대, RAID 구성이면 여러 디스크일 수 있다.
- 관리자는 파티션이 저장될 디렉터리 목록을 `log.dirs`로 정의한다 — 카프카가 오류 로그를
  두는 위치(`log4j.properties`에 설정)와 혼동하지 말 것. 보통 카프카가 쓸 마운트
  포인트마다 디렉터리를 하나씩 넣는다 (6장, p.149).[^shapira2021]

## 파티션 할당

- 토픽을 만들면 카프카가 먼저 파티션을 브로커에 배분한다. 브로커 6대에 파티션 10개,
  복제 팩터 3이면 **파티션 레플리카 30개를 6대에 배분**하는 문제가 된다 (6장,
  p.151).[^shapira2021]
- 목표 셋 (6장, p.151):[^shapira2021]
  - 레플리카를 브로커에 고르게 펼친다 — 이 예에서는 브로커당 5개.
  - 파티션마다 각 레플리카가 서로 다른 브로커에 있게 한다. 파티션 0의 리더가 브로커 2에
    있으면 팔로워는 3과 4에 둘 수 있지만 2와 3에는 둘 수 없다.
  - **브로커에 랙 정보가 있으면(0.10.0 이상) 각 파티션의 레플리카를 가능한 한 서로 다른
    랙에 할당한다.** 랙 하나가 통째로 죽어도 파티션 전체가 사용 불가가 되지 않는다.
- 절차는 라운드 로빈이다 — 임의의 브로커에서 시작해 리더를 차례로 배정하고, 파티션마다
  리더에서 오프셋을 늘려 가며 레플리카를 배치한다 (6장, p.151).[^shapira2021]
- 랙 인식을 고려하면 브로커를 번호순이 아니라 **랙이 번갈아 나오는 순서로 정렬한 뒤**
  같은 절차를 돌린다. 브로커 0·1이 한 랙, 2·3이 다른 랙이면 0, 2, 1, 3 순으로 고른다 —
  이러면 파티션 0의 리더가 브로커 2일 때 첫 레플리카는 완전히 다른 랙의 브로커 1이 된다
  (6장, pp.151–152).[^shapira2021]
- 브로커를 고른 다음 디렉터리를 고르는 규칙은 별개이며 아주 단순하다 — **디렉터리별
  파티션 개수를 세어 가장 적은 디렉터리에 새 파티션을 넣는다.** 그래서 디스크를 새로
  추가하면 균형이 맞을 때까지 새 파티션이 전부 그 디스크에 생긴다 (6장,
  p.152).[^shapira2021]
- 여기 함정이 있다 (6장, p.152):[^shapira2021]
  - **브로커 할당은 가용 공간이나 현재 부하를 보지 않는다.**
  - **디스크 할당은 파티션 개수만 보고 파티션 크기는 보지 않는다.**
  - 그래서 브로커마다 디스크 용량이 다르거나(구·신형 서버 혼재), 일부 파티션이 비정상적으로
    크거나, 한 브로커에 크기가 다른 디스크가 섞여 있으면 할당에 주의해야 한다.

## 세그먼트 — 파일 관리

- 보존은 카프카의 중요한 개념이다. 데이터를 영원히 보관하지 않고, 모든 컨슈머가 읽기를
  기다리지도 않는다 — 관리자가 토픽마다 보존 기간(또는 보존 바이트)을 설정한다 (6장,
  p.152).[^shapira2021]
- 큰 파일에서 지울 메시지를 찾아 일부를 삭제하는 일은 느리고 오류가 나기 쉬우므로,
  **파티션을 세그먼트(segment)로 쪼갠다.** 기본값은 세그먼트당 데이터 1GB 또는 1주치 중
  더 작은 쪽이며, 한도에 닿으면 파일을 닫고 새 파일을 연다 (6장,
  pp.152–153).[^shapira2021]
- 지금 쓰고 있는 세그먼트를 액티브 세그먼트(active segment)라 하고, **액티브 세그먼트는
  절대 삭제되지 않는다** (6장, p.153).[^shapira2021]
- 여기서 실무적으로 중요한 결과가 나온다. 원문 직인용 (6장, p.153):[^shapira2021]

> The active segment is never deleted, so if you set log retention to only store a day
> of data, but each segment contains five days of data, you will really keep data for
> five days because we can't delete the data before the segment is closed.

  - 반대로 1주치를 보관하되 하루마다 세그먼트를 새로 굴리기로 하면, 매일 새 세그먼트를
    열고 가장 오래된 것을 지우므로 파티션은 대체로 세그먼트 7개를 갖게 된다.
- 브로커는 **모든 파티션의 모든 세그먼트에 대해 열린 파일 핸들을 유지한다 — 비활성
  세그먼트도 마찬가지다.** 그래서 열린 파일 핸들 수가 비정상적으로 많아지고 OS를 그에
  맞게 튜닝해야 한다 (6장, p.153).[^shapira2021]

## 파일 형식

- 각 세그먼트는 하나의 데이터 파일에 저장되며, 그 안에 카프카 메시지와 오프셋이 담긴다
  (6장, p.153).[^shapira2021]
- 핵심 설계 결정: **디스크의 데이터 형식이 프로듀서→브로커, 브로커→컨슈머로 오가는
  메시지 형식과 동일하다** (6장, p.153).[^shapira2021]
  - 이것이 [제로카피](../concepts/kafka-request-processing.md) 최적화를 가능하게 하고,
    프로듀서가 이미 압축한 메시지를 풀었다 다시 압축하는 일도 피하게 한다.
  - 대가도 명확하다 — **메시지 형식을 바꾸기로 하면 와이어 프로토콜과 디스크 형식이 함께
    바뀌어야 하고, 브로커는 업그레이드 때문에 파일에 두 형식이 섞인 경우를 다룰 줄 알아야
    한다.**
- 다운 컨버전의 비용도 여기서 나온다 — v2 메시지를 v2 미지원 컨슈머가 읽으려 하면 브로커가
  v2에서 v1으로 변환해야 하는데, **이 변환은 정상 소비보다 CPU와 메모리를 훨씬 많이 쓰므로
  피하는 것이 낫다.** KIP-188이 `FetchMessageConversionsPerSec`와
  `MessageConversionsTimeMs` 지표를 도입했고, 옛 클라이언트를 쓰고 있다면 지표를 확인하고
  가능한 한 빨리 업그레이드하기를 권한다 (6장, p.155).[^shapira2021]
- 메시지는 사용자 페이로드와 시스템 헤더로 이뤄진다. 사용자 페이로드는 선택적 키, 값,
  선택적 헤더 모음(각 헤더가 자체 키/값 쌍)을 담는다 (6장, p.153).[^shapira2021]
- 0.11 버전(v2 메시지 형식)부터 **프로듀서는 항상 배치로 보낸다.** 메시지 하나만 보내면
  배치 오버헤드가 붙지만, 둘 이상이면 배치가 공간을 아껴 네트워크와 디스크 사용을 줄인다
  (6장, p.153).[^shapira2021]
  - `linger.ms=10` 같은 작은 지연이 성능에 도움이 되는 이유가 이것이다 — 한 번에 보내는
    메시지 수가 늘어난다.
  - **카프카는 파티션마다 별도 배치를 만들므로, 적은 파티션에 쓰는 프로듀서가 더 효율적이다.**
  - 프로듀서는 하나의 프로듀스 요청에 여러 배치를 담을 수 있다. 압축을 쓴다면 큰 배치를
    보낼수록 네트워크와 브로커 디스크 양쪽에서 압축률이 좋아진다.
- 배치 헤더가 담는 것 (6장, p.154):[^shapira2021]
  - 메시지 형식의 현재 버전을 나타내는 매직 넘버.
  - 배치 첫 메시지의 오프셋과 마지막 메시지 오프셋과의 차이 — **나중에 배치가 압착되어
    일부 메시지가 제거돼도 이 값들은 보존된다.** 프로듀서가 배치를 만들 때 첫 오프셋은
    0이며, 이 배치를 처음 영속화하는 브로커(파티션 리더)가 실제 오프셋으로 바꾼다.
  - 첫 메시지의 타임스탬프와 배치 내 최대 타임스탬프. 타임스탬프 유형이 생성 시각이 아니라
    추가 시각이면 브로커가 값을 정한다.
  - 배치 크기(바이트).
  - 배치를 받은 리더의 에포크 — **리더 선출 뒤 메시지를 잘라낼 때 쓰인다**(KIP-101,
    KIP-279).
  - 손상 검증용 체크섬.
  - 속성 16비트 — 압축 유형, 타임스탬프 유형(클라이언트/브로커), 배치가 트랜잭션의
    일부인지 컨트롤 배치인지.
  - 프로듀서 ID, 프로듀서 에포크, 배치의 첫 시퀀스 — 정확히 한 번 보장에 쓰인다.
  - 그리고 배치에 속한 메시지들.
- 레코드 각각이 담는 것 (6장, p.154):[^shapira2021]
  - 레코드 크기(바이트).
  - 속성 — 현재 레코드 수준 속성은 없어 쓰이지 않는다.
  - 현재 레코드 오프셋과 배치 첫 오프셋의 **차이**.
  - 이 레코드 타임스탬프와 배치 첫 타임스탬프의 **차이**(밀리초).
  - 사용자 페이로드: 키, 값, 헤더.
- 설계 의도가 여기 드러난다 — **레코드당 오버헤드는 아주 작고 시스템 정보 대부분이 배치
  수준에 있다.** 첫 오프셋과 타임스탬프를 헤더에 한 번 저장하고 레코드마다 차이만 저장하면
  레코드 오버헤드가 크게 줄어, 큰 배치일수록 효율이 좋아진다 (6장,
  p.154).[^shapira2021]
- 사용자 데이터 배치 외에 **컨트롤 배치**가 있다 — 트랜잭션 커밋 같은 것을 나타내며,
  컨슈머가 처리하고 사용자 애플리케이션에 전달하지 않는다. 현재는 버전과 유형 지시자만
  담는다(0=중단된 트랜잭션, 1=커밋) (6장, p.155).[^shapira2021]
- 직접 확인하는 수단으로 브로커에 `DumpLogSegment` 도구가 들어 있다 — 파일시스템의 파티션
  세그먼트를 열어 내용을 본다. `--deep-iteration`을 주면 래퍼 메시지 안에 압축된 메시지
  정보를 보여 준다 (6장, p.155).[^shapira2021]

## 인덱스

- 컨슈머는 사용 가능한 아무 오프셋에서나 페치를 시작할 수 있다. 그래서 오프셋 100부터
  1MB를 달라는 요청이 오면 브로커는 **그 파티션의 여러 세그먼트 중 어디에 있을지 모르는
  오프셋 100의 메시지를 빠르게 찾아야 한다** (6장, p.155).[^shapira2021]
- 그래서 카프카는 파티션마다 인덱스를 유지한다 — **오프셋을 세그먼트 파일과 그 안의 위치로
  매핑한다** (6장, p.155).[^shapira2021]
- 두 번째 인덱스는 **타임스탬프를 메시지 오프셋으로 매핑**한다. 타임스탬프로 메시지를 찾을
  때 쓰이며, Kafka Streams가 이 조회를 많이 쓰고 일부 페일오버 시나리오에도 유용하다
  (6장, p.156).[^shapira2021]
- 인덱스도 세그먼트로 쪼개져 있어 메시지가 지워질 때 옛 인덱스 항목도 지울 수 있다 (6장,
  p.156).[^shapira2021]
- 카프카는 **인덱스의 체크섬을 유지하지 않는다.** 인덱스가 손상되면 해당 로그 세그먼트의
  메시지를 다시 읽어 오프셋과 위치를 기록하는 것만으로 재생성된다. 그래서 **관리자가
  인덱스 세그먼트를 지워도 완전히 안전하다** — 다만 복구가 오래 걸릴 수 있다 (6장,
  p.156).[^shapira2021]

## 계층화된 저장소

> **버전 조건**: 2018년 말 시작돼 **2판 집필 시점에는 진행 중이었고 3.0 릴리스를 목표로
> 하던 기능**이다. 아래는 그 시점의 설계와 측정치다 (6장, p.149).[^shapira2021]

- #hypothesis 소스는 "3.0 릴리스를 목표로 진행 중"이라고만 적으므로, 계층화된 저장소가
  실제로 3.0에 들어갔는지는 이 소스로 판정할 수 없다. 카프카의 다른 대형 기능(KRaft)도
  2판이 예고한 일정보다 늦게 완성됐다는 점을 보면 이 기능 역시 3.0보다 뒤에 도착했을
  가능성이 있다. 후속 소스로 도입 릴리스를 확인해야 한다.

- 동기는 파티션이 로컬 디스크에 묶여 있다는 데서 온다 (6장, pp.149–150):[^shapira2021]
  - 파티션에 저장할 수 있는 데이터량에 한계가 있어 **최대 보존 기간과 파티션 수가 제품
    요구가 아니라 물리 디스크 크기에 끌려간다.**
  - 디스크와 클러스터 크기가 저장 요구로 결정되므로, 지연과 처리량만 고려했을 때보다 큰
    클러스터가 되고 비용이 오른다.
  - 클러스터를 늘리거나 줄일 때 파티션 이동 시간이 파티션 크기에 좌우된다 — **큰 파티션은
    클러스터를 덜 탄력적으로 만든다.**
- 구조는 두 계층이다 — 로컬 계층은 지금의 카프카 저장 계층 그대로 브로커 로컬 디스크에
  로그 세그먼트를 두고, **원격 계층은 HDFS나 S3 같은 전용 저장 시스템에 완료된 로그
  세그먼트를 둔다** (6장, p.150).[^shapira2021]
- 계층별로 보존 정책을 따로 둘 수 있다. 로컬이 훨씬 비싸므로 **로컬은 몇 시간에서 며칠,
  원격은 며칠에서 몇 달**로 잡는 식이다 (6장, p.150).[^shapira2021]
- 로컬이 원격보다 지연이 훨씬 낮은데, 지연에 민감한 애플리케이션은 꼬리 읽기를 하므로
  로컬에서 서비스되고 **기존의 페이지 캐시 활용 기전에서 그대로 이득을 본다.** 백필이나
  장애 복구처럼 오래된 데이터가 필요한 쪽이 원격에서 읽는다 (6장,
  p.150).[^shapira2021]
- 이중 계층이 주는 것 (6장, p.150):[^shapira2021]
  - 메모리·CPU와 독립적으로 저장을 확장할 수 있어 **카프카가 장기 저장 솔루션이 된다.**
  - 브로커에 저장되는 데이터가 줄어 **복구와 리밸런싱 때 복사할 데이터가 줄어든다.** 원격
    계층에 있는 세그먼트는 브로커로 복원할 필요가 없다.
  - 보존 기간을 늘리려고 클러스터 저장소를 늘리고 노드를 더할 필요가 없어진다.
- 설계는 KIP-405에 있고, `RemoteLogManager`라는 구성 요소와 리더 따라잡기·리더 선출 같은
  기존 기능과의 상호작용이 포함된다 (6장, p.150).[^shapira2021]
- KIP-405가 문서화한 성능 실측 (6장, pp.150–151):[^shapira2021]
  - 카프카의 통상적인 고처리량 워크로드에서는 브로커가 세그먼트를 원격으로도 보내야 하므로
    **지연이 p99 기준 21ms에서 25ms로 조금 늘었다.**
  - 일부 컨슈머가 오래된 데이터를 읽는 경우, 계층화된 저장소가 없으면 p99 21ms 대 60ms로
    큰 영향을 받지만 **계층화된 저장소를 켜면 25ms 대 42ms로 영향이 뚜렷이 줄었다.**
  - 이유는 원격 읽기가 네트워크 경로로 이뤄져 **로컬 디스크 I/O나 페이지 캐시를 놓고
    경합하지 않고, 페이지 캐시를 새 데이터로 온전히 남겨 두기 때문**이다.
  - 즉 계층화된 저장소는 무한 저장·저비용·탄력성에 더해 **과거 읽기와 실시간 읽기 사이의
    격리**를 제공한다.
