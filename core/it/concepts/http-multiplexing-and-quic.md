하나의 질문: **HTTP/2와 HTTP/3는 선로 위 형식과 전송을 갈아 무엇을 얻었고, 그래도 남은 것은
무엇인가.**

## 버전 조건

> **버전 조건**: 2025년 저술 시점. 배포 현황 수치는 2024년 실측 보고 기준이고, 관찰 기록의 도구
> 판은 nghttp2 1.62.1·curl 8.8.0이며 서버는 nginx 1.27.0이다. 저자들 스스로 **QUIC의 새 판이
> 구현되면 이 패킷 순서의 세부는 달라질 수 있다**고 적는다(4장, p.146). 프레임과 패킷 형식의
> 정본은 이 책이 아니라 각 판의 RFC이고, HTTP 의미론의 정본은
> [HTTP의 정의와 문서의 범위](../concepts/http-definition-and-scope.md) 계열이 갖는다.

## major 번호가 오른다는 것의 뜻

- 번호가 1에서 2로 오른 것이 선언하는 것이 하나다. **HTTP major 판 번호의 증가는 프로토콜 안
  메시지의 형식이 바뀌었음을 가리킨다** (4장, p.133).[^dynowski2025] 저자들이 그 근거로 판
  번호의 사용과 해석을 다루는 RFC 2145를 각주에 든다.
  - 같은 규칙을 규범 쪽에서 진술하는 자리가
    [HTTP 버전 번호와 의미론의 분리](../concepts/http-version-numbering.md)다.
- 내력이 짧다. **2009년 구글이 SPDY라는 프로토콜의 작업을 공개했고 그것이 뒤에 HTTP/2가
  되었으며, 2015년 RFC로 출판되었다** (4장, p.133과 그 각주).[^dynowski2025]
- 동기는 하나였다. **HTTP/2의 주된 동기는 HTTP/1.1과 견주어 웹사이트 적재 속도를 더 끌어올리는
  것이었다** (4장, p.133).[^dynowski2025]
- 설계 방법이 특이했고 저자들이 그 조건을 짚는다. **구글이 택한 접근은 실제 웹 트래픽에서 나온
  실험 결과에 근거해 프로토콜을 설계하고 진화시키는 것이었고, 이것이 가능했던 것은 구글이
  클라이언트(2008년 출시된 크롬 브라우저)와 서버 인프라 양쪽을 쥐고 있었기 때문이다**
  (4장, p.133).[^dynowski2025]
- 저자들이 다루지 않기로 한 것도 밝힌다. **자원 우선순위나 서버 푸시처럼 덜 쓰이는 HTTP/2 기능은
  다루지 않으며, 서버 푸시는 이미 크롬에서 제거되었다** (4장, p.133 각주).[^dynowski2025]

## 이진 프레임이 바꾼 것

- 첫 변화가 메시지를 쪼개는 방식이다. **HTTP/2는 HTTP 메시지를 이진 부호화된 프레임(frame)으로
  가르며, 프레임 종류마다 프로토콜 안에서 맡은 목적이 있다**
  (4장, p.133).[^dynowski2025] 저자들이 드는 예가 넷이다.
  - `DATA` — HTTP 메시지 바디
  - `HEADERS` — HTTP 메시지 헤더
  - `SETTINGS` — HTTP/2에 관련된 여러 설정
  - `GOAWAY` — 새 스트림을 시작하지 않겠다는 의사, 또는 심각한 오류의 신호
- 읽는 쪽이 쉬워지는 이유가 길이에 있다. **프레임 형식에 메시지 길이가 포함된 덕에 HTTP/2 프레임은
  HTTP/1보다 기계가 읽기 쉽다. HTTP/2에서는 프레임의 시작에서 길이와 종류를 읽고, 그다음 데이터를
  읽어 프레임 종류에 따라 해석한다. HTTP/1에서는 메시지 경계가 `<CR><LF>`로 표시되고 메시지
  바디의 길이는 `Content-Length` 헤더가 정한다** (4장, p.133).[^dynowski2025]
  - 프레이밍이 무엇을 해야 하는가를 판과 무관하게 규정한 자리가
    [HTTP 메시지 추상과 프레이밍](../concepts/http-message-abstraction-and-framing.md)이다.

## 헤더 압축 HPACK

- 압축이 필요한 이유가 HTTP의 성질에서 나온다. **HTTP가 무상태이기 때문에(쿠키의 존재는 여기서
  무시하자) 헤더는 모든 HTTP 요청·응답과 함께 거듭 보내진다. HTTP/1.0이 이미 메시지 바디 압축을
  허용하는 데 반해 HTTP/2는 헤더를 HPACK이라는 맞춤 압축 형식으로 압축한다**
  (4장, p.134).[^dynowski2025]
- 효과가 방향마다 다르다. **HTTP 요청에서는 메시지 바디 대비 헤더 크기의 비중이 줄고, HTTP
  응답에서도 이득이 난다** (4장, p.134).[^dynowski2025]
- 형식이 그냥 압축이 아니다. **HPACK 형식은 CRIME 계열 보안 공격에 대한 압축의 취약성을 줄이도록
  설계되었다** (4장, p.134 각주).[^dynowski2025]

## 스트림과 다중화

- HTTP/2가 도입한 새 개념이 스트림이고, 저자들이 그 규정을 원문으로 옮긴다. 원문 직인용
  (4장, p.134):[^dynowski2025]

  > an independent, bidirectional sequence of frames exchanged between the client and server
  > within an HTTP/2 connection

  클라이언트와 서버가 하나의 HTTP/2 연결 안에서 주고받는, 독립적이고 양방향인 프레임의 열이다.
- 이 낱말에 주의가 붙는다. **이것은 TCP 스트림과 다르다** (4장, p.134).[^dynowski2025] TCP 쪽
  규정은 [소켓 API와 클라이언트·서버 규정](../concepts/socket-api-and-client-server-roles.md)에
  있다.
- 다중화가 실제로 서는 자리가 둘이다 (4장, p.134):[^dynowski2025]
  - **HTTP/2는 여전히 TCP를 전송 프로토콜로 쓰며, 한 TCP 세그먼트의 데이터가 여러 HTTP/2 프레임을
    담을 수 있다.** 그래서 단일 TCP 세그먼트가 서로 다른 HTTP 문서 자원 스트림(예컨대 서로 다른
    CSS 파일)에 속하는 프레임들을 담을 수 있다.
  - **TCP 세그먼트가 어느 한 스트림에 속하는 `DATA` 프레임 하나만 나를 수도 있고, 그런 세그먼트들이
    TCP 스트림 안에 라운드 로빈 방식으로 놓일 수 있다.**
- 우선순위도 동적으로 바꿀 수 있다. **클라이언트는 `PRIORITY` 프레임을 보내 이 스트림들의 우선순위
  변경을 동적으로 요청할 수 있다** (4장, p.134).[^dynowski2025]

## 다중화해도 HOL 블로킹은 남는다

- 이 장에서 가장 중요한 한계 진술이다. **다중화에도 불구하고 HTTP/2는 HOL 블로킹 문제를 풀지
  못한다. 단일 TCP 연결을 쓰기 때문이다** (4장, p.134).[^dynowski2025]
- 이득이 나는 조건이 한정된다. **HTTP/2가 구현한 응용 계층의 다중화는 패킷 유실이 없는 네트워크에서
  여러 HTTP 자원을 더 낮은 지연으로 가져오게 해 준다** (4장, p.134).[^dynowski2025]
- 유실이 나면 되돌아간다. **유실이 일어나면 어느 한 HTTP/2 스트림을 나르는 TCP 세그먼트가 그 TCP
  스트림의 나머지 세그먼트의 재조립을 막고, 그래서 다른 HTTP/2 스트림들도 함께 막힌다**
  (4장, p.134).[^dynowski2025]
  - TCP 쪽 기제의 규정과 패킷 수준 관찰은
    [HTTP 초기 판들과 TCP의 한계](../concepts/http-early-versions-and-tcp-limits.md)에 있다.
  - 저자들이 각주에 덧붙이는 뒷말이 있다. **HTTP/2가 TCP HOL 블로킹 문제를 풀지 못하므로, 최소한의
    프로토콜 변경으로 HTTP를 빠르게 만드는 것이 HTTP/1.1에 헤더를 더하는 것만으로 가능하지 않았겠
    느냐는 의문이 제기되었다** (4장, p.134 각주).[^dynowski2025]

## h2c 요청 하나가 프레임으로 보이는 모양

- 저자들이 암호화하지 않은 h2c로 요청 하나를 보내고 프레임 순서를 보인다
  (4장 §"HTTP/2 Frames and Streams"(pp.135–138)).[^dynowski2025]
  - 클라이언트가 먼저 이른바 "매직" 메시지를 보내 HTTP/2 프로토콜임을 알린다.
  - 이어 `SETTINGS` 프레임으로 자기 설정(동시 스트림 수와 스트림에 처음 보낼 데이터 양을 정하는
    초기 윈도 크기)을 보낸다. **설정은 언제나 스트림 0으로 주고받는다.**
  - 클라이언트가 HTTP 헤더를 담은 `HEADERS` 프레임을 스트림 1로 보낸다.
  - 서버가 자기 `SETTINGS`와 `WINDOW_UPDATE`를 비롯한 프레임 여럿과 자기 `HEADERS`로 답한다.
  - 서버가 스트림 1로 `DATA` 프레임에 바디를 실어 보낸다.
  - 클라이언트가 `GOAWAY` 프레임으로 새 스트림을 시작하지 않겠다는 의사를 알린 뒤 TCP 연결 종료를
    시작한다.
- 이 순서가 확인해 주는 것이 하나다. **여러 HTTP/2 프레임이 단일 TCP 세그먼트에 실려 간다**
  (4장, p.138).[^dynowski2025]
- 도구가 보이는 순서에 함정이 있다. **nghttp2의 구현 세부 때문에 헤더의 실제 값이 `HEADERS` 프레임보다
  앞서 출력되고, `DATA` 프레임도 실제 데이터 뒤에 나타난다** (4장, p.137).[^dynowski2025]

## 미들박스와 프로토콜 경화

- 이진 프레이밍이 배포에 값을 청구한다. **HTTP/2로 전달되는 메시지는 형식상 HTTP와 비슷하지만
  이진 프레이밍 때문에 네트워크 패킷 수준에서 낯설게 보인다. 그것이 미들박스(middlebox)의 존재
  때문에 그런 새 프로토콜을 인터넷에 배포할 가능성에 영향을 주며, 미들박스는 최종 사용자 기기와
  함께 네트워크 프로토콜의 진화를 제약해 이른바 프로토콜 경화(protocol ossification)를 낳는다**
  (4장, p.135).[^dynowski2025]
- 미들박스의 규정은 IP 라우터의 기능이 아닌 기능을 수행하는 모든 중개 장치다. 저자들이 드는 예가
  NAT와 방화벽과 로드 밸런서와 침입 탐지·방지 시스템과 CDN 캐시다
  (4장, p.135 각주).[^dynowski2025]
  - 이 규정은 RFC 9110이 말하는 중개자보다 넓다. 그쪽은 HTTP 통신의 참여자로 행동하는 프록시와
    게이트웨이와 터널을 가르고, 그 밖에 더 낮은 계층에서 트래픽에 손대는 것을 따로 다룬다. 경계는
    [HTTP 중개자](../concepts/http-intermediaries.md)에 있다.
- 경화가 구체적으로 무엇인지도 적힌다. **어떤 미들박스는 인식하지 못한 트래픽을 막거나 메타데이터
  (예컨대 HTTP나 TCP 헤더)를 고쳐서 새 프로토콜 판을 깨뜨린다. 미들박스와 운영체제가 새 프로토콜
  판을 채택하는 데 몇 해가 걸릴 수 있다** (4장, p.135).[^dynowski2025]
- 해법이 둘이고 그것이 다음 판의 모양을 결정한다. **패킷 구조를 암호화로 미들박스의 눈에서 감추는
  것과, 프로토콜을 운영체제 커널 공간이 아니라 사용자 공간에 구현하는 것이다**
  (4장, p.135).[^dynowski2025]
- HTTP/2는 절반만 갔다. **HTTP/2 명세는 암호화를 요구하지 않지만 웹 브라우저는 암호화된 판인
  h2만 지원한다. 다른 종류의 클라이언트는 평문 판인 h2c도 지원한다**
  (4장, p.135).[^dynowski2025]
  - 버전 조건: 2025년 저술 시점의 브라우저 구현 관행이다. 명세의 요건이 아니다.

## 왜 새 전송이 필요했는가

- 2010년대 초의 조건이 달라졌다. **스마트폰(아이폰은 2007년 발표)과 태블릿 같은 모바일 기기가
  덜 성능 좋은 망과 함께 떠오르면서 웹 자원을 가져오는 지연을 줄이는 것이 HTTP의 첫째 우선순위로
  이어졌다** (4장, p.139).[^dynowski2025]
- 그리고 새 요구가 둘 생겼다. **멀티호밍(한 기기가 네트워크 인터페이스나 IP 주소를 여럿 쓰는 것)과
  연결 이주(connection migration)가 중요해졌다. 모바일 기기가 집 와이파이와 5G 같은 셀룰러 망
  사이를 오가거나 고속 열차 여행처럼 셀룰러 망에서 먼 거리를 이동하면 IP 주소가 바뀌고, 그것이
  TCP 연결의 종료와 재수립으로 이어진다** (4장, p.139).[^dynowski2025]
- 저자들이 그 뿌리를 설계자의 회고로 짚는다. IP를 TCP에서 갈라낼 때 IP 주소를 종단 연결 식별자의
  일부로 쓰는 것이 영리하다고 여겼는데 나쁜 실수였고, 그것이 멀티호밍과 IP 주소가 바뀌는 이동성을
  망가뜨렸다는 빈트 서프(Vint Cerf)의 2010년 진술이다 (4장, p.139 각주).[^dynowski2025]
- 앞선 시도가 넷 있었다. **T/TCP(1994년 RFC)와 STCP(2000년 RFC)와 MPTCP(2012년 초안 RFC)와
  TCP Fast Open(2012년 초안 RFC)이다. 그러나 그것들은 불완전한 해법이었거나 보안 문제가 있었거나,
  인터넷에 배포된 TCP의 경화 때문에 채택되지 못했다** (4장, p.139).[^dynowski2025]
  - #hypothesis 저자들이 STCP를 "Stream TCP"로 풀어 적는데, 2000년 RFC로 나온 그 이름의 프로토콜은
    통상 SCTP(Stream Control Transmission Protocol)로 불린다. 오식으로 보이지만 저자들이 다른
    설명을 붙이지 않았으므로 원문 표기를 그대로 적어 둔다.

## QUIC이 채택을 얻으려고 고른 것

- **2013년 구글이 QUIC이라는 전송 프로토콜의 작업을 발표했고, 그것은 Stream TCP와 TCP Fast Open
  같은 프로토콜의 착상에서 영감을 받았으며 HTTP/3의 바탕이 되었다**
  (4장, p.139).[^dynowski2025]
- 설계 선택이 앞의 실패에서 곧장 나온다 (4장, p.139):[^dynowski2025]
  - **HTTP/2와 마찬가지로 QUIC은 암호화로 프로토콜 세부를 미들박스에서 감춘다는 착상을 썼다.**
    QUIC의 필수 암호화는 인터넷의 TLS 채택 증가와 때를 같이했고, 저자들이 드는 예가 2014년 결성된
    Let's Encrypt다.
  - **프로토콜이 운영체제(커널 공간)가 아니라 애플리케이션(사용자 공간)에서 동작하게 했다.**
  - **새 프로토콜을 만드는 대신 UDP 위에 프로토콜을 얹었다.** 새 프로토콜을 만들었다면 인터넷에
    배포되는 데 몇 해가 걸릴 수 있었다.

## QUIC의 기능 넷

- **필수 암호화와 TLS의 긴밀한 통합** (4장, p.140).[^dynowski2025]
  - **QUIC은 전통적인 OSI 모형 계층의 뜻으로 TLS를 쓰지 않는다. 대신 암호 정보를 얻으려고 TLS
    API 일부를 쓴다.**
  - **QUIC은 패킷마다 따로 암호화하는데, TLS는 최대 16KB 크기의 레코드 단위로 동작하므로 TLS
    레코드 하나가 여러 TCP 세그먼트에 걸친다. TLS는 데이터를 복호화하려면 레코드 전체가
    필요하고, 이것이 잠재적인 TLS HOL 블로킹을 낳는데 QUIC은 그것을 없앤다.**
  - 암호화가 다 덮지는 못한다. **아직 암호화되지 않고 남은 것 가운데 하나가 ClientHello에 실려
    대상 도메인을 드러내는 서버 이름 표시(SNI)다** (4장, p.140 각주).[^dynowski2025]
- **클라이언트가 HTTP 메시지를 보내기 전 왕복 수의 감소** (4장, p.141).[^dynowski2025]
  - **낙관적 핸드셰이크를 써서 그렇게 한다. QUIC 핸드셰이크에서 클라이언트는 서버의 TLS
    파라미터에 대한 자기 추측을 보내고, 이것이 초기 연결을 1 RTT로 줄인다.**
  - **TCP Fast Open과 비슷하게, 되돌아온 클라이언트가 안전한 HTTP 메서드를 쓰는 경우에는 QUIC이
    0-RTT(TLS 1.3의 기능) 재연결을 지원한다.** 지난 연결 이후 TLS 정보가 바뀌지 않았다고 낙관적으로
    가정하기에 클라이언트가 HTTP 메시지를 곧장 보낼 수 있다.
  - **클라이언트가 정당하지 않을 경우의 반사 공격을 막으려고 검증 토큰과 왕복을 더 쓰는 대체 경로로
    이뤄진 추가 기제가 있다.**
  - **왕복 수 감소는 모바일 같은 고지연 망에서 더 눈에 띄게 이롭다.**
- **연결 이주의 지원** (4장, p.141).[^dynowski2025]
  - **TCP가 연결 식별에 쓰는 네 쌍(출발지 IP 주소, 출발지 포트, 목적지 IP 주소, 목적지 포트) 대신
    QUIC은 핸드셰이크 동안 생성되고 교환되는 연결 ID(connection ID)의 집합을 쓴다.**
  - **연결 이주 중에 클라이언트는 사생활을 위해 그 연결 ID 가운데 하나를 쓰고, 그것이 서버로 하여금
    연결을 끊김 없이 이주시키게 한다.** 사용자와 지속적인 상호작용이 필요한 웹 애플리케이션에서
    체감이 클 수 있다.
  - 왜 하나가 아니라 집합인지가 각주에 있다. **연결 ID는 패킷에 평문으로 들어 있어 클라이언트
    추적을 허용하게 된다** (4장, p.141 각주).[^dynowski2025]
    - #hypothesis 본문은 연결 ID의 집합을 "암호화된"이라 적고 각주는 평문이라 적는다. 집합을 두고
      바꿔 쓰는 설계가 추적을 막는 쪽이므로 각주 쪽이 기제를 정확히 말하는 것으로 읽히지만, 저자들이
      그 차이를 설명하지 않는다.
- **TCP와 견준 HOL 블로킹 문제의 축소** (4장, p.141).[^dynowski2025]
  - **QUIC은 독립적인 스트림을 쓰므로 HOL 블로킹 문제가 그것들을 나르는 해당 패킷의 유실에 영향받는
    스트림들로 한정된다. QUIC은 단일 패킷 안에서도, 패킷들 사이에서도 스트림을 다중화할 수 있다.**
  - 그런데 이득이 확실하지 않다는 단서가 붙는다. **인터넷에서 패킷 유실은 흔히 몰려서 일어나므로
    여러 스트림을 나르는 QUIC 패킷들이 주어진 시간 구간 안에서 함께 유실될 수 있다. 그래서 그런
    경우에는 HOL 블로킹 축소로 인한 이득이 불분명하다.**
  - 대가가 압축에서 돌아온다. **스트림 수준 HOL 블로킹의 귀결 하나는 QUIC 스트림이 내부적으로는
    순서가 잡혀 있으나 서로 다른 스트림 사이에서는 반드시 순서가 잡혀 있지는 않다는 것이다.
    HTTP/2가 쓰는 HPACK 압축이 스트림의 순서 보존 전달을 요구했기 때문에, 이 거동 때문에 전용
    QPACK 헤더 압축 알고리즘이 개발되었다.**

## 그림 4-5가 배치하는 층

- 그림 4-5는 세 판의 계층 구조를 한 장으로 맞대는데, **그 배치의 상당 부분이 그림에만 있고 본문에는
  없다.** 읽어 옮긴다 (4장, p.140 그림 4-5).[^dynowski2025]

  | 층 | HTTP/1.1 | HTTP/2 | HTTP/3 |
  |---|---|---|---|
  | 맨 위 | HTTP 의미론 (세 판을 가로지르는 한 칸) | 〃 | 〃 |
  | HTTP 판 | 파이프라이닝 | 헤더 압축(HPACK) · 서버 푸시 · 우선순위 지정 · 스트림 다중화 | 헤더 압축(QPACK) · 서버 푸시 · 우선순위 지정 |
  | 보안 | TLS — 인증 · 키 협상 · 세션 재개 · 암복호화 | 〃 | TLS — 인증 · 키 협상 · 세션 재개/0-RTT (QUIC 안에 들어 있다) |
  | 전송 | TCP — 혼잡 제어 · 신뢰성 · 연결 지향 · 포트 번호 | 〃 | QUIC — 스트림 다중화 · 암복호화 · 연결 이주 · 혼잡 제어 · 신뢰성 · 연결 지향 / 그 아래 UDP — 포트 번호 |
  | 맨 아래 | IPv4/IPv6 | 〃 | 〃 |

- 이 그림에서 두 가지가 본문의 서술을 눈으로 확인해 준다.
  - **HTTP 의미론이 세 판 위를 가로지르는 한 칸으로 그려진다.** 이 KB에서 그 칸을 채우는 것이
    RFC 9110 계열이고, 아래의 [의미론의 정본은 여기가 아니다](#의미론의-정본은-여기가-아니다)가
    그 경계를 적는다.
  - **HTTP/3에서는 TLS가 QUIC 안에 들어가고 스트림 다중화가 HTTP 판이 아니라 QUIC 층으로 내려간다.**
    본문이 "QUIC은 전통적인 OSI 계층의 뜻으로 TLS를 쓰지 않는다"고 적은 것의 그림판이다.

## HOL 블로킹이라는 낱말이 층마다 가리키는 것

- 이 장에서 HOL 블로킹이라는 같은 낱말이 다섯 자리에 나오는데 가리키는 것이 다르다. 저자들이
  자리마다 따로 적은 것을 한데 모은다.

  | 어디의 HOL인가 | 무엇이 무엇을 막는가 | 출처 |
  |---|---|---|
  | TCP | 세그먼트 하나가 유실되면 뒤따르는 세그먼트가 버퍼에 쌓이고 재전송 뒤에야 재조립된다 | 4장, p.122 |
  | HTTP/1.1 파이프라이닝 | 응답이 요청과 같은 순서로 와야 하므로 앞 응답이 늦으면 뒤 응답이 막힌다 | 4장, p.128 |
  | HTTP/2 | 다중화는 되지만 단일 TCP 연결이라 TCP HOL이 그대로 걸리고, 한 스트림의 유실이 다른 스트림까지 막는다 | 4장, p.134 |
  | TLS | 레코드 전체가 있어야 복호화되는데 레코드가 여러 TCP 세그먼트에 걸친다 | 4장, p.140 |
  | QUIC | 스트림이 독립이라 유실된 패킷이 나르던 스트림들로 한정된다. 다만 유실이 몰려 일어나면 이득이 불분명하다 | 4장, p.141 |

- 그림 4-6이 앞의 셋을 한 장에 겹쳐 놓고 저자들이 그 그림을 본문으로 푼다
  (4장, pp.142–143):[^dynowski2025]
  - **HTTP/1.1에서 TCP 세그먼트 하나가 유실되거나 늦으면 보내는 쪽은 뒤 세그먼트를 계속 보내지만
    받는 쪽에서 버퍼에 쌓인다. 그 결과 빠진 세그먼트가 재전송되고 TCP가 스트림을 재조립하기
    전까지는 HTTP 메시지들이 받는 쪽 애플리케이션에 전달되지 못한다. TCP 지속 연결이 스트림
    전체를 대상으로 동작하고 세그먼트마다 순서대로 전달되어야 하기 때문이다.**
  - **HTTP/2는 서로 다른 HTTP 메시지에 속하는 프레임을 단일 TCP 세그먼트 안에서, 그리고 세그먼트들
    사이에서 다중화한다. 그림의 경우 유실·지연된 둘째 TCP 세그먼트가 HTTP 메시지 1과 3의 조각을
    함께 담고 있어서 메시지 2와 4가 버퍼에 쌓인다.**
  - **HTTP/3에서는 각 QUIC 스트림이 독립이므로 HOL 블로킹 문제가 줄어든다. 유실·지연된 QUIC 패킷이
    나르던 프레임이 속한 스트림만 막힌다.**

## 1-RTT와 0-RTT

- 그림 4-7이 재는 것은 **클라이언트가 첫 HTTP 요청을 보내기 전에 서버와 연결을 초기화하는 데
  필요한 왕복 수의 차이**다 (4장, p.143).[^dynowski2025]
- 수치가 셋이다 (4장, p.143).[^dynowski2025]
  - **HTTP/2와 HTTP/1은 둘 다 2 RTT를 요구하고 HTTP/3은 1 RTT를 요구한다.**
  - **재연결(모바일 클라이언트가 와이파이에서 서버와 끊었다가 다시 붙는 것)과 연결 이주(클라이언트가
    와이파이에서 5G로 옮기는 것)는 이상적인 조건에서 0-RTT로 동작할 수 있으며, 이는 HTTP 요청이
    첫 RTT 안에 보내질 수 있다는 뜻이다.**
- 그림이 본문보다 더 말해 주는 것이 하나 있다. **왼쪽 칸에서 2 RTT를 채우는 것은 TCP 핸드셰이크와
  TLS 1.3이고 HTTP/2 요청은 그다음 세 번째 왕복에 놓인다. 오른쪽 칸에서는 QUIC과 TLS 1.3이 한
  왕복에 겹쳐 있고 HTTP/3 요청이 두 번째 왕복에 놓인다** (4장, p.143 그림 4-7).[^dynowski2025]
  아래 패킷 관찰에서 저자들이 "요청이 두 번째 RTT에 일어난다"고 적는 것과 같은 그림이다.

## QUIC 핸드셰이크가 패킷으로 보이는 모양

- 저자들이 curl로 HTTP/3 요청을 보내고, 포획한 패킷을 세션 비밀로 복호화해 읽는다
  (4장 §"QUIC 1-RTT Connection Establishment"(pp.144–147)).[^dynowski2025] 순서에서 읽히는 것을
  옮긴다.
  - **클라이언트가 Initial QUIC 패킷을 보낸다. 그 안의 `CRYPTO` 프레임이 TLS 1.3 Client Hello와
    여러 TLS 확장을 담으며, 확장에는 클라이언트가 h3(HTTP/3) 지원을 서버에 알리는 응용 계층
    프로토콜 협상(ALPN)이 든다. 서버 도메인 이름을 담은 SNI도 있고, QUIC 전송 파라미터도 이 프레임에
    들어 있다. 이 QUIC 패킷은 암호화되지 않는다.**
  - **`PADDING` 프레임이 패킷 크기를 인위적으로 키우는데, 패킷 크기 분석으로 방문한 웹사이트를
    알아맞히는 웹사이트 지문 공격을 막으려는 것이다.**
  - **클라이언트가 목적지 연결 ID(DCID)를 자기가 고른 값으로 두는데, 그 값은 다음 QUIC 패킷에서
    서버가 자기 출발지 연결 ID(SCID)로 준 실제 값으로 덮어써진다.**
  - **패킷 번호(PKN)는 패킷 종류(Initial, Handshake, 1-RTT)마다 따로 늘어나며 보낸 것과 받은 것의
    열이 따로 있다. PKN은 TCP 순서 번호와 역할이 비슷하다.**
  - **서버가 `CRYPTO` 프레임을 담은 Handshake 패킷으로 답한다. 그 안에 TLS 1.3 Server Hello와 서버
    인증서 조각이 들어 있고, 인증서나 ALPN 같은 정보는 암호화된다.** 이 패킷의 시각이 약 0.003초의
    RTT 추정치를 준다.
  - **그다음 패킷부터 1-RTT 패킷 종류의 열이 시작된다. PP는 보호된 적재물(Protected Payload)의
    약자로 QUIC 패킷이 1-RTT 트래픽 비밀로 보호되고 있음을 가리킨다.** `PING` 프레임은 클라이언트의
    생존 표시다.
  - **클라이언트가 스트림 0으로 HTTP 요청을 보내고, 이것은 예상대로 두 번째 RTT에 일어난다.**
  - 서버가 헤더와 바디를 보내고, 클라이언트가 `CC`(CONNECTION_CLOSE) 프레임을 보낸다.
- curl 쪽 출력에서 서버가 알리는 것이 하나 더 있다. **`alt-svc` 헤더로 서버가 앞으로 24시간 동안
  HTTP/3를 지원한다고 알린다** (4장, p.145).[^dynowski2025]

## 저술 시점의 배포 현황

- **2024년에 세 HTTP 판(HTTP/1.1, HTTP/2, HTTP/3)이 모두 웹에서 활발히 쓰이고 있다. 각각이 얼마나
  많은 트래픽을 나르는지는 클라이언트의 종류(데스크톱 브라우저, 모바일 앱, 자동화된 봇)와 상대하는
  서버의 종류에 달려 있다** (4장, p.147).[^dynowski2025]
  - 버전 조건: 2025년 저술 시점, 2024년 실측 보고 기준.
- 수치가 셋이다 (4장, p.147):[^dynowski2025]
  - **브라우저로 접근한 웹사이트의 약 60퍼센트가 HTTP/2를 지원하며, 이 비율은 지난 몇 해 동안
    안정적이되 약간의 감소를 보인다.**
  - **약 30퍼센트의 웹사이트가 HTTP/3를 지원하며 이 지원은 아직 늘고 있다.**
  - **다만 API에 쓰이는 HTTP 판으로 보면 HTTP/1.1이 요청의 약 50퍼센트로 여전히 지배적이고, 이것도
    약간의 감소를 보인다. 그럼에도 어떤 검색이나 소셜 미디어 봇은 HTTP/1.1을 거의 전적으로 쓴다.**
  - 버전 조건: 2025년 저술 시점, 2024년 실측 보고 기준. 세 수치 전부에 걸린다.
- 클라이언트 쪽 지원도 최근이다. **주요 브라우저에서 HTTP/3 지원이 가능해진 것은 2024년 중반부터이고,
  이 장의 시연에 쓰인 데비안 리눅스의 curl도 마찬가지다** (4장, p.147 각주).[^dynowski2025]
  - 버전 조건: 2025년 저술 시점.

## HTTP/3가 웹 API에 주는 것과 뺏는 것

- 저자들이 이 장을 웹 API의 물음으로 닫는다. **왕복 수 감소로 인한 성능 이득은 고지연 망에서, 곧
  네트워크 인프라가 덜 좋은 지역에서 체감될 수 있다** (4장, p.147).[^dynowski2025]
- 그런데 그 이득이 되돌려질 수 있다. **클라이언트가 먼저 HTTP/1.1이나 HTTP/2를 쓰기로 하고, 서버가
  `alt-svc` 헤더로 HTTP/3 지원을 확인해 준 뒤에야 HTTP/3로 갈아타기로 할 수 있다. 그러면 왕복이
  더 붙어 QUIC의 초기 연결 지연 감소 이점이 상쇄된다** (4장, pp.147–148).[^dynowski2025]
- 남는 이점 하나가 압축이다. **HTTP/3의 이점 하나는 헤더 압축이고, 이것이 인터넷 트래픽 크기를
  줄이는 데 도움이 된다** (4장, p.148).[^dynowski2025]
- 비용도 넷이다 (4장, p.148):[^dynowski2025]
  - **QUIC은 현재 기기에 처리 비용을 지운다. UDP가 TCP만큼 최적화되어 있지 않고, 레코드당 연산과
    견주어 패킷당 TLS 연산이 상대적으로 더 잦기 때문이다.**
  - **구글 앱 엔진, 애저 앱 서비스, AWS 엘라스틱 빈스톡 같은 일부 클라우드 애플리케이션 호스팅
    플랫폼에서는 HTTP/3가 기본으로 지원되지 않아, HTTP/3 트래픽을 받으려면 CDN이나 게이트웨이나
    로드 밸런서 같은 프록시를 써야 한다.**
  - **기업은 TLS 1.3을 지원하지 않는 낡은 미들박스에 기대고 있을 수 있고, 지원하더라도 QUIC(과 UDP)
    트래픽을 막을 수 있다.**
  - **중간자 공격 위치에 있는 미들박스는 대신 더 낡은 TLS 1.2를 선호한다. 정적 키를 써서 트래픽을
    더 쉽게 복호화하고 들여다볼 수 있기 때문이다.**
  - 버전 조건: 2025년 저술 시점의 플랫폼 지원 현황이다.
- 그래서 저자들이 내리는 값 판정이 뜻밖의 자리에 있다. **HTTP/3의 주된 직접적 이점은 QUIC을
  인터넷에 배포하는 운반차로 쓰이는 것일 수 있다** (4장, p.148).[^dynowski2025] 그 위에 다른
  프로토콜을 올릴 길이 열렸고, 저자들이 드는 예가 애플의 iCloud Private Relay over QUIC, 마이크로소프트의
  SMB over QUIC, SSH over HTTP/3, WebTransport over HTTP/3다.

## 둘째 소스 — 2022년에 이것을 "지켜볼 것"으로 적은 자리

한 해 앞선 2022년 API 아키텍처 운영서가 마무리 장의 §"Preparing for the Future"에서 HTTP/3를
**아직 절 하나를 통째로 줄 만하지는 않으나 API 아키텍처에 미칠 미래 영향 때문에 지켜볼 만한
주제 셋** 가운데 하나로 든다 (10장 §"HTTP/3", p.234).[^gough2022]

- **그쪽의 서술은 이 페이지의 본문과 어긋나지 않는다** — **HTTP 의미론은 판들에 걸쳐 일관되고
  같은 요청 메서드·상태 코드·메시지 필드가 대체로 모든 판에 적용되며, 차이는 그 의미론을 밑에
  깔린 전송 프로토콜에 어떻게 대응시키는가에 있다**고 적고, **HTTP/1.1과 HTTP/2는 TCP를 전송으로
  쓰고 HTTP/3는 UDP를 쓰는 전송층 네트워크 프로토콜인 QUIC을 쓴다**고 잇는다. **QUIC으로 갈아탄
  것은 HTTP/2의 주요 문제인 "헤드 오브 라인 블로킹"을 고치는 것을 겨냥하고, 그것은 특히 여러
  자원을 불러와야 하는 웹사이트에 영향을 준다** (10장, p.234).[^gough2022] 위
  [HTTP 버전 번호와 의미론의 분리](../concepts/http-version-numbering.md)와
  [다중화해도 HOL 블로킹은 남는다](#다중화해도-hol-블로킹은-남는다)가 같은 것을 더 길게 적는다.
- **그쪽이 더하는 것은 인프라 쪽 대가 한 줄이다** — **HTTP/3는 잠재적으로 큰 속도 이득을
  약속했지만 밑에 깔린 전송 프로토콜이 바뀌었으므로 인그레스 프록시와 다른 네트워킹 구성 요소의
  업그레이드가 필요할 것이다** (10장, p.234).[^gough2022]
  - **이 한 줄이 위 [HTTP/3가 웹 API에 주는 것과 뺏는 것](#http3가-웹-api에-주는-것과-뺏는-것)의
    둘째 비용과 같은 것을 가리킨다** — 그쪽(2025년)은 **일부 클라우드 호스팅 플랫폼이 HTTP/3를
    기본 지원하지 않아 CDN이나 게이트웨이나 로드 밸런서 같은 프록시를 써야 한다**고 적는다.
    **세 해 간격의 두 소스가 같은 자리를 짚는다.** #hypothesis
- **채택 수치는 두 소스가 다르게 적고, 재는 대상이 다르다** (10장, p.234):[^gough2022]
  - 버전 조건: 2022년 저술 시점. **저술 시점에 이미 도는 웹 브라우저의 70퍼센트 이상이 HTTP/3를
    지원한다**는 것이 그쪽의 수치다.
  - **위 [저술 시점의 배포 현황](#저술-시점의-배포-현황)의 2024년 실측은 웹사이트의 약
    30퍼센트가 HTTP/3를 지원한다**고 적는다. **두 수치는 겨루지 않는다** — 하나는 **브라우저
    쪽 지원**이고 하나는 **사이트 쪽 지원**이다. **모순으로 걸지 않는다.**
  - **다만 클라이언트 쪽 수치는 두 소스가 갈린다.** 2025년 소스는 **주요 브라우저에서 HTTP/3
    지원이 가능해진 것은 2024년 중반부터**라고 적는데, 2022년 소스는 이미 **70퍼센트 이상**이라
    적는다. **이 KB는 어느 쪽도 확인할 수 없어 두 진술을 그대로 나란히 둔다** — "지원 가능"과
    "지원함"이 같은 것을 재는지가 불분명하고, 두 소스 모두 측정 출처를 대지 않는다.
    #hypothesis

## 의미론의 정본은 여기가 아니다

- 이 페이지가 담는 것은 **판마다의 선로 위 형식과 전송층 선택과 그 성능 귀결**이다. 메서드와 상태
  코드와 헤더 필드의 뜻은 판이 바뀌어도 같으므로 이 소스의 몫이 아니다.
- 그것을 이 장의 그림 4-5가 스스로 그린다. **HTTP 의미론이 세 판 위를 가로지르는 한 칸으로 놓여
  있다.** 이 KB에서 그 칸을 채우는 것이 RFC 9110 계열이고
  [HTTP 의미론](../synthesis/http-semantics.md) 허브가 모은다.
- 특히 헷갈리기 쉬운 두 자리를 적어 둔다.
  - **여기서 말하는 스트림과 프레임은 HTTP/2·HTTP/3의 전송 형식이지 메시지 의미론이 아니다.** 판과
    무관한 메시지의 추상은
    [HTTP 메시지 추상과 프레이밍](../concepts/http-message-abstraction-and-framing.md)에 있고,
    거기서는 제어 데이터가 HTTP/2 이상에서 의사 헤더 필드로 실린다는 것까지가 규범이다.
  - **여기서 말하는 미들박스는 RFC 9110의 중개자보다 넓은 범주다.** HTTP 통신의 참여자로 행동하는
    중개자의 분류는 [HTTP 중개자](../concepts/http-intermediaries.md)에 있다.
