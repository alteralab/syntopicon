## 어디에 두는가

- 절을 여는 규정 — **가드레일(guardrail)은 위험을 완화하고 당신과 당신의 사용자를 보호하는 데 도움이
  된다. 그것은 위험에 대한 노출이 있는 곳이면 어디든 놓여야 한다. 일반적으로 그것은 입력을 둘러싼
  가드레일과 출력을 둘러싼 가드레일로 분류될 수 있다** (10장, p.451).[^huyen2025]

## 입력 가드레일이 막는 두 위험

- **입력 가드레일은 통상 두 종류의 위험에 대해 보호한다: 외부 API로 사적 정보를 흘리는 것과 당신의
  시스템을 훼손하는 나쁜 프롬프트를 실행하는 것이다** (10장, p.451).[^huyen2025]
- 5장이 맡은 쪽 — **5장은 공격자가 프롬프트 해킹을 통해 애플리케이션을 악용할 수 있는 여러 방식과
  그것에 맞서 애플리케이션을 방어하는 법을 논의한다. 위험을 완화할 수는 있지만, 모델이 응답을 생성하는
  방식의 본질적 성질과 피할 수 없는 사람의 실수 탓에 그것이 완전히 제거될 수는 결코 없다** (10장,
  p.452).[^huyen2025]

## 사적 정보가 새는 세 경로

- **외부 API로 사적 정보를 흘리는 것은 외부 모델 API를 쓰는 데 특유한 위험이다 — 당신의 데이터를
  조직 밖으로 보내야 하기 때문이다. 이는 다음을 포함한 많은 이유로 일어날 수 있다** (10장,
  p.452):[^huyen2025]
  - **직원이 회사의 비밀이나 사용자의 사적 정보를 프롬프트에 복사해 서드파티 API로 보낸다.**
  - **애플리케이션 개발자가 회사의 내부 정책과 데이터를 애플리케이션의 시스템 프롬프트에 넣는다.**
  - **도구가 내부 데이터베이스에서 사적 정보를 가져와 그것을 맥락에 더한다.**
  - 각주가 든 실물 — **한 예는 삼성 직원이 삼성의 독점 정보를 ChatGPT에 넣어 회사의 비밀을 우발적으로
    흘린 경우다** (10장, p.452 각주 1).[^huyen2025]

## 민감 데이터를 탐지하고 가린다

- 완전 봉쇄는 없다 — **서드파티 API를 쓸 때 잠재적 유출을 제거하는 빈틈없는 방법은 없다. 그러나
  가드레일로 그것을 완화할 수 있다. 민감 데이터를 자동으로 탐지하는, 이용 가능한 많은 도구 중 하나를 쓸
  수 있다. 어떤 민감 데이터를 탐지할지는 당신이 정한다** (10장, p.452).[^huyen2025] 흔한 민감 데이터
  범주는 다음과 같다 (10장, p.452):[^huyen2025]
  - **개인 정보(ID 번호, 전화번호, 은행 계좌).**
  - **사람의 얼굴.**
  - **회사의 지식재산이나 특권 정보와 결부된 특정 키워드와 문구.**
- 두 선택지 — **많은 민감 데이터 탐지 도구는 어떤 문자열이 유효한 집 주소를 닮았는지 판정하는 것처럼
  잠재적으로 민감한 정보를 식별하는 데 AI를 쓴다. 질의가 민감한 정보를 담고 있다고 밝혀지면 두 가지
  선택지가 있다: 질의 전체를 막거나 그것에서 민감한 정보를 제거하는 것이다. 예컨대 사용자의 전화번호를
  자리표시 [PHONE NUMBER]로 가릴 수 있다. 생성된 응답이 이 자리표시를 담고 있으면 이 자리표시를 원래
  정보로 사상하는 PII 역방향 사전(reverse dictionary)을 써서 그것을 되돌릴 수 있다** (10장,
  p.452).[^huyen2025]
- 도판이 보인 왕복 — 도판은 같은 질의를 사용자 질의·가려진 질의·모델 응답·되돌린 응답의 네 단계로
  늘어놓고, 그 사이에 가역 PII 사상(Reversible PII map) 표를 둔다. 표는 `[ACCESS_TOKEN]`을
  `"secret_token_that_shouldn't_be_leaked"`에 사상하고, 질의 안의 그 토큰이 가려진 단계에서
  `[ACCESS_TOKEN]`으로 바뀌었다가 마지막 단계에서 되돌아온다 (10장, p.453, Figure
  10-3).[^huyen2025]

## 출력 가드레일의 두 기능

- **모델은 여러 다른 방식으로 실패할 수 있다. 출력 가드레일에는 두 가지 주요 기능이 있다** (10장,
  p.453):[^huyen2025]
  - **출력 실패를 잡는다.**
  - **서로 다른 실패 모드를 다룰 정책을 명세한다.**
- 무엇이 실패인지 먼저 안다 — **당신의 기준에 못 미치는 출력을 잡으려면 실패가 어떻게 생겼는지 이해해야
  한다. 탐지하기 가장 쉬운 실패는 모델이 그러지 말아야 할 때 빈 응답을 돌려주는 것이다** (10장,
  p.453).[^huyen2025]
  - 각주의 단서 — **사용자가 모델에게 빈 응답을 돌려 달라고 요청하는 것도 가능하다** (10장, p.453
    각주 2).[^huyen2025]

## 무엇이 실패인가

- **실패는 애플리케이션마다 다르게 생겼다. 두 주요 범주인 품질과 보안에서 흔한 실패는 다음과 같다.
  품질 실패는 4장에서, 보안 실패는 5장에서 논의된다** (10장, pp.453–454):[^huyen2025]
  - **품질**
    - **기대되는 출력 형식을 따르지 않는 잘못된 형식의 응답. 예컨대 애플리케이션은 JSON을 기대하는데
      모델은 유효하지 않은 JSON을 생성한다.**
    - **모델이 환각한, 사실적으로 일관되지 않은 응답.**
    - **일반적으로 나쁜 응답. 예컨대 모델에게 에세이를 쓰라고 했는데 그 에세이가 그냥 나쁘다.**
  - **보안**
    - **인종차별적 내용·성적 내용·불법 행위를 담은 독성 응답.**
    - **사적이고 민감한 정보를 담은 응답.**
    - **원격 도구 실행과 코드 실행을 촉발하는 응답.**
    - **당신의 회사나 경쟁사를 잘못 특징짓는 브랜드 위험 응답.**
- 반대쪽도 함께 재라 — **5장에서 상기하듯 보안 측정에서는 보안 실패만이 아니라 거짓 거절률도 추적하는
  것이 중요하다. 지나치게 안전해서 정당한 요청조차 막아 사용자 워크로드를 방해하고 사용자 좌절을
  일으키는 시스템도 있을 수 있다** (10장, p.454).[^huyen2025]

## 재시도와 병렬 호출

- 확률성을 이용한다 — **많은 실패는 단순한 재시도 로직으로 완화될 수 있다. AI 모델은 확률적이어서,
  질의를 다시 시도하면 다른 응답을 받을 수 있다는 뜻이다. 예컨대 응답이 비어 있으면 X번 다시 시도하거나
  비어 있지 않은 응답을 받을 때까지 다시 시도하라. 마찬가지로 응답의 형식이 잘못되었으면 응답이 올바르게
  형식화될 때까지 다시 시도하라** (10장, p.454).[^huyen2025]
- 대가와 우회 — **그러나 이 재시도 정책은 추가 지연과 비용을 발생시킬 수 있다. 재시도 하나하나가 또
  한 번의 API 호출을 뜻한다. 재시도가 실패 뒤에 수행되면 사용자가 체감하는 지연은 두 배가 될 것이다.
  지연을 줄이려면 호출을 병렬로 할 수 있다. 예컨대 질의마다 첫 질의가 실패하기를 기다렸다가 다시
  시도하는 대신, 이 질의를 동시에 두 번 모델에 보내 두 응답을 받아 더 나은 쪽을 고른다. 이는 지연을
  관리 가능하게 유지하면서 중복 API 호출의 수를 늘린다** (10장, p.454).[^huyen2025]

## 사람에게 넘긴다

- **까다로운 요청에 대해 사람으로 되돌아가는 것도 흔하다. 예컨대 특정 문구를 담은 질의를 사람 운영자에게
  이관할 수 있다. 어떤 팀은 대화를 언제 사람에게 이관할지 정하는 데 특화된 모델을 쓴다. 예컨대 한 팀은
  자기들의 감정 분석 모델이 사용자 메시지에서 분노를 탐지할 때 대화를 사람 운영자에게 이관한다. 다른
  팀은 사용자가 루프에 갇히는 것을 막으려고 일정 턴 수 뒤에 대화를 이관한다** (10장,
  p.454).[^huyen2025]

## 신뢰성과 지연의 맞바꿈

- **가드레일에는 맞바꿈이 따른다. 하나는 신뢰성 대 지연 맞바꿈(reliability versus latency trade-off)이다.
  가드레일의 중요성을 인정하면서도 어떤 팀은 저자에게 지연이 더 중요하다고 말했다. 그 팀들은 가드레일이
  애플리케이션의 지연을 크게 늘릴 수 있다는 이유로 그것을 구현하지 않기로 결정했다** (10장,
  p.455).[^huyen2025]
  - 각주가 붙인 반응 — **몇몇 초기 독자는 지연을 위해 가드레일을 무시한다는 발상이 자기들에게 악몽을
    안겼다고 저자에게 말했다** (10장, p.455 각주 3).[^huyen2025]

## 스트리밍 모드의 구멍

- **출력 가드레일은 스트림 완성 모드에서 잘 작동하지 않을 수 있다. 기본적으로 응답 전체가 사용자에게
  보여지기 전에 생성되는데 이는 오래 걸릴 수 있다. 스트림 완성 모드에서는 새 토큰이 생성되는 대로
  사용자에게 스트리밍되어 사용자가 응답을 보기까지 기다려야 하는 시간을 줄인다. 단점은 부분 응답을
  평가하기 어려워서, 시스템 가드레일이 그것이 막혀야 한다고 판정하기 전에 안전하지 않은 응답이
  사용자에게 스트리밍될 수 있다는 것이다** (10장, p.455).[^huyen2025]

## 자체 호스팅이냐 서드파티냐

- **얼마나 많은 가드레일을 구현해야 하는지는 모델을 자체 호스팅하는지 서드파티 API를 쓰는지에도 달려
  있다. 둘 다의 위에 가드레일을 구현할 수는 있지만, 서드파티 API는 API 제공자가 통상 많은 가드레일을
  기본으로 제공하므로 당신이 구현해야 할 가드레일을 줄일 수 있다. 동시에 자체 호스팅은 요청을 외부로
  보낼 필요가 없다는 뜻이고, 이는 많은 종류의 입력 가드레일에 대한 필요를 줄인다** (10장,
  p.455).[^huyen2025]

## 어느 수준에 구현되는가

- 모델 제공자 쪽 — **애플리케이션이 실패할 수 있는 자리가 많다는 것을 감안하면 가드레일은 아주 여러
  수준에서 구현될 수 있다. 모델 제공자는 자기 모델을 더 낫고 더 안전하게 만들려고 모델에 가드레일을
  붙인다. 그러나 모델 제공자는 안전성과 유연성의 균형을 잡아야 한다. 제약은 모델을 더 안전하게 만들 수
  있지만 특정 유스케이스에는 덜 쓸모 있게 만들 수도 있다** (10장, p.455).[^huyen2025]
- 애플리케이션 개발자 쪽과 기성품 — **가드레일은 애플리케이션 개발자가 구현할 수도 있다. 많은 기법이
  248쪽 "Defenses Against Prompt Attacks"에서 논의된다. 상자에서 꺼내 바로 쓸 수 있는 가드레일
  솔루션에는 Meta의 Purple Llama, NVIDIA의 NeMo Guardrails, Azure의 PyRIT, Azure의 AI content
  filters, Perspective API, 그리고 OpenAI의 content moderation API가 있다. 입력과 출력의 위험이
  겹치기 때문에 하나의 가드레일 솔루션이 입력과 출력 양쪽에 대한 보호를 제공할 가능성이 높다. 어떤 모델
  게이트웨이는 가드레일 기능도 제공한다** (10장, p.455).[^huyen2025]

## 스코어러를 어디 두는가

- **가드레일이 붙은 아키텍처는 Figure 10-4처럼 생겼다. 저자는 스코어러(scorer)를 모델 API 아래에
  두었는데, 스코어러가 흔히 AI 기반이기 때문이다 — 스코어러가 통상 생성 모델보다 작고 빠르긴 하지만.
  그러나 스코어러는 출력 가드레일 상자 안에 놓일 수도 있다** (10장, p.455).[^huyen2025] 도판은 입력
  가드레일(예: PII 삭제)을 맥락 구성과 모델 API 사이에, 출력 가드레일(안전성·검증, 구조화 출력)을 모델
  API와 사용자 사이에 놓고, 모델 API 상자 안에 Generation과 Scoring을 함께 둔다 (10장, p.456,
  Figure 10-4).[^huyen2025]
