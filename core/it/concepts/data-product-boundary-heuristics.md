## 하나의 질문

**어떤 데이터가 이 데이터 프로덕트에 들어가고 어떤 데이터가 다른 것으로 가는가.**

- **이 물음이 조직 설계의 문제로 제기된다** — **데이터 프로덕트의 경계가 팀의 경계를 직접
  정의한다. 내가 자주 받는 질문 하나가 데이터 프로덕트 경계를 어떻게 식별하는가이다. 어떤
  데이터가 이 데이터 프로덕트에 들어가고 어떤 데이터가 저것에 들어가야 하는가. 데이터 프로덕트에
  올바른 세밀도(granularity)는 무엇인가** (16장, p.321).[^dehghani2022]
- 왜 여기 놓였는지도 밝힌다 — **이 질문들은 중요하며 데이터 프로덕트 팀의 배정과 그들의 장기
  책임을 뒷받침한다. 그래서 나는 그것들을 조직 구조에 대한 설계 결정과 관련해 여기서 답한다**
  (16장, p.321).[^dehghani2022]

## 답이 정확한 과학이 아니라는 단서

- **이 질문들에 대한 답은 정확한 과학이 아니며, 더 중요하게는 조직이 데이터 메시 구현을
  진화시키면서 시간에 따라 바뀔 것이다** (16장, p.321).[^dehghani2022]
- 그래서 내놓는 것의 성격 — **데이터 프로덕트를 뒷받침하는 원칙 일부를 고려하면, 당신이 선택한
  경계가 지금 이 순간에 옳은 것인지 아닌지를 시험하는 **휴리스틱(heuristics)** 집합에 도달할
  것이다** (16장, p.321).[^dehghani2022]
- 무엇에 의존해 바뀌는지가 열거된다 — **좋은 경계가 어떻게 생겼는지는 시간에 따라 바뀔 것이다.
  그것은 당신이 데이터 메시 진화의 어느 단계에 있는지, 많은 수의 데이터 프로덕트를 다룰 운영
  성숙도 수준, 메시의 복잡성, 플랫폼의 가용 능력, 그리고 기반 벤더 제공 기술이 어느 시점에
  부과할 수 있는 단단한 제약에 달려 있다. **지속적 개선과 변화를 계획하고 설계하라. 정적이고
  완벽한 설계를 위해서가 아니라**** (16장, p.321).[^dehghani2022]
  진화 단계는 [데이터 메시의 진화적 채택 단계](../concepts/data-mesh-adoption-phases.md)에 있다.

## ① 기존 비즈니스 도메인과 하위 도메인에서 시작한다

판정 질문 — **데이터 프로덕트가 비즈니스 도메인에 정렬되어 있는가. 아니면 이론적 모델링에 근거해
제조된 데이터 프로덕트인가. 비즈니스 현실과 진실에 부합하는가** (16장, p.321).[^dehghani2022]

- **데이터 프로덕트는 비즈니스-기술 정렬 도메인이 소유하고·소싱하고·소비한다. 이것이 데이터
  메시의 근본적 조직 가정이다. 비즈니스 도메인을 발견하는 것이 데이터 프로덕트의 창출과 소유권을
  이끈다. 그들이 공유하거나 필요로 하는 데이터 프로덕트를 발견하기 위해 비즈니스 도메인을
  식별하는 것에서 시작하라** (16장, p.321).[^dehghani2022]
- 도메인 발견의 부담을 없앤다 — **비즈니스 도메인을 어떻게 식별하느냐고 물을지 모른다. 사실 별로
  할 것이 없다. **그것들은 이미 존재한다.** 그것들은 비즈니스가 자기 자원·책임·결과·지식을
  어떻게 나누는지를 표현한다** (16장, p.321).[^dehghani2022]
- 맞지 않는 경우의 처리 — **데이터 프로덕트가 한 도메인과 딱 맞아떨어지지 않고 여러 도메인의
  집계인 경우가 있다. 그 경우 새 도메인이 확립되거나, 데이터 프로덕트의 수명 주기와 설계에 더
  강한 영향력을 가진 기존 도메인이 그 소유권을 갖는다** (16장, pp.321–322).[^dehghani2022]

## ② 장기 소유권에 적합한가

판정 질문 — **데이터 프로덕트가 장기 소유권에 적합한가. 이 도메인을 소유할 만큼 신경 쓰는
사람이 있는가** (16장, p.322).[^dehghani2022]

- **데이터 프로덕트는 장기 소유권을 가진 오래 서 있는 아티팩트다. 그것은 특정 프로젝트를 위해
  만들어졌다가 원래 프로젝트 개발자에게 잊히는 아티팩트가 아니다. 그것들은 변화하고 새로운 사용에
  따라 시간이 지나며 진화할 것이 기대된다** (16장, p.322).[^dehghani2022]
- **판정이 배타적이다** — **당신이 식별하는 데이터 프로덕트가 그런 수명을 갖지 않는다면 그것은
  데이터 프로덕트가 아니다. 그것은 특정 프로젝트를 위해 지어진 특정 애플리케이션 데이터베이스
  안의 데이터셋일 수 있다** (16장, p.322).[^dehghani2022]

## ③ 독립적 수명 주기를 가져야 한다

판정 질문 — **데이터 프로덕트가 사용 편의와 원자적 무결성을 위한 높은 응집(high cohesion)을
갖는가. 데이터 프로덕트가 서빙하는 모든 데이터가 같은 수명 주기를 갖는가. 아니면 서로 다른
프로세스와 트리거에 따라 각기 독립적으로 바뀌는 여러 데이터셋을 데이터 프로덕트가 엮고 있는가**
(16장, p.322).[^dehghani2022]

- 처방 — **나는 각 데이터 프로덕트가 **같은 수명 주기(생성·갱신·삭제)를 가진 데이터를, 단일하고
  잘 정의된 프로세스에 근거해** 담도록 설계하기를 제안한다. 느슨한 결합과 높은 응집 원칙을 적용해
  어떤 데이터셋이 도메인 데이터 프로덕트에 속하거나 속하지 않아야 하는지를 정의하는 것이 데이터의
  무결성과 사용성을 보장한다** (16장, p.322).[^dehghani2022]
- 사용자 쪽 기준도 붙는다 — **데이터 프로덕트의 사용자는 여러 데이터셋을 결합한 논리적 결정을
  쉽게 이해할 수 있어야 한다. **각 데이터 프로덕트는 독립적으로 가치와 의미를 이끌어야 한다** —
  데이터 사용자가 의미 있는 것을 얻으려 늘 다른 데이터 프로덕트와 조인해야 하지 않고서**
  (16장, p.322).[^dehghani2022]
- 저자가 실제 예에서 **둘 다 허용한다** — listener profiles 집계 데이터 프로덕트는 등록·구독
  변경·청취 행동·위치라는 서로 다른 트리거를 갖지만 **이 트리거들 전부가 하나의 집계 개체인
  listener profiles를 단일 변환 로직으로 바꾼다**. 그러면서도 **물론 이 데이터 프로덕트를
  listener personal information과 listener profiles로 더 쪼개 더 독립적인 수명 주기를 얻는
  것도 괜찮다. 전자는 등록 때문에, 후자는 청취 행동 때문에 바뀐다. 나는 두 모델 모두 받아들일
  만하다고 생각한다. **나는 데이터 수명 주기의 응집을 존중하면서 덜 세밀한 데이터 프로덕트에서
  시작한다**** (16장, p.322).[^dehghani2022]
- 반대로 쪼개야 하는 조건이 명시된다 — **데이터 프로덕트가 서로 다른 수명 주기로 각기 독립적으로
  바뀌는 완전히 다른 두 유형의 데이터를, **두 집합체 루트(aggregate root)** 아래에서 서빙한다면,
  경계는 두 개의 다른 데이터 프로덕트를 만들도록 정제되어야 한다** (16장,
  p.323).[^dehghani2022] 각주가 집합체를 정의한다 — **"집합체(aggregate)는 단일 단위로 다뤄질
  수 있는 도메인 객체의 군집이다. 집합체는 그 구성 객체 중 하나를 집합체 루트로 갖는다"**
  (16장, p.323, 각주 10).[^dehghani2022]
- **병리적 예가 이름째 주어진다** — **병리적 예는 청취자의 플레이리스트·기기·프로필 등을 전부
  하나의 데이터 프로덕트로 서빙하는 **everything we know about listeners**라는 데이터
  프로덕트다. 이 출력 각각이 독립적으로 바뀔 수 있으므로 서로 다른 데이터 프로덕트로 변환되어야
  한다** (16장, p.323).[^dehghani2022]

## ④ 독립적으로 의미 있어야 한다

판정 질문 — **데이터 프로덕트가 독립적으로 의미 있는 데이터를 제공하는가. 데이터 프로덕트
사용자 전부가 그것을 쓰려면 다른 것들과 조인하고 연결해야 하는가** (16장,
p.323).[^dehghani2022]

- **이 휴리스틱이 차원 모델링과 정면으로 갈린다** — **전통적 데이터 웨어하우징은 데이터베이스
  정규화 기법을 써서, 각기 한 개체에 관한 데이터를 담는 많은 서로 다른 차원 테이블을 팩트
  테이블과 조인한다. 이것은 많은 차원에 걸쳐 데이터를 교차 상관하는 매우 유연한 질의 시스템을
  허용한다. **이 고노력 모델링은 시간이 많이 들고 유스케이스의 부분 집합만 감당할 수 있다****
  (16장, p.323).[^dehghani2022]
- 데이터 메시 쪽의 선택 — **메시 위 데이터 프로덕트는 가능한 모든 질의에 최적화된 하나의 완벽한
  모델을 설계하려 하지 않는다. 메시 위 데이터 프로덕트는 **최소 모델링과 최대 재사용성**에
  최적화하며, 필요할 때만 목적 적합한 데이터 프로덕트의 조합이 있다. 따라서 그것들은 독립적으로
  가치 — 의미 있는 데이터 — 를 제공하려 시도한다. **불필요한 조인을 피하려 필요하면 다른 데이터
  프로덕트의 정보를 복제한다.** 이것이 데이터 프로덕트 간 조인을 대체하지는 않지만, 대다수
  시나리오에서 데이터 프로덕트가 독립적으로 유용할 수 있게 보장한다** (16장,
  p.323).[^dehghani2022]
  - 곧 **정규화 대신 의도적 복제**다.
    [정규화와 비정규화](../concepts/normalization-and-denormalization.md)의 축에서 저자는
    비정규화 쪽을 조직적 자율성의 대가로 고른다.
  - 상대편은 [차원 모델링](../concepts/dimensional-modeling.md)·[팩트 테이블](../concepts/fact-table.md)·
    [차원 테이블](../concepts/dimension-table.md)이다.

## ⑤ 사용자 없는 데이터 프로덕트는 존재하지 않는다

판정 질문 — **데이터 프로덕트가 누구에게든 쓰이고 있는가. 어떤 리포트에 데이터를 제공하거나·어떤
ML 모델을 학습시키거나·하류 데이터 프로덕트에 먹이고 있는가. 아니면 언젠가 필요할지 모를 가상의
유스케이스를 위해 만들어졌는가** (16장, p.324).[^dehghani2022]

- 유혹의 진단 — **데이터에 관심 있는 사람들에게는 조직이 언젠가 필요로 할지 모를 데이터 프로덕트를
  미리 결정하려는 유혹이 있다. 아마도 놓칠까 봐 두려운 마음이 그런 데이터 프로덕트의 창출을
  이끌 것이다** (16장, p.324).[^dehghani2022]
- 저자가 **부분적으로 동의한 뒤 기각한다** — **비즈니스의 현실을 디지털로 더 일찍 포착할수록,
  미래 유스케이스가 과거로부터 통찰을 이끌어 낼 기회를 주기 쉬워진다는 데 나는 동의한다. 그러나
  **그런 사전 투자의 비용과, 우리가 실제로 무엇을 포착해야 하는지에 대한 지식의 결여가 그
  이익을 능가하지 못한다**. 그래서 대신 나는 15장에서 도입한 비즈니스 주도 실행 접근을 따라
  유스케이스를 먼저 발견하고 그다음 필요한 데이터 프로덕트를 빠르게 짓기 시작하기를 제안한다**
  (16장, p.324).[^dehghani2022]
- **이것이 15장의 YAGNI 논의와 짝을 이룬다** —
  [데이터 메시 실행 프레임워크](../concepts/data-mesh-execution-framework.md)에서 저자는 소스
  정렬 데이터 프로덕트가 "알려진 유스케이스의 정확한 필요를 넘어서" 데이터를 포착해야 한다고
  했다. 두 서술은 **범위**에서 갈린다 — 이미 존재하는 데이터 프로덕트가 담는 **데이터의 폭**은
  넓히되, 아무도 안 쓰는 **데이터 프로덕트 자체**는 만들지 않는다.

## 골디락스 존

- 세 축의 교집합으로 정의된다 — **데이터 프로덕트 경계의 골디락스 존(Goldilocks zone) — 그
  세밀도, 그것이 서빙하는 데이터, 그것이 실행하는 변환 — 은 **사용 용이성(ease of usability)·
  유지보수 용이성(ease of maintenance)·비즈니스 관련성(business relevance)**의 교차점에 있다**
  (16장, p.323).[^dehghani2022]
- 축마다 위반 신호와 조치가 붙는다 (16장, pp.323–324):[^dehghani2022]
  - 사용 용이성 — **데이터 프로덕트 출력은 그 자체로 사용 가능해야 하고 사용자에게 가치와 의미를
    전달해야 한다. 데이터 프로덕트가 부풀어 있어 독립적으로 바뀔 수 있는 너무 많은 면을
    인코딩하고 있고 왜·어떻게 바뀌는지 이해하기 어렵다면, 더 단순한 데이터 프로덕트로 쪼갤
    때다.**
  - 유지보수 용이성 — **데이터 프로덕트 변환 로직의 복잡도가 그 유지보수성을 저해해서는 안 된다.
    쉽게 이해되고·테스트되고·유지되어야 한다. 데이터 프로덕트의 변환이 **변경 실패 비율이 높은
    복잡한 파이프라인**이 된다면 그 경계를 다시 볼 때다. 아마도 독립적 데이터 프로덕트로 분리할
    때다.**
  - 비즈니스 관련성 — **데이터 프로덕트가 비즈니스의 현실을 닮지 않고 집계와 변환을 거쳐 원래
    비즈니스 맥락에서 멀리 변형되었다면, 그것은 **완벽한 모델링의 땅**으로 표류했을 수 있다. 이
    먼 땅에서는 유지보수 비용이 늘고 데이터 프로덕트를 이해하고 쓰기가 더 어렵다. 복잡한 변환의
    이유를 다시 보고 실세계 맥락으로 되돌릴 때다.**
- 변경 실패 비율이 경계 판정의 신호로 쓰인다는 점이 특징이다 — 같은 지표가
  [데이터 메시의 적합성 함수](../concepts/data-mesh-fitness-functions.md)에도 있다. 지표가
  측정만 하는 것이 아니라 **아키텍처 결정을 촉발한다.**
