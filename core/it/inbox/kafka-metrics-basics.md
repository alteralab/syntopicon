하나의 질문: **카프카의 지표를 어디서 얻고, 그 많은 것 중 무엇을 왜 모으는가.**

- 이 장이 서 있는 자리부터가 문제 서술이다 — **아파치 카프카 애플리케이션에는 측정값이
  너무 많아서 무엇이 볼 만하고 무엇을 제쳐 둘 만한지 헷갈리기 쉽다.** 전체 트래픽 속도 같은
  단순한 지표부터 요청 종류마다의 상세한 시간 지표, 토픽별·파티션별 지표까지 있으며,
  **브로커의 모든 동작을 상세히 들여다보게 해 주지만 동시에 모니터링 시스템 담당자에게
  골칫거리가 될 수도 있다** (13장, p.339).[^shapira2021]
- 그래서 이 장이 하겠다고 선언하는 것은 전수 목록이 아니다 — **항상 지켜볼 가장 중요한
  지표와 그것에 어떻게 대응할지, 그리고 문제를 디버깅할 때 손에 두면 좋은 지표들**이며,
  **가용한 지표의 전수 목록은 아니다. 목록이 자주 바뀌고 다수는 카프카 코어 개발자에게나
  유익하기 때문**이다 (13장, p.339).[^shapira2021]

## 지표는 어디에 있는가

- **카프카가 노출하는 모든 지표는 JMX(Java Management Extensions) 인터페이스로 접근할 수
  있다** (13장, p.339).[^shapira2021]
- 외부 모니터링 시스템에서 쓰는 가장 쉬운 방법은 **그 시스템이 제공하는 수집 에이전트를
  카프카 프로세스에 붙이는 것**이고, 형태는 둘이다 (13장, pp.339–340):[^shapira2021]
  - **시스템에서 별도 프로세스로 돌며 JMX 인터페이스에 접속하는 것** — Nagios XI의
    `check_jmx` 플러그인이나 jmxtrans가 그 예다.
  - **카프카 프로세스 안에서 직접 돌며 HTTP 연결로 지표에 접근하게 해 주는 JMX 에이전트** —
    Jolokia나 MX4J가 그 예다.
- **모니터링 에이전트를 설정하는 방법을 깊이 다루는 것은 이 장의 범위 밖**이고 **선택지가
  너무 많아 전부를 제대로 다룰 수 없다.** 조직에 자바 애플리케이션 모니터링 경험이 없다면
  **서비스형 모니터링(monitoring as a service)을 대신 고려할 만하다** — 에이전트·수집
  지점·저장·그래프·경보를 묶어 파는 회사가 많고 에이전트 구성도 도와준다 (13장,
  p.340).[^shapira2021]
- 브로커의 JMX 포트를 찾는 경로가 정해져 있다 — **모니터링 시스템처럼 브로커의 JMX에 직접
  붙는 애플리케이션의 설정을 돕기 위해, 브로커는 설정된 JMX 포트를 주키퍼에 저장되는 브로커
  정보에 적어 둔다. `/brokers/ids/<ID>` znode가 브로커에 대한 JSON 형식 데이터를 담고 거기에
  호스트명과 `jmx_port` 키가 들어 있다** (13장, p.340).[^shapira2021]
  - #hypothesis KRaft 모드에는 이 znode가 없으므로 경로가 달라진다. 책은 주키퍼 저장만
    서술하고 경계를 밝히지 않는다 — 확인하려면 아파치 카프카 운영 문서가 필요하다. 두 모드가
    무엇을 어디에 두는지는 [주키퍼와 KRaft](../concepts/zookeeper-and-kraft.md)에 있다.
- 원격 JMX를 켜는 것은 별개의 결정이고, 책은 여기에 경고를 붙인다 (13장,
  p.340):[^shapira2021]

  > However, it should be noted that remote JMX is disabled by default in Kafka for security
  > reasons. If you are going to enable it, you must properly configure security for the port.
  > This is because JMX not only allows a view into the state of the application, it also
  > allows code execution. It is highly recommended that you use a JMX metrics agent that is
  > loaded into the application.

## 카프카만 지표를 주는 것이 아니다

- **모든 지표가 카프카 자체에서 오지는 않는다.** 브로커를 모니터링할 때 지표를 얻을 수 있는
  자리는 크게 다섯 범주다 (13장, p.340, 표 13-1):[^shapira2021]

  | 범주 | 무엇 |
  |---|---|
  | Application metrics | 카프카 자체가 JMX 인터페이스로 주는 지표 |
  | Logs | 역시 카프카 자체에서 오는 다른 종류의 모니터링 데이터. 숫자가 아니라 텍스트나 구조화된 데이터라서 처리가 조금 더 필요하다 |
  | Infrastructure metrics | 카프카 앞에 있으면서 여전히 요청 경로 안에 있고 내가 통제하는 시스템에서 오는 지표. 로드 밸런서가 예다 |
  | Synthetic clients | 카프카 배포 바깥에 있는 도구에서 오는 데이터. 클라이언트와 같지만 직접 통제하며 보통은 실제 클라이언트와 같은 일을 하지 않는다. Kafka Monitor 같은 외부 모니터가 여기에 든다 |
  | Client metrics | 클러스터에 접속하는 카프카 클라이언트가 노출하는 지표 |

- 이 목록은 순서가 있다 — **카프카 여정을 멀리 갈수록 이 지표 출처들이 더 중요해지는데,
  목록에서 아래로 갈수록 카프카에 대해 더 객관적인 관점을 주기 때문**이다. **시작할 때는
  브로커의 지표에 의존하는 것으로 충분하지만 나중에는 브로커가 어떻게 동작하는지에 대한 더
  객관적인 시야를 원하게 된다** (13장, p.341).[^shapira2021]
- 객관적 측정의 가치를 보이는 예 — **웹 서버는 잘 돌고 있고 자기가 보고하는 지표는 전부
  정상이라고 말한다. 그런데 웹 서버와 외부 사용자 사이 네트워크에 문제가 있어 아무도 웹 서버에
  닿지 못한다. 네트워크 밖에서 돌며 웹사이트 접근 가능 여부를 확인하는 합성
  클라이언트(synthetic client)라면 이것을 탐지해 경보를 낸다** (13장, p.341).[^shapira2021]
- **인프라 지표는 환경에 따라 달라서 이 장의 논의 범위 밖**이다 (13장,
  p.341).[^shapira2021]

## 경보용인가 디버깅용인가

- **스스로에게 던져야 할 첫 질문은 주 목적이 카프카에 문제가 있을 때 알림을 받는 것인지,
  일어난 문제를 디버깅하는 것인지**다. **보통은 둘 다 조금씩이지만, 어떤 지표가 둘 중 어느
  쪽인지 알면 수집한 뒤 다르게 다룰 수 있다** (13장, p.341).[^shapira2021]
- 경보용 지표의 성질 (13장, p.341):[^shapira2021]
  - **아주 짧은 기간에만 유용하다 — 보통 문제에 대응하는 데 걸리는 시간보다 그리 길지 않고,
    시간 단위나 길어야 일 단위로 잰다.**
  - **소비자는 알려진 문제에 대응하는 자동화이고, 자동화가 아직 없는 경우에는 사람 운영자다.**
  - **더 객관적인 것이 중요하다** — **클라이언트에 영향을 주지 않는 문제는 영향을 주는 문제보다
    훨씬 덜 심각하기 때문**이다.
- 디버깅용 데이터의 성질 (13장, pp.341–342):[^shapira2021]
  - **시간 지평이 더 길다** — **한동안 존재해 온 문제를 진단하거나 더 복잡한 문제를 깊이
    들여다보는 일이 잦기 때문**이며, **수집 후 며칠에서 몇 주까지 남아 있어야 한다.**
  - **보통 더 주관적인 측정값이거나 카프카 애플리케이션 자체에서 나온 데이터다.**
  - **이 데이터를 반드시 모니터링 시스템으로 수집해 넣어야 하는 것은 아니다** — **그 자리에서
    문제를 디버깅하는 데 쓴다면 필요할 때 지표에 접근할 수 있는 것으로 충분**하며,
    **수만 개의 값을 상시 수집해 모니터링 시스템을 압도할 필요가 없다.**
- 세 번째 종류가 따로 있다 — **결국 필요해지는 것이 애플리케이션의 이력 데이터이며, 가장 흔한
  용도는 용량 관리다.** 그래서 **컴퓨트·저장·네트워크를 포함해 쓰인 자원 정보를 담고, 아주 긴
  기간(연 단위)을 보관해야 하며, 지표를 맥락에 놓기 위한 추가 메타데이터(예: 브로커가 클러스터에
  추가되거나 제거된 시점)도 수집해야 할 수 있다** (13장, p.342).[^shapira2021] 그 용량 판단이
  무엇을 계산하는지는
  [카프카 하드웨어와 클러스터 산정](../concepts/kafka-hardware-and-cluster-sizing.md)에 있다.

## 자동화가 보는가 사람이 보는가

- **또 하나 고려할 질문은 지표의 소비자가 누구인가**다 (13장, p.342).[^shapira2021]
  - **자동화가 소비한다면 지표는 아주 구체적이어야 한다. 작은 세부를 각각 서술하는 지표가 많아도
    괜찮다 — 컴퓨터는 많은 데이터를 처리하라고 있는 것이기 때문**이며, **데이터가 구체적일수록
    의미 해석의 여지가 줄어 그것에 작용하는 자동화를 만들기 쉽다.**
  - **사람이 소비한다면 지표를 많이 보여 주는 것은 압도적**이다. **그 측정값에 기반해 경보를
    정의할 때 이 점이 더 중요해진다.**
- 경보를 남발할 때 무너지는 자리에 이름이 있다 — **경보 피로(alert fatigue)** 다. **경보가 너무
  많이 울려 문제가 얼마나 심각한지 알기 어려워지는 상태**를 뜻하며, **지표마다 문턱값을 제대로
  정의하고 최신으로 유지하는 것도 어렵다. 경보가 압도적이거나 자주 틀리면 우리는 경보가
  애플리케이션의 상태를 올바로 서술한다고 믿지 않게 된다** (13장, p.342).[^shapira2021]
- 책이 드는 비유는 자동차다 — **공연비를 맞추려면 컴퓨터는 공기 밀도·연료·배기를 비롯한
  수많은 측정값이 필요하지만 그 측정값들은 운전자에게 압도적이다. 그래서 "Check Engine" 등이
  있다 — 지시등 하나가 문제가 있음을 알리고, 정확히 무엇인지는 따로 더 상세한 정보를 찾아볼
  방법이 있다** (13장, p.342).[^shapira2021] 이 장이 지표를 고르는 기준이 이것이다 — **경보를
  단순하게 유지하도록 가장 넓은 범위를 덮어 주는 지표를 짚는 것**이다 (13장, p.342).

## 상태 검사

- **카프카에서 지표를 어떻게 수집하든, 단순한 상태 검사(health check)로 애플리케이션 프로세스
  전체의 건강도 함께 모니터링할 방법을 반드시 갖춰야 한다.** 방법은 둘이다 (13장,
  p.343):[^shapira2021]
  - **브로커가 살아 있는지 죽었는지 보고하는 외부 프로세스(상태 검사).**
  - **브로커가 지표를 보고하지 않는 것에 경보를 거는 것(stale metrics라고도 부른다).**
- **두 번째 방법도 동작하지만 카프카 브로커의 장애와 모니터링 시스템 자체의 장애를 구분하기
  어렵게 만들 수 있다** (13장, p.343).[^shapira2021]
- 구현의 난이도는 양쪽이 다르다 — **카프카 브로커라면 외부 포트(클라이언트가 브로커에 접속할
  때 쓰는 바로 그 포트)에 접속해 응답하는지 확인하는 것으로 충분하다. 클라이언트
  애플리케이션이라면 더 복잡해서, 프로세스가 돌고 있는지 보는 단순한 확인부터 애플리케이션
  건강을 판정하는 내부 메서드까지 걸쳐 있다** (13장, p.343).[^shapira2021]

## 감시자를 감시하는 자

- 카프카를 모니터링 파이프라인으로 쓰는 조직에는 고유한 함정이 하나 있다 — **많은 조직이
  중앙 모니터링 시스템이 소비할 애플리케이션 지표·시스템 지표·로그를 모으는 데 카프카를 쓴다.
  애플리케이션과 모니터링 시스템을 분리하는 훌륭한 방법이지만 카프카 자체에는 특유의 우려를
  낳는다 — 같은 시스템으로 카프카를 모니터링하면 카프카가 망가졌을 때 그것을 결코 알 수 없을
  가능성이 매우 높다. 모니터링 시스템의 데이터 흐름도 함께 망가지기 때문**이다 (13장,
  p.347).[^shapira2021]
- 해법의 예 (13장, p.347):[^shapira2021]
  - **카프카에 의존하지 않는 별도의 모니터링 시스템을 카프카용으로 쓴다.**
  - **데이터센터가 여럿이면 데이터센터 A의 카프카 클러스터 지표를 데이터센터 B로 생산하고 그
    반대도 하도록 한다.**
- 어떻게 처리하든 지켜야 할 것은 하나다 (13장, p.347):[^shapira2021]

  > However you decide to handle it, make sure that the monitoring and alerting for Kafka
  > does not depend on Kafka working.
