# kb-new

**기본 답은 "만들지 마라"다.** 대부분의 구분 요구는 기존 KB의 디렉터리와 허브로
해소된다. KB를 늘리면 검색 스코프가 갈라지고, 크로스 KB 링크가 생기고, 허브가
이중화된다 — 비용은 나중에 청구되고 되돌리기 어렵다.

**주제 분리는 사유가 아니다.** "머신러닝은 따로", "업무용은 따로"는 전부 기존 KB
안에서 푼다.

## ① 판단 게이트

### KB가 0개면 게이트를 건너뛴다

비교할 기존 KB가 없으므로 심사가 무의미하다. 첫 KB는 바로 만든다 —
여기서 막으면 시스템이 시작되지 않는다.

```
uv run tools/validate.py       # "KB 0개"면 게이트 생략
```

### KB가 있으면 3문을 묻는다

1. **기밀·접근 통제 경계인가?**
2. **별도 동기화/백업 정책이 필요한가?**
3. **`type` 어휘·링크 문법의 분기가 필요한가?**
   (새 주제·새 디렉터리는 사유가 아니다)

**전부 아니오** → KB를 만들지 않는다. 기존 KB 안에서 개념 페이지 + 허브로 해소하는
길을 제시한다. 사용자가 요구했다는 이유로 만들지 않되, 왜 안 만드는지는 설명한다.

**하나라도 예** → 동거 KB가 아니라 **저장소 분리**다. 아래로 간다.

## 저장소 분리 — 비가역

동거 KB로 처리하면 격리 사유가 링크 하나로 무효화된다. 크로스 KB 링크는 비권장일
뿐 금지가 아니고, 백업·동기화 정책도 저장소 단위라 갈라놓을 수 없다.

분리하기 전에 사용자에게 알린다:

- **재병합 절차는 없고 만들지도 않는다.**
- 공유 자산(`schema/`·`tools/`)은 **시점 사본**으로 복사하고 이후 동기화하지 않는다.
  드리프트는 사고가 아니라 의도된 결과다 — 분기가 곧 분리 사유였기 때문이다.
- 스킬은 사용자 레벨 1세트를 그대로 쓴다.
- citekey는 결정적 규칙을 공유하므로 두 저장소에서 같은 키로 수렴한다.

이 저장소에는 아무것도 만들지 않는다. 새 저장소에서 `git init` 후 `tools/kb-new.py`를 돈다.

## ② 기계 단계

이름과 한 줄 설명을 정한다. 이름은 소문자 kebab이고 **qmd 컬렉션 이름이 되므로
전역에서 유일**해야 한다.

```
uv run tools/kb-new.py <이름> --title "<제목>" --description "<한 줄>" --dry-run
uv run tools/kb-new.py <이름> --title "<제목>" --description "<한 줄>"
```

손으로 `mkdir` 하지 않는다. 스크립트가 골격 생성·qmd 컬렉션 등록·라우터 갱신·
사후 validate를 한 묶음으로 한다. 골격의 정본은 `schema/layout.yaml`이다.

거부되는 경우와 뜻:

| 메시지 | 뜻 |
|---|---|
| KB 이름 … | 문자집합 위반. 소문자 kebab, 숫자로 시작 불가 |
| 공유 자산 이름입니다 | 루트 완전 분할이 깨진다. 다른 이름을 쓴다 |
| 비어 있지 않습니다 | 기존 디렉터리를 KB로 승격하지 않는다 |
| 이미 다른 경로를 가리킵니다 | qmd 컬렉션 이름 충돌. 이름을 바꾸거나 기존 컬렉션을 정리한다 |

## ③ 편입

만든 뒤:

```
uv run tools/reindex.py
qmd update && qmd embed        # qmd가 있으면
git add -A && git commit
```

그리고 운영에 편입한다 — 주간 lint·격주 inbox 리뷰의 대상이 되고, 임계 경보는
**KB별로 집계**된다(전역 집계는 방치된 KB를 희석한다).

`<kb>/overview.md`의 `## Hubs`는 비어 있다. 첫 허브는 콘텐츠가 쌓인 뒤
lint의 `hub-candidate` 리포트를 보고 사람이 고른다 — 미리 채우지 않는다.
