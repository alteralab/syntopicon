# 클라이언트/서버와 티어 아키텍처

하나의 질문: **한 체계를 프론트엔드와 백엔드로 가르는 분리는 무엇 때문에 생겨났고, 그 선이
시대마다 어디에 그어졌는가.**

## 단일 아키텍처 — 컴퓨터와 소프트웨어가 하나였을 때

- 출발점 — **태초에 컴퓨터만 있었고 소프트웨어가 그 위에서 돌았다. 둘은 단일한 실체로
  시작했다가, 진화하고 더 정교한 역량의 필요가 커지면서 갈라졌다** (9장 §"Unitary
  Architecture", p.134).[^richards2025]
- 저자들이 드는 갈라짐의 예 둘 (9장, p.134):[^richards2025]
  - **메인프레임 컴퓨터는 단수의 체계로 시작해 점차 데이터를 자기 종류의 체계로 분리해 냈다.**
  - **개인용 컴퓨터(PC)가 처음 상업적으로 개발됐을 때도 초점은 대체로 한 대의 기계였다. PC를
    네트워크로 잇는 것이 흔해지면서 클라이언트/서버 같은 분산 체계가 나타났다.**
- **단일 아키텍처는 남아 있되 좁은 자리에만 남는다** — **임베디드 체계와 그 밖의 고도로 제약된
  환경 밖에 단일 아키텍처는 거의 없다** (9장 §"Client/Server", p.135).[^richards2025]
- 그 이유가 특성으로 적힌다 — **소프트웨어 체계는 시간이 지나며 기능을 더하는 경향이 있고,
  성능과 규모 같은 운영 아키텍처 특성을 유지하려면 관심사를 가르는 일이 필요해진다** (9장,
  p.135).[^richards2025]
  - **분리의 동기가 설계 취향이 아니라 운영 특성이라는 것이 이 대목의 요점이다.** 그 특성들의
    규정은 [아키텍처 특성의 분류와 목록](../concepts/architectural-characteristics-categories.md)에 있다.

## 2티어 — 프론트엔드와 백엔드로 가르기

- **많은 아키텍처 스타일이 체계의 부분들을 효율적으로 가르는 방법을 다루는데, 그중 한 근본
  스타일은 기술 기능을 프론트엔드와 백엔드로 가르는 것이고 그것을 2티어(two-tier) 또는
  클라이언트/서버(client/server) 아키텍처라 부른다** (9장, p.135).[^richards2025]
- 그리고 그 하나가 여럿으로 갈린다 — **시대와 체계의 컴퓨팅 역량에 따라 서로 다른 맛으로
  나온다** (9장, p.135).[^richards2025]

## 세 변종

| 변종 | 클라이언트 쪽 | 서버 쪽 | 무엇이 그것을 가능하게 했는가 |
|---|---|---|---|
| 데스크톱과 데이터베이스 서버 | 윈도우 같은 사용자 인터페이스로 쓴 리치 데스크톱 애플리케이션 | 별도의 데이터베이스 서버 | 표준 네트워크 프로토콜로 접속할 수 있는 독립형 데이터베이스 서버의 등장 |
| 브라우저와 웹 서버 | 웹 브라우저(훨씬 얇은 클라이언트) | 웹 서버, 그 뒤에 다시 데이터베이스 서버 | 웹 개발의 도래 |
| 단일 페이지 자바스크립트 애플리케이션 | 브라우저 안 자바스크립트로 쓴 리치 클라이언트 | 같음 | 웹 응답성과 브라우저의 자바스크립트 구현이 함께 좋아진 것 |

- **데스크톱과 데이터베이스 서버** — 초기 PC 아키텍처는 **표현 로직은 데스크톱에 두고, 양과
  복잡도 둘 다에서 계산이 더 무거운 작업은 더 튼튼한 데이터베이스 서버에서 일어나게** 했다
  (9장 §"Desktop and database server", p.135).[^richards2025]
- **브라우저와 웹 서버** — 책임 분리는 데스크톱 변종과 비슷하되 클라이언트가 훨씬 얇아져
  **방화벽 안팎으로 더 넓은 배포**가 가능해졌다 (9장 §"Browser and web server",
  p.135).[^richards2025]
  - **데이터베이스가 따로 있는데도 2티어로 세는 근거가 적힌다** — **데이터베이스가 웹 서버와
    분리돼 있어도 많은 아키텍트는 여전히 이것을 2티어로 본다. 웹 서버와 데이터베이스 서버가
    운영 센터 안의 한 부류의 기계에서 돌고, 사용자 인터페이스는 사용자의 브라우저에서 돌기
    때문**이다 (9장, p.135).[^richards2025]
  - 곧 **티어를 세는 잣대가 배포 단위의 개수가 아니라 그것이 누구의 기계에서 도는가**다.
    같은 낱말을 층과 가르는 다른 소스의 규정은
    [계층 아키텍처](../concepts/layered-architecture.md) §"층과 티어는 다르다"에 있다.
- **단일 페이지 자바스크립트 애플리케이션** — **원래의 데스크톱 변종을 닮되 리치 클라이언트가
  데스크톱 애플리케이션이 아니라 브라우저 안의 자바스크립트로 쓰인** 계열이다 (9장 §"Single-page
  JavaScript applications", p.135).[^richards2025]
- 저자들이 이 절에서 끌어내는 일반화 — **애플리케이션의 필요와 플랫폼의 역량에 따라, 아키텍처의
  서로 다른 부분을 가르는 층은 언제나 있을 것이다** (9장, p.135).[^richards2025]

## 3티어

- **더 많은 분리의 층을 준 3티어 아키텍처(three-tier architecture)는 1990년대 후반에 인기를
  얻었다** (9장 §"Three-tier", p.136).[^richards2025]
- 계기가 도구다 — **자바와 .NET에서 애플리케이션 서버 같은 도구가 두드러지자 기업들은 자기
  토폴로지에 더 많은 층을 짓기 시작했다** (9장, p.136).[^richards2025]
- 한 체계의 셋이 이렇게 적힌다 (9장, p.136):[^richards2025] **산업용 데이터베이스 서버를 쓰는
  데이터베이스 티어 · 애플리케이션 서버가 관리하는 애플리케이션 티어 · 생성된 HTML과, 역량이
  커지면서 점점 더 자바스크립트로 코딩된 프론트엔드.**
- 그 위에서 도는 배선 — **3티어 아키텍처는 CORBA(Common Object Request Broker Architecture)와
  DCOM(Distributed Component Object Model) 같은 네트워크 수준 프로토콜과 대응해 분산 아키텍처를
  짓는 일을 도왔다** (9장, p.136).[^richards2025]
- **그 배관이 어디로 갔는가**가 이 절의 결론이다 — 2025년 저술 시점에 **개발자가 TCP/IP 같은
  네트워크 프로토콜이 어떻게 도는지 걱정하지 않는 것처럼(그냥 되기 때문에), 대부분의 아키텍트도
  분산 아키텍처에서 이 수준의 배관을 걱정할 필요가 없다. 그 시대 도구가 주던 역량은 메시지 큐
  같은 도구로든 이벤트 주도 아키텍처 같은 아키텍처 패턴으로든 남아 있다** (9장,
  p.136).[^richards2025]
  - 그 이벤트 주도 쪽의 전문은 같은 책 15장이 갖는다 — 이 KB의 자리는
    [이벤트 주도 애플리케이션 구조](../concepts/event-driven-application-structure.md)와
    [메시징 패턴](../synthesis/messaging-patterns.md)이다.

## 사라진 스타일이 언어에 남긴 잔재

**곁글 하나가 이 절 전체의 교훈을 담는다.** 저자들이 드는 것은 3티어가 영원할 것이라 가정하고
언어에 그 가정을 박은 사례다 (9장 곁글 §"Three-Tier Architectures, Language Design, and
Long-Term Implications", p.136).[^richards2025]

- **1990년대에 자바 언어가 설계될 때 3티어 컴퓨팅이 대유행이었고, 앞으로 모든 체계가 3티어
  아키텍처를 가질 것이라고들 가정했다.**
- **당시 C++ 같은 기존 언어의 흔한 골칫거리 하나는 체계 사이에서 객체를 네트워크 너머로 일관되게
  옮기는 일이 얼마나 번거로운가였다. 그래서 자바 설계자들은 그 역량을 직렬화(serialization)라는
  기제로 코어에 넣기로 했다.**
- **모든 자바 객체는 직렬화를 지원할 것을 요구하는 인터페이스를 구현한다. 설계자들은 3티어
  아키텍처가 영원히 있을 것이므로 그것을 언어에 구워 넣으면 큰 편의가 되리라고 생각했다.**
- **물론 그 아키텍처 스타일은 왔다가 갔고 — 그 잔재는 자바에 남아 있다. 사실상 아무도 직렬화를
  쓰지 않는데도 새 자바 기능은 하위 호환성을 위해 직렬화를 지원해야 하고, 그것이 언어 설계자들을
  크게 좌절시킨다.**
- 끌어내는 교훈 두 줄 (9장, p.136):[^richards2025]
  - **설계 결정의 장기적 함의를 이해하는 일은 소프트웨어에서나 다른 공학 분야에서나 늘 우리를
    비켜 갔다.**
  - **단순한 설계를 선호하라는 영구적 조언은 여러 면에서 미래 대비(future-proofing) 전략이다.**
- **이 KB의 다른 소스가 같은 기제를 다른 잣대로 기각한다.** [데이터 인코딩 형식](../concepts/data-encoding-formats.md)은
  언어 내장 직렬화를 언어 종속·보안·버저닝·효율 넷으로 기각하고 자바의 내장 직렬화를 **나쁜
  성능과 부푼 인코딩으로 악명 높다**고 적는다. **겨루지 않고 층이 다르다** — 그쪽은 그것을
  **쓰지 말라**고 하고, 이 곁글은 **왜 지울 수 없는가**를 적는다. 두 서술이 합쳐지면 "쓰이지
  않는데 뗄 수도 없다"가 된다.
