이 페이지의 질문: **스레드 풀은 왜 있어야 하고, 안에서 무엇이 어떻게 도는가.**

저자가 3장을 여는 자리에서 1장의 빚을 갚는다 — 실행자 프레임워크는 본질적으로 스레드 풀의
구현인데, 1장에서는 스레드 풀이 어떻게 도는지, 무엇보다 왜 필요했는지를 제대로 설명하지 않았다는
것이다 (3장, p.91).[^rahman2025] 1장이 실행자를 쓰는 쪽에서 본 자리는
[실행자 프레임워크와 그 한계](../concepts/executor-framework-and-its-limits.md)에 있다.

## 스레드 풀이란 무엇인가

- 이름 그대로다 — 스레드 풀(thread pool)은 애플리케이션이 시작될 때 만들어져 애플리케이션이 도는
  내내 계속 살아 있는 스레드의 무리다. 풀의 종류마다 만드는 전략은 다를 수 있지만, 본질은 일정 수의
  스레드를 준비해 두고 계속 돌린다는 것이다 (3장, p.91).[^rahman2025]
- 나머지 절반이 큐다 — 스레드 풀은 작업을 담아 둘 큐를 갖는다. 스레드가 나는 대로 큐에서 작업을
  집어 실행하고, 하나를 끝내면 다음 것을 집어 큐에 작업이 있는 한 계속 실행한다 (3장,
  p.92).[^rahman2025]
- 양쪽 극단에서의 동작도 정해져 있다 — 쓸 작업이 없으면 새 작업이 올 때까지 기다리고, 모든 스레드가
  각기 다른 작업을 실행하느라 바쁘면 추가 작업은 큐에 놓여 스레드가 날 때까지 거기서 기다린다 (3장,
  p.92).[^rahman2025]

## 왜 필요한가

- 첫째 이유가 죽지 않기다 — 스레드를 만드는 일 자체는 쉽지만 임기응변으로 많이 만드는 것은 문제가
  될 수 있다. 수요가 자라는 대로 계속 만들면 결국 운영 체제가 허용하는 최대 스레드 수에 닿아
  애플리케이션이 죽고, 저자는 이것을 바람직하지 않은 결과라고 적는다 (3장, p.92).[^rahman2025]
  그 상한이 무엇인지는 [스레드의 숨은 비용](../concepts/hidden-costs-of-threads.md)에 있다.
- 그래서 풀이 주는 것이 통제다 — 돌고 있는 애플리케이션에서 만들 수 있는 스레드의 수를 통제하고
  싶은데, 스레드 풀이 그 통제를 준다 (3장, p.92).[^rahman2025]
- 부수 효과가 속도 제한이다 — 동시 작업이 너무 많으면 압도당할 자원에 대해 자연스러운 속도 제한
  (rate limiting)의 수단이 된다. 애플리케이션에 몇 개가 최적인지 정해 시작할 때 그 상한을 세워
  두면, 특히 동시 작업이 대량으로 제출될 때 자원 고갈을 막을 수 있다 (3장, p.92).[^rahman2025]
  가상 스레드 시대에 이 자리가 어떻게 비는지는
  [가상 스레드 시대의 속도 제한](../concepts/rate-limiting-with-virtual-threads.md)에 있다.
- 저자의 예가 웹 애플리케이션이다 — 들어오는 요청마다 새 스레드를 만들면 갑작스러운 요청 폭주가
  애플리케이션을 죽일 수 있다 (3장, p.92).[^rahman2025]

## 통제 말고 얻는 것

- 응답 시간 — 스레드 풀은 새 스레드가 만들어지기를 기다리지 않고 작업이 곧바로 실행되게 해 준다
  (3장, p.92).[^rahman2025]
- 수명 주기의 위임 — 스레드 풀이 스레드의 수명 주기를 관리한다. 그래서 스레드를 손으로 다루는
  복잡함이 최소로 줄고 스레드 누수(thread leak) 같은 오류의 위험이 준다 (3장, p.92).[^rahman2025]
- 시선의 이동 — 게다가 작업을 일의 단위(units of work)로 보는 감각을 주어, 스레드의 나사와 볼트를
  다루는 대신 동시에 실행하고 싶은 업무 로직으로 초점을 옮기게 한다 (3장, p.92).[^rahman2025]

## 직접 만들어 본 최소 구현

- 저자는 여기서 `SimpleThreadPool`이라는 클래스를 처음부터 만들어 스레드 풀의 핵심 개념과 내부
  동작을 보인다 (3장, p.92).[^rahman2025]

  워커의 실행 반복이 풀 전체의 심장이고, 나머지는 그 둘레의 관리 코드다.

  ```java
  class Worker extends Thread {
      @Override
      public void run() {
          while (running) {
              try {
                  Runnable task = queue.take();
                  task.run();
              } catch (InterruptedException e) {
                  Thread.currentThread().interrupt();
              }
          }
      }
  }
  ```

- 워커의 정체가 한 줄이다 — `Worker`는 `SimpleThreadPool`의 내부 클래스라 작업을 `Runnable` 형태로
  담아 둘 큐에 직접 닿을 수 있고, 각각이 공유 큐에서 작업을 끊임없이 꺼내 실행하는 독립적인
  스레드다 (3장, p.93).[^rahman2025]
- 수명 주기의 손잡이가 `running` 플래그다 — 이 플래그는 풀의 필드라서 원할 때 풀을 우아하게 내릴 수
  있다. 큐에 작업이 있고 풀이 돌고 있는 한 이 스레드는 계속 꺼내려 든다 (3장, p.93).[^rahman2025]
- 블로킹 큐를 쓰는 이유도 여기 있다 — 작업이 없으면 스레드가 하나 생길 때까지 기다린다 (3장,
  p.93).[^rahman2025]
- 스레드 그룹이 관리를 쉽게 한다 — 모든 `Worker` 스레드가 하나의 `ThreadGroup` 아래 묶인다. 인터럽트
  신호로 전부 내리고 싶으면 그룹을 인터럽트하면 되고 개별로 할 필요가 없다. 다만 저자는 내부에서는
  실제로 개별 인터럽트가 일어난다고 덧붙인다 (3장, p.93).[^rahman2025]
- 겉으로 드러난 메서드가 둘이다 — `submit()`과 `shutdown()`. `AutoCloseable`을 구현해
  try-with-resources 패턴으로 쓸 수 있게 했고, 그래서 `close()`도 있다 (3장,
  p.95).[^rahman2025]
- `close()`가 하는 일이 우아한 종료다 — 종료를 시작하기 전에 큐가 빌 때까지 잠시 기다려, 밀린 작업이
  진행되도록 보장한다 (3장, p.95).[^rahman2025]

## 설계 결정 여섯 자리

저자가 이 구현에서 드러나는 중요한 설계 결정으로 여섯을 짚는다 (3장, pp.94–95).[^rahman2025]

- `volatile` 키워드가 모든 스레드에게 `running` 플래그의 변경을 즉시 보이게 해, 워커가 종료 신호를
  놓치는 일을 막는다. 왜 `volatile`이 필요한지의 기제는
  [자바 메모리 모델과 동시성](../synthesis/java-memory-model-and-concurrency.md) 쪽이 갖는다.
- `LinkedBlockingDeque`가 작업 제출과 회수에 스레드 안전한 연산을 준다. 그리고 그 유계 용량이
  작업이 한없이 쌓여 메모리가 고갈되는 것을 막는다.
- 워커는 생성 즉시 시작되어, 작업이 제출되는 대로 처리할 준비가 되어 있다.
- `put()` 메서드는 큐가 가득 차면 막힌다. 풀이 감당하지 못할 때 자연스러운 배압(backpressure)이
  되는 자리다.
- 스레드 그룹을 인터럽트하면 모든 워커에게 동시에 신호가 가서, 조율된 종료를 촉발한다.
- 우아한 종료가 밀린 작업이 끝나기를 기다려, 풀을 닫는 동안 일이 손실되지 않게 한다.

## 이것이 단순화라는 것

- 저자가 스스로 범위를 긋는다 — 이 예제는 기본 개념을 이해하려고 아주 단순하게 만든 것이고, 실제
  애플리케이션에서는 더 튼튼하고 기능이 풍부한 스레드 풀 구현인 `ExecutorService`를 쓰는 것이
  보통이다 (3장, p.96).[^rahman2025]
- 실제 풀이 더 하는 일의 예가 하나 제시된다 — 어떤 스레드 풀은 최소와 최대 스레드 수를 갖는다.
  평소에는 최소 수만 살아 있고 필요하면 최대까지 늘릴 수 있다는 뜻이다 (3장,
  p.96).[^rahman2025] 그 손잡이의 실물은
  [ThreadPoolExecutor 설정과 풀 크기](../concepts/thread-pool-executor-configuration.md)에 있다.
