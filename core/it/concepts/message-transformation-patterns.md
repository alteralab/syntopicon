하나의 질문: **애플리케이션마다 다른 데이터 형식의 차이를 통합 해법의 어느 자리에서 흡수하는가.**

[메시징의 여섯 뿌리 패턴](messaging-root-patterns.md)에서 *Message Translator*(85)가 정의되고 나면
이 장은 그 하나가 갈라지는 방식의 목록이다. 저자들이 장의 자리를 이렇게 잡는다 — ***Message
Translator*(85)에 서술했듯 메시징 시스템으로 통합돼야 하는 애플리케이션들이 공통 데이터 형식에
합의하는 일은 드물다. (…) 기존 애플리케이션을 통합하는 것은 흔히 애플리케이션이 다른 시스템과
더 쉽게 작동하도록 애플리케이션을 수정할 자유가 없다는 뜻이다. 오히려 통합 해법이 서로 다른
시스템 사이의 차이를 수용하고 해소해야 한다** (8장, p.327).[^hohpe2004]

## 형식 차이는 애초에 왜 남는가

- 여섯 패턴의 역할이 서두에서 한 문단으로 배열된다 — **대부분의 메시징 시스템은 메시지 헤더의
  형식과 내용에 구체적 요구를 부과한다. 우리는 메시지 페이로드 데이터를 메시징 인프라의 요구에
  부합하는 *Envelope Wrapper*(330)로 감싼다. 메시지가 서로 다른 메시징 인프라를 건너 전달되면
  여러 *Envelope Wrapper*(330)가 결합될 수 있다. *Content Enricher*(336)는 대상 시스템이 발신
  시스템이 공급할 수 없는 데이터 필드를 요구할 때 필요하다. (…) *Content Filter*(342)는 그 반대를
  한다 — 메시지에서 원치 않는 데이터를 제거한다. *Claim Check*(346)도 메시지에서 데이터를
  제거하지만 나중의 회수를 위해 저장한다. *Normalizer*(352)는 여러 다른 형식으로 도착하는 메시지를
  공통 형식으로 번역한다** (8장, p.327).[^hohpe2004]
- **채널만으로는 결합이 사라지지 않는다** — ***Message Channel*(60)과 *Message Router*(78)는 한
  애플리케이션이 다른 애플리케이션의 위치를 알아야 할 필요를 없앰으로써 애플리케이션 사이의 기본
  의존을 제거할 수 있다. 한 애플리케이션은 *Message Channel*(60)로 메시지를 보내고 어떤
  애플리케이션이 그것을 소비할지 걱정하지 않을 수 있다. 그러나 메시지 형식은 또 다른 의존의 집합을
  부과한다. 한 애플리케이션이 다른 애플리케이션의 데이터 형식으로 메시지를 형식화해야 한다면
  *Message Channel*(60) 형태의 결합 해소는 어느 정도 환상이다. 수신 애플리케이션의 어떤 변경이나
  한 수신 애플리케이션에서 다른 것으로의 전환도 여전히 발신 애플리케이션의 변경을 요구한다**
  (8장, p.328).[^hohpe2004]

## 메타데이터는 나란히 흐르는 두 번째 시스템이다

- 메타데이터가 무엇인지가 실물로 정의된다 — **한 형식에서 다른 형식으로 메시지를 변환하는 것은
  메타데이터, 곧 실제 데이터의 형식을 서술하는 데이터를 다룰 것을 요구한다. 한 애플리케이션에서
  다른 애플리케이션으로 가는 메시지가 ID 123인 고객이 캘리포니아 샌프란시스코에서 노스캐롤라이나
  롤리로 이사했다고 알려 준다면, 연관된 메타데이터는 이 Address Change 메시지가 수치 고객 ID
  필드를 쓰고 고객의 이름과 성을 각각 최대 40자의 두 텍스트 필드에 저장한다고 알려 줄 수 있다**
  (8장, p.328).[^hohpe2004]
- **그래서 통합 해법이 두 개의 병렬 시스템이 된다** — **메타데이터는 통합에서 아주 중요한 역할을
  하므로 우리는 대부분의 통합 해법을 두 개의 병렬 시스템 사이의 상호작용으로 볼 수 있다. 하나는
  실제 메시지 데이터를 다루고 다른 하나는 메타데이터를 다룬다. 메시지 데이터의 흐름을 설계하는 데
  쓰이는 패턴 다수가 메타데이터의 흐름을 관리하는 데도 쓰일 수 있다. 예컨대 *Channel
  Adapter*(127)는 메시지를 시스템 안팎으로 옮길 수 있을 뿐 아니라 외부 애플리케이션에서 메타데이터를
  추출해 중앙 메타데이터 저장소에 적재할 수도 있다. 이 저장소를 써서 통합 개발자는 애플리케이션
  메타데이터와 *Canonical Data Model*(355) 사이의 변환을 정의할 수 있다** (8장,
  p.328).[^hohpe2004]
- 변환의 설정 자체가 쉬워진다 — **변환을 만드는 것은 *Channel Adapter*(127)가 메타데이터도 추출할
  수 있으면 훨씬 단순해진다. 이 메타데이터는 저장소에 적재되어 *Message Translator*(85)의 설정과
  검증을 크게 단순화할 수 있다. 메타데이터는 다양한 형식으로 저장될 수 있다. XML 메시지에 쓰이는
  흔한 형식은 XSD — eXtensible Schema Definition이다** (8장, p.329).[^hohpe2004]

## 메시징 밖에도 같은 문제가 있다

- 원리가 메시징 전용이 아님이 명시된다 — **이 변환 패턴에 담긴 원리 다수는 메시지 기반 통합 밖에도
  적용 가능하다. 예컨대 *File Transfer*(43)는 시스템 사이에서 변환 기능을 수행해야 한다. 마찬가지로
  *Remote Procedure Invocation*(50)은 애플리케이션의 내부 형식이 다르더라도 호출될 서비스가 지정한
  데이터 형식으로 요청을 해야 한다. 이는 전형적으로 호출하는 애플리케이션이 데이터 변환을 수행할
  것을 요구한다** (8장, p.329).[^hohpe2004] 네 통합 스타일은
  [애플리케이션 통합의 네 가지 스타일](../concepts/application-integration-styles.md)에 있다.
- **ETL이 여기서 대비된다** — **가장 정교한 변환 엔진 일부는 Informatica나 DataMirror 같은
  ETL(extract, transform, load) 도구에 통합돼 있다. 이 도구들은 전형적으로 개별 메시지를 변환하는
  대신 큰 데이터 집합을 한 번에 변환한다** (8장, p.329).[^hohpe2004]
- 이 장이 다루지 않는 것도 명시된다 — **이 장은 기본 *Message Translator*(85) 패턴의 변형에 초점을
  둔다. 개체 사이의 구조적 변환의 세부(예컨대 한 모델은 고객과 주소 사이의 다대다 관계를 지원하고
  다른 모델은 고객 레코드에 주소 필드를 포함할 때 두 데이터 모델 사이를 어떻게 변환하는가)로는
  들어가지 않는다** (8장, p.329).[^hohpe2004]

## Envelope Wrapper — 인프라 규약에 맞는 봉투에 싼다

- 문제 — **메시지 헤더 필드나 암호화 같은 구체적 요구를 메시지 형식에 부과하는 메시징 교환에 기존
  시스템이 어떻게 참여할 수 있는가?** (8장, p.330).[^hohpe2004]
- 양쪽이 서로를 무효로 본다 — **대부분의 메시징 시스템은 메시지 데이터를 헤더와 바디로 나눈다.
  헤더는 메시징 인프라가 메시지의 흐름을 관리하는 데 쓰는 필드를 담는다. 그러나 통합 해법에
  참여하는 대부분의 엔드포인트 시스템은 일반적으로 이 추가 데이터 요소를 알지 못한다. 어떤 경우
  시스템은 이 필드가 자기가 쓰는 메시지 형식과 맞지 않으므로 오류라고 여길 수도 있다. 반대로
  애플리케이션 사이에서 메시지를 라우팅하는 메시징 컴포넌트는 헤더 필드를 요구할 수 있고 적절한
  헤더 필드를 담지 않은 메시지를 무효로 여길 것이다** (8장, p.330).[^hohpe2004]
- 보안이 대표적 실물이다 — **메시징 시스템이 독자적 보안 스킴을 쓴다고 하자. 유효한 메시지는 다른
  메시징 컴포넌트에 의해 처리되도록 수락되기 위해 보안 자격 증명을 담아야 할 것이다. 그런 스킴은
  인가되지 않은 사용자가 시스템에 메시지를 밀어 넣는 것을 막는 데 유용하다. 게다가 메시지 내용이
  인가되지 않은 청취자의 도청을 막기 위해 암호화될 수 있다 — pub-sub 기제에서 특히 중요한 이슈다.
  그러나 메시징 시스템을 통해 통합되는 기존 애플리케이션은 사용자 정체나 메시지 암호화의 개념을
  알지 못할 가능성이 높다. 결과적으로 "원시(raw)" 메시지가 메시징 시스템의 규칙에 부합하는
  메시지로 번역돼야 한다** (8장, p.330).[^hohpe2004]
- 인프라가 여럿일 때도 같은 문제다 — **어떤 대기업은 하나 이상의 메시징 인프라를 쓴다. 따라서
  메시지가 *Messaging Bridge*(133)를 써서 메시징 시스템을 건너 라우팅돼야 할 수 있다. 각 메시징
  시스템은 메시지 바디와 헤더의 형식에 다른 요구를 가질 가능성이 높다** (8장,
  p.330).[^hohpe2004]
- **터널링이 여기서 이름을 얻는다** — **이 시나리오는 기존 TCP/IP 기반 네트워크 프로토콜을 보고
  배울 수 있는 또 다른 경우다. 많은 경우 다른 시스템으로의 연결성이 Telnet이나 Secure
  Shell(`ssh`) 같은 특정 프로토콜로 제한된다. 다른 프로토콜(예컨대 FTP)을 쓴 통신을 가능케 하려면
  그 프로토콜 형식이 지원되는 프로토콜에 부합하는 패킷으로 캡슐화돼야 한다. 반대편 끝에서 패킷
  페이로드가 추출될 수 있다. 이 과정을 *터널링(tunneling)* 이라 한다** (8장,
  p.330).[^hohpe2004]
- **캡슐화가 데이터를 안 보이게 만드는 문제** — **한 메시지 형식이 다른 것 안에 캡슐화되면 시스템은
  데이터 페이로드 안의 정보에 대한 접근을 잃을 수 있다. 대부분의 메시징 시스템은 컴포넌트(예컨대
  *Message Router*[78])가 정의된 메시지 헤더의 일부인 데이터 필드에만 접근하게 허용한다. 한 메시지가
  다른 메시지 안의 데이터 필드로 포장되면 컴포넌트는 원본 메시지의 필드를 라우팅이나 변환 기능
  수행에 쓰지 못할 수 있다. 그러므로 어떤 데이터 필드는 원본 메시지에서 새 메시지 형식의 메시지
  헤더로 승격돼야 할 수 있다** (8장, p.331).[^hohpe2004]
- 해법 — ***Envelope Wrapper*를 써서 애플리케이션 데이터를 메시징 인프라에 부합하는 봉투 안에
  싸라. 메시지가 목적지에 도착하면 풀어라** (8장, p.331).[^hohpe2004]

### 싸고 푸는 다섯 단계

저자들이 과정을 다섯 단계로 나눈다 (8장, p.331).[^hohpe2004]

- **① 메시지 소스가 원시 형식으로 메시지를 발행한다. 이 형식은 전형적으로 애플리케이션의 성격이
  정하며 메시징 인프라의 요구에 부합하지 않는다.**
- **② 래퍼가 원시 메시지를 받아 메시징 시스템에 부합하는 메시지 형식으로 변환한다. 여기에는 메시지
  헤더 필드 추가, 메시지 암호화, 보안 자격 증명 추가 등이 포함될 수 있다.**
- **③ 메시징 시스템이 부합하는 메시지를 전송한다.**
- **④ 결과 메시지가 언래퍼에 전달된다. 언래퍼는 래퍼가 가한 어떤 수정이든 되돌린다. 여기에는
  헤더 필드 제거, 메시지 복호화, 보안 자격 증명 검증이 포함될 수 있다.**
- **⑤ 메시지 수신자가 "평문(clear text)" 메시지를 받는다.**

- 우편 봉투의 유비가 정확히 어디까지 가는지 적힌다 — **봉투는 전형적으로 메시지 헤더와 메시지
  바디(페이로드)를 둘 다 싼다. 헤더는 우편 봉투의 바깥에 있는 정보라고 생각할 수 있다: 그것은
  메시징 시스템이 메시지를 라우팅하고 추적하는 데 쓰인다. 봉투의 내용물은 페이로드 또는 바디다 —
  메시징 인프라는 메시지가 목적지에 도착할 때까지 (일정한 한계 안에서) 그것에 별로 신경 쓰지
  않는다** (8장, pp.331–332).[^hohpe2004]

### 승격과 터널링

- **래퍼는 Content Enricher의 성질을 조금 갖는다** — **래퍼가 원시 메시지에 정보를 더하는 것은
  전형적이다. 예컨대 내부 메모가 우편 시스템으로 보내지기 전에 우편번호를 조회해야 한다. 그런
  의미에서 래퍼는 *Content Enricher*(336)의 어떤 측면을 통합한다. 그러나 래퍼는 실제 정보
  내용을 강화하지 않고, 메시지의 라우팅·추적·처리에 필요한 정보를 더한다** (8장,
  p.332).[^hohpe2004]
- 그 정보의 출처가 셋으로 갈린다 — **이 정보는 즉석에서 만들어질 수도 있고(예: 고유 메시지 ID
  생성이나 타임스탬프 추가), 인프라에서 추출될 수도 있고(예: 보안 맥락의 회수), 데이터가 원래
  메시지 바디에 담겨 있다가 래퍼에 의해 메시지 헤더로 갈라질 수도 있다(예: 원시 메시지에 담긴
  키 필드). 이 마지막 선택지는 때로 *승격(promotion)* 이라 불린다 — 특정 필드가 바디 안에 숨어
  있던 상태에서 헤더에 두드러지게 보이는 상태로 "승격"되기 때문이다** (8장,
  p.332).[^hohpe2004]
- 래퍼는 사슬을 이룬다 — **여러 래퍼와 언래퍼가 사슬을 이루는 일이 잦으며 계층 프로토콜 모델을
  활용한다. 이는 메시지의 페이로드가 새 봉투를 담고, 그 봉투가 다시 헤더와 페이로드 절을 싸는
  상황으로 귀결된다** (8장, p.332).[^hohpe2004]
- 예제가 개념을 말한 대목 — **중개자 사슬은 신뢰 경계를 건널 때 아주 흔하다. 우리는 모든 메시지를
  인코딩하고 다른 메시지 안에 싸서 어떤 중개자도 메시지 내용이나 헤더를 보지 못하게 할 수 있다
  (예컨대 메시지의 주소가 기밀일 수 있다). 그러면 수신자가 메시지를 풀고 페이로드를 디코딩해
  인코딩되지 않은 메시지를 신뢰 환경으로 통과시킨다** (8장, p.333).[^hohpe2004] 그리고 TCP/IP가
  같은 구조의 실물이다 — **애플리케이션 데이터가 먼저 TCP 봉투에 싸이고, 그것이 IP 봉투에 싸이고,
  그것이 이더넷 봉투에 싸인다. 네트워크가 스트림 지향적이므로 봉투는 데이터 스트림의 시작과 끝을
  표시하는 헤더와 트레일러 둘 다로 구성될 수 있다** (8장, p.333).[^hohpe2004]

## Content Enricher — 빠진 것을 밖에서 가져온다

- 문제 — **메시지 발신자가 요구되는 데이터 항목을 전부 갖고 있지 않다면 다른 시스템과 어떻게
  통신하는가?** (8장, p.336).[^hohpe2004]
- **Message Translator와 갈리는 지점이 명확히 그어진다** — **이 문제는 *Message Translator*(85)의
  특수한 경우이므로 같은 고려 일부가 적용된다. 그러나 이 문제는 *Message Translator*(85)에 서술된
  기본 예와 약간 다르다. *Message Translator*(85)의 서술은 수신 애플리케이션이 필요로 하는
  데이터가 형식은 틀렸을지언정 이미 들어오는 메시지에 담겨 있다고 가정했다. 이 새로운 경우에는
  필드를 재배열하는 단순한 문제가 아니다. 우리는 실제로 메시지에 추가 정보를 주입해야 한다**
  (8장, p.336).[^hohpe2004]
- 실물 — 병원 일정 시스템이 진료 완료를 알리는데 회계 시스템은 **환자의 전체 이름·보험사·주민번호를
  요구한다. 그러나 일정 시스템은 이 정보를 저장하지 않는다. 그것은 고객 관리 시스템에 담겨 있다**
  (8장, p.337).[^hohpe2004]

### 기각된 네 대안

- **선택지 A — 일정 시스템이 추가 정보를 저장하도록 고친다.** **이 접근은 두 가지 중대한 단점이
  있다. 첫째, 일정 시스템의 내부 구조 수정을 요구한다. 대부분의 경우 일정 시스템은 패키지
  애플리케이션이고 이런 유형의 수정을 허용하지 않을 수 있다. 둘째, 일정 시스템이 커스터마이즈
  가능하더라도 우리가 **다른 시스템의 구체적 필요에 기반해** 그 시스템을 바꾸고 있다는 것을 고려해야
  한다. 예컨대 방문을 확인하는 편지를 환자에게 보내고 싶어지면 고객의 우편 주소를 수용하기 위해
  일정 시스템을 또 바꿔야 할 것이다** (8장, p.337).[^hohpe2004]
- **선택지 B — 일정 시스템이 보내기 직전에 고객 관리 시스템에 요청한다.** **이는 첫째 문제를
  푼다. (…) 그러나 둘째 문제가 남는다: 일정 시스템은 회계 시스템에 알리기 위해 주민번호와 보험사
  정보가 요구된다는 것을 알아야 한다. 따라서 메시지의 의미가 Doctor Visit보다 Notify Insurance에
  더 가까워진다. 느슨하게 결합된 시스템에서 우리는 한 시스템이 다음 시스템에게 무엇을 하라고
  지시하는 것을 원하지 않는다. 우리는 대신 *Event Message*(151)를 보내고 다른 시스템들이 무엇을
  할지 정하게 한다. 게다가 이 해법은 일정 시스템을 고객 관리 시스템에 더 단단히 결합시킨다 —
  일정 시스템이 이제 없는 데이터를 어디서 가져올지 알아야 하기 때문이다. 이는 일정 시스템을
  회계 시스템과 고객 관리 시스템 양쪽에 묶는다. 이런 유형의 결합은 취약한 통합 해법으로 이어지므로
  바람직하지 않다** (8장, p.338).[^hohpe2004]
- **선택지 C — 메시지를 고객 관리 시스템에 먼저 보낸다.** **이는 일정 시스템을 메시지의 후속
  흐름에서 잘 떼어 낸다. 그러나 이제 우리는 환자가 의사를 방문한 뒤 보험사가 청구서를 받는다는
  업무 규칙을 고객 관리 시스템 안에 구현하게 된다. 이는 고객 관리 시스템 안의 로직을 수정할 것을
  요구한다. 고객 관리 시스템이 패키지 애플리케이션이면 이 수정은 어렵거나 불가능할 수 있다.
  수정할 수 있더라도 이제 고객 관리 시스템을 청구 메시지 발송에 간접적으로 책임지게 만든다. (…)
  그러나 어떤 필드가 다른 시스템에서 회수돼야 한다면 우리는 시작한 곳과 비슷한 상황에 있게
  된다** (8장, p.338).[^hohpe2004]
- **선택지 D — 회계 시스템이 고객 ID만 받고 스스로 회수하게 고친다.** **이 접근은 두 가지 단점이
  있다. 첫째, 이제 회계 시스템을 고객 관리 시스템에 결합시킨다. 둘째, 이 선택지는 다시 우리가
  회계 시스템에 대한 통제를 갖는다고 전제한다. 대부분의 경우 회계 시스템은 커스터마이즈 선택지가
  제한된 패키지 애플리케이션이다** (8장, p.338).[^hohpe2004]
- 해법 — **특화된 변환기인 *Content Enricher*를 써서 외부 데이터 소스에 접근해 없는 정보로 메시지를
  증강하라** (8장, p.338).[^hohpe2004]
- 정의 — ***Content Enricher*는 들어오는 메시지 안의 정보(예: 키 필드)를 써서 외부 소스에서
  데이터를 회수한다. *Content Enricher*가 필요한 데이터를 자원에서 회수한 뒤 그 데이터를 메시지에
  덧붙인다. 들어오는 메시지의 원래 정보는 결과 메시지로 넘어갈 수도 있고 수신 애플리케이션의
  구체적 필요에 따라 더 이상 필요 없을 수도 있다** (8장, p.339).[^hohpe2004]

### 정보의 출처 세 가지

- **① 계산(Computation)** — ***Content Enricher*가 없는 정보를 계산할 수 있다. 이 경우 알고리즘이
  추가 정보를 통합한다. (…) 이 형태의 *Content Enricher*는 외부 데이터 소스가 필요 없으므로 기본
  *Message Translator*(85)와 아주 비슷하다** (8장, p.339).[^hohpe2004]
- **② 환경(Environment)** — ***Content Enricher*가 운영 환경에서 추가 데이터를 회수할 수 있다.
  가장 흔한 예는 타임스탬프다. 예컨대 수신 시스템이 각 메시지에 타임스탬프를 나르도록 요구할 수
  있다. 발신 시스템이 이 필드를 포함하지 않으면 *Content Enricher*가 운영체제에서 현재 시각을
  가져와 메시지에 더할 수 있다** (8장, p.339).[^hohpe2004]
- **③ 다른 시스템(Another System)** — **이 선택지가 가장 흔하다. *Content Enricher*는 다른
  시스템에서 없는 데이터를 회수해야 한다. 이 데이터 자원은 데이터베이스·파일·LDAP 디렉터리·
  애플리케이션, 또는 없는 데이터를 수동으로 입력하는 사용자를 포함해 여러 형태를 취할 수 있다**
  (8장, p.339).[^hohpe2004]
- **여기서는 느슨한 결합이 목표가 아니다** — ***Content Enricher*와 데이터 소스 사이의 상호작용은
  정의상 동기적이므로(*Content Enricher*는 데이터 소스가 요청된 데이터를 반환할 때까지 강화된
  메시지를 보낼 수 없다) 동기 프로토콜(예: HTTP나 데이터베이스로의 ODBC 연결)이 비동기 메시징을
  쓰는 것보다 나은 성능을 낼 수 있다. *Content Enricher*와 데이터 소스는 본질적으로 단단히
  결합돼 있으므로 *Message Channel*(60)을 통해 느슨한 결합을 달성하는 것은 그만큼 중요하지
  않다** (8장, p.340).[^hohpe2004]

### 참조로 보내고 나중에 복원한다

- **참조를 쓰는 것이 맞교환임이 명시된다** — ***Content Enricher*는 메시지에 담긴 참조를 해소하는
  데 여러 경우에 쓰인다. 메시지를 작고 관리하기 쉽게 유지하기 위해 우리는 흔히 모든 데이터
  요소를 가진 완전한 객체를 넘기는 대신 객체에 대한 단순한 참조를 넘기기로 고른다. 이 참조는
  보통 키나 고유 ID의 형태를 취한다. (…) 명백한 맞교환이 얼마간 있다. 참조를 쓰는 것은 원본
  메시지의 데이터 양을 줄이지만 자원에서의 추가 조회를 요구한다** (8장,
  pp.340–341).[^hohpe2004]
- 무엇이 균형을 결정하는가 — **참조의 사용이 성능을 개선하는지는 얼마나 많은 컴포넌트가 참조만으로
  단순히 작동할 수 있는가 대 얼마나 많은 컴포넌트가 원본 메시지 내용 일부를 복원하기 위해
  *Content Enricher*를 써야 하는가에 의존한다. 예컨대 메시지가 최종 수신자에 도달하기 전에 긴
  중개자 목록을 통과하면 객체 참조를 쓰는 것이 메시지 트래픽을 크게 줄일 수 있다. 우리는 최종
  수신자 직전의 마지막 단계로 *Content Enricher*를 삽입해 없는 정보를 메시지에 적재할 수 있다.
  메시지가 도중에 나르고 싶지 않은 데이터를 이미 담고 있다면 *Claim Check*(346)를 써서 데이터를
  저장하고 그것에 대한 참조를 얻을 수 있다** (8장, p.341).[^hohpe2004]
- **Enricher와 Filter가 짝으로 쓰인다** — **외부 당사자와 통신할 때 *Content Enricher*가 흔히
  쓰인다 — 그들이 특정 메시지 표준(예: ebXML)에 부합하는 메시지를 요구하기 때문이다. 이 표준 대부분은
  긴 데이터 목록을 가진 큰 메시지를 요구한다. 우리는 보통 내부 메시지를 가능한 한 단순하게 유지한
  다음 조직 밖으로 메시지를 보낼 때마다 *Content Enricher*를 써서 없는 필드를 더함으로써 내부
  운영을 크게 단순화할 수 있다. 마찬가지로 *Content Filter*(342)를 써서 들어오는 메시지에서
  불필요한 정보를 벗겨 낼 수 있다** (8장, p.341).[^hohpe2004]

## Content Filter — 덜어 내는 것도 값을 올린다

- 문제 — **몇 개의 데이터 항목에만 관심이 있을 때 큰 메시지를 다루는 것을 어떻게 단순화하는가?**
  (8장, p.342).[^hohpe2004]
- **첫째 이유는 보안이다** — **왜 메시지에서 값진 데이터 요소를 제거하고 싶겠는가? 흔한 이유 하나는
  보안이다. 서비스에서 데이터를 요청하는 애플리케이션은 응답 메시지가 담은 모든 데이터 요소를 볼
  권한이 없을 수 있다. 서비스 제공자는 보안 스킴을 알지 못하고 사용자 정체와 무관하게 항상 모든
  데이터 요소를 반환할 수 있다. 우리는 요청자의 입증된 정체에 기반해 민감한 데이터를 제거하는
  단계를 더해야 한다. 예컨대 급여 시스템은 직원에 대한 모든 데이터를 반환하는 단순한 인터페이스만
  노출할 수 있다. 이 데이터는 급여 정보·주민번호·기타 민감 정보를 포함할 수 있다. 직원의 입사일을
  반환하는 서비스를 만들려 한다면 결과 메시지에서 모든 민감 정보를 제거한 다음 요청자에게
  돌려주고 싶을 것이다** (8장, p.342).[^hohpe2004]
- **둘째 이유는 위원회 설계의 거대 문서다** — **여러 표준 단체와 위원회가 특정 산업과 애플리케이션에
  대한 표준 XML 데이터 형식을 정의한다. 잘 알려진 예는 RosettaNet·ebXML·ACORD 등 많다. 이 XML
  형식은 합의된 표준에 기반해 외부 당사자와 상호작용하는 데 유용하지만, "위원회 설계" 접근은
  보통 아주 큰 문서로 귀결된다. 문서 다수가 여러 중첩 수준으로 구성된 수백 개의 필드를 갖는다.
  그렇게 큰 문서는 내부 메시지 교환에 쓰기 어렵다. 예컨대 대부분의 시각(드래그 앤 드롭 스타일)
  변환 도구는 매핑될 문서가 수백 개 요소를 가지면 쓸 수 없게 된다. 또 디버깅이 큰 악몽이 된다**
  (8장, p.342).[^hohpe2004]
- **덜어 내는 것이 강화라는 진술** — **어떤 의미에서 요소를 제거하는 것은 그런 메시지의 유용성을
  *강화한다* — 중복되고 무관한 필드가 제거되어 더 의미 있는 메시지와 개발자 실수의 여지가 더 적은
  상태를 남기기 때문이다** (8장, p.343).[^hohpe2004]
- 해법 — ***Content Filter*를 써서 메시지에서 중요하지 않은 데이터 항목을 제거하고 중요한 항목만
  남겨라** (8장, p.343).[^hohpe2004]

### 계층을 평탄화한다

- 둘째 용법이 구조에 관한 것이다 — ***Content Filter*가 반드시 데이터 요소를 제거하기만 하는 것은
  아니다. *Content Filter*는 메시지의 구조를 단순화하는 데도 유용하다. 흔히 메시지는 트리 구조로
  표현된다. 외부 시스템이나 패키지 애플리케이션에서 나오는 많은 메시지는 일반적이고 정규화된
  데이터베이스 구조를 본떠 모델링됐기 때문에 여러 수준의 중첩된 반복 그룹을 담는다. 알려진 제약과
  가정이 이 수준의 중첩을 불필요하게 만드는 일이 잦고, *Content Filter*를 써서 계층을 다른
  시스템이 더 쉽게 이해하고 처리할 수 있는 단순한 요소 목록으로 "평탄화(flatten)"할 수 있다**
  (8장, p.343).[^hohpe2004]
- **정적 Splitter와의 등가가 여기서 다시 확인된다** — **여러 *Content Filter*를 *정적
  Splitter*(*Splitter*[259] 참조)로 써서 하나의 복잡한 메시지를 각각 큰 메시지의 특정 측면을 다루는
  개별 메시지로 쪼갤 수 있다** (8장, p.343).[^hohpe2004]
- 예제가 개념을 말한 대목 — 데이터베이스 어댑터가 발행하는 메시지의 형태와 그 대안. **물리
  데이터베이스 스키마가 관련 개체를 외래 키와 관계 테이블로 연결된 별도 테이블에 저장하는 것이
  바람직하다. (…) 많은 상용 데이터베이스 어댑터는 이 관련 테이블들을 메시지 수신자에게 관련 없을
  수 있는 기본 키·외래 키 같은 추가 필드를 담을 수 있는 계층적 메시지 구조로 번역한다** (8장,
  p.344).[^hohpe2004] 대안도 명시된다 — ***Content Filter*가 이 특정 문제의 유일한 해법은 아니다.
  예컨대 데이터베이스에 테이블 관계를 해소하고 단순한 결과 집합을 반환하는 뷰를 설정할 수 있다.
  데이터베이스에 뷰를 더할 능력이 있다면 단순한 선택일 수 있다. 많은 상황에서 기업 통합은 가능한
  한 침습적이지 않기를 목표로 하고 그 지침에는 데이터베이스에 뷰를 더하지 않는 것이 포함될 수
  있다** (8장, p.345).[^hohpe2004]

## Claim Check — 맡기고 키만 들려 보낸다

- 문제 — **정보 내용을 희생하지 않고 시스템을 건너 보내지는 메시지의 데이터 양을 어떻게 줄일 수
  있는가?** (8장, p.346).[^hohpe2004]
- *Content Filter*와의 차이 — **필드를 일시적으로만 제거하고 싶을 수 있다. 예컨대 메시지가 메시지
  흐름의 나중에 필요하지만 모든 중간 처리 단계에는 필요하지 않은 데이터 항목 집합을 담을 수 있다.
  이 정보 전부를 각 처리 단계마다 나르고 싶지 않다 — 성능 저하를 일으킬 수 있고, 여분의 데이터를
  너무 많이 나르므로 디버깅을 더 어렵게 만들기 때문이다** (8장, p.346).[^hohpe2004]
- 왜 메시지로 나르는 것이 비싼가 — **메시지로 큰 양의 데이터를 옮기는 것은 비효율적일 수 있다.
  어떤 메시징 시스템은 메시지 크기에 하드 리밋을 갖기도 한다. 다른 메시징 시스템은 데이터의 XML
  표현을 쓰는데 이는 메시지 크기를 한 자릿수 이상 키울 수 있다. 그러므로 메시징이 정보를 전송하는
  가장 신뢰할 만하고 반응적인 방법을 제공하더라도 가장 효율적이지는 않을 수 있다** (8장,
  p.346).[^hohpe2004]
- **작게 유지하면 숨은 가정이 줄어든다** — **또한 메시지에 더 적은 데이터를 나르는 것은 중간 시스템이
  자기를 위한 것이 아닌 정보에 의존하는 것을 막는다. 예컨대 일련의 중개자를 통해 한 시스템에서
  다른 시스템으로 주소 정보를 보내면 중개자들이 주소 데이터에 대해 가정을 세우기 시작해 메시지
  데이터 형식에 의존하게 될 수 있다. 메시지를 가능한 한 작게 만드는 것은 그런 숨은 가정을 들여올
  가능성을 줄인다** (8장, p.346).[^hohpe2004]
- 해법 — **메시지 데이터를 영속 저장소에 저장하고 후속 컴포넌트에 *Claim Check*를 넘겨라. 이
  컴포넌트들은 *Claim Check*를 써서 저장된 정보를 회수할 수 있다** (8장,
  p.347).[^hohpe2004]
- 다섯 단계 (8장, p.347):[^hohpe2004]
  - **① 데이터가 든 메시지가 도착한다.**
  - **② Check Luggage 컴포넌트가 그 정보에 대한 고유 키를 생성한다. 이 키가 나중에 *Claim
    Check*로 쓰인다.**
  - **③ Check Luggage 컴포넌트가 메시지에서 데이터를 추출해 파일이나 데이터베이스 같은 영속
    저장소에 저장한다. 저장된 데이터를 키와 연관시킨다.**
  - **④ 메시지에서 영속화된 데이터를 제거하고 *Claim Check*를 더한다.**
  - **⑤ 다른 컴포넌트가 *Content Enricher*(336)를 써서 *Claim Check*에 기반해 데이터를 회수할 수
    있다.**
- 은유 — **이 과정은 공항의 수하물 위탁과 유비적이다. 짐을 전부 들고 다니고 싶지 않으면 항공사
  카운터에 맡기면 된다. 그 대가로 맡긴 각 짐을 고유하게 식별하는 참조 번호가 적힌 스티커를 표에
  받는다. 최종 목적지에 도착하면 짐을 되찾을 수 있다** (8장, p.347).[^hohpe2004]
- **데이터가 결국 옮겨진다면 무엇을 얻었는가**가 자문자답된다 — **그림이 보여 주듯 원본 메시지에
  담겼던 데이터는 여전히 궁극적 목적지로 "옮겨져야" 한다. 그러면 우리가 얻은 것이 있는가? 있다 —
  메시징을 통해 데이터를 전송하는 것이 중앙 데이터스토어에 저장하는 것보다 덜 효율적일 수 있기
  때문이다. 예컨대 메시지가 큰 양의 데이터를 요구하지 않는 여러 라우팅 단계를 거칠 수 있다.
  메시징 시스템을 쓰면 메시지 데이터가 매 단계에서 마샬링·언마샬링되고 아마 암호화·복호화될
  것이다. 이런 유형의 연산은 CPU를 아주 많이 쓸 수 있고, 어떤 중간 단계도 필요로 하지 않고 최종
  목적지만 필요로 하는 데이터에는 완전히 불필요할 것이다** (8장,
  pp.347–348).[^hohpe2004]
- 완전히 국소적으로 쓸 수도 있다 — ***Claim Check*는 메시지가 여러 컴포넌트를 거쳐 발신자에게
  돌아오는 시나리오에서도 잘 작동한다. 이 경우 Check Luggage 컴포넌트와 *Content Enricher*(336)가
  같은 컴포넌트에 국소적이고 데이터는 네트워크를 건널 필요가 전혀 없다** (8장,
  p.348).[^hohpe2004]

### 키를 무엇으로 할 것인가

- 세 후보가 있다 — **① 고객 ID 같은 업무 키(business key)가 이미 메시지 바디에 담겨 있을 수 있다.
  ② 메시지가 데이터스토어의 데이터를 메시지와 연관시키는 데 쓸 수 있는 메시지 ID를 담을 수 있다.
  ③ 고유 ID를 생성할 수 있다** (8장, p.348).[^hohpe2004]
- 업무 키는 추상화 여부가 판단점이다 — **기존 업무 키를 재사용하는 것이 가장 쉬운 선택으로 보인다.
  (…) 이 키를 다른 컴포넌트에 넘길 때 우리는 그 컴포넌트들이 그 키가 그냥 추상 키가 아니라 고객
  ID임을 알기를 원하는지 정해야 한다. 키를 추상 키로 표현하는 것은 모든 키를 같은 방식으로 처리할
  수 있고 추상 키에 기반해 데이터스토어에서 데이터를 회수하는 일반적 기제를 만들 수 있다는 이점이
  있다** (8장, p.349).[^hohpe2004]
- **메시지 ID는 일반적으로 나쁜 선택이다** — **메시지 ID를 키로 쓰는 것은 편리해 보이지만 일반적으로
  좋은 생각이 아니다. 메시지 ID를 데이터 회수용 키로 쓰는 것은 단일 데이터 요소에 이중 의미가
  붙는 결과를 낳고 충돌을 일으킬 수 있다. 예컨대 *Claim Check* 참조를 다른 메시지로 넘겨야 한다고
  하자. 새 메시지는 새 고유 ID를 배정받을 것이므로 더 이상 그 새 ID로 데이터스토어에서 데이터를
  회수할 수 없다. 메시지 ID의 사용은 데이터가 단일 메시지의 범위 안에서만 접근 가능하기를 원하는
  상황에서만 의미가 있을 수 있다. 그러므로 일반적으로 키를 담을 새 요소를 배정하고 이 나쁜 형태의
  "요소 재사용"을 피하는 것이 낫다** (8장, p.349).[^hohpe2004]

### 맡긴 것을 언제 지우는가

- 세 정책이 제시된다 — **데이터가 데이터스토어에 일시적으로만 저장될 수 있다. 안 쓰는 데이터를
  어떻게 제거하는가? ① 데이터스토어에서 데이터 회수의 의미를 수정해 읽힐 때 데이터를 삭제하게 할
  수 있다. 이 경우 데이터를 한 번만 회수할 수 있는데, 이는 보안상의 이유로 어떤 경우에는 실제로
  바람직할 수 있다. 그러나 여러 컴포넌트가 같은 데이터에 접근하는 것을 허용하지 않는다. ② 대안으로
  데이터에 만료일을 붙이고 특정 나이를 넘은 모든 데이터를 주기적으로 제거하는 가비지 컬렉션
  프로세스를 정의할 수 있다. ③ 셋째 선택지로 어떤 데이터도 제거하고 싶지 않을 수 있다. 데이터스토어로
  업무 시스템(예: 회계 시스템)을 쓰고 있고 그 시스템의 모든 데이터를 유지해야 하기 때문일 수
  있다** (8장, p.349).[^hohpe2004]
- 데이터스토어의 형태는 열려 있다 — **데이터스토어의 구현은 다양한 형태를 취할 수 있다. 데이터베이스가
  명백한 선택이지만 XML 파일 집합이나 인메모리 메시지 저장소도 데이터스토어로 복무할 수 있다. 때로
  애플리케이션을 데이터스토어로 쓸 수도 있다. **데이터스토어가 통합 해법의 다른 부분에 있는
  컴포넌트에서 도달 가능해서 그 부분들이 원본 메시지를 재구성할 수 있는 것이 중요하다**** (8장,
  p.349).[^hohpe2004]

### Claim Check로 정보를 감춘다

- 원래 의도와 다른 쓰임 — **원래 *Claim Check*의 의도는 큰 양의 데이터를 돌려 보내는 것을 피하는
  것이지만 다른 목적에도 복무할 수 있다. 우리는 흔히 외부 당사자에게 메시지를 보내기 전에 민감한
  데이터를 제거하고 싶다. 이는 외부 당사자가 알 필요가 있는 것만 받는다는 뜻이다. 예컨대 직원
  데이터를 외부 당사자에게 보낼 때 직원을 어떤 마법의 고유 ID로 참조하고 주민번호 같은 필드를
  제거하는 편을 선호할 수 있다. 외부 당사자가 요구되는 처리를 완료한 뒤 데이터스토어의 데이터와
  외부 당사자가 반환한 메시지를 병합해 완전한 메시지를 재구성한다** (8장,
  pp.349–350).[^hohpe2004]
- **키가 접근 통제 수단이 된다** — **이 메시지들에 특별한 고유 키를 생성해 외부 당사자가 자기가
  가진 키로 취할 수 있는 행동을 제한할 수도 있다. 이는 외부 당사자가 우리 시스템에 악의적으로
  메시지를 밀어 넣는 것을 막을 것이다. 무효한(또는 만료됐거나 이미 쓰인) 키를 담은 메시지는 그
  나쁜 키로 메시지 데이터를 회수하려 할 때 *Content Enricher*(336)에 의해 차단될 것이다** (8장,
  p.350).[^hohpe2004] 같은 문제의 데이터 파이프라인 판이
  [개인 데이터 제거 패턴](../concepts/personal-data-removal-patterns.md)과
  [데이터 암호화와 익명화 패턴](../concepts/data-encryption-and-anonymization-patterns.md)에 있다.
- **Process Manager가 Claim Check가 된다** — **하나 이상의 외부 당사자와 상호작용하면 *Process
  Manager*(312)가 *Claim Check*의 기능을 제공할 수 있다. *Process Manager*(312)는 메시지가 도착할
  때 프로세스 인스턴스(때로 태스크나 잡이라 불린다)를 만든다. *Process Manager*(312)는 각 개별
  프로세스 인스턴스에 추가 데이터가 연관되는 것을 허용한다. 사실상 프로세스 엔진이 이제 우리
  메시지 데이터를 저장하는 데이터스토어 역할을 한다. 이는 *Process Manager*(312)가 외부 당사자에게
  그 당사자와 관련된 데이터만 담은 메시지를 보내게 해 준다. (…) *Process Manager*(312)가 외부
  당사자에게서 응답 메시지를 받으면 새 데이터를 프로세스 인스턴스가 이미 저장한 데이터와 병합한다**
  (8장, pp.350–351).[^hohpe2004]

## Normalizer — 형식이 다른 동등 메시지를 모은다

- 문제 — **의미적으로 동등하지만 다른 형식으로 도착하는 메시지를 어떻게 처리하는가?** (8장,
  p.352).[^hohpe2004]
- **통일 형식을 강제하는 안이 언제 통하는가** — **기술적 관점에서 가장 쉬운 해법은 모든 참여자에게
  통일된 형식을 지시하는 것으로 보일 수 있다. 사업이 대기업이고 B2B 교환이나 공급 채널을 통제한다면
  이것이 통할 수 있다. 예컨대 General Motors가 공통 메시지 형식으로 공급자로부터 주문 상태 갱신을
  받고 싶다면 Joe's Supplier 사업이 GM의 지침에 부합할 가능성이 높다고 꽤 확신할 수 있다. 그러나
  다른 많은 상황에서 사업은 그런 사치를 누리지 못할 것이다. 오히려 많은 사업 모델이 메시지 수신자를
  정보의 "집계자(aggregator)"로 위치시키고, 개별 참여자와의 합의 일부는 그들의 시스템 인프라에
  최소한의 변경만 요구된다는 것이다. 결과적으로 집계자는 EDI 레코드나 쉼표 구분 파일부터 XML
  문서나 이메일로 도착하는 Excel 스프레드시트에 이르는 어떤 데이터 형식으로 도착하는 정보든 기꺼이
  처리하게 된다** (8장, p.352).[^hohpe2004]
- **변화율이 더 중요한 고려다** — **다수의 파트너를 다룰 때 중요한 고려 하나는 변화율(rate of
  change)이다. 각 참여자가 처음부터 다른 데이터 형식을 선호할 수 있을 뿐 아니라 선호 형식이 시간이
  지나며 바뀔 수도 있다. 게다가 새 참여자가 합류하고 다른 이는 빠질 수 있다. 특정 파트너가 몇 년에
  한 번만 데이터 형식을 바꾸더라도 수십 개 파트너를 다루면 빠르게 월간 또는 주간 변경으로 귀결될
  수 있다. 시스템 전체에 걸친 변경의 "파급 효과(ripple effect)"를 피하기 위해 이 변경들을 처리의
  나머지에서 가능한 한 격리하는 것이 중요하다** (8장, p.352).[^hohpe2004]
- 채널로만 푸는 안의 대가 — **가장 쉬운 방법은 메시지 타입마다 하나씩 *Datatype Channel*(111)의
  모음을 쓰는 것이다. 각 *Datatype Channel*(111)이 다른 *Message Translator*(85)에 연결된다. 이
  접근의 단점은 많은 수의 메시지 형식이 똑같이 많은 수의 *Message Channel*(60)로 번역된다는
  것이다** (8장, p.353).[^hohpe2004]
- 해법 — ***Normalizer*를 써서 각 메시지 타입을 커스텀 *Message Translator*를 거쳐 라우팅해 결과
  메시지가 공통 형식에 맞게 하라** (8장, p.353).[^hohpe2004]
- 구조 — ***Normalizer*는 메시지 형식마다 하나의 *Message Translator*(85)를 특징으로 하고 들어오는
  메시지를 *Message Router*(78)를 통해 올바른 *Message Translator*(85)로 라우팅한다** (8장,
  p.353).[^hohpe2004]

### 형식을 어떻게 알아내는가

- 전제가 무엇인지 먼저 밝힌다 — **메시지를 올바른 *Message Translator*(85)로 라우팅하는 것은
  *Message Router*(78)가 들어오는 메시지의 타입을 탐지할 수 있다고 전제한다. 많은 메시징 시스템이
  이런 유형의 태스크를 단순하게 만들기 위해 각 메시지에 메시지 헤더의 타입 지정자 필드를 붙인다.
  그러나 많은 B2B 시나리오에서 메시지는 기업의 내부 메시징 시스템에 부합하는 메시지로 도착하지
  않고 쉼표 구분 파일이나 연관 스키마 없는 XML 문서 같은 다양한 형식으로 도착한다. 어떤 들어오는
  데이터 형식에든 타입 지정자를 붙이는 것이 확실히 모범 사례이지만, 세상이 완벽과는 거리가 멀다는
  것을 우리는 너무 잘 안다** (8장, pp.353–354).[^hohpe2004]
- 그래서 세 가지 실용적 단서가 제시된다 (8장, p.354):[^hohpe2004]
  - **스키마 없는 XML 문서의 흔한 한 방법은 루트 요소의 이름을 써서 올바른 타입을 가정하는 것이다.
    여러 데이터 형식이 같은 루트 요소를 쓰면 XPath 표현식으로 특정 하위 노드의 존재를 판별할 수
    있다.**
  - **쉼표 구분 파일은 창의성이 조금 더 필요할 수 있다. 때로 필드의 개수와 데이터의 타입(예: 수치
    대 문자열)에 기반해 타입을 정할 수 있다.**
  - **데이터가 파일로 도착하면 가장 쉬운 방법은 파일명이나 폴더 구조를 대리 *Datatype
    Channel*(111)로 쓰는 것일 수 있다. 각 사업 파트너가 고유한 명명 규칙으로 파일 이름을 지을 수
    있다. 그러면 *Message Router*(78)가 파일명을 써서 메시지를 적절한 *Message Translator*(85)로
    라우팅할 수 있다.**
- 라우터를 두는 것이 재사용도 낳는다 — ***Message Router*(78)의 사용은 같은 변환이 여러 사업
  파트너에 쓰이는 것도 가능케 한다. 여러 사업 파트너가 같은 형식을 쓰거나 변환이 여러 메시지
  형식을 수용할 만큼 일반적이면 유용할 수 있다. 예컨대 XPath 표현식은 문서 형식이 달라도 XML
  문서에서 요소를 골라내는 데 훌륭하다** (8장, p.354).[^hohpe2004]

## Canonical Data Model — 번역기 수를 제곱에서 선형으로

- 문제 — **다른 데이터 형식을 쓰는 애플리케이션들을 통합할 때 의존을 어떻게 최소화하는가?** (8장,
  p.355).[^hohpe2004]
- 왜 형식이 제각각인가 — **독립적으로 개발된 애플리케이션들은 다른 데이터 형식을 쓰는 경향이 있다 —
  각 형식이 오직 그 애플리케이션만 염두에 두고 설계됐기 때문이다. 애플리케이션이 어떤 알려지지
  않은 애플리케이션에 메시지를 보내거나 받도록 설계될 때 그 애플리케이션은 자연스럽게 자기에게
  가장 편리한 메시지 형식을 쓸 것이다** (8장, p.355).[^hohpe2004]
- 짝마다 번역기를 두면 — ***Message Translator*(85)는 애플리케이션을 바꾸거나 애플리케이션들이
  서로의 데이터 형식을 알게 하지 않고 메시지 형식의 차이를 해소한다. 그러나 많은 수의 애플리케이션이
  서로 통신하면 통신하는 애플리케이션 쌍마다 하나의 *Message Translator*(85)가 필요할 수 있다.
  (…) 요구되는 *Message Translator*(85)의 수는 통합되는 애플리케이션 수에 따라 지수적으로 늘어나
  빠르게 관리 불가능해진다** (8장, pp.355–356).[^hohpe2004]
- **간접이 남아 있는 곳** — ***Message Translator*(85)가 통신하는 두 애플리케이션이 쓰는 메시지
  형식 사이에 간접을 제공하지만, 그것은 여전히 어느 쪽 애플리케이션이든 그가 쓰는 메시지 형식에
  의존한다. 결과적으로 한 애플리케이션의 데이터 형식이 바뀌면 바뀌는 애플리케이션과 그것이 통신하는
  모든 다른 애플리케이션 사이의 모든 *Message Translator*(85)가 바뀌어야 한다. 마찬가지로 새
  애플리케이션이 해법에 추가되면 메시지를 교환하기 위해 기존 각 애플리케이션에서 새 애플리케이션으로
  가는 새 *Message Translator*(85)가 만들어져야 한다** (8장, p.356).[^hohpe2004]
- 지연도 대가다 — **메시지 흐름에 주입되는 각 추가 변환 단계가 지연을 늘리고 메시지 처리량을 줄일
  수 있다는 것도 염두에 두어야 한다** (8장, p.356).[^hohpe2004]
- 해법 — **어떤 특정 애플리케이션에도 독립적인 *Canonical Data Model*을 설계하라. 각 애플리케이션이
  이 공통 형식으로 메시지를 생산하고 소비하도록 요구하라** (8장, p.356).[^hohpe2004]
- **이득이 수치로 제시된다** — **애플리케이션이 소수만 통합 해법에 참여하면 *Canonical Data Model*의
  사용이 지나치게 복잡해 보일 수 있다. 그러나 애플리케이션 수가 늘면서 해법은 빠르게 값을 한다.
  각 애플리케이션이 다른 모든 애플리케이션에 메시지를 보내고 받는다고 가정하면, 두 애플리케이션으로
  된 해법은 애플리케이션의 데이터 형식 사이를 직접 번역하면 *Message Translator*(85)가 둘만
  필요한 반면 *Canonical Data Model*은 넷을 요구한다. 세 애플리케이션으로 된 해법은 어느 접근으로도
  여섯 개의 *Message Translator*(85)를 요구한다. 그러나 여섯 애플리케이션으로 된 해법은 *Canonical
  Data Model* 없이는 30개(!)의 *Message Translator*(85)를, *Canonical Data Model*을 쓰면 12개만
  요구한다** (8장, p.357).[^hohpe2004]
- 교체를 예상할 때도 값한다 — ***Canonical Data Model*은 기존 애플리케이션이 앞으로 다른 애플리케이션으로
  대체될 가능성이 높을 때도 아주 유용할 수 있다. 예컨대 여러 애플리케이션이 앞으로 새 시스템으로
  대체될 가능성이 높은 레거시 시스템과 인터페이스하고 있다면, *Canonical Data Model*의 개념이
  원래 해법에 내장돼 있으면 한 애플리케이션에서 다른 것으로 전환하는 노력이 훨씬 줄어든다** (8장,
  p.357).[^hohpe2004]

### 적합하게 만드는 세 가지 방법

- **① 애플리케이션의 내부 데이터 형식을 바꾼다** — **이론적으로는 가능할 수 있으나 복잡한 실생활
  시나리오에서는 그럴 법하지 않다. 각 애플리케이션이 네이티브로 같은 데이터 형식을 쓰게 만드는
  것이 쉬웠다면 우리는 *Messaging*(53) 대신 *Shared Database*(47)를 쓰는 편이 나았을 것이다**
  (8장, p.357).[^hohpe2004]
- **② 애플리케이션 안에 Messaging Mapper를 구현한다** — **커스텀 애플리케이션은 매퍼를 써서 원하는
  데이터 형식을 생성할 수 있다** (8장, p.357).[^hohpe2004]
- **③ 외부 Message Translator를 쓴다** — **애플리케이션 고유의 메시지 형식에서 *Canonical Data
  Model*이 지정한 형식으로 번역하기 위해 외부 *Message Translator*(85)를 쓸 수 있다. 이것이
  패키지 애플리케이션의 데이터를 변환하는 유일한 선택지일 수 있다** (8장,
  p.357).[^hohpe2004]
- 무엇으로 고르는가 — ***Messaging Mapper*(477)를 쓸지 외부 *Message Translator*(85)를 쓸지는
  변환의 복잡성과 애플리케이션의 유지보수성에 의존한다. 패키지 애플리케이션은 소스 코드를 이용할
  수 없으므로 보통 *Messaging Mapper*(477)의 사용을 배제한다** (8장, p.357).[^hohpe2004]
- **공개와 사적의 구분이 생긴다** — **외부 *Message Translator*(85)를 쓸 때 우리는 *공개(public)*
  (정규) 메시지와 *사적(private)*(애플리케이션 고유) 메시지를 구별해야 한다. 애플리케이션과 그와
  연관된 *Message Translator*(85) 사이의 메시지는 다른 어떤 애플리케이션도 이 메시지를 쓰면 안
  되므로 사적으로 간주된다. *Message Translator*(85)가 메시지를 *Canonical Data Model*에 부합하는
  형식으로 변환하고 나면 그 메시지는 공개로 간주되고 다른 시스템들이 쓸 수 있다** (8장,
  p.358).[^hohpe2004]

### 이중 번역의 대가

- 이름이 붙는다 — ***Canonical Data Model*의 사용은 메시지 흐름에 일정한 오버헤드를 들여온다. 각
  메시지는 이제 하나가 아니라 두 개의 번역 단계를 거쳐야 한다: 소스 애플리케이션의 형식에서 공통
  형식으로 가는 번역 하나, 공통 형식에서 대상 애플리케이션의 형식으로 가는 번역 하나. 이런 이유로
  *Canonical Data Model*의 사용은 때로 *이중 번역(double translation)* 이라 불린다(한
  애플리케이션의 형식에서 다른 것으로 직접 변환하는 것은 *직접 번역(direct translation)* 이라
  한다)** (8장, p.358).[^hohpe2004]
- **처방이 조건과 함께 제시된다** — **각 번역 단계는 메시지 흐름에 추가 지연을 일으킨다. 그러므로
  아주 높은 처리량의 시스템에는 직접 번역이 유일한 선택일 수 있다. 유지보수성과 성능 사이의 이
  맞교환은 흔하다. **최선의 조언은 성능 요구가 허락하지 않는 한 더 유지보수 가능한 해법(곧
  *Canonical Data Model*)을 쓰라는 것이다.** 완화 요인은 많은 번역이 무상태이고 따라서 병렬로
  실행되는 여러 *Message Translator*(85)로 부하 분산을 하기에 적합하다는 점일 수 있다** (8장,
  p.358).[^hohpe2004]

### 설계가 성공할 확률을 올리는 조건

- **실패의 배경이 먼저 인정된다** — ***Canonical Data Model*을 설계하는 것은 어려울 수 있다.
  대부분의 기업은 최소 하나의 실패한 "전사 데이터 모델(enterprise data model)" 시도를 겪었다.
  균형 잡힌 모델을 달성하려면 설계자는 통합되는 모든 애플리케이션에 똑같이 잘 작동하는 통일된
  모델을 만들려 애써야 한다. 불행히도 이 이상은 실제로 달성하기 어렵다** (8장,
  p.358).[^hohpe2004] 같은 시도의 실패가
  [도메인 소유권 원칙](../concepts/domain-ownership-principle.md)과
  [연합 컴퓨팅 거버넌스 원칙](../concepts/federated-computational-governance-principle.md)에서
  데이터 메시가 정면으로 기각하는 대목이기도 하다.
- **범위를 좁히면 확률이 오른다** — ***Canonical Data Model*을 성공적으로 설계할 가능성은 *Canonical
  Data Model*이 모든 애플리케이션 안에서 쓰이는 데이터의 완전한 집합을 모델링할 필요가 없고 메시징에
  참여하는 부분만 모델링하면 된다는 점을 고려할 때 개선된다. 이는 *Canonical Data Model* 생성의
  복잡성을 크게 줄일 수 있다** (8장, p.358).[^hohpe2004]
- **정치적 이점도 명시된다** — ***Canonical Data Model*을 쓰는 것은 정치적 이점도 가질 수 있다.
  *Canonical Data Model*을 쓰면 개발자와 업무 사용자가 특정 패키지 구현이 아니라 회사의 업무
  도메인 관점에서 통합 해법을 논할 수 있다. 예컨대 패키지 애플리케이션들은 고객이라는 공통 개념을
  "계정(account)"·"지불인(payer)"·"연락처(contact)" 같은 여러 다른 내부 형식으로 표현할 수 있다.
  *Canonical Data Model*을 정의하는 것은 애플리케이션 사이의 의미 불협화(semantic dissonance)
  사례를 해소하는 첫 단계인 일이 잦다** (8장, p.359).[^hohpe2004]

### 의존은 여러 층에 있다

- **네 층이 나란히 세워진다** — ***Message Channel*(60)의 사용은 애플리케이션 사이에 공통 전송
  계층을 제공하고 애플리케이션 고유의 전송 프로토콜 사이의 의존을 제거한다. *Message Router*(78)는
  위치 독립성을 제공해 발신 애플리케이션이 수신 애플리케이션의 위치에 의존하지 않아도 되게 한다.
  XML 같은 공통 데이터 표현의 사용은 애플리케이션 고유 데이터 타입에 대한 의존을 제거한다. 마지막으로
  *Canonical Data Model*은 애플리케이션이 쓰는 데이터 형식과 의미에 대한 의존을 해소한다** (8장,
  p.359).[^hohpe2004]
- **정규 모델도 변한다** — **늘 그렇듯 유일한 상수는 변화다. 그러므로 *Canonical Data Model*에
  부합하는 메시지는 *Format Indicator*(180)를 지정해야 한다** (8장, p.359).[^hohpe2004]
  *Format Indicator*는 [메시지 구성 패턴](../concepts/message-construction-patterns.md)에 있고, 같은 문제의
  2026년 KB 작성 시점 대응물이 [하위·상위 호환성](../concepts/backward-and-forward-compatibility.md)이다.
- 예제가 개념을 말한 대목 — **WSDL이 사실상 Canonical Data Model이다.** **애플리케이션에서 외부
  서비스에 접근할 때 그 서비스가 이미 쓸 *Canonical Data Model*을 지정하고 있을 수 있다. XML 웹
  서비스의 세계에서 데이터 형식은 WSDL(Web Services Definition Language) 문서로 지정된다. WSDL은
  서비스가 소비하고 생산할 수 있는 요청·응답 메시지의 구조를 지정한다. 대부분의 경우 WSDL에 지정된
  데이터 형식은 그 서비스를 제공하는 애플리케이션의 내부 형식과 다르다. 사실상 WSDL은 대화에
  참여하는 양쪽이 쓸 *Canonical Data Model*을 지정한다** (8장, p.360).[^hohpe2004]
