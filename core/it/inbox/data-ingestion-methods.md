## 카탈로그의 지위

- 저자들이 미리 다는 단서 — **이제 배치와 스트리밍 반입의 밑에 있는 유의한 패턴들을 서술했으니
  데이터를 반입할 수 있는 방법에 집중하자. 흔한 방법 몇 가지를 인용하겠지만 데이터 반입 실천과
  기술의 우주는 방대하고 날마다 커지고 있음을 유념하라** (7장, pp.250–251).[^reis2022]
  - 즉 이 목록은 **완결된 분류가 아니라 저자들이 고른 표본**이다. 목록의 형태(무엇이 한 항목으로
    묶였는가)가 정보이지 목록의 완전성이 정보가 아니다.

## 직접 데이터베이스 연결 — JDBC와 ODBC

- **데이터는 네트워크 연결을 통해 질의하고 읽음으로써 반입을 위해 데이터베이스에서 당겨질 수
  있다. 가장 흔하게 이 연결은 ODBC나 JDBC를 써서 이뤄진다** (7장, p.251).[^reis2022]
- ODBC — **ODBC는 표준 ODBC API로 발행된 명령을 데이터베이스에 발행되는 명령으로 번역하기 위해
  데이터베이스에 접근하는 클라이언트가 호스팅하는 드라이버를 쓴다. 데이터베이스는 질의 결과를
  전선 너머로 돌려주고, 드라이버가 이를 받아 클라이언트가 읽을 표준 형식으로 되돌린다. 반입의
  경우 ODBC 드라이버를 활용하는 애플리케이션이 반입 도구다. 반입 도구는 많은 작은 질의로 또는
  하나의 큰 질의로 데이터를 당길 수 있다** (7장, p.251).[^reis2022]
- JDBC — **JDBC는 개념적으로 ODBC와 놀랍도록 비슷하다. 자바 드라이버가 원격 데이터베이스에
  연결하고 표준 JDBC API와 대상 데이터베이스의 네이티브 네트워크 인터페이스 사이의 번역 층
  역할을 한다** (7장, p.251).[^reis2022]
- 왜 한 언어에 API가 헌정됐는가 — **단일 프로그래밍 언어에 헌정된 데이터베이스 API를 갖는 것이
  이상해 보일 수 있지만 여기에는 강한 동기가 있다. 자바 가상 머신(JVM)은 표준적이고, 하드웨어
  아키텍처와 운영체제를 가로질러 이식 가능하며, JIT 컴파일러를 통해 컴파일된 코드의 성능을
  제공한다. JVM은 코드를 이식 가능한 방식으로 돌리는 극히 인기 있는 컴파일 VM이다** (7장,
  p.251).[^reis2022]
- 그 결과가 드라이버 이식성이다 — **JDBC는 비범한 데이터베이스 드라이버 이식성을 제공한다.
  ODBC 드라이버는 OS와 아키텍처 네이티브 바이너리로 배포된다 — 데이터베이스 벤더는 지원하려는
  각 아키텍처/OS 버전마다 버전을 유지해야 한다. 반면 벤더는 어떤 JVM 언어(예: 자바·스칼라·
  클로저·코틀린)나 JVM 데이터 프레임워크(즉 스파크)와도 호환되는 단일 JDBC 드라이버를 배포할 수
  있다. JDBC는 대단히 인기가 있어 파이썬 같은 비JVM 언어의 인터페이스로도 쓰인다 — 파이썬
  생태계는 파이썬 코드가 로컬 JVM에서 도는 JDBC 드라이버와 이야기하게 하는 번역 도구를 제공한다**
  (7장, p.251).[^reis2022]
- 병렬 연결의 대가 — **JDBC와 ODBC는 관계형 데이터베이스로부터의 데이터 반입에 광범위하게 쓰이며
  직접 데이터베이스 연결이라는 일반 개념으로 돌아간다. 데이터 반입을 가속하기 위해 다양한 향상이
  쓰인다. 많은 데이터 프레임워크가 여러 동시 연결을 병렬화하고 질의를 분할해 데이터를 병렬로 당길
  수 있다. 반면 공짜는 없다 — 병렬 연결을 쓰면 원천 데이터베이스의 부하도 늘어난다** (7장,
  p.251).[^reis2022]
- 이 표준들이 늙고 있다 — **JDBC와 ODBC는 오랫동안 데이터베이스로부터의 데이터 반입의 금본위
  였지만, 이 연결 표준들은 많은 데이터 엔지니어링 응용에서 나이를 드러내기 시작하고 있다. 이
  연결 표준들은 중첩 데이터와 씨름하며 데이터를 행으로 보낸다. 이는 네이티브 중첩 데이터가
  전선으로 보내지기 위해 문자열 데이터로 재인코딩돼야 하고, 컬럼 데이터베이스의 컬럼이 행으로
  재직렬화돼야 한다는 뜻이다** (7장, pp.251–252).[^reis2022]
  - **행 지향 프로토콜이 컬럼 저장을 만나는 지점의 임피던스 불일치**다. 컬럼 저장이 왜 그
    형태인지는 [컬럼 지향 저장](../concepts/column-oriented-storage.md)에 있다.
- 그래서 우회로가 생겼다 — **"파일 기반 내보내기와 반입"에서 논했듯 이제 많은 데이터베이스가
  JDBC/ODBC를 우회하고 Parquet·ORC·Avro 같은 형식으로 데이터를 직접 내보내는 네이티브 파일
  내보내기를 지원한다. 대안으로 많은 클라우드 데이터 웨어하우스가 직접 REST API를 제공한다**
  (7장, p.252).[^reis2022]
- 실무의 조립 방식 — **JDBC 연결은 일반적으로 다른 반입 기술과 통합돼야 한다. 예컨대 우리는 흔히
  리더 프로세스로 JDBC를 통해 데이터베이스에 연결하고, 추출한 데이터를 여러 객체로 쓴 다음, 하류
  시스템으로의 반입을 오케스트레이션한다. 리더 프로세스는 완전히 임시적인 클라우드 인스턴스에서
  돌 수도 있고 오케스트레이션 시스템에서 돌 수도 있다** (7장, p.252).[^reis2022]

## API

- 저자들이 인용하는 한 줄 — 직인용한다 (7장, p.254, Karl Hughes 인용):[^reis2022]

  > The bulk of software engineering is just plumbing.

- 현실 — **5장에서 언급했듯 API는 중요성과 인기가 계속 커지는 데이터 원천이다. 전형적 조직은
  SaaS 플랫폼이나 파트너 회사 같은 수백 개의 외부 데이터 원천을 가질 수 있다. 냉혹한 현실은 API를
  통한 데이터 교환에 제대로 된 표준이 존재하지 않는다는 것이다. 데이터 엔지니어는 문서를 읽고,
  외부 데이터 소유자와 소통하고, API 연결 코드를 쓰고 유지하는 데 상당한 시간을 쓸 수 있다**
  (7장, p.254).[^reis2022]
- 상황을 바꾸는 세 흐름 (7장, pp.254–255):[^reis2022]
  - **첫째, 많은 벤더가 다양한 프로그래밍 언어를 위한 API 클라이언트 라이브러리를 제공해 API
    접근의 복잡성 상당 부분을 제거한다.**
  - **둘째, 수많은 데이터 커넥터 플랫폼이 이제 SaaS·오픈소스·관리형 오픈소스로 가용하다. 이
    플랫폼은 많은 데이터 원천에 대한 턴키 데이터 연결성을 제공하며, 지원되지 않는 데이터 원천을
    위한 커스텀 커넥터 작성 프레임워크를 제공한다.**
  - **셋째 흐름은 데이터 공유(data sharing)의 출현이다 — 즉 BigQuery·Snowflake·Redshift·S3
    같은 표준 플랫폼을 통해 데이터를 교환하는 능력이다. 데이터가 이 플랫폼 중 하나에 착지하면
    저장·처리·이동이 간단하다. 데이터 공유는 데이터 엔지니어링 공간에 크고 빠른 영향을 끼쳤다.**
- 저자들의 권고 — **데이터 공유가 선택지가 아니고 직접 API 접근이 필요할 때 바퀴를 다시 발명하지
  마라. 관리형 서비스가 비싼 선택지처럼 보일 수 있지만, 당신 시간의 가치와 더 높은 가치의 일에
  시간을 쓸 수 있었을 때 API 커넥터를 짓는 기회비용을 고려하라** (7장, p.255).[^reis2022]
- 커스텀이 남는 자리 — **커스텀 연결 작업은 기존 프레임워크가 잘 지원하지 않는 API를 위해 아껴
  두라 — 작업할 것이 여전히 많이 있음을 알게 될 것이다. 커스텀 API 연결을 다루는 데는 두 측면이
  있다: 소프트웨어 개발과 운영. 소프트웨어 개발 모범 사례를 따르라 — 버전 관리·지속적 배포·자동화
  테스트를 써야 한다. 데브옵스 모범 사례를 따르는 것에 더해 오케스트레이션 프레임워크를 고려하라.
  이는 데이터 반입의 운영 부담을 극적으로 간소화할 수 있다** (7장, p.255).[^reis2022]

## 메시지 큐와 이벤트 스트리밍 플랫폼

- 자리 — **메시지 큐와 이벤트 스트리밍 플랫폼은 웹·모바일 애플리케이션, IoT 센서, 스마트 장치에서
  실시간 데이터를 반입하는 널리 퍼진 방식이다. 실시간 데이터가 더 흔해지면서 실시간 데이터를 다루는
  방식을 반입 워크플로에 도입하거나 개조하는 자신을 자주 발견할 것이다. 이 때문에 실시간 데이터를
  반입하는 방법을 아는 것이 본질적이다. 인기 있는 실시간 데이터 반입에는 메시지 큐와 이벤트
  스트리밍 플랫폼이 포함되며 이는 5장에서 다뤘다. 이 둘 다 원천 시스템이지만 데이터를 반입하는
  방식으로도 작동한다. 두 경우 모두 구독하는 발행자로부터 이벤트를 소비한다** (7장,
  p.255).[^reis2022]
  - **같은 물건이 원천 시스템이자 반입 수단이라는 이중 지위**가 이 절의 요지다. 5장 쪽의
    서술은 [발행-구독 메시징](../concepts/publish-subscribe-messaging.md)의 "원천 시스템으로서의
    메시지 큐" 절에 있다.
- 메시지와 스트림의 차이 재확인 — **메시지와 스트림의 차이를 상기하자. 메시지(message)는 개별
  이벤트 수준에서 다뤄지며 일시적(transient)이도록 의도됐다. 메시지가 소비되고 나면 확인 응답되고
  큐에서 제거된다. 반면 스트림(stream)은 이벤트를 순서 있는 로그에 반입한다. 로그는 원하는 만큼
  오래 영속하며, 이벤트가 다양한 범위에 걸쳐 질의되고 집계되고 다른 스트림과 결합돼 하류 소비자에게
  발행되는 새 변환을 만들 수 있게 한다** (7장, p.255).[^reis2022]
- 그리고 이것이 반입을 **비선형**으로 만든다 — **마지막 지점이 배치 반입과 스트리밍 반입 사이의
  본질적 차이다. 배치가 보통 정적 워크플로(데이터를 반입하고 저장하고 변환하고 서빙)를 수반하는
  반면 메시지와 스트림은 유동적이다. 반입이 비선형일 수 있으며, 데이터가 발행되고 소비되고 재발행되고
  재소비된다. 실시간 반입 워크플로를 설계할 때 데이터가 어떻게 흐를지 염두에 두라** (7장,
  p.256).[^reis2022]
- 처리량이라는 또 하나의 축 — **또 하나의 고려사항은 실시간 데이터 파이프라인의 처리량이다.
  메시지와 이벤트는 가능한 한 적은 지연으로 흘러야 하며, 이는 적절한 파티션(또는 샤드) 대역폭과
  처리량을 프로비저닝해야 한다는 뜻이다. 이벤트 처리를 위한 충분한 메모리·디스크·CPU 자원을
  제공하고, 실시간 파이프라인을 직접 관리한다면 급등을 감당하고 부하가 줄면 돈을 아끼도록
  오토스케일링을 넣으라. 이런 이유로 스트리밍 플랫폼을 관리하는 것은 상당한 운영 오버헤드를
  수반할 수 있다. 실시간 반입 파이프라인에 관리형 서비스를 고려하고, 실시간 데이터에서 가치를
  얻을 방법에 주의를 집중하라** (7장, p.256).[^reis2022]

## 관리형 데이터 커넥터

- 저자들이 먼저 던지라는 질문 — **요즘 데이터베이스나 API에 대한 데이터 반입 커넥터를 쓰는 것을
  고려한다면 스스로에게 물으라: 이것이 이미 만들어져 있는가? 나아가 이 연결의 성가신 세부를
  관리해 줄 서비스가 있는가?** (7장, p.256).[^reis2022]
- 무엇을 대신해 주는가 — **이 도구들은 특정 원천에 연결하기 위해 복잡한 배관을 짓는 데이터
  엔지니어의 수고를 덜기 위해 표준 커넥터 집합을 즉시 제공하는 것을 목표로 한다. 데이터 커넥터를
  만들고 관리하는 대신 이 서비스를 서드파티에 아웃소싱한다** (7장, p.256).[^reis2022]
- 일반적 형태 — **일반적으로 이 공간의 선택지들은 사용자가 대상과 원천을 설정하고, 다양한
  방식(예: CDC·복제·잘라내고 다시 적재)으로 반입하고, 권한과 자격 증명을 설정하고, 갱신 빈도를
  설정하고, 데이터 동기화를 시작하게 한다. 벤더나 클라우드가 무대 뒤에서 데이터 동기화를 완전히
  관리하고 모니터링한다. 데이터 동기화가 실패하면 오류 원인에 대한 로그 정보와 함께 경보를 받는다**
  (7장, p.256).[^reis2022]
- 판정 — **우리는 자체 커넥터를 만들고 관리하는 대신 관리형 커넥터 플랫폼을 쓸 것을 제안한다.
  벤더와 OSS 프로젝트는 각각 일반적으로 수백 개의 미리 만들어진 커넥터 옵션을 갖고 있고 커스텀
  커넥터를 쉽게 만들 수 있다. 데이터 커넥터의 생성과 관리는 요즘 대체로 차별화되지 않는 무거운
  일(undifferentiated heavy lifting)이며 가능하면 언제나 아웃소싱해야 한다** (7장,
  p.257).[^reis2022]
  - 저자들이 드는 실물은 **Fivetran·Matillion·Airbyte**다 (7장, p.268).[^reis2022]
  - 이 권고는 **"커넥터를 직접 쓰지 말라"**에서 멈추지 않고 **"커넥터 관리 자체가 차별화되지
    않는 일"**이라는 더 센 주장으로 간다. 오픈소스 프레임워크로 같은 층을 직접 운영하는 쪽의
    논거는 [카프카 커넥트](../concepts/kafka-connect.md)에 있다 — 그쪽은 프로듀서·컨슈머를
    직접 쓰는 대신 커넥트를 고르는 기준을 논하지, 커넥트 자체를 아웃소싱하라고 하지 않는다.
    **두 소스가 "무엇을 남의 일로 넘길 것인가"의 경계를 다르게 긋는다.**

## 오브젝트 저장으로 데이터를 옮기기

- **오브젝트 저장은 공용 클라우드의 멀티테넌트 시스템이며 방대한 양의 데이터 저장을 지원한다.
  이는 오브젝트 저장을 데이터 레이크 안팎으로 데이터를 옮기고, 팀 사이에서, 조직 사이에서 데이터를
  전송하는 데 이상적으로 만든다. 서명된 URL로 객체에 단기 접근을 제공해 사용자에게 임시 권한을 줄
  수도 있다** (7장, p.257).[^reis2022]
- 저자들의 판정 — **우리 관점에서 오브젝트 저장은 파일 교환을 다루는 가장 최적이고 안전한
  방법이다. 공용 클라우드 저장은 최신 보안 표준을 구현하고, 확장성과 신뢰성의 견고한 실적을
  가지며, 임의 유형과 크기의 파일을 받아들이고, 고성능 데이터 이동을 제공한다** (7장,
  p.257).[^reis2022] 그 시스템 자체는 [오브젝트 스토어](../concepts/object-stores.md)에 있다.

## EDI

- **데이터 엔지니어의 또 하나의 실무적 현실이 전자 데이터 교환(EDI)이다. 이 용어는 어떤 데이터
  이동 방법이든 가리킬 만큼 모호하다. 보통은 이메일이나 플래시 드라이브 같은 다소 고풍스러운
  파일 교환 수단을 가리킨다. 데이터 엔지니어는 어떤 데이터 원천이 더 현대적인 데이터 전송 수단을
  지원하지 않는다는 것을 알게 될 것이다 — 흔히 고풍스러운 IT 시스템이나 인간 프로세스 한계 때문이다**
  (7장, p.257).[^reis2022]
- 그래도 자동화할 수 있다 — **엔지니어는 최소한 자동화를 통해 EDI를 향상시킬 수 있다. 예컨대
  파일을 받는 즉시 회사 오브젝트 저장에 저장하는 클라우드 기반 이메일 서버를 세울 수 있다. 이는
  데이터를 반입하고 처리하는 오케스트레이션 프로세스를 촉발할 수 있다. 이는 직원이 첨부 파일을
  내려받아 내부 시스템에 수동 업로드하는 것 — 우리가 여전히 자주 보는 — 보다 훨씬 견고하다**
  (7장, p.257).[^reis2022]

## 데이터베이스와 파일 내보내기

- 내보내기가 원천에 주는 부하 — **엔지니어는 원천 데이터베이스 시스템이 파일 내보내기를 어떻게
  다루는지 알아야 한다. 내보내기는 많은 트랜잭션 시스템에서 데이터베이스에 상당한 부하를 주는 큰
  데이터 스캔을 수반한다. 원천 시스템 엔지니어는 애플리케이션 성능에 영향을 주지 않고 이 스캔을
  언제 돌릴 수 있는지 평가해야 하며 부하를 완화할 전략을 택할 수 있다** (7장, p.257).[^reis2022]
- 완화 전략 둘 — **내보내기 질의는 키 범위로 질의하거나 한 번에 한 파티션씩 질의해 더 작은
  내보내기로 쪼갤 수 있다. 대안으로 읽기 복제본이 부하를 줄일 수 있다. 읽기 복제본은 내보내기가
  하루에 여러 번 일어나고 높은 원천 시스템 부하와 겹칠 때 특히 적절하다** (7장,
  p.257).[^reis2022]
- 클라우드 웨어하우스는 이걸 잘한다 — **주요 클라우드 데이터 웨어하우스는 직접 파일 내보내기에
  고도로 최적화돼 있다. 예컨대 Snowflake·BigQuery·Redshift 등이 다양한 형식으로 오브젝트 저장에
  직접 내보내기를 지원한다** (7장, p.258).[^reis2022]
- 내보내기 형식을 고르는 실무 이슈(CSV의 위험과 Parquet·Avro·Arrow·ORC의 이점)는
  [데이터 인코딩 형식](../concepts/data-encoding-formats.md)의 "내보내기 형식으로 고를 때" 절에
  있다.

## 셸·SSH·SFTP·SCP

- **셸(shell)** — **셸은 데이터를 반입하기 위해 명령을 실행할 수 있는 인터페이스다. 셸은 사실상
  어떤 소프트웨어 도구를 위한 워크플로든 스크립트로 짜는 데 쓸 수 있으며, 셸 스크립팅은 반입
  프로세스에서 여전히 광범위하게 쓰인다. 셸 스크립트는 데이터베이스에서 데이터를 읽고, 다른 파일
  형식으로 재직렬화하고, 오브젝트 저장에 업로드하고, 대상 데이터베이스에서 반입 프로세스를 촉발할
  수 있다. 단일 인스턴스나 서버에 데이터를 저장하는 것이 고도로 확장 가능하지는 않지만 우리 데이터
  원천 다수는 특별히 크지 않고 그런 접근이 잘 통한다** (7장, p.258).[^reis2022]
  - 언제 벗어나야 하는가 — **덧붙여 클라우드 벤더는 일반적으로 견고한 CLI 기반 도구를 제공한다.
    AWS CLI에 명령을 발행하는 것만으로 복잡한 반입 프로세스를 돌리는 것이 가능하다. 반입 프로세스가
    더 복잡해지고 SLA가 더 엄격해지면 엔지니어는 제대로 된 오케스트레이션 시스템으로 옮기는 것을
    고려해야 한다** (7장, p.259).[^reis2022]
- **SSH** — **SSH는 반입 전략이 아니라 다른 반입 전략과 함께 쓰이는 프로토콜이다. 우리는 SSH를
  몇 가지로 쓴다. 첫째, SSH는 앞서 언급한 SCP를 통한 파일 전송에 쓸 수 있다. 둘째, SSH 터널은
  데이터베이스로의 안전하고 격리된 연결을 허용하는 데 쓰인다** (7장, p.259).[^reis2022]
  - 배스천 호스트 — **애플리케이션 데이터베이스는 결코 인터넷에 직접 노출돼서는 안 된다. 대신
    엔지니어는 배스천 호스트(bastion host) — 즉 문제의 데이터베이스에 연결할 수 있는 중간 호스트
    인스턴스 — 를 세울 수 있다. 이 호스트 머신은 인터넷에 노출되지만 지정된 IP 주소에서 지정된
    포트로의 최소 접근만 허용하도록 잠겨 있다. 데이터베이스에 연결하려면 원격 머신이 먼저 배스천
    호스트로 SSH 터널 연결을 열고 그 호스트 머신에서 데이터베이스로 연결한다** (7장,
    p.259).[^reis2022]
- **SFTP와 SCP** — **보안 FTP(SFTP)와 보안 복사(SCP) 양쪽에서 데이터에 접근하고 보내는 것은
  데이터 엔지니어가 보통 정기적으로 쓰지 않더라도(IT나 보안/시크옵스가 다룰 것이다) 익숙해져야
  할 기법이다** (7장, p.259).[^reis2022]
  - 현실 — **엔지니어가 SFTP 언급에 움찔하는 것은 당연하다(때로는 FTP가 프로덕션에서 쓰인다는
    사례까지 듣는다). 그럼에도 SFTP는 많은 업체에 여전히 실무적 현실이다. 그들은 SFTP를 써서
    데이터를 소비하거나 제공하는 파트너 업체와 일하며 다른 표준에 의존할 의사가 없다. 데이터 유출을
    피하려면 이런 상황에서 보안 분석이 결정적이다** (7장, p.259).[^reis2022]
  - **SCP는 SSH 연결 위에서 도는 파일 교환 프로토콜이다. SCP는 올바로 설정되면 안전한 파일 전송
    선택지가 될 수 있다. 다시, SCP 보안을 강화하기 위해 추가 네트워크 접근 통제(심층 방어)를
    더할 것을 강력히 권장한다** (7장, p.259).[^reis2022]

## 웹훅

- 방향이 뒤집힌다 — **5장에서 논했듯 웹훅(webhooks)은 흔히 역 API(reverse APIs)라 불린다.
  전형적 REST 데이터 API에서 데이터 제공자는 엔지니어에게 API 명세를 주고 엔지니어는 그것으로
  데이터 반입 코드를 쓴다. 코드가 요청을 만들고 응답으로 데이터를 받는다** (7장,
  p.259).[^reis2022]
- **웹훅에서는 데이터 제공자가 API 요청 명세를 정의하지만 데이터 제공자가 API 호출을 받는 것이
  아니라 만든다. API 엔드포인트를 제공자가 호출하도록 제공하는 것은 데이터 소비자의 책임이다.
  소비자는 각 요청을 반입하고 데이터 집계·저장·처리를 다룰 책임을 진다** (7장,
  pp.259–260).[^reis2022]
- 순진하게 지으면 부서진다 — **웹훅 기반 데이터 반입 아키텍처는 부서지기 쉽고 유지하기 어렵고
  비효율적일 수 있다. 적절한 기성 도구를 쓰면 데이터 엔지니어는 더 낮은 유지보수·인프라 비용으로
  더 견고한 웹훅 아키텍처를 지을 수 있다. 예컨대 AWS의 웹훅 패턴은 서버리스 함수 프레임워크
  (Lambda)로 들어오는 이벤트를 받고, 관리형 이벤트 스트리밍 플랫폼(Kinesis)으로 메시지를 저장·
  버퍼링하고, 스트림 처리 프레임워크(Flink)로 실시간 분석을 다루고, 오브젝트 저장(S3)을 장기
  저장으로 쓸 수 있다** (7장, p.260).[^reis2022]
- 그리고 이 사실이 뭔가를 드러낸다 — **이 아키텍처가 단순히 데이터를 반입하는 것보다 훨씬 많은
  일을 한다는 것을 알아챌 것이다. 이는 반입이 데이터 엔지니어링 수명 주기의 다른 단계들과 얽혀
  있음을 강조한다 — 저장과 처리에 대한 결정 없이 반입 아키텍처를 정의하는 것은 흔히 불가능하다**
  (7장, p.260).[^reis2022]
  - 웹훅의 5장 쪽 서술은 [웹 서비스와 REST](../concepts/web-services-and-rest.md)에 있다.

## 웹 인터페이스와 웹 스크래핑

- **웹 인터페이스** — **데이터 접근을 위한 웹 인터페이스는 데이터 엔지니어에게 실무적 현실로
  남아 있다. 우리는 SaaS 플랫폼의 모든 데이터와 기능이 API나 파일 드롭 같은 자동화된 인터페이스로
  노출되지는 않는 상황에 자주 부딪힌다. 대신 누군가가 웹 인터페이스에 수동으로 접근해 리포트를
  생성하고 로컬 머신에 파일을 내려받아야 한다. 이는 사람이 리포트 돌리는 것을 잊거나 노트북이
  죽는 것 같은 명백한 단점이 있다. 가능한 곳에서는 데이터에 자동 접근을 허용하는 도구와 워크플로를
  고르라** (7장, p.260).[^reis2022]
- **웹 스크래핑** — **웹 스크래핑(web scraping)은 흔히 웹 페이지의 다양한 HTML 요소를 훑어
  웹 페이지에서 데이터를 자동으로 추출한다. 상품 가격 정보를 뽑기 위해 이커머스 사이트를
  스크래핑하거나 뉴스 애그리게이터를 위해 여러 뉴스 사이트를 스크래핑할 수 있다. 웹 스크래핑은
  널리 퍼져 있고 데이터 엔지니어로서 만날 수 있다. 또한 윤리적·법적 선이 흐릿한 탁한 영역이다**
  (7장, p.260).[^reis2022]
- 시작하기 전의 세 조언 (7장, p.261):[^reis2022]
  - **첫째, 웹 스크래핑을 해야 하는지 아니면 데이터가 서드파티에서 가용한지 스스로에게 물으라.
    스크래핑하기로 결정했다면 좋은 시민이 되라. 부주의하게 서비스 거부(DoS) 공격을 만들지 말고
    IP 주소가 차단되지 않게 하라. 얼마나 많은 트래픽을 생성하는지 이해하고 웹 크롤링 활동을
    적절히 조절하라. 수천 개의 동시 Lambda 함수를 띄워 스크래핑할 수 있다고 해서 그래야 하는
    것은 아니다 — 과도한 웹 스크래핑은 AWS 계정 비활성화로 이어질 수 있다.**
  - **둘째, 활동의 법적 함의를 알라. 다시, DoS 공격을 생성하는 것은 법적 결과를 수반할 수 있다.
    서비스 약관을 위반하는 행동은 고용주나 개인에게 골칫거리를 안길 수 있다.**
  - **셋째, 웹 페이지는 HTML 요소 구조를 끊임없이 바꾸므로 웹 스크레이퍼를 갱신 상태로 유지하기가
    까다롭다. 스스로에게 물으라 — 이 시스템들을 유지하는 두통이 그만한 값어치를 하는가?**
- 처리 단계로 이어진다 — **웹 스크래핑은 데이터 엔지니어링 수명 주기 처리 단계에 흥미로운
  함의를 갖는다. 엔지니어는 웹 스크래핑 프로젝트 초입에 다양한 요인을 생각해야 한다. 데이터로
  무엇을 하려는가? 파이썬 코드로 스크래핑한 HTML에서 필요한 필드만 뽑아 이 값들을 데이터베이스에
  쓸 것인가? 스크래핑한 웹사이트의 완전한 HTML 코드를 유지하고 스파크 같은 프레임워크로 이
  데이터를 처리할 것인가? 이 결정들은 반입 하류의 아주 다른 아키텍처로 이어질 수 있다** (7장,
  p.261).[^reis2022]

## 데이터 마이그레이션용 전송 어플라이언스

- 언제 전선을 포기하는가 — **방대한 양의 데이터(100TB 이상)의 경우 인터넷을 통해 데이터를 직접
  전송하는 것은 느리고 비쌀 수 있다. 이 규모에서 데이터를 옮기는 가장 빠르고 효율적인 방법은
  전선이 아니라 트럭이다. 클라우드 벤더는 물리적 "하드 디스크 상자"를 통해 데이터를 보내는 능력을
  제공한다. 전송 어플라이언스(transfer appliance)라 불리는 저장 장치를 주문해 서버에서 데이터를
  적재한 뒤 클라우드 벤더에 돌려보내면 벤더가 데이터를 업로드한다** (7장, p.261).[^reis2022]
- 규모의 기준선 — **데이터 크기가 100TB 언저리라면 전송 어플라이언스 사용을 고려하라는 제안이다.
  극단에서 AWS는 세미트레일러로 보내지는 전송 어플라이언스 Snowmobile까지 제공한다! Snowmobile은
  데이터 크기가 페타바이트 이상인 데이터센터 전체를 들어 옮기려는 것이다** (7장,
  p.261).[^reis2022]
- 멀티클라우드에도 쓰인다 — **전송 어플라이언스는 하이브리드 클라우드나 멀티클라우드 설정을
  만드는 데 편리하다. 예컨대 아마존의 데이터 전송 어플라이언스(AWS Snowball)는 임포트와 익스포트를
  모두 지원한다. 두 번째 클라우드로 마이그레이션하려면 사용자가 데이터를 Snowball 장치로 내보낸
  뒤 두 번째 전송 어플라이언스로 임포트해 데이터를 GCP나 Azure로 옮길 수 있다. 어색하게 들릴 수
  있지만 클라우드 사이에 인터넷으로 데이터를 미는 것이 가능하더라도 데이터 이그레스 요금이 이를
  비싼 제안으로 만든다. 물리적 전송 어플라이언스는 데이터 볼륨이 유의할 때 더 싼 대안이다**
  (7장, pp.261–262).[^reis2022]
- 다만 일회성이다 — **전송 어플라이언스와 데이터 마이그레이션 서비스는 일회성 데이터 반입
  이벤트이며 진행 중 워크로드에는 제안되지 않는다는 것을 기억하라. 하이브리드나 멀티클라우드
  시나리오에서 지속적 데이터 이동을 요구하는 워크로드가 있다고 하자. 그 경우 데이터 크기는 아마도
  진행 중 기준으로 훨씬 작은 데이터 크기를 배칭하거나 스트리밍하고 있을 것이다** (7장,
  p.262).[^reis2022]

## 데이터 공유

- 정의와 그 한계 — **데이터 공유(data sharing)는 데이터를 소비하는 인기 있는 선택지로 커지고
  있다. 데이터 제공자는 데이터셋을 서드파티 구독자에게 무료로 또는 유료로 제공한다. 이 데이터셋은
  흔히 읽기 전용 방식으로 공유되며, 이는 이 데이터셋을 자신의 데이터(그리고 다른 서드파티
  데이터셋)와 통합할 수 있지만 공유된 데이터셋을 소유하지는 않는다는 뜻이다. 엄밀한 의미에서
  이것은 데이터셋의 물리적 소유를 얻는 반입이 아니다. 데이터 제공자가 데이터셋에 대한 접근을
  제거하기로 하면 더는 접근할 수 없게 된다** (7장, p.262).[^reis2022]
  - **"엄밀히 말하면 반입이 아니다"**라는 이 단서가 이 항목을 카탈로그의 다른 항목들과 가른다 —
    데이터가 움직이지 않는데도 반입 수단 목록에 들어와 있다.
- **많은 클라우드 플랫폼이 데이터 공유를 제공해 자기 데이터를 공유하고 다양한 제공자로부터
  데이터를 소비할 수 있게 한다. 이 플랫폼 일부는 회사와 조직이 데이터를 판매용으로 제공할 수 있는
  데이터 마켓플레이스도 제공한다** (7장, p.262).[^reis2022] 5장 쪽 서술은
  [데이터 공유와 서드파티 원천](../concepts/data-sharing-and-third-party-sources.md)에 있다.
