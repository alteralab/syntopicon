하나의 질문: **데이터 프로덕트를 독립적으로 배포·관리되는 최소 아키텍처 단위로 삼으면, 그
단위 안에는 무엇이 들어가야 하는가.**

[데이터 메시](../concepts/data-mesh.md)의 둘째 원칙
([제품으로서의 데이터](../concepts/data-as-a-product-principle.md))를 아키텍처로 옮길 때
생기는 구성물이다. 원전 3부 9장이 이 단위를 정의하고, 그 단위가 바깥과 만나는 표면은
[데이터 프로덕트의 포트와 사이드카](../concepts/data-product-ports-and-sidecar.md)가 받는다.

## 아키텍처 퀀텀이라는 빌려온 정의

- 저자는 정의를 자기가 만들지 않고 *Building Evolutionary Architectures*에서 가져온다 (9장,
  p.151):[^dehghani2022]

> An *architectural quantum*, defined in *Building Evolutionary Architectures* (O'Reilly),
> is the smallest unit of architecture that can be independently deployed, has high
> functional cohesion, and includes all the "structural elements required for its function."

- 그 정의를 데이터 프로덕트에 대입한 것이 이 개념이다 — **데이터 메시의 경우 데이터
  프로덕트가 하나의 아키텍처 퀀텀(architectural quantum)이다. 독립적으로 배포되고 관리될 수
  있는 가장 작은 아키텍처 단위다. 높은 기능적 응집(functional cohesion)을 갖는다 — 곧 특정
  분석 변환을 수행하고 그 결과를 도메인 지향 분석 데이터로 안전하게 공유한다. 그 기능을
  수행하는 데 필요한 모든 구조 구성 요소를 갖는다: 변환 코드, 데이터, 메타데이터, 데이터를
  규율하는 정책, 그리고 인프라에 대한 의존이다** (9장, p.151).[^dehghani2022]
- 이 책의 서술 층위에서는 낱말이 서로 바꿔 쓰인다 — **이 장처럼 엄격히 아키텍처적인 논의에서
  나는 데이터 프로덕트(아키텍처 퀀텀으로서의)를 데이터 프로덕트 퀀텀(data product quantum),
  혹은 게으르게 데이터 퀀텀(data quantum)으로 줄여 쓸 수 있다. 이것들은 모두 교환 가능하다.
  데이터 퀀텀은 데이터 프로덕트의 아키텍처를 설계하는 데이터 메시의 견해 있는 방식이다**
  (9장, p.151).[^dehghani2022]
- 9장 도입의 요약은 이 단위의 지위를 한 줄로 못 박는다 — **데이터 퀀텀은 데이터 메시
  아키텍처의 근본 단위(foundational unit)다. 도메인 지향 데이터와, 필요한 데이터 변환을
  수행하고 데이터와 그 데이터를 규율하는 정책을 공유하는 코드를 담는다** (9장,
  p.144).[^dehghani2022]

## 왜 하필 "퀀텀"인가

- 저자가 신조어 선택을 스스로 변호한다 — **왜 데이터 서비스, 데이터 액터, 데이터 에이전트,
  데이터 오퍼레이터, 데이터 트랜스포머 등이 아닌가. 그것들도 다 괜찮은 선택으로 보일 수
  있다. 오퍼레이터·트랜스포머 같은 이름 다수는 데이터 퀀텀의 한 측면, 곧 그 태스크와 변환
  실행만을 지나치게 강조한다. 마찬가지로 데이터 서비스는 또 다른 측면, 곧 데이터를 서빙하는
  것을 강조한다. 퀀텀은 *Building Evolutionary Architectures*에서 처음 도입되고 나중에
  *Software Architecture: The Hard Parts*에서 확장된 것으로, 데이터 퀀텀의 의도를 완벽히
  체현한다 — 그 일이 무엇이든 자율적으로 수행하는 데 필요한 전부다** (9장,
  p.151).[^dehghani2022]
  - 저자는 이 작명이 부담이라는 것을 인정한다 — **이미 빽빽하게 채워진 기술 어휘 속에서 이
    신조어(neologism)에 대한 내 논거를 당신이 받아들이기를 바란다** (9장,
    p.151).[^dehghani2022]

## 스케일아웃의 축이자 결합의 주체

- 퀀텀이 아키텍처에서 하는 일이 규정된다 — **아키텍처 퀀텀은 시스템이 스케일아웃할 수 있는
  축(axis)이다. 데이터 메시는 더 많은 데이터 프로덕트를 추가하고 연결함으로써 스케일아웃한다**
  (9장, p.151).[^dehghani2022]
- 결합의 종류도 갈라 둔다 — **아키텍처 퀀텀은 정적 결합(static coupling, 예: 빌드 시점
  라이브러리)이나 동적 결합(dynamic coupling, 예: 비동기 런타임 API)을 통해 다른 구성 요소와
  통합된다. 데이터 프로덕트는 데이터 공유 인터페이스의 동적 결합을 통해 다른 데이터 프로덕트와
  통합된다** (9장, p.151).[^dehghani2022]
  - 데이터 메시가 고르는 쪽이 **동적 결합**임을 이 한 줄이 정한다. 같은 갈림이
    [마이크로서비스와 서버리스](../concepts/microservices-and-serverless.md)의 서비스 간 통합
    선택과 나란히 놓인다.

## 세 종류의 구조 구성 요소

- 데이터 프로덕트가 담아야 할 것의 범위 — **데이터 프로덕트는 데이터 그 이상을 캡슐화한다.
  자율적인 방식으로 그 기준선 사용성 특성 — 발견 가능·이해 가능·주소 지정 가능 등 — 을
  드러내면서도 규정을 준수하고 안전한 방식으로 데이터를 계속 공유하는 데 필요한 모든 구조
  구성 요소를 담아야 한다** (9장, p.152).[^dehghani2022] 여기서 열거되는 사용성 특성은
  [제품으로서의 데이터 원칙](../concepts/data-as-a-product-principle.md)의 여덟 속성이다.
- 고수준에서 그 구성 요소는 세 종류다 — **코드(code), 데이터(그리고 메타데이터와 설정), 그리고
  인프라 의존의 명세(specifications of its infrastructure dependencies)** (9장, p.152,
  그림 9-7).[^dehghani2022]

| 종류 | 그림 9-7이 열거하는 것 |
|---|---|
| 코드 | 데이터 변환, 데이터 공유 API, 발견·관측 가능성 API, 계산적 정책 실행, 계산적 문서화 |
| 데이터와 메타데이터 | 다중 언어 데이터(polyglot data), 데이터 모델(구문·의미), 문서, SLO, 계보(lineage), 정책 설정 |
| 플랫폼 의존 | 인프라 의존의 명세 — 컴퓨트, 스토리지 |

## 코드 ① 변환 코드 — 외부 파이프라인의 폐기

- 코드를 담아야 하는 이유가 수명 주기 통제다 — **데이터 프로덕트가 분석 데이터의 수명 주기를
  독립적으로 통제하려면 — 그것을 생성하는 업무 로직을 유지하고, 그 개정을 통제하고, 접근을
  관리하고, 그 내용을 공유하려면 — 코드를 포함하고 그것을 자기 계산 맥락(computational
  context) 안에서 돌려야 한다** (9장, p.153).[^dehghani2022]
- 여기서 데이터 프로덕트와 다른 데이터 산출물의 근본 차이가 나온다 — **이것이 데이터 메시가
  데이터 프로덕트라 부르는 것과 다른 형태의 데이터 아티팩트 사이의 근본적 차이다. 데이터
  프로덕트는 능동적(active)이고, 파일이나 테이블 같은 다른 데이터 아티팩트는 수동적(passive)이다**
  (9장, p.153).[^dehghani2022] 같은 낱말을 서빙 단계의 산출물로 보는
  [데이터 프로덕트](../concepts/data-products.md) 쪽과 갈리는 자리가 여기다.
- 전통 아키텍처에서 이 코드가 있던 자리 — **전통적 아키텍처에서 이 코드는 데이터 프로덕트
  바깥에, 데이터 파이프라인(data pipeline)으로 산다. 파이프라인은 독립적 아티팩트로, 아마도 DAG
  설정으로 관리된다. 그 출력 데이터는 독립적으로, 아마도 웨어하우스의 테이블로 관리된다** (9장,
  p.153).[^dehghani2022]
- 데이터 메시가 하는 조작은 이동이 아니라 **개념의 제거**다 — **데이터 메시는 외부(external)
  파이프라인이라는 개념을 없애고 내부(internal) 변환 코드를 도입한다. 이 코드는 파이프라인으로
  구현될 수도, 아닐 수도 있다. 중요한 차별점은 그 코드가 데이터 프로덕트의 내부 구현으로
  캡슐화된다는 것이다. 그 수명 주기는 데이터 프로덕트가 통제하고, 데이터 프로덕트에 할당된
  실행 맥락에서 돈다** (9장, p.153).[^dehghani2022]
  - [배치 워크플로와 DAG](../concepts/batch-workflows-and-dags.md)가 DAG를 일급 아티팩트로 두는
    서술과 갈리는 자리다. 저자는 오케스트레이션을 부정하지 않고 **그 아티팩트의 소유 경계**를
    옮긴다.
- 남는 코드의 성격 — **변환 코드는 도메인 특유(domain-specific)이고 도메인의 업무 로직과 데이터의
  집계·모델링을 캡슐화한다. 이것이 데이터 프로덕트 개발자가 시간과 주의의 대부분을 쓰는
  코드다** (9장, p.153).[^dehghani2022] 구현과 함께 **그것을 검증하는 자동화된 테스트**도 이
  코드에 포함된다 (9장, p.153).[^dehghani2022]
- 저자가 의도적으로 빼는 것이 있다 — **데이터 반입(data ingestion)이나 데이터 정화(data
  cleansing) 같은 전통적 데이터 파이프라인 단계를 변환 코드에서 뺐음에 유의하라. 이는 데이터
  메시와 전통적 파이프라인의 차이를 더 드러내기 위함이다** (9장, p.153).[^dehghani2022] 반입은
  변환 코드가 아니라 **입력 함수**로 분류된다 (9장, p.155).[^dehghani2022]

## 정화는 상류의 책임이다

- 저자가 정화를 상류로 밀어 버린다 — **데이터 정화는 거의 언제나 상류 소스 — 예컨대 데이터
  프로덕트 — 의 책임이다. 그것이 무결성 있는 데이터를 제공한다. 따라서 전형적인 정화 활동은
  데이터 프로덕트 코드에서 거의 필요하지 않다** (9장, p.154).[^dehghani2022]
- 그 근거가 기대치의 역전이다 — **전통적으로 파이프라인의 데이터 정화 활동은 불완전하거나
  부정확하거나 부정밀하거나 무관한 데이터를 다루는 것을 포함한다. 데이터가 더러울 것이라 예상하는
  것이 규범이다. 데이터 메시의 경우 상류 데이터 프로덕트가 자기 보증에 따라 정화된 데이터를
  제공한다. (…) 더러운 데이터를 받는 것은 오류이지 규범이 아니다** (9장,
  p.154).[^dehghani2022]
- 예외도 명시된다 — **보증 수준이 하류 데이터 프로덕트의 필요보다 낮은 경우가 있을 수 있고, 그
  경우 그 변환 코드에 정화를 포함할 수 있다** (9장, p.154).[^dehghani2022] 저자의 예는 결제
  정보 없이 준실시간으로 구독 이벤트를 내는 **listener subscriptions** 데이터 프로덕트이고,
  하류의 **subscription payments**가 그 이벤트를 결제 정보와 통합해야 한다 (9장,
  p.154).[^dehghani2022]
  - 그런데도 저자는 그것을 더러운 데이터라 부르지 않는다 — **나는 listener subscriptions를 더러운
    데이터라 부르지 않는다. 정보가 빠져 있어도 다른 많은 용법에 완벽히 합당한 데이터 프로덕트다.
    빠진 결제 정보는 그 계약(contract)의 일부다** (9장, p.154).[^dehghani2022]
- 그래서 정화 작업의 존재 자체가 진단 신호가 된다 — **당신이 정화 태스크를 짓고 있는 자신을
  발견한다면, 나는 그것이 상류의 무언가가 고쳐져야 한다는 징후라고 제안한다** (9장,
  p.155).[^dehghani2022] 정화를 하류 파이프라인의 상시 단계로 두는
  [데이터 품질 관리](../concepts/data-quality-management.md)의 처방과 정면으로 갈린다 — 대립은
  처방이고, 조건은 **상류가 데이터 프로덕트로서 품질을 보증하는가**이다.

## 코드 ② 인터페이스 코드

- 인터페이스가 코드에 속하는 이유 — **데이터 프로덕트는 자기 데이터, 발견 가능성 정보, 사용성
  문서, 관측 가능성 메트릭, SLO 등에 대한 접근을 인터페이스(API)를 통해 제공한다. 이 API들은
  정의된 계약 — 데이터 프로덕트가 어떤 정보를 어떻게 소통하는가에 대한 합의 — 을 따른다** (9장,
  p.155).[^dehghani2022] 그 정보를 제공하고 서빙하는 데 코드가 든다 (9장,
  p.155).[^dehghani2022]
- 세 갈래로 나뉜다 — **출력 데이터 API(output data APIs), 입력 데이터 API(input data APIs),
  발견·관측 가능성 API(discovery and observability APIs)** (9장, p.155, 그림 9-9).[^dehghani2022]
  각각의 구실은 [데이터 프로덕트의 포트와 사이드카](../concepts/data-product-ports-and-sidecar.md)가
  받는다.
- 표준화의 주체가 갈린다 — **거버넌스가 모든 데이터 프로덕트에 걸쳐 이 인터페이스들의 정의를
  표준화하고, 플랫폼이 그것을 구현하는 기제를 제공한다** (9장, p.155).[^dehghani2022]
- 낱말 하나가 여기서 고정된다 — **데이터 메시는 자기 인터페이스 API에 대해 포트(port)라는 어구를
  교환 가능하게 쓴다. 이 API들의 구현은 REST처럼 동기적일 수도, 이상적으로는 pub/sub 메시징을
  쓰는 것처럼 비동기적일 수도 있다** (9장, p.155).[^dehghani2022]
- 전통 아키텍처와 갈리는 지점이 **인터페이스의 소유자**다 — **전통적으로는 중앙집중적이고 공유된
  서비스가 이 인터페이스들을 구현한다. API 수명 주기는 도메인의 데이터나 파이프라인과 독립적이다.
  예컨대 데이터에 접근하려면 데이터 소비자가 중앙 카탈로그로 가서 데이터셋을 찾은 다음 플랫폼
  스토리지 시스템의 내장까지 직접 손을 뻗는다. 대조적으로 데이터 메시는 각 데이터 프로덕트가
  코드로서 제공하는, 의도적으로 설계된 인터페이스를 도입한다** (9장, p.156).[^dehghani2022]
  - 그 결과로 얻는 것 — **이 인터페이스들은 궁극적으로 기저 스토리지로 접근을 유도할 수 있지만,
    데이터 프로덕트가 런타임에 어디서 어떻게 할지를 통제할 수 있는 방식으로 그렇게 한다.
    인터페이스는 버저닝되고 데이터 프로덕트 코드·데이터의 나머지와 동기화된 상태로 남는다**
    (9장, p.156).[^dehghani2022]

## 코드 ③ 정책 코드

- 마지막 갈래 — **데이터 프로덕트 구현이 캡슐화하는 코드의 마지막 범주는 암호화·접근 통제·품질·
  규정 준수 같은 다양한 행위적·구조적 정책을 설정하고 실행하는 책임을 지는 코드다** (9장,
  p.156).[^dehghani2022]
- 저자의 예 — **데이터 프로덕트가 프라이버시 분류를 protected로 설정하면 그 데이터는 쓸 때
  암호화되고, 읽는 이가 필요한 권한을 갖고 있음을 검증한 뒤에만 복호화되어 읽힌다. 프라이버시
  등급을 해석·검증하고, 읽는 이의 권한을 확인하고, 데이터를 암호화·복호화하는 등에 관여하는
  코드는 데이터의 흐름 속에서 그리고 데이터 프로덕트의 계산 맥락 안에서 실행된다** (9장,
  p.156).[^dehghani2022]
- 이 코드의 출처는 도메인이 아니다 — **이 코드는 플랫폼이 제공하지만 데이터 프로덕트의 읽기·쓰기
  함수로 흐르는 길에서 호출된다** (9장, p.157).[^dehghani2022]
  [연합 컴퓨테이셔널 거버넌스 원칙](../concepts/federated-computational-governance-principle.md)이
  말하는 "결정은 전역, 실행은 지역"이 아키텍처로 내려온 지점이다.

## 데이터와 메타데이터 — 저자가 그 낱말을 피하는 이유

- 데이터가 존재 이유다 — **분석 데이터에 대한 접근이 데이터 프로덕트가 존재하는 이유다. 데이터
  프로덕트는 자기 도메인 데이터의 수명 주기를 관리한다. 데이터의 성질과 데이터 사용자의 필요에
  따라 파일·테이블·컬럼 등 여러 양식으로 그것에 대한 접근을 제공한다** (9장,
  p.157).[^dehghani2022]
- 분석 데이터가 무엇을 담는지도 규정된다 — **분석 데이터는 일어난 사업의 사실, 관찰된 추세, 또는
  미래에 대한 예측과 권고를 반영한다** (9장, p.157).[^dehghani2022]
- 메타데이터의 수명 주기가 데이터와 다르다는 관찰 — **메타데이터의 수명 주기와 변경 빈도는 그
  타입에 달렸다. 예컨대 데이터 모델 — 의미론이든 구문이든 — 은 덜 자주 바뀌고 빌드 시점에
  바뀐다. 그러나 대부분의 메타데이터 변경은 데이터 프로덕트가 새 데이터를 생성하면서 일어난다.
  데이터의 통계적 성질과 현재 SLO 메트릭 값을 포함해서다** (9장, p.157).[^dehghani2022]
- **저자는 metadata라는 낱말을 의도적으로 쓰지 않는다** — **나는 데이터 메시 어휘에서 메타데이터라는
  용어를 거의 쓰지 않는다. 나는 이 포괄적 만능 용어가 혼란스럽고 심지어 해롭다고 자주 느낀다.
  그것은 각자 의도적 설계와 시스템 지원을 받을 자격이 있는 의미론적으로 서로 다른 많은 개념들을
  metadata라 불리는 온갖 것의 양동이 하나로 융합한다. 이 융합은 시간이 지나면서 뒤엉킨 복잡성이
  되는 취약하고 중앙집중적인 아키텍처로 이어진다. 데이터 메시 아키텍처는 메타데이터와 그 범주·
  타입이 데이터 프로덕트 인터페이스 계약의 일부가 되기를 기대한다** (9장,
  p.157).[^dehghani2022] [메타데이터 관리](../concepts/metadata-management.md)가 그 낱말을
  하나의 관리 대상 범주로 세우는 서술과 갈리는 자리다 — 저자는 메타데이터의 필요를 부정하는 것이
  아니라 **그 낱말이 가리키는 덩어리를 한 시스템이 관리한다는 설계**를 부정한다.
- 생성 주체도 뒤집힌다 — **전통적 데이터 아키텍처로부터의 큰 이탈은 데이터 프로덕트 자신이
  메타데이터를 생성할 책임을 진다는 점이다. 메타데이터가 외부 시스템에 의해 — 흔히 데이터가
  생성된 **뒤에** — 추출·외삽·투영되는 전통적 시스템과 반대다. 전통적 세계에서는 중앙 데이터
  카탈로그 같은 외부 시스템이 모든 데이터셋에서 메타데이터를 추출·수집·서빙하려 시도한다** (9장,
  p.157).[^dehghani2022]

## 플랫폼 의존

- 무엇을 플랫폼이 하고 무엇이 데이터 프로덕트에 남는가 — **플랫폼은 데이터 프로덕트를 짓고·
  배포하고·돌리는 것을 가능하게 한다. 플랫폼이 인프라 자원을 중앙에서 관리하는 한편, 데이터
  프로덕트의 자율적 운영을 지원하기 위해 데이터 프로덕트마다 격리를 두고 자원을 프로비저닝하고
  할당한다** (9장, p.157).[^dehghani2022]
- 격리의 판정 기준이 배포 간섭이다 — **한 데이터 프로덕트의 배포나 갱신이 다른 데이터 프로덕트에
  영향을 주지 않는 것이 중요하다. 예컨대 한 데이터 프로덕트를 그 호스팅 인프라에 배포하는 것이
  공유 인프라 위 다른 것들의 운영을 방해해서는 안 된다** (9장, p.157).[^dehghani2022]
- 데이터 프로덕트가 선언하는 것은 목표 상태다 — **데이터 프로덕트는 자기 기대 목표 상태와
  플랫폼에 대한 의존을 정의하고 통제한다. 예컨대 데이터가 얼마나 오래 보존되어야 하는가나 그
  출력 데이터에 대한 접근 양식의 종류에 관한 기대가 플랫폼 의존으로 표현될 수 있고, 플랫폼이
  올바른 타입의 스토리지를 프로비저닝·관리하는 데 쓴다** (9장, p.158).[^dehghani2022]
  [셀프서브 데이터 플랫폼 원칙](../concepts/self-serve-data-platform-principle.md)이 말하는
  선언적 모델링이 데이터 프로덕트 쪽에서 어떤 모양이 되는지가 이 문장이다.

## 저자 자신이 매긴 성숙도

- 9장 마무리 표(표 9-1)는 저자가 각 논리 구성 요소에 붙인 성숙도 판정이다. 원전에서 드물게
  자기 제안의 미완성을 명시적으로 등급화한 자리다 (9장, pp.168–169).[^dehghani2022]

| 구성 요소 | 저자의 성숙도 판정 |
|---|---|
| 도메인(Domain) | 잘 확립된 개념(well-established) |
| 도메인 운영 인터페이스 | 성숙한 구현이 있다 — REST·GraphQL·gRPC 등 사실상의 표준이 받쳐 준다 |
| 도메인 분석 데이터 인터페이스 | 집필 시점 이 API들의 구현은 맞춤형이거나 플랫폼 특유다 |
| 데이터(프로덕트) 퀀텀 | 집필 시점 맞춤 구현을 갖는 실험적(experimental) 개념 |
| 데이터(프로덕트) 컨테이너 | 실험적 개념, 맞춤 구현 |
| 데이터 프로덕트 사이드카 | 실험적 개념, 맞춤 구현 |
| 입력 데이터 포트 | 기존 이벤트 스트리밍·파이프라인 관리 기술로 맞춤 구현 |
| 출력 데이터 포트 | 벤더 특유의 맞춤 구현. 성숙한 구현은 시간 데이터에 대한 다중 접근 양식을 지원하는 열린 데이터 공유 표준을 요구한다 |
| 발견·관측 가능성 API | 맞춤 구현은 지어졌다. 성숙한 구현은 열린 표준을 요구하고, 일부 표준이 개발 중이다(각주는 OpenLineage를 예로 든다) |
| 제어 포트 | 집필 시점 실험적 |
| 플랫폼 플레인 | 일반적이고 잘 확립된 개념 |
| 데이터 인프라 유틸리티 플레인 | 이 플레인을 구성하는 서비스들은 성숙하고 다수 벤더가 자동 프로비저닝을 지원한다 |
| 데이터 프로덕트 경험 플레인 | 맞춤 구현만 있고 공개된 참조 구현은 없다 |
| 메시 경험 플레인 | 발견·검색 등 일부 서비스의 맞춤 구현만 있고 공개된 참조 구현은 없다 |

- 저자는 논리와 물리의 거리도 열어 둔다 — **구성 요소들은 논리적인 것으로 간주되며, 그 물리적
  구현은 다른 형태를 취할 수 있다. 예컨대 사이드카를 통한 정책 실행이라는 아이디어는 물리적으로
  데이터 퀀텀에 동반하는 프로세스(서비스)로 구현될 수도 있고(동적 결합), 공유 라이브러리로
  구현될 수도 있다(정적 결합)** (9장, p.168).[^dehghani2022]
- 3부 도입은 이 부 전체의 인식적 지위를 미리 밝혀 둔다 — **이 부는 부분적으로 데이터 메시
  아키텍처를 구현한 내 경험에 근거하고 부분적으로 개인 의견에 근거한다. 어떤 개념은 구현되고
  테스트되었으며, 어떤 것은 더 사변적이고 추가 실험과 테스트를 요구한다** (3부 도입,
  pp.140–141).[^dehghani2022] 3부에서 제외된 것도 명시된다 — **이 책에 포함되지 않은 것은
  아키텍처의 물리 계층과 오늘날 아키텍처 구성 요소를 구현하는 데 쓸 수 있는 특정 기술들이다.
  예컨대 데이터 프로덕트 변환 흐름을 관리하는 데 Apache Airflow를 쓸지 Prefect를 쓸지 Azure
  Data Factory를 쓸지는 여기서 범위 밖이다** (3부 도입, p.140).[^dehghani2022]

## 빌려온 원전이 이 KB에 들어왔다

**이 페이지가 정의를 빌려 온 그 책이 이 KB에 들어왔다.** 원전은
[아키텍처 퀀텀](../concepts/architectural-quantum.md)이다. 두 소스가 **서로를 호명하므로** 이 대조는 이 KB가
억지로 붙인 것이 아니다 — 이 페이지가 퀀텀의 출처로 그 책을 지목하고, 그 책은 데이터 메시를
자하마크 데흐가니와 여러 혁신가의 것으로 적고 전문을 이 책으로 넘긴다 (5장,
pp.119–121).[^ford2022-evolutionary]

- **원전이 정의를 두 번 내린다.** 앞의 것은 **독립 배포 가능성과 높은 기능적 응집과 필요한 구조
  요소 전부**라는 세 마디이고 (5장, p.91), 뒤의 것은 거기에 **높은 정적 결합과 동기 동적 결합**을
  더한 네 조건이다 (5장, p.92).[^ford2022-evolutionary]
- **이 페이지가 인용한 것은 앞의 것이다.** 위
  [아키텍처 퀀텀이라는 빌려온 정의](#아키텍처-퀀텀이라는-빌려온-정의)의 직인용을 원전과 맞대 보면
  조건 셋째와 넷째가 들어 있지 않다. **누락이 아니라 앞 정의를 인용한 것이다.**

| 조건 | 원전 | 이 페이지의 데이터 퀀텀 |
|---|---|---|
| 독립 배포 가능성 | 첫째 조건 | 그대로 가져간다 |
| 높은 기능적 응집 | 둘째 조건 | 그대로 가져가되 내용을 분석 변환과 그 결과 공유로 채운다 |
| 높은 정적 결합 | 셋째 조건 | **인용에 없다.** 구조 요소 목록이 그 자리를 채운다 |
| 동기 동적 결합 | 넷째 조건 | **뒤집힌다** — 협력 퀀텀은 비동기 통신과 결과적 일관성으로 협력자와 말한다 |

- **넷째의 뒤집힘이 이 대조의 핵심이다.** 원전의 네 조건짜리 정의는 **동기** 동적 결합을 요구하는데,
  같은 책이 데이터 프로덕트 퀀텀을 다루며 붙이는 이름인 **협력 퀀텀(cooperative quantum)**은
  협력자와 **비동기 통신과 결과적 일관성**으로 말한다고 정의된다 (5장,
  p.123).[^ford2022-evolutionary] 곧 **데이터 퀀텀은 원전의 네 조건짜리 정의를 만족하지 않는
  별도 범주**이고, 원전 저자들이 그 별도 범주에 이름을 준 것이다.
  - **이름 하나가 원전에만 있다.** "협력 퀀텀"이라는 이름과 그 정의는 이 페이지의 소스가 쓰지
    않는 것으로 이 KB가 확인했다. #hypothesis
- **원전이 이 책의 DPQ를 자기 어휘로 요약한다.** 서비스 옆에 붙되 결합된 형태로 팀이 만들고,
  코드와 데이터를 함께 담아 분석·보고 부분에 대한 인터페이스가 되며, **운영상 독립이되 행동과
  데이터가 높게 결합된 집합**이다. 세 종류(원천 정렬·집계·목적 적합)도 적는다 (5장,
  pp.120–121).[^ford2022-evolutionary] **두께가 다를 뿐 어긋나지 않는다** — 원전은 한 절로
  요약하고 전문을 이 책으로 넘긴다.
- **낱말 선택의 변호가 양쪽에 있다.** 이 페이지의 위 [왜 하필 "퀀텀"인가](#왜-하필-퀀텀인가)가
  물리학·라틴어 어원을 대는데, 원전도 같은 변호를 한다 — 라틴어 `quantus`("얼마나 큰" 또는 "얼마나
  많은")에서 왔고 물리학이 가져가기 전에는 법률 쪽이 "요구되거나 허용된 양"을 가리키는 데 썼으며,
  라틴어 어근 때문에 단수가 quantum 복수가 quanta다 (5장, p.91).[^ford2022-evolutionary]

## 저자 자신이 아키텍처 쪽 책에 쓴 같은 단위

**이 페이지의 저자가 공저자로 참여한 2021년 책의 14장이 같은 단위를 아키텍처 어휘로 다시
쓴다.** 위 [빌려온 원전이 이 KB에 들어왔다](#빌려온-원전이-이-kb에-들어왔다)가 2022년 책 5장을
통해 읽은 그 서술의 **원래 자리가 여기**이고, 2022년 5장이 그것을 축약한 것이다. **저자가
겹치므로 이것은 제3자의 해석이 아니라 같은 사람이 다른 독자를 향해 쓴 판**이다.

- **DPQ의 규정** — 서비스 `Alpha`가 행동과 트랜잭션(운영) 데이터를 담을 때, 그 도메인은
  **코드와 데이터를 함께 담고 체계의 분석·보고 부분 전체에 대한 인터페이스 노릇을 하는 데이터
  프로덕트 퀀텀**을 포함한다. **DPQ는 운영상 독립이되 높게 결합된 행동과 데이터의 집합**이다
  (14장, p.391).[^ford2021-hard-parts]
- **DPQ 세 종류** (14장, pp.391–392):[^ford2021-hard-parts]

| 종류 | 무엇을 하는가 |
|---|---|
| `Source-aligned (native) DPQ` | 협력하는 아키텍처 퀀텀(대개 마이크로서비스)을 대신해 분석 데이터를 제공하며 **협력 퀀텀으로 동작한다** |
| `Aggregate DQP` | 여러 입력에서 데이터를 **동기 또는 비동기로** 집계한다. 어떤 집계에는 비동기 요청으로 충분하고, 다른 것에는 집계 DPQ가 원천 정렬 DPQ에 **동기 질의**를 해야 할 수도 있다 |
| `Fit-for-purpose DPQ` | 분석 보고·비즈니스 인텔리전스·기계 학습 같은 **특정 요구를 위해 맞춤 제작**한 것 |

  - **원문 오식** — 둘째 항목의 표제가 `Aggregate DQP`로 인쇄돼 있다(`DPQ`). 같은 오식이
    p.395의 사가에도 한 번 더 나온다(`the DQP cooperative quantum`). 그대로 옮기고 표시한다.
- **DPQ가 도메인 팀 소유라는 것도 못 박힌다** — DPQ는 **그 서비스를 구현하는 책임을 지는 도메인
  팀이 소유하는 컴포넌트**이고, 데이터베이스에 저장된 정보와 **겹치며**, 도메인 행동 일부와
  **비동기로 상호작용할 수 있다.** 분석과 비즈니스 인텔리전스를 위해 **데이터뿐 아니라 행동도
  갖는다** (14장, pp.392–393).[^ford2021-hard-parts]
- **협력 퀀텀의 정의가 여기서 나온다** (14장, p.393):[^ford2021-hard-parts]

  > *Cooperative quantum*
  > An operationally separate quantum that communicates with its cooperator via asynchronous
  > communication and eventual consistency, yet features tight contract coupling with its
  > cooperator and generally looser contract coupling to the analytics quantum, the service
  > responsible for reports, analysis, business intelligence, and so on.

  - 협력하는 두 퀀텀은 **운영상 독립이되 데이터의 두 면**을 나타낸다 — 퀀텀 쪽의 운영 데이터와
    데이터 프로덕트 퀀텀 쪽의 분석 데이터다 (14장, p.393).[^ford2021-hard-parts]
  - **분석 퀀텀(analytics quantum)**은 자기가 필요한 개별 DPQ들에 **정적 퀀텀 결합**을 갖고,
    요청 종류에 따라 동기 호출도 비동기 호출도 한다 — 어떤 DPQ는 **SQL 인터페이스**를 제공해
    동기 질의를 받고, 다른 요구는 여러 DPQ에 걸쳐 정보를 집계한다 (14장,
    p.393).[^ford2021-hard-parts]
  - **2022년 판이 이 정의의 뒷부분을 잘랐다.** `eventual consistency` 뒤의 쉼표와, `the
    analytics quantum`이 무엇인지 밝히는 동격구(`the service responsible for…`)가 2021년
    쪽에만 있다. 사실 주장은 달라지지 않는다.
- **그림 14-1이 본문에 없는 라벨을 담는다.** 이미지 조판이라 렌더해 읽었다 (14장, p.391,
  그림 14-1):[^ford2021-hard-parts] 바깥 점선 상자가 **`Domain (includes both services and
  data product quantum)`**이고 그 안에 `Alpha Data Product Quantum`과 `Service Alpha`가 각각
  컴포넌트 여섯과 `Database` 하나씩을 담고 놓이며, 둘을 잇는 화살표에 **`Cooperative Quanta`**
  라벨이 붙는다. 왼쪽 바깥으로 나가는 화살표 둘(실선과 점선)에는 **`Communication to Data
  Product Aggregator and/or other data product quanta`**가 붙는다. **본문은 이 라벨들을 적지
  않는다.**

### 정의의 네 자리를 결산한다

**위 [빌려온 원전이 이 KB에 들어왔다](#빌려온-원전이-이-kb에-들어왔다)가 열어 둔 실타래가
여기서 닫힌다.** 이 페이지가 인용한 세 마디 정의가 어느 판본의 것인지가 물음이었다.

| 자리 | 인쇄된 아키텍처 퀀텀 정의 | 조건 수 |
|---|---|---|
| ford2021 2장 pp.28–29 | 네 조건 | 넷 |
| ford2022 5장 p.91 | **느슨한 개념 정의** — 독립 배포 · 높은 기능적 응집 · 기능에 필요한 구조 요소 전부 | 셋 |
| ford2022 5장 p.92 | 네 조건 — **ford2021 2장과 낱말 하나까지 같다** | 넷 |
| **ford2021 14장** | **없다** — 정의를 다시 내리지 않고 쓰기만 한다 | — |
| 이 페이지(dehghani2022 9장 p.151) | **ford2022 p.91의 세 마디를 직인용** | 셋 |

- **결산** — 이 페이지가 빌려 온 세 마디 정의는 **2022년 판에만 있는 것**이고, **저자가 공저자로
  참여한 2021년 책의 분석 데이터 장은 퀀텀을 한 번도 정의하지 않는다**(14장 §"The Data Mesh"
  pp.389–394 전문 추출에 `smallest unit`·`independently deployed`·`structural elements`
  0건).[^ford2021-hard-parts] 곧 **정의 표류가 아니라 판본 사이의 추가**이고, 세 자리만
  실재한다.
  - **다만 연대가 어긋난다.** 이 페이지의 소스는 2022년에 나왔고 그 세 마디 정의가 실린
    *Building Evolutionary Architectures* 2판도 2022년이다. **어느 쪽이 먼저인지를 이 KB는
    확인하지 않았고**, 이 페이지의 소스도 판을 특정하지 않은 채 책 이름만 댄다. #hypothesis
- **`contradicts`를 걸지 않았다.** 세 마디와 네 조건은 **최대 하나만 참일 수 있는** 주장이
  아니다 — 뒤의 것이 앞의 것에 조건 둘을 더한 것이고, 그 사실을 2022년 판 자신이 두 정의를
  나란히 인쇄하는 방식으로 드러낸다.

### 어느 결합이 정적이고 어느 결합이 동적인가

**2021년 14장이 이 페이지가 갖지 않은 판정 하나를 더한다** — DPQ의 결합을 그 책의 정적·동적
결합 어휘로 분류하는 것이다 (14장 §"Data Mesh, Coupling, and Architecture Quantum",
p.393):[^ford2021-hard-parts]

- **정적 결합** — 분석 보고는 해법의 필수 기능일 가능성이 높으므로 **DPQ와 그 통신 구현은
  아키텍처 퀀텀의 정적 결합에 속한다.** 마이크로서비스 아키텍처에서 서비스 플레인이 가용해야
  하는 것이, 설계가 메시징을 요구할 때 메시지 브로커가 가용해야 하는 것과 같다.
  - **다만 사이드카 패턴처럼 직교해야 한다** — DPQ는 **서비스 안의 구현 변경에 대해 직교해야
    하고 데이터 플레인과는 별도의 계약을 유지해야 한다.** 그 구조 층은
    [데이터 프로덕트의 포트와 사이드카](../concepts/data-product-ports-and-sidecar.md)에 있다.
- **동적 결합** — **데이터 사이드카는 언제나 결과적 일관성과 비동기성을 함께 갖는 통신 패턴
  가운데 하나를 구현해야 한다.** 지목되는 칸은 **`Parallel Saga(aeo)`(p.346)와
  `Anthology Saga(aec)`(p.349) 둘**이다.
  - **금지가 명시된다** — **데이터 사이드카는 운영 데이터와 분석 데이터를 맞춰 두라는 트랜잭션
    요구를 결코 포함해서는 안 된다.** 그러면 직교 결합 끊김이라는 DPQ의 목적 자체가 무너진다.
  - 데이터 플레인으로 가는 통신도 **일반적으로 비동기여야** 도메인 서비스의 운영 아키텍처
    특성에 주는 충격이 최소가 된다.
    - **원문 오식** — `genearlly`(generally)로 인쇄돼 있다.
  - **이 판정이 이 페이지의 위 [스케일아웃의 축이자 결합의 주체](#스케일아웃의-축이자-결합의-주체)를
    좁힌다.** 그쪽은 정적 결합과 동적 결합 **둘 다 가능하다**고만 적는데, 2021년 14장은
    **동적 결합의 여덟 칸 가운데 둘만 허용하고 여섯을 금지한다.** 어긋나지 않고 더 구체적이다
    — 여덟 칸의 어휘와 칸마다의 기제는 [아키텍처 퀀텀](../concepts/architectural-quantum.md)과
    [트랜잭셔널 사가 패턴](../concepts/transactional-saga-patterns.md)이 갖는다.

### 언제 데이터 메시를 쓰는가

**이 페이지의 소스가 채택 심사를 별도 장으로 다룬다면, 2021년 14장은 아키텍처 조건 하나로
줄여 적는다** (14장 §"When to Use Data Mesh", pp.393–394):[^ford2021-hard-parts]

- **가장 적합한 자리** — **잘 담긴 트랜잭션성과 서비스 사이의 좋은 격리를 갖춘 마이크로서비스
  같은 현대 분산 아키텍처**다. 그런 곳에서 **도메인 팀이 다른 퀀텀들이 소비하는 데이터의 양과
  주기와 품질과 투명성을 스스로 정할 수 있다.**
- **더 어려운 자리** — **분석 데이터와 운영 데이터가 항상 동기화되어 있어야 하는 아키텍처**다.
  분산 아키텍처에서 그것은 벅찬 도전이고, **결과적 일관성을 떠받칠 길을 (아마도 매우 엄격한
  계약과 함께) 찾으면** 다른 어려움을 부과하지 않는 여러 패턴이 열린다.
- **절충표 14-3의 열 머리글과 값을 그대로 옮긴다** (14장, p.394):[^ford2021-hard-parts]

| Advantage | Disadvantage |
|---|---|
| Highly suitable for microservices architectures | Requires contract coordination with data product quantum |
| Follows modern architecture principles and engineering practices | Requires asynchronous communication and eventual consistency |
| Allows excellent decoupling between analytical and operational data | |
| Carefully formed contracts allow loosely coupled evolution of analytical capabilities | |

- **이 조건이 이 페이지의 소스와 어긋나는가.** 어긋나지 않고 **축이 다르다.** 이 페이지의
  소스는 채택 여부를 **조직의 복잡성과 데이터 출처 수 같은 변곡점**으로 심사하고
  ([데이터 메시 변곡점](../concepts/data-mesh-inflection-point.md)·
  [채택 심사](../concepts/data-mesh-adoption-phases.md)), 2021년 14장은 **운영계 아키텍처가
  이미 어떤 모양인가**를 묻는다. **두 소스가 이 자리에서 서로를 호명하지 않는다** — 이 대조는
  이 KB가 세운 읽기다. #hypothesis
  - **2021년 14장이 이 페이지의 소스에 없는 말을 하는가.** 이 KB가 확인한 범위에서 **하나
    있다** — 위 §"어느 결합이 정적이고 어느 결합이 동적인가"의 여덟 칸 제한이다. 나머지(데이터
    메시의 규정·네 원칙·DPQ 세 종류·채택 조건)는 그 책이 자기 전문을 데이터 메시 책으로
    넘기며 요약한 것이다 — **데이터 메시는 폭넓은 주제이고 자하마크 데흐가니의 *Data Mesh*가
    온전히 다룬다**고 저자들 자신이 적는다 (14장, p.390).[^ford2021-hard-parts]
