이 페이지의 질문: **LSM 트리는 어떻게 쓰기를 순차화하고, 그 대가를 읽기에서 어떻게 치르는가.**

## 불변 대 가변

- 장의 문을 여는 인용이 이 구조의 착상을 요약한다 (7장, p.129):[^petrov2019]

> Accountants don't use erasers or they end up in jail.
> —Pat Helland

- 회계사는 기록을 고쳐야 하면 기존 값을 지우는 대신 정정을 담은 새 기록을 만든다. 분기 보고서가
  나오면 직전 분기 결과를 바로잡는 작은 수정이 담길 수 있고, 최종 수치를 얻으려면 기록들을 훑어
  소계를 계산해야 한다 (7장, p.129).[^petrov2019]
- 마찬가지로 **불변 저장 구조는 기존 파일의 수정을 허용하지 않는다** — 테이블은 한 번 쓰이고 다시
  수정되지 않으며, 새 레코드는 새 파일에 덧붙고, 최종 값을 찾으려면(또는 없다고 결론 내리려면)
  여러 파일에서 레코드를 재구성해야 한다. 반대로 가변 저장 구조는 디스크의 레코드를 제자리에서
  고친다 (7장, p.129).[^petrov2019]
- 안팎의 구분이 뚜렷하다 — **내부적으로 불변 파일은 사본을 여럿 담을 수 있고 최신 것이 옛것을
  덮어쓴다. 가변 파일은 대개 최신 값만 담는다. 접근될 때 불변 파일은 처리되고, 중복 사본이
  조정되고, 최신 것이 클라이언트에 반환된다** (7장, p.129).[^petrov2019]
- 이 책은 다른 책·논문처럼 **B-트리를 가변 구조의 전형으로, LSM 트리(Log-Structured Merge Tree)를
  불변 구조의 전형으로** 든다 (7장, p.129).[^petrov2019]
- 최적화 방향이 정반대다 (7장, p.130):[^petrov2019]
  - **인플레이스 갱신 구조는 읽기 성능에 최적화**돼 있다 — 디스크에서 데이터를 찾으면 레코드를 그대로
    반환할 수 있다. 대가는 쓰기 성능이다: 제자리에서 갱신하려면 먼저 디스크에서 찾아야 한다.
  - **추가 전용 저장은 쓰기 성능에 최적화**돼 있다 — 덮어쓰려고 레코드를 찾을 필요가 없다. 대가는
    읽기다: 여러 버전을 가져와 조정해야 한다.
- 가변 B-트리의 구조와 구성 방식 때문에 읽기·쓰기·유지보수 중 I/O 연산 대부분이 임의 접근이다.
  쓰기마다 먼저 레코드를 담은 페이지를 찾아야 하고, 노드 분할과 병합이 이미 쓰인 레코드를
  재배치하며, **페이지의 셀 하나만 고쳐도 페이지 전체를 다시 써야 한다** (7장,
  p.130).[^petrov2019]

## LSM 트리가 하는 일

- **LSM 트리는 버퍼링과 추가 전용 저장으로 순차 쓰기를 달성하는, 가장 인기 있는 불변 온디스크 저장
  구조다.** B-트리와 비슷한 디스크 상주 구조의 변종인데 노드가 완전히 채워지고 순차 디스크 접근에
  최적화돼 있다. Patrick O'Neil과 Edward Cheng의 1996년 논문이 처음 도입했고, 이름은 모든 변경을
  로그 같은 파일에 쓰는 로그 구조 파일시스템에서 왔다 (7장, p.130).[^petrov2019]
- **"merge"라는 말은 불변성 때문에 트리 내용이 병합 정렬과 비슷한 방식으로 합쳐진다는 뜻이다.**
  이 병합은 중복 사본이 차지한 공간을 회수하는 유지보수 때, 그리고 내용을 사용자에게 반환하기 전
  읽기 때 일어난다 (7장, p.131).[^petrov2019]
- 흥미로운 되먹임 하나 (7장, p.131):[^petrov2019]

> LSM Trees write immutable files and merge them together over time. These files usually
> contain an index of their own to help readers efficiently locate data. Even though LSM
> Trees are often presented as an alternative to B-Trees, it is common for B-Trees to be
> used as the internal indexing structure for an LSM Tree's immutable files.

- 불변성이 주는 것 (7장, p.131):[^petrov2019]
  - **순차 쓰기** — 데이터가 한 번의 패스로 디스크에 쓰이고 파일은 추가 전용이다. 가변 구조도 한
    패스로 블록을 미리 할당할 수 있지만(예: ISAM) 이후 접근은 여전히 임의 읽기·쓰기를 요구한다.
  - **단편화 방지** — 레코드를 순차로 배치할 수 있다.
  - **높은 밀도** — 나중에 쓸 레코드나 갱신 레코드가 커질 경우를 위한 여분 공간을 예약하지 않는다.
  - **쓰기 경로에서 디스크 조회 불필요** — 삽입·갱신·삭제가 디스크에서 레코드를 찾을 필요가 없어
    쓰기 성능과 처리량이 크게 개선된다. 대신 중복 내용이 허용되고 충돌은 읽기 시점에 해소된다.
  - **동시 접근의 단순화** — 읽기와 쓰기가 설계상 교차하지 않아 세그먼트 잠금 없이 디스크를 읽고
    쓸 수 있다. 가변 구조는 온디스크 구조 무결성을 지키려고 계층적 잠금과 래치를 쓰고, 여러 동시
    독자를 허용하되 기록자에게는 서브트리 배타 소유를 요구한다.
- **LSM 트리는 쓰기가 읽기보다 훨씬 잦은 애플리케이션에 특히 유용하다** — 데이터량과 유입 속도가
  계속 커지는 현대 데이터 집약 시스템에서 흔한 경우다 (7장, p.131).[^petrov2019]
- 두 구조 모두 정리 작업이 필요하지만 이유가 다르다 — **LSM 트리는 할당된 파일 수가 꾸준히 늘어
  읽기 중 접근하는 파일 수를 최소로 하려고 파일을 병합·재작성해야 하고, 가변 파일은 단편화를 줄이고
  갱신·삭제된 레코드가 차지한 공간을 회수하려고 부분 또는 전체를 다시 써야 한다** (7장,
  pp.131–132).[^petrov2019]

## 가장 단순한 데이터베이스와 해시 색인

kleppmann은 같은 구조에 다른 문으로 들어간다 — 셸 함수 두 개짜리 데이터베이스에서 출발해
그것을 고쳐 나가는 길이다.

- **세상에서 가장 단순한 데이터베이스**가 셸 함수 둘로 구현된다 (4장, p.116):[^kleppmann2026]

  ```sh
  db_set () {
      echo "$1,$2" >> database
  }

  db_get () {
      grep "^$1," database | sed -e "s/^$1,//" | tail -n 1
  }
  ```

- **저장 형식은 매우 단순하다: 각 줄이 쉼표로 구분된 키-값 쌍 하나를 담은 텍스트 파일이다(이스케이핑
  문제를 무시하면 대략 CSV 파일 같다). `db_set` 호출은 매번 파일 끝에 덧붙인다. 키를 여러 번 갱신하면
  옛 버전의 값이 덮어써지지 않는다 — 최신 값을 찾으려면 파일에서 그 키의 마지막 출현을 봐야
  한다**(그래서 `db_get`에 `tail -n 1`이 있다) (4장, p.116).[^kleppmann2026]
- 이 단순한 것이 왜 빠른지 — **`db_set` 함수는 이렇게 단순한 것치고 꽤 좋은 성능을 갖는데, 파일에
  덧붙이는 것이 일반적으로 매우 효율적이기 때문이다. `db_set`이 하는 것과 비슷하게 많은
  데이터베이스가 내부적으로 로그(log)를 쓰는데, 이는 추가 전용 데이터 파일이다** (4장,
  p.117).[^kleppmann2026]
- 낱말의 뜻을 못 박는다 — **로그라는 낱말은 흔히 애플리케이션 로그를 가리키는 데 쓰이지만, 이
  책에서 로그는 더 일반적인 뜻으로 쓰인다: 디스크에 있는 레코드의 추가 전용 열. 사람이 읽을 수
  있어야 하는 것은 아니며, 이진일 수도 있고 데이터베이스 시스템의 내부용일 수도 있다** (4장,
  p.117).[^kleppmann2026]
- 읽기 쪽이 무너진다 — **`db_get` 함수는 레코드가 많으면 성능이 끔찍하다. 키를 조회할 때마다
  처음부터 끝까지 데이터베이스 파일 전체를 스캔해야 한다. 알고리즘 용어로 조회 비용은 O(n)이다:
  데이터베이스의 레코드 수 n을 두 배로 늘리면 조회가 두 배 오래 걸린다** (4장,
  p.117).[^kleppmann2026]
- 그래서 색인이 필요해진다 — **색인(index)은 주 데이터에서 파생된 추가 구조다. 많은 데이터베이스가
  색인을 더하고 지울 수 있게 하며 이는 데이터베이스의 내용에 영향을 주지 않는다 — 질의의 성능에만
  영향을 준다. 추가 구조를 유지하는 데는 오버헤드가 따르며 특히 쓰기에서 그렇다** (4장,
  p.117).[^kleppmann2026]
- 그 거래가 저장 시스템의 중요한 트레이드오프로 명시된다 — **잘 고른 색인은 읽기 질의를 빠르게
  하지만, 모든 색인은 추가 디스크 공간을 소비하고 쓰기를 느리게 하며 때로는 상당히 그렇다. 이런
  이유로 데이터베이스는 보통 기본적으로 모든 것을 색인하지 않고, 애플리케이션의 전형적 질의 패턴에
  대한 지식을 쓰는 사람이 색인을 손으로 고르기를 요구한다** (4장, p.117).[^kleppmann2026]
- 첫 처방이 인메모리 해시 맵이다 — **키마다 그 키의 최신 값을 찾을 수 있는 바이트 오프셋으로 가는
  해시 맵을 메모리에 유지하는 것이다. 새 키-값 쌍을 파일에 덧붙일 때마다 방금 쓴 데이터의 오프셋을
  반영하도록 해시 맵도 갱신한다. 값을 조회할 때는 해시 맵으로 로그 파일의 오프셋을 찾고 그 위치로
  탐색해 값을 읽는다. 데이터 파일의 그 부분이 이미 파일시스템 캐시에 있으면 읽기에 디스크 I/O가 전혀
  필요 없다** (4장, p.118).[^kleppmann2026]
- 그 처방의 문제가 넷으로 열거된다 (4장, pp.118–119):[^kleppmann2026]
  - **덮어써진 옛 로그 항목이 차지한 디스크 공간을 결코 회수하지 못한다. 계속 쓰면 디스크 공간이
    바닥날 수 있다.**
  - **해시 맵이 영속화되지 않으므로 데이터베이스를 재시작할 때 다시 지어야 한다** — 예컨대 로그 파일
    전체를 스캔해 키마다 최신 바이트 오프셋을 찾는 식이다. **데이터가 많으면 재시작이 느려진다.**
  - **해시 테이블이 메모리에 들어가야 한다. 원리상 디스크에 해시 테이블을 유지할 수도 있지만
    불행히도 온디스크 해시 맵을 잘 수행하게 만들기는 어렵다. 임의 접근 I/O가 많이 필요하고, 가득
    찼을 때 키우는 것이 비싸며, 해시 충돌이 성가신 로직을 요구한다.**
  - **범위 질의가 효율적이지 않다.** 예컨대 10000부터 19999까지의 키를 쉽게 훑을 수 없고 해시
    맵에서 키마다 개별로 조회해야 한다.
- 그래서 정렬로 간다 — **실무에서 해시 테이블은 데이터베이스 색인에 그리 자주 쓰이지 않는다. 대신
  키로 정렬된 구조에 데이터를 두는 것이 훨씬 흔하다** (4장, p.119).[^kleppmann2026] 그 구조가
  아래의 SSTable이다.

## 로그 구조 접근 — 네 단계

- 문제 제기 — **SSTable 파일 형식은 추가 전용 로그보다 읽기에 낫지만 쓰기를 더 어렵게 만든다.
  끝에 그냥 덧붙일 수 없는데 그러면 파일이 더 이상 정렬돼 있지 않기 때문이다(키가 우연히 오름차순으로
  쓰이는 경우가 아니라면). 중간 어딘가에 키가 삽입될 때마다 SSTable 전체를 다시 써야 한다면 쓰기가
  너무 비싸질 것이다** (4장, p.120).[^kleppmann2026]
- **이 문제를 로그 구조 접근법(log-structured approach)으로 풀 수 있는데, 이는 추가 전용 로그와
  정렬된 파일 사이의 하이브리드다** (4장, p.120).[^kleppmann2026] 네 단계다 (4장,
  p.120):[^kleppmann2026]
  1. **쓰기가 들어오면 레드-블랙 트리·스킵리스트·트라이 같은 인메모리 정렬 맵 자료 구조에
     더한다. 이 자료 구조들로는 키를 아무 순서로나 삽입하고, 효율적으로 조회하고, 정렬된 순서로
     되읽을 수 있다. 이 인메모리 자료 구조를 멤테이블(memtable)이라 한다.**
  2. **멤테이블이 어떤 임계치(보통 몇 메가바이트)보다 커지면 정렬된 순서로 SSTable 파일로 디스크에
     써 낸다. 이 새 SSTable 파일을 데이터베이스의 가장 최근 세그먼트(segment)라 하고, 더 오래된
     세그먼트들과 나란히 별도 파일로 저장된다. 각 세그먼트는 자기 내용에 대한 별도 색인을 갖는다.
     새 세그먼트가 디스크에 쓰이는 동안 데이터베이스는 새 멤테이블 인스턴스에 계속 쓸 수 있고,
     SSTable 쓰기가 완료되면 옛 멤테이블의 메모리가 해제된다.**
  3. **키의 값을 읽으려면 먼저 멤테이블과 가장 최근 온디스크 세그먼트에서 키를 찾는다. 거기 없으면
     그다음으로 오래된 세그먼트에서 계속 찾아, 키를 찾거나 가장 오래된 세그먼트에 닿을 때까지
     이어진다. 어느 세그먼트에도 키가 나타나지 않으면 데이터베이스에 존재하지 않는 것이다.**
  4. **때때로 배경에서 병합과 컴팩션 프로세스를 돌려 세그먼트 파일들을 합치고 덮어써지거나 삭제된
     값을 버린다.**
- 병합이 무엇을 닮았는지 — **세그먼트 병합은 병합 정렬(mergesort) 알고리즘과 비슷하게 작동한다:
  입력 파일들을 나란히 읽기 시작해 각 파일의 첫 키를 보고, (정렬 순서상) 가장 작은 키를 출력
  파일로 복사하고, 반복한다. 같은 키가 하나 이상의 입력 파일에 나타나면 더 최근 값만 유지한다.
  이는 키로 정렬되고 키당 값이 하나인 새 병합 세그먼트 파일을 만들며, SSTable을 한 번에 한 키씩
  순회할 수 있으므로 최소한의 메모리만 쓴다** (4장, p.120).[^kleppmann2026]
- 멤테이블의 지속성 — **데이터베이스가 크래시했을 때 멤테이블의 데이터가 유실되지 않게 하려고 저장
  엔진은 모든 쓰기가 즉시 덧붙는 별도의 로그를 디스크에 유지한다. 이 로그는 키로 정렬돼 있지
  않지만, 그 유일한 목적이 크래시 후 멤테이블을 복원하는 것이므로 상관없다. 멤테이블이 SSTable로
  쓰일 때마다 로그의 대응 부분을 버릴 수 있다** (4장, p.120).[^kleppmann2026]
- 삭제 — **키와 그에 결부된 값을 지우고 싶으면 데이터 파일에 툼스톤(tombstone)이라 불리는 특별한
  삭제 레코드를 덧붙여야 한다. 로그 세그먼트가 병합될 때 툼스톤은 병합 프로세스에 그 삭제된 키의
  이전 값을 전부 버리라고 말해 준다. 툼스톤이 가장 오래된 세그먼트에 병합되고 나면 버릴 수
  있다** (4장, p.121).[^kleppmann2026]

## 이름과 계보, 그리고 불변 세그먼트가 주는 것

- 계보가 명시된다 — **여기 서술된 알고리즘은 본질적으로 RocksDB·Cassandra·ScyllaDB·HBase에서 쓰이는
  것이며, 모두 구글의 Bigtable 논문(SSTable과 memtable이라는 용어를 도입했다)에서 영감을 받았다. 이
  알고리즘은 원래 1996년에 Log-Structured Merge-tree(LSM 트리)라는 이름으로 발표됐고, 로그 구조
  파일시스템에 대한 앞선 작업 위에 지어졌다. 이런 이유로 정렬된 파일을 병합하고 컴팩션하는 원리에
  기반한 저장 엔진을 흔히 LSM 저장 엔진이라 부른다** (4장, p.121).[^kleppmann2026]
- 세그먼트의 생애 — **LSM 저장 엔진에서 세그먼트 파일은 한 번의 패스로 쓰이고(멤테이블을 써 내거나
  기존 세그먼트를 병합해서) 그 뒤로는 불변이다. 세그먼트의 병합과 컴팩션은 배경 스레드에서 할 수
  있다. 병합이 진행되는 동안에도 병합의 입력 세그먼트를 써서 읽기를 계속 처리할 수 있다. 병합
  프로세스가 완료되면 읽기 요청을 입력 세그먼트 대신 새 병합 세그먼트로 전환하고, 그 뒤 입력 세그먼트
  파일을 삭제할 수 있다** (4장, p.121).[^kleppmann2026]
- 로컬 디스크에 매일 필요가 없다 — **세그먼트 파일이 반드시 로컬 디스크에 저장돼야 하는 것은
  아니다. 오브젝트 스토리지에 쓰기에도 잘 맞는다.** SlateDB와 Delta Lake가 이 접근을 취한다 (4장,
  p.122).[^kleppmann2026]
- 크래시 복구가 단순해진다 — **불변 세그먼트 파일을 갖는 것은 크래시 복구도 단순하게 한다. 멤테이블을
  써 내는 중이거나 세그먼트를 병합하는 중에 크래시가 나면 데이터베이스는 완성되지 않은 SSTable을
  그냥 지우고 처음부터 다시 시작하면 된다. 멤테이블에 쓰기를 영속화하는 로그는 레코드를 쓰는 도중
  크래시가 났거나 디스크가 가득 찼으면 불완전한 레코드를 담을 수 있다. 이런 문제는 보통 로그에
  체크섬을 포함시키고 손상되거나 불완전한 로그 항목을 버림으로써 탐지된다** (4장,
  p.122).[^kleppmann2026]
- 스냅샷도 값싸진다 — **SSTable 세그먼트 파일의 불변한 성격은 어느 시점의 데이터베이스 스냅샷을
  뜨고 싶을 때(예: 백업이나 테스트용 사본 생성) 유용하다. 멤테이블을 써 내고 그 시점에 어떤
  세그먼트 파일이 존재했는지를 기록할 수 있다. 스냅샷의 일부인 파일을 지우지 않는 한 그것들을
  실제로 복사할 필요가 없다. 페이지가 덮어써지는 B-트리에서는 그런 스냅샷을 효율적으로 뜨기가 더
  어렵다** (4장, p.132).[^kleppmann2026]

## 구조 — 멤테이블과 디스크 컴포넌트

- LSM 트리는 작은 메모리 상주 컴포넌트와 큰 디스크 상주 컴포넌트로 이뤄진다. 불변 파일 내용을
  디스크에 쓰려면 먼저 메모리에 버퍼링하고 내용을 정렬해야 한다 (7장, p.132).[^petrov2019]
- **메모리 상주 컴포넌트(흔히 멤테이블memtable)는 가변이다** — 레코드를 버퍼링하고 읽기·쓰기 연산의
  대상이 된다. 크기가 설정 가능한 임계에 닿으면 내용이 디스크에 영속화된다. 멤테이블 갱신은 디스크
  접근을 일으키지 않아 I/O 비용이 없다 (7장, p.132).[^petrov2019]
- 지속성은 별도의 **선행 기록 로그(write-ahead log)** 파일이 보장한다. 레코드가 로그에 덧붙고
  메모리에서 커밋된 뒤에야 클라이언트에 연산이 확인된다 (7장, p.132).[^petrov2019]
- 버퍼링은 메모리에서 이뤄진다 — 모든 읽기·쓰기가 동시 접근을 허용하는 정렬된 자료 구조를 유지하는
  메모리 상주 테이블에 적용된다. 보통 어떤 형태의 인메모리 정렬 트리이거나 비슷한 성능 특성을 주는
  자료 구조다 (7장, p.132).[^petrov2019]
- **디스크 상주 컴포넌트는 읽기 전용이다** — 버퍼링된 내용이 영속화되고 파일은 절대 수정되지 않는다.
  덕분에 단순한 연산으로 생각할 수 있다: 인메모리 테이블에 대한 쓰기, 디스크·메모리 테이블에 대한
  읽기, 병합, 그리고 파일 제거 (7장, p.132).[^petrov2019]

## 이중 컴포넌트와 다중 컴포넌트

- **이중 컴포넌트 LSM 트리**는 불변 세그먼트로 이뤄진 디스크 컴포넌트를 하나만 갖는다. 그 디스크
  컴포넌트는 노드 점유율 100%에 읽기 전용 페이지를 갖는 B-트리로 조직된다 (7장,
  pp.132–133).[^petrov2019]
- 메모리 상주 트리 내용은 부분 단위로 플러시된다. 플러시할 인메모리 서브트리마다 디스크에서 대응
  서브트리를 찾아, 메모리 세그먼트와 디스크 서브트리를 병합한 내용을 디스크의 새 세그먼트에 쓴다.
  플러시가 끝나면 대체된 메모리·디스크 서브트리는 버려지고 병합 결과로 대치되어 기존 디스크 트리에서
  주소 지정 가능해진다 (7장, p.133).[^petrov2019]
- 병합은 디스크 리프 노드를 읽는 반복자와 인메모리 트리 내용을 발맞춰 전진시키는 식으로 구현할 수
  있다. **두 원천이 모두 정렬돼 있으므로 정렬된 병합 결과를 내려면 각 단계에서 두 반복자의 현재
  값만 알면 된다** (7장, p.133).[^petrov2019]
- 서브트리 병합과 플러시를 구현할 때 보장해야 할 것 셋 (7장, p.134):[^petrov2019]
  1. 플러시가 시작되는 즉시 모든 새 쓰기는 새 멤테이블로 가야 한다.
  2. 서브트리 플러시 중에 디스크 상주 서브트리와 플러시 중인 메모리 상주 서브트리 모두 읽기에
     열려 있어야 한다.
  3. 플러시 후 병합된 내용의 공개와 병합되지 않은 디스크·메모리 내용의 폐기는 원자적으로 수행돼야
     한다.
- 다만 저자는 **집필 시점에 알려진 이중 컴포넌트 구현이 없다**고 적는다. 쓰기 증폭 특성으로 설명할
  수 있는데, 병합이 멤테이블 플러시로 발동되므로 비교적 잦기 때문이다 (7장,
  p.134).[^petrov2019]
- **다중 컴포넌트 LSM 트리**는 디스크 상주 테이블을 하나 이상 갖고, 멤테이블 내용 전체를 한 번에
  플러시한다. 플러시가 여러 번 일어나면 디스크 테이블이 여럿 생기고 그 수는 시간이 갈수록 늘기만
  한다. **어느 테이블이 필요한 레코드를 갖고 있는지 늘 알 수는 없으므로 여러 파일에 접근해야 할 수
  있다** (7장, p.134).[^petrov2019]
- 그래서 테이블 수를 최소로 유지하려고 주기적 병합 과정인 **컴팩션(compaction)** 이 발동한다 —
  여러 테이블을 골라 내용을 읽고 병합해 새 합본 파일에 쓰고, 옛 테이블은 새 병합 테이블의 등장과
  동시에 버려진다. 자세한 것은 [LSM 컴팩션](../concepts/lsm-compaction.md)이 다룬다 (7장,
  p.134).[^petrov2019]

## 인메모리 테이블의 전환

- 멤테이블 플러시는 주기적으로 또는 크기 임계로 발동할 수 있다. 플러시 전에 **멤테이블이 전환돼야
  한다** — 새 멤테이블이 할당되어 모든 새 쓰기의 대상이 되고, 옛것은 플러시 상태로 옮겨진다. 이 두
  단계는 원자적으로 수행돼야 한다. 플러시 중인 멤테이블은 내용이 완전히 플러시될 때까지 읽기에
  열려 있고, 그 뒤 새로 쓰인 디스크 테이블에 자리를 내주고 버려진다 (7장, p.135).[^petrov2019]
- 컴포넌트의 상태와 역할 (7장, p.135):[^petrov2019]
  - **현재 멤테이블** — 쓰기를 받고 읽기를 처리한다.
  - **플러시 중인 멤테이블** — 읽기에 열려 있다.
  - **온디스크 플러시 대상** — 내용이 불완전하므로 읽기에 참여하지 않는다.
  - **플러시된 테이블** — 플러시된 멤테이블이 버려지는 즉시 읽기에 열린다.
  - **컴팩션 중인 테이블** — 현재 병합 중인 디스크 테이블.
  - **컴팩션된 테이블** — 플러시된 테이블이나 다른 컴팩션된 테이블에서 만들어진 것.
- 데이터가 메모리에서 이미 정렬돼 있으므로 디스크 테이블은 메모리 내용을 순차로 써 내는 것만으로
  만들어진다. **멤테이블이 완전히 플러시되기 전까지 그 내용의 유일한 디스크 버전은 선행 기록
  로그다.** 완전히 플러시되면 로그를 잘라 낼 수 있고, 플러시된 멤테이블에 적용된 연산이 담긴 로그
  구간을 버릴 수 있다 (7장, p.136).[^petrov2019]

## 갱신과 삭제 — 툼스톤

- LSM 트리에서 삽입·갱신·삭제는 디스크에서 레코드를 찾을 필요가 없다. 대신 중복 레코드가 읽기
  시점에 조정된다 (7장, p.136).[^petrov2019]
- **멤테이블에서 레코드를 없애는 것만으로는 삭제가 되지 않는다.** 다른 디스크·메모리 테이블이 같은
  키의 레코드를 갖고 있을 수 있기 때문이다. 멤테이블에서 항목을 지우기만 하면 삭제가 아무 효과가
  없거나 이전 값을 되살리게 된다 (7장, p.136).[^petrov2019]
  - 예: 플러시된 디스크 테이블에 `k1 → v1`이 있고 멤테이블에 `k1 → v2`가 있을 때, 멤테이블에서 v2를
    지우고 플러시하면 v1이 그 키에 결부된 유일한 값이 되어 **사실상 부활한다**.
- 그래서 **삭제는 명시적으로 기록돼야 한다.** 특정 키에 결부된 레코드의 제거를 나타내는 특별한 삭제
  항목(툼스톤tombstone 또는 dormant certificate라고도 한다)을 삽입하는 방식이다. 조정 과정이 툼스톤을
  집어 가려진 값을 걸러 낸다 (7장, p.137).[^petrov2019]
- 키 하나가 아니라 연속된 키 범위를 지우는 것이 유용할 때가 있고, 이때는 **술어 삭제(predicate
  delete)** 를 쓴다 — 일반 레코드 정렬 규칙에 따라 정렬되는 술어를 담은 삭제 항목을 덧붙이고, 조정
  중에 술어에 맞는 레코드를 건너뛰어 클라이언트에 반환하지 않는다. Apache Cassandra가 이 방식을
  구현하고 **범위 툼스톤(range tombstone)** 이라 부른다 (7장, p.137).[^petrov2019]
- 범위 툼스톤을 쓸 때는 범위 겹침과 디스크 테이블 경계 때문에 **해소 규칙을 신중히 따져야 한다** —
  한 테이블의 시작·끝 툼스톤 쌍이 다른 테이블의 레코드를 최종 결과에서 가릴 수 있다 (7장,
  p.137).[^petrov2019]

## 조회 — 병합-반복

- LSM 트리는 여러 컴포넌트로 이뤄지므로 조회 시 대개 하나 이상의 컴포넌트에 접근하고, 그 내용을
  병합·조정한 뒤에야 클라이언트에 반환할 수 있다 (7장, p.137).[^petrov2019]
- 디스크 테이블 내용이 정렬돼 있으므로 **다중 경로 병합 정렬(multiway merge-sort)** 알고리즘을 쓸 수
  있다. 저장 엔진은 보통 파일 내용을 항해할 커서나 반복자를 제공하는데, 마지막으로 소비한 레코드의
  오프셋을 들고 있고, 반복이 끝났는지 확인할 수 있으며, 다음 레코드를 가져오는 데 쓸 수 있다
  (7장, p.137).[^petrov2019]
- 다중 경로 병합 정렬은 최대 N개(N은 반복자 수) 요소를 담는 우선순위 큐(min-heap 같은)를 쓴다.
  각 반복자의 헤드를 큐에 넣으면 큐의 머리는 모든 반복자의 최솟값이 된다 (7장,
  p.138).[^petrov2019]
- 절차 (7장, p.139):[^petrov2019]
  1. 처음에 각 반복자의 첫 항목으로 큐를 채운다.
  2. 큐에서 가장 작은 요소(머리)를 꺼낸다.
  3. 그 반복자가 소진되지 않았으면 거기서 큐를 다시 채운다.
- 모든 반복자 내용이 정렬돼 있으므로, 직전 최솟값을 냈던 반복자에서 값을 다시 넣어도 **큐가 여전히
  모든 반복자의 최솟값들을 담는다는 불변식이 보존된다.** 어느 반복자가 소진되면 그 반복자의 헤드를
  다시 넣지 않고 진행하고, 질의 조건이 충족되거나 모든 반복자가 소진될 때까지 잇는다 (7장,
  p.138).[^petrov2019]
- 병합-반복 중 같은 키의 레코드를 둘 이상 만날 수 있다. 우선순위 큐와 반복자의 불변식에서, **각
  반복자가 키당 레코드를 하나만 갖고 있는데 큐에 같은 키의 레코드가 여럿 있다면 그것들은 서로 다른
  반복자에서 왔음을 안다** (7장, p.138).[^petrov2019]
- 복잡도는 정렬된 컬렉션 병합과 같다 — **메모리 오버헤드 O(N)**(N은 반복자 수), 반복자 헤드의
  정렬된 컬렉션 유지가 평균 O(log N) (7장, p.140).[^petrov2019]

## 조정

- 병합-반복은 한 측면일 뿐이고, 다른 중요한 측면이 같은 키에 결부된 레코드의 **조정(reconciliation)과
  충돌 해소**다. 앞의 우선순위 큐 구현은 같은 키에 값이 여럿 결부되는 것을 허용하고 조정을 발동시킬
  수 있어야 한다 (7장, p.140).[^petrov2019]
- 어느 것이 우선하는지 알아야 하며, 레코드는 그에 필요한 메타데이터(타임스탬프 같은)를 들고 있다.
  여러 원천에서 온 항목 사이의 순서를 정하고 어느 것이 더 최신인지 알아내려면 타임스탬프를 비교한다.
  **더 높은 타임스탬프의 레코드에 가려진 레코드는 클라이언트에 반환되지도, 컴팩션 중에 쓰이지도
  않는다** (7장, p.140).[^petrov2019]
- 관련 용어 하나. 원문 직인용 (7장, p.140):[^petrov2019]

> An operation that inserts the record to the database if it does not exist, and updates
> an existing one otherwise, is called an *upsert*. In LSM Trees, insert and update
> operations are indistinguishable, since they do not attempt to locate data records
> previously associated with the key in all sources and reassign its value, so we can say
> that we upsert records by default.

## SSTable

kleppmann은 같은 파일 형식을 **희소 색인**과 **블록**이라는 두 낱말로 서술한다.

- 정의 — **키로 정렬된 구조의 한 예가 Sorted Strings Table, 줄여서 SSTable이다. 이 파일 형식도
  키-값 쌍을 저장하지만, 그것들이 키로 정렬돼 있고 각 키가 파일에 한 번만 나타나도록 보장한다**
  (4장, p.119).[^kleppmann2026]
- 그 결과 모든 키를 메모리에 둘 필요가 없어진다 — **SSTable 안의 키-값 쌍을 몇 킬로바이트의
  블록(blocks)으로 묶고 각 블록의 첫 키만 색인에 저장할 수 있다. 키의 일부만 저장하는 이런 종류의
  색인을 희소(sparse)하다고 한다. 이 색인은 SSTable의 별도 부분에 저장되는데, 예컨대 불변
  B-트리나 트라이, 또는 특정 키를 빠르게 조회할 수 있게 하는 다른 자료 구조를 쓴다** (4장,
  p.119).[^kleppmann2026]
- 정렬이 그 사이를 메운다 — 한 블록의 첫 키가 `handbag`이고 다음 블록의 첫 키가 `handsome`일 때
  희소 색인에 없는 `handiwork`를 찾는다면, **정렬 때문에 `handiwork`가 `handbag`과 `handsome`
  사이에 나타나야 한다는 것을 안다. 그래서 `handbag`의 오프셋으로 탐색해 거기서부터 파일을 스캔해
  `handiwork`를 찾으면 된다(파일에 그 키가 없으면 못 찾는다). 몇 킬로바이트짜리 블록은 매우 빠르게
  스캔할 수 있다** (4장, p.119).[^kleppmann2026]
- 블록 단위 압축이 따라온다 — **레코드의 각 블록은 압축될 수도 있다. 디스크 공간을 아끼는 것 말고도
  압축은 CPU 시간을 조금 더 쓰는 대가로 I/O 대역폭 사용을 줄인다** (4장,
  p.119).[^kleppmann2026]

petrov는 같은 형식을 인덱스 파일과 데이터 파일이라는 두 컴포넌트로 서술한다. 두 서술은 층이
다르다 — kleppmann의 "희소 색인"이 petrov의 "인덱스 파일"이 담는 것의 한 구현이다.

- 디스크 상주 테이블은 흔히 **SSTable(Sorted String Table)** 로 구현된다. 이름 그대로 SSTable의
  레코드는 정렬되어 키 순서로 배치된다 (7장, p.145).[^petrov2019]
- SSTable은 보통 두 컴포넌트로 이뤄진다 — **인덱스 파일과 데이터 파일.** 인덱스 파일은 B-트리처럼
  로그 조회를 허용하는 구조나 해시테이블처럼 상수 시간 조회를 허용하는 구조로 구현된다 (7장,
  p.145).[^petrov2019]
- 데이터 파일이 키 순서로 레코드를 담으므로, **인덱싱에 해시테이블을 써도 범위 스캔이 막히지
  않는다** — 해시테이블은 범위의 첫 키를 찾는 데만 쓰이고 범위 자체는 범위 술어가 맞는 동안 데이터
  파일에서 순차적으로 읽힌다 (7장, p.145).[^petrov2019]
- 인덱스 컴포넌트는 키와 데이터 엔트리(실제 레코드가 있는 데이터 파일 안의 오프셋)를, 데이터
  컴포넌트는 연결된 키-값 쌍을 담는다. 차이는 **셀이 순차적으로 쓰이고 SSTable 수명 동안 수정되지
  않는다는 것**이다. 인덱스 파일이 데이터 파일의 레코드를 가리키는 포인터를 담으므로 인덱스가
  만들어지는 시점에 오프셋이 알려져 있어야 한다 (7장, pp.145–146).[^petrov2019]
- 컴팩션 중에는 인덱스 컴포넌트에 접근하지 않고 데이터 파일을 순차적으로 읽을 수 있다 — 레코드가
  이미 정렬돼 있기 때문이다. **컴팩션 대상 테이블들의 순서가 같고 병합-반복이 순서 보존이므로,
  병합 결과 테이블도 한 번의 패스로 레코드를 순차로 써서 만들어진다. 파일이 완전히 쓰이는 즉시 그
  파일은 불변으로 간주된다** (7장, p.146).[^petrov2019]
- LSM 인덱싱의 흥미로운 발전 하나가 Apache Cassandra의 **SASI(SSTable-Attached Secondary
  Indexes)** 다. 기본 키뿐 아니라 다른 필드로도 내용을 인덱싱하려고 인덱스 구조와 그 수명 주기를
  SSTable 수명 주기에 묶어 SSTable마다 인덱스를 만든다. 멤테이블이 플러시될 때 SSTable 기본 키
  인덱스와 함께 보조 인덱스 파일이 만들어진다. LSM 트리가 메모리에 데이터를 버퍼링하므로 SASI는
  멤테이블 내용을 인덱싱하는 별도의 인메모리 구조도 유지한다. **SSTable 수명 주기에 얹는 이점은
  멤테이블 플러시나 컴팩션 중에 인덱스를 만들 수 있다는 것**이다 (7장, p.146).[^petrov2019]

## 스킵리스트와 디스크 접근

- 메모리에 정렬된 데이터를 두는 자료 구조는 여럿인데, 단순함 때문에 최근 인기를 얻은 것이
  **스킵리스트(skiplist)** 다. 구현 난도는 단일 연결 리스트보다 크게 높지 않으면서 확률적 복잡도
  보장이 탐색 트리에 가깝다 (7장, pp.148–149).[^petrov2019]
- 스킵리스트는 삽입·갱신에 회전이나 재배치를 요구하지 않고 **확률적 균형**을 쓴다. 노드가 작고
  메모리에 임의로 할당되므로 인메모리 B-트리보다 대체로 캐시 친화적이지 않다 (7장,
  p.149).[^petrov2019]
- 높이가 다른 노드들이 연결 계층을 이뤄 항목 범위를 건너뛸 수 있게 한다. **노드 높이는 난수 함수로
  정해지고 삽입 시에 계산된다.** 같은 높이의 노드가 레벨을 이루며, 무한 성장을 막으려고 레벨 수에
  상한을 둔다. 레벨마다 노드 수가 지수적으로 적어진다 (7장, p.149).[^petrov2019]
- Apache Cassandra는 보조 인덱스 멤테이블 구현에, WiredTiger는 일부 인메모리 연산에 스킵리스트를
  쓴다 (7장, p.150).[^petrov2019]
- 테이블 내용 대부분이 디스크에 있고 저장 장치가 블록 단위 접근을 허용하므로 많은 LSM 구현이 디스크
  접근과 중간 캐싱에 페이지 캐시를 쓴다. **가장 눈에 띄는 차이는 메모리 내용이 불변이라 동시 접근에
  추가 잠금이나 래치가 필요 없다는 것**이다. 참조 계수로 현재 접근 중인 페이지가 축출되지 않게 하고,
  컴팩션 중 파일이 제거되기 전에 진행 중인 요청이 끝나게 한다 (7장, p.150).[^petrov2019]
- 또 다른 차이는 **LSM 트리의 레코드가 반드시 페이지에 정렬되지는 않는다는 것**이다. 포인터도 페이지
  ID가 아니라 절대 오프셋으로 구현할 수 있다. 어떤 레코드는 페이지 경계를 넘어 여러 페이지를 메모리에
  올려야 한다 (7장, p.150).[^petrov2019]
- 압축(compression)도 적용되는데, LSM 테이블이 불변이고 대체로 한 번의 패스로 쓰인다는 점이 다르다.
  페이지 단위로 압축하면 압축된 페이지가 원본보다 작아 페이지에 정렬되지 않으므로, **압축된 페이지의
  오프셋과 크기를 저장하는 간접 계층**이 있어야 주소 지정이 된다 (7장, p.151).[^petrov2019]

## 정렬을 포기한 변종

- 지금까지의 구조는 데이터를 순서대로 저장한다. **정렬 없는 저장소는 대체로 별도의 로그를 요구하지
  않고, 레코드를 삽입 순서로 저장해 쓰기 비용을 줄인다** (7장, p.152).[^petrov2019]
- **Bitcask**(Riak에서 쓰이는 저장 엔진 중 하나)는 정렬 없는 로그 구조 저장 엔진이다. 버퍼링에
  멤테이블을 쓰지 않고 레코드를 로그 파일에 직접 저장한다 (7장, p.153).[^petrov2019]
  - 값을 검색 가능하게 하려고 **keydir**이라는 자료 구조를 쓰는데, 키마다 최신 레코드의 참조를
    들고 있다. 옛 레코드는 디스크에 남아 있을 수 있지만 keydir에서 참조되지 않고 컴팩션 중에
    가비지 컬렉션된다. keydir는 인메모리 해시맵이며 **시작 시 로그 파일에서 다시 지어야 한다.**
  - 쓰기는 키와 레코드를 로그 파일에 순차로 덧붙이고 새 위치의 포인터를 keydir에 넣는다. 읽기는
    keydir로 키를 찾아 포인터를 따라간다. **어느 순간에도 keydir에는 키당 값이 하나뿐이므로 포인트
    질의는 여러 원천의 데이터를 병합할 필요가 없다.**
  - 레코드가 로그 파일에 직접 저장되므로 **별도의 선행 기록 로그를 둘 필요가 없어 공간 오버헤드와
    쓰기 증폭이 함께 줄어든다.** 대가는 keydir와 데이터 파일 모두 정렬돼 있지 않아 **범위 스캔을
    제공하지 못한다는 것**이다. 그리고 모든 키를 메모리에 두고 시작 시 keydir를 다시 짓는 것이 어떤
    용도에서는 결정적 결함이 될 수 있다 (7장, pp.153–154).
- **WiscKey**는 정렬을 가비지 컬렉션에서 떼어 낸다 — 키는 LSM 트리에 정렬해 두고, 레코드는 vLog(value
  log)라는 정렬 없는 추가 전용 파일에 둔다. **키는 대체로 레코드보다 훨씬 작으므로 키를 컴팩션하는
  것이 훨씬 효율적이다.** 갱신·삭제 비율이 낮아 가비지 컬렉션으로 회수할 공간이 많지 않은 용도에
  특히 유용하다 (7장, p.154).[^petrov2019]
  - 어려움은 vLog 데이터가 정렬돼 있지 않아 **범위 스캔이 임의 I/O를 요구한다**는 것이다. WiscKey는
    SSD 내부 병렬성으로 블록을 병렬 프리페치해 비용을 줄이지만, 블록 전송 관점에서는 여전히 비싸다 —
    범위 스캔에서 레코드 하나를 가져오려고 그것이 있는 페이지 전체를 읽어야 한다.
  - vLog 전체를 훑지 않으려고 살아 있는 키를 담은 vLog 구간 정보를 가진 head·tail 포인터를 쓴다.
    다만 vLog 데이터가 정렬돼 있지 않고 생존 정보를 담지 않아 **어느 값이 살아 있는지 알려면 키 트리를
    훑어야 한다** — 전통적 LSM 트리가 키 인덱스에 접근하지 않고 컴팩션 중에 해소할 수 있는 것과
    대비되는 추가 복잡도다 (7장, p.155).

## 동시성

- LSM 트리의 주된 동시성 난점은 **테이블 뷰 전환**(플러시와 컴팩션 중에 바뀌는 메모리·디스크 테이블
  모음)과 **로그 동기화**다 (7장, p.155).[^petrov2019]
- 플러시 중 지켜야 할 규칙 (7장, p.156):[^petrov2019]
  - 새 멤테이블이 읽기·쓰기에 열려야 한다.
  - 옛(플러시 중인) 멤테이블이 읽기에 계속 보여야 한다.
  - 플러시 중인 멤테이블이 디스크에 쓰여야 한다.
  - 플러시된 멤테이블의 폐기와 플러시된 디스크 테이블의 등장이 **원자적 연산**으로 수행돼야 한다.
  - 플러시된 멤테이블에 적용된 연산의 로그 항목을 담은 선행 기록 로그 세그먼트를 버려야 한다.
- 동기화 지점은 셋으로 정리된다 — **멤테이블 전환**(이후 모든 쓰기가 새 멤테이블로 가고 옛것은 읽기에
  남는다), **플러시 마무리**(테이블 뷰에서 옛 멤테이블을 플러시된 디스크 테이블로 대치), **선행 기록 로그
  절단**(플러시된 멤테이블에 결부된 로그 세그먼트 폐기) (7장, p.156).[^petrov2019]
- 이 연산들은 정확성에 심각한 함의를 갖는다 — **옛 멤테이블에 계속 쓰면 데이터 손실이 날 수 있고**(이미
  플러시된 구간에 쓰는 경우), **옛 멤테이블을 디스크 짝이 준비될 때까지 읽기에 남겨 두지 않으면 결과가
  불완전해진다** (7장, p.156).[^petrov2019]
- 로그 절단도 플러시와 조율돼야 한다. **플러시가 끝나기 전에 로그 세그먼트를 버리고 노드가 크래시하면 로그
  내용이 재생되지 않아 그 세그먼트의 데이터가 복원되지 않는다** (7장, pp.156–157).[^petrov2019]
