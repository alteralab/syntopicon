# 왜 카프카인가

하나의 질문: **발행/구독 메시징 시스템의 선택지는 많은데, 무엇이 아파치 카프카를
좋은 선택으로 만드는가** (1장, p.10).[^shapira2021]

## 다중 프로듀서

- 카프카는 여러 프로듀서를 매끄럽게 처리한다 — 클라이언트가 여러 토픽을 쓰든 하나의
  토픽을 쓰든 상관없다 (1장, p.10).[^shapira2021]
- 그래서 **여러 프론트엔드 시스템의 데이터를 모아 일관되게 만드는 데 적격**이다
  (1장, p.10).[^shapira2021]
- 예: 여러 마이크로서비스로 콘텐츠를 서빙하는 사이트가, 모든 서비스가 공통 형식으로
  쓸 수 있는 페이지 뷰 토픽 하나를 둔다. 컨슈머 애플리케이션은 애플리케이션마다
  하나씩인 여러 토픽을 조율해 소비할 필요 없이 **사이트 전체의 페이지 뷰 스트림
  하나만** 받으면 된다 (1장, p.10).[^shapira2021]

## 다중 컨슈머

- 카프카는 여러 컨슈머가 서로 간섭 없이 어떤 메시지 스트림이든 읽도록 설계됐다
  (1장, p.10).[^shapira2021]
- 대조점이 결정적이다: **한 클라이언트가 소비하면 다른 누구도 그 메시지를 쓸 수 없게
  되는 많은 큐 시스템과 반대다** (1장, p.10).[^shapira2021]
- 동시에 여러 카프카 컨슈머가 [그룹의 일원](../concepts/producers-and-consumers.md)으로
  묶여 스트림을 나눠 읽을 수도 있다 — 이 경우 주어진 메시지는 그룹 전체에 대해 한 번만
  처리된다 (1장, p.10).[^shapira2021]

## 디스크 기반 보존

- 지속성 있는 메시지 보존 덕분에 **컨슈머가 항상 실시간으로 일할 필요가 없다** (1장,
  p.11).[^shapira2021]
- 메시지는 디스크에 쓰이고 설정 가능한 보존 규칙과 함께 저장되며, 이 옵션은 토픽별로
  고를 수 있다 — 스트림마다 컨슈머의 필요에 따라 다른 보존 기간을 갖는다 (1장,
  p.11).[^shapira2021]
- 여기서 오는 것 (1장, p.11):[^shapira2021]
  - 컨슈머가 느린 처리나 트래픽 폭주로 뒤처져도 데이터 유실 위험이 없다.
  - 컨슈머 쪽 유지보수를 위해 애플리케이션을 잠시 내려도 프로듀서 쪽에 메시지가 밀리거나
    유실될 걱정이 없다.
  - 컨슈머를 멈춰 두면 메시지는 카프카에 남아 있고, 재시작하면 **멈춘 지점부터 유실
    없이** 이어서 처리한다.

## 확장성

- 유연한 확장성 덕에 어떤 크기의 데이터든 다루기 쉽다 (1장, p.11).[^shapira2021]
- 성장 경로: 개념 증명용 브로커 한 대 → 브로커 3대의 소규모 개발 클러스터 → 데이터가
  커지면서 수십, 수백 대 브로커의 프로덕션 클러스터 (1장, p.11).[^shapira2021]
- **확장 작업은 클러스터가 온라인인 상태에서 수행되며 시스템 전체의 가용성에 영향을
  주지 않는다** (1장, p.11).[^shapira2021]
- 여러 브로커로 이뤄진 클러스터는 개별 브로커 장애를 견디면서 계속 클라이언트를
  서빙한다. 동시다발 장애를 더 견뎌야 하는 클러스터는 복제 팩터(replication factor)를
  높게 설정한다 (1장, p.11).[^shapira2021]

## 고성능

- 앞의 특징들이 합쳐져 카프카를 **높은 부하에서 뛰어난 성능을 내는 발행/구독 메시징
  시스템**으로 만든다 (1장, p.11).[^shapira2021]
- 프로듀서·컨슈머·브로커 모두 매우 큰 메시지 스트림을 다루도록 확장할 수 있고,
  그러면서도 **생산 시점부터 컨슈머가 쓸 수 있게 되기까지 1초 미만(subsecond)의
  메시지 지연**을 제공한다 (1장, p.11).[^shapira2021]

## 플랫폼 기능

- 코어 아파치 카프카 프로젝트에는 개발자가 자주 하는 작업을 훨씬 쉽게 만드는 스트리밍
  플랫폼 기능이 추가됐다 (1장, p.11).[^shapira2021]
- 다만 **YARN처럼 구조화된 런타임 환경을 포함하는 완전한 플랫폼은 아니다** — 탄탄한
  기반과 실행 위치의 유연성을 주는 API·라이브러리 형태다 (1장, p.11).[^shapira2021]
- 두 축 (1장, pp.11–12):[^shapira2021]
  - Kafka Connect: 원천 데이터 시스템에서 카프카로 데이터를 당겨 오거나, 카프카의
    데이터를 싱크 데이터 시스템으로 밀어 넣는 작업을 돕는다.
  - Kafka Streams: 확장 가능하고 내결함성(fault tolerant) 있는 스트림 처리
    애플리케이션을 쉽게 개발하는 라이브러리다.
