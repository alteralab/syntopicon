하나의 질문: **GraphQL은 다른 그래프 질의 언어들과 무엇이 다르며, 왜 일부러 표현력을
줄였는가.**

## 무엇을 위한 언어인가

- 위치부터 다르다 — **GraphQL은 설계상 이 장에서 본 다른 언어들보다 훨씬 제한적인 질의
  언어다. 그것은 OLTP 질의를 위한 것이며, 그 목적은 사용자 기기에서 도는 클라이언트
  소프트웨어(모바일 앱이나 자바스크립트 웹 앱 프런트엔드 같은)가 UI를 렌더링하는 데 필요한
  필드를 담은, 특정 구조의 JSON 문서를 요청할 수 있게 하는 것이다** (3장,
  pp.98–99).[^kleppmann2026]
- 무엇을 사는가와 그 대가 — **GraphQL 인터페이스는 개발자가 서버 쪽 API를 바꾸지 않고 클라이언트
  코드의 질의를 빠르게 바꿀 수 있게 해 준다. 그러나 그 유연성에는 비용이 따른다. GraphQL을
  채택하는 조직은 흔히 그 질의를 내부 서비스에 대한 요청(보통 REST나 gRPC를 쓴다)으로 변환하는
  도구가 필요하다. 인가(authorization)·속도 제한·성능 문제도 추가적인 걱정거리다** (3장,
  p.99).[^kleppmann2026]

## 의도적으로 제한된 언어

- **이 언어는 의도적으로 제한돼 있는데, GraphQL 질의가 신뢰할 수 없는 출처에서 오기 때문이다.
  그것은 실행이 비쌀 수 있는 어떤 것도 허용하지 않는다. 그러지 않으면 사용자가 (아마 의도치
  않게) 비싼 질의를 많이 돌려 서버에 서비스 거부 상태를 일으킬 수 있기 때문이다** (3장,
  p.99).[^kleppmann2026]
- 구체적으로 두 가지가 막혀 있다 — **특히 GraphQL은 재귀 질의를 허용하지 않으며(Cypher·SPARQL·
  SQL·Datalog와 달리), "미국에서 태어나 지금 유럽에 사는 사람 찾기" 같은 임의의 검색 조건도
  허용하지 않는다 — 서비스 소유자가 그런 검색 기능을 제공하기로 명시적으로 선택하지 않는 한
  그렇다** (3장, p.99).[^kleppmann2026] 그 재귀가 다른 언어에서 어떻게 표현되는지는
  [그래프 질의 언어](../concepts/graph-query-languages.md)에 있다.

## 질의와 응답의 모양

- **그럼에도 GraphQL은 유용하다.** 저자들이 든 예는 **디스코드나 슬랙 같은 그룹 채팅
  애플리케이션**이다. **질의는 사용자가 접근할 수 있는 모든 채널을 요청하며, 채널 이름과 각
  채널의 가장 최근 메시지 50개를 포함한다. 각 메시지에 대해 질의는 타임스탬프, 메시지 내용,
  그리고 발신자의 이름과 프로필 사진 URL을 요청한다. 메시지가 다른 메시지에 대한 답글이면
  질의는 그 메시지의 발신자 이름과 내용도 요청한다**(답글 위에 작은 글씨로 렌더링되어 맥락을
  제공할 수 있다) (3장, p.99, 예제 3-13):[^kleppmann2026]

  ```graphql
  query ChatApp {
    channels {
      name
      recentMessages(latest: 50) {
        timestamp
        content
        sender {
          fullName
          imageUrl
        }
        replyTo {
          content
          sender {
            fullName
          }
        }
      }
    }
  }
  ```

- 응답의 성질 — **응답은 질의의 구조를 그대로 비추는 JSON 문서다. 그것은 요청된 속성을 정확히
  담으며 그 이상도 이하도 아니다. 이 접근은 서버가 사용자 인터페이스를 렌더링하기 위해
  클라이언트가 어떤 속성을 필요로 하는지 알 필요가 없다는 이점을 갖는다 — 클라이언트가 필요한
  것을 그냥 요청할 수 있다** (3장, p.100).[^kleppmann2026]
- 그 이점의 실물 — **예컨대 이 질의는 replyTo 메시지 발신자의 프로필 사진 URL을 요청하지 않지만,
  UI가 그 프로필 사진을 포함하도록 바뀐다면 클라이언트가 필요한 imageUrl 속성을 질의에 더하는
  것만으로 충분하고 서버 쪽 변경은 필요 없다** (3장, p.100).[^kleppmann2026]

## 중복을 받아들이는 선택

- **이 예에서 메시지 발신자의 이름과 이미지 URL은 메시지 객체에 직접 끼워 넣어져 있다. 같은
  사용자가 여러 메시지를 보내면 이 정보가 메시지마다 반복된다. 원칙적으로 이 중복을 줄이는 것이
  가능하겠지만, GraphQL은 요청된 데이터에 기반해 UI를 렌더링하기 더 단순하게 만들기 위해 더 큰
  응답 크기를 받아들이는 설계 선택을 한다** (3장, p.100).[^kleppmann2026]
- **replyTo 필드도 마찬가지다 — 둘째 메시지가 첫째에 대한 답글이라 내용과 발신자 이름이 replyTo
  아래에 중복된다. 대신 답글 대상 메시지의 ID를 반환할 수도 있겠지만, 그러면 그 ID가 반환된 최근
  50개 메시지에 없을 경우 클라이언트가 서버에 추가 요청을 해야 한다. 내용을 중복시키는 것이
  데이터를 다루기 훨씬 단순하게 만든다** (3장, p.100).[^kleppmann2026] 같은 트레이드오프의
  일반형은 [정규화와 비정규화](../concepts/normalization-and-denormalization.md)에 있다.

## 서버 쪽은 정규화돼 있어도 된다

- **서버의 데이터베이스는 데이터를 더 정규화된 형태로 저장하고 질의를 처리하기 위해 필요한
  조인을 수행할 수 있다. 예컨대 서버는 메시지를 발신자의 사용자 ID, 그리고 그것이 답글인 메시지의
  ID와 함께 저장할 수 있다. 앞의 질의 같은 것을 받으면 서버는 그 ID들을 풀어 그것이 가리키는
  레코드를 찾는다. 다만 GraphQL 스키마에 명시적으로 선언된 조인만 클라이언트가 요청할 수 있다**
  (3장, p.101).[^kleppmann2026]
- 마지막 판정 — **GraphQL 질의에 대한 응답이 문서 데이터베이스의 응답과 비슷해 보이고 이름에
  "그래프"가 들어가지만, GraphQL은 어떤 종류의 데이터베이스 — 관계형·문서·그래프 — 위에도 구현될
  수 있다** (3장, p.101).[^kleppmann2026]

## REST와의 관계

- 데이터 엔지니어링 개론이 붙이는 위치 — **GraphQL은 애플리케이션 데이터를 위한 질의 언어이자
  일반 REST API의 대안으로 페이스북에서 만들어졌다. REST API가 일반적으로 질의를 특정 데이터
  모델로 제한하는 반면, GraphQL은 단일 요청에서 여러 데이터 모델을 회수할 가능성을 연다. 이는
  REST보다 더 유연하고 표현적인 질의를 허용한다. GraphQL은 JSON을 중심으로 지어져 있고 JSON
  질의를 닮은 모양으로 데이터를 돌려준다** (5장, p.175).[^reis2022]
- 둘 중 하나를 고르는 문제가 아니다 — **REST와 GraphQL 사이에는 일종의 성전 같은 것이 있어
  어떤 엔지니어링 팀은 한쪽 편이고 어떤 팀은 양쪽을 쓴다. 현실에서 엔지니어는 원천 시스템과
  상호작용하면서 둘 다 마주칠 것이다** (5장, p.175).[^reis2022]

## 마이크로서비스 쪽에서 본 같은 언어

위 절들이 GraphQL을 **질의 언어들 사이의 한 자리**로 놓는다면, 2021년 마이크로서비스
실무서는 그것을 **마이크로서비스 사이 통신 기술의 후보 넷 중 하나**로 놓고 채점한다.
그래서 더해지는 것이 **어디에 두는 기술인가**와 **무엇이 아직 아픈가**다.

- 왜 인기를 얻었는가 — **클라이언트 쪽 기기가 질의를 정의해 같은 정보를 얻으려고 여러 번
  요청할 필요를 없앨 수 있다**는 한 가지를 잘하기 때문이다. 그 이득이 둘로 적힌다 —
  **제약이 큰 클라이언트 기기의 성능을 크게 개선할 수 있고**, **서버 쪽에 맞춤 집계를 구현할
  필요를 없앨 수 있다** (5장 §GraphQL, p.133).[^newman2021]
  - 저자가 드는 실물은 모바일 화면 하나다 — 고객 정보 몇 필드와 최근 주문 다섯 건의 날짜·
    금액·배송 상태만 필요한 화면을 위해 하류 마이크로서비스 둘을 각각 부르면 **호출이 여러
    번이 되고 실제로 필요하지 않은 정보까지 끌어오게 된다.** 모바일에서는 그것이 **데이터
    요금과 시간**의 낭비다 (5장, p.133).[^newman2021]
- 배치가 어떻게 되는가 — **클라이언트 기기에 GraphQL 엔드포인트를 노출하는 마이크로서비스가
  하나 필요하고**, 그 엔드포인트가 **모든 클라이언트 질의의 입구**이면서 클라이언트가 쓸
  스키마를 노출한다 (5장, p.133).[^newman2021]

### 남아 있는 도전 다섯

- **언어 지원은 더 이상 문제가 아니다** — 초기에는 자바스크립트가 유일한 선택이었으나 지금은
  주요 기술이 모두 명세를 지원하고, 구현들도 크게 좋아져 **몇 해 전보다 훨씬 덜 위험한
  선택**이 됐다 (5장 §Challenges, p.133).[^newman2021]
  - 버전 조건: 2021년 저술 시점. "지금"과 "몇 해 전"의 기준이 그 시점이다.
- **동적으로 바뀌는 질의가 서버 부하를 만든다** — 저자는 그 능력 때문에 **GraphQL 질의가 서버
  쪽에 상당한 부하를 일으킨 팀들의 이야기를 들었다**고 적고, SQL과 견준다. 비싼 SQL 문이
  데이터베이스에 문제를 일으키는 것과 같은 문제인데 **갈리는 지점은 도구다** — SQL에는 질의
  계획기(query planner)가 있어 문제 질의를 진단하도록 돕지만 **GraphQL에서 같은 문제는 추적하기
  더 어렵다.** 서버 쪽 요청 스로틀링이 후보 해법이나, **호출의 실행이 여러 마이크로서비스에
  흩어질 수 있어 간단하지 않다** (5장, pp.133–134).[^newman2021]
  - **이것이 위 [의도적으로 제한된 언어](#의도적으로-제한된-언어) 절과 겨루지 않는다.**
    그쪽이 말하는 것은 **언어 설계가 무엇을 금지하는가**(재귀 질의와 임의 검색 조건)이고,
    이쪽이 말하는 것은 **허용된 질의가 여러 하류 서비스로 펼쳐질 때의 실제 비용과 그 진단
    가능성**이다. 금지 목록은 질의의 모양을 묶을 뿐 비용의 상한을 주지 않으므로 두 서술은
    같은 방향으로 겹친다 — 그쪽도 속도 제한과 성능을 걱정거리로 적어 두었다. 모순 쌍으로
    세우지 않았다.
- **캐싱이 REST보다 복잡하다** — REST 기반 API에서는 응답 헤더로 클라이언트 기기나 CDN 같은
  중간 캐시가 응답을 캐시하게 할 수 있지만 **GraphQL에서는 같은 방식이 되지 않는다.** 저자가
  본 조언은 **반환되는 자원마다 ID를 붙이고 클라이언트 기기가 그 ID에 대해 요청을 캐시하게
  하는 것**인데(한 GraphQL 질의가 여러 자원을 담을 수 있다는 점을 함께 적는다), 그러면
  **CDN이나 캐싱 리버스 프록시를 쓰는 일이 추가 작업 없이는 대단히 어려워진다** (5장,
  p.134).[^newman2021]
  - 저자의 판정이 세다 (5장, p.134):[^newman2021]

    > caching feels like it was either consciously or unconsciously ignored as part of the
    > initial development of GraphQL

  - 다만 조건을 붙인다 — 질의가 **특정 사용자에게 고도로 특유한** 성질이면 캐시 적중률이
    낮을 것이므로 요청 수준 캐싱의 부재가 결격 사유가 아닐 수 있다. 그래도 저자는 **결국
    클라이언트 기기에 혼합 해법**(일반적인 요청은 REST로, 나머지는 GraphQL로)이 남을지
    모르겠다고 적는다 (5장, p.134).[^newman2021]
  - 버전 조건: 2021년 저술 시점. 저자가 구현별 해법의 예로 드는 것은 자바스크립트 Apollo
    구현이다. 이 KB는 그 구현의 문서를 반입하지 않았다.
- **쓰기가 읽기만큼 맞지 않는다** (5장, p.134):[^newman2021]

  > while GraphQL theoretically can handle writes, it doesn't seem to fit as well as for reads.

  - 그 결과로 **읽기에는 GraphQL을, 쓰기에는 REST를 쓰는** 팀들이 생긴다 (5장,
    p.134).[^newman2021]
- **마지막 항이 주관적이라고 저자가 스스로 밝힌다** (5장, p.134):[^newman2021]

  > GraphQL makes it feel like you are just working with data, which can reinforce the idea
  > that the microservices you are talking to are just wrappers over databases.

  - 저자는 GraphQL을 **데이터베이스에서 데이터를 꺼내는 일반 API로 설계된 OData와 견주는
    사람들**을 여럿 봤다고 적고, 마이크로서비스를 데이터베이스 위의 껍데기로 다루는 착상이
    문제적이라는 자기 책의 논지를 되부른다. 조문은 **마이크로서비스는 네트워크 인터페이스로
    기능을 노출하고**, 그 기능 일부가 데이터를 요구하거나 데이터를 내놓더라도 **자기 내부
    로직과 행동을 가져야 한다**는 것이다. 그래서 처방이 하나 나온다 — **GraphQL API가 밑에
    깔린 마이크로서비스의 데이터 저장소에 결합되지 않게 하는 것이 필수적이다** (5장,
    p.134).[^newman2021]

### 어디에 쓸 것인가

- 자리 — **체계의 경계에서 외부 클라이언트에 기능을 노출하는 것**이 GraphQL의 단맛 나는
  지점이다 (5장 §"Where to use it", p.135):[^newman2021]

  > GraphQL's sweet spot is for use at the perimeter of the system, exposing functionality to
  > external clients.

  - 그 클라이언트는 전형적으로 GUI이고, **모바일 기기에는 명백히 맞는다**(화면에 데이터를
    보일 여력과 모바일 네트워크의 성질 때문이다). 외부 API에도 쓰였고 저자가 드는 초기
    채택자가 깃허브다. 외부 클라이언트가 필요한 정보를 얻으려 여러 번 호출해야 하는 외부
    API라면 **GraphQL이 그 API를 훨씬 효율적이고 친절하게** 만들 수 있다 (5장,
    p.135).[^newman2021]
- **마이크로서비스 사이 통신을 대체하지 않는다**는 판정이 명시적이다 (5장,
  p.135):[^newman2021]

  > Fundamentally, GraphQL is a call aggregation and filtering mechanism, so in the context of
  > a microservice architecture it would be used to aggregate calls over multiple downstream
  > microservices. As such, it's not something that would replace general
  > microservice-to-microservice communication.

  - **이 판정이 위 [REST와의 관계](#rest와의-관계) 절과 같은 방향이다.** 이 페이지의 다른
    소스도 GraphQL을 클라이언트 쪽 질의 언어로 두고 그 질의가 **내부 서비스에 대한 요청으로
    변환된다**고 적으므로, 뉴먼은 그 배치를 더 분명한 조문으로 만든 것이다. 겨루지 않는다.
  - 대안 하나가 이름으로 나온다 — 백엔드 포 프런트엔드(backend for frontend, BFF) 패턴이고,
    저자는 그 비교를 자기 책 14장으로 미룬다 (5장, p.135).[^newman2021]

## 14장 — BFF를 구현하는 수단으로

**같은 책의 14장이 이 언어를 다시 꺼내는 자리는 사용자 인터페이스의 집계 층이다.** 5장이
"경계에서 외부 클라이언트에"라고만 적은 그 경계를 14장이 **UI 하나마다 두는 집계 층**으로
구체화한다.

- **저자가 리졸버로 구현을 규정한다** — GraphQL 질의를 다룰 **리졸버(resolver)**가 서버 쪽에
  앉아 **질의를 실제 정보를 가져오는 호출로 매핑**한다. 마이크로서비스 아키텍처라면 ID 123인
  주문 요청을 그에 해당하는 마이크로서비스 호출로 매핑할 수 있는 리졸버가 필요하다 (14장
  §GraphQL, p.489).[^newman2021]
- **그래서 판정이 나온다** — 이런 식으로 **집약 게이트웨이를, 나아가 프런트엔드를 위한
  백엔드(backend for frontend, BFF)까지 GraphQL로 구현할 수 있다** (14장,
  p.489).[^newman2021]
- **BFF 구현에 견준 이점이 명시된다** — **클라이언트에서 질의를 바꾸기만 하면 집계와 걸러 내기가
  바뀌고**, GraphQL 타입이 그 질의를 지원하는 한 **서버 쪽 변경이 필요 없다.** 이것이 **집계
  로직의 변경이 BFF 자체의 변경으로도 이어져야 하는 구현에 견줘 상당한 이점**이다 (14장,
  p.489).[^newman2021]
  - **경합 쪽으로도 이어진다** — 클라이언트가 서버 쪽 변경 없이 질의를 동적으로 바꿀 수 있으므로
    **GraphQL 서버가 공유되고 경합하는 자원이 될 가능성이 줄어든다.** 그것이 범용 집약
    게이트웨이의 문제였다 (14장, p.489).[^newman2021]
  - **다만 서버 쪽 변경이 아예 사라지지는 않는다** — **새 타입을 노출하거나 기존 타입에 필드를
    더해야 하면 서버 쪽 변경이 여전히 필요하다.** 그래서 **팀 경계에 맞춰 GraphQL 서버 백엔드를
    여럿 두고 싶어질 수 있고**, 그 결론이 한 문장이다 (14장, p.489):[^newman2021]

    > so GraphQL becomes a way of implementing a BFF.

- **5장의 채점이 철회되지 않는다.** 저자는 14장에서 **GraphQL에 대한 우려를 5장에 상세히
  적었다고 스스로 되짚으면서**, 그럼에도 서로 다른 종류의 UI의 필요에 맞춰 동적으로 질의하게
  해 주는 **깔끔한 해법**이라고 적는다 (14장, p.489).[^newman2021] 위
  [마이크로서비스 쪽에서 본 같은 언어](#마이크로서비스-쪽에서-본-같은-언어) 절의 캐싱·쓰기·
  동적 질의 부하에 대한 판정은 그대로 서 있고, 14장은 **그 판정을 안고도 쓸 자리를 좁혀 지정한
  것**이다. 겨루지 않는다.
- 이 집계 층의 전문은 [프런트엔드를 위한 백엔드](../concepts/backend-for-frontend.md)가 갖는다.
