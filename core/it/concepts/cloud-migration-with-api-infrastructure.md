하나의 질문: **이미 돌고 있는 API 기반 체계를 클라우드로 옮길 때, 게이트웨이와 서비스 메시가
무엇을 대신해 주는가.**

## 버전 조건

> **버전 조건**: 이 페이지의 제품 이름과 성숙도 판정은 **2022년 저술 시점**의 것이다. 저자들이
> 리플랫폼의 예로 대는 것은 **MySQL 호환 AWS RDS · Azure Database · GCP Cloud SQL**이고 (9장,
> p.213), 네트워크 정책 플러그인의 예로 대는 것은 **Calico**다 (9장, p.221).[^gough2022]
> **다중 위치·다중 클러스터 서비스 메시로 서비스를 옮기는 선택지를 저자들 스스로 "초기
> 단계"(nascent)라고 적고** (9장, p.209), **그 기제가 메시 구현마다 다르다**는 각주를 단다
> (9장, p.222 각주).[^gough2022] 이전 전략 여섯과 구역·제로 트러스트의 규정은 시점에 매이지
> 않는다. `stale_after`는 적지 않는다 — 이 책에 벤더가 공표한 지원 종료일이 없다.

## 이 페이지가 담는 것과 담지 않는 것

- **담는 것** — 이 책 9장 "Using API Infrastructure to Evolve Toward Cloud Platforms"
  전량(pp.209–224)이다. **애플리케이션을 API로 쪼개는 일(8장)과 짝을 이루는 인프라 쪽**이다.
- **담지 않는 것** — 애플리케이션 쪽 재설계는
  [API 주도 재설계와 이음매](../concepts/api-driven-redesign-and-seams.md)와
  [API 이행 패턴과 고통 지점](../concepts/api-migration-patterns-and-pain-points.md)이 갖는다. 이 장이 이
  체계 위에서 실제로 밟는 걸음들은 [회의 시스템 사례 연구](conference-system-case-study.md)에 있다.
- **이 장이 이 책에서 서는 자리** — **API 프로그램이 인프라 변경을 이끄는 경우**를 다룬다.
  저자들은 인프라가 **하드웨어가 고장 나고 회사와 기술이 합병·인수되고 전사 IT 정책이 업그레이드를
  지시하면서 자기 나름의 박자로 바뀐다**고 적고, **그러나 때로는 API 프로그램이 인프라 변경을
  이끌며 특히 현대화와 더 클라우드 같은(소프트웨어로 정의된) 인프라로 옮기는 일과 관련해 그렇다**고
  잇는다 (9장, p.209).[^gough2022]
- **이 책이 더하는 것 넷** — 게이트웨이가 주는 **위치 투명성(location transparency)**으로 트래픽을
  점차 옮기는 방식 · **엣지에서 시작해 안쪽으로**라는 이전 순서 · 이전 중에 **남북과 동서의 선이
  흐려진다**는 관찰 · 그리고 **구역 기반 네트워크와 제로 트러스트를 이전 기간 동안 다리 놓는**
  메시와 네트워크 정책의 배치다.

## 클라우드 이전 전략 여섯

- **출처가 둘로 겹쳐 있다** — **가트너의 2010년 글 "Migrating Applications to the Cloud: Rehost,
  Refactor, Revise, Rebuild, or Replace?"를 바탕으로 아마존 웹 서비스가 2016년에 블로그를 내
  클라우드 이전의 "여섯 R"을 제시했다** (9장 §"Choosing a Cloud Migration Strategy",
  p.211).[^gough2022] **이 KB는 그 두 글을 원전으로 확인하지 않았다** — 이 책을 통한 2차 경유다.
- **API를 특별히 살펴야 하는 이유** — **API는 흔히 사용자에게 가장 가까운 업무 주도 구성 요소이고
  요청 대다수의 핵심 인그레스 지점**이므로, **이전 접근을 정할 때 특별한 주의를 기울여야** 한다
  (9장, p.211).[^gough2022]
- **여섯은 "아무것도 하지 않음"부터 완전한 재구축이나 폐기까지의 스펙트럼**을 이룬다 (9장,
  p.211).[^gough2022]

| 전략 | 이 책의 규정 | 이 체계에 대한 저자들의 판정 |
|---|---|---|
| **유지 또는 재검토**(retain or revisit) | **(당분간) 아무것도 하지 않는** 전략 | **유효하지 않다** — 문제를 미루는 것일 뿐이고 클라우드로 간다는 목표를 뒤로 미룬다 |
| **재호스팅**(rehost) | **"리프트 앤 시프트". 재아키텍처 없이 체계와 워크로드를 클라우드 플랫폼으로 옮긴다** | **탄탄한 전략일 수 있으나 고르지 않았다** — 자기 MySQL 인스턴스를 그대로 들어 옮기는 대신 클라우드 기반 서비스형 데이터베이스를 쓰고 싶었다 |
| **리플랫폼**(replatform) | **"리프트 팅커 앤 시프트". 재호스팅과 아주 비슷하되 최소한의 재작업만 요구하는 클라우드 서비스 일부를 활용한다** | **이것을 골랐다** — 큰 재작업을 피하면서 새 클라우드 서비스를 활용한다 |
| **재구매**(repurchase) | **주로 다른 제품으로 옮기는 것**. 예로 드는 것은 사내 메일 서버를 계속 돌리는 대신 SaaS 기반 메일 발송 서비스를 구독하는 것 | **선택지가 없다** — 이 체계는 주로 맞춤 애플리케이션과 표준 데이터 저장소로 돼 있다 |
| **리팩터·재아키텍처**(refactor/re-architect) | **애플리케이션이 어떻게 설계되고 개발되는지를 다시 상상하는 것**이고 대개 클라우드 네이티브 기능을 쓴다. **외부 기능은 바뀌지 않아야 하고 내부에서 그것을 이루는 방식이 확실히 바뀐다** | **명시적으로 고르지 않았다** — 이 책 전체에 걸쳐 이미 재아키텍처를 해 왔기 때문이다 |
| **폐기**(retire) | **이전 중에 체계를 그냥 없애는 것.** 큰 이전에는 더 이상 쓰이지 않고 잊힌 체계가 적어도 하나는 있게 마련이다 | **아직 폐기할 부분이 없다.** 다만 전체 목표 하나가 레거시 회의 체계의 폐기이고, 리플랫폼과 리팩터가 끝나면 그쪽으로 갈 수 있다 |

### 유지 또는 재검토

- **이 선택지를 깎아내리지 말라는 단서** — **할인하고 싶은 유혹이 있지만 많은 아키텍트(저자들
  포함)가 "싸울 전장을 골라라"라고 권할 것이고, 때로는 API를 이전하는 전투가 그 수고에 대한
  수익만큼의 가치가 없다** (9장 §"Retain or Revisit", p.211).[^gough2022]
- **다만 절차가 붙는다** — 이 결정은 **탄탄한 업무·기술 평가에 근거해야** 하고 **행동하지 않기로
  한 결정을 적절하게 내부와 외부에 알려야** 한다 (9장, p.211).[^gough2022]
  - **여기가 ADR이 빛나는 자리다** — **그런 결정의 종이 자취와 근거를 미래를 위해 남기는 일**이다
    (9장, p.211).[^gough2022] 그 양식의 정본은
    [아키텍처 결정 기록](../concepts/architecture-decision-records.md)이다.
- **목차에 없는 곁상자 하나가 그 "알리기"를 조문으로 적는다** — **평가 결과 지금은 진화시키지
  않기로 했더라도 행동을 취해야 하는 알려진 날짜를 전달하는 것은 여전히 중요하다.** 예로 드는
  것은 **업무 부문이 알려진 날짜에 문을 닫는 경우 · 체계가 수명 종료(EOL)에 이르는 경우 · 핵심
  소프트웨어나 데이터 저장소 라이선스가 알려진 시점에 만료되는 경우**이고, 그것을 **소비자에게
  폐기 예고(deprecation warning)로 알려야** 한다. **계약과 SLA에 요구되는 폐기 고지가 박혀 있을
  가능성이 크니 반드시 그것들을 확인하라** (9장 곁상자 "Communicating Change and
  Deprecations", p.212).[^gough2022] 판의 수명 주기 쪽 정본은 [API 수명 주기](../concepts/api-lifecycle.md)다.
- **이 절이 이전 일반에 붙이는 경고 하나** — **애플리케이션을 클라우드로 옮길 때 고려할 핵심
  요인 하나가 진화의 걸음마다 두 서비스 사이에 지연이 들어온다는 것**이다. **트래픽이 많은
  서비스라면 네트워크 경계를 건널 때마다 요청마다 느려짐을 겪는다.** **그 저하가 어떤 모양인지
  이해하는 것이 중요한 고려이고, 그것이 SLA를 어긴다면 그 서비스를 옮기는 것이 선택지가 아닐 수
  있다** (9장, p.212).[^gough2022] 1장에서 제약 안에서 프로토콜을 고르고 API를 설계하는 법을
  다룬 자리(§"Modeling Exchanges and Choosing an API Format", p.20)를 가리킨다.

### 재호스팅 — 리프트 앤 시프트

- **규정과 듣는 조건** — **워크로드를 통합하려 하거나 그냥 현재 인프라에서 벗어나야 한다면 흔히
  효과적인 전략**일 수 있다 (9장 §"Rehost", p.212).[^gough2022]
- **단서** — **클라우드 인프라가 언제나 온프레미스 하드웨어와 같은 방식으로 동작하지는 않으므로,
  당신이 세운 가정을 식별하고 확인하라** (9장, p.212).[^gough2022]
- **목차에 없는 곁상자 하나가 그 가정의 실물을 든다** — **많은 "리프트 앤 시프트" 프로젝트가
  예상대로 되지만 어떤 것은 안 된다. 특히 특수 맞춤 체계와 커스텀 하드웨어와 관련해 그렇다.**
  예로 드는 것 둘은 **체계 안의 모든 통신이 로컬 버스나 전용 네트워크 연결로 일어난다고 가정하는
  구식 특수 체계**(클라우드에서는 그렇지 않다)와 **밑에 깔린 블록 저장 체계의 특정 하드웨어 특성
  (또는 보장)을 가정하는 데이터 저장소 기술**이다. **의심스러우면 조사하라** (9장 곁상자 "Be
  Cautious with Specialist Systems and Bespoke Hardware", p.212).[^gough2022]

### 리플랫폼 — 리프트 팅커 앤 시프트

- **바꿔 끼우는 대상의 예 둘** (9장 §"Replatform", p.213):[^gough2022]
  - **체계 구성 요소로 돌던 기존 데이터 저장소를 프로토콜 호환 클라우드 서비스로 바꿔 끼우는 것** —
    네이티브 MySQL을 MySQL 호환 클라우드 데이터베이스로 바꾸는 식이다.
  - **언어별 애플리케이션 서버나 컨테이너를 갱신하거나 바꾸는 것.**

### 재구매와 리팩터·재아키텍처와 폐기

- **리팩터·재아키텍처를 언제 고르는가** — **기존 환경에서는 이루기 어려울 기능·확장·성능을 더해야
  한다는 강한 업무 필요**가 대개 이끈다. **조직이 기존 모놀리식 애플리케이션을 마이크로서비스로
  분해하기로 결정했다면 클라우드 네이티브 패턴 채택도 함께 고려되는 일이 아주 잦다** (9장
  §"Refactor/Re-architect", p.213).[^gough2022]
  - **대가와 이득이 같은 문장에 있다** — **이 패턴이 구현 비용이 가장 큰 편이지만, 제품과 시장의
    적합성이 좋고 기존 기술 선택에 제약받고 있다면 가장 이로울 수도 있다** (9장,
    p.213).[^gough2022]
- **이 절이 API 쪽에 붙이는 한 줄이 이 장의 논지를 요약한다** — **API 인프라와 설계가 더
  클라우드 네이티브한 사고방식으로 이끈다.** **1장에서 논한 대로 API를 정의하고 모형화하는 것이
  리팩터·재아키텍처 동안 서비스를 표현하는 깔끔한 기제를 제공하고**, **많은 클라우드 기반 서비스와
  상호작용 자체가 API에 기반한다는 것도 핵심**이다. **재아키텍처할 때의 API 전략은 클라우드에서
  쓰려는 서비스와 체계만큼이나 중요하다** (9장, p.214).[^gough2022]

## API 관리가 이전에서 맡는 자리

- **규정** — **API 관리자는 본질적으로 심장부에 초강화된 게이트웨이를 두고 API의 게시와 통제를
  위한 다양한 추가 기능을 제공하는 것**이다 (9장 §"Role of API Management", p.215).[^gough2022]
- **무엇을 주는가** (9장, p.215):[^gough2022]
  - **정책** — **OAuth2 챌린지 · 콘텐츠 검증 · 속도 제한 · 스로틀링** 등 게이트웨이에 전형적인
    엣지 관심사를 가능하게 한다.
  - **개발자 포털** — **개발자가 제공되는 API를 소비하는 체계를 지을 때 쓸 수 있는 모든 API의
    마켓플레이스**를 담는다.
  - **수익화** — **외부 고객에게도, 그리고 기업과 부문 간 배치에서 흔한 내부 "차지백"에도** 쓸 수
    있다.
- **분류상의 자리** — **API 관리는 엔터프라이즈 게이트웨이 범주 안에 든다** (9장,
  p.215).[^gough2022] 그 분류의 정본은
  [API 게이트웨이의 규정과 기능과 배치](../concepts/api-gateway-capabilities-and-deployment.md)다.
- **이전에서 가장 중요한 부분** — **뒤에서 계속 변경을 가하는 동안 API를 발견할 중앙 지점을
  제공할 수 있다는 것**이다. **레거시 회의 체계를 API로 앞세우면서 동시에 새로 떼어 낸 참석자
  API를 제공하는 것이 가능**하고, **API에 걸린 계약이 바뀌지 않는다고 가정하면 API 관리 층 뒤에서
  진화하는 것이 가능**하다 (9장, p.216).[^gough2022]
- **API 우선과의 연결** — **조직들은 흔히 "API 우선"(API First)이라는 개념을 이야기하는데, 체계
  사이의 모든 상호작용이 신중하게 설계되고 API로 모형화된다는 뜻**이다. **좋은 설계 원칙을 따르고
  "API 우선" 설계를 지향하면 API 관리 같은 도구를 써서 외부 고객에게도 조직 내부에서도 가치를
  풀어낼 수 있다** (9장, p.216).[^gough2022] 이 책이 그 개념을 세우는 자리는
  [OpenAPI 명세 실무](openapi-specification-practice.md)다.

## 남북과 동서의 선이 흐려진다

- **문제의 발생 경로** — **한 번에 다 바꾸는 위험을 지지 않고 서비스를 점진적으로 이전하기로
  골랐으므로, 여러 클라우드 환경과 온프레미스 데이터 센터에 걸쳐 서비스를 돌리는 일이 추가
  도전을 낳는다.** **많은 점진적 클라우드 이전이 그렇듯 사용자가 낸 API 요청 하나를 채우려면
  트래픽이 여러 네트워크를 건너야 한다** (9장 §"North–South Versus East–West: Blurring Lines of
  Traffic Management", p.216).[^gough2022]
- **요약이 그 관찰을 한 문장으로 다시 적는다** — **API 애플리케이션을 클라우드로 이전할 때
  남북(인그레스) 트래픽 관리와 동서(서비스 간) 트래픽 관리 사이의 선이 흐려지는 것을 흔히 보게
  된다** (9장 §"Summary", p.223).[^gough2022] 두 층을 가르는 정본은
  [API 게이트웨이와 서비스 메시](../concepts/api-gateway-and-service-mesh.md)다.

### 엣지에서 시작해 안쪽으로

- **이 책이 고른 순서** — **엣지에서 시작해 API 게이트웨이를 서비스 하나와 함께 클라우드로
  옮겼다** (9장 §"Start at the Edge and Work Inward", p.216).[^gough2022]
- **그 순서의 값어치** — **이전 팀이 기존 체계를 흐트러뜨리지 않고 완전히 새로운 클라우드 환경을
  처음 세워 볼 기회를 준다**는 것이다. **기존 게이트웨이를 그대로 돌리면서 현재 게이트웨이의
  복제본을 클라우드에 배포할 수 있고, 그러면 프로덕션 체계를 흐트러뜨리지 않고 클라우드 기반
  게이트웨이를 점진적으로 구성해 위험을 최소화할 수 있다** (9장, p.216).[^gough2022]
- **게이트웨이가 그것을 가능하게 하는 성질에 이름이 붙는다** — **API 게이트웨이의 사용은 서비스와
  API에 위치 투명성(location transparency)을 제공할 수 있고, 그래서 서비스를 클라우드에 배포하고
  트래픽을 기존 서비스에서 새 서비스로 점차 옮기되 소비자에게 미치는 영향은 제한적이거나 전혀
  없게 할 수 있다** (9장, p.209).[^gough2022]
- **덧붙는 권고 둘** (9장, p.217):[^gough2022]
  - **순수하게 클라우드 안에서만 도는 격리된 개념 증명을 짓고, 그것이 검증된 뒤에야 클라우드
    환경으로 드나드는 라우팅을 실험하기 시작하는 것이 흔히 합리적이다.**
  - **클라우드 기반 아키텍처를 설계하는 것은 설계 관점에서 흔히 패러다임 전환**이니 **새 인프라를
    배우고 이해하는 데 필요한 시간을 과소평가하지 마라.**

### 네트워크를 넘는 라우팅

- **이전이 라이브로 가기 전에 새 체계와 옛 체계가 서로 다른 네트워크를 건너 상호작용할 수 있음을
  보장해야** 한다 (9장 §"Crossing Boundaries: Routing Across Networks", p.217).[^gough2022]
- **선택지가 규모에 따라 갈린다** (9장, p.217):[^gough2022]
  - **모놀리식 애플리케이션 하나와 단순한 경로 몇 개뿐이면**, **새 API 게이트웨이에서 옛
    게이트웨이로 임시로 라우팅하는 것이 가장 쉬울 수 있고 단순한 HTTP 리다이렉트로도 가능**하다.
  - **네트워크를 건널 경로가 많거나 트래픽이 일단 네트워크에 들어오면 나가서는 안 된다면**,
    **가상 사설망 피어링이나 종단점, 또는 다중 클러스터 서비스 메시** 같은 다른 선택지를 고려해야
    한다.
- **조직 쪽 귀결 하나** — **API 트래픽이 여러 네트워크를 건너면 정보 보안 팀과 상의해야 할
  가능성이 크다. 그것이 경계 방어와 구역 아키텍처에 대한 전통적 접근을 흐트러뜨리기 때문**이다
  (9장, p.217).[^gough2022]

## 구역 아키텍처에서 제로 트러스트로

### 구역 나누기

- **왜 생겼는가** — **상업 인터넷이 인기를 얻으면서 규제 산업들이 점점 더 애플리케이션 접근을
  제공하기 시작했고, 그러면서 새 체계도 기존 내부 체계도 사용자를 마주하게 됐다. 구역
  아키텍처의 등장이 안전한 네트워크 설계의 모범 사례를 제공했다** (9장 §"Getting in the Zone",
  p.217).[^gough2022]
- **구역화의 규정** — **완전히 열려 있거나 평평한 네트워크의 위험을 완화하려고 인프라 서비스를
  같은 네트워킹 보안 정책과 보안 요건을 갖는 논리적 묶음으로 분할하는 것**이다 (9장,
  p.217).[^gough2022]
- **저자들이 드는 실물 하나** — **Log4Shell(CVE-2021-44228)**은 **영향을 받는 Log4J 라이브러리를
  쓰는 자바 애플리케이션에 심각한 위험을 지우는 제로데이 취약점**이고, **그 익스플로잇으로
  공격자가 네트워크 안 호스트에 접근해 악성 활동을 시작할 수 있었다** (9장, p.217).[^gough2022]
  - **거기서 낱말 하나가 정의된다** — **영향과 익스플로잇 아래 놓이는 서비스의 범위를 공격의
    폭발 반경(blast radius)이라 한다** (9장, p.217).[^gough2022]
  - **구역화가 그 반경을 줄이는 방식** — **신뢰되지 않은 요청이 전부 고가치 정보가 거의 없는
    구역으로 들어오면 폭발 반경이 최소화되고 보안 운영 팀이 심각한 장애를 막을 시간을 번다**
    (9장, pp.217–218).[^gough2022]
  - **구역은 계단식이다** — **다음 구역으로 넘어갈 때마다 인바운드 트래픽에 챌린지를 거는
    심층 방어(defense-in-depth) 완화가 더 걸린다** (9장, p.218).[^gough2022]
- **구역 사이의 경계** — **구역은 보안·네트워크 장비로 구현된 경계(Zone Interface Points)로
  갈린다.** **구역화는 보안 정책에 따라 지정된 구성 요소와 사용자에게만 접근과 데이터 통신 흐름을
  제한하는 논리적 설계 접근**이다 (9장, p.218).[^gough2022]
- **구역을 정의하는 방식은 여럿**이고 **표준화된 것(흔히 국가 수준)도 맞춤인 것도 있는데**,
  저자들은 **대다수 구역 아키텍처에서 발견되는 전형적인 네 구역**을 캐나다 정부의 ITSG-22에서
  가져온 그림과 함께 든다 (9장, p.218).[^gough2022]

| 구역 | 이 책이 옮기는 규정 |
|---|---|
| **공공 구역**(Public Zone, PZ) | **완전히 열려 있고 공공 인터넷·공중 전화망·기타 공공 통신사 백본 네트워크와 서비스 같은 공용 네트워크를 포함**한다 |
| **공공 접근 구역**(Public Access Zone, PAZ) | **운영 체계와 공공 구역 사이의 접근을 중개**하고 **흔히 비무장지대(DMZ)를 포함**한다 |
| **운영 구역**(Operations Zone, OZ) | **일상 운영을 위한 표준 환경**이고 **종단 체계에 적절한 보안 통제**를 갖춘다. **민감 정보 처리에 적합할 수 있으나, 이 지침의 범위를 넘는 추가적이고 강하고 신뢰할 만한 보안 통제 없이는 민감 데이터의 큰 저장소나 임무 핵심 애플리케이션에는 일반적으로 부적합**하다 |
| **제한 구역**(Restricted Zone, RZ) | **업무에 핵심인 IT 서비스나 민감 정보의 큰 저장소에 일반적으로 적합한 통제된 네트워크 환경**을 제공하고, **공공 구역의 체계에서 PAZ와 OZ를 거친 접근을 지원**한다 |

- **그림 9-3이 본문에 없는 것을 보여 준다** — 네 구역 위에 **"통제되지 않은 구역"(Uncontrolled
  Zone)과 "통제된 구역들"(Controlled Zones)이라는 상위 묶음**이 그려지고, **통제되지 않은 구역이
  둘(인터넷의 PZ와 "다른 정부 부처"의 PZ)로 그려지며**, **각 구역 쌍 사이마다 "Perimeter" 상자가
  끼어 있다.** 본문은 그 상위 묶음도 두 개의 PZ도 적지 않는다 (9장 그림 9-3,
  p.218).[^gough2022]

### 성과 해자의 가정을 클라우드가 흔든다

- **비유** — **이 경계 기반 네트워크 설계 접근은 옛 "성과 해자"(castle and moat) 방어와 다소
  비슷해서, 공격자가 인그레스 지점에서 가장 애를 먹지만 일단 성벽 안에 들어오면 대체로 돌아다니기
  쉬워진다** (9장, p.219).[^gough2022]
- **그 이유** — **체계 경계나 네트워크나 위치 안에서 비롯한 통신에 대해 가정이 세워지기 때문**이다
  (9장, p.219).[^gough2022]
- **클라우드가 그 가정을 흔드는 세 갈래** (9장, p.219):[^gough2022]
  - **많은 클라우드 플랫폼에서 밑에 깔린 인프라의 지리적·네트워크 위치가 추상화돼 있거나 아예
    알 수 없다.**
  - **클러스터 제공자의 보호가 있어도 공급망 공격의 위험이 남는다** — **빌드 시점에 소프트웨어에
    악성 내용이 끼어드는 것**이다.
  - **인프라 제공자 쪽의 악의적 사용자가 플랫폼 수준에서 정보에 접근할 가능성**이 있다.
- **그래서 균질성이 값을 갖는다** — **배포 종류마다 다른 종류의 보안을 돌리는 것도 가능하지만,
  더 균질한 접근이 가정이 세워질 위험과 서로 다른 보안 기법을 배워야 할 요구를 줄인다.**
  **구역 기반 아키텍처에는 본래적 신뢰가 설계돼 있고, 그것이 새 접근인 제로 트러스트의 진화를
  촉발했다** (9장, p.219).[^gough2022]

### 아무도 믿지 말고 검증하라

- **이 책이 옮기는 규정** — **제로 트러스트 보안 모형은 제로 트러스트 아키텍처 또는 경계 없는
  보안(perimeterless security)이라고도 하며, 현대 네트워크 체계의 설계와 구현에 대한 접근을
  서술한다.** **그 밑에 깔린 주된 착상은 "절대 믿지 말고 늘 검증하라"(never trust, always
  verify)이고, 이는 장치가 기업 LAN 같은 허가된 네트워크에 연결돼 있어도, 그리고 전에 검증된 적이
  있어도 기본적으로 신뢰돼서는 안 된다는 뜻**이다 (9장 §"Trust No One and Verify",
  p.219).[^gough2022]
- **근거** — **전통적 접근, 곧 관념상의 "기업 경계" 안의 장치나 VPN으로 연결된 장치를 믿는 것은
  기업 네트워크의 복잡한 환경에서는 적절하지 않다**는 것이다 (9장, p.219).[^gough2022]
- **무엇을 주장하는가** — **위치와 무관하게 장치의 신원과 무결성을 확인하는 것을 포함한 상호
  인증**과, **사용자 인증과 결합된 장치 신원·장치 건강에 대한 확신에 근거해 애플리케이션과
  서비스에 대한 접근을 제공하는 것**이다 (9장, p.219).[^gough2022]
- **원칙 여덟을 목록으로 든다** (9장, p.220):[^gough2022]
  - **사용자·장치·서비스·데이터를 포함해 당신의 아키텍처를 알라.**
  - **당신의 사용자·서비스·장치 신원을 알라.**
  - **당신의 사용자 행동과 장치와 서비스의 건강을 평가하라.**
  - **정책을 써서 요청을 인가하라.**
  - **어디에서나 인증하고 인가하라.**
  - **접근에 관한 모든 것 — 사용자·장치·서비스 — 에 모니터링을 집중하라.**
  - **당신 자신의 것을 포함해 어떤 네트워크도 믿지 마라.**
  - **제로 트러스트를 위해 서비스를 고르고 설계하라.**
- **그 목록의 출처가 본문에 없다.** 저자들은 **"우리 지침(our guidance)에 서술된 여덟 원칙"**이라
  적는데, **이 책 어디에도 그 지침이 저자들의 것이라는 근거가 없고 그 문단에는 각주도
  하이퍼링크도 없다**(그 쪽의 링크는 다음 절의 NIST 문서 하나뿐이다 — 실측). **이 KB는 그 여덟을
  이 책이 옮긴 것으로만 적고 바깥 귀속을 보태지 않는다.**
- **구역과 부딪히는 자리** — **여덟 원칙은 전적으로 합리적이지만 구역 아키텍처에서 고려하기가
  매우 까다롭고, 구역의 신뢰 가정이라는 개념이 이 점들 가운데 여럿에 도전한다.** 저자들이 드는
  예는 **구역 아키텍처가 흔히 체계의 엣지에서 사용자를 한 번만 인증하고 경계 안의 모든 네트워크를
  기본적으로 신뢰한다**는 것이다 (9장, p.220).[^gough2022]

### 제로 트러스트에서 서비스 메시가 맡는 일과 맡지 못하는 일

- **저자들이 드는 참조 문서** — **2020년 NIST가 펴낸 *Zero Trust Architecture*가 제로 트러스트와
  핵심 아키텍처 고려를 정의하는 훌륭한 문서**다 (9장 §"Role of Service Mesh in Zero Trust
  Architectures", p.220).[^gough2022] **이 KB는 그 문서를 원전으로 확인하지 않았다** — 이 책을
  통한 2차 경유다.
- **메시와 게이트웨이를 합친 것이 왜 플랫폼이 되는가** (9장, p.220):[^gough2022]
  - **서비스 메시가 아키텍처 구성 요소들이 어떻게 표현되고 그 사이로 트래픽이 어떻게 흐르는지를
    균질하게 모형화하도록 돕는다.**
  - **밑에 깔린 기술이 도는 프로세스의 신원을 둘러싼 구체적인 모형을 가능하게 하고, 인증서 관리가
    신원을 단언하고 증명하는 것을 돕는다.**
  - **능동적 추적과 모니터링의 통합이 플랫폼의 모든 지점에서 분석을 가능하게 한다** — 사용자만이
    아니라 **밑에 깔린 서비스와 쿠버네티스 파드 건강**까지다.
  - **모든 인그레스 트래픽은 강한 챌린지를 거쳐야** 하고 흔히 **7장에서 논한 OAuth2로 그 요청을
    단언**하며, **클러스터 안의 트래픽은 mTLS로 인증과 인가를 강하게 단언**할 수 있다.
- **그러나 원칙 하나가 메시에게 흥미로운 도전이 된다** — **"당신 자신의 것을 포함해 어떤 네트워크도
  믿지 마라"**다. **대다수 서비스 메시 모형에서 사이드카는 서비스나 앱과 강하게 결합돼 사이드카를
  거쳐 라우팅함으로써 트래픽 관리와 보안을 가능하게 한다.** **그러나 그 배치의 단순함은 당신이
  돌고 있는 플랫폼에 대해 구체적인 단언을 할 수 없다는 뜻이고, 애플리케이션과 사이드카 아래에
  앉아 있는 것이 신뢰 기반 가정을 하지 않도록 안전하게 지켜져야 한다** (9장,
  p.220).[^gough2022]
  - **곧 메시는 애플리케이션 층의 신뢰를 세우지만 자기가 올라앉은 층은 보증하지 못한다**는 것이
    이 절의 실질이다.

### 네트워크 정책으로 메시를 보강하기

- **전제** — **플랫폼 보안이 애플리케이션 수준에서 하는 모든 가정을 떠받치므로, 완전한 제로
  트러스트를 얻으려면 한 층 아래로 내려가야** 한다 (9장 §"Augmenting Service Mesh with Network
  Policies", p.221).[^gough2022] **이 소제목은 목차에 없다**(본문 bbox 실측).
- **수단** — **쿠버네티스에는 Calico 같은 네트워크 플러그인을 쓸 수 있게 하는 NetworkPolicy라는
  개념이 있고, 그 통제로 파드를 자기가 도는 플랫폼에서 격리할 수 있다** (9장,
  p.221).[^gough2022] 쿠버네티스 쪽 정본은
  [컨테이너 오케스트레이션과 쿠버네티스](container-orchestration-and-kubernetes.md)다.
- **저자들이 정책 셋을 차례로 쌓는다** (9장, pp.221–222):[^gough2022]
  - **첫째 — 전부 거부.** **주어진 파드로 들어오고 나가는 모든 인바운드·아웃바운드 트래픽을
    잠그는 정책**이고 **제로 트러스트 아키텍처에서는 이것이 파드의 기본값**이다. **규칙을 적용하면
    파드가 완전히 격리된다.**
  - **둘째 — DNS 조회 허용.** **서비스 메시 구현은 흔히 중앙 DNS 체계로 서비스 이름을 조회하는 데
    의존하는데 그것마저 잠긴다.** **플랫폼이 잠긴 채로 있으면서도 서비스 메시가 동작하게 하려면
    통제된 시나리오 몇 가지를 열어야** 하고, 이 정책은 **레거시 회의 체계가 참석자 서비스를 찾을 수
    있도록 DNS 조회를 허용**한다.
  - **셋째 — 대상 네임스페이스로의 이그레스 허용.** 그 시점에 **레거시 회의 서비스는 사이드카를
    통해 참석자가 어디 있는지 발견할 수 있지만 요청 자체는 차단된다.** **서비스 메시의 모든 라우팅
    규칙에는 네트워크 정책 어댑터에 정의된 대응하는 허용 규칙이 필요하다.**
  - **인그레스 쪽도 남는다** — **인그레스가 동작하려면 서비스 메시 게이트웨이에서 대상 서비스로
    가는 인그레스 규칙도 더해야** 한다.
- **그 운영상의 귀결이 앞 장을 다시 부른다** — **규칙과 구성이 릴리스 시점에 일관되게 적용되도록
  보장하는 것이 의견 있는 플랫폼(opinionated platform)을 고려할 또 하나의 이유**다 (9장, p.222;
  5장 §"Application Decisions for Effective Software Releases", p.142를 가리킨다).[^gough2022]
  그 개념의 정본은 [플랫폼 팀과 포장된 길](platform-team-and-paved-road.md)이다.

### 다중 클러스터 메시 피어링

- **위 셋의 결과에 이름이 붙는다** — **서비스 메시와 네트워크 정책을 씀으로써 마이크로세분화된
  아키텍처(microsegmented architecture)를 만든 것**이다. **이 접근의 이득은 클라우드와 예전에
  구역 기반이던 환경 둘 다를 포함하는 하이브리드 아키텍처에서 보안이 일관되는 시나리오를 가질 수
  있다는 것**이다 (9장, p.222).[^gough2022]
- **떠오르고 있는 패턴 하나** — **서비스 메시를 써서 서로 다른("다중 클러스터") 네트워크를
  다리 놓는 것**이다. **클러스터들에 걸쳐 서비스 메시를 함께 피어링해 이루고, 온프레미스와
  클라우드의 데이터 평면을 결합된 제어 평면의 앎 아래로 가져온다** (9장, p.222).[^gough2022]
  - **각주가 단서를 단다** — **이것의 기제는 서비스 메시 구현마다 다르다** (9장, p.222
    각주).[^gough2022]
  - **그 배치에서 서비스 메시가 모든 라우팅을 책임지고 네트워크를 가로지르는 제로 트러스트
    아키텍처를 제공할 수 있다.** **이 길을 택하는 이점은 안전한 진화적 아키텍처와 균질한 보안
    환경으로 이어진다는 것이고, 온프레미스가 클라우드처럼 동작하게 만듦으로써 나머지 서비스를
    클라우드로 진화시킬 쉬운 길이 생긴다** (9장, p.222).[^gough2022]
- **그림 9-4가 본문에 없는 것을 보여 준다** — 다중 클러스터 메시 그림에서 **API 게이트웨이가
  메시 상자 *안*에 놓이고 그 C4 유형 라벨이 `[Service Mesh Infrastructure]`**이며, **세 요청
  화살표가 모두 `[mTLS Service Mesh Routed]`로 라벨돼 있고**(클라우드 클러스터 내부 · 클라우드
  교차 클러스터 · 온프레미스 클러스터 내부), **클라우드 쪽과 온프레미스 쪽이 각자의 데이터
  저장소를 갖는다.** 본문은 게이트웨이가 메시 안에 있다고 적지 않는다 (9장 그림 9-4,
  p.223).[^gough2022]
- **요약이 그 다리를 한 줄로 적는다** — **제로 트러스트를 채택하면 제로 트러스트와 구역 아키텍처
  둘을 결합할 수 있고, 그것이 이전 기간 동안 클라우드와 온프레미스 체계를 다리 놓는 데 도움이
  된다** (9장 §"Summary", p.224).[^gough2022] **업계가 구역 네트워크 아키텍처에서 "제로 트러스트"
  체계로 옮겨 가고 있고 서비스 메시 기술이 그 이동을 촉진할 수 있다**는 것이 그 앞 불릿이다
  (9장, p.224).[^gough2022]

## 이 KB의 다른 서술과 나란히

- **제로 트러스트** — 이 KB의 정본은
  [암묵적 신뢰와 제로 트러스트](zero-trust-and-implicit-trust.md)이고 2021년 마이크로서비스
  실무서에서 왔다. **겨루지 않고 층이 다르다.** 그쪽은 **제로 트러스트가 제품이 아니라
  사고방식**이라고 못 박고 **양자택일이 아니라 정도**라고 적는다. 이 책은 **그 사고방식을
  인프라 구성물로 구현하는 경로**(메시 + 네트워크 정책 + 다중 클러스터 피어링)를 주고 **원칙
  여덟을 목록으로** 준다.
  - **한 자리에서 두 소스가 같은 결론에 다른 길로 닿는다** — 그쪽은 **데이터 민감도로 구역을 나눈
    회사**를 실물로 들며 **제로 트러스트와 구역 나누기가 배타적이지 않다**고 적고, 이 책은
    **이전 기간 동안 구역과 제로 트러스트를 결합하는 하이브리드**를 권한다. **다른 것은 동기다** —
    그쪽은 **심층 방어**를, 이 책은 **이전 중의 공존**을 이유로 든다. 이 대조는 이 KB가 세운 것이다.
- **구역(zone)이라는 낱말이 이 KB에서 셋을 가리킨다.** **이 책의 구역은 네트워크 보안 구역**이고,
  [암묵적 신뢰와 제로 트러스트](zero-trust-and-implicit-trust.md)의 구역은 **데이터 민감도 등급**이며,
  [진화적 아키텍트의 역할](evolutionary-architect-role.md)의 구역은 **아키텍트가 경계를 걱정하는
  조직·설계 단위**다. **셋을 합치지 않는다.**
- **다중 클러스터** — 이 KB가 이 낱말로 이미 갖는 것은 **카프카의 클러스터 간 미러링**과
  **이벤트 기반 마이크로서비스의 다중 클러스터 복제**인데, **둘 다 데이터 복제**이고 이 책의 것은
  **트래픽 라우팅의 제어 평면 결합**이다. **같은 낱말의 다른 대상이라 겨루지 않는다.**
- **클라우드 이전 전략** — 이 KB에 **여섯 R을 적은 페이지가 없었다**(`lift and shift`·리플랫폼·
  클라우드 이전으로 훑어 확인). [클라우드 네이티브 아키텍처](cloud-native-architecture.md)는
  **클라우드를 전제로 다시 설계한 체계의 성질**을 다루지 **거기까지 가는 전략**을 다루지 않는다.
  **이 장이 그 공백을 메운다.**
- **Log4Shell** — 이 KB에 그 취약점을 이름으로 적은 페이지가 없었다. 이 책은 **폭발 반경을
  설명하는 실물**로만 쓰고 그 취약점 자체를 분석하지 않는다.
