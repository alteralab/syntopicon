이 페이지의 질문: **개발자가 스레드를 직접 쓰지 않는 순간에도 자바 플랫폼의 무엇이 스레드 위에
서 있는가.**

## 동시성은 자바의 설계 목표였다

- 자바는 동시성을 염두에 두고 설계되었고, 멀티스레딩을 언어에 내장한 초기 언어 가운데 하나다. 그
  덕분에 개발자가 동시성을 얻으려고 운영 체제별 기능에 의존할 필요가 없어졌다 (1장, pp.1–2).[^rahman2025]
- 진화는 네 걸음으로 서술된다 — 기본 동기화와 스레드 관리에서 시작해, Java 5의
  `java.util.concurrent`가 실행자 프레임워크(Executor framework)와 락과 동시 컬렉션을 들이고,
  Java 7의 포크/조인 프레임워크(Fork/Join framework)가 멀티코어 성능을 끌어들였으며, 2025년 저술 시점 기준 가장 최근에는
  프로젝트 룸(Project Loom)이 경량 사용자 모드 스레드와 구조적 동시성(structured concurrency)으로
  전통적 스레드 기반 동시성의 복잡성과 한계를 다뤘다 (1장, p.1).[^rahman2025]
  - 같은 계보를 가상 머신 안쪽에서 본 서술이
    [가상 스레드와 코루틴](../concepts/virtual-threads-and-coroutines.md)에 있다. 이 페이지가
    말하는 것은 언어와 라이브러리 쪽 지형이다.

## 스레드는 무엇을 나누고 무엇을 따로 갖는가

- 정의가 두 줄이다 — 자바에서 스레드(thread)는 실행의 최소 단위이며, 프로그램 안에서 독립적으로
  진행되는 실행 경로다 (1장, p.2).[^rahman2025]
- 공유하는 것과 따로 갖는 것이 갈린다 — 스레드들은 같은 주소 공간(address space)을 공유해 같은
  변수와 자료 구조에 닿지만, 프로그램 카운터(program counter)와 스택과 지역 변수는 스레드마다
  따로 갖는다. 그래서 독립적으로 돌면서도 필요할 때 서로 주고받을 수 있다 (1장, p.2).[^rahman2025]
- 스케줄링은 자바가 하지 않는다 — 자바의 스레딩 모델은 밑의 운영 체제에 스케줄링과 실행을 맡기고,
  운영 체제가 스레드마다 CPU 시간을 배분하며 전환을 관리한다. 스레드를 여러 CPU에 흩뿌리면
  비로소 진짜 병렬이 된다 (1장, p.2).[^rahman2025]
  - 이 매핑이 무엇을 결정하고 무엇은 결정하지 않는지는
    [스레드 구현 모델](../concepts/thread-implementation-models.md)이, 배분 방식을 프로그램이
    어디까지 통제하는지는
    [자바 스레드 스케줄링과 상태 전이](../concepts/java-thread-scheduling-and-states.md)가 답한다.
- 스레드가 많아진다는 것은 실행 환경이 그만큼 늘어난다는 뜻이고, 웹 서버와 데이터 처리 파이프라인과
  실시간 시스템처럼 동시성이 많이 필요한 곳에서 처리량과 응답성을 올린다 (1장, p.3).[^rahman2025]

## 병렬성과 동시성은 다른 말이다

- 저자가 두 낱말을 갈라 놓는다 — 병렬성(parallelism)은 둘 이상을 동시에 하는 것이라 CPU 코어 둘
  이상 같은 처리 장치가 여럿 필요하고, 동시성(concurrency)은 프로그램의 여러 부분이 겹쳐 진행될 수
  있게 설계하는 일이라 반드시 같은 순간일 필요가 없다 (1장, p.3).[^rahman2025]
  - 저자의 비유는 부엌이다 — 병렬성은 여러 사람이 나란히 집을 짓는 쪽이고, 동시성은 요리사 한 명이
    여러 요리를 번갈아 다루는 쪽이다. 요리사를 더 넣으면 산출은 늘지만 그것이 곧 병렬은 아니다.
    한 사람이 양파를 썰 때 다른 사람은 오븐에 넣고 있을 뿐이고, 목표는 여전히 식사를 차리는
    것이다 (1장, p.3).[^rahman2025]
- 장 머리의 제사(題詞)는 롭 파이크(Rob Pike)의 말이다 — 동시성은 많은 일을 다루는 것이고 병렬성은
  많은 일을 하는 것이다 (1장, p.1).[^rahman2025]

## 가장 단순한 프로그램도 이미 스레드다

- 스레드라는 개념이 자바 생태계 전체가 구현되고 작동하는 방식의 바탕이며, 많은 기능과 도구가 그 위에
  서 있다. 메모리 관리를 맡는 가비지 컬렉션이든 화면에 한 줄을 찍는 일이든 배후에서는 스레드가
  일하고 있다 (1장, p.3).[^rahman2025]
- 처음 쓰는 프로그램조차 그렇다 — 한 줄짜리 출력은 단일 스레드 작업처럼 보이지만 자바 가상 머신(Java
  Virtual Machine, JVM)은 그 코드를 흔히 main 스레드라 부르는 스레드에서 실행한다 (1장,
  p.3).[^rahman2025] 실행 중인 스레드 이름을 함께 찍어 보면 그 이름이 나온다.

  ```java
  public class HelloWorld {
      public static void main(String[] args) {
          System.out.println("Hello, World!");
          // Displaying the thread that's executing the main method
          System.out.println("Executed by thread: " + Thread.currentThread().getName());
      }
  }
  ```

  - 출력의 둘째 줄에 나오는 이름은 보통 `main`이다 (1장, pp.3–4).[^rahman2025]
- 그래서 결론이 강하다 — 자바 개발자는 알든 모르든 거의 모든 일에서 스레드의 힘을 쓰고 있고,
  스레드는 자바가 큰 데이터베이스와 대규모 분산 시스템까지 감당하게 만드는 요소다 (1장,
  p.4).[^rahman2025]

## 예외와 디버거와 프로파일러가 기대는 자리

- 자바 스레드는 코드 실행 말고도 플랫폼의 모든 층에 걸쳐 있으며, 예외 처리와 디버깅과 프로파일링의
  바탕이다 (1장, p.4).[^rahman2025]
- 예외 — 스레드마다 자기 호출 스택(call stack)이 있어 그 스레드가 사는 동안의 메서드 호출을 모두
  기록한다. 예외가 던져지면 그 호출 스택이 진단 이력의 핵심이 되어, 예외에 이르기까지의 호출 순서를
  보여 주고 근본 원인을 좇게 해 준다 (1장, p.4).[^rahman2025]
  - 스택 트레이스가 예외가 난 스레드의 문맥 안에서 호출 스택을 들여다보게 해 주고, 여러 스레드가
    같은 일이나 다른 일을 동시에 돌리는 멀티스레드 애플리케이션의 디버깅에서 이 세밀함이 특히
    값지다 (1장, p.5).[^rahman2025]
- 디버거 — 디버거가 실행을 정확히 어디서 멈출지 알아내는 근거도 스레딩이다. 애플리케이션의 여러
  스레드에 자기를 붙여서 어느 스레드를 들여다볼지 고르고, 도는 애플리케이션의 스레드 상태를 바꿀
  수도 있다 (1장, p.5).[^rahman2025]
  - 스텝 인·스텝 오버·스텝 아웃이 모두 스레드를 기준으로 이뤄지고, 디버깅 세션에서 활성 스레드들의
    호출 스택을 따로따로 볼 수 있다. 호출 스택은 스레드가 어떻게 지금 지점에 왔는지를 알려 주며,
    예기치 않은 예외나 잘못된 데이터 조작의 원인을 찾을 때 그 경로가 결정적이다 (1장,
    p.6).[^rahman2025]
- 프로파일러 — 프로파일링 도구는 스레드 정보에 기대어 애플리케이션이 어떻게 도는지를 세밀하게
  보여 주고, 느려지는 지점을 짚고 멀티스레드 코드의 까다로운 타이밍 문제를 풀게 해 준다. 저자는
  스레드를 자바 성능 분석의 등뼈라고 부른다 (1장, p.6).[^rahman2025]

## 개발자가 부르지 않는 스레드들

- 개발자가 직접 쓰지 않는 스레드들이 밑에서 계속 돌며 이득을 보탠다 — 메모리 관리를 맡는 가비지
  컬렉션 스레드, 성능을 올리는 적시(just-in-time, JIT) 컴파일러 스레드, JVM이 매끄럽게 돌게 하는
  시그널 디스패처와 파이널라이저와 레퍼런스 핸들러 스레드, 그리고 핵심 JVM 작업과 진단을 맡는 가상
  머신 스레드와 서비스 스레드다 (1장, p.6).[^rahman2025]
- 그래서 저자의 결론은 자바 스레드가 플랫폼의 가장 본질적인 층 가운데 하나이며 자바 개발자가
  이해해야 하는 것이라는 쪽이다 (1장, p.6).[^rahman2025]
