하나의 질문: **아키텍처를 재는 테스트와 지표를 무엇으로 균형 잡는가.**

적합도 함수 자체의 정의와 분류는 [아키텍처 적합도 함수](../concepts/architecture-fitness-functions.md)에
있고, 이 페이지는 그 분류 가운데 둘을 골라 **층으로 쌓는 유비**만 담는다.

## 이 장이 서는 자리

- 이 장의 저자는 레네 바이스(Rene Weiss)이고, 감사 글에서 **이 책이 자기의 첫 책 기고**라고
  밝힌다. 소프트웨어 아키텍처를 생각하는 방식에 큰 영향을 준 사람으로 독일 embarc의 슈테판
  토트(Stefan Toth)와 슈테판 최르너(Stefan Zörner) 둘을 들고, **그들과 일하며 진화적 아키텍처라는
  발상을 처음 접했고 그 "씨앗"이 결국 이 장의 생각으로 이어졌다**고 적는다 (서문,
  p.xi).[^ciceri2022]
- 장 도입이 이 장의 주장을 한 문단으로 세운다 — **적합도 함수는 진화적 컴퓨팅(evolutionary
  computing)에서 빌려 온 개념이고 소프트웨어 체계의 지표를 정의하는 데도 쓸 수 있는 간결한
  방법**이다. 새 체계를 짓는 중이든 이미 있는 체계를 개선하는 중이든, 적합도 함수는 **자기 체계에
  맞춘 지표를 정의하게** 돕는다 (2장(바이스), p.21).[^ciceri2022]
  - **이 장이 더하는 것이 그다음 문장에 있다** — **적합도 함수와 지표를 테스트 피라미드 개념과
    결합하면 지표를 정의하고 우선순위를 매기고 균형 잡을 수 있으며 목표를 향한 진척을 잴 수
    있다** (2장(바이스), p.21).[^ciceri2022]

## 적합도 함수가 목표 지표를 낳는다

- **정의는 빌려 온다.** 저자는 닐 포드·리베카 파슨스·패트릭 콰의 *Building Evolutionary
  Architectures*(오라일리, 2017) 1장에서 적합도 함수의 정의를 그대로 인용한다 (2장(바이스), p.21,
  각주 1):[^ciceri2022]

  > an objective function used to summarize how close a prospective design solution is to
  > achieving the set aims

- **그 정의에 저자가 붙이는 조항 둘** (2장(바이스), p.21):[^ciceri2022]
  - 그런 함수는 **보통 이산값(discrete value)을 출력하고, 그 값이 달성하거나 개선하려는
    지표**다.
  - 목표에 닿았는지 알려면 **바라는 지표를 재는 테스트나 검증 기제가 필요**하다. **이상적으로는
    자동화되기를 바라지만 그것이 적합도 함수의 요건은 아니다.**
- **저자가 이 방식을 고르는 이유는 유연성이다** — 적합도 함수로 목표 지표를 만드는 발상은 **아주
  유연**해서, 코드 커버리지나 순환 복잡도(cyclomatic complexity) 같은 코드 구조 지표처럼 **전형적인
  지표를 기술하고 통합하는 데도 쓸 수 있고**, 동시에 그 **개방성이 자기 체계와 맥락에 맞춘
  아키텍처 지표를 재단하게** 한다 (2장(바이스), pp.21–22).[^ciceri2022]
  - 각주가 순환 복잡도를 따로 규정한다 — **정적 코드 분석 도구로 흔히 도출되는 널리 쓰이는 코드
    지표**이고 **1976년 토머스 J. 매케이브가 개발**했으며 **값이 높으면 코드를 이해하기 어렵고
    바꾸기도 어려울 수 있다는 표시**다 (2장(바이스), p.22, 각주 2).[^ciceri2022]
- **개념도가 넷의 관계를 고정한다.** 적합도 함수는 **목표 지표를 정의하고**, 동시에 **관련 맥락을
  기술**한다. 저자는 그 맥락을 **적합도 함수 맥락(fitness function context)**이라 부르고, 거기에
  **환경에 관한 추가 정보, 정의, 테스트에 영향을 주는 제약**이 들 수 있다고 적는다 (2장(바이스),
  p.22).[^ciceri2022]
  - 그림 2-1은 이미지로 조판돼 있고 화살표 라벨이 본문에 없다. 쪽 렌더로 읽은 라벨 전문이다
    (그림 2-1):[^ciceri2022]

    > Fitness function —(Defines)→ Target metrics
    > Fitness function —(Describes)→ Fitness function context
    > Fitness function context —(Influences)→ (Architectural) test/verification
    > (Architectural) test/verification —(Verifies and tests for)→ Target metrics
    > (Architectural) test/verification —(Implements runnable and testable versions)→ Fitness function

  - **실선 상자와 점선 상자가 갈린다** — 적합도 함수와 목표 지표는 실선, 적합도 함수 맥락과
    (아키텍처) 테스트/검증은 점선이다. 이 구분은 본문에 없다.
- **정의 시점이 못 박힌다** — 적합도 함수와 그 맥락과 실제 목표 지표는 **강하게 서로 얽혀 있고
  셋 다 설계 시점(design time)에 정의**한다. **아키텍처 테스트는 그 뒤에 만들어지며 적합도 함수와
  그 지표의 정의에 속하지 않는다** (2장(바이스), p.22).[^ciceri2022]
  - 그 순서가 실무에 미치는 것도 적힌다 — 테스트를 자동화하면 구현 뒤에 **지표가 자동으로
    만들어진다.** 그 구현에서 체계나 아키텍처의 무언가를 바꾸고 새 도구와 프레임워크를 평가하고
    **"공학" 쪽에서 창의적이어야 할 수 있는데, 이 전부는 목표와 지표를 정의한 뒤에 하는
    일**이다 (2장(바이스), pp.22–23).[^ciceri2022]
- **한 줄 요약이 이 절의 결론이다** — **적합도 함수는 "좋음"에 대한 당신의 정의 역할을 한다**
  (2장(바이스), p.23).[^ciceri2022]

## 아키텍처 테스트는 기능 테스트가 아니다

- **아키텍처 테스트가 목표 지표를 만든다.** 그런 테스트는 흔히 **만들어진 지표가 어떤 임계 위(또는
  아래)에 있는지도 직접 검증**한다. 보통 자동화되어 **지속적 통합(CI) 워크플로의 일부로
  실행**되고, 어떤 것은 **특정 촉발 없이도 연속으로 실행·검증될 수 있다** (2장(바이스),
  p.22).[^ciceri2022]
- **저자가 용어를 일부러 가른다** — **아키텍처 테스트(architectural tests)**와 **아키텍처
  검증(architectural verification)**이라는 말을 쓰는 이유는 **기능 테스트와 명시적으로 구별하기
  위해서**다 (2장(바이스), p.22).[^ciceri2022]
  - 저자의 대조 실물 하나 — **기능 테스트는 체계에 새 고객을 제대로 만들 수 있는지를 본다. 같은
    자리의 아키텍처 테스트는 고객 열을 만들면서 아키텍처적 또는 정성적 목표도 달성하는지를 본다.**
    이 시나리오의 아키텍처 테스트는 **고객 열이 얼마나 빨리 만들어졌는지에 대한 지표를 만들고 그것이
    10밀리초 안이었는지 검증**한다 (2장(바이스), p.22).[^ciceri2022]

## 적합도 함수를 한 줄로 적어 본 실물 넷

- **저자가 적합도 함수를 짧은 목록으로 적어 보인다.** 이 장에서 적합도 함수는 코드가 아니라
  **한두 줄의 명세문**으로 적히고, 그 명세문 안에 목표 지표와 실행 맥락과 실패 조건이 함께 들어간다.
- **예 둘은 가상 체계의 테스트 커버리지다** — 단위 테스트 커버리지를 90% 임계 위로 유지하는 것이
  결정적이고, 자동화된 통합 테스트의 목표는 라인 커버리지 50% 위다 (2장(바이스), p.23,
  예 2-1·2-2):[^ciceri2022]

  > Unit Test Coverage > 0.9;
  > Execute on each CI Build; Fail when below target coverage

  > Integration Test Coverage > 0.5;
  > Execute on each nightly integration test build;
  > Fail when below target coverage

  - 각주가 테스트 커버리지를 규정한다 — **어떤 테스트 집합이 소스 코드를 얼마나 덮는지를 재는
    소프트웨어 개발의 용어**이고, 자동화 테스트 실행 중 닿은("테스트된") 코드 라인을 재는
    **라인 커버리지**가 아주 흔하며 분기 커버리지 같은 다른 재기도 있는데 **이 장은 단순한 설명을
    위해 라인 커버리지로 간다.** 100줄짜리 프로그램의 커버리지가 80%면 80줄이 테스트 실행에
    닿았다는 뜻이다 (2장(바이스), p.23, 각주 3).[^ciceri2022]
  - 저자가 이 두 예에서 읽어 내는 구조 — 적합도 함수는 **충족할 목표 지표**(테스트 커버리지)와
    **그 지표에 관련된 맥락**(어떤 종류의 테스트를 언제 실행하는가)과 **지표를 자동으로 검증하는 데
    필요한 추가 맥락 정보**를 정의한다. **실제 구현**(실행 중 덮인 코드를 재는 일, 특정 테스트 환경을
    세우고 테스트를 수행하고 결과를 검증하는 일)**은 아키텍처 테스트를 구현하는 쪽에 속한다**
    (2장(바이스), p.23).[^ciceri2022]
- **예 둘은 제삼자 API의 네트워크 지연이다.** 테스트 대상 체계가 REST/JSON API로 제삼자 체계와
  통합되는데, 그 API가 느리거나 응답하지 않으면 자기 체계의 안정성과 성능이 떨어지므로 **그런 사건을
  제대로 다루고 기대대로 수행하는지 검증**하려는 것이다 (2장(바이스), p.24,
  예 2-3):[^ciceri2022]

  > Integration test errors = 0% (when network latency is 10s for third-party API call);
  > Execute on each nightly integration test build; Fail when integration test fails

  - 저자가 이 예에서 **적합도 함수의 부분들이 앞의 둘만큼 뻔하지 않다**고 인정한다. 충족할 지표는
    **0% 테스트 오류**이고, 맥락은 **통합 실행 중 제삼자 API 호출에 10초 네트워크 지연을 모사한다**는
    것이다. 실제 테스트 구현이 환경을 세우고 지연을 모사하고 야간 통합 테스트 빌드를 실행하고 그
    테스트가 올리는 어떤 오류에도 실패하는 일을 맡는다 (2장(바이스), p.24).[^ciceri2022]
  - **변형은 같은 맥락에 지표 하나를 더 얹는다** — 10초 지연을 걸어 둔 채 **전체 처리량 같은 지표를
    더해 특정 폴백 기제가 제대로 도는지까지 테스트**하는 것이다 (2장(바이스), p.24,
    예 2-4):[^ciceri2022]

    > Integration test errors = 0% (when network latency is 10s for third-party API call);
    > Execute on each nightly integration test build; Fail when integration test fails;
    > Fail when test execution duration is > 10 minutes (standard execution time,
    > without network latency is below 5 minutes)

  - 저자가 이 변형에서 노리는 것은 **폴백 기제가 돌고 전체 체계가 여전히 일정 시간 안에
    수행되는지**이고, 그 시간 틀을 **표준 네트워크 지연일 때 실행 시간의 최대 두 배**로 잡는다
    (2장(바이스), p.24).[^ciceri2022]

## 빌려 온 원본 — 기능 테스트 피라미드

- **저자가 테스트 피라미드를 남의 개념으로 들여온다** — **자동화된 기능 테스트의 여러 종류를 세
  층으로 분류하는 데 쓰이는 널리 알려지고 받아들여진 개념**이라고 적고, 마틴 파울러의 규정을
  인용한다 (2장(바이스), p.30):[^ciceri2022]

  > a way of thinking about how different kinds of automated tests should be used to create a
  > balanced portfolio

  - 이 맥락에서 **균형 잡힌(balanced)**은 **실행 시간과 운영·유지 비용을, 자동화 테스트가 주는
    확신과 저울질하는 포트폴리오**를 뜻한다. **보통 테스트가 많을수록 애플리케이션이 기대대로
    돈다는 확신이 커지지만, 대개 그 테스트의 운영·유지 비용이 커진다는 단점이 따라온다**
    (2장(바이스), pp.30–31).[^ciceri2022]
- **저자가 대는 출처가 넷이다** — 애슐리 데이비스의 *Bootstrapping Microservices with Docker,
  Kubernetes, and Terraform*(매닝, 2021), 리사 크리스핀과 재닛 그레고리의 *Agile Testing*(애디슨
  웨슬리, 2008), 그리고 마틴 파울러의 "TestPyramid"(MartinFowler.com, 2012년 5월 1일)이며, 인용문
  자체의 출처는 파울러의 그 글이다 (2장(바이스), p.30, 각주 6·7).[^ciceri2022]
  - **이 KB가 확인한 원전은 아니다** — 귀속은 **이 장이 그렇게 귀속한다**까지다.
- **층 셋의 규정은 정의 목록으로 주어진다** (2장(바이스), p.31):[^ciceri2022]

  | 층 | 무엇이 있는가 | 실패했을 때 |
  |---|---|---|
  | 바닥 층(base layer) | **우리가 하는 가장 쉬운 테스트, 곧 단위 테스트** | **문제 위치가 아주 분명하다** — 테스트 중인 단위 안에 있을 수밖에 없다. 반면 이 단위가 문제를 일으켜 최종 사용자가 잘못된 행동을 알아차릴 실세계 사용 사례는 **단위 테스트가 실패했을 때 쉽게 도출되지 않는 일이 잦다** |
  | 가운데 층(middle layer) | **서비스 테스트와 통합 테스트.** (때로 컴포넌트 테스트와 API 테스트도 여기 놓인다) | — |
  | 꼭대기 층(top layer) | **종단(E2E) 테스트**, 흔히 애플리케이션의 사용자 인터페이스(UI) 층을 통해 직접 실행된다 | **실세계 사용 사례가 어떻게 부정적 영향을 받을지 보기 쉽다.** 그러나 **오류를 일으킨 컴포넌트를 짚어 내기는 더 어려울 수 있다** — 이 수준에서는 많은 컴포넌트가 함께 돌기 때문이다 |

- 그림 2-2는 이미지로 조판돼 있다. 쪽 렌더로 읽은 라벨 전문이다 (그림 2-2):[^ciceri2022]

  > 왼쪽 세로축 `Execution`: 위 `Slow` — 아래 `Fast`
  > 오른쪽 세로축 `Maintenance/running cost`: 위 `Expensive` — 아래 `Cheap`
  > 층(위에서 아래로): `E2E UI` · `Service integration` · `Unit`

- **비용의 방향이 층을 정한다** — 피라미드 바닥의 테스트는 보통 **실행이 빠르고 유지·운영이 쉽고
  싸다.** 위로 갈수록 **실행이 느리고 개발·유지 비용이 커진다.** 그래서 **세 층에 걸쳐 테스트 수를
  균형 잡는 것이 결정적**이고, 그 목표는 **유지 가능한 테스트 집합으로 체계가 해야 할 일을 하고
  있다는 가능한 한 높은 확신을 얻는 것**이다 (2장(바이스), p.31).[^ciceri2022]
- **저자가 원본에 단서를 단다** — 이것은 **테스트와 자동화 노력을 어디에 둘지 정하는 데 쓸 수 있는
  모델이지만 이 이상화된 모델이 늘 옳지는 않다.** 가운데 층에 통합 테스트를 많이 써야 할 수도 있고,
  **사용자 인터페이스가 없는 체계라면 꼭대기 층에 테스트가 하나도 없을 수 있다** (2장(바이스),
  p.31).[^ciceri2022]

## 각색 — 적합도 함수 테스트 피라미드

- **저자의 자기 규정** — 적합도 함수 테스트 피라미드 개념은 **기능 테스트 피라미드 개념과 밀접하게
  관련**되고, 저자는 **그 주 개념을 적합도 함수와 아키텍처 지표 쪽으로 각색해 아키텍처 테스트에서
  균형을 얻는 데 재사용**했다 (2장(바이스), p.32).[^ciceri2022]
- **저자가 모델의 지위를 먼저 낮춘다.** 통계학자 조지 박스를 인용하고 스스로에게 붙인 단서가 이
  장에서 가장 조심스러운 문장이다 (2장(바이스), p.32, 각주 8):[^ciceri2022]

  > all models are wrong … still some are useful

  - 저자는 **여기 제시하는 모델이 쓸모 있는 쪽에 들기를 바란다**고 적는다. 인용의 출처로 대는 것은
    George E. P. Box, "Science and Statistics", *Journal of the American Statistical
    Association* 71, no. 356 (1976): 791–799이다 (2장(바이스), p.32).[^ciceri2022]
- **모양의 대응은 그대로다** — 기능 피라미드와 마찬가지로 **가장 쉽고 싼 테스트가 바닥에, 더 진보된
  테스트가 가운데에, 가장 복잡하면서 "최선"의 실세계 피드백을 줄 테스트가 꼭대기에** 온다
  (2장(바이스), p.32).[^ciceri2022]
- **층을 가르는 것은 분류 축 가운데 둘뿐이라는 축소가 이 유비의 핵심이다.** 적합도 함수는 늘 여러
  분류에 걸쳐 만들어지고 **필수 분류 전부가 쓸모 있는 적합도 함수를 기술하는 데 관련되지만, 피라미드
  층의 분류에 관련된 것은 몇 개뿐**이다 (2장(바이스), p.32).[^ciceri2022]
  - **실행 속도는 조건부로만 든다** — 저자는 **실행(빠름 대 느림)을 일부 환경에서만 층 분류의 관련
    요인으로 본다** (2장(바이스), p.32).[^ciceri2022]
  - **층을 가르는 두 축은 피드백 범위(원자적 대 전체적)와 실행 촉발**이다 (2장(바이스),
    pp.32–33).[^ciceri2022] 두 축의 전문은
    [아키텍처 적합도 함수](../concepts/architecture-fitness-functions.md)에 있다.
  - 각주가 그 선택의 근거를 남에게 돌린다 — **포드·파슨스·콰가 이 두 분류를 자연스러운
    "매시업(mash-up)"이라 부르고**, 실세계 적합도 함수와 지표와 테스트의 정의에 올 때 이 둘이
    밀접하게 관련되기 때문이다. 다른 분류도 영향을 줄 수 있지만 **그것은 구체적 사용 사례에 크게
    의존한다** (2장(바이스), p.33, 각주 9).[^ciceri2022]
- **꼭대기에 오는 것이 한 문장으로 제한된다** — **전체적 적합도 함수만이 피라미드의 꼭대기 층에
  나타난다.** 실행 쪽에서는 **연속으로 도는 테스트와 검증이 달성하기 더 어렵고 특히 전체적
  피드백에서 그렇다.** 그래서 **두 분류가 상호작용해 각 층에 무엇이 오는지를 정한다**
  (2장(바이스), p.33).[^ciceri2022]
- 그림 2-3은 이미지로 조판돼 있다. 쪽 렌더로 읽은 라벨 전문이다 (그림 2-3):[^ciceri2022]

  > 왼쪽 세로축 `Breadth of feedback on the whole system`: 위 `Most` — 아래 `Limited`
  > 오른쪽 세로축 `Maintenance/running cost`: 위 `Expensive` — 아래 `Cheap`
  > 층(위에서 아래로): `Continuous holistic` · `Triggered holistic/continual atomic` ·
  > `Triggered atomic`

  - **소스 안에서 낱말이 흔들린다** — 그림 2-3의 꼭대기 층 라벨은 `Continuous holistic`이고 가운데
    층 라벨은 `continual atomic`인데, 같은 가운데 층을 적는 본문(p.34)은 `continuous atomic`이라
    적고, 분류 카탈로그 표(p.30)는 촉발 축의 값을 `Triggered or continuous`로 적는다.
    **이 장은 continual과 continuous를 갈라 쓰지 않는다.**

## 꼭대기 층

- **규정** — 꼭대기 층 테스트는 **전체적이고, 체계의 건강과 최종 사용자를 위한 기능성에 대해 가장
  정교한 피드백**을 준다. 그래서 그 지표와 검증은 **실세계 사용 사례에 가장 가깝다** (2장(바이스),
  p.33).[^ciceri2022]
- **대가가 함께 적힌다** — 보통 **짓고 유지하기 가장 어렵고 비싸며**, 어떤 상황에서는 **비결정적
  행동을 보일 가능성도 더 높다.** 많은 컴포넌트가 관여하고 체계의 넓은 부분을 테스트하기 때문이다.
  **전체 체계에 대한 전체적 피드백을 적극적으로 노리되 격리하기 어려운 예상 밖 오류도 계산에
  넣어야 한다** (2장(바이스), p.33).[^ciceri2022]
- **그래서 개수가 제한된다** — 꼭대기 수준 테스트는 짓고 유지하기 복잡하고 드러내는 문제를 근본
  원인까지 추적하기 어려울 때가 있으므로, **노력과 산출을 저울질해 "좋은" 것 몇 개만 고른다**
  (2장(바이스), p.34).[^ciceri2022]
- **실물 둘** (2장(바이스), p.34):[^ciceri2022]
  - 온라인 상점에서 **분당 체크아웃율, 분당 매출, 분당 로그인 수 같은 핵심 지표를 목표 회랑(target
    corridor)으로 정의된 기대 범위 안에 있는지 상시 측정**하는 것. **이탈은 다뤄야 할 기저 기술
    문제를 드러낼 수 있고, 그 문제는 직전 배포가 들여왔을 수도 있다.**
  - **카오스 엔지니어링(chaos engineering)** — **프로덕션 환경에 오류를 들여 체계의 회복력을
    테스트하면서 최종 사용자에 대한 체계의 전반적 건강과 준비 상태를 재는 실천**이다. 각주가 드는
    참조는 "Principles of Chaos Engineering"과 넷플릭스의 Chaos Monkey다 (2장(바이스), p.34,
    각주 10).

## 가운데 층

- **규정** — 가운데 층은 **촉발 전체적(triggered holistic) 또는 연속 원자적(continuous atomic)
  적합도 함수**로 이루어진다. 이 함수들은 **전체 체계의 건강에 대한 넓은 피드백을 주지만 상시로
  돌지는 않고 전담 개발 행위에 의해 촉발**된다 (2장(바이스), p.34).[^ciceri2022]
- **촉발 전체적 쪽의 실물** — 통합 테스트 빌드의 일부로, 또는 자동화된 배포 파이프라인 안의 테스트
  체계나 스테이지를 이용해 테스트·실행·평가되는 지표다. **여러 테스트 케이스를 쓰는 통합 테스트
  실행은 다른 체계 부분이나 제삼자 체계의 실패를 모사해 전체 체계의 성능·트랜잭션 행동·회복력에
  대한 탄탄한 피드백**을 줄 수 있다. 저자는 **예 2-3과 2-4를 이 층의 테스트로 본다** (2장(바이스),
  p.34).[^ciceri2022]
- **연속 원자적 쪽의 실물** — **프로덕션 체계에서 연속으로 평가되는 단순한 원자적 적합도 함수**도
  이 층에 든다. 트랜잭션 지속 시간이나 최종 사용자 성능(웹 애플리케이션의 브라우저 로드 시간) 같은
  **원자적 값의 라이브 모니터링과 측정**이다 (2장(바이스), p.34).[^ciceri2022]

## 바닥 층

- **규정** — 바닥은 **"촉발 원자적(triggered atomic)" 적합도 함수**를 담는다. 보통 **구현과 실행이
  쉽고 싸며**, 단순하기 때문에 **이미 잘 자리 잡아 CI/CD 파이프라인에 통합돼 있는 일이 잦다.
  쓸모 있는 지표를 정의하려는 노력의 기반**을 이것들이 이룬다 (2장(바이스), p.34).[^ciceri2022]
- **실물 셋** — **코드 커버리지 지표, 순환 복잡도 같은 정적 코드 분석, 단순한 성능 테스트**다
  (2장(바이스), pp.34–35).[^ciceri2022]

## 모양을 뒤집어도 되는가, 그리고 유비가 깨지는 자리

- **저자의 권고는 모양을 따르는 쪽이다** — **바닥 층에 넓은 기반을 짓고 위층으로 갈수록 균형 잡힌
  접근을 쓰라**는 것이다 (2장(바이스), p.35).[^ciceri2022]
- **그러나 모양은 규칙이 아니다** (2장(바이스), p.35):[^ciceri2022]
  - **꼭대기 층 테스트를 하나도 만들지 않고(심지어 가운데 층 테스트도 없이) 적합도 함수를 쓰는
    것이 가능하다.**
  - **피라미드를 뒤집어야 하는 경우까지 있을 수 있다** — 연속 전체적 척도가 많고 촉발 원자적
    범주에는 몇 개뿐인 모양이다. **이것은 늘 맥락과 목표에 크게 의존하지만, 저자는 보통 피라미드
    모양을 따라 바닥에 가장 많고 위층으로 갈수록 적게 두기를 권한다.**
- **저자 스스로 유비가 깨지는 자리를 짚는다** — **바닥에 몇 개를 두어야 하는가를 생각하면 유비가
  무너진다.** 단위 테스트는 그 세분도에서 값어치가 있다면 **보통 아무도 개수를 제한할 생각을 하지
  않는다.** 그런데 **적합도 함수 테스트 피라미드의 바닥에 대해서는 가능한 한 많은 테스트를 만들라고
  권하지 않는다 — 전부가 추가 오버헤드를 만들기 때문**이다 (2장(바이스), p.35).[^ciceri2022]
  - **이 자인이 유비의 경계를 정한다.** 기능 테스트 피라미드가 "바닥은 많을수록 좋다"는 쪽으로
    읽히는 데 반해, 이쪽 바닥은 **개수가 아니라 선별**이 조항이다.

## 예 넷을 전면 분류해 층에 앉히기

- **저자가 앞의 예를 도로 꺼내 분류 축 전부에 대 본다.** 목적은 **이론적 도입을 살아 있게 만드는
  것**이다 (2장(바이스), p.35).[^ciceri2022]

| | 예 2-1 (단위 테스트 커버리지) | 예 2-3 (네트워크 지연) | 예 2-4 (지연 + 성능) |
|---|---|---|---|
| 피드백 범위 | **원자적** — 단위 테스트 커버리지는 전체 체계의 기능에 대해 제한된 피드백만 준다 | **원자적/전체적** — 전체적 자격이 있는지 분류하기가 더 어렵다. 실행되는 테스트와 우리 체계에 대한 제삼자 체계의 중요도에 주로 달렸다. 제삼자 체계가 여러 사용 사례에 쓰이면 전체적으로 분류할 수 있고, 아니면 원자적으로 본다 | **어느 쪽이든 될 수 있다** — 여기에 전체 체계의 성능이 판단 재료로 더 붙는다 |
| 실행 촉발 | 촉발 | 촉발 | 촉발 |
| 실행 위치 | CI/CD — 소스 관리로의 푸시마다 촉발되어 단위 테스트를 실행하고 커버리지를 잰다 | CI/CD와 테스트 환경 — CI 워크플로 안에서 야간에 촉발되지만 테스트는 테스트 환경에서 수행된다 | 같다 |
| 지표 유형 | 특정 값(> 90%) | 0/1(모든 테스트가 통과했는가) — 전체 테스트의 양성률에 관심 있다고 주장할 수도 있으나 **전부 통과를 요구하므로 0 아니면 1의 결정**이다 | 두 유형 — 통과 여부의 0/1과 성능 측정의 특정 값(이 경우 10분보다 빠름) |
| 자동화 | 자동 | 자동, 야간 실행 | 자동, 야간 실행 |
| 품질 속성 | **유지보수성** — 좋은 테스트 커버리지를 체계를 더 쉽게 유지(적응·변경·개선)할 수 있다는 표시로 다룬다 | **신뢰성** — 제삼자 인터페이스가 느리게 응답해도 체계의 신뢰성을 높게 유지하려는 목표 | **신뢰성과 성능 효율성** |
| 정적/동적 | 정적 | 정적 | **정적** — 두 지표가 여기서 정적으로 정의되고 목표값이 다른 적합도 함수의 결과에 의존하지 않기 때문 |
| 층 | **바닥 층** | 가운데 층 | 가운데 층 |

- **예 2-2(통합 테스트 커버리지)의 분류는 예 2-1과 같고, 그 적합도 함수도 피라미드의 바닥 층에
  놓인다** (2장(바이스), p.36).[^ciceri2022]

## 꼭대기 층의 예 둘

- **예 2-5는 온라인 상점의 매출 회랑이다** — **하루 내내 분당 매출을 측정하고, 그 시각 기준으로
  분당 매출이 표가 주는 회랑 밖으로 나가면 실패**시킨다 (2장(바이스), p.38, 예 2-5):[^ciceri2022]

  | 하루의 시간대 | 최소 매출(분당) |
  |---|---|
  | 01:00 AM – 05:00 AM | € 200 |
  | 05:01 AM – 07:00 AM | € 400 |
  | 07:01 AM – 09:00 AM | € 600 |
  | 09:01 AM – 11:30 AM | € 900 |
  | 11:31 AM – 01:30 PM | € 1100 |
  | 01:31 PM – 05:30 PM | € 950 |
  | 05:31 PM – 07:30 PM | € 1500 |
  | 07:31 PM – 09:00 PM | € 750 |
  | 09:01 PM – 00:59 AM | € 300 |

  - **저자가 이 표를 실물로 내세우지 않는다** — 각주가 **위 예에만 있는 아주 단순화된 표이고
    실세계 판이라면 시간과 기대 매출 사이에 더 세분된 구조나 더 복잡한 연결을 가질 것**이라고
    적는다 (2장(바이스), p.38, 각주 11).[^ciceri2022]
  - 분류 — **전체적**(전체 체계 성능의 직접 측정) · **연속, 프로덕션 환경** · **이산값**(값은
    매출이고 임계 위인지 검증이 필요하다) · **자동** · **품질 속성 복수**(신뢰성·성능 효율성·사용성
    등 — 전체 체계를 재므로 여러 품질 속성의 직접 검증을 보인다) · **동적**. **피라미드의 꼭대기
    층**이다 (2장(바이스), p.38).[^ciceri2022]
- **예 2-6은 롤아웃 중 신뢰성이다** — **새 릴리스를 밤 01:00에 프로덕션 체계에 배포하고, 릴리스가
  롤아웃되는 동안 최종 사용자 주요 사용 사례 다섯(로그인·장바구니 담기·장바구니에서 빼기·장바구니
  보기·체크아웃)을 담은 회귀 테스트 집합을 상시 수행**해, 체계가 모든 행위를 수행하고 100ms 안에
  응답하는지 본다. **테스트 케이스가 실패하면 실패시키고, 체계가 행위를 수행하지 못하거나 100ms 안에
  응답하지 못해도 실패**시킨다 (2장(바이스), pp.38–39, 예 2-6).[^ciceri2022]
  - 각주가 이 예의 의도를 밝힌다 — **롤링 업데이트가 수행되는 동안 체계가 가동 중임을 검증하는
    신뢰성 테스트**이고, **배포 중 무중단을 체계가 제공하는지 검증**하며, 나아가 **어떤 이유로 노드
    하나가 내려가도 전체 체계가 응답하고 기대대로 수행됨을 보일 수 있다** (2장(바이스), p.38,
    각주 12).[^ciceri2022]
  - 분류 — **전체적**(배포 중 전체 체계의 직접 측정이며 모든 온라인 노드의 측정은 아니다) ·
    **촉발, 프로덕션 환경**(이산 촉발, 밤 01:00) · **두 유형**(성능의 이산값과, 배포 중 체계가
    가용하고 테스트가 실패하지 않는다는 0/1) · **자동** · **신뢰성과 성능 효율성** · **정적**.
    이것도 **꼭대기 층**이다 (2장(바이스), p.39).[^ciceri2022]

## 분류가 흑백이 아니라는 자인과 분류의 두 쓰임

- **저자가 분류의 정확성을 목표에서 내린다** — 실세계 예의 분류는 **각 분류마다 흑백의 결정이 늘
  되지는 않는다.** 그리고 **그것이 이 분류들의 목표도 아니다** (2장(바이스), p.39).[^ciceri2022]
- **그래서 분류의 쓰임이 둘로 정리된다** (2장(바이스), p.39):[^ciceri2022]
  - **첫째, 적합도 함수와 그 지표의 중요한 측면들의 카탈로그로 쓴다.**
  - **둘째, 소프트웨어 아키텍트가 덮이지 않은 영역을 식별하고 추가 노력이 필요한 곳을 정하도록
    돕는다.**

## 적합도 함수와 지표를 기르는 절차 일곱

- **출발점은 도구가 아니라 품질 목표다** — 저자는 **소프트웨어 아키텍처 작업과 관련된 모든 활동의
  주된 출발점이 체계의 품질 목표**라고 적고, **적합도 함수와 지표 작업에서도 그것을 출발
  활동으로 권한다.** 이해관계자와 주요 품질 목표를 아직 맞추지 않았다면 **거기서 시작하는 것이
  좋은 기회**이고, 관련 품질 목표를 모아 **모든 이해관계자가 동의하는 공유된 상**을 만들라는
  것이다 (2장(바이스), pp.39–40).[^ciceri2022]
- **선행 원전의 처방을 인용하고 곧바로 유보를 단다.** 포드·파슨스·콰의 문장이 먼저 인용된다
  (2장(바이스), p.40, 각주 13):[^ciceri2022]

  > Teams should identify fitness functions as part of their initial understanding of the
  > overall architecture concerns that their design must support. They should also identify
  > their system fitness function early to help determine the sort of change that they want
  > to support.

  - **저자의 유보** — 일반적으로는 이 생각을 지지하지만 **처음부터 모든 적합도 함수를 식별하기는
    어렵다. 시작할 때 모든 요구사항을 알기 어려운 것과 마찬가지다.** 그래서 **작고 쉬운 데서
    시작해 체계를 구현하며 배우고, 그 배움으로 적합도 함수와 지표를 개선하거나 바꾸거나 더하라**고
    권한다. **피라미드 바닥 층의 관련 테스트에서 시작하라** (2장(바이스), p.40).[^ciceri2022]
- **절차는 스크럼 같은 반복 개발 과정에 통째로 통합하는 것이 전제다** (2장(바이스),
  pp.40–41):[^ciceri2022]
  1. **핵심 이해관계자와 함께 가장 중요한 품질 속성을 식별하고 아키텍처 목표를 세우고 문서화한다.**
     목표를 쓰면 **체계에 값어치를 더하지 않는 적합도 함수와 자동화 테스트를 만드는 함정**을
     피한다. 저자는 **핵심 품질 목표를 겨냥하지 않은 테스트를, 그저 쉽다는 이유로 자동화해 값어치가
     거의 없거나 전혀 없던 일을 자주 보았다**고 적는다.
  2. **적합도 함수와 목표 지표의 첫 초안을 만든다.** 중요한 차원들을 생각하고 **초안을 팀 전체와
     공유하는 목록(백로그여도 된다)에 넣고 이미 관련되리라 예상되는 분류를 문서화**한다. 공유 목록을
     쓰는 이유는 **정의와 자동화 테스트 구현에 노력이 들기 때문**이고, 백로그가 있으면 **구현할
     준비가 될 때까지 생각을 모아 둘 수 있다.** 초안마다 분류를 적어 두면 나중에 **아직 덮지 못한
     품질 목표 같은 새 영역의 적합도 함수를 고르거나, 다른 층의 테스트를 더해 포트폴리오를 균형
     잡는 데** 쓸모 있다.
  3. **지금 중요하고 도움이 되고 테스트하기 실현 가능한 것을 우선순위 매겨 고른다.** 어떤 테스트도
     덮지 않은 영역·차원과 피라미드 층을 함께 본다. **이 절차가 처음이라면 피라미드 바닥의 단순한
     것부터 시작한다.**
  4. **고른 것 가운데 아직 끝내지 못한 정의를 마무리한다.** **전체 정의와 피라미드 층 분류를
     보관**하면 절차의 다음 회차에서 **이미 덮은 영역의 값진 개관**이 된다.
  5. **지표를 만들 수 있는 자동화된 테스트를 개발한다.** 적합도 함수의 유형과 정의에 따라 다르지만
     보통 **그 테스트가 목표 지표를 직접 검증하는지도 확인**해야 한다. **기본으로 자동화하기를 강력히
     권하고, 아주 특정한 소수의 지표만 수동으로 만들고 검증**한다.
  6. **결과를 시각화한다.** 대시보드나 다른 형태의 시각화로 **팀 전체와, 필요할 때 관련
     이해관계자와** 결과를 공유한다.
  7. **필요에 따라 정기적으로 반복한다.** 어떤 테스트의 출력은 믿을 수 없고, 어떤 지표는 더 이상
     쓸모없으며, 유지 노력이 너무 클 수 있다. **충분한 값어치를 주지 않거나 더 이상 필요 없는
     테스트와 적합도 함수를 폐기**한다. 기존 것도 바꾼다 — **체계의 개선을 반영해 더 엄격하게
     만들거나, 전체 목표에 덜 관련되면 덜 엄격하게** 만든다.

## 맺음 — 지표가 최종 목적이다

- **임의로 테스트하는 것의 대가** — 체계를 임의로 테스트하면 **성능·보안·수정 가능성 같은 관련
  영역의 전반적 품질이라는 가장 중요한 것에서 초점을 잃을 수 있다** (2장(바이스),
  p.41).[^ciceri2022]
- **저자가 남기는 처방 셋** (2장(바이스), p.41):[^ciceri2022]
  - **짓기가 상대적으로 쉽고 필요에 따라 개발·확장할 수 있는 아키텍처 테스트의 단단한 기반에서
    시작하라.**
  - **적합도 함수를 체계에 맞춘 지표를 만드는 방법으로 쓰면 맞춤이 가능해지고, 이 장의 절차를
    따르면 불필요한 오버헤드가 줄어든다.**
  - **적합도 함수 테스트 피라미드는 테스트를 분류하고 노력을 균형 잡는 층을 하나 더 준다.**
- **마지막 문장이 이 장의 값어치 규정이다** — **지표가 최종 목적이다. 지표는 팀을 소프트웨어 체계의
  합의된 목표에 붙들어 두는 편향 없는 척도(unbiased measures)다** (2장(바이스),
  p.41).[^ciceri2022]

## 이 KB의 다른 자리들과 맞대어 본 것

- **테스트 피라미드의 원전은 이 KB에 없다.** 이 KB가 피라미드를 다루는 자리들은 전부 2차
  서술이고, 이 장도 마찬가지다 — 인용문은 파울러의 2012년 글에서 오고 마이크 콘의
  *Succeeding with Agile*은 이 장이 아예 들지 않는다.
  [종단 테스트를 왜 줄이는가](../concepts/why-fewer-end-to-end-tests.md)와
  [구글의 테스트 크기 어휘와 스위트 운영](../concepts/google-test-sizes-and-suite-operations.md)이
  같은 피라미드를 각각 2015년 구글 블로그와 2020년 구글 책 쪽에서 받는다. **이 장은 그 계보에
  넷째 각도를 더한다 — 재는 대상이 기능이 아니라 아키텍처 특성인 피라미드다.**
- **그래서 이 페이지는 기능 테스트 배합의 처방과 겨루지 않는다.** 종단 테스트를 적게 두라는 쪽은
  **기능 테스트의 배합**을 정하고, 이 장은 **아키텍처 테스트와 지표의 배합**을 정한다. 두 피라미드의
  꼭대기에 오는 것이 다르다 — 저쪽 꼭대기는 UI를 지나는 종단 테스트이고, 이쪽 꼭대기는 프로덕션에서
  연속으로 도는 전체적 지표와 카오스 엔지니어링이다. **한쪽만 참일 수 있는 문장 쌍은 없다.**
- **분류 축의 대조는 적합도 함수 쪽 페이지에 있다.**
  [아키텍처 적합도 함수](../concepts/architecture-fitness-functions.md)가 2017년 원전의 여섯 축을
  갖고, 이 장이 그것을 필수 여섯과 선택 넷으로 다시 자른 결과와의 대조표도 거기 있다. **같은
  지형의 다른 자름이고 모순이 아니다.**
- **품질 목표에서 출발하라는 조항은 같은 방향의 다른 소스와 만난다.**
  [검증 가능한 가로지르는 기능 요건](../concepts/testable-cross-functional-requirements.md)이
  가정을 구체적 기대로 바꾸는 일을 다루고, 이 장은 그 기대를 **적합도 함수의 목표 지표로
  적는 자리**를 준다. 두 자리 모두 FURPS를 언급하지만 이 KB가 원전으로 확인한 것은 아니다.
- **바닥 층이 CI/CD 파이프라인에 이미 통합돼 있다는 관찰은 파이프라인 쪽 페이지와 이어진다** —
  [점진적 변경과 배포 파이프라인](../concepts/incremental-change-and-deployment-pipelines.md)이
  적합도 함수가 도는 자리로서의 파이프라인을 갖는다.
