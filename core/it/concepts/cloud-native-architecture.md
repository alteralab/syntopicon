이 페이지의 질문: **클라우드를 단지 임대 서버로 쓰는 것과, 클라우드를 전제로 다시
설계하는 것은 시스템 내부에서 무엇이 다른가.**

## 클라우드 네이티브란

- 클라우드의 부상은 경제 모델(하드웨어를 사고 라이선스를 사는 대신 서비스를
  구독)만이 아니라 **데이터 시스템이 기술적으로 구현되는 방식**에도 깊은 영향을
  줬다. 클라우드 네이티브(cloud native)는 클라우드 서비스를 활용하도록 설계된
  아키텍처를 가리키는 말이다 (1장, p.14).[^kleppmann2026]
- 원리적으로는 자체 호스팅할 수 있는 거의 모든 소프트웨어를 클라우드 서비스로도
  제공할 수 있고, 실제로 많은 인기 데이터 시스템에 관리형 서비스가 나와 있다. 그러나
  처음부터 클라우드 네이티브로 설계된 시스템은 여러 이점을 보인 바 있다 — **같은
  하드웨어에서 더 나은 성능, 장애에서의 더 빠른 복구, 부하에 맞춘 빠른 컴퓨팅 확장,
  더 큰 데이터셋 지원** (1장, p.15).[^kleppmann2026]
- 저자들이 든 대비 사례 (1장, p.15):[^kleppmann2026]
  - 운영/OLTP — 자체 호스팅: MySQL·PostgreSQL·MongoDB / 클라우드 네이티브: AWS
    Aurora·Azure SQL DB Hyperscale·Google Cloud Spanner.
  - 분석/OLAP — 자체 호스팅: Teradata·ClickHouse·Spark / 클라우드 네이티브:
    Snowflake·Google BigQuery·Azure Synapse Analytics.

## 클라우드 서비스의 계층화

- 자체 호스팅 소프트웨어의 시스템 요구는 대체로 단순하다: 리눅스·윈도우 같은 통상의
  운영체제 위에서 돌고, 데이터를 파일시스템의 파일로 저장하며, TCP/IP 같은 표준
  네트워크 프로토콜로 통신한다. GPU나 RDMA 네트워크 인터페이스 같은 특수 하드웨어에
  의존하는 시스템도 일부 있지만 대체로 **범용 컴퓨팅 자원**(CPU·RAM·파일시스템·IP
  네트워크)을 쓴다 (1장, p.15).[^kleppmann2026]
- 클라우드에서 이런 소프트웨어는 IaaS 환경의 VM(인스턴스)에서 돌 수 있다. 물리
  기계에 비해 클라우드 인스턴스는 더 빨리 준비되고 크기 선택지가 다양하지만, 그 외에는
  전통적 컴퓨터와 비슷하다 — 원하는 소프트웨어를 아무거나 돌릴 수 있고 **관리 책임도
  당신에게 있다** (1장, p.15).[^kleppmann2026]
- 대조적으로 클라우드 네이티브 서비스의 핵심 아이디어는 운영체제가 관리하는 컴퓨팅
  자원만 쓰는 것이 아니라, **더 낮은 층위의 클라우드 서비스 위에 더 높은 층위의
  서비스를 쌓는 것**이다 (1장, p.15).[^kleppmann2026]
  - Amazon S3·Azure Blob Storage·Cloudflare R2 같은 오브젝트 스토리지(object storage)
    서비스는 큰
    파일을 저장한다. 통상의 파일시스템보다 API가 제한적이지만(기본적인 파일 읽기·쓰기),
    **아래의 물리 기계를 감춘다** — 서비스가 데이터를 여러 기계에 자동으로 분산하므로
    한 기계의 디스크 공간이 모자랄 걱정을 하지 않아도 되고, 일부 기계나 디스크가 완전히
    고장 나도 데이터가 유실되지 않는다.
  - 다른 서비스들이 다시 그 위에 세워진다. 예컨대 Snowflake는 데이터 저장을 S3에
    의존하는 클라우드 기반 분석 데이터베이스(데이터 웨어하우스)이고, 또 다른 서비스들이
    다시 Snowflake 위에 세워진다.
- 컴퓨팅의 다른 추상화가 늘 그렇듯 **무엇을 써야 하는가에 하나의 정답은 없다**.
  일반 규칙으로, 상위 추상화일수록 특정 유스케이스에 더 맞춰져 있다. 상위 시스템이
  설계된 상황에 당신의 필요가 맞으면 하위에서 직접 짓는 것보다 훨씬 덜 번거롭게
  해결되고, 어떤 상위 시스템도 맞지 않으면 하위 부품으로 직접 짓는 것이 유일한
  선택지다 (1장, p.16).[^kleppmann2026]

## 저장과 연산의 분리

- 전통적 컴퓨팅에서 디스크 저장은 **지속성 있는(durable)** 것으로 간주된다 — 한 번
  쓰면 유실되지 않는다고 가정한다. 개별 디스크 고장을 견디려고 같은 기계에 붙은 여러
  디스크에 사본을 유지하는 RAID를 흔히 쓰며, 하드웨어로도 OS 소프트웨어로도 구현할 수
  있고 파일시스템에 접근하는 애플리케이션에는 투명하다 (1장, p.16).[^kleppmann2026]
- 클라우드에서 컴퓨트 인스턴스에도 로컬 디스크가 붙어 있을 수 있지만, **클라우드
  네이티브 시스템은 그 디스크를 장기 저장이라기보다 일시적 캐시처럼 다룬다.** 인스턴스가
  고장 나면 로컬 디스크에 접근할 수 없게 되고, 부하 변화에 맞춰 더 크거나 작은
  인스턴스(다른 물리 기계)로 교체될 수도 있기 때문이다 (1장, p.16).[^kleppmann2026]
- 대안으로 클라우드는 한 인스턴스에서 떼어 다른 인스턴스에 붙일 수 있는 가상 디스크
  저장(Amazon EBS, Azure 관리 디스크, Google Cloud 영구 디스크)을 제공한다. 이것은 물리
  디스크가 아니라 **디스크의 동작을 흉내 내는 별도 기계 집합이 제공하는 클라우드
  서비스**이며, 블록 장치(block device, 블록 크기는 보통 4 KiB)를 에뮬레이션한다.
  덕분에 전통적인 디스크 기반 소프트웨어를 클라우드에서 돌릴 수 있지만, 블록 장치
  에뮬레이션은 클라우드 전용으로 새로 설계한 시스템이라면 피할 수 있는 오버헤드를
  들여온다. 또 **가상 블록 장치의 모든 I/O 연산이 네트워크 호출이므로 애플리케이션이
  네트워크 순단(glitch)에 아주 민감해진다** (1장, p.16).[^kleppmann2026]
- 그래서 클라우드 네이티브 서비스는 대체로 가상 디스크를 피하고, 특정 워크로드에
  최적화된 전용 저장 서비스 위에 짓는다. S3 같은 오브젝트 스토리지는 수백 킬로바이트에서
  수 기가바이트에 이르는 **비교적 큰 파일의 장기 저장**을 겨냥한다. 데이터베이스에
  저장되는 개별 행이나 값은 보통 그보다 훨씬 작기 때문에, 클라우드 데이터베이스는
  작은 값들은 별도 서비스에서 관리하고 **여러 값을 담은 큰 데이터 블록을 오브젝트
  스토어에 저장**하는 식으로 쓴다 (1장, p.16).[^kleppmann2026]
- 전통적 시스템 아키텍처에서는 같은 컴퓨터가 저장(디스크)과 연산(CPU·RAM)을 모두
  책임지지만, 클라우드 네이티브 시스템에서는 이 두 책임이 어느 정도 분리(disaggregated)돼
  있다. 예컨대 S3는 파일만 저장하므로 그 데이터를 분석하려면 S3 **바깥** 어딘가에서
  분석 코드를 돌려야 하고, 이는 **데이터를 네트워크로 옮기는 것**을 함의한다 (1장,
  p.17).[^kleppmann2026] 그 대가는
  [분산 시스템과 단일 노드](../concepts/distributed-versus-single-node.md) 참조.
- 이 구조가 [데이터 레이크](../concepts/data-lake.md)를 관계형 저장보다 싸게 만드는
  근거이기도 하다 (1장, p.10).[^kleppmann2026]

## 멀티테넌시

- 클라우드 네이티브 시스템은 흔히 **멀티테넌트(multitenant)** 다 — 고객마다 별도
  기계를 두는 대신, 여러 고객의 데이터와 연산을 같은 공유 하드웨어에서 같은 서비스가
  처리한다 (1장, p.17).[^kleppmann2026]
- 멀티테넌시(multitenancy)가 주는 것: 더 나은 하드웨어 활용률, 더 쉬운
  확장성(scalability), 클라우드 제공자
  입장에서 더 쉬운 관리 (1장, p.17).[^kleppmann2026]
- 대가로 요구되는 것: **한 고객의 활동이 다른 고객의 성능이나 보안에 영향을 주지
  않도록 하는 세심한 엔지니어링** (1장, p.17).[^kleppmann2026]

## 테넌시는 결정 사항이다 — 성능과 보안

위 절이 멀티테넌시를 클라우드 시스템의 **성질**로 서술한다면, 데이터 엔지니어링 쪽 소스는
그것을 데이터 엔지니어가 내려야 할 **결정**으로 놓는다.

- 알갱이가 여럿이다 — **데이터 엔지니어로서 여러 팀·조직·고객에 걸쳐 시스템을 공유하는 데 관한
  결정을 내려야 한다. 어떤 의미에서 모든 클라우드 서비스는 멀티테넌트지만, 이 멀티테넌시는 다양한
  알갱이로 일어난다. 예컨대 클라우드 컴퓨트 인스턴스는 보통 공유 서버 위에 있지만 VM 자체가 어느
  정도의 격리를 제공한다. 객체 저장소는 멀티테넌트 시스템이지만, 고객이 권한을 올바르게 설정하는
  한 클라우드 벤더가 보안과 격리를 보장한다** (3장, p.94).[^reis2022]
- **엔지니어는 훨씬 작은 규모에서 멀티테넌시에 관한 결정을 내려야 하는 경우가 잦다. 예컨대 큰
  회사의 여러 부서가 같은 데이터 웨어하우스를 공유하는가? 조직이 같은 테이블 안에서 여러 큰
  고객의 데이터를 공유하는가?** (3장, p.94).[^reis2022]
- 고려할 요인은 둘이다 — **성능과 보안이다. 클라우드 시스템 안에 큰 테넌트가 여럿 있을 때 시스템이
  모든 테넌트에 일관된 성능을 지원하는가? 아니면 시끄러운 이웃 문제(noisy neighbor problem)가
  있을 것인가? 곧 한 테넌트의 높은 사용이 다른 테넌트의 성능을 떨어뜨릴 것인가?** (3장,
  p.94).[^reis2022] 이 대가는 위 [멀티테넌시](#멀티테넌시)가 말하는 "세심한 엔지니어링"이 실제로
  막아야 하는 실패다.
- 보안 쪽 — **보안에 관해서는 서로 다른 테넌트의 데이터가 적절히 격리돼야 한다. 회사에 외부 고객
  테넌트가 여럿 있으면 그 테넌트들은 서로를 알지 못해야 하고, 엔지니어는 데이터 유출을 막아야
  한다. 데이터 격리 전략은 시스템마다 다르다. 예컨대 멀티테넌트 테이블을 쓰고 뷰를 통해 데이터를
  격리하는 것이 완벽히 받아들일 만한 경우가 잦다. 그러나 이 뷰가 데이터를 새게 할 수 없음을
  확실히 해야 한다. 적절한 전략과 위험을 이해하려면 벤더나 프로젝트 문서를 읽으라** (3장,
  pp.94–95).[^reis2022]

## 오브젝트 스토리지가 떠받치는 데이터베이스

같은 책 6장이 위 [저장과 연산의 분리](#저장과-연산의-분리)를 복제 쪽에서 이어받는다 —
오브젝트 스토어(object store)가 아카이브 자리를 넘어 **트랜잭션·리더 선출(leader
election)·복제까지 떠안는** 흐름이다.

- 아카이브 용도의 기본형부터 — **복제 로그를 전체 데이터베이스의 주기적 스냅샷과 함께 오브젝트
  스토어에 아카이브할 수 있다. 이것이 데이터베이스 백업과 재해 복구를 구현하는 좋은 방법이고,
  새 팔로워를 세우는 앞 두 단계(스냅샷 뜨기와 복사)를 그 파일들을 오브젝트 스토어에서 내려받는
  것으로 수행할 수 있다.** WAL-G가 PostgreSQL·MySQL·SQL Server에 대해, Litestream이 SQLite에
  대해 이 일을 한다 (6장, p.202).[^kleppmann2026]
- 그 위의 흐름 — **오브젝트 스토리지는 데이터 아카이빙 이상에 쓸 수 있고, 많은 데이터베이스가
  Amazon S3·Google Cloud Storage·Azure Blob Storage 같은 오브젝트 스토어를 라이브 질의를
  서빙하는 데 쓰기 시작했다.** 이점 넷 (6장, p.203):[^kleppmann2026]
  - **다른 클라우드 저장 옵션에 비해 값싸다. 그래서 클라우드 데이터베이스가 덜 질의되는 데이터를
    더 싸고 지연이 높은 저장소에 두면서 워킹 셋(working set)은 메모리·SSD·NVMe에서 서빙할
    수 있다.**
  - **멀티 존·듀얼 리전(region)·멀티 리전 복제를 매우 높은 내구성(durability) 보장과 함께
    제공한다. 덕분에
    데이터베이스가 존 간 네트워크 요금을 우회할 수도 있다.**
  - **오브젝트 스토어의 조건부 쓰기(conditional write) 기능** — 본질적으로 **비교 후 설정
    (compare-and-set, CAS) 연산** — **을 써서 트랜잭션과 리더십 선출을 구현할 수 있다.**
  - **여러 데이터베이스의 데이터를 같은 오브젝트 스토어에 두면 데이터 통합이 단순해진다.**
    Parquet·Iceberg 같은 개방 포맷을 쓸 때 특히 그렇다.
- 이 이점들이 합쳐지는 지점을 저자들이 한 문장으로 적는다 — **트랜잭션·리더십 선출·복제의
  책임을 오브젝트 스토리지로 옮김으로써 데이터베이스 아키텍처를 극적으로 단순화한다** (6장,
  p.203).[^kleppmann2026]
- 대가도 명시된다 (6장, p.203):[^kleppmann2026]
  - **오브젝트 스토어는 로컬 디스크나 Amazon EBS 같은 가상 블록 장치보다 읽기·쓰기 지연이 훨씬
    높다.**
  - **많은 클라우드 제공자가 API 호출당 요금을 물리므로 비용을 줄이려 읽기·쓰기를 배치해야 하고,
    그 배치가 지연을 더 늘린다.**
  - **객체가 흔히 불변이라 큰 객체 안의 무작위 쓰기는 극도로 자원 집약적인 연산이 된다.**
  - **많은 오브젝트 스토어가 표준 파일시스템 인터페이스를 제공하지 않아, 오브젝트 스토리지 통합이
    없는 시스템은 이를 활용할 수 없다.** FUSE(filesystem in userspace) 같은 인터페이스로 버킷을
    파일시스템처럼 마운트할 수 있지만 **많은 FUSE 인터페이스가 비순차 쓰기나 심링크 같은 POSIX
    기능을 결여하며 시스템이 그것에 의존할 수 있다.**
- 시스템마다 대응이 갈린다 (6장, p.203):[^kleppmann2026]
  - **계층형 저장(tiered storage)** — **덜 자주 접근되는 데이터를 오브젝트 스토리지에 두고, 새
    데이터나 자주 접근되는 데이터는 SSD·NVMe, 심지어 메모리 같은 더 빠른 장치에 둔다.**
  - **오브젝트 스토리지를 주 저장 계층으로 쓰되 WAL은 별도의 저지연 저장 시스템에 두는 방식** —
    Amazon EBS나 Neon의 Safekeepers가 그 자리다.
  - **제로 디스크 아키텍처(zero-disk architecture, ZDA)** — **모든 데이터를 오브젝트 스토리지에
    영속시키고 디스크와 메모리는 캐싱 전용으로만 쓴다. 그래서 노드가 영속 상태를 전혀 갖지 않고
    운영이 극적으로 단순해진다.** **WarpStream·Confluent Freight·Buf의 Bufstream·Redpanda
    Serverless가 전부 제로 디스크 아키텍처로 지은 카프카 호환 시스템**이고, **거의 모든 2026년 저술 시점의
    클라우드 데이터 웨어하우스도 그런 아키텍처를 채택하며 Turbopuffer(벡터 검색 엔진)와
    SlateDB(클라우드 네이티브 LSM 저장 엔진)도 그렇다.**
  - 마지막 항목이 [카프카 물리 저장](../concepts/kafka-physical-storage.md)이 전제하는 로컬
    디스크 설계와 정면으로 갈리는 지점이다 — 같은 프로토콜을 말하면서 지속성 계층의 위치가 다르다.
