KEY: why-data-outside-git
--- SUMMARY ---
데이터 엔지니어링이 데이터를 git 밖(S3·DB)에 두는 이유는 1차 소스 기준으로 다섯 속성에 귀착한다: (1) 크기 — GitHub 파일 100MiB 차단·저장소 1–5GB 권장, lakeFS/Iceberg는 페타바이트급 대상, (2) 바이너리 — Git LFS의 명시 대상은 audio/video/datasets/graphics, DVC의 대상은 GB급 model weights, (3) 기계 생성·불변 파일 — Iceberg는 Parquet/ORC/Avro immutable file을 Spark/Trino 등 스캔 엔진이 소비, (4) 동시 다중 쓰기 — Iceberg optimistic concurrency, Wikipedia의 다중 동시 편집자, (5) 대규모 읽기 서빙 — Wikipedia ~10만 hits/s. 사용자 가설의 최선형(steelman)인 Wikipedia는 실제로 본문을 MySQL에 두지만, 그 정당화는 동시성과 서빙이지 저장 효율이 아니다 — Wikipedia조차 revision 텍스트를 diff 압축(~98%)으로 저장하며 이는 git packfile과 동일한 원리다. 반대편 근거: git의 설계 워크로드 자체가 '사람이 저작한 다수의 작은 라인 지향 텍스트 파일'(Linux kernel)이고, packfile delta 압축은 텍스트 버전 이력에 최적이며, 실측 상한은 linux 저장소 6.2GB(정상 작동)·Windows 저장소 300GB(vanilla git 붕괴, GVFS 필요)다. 산수: md 1만 개×10KB=100MB는 GitHub 권장 상한의 1/10, git 실붕괴 지점의 1/3000이고, 현재 syntopicon 실측은 md 218개·0.8MB·.git 3.6MB로 그보다 다시 2자릿수 아래다. 판정 재료: 다섯 속성 중 '사람이 저작한 md 텍스트·단일 작성자' 코퍼스가 공유하는 것은 0개이며, Hive/Iceberg 유추가 실제로 대응하는 계층(기계 생성·기계 소비·재생성 가능 데이터)은 syntopicon에서 이미 git 밖에 있는 파생 인덱스(SQLite·qmd)와 archive/다 — 즉 이 시스템은 이미 그 분리를 수행하고 있고, 남은 질문은 정본(사람이 읽고 쓰는 산문)의 기질인데 그것의 속성은 데이터가 아니라 코드와 동형이다. 콘텐츠를 DB로 옮기는 것이 옳아지는 전환 조건은 소스에서 역산하면 '다중 동시 편집자 등장, 파일당 수십 MiB 바이너리 정본화, 또는 총량이 수 GB를 넘는 기계 생성 콘텐츠'이며, 셋 다 현 시스템 정의(단일 작성자, 사람 저작 텍스트, 10–20년×수천 파일)에서 발생하지 않는다.
--- FINDINGS ---
[LB] git 객체 모델은 파일 버전마다 전체 스냅샷(blob)을 저장하지만, packfile 단계에서 이름·크기가 비슷한 객체들을 delta 압축한다 — 즉 '스냅샷 저장 = 비대화'는 텍스트에는 성립하지 않는다. Pro Git 실측 예: 22K 파일 두 버전이 pack 후 한쪽은 원본, 다른 쪽은 9바이트 delta로 저장.
     src: https://git-scm.com/book/en/v2/Git-Internals-Packfiles (Pro Git 2nd ed. (상시 갱신))
[LB] git이 대용량 파일에 부적합해지는 지점은 GitHub 공식 한도로 정량화된다: 파일 50MiB 경고·100MiB 차단, 저장소 1GB 권장·5GB 이하 강력 권장. 이유는 인프라 성능·클론 속도. 이는 파일당 수 KB인 md와 무관한 자릿수다.
     src: https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github (2026 현행)
[  ] Git LFS의 공식 존재 이유는 '대용량·바이너리'(audio, video, datasets, graphics)를 포인터로 치환해 클론/페치 데이터량을 줄이는 것 — 텍스트 md는 LFS가 겨냥하는 파일 부류에 없다.
     src: https://git-lfs.com/ (2026 현행)
[LB] DVC가 git에서 데이터를 빼는 공식 이유: GB급 model weights·datasets 같은 바이너리 아티팩트가 저장소를 비대화하고 Git hosting 한도에 걸리므로, git에는 경량 .dvc 메타파일만 두고 실데이터는 S3/SFTP/HDFS로 보낸다. 판별 기준은 '크기+바이너리'이지 '데이터냐 아니냐'가 아니다.
     src: https://doc.dvc.org/use-cases/versioning-data-and-models (2026 현행)
[  ] lakeFS가 git을 못 쓰는 이유는 페타바이트 규모: git은 파일 내용 자체를 추적하므로 대규모 데이터셋에 비실용적이고, lakeFS는 데이터를 S3 등 object storage에 둔 채 metadata 연산만으로 zero-copy branching을 한다.
     src: https://docs.lakefs.io/ (2026 현행)
[LB] Dolt의 공식 답변('So you want Git for data?'): git이 데이터에 부적합한 건 100MB 파일 한도뿐 아니라 diff/merge 입도가 라인 단위라 테이블형 데이터에 무의미하고("Diffs on CSV and JSON are of marginal utility in Git"), schema 개념과 query language가 없기 때문. 역으로 이 논거는 '라인 지향 산문 텍스트'에는 git diff가 자연 입도임을 함의한다.
     src: https://www.dolthub.com/blog/2020-03-06-so-you-want-git-for-data/ (2020-03-06)
[LB] Iceberg가 다루는 데이터의 속성 명세: "The open table format for analytic datasets" — 거대(huge) 분석 테이블용 고성능 포맷, Parquet/ORC/Avro immutable data file, Spark·Trino·Flink·Presto·Hive·Impala 등 스캔 엔진이 소비, optimistic concurrency로 동시 다중 writer 지원. 전부 기계 생성·기계 소비 데이터의 속성이다.
     src: https://iceberg.apache.org/spec/ (2026 현행)
[LB] git이 잘 다루는 데이터의 공식 정의는 설계 목표 자체에 있다: git은 Linux kernel — 수만 개의 작은 텍스트 소스 파일, 수천 병렬 브랜치 — 을 속도·데이터 크기 면에서 효율적으로 다루도록 만들어졌다. '사람이 저작한 라인 지향 텍스트 파일 다수'가 git의 설계 워크로드 그 자체다.
     src: https://git-scm.com/book/en/v2/Getting-Started-A-Short-History-of-Git (Pro Git 2nd ed.)
[LB] 실측 상한 캘리브레이션 (1): torvalds/linux — 약 8만+ 텍스트 파일·백만 단위 커밋 이력 전체가 GitHub API 기준 6,246,766KB(~6.2GB)이고 vanilla git으로 정상 작동한다. md 1만 개×10KB=100MB 가정치의 60배 이력을 git이 무리 없이 다룬다는 실증.
     src: https://api.github.com/repos/torvalds/linux (2026-08-08)
[LB] 실측 상한 캘리브레이션 (2): vanilla git이 실제로 무너지는 지점은 Microsoft Windows 저장소 — 3.5M 파일·300GB에서 "many of the commands would take 30 minutes up to hours and a few would never complete" → GVFS 개발. 100MB 코퍼스와는 약 3,000배(3자릿수) 차이.
     src: https://devblogs.microsoft.com/bharry/the-largest-git-repo-on-the-planet/ (2017-05-24)
[LB] steelman — 콘텐츠가 DB에 사는 것이 옳은 조건의 실례: Wikipedia(MediaWiki)는 page/revision/text 테이블(MySQL/MariaDB)에 본문을 저장한다. 성립 조건은 (a) 다수 동시 편집자와 트랜잭션 격리, (b) ~초당 10만 히트 웹 서빙과 캐시 계층, (c) 인덱스 질의 기반 렌더링. 즉 '다중 동시 쓰기 + 대규모 읽기 서빙'이 DB 기질의 정당화다.
     src: https://www.mediawiki.org/wiki/Manual:MediaWiki_architecture (2026 현행)
[LB] steelman의 이면: Wikipedia조차 revision 본문 텍스트를 저장할 때 인접 revision 간 diff+gzip으로 압축률 ~98%를 얻는다 — '산문 텍스트 버전들은 delta 압축이 극히 잘 된다'는 실증이며, 이는 git packfile이 하는 일과 동일하다. DB 기질을 택한 이유는 저장 효율이 아니라 동시성·서빙이다.
     src: https://www.mediawiki.org/wiki/Manual:MediaWiki_architecture (2026 현행)
[LB] syntopicon 로컬 실측: md 218개·총 801,971 bytes(평균 3.7KB/파일), .git 전체 3.6MB. 가정치(1만 파일×10KB=100MB)까지 가도 GitHub 권장 상한(1GB)의 1/10, 파일당 크기는 경고 한도(50MiB)의 1/5000, git 실붕괴 지점(300GB)의 1/3000.
     src: file:///Users/angyojun/workspace/syntopicon (2026-08-08)
[LB] 속성 대조표 — 데이터를 git 밖에 두는 5속성 중 md 코퍼스가 공유하는 것은 0개: [크기] PB(Iceberg/lakeFS)·GB바이너리(DVC) vs ~100MB 텍스트 상한 — 불공유. [바이너리] LFS 대상은 audio/video/datasets vs 라인 지향 UTF-8 산문 — 불공유. [기계생성·불변파일] Iceberg는 엔진이 쓰고 엔진이 스캔 vs 사람이 저작·에이전트가 편집·사람이 읽음 — 불공유. [동시다중쓰기] Iceberg optimistic concurrency·Wikipedia 다중 편집자 vs 단일 작성자 — 불공유. [스캔/서빙 소비] 10만 hits/s 웹서빙 vs 파생 인덱스(SQLite·qmd)는 이미 git 밖 소모품으로 분리됨 — 불공유(그리고 그 분리는 이미 시행 중).
     src: https://iceberg.apache.org/ (2026-08-08)
--- UNRESOLVED ---
 - DVC·lakeFS 문서의 축자 인용 미확보 — WebFetch 요약 모델의 패러프레이즈에 의존(취지는 교차 확인됨). 원문 직접 열람으로 인용 문구 확정 필요.
 - Iceberg spec의 정확한 규모 표현('huge, petabyte-scale' 등)은 홈페이지 헤드라인만 축자 확보. spec 본문의 축자 인용은 미확정.
 - WebSearch 세션 예산(200/200) 소진으로 '대형 텍스트 전용 저장소'(예: 위키 덤프를 git에 넣은 실험, 학술 벤치마크)의 추가 실증 사례를 탐색하지 못함 — Linux/Windows 두 캘리브레이션 점으로 갈음.
 - Wikipedia 'over 100,000 hits per second' 수치의 측정 시점이 MediaWiki 문서에 명시돼 있지 않음(문서 자체가 다소 오래된 수치일 가능성).
 - git이 '다수의 작은 파일'에서 성능 저하를 보이기 시작하는 파일 개수 임계(수십만~수백만 구간)의 정밀한 1차 벤치마크는 미확보 — Windows 사례(3.5M 파일)로 상한만 확인. 다만 1만 파일은 linux 트리(8만+)보다도 작아 판정에는 영향 없음.

데이터 엔지니어링 생태계 자신의 실측 결과, 경계선은 사용자 유비("데이터는 git 밖")가 가정하는 "코드 vs 데이터"가 아니라 "사람이 저작·리뷰하는 작은 텍스트 = git / 기계가 생성하는 대량·민감 산출물 = 외부 저장소(DB·S3)"로 그어져 있고, 이는 공식 문서들에 명문화되어 있다. 양방향 모두 확인된다: dbt는 '데이터'(CSV)라도 작고 정적이고 사람이 관리하면 git에 커밋하라고 공식 안내하며(seeds: "version controlled and code reviewable"), 반대로 Terraform은 '텍스트'(JSON state)라도 기계 생성물이면 git에서 배제하고 S3류 원격 백엔드에 두라고 안내한다. 즉 판별자는 포맷이 아니라 저작 주체·크기·리뷰 필요성이다. Hive/Iceberg에서 S3로 분리되는 것은 기계가 적재한 테이블 데이터이고, 그 테이블을 정의하는 DDL·dbt 모델·설명문·DAG·매니페스트는 전부 git에 산다 — 유비를 syntopicon에 정확히 대응시키면 S3 쪽에 해당하는 것은 archive/ 스냅샷·SQLite·qmd 색인(이미 git 밖·restic/재생성)이고, 사람이 저작·리뷰·diff하는 지식 md는 dbt models·docs와 같은 쪽이므로 현 설계가 이미 데이터 엔지니어링의 경계와 동형이다. 사용자 가설이 옳아지는 조건도 실재한다(Wikipedia의 wikitext는 MySQL에, DataHub의 설명문은 metadata store에): 다수 동시 저자, 웹 UI가 유일한 편집 수단, 대량 서빙, 세밀한 권한 — 특히 같은 종류의 콘텐츠(데이터셋 설명문)를 dbt는 git에, DataHub는 DB에 두는 대비가 갈림 요인이 '편집 주체 수와 인터페이스'임을 보여준다. 이 조건들은 단일 작성자·에이전트가 파일을 직접 읽고 편집·수십~수천 파일 규모인 이 시스템에 하나도 성립하지 않으므로, 실측된 판정 재료는 PLAN 원칙 1(md+git=canonical substrate) 유지 쪽을 지지한다.

--- SUMMARY ---
결론 재료: '콘텐츠는 DB에'가 옳은 조건은 실재하지만(Wikipedia: 활성 편집자 25만·초당 ~1.9 편집·초당 10만 hit·익명 웹 편집 UI·행 수준 권한 — MediaWiki도 원래 flat file이었다가 이 압력으로 DB화), syntopicon에는 그 조건이 하나도 성립하지 않는다(단일 작성자·세션 직렬 편집·읽기 부하 0). 사용자의 Hive/Iceberg 유비는 범주 오류로 판정할 재료가 있다: Iceberg는 스스로 '거대 분석 테이블용' 포맷이라 명시하며, 분리 대상은 기계 생성 tabular data다. 사람이 저작하는 텍스트의 업계 정본은 소스 코드와 같은 취급 — Microsoft Learn(azure-docs 27GB 리포, md+PR), Google 문서 가이드, Write the Docs가 실증한다. 오히려 syntopicon의 현 구조(정본=md/git, SQLite·qmd=재생성 파생물)가 lakehouse 패턴의 올바른 등가물이다: '정본 기질 + 소모성 인덱스 계층'. git-as-DB 반대론(질의 불가·동시 쓰기 race·~110 commits/s·구조화 데이터 diff 무용)은 전수 점검 결과 단일 작성자·산문 md·파생 인덱스 분담 구조에서 전부 기각되고, 같은 반대론자들이 git이 맞다고 인정하는 조건(버저닝·감사 이력·오프라인·승인 워크플로)이 정확히 이 시스템의 요구다. DB 정본의 exit 비용은 Notion 자체 문서가 실증(export 라운드트립 불가·30시간·부분 손실). 에이전트 관점에서도 Claude Code의 1급 인터페이스(Read/Edit/grep/git)와 지속 메커니즘(CLAUDE.md/SKILL.md)이 전부 파일이라, DB 이전은 에이전트를 2급 통로(MCP/SQL)로 강등시킨다. 단 하나의 통념 교정: LOC 권장 포맷에서 plain text는 최상위가 아니라 하위 tier(Preferred는 XML/EPUB3/PDF-A, 인코딩만 UTF-8 최우선)이므로 '공공기관이 plain text를 최상위 권장'이라는 논거는 쓰지 말 것 — 다만 proprietary DB 내부 표현은 아예 목록에 없다. 종합: PLAN 원칙 1을 뒤집을 실증 근거는 발견되지 않았고, DB 정본이 옳아지는 조건(다수 동시 편집자, 비기술 편집자용 웹 UI, 행 수준 권한, 기계 생성 tabular 데이터)이 미래에 생기면 그때 재심하는 조건부 트리거로 기록하는 것이 타당하다.

[LB] git-as-database 반대론의 실제 논거 목록과 이 시스템에의 적용 판정: (1) 질의 불가 — "You can query by key … and that's about it"; (2) 동시 쓰기 race — "Between the time you commit and update the branch head, another commit might get in"; (3) 쓰기 처리량 ~110 commits/sec 한계; (4) 자동 머지 불가한 데이터 충돌. 적용 판정: (1)은 syntopicon에서 파생 인덱스(SQLite·qmd)가 담당하도록 이미 설계됨(반대론 자체가 'separate indices'를 해법으로 언급); (2)(4)는 단일 작성자·세션 직렬 편집에서 성립하지 않음; (3) 110 commits/sec는 인간+에이전트 ingest 속도의 수천 배. 같은 저자가 git이 잘 맞는 조건으로 든 것 — 계층 데이터, 오프라인 동작, 무료 버저닝·감사 이력, 승인 워크플로 — 은 전부 이 시스템의 요구와 일치한다.

KEY: git-text-limits
--- SUMMARY ---
판정 재료 요약 — git 한계 실측 vs 사용자 KB 규모.

(1) git이 실제로 무너지는 지점은 실측으로 확정된다: Windows 저장소 3.5M 파일/300GB에서 vanilla git 명령이 30분–수 시간(일부 미완료)이라 GVFS가 필요했고(MS 1차 소스, 2017), Facebook은 '커널의 수 배 + 하루 수천 커밋' 규모에서 성장 투영에 근거해 Mercurial로 갔다(2014). 반면 Linux(1.46M 커밋/6.25GB)와 Chromium(1.80M 커밋/65.8GB)은 오늘도 plain git으로 동작한다(GitHub API 2026-08-08 실측).

(2) 문서 코퍼스의 직접 증거: MDN content는 md 14,587개/502MB/29,615커밋을 plain git + PR 리뷰로 운영 중이다. 사용자 KB의 20년 공격적 상한(약 3.1만 md/약 620MB/약 5.2만 커밋)이 정확히 이 '검증된 동작 구간'이며, git이 무너진 실측선에서 파일 수 약 2자릿수, 크기 약 3자릿수 아래다. 현재 45개 파일 기준으로는 전 구간이 여유다.

(3) 사용자 가설을 성실히 검토한 결과, 콘텐츠가 DB에 사는 것이 옳은 조건은 실재하지만(Wikipedia/MediaWiki: 다수 동시 편집자의 트랜잭션, 초당 10만+ 히트 서빙, 리비전 압축 스토리지) 단일 작성자·로컬·에이전트 매개 KB에는 하나도 성립하지 않는다. SQLite 공식 문서조차 서버형 DB의 경계를 '네트워크 다중 동시 접근'으로 긋는다. Hive/Iceberg의 데이터-코드 분리는 TB–PB급 기계 생성 데이터와 다중 엔진 동시 접근이 동기이며, 사람이 라인 단위로 리뷰하는 산문 코퍼스는 그 의미의 'data'가 아니라 'code' 쪽 성질이다 — 사용자 시스템에서 그 분리는 이미 archive/(git 밖, restic)와 파생 인덱스(git 밖, 소모품)에 적용되어 있다.

(4) 대안 기질 비용: Postgres 정본은 정책상 20년간 최소 4회 이상의 강제 메이저 마이그레이션(5년 EOL, pg_upgrade/dump 필수)을 수반한다. SQLite 정본(중간형)은 장수 측면에서는 유효하나(2050년 지원 공약, 의회도서관 보존 권장 포맷) text diff·blame·리뷰를 구조적으로 포기한다 — SQLite 자신의 appfileformat 문서도 VCS diffability를 다루지 않는다. git-산문의 실제 한계(문단 rewrap 시 라인 diff 노이즈)는 명세 수준으로 인정되어 있고 Semantic Line Breaks·word-diff라는 표준 완화책이 있으며, 산문의 git 리뷰는 Google/MS/AWS가 쓰는 업계 표준 관행(Docs as Code)이다.

결론 재료: PLAN 원칙 1(md+git=정본)을 뒤집을 실측 근거는 발견되지 않았다. DB 정본이 옳아지는 조건(다중 동시 작성자, 대규모 서빙, 수백 GB–TB급)은 이 시스템 규모·형태와 2–3자릿수 이상 떨어져 있다.
