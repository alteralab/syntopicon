하나의 질문: **데이터 엔지니어링의 다음이 무엇이냐는 물음에 2022년의 저자들은 무엇이라
답했고, 그 답의 어디까지가 근거 있는 추론이고 어디부터가 추측인가.**

## 이 페이지의 서술 지위

> **이 페이지의 claim은 사실 서술이 아니라 2022년 집필 시점 저자들의 전망이다.** 저자들 스스로
> 그렇게 표시한다 — **아무도 미래를 예측할 수 없지만 우리는 과거·현재·현행 추세에 대한 좋은
> 시야를 갖고 있다. 이 마지막 장은 진행 중인 발전의 관측과 야생의 미래 추측을 포함해 미래에 대한
> 우리 생각을 제시한다** (11장, p.379).[^reis2022] 그래서 이하 항목에는 `#hypothesis`를 달았다.
> 실현 여부의 사후 채점은 이 페이지의 몫이 아니다 — 이 페이지가 보존하는 것은 **2022년에 이
> 분야가 자기 다음을 어떻게 상상했는가**다.

- 저자들이 무엇을 골랐는지의 기준 — **이 책에서 우리는 앞으로 몇 년 동안 유용하리라 느끼는 큰
  생각에 집중한다 — 그래서 데이터 엔지니어링 수명 주기와 그 저류의 연속체다. 운영 순서와 모범 실무·
  기술의 이름은 바뀔 수 있지만 수명 주기의 일차 단계는 앞으로 여러 해 온전히 남을 가능성이 크다**
  (11장, p.379).[^reis2022] 잡음을 걸러 **바뀔 것 같지 않은 것**을 찾는 일이 이 책을 조직하는 데
  가장 어려운 부분이었다고 밝힌다 (11장, p.379).[^reis2022]

## 클라우드 규모의 데이터 OS와 상호운용성

- 비유의 출발 — **스마트폰이든 랩톱이든 애플리케이션 서버든 스마트 온도조절기든, 이 기기들은
  필수 서비스를 제공하고 태스크와 프로세스를 오케스트레이션하기 위해 운영체제에 의존한다.
  머신에서 애플리케이션을 돌릴 때 그것은 사운드·그래픽 하드웨어에 직접 접근하지 않는다. 대신
  운영체제 서비스에 명령을 보내 창을 그리고 소리를 낸다. 이 명령은 표준 API로 발행된다** (11장,
  p.381).[^reis2022]
- 데이터로 옮기면 — **이 책 전반에서 언급한 단순화된 데이터 서비스(예컨대 Google Cloud BigQuery·
  Azure Blob Storage·Snowflake·AWS Lambda)는 운영체제 서비스를 닮았지만 훨씬 큰 규모로, 단일
  서버가 아니라 많은 머신에 걸쳐 돈다** (11장, p.382).[^reis2022] #hypothesis
- 다음 층 — **이 단순화된 서비스가 가용해진 지금, 클라우드 데이터 운영체제라는 이 관념의 다음
  진화 전선은 더 높은 추상화 수준에서 일어날 것이다. Benn Stancil은 데이터 파이프라인과 데이터
  애플리케이션을 짓기 위한 표준화된 데이터 API의 출현을 요청했다. 우리는 데이터 엔지니어링이 소수의
  데이터 상호운용 표준 주위로 점차 응집하리라 예측한다. 클라우드의 오브젝트 저장은 다양한 데이터
  서비스 사이의 배치 인터페이스 계층으로서 중요성이 커질 것이다. Parquet·Avro 같은 새 세대 파일
  형식은 이미 클라우드 데이터 교환 목적으로 자리를 넘겨받아 CSV의 끔찍한 상호운용성과 원시 JSON의
  형편없는 성능을 유의하게 개선하고 있다** (11장, p.382).[^reis2022] #hypothesis 그 형식들의
  실물은 [데이터 인코딩 형식](../concepts/data-encoding-formats.md)에 있다.
- 메타데이터가 재료다 — **데이터 API 생태계의 또 다른 결정적 재료는 스키마와 데이터 계층을 서술하는
  메타데이터 카탈로그다. 2022년 저술 시점에 이 역할은 대체로 레거시 Hive 메타스토어가 채우고 있다. 우리는 새
  진입자가 그 자리를 넘겨받으리라 기대한다. 메타데이터는 애플리케이션과 시스템에 걸쳐, 그리고
  클라우드와 네트워크에 걸쳐 데이터 상호운용성에서 결정적 역할을 하며 자동화와 단순화를 이끌 것이다**
  (11장, p.382).[^reis2022] #hypothesis
- 오케스트레이션도 자란다 — **우리는 클라우드 데이터 서비스를 관리하는 발판에서도 유의한 개선을 볼
  것이다. Apache Airflow가 첫 진정한 클라우드 지향 데이터 오케스트레이션 플랫폼으로 등장했지만
  우리는 유의한 향상의 문턱에 있다. Airflow는 그 방대한 인지도 위에서 능력을 키울 것이다.
  Dagster·Prefect 같은 새 진입자는 오케스트레이션 아키텍처를 바닥부터 다시 지어 경쟁할 것이다**
  (11장, p.382).[^reis2022] #hypothesis
  - 무엇이 더해지는가 — **이 차세대 데이터 오케스트레이션 플랫폼은 강화된 데이터 통합과 데이터
    인지를 특징으로 할 것이다. 오케스트레이션 플랫폼은 데이터 카탈로깅·계보와 통합되어 그 과정에서
    유의하게 더 데이터를 인지하게 된다. 더해서 오케스트레이션 플랫폼은 (Terraform 같은) IaC 능력과
    (GitHub Actions·Jenkins 같은) 코드 배포 기능을 지을 것이다. 이는 엔지니어가 파이프라인을 코딩한
    다음 그것을 오케스트레이션 플랫폼에 넘겨 자동으로 빌드·테스트·배포·모니터링하게 해 줄 것이다.
    엔지니어는 인프라 명세를 파이프라인에 직접 쓸 수 있을 것이며, 빠진 인프라와 서비스(Snowflake
    데이터베이스·Databricks 클러스터·Amazon Kinesis 스트림 같은)는 파이프라인이 처음 돌 때 배포될
    것이다** (11장, p.382).[^reis2022] #hypothesis 2022년 저술 시점의 DAG 실행 모델은
    [배치 워크플로와 DAG](../concepts/batch-workflows-and-dags.md)에 있다.
- 라이브 데이터 쪽 — **우리는 라이브 데이터(live data) 영역에서도 유의한 향상을 볼 것이다 — 예컨대
  스트리밍 데이터를 반입하고 질의할 수 있는 스트리밍 파이프라인과 데이터베이스. 과거에 스트리밍
  DAG를 짓는 것은 높은 지속적 운영 부담을 동반한 극도로 복잡한 프로세스였다. Apache Pulsar 같은
  도구는 스트리밍 DAG가 상대적으로 단순한 코드로 복잡한 변환과 함께 배포될 수 있는 미래를 가리킨다**
  (11장, p.383).[^reis2022] #hypothesis

## MDS는 그리 모던하지 않다

- 진단 — **솔직히 말해 모던 데이터 스택(MDS)은 2022년 저술 시점에 그리 모던하지 않다. 우리는 MDS가 강력한 데이터 도구의
  훌륭한 선택지를 대중에게 가져오고 가격을 낮추고 데이터 분석가가 자기 데이터 스택의 통제권을 쥐게 한
  것에 박수를 보낸다. ELT의 부상, 클라우드 데이터 웨어하우스, SaaS 데이터 파이프라인의 추상화는
  많은 회사에서 판을 확실히 바꿔 BI·분석·데이터 과학에 새 힘을 열어 주었다** (11장,
  p.385).[^reis2022]
- 그러나 — **그렇게 말했지만 MDS는 기본적으로 2022년 저술 시점의 클라우드와 SaaS 기술을 써서 옛 데이터 웨어하우스
  실무를 재포장한 것이다. MDS가 클라우드 데이터 웨어하우스 패러다임 주위로 지어졌기 때문에, 차세대
  실시간 데이터 애플리케이션의 잠재력과 비교하면 몇 가지 심각한 한계를 갖는다. 우리 관점에서 세계는
  데이터 웨어하우스 기반의 내부 대면 분석·데이터 과학의 사용을 넘어, 차세대 실시간 데이터베이스로
  기업 전체와 애플리케이션을 실시간으로 구동하는 쪽으로 움직이고 있다** (11장, p.385).[^reis2022]
  #hypothesis 2022년 저술 시점 "모던 데이터 스택"의 서술 자체는 [데이터 레이크](../concepts/data-lake.md)에 있다.
- 무엇이 이 진화를 미는가 — **많은 경우 분석(BI와 운영 분석)은 자동화로 대체될 것이다. 2022년 저술 시점에 대부분의
  대시보드와 리포트는 *무엇*과 *언제*에 관한 질문에 답한다. 스스로 물으라, "*무엇*이나 *언제* 질문을
  하고 있다면 다음에 나는 어떤 행동을 취하는가?" 그 행동이 반복적이라면 그것은 자동화의 후보다.
  이벤트가 일어날 때 행동을 자동화할 수 있는데 왜 리포트를 보고 행동을 결정하는가?** (11장,
  p.385).[^reis2022] #hypothesis
- 실물의 근거 — **TikTok·Uber·Google·DoorDash 같은 제품을 쓰는 것이 왜 마법처럼 느껴지는가? 버튼 한
  번으로 짧은 영상을 보고 차나 음식을 주문하고 검색 결과를 찾는 것처럼 보이지만 후드 아래에서는 많은
  일이 일어나고 있다. 이 제품들은 진정한 실시간 데이터 애플리케이션의 예로, 극도로 정교한 데이터
  처리와 ML을 아주 작은 지연으로 수행하면서 버튼 한 번에 필요한 행동을 전달한다. 2022년 저술 시점에 이 수준의
  정교함은 큰 기술 회사의 맞춤 제작 기술 뒤에 잠겨 있지만, MDS가 클라우드 규모 데이터 웨어하우스와
  파이프라인을 대중에게 가져온 것과 비슷하게 이 정교함과 힘은 민주화되고 있다. 데이터 세계는 곧
  "라이브"가 될 것이다** (11장, p.385).[^reis2022] #hypothesis

## MDS의 후계자

- 정의 — **실시간 기술의 이 민주화가 우리를 MDS의 후계자로 이끌 것이다: 라이브 데이터 스택(live
  data stack)이 곧 접근 가능하고 널리 퍼질 것이다. 라이브 데이터 스택은 스트리밍 기술을 써서
  실시간 분석과 ML을 애플리케이션에 융합하며, 애플리케이션 원천 시스템에서 데이터 처리와 ML까지,
  그리고 되돌아오는 전체 데이터 수명 주기를 포괄한다** (11장, p.385).[^reis2022] #hypothesis
- 무엇을 반복하는가 — **MDS가 클라우드를 활용해 온프레미스 데이터 웨어하우스와 파이프라인 기술을
  대중에게 가져온 것처럼, 라이브 데이터 스택은 엘리트 기술 회사에서 쓰이는 실시간 데이터 애플리케이션
  기술을 가져다 모든 규모의 회사가 쓰기 쉬운 클라우드 기반 제공물로 만든다. 이는 더 나은 사용자 경험과
  업무 가치를 만드는 새로운 가능성의 세계를 열 것이다** (11장, p.386).[^reis2022] #hypothesis

## 스트리밍 파이프라인과 실시간 분석 데이터베이스

- 두 핵심 기술 — **MDS는 데이터를 경계 있는 것으로 다루는 배치 기법에 스스로를 한정한다. 대조적으로
  실시간 데이터 애플리케이션은 데이터를 경계 없는 연속 스트림으로 다룬다. 스트리밍 파이프라인과 실시간
  분석 데이터베이스가 MDS에서 라이브 데이터 스택으로의 이동을 촉진할 두 핵심 기술이다. 이 기술들이
  한동안 존재해 왔지만 빠르게 성숙하는 관리형 클라우드 서비스가 그것들이 훨씬 널리 배포되게 할 것이다**
  (11장, p.386).[^reis2022] #hypothesis
- 스트리밍의 위상 변화 — **스트리밍 기술은 예측 가능한 미래 동안 극단적 성장을 계속 볼 것이다. 이는
  스트리밍 데이터의 업무적 효용에 대한 더 명확한 초점과 함께 일어날 것이다. 2022년 저술 시점까지 스트리밍 시스템은
  흔히 비싼 신기함이나 A에서 B로 데이터를 옮기는 멍청한 파이프로 다뤄졌다. 미래에 스트리밍은 조직의
  기술과 업무 프로세스를 근본적으로 변형시킬 것이며, 데이터 아키텍트와 엔지니어가 이 근본적 변화를
  이끌 것이다** (11장, p.386).[^reis2022] #hypothesis
- 실시간 분석 데이터베이스 — **실시간 분석 데이터베이스는 이 데이터에 대한 빠른 반입과 초 이하 질의를
  모두 가능하게 한다. 이 데이터는 역사적 데이터셋과 강화되거나 결합될 수 있다. 스트리밍 파이프라인과
  자동화, 혹은 실시간 분석이 가능한 대시보드와 결합되면 완전히 새로운 수준의 가능성이 열린다. 더는
  느리게 도는 ELT 프로세스·15분 갱신·다른 느리게 움직이는 부품에 제약받지 않는다. 데이터는 연속적인
  흐름으로 움직인다. 스트리밍 반입이 더 널리 퍼지면서 배치 반입은 점점 덜 흔해질 것이다. 데이터
  파이프라인의 머리에 왜 배치 병목을 만드는가? 우리는 결국 배치 반입을 지금 다이얼업 모뎀을 보는 것과
  같은 방식으로 보게 될 것이다** (11장, pp.386–387).[^reis2022] #hypothesis
- 어떤 데이터베이스가 이것을 하는가 — **데이터 웨어하우스와 데이터 레이크는 많은 양의 데이터를
  보관하고 애드혹 질의를 수행하는 데는 훌륭하지만, 빠르게 움직이는 데이터에 대한 저지연 데이터
  반입이나 질의에는 그리 잘 최적화돼 있지 않다. 라이브 데이터 스택은 스트리밍을 위해 특별히 지어진
  OLAP 데이터베이스로 구동될 것이다. 2022년 저술 시점에 Druid·ClickHouse·Rockset·Firebolt 같은 데이터베이스가
  차세대 데이터 애플리케이션의 백엔드를 구동하는 데서 앞장서고 있다. 우리는 스트리밍 기술이 빠르게
  진화하고 새 기술이 확산되리라 기대한다** (11장, p.387).[^reis2022] #hypothesis

## ELT에서 STL로

- 되돌아감 — **스트림의 부상과 함께 우리는 데이터 변환에서 과거로의 회귀 순간을 기대한다. 우리는
  ELT에서 벗어나 — 데이터베이스 안 변환 — ETL처럼 보이는 무언가로 옮겨 갈 것이다. 우리는 잠정적으로
  이것을 스트림·변환·적재(stream, transform, and load, STL)라 부른다. 스트리밍 맥락에서 추출은
  지속적이고 끝나지 않는 프로세스다. 물론 배치 변환이 완전히 사라지지는 않을 것이다. 배치는 모델 학습·
  분기 리포팅 등에 여전히 아주 유용할 것이다. 그러나 스트리밍 변환이 표준이 될 것이다** (11장,
  p.387).[^reis2022] #hypothesis 배치 쪽 변환의 본가는
  [수명 주기의 변환 단계](../concepts/transformation-in-the-lifecycle.md)다.

## 데이터 모델링이 상류로 간다

- 저자들이 지목하는 공백 — **또 하나 파괴가 무르익었다고 보는 영역은 데이터 모델링으로, 여기서는
  2000년대 초 이래 진지한 혁신이 없었다. 8장에서 배운 전통적인 배치 지향 데이터 모델링 기법은
  스트리밍 데이터에 맞지 않는다. 새 데이터 모델링 기법은 데이터 웨어하우스 안이 아니라 데이터를
  생성하는 시스템에서 일어날 것이다. 우리는 데이터 모델링이 — 시맨틱·지표·계보·데이터 정의를 포함한
  — 상류 정의 계층(upstream definitions layer)이라는 어떤 관념을 수반하리라 기대하며, 그것은
  애플리케이션에서 데이터가 생성되는 곳에서 시작한다. 모델링은 데이터가 전체 수명 주기를 통해 흐르고
  진화하면서 모든 단계에서도 일어날 것이다** (11장, p.387).[^reis2022] #hypothesis 그 정의 계층의
  2022년 저술 시점 판본이 [시맨틱 계층과 메트릭 계층](../concepts/semantic-and-metrics-layers.md)이고,
  대체 대상으로 지목된 기법은 [차원 모델링](../concepts/dimensional-modeling.md) 계열이다.

## 애플리케이션과 데이터의 융합

- 진단 — **우리는 다음 혁명이 애플리케이션 계층과 데이터 계층의 융합이라 기대한다. 지금 애플리케이션은
  한 영역에 앉아 있고 MDS는 다른 영역에 앉아 있다. 설상가상으로 데이터는 그것이 분석에 어떻게 쓰일지에
  대한 고려 없이 만들어진다. 결과적으로 시스템들이 서로 말하게 하려면 많은 덕트 테이프가 필요하다. 이
  누덕누덕한 사일로 설정은 어색하고 볼품없다** (11장, p.387).[^reis2022]
- 전망 — **곧 애플리케이션 스택은 데이터 스택이 될 것이고 그 반대도 마찬가지일 것이다. 애플리케이션은
  스트리밍 파이프라인과 ML로 구동되는 실시간 자동화와 의사결정을 통합할 것이다. 데이터 엔지니어링
  수명 주기가 반드시 바뀌지는 않겠지만 수명 주기 단계 사이의 시간은 극적으로 짧아질 것이다. OLTP와
  OLAP 유스케이스의 혼합을 다루도록 설계된 신흥 데이터베이스 기술에 주의를 기울이라. 피처 스토어도
  ML 유스케이스에서 비슷한 역할을 할 수 있다** (11장, p.387).[^reis2022] #hypothesis

## 앱과 ML의 타이트한 피드백

- **또 하나 우리가 흥분하는 영역은 애플리케이션과 ML의 융합이다. 2022년 저술 시점에 애플리케이션과 ML은 분리된
  시스템으로, 애플리케이션과 분석의 관계와 같다. 소프트웨어 엔지니어는 여기서 자기 일을 하고 데이터
  과학자와 ML 엔지니어는 저기서 자기 일을 한다** (11장, p.388).[^reis2022]
- 왜 붙을 것인가 — **ML은 데이터가 사람이 손으로 처리할 수 없을 만큼 높은 속도와 양으로 생성되는
  시나리오에 잘 맞는다. 데이터 크기와 속도가 자라면서 이는 모든 시나리오에 적용된다. 빠르게 움직이는
  데이터의 높은 양은 정교한 워크플로·행동과 결합되어 ML의 후보다. 데이터 피드백 루프가 짧아지면서
  우리는 대부분의 애플리케이션이 ML을 통합하리라 기대한다. 데이터가 더 빨리 움직이면서 애플리케이션과
  ML 사이의 피드백 루프는 더 타이트해질 것이다. 라이브 데이터 스택의 애플리케이션은 지능적이며
  데이터의 변화에 실시간으로 적응할 수 있다. 이는 점점 더 똑똑한 애플리케이션과 커지는 업무 가치의
  순환을 만든다** (11장, p.388).[^reis2022] #hypothesis

## 다크 매터 데이터와 스프레드시트

- 무시된 사실 — **가장 널리 쓰이는 데이터 플랫폼은 무엇인가? 그것은 소박한 스프레드시트다. 어느
  추정치를 읽느냐에 따라 스프레드시트의 사용자 기반은 7억에서 20억 명 사이다. 스프레드시트는 데이터
  세계의 다크 매터다. 상당량의 데이터 분석이 스프레드시트에서 돌아가며 이 책이 서술하는 정교한 데이터
  시스템에는 결코 이르지 않는다. 많은 조직에서 스프레드시트가 재무 리포팅·공급망 분석, 심지어 CRM을
  다룬다** (11장, p.388).[^reis2022]
- 왜 이기는가 — **본질적으로 스프레드시트란 무엇인가? 스프레드시트는 복잡한 분석을 지원하는 대화식
  데이터 애플리케이션이다. pandas(파이썬 데이터 분석 라이브러리) 같은 순수 코드 기반 도구와 달리
  스프레드시트는 파일을 열어 리포트를 볼 줄만 아는 사람부터 정교한 절차적 데이터 처리를 스크립트할 수
  있는 파워 유저까지 사용자 전 스펙트럼에 접근 가능하다. 지금까지 BI 도구는 데이터베이스에 비견할
  만한 대화성을 가져오는 데 실패했다. UI와 상호작용하는 사용자는 보통 특정 가드레일 안에서 데이터를
  자르고 써는 데 한정되며 범용 프로그램적 분석은 하지 못한다** (11장, p.388).[^reis2022]
- 전망 — **우리는 스프레드시트의 대화식 분석 능력을 클라우드 OLAP 시스템의 백엔드 힘과 결합하는 새
  부류의 도구가 나타나리라 예측한다. 실제로 몇몇 후보가 이미 경합 중이다. 이 제품 범주의 궁극적
  승자는 스프레드시트 패러다임을 계속 쓸 수도 있고, 데이터와 상호작용하는 완전히 새 인터페이스 관용구를
  정의할 수도 있다** (11장, p.388).[^reis2022] #hypothesis

## 저자들이 스스로 붙인 확신의 등급

- 두 갈래로 갈라 놓는다 — **우리 예측의 어떤 측면은 상대적으로 안전한 기반 위에 있다. 관리형 도구의
  단순화와 "엔터프라이지" 데이터 엔지니어링의 부상은 우리가 이 책을 쓰는 동안 나날이 진행됐다. 다른
  예측은 본성상 훨씬 더 추측적이다. 우리는 신흥 라이브 데이터 스택의 힌트를 보지만, 이는 개별 엔지니어와
  그들을 고용하는 조직 양쪽에 유의한 패러다임 전환을 수반한다. 아마 실시간 데이터를 향한 추세는 다시
  한번 멎고, 대부분의 회사가 기본적인 배치 처리를 계속할 것이다. 분명 우리가 식별하는 데 완전히 실패한
  다른 추세가 존재한다. 기술의 진화는 기술과 문화의 복잡한 상호작용을 수반한다. 둘 다 예측 불가능하다**
  (11장, p.389).[^reis2022] 이 절이 위 `#hypothesis` 표시의 근거다.
- 도구를 쓰는 쪽도 추세를 정한다 — **미래에 관해 여러분 중 다수가 다음에 무엇이 올지 결정하는 역할을
  할 것이다. 기술 추세는 기저 기술을 만드는 이들만이 아니라 그것을 채택하고 잘 쓰는 이들에 의해서도
  정의된다. 성공적인 도구 *사용*은 도구 *창조*만큼 결정적이다** (11장, p.389).[^reis2022]
