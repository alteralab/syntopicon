이 페이지의 질문: **가상 머신에 문제가 생겼을 때 명령 줄에서 무엇으로 어떤 데이터를
꺼내는가.**

## 무엇을 데이터라 부르는가

- 문제 해결의 세 요소가 먼저 정의된다 — **시스템에서 발생한 문제의 원인을 찾을 때 관련 기초
  지식은 탄탄한 토대가 되고 데이터는 근거가 되며 도구는 지식을 활용해 데이터를 처리하는 수단이
  된다** (4장, p.197).[^zhou2024]
- **여기서 말하는 데이터는 예외 스택, 가상 머신 운영 로그, 가비지 컬렉터 로그, 스레드 덤프
  스냅숏(javacore 파일), 힙 덤프 스냅숏(hprof 파일) 등을 모두 포괄한다** (4장,
  p.197).[^zhou2024]
- 그리고 도구에 기대는 것을 경계한다 — **도구를 익히기 앞서, 도구를 자유자재로 다루는 힘은
  지식과 기술에 있다는 사실을 깨달아야 한다. 아무리 좋은 도구라도 그저 갖고 있기만 해서는
  문제를 해결하는 최종 병기가 될 수 없다** (4장, p.197).[^zhou2024]

## 도구의 세 범주와 얇은 래퍼 구조

- JDK가 주는 도구는 **라이선스와 성숙 수준에 따라 세 범주**로 나뉜다 (4장,
  pp.198–199):[^zhou2024]
  - **상용 인증 도구** — **JMC와 JFR이 여기 속한다. 개인 개발 목적으로는 무료이나 상용 환경에서
    이용하려면 비용을 지불해야 한다.**
  - **공식 지원 도구** — **장기간 지원되는 도구들이다. 플랫폼이나 JDK 버전에 따라 작은 차이는
    있을 수 있지만 갑자기 사라지는 일은 없을 것**이며, **제거되기 전에 '폐기 대상' 기간이
    주어진다**는 뜻이다.
  - **실험적 도구** — **'공식 지원되지 않으며 실험적'이라는 딱지가 붙은 도구들**이며 **차후 앞의
    두 범주로 승격될 수도 있고 소리 소문 없이 사라질 수도 있다.**
- 파일 크기에서 구조가 드러난다 — **도구들 대부분은 크기가 이상하리만치 작아 상당수가 고작
  20KB 내외인데, JDK 개발 팀이 일부러 통일한 건 아니고 그저 얇은 래퍼 형태의 명령 줄 도구들이기
  때문이다. 실제 동작하는 코드는 자바로 구현되어 JDK 도구 라이브러리에 담겨 있다** (4장,
  p.199).[^zhou2024]
  - **리눅스 버전 JDK에서는 이 도구들 중 상당수가 셸 스크립트로 작성되어 있어서 텍스트 편집기로
    수정할 수도 있다** (4장, p.199).
  - 그렇게 만든 이유가 운영 제약이다 — **애플리케이션이 프로덕션 환경에 배포되면 서버에
    물리적으로 직접 접근하거나 SSH 등으로 원격 접속하는 데 제약이 있을 수 있다. 이럴 경우라도
    개발자는 JDK 도구 라이브러리의 인터페이스와 구현 코드를 이용하여 강력한 모니터링과 분석
    기능을 애플리케이션에서 직접 제공할 수 있다** (4장, p.199).
  - 다만 이식성에 조건이 붙는다 — **일부 도구는 자바 SE 표준이 아닌 API를 쓰기도 하며, 이에
    해당하는 도구는 핫스팟(또는 오라클에서 JDK 소스 코드 라이선스를 구입한 가상 머신)에서만
    실행될 수 있다** (4장, p.199).
- 호환성의 기본 방향 — **대체로 상위 버전 JDK의 도구들은 하위 버전 JDK의 가상 머신에서
  구동되는 프로그램과 호환되며 반대도 마찬가지**지만, **런타임 환경에 따른 미묘한 차이와 호환성
  문제를 원치 않는다면 더 높은 버전을 사용하길 권한다** (4장, pp.199–200).[^zhou2024]
- 모니터링을 받으려면 JMX가 켜져 있어야 한다 — **도구들 대부분이 JMX를 기반으로 하거나 JMX를
  이용하기 때문**이다 (4장, p.200).[^zhou2024]
  - 버전 조건: JDK 5 이하의 가상 머신에서 구동되는 프로그램은 시작 시
    `-Dcom.sun.management.jmxremote` 매개 변수를 추가해 JMX 관리 기능을 켜야 한다. **JDK 6
    이상에서 구동된다면 JMX가 기본으로 켜져 있으므로 별다른 매개 변수를 추가하지 않아도 된다**
    (4장, p.200).
- 아래에서 다루는 여섯 도구는 저자가 **특별히 선별한, 가장 널리 쓰이는 명령 줄 도구**이며
  **(별도 언급이 없다면) JDK 5 때부터 제공되던 도구들**이다 (4장, pp.199·209).[^zhou2024]

## jps: 어느 프로세스인가

- **JDK 도구의 이름 중 상당수가 유닉스 명령어에서 유래했는데, 대표적으로 JVM 프로세스 상태
  도구(JVM process status tool)인 jps가 있다. jps의 이름은 유닉스 `ps` 명령어에서 따왔고 기능
  역시 비슷하다** (4장, p.200).[^zhou2024]
- 하는 일은 **동작 중인 가상 머신 프로세스 목록을 보여 주며 각 프로세스에서 가상 머신이 실행한
  메인 클래스(`main()` 메서드를 포함하는 클래스)의 이름과 로컬 가상 머신 식별자(이하 LVMID)를
  알려 주는 것**이다 (4장, p.200).[^zhou2024]
  - 왜 가장 자주 쓰이는지 — **대다수 다른 JDK 도구에서 모니터링할 가상 머신 프로세스를
    명시하려면 LVMID를 알아야 하기 때문**이다 (4장, p.200).
  - **로컬 가상 머신 프로세스의 LVMID 값은 운영 체제의 프로세스 아이디, 즉 PID와 같다.** 따라서
    작업 관리자나 `ps`로도 알아낼 수 있지만, **여러 가상 머신 프로세스가 동시에 시작하여 프로세스
    이름으로 구분할 수 없다면 jps를 통해 메인 클래스가 무엇인지 확인해 봐야 한다** (4장, p.200).
- 명령 형식은 `jps [options] [hostid]`이며, **원격 가상 머신의 프로세스 상태도 알아낼 수 있다.
  이때 RMI 서비스를 이용하는데, `hostid` 매개 변수가 바로 RMI 레지스트리에 등록된 호스트명을
  가리킨다** (4장, pp.200–201).[^zhou2024]
- 자주 쓰이는 옵션 (4장, p.201, 표 4-1):[^zhou2024]

  | 옵션 | 설명 |
  |---|---|
  | `-q` | LVMID만 출력(메인 클래스 이름 생략) |
  | `-m` | 가상 머신 프로세스 시작 시 `main()` 메서드에 전달된 매개 변수 출력 |
  | `-l` | 메인 클래스의 완전한 이름 출력(프로세스가 JAR 패키지를 실행 중이라면 JAR 경로 출력) |
  | `-v` | 가상 머신 프로세스 시작 시 주어진 가상 머신 매개 변수 출력 |

## jstat: 힙과 GC를 텍스트로 훑기

- **JVM 통계적 모니터링 도구(JVM statistics monitoring tool)인 jstat은 가상 머신의 다양한 작동
  상태 정보를 모니터링하는 데 사용한다. 로컬 또는 원격 가상 머신 프로세스의 클래스 로딩,
  메모리, 가비지 컬렉션, JIT 컴파일과 같은 런타임 데이터를 보여 준다** (4장,
  p.201).[^zhou2024]
  - 자리매김이 분명하다 — **텍스트 콘솔 환경만 제공하는 서버에서는 런타임에 가상 머신의 성능
    문제를 찾는 보편적인 도구일 것**이다 (4장, p.201).
- 명령 형식은 `jstat [option vmid [interval[s|ms] [count]]]`이며, **`interval`과 `count`는 질의
  간격과 횟수를 뜻하고 이 두 매개 변수를 생략하면 질의를 한 번만 수행한다.** 원격 프로세스의
  `vmid`는 `[protocol:][//]lvmid[@hostname[:port]/servername]` 형태다 (4장,
  pp.201–202).[^zhou2024]
- **`option` 매개 변수는 크게 3개 부류로 나뉜다(클래스 로딩, 가비지 컬렉션, 런타임 컴파일
  대상)** (4장, pp.201–202, 표 4-2):[^zhou2024]

  | 옵션 | 설명 |
  |---|---|
  | `-class` | 클래스 로딩/언로딩 횟수, 총 점유 공간, 클래스 로딩 시간 모니터링 |
  | `-gc` | 자바 힙 상태 모니터링. 에덴, 생존자 공간, 구세대 등의 사용량, 총 가비지 컬렉션 시간 등 |
  | `-gccapacity` | 기본적으로 `-gc`와 같지만 자바 힙의 다양한 공간의 최대/최소 사용량에 초점 |
  | `-gcutil` | 기본적으로 `-gc`와 같지만 전체 공간 중 사용률(%)에 초점 |
  | `-gccause` | `-gcutil` 기능에 추가로, 최근 가비지 컬렉션이 일어난 이유 출력 |
  | `-gcnew` | 신세대 가비지 컬렉션 상태 모니터링 |
  | `-gcnewcapacity` | 기본적으로 `-gcnew`와 같지만 최대/최소 사용량에 초점 |
  | `-gcold` | 구세대의 가비지 컬렉션 상태 모니터링 |
  | `-gcoldcapacity` | 기본적으로 `-gcold`와 같지만 최대/최소 사용량에 초점 |
  | `-compiler` | JIT 컴파일러가 컴파일한 메서드와 소요 시간 등의 정보 출력 |
  | `-printcompilation` | 런타임에 컴파일된 메서드들 출력 |

- 이클립스를 막 시작한 뒤 사용률을 보는 예다. `5404`는 jps로 알아낸 LVMID다 (4장,
  p.202):[^zhou2024]

  ```sh
  jstat -gcutil 5404
  ```

  ```text
  S0     S1     E      O      M      CCS    YGC  YGCT   FGC  FGCT   CGC  CGCT   GCT
  0.00   87.26  31.15  61.28  97.83  92.61  17   0.156  0    0.000  8    0.014  0.170
  ```

  - **수많은 약자와 수치가 등장하는데 크게 힙 공간별 사용률과 GC 통계로 구분할 수 있다** (4장,
    p.202).
  - 저자의 해석 — **이클립스는 신세대의 에덴 공간을 31.15% 사용 중이며, 두 생존자 공간 중 하나의
    87.26%를 쓰고 있다. 구세대는 61.28%를, 메타스페이스와 압축 클래스 공간은 각각 97.83%와
    92.61%를 사용하고 있다. 신세대 컬렉션은 17차례 수행했고 걸린 시간은 총 0.156초다. 전체
    GC는 0차례 수행해서 걸린 시간은 0초다. 동시 GC는 8차례 수행하는 데 0.014초가 걸렸다. 그래서
    가비지 컬렉션에 든 시간은 총 0.170초다** (4장, pp.202–203).
  - 버전 조건: 위 열 구성은 JDK 11 이상이다. **JDK 7까지는 영구 세대를 이용했기 때문에 `M`과
    `CCS` 대신 `P` 항목을 출력**하고, **동시 GC 통계(`CGC`·`CGCT`)는 JDK 11부터 등장한
    통계**다 (4장, p.203).
  - 문서의 공백도 기록해 둘 만하다 — **오라클 공식 문서에는 JDK 21까지도 동시 GC(`CGC`와
    `CGCT`) 항목을 설명하지 않고 있어, 이럴 때는 어쩔 수 없이 jstat 도구의 소스 코드를 직접
    확인해 봐야 한다.** JDK 17과 21 기준 소스는 **`JDK_SRC_HOME/src/jdk.jcmd/share/classes/sun/
    tools/jstat`** 디렉터리에 있다 (4장, p.203).
- 한계와 그럼에도 쓰이는 이유 — **jstat은 가상 머신 상태 정보를 텍스트로만 보여 주어 VisualVM
  이나 JMC처럼 시각적으로 보여 주는 모니터링 도구보다 직관적이지 않다. 하지만 실제 프로덕션
  환경에서는 그래픽 인터페이스를 사용하지 못하는 경우가 많고, 대다수 서버 관리자가 텍스트
  콘솔을 능숙하게 다루기 때문에 실무 현장에서도 jstat을 사용하는 모습을 흔히 볼 수 있다**
  (4장, p.203).[^zhou2024]

## jinfo: 매개 변수 읽고 바꾸기

- **jinfo는 가상 머신의 다양한 매개 변수를 실시간으로 확인하고 변경하는 도구**다. 형식은
  `jinfo [options] vmid`이며 쓰임은 셋이다 (4장, p.203):[^zhou2024]
  - **가상 머신 시작 시 명시한 매개 변수 목록을 보고 싶을 때는 `-flags` 매개 변수를 사용한다.**
  - **명시하지 않은 매개 변수의 시스템 기본값을 알고 싶다면 `-flag` 옵션 다음에 원하는 매개
    변수 이름을 적어 주면 된다** — 예컨대 `jinfo -flag ConcGCThreads 1444`는
    `-XX:ConcGCThreads=2`를 출력한다.
  - **`-sysprops` 매개 변수는 자바 시스템의 속성, 즉 `System.getProperties()` 내용을 출력한다.**
- 버전 조건: JDK 6 이상 — **jinfo는 JDK 5 시절에 리눅스 버전 JDK와 함께 소개되었고 당시에는
  정보를 얻는 기능만 제공했다. JDK 6부터는 윈도우도 지원하기 시작했고, 실행 중에 일부 매개
  변수의 값을 수정할 수 있게 되었다**(`-flag [+|-]이름` 또는 `-flag 이름=값` 형태) (4장,
  p.203).[^zhou2024]
- 대안도 하나 적혀 있다 — **JDK 6 이상에서는 `java -XX:+PrintFlagsFinal` 명령으로도 매개 변수
  기본값을 확인할 수 있다** (4장, p.203).[^zhou2024]

## jmap: 힙을 파일로 떠내기

- **jmap은 힙 스냅숏을 파일로 덤프해 주는 자바용 메모리 맵 명령어**이며, **힙 스냅숏 덤프
  외에도 F-큐, 자바 힙과 메서드 영역 상세 정보(사용량, 적용 중인 컬렉터 등)도 알아낼 수
  있다** (4장, p.204).[^zhou2024]
- jmap 없이 힙을 뜨는 길도 있다 — **`-XX:+HeapDumpOnOutOfMemoryError` 매개 변수를 사용하면
  메모리가 오버플로될 때 가상 머신이 자동으로 힙을 덤프해 주고, 리눅스에서는 `kill -3` 명령으로
  가상 머신에 프로세스 종료 시그널을 보내도 된다** (4장, p.204).[^zhou2024] 오버플로 자체의
  종류는 [런타임 데이터 영역과 메모리 오버플로](../concepts/jvm-runtime-data-areas.md)에 있다.
- 옵션 (4장, p.204, 표 4-3):[^zhou2024]

  | 옵션 | 설명 |
  |---|---|
  | `-dump` | 자바 힙의 스냅숏을 덤프한다. 형식은 `-dump:[live,]format=b,file=<filename>`이며 하위 매개 변수 `live`를 추가하면 살아 있는 객체만 덤프한다 |
  | `-finalizerinfo` | F-큐 안의 객체들을 출력한다. F-큐에는 `Finalizer` 스레드가 `finalize()` 메서드를 실행해 주길 기다리는 객체들이 담겨 있다 |
  | `-heap` | 사용 중인 컬렉터, 매개 변수 설정, 세대 상태 등 자바 힙 관련 상세 정보를 출력한다 |
  | `-histo` | 클래스와 인스턴스 개수, 총 용량 등 힙에 있는 객체들의 통계 정보를 출력한다 |

  - 실제 사용은 `jmap -dump:format=b,file=jconsole.bin 15396` 꼴이며, 출력은 덤프된 바이트 수와
    걸린 시간을 알려 준다 (4장, p.204).

## jhat: 덤프를 브라우저로 보기

- 버전 조건: JDK 8 이하 — **jhat은 JDK 8까지 제공되던 JVM 힙 분석 도구(JVM heap analysis
  tool)로, jmap으로 덤프한 힙 스냅숏을 분석할 수 있다. JDK 9부터는 jhsdb가 그 자리를 대신
  한다** (4장, pp.204–205).[^zhou2024]
- **jhat은 작은 HTTP·웹 서버를 내장하고 있어서 분석이 완료되면 웹 브라우저로 결과를 살펴볼 수
  있다**(기본 포트 7000) (4장, pp.204–205).[^zhou2024]
- **하지만 실무에서 jhat을 직접 사용해 분석하는 사람은 많지 않다.** 이유는 둘이다 (4장,
  p.205):[^zhou2024]
  - **힙 스냅숏 덤프를 애플리케이션이 배포된 서버에서 직접 분석하는 일은 드물다. 분석은 시간이
    오래 걸리고 하드웨어 자원을 많이 소모하는 작업이기 때문에 반드시 다른 기기에서 수행해야
    한다. 따라서 명령 줄 도구에 얽매일 이유도 없다.**
    - 덧붙는 조건 — **생성된 덤프 파일을 읽어 들이려면 메모리가 상당히 많이 필요하기 때문에
      일반적으로 64비트 JDK와 대용량 메모리를 갖춘 서버를 이용한다** (4장, p.205).
  - **jhat의 분석 기능은 단순한 편이다. VisualVM이나 이클립스 메모리 분석기, IBM 힙
    분석기(IBM HeapAnalyzer) 등의 전문 분석 도구가 기능 면에서 jhat보다 뛰어나다.**
    - 덤프 파일 형식은 가상 머신마다 다르다 — **IBM 힙 분석기는 IBM J9 가상 머신이 생성한 덤프
      파일을 분석하는 데 쓰이며, 가상 머신에 따라 덤프 파일 형식이 다르기 때문에 다른 가상 머신
      분석에는 쓰일 수 없다** (4장, p.205).
- 분석의 두 축 — **분석 결과는 기본적으로 패키지 단위로 묶어 보여 주며, 메모리 누수 분석에는
  주로 힙 히스토그램(`jmap -histo`와 같은 기능)과 OQL을 이용한다. 힙 히스토그램은 메모리를 가장
  많이 차지하는 객체를 찾는 방식이고, OQL은 메모리상의 객체를 세는 표준 객체 질의 언어다.
  OQL의 문법은 SQL과 비슷하다** (4장, pp.205–206).[^zhou2024]

## jstack: 스레드가 멈춰 있을 때

- **스택 추적 도구인 jstack은 현재 가상 머신의 스레드 스냅숏을 생성하는 데 쓰인다(일반적으로
  스레드 덤프 또는 자바 코어 파일이라고 부른다). 스레드 스냅숏은 현재 가상 머신에서 실행 중인
  각 스레드의 메서드 스택들의 집합**이다 (4장, p.206).[^zhou2024]
- 언제 뜨는가 — **주로 스레드가 장시간 멈춰 있을 때 원인을 찾기 위해 생성한다. 주된 원인은
  스레드 사이의 교착 상태(deadlock), 무한 루프, 외부 자원 요청으로 인한 긴 기다림 등이다.
  스레드가 멈춰 있다면 jstack으로 각 스레드의 호출 스택을 볼 수 있고, 그러면 응답하지 않는
  스레드가 뒤에서 무슨 일을 하고 있는지 또는 어떤 자원을 기다리고 있는지 알 수 있다** (4장,
  p.206).[^zhou2024]
- 옵션은 둘이다 — **`-l`은 스택 정보에 더해 락 관련 정보도 함께 출력하고, `-e`는 스레드 관련
  정보를 추가로 출력한다** (4장, p.206, 표 4-4).[^zhou2024]
- 출력에서 읽는 것 — **각 스레드의 우선순위, CPU 사용 시간, 생성 후 경과 시간, 스레드 상태,
  메서드 호출 스택 등 다양한 정보를 알 수 있다** (4장, p.208).[^zhou2024]
- 같은 일을 애플리케이션 안에서도 할 수 있다 — **JDK 5부터는 `java.lang.Thread` 클래스에 추가된
  `getAllStackTraces()` 메서드로 가상 머신이 실행하는 모든 스레드의 `StackTraceElement` 객체를
  얻을 수 있다. 이 메서드를 이용하면 코드 단 몇 줄로 jstack의 기능 대부분을 구현할 수 있다**
  — 저자는 이것으로 **관리자 페이지를 만들어 브라우저에서 언제든지 스레드 스택 정보를 확인**
  한다 (4장, p.208).[^zhou2024] 앞서 도구를 자바로 구현한 이유와 같은 이야기다.

## jcmd와 jhsdb로의 대체

- **최신 JDK에서는 JCMD와 JHSDB의 명령 줄 모드처럼 더 강력한 대체제가 제공되지만 사용법은
  비슷하다. 앞으로 JDK가 어떻게 발전해 가든 이 기본 도구들을 익히는 데 들인 노력과 시간은 결코
  낭비가 아닐 것**이다 (4장, pp.209).[^zhou2024]
- 대응은 이렇다 (4장, p.213, 표 4-15):[^zhou2024]

  | 기본 도구 | JCMD | JHSDB |
  |---|---|---|
  | `jps -lm` | `jcmd` | N/A |
  | `jmap -dump <pid>` | `jcmd <pid> GC.heap_dump` | `jhsdb jmap --binaryheap` |
  | `jmap -histo <pid>` | `jcmd <pid> GC.class_histogram` | `jhsdb jmap --histo` |
  | `jstack <pid>` | `jcmd <pid> Thread.print` | `jhsdb jstack --locks` |
  | `jinfo -sysprops <pid>` | `jcmd <pid> VM.system_properties` | `jhsdb info --sysprops` |
  | `jinfo -flags <pid>` | `jcmd <pid> VM.flags` | `jhsdb jinfo --flags` |

- JDK가 배포하는 모니터링·문제 해결 도구 전체의 생존 구간도 정리되어 있다 (4장, p.211, 표
  4-12):[^zhou2024]

  | 이름 | 주 용도 | JDK 버전 |
  |---|---|---|
  | `jps` | JVM 프로세스 상태 도구. 지정한 시스템의 모든 핫스팟 가상 머신 프로세스를 출력 | 7~ |
  | `jstat` | JVM 통계적 모니터링 도구. 핫스팟의 다양한 런타임 데이터를 수집 | 7~ |
  | `jstatd` | jstat의 데몬. 원격 모니터링 도구를 연결할 수 있는 인터페이스를 제공 | 7~ |
  | `jinfo` | 가상 머신의 설정 정보를 출력 | 7~ |
  | `jmap` | 가상 머신의 메모리 덤프 스냅숏(heapdump 파일)을 생성 | 7~ |
  | `jfr` | 자바 애플리케이션의 런타임 진단 및 프로파일링 | 13~ |
  | `jhat` | 힙 덤프 스냅숏 분석. HTTP·웹 서버를 내장 | 7~8 (JDK 9에서 jhsdb로 대체) |
  | `jstack` | 가상 머신의 스레드 스냅숏을 보여 줌 | 7~ |
  | `jhsdb` | SA 기반의 핫스팟 프로세스 디버거 | 9~ |
  | `jsadebugd` | SA 기반의 디버거 데몬 | 7~8 |
  | `jcmd` | 가상 머신 진단용 명령 줄 도구. 실행 중인 JVM에 진단 명령을 보냄 | 7~ |
  | `jconsole` | JMX 명세를 따르는 GUI 모니터링 도구 | 7~ |
  | `jmc` | 성능 오버헤드 없이 자바 애플리케이션을 모니터링·관리 | 7~10 (JDK 11부터 별도 제공) |
  | `jvisualvm` | 자바 VisualVM. 메모리·CPU 분석, 힙 덤프 분석, 메모리 누수 검출, MBean 접근 등 | 7~8 (JDK 9부터 별도 제공) |

  - 이 표는 **JDK 7 이후 버전이 제공하는 모든 도구**를 정리한 열 개 표(기본·보안·국제화·원격
    메서드 호출·자바 IDL·배포·웹 스타트·모니터링·웹 서비스·REPL) 중 하나이며, **중간에 사라진
    도구도 포함**한다 (4장, pp.209–212).
