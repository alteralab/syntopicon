## 하나의 질문

**데이터 프로덕트의 내부를 설계할 때, 무엇을 설계 단위로 삼는가.**

[데이터 퀀텀](../concepts/data-quantum.md)이 무엇으로 이뤄지고
[어떤 표면](../concepts/data-product-ports-and-sidecar.md)을 갖는지가 3부에서 정해지고 나면,
4부는 그 안쪽 설계로 들어간다. 저자가 고른 설계 단위는 능력(capability)도 계층(layer)도
아니고 **어포던스**다.

## 어포던스라는 낱말 — 성질이 아니라 관계

- 출처가 명시된다 — 4부 도입의 각주는 **어포던스는 Don Norman이 자기 책 *The Design of
  Everyday Things*에서 정의한 것이다**라고 적는다 (4부 도입, p.191).[^dehghani2022]
- 저자가 부를 조직한 축이 이것이다 — **나는 이 부를 데이터 프로덕트의 개별
  어포던스(affordance) 중심으로 조직했다 — 데이터 프로덕트의 성질과 사람(또는 시스템)이 그것과
  상호작용할 수 있는 방식 사이의 관계다. 예컨대 데이터 메시 사용자가 데이터 프로덕트를
  발견하거나·읽거나·그 수명 주기를 관리하는 방식으로, 데이터 프로덕트와 직접 상호작용한다**
  (4부 도입, p.191).[^dehghani2022]
- Norman의 정의는 원문 그대로 직인용된다 (11장, p.194):[^dehghani2022]

> The term *affordance* refers to the relationship between a physical object and a person
> (or for that matter, any interacting agent, whether animal or human, or even machines
> and robots).
>
> An affordance is a relationship between the properties of an object and the capabilities
> of the agent that determine just how the object could possibly be used. A chair affords
> ("is for") support and, therefore, affords sitting. Most chairs can also be carried by a
> single person (they afford lifting), but some can only be lifted by a strong person or by
> a team of people. If young or relatively weak people cannot lift a chair, then for these
> people, the chair does not have that affordance, it does not afford lifting.
>
> The presence of an affordance is jointly determined by the qualities of the object and
> the abilities of the agent that is interacting. This relational definition of affordance
> gives considerable difficulty to many people. We are used to thinking that properties
> are associated with objects. But affordance is not a property. An affordance is a
> relationship. Whether an affordance exists depends upon the properties of both the
> object and the agent.

- 저자는 이 방법에 이름을 붙인다 — **나는 데이터 프로덕트 아키텍처 설계에 대한 이 접근을
  어포던스에 의한 설계(design by affordances)라 부른다** (11장, p.194).[^dehghani2022]
- 아키텍처의 구성 요소 목록에 이것을 **덧붙이는** 것임을 밝힌다. *Fundamentals of Software
  Architecture*가 정의하는 넷 — **구조(structure, 구성 요소와 그 인터페이스·상호작용·통합),
  특성(characteristics, 확장성·신뢰성 등의 능력), 결정(decisions, 설계를 규율하는 확고한 규칙),
  원칙(principles, 결정에 영향을 주는 지침)** — 에 **이것들에 더해 나는 또 다른 요소, 어포던스에
  초점을 맞추고 도입할 것이다**를 얹는다 (11장, pp.193–194).[^dehghani2022]

## 왜 그것이 인터페이스 설계에서 중요한가

- 관계로 보면 **상대편의 능력에 대한 가정**이 설계에 드러난다 — **왜 이것이 데이터 프로덕트
  인터페이스와 능력의 설계에서 중요한가. 각 데이터 프로덕트 성질에 대해, 예컨대 바이템포럴
  데이터를 서빙하는 것에 대해, 그 성질과 무엇이 또는 누가 상호작용할 것이고 그들이 무엇을 할 수
  있는지 — 예컨대 시간을 인지하는(time-aware) 에이전트인지 — 에 대한 가정이 있다** (11장,
  pp.194–195).[^dehghani2022]
- 그 가정이 분산 시스템의 무결성 조건이 된다 — **어포던스가 정의하는 이 가정과 제약은
  분산 시스템이 무결성과 신뢰성을 갖고 작동하게 하는 데 필요하다. 당신은 본질적으로 데이터
  프로덕트의 성질·능력과 데이터 메시 생태계의 다른 에이전트들 — 데이터 제공자·소비자·소유자·
  거버넌스, 그리고 데이터 플랫폼의 서비스나 다른 데이터 프로덕트 같은 구성 요소들 — 의 관계를
  점검함으로써 데이터 프로덕트를 설계하는 것이다** (11장, p.195).[^dehghani2022]
- 그러면서도 실용적 근사를 허락한다 — **대개의 경우 이 어포던스들 각각을 데이터 프로덕트의
  성질(property)로 생각해도 된다. 다만 그 성질이 누구·무엇에게 어포드하고 누구에게는 아닌지를
  염두에 두라** (11장, p.195).[^dehghani2022]
- "데이터 프로덕트 사용자"의 외연이 넓게 고정된다 — **다음 맥락에서 데이터 프로덕트
  사용자(data product user)라는 어구는 데이터 프로덕트 생태계에서 데이터 프로덕트와
  상호작용하는 모든 에이전트를 가리킨다. 여기에는 데이터 프로덕트 개발자·소유자·소비자·거버넌스
  그룹 등 사람뿐 아니라 다른 데이터 프로덕트와 멀티플레인 데이터 플랫폼의 서비스 같은 시스템도
  포함된다** (11장, p.196).[^dehghani2022]

## 여덟 어포던스

- 그림 11-1이 여덟을 원형으로 배치한다 — **그림 11-1은 데이터 프로덕트가 **자율적으로**
  의미 있고·이해 가능하고·신뢰할 수 있으며 생태계의 다른 데이터에 연결될 수 있는 데이터를
  변환하고 서빙하기 위한 어포던스들을 열거한다. 여기서 자율적으로(autonomously)라는 낱말은 그
  수명 주기가 다른 데이터 프로덕트에 대한 중단 없이 독립적으로 관리될 수 있다는 뜻이다. 그것은
  자기 일을 하는 데 필요한 모든 구조 구성 요소를 갖는다. 다른 데이터 프로덕트나 플랫폼
  서비스에 대한 의존은 명시적 계약을 가진 API를 통하며, 느슨한 결합을 만든다** (11장,
  p.195).[^dehghani2022]
- 표 11-1이 각 어포던스와 그것을 다루는 장을 짝지운다 (11장, pp.196–197):[^dehghani2022]

| 어포던스 | 다루는 자리 | 저자의 서술 |
|---|---|---|
| 데이터 서빙(Serve Data) | 12장 p.201 | 불변(immutable)이고 바이템포럴(bitemporal)한 데이터를, 여러 접근 양식을 지원하는 명확히 정의된 읽기 전용 인터페이스로 공유한다 |
| 데이터 소비(Consume Data) | 12장 p.217 | 여러 타입의 상류 소스에서 데이터를 소비한다 — 협력 운영 애플리케이션·다른 데이터 프로덕트·외부 시스템 |
| 데이터 변환(Transform Data) | 12장 p.226 | 입력 데이터를 처리·변환해 자기가 서빙할 새 데이터로 만든다. 변환은 프로그램 코드일 수도, 기계 학습 모델일 수도, 추론을 돌리는 복잡한 질의일 수도 있다 |
| 발견·이해·탐색·신뢰(Discover \| Understand \| Explore \| Trust) | 13장 p.233 | 사용자가 발견하고·탐색하고·이해하고·신뢰할 수 있게 하는 API와 정보를 서빙한다 |
| 데이터 조합(Compose Data) | 13장 p.244 | 사용자가 자기 데이터를 다른 데이터 프로덕트의 데이터와 조합·상관·조인할 수 있게 한다. 데이터 퀀텀은 집합(테이블 또는 그래프) 연산을 계산적으로 수행함으로써 프로그램적 데이터 조합 가능성을 어포드한다 |
| 수명 주기 관리(Manage Life Cycle) | 14장 p.255 | 사용자가 그 수명 주기를 관리할 수 있게 한다. 개발자가 짓고·프로비저닝하고·유지할 수 있도록 빌드 시점·런타임 설정과 코드 집합을 제공한다 |
| 관측·디버그·감사(Observe \| Debug \| Audit) | 14장 p.262 | 행위를 모니터링하고·이슈를 디버그하고·감사할 수 있게 한다. 데이터 처리 로그·계보(lineage)·런타임 메트릭·접근 로그 같은 필요한 정보를 제공하는 프로그램적 API를 제공한다 |
| 데이터 거버넌스(Govern Data) | 14장 p.258 | 데이터 사용자(거버넌스 그룹·데이터 프로덕트 개발자)와 메시 경험 플레인(관리·정책 제어)에게 자기 데이터를 스스로 거버넌스할 API와 계산적 정책 집합을 제공한다 |

- 원형 배치가 우연이 아니다 — 어느 어포던스도 다른 것의 하위 계층이 아니고, 전부가 같은 퀀텀의
  표면에서 대등하게 나온다. 이것이 아래 "코이퀄(coequal) 노드" 서술과 같은 발상이다.

## 어포드하지 않는 것이 같이 적혀 있다

- 표 11-1의 특이한 점은 **부정형 조항**이 각 어포던스에 붙어 있다는 것이다. 어포던스가 관계인
  이상 "누구에게 어포드하지 않는가"가 설계의 일부이기 때문이다.
- 서빙 — **상태를 유지하기 위해 데이터를 갱신하거나 삭제해야 하는 트랜잭션·운영 애플리케이션에는
  어포드하지 않는다** (11장, p.196).[^dehghani2022] 이 한 줄이 데이터 프로덕트의 출력을
  읽기 전용·추가 전용으로 못 박는다 — 같은 갈림이
  [불변성과 상태·스트림](../concepts/state-streams-and-immutability.md)의 추가 전용 원장과
  [CRUD와 삽입 전용 패턴](../concepts/crud-and-insert-only-patterns.md)에 있다.
- 소비 — **자기가 식별하고 설정한 소스에서 소비하는 것만 어포드한다. 자기가 식별하고 설정하지
  않은 소스에서 소비하는 것은 어포드하지 않는다** (11장, p.196).[^dehghani2022] 곧 밀어넣기가
  아니라 끌어오기다.
- 조합 — **여러 데이터 프로덕트에 걸쳐 공유되는 단일하고 단단히 결합된 데이터 스키마(예: SQL
  스키마)를 요구하는 시스템에는 데이터 조합 가능성을 어포드하지 않는다** (11장,
  p.196).[^dehghani2022] [전사 데이터 웨어하우스](../concepts/enterprise-data-warehouse.md)의
  통합 스키마와 [표준 차원](../concepts/conformed-dimension.md)이 전제하는 조합 방식이
  여기서 명시적으로 배제된다.

## 아키텍처 특성 ① 변화를 위한 설계

- 세 특성이 공통 평가 기준으로 제시된다 — **모든 데이터 프로덕트의 설계가 공유하는 공통
  아키텍처 특성 집합이 있다. 당신은 이 특성들에 비추어 자기 데이터 프로덕트의 설계를 평가해
  "규모에서 데이터로부터 가치를 얻는다"는 데이터 메시 목표가 충족되는지 확인할 수 있다**
  (11장, p.197).[^dehghani2022]
- 첫째 — **데이터와 그 모델을 바꾸는 것은 데이터 프로덕트의 필수 설계 특성이다. 앞 장들에서
  회상하면, 우아하게 변화에 응답하는 것(responding gracefully to change)은 데이터 메시의
  목표이고 따라서 모든 데이터 프로덕트가 받쳐야 할 특성이다** (11장, p.197).[^dehghani2022]
- 그 목표는 [데이터 메시](../concepts/data-mesh.md) 1장이 세운 세 목표 중 하나다.
- 시간이 변화 관리의 도구로 지목된다 — **예컨대 데이터 프로덕트의 여러 측면을 API로 앞세우는
  설계 결정이 변화를 더 관리 가능하게 만든다. 또 다른 예로, 데이터 프로덕트의 많은 측면에
  시간을 속성으로 더하는 것 — 데이터의 스냅샷, 데이터 모델의 스냅샷, SLO의 시간 등 — 이 이
  파라미터들의 변화 처리를 쉽게 만든다. **기본적으로 모든 데이터 프로덕트 아티팩트와 데이터는
  시간이라는 개념을 써서 버저닝된다**** (11장, p.197).[^dehghani2022] 12장의 바이템포럴 서술이
  이 문장의 전개다.
- 확장(extension)은 변화의 부분집합으로 놓인다 — **확장을 위한 설계는 변화를 위한 설계 특성의
  부분집합으로 볼 수 있다. 데이터 프로덕트 능력은 시간이 지나면서 진화하고 성숙한다. 예컨대
  어느 날은 파일을 통한 단일 접근 양식만 지원하다가 나중에 이벤트와 테이블을 지원하도록
  진화할 수 있다** (11장, p.197).[^dehghani2022]
  - 확장성의 기제로 결합 방식이 갈린다 — **협력하는 사이드카나 에이전트 같은 느슨하게 결합된
    구성 요소가 확장성을 개선한다. 그것들은 새 능력으로 확장되어 배포 시점이나 런타임에 데이터
    프로덕트에 주입될 수 있는 반면, 정적으로 링크된 공유 라이브러리는 가용해지려면 데이터
    프로덕트의 재빌드를 요구하므로 덜 쉽게 확장된다** (11장, p.197).[^dehghani2022]
    9장 표 9-1이 사이드카를 동적 결합·정적 결합 둘 다로 구현 가능하다고 열어 둔 자리에서,
    저자가 어느 쪽을 선호하는지가 여기서 드러난다.

## 아키텍처 특성 ② 확장을 위한 설계

- 둘째 — **데이터 프로덕트의 설계는 스케일아웃 메시로 귀결되어야 한다. 메시는 데이터
  프로덕트가 더해지고, 소스의 수가 늘고, 데이터 사용자의 다양성과 수가 커지는 동안에도 변화에
  대한 민첩성과 데이터 접근 속도를 유지하면서 스케일아웃해야 한다** (11장,
  p.197).[^dehghani2022]
- 그 대가로 무엇을 금지하는가가 명시된다 — **동기화·조정·접근의 어떤 중앙집중 지점이든 이
  트레이드오프에 해로울 수 있다. 그래서 데이터 프로덕트는 자율적이다** (11장,
  p.198).[^dehghani2022]
- 사이드카 결정이 이 특성에서 파생된 것으로 재서술된다 — **예컨대 접근 통제나 다른 정책을
  데이터 프로덕트의 실행 맥락 — 곧 사이드카 — 에서 강제한다는 설계 결정은 아키텍처적 결정이다.
  대안으로 데이터 사용자와 데이터 프로덕트 사이에 중앙 게이트웨이를 써서 접근을 통제하면 시간이
  지나면서 병목(chokepoint)이 된다** (11장, p.198).[^dehghani2022]

## 아키텍처 특성 ③ 가치를 위한 설계

- 셋째 — **데이터 프로덕트의 설계는 소비자에게 가치를 최소한의 마찰로 전달하는 것을 그
  중심에 두어야 한다. 이것이 다소 자명하고 어쩌면 군더더기로 보일지 모르지만, 소프트웨어
  공학의 이야기는 가치 전달에 거의 도움이 되지 않는 영리한 설계들로 어질러져 있다** (11장,
  p.198).[^dehghani2022]
- 그리고 이 특성이 바로 앞 특성과 **긴장**한다는 것을 저자 스스로 예로 든다 — **데이터
  프로덕트 인터페이스의 설계는 사용자와 쉽게 이해 가능하고·신뢰할 수 있고·안전한 데이터를,
  최소한의 단계·점검·개입으로 공유하는 데 초점을 맞춰야 한다. 예컨대 데이터
  바이템포럴리티(bitemporality)는 분산 시스템에서 데이터의 무결성과 신뢰를 유지하고 추론하는 데
  필요하지만, 많은 사용자는 일상적 사용에서 시간에 신경 쓰지 않는다. 그래서 데이터 프로덕트가
  바이템포럴리티를 내부적으로 유지하더라도, 기본값으로 "지금" 또는 "최신"을 가정해 시간이라는
  개념을 줄이는 지름길 API(shortcut APIs)를 줄 수 있다** (11장, p.198).[^dehghani2022]
  - 이것이 12장 바이템포럴 설계의 사용성 안전판이다 — 모델은 두 시간 축을 전부 유지하되,
    표면은 기본값으로 축을 접는다.

## 복잡 적응계 ① 지역 규칙에서 창발하는 전역 행위

- 저자가 계열을 선언한다 — **데이터 메시 같은 아키텍처는 복잡 적응계(complex adaptive
  systems)와 성질을 공유한다. 그것은 동적 상호연결성을 가진 자율적 자기 조직화 에이전트들의
  네트워크로 이뤄진다. 복잡 적응계에서 영감을 받는 것은 아키텍처 설계에 두 가지 방식으로
  영향을 준다** (11장, p.198).[^dehghani2022]
- 첫째 영향의 출처가 새 떼다 — **강력한 집단 행위가 각 에이전트를 지역적으로 규율하는 단순하고
  작은 규칙 집합에서 창발한다는 사실에서 영감을 얻을 수 있다. 예컨대 가을 하늘의 수천 마리
  찌르레기가 아름답게 동기화된 무리를 이루는 것은 모든 새가 세 단순 규칙을 따르는 데서
  창발한다: 분리(separation, 가까운 무리 동료와 부딪히지 않기)·정렬(alignment, 가까운 선도
  동료를 따르기)·응집(cohesion, 이웃 동료와 비슷한 속도로 움직이기)이다. 새들은 전역
  오케스트레이터도 전체에 대한 지식도 필요하지 않다** (11장, p.198).[^dehghani2022]
  각주는 Craig Reynolds, "Flocks, Herds and Schools: A Distributed Behavioral Model",
  SIGGRAPH '87을 든다 (11장, p.198).[^dehghani2022]
- 그 대응물이 포트다 — **비슷하게, 강력한 집단 행위가 각 데이터 프로덕트에 대한 작은 단순
  특성·행위 규칙 집합을 정의함으로써 메시에서 창발한다. 예컨대 각 데이터 프로덕트는 자기 입력
  포트(직속 상류 소스에서 어떤 입력 데이터를 어떻게 소비하는지)를 정의하고 자기 출력 포트(어떤
  데이터를 어떻게 공유하는지)를 정의한다** (11장, p.199).[^dehghani2022]
- **계보가 창발물로 재정의된다** — **입력 포트와 출력 포트가 각 데이터 프로덕트가 지역적으로
  설정하는 데이터 흐름(data flow) 구성을 정의한다. 이 지역 데이터 흐름 규칙에서 메시 수준의
  계보 그래프(graph of lineage) — 모든 데이터 프로덕트 사이 메시 전반의 데이터 흐름 그래프 —
  가 창발한다** (11장, p.199).[^dehghani2022]
- 그리고 그 부정형이 이어진다 — **이 경우 데이터 흐름 그래프나 계보의 중앙집중적 정의는 없다.
  어느 데이터 프로덕트도 메시 전체에 대한 지식을 갖지 않는다. 전역 설정을 인지하는 파이프라인의
  중앙 오케스트레이터도 없다. 이것은 중앙 오케스트레이터가 모든 파이프라인 설정의 중앙 저장소와
  함께 일하는 기존 데이터 파이프라인 설계와 다르다** (11장, p.199).[^dehghani2022]
  - [배치 워크플로와 DAG](../concepts/batch-workflows-and-dags.md)와
    [분산 작업 오케스트레이션](../concepts/distributed-job-orchestration.md)이 중앙 스케줄러와
    전역 DAG 저장소를 전제하는 서술과 정면으로 갈린다. **대립은 처방이고, 조건은 파이프라인의
    소유 경계가 도메인 안인가 밖인가이다** — 저자는 오케스트레이션 자체가 아니라 그 그래프를
    누가 선언하는지를 뒤집는다.
  - [메타데이터 관리](../concepts/metadata-management.md)가 계보를 중앙 카탈로그가 수집·투영해
    만드는 산출물로 두는 서술과도 여기서 갈린다 — 저자에게 계보는 수집물이 아니라 창발물이다.
- 다른 창발물도 열거된다 — **다른 창발 메시 수준 성질의 예로는, 데이터 프로덕트 의미론과
  그것의 직속 노드에 대한 관계라는 지역 정의에서 창발하는 전역 지식 그래프(global knowledge
  graph), 그리고 각 데이터 프로덕트가 제공하는 지역 메트릭·로그에 상관 식별자(correlation
  identifiers)를 기반으로 한 메시 수준 런타임 성능이 있다** (11장, p.199).[^dehghani2022]
- 창발물이 드러나는 자리도 지정된다 — **창발적 성질과 행위는 데이터 플랫폼의 메시 경험
  플레인(mesh experience plane) 서비스를 통해 표면화될 수 있다** (11장, p.199).[^dehghani2022]
  [멀티플레인 데이터 플랫폼](../concepts/multiplane-data-platform.md)의 셋째 플레인이 하는 일이
  이 문장으로 정의된다.

## 복잡 적응계 ② 중앙 오케스트레이터 없음

- 둘째 영향 — **데이터 메시는 복잡 적응계처럼 중앙 통제 아키텍처 요소가 필요 없다. 새 떼는
  오케스트레이터를 갖지 않지만 갖고 있는 것은 속도·거리·선도자를 감지하는 방식을 정의하는
  생물학적 **표준(standards)** 집합이다** (11장, p.199).[^dehghani2022]
- 표준이 오케스트레이터를 대체한다 — **비슷하게 데이터 메시는 상호운용성과 행위의 응집을 위해
  각 데이터 프로덕트가 따르는 표준 집합을 도입한다. 예컨대 10장에서 나는 메시 경험 플레인이
  제공하는 서비스로 "전역 정책(global policies)"을 도입했다. 이 서비스는 각 데이터 프로덕트에
  대한 접근 통제 규칙을 편리하게 설정할 수 있다. 그러나 규칙의 해석과 실행은 데이터 프로덕트
  안에서 올바른 시점 — 읽기 또는 쓰기 접근 — 에 지역적으로 일어나며, 중앙 접근 통제 권위의
  개입이 없다** (11장, p.199).[^dehghani2022]
- 저작의 분산은 선택지로 열려 있다 — **일부 조직에서는 규칙 저작 자체가 탈중앙화되어 데이터
  프로덕트에 지역적으로 위임된다. 그러나 플랫폼은 규칙의 균일한 해석과 실행을 위해 각 데이터
  프로덕트 안에 표준화된 사이드카를 내장한다** (11장, p.199).[^dehghani2022]
- [연합 컴퓨테이셔널 거버넌스 원칙](../concepts/federated-computational-governance-principle.md)의
  "결정은 전역, 실행은 지역"이 여기서 복잡 적응계의 언어로 다시 진술된다.

## 4부 자신이 긋는 범위

- 4부 도입이 목적을 좁힌다 — **4부의 목적은 데이터 메시의 비전과 양립 가능한 설계 기법을
  식별하고 그렇지 않은 것과 분리하도록 돕는 것이다. **데이터 프로덕트를 어떻게 구현하는지에
  대한 핸드북이 되려는 것이 아니다.** 각 어포던스의 논의는 그것이 무엇인지, 왜 중요한지, 그리고
  데이터 메시적 접근의 특징이 무엇인지를 다룰 것이다** (4부 도입, p.192).[^dehghani2022]
- 기술 불가지도 3부와 같다 — **3부와 비슷하게 여기서의 논의도 기술 불가지(technology
  agnostic)로 남을 것이다. 다만 내가 각 어포던스에 대해 도입하는 설계 특징들이 데이터 메시와
  양립 가능한 기술을 고르는 데 지침이 될 것이다** (4부 도입, p.192).[^dehghani2022]
- 그 지침의 예로 **한 문장짜리 기술 선택 기준**이 제시된다 — **예컨대 데이터 프로덕트에 대한
  *dump pipes and smart filters* 원칙 — 데이터 프로덕트에 대한 *dumb pipes and smart
  endpoints*에 해당하는 것 — 은 데이터 프로덕트 사이의 데이터 흐름을 통제하기 위해 데이터 처리
  파이프라인을 부과하지 않는 기술을 고르도록 이끌 것이다** (4부 도입, p.192).[^dehghani2022]
  - 원계열은 마이크로서비스의 "smart endpoints and dumb pipes"다 —
    [마이크로서비스와 서버리스](../concepts/microservices-and-serverless.md)가 ESB의 지능을
    파이프에서 끝점으로 옮긴 것과 같은 조작이고, 데이터 쪽 상대는
    [엔터프라이즈 버스 아키텍처](../concepts/enterprise-bus-architecture.md)다.
  - 원문이 `dump pipes`(dumb의 오식으로 보인다)와 `dumb pipes`를 한 문장에서 함께 쓰고 있어
    그대로 옮긴다. #hypothesis — 저자의 의도는 두 어구가 같은 원칙의 데이터판·서비스판이라는
    것이다.
- 4부가 어포던스별로 어느 장에 배치되는지는 위 표 11-1이 그대로 지도다 (4부 도입,
  pp.191–192).[^dehghani2022]
- 저자가 11장을 세 줄로 요약한다 (11장, p.200):[^dehghani2022]
  - **첫째, 메시의 데이터 프로덕트와 다른 구성 요소·사용자 사이의 관계를 봄으로써 올바른 설계에
    도달할 것이다 — 데이터 프로덕트 어포던스, 곧 데이터 서빙·소비·발견·거버넌스·감사 등이다.**
  - **둘째, 스케일아웃 아키텍처를 설계할 것이다. 다른 것을 깨뜨릴 두려움 없이 바뀔 수 있는
    코이퀄(coequal) 데이터 프로덕트를 만든다. 그것들은 중앙집중 병목을 부과하지 않고 스케일아웃하며
    가치 전달이라는 결과에 설계를 집중한다.**
  - **셋째, 가능한 곳에서 복잡 적응계의 원리를 배치할 것이다. 각 데이터 프로덕트에 단순하고
    지역적인 규칙과 행위를 설계하여 집단적으로 메시 수준의 지식과 지능의 창발로 이어지게 한다.**
