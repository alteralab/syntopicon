하나의 질문: **레코드가 어느 파티션에 쓰일지는 무엇이 정하고, 그 규칙은 언제
깨지는가.**

## 키가 하는 두 가지 일

- 카프카 메시지는 키/밸류 쌍이다. **토픽과 밸류만으로 `ProducerRecord`를 만들 수 있고
  그러면 키는 기본적으로 `null`이 되지만, 대부분의 애플리케이션은 키를 붙여
  생산한다** (3장, p.68).[^shapira2021]
- 키의 목적은 둘이다 (3장, p.68):[^shapira2021]
  - **메시지와 함께 저장되는 추가 정보**다.
  - **메시지가 쓰일 토픽 파티션을 정하는 데 통상 쓰인다.** 압착된 토픽(compacted topic)
    에서도 중요한 역할을 한다.
- 따라오는 성질: **같은 키를 가진 모든 메시지는 같은 파티션으로 간다.** 어떤 프로세스가
  토픽의 파티션 일부만 읽고 있다면 **하나의 키에 대한 모든 레코드는 같은 프로세스가
  읽게 된다** (3장, p.68).[^shapira2021]

## 키가 없을 때 — 스티키 라운드 로빈

- 키가 `null`이고 기본 파티셔너를 쓰면 레코드는 **토픽의 가용 파티션 중 하나로 무작위
  전송**되며, 파티션 사이 균형을 맞추는 데 **라운드 로빈(round-robin)** 알고리즘이
  쓰인다 (3장, p.69).[^shapira2021]
- 아파치 카프카 2.4 프로듀서부터, 키가 `null`일 때 기본 파티셔너가 쓰는 라운드 로빈
  알고리즘은 **스티키(sticky)**하다 — **한 파티션으로 가는 메시지 배치를 채운 뒤에야
  다음 파티션으로 전환한다.** 그 결과 같은 수의 메시지를 **더 적은 요청으로** 보내게 돼
  **지연이 낮아지고 브로커의 CPU 사용이 줄어든다** (3장, p.69).[^shapira2021]
  - 버전 조건: Kafka 2.4 이상 — 그 이전 프로듀서의 기본 파티셔너는 이 스티키 처리를
    하지 않는다.

## 키가 있을 때 — 해시 배분

- 키가 있고 기본 파티셔너를 쓰면 카프카는 **키를 해시하고**(자바가 업그레이드돼도 해시
  값이 바뀌지 않도록 **카프카 자체의 해시 알고리즘**을 쓴다) 그 결과로 메시지를 특정
  파티션에 대응시킨다 (3장, p.69).[^shapira2021]
- 대응의 대상 집합에 주의한다 — **키가 항상 같은 파티션에 대응되는 것이 중요하므로,
  가용 파티션이 아니라 토픽의 모든 파티션을 써서 대응을 계산한다.** 그래서 **특정
  파티션이 사용 불가인 상태에서 그 파티션으로 쓰면 에러를 받을 수 있다** — 드문 일이다
  (3장, p.69).[^shapira2021]
- 카프카가 자체 해시를 쓰는 이유는 일반 이론 쪽에서 더 넓게 서술된다 — **많은 프로그래밍
  언어에 내장된 단순 해시 함수는(해시 테이블용이므로) 샤딩(sharding)에 적합하지 않을 수 있다. 자바의
  `Object.hashCode()`와 루비의 `Object#hash`는 같은 키가 프로세스마다 다른 해시 값을 가질 수
  있어서 샤딩에 쓸 수 없다** (7장, p.258).[^kleppmann2026]
  - 두 소스가 같은 결론에 다른 근거를 댄다 — 카프카 쪽 근거는 **자바가 업그레이드돼도 해시
    값이 바뀌지 않게 하려고**(3장, p.69)이고, DDIA 쪽 근거는 **같은 프로세스가 아니면 값이
    달라질 수 있어서**다. 어느 쪽이든 결론은 같다: **샤딩용 해시는 언어 런타임이 아니라
    시스템이 정의해야 한다.**
- 해시 함수에 요구되는 성질과 실물 선택도 같은 자리에서 서술된다 — **좋은 해시 함수는
  치우친(skewed) 데이터를 받아 균등 분포로 만들고, 입력이 매우 비슷해도 그 해시는 값 범위에 고르게
  분포한다(같은 키는 항상 같은 출력을 낸다). 샤딩 목적의 해시 함수는 암호학적으로 강할 필요가
  없다 — MongoDB는 MD5를, 카산드라와 ScyllaDB는 Murmur3를 쓴다** (7장,
  p.258).[^kleppmann2026] 아래 [커스텀 파티셔너](#커스텀-파티셔너)의 예제 코드가 부르는
  `Utils.murmur2`도 그 Murmur 계열이다 (3장, p.70).[^shapira2021]

## 기본 파티셔너 밖의 선택지

- 기본 파티셔너 외에 카프카 클라이언트는 `RoundRobinPartitioner`와
  `UniformStickyPartitioner`도 제공한다. 이들은 **메시지에 키가 있어도** 각각 무작위
  파티션 배정과 스티키 무작위 파티션 배정을 한다 (3장, p.69).[^shapira2021]
- 쓸모가 생기는 상황: **키가 소비하는 애플리케이션에는 중요하지만 워크로드가
  치우칠 때**다 — 카프카 레코드의 키를 관계형 데이터베이스 적재의 기본 키로 쓰는 ETL
  애플리케이션이 그 예이며, 이때 **키 하나가 불균형하게 큰 워크로드를 가질 수 있다.**
  `UniformStickyPartitioner`를 쓰면 **모든 파티션에 워크로드가 고르게 분산된다** (3장,
  p.69).[^shapira2021]

## 파티션 수가 변하면 대응이 깨진다

- 기본 파티셔너를 쓸 때 **키와 파티션의 대응은 토픽의 파티션 수가 변하지 않는 한에서만
  일관적이다** (3장, p.69).[^shapira2021]
- 파티션 수가 일정한 동안에는 예컨대 **사용자 045189에 관한 레코드가 항상 파티션 34에
  쓰인다**고 확신할 수 있고, 파티션에서 데이터를 읽을 때 온갖 최적화가 가능해진다 (3장,
  p.69).[^shapira2021]
- 그러나 **토픽에 새 파티션을 추가하는 순간 이 보장은 사라진다** — 옛 레코드는 파티션
  34에 남아 있는데 새 레코드는 다른 파티션에 쓰일 수 있다 (3장, p.69).[^shapira2021]
- 그래서 **키에 의한 파티셔닝이 중요하다면 가장 쉬운 해법은 충분한 파티션으로 토픽을
  만들고 절대 파티션을 추가하지 않는 것**이다 (3장, p.69).[^shapira2021]
- 이 성질은 카프카의 특이 사항이 아니라 **해시를 개수로 나눈 나머지에 배정하는 모든 스킴의
  성질**이다 — **문제는 노드 수 N이 바뀌면 대부분의 키를 한 노드에서 다른 노드로 옮겨야 한다는
  것이며, 모듈로(modulo) N 함수는 계산하기 쉽지만 불필요한 레코드 이동이 많아
  리밸런싱(rebalancing)이 매우 비효율적이다** (7장,
  pp.258–259).[^kleppmann2026]
- 그래서 위 카프카 권고("충분히 만들고 늘리지 마라")는 일반 해법의 한 사례로 읽힌다 —
  **단순하지만 널리 쓰이는 해법 하나는 노드 수보다 훨씬 많은 샤드(shard)를 만들고 각 노드에 샤드를
  여러 개 배정하는 것**이다. 그러면 **노드 사이를 옮기는 것은 샤드 전체뿐이고, 샤드의 개수도
  키를 샤드에 배정하는 방식도 바뀌지 않으며, 바뀌는 것은 샤드를 노드에 배정하는 방식뿐**이다
  (7장, pp.259–260).[^kleppmann2026]
  - 카프카의 파티션 재할당이 정확히 이 "샤드를 노드에 다시 배정하는" 연산이다 — 절차는
    [파티션과 레플리카 관리](../concepts/kafka-partition-and-replica-administration.md)에 있다.
  - 같은 이론이 대가도 말해 준다 — **처음 설정한 샤드 수가 틀린 것으로 드러나면 비싼
    리샤딩(resharding)이 필요하고, 어떤 시스템은 리샤딩 중 동시 쓰기를 허용하지 않아 다운타임 없이 샤드
    수를 바꾸기 어렵다** (7장, p.260).[^kleppmann2026] 카프카에서 그 대가는 파티션을 줄일 수
    없다는 형태로 나타난다.

## 커스텀 파티셔너

- 카프카는 해시 파티셔닝만 강제하지 않으며, **데이터를 다르게 파티셔닝할 좋은 이유가
  있을 때**가 있다 (3장, p.70).[^shapira2021]
- 책이 드는 상황: B2B 벤더이고 **최대 고객사 하나가 일일 거래의 10% 이상**을 차지할 때,
  기본 해시 파티셔닝을 쓰면 **그 고객의 레코드가 다른 계정들과 같은 파티션에 배정돼 한
  파티션만 훨씬 커진다.** 서버 공간이 고갈되고 처리가 느려질 수 있으므로, **그 고객에게
  전용 파티션 하나를 주고 나머지 계정은 해시 파티셔닝으로 나머지 파티션에 대응**시키는
  것이 목표가 된다 (3장, p.70).[^shapira2021]
- 구현의 요건: `Partitioner` 인터페이스는 `configure`·`partition`·`close` 메서드를
  포함한다. 아래 예제는 `partition`만 구현하지만, **특별 취급할 고객 이름은
  `partition`에 하드코딩하지 말고 `configure`를 통해 넘겼어야 한다** (3장,
  p.70).[^shapira2021]

  아래가 그 커스텀 파티셔너다 — `Partitioner`·`partition(`으로 찾는다.

  ```java
  public class BananaPartitioner implements Partitioner {

      public void configure(Map<String, ?> configs) {}

      public int partition(String topic, Object key, byte[] keyBytes,
                           Object value, byte[] valueBytes,
                           Cluster cluster) {
          List<PartitionInfo> partitions = cluster.partitionsForTopic(topic);
          int numPartitions = partitions.size();

          if ((keyBytes == null) || (!(key instanceOf String)))
              throw new InvalidRecordException("We expect all messages " +
                  "to have customer name as key");

          if (((String) key).equals("Banana"))
              return numPartitions - 1; // Banana will always go to last partition

          // Other records will get hashed to the rest of the partitions
          return Math.abs(Utils.murmur2(keyBytes)) % (numPartitions - 1);
      }

      public void close() {}
  }
  ```

- 예제가 던지는 예외의 조건도 규칙의 일부다 — **키가 `String`이 아닌 경우를 예외로
  막는다** (3장, p.71).[^shapira2021]

## 핫 키를 다루는 두 처방

위 커스텀 파티셔너가 푸는 문제에는 일반 이름이 있다 — **불균형하게 높은 부하가 걸린 샤드를
핫 샤드(hot shard) 또는 핫 스팟(hot spot)이라 하고, 키 하나가 특히 높은 부하를 가지면 그것을
핫 키(hot key)라 한다** (7장, p.256).[^kleppmann2026] 처방이 둘이고, 카프카의 두 선택지가
각각에 대응한다.

- **처방 하나 — 그 키에 자기 샤드를 준다.** **키의 범위(또는 해시의 범위)를 기준으로 샤드를
  정의하는 시스템이라면 개별 핫 키를 자기만의 샤드에 두는 것이 가능해지고, 어쩌면 그 샤드에
  전용 기계를 배정할 수도 있다** (7장, p.264).[^kleppmann2026] 위
  [커스텀 파티셔너](#커스텀-파티셔너)의 "Banana 고객에게 마지막 파티션 하나를 준다"가 이
  처방의 실물이다.
- **처방 둘 — 무작위 접미사로 키를 쪼갠다.** **어떤 키가 매우 뜨거울 것을 안다면 그 키의 앞이나
  뒤에 무작위 수를 붙인다. 무작위 두 자리만 붙여도 그 키에 대한 쓰기가 100개 키로 고르게
  쪼개져 서로 다른 샤드로 분산될 수 있다** (7장, p.264).[^kleppmann2026] 카프카에서 키를
  무시하고 고르게 뿌리는 `UniformStickyPartitioner`가 같은 효과를 노린다(위
  [기본 파티셔너 밖의 선택지](#기본-파티셔너-밖의-선택지)).
  - 이 처방의 대가를 카프카 쪽 서술은 말하지 않고 DDIA가 적는다 — **쓰기를 여러 키로 쪼개고
    나면 읽기가 100개 키 전부에서 읽어 합쳐야 하고, 핫 키의 각 샤드로 가는 읽기 양은 줄지 않고
    쓰기 부하만 쪼개진다. 게다가 어떤 키가 쪼개져 있는지 추적하는 부기가 필요하다** (7장,
  p.264).[^kleppmann2026]
- 어느 처방이든 영구적이지 않다는 경고도 붙는다 — **부하는 시간에 따라 변한다. 바이럴이 된
  게시물은 며칠 높은 부하를 겪다가 잦아들고, 어떤 키는 쓰기에만 뜨겁고 다른 키는 읽기에만
  뜨거워 서로 다른 전략이 필요하다** (7장, p.264).[^kleppmann2026]
