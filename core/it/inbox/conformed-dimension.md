# 표준 차원

하나의 질문: **서로 다른 업무 프로세스의 측정값을 어떻게 한 리포트에서 비교 가능하게 만드는가.** 표준 차원(conformed dimension)은 [버스 아키텍처](enterprise-bus-architecture.md)의 주춧돌로, 업무 프로세스 팩트 테이블들이 공유하는 표준화된 차원이다. common/master/reference/shared dimension 등 여러 별칭으로 불린다 (4장, p.130).[^kimball2013]

## 정의와 운영 원칙

- 구축·배포 원칙은 원문 직인용 (4장, p.130):[^kimball2013]

> Conformed dimensions should be built once in the ETL system and then replicated either logically or physically throughout the enterprise DW/BI environment.

- 만들어진 표준 차원을 개발 팀들이 실제로 쓰겠다고 서약하는 것이 결정적이다. 이는 기술이 아니라 정책 결정이며, 사용 의무화는 CIO가 명해야 한다 (4장, p.130).[^kimball2013]

## drill-across의 전제

- 표준 차원은 일관성·재사용을 넘어, 서로 다른 업무 프로세스의 성과 측정값을 **한 리포트에 결합**하는 것을 가능하게 한다. 멀티패스(multipass) SQL로 각 차원 모델을 따로 질의한 뒤, 공통 차원 속성(예: 제품명)을 기준으로 결과를 완전 외부 조인(full outer join)한다 — 이 연결이 drill across다 (4장, pp.130–131).[^kimball2013]
- drill across가 성립하는 조건: **차원 테이블 속성 값이 동일**할 때 직관적으로 동작한다. 완전 외부 조인은 한쪽 질의 결과에만 나타나는 행도 결합 리포트에 포함시킨다 (4장, p.131).[^kimball2013]
- BI 제품들이 이 기법을 multipass, multi-select, multi-fact, stitch query 등 제각각의 이름으로 지원하며, 결과 결합 위치(임시 테이블·앱 서버·리포트)도 구현마다 다르다. 팩트 테이블 간 교차 계산(cross-fact calculation)은 각 질의 결과가 반환된 뒤 BI 애플리케이션에서 수행해야 하는 경우가 많다 (4장, p.131).[^kimball2013]

## 동일(identical) 표준 차원

- 가장 기본형: 어느 팩트 테이블에 조인되든 같은 것을 뜻하는 차원. 일관된 차원 키, 속성 열 이름, 속성 정의, 속성 값(리포트 라벨·그룹핑으로 번역된다)을 가진다 (4장, p.131).[^kimball2013]
- 합치가 깨지는 예: 한쪽은 Month, 다른 쪽은 Month Name으로 부르거나, 값이 한쪽은 "July"인데 다른 쪽은 "JULY"인 경우 (4장, p.131).[^kimball2013]
- 물리적으로 같은 테이블일 수도 있으나, 여러 DB 플랫폼이 섞인 현실에서는 ETL에서 한 번 만들어 각 차원 모델로 동기 복제하는 편이 더 흔하다. 어느 쪽이든 행 수·키 값·속성 라벨·정의·값이 같아야 하고, 속성 열 이름은 차원 간에 고유해야 한다 (4장, p.131).[^kimball2013]
- 대부분의 표준 차원은 가능한 가장 세밀한 grain(개별 제품, 개별 일자)에서 정의된다 (4장, p.132).[^kimball2013]
- 같은 grain이라도 부분 합치가 있을 수 있다: 재고 분석 전용 보조 속성이 붙어도 키와 공통 열이 동일하면 여전히 합치다. 단, 그 추가(add-on) 속성으로는 프로세스를 가로질러 drill across할 수 없다 (4장, p.132).[^kimball2013]

## 축소(shrunken) 표준 차원

- 속성 부분집합에 의한 축소 롤업(shrunken rollup): 팩트 테이블이 원자 차원보다 높은 grain에서 측정값을 담을 때 필요하다. 예: 일별 스냅샷에 더한 주별 재고 스냅샷, 제품 수준의 소매 판매 대 브랜드 수준의 예측. grain이 달라 한 차원 테이블을 공유할 수 없지만, 롤업 테이블의 속성이 원자 차원 속성의 **엄격한 부분집합**이면 여전히 합치다 — 공통 속성(브랜드·카테고리 설명 등)은 두 테이블에서 라벨·정의·값이 동일해야 한다. 상세 테이블과 롤업 테이블의 기본 키는 별개다 (4장, p.132).[^kimball2013]
- 행 부분집합(row subset)에 의한 축소: 같은 상세 수준이지만 행의 부분집합만 담는 경우. 예: 전사 제품 차원에서 사업부별 제품만 뽑은 차원. 부분집합 차원에 조인되는 팩트 테이블도 같은 제품 부분집합으로 제한돼야 하며, 그렇지 않으면 참조 무결성 위반으로 예기치 않은 질의 결과가 나온다 — 행 부분집합은 사용자 혼란·오류 가능성을 의식해야 한다 (4장, pp.132–133).[^kimball2013]
- 날짜·월 차원은 행과 열 부분집합이 동시에 일어나는 특수 예다: 월 차원은 월말 일자 행들에서 월 grain에 안 맞는 열(주중/주말 표시, 휴일 표시 등)을 뺀 것으로 구성될 수 있다 (4장, p.134).[^kimball2013]
- 버스 매트릭스 표기: 축소 차원용 새 열을 만들지 말고, 원자 차원 셀에 grain을 텍스트로 적거나 열을 세분한다 — 원자 차원과의 합치를 강조하기 위해서다 (4장, p.134).[^kimball2013]

## 스토브파이프 방지와 합치의 한계

- 고립·독립 차원 모델(스토브파이프)은 분석 기회 상실보다 나쁘다: 화해 불가능한 조직 관과 서로 비교할 수 없는 리포트를 고착시키고, 존재 자체로 일관된 DW/BI 환경의 발전을 막는다. 표준 차원 없이 지어진 스토브파이프는 개조 비용이 재구축 비용을 넘기 일쑤라, 결국 폐쇄 후 버스 아키텍처 안에서 다시 지어지곤 한다 (4장, pp.129–130).[^kimball2013]
- 합치가 무의미한 경우도 있다(limited conformity): 전혀 다른 업종에 걸친 대기업 집단처럼 사업 라인마다 고객·제품이 유일하고 교차 판매 관심도 없다면 전사 아키텍처 시도 자체의 사업 가치가 없을 수 있다. 공통 정의 합의 의사는 전사 DW/BI를 지을 조직인지 가르는 리트머스 시험이다 — 합의가 안 되면 자회사별 독립 웨어하우스가 낫고, 대신 "전사 성과"를 묻지 말아야 한다 (4장, p.135).[^kimball2013]
- 그렇다고 포기 선언이 답은 아니다: 제품 설명·카테고리·사업 라인 몇 속성만이라도 합치시키는 최소공통분모 접근이 올바른 방향의 첫걸음이다. 차원 전체에 대한 전원 합의가 선행 조건이 아니다 (4장, p.135).[^kimball2013]
- 합치의 진짜 난관은 기술이 아니라 문화·조직 정치다: 속성 이름·정의·값에 대한 전사 합의가 필요하며, 이를 이끄는 데이터 거버넌스는 IT가 아니라 업무 측 전문가가 주도해야 성공 확률이 높다 — IT는 조직적 권위가 없다 (4장, pp.135–137).[^kimball2013]

## 애자일과 표준 차원

- "애자일이라 표준 차원 합의를 기다릴 수 없다"는 흔한 반론은 뒤집을 수 있다: 표준 차원이야말로 애자일 DW/BI 개발을 가능하게 한다. 차원 테이블을 개발 주기마다 조금씩 다르게 재작성하는 대신 한 번 만들어 재사용하는 데서 지렛대가 나오고, 마스터 표준 차원 포트폴리오가 갖춰질수록 새 프로세스의 시장 투입 시간이 줄어 ETL 개발이 거의 팩트 테이블 추가에만 집중된다 (5장 예고를 포함해 4장, pp.137–138).[^kimball2013]
- 모든 속성 합의가 필요한 것도 아니다: 전사적 의미가 있는 속성 부분집합만 먼저 식별하면 되고, 전사 제품 카테고리 같은 **단 하나의 속성**도 통합 노력의 유효한 출발점이다. 이후 아키텍처 스프린트에서 반복적으로 속성을 늘려간다 (4장, p.138).[^kimball2013]
- 합치를 건너뛴 대가: 부서별 분석 사일로는 비슷한 라벨 아래 미묘하게 다른 업무 규칙을 숨겨, 비교 가능해 보이지만 실제로는 아닌 데이터를 만든다. 사용자는 불일치 조정에 과도한 시간을 쓰게 되어 오히려 애자일한 의사결정을 잃는다 (4장, p.138).[^kimball2013]

## 표준 팩트(conformed fact)

- 데이터 아키텍처 노력의 95% 이상이 표준 차원이고 나머지 5%가 표준 팩트 정의다. 매출·이익·표준 원가 같은 KPI가 여러 모델에 살면, **같은 이름으로 불리려면 기저 정의와 산식이 같아야 한다**. 정의가 다르면 서로 다른 이름을 붙여 사용자가 비호환 팩트를 계산에 섞지 못하게 해야 한다 (4장, pp.138–139).[^kimball2013]
- 단위가 다른 경우(창고는 배송 케이스, 매장은 스캔 단위): 변환 계수를 차원 테이블에 묻어두고 사용자에게 맡기는 방식은 수용 불가 — 팩트를 두 단위 모두로 싣는 것이 올바른 해법이다 (4장, p.139).[^kimball2013]

[^kimball2013]: Kimball & Ross 2013, 4장 "Inventory" · 5장 "Procurement"
