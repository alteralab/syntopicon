이 페이지의 질문: **데이터 웨어하우스의 물리 인프라 — 환경·하드웨어·데이터베이스
옵션 — 를 무엇을 기준으로 고르는가.** 어떤 워크로드가 이 선택을 강제하는지는
[EDW](../concepts/enterprise-data-warehouse.md)에, 계층별 구체 설정은
[스테이징 영역](../concepts/staging-area.md)·[Data Vault 아키텍처](../concepts/data-vault-architecture.md)·[정보 마트](../concepts/information-mart.md)에 있다.

- 데이터 웨어하우스 프로젝트는 데이터베이스 시스템의 물리 아키텍처(physical
  architecture)에 특수한 요구를 가지며, 이 요구가 운영 데이터 스토어와 웨어하우스를
  가르고, 흔히 과소평가된다 (8장 서두, p.224).[^linstedt2016]
- 이 장이 서술하는 것은 **최선의 경우**다. 실제로는 웨어하우스가 논리 드라이브
  하나만 갖는 경우가 많고 그것도 괜찮다 — 적어도 Raw Data Vault의 데이터를 지킬
  어떤 형태의 장애 보호가 있는 한. 성능 병목을 만나면 그때 이 선택지들로 돌아온다
  (§8.6, p.242).[^linstedt2016]

## 무엇이 물리 아키텍처를 정하는가

- 물리 아키텍처는 여섯 요인에 달렸다 (§8.4, p.233):[^linstedt2016]
  - **데이터 크기** — 웨어하우스에 포함할 기업 기능 단위 수, 입력 원천의 수와 크기,
    풀어야 할 업무 문제 수(정보 마트 수를 좌우한다).
  - **변동성(volatility)** — Raw Data Vault가 원천의 모든 변경을 추적하므로, 원천의
    변동성은 두 방향으로 웨어하우스를 키운다: 데이터 크기가 커지고, 갱신이 훨씬
    잦아진다.
  - **업무 프로세스 수** — 포함할 프로세스가 많을수록 적재할 원천이 늘고, 적재·운영에
    드는 자원도 는다.
  - **사용자 수** — 사용자 수만이 아니라 활동성·동시 접속·월말 리포팅 같은 사용 첨두가
    함께 자원을 정한다.
  - **사용의 성격** — 프런트엔드 도구가 하드웨어를 정한다. 가상 정보 마트는 저장을 덜
    쓰고 CPU를 더 쓰며, 물질화하는 쪽은 저장을 더 쓴다.
  - **서비스 수준 협약(SLA)** — 전 세계에서 접근하면 24 × 7 가용성이 표준이 되고, 이는
    적재 주기까지 제약한다. 리포트 응답이 1초 미만이어야 하면 계산 능력이 더 든다.
- 시스템 요소는 균형이 목표다. 방치하면 요소 하나만 초과하거나 균형을 잃는다 — 예컨대
  아키텍처가 I/O 읽기를 많이 요구해서다. 최적 성능을 위해서는 요소들이 항상은
  아니더라도 대체로 균형을 유지해야 한다 (§8.4.1, pp.233–234).[^linstedt2016]

## 환경은 셋으로 가른다

- OLTP와 웨어하우스를 인프라로 가르는 것만으로는 부족하다. 소프트웨어 개발의 표준
  원칙을 따라 **개발·테스트·운영** 환경을 구분해야 한다. 근거는 둘이다: 시스템과 적재
  데이터의 안정성 요구가 다르고, 보안 요구가 다르다 — 개발자와 테스터가 운영 데이터에
  접근해서는 안 되는 업무 영역이 있다 (§8.2, p.226).[^linstedt2016]
- 테스트 환경은 현재 운영 중인 전 기능과 운영 데이터의 사본을 제공한다. 저장 한계나
  법적 요구 때문에 전체 사본이 늘 가능하지는 않다 — **일반 지침은 운영 데이터의 최소
  50%를 테스트에 쓰는 것**이다 (§8.2, p.227).[^linstedt2016]
- 테스트 환경의 용도는 신기능 검증만이 아니다. 설치·설정 루틴 같은 **배포 절차 자체**를
  현실적인 운영 사본에 대고 시험하는 자리이며, 기술 테스트를 통과한 뒤에는 업무
  사용자의 수용 테스트(acceptance test) 기반이 된다 (§8.2, p.227).[^linstedt2016]
- 운영 환경에 대고 테스트나 개발 활동을 수행하는 것은 "매우 논쟁적"이다 — 저자들이
  괄호 안에 붙인 대로, 이것은 "하지 마라!"의 외교적 표현이다. 운영 환경은 개발·테스트
  환경과 **물리적으로** 분리해야 한다. 개발·테스트가 요구하는 추가 부하가 같은 인프라
  위에서는 운영에 영향을 주기 때문이다 (§8.2, p.227).[^linstedt2016]

## 블루그린 배포

- 문제는 배포가 한 스프린트 안에서 **두 번 순차로** 일어난다는 것이다: 먼저 테스트
  환경에 배포해 기능과 배포 절차 자체를 시험하고 수용 테스트를 받은 뒤, 운영 환경에
  배포한다. 앞의 배포가 통과하기 전에는 뒤를 시작할 수 없으므로, 2주 스프린트를
  노리는 조직에게 이것이 심각한 병목이 된다 (§8.2.1, pp.227–228).[^linstedt2016]
- 해법으로 메인프레임 세계의 개념을 가져온다 — **블루그린 배포(blue-green
  deployment)**. 개발 환경 하나에 운영 환경 **둘**을 두고, 그 사이의 라우터가 사용자
  요청을 현재 활성인 쪽으로 보낸다. 비활성 환경은 동기 상태를 유지하되 실제 운영에는
  쓰이지 않는다 (§8.2.1, p.228).[^linstedt2016]
- 절차: 신기능을 운영 데이터에 대고 시험할 때가 되면 **비활성 운영 환경을 테스트
  환경으로 쓴다.** 수용 테스트까지 끝나면 옛 버전의 활성 환경과 신기능이 든 비활성
  환경이 나란히 있게 되고, 라우터를 핫 스위칭하면 신기능이 즉시 운영에 들어간다.
  전제는 테스트 시작 전 두 환경이 동기화돼 있어야 한다는 것이며, 그 시점이 보통
  스프린트 후반이므로 QA 팀에게는 스프린트 초부터 동기화할 시간이 있다
  (§8.2.1, p.228).[^linstedt2016]
- 대가 셋 (§8.2.1, pp.228–229):[^linstedt2016]
  - 운영 인프라가 두 벌 필요하다. **둘 다 전체 운영 부하를 감당해야 하고 소프트웨어
    라이선스도 그만큼 든다** — 기존 방식의 테스트 환경은 운영보다 약해도 목적을 잘
    수행했지만 여기서는 그럴 수 없다.
  - 규율이 필요하다. 테스트를 통과한 환경이 활성이 되므로, 같은 배포를 반대편
    환경에도 수행해야 동기화가 유지된다. 대안으로 데이터베이스 복제와 분산 파일
    시스템 복제로 ETL 코드를 맞추는 방법이 있다.
  - 신기능이 ETL 변경을 요구하면 그 ETL을 양쪽 환경에서 실행해야 하는데 늘 가능하지는
    않다. 추출이 표준 패턴을 따르고 업무 로직이 물질화 없는 가상 뷰로 구현돼 있으면
    완화되는데, **둘 다 Data Vault 적재 패턴의 성질이다** — 표준 패턴은 생성할 수 있고
    복제 환경에 배포하기 쉬우며, 변경 흡수는 단일 메타데이터 계층에서 이뤄진다.
- 방법론 쪽에서 반복 주기 단축의 수단으로 블루그린을 지목한 것과 같은 이야기다 —
  [Data Vault 2.0 방법론](../concepts/data-vault-methodology.md) 참조.

## 하드웨어 아키텍처 세 갈래

Data Vault 2.0은 증분 구축(incremental build-out)을 전제하므로, 웨어하우스는 시간이
지나면 초기 하드웨어(디스크·CPU)를 반드시 넘어선다. 확장 가능한 아키텍처가 필요한
이유다 (§8.4.1, p.233).[^linstedt2016]

- **단일 서버**: 데이터베이스 설치 하나가 자기 디스크를 쓴다. 확장은 서버 상자 안으로
  한정된다 — 마더보드의 CPU 소켓 수가 CPU 수를, 드라이브 슬롯 수가 디스크 수를
  제한한다. 더 큰 섀시로 바꾸거나 디스크 컨트롤러를 더해 어느 정도 늘릴 수 있으나,
  어느 지점부터는 하드웨어 추가 비용이 너무 커서 확장이 비현실적이 된다
  (§8.4.1, p.234).[^linstedt2016]
- **확장 가능한 공유 데이터베이스(scalable shared database)**: 읽기 전용 데이터베이스
  하나를 여러 서버 인스턴스가 저장 영역 네트워크(storage attached network, SAN)를
  통해 함께 쓴다. 인스턴스마다 자기 메모리·CPU·tempdb를 갖고, 질의는 인스턴스 하나
  안에서만 실행되지만(인스턴스를 가로지를 수 없다) 서로의 실행을 막지도 않는다.
  갱신은 **재적재(refresh) 단계**를 거친다 — 낡은 사본을 갱신한 뒤 리포팅 서버들에
  다시 부착한다 (§8.4.1, pp.234–235).[^linstedt2016]
  - 읽기 전용 제약 때문에 **물질화된 정보 마트 전용**이다. Raw Data Vault 계층에는
    쓰지 말아야 하고, 실시간·준실시간 적재가 있으면 특히 그렇다
    (§8.4.1, p.235).[^linstedt2016]
- **대규모 병렬 처리(massively parallel processing, MPP)**: 그리드의 여러 노드에
  데이터를 분산하고 각 노드가 데이터의 부분집합만 가지며, 사용자 질의는 모든 노드가
  함께 답한다. 두 가지 테이블 유형을 쓴다 — 각 노드에 **복제되는(replicated)** 테이블과
  내용이 노드들에 **분산되는(distributed)** 테이블. 복제는 비교적 작은 차원 테이블에
  적합하다(데이터가 로컬에 있어 조인 성능이 오른다). 사용자 질의는 제어 노드(control
  node)에 던져지고 활성 서버들이 실행하며, 적재와 백업은 그 목적으로 제어 랙에 따로
  더한 노드들이 맡는다 (§8.4.1, pp.235–236).[^linstedt2016]
  - **분산 키는 실무에서 잘 흩어지지 않는다** — 분산이 키 분포에 달렸는데 키 분포는
    흔히 편중돼 있기 때문이다. **키를 해싱하면 매우 무작위적이고 고르게 분포된 해시
    값이 나오므로 이 점에서 도움이 된다** (§8.4.1, p.236).[^linstedt2016] 같은 원리를
    샤딩 쪽에서 본 자리는 [해시 샤딩](../concepts/hash-sharding.md)이고, Data Vault가
    해시 키를 택한 다른 이유들은 [Data Vault 해싱](../concepts/hashing-in-data-vault.md)에
    있다.
- **Data Vault 2.0은 특정 아키텍처를 요구하지 않는다.** 다만 증분 구축 때문에 초기
  하드웨어 사양은 제한된 기간만 버티므로, 목표는 웨어하우스를 시간에 걸쳐 확장하고
  아키텍처가 병목이 되는 즉시 원래 구조를 연장하는 것이다 (§8.4.1, p.236).[^linstedt2016]

## 프로세서와 메모리

- 코어당 라이선스를 요구하는 데이터베이스 에디션에서는 다중 코어 CPU가 매우 비싸질 수
  있다. 그럼에도 웨어하우징, **특히 Data Vault 적재 패턴을 구현하는 쪽은 다중 코어에서
  큰 이득을 본다** — 허브·링크·새틀라이트를 적재 프로세스마다 개별 코어를 써서 병렬로
  적재할 수 있기 때문이며, 코어가 많으면 동시에 질의하는 사용자도 늘릴 수 있다. 같은
  이유로 하이퍼스레딩(Hyper-Threading Technology)을 켜는 것이 좋고, 프로세서 캐시
  크기도 성능에 영향을 준다. 지침은 "재정이 허락하는 한 많이", 그 밖의 경우에는 균형
  잡힌 시스템 (§8.4.2, p.237).[^linstedt2016] 병렬 적재의 실제는
  [적재 패턴](../concepts/data-vault-loading-patterns.md) 참조.
- 데이터베이스 서버는 디스크의 페이지를 캐시하는 데 물리 메모리를 쓴다. 운영계가 작은
  트랜잭션을 다루는 데 비해 웨어하우스는 **큰 질의**(질의가 건드리는 데이터량 기준)를
  다루고, 큰 테이블을 다루는 질의는 흔히 여러 번의 패스를 요구한다 — 테이블이 이미
  메모리에 있으면 성능이 크게 좋아진다. 메모리가 부족하면 페이지 파일·tempdb·디스크
  재읽기로 떨어지므로, RAM은 많을수록 낫다 (§8.4.3, p.237).[^linstedt2016]

## 저장 장치 — RAID·SSD·SAN

- RAID 수준별 성격 (§8.4.4, pp.237–238):[^linstedt2016]
  - **RAID-0**: 보호 없는 스트라이프. 개별 디스크의 접근 속도와 용량을 합친다(100GB
    디스크 넷이면 400GB 논리 디스크). 데이터를 네 디스크에 동시에 쓰므로 **가용한
    RAID 중 가장 빠르다.** 그러나 장애 보호가 없다 — 디스크 하나가 죽으면 어레이 전체가
    무효가 되고 남은 디스크의 데이터도 읽을 수 없게 된다.
  - **RAID-1**: 단순 미러. 논리 크기는 개별 디스크와 같다(100GB 둘 → 100GB). 하나가
    죽어도 정확한 사본이 둘째 디스크에 남는다.
  - **RAID-5**: 최소 세 디스크를 요구하며 패리티 비트를 계산해 어레이 전체에 분산한다.
    총 용량은 전 드라이브 용량에서 드라이브 하나 몫을 뺀 값이다. 한 드라이브가 죽으면
    교체 후 분산 패리티와 나머지 데이터로 재구축할 수 있지만, **둘 이상이 동시에 죽으면
    어레이의 데이터가 전부 사라진다.** RAID-1보다 느리지만 가용 용량이 커서 비용
    효율이 높다.
  - **RAID-6**: 패리티 비트를 둘 계산·분산해 동시 두 디스크 장애를 견딘다. 최소 네
    디스크가 필요하다. **1TB를 넘는 물리 디스크, 또는 물리 디스크가 다섯을 넘는 디스크
    어레이에 권장된다.**
  - 여러 수준을 조합한 고급 수준도 있다 — 예컨대 RAID-50은 RAID-5 어레이 둘을 스트라이프
    (RAID-0)로 묶는다.
- 디스크 컨트롤러도 나눈다. 행 데이터는 인덱스 데이터와, 그리고 둘 다 로그 파일과
  분리해 각각 별도의 물리 디스크나 디스크 어레이에 둔다. 데이터 접근의 병렬성과 대역폭을
  극대화하려면 **컨트롤러까지 분리**하는 것이 최선이다 (§8.4.4, p.238).[^linstedt2016]
- SSD의 자리는 인덱스다. 소비자용 SSD는 수명 동안 허용되는 쓰기 횟수가 매우 제한적인
  반면 엔터프라이즈급은 프로그램·소거 사이클이 훨씬 많다. 인덱스는 배치 적재 뒤에만
  갱신되지만 **매우 자주, 그리고 더 중요하게는 무작위 순서로** 접근되므로 SSD의 무작위
  접근 모드를 잘 활용한다 (§8.4.4, pp.238–239).[^linstedt2016]
- 저장 영역 네트워크(SAN)의 이점 넷: **가용성**(SAN 저장이 로컬 저장보다 신뢰성이 높은
  경우가 많아 다운타임을 줄일 잠재력이 있다), **재해 복구**(중앙 백업이라 운영 비용이
  줄고 복원이 빠르다), **중앙 관리**(서버를 열지 않고 원격으로 용량을 배정할 수 있고
  재부팅이 필요 없는 경우가 많다), **공간 활용률**(로컬 저장은 실제 필요보다 많이 붙여
  두어 저활용되기 쉽다). 다만 **대역폭이 전송 프로토콜에 제한된다** — 이 한계가 웨어하우스
  애플리케이션의 성능에 영향을 줄 수 있다 (§8.4.4, p.239).[^linstedt2016]

## 네트워크

- 웨어하우스 서버의 네트워크 인터페이스는 여섯 방향으로 쓰인다: 원천에서 데이터 반입,
  분석 도구로의 데이터 반출, 애플리케이션 질의 수신, 애드혹 리포팅의 사용자 질의 수신,
  질의 응답 반환, SAN 데이터 접근 (§8.4.5, p.239).[^linstedt2016]
- 부하는 한쪽으로 쏠린다. 질의 자체는 텍스트라 매우 작고 응답도 대개 집계·축약돼 있어
  현대 네트워크 인터페이스에 문제가 되지 않는다. **문제가 되는 것은 반입·반출과 SAN
  접근이다.** 대응은 인터페이스를 여럿 두어 내결함성을 높이고 **의무를 분리**하는 것이며
  (오늘날 많은 서버가 카드를 둘 갖는다), SAN이 전용 파이버 채널 망을 쓰는 것이 그
  분리의 예다. 원천과 웨어하우스 사이의 네트워크 구성 요소를 점검하면 실제 대역폭을
  제한하는 병목이 드러나기도 한다 (§8.4.5, p.240).[^linstedt2016]

## 데이터베이스 옵션

### tempdb

- 데이터베이스 엔진은 내부 객체와 버전 저장소를 담는 데이터베이스를 유지한다. 들어가는
  것은 넷이다: 임시 사용자 객체(임시 테이블·임시 저장 프로시저·커서·테이블 변수), 내부
  객체(스풀·정렬의 중간 결과), 읽기 커밋 트랜잭션의 행 버전(행 버전 격리·스냅샷 격리),
  일부 데이터베이스 기능이 만드는 행 버전 (§8.5.1, p.240).[^linstedt2016]
  [스냅샷 격리와 MVCC](../concepts/snapshot-isolation-and-mvcc.md)가 왜 버전 저장소를
  요구하는지의 자리다.
- **웨어하우징에서 이 데이터베이스는 무겁게 쓰인다** — 인덱스와 정렬 연산이 매우 빈번하고
  둘 다 tempdb의 도움을 받는다. 초기 인프라 설정 시의 지침 일곱 (§8.5.1,
  pp.240–241):[^linstedt2016]
  - 버전 조건: Microsoft SQL Server 2014 기준. 제품이 다르면 임시 영역의 이름과 설정
    수단이 다르다.
  - 복구 모델을 SIMPLE로 — 로그 공간을 자동 회수해 데이터베이스를 작게 유지한다.
  - 가장 빠른 디스크로 옮긴다.
  - 다른 데이터·로그 파일과 **다른 디스크**에 둔다.
  - **CPU 코어당 데이터 파일 하나**를 만든다.
  - 자동 증가를 허용한다 — 물리 디스크만이 한계여야 하고 논리 한계를 두지 않는다.
  - 필요하면 사전 할당한다(운영 중 공간 할당으로 중단되면 안 되는 경우).
  - 증가 증분을 너무 작게 두지 않는다 — 잦은 확장을 막는다.
- 공간 제약이나 사용 패턴 변화로 인한 병목을 알아채려면 크기를 주기적으로(예: 주
  단위) 감시하라고 권한다 (§8.5.1, p.241).[^linstedt2016]

### 파티셔닝

- 테이블이나 인덱스의 데이터가 관리 불가능할 만큼 커지면 백업·복원 같은 유지 기능의
  성능이 떨어진다. 운영계는 이를 아카이빙으로 푸는데 **웨어하우스에는 그 선택지가
  없다 — 가능한 한 모든 이력을 유지하려 하기 때문이다.** 게다가 웨어하우스의 테이블은
  운영계보다 훨씬 커서 문제가 더 심각하다 (§8.5.2, p.241).[^linstedt2016]
- 파티셔닝은 데이터를 파티션(partition)이라는 작은 조각으로 쪼갠다. 삽입 시 행이 한
  파티션으로 유도되고, 파티션 단위로 전송·접근이 가능해진다 — 다른 파티션에 영향을 주지
  않고 원천 데이터를 한 파티션에 직접 적재하거나, 파티션 단위로 압축하거나, 인덱스를
  부분 재구축할 수 있다. 질의 성능에도 이득이다: **파티션을 직접 조인할 수 있어 옵티마이저가
  등가 조인(equi-join) 질의의 성능을 개선한다** (§8.5.2, p.241).[^linstedt2016]
- 구성 요소 셋 (§8.5.2, pp.241–242):[^linstedt2016]
  - **파티션 함수(partition function)** — 행을 파티션으로 분배하며, 파티션 수와 경계를
    정의한다. 분배는 흔히 datetime 컬럼(예: 판매 주문의 판매일) 기준이며, 월이나 일에
    따라 12개 또는 365개 파티션으로 나눈다.
  - **파티션 스킴(partition scheme)** — 파티션 함수의 파티션들을 파일그룹에 대응시킨다.
    파티션을 별도 디스크에 배치하고, 파티션을 담은 파일그룹만 독립적으로 백업할 수 있게
    한다.
  - **파티셔닝 컬럼(partitioning column)** — 파티션 함수가 분배 기준으로 삼는 컬럼.
- 적재 패턴과 질의 모두 파티셔닝에서 큰 이득을 보는데, **특히 파티션이 여러 물리
  디스크에 분산될 때** 그렇다. 그러려면 파일그룹이 필요하다 (§8.5.2, pp.241–242).[^linstedt2016]
  스테이징 정리를 파티션 삭제로 하는 실무는 [스테이징 영역](../concepts/staging-area.md)에 있다.

### 파일그룹

- 파일그룹(filegroup)은 파티션 스킴의 파티션들을 여러 물리 디스크나 RAID 어레이로
  분배하는 수단이다. 파일그룹마다 특정 논리 디스크 드라이브에 결부되고 다른 파일그룹과
  독립적으로 접근되며, 백업·복원도 독립적으로 할 수 있다 (§8.5.3, p.242).[^linstedt2016]
- 행 데이터와 인덱스를 가르는 데도 쓴다. 각각을 자기 컨트롤러를 가진 다른 물리 드라이브에
  두면 여러 디스크 헤드가 페이지를 읽으므로 서버가 행 데이터와 인덱스 데이터를 **병렬로**
  읽을 수 있어 성능이 오른다. 인덱스는 읽기 집약적이므로 인덱스 파일그룹을 SSD에 두는
  것을 고려하라 (§8.5.3, p.242).[^linstedt2016]
- 같은 이유로 행 데이터와 **로그 데이터**도 다른 물리 디스크로 가른다. 로그를 유지할 때
  데이터베이스는 모든 트랜잭션을 별도 디스크에 쓰므로 그 디스크는 쓰기에 최적화돼야 하고,
  데이터 페이지를 담는 디스크는 질의의 많은 읽기를 감당해야 한다 (§8.5.3, p.242).[^linstedt2016]

### 데이터 압축

- 페이지 수준 압축의 이득 셋 (§8.5.4, p.242):[^linstedt2016]
  - **I/O 활용 개선** — 페이지가 압축돼 있으니 한 페이지에 더 많은 데이터가 들어간다.
    페이지는 압축된 형태로 읽고 쓰이며 **CPU가 쓸 때에만 풀린다.** 따라서 같은 I/O로 더
    많은 데이터를 디스크와 주고받는다.
  - **페이지 래칭(page latching) 감소** — 한 페이지에 더 많은 데이터가 들어가므로 데이터를
    안전하게 가져오는 데 필요한 래칭이 줄어든다.
  - **메모리 활용 개선** — 버퍼 캐시에 들어가는 데이터량이 함께 늘어난다.
- 판정: 압축은 CPU를 더 쓰지만 같은 양의 데이터를 저장·조회하는 데 I/O를 덜 쓴다.
  **따라서 가능한 곳에서는 켜는 쪽이 낫다.** 예외는 계산 능력이 제한된 서버, 그리고 쓰기가
  많고 읽기가 적은 워크로드다 — 다만 후자는 웨어하우징에서 해당되지 않아야 정상이다
  (§8.5.4, p.242).[^linstedt2016] 압축이 열 지향 저장에서 어떻게 다른 지렛대가 되는지는
  [열 지향 저장](../concepts/column-oriented-storage.md) 참조.

## 점진적 구축이 곧 조달 전략이다

- 좋은 접근은 **RAID 5나 6으로 시작해 단일 디스크 어레이가 성능 병목이 되는 즉시 확장하는
  것**이다. 이는 엔터프라이즈 웨어하우스를 지을 때 써야 할 증분 구축을 그대로 따른다
  (§8.6, p.243).[^linstedt2016]
- **여러 해를 미리 계획하지 마라.** 웨어하우스 이니셔티브를 시작하되 앞으로 제한된 햇수만
  내다본다. 엔터프라이즈 웨어하우스의 성공은 아무도 예견할 수 없고, 인프라 구축 비용이
  높아서 프로젝트가 일찍 멈추는 것을 바라지 않기 때문이다. 성공을 보이고 사용자가 더
  많은 기능을 요구할 때 시스템을 키운다 (§8.6, pp.242–243).[^linstedt2016]
- CPU·메모리도 같다. 부품을 살 때 **초기 구성을 연장할 수 있는지**를 확인하라 — 더 강한
  CPU로 교체하거나 듀얼 소켓 마더보드에 CPU를 하나 더 꽂거나 RAM 모듈을 추가할 수 있어야
  한다. 그래서 확장 가능한 하드웨어 플랫폼에 돈을 더 쓴다 (§8.6, p.243).[^linstedt2016]
- 파일그룹은 처음부터 나눠 둔다. 모든 데이터베이스 객체를 같은 파일그룹에(예: 행 데이터와
  인덱스 데이터를 함께) 두면 **나중에 객체를 옮기는 일이 더 복잡하고 더 오래 걸린다**
  (§8.6, p.243).[^linstedt2016]
