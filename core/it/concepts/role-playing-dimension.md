하나의 질문: **같은 차원이 한 팩트 테이블에 여러 번 필요할 때(주문일·요청 출하일처럼) 물리 테이블을 몇 개 두어야 하나.**

답은 하나다 — 물리 테이블은 하나만 두고, 역할(role)마다 고유하게 라벨링한 뷰(view)나 별칭(alias)으로 노출한다 (6장, pp.170–171).[^kimball2013]

> Role playing in a dimensional model occurs when a single dimension
> simultaneously appears several times in the same fact table. The underlying
> dimension may exist as a single physical table, but each of the roles should
> be presented to the BI tools as a separately labeled view.

## 왜 문제가 되나 — 이중 조인의 SQL 해석

- 트랜잭션 팩트 테이블의 1차 날짜는 트랜잭션 날짜(예: 주문일)지만, 요청 출하일처럼 부가 날짜가 흔히 따라온다. 각 날짜는 팩트 테이블의 외래 키여야 하는데, 두 외래 키를 **같은** 날짜 차원 테이블에 동시에 조인할 수는 없다 — SQL은 이 양방향 동시 조인을 "두 날짜가 동일해야 한다"는 조건으로 해석하기 때문이다 (6장, p.170).[^kimball2013]

## 해법 — 단일 물리 테이블 + 역할별 뷰/별칭

- 물리 날짜 차원 테이블은 하나만 만들어 관리하고, 뷰나 별칭으로 "독립된 두 날짜 차원"이라는 논리적 환상을 만든다. 이렇게 만든 두 논리 차원은 서로 완전히 무관한 제약을 걸 수 있는 독립 차원처럼 동작한다 (6장, pp.170–171).[^kimball2013]
- 각 뷰/별칭의 컬럼은 **고유하게 라벨링**해야 한다 — 주문 월(order month)과 요청 출하 월(requested ship month)을 구분하지 않으면, 두 컬럼이 한 리포트에 끌려 나왔을 때 구별할 수 없다 (6장, p.170).[^kimball2013]
- SQL 별칭이나 BI 도구 시맨틱 계층의 별칭 기능도 쓸 수 있지만, 여러 BI 도구와 직접 SQL 접근이 혼용되는 조직에서는 별칭 방식은 피하라고 경고한다 — 뷰가 모두에게 일관되게 보인다 (6장, p.171).[^kimball2013]

## 왜 물리 복제·조합 테이블이 아닌가

- 역할 조합마다 키를 부여한 단일 조합 날짜 테이블(주문일×요청출하일)은 두 가지로 무너진다: (1) 연 365행짜리 깔끔한 일 단위 테이블이 모든 날짜 조합을 담느라 크기가 폭발하고, (2) 조합 테이블은 더 이상 일·주·월 단위의 다른 적합(conformed) 날짜 차원들과 일치하지 않게 된다 (6장, p.171).[^kimball2013]
- 즉 물리 복제 대신 뷰를 쓰는 이유는 관리 지점을 하나로 유지하면서 표준 차원의 지위를 지키는 것이다. 예외는 도구 제약뿐 — 같은 차원의 다중 역할을 지원하지 않는 OLAP 제품에서는 역할마다 별도 차원을 만들 수밖에 없고, 그 결과 관계형 스타 스키마에서는 단순히 역할이었을 것들이 별개 차원으로 흩어진다 (6장, p.171).[^kimball2013]

## 어디까지 쓰이나

- 출하 송장 팩트: 송장일·요청 출하일·실제 출하일의 3개 역할 (6장, p.188).[^kimball2013]
- 주문 이행 파이프라인의 누적 스냅샷 팩트: 마일스톤 날짜 9개가 모두 날짜 차원의 역할이다. 이때 날짜 차원에는 Unknown/To Be Determined 행이 필요하다 — 파이프라인 행이 처음 적재될 때 다수의 날짜가 아직 미정이기 때문 (6장, pp.194–195).[^kimball2013]
- 총계정원장 분개 팩트: 전기일(posting date)과 회계 유효일을 구분해야 하면 두 번째 역할 연기 날짜 차원을 둔다 (7장, p.207).[^kimball2013]
- 고객 차원 안의 날짜(첫 구매일 등): SQL date 타입으로 두지 않고 날짜 차원으로의 외래 키로 바꾸면, 역할별 뷰(예: First Purchase Date 차원)가 차원 아웃리거(outrigger) 형태로 붙는다 (8장, pp.238–239).[^kimball2013]
- 팩트 테이블 밖에서도: 판매담당–고객 배정의 factless 팩트처럼 유효일·만료일 쌍도 날짜 차원의 2개 역할이다 (6장, p.177).[^kimball2013]

- 의료 청구·수납 누적 스냅샷의 날짜 외래 키 8개도 같은 처리를 받는다 — **누적 스냅샷 팩트
  테이블은 언제나 여러 날짜 스탬프를 수반**하며, 8개 키를 날짜 차원 한 인스턴스에 조인하지
  말고 단일 물리 테이블 위에 뷰 8개를 만들어 각각 독립 차원인 것처럼 조인한다. **뷰 정의는
  컬럼 이름을 겉보기로 구별되게 다시 라벨링**해야 BI 도구가 이해 가능한 이름을 보여 준다
  (14장, p.345).[^kimball2013]
- 날짜만 역할을 연기하는 것이 아니다: 의료 스키마에서 지급자(payer) 차원이 1차·2차 보험사로,
  의사 차원이 의뢰의·주치의·자문의·보조의로, 입원 청구 스키마에서는 입원 담당의와 주치의로
  각각 역할을 나눈다. 병원 환경에서는 의사마다 소속 조직이 다를 수 있으므로 **의사 조직
  차원도 역할별로 함께 갈라 둔다** (14장, pp.345, 348).[^kimball2013]
- 원천에 없는 역할을 추출 단계에서 만들어 내기도 한다: 항공편 스키마는 grain을 구간(segment)
  수준에 두면서 **여정 출발지·여정 목적지라는 공항 차원 역할 둘을 추가**하는데, 이 값은 추출
  중에 티켓에서 **4시간을 넘는 체류**(그 항공사의 공식 스톱오버 정의)를 찾아 결정한다 (12장,
  p.316).[^kimball2013]

## 예외 — 상관된 역할들을 하나로 합칠 때

- 원칙과 예외를 한 문단으로 못박은 대목이 있다 (12장, p.320):[^kimball2013]

> In most cases, role-playing dimensions should be treated as separate logical
> dimensions created via views on a single physical table. In isolated situations,
> it may make sense to combine the separate dimensions into a single dimension,
> notably when the data volumes are extremely small or there is a need for
> additional attributes that depend on the combined underlying roles for context
> and meaning.

- **극소 볼륨의 예 — 좌석 등급**: 구매 등급과 탑승 등급을 둘 다 분석하고 업그레이드·다운그레이드
  여부로 필터링하려면 역할 연기 차원 하나와 업그레이드 지표용 외래 키 하나를 더 다는 것이
  자연스러운 첫 반응이다(그러지 않으면 BI 애플리케이션이 이코노미→프리미엄 이코노미,
  이코노미→비즈니스 등 수많은 조합을 업그레이드로 판정하는 로직을 떠안는다). 그런데 등급
  차원은 4행뿐이고 업그레이드 지표도 3행뿐이다. 행 수가 이렇게 작으면 **데카르트 곱 16행짜리
  단일 등급 차원으로 합치고**, 구매–탑승 등급의 관계를 서술하는 등급 변경 지표까지 그 안에
  둘 수 있다 — 사실상 [정크 차원](../concepts/junk-dimension.md)의 일종이며, 이 사례에서는
  속성들이 밀접히 상관돼 있다 (12장, pp.319–320).[^kimball2013]
  - 단, 재고 가용성이나 티켓 구매 같은 **다른 팩트 테이블은 4행짜리 표준 등급 차원을 참조**한다
    (12장, p.320).[^kimball2013] 합치는 것은 그 팩트 테이블 하나의 사정이다.
- **조합 의존 속성의 예 — 출발지·목적지**: 공항은 볼륨이 커서 분리된 역할 연기가 더 실용적으로
  보인다. 그러나 업무 사용자는 각 공항의 특성만이 아니라 **도시 쌍(city-pair) 사이의 거리와
  도시 쌍의 유형(국내·대서양 횡단 등)** 처럼 조합에 의존하는 속성을 원한다 (12장,
  p.320).[^kimball2013]
  - 결정적 논거는 **라벨 일관성**이다. "출발이 SFO였든 DEN이었든 SFO–DEN 사이의 총 활동"
    같은 단순한 질문조차 분리된 두 차원으로는 까다롭고, SQL 전문가가 프로그램으로 답을 낼 수
    있더라도 **무방향 도시 쌍 노선에 표준 라벨이 없다** — 어떤 리포팅 애플리케이션은
    SFO-DEN, 다른 것은 DEN-SFO, San Fran-Denver, Den-SF로 적는다. 일관되지 않은 라벨을 BI
    애플리케이션 코드에 박아 넣는 대신 **속성 값을 차원 테이블에 저장해 전사가 공통 표준
    라벨을 쓰게** 해야 한다. 웨어하우스를 애써 만들어 놓고 애플리케이션 코드가 제각각의
    리포트 라벨을 구현하게 두는 것은 부끄러운 일이고, 사업 후원자는 그것을 오래 참지 않는다
    (12장, p.320).[^kimball2013]
  - 두 선택지 (12장, pp.320–321):[^kimball2013] ① 방향 노선명·무방향 노선명·유형·거리를 담는
    **도시 쌍 노선 차원을 팩트 테이블에 하나 더 붙인다**. ② 출발·도착 공항 속성과 노선 속성을
    **단일 차원으로 합친다** — 이론적 상한은 데카르트 곱이지만 항공사가 모든 공항 쌍을 운항하지
    않으므로 실제 행 수는 훨씬 작다. 다만 출발지 속성 수십 개 + 도착지 속성 수십 개 + 노선
    속성이면 **분리해 두고 싶어질 가능성이 크다.**
  - 브리지 기각: 출발지–도착지가 다대다이긴 하나 **기존 팩트 테이블 안에서 깔끔하게 표현되므로
    브리지를 쓸 필요가 없다** (12장, p.321).[^kimball2013]
- 종합 판정 — **상관된 차원을 합치는 것은 규칙이 아니라 예외로 보아야 한다** (12장,
  p.324).[^kimball2013]

## 자기 자신을 역할로 부르는 차원 — 직원과 관리자

9장은 같은 차원이 **같은 팩트 테이블에서 두 주체로 등장하는** 경우를 다룬다. 관리자 이름
정도가 아니라 그 이상을 원하면 구조가 필요해진다 (9장, p.271).[^kimball2013]

- **선택지 ① 팩트 테이블에 이중 외래 키**: 관리자의 직원 키를 팩트 테이블의 또 하나의 외래
  키로 두고, 모든 속성 이름이 "manager"를 가리키는 역할 연기 직원 차원에 조인한다. 팩트 행이
  삽입될 때마다 직원과 그 관리자가 결부되고, **두 차원이 팩트 테이블에 대칭적 접근을 제공하므로
  직원 속성으로든 관리자 속성으로든 사실상 동일한 질의 성능**으로 필터·그룹핑할 수 있다.
  단점은 관리 보고를 지원하려면 **이 이중 외래 키를 모든 팩트 테이블에 박아 넣어야 한다**는
  것이다 (9장, p.271).[^kimball2013]
- **선택지 ② 직원 차원의 아웃리거**: 관리자의 직원 키를 직원 차원 행의 속성으로 두고, 직원
  차원을 역할 연기한 아웃리거에 조인한다 — 속성 이름은 모두 "manager"를 붙여 직원 특성과
  구별한다 (9장, p.272).[^kimball2013] 이 키를 타입 1로 둘지 타입 2로 둘지가 낳는 결과는
  [SCD](../concepts/slowly-changing-dimension.md)의 "관리자 키의 파급" 절에 있다.

## 버스 매트릭스에 적는 법

- 버스 매트릭스에서는 한 셀 안에 여러 역할을 나열하는 표기가 가장 흔하다(예: Ordering 행의 Date 열에 "Order Date, Requested Ship Date"). 역할 수가 적고 프로세스 간 재사용이 잦으면 표준 차원 열 아래 하위 열을 만들 수도 있다 (6장, pp.171–172).[^kimball2013]

[^kimball2013]: Kimball & Ross 2013, 6–8장 "Order Management" · "Accounting" · "Customer Relationship Management" · 9장 "Human Resources Management" · 12장 "Transportation" · 14장 "Healthcare"
