## 하나의 질문

**데이터를 불변으로 두면서도 과거에 대한 우리의 이해가 바뀌는 것을 어떻게 표현하는가.**

데이터 메시가 [데이터 프로덕트](../concepts/data-product-serving-design.md)의 출력을 불변·읽기
전용으로 못 박고 나면 남는 문제가 이것이다. 저자의 답은 **시간 축을 하나 더 두는 것**이다 —
과거는 바꾸지 않고, 과거에 대한 현재의 이해를 새 시각으로 덧붙인다.

## 정의 — 두 타임스탬프

- 절 머리의 제사(題詞)가 방향을 잡는다 (12장, p.208):[^dehghani2022]

> It seems that change and time are inseparable: changes take time; are located and
> ordered in time; and they are separated by time. The inseparability of time and change
> is a kind of logical truth.
> — Raymond Tallis

- 정의 — **바이템포럴(bitemporal) 데이터는 데이터의 모든 조각이 두 타임스탬프를 기록하도록
  데이터를 모델링하는 방식이다: "이벤트가 실제로 일어났거나 상태가 실제로 그러했던 때"인
  실제 시간(actual time)과, "데이터가 처리된 때"인 처리 시간(processing time)의 결합이다**
  (12장, p.208).[^dehghani2022]
- 그 모델링이 가능하게 하는 것 — **바이템포럴 데이터 모델링은 데이터를 불변 엔티티로, 곧
  {데이터 프로덕트 필드, 실제 시간, 처리 시간}의 튜플로 서빙하는 것을 가능하게 한다. 여기서
  처리 시간은 새 데이터 엔티티가 처리될 때마다 단조증가(monotonically increases)하며, 시간적
  분석과 시간 여행(time travel) — 곧 과거 추세를 보고 미래 가능성을 예측하는 것 — 을 수행할 수
  있게 한다. 이 두 결과 모두 데이터 메시에 본질적이다** (12장, p.209).[^dehghani2022]
- 각주가 재처리의 귀결을 못 박는다 — **이전 데이터를 재처리하는 것, 예컨대 과거 오류를 고치는
  것은 새 데이터 엔티티와 새 처리 시간을 낳는다. 데이터 프로덕트의 폐기 레코드 정책이 과거
  (오류) 데이터 엔티티를 보존할지 말지를 결정할 수 있다** (12장, p.209, 각주
  3).[^dehghani2022]
- 저자가 출처를 밝힌다 — **Martin Fowler가 이 바이템포럴리티를 단순하고 훌륭한 글
  "Bitemporal History"에서 제시한다. 이 절에서 나는 데이터 프로덕트가 이 개념을 처리의
  지연이나 데이터의 모양(이벤트냐 스냅샷이냐)에 불가지인 통합 모델로 채택하는 방식을
  요약한다** (12장, p.210).[^dehghani2022]
- 두 축의 관계 — **실제 시간과 처리 시간은 데이터 프로덕트가 보존하고 서빙하는, 서로 얽힌
  (entangled) 두 시간 축이다** (12장, p.209).[^dehghani2022]

## 실제 시간의 유동

- 무엇을 담는가 — **분석 사용 사례의 필요에 맞는 형태로 데이터를 표현하기 위해, 데이터
  프로덕트는 무한한 시간 폭에 걸쳐 도메인의 상태(또는 이벤트)를 시간에 따라 포착하고 공유한다.
  예컨대 **podcast listeners** 데이터 프로덕트는 "1년 전부터 지금까지의 일별 팟캐스트 청취자
  정보"를 공유할 수 있다** (12장, p.209).[^dehghani2022]
  - 무한의 뜻은 조건부다 — **무한의 정의는 데이터 퀀텀의 데이터 보존 정책에 달렸다** (12장,
    p.209, 각주 4).[^dehghani2022]
- 정의 — **실제 시간은 이벤트가 일어난 때 또는 특정 상태가 존재하는 때다. 예컨대 2021-07-15는
  그날 실제로 Daff의 팟캐스트를 들은 podcast listeners(데이터)의 실제 시간이다** (12장,
  p.209).[^dehghani2022]
- 왜 분석에서만 두드러지는가 — **실제 시간의 존재는 중요하다. 예측적·진단적 분석은 무언가가
  실제로 일어난 시각에 민감하기 때문이다. 많은 운영 기능은 그렇지 않다. 대부분의 경우 운영
  기능은 데이터의 현재 상태를 다룬다. 예컨대 "현재 팟캐스트 청취자들의 현 주소를 줘, 인쇄된
  마케팅 자료를 보내게"다** (12장, p.209).[^dehghani2022]
  - 운영 데이터와 분석 데이터의 갈림이 시간 축의 유무로 다시 진술되는 자리다 —
    [데이터 메시](../concepts/data-mesh.md) 1장이 세운 두 데이터의 구분과 같은 선이다.
- 이 축은 단조롭지 않다 — **실제 시간은 요동친다(fluctuate). 데이터 프로덕트는 순서가 어긋난
  실제 시간을 관측하거나, 원천 데이터에 수정이 가해진 뒤 같은 실제 시간에 대한 새 데이터를
  받을 수 있다** (12장, p.210).[^dehghani2022]

## 처리 시간의 연속체

- 정의 — **처리 시간은 데이터 프로덕트가 특정 실제 시간에 대한 상태나 이벤트에 관한 자기 지식
  또는 이해를 관측·처리·기록·서빙하는 시각이다. 예컨대 2021-08-12T01:00에 **podcast listeners**
  데이터 프로덕트는 2021-08-11에 팟캐스트를 들은 모든 사람에 대한 데이터를 처리하고 그때의
  세계 상태에 대한 이해를 얻는다. 2021-08-12T01:00이 처리 시간이다** (12장,
  p.210).[^dehghani2022]
- 이 축이 변화를 위한 설계의 열쇠라고 못 박는다 — **처리 시간을 데이터의 필수 속성으로 제공하는
  것이 변화를 위한 설계(design for change)의 열쇠다. 과거에 대한 우리의 이해는 바뀐다. 과거에
  일어난 오류를 고치거나, 과거에 대한 이해를 개선하는 새 정보를 알게 된다. 우리는 과거를 바꿀
  수 없지만, 바꿀 수 있는 것은 현재의 처리 시간이다. 우리는 과거 실제 시간에 대한 수정을
  반영하는 새 처리 시간을 가진 새 데이터 조각을 서빙한다** (12장, p.210).[^dehghani2022]
- 한 줄로 압축된 성질 — **처리 시간은 앞으로 단조롭게 움직인다고 신뢰할 수 있는 유일한
  시간이다** (12장, p.210).[^dehghani2022]

## 처리 시간이 접어 넣은 네 시각

- 저자가 의도적으로 뭉갠 구분이 있다 — **나는 처리 시간을 써서 네 개의 서로 다른 시각을 하나로
  접는다(collapse)** (12장, p.210):[^dehghani2022]

| 접힌 시각 | 저자의 정의 |
|---|---|
| 관측 시간(observation time) | 데이터 프로덕트가 이벤트나 상태를 인지하게 되는 때 |
| 처리 시간(processing time) | 데이터 프로덕트가 관측된 데이터를 처리·변환하는 때 |
| 기록 시간(record time) | 데이터 프로덕트가 처리된 데이터를 저장하는 때 |
| 발행 시간(publish time) | 데이터가 데이터 사용자의 접근에 가용해지는 때 |

- 접는 근거 — **이 미묘한 시간 차이들은 데이터 프로덕트의 내부에 가장 관련이 있고 데이터
  사용자에게는 그렇지 않다. 따라서 나는 그것들을 데이터 사용자에게 가장 중요한 하나의 처리
  시간으로 접었다** (12장, p.210).[^dehghani2022]
  - 이것이 [데이터 프로덕트 어포던스](../concepts/data-product-affordances.md)가 말하는
    "어포던스는 상대의 능력에 대한 가정"의 실행례다 — 무엇을 접을지가 **누가 그 구분을 쓸
    수 있는가**로 결정된다.
  - [스트림 처리의 시간 의미론](../concepts/stream-processing-time-semantics.md)이 이벤트
    시간·수집 시간·처리 시간을 **분리 유지**하는 서술과 갈리는 자리다. 대립은 처방이고,
    조건은 **구분을 소비하는 쪽이 프레임워크 내부인가 데이터 사용자인가**이다.

## 철회 — 과거를 고치는 유일한 방법

- 첫째 효과 — **세계에 대한 우리의 이해는 계속 진화한다. 그 이해에는 오류나 누락 정보가 있을
  수 있다. 이 경우 나중의 처리 시간에 우리는 오해를 고친다. 예컨대 2021-08-12T1:00에 우리는
  "2021-08-11에 팟캐스트를 들은 사람들"에 대한 모든 정보를 처리하는데, 청취자 수를 세는 데
  실수를 해서 3,000을 계산한다. 다음번 2021-08-13T10:00에 정보를 처리할 때 우리는 오류를 고쳐
  2021-08-11의 새 카운트 2,005를 만든다. 3,000과 2,005는 같은 정체성 "2021-08-11의 팟캐스트
  청취자 수"에 대한 서로 다른 두 값이 되고, 2021-08-12T10:00에 처리된 상태와
  2021-08-13T10:00에 처리된 상태라는 두 개의 분리된 상태로 포착된다** (12장,
  p.211).[^dehghani2022]
- 그래서 변화가 예외가 아니라 기본이 된다 — **바이템포럴리티를 쓰는 것은 변화를 — 데이터의
  상태·데이터 모델·SLO 메트릭 등의 변화를 — 안으로 짓는다. 변화의 연속적 처리가 모든 소비자와
  메시 전체에 내장된 기본 행위가 된다** (12장, p.211).[^dehghani2022]
- 소비자 쪽 효과 — **이것은 데이터 사용자의 로직을 크게 단순화한다. 과거에 대한 갱신은 더 이상
  특별한 경우도 놀라움도 아니다. 그것은 그저 과거에 대한 새 이야기를 하는 새로 처리된
  데이터다. 소비자는 자기가 과거 한 시점에 처리한 데이터를 추적하고 고정(pin)할 수 있으며,
  데이터의 과거 개정판에 접근하기 위해 그 시점으로 되돌아갈 수 있다** (12장,
  p.211).[^dehghani2022]
- 저자가 난이도를 인정한다 — **물론 그런 시스템을 짓는 것은 쉬운 공학 과제가 아니다** (12장,
  p.211).[^dehghani2022]
- 앞 절과 이어진다 — 불변성이 없으면 이 모델이 성립하지 않는다. 저자는 불변성을 **변화를
  위한 설계의 또 다른 핵심 조력자**로, 그리고 **새 처리 시간과 그 불변 상태의 전파를 통해 메시의
  최종적 일관성(eventual consistency)을 유지하는** 수단으로 규정한다 (12장,
  p.208).[^dehghani2022]

## 스큐 — 두 시간의 거리

- 정의 — **스큐(skew)는 실제 시간과 처리 시간 사이의 시간 차다. 진짜 실시간 시스템만이 무시할
  수 있는 스큐를 갖는다 — 이벤트가 처리되고 세계에 대한 우리의 이해가 이벤트 발생과 거의 정확히
  동시에 형성된다. 이것은 데이터 처리 시스템에서, 특히 각자 실제 이벤트 소스로부터 여러 홉
  떨어져 데이터를 처리하는 데이터 프로덕트들의 사슬을 가진 분석 데이터 처리에서 매우 드물다**
  (12장, p.211).[^dehghani2022]
- 두 시간을 다 노출하는 이유가 여기 있다 — **두 시간의 존재가 데이터 사용자에게 스큐를 알려,
  그들이 자기 적시성 필요에 따라 데이터를 어떻게 처리할지 결정할 수 있게 한다. 소스 정렬
  데이터 프로덕트에서 멀어질수록 스큐는 커질 수 있다** (12장, p.211).[^dehghani2022]
  - 스큐가 **보고되는 값**이라는 점이 중요하다 — 스트림 처리가 워터마크로 스큐를 **감추고
    윈도우를 닫는** 것과 대비된다.

## 윈도잉

- **데이터 프로덕트가 상류 데이터를 시간 윈도우에 걸쳐 집계하는 것은 흔하다. 예컨대
  **play sessions**는 청취자가 플레이어 장치와 교전하는 동안의 모든 이벤트를 집계한다 —
  예컨대 청취자가 한 팟캐스트에서 다른 것으로 이동하다가 마침내 하나를 골라 몇 분 듣고 플레이어를
  치우는 일련의 play 이벤트다. 이는 플레이어와 교전하는 청취자의 행동 분석에 도움이 된다. 이
  경우 play 이벤트들의 실제 시간은 여러 분에 걸칠 수 있다 — 시간 윈도우다. 윈도우를 아는 데이터
  사용자는 그 데이터에 시간 인지 연산(time-aware operations)을 수행할 수 있다** (12장,
  p.211).[^dehghani2022]
  - 윈도우가 프레임워크의 내부 상태가 아니라 **서빙되는 데이터의 성질**로 나오는 것이 차이다 —
    [스트림 처리의 시간 윈도우](../concepts/stream-processing-time-windows.md)가 윈도우를 처리
    엔진의 연산자로 두는 서술과 자리가 다르다.

## 연속적 변화의 반응형 처리

- **데이터 메시는 끊임없는 변화 속의 세계를 가정한다. 이 끊임없는 변화는 새 데이터가 도착하는
  형태일 수도 있고, 처리 시간으로 표시되는 과거에 대한 우리 이해의 진화일 수도 있다. 데이터
  프로덕트는 상류 데이터 프로덕트가 바뀌었다는 이벤트 — 새 처리 시간이 가용해졌다 — 에
  반응함으로써 변화를 연속적으로 처리할 수 있다** (12장, p.212).[^dehghani2022]
- 그 결과 — **처리 시간은 연결된 데이터 프로덕트 사이에 반응형이고 비동기적인 데이터 처리를
  만드는 원시 기제(primitive mechanism)가 된다** (12장, p.212).[^dehghani2022]
  - 곧 처리 시간의 전진 자체가 **트리거**다. 별도 스케줄러가 필요 없다는 11장의 "중앙
    오케스트레이터 없음"이 기제 수준에서 어떻게 성립하는지가 이 문장이다.

## 시간성이 모든 측면을 버저닝한다

- **처리 시간, 곧 데이터 프로덕트의 시간 개념은 시간에 따라 변하는 데이터 프로덕트의 모든
  속성과 성질에 내장된다: 데이터 스키마·데이터 의미론·데이터 사이 관계·SLO·기타 메타다.
  그것들은 자동으로 시간에 의해 버저닝된다** (12장, p.212).[^dehghani2022]
- **처리 시간은 데이터 프로덕트의 영속적 성질 — 곧 데이터 스키마 — 을 버저닝하는 원시 요소가
  된다. 처리 시간은 데이터 프로덕트의 SLO 같은 시간 가변 정보를 상관시키는 파라미터가 된다**
  (12장, p.212).[^dehghani2022]
  - 이것이 11장의 **"기본적으로 모든 데이터 프로덕트 아티팩트와 데이터는 시간이라는 개념을 써서
    버저닝된다"**의 구현 근거다 — 스키마 버저닝을 별도 레지스트리에 두는
    [하위·상위 호환성](../concepts/backward-and-forward-compatibility.md) 계열과 자리가 갈린다.

## 그림 12-4가 한 장에 담은 것

- 그림 12-4는 처리 시간을 세로축, 실제 시간을 가로축으로 두고 한 데이터 프로덕트의 두 시간
  차원을 그린다 (12장, p.213).[^dehghani2022] 저자가 그 안에서 짚는 것은 셋이다 (12장,
  p.212):[^dehghani2022]
  - **스큐** — **데이터 퀀텀이 이벤트를 처리하고 그 데이터의 상태에 대한 이해를 얻고 형성하는
    것이, 이벤트가 실제로 일어난 시점보다 늦는 것은 불가피하다. 예컨대 2021-08-11 동안의 일별
    청취자 상태는 발생 시각보다 늦은 2021-08-12T01:00에 시스템에 알려진다. 팟캐스트 청취자의
    일별 상태를 알기까지 최소 1시간, 최대 25시간의 스큐가 있다.**
  - **처리 오류** — **2021-08-12T01:00에 처리된 총 청취자는 계산에 오류가 있었고 2021-08-11의
    일별 총 청취자를 2,005명 대신 3,000명으로, 조금 낙관적으로 포착했다.**
  - **철회** — **2021-08-12T01:00에 일어난 오류를 데이터 프로덕트 개발자가 잡았고, 처리
    코드에 수정이 적용되었으며, 다음 처리 구간인 2021-08-13T01:00에 올바른 값 2,005가
    보고된다. 따라서 처리 시간 2021-08-13T01:00에 서빙되는 데이터는 2021-08-11과 2021-08-12의
    일별 팟캐스트 청취자 데이터를 포함한다.**
- 도판이 붙인 이름표 — *knowledge history*(어느 시점에 알려진·처리된 데이터), *knowledge
  diff*(서로 다른 두 처리 시간에서의 지식 차이), 24시간 처리 구간, 24시간 윈도우 (12장, p.213,
  그림 12-4).[^dehghani2022]

## 두 파라미터를 받는 함수로서의 서빙 API

- 그림 12-4의 결론이 API 시그니처다 — **그림 12-4가 보여 주는 것은 데이터 서빙 인터페이스와
  API가 두 시간 파라미터, 곧 처리 시간과 실제 시간을 갖는 함수라는 것이다. 사용의 단순함을
  위해 그것들은 데이터의 최신 상태에만 관심 있는 데이터 사용자를 위해 `latest` 같은 특수하고
  기본적인 파라미터를 받을 수 있다** (12장, p.213).[^dehghani2022]
  - 11장의 "가치를 위한 설계"가 말한 **지름길 API**의 정체가 이것이다.
- 시간의 표준화 주체는 거버넌스다 — **이 예에서 나는 단순함을 위해 저해상도 벽시계 시간을
  썼다. 거버넌스가 시간을 어떻게 표준화할지 정하고, 플랫폼이 그것을 일관되게 구현한다** (12장,
  p.213).[^dehghani2022]
- 두 축의 구현이 서로 다르게 지정된다 (12장, pp.213–214):[^dehghani2022]
  - **처리 시간은 순서 있는 읽기(ordered reads)를 보장한다. 그것은 내부 시스템 시간, 에폭 이후의
    증분 카운터, 또는 단조증가하는 수로 구현될 수 있다. 데이터 소비자는 처리 시간을 자기가 어떤
    데이터를 소비했는지 아는 인덱스로 쓴다.** 각주는 **흔히 Kafka 같은 기저 기술이 이 기제를
    제공한다**고 적는다 (12장, p.214, 각주 5).[^dehghani2022]
  - **실제 시간은 ISO 8601 같은 DateTime 표준을 따를 수 있다.**
  - 처리 시간이 **논리적 시계일 수 있고 실제 시간은 벽시계여야 한다**는 이 비대칭이 중요하다 —
    [물리 시계와 동기화](../concepts/physical-clocks-and-synchronization.md) 계열의 문제가
    한쪽 축에만 걸린다.
- 시간 여행의 범위는 정책이 정한다 — **분석 데이터의 데이터 사용자는 시간 여행을 수행해 데이터에
  접근할 때 시간을 앞뒤로 오갈 수 있다. 얼마나 멀리 되돌아갈 수 있는지의 상한은 달라질 수 있다 —
  처음 처리된 데이터까지일 수도, 최신 것뿐일 수도 있다. 이는 데이터 프로덕트의 보존 정책에
  달렸다** (12장, p.214).[^dehghani2022] 그림 12-5가 처리 시간 축을 따라 일별 집계 스냅샷이
  놓이고 그중 하나가 *retraction*으로 표시되는 그림이다 (12장, p.214).[^dehghani2022]

## 상태냐 이벤트냐는 직교하는 관심사다

- **시스템이 데이터를 인코딩하고 처리하는 방식은 두 진영으로 나뉜다: 상태(states)와
  이벤트(events)다. 상태는 한 시점의 시스템 조건을 포착한다 — 예컨대 "오늘의 팟캐스트 청취자
  수"다. 이벤트는 특정 상태 변화의 발생을 포착한다 — 예컨대 "새 팟캐스트 청취자가 접속했다"다.
  상태와 (변화) 이벤트는 데이터를 저장하거나 서빙하는 매우 다른 두 방식을 요구하지만, 나는
  그것을 여기서 논한 시간 차원과 **직교하는(orthogonal)** 관심사로 본다. 변화 이벤트의 스트림을
  포착·서빙하는 것이 말이 되는지, 시스템의 추론된 상태의 스트림을 스냅샷으로 할지, 아니면 둘 다
  할지는 데이터 프로덕트의 로직에 달렸다. 데이터 독자들은 둘 다 보고 싶어 할 가능성이 크다.
  그럼에도 두 시간 축의 존재는 남는다** (12장, pp.214–215).[^dehghani2022]
  - 각주가 계열을 든다 — **데이터 처리의 이중성(duality)은 많은 시스템에서 관찰될 수 있다:
    스트림 대 테이블(예: Confluent), 스냅샷 대 델타(예: Databricks Delta Lake)다** (12장,
    p.214, 각주 6).[^dehghani2022]
  - 이 각주가 [스트림-테이블 이중성](../concepts/stream-table-duality.md)과
    [상태·스트림·불변성](../concepts/state-streams-and-immutability.md)을 정면으로 가리킨다.
    저자의 기여는 그 이중성을 **부정하거나 대체하는 것이 아니라, 그것과 직교하는 축을 하나 더
    세우는 것**이다.

## 철회의 기회를 줄이는 두 전략

- 전제 — **철회를 다루는 방법이 있음에도, 데이터 프로덕트는 오류와 철회의 필요를 줄이도록
  노력해야 한다** (12장, p.215).[^dehghani2022]
- **① 처리 시간 구간을 늘려 품질 통제를 넣는다** — **play events 데이터 프로덕트를 생각해 보라.
  그것은 player devices에서 오는 신호를 포착한다. 데이터 프로덕트는 때때로 이벤트를 놓치거나
  지연된 것을 받을 수 있다. 이는 네트워크 중단, 온디바이스 캐시 접근 불가 등 때문이다. 그러나
  데이터 프로덕트의 변환 코드는 처리 지연을 도입해 합성적으로 예측·생성된 것으로 누락 신호를
  보정하거나, 신호를 중앙값이나 다른 통계적 표현으로 집계할 수 있다. 이는 데이터 프로덕트가 실제
  시간과 처리 시간 사이에 더 긴 스큐를 도입해 오류를 제때 고치고 철회를 피할 기회를 갖는다는
  뜻이다** (12장, p.215).[^dehghani2022]
  - 저자의 예 — **결제 트랜잭션을 준실시간으로 받는 한편, 보정·정산된 결제 계정의 일별 덤프가
    나중에 서빙된다. 이는 처리 구간을 늘리는 것을 요구한다. 결제의 경우 계정의 정확성이
    트랜잭션의 적시성보다 선호된다** (12장, p.215).[^dehghani2022]
  - **스큐가 조정 가능한 설계 파라미터**라는 것이 요점이다 — 정확성과 적시성의 교환을 스큐의
    길이로 산다.
- **② 예상 오류를 반영하도록 SLO를 조정한다** — **어떤 소비자는 준실시간 데이터의 오류에
  완벽히 관용적일 수 있다. 예컨대 player errors를 탐지하는 앱은 최선 노력으로, 여기저기 이벤트가
  빠져도 개의치 않는다. 이 경우 play events 데이터 프로덕트는 그 소비자 범주를 위해 정산 없이
  데이터를 발행할 수 있다. 그러나 이 경우 데이터 프로덕트는 누락 신호 관점에서 발생할 수 있는
  예상 오류 범위에 따라 자기 품질 목표를 소통한다** (12장, p.215).[^dehghani2022]
  - [서비스 수준 목표](../concepts/service-level-objectives.md)가 여기서 **품질 계약**으로 쓰인다 —
    오류를 없애는 대신 오류의 범위를 계약에 적는다.

## 세 소스의 시간 축을 한자리에서

이 KB가 지금까지 반입한 시간 축 처방이 여기서 처음 한자리에 모인다. **셋은 서로 모순되지
않는다 — 축의 개수와 그 축을 누가 소비하는가가 다르다.**

| 소스 | 축의 이름 | 축의 개수 | 과거를 고치는 방법 | 축을 소비하는 쪽 |
|---|---|---|---|---|
| Dehghani, 데이터 메시 (12장) | 실제 시간(actual time) · 처리 시간(processing time) | 둘 다 데이터에 기록 | 새 처리 시간의 새 엔티티(철회) — 원본은 남는다 | **데이터 사용자**(시간 여행 API의 파라미터) |
| Kimball, [SCD](../concepts/slowly-changing-dimension.md) 타입 2 | 유효 시각 · 만료 시각(행 유효 구간) | 차원 행 하나에 구간 하나 | 새 행 + 대리 키 — 사실상 실제 시간 한 축 | **질의 작성자**(조인 시 유효 구간 필터) |
| Kleppmann, [상태·스트림·불변성](../concepts/state-streams-and-immutability.md) | 로그의 오프셋 순서(사실상 처리 시간) | 하나(추가 전용 로그) | 보상 이벤트를 추가 — 원본은 남는다 | **파생 뷰를 만드는 쪽** |
| Reis·Housley / Kafka, [스트림 시간 의미론](../concepts/stream-processing-time-semantics.md) | 이벤트 시간 · 수집 시간 · 처리 시간 | 셋을 분리 유지 | 스트래글러 처리·워터마크 — 재처리가 정석 | **처리 엔진**(윈도우 확정 판정) |

- 축의 대응은 이렇게 읽힌다: Dehghani의 **실제 시간 ≈ 이벤트 시간 ≈ SCD의 유효 구간**,
  **처리 시간 ≈ 트랜잭션 시간 ≈ 로그 오프셋**이다. #hypothesis — 저자는 이 대응을 명시하지
  않는다. 다만 Fowler의 "Bitemporal History"를 출처로 들고 있고, 그 글의 두 축은 시간 데이터베이스
  문헌의 **유효 시간(valid time)·트랜잭션 시간(transaction time)**이므로 대응은 거의 확실하다.
- **진짜 갈리는 것은 두 가지다.**
  - **철회의 표현**: SCD 타입 1은 덮어쓰고, 타입 2는 새 행을 만들되 그 이전에 **잘못 적재된
    값**을 고칠 축이 없다(같은 유효 구간의 두 판본을 구분할 수단이 없다). Dehghani의 처리 시간
    축이 정확히 그 자리를 메운다. 이것은 처방 대립이 아니라 **표현력의 차이**다 — SCD는 단일
    시간 모델이고 바이템포럴은 이중 시간 모델이다.
  - **누가 시간을 본다고 가정하는가**: 스트림 처리는 세 시각을 엔진 안에 두고 사용자에게는
    확정된 윈도우 결과만 준다. Dehghani는 두 시각을 **API 파라미터로 사용자에게 노출**하고
    기본값(`latest`)으로만 감춘다. 이 갈림은 진짜 처방 대립이며, 조건은 **소비자가 시간 인지
    에이전트인가**이다 — 11장의 어포던스 정의가 그대로 판정 기준이다.
