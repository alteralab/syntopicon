하나의 질문: **커넥트는 안에서 어떤 부품으로 나뉘고, 각 부품은 무엇을 책임지는가.**

도구를 쓰는 쪽은 [카프카 커넥트](../concepts/kafka-connect.md)에 있다.

## 세 개념과 그 사이

- **카프카 커넥트가 어떻게 동작하는지 이해하려면 세 가지 기본 개념과 그것들이 어떻게
  상호작용하는지를 이해해야** 한다 (9장, p.225).[^shapira2021]
- **커넥트를 쓰려면 워커 클러스터를 돌리고 커넥터를 만들거나 제거해야** 하는데, **앞에서
  파고들지 않은 세부가 하나 더 있으니 컨버터(converter)에 의한 데이터 취급**이다 —
  **MySQL의 행을, 커넥터가 카프카에 쓴 JSON 레코드로 변환한 구성 요소가 그것**이다 (9장,
  p.226).[^shapira2021]

## 커넥터와 태스크

- **커넥터 플러그인은 커넥터 API를 구현하며, 그 API는 두 부분으로 이뤄진다** — 커넥터와
  태스크다 (9장, p.226).[^shapira2021]
- **커넥터(connector)가 책임지는 세 가지** (9장, p.226):[^shapira2021]
  - **커넥터를 위해 몇 개의 태스크가 돌지 결정한다.**
  - **태스크들 사이에 데이터 복사 작업을 어떻게 나눌지 결정한다.**
  - **워커에서 태스크의 설정을 얻어 전달한다.**
- 예로 든 JDBC 소스 커넥터의 절차 — **데이터베이스에 연결해 복사할 기존 테이블들을 발견하고
  그에 기반해 태스크가 몇 개 필요한지 결정하는데, `tasks.max` 설정값과 테이블 수 중 작은
  쪽을 고른다.** **태스크 수가 정해지면 각 태스크에 대한 설정을 생성**하는데 **커넥터 설정
  (예: `connection.url`)과 각 태스크가 복사하도록 배정한 테이블 목록을 함께 쓴다.**
  **`taskConfigs()` 메서드가 맵의 리스트, 즉 돌리려는 각 태스크의 설정을 반환**한다. 그러면
  **워커들이 태스크를 시작하고 각각에 고유한 설정을 주어 데이터베이스에서 고유한 테이블
  부분집합을 복사하게 하는 것을 책임진다.** 배치의 성질도 명시된다 — **REST API로 커넥터를
  시작하면 어느 노드에서든 시작될 수 있고, 그것이 시작하는 태스크들도 어느 노드에서든
  실행될 수 있다** (9장, p.226).[^shapira2021]
- **태스크(task)는 실제로 데이터를 카프카 안팎으로 옮기는 것을 책임진다.** **모든 태스크는
  워커로부터 컨텍스트(context)를 받아 초기화**된다 (9장, p.226):[^shapira2021]
  - **소스 컨텍스트는 소스 태스크가 소스 레코드의 오프셋을 저장할 수 있게 하는 객체를
    포함**한다 — **파일 커넥터에서 오프셋은 파일 안의 위치이고, JDBC 소스 커넥터에서
    오프셋은 테이블의 타임스탬프 컬럼일 수 있다.**
  - **싱크 커넥터의 컨텍스트는 커넥터가 카프카에서 받는 레코드를 통제할 수 있게 하는
    메서드들을 포함**한다 — **배압(back pressure) 적용, 재시도, 정확히 한 번 전달을
    위한 오프셋 외부 저장** 같은 것에 쓰인다.
  - **태스크가 초기화된 뒤에는 그 태스크를 위해 `Connector`가 만든 설정을 담은 `Properties`
    객체와 함께 시작**된다. **태스크가 시작되면 소스 태스크는 외부 시스템을 폴링해 워커가
    카프카 브로커로 보낼 레코드 리스트를 반환**하고, **싱크 태스크는 워커를 통해 카프카에서
    레코드를 받아 외부 시스템에 그 레코드를 쓰는 것을 책임진다.**

## 워커

- **카프카 커넥트의 워커 프로세스는 커넥터와 태스크를 실행하는 "컨테이너" 프로세스**다.
  책임은 넷이다 — **커넥터와 그 설정을 정의하는 HTTP 요청 처리, 커넥터 설정을 내부 카프카
  토픽에 저장, 커넥터와 그 태스크의 시작, 적절한 설정의 전달** (9장, p.227).[^shapira2021]
- 고가용성이 여기서 나온다 — **워커 프로세스가 멈추거나 죽으면 커넥트 클러스터의 다른
  워커들이 (카프카 컨슈머 프로토콜의 하트비트를 써서) 그것을 인지하고 그 워커에서 돌던
  커넥터와 태스크를 남은 워커들에 재배정**한다. **새 워커가 커넥트 클러스터에 합류하면 다른
  워커들이 알아채고 커넥터나 태스크를 배정해 모든 워커 사이에 부하가 공정하게 분산되게**
  한다. **워커는 소스·싱크 커넥터 양쪽의 오프셋을 내부 카프카 토픽에 자동으로 커밋하는 것과
  태스크가 오류를 던질 때 재시도를 처리하는 것도 책임진다** (9장, p.227).[^shapira2021]
  하트비트가 무엇을 재는지는
  [컨슈머 그룹과 리밸런스](../concepts/kafka-consumer-groups-and-rebalance.md)에 있다.
- 경계선의 정본 서술은 원문 그대로 (9장, p.227):[^shapira2021]

  > The best way to understand workers is to realize that connectors and tasks are
  > responsible for the "moving data" part of data integration, while the workers are
  > responsible for the REST API, configuration management, reliability, high
  > availability, scaling, and load balancing.

- **이 관심사 분리가 클래식 컨슈머/프로듀서 API 대비 커넥트 API를 쓰는 주된 이점**이다.
  **경험 있는 개발자는 카프카에서 데이터를 읽어 데이터베이스에 삽입하는 코드를 쓰는 데
  하루 이틀이면 된다는 것을 알지만, 설정·오류·REST API·모니터링·배포·확장과 축소·장애
  처리까지 다뤄야 하면 제대로 하는 데 몇 달이 걸릴 수 있다.** 게다가 **대부분의 데이터
  통합 파이프라인은 소스나 타깃이 하나만 있는 것이 아니므로, 단 하나의 데이터베이스 통합을
  위한 맞춤 코드에 쓴 그 노력을 다른 기술들을 위해 여러 번 반복하게** 된다. **커넥터로
  데이터 복사를 구현하면 커넥터가 워커에 꽂히고, 워커가 신경 쓸 필요 없는 복잡한 운영 문제
  한 무더기를 처리**한다 (9장, p.227).[^shapira2021]

## 컨버터와 커넥트의 데이터 모델

- **커넥트 API 퍼즐의 마지막 조각이 커넥터 데이터 모델과 컨버터**다. **카프카의 커넥트
  API는 데이터 API를 포함하는데, 여기에는 데이터 객체와 그 데이터를 기술하는 스키마가 둘 다
  들어 있다** (9장, p.227).[^shapira2021]
- 예로 든 JDBC 소스 커넥터의 절차 — **데이터베이스에서 컬럼을 읽고, 데이터베이스가 반환한
  컬럼의 데이터 타입에 기반해 `Connect Schema` 객체를 구성**한다. **그런 다음 그 스키마를
  써서 데이터베이스 레코드의 모든 필드를 담는 `Struct`를 구성하고, 각 컬럼에 대해 컬럼
  이름과 그 컬럼의 값을 저장**한다. **모든 소스 커넥터가 비슷한 일을 한다 — 소스 시스템에서
  이벤트를 읽고 `Schema`와 `Value` 쌍을 생성**한다. **싱크 커넥터는 반대로 `Schema`와
  `Value` 쌍을 받아 `Schema`를 써서 값을 파싱하고 타깃 시스템에 삽입**한다 (9장,
  p.227).[^shapira2021]
- 그래도 남는 질문 — **소스 커넥터가 데이터 API에 기반해 객체를 생성하는 법을 알더라도
  `Connect` 워커가 이 객체들을 카프카에 어떻게 저장하는가**의 문제다. **여기서 컨버터가
  등장**한다. **워커(또는 커넥터)를 설정할 때 카프카에 데이터를 저장하는 데 쓸 컨버터를
  고르며, 현재 가용한 선택지는 원시 타입·바이트 배열·문자열·에이브로·JSON·JSON 스키마·
  프로토버프**다. **JSON 컨버터는 결과 레코드에 스키마를 포함하거나 포함하지 않도록 설정할
  수 있어 구조화 데이터와 반구조화 데이터를 모두 지원**한다. **커넥터가 데이터 API 레코드를
  반환하면 워커는 설정된 컨버터를 써서 레코드를 에이브로 객체·JSON 객체·문자열로 변환하고
  그 결과가 카프카에 저장된다** (9장, p.228).[^shapira2021] 형식 자체의 성질은
  [카프카 직렬화와 스키마 레지스트리](../concepts/kafka-serialization-and-schema-registry.md)에
  있다.
- **싱크 커넥터에는 반대 과정이 일어난다** — **커넥트 워커가 카프카에서 레코드를 읽으면
  설정된 컨버터를 써서 레코드를 카프카의 형식(원시 타입·바이트 배열·문자열·에이브로·JSON·
  JSON 스키마·프로토버프)에서 커넥트 데이터 API 레코드로 변환한 뒤 싱크 커넥터에 넘겨
  목적지 시스템에 삽입**한다 (9장, p.228).[^shapira2021]
- 그래서 얻는 것 — **커넥트 API는 커넥터 구현과 독립적으로 카프카에 저장된 서로 다른 유형의
  데이터를 지원할 수 있다.** 즉 **컨버터가 가용하기만 하면 어떤 커넥터든 어떤 레코드 타입과
  함께 쓸 수 있다** (9장, p.228).[^shapira2021]

## 오프셋 관리

- **오프셋 관리는 (REST API를 통한 배포·설정 관리에 더해) 워커가 커넥터를 위해 수행하는
  편리한 서비스 중 하나**다. **커넥터는 어떤 데이터를 이미 처리했는지 알아야 하고, 카프카가
  제공하는 API로 어떤 이벤트가 이미 처리됐는지에 대한 정보를 유지**할 수 있다 (9장,
  p.228).[^shapira2021]
- 소스 커넥터 쪽 — **커넥터가 커넥트 워커에 반환하는 레코드는 논리적 파티션과 논리적
  오프셋을 포함한다.** **이것들은 카프카 파티션과 카프카 오프셋이 아니라 소스 시스템에서
  필요한 파티션과 오프셋**이다. **파일 소스에서는 파티션이 파일이고 오프셋이 파일 안의 줄
  번호나 문자 번호일 수 있으며, JDBC 소스에서는 파티션이 데이터베이스 테이블이고 오프셋이
  테이블에 있는 레코드의 ID나 타임스탬프일 수 있다** (9장, p.228).[^shapira2021]
  - **소스 커넥터를 쓸 때 관여하는 가장 중요한 설계 결정 중 하나가 소스 시스템의 데이터를
    파티셔닝하고 오프셋을 추적하는 좋은 방법을 정하는 것**이다 — **이것이 커넥터가 달성할
    수 있는 병렬성 수준과, 최소 한 번 또는 정확히 한 번 의미론을 전달할 수 있는지에 영향을
    준다** (9장, p.228).[^shapira2021]
- 저장 시점 — **소스 커넥터가 (각 레코드에 대한 소스 파티션과 오프셋을 포함한) 레코드
  리스트를 반환하면 워커는 레코드들을 카프카 브로커로 보낸다. 브로커가 레코드들을 성공적으로
  확인하면 그때 워커가 카프카로 보낸 레코드들의 오프셋을 저장**한다. **이것이 커넥터가
  재시작이나 크래시 후 가장 최근에 저장된 오프셋부터 이벤트 처리를 시작할 수 있게** 한다
  (9장, pp.228–229).[^shapira2021]
- **저장 메커니즘은 플러그인 가능하며 보통 카프카 토픽**이다 — **토픽 이름은
  `offset.storage.topic` 설정으로 통제**한다. 그에 더해 **커넥트는 카프카 토픽을 써서 만든
  모든 커넥터의 설정과 각 커넥터의 상태를 저장하며, 각각 `config.storage.topic`과
  `status.storage.topic` 설정으로 이름이 정해진다** (9장, p.229).[^shapira2021]
- 싱크 커넥터 쪽 — **반대이되 비슷한 워크플로**다. **카프카 레코드를 읽는데 그것들은 이미
  토픽·파티션·오프셋 식별자를 갖고 있다.** **그런 다음 그 레코드들을 목적지 시스템에
  저장해야 하는 `connector put()` 메서드를 호출하고, 커넥터가 성공을 보고하면 커넥터에 준
  오프셋을 보통의 컨슈머 커밋 방법으로 카프카에 다시 커밋**한다 (9장,
  p.229).[^shapira2021] 그 커밋 방법의 선택지는
  [오프셋 커밋 전략](../concepts/kafka-offset-commit-strategies.md)에 있다.
- 왜 프레임워크가 이것을 맡는가 — **프레임워크 자체가 제공하는 오프셋 추적이 개발자가
  커넥터를 쓰기 쉽게 만들고, 서로 다른 커넥터를 쓸 때 어느 정도 수준의 일관된 동작을
  보장**하기 때문이다 (9장, p.229).[^shapira2021]
