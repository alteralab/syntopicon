하나의 질문: **배치 잡의 입력과 출력을 여러 기계에 흩어 놓는 파일시스템은 로컬 파일시스템의
무엇을 어떻게 옮겨 온 것인가.**

## 로컬 파일시스템의 네 계층

- **운영체제가 제공하는 파일시스템은 여러 계층으로 이뤄져 있다** (11장,
  p.458):[^kleppmann2026]
  - **가장 낮은 수준에서 블록 장치 드라이버(block device drivers)가 디스크와 직접 이야기하고
    위 계층들이 원시 블록을 읽고 쓸 수 있게 한다.**
  - **블록 계층 위에는 최근 접근한 블록을 더 빠른 접근을 위해 메모리에 유지하는 페이지
    캐시(page cache)가 앉는다.**
  - **블록 API는 큰 파일을 블록으로 쪼개고 아이노드(inodes)·디렉터리·파일 같은 파일 메타데이터를
    추적하는 파일시스템 계층에 감싸인다. 리눅스의 두 흔한 구현이 예컨대 ext4와 XFS다.**
  - **마지막으로 운영체제는 가상 파일시스템(virtual filesystem, VFS)이라 불리는 공통 API를 통해
    서로 다른 파일시스템을 애플리케이션에 노출한다. VFS는 애플리케이션이 밑에 깔린 파일시스템과
    무관하게 표준적인 방식으로 읽고 쓸 수 있게 해 주는 것이다.**
- 페이지 캐시 계층의 세부는 [페이지 캐시와 축출](../concepts/page-cache-and-eviction.md)에 있다.

## 블록이 커진다

- **분산 파일시스템도 거의 같은 방식으로 동작한다. 파일은 블록으로 쪼개지고 그 블록은 많은
  기계에 분산된다. DFS 블록은 통상 로컬 블록보다 훨씬 크다. HDFS는 128 MB가 기본값이고, JuiceFS와
  많은 오브젝트 스토어는 4 MB 블록을 쓴다 — ext4의 4,096바이트보다 훨씬 크다. 블록이 크다는 것은
  추적할 메타데이터가 적다는 뜻이고, 이는 페타바이트 크기의 데이터셋에서 큰 차이를 만든다. 큰
  블록은 또한 블록을 읽는 것 대비 그것을 탐색하는 오버헤드를 낮춘다** (11장,
  p.458).[^kleppmann2026]
- 부분 블록 쓰기의 제약이 사라진다 — **대부분의 물리 저장 장치는 부분 블록을 쓸 수 없어서
  운영체제는 데이터가 블록 전체를 차지하지 않더라도 쓰기가 블록 전체를 쓰도록 요구한다. 분산
  파일시스템은 블록이 더 크고 보통 운영체제 파일시스템 위에 구현되므로 이 요구가 없다. 예컨대
  128 MB 블록으로 저장된 900 MB 파일은 128 MB를 쓰는 블록 일곱 개와 4 MB를 쓰는 블록 하나를
  갖는다** (11장, p.458).[^kleppmann2026]

## 데이터 노드

- **DFS 블록은 그 블록을 저장하는 클러스터의 기계에 네트워크 요청을 함으로써 읽힌다. 각 기계는
  데몬을 돌리며, 원격 프로세스가 자기 로컬 파일시스템의 파일로서 블록을 읽고 쓸 수 있게 하는
  API를 노출한다. HDFS는 이 데몬을 DataNodes라 부르고 GlusterFS는 glusterfsd 프로세스라 부른다.
  이 책에서는 그것을 데이터 노드(data nodes)라 부르겠다** (11장, p.458).[^kleppmann2026]
- 페이지 캐시도 대응물을 갖는다 — **분산 파일시스템은 페이지 캐시의 분산 등가물도 구현한다. DFS
  블록이 데이터 노드에 파일로 저장되므로 읽기와 쓰기는 각 데이터 노드의 운영체제를 거치고, 거기에
  인메모리 페이지 캐시가 포함된다. 이는 자주 읽히는 데이터 블록을 데이터 노드의 메모리에 유지한다.
  어떤 분산 파일시스템은 JuiceFS에서 발견되는 클라이언트 측·로컬 디스크 캐싱 같은 더 많은 캐싱
  계층도 구현한다** (11장, p.458).[^kleppmann2026]

## 메타데이터 서비스

- **ext4와 XFS 같은 파일시스템은 여유 공간, 파일 블록 위치, 디렉터리 구조, 권한 설정 등을 포함한
  저장 메타데이터를 추적한다. 분산 파일시스템도 기계들에 흩어진 파일 위치와 권한 설정 등을 추적할
  방법이 필요하다. Hadoop에는 클러스터의 메타데이터를 유지하는 NameNode라는 서비스가 있다.
  DeepSeek의 3FS에는 FoundationDB 같은 키-값 저장소에 데이터를 영속화하는 메타데이터 서비스가
  있다** (11장, p.459).[^kleppmann2026]

## VFS 자리를 대신하는 프로토콜

- **파일시스템 위에는 VFS가 앉는다. 배치 처리에서 가까운 대응물은 분산 파일시스템의
  프로토콜이다. 분산 파일시스템은 배치 처리 시스템이 파일을 읽고 쓸 수 있도록 프로토콜이나
  인터페이스를 노출해야 한다. 이 프로토콜은 플러그 가능한 인터페이스로 작동한다; 어떤 DFS든 그
  프로토콜을 구현하기만 하면 쓰일 수 있다. 예컨대 아마존 S3의 API는 MinIO, Cloudflare의 R2,
  Tigris, Backblaze의 B2 등 많은 저장 시스템에 널리 채택됐다. S3 지원을 갖춘 배치 처리 시스템은
  이 저장 시스템 중 무엇이든 쓸 수 있다** (11장, p.459).[^kleppmann2026]
- 반대 방향도 있다 — **어떤 DFS는 운영체제의 VFS에 다른 파일시스템과 똑같이 보이는 POSIX 호환
  파일시스템을 구현한다. VFS에 통합하기 위해 흔히 Filesystem in Userspace(FUSE)나 Network File
  System(NFS) 프로토콜이 쓰인다. NFS는 아마 가장 잘 알려진 분산 파일시스템 프로토콜이다. 이
  프로토콜은 원래 여러 클라이언트가 단일 서버의 데이터를 읽고 쓸 수 있게 하려고 개발됐다. 더
  최근에는 Amazon Elastic File System(EFS)과 Archil 같은 파일시스템이 훨씬 더 확장 가능한
  NFS 호환 분산 파일시스템 구현을 제공한다. NFS 클라이언트는 여전히 한 엔드포인트에 접속하지만,
  그 밑에서 이 시스템들은 분산 메타데이터 서비스 및 데이터 노드와 통신해 데이터를 읽고 쓴다**
  (11장, p.459).[^kleppmann2026]

## 공유 없음 원칙

- 별도 상자로 아키텍처 계보를 못박는다 — **분산 파일시스템은 공유 없음(shared-nothing) 원칙에
  기반하며, 이는 네트워크 결합 저장(network attached storage, NAS)과 저장 영역
  네트워크(storage area network, SAN) 아키텍처의 공유 디스크 접근과 대비된다. 공유 디스크
  저장은 중앙 집중식 저장 어플라이언스로 구현되며, 흔히 맞춤 하드웨어와 파이버 채널(Fibre
  Channel) 같은 특수 네트워크 인프라를 쓴다. 반면 공유 없음 접근은 특수 하드웨어를 요구하지
  않고 통상의 데이터센터 네트워크로 연결된 컴퓨터만 요구한다** (11장,
  p.459).[^kleppmann2026] 그 세 아키텍처의 대비는
  [분산 대 단일 노드](../concepts/distributed-versus-single-node.md)에 있다.

## 복제와 이레이저 코딩

- **많은 분산 파일시스템은 범용 하드웨어 위에 지어지는데, 이는 더 싸지만 엔터프라이즈급
  하드웨어보다 실패율이 높다. 기계와 디스크 장애를 견디기 위해 파일 블록은 여러 기계에
  복제된다. 이는 또한 스케줄러가 워크로드를 더 고르게 분산할 수 있게 하는데, 태스크의 입력
  데이터 레플리카를 담은 어느 노드에서든 태스크를 실행할 수 있기 때문이다** (11장,
  p.459).[^kleppmann2026]
- 복제의 두 갈래 — **복제는 6장에서 서술한 대로 같은 데이터의 사본 여럿을 여러 기계에 그냥
  유지하는 것을 뜻할 수도 있고, 리드–솔로몬 코드(Reed–Solomon codes) 같은 이레이저 코딩(erasure
  coding) 방식을 쓰는 것을 뜻할 수도 있다. 이레이저 코딩은 전체 복제보다 낮은 저장 오버헤드로
  잃어버린 데이터를 복구할 수 있게 한다. 이 기법들은 같은 기계에 붙은 여러 디스크에 걸쳐 중복성을
  제공하는 RAID와 비슷하다; 차이는 분산 파일시스템에서는 파일 접근과 복제가 특수 하드웨어 없이
  통상의 데이터센터 네트워크로 이뤄진다는 것이다** (11장, pp.459–460).[^kleppmann2026]
  복제 일반은 [데이터 복제](../synthesis/data-replication.md) 허브가 담당한다.

## HDFS — 계보와 오브젝트 저장과의 차이

- 계보 — **최근의 과거에 "하둡"은 사실상 "빅데이터"의 동의어였다. 하둡 분산 파일시스템은 Google
  File System(GFS)에 기반하며 처음에는 맵리듀스 프로그래밍 모델로 데이터를 처리하도록 설계됐다**
  (6장, p.211).[^reis2022]
- 오브젝트 저장과의 핵심 차이 — **하둡은 오브젝트 저장과 비슷하지만 핵심 차이가 있다: 하둡은
  컴퓨트와 저장을 같은 노드에 결합하는 반면 오브젝트 스토어는 일반적으로 내부 처리 지원이 제한적
  이다** (6장, p.211).[^reis2022] 그 대비의 다른 쪽 서술은
  [오브젝트 스토어](../concepts/object-stores.md)의 데이터 지역성 절에 있다.
- 블록과 네임노드 — **하둡은 큰 파일을 블록(blocks)으로 쪼개는데, 이는 수백 메가바이트 미만 크기의
  데이터 청크다. 파일시스템은 네임노드(NameNode)가 관리하며, 네임노드는 디렉터리·파일 메타데이터와
  클러스터에서 파일 블록의 위치를 서술하는 상세 카탈로그를 유지한다** (6장, p.211).[^reis2022]
- 복제 계수와 자동 복구 — **전형적 설정에서 각 데이터 블록은 세 노드에 복제된다. 이는 데이터의
  내구성과 가용성을 둘 다 높인다. 디스크나 노드가 실패하면 어떤 파일 블록의 복제 계수가 3 아래로
  떨어질 것이다. 네임노드는 다른 노드에 이 파일 블록을 복제해 다시 올바른 복제 계수에 도달하도록
  지시할 것이다. 따라서 상관 장애(correlated failure, 예: 데이터센터를 때리는 소행성)가 아닌 한
  데이터를 잃을 확률은 매우 낮다** (6장, pp.211–212).[^reis2022] 그 계산의 일반형은
  [복제와 이레이저 코딩](#복제와-이레이저-코딩) 절에 있다.
- 저장 시스템만이 아니다 — **하둡은 단순히 저장 시스템이 아니다. 하둡은 컴퓨트 자원을 저장 노드와
  결합해 제자리 데이터 처리를 허용한다. 이는 원래 맵리듀스 프로그래밍 모델로 달성됐다** (6장,
  p.212).[^reis2022]

## "하둡은 죽었다"는 말의 정확한 범위

- 저자들의 판정 — **하둡이 죽었다는 주장을 자주 본다. 이는 부분적으로만 참이다. 하둡은 더 이상
  뜨겁고 최첨단인 기술이 아니다. Apache Pig 같은 많은 하둡 생태계 도구가 이제 생명 유지 장치에
  있고 주로 레거시 잡을 돌리는 데 쓰인다. 순수 맵리듀스 프로그래밍 모델은 밀려났다. HDFS는 다양한
  응용과 조직에서 여전히 널리 쓰인다** (6장, p.212).[^reis2022]
- 어디에 남아 있는가 — **하둡은 여전히 많은 레거시 설치에 나타난다. 빅데이터 열풍의 정점에 하둡을
  채택한 많은 조직은 새 기술로 이전할 즉각적 계획이 없다. 이는 방대한(수천 노드) 하둡 클러스터를
  돌리고 온프레미스 시스템을 효과적으로 유지할 자원을 가진 회사에 좋은 선택이다. 더 작은 회사는
  작은 하둡 클러스터를 돌리는 비용 오버헤드와 규모 한계를 클라우드 해법으로의 이전과 견줘 다시
  생각해 볼 수 있다** (6장, p.212).[^reis2022]
- 그리고 현행 엔진의 재료다 — **덧붙여 HDFS는 Amazon EMR 같은 많은 현행 빅데이터 엔진의 핵심
  재료다. 사실 Apache Spark는 여전히 HDFS 클러스터에서 흔히 돌아간다** (6장,
  p.212).[^reis2022] 그 하이브리드 배치는
  [컴퓨트와 저장의 분리](../concepts/compute-storage-separation.md)에 있다.
