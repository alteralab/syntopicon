이 페이지의 질문: **실행 중인 핫스팟 프로세스의 내부 자료 구조를 밖에서 어떻게 들여다보고,
그것으로 무엇을 확인할 수 있는가.**

## 서비스 에이전트란 무엇인가

- **JHSDB는 SA를 통해 프로세스 외부에서 디버깅할 수 있는 도구**이며, **SA는 핫스팟 가상 머신이
  제공하는 API 집합으로 자바 가상 머신의 런타임 정보를 제공한다. 대부분 자바 언어로 구현되었고
  JNI 코드도 일부 사용한다** (4장, p.214).[^zhou2024]
- 설계의 핵심은 '비추기'다 — **SA는 핫스팟의 내부 데이터 구조를 참고해 설계되었다. 이 구조들은
  핫스팟 C++ 코드의 데이터를 자바 객체로 그대로 추상화한 것이다. SA의 API를 이용하면 다른
  핫스팟의 내부 데이터를 독립된 자바 가상 머신 프로세스에서 분석할 수 있다. 또한 핫스팟이
  런타임에 메모리를 어떻게 활용하는지 스냅숏의 덤프 파일로부터 상세하게 복원할 수 있다**
  (4장, p.214).[^zhou2024]
- 비유도 붙는다 — **SA의 작동 원리는 리눅스의 GDB나 윈도우의 Windbg와 비슷하다** (4장,
  p.214).[^zhou2024]
- 버전 조건: JDK 9 이상에서 공식 도구다 — **JHSDB는 공식적으로는 JDK 9에 와서야 제공되었지만
  훨씬 전부터 `sa-jdi.jar` 패키지 안에 HSDB(GUI 도구)와 CLHSDB(명령 줄 도구) 형태로 존재했고**,
  정식 편입 이후 **별도로 찾아 다운로드하지 않고도 무료로 사용할 수 있게 되었다** (4장,
  p.212).[^zhou2024]
- GUI와 명령 줄은 같은 것을 준다 — **JHSDB의 GUI가 제공하는 모든 작업은 명령 줄에서도 수행할 수
  있다**(콘솔에서 `help`) (4장, p.216).[^zhou2024]

## 실험: 변수 자체는 어디에 저장되는가

- 책이 던지는 질문은 이것이다 — **"`staticObj`, `instanceObj`, `localObj` 변수들 자체는(변수가
  가리키는 객체가 아닌) 어디에 저장될까?"** (4장, p.214).[^zhou2024] 실험 코드는 다음과 같다.

  ```java
  public class JHSDBTestCase {
      static class Test {
          static ObjectHolder staticObj = new ObjectHolder();
          ObjectHolder instanceObj = new ObjectHolder();

          void foo() {
              ObjectHolder localObj = new ObjectHolder();
              System.out.println("done");     // 중단점 설정
          }
      }

      private static class ObjectHolder {}

      public static void main(String[] args) {
          Test test = new JHSDBTestCase.Test();
          test.foo();
      }
  }
  ```

- 2·3장의 지식만으로 낼 수 있는 답이 먼저 제시된다 — **`staticObj`는 `Test`의 클래스 정보와 함께
  메서드 영역에 저장되고, `instanceObj`는 `Test`의 객체 인스턴스와 함께 자바 힙에 저장된다.
  마지막으로 `localObj`는 `foo()` 메서드의 스택 프레임의 지역 변수 테이블에 저장된다** (4장,
  p.215).[^zhou2024] 그 영역들의 정의는
  [런타임 데이터 영역과 메모리 오버플로](../concepts/jvm-runtime-data-areas.md)에 있다.
- 실험 조건은 셋이다 — **중단점을 걸어 프로그램을 일시 정지**시키고, **JHSDB는 압축 포인터를
  지원하지만 일부 버전에서는 결함이 많아서 64비트 시스템이라면 압축 포인터를 비활성화**하며,
  **메모리에서 객체를 찾는 속도를 높이려면 자바 힙 크기도 제한하는 게 좋다.** 책이 쓴 매개
  변수는 `-Xmx10m -XX:+UseSerialGC -XX:-UseCompressedOops`다 (4장, p.215).[^zhou2024]
- 붙이는 절차는 jps로 PID를 얻은 뒤 `jhsdb hsdb --pid <pid>`로 GUI 모드를 띄우는 것이다 (4장,
  p.215).[^zhou2024]

## 힙에서 객체 찾기

- **Tools → Heap Parameters**를 열면 **시리얼 컬렉터의 전형적인 세대별 메모리 레이아웃**이
  보이며, **신세대의 에덴, S1, S2와 구세대의 용량(바이트 단위) 및 가상 메모리 주소의 시작 주소와
  끝나는 범위를 확인할 수 있다** (4장, p.216).[^zhou2024]
  - 컬렉터를 지정하지 않았다면 다르게 보인다 — **JDK의 기본값이 G1이므로 `garbage-first heap
    [...] region size 1024K` 형태의 정보가 출력**된다 (4장, p.217). 리전 기반 레이아웃의 정체는
    [클래식 가비지 컬렉터](../concepts/hotspot-classic-collectors.md)에 있다.
- **`scanoops` 명령으로 자바 힙의 신세대에서 `ObjectHolder`의 인스턴스를 찾아보자. 에덴의 시작
  주소에서 생존자 공간의 끝 주소를 이용하면 되고, `ObjectHolder`는 패키지명을 포함한 완전한
  이름을 사용해야 한다** (4장, p.217).[^zhou2024]
  - 결과 — **기대한 대로 인스턴스 3개를 찾아 주소를 출력했고 모두 에덴의 주소 범위에 있다.
    이로써 일반적인 환경에서 새로운 객체는 에덴에 만들어진다는 규칙이 잘 지켜졌음을 확인했다**
    (4장, p.217). 그 규칙 자체는
    [세대 단위 컬렉션과 메모리 할당 전략](../concepts/generational-collection.md)에 있다.
- **Tools → Inspector**로 그 주소를 열면 **객체 헤더와 객체 메타데이터를 가리키는 포인터**가
  보인다. **객체 메타데이터에는 자바 클래스 이름, 상속 관계, 인터페이스 구현 관계, 필드 정보,
  메서드 정보, 런타임 상수 풀 포인터, 내부 가상 메서드 테이블(vtable), 인터페이스 메서드
  테이블(itable) 등의 정보가 담겨 있다** (4장, p.218).[^zhou2024] 객체 헤더의 구성은
  [객체 생성과 메모리 레이아웃](../concepts/object-creation-and-memory-layout.md)에 있다.

## 누가 그 객체를 가리키는가

- 역참조를 찾는 기능이 `revptrs`다. **원래 JHSDB의 Tools → Compute Reverse Ptrs 메뉴를 실행하면
  되지만** 저자의 환경에서는 **스윙 인터페이스에서 널 포인터 예외가 발생**해 명령 줄로 대신했다
  (4장, p.218).[^zhou2024]
- **첫 번째 객체를 참조하는 곳은 `java.lang.Class`의 인스턴스**였고, **인스펙터로 그 주소를 열어
  보면 실제로 `java.lang.Class` 타입의 객체 인스턴스이며 `staticObj`라는 이름의 인스턴스 필드를
  가지고 있음을 확인할 수 있다** (4장, p.218).[^zhou2024]
  - 명세와 구현이 갈리는 자리다 — **《자바 가상 머신 명세》의 개념 모델에 따르면 Class 관련
    정보는 모두 메서드 영역에 저장된다. 하지만 메서드 영역을 어떻게 구현해야 하는지는 정의하지
    않아서 가상 머신에 따라 고유한 방식을 선택할 수 있다** (4장, p.219).
  - **JDK 7 이후의 핫스팟 가상 머신은 정적 변수와 그에 매핑된 Class 객체를 함께 자바 힙에
    저장하기로 했다. 실험 결과에서도 분명하게 확인할 수 있다** (4장, p.219).[^zhou2024]
    - 버전 조건: JDK 7 이상. **JDK 7 이전, 즉 영구 세대 퇴출을 시작하기 전에는 정적 변수를 영구
      세대에 저장했고, JDK 7부터는 정적 변수와 문자열 상수를 영구 세대에 저장하지 않게 바뀌었다**
      (4장, p.219).
    - 그래서 앞서 지식만으로 낸 답 중 첫째("`staticObj`는 메서드 영역에 저장된다")는 **개념
      모델 수준에서는 맞지만 핫스팟 구현 수준에서는 자바 힙**을 가리킨다.
- **두 번째 객체를 `revptrs`로 찾으면 `JHSDBTestCase$Test` 타입의 객체 인스턴스**가 나오고,
  **자바 힙에 있는 그 객체의 `instanceObj` 필드가 두 번째 `ObjectHolder`를 가리킨다** —
  **예상과 완벽히 일치하는 결과**다 (4장, p.219).[^zhou2024]
- **세 번째 `ObjectHolder` 인스턴스를 같은 방식으로 찾으면 JHSDB가 `null`을 반환한다.**
  **`revptrs` 명령이 스택을 참조하는 포인터는 찾지 못하는 걸로 보인다** (4장,
  pp.219–220).[^zhou2024]
  - 그래서 눈으로 확인한다 — **Java Threads 창에서 `main` 스레드를 선택한 다음 Stack Memory
    버튼을 클릭**하면 스택 메모리가 보이고, **이 스레드에는 메서드 스택 프레임이 단 둘뿐이라
    특정 주소의 값이 정확히 세 번째 객체의 주소임을 눈으로 확인할 수 있다.** **JHSDB가 그 옆에
    생성해 둔 주석을 보면 신세대의 `JHSDBTestCase$ObjectHolder` 객체를 참조함을 알 수 있다**
    (4장, pp.220–221).
- 실험의 결론 — **테스트 코드의 객체 3개를 어디에서 참조하고 있는지 성공적으로 추적해 냈고,
  "변수들 자체는 어디에 저장될까?"라는 질문의 답도 확인할 수 있었다** (4장,
  p.221).[^zhou2024]
- 저자의 마무리 — **JHSDB는 매우 강력하고 유연하다. 이번 절에서는 아주 살짝 맛만 본 수준**이며,
  **실무 개발 프로젝트에서 이 도구를 활용하여 가상 머신 프로세스나 덤프된 메모리 스냅숏을
  디버깅하며 구체적인 경험을 쌓아 보기 바란다** (4장, p.221).[^zhou2024]
