하나의 질문: **자원을 지운다는 것을 API에서 어떻게 표현하고, 지운 뒤의 조회와 되살리기는
무엇이 책임지는가.**

## 두 가지 삭제

- 저자들이 먼저 범위를 긋는다 — **이 절의 삭제 논의는 REST 지향이다** (2장 §"Deletion",
  p.67).[^dynowski2025]
- 규정 (2장, p.67).[^dynowski2025]
  - **REST API에서 자원을 지우는 것은 두 방식으로 구현된다 — 소프트 삭제(soft-delete)이거나
    하드 삭제(hard-delete)다.**
  - **소프트 삭제는 자원을 보존하되 지워졌다고 표시하고, 하드 삭제는 자원을 체계에서 지운다.**

## 규제가 요구하는 소거와는 다르다

- 곁주에 경계가 하나 붙는다 — **소프트 삭제는 여러 데이터 보호 규제가 요구하는 데이터 소거
  요건을 온전히 충족하지 못한다.** 저자들이 드는 규제가 **유럽 연합의 일반 데이터 보호
  규정(GDPR)** 과 **캘리포니아 소비자 프라이버시법(CCPA)** 이다 (2장, p.67).[^dynowski2025]

## 소프트 삭제를 무엇으로 표시하는가

- **소프트 삭제는 자원에 어떤 종류의 라벨링을 요구한다.** 저자들이 드는 모양이 **`soft_delete`
  플래그와 전이 타임스탬프를 함께 두어 자원이 소프트 삭제되었는지와 언제 그랬는지를 가리키는
  것**이다 (2장, p.67).[^dynowski2025]
- 대안이 하나 제시되고 곧바로 대가가 붙는다 — **자원의 삭제 상태를 여러 상태로 서술할 수도
  있다**(`active`·`pending_deletion`·`soft_deleted`). **둘보다 많은 상태를 쓰는 문제는 자원의
  삭제 상태가 어떻게 진행되었는지를 추적하려면 전이 이력을 유지해야 한다는 것**이다 (2장,
  p.67).[^dynowski2025]

## 어떤 코드를 돌려주는가

- 소프트 삭제 쪽 (2장, p.67).[^dynowski2025]
  - **소프트 삭제를 수행할 때는 갱신된 상태의 자원 표현을 200(OK) 상태 코드와 함께 돌려준다.**
  - **이미 소프트 삭제된 자원에 대한 후속 소프트 삭제 요청은 412(Precondition Failed)를
    돌려줘야 한다.**
- 하드 삭제 쪽 (2장, p.67).[^dynowski2025]
  - **하드 삭제를 소프트 삭제와 함께 구현하려면 API 자원에 지우는(erase, wipe, prune) 동작을
    더해야 한다** — `HTTP DELETE /api/orders/123?action=erase`.
  - **하드 삭제를 수행할 때 응답은 지워진 자원과 함께 200(OK)을 돌려주거나, 내용 없이
    204(No Content)를 돌려줘야 한다.**
  - **이미 지워진 자원에 대한 후속 하드 삭제 요청은 404(Not Found)를 돌려줘야 한다.**
- 곁주에 한 줄이 붙는다 — **혼동을 피하려면 HTTP 메서드의 비표준 동작을 반드시 문서화하라**
  (2장, p.67).[^dynowski2025]

## 소프트 삭제를 뒤늦게 들이면 깨진다

- **버저닝된 API에서 소프트 삭제를 더하는 것은 깨는 변경일 수 있다** (2장,
  p.68).[^dynowski2025]
- 그래서 도입 전에 물어야 할 것이 둘이다 — **그것이 API가 돌려주는 데이터에 어떤 영향을
  미칠지**, 그리고 **사용자가 기대하는 것을 바꾸는지**다 (2장, p.68).[^dynowski2025]
- 판정 — **소프트 삭제가 기존 클라이언트를 예상 밖으로 행동하게 만들 수 있다면**(전에 보던
  데이터가 사라지는 것 같은 일) **그 소프트 삭제를 API의 새 판으로 내보내라** (2장,
  p.68).[^dynowski2025]

## 조회 쪽에 따라오는 것

- 삭제 방식이 조회의 의미를 바꾼다 — **소프트 삭제를 구현하는가 하드 삭제를 구현하는가에 따라
  API가 자원을 돌려주는 방식이 달라진다** (2장, p.68).[^dynowski2025]
  - **소프트 삭제된 뒤 그 자원을 조회하면 메서드는 하드 삭제일 때처럼 404(Not Found)를 내지
    말고 자원을 돌려줘야 한다.**
  - **여러 자원을 요청할 때 응답은 `soft_delete` 플래그가 거짓인 것만 돌려줘야 한다.**
  - **API 인터페이스는 클라이언트가 소프트 삭제된 자원을 볼 수 있게 하는 `include_deleted`
    플래그를 가져야 하고**, 그 플래그가 없으면 **API 응답이 소프트 삭제된 자원을 걸러 내
    클라이언트가 받지 않게 해야 한다.**

## 되살리기와 만료

- **API에는 소프트 삭제된 자원을 되살리는(undelete, restore) 동작도 필요하다.** 그 수단으로 드는
  것이 **자원에 맞춤 동작을 구현하는 것**이고, 모양이
  `https://example.com/api/v1/order/1?restore`다 (2장, p.68).[^dynowski2025]
- **이미 복원된 객체를 복원하는 경우 API는 HTTP 412(Precondition Failed) 상태 코드를 돌려줘야
  한다** (2장, p.68).[^dynowski2025]
- 마지막으로 정리 수단이 하나 붙는다 — **자원에 `expiration_date`를 더해 소프트 삭제된 자원을
  주기적으로 데이터베이스에서 제거할 수 있다** (2장, p.68).[^dynowski2025]
