하나의 질문: **이력 데이터의 재처리와 방금 도착한 이벤트의 처리를 같은 시스템에서 하려면
무엇이 필요한가.**

## 두 제안

- **배치와 스트림 처리를 통합하려는 초기 제안이 람다 아키텍처(lambda architecture)였는데,
  여러 문제가 있었고 쓰이지 않게 됐다** (13장, p.546).[^kleppmann2026]
- **더 최근의 시스템은 배치 계산(이력 데이터 재처리)과 스트림 계산(도착하는 대로 이벤트를
  처리하는 것)이 같은 시스템에서 구현되게 하며, 이 접근은 때때로 카파 아키텍처(kappa
  architecture)로 알려져 있다** (13장, p.546).[^kleppmann2026]

## 통합이 요구하는 세 기능

- **배치와 스트림 처리를 한 시스템에서 통합하려면 다음 기능이 필요하다** (13장,
  p.546):[^kleppmann2026]
  - **최근 이벤트의 스트림을 다루는 같은 처리 엔진을 통해 이력 이벤트를 재생(replay)할 수 있는
    능력. 예컨대 로그 기반 메시지 브로커는 메시지를 재생할 수 있고, 어떤 스트림 프로세서는
    분산 파일시스템이나 객체 저장소에서 입력을 읽을 수 있다.**
  - **스트림 프로세서를 위한 정확히 한 번 의미론 — 즉 결함이 실제로 일어났더라도 출력이 결함이
    없었을 때와 같도록 보장하는 것. 배치 처리와 마찬가지로 이는 실패한 태스크의 부분 출력을
    버리는 것을 요구한다.**
  - **처리 시간이 아니라 이벤트 시간으로 윈도잉하는 도구. 이력 이벤트를 재처리할 때 처리 시간은
    무의미하기 때문이다. 예컨대 Apache Beam이 그런 계산을 표현하는 API를 제공하며, 이는 Apache
    Flink나 Google Cloud Dataflow로 실행될 수 있다.**

## 람다의 세 계층

데이터 엔지니어링 쪽 소스는 같은 두 아키텍처를 **왜 그것이 나왔는지**의 역사와 함께 적는다.

- 배경 — **"옛날"(2010년대 초·중반)에 카프카가 고도로 확장 가능한 메시지 큐로 등장하고 스톰·
  삼자 같은 스트리밍/실시간 분석 프레임워크가 나오면서 스트리밍 데이터로 작업하는 것의 인기가
  폭발했다. 이 기술들은 회사가 대량의 데이터에 대해 집계·사용자 랭킹·제품 추천 같은 새로운 종류의
  분석과 모델링을 수행하게 해 줬다. 데이터 엔지니어는 배치와 스트리밍 데이터를 하나의 아키텍처로
  조정할 방법을 알아내야 했다. 람다 아키텍처(Lambda architecture)가 이 문제에 대한 초기의 인기
  있는 응답 중 하나였다** (3장, p.104).[^reis2022]
- 구조 — **람다 아키텍처에서는 서로 독립적으로 동작하는 시스템들 — 배치·스트리밍·서빙 — 을 갖는다.
  원천 시스템은 이상적으로 불변이고 추가 전용이며, 처리를 위해 데이터를 스트림과 배치 두 목적지로
  보낸다. 인스트림 처리는 통상 NoSQL 데이터베이스인 "속도(speed)" 계층에서 가능한 한 낮은 지연으로
  데이터를 서빙하려 한다. 배치 계층에서는 데이터 웨어하우스 같은 시스템에서 데이터가 처리·변환돼
  미리 계산되고 집계된 데이터 뷰를 만든다. 서빙 계층은 두 계층의 질의 결과를 집계해 결합된 뷰를
  제공한다** (3장, p.104).[^reis2022]
- 판정 — **람다 아키텍처에는 그 몫의 난제와 비판이 있다. 서로 다른 코드베이스를 가진 여러 시스템을
  관리하는 것은 들리는 만큼 어려워, 조정하기 극히 어려운 코드와 데이터를 가진 오류 나기 쉬운
  시스템을 만든다** (3장, p.105).[^reis2022] 위 [두 제안](#두-제안)이 "여러 문제가 있었고 쓰이지
  않게 됐다"고 요약한 그 문제들이다.
- 그럼에도 언급하는 이유 — **람다 아키텍처가 여전히 주목을 받고 데이터 아키텍처 검색 엔진 결과에서
  인기가 있기 때문에 언급한다. 분석을 위해 스트리밍과 배치 데이터를 결합하려 한다면 람다는 저자들의
  첫 권고가 아니다. 기술과 실무는 앞으로 나아갔다** (3장, p.105).[^reis2022]

## 카파 — 스트림을 유일한 백본으로

- **람다 아키텍처의 결점에 대한 응답으로 제이 크렙스가 카파 아키텍처(Kappa architecture)라는
  대안을 제안했다. 중심 논지는 이것이다 — 반입·저장·서빙 전부에 대해 스트림 처리 플랫폼을 백본으로
  쓰면 안 되는가? 이는 진정한 이벤트 기반 아키텍처를 촉진한다. 라이브 이벤트 스트림을 직접 읽고
  배치 처리를 위해 큰 데이터 덩어리를 재생함으로써 실시간과 배치 처리가 같은 데이터에 매끄럽게
  적용될 수 있다** (3장, p.105).[^reis2022] 그 재생 능력의 근거는 위
  [통합이 요구하는 세 기능](#통합이-요구하는-세-기능)의 첫째와 같다.
- 채택되지 않은 두 이유 — **원래의 카파 아키텍처 글이 2014년에 나왔지만 널리 채택된 것을 보지
  못했다. 여기에는 몇 가지 이유가 있을 수 있다. 첫째, 스트리밍 자체가 많은 회사에게 여전히
  다소 미스터리다 — 말하기는 쉽지만 실행하기는 예상보다 어렵다. 둘째, 카파 아키텍처는 실무에서
  복잡하고 비싼 것으로 드러난다. 어떤 스트리밍 시스템은 방대한 데이터 양으로 확장할 수 있지만
  복잡하고 비싸며, 배치 저장과 처리는 거대한 이력 데이터셋에 대해 훨씬 효율적이고 비용
  효과적으로 남아 있다** (3장, p.105).[^reis2022]

## 데이터플로 모델이 이어받은 것

- 두 제안의 공통 배경 — **람다와 카파 둘 다 2010년대 하둡 생태계가 애초에 잘 맞지 않았을 복잡한
  도구들을 덕트 테이프로 붙이려 함으로써 생긴 한계를 다루려 했다. 배치와 스트리밍 데이터를
  통합한다는 중심 난제는 남았고, 람다와 카파 둘 다 이 추구에서 계속된 진전에 영감과 토대를
  제공했다** (3장, p.105).[^reis2022]
- 남은 문제 — **배치와 스트림 처리를 관리하는 중심 문제 중 하나는 여러 코드 경로를 통합하는
  것이다. 카파 아키텍처는 통합된 큐잉·저장 계층에 기대지만, 실시간 통계를 모으거나 배치 집계
  잡을 돌리려면 여전히 서로 다른 도구를 마주해야 한다. 오늘날 엔지니어는 이를 여러 방식으로 풀려
  하며, 구글은 데이터플로 모델(Dataflow model)과 그것을 구현하는 Apache Beam 프레임워크를 개발해
  자기 자취를 남겼다** (3장, p.106).[^reis2022]
- 그 핵심 발상 — **데이터플로 모델의 핵심 발상은 모든 데이터를 이벤트로 보고, 집계는 다양한 종류의
  윈도우에 대해 수행되는 것으로 보는 것이다. 진행 중인 실시간 이벤트 스트림은 무경계 데이터
  (unbounded data)다. 데이터 배치는 그냥 경계가 있는 이벤트 스트림이고, 그 경계가 자연스러운 윈도우를
  제공한다. 엔지니어는 실시간 집계를 위해 슬라이딩·텀블링 같은 다양한 윈도우 중에서 고를 수 있다.
  실시간과 배치 처리가 거의 동일한 코드를 써서 같은 시스템에서 일어난다** (3장, p.106).[^reis2022]
  그 윈도우들은 [스트림 처리의 시간 윈도우](../concepts/stream-processing-time-windows.md)에 있다.
- **"스트리밍의 특수한 경우로서의 배치"라는 철학이 이제 더 널리 퍼졌다. 플링크·스파크 같은 다양한
  프레임워크가 비슷한 접근을 채택했다** (3장, p.106).[^reis2022]

## 2025년 소스가 이 두 아키텍처를 다시 채점한다

위 [카파 — 스트림을 유일한 백본으로](#카파--스트림을-유일한-백본으로)가 2022년 소스의 판정으로
**널리 채택된 것을 보지 못했다**고 적어 두었다. **2025년 소스가 같은 물음에 다르게 답한다.**
[bellemare2025](../sources/bellemare2025.md) 2장이 두 아키텍처를 한 절씩 다루면서 **카파를
권하고 람다를 역사적 맥락으로만 싣는다.**

- **카파의 규정과 귀속** — **카파 아키텍처는 2014년 제이 크렙스(Jay Kreps)가 처음 제시했고**
  그는 아파치 카프카의 공동 창시자이자 컨플루언트의 공동 창업자다. **카파는 현재 데이터와 이력
  데이터 양쪽의 유일한 기록으로 이벤트 스트림에 기댄다.** 소비자는 스트림의 처음부터 소비해
  창설 이래 일어난 모든 것의 전체 그림을 얻고, 결국 스트림의 머리와 최신 이벤트에 도달한다
  (2장 §"The Kappa Architecture", p.39).[^bellemare2025] 귀속과 연도가 위 2022년 소스의 서술과
  같다.
- **채택 판정이 갈리는 자리가 여기다** — 그쪽은 **카파 아키텍처가 현대 이벤트 브로커와 클라우드
  컴퓨팅 혁명이 가져온 값싼 저장소의 조합으로 비로소 실현되었다**고 적는다. **필요한 만큼 데이터를
  스트림에 저장하는 것이 저렴하고 쉬우며, 몇 시간이나 며칠 뒤 레코드를 지우는 강제 TTL을 적용하던
  브로커 기술에 더는 묶이지 않는다** (2장, p.40).[^bellemare2025]
  - **두 소스가 겨루는 것이 아니라 시점이 다르다.** 2022년 소스가 든 미채택의 두 이유는 **스트리밍
    자체의 어려움**과 **복잡성·비용**이었고, 2025년 소스가 드는 실현의 근거는 **저장 비용의 하락과
    브로커의 무기한 보존**이다. **둘째 이유에 대한 답이고 첫째 이유에는 답하지 않는다.** 이 대비는
    이 KB가 두 소스를 맞대어 세운 것이다.
  - 버전 조건: 2025년 저술 시점의 시장 판정이다. **2022년 소스의 미채택 관찰과 같은 축에서
    읽어야 한다** — 어느 쪽도 채택률의 실측을 대지 않는다.
- **카파의 대가도 그쪽이 적는다** — **각 서비스가 자기 상태를 스스로 지어야 하고, 아주 큰
  데이터셋이면 스트림에서 구체화하는 데 시간이 걸릴 수 있다.** 파티션 수가 적고 병렬화가 충분치
  않으면 **여러 시간이나 며칠**이 걸릴 수 있다. 저자는 이것을 **하이드레이션 시간(hydration
  time)** 이라 부르고 **서비스 생애 주기에 계획해 두어야 한다**고 적는다 (2장,
  p.40).[^bellemare2025]
  - **완화책이 스냅샷과 백업이다** — 구체화되고 계산된 상태의 스냅샷이나 백업을 유지해 두면
    애플리케이션을 적재할 때 백업 데이터에서 적재해 중단 지점부터 처리를 재개한다. **이는
    애플리케이션 자신의 책임이되** 스냅샷과 백업은 **Apache Kafka Streams·Apache Flink·Apache
    Spark Structured Streaming** 같은 주요 스트림 처리 기술에 딸려 온다 (2장, p.40).
    [^bellemare2025]
    - 버전 조건: 2025년 저술 시점의 제품 기능이다.
- **카파가 서비스에 주는 보장 하나가 이 절의 결론이다** — **카파 아키텍처는 탈결합된 이벤트 기반
  마이크로서비스를 짓는 데 열쇠**인데, 서비스에 **주어진 데이터 집합에 대해 이벤트 스트림이 단일
  진실 원천 노릇을 할 수 있다**는 강력한 보장 하나를 주기 때문이다. **이차·삼차 저장소로 갈 필요가
  없다** (2장, p.40).[^bellemare2025] 이 주장을 이 KB의 기록/파생 구분과 맞댄 결과는
  [기록 시스템과 파생 데이터](system-of-record-and-derived-data.md)에 있다.
- **코드로 본 카파.** 저자는 카파가 코드로 어떻게 보이는지를 스트림 처리 프레임워크 둘로 보인다.
  아래는 카프카 스트림즈 판이고, **두 KTable이 각각 소스 토픽을 구체화한 테이블이며 그 둘을
  윈도우 없는 내부 조인으로 이어 비정규화되고 풍부해진 상품 데이터의 KTable을 만든다** (2장
  §"The Kappa Architecture", pp.40–41, Example 2-1):[^bellemare2025]

  ```java
  StreamsBuilder builder = new StreamsBuilder();

  // Materializes the tables from the source Kafka topics
  KTable products = builder.table("products");
  KTable productReviews = builder.table("product_reviews");

  // Join events on the primary key, apply business logic as needed
  KTable productsWithReviews = products.join(productReviews, businessLogic(..), ...);
  builder.build();
  ```

  - 저자가 같은 일을 **Flink SQL**로도 보인다(Example 2-2, p.41) — 두 `CREATE TABLE`이
    `'connector' = 'kafka'`로 토픽을 잡고 `INNER JOIN`으로 잇는 형태다. **이 페이지에는 대표
    하나만 두었고** 그쪽 목록은 옮기지 않았다.
  - 버전 조건: 카프카 스트림즈의 `StreamsBuilder`·`KTable` API와 Flink SQL의 커넥터 문법은
    2025년 저술 시점 기준이다.

## 람다가 실무에서 어려운 이유 다섯

같은 소스가 **람다를 쓰지 말라고 명시한다** — **람다 아키텍처는 이벤트 스트림에 이벤트를 무기한
저장할 수 없다는 낡은 관념에 기대고 있다.** 스트림에 강제 TTL을 적용하던 낡은 기술과는 정합적이나
**많은 사람의 머릿속에 고집스럽게 남아 있어서 역사적 맥락을 위해 이 책에 싣되 사용을 권하는 것은
아니다** (2장 §"The Lambda Architecture", p.42).[^bellemare2025]

- **그쪽이 가르는 람다의 두 판본**이 위 [람다의 세 계층](#람다의-세-계층)과 축이 다르다 (2장,
  p.42):[^bellemare2025]
  - **첫째 판본** — 이력 저장소와 스트림을 **독립으로** 짓는다. 생산자가 이벤트 스트림과 이력
    데이터 저장소 양쪽에 새 데이터를 쓴다.
  - **둘째 판본** — 이력 저장소를 **스트림에서** 채운다. 생산자가 이벤트 스트림에 쓰고, 이차
    프로세스가 그것을 데이터 저장소로 병합하며, 소비자는 이력 데이터를 먼저 읽고 스트림으로
    넘어간다.
- **첫째 판본의 치명적 결함이 원자성이다** — **데이터가 원자적으로 쓰이지 않는다.** 여러 독립
  체계에 걸친 고성능 분산 트랜잭션을 얻기는 매우 어렵고, 실제로는 생산자가 한쪽을 먼저 갱신하고
  다른 쪽을 갱신하므로 **중간의 간헐적 실패가 이력 저장소에는 쓰였는데 스트림에는 안 쓰인(혹은 그
  반대) 상태**를 남긴다 (2장, p.43).[^bellemare2025]
  - **그 결과가 발산(diverge)이다** — 스트림에서 만든 결과와 이력 데이터에서 만든 결과가 달라진다.
    **스트림만 읽는 옛 소비자와 이력 데이터로 부트스트랩하는 새 소비자가 다른 결과를 계산할 수
    있고**, 원인을 추적하기가 매우 어렵다 — **이벤트 스트림 데이터가 시간 제한되어 있어 발산의
    증거가 며칠 뒤 지워지기 때문**이다 (2장, p.43).[^bellemare2025]
- **둘째 판본에 대한 저자의 채점이 날카롭다** — **눈을 조금 가늘게 뜨고 보면 카파와 아주 닮았다.
  다만 서비스가 상태 저장소를 마이크로서비스 *바깥*에 짓는다는 점이 다르다.** 유일한 복잡함은
  **이벤트 브로커와 이력 데이터 저장소 사이의 어색한 분리**이고, 그것은 **이제는 유효하지 않은
  관념(이벤트 브로커가 이벤트를 무기한 저장할 수 없다)의 산물**이다 (2장, p.43).[^bellemare2025]
- **실무에서 람다를 잘 하기 어려운 이유로 저자가 드는 것이 다섯이다** (2장,
  p.44):[^bellemare2025]

  | 장애물 | 그쪽의 서술 |
  |---|---|
  | **생산자가 여분의 코드를 유지해야 한다** | 스트림에 쓰는 코드와 이력 저장소에 쓰는 코드 |
  | **소비자가 두 코드 경로를 유지해야 한다** | 하나는 이력 저장소를, 하나는 스트림을 읽는다. **데이터를 빠뜨리거나 실수로 중복하지 않으면서 매끄럽게 전환하는 코드**를 써야 하고, 분산 체계와 간헐적 실패 아래서 실무상 꽤 까다롭다 |
  | **스트림 데이터가 이력 데이터와 같은 결과로 수렴하지 않을 수 있다** | 생산자가 둘 사이의 발산을 막아야 하는데 **양쪽에 대한 원자적 갱신 없이는 어렵다** |
  | **스트림과 이력 데이터 모델이 함께 진화해야 한다** | 데이터 형식을 갱신하려면 **이력 저장소와 스트림 두 자리**에서 코드를 고쳐야 한다 |
  | **여러 람다 데이터셋을 병합하는 것은 거의 불가능하다** | 카파 데이터셋은 병합이 쉽고 **오프라인 저장소와 이벤트 스트림 사이를 건너갈 일이 없다.** 람다에서는 오프라인 이력 데이터셋끼리, 그리고 그것과 이벤트 스트림을 화해시켜야 한다. **스트림이 둘이면 화해가 하나(스트림 대 스트림)인데 람다 모드에서는 넷**이다 — 스트림과 오프라인 저장소의 조합마다 하나씩 |

  표의 다섯 항목과 각 서술은 원문 정의 목록을 그대로 옮긴 것이고 **표 형식은 이 KB가 만든 것**이다.
  마지막 칸의 "카파 모드에서 넷"은 **원문 그대로**이고, 저자가 그 자리에서 람다를 가리키는 문맥과
  낱말이 어긋난다 — #hypothesis 조판상의 실수로 보인다.
- **저자의 결론** — **람다 아키텍처는 어떤 합리적 규모에서도 관리하기에 그저 너무 어렵다.**
  데이터 접근의 부담을 전부 소비자에게 지우고, 데이터 원천이 하나를 넘어서면 복잡성이 크게 는다.
  **인지적으로도 코딩 면에서도 이력 데이터를 제공하는 단일 스트림 원천을 갖는 카파에 기대는 편이
  훨씬 쉽다** (2장, p.44).[^bellemare2025]
