하나의 질문: **모든 질의를 같은 모델에 보내야 하는가.**

## 왜 라우터가 생기는가

- **애플리케이션이 자라 더 많은 모델을 수반하게 되면, 여러 모델을 서빙하는 복잡도와 비용을 관리하도록
  돕기 위해 라우터(router)와 게이트웨이(gateway)가 등장한다** (10장, p.456).[^huyen2025]

## 두 가지 이득

- **모든 질의에 하나의 모델을 쓰는 대신 서로 다른 종류의 질의에 서로 다른 해법을 둘 수 있다. 이 접근에는
  여러 이점이 있다. 첫째, 그것은 특화된 모델을 쓸 수 있게 해 주는데, 특화 모델은 특정 질의에서 범용
  모델보다 잠재적으로 더 잘할 수 있다. 예컨대 기술 문제 해결에 특화된 모델 하나와 청구에 특화된 모델
  하나를 둘 수 있다. 둘째, 이는 비용을 아끼는 데 도움이 될 수 있다. 모든 질의에 하나의 비싼 모델을
  쓰는 대신 더 단순한 질의를 더 싼 모델로 라우팅할 수 있다** (10장, p.456).[^huyen2025]

## 의도 분류기

- 라우터의 본체 (10장, p.456):[^huyen2025]

  > A router typically consists of *an intent classifier* that predicts what the user is trying to
  > do.

  **예측된 의도에 근거해 질의가 적절한 해법으로 라우팅된다** (10장, p.456).[^huyen2025] 고객 지원
  챗봇에 관련된 서로 다른 의도의 예다 (10장, p.456):[^huyen2025]
  - **사용자가 비밀번호를 재설정하려 한다면 비밀번호 복구에 대한 FAQ 페이지로 보낸다.**
  - **요청이 청구 실수를 바로잡는 것이라면 사람 운영자에게 보낸다.**
  - **요청이 기술 문제 해결에 관한 것이라면 문제 해결에 특화된 챗봇으로 보낸다.**

## 범위 밖 대화를 막는다

- **의도 분류기는 당신의 시스템이 범위 밖 대화에 끌려 들어가는 것을 막을 수 있다. 질의가 부적절하다고
  판정되면 챗봇은 API 호출을 낭비하지 않고 준비된 응답 하나를 써서 정중하게 답하기를 거절할 수 있다.
  예컨대 사용자가 다가올 선거에서 누구에게 투표하겠느냐고 물으면, 챗봇은 이렇게 응답할 수 있다: "챗봇으로서
  저는 투표할 능력이 없습니다. 저희 제품에 대해 질문이 있으시면 기꺼이 돕겠습니다."** (10장,
  p.457).[^huyen2025]

## 애매한 질의를 되묻는다

- **의도 분류기는 시스템이 애매한 질의를 탐지해 명확히 해 달라고 요청하는 데도 도움이 될 수 있다. 예컨대
  "Freezing"이라는 질의에 대해 시스템은 "계좌를 동결하고 싶으신가요, 아니면 날씨 이야기를 하시는
  건가요?"라고 묻거나 그냥 "죄송합니다. 더 설명해 주시겠어요?"라고 물을 수 있다** (10장,
  p.457).[^huyen2025]

## 다음 행동 예측기

- **다른 라우터는 모델이 다음에 무엇을 할지 정하는 것을 도울 수 있다. 예컨대 행동이 여러 개인 에이전트라면
  라우터는 다음 행동 예측기(next-action predictor)의 형태를 취할 수 있다: 모델이 다음에 코드 인터프리터를
  써야 하는가 검색 API를 써야 하는가? 메모리 시스템을 가진 모델이라면 라우터는 모델이 메모리 계층의 어느
  부분에서 정보를 끌어와야 할지 예측할 수 있다** (10장, p.457).[^huyen2025]
- 저자가 든 예 — **사용자가 멜버른을 언급하는 문서를 현재 대화에 첨부했다고 상상하라. 나중에 사용자가
  묻는다: "멜버른에서 가장 귀여운 동물이 뭐야?" 모델은 이 질의에 대해 첨부된 문서의 정보에 기댈지
  인터넷을 검색할지 정해야 한다** (10장, p.457).[^huyen2025]

## 무엇으로 만드는가

- **의도 분류기와 다음 행동 예측기는 파운데이션 모델 위에 구현될 수 있다. 많은 팀이 GPT-2·BERT·Llama 7B
  같은 더 작은 언어 모델을 의도 분류기로 적응시킨다. 많은 팀은 더 작은 분류기를 밑바닥부터 훈련하는 쪽을
  택한다. 라우터는 빠르고 싸야 하며, 그래야 상당한 추가 지연과 비용을 발생시키지 않고 여러 개를 쓸 수
  있다** (10장, p.457).[^huyen2025]

## 컨텍스트 한계가 다를 때

- **서로 다른 컨텍스트 한계를 가진 모델로 질의를 라우팅할 때는 질의의 맥락이 그에 맞게 조정되어야 할 수
  있다. 4K 컨텍스트 한계를 가진 모델로 보내기로 되어 있는 1,000토큰 질의를 생각해 보라. 그다음 시스템이
  8,000토큰 맥락을 가져오는 웹 검색 같은 행동을 취한다. 질의의 맥락을 잘라 원래 의도한 모델에 맞추거나,
  질의를 더 큰 컨텍스트 한계를 가진 모델로 라우팅할 수 있다** (10장, p.457).[^huyen2025]

## 라우팅은 검색 앞에 온다

- 어디 그리는가 — **라우팅은 대개 모델로 이뤄지므로 저자는 라우팅을 Figure 10-5의 모델 API 상자 안에
  두었다. 스코어러처럼 라우터도 통상 생성에 쓰이는 모델보다 작다** (10장, p.457).[^huyen2025] 도판은
  모델 API 상자 안에 Routing·Generation·Scoring 셋을 쌓는다 — **라우팅은 시스템이 질의마다 최적의
  해법을 쓰도록 돕는다** (10장, p.458, Figure 10-5 설명).[^huyen2025]
- 그림이 감추는 순서 — **라우터를 다른 모델과 함께 묶는 것은 모델을 관리하기 쉽게 만든다. 그러나
  라우팅이 흔히 검색 *앞에* 일어난다는 점을 유념하는 것이 중요하다. 예컨대 검색 전에 라우터는 질의가
  범위 안인지, 그렇다면 검색이 필요한지 판정하는 것을 도울 수 있다. 라우팅은 검색 뒤에도 일어날 수
  있는데, 질의를 사람 운영자에게 보내야 할지 정하는 것이 그 예다. 그러나 라우팅 - 검색 - 생성 - 채점이
  훨씬 더 흔한 AI 애플리케이션 패턴이다** (10장, p.457).[^huyen2025]
