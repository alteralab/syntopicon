# Data Vault 적재 패턴

**목차**: [공통 원칙](#공통-원칙) · [허브 적재](#허브-적재) · [링크 적재](#링크-적재) · [새틀라이트 적재](#새틀라이트-적재) · [삭제 처리](#삭제-처리) · [참조 테이블 적재](#참조-테이블-적재)

Raw Data Vault의 각 엔티티 타입에는 표준 적재 템플릿이 있다. 모든 템플릿의
공통 목표는 [스테이징 영역](staging-area.md)의 raw 데이터를 **변형 없이**
타깃으로 옮기는 것 — 존재 확인과 중복 방지만 하고, 업무 규칙은 적용하지 않는다.

## 공통 원칙

- Raw Data Vault 적재는 INSERT INTO … SELECT FROM 수준의 단순한 문장으로
  충분하다. 소프트 업무 규칙은 금지, 데이터 타입 정렬 같은 하드 룰만 허용된다.
  재계산이 필요하면 Business Vault나 정보 마트 적재로 미룬다
  (§12.1, p.473; §12.1.8.1, p.546).[^linstedt2016]
- 성능 규칙 세 가지: 프로세스 복잡도 감소 → 다루는 데이터량 감소 → 병렬성
  증가. **병렬화는 마지막 수단**이다 — 분할·병렬화는 유지 비용을 늘리므로,
  복잡도 감소부터 손댄다. 병렬화하려면 적재 중 Raw Data Vault의 참조 무결성을
  꺼야 한다 (12장 서두, pp.470–471).[^linstedt2016]
- 한 번의 실행은 **한 load date(한 배치)만** 적재한다. 스테이징에 배치가 여러 개
  쌓였으면 오래된 것부터 순서대로 — 델타(변화 감지)가 올바르게 적재되는 조건이다
  (§12.1.1, p.476; §12.1.2, p.491).[^linstedt2016]
- 모든 원천이 준비될 때까지 밤에 기다렸다 한 번에 돌리지 말고, 원천 시스템이
  준비되는 대로 스테이징→Data Vault→(의존이 충족된) 마트까지 시차를 두고
  흘려보낸다(staggered). 적재 피크가 분산되고 하루 다회 적재가 가능해진다
  (12장 서두, pp.471–472).[^linstedt2016]

## 허브 적재

- 템플릿: 스테이징에서 업무 키의 **distinct 목록** 추출 → 타깃 허브에 존재
  확인 → 없는 키만 insert. 이미 있으면 흐름에서 버린다 (§12.1.1, pp.473–475).[^linstedt2016]
- [허브](../concepts/data-vault-hub.md)는 insert 전용이다. 원천에서 키가
  삭제돼도 허브에는 남는다 — 삭제·갱신을 하지 않는다 (§12.1.1, pp.473, 475).[^linstedt2016]
- 존재 확인(lookup)은 해시 키가 아니라 **업무 키**로 한다. 해시 충돌을 기본 키
  위반으로 드러내기 위해서다 — 상세는 [해시 규율](hashing-in-data-vault.md).
  해시 키는 스테이징에서 이미 계산됐으므로 적재 과정에서 다시 해시하지 않는다
  (§12.1.1, pp.474–476).[^linstedt2016]
- 같은 업무 키가 여러 원천 테이블에서 오면 UNION으로 합치거나 템플릿을 원천마다
  반복 실행한다(후자가 메타데이터 주도 자동화에 유리). 레코드 소스는 메타데이터에
  정의된 **최우선순위(마스터) 원천**이 키를 먼저 적재해 결정되게 한다
  (§12.1.1, p.474).[^linstedt2016]
- 여러 프로세스가 같은 허브에 병렬 insert하면 잠금 전략이 필요하다: 테이블
  잠금은 효율적이지만 사실상 순차 실행(또는 데드락 자동 재시작)을 요구하고, 행
  잠금 + 마이크로배치 커밋은 완전 병렬을 허용한다 (§12.1.1, p.478).[^linstedt2016]

### NULL 업무 키와 고스트 레코드

- 원천이 업무 키 자리에 NULL을 주는 경우는 두 가지로 구분해 적재한다: 필수
  키가 누락된 **오류**(예: 인공 키 −1)와, 선택적 키가 제공되지 않은 **정상**
  (예: 인공 키 −2). 허브에 이 두 고스트 레코드(ghost record)를 미리 두고, 링크
  적재 시 NULL 참조를 해당 인공 키로 치환한다 (§12.1.2, pp.491–492).[^linstedt2016]
- 이렇게 하면 오류 데이터도 Raw Data Vault에 통합돼 분석 가능해지고, 정제는
  나중에 정보 마트 적재의 업무 로직이 맡는다 (§12.1.2, p.492).[^linstedt2016]

## 링크 적재

- 템플릿은 허브와 같은 골격이다: 관계의 distinct 목록 추출 → 존재 확인 → 없는
  관계만 insert. 차이는 두 가지 — 추출 대상이 업무 키가 아니라 **참조 허브들의
  해시 키 + 관계 자체의 해시 키**이고, 존재 확인도 해시 키로 한다([링크](../concepts/data-vault-link.md)에는
  업무 키가 저장되지 않기 때문) (§12.1.2, p.489).[^linstedt2016]
- 링크 적재는 허브 테이블에 대한 lookup이 전혀 없다 — 허브 적재와 **완전히
  독립**이어서 순서 의존이 사라진다. 해시 키가 스테이징에서 계산돼 있는 것이
  전제다 (§12.1.2, p.489).[^linstedt2016]
- 입도(grain)가 다른 관계를 한 링크 테이블에 섞으면 NULL 허브 참조가 생긴다
  — "링크 과적(link overloading)"이라 부르며 피해야 한다. 입도별로 링크를
  분리하고 각 링크에 새틀라이트를 단다 (§12.1.2, p.490).[^linstedt2016]
- **무이력 링크**(no-history link, transactional link): 트랜잭션·센서 이벤트당
  한 행이므로 distinct 관계 목록이 아니다. 존재 확인은 옵션이 되는데, 남겨두면
  적재 중단 후 재시작 시 중복 없이 이어서 적재할 수 있다(복구 가능성 확보)
  (§12.1.3, p.501).[^linstedt2016]

## 새틀라이트 적재

- 템플릿: 스테이징에서 변경 후보의 distinct 목록 추출(완전 중복은 여기서 걸러짐;
  업무적으로 의미 있는 중복이라면 multi-active 새틀라이트를 검토) → 부모 해시
  키로 타깃 [새틀라이트](../concepts/data-vault-satellite.md)의 **최신 활성
  레코드** 조회 → 비교 → 달라진 레코드만 insert. 새틀라이트는 델타만 담는다 —
  변화 없는 레코드는 버린다 (§12.1.4, pp.509–510).[^linstedt2016]
- 비교는 전 열 비교가 기본이고, hash diff가 있으면 열 하나 비교로 줄어든다
  (NULL 처리도 hash diff 계산에 이미 반영돼 있어 사라진다). 일부 열만 비교하는
  변형은 변화 누락을 낳으므로 드문 경우에만 쓴다. 대소문자 구분 여부는 원천
  특성에 따라 정한다 (§12.1.4, pp.510–511).[^linstedt2016]

### 종료일 부여

- 적재 직후 새틀라이트에는 부모당 활성 레코드(종료일이 NULL 또는 9999-12-31)가
  여러 개 남을 수 있다. 이는 비일관 상태이므로 배치 적재 후 **별도의 종료일
  부여(end-dating) 프로세스**를 돌린다 — 적재와 분리하는 것이 단순성과 성능의
  요건이다 (§12.1.5, pp.534, 537).[^linstedt2016]
- 규칙: 부모 해시 키별로 load date 내림차순 정렬 → 최신 레코드만 활성으로 남기고
  → 나머지 각 레코드의 종료일에 **다음(더 새로운) 레코드의 load date를 이월
  (carry-over)** 한다 (§12.1.5, pp.535–536).[^linstedt2016]
- 갱신 문장은 부모 해시 키 단위로 실행해야 데이터량에 선형으로 확장된다. 또한
  프로세스가 그룹 전체를 다루므로, 이전 적재가 중단돼 남긴 비일관 상태도 함께
  정리된다 — 재시작 가능성(restartability)의 일부다 (§12.1.5, p.537).[^linstedt2016]
- 참조 테이블의 새틀라이트에도 같은 프로세스가 필요하다 (§12.2.2.1, p.558).[^linstedt2016]

### 신규/변경 분리와 무이력 새틀라이트

- 열 비교는 타깃에 이미 있는 부모 키에만 의미가 있다. 스테이징 look-ahead로
  **신규 키와 변경 키를 분리**하면, 신규는 비교 없이 직행하는 단순 템플릿으로
  적재된다. 신규가 변경보다 많은 원천에서 특히 유효하다 (§12.1.6, pp.537–539).[^linstedt2016]
- 두 프로세스는 서로 겹치지 않는 기본 키 집합을 다루므로 **병렬 실행**할 수 있다
  (§12.1.6, p.539).[^linstedt2016]
- 무이력 새틀라이트는 변화 추적이 없으므로 신규 전용 템플릿을 그대로 쓴다.
  재시작 안전성은 부모 해시 키 존재 확인으로 확보한다 (§12.1.7, pp.539, 544).[^linstedt2016]

## 삭제 처리

- 허브·링크에서 레코드를 **삭제하지도, 종료일을 달지도 않는다**. 새틀라이트가
  키·관계를 참조하므로 삭제는 통합을 깨고, 허브·링크에 종료일을 달면 관계가
  재개될 때(퇴사 후 재입사 등) 중복 키로 모델이 깨진다 (§12.1.8, p.544).[^linstedt2016]
- 대신 **유효성 새틀라이트**(effectivity satellite)에 존재·관계의 시작일·종료일을
  기록한다. 허브는 "존재한 적 있는 모든 키", 링크는 "존재한 적 있는 모든 관계"만
  답하고, 유효 기간은 새틀라이트가 답한다. 물리 삭제는 법적·프라이버시 요건이
  있을 때만 수행한다 (§12.1.8, p.544).[^linstedt2016]
- 원천 피드에서 키가 사라졌다고 삭제된 것은 아니다(범위 밖·추출 실패·델타
  필터·ETL 오류). CDC나 감사 추적이 있으면 그것으로 유효성 새틀라이트를
  적재하고, 없으면 확실한 판별이 불가능하므로 허브·링크에 최근 관측일(last seen
  date)을 두어 추정한다 — 전체 적재(full load) 전제의 educated guess다
  (§12.1.9, pp.546–547).[^linstedt2016]

## 참조 테이블 적재

- **무이력 참조 테이블**: 이력 불요·전체 적재·동일 인프라·스테이징 완전 통제·
  모든 코드 보존·변환 불요 등의 조건이 모두 충족되면 물리 적재 없이 SQL 뷰로
  가상화할 수 있다 — 분석용 MDM 데이터가 전형이고, 나중에 필요하면 다음
  스프린트에서 물리화한다 (§12.2.1, pp.551–552).[^linstedt2016]
- MERGE 문은 성능 문제로 웨어하우스 적재에 일반적으로 비권장이지만, 참조
  테이블처럼 작은 테이블에서는 단순성을 위해 허용된다 (§12.2.1, p.555).[^linstedt2016]
- **이력형 참조 테이블**: 무이력 테이블(코드 목록)에 새틀라이트를 단 2-테이블
  구조. 이 새틀라이트는 해시 키가 아니라 **코드 자체**를 부모 키로 쓴다(참조
  테이블의 목적이 가독성이므로 해시 키가 없다). 적재는 표준 새틀라이트 템플릿과
  같고 종료일 부여도 필요하다 (§12.2.2, pp.555–558).[^linstedt2016]
- **코드·설명(code and descriptions) 테이블**: 코드 몇 개짜리 그룹이 수백 개인
  원천에서, 그룹마다 테이블을 만드는 대신 표준 속성(설명·정렬 순서 등)만 담는
  일반화 테이블 하나로 통합한다. 비표준 속성이 필요한 그룹만 개별 참조 테이블로
  뺀다. 이력이 필요하면 역시 새틀라이트를 단다 (§12.2.3–4, pp.558, 562).[^linstedt2016]

적재가 끝난 배치는 스테이징에서 정리한다 — 방식과 주기는
[스테이징 영역](staging-area.md) 참조 (§12.3, pp.566–567).[^linstedt2016]

[^linstedt2016]: Linstedt & Olschimke 2016, 12장 "Loading the Data Vault"
