## 버전 조건

> **버전 조건**: 이 페이지가 드는 제품과 형식 이름(Protocol Buffers·Avro·gzip·Brotli·
> GraphQL·HATEOAS)은 **2025년 저술 시점**의 것이다. 모범 사례 아홉과 성능 손잡이 다섯의
> 성격은 시점에 매이지 않는다.

## 설계 패턴이라는 낱말

- 장의 자리부터 적힌다 — **이 장은 API 수명 주기의 설계 단계를 위한 실무 안내**이고, **API 설계
  패턴·API 보안 패턴·API 모범 사례 같은 흔한 API 주제에 대한 인식을 높이는 것**을 목표로 한다
  (2장 머리말, p.41).[^dynowski2025]
- 규정 (2장, p.41).[^dynowski2025]

  > A software design pattern is a blueprint for solving a particular, commonly occurring
  > problem when creating software.

- 그 규정이 이 장의 존재 근거로 이어진다 — **API를 설계하는 것은 다차원적 과정이지만 어떤
  도전들은 API 스타일과 무관하게 공통이다. 설계 패턴이 그 도전들에 대한 해법의 개발을 안내할 수
  있다** (2장, p.41).[^dynowski2025]
- 제시 형식도 명시된다 — **이 장은 그 패턴들을 하나씩, 요리책 같은 형식으로 제시해 당신이
  그것들을 고르고 자기 설계 과정에 통합하는 것을 돕는다.** 실제 적용은 5장에서 예제 REST API를
  지으며 보인다 (2장, p.41).[^dynowski2025]

## 이 장이 답하려는 물음들

- 절의 입구에서 물음이 열거된다 — **어떤 API 스타일로 작업하든 다음과 같은 물음에 답해야
  한다** (2장 §"Examples of API Design Patterns", p.41).[^dynowski2025]
  - **API 문서에 어떤 자연어를 쓸 것인가**
  - **API를 어떻게 버저닝할 것인가**
  - **인터페이스의 이름을 어떻게 지을 것인가**
  - **어떤 인코딩을 쓸 것인가**
  - **데이터를 어떻게 서빙할 것인가**
- 더 공부할 곳으로 저자들이 드는 것이 **JJ Geewax의 *API Design Patterns*(Manning, 2021)** 과
  **구글의 API 설계 지침, 마이크로소프트의 REST API 설계 지침, The REST API Tutorial과
  Learn REST API Design 개관**이다 (2장, p.41).[^dynowski2025] 이 KB는 그 가운데 어느 것도
  원전으로 갖고 있지 않다.

## 블로흐의 격언과 그 옮겨 읽기

- 저자들은 모범 사례를 자기 목록으로 시작하지 않고 남의 격언을 먼저 놓는다 — **조슈아 J.
  블로흐의 "How to Design a Good API and Why It Matters" 글이 API 설계에 관한 격언 묶음을
  담고 있고**, **그 격언들이 소프트웨어 라이브러리의 관점에서 진술되었지만 네트워크 기반 API를
  포함한 넓은 범위의 API에 적용 가능하다**고 적는다 (2장 §"API Design Best Practices",
  p.73).[^dynowski2025]
- 왜 좋은 API 설계가 중요한가에 대한 답 (2장, p.73).[^dynowski2025]

  > APIs can be among your greatest assets or liabilities. Good APIs create long-term
  > customers; bad ones create long-term support nightmares.
  >
  > Public APIs, like diamonds, are forever. You have one chance to get it right so give it
  > your best.
  >
  > All programmers are API designers. Good programs are modular, and intermodular
  > boundaries define APIs. Good modules get reused.
  >
  > —Joshua J. Bloch, 2006

- 저자들이 그것을 네트워크 기반 API의 공간으로 옮겨 읽는다 (2장, p.73).[^dynowski2025]
  - **이십 년 전 블로흐는 API가 고객을 마주하는 자산이라는 것을 알아차렸고, 오늘 우리는 API를
    잘 설계되면 비용 효율적일 수 있는 제품으로 다룬다.**
  - **API 설계가 중요한 이유는 API가 한 번 프로덕션에 들어가면 그것을 바꿀 능력이 제한되고,
    형편없이 설계된 API를 유지보수하는 것이 악몽이기 때문이다.**
  - **API는 모듈들(엔드포인트·프로시저·필드 따위)로 지어지고, 각 모듈은 재사용 가능한 기능을
    제공하며 API가 존재하는 동안 내내 가도록 설계된다.**

## 모범 사례 아홉

- **네트워크 기반 API 설계를 위한 고수준 모범 사례의 선별**로 아홉이 열거된다 (2장,
  pp.74–75).[^dynowski2025]
  - **대상에 맞춘(Tailored to the audience)** — API가 클라이언트의 필요에 맞게 설계된다.
    클라이언트는 웹 브라우저·모바일 기기·스마트워치·IoT 기기·AI 에이전트 따위일 수 있다.
    **어떤 API 스타일은 다른 스타일보다 클라이언트의 필요에 맞추는 유연성이 크다** — 예로 드는
    것이 클라이언트가 원하는 형식으로 데이터를 요청하게 하는 GraphQL이다.
  - **직관적인(Intuitive)** — **직관적인 API는 문서 없이도 항해할 수 있다.** 예로 드는 것이
    **HATEOAS를 갖춘 REST API**이고, **응답이 관련 자원과 허용되는 동작으로 가는 링크를 담기
    때문**이다.
  - **유지보수 가능한(Maintainable)** — **유지보수 가능한 API는 클라이언트를 어지럽히지 않고
    진화한다.** 방법이 둘이다 — **후진 호환 변경을 하거나, 버저닝으로 깨는 변경을 알리는 것.**
  - **문서화된(Documented)** — **API에는 문서가 딸린다. 문서의 존재가 API의 사용성과 채택에
    영향을 주고, 문서의 부재가 그 사용을 방해할 수 있다.**
  - **오용하기 어려운(Hard to misuse)** — **API가 최소 놀람의 원칙을 따른다**는 뜻이고,
    **간단한 일은 곧바로 되고, 복잡한 일은 달성 가능하며, 오류는 내기 어려워야 한다**는 것이다.
    이 원칙은 **표준적인 설계 관행과 오류 메시지와 데이터 검증을 써서 개발자에게 예측 가능한
    경험을 주는 API를 만드는 것을 돕는다.**
  - **테스트 가능한(Testable)** — **API 개발자나 사용자가 자기가 짓거나 쓰는 API를 테스트할
    수단을 가져야 한다.** **설정 때문에 API 테스트가 불가능하면 실제 API를 대신할 알맞은 모의
    API가 쓰여야 한다.**
  - **안전한(Secure)** — **API는 당신의 체계로 들어가는 관문이다.** 요구가 넷이다 — **입력은
    API 취약점을 악용할 위험을 줄이도록 검증되어야 하고, 출력은 민감 정보를 노출해서는 안
    되며, API가 쓰는 라이브러리와 외부 서비스는 최신 보안 패치로 갱신되어야 하고, 안전한 API는
    중복 요청을 다루고 들어오는 요청의 바람직하지 않은 과잉을 억누를 수 있다.**
  - **효율적인(Efficient)** — **API는 체계 자원의 사용을 최소화하려 애쓴다.** **클라이언트가
    응답을 맞춤할 수 있게 하면 API가 데이터 전송을 줄이고 자원 사용을 최적화할 수 있다.**
    수단으로 드는 것이 **필드 필터링**(REST의 희소 필드셋 같은)과 **GraphQL 같은 질의 지향
    API**다.
  - **오류를 전달하는(Communicates errors)** — **API는 자기 스타일에 알맞은 표준 오류 코드로
    자기 상태를 전달한다.** **REST API는 HTTP 상태 코드를, gRPC API는 gRPC 상태 코드를
    쓴다.** 거기에 더해 **API는 문제를 해결할 맥락과 안내를 주는 사람이 읽을 수 있는 오류
    메시지를 제공한다. 표준 오류 코드와 서술적 메시지의 이 결합이 개발자가 운영상의 문제를
    이해하고 다루는 것을 돕는다.**

## 성능을 올리는 다섯 손잡이

- 곁글 하나가 API 성능을 올리는 팁 다섯을 든다. **각 항목마다 되사는 대가가 같이 적혀
  있다는 것이 이 목록의 성격**이다 (2장 곁글 §"General Tips to Improve API Performance",
  p.75).[^dynowski2025]
  - **압축** — **gzip이나 Brotli 같은 알맞은 데이터 압축 알고리즘을 고르면 API 응답의 크기가
    줄어 네트워크로 데이터를 더 빨리 옮길 수 있다. 더 작은 적재물이 성능을 개선하며 특히 대역폭이
    제약된 조건에서 그렇다.** 대가는 **압축이 CPU 사용을 늘리므로 API 설계자가 계산 비용과
    대역폭 비용의 균형을 잡아야 한다**는 것이다.
  - **인코딩** — **인코딩 형식이 API 성능에 영향을 준다. Protocol Buffers와 Avro 같은 이진
    형식이 JSON과 XML 같은 텍스트 기반 형식보다 크기와 처리 속도에서 대체로 낫다.** 대가는
    **텍스트 기반 형식이 디버깅이나 사람의 가독성에는 더 나을 수 있다**는 것이다.
  - **캐싱** — **API 앞에 캐시를 두면 API가 기대는 데이터베이스나 저장소 같은 자원의 사용이
    줄어든다.** 대가가 셋이다 — **메모리 사용이 늘고**, **데이터 원천과 동기화되지 않으면
    캐시된 데이터가 낡거나 소실될 수 있으며**, **개발과 운영 비용이 늘어난다.**
  - **하드웨어** — **수직 확장(더 많은 CPU·메모리·저장을 주는 인스턴스로 교체하거나
    업그레이드하는 것)이 체계 성능을 개선할 수 있다.** 대가가 둘이다 — **이 방법이 성능 문제의
    밑에 있는 원인을 가릴 수 있고**, **하드웨어 확장에는 한계가 있어 그 지점을 넘으면 수평
    확장(하드웨어를 더 붙이는 것)이 필요해진다.**
  - **API 속도 제한** — **주어진 시간 구간 안에 클라이언트당 API 요청 수를 제한하면 남용이 줄고
    백엔드 자원이 보호된다.**

## 느슨한 표준이라 표준이 필요하다

**2022년 API 아키텍처 운영서가 같은 물음을 다른 쪽에서 연다.** 위 아홉은 잘 된 API가 무엇을
만족하는가이고, 이 절부터는 **그 만족을 누가 정해 주는가**다.

- **출발이 REST의 느슨함이다** — **REST는 아주 기본적인 규칙 몇 개를 갖지만 대부분의 구현과
  설계는 개발자의 몫으로 남는다** (1장 §"REST API Standards and Structure",
  p.8).[^gough2022]
- **저자들이 그 공백을 물음 셋으로 보인다** (1장, p.8):[^gough2022]
  - **오류를 전달하는 최선의 방법은 무엇인가.**
  - **페이지네이션은 어떻게 구현해야 하는가.**
  - **호환성이 자주 깨지는 API를 짓는 것을 어떻게 하면 우연히 피할 수 있는가.**
- **그래서 필요해지는 것** — **서로 다른 구현들에 걸쳐 균일성과 기대를 제공하려면 API에 대한 더
  실무적인 정의를 갖는 것이 유용하고, 여기가 표준이나 지침이 도울 수 있는 자리다.** 단서가
  붙는다 — **고를 출처가 다양하다** (1장, p.8).[^gough2022]
- **저자들이 고른 것은 마이크로소프트 REST API 가이드라인**이다. **오픈소스로 공개된 일련의 내부
  지침**이라고 적는다 (1장, p.8).[^gough2022]
  - 버전 조건: 2022년 저술 시점. 그 지침 문서의 내용과 절 번호가 그 시점의 것이다.
  - **그 지침은 RFC-2119를 쓴다** — **`MUST`·`SHOULD`·`SHOULD NOT`·`MUST NOT` 같은 표준을 위한
    용어를 정의해, 개발자가 요건이 선택인지 필수인지 판단하게 한다** (1장,
    pp.8–9).[^gough2022]
  - **저자들 자신이 이 목록이 자란다고 적는다** — **REST API 표준은 진화하고 있어서 열린 API
    표준 목록을 책의 깃허브 페이지에 두었고, 다른 독자에게 유용할 열린 표준을 풀 리퀘스트로
    기여해 달라고 청한다** (1장, p.9).[^gough2022]
- **장의 요약이 같은 것을 되풀이한다** — **REST는 꽤 느슨한 표준이다. API를 지을 때 합의된 API
  표준에 맞추면 API가 일관되고 소비자가 기대하는 동작을 갖게 된다. API 표준은 비호환 API로 이어질
  수 있는 설계 결정을 미리 끊어 내는 데도 도움이 된다** (1장 §"Summary",
  p.24).[^gough2022]

## 표준이 실제로 정해 주는 것

**저자들이 참석자 API를 실제로 설계하며 그 지침이 결정해 주는 자리를 넷 보인다.**

- **민감 정보를 URI에 두지 않는다** — 새 참석자를 만드는 `POST`의 응답에서 **`Location` 헤더가
  서버에 만들어진 새 자원의 위치를 드러내고, 이 API는 사용자를 위한 고유 ID를 모델링한다.
  `email` 필드를 고유 ID로 쓰는 것도 가능하지만, 마이크로소프트 REST API 가이드라인은 §7.9에서
  개인 식별 정보(PII)가 URL의 일부가 되어서는 안 된다고 권고한다** (1장, p.9).[^gough2022]
  - **근거가 붙는다** — **민감 데이터를 URL에서 빼는 이유는 경로나 질의 파라미터가 네트워크에서
    부주의하게 캐시될 수 있기 때문**이고, 저자들이 드는 예가 **서버 로그나 다른 곳**이다 (1장,
    p.9).[^gough2022]
- **이름은 표준을 넘어 조직의 사전으로 넓힌다** (1장, p.9):[^gough2022]
  - **API의 또 다른 어려운 면이 이름 짓기다.** 저자들이 그 무게를 대는 방식 — **이름 하나를
    바꾸는 것처럼 단순한 것이 호환성을 깰 수 있다.**
  - **마이크로소프트 REST API 가이드라인에 써야 할 표준 이름의 짧은 목록이 있지만, 팀은 그것을
    확장해 표준을 보충하는 공통 도메인 데이터 사전(domain data dictionary)을 가져야 한다.**
  - **많은 조직에서 데이터 설계와, 경우에 따라서는 거버넌스에 관한 요건을 선제적으로 조사하는
    것이 엄청나게 도움이 된다.**
  - **회사가 제공하는 모든 API에 걸쳐 일관성을 제공하는 조직은 소비자가 응답을 이해하고 연결할 수
    있게 하는 균일성을 제시한다.**
  - **어떤 도메인에는 이미 널리 알려진 용어가 있을 수 있다. 그것을 쓰라.**
- **컬렉션을 배열이 아니라 객체로 감싼다** (1장 §"Collections and Pagination",
  p.10):[^gough2022]
  - **`GET /attendees` 요청을 원시 배열을 담은 응답으로 모델링하는 것이 합리적으로 보인다.**
  - **대안은 참석자 배열을 객체 안에 중첩하는 것이다. 배열 응답이 객체 안에 돌아오는 것이 이상해
    보일 수 있지만, 이유는 그래야 더 큰 컬렉션과 페이지네이션을 모델링할 수 있기 때문이다.**
  - **페이지네이션은 부분 결과를 돌려주면서 소비자가 다음 결과 집합을 어떻게 요청하는지의 지시를
    함께 주는 것을 수반한다.**
  - **판정이 붙는다** — **이것은 뒤늦은 깨달음의 이점을 거두는 것이다. 나중에 페이지네이션을 더하며
    표준이 권고하는 `@nextLink`를 넣으려고 배열에서 객체로 바꾸면 호환성이 깨진다.**
  - **페이지네이션 패턴 자체의 정본은 이 페이지가 아니다** —
    [API 목록 조회 패턴](api-list-query-patterns.md)이다. **여기 있는 것은 그 패턴을 나중에 들일
    수 있게 응답의 모양을 미리 정해 두라는 조문이다.**
- **필터는 표현 언어를 표준에서 빌린다** (1장 §"Filtering Collections",
  pp.10–11):[^gough2022]
  - **컬렉션이 커지면 페이지네이션에 더해 필터링을 더해야 할 수도 있다.**
  - **필터링 표준은 REST 안에서 필터 질의가 어떻게 동작해야 하는지를 표준화하는 표현 언어를
    제공하고, 그것은 OData 표준에 기반한다.** 저자들이 드는 예가 **`displayName`이 `Jim`인 모든
    참석자를 `$filter=displayName eq 'Jim'`으로 찾는 것**이다.
  - **처음부터 모든 필터링과 검색 기능을 완성할 필요는 없다. 다만 표준에 맞춰 API를 설계하면
    소비자의 호환성을 깨지 않으면서 진화하는 API 아키텍처를 떠받칠 수 있다.**
  - **저자들이 같은 자리에서 다른 스타일을 가리킨다** — **필터링과 질의는 GraphQL이 정말 잘하는
    기능이고, 특히 여러 서비스에 걸친 질의와 필터링이 문제가 되면 그렇다** (1장,
    p.11).[^gough2022]

## 오류를 다루는 규약

- **왜 미리 정하는가** — **API를 소비자에게 확장할 때 중요한 고려가 여러 오류 시나리오에서 무엇이
  일어나야 하는지를 정의하는 것이다. 오류 표준은 미리 정의해 프로듀서들과 나눠 일관성을 제공하는
  것이 유용하다** (1장 §"Error Handling", p.11).[^gough2022]
- **오류가 무엇을 해야 하는가** — **오류는 요청에 무엇이 잘못됐는지를 소비자에게 정확히 서술해야
  하고, 그래야 그 API에 들어가는 지원 부담이 늘어나는 것을 피한다** (1장,
  p.11).[^gough2022]
- **저자들이 지침의 조문을 그대로 인용한다** (1장, p.11):[^gough2022]

  > For non-success conditions, developers SHOULD be able to write one piece of code that
  > handles errors consistently.

- **상태 코드를 정확히 주어야 하는 이유는 소비자 쪽에 있다** — **소비자가 흔히 응답에 담긴 상태
  코드를 중심으로 로직을 짓기 때문**이다. 그리고 반례를 든다 — **성공을 가리키는 `2xx` 계열 응답과
  함께 본문에 오류를 돌려주는 API를 많이 봤다** (1장, p.11).[^gough2022]
- **계열마다 소비자 라이브러리가 하는 일이 다르다** (1장, p.11):[^gough2022]
  - **`3xx`(리다이렉트)** — **일부 소비 라이브러리 구현이 능동적으로 따라가고, 그것이 제공자가
    외부 소스를 재배치하고 접근하게 해 준다.**
  - **`4xx`** — **보통 클라이언트 쪽 오류를 가리키고, 이 시점에서 메시지 필드의 내용이 개발자나
    최종 사용자에게 극히 유용하다.**
  - **`5xx`** — **보통 서버 쪽 실패를 가리키고, 일부 클라이언트 라이브러리는 이런 유형의 실패에서
    재시도한다.**
- **문서화가 요구되는 자리 하나** — **예상치 못한 실패에서 서비스에 무엇이 일어나는지를 고려하고
  문서화하는 것이 중요하다.** 저자들이 드는 물음이 **결제 체계에서 `500`이 결제가 통과했다는
  뜻인가 아닌가**다 (1장, p.11).[^gough2022]
- **외부로 나가는 오류에서 벗겨 낼 것** (1장, p.11):[^gough2022]
  - **외부 소비자에게 돌려보내는 오류 메시지가 스택 트레이스와 다른 민감한 정보를 담지 않게 하라.
    이 정보는 체계를 손상시키려는 해커를 도울 수 있다.**
  - **마이크로소프트 지침의 오류 구조에는 `InnerError`라는 개념이 있어서 더 상세한 스택
    트레이스나 이슈 서술을 놓기에 유용할 수 있다. 디버깅에는 엄청나게 도움이 되겠지만 외부
    소비자에게 가기 전에 벗겨져야 한다.**
- **절의 결론** — **REST API 구축의 표면만 긁었지만 API를 짓기 시작할 때 내려야 할 중요한 결정이
  많다는 것은 분명하다. 직관적이고 일관되며 진화할 수 있고 호환되는 API를 제시하려는 욕구를
  합치면, API 표준을 일찍 채택할 값이 있다** (1장, p.11).[^gough2022]

## 어떤 표준을 채택할 것인가

**같은 책이 이 결정을 ADR 지침 한 칸으로 적는다.** 그 양식의 규정은
[아키텍처 결정 기록](architecture-decision-records.md)이 갖는다.

- **결정** — **어떤 API 표준을 채택해야 하는가** (1장 표 1-2, p.12).[^gough2022]
- **논의할 점 넷** (1장 표 1-2, p.12):[^gough2022]
  - **조직에 이미 회사 안의 다른 표준들이 있는가.**
  - **그 표준들을 외부 소비자에게까지 확장할 수 있는가.**
  - **소비자에게 노출해야 하고 이미 표준을 갖고 있는 서드파티 API(예를 들어 아이덴티티 서비스)를
    쓰고 있는가.**
  - **표준이 없을 때의 영향이 우리 소비자에게 어떻게 보이는가.**
- **권고 넷** (1장 표 1-2, p.12):[^gough2022]
  - **조직의 문화와, 인벤토리에 이미 갖고 있을 수 있는 API의 형식에 가장 잘 맞는 API 표준을
    고르라.**
  - **표준을 진화시키고 도메인이나 산업에 특정한 수정을 더할 준비를 하라.**
  - **나중에 일관성을 위해 호환성을 깨야 하는 일을 피하려면 일찍 무언가로 시작하라.**
  - **기존 API에 비판적이 되라. 소비자가 이해할 형식인가, 아니면 그 콘텐츠를 내주는 데 더 많은
    노력이 필요한가.**

## 규칙이 아니라 지침이다

- 블로흐의 격언 묶음이 끝나는 자리를 저자들이 그대로 자기 결론으로 쓴다 — 그 마지막 격언이
  **설계 격언이나 패턴이 규칙이 아니라 안내가 되도록 의도되었다**고 말한다는 것이다 (2장,
  p.73).[^dynowski2025]

  > API design is an art, not a science. Strive for beauty, and trust your gut. Do not adhere
  > slavishly to the above heuristics, but violate them only infrequently and with good
  > reason.
  >
  > —Joshua J. Bloch, 2006

- 장의 요약이 같은 것을 되풀이하며 범위도 한 번 더 긋는다 (2장 §"Summary",
  p.76).[^dynowski2025]
  - **이 장이 서술한 API 설계 패턴들은 REST API에 초점을 두지만 다른 API 스타일에도 적용될 수
    있다.**
  - **탐색된 API 보안 패턴들 — 암호화, 인증과 인가, 데이터 검증 — 도 여러 API 스타일에 걸쳐
    공통이다.**
  - 그리고 결론 — **이 장에서 가져갈 것은, API 설계자인 당신이 고를 수 있는 설계 패턴이 많이
    존재하지만 그것들은 규칙이 아니라 안내가 되도록 의도되었다는 것이다.**
