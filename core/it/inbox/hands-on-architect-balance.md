하나의 질문: **아키텍트가 코드를 계속 만지면서도 팀의 병목이 되지 않으려면 무엇을 맡아야
하는가.**

## 전제 — 모든 아키텍트는 코딩해야 한다

- **저자들의 선언** — 아키텍트가 마주하는 어려운 과제 하나가 **코딩 실무와 소프트웨어 아키텍처의
  균형을 어떻게 잡는가**다. 저자들은 **모든 아키텍트가 코딩해야 하고 일정 수준의 기술적 깊이를
  유지해야 한다고 굳게 믿는다.** 그리고 곧바로 단서를 붙인다 — **쉬운 일처럼 보일 수 있지만
  때로는 꽤 이루기 어렵다** (2장 §"Balancing Architecture and Hands-On Coding",
  p.33).[^richards2025]
  - **여기서 요구되는 "기술적 깊이"의 규정은 앞 절에 있다** —
    [기술적 너비와 지식 피라미드](technical-breadth-and-knowledge-pyramid.md)가 그 자리이고,
    저자들 자신이 이 문장에서 그 절을 가리킨다 (2장, p.33).[^richards2025] **곧 이 절은 너비를
    사기 위해 깊이를 일부 내주라는 앞 절의 처방에 하한을 긋는다.**

## 병목 함정 안티패턴

- **첫째 조언이 회피다** — 코딩 실무와 아키텍트 역할의 균형을 잡으려는 사람을 위한 저자들의 첫
  조언은 **병목 함정(Bottleneck Trap)을 피하는 것**이다 (2장, p.34).[^richards2025]
- **규정** — 병목 함정 안티패턴은 **아키텍트가 체계의 임계 경로(critical path)에 있는 코드를
  자기 소유로 떠맡아 팀의 병목이 될 때 일어난다.** 그 코드는 **대개 밑에 깔린 프레임워크 코드나
  더 복잡한 부분들**이다 (2장, p.34).[^richards2025]
- **원인** — **아키텍트가 전업 개발자가 아니기 때문**이다. 그래서 **개발 작업(소스 코드를 쓰고
  테스트하는 일)과 아키텍트 역할(도식을 그리고 회의에 참석하고, 그리고 또 회의에 참석하는 일)의
  균형을 잡아야 한다** (2장, p.34).[^richards2025]

## 회피책 — 임계 경로를 위임하고 늦은 이터레이션의 작은 기능을 맡는다

- **처방** — 병목 함정을 피하는 방법 하나는 **아키텍트가 체계의 임계 부분을 개발 팀의 다른
  사람들에게 위임하고, 자신은 한 번에서 세 번 이터레이션 뒤의 작은 업무 기능(서비스나 UI 화면
  따위) 코딩에 집중하는 것**이다 (2장, p.34).[^richards2025]
- **저자들이 세는 긍정적 효과 셋** (2장, p.34):[^richards2025]
  - **하나** — 아키텍트가 **팀의 병목이 되는 것을 피하면서 프로덕션 코드를 쓰는 실무 경험을
    얻는다.**
  - **둘** — **임계 경로와 프레임워크 코드가 개발 팀에 분산되고**, 그것이 **있어야 할 곳**이다.
    그래서 팀이 **체계의 더 어려운 부분에 대한 소유권과 더 나은 이해를 갖는다.**
  - **셋, 그리고 어쩌면 가장 중요한 것** — 아키텍트가 **개발 팀과 같은 업무 관련 소스 코드를
    쓰게 된다.** 그것이 **프로세스·절차·개발 환경을 둘러싼 개발 팀의 고충을 더 잘 알아보게
    돕고, 바라건대 그것들을 개선하는 일로 이어진다.**

## 팀과 함께 개발할 수 없을 때의 기법 다섯

- **물음** — 그런데 아키텍트가 개발 팀과 함께 코드를 개발할 수 없다면, 어떻게 코드를 계속 만지고
  일정 수준의 기술적 깊이를 유지하는가. 저자들이 이탤릭 소제목을 붙인 기법 다섯을 준다 (2장,
  pp.34–35).[^richards2025]
- **하나 — 잦은 개념 증명(frequent proofs-of-concept)** — 개념 증명(POC)을 자주 하면 **아키텍트가
  소스 코드를 쓰게 되고**, 동시에 **구현 세부를 고려에 넣어 아키텍처 결정을 검증하는 데도
  도움이 된다.** 저자들이 드는 실물 — **아키텍트가 캐싱 해법 둘 사이에서 고르지 못하고 막혔을
  때, 각 캐싱 제품으로 동작하는 예제를 만들어 결과를 비교하는 것**이 결정을 돕는 효과적인 방법
  하나다. 그러면 **구현 세부와 완전한 해법을 개발하는 데 드는 노력의 양을 직접 보게 되고**,
  **서로 다른 캐싱 해법 사이의 확장성·성능·전반적 결함 감내 같은 아키텍처 특성을 더 잘 비교할 수
  있다** (2장, p.34).[^richards2025]
  - **저자들이 개념 증명 코드에 품질 요구를 건다** — **가능하면 언제나 아키텍트는 자기가 쓸 수
    있는 최선의 프로덕션 품질 코드를 써야 한다.** 이유가 둘이다 (2장, pp.34–35):[^richards2025]
    - **첫째 — 꽤 자주 "버릴(throwaway)" 개념 증명 코드가 소스 코드 저장소로 들어가 다른 사람들이
      따라야 할 참조 아키텍처나 길잡이 예제가 된다.** **아키텍트가 가장 원하지 않을 일이 자기
      엉성한 버릴 코드가 자기 평소 일의 품질을 대표하는 것으로 취급되는 것**이다.
    - **둘째 — 프로덕션 품질의 개념 증명 코드를 쓴다는 것은 품질 좋고 잘 구조화된 코드를 쓰는
      연습을 한다는 뜻**이다. 그러지 않으면 **빠르고 엉성한 POC를 만들며 나쁜 코딩 습관을 계속
      기르게 된다.**
- **둘 — 기술 부채 처리(tackle technical debt)** — 아키텍트가 **기술 부채 일부를 처리하면 개발
  팀은 임계적인 기능 사용자 스토리에 매달릴 수 있게 풀려난다.** 저자들이 그 배치의 근거로 드는
  것 — **기술 부채는 대개 우선순위가 낮으므로, 아키텍트가 주어진 이터레이션 안에 기술 부채 과제를
  끝내지 못해도 세상이 끝나지 않고 일반적으로 그 이터레이션의 성공에 영향을 주지 않는다** (2장,
  p.35).[^richards2025]
- **셋 — 버그 수정(fix bugs)** — 마찬가지로 **이터레이션 안에서 버그 수정을 맡는 것도 개발 팀을
  도우면서 코딩 실무 기량을 유지하는 방법**이다. 저자들이 덧붙이는 것 — **분명 화려하지는 않지만,
  이 기법은 아키텍트가 코드 베이스와 어쩌면 아키텍처 안의 문제와 약점을 식별하게 해 준다** (2장,
  p.35).[^richards2025]
- **넷 — 자동화(automate)** — **개발 팀의 일상 과제를 돕는 단순한 명령줄 도구와 분석기를 만들어
  자동화를 활용하는 것**이 코딩 실무 기량을 유지하면서 개발 팀을 더 효과적으로 만드는 또 하나의
  좋은 방법이다. **개발 팀이 되풀이하는 과제를 찾아 자동화하라. 그들이 그 자동화를 고마워할
  것이다.** 저자들이 드는 실물이 **다른 린트 검사에 없는 특정 코딩 표준을 검사하는 자동 소스
  검증기, 자동화된 체크리스트, 되풀이되는 수작업 코드 리팩터링 과제**다 (2장,
  p.35).[^richards2025]
  - **같은 기법의 둘째 층이 거버넌스다** — **아키텍처의 활력과 준수를 보장하는 아키텍처 분석과
    적합도 함수 형태의 자동화**도 코드를 계속 만지는 좋은 방법이다. 저자들이 드는 실물 —
    **아키텍트가 자바 플랫폼에서 ArchUnit으로 자바 코드를 써서 아키텍처 준수를 자동화하거나,
    맞춤 적합도 함수를 써서 아키텍처 준수를 보장하면서 실무 경험을 얻을 수 있다.** 저자들이
    그 기법들을 6장으로 넘긴다 (2장, p.35).[^richards2025]
- **다섯 — 코드 리뷰(do code reviews)** — 아키텍트가 코드를 계속 만지는 **마지막 기법은
  잦은 코드 리뷰를 하는 것**이다. **아키텍트가 실제로 코드를 쓰지는 않지만, 적어도 소스 코드에
  관여한 상태로 남게 한다.** 저자들이 세는 부수 이익 둘 — **아키텍처 준수의 보장**과 **팀에서
  멘토링·코칭 기회를 식별하는 것**이다 (2장, p.35).[^richards2025]
  - **저자들이 절의 첫머리에서 "기법과 요령 몇"이라 예고하며 개수를 세지 않는다** (2장,
    p.34).[^richards2025] 다섯이라는 수는 이탤릭 소제목을 센 것이다. **앞의 넷이 아키텍트가
    직접 코드를 쓰는 기법이고 다섯째만 쓰지 않는 기법**이라는 가름은 이 KB가 세운 것이다.
    #hypothesis

## 이 KB의 다른 소스들과 맞대어 본 자리

**모순으로 판정한 쌍이 없다.** `contradicts`를 걸지 않았다.

- **"아키텍트가 코딩해야 하는가"는 이 KB에 이미 선 논쟁이고 이 페이지가 셋째 자리다.**
  [진화적 아키텍트의 역할](evolutionary-architect-role.md)이 그 논쟁의 자리인데, 그 페이지의
  정리대로 **뉴먼 쪽은 아키텍트가 코드에 가까이 남으라고 하고, 하멜로 쪽은 손대는 아키텍트
  원형 자체를 상아탑의 변종으로 본다**
  ([전통적 아키텍처 실천](traditional-architecture-practice.md)의 "손을 대는 아키텍트" 절).
  **이 소스는 첫째 쪽에 서되 조건을 붙인다** — 코딩하라, **단 임계 경로는 맡지 마라**. 하멜로
  쪽이 손대는 아키텍트의 약점으로 지적한 것이 **팀에서 팀으로 뛰어다니느라 어디에도 충분히
  머물지 못해 전체가 상한다**는 것인데, **이 소스가 지적하는 약점은 반대로 한 자리에 너무 깊이
  박혀 병목이 된다는 것**이다. **두 약점이 같은 실천의 서로 다른 실패 형태이고 겨루지 않는다.**
  이 대조는 이 KB가 세운 것이며 두 소스는 서로를 호명하지 않는다. #hypothesis
- **적합도 함수를 코딩 실무의 자리로 쓰는 용법이 이 KB에 새롭다.**
  [아키텍처 적합도 함수](architecture-fitness-functions.md)와
  [자동화된 아키텍처 거버넌스](automated-architectural-governance.md)는 적합도 함수를 **거버넌스
  수단**으로 다루는데, **이 절은 같은 것을 아키텍트가 기술적 깊이를 유지하는 수단으로 쓴다.**
  **같은 도구의 부수 효과를 목적으로 세우는 자리**다.
- **ArchUnit이 이 KB에 이미 있다.** [자동화된 아키텍처 거버넌스](automated-architectural-governance.md)가
  그것을 턴키 도구 계열로 다룬다. **이 절은 그것을 아키텍트 개인의 실무 유지 수단으로 다시
  든다.**
- **기술 부채를 아키텍트가 보는 일이 이 KB에 이미 있다.**
  [진화적 아키텍트의 역할](evolutionary-architect-role.md)의 "기술 부채를 보는 것이 아키텍트의
  일이다" 절이 그 자리인데, **그쪽은 보는 일이고 이쪽은 직접 갚는 일**이다. **층이 다르다.**
