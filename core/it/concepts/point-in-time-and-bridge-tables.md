# PIT 테이블과 Bridge 테이블

하나의 질문: **Data Vault의 조인 폭발에서 질의 성능을 어떻게 회복하나.**

Raw Data Vault는 허브·링크·새틀라이트로 잘게 정규화되어 있어, 정보 마트를 뽑아내려면 매번 여러 테이블을 다시 조인해야 한다. Data Vault 2.0은 이를 위해 질의 보조 테이블(query assistant table) 두 종을 표준에 둔다 — 하나의 허브(링크)에 붙은 여러 새틀라이트를 시점별로 묶는 **point-in-time(PIT) 테이블**, 여러 허브와 링크를 가로지르는 지름길인 **Bridge 테이블**.

## 문제: 다중 새틀라이트와 시간 정렬

- 하나의 허브나 링크에 새틀라이트가 여럿 붙는 것은 데이터 웨어하우스에서 매우 흔하다 — 여러 소스 시스템을 통합하기 때문이다. 문제는 각 소스의 비즈니스 객체 변경이 **같은 시점에 일어나지 않는다**는 것이다 (§6.1, pp.174–175).[^linstedt2016] 새틀라이트 분리는 ../concepts/data-vault-satellite.md 참조.
- 새틀라이트는 소스의 모든 변경을 담지도 않는다 — 적재 피드가 공급하는 만큼의 델타만 추적한다. 예를 들어 배치가 6시간마다 돌면 새틀라이트의 델타도 6시간 단위 상태만 남는다 (§6.1, p.176).[^linstedt2016]
- 그래서 "특정 날짜의 승객 상태"를 묻는 질의는 새틀라이트마다 유효 구간이 달라, 복잡한 시간 범위 처리를 낀 외부 조인(OUTER JOIN)이 필요해진다. 새틀라이트가 셋을 넘으면 복잡할 뿐 아니라 느려진다 (§6.1, pp.176–177).[^linstedt2016]
- 해법의 방향은 외부 조인을 **동등 조인(equi-join)** 으로 바꾸는 것이고, 이를 위해 PIT 테이블과 새틀라이트의 고스트 레코드(ghost record)가 도입된다 (§6.1, p.177).[^linstedt2016]

## PIT 테이블

### 구조: 스냅샷 날짜별 키 조합

- PIT 테이블은 데이터 소비자가 요구하는 주기(일 단위, 초 단위 등)로 스냅샷을 만든다. 행의 유일 키는 **부모 해시 키 + 스냅샷 날짜** 조합이고, 각 조합마다 그 스냅샷 시점에 유효했던 **각 새틀라이트의 해시 키와 적재 시각(load date)** 을 한 행에 나란히 담는다 — 새틀라이트당 적재 시각 컬럼 하나 (§6.1.1, pp.177–179).[^linstedt2016]
- 각 PIT 행 자체도 해시 키로 식별되며, 이 값은 하류에서 정보 마트의 Type 2 차원 테이블을 적재할 때 그대로 쓸 수 있다 (§6.1.1, p.178).[^linstedt2016]
- PIT의 데이터는 시스템이 계산한 것이지 소스에서 온 것이 아니므로 **감사 대상이 아니다**. 이 테이블의 목적은 오직 성능이다 (§6.1, p.177).[^linstedt2016] 그래서 record source 같은 시스템 속성도 두지 않는다 (§6.1.1, p.180).[^linstedt2016]
- PIT는 Business Vault 내지 정보 마트 계층의 일부로 취급하며, 성능을 위해 계산 컬럼을 추가해도 된다 (§6.1.1, p.177).[^linstedt2016]

### 고스트 레코드: NULL을 없애 동등 조인을 성립시키는 장치

- 어떤 스냅샷 날짜에는 대응하는 새틀라이트 항목이 없을 수 있다 — 그 시점에 소스가 비즈니스 키를 몰랐거나 삭제된 경우다. 이때 PIT가 NULL을 가리키면 다시 외부 조인이 필요해진다 (§6.1.1, p.179).[^linstedt2016]
- 그래서 각 새틀라이트에 인위적 레코드 하나를 넣는다:

> If the source system doesn’t provide a corresponding record from the source system, the PIT table should point to an unknown record. In Data Vault 2.0 modeling, this record is called the ghost record. This record should be added to each satellite. (§6.1.1, p.179)[^linstedt2016]

- 고스트 레코드는 해당 타입의 최소 적재 시각·최대 종료일을 가져 항상 유효하고, record source를 SYSTEM으로 두어 인위 생성임을 표시한다. PIT의 NULL 참조를 전부 고스트 레코드 참조로 바꾸면 질의는 순수 동등 조인이 된다 (§6.1.1, pp.179–180).[^linstedt2016]

### 폭과 창 관리

- PIT의 폭이 너무 커지면 성능이 도로 떨어져 이점을 잃는다 — 특히 페이지 크기가 8KB로 제한되는 DBMS에서 민감하다 (§6.1.1, p.180).[^linstedt2016]
- 성능 유지책 둘: DB 수준 압축(저장량·I/O 개선, 대신 CPU 비용), 그리고 안 쓰는 스냅샷 삭제 (§6.1.1, p.180).[^linstedt2016]
- 관리 창(managed window): 최근 N개월만 유지하고 그보다 오래된 스냅샷은 지운다. 얼마나 남길지는 비즈니스가 정해야 하고, PIT 테이블마다 다르게 지정된다 (§6.1.2, p.181).[^linstedt2016]
- 로그 스케일 PIT(logarithmic PIT table): 이번 달은 일별, 올해는 주별, 최근 5년은 월별 스냅샷만 남기고 나머지는 삭제 — 저장량과 질의 성능의 절충이다. 지운 스냅샷이 다시 필요하면 처음 만들 때와 같은 알고리즘으로 재구축할 수 있다 (§6.1.2, pp.181–182).[^linstedt2016]
- 표준 PIT는 규칙적 스냅샷 기반이지만, 부모에 매달린 새틀라이트들의 모든 적재 시각에서 스냅샷 날짜를 유도해 전체 이력을 담을 수도 있다. 다만 전체 이력은 규칙이 아니라 예외여야 한다 (§6.1.1, p.180).[^linstedt2016]

## Bridge 테이블

### 구조: 허브·링크를 가로지르는 지름길

- Bridge 테이블도 목적은 같다 — Raw Data Vault 질의의 조인 수를 줄여 성능을 높인다. 역시 시스템 생성이라 감사 불가이고 Business Vault 소속이며, 실제로 성능 문제가 있을 때만 만들어야 한다 (§6.2, p.182).[^linstedt2016]
- PIT가 한 허브(링크)의 새틀라이트들을 종으로 묶는 반면, Bridge는 **여러 허브와 링크를 횡으로 가로지른다**. 특화된 링크 테이블과 비슷하다 (§6.2, p.182).[^linstedt2016] 링크 구조는 ../concepts/data-vault-link.md 참조.

> The bridge table acts as a higher-level fact-less fact table and contains hash keys from the hubs and links it spans. (§6.2, p.182)[^linstedt2016]

- 구성: 걸치는 허브·링크들의 해시 키 전부 + 스냅샷 날짜 + 행별 해시 키. 비즈니스 키·계산/집계 필드는 선택이다 (§6.2.1, p.183).[^linstedt2016] 재고 추적처럼 상품·매장·일 단위로 재고를 세는 경우에는 스냅샷 날짜를 기본 키에 포함하기도 한다 (§6.2.1, p.183).[^linstedt2016]
- 새틀라이트 정보는 담지 않는 것이 원칙이다 — 폭이 너무 커지기 때문이다 (§6.2, p.182).[^linstedt2016] 비즈니스 키 추가도 신중해야 한다: 폭이 커지면 성능이 급락하고 데이터 단편화·과잉 인덱싱을 부른다 (§6.2.1, p.184).[^linstedt2016]
- 예외적으로 KPI 값 같은 새틀라이트 데이터를 담아 팩트 테이블의 측정값 재료로 쓸 수 있는데, 이때 새틀라이트 데이터의 grain이 Bridge 키들의 grain과 일치해야 한다 — 어긋나면 집계 시 이중·삼중 계산이 난다 (§6.2.1, p.184).[^linstedt2016]

### grain과 적재 주의점

- Bridge는 걸치는 링크들과 같은 grain일 필요가 없다. GROUP BY로 집계 값을 실어 더 높은 grain으로 만들 수 있고, 그러면 탐색 링크(exploration link)와 매우 비슷해진다 (§6.2, p.182).[^linstedt2016]
- 적재 시 관련 허브들의 비즈니스 키 데카르트 곱(Cartesian product)이 생기므로 WHERE 절로 제한해야 하며, 모든 조합이 아니라 대상 팩트 테이블이 요구하는 grain에 맞춰야 한다. 정보 마트에 grain이 다른 팩트 테이블이 여럿이면 grain 정의당 최소 한 개씩 Bridge를 둔다 (§6.2, pp.182–183).[^linstedt2016]
- 가상화 정보 마트(SQL 뷰로 제공)에서는 뷰 계산 비용 때문에 특히 유효하다 — 시간이 오래 걸리는 계산을 Bridge에 미리 실어두면 접근이 극적으로 빨라진다 (§6.2, p.182).[^linstedt2016]

## 둘의 비교

- 공통점: 둘 다 시스템 생성 엔터티로 코어 아키텍처 밖이고, 그래서 감사 불가이며, 계산 필드를 담을 수 있고, 스냅샷 날짜로 식별되며, 특히 가상화 정보 마트의 성능 조력자다 (§6.2.2, p.184).[^linstedt2016]
- 차이: PIT는 **단일 허브(링크) 전용**으로 그 새틀라이트들의 적재 시각 스냅샷을 만들고(부모 해시 키 + 새틀라이트별 적재 시각), Bridge는 **여러 허브·링크에 걸쳐** 그들의 해시 키를 모으며 비즈니스 키를 함께 싣는 것이 관행이다 (§6.2.2, p.184).[^linstedt2016]
- 저자들의 단서: 올바른 하드웨어가 갖춰져 있다면 사실 둘 다 필요 없어야 한다 (§6.2.2, p.184).[^linstedt2016] #hypothesis — 하드웨어 성능으로 조인 비용이 흡수되는 환경이라면 보조 구조는 유지비만 남긴다는 취지로 읽히나, 기준이 제시되지는 않는다.

[^linstedt2016]: Linstedt & Olschimke 2016, 6장 "Advanced Data Vault Modeling"
