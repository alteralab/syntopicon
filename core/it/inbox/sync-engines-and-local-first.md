하나의 질문: **인터넷 연결이 끊긴 동안에도 읽고 써야 하는 앱은 복제를 어떻게 하는가.**

## 기기 하나가 리전 하나다

- 다중 리더 복제는 **인터넷 연결이 끊긴 동안에도 계속 동작해야 하는 애플리케이션에도 적절하다.**
  예로 휴대폰·노트북 등 여러 기기의 캘린더 앱을 보자 — **인터넷 연결 여부와 무관하게 언제든 회의를
  보고(읽기 요청) 새 회의를 입력(쓰기 요청)할 수 있어야 하고, 오프라인 중의 변경은 기기가 다음에
  온라인일 때 서버·다른 기기와 동기화돼야 한다** (6장, p.220).[^kleppmann2026]
- 이 경우 **모든 기기가 쓰기 요청을 받는 리더 역할의 로컬 데이터베이스 레플리카를 갖고, 캘린더
  레플리카들 사이에 비동기 다중 리더 복제 프로세스(sync)가 있다. 복제 지연은 인터넷 접속 가능
  시점에 따라 몇 시간이나 며칠일 수 있다** (6장, p.220).[^kleppmann2026]
- 아키텍처 관점에서 **이 구성은 리전 사이의 다중 리더 복제와 매우 유사하되 극단으로 간 것**이다 —
  **각 기기가 "리전"이고 그 사이의 네트워크 연결은 극도로 불안정하다** (6장,
  p.220).[^kleppmann2026]

## 실시간 협업도 같은 구조다

- 많은 현대 웹앱이 **실시간 협업(real-time collaboration)** 기능을 제공한다 — 문서·스프레드시트의
  구글 독스·시트, 그래픽의 피그마, 프로젝트 관리의 리니어. **이 앱들의 반응성은 사용자 입력이 서버
  왕복을 기다리지 않고 즉시 UI에 반영되고, 한 사용자의 편집이 협업자에게 낮은 지연으로 보이는 데서
  온다** (6장, pp.220–221).[^kleppmann2026]
- 이 역시 **다중 리더 아키텍처**로 귀결된다 — **공유 파일을 연 각 브라우저 탭이 레플리카이고, 파일에
  가한 갱신은 같은 파일을 연 다른 사용자의 기기로 비동기 복제된다. 오프라인 편집을 허용하지 않는
  앱이라도 여러 사용자가 서버 응답을 기다리지 않고 편집할 수 있다는 사실만으로 이미 다중 리더다**
  (6장, p.221).[^kleppmann2026]
- **오프라인 편집과 실시간 협업은 비슷한 복제 인프라를 요구한다.** 애플리케이션은 **사용자가 파일에
  가한 변경을 포착해 즉시 협업자에게 보내거나(온라인) 나중에 보내려고 로컬에 저장해야 하고(오프라인),
  협업자의 변경을 받아 사용자의 로컬 사본에 병합하고 UI를 최신 버전으로 갱신해야 한다. 여러 사용자가
  동시에 파일을 바꿨으면 그 변경을 병합하는 충돌 해소 로직이 필요할 수 있다** (6장,
  p.221).[^kleppmann2026]

## 싱크 엔진·오프라인 우선·로컬 우선

- **이 과정을 지원하는 소프트웨어 라이브러리를 싱크 엔진(sync engine)이라 한다.** 아이디어 자체는
  오래됐지만 용어는 최근에야 주목받았다 (6장, p.221).[^kleppmann2026]
- 세 용어의 구분 (6장, p.221):[^kleppmann2026]
  - **오프라인 우선(offline-first)** — 사용자가 오프라인에서 파일 편집을 계속할 수 있는 애플리케이션.
    싱크 엔진으로 구현될 수 있다.
  - **로컬 우선 소프트웨어(local-first software)** — **오프라인 우선일 뿐 아니라, 그 소프트웨어를
    만든 개발자가 자기 온라인 서비스를 전부 닫아도 계속 동작하도록 설계된 협업 앱.** 여러 서비스
    제공자가 존재하는 개방 표준 싱크 프로토콜의 싱크 엔진을 써서 달성할 수 있다.
  - 예시 — **깃은(실시간 협업은 지원하지 않지만) 깃허브·깃랩 등 어느 저장소 호스팅 서비스로도 동기화할
    수 있으므로 로컬 우선 협업 시스템이다.**

## 싱크 엔진의 이점과 한계

- 대비되는 기준선: **오늘날 웹앱을 만드는 지배적 방식은 클라이언트에 영속 상태를 거의 두지 않고 새
  데이터가 필요하거나 갱신될 때마다 서버에 요청하는 것**이다. **싱크 엔진을 쓰면 클라이언트에 영속
  상태가 있고 서버와의 통신은 백그라운드 프로세스로 옮겨진다** (6장, p.221).[^kleppmann2026]
- 이점 넷 (6장, pp.221–222):[^kleppmann2026]
  - **데이터를 로컬에 두면 서비스 호출을 기다릴 때보다 UI가 훨씬 빨리 반응한다.** 어떤 앱은 **그래픽
    시스템의 다음 프레임 안에 사용자 입력에 응답하는 것을 목표로 하며, 이는 60Hz 디스플레이에서
    16ms 안에 렌더링하는 것을 뜻한다.**
  - **오프라인에서 계속 작업할 수 있게 하는 것은 특히 간헐적 연결의 모바일 기기에서 가치 있다.**
    싱크 엔진이 있으면 **앱이 별도의 오프라인 모드를 둘 필요가 없다 — 오프라인은 매우 큰 네트워크
    지연과 같기 때문이다.**
  - **프런트엔드 앱의 프로그래밍 모델이 단순해진다.** 애플리케이션 코드에서 명시적 서비스 호출을 하면
    **모든 서비스 호출이 에러 처리를 요구한다**(서버 데이터 갱신 요청이 실패하면 UI가 그 에러를
    어떻게든 반영해야 한다). **싱크 엔진은 앱이 로컬 데이터에 읽고 쓰게 하며 이 연산은 거의 실패하지
    않으므로 더 선언적인 프로그래밍 스타일로 이어진다.**
  - **다른 사용자의 편집을 실시간으로 표시하려면 그 편집 알림을 받아 UI를 효율적으로 갱신해야 하는데,
    반응형 프로그래밍(reactive programming) 모델과 결합한 싱크 엔진이 이를 구현하는 좋은 방법이다.**
- 적용 한계는 데이터 양이다 — **싱크 엔진은 사용자가 필요할 수 있는 모든 데이터가 미리 다운로드돼
  클라이언트에 영속 저장될 때 가장 잘 작동한다.** 필요할 때 오프라인 접근이 가능하다는 뜻이지만,
  **사용자가 매우 큰 양의 데이터에 접근할 수 있으면 싱크 엔진이 적합하지 않다는 뜻이기도 하다.**
  예컨대 **사용자가 만든 모든 파일을 내려받는 것은 괜찮지만(한 사용자가 그렇게 많이 만들지 않는다)
  이커머스 웹사이트의 전체 카탈로그를 내려받는 것은 말이 되지 않는다** (6장,
  p.222).[^kleppmann2026]

## 계보와 이웃 분야

- **싱크 엔진은 1980년대 로터스 노츠가 개척했다**(그 용어를 쓰지는 않았다). **캘린더처럼 특정 앱에
  한정된 sync도 오래 존재했다.** 오늘날에는 범용 싱크 엔진이 많다 — **독점 백엔드 서비스를 쓰는
  것**(구글 파이어스토어·Realm·Ditto)과 **오픈소스 백엔드를 가져 로컬 우선 소프트웨어를 만들기에
  적합한 것**(PouchDB/CouchDB·Automerge·Yjs)이 있다 (6장, p.222).[^kleppmann2026]
- **멀티플레이어 비디오 게임도 비슷한 필요를 갖는다** — 사용자의 로컬 동작에 즉시 반응하고 네트워크로
  비동기 수신한 다른 플레이어의 동작과 조화시켜야 한다. **게임 개발 용어로 싱크 엔진에 해당하는
  것은 넷코드(netcode)** 다. 다만 **넷코드의 기법은 게임의 요구에 꽤 특수해 다른 종류의 소프트웨어로
  직접 이어지지 않으므로 이 책은 더 다루지 않는다** (6장, p.222).[^kleppmann2026]
