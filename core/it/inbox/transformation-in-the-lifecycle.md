하나의 질문: **반입해 저장한 데이터를 실제로 쓸 수 있는 것으로 바꾸는 일은 수명 주기의 어디에
얼마나 흩어져 있는가.**

## 가치가 시작되는 자리

- 정의 — **데이터를 반입하고 저장한 뒤에는 그것으로 무언가를 해야 한다. 데이터 엔지니어링
  수명 주기의 다음 단계는 변환(transformation)이며, 데이터가 원래 형태에서 하류
  유스케이스에 유용한 무언가로 바뀌어야 한다는 뜻이다** (2장, p.43).[^reis2022]
- 없으면 어떻게 되나 — **적절한 변환이 없으면 데이터는 무기력하게 앉아 있을 뿐이고 리포트·
  분석·ML에 유용한 형태가 아니다. 보통 변환 단계는 데이터가 하류 사용자 소비를 위한 가치를
  만들기 시작하는 자리다** (2장, p.43).[^reis2022]
- 층위 — **반입 직후의 기본 변환은 데이터를 올바른 타입으로 매핑하고(예컨대 반입된 문자열
  데이터를 수치·날짜 타입으로 바꾸기), 레코드를 표준 형식에 넣고, 나쁜 레코드를 제거한다.
  이후 단계의 변환은 데이터 스키마를 변환하고 정규화를 적용할 수 있다. 하류에서는 리포팅을
  위한 대규모 집계를 적용하거나 ML 프로세스를 위해 데이터를 피처화할 수 있다** (2장,
  p.43).[^reis2022]

## 변환 단계의 고려 사항

- 저자들이 꼽는 세 질문 (2장, p.43):[^reis2022]
  - **변환의 비용과 투자 수익(ROI)은 얼마인가? 관련된 업무 가치는 무엇인가?**
  - **변환이 가능한 한 단순하고 자기 완결적(self-isolated)인가?**
  - **변환이 어떤 업무 규칙을 뒷받침하는가?**
- 두 양식 — **배치로 변환할 수도 있고 스트리밍 중 인플라이트로 변환할 수도 있다. 사실상 모든
  데이터는 연속 스트림으로 삶을 시작하며 배치는 데이터 스트림을 처리하는 특화된 방식일
  뿐이다. 배치 변환이 압도적으로 인기 있지만, 스트림 처리 해법의 인기가 커지고 스트리밍
  데이터의 양이 전반적으로 늘고 있으므로 우리는 스트리밍 변환의 인기가 계속 커져 어쩌면
  특정 도메인에서는 머지않아 배치 처리를 완전히 대체하리라 기대한다** (2장,
  p.43).[^reis2022]

## 독립된 단계가 아니다

- **논리적으로 우리는 변환을 데이터 엔지니어링 수명 주기의 독립된 영역으로 취급하지만, 실제
  수명 주기의 현실은 훨씬 복잡할 수 있다. 변환은 흔히 수명 주기의 다른 국면에 얽혀 있다.
  보통 데이터는 원천 시스템에서, 또는 반입 도중 인플라이트로 변환된다** (2장,
  p.43).[^reis2022]
- 실물 두 가지 — **원천 시스템이 레코드를 반입 프로세스로 넘기기 전에 이벤트 타임스탬프를
  더할 수 있다. 또는 스트리밍 파이프라인 안의 레코드가 데이터 웨어하우스로 보내지기 전에
  추가 필드와 계산으로 "풍부해질(enriched)" 수 있다** (2장, p.43).[^reis2022]
- **변환은 수명 주기의 여러 부분에 편재한다. 데이터 준비(data preparation), 데이터
  랭글링(data wrangling), 정제 — 이 변환적 과업들이 데이터의 최종 소비자에게 가치를 더한다**
  (2장, p.43).[^reis2022]

## 업무 로직이 주된 동인이다

- **업무 로직(business logic)은 데이터 변환의 주된 동인이며, 흔히 데이터 모델링에서 그렇다.
  데이터는 업무 로직을 재사용 가능한 요소로 번역한다(예컨대 판매는 "누군가가 나에게서 액자
  12개를 각 $30에, 총 $360에 샀다"를 뜻한다)** (2장, pp.43–44).[^reis2022]
- 왜 모델링이 필요한가 — **데이터 모델링은 업무 프로세스에 대한 명확하고 현재적인 그림을
  얻는 데 결정적이다. 원시 소매 트랜잭션의 단순한 뷰는 CFO가 재무 건전성의 명확한 그림을
  얻도록 회계 규칙의 로직을 더하지 않으면 유용하지 않을 수 있다. 변환 전반에 걸쳐 업무
  로직을 구현하는 표준적 접근을 확보하라** (2장, p.44).[^reis2022] 그 모델링의 방법론 축은
  [데이터 웨어하우스 모델링](../synthesis/data-warehouse-modeling.md)에 있다.

## ML 피처화

- **ML을 위한 데이터 피처화(featurization)는 또 하나의 데이터 변환 프로세스다. 피처화는 ML
  모델 학습에 유용한 데이터 피처를 추출하고 강화하는 것을 의도한다. 피처화는 도메인
  전문성(어떤 피처가 예측에 중요할지 식별하는)과 데이터 과학의 폭넓은 경험을 결합하는
  흑마술일 수 있다** (2장, p.44).[^reis2022]
- 데이터 엔지니어의 몫 — **이 책에서 요점은, 데이터 과학자가 데이터를 어떻게 피처화할지
  정하고 나면 피처화 프로세스는 데이터 파이프라인의 변환 단계에서 데이터 엔지니어가
  자동화할 수 있다는 것이다** (2장, p.44).[^reis2022]

## 변환은 질의와 무엇이 다른가

8장이 이 단계를 다시 열고, 2장이 하지 않은 일을 한다 — **변환을 질의와 구별하는 두 기준**을
세우는 것이다.

- 저자들이 인용으로 여는 문장 (8장, p.309, Bill Inmon 인용):[^reis2022]

  > The net result of transforming data is the ability to unify and integrate data. Once data
  > is transformed, the data can be viewed as a single entity. But without transforming data,
  > you cannot have a unified view of data across the organization.

- 왜 변환이 필요한가 — **질의와 데이터 모델링을 다뤘으니, 데이터를 모델링하고 질의해 결과를 얻을
  수 있다면 왜 변환을 생각해야 하는지 궁금할 수 있다. 변환은 하류 사용을 위해 데이터를 조작하고
  향상시키고 저장해, 확장 가능하고 신뢰할 만하고 비용 효율적인 방식으로 그 가치를 높인다** (8장,
  p.309).[^reis2022]
- 그 절박함의 실물 — **특정 데이터셋의 결과를 볼 때마다 질의를 돌린다고 상상해 보라. 하루에 같은
  질의를 수십 번 또는 수백 번 돌릴 것이다. 이 질의가 20개 데이터셋에 걸쳐 파싱·정제·조인·유니온·
  집계를 수반한다고 상상해 보라. 고통을 더 악화시키자면 그 질의가 도는 데 30분이 걸리고 상당한
  자원을 소비하며 여러 번 반복하면 상당한 클라우드 요금을 발생시킨다. 당신과 이해관계자들은 아마
  미쳐 버릴 것이다. 고맙게도 질의 결과를 저장하거나, 적어도 가장 컴퓨트 집약적인 부분만 한 번 돌려
  후속 질의를 단순화할 수 있다** (8장, p.309).[^reis2022]
- **첫째 기준 — 영속성** — **변환은 질의와 다르다. 질의(query)는 필터와 조인 로직에 기반해 다양한
  원천에서 데이터를 회수한다. 변환(transformation)은 추가 변환이나 질의가 소비할 수 있도록 결과를
  영속시킨다(persists). 이 결과는 일시적으로 또는 영구적으로 저장될 수 있다** (8장,
  p.309).[^reis2022]
- **둘째 기준 — 복잡성** — **영속성 외에 변환을 질의와 구별하는 둘째 측면이 복잡성이다. 여러 원천의
  데이터를 결합하고 여러 최종 출력을 위해 중간 결과를 재사용하는 복잡한 파이프라인을 짓게 될 가능성이
  크다. 이 복잡한 파이프라인은 데이터를 정규화하거나 모델링하거나 집계하거나 피처화할 수 있다. 공통
  테이블 표현식·스크립트·DAG를 써서 단일 질의로 복잡한 데이터플로를 지을 수는 있지만, 이는 빠르게
  다루기 힘들고 일관성 없고 난해해진다. 변환의 등장이다** (8장, p.309).[^reis2022]
- 그리고 오케스트레이션에 의존한다 — **변환은 이 책의 주요 저류 중 하나에 결정적으로 의존한다:
  오케스트레이션이다. 오케스트레이션은 많은 이산 연산 — 하류 변환이나 서빙이 소비하도록 데이터를
  일시적 또는 영구적으로 저장하는 중간 변환 같은 — 을 결합한다. 점점 변환 파이프라인은 여러 테이블과
  데이터셋뿐 아니라 여러 시스템에 걸친다** (8장, p.309).[^reis2022]

## 배치 변환의 부품들

- 정의 — **배치 변환(batch transformations)은 데이터가 도착하는 대로 연속적으로 처리되는 스트리밍
  변환과 대조적으로 이산 데이터 덩어리에 대해 돈다. 배치 변환은 진행 중 리포팅·분석·ML 모델을
  지원하기 위해 고정된 일정(예: 매일·매시간·15분마다)으로 돌 수 있다** (8장, p.310).[^reis2022]
- **분산 조인** — **분산 조인 뒤의 기본 발상은 논리 조인(질의 로직이 정의하는 조인)을 클러스터의
  개별 서버에서 도는 훨씬 작은 노드 조인으로 쪼개야 한다는 것이다. 기본 분산 조인 패턴은
  MapReduce·BigQuery·Snowflake·Spark 어디에 있든 적용되지만 처리 단계 사이 중간 저장의 세부는
  다르다(디스크냐 메모리냐). 최선의 시나리오에서 조인 한쪽의 데이터는 단일 노드에 들어갈 만큼
  작다(브로드캐스트 조인). 흔히 더 자원 집약적인 셔플 해시 조인이 필요하다** (8장,
  p.310).[^reis2022] 두 조인의 상세는
  [배치 조인과 그룹핑](../concepts/batch-joins-and-grouping.md)에 있다.
- **ETL과 ELT의 자리** — **3장에서 논했듯 관계형 데이터베이스 초창기로 거슬러 가는 널리 퍼진 변환
  패턴이 배치 ETL이다. 전통적 ETL은 대상 스키마 — 데이터 마트나 킴벌 스타 스키마 같은 — 를 준비하는
  동안 데이터를 당기고 변환하고 정제하기 위해 외부 변환 시스템에 의존한다. 변환된 데이터는 그다음
  업무 분석이 수행될 수 있는 데이터 웨어하우스 같은 대상 시스템으로 적재된다** (8장,
  p.311).[^reis2022]
  - 왜 그 패턴이었나 — **ETL 패턴 자체는 원천과 대상 시스템 양쪽의 한계에 의해 추동됐다. 추출
    단계가 주요 병목이기 쉬웠고 원천 RDBMS의 제약이 데이터를 당길 수 있는 속도를 제한했다. 그리고
    변환은 전용 시스템에서 다뤄졌는데 대상 시스템이 저장과 CPU 용량 양쪽에서 극도로 자원 제약적이었기
    때문이다** (8장, p.312).[^reis2022]
  - ELT의 두 판본 — **이제 인기 있는 ETL의 진화가 ELT다. 데이터 웨어하우스 시스템이 성능과 저장
    용량에서 자라면서, 원천 시스템에서 원시 데이터를 그냥 추출해 최소한의 변환으로 데이터 웨어하우스에
    임포트한 뒤 웨어하우스 시스템에서 직접 정제하고 변환하는 것이 흔해졌다** (8장,
    p.312).[^reis2022] **둘째의 약간 다른 ELT 개념은 데이터 레이크의 출현과 함께 대중화됐다. 이
    판본에서 데이터는 적재되는 시점에 변환되지 않는다. 실제로 방대한 양의 데이터가 아무 준비 없이,
    아무 계획 없이 적재될 수 있다. 가정은 변환 단계가 미정의 미래 시점에 일어나리라는 것이다.
    계획 없이 데이터를 반입하는 것은 데이터 늪을 위한 훌륭한 레시피다** (8장, p.312).[^reis2022]
  - 인몬의 반대 인용 (8장, p.312, Inmon 인용):[^reis2022]

    > I've always been a fan of ETL because of the fact that ETL forces you to transform data
    > before you put it into a form where you can work with it. But some organizations want to
    > simply take the data, put it into a database, then do the transformation.… I've seen too
    > many cases where the organization says, oh we'll just put the data in and transform it
    > later. And guess what? Six months later, that data [has] never been touched.

  - **저자들의 처방은 낱말의 적용 수준을 낮추는 것이다** — **레이크하우스 환경에서 ETL과 ELT의 선이
    다소 흐려질 수 있음도 보았다. 오브젝트 저장을 기반 계층으로 쓰면 무엇이 데이터베이스 안이고
    밖인지가 더는 분명하지 않다. 데이터 연합·가상화·라이브 테이블의 출현으로 모호성은 더 악화된다.
    점점 우리는 ETL과 ELT라는 용어가 (조직 전체의 변환 패턴을 서술하는) 매크로 수준이 아니라 (개별
    변환 파이프라인 안의) 마이크로 수준에만 적용돼야 한다고 느낀다. 조직은 더 이상 ETL이나 ELT로
    표준화할 필요가 없고, 대신 데이터 파이프라인을 지으면서 건별로 적절한 기법을 적용하는 데 집중할
    수 있다** (8장, p.312).[^reis2022]
    - **이것이 이 KB의 ETL·ELT 서술 전체에 걸리는 판정**이다. 웨어하우스 쪽의 정의는
      [엔터프라이즈 데이터 웨어하우스](../concepts/enterprise-data-warehouse.md)에,
      스트리밍 파이프라인 쪽은
      [데이터 파이프라인 설계 고려사항](../concepts/kafka-data-pipeline-considerations.md)에
      있는데, 8장은 그 대립 자체를 **조직 표준의 문제에서 파이프라인별 선택의 문제로 강등**한다.

## SQL이냐 코드냐

- 구분 자체가 낡았다 — **이 시점에서 SQL 기반 변환 시스템과 비SQL 기반 변환 시스템의 구분은 다소
  인위적으로 느껴진다. 하둡 플랫폼에 Hive가 도입된 이래 SQL은 빅데이터 생태계의 일급 시민이 됐다.
  예컨대 Spark SQL은 Apache Spark의 초기 기능이었다. 카프카·플링크·빔 같은 스트리밍 우선 프레임워크도
  기능과 역량은 다양하지만 SQL을 지원한다** (8장, pp.312–313).[^reis2022]
- **SQL 전용 도구와 더 강력한 범용 프로그래밍 패러다임을 지원하는 도구를 대비해 생각하는 것이 더
  적절하다. SQL 전용 변환 도구는 독점과 오픈 소스의 넓은 스펙트럼에 걸쳐 있다** (8장,
  p.313).[^reis2022]
- **SQL은 선언적이지만 복잡한 워크플로를 만들 수 있다** — **우리는 SQL이 "절차적이지 않다"는 이유로
  기각되는 것을 자주 듣는다. 이는 기술적으로 옳다. SQL은 선언적 언어다 — 데이터 처리 절차를 코딩하는
  대신, SQL 작성자는 최종 데이터의 특성을 집합론적 언어로 규정하고, SQL 컴파일러와 옵티마이저가 데이터를
  그 상태로 만드는 데 필요한 단계를 결정한다** (8장, p.313).[^reis2022]
  - **사람들은 때로 SQL이 절차적이지 않으므로 복잡한 파이프라인을 지을 수 없다고 함의한다. 이는
    거짓이다. SQL은 공통 테이블 표현식·SQL 스크립트·오케스트레이션 도구를 써서 복잡한 DAG를 짓는 데
    효과적으로 쓰일 수 있다** (8장, p.313).[^reis2022]
  - 그리고 반대 방향의 관찰 — **분명히 하자면 SQL에는 한계가 있지만, 우리는 엔지니어가 SQL에서 더
    쉽고 효율적으로 될 수 있는 일을 파이썬과 스파크에서 하는 것을 자주 본다** (8장,
    p.313).[^reis2022]
- 스파크 대신 SQL을 언제 쓰지 않는가 — **Spark SQL이나 다른 SQL 엔진 대신 네이티브 스파크나 파이스파크
  코드를 쓸지 결정할 때 스스로에게 다음 질문을 던지라** (8장, p.313):[^reis2022]
  - **1. SQL로 그 변환을 코딩하는 것이 얼마나 어려운가?**
  - **2. 결과 SQL 코드가 얼마나 읽기 좋고 유지보수 가능한가?**
  - **3. 변환 코드의 일부는 조직 전역의 미래 재사용을 위해 커스텀 라이브러리로 밀어 넣어야 하는가?**
  - 1번에 대한 답 — **스파크로 코딩된 많은 변환이 꽤 단순한 SQL 문으로 실현될 수 있다. 반면 변환이
    SQL로 실현 불가능하거나 구현하기 극도로 어색하다면 네이티브 스파크가 더 나은 선택지다. 예컨대
    접미사를 테이블에 넣고 그 테이블과 조인하고 파싱 함수로 접미사를 찾은 뒤 부분 문자열 함수로 단어를
    어간으로 줄여 SQL로 단어 어간 추출을 구현할 수 있을지도 모른다. 그러나 이는 고려할 엣지 케이스가
    무수한 극도로 복잡한 프로세스처럼 들린다. 여기서는 더 강력한 절차적 프로그래밍 언어가 더 맞다**
    (8장, p.313).[^reis2022] **2번은 밀접히 관련된다. 단어 어간 추출 질의는 읽기 좋지도 유지보수
    가능하지도 않을 것이다** (8장, p.313).[^reis2022]
  - 3번에 대한 답 — **SQL의 주요 한계 중 하나는 라이브러리나 재사용 가능한 코드라는 자연스러운 개념을
    포함하지 않는다는 것이다. 예외 하나는 어떤 SQL 엔진이 사용자 정의 함수(UDF)를 데이터베이스 안의
    객체로 유지할 수 있게 해 준다는 것이다. 그러나 이는 배포를 관리할 외부 CI/CD 시스템 없이는 Git
    저장소에 커밋되지 않는다. 나아가 SQL은 더 복잡한 질의 구성 요소의 재사용성에 대한 좋은 개념이
    없다. 물론 재사용 가능한 라이브러리는 스파크와 파이스파크에서 만들기 쉽다** (8장,
    p.314).[^reis2022]
  - 그래도 SQL을 재활용하는 두 방법 — **SQL을 재활용하는 것이 두 방식으로 가능함을 덧붙이겠다. 첫째,
    SQL 질의의 결과를 테이블에 커밋하거나 뷰를 만듦으로써 쉽게 재사용할 수 있다. 이 과정은 흔히
    Airflow 같은 오케스트레이션 도구에서 가장 잘 다뤄지므로 원천 질의가 끝난 뒤 하류 질의가 시작할 수
    있다. 둘째, Data Build Tool(dbt)이 SQL 문의 재사용을 촉진하고 커스터마이징을 쉽게 하는 템플릿
    언어를 제공한다** (8장, p.314).[^reis2022]
  - 스파크 최적화 네 조언 — **네이티브 스파크로 코딩할 때 염두에 둘 최상위 사항 몇 가지** (8장,
    p.314):[^reis2022] **1. 일찍 그리고 자주 필터하라. 2. 핵심 스파크 API에 크게 의존하고 스파크
    네이티브 방식을 이해하는 법을 배우라. 네이티브 스파크 API가 유스케이스를 지원하지 않으면 잘 유지되는
    공개 라이브러리에 의존하려 노력하라. 좋은 스파크 코드는 실질적으로 선언적이다. 3. UDF에 주의하라.
    4. SQL을 섞어 쓰는 것을 고려하라.**
    - 왜 그런가 — **스파크와 다른 코드 중심 처리 프레임워크에서는 SQL 기반 엔진에서 자동으로 처리되는
      최적화의 상당 부분에 코드 작성자가 책임을 지게 된다. 스파크 API는 강력하고 복잡하므로 재배열·
      결합·분해 후보를 식별하기가 그리 쉽지 않다** (8장, p.314).[^reis2022] 그리고 파이스파크에
      대한 단서 — **파이스파크는 스칼라 스파크의 API 래퍼다. 코드는 API를 호출함으로써 JVM에서 도는
      네이티브 스칼라 코드로 작업을 밀어 넣는다. 파이썬 UDF를 돌리면 데이터가 파이썬으로 넘겨지도록
      강제되어 처리가 덜 효율적이다** (8장, p.315).[^reis2022]

## 갱신 패턴

- 왜 문제인가 — **변환이 데이터를 영속시키므로 우리는 흔히 영속된 데이터를 제자리에서 갱신하게 된다.
  데이터를 갱신하는 것은 데이터 엔지니어링 팀의 주요 통점이며, 특히 데이터 엔지니어링 기술 사이를
  전환할 때 그렇다** (8장, p.315).[^reis2022]
- 데이터 레이크의 원죄 — **원래 데이터 레이크 개념이 데이터 갱신을 제대로 고려하지 않았다는 것을
  이 책 전체에서 여러 번 언급했다. 이는 이제 몇 가지 이유로 말이 안 되는 것으로 보인다. 데이터 갱신은
  빅데이터 커뮤니티가 기각했음에도 오랫동안 데이터 변환 결과를 다루는 핵심 부분이었다. 갱신 역량이
  없다는 이유로 상당한 양의 작업을 다시 돌리는 것은 어리석다. 따라서 레이크하우스 개념은 이제 갱신을
  내장한다. 또한 GDPR과 다른 데이터 삭제 표준은 이제 조직이 원시 데이터셋에서도 표적화된 방식으로
  데이터를 삭제할 것을 요구한다** (8장, p.315).[^reis2022]
- 저자들이 드는 패턴들 (8장, pp.316–317):[^reis2022]
  - **잘라내고 다시 적재(truncate and reload) — 잘라내기는 아무것도 갱신하지 않는 갱신 패턴이다.
    그것은 단순히 옛 데이터를 지운다. 잘라내고 다시 적재하는 갱신 패턴에서 테이블은 데이터가 비워지고
    변환이 다시 돌아 이 테이블로 적재되어, 사실상 새 테이블 버전을 생성한다.**
  - **삽입 전용(insert only) — 삽입 전용은 옛 레코드를 바꾸거나 삭제하지 않고 새 레코드를 삽입한다.
    삽입 전용 패턴은 데이터의 현재 뷰를 유지하는 데 쓰일 수 있다 — 예컨대 옛 레코드를 삭제하지 않고
    레코드의 새 버전이 삽입되면 질의나 뷰가 기본 키로 최신 레코드를 찾아 현재 데이터 상태를 제시할 수
    있다.** 그 대가 — **이 접근의 단점은 질의 시점에 최신 레코드를 찾는 것이 계산적으로 극도로 비쌀 수
    있다는 것이다. 대안으로 모든 레코드를 유지하는 구체화 뷰·삽입 전용 테이블과, 서빙을 위한 현재 상태를
    담는 잘라내고 다시 적재하는 대상 테이블을 쓸 수 있다.** 그리고 경고 — **컬럼 지향 OLAP 데이터베이스에
    데이터를 삽입할 때 흔한 문제는 행 지향 시스템에서 전환한 엔지니어가 단일 행 삽입을 쓰려 한다는 것이다.
    이 안티패턴은 시스템에 막대한 부하를 준다. 그것은 데이터가 많은 별도 파일에 쓰이게도 하는데, 이는
    후속 읽기에 극도로 비효율적이며 데이터를 나중에 다시 클러스터링해야 한다. 대신 주기적 마이크로배치나
    배치 방식으로 데이터를 적재할 것을 권한다.** 예외도 든다 — **자주 삽입하지 말라는 조언에 예외를
    언급하겠다: BigQuery와 Apache Druid가 쓰는 향상된 람다 아키텍처로, 스트리밍 버퍼를 컬럼 저장과
    혼성화한다.**
  - **삭제(delete) — 삭제는 원천 시스템이 데이터를 삭제하고 최근 규제 변경을 충족할 때 결정적이다.
    컬럼 시스템과 데이터 레이크에서 삭제는 삽입보다 비싸다.** 하드와 소프트 — **데이터를 삭제할 때
    하드 삭제가 필요한지 소프트 삭제가 필요한지 고려하라. 하드 삭제(hard delete)는 데이터베이스에서
    레코드를 영구히 제거하는 반면 소프트 삭제(soft delete)는 레코드를 "삭제됨"으로 표시한다. 하드
    삭제는 성능상의 이유로(가령 테이블이 너무 커서) 데이터를 제거해야 하거나 그렇게 할 법적·규정 준수
    이유가 있을 때 유용하다. 소프트 삭제는 레코드를 영구히 삭제하고 싶지 않지만 질의 결과에서 걸러
    내고 싶을 때 쓸 수 있다.** 셋째 방식 — **삽입 삭제(insert deletion)는 레코드의 이전 버전을 수정하지
    않고 `deleted` 플래그를 가진 새 레코드를 삽입한다. 이는 삽입 전용 패턴을 따르면서도 삭제를 설명할
    수 있게 한다. 다만 최신 테이블 상태를 얻는 질의가 조금 더 복잡해진다는 점에 유의하라. 이제 중복을
    제거하고 키별로 각 레코드의 최신 버전을 찾고 최신 버전이 `deleted`인 레코드는 보이지 않아야 한다.**
  - **업서트와 병합(upsert/merge) — 이 갱신 패턴 중 업서트와 병합 패턴이 데이터 엔지니어링 팀에
    일관되게 가장 많은 문제를 일으키며, 특히 행 기반 데이터 웨어하우스에서 컬럼 기반 클라우드 시스템으로
    전환하는 사람들에게 그렇다. 업서팅(upserting)은 원천 레코드 집합을 가져와 기본 키나 다른 논리
    조건으로 대상 테이블과의 일치를 찾는다. 키 일치가 일어나면 대상 레코드가 갱신된다(새 레코드로
    대체된다). 일치가 없으면 데이터베이스는 새 레코드를 삽입한다. 병합 패턴은 여기에 레코드를 삭제하는
    능력을 더한다.**
    - 무엇이 문제인가 — **업서트/병합 패턴은 원래 행 기반 데이터베이스를 위해 설계됐다. 행 기반
      데이터베이스에서 갱신은 자연스러운 프로세스다 — 데이터베이스가 문제의 레코드를 조회해 제자리에서
      바꾼다. 반면 파일 기반 시스템은 실제로 제자리 파일 갱신을 지원하지 않는다. 이 시스템들은 모두
      기록 시 복사(COW)를 활용한다. 파일의 한 레코드가 바뀌거나 삭제되면 파일 전체가 새 변경과 함께
      다시 쓰여야 한다** (8장, p.317).[^reis2022]
    - 그래서 초기 빅데이터가 갱신을 거부했다 — **이것이 빅데이터와 데이터 레이크의 초기 채택자들이
      갱신을 거부한 이유의 일부다. 파일과 갱신을 관리하는 것이 너무 복잡해 보였다. 그래서 그들은
      단순히 삽입 전용 패턴을 쓰고 데이터 소비자가 질의 시점이나 하류 변환에서 데이터의 현재 상태를
      결정하리라 가정했다. 실제로는 Vertica 같은 컬럼 데이터베이스가 사용자에게서 COW의 복잡성을
      숨김으로써 제자리 갱신을 오랫동안 지원해 왔다. 그것들은 파일을 스캔하고 관련 레코드를 바꾸고
      새 파일을 쓰고 테이블의 파일 포인터를 바꾼다** (8장, p.317).[^reis2022]
    - 비용의 방향 — **여기서 이해할 핵심이 몇 가지 있다. 분산 컬럼 데이터 시스템이 네이티브 갱신
      명령을 지원하더라도 병합은 비용과 함께 온다 — 단일 레코드를 갱신하거나 삭제하는 성능 영향이 꽤
      클 수 있다. 반면 병합은 큰 갱신 집합에 대해 극도로 성능이 좋을 수 있고 트랜잭션 데이터베이스를
      능가할 수도 있다** (8장, p.317).[^reis2022]
    - COW의 해상도 — **덧붙여 COW가 테이블 전체를 다시 쓰는 일은 거의 없다는 것을 이해하는 것이
      중요하다. 문제의 데이터베이스 시스템에 따라 COW는 다양한 해상도(파티션·클러스터·블록)로 작동할
      수 있다. 성능 좋은 갱신을 실현하려면 필요와 문제 데이터베이스의 내부에 기반해 적절한 파티셔닝·
      클러스터링 전략을 개발하는 데 집중하라** (8장, p.318).[^reis2022]
    - 빈도가 함정이다 — **삽입과 마찬가지로 갱신이나 병합 빈도에 주의하라. 우리는 많은 엔지니어링
      팀이 데이터베이스 시스템을 전환하면서 CDC로부터 준실시간 병합을 옛 시스템에서 하던 그대로 돌리려
      하는 것을 봤다. 그것은 그냥 통하지 않는다. CDC 시스템이 아무리 좋아도 이 접근은 대부분의 컬럼
      데이터 웨어하우스를 무릎 꿇릴 것이다. 우리는 시스템이 갱신에서 몇 주씩 뒤처지는 것을 봤는데,
      단순히 매시간 병합하는 접근이 훨씬 더 말이 됐을 상황이었다** (8장, p.318).[^reis2022]
    - 실시간에 다가가는 길 — **컬럼 데이터베이스를 실시간에 더 가깝게 만드는 다양한 접근을 쓸 수
      있다. 예컨대 BigQuery는 테이블에 새 레코드를 스트리밍 삽입하게 해 준 뒤, 효율적인 준실시간
      중복 제거 테이블 뷰를 제시하는 특화된 구체화 뷰를 지원한다. Druid는 초고속 실시간 질의를 지원하기
      위해 2계층 저장과 SSD를 쓴다** (8장, p.318).[^reis2022]

## 스키마 갱신과 데이터 랭글링

- **스키마 갱신** — **데이터는 엔트로피를 가지며 당신의 통제나 동의 없이 바뀔 수 있다. 외부 데이터
  원천이 스키마를 바꾸거나 애플리케이션 개발 팀이 스키마에 새 필드를 더할 수 있다. 행 기반 시스템에
  대한 컬럼 시스템의 이점 하나는 데이터를 갱신하는 것은 더 어렵지만 스키마를 갱신하는 것은 더 쉽다는
  것이다. 컬럼은 일반적으로 추가·삭제·이름 변경될 수 있다** (8장, p.318).[^reis2022]
  - 그런데도 조직이 문제다 — **이 기술적 개선에도 불구하고 실무적 조직 스키마 관리는 더 도전적이다.
    어떤 스키마 갱신은 자동화될 것인가? (이것이 Fivetran이 원천에서 복제할 때 쓰는 접근이다.) 편리하게
    들리지만 하류 변환이 깨질 위험이 있다** (8장, p.318).[^reis2022]
  - 절차의 질문들 — **직접적인 스키마 갱신 요청 프로세스가 있는가? 데이터 과학 팀이 이전에 반입되지
    않은 원천의 컬럼을 더하려 한다고 하자. 리뷰 프로세스는 어떻게 생겼는가? 하류 프로세스가 깨질
    것인가? (명시적 컬럼 선택 대신 `SELECT *`를 돌리는 질의가 있는가? 이는 일반적으로 컬럼
    데이터베이스에서 나쁜 실천이다.) 변경을 구현하는 데 얼마나 걸릴 것인가? 테이블 포크 — 즉 이
    프로젝트에 특정한 새 테이블 버전 — 를 만드는 것이 가능한가?** (8장, p.318).[^reis2022]
  - 반구조 데이터에 대한 새 선택지 — **반구조 데이터에 흥미로운 새 선택지가 나타났다. 문서 저장소에서
    발상을 빌려, 많은 클라우드 데이터 웨어하우스가 이제 임의의 JSON 데이터를 인코딩하는 데이터 타입을
    지원한다. 한 접근은 원시 JSON을 필드에 저장하면서 자주 접근되는 데이터를 인접한 평탄화된 필드에
    저장하는 것이다. 이는 추가 저장 공간을 쓰지만 평탄화된 데이터의 편의와 고급 사용자를 위한 반구조
    데이터의 유연성을 함께 제공한다. JSON 필드의 자주 접근되는 데이터는 시간이 지나며 스키마에 직접
    더해질 수 있다** (8장, p.318).[^reis2022] **이 접근은 데이터 엔지니어가 자주 바뀌는 스키마를 가진
    애플리케이션 문서 저장소에서 데이터를 반입해야 할 때 극도로 잘 통한다. 데이터 웨어하우스에서 반구조
    데이터를 일급 시민으로 갖는 것은 극도로 유연하며, 데이터가 더는 행과 컬럼에 제약되지 않으므로 데이터
    분석가와 데이터 과학자에게 새 기회를 연다** (8장, p.319).[^reis2022]
- **데이터 랭글링** — **데이터 랭글링(data wrangling)은 지저분하고 기형인 데이터를 유용하고 깨끗한
  데이터로 바꾼다. 이는 일반적으로 배치 변환 프로세스다** (8장, p.319).[^reis2022]
  - 통점의 실물 — **데이터 랭글링은 오랫동안 데이터 엔지니어의 주요 고통이자 고용 안정의 원천이었다.
    예컨대 개발자가 파트너 업체에서 트랜잭션과 인보이스에 관한 EDI 데이터를 받는데, 구조화된 데이터와
    텍스트가 섞여 있을 수 있다. 이 데이터를 랭글링하는 전형적 과정은 먼저 그것을 반입하려 시도하는
    것이다. 데이터가 너무 기형이라 상당한 양의 텍스트 전처리가 관여하는 일이 잦다. 개발자는 데이터를
    단일 텍스트 필드 테이블로 반입하기로 할 수 있다 — 행 전체가 단일 필드로 반입된다. 그다음 개발자는
    데이터를 파싱하고 쪼개는 질의를 쓰기 시작한다. 시간이 지나면서 그들은 데이터 이상과 엣지 케이스를
    발견한다. 결국 그들은 데이터를 대략의 형태로 만든다. 그때에야 하류 변환의 프로세스가 시작될 수
    있다** (8장, p.319).[^reis2022]
  - 랭글링 도구 — **데이터 랭글링 도구는 이 과정의 유의한 부분을 단순화하는 것을 목표로 한다. 이
    도구들은 노코드라고 주장하기 때문에 데이터 엔지니어를 자주 밀어낸다. 우리는 데이터 랭글링 도구를
    기형 데이터를 위한 통합 개발 환경(IDE)으로 생각하는 것을 선호한다. 실무에서 데이터 엔지니어는
    고약한 데이터를 파싱하는 데 너무 많은 시간을 쓴다. 자동화 도구는 데이터 엔지니어가 더 흥미로운
    과업에 시간을 쓰게 해 준다. 랭글링 도구는 엔지니어가 일부 파싱과 반입 작업을 분석가에게 넘길 수
    있게 해 주기도 한다** (8장, p.319).[^reis2022]
  - 작동 방식 — **그래픽 데이터 랭글링 도구는 일반적으로 시각적 인터페이스에 데이터 표본을 제시하며,
    추론된 타입, 분포·이상 데이터·이상치·널을 포함한 통계를 함께 보여 준다. 사용자는 그다음 데이터
    이슈를 고치는 처리 단계를 더할 수 있다. 한 단계는 잘못 타이핑된 데이터를 다루거나 텍스트 필드를
    여러 부분으로 쪼개거나 조회 테이블과 조인하는 지시를 제공할 수 있다** (8장, p.319).[^reis2022]
    **전체 잡이 준비되면 사용자는 전체 데이터셋에 단계를 돌릴 수 있다. 잡은 일반적으로 큰 데이터셋을
    위해 스파크 같은 확장 가능한 데이터 처리 시스템으로 밀린다. 잡이 돈 뒤 그것은 오류와 처리되지
    않은 예외를 반환한다. 사용자는 이 이상치를 다루기 위해 레시피를 더 다듬을 수 있다** (8장,
    p.319).[^reis2022]
  - 권고 — **우리는 지망생과 노련한 엔지니어 모두가 랭글링 도구를 실험해 볼 것을 강력히 권한다.
    주요 클라우드 제공자가 자기 버전의 데이터 랭글링 도구를 팔고 많은 서드파티 선택지가 있다. 데이터
    엔지니어는 이 도구가 자기 일의 특정 부분을 유의하게 간소화한다는 것을 알게 될 수 있다. 조직적으로
    데이터 엔지니어링 팀은 새롭고 지저분한 데이터 원천에서 자주 반입한다면 데이터 랭글링 전문가를
    훈련시키는 것을 고려할 수 있다** (8장, p.319).[^reis2022]

## 업무 로직과 파생 데이터

- 가장 흔한 유스케이스 — **변환의 가장 흔한 유스케이스 중 하나가 업무 로직을 렌더링하는 것이다.
  이 논의를 배치 변환 아래 둔 이유는 이런 유형의 변환이 여기서 가장 자주 일어나기 때문이지만, 스트리밍
  파이프라인에서도 일어날 수 있음에 유의하라** (8장, p.320).[^reis2022]
- 예 — **회사가 여러 특화된 내부 이익 계산을 쓴다고 하자. 한 버전은 마케팅 비용 차감 전 이익을 볼 수
  있고 다른 것은 마케팅 비용을 뺀 뒤의 이익을 볼 수 있다. 이것이 직관적인 회계 연습처럼 보이지만 이
  메트릭들 각각은 렌더링하기 대단히 복잡하다** (8장, p.320).[^reis2022]
  - **마케팅 비용 차감 전 이익은 사기 주문을 설명해야 할 수 있다. 전 영업일에 대한 합리적 이익 추정을
    결정하는 것은, 사기 팀이 의심스러운 주문을 조사하는 동안 다가올 며칠 안에 취소될 주문에 매출과
    이익의 몇 퍼센트가 결국 손실될지 추정하는 것을 수반한다. 데이터베이스에 사기 확률이 높은 주문이나
    자동 취소된 주문을 나타내는 특별한 플래그가 있는가? 업무는 특정 주문에 대한 사기 위험 평가 프로세스가
    완료되기도 전에 일정 비율의 주문이 사기로 취소될 것이라고 가정하는가?** (8장,
    pp.320–321).[^reis2022]
  - **마케팅 비용 차감 후 이익은 앞 메트릭의 모든 복잡성에 더해 특정 주문에 귀속된 마케팅 비용을
    설명해야 한다. 회사가 순진한 귀속 모델 — 예컨대 가격으로 가중된 품목별 마케팅 비용 — 을 갖고 있는가?
    마케팅 비용은 부서별로, 품목 카테고리별로, 또는 가장 정교한 조직에서는 사용자 광고 클릭에 기반해
    개별 품목별로 귀속될 수도 있다** (8장, p.321).[^reis2022]
- 파생 데이터의 정의와 그 비판 — **이런 유형의 리포팅 데이터는 파생 데이터(derived data) —
  데이터 시스템에 저장된 다른 데이터로부터 계산된 데이터 — 의 전형적 예다. 파생 데이터 비판자들은
  파생 메트릭에서 ETL이 일관성을 유지하기 어렵다는 점을 지적할 것이다. 예컨대 회사가 귀속 모델을
  갱신하면 이 변경은 리포팅용 많은 ETL 스크립트로 병합돼야 할 수 있다. (ETL 스크립트는 DRY 원칙을
  깨는 것으로 악명 높다.) 이 ETL 스크립트를 갱신하는 것은 처리 로직과 이전 변경에 대한 도메인 전문성이
  관여하는 수동적이고 노동 집약적인 프로세스다. 갱신된 스크립트는 일관성과 정확성도 검증돼야 한다**
  (8장, p.321).[^reis2022]
- 저자들의 응답 — **우리 관점에서 이는 정당한 비판이지만 반드시 아주 건설적이지는 않은데, 이 경우
  파생 데이터의 대안이 똑같이 불쾌하기 때문이다. 이익 데이터가 이익 로직을 포함해 데이터 웨어하우스에
  저장되지 않으면 분석가들이 자기 리포팅 질의를 돌려야 할 것이다. 업무 로직 변경을 정확히 나타내도록
  복잡한 ETL 스크립트를 갱신하는 것은 압도적이고 노동 집약적인 과업이지만, 분석가들이 리포팅 질의를
  일관되게 갱신하게 만드는 것은 거의 불가능하다** (8장, p.321).[^reis2022]
- 흥미로운 대안 — **흥미로운 대안 하나는 업무 로직을 메트릭 계층(metrics layer)으로 밀되 데이터
  웨어하우스나 다른 도구가 계산적 무거운 일을 하게 하는 것이다. 메트릭 계층은 업무 로직을 인코딩하고
  분석가와 대시보드 사용자가 정의된 메트릭 라이브러리로 복잡한 분석을 짓게 해 준다. 메트릭 계층은
  메트릭에서 질의를 생성해 데이터베이스에 보낸다** (8장, p.321).[^reis2022] 시맨틱·메트릭 계층의
  상세는 [수명 주기의 서빙 단계](../concepts/serving-in-the-lifecycle.md) 쪽에 있다.

## MapReduce 이후 — 메모리로 옮겨 간 처리

- 왜 MapReduce를 여전히 다루는가 — **배치 변환에 대한 어떤 논의도 MapReduce를 건드리지 않고는
  완전할 수 없다. 이는 MapReduce가 요즘 데이터 엔지니어에 의해 널리 쓰이기 때문이 아니다. MapReduce는
  빅데이터 시대를 정의한 배치 데이터 변환 패턴이었고, 데이터 엔지니어가 오늘날 쓰는 많은 분산 시스템에
  여전히 영향을 주며, 데이터 엔지니어가 기본 수준에서 이해하는 것이 유용하다** (8장,
  p.322).[^reis2022] 그 기제는 [MapReduce](../concepts/mapreduce.md)에 있다.
- 무엇이 한계였나 — **구글의 원래 MapReduce 모델은 극도로 강력하지만 이제는 과도하게 경직된 것으로
  여겨진다. 그것은 디스크에서 읽고 디스크로 쓰는 다수의 단명하는 임시 태스크를 활용한다. 특히 중간
  상태가 메모리에 보존되지 않는다 — 모든 데이터는 디스크에 저장하거나 네트워크로 밀어 태스크 사이에서
  전송된다. 이는 상태와 워크플로 관리를 단순화하고 메모리 소비를 최소화하지만, 높은 디스크 대역폭
  활용을 부르고 처리 시간을 늘릴 수도 있다** (8장, pp.322–323).[^reis2022]
- 전제가 바뀌었다 — **MapReduce 패러다임은 마그네틱 디스크 용량과 대역폭이 너무 싸서 데이터에 막대한
  양의 디스크를 던져 초고속 질의를 실현하는 것이 말이 된다는 발상을 중심으로 구성됐다. 이는 어느 정도
  통했다 — MapReduce는 하둡 초기에 데이터 처리 기록을 거듭 세웠다** (8장, p.323).[^reis2022]
- 무엇이 뒤따랐는가 — **그러나 우리는 꽤 오랫동안 포스트 MapReduce 세계에 살아 왔다. 포스트
  MapReduce 처리는 MapReduce를 진정으로 버리지 않는다 — 그것은 여전히 맵·셔플·리듀스의 요소를 포함하지만
  인메모리 캐싱을 허용하기 위해 MapReduce의 제약을 완화한다. RAM이 전송 속도와 탐색 시간에서 SSD와
  HDD보다 훨씬 빠르다는 것을 상기하라. 신중히 선택된 아주 적은 양의 데이터를 메모리에 영속시키는 것만으로도
  특정 데이터 처리 태스크를 극적으로 빠르게 하고 MapReduce의 성능을 완전히 압도할 수 있다** (8장,
  p.323).[^reis2022]
- **예컨대 스파크·BigQuery와 다양한 다른 데이터 처리 프레임워크가 인메모리 처리를 중심으로 설계됐다.
  이 프레임워크들은 데이터를 메모리에 상주하는 분산 집합으로 다룬다. 데이터가 가용 메모리를 넘치면 이는
  디스크로 흘림(spill to disk)을 일으킨다. 디스크는 처리를 위한 2급 데이터 저장 계층으로 다뤄지지만
  여전히 매우 가치 있다** (8장, p.323).[^reis2022]
- 클라우드가 이를 밀었다 — **클라우드는 메모리 캐싱의 더 넓은 채택을 이끄는 요인 중 하나다. 특정
  처리 잡 동안 메모리를 임차하는 것이 하루 24시간 소유하는 것보다 훨씬 효과적이다. 변환을 위해 메모리를
  활용하는 발전은 예측 가능한 미래에 계속 이득을 낼 것이다** (8장, p.323).[^reis2022]

## 변환 단계에 걸리는 저류

- 왜 이 단계에서 특히 결정적인가 — **변환 단계는 데이터가 업무에 유용한 무언가로 변이하고
  변형하는 자리다. 움직이는 부품이 많으므로 저류가 이 단계에서 특히 결정적이다** (8장,
  p.330).[^reis2022]
- **보안** — **질의와 변환은 이질적 데이터셋을 새 데이터셋으로 결합한다. 이 새 데이터셋에 누가
  접근하는가? 누군가 데이터셋에 접근할 수 있다면 데이터셋의 컬럼·행·셀 수준 접근을 계속 통제하라**
  (8장, p.330).[^reis2022]
  - **질의 시점의 데이터베이스에 대한 공격 벡터를 알아 두라. 데이터베이스에 대한 읽기/쓰기 권한은
    엄격히 모니터링되고 통제돼야 한다. 데이터베이스에 대한 질의 접근은 조직의 시스템과 환경에 대한
    접근을 통상 통제하는 것과 같은 방식으로 통제돼야 한다** (8장, pp.330–331).[^reis2022]
  - **자격 증명을 숨겨 두라. 비밀번호·접근 토큰·기타 자격 증명을 코드나 암호화되지 않은 파일에
    복사해 붙이는 것을 피하라. 데이터베이스 사용자명과 비밀번호가 코드베이스에 직접 붙어 있는 코드를
    GitHub 저장소에서 보는 일은 충격적일 만큼 흔하다! 말할 필요도 없이 비밀번호를 다른 사용자와
    공유하지 마라. 마지막으로 보안되지 않았거나 암호화되지 않은 데이터가 공용 인터넷을 가로지르게
    절대 허용하지 마라** (8장, p.331).[^reis2022]
- **데이터 관리** — **데이터 관리는 원천 시스템 단계(그리고 데이터 엔지니어링 수명 주기의 다른 모든
  단계)에서 본질적이지만 변환 단계에서 특히 결정적이다. 변환은 본질적으로 관리돼야 하는 새 데이터셋을
  만든다. 수명 주기의 다른 단계와 마찬가지로 데이터 모델과 변환에 모든 이해관계자를 참여시키고 그들의
  기대를 관리하는 것이 결정적이다. 또한 데이터의 각 업무 정의에 맞는 명명 관례에 모두가 동의하도록
  하라. 적절한 명명 관례는 이해하기 쉬운 필드 이름에 반영돼야 한다. 사용자는 필드가 언제 만들어졌을
  때 무엇을 뜻하는지, 누가 데이터셋을 유지하는지 등에 대한 더 명확한 정보를 데이터 카탈로그에서 확인할
  수도 있다** (8장, p.331).[^reis2022]
  - 정의의 정확성 — **변환 단계에서는 정의적 정확성을 설명하는 것이 핵심이다. 변환이 기대되는 업무
    로직을 지키는가? 점점 변환과 독립적으로 앉는 시맨틱 또는 메트릭 계층이라는 개념이 인기를 얻고
    있다. 런타임에 변환 안에서 업무 로직을 강제하는 대신, 왜 이 정의들을 변환 계층 앞의 독립 단계로
    유지하지 않는가? 아직 이르지만 시맨틱·메트릭 계층이 데이터 엔지니어링과 데이터 관리에서 더
    인기 있고 흔해지리라 기대하라** (8장, p.331).[^reis2022]
  - MDM과 계보 — **변환이 데이터를 변이시키는 것을 수반하므로 쓰고 있는 데이터가 결함이 없고 지상
    진실을 나타내는지 확인하는 것이 결정적이다. 회사에서 MDM이 선택지라면 그 구현을 추구하라. 표준
    차원과 다른 변환은 데이터의 원래 무결성과 지상 진실을 보존하기 위해 MDM에 의존한다** (8장,
    p.331).[^reis2022] **데이터 변환은 잠재적으로 데이터셋이 어떻게 유도됐는지 알기 어렵게 만든다.
    데이터를 변환하면서 데이터 계보(data lineage) 도구가 값을 매길 수 없게 된다. 데이터 계보 도구는
    새 변환을 만들면서 이전 변환 단계를 이해해야 하는 데이터 엔지니어와, 질의를 돌리고 리포트를 지으면서
    데이터가 어디에서 왔는지 이해해야 하는 분석가 양쪽을 돕는다** (8장, p.331).[^reis2022]
  - 규정 준수 — **마지막으로 규정 준수가 데이터 모델과 변환에 어떤 영향을 주는가? 민감 필드가 필요하면
    마스킹되거나 난독화되는가? 삭제 요청에 응답해 데이터를 삭제할 능력이 있는가? 데이터 계보 추적이
    삭제된 데이터에서 유도된 데이터를 보고 원시 원천 하류의 데이터를 제거하기 위해 변환을 다시 돌리게
    해 주는가?** (8장, p.332).[^reis2022]
- **데이터옵스** — **질의와 변환에서 데이터옵스는 두 관심 영역을 갖는다: 데이터와 시스템이다. 이
  영역들의 변경이나 이상에 대해 모니터링하고 경보를 받아야 한다. 데이터 관측 가능성(data
  observability) 분야가 지금 폭발하고 있으며 데이터 신뢰성에 큰 초점이 있다. 데이터 신뢰성
  엔지니어(data reliability engineer)라는 최근의 직함까지 있다** (8장, p.332).[^reis2022]
  - 데이터 쪽 — **데이터를 질의할 때 입력과 출력이 올바른가? 어떻게 아는가? 이 질의가 테이블에
    저장되면 스키마는 올바른가? 데이터의 형상과 min/max 값·널 개수 같은 관련 통계는 어떤가? 입력
    데이터셋과 변환된 데이터셋에 데이터 품질 테스트를 돌려야 하며, 이는 데이터가 상류·하류 사용자의
    기대를 충족하는지 보장한다. 변환에 데이터 품질 이슈가 있으면 이 이슈에 플래그를 세우고 변경을
    롤백하고 근본 원인을 조사할 수 있어야 한다** (8장, p.332).[^reis2022]
  - Ops 쪽 — **시스템은 어떻게 수행되고 있는가? 질의 대기열 길이·질의 동시성·메모리 사용·저장
    활용·네트워크 지연·디스크 I/O 같은 메트릭을 모니터링하라. 메트릭 데이터를 써서 병목과 리팩터링·
    튜닝 후보가 될 성능 나쁜 질의를 찾아내라. 질의가 완벽히 괜찮다면 데이터베이스 자체를 어디에서
    튜닝할지(예컨대 더 빠른 조회 성능을 위해 테이블을 클러스터링) 좋은 감을 얻을 것이다. 또는
    데이터베이스의 컴퓨트 자원을 업그레이드해야 할 수도 있다. 오늘날의 클라우드와 SaaS 데이터베이스는
    시스템을 빠르게 업그레이드(하고 다운그레이드)할 엄청난 유연성을 준다. 데이터 주도적 접근을 취하고
    관측 가능성 메트릭을 써서 질의 이슈인지 시스템 관련 이슈인지 정확히 짚어 내라** (8장,
    p.332).[^reis2022]
  - 비용 프로필의 이동 — **SaaS 기반 분석 데이터베이스로의 전환은 데이터 소비의 비용 프로필을
    바꾼다. 온프레미스 데이터 웨어하우스 시절에는 시스템과 라이선스를 선불로 구매했고 추가 사용 비용이
    없었다. 전통적 데이터 엔지니어가 비싼 구매에서 최대 효용을 짜내기 위해 성능 최적화에 집중했다면,
    소비 기준으로 과금하는 클라우드 데이터 웨어하우스로 일하는 데이터 엔지니어는 비용 관리와 비용
    최적화에 집중해야 한다. 이것이 FinOps의 실천이다** (8장, p.332).[^reis2022] 그쪽은
    [FinOps와 비용 최적화](../concepts/finops-and-cost-optimization.md)에 있다.
- **데이터 아키텍처** — **3장의 좋은 데이터 아키텍처의 일반 규칙이 변환 단계에 적용된다. 내파하지
  않고 데이터를 처리하고 변환할 수 있는 견고한 시스템을 지으라. 반입과 저장에 대한 선택은 신뢰할
  만한 질의와 변환을 수행하는 일반 아키텍처의 능력에 직접 영향을 준다. 반입과 저장이 질의·변환 패턴에
  적절하다면 좋은 상태일 것이다. 반면 질의와 변환이 상류 시스템과 잘 통하지 않으면 고통의 세계가
  기다린다** (8장, p.333).[^reis2022]
  - 실패의 실물 — **예컨대 데이터 팀이 잘못된 일에 잘못된 데이터 파이프라인과 데이터베이스를 쓰는
    것을 자주 본다. 데이터 팀이 실시간 데이터 파이프라인을 RDBMS나 엘라스틱서치에 연결하고 이것을
    데이터 웨어하우스로 쓸 수 있다. 이 시스템들은 대량 집계 OLAP 질의에 최적화돼 있지 않으며 이
    워크로드에서 내파할 것이다. 이 데이터 팀은 자기 아키텍처 선택이 질의 성능에 어떤 영향을 줄지
    분명히 이해하지 못했다** (8장, p.333).[^reis2022]
- **오케스트레이션** — **데이터 팀은 흔히 단순한 시간 기반 스케줄(예: 크론 잡)로 변환 파이프라인을
  관리한다. 이는 처음에는 꽤 잘 통하지만 워크플로가 더 복잡해지면 악몽이 된다. 의존 기반 접근을 써서
  복잡한 파이프라인을 관리하려면 오케스트레이션을 쓰라. 오케스트레이션은 여러 시스템에 걸치는
  파이프라인을 조립하게 해 주는 접착제이기도 하다** (8장, p.333).[^reis2022]
- **소프트웨어 공학** — **변환 코드를 쓸 때 SQL·파이썬·JVM 기반 언어 같은 많은 언어를, 데이터
  웨어하우스에서 분산 컴퓨팅 클러스터까지 그 사이의 모든 것에 이르는 플랫폼에서 쓸 수 있다. 각 언어와
  플랫폼은 자기 강점과 기벽을 가지므로 도구의 모범 사례를 알아야 한다. 예컨대 스파크나 대스크 같은
  분산 시스템이 구동하는 파이썬으로 데이터 변환을 쓸 수 있다. 데이터 변환을 돌릴 때 네이티브 함수가
  훨씬 잘 통할 텐데 UDF를 쓰고 있는가? 우리는 형편없이 작성된 굼뜬 UDF가 내장 SQL 명령으로 교체되어
  즉각적이고 극적인 성능 개선이 일어난 사례를 봤다** (8장, p.333).[^reis2022]
  - **분석 공학의 부상** — **분석 공학의 부상은 소프트웨어 공학 실천을 최종 사용자에게 가져오며,
    코드로서의 분석(analytics as code)이라는 개념을 동반한다. dbt 같은 분석 공학 변환 도구가 인기를
    폭발시켜, 분석가와 데이터 과학자가 DBA나 데이터 엔지니어의 직접 개입 없이 SQL을 써서 데이터베이스
    안 변환을 쓸 수 있게 했다. 이 경우 데이터 엔지니어는 분석가와 데이터 과학자가 쓰는 코드 저장소와
    CI/CD 파이프라인을 세울 책임을 진다. 이는 데이터 엔지니어의 역할에 큰 변화인데, 역사적으로 그들은
    기저 인프라를 짓고 관리하고 데이터 변환을 만들었다. 데이터 도구가 진입 장벽을 낮추고 데이터 팀
    전역에서 더 민주화되면서 데이터 팀의 워크플로가 어떻게 바뀔지 지켜보는 것은 흥미로울 것이다**
    (8장, pp.333–334).[^reis2022]
  - 로우코드 도구에 대한 단서 — **GUI 기반 로우코드 도구를 쓰면 변환 워크플로의 유용한 시각화를
    얻는다. 여전히 무대 뒤에서 무엇이 일어나는지 이해해야 한다. 이 GUI 기반 변환 도구는 흔히 무대
    뒤에서 SQL이나 다른 언어를 생성한다. 로우코드 도구의 요점이 저수준 세부에 관여할 필요를 덜어
    주는 것이지만, 무대 뒤의 코드를 이해하는 것은 디버깅과 성능 최적화에 도움이 된다. 도구가 성능
    좋은 코드를 생성하고 있다고 맹목적으로 가정하는 것은 실수다** (8장, p.334).[^reis2022]
  - 마무리 권고 — **우리는 데이터 엔지니어가 질의와 변환 단계에서 소프트웨어 공학 모범 사례에 특별한
    주의를 기울일 것을 제안한다. 데이터셋에 더 많은 처리 자원을 던지고 싶은 유혹이 들지만, 깨끗하고
    성능 좋은 코드를 쓰는 법을 아는 것이 훨씬 나은 접근이다** (8장, p.334).[^reis2022]
