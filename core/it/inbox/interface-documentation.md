하나의 질문: **인터페이스 주석에는 무엇이 들어가고 무엇이 들어가면 안 되며, 그 경계를 어떻게

## 주석만이 추상을 서술할 수 있다

- 이 절의 규정 — **주석의 가장 중요한 역할 중 하나는 추상을 정의하는 것이다. 4장에서 추상이
  어떤 실체의 단순화된 관점이며 본질적 정보는 보존하되 안전하게 무시할 수 있는 상세는
  생략한다는 것을 상기하라. 코드는 추상을 서술하기에 적합하지 않다; 너무 저수준이고 추상에서
  보이면 안 되는 구현 상세를 포함한다** (13장 §13.5, pp.109–110).[^ousterhout2021]
- 그래서 결론이 강하다 (13장 §13.5, p.110):[^ousterhout2021]

> The only way to describe an abstraction is with comments. If you want code that presents
> good abstractions, you must document those abstractions with comments.

  - [깊은 모듈과 얕은 모듈](../concepts/deep-and-shallow-modules.md)의 깊이 개념이 여기서 문서의 문제가
    된다 — 인터페이스가 구현보다 단순하다는 것을 **보여 주는 물건이 인터페이스 주석**이다.

## 첫 단계 — 인터페이스 주석과 구현 주석을 가른다

- 조문 — **추상을 문서화하는 첫 단계는 인터페이스 주석을 구현 주석과 분리하는 것이다. 인터페이스
  주석은 누군가가 클래스나 메서드를 *쓰기* 위해 알아야 하는 정보를 제공한다; 그것이 추상을
  정의한다. 구현 주석은 클래스나 메서드가 그 추상을 구현하기 위해 내부적으로 *어떻게* 동작하는지
  서술한다. 이 두 종류의 주석을 분리하는 것이 중요한데, 인터페이스의 사용자가 구현 상세에
  노출되지 않게 하기 위해서다** (13장 §13.5, p.110).[^ousterhout2021]
- **그리고 여기서 주석이 설계 진단 장치가 된다** — **더구나 이 두 형태는 서로 달라야 한다.
  인터페이스 주석이 구현까지 서술해야 한다면 그 클래스나 메서드는 얕다. 이것은 주석을 쓰는
  행위가 설계의 질에 대한 단서를 줄 수 있다는 뜻이다; 15장이 이 발상으로 돌아올 것이다**
  (13장 §13.5, p.110).[^ousterhout2021] 전문은
  [주석을 먼저 써라](write-the-comments-first.md)에 있다.

## 클래스 인터페이스 주석이 담는 것

- 규정 — **클래스의 인터페이스 주석은 그 클래스가 제공하는 추상의 고수준 서술을 제공한다**
  (13장 §13.5, p.110).[^ousterhout2021] 저자가 든 실물은 HTTP 서버 클래스의 여섯 줄짜리
  주석으로, 이 클래스로 애플리케이션이 HTTP 요청을 받아 처리하고 응답을 돌려줄 수 있다는 것,
  각 인스턴스가 요청을 받는 특정 소켓에 대응한다는 것, 현재 구현이 단일 스레드이고 한 번에
  요청 하나를 처리한다는 것을 적는다.
- 그 주석이 담은 셋과 담지 않은 것 — **이 주석은 어떤 구현 상세도, 심지어 특정 메서드의 구체도
  없이 클래스의 전체 능력을 서술한다. 또 클래스의 각 인스턴스가 무엇을 나타내는지 서술한다.
  마지막으로 주석은 클래스의 한계를 서술하는데(여러 스레드에서의 동시 접근을 지원하지 않는다),
  이것은 그 클래스를 쓸지 고민하는 개발자에게 중요할 수 있다** (13장 §13.5,
  p.110).[^ousterhout2021]

## 메서드 인터페이스 주석이 담는 다섯

- 두 층위가 섞인다 — **메서드의 인터페이스 주석은 추상을 위한 고수준 정보와 정밀함을 위한
  저수준 상세를 둘 다 포함한다** (13장 §13.5, p.110).[^ousterhout2021]
- 다섯 항목 (13장 §13.5, pp.110–111):[^ousterhout2021]
  - **주석은 보통 호출자가 인지하는 대로의 메서드 동작을 서술하는 한두 문장으로 시작한다;
    이것이 더 높은 층위의 추상이다.**
  - **주석은 각 인수와 (있다면) 반환값을 서술해야 한다. 이 주석들은 아주 정밀해야 하며,
    인수 값에 대한 제약과 인수 사이의 의존을 서술해야 한다.**
  - **메서드에 부수 효과가 있다면 그것은 인터페이스 주석에 문서화돼야 한다. 부수
    효과(side effect)는 시스템의 미래 동작에 영향을 주지만 결과의 일부가 아닌 메서드의
    모든 귀결이다. 예컨대 메서드가 내부 자료 구조에 값을 더하고 그것을 미래의 메서드 호출로
    가져올 수 있다면 이것이 부수 효과다; 파일 시스템에 쓰는 것도 부수 효과다.**
  - **메서드의 인터페이스 주석은 그 메서드에서 나올 수 있는 모든 예외를 서술해야 한다.**
  - **메서드가 호출되기 전에 만족돼야 하는 선행 조건이 있다면 그것도 서술돼야 한다(어쩌면
    다른 메서드가 먼저 호출돼야 한다든가; 이진 탐색 메서드라면 탐색되는 리스트가 정렬돼
    있어야 한다). 선행 조건은 최소화하는 것이 좋은 생각이지만, 남은 것은 반드시 문서화돼야
    한다.**
- **대표 실물이 버퍼 복사 메서드의 주석이다.** 특수 사례의 처리까지 반환값 설명에 흡수한
  형태이고, 이 페이지가 복사해 쓸 만한 유일한 물건이다 (13장 §13.5,
  p.111):[^ousterhout2021]

  ```c
  /**
   * Copy a range of bytes from a buffer to an external location.
   *
   * \param offset
   *     Index within the buffer of the first byte to copy.
   * \param length
   *     Number of bytes to copy.
   * \param dest
   *     Where to copy the bytes: must have room for at least
   *     length bytes.
   *
   * \return
   *     The return value is the actual number of bytes copied,
   *     which may be less than length if the requested range of
   *     bytes extends past the end of the buffer. 0 is returned
   *     if there is no overlap between the requested range and
   *     the actual buffer.
   */
  ```

- 저자의 해설 — **이 주석의 문법(예컨대 `\return`)은 C/C++ 코드에서 주석을 뽑아 웹 페이지로
  컴파일하는 프로그램인 Doxygen의 관례를 따른다. 이 주석의 목표는 개발자가 그 메서드를
  호출하는 데 필요한 모든 정보를 제공하는 것이며, 여기에는 특수 사례가 어떻게 처리되는지도
  포함된다(이 메서드가 10장의 조언을 따라 범위 지정과 관련된 오류를 존재에서 없앤 방식에
  주목하라)** (13장 §13.5, pp.111–112).[^ousterhout2021] 그 조언의 전문은
  [오류를 존재에서 없애기](../concepts/define-errors-out-of-existence.md)에 있다.
- 그리고 두 방향의 요구가 함께 적힌다 — **개발자는 그 메서드를 호출하려고 본문을 읽을 필요가
  없어야 하고, 인터페이스 주석은 그 메서드가 어떻게 구현됐는지에 대한 정보를, 이를테면
  원하는 데이터를 찾으려고 내부 자료 구조를 어떻게 훑는지 같은 것을 전혀 주지 않는다** (13장
  §13.5, p.112).[^ousterhout2021]

## 붉은 깃발 — 구현 문서가 인터페이스를 오염시킨다

- 조문 (13장 §13.5, p.115):[^ousterhout2021]

> **Red Flag: Implementation Documentation Contaminates Interface**
>
> This red flag occurs when interface documentation, such as that for a method, describes
> implementation details that aren't needed in order to use the thing being documented.

- 저자가 든 실물은 `isReady` 메서드의 첫 판 문서다. 그 주석은 이 함수가 **DCFT 모듈로 구현돼
  있고 호출될 때마다 조금씩 진행하며 `getNext()`가 while 루프에서 이것을 호출한다는 것, 그리고
  규칙 기반 접근으로 구현돼 특정 순서로 규칙을 검사한다는 것**을 적는다.
- 진단 — **다시 한번 이 문서화의 대부분, 이를테면 DCFT 언급과 둘째 문단 전체는 구현에 관한
  것이므로 여기 속하지 않는다; 이것은 인터페이스 주석에서 가장 흔한 오류 중 하나다. 구현
  문서화 중 일부는 쓸모 있지만, 그것은 메서드 안으로 들어가서 인터페이스 문서화와 명확히
  분리돼야 한다** (13장 §13.5, p.115).[^ousterhout2021]
- 남은 문제 둘 — **더구나 문서화의 첫 문장이 알아보기 어렵고(`RESULT_READY`가 무슨 뜻인가?)
  중요한 정보 일부가 빠져 있다. 마지막으로 여기서 `getNext`의 구현을 서술할 필요가 없다**
  (13장 §13.5, p.115).[^ousterhout2021]
- 고친 판이 채운 것 — **이 판의 주석은 "ready"가 무슨 뜻인지 더 정밀한 정보를 제공하고,
  색인 조회가 진행하려면 이 메서드가 결국 호출돼야 한다는 중요한 정보를 제공한다** (13장
  §13.5, p.116).[^ousterhout2021]
  - 즉 고친 주석이 **구현을 덜어 낸 만큼 인터페이스를 더했다**. 짧게 만드는 것이 목적이
    아니라 층위를 맞추는 것이 목적이다.

## 무엇이 인터페이스에 속하는가 — 다섯 문항

저자가 분산 저장 시스템의 `IndexLookup` 클래스를 놓고 독자에게 문항을 내고 장 끝에서
답한다. **각 정보에 대해 개발자가 그 클래스를 쓰기 위해 그 정보를 알아야 하는지 자문해
보라**는 것이다 (13장 §13.5, p.113; §13.9, p.120).[^ousterhout2021]

| 정보 | 인터페이스에 속하는가 | 저자의 근거 |
|---|---|---|
| `IndexLookup`이 색인·객체를 가진 서버에 보내는 **메시지의 형식** | 아니오 | **클래스 안에 감춰져야 할 구현 상세다** |
| 객체가 원하는 범위에 드는지 판정하는 **비교 함수**(정수·부동소수점·문자열 중 무엇으로 비교하는가) | 예 | **클래스 사용자가 이 정보를 알아야 한다** |
| 서버에서 색인을 저장하는 데 쓰는 **자료 구조** | 아니오 | **이 정보는 서버 쪽에 캡슐화돼야 한다; `IndexLookup`의 구현조차 이것을 알 필요가 없다** |
| **여러 서버에 요청을 동시에 내보내는지** 여부 | 어쩌면 | **`IndexLookup`이 성능을 높이려고 특별한 기법을 쓴다면 사용자가 성능에 신경 쓸 수 있으므로 문서화가 이에 대한 고수준 정보를 제공해야 한다** |
| **서버 크래시 처리 기제** | 아니오 | **RAMCloud는 서버 크래시에서 자동으로 복구하므로 크래시가 애플리케이션 층 소프트웨어에 보이지 않는다; 따라서 인터페이스 문서화에서 크래시를 언급할 필요가 없다. 크래시가 애플리케이션까지 반영된다면 인터페이스 문서화는 그것이 어떻게 드러나는지 서술해야 할 것이다(크래시 복구가 어떻게 동작하는지의 상세는 아니고)** |

- 마지막 행이 이 표에서 가장 미묘하다 — **오류를 감출 수 있으면 그것은 인터페이스에서도
  사라진다.** [오류를 존재에서 없애기](../concepts/define-errors-out-of-existence.md)의 마스킹이
  문서 층에서 되받히는 자리다.

## 긴 주석을 짧게 고친 실물

- 원래 주석의 문제 둘 (13장 §13.5, p.114):[^ousterhout2021]
  - **첫 문단 대부분이 인터페이스가 아니라 구현에 관한 것이다. 한 예로 사용자는 서버와
    통신하는 데 쓰는 특정 원격 프로시저 호출의 이름을 알 필요가 없다. 첫 문단 후반부가
    가리키는 설정 매개변수는 전부 클래스의 유지보수자에게만 관련되는 private 변수이지
    사용자에게 관련되는 것이 아니다. 이 구현 정보는 전부 주석에서 빠져야 한다.**
  - **주석은 또 뻔한 것들을 여럿 포함한다. 예컨대 사용자에게 `IndexLookup.h`를 include하라고
    말할 필요가 없다: C++ 코드를 쓰는 사람이라면 누구나 이것이 필요하다고 짐작할 수 있다.
    게다가 "필요한 모든 정보를 제공해서"라는 문구는 아무 말도 하지 않으므로 생략할 수 있다.**
- 고친 주석은 두 문단으로, 이 클래스가 색인을 써서 범위 질의를 하는 데 쓰이고 각 인스턴스가
  하나의 범위 질의를 나타낸다는 것, 그리고 `getNext()`와 그 뒤의 접근자를 어떻게 쓰는지를
  적는다.
- **마지막 문단을 남긴 이유가 이 절의 판단이다** — **이 주석의 마지막 문단은 엄밀히 말해
  필요하지 않은데, 대부분 개별 메서드의 주석에 있는 정보를 중복하기 때문이다. 그러나 클래스
  문서화에 그 메서드들이 어떻게 함께 동작하는지 보여 주는 예를 두는 것이 도움이 될 수 있다.
  사용 패턴이 뻔하지 않은 깊은 클래스에서는 특히 그렇다** (13장 §13.5,
  p.114).[^ousterhout2021]
- 무엇을 뺐는지도 명시된다 — **새 주석이 `getNext`의 NULL 반환값을 언급하지 않는다는 데
  주목하라. 이 주석은 각 메서드의 모든 상세를 문서화하려는 것이 아니다; 그것은 독자가
  메서드들이 어떻게 함께 동작하고 각 메서드가 언제 호출될 만한지 이해하도록 돕는 고수준
  정보만 제공한다. 상세는 개별 메서드의 인터페이스 주석을 참조하면 된다. 이 주석은 또 서버
  크래시를 언급하지 않는데, 서버 크래시가 이 클래스의 사용자에게 보이지 않기 때문이다
  (시스템이 자동으로 복구한다)** (13장 §13.5, p.114).[^ousterhout2021]

## 같은 경계를 조직의 조문으로 두는 둘째 소스

**한 대규모 조직의 2020년 자기 보고가 이 페이지의 규칙들을 권고가 아니라 의무로 둔다.**
그 소스의 지위와 규모 전제의 정본은 [소스 메타](../sources/winters2020-swe-at-google.md)이고,
이 KB의 자리는 [문서 유형과 한 문서 한 목적](documentation-types-and-single-purpose.md)이다.

- **격이 다르다.** 이 페이지의 조문은 **설계 원칙**이고, 저쪽은 **거의 모든 코드 파일이
  파일 주석을 담아야 하고 모든 공개 클래스와 구조체가 클래스 주석을, 모든 자유 함수와
  공개 메서드가 함수 주석을 담아야 한다**고 적는다 (10장 §"File comments" ·
  §"Class comments" · §"Function comments").[^winters2020-swe-at-google] **같은 요구를
  조직이 집행하는 규칙으로 두는 것**이고, 그 집행 수단은 같은 책의 다른 장이 갖는다.
- **서식 규약이 독자 모형에서 연역돼 나온다는 것이 저쪽의 구조다.** 저쪽은 문서 독자를
  **찾는 사람(무엇을 원하는지 알고 맞는지 확인하려는 사람)**과 **헤매는 사람(무엇을
  원하는지 모르는 사람)**으로 가르고 (10장 §"Types of
  Audiences"),[^winters2020-swe-at-google] 앞쪽에는 **일관성**이 뒤쪽에는 **명료함**이
  열쇠라고 둔다. 그리고 그 일관성을 구체적 규약으로 내린다 — **클래스 주석은 명사형으로,
  함수 주석은 그 함수가 무엇을 하고 무엇을 돌려주는지를 적는 서술 동사로 시작**하라는
  것이고, **동사로 시작하면 찾는 사람이 동사만 읽으며 API를 훑을 수 있기 때문**이다.
  - **이 페이지가 메서드 주석에 무엇을 담을지를 다섯으로 세운 것과 겨루지 않는다** —
    **이쪽은 무엇을 담는가를 묻고 저쪽은 어떤 말로 시작하는가를 묻는다.** 층이 다르다.
- **저쪽이 명시적으로 기각하는 것이 하나 있다.** 어떤 문서 문체와 생성기가 요구하는
  **반환값·예외 따위를 항목으로 쪼개는 상용구**를 이 회사는 필요하다고 보지 않았고,
  **인위적인 절 경계로 나누지 않은 한 덩어리 산문 주석**이 더 명료할 때가 많다고 적는다
  (10장 §"Function comments").[^winters2020-swe-at-google] **근거는 사후 조건과 매개변수와
  반환값과 예외 상황이 서로 독립이 아니라는 것**이다.
  - **이 KB의 읽기 — 상용구 서식은 항목들이 서로 독립일 때 값을 한다.** 반환값이 매개변수에
    달려 있고 예외가 특정 입력에서만 나는데 셋을 따로 적으면 **그 사이의 관계가 서식에
    의해 지워진다.** **서식이 정보를 나르지 않고 자르는 자리**라는 진단이다.
  - **`contradicts`를 걸지 않았다** — 겨루는 것이 사실이 아니라 서식 선택이다. **다만
    같은 소스 축의 [코드는 뻔해야 한다](obvious-code.md)가 매개변수 상용구 블록의 여백을
    다듬는 실물을 싣는다.** **한 소스가 다듬고 있는 서식을 다른 소스가 없애자고 하는
    자리**라 적어 둔다.
- **이 페이지의 붉은 깃발(구현 문서가 인터페이스를 오염시킨다)이 저쪽에서는 문서 묶음
  사이의 규칙으로 한 층 올라간다.** 저쪽은 **고객을 위한 문서와 제공자를 위한 문서를
  가능한 한 떼어 두라**고 적고, 흔한 실수로 **자기가 내놓는 라이브러리의 참조 API 안에
  설계 결정을 적어 넣는 것**을 지목하며 그런 근거는 설계 문서에 두라고 한다 (10장
  §"Types of Audiences" · §"The Parameters of Good Documentation").[^winters2020-swe-at-google]
  **같은 규칙이 한 주석 안과 문서 묶음 사이라는 두 층위에 걸린다.**
