하나의 질문: **새 헤더 필드를 하나 만들려 할 때, 이름과 값과 문서에 무엇이 걸리는가.**

## 버전 조건

> **버전 조건**: RFC 9110(2022-06, STD 97) 기준. 2026-09-07 시점 이를 갱신하거나 폐기하는
> RFC 없음(datatracker 실측).

## 왜 필드가 가장 널리 쓰이는 확장점인가

- 원전이 한 줄로 못박는다. **HTTP에서 가장 널리 쓰이는 확장점은 새 헤더 필드와 트레일러 필드의
  정의다** (§16.3).[^fielding2022-rfc9110]
- 새 필드는 수신자가 이해할 때 **이미 정의된 필드의 해석을 덮거나 강화하고, 요청 평가에 전제
  조건을 정의하고, 응답의 뜻을 좁힐 수 있다** (§16.3).[^fielding2022-rfc9110]
- 그러나 정의했다고 배포되거나 인식되는 것은 아니다. **대부분의 필드는 수신자가 알아보지 못한
  필드를 안전하게 무시하되 하류로 전달하리라는 기대 위에 설계된다**
  (§16.3).[^fielding2022-rfc9110] 그 전달 요건 자체는
  [HTTP 필드의 문법과 결합](../concepts/http-field-syntax-and-combining.md)에 있다.
- 상대가 그 필드를 이해하는지 알아내는 길도 원전이 적는다. 이전 통신(프로토콜 버전이나 앞선
  메시지에 실린 필드), 특정 미디어 타입의 사용, OPTIONS 요청이나 잘 알려진 URI와의 상호작용이다
  (§16.3).[^fielding2022-rfc9110]

## 필드 이름 레지스트리

- 필드 이름 레지스트리는 HTTP 필드 이름의 이름 공간을 정의하고, **누구나 등록을 요청할 수 있다**
  (§16.3.1).[^fielding2022-rfc9110] 다른 확장점들이 IETF Review를 요구하는 것과 갈리는 자리다.
- 등록 요청에 담기는 정보는 넷이다 (§16.3.1).[^fielding2022-rfc9110]
  - **필드 이름.** §5.1의 field-name 문법을 따라야 하고(MUST), 글자와 숫자와 하이픈으로만 제한하며
    첫 글자는 글자인 편이 좋다(SHOULD).
  - **상태.** `permanent`·`provisional`·`deprecated`·`obsoleted` 중 하나다.
  - **명세 문서.** 잠정 등록에서는 선택이지만 권장된다.
  - **주석**(선택).
- 상태가 배정되는 방식에 규칙이 있다. **표준이 정의한 이름은 `permanent`이고**, 그 밖의 이름도
  전문가가 공동체와 상의해 실제로 쓰이고 있다고 판단하면 `permanent`가 될 수 있다. 나머지는
  `provisional`로 등록되는 편이 좋다 (§16.3.1).[^fielding2022-rfc9110]
- 잠정 항목은 쓰이지 않는다고 판단되면 전문가가 지울 수 있고, 언제든 영구로 바꿀 수도 있다. 널리
  배포되었는데 등록될 기미가 없는 이름은 **제3자가 대신 등록할 수도 있다**
  (§16.3.1).[^fielding2022-rfc9110]

## 새 필드가 문서화해야 하는 것

- 임시로 쓰는 것은 그렇다 쳐도, **넓게 쓰일 필드는 상호운용을 위해 신중히 문서화되어야 한다**고
  원전이 적고 목록을 준다 (§16.3.2).[^fielding2022-rfc9110]
  - 어떤 조건에서 쓸 수 있는가 — 응답에만인가 요청에만인가, 모든 메시지인가, 특정 메서드의 응답에만
    인가.
  - 문맥이 그 의미론을 더 좁히는가 — 특정 요청 메서드나 상태 코드와 함께 쓰일 때.
  - **전달하는 정보의 적용 범위.** 기본은 그 필드가 딸린 메시지 하나뿐이다. 자원의 모든 표현이나
    자원 자체나 더 넓은 범위에 적용하려면 콘텐츠 협상, 적용 기간, 다중 테넌트 서버 배치 같은
    문제를 신중히 고려해야 한다.
  - 중개자가 값을 넣거나 지우거나 고쳐도 되는 조건.
  - **트레일러에 실릴 수 있는가. 기본은 실릴 수 없다.**
  - `Connection` 필드에 이름을 나열해야 하는가 — 곧 hop-by-hop 필드인가.
  - 프라이버시 관련 데이터의 노출 같은 보안 고려가 새로 생기는가.

## 요청 필드에 붙는 셋

- 요청 헤더 필드에는 기본 동작이 맞지 않을 때 문서화해야 할 것이 셋 더 있다
  (§16.3.2).[^fielding2022-rfc9110]
  - **`Vary` 응답 필드에 이름을 나열하는 것이 적절한가** — 원 서버의 콘텐츠 선택 알고리즘이 그
    요청 필드를 쓸 때다.
  - PUT 요청으로 받았을 때 저장되어야 하는 필드인가.
  - **보안상의 이유로 자동 리다이렉션 시 지워져야 하는 필드인가.** 그 절차가
    [리다이렉션 3xx와 메서드 보존](../concepts/http-redirection-status-codes.md)에 있는 다섯
    단계다.

## 이름을 고르는 규칙

- 원칙은 **짧지만 서술적으로**다. 짧으면 쓸데없는 데이터 전송을 피하고, 서술적이면 혼동과 더 넓게
  쓰일 이름에 대한 "자리 차지"를 피한다 (§16.3.2.1).[^fielding2022-rfc9110]
- 쓰임이 제한된 필드는 **그 쓰임을 접두로 붙인 이름이 권장된다.** 원전이 드는 예가 Foo 응용의
  설명 필드를 `Foo-Desc`로 짓는 것이다 — `Description`은 너무 일반적이고 `Foo-Description`은
  쓸데없이 길다 (§16.3.2.1).[^fielding2022-rfc9110]
- 문법이 허용하는 문자와 실제로 통하는 문자가 다르다. **새 필드 이름은 영숫자와 `-`와 `.`로
  스스로를 제한하는 것이 좋고(SHOULD) 글자로 시작하는 것이 좋다**(SHOULD). 원전이 드는 문제 문자가
  밑줄이고, 비HTTP 게이트웨이 인터페이스를 지날 때 문제가 될 수 있다
  (§16.3.2.1).[^fielding2022-rfc9110] 그 위험의 실체는
  [HTTP 보안 고려](../concepts/http-security-considerations.md)의 필드 이름 매핑 절에 있다.
- 오래된 관행 하나를 명시적으로 막는다 (§16.3.2.1).[^fielding2022-rfc9110]

  > Field names ought not be prefixed with "X-"; see [BCP178] for further information.

  **필드 이름에 `X-` 접두를 붙이지 않는 편이 좋다**는 조문이고 근거로 BCP 178을 가리킨다.
- 다른 접두들은 쓰인다. `Accept-`가 여러 콘텐츠 협상 헤더에, `Content-`가 §6.4가 설명하는 자리에
  쓰인다. 다만 **이 접두들은 필드의 목적을 알아보게 돕는 것일 뿐 어떤 자동 처리도 일으키지 않는다**
  (§16.3.2.1).[^fielding2022-rfc9110]

## 값을 설계하는 규칙

- 새 필드 정의의 큰 몫이 값 문법이다 — 송신자가 무엇을 만들어야 하고 수신자가 받은 것에서 의미론을
  어떻게 끌어내야 하는가다 (§16.3.2.2).[^fielding2022-rfc9110]
- 문법을 적을 때는 **이 명세의 ABNF 규칙이나 구조화 필드(RFC 8941)의 규칙을 쓰는 것이 권장된다.**
  요구는 아니다 (§16.3.2.2).[^fielding2022-rfc9110]
- 가장 실무적인 경고가 결합이다. **여러 필드 줄이 합쳐질 때 값이 어떻게 되는지를 신중히 고려하라**는
  것이고, 이유는 송신자가 잘못해서 값을 여러 번 보낼 수 있고 중개자와 HTTP 라이브러리가 결합을
  자동으로 해 버리기 때문이다. 그래서 **값이 하나만 예상되는 필드에도 이 고려가 걸린다**
  (§16.3.2.2).[^fielding2022-rfc9110] 결합 규칙 자체는
  [HTTP 필드의 문법과 결합](../concepts/http-field-syntax-and-combining.md)에 있다.
- 귀결이 콤마 처리다. **콤마를 담는 값은 구분하거나 인코딩하는 것이 좋다** — 인용 문자열 규칙이나
  RFC 8941의 String 타입이나 필드 특정 인코딩으로. 그래야 데이터 안의 콤마가 리스트를 가르는
  콤마와 헷갈리지 않는다 (§16.3.2.2).[^fielding2022-rfc9110]
- 원전이 좋은 예와 나쁜 예를 짝으로 든다 (§16.3.2.2).[^fielding2022-rfc9110]
  - `Content-Type`은 콤마를 인용 문자열 안에서만 허용하므로 값이 여럿 실려도 신뢰할 만하게 파싱된다.
  - **`Location`은 따라 하지 말아야 할 반례다.** URI가 콤마를 담을 수 있어서 콤마를 담은 값 하나와
    값 둘을 신뢰할 만하게 구분할 수 없다.
- 싱글턴 값을 갖는 필드의 저자에게는 하나가 더 걸린다. **원소가 여럿 실려 온 메시지를 어떻게
  다룰지 문서화하는 것이 좋다.** 그 필드를 무시하는 것이 무난한 기본값이지만 늘 옳은 선택은
  아니라고 원전이 적는다 (§16.3.2.2).[^fielding2022-rfc9110]
