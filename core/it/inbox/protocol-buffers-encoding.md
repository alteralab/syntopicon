하나의 질문: **필드 이름을 인코딩에서 빼면 무엇을 얻고, 그 대신 무엇을 영원히 못 바꾸게
되는가.**

## 무엇이고 어떻게 쓰는가

- 정의와 계보 — **프로토콜 버퍼(Protocol Buffers, protobuf)는 구글에서 개발된 이진 인코딩
  라이브러리다. 원래 페이스북에서 개발된 Apache Thrift와 비슷하며, 이 절이 프로토콜 버퍼에 대해
  말하는 것 대부분이 Thrift에도 적용된다** (5장, p.169).[^kleppmann2026]
- 스키마가 필수다 — **프로토콜 버퍼는 인코딩되는 어떤 데이터에도 스키마를 요구한다** (5장,
  p.169).[^kleppmann2026] `userName`·`favoriteNumber`·`interests`를 가진 레코드를 인코딩하려면
  **프로토콜 버퍼 인터페이스 정의 언어(interface definition language, IDL)** 로 스키마를 이렇게
  기술한다 (5장, p.169):[^kleppmann2026]

  ```proto
  syntax = "proto3";

  message Person {
      string user_name = 1;
      int64 favorite_number = 2;
      repeated string interests = 3;
  }
  ```

- 코드 생성이 따라온다 — **프로토콜 버퍼는 위와 같은 스키마 정의를 받아 여러 프로그래밍 언어로 그
  스키마를 구현하는 클래스를 만들어 내는 코드 생성 도구를 함께 제공한다. 애플리케이션 코드는 이
  생성된 코드를 호출해 스키마에 부합하는 레코드를 인코딩하거나 디코딩할 수 있다** (5장,
  p.169).[^kleppmann2026]
- 스키마 언어의 야심이 작다 — **이 스키마 언어는 JSON Schema에 비해 매우 단순하다. 각 레코드의
  필드와 그 타입을 정의하지만 필드의 가능한 값에 대한 다른 제약은 지원하지 않는다** (5장,
  p.169).[^kleppmann2026]

## 필드 이름이 사라진 자리에 번호가 온다

- 크기부터 — **프로토콜 버퍼 인코더로 예제 레코드를 인코딩하면 33바이트가 필요하다** (5장,
  p.169).[^kleppmann2026] MessagePack의 66바이트와 대비된다.
- 무엇이 남고 무엇이 사라졌는가 — **각 필드는 타입 주석(문자열인지 정수인지 등을 나타내는)과, 필요한
  곳에서는 길이 표시(문자열의 길이 같은)를 갖는다. 데이터에 나타나는 문자열(`Martin`·`daydreaming`·
  `hacking`)은 앞서처럼 ASCII(정확히는 UTF-8)로 인코딩된다** (5장, p.169).[^kleppmann2026]
- 결정적 차이 — **이 예에는 필드 이름(`userName`·`favoriteNumber`·`interests`)이 없다. 대신 인코딩된
  데이터는 필드 태그(field tags)를 담는데 이는 숫자(1·2·3)다. 그것들은 스키마 정의에 나타나는
  번호다. 필드 태그는 필드의 별칭 같은 것이다 — 필드 이름을 철자할 필요 없이 우리가 말하는 필드를
  가리키는 간결한 방법이다** (5장, p.170).[^kleppmann2026]
- 더 짜내는 두 가지 — **프로토콜 버퍼는 필드 타입과 태그 번호를 한 바이트에 채워 넣음으로써 공간을
  더 아낀다. 가변 길이 정수(variable-length integers)를 쓴다: 수 1337은 2바이트로 인코딩되며, 각
  바이트의 최상위 비트가 더 올 바이트가 있는지를 나타내는 데 쓰인다(정수를 바이트가 읽히는 대로
  재구성하는 것을 단순화하려고 최하위 7비트가 첫 바이트에 저장된다). 이는 –64에서 63까지의 수가
  1바이트로, –8,192에서 8,191까지가 2바이트로 인코딩된다는 뜻이다. 더 큰 수는 더 많은 바이트를
  쓴다** (5장, p.170).[^kleppmann2026]
- 리스트를 다루는 방식 — **프로토콜 버퍼에는 명시적인 리스트나 배열 데이터타입이 없다. 대신
  `interests` 필드의 `repeated` 수식자가 그 필드가 단일 값이 아니라 값의 리스트를 담음을 나타낸다.
  이진 인코딩에서 리스트 원소는 단순히 같은 레코드 안에서 같은 필드 태그가 반복해 나타나는 것으로
  표현된다** (5장, p.170).[^kleppmann2026]

## 스키마 진화 — 필드 추가

- 이름부터 — **스키마는 필연적으로 시간이 지나며 바뀌어야 한다. 이것을 스키마 진화(schema
  evolution)라 한다** (5장, p.171).[^kleppmann2026]
- 인코딩의 구조가 무엇을 고정하는지 — **인코딩된 레코드는 인코딩된 필드들의 이어 붙임일 뿐이다. 각
  필드는 태그 번호로 식별되고 데이터타입으로 주석이 붙는다. 필드 값이 설정되지 않으면 인코딩된
  레코드에서 그냥 생략된다. 여기서 필드 태그가 인코딩된 데이터의 의미에 결정적임을 알 수 있다.
  인코딩된 데이터가 필드 이름을 결코 참조하지 않으므로 스키마에서 필드의 이름은 바꿀 수 있지만,
  필드의 태그는 바꿀 수 없다 — 그러면 기존에 인코딩된 모든 데이터가 무효가 되기 때문이다** (5장,
  p.171).[^kleppmann2026]
- 전진 호환이 어떻게 나오는가 — **각 필드에 새 태그 번호를 주기만 하면 스키마에 새 필드를 더할 수
  있다. 옛 코드(더한 새 태그 번호를 모르는)가 새 코드가 쓴 데이터를 읽으려 할 때 인식하지 못하는
  태그 번호의 새 필드를 만나면 그냥 그 필드를 무시하면 된다. 데이터타입 주석이 파서에게 몇 바이트를
  건너뛰어야 하는지 알아내게 해 주며 알 수 없는 필드를 보존한다. 이것이 전진 호환을 유지한다:
  옛 코드가 새 코드가 쓴 레코드를 읽을 수 있다** (5장, p.171).[^kleppmann2026] 그 "보존"이
  [알 수 없는 필드를 보존하지 않으면](../concepts/backward-and-forward-compatibility.md#알-수-없는-필드를-보존하지-않으면)
  생기는 데이터 유실을 막는 장치다.
- 후진 호환은 어떻게 나오는가 — **각 필드가 유일한 태그 번호를 갖는 한 새 코드는 언제나 옛 데이터를
  읽을 수 있는데, 태그 번호가 여전히 같은 뜻을 갖기 때문이다. 새 스키마에 필드가 더해졌는데 아직 그
  필드를 담지 않은 옛 데이터를 읽으면 기본값으로 채워진다**(예: 필드 타입이 문자열이면 빈 문자열,
  수면 0) (5장, p.171).[^kleppmann2026]

## 스키마 진화 — 필드 제거와 타입 변경

- 제거는 추가의 거울상이다 — **필드를 제거하는 것은 필드를 더하는 것과 비슷하되 후진·전진 호환의
  걱정이 뒤집힌다. 같은 태그 번호를 결코 다시 쓸 수 없는데, 옛 태그 번호를 포함하는 데이터가 어딘가에
  여전히 쓰여 있을 수 있고 그 필드는 새 코드가 무시해야 하기 때문이다. 과거에 쓰인 태그 번호는 잊히지
  않도록 스키마 정의에서 예약(reserved)할 수 있다** (5장, p.171).[^kleppmann2026]
- 타입 변경은 조건부로 가능하다 — **필드의 데이터타입을 바꾸는 것은 어떤가. 어떤 타입에서는
  가능하지만(세부는 문서를 확인하라) 값이 잘릴 위험이 있다** (5장, p.171).[^kleppmann2026]
- 저자가 든 구체적 사고 — **32비트 정수를 64비트 정수로 바꾼다고 하자. 새 코드는 옛 코드가 쓴
  데이터를 쉽게 읽을 수 있는데, 파서가 빠진 비트를 0으로 채울 수 있기 때문이다. 그러나 옛 코드가 새
  코드가 쓴 데이터를 읽으면 옛 코드는 여전히 32비트 변수로 값을 담고 있다. 디코딩된 64비트 값이
  32비트에 들어가지 않으면 잘린다** (5장, p.171).[^kleppmann2026]
