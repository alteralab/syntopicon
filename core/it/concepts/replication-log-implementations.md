하나의 질문: **리더가 팔로워에 보내는 "데이터 변경"은 실제로 어떤 형식이고, 형식마다
무엇이 대가인가.**

## 문장 기반 복제

- 가장 단순한 경우, **리더는 자기가 실행하는 모든 쓰기 요청(문장, statement)을 로깅하고 그
  문장 로그를 팔로워에 보낸다.** 관계형 데이터베이스라면 모든 `INSERT`·`UPDATE`·`DELETE`
  문장이 팔로워로 전달되고, **각 팔로워가 그 SQL 문장을 클라이언트에게서 받은 것처럼 파싱해
  실행한다** (6장, p.206).[^kleppmann2026]
- 합리적으로 들리지만 여러 방식으로 깨진다 (6장, pp.206–207):[^kleppmann2026]
  - **비결정적 함수를 호출하는 문장** — 현재 날짜·시각을 얻는 `NOW`나 난수를 얻는 `RAND`
    같은 것은 **레플리카마다 다른 값을 만들기 쉽다.**
  - **자동증가 컬럼을 쓰거나 데이터베이스의 기존 데이터에 의존하는 문장**(예:
    `UPDATE … WHERE <조건>`) — **레플리카마다 정확히 같은 순서로 실행돼야 하고, 그러지
    않으면 효과가 달라진다.** 동시에 실행되는 트랜잭션이 여럿일 때 이는 제약이 된다.
  - **부작용이 있는 문장**(트리거·저장 프로시저·사용자 정의 함수) — **부작용이 절대적으로
    결정적이지 않는 한 레플리카마다 다른 부작용이 일어날 수 있다.**
- 우회는 가능하다 — **리더가 비결정적 함수 호출을 고정된 반환값으로 치환해 로깅하면 모든
  팔로워가 같은 값을 얻는다.** 그리고 **결정적 문장을 고정된 순서로 실행한다는 아이디어는
  이벤트 소싱 모델과 유사하며, 이 접근은 상태 기계 복제(state machine replication)라고도
  불린다** (6장, p.207).[^kleppmann2026]
- 실제 채택: **MySQL은 5.1 이전에 문장 기반 복제를 썼다.** 지금도 꽤 간결하기 때문에 때때로
  쓰이지만, **문장에 비결정성이 있으면 MySQL은 이제 행 기반 복제로 전환한다.** VoltDB는 문장
  기반 복제를 쓰면서 **트랜잭션이 결정적일 것을 요구해 안전하게 만든다.** 그러나 **결정성은
  실무에서 보장하기 어려워 많은 데이터베이스가 다른 복제 방법을 선호한다** (6장,
  p.207).[^kleppmann2026]

## WAL 배송

- 4장에서 **B-트리 저장 엔진을 견고하게 만들려면 쓰기 선행 로그(write-ahead log, WAL)가
  필요하다**는 것을 봤다 — **모든 수정이 먼저 WAL에 쓰여 크래시 후 트리를 일관된 상태로
  복원할 수 있게 한다** (6장, p.207).[^kleppmann2026]
- **WAL은 인덱스와 힙을 일관된 상태로 복원하는 데 필요한 모든 정보를 담으므로, 같은 로그를
  써서 다른 노드에 레플리카를 만들 수 있다.** 리더는 로그를 디스크에 쓰는 것에 더해
  **네트워크로 팔로워에게도 보내고, 팔로워가 이 로그를 처리하면 리더에 있는 것과 정확히 같은
  파일 사본을 만든다.** PostgreSQL과 오라클 등이 이 방법을 쓴다 (6장,
  p.207).[^kleppmann2026]
- **주된 단점은 로그가 데이터를 매우 낮은 수준에서 기술한다는 것**이다 — **WAL은 어느 디스크
  블록의 어느 바이트가 바뀌었는지를 담는다.** 그래서 **복제가 저장 엔진에 강하게 결합되고,
  데이터베이스가 저장 포맷을 버전 사이에 바꾸면 리더와 팔로워에서 다른 버전의 소프트웨어를
  돌리는 것이 대개 불가능하다** (6장, p.207).[^kleppmann2026]
- 사소한 구현 세부로 보이지만 운영에 큰 영향이 있다 — **복제 프로토콜이 팔로워가 리더보다 새
  버전의 소프트웨어를 쓰는 것을 허용하면, 팔로워를 먼저 업그레이드한 뒤 페일오버(failover)로
  업그레이드된 노드 하나를 새 리더로 만드는 무중단 업그레이드를 할 수 있다. 버전 불일치를
  허용하지 않으면 (WAL 배송(WAL shipping)이 흔히 그렇다) 그런 업그레이드에는 다운타임이
  필요하다** (6장,
  p.208).[^kleppmann2026]

## 논리 로그 — 행 기반

- 대안은 **복제용 로그 형식과 저장 엔진용 로그 형식을 다르게 쓰는 것**이며, 이렇게 하면
  **복제 로그를 저장 엔진 내부에서 분리할 수 있다.** 이런 종류의 복제 로그를 저장 엔진의
  (물리적) 데이터 표현과 구분해 **논리 로그(logical log)** 라 부른다 (6장,
  p.208).[^kleppmann2026]
- 관계형 데이터베이스의 논리 로그는 보통 **행 단위의 쓰기를 기술하는 레코드의 계열**이다
  (6장, p.208):[^kleppmann2026]
  - **삽입된 행** — 로그는 모든 컬럼의 새 값을 담는다.
  - **삭제된 행** — 로그는 삭제된 행을 유일하게 식별하기에 충분한 정보를 담는다. 보통 기본
    키이고, 테이블에 기본 키가 없으면 모든 컬럼의 옛 값을 로깅해야 한다.
  - **갱신된 행** — 로그는 갱신된 행을 유일하게 식별하기에 충분한 정보와, 모든 컬럼(적어도
    바뀐 모든 컬럼)의 새 값을 담는다.
- 여러 행을 수정하는 트랜잭션은 **그런 로그 레코드를 여러 개 만들고, 뒤이어 트랜잭션이
  커밋됐음을 가리키는 레코드**가 붙는다. **MySQL은 행 기반 복제로 설정되면 WAL에 더해 binlog라는
  별도의 논리 복제 로그를 유지하고, PostgreSQL은 물리 WAL을 행 삽입·갱신·삭제 이벤트로 디코딩해
  논리 복제를 구현한다** (6장, p.208).[^kleppmann2026]
- **논리 로그는 저장 엔진 내부에서 분리돼 있으므로 하위 호환을 유지하기가 더 쉽고, 리더와
  팔로워가 다른 버전의 데이터베이스 소프트웨어를 돌릴 수 있다.** 이것이 다시 **최소 다운타임
  업그레이드를 가능하게 한다** (6장, p.208).[^kleppmann2026]
- **논리 로그 형식은 외부 애플리케이션이 파싱하기도 쉽다.** 데이터베이스 내용을 외부
  시스템으로 보내고 싶을 때 유용하다 — 오프라인 분석용 데이터 웨어하우스나, 커스텀 인덱스·캐시
  구축 전용 시스템 같은 것이다. **이 기법을 변경 데이터 캡처(change data capture)라 한다**
  (6장, p.208).[^kleppmann2026]

## 세 방식이 갈리는 축

- 세 방식을 가르는 축은 결국 **로그가 무엇을 기술하는가**다 — 문장 기반은 **연산**을, WAL
  배송은 **바이트 수준의 물리 변경**을, 논리 로그는 **행 수준의 논리 변경**을 기술한다.
  결정성 요구는 앞으로 갈수록 세지고 저장 엔진 결합은 가운데가 가장 세다 (6장,
  pp.206–208).[^kleppmann2026]
- 카프카의 복제는 이 분류 어디에도 정확히 들어맞지 않는다 — 카프카에서 리더가 팔로워에
  보내는 것은 데이터베이스의 변경 기술이 아니라 **파티션 로그의 메시지 그 자체**이고, 로그가
  곧 데이터이기 때문이다. #hypothesis 이 대응은 두 소스가 직접 적지 않았고 카프카의
  `Fetch` 기반 복제 서술과 위 분류를 맞대어 끌어낸 것이다 —
  [카프카 복제 프로토콜](../concepts/kafka-replication-protocol.md)과
  [카프카 물리 저장](../concepts/kafka-physical-storage.md)이 그 원본 서술이다.
