하나의 질문: **카프카를 외부 데이터 저장소에 이을 때 왜 프로듀서·컨슈머를 직접 쓰지
않으며, 커넥트는 무엇을 대신해 주는가.**

## 버전 조건

> **버전 조건**: Kafka 0.9 이상. **커넥트 API는 0.9 버전에서 아파치 카프카에 추가**됐다
> (9장, p.203).[^shapira2021] 그 이전 릴리스에는 이 페이지의 내용이 적용되지 않는다.
> 아래 REST API 응답 예시는 **3.0.0 프리릴리스 스냅샷**에서 얻은 것이다 (9장,
> p.213).[^shapira2021]

## 언제 클라이언트 대신 커넥트를 쓰는가

- 카프카에 쓰거나 카프카에서 읽을 때 선택지는 둘이다 — **전통적인 프로듀서·컨슈머
  클라이언트**(이 책 3장과 4장)를 쓰거나 **커넥트 API와 커넥터**를 쓰는 것이다 (9장,
  p.210).[^shapira2021] 클라이언트 쪽은
  [프로듀서와 컨슈머](../concepts/producers-and-consumers.md)가 진입점이다.
- **카프카 클라이언트는 자기 애플리케이션에 임베드되는 클라이언트**로, 애플리케이션이
  카프카에 데이터를 쓰거나 읽게 해 준다. **애플리케이션의 코드를 수정할 수 있고,
  카프카로 데이터를 밀어 넣거나 카프카에서 당겨 오려고 할 때 카프카 클라이언트를 쓴다**
  (9장, p.210).[^shapira2021]
- **커넥트는 직접 쓰지 않았고 코드나 API를 수정할 수 없거나 수정하지 않을 데이터 저장소에
  카프카를 연결할 때 쓴다.** **외부 데이터 저장소에서 카프카로 데이터를 당겨 오거나
  카프카에서 외부 저장소로 밀어 넣는 데** 쓰이며, **연결하려는 데이터 저장소용 커넥터가
  필요한데 요즘 커넥터는 풍부하다.** 그래서 **실무에서 카프카 커넥트 사용자는 설정 파일만
  쓰면 된다** (9장, p.210).[^shapira2021]
- 커넥터가 아직 없을 때의 판단 — **카프카 클라이언트로 앱을 짜거나 커넥트 API를 쓰는 것
  중 고를 수 있는데 커넥트가 권장된다.** 이유는 **설정 관리·오프셋 저장·병렬화·오류 처리·
  서로 다른 데이터 타입 지원·표준 REST API 같은 기본 제공 기능**이다. **카프카를 데이터
  저장소에 연결하는 작은 앱을 쓰는 일은 간단해 보이지만 데이터 타입과 설정에 관해 처리해야
  할 자잘한 세부가 많아 사소하지 않고**, 더구나 **그 파이프라인 앱을 유지하고 문서화해야
  하며 팀원들이 쓰는 법을 배워야** 한다. **커넥트는 카프카 생태계의 표준 부분으로 이
  대부분을 대신 처리해 주므로 외부 저장소로 데이터를 나르는 일에 집중**할 수 있다 (9장,
  pp.210–211).[^shapira2021]

## 커넥트란 무엇인가

- 정의는 원문 그대로 (9장, p.211):[^shapira2021]

  > Kafka Connect is a part of Apache Kafka and provides a scalable and reliable way to
  > copy data between Kafka and other datastores.

- 구조 — **커넥트는 데이터를 옮기는 일을 책임지는 커넥터 플러그인(connector plug-in)을
  개발·실행하는 API와 런타임을 제공**한다. **카프카 커넥트는 워커 프로세스(worker process)
  클러스터로 돈다.** **워커에 커넥터 플러그인을 설치한 다음 REST API로 특정 설정을 가진
  커넥터(connector)를 설정·관리**한다. **커넥터는 추가 태스크(task)를 시작해 대량의 데이터를
  병렬로 옮기고 워커 노드의 가용 자원을 더 효율적으로 쓴다** (9장, p.211).[^shapira2021]
- 두 방향의 태스크가 하는 일 — **소스 커넥터 태스크는 소스 시스템에서 데이터를 읽어
  커넥트 데이터 객체를 워커 프로세스에 제공하기만 하면 되고, 싱크 커넥터 태스크는 워커에서
  커넥트 데이터 객체를 받아 타깃 데이터 시스템에 쓰는 것을 책임진다** (9장,
  p.211).[^shapira2021]
- 형식은 컨버터가 담당한다 — **카프카 커넥트는 컨버터(converter)를 써서 그 데이터 객체를
  카프카에 서로 다른 형식으로 저장하는 것을 지원**한다. **JSON 형식 지원은 아파치 카프카의
  일부이고, 컨플루언트 스키마 레지스트리가 에이브로·프로토버프·JSON 스키마 컨버터를
  제공**한다. 그래서 **사용자는 쓰는 커넥터와 독립적으로 카프카에 데이터가 저장되는 형식,
  그리고 (있다면) 데이터의 스키마를 어떻게 다룰지를 고를 수 있다** (9장,
  p.211).[^shapira2021] 부품별 책임의 상세는
  [카프카 커넥트 내부 구조](../concepts/kafka-connect-internals.md)에 있다.
- 범위에 대한 저자들의 못박음 — **이 장은 카프카 커넥트와 그 많은 커넥터의 모든 세부를
  다룰 수 없고 그것만으로 책 한 권이 된다.** 개요와 사용법, 참고 자료 포인터만 준다 (9장,
  p.211).[^shapira2021]

## 커넥트 돌리기 — 워커 설정

- **커넥트는 아파치 카프카와 함께 배포되므로 따로 설치할 필요가 없다.** 다만 **프로덕션
  용도, 특히 커넥트로 대량 데이터를 옮기거나 많은 커넥터를 돌릴 계획이라면 카프카 브로커와
  별도의 서버에서 커넥트를 돌려야** 한다. 그 경우 **모든 기계에 아파치 카프카를 설치하고
  일부 서버에서는 브로커를, 다른 서버에서는 커넥트를 시작**한다 (9장, p.211).[^shapira2021]
- **커넥트 워커를 시작하는 것은 브로커를 시작하는 것과 아주 비슷하다** — 프로퍼티 파일을
  주고 시작 스크립트를 부른다: `bin/connect-distributed.sh config/connect-distributed.properties`
  (9장, p.211).[^shapira2021]
- 커넥트 워커의 핵심 설정들 (9장, pp.212–213):[^shapira2021]
  - `bootstrap.servers` — **커넥트가 함께 일할 카프카 브로커 목록.** **커넥터가 그
    브로커들로 또는 그 브로커들에서 데이터를 파이프**한다. **클러스터의 모든 브로커를
    지정할 필요는 없지만 최소 셋을 권장**한다.
  - `group.id` — **같은 그룹 ID를 가진 모든 워커가 같은 커넥트 클러스터의 일부**다.
    **클러스터에서 시작된 커넥터는 어느 워커에서든 돌고 태스크도 마찬가지**다.
  - `plugin.path` — **카프카 커넥트는 커넥터·컨버터·변환·비밀 제공자를 내려받아 플랫폼에
    추가할 수 있는 플러그인 가능 아키텍처를 쓰므로 커넥트가 그 플러그인들을 찾아 로드할 수
    있어야** 한다. **커넥터와 그 의존성이 있을 위치로 디렉터리를 하나 이상 설정**할 수 있다
    (예: `plugin.path=/opt/connectors,/home/gwenshap/connectors`). **이 디렉터리 안에
    커넥터마다 하위 디렉터리를 만드는 것이 보통**이라 앞의 예에서는 `/opt/connectors/jdbc`와
    `/opt/connectors/elastic`을 만들고, **각 하위 디렉터리에 커넥터 jar 자체와 모든 의존성을
    넣는다.** **커넥터가 uberJar로 배포되고 의존성이 없으면 `plugin.path`에 직접 놓을 수 있고
    하위 디렉터리를 요구하지 않지만, 최상위 경로에 의존성을 놓는 것은 동작하지 않는다.**
    - **대안은 커넥터와 모든 의존성을 카프카 커넥트 클래스패스에 추가하는 것이지만
      권장되지 않는다** — **커넥터가 카프카의 의존성 중 하나와 충돌하는 의존성을 가져오면
      오류를 낼 수 있기 때문**이다. **권장 접근은 `plugin.path` 설정**이다.
  - `key.converter`와 `value.converter` — **커넥트는 카프카에 저장되는 여러 데이터 형식을
    다룰 수 있고, 두 설정이 카프카에 저장될 메시지의 키 부분과 값 부분에 대한 컨버터를
    설정**한다. **기본값은 아파치 카프카에 포함된 `JSONConverter`를 쓰는 JSON 형식**이며,
    **컨플루언트 스키마 레지스트리의 일부인 `AvroConverter`·`Protobuf Converter`·
    `JsonSchemaConverter`로도 설정**할 수 있다.
    - **어떤 컨버터는 컨버터 특유의 설정 매개변수를 포함**하는데, **키 컨버터에 적용할지
      값 컨버터에 적용할지에 따라 `key.converter.` 또는 `value.converter.`를 접두어로**
      붙여야 한다. 예컨대 **JSON 메시지는 스키마를 포함할 수도 스키마리스일 수도 있으므로
      어느 쪽이든 지원하려면 `key.converter.schemas.enable`을 각각 true나 false로**
      설정하고, **값 컨버터에는 `value.converter.schemas.enable`** 을 쓴다. **에이브로
      메시지도 스키마를 포함하지만 `key.converter.schema.registry.url`과
      `value.converter.schema.registry.url`로 스키마 레지스트리 위치를 설정**해야 한다.
  - `rest.host.name`과 `rest.port` — **커넥터는 보통 카프카 커넥트의 REST API로 설정·
    모니터링되며, REST API용 특정 포트를 설정할 수 있다.**
- 확인 절차 — **워커가 뜨고 클러스터가 생기면 REST API를 확인해 잘 돌고 있는지 본다.**
  `curl http://localhost:8083/`으로 **베이스 REST URI에 접근하면 현재 돌고 있는 버전이
  반환**되고, `curl http://localhost:8083/connector-plugins`로 **어떤 커넥터 플러그인이
  가용한지** 확인한다. **순정 아파치 카프카에서는 파일 소스, 파일 싱크, 그리고 미러메이커
  2.0의 일부인 커넥터들만 가용**하다 (9장, pp.213–214).[^shapira2021] 그 미러메이커 쪽
  커넥터들이 무엇인지는 [미러메이커](../concepts/kafka-mirrormaker.md)에 있다.
- **독립 실행 모드(standalone mode)** — **분산 모드와 비슷하되 `bin/connect-distributed.sh`
  대신 `bin/connect-standalone.sh`를 돌린다.** **REST API 대신 명령줄에서 커넥터 설정 파일을
  넘길 수도** 있다. **이 모드에서는 모든 커넥터와 태스크가 그 하나의 독립 실행 워커에서
  돈다.** **커넥터와 태스크가 특정 기계에서 돌아야 하는 경우에 쓴다** — 예컨대 **syslog
  커넥터는 포트를 리스닝하므로 어느 기계에서 돌고 있는지 알아야** 한다 (9장, p.214,
  "Standalone Mode" 박스).[^shapira2021]

## 예제 하나: 파일 소스와 파일 싱크

- **아파치 카프카의 일부인 파일 커넥터와 JSON 컨버터를 쓰는 예제**이며, **따라 하려면
  주키퍼와 카프카가 떠 있어야** 한다. **실제 프로덕션 환경이라면 고가용성을 위해 워커를
  최소 둘 셋 돌리고 싶겠지만 이 예에서는 하나만 시작**한다 (9장, p.214).[^shapira2021]
- **파일 소스**는 **카프카 설정 파일을 읽도록 설정**한다 — **카프카의 설정을 카프카 토픽으로
  파이핑**하는 것이다. 설정은 `connector.class`가 `FileStreamSource`,
  `file`이 `config/server.properties`, `topic`이 `kafka-config-topic`이다 (9장,
  p.214).[^shapira2021]
- 결과 — **콘솔 컨슈머로 보면 `config/server.properties` 파일의 내용이 그대로, 커넥터에
  의해 줄 단위로 JSON으로 변환되어 `kafka-config-topic`에 들어가 있다.** **기본적으로 JSON
  컨버터가 각 레코드에 스키마를 넣는데, 이 경우 스키마는 매우 단순하다 — `payload`라는
  이름의 `string` 타입 단일 컬럼 하나뿐이고 파일의 각 줄을 담는다** (9장,
  p.215).[^shapira2021]
- **파일 싱크**로 그 토픽의 내용을 파일에 덤프하면 **결과 파일은 원본 `server.properties`와
  완전히 동일해야 한다 — JSON 컨버터가 JSON 레코드를 단순 텍스트 줄로 되돌리기 때문**이다
  (9장, p.215).[^shapira2021]
  - 소스 설정과 달라지는 세 곳 — **클래스가 `FileStreamSource`가 아니라 `FileStreamSink`**,
    **`file` 속성이 레코드의 소스가 아니라 목적지 파일을 가리킨다**, 그리고 **`topic` 대신
    `topics`를 지정한다.** **복수형에 주의** — **싱크로는 여러 토픽을 한 파일에 쓸 수 있지만
    소스는 한 토픽에만 쓸 수 있다** (9장, p.216).[^shapira2021]
- 커넥터 삭제는 `curl -X DELETE http://localhost:8083/connectors/dump-kafka-config`다 (9장,
  p.216).[^shapira2021]
- 경고 — **이 예제가 FileStream 커넥터를 쓴 것은 단순하고 카프카에 내장돼 있어 카프카 외에
  아무것도 설치하지 않고 첫 파이프라인을 만들 수 있기 때문**이다. **실제 프로덕션
  파이프라인에는 쓰지 말아야 한다 — 한계가 많고 신뢰성 보장이 없다.** **파일에서 데이터를
  반입하려면 FilePulse Connector·FileSystem Connector·SpoolDir 같은 대안이 여럿** 있다
  (9장, p.216).[^shapira2021]

## 예제 둘: MySQL에서 엘라스틱서치로

- 하는 일 — **MySQL 테이블을 카프카 토픽으로 스트리밍하고, 거기서 엘라스틱서치로 적재해
  내용을 색인**한다. 저자들은 **맥북에서 테스트**했고 `brew install mysql`,
  `brew install elasticsearch`로 설치했다 (9장, p.216).[^shapira2021]
- 커넥터를 얻는 방법 셋 (9장, p.216):[^shapira2021] **Confluent Hub client로 내려받아
  설치**, **Confluent Hub 웹사이트(또는 관심 커넥터가 호스팅된 다른 웹사이트)에서 내려받기**,
  **소스 코드에서 빌드**(`git clone` 후 `mvn install -DskipTests`).
- 설치 — **`/opt/connectors` 같은 디렉터리를 만들고 `config/connect-distributed.properties`가
  `plugin.path=/opt/connectors`를 포함하도록 갱신**한 뒤, **빌드한 `target` 디렉터리의 jar와
  그 의존성을 `plugin.path`의 적절한 하위 디렉터리로 복사**한다 (9장, p.217).[^shapira2021]
  - **MySQL에 연결하려면 MySQL JDBC 드라이버를 따로 내려받아 설치**해야 한다 — **라이선스
    이유로 커넥터와 함께 배포되지 않기 때문**이며, 받은 jar를 `/opt/connectors/jdbc`에 놓는다
    (9장, p.217).[^shapira2021]
- 설정 옵션을 찾는 방법 — **문서를 봐도 되지만 REST API로 가용한 설정 옵션을 찾을 수도**
  있다. **클래스 이름만 담은 설정(필요한 최소 설정)을 커넥터 설정 검증 엔드포인트로 보내면
  모든 가용 설정의 JSON 정의를 응답으로 받는다** (9장, p.218).[^shapira2021]
- 커넥터 생성은 JSON 설정을 REST API에 POST하는 것이다. 아래는 **MySQL의 `login` 테이블을
  타임스탬프 컬럼 기준으로 읽어 `mysql.` 접두어를 붙인 토픽으로 보내는 JDBC 소스 커넥터**
  이며, `mode`·`table.whitelist`·`timestamp.column.name`·`topic.prefix`로 찾는다 (9장,
  p.219):[^shapira2021]

  ```sh
  echo '{"name":"mysql-login-connector", "config":{"connector.class":"JdbcSourceConnector","connection.url":"jdbc:mysql://127.0.0.1:3306/test?user=root","mode":"timestamp","table.whitelist":"login","validate.non.null":"false","timestamp.column.name":"login_time","topic.prefix":"mysql."}}' | curl -X POST -d @- http://localhost:8083/connectors --header "content-Type:application/json"
  ```

- 확인과 흔한 실패 — **`mysql.login` 토픽에서 데이터를 읽어 동작을 확인**한다. **토픽이
  없다거나 데이터가 보이지 않으면 커넥트 워커 로그에서 오류를 확인**하는데, 예로 든 것이
  **`Access denied for user 'root;'@'localhost' (using password: NO)`** 다. **드라이버가
  클래스패스에 있는지, 테이블을 읽을 권한이 있는지도 흔한 원인**이다. **커넥터가 돌기
  시작하면 `login` 테이블에 행을 추가할 때마다 즉시 `mysql.login` 토픽에 반영**된다 (9장,
  p.219).[^shapira2021]
- 엘라스틱서치 싱크 쪽 설정에서 설명이 필요한 것들 (9장, p.221):[^shapira2021]
  **`connection.url`은 앞서 설정한 로컬 엘라스틱서치 서버의 URL**이고, **카프카의 각 토픽은
  기본적으로 토픽과 같은 이름의 별도 엘라스틱서치 인덱스가 된다.**
  - **JDBC 커넥터는 메시지 키를 채우지 않으므로 카프카의 이벤트는 널 키를 갖는다.**
    **카프카의 이벤트에 키가 없으므로 엘라스틱서치 커넥터에게 토픽 이름·파티션 ID·오프셋을
    각 이벤트의 키로 쓰라고 알려야 하며, `key.ignore`를 true로 설정해서 한다.**
- 그다음 — **JDBC 소스와 엘라스틱서치 싱크를 빌드·설치하는 법을 봤으니 유스케이스에 맞는
  어떤 커넥터 쌍이든 만들어 쓸 수 있다.** **컨플루언트는 자체 사전 빌드 커넥터 집합과
  커뮤니티·다른 벤더의 것들을 Confluent Hub에서 유지**하며, **목록에서 아무거나 골라
  내려받고 문서를 보거나 REST API에서 설정을 당겨 설정한 뒤 워커 클러스터에서 돌린다**
  (9장, p.222).[^shapira2021]
- **커넥터 API는 공개돼 있고 누구나 새 커넥터를 만들 수 있다.** **통합하려는 데이터 저장소에
  기존 커넥터가 없으면 직접 쓰기를 권하고, 그다음 Confluent Hub에 기여해 다른 사람들이
  발견하고 쓸 수 있게** 할 수 있다. **커넥터 빌드의 모든 세부는 이 장의 범위 밖**이지만
  **방법을 설명하는 블로그 포스트가 여럿 있고, 카프카 서밋 NY 2019·런던 2018·아파치콘의
  발표들이 있으며, 기존 커넥터를 시작점으로 보고 아파치 메이븐 아키타입으로 시작하는 것도
  권장**된다 (9장, p.223, "Build Your Own Connectors" 박스).[^shapira2021]

## 변경 데이터 캡처와 디비지움

- **여기서 쓴 JDBC 커넥터는 JDBC와 SQL로 데이터베이스 테이블을 스캔해 새 레코드를 찾는다.**
  **타임스탬프 필드나 증가하는 기본 키를 써서 새 레코드를 탐지**하는데, **이는 상대적으로
  비효율적이고 때로는 부정확한 프로세스**다 (9장, p.220, "Change Data Capture and Debezium
  Project" 박스).[^shapira2021]
- **모든 관계형 데이터베이스는 구현의 일부로 트랜잭션 로그(리두 로그·빈로그·WAL이라고도
  한다)를 갖고, 많은 데이터베이스가 외부 시스템이 그 트랜잭션 로그에서 직접 데이터를 읽는
  것을 허용**한다 — **훨씬 정확하고 효율적인 프로세스이며 변경 데이터 캡처(change data
  capture)라 알려져 있다.** **대부분의 현대 ETL 시스템은 변경 데이터 캡처를 데이터 소스로
  쓴다** (9장, p.220).[^shapira2021]
  - 이 서술은 이 KB의 웨어하우스 쪽 서술과 **같은 방향으로 겹친다** —
    [ETL 34 서브시스템](../concepts/etl-subsystems.md)의 변경 데이터 캡처(2)는 감사 컬럼·
    시각 기반 추출·전체 비교·로그 스크래핑·메시지 큐 감시 다섯 방법을 늘어놓고 **시각 기반
    추출은 실패 재시작 시 중복·누락을 만들어 신뢰할 수 없다**고 못박는다. 이 책이 JDBC
    커넥터의 타임스탬프 스캔을 "때로 부정확하다"고 말하고 트랜잭션 로그 쪽을 권하는 것이
    같은 판정의 카프카 쪽 실물이다.
- **디비지움 프로젝트(Debezium Project)는 다양한 데이터베이스를 위한 고품질 오픈소스 변경
  캡처 커넥터 모음을 제공**한다. **관계형 데이터베이스에서 카프카로 데이터를 스트리밍할
  계획이고 자기 데이터베이스용이 있다면 디비지움 변경 캡처 커넥터를 강력히 권장**한다.
  덧붙여 **디비지움 문서는 저자들이 본 것 중 최고 수준으로, 커넥터 자체를 문서화하는 것에
  더해 특히 마이크로서비스 맥락에서 변경 데이터 캡처에 관한 유용한 설계 패턴과 유스케이스를
  다룬다** (9장, p.220).[^shapira2021] 마이크로서비스 쪽 맥락은
  [마이크로서비스와 서버리스](../concepts/microservices-and-serverless.md)에 있다.

## 커넥트를 쓰지 않는 길

- **다른 데이터 저장소를 위한 반입 프레임워크** — **어떤 사람들은 하둡이나 엘라스틱서치 같은
  시스템 중심으로 데이터 아키텍처를 짓고 그런 시스템은 자체 반입 도구를 갖는다 — 하둡에는
  플룸, 엘라스틱서치에는 로그스태시나 플루언트드**다. **카프카가 아키텍처의 필수 부분이고
  목표가 다수의 소스와 싱크를 잇는 것일 때 커넥트 API를 권장**하고, **실제로 하둡 중심이나
  엘라스틱 중심 시스템을 짓고 있으며 카프카가 그 시스템의 여러 입력 중 하나일 뿐이라면
  플룸이나 로그스태시를 쓰는 것이 말이 된다** (9장, p.229).[^shapira2021]
- **GUI 기반 ETL 도구** — **인포매티카 같은 구식 시스템, 탈렌드·펜타호 같은 오픈소스 대안,
  아파치 나이파이·스트림셋 같은 신형 대안 모두 아파치 카프카를 데이터 소스이자 목적지로
  지원**한다. **이미 이런 시스템을 쓰고 있다면(예: 이미 모든 것을 펜타호로 하고 있다면)
  카프카만을 위해 또 다른 데이터 통합 시스템을 추가하는 데 관심이 없을 수 있고, GUI 기반
  접근으로 ETL 파이프라인을 짓고 있다면 그쪽이 말이 된다.** **주된 단점은 대개 복잡한
  워크플로를 위해 만들어져 있어서 단지 카프카에 데이터를 넣고 빼려는 것뿐이라면 다소 무겁고
  번거로운 해법이 된다는 것**이다 (9장, p.229).[^shapira2021]
  - 저자들의 견해는 명시적이다 — **데이터 통합은 모든 조건에서 메시지를 충실히 전달하는
    데 집중해야 하는데 대부분의 ETL 도구는 불필요한 복잡성을 더한다**고 본다. 그래서
    **카프카를 데이터 통합(커넥트)·애플리케이션 통합(프로듀서와 컨슈머)·스트림 처리를 모두
    다룰 수 있는 플랫폼으로 보라**고 권하며, **카프카는 데이터 저장소만 통합하는 ETL 도구의
    유효한 대체재가 될 수 있다**고 말한다 (9장, p.230).[^shapira2021] 그 ETL 도구들이 원래
    무엇을 하는 물건인지는
    [ETL 34 서브시스템](../concepts/etl-subsystems.md)에 있다.
- **스트림 처리 프레임워크** — **거의 모든 스트림 처리 프레임워크가 카프카에서 이벤트를 읽어
  다른 시스템에 쓰는 기능을 포함**한다. **목적지 시스템이 지원되고 이미 그 프레임워크로
  카프카의 이벤트를 처리할 의도라면 데이터 통합에도 같은 프레임워크를 쓰는 것이 합리적으로
  보인다.** **이는 스트림 처리 워크플로에서 한 단계를 아끼는 경우가 많고**(처리된 이벤트를
  카프카에 저장할 필요 없이 읽어서 다른 시스템에 쓰면 된다), **단점은 유실·손상 메시지 같은
  것의 문제 해결이 더 어려울 수 있다는 것**이다 (9장, p.230).[^shapira2021]
- 고를 때의 기준 (9장, pp.230–231):[^shapira2021] **어떤 데이터 통합 해법에 안착하든 가장
  중요한 기능은 모든 장애 조건에서 모든 메시지를 전달하는 능력**이다. 저자들은 **커넥트가
  카프카의 검증된 신뢰성 기능과 통합돼 있어 극히 신뢰성 있다고 믿지만, 자기가 고른 시스템을
  직접 테스트하는 것이 중요**하다고 말한다 — **멈춘 프로세스·죽은 기계·네트워크 지연·높은
  부하를 메시지 유실 없이 견디는지 확인**하라는 것이다. **신뢰성이 대개 가장 중요한 요구지만
  요구 하나일 뿐이므로 먼저 요구사항을 검토하고**
  ([데이터 파이프라인 설계 고려사항](../concepts/kafka-data-pipeline-considerations.md))
  **고른 시스템이 그것을 만족하는지 확인**해야 하며, **그것으로도 충분하지 않다 — 자기 요구를
  지원하는 방식으로 쓰고 있는지 확신할 만큼 그 해법을 충분히 알아야** 한다. **카프카가 최소
  한 번 의미론을 지원한다는 것만으로는 부족하고, 완전하지 않은 신뢰성으로 끝날 방식으로
  실수로 설정하고 있지 않은지 확인**해야 한다.
