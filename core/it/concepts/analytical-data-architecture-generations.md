하나의 질문: **분석 데이터 아키텍처의 지난 세 세대는 무엇이 달랐고 무엇이 같았는가.**

이 페이지는 *Data Mesh*(2022) 8장의 역사 서술이다. 저자가 이 장을 쓴 목적은 연대기가 아니라
**진단**이다 — 장 제사가 그것을 말한다 (8장, p.121):[^dehghani2022]

> Today's problems come from yesterday's "solutions."
> —Peter M. Senge, *The Fifth Discipline*

각 세대의 아키텍처 자체에 대한 정본 서술은 그 세대의 전용 페이지가 받는다
([EDW](../concepts/enterprise-data-warehouse.md)·[데이터 레이크](../concepts/data-lake.md)) —
여기 있는 것은 **한 저자가 셋을 한 계열로 묶어 읽는 판정**이다.

## 무엇을 세대로 세는가

- 장 첫 문단이 대비를 세운다 — **조직 복잡성, 데이터 원천의 증식, 데이터 기대의 성장: 이것들이
  분석 데이터 관리의 기존 접근에 스트레스를 준 힘이다. 우리 방법은 기계를 확장하는 데
  놀라운 진전을 이뤘다 — 행성 규모의 분산 데이터 저장으로 다양한 데이터 유형의 큰 볼륨을
  관리하고, 스트림으로 고속 데이터를 신뢰성 있게 전송하고, 데이터 집약 워크로드를 동시에 그리고
  빠르게 처리하는 것이다. 그러나 우리 방법은 조직 복잡성과 규모, 곧 **인간 규모(the human
  scale)**에 관해서는 한계가 있다** (8장, p.121).[^dehghani2022] 이 문장이 이 장 전체의 축이다 —
  실패는 기계 확장성이 아니라 조직 확장성에 있다는 것. 기계 쪽 축은
  [확장성과 부하](../concepts/scalability-and-load.md)가 받는다.
- 세대를 세는 단위도 기술이 아니라 아키텍처다 — **분석 데이터 기술의 수에서는 가속된 성장을
  보았지만 **고수준 아키텍처(high-level architecture)**는 아주 적은 변화만 겪었다** (8장,
  p.121).[^dehghani2022] 저자가 붙이는 단서 — **다음 각 아키텍처 패러다임을 뒷받침하는 기저
  기술들은 많은 반복과 개선을 거쳤다. 여기서의 초점은 기술과 구현이 아니라 아키텍처 패턴이다**
  (8장, p.122).[^dehghani2022]

## 1세대 — 데이터 웨어하우스 아키텍처

- 기원과 목적 — **오늘날의 데이터 웨어하우징 아키텍처는 1960년대에 정식화된 팩트와 차원 같은
  이른 개념의 영향을 받았다. 이 아키텍처는 운영 시스템에서 비즈니스 인텔리전스(BI) 시스템으로
  데이터를 옮기는 것을 의도한다. BI 시스템은 전통적으로 조직의 운영 계획과 함께 경영진을
  서빙해 왔다** (8장, p.122).[^dehghani2022] 그 1960년대 개념의 정본은
  [차원 모델링](../concepts/dimensional-modeling.md)에 있다.
- 저자가 "많이 진화했지만 원래 특성 다수는 그대로"라며 꼽는 다섯 (8장, p.122):[^dehghani2022]
  - 많은 운영 데이터베이스와 원천에서 **추출된다**(extracted).
  - 다차원적·시변적 테이블 형식으로 표현되는 **보편 스키마(universal schema)로 변환된다**.
  - 웨어하우스 테이블로 **적재된다**(loaded).
  - **SQL 같은 질의로 접근된다.**
  - 주로 **리포팅과 분석 시각화 용례를 위해 데이터 분석가를 서빙한다.**
- 데이터 마트와의 관계도 이 층위에서 정리한다 — **데이터 웨어하우스 접근은 데이터 마트로
  정련되었고, 데이터 마트가 조직의 한 부서를 서빙하는 반면 데이터 웨어하우스는 여러 부서에
  걸쳐 통합하는 더 큰 조직을 서빙한다는 흔한 구분이 있다. 범위와 무관하게 **아키텍처적 모델링
  관점에서 둘은 비슷한 특성을 갖는다**** (8장, p.122).[^dehghani2022] 곧 저자에게 마트와
  웨어하우스는 같은 세대다.
- 실패 서술은 비용과 부채로 간다 — **조직 규모의 데이터 웨어하우징이 가능한 단일 기술을
  만드는 것의 어려움과 비용이, 흔히 독점적이고 비싸며 사용에 전문화를 요구하는 엔터프라이즈
  데이터 웨어하우스 해법으로 이어졌다. 시간이 지나면서 그것들은 특화된 집단만이 이해하고
  유지할 수 있는 수천 개의 ETL 잡·테이블·리포트를 포함하게 된다. 나이와 기원 때문에 그것들은
  CI/CD 같은 현대 엔지니어링 실천에 잘 맞지 않고 시간에 걸쳐 기술 부채와 늘어난 유지 비용을
  발생시킨다. 이 기술 부채를 벗어나려는 조직은 하나의 데이터 웨어하우스 해법에서 다른 것으로
  옮겨 가는 영구적 순환 안에 있는 자신을 발견한다** (8장, p.122).[^dehghani2022]

## 2세대 — 데이터 레이크 아키텍처

- 도입 시점과 동기 — **데이터 레이크 아키텍처는 데이터 웨어하우징 아키텍처의 난제에 대응해
  2010년에 도입되었다: 기계 학습 모델 훈련 과정에서 데이터 과학자가 데이터에 접근하는 것이다.
  데이터 과학자는 사업의 현실에 가능한 한 가까운 원래 형태의 데이터를 필요로 한다. 데이터
  과학자는 데이터가 정확히 어떻게 모델링되어야 하는지 예측할 수 없으므로 원시 데이터에 대한
  접근을 선호한다. 더해서 기계 학습 훈련은 대규모로 병렬화된 데이터 읽기를 요구했다** (8장,
  p.123).[^dehghani2022]
- 웨어하우스와 같은 것과 다른 것 — **데이터 레이크 아키텍처는 데이터 웨어하우스와 마찬가지로
  데이터가 운영 시스템에서 추출되어 흔히 오브젝트 스토어 형식의 중앙 저장소로 적재된다고
  가정한다. 그러나 데이터 웨어하우징과 달리 데이터 레이크는 데이터의 사전 변환과 모델링이
  아주 적거나 없다고 가정한다. 데이터를 원천에 가까운 형태로 유지하려 시도한다** (8장,
  p.123).[^dehghani2022]
- **사전 변환이 왜 해로운가**의 논거가 여기 있다 — **사전 변환은 블로커이며 모델 훈련의 더 느린
  반복으로 이어진다. 더해서 그것은 운영 시스템 데이터의 본성을 바꾸고, 변환된 데이터로 훈련된
  모델이 실제 프로덕션 질의에 대해 성능을 내지 못하는 방식으로 데이터를 변이시킨다** (8장,
  p.124).[^dehghani2022]
  - 저자가 드는 구체 사례 — **음악 추천기(music recommender)를 예로 들면, 웨어하우스에서
    변환·모델링된 데이터로 훈련되었을 때 운영 맥락에서 호출되면 — 예컨대 로그인한 청취자의
    세션 정보로 추천 서비스가 호출될 때 — 성능을 내지 못한다. 모델 훈련에 쓰인 심하게 변환된
    데이터는 청취자 속성 일부를 놓치거나 그것들을 다른 표현으로 인코딩했다** (8장,
    p.124).[^dehghani2022]
- 저자가 꼽는 레이크 아키텍처의 아홉 특성 (8장, p.124):[^dehghani2022]
  - 많은 운영 데이터베이스와 원천에서 **추출된다.**
  - **원래 내용과 구조를 가능한 한 많이 표현한다.**
  - Parquet·Avro 같은 **인기 저장 형식에 맞도록 최소한으로 변환된다.**
  - **원천 스키마에 가능한 한 가까운 상태로 확장 가능한 오브젝트 스토리지에 적재된다.**
  - **오브젝트 스토리지 인터페이스를 통해 접근된다** — 파일 또는 2차원 배열형 구조인
    데이터프레임으로 읽는다.
  - 주로 **데이터 과학자가** 분석과 기계 학습 모델 훈련을 위해 레이크 저장소에 접근한다.
  - 레이크 하류에 목적 적합 데이터 마트로서 **레이크쇼어 마트(lakeshore marts)가 만들어진다.**
  - **레이크쇼어 마트는 애플리케이션과 분석 용례에 쓰인다.**
  - 레이크 하류에 기계 학습 훈련을 위해 모델링·저장된 목적 적합 열 지향 데이터로서
    **피처 스토어(feature stores)가 만들어진다.**
- 판정은 두 낱말이다 — **데이터 레이크 아키텍처는 복잡성과 퇴화(complexity and deterioration)로
  고통받는다. 그것은 초전문화된 데이터 엔지니어의 중앙 팀이 운영하는 배치나 스트리밍 잡의
  복잡하고 다루기 힘든 파이프라인을 만든다. 그것은 시간이 지나며 퇴화한다. 관리되지 않는
  데이터셋들은 흔히 신뢰받지 못하고 접근 불가능하며 가치를 거의 제공하지 못한다. 데이터 계보와
  의존성은 가려져 추적하기 어렵다** (8장, p.125).[^dehghani2022] 같은 현상을 데이터 엔지니어링
  쪽 소스가 "데이터 레이크 1.0의 실패"로 적은 자리와 나란히 두는 곳은
  [데이터 레이크](../concepts/data-lake.md)다.

## 3세대 — 멀티모달 클라우드 아키텍처

- 이름과 지위 — **세 번째이자 최신 세대의 데이터 아키텍처는 데이터 메시 이전의 것으로, 몇 가지
  현대적 비틀림과 함께 이전 세대들과 대체로 비슷하다** (8장, p.126).[^dehghani2022] 저자가 꼽는
  비틀림 넷 (8장, p.126):[^dehghani2022]
  - **Kappa 같은 아키텍처로 준실시간 데이터 가용성을 위한 스트리밍을 지원한다.**
  - **Apache Beam 같은 프레임워크로 데이터 변환을 위해 배치와 스트림 처리를 통일하려 시도한다.**
  - **클라우드 기반 관리형 서비스를 온전히 받아들이고 컴퓨트와 스토리지가 격리된 현대적 클라우드
    네이티브 구현을 사용한다. 비용 최적화를 위해 클라우드의 탄력성을 활용한다.**
  - **웨어하우스와 레이크를 한 기술로 수렴시킨다** — 임베디드 ML 훈련을 포함하도록 데이터
    웨어하우스를 확장하거나, 반대로 데이터 웨어하우스의 무결성·트랜잭션성·질의 시스템을 데이터
    레이크 해법 안에 짓는다. (각주 1이 드는 예: **집필 시점에 Google BigQuery ML이나 Snowflake
    Snowpark는 일부 ML 능력을 임베드한 전통적 데이터 웨어하우스 해법의 예이고, Databricks
    Lakehouse는 웨어하우스 같은 트랜잭션과 질의 지원을 갖춘 전통적 레이크 저장 해법의 예다.**)
- 그럼에도 판정은 같다 — **이 3세대 데이터 플랫폼은 실시간 데이터 분석 같은 이전 세대의 간극
  일부를 다루면서 빅데이터 인프라 관리 비용도 줄이고 있다. 그러나 그것들은 이전 세대의 한계로
  이어진 기저 특성 다수를 여전히 앓는다** (8장, p.126).[^dehghani2022]
- 기술 혁신이 진단을 흐리지 않게 저자는 캄브리아기 폭발이라는 은유를 쓴다 — **분석 데이터
  아키텍처의 역사를 훑어보면 그것이 진화적 개선을 거쳤음이 분명하다. 그 사이 기술과 그것을
  뒷받침하는 제품은 캄브리아기 폭발(Cambrian explosion)을 겪었다** (8장,
  p.126).[^dehghani2022] 그림 8-3이 인용하는 FirstMark의 연례 빅데이터·AI 지형도는
  **읽으라고 있는 것이 아니라 그냥 훑어보고 어지러움을 느끼라고 있는 것**이다 (8장,
  p.127).[^dehghani2022] — 곧 도구 수의 증가가 아키텍처 가정의 변화를 뜻하지 않는다는 논증이다.

## 바뀌지 않은 세 가정

- 저자가 던지는 질문 — **그렇다면 질문은 이것이다. 무엇이 바뀌지 않았는가? 분석 데이터
  아키텍처의 모든 세대가 지니고 다니는 기저 특성은 무엇인가? 부인할 수 없는 혁신에도 불구하고
  지난 몇십 년 동안 도전받지 않은 채 남아 면밀히 평가되어야 하는 근본 가정들이 있다** (8장,
  p.127):[^dehghani2022]

| 가정 | 원문 |
|---|---|
| 중앙집중 | Data must be centralized to be useful—managed by a centralized organization, with an intention to have an enterprise-wide taxonomy. |
| 모놀리식 | Data management architecture, technology, and organization are monolithic. |
| 기술 주도 | The enabling technologies drive the paradigm—architecture and organization. |

- **적용 범위의 한정이 붙는다** — **이 장에서 논의되는 아키텍처 특성은, 중앙집중을 포함해,
  논리 아키텍처(logical architecture)에만 적용된다. 데이터가 물리적으로 어디에 저장되는가 같은
  물리 아키텍처 관심사는 이 대화의 범위 밖이며 논리 아키텍처 관심사와 무관하다. 논리 아키텍처는
  데이터 개발자와 소비자의 경험 계층에 초점을 둔다 — 데이터가 단일 팀에 의해 관리되는가 아닌가
  (데이터 소유권), 데이터가 단일 스키마를 갖는가 아닌가(데이터 모델링), 그리고 한 데이터 모델의
  변경이 하류 사용자에게 긴밀한 결합과 영향을 갖는가(의존성)** (8장, p.127).[^dehghani2022]
  이 단서가 있어야 "Snowflake는 컴퓨트와 스토리지를 분리했는데 왜 모놀리식인가" 같은 반론이
  성립하지 않는다.

## 가정 하나 — 모놀리식

저자는 모놀리식을 아키텍처·기술·조직 셋으로 나눠 각각 진단한다.

**모놀리식 아키텍처.** 정의는 다른 책에서 인용한다 — **아키텍처 양식은 두 주요 유형으로 분류될
수 있다: 모놀리식(모든 코드의 단일 배포 단위)과 분산(원격 접근 프로토콜로 연결된 다중 배포
단위)** (8장, p.128, 각주 3은 출처를 Mark Richards and Neal Ford, *Fundamentals of Software
Architecture*, O'Reilly, 2020으로 밝힌다).[^dehghani2022]

- 3만 피트에서 본 데이터 플랫폼의 목표는 셋이다 (8장, p.128):[^dehghani2022]
  - **엔터프라이즈 안팎의 모든 구석에서 데이터를 반입한다**(ingest) — 사업을 돌리는 도메인의
    운영·트랜잭션 시스템에서 엔터프라이즈의 지식을 증강하는 외부 데이터 제공자까지.
  - **원천 데이터를 소비자의 필요를 다룰 수 있는 신뢰할 만한 데이터로 정제·풍부화·변환한다.**
  - **다양한 필요를 가진 다양한 소비자에게 데이터셋을 서빙한다** — 데이터 탐색과 기계 학습
    훈련에서 비즈니스 인텔리전스 리포트까지.
- 모놀리스 자체를 나쁘다고 말하지는 않는다 — **모놀리식 아키텍처는 해법을 짓는 좋고 단순한
  출발점일 수 있다 — 예컨대 하나의 코드 베이스, 한 팀을 관리하는 것 — 그러나 해법이 확장될 때
  부족해진다** (8장, p.129).[^dehghani2022] **조건이 다르면 판정이 다르다**는 이 책의 되풀이되는
  단서다.
- 규모에서 생기는 마찰 셋 (8장, pp.129–130):[^dehghani2022]
  - **편재하는 데이터와 원천 증식** — **데이터가 더 편재하게 이용 가능해질수록, 중앙집중 플랫폼과
    팀의 통제 아래 그것을 전부 소비하고 한곳에서 논리적으로 조화시키는 능력은 줄어든다. (…)
    중앙 고객 마스터 데이터 관리 아래 데이터를 반입하고 조화시켜야 가치를 얻는다는 가정이
    병목을 만들고 다양한 데이터 원천을 활용하는 능력을 늦춘다. 새 원천에서 데이터를 이용 가능하게
    만드는 조직의 반응은 원천 수가 늘수록 느려진다.**
  - **혁신 의제와 용례 증식** — **조직의 빠른 실험 필요는 플랫폼에서 데이터를 소비하는 더 많은
    용례를 도입한다. (…) 데이터 소비자의 필요를 충족하는 긴 응답 시간은 역사적으로 조직적 마찰의
    지점이었고 현대 데이터 플랫폼 아키텍처에서도 여전히 그렇다. 데이터를 필요로 하고 용례를 아는
    사람·시스템과, 데이터를 만들었고 그 데이터를 가장 잘 아는 실제 원천·팀·시스템 사이의 단절이
    회사의 데이터 주도 혁신을 방해한다. 그것은 올바른 데이터에 접근하는 데 필요한 시간을 늘리고,
    가설 주도 개발의 블로커가 되며, 데이터 품질과 데이터에 대한 신뢰를 낮춘다.**
  - **조직 복잡성** — **데이터 지형의 변동성과 지속적 변화를 섞어 넣으면 이 모놀리식 아키텍처는
    동기화와 우선순위 결정의 지옥이 된다. 조직의 이동하는 데이터 우선순위와 활동 전반을 중앙집중
    데이터 플랫폼과 정렬시키는 것은 승산 없는 상황이다.**

**모놀리식 기술.** — **기술 관점에서 모놀리식 아키텍처는 그것을 가능케 하는 기술과 조화롭게
일치해 왔다. 데이터 레이크나 데이터 웨어하우스 아키텍처를 지원하는 기술은 기본적으로 모놀리식
아키텍처를 가정한다** (8장, p.130).[^dehghani2022]

- 웨어하우스 쪽 — **Snowflake·Google BigQuery·Synapse 같은 데이터 웨어하우징 기술은 모두
  모놀리식 논리 아키텍처를 갖는다. 물리·구현 계층에서는 자원 격리와 분해에 막대한 진전이
  있었지만 — 예컨대 Snowflake는 컴퓨트 자원 확장을 스토리지 자원에서 분리하고 BigQuery는 최신
  세대 분산 파일 시스템을 사용한다 — **기술의 사용자 경험은 모놀리식으로 남아 있다**** (8장,
  p.130).[^dehghani2022] 이것이 위 논리/물리 단서의 실물 적용이다.
- 레이크 쪽 — **오브젝트 스토리지와 파이프라인 오케스트레이션 도구 같은 데이터 레이크 기술은
  분산 방식으로 배포될 수 있다. 그러나 기본적으로 그것들은 모놀리식 레이크 아키텍처의 생성으로
  이어진다. 예컨대 데이터 처리 파이프라인 DAG(directed acyclic graph) 정의와 오케스트레이션은
  파이프라인 잡 의존성과 복잡성을 추상하는 인터페이스와 계약 같은 구성물을 결여하고 있으며,
  이는 긴밀히 결합된 미로 같은 파이프라인을 갖는 큰 진흙 공(big ball of mud) 모놀리식
  아키텍처로 이어진다. 여기서는 변경이나 실패를 프로세스의 한 단계로 격리하기 어렵다. 어떤
  클라우드 제공자는 레이크 스토리지 계정 수에 제한을 두는데, 소수의 모놀리식 레이크 셋업만
  있으리라 가정한 것이다** (8장, p.130).[^dehghani2022]

**모놀리식 조직.** — **조직 관점에서 콘웨이의 법칙(Conway's law)이 모놀리식 조직 구조 —
비즈니스 인텔리전스 팀·데이터 분석 그룹·데이터 플랫폼 팀 — 와 함께 완전히 작동해 왔다. 조직
전반의 데이터를 책임지는 구조다** (8장, p.130).[^dehghani2022] 인용되는 원문 (8장, p.130):

> Any organization that designs a system (defined broadly) will produce a design whose
> structure is a copy of the organization's communication structure.
> —Melvin Conway, 1968

- 그 안에서 사는 사람의 위치 — **데이터 플랫폼을 짓고 운영하는 사람들의 삶을 관찰할 만큼 가까이
  줌인하면, 데이터가 비롯되거나 사용되는 조직의 운영 단위에서 사일로화된 초전문화 데이터
  엔지니어 집단을 발견한다. 데이터 엔지니어들은 조직적으로 사일로화되었을 뿐 아니라 업무·도메인
  지식이 대개 부재한 채 데이터 도구에 대한 기술 전문성에 근거해 한 팀으로 분리·묶음되어 있다**
  (8장, pp.130–131).[^dehghani2022]
  - 그 위치의 결과 — **그들은 합의된 계약에 근거해 의미 있고 진실하며 올바른 데이터를 공유할
    유인이 없는 운영 팀에서 데이터를 소비해야 한다. 데이터 팀의 조직적 사일로 때문에, 최선을
    다함에도 이 데이터 엔지니어들은 데이터를 생성하는 원천 도메인에 대한 이해가 거의 없고 팀
    안에 도메인 전문성이 없다. 그들은 데이터가 어떻게 사용되는지 깊이 이해하지 못한 채 운영이든
    분석이든 다양한 필요에 데이터를 제공해야 한다** (8장, p.131).[^dehghani2022]
  - 세 자리의 요약 — **현실에서 우리가 발견하는 것은 단절된 원천 팀, 데이터 팀의 백로그 위
    자리를 두고 다투는 좌절한 소비자, 그리고 과도하게 늘어나고 저평가된 데이터 팀이다** (8장,
    p.131).[^dehghani2022] 같은 역할의 역사를 데이터 엔지니어링 쪽 어휘로 적은 자리는
    [데이터 엔지니어 역할의 진화](../concepts/data-engineer-evolution.md)에 있다.
- **복잡한 모놀리스** — **모놀리식 아키텍처는 규모를 만날 때 — 여기서 규모는 원천·소비자·변환의
  다양성이다 — 모두 비슷한 운명에 직면해 복잡해지고 유지하기 어려워진다. 뻗어 나가는 데이터
  파이프라인의 복잡성 부채(complexity debt), 반입·변환 로직을 구현하는 덕트 테이프로 붙인
  스크립트, 명확한 아키텍처적·조직적 모듈성이 없는 다수의 데이터셋 — 테이블이나 파일 — 그리고 그
  데이터셋 위에 지어진 수천 개의 리포트가 팀을 가치 창출 대신 부채의 이자를 갚느라 바쁘게
  만든다** (8장, pp.131–132).[^dehghani2022]
  - 결론 — **요컨대 모놀리식 아키텍처·기술·조직 구조는 대규모의 복잡한 조직의 분석 데이터
    관리에 적합하지 않다** (8장, p.132).[^dehghani2022]

## 가정 둘 — 중앙집중 데이터 소유권

- 관행의 서술 — **모놀리식 데이터 플랫폼이 서로 다른 도메인에 속하는 데이터 — 예컨대 재생
  이벤트·매출 KPI·아티스트·앨범·레이블·오디오·팟캐스트·음악 이벤트 등 — 를 다수의 이질적
  도메인에서 수집해 호스팅하고 소유한다는 것은 받아들여진 관례다** (8장, p.132).[^dehghani2022]
- 진단의 축은 DDD 적용의 비대칭이다 — **지난 십 년간 우리는 도메인 주도 설계와 바운디드
  컨텍스트를 운영 시스템 설계에 성공적으로 적용해 규모에서 소프트웨어 복잡성을 관리해 왔지만,
  데이터에 대해서는 도메인 주도 설계 패러다임을 대체로 무시했다. DDD의 전략 설계는 크고 복잡한
  조직에서 규모에 맞춰 소프트웨어 모델링을 관리하는 일련의 원칙을 도입한다. 그것은 단일 정규
  모델에서 다수의 바운디드 컨텍스트 모델로 옮겨 갈 것을 권한다. 그것은 각각 조직의 한 단위가
  소유하고 관리하는 다수의 모델을 가정한다. 그리고 이 모델들 사이의 관계를 명시적으로 표현한다**
  (8장, p.132).[^dehghani2022]
  - 비대칭의 결론 — **운영 시스템은 서비스와 그 데이터를 기존 업무 도메인에 정렬시키며 도메인
    지향 운영 데이터 소유권을 향해 DDD의 전략 설계 기법을 적용해 온 반면, **분석 데이터
    시스템은 도메인 바깥에 중앙집중 데이터 소유권을 유지해 왔다**** (8장,
    p.133).[^dehghani2022] 이 논증의 전문은
    [도메인 소유권 원칙](../concepts/domain-ownership-principle.md)에 있다.
- **조건부 판정이 명시된다** — **이 중앙집중 모델은 더 적은 용례와 더 단순한 도메인을 가진
  조직에는 통할 수 있지만, 풍부하고 복잡한 도메인을 가진 엔터프라이즈에는 실패한다** (8장,
  p.133).[^dehghani2022]
- 규모 말고 두 가지가 더 걸린다 — **규모의 한계에 더해 데이터 중앙집중의 다른 난제는 데이터
  품질과 변화에 대한 회복력이다. 이는 데이터에 가장 익숙한 업무 도메인과 팀이 데이터 품질을
  책임지지 않기 때문이다. 데이터 원천에서 멀고 데이터의 도메인에서 격리된 중앙 데이터 팀이
  데이터 정제·풍부화 파이프라인을 통해 품질을 데이터에 되돌려 넣는 일을 맡는다. 흔히 파이프라인
  반대편에서 중앙 시스템으로 튀어나오는 데이터는 원래 형태와 의미를 잃는다** (8장,
  p.133).[^dehghani2022]
- 중앙집중의 기원도 한 줄로 적는다 — **분석 데이터의 중앙집중은 사일로화되고 파편화된
  애플리케이션 데이터베이스 — 흔히 다크 데이터(dark data)라 알려진 — 에 대한 우리 산업의
  응답이었다. 가트너가 만든 이 낱말은 조직이 정규 업무 활동 중에 수집·처리·저장하지만 분석이나
  다른 목적에 사용하지 못하는 정보 자산을 가리킨다** (8장, p.133).[^dehghani2022]

## 가정 셋 — 기술 지향

- 진단 — **웨어하우스에서 레이크로, 그리고 전부 클라우드 위로 온 분석 데이터 아키텍처의 지난
  세대들을 돌아보면, 우리는 기술 주도 아키텍처에 심하게 기대어 왔다. 데이터 관리 시스템의
  전형적 해법 아키텍처는 각각 종단 간 저장·처리 흐름의 한 조각인 기술적 기능을 수행하는 다양한
  기술들을 단지 배선해 놓은 것일 뿐이다** (8장, p.133).[^dehghani2022]
  - 저자가 드는 예 — **먼저 Cloud Pub/Sub이 지원하는 반입(ingestion) 기능을 만나고, 그다음
    Cloud Storage로 데이터를 발행(publishing)하며, 그것이 BigQuery를 통해 데이터를
    서빙(serves)한다. 이 접근은 기술적으로 분할된 아키텍처(technically partitioned
    architecture)로 이어지고 결과적으로 활동 지향 팀 분해(activity-oriented team
    decomposition)로 이어진다** (8장, p.133).[^dehghani2022]

**기술적으로 분할된 아키텍처.** — **아키텍트와 기술 리더는 성장에 대응해 아키텍처를 분해한다.
다수의 새 원천을 태우거나 새 소비자의 증식에 대응할 필요가 플랫폼의 성장을 요구한다. 아키텍트는
시스템을 최상위 구성 요소로 쪼개 확장할 방법을 찾아야 한다** (8장, pp.134–135).[^dehghani2022]

- 인용되는 정의 — **최상위 기술적 분할(top-level technical partitioning)은 시스템을 그 기술적
  능력과 관심사에 근거해 구성 요소로 분해한다. 이는 업무 도메인 관심사보다 구현 관심사에 더
  가까운 분해다** (8장, p.135, *Fundamentals of Software Architecture* 인용).[^dehghani2022]
- 적용 실물 — **모놀리식 데이터 플랫폼의 아키텍트와 리더는 파이프라인 아키텍처에 근거한 모놀리식
  해법을 반입·정제·집계·풍부화·서빙 같은 기술적 기능으로 분해해 왔다. 최상위 기능적 분해는
  동기화 오버헤드와 데이터 변경에 대한 느린 응답으로 이어진다. 대안적 접근은 **최상위 도메인
  지향 분할(top-level domain-oriented partitioning)**이다. 여기서는 이 기술적 기능들이 모든
  도메인 안에 임베드되고, 도메인에 대한 변경이 최상위 동기화 없이 국소적으로 관리될 수 있다**
  (8장, p.135).[^dehghani2022]

**활동 지향 팀 분해.** — **시스템을 아키텍처 구성 요소로 쪼개는 동기 중 하나는 각자 하나의
아키텍처 구성 요소를 짓고 운영할 수 있는 독립 팀을 만드는 것이다. 이 팀들은 다시 작업을
병렬화해 더 높은 운영 확장성과 속도에 이를 수 있다. 최상위 기술적 분해의 결과는 팀을 활동 지향
그룹으로 분해하는 것이다** (8장, p.135).[^dehghani2022]

- 그 모델의 내재적 한계 — **이 모델이 흐름의 다른 활동에 팀을 배정함으로써 어느 정도의 규모를
  제공하기는 하지만, **중요한 것을 확장하지 못하는** 내재적 한계가 있다: 결과의 전달 — 이 경우
  새로운 품질과 신뢰할 만한 데이터의 전달이다. 결과를 전달하려면 팀 간 동기화와 활동에 대한 변경
  정렬이 필요하다. 그런 분해는 **변경 또는 결과의 축에 직교하며**(orthogonal to the axis of
  change or outcome), 가치 전달을 늦추고 조직적 마찰을 도입한다** (8장,
  pp.135–136).[^dehghani2022]
  - 대안의 이름 — **반대로 결과 지향 팀 분해(outcome-oriented team decomposition)는 빠르게
    전달되고 낮은 동기화 오버헤드를 갖는 종단 간 결과에 최적화한다** (8장,
    p.136).[^dehghani2022]
  - 저자가 드는 사례의 결론 — **새 기능을 태우기 위해 변해야 하는 가장 작은 단위, 곧 새 데이터셋을
    풀어 새롭거나 기존의 소비에 이용 가능하게 만드는 단위는 여전히 파이프라인 전체 — 모놀리스 —
    로 남는다. 이것이 데이터의 새 소비자나 원천에 대응해 더 높은 속도와 규모를 달성할 우리
    능력을 제한한다** (8장, p.136).[^dehghani2022]
- **반쯤 한 대응은 안티패턴으로 명시된다** — **최근 몇 해 사이 중앙 데이터 팀을 도메인 지향
  데이터 팀으로 분해하려는 움직임이 있었다. 그것이 개선이기는 하지만 장기적 데이터 소유권과
  데이터 품질의 문제를 풀지 못한다. 데이터 팀은 실제 도메인에서 여전히 멀고, 도메인 시스템의
  변경 및 그들의 필요와 동기화되지 않은 채로 남는다. **이것은 안티패턴이다**** (8장,
  p.136).[^dehghani2022] 이 한 줄이 "우리는 이미 도메인별 데이터 팀을 두었다"는 흔한 반론을
  저자가 미리 기각하는 자리다.

## 저자가 내리는 판정

- 8장 회고의 제사 (8장, p.137):[^dehghani2022]

> The definition of insanity is doing the same thing over and over again and expecting
> different results.
> —Albert Einstein

- 세대를 가로지르는 공통 진단 — **데이터 아키텍처의 진화가 필요했고 개선이었음에도, 기존의 모든
  분석 데이터 아키텍처는 그것들이 조직적으로 확장되는 것을 막는 공통된 특성 집합을 공유한다.
  그것들은 모두 중앙집중 소유권을 갖는 모놀리식이며 기술적으로 분할되어 있다** (8장,
  p.137).[^dehghani2022] 통합 모델의 공통점도 한 줄로 적는다 — **그 접근 전부가 부서지기 쉽고
  유지하기 어려운 채로 남는 파이프라인 기반 통합 모델을 갖는다** (8장, p.137).[^dehghani2022]
- **가정이 언제 유효했고 언제 무효가 되는가 — 이 페이지에서 가장 중요한 한 문단이다** (8장,
  p.137):[^dehghani2022]

> These characteristics are the consequence of an age-old assumption that to satisfy
> analytical use cases, data must be extracted from domains and consolidated and
> integrated under the central repositories of a warehouse or a lake. This assumption was
> valid when data use cases were limited to low-frequency reports. It was valid when data
> was being sourced from a handful of systems. It is no longer valid when data gets
> sources from hundreds of microservices and millions of devices from within and outside
> of enterprises. It is no longer valid when tomorrow's use cases for data are beyond our
> imagination today.

  - 곧 저자의 판정은 **"과거의 아키텍처가 틀렸다"가 아니라 "그 아키텍처를 정당화하던 조건이
    끝났다"**이다. 같은 형식의 조건부 판정을 2장이 중앙화 일반에 대해 내리는 자리는
    [EDW](../concepts/enterprise-data-warehouse.md)의 "데이터 메시가 보는 웨어하우스"에 있다.

## 같은 세대 이야기를 아키텍처 쪽 책이 두 세대로 적는다

**이 페이지의 저자가 2021년에 공저자로 참여한 아키텍처 책의 14장이 같은 역사를 적는데, 셋이
아니라 둘로 끊는다** (14장 §"Previous Approaches", pp.382–388).[^ford2021-hard-parts]

| 항목 | 이 페이지(dehghani2022 8장) | ford2021 14장 |
|---|---|---|
| 세는 단위 | **세대 셋** — 웨어하우스 · 레이크 · 멀티모달 클라우드 | **이전 접근 둘** — 웨어하우스 · 레이크 |
| 3세대에 해당하는 것 | 멀티모달 클라우드 아키텍처를 따로 센다 | **없다.** 클라우드는 웨어하우스 실패 서술 안의 한 조건으로만 나온다 |
| 실패의 공통 원인 | **바뀌지 않은 세 가정**(중앙집중·모놀리식·기술 주도) | **기술적 분할 대 도메인 분할** 하나로 모은다 |
| 다음으로 넘어가는 논거 | 세 가정이 규모에서 무너진다 | 데이터를 **맥락에서 떼어 놓는다**는 판정 하나 |

- **어긋나지 않고 굵기가 다르다.** ford2021 쪽 판정인 **기술적 분할**은 이 페이지 위
  [가정 셋 — 기술 지향](#가정-셋--기술-지향)과 같은 것이고, 3세대를 따로 세지 않는 것은
  **그 책이 분석 데이터를 한 장으로 다루며 전문을 이 페이지의 소스로 넘기기 때문**이다 (14장,
  p.390).[^ford2021-hard-parts] **두 저작의 저자가 겹치므로 이것은 서로 다른 두 주장이
  아니라 같은 주장의 두 분량이다.**
- 두 양식 각각에 ford2021이 붙이는 실패 목록과 절충표는
  [EDW](../concepts/enterprise-data-warehouse.md)와 [데이터 레이크](../concepts/data-lake.md)가
  갖는다 — 이 페이지는 세대의 **틀**만 소유한다.
