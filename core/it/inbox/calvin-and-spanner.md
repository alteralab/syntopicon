하나의 질문: **분산 트랜잭션의 조율 비용을 줄이는 두 가지 길은 각각 무엇을 먼저 정하고
무엇을 나중으로 미루는가.**

## 무엇이 문제인가

- 락을 잡는 시간을 줄이려면 — **경합과 트랜잭션이 락을 쥐고 있는 총 시간을 줄이는 방법 중 하나는,
  레플리카들이 락을 획득하고 실행을 진행하기 전에 실행 순서와 트랜잭션 경계에 동의하게 하는 것이다.
  이를 달성할 수 있으면 노드 장애가 트랜잭션 중단을 일으키지 않는다. 같은 트랜잭션을 병렬로
  실행하는 다른 참여자에게서 노드가 상태를 복구할 수 있기 때문이다** (13장,
  p.266).[^petrov2019]
- 전통적 방식과의 대비 — **전통적 데이터베이스 시스템은 2단계 잠금이나 낙관적 동시성 제어를 써서
  트랜잭션을 실행하며 결정적 트랜잭션 순서가 없다. 이는 순서를 보존하기 위해 노드들이 조율돼야
  한다는 뜻이다. 결정적 트랜잭션 순서는 실행 단계의 조율 오버헤드를 없애고, 모든 레플리카가 같은
  입력을 받으므로 동등한 출력도 낸다** (13장, p.266).[^petrov2019]

## Calvin — 결정적 트랜잭션 순서

- 정체 — **이 접근은 흔히 Calvin이라 불리며 빠른 분산 트랜잭션 프로토콜이다. Calvin으로 분산
  트랜잭션을 구현하는 저명한 예 중 하나가 FaunaDB다** (13장, p.266).[^petrov2019]
- 시퀀서 — **결정적 순서를 달성하기 위해 Calvin은 시퀀서(sequencer)를 쓴다. 모든 트랜잭션의
  진입점이다. 시퀀서는 트랜잭션이 실행되는 순서를 결정하고 전역 트랜잭션 입력 계열을 세운다. 경합을
  최소화하고 결정을 배치로 묶기 위해 타임라인은 에포크(epoch)로 나뉜다. 시퀀서는 트랜잭션을 모아
  짧은 시간 창으로 묶는데(원 논문은 10밀리초 배치를 언급한다) 이것이 복제 단위이기도 하므로
  트랜잭션이 개별적으로 전달될 필요가 없다** (13장, p.266).[^petrov2019]
- 스케줄러 — **트랜잭션 배치가 성공적으로 복제되는 즉시 시퀀서는 그것을 스케줄러(scheduler)로
  전달하고, 스케줄러가 트랜잭션 실행을 조율한다. 스케줄러는 시퀀서가 지정한 직렬 실행 순서를
  보존하면서 트랜잭션의 부분들을 병렬로 실행하는 결정적 스케줄링 프로토콜을 쓴다. 트랜잭션을 특정
  상태에 적용하면 그 트랜잭션이 지정한 변경만 만들어짐이 보장되고 트랜잭션 순서가 미리 정해져
  있으므로, 레플리카는 시퀀서와 더 통신할 필요가 없다** (13장, pp.266–267).[^petrov2019]
- 읽기 집합과 쓰기 집합 — **Calvin의 각 트랜잭션은 읽기 집합(read set, 그것을 실행하는 데 필요한
  현재 데이터베이스 상태의 데이터 레코드 모음인 그 의존 관계)과 쓰기 집합(write set, 트랜잭션 실행의
  결과, 다시 말해 그 부작용)을 갖는다. Calvin은 읽기·쓰기 집합을 결정하는 추가 읽기에 의존하는
  트랜잭션을 기본적으로 지원하지 않는다** (13장, p.267).[^petrov2019]

## Calvin의 실행 절차

- **스케줄러가 관리하는 워커 스레드는 네 단계로 실행을 진행한다** (13장,
  p.267):[^petrov2019]
  1. **트랜잭션의 읽기·쓰기 집합을 분석하고, 읽기 집합에서 노드 로컬 데이터 레코드를 결정하고,
     활성 참여자 목록**(즉 쓰기 집합의 원소를 들고 있으며 데이터를 수정할 참여자)**을 만든다.**
  2. **트랜잭션 실행에 필요한 로컬 데이터, 다시 말해 그 노드에 있는 읽기 집합 레코드를 모은다.
     모인 데이터 레코드는 해당 활성 참여자에게 전달된다.**
  3. **이 워커 스레드가 활성 참여자 노드에서 실행되고 있으면, 2단계에서 실행된 연산의 상대편으로서
     다른 참여자에게서 전달된 데이터 레코드를 받는다.**
  4. **마지막으로 트랜잭션 배치를 실행하고 결과를 로컬 저장소에 영속화한다. 실행 결과를 다른
     노드에 전달할 필요는 없다. 그들도 트랜잭션에 대해 같은 입력을 받아 스스로 실행하고 결과를
     로컬에 영속화하기 때문이다.**
- 배치와 합의 — **전형적인 Calvin 구현은 시퀀서·스케줄러·워커·저장 서브시스템을 같은 자리에 둔다.
  시퀀서들이 정확히 어느 트랜잭션이 현재 에포크/배치에 들어가는지에 대해 합의에 이르도록 Calvin은
  Paxos 합의 알고리즘이나, 전용 레플리카가 리더 역할을 하는 비동기 복제를 쓴다. 리더를 쓰면 지연이
  개선될 수 있지만, 노드들이 진행하려면 실패한 리더의 상태를 재현해야 하므로 복구 비용이 더
  높아진다** (13장, p.267).[^petrov2019]

## Spanner — 합의 그룹 위의 2단계 커밋

- 정체 — **Calvin은 종종 Spanner라 불리는 다른 분산 트랜잭션 관리 접근과 대비된다. 그 구현(또는
  파생물)에는 여러 오픈 소스 데이터베이스가 포함되는데 가장 저명한 것이 CockroachDB와 YugaByte
  DB다. Calvin이 시퀀서에 대한 합의에 이름으로써 전역 트랜잭션 실행 순서를 세우는 반면, Spanner는
  파티션마다(다시 말해 샤드마다) 합의 그룹 위에서 2단계 커밋을 쓴다** (13장,
  p.268).[^petrov2019]
- 세 가지 연산 유형 — **Spanner는 세 가지 주요 연산 유형을 제공한다. 읽기-쓰기 트랜잭션, 읽기 전용
  트랜잭션, 스냅샷 읽기다. 읽기-쓰기 트랜잭션은 락, 비관적 동시성 제어, 리더 레플리카의 존재를
  요구한다. 읽기 전용 트랜잭션은 락이 없고 어느 레플리카에서든 실행될 수 있다. 리더는 최신
  타임스탬프에서의 읽기에만 필요한데, 이는 Paxos 그룹에서 최신 커밋 값을 가져온다. 특정
  타임스탬프에서의 읽기는 일관되는데, 값이 버전 관리되고 스냅샷 내용은 일단 쓰이면 바뀔 수 없기
  때문이다. 각 데이터 레코드에는 트랜잭션 커밋 시각 값을 담은 타임스탬프가 배정되며, 이는 레코드의
  타임스탬프가 붙은 버전 여럿이 저장될 수 있음을 함의한다** (13장, pp.268–269).[^petrov2019]
- 구조 — **각 스팬서버(spanserver, 레플리카이자 클라이언트에 데이터를 제공하는 서버 인스턴스)는
  Paxos 상태 기계가 붙은 태블릿(tablet)을 여럿 들고 있다. 레플리카는 Paxos 그룹이라 불리는 레플리카
  집합으로 묶이며, 이것이 데이터 배치와 복제의 단위다. 각 Paxos 그룹에는 오래 사는 리더가 있다.
  리더들은 다중 샤드 트랜잭션 중에 서로 통신한다** (13장, p.269).[^petrov2019]
- 읽기와 쓰기의 경로 — **모든 쓰기는 Paxos 그룹 리더를 거쳐야 하고, 읽기는 최신 상태의 레플리카에
  있는 태블릿에서 직접 제공될 수 있다. 리더는 2단계 잠금 기전으로 동시성 제어를 구현하는 데 쓰이는
  락 테이블과, 다중 샤드 분산 트랜잭션을 책임지는 트랜잭션 관리자를 들고 있다. 동기화가 필요한
  연산(트랜잭션 안의 쓰기와 읽기 등)은 락 테이블에서 락을 획득해야 하고, 다른 연산(스냅샷 읽기)은
  데이터에 직접 접근할 수 있다** (13장, p.269).[^petrov2019]
- 2PC의 가용성 문제를 어떻게 푸는가 — **다중 샤드 트랜잭션에서 그룹 리더들은 일관성을 보장하기
  위해 조율하고 2단계 커밋을 수행하며, 격리를 보장하기 위해 2단계 잠금을 쓴다. 2PC 알고리즘은
  성공적 커밋을 위해 모든 참여자의 존재를 요구하므로 가용성을 해친다. Spanner는 코호트로 개별 노드가
  아니라 Paxos 그룹을 씀으로써 이를 푼다. 이는 그룹 구성원 일부가 내려가 있어도 2PC가 계속 동작할 수
  있다는 뜻이다. Paxos 그룹 안에서 2PC는 리더 역할을 하는 노드에만 접촉한다** (13장,
  p.269).[^petrov2019]
- 커밋 절차 — **Paxos 그룹은 여러 노드에 걸쳐 트랜잭션 관리자 상태를 일관되게 복제하는 데 쓰인다.
  Paxos 리더는 먼저 쓰기 락을 획득하고, 이전 어느 트랜잭션의 타임스탬프보다 크다고 보장되는 쓰기
  타임스탬프를 고르고, Paxos를 통해 2PC 준비 항목을 기록한다. 트랜잭션 코디네이터는 타임스탬프를
  모아 어느 준비 타임스탬프보다도 큰 커밋 타임스탬프를 생성하고, Paxos를 통해 커밋 항목을 기록한다.
  그다음 커밋에 고른 타임스탬프가 지날 때까지 기다리는데, 클라이언트가 타임스탬프가 과거인 트랜잭션
  결과만 보게 보장해야 하기 때문이다. 그 뒤 이 타임스탬프를 클라이언트와 리더들에게 보내고, 리더들은
  새 타임스탬프로 커밋 레코드를 자기 로컬 Paxos 그룹에 기록하고 이제 락을 풀 수 있다** (13장,
  p.270).[^petrov2019]
- 단일 샤드는 값이 싸다 — **단일 샤드 트랜잭션은 트랜잭션 관리자에 물을 필요가 없고(따라서 파티션
  간 2단계 커밋을 수행할 필요도 없다). Paxos 그룹과 락 테이블을 참조하는 것만으로 샤드 안의 트랜잭션
  순서와 일관성을 보장하기에 충분하기 때문이다** (13장, p.270).[^petrov2019]

## TrueTime과 외부 일관성

- TrueTime — **일관성을 달성하고 트랜잭션 순서를 부과하기 위해 Spanner는 TrueTime을 쓴다. 불확실성
  경계도 노출하는 고정밀 벽시계 API로, 로컬 연산이 불확실성 경계가 지날 때까지 기다리도록 인위적
  느려짐을 도입할 수 있게 해 준다** (13장, p.268).[^petrov2019]
- 외부 일관성 — **Spanner 읽기-쓰기 트랜잭션은 외부 일관성(external consistency)이라 불리는 직렬화
  순서를 제공한다. 분산 트랜잭션의 경우에도 트랜잭션 타임스탬프가 직렬화 순서를 반영한다. 외부
  일관성은 선형성과 동등한 실시간 성질을 갖는다 — 트랜잭션 T1이 T2가 시작하기 전에 커밋하면 T1의
  타임스탬프가 T2의 타임스탬프보다 작다** (13장, p.270).[^petrov2019]

## 둘의 대비

- 저자의 요약 — **정리하면 Spanner는 일관된 트랜잭션 로그 복제에 Paxos를, 샤드 간 트랜잭션에 2단계
  커밋을, 결정적 트랜잭션 순서화에 TrueTime을 쓴다. 이는 다중 파티션 트랜잭션이 Calvin에 비해 추가
  2단계 커밋 라운드 때문에 더 높은 비용을 갖는다는 뜻이다. 두 접근 모두 이해하는 것이 중요한데,
  파티션된 분산 데이터 스토어에서 트랜잭션을 수행할 수 있게 해 주기 때문이다** (13장,
  p.270).[^petrov2019]
- 장의 결론이 가리키는 방향 — **현대 데이터베이스 시스템의 분산 트랜잭션은 종종 합의 알고리즘을
  써서 구현된다. 예컨대 이 장에서 논한 Calvin과 Spanner 둘 다 Paxos를 쓴다. 합의 알고리즘은 원자적
  커밋 알고리즘보다 더 복잡하지만 훨씬 나은 내결함성 성질을 가지며, 결정을 그 개시자에게서 분리하고
  참여자가 값을 받아들일지 말지가 아니라 값 자체에 대해 결정하게 해 준다** (13장,
  p.277).[^petrov2019]
