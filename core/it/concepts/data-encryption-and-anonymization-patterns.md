하나의 질문: **접근 통제를 뚫고 들어온 사람이 데이터를 손에 넣었을 때, 그것이 읽히지 않게 하려면
무엇을 하는가.**

Konieczny의 7장 셋째 범주인 **데이터 보호**(Data Protection)의 세 패턴이다. 나머지 범주는
[개인 데이터 제거 패턴](personal-data-removal-patterns.md)과
[세밀한 접근과 자격 증명 패턴](fine-grained-access-and-credential-patterns.md)에 있다.

## 접근 제어만으로 부족한 이유

- 범주의 전제 — **논리적 수준(즉 데이터베이스나 클라우드 서비스 범위)에서 데이터 접근을 통제하는
  것으로 완전히 안전한 시스템을 짓기에 충분하다고 생각할 수 있다. 불행히도 그것은 해법의 일부일
  뿐이다. 빠진 부분은 데이터 자체를 보호하는 것, 따라서 예상치 못한 사용으로부터 그것을 지키는 것에
  관련된다** (7장, p.215).[^konieczny2025]
- 장 도입부가 같은 것을 다른 말로 세워 둔다 — **데이터 보호는 또 다른 중요한 보안 측면이다.
  데이터셋 위치(테이블이나 파일 시스템 경로 같은)에 실수로 접근을 줘도 사용자가 데이터를 읽을 수
  있다는 뜻은 아니다. 암호화 같은 추가 보호 계층을 썼다면 소비자는 데이터셋에 접근하기 위해 복호화
  키도 필요할 것이다** (7장, p.197).[^konieczny2025]

## Encryptor — 키가 없으면 못 읽는다

- 문제의 실물 — 세밀한 접근 정책을 구현하고 나서 **정지 상태와 이동 중 데이터의 보안을 강제하는
  임무를 받았다. 이해관계자들은 무단 인물이 스트리밍 브로커와 잡 사이에 전송되는 데이터를 가로채거나,
  같은 인물이 서버에서 데이터를 물리적으로 훔칠 수 있다고 걱정한다** (7장,
  pp.215–216).[^konieczny2025]
- **두 보호 수준이 필요하므로 패턴은 두 구현을 갖는다** (7장, p.216).[^konieczny2025]
- 첫째는 **정지 데이터**(data at rest)다 — **클라이언트 쪽 또는 서버 쪽 접근으로 저장된 데이터를
  암호화하며, 두 접근의 차이는 암호화 키 관리로 귀착된다. 클라이언트 쪽 구현에서 데이터 생산자가
  저장으로 보내기 전에 데이터를 암호화할 책임을 진다. 자연히 암호화 키 관리에도 책임을 진다. 서버 쪽
  암호화라면 모든 암호화·복호화 작업이 서버 쪽에서 이뤄진다. 소비자나 생산자는 요청만 발행하고 서버가
  암호화 키 관리를 포함한 나머지를 한다** (7장, p.216).[^konieczny2025]
  - 클라우드에서는 후자가 표준이다 — **각 주요 제공자가 서버 쪽 암호화를 지원하는 모든 서비스에
    자유롭게 적용할 수 있는 자체 암호화 키 저장소를 갖는다. AWS와 GCP에서는 Key Management
    Service(KMS)를, Azure에서는 Key Vault 서비스를 쓴다** (7장, p.216).[^konieczny2025]
  - 암호화된 데이터 저장과의 상호작용 네 단계 (7장, p.217):[^konieczny2025]
    - **요청이 먼저 암호화된 데이터 저장에 닿는다. 그러나 그것은 직접 반환하지 않는다.**
    - **데이터를 반환하는 대신 저장은 암호화 키를 식별하고 암호화 키 저장소에 복호화 키를 요청한다.
      클라이언트가 데이터를 복호화할 권한이 없으면 요청은 실패한다. 그렇지 않으면 계속된다.**
    - **다음으로 데이터 저장이 가져온 복호화 키로 데이터를 복호화한다.**
    - **마지막으로 복호화된 레코드가 클라이언트에 되돌아간다.**
  - 클라우드 사용자에게 남는 몫 — **이 복잡한 교환은 클라우드 제공자에 의해 당신에게 완전히
    추상화된다. 당신의 유일한 책임은 데이터 저장에 적절한 암호화 전략을 설정하고, 읽고 쓰는 모든
    클라이언트에 대해 데이터 저장과 암호화 키 저장소 접근을 관리하는 것이다** (7장,
    p.217).[^konieczny2025]
- 둘째는 **이동 데이터**(data in transit)다 — **클라이언트와 데이터 저장이 네트워크를 가로질러
  데이터를 교환하는 자리다. 클라우드에서의 구현은 클라이언트 쪽 SDK 수준에서 보안 통신을 활성화하고
  서비스에서 요구되는 프로토콜 버전을 설정하는 것으로 한정되므로 비교적 쉽다** (7장,
  p.217).[^konieczny2025]
- 두 조각을 잇는 것이 이 패턴의 실체다 — **앞의 두 스니펫을 요약하면 암호화란 그저 키를 암호화된
  자원과 모든 인가된 아이덴티티에 연관 짓는 문제라고 말할 수 있다** (7장,
  p.219).[^konieczny2025] Terraform으로 KMS 키를 선언할 때
  **유일하게 신비하지만 본질적인 파라미터가 `deletion_window_in_days`인데, 잘못된 제거의 경우
  암호화 키 복원 창을 보장하려고 거기 있다** (7장, p.218).[^konieczny2025]

## 암호화가 되사는 것 — CPU·키 분실·프로토콜

- **암호화·복호화 오버헤드** — **아마 가장 먼저 떠오르는 결과가 CPU 오버헤드다. 데이터는 평문이
  아니라 어떤 식으로든 변형된, 읽을 수 없는 판으로 저장된다. 암호화·복호화 액션 없이는 쓸 수 없다.
  그런 이유로 각 쓰기·읽기 요청이 CPU에 약간의 추가 압력을 준다** (7장,
  p.217).[^konieczny2025]
- **데이터 손실 위험** — 보호와 차단이 같은 기제라는 대칭이다. **Encryptor 패턴이 정지 데이터를
  무단 접근으로부터 보호하는 경향이 있지만, 부작용으로 인가된 사용자의 접근도 막을 수 있다. 다만
  이는 암호화 키를 잃거나 단순히 그 접근을 잃는 경우에만 일어날 수 있다** (7장,
  p.217).[^konieczny2025]
  - 완화 — **이 문제를 완화하려고 클라우드 제공자는 흔히 암호화 저장소에 소프트 삭제(soft deletes)를
    구현한다. 즉 보내는 어떤 삭제 요청도 즉시 효력을 갖지 않는다. 대신 우발적 삭제의 경우 키를 복원할
    수 있는 유예 기간의 혜택을 받는다** (7장, p.217).[^konieczny2025]
- **프로토콜 갱신** — **이동 중 암호화는 정지 암호화보다 설정이 훨씬 쉽다. 그러나 그것도 최신
  상태로 유지돼야 하는 시스템의 추가 구성 요소다. HTTPS의 가능한 암호화 채널인 전송 계층
  보안(Transport Layer Security, TLS) 프로토콜이 그렇다. 수년에 걸쳐 여러 암호화 문제가 탐지되어
  TLS 1.0과 1.1 버전의 폐지로 이어졌다. 그런 이유로 이 오래된 릴리스를 쓰는 어떤 서비스든
  업그레이드돼야 한다** (7장, p.218).[^konieczny2025]
  - 버전 조건: TLS 1.0·1.1 폐지 이후 — RFC 8996이 근거다. 저자의 예제도 Azure Event Hubs의
    `minimum_tls_version = "1.2"`를 설정한다.
  - 클라우드가 이 부담을 줄인다 — **이 연산은 어려운 추가 유지보수 태스크로 보이지만, 클라우드
    제공물에서는 서비스 수준에서 새 암호화 프로토콜 버전으로 업그레이드하는 것으로 매우 자주
    단순화되고 축소된다** (7장, p.218).[^konieczny2025]

## Anonymizer — 식별 정보를 없앤다

- 문제의 실물 — 외부 데이터 분석 회사와 계약했는데 **데이터셋이 PII 속성을 많이 포함하고 일부
  사용자가 그것을 제3자와 공유하는 데 동의하지 않았으므로, 공유 데이터셋을 프라이버시 규제에
  부합하게 만드는 파이프라인을 쓰는 임무를 받았다** (7장, p.219).[^konieczny2025]
  - 저자가 상자로 넓혀 둔 범위 — **예제는 PII 데이터를 참조하는데 아마 가장 흔히 논의되는
    유스케이스이기 때문이지만, 그것이 보호를 요구하는 유일한 데이터 유형은 아니다. 다른 예로 보호
    대상 건강 정보(PHI)와 지식 재산(IP) 데이터가 있다** (7장, p.220).[^konieczny2025]
- **패턴의 목표는 데이터셋에서 민감 데이터를 제거해 각 행을 익명 정보로 변환하는 것이다. 이 프로세스
  덕에 데이터 소비자는 사용자를 식별할 수 없게 된다** (7장, p.220).[^konieczny2025]
- 세 구현 (7장, p.220):[^konieczny2025]
  - **데이터 제거(data removal)가 가장 구현하기 쉬운데, 선택된 열을 입력 데이터셋에서 빼기
    때문이다.**
  - **데이터 교란(data perturbation)이 더 복잡하다. 입력 값에 잡음을 더해 값이 다른 의미를 갖게
    한다. 예컨대 IP 열에서 임의 위치에 추가 속성을 더해 "123.456.789.012"가 "1823.456.7809.012"가
    되게 할 수 있다.**
  - **합성 데이터 대체(synthetic data replacement)는 원본 값을 합성 데이터 생성기에서 오는 값으로
    치환한다. 입력 열의 유형을 해석하고 대응하는 대체값을 생성할 수 있는 똑똑한 모델(아마도 기계
    학습 모델)이 있다는 뜻이다. 대체값은 원본 속성과 같아 보이지만 다른 값을 갖는다. 예컨대 국가
    열에서 "Portugal"이 합성적으로 "Croatia"로 대체될 수 있다.**
- 구현 난이도의 순서 — **구현하기 가장 쉬운 방법은 앞의 둘이다. 매핑 함수나 열 변환으로 값을
  제거하거나 교란할 수 있다. 합성 데이터 방법은 대체값을 분석하고 생성할 수 있는 모델을 짓기 위해
  데이터 과학 팀과의 작업을 수반할 수 있다. 덜 이상적인 판에서는 결국 열마다 임의 값을 생성하는 대체
  함수를 만들어 스스로 해법을 구현할 수 있다** (7장, pp.220–221).[^konieczny2025]
- 결과는 하나뿐이고 무겁다 — **정보 손실. 정보를 제거하거나 대체할 때 데이터셋이 새로운 무언가가
  된다는 것은 명백하다. 이는 데이터 분석가·데이터 과학자 같은 기술 사용자를 포함한 최종 사용자가
  자기 일에서 이 민감 열에 기댈 수 없다는 뜻이다. 그것은 거짓 데이터 예측 모델과 부정확한 데이터
  통찰을 포함한 여러 문제로 이어질 수 있다** (7장, p.221).[^konieczny2025]
- 열 제거와 열 대체를 함께 보이는 것이 이 패턴의 대표 코드다 — 저자는 **생일 열을 제거하고 이메일
  주소를 Faker 라이브러리가 만든 합성 데이터로 대체**한다 (7장, p.221):[^konieczny2025]

  ```python
  @pandas_udf(StringType())
  def replace_email(emails: pandas.Series) -> pandas.Series:
    faker_generator = Faker()
    return emails.apply(lambda email: faker_generator.email())

  users.drop('birthday').withColumn('email', replace_email(users.email))
  ```

  - 열을 빼는 두 방법의 판단 기준 — **먼저 `SELECT` 문에서 읽을 열 목록에서 그것을 생략할 수 있다.
    이 접근은 읽을 열이 많지 않을 때 좋다. 그렇지 않다면 반대 접근을 취해 `drop` 함수로 열을 제거할
    수 있다** (7장, p.221).[^konieczny2025]

## Pseudo-Anonymizer — 업무 의미를 남기고 바꿔 쓴다

- 이 패턴이 존재하는 이유는 앞 패턴의 결과다 — **Anonymizer 패턴은 강한 데이터 보호를 제공한다.
  그러나 누락되거나 변경된 값 때문에 데이터 과학·데이터 분석 파이프라인에 대한 그 영향이 매우 나쁠 수
  있다. Pseudo-Anonymizer 패턴이 이 영향을 줄인다** (7장, p.222).[^konieczny2025]
- 문제의 실물 — 외부 분석가에게 공유한 익명화 데이터셋에 열이 다 없어서 **팀이 대부분의 업무 질의에
  답할 수 없었다. 팀원들은 여전히 실제 PII 값을 숨기되 더 쓸 만한 형태로 대체한 새 데이터셋을 달라고
  요청했다** (7장, p.222).[^konieczny2025]
- 네 구현 (7장, pp.222–223):[^konieczny2025]
  - **데이터 마스킹(data masking)은 민감 데이터를 무의미한 문자나 더 현실적인 치환값으로 대체한다.
    예컨대 999-55-1040 같은 사회보장번호(SSN)는 XXX-XX-1040이나 9XX-5X-1XXX로 마스킹될 수 있다.
    보다시피 이 마스킹 전략을 적용하면 서로 다른 여러 사용자가 같은 마스킹된 SSN을 공유할 수 있다.**
  - **데이터 토큰화(data tokenization)는 초기 값을 가상의 값으로 치환한다. 그러나 원본 값과 그
    대체값 사이의 매핑을 토큰 볼트 저장소에 저장한다. 여기서 핵심은 보호된 속성이 노출되지 않도록
    볼트 접근을 보안하는 것이다. 볼트 접근 보안이 뚫리면 무단 인물이 접근해 토큰화된 값을 되돌릴 수
    있다.**
  - **해싱(hashing)은 민감 값을 완전히 그리고 되돌릴 수 없게 대체한다. 예컨대
    `contact@waitingforcode.com` 같은 이메일은 SHA-256 알고리즘으로 해싱되고 Base64 스킴으로
    인코딩되면 `gD0B+pUp-XYVZ9nqhgLRuban0CilZRKVp4dcmvmocsYE=` 같은 문자열이 될 수 있다.**
  - **암호화(encryption)는 열이나 행에 적용되는 암호화 키에 기대는데, Encryptor 패턴의 데이터셋
    키와 조금 비슷하다. 여기서 암호화 키에 접근하는 사용자는 원본 값을 복원할 수 있어야 한다.**
- 구현 노력이 갈리는 자리 — **어떤 것(데이터 마스킹 같은)은 쉬운 열 변환 함수로 표현될 수 있다.
  다른 것(추가 매핑 테이블을 요구하는 토큰화 같은)은 추가 구현 노력이 필요할 수 있다** (7장,
  p.223).[^konieczny2025]
- 일반화(generalization)와 마스킹을 섞은 `mapInPandas` 매핑이 이 패턴의 대표 코드다 — 국가를
  지리적 영역으로 바꾸고 SSN을 마스킹한다 (7장, p.225):[^konieczny2025]

  ```python
  def pseudo_anonymize_users(input_pandas: pandas.DataFrame) -> pandas.DataFrame:
    def pseudo_anonymize_country(country: str) -> str:
      countries_area_mapping = {
        'Poland': 'eu', 'France': 'eu', 'Spain': 'eu', 'the USA': 'na'
      }
      return countries_area_mapping[country]

    def pseudo_anonymize_ssn(ssn: str) -> str:
      return f'{ssn[0]}***-{ssn[5]}***-{ssn[10]}***'
    for rows in input_pandas:
      rows['country'] = rows['country'].apply(lambda c: pseudo_anonymize_country(c))
      rows['ssn'] = rows['ssn'].apply(lambda ssn: pseudo_anonymize_ssn(ssn))
      yield rows
  ```

  - 매핑 하나로 다 되지 않는 자리가 있다 — **`mapInPandas` 매핑은 타입 변경 때문에 급여 열에 대한
    범위 변환을 포함하지 않는다. 급여는 입력 데이터셋에 정수로 정의돼 있는데 범위는 문자열 타입이다.
    타입 비호환 변환이므로 그것을 다루려면 단순한 열 기반 매핑이 필요하다** (7장,
    p.225).[^konieczny2025] 저자는 `CASE WHEN salary BETWEEN 0 AND 50000 THEN "0-50000"`
    식의 `expr`을 따로 건다.

## 익명화와 가명화를 가르는 한 문장

- 저자가 상자로 갈라 둔 정의다 — **현재 서술 중인 패턴에 포함된 가명화 기법들은 때때로 익명화
  프로세스의 일부로 제시된다. 그러나 그들 사이에는 중요한 차이가 있다. 가명화된 PII 데이터는 다른
  데이터셋과 결합되면 식별 가능해질 수 있다. 익명화된 데이터셋에서는 그렇지 않은데, 결합의 경우에도
  데이터가 식별 불가능하게 남는다** (7장, p.223).[^konieczny2025]
  - **이 KB의 다른 소스와 나란히 두면 조건이 붙는다.** 저자의 "익명화된 데이터셋은 결합해도 식별
    불가능하게 남는다"는 서술은 **패턴을 올바로 적용했을 때의 정의**이지, 실제 데이터셋에 대한
    경험적 보장이 아니다. Kleppmann & Riccomini는 같은 문제를 반대 방향에서 본다 — **재식별이
    아예 불가능하더라도 사용자는 이미 자기 정보 공개에 대한 주체성을 잃었다**
    ([결정권으로서의 프라이버시](../concepts/privacy-as-a-decision-right.md)). #hypothesis
    두 서술은 충돌하지 않지만 초점이 다르다 — Konieczny는 파이프라인이 규제에 부합하는지를,
    Kleppmann은 그 부합이 프라이버시를 회복하지 못한다는 것을 말한다.

## 거짓 보안감 — 표 두 개를 조인하면 사람이 나온다

- **Pseudo-Anonymizer는 개인 데이터를 흐리게 하기는 하지만 Anonymizer 패턴보다 약한 보안 보장을
  제공한다. 가장 큰 문제 중 하나가 데이터셋의 결합에서 오는데, 거기서 가명화된 열이 사람을 식별하는
  PII 열이 될 수 있다** (7장, p.223).[^konieczny2025]
- 저자의 실물 예제는 두 표다 — 가상의 데이터 엔지니어 John Doe는 유럽의 작은 나라 산마리노에 살며
  Cheetach Processor라는 프레임워크를 발명했다 (7장, pp.223–224):[^konieczny2025]

  | 표 | 열 | 값 |
  |---|---|---|
  | 표 7-1 음식 선호 | User ID · Liked foods · Disliked foods | 1000 · carrot, broccoli, potato · chips, chocolate bar |
  | 표 7-2 사용자 등록 | User ID · Country · Role | 1000 · `S*n M****o` · `C******h P*******r i******r` |

- **표 7-1은 사용자의 아이덴티티를 완벽하게 보호한다. 그러나 그것을 표 7-2와 결합하면 "S\*n
  M\*\*\*\*o에 사는 C\*\*\*\*\*\*h P\*\*\*\*\*\*\*r i\*\*\*\*\*\*r가 당근·브로콜리·감자를
  좋아한다" 같은 것을 얻게 된다. 마스킹된 국가 열의 이름과 일치하는 나라는 많지 않다. 산마리노에
  이르고 나면 "inventor" 부분도 발견해 사용자 ID 1000이 우리의 유명한 John Doe를 가리킨다고
  식별할 수 있다** (7장, p.224).[^konieczny2025]
- 그리고 완전 익명화였다면 어떻게 달랐을지를 저자가 명시한다 — **완전 익명화라면 식별이 불가능했을
  텐데, Country와 Role 열이 둘 다 제거되거나 예컨대 "Europe"과 "Software engineer"로 변경됐을
  것이기 때문이다. 이제 두 표를 결합한 뒤에도 이 소프트웨어 엔지니어가 누구인지 명확하지 않다는 것을
  알 수 있다** (7장, p.224).[^konieczny2025]
  - **판정 규칙이 여기서 나온다** — 가명화 강도는 열 하나로 정해지지 않는다. **같은 조인 키로 닿을
    수 있는 모든 데이터셋의 합집합**에서 정해진다. 저자 자신이 예제가 추상적임을 인정하면서도
    **"그 자명함은 가명화가 데이터셋을 결합할 때 주는 거짓 보안감을 명확히 보이기 위해 거기 있다"**고
    쓴다 (7장, p.224).[^konieczny2025]

## 정보 손실은 두 종류다

- 첫째는 **값의 충돌**이다 — **이를 보여 주는 최고의 예가 데이터 마스킹 전략이다. SSN 예제에서
  보았듯 숫자 일부가 보존된다. 그 때문에 서로 다른 두 SSN이 이제 같은 사용자를 가리킬 수 있다. 예컨대
  999-55-1040과 999-13-1040이 둘 다 같은 형식 XXX-XX-1040으로 마스킹될 수 있다** (7장,
  p.224).[^konieczny2025]
- 둘째는 **타입 손실**이다 — **이 손실에 더해 데이터 타입 손실도 있다. 그 훌륭한 예가 일반화
  방법으로, 거기서 수치 값이 텍스트 타입으로 표현되는 수치 범위로 대체될 수 있다** (7장,
  p.224).[^konieczny2025] 위 급여 열이 그 실물이다 — `50000`(정수)이 `"50000-60000"`(문자열)이
  된다.
- **두 손실이 향하는 방향이 다르다** — 값 충돌은 집계·조인의 **정확도**를 깎고, 타입 손실은
  하류 스키마의 **호환성**을 깬다. 앞의 것은 조용히 틀린 답을 내고, 뒤의 것은 시끄럽게 실패한다.
