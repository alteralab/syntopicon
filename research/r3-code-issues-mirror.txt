--- SUMMARY ---
종합 판정 재료: (1) '설치된 버전의 라이브러리 소스를 에이전트가 직접 읽는' 관행은 실재하며 1차 근거가 있다 — Vercel AI SDK 공식 문서가 node_modules 내 소스 정독을 버전 일치의 수단으로 명시 권장하고, Claude Code는 지시 없이도 자발적으로 node_modules에서 API·타입을 확인한다(issue #55146). Anthropic 공식 best-practices에는 명시 권고가 없고 '필요한 파일을 스스로 읽게 하라' 수준이다. (2) 연구 실증은 비대칭적이다: 버전 조건부 태스크에서 정량 입증된 것은 문서 RAG(+~10%p, GitChameleon)와 실행 피드백(+10~20%p)이고, '라이브러리 소스 코드를 retrieval 소스로 쓴' 통제 실험은 찾지 못했다(GitChameleon은 docs만 실험, CodeRAG-Bench는 GitHub repo 포함 datastore가 이득이지만 소스별 우열 미확정). 대신 SWE-agent의 2배 성능(ACI= bounded 검색+정독)이 '무색인 lexical 탐색 + 코드 정독' 구조 자체의 유효성을 입증하고, BM25가 dense embedding을 이긴다는 결과(2503.15231)는 사용자의 rg 계약과 정합적이다. (3) 버전 혼동은 VersiCode·LibEvolutionEval·GitChameleon으로 계측된 실재 문제이며, '설치된 버전 산출물 읽기'가 그 우회 수단이라는 실무 주장(Vercel)과 상업적 방증(Context7)이 있다. (4) 반대 근거도 명확하다: 임베딩·전량 색인 관점에서 의존 코드는 노이즈(Cursor 기본 제외), 통제 없는 코드 읽기는 토큰 낭비 불만의 대상, 무관 코드 retrieval은 성능을 낮춘다는 연구 복수 — 실무 완화책은 '표적 정독 + tests/픽스처 제외'다. 캐시 계약 관점 시사점: 버전별 코드는 외부 유래·버전 종속·재생성 가능(git tag에서 결정론적)·인간 저작물 제로를 모두 충족하고, '무색인 rg + 정독' 소비 모델과도 연구적으로 정합적이나, 가치의 실증 강도는 docs(정량 실증)보다 한 단계 약한 '관행+구조적 실증' 수준이다.

     src: https://github.com/anthropics/claude-code/issues/55146 (2026-04-30)
[LB] GitChameleon 2.0(버전 조건부 코드 생성 벤치마크, 328문항): 문서(docs) RAG로 GPT-4.1이 48.5%→58.5%(약 +10%p), Claude 4 Sonnet 59.4% 등 최대 ~10%p 향상. 단, retrieval corpus는 'API documentation' 뿐이며 라이브러리 소스 코드를 retrieval 소스로 쓴 조건은 실험되지 않았다. self-debugging(실행 피드백)은 +10~20%p로 docs RAG보다 컸다. Claude Code 에이전트 자체는 48.8%.
     src: https://arxiv.org/abs/2507.12367 (2025-07 (arXiv), ACL 2026 게재)
[  ] 코드 자체를 retrieval 소스로 쓰는 통제 실험은 CodeRAG-Bench(NAACL 2025 Findings)가 가장 가깝다: GitHub repositories를 포함한 5개 소스에서 retrieval을 평가했고, '다양한 대형 datastore에서의 retrieval은 GPT-4에도 유의미한 이득'이지만 (1) 어려운 태스크(DS-1000, SWE-bench)에서 retrieval 품질이 낮고 (2) oracle retrieval과 실제 retrieval 사이 큰 격차, (3) 일부 모델은 retrieval 이득이 작음을 보고. '코드 retrieval > 문서 retrieval'을 입증한 깨끗한 비교는 발견하지 못했다.
     src: https://code-rag-bench.github.io/ (2024-06 arXiv (2406.14497), NAACL 2025)
[LB] docs RAG의 효과는 비인기 라이브러리에서 극대화된다: 'When LLMs Meet API Documentation'(arXiv 2503.15231)은 Polars·Ibis·GeoPandas·Ivy에서 문서 top-5 retrieval로 pass rate 83–220% 상대 향상을 실측했고, 문서 구성요소 중 '예제 코드'가 압도적으로 중요(예제 제거 시 Qwen32B 66–82% → 22–39%), 반면 파라미터 목록은 제거 시 오히려 약간 향상(=노이즈). 또 BM25가 dense embedding을 크게 이김(recall@5 0.72–0.94 vs 0.21–0.72) — 무색인 rg(리터럴 매칭) 접근이 코드류 코퍼스에 유리하다는 방증.
     src: https://arxiv.org/html/2503.15231v1 (2025-03 (arXiv))
[LB] 버전 혼동(파라메트릭 지식의 낡음)은 계측된 실재 문제다: VersiCode(300개 라이브러리·2,207개 버전)에서 GPT-4o조차 Pass@1 70.44로 HumanEval/MBPP(85+) 대비 크게 하락, 일부 모델은 50점 이상 격차. LibEvolutionEval은 '버전 관련 맥락(버전 명시 + 해당 버전 문서 retrieval)을 주면 성능이 실질 개선'되고 모델이 deprecated API에서 특히 취약함을 보고. 즉 '설치된 버전의 산출물을 읽히는 것'이 버전 혼동 우회 수단이라는 연구적 근거는 성립하나, 실험된 매체는 주로 버전별 문서이지 소스 코드가 아니다.
     src: https://arxiv.org/abs/2406.07411 (2024-06 (VersiCode arXiv v1))
[LB] SWE-bench류 에이전트의 성공 구조 자체가 '코드 정독 + 검색 도구'의 유효성 실증이다: SWE-agent(NeurIPS 2024)는 find_file/search_file/search_dir 같은 코드 탐색 인터페이스(ACI)를 제공하는 것만으로 동일 GPT-4의 SWE-bench 점수를 raw bash 대비 약 2배로 올렸고, 핵심은 '간결하고 크기 제한된 출력'이었다. 이는 사용자의 'rg + 파일 정독, 무색인' vendor 계약과 같은 형태(색인 없는 lexical 탐색 + bounded read)가 에이전트에 충분히 작동함을 시사한다. 단 이는 수정 대상 저장소의 코드이지 의존 라이브러리 코드에 대한 직접 실험은 아니다.
     src: https://proceedings.neurips.cc/paper_files/paper/2024/file/5a7c947568c1b1328ccc5230172e1e7c-Paper-Conference.pdf (2024 (NeurIPS))
[LB] 반대 근거 (1) — 임베딩/색인 관점에서 의존 코드는 노이즈로 취급된다: Cursor는 node_modules·빌드 산출물을 기본 ignore 목록으로 색인에서 제외하며, 실무 보고는 'AI가 문맥으로 API를 추론하므로 node_modules 색인이 불필요하고, 제외해도 React Hooks/Lodash/Axios 제안이 정상 동작'이라고 한다. ClaudeLog는 grep이 deny 규칙을 우회해 node_modules를 훑으며 대량 토큰을 태우는 문제와 차단법을 다룬다. 즉 '전량 색인·무차별 검색'은 실무에서 명확한 반대 근거가 있고, 가치가 인정되는 것은 '필요 시 표적 정독'이다.
     src: https://claudelog.com/faqs/how-to-stop-claude-code-reading-node-modules/ (2026-01-15 (eastondev), ClaudeLog 게시일 미상)
[LB] 반대 근거 (2) — retrieval 노이즈 연구: 검색된 코드 스니펫이 입력 의도와 무관하면 생성 성능을 떨어뜨린다는 실증이 복수 존재한다. 'An Empirical Study of Retrieval-Augmented Code Generation'(arXiv 2501.13742)은 무관한 retrieved code가 노이즈로 작용해 성능을 낮춘다고 보고하고, repository-level QA 연구(arXiv 2603.26567)는 '대형 저장소에서는 접선적으로 관련된 파일·의존이 많아 distracting retrieval 위험이 급증'하며 무관 문맥 추가 시 성능이 뚜렷이 하락한다고 보고한다. 실무 측 완화책의 예: Simon Willison은 코드를 LLM에 먹일 때 tests·문서를 제외하고 .py만 추렸다(files-to-prompt -e py).
     src: https://arxiv.org/pdf/2501.13742 (2025-01 (arXiv))

(1) 규모: 5개 저장소 전체 이력 합계 ~11.6GB이나 ClickHouse(9.8GB)가 84%를 차지하고, 나머지 4개는 87MB~671MB에 그친다. 문서/사이트 저장소가 코드 저장소보다 큰 경우가 5개 중 4개(docs.getdbt.com은 dbt-core의 19배)라서, 기존 문서 미러를 이미 감당하는 vendor 레이어에 코드 미러를 더해도 저장량 증가는 지배적이지 않다. (2) 권장 기법: shallow(--depth)는 GitHub 공식 블로그가 일회성 빌드 외 비권장이고 과거 태그 다중 보관에 구조적으로 부적합. 적합한 조합은 blobless clone(--filter=blob:none) + git worktree — 객체 저장소는 공유되어 .git 측 N버전 추가 비용은 버전 간 고유 blob뿐이지만, '추가 비용이 delta뿐'은 절반만 참으로, rg 검색이 요구하는 워킹트리는 버전당 통으로 든다(Spark 버전당 ~198MB). (3) 오프라인 충돌: blobless는 공식 문서상 promisor remote 온라인 접속을 요구하므로, '온라인일 때 버전별 워크트리를 만들어 blob를 상주시키는' 운용 규율이 전제되어야 캐시 계약(오프라인 정독)과 양립한다. (4) 노이즈: Spark는 테스트·픽스처가 워킹트리의 58%(골든 파일만 30%)라 .rgignore(ripgrep 최우선순위 ignore) 한 장이 검색 코퍼스를 절반 이하로 줄인다. (5) 유지비: 태그 고정 미러는 갱신 0이 원칙이나 예외 둘 — 태그는 기술적으로 가변이며 tj-actions 사고(2025-03)처럼 소급 재작성될 수 있고(단 git은 fetch된 태그를 자동 덮어쓰지 않으므로 미러는 오히려 보호됨), release branch는 6~18개월간 patch 태그가 계속 신설되므로 '최신 patch 추적'은 주기적 git fetch(증분 비용만)가 필요하다. 종합 판정: 코드 미러는 캐시 계약(외부 유래·버전 종속·재생성 가능·인간 저작물 제로)과 부합하며, 실무 규약은 [blobless bare clone 1개 + 화이트리스트된 태그의 worktree 소수 + .rgignore]가 예산(2-3주당 30-45분) 내에서 성립한다. 단 ClickHouse만은 이력 9.8GB라 blobless 필수이고 submodule(contrib) 비용은 미측정.

핵심 결론 재료. (1) 버전 고정 원격 코드 검색은 사실상 막혀 있다: GitHub 코드 검색은 웹 UI·REST API 모두 공식 문서로 "default branch만" 확정(태그/과거 버전 원격 검색 불가), grep.app도 rev 문법이 문서화돼 있지 않다. 유일한 원격 예외는 sourcegraph.com — 무인증 태그 고정 검색(spark@v3.5.1)이 2026-08-08 실측으로 동작하지만 count:1에 10초+로 느리고, 2024년 본체 비공개화·공개 색인 축소 등 지속성 리스크가 커서 10-20년 시스템의 의존처로는 부적합. 따라서 (a) 코드 편입은 로컬이 정답이며, 캐시 계약(외부 유래·버전=tag·재생성 가능·인간 저작물 제로)과 완전 정합한다. 최소 형태는 버전별 디렉토리 복사가 아니라 풀 clone 1개 + git grep <tree-ish>(checkout 불필요)이고, 검색 성능은 무색인 rg로 충분(커널 트리 75k 파일 regex 0.08초; Spark git 578MB·ClickHouse만 10GB급). 색인형이 필요해지면 sourcebot(zoekt 기반, revisions.tags glob으로 태그 고정 색인 최대 64 rev, MCP 서버는 유료 라이선스 필요, 활발히 개발 중)이 유일하게 살아있는 자가호스팅 선택지다. (2) 이슈 편입은 계약 위반: 이슈는 버전 종속이 아니라 시점 종속·연속 변이 데이터이고(GitHub issues에는 구조적 버전 필드 자체가 없음), 소스도 기술별 이원화(Spark·Kafka 정본은 JIRA 58,235/19,618건, ClickHouse·dbt는 GitHub 30,100/8,692건)라 단일 수집 규약이 성립하지 않는다. JIRA만 affectedVersion으로 버전 절단이 가능(SPARK 4.0.0 → 5,881건). 규모상 로컬 미러 없이 인증 API on-demand(5,000 req/hr)로 충분하므로, 이슈는 vendor 편입 대신 질의 시점 조회 + 필요한 판단만 canon으로 승격하는 편이 계약에 맞다.

이슈 코퍼스의 가치는 상용에서 실증된다 — kapa.ai(공식 커넥터, '문서에 없는 워크어라운드가 이슈에 있다'), Dosu(LangChain·Airflow 등 5,955+ repos), Glean(issues를 1급 색인 대상) 3사 모두 GitHub issues를 색인한다. 그러나 세 가지가 사용자의 vendor 캐시 계약과 어긋난다. (1) 셋 다 '필터링된 부분집합'만 넣는다: kapa는 state/나이/라벨 필터와 라벨별 복수 소스를 계약의 일부로 삼고, 자사 RAG 모범사례에서 이슈·티켓류를 recency+authority 필터가 필요한 2급 소스로 격하한다. 중복률 10–30%(연구 종합)라는 구조적 노이즈가 그 이유다. SWE-bench도 raw 이슈가 아니라 'PR로 해결+테스트 검증' 통과분만 태스크화한다. (2) '버전별' 조직은 원천 데이터상 성립하지 않는다: GitHub API 실측으로 ClickHouse 이슈의 milestone 사용률 0.0%(30,100/30,100 무-milestone), dbt-core 16.2%. JIRA도 KAFKA affectedVersion 39.9%(Bug 61.5%), SPARK 83.9%로 프로젝트별 편차가 크고, Falessi(TOSEM 2021, Apache 212개 프로젝트 12.5만 defect)는 채워진 affected version조차 과반(51%)에서 사용 불가라고 보고한다. 즉 vendor 레이어의 '버전=git tag/디렉토리' 규약을 이슈에 적용할 수 없다 — 성립하는 조직 축은 라벨(실측 91–94% 사용)과 closed 상태다. (3) 규모: 4개 대상 기술만으로 11만+ 건이라 전량 미러는 '무색인 rg+정독' 운영 모델·유지비 예산과 충돌한다. 종합 판정 재료: 이슈는 캐시 계약 중 외부 유래·재생성 가능(REST API로 언제든 재수집, 이번 실측이 그 증명)·인간 저작물 제로는 충족하지만 '버전 종속' 축이 무너지므로, 넣는다면 버전별 미러가 아니라 '필터된 스냅샷'(closed+특정 라벨, 필요 시점 질의-수집)이라는 별도 계약이 필요하다. 참고로 상용 3사의 용도(유입 질문 1건에 과거 코퍼스 매칭하는 지원 봇/중복 탐지)는 사용자의 용도(인간+에이전트가 버전 맥락에서 브라우징·정독)와 접근 패턴이 달라, 상용 실증을 개인 KB 미러의 직접 근거로 삼기엔 한 단계 번역이 필요하다.

결론 재료: (a) 버전별 코드는 캐시 계약에 완전 부합 — 외부 유래·tag(→SHA)로 버전 종속·clone은 rate limit 없이 바이트 결정적 재생성·인간 저작물 제로. 실측 비용은 dbt 87MB/Kafka 298MB/Spark 578MB/ClickHouse 9.8GB(API size 필드)로, ClickHouse만 shallow/partial clone 축소가 필요한 수준. 유일 리스크는 태그 가변성(tj-actions 사건이 실증)이며 commit SHA를 vendor 메타에 고정 기록하면 방어된다. 선례도 정확히 이 경계에 있다 — Sourcebot(코드만 미러·색인, MCP로 에이전트 제공), SWE-bench(commit 고정 스냅샷=에이전트 환경), Google 모노레포 vendoring. (b) 이슈 전량 미러는 계약 4조항 중 3개와 어긋난다: ① 버전 종속이 아니라 시간 스트림이다(GH Archive가 이슈를 불변 이벤트 로그로 모델링하는 이유 — 스냅샷은 시점 절단면일 뿐 완결 산출물이 아님) ② 재생성이 API 정책에 묶인다 — ClickHouse 30,100 이슈+3만 이상 댓글은 PAT 5,000req/hr 하에 수천 요청·수 시간이고, comments endpoint가 30,000건(page 300)에서 422로 잘리는 것을 실측해 시간창 분할 엔지니어링 없이는 전량 수집 자체가 불가 ③ 재수집이 비결정적(이슈는 수정·삭제됨). 결정타로 Spark·Kafka는 JIRA가 정식 트래커라(Kafka는 has_issues=false 실측) GitHub API 미러가 대상 기술의 절반에서 성립하지 않는다. 권고 재료: 이슈는 전량 미러 대신 ① 질의 시 gh/JIRA로 조회(원격이 곧 색인) ② 버전 귀속 정보는 릴리스 노트/CHANGELOG 미러로 대체(Keep a Changelog가 정의하는 '버전별 완결 큐레이션'이라 캐시 계약에 부합) ③ 유용했던 개별 이슈는 vendor가 아니라 canon에 인용·발췌로 승격 — 선별은 저작 행위라 '인간 저작물 제로' 조항상 vendor에 둘 수 없다.

'이슈는 버전 축 산출물이 아니라 이벤트 스트림'이라는 존재론적 해석은 이 사실들로부터의 저자 추론이지만 GH Archive의 설계와 정합적.
  [CONFIRMED] SWE-bench는 특정 base commit checkout 스냅샷을 Docker로 동결하고 이슈 텍스트는 과제 시점 동결 사본만 사용 — '코드=커밋 고정, 이슈=시점 동결'이 재현성 분야 표준
       note: 실질 내용은 1차 소스로 확인: swebench.com datasets 문서에 base_commit(checkout 대상 커밋 해시)·problem_statement(동결된 이슈 텍스트) 필드가 명시되고, docker_setup 페이지는 "Docker-based evaluation harness to ensure consistent, reproducible results"를 명시. 단 claim이 제시한 인용문 "Each SWE-bench instance pairs an issue description with a codebase snapshot checked out at a specific Git commit"은 인용된 URL(docker_setup 페이지)에 없음 — 2차 소스(해설 글)에 도는 표현으로, 출처 표기가 부정확. 내용은 참, 인용 귀속만 어긋남.
  [CONFIRMED] 릴리스 노트/CHANGELOG는 버전별 완결·동결 산출물(Keep a Changelog 정의)이라 캐시 계약에 부합하고, '유용 이슈 선별 보관'은 큐레이션이라 정본 성격
       note: keepachangelog.com 1.1.0에서 "a curated, chronologically ordered list of notable changes for each version" 정의를 축자 확인했고, "Using commit log diffs as changelogs is a bad idea: they're full of noise"도 원문에 실재. 외부 검증 가능한 부분은 전부 정확. 다만 후반부(선별 보관 = 저작 행위 = canon 성격, '인간 저작물 제로' 조항과의 충돌)는 외부 소스가 아니라 사용자 프로젝트 내부 계약에 대한 저자의 논증 — 논리는 일관되나 외부 사실 검증 대상은 아님.
