하나의 질문: **도메인이 자기 분석 데이터를 "제품"으로 공유한다는 것은 무엇을 요구하며, 그
제품이 최소한 갖춰야 할 속성은 무엇인가.**

[데이터 메시](../concepts/data-mesh.md)의 둘째 원칙이다.
[도메인 소유권 원칙](../concepts/domain-ownership-principle.md)이 낳는 부작용에 대한 답으로
설계되었다.

## 무엇에 대한 응답인가

- 원래 있던 문제 — **기존 분석 데이터 아키텍처의 오래된 난제 하나는 데이터를 쓰는 데 드는 높은
  마찰과 비용이다: 발견하고, 이해하고, 신뢰하고, 탐색하고, 궁극적으로 품질 있는 데이터를
  소비하는 일이다** (3장, p.29).[^dehghani2022]
  - 저자가 드는 실측 — **데이터 과학 플랫폼 회사 Anaconda의 2022년 저술 시점 기준 최근 보고서 "The State of Data
    Science 2020"은 데이터 과학자 시간의 거의 절반이 데이터 준비 — 데이터 적재와 정화 — 에
    쓰인다는 것을 발견한다** (3장, p.29).[^dehghani2022]
- 데이터 메시가 이 문제를 **악화시킬** 수 있다는 것이 이 원칙의 출발점이다 — **손대지 않으면 이
  문제는 데이터 메시에서 오히려 심해진다. 데이터를 제공하는 자리와 팀, 곧 도메인의 수가 늘기
  때문이다** (3장, p.29).[^dehghani2022]
- 그래서 이 원칙이 무엇을 요구하는지 — **제품으로서의 데이터는 도메인이 제공하는 분석 데이터가
  제품으로 다뤄지고, 그 데이터의 소비자가 고객으로 — 행복하고 만족스럽게 — 다뤄질 것을
  기대한다** (3장, p.29).[^dehghani2022]
- 책임의 방향이 뒤집힌다 — **이전 패러다임과 비교해 제품으로서의 데이터는 책임 모델을 역전한다.
  데이터 레이크나 데이터 웨어하우징 아키텍처에서는 품질과 무결성을 갖춘 데이터를 만드는 책무가
  원천의 하류에 있고 중앙 데이터 팀에 남는다. 데이터 메시는 이 책임을 데이터의 원천 가까이로
  옮긴다** (3장, p.30).[^dehghani2022]
  - 새로운 발상은 아니라고 저자가 스스로 적는다 — **이 전환은 데이터 메시 고유의 것이 아니다.
    사실 지난 10년간 우리는 테스트와 운영에서 시프트 레프트(shift left) 추세를 보아 왔고, 그
    근거는 문제를 원천 가까이에서 다룰 때 더 싸고 효과적이라는 것이다** (3장,
    p.30).[^dehghani2022]
- 그래서 메시 위에서 오가는 단위가 재정의된다 — **메시에서 공유되는 것은 단순히 데이터가 아니라
  데이터 프로덕트(data product)라고까지 말하겠다** (3장, p.30).[^dehghani2022]
- 낱말의 범위를 좁히는 주석이 붙는다 — **제품으로서의 데이터는 데이터가 모델링되고 공유되는
  방식에 제품 사고를 적용하는 것이다. 제품을 파는 것(product selling)과 혼동하지 말 것**
  (3장, p.31).[^dehghani2022]

## 제품 사고를 데이터에 적용한다

- 근거로 삼는 제품론 — **INSPIRED에서 Marty Cagan은 성공한 제품이 공통으로 갖는 세 특성이
  있음을 설득력 있게 보인다: 실현 가능하고(feasible), 가치 있고(valuable), 사용 가능하다
  (usable)** (3장, p.29).[^dehghani2022] 데이터 프로덕트는 그 교집합에 놓이도록 표준화된
  특성을 갖는 개념으로 정의된다 (3장, pp.29–30).[^dehghani2022]
  - 셋 중 "실현 가능"은 이 원칙이 담당하지 않는다 — **4장이 데이터 프로덕트를 짓는 것을 실현
    가능하게 만드는 방법을 서술한다** (3장, p.30).[^dehghani2022]
- 이 전환이 어디서 왔는지 — **지난 10년간 고성과 조직은 내부 운영 기술을 외부 기술과 마찬가지로
  제품처럼 다루는 발상을 받아들였다. 그들은 내부 개발자를 고객으로 대하고 그 만족을 성공의
  신호로 삼는다** (3장, p.31).[^dehghani2022] 저자가 드는 두 사례 계열은 **내부 플랫폼에 제품
  관리 기법을 적용하는 것(예: Spotify Backstage)과 API를 제품으로 다루는 것(예: Square
  APIs)**이다 (3장, p.31).[^dehghani2022]
- 데이터에는 그 재료가 빠져 있었다 — **운영 팀은 여전히 자기 데이터를 사업을 돌린 부산물로
  인식하고, 다른 누군가 — 예컨대 데이터 팀 — 가 그것을 주워 제품으로 재활용하도록 남겨 둔다**
  (3장, p.31).[^dehghani2022]
- 제품 소유권이 데이터에 적용된 모습은 하나의 도메인이 **서로 다른 사용자에게 서로 다른 양식을
  내놓는 것**으로 나타난다 — 저자의 예에서 미디어 플레이어 도메인은 **무한 이벤트 로그로 노출된
  준실시간 플레이 이벤트와, 객체 저장소에 직렬화된 파일로 노출된 집계 플레이 세션이라는 두 가지
  다른 종류의 데이터를 제품으로 제공한다** (3장, p.32).[^dehghani2022]
- 이 원칙은 역할 신설을 요구한다 — **좋은 의도만으로 데이터를 제품처럼 다루는 일이 그냥 일어나지는
  않는다. 그래서 이 원칙은 도메인에 데이터 프로덕트 소유자(domain data product owner)와 데이터
  프로덕트 개발자(data product developer)라는 새 역할을 도입한다** (3장, p.30).[^dehghani2022]

| 역할 | 무엇을 책임지는가 |
|---|---|
| 데이터 프로덕트 개발자 | 데이터 프로덕트가 살아 사용되는 동안 그것을 개발·서빙·유지하는 책임 (3장, p.42) |
| 데이터 프로덕트 소유자 | 도메인 데이터 프로덕트가 가치를 전달하고, 데이터 사용자를 만족시키고 늘리며, 수명 주기를 유지하는 데서의 성공에 대한 책무 (3장, p.42) |

## 데이터 제품 설계가 소프트웨어 제품 설계와 갈리는 자리

- 차이는 용법의 무한성에 있다 — **데이터 프로덕트 소유권과 다른 종류의 제품 사이의 차이는 데이터
  용법의 무경계적 성질에 있다. 어떤 데이터가 다른 데이터와 결합되어 궁극적으로 통찰과 행동으로
  바뀌는 방식 말이다. 어느 시점에서든 데이터 프로덕트 소유자는 오늘 알려진 실행 가능한 용법을
  알거나 계획할 수 있지만, 오늘 생산되는 데이터의 미래 용법 중 상당 부분은 그들의 상상 너머에
  미지로 남는다** (3장, p.32).[^dehghani2022]
- 그 무게는 원형마다 다르다 — **이는 원천 정렬 도메인에 더 참이고 소비자 정렬 도메인에 덜
  참이다** (3장, p.32).[^dehghani2022] 그래서 원천 정렬 데이터 프로덕트는 **즉각적인 알려진
  용법과 미지의 용법 사이에서 균형을 잡아야 하며, 어떻게 쓰일지에 대해 너무 많은 가정을 하지
  않은 채 사업의 실재를 가능한 한 가깝게 데이터로 모델링하려 애쓰는 것 외에 선택지가 없다**
  (3장, pp.32–33).[^dehghani2022]
  - 저자가 드는 안전한 선택 — **모든 플레이 이벤트를 무한한 고해상도 로그로 포착하는 것은 안전한
    선택이다. 그것은 오늘 포착된 데이터에서 다른 변환을 짓고 새 통찰을 추론할 수 있는 미래
    사용자의 스펙트럼을 열어 둔다** (3장, p.33).[^dehghani2022]
- 저자의 결론 한 줄 — **이것이 데이터 제품 설계와 소프트웨어 제품 설계의 주된 차이다** (3장,
  p.33).[^dehghani2022]

## 여덟 가지 기본 사용성 속성

- 지위 — **데이터 프로덕트가 유용하다고 여겨지려면 갖춰야 할, 협상 불가능한 기본 특성의
  집합이다. 이 특성들은 도메인이나 원형과 무관하게 모든 데이터 프로덕트에 적용된다. 나는 이것을
  기본 데이터 프로덕트 사용성 속성(baseline data product usability attributes)이라 부른다**
  (3장, p.33).[^dehghani2022] 저자는 이 여덟을 두문자 **DAUTNIVS**로 묶는다 (3장,
  그림 3-3).[^dehghani2022]
- 시점 한정 — **이 사용성 특성은 데이터 사용자의 경험을 축으로 잡혀 있다. 기술적 능력을 표현하려는
  것이 아니다** (3장, p.34).[^dehghani2022] 기존 원칙과의 관계도 밝힌다 — **과거에 FAIR 데이터로
  알려진 것 — 발견 가능성·접근성·상호운용성·재사용성 원칙을 만족하는 데이터 — 에 더하는
  것이다** (3장, p.34).[^dehghani2022]

### ① 발견 가능(Discoverable)

- 기존 방식 — **발견 가능성의 전통적 구현은 이용 가능한 데이터셋을 나열하는 중앙 레지스트리나
  카탈로그이며, 각 데이터셋에 대한 소유자·위치·샘플 데이터 등의 부가 정보를 담는다. 이 정보는
  흔히 중앙 데이터 팀이나 거버넌스 팀이 사후에 큐레이션한다** (3장, p.34).[^dehghani2022]
- 데이터 메시의 방식 — **데이터 메시의 데이터 프로덕트 발견 가능성은 데이터 프로덕트 스스로가
  발견 가능성 정보를 의도적으로 제공하는 시프트 레프트 해법을 받아들인다. 개별 데이터 프로덕트가
  자기 수명 주기의 여러 지점 — 빌드·배포·실행 — 에서 표준화된 방식으로 그 정보를 제공하는 데
  의존한다** (3장, p.34).[^dehghani2022]
  - 무엇을 제공하는가 — **원천, 소유자, 적시성·품질 지표 같은 런타임 정보, 샘플 데이터셋, 그리고
    가장 중요하게는 소비자가 기여한 정보(그 데이터가 가능하게 한 상위 용법과 애플리케이션)**
    (3장, p.34).[^dehghani2022] 그 반대편 서술은
    [메타데이터 관리](../concepts/metadata-management.md)에 있다.

### ② 주소 지정 가능(Addressable)

- **데이터 프로덕트는 데이터 사용자가 프로그램으로든 수동으로든 접근할 수 있는 영구적이고 유일한
  주소를 제공한다** (3장, p.35).[^dehghani2022]
- 주소 체계가 흡수해야 하는 변화 넷 (3장, p.35):[^dehghani2022] **데이터 프로덕트의 의미·구문
  변경(스키마 진화), 시간에 따른 새 데이터의 지속적 릴리스(파티셔닝 전략과 시간 창별 튜플
  묶기), 새로 지원되는 데이터 접근 양식(직렬화·표현·질의의 새 방법), 변하는 런타임 행동 정보
  (예: 서비스 수준 목표·접근 로그·디버그 로그).**
- 진입점의 형태 — **데이터 프로덕트는 그 문서·서비스 수준 목표·서빙하는 데이터를 포함해 그
  프로덕트에 관한 모든 정보로 들어가는 입구 역할을 하는, 주소 지정 가능한 집합 루트(addressable
  aggregate root)를 가져야 한다** (3장, p.35).[^dehghani2022]

### ③ 이해 가능(Understandable)

- 두 층을 이해해야 한다 — **의미(semantics)와, 데이터가 인코딩된 다양한 구문(syntax)이다**
  (3장, p.35).[^dehghani2022]
- 의미 쪽 — **각 데이터 프로덕트는 의미적으로 일관된 데이터, 곧 특정한 뜻을 지닌 데이터를
  제공한다. 데이터 사용자는 이 뜻을 이해해야 한다 — 데이터 프로덕트가 어떤 종류의 개체를
  캡슐화하는지, 개체들 사이의 관계는 무엇인지, 그리고 인접한 데이터 프로덕트는 무엇인지**
  (3장, p.35).[^dehghani2022]
- 동반 자료 — **샘플 데이터셋과 예시 소비자 코드가 이상적으로 이 정보에 동반된다** (3장,
  p.36).[^dehghani2022] 그리고 **계산 문서(computational notebooks) 같은 동적·계산 문서가
  데이터 프로덕트의 이야기를 하는 훌륭한 동반자다 — 데이터의 문서화와 그것을 쓰는 코드를 함께
  담고, 코드의 결과를 시각적으로 즉시 보여 준다** (3장, p.36).[^dehghani2022]
- 사회적 층도 셈에 넣는다 — **이해는 사회적 과정이다. 우리는 서로에게서 배운다. 데이터 프로덕트는
  사용자들이 자기 경험과 활용법을 공유할 수 있게 소통을 촉진한다** (3장, p.36).[^dehghani2022]
- 기준선 — **사용 가능한 데이터 프로덕트를 이해하는 데는 손잡아 주기(hand-holding)가 필요 없다.
  셀프서브 방식의 이해가 기본 사용성 특성이다** (3장, p.36).[^dehghani2022]

### ④ 신뢰 가능·진실(Trustworthy and truthful)

- 신뢰의 정의를 빌려 온다 — Rachel Botsman의 **"미지와의 자신 있는 관계"(a confident relationship
  with the unknown)** (3장, p.36).[^dehghani2022] 저자가 다시 쓰는 형태는 **알려진 것과 미지
  사이의 다리**이며, **데이터 프로덕트는 데이터 사용자가 그 데이터에 대해 자신 있게 아는 것과,
  신뢰하기 위해 알아야 하지만 모르는 것 사이의 간극을 닫아야 한다** (3장, p.36).[^dehghani2022]
- 무엇을 확신해야 하는가 — **데이터 프로덕트가 진실하다는 것, 곧 사업의 사실을 올바르게
  대표한다는 것을 데이터 사용자가 자신 있게 알아야 한다. 데이터가 실제 일어난 사건의 실재를
  얼마나 가깝게 반영하는지, 업무 사실에서 만들어진 집계와 투영이 진실할 확률이 얼마인지를
  자신 있게 알아야 한다** (3장, p.36).[^dehghani2022]
- **정면 대비** — **전통적 데이터 관리 접근에서는 오류가 있고 사업의 진실을 반영하지 않으며
  그냥 신뢰할 수 없는 데이터를 추출해 온보딩하는 것이 흔하다. 여기가 중앙집중 데이터 파이프라인
  노력의 대부분이 집중된 자리다 — 반입 이후의 데이터 정화다** (3장, p.37).[^dehghani2022]
  - 데이터 메시의 처방 — **데이터 프로덕트의 소유자가 자기 도메인에 특유한, 받아들일 만한 수준의
    품질과 신뢰성을 데이터 프로덕트의 본질적 특성으로서 소통하고 보증해야 한다. 이는 데이터
    프로덕트 생성 시점에 정화와 자동화된 데이터 무결성 테스트를 수행한다는 뜻이다** (3장,
    p.37).[^dehghani2022] 반대편의 처방은
    [데이터 품질 관리](../concepts/data-quality-management.md)에 있다.
- **계보의 지위가 낮아진다** — **각 데이터 프로덕트에 신뢰성을 짓는 규율이 자리 잡으면, 조사
  프로세스와 계보 트리를 훑는 탐지 기법으로 신뢰를 확립할 필요가 줄어든다는 것이 내 의견이다**
  (3장, p.37).[^dehghani2022]
  - 다만 없어지지는 않는다 — **그렇게 말했지만 데이터 계보(data lineage)는 사후 근본 원인 분석,
    디버깅, 데이터 컴플라이언스 감사, ML 훈련을 위한 데이터 적합성 평가 같은 몇몇 시나리오에서
    중요한 요소로 남는다** (3장, p.37).[^dehghani2022]

### ⑤ 네이티브 접근 가능(Natively accessible)

- 문제 설정 — **사용성과, 특정 데이터 사용자가 자기 네이티브 도구로 얼마나 쉽게 접근할 수
  있는가 사이에는 직접적인 연결이 있다** (3장, p.38).[^dehghani2022]
- 저자가 세는 사용자 스펙트럼 — **스프레드시트로 데이터를 탐색하는 데 익숙한 데이터 분석가,
  질의 언어로 통계 모델을 만들어 시각화나 리포트를 내는 데이터 분석가, 데이터를 큐레이션·구조화해
  데이터 프레임을 소비해 ML 모델을 훈련하는 데이터 과학자, 실시간 이벤트 스트림이나 풀 기반
  API를 기대하는 데이터 집약 애플리케이션 개발자** (3장, p.38).[^dehghani2022]
- 구현 두 갈래 — **데이터의 다중 언어 저장(polyglot storage)으로 구현하거나, 같은 데이터 위에
  여러 읽기 어댑터를 짓는 것으로 구현할 수 있다** (3장, p.38).[^dehghani2022]

### ⑥ 상호운용 가능(Interoperable)

- 문제 — **분산 데이터 아키텍처의 주된 우려 하나는 도메인에 걸쳐 데이터를 상관시키고 이어 붙이는
  능력이다: 조인·필터·집계** (3장, p.39).[^dehghani2022]
- 표준화해야 하는 일곱 항 (3장, p.39):[^dehghani2022] **필드 타입(공통으로 명시 정의된 타입
  체계), 다의어 식별자(데이터 프로덕트 경계를 넘는 개체를 보편적으로 식별), 데이터 프로덕트 전역
  주소(각 데이터 프로덕트에 할당된 유일 전역 주소, 이상적으로는 균일한 스킴), 공통 메타데이터
  필드(데이터가 발생한 시각과 기록된 시각의 표현 등), 스키마 링킹(다른 데이터 프로덕트가 정의한
  스키마·타입을 링크·재사용하는 능력), 데이터 링킹(다른 데이터 프로덕트의 데이터에 링크·매핑하는
  능력), 스키마 안정성(하위 호환을 존중하는 스키마 진화 접근).**
- 저자의 위치 규정 — **상호운용성은 어떤 분산 시스템 설계에서든 기초이며, 데이터 메시도 예외가
  아니다** (3장, p.39).[^dehghani2022]

### ⑦ 그 자체로 가치 있음(Valuable on its own)

- **데이터 프로덕트는 다른 데이터 프로덕트와 조인되고 상관되지 않아도 그 자체로 가치 있고 의미
  있는 데이터셋을 담아야 한다. 데이터 프로덕트가 그 자체로 아무 가치도 서빙하지 않는다면 존재해서는
  안 된다** (3장, p.40).[^dehghani2022]
- **마이그레이션 안티패턴** — **웨어하우스 아키텍처에서 데이터 메시로 옮길 때 흔한 안티패턴이
  있다: 웨어하우스 테이블을 데이터 프로덕트로 직접 매핑하면 아무 가치 없는 데이터 프로덕트가
  만들어질 수 있다. 데이터 웨어하우스에는 개체 사이의 상관을 최적화하는 글루 테이블(일명 팩트
  테이블)이 있다. 한 종류 개체의 식별자를 다른 종류로 매핑하는 식별자 테이블이다. 그런 식별자
  테이블은 다른 테이블에 조인되지 않으면 그 자체로 의미도 가치도 없다. 단지 조인을 돕는 기계적
  구현일 뿐이다** (3장, p.40).[^dehghani2022]
  - 그 자리를 무엇이 대신하는가 — **메시 전반에서 기계가 정보를 상관시키게 하려고만 존재하는
    기계적 데이터 프로덕트는 없다. 색인이나 팩트 테이블 같은 기계 최적화는 플랫폼이 자동으로
    만들고 데이터 프로덕트에서 감춰야 한다** (3장, p.40).[^dehghani2022] 그 글루 테이블의
    본가는 [팩트 테이블](../concepts/fact-table.md)이다.

### ⑧ 안전(Secure)

- 검증 지점이 옮겨진다 — **데이터 메시 같은 분산 아키텍처에서 접근 통제는 데이터 프로덕트가
  데이터·접근·읽기·쓰기의 흐름 바로 그 자리에서 검증한다. 접근 통제 정책은 동적으로 바뀔 수
  있다. 데이터 프로덕트에 접근하는 모든 지점에서 지속적으로 재평가된다** (3장,
  p.40).[^dehghani2022]
- 접근은 이분법이 아니다 — **많은 경우 사용자가 실제 레코드를 볼 수 없더라도 데이터의 모양을
  보고 통계적 특성으로 평가할 충분한 권한은 가질 수 있다** (3장, p.40).[^dehghani2022]
- 정의와 강제가 갈린다 — **접근 통제 정책은 중앙에서 정의되되 런타임에는 개별 데이터 프로덕트가
  강제한다. 데이터 프로덕트는 코드로서의 보안 정책(security policy as code) 실천을 따른다.
  이는 보안 정책을 버전 관리되고 자동으로 테스트·배포·관측되며 계산적으로 평가·강제될 수 있는
  방식으로 쓴다는 뜻이다** (3장, p.40).[^dehghani2022]
- 그 정책이 다루는 관심사 다섯 (3장, pp.40–41):[^dehghani2022] **접근 통제(누가·무엇을·어떻게),
  암호화(디스크·메모리·전송 중 중 어느 것을 어떤 알고리즘으로, 키 관리와 유출 시 영향 반경
  최소화), 기밀 수준(개인 식별 정보·개인 건강 정보 등 어떤 기밀 정보를 담는가), 데이터
  보존(정보를 얼마나 오래 보관해야 하는가), 규제와 협약(GDPR·CCPA·도메인별 규제·계약상 합의).**

## 신뢰를 재는 SLO

- 신뢰 간극을 닫는 장치는 객관적 측정치다 — **데이터 프로덕트의 서비스 수준 목표(service-level
  objectives, SLOs)를 보증하고 소통하는 것이다. 데이터를 둘러싼 불확실성을 제거하는 객관적
  측정치다** (3장, p.36).[^dehghani2022]
- 저자가 드는 일곱 항 (3장, p.37):[^dehghani2022]

| SLO | 원어 | 무엇을 재는가 |
|---|---|---|
| 변경 간격 | Interval of change | 데이터의 변경이 얼마나 자주 반영되는가 |
| 적시성 | Timeliness | 업무 사실이 발생한 시각과 데이터 사용자에게 이용 가능해지는 시각의 어긋남 |
| 완전성 | Completeness | 필요한 모든 정보의 이용 가능 정도 |
| 데이터의 통계적 모양 | Statistical shape of data | 분포·범위·부피 등 |
| 계보 | Lineage | 원천에서 여기까지의 데이터 변환 여정 |
| 시간에 따른 정밀도와 정확도 | Precision and accuracy over time | 시간이 지남에 따른 업무 진실성의 정도 |
| 운영 품질 | Operational qualities | 신선도·일반 가용성·성능 |

- 계보가 여기에 SLO 항목으로 들어와 있다는 점에 유의한다 — 앞의 "신뢰 가능" 절에서 저자는 계보
  **의존**을 낮추자고 하면서도, 계보를 **제공**하는 것은 데이터 프로덕트의 의무로 남긴다 (3장,
  p.37).[^dehghani2022] 낮아지는 것은 계보의 제공 의무가 아니라 신뢰 확립 수단으로서의
  일차성이다.

## 다섯 가지 전환

### ① 도메인에 데이터 프로덕트 소유권을 포함시킨다

- 저자가 배치하는 계보 — **지난 10년간 팀은 기능 분할에서 교차 기능으로 계속 옮겨 왔다. DevOps
  운동은 업무 서비스를 짓는 것과 운영하는 것 사이의 간극을 닫고 dev·ops 교차 기능 팀을 만들었다.
  고객 집착적 제품 개발은 설계와 제품 소유권을 개발자에게 더 가까이 가져왔다** (3장,
  p.41).[^dehghani2022] 분석 데이터를 제품으로 도입하는 것은 그 목록에 얹히는 다음 항이다.
- 배치 규칙 — **도메인마다 이 역할들을 정의하고, 도메인의 복잡도와 데이터 프로덕트의 수에 따라
  한 명 또는 여러 명을 배정하라** (3장, p.42).[^dehghani2022]
- 팀 대 프로덕트의 대응은 일대일이 아니다 — **각 도메인 팀은 하나 또는 여러 데이터 프로덕트를
  서빙할 수 있다. 기존 운영 도메인에 자연스럽게 들어맞지 않는 데이터 프로덕트를 서빙하기 위해
  새 팀을 만드는 것도 가능하다** (3장, p.45).[^dehghani2022]

### ② 변화를 만들기 위해 어휘를 다시 짠다

- **반입에서 소비로** — **데이터 분석에서 흔히 쓰는 용어 하나가 반입(ingestion)이다. 상류
  원천에서 데이터를 받는 것인데, 그 원천은 흔히 자기 운영의 부산물로 데이터를 배설한(egested)
  믿을 수 없는 원천이다. 그러면 하류 파이프라인의 일은 가치를 만들기 위해 소비되기 전에 그
  데이터를 반입하고 정화하고 처리하는 것이 된다** (3장, p.42).[^dehghani2022]
  - 제안 — **데이터 메시는 상류 데이터를 받는 것을 반입에서 소비(consumption)로 다시 짤 것을
    제안한다. 미묘한 차이는 상류 데이터가 이미 정화·처리되어 소비 준비가 된 채로 서빙된다는
    것이다** (3장, p.42).[^dehghani2022] 그 어휘가 쓰이는 자리는
    [수명 주기의 반입 단계](../concepts/ingestion-in-the-lifecycle.md)다.
- **추출에서 발행·서빙·공유로** — **ETL(extract, transform, load)에서 쓰이는 추출(extraction)이라는
  낱말도 비판적으로 평가되어야 한다. 추출은 제공자에게 수동적 역할을, 소비자에게 침입적 역할을
  환기한다. 우리가 알듯이, 자기 애플리케이션 외의 외부 사용에 최적화되지 않은 운영 데이터베이스에서
  데이터를 추출하는 것은 온갖 병리적 결합과 취약한 설계를 만든다. 대신 언어를 발행(publish)·
  서빙(serve)·공유(share)로 옮길 수 있다** (3장, p.42).[^dehghani2022]
- 어휘론의 근거로 인지언어학을 든다 — **George Lakoff는 Metaphors We Live By에서 논쟁이라는
  개념을 둘러싼 언어를 전쟁에서 춤으로 옮길 때의 결과를 우아하게 보인다. 이 예기치 못한 언어의
  재구성은 심오한 행동적 영향을 갖는다** (3장, pp.42–43).[^dehghani2022]

### ③ 자산이 아니라 제품으로 생각한다

- 비판 대상 — **"데이터는 자산이다", "데이터는 자산처럼 관리되어야 한다". 이 어구들이 빅데이터
  관리의 어법을 지배해 왔다. 수십 년간 엔터프라이즈 아키텍처 방법론의 Open Group 표준인 TOGAF는
  명시적으로 "Data Is an Asset"을 데이터 원칙의 첫째로 적어 두었다** (3장,
  p.43).[^dehghani2022]
- 그 은유가 낳은 결과 — **자산으로서의 데이터는 성공을 허영 지표(vanity metrics) — 보기 좋거나
  기분 좋게 만들지만 성과에 영향을 주지 않는 지표 — 로 재게 만들었다. 레이크나 웨어하우스에
  포착된 데이터셋과 테이블의 수, 또는 데이터의 부피 같은 것이다** (3장, p.43).[^dehghani2022]
  - 근본 성향 — **자산으로서의 데이터는 데이터를 공유하기보다 보관하고 저장하는 것을 조장한다**
    (3장, p.43).[^dehghani2022] 저자는 TOGAF 자신이 그 원칙 바로 뒤에 "Data Is Shared"를
    두었다는 점을 지적한다 (3장, p.43).[^dehghani2022]
- 대체 지표 — **제품으로서의 데이터로 은유를 바꾸고, 그와 함께 오는 관점 변화 — 예컨대 데이터의
  채택, 사용자 수, 그리고 데이터를 쓰는 만족도로 성공을 재는 것 — 를 제안한다** (3장,
  p.43).[^dehghani2022]

### ④ 신뢰하되 검증하는 데이터 문화를 세운다

- 목표 상태 — **제품으로서의 데이터 원칙은 데이터 사용자가 기본적으로 데이터의 타당성을 신뢰할
  수 있고, 자기 용법에 대한 적합성을 검증하는 데 초점을 둘 수 있는 문화로 이끄는 여러 실천을
  구현한다** (3장, p.43).[^dehghani2022]
- 현재 상태 — **2022년 저술 시점에 이런 실천이 없는 상태에서 데이터 계보는 신뢰를 확립하는 핵심 재료로
  남아 있다. 데이터 사용자는 데이터가 신뢰할 수 없다고 가정하고, 신뢰하기 전에 계보를 통한
  탐정 조사를 요구하는 것 외에 선택지가 없었다** (3장, pp.43–44).[^dehghani2022]
  - 그 불신의 원인을 셋으로 짚는다 — **제공자가 사용자와 그 필요를 볼 수 없다는 것, 데이터에
    대한 장기 책무가 없다는 것, 계산적 보증이 없다는 것** (3장, p.44).[^dehghani2022]
- 목표 문화의 이름 — **유죄 추정에서 러시아 속담 "신뢰하되 검증하라"(trust but verify)로**
  (3장, p.44).[^dehghani2022]

### ⑤ 데이터와 연산을 하나의 논리 단위로 묶는다

- 기존 직관의 진단 — **데이터 프로덕트라는 낱말을 들으면 상당수 독자가 정적인 파일이나 테이블,
  열과 행, 어떤 저장 매체를 떠올린다. 정적이라 느껴진다. 누적된 것이다** (3장,
  p.44).[^dehghani2022]
- 그 직관이 낳는 것 — **이 관점은 코드(연산)와 데이터의 분리를 낳는다. 이 경우 데이터를 유지하고
  만들고 서빙하는 코드의 분리다. 이 분리는 시간이 지나며 썩어 가는 고아 데이터셋을 만든다. 규모에
  이르면 우리는 이 분리를 데이터 스왐프(data swamps) — 퇴화한 데이터 레이크 — 로 경험한다**
  (3장, p.44).[^dehghani2022]
- 데이터 메시의 배치 — **데이터 대 코드라는 이중 양식에서 데이터와 코드를 하나의 아키텍처 단위,
  곧 특정 도메인의 고품질 데이터를 제공하는 자기 일을 하기에 구조적으로 완전한 단일 배포 단위로
  옮긴다. 하나는 다른 하나 없이 존재하지 않는다** (3장, p.44).[^dehghani2022]
- 마이크로서비스와의 대비가 결정적이다 — **차이는 코드와 데이터의 관계다. 마이크로서비스
  아키텍처에서는 데이터가 코드를 섬긴다. 코드가 업무 능력을 서빙하는 자기 일을 완수할 수 있도록
  상태를 유지한다. 데이터 프로덕트와 데이터 메시의 경우 이 관계는 역전된다: 코드가 데이터를
  섬긴다. 코드는 데이터를 변환하고, 무결성을 유지하고, 정책을 다스리고, 궁극적으로 데이터를
  서빙한다** (3장, p.44).[^dehghani2022] 그 원본 계열은
  [마이크로서비스와 서버리스](../concepts/microservices-and-serverless.md)에 있다.
- 물리 층은 여전히 갈린다 — **코드와 데이터를 호스팅하는 기저의 물리 인프라는 분리된 채로 둔다**
  (3장, p.44).[^dehghani2022]
