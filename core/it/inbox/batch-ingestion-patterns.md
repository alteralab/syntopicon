하나의 질문: **배치로 반입하기로 정하고 나면 무엇이 아직 결정되지 않은 채 남는가.**

- 배치 반입이 무엇인지부터 — **대량으로 데이터를 처리하는 것을 수반하는 배치 반입은 데이터를
  반입하는 편리한 방식인 경우가 많다. 이는 시간 간격이나 누적된 데이터의 크기에 기반해 원천
  시스템에서 데이터의 부분집합을 취함으로써 데이터가 반입된다는 뜻이다** (7장,
  p.244).[^reis2022]
- 저자들이 이 절에서 다루는 다섯 패턴 (7장, p.245):[^reis2022]
  - **스냅샷 또는 차등 추출 / 파일 기반 내보내기와 반입 / ETL 대 ELT / 삽입·갱신·배치 크기 /
    데이터 마이그레이션**

## 배치를 자르는 두 기준

- **시간 간격 배치 반입(time-interval batch ingestion)은 데이터 웨어하우징을 위한 전통적 업무
  ETL에 널리 퍼져 있다. 이 패턴은 흔히 일간 리포팅을 제공하기 위해 비업무 시간 동안 밤새 하루
  한 번 데이터를 처리하는 데 쓰이지만 다른 빈도도 쓸 수 있다** (7장, p.245).[^reis2022]
- **크기 기반 배치 반입(size-based batch ingestion)은 데이터가 스트리밍 기반 시스템에서 오브젝트
  저장으로 옮겨질 때 꽤 흔하다. 궁극적으로 데이터 레이크에서의 미래 처리를 위해 데이터를 이산
  블록으로 잘라야 한다. 어떤 크기 기반 반입 시스템은 총 이벤트 수의 바이트 크기 같은 다양한
  기준으로 데이터를 객체로 쪼갤 수 있다** (7장, p.245).[^reis2022]
- 이 두 기준은 2장이 배치의 발동 조건으로 든 것과 같다 — **배치 데이터는 미리 정해진 시간
  간격으로, 또는 데이터가 미리 설정된 크기 임계에 닿을 때 반입된다** (2장, p.41).[^reis2022]
  7장은 그 둘을 각각 **어디에서 쓰이는가**로 나눠 놓은 것이다: 시간 간격은 웨어하우스 ETL,
  크기 기반은 스트림에서 오브젝트 저장으로 내리는 착지 지점.

## 전체 스냅샷과 증분 추출

- 두 선택지 — **데이터 엔지니어는 원천 시스템의 전체 스냅샷을 포획할지 차등(differential,
  때로 증분(incremental)이라 불리는) 갱신을 포획할지 골라야 한다. 전체 스냅샷(full snapshots)
  으로 엔지니어는 각 갱신 읽기마다 원천 시스템의 현재 상태 전체를 잡는다. 차등 갱신
  (differential update) 패턴으로 엔지니어는 원천 시스템에서 마지막으로 읽은 이후의 갱신과
  변경만 당길 수 있다** (7장, p.246).[^reis2022]
- 그런데 판정이 단순하지 않다 — **차등 갱신이 네트워크 트래픽과 대상 저장 사용을 최소화하는 데
  이상적이지만, 전체 스냅샷 읽기는 그 단순성 때문에 여전히 극히 흔하다** (7장,
  p.246).[^reis2022]
  - 이 판정은 5장에서 원천 시스템 쪽으로 본 서술과 짝을 이룬다 — 원천이 CRUD 패턴이면
    스냅샷 기반 추출을 쓸 수 있지만 CDC를 통한 이벤트 추출은 연산의 완전한 이력을 준다
    (5장, p.162).[^reis2022] 그쪽은
    [CRUD와 삽입 전용 패턴](../concepts/crud-and-insert-only-patterns.md)에 있다.
    **여기서 저자들이 더하는 것은 "단순성"이라는 반대 방향의 힘**이다 — 이력이 필요 없다면
    전체 스냅샷이 여전히 합리적 기본값이라는 것.

## 이름 붙은 패턴 — Full Loader

위 절의 "전체 스냅샷"에 Konieczny가 이름과 결과 목록을 붙인다. **전체 적재(full load) 디자인
패턴은 매번 완전한 데이터셋을 대상으로 작동하는 데이터 반입 시나리오를 가리키며, 데이터베이스
부트스트랩이나 참조 데이터셋(reference dataset) 생성을 포함해 많은 상황에서 유용하다**
(2장, p.8).[^konieczny2025]

- **언제 고르는가는 원천이 정한다.** 저자의 문제 서술이 판정 조건을 준다 — 외부 데이터 제공자의
  장치 데이터셋은 주에 몇 번만 바뀌고 행 수가 백만을 넘지 않는 아주 느리게 진화하는 엔티티인데,
  **불행히도 데이터 제공자가 마지막 반입 이후 바뀐 행을 탐지하게 해 줄 어떤 속성도 정의하지
  않는다** (2장, p.8).[^konieczny2025] 그래서 **데이터셋에 마지막 갱신 값이 없다는 것이 Full
  Loader 패턴을 이 문제의 이상적 해법으로 만든다** (2장, p.8).[^konieczny2025]
  - 즉 이 패턴은 성능이 좋아서가 아니라 **증분을 식별할 수단이 원천에 없어서** 선택된다.
- 가장 단순한 구현은 추출·적재 두 단계(EL)에 의존해 네이티브 데이터 저장 명령으로 한
  데이터베이스에서 내보내 다른 데이터베이스로 들여온다. **이 EL 접근은 데이터 변환을 요구하지
  않으므로 동질적(homogeneous) 데이터 저장에 이상적이다** (2장, p.8).[^konieczny2025]
  - 저자가 여기에 이름을 하나 더 붙인다 — **추출·적재 잡은 데이터가 원천에서 목적지까지
    파이프라인을 그냥 통과하기 때문에 패스스루 잡(passthrough jobs)이라고도 불린다** (2장,
    p.8).[^konieczny2025]
  - 이질적 데이터베이스 사이라면 EL이 성립하지 않는다 — **입력 형식을 출력 형식에 맞추는 얇은
    변환 계층이 추출과 적재 단계 사이에 필요하고, 파이프라인은 그때 ETL 잡이 된다** (2장,
    p.9).[^konieczny2025] 위 [반입 관점에서 본 ETL과 ELT](#반입-관점에서-본-etl과-elt)가 말한
    E와 L의 자리가 여기서 그대로 쓰인다.
- 결과 ① **데이터 볼륨** — Full Loader 구현은 흔히 어떤 정규 일정으로 도는 배치 잡이다. 적재되는
  데이터셋의 볼륨이 천천히 자라면 거의 일정한 컴퓨트 요구 덕분에 오래도록 문제없이 작동한다.
  반대로 **더 동적으로 진화하는 데이터셋은 정적 컴퓨트 자원을 쓸 때 문제가 될 수 있다 — 예컨대
  데이터셋 크기가 하루 사이에 두 배가 되면 반입 프로세스가 느려지고 정적 하드웨어 한계 때문에
  실패할 수도 있다** (2장, p.9).[^konieczny2025] 완화책은 데이터 처리 계층의 오토스케일링이다.
- 결과 ② **데이터 일관성** — 데이터를 완전히 덮어써야 하므로 매 실행마다
  드롭-앤-인서트(drop-and-insert)로 통째 교체하고 싶어지는데, 그 전략에는 단점이 있다 (2장,
  p.9).[^konieczny2025]
  - 소비자 관점의 위험 — **데이터 반입 프로세스가 데이터셋을 읽는 파이프라인과 동시에 돌면
    소비자는 부분 데이터를 처리하거나, 삽입 단계가 완료되지 않았다면 아무 데이터도 보지 못할 수
    있다** (2장, p.9).[^konieczny2025]
  - 완화책 둘. **트랜잭션이 데이터 가시성을 자동으로 관리하며 이 동시성 이슈의 가장 쉬운
    완화책**이고, 데이터 저장이 트랜잭션을 지원하지 않으면 **뷰 같은 단일 데이터 노출
    추상(single data exposition abstraction)에 의존해 하부의 기술적이고 감춰진 구조만 조작할 수
    있다** (2장, p.9).[^konieczny2025] 실물은 두 기술 테이블 사이를 뷰가 가리키는 대상을 바꿔
    전환하는 것이다(그림 2-1).
  - 되돌리기 — **완전히 덮어쓰면 예기치 못한 문제가 생겼을 때 이전 버전의 데이터셋을 쓰지
    못할 수 있다. Delta Lake·Apache Iceberg·GCP BigQuery처럼 시간 여행(time travel) 기능을
    지원하는 형식을 쓰지 않는 한 그렇다** (2장, p.10).[^konieczny2025] 단일 노출 추상으로 직접
    구현할 수도 있다.
- 구현의 폭이 넓다는 것이 이 패턴의 특징이다 — 동일하거나 호환되는 데이터 저장 사이라면
  `aws s3 sync s3://input-bucket s3://output-bucket --delete` 한 줄로 끝나고(`--delete`가 원천에
  없는데 목적지에 있는 객체를 지운다), 세밀한 조정이 필요하면 Apache Spark 같은 분산 처리
  프레임워크를, 네이티브 버저닝이 없는 데이터베이스라면 버전이 붙은 테이블에 `COPY`로 적재하고
  `CREATE OR REPLACE VIEW`로 노출을 바꾸는 두 태스크로 나눈다 (2장, pp.10–11).[^konieczny2025]

## 이름 붙은 패턴 — Incremental Loader

- 자리부터 — **전체 적재는 쉬운 시나리오지만 연속적으로 자라는 데이터셋에는 구현 비용이 비쌀 수
  있다. 증분 적재 패턴은 물리적으로 또는 논리적으로 나뉜 데이터셋의 더 작은 부분을, 흔히 더 높은
  빈도로 반입하기 때문에 그런 데이터셋에 더 나은 후보다** (2장, p.12).[^konieczny2025]
- **구현이 둘로 갈리고, 갈림의 축은 입력 데이터 구조다** (2장, p.12):[^konieczny2025]
  - **델타 컬럼(delta column)** — 마지막 실행 이후 추가된 행을 식별하는 컬럼. 불변 방문 같은
    이벤트 주도 데이터에서는 전형적으로 이 컬럼이 반입 시각(ingestion time)이 된다.
  - **시간 분할 데이터셋(time-partitioned datasets)** — 반입 잡이 시간 기반 파티션을 써서 반입할
    새 레코드 뭉치 전체를 탐지한다. **반입할 데이터가 이미 걸러져 저장 계층에 논리적으로 조직돼
    있으므로 프로세스를 크게 단순화하고 최적화한다.**
- 둘의 실질적 차이는 **상태를 누가 갖느냐**다 — **델타 컬럼 구현은 새 행을 증분 처리하기 위해
  마지막 반입 시각 값을 기억해야 한다. 반면 파티션 기반 구현은 실행 날짜에서 처리할 파티션을
  암묵적으로 해결할 수 있으므로 그 요구가 없다 — 예컨대 로더가 11:00에 돌면 10:00 파티션을
  겨냥할 수 있다** (2장, p.13).[^konieczny2025]
- **이벤트 시각을 델타 컬럼으로 쓰는 것은 위험하다** — **데이터 생산자가 이미 처리한 이벤트
  시각에 대해 늦은 데이터(late data)를 내보내면 반입 프로세스가 레코드를 놓칠 수 있다** (2장,
  p.12).[^konieczny2025] 늦은 데이터 자체의 서술은
  [스트림 반입 고려사항](stream-ingestion-considerations.md)의 지각 도착 절에 있다.
- 결과 ① **하드 삭제(hard deletes)** — 가변 데이터에서 이 패턴은 까다롭다. **데이터 제공자가
  행을 삭제하면 그 정보는 입력 데이터셋에서 물리적으로 사라진다. 그러나 삭제된 행에는 델타
  컬럼이 존재하지 않으므로 당신 쪽 데이터셋 버전에는 여전히 남아 있다** (2장,
  p.13).[^konieczny2025]
  - 완화책은 생산자 쪽 규약이다 — **소프트 삭제(soft deletes)에 의존할 수 있다. 생산자가
    데이터를 물리적으로 제거하는 대신 삭제됨으로 표시하는 것, 다르게 말해 `DELETE` 대신
    `UPDATE` 연산을 쓰는 것이다** (2장, p.13).[^konieczny2025]
  - 다른 답 — **삽입 전용(insert-only) 데이터셋. 이름이 시사하듯 `INSERT` 연산을 통한 새 행만
    받아들인다. 삭제·수정된 항목을 올바르게 탐지해야 하는 데이터 재구성 책임을 소비자에게
    떠넘긴다. 삽입 전용 테이블은 추가 전용(append-only) 테이블이라고도 불린다** (2장,
    p.14).[^konieczny2025] 원천 시스템 쪽에서 본 같은 갈림은
    [CRUD와 삽입 전용 패턴](../concepts/crud-and-insert-only-patterns.md)에 있다.
- 결과 ② **백필** — 이 패턴이 백필에서 놀랄 만큼 나쁘게 작동한다. **델타 컬럼 구현에 의존하는
  파이프라인이 두 달치 데이터를 처리한 뒤 백필을 시작하라는 요청을 받으면, 반입 프로세스를
  띄울 때 증분이 아니라 전체 적재를 하게 된다. 따라서 잡은 여분의 행을 감당할 더 많은 자원을
  필요로 한다** (2장, p.14).[^konieczny2025]
  - 완화책은 **반입 윈도를 제한하는 것**이다 — 반입 잡이 시간마다 돈다면 SQL에서
    `delta_column BETWEEN ingestion_time AND ingestion_time + INTERVAL '1 HOUR'`로 한 시간으로
    제한한다. 이것이 두 가지를 가져온다: **데이터 볼륨에 대한 더 나은 통제**(백필의 경우에도
    컴퓨트 요구에 놀라지 않는다)와 **동시 반입**(입력 데이터 저장이 지원하는 한 여러 백필 잡을
    동시에 돌릴 수 있다) (2장, p.14).[^konieczny2025]
  - **파티션 기반 구현에는 이 데이터셋 크기 문제가 애초에 생기지 않는다** — 반입 잡이 한 번에
    한 파티션만 다룬다면 (2장, p.14).[^konieczny2025] 이것이 두 구현을 가르는 가장 실질적인
    차이다.
- 구현 예제도 갈림을 그대로 보여 준다. 파티션 기반은 Airflow DAG가 `FileSensor`로 다음 파티션이
  나타나기를 기다리는 것으로 시작하는데, **부분 데이터를 적재하고 무효한 데이터셋을 전파하는
  것을 피하기 위해 요구되는 단계**다. Airflow는 AWS Glue(`AwsGlueCatalogPartitionSensor`)·GCP
  BigQuery(`BigQueryTablePartitionExistenceSensor`)·Databricks(`DatabricksPartitionSensor`) 등
  다른 백엔드용 센서도 포함한다 (2장, p.15).[^konieczny2025] 델타 컬럼 구현은 **센서 단계를
  제거하고 반입 잡을 직접 실행한다** (2장, p.15).[^konieczny2025]
- 두 구현의 대조를 한자리에 놓으면:

  | | 델타 컬럼 | 시간 분할 |
  |---|---|---|
  | 상태 | 마지막 반입 시각을 기억해야 한다 | 실행 날짜에서 파티션을 암묵 해결 |
  | 트리거 | 잡을 직접 실행 | 센서로 파티션 준비를 기다린다 |
  | 백필 | 전체 적재로 퇴화 — 윈도 제한이 필요 | 파티션 단위라 문제 없음 |
  | 함정 | 이벤트 시각을 쓰면 늦은 데이터를 놓친다 | 파티션 준비 판정이 필요([Readiness Marker](ingestion-triggering-patterns.md)) |

## 파일 기반 내보내기와 반입

- **데이터는 파일을 써서 데이터베이스와 시스템 사이에서 옮겨지는 일이 꽤 잦다. 데이터는 교환
  가능한 형식의 파일로 직렬화되고 이 파일이 반입 시스템에 제공된다. 우리는 파일 기반 내보내기를
  푸시 기반(push-based) 반입 패턴으로 본다. 이는 데이터 내보내기와 준비 작업이 원천 시스템 쪽에서
  이뤄지기 때문이다** (7장, p.246).[^reis2022]
- 직접 연결보다 나은 이유가 보안이다 — **파일 기반 반입은 직접 데이터베이스 연결 접근보다 몇
  가지 잠재적 이점을 갖는다. 보안상의 이유로 백엔드 시스템에 직접 접근을 허용하는 것이 바람직하지
  않은 경우가 많다. 파일 기반 반입으로는 내보내기 프로세스가 데이터 원천 쪽에서 돌아 원천 시스템
  엔지니어가 어떤 데이터가 내보내지고 데이터가 어떻게 전처리되는지에 대해 완전한 통제권을 갖는다**
  (7장, p.246).[^reis2022]
- 교환 수단 — **파일이 만들어지고 나면 다양한 방식으로 대상 시스템에 제공될 수 있다. 흔한 파일
  교환 방법은 오브젝트 저장·보안 파일 전송 프로토콜(SFTP)·전자 데이터 교환(EDI)·보안 복사(SCP)다**
  (7장, p.246).[^reis2022] 각각의 실물은
  [데이터를 반입하는 방법들](../concepts/data-ingestion-methods.md)에 있다.

## 반입 관점에서 본 ETL과 ELT

7장은 ETL·ELT 전체를 다시 정의하지 않고 **반입에 해당하는 두 글자 E와 L만** 떼어 낸다.

- **3장은 배치 워크로드에서 만나게 될 극히 흔한 반입·저장·변환 패턴인 ETL과 ELT를 소개했다.
  다음은 ETL과 ELT의 추출·적재 부분에 대한 간단한 정의다** (7장, p.246):[^reis2022]
  - **추출(Extract) — 원천 시스템에서 데이터를 가져오는 것을 뜻한다. 추출이 데이터를 당기는
    것을 함의하는 듯 보이지만 푸시 기반일 수도 있다. 추출은 메타데이터와 스키마 변경을 읽는
    것도 요구할 수 있다.**
  - **적재(Load) — 데이터가 추출되고 나면 저장 목적지에 적재되기 전에 변환되거나(ETL) 미래
    변환을 위해 그냥 저장으로 적재될 수 있다(ELT). 데이터를 적재할 때 적재하는 시스템의 유형,
    데이터의 스키마, 적재의 성능 영향에 유의해야 한다.**
- **추출이 반드시 풀이 아니다**라는 이 단서가 2장의 서술과 나란히 놓인다 — 2장은 **ETL의 추출
  (E) 부분은 우리가 풀 반입 모델을 다루고 있음을 분명히 한다**고 적었다 (2장, p.42).[^reis2022]
  충돌이 아니라 범위의 차이다: 2장은 전통적 ETL의 실제 관행을, 7장은 낱말의 논리적 범위를
  말한다. 실제로 같은 7장이 파일 기반 내보내기를 푸시로 분류한다 (7장, p.246).[^reis2022]
- ETL·ELT의 전문은 이 페이지가 아니라 웨어하우스 쪽에 있다 —
  [엔터프라이즈 데이터 웨어하우스](../concepts/enterprise-data-warehouse.md)의 ETL·ELT 절,
  그리고 같은 판단을 스트리밍 파이프라인 쪽에서 본
  [데이터 파이프라인 설계 고려사항](../concepts/kafka-data-pipeline-considerations.md).

## 삽입·갱신·배치 크기

- 문제의 형태 — **배치 지향 시스템은 사용자가 적은 수의 큰 연산 대신 많은 작은 배치 연산을
  수행하려 할 때 성능이 나쁜 경우가 많다. 예컨대 트랜잭션 데이터베이스에서는 한 번에 한 행을
  삽입하는 것이 흔하지만, 이는 많은 컬럼 데이터베이스에 나쁜 패턴이다. 그것이 작고 최적이지 않은
  파일을 많이 만들게 하고 시스템이 많은 수의 객체 생성(create object) 연산을 돌게 강제하기
  때문이다. 많은 작은 제자리 갱신 연산을 돌리는 것은 더 큰 문제인데, 갱신을 돌리기 위해
  데이터베이스가 기존 컬럼 파일을 각각 스캔하게 만들기 때문이다** (7장, p.247).[^reis2022]
  - 왜 컬럼 저장에서 특히 나쁜지는
    [컬럼 지향 저장](../concepts/column-oriented-storage.md)의 압축·정렬 절이 설명한다 — 컬럼
    파일은 통째로 정렬·압축돼 있어 한 행만 고치는 연산이 성립하지 않는다.
- 저자들의 처방은 도구의 한계를 아는 것이다 — **작업 중인 데이터베이스나 데이터 저장에 적절한
  갱신 패턴을 이해하라. 또한 어떤 기술은 높은 삽입률을 위해 목적에 맞게 지어졌다는 것을 이해하라.
  예컨대 Apache Druid와 Apache Pinot은 높은 삽입률을 감당할 수 있다. SingleStore는 OLAP과 OLTP
  특성을 결합한 하이브리드 워크로드를 관리할 수 있다. BigQuery는 높은 비율의 평범한 SQL 단일 행
  삽입에서는 성능이 나쁘지만 데이터가 그 스트림 버퍼를 통해 들어오면 극히 잘 수행한다. 도구의
  한계와 특성을 알라** (7장, p.247).[^reis2022]

## 데이터 마이그레이션

- 규모 — **새 데이터베이스나 환경으로 데이터를 마이그레이션하는 것은 보통 사소하지 않으며
  데이터를 대량으로 옮겨야 한다. 때로 이는 테라바이트 또는 훨씬 더 큰 데이터 크기를 옮기는
  것을 뜻하며, 흔히 특정 테이블의 마이그레이션과 전체 데이터베이스·시스템의 이동을 수반한다**
  (7장, p.247).[^reis2022]
- 빈도는 낮지만 함정은 스키마에 있다 — **데이터 마이그레이션은 데이터 엔지니어로서 정기적으로
  일어나는 일은 아니겠지만 익숙해져야 한다. 데이터 반입에서 자주 그렇듯 스키마 관리가 결정적
  고려사항이다. 한 데이터베이스 시스템에서 다른 시스템으로(가령 SQL Server에서 Snowflake로)
  데이터를 마이그레이션한다고 하자. 두 데이터베이스가 아무리 닮았어도 스키마를 다루는 방식에
  미묘한 차이가 거의 언제나 존재한다. 다행히 완전한 테이블 마이그레이션을 감행하기 전에 데이터
  표본의 반입을 테스트해 스키마 이슈를 찾는 것은 일반적으로 쉽다** (7장, p.247).[^reis2022]
- 대량으로 옮기고, 진짜 어려움은 데이터가 아니다 — **대부분의 데이터 시스템은 데이터가 개별
  행이나 이벤트가 아니라 대량으로 옮겨질 때 최고 성능을 낸다. 파일 또는 오브젝트 저장은 데이터
  전송을 위한 훌륭한 중간 단계인 경우가 많다. 또한 데이터베이스 마이그레이션의 가장 큰 도전 중
  하나는 데이터 자체의 이동이 아니라 데이터 파이프라인 연결을 옛 시스템에서 새 시스템으로 옮기는
  것이다** (7장, p.247).[^reis2022]
- **다양한 유형의 데이터 마이그레이션을 자동화하는 많은 도구가 있음을 알아 두라. 특히 크고 복잡한
  마이그레이션의 경우 수동으로 하거나 자체 마이그레이션 솔루션을 쓰기 전에 이 선택지들을 살펴볼
  것을 제안한다** (7장, p.247).[^reis2022]
