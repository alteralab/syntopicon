이 페이지의 질문: **저장 매체의 물리가 온디스크 자료 구조에 무엇을 강요하는가.**

- 공간과 복잡도 요건을 만족한다고 해서 아무 자료 구조나 온디스크 저장에 효과적으로 쓸 수 있는
  것은 아니다. **데이터베이스에서 쓰이는 자료 구조는 영속 매체의 한계를 감안해 적응돼야 한다**
  (2장, p.29).[^petrov2019]
- 온디스크 자료 구조는 데이터가 너무 커서 전체를 메모리에 두는 것이 불가능하거나 타당하지 않을
  때 쓰인다. 어느 시점에도 데이터의 일부만 메모리에 캐시될 수 있고 나머지는 효율적으로 접근할
  수 있는 방식으로 디스크에 있어야 한다 (2장, p.29).[^petrov2019]

## 하드 디스크 드라이브

- 전통적 알고리즘 대부분은 회전 디스크가 가장 널리 쓰이는 영속 저장 매체이던 때 개발됐고, 그
  사실이 설계에 크게 영향을 줬다 (2장, p.30).[^petrov2019]
- 회전 디스크에서 **탐색(seek)** 은 임의 읽기 비용을 올린다 — 디스크 회전과 기계적 헤드 이동으로
  읽기·쓰기 헤드를 원하는 위치에 놓아야 하기 때문이다. **그러나 그 비싼 부분이 끝나면 연속된
  바이트를 읽거나 쓰는 일(순차 연산)은 비교적 싸다** (2장, p.30).[^petrov2019]
- 회전 드라이브의 최소 전송 단위는 섹터(sector)이므로 어떤 연산이든 최소한 섹터 하나를 읽거나
  쓴다. 섹터 크기는 보통 512바이트에서 4KB 사이다 (2장, p.30).[^petrov2019]
- **헤드 위치 잡기가 HDD 연산에서 가장 비싼 부분이다.** 순차 I/O(디스크에서 연속된 메모리
  세그먼트를 읽고 쓰기)의 긍정적 효과를 자주 듣는 이유가 이것이다 (2장, p.30).[^petrov2019]

## 솔리드 스테이트 드라이브

- SSD에는 움직이는 부품이 없다. 전형적인 SSD는 메모리 셀로 지어지고, 셀들이 문자열(보통 문자열당
  32–64셀)로 연결되고, 문자열이 배열로, 배열이 페이지로, 페이지가 블록으로 묶인다. 정확한 기술에
  따라 셀 하나가 1비트 또는 여러 비트를 담는다. **페이지 크기는 장치마다 다르지만 보통 2–16KB,
  블록은 보통 페이지 64–512개를 담는다.** 블록은 플레인으로, 플레인은 다이에 놓이며 SSD는 다이를
  하나 이상 가질 수 있다 (2장, p.30).[^petrov2019]
- 여기가 결정적이다. 쓰기(프로그래밍)와 읽기의 최소 단위는 페이지지만, **변경은 비어 있는(곧
  미리 지워진) 메모리 셀에만 할 수 있다. 그리고 지우기의 최소 단위는 페이지가 아니라 여러
  페이지를 담은 블록이라 흔히 지우기 블록(erase block)이라 부른다. 빈 블록의 페이지는 순차적으로
  쓰여야 한다** (2장, p.31).[^petrov2019]
- 페이지 ID를 물리 위치로 매핑하고 빈·쓰인·버려진 페이지 상태를 추적하는 플래시 메모리 컨트롤러의
  부분이 **플래시 변환 계층(Flash Translation Layer, FTL)** 이다. FTL은 가비지 컬렉션도 맡는데,
  안전하게 지울 수 있는 블록을 찾는 일이다. **어떤 블록에는 아직 살아 있는 페이지가 남아 있을 수
  있고, 이때 FTL은 살아 있는 페이지를 새 위치로 옮기고 페이지 ID를 거기로 다시 매핑한 뒤 이제
  쓰이지 않는 블록을 지워 쓰기에 열어 준다** (2장, p.31).[^petrov2019]
- SSD에서는 임의 대 순차 I/O의 강조가 HDD만큼 세지 않다 — 임의 읽기와 순차 읽기의 지연 차이가
  그만큼 크지 않기 때문이다. 다만 프리페칭, 연속 페이지 읽기, 내부 병렬성 때문에 여전히 어느
  정도 차이는 있다 (2장, pp.31–32).[^petrov2019]
- 가비지 컬렉션은 보통 백그라운드 작업이지만, **특히 임의·비정렬 쓰기 워크로드에서 쓰기 성능에
  나쁜 영향을 줄 수 있다.** 온전한 블록만 쓰고 같은 블록에 대한 후속 쓰기를 합치면 필요한 I/O
  연산 수를 줄이는 데 도움이 된다 (2장, p.32).[^petrov2019]

## 블록이 최소 단위라는 사실

- 두 장치 유형 모두 개별 바이트가 아니라 메모리 청크를 주소 지정하므로(곧 블록 단위 접근),
  대부분의 운영체제에는 **블록 장치(block device) 추상화**가 있다. 이 추상화는 내부 디스크 구조를
  감추고 I/O 연산을 내부적으로 버퍼링하므로, **블록 장치에서 한 워드를 읽으면 그것을 담은 블록
  전체가 읽힌다. 이것은 무시할 수 없는 제약이며 디스크 상주 자료 구조를 다룰 때 항상 감안해야
  한다** (2장, p.31).[^petrov2019]
- 그래서 효율적인 온디스크 구조를 짓는 주된 한계이자 설계 조건은 **디스크 연산의 최소 단위가
  블록이라는 사실**이다. 블록 안의 특정 위치를 가리키는 포인터를 따라가려면 블록 전체를 가져와야
  한다. 어차피 그래야 한다면, **그 사실을 이용하도록 자료 구조의 레이아웃을 바꿀 수 있다** (2장,
  p.32).[^petrov2019]
- 디스크에서는 포인터의 의미가 조금 다르다 — 메모리 매핑 파일을 쓰는 경우가 아니면 대개 데이터
  레이아웃을 손으로 관리하므로, 대상 포인터 주소를 계산하고 포인터를 명시적으로 따라가야 한다.
  온디스크 오프셋은 대체로 미리 계산되거나 디스크로 플러시될 때까지 메모리에 캐시된다. **온디스크
  구조에서 긴 의존 사슬을 만들면 코드와 구조의 복잡도가 크게 오르므로 포인터의 개수와 그것이
  걸치는 범위를 최소로 유지하는 편이 좋다** (2장, p.32).[^petrov2019]

## 설계 원칙

- 요약하면 온디스크 구조는 대상 저장 장치의 특성을 감안해 설계되며 대체로 **디스크 접근 횟수를
  줄이는 쪽으로 최적화한다.** 지역성을 높이고, 구조의 내부 표현을 최적화하고, 페이지 밖으로
  나가는 포인터의 수를 줄여서 그렇게 한다 (2장, p.32).[^petrov2019]
- 디스크 구현에 더 적합한 트리가 갖춰야 할 성질 둘 (2장, p.29):[^petrov2019]
  - **인접 키의 지역성을 높이기 위한 높은 팬아웃(fanout).**
  - **순회 중 탐색 횟수를 줄이기 위한 낮은 높이.**
- 둘은 반비례한다 — 팬아웃이 높을수록 높이가 낮다. 팬아웃이 높으면 노드마다 자식을 더 많이 담을
  수 있어 노드 수가 줄고 따라서 높이가 준다 (2장, p.29).[^petrov2019]

## 로그 스태킹 — 층이 겹칠 때

- 많은 현대 파일시스템이 로그 구조다 — 쓰기를 메모리 세그먼트에 버퍼링하고 가득 차면 추가 전용
  방식으로 디스크에 플러시한다. **SSD도 작은 임의 쓰기를 다루고, 쓰기 오버헤드를 최소화하고,
  마모 평준화를 개선하고, 장치 수명을 늘리려고 로그 구조 저장을 쓴다** (7장, p.157).[^petrov2019]
- 로그 구조 저장(log-structured storage, LSS) 시스템은 SSD가 값싸지던 무렵부터 인기를 얻기
  시작했다. **LSM 트리와 SSD는 궁합이 좋다** — 순차 워크로드와 추가 전용 쓰기가 SSD 성능에 나쁜
  영향을 주는 인플레이스 갱신의 증폭을 줄여 주기 때문이다 (7장, p.157).[^petrov2019]
- 그런데 **로그 구조 시스템을 여러 층으로 쌓으면 LSS로 풀려던 문제(쓰기 증폭, 단편화, 낮은
  성능)를 도리어 만날 수 있다.** 최소한 애플리케이션을 개발할 때 SSD의 플래시 변환 계층과
  파일시스템을 염두에 둬야 한다 (7장, p.157).[^petrov2019]
- 마모 평준화(wear leveling)는 부하를 매체 전체에 고르게 분산해, 프로그램·지우기 사이클 수가 많아
  블록이 조기에 못 쓰게 되는 핫스팟을 피한다. 플래시 메모리 셀이 견디는 프로그램·지우기 사이클
  수가 한정돼 있어 필요한 일이다 (7장, p.158).[^petrov2019]
- 스태킹이 손해를 내는 방식 (7장, pp.159–160):[^petrov2019]
  - **층마다 자기 장부를 따로 적어야 하고**, 하부 로그가 그 노력을 중복하지 않게 할 정보를 노출하지
    않는 경우가 대부분이다.
  - 층들이 LSS 관련 스케줄링(세그먼트 폐기나 재배치 같은 것)을 서로 알리지 않으므로, **하부
    서브시스템이 이미 버려졌거나 곧 버려질 데이터에 중복 연산을 수행할 수 있다.**
  - 표준 세그먼트 크기가 없어서 **정렬되지 않은 상위 세그먼트가 하위 세그먼트 여럿을 차지할 수
    있다.** 상위 로그 세그먼트를 버리면 이웃 세그먼트의 일부가 단편화되고 재배치될 수 있다.
- "로그 구조 저장은 순차 I/O가 전부"라고 말하지만, 데이터베이스 시스템은 **여러 쓰기 스트림**을
  가질 수 있다(예: 로그 쓰기와 레코드 쓰기가 나란히). 하드웨어 수준에서 보면 인터리브된 순차 쓰기
  스트림이 같은 순차 패턴으로 번역되지 않는다 — **블록이 반드시 쓰기 순서로 놓이지는 않는다**
  (7장, pp.159–160).[^petrov2019]
- 그래서 일부 벤더는 워크로드를 격리하려고 로그를 별도 장치에 두기를 권한다. 다만 **더 중요한 것은
  파티션을 하부 하드웨어에 정렬하고 쓰기를 페이지 크기에 정렬하는 것**이다 (7장,
  p.160).[^petrov2019]

## 층을 건너뛰기

- 소프트웨어 층을 쌓는 대신 모든 간접 계층을 건너뛰고 하드웨어를 직접 쓰는 길도 있다. 예로
  **오픈 채널 SSD(Open-Channel SSD)** 를 대상으로 개발하면 파일시스템과 플래시 변환 계층을
  피할 수 있어 최소 두 층의 로그를 없애고 마모 평준화·가비지 컬렉션·데이터 배치·스케줄링을 더
  통제할 수 있다 (7장, p.161).[^petrov2019]
  - 사례로 LOCS(오픈 채널 SSD 위의 LSM 트리 기반 KV 스토어)와 리눅스 커널의 LightNVM이 있다.
  - 커널 페이지 캐시를 우회하는 `O_DIRECT` 플래그와 견줄 수 있다 — 통제는 더 좋아지지만 페이지
    관리를 손으로 해야 한다 (7장, p.162).
- Software Defined Flash(SDF)는 하드웨어·소프트웨어를 함께 설계한 오픈 채널 SSD 시스템으로,
  **읽기 단위와 쓰기 단위의 크기가 다르고 쓰기 단위 크기가 지우기 단위(블록)에 대응하는 비대칭
  I/O 인터페이스**를 노출해 쓰기 증폭을 크게 줄인다. 가비지 컬렉션과 페이지 재배치를 수행하는
  소프트웨어 층이 하나뿐이라 로그 구조 저장에 이상적인 설정이다 (7장, p.162).[^petrov2019]
- 다만 층을 잘 쌓는 것 자체가 이득을 낼 수 있다는 반례도 이 장에 있다 — Bw-트리를 얹은 LLAMA는
  **하부 로그 구조 저장이 상위 자료 구조의 의미를 알기 때문에**, 여러 델타 노드를 하나의 연속된
  물리 위치로 통합하고 서로 상쇄되는 갱신(삽입 뒤 삭제)을 논리적으로 합쳐 마지막 삭제만 영속화할
  수 있다 (7장, pp.160–161).[^petrov2019]
- 저자의 결론 (7장, p.162):[^petrov2019]

> Hiding complexity behind a simple API might sound compelling, but can cause
> complications in cases in which software layers have different semantics. Exposing
> some underlying system internals may be beneficial for better integration.
