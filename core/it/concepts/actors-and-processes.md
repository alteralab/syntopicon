하나의 질문: **상태를 전혀 공유하지 않고 메시지만 주고받게 하면 동시성 문제가 어디로 가는가.**

## 두 낱말의 정의

- 이 Topic의 목적 — **액터와 프로세스는 공유 메모리에 대한 접근을 동기화하는 부담 없이 동시성을
  구현하는 흥미로운 방법을 제공한다** (Topic 35).[^thomas2020]
- **액터**(actor)의 정의 — **액터는 자기 자신의 지역(이자 사적인) 상태를 가진 독립적인 가상
  프로세서다. 각 액터는 사서함(mailbox)을 가진다. 메시지가 사서함에 나타나고 액터가 놀고 있으면,
  그것은 활동을 시작해 그 메시지를 처리한다. 처리를 마치면 사서함의 다른 메시지를 처리하거나,
  사서함이 비어 있으면 다시 잠든다** (Topic 35).[^thomas2020]
  - 처리 중에 할 수 있는 것 셋 — **메시지를 처리할 때 액터는 다른 액터를 만들 수 있고, 자기가 아는
    다른 액터에게 메시지를 보낼 수 있고, 다음 메시지가 처리될 때 현재 상태가 될 새 상태를 만들 수
    있다** (Topic 35).[^thomas2020]
  - 셋째가 중요하다. 상태를 **제자리에서 고치는** 것이 아니라 **다음 상태를 만들어 돌려준다** —
    그래서 처리 중인 메시지 하나가 상태의 유일한 소유자가 된다.
- **프로세스**(process)의 정의 — **프로세스는 전형적으로 더 범용의 가상 프로세서로, 흔히 동시성을
  촉진하기 위해 운영 체제가 구현한다. 프로세스는 (규약에 의해) 액터처럼 행동하도록 제약될 수
  있고, 여기서 우리가 뜻하는 프로세스는 그런 종류의 프로세스다** (Topic 35).[^thomas2020]

## 정의에서 발견되지 않는 것 넷

저자들이 **없는 것**을 세는 방식으로 모델을 규정한다 (Topic 35).[^thomas2020]

- **통제하고 있는 단일한 **것**이 없다. 아무것도 다음에 무엇이 일어날지 스케줄링하지 않고, 원시
  데이터에서 최종 출력까지의 정보 전달을 조율하지 않는다.**
- **시스템 안의 **유일한** 상태는 메시지 안과 각 액터의 지역 상태에 담긴다. 메시지는 수신자가 읽는
  것 말고는 검사될 수 없고, 지역 상태는 액터 바깥에서 접근할 수 없다.**
- **모든 메시지는 단방향이다 — 응답이라는 개념이 없다. 액터가 응답을 돌려주기를 원한다면 당신이
  보내는 메시지에 당신 자신의 사서함 주소를 포함시키고, 그러면 그것이 (결국) 그 사서함으로 그저
  또 하나의 메시지로서 응답을 보낼 것이다.**
- **액터는 각 메시지를 완결까지 처리하고, 한 번에 메시지 하나만 처리한다.**

넷째가 [공유 상태는 틀린 상태](shared-state-is-incorrect-state.md)의 문제를 정의상 없앤다 —
확인과 갱신이 한 메시지 안에 있으므로 그 사이에 다른 누구도 끼어들 수 없다.

## 그래서 액터는 동시적일 수밖에 없다

- 귀결 — **그 결과 액터는 동시적으로, 비동기적으로 실행되며 아무것도 공유하지 않는다. 물리적
  프로세서가 충분하다면 각각에 액터 하나를 돌릴 수 있다. 프로세서가 하나뿐이면 어떤 런타임이
  그것들 사이의 문맥 전환을 처리할 수 있다. 어느 쪽이든 액터 안에서 도는 코드는 같다** (Topic
  35).[^thomas2020]

## 식당을 액터로 다시 짓기

- 저자들이 앞 Topic의 식당을 액터 셋(손님·종업원·파이 진열장)으로 다시 짓는다. 메시지 흐름은
  이렇다 (Topic 35):[^thomas2020] 외부에서 손님에게 배고프다고 알리면 → 손님이 종업원에게 파이를
  청하고 → 종업원이 진열장에게 손님에게 파이를 가져다주라고 하고 → 진열장에 조각이 있으면 그것을
  손님에게 보내고 종업원에게도 계산서에 올리라고 알리고 → 파이가 없으면 진열장이 종업원에게 알리고
  종업원이 손님에게 사과한다.
- 상태를 쥐고 있는 액터가 대표 코드다 (Topic 35):[^thomas2020]

  ```javascript
  const pieCaseActor = {
    'get slice': (msg, context, state) => {
      if (state.slices.length == 0) {
        dispatch(msg.waiter,
                 { type: 'error', msg: "no pie left", customer: msg.customer })
        return state
      }
      else {
        var slice = state.slices.shift() + " pie slice";
        dispatch(msg.customer,
                 { type: 'put on table', food: slice });
        dispatch(msg.waiter,
                 { type: 'add to order', food: slice, customer: msg.customer });
        return state;
      }
    }
  }
  ```

  - 읽는 법 — **파이 진열장은 상태를 가진다: 자기가 쥔 파이 조각 전부의 배열이다. 종업원에게서
    `'get slice'` 메시지를 받으면 남은 조각이 있는지 본다. 있으면 조각을 손님에게 넘기고, 종업원에게
    주문을 갱신하라고 알리고, 마지막으로 조각이 하나 줄어든 갱신된 상태를 돌려준다** (Topic
    35).[^thomas2020]
- 구현의 사정 — **우리는 Nact 라이브러리를 써서 자바스크립트로 코드를 구현하기로 했다. 여기에 작은
  래퍼를 더해 액터를 단순한 객체로 쓸 수 있게 했는데, 키는 그것이 받는 메시지 타입이고 값은 그
  특정 메시지가 수신될 때 돌릴 함수다. (대부분의 액터 시스템이 비슷한 종류의 구조를 갖지만 세부는
  호스트 언어에 달렸다.)** (Topic 35)[^thomas2020]
- 실행 결과에서 볼 것 — 손님 1이 세 조각, 손님 2가 두 조각을 청하는데 진열장에는 사과·복숭아·체리
  세 조각뿐이다. 그래서 앞의 셋은 배달되고 나머지 둘에는 사과가 돌아간다. 저자들이 덧붙이는 한
  마디가 이 모델의 성질을 말한다 — **당신이 보는 순서는 다를 수 있다** (Topic 35).[^thomas2020]

## 명시적 동시성이 없다

- **핵심 귀결** — **액터 모델에서는 공유 상태가 없으므로 동시성을 다루는 코드를 쓸 필요가 전혀
  없다. 또한 명시적인 처음부터 끝까지의 "이것을 하고, 저것을 하라" 로직을 코딩할 필요도 없는데,
  액터들이 자기가 받는 메시지에 근거해 스스로 알아내기 때문이다** (Topic 35).[^thomas2020]
- **그리고 배치가 사라진다** — **기저 아키텍처에 대한 언급도 없다. 이 구성 요소 집합은 단일
  프로세서에서든, 여러 코어에서든, 네트워크로 연결된 여러 기계에서든 똑같이 잘 동작한다** (Topic
  35).[^thomas2020]
  - 이것이 [분산 액터 프레임워크](../concepts/distributed-actor-frameworks.md)가 "위치 투명성이
    여기서는 통한다"고 판정하는 자리의 근거다. 다만 이 책은 그 판정을 하지 않고 성질만 진술한다.

## 얼랭이 무대를 마련했다

- 지위 — **얼랭 언어와 런타임은 액터 구현의 훌륭한 예다(얼랭의 발명자들이 원래의 액터 논문을 읽지
  않았는데도 그렇다). 얼랭은 액터를 **프로세스**라 부르지만 그것은 일반적인 운영 체제 프로세스가
  아니다. 대신 우리가 논의해 온 액터와 꼭 같이 얼랭 프로세스는 가볍고(한 기계에서 수백만 개를
  돌릴 수 있다), 메시지를 보내 통신한다. 각각은 다른 것들에서 격리돼 있어 상태의 공유가 없다**
  (Topic 35).[^thomas2020]
- **더해지는 것 둘** — **더해서 얼랭 런타임은 수퍼비전(supervision) 시스템을 구현하는데, 그것은
  프로세스의 수명을 관리하며 실패 시 프로세스나 프로세스 집합을 재시작할 수 있다. 그리고 얼랭은
  핫코드 로딩도 제공한다: 도는 시스템을 멈추지 않고 그 안의 코드를 교체할 수 있다** (Topic
  35).[^thomas2020]
  - 수퍼비전 트리는 [죽은 프로그램은 거짓말하지 않는다](dead-programs-tell-no-lies.md)가 "일찍
    죽어라"의 실물로 든 바로 그 장치다 — 액터가 죽어도 안전한 것은 공유 상태가 없어 죽은 액터가
    남길 반쯤 갱신된 상태가 없기 때문이다. #hypothesis 저자들이 이 두 Topic을 연결하지는 않는다.
- 실적 주장 — **얼랭 시스템은 세계에서 가장 신뢰성 있는 코드 일부를 돌리며, 흔히 나인 나인
  (nine nines) 가용성이 인용된다** (Topic 35).[^thomas2020]
  - 이 수치의 지위: 저자들이 인용된 주장으로 옮긴 것이지 측정 조건을 밝히지 않는다. #hypothesis
- 그리고 범위의 확장 — **그러나 얼랭(과 그 후손 엘릭서)이 유일한 것은 아니다 — 대부분의 언어에
  액터 구현이 있다. 당신의 동시적 구현에 그것들을 쓰는 것을 고려하라** (Topic 35).[^thomas2020]

## 이 KB의 액터 서술과 나란히

- [분산 액터 프레임워크](../concepts/distributed-actor-frameworks.md)는 같은 모델을 **네트워크로
  늘렸을 때**를 묻는다. 두 서술이 정확히 맞물린다 — 이 Topic이 "기저 아키텍처에 대한 언급이 없다"고
  말한 자리에서 그쪽은 "그래서 위치 투명성이 RPC에서보다 잘 작동한다"고 이유를 대고, 이 Topic이
  다루지 않는 대가(롤링 업그레이드의 전진·후진 호환성)를 덧붙인다.
- **다만 한 지점에서 강조가 다르다.** 이 책은 "메시지가 유실될 수 있다"를 정의에 넣지 않고 단방향
  성만 말한다. 클레프만 쪽은 **전달이 보장되지 않는다는 것이 모델의 전제**라고 적는다. 어긋나는
  것이 아니라, 한 프로세스 안을 보는 서술과 네트워크를 보는 서술의 차이다.
- [스레드 안전성 구현 수단](../concepts/thread-safety-implementation.md)의 셋째 갈래(공유 자체를
  없애는 재진입 코드·스레드 로컬)가 같은 전략의 JVM 판이다. 액터는 그것을 언어·런타임 수준의
  기본값으로 만든 것이다.
