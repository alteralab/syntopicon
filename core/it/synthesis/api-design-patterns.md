# API 설계 패턴

## 이 허브가 답하는 물음

**스타일을 고른 다음, 어느 스타일에서나 되풀이되는 설계 물음에 무엇으로 답하는가**가 여기
산다. 이름을 어떻게 붙이고, 판이 바뀔 때 어떻게 매기고, 적재물의 필드를 어떻게 적고, 큰 목록을
어떻게 내주고, 정상 왕복에서 벗어난 요청을 어떻게 다루고, 지운다는 것을 어떻게 표현하는가다.

**가르는 기준은 무엇에 매이는가다.** 여기 모인 것은 **스타일에 매이지 않는** 물음들이고,
스타일 하나하나의 규정과 유래와 절충은 [네트워크 API 스타일](network-api-styles.md)이 갖는다.
이 패턴들이 규칙이 아니라 지침이라는 판정도 이 허브의 첫 페이지에 있다.

## 어느 스타일에서나 되풀이되는 설계 물음

- [API 설계 모범 사례](../concepts/api-design-best-practices.md) — 이 묶음의 입구.
  설계 패턴이라는 낱말의 규정과 스타일과 무관하게 공통인 도전이 있다는 전제, 블로흐의 격언 둘,
  대상 맞춤·직관·유지보수·문서화·오용하기 어려움·테스트 가능·안전·효율·오류 전달이라는 아홉,
  성능 손잡이 다섯과 각각이 되사는 대가, 그리고 이 패턴들이 규칙이 아니라 지침이라는 판정
- [API 이름과 버저닝](../concepts/api-naming-and-versioning.md) — 인터페이스에 이름을 붙이는
  일과 계약이 바뀔 때 판을 매기는 일. 자원 지향과 의도 지향의 구별, 같은 CRUD 다섯을 네
  스타일이 이름 짓는 대응표, 깨는 변경과 안 깨는 변경의 목록, 판을 놓는 네 자리와 세 형식
- [서비스 설계 지침과 API 윤곽](../concepts/service-design-guidelines-and-api-contours.md) —
  **같은 두 물음에 2019년 실무서가 내놓는 한 판.** 위 페이지가 판을 놓을 자리와 형식의 지도를
  준다면 이쪽은 그 조합 하나를 규범으로 고르고(메이저는 경로, 마이너는 날짜 질의 파라미터) 그
  근거로 **소프트웨어에 "판" 같은 것은 없고 메이저는 그저 별개 배포 산출물**이라는 주장을 댄다.
  깨는 변경의 목록에 **선택적 출력 필드의 삭제**와 **구조적으로 유의미한 문자열**이라는 단서를
  더한다
- [API 적재물 필드 설계 규약](../concepts/api-payload-field-conventions.md) — 형식을 고른 다음
  필드에 걸리는 규약. 언어 사이 직렬화 어긋남, null과 누락 필드, 불리언 표기와 이름, 값의
  경계, 열거형이 없는 형식에서의 우회
- [API 목록 조회 패턴](../concepts/api-list-query-patterns.md) — 큰 데이터셋을 목록으로 내주는
  일. 필터 문자열과 필드 기반 필터링, 세기와 정렬이 분산에서 무너지는 자리, 오프셋 기반과
  커서 기반 페이지네이션
- [API 요청 수명 패턴](../concepts/api-request-lifecycle-patterns.md) — 요청 하나가 정상
  왕복에서 벗어날 때. 긴 작업과 202와 작업 자원, 요청 ID로 막는 중복 제거, 클라이언트별 속도
  제한과 그것만으로 막히지 않는 것
- [API 자원 삭제 패턴](../concepts/api-resource-deletion-patterns.md) — 지운다는 것을 API에서
  표현하는 두 방식. 소프트 삭제와 하드 삭제의 상태 코드, 뒤늦게 들이면 깨진다는 경고,
  되살리기와 만료

## 그 설계를 나누고 검증하는 자리

- [OpenAPI 명세를 쓰는 실무](../concepts/openapi-specification-practice.md) — 고른 형식을
  소비자와 나누는 문서 하나를 축으로 돌리는 일. 명세가 담는 것과 클라이언트 코드·구현 스텁의
  생성, 명세가 모양만 전하고 조건별 의미론은 담지 않는다는 한계, 인바운드 관문에서 명세로
  메시지를 검사해 끊는 쓰임, 예제를 모의 응답으로 돌려 짓기 전에 시험하는 쓰임, 명세 둘을
  맞대어 깨는 변경을 파이프라인에서 잡는 쓰임, 그리고 REST 명세와 RPC 스키마를 서로 변환하려
  할 때의 함정
- [API 테스트의 유형과 경계](../concepts/api-test-types-and-boundaries.md) — 설계한 API를
  무엇으로 검증하는가. 계약·컴포넌트·통합·종단 네 유형의 규정과 각각이 들여다보는 경계, 계약
  테스트와 컴포넌트 테스트를 가르는 선, 스텁 서버를 얻는 세 길과 손수 만든 스텁이 틀리는 방식,
  실물을 띄워도 경계 안이면 종단이 아니라는 판정, 그리고 이 네 결정을 묻는 ADR 지침 넷.
  **정본 자리는 [테스트 스위트의 운영](test-suite-operations.md)이다**
