이 페이지의 질문: **스레드 풀 하나에 작업을 던지는 것과 스레드마다 큐를 주는 것은 무엇이
달라지는가.**

## 무엇을 겨냥한 설계인가

- 실행자 프레임워크는 쓸모가 크지만 심한 캐시 경합이나 복잡한 작업 의존 관계가 필요한 상황에서
  문제가 될 수 있다. 자바의 포크/조인 풀(Fork/Join Pool)이 성능 중심 설계와 전용 알고리즘으로 그
  문제를 다룬다 (1장, p.21).[^rahman2025] 그 캐시 경합이 무엇인지는
  [거짓 공유와 캐시 일관성](../concepts/false-sharing-and-cache-coherence.md)에 있다.
- 위치가 분명하다 — 포크/조인 풀은 `ExecutorService`의 전용 구현이며, 더 정교한 스레드 풀링 기제로
  지능적인 작업 스케줄링을 통해 성능과 자원 효율을 올린다 (1장, p.21).[^rahman2025]

## 캐시 친화성

- 캐시 친화성(cache affinity)은 CPU 캐시의 지역성(locality)을 살리는 방식으로 작업을 끝낸다는
  개념이다. 어떤 작업이 특정 CPU에서 실행되면 그 데이터가 해당 코어의 캐시에 올라가고, 관련된 다른
  작업이 같은 코어에서 실행되면 이미 캐시에 있는 데이터의 덕을 보아 메모리 접근 시간이 줄고 성능이
  오른다 (1장, p.21).[^rahman2025]
- 포크/조인 풀이 캐시 친화성을 북돋우는 이유는 워커 스레드가 보통 자기 로컬 큐의 작업을 실행하기
  때문이다. 작업들이 같은 공유 데이터에 자주 닿을 때 특히 도움이 된다 (1장, p.21).[^rahman2025]
- 그렇게 해서 줄이는 것이 캐시 미스(cache miss)다 — 작업에 필요한 데이터가 캐시에 없어 주기억
  장치에서 가져와야 하는 상황이고, 훨씬 느린 과정이다 (1장, p.21).[^rahman2025]
- 저자의 예는 큰 배열이다 — 병렬 작업들이 한 배열의 서로 다른 조각을 처리한다면 같은 코어에서 돌게
  하는 편이 이득이다. 그 조각의 데이터가 캐시에 남아 다음 작업이 빨리 닿을 수 있고, 그러지 않으면
  같은 데이터를 캐시로 계속 다시 올려야 한다 (1장, p.21).[^rahman2025]

## 작업 훔치기 알고리즘

- 포크/조인 풀은 스레드 사이의 부하를 고르게 하려고 동적인 작업 훔치기(work-stealing) 알고리즘을
  쓴다. 공유 작업 큐 하나를 두는 대신 풀의 스레드마다 자기 큐를 갖는다 (1장, p.21).[^rahman2025]
- 기제가 한 줄이다 — 어떤 스레드가 할 일이 떨어지면 다른 스레드 큐의 꼬리에서 작업을 훔쳐 온다.
  이 동적 알고리즘이 CPU 사용을 최대로 끌어올려, 할 일이 남아 있는 한 노는 스레드가 없게 만든다
  (1장, p.21).[^rahman2025]
- 그래서 얻는 것이 재분배다 — 작업을 동적으로 다시 나누어 모든 스레드가 생산적으로 남게 하고, 전체
  CPU 활용을 올리며 노는 시간을 줄인다 (1장, p.21).[^rahman2025]

## 전통 스레드 풀과 무엇이 다른가

3장이 같은 풀을 `ThreadPoolExecutor`와 나란히 놓고 네 자리에서 가른다.

- 나이와 지위가 먼저 적힌다 — 자바 7 이래로 범용 `ThreadPoolExecutor` 말고 `ForkJoinPool`이라는
  특별한 스레드 풀이 있었다. 다른 풀처럼 보이지만 특별한 목적이 있고, `ExecutorService` 인터페이스를
  구현하면서도 핵심 설계와 운영 원리에서 전통적인 `ThreadPoolExecutor`와 크게 다르다 (3장,
  p.103).[^rahman2025]
  - 버전 조건: 자바 7 이상 — 이 풀이 JDK에 들어온 릴리스다.
- 첫째 차이가 큐의 소유자다 — 스레드마다 자기 작업 큐를 갖는 작업 훔치기 기제를 쓰고, 노는 스레드는
  다른 스레드 덱(deque)의 꼬리에서 작업을 훔쳐 올 수 있다. 반면 전통적인 풀은 공유 큐 하나를 두고
  노는 스레드에 작업을 배정하는데, 스레드가 작업을 놓고 다투게 되므로 경합과 부담으로 이어질 수
  있다 (3장, p.103).[^rahman2025]
- 둘째 차이가 스레드 수의 탄력이다 — 전통적인 스레드 풀은 보통 고정되거나 유계인 스레드 수를
  유지하고 생성과 종료가 덜 동적이다. 반면 `ForkJoinPool`은 작업 부하와 프로세서 가용성에 따라
  활성 스레드 수를 적응적으로 조절할 수 있고, 효율을 유지하려고 스레드를 동적으로 더하거나
  멈추거나 재개할 수도 있다 (3장, p.103).[^rahman2025]
- 셋째 차이가 동기화의 양이다 — 전통적인 스레드 풀은 작업 접근과 스레드 동기화를 관리하려고 락이나
  조건 변수 같은 명시적 동기화 기제에 기대는 일이 많다. 반면 `ForkJoinPool`은 작업 훔치기 알고리즘
  덕분에 명시적 동기화의 필요를 최소로 줄인다. 그래서 스레드가 더 자율적으로 움직여 경합과 부담이
  줄고, 뛰어난 성능이 나온다 (3장, p.104).[^rahman2025]
- 넷째 차이가 작업 사이의 의존이다 —
  [의존하는 하위 작업과 스레드 풀의 교착](../concepts/recursive-task-decomposition-deadlock.md)이
  그 실증을 갖는다.

## 덱의 두 끝

- 큐의 정체가 양방향이다 — 각 워커 스레드는 `WorkQueue`라는 이름의 자기 덱(deque, double-ended
  queue)을 유지한다 (3장, p.108).[^rahman2025]
- 두 끝의 규칙이 갈린다 — 작업은 보통 워커 스레드 자신이 한쪽 끝에서 후입선출(LIFO)로 넣고 꺼내며,
  다른 스레드는 반대쪽 끝에서 선입선출(FIFO)로 훔쳐 간다 (3장, p.108).[^rahman2025]
- 쪼갠 것은 자기 큐로 간다 — 워커 스레드가 분할 정복 알고리즘의 일부로 작업을 쪼개면, 새로 만든
  하위 작업을 자기 작업 큐에 바로 넣는다 (3장, p.108).[^rahman2025]
- 바깥에서 들어오는 것은 다른 문으로 들어온다 — 워커 스레드가 아닌 외부 스레드가 제출하는 작업은
  제출 큐(submission queue)를 통해 시스템에 들어온다. 이 큐는 `WorkQueue`와 비슷하지만
  `ForkJoinPool` 자신이 관리한다 (3장, p.109).[^rahman2025]
- 저자의 비유가 부지런한 벌이다 — 워커 스레드는 스스로 바쁘게 있으려고 끊임없이 일을 찾아 훑는다.
  워커의 수가 제한되어 있으니 늘 값어치 있는 일을 하고 있게 하고 싶은 것이다. 자기 큐의 작업이
  떨어지면 그 워커는 훔치는 자가 되어 다른 워커의 큐에서 작업을 훔치려 든다 (3장,
  p.109).[^rahman2025]
- 두 끝을 쓰는 이유가 경합이다 — 훔치기가 경합을 만들 것 같지만, 경합을 최소로 줄이려고 두 스레드가
  큐의 서로 다른 끝에서 작업을 집는다 (3장, pp.109–110).[^rahman2025]
- 후입선출이 불공평해 보이는 문제에 저자가 답한다 — CPU에는 최근에 접근한 데이터를 담아 두는 캐시가
  있으므로, 가장 새 작업을 먼저 처리하면 그 작업에 필요한 데이터가 이미 캐시에 있을 확률이 높아진다.
  그래서 캐시 미스가 줄고 성능이 오른다 (3장, p.110).[^rahman2025]
- 그러면 오래된 작업은 훔치는 쪽이 맡는다 — 훔치는 스레드가 큐의 꼬리에서 그것들을 가져간다 (3장,
  p.110).[^rahman2025]

## 왜 락이 아니라 CAS인가

- 큐 관리에 쓰는 것이 락이 아니다 — 락 같은 동기화 기제를 명시적으로 쓰지 않고, 비교 후 교환
  (compare-and-swap, CAS) 같은 원자적 연산으로 동시 접근을 효율적으로 관리한다 (3장,
  p.109).[^rahman2025] CAS 자체가 하드웨어 수준에서 무엇인지는
  [스레드 안전성 구현 수단](../concepts/thread-safety-implementation.md)이 갖는다.
- CAS의 규칙을 저자가 한 문장으로 적는다 — 락을 얻는 대신, CAS를 쓰는 스레드는 변수의 현재 값을
  기대하는 값과 비교해 둘이 같을 때만 새 값으로 바꾼다 (3장, p.110).[^rahman2025]
- 실패했을 때의 규칙이 재시도다 — CAS에서는 스레드가 서로를 막지 않는다. 각 스레드가 공유 변수를
  원자적으로 바꾸려 시도하고, 다른 스레드가 먼저 값을 바꿔 연산이 실패하면 성공할 때까지 다시
  시도한다 (3장, p.111).[^rahman2025]
- 그래서 얻는 것이 논블로킹이다 — 이 방식은 논블로킹이고, 락을 얻고 놓는 부담을 줄이므로 특히 경합이
  가벼울 때 대체로 더 효율적이다 (3장, pp.111–112).[^rahman2025]
- 결론이 이 풀로 돌아온다 — 바로 이것이 `ForkJoinPool`이 자기 작업 훔치기 큐에 CAS 연산을 쓰는
  이유이며, 스레드를 기다리게 두는 대신 생산적으로 남게 한다 (3장, p.112).[^rahman2025]

## 쪼개는 것은 개발자 책임이다

- 원래 목적이 병렬 처리 가속이다 — `ForkJoinPool`은 처음에 가용 프로세서 코어를 모두 활용해 병렬
  처리를 빠르게 하려고 설계되었고, 그 수단이 분할 정복 알고리즘이었다. 큰 작업을 독립적으로 계산할
  만큼 단순해질 때까지 더 작은 작업으로 나눈다는 것이다 (3장, p.112).[^rahman2025]
- 그러나 나누는 주체가 풀이 아니다 (3장, p.112):[^rahman2025]

  > it is the developer's responsibility to determine how to break the tasks down

- 그 자리를 메우는 것이 `RecursiveTask`와 `RecursiveAction` 같은 클래스다. 개발자가 보통 이들을
  상속해 자기 작업 클래스를 만들고 로직을 넣는다 (3장, p.112).[^rahman2025]
- 기다림의 규칙도 적힌다 — 작업이 여러 자식 작업으로 쪼개지면 부모 작업은 하위 작업이 실행될 때까지
  기다리고, 하위 작업이 끝나면 모든 결과를 하나로 조인(병합)한다 (3장, p.112).[^rahman2025]
- 여기가 다른 풀과 확연히 갈리는 자리다 — 부모 작업이 자식의 완료를 기다리는 동안, 워커 스레드는
  자기 큐의 다른 작업을 계속 하거나 작업이 떨어지면 다른 워커에게서 훔쳐 올 수 있다 (3장,
  p.112).[^rahman2025]

## 쓰는 법과 이 페이지가 다루지 않는 것

- 포크/조인 풀은 작업을 보내는 과정을 단순하게 만들고, 추가 관리 없이 알아서 작업을 효율적으로
  나눈다 (1장, p.22).[^rahman2025]

  ```java
  ForkJoinPool forkJoinPool = new ForkJoinPool();
  forkJoinPool.submit(() -> {
      // your parallelized tasks here
  }).join();
  ```

- 저자는 제출이 쉽다는 점을 짚고, 프레임워크가 효율적인 작업 분배를 알아서 처리해 복잡한 스레드
  관리의 짐을 개발자에게서 덜어 간다고 적는다 (1장, p.22).[^rahman2025]
- 범위를 저자가 직접 긋는다 — 포크/조인 풀은 보통 분할 정복(divide-and-conquer) 알고리즘과 함께
  이야기되고 `RecursiveAction`과 `RecursiveTask`로 작업을 잘게 쪼개지만, 여기서 초점은 그 작업을
  만드는 분할 정복 전략이 아니라 포크/조인 풀 자체다. 더 자세한 논의는 다음 장으로 미룬다 (1장,
  p.22).[^rahman2025]
