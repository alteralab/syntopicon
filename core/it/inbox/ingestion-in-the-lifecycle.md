하나의 질문: **원천에서 데이터를 가져오는 이 한 단계가 왜 파이프라인 전체의 신뢰성을
결정하는가.**

## 최대의 병목

- 자리 — **데이터 원천, 쓰고 있는 원천 시스템의 특성, 데이터가 저장되는 방식을 이해한 뒤에는
  데이터를 모아야 한다. 데이터 엔지니어링 수명 주기의 다음 단계는 원천 시스템으로부터의 데이터
  반입(data ingestion)이다** (2장, p.39).[^reis2022]
- 판정 — **우리 경험상 원천 시스템과 반입은 데이터 엔지니어링 수명 주기의 가장 중대한
  병목을 이룬다. 원천 시스템은 보통 직접 통제 밖에 있고 무작위로 응답 불능이 되거나 낮은
  품질의 데이터를 줄 수 있다. 또는 데이터 반입 서비스가 여러 이유로 알 수 없게 작동을 멈출
  수 있다. 그 결과 데이터 흐름이 멈추거나 저장·처리·서빙에 불충분한 데이터를 전달한다**
  (2장, p.40).[^reis2022]
- 파급 — **신뢰할 수 없는 원천과 반입 시스템은 데이터 엔지니어링 수명 주기 전체에 파문
  효과(ripple effect)를 낳는다** (2장, p.40).[^reis2022]

## 반입 단계의 공학 질문

- 시스템을 설계하거나 짓기 전에 던지는 일차 질문들 (2장, p.40):[^reis2022]
  - **내가 반입하려는 데이터의 유스케이스는 무엇인가? 같은 데이터셋의 여러 버전을 만드는
    대신 이 데이터를 재사용할 수 있는가?**
  - **이 데이터를 생성하고 반입하는 시스템은 신뢰할 만한가, 그리고 데이터는 내가 필요할 때
    가용한가?**
  - **반입 이후 데이터의 목적지는 어디인가?**
  - **데이터에 얼마나 자주 접근해야 하는가? 데이터는 보통 어떤 볼륨으로 도착하는가?**
  - **데이터는 어떤 형식인가? 하류의 저장·변환 시스템이 이 형식을 다룰 수 있는가?**
  - **원천 데이터는 하류에서 즉시 쓰기 좋은 상태인가? 그렇다면 얼마 동안 그런가, 그리고
    무엇이 그것을 못 쓰게 만들 수 있는가?**
  - **데이터가 스트리밍 원천에서 온다면 목적지에 닿기 전에 변환돼야 하는가? 스트림 자체
    안에서 데이터를 변환하는 인플라이트 변환(in-flight transformation)이 적절하겠는가?**

## 배치는 스트림의 특수한 처리 방식이다

- 이 책이 세우는 관점 — **우리가 다루는 사실상 모든 데이터는 본질적으로 스트리밍이다.
  데이터는 거의 언제나 그 원천에서 연속적으로 생산되고 갱신된다. 배치 반입은 단지 이
  스트림을 큰 덩어리로 처리하는 특화되고 편리한 방식일 뿐이다 — 예컨대 하루치 데이터
  전부를 한 배치로 다루는 것** (2장, p.40).[^reis2022]
  - 이 관점은 Kleppmann이 배치와 스트림을 유한·무한 입력의 차이로 가르는 서술과 층위가
    다르다. 저자들은 **처리 대상의 존재론**(모든 데이터는 스트림)을 말하고, 그쪽은
    **계산의 종료 조건**(입력이 유한한가)을 말한다. 후자의 축은
    [배치 처리](../synthesis/batch-processing.md)와
    [스트림 처리](../synthesis/stream-processing.md)에 있다.
- **스트리밍 반입은 하류 시스템 — 다른 애플리케이션이든, 데이터베이스든, 분석 시스템이든 —
  에 연속적이고 실시간인 방식으로 데이터를 제공하게 해 준다. 여기서 실시간(또는 준실시간)은
  데이터가 생산된 뒤 짧은 시간(예: 1초 미만) 안에 하류 시스템에서 가용해진다는 뜻이다.
  실시간이라 부를 자격을 주는 지연은 도메인과 요구사항에 따라 다르다** (2장,
  p.41).[^reis2022]
- 배치의 발동 조건과 그 대가 — **배치 데이터는 미리 정해진 시간 간격으로, 또는 데이터가 미리
  설정된 크기 임계에 닿을 때 반입된다. 배치 반입은 한 방향 문(one-way door)이다 — 데이터가
  일단 배치로 쪼개지고 나면 하류 소비자의 지연은 본질적으로 제약된다** (2장,
  p.41).[^reis2022]
- 왜 배치가 기본이었나 — **레거시 시스템의 한계 때문에 배치는 오랫동안 데이터를 반입하는
  기본 방식이었다. 배치 처리는 특히 분석과 ML에서 하류 소비를 위해 데이터를 반입하는 극히
  인기 있는 방식으로 남아 있다** (2장, p.41).[^reis2022]
- 무엇이 바뀌었나 — **그러나 많은 시스템에서 저장과 연산이 분리된 것, 그리고 이벤트 스트리밍·
  처리 플랫폼이 흔해진 것이 데이터 스트림의 연속 처리를 훨씬 접근 가능하고 점점 더 인기
  있게 만든다. 선택은 대체로 유스케이스와 데이터 적시성에 대한 기대에 달렸다** (2장,
  p.41).[^reis2022]

## 스트리밍 우선을 고르기 전에

- 저자들이 던지라는 질문들 (2장, pp.41–42):[^reis2022]
  - **실시간으로 반입하면 하류 저장 시스템이 그 데이터 흐름 속도를 감당할 수 있는가?**
  - **밀리초 단위 실시간 반입이 필요한가? 아니면 이를테면 매 분 데이터를 모아 반입하는
    마이크로배치(micro-batch) 접근으로 충분한가?**
  - **스트리밍 반입의 유스케이스는 무엇인가? 스트리밍을 구현해 실현하는 구체적 이득은
    무엇인가? 실시간으로 데이터를 받으면 배치보다 나아지는 어떤 행동을 취할 수 있는가?**
  - **스트리밍 우선 접근이 그냥 배치를 하는 것보다 시간·돈·유지보수·다운타임·기회비용
    면에서 더 비싸지 않겠는가?**
  - **인프라가 실패해도 내 스트리밍 파이프라인과 시스템은 신뢰할 만하고 이중화돼 있는가?**
  - **유스케이스에 가장 적절한 도구는 무엇인가? 관리형 서비스(Amazon Kinesis, Google Cloud
    Pub/Sub, Google Cloud Dataflow)를 써야 하는가, 아니면 카프카·플링크·스파크·펄사 등의
    인스턴스를 직접 세워야 하는가? 후자라면 누가 관리할 것인가? 비용과 트레이드오프는?**
  - **ML 모델을 배포한다면 온라인 예측과 어쩌면 연속 학습으로 어떤 이득을 얻는가?**
  - **살아 있는 프로덕션 인스턴스에서 데이터를 받는가? 그렇다면 반입 프로세스가 이 원천
    시스템에 주는 영향은 무엇인가?**
- 저자들의 권고 — **스트리밍 우선은 좋은 생각처럼 보일 수 있지만 늘 단순하지는 않다. 추가
  비용과 복잡성이 본질적으로 발생한다. 많은 훌륭한 반입 프레임워크가 배치와 마이크로배치
  양식을 모두 다룬다. 우리는 배치가 모델 학습과 주간 리포팅 같은 흔한 유스케이스에 훌륭한
  접근이라고 본다. 배치 대비 트레이드오프를 정당화하는 업무 유스케이스를 식별한 뒤에만
  진짜 실시간 스트리밍을 채택하라** (2장, p.42).[^reis2022]

## 푸시와 풀

- 정의 — **데이터 반입의 푸시(push) 모델에서는 원천 시스템이 데이터베이스든 객체 저장소든
  파일시스템이든 타깃으로 데이터를 써 낸다. 풀(pull) 모델에서는 원천 시스템에서 데이터를
  회수해 온다** (2장, p.42).[^reis2022]
- 경계가 흐리다 — **푸시와 풀 패러다임 사이의 선은 꽤 흐릿할 수 있다. 데이터는 데이터
  파이프라인의 여러 단계를 지나가면서 흔히 밀리기도 하고 당겨지기도 한다** (2장,
  p.42).[^reis2022]
- ETL은 풀이다 — **배치 지향 반입 워크플로에서 흔히 쓰이는 ETL(extract, transform, load)
  프로세스를 보자. ETL의 추출(E) 부분은 우리가 풀 반입 모델을 다루고 있음을 분명히 한다.
  전통적 ETL에서 반입 시스템은 고정된 스케줄로 현재 원천 테이블 스냅샷을 질의한다** (2장,
  p.42).[^reis2022]
- CDC는 방식마다 다르다 (2장, p.42):[^reis2022]
  - **한 흔한 방법은 원천 데이터베이스에서 행이 바뀔 때마다 메시지를 촉발한다. 이 메시지는
    큐로 밀리고 반입 시스템이 그것을 집어 간다.**
  - **또 다른 흔한 CDC 방법은 데이터베이스의 모든 커밋을 기록하는 이진 로그(binary log)를
    쓴다. 데이터베이스는 자기 로그로 민다. 반입 시스템은 로그를 읽지만 그 밖에는
    데이터베이스와 직접 상호작용하지 않는다. 이는 원천 데이터베이스에 추가 부하를 거의
    또는 전혀 더하지 않는다.**
  - **배치 CDC의 어떤 판본은 풀 패턴을 쓴다. 예컨대 타임스탬프 기반 CDC에서 반입 시스템은
    원천 데이터베이스를 질의해 이전 갱신 이후 바뀐 행을 당겨 온다.**

  같은 기제를 로그 관점에서 더 깊이 다룬 것이
  [변경 데이터 캡처](../concepts/change-data-capture.md)다.
- 스트리밍은 백엔드를 우회한다 — **스트리밍 반입에서 데이터는 백엔드 데이터베이스를 우회해
  엔드포인트로 직접 밀리며, 보통 이벤트 스트리밍 플랫폼이 데이터를 버퍼링한다. 이 패턴은
  센서 데이터를 뿜는 IoT 센서 무리에 유용하다. 현재 상태를 유지하는 데이터베이스에 의존하는
  대신 기록된 각 판독을 하나의 이벤트로 생각하면 된다** (2장, p.42).[^reis2022]
- **이 패턴은 소프트웨어 애플리케이션에서도 인기가 커지고 있는데, 실시간 처리를 단순화하고,
  앱 개발자가 하류 분석을 위해 메시지를 재단할 수 있게 하며, 데이터 엔지니어의 삶을 크게
  단순화하기 때문이다** (2장, p.42).[^reis2022]
