하나의 질문: **디스크에 놓을 바이너리 파일 형식은 무엇을 정해야 하는가.**

## 왜 메모리와 다르게 설계하는가

- 접근 방식부터 다르다 — **애플리케이션 개발자의 관점에서 가상 메모리 덕분에 메모리 접근은
  대체로 투명하고 오프셋을 손으로 관리하지 않아도 된다. 디스크는 시스템 콜로 접근되며, 보통
  대상 파일 안의 오프셋을 지정하고 온디스크 표현을 메인 메모리에 맞는 형태로 해석해야 한다**
  (3장, p.45).[^petrov2019]
- 그래서 **효율적인 온디스크 구조는 이 구분을 염두에 두고 설계돼야 하고, 그러려면 짓고
  수정하고 해석하기 쉬운 파일 형식(file format)을 마련해야 한다** (3장, p.45).[^petrov2019]
- 온디스크 구조에서 **포인터 관리의 의미론은 인메모리 것과 다소 다르다. 온디스크
  [B-트리](../concepts/b-tree-structure.md)를 페이지 관리 기제로 생각하면 유용하다 —
  알고리즘이 페이지(pages)를 조립하고 항해해야 하며, 페이지와 그것을 가리키는 포인터가 그에
  맞게 계산되고 배치돼야 한다** (3장, p.45).[^petrov2019]
- 비유가 하나 있다 — **파일 형식을 만드는 일은 관리되지 않는 메모리 모델(unmanaged memory
  model)을 쓰는 언어에서 자료 구조를 만드는 것과 여러모로 비슷하다. 데이터 블록을 할당하고
  고정 크기 프리미티브와 구조로 원하는 대로 잘라 쓰며, 더 큰 메모리 청크나 가변 크기 구조를
  참조하려면 포인터를 쓴다** (3장, p.46).[^petrov2019]
- 다만 결정적으로 갈리는 대목이 있다 — **관리되지 않는 메모리 모델의 언어는 (합리적 범위
  안에서) 필요할 때마다 메모리를 더 할당하게 해 주고, 연속 메모리 세그먼트가 있는지·단편화됐는지·
  해제한 뒤 무슨 일이 벌어지는지 생각하거나 걱정하지 않아도 되게 한다. 디스크에서는 가비지
  컬렉션과 단편화(fragmentation)를 우리가 직접 챙겨야 한다** (3장, p.46).[^petrov2019]
- 그래서 **데이터 배치는 메모리에서보다 디스크에서 훨씬 중요하다. 디스크 상주 자료 구조가
  효율적이려면 빠른 접근을 허용하는 방식으로 디스크에 데이터를 배치하고, 영속 저장 매체의
  특성을 고려하고, 이진 데이터 형식을 마련하고, 효율적으로 직렬화·역직렬화하는 수단을 찾아야
  한다** (3장, p.46).[^petrov2019]
- 반대로 **메인 메모리에 저장할 때는 메모리 배치 문제 대부분이 존재하지 않거나, 풀기 더 쉽거나,
  서드파티 라이브러리로 풀 수 있다. 예컨대 가변 길이 필드와 특대 데이터를 다루는 일이 훨씬
  직관적이다 — 메모리 할당과 포인터를 쓸 수 있고 특별한 방식으로 배치할 필요가 없기
  때문**이다 (3장, p.46).[^petrov2019]
- **운영체제와 파일시스템이 책임 일부를 떠맡아 주더라도, 온디스크 구조를 구현하는 일은 더 많은
  세부에 주의를 요구하고 함정이 더 많다** (3장, p.46).[^petrov2019]

## 프리미티브와 바이트 순서

- **디스크에 데이터를 효율적으로 저장하려면 압축적이면서 직렬화·역직렬화하기 쉬운 형식으로
  인코딩돼야 한다.** 이진 형식을 이야기할 때 배치(layout)라는 낱말이 자주 등장하는데,
  **`malloc`과 `free` 같은 프리미티브 없이 `read`와 `write`만 있으므로 접근을 다르게 생각하고
  데이터를 그에 맞게 준비해야 하기 때문**이다 (3장, p.47).[^petrov2019]
- **키와 값은 `integer`·`date`·`string` 같은 타입(type)을 가지며 원시 이진 형태로 표현될 수
  있다**(직렬화되고 역직렬화된다). **대부분의 수치 데이터 타입은 고정 크기 값으로 표현된다**
  (3장, p.47).[^petrov2019]
- **여러 바이트짜리 수치 값을 다룰 때는 인코딩과 디코딩에 같은 바이트 순서(byte-order,
  엔디언endianness)를 쓰는 것이 중요하다.** 두 갈래의 정의는 이렇다 (3장,
  p.47):[^petrov2019]
  - **빅 엔디언(Big-endian)** — **가장 유의한 바이트(most-significant byte, MSB)에서 시작해
    유의도가 감소하는 순서로 바이트가 이어진다. 곧 MSB가 가장 낮은 주소를 갖는다.**
  - **리틀 엔디언(Little-endian)** — **가장 덜 유의한 바이트(least-significant byte, LSB)에서
    시작해 유의도가 증가하는 순서로 바이트가 이어진다.**
- 실물 예 — **RocksDB는 대상 플랫폼의 바이트 순서를 식별하는 플랫폼별 정의를 갖는다. 대상
  플랫폼의 엔디언이 값의 엔디언과 맞지 않으면 `EndianTransform`으로 바이트를 뒤집는데, 이는
  값을 역순으로 읽어 결과에 이어 붙인다** (3장, p.48).[^petrov2019]
  - 그 정의는 플랫폼 의존이다 — **플랫폼(macOS·Solaris·Aix·BSD 계열·Windows)에 따라
    `kLittleEndian` 변수가 그 플랫폼이 리틀 엔디언을 지원하는지 여부로 설정된다** (3장, p.48
    각주 1).[^petrov2019]
- **레코드는 숫자·문자열·불리언과 그 조합 같은 프리미티브로 이뤄진다. 그러나 네트워크로
  데이터를 옮기거나 디스크에 저장할 때는 바이트 열만 쓸 수 있다.** 그래서 **레코드를 보내거나
  쓰려면 직렬화(serialize)해야 하고**(해석 가능한 바이트 열로 바꾼다) **받거나 읽은 뒤 쓰려면
  역직렬화(deserialize)해야 한다**(바이트 열을 원래 레코드로 되옮긴다) (3장,
  p.48).[^petrov2019]
- 크기는 이렇게 갈린다 — **`byte` 값은 8비트, `short`는 2바이트(16비트), `int`는
  4바이트(32비트), `long`은 8바이트(64비트)다** (3장, p.48).[^petrov2019]
- 부동소수점은 별도다 — **`float`과 `double` 같은 부동소수점 수는 부호(sign)·분수(fraction)·
  지수(exponent)로 표현된다. IEEE Standard for Binary Floating-Point Arithmetic(IEEE 754)
  표준이 널리 받아들여진 부동소수점 표현을 서술한다. 32비트 `float`은 단정도 부동소수점
  값을 나타내며, 첫 23비트가 분수, 다음 8비트가 지수, 1비트가 부호(음수인지 여부)를
  나타낸다** (3장, p.48).[^petrov2019]
- 정확도에 대한 경고가 붙는다 — **부동소수점 값은 분수로 계산되므로 이 표현이 내는 수는 근사일
  뿐이다** (3장, p.48).[^petrov2019]

## 가변 크기 데이터와 비트 묶기

- **모든 프리미티브 수치 타입은 고정 크기다. 더 복잡한 값을 조합하는 일은 C의 `struct`와
  거의 같다 — 프리미티브 값을 구조로 묶고, 고정 크기 배열이나 다른 메모리 영역으로 가는
  포인터를 쓸 수 있다** (3장, p.49).[^petrov2019]
  - 다만 **컴파일러가 구조에 패딩을 더할 수 있고 그것 또한 아키텍처 의존이라는 점은 짚어 둘
    만하다. 이는 정확한 바이트 오프셋과 위치에 대한 가정을 깨뜨릴 수 있다** (3장, p.49
    각주 2).[^petrov2019]
- **문자열과 그 밖의 가변 크기 데이터 타입(고정 크기 데이터의 배열 등)은 배열이나 문자열의
  길이를 나타내는 숫자 뒤에 `size` 바이트의 실제 데이터가 오는 식으로 직렬화될 수 있다.
  문자열의 경우 이 표현을 흔히 UCSD String 또는 Pascal String이라 부르는데, 파스칼
  프로그래밍 언어의 인기 있는 구현에서 이름을 땄다** (3장, p.49).[^petrov2019]
- **대안은 널 종료 문자열(null-terminated strings)이며, 읽는 쪽이 문자열 끝 기호에 닿을
  때까지 바이트 단위로 내용을 소비한다. 파스칼 문자열 접근법에는 이점이 여럿 있다 — 문자열
  내용을 순회하는 대신 상수 시간에 길이를 알아낼 수 있고, 메모리에서 `size` 바이트를 잘라
  바이트 배열을 문자열 생성자에 넘기는 것으로 언어 고유의 문자열을 구성할 수 있다** (3장,
  p.49).[^petrov2019]
- 불리언은 공간을 아낄 자리다 — **불리언은 1바이트를 쓰거나 `true`와 `false`를 1과 0으로
  인코딩해 표현할 수 있다. 불리언이 값을 둘만 가지므로 표현에 온전한 1바이트를 쓰는 것은
  낭비이고, 개발자들은 흔히 불리언 값들을 여덟 개씩 묶어 각 불리언이 딱 1비트를 차지하게
  한다. 모든 1 비트를 set이라 하고 모든 0 비트를 unset 또는 empty라 한다** (3장,
  p.49).[^petrov2019]
- **열거형(Enums, enumerated types의 줄임)은 정수로 표현될 수 있고 이진 형식과 통신
  프로토콜에서 자주 쓰인다. 자주 반복되는 저카디널리티 값을 나타내는 데 쓰인다** — 예로
  B-트리 노드 타입을 `ROOT`·`INTERNAL`·`LEAF`의 열거형으로 인코딩할 수 있다 (3장,
  p.49).[^petrov2019]
- **밀접하게 관련된 또 하나의 개념이 플래그(flags)이며, 묶인 불리언과 열거형의 조합 같은
  것이다. 플래그는 상호 배타적이지 않은, 이름 붙은 불리언 파라미터를 나타낼 수 있다** — 예로
  **페이지가 값 셀을 담는지, 값이 고정 크기인지 가변 크기인지, 이 노드에 딸린 오버플로
  페이지가 있는지를 플래그로 표시할 수 있다** (3장, p.50).[^petrov2019]
- 마스크에 제약이 하나 붙는다 — **모든 비트가 플래그 값 하나를 나타내므로 마스크에는 2의
  거듭제곱 값만 쓸 수 있다**(이진에서 2의 거듭제곱은 언제나 세워진 비트가 하나뿐이므로;
  예컨대 2³ == 8 == 1000b, 2⁴ == 16 == 0001 0000b) (3장, p.50).[^petrov2019]
- **묶인 불리언과 마찬가지로 플래그 값은 비트마스크(bitmasks)와 비트 연산자로 묶인 값에서
  읽고 쓸 수 있다.** 플래그 하나를 세우려면 비트 OR(`|`)와 비트마스크를 쓰고, 비트마스크
  대신 비트시프트(`<<`)와 비트 인덱스를 쓸 수도 있다. 비트를 내리려면 비트 AND(`&`)와 비트
  부정 연산자(`~`)를 쓰고, n번째 비트가 세워졌는지 검사하려면 비트 AND 결과를 0과 비교한다
  (3장, p.50).[^petrov2019]

  ```c
  // Set the bit
  flags |= HAS_OVERFLOW_PAGES;
  flags |= (1 << 2);

  // Unset the bit
  flags &= ~HAS_OVERFLOW_PAGES;
  flags &= ~(1 << 2);

  // Test whether or not the bit is set
  is_set = (flags & HAS_OVERFLOW_PAGES) != 0;
  is_set = (flags & (1 << 2)) != 0;
  ```

## 파일의 뼈대

- 설계의 첫 단추는 주소 지정이다 — **보통 파일 형식 설계는 주소 지정을 어떻게 할지 정하는
  데서 시작한다. 파일이 같은 크기 페이지로 쪼개질 것인지, 그 페이지가 블록 하나로 표현될
  것인지 여러 개의 연속 블록으로 표현될 것인지 정한다. 대부분의 인플레이스 갱신 저장 구조는
  같은 크기 페이지를 쓰는데, 읽기·쓰기 접근을 크게 단순화하기 때문이다. 추가 전용 저장
  구조도 흔히 페이지 단위로 쓴다 — 레코드가 차례로 덧붙고 메모리에서 페이지가 차는 즉시
  디스크로 플러시된다** (3장, p.50).[^petrov2019]
- **파일은 대개 고정 크기 헤더(header)로 시작하고 고정 크기 트레일러(trailer)로 끝날 수 있다.
  둘은 빠르게 접근돼야 하거나 파일의 나머지를 디코딩하는 데 필요한 보조 정보를 담는다. 파일의
  나머지는 페이지로 쪼개진다** (3장, p.50).[^petrov2019]
- **많은 데이터 스토어가 고정 스키마를 갖는데, 테이블이 담을 수 있는 필드의 개수·순서·타입을
  지정한다. 고정 스키마를 갖는 것은 디스크에 저장되는 데이터의 양을 줄이는 데 도움이 된다 —
  필드 이름을 반복해서 쓰는 대신 그 위치 식별자를 쓸 수 있다** (3장, p.51).[^petrov2019]
- 그 배치의 실물 — **고정 크기 필드(생년월일·세금 번호 등)를 구조의 앞머리에 두고 가변 크기
  필드를 그 뒤에 둘 수 있다. 이제 `first_name`에 접근하려면 고정 크기 영역 뒤로
  `first_name_length` 바이트를 잘라 내면 된다. `last_name`에 접근하려면 그 앞에 오는 가변
  크기 필드들의 크기를 확인해 시작 위치를 찾을 수 있다. 여러 필드를 아우르는 계산을 피하려면
  오프셋(offset)과 길이(length)를 둘 다 고정 크기 영역에 인코딩할 수 있고, 그러면 어떤 가변
  크기 필드든 개별적으로 찾을 수 있다** (3장, p.51).[^petrov2019]
- 그 위로 계층이 쌓인다 — **더 복잡한 구조를 짓는 일은 대개 계층을 짓는 일이다. 프리미티브로
  이뤄진 필드, 필드로 이뤄진 셀, 셀로 이뤄진 페이지, 페이지로 이뤄진 섹션, 섹션으로 이뤄진
  리전 하는 식이다. 여기에 따라야 할 엄격한 규칙은 없고, 어떤 종류의 데이터를 위한 형식을
  만드는가에 전적으로 달렸다** (3장, p.51).[^petrov2019]
- **데이터베이스 파일은 흔히 여러 부분으로 구성되며, 항해를 돕고 그 부분들의 시작 오프셋을
  가리키는 룩업 테이블이 파일 헤더나 트레일러 또는 별도 파일에 쓰인다** (3장,
  p.51).[^petrov2019]

## 버저닝과 매직 넘버

- 형식은 반드시 바뀐다 — **데이터베이스 시스템은 끊임없이 진화하고 개발자들은 기능을 더하고
  버그와 성능 문제를 고치려 일한다. 그 결과로 이진 파일 형식이 바뀔 수 있다. 대개 어떤 저장
  엔진이든 하나 이상의 직렬화 형식을 지원해야 한다**(예컨대 현행 하나와 하위 호환을 위한
  레거시 하나 이상). **그러려면 지금 상대하는 파일이 어느 버전인지 알아낼 수 있어야 한다**
  (3장, p.58).[^petrov2019]
- 세 가지 방법이 열거된다 (3장, pp.58–59):[^petrov2019]
  - **파일명의 버전 접두** — **아파치 카산드라는 파일명에 버전 접두를 쓴다. 그러면 파일을
    열지 않고도 어느 버전인지 알 수 있다. 4.0부터 데이터 파일명은 `na` 접두를 갖는다
    (`na-1-big-Data.db` 같은 식). 더 옛 파일은 다른 접두를 갖는다 — 3.0에서 쓰인 파일은
    `ma` 접두다.**
    - 버전 조건: 카산드라 4.0 이상이 `na`, 3.0이 `ma`.
  - **별도 파일** — **PostgreSQL은 버전을 `PG_VERSION` 파일에 저장한다.**
  - **인덱스 파일 헤더** — **버전을 인덱스 파일 헤더에 직접 저장할 수도 있다. 이 경우 헤더의
    일부(또는 헤더 전체)가 버전 사이에 바뀌지 않는 형식으로 인코딩돼야 한다. 파일이 어느
    버전으로 인코딩됐는지 알아낸 뒤에 내용을 해석할 버전별 리더를 만들 수 있다.**
- **어떤 파일 형식은 매직 넘버(magic number)로 버전을 식별한다** (3장, p.59).[^petrov2019]
- 매직 넘버의 정의와 용도 — **파일이나 페이지 헤더에 자주 놓이는 값 중 하나가 매직 넘버다.
  보통 여러 바이트짜리 블록이며 상수 값을 담아 그 블록이 페이지임을 알리거나, 그 종류를
  지정하거나, 버전을 식별하는 데 쓸 수 있다** (4장, p.62).[^petrov2019]
- **매직 넘버는 검증과 온전성 검사(sanity check)에 자주 쓰인다. 임의의 오프셋에 있는 바이트
  열이 매직 넘버와 정확히 일치할 확률은 매우 낮다. 일치한다면 오프셋이 맞을 가능성이 높다.**
  예로 **페이지가 올바르게 적재되고 정렬됐는지 확인하려고 쓰기 중에 매직 넘버 `50 41 47 45`
  (`PAGE`의 16진)를 헤더에 놓을 수 있다. 읽기 중에는 읽은 헤더의 네 바이트를 기대한 바이트
  열과 비교해 페이지를 검증한다** (4장, p.62).[^petrov2019]

## 체크섬

- 손상은 실제로 일어난다 — **디스크의 파일은 소프트웨어 버그와 하드웨어 장애로 망가지거나
  손상될 수 있다. 이 문제를 식별하고 손상된 데이터가 다른 서브시스템이나 다른 노드로 번지는
  것을 막으려면 체크섬(checksums)과 순환 중복 검사(cyclic redundancy checks, CRCs)를 쓸 수
  있다** (3장, p.59).[^petrov2019]
- 용어가 뭉개져 쓰인다는 지적 — **어떤 자료는 암호학적 해시 함수와 비암호학적 해시 함수,
  CRC, 체크섬을 구분하지 않는다. 이들의 공통점은 큰 데이터 청크를 작은 수로 줄인다는 것이지만,
  쓰임새와 목적과 보장은 서로 다르다** (3장, p.59).[^petrov2019]
- 셋의 등급이 나뉜다 (3장, p.59):[^petrov2019]
  - **체크섬은 가장 약한 형태의 보장을 제공하며 여러 비트에 걸친 손상을 탐지하지 못한다.
    보통 `XOR`과 패리티 검사 또는 합산으로 계산된다.**
  - **CRC는 버스트 오류(burst errors, 예컨대 연속된 여러 비트가 손상된 경우)를 탐지하는 데
    도움이 되고, 그 구현은 대개 룩업 테이블과 다항식 나눗셈을 쓴다. 다중 비트 오류를 탐지하는
    것은 결정적으로 중요한데, 통신 네트워크와 저장 장치 장애의 상당 비율이 이런 식으로
    나타나기 때문이다.**
  - **비암호학적 해시와 CRC는 데이터가 변조됐는지 검증하는 데 쓰여서는 안 된다. 그 용도에는
    보안을 위해 설계된 강한 암호학적 해시를 언제나 써야 한다. CRC의 주 목표는 데이터에
    의도치 않고 우발적인 변경이 없었음을 확인하는 것이며, 이 알고리즘들은 공격과 의도적 변경에
    저항하도록 설계되지 않았다.**
- 쓰는 절차는 단순하다 — **디스크에 데이터를 쓰기 전에 체크섬을 계산해 데이터와 함께 쓴다.
  다시 읽을 때 체크섬을 다시 계산해 쓰인 것과 비교한다. 체크섬 불일치가 있으면 손상이 일어난
  것이고 읽은 데이터를 써서는 안 된다** (3장, p.59).[^petrov2019]
- 단위가 파일이 아니라 페이지인 이유 — **파일 전체에 대해 체크섬을 계산하는 것은 흔히
  비실용적이고 접근할 때마다 전체 내용을 읽을 일도 없으므로, 체크섬은 대개 페이지 단위로
  계산돼 페이지 헤더에 놓인다. 이렇게 하면 체크섬이 더 견고할 수 있고**(데이터의 작은
  부분집합에 대해 수행되므로) **손상이 페이지 하나 안에 갇히면 파일 전체를 버리지 않아도
  된다** (3장, p.59).[^petrov2019]
