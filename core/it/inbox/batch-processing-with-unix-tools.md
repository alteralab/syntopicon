하나의 질문: **단일 기계의 Unix 파이프라인이 분산 배치 처리의 무엇을 미리 보여 주는가.**

## 소재 — 웹 서버 로그 한 줄

- 설정 — **요청을 서빙할 때마다 로그 파일에 한 줄을 덧붙이는 웹 서버가 있다고 하자. 예컨대
  NGINX 기본 접근 로그 형식을 쓰면 로그의 한 줄은 다음과 같이 생겼을 것이다** (11장,
  p.454).[^kleppmann2026] 그 줄을 해석하려면 형식 정의를 봐야 한다 —
  `$remote_addr - $remote_user [$time_local] "$request"` 다음에
  `$status $body_bytes_sent "$http_referer" "$http_user_agent"` 가 오며, 뒤에 쓰이는
  일곱째 공백 구분 필드가 요청된 URL이다 (11장, p.454).[^kleppmann2026]
- 왜 이것이 장난감 예제가 아닌가 — **로그 파싱은 억지스러워 보일지 모르지만 많은 현대 기술
  기업의 운영에서 결정적인 부분이고, 광고 파이프라인부터 결제 처리까지 모든 것에 쓰인다. 실제로
  그것은 MapReduce와 "빅 데이터" 운동의 급속한 채택 뒤에 있던 추동력이었다** (11장,
  p.454).[^kleppmann2026]

## 명령의 연쇄

- 과제와 답 — **웹사이트에서 가장 인기 있는 페이지 다섯 개를 찾고 싶다고 하자. Unix 셸에서
  다음과 같이 할 수 있다** (11장, p.454).[^kleppmann2026] 여섯 단계가 파이프로 이어진다.

  ```sh
  cat /var/log/nginx/access.log | awk '{print $7}' | sort | uniq -c | sort -r -n | head -n 5
  ```

- 각 단계가 하는 일 (11장, pp.454–455):[^kleppmann2026]
  - **로그 파일을 읽는다.** (엄밀히 말해 `cat`은 여기서 불필요하다 — 입력 파일을 `awk`의
    인수로 직접 줄 수 있기 때문이다. 그러나 이렇게 쓰면 선형 파이프라인이 더 잘 드러난다.)
  - **각 줄을 공백으로 필드로 쪼개고 각 줄에서 일곱째 필드만 출력한다. 이것이 마침 요청된
    URL이다.**
  - **요청된 URL 목록을 알파벳순으로 정렬한다. 정렬하는 이유는 어떤 URL이 n번 요청됐다면
    정렬된 파일이 같은 URL을 연달아 n번 담게 만들기 위해서다.**
  - **`uniq` 명령은 인접한 두 줄이 같은지 검사해 입력에서 반복된 줄을 걸러 낸다. `-c` 옵션은
    카운터도 출력하게 한다: 서로 다른 URL마다 그 URL이 입력에 몇 번 나타났는지 보고한다.**
  - **둘째 `sort`는 각 줄 앞의 숫자(`-n`)로 정렬하는데, 그 숫자가 그 URL이 요청된 횟수다.
    그다음 결과를 역순(`-r`)으로 — 가장 큰 수가 먼저 오도록 — 돌려준다.**
  - **마지막으로 `head`는 입력의 첫 다섯 줄(`-n 5`)만 출력하고 나머지는 버린다.**
- 저자들의 평가 — **앞의 명령줄은 Unix 도구에 익숙하지 않다면 다소 알아보기 어려워 보이겠지만
  믿을 수 없을 만큼 강력하다. 그것은 기가바이트짜리 로그 파일을 몇 초 만에 처리하고, 필요에 맞게
  분석을 쉽게 고칠 수 있다** (11장, p.455).[^kleppmann2026] 예컨대 **보고서에서 CSS 파일을
  빼고 싶으면 `awk` 인수를 `$7 !~ /\.css$/ {print $7}`로 바꾸고, 상위 페이지 대신 상위 클라이언트
  IP 주소를 세고 싶으면 `awk` 인수를 `{print $1}`로 바꾸면 된다** (11장,
  p.455).[^kleppmann2026]

## 같은 일을 하는 프로그램

- 대안 — **Unix 명령의 연쇄 대신 같은 일을 하는 간단한 프로그램을 쓸 수도 있다** (11장,
  p.456).[^kleppmann2026] 책의 파이썬 판은 해시 테이블에 URL별 카운터를 들고 마지막에 정렬한다.

  ```python
  from collections import defaultdict

  counts = defaultdict(int)

  with open('/var/log/nginx/access.log', 'r') as file:
      for line in file:
          url = line.split()[6]
          counts[url] += 1

  top5 = sorted(((count, url) for url, count in counts.items()),
                reverse=True)[:5]

  for count, url in top5:
      print(f"{count} {url}")
  ```

- 저자들의 판정 — **이 프로그램은 Unix 명령 연쇄만큼 간결하지는 않지만 꽤 읽을 만하고, 둘 중
  어느 쪽을 선호하는지는 부분적으로 취향의 문제다. 그러나 둘 사이의 표면적인 문법 차이 말고도
  실행 흐름에 큰 차이가 있으며, 이 분석을 큰 파일에서 돌리면 그것이 분명해진다** (11장,
  p.456).[^kleppmann2026]

## 정렬인가 인메모리 집계인가

- 차이의 정체 — **파이썬 스크립트는 URL의 인메모리 해시 테이블을 유지하며, 각 URL은 그것이
  보인 횟수로 매핑된다. Unix 파이프라인 예제에는 그런 해시 테이블이 없고, 대신 같은 URL의 여러
  출현이 그냥 반복되는 URL 목록을 정렬하는 데 기댄다** (11장, p.456).[^kleppmann2026]
- 무엇이 갈림길인가 — **어느 접근이 더 나은가? 그것은 URL이 몇 개인가에 달렸다. 대부분의
  중소 규모 웹사이트에서는 아마 모든 구별되는 URL과 URL마다의 카운터를 (가령) 1 GB 메모리에
  넣을 수 있을 것이다. 이 예에서 잡의 작업 집합(working set, 잡이 임의 접근해야 하는 메모리의
  양)은 구별되는 URL의 수에만 달렸다. 단일 URL에 대한 로그 항목이 백만 개 있어도 해시 테이블에
  필요한 공간은 여전히 URL 하나에 카운터 크기를 더한 것뿐이다. 이 작업 집합이 충분히 작으면
  인메모리 해시 테이블이 잘 동작한다 — 노트북에서도** (11장, p.457).[^kleppmann2026]
- 반대쪽 — **한편 잡의 작업 집합이 가용 메모리보다 크면, 정렬 접근이 디스크를 효율적으로 쓸 수
  있다는 이점을 갖는다. 그것은 로그 구조화 저장에서 논의한 것과 같은 원리다: 데이터 덩어리를
  메모리에서 정렬해 세그먼트 파일로 디스크에 써 내고, 그다음 여러 정렬된 세그먼트를 더 큰
  정렬된 파일로 병합할 수 있다. 병합 정렬(mergesort)은 디스크에서 잘 수행되는 순차 접근
  패턴을 갖는다** (11장, p.457).[^kleppmann2026] 그 원리의 본가는
  [LSM 트리](../concepts/lsm-tree.md)와 [LSM 컴팩션](../concepts/lsm-compaction.md)에 있다.
- 그래서 도구가 알아서 한다 — **GNU Coreutils(Linux)의 `sort` 유틸리티는 디스크로 흘려보내는
  것으로 메모리보다 큰 데이터셋을 자동으로 다루고, 여러 CPU 코어에 걸쳐 정렬을 자동으로
  병렬화한다. 이는 앞서 본 단순한 Unix 명령 연쇄가 메모리 부족 없이 큰 데이터셋으로 쉽게
  확장된다는 뜻이다. 병목은 입력 파일을 디스크에서 읽을 수 있는 속도일 가능성이 높다** (11장,
  p.457).[^kleppmann2026]

## 어디서 멈추는가

- **Unix 도구의 한계는 그것들이 단일 기계에서 돈다는 것이다. 메모리나 로컬 디스크에 담기에 너무
  큰 데이터셋은 문제가 되고, 바로 거기서 분산 배치 처리 프레임워크가 등장한다** (11장,
  p.457).[^kleppmann2026]
- 이 예제가 뒤에서 되돌아오는 자리는 셋이다. **MapReduce의 데이터 처리 패턴은 이 웹 서버 로그
  분석 예제와 아주 비슷하고**, 매퍼가 `awk '{print $7}'`, 리듀서가 `uniq -c`에 대응한다 (11장,
  pp.466–467).[^kleppmann2026] **명령 연쇄로 이어진 이 패턴이 분산 배치에서는
  워크플로가 되고** (11장, p.464),[^kleppmann2026] **파이프가 쓰는 작은 인메모리 버퍼가
  가득 차면 생산 프로세스가 기다려야 하는 것이 백프레셔(backpressure)의 한 형태**다 (11장,
  pp.464–465).[^kleppmann2026]
