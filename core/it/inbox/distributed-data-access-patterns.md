하나의 질문: **소유하지 않은 데이터를 읽어야 할 때 무엇으로 읽으며, 네 선택지는 각각 무엇을
얻고 무엇을 내주는가.**

## 이 장이 여는 물음

- **모놀리스에서는 이것이 물음이 아니었다** — 데이터베이스 하나를 쓰는 대부분의 모놀리식
  체계에서 개발자는 테이블을 읽는 데 두 번 생각하지 않는다. SQL 테이블 조인이 예사이고,
  질의 하나로 필요한 데이터 전부를 데이터베이스 호출 한 번에 가져올 수 있다. **데이터가 서로
  다른 서비스가 소유하는 별도 데이터베이스나 스키마로 갈리면서 읽기 연산의 데이터 접근이
  어려워지기 시작한다** (10장, p.284).[^ford2021-hard-parts]
- **장이 스스로 범위를 적는다** (10장, p.284):[^ford2021-hard-parts]

  > This chapter describes the various ways services can gain read access to data they
  > don't own—in other words, outside the bounded context of the services needing the
  > data. The four patterns of data access we discuss in this chapter include the Inter-
  > service Communication pattern, Column Schema Replication pattern, Replicated
  > Cache pattern, and the Data Domain pattern.

  - **읽기다.** 쓰기 권한이 누구에게 있는가는 이 장의 물음이 아니고
    [서비스의 데이터 소유권](service-data-ownership.md)이 갖는다. 이 장은 **주인이 정해진 뒤
    주인이 아닌 쪽이 그 데이터를 어떻게 보는가**를 묻는다.
  - **경계 컨텍스트 밖이라는 것이 물음의 형태다.** 데이터를 필요로 하는 서비스의 경계
    컨텍스트 밖에 그 데이터가 있다는 사실이 네 패턴을 부른다.
- **넷마다 얻는 것과 내주는 것이 있다** — 저자들이 "또 한 번, 절충"이라고 적는다 (10장,
  p.284).[^ford2021-hard-parts]

## 넷을 설명하는 공통 예

- **9장의 위시리스트 서비스와 카탈로그 서비스가 되돌아온다** (10장, pp.284–285, 그림
  10-1).[^ford2021-hard-parts]
  - **위시리스트 서비스**(Wishlist Service)는 고객이 언젠가 사고 싶어 할 항목의 목록을
    유지하고, `Wishlist` 테이블에 **고객 ID·항목 ID·담은 날짜**를 갖는다.
  - **카탈로그 서비스**(Catalog Service)는 회사가 파는 모든 항목을 유지하고, **항목 ID·항목
    설명(`item_desc`)·무게와 높이와 길이 같은 정적 제품 치수 정보**를 갖는다.
- **어긋남은 한 줄이다** — 고객이 자기 위시리스트를 보여 달라고 하면 **항목 ID와 항목 설명이
  함께** 돌아가야 하는데, **위시리스트 서비스의 테이블에 항목 설명이 없다.** 그 데이터는
  변경 통제와 데이터 소유권을 제공하는 단단히 이루어진 경계 컨텍스트 안에서 카탈로그
  서비스가 소유한다 (10장, p.284).[^ford2021-hard-parts]
- **그래서 아키텍트는 이 장의 데이터 접근 패턴 가운데 하나를 써야 한다** (10장,
  p.284).[^ford2021-hard-parts]

## 패턴 하나 - 서비스 간 통신

- **규정** (10장 §"Interservice Communication Pattern", p.285):[^ford2021-hard-parts]

  > The *Interservice Communication pattern* is by far the most common pattern for
  > accessing data in a distributed system. If one service (or system) needs to read data
  > that it cannot access directly, it simply *asks* the owning service or system for it by
  > using some sort of remote access protocol.

  - 저자들이 그 뒤에 한 줄을 붙인다 — **이보다 단순할 수 있겠는가.** 그리고 곧바로 뒤집는다 —
    **소프트웨어 아키텍처의 대부분이 그렇듯 보이는 것이 전부가 아니고, 이 흔한 기법은
    불행히도 단점투성이다** (10장, p.285).[^ford2021-hard-parts]
- **기제** — 위시리스트 서비스가 카탈로그 서비스에 **동기 원격 접근 호출**을 걸어 항목 ID
  목록을 넘기고 그에 대응하는 항목 설명 목록을 받는다 (10장, p.285, 그림
  10-2).[^ford2021-hard-parts]
  - **고객 위시리스트를 가져오는 *모든* 요청마다** 그 원격 호출이 일어난다 (10장,
    p.285).[^ford2021-hard-parts]
- **둘째 단점이 서비스 결합이다** — 위시리스트가 카탈로그 서비스의 가용에 기대야 하므로 두
  서비스는 **의미적으로도 정적으로도 결합돼** 있고, **카탈로그 서비스가 살아 있지 않으면
  위시리스트 서비스도 살아 있지 않다.** 게다가 그 단단한 정적 결합 때문에 **위시리스트
  서비스가 수요에 맞춰 확장하면 카탈로그 서비스도 함께 확장해야 한다** (10장,
  p.286).[^ford2021-hard-parts]
- **표 10-1의 열 머리글과 값을 그대로 옮긴다** (10장, p.286):[^ford2021-hard-parts]

| Advantages | Disadvantages |
|---|---|
| Simplicity | Network, data, and security latency (performance) |
| No data volume issues | Scalability and throughput issues |
| | No fault tolerance (availability issues) |
| | Requires contracts between services |

  - 빈 칸은 원문에서도 비어 있다. **이 패턴만 이점 칸이 둘이고 단점 칸이 넷이다** — 넷 가운데
    이점이 가장 적게 적히는 패턴이다.

## 지연 셋과 그 구간

- **첫째 단점은 느린 성능이고, 저자들이 그것을 지연 셋으로 가른다** (10장,
  pp.285–286).[^ford2021-hard-parts] 셋 다 구간을 준다.

| 지연 | 무엇인가 | 구간 |
|---|---|---|
| 네트워크 지연(network latency) | 서비스로 오가는 **패킷 전송 시간** | 보통 **30ms에서 300ms 사이** |
| 보안 지연(security latency) | 대상 서비스의 엔드포인트가 요청을 수행하는 데 **추가 인가**를 요구할 때 생긴다 | 엔드포인트 보안 수준에 따라 크게 달라지되 대부분의 체계에서 **20ms에서 400ms 사이**일 수 있다 |
| 데이터 지연(data latency) | 최종 사용자에게 돌려줄 정보를 얻으려 **데이터베이스 호출을 여러 번** 해야 하는 상황. 이 예에서는 SQL 테이블 조인 한 문장 대신 카탈로그 서비스가 항목 설명을 가져오는 **추가 데이터베이스 호출**을 해야 한다 | **10ms에서 50ms**의 처리 시간이 더 붙을 수 있다 |

- **셋을 다 더하면 항목 설명을 얻는 데만 최대 1초의 지연이 될 수 있다** (10장,
  p.286).[^ford2021-hard-parts]
  - **저자들이 그 구간의 근거를 대지 않는다.** #hypothesis 7장의 다섯 홉·300밀리초와 같은
    부류이고, 그 자리는 [서비스 세분도](service-granularity.md)에 있다.
  - 지역 호출과 원격 호출이 갈리는 지점의 일반형은
    [원격 프로시저 호출의 문제](../concepts/remote-procedure-call-problems.md)에 있다. **이
    패턴은 그 페이지가 세는 갈림의 실물이고, 이쪽은 거기에 구간 수치를 붙인다.**

## 패턴 둘 - 컬럼 스키마 복제

- **규정** (10장 §"Column Schema Replication Pattern", p.287):[^ford2021-hard-parts]

  > With the *Column Schema Replication pattern*, columns are replicated across tables,
  > therefore replicating the data and making it available to other bounded contexts.

  - **기제** — `item_desc` 열을 `Wishlist` 테이블에 **더한다.** 그러면 그 데이터가 카탈로그
    서비스에 물어보지 않아도 위시리스트 서비스에 있다 (10장, p.287, 그림
    10-3).[^ford2021-hard-parts]
- **가장 큰 문제 둘이 데이터 동기화와 데이터 일관성이다** (10장, p.287).[^ford2021-hard-parts]
  제품이 만들어지거나 카탈로그에서 빠지거나 제품 설명이 바뀔 때마다 카탈로그 서비스가
  **위시리스트 서비스(와 그 데이터를 복제하는 다른 모든 서비스)에 그 변경을 어떻게든 알려야
  한다.**
  - **그 알림은 대개 큐·토픽·이벤트 스트리밍을 쓰는 비동기 통신으로 한다.** **즉각적인
    트랜잭션 동기화가 요구되지 않는 한 비동기가 동기보다 선호되는 선택**인데, 응답성을
    올리고 **서비스 사이의 가용성 의존을 줄이기** 때문이다 (10장, p.287).[^ford2021-hard-parts]
- **셋째 문제가 소유권의 거버넌스다** — 데이터가 **다른 서비스에 속한 테이블 안에** 복제되므로
  그 서비스들이 **공식적으로 소유하지 않는데도 그 데이터를 갱신할 수 있다.** 그것이 다시 더
  많은 데이터 일관성 문제를 만든다 (10장, p.287).[^ford2021-hard-parts]
- **얻는 것이 뚜렷하다** — 데이터 동기화 때문에 서비스들이 여전히 결합돼 있기는 하나, **읽기
  접근이 필요한 서비스가 데이터를 즉시 갖고 자기 테이블에 단순한 SQL 조인이나 질의를 할 수
  있다.** 그것이 **성능·내결함성·확장성을 올리고, 셋 다 서비스 간 통신 패턴에서는 단점이던
  것들**이다 (10장, p.288).[^ford2021-hard-parts]
- **저자들이 이 패턴에 경고를 붙인다** — 위시리스트와 카탈로그 같은 시나리오에는 **대체로
  쓰지 말라고 주의를 준다.** 고려해 볼 만한 상황은 **데이터 집계·리포팅**이거나, **큰 데이터
  양·높은 응답성 요구·높은 내결함성 요구 때문에 다른 데이터 접근 패턴이 맞지 않는** 자리다
  (10장, p.288).[^ford2021-hard-parts]
- **표 10-2의 열 머리글과 값을 그대로 옮긴다** (10장, p.288):[^ford2021-hard-parts]

| Advantages | Disadvantages |
|---|---|
| Good data access performance | Data consistency issues |
| No scalability and throughput issues | Data ownership issues |
| No fault-tolerance issues | Data synchronization is required |
| No service dependencies | |

## 패턴 셋 - 복제 캐싱

- **이 패턴이 뒤집는 전제가 첫 문장에 있다** — 대부분의 개발자와 아키텍트는 캐싱을 **전체
  응답성을 올리는 기법**으로 생각한다. 인메모리 캐시에 데이터를 담아 두면 조회가 수십
  밀리초에서 **몇 나노초**로 내려간다. **그런데 캐싱은 분산 데이터 접근과 공유에도 효과적인
  도구가 될 수 있다** (10장 §"Replicated Caching Pattern", p.288).[^ford2021-hard-parts]
- **규정** (10장, p.288):[^ford2021-hard-parts]

  > This pattern leverages *replicated in-memory caching* so that data needed by other
  > services is made available to each service without them having to ask for it. A
  > replicated cache differs from other caching models in that data is held in-memory
  > within each service and is continuously synchronized so that all services have the
  > same exact data at all times.

  - **다른 캐싱 모형과 갈리는 두 조건이 이 문장에 있다** — 데이터가 **서비스마다 그 안에
    인메모리로** 있고, **계속 동기화돼 모든 서비스가 언제나 정확히 같은 데이터**를 갖는다.
- **기제** — 외부 캐시 의존이 없고 **캐시 인스턴스끼리 서로 통신한다.** 한 캐시에 갱신이
  일어나면 그 갱신이 **즉시(뒤에서) 비동기로** 같은 캐시를 쓰는 다른 서비스들에 전파된다
  (10장, p.290, 그림 10-6).[^ford2021-hard-parts]
- **이 예에서의 배치** — 카탈로그 서비스가 제품 설명의 인메모리 캐시를 **소유하고**(곧 그
  캐시를 고칠 수 있는 유일한 서비스이고), 위시리스트 서비스는 같은 캐시의 **읽기 전용
  인메모리 복제본**을 갖는다 (10장, p.290, 그림 10-7).[^ford2021-hard-parts]
  - 그래서 위시리스트 서비스는 **제품 설명을 가져오려고 카탈로그 서비스를 호출할 필요가 없다.**
    이미 자기 안에 인메모리로 있기 때문이다. 카탈로그 서비스가 제품 설명을 갱신하면 **캐싱
    제품이 위시리스트 서비스 쪽 캐시를 갱신해** 데이터를 일관되게 만든다 (10장,
    p.291).[^ford2021-hard-parts]
- **이점 셋이 뚜렷하다** — **응답성·내결함성·확장성**이다 (10장, p.291).[^ford2021-hard-parts]
  - **응답성** — 서비스 사이에 명시적인 서비스 간 통신이 필요 없으므로 데이터가 인메모리로
    바로 있고, **소유하지 않은 데이터에 대한 가장 빠른 접근**이 된다.
  - **내결함성** — 카탈로그 서비스가 내려가도 위시리스트 서비스는 계속 돈다. 카탈로그
    서비스가 다시 올라오면 **위시리스트 서비스에 아무 지장 없이 캐시들이 서로 연결된다.**
  - **확장성** — 위시리스트 서비스가 카탈로그 서비스와 **독립적으로 확장할 수 있다.**
- **저자들이 이 자리에서 자기 앞 책의 제1법칙을 불러 절충이 있음을 예고한다** (10장,
  p.291):[^ford2021-hard-parts]

  > everything in software architecture is a trade-off, and if an
  > architect thinks they have discovered something that *isn't* a trade-off, it means they
  > just haven't *identified* the trade-off yet.

  - **원문이 그 출처를 `The Fundamentals of Software Architecture`라 적는데 그 책의 실제 제목에
    정관사가 없다**(*Fundamentals of Software Architecture*). 원문 그대로 두었다. 그 책은 이
    KB에 없다.
- **버전 조건**: 2021년 저술 시점 — **모든 캐싱 제품이 복제 캐싱을 지원하지는 않으므로 캐싱
  제품 벤더에 지원 여부를 확인하는 것이 중요하다**고 저자들이 적고, 지원하는 인기 제품으로
  **Hazelcast·Apache Ignite·Oracle Coherence** 셋을 든다 (10장,
  p.290).[^ford2021-hard-parts]
- **표 10-3의 열 머리글과 값을 그대로 옮긴다** (10장, p.293):[^ford2021-hard-parts]

| Advantages | Disadvantages |
|---|---|
| Good data access performance | Cloud and containerized configuration can be hard |
| No scalability and throughput issues | Not good for high data volumes |
| Good level of fault tolerance | Not good for high update rates |
| Data remains consistent | Initial service startup dependency |
| Data ownership is preserved | |

## 인메모리 캐싱 모형 셋

- **저자들이 복제 캐싱을 설명하려고 캐싱 모형 셋을 맞댄다** (10장,
  pp.289–290).[^ford2021-hard-parts]

| 모형 | 데이터가 어디에 있는가 | 서비스 사이 동기화 | 데이터 공유에 쓸 수 있는가 |
|---|---|---|---|
| 단일 인메모리(single in-memory) | 서비스마다 자기 내부 인메모리 캐시 | **없다** — 서비스마다 자기에게만 고유한 데이터를 갖는다 | **못 쓴다** — 캐시 동기화가 없기 때문이다. 서비스 안의 응답성과 확장성을 올리는 데까지다 |
| 분산 캐싱(distributed caching) | 서비스 밖 **캐싱 서버**에. 서비스는 독점 프로토콜로 그 서버에 요청해 공유 데이터를 조회하거나 갱신한다 | 중앙에 하나이므로 해당 없음 | 공유할 수는 있다. **다만 이 패턴에는 효과적이지 않다**(아래) |
| 복제 캐싱(replicated caching) | **서비스마다 자기 안에** 인메모리로, 외부 캐시 의존 없이 | **있다** — 캐시 인스턴스끼리 갱신을 비동기로 전파한다 | **쓸 수 있다.** 이 패턴이 기대는 모형이다 |

- **분산 캐시 모형을 이 패턴에 쓸 수 없는 이유가 셋으로 적힌다** (10장,
  p.289).[^ford2021-hard-parts]
  1. **서비스 간 통신 패턴의 내결함성 문제가 해결되지 않는다** — 데이터를 얻으려고 서비스에
     기대던 것이 **캐싱 서버에 기대는 것으로 옮겨 갔을 뿐**이다.
  2. **경계 컨텍스트가 깨진다** — 캐시 데이터가 중앙화되고 공유되므로 다른 서비스가 그 데이터를
     갱신할 수 있고, 그것이 **데이터 소유권에 관한 경계 컨텍스트를 깨뜨린다.** 캐시와 소유
     데이터베이스 사이에 불일치가 생길 수 있고, 엄격한 거버넌스로 다룰 수 있을 때도 있으나
     **그래도 이 모형의 문제로 남는다.**
  3. **중앙 분산 캐시로의 접근은 원격 호출**이므로 네트워크 지연이 조회 시간에 더해지고, 인메모리
     복제 캐시에 비해 전체 응답성이 나빠진다.

## 복제 캐시가 무는 대가 넷

- **저자들이 절충을 순서대로 넷 센다** (10장, pp.292–293).[^ford2021-hard-parts]
- **첫째 — 캐시 데이터와 기동 시점에 관한 서비스 의존이다.**
  - 카탈로그 서비스가 캐시를 소유하고 채울 책임을 지므로 **최초 위시리스트 서비스가 기동할 때
    카탈로그 서비스가 돌고 있어야 한다.** 카탈로그 서비스가 없으면 최초 위시리스트 서비스는
    연결이 설 때까지 **대기 상태로 들어가야 한다.**
  - **영향을 받는 것은 *최초* 인스턴스뿐이다** — 카탈로그 서비스가 내려가 있어도 다른
    위시리스트 인스턴스는 **다른 위시리스트 인스턴스 하나에서 캐시 데이터를 넘겨받아** 기동할
    수 있다.
  - **한 번 캐시가 차고 나면 카탈로그 서비스의 가용이 더는 필요하지 않다** — 캐시가
    위시리스트 서비스에 들어온 뒤로는 카탈로그 서비스가 오르내려도 위시리스트 서비스(와 그
    인스턴스 전부)에 영향이 없다.
- **둘째 — 데이터 양이다.**
  - 데이터 양이 너무 많으면(예컨대 **500MB를 넘으면**) 이 패턴의 타당성이 빠르게 떨어지고,
    특히 그 데이터를 필요로 하는 서비스 인스턴스가 여럿일 때 그렇다.
  - **서비스 인스턴스마다 자기 복제 캐시를 갖는다** — 캐시 크기가 500MB이고 서비스 인스턴스가
    5개면 **쓰이는 총 메모리가 2.5GB**다.
  - **그래서 아키텍트는 캐시의 크기와 캐시 데이터를 필요로 하는 서비스 인스턴스의 총수를
    *둘 다* 분석해** 복제 캐시의 총 메모리 요구를 정해야 한다.
- **셋째 — 변경률이다.**
  - 데이터의 변경률(갱신률)이 너무 높으면 **복제 캐싱 모형은 대개 서비스 사이의 데이터를
    온전히 동기 상태로 유지하지 못한다.** 데이터 크기와 복제 지연에 따라 달라지되, **일반적으로
    이 패턴은 변동이 심한 데이터(제품 재고 수량 같은)에 잘 맞지 않고** 상대적으로 정적인
    데이터(제품 설명 같은)에 잘 맞는다.
- **넷째 — 설정과 셋업 관리다.**
  - 복제 캐싱 모형에서 서비스들은 **TCP/IP 방송과 조회**로 서로를 안다. 그 방송과 조회 범위가
    너무 넓으면 **소켓 수준의 핸드셰이크를 맺는 데 오래 걸릴 수 있다.**
  - **클라우드와 컨테이너 환경이 이것을 특히 어렵게 만든다** — IP 주소에 대한 통제가 없고 그
    환경들의 IP 주소가 동적이기 때문이다.

## 패턴 넷 - 데이터 도메인

- **9장의 데이터 도메인을 데이터 접근에도 그대로 쓴다** — 9장은 여러 서비스가 같은 테이블에
  써야 하는 **공동 소유권**을 푸는 데 데이터 도메인을 썼고, 서비스들이 공유하는 테이블을
  **하나의 스키마에 넣어 두 서비스가 그 스키마를 공유**하게 했다. **같은 패턴을 데이터 접근에도
  쓸 수 있다**는 것이 이 절이다 (10장 §"Data Domain Pattern", p.293).[^ford2021-hard-parts]
  그 도메인의 규정과 절차는
  [모놀리식 데이터를 쪼개는 다섯 단계](decomposing-monolithic-data.md)가, 공동 소유권의 기법
  쪽은 [서비스의 데이터 소유권](service-data-ownership.md)이 갖는다.
- **저자들이 이 패턴을 소거법으로 도입한다** (10장, p.293).[^ford2021-hard-parts] 서비스 간
  통신은 카탈로그 서비스의 신뢰성 문제와 네트워크 지연·추가 조회의 성능 문제 때문에, 컬럼
  스키마 복제는 높은 데이터 일관성 요구 때문에, 복제 캐시는 높은 데이터 양 때문에 각각
  막혔다고 가정하면 **남는 유일한 해법이 데이터 도메인을 만드는 것**이다.
- **기제** — `Wishlist` 테이블과 `Product` 테이블을 **같은 공유 스키마에 합쳐** 위시리스트
  서비스와 카탈로그 서비스 양쪽이 접근하게 한다. 두 테이블은 **어느 서비스의 소유도 아니고
  둘 사이에 공유되며 더 넓은 경계 컨텍스트를 이룬다.** 제품 설명을 얻는 일은 **두 테이블
  사이의 단순한 SQL 조인**이 된다 (10장, pp.293–294, 그림 10-8).[^ford2021-hard-parts]
- **이점이 크다** — 분산 아키텍처에서 데이터 공유가 대체로 권장되지 않는데도 이 패턴은 다른
  데이터 접근 패턴들에 비해 큰 이점을 갖는다 (10장, p.294).[^ford2021-hard-parts]
  - **서비스들이 서로에게서 완전히 결합이 끊기므로** 가용성 의존·응답성·처리량·확장성 문제가
    모두 풀린다.
  - **응답성이 아주 좋다** — 데이터가 보통의 SQL 호출로 있어서 **복제 캐시 패턴에서 필요하던
    서비스 기능 안의 추가 데이터 집계를 할 필요가 없다.**
  - **데이터 일관성과 데이터 무결성이 아주 높게 채점된다** — 여러 서비스가 같은 데이터
    테이블에 접근하므로 데이터를 옮기거나 복제하거나 동기화할 필요가 없다.
  - **무결성이 보존된다** — 테이블 사이에 **외래 키 제약을 강제할 수 있고**, 뷰·저장
    프로시저·트리거 같은 다른 데이터베이스 아티팩트도 데이터 도메인 안에 존재할 수 있다.
    **사실 그 무결성 제약과 데이터베이스 아티팩트의 보존 자체가 이 패턴을 쓰는 또 하나의
    구동 요인이다.**
- **계약이 사라지는 자리가 이 패턴의 핵심 절충이다** (10장, p.294).[^ford2021-hard-parts]
  - 이 패턴에서는 서비스 사이에 데이터를 옮기는 **추가 계약이 필요 없다 — 테이블 스키마가
    계약이 된다.**
  - **그것이 이점이자 동시에 절충이다.** 서비스 간 통신 패턴과 복제 캐시 패턴이 쓰는 계약은
    **테이블 스키마 위의 추상 계층**을 이루어 테이블 구조의 변경이 좁은 경계 컨텍스트 안에
    머물고 다른 서비스에 영향을 주지 않게 한다. **이 패턴은 더 넓은 경계 컨텍스트를 이루므로,
    데이터 도메인 안 어느 테이블의 구조가 바뀌면 여러 서비스가 함께 바뀌어야 할 수 있다.**
- **또 하나의 단점이 보안이다** — 이 패턴이 데이터 접근과 관련한 보안 문제를 열 수 있다. 그림
  10-8에서 위시리스트 서비스는 **데이터 도메인 안의 *모든* 데이터에 완전한 접근 권한**을 갖는데,
  이 예에서는 괜찮아도 **데이터 도메인에 접근하는 서비스가 어떤 데이터에는 접근하면 안 되는
  때**가 있을 수 있다. **더 좁은 경계 컨텍스트와 엄격한 서비스 소유권은 주고받는 계약을 통해
  다른 서비스가 특정 데이터에 접근하지 못하게 막을 수 있다** (10장,
  p.295).[^ford2021-hard-parts]
- **표 10-4의 열 머리글과 값을 그대로 옮긴다** (10장, p.295):[^ford2021-hard-parts]

| Advantages | Disadvantages |
|---|---|
| Good data access performance | Broader bounded context to manage data changes |
| No scalability and throughput issues | Data ownership governance |
| No fault tolerance issues | Data access security |
| No service dependency | |
| Data remains consistent | |

## 넷을 한자리에 놓으면

**원문에 네 패턴을 맞댄 표가 없다. 아래는 이 KB가 절충표 넷과 본문에서 모은 것이다.**

| | 서비스 간 통신 | 컬럼 스키마 복제 | 복제 캐싱 | 데이터 도메인 |
|---|---|---|---|---|
| 데이터가 어디에 있는가 | 주인 쪽에만 | **남의 테이블에 복사된 열로** | **서비스마다 인메모리 사본으로** | **공유 스키마에 함께** |
| 읽을 때 무엇이 일어나는가 | 원격 호출 | 자기 테이블 조인 | 메모리 조회 | 두 테이블 SQL 조인 |
| 데이터 양의 한계 | **없다**(`No data volume issues`) | 없다 | **있다**(500MB 언저리부터 타당성이 떨어진다) | 없다 |
| 내결함성 | **없다**(`No fault tolerance`) | 문제 없음 | 좋다 | 문제 없음 |
| 일관성 | 언제나 최신 | **문제 있음**(`Data consistency issues`) | 유지된다 | 유지된다 |
| 소유권 | 지켜진다 | **문제 있음**(`Data ownership issues`) | **보존된다** | **거버넌스가 따로 필요하다** |
| 계약 | **필요하다**(`Requires contracts between services`) | 비동기 알림이 필요하다 | 캐싱 제품이 맡는다 | **테이블 스키마가 계약이 된다** |
| 저자들이 권하는 자리 | 가장 흔한 기본값이되 단점이 많다 | **대체로 말린다.** 집계·리포팅이나 다른 셋이 다 막힐 때 | 상대적으로 정적인 데이터 | 다른 셋이 전부 막혔을 때 |

- **절충표 넷이 공통으로 적는 이점이 `Good data access performance`와 `No scalability and
  throughput issues`이고, 그 둘을 서비스 간 통신만 갖지 못한다.** 곧 **가장 흔한 패턴이 나머지
  셋이 공유하는 이점을 하나도 갖지 않는다.** #hypothesis 저자들이 그 대비를 따로 적지 않는다.
- **넷 가운데 이점 칸이 다섯 줄인 것이 복제 캐싱과 데이터 도메인 둘이고, 그 둘만 `Data
  remains consistent`를 적는다.**
- **넷의 이름이 책 안에서 한 번씩 흔들린다** — 셋째 패턴의 절 제목과 표 10-3은 `Replicated
  Caching`이고, 장 도입부의 목록(p.284)과 데이터 도메인 절 본문(p.293)은 `Replicated Cache
  pattern`이다. 내결함성의 표기도 표마다 갈린다 — 표 10-1은 `No fault tolerance`, 표 10-2는
  `No fault-tolerance issues`, 표 10-4는 `No fault tolerance issues`다. **원문 그대로
  두었다.** 9장에서 `delegate`와 `delegation`이 갈린 것과 같은 부류다.

## 뉴먼의 캐시 분류에서 이 패턴은 어디에 앉는가

**다른 소스가 캐시를 자리로 셋 가른다. 복제 캐시가 그 셋에 없다.**

- 뉴먼은 캐시를 **클라이언트 쪽·서버 쪽·요청 캐시** 셋으로 가르고, 클라이언트 쪽을 **오리진의
  범위 밖에서 캐시되는 것**으로 규정한다 (13장 §"Where to Cache", pp.437–442).[^newman2021]
  그 전문은 [분산 체계에서의 캐싱](../concepts/caching-in-distributed-systems.md)에 있다.
- **이 KB의 읽기로는 복제 캐시가 그 분류의 클라이언트 쪽에 앉는다** — 데이터가 오리진(카탈로그
  서비스) 밖인 소비자(위시리스트 서비스) 안에 있기 때문이다. #hypothesis **두 책이 서로를
  호명하지 않으므로 이 대응은 이 KB가 세운 것이다.**
- **그런데 이 대응이 뜻밖의 결과를 낸다 — 포드의 패턴이 뉴먼이 적은 클라이언트 쪽 캐시의 대가에
  대한 답이 된다.**
  - 뉴먼이 클라이언트 쪽 캐시의 대가로 드는 둘째가 **클라이언트들 사이의 불일치**다. 판매·추천·
    프로모션이 각각 카탈로그의 데이터를 캐시하고 있으면 **어떤 무효화 기제를 써도 셋이 정확히
    같은 순간에 갱신된다고 보장할 수 없고**, 알림 기반 무효화 같은 기법이 줄여 줄 수는 있어도
    없애지 못한다 (13장, p.439).[^newman2021]
  - **복제 캐시의 규정이 정확히 그 보장을 주장한다** — `continuously synchronized so that all
    services have the same exact data at all times`다 (10장, p.288).[^ford2021-hard-parts]
  - **그러면서 포드 자신이 그 보장에 조건을 단다** — 변경률이 너무 높으면 **대개 데이터를
    온전히 동기 상태로 유지하지 못한다**는 셋째 절충이다 (10장, p.292).[^ford2021-hard-parts]
    **두 소스가 같은 방향을 가리키는 셈이고, 포드 쪽은 그 보장을 정적인 데이터로 범위를
    좁혀서 산다.** 모순 쌍을 걸지 않았다.
- **뉴먼이 불일치의 완화로 드는 공유 클라이언트 쪽 캐시가 포드의 분산 캐싱 모형이고, 포드는
  그것을 이 용도로 기각한다.**
  - 뉴먼 쪽 근거 — 클라이언트 사이 불일치가 사라지고 데이터 복사본 수가 줄어 메모리 면에서도
    효율적일 수 있다. 대신 **클라이언트가 공유 캐시까지 한 번 왕복해야 한다** (13장,
    p.439).[^newman2021]
  - 포드 쪽 근거 — **의존이 사라지는 것이 아니라 캐싱 서버로 옮겨 갈 뿐**이고, 중앙 캐시를
    다른 서비스가 갱신할 수 있어 **소유권의 경계 컨텍스트가 깨지며**, 원격 호출이라 네트워크
    지연이 붙는다 (10장, p.289).[^ford2021-hard-parts]
  - **겨루는 것이 아니라 재는 것이 다르다.** 뉴먼은 **복사본 수와 불일치**를 재고 포드는
    **내결함성과 데이터 소유권**을 잰다. 최대 하나만 참 시험을 통과하지 못하므로(둘 다 참이다)
    `contradicts`를 걸지 않았다.
- **한 자리는 방향이 정말로 반대다. 그 자리를 그대로 적어 둔다.**
  - **뉴먼의 황금률**은 **캐싱을 우선 성능 최적화로 다루고 데이터의 신선도를 따지기 쉽도록
    가능한 한 적은 자리에 캐시하라**는 것이고, 거기에 **이상적인 캐시 자리 수는 0**이라는 조문이
    붙는다 (13장, pp.447–448).[^newman2021]
  - **포드의 이 패턴은 그 반대쪽으로 간다** — 캐싱을 **성능이 아니라 데이터 접근의 수단**으로
    쓰고, **서비스 인스턴스마다 하나씩** 캐시를 놓는다(그래서 인스턴스 수를 곱해 메모리를
    계산하라는 조문이 따라온다).
  - **그래도 모순 쌍을 걸지 않았다.** 최대 하나만 참 시험을 적용하면 둘 다 참일 수 있다 —
    **뉴먼의 것은 지침이고 포드의 것은 대가가 명시된 패턴**이다. 뉴먼 자신이 0 말고는 전부
    **해야만 하는 최적화**여야 한다고 적고, 포드는 다른 셋이 막혔을 때 이 패턴이 무는 대가
    넷을 먼저 세운다. **두 서술을 함께 읽으면 "이 패턴을 고를 때 뉴먼의 조문은 그 결정이
    해야만 하는 것인지를 묻는 시험으로 남는다"가 된다.** #hypothesis 이 종합은 이 KB의 것이고
    두 책은 서로를 호명하지 않는다.
  - **낡음이 누적된다는 뉴먼의 셈이 이 패턴에는 걸리지 않는다** — 그 셈은 **캐시가 중첩됐을
    때**의 것인데(클라이언트 쪽 TTL 1분 + 서버 쪽 TTL 1분 = 최대 2분), 복제 캐시는 계층이
    하나이고 TTL이 아니라 갱신 전파로 맞춘다. #hypothesis

## 조인이 계층을 올라간 자리에 이 넷이 온다

- **다른 소스가 데이터베이스를 쪼갤 때 깨지는 첫째로 조인을 든다** — 마이크로서비스의 이름으로
  데이터베이스를 쪼개면 **조인 연산이 데이터 계층에서 마이크로서비스 자체로 올라가고**, 아무리
  애써도 그만큼 빠르지는 않을 가능성이 높다 (3장 §Performance, p.81).[^newman2021] 그 전문은
  [데이터 분해가 부르는 문제들](data-decomposition-concerns.md)에 있다.
- **그쪽이 내놓는 대처 셋이 이 장의 패턴 넷 가운데 둘과 같은 것이다** (3장,
  p.83):[^newman2021]

| 뉴먼의 대처 | 포드의 패턴 |
|---|---|
| 식별자를 하류에서 **대량으로 조회**하게 한다 | **서비스 간 통신 패턴** — 그림 10-2가 정확히 항목 ID 목록을 넘겨 설명 목록을 받는 대량 조회다 |
| 필요한 정보를 **국소적으로 캐시**한다 | **복제 캐싱 패턴** — 다만 포드 쪽은 계속 동기화되는 복제 캐시로 조건을 좁힌다 |
| **공격적으로 캐시**한다(월 단위 보고서처럼 드문 연산일 때) | 대응하는 패턴이 없다 — 포드의 넷은 전부 **읽기 시점에 최신을 어떻게 볼 것인가**를 다루고 TTL 기반 낡음을 선택지로 세지 않는다 |

- **포드가 더하는 것이 둘이다** — **컬럼 스키마 복제**(데이터베이스 층에서 열을 복사해 조인을
  다시 데이터 계층으로 내린다)와 **데이터 도메인**(테이블을 같은 스키마에 되합쳐 조인이 애초에
  올라가지 않게 한다)이다. **뉴먼의 대처 목록에 이 둘이 없다.** #hypothesis
- **두 소스가 같은 방향이고 모순 쌍을 걸 자리가 없다.** 뉴먼은 **쪼개면 무엇이 깨지는가**를
  적고 포드는 **깨진 자리를 무엇으로 메우는가**를 적는다. 두 책이 이 자리에서 서로를 호명하지
  않으므로 이 대응은 이 KB가 세운 것이다.

## 책의 사례 - 티켓 배정의 데이터 접근

**9장이 전문가 프로필 테이블의 주인을 User Management 서비스로 정하고 나자, 배정 알고리즘이
그 데이터를 어떻게 읽을 것인가가 남았다. 이 장이 그 물음에 답한다.**

- **여는 사가가 문제를 세운다** (10장, pp.283–284, 사가).[^ford2021-hard-parts]
  - **배정 알고리즘이 그 테이블에 하는 읽기 수가 워낙 많아 질의마다 원격 호출을 하는 것이
    현실적이지 않다**는 것이 출발점이다.
  - 질의 수를 줄이게 알고리즘을 고칠 수 있느냐는 제안이 **절대 불가**로 기각된다.
  - **메시징으로 바꾸면 되지 않느냐는 제안도 기각된다** — **"그건 같은 것이다. 메시징을 쓰든
    REST를 쓰든 다른 어떤 원격 접근 프로토콜을 쓰든 나는 여전히 정보가 돌아오기를 기다려야
    한다."** 이 대사가 이 장의 첫째 패턴이 왜 지연을 무는지를 사례 쪽에서 미리 적는다.
- **닫는 사가가 소거법으로 둘까지 줄인 뒤 수치로 고른다** (10장, pp.295–297,
  사가).[^ford2021-hard-parts]
  - **서비스 통합은 두 서비스가 전혀 다른 도메인에 있어 기각**되고, **공유 데이터 도메인은 티켓
    배정 서비스가 이미 공유 티켓 데이터 도메인 스키마에 붙어 있어 기각**된다(한 서비스가 두
    데이터베이스에 붙을 수 없다는 6장의 규칙이다). **남는 것이 서비스 간 통신과 복제 캐싱
    둘**이다.
  - **데이터 양을 실제로 센다** — 전문가가 **900명**이고, 필요한 것은 전문가의 기술·서비스
    지역·표준 스케줄 가용성이라 **1명당 약 1.3KB**이므로 **합계 약 1,200KB**다. 그리고
    데이터가 상대적으로 정적이다.
  - **인스턴스 수도 센다** — 안전하게 최대치를 쓰기로 하고 **User Management 서비스 최대 2개,
    티켓 배정 서비스 최대 4개**를 잡는다. 이것이 위 §복제 캐시가 무는 대가 넷의 둘째 조문(크기
    × 인스턴스 수)을 그대로 적용한 자리다.
  - **가설 기반 접근으로 절충을 캐낸다** — 아키텍트가 복제 캐시를 가설로 세우고 **다른 절충이
    떠오르느냐**고 물어 팀이 스스로 대가를 찾게 한다. 8장 둘째 사가와 같은 방법이다.
  - **팀이 찾아낸 첫째 절충이 기동 의존**이다 — **User Management 서비스가 먼저 떠 있지 않으면
    티켓 배정이 기능하지 못한다.** 아키텍트가 그것을 서비스 간 통신과 맞댄다 — **원격 호출을
    쓰면 상대가 내려갈 때마다 티켓 배정이 멎지만, 복제 캐시는 한 번 뜨고 나면 더는 의존하지
    않으므로 이 경우에 오히려 더 내결함성이 있다.**
  - **둘째 절충은 팀의 경험 없음이다** — 어떤 캐싱 제품을 쓸 것이냐는 물음에서 나온다. 아무도
    복제 캐싱을 해 본 적이 없다는 것이 **위험**으로 기록되고, 한 사람이 제품 조사와 개념 증명을
    맡기로 하며 아키텍트가 **라이선스 비용과 배포 환경의 기술적 제약**(가용 영역 교차·방화벽
    따위)을 조사하기로 한다.
  - **조사와 개념 증명 뒤에 비용과 노력 면에서 타당하다고 확인되고** 수석 아키텍트의 승인을 받아
    ADR이 만들어진다.
- **ADR의 세 칸을 옮긴다** (10장, pp.297–298, ADR).[^ford2021-hard-parts]

| 칸 | 내용 |
|---|---|
| 제목 | `ADR: Use of In-Memory Replicated Caching for Expert Profile Data` |
| 맥락 | 티켓 배정 서비스가 별도 경계 컨텍스트에서 User Management 서비스가 소유하는 전문가 프로필 테이블에 **끊임없이 접근해야 한다.** 접근 방법은 **서비스 간 통신·인메모리 복제 캐싱·공통 데이터 도메인** 셋이다 |
| 결정 | User Management 서비스와 티켓 배정 서비스 사이에 **복제 캐싱을 쓰되 쓰기 연산의 유일한 주인은 User Management 서비스**로 한다. 티켓 배정 서비스가 이미 공유 티켓 데이터 도메인 스키마에 붙어 있어 추가 스키마에 붙을 수 없고, 사용자 관리 기능과 핵심 티켓팅 기능이 별도 도메인에 있어 테이블을 한 스키마에 합치고 싶지 않으므로 **공통 데이터 도메인은 선택지가 아니다.** 인메모리 복제 캐시는 서비스 간 통신 선택지에 딸린 **성능과 내결함성 문제를 해소한다** |
| 귀결 | 티켓 배정 서비스의 첫 인스턴스를 띄울 때 **User Management 서비스의 인스턴스가 최소 하나는 돌고 있어야 한다.** 이 선택지에는 **캐싱 제품의 라이선스 비용**이 든다 |

- **이 ADR이 맥락 칸에 대안 목록을 제대로 담는 드문 자리다** — 셋을 명시하고 결정 칸에서
  그중 하나를 기각한 근거까지 적는다. 그 형식의 규정과 열셋 전체의 대조는
  [아키텍처 결정 기록](architecture-decision-records.md)에 있다.
- **귀결 칸이 다시 두 층을 섞는다** — 기동 순서라는 **운영 제약**과 라이선스라는 **비용**이 한
  칸에 함께 있다. p.184·p.280 ADR의 같은 버릇이다. #hypothesis
- **10장에도 Summary 절이 없다** — 6장부터 9장까지와 같이 사가와 ADR로 끝나고 p.299가
  11장이다.
- 이 사례의 전체 설정은 [Sysops Squad 사례](sysops-squad-case.md)에 있다.
