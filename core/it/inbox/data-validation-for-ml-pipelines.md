하나의 질문: **코드가 아니라 파이프라인을 흐르는 데이터를 검증할 때, 무엇이 "옳은
데이터"를 정하고 그 기대(expectation)는 어디서 오는가.**

## 이 페이지의 지위 — 심사 논문이자 배포 관측 보고

- **근거 등급은 `peer-reviewed`다.** 심사 학회 논문집에 실렸고 게재 레코드가 1쪽에
  인쇄돼 있다 (`Proceedings of the 2nd SysML Conference, Palo Alto, CA, USA,
  2019`).[^breck2019-data-validation] **학회 이름은 문면대로 SysML이다** — 이 학회는
  2019년 회차 뒤 MLSys로 개명해서 같은 논문이 두 이름으로 인용된다.
- **그러나 6절은 통제 실험이 아니라 자기 배포 관측이다.** 자기 시스템이 이미 깔린 구글
  내부 파이프라인을 들여다본 보고이므로 **대조군이 없다.** "데이터 검증을 켠 쪽과 끄고
  돌린 쪽"의 비교는 이 논문에 없고, 6.2절의 사례는 일화로 제시된다. **아래
  [프로덕션에서 잰 것](#프로덕션에서-잰-것)의 수치는 그 조건 아래서만
  읽는다** — 검증의 효과 크기가 아니라 배포된 시스템에서 무엇이 얼마나 자주 일어났는가다.
- **이 등급이 여는 것은 이 논문이 스스로 잰 값뿐이다.** 7절이 훑는 제3자 수치는 경유
  값이라 여기 옮기지 않는다.

## 데이터 오류가 코드 오류와 다른 점 — 값은 유효한데 틀렸다

이 논문의 문제 설정 전체가 1절의 사례 하나 위에 서 있고, 그 사례는 **구글에서 실제로
일어난 데이터 관련 장애**라고 논문이 밝힌다.[^breck2019-data-validation]

- 서빙 스택을 리팩터링하다가 버그가 들어가 **정수 자질 하나가 서빙 데이터의 어떤
  조각(slice)에서 -1로 고정된다** (Example 1.1, PDF p.2):[^breck2019-data-validation]

  > introduces a bug that pins the value of a specific int feature to -1 for some slice of
  > the serving data (e.g., imagine that the feature's value is generated by doing a RPC
  > into a backend system and the bug causes the RPC to fail, thus returning an error
  > value)

- **여기가 이 축의 급소다** — 그 데이터는 어느 타입 검사도 통과한다
  (Example 1.1, PDF p.2):[^breck2019-data-validation]

  > Note that the data looks perfectly fine for the training code, since -1 is an
  > acceptable value for the int feature.

- 그래서 판정의 근거가 값 하나에 있을 수 없다. 파이프라인이 데이터 생성 논리를 볼 수
  없고 **부작용으로만** 안다는 것이 논문의 진단이고, 그 부작용의 실물이 "어떤 조각에서
  -1이 더 흔해졌다"는 **빈도의 변화**다 (§1, PDF p.2).[^breck2019-data-validation]
- 그 위에 이런 총평이 붙는다 (§1, PDF p.2):[^breck2019-data-validation]

  > Overall, there is little a-priori information that the pipeline can leverage to reason
  > about data errors.

  **곧 데이터 쪽에는 선재하는 명세가 없다.** 이 페이지의 나머지는 "그러면 기대를 어디서
  구하는가"에 대한 이 논문의 답이다.

## 전파와 증폭 — 왜 상류에서 잡아야 하는가

- 모델의 예측이 로그로 남아 다음 훈련 데이터가 되는 되먹임 고리가 이 문제를 키운다
  (§1, PDF p.1):[^breck2019-data-validation]

  > Such feedback loops have the potential to amplify even "small" data errors and lead to
  > gradual regression of model performance over a period of time.

- 그래서 결론이 **배치의 상류 이동**이다 (§1, PDF p.1):[^breck2019-data-validation]

  > Therefore, it is imperative to catch data errors early, before they propagate through
  > these complex loops and taint more of the pipeline's state.

- 위 -1 사례에서 그 고리가 어떻게 닫히는지가 문면에 있다 — 서빙 데이터가 훈련 데이터가
  되므로 다음 판 모델이 그 데이터로 학습되고, **오류는 발견돼 고쳐질 때까지 서빙
  데이터에(따라서 다음 훈련 배치에) 계속 남는다** (Example 1.1, PDF
  p.2).[^breck2019-data-validation]
- 같은 절이 데이터를 알고리즘·인프라와 같은 급으로 올리라고 요구한다 — `we need to
  elevate data to a first-class citizen in ML pipelines, on par with algorithms and
  infrastructure` (§1, PDF p.1).[^breck2019-data-validation]

## 모델 품질 지표는 데이터 오류의 안전망이 아니다

**이 절은 "지표가 오라클 노릇을 한다"는 기대를 논문이 명시적으로 거절하는 자리다.**

- 논문의 요구는 2차 효과가 아니라 데이터에 직접 거는 장치다 (§1, PDF
  p.2):[^breck2019-data-validation]

  > it is important to rely on mechanisms specific to data validation rather than on
  > detection of second-order effects.

- 왜 안 되는지도 같은 자리에 있다 (§1, PDF p.2):[^breck2019-data-validation]

  > The resilience of ML algorithms to noisy data means that errors may result in a small
  > drop in model quality, one that can be easily missed if the data errors affect the
  > model only on specific slices of the data but the aggregate model metrics still look
  > okay.

- **집계 지표의 둔감함이 곧 이 오라클의 실패 조건이다.** 모델이 나쁜 데이터에 견디는
  성질이 여기서는 미덕이 아니라 은폐 기제로 작동한다. 데이터가 조각 단위로 망가질 때
  총계는 멀쩡해 보인다.
- 같은 이유가 표본 검증을 기본에서 끈 근거로도 쓰인다 — 배치 전체를 검증해야 **드물거나
  작지만 중요한 조각에서만 나타나는 이상이 조용히 무시되지 않는다**고 적는다 (§2, PDF
  p.3).[^breck2019-data-validation] 조용한 건너뜀을 막는 쪽이 비용보다 먼저다.

## 표적은 데이터 클리닝이 아니라 코드 버그다

- 논문이 프로덕션 데이터 오류의 가장 흔한 출처를 코드 버그로 지목하고, 거기서 세 가지
  함의를 끌어낸다 (§1, PDF p.2):[^breck2019-data-validation]
  - **오류에 구조가 있다** — 잘못된 코드의 실행을 반영하므로(그 조각의 훈련 예제 전부가
    -1을 받는 식) 무작위 잡음처럼 흩어지지 않는다.
  - **데이터 클리닝 문헌이 다루는 오류와 종류가 다르다** — 개체 해소(entity resolution)
    같은 문제와 같은 것이 아니라고 명시한다.
  - **고치려면 코드를 고쳐야 하고 그것은 자동화가 지극히 어렵다** — 데이터를 자동으로
    "패치"할 수 있다 해도 훈련과 서빙 양쪽에 일관되게 적용해야 하며, 서빙 쪽은 지연
    요건이 빡빡한 스트림이다.
- **그래서 이 시스템의 산출물은 교정이 아니라 경보다.** 실무의 통상 절차는 온콜
  엔지니어가 조사해 코드에서 버그를 찾아 훈련·서빙 양쪽에 수정을 넣는 것이라고
  적는다 (§1, PDF p.2).[^breck2019-data-validation]

## 검증을 세 층으로 가른다

시스템이 지원하는 검증 종류가 셋이고, 각각이 답하는 질문이 문면에 적혀 있다 (§2, PDF
p.4):[^breck2019-data-validation]

| 층 | 원문이 적은 질문 | 잡으려는 것 |
|---|---|---|
| **단일 배치 검증**(single-batch validation) | `are there any anomalies in a single batch of data?` | 배치 하나 안의 이상. 목표는 온콜에게 알리고 조사를 시작시키는 것 |
| **배치 간 검증**(inter-batch validation) | `are there any significant changes between the training and serving data, or between successive batches of the training data?` | 소프트웨어 스택 사이에서 생기는 오류(훈련 데이터 생성과 서빙 데이터 생성의 논리가 다를 때)와 새 코드 롤아웃의 버그 |
| **모델 테스트**(model testing) | `are there any assumptions in the training code that are not reflected in the data ...?` | 훈련 코드가 데이터에 대해 품은 가정 중 데이터에 없는 것 |

- **앞의 둘이 대장이 적어 둔 단일 배치 대 배치 간 2분법이고, 원문에는 셋째가 있다.**
  2분법은 *데이터를 무엇과 비교하는가*의 축(자기 자신 대 다른 배치)이고, 셋째는 비교
  대상이 데이터가 아니라 **훈련 코드**여서 축이 다르다. 셋을 나란히 적을 때 이 비대칭을
  같이 적어야 한다.
- **논문 스스로 이 셋이 망라적이지 않다고 적는다** — `we acknowledge that these checks
  are not exhaustive`이고, 근거는 증명이 아니라 프로덕션 경험이다 (§2, PDF
  p.4).[^breck2019-data-validation]
- **배치는 미니배치가 아니다** (§2, PDF p.3).[^breck2019-data-validation] 여기서 배치는
  파이프라인이 주기적으로 받아들이는 더 큰 시간 구간(예: 하루)이고, 훈련 중 모델 파라미터를
  갱신하는 미니배치와 다르다고 못 박는다.

## 기대의 정본은 스키마이고 스키마는 데이터에서 온다

- 이상(anomaly)의 정의가 먼저다 (§3, PDF p.4):[^breck2019-data-validation]

  > we consider any deviation within a batch from the expected data characteristics, given
  > expert domain knowledge, as an anomaly.

  **"기대되는 데이터 특성"이 정의 안에 들어 있다.** 그러므로 이상 탐지의 실질은 그 기대를
  어디에 적어 두느냐로 옮겨 간다.
- 그 자리가 스키마(schema)다 — 데이터베이스의 스키마 개념을 일반화해 `codifies the expectations
  for correct data`하게 만든 것이고, 훈련 알고리즘이 받는 키-값 목록 형식으로 바뀌면서
  사라진 의미론을 되잡는 **논리 모델**로 규정한다 (§1 PDF p.2, §3 PDF
  p.4).[^breck2019-data-validation]
  - 논문이 드는 예가 이 성격을 드러낸다 — `("age", 150)`이라는 키-값은 그 자질이 사람의
    나이면 오류이고 문서의 나이(일 단위)면 완전히 유효하다 (§3, PDF
    p.4).[^breck2019-data-validation] **자질의 의미를 아는 것은 데이터가 아니라 사람이다.**
- **그런데 이 스키마는 데이터보다 먼저 있지 않다.** 논문이 데이터베이스와의 차이로 드는
  대목이 이 페이지의 중심이다 (§1, PDF pp.2–3):[^breck2019-data-validation]

  > Another difference is that in database systems the schema comes first and provides a
  > mechanism to verify both updates and queries against the data. This assumption breaks
  > in the context of ML pipelines where data generation is decoupled from the pipeline.
  > In essence, in our setup the data comes first. This necessitates new workflows where
  > the schema can be inferred from and co-evolve with the data.

- **곧 기대의 출처가 명세가 아니라 이미 지나간 데이터다.** 이 배치는 검증 축의 다른
  자리에서 이미 나온 구조다 — 기대값을 대상 자신의 현재 동작에서 길어 오는
  [특성화 테스트](../concepts/characterization-test.md)와 그 대가를 잰
  [현재 동작을 오라클로 쓴다는 것](../concepts/current-behaviour-as-oracle.md)이 같은
  모양을 코드 층에서 다룬다. **이 논문은 그 절차를 데이터 층에서 반복하면서, 그
  절차에만 있는 위험(과적합한 기대)을 아래에서 스스로 짚는다.**
- 자질에 붙는 제약(constraint)은 기본 성질(타입·도메인·값 개수)에 더해 **ML 맥락에 고유하고
  코드 중심 오류 양상을 반영하는 것**들이다 (§3, PDF p.4).[^breck2019-data-validation]
  - 존재(presence) 제약은 **데이터 생성 코드가 어떤 예제에서 자질을 조용히 빠뜨리는
    버그**를 겨냥한다(RPC 실패로 자질을 건너뛰는 코드 따위).
  - 도메인(domain) 제약은 **같은 값의 표현이 바뀌는 버그**를 겨냥한다(국가 코드 문자열을
    소문자로 바꾸는 코드 변경 따위).
  - 부록 A가 자질 수준 제약을 더 늘어놓는다 (부록 A, PDF p.13):[^breck2019-data-validation]
    자질 타입(INT·FLOAT·BYTES), 자질 존재(예제 중 최소 몇 분율에 나와야 하는가), 자질 값
    개수(스칼라인가 목록인가·길이가 같은가), 자질 도메인(스키마 수준의 이름 붙은 도메인을
    여러 자질이 공유할 수 있다), 원시 타입과 다른 **의미 타입**(문자열 `"TRUE"`/`"FALSE"`로
    부호화된 불리언 따위), 그리고 **자질 수명 주기 단계**(`UNKNOWN_STAGE`·`PLANNED`·
    `ALPHA`·`BETA`·`PRODUCTION`·`DEPRECATED`·`DEBUG_ONLY`) — 단계가 다르면 같은 이상의
    무게도 다르다는 것이 이 마지막 항목의 요지다.
  - 훈련-서빙 왜곡과 배치 간 드리프트(drift)를 재는 임계값도 **스키마 안의 제약으로** 들어간다
    (`skew_comparator`·`drift_comparator`, 그림 7, PDF p.13).[^breck2019-data-validation]
    곧 **경보의 민감도까지 같은 파일이 소유한다.**

## 스키마의 수명 주기 — 추론하고 사람이 고치고 버전 관리에 넣는다

- 수천 개 자질을 쓰는 파이프라인에서 스키마를 손으로 짓는 것은 **채택 자체를 막는
  장벽**이라고 논문이 적는다 (§3, PDF p.5).[^breck2019-data-validation] 그래서 Data
  Validator가 파이프라인의 가용한 모든 배치에서 **기본 판 스키마를 합성한다.**
- **추론의 목표는 정확한 재현이 아니라 과적합 회피다** (§3, PDF
  p.5):[^breck2019-data-validation]

  > an overfitted schema is more likely to cause spurious alerts when validating a new
  > batch of data, which in turn increases the cognitive overhead for the on-call
  > engineers, reduces their trust in the system, and may even lead them to switch off
  > data validation altogether.

  **경보를 너무 잘 내는 검증기는 꺼진다** — 이 문장이 이 시스템의 설계 제약 대부분을
  설명한다.
- 그 추론이 무엇으로 되는지에 대한 논문의 답은 겸손하다 — `We currently rely on a set of
  reasonable heuristics`이고, 과적합의 양에 보증이나 제어를 붙이는 **더 형식적인 해법은
  향후 과제**라고 적는다 (§3, PDF p.5).[^breck2019-data-validation]
- 초기 스키마가 서면 그다음은 **제안과 승인의 고리**다 (§3, PDF
  p.5):[^breck2019-data-validation] 새 데이터가 들어오면 시스템이 스키마 갱신을 권고하고,
  사용자 인터페이스가 중요한 제안으로 주의를 끌어 클릭 한 번으로 적용하게 하며, 사용자는
  제안을 받아들이거나 직접 고친다. 그림 4의 예시가 그 실물이다 — `event` 자질에
  `IMPRESSIONS`라는 새 값이 나타나자 검증기가 **도메인에 그 값을 더하라는 제안**을
  빨간 `+` 줄로 낸다 (그림 4, PDF p.5).
- **그래서 경보 하나에 결말이 둘이다** — 데이터 생성 과정을 고치거나, 그 경보가 데이터의
  자연스러운 진화에 해당하면 **스키마를 고친다** (§6.1, PDF
  p.8).[^breck2019-data-validation]
- 스키마의 지위에 대한 요구가 명시적이다 (§3, PDF p.5):[^breck2019-data-validation]

  > We expect owners of pipelines to treat the schema as a production asset at par with
  > source code and adopt best practices for reviewing, versioning, and maintaining the
  > schema.

  실제로 자기네 파이프라인에서는 스키마를 **소스 코드의 버전 관리 시스템에 넣어 둔다**고
  적는다 (§3, PDF pp.5–6).
- **훈련 알고리즘과의 공진화도 같은 구조다** — 모델 단위 테스트가 어긋남을 찾으면 스키마를
  고치거나(새 기대를 적어) 훈련 코드를 고친다(실제 데이터 모양에 맞춰). 논문은 이것을
  **또 하나의 공진화**라고 부른다 (§1, PDF p.3).[^breck2019-data-validation]

## 이 스키마가 못 적는 것

- 논문이 완전성을 주장하지 않는다 (§3, PDF p.5):[^breck2019-data-validation]

  > we do not make any claims on completeness – there are reasonable data properties that
  > our schema cannot encode.

- 대신 **표현력을 좁게 유지한 것이 의도**라고 밝힌다. 검증기가 거짓 양성을 피하는 방법
  자체가 좁힘이다 (§3, PDF p.5):[^breck2019-data-validation]

  > avoids false positives by focusing on the narrow set of constraints that can be
  > expressed in our schema and by requiring that the schema is manually curated, thus
  > ensuring that the user actually cares about the encoded constraints.

  **사람이 손으로 고르게 만드는 것이 정밀도 장치의 일부다.** 자동 추론만으로 끝내지 않는
  이유가 여기 있다.
- 7절이 이 선택을 아마존 쪽 시스템과 정면으로 대비한다 — 저쪽은 사용자가 **임의 제약**을
  쓰게 하고, 이쪽은 대다수 사용자의 제약을 담아내면서 **스키마 관리 도구를 만들 수 있는
  제한된 정의 언어**를 골랐다고 적는다 (§7, PDF p.10):[^breck2019-data-validation]

  > While Amazon's system allows users to express arbitrary constraints, we opted to have a
  > restrictive schema definition language that captures the data constraints for most of
  > our users while permitting us to develop effective tools to help users manage their
  > schema.

  **그 대비의 반대쪽이 이 KB에 있다** —
  [선언적 데이터 품질 제약](../concepts/declarative-data-quality-constraints.md)이 여기서
  `Schelter et al., 2018`로 지목된 논문이고, 거기서 임의 제약을 여는 근거(외부 서비스
  호출과 임의 함수를 메트릭에 걸 수 있어야 한다는 유연성 원칙)와 그 대가(제약 집합을
  기계가 관리하지 못해 제안 기능으로 거들고, 그 제안이 표본에서만 참일 수 있다는 것)를
  볼 수 있다. **인용 방향은 한쪽뿐이다** — 저쪽이 1년 먼저 나와 이 논문을 인용하지 않고,
  이 논문이 저쪽을 인용한다.

## 배치 간 검증 — 훈련-서빙 왜곡 세 종류

훈련 데이터와 서빙 데이터가 어긋나는 것을 **훈련-서빙 왜곡**(training-serving skew)이라
부르고, 가장 흔한 원인으로 **두 데이터를 만드는 코드 경로가 다르다**는 것을 든다. 경로가
갈리는 이유는 오프라인 훈련 데이터 생성과 온라인 서빙 데이터 생성의 지연·처리량 요건이
크게 다르기 때문이다 (§4, PDF p.6).[^breck2019-data-validation]

- **용어 주의**: 이 KB는 `skew`를 이미 두 뜻으로 쓴다 — 파티션 사이의 부하 불균형을
  가리키는 [핫스팟 완화](../concepts/relieving-hot-spots.md)의 치우침, 그리고 실제 시각과
  처리 시각의 거리를 가리키는 [이중 시간 데이터](../concepts/bitemporal-data.md)의 스큐다.
  **훈련-서빙 왜곡은 그 둘 중 어느 것도 아닌 셋째 뜻**이라 이 페이지는 왜곡으로 적어
  구분한다.

논문이 경험상 세 범주로 나눈다 (§4, PDF p.6):[^breck2019-data-validation]

- **자질 왜곡**(feature skew) — 같은 예제의 어떤 자질이 훈련 때와 서빙 때 다른 값을 갖는
  경우. 흔한 원인은 개발자가 훈련 데이터 경로에 자질을 더하거나 빼면서 서빙 경로에는
  같은 일을 하지 않는 것이다.
  - 더 흥미로운 기제로 **시간 여행**(time travel)을 든다 — 자질 값이 정적이지 않은
    데이터 원천을 질의해 정해질 때 생긴다. 광고 노출마다 클릭 수를 데이터베이스에서
    가져오는 예에서, 훈련 데이터를 나중에 같은 데이터베이스로 만들면 **서빙 시점 이후에
    쌓인 클릭까지 들어가** 클릭 수가 서빙 때보다 높게 보인다.
- **분포 왜곡**(distribution skew) — 훈련 배치의 자질 값 분포가 서빙 때 보이는 분포와
  다른 경우. 서빙 데이터 양이 너무 커서 표본을 뽑아 다음 날 훈련에 쓰는 설정에서,
  **표본 추출 방식의 결함**이 곧바로 이 왜곡이 된다.
- **채점-서빙 왜곡**(scoring/serving skew) — 채점된 예제 중 일부만 실제로 서빙될 때
  생긴다. 백 개를 채점해 열 개를 보여 주고 사용자가 하나를 클릭하면 그 하나가 양성,
  나머지 아홉이 음성 예제가 되지만 **한 번도 보여 주지 않은 아흔 개는 라벨이 없어 훈련
  데이터에 아예 나타나지 않는다.** 논문은 이것이 암묵적 되먹임 고리를 세워 하위 순위
  항목의 오예측 가능성을 더 키운다고 적고, **이 종류의 탐지가 앞의 둘보다 어렵다**고
  덧붙인다.

탐지 배치도 같은 절에 있다 (§4, PDF p.6):[^breck2019-data-validation] 서빙 인프라가
서빙 데이터의 표본을 로그로 남겨 훈련 파이프라인으로 되가져오고, Data Validator가 들어오는
훈련 배치와 서빙 배치를 계속 비교한다. **자질 왜곡은 대응하는 배치들을 키로 조인한 뒤
자질별로 비교**하고, **분포 왜곡은 분포 사이 거리를 재는 지표**에 기댄다. 서빙 배치도
스키마에 비추어 따로 검증한다.

## 분포 거리 — 카이제곱 검정이 왜 안 되는가

- 출발점은 **분포가 다른 것이 정상**이라는 인정이다 — 날마다 예제 분포는 실제로 다르므로
  거리는 언제나 양수이고, 물음은 **경보를 낼 만큼 큰가**로 옮겨 간다 (§4, PDF
  p.6).[^breck2019-data-validation]
- 통계적 적합도 검정을 버린 이유가 기계적이다 (§4, PDF pp.6–7):[^breck2019-data-validation]

  > the variance of test statistics typically has an inverse square relationship to the
  > total number of examples, which makes these tests sensitive to even minute differences
  > in the two distributions.

- **그것을 합성 실험으로 보인다** (§4, PDF p.7, 그림 5).[^breck2019-data-validation]
  - 설정: N(0,1)에서 **1억 점**을 뽑아 대조 표본으로 삼고, 그중 **1만 점**을 N(0,2)에서
    뽑은 것으로 무작위 치환한다. 논문은 이 치환량을 **원 데이터의 0.01%**(1만/1억, 표본
    개수 기준 비율)라고 적고, ML이 견딜 만한 미량이며 **사람이라면 두 분포를 "같다"고
    볼 양**이라고 규정한다.
  - 결과: 유의수준 1% 기준으로 카이제곱 검정을 **10회 시행**했더니 **7회에서** 귀무가설을
    기각해 분포 왜곡 경보를 냈을 것이다 — 논문의 표현으로 `this method would needlessly
    fire an alert 7 out of 10 times and would most likely be considered a flaky detection
    method`.
  - **단위와 분모**: 7/10은 시행 횟수이고 파이프라인 수가 아니다. 0.01%는 치환된 점의
    비율이다. **이 실험은 합성 데이터다** — 저자들은 실제 제품 팀의 오류 없는 데이터로도
    반복해 정성적으로 같은 결과를 얻었다고 적지만 그쪽 수치는 논문에 없다.
- 대신 고른 지표는 **값마다의 확률 차 중 최댓값**(largest change in probability)이다
  (§4, PDF p.7):[^breck2019-data-validation]

  ```math
  d_\infty(p, q) = \max_{i \in S} |p_i - q_i|
  ```

  - 고른 이유가 통계적 우월성이 아니라 **사람이 쓸 수 있음**이다 — 자연스러운 해석이
    있어 팀이 임계값을 정하기 쉽고(`allow changes of only up to 1% for each value` 같은
    식으로), 경보에 **범인 값**(culprit value)이 딸려 와 조사의 출발점이 된다.
  - 그 범인 값의 예로 다시 `-1`이 나온다 — 빈도 변화가 가장 큰 값이 `-1`이면 백엔드가
    실패해 기본값을 내는 문제일 수 있고, 논문은 **자기네 프로덕션 파이프라인에서 실제로
    관측된 상황**이라고 괄호로 덧붙인다.
  - 부록 B가 별개의 지표 `d₁`(값마다의 확률 차의 절댓값 합)을 함께 다루므로 **두 기호를
    섞으면 뜻이 뒤집힌다** (부록 B, PDF pp.13–14).[^breck2019-data-validation] 같은 자리에서
    경험 드리프트와 이론 드리프트의 관계를 디리클레 사전분포로 다루고, **표본 수가 각각
    10억 이상이고 값의 가짓수가 100 미만이면 경험 드리프트가 이론 드리프트의 건전한
    근사**라고 결론짓는다.

## 모델 단위 테스트 — 스키마로 훈련 코드를 퍼즈한다

- 겨냥이 다르다 — 앞의 두 층이 기대와 데이터의 어긋남을 찾는다면, 이 층은 **기대와 훈련
  코드의 가정**이 어긋난 것을 찾는다 (§5, PDF p.7).[^breck2019-data-validation]
- 예가 로그 변환이다 — 훈련 코드가 어떤 수치 자질에 로그를 취하면 그 값이 늘 양수라는
  암묵 가정을 하는 것인데, 스키마가 그 가정을 적고 있지 않고 마침 그 훈련 배치에 양수만
  들어 있으면 **검증도 훈련도 아무것도 잡지 못한다.** 모델이 서빙에 올라가 비양수 값을
  만나는 순간 서빙 인프라 안에서 터진다 (§5, PDF p.7).[^breck2019-data-validation]
- 방법은 **퍼즈 테스트**(fuzz testing)이고, 스키마가 입력 생성을 안내한다 (§5, PDF
  pp.7–8).[^breck2019-data-validation] 스키마 제약을 지키는 합성 예제를 만들어 훈련 코드를
  몇 번 돌린다 — `event` 자질이 있으면 값 하나가 `CLICK`이나 `CONVERSION` 중 균일 무작위로
  뽑히고, 정수 자질은 스키마가 정한 범위 안의 난수가 되는 식이다. **생성에 시드를 줄 수
  있어 결정적 출력이 나온다.**
- 어긋남을 찾으면 결말이 둘이고 **둘 다 하는 것이 가장 튼튼하다**고 적는다 (§5, PDF
  p.8):[^breck2019-data-validation] 훈련 코드를 고치거나(`max(value, 1)`에 변환을 걸거나),
  스키마에 그 자질이 양수라고 적거나. 둘 다 하면 데이터가 그 가정을 어길 때 경보가 뜨고
  데이터가 틀렸을 때 모델이 죽지 않는다.
- **논문이 한계를 스스로 적는다** — `This fuzz-testing strategy is obviously not
  fool-proof`이고 무작위 데이터가 오류를 못 건드린 채 통과할 수 있다 (§5, PDF p.8).
  그러면서 실무에서는 **수백 개 정도의 무작위 예제**로도 흔한 오류가 걸렸다고 적는다.
- 이 층의 지위 주장이 하나 있다 (§5, PDF p.8):[^breck2019-data-validation]

  > To our knowledge, this application of unit testing in the context of ML and for the
  > purpose of data validation is a novel aspect of our work.

  **저자들의 자기 규정이지 독립적으로 확인된 우선권 주장이 아니다.**

## 경보의 정밀도가 설계 제약이 된다

- 요구가 명시적이다 — 시스템은 **높은 정밀도로 믿을 만한 경보를 내고**, 온콜이 근본 원인을
  빨리 짚을 만큼의 맥락을 함께 줘야 한다 (§1, PDF p.2).[^breck2019-data-validation]
- 이유는 사람 쪽에 있다 (§1, PDF p.2):[^breck2019-data-validation]

  > Our experience shows that on-calls tend to ignore alerts that are either spammy or not
  > actionable, which can cause important errors to go unnoticed.

- **이 제약이 앞의 선택 셋을 한 줄로 꿴다** — 표현력을 좁힌 스키마, 과적합을 피하는 추론,
  카이제곱 대신 해석 가능한 거리. 셋 다 재현율이 아니라 **정밀도와 조치 가능성**을 산
  결정이다.
- 논문이 이 사람 요인을 미해결로 남긴 자리도 있다 — 고쳐지지 않는 이상의 이유 하나로
  **인지 부하에 따라 경보를 놓치거나 무시하는 사람**을 들면서, 경보를 **어떻게 그리고
  언제** 전달할지에 유의해야 한다고 되풀이한다 (§6.1, PDF p.9).[^breck2019-data-validation]

## 프로덕션에서 잰 것

**아래는 전부 대조군 없는 배포 관측이다** — 위
[이 페이지의 지위](#이-페이지의-지위--심사-논문이자-배포-관측-보고) 참조.

- **표본**: 데이터 검증을 쓰고 프로덕션 서빙 인프라로 모델을 미는 **700개 넘는 ML
  파이프라인**이다 (§6.1, PDF p.8).[^breck2019-data-validation]
- **스키마는 실제로 진화한다** (그림 6, PDF p.8).[^breck2019-data-validation] 700개 넘는
  파이프라인에 걸친 **수동 스키마 변경 횟수의 히스토그램**이고, 대다수가 **다섯 번
  이하**의 스키마 개정을 갖고 그 뒤로 분포가 잦아든다. 논문의 읽기는 입력 데이터가
  **진화하되 완전히 변덕스럽지는 않다**는 것이다.
  - 도판 자체는 이미지라 막대별 값은 옮기지 않는다. 가로축은 스키마 편집 횟수
    (`1`·`[2-5]`·`[5-10]`·`[10-20]`·`[20-50]`), 세로축은 파이프라인의 백분율이다.
- **이상 종류별 분포** (표 1, PDF p.9).[^breck2019-data-validation] **집계 창은 최근
  30일**이고 단위는 **평가 대상 파이프라인의 비율**이다. 열 셋의 뜻이 각각 다르다 —
  `Used`는 그 경보를 낼 수 있는 스키마를 가진 파이프라인의 비율, `Fired`는 하루라도 그
  이상이 발화한 파이프라인의 비율, `Fixed given Fired`는 발화한 것 중 고쳐진 비율이다.
  **셋을 같은 분모로 읽으면 안 된다.** 표에서 가장 자주 발화한 셋만 옮긴다.

  | 이상 범주 | Used | Fired | Fixed given Fired |
  |---|---|---|---|
  | 새 자질 열(데이터에는 있고 스키마에는 없음) | 100% | 10% | 65% |
  | 범주형 자질의 도메인 밖 값 | 45% | 6% | 66% |
  | 자질 열 누락(스키마에는 있고 데이터에는 없음) | 97% | 6% | 53% |

  - **"고쳐졌다"의 조작적 정의가 캡션에 있다** — 그 종류의 이상이 **이틀 연속 발화하지
    않으면** 고쳐진 것으로 셌다. 캡션이 스스로 두 오차를 적는다: 고친 다음 날 같은
    종류의 새 이상이 오면 **수정을 놓치고**, 파이프라인이 멈췄거나 예제 검증을 껐으면
    **고쳐지지 않은 것이 고쳐진 것으로 보인다.**
  - 논문의 읽기 — 가장 흔한 둘(새 자질 열, 예상 밖 문자열 값)은 **건강한 파이프라인에서도
    생긴다.** 우편번호 같은 필드에는 새 값이 늘 나타나고 자질 엔지니어는 새 열을 계속
    만든다. 반면 **자질 누락과 데이터 누락은 걱정거리**다.
  - 거의 발화하지 않는 검사도 값이 있다고 적는다 — 자질 열의 물리 타입이 틀리는 일은 아주
    드물지만, 그 검사가 **스키마의 규정적 성격과 디스크 위 실제 데이터의 일치**를 확인해
    준다.
- **모델 단위 테스트의 플릿 통계** (§6.1, PDF p.9).[^breck2019-data-validation] 집계 창은
  **한 달**이다.
  - **파이프라인의 70% 넘게**가 모델 단위 테스트를 하나 이상 정의해 두었다.
  - 그 테스트들이 **8만 회 넘게** 실행됐다(지속적 테스트 프레임워크가 돌린 것 포함).
  - 그 실행 중 **6%가 실패**했고, 실패는 훈련 코드가 데이터에 대해 틀린 가정을 했거나
    **스키마가 덜 명시됐다**는 뜻이라고 적는다.
- **사례 연구의 수치는 단위가 문면에 없다.** Google Play 추천 파이프라인에서 로그에는 늘
  빠지고 훈련에는 늘 있던 자질 몇을 찾아냈고, 그 왜곡을 없앤 뒤 온라인 A/B 실험에서
  `improved the app install rate on the main landing page of the app store by 2%`였다
  (§6.2, PDF p.9).[^breck2019-data-validation] **상대 증가인지 절대 퍼센트포인트인지
  원문이 밝히지 않으므로** 이 KB는 원문 표현까지만 옮긴다.
- **진단 시간의 사례** (§6.2, PDF pp.9–10).[^breck2019-data-validation] 영상 추천 팀이
  새 플랫폼으로 옮기는 중 서빙 데이터의 자질 누락 경보가 떴고, 백엔드가 자질 일부를 다른
  형식으로 저장해 파싱 코드에서 조용히 버려지고 있었다. **문제를 진단하고 고치는 데 이틀이
  걸렸고, 비슷한 문제가 몇 달씩 걸린 적이 있다**고 적는다. **표본 하나짜리 일화이고
  비교 대상이 "비슷한 문제"라는 서술뿐**이므로 효과 크기로 쓸 수 없다.
- **검증만 쓰는 팀이 있다** (§6.2, PDF p.10).[^breck2019-data-validation] 훈련도 서빙도
  하지 않고 **오직 데이터 검증을 돌리려고** ML 파이프라인을 세우는 팀들이 있다 — 훈련·서빙
  인프라는 예전 것을 쓰면서 데이터 감시와 경보만 이쪽에서 받는다. 자질 저장소 이전을
  검증하는 데 쓴 팀도 둘 있다(옛 저장 시스템과 새 저장 시스템의 데이터셋에 스키마 검증과
  드리프트 탐지를 걸었다).

## 이 KB의 다른 데이터 페이지와 갈리는 자리

이 페이지가 답하는 질문은 **기대가 어디서 오는가**다. 이웃한 데이터 페이지들은 같은
낱말을 쓰면서 다른 질문에 답한다.

- [선언적 데이터 품질 제약](../concepts/declarative-data-quality-constraints.md) —
  **선언한 것이 무엇으로 환원되어 어떻게 실행되는가.** 같은 해에 같은 문제를 푼 아마존
  쪽 시스템이고, 7절이 이 논문과 정면으로 대비한다(위
  [이 스키마가 못 적는 것](#이-스키마가-못-적는-것) 참조). **기대의 출처를 묻는 이
  페이지와 달리 그쪽은 제약의 실행 기제를 묻는다** — 제약을 메트릭 계산으로 번역해
  집계 질의로 몰아넣고, 데이터가 자라면 상태를 들고 증분으로 다시 잰다.
- [데이터 품질 강제 패턴](../concepts/data-quality-enforcement-patterns.md) — **규칙을
  어느 자리에서 강제하는가.** AWAP는 변환 앞뒤에 감사 단계를 두고, Constraints Enforcer는
  검증을 저장소에 위임한다. 규칙의 내용은 주어진 것으로 놓는다. **이 페이지는 그 규칙이
  어떻게 생겨나 어떻게 낡는지를 담당한다** — 이 논문의 스키마는 강제되는 자리가 아니라
  **추론되고 승인되는 자리**에서 산다.
- [품질 관측 패턴](../concepts/quality-observation-patterns.md) — **오늘의 규칙이
  낡았는지 어떻게 관측하는가.** 이 논문의 답은 관측이 아니라 **스키마 갱신 제안**이라는
  점에서 갈린다.
- [관측 탐지 패턴](../concepts/observability-detector-patterns.md) — **초록불로 끝난 잡이
  실은 틀렸다는 것을 어떻게 아는가.** 거기의 Skew Detector가 재는 것은 볼륨이고 여기의
  왜곡은 값의 분포다. **죽음의 고리와 되먹임 고리가 같은 모양이라는 것이 두 페이지가
  만나는 자리다** — 저쪽은 직전 실행을 기준으로 삼아 나쁜 날이 새 기준이 되고, 이쪽은
  서빙 데이터가 다음 훈련 데이터가 되어 오류가 눌러앉는다.
- [데이터 웨어하우스의 데이터 품질 관리](../concepts/data-quality-management.md) —
  **나쁜 데이터를 어디서 교정하는가.** 그쪽은 원천 그대로 적재하고 교정을 하류로 미룬다.
  **이 논문은 교정 자체를 하지 않는다** — 오류의 출처가 코드 버그라 데이터를 고치는 것이
  답이 아니라고 보기 때문이다.
- [훈련 데이터 품질](../concepts/training-data-quality.md) — **좋은 훈련 데이터란
  무엇인가**(양 대 질). 이 페이지는 좋고 나쁨이 아니라 **기대와의 어긋남**을 다룬다.
- [읽기 스키마와 쓰기 스키마](../concepts/schema-on-read-and-schema-on-write.md) —
  **스키마를 강제하지 않는다는 말의 뜻.** 그쪽의 "암묵 스키마는 늘 있다"는 지적과 이쪽의
  "데이터가 먼저 오고 스키마가 역공학된다"는 배치가 같은 사실의 두 면이다.

## 이어지는 페이지

- [테스트 오라클](../concepts/test-oracle.md) — 기대값의 출처를 네 갈래로 가른 이론.
  **데이터 쪽에는 명세 오라클이 없다**는 이 논문의 진단이 그 분류의 어디에 앉는지가
  두 페이지가 만나는 자리다
- [현재 동작을 오라클로 쓴다는 것](../concepts/current-behaviour-as-oracle.md) —
  기대값을 대상 자신에게서 길어 올릴 때 무엇이 남고 무엇이 사라지는가. 스키마 추론이
  데이터 층에서 같은 절차이고, **과적합한 스키마**가 그쪽의 "관측을 의도로 오해하기"에
  대응한다
- [특성화 테스트](../concepts/characterization-test.md) — 같은 절차의 처방 쪽
- [속성 기반 테스트](../concepts/property-based-testing.md) — 기대를 사례가 아니라
  속성으로 적고 입력을 기계가 만들게 하는 갈래. 모델 단위 테스트가 **스키마를 생성기의
  명세로 쓴다**는 점에서 같은 구조이고, 다만 판정이 속성 위반이 아니라 **훈련 코드의
  예외**라는 점이 다르다
- [소비자 주도 계약](../concepts/consumer-driven-contracts.md) — 기대를 적은 사양을
  **누가 소유하는가**. 이 논문에서는 파이프라인 소유자가 스키마를 큐레이션하는데, 정작
  **데이터를 만드는 팀은 다른 팀**이라 계약의 방향이 소비자 주도 쪽에 가깝다
- [후진 호환과 전진 호환](../concepts/backward-and-forward-compatibility.md) — 스키마가
  바뀌는 동안 옛 판과 새 판이 함께 도는 문제. **스키마 진화의 조건**을 다루는 그쪽과
  **스키마가 어떻게 생겨나는가**를 다루는 이쪽이 이어진다
- [에이브로의 쓰기 스키마와 읽기 스키마](../concepts/avro-writer-and-reader-schema.md) —
  같은 진화 문제를 인코딩 층에서 푸는 장치
- [데이터 프로덕트 관측 가능성](../concepts/data-product-observability.md) — 기대를 코드화한
  것을 관측의 구성 요소로 두는 자리
- [데이터 프로덕트 발견 가능성](../concepts/data-product-discoverability.md) — 데이터의
  기대 값과 분포를 사용자·개발자가 코드로 적는다는 같은 장치의 조직 축
- [계약에 의한 설계](../concepts/design-by-contract.md) — 사전·사후 조건이 기대의 출처가
  되는 갈래
- [드리프트 탐지](../concepts/drift-detection.md) — 아무도 배포하지 않았는데 달라지는
  것들. 그쪽은 프롬프트·사용자 행동·기저 모델이고 이쪽은 자질 값의 분포다
- [테스트 오라클 문제](../synthesis/test-oracle-problem.md) — 판정 근거 쪽의 허브
- [데이터 엔지니어링 설계 패턴](../synthesis/data-engineering-design-patterns.md) —
  데이터 품질 패턴 쪽의 허브
