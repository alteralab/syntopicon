하나의 질문: **태스크와 파이프라인 사이의 의존을 어디에 어떻게 그리는가.**

Konieczny의 6장은 그 답을 네 범주·여덟 패턴으로 가른다 — **순서**(Sequence), **팬인**(Fan-In),
**팬아웃**(Fan-Out), **오케스트레이션**(Orchestration). 앞의 셋은 그래프의 모양(직렬·합류·분기)을
정하고, 마지막 하나는 그 그래프를 **몇 개나 동시에 돌릴 것인가**를 정한다.

## 두 층위에서 같은 패턴이 산다

- 이 장의 목표 — **데이터 흐름 디자인 패턴의 목표는 데이터셋 생성에 필요한 모든 단계를 설계하고
  조율하는 것이다. 파이프라인에서 여러 태스크를 사슬로 잇는 것, 병렬 또는 배타 실행 분기를 만드는
  것, 물리적으로 분리된 파이프라인의 의존을 관리하는 것 같은 행동이 여기 포함된다** (6장,
  p.165).[^konieczny2025]
- **이 장 전체를 읽는 열쇠가 되는 구분** — **데이터 흐름 디자인 패턴은 두 개의 다른 수준에서
  동작한다. 첫째 수준은 데이터 오케스트레이션(data orchestration)으로, 여기서 패턴은 하나 또는
  여러 데이터 파이프라인에서 동작한다. 이는 특히 팀 간 협업 문제를 다루려 할 때 유용하다. 둘째
  수준은 데이터 처리 계층(data processing layer)으로, 당신 잡의 환경이다. 여기서 데이터 흐름
  디자인 패턴은 비즈니스 로직을 더 잘 조직해 시간이 지나도 더 명백하고 유지보수하기 쉽게 만드는 것을
  돕는다** (6장, p.165).[^konieczny2025]
  - 여덟 패턴 중 일곱이 **두 층위 모두에서 구현 가능**하고, 저자는 패턴마다 "오케스트레이션에서는
    이렇게, 처리 계층에서는 이렇게"를 따로 적는다. 그래서 이 페이지의 판단은 대부분 "패턴을 쓸까"가
    아니라 **"어느 층위에 그릴까"**다.
- 5장에서 넘어오는 동기 — 데이터 값 패턴이 만든 통찰은 **여전히 당신에게 국소적으로 남는다**.
  값 있는 데이터셋을 조직 내 다른 팀에 노출해 그들의 국소 유스케이스를 강화하게 하면 반대 방향도
  성립한다 — **다른 팀이 그들의 값 있는 데이터셋을 공유해 당신 데이터의 값을 올릴 수 있다.**
  데이터 값 패턴 계열처럼 들리지만 **적용할 규칙 집합이 다르고, 그래서 데이터 흐름 디자인 패턴으로
  다시 찾게 된다** (6장, p.165).[^konieczny2025]

## Local Sequencer — 한 파이프라인 안에서 잇는다

- 범주의 전제 — 순서는 **파이프라인의 복잡성·성능·유지보수에 영향을 주는 중요한 요인**이다.
  저자의 반례는 처리된 데이터셋을 여러 곳에 쓰는 잡이다 — **워크플로에서 그것을 단일 단위로
  표현하면, 데이터베이스 하나에 대한 적재 부분만 재생해야 할 때마다 실행 전체를 재시작해야 한다**
  (6장, p.166).[^konieczny2025]
- 문제의 실물 — 수십 줄에서 수백 줄로 자란 가장 오래된 잡, 세 배가 된 변환 개수, **잡 자체가 매우
  자주 실패하는데 매번 처음부터 다시 시작해야 해서 긴 디버깅 여정으로 이어진다.** 단서가 하나
  붙는다 — **비즈니스 로직은 하나도 제거할 수 없다** (6장, p.166).[^konieczny2025]
- 해법은 소프트웨어 공학의 상식을 그대로 옮긴 것이다 — **복잡한 로직을 단순화하는 좋은 실천은 그것을
  더 작고 따라서 더 접근 가능한 단계로 분해하는 것이다. 데이터 엔지니어링에서도 유효하며, 재조직은
  가독성을 개선하고 관심사 분리도 부각한다** (6장, p.166).[^konieczny2025]
  - **최종 목표는 하나의 큰 컴포넌트를 여러 작지만 연결된 항목으로 분리해 순차적으로(즉 하나씩
    차례로) 돌리는 것이다. 태스크 사이의 의존은 데이터셋 의존에 따라 조직돼야 한다** (6장,
    p.166).[^konieczny2025]
- 저자의 예제는 2장 패턴 둘을 잇는 것이다 — 데이터가 거기 있는지 판정하는 **Readiness Marker**와
  물리적으로 적재하는 **Full Loader**. 이 둘을 **의존 태스크 둘(데이터 오케스트레이션 계층 의존)로
  구현하거나 단일 태스크(데이터 처리 계층 의존)로 구현할 수 있다** (6장, p.167).[^konieczny2025]
- 어느 층위에 그릴지 가르는 세 기준 (6장, p.167):[^konieczny2025]
  - **관심사 분리** — **모든 연산을 같은 항목에 넣으면 이해하기 어려워질 수 있다. 여기서 좋은
    지표는 이름 짓기 어려움이다. 이름을 찾기 힘들거나 이름이 너무 길다고 느껴진다면, 그것은 데이터
    처리 계층의 단일 태스크에 너무 많은 연산을 넣었다는 지표일 수 있다.**
  - **유지보수성** — **데이터 처리 순차성에 의존하는 것은 유지보수에도 도전적이다. 백필이나 자동
    재시도의 경우 실패한 태스크 이전의 성공한 모든 태스크를 다시 계산하게 된다. 예컨대 준비 상태
    확인이 유료 API 10개를 호출하는데 세 번 실패한 잡을 재시작해야 한다면, API 호출을 잡에 포함시킨
    경우 비용 증가를 곧 보게 될 것이다.**
  - **구현 노력** — **데이터 오케스트레이터는 SQL 질의 실행이나 API 호출 같은 흔한 태스크를
    기본 제공하는 여러 추상을 줄 수 있다. 모든 태스크를 한 단위로 합치면 그 편의를 활용할 수 없고
    아마 바퀴를 다시 발명해야 할 것이다.**
- Airflow에서 이 패턴은 `>>` 하나로 표현된다 — **왼쪽이 오른쪽보다 먼저 돌아야 하므로 `>>` 기호로
  의존을 표현한다** (6장, p.169):[^konieczny2025]

  ```python
  input_data_sensor >> load_data_to_table >> expose_new_table
  ```

  - 저자의 자평 — 이것을 사람 말로 옮기면 **"파이프라인은 데이터가 가용해지기를 기다리며 시작한다.
    조건이 충족되면 다음 태스크가 입력 데이터를 내부 테이블에 적재한다. 나중에 마지막 태스크가 내부
    테이블을 최종 사용자에게 노출한다"**가 되는데, **Airflow의 언어가 더 간결하다** (6장,
    p.169).[^konieczny2025]
  - 같은 것을 AWS EMR Step API로도 쓸 수 있고, 거기서는 **의존 설정이 중요하다 —
    `ActionOnFailure=TERMINATE_CLUSTER`. 그러지 않으면 부분 데이터를 노출하고 잡을 성공으로
    간주해 비일관성을 들여올 수 있다. Airflow에는 그런 설정이 필요 없다. 기본적으로 상류 잡의
    성공에 기반한 순차 처리를 활성화하기 때문이다** (6장, p.169).[^konieczny2025]
  - 처리 계층에서는 명시적 사슬 연산자가 없다 — **이전에 정의된 각 변수를 다음 단계의 입력으로
    간주하는 것이 발상이고, 명시적 사슬 연결 인자가 없어도 용법은 직관적으로 남는다** (6장,
    p.169).[^konieczny2025]
- 저자가 상자로 남긴 단서 — **Local Sequencer 패턴은 고급 처리 로직을 만들 때 데이터
  오케스트레이터가 단순한 CRON 표현식에 견줘 갖는 힘을 보여 준다. 그러나 의존이 필요 없는 고립된
  유스케이스라면 CRON 표현식도 여전히 유효한 해법일 수 있다** (6장, p.170).[^konieczny2025]

## 경계는 재시작 경계다

- 결과 절이 첫 자리에 두는 것이자 이 패턴에서 가장 무거운 것이다 — **경계를 잘못 정의하면 실행 시간이 너무 늘거나, 데이터
  오케스트레이션 로직의 스케줄러를 확장할 수 없는 경우 다른 파이프라인에까지 영향을 줄 수 있다.
  그러므로 범위와 태스크 개수 사이에서 좋은 균형을 찾는 것이 중요하다** (6장,
  p.168).[^konieczny2025]
- 저자가 주는 판단 규칙은 하나다 — **데이터 처리 계층과 데이터 오케스트레이션 계층 양쪽에 적용되는
  좋은 어림규칙은 재시작 경계(restart boundaries)를 생각하는 것이다. 즉 개별적으로 재시작돼야 할
  태스크가 무엇인가?** 반입 예제에서는 **Readiness Marker와 Full Loader 태스크가 개별적으로
  실패해야 하고 서로에게 영향을 주지 않아야 한다. 달리 말해 적재 단계가 실패하면 Readiness Marker는
  다시 돌지 않아야 한다. 적재 실행이 이미 데이터의 존재를 함의하기 때문이다** (6장,
  p.168).[^konieczny2025]
  - 각주가 그 전제를 밝힌다 — **이것은 원천의 데이터가 불변임을 가정한다. 생산자가 데이터셋을
    제거할 수 있다면 물론 Readiness Marker 단계를 다시 돌려야 한다** (6장,
    p.168, 각주 1).[^konieczny2025]
- 처리 계층에서는 다른 선을 쓴다 — **가장 컴퓨트 비용이 큰 연산 사이에 경계를 두는 일이 잦다.
  예컨대 중간 데이터셋을 생성한 뒤 최종본으로 변환하는 것이 비싸다면 잡에서 거기 분리선을 둘 수 있다.
  그 덕에 최종 변환이 실패해도 재시도마다 이 비싼 중간 데이터셋 생성을 실행할 필요가 없다** (6장,
  p.168).[^konieczny2025]
- 그리고 재시작 경계와 **반대로 끌어당기는 축이 하나 더 있다** — **트랜잭션 관점에서도 로직 분리를
  추론할 수 있다. 두 개 이상의 연산이 단일 단위로 수행돼야 한다면 함께 두는 것이 말이 된다. 그
  예가 Dynamic Late Data Integrator 패턴을 구현하는 데이터 처리 잡인데, 그것은 데이터를 처리하는
  것에 더해 상태 테이블의 마지막 처리 버전도 갱신한다. 처리 로직과 처리된 버전 저장이 서로에게
  의존하므로 단일 단위로 실행하는 것이 말이 된다** (6장, p.168).[^konieczny2025]
  - **판정 규칙이 하나가 아니라 둘이고 서로 반대 방향으로 민다** — 재시작 경계는 쪼개라고 하고,
    트랜잭션 경계는 붙이라고 한다. 저자는 우선순위를 정하지 않고 둘을 나란히 둔다.

## Isolated Sequencer — 물리적으로 갈린 파이프라인을 잇는다

- 문제의 실물 — 원천 데이터셋을 정제·강화해 시각화 도구용 뷰로 노출하는 팀이 있는데, 시각화 팀과의
  회의 끝에 **대시보드 데이터셋 변환을 데이터 준비 파이프라인에 직접 포함시키는 것은 좋은 생각이
  아니라고 합의했다. 그 부분에 대한 책임을 당신 팀이 지지 않기 때문이다** (6장,
  p.170).[^konieczny2025]
- 해법의 목표 — **물리적으로 격리된 파이프라인들을 결합할 방법을 찾는 것이다. Local Sequencer와
  마찬가지로 가장 중요한 관심사는 경계의 식별이다. 가장 쉬운 해법은 파이프라인을 소비자와 생산자,
  또는 팀 관점에서 나누는 것이다** (6장, p.170).[^konieczny2025]
  - 생산자이면서 동시에 소비자인 경우가 판단을 요구한다 — **모든 생산자·소비자 로직을 한 파이프라인에
    합치는 것이 읽기 어렵게 만든다면 생산자·소비자 접근을 따라 여러 파이프라인으로 쪼개는 것을
    고려해야 한다. 그렇지 않다면 함께 두는 것을 선호해 Local Sequencer 패턴을 쓰는 편이 낫다**
    (6장, p.170).[^konieczny2025]

## 데이터 기반과 태스크 기반 — 누가 바뀔 수 있는가

- **경계 정의는 첫 단계일 뿐이고, 둘째 단계는 촉발 기제(triggering mechanism)를 찾는 것이다.
  여기에는 두 전략이 있다 — 데이터 기반과 태스크 기반** (6장, p.171).[^konieczny2025]
  - **데이터 기반 전략은 2장의 Readiness Marker 패턴에 기반한다. 데이터 생산자가 데이터셋과
    처리 준비가 됐음을 알리는 마커 파일을 생성한다. 소비자는 그 마커 파일을 듣고 있다가 생성을
    탐지하는 즉시 일을 시작한다** (6장, p.171).[^konieczny2025]
  - **태스크 기반 전략에서 데이터 생산자는 마커 파일을 만들지 않는다. 대신 생성된 데이터셋을
    소비할 책임이 있는 파이프라인을 직접 촉발한다** (6장, p.171).[^konieczny2025]
- **결합도가 갈린다** — **데이터 기반 해법의 파이프라인들은 느슨하게 결합되어 진화의 여지가 더
  많다. 유일한 요구는 마커 파일을 존중하는 것이다. 반면 태스크 기반 해법을 이루는 파이프라인들은
  강하게 결합된다. 즉 물리적으로 분리돼 있어도 홀로 살 수 없다. 이것은 데이터 생산자 쪽에서 특히
  눈에 띈다 — 소비자 쪽의 단순한 태스크·파이프라인 이름 변경이 의존 사슬 전체를 실패시키는데,
  생산자가 더 이상 존재하지 않는 태스크를 촉발하려 하기 때문이다** (6장, p.171).[^konieczny2025]
- 그리고 그 결합도가 **바꿀 권한을 누가 갖는지**를 정한다 — **어느 쪽이 바뀔 수 있는가? 데이터
  기반 접근에서 데이터셋 소비자는 더 많은 자유를 갖는다. 데이터 제공자에게 알리지 않고 다른
  데이터셋을 쓰기로 결정할 수도 있다. 반면 태스크 기반 전략에서 소비자는 데이터셋을 그냥 건너뛰기로
  결정할 수 없다. 생산자가 직접 촉발 기제를 갖고 있기 때문이다. 데이터셋이 제거되면 생산자의
  파이프라인이 실패할 수 있다** (6장, p.171).[^konieczny2025]
  - 태스크 기반이 맞는 자리도 저자가 짚는다 — **공유 데이터셋이 없다면(예컨대 소비자가 제공자의
    데이터로 작업하는 대신 사용자에게 어떤 알림을 보내야 한다면) 좋은 접근일 수 있다** (6장,
    p.171).[^konieczny2025]
- Airflow에서 데이터 기반은 `FileSensor`로, 태스크 기반은 `ExternalTaskMarker`·
  `ExternalTaskSensor` 짝으로 구현된다 — 후자에서 **센서는 데이터 제공자의 태스크 실행을 기다리는
  소비자 파이프라인을 나타내고, 마커는 백필을 자동화한다. 마커 태스크는 `devices_loader`
  파이프라인에서 이뤄진 어떤 백필이든 탐지해 자동으로 국소 실행한다** (6장, p.174):[^konieczny2025]

  ```python
  # devices_loader
  success_execution_marker = ExternalTaskMarker(
   task_id='trigger_downstream_consumers',
   external_dag_id='devices_aggregator',
   external_task_id='downstream_trigger_sensor',
  )
  (input_data_sensor >> load_new_devices_to_internal_storage()
     >> success_execution_marker)

  # devices_aggregator
  parent_dag_sensor = ExternalTaskSensor(
   task_id='downstream_trigger_sensor',
   external_dag_id='devices_loader',
   external_task_id='trigger_downstream_consumers',
   allowed_states=['success'],
   failed_states=['failed', 'skipped']
  )
  parent_dag_sensor >> load_data_to_table >> refresh_aggregates
  ```

  - 데이터 기반 쪽의 의존은 **암묵적**이다 — 소비자의 센서가 **일종의 의존 강제자다. 그것이
    실패하면 데이터 제공자가 합의한 대로 데이터를 전달하지 못했다는 뜻이다. 그러나 두 파이프라인이
    상호의존하는지 알 방법이 없다** (6장, p.173).[^konieczny2025]
  - 그 공백을 메우는 것이 리니지다 — **복잡한 데이터 시스템의 중요한 구성 요소는 데이터셋 사이의
    의존을 표현하게 해 주는 데이터 리니지(data lineage) 도구다. 우리 예제에서는 그것으로
    `devices_loader`의 출력을 어떤 데이터셋·파이프라인이 소비하는지 볼 수 있다** (6장,
    p.174).[^konieczny2025] 저자는 10장의 데이터 리니지 패턴 둘과 오픈소스 표준 OpenLineage를
    가리킨다.

## 격리가 되사는 것 — 스케줄과 대화

- 저자의 자평 — **가장 큰 도전은 모든 파이프라인을 동기 상태로 유지하는 것이다. 게다가 이 패턴의
  가장 큰 단점은 논리적 격리를 더하면서 추가 운영 제약도 더한다는 것이다** (6장,
  p.172).[^konieczny2025]
- **스케줄링** — **태스크 기반 해법은 진화 부분에만 영향을 주지 않는다. 스케줄링 빈도라는 중요한
  것도 관련된다. 이상적으로 두 파이프라인이 같은 스케줄을 공유해야 생산자가 소비자를 직접 촉발할 수
  있다. 그렇지 않다면 둘 중 하나가 복잡성을 더 들여와야 한다** (6장, p.172).[^konieczny2025]
  - **생산자 쪽이라면 계획된 실행 스케줄 일부에 대해 촉발 부분을 건너뛰는 조건을 더해야 한다.
    소비자 쪽이라면 같은 일을 하되 자기 스케줄을 생산자에 맞추고 필요할 때만 물리적 데이터 처리를
    돌려야 한다** (6장, p.172).[^konieczny2025]
- **커뮤니케이션** — **Isolated Sequencer는 무엇보다 서로 다른 팀이 관리하는 파이프라인을
  다룬다. 조직에 좋은 커뮤니케이션 문화가 없다면 그것이 문제일 수 있다** (6장,
  p.172).[^konieczny2025]
  - 기술적 우회는 값이 비싸다 — **생산자든 소비자든 반대편의 조건이 바뀌지 않았는지 확인하는 기제를
    더할 수 있다. 그것은 많은 노력을 요구하고, 반대편이 보안상의 이유로 어떤 들어오는 연결도
    받지 않는다면 구현이 불가능할 수도 있다** (6장, p.172).[^konieczny2025]
  - 그래서 저자가 내놓는 답은 기술 밖에 있다 — **더 탄력적인 접근은 더 많은 노력과 시간을 요구한다.
    커뮤니케이션을 효율적으로 만드는 조직 변화를 수반한다. 격리된 각 팀은 자기 입력과 출력을 알고
    있어야 하며, 그래야 계획을 세우는 모든 의존 당사자와, 특히 파괴적 변경을 들여오는 쪽과 효과적으로
    소통할 수 있다. 당신이 이 진화의 촉매일 수 있지만 구현은 당신 일의 기술적 측면을 훨씬 넘어선다**
    (6장, p.173).[^konieczny2025]

## Aligned Fan-In — 모든 부모가 성공해야 한다

- **가장 쉬운 팬인 패턴이다. 모든 직접 부모 태스크가 성공해야 계속 진행한다고 그냥 가정한다**
  (6장, p.175).[^konieczny2025]
- 문제의 실물 — 파이프라인이 원시 방문 이벤트에서 **일간** 집계를 만드는데 데이터셋은 조직 로직상
  **시간 단위로 분할**돼 있다. **소비자는 전체 뷰에만 관심이 있으므로 파이프라인을 일간으로 돌리는
  것은 말이 되지 않는다. 그러나 한 잡에서 너무 많은 데이터가 처리되는 것을 피하려고 시간 분할을
  활용하고 싶다** (6장, p.175).[^konieczny2025]
- 오케스트레이션 쪽 구현은 단순하다 — **공통 태스크로 합류하는 별도 분기들을 정의하는 것이다.
  우리 예에서 이 분기들은 하루의 각 시간에 대한 부분 집계를 생성하는 데이터 처리 잡을 나타낸다.
  모두 완료되면 병합 태스크가 이 시간별 결과를 받아 그날의 최종 출력을 계산한다** (6장,
  p.175).[^konieczny2025]
- 처리 계층은 그렇게 단순하지 않다 — **여기서도 분기를 정의해야 하지만 추가로 분기들이 서로 어떻게
  상호작용하는지 정의해야 한다** (6장, p.176).[^konieczny2025]
  - **첫째 상호작용 결과는 여러 출력이 만들어 낸 단일 데이터 처리 추상이다. 이 맥락에서 `UNION`
    연산자를 써서 열 개수는 같고 행이 더 많은 데이터셋을 얻게 된다. 대안은 `JOIN` 연산으로,
    데이터셋을 행 단위로 결합해 추가 열을 더한다. `JOIN` 접근은 언제나 `UNION` 기반 해법보다 적은
    행을 저장한다. 수직(`UNION`)·수평(`JOIN`) 정렬로 생각할 수 있다** (6장,
    p.176).[^konieczny2025]
  - `UNION`의 함정 하나 — **기본적으로 `UNION`은 위치 기반이라 호환되지 않는 필드를 결합할 수
    있고 이는 오류로 이어진다.** Spark는 **위치가 아니라 열 이름으로 데이터셋을 결합하는
    `unionByName` 메서드**를 제공하지만 **그렇게 인기 있지는 않으므로 SQL이나 다른 도구에서 기본
    `UNION` 구현을 쓸 때 이 점을 유념해야 한다** (6장, p.178).[^konieczny2025]
- **이 패턴의 큰 이점은 피드백 루프 최적화다** — **패턴을 쓰지 않는데 마지막 시간의 처리에 문제가
  있다면 파이프라인은 하루치를 처리한 끝에 가서야 오류를 반환할 것이다. 반면 분리된 로직이라면 더
  작은 볼륨에서 동시에 일하는 24개의 작은 잡을 갖게 되고 결과적으로 문제를 더 빨리 반환한다** (6장,
  p.176).[^konieczny2025]
- 실패 재생도 같은 이유로 싸진다 — **24시간 중 마지막 하나만 실패한다면 그 시간만 고치고 재생하면
  된다. 그러므로 Aligned Fan-In 패턴 없이 24시간에 대한 단일 빅데이터 처리 태스크였다면 나머지
  23시간도 처리해야 했을 것이다. 그리고 이 패턴에서도 Local Sequencer 패턴에서처럼 백필 용이성에
  기반한 분리 로직을 쓰게 된다** (6장, p.176).[^konieczny2025]

## 정렬의 네 가지 대가

- **인프라 스파이크** — **일간 집계 잡이 24개 잡을 동시에 돌릴 것이다. 탄력적 프로비저닝 용량이
  있다면 문제가 아니지만, 없다면 좋은 균형을 찾아 허용 동시 실행 수를 더 작은 수로 줄여야 한다**
  (6장, p.176).[^konieczny2025]
  - 대안 하나 — **동시성을 줄이는 다른 접근은 분기를 가능한 한 빨리, 완전히 증분적인 방식으로
    돌리는 것이다. 24개 시간별 분기라면 각 분기를 매시간 돌리고 그날의 마지막 실행에서만 결과를
    집계한다는 뜻이다** (6장, p.176).[^konieczny2025]
- **스케줄링 스큐**(scheduling skew) — **자식 태스크가 모든 부모의 성공 실행을 요구하므로 부모의
  실행 시간이 불균형하면 스케줄링 스큐로 이어진다. 그렇게 되면 성공한 모든 태스크가 가장 느린 것을
  기다린다. 결과적으로 자식 태스크의 촉발 시각은 가장 긴 부모 태스크에 의존한다** (6장,
  pp.176–177).[^konieczny2025]
- **스케줄링 오버헤드** — **파이프라인이 너무 세밀해도 스케줄링 오버헤드를 수반한다는 것을 알아야
  한다. 데이터 오케스트레이터는 태스크를 스케줄하고 조율하는 데 자원 대부분을 할당해야 할 것이다.
  그러나 그것이 분리하고 가독성을 개선하려면 치러야 할 값이다** (6장, p.177).[^konieczny2025]
- **복잡성** — **분리할수록 파이프라인이 길어진다. 이는 가독성과 이해도 저하 같은 부정적 효과로
  이어질 수 있다. 불행히도 만능 해법은 없으므로 각 파이프라인마다 올바른 경계를 개별적으로 식별해야
  한다** (6장, p.177).[^konieczny2025]
  - 저자가 이 장 전체의 질문으로 압축해 남긴 두 문장 — **"어떤 태스크들이 단일 실행 단위에
    속하는가?"와 "어떤 연산들이 개별적으로 백필돼야 하는가?"** (6장, p.177).[^konieczny2025]

## Unaligned Fan-In — 부분 결과를 내보낸다

- 문제의 실물 — Aligned Fan-In으로 몇 주 잘 돌던 시간별 처리가 **실패한 태스크를 관리하는 적절한
  방법을 결여**했다. **몇 번 어떤 시간이 올바로 처리되지 않았고 그래서 하류 소비자를 위한 집계 뷰를
  생산하지 못했다. 회의 끝에 부분 데이터셋이라도 내보내고 나중에 빈틈을 메우는 편이 낫다고 합의했다**
  (6장, p.178).[^konieczny2025]
- 해법은 **부모의 결과에 대한 의존을 완화**하는 것이고, 두 시나리오가 열린다 (6장,
  p.179):[^konieczny2025]
  - **일부 부모가 성공하고 남은 실패가 허용 가능하다면 어쨌든 자식 태스크를 촉발할 수 있다. 결과적으로
    문제 진술에 있던 부분 데이터셋 문제로 이어질 부분 입력에서 작업하게 될 수 있다.**
  - **모든 부모가 실패한다면, 성공 기준에 기반해 태스크를 돌리는 대신 실패 기준에 기반해 태스크를
    스케줄할 수 있다. 예컨대 그 태스크는 폴백이거나 오류 관리 태스크일 수 있다.**
- Airflow에서는 `trigger_rule` 속성 하나가 이 패턴의 전부다 — Aligned 판과 코드가 동일하고
  **`trigger_rule=TriggerRule.ALL_DONE` 한 줄만 다르다. 기본적으로 Airflow는 모든 부모가 성공할
  때만 태스크를 시작한다. 여기서는 결과와 무관하게 모든 부모 태스크가 완료되기를 기대하는 다른 조건을
  쓴다** (6장, p.181).[^konieczny2025]
- **가독성** — **Unaligned Fan-In 패턴은 데이터 흐름의 가독성과 일반적 이해를 떨어뜨릴 수 있다.
  하류 태스크 두 종류(모든 부모가 성공할 때 실행되는 것과 일부 실패가 있을 때 실행되는 것)를 더할 때
  특히 눈에 띈다. 코드에 들어가지 않고는 실행 흐름을 쉽게 판정할 수 없어 파이프라인이 혼란스러워질
  것이다** (6장, p.179).[^konieczny2025]
  - 저자 자신이 `trigger_rule` 예제를 두고 같은 지적을 반복한다 — **유일한 문제는 규칙이 코드
    안에 숨어 있어서, 파이프라인 그래프를 시각적으로 분석하면 그것을 볼 수 없다는 점이다** (6장,
    p.181).[^konieczny2025]
  - 완화책 — **데이터 오케스트레이션 도구가 "그 외" 시나리오를 다루는 커스텀 함수를 제공하는지
    확인하는 편이 언제나 낫다. 오류를 다룰 때 Airflow에는 실패한 호출을 관리하는
    `on_failure_callback` 함수가 있고, AWS Step Functions는 실패 처리기를 직접 촉발할 수 있는
    `Catch` 필드 타입으로 이를 지원한다** (6장, p.180).[^konieczny2025]

## 부분 데이터는 반드시 알려야 한다

- **부분적으로 성공한 부모들로부터 데이터셋을 생성하기로 했다면 이 사실을 데이터셋 소비자와 공유하는
  것이 중요하다. 그러지 않으면 그들이 완전성 상태에 대해 부정확한 가정을 할 수 있다** (6장,
  p.180).[^konieczny2025]
- 저자가 나열하는 세 가지 방법 (6장, p.180):[^konieczny2025]
  - **가장 단순한 방법은 생성된 데이터셋에 동반하는 완전성 테이블(completeness table)에 완전성
    지표를 저장하고 약간의 산수를 하는 것이다. 예컨대 24개 부모 중 12개만 성공하면 50% 완전이고,
    6개만 성공하면 25%가 되는 식이다.**
  - **다른 방법은 이 정보를 메타데이터 계층에 더하는 것이다(예컨대 클라우드 객체 저장소에 쓰인
    객체의 태그로).**
  - **이 정적 정보를 하류 소비자와 공유되는 알림으로 보완할 수도 있다(예컨대 이메일로).**
- 넷째 선택지는 아예 내보내지 않는 것이다 — **부분 데이터셋을 공유하지 않고 비공개로 두기로 결정할
  수도 있다. 그 경우 먼저 완전성을 판정하고 완전성 상태가 100%가 아니면 결과를 내부 테이블이나
  폴더에 써야 한다** (6장, p.180).[^konieczny2025]
- 완전성 표시를 SQL 안에서 계산하는 것이 이 패턴의 대표 코드다 — **처리된 시간 수가 24와 다르면 그
  행을 근사치로 표시하는 플래그**를 서브질의로 세운다 (6장, p.181):[^konieczny2025]

  ```sql
  INSERT INTO dedp.visits_cube (...,is_approximate)
  SELECT ...,
   (SELECT CASE WHEN hours_subquery.all_hours = 24 THEN false ELSE true END FROM
    (SELECT COUNT(DISTINCT execution_time_hour_id) AS all_hours FROM dedp.visits_raw
       WHERE execution_time_id = '{{ ds }}')
   AS hours_subquery)
  FROM dedp.visits_raw GROUP BY CUBE(...);
  ```

## Parallel Split — 한 부모에서 갈라진다

- 팬아웃 범주의 전제 — **지금까지는 언제나 공통 태스크로 합류하는 파이프라인을 보았다. 그러나 아직
  마지막 유형이 빠졌는데, 한 태스크가 다른 여럿의 입력이 되는 것이다. 이 접근은 하나의 데이터셋이
  데이터 분석이나 데이터 과학처럼 서로 다른 목적으로 여러 팀에 쓰일 때 유용할 수 있다** (6장,
  p.182).[^konieczny2025]
- **첫 팬아웃 패턴에서 부모 태스크 하나가 적어도 두 자식 태스크의 요구 사항이다. 그것들의 로직이
  격리돼 있고 유일한 공통점이 같은 부모 요구 사항이므로 병렬로 돌 수 있다** (6장,
  p.182).[^konieczny2025]
- 문제의 실물은 마이그레이션이다 — 아무도 모르는 C# 레거시 프레임워크를 파이썬으로 다시 쓰는데,
  **역공학 접근이 완벽하지 않을 수 있으므로 소비자가 새 해법으로 전환할 때까지 옛 파이프라인을 계속
  돌리는 편을 택한다. 그러므로 마이그레이션 동안 처리된 데이터셋을 두 곳에 써야 한다** (6장,
  p.183).[^konieczny2025]
- 처리 계층 구현에서 저자가 못 박는 세 가지 (6장, p.183):[^konieczny2025]
  - **분할 처리가 별도의 데이터 읽기 연산을 촉발해서는 안 된다. 대신 모든 공통 계산은 한 번만
    돌아야 한다. SQL의 임시 테이블이나 Spark의 `.persist()` 메서드로 중간 데이터셋을 구체화해
    이를 달성할 수 있다.**
  - **병렬 분기들이 서로 간섭하지 않도록 보장해야 한다. 그러므로 코드베이스가 전역·공유 변수를
    쓴다면 그것들은 읽기 전용이거나 모든 쓰기 프로세스에 걸쳐 호환되는 수정이어야 한다.**
  - **계산이 실행 시간에 민감하다면 전용 컴퓨트 자원을 할당하거나 분할된 작업부하를 병렬로 수용하도록
    자동 확장을 정의해야 한다.**
- **블록된 실행** — **이 단점은 데이터 오케스트레이션 계층과, 각 실행이 이전 실행이 성공한 경우에만
  도는 시간 의존 파이프라인에 유효하다. Parallel Split의 경우 촉발 조건이 그 패턴이 만든 가장 느린
  분기에 기반하게 된다. 달리 말해 각 파이프라인이 가장 느린 분기의 완료를 기다려야 한다. 실패가
  있다면 결과는 더 나빠지는데, 이후 실행이 아예 돌지 않을 것이기 때문이다** (6장,
  pp.183–184).[^konieczny2025]
  - 완화책 — **그런 위험이 있다면 느린 분기를 전용 파이프라인으로 내보내고 그 실행을 Isolated
    Sequencer 패턴에서 제시한 촉발 규칙 중 하나(즉 데이터셋 기반 또는 태스크 기반 의존)에 조건
    거는 것을 고려할 수 있다** (6장, p.184).[^konieczny2025]
- **하드웨어** — **주 잡이 다른 두 잡을 위한 중간 데이터셋을 생성해야 한다면 그 둘은 같은 하드웨어
  기대치를 가져야 한다. 예컨대 하나가 CPU 과중이고 다른 하나가 메모리 과중이면 맞춰진 인프라를 쓸 수
  없을 것이다** (6장, p.184).[^konieczny2025] 해법은 Local Sequencer에서와 같다 — 중간
  데이터셋을 생성해 두고 병렬 잡을 각자의 전용 하드웨어에서 시작한다.
- 재시도가 데이터를 두 번 쓰는 것을 막는 자리가 하나 더 있다 — **여러 실행은 데이터셋 볼륨을 늘릴
  뿐 아니라 중복 같은 데이터 품질 문제도 들여올 수 있다. 다행히 일부 데이터 형식은 재시도된 쓰기에
  대한 보호를 갖는다. Delta Lake가 그렇고 거기서 `txnVersion`과 `txnAppId` 옵션을 활용할 수 있다**
  (6장, p.185).[^konieczny2025]
  - **어떤 이유로든 그 코드를 여러 번 재생해야 한다면 첫 실행에 대해서만 물리적으로 데이터를 쓴다.
    `txnVersion`과 `txnAppId` 속성이 바뀌지 않으므로 이후 모든 실행은 무시된다. 이 쓰기 중복 제거
    기능이 당신 도구에 기본 제공되지 않는다면 4장의 데이터 멱등성 디자인 패턴 중 하나를 여전히 활용할
    수 있다** (6장, p.186).[^konieczny2025]

## Exclusive Choice — 갈래 중 하나만 고른다

- **둘째 팬아웃 패턴도 공통 부모에 기대지만, 병렬 하류 태스크를 돌리는 대신 하나만 고른다** (6장,
  p.186).[^konieczny2025]
- 문제의 실물 — 새 잡 버전을 2024년 1월 1일부터만 실행하되 **백필의 경우 이전 날짜는 여전히 이전
  잡을 돌려야 한다. 전체 실행 이력을 유지하려고 새 파이프라인을 만들지 않고 이 진화를 하고 싶다**
  (6장, p.186).[^konieczny2025]
- 구현은 Parallel Split과 거의 같고 **분기 한 단계 전에서 달라진다** — **마지막 공통 지점 직후에
  하류 태스크를 직접 선언하는 대신, 다음에 어느 경로를 따를지 결정하는 조건 평가자 태스크를 더해야
  한다** (6장, p.186).[^konieczny2025]
  - 제품별로 이름이 다르다 — **Airflow는 전용 태스크 유형인 분기 연산자(branch operator)로 하고,
    Azure Data Factory는 if condition activity로 이 패턴을 구현한다** (6장,
    p.186).[^konieczny2025]
  - 처리 계층에서는 더 단순하다 — **컴퓨트 계층 프로그래밍 언어의 `if-else`나 `switch` 문을
    필연적으로 쓰게 되므로 구현이 훨씬 간단하다** (6장, p.187).[^konieczny2025]
- **복잡성 공장**(complexity factory) — **이 패턴이 낳는 가장 큰 위험은 그 유연성에서 온다.
  원하는 만큼 분기를 더할 수 있고, 분기 수가 많으면 파이프라인 이해도가 꽤 빨리 나빠진다** (6장,
  p.187).[^konieczny2025]
  - **애플리케이션에서 여러 `if-else` 문을 보는 것이 드물지 않으므로 이 실천을 데이터 오케스트레이션
    계층에서 반복하고 싶을 수 있다. 그러나 그 맥락에서 여러 조건은 결국 다시 합쳐지거나 더 쪼개지는
    여러 실행 분기를 뜻한다. 그러면 컴포넌트가 거의 읽을 수 없게 된다** (6장,
    p.187).[^konieczny2025]
  - 임계값 대신 저자가 주는 것은 절차다 — **`if-else` 조건에 대해 합의된 단일 임계값은 없다. 뭔가
    잘못됐는지 알아내려면 최근에 프로젝트에 합류한 상상 속 친구에게 파이프라인을 설명해 볼 수 있다.
    설명이 간결하지 않고 많은 질문과 답으로 이어진다면 파이프라인이 너무 복잡할 수 있다** (6장,
    p.187).[^konieczny2025] 저자는 이것을 **러버덕 디버깅**(rubber duck debugging)의 전용이라고
    상자로 밝힌다.
- **숨은 로직**(hidden logic) — 처리 계층 구현에 걸리는 결과다. **잡이 조건문과 분기를 포함해
  아마도 다른 데이터셋을 생성하거나 다른 출력 데이터 저장과 상호작용한다면, 이는 미래에 문제가 될 수
  있다** (6장, p.188).[^konieczny2025]
  - 이유가 사람 쪽에 있다 — **코드를 쓴 뒤 며칠이나 몇 주는 기억하고 이해하는 일이 잦다. 그러다
    시간이 지나면 더 많은 코드를 쓰고 다른 문제를 풀며 아마 이 특정 잡이 여러 가능한 결과를 갖는다는
    것을 잊을 것이다. 그런 이유로 주어진 파이프라인에 대해 데이터 오케스트레이션 계층 위에서
    Exclusive Choice 패턴을 적용하는 편이 나을 수 있다** (6장, p.188).[^konieczny2025]
  - **처방이 명시적으로 층위를 지정하는 유일한 자리다** — 다른 패턴에서 저자는 두 층위를 나란히
    두지만, 여기서는 오케스트레이션 계층을 권한다. 근거가 기술이 아니라 **코드를 읽는 사람의 망각**이다.
- **무거운 조건** — **데이터 처리 계층에 패턴을 구현하는데 조건이 데이터를 처리해야 한다면, 이것이
  잡의 실행 시간에 영향을 준다는 것을 알아야 한다. 그런 이유로 데이터셋과 상호작용하지 않아 돌리기가
  더 빠른 메타데이터 기반 조건을 선호하는 편이 언제나 낫다** (6장, p.188).[^konieczny2025]
  - **데이터 처리를 피할 수 없다면 이 단계를 최선을 다해 최적화하라. 여러 번 처리하지 않도록,
    그리고 매번 데이터셋 전체를 읽지 않는 증분 처리를 구현할 방법이 있도록 보장하라** (6장,
    p.188).[^konieczny2025]

## Single Runner — 동시 실행을 하나로 묶는다

- 마지막 범주가 하는 일이 다르다 — **지금까지는 개별 흐름과 그 내부·외부 의존을 조직하기만 했다. 이
  단계에서 그것들은 데이터 오케스트레이션 계층 위에 앉은 단순한 정적 자원이다. 마지막 패턴 계열과
  함께 그것들은 데이터 처리 태스크를 돌리는 동적 컴포넌트가 된다** (6장, p.191).[^konieczny2025]
- 문제의 실물 — 5장 **Incremental Sessionizer** 패턴으로 구현한 세션화 파이프라인을 개념 증명
  단계에서는 수동으로 돌려 왔는데, 릴리스 주기에 들어가면서 오케스트레이션이 필요해졌다 (6장,
  p.191).[^konieczny2025]
- **세션화 문제는 증분적, 따라서 순차적 실행을 수반한다. 결과적으로 한 번에 한 파이프라인보다 많이
  돌릴 수 없다. Single Runner 패턴은 주어진 파이프라인의 실행이 언제나 하나만 있도록 보장한다.
  구현은 데이터 흐름의 동시성 수준을 설정하는 것으로 이뤄지고, Apache Airflow와 Azure Data
  Factory에서는 설정 주도 접근 덕에 쉽게 달성된다. 두 오케스트레이터 모두 한 번에 최대 하나의
  발생만 돌리려 할 때 1로 설정할 수 있는 동시성 속성을 지원한다** (6장,
  p.191).[^konieczny2025]
  - 네이티브 지원이 없을 때의 폴백과 그 구멍 — **이전 실행의 완료를 기다리는 Readiness Marker
    패턴을 구현해야 할 수 있다. 여기 작은 함정은 그 해법이 미래 실행의 촉발을 막지는 못한다는 점이다.
    그것들 전부가 데이터를 처리하기 전에 선행 실행의 완료를 기다리게 된다** (6장,
    p.192).[^konieczny2025]
- **백필** — **제한된 동시성은 백필하지 않는 한 아마 문제가 되지 않을 것이다. 그러나 백필한다면
  파이프라인의 순차적 성격 때문에 재처리가 매우 느릴 것이다. 불행히도 할 수 있는 일이 많지 않은데,
  단일 동시성이 완화될 수 없는 비즈니스 요구 사항이기 때문이다. 달리 말해 여러 파이프라인을 병렬로
  돌리면 결과가 틀릴 것이다** (6장, p.192).[^konieczny2025]
  - 유일한 여지 — **할 수 있는 유일한 일은 매번 파이프라인 전체를 정말로 백필해야 하는지 보는
    것이다. 예컨대 데이터 흐름이 데이터 처리와 데이터 적재 단계로 구성되고 설정을 바꾼 뒤 생성된
    데이터셋을 다른 위치에 삽입하기만 하면 된다면 데이터 처리 부분을 피할 수 있다** (6장,
    p.192).[^konieczny2025]
- **지연** — **백필이 Single Runner의 최악 시나리오다. 덜 심각한 경우는 낙오자(straggler)로,
  일부 파이프라인이 다른 것보다 느리게 도는 것이다. 보통 모든 태스크 실행이 30분 걸리는데 최근
  1.5시간으로 늘었다고 하자. 데이터가 점점 지연될 것이다. 그리고 결과는 매우 심각할 수 있다.
  파이프라인이 점점 느려질 뿐 아니라 모든 하류 소비자도 이 추가 지연을 겪는다** (6장,
  p.192).[^konieczny2025]
- Airflow는 두 속성이 짝을 이룬다 — **`max_active_runs`는 얼마나 많은 동시 파이프라인이 허용되는지
  정하고 여기서는 순차 실행에 의존하는 로직이므로 값이 1이어야 한다. `depends_on_past` 속성은 각
  태스크에 적용되어 이전 실행의 성공 시에만 실행을 강제한다. 달리 말해 이전 실행의 태스크 A가
  실패하면 현재 실행의 같은 태스크가 시작하지 않는다** (6장, p.193):[^konieczny2025]

  ```python
  with DAG('visits_trend_generator', max_active_runs=1, default_args={
    'depends_on_past': True,
    # ...
  ```

  - 클러스터 단위로 거는 자리도 있다 — **AWS EMR 서비스는 실행 순서를 제어하는 스텝만 제공하는
    것이 아니라 한 클러스터에서 얼마나 많은 잡이 병렬로 돌 수 있는지 정하는 `StepConcurrencyLevel`
    파라미터도 제공한다** (6장, p.193).[^konieczny2025]
  - **같은 이름의 설정이 제품마다 다르게 동작한다** — **Airflow는 활성 실행이 하나 있으면 새 실행을
    스케줄하지 않지만, Data Factory는 그것들을 만들어 최대 100개 동시 실행을 지원하는 유계 큐에
    저장한다. 서비스는 여전히 다른 실행을 스케줄하지만 큐가 가득 차면 스케줄링 액션이 "Too many
    requests"를 뜻하는 429 오류를 반환한다** (6장, p.193).[^konieczny2025]

## Concurrent Runner — 제약을 푼다

- **Single Runner 패턴의 백필과 지연 문제는 다음 패턴으로 쉽게 다뤄질 수 있다. 해야 할 일은 동시성
  제약을 완화하는 것뿐이다** (6장, p.193).[^konieczny2025]
- 문제의 실물 — 반입 빈도가 보통 30분에서 1시간인데 **가끔 전체 프로세스가 더 오래 걸린다. Single
  Runner 패턴으로 돌고 있으므로 이후 모든 전달이 지연된다. 적재되는 데이터셋들이 서로 의존하지
  않는데 순차 실행이 정말 필요한지 의문이 든다** (6장, p.193).[^konieczny2025] 답은 아니오다 —
  **데이터셋이 독립이므로 어떤 순서로든 반입할 수 있고 따라서 완화된 동시성 제약으로 반입할 수 있다.**
- 구현은 한 줄이지만 저자가 경고를 붙인다 — **동시성을 1보다 높게 정의하는 것으로 이뤄진다. 그러나
  큰 힘에는 큰 책임이 따른다. 인프라 맥락에서 다른 파이프라인을 고려하는 적절한 균형을 잡아야 한다**
  (6장, p.194).[^konieczny2025]
- **자원 기아**(resource starvation) — **멀티테넌트 환경(즉 오케스트레이터가 여러 다른 팀에 의해
  쓰일 때) 작업이라면 특히 그렇다. 한 무리의 파이프라인이 꽤 높은 동시성 수준을 갖고 동시에 백필을
  돌린다면 스케줄러가 다른 파이프라인을 시작할 용량이 없을 수 있다** (6장,
  p.194).[^konieczny2025]
  - 처방 — **이를 다루는 최선의 방법은 작업부하 관리 기능(workload management feature)으로
    파이프라인의 동시성을 제어하는 것이다. 이것은 파이프라인을 돌리는 사용자 그룹에 특정 컴퓨트 용량을
    할당하는 것으로 이뤄진다. 그러면 팀이 허용 동시성을 매우 높게 잡아도 작업부하에 배정된 임계값보다
    많은 용량을 쓸 수 없게 된다** (6장, p.194).[^konieczny2025]
  - 서버리스는 사정이 다르다 — **자원 기아는 서버리스 오케스트레이터에는 문제가 아닐 수 있는데, 꽤
    높은 동시성 수준을 제공하는 일이 잦기 때문이다. 예컨대 집필 시점 AWS Step Functions는 최대
    10,000개의 병렬 자식 워크플로 실행을 허용한다** (6장, p.194).[^konieczny2025]
- **공유 상태** — **공유 상태는 동시 실행을 허용하는 모든 것에 대해 꽤 흔한 함정이다. 파이프라인이
  공유 컴포넌트에서 동작한다면 동시적이고 따라서 비결정적인 실행이 예상치 못한 부작용 때문에 많은
  문제의 원천이 될 수 있다. 한 예는 Dynamic Late Data Integrator 패턴으로, 거기서 동시 실행은
  잘해야 백필을 여러 번 촉발하고 최악의 경우 어떤 실행 날짜에 대해서도 아예 촉발하지 않을 수 있다**
  (6장, p.194).[^konieczny2025]
  - 원서의 상호 참조가 어긋나 있다 — 이 자리(p.194)는 Dynamic Late Data Integrator를 **4장**의
    패턴이라고 쓰지만, 그 패턴은 **3장 "Error Management Design Patterns"의 늦은 데이터 범주**에
    있다(이 KB의 [늦은 데이터 통합](late-data-integration.md)). p.168은 같은 패턴을 장 번호 없이
    참조한다.
- 두 오케스트레이션 패턴이 갈리는 자리를 저자가 요약에서 못 박는다 — **Single Runner의 목표는
  파이프라인의 인스턴스 하나만 언제나 돌게 하는 것이다. 그것은 현재 인스턴스의 로직이 이전 인스턴스의
  출력에 의존하는 증분 데이터 처리에 결정적이다. 반면 Concurrent Runner는 이름대로 여러 인스턴스가
  병렬로 돌게 한다. 격리된 실행을 가속하는(예컨대 백필 동안) 좋은 후보다** (6장,
  p.195).[^konieczny2025]
- 마지막으로 제품 사이의 능력 차 하나 — **이 유연성 수준이 모든 데이터 오케스트레이터에 존재하지는
  않는다. 이전 절에서 소개한 Azure Data Factory에서는 동시성과 트리거 기반 의존을 정의할 수 있지만
  태스크 기반 의존은 정의할 수 없다** (6장, p.195).[^konieczny2025]
