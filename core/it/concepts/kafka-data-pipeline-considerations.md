하나의 질문: **여러 시스템을 잇는 데이터 파이프라인을 설계할 때 무엇을 따져야 하고,
그 각각에 대해 카프카는 무엇을 해 주는가.**

이 장의 고려사항들은 **카프카에 고유한 것이 아니라 일반적인 데이터 통합 문제**라고
책이 직접 못박는다 — 그 위에서 카프카가 왜 데이터 통합 유스케이스에 잘 맞는지를
보인다 (9장, p.204).[^shapira2021]

## 파이프라인의 두 모양과 카프카의 자리

- 사람들이 아파치 카프카로 데이터 파이프라인을 짓는다고 할 때 가리키는 유스케이스는
  대개 둘이다 — **① 아파치 카프카가 두 끝점 중 하나인 파이프라인**(예: 카프카에서 S3로,
  또는 몽고DB에서 카프카로) 과 **② 서로 다른 두 시스템 사이의 파이프라인이되 카프카를
  중개자로 쓰는 것**(예: 트위터에서 엘라스틱서치로 보내되 먼저 트위터에서 카프카로,
  다시 카프카에서 엘라스틱서치로) 이다 (9장, p.203).[^shapira2021]
- **카프카 커넥트(Kafka Connect)는 0.9 버전에서 아파치 카프카에 추가**됐다. 링크드인과
  다른 큰 조직에서 카프카가 두 유스케이스 모두에 쓰이는 것을 본 뒤였고, **모든 조직이
  카프카를 데이터 파이프라인에 통합하며 똑같은 문제를 처음부터 풀게 하는 대신 그 문제
  일부를 푸는 API를 카프카에 넣기로** 한 결정이었다 (9장, p.203).[^shapira2021]
- **카프카가 데이터 파이프라인에 주는 주된 가치는 파이프라인의 여러 단계 사이에서
  아주 크고 신뢰성 있는 버퍼 노릇을 할 수 있다는 것**이다. **이것이 파이프라인 안의
  데이터 프로듀서와 컨슈머를 효과적으로 분리(decouple)** 하고, **적시성과 가용성 요구가
  서로 다른 여러 대상 애플리케이션·시스템이 같은 데이터를 원천에서 쓸 수 있게** 한다.
  **이 분리에 신뢰성·보안·효율성이 더해져 카프카를 대부분의 데이터 파이프라인에 잘
  맞는 선택**으로 만든다 (9장, p.203).[^shapira2021]
- 어떤 조직은 카프카를 파이프라인의 **끝점**으로 생각해 "카프카에서 엘라스틱으로
  데이터를 어떻게 가져오나" 같은 질문을 한다. 유효한 질문이지만 저자들은 **카프카가
  아닌 끝점이 최소 둘(어쩌면 여럿) 포함되는 더 큰 맥락**에서 논의를 시작하자고 하며,
  데이터 통합 문제에 부딪힌 사람은 **눈앞의 끝점만이 아니라 큰 그림을 보라**고 권한다
  (9장, p.204, "Putting Data Integration in Context" 박스):[^shapira2021]

  > Focusing on short-term integrations is how you end up with a complex and
  > expensive-to-maintain data integration mess.

## 적시성

- **어떤 시스템은 데이터가 하루 한 번 대량으로 도착하기를 기대하고, 어떤 것은 생성 후
  몇 밀리초 안에 도착하기를 기대**하며 **대부분의 파이프라인은 그 사이 어딘가**다.
  **좋은 데이터 통합 시스템은 파이프라인마다 다른 적시성(timeliness) 요구를 지원하고,
  업무 요구가 바뀔 때 시간표 사이의 이전을 쉽게** 만든다 (9장, p.204).[^shapira2021]
- 카프카가 그 범위를 덮는 방식 — **확장 가능하고 신뢰성 있는 저장을 갖춘 스트리밍 데이터
  플랫폼이므로 준실시간 파이프라인부터 일 배치까지 무엇이든 지원**한다. **프로듀서는
  필요한 만큼 자주 또는 드물게 카프카에 쓸 수 있고, 컨슈머도 최신 이벤트를 도착하는 대로
  읽어 전달하거나 배치로 일할 수 있다** — 예컨대 한 시간에 한 번 돌아 카프카에 접속해
  지난 한 시간 동안 쌓인 이벤트를 읽는 식이다 (9장, pp.204–205).[^shapira2021]
- 이 맥락에서 카프카를 보는 유용한 방식은 **프로듀서와 컨슈머 사이의 시간 민감도 요구를
  분리하는 거대한 버퍼**로 보는 것이다. **프로듀서는 실시간으로 이벤트를 쓰고 컨슈머는
  이벤트를 배치로 처리하거나 그 반대일 수도** 있다. 그 덕에 **배압(back pressure)을
  적용하는 것도 자명해진다 — 소비 속도가 전적으로 컨슈머에 의해 결정되므로 카프카 자체가
  (필요할 때 ack를 지연시켜) 프로듀서에 배압을 건다** (9장, p.205).[^shapira2021]
  `acks`가 언제 돌아오는지는
  [프로듀서 설정](../concepts/kafka-producer-configuration.md)에 있다.

## 신뢰성

- 목표는 **단일 실패 지점을 피하고 온갖 종류의 장애 이벤트에서 빠르고 자동적으로 복구**
  하는 것이다. **데이터 파이프라인은 업무에 결정적인 시스템으로 데이터가 도착하는 통로인
  경우가 많아 몇 초를 넘는 실패가 크게 파괴적일 수 있고, 특히 적시성 요구가 밀리초 쪽에
  있을 때 그렇다** (9장, p.205).[^shapira2021]
- 또 하나의 신뢰성 고려는 **전달 보장**이다 — **어떤 시스템은 데이터 유실을 감당할 수
  있지만 대개는 최소 한 번(at-least-once) 전달을 요구**한다. 이는 **원천 시스템의 모든
  이벤트가 목적지에 도달하되 재시도가 때때로 중복을 만든다**는 뜻이다. **정확히 한 번
  (exactly-once) 전달 요구도 흔하다** — **원천 시스템의 모든 이벤트가 유실도 중복도
  없이 목적지에 도달**하는 것이다 (9장, p.205).[^shapira2021] 보장의 정의와 그 경계는
  [카프카의 신뢰성 보장](../concepts/kafka-reliability-guarantees.md)에 있다.
- 카프카가 어디까지 주는가 — **카프카는 그 자체로 최소 한 번을 제공하고, 트랜잭션 모델이나
  유니크 키를 가진 외부 데이터 저장소와 결합하면 정확히 한 번을 제공**한다. **끝점의
  다수가 정확히 한 번 전달에 맞는 의미론을 제공하는 데이터 저장소이므로 카프카 기반
  파이프라인은 종종 정확히 한 번으로 구현될 수 있다.** 특기할 것은 **커넥트 API가
  오프셋을 다루면서 외부 시스템과 통합하는 API를 제공함으로써 커넥터가 종단 간 정확히
  한 번 파이프라인을 만들기 쉽게 한다**는 점이고, **실제로 가용한 오픈소스 커넥터 다수가
  정확히 한 번 전달을 지원**한다 (9장, p.205).[^shapira2021] 오프셋을 커넥트가 어떻게
  들고 있는지는
  [카프카 커넥트 내부 구조](../concepts/kafka-connect-internals.md)의 오프셋 관리 절에
  있다.

## 높고 변하는 처리량

- **현대 데이터 시스템이 흔히 요구하는 매우 높은 처리량으로 확장 가능해야 하고, 더
  중요하게는 처리량이 갑자기 증가할 때 적응할 수 있어야** 한다 (9장, p.205).[^shapira2021]
- **카프카가 프로듀서와 컨슈머 사이에서 버퍼 노릇을 하므로 컨슈머 처리량을 프로듀서
  처리량에 결합할 필요가 더 이상 없다.** **복잡한 배압 메커니즘을 구현할 필요도
  없다 — 프로듀서 처리량이 컨슈머의 것을 넘으면 컨슈머가 따라잡을 때까지 데이터가
  카프카에 쌓이기 때문**이다. **컨슈머나 프로듀서를 독립적으로 추가해 확장하는 카프카의
  능력이 파이프라인의 어느 쪽이든 동적·독립적으로 확장해 변하는 요구에 맞추게** 해 준다
  (9장, p.205).[^shapira2021]
- **카프카는 고처리량 분산 시스템으로 적당한 클러스터에서도 초당 수백 메가바이트를 처리할
  수 있으므로 파이프라인이 수요만큼 확장되지 못할 걱정은 없다.** 그에 더해 **커넥트 API는
  작업의 병렬화에 집중하며, 시스템 요구에 따라 단일 노드에서도 확장해서도 할 수 있다**
  (9장, p.206).[^shapira2021] 이 병렬화가 실제로 어떻게 갈라지는지는
  [카프카 커넥트 내부 구조](../concepts/kafka-connect-internals.md)의 커넥터와 태스크
  절에 있다.
- **카프카는 여러 유형의 압축도 지원해 처리량 요구가 커질 때 사용자와 관리자가 네트워크·
  저장 자원의 사용을 통제**할 수 있게 한다 (9장, p.206).[^shapira2021]

## 데이터 형식

- **데이터 파이프라인에서 가장 중요한 고려사항 중 하나가 서로 다른 데이터 형식과 데이터
  타입의 조정(reconciling)** 이다. **지원되는 데이터 타입은 데이터베이스와 저장 시스템마다
  다르다.** 실제로 겪는 조합의 예 — **XML과 관계형 데이터를 카프카에 적재하고, 카프카
  안에서는 에이브로를 쓰고, 엘라스틱서치에 쓸 때는 JSON으로, HDFS에 쓸 때는 파케이로,
  S3에 쓸 때는 CSV로 변환**해야 하는 식이다 (9장, p.206).[^shapira2021]
- **카프카 자체와 커넥트 API는 데이터 형식에 관해서는 완전히 불가지론적(agnostic)** 이다.
  **프로듀서와 컨슈머는 어떤 시리얼라이저든 써서 자기에게 맞는 어떤 형식으로도 데이터를
  표현할 수 있다.** **카프카 커넥트는 데이터 타입과 스키마를 포함하는 자체 인메모리 객체를
  갖지만 플러그인 가능한 컨버터(converter)를 허용해 이 레코드를 어떤 형식으로도 저장**할
  수 있다. **즉 카프카에 어떤 데이터 형식을 쓰든 그것이 커넥터 선택을 제한하지 않는다**
  (9장, p.206).[^shapira2021] 클라이언트 쪽 직렬화 선택지는
  [카프카 직렬화와 스키마 레지스트리](../concepts/kafka-serialization-and-schema-registry.md)에
  있고, 커넥트 쪽 컨버터의 위치는
  [카프카 커넥트 내부 구조](../concepts/kafka-connect-internals.md)에 있다.
- **많은 소스와 싱크가 스키마를 갖는다** — **데이터와 함께 소스에서 스키마를 읽어 저장해
  두었다가 싱크 데이터베이스에서 호환성 검증에 쓰거나 아예 스키마를 갱신하는 데 쓸 수**
  있다. **고전적인 예가 MySQL에서 스노우플레이크(Snowflake)로 가는 파이프라인**이다 —
  **누군가 MySQL에 컬럼을 추가하면 좋은 파이프라인은 새 데이터를 적재할 때 스노우플레이크
  쪽에도 그 컬럼이 추가되게** 한다 (9장, p.206).[^shapira2021]
- 카프카에서 나가는 쪽 — **외부 시스템으로 데이터를 쓸 때는 싱크 커넥터가 외부 시스템에
  쓰이는 형식을 책임진다.** **어떤 커넥터는 이 형식을 플러그인 가능하게** 하는데,
  **S3 커넥터가 에이브로와 파케이 중 선택하게 하는 것**이 그 예다 (9장,
  p.206).[^shapira2021]
- 형식만으로는 부족하다 — **범용 데이터 통합 프레임워크는 여러 소스와 싱크 사이의 동작
  차이도 다뤄야** 한다. **Syslog는 데이터를 밀어내는(push) 소스인 반면 관계형 데이터베이스는
  프레임워크가 데이터를 당겨(pull) 와야** 하고, **HDFS는 추가 전용(append-only)이라 쓰기만
  가능한 반면 대부분의 시스템은 데이터를 추가하는 것과 기존 레코드를 갱신하는 것 둘 다
  허용**한다 (9장, p.206).[^shapira2021]

## 변환 — ETL과 ELT

- **변환은 다른 요구사항들보다 논쟁적**이며, **데이터 파이프라인을 짓는 접근은 일반적으로
  둘 — ETL과 ELT**다. 두 낱말의 정의는 원문 그대로 (9장, p.207):[^shapira2021]

  > ETL, which stands for *Extract-Transform-Load*, means that the data pipeline is
  > responsible for making modifications to the data as it passes through.
  >
  > ELT stands for *Extract-Load-Transform* and means that the data pipeline does only
  > minimal transformation (mostly around data type conversion), with the goal of making
  > sure the data that arrives at the target is as similar as possible to the source data.

  - 정의 자체는 이 KB의 웨어하우스 쪽 서술과 **같다** — 변환을 적재 앞에 두면 ETL,
    뒤에 두면 ELT다([EDW](../concepts/enterprise-data-warehouse.md)의 "웨어하우스가 생긴
    시점과 이유" 절, [ETL 34 서브시스템](../concepts/etl-subsystems.md)의 "ETL이라는 말이
    가리키는 범위가 넓어졌다" 절). **다른 것은 판단의 근거다** — 저쪽은 웨어하우스 적재의
    순서 문제로 보고, 이 책은 **파이프라인이 하류에서 무엇을 지워 버리는가**의 문제로 본다.
- ETL 쪽의 계산 — **데이터를 저장하고 수정하고 다시 저장할 필요가 없으므로 시간과 저장
  공간을 아낀다는 이점이 있다고 여겨진다(perceived benefit).** **변환에 따라 이 이점이
  실제일 때도 있지만, 때로는 계산과 저장의 부담을 데이터 파이프라인 자체로 옮기는 것일
  뿐이라 바람직할 수도 아닐 수도** 있다 (9장, p.207).[^shapira2021]
- **ETL의 주된 단점은 파이프라인에서 데이터에 일어난 변환이 파이프라인 하류에서 데이터를
  더 처리하려는 사람들의 손을 묶는다는 것**이다. **몽고DB와 MySQL 사이의 파이프라인을
  만든 사람이 특정 이벤트를 걸러내거나 레코드에서 필드를 빼기로 결정했다면, MySQL의
  데이터에 접근하는 모든 사용자와 애플리케이션은 부분 데이터만 갖게 된다. 누락된 필드에
  접근해야 하면 파이프라인을 다시 지어야 하고 (있다고 가정할 때) 이력 데이터도 재처리가
  필요**하다 (9장, p.207).[^shapira2021]
- ELT 쪽의 계산 — **타깃 시스템이 "원시 데이터(raw data)"를 수집하고 필요한 처리는 전부
  타깃 시스템에서 한다.** **이점은 타깃 시스템의 사용자에게 최대의 유연성을 준다는 것**이며
  (**모든 데이터에 접근할 수 있으므로**), **모든 데이터 처리가 한 시스템에 국한되고
  파이프라인과 별도 애플리케이션으로 쪼개지지 않으므로 문제 해결도 더 쉬운 경향**이 있다.
  **단점은 변환이 타깃 시스템의 CPU와 저장 자원을 쓴다는 것**이며, **어떤 경우 이 시스템들은
  비싸서 가능하면 계산을 그 시스템 밖으로 옮기려는 강한 동기가 생긴다** (9장,
  p.207).[^shapira2021]
  - ELT의 이점 서술은 [데이터 레이크](../concepts/data-lake.md)의 스시 원칙("원시 데이터가
    낫다")과 **같은 주장**이다. 이 책이 더한 것은 **그 반대쪽 비용 항** — 타깃의 CPU·저장을
    쓰고, 그 시스템이 비싸면 계산을 밖으로 빼려는 동기가 생긴다는 것이다. 스시 원칙 쪽
    서술에는 이 비용 항이 없다.
- **카프카 커넥트는 단일 메시지 변환(single message transformation, SMT) 기능을 포함**해
  **레코드가 소스에서 카프카로, 또는 카프카에서 타깃으로 복사되는 동안 레코드를 변환**한다.
  **다른 토픽으로 메시지 라우팅, 메시지 필터링, 데이터 타입 변경, 특정 필드 가리기(redacting)
  등**이 여기 들어간다. **조인과 집계를 수반하는 더 복잡한 변환은 보통 카프카 스트림즈로
  하며 별도의 장에서 다룬다** (9장, p.207).[^shapira2021] 상세는
  [단일 메시지 변환(SMT)](../concepts/kafka-single-message-transformations.md).
- 카프카로 ETL 시스템을 지을 때의 지침 한 덩어리 (9장, p.208, 경고 박스):[^shapira2021]
  **카프카는 일대다 파이프라인을 짓게 해 준다 — 원천 데이터가 카프카에 한 번 쓰이고 여러
  애플리케이션이 소비해 여러 타깃 시스템에 쓴다.** **어느 정도의 전처리와 정리는 예상되는
  일이다** — **타임스탬프와 데이터 타입의 표준화, 계보(lineage) 추가, 어쩌면 개인 정보
  제거처럼 데이터의 모든 컨슈머에게 이로울 변환들**이다. **그러나 반입 시점에 데이터를
  조급하게 정리하고 최적화하지는 마라 — 다른 곳에서는 덜 정제된 형태가 필요할 수도 있다.**
  - 이 지침은 KB 안에서 **중간 입장**에 해당한다. Kimball은 가치가 적재 **전** 정제·통합에서
    나온다고 보고([ETL 34 서브시스템](../concepts/etl-subsystems.md)), 스시 원칙은 원시
    보존을 우선한다([데이터 레이크](../concepts/data-lake.md)). 이 책은 **모든 컨슈머에게
    이로운 변환만 앞에 두고 나머지는 뒤로 미루라**는 선을 긋는다.

## 보안

- 데이터 파이프라인 관점에서 주된 보안 관심사 다섯 (9장, p.208):[^shapira2021]
  - **카프카로 반입되는 데이터에 누가 접근하는가?**
  - **파이프를 지나는 데이터가 암호화되게 할 수 있는가?** 주로 **데이터센터 경계를 넘는
    파이프라인의 관심사**다.
  - **파이프라인을 수정하도록 허용된 사람은 누구인가?**
  - **데이터 파이프라인이 접근 통제된 위치에서 읽거나 써야 한다면 제대로 인증할 수 있는가?**
  - **PII(개인 식별 정보) 취급이 저장·접근·사용에 관한 법과 규제를 준수하는가?**
- 카프카가 주는 것 — **소스에서 카프카로, 카프카에서 싱크로 파이프될 때 데이터를 전선에서
  암호화**할 수 있고, **(SASL을 통한) 인증과 인가를 지원**하므로 **토픽에 민감 정보가 있으면
  인가받지 않은 누군가가 덜 안전한 시스템으로 그것을 파이프할 수 없게** 할 수 있다.
  **인가·비인가 접근을 추적하는 감사 로그**도 제공하며, **코딩을 조금 더하면 각 토픽의
  이벤트가 어디서 왔고 누가 수정했는지 추적해 레코드마다 전체 계보를 제공**할 수도 있다
  (9장, p.208).[^shapira2021]
- 커넥트 쪽으로 넘어오는 문제 — **카프카 커넥트와 그 커넥터들은 외부 데이터 시스템에
  연결하고 인증할 수 있어야 하며, 커넥터 설정은 외부 데이터 시스템 인증용 자격 증명을
  포함**한다 (9장, p.208).[^shapira2021]
  - **요즘은 설정 파일에 자격 증명을 저장하는 것이 권장되지 않는다** — **설정 파일을 각별히
    다루고 접근을 제한해야 한다는 뜻이 되기 때문**이다. **흔한 해법은 해시코프 볼트
    (HashiCorp Vault) 같은 외부 비밀 관리 시스템을 쓰는 것**이고, **카프카 커넥트는 외부
    비밀 설정(external secret configuration)을 지원**한다. **아파치 카프카 자체는 플러그인
    가능한 외부 설정 제공자(config provider)를 도입할 수 있게 하는 프레임워크와 파일에서
    설정을 읽는 예제 제공자만 포함**하며, **볼트·AWS·애저와 통합되는 커뮤니티 개발 외부
    설정 제공자들이 따로** 있다 (9장, pp.208–209).[^shapira2021]
- **카프카 보안 자체는 이 책 11장에서 상세히 다룬다** (9장, p.208).[^shapira2021] 이 KB에는
  아직 그 장이 들어와 있지 않다 — **미해소**.

## 장애 처리

- **모든 데이터가 항상 완벽할 것이라 가정하는 것은 위험하다.** **장애 처리를 미리 계획하는
  것이 중요**하며 던져야 할 질문들이 있다 — **잘못된 레코드가 애초에 파이프라인에 들어오는
  것을 막을 수 있는가? 파싱할 수 없는 레코드에서 복구할 수 있는가? 나쁜 레코드가 (아마
  사람에 의해) 고쳐져 재처리될 수 있는가? 나쁜 이벤트가 정상 이벤트와 똑같이 생겨서 며칠
  뒤에야 문제를 발견하면 어떻게 되는가?** (9장, p.209).[^shapira2021]
- 카프카가 주는 여유 — **카프카는 모든 이벤트를 오랜 기간 저장하도록 설정될 수 있으므로
  필요할 때 시간을 되돌려 오류에서 복구하는 것이 가능**하다. **타깃 시스템으로 간 것이
  유실됐다면 카프카에 저장된 이벤트를 그 시스템으로 재생(replay)하는 것도 가능**하다
  (9장, p.209).[^shapira2021] 보존 기간을 정하는 기준은
  [카프카 브로커 설정](../concepts/kafka-broker-configuration.md)에 있다.
  - 같은 질문을 웨어하우스 백룸에서 다루는 쪽이
    [ETL 34 서브시스템](../concepts/etl-subsystems.md)의 품질 스크린(4)이다 — 거기서는
    실패한 레코드를 중단·격리(suspense)·태깅 중 하나로 처리하며 **태깅 후 통과**를 최선으로
    본다. 커넥트가 제공하는 대응물이 데드 레터 큐다
    ([단일 메시지 변환(SMT)](../concepts/kafka-single-message-transformations.md)).
    나쁜 데이터를 고치지 말고 보존하라는 또 다른 처방은
    [데이터 웨어하우스의 데이터 품질 관리](../concepts/data-quality-management.md)의
    "나쁜 데이터의 가치"에 있다.

## 결합과 민첩성

- **데이터 파이프라인 구현의 바람직한 특성은 데이터 소스와 데이터 타깃을 분리(decouple)
  하는 것**이다. **우연한 결합(accidental coupling)이 생기는 경로는 여럿**이다 (9장,
  p.209).[^shapira2021]
- **임시방편 파이프라인(ad hoc pipelines)** — **어떤 회사는 연결하려는 애플리케이션 쌍마다
  커스텀 파이프라인을 만든다.** **로그스태시로 로그를 엘라스틱서치에 덤프하고, 플룸으로
  로그를 HDFS에 덤프하고, 오라클 골든게이트로 오라클에서 HDFS로 데이터를 가져오고,
  인포매티카로 MySQL과 XML에서 오라클로 가져오는** 식이다. **이것은 데이터 파이프라인을
  특정 끝점에 밀결합시키고 배포·유지·모니터링에 상당한 노력이 드는 통합 지점의 난장판을
  만든다.** 게다가 **회사가 채택하는 모든 새 시스템이 추가 파이프라인 구축을 요구하므로
  새 기술을 채택하는 비용이 올라가고 혁신이 억제**된다 (9장, p.209).[^shapira2021]
  같은 N×M 문제를 메시징 계층에서 서술한 쪽이
  [발행/구독 메시징](../concepts/publish-subscribe-messaging.md)이고, 그 문제가 카프카를
  낳은 경위는 [카프카의 기원](../concepts/kafka-origin-at-linkedin.md)에 있다.
- **메타데이터 유실(loss of metadata)** — **파이프라인이 스키마 메타데이터를 보존하지 않고
  스키마 진화를 허용하지 않으면 소스에서 데이터를 만드는 소프트웨어와 목적지에서 그것을
  쓰는 소프트웨어를 밀결합**시키게 된다. **스키마 정보가 없으면 양쪽 소프트웨어 제품이
  데이터를 파싱하고 해석하는 법에 관한 정보를 포함해야** 한다. **오라클에서 HDFS로 데이터가
  흐르는데 DBA가 오라클에 새 필드를 추가하면서 스키마 정보를 보존하지 않고 스키마 진화를
  허용하지 않으면, HDFS에서 데이터를 읽는 모든 앱이 깨지거나 모든 개발자가 동시에
  애플리케이션을 업그레이드해야 한다 — 어느 쪽도 민첩하지 않다.** **파이프라인이 스키마
  진화를 지원하면 각 팀은 자기 속도로 애플리케이션을 수정할 수 있고 나중에 일이 깨질 걱정을
  하지 않아도** 된다 (9장, p.209).[^shapira2021] 스키마 진화가 실제로 어떻게 성립하는지는
  [카프카 직렬화와 스키마 레지스트리](../concepts/kafka-serialization-and-schema-registry.md)의
  에이브로 절에 있다.
- **극단적 처리(extreme processing)** — **어떤 처리는 데이터 파이프라인에 본래적**이다.
  **결국 서로 다른 데이터 형식이 말이 되고 서로 다른 유스케이스가 지원되는 서로 다른 시스템
  사이에서 데이터를 옮기는 일이기 때문**이다. **그러나 너무 많은 처리는 어떤 필드를 보존할지,
  데이터를 어떻게 집계할지 같은 결정에 모든 하류 시스템을 묶는다.** 그러면 **하류 애플리케이션의
  요구가 바뀔 때마다 파이프라인이 끊임없이 바뀌게 되는데 이는 민첩하지도, 효율적이지도,
  안전하지도 않다.** **더 민첩한 방법은 가능한 한 많은 원시 데이터를 보존하고 카프카 스트림즈
  앱을 포함한 하류 앱이 데이터 처리와 집계에 관해 자기 결정을 내리게 하는 것**이다 (9장,
  p.210).[^shapira2021]
