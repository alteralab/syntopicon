하나의 질문: **DSL로 정의한 토폴로지가 실행 시점에 무엇이 되고 어떻게 나뉘어 도는가.**

## 버전 조건

> **버전 조건**: Kafka 2.8 기준. 이 장은 아파치 카프카 2.8 시점의 API와 의미론을
> 기록한다 (14장, p.382).[^shapira2021]

## 토폴로지 짓기

- **모든 스트림즈 애플리케이션은 하나의 토폴로지를 구현하고 실행한다. 토폴로지(다른 스트림
  처리 프레임워크에서는 DAG, 유향 비순환 그래프라고도 불린다)는 모든 이벤트가 입력에서
  출력까지 거쳐 가는 연산과 전이의 집합**이다 (14장, p.410).[^shapira2021]
- **아무리 단순한 앱이라도 사소하지 않은 토폴로지를 갖는다. 토폴로지는 프로세서들로
  이뤄지며 그것이 토폴로지 그래프의 노드다. 대부분의 프로세서는 필터·맵·집계 같은 데이터에
  대한 연산을 구현한다. 토픽에서 데이터를 소비해 넘겨주는 소스 프로세서(source processor)와,
  앞선 프로세서에서 데이터를 받아 토픽으로 생산하는 싱크 프로세서(sink processor)도 있다.
  토폴로지는 언제나 하나 이상의 소스 프로세서로 시작해 하나 이상의 싱크 프로세서로 끝난다**
  (14장, pp.410–411).[^shapira2021]
  - 스트림 프로세서라는 낱말이 처음 등장하는 자리는 스트림 처리 개념 쪽이다 — **처리
    토폴로지는 하나 이상의 소스 스트림에서 시작해 이벤트 스트림으로 연결된 스트림
    프로세서의 그래프를 거쳐 하나 이상의 싱크 스트림에 결과가 쓰일 때까지 간다. 각 스트림
    프로세서는 이벤트를 변환하기 위해 이벤트 스트림에 적용되는 계산 단계**다 (14장,
    pp.385–386).[^shapira2021]

## 토폴로지 최적화하기

- **기본적으로 카프카 스트림즈는 DSL API로 지어진 애플리케이션을 각 DSL 메서드를 저수준
  등가물로 독립적으로 매핑해 실행한다. 각 DSL 메서드를 독립적으로 평가함으로써 전체 결과
  토폴로지를 최적화할 기회가 놓쳐졌다** (14장, p.411).[^shapira2021]
- 카프카 스트림즈 애플리케이션의 실행은 **3단계 프로세스**다 (14장,
  p.411):[^shapira2021]
  1. **`KStream`과 `KTable` 객체를 만들고 그것들에 필터·조인 같은 DSL 연산을 수행함으로써
     논리적 토폴로지가 정의된다.**
  2. **`StreamsBuilder.build()`가 논리적 토폴로지로부터 물리적 토폴로지를 생성한다.**
  3. **`KafkaStreams.start()`가 토폴로지를 실행한다 — 여기가 데이터가 소비·처리·생산되는
     자리다.**
- **논리적 정의에서 물리적 토폴로지가 생성되는 둘째 단계가 계획 전체에 대한 최적화가
  적용될 수 있는 자리**다 (14장, p.411).[^shapira2021]
- 버전 조건: Kafka 2.8 기준 — **현재 아파치 카프카는 대부분 가능한 곳에서 토픽을 재사용하는
  정도의 최적화 몇 가지만 포함한다. `StreamsConfig.TOPOLOGY_OPTIMIZATION`을
  `StreamsConfig.OPTIMIZE`로 설정하고 `build(props)`를 호출해 활성화할 수 있다. 설정을
  넘기지 않고 `build()`만 호출하면 최적화는 여전히 비활성**이다 (14장,
  p.411).[^shapira2021]
- 권고 — **최적화를 켠 경우와 끈 경우로 애플리케이션을 테스트해 실행 시간과 카프카에 쓰인
  데이터 양을 비교하고, 물론 알려진 여러 시나리오에서 결과가 동일한지 검증하라** (14장,
  p.411).[^shapira2021]

## 토폴로지 테스트하기

- **카프카 스트림즈 애플리케이션의 주된 테스트 도구는 `TopologyTestDriver`** 다. **이
  테스트들은 평범한 단위 테스트처럼 보인다 — 입력 데이터를 정의하고 목(mock) 입력 토픽에
  생산한 뒤 테스트 드라이버로 토폴로지를 돌리고 목 출력 토픽에서 결과를 읽어 기대값과
  비교해 검증**한다 (14장, p.411).[^shapira2021]
  - 버전 조건: Kafka 1.1.0 이상(도입)·2.4 이상(권장) — **1.1.0에서 도입된 이래 API가 크게
    개선됐고 2.4 이후 버전은 편리하고 쓰기 쉽다** (14장, p.411).[^shapira2021]
- 한계도 명시된다 — **`TopologyTestDriver`가 카프카 스트림즈 캐싱 동작(이 책에서 논의하지
  않는 최적화이며 이 프레임워크가 시뮬레이트하는 상태 저장소 자체와는 전혀 무관하다)을
  시뮬레이트하지 않으므로 그것이 탐지하지 못하는 오류 부류 전체가 있다** (14장,
  p.411).[^shapira2021]
- 통합 테스트 쪽에는 **인기 있는 프레임워크가 둘 — `EmbeddedKafkaCluster`와
  Testcontainers**다. **전자는 테스트를 돌리는 JVM 안에서 카프카 브로커를 돌리고, 후자는
  카프카 브로커(그리고 테스트에 필요한 다른 여러 구성 요소)를 담은 도커 컨테이너를
  돌린다.** **Testcontainers가 권장**되는데 **도커를 씀으로써 카프카와 그 의존성·자원
  사용을 테스트 대상 애플리케이션으로부터 완전히 격리**하기 때문이다 (14장,
  p.411).[^shapira2021]

## 토폴로지 규모 확장하기

- **카프카 스트림즈는 애플리케이션 한 인스턴스 안에서 여러 실행 스레드를 허용하고 분산된
  인스턴스 사이의 부하 분산을 지원함으로써 확장한다. 여러 스레드로 한 머신에서 돌리거나
  여러 머신에서 돌릴 수 있고, 어느 쪽이든 애플리케이션의 모든 활성 스레드가 데이터 처리에
  드는 일을 나눠 갖는다** (14장, p.412).[^shapira2021]
- **스트림즈 엔진은 토폴로지를 태스크(task)로 쪼개 실행을 병렬화한다. 태스크의 수는 스트림즈
  엔진이 정하며 애플리케이션이 처리하는 토픽의 파티션 수에 달려 있다. 각 태스크는 파티션의
  부분집합을 책임진다 — 태스크는 그 파티션들을 구독해 이벤트를 소비하고, 소비하는 이벤트마다
  이 파티션에 적용되는 모든 처리 단계를 순서대로 실행한 뒤 결국 결과를 싱크에 쓴다. 태스크는
  각각이 다른 태스크와 독립적으로 실행될 수 있으므로 카프카 스트림즈에서 병렬성의 기본
  단위**다 (14장, p.412).[^shapira2021]
- 스레드와 인스턴스의 관계 — **애플리케이션 개발자가 각 인스턴스가 실행할 스레드 수를 고를
  수 있다. 스레드가 여럿이면 각 스레드가 애플리케이션이 만드는 태스크의 부분집합을
  실행한다. 여러 서버에서 여러 인스턴스가 돌면 서버마다 각 스레드에 대해 다른 태스크가
  실행된다.** 그래서 **스트리밍 애플리케이션은 처리 중인 토픽의 파티션 수만큼 태스크를
  갖는다. 더 빨리 처리하고 싶으면 스레드를 더하고, 서버 자원이 모자라면 다른 서버에서
  애플리케이션 인스턴스를 하나 더 시작한다. 카프카가 작업을 자동으로 조율한다** (14장,
  pp.413–414).[^shapira2021] 파티션 수가 병렬성의 상한이 되는 같은 규칙은
  [토픽과 파티션](../concepts/topics-and-partitions.md)과
  [컨슈머 그룹과 리밸런스](../concepts/kafka-consumer-groups-and-rebalance.md).
- **때로 처리 단계가 여러 파티션의 입력을 요구해 태스크 사이에 의존이 생길 수 있다.** 조인이
  그렇다 — **결과를 내려면 각 스트림의 파티션에서 데이터가 필요하다. 카프카 스트림즈는 한
  조인에 필요한 모든 파티션을 같은 태스크에 배정해 그 태스크가 관련 파티션 전부에서 소비해
  독립적으로 조인을 수행할 수 있게** 한다 (14장, p.413).[^shapira2021]
  - 버전 조건: Kafka 2.8 기준 — **그래서 카프카 스트림즈는 현재 조인 연산에 참여하는 모든
    토픽이 같은 수의 파티션을 갖고 조인 키에 기반해 파티션돼 있을 것을 요구**한다 (14장,
    p.413).[^shapira2021]
- 리파티셔닝이 만드는 의존은 다르다 — **클릭 스트림 예제에서 모든 이벤트는 사용자 ID로
  키가 붙어 있는데, 페이지별 혹은 우편번호별 통계를 만들고 싶다면 카프카 스트림즈가
  우편번호로 데이터를 리파티션하고 새 파티션으로 집계를 돌린다. 태스크 1이 파티션 1의
  데이터를 처리하다 데이터를 리파티션하는 프로세서(`groupBy` 연산)에 도달하면 셔플 —
  다른 태스크로 이벤트를 보내는 일 — 이 필요하다** (14장, p.414).[^shapira2021]
- 카프카 스트림즈가 다른 프레임워크와 갈리는 지점이 여기다 — **다른 스트림 프로세서
  프레임워크와 달리 카프카 스트림즈는 새 키와 파티션을 가진 새 토픽에 이벤트를 씀으로써
  리파티션한다. 그러면 또 다른 태스크 집합이 새 토픽에서 이벤트를 읽어 처리를 이어 간다.
  리파티셔닝 단계는 토폴로지를 각자의 태스크를 갖는 두 개의 하위 토폴로지로 쪼갠다. 둘째
  태스크 집합은 첫 하위 토폴로지의 결과를 처리하므로 첫째에 의존하지만, 첫째가 자기 속도로
  토픽에 데이터를 쓰고 둘째가 그 토픽에서 소비해 자기 속도로 이벤트를 처리하므로 여전히
  독립적으로 병렬 실행될 수 있다. 태스크 사이에 통신도 공유 자원도 없고 같은 스레드나
  서버에서 돌 필요도 없다. 이것이 카프카가 하는 더 유용한 일 중 하나다 — 파이프라인의 서로
  다른 부분 사이의 의존을 줄이는 것**이다 (14장, pp.414–415).[^shapira2021]
  - 이 두 단계 구조를 패턴 이름으로 부른 자리가
    [스트림 처리 설계 패턴](../concepts/stream-processing-design-patterns.md)의 다단계 처리다.

## 장애 견디기

- **확장을 가능하게 한 같은 모델이 장애를 우아하게 다루는 것도 가능하게 한다. 첫째, 카프카는
  고가용이고 따라서 카프카에 영속화한 데이터도 고가용이다. 애플리케이션이 실패해 재시작해야
  하면 카프카에서 스트림의 마지막 위치를 조회해 실패 전 마지막으로 커밋한 오프셋부터 처리를
  이어 갈 수 있다. 로컬 상태 저장소를 잃어도(예컨대 그것이 저장된 서버를 교체해야 해서)
  스트림즈 애플리케이션은 카프카에 저장한 체인지 로그에서 언제나 그것을 다시 만들 수 있다**
  (14장, p.415).[^shapira2021]
- **카프카 스트림즈는 태스크의 고가용성을 위해 카프카의 컨슈머 조율도 활용한다. 태스크가
  실패했는데 활성 상태인 스레드나 다른 스트림즈 애플리케이션 인스턴스가 있으면 태스크는
  가용한 스레드 중 하나에서 재시작한다. 이는 컨슈머 그룹이 그룹 내 컨슈머 하나의 장애를
  남은 컨슈머에 파티션을 배정해 다루는 방식과 비슷하다** (14장, p.415).[^shapira2021]
  - **카프카 스트림즈는 정적 그룹 멤버십(static group membership)과 협력적 리밸런싱
    (cooperative rebalancing) 같은 카프카 컨슈머 그룹 조율 프로토콜의 개선(4장), 그리고
    카프카의 정확히 한 번 의미론 개선(8장)의 덕을 봤다** (14장, p.415).[^shapira2021] 그
    둘은 [컨슈머 그룹과 리밸런스](../concepts/kafka-consumer-groups-and-rebalance.md)와
    [카프카 트랜잭션](../concepts/kafka-transactions.md)에 있다.
- 이론과 현실의 차이도 적어 둔다 — **여기 서술한 고가용성 방법이 이론적으로는 잘 작동하지만
  현실은 복잡도를 끌어들인다. 중요한 관심사 하나가 복구 속도다. 스레드가 실패한 스레드에서
  돌던 태스크의 처리를 시작해야 할 때, 먼저 저장된 상태 — 예컨대 현재 집계 윈도우 — 를
  복구해야 한다. 흔히 이는 카프카 스트림즈 상태 저장소를 예열하기 위해 카프카에서 내부
  토픽을 다시 읽음으로써 이뤄진다. 실패한 태스크의 상태를 복구하는 데 걸리는 동안 스트림
  처리 잡은 그 데이터 부분집합에 대해 진전하지 못하므로 가용성이 떨어지고 데이터가
  낡는다** (14장, p.415).[^shapira2021]
- 그래서 **복구 시간을 줄이는 일은 흔히 상태를 복구하는 데 걸리는 시간을 줄이는 일로
  귀결된다. 핵심 기법은 모든 카프카 스트림즈 토픽이 공격적 압착으로 설정되게 하는 것** —
  **`min.compaction.lag.ms`를 낮게 잡고 세그먼트 크기를 기본 1GB 대신 100MB로 설정**한다.
  **각 파티션의 마지막 세그먼트인 활성 세그먼트는 압착되지 않는다는 점을 기억하라** (14장,
  pp.415–416).[^shapira2021] 그 설정들이 사는 자리는
  [카프카 로그 압착](../concepts/kafka-log-compaction.md)과
  [카프카 물리적 저장소](../concepts/kafka-physical-storage.md).
- **더 빠른 복구를 위해서는 스탠바이 레플리카(standby replica) 설정을 권한다** —
  **스트림 처리 애플리케이션에서 활성 태스크를 그저 따라다니며 현재 상태를 다른 서버에서
  뜨겁게 유지하는 태스크들**이다. **페일오버가 일어나면 이미 가장 최신 상태를 갖고 있으므로
  거의 다운타임 없이 처리를 이어 갈 준비가 돼 있다** (14장, p.416).[^shapira2021]

## 미해소

- 확장성과 고가용성의 더 자세한 내용은 이 장이 외부로 넘긴다 — 책이 지목한 곳은 **그 주제에
  대한 블로그 포스트와 카프카 서밋 발표**이며 (14장, p.416),[^shapira2021] 스탠바이 레플리카의
  설정 키와 개수 산정은 나오지 않는다. 해소하려면 **카프카 스트림즈 공식 문서(Developer
  Guide의 Running Streams Applications·`num.standby.replicas`)** 가 필요하다.
