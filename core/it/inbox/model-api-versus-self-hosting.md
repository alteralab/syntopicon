하나의 질문: **모델을 직접 돌릴 것인가 남의 API로 부를 것인가를 무엇으로 가르는가.**

## 추론 서비스와 모델 API

- 정의 — **모델이 사용자에게 접근 가능해지려면 그것을 호스팅하고 실행할 기계가 필요하다. 모델을
  호스팅하고 사용자 질의를 받아, 질의에 대한 응답을 생성하려고 모델을 돌리고, 그 응답을 사용자에게
  돌려주는 서비스를 추론 서비스(inference service)라 부른다. 사용자가 상호작용하는 인터페이스를 모델
  API(model API)라 부른다. 모델 API라는 용어는 통상 추론 서비스의 API를 가리키는 데 쓰이지만, 파인
  튜닝 API와 평가 API 같은 다른 모델 서비스의 API도 있다** (4장, p.183).[^huyen2025]

## 개발자는 셋 중 하나를 고른다

- **모델을 개발한 뒤 개발자는 그것을 오픈 소스로 공개하거나, API를 통해 접근 가능하게 만들거나, 둘 다
  할 수 있다. 많은 모델 개발자가 모델 서비스 제공자이기도 하다. Cohere와 Mistral은 어떤 모델을 오픈
  소스로 공개하고 어떤 모델에는 API를 제공한다. OpenAI는 통상 자기 상용 모델로 알려져 있지만 모델을
  오픈 소스로 공개하기도 했다(GPT-2, CLIP). 통상 모델 제공자는 더 약한 모델을 오픈 소스로 공개하고
  가장 좋은 모델은 유료 장벽 뒤에 — API를 통해서든 자기 제품을 구동하는 데든 — 둔다** (4장,
  p.183).[^huyen2025]

## 같은 모델도 API마다 다르다

- **모델 API는 모델 제공자(OpenAI와 앤트로픽 같은), 클라우드 서비스 제공자(Azure와 GCP[Google Cloud
  Platform] 같은), 서드파티 API 제공자(Databricks Mosaic, Anyscale 등)를 통해 이용 가능할 수 있다.
  같은 모델이 서로 다른 기능·제약·가격을 가진 서로 다른 API를 통해 이용 가능할 수 있다. 예컨대 GPT-4는
  OpenAI와 Azure API 양쪽을 통해 이용 가능하다. 서로 다른 API가 이 모델을 최적화하는 데 서로 다른
  기법을 쓸 수 있으므로 서로 다른 API를 통해 제공되는 같은 모델의 성능에는 약간의 차이가 있을 수 있다.
  따라서 모델 API를 바꿀 때는 반드시 철저한 테스트를 돌려라** (4장, pp.183–184).[^huyen2025]

## 누구의 경쟁 우위인가

- 비대칭 — **상용 모델은 모델 개발자가 라이선스한 API를 통해서만 접근 가능하다. 오픈 소스 모델은 어떤
  API 제공자든 지원할 수 있어, 당신에게 가장 잘 맞는 제공자를 고를 수 있게 한다. 상용 모델 제공자에게는
  모델이 그들의 경쟁 우위다. 자기 모델이 없는 API 제공자에게는 API가 그들의 경쟁 우위다. 이는 API
  제공자가 더 나은 가격으로 더 나은 API를 제공할 동기를 더 가질 수 있다는 뜻이다** (4장,
  p.184).[^huyen2025]
  - 각주 — **예컨대 집필 시점 기준 GPT-4 모델은 OpenAI나 Azure를 통해서만 접근할 수 있다. 어떤 사람은
    OpenAI의 독점 모델 위에 서비스를 제공할 수 있다는 것이 마이크로소프트가 OpenAI에 투자한 핵심
    이유라고 주장할 수도 있다** (4장, p.184 각주 13).[^huyen2025]
- 서드파티가 생긴 이유 — **더 큰 모델을 위한 확장 가능한 추론 서비스를 만드는 것은 사소하지 않기 때문에
  많은 기업이 그것을 직접 만들고 싶어 하지 않는다. 이는 오픈 소스 모델 위에 서는 많은 서드파티 추론·파인
  튜닝 서비스의 탄생으로 이어졌다. AWS·Azure·GCP 같은 주요 클라우드 제공자는 모두 인기 오픈 소스 모델에
  API 접근을 제공한다. 수많은 스타트업이 같은 일을 하고 있다** (4장, p.184).[^huyen2025]
- 저자의 분류 상자 — **자기 사설망 안에 자기 서비스를 배포할 수 있는 상용 API 제공자도 있다. 이 논의에서
  저자는 이런 사설 배포 상용 API를 자체 호스팅 모델과 비슷하게 취급한다** (4장, p.184).[^huyen2025]

## 일곱 축

- **모델을 직접 호스팅할지 모델 API를 쓸지에 대한 답은 유스케이스에 달려 있다. 그리고 같은 유스케이스도
  시간이 지나면 바뀔 수 있다. 고려할 일곱 축이 있다: 데이터 프라이버시, 데이터 계보, 성능, 기능, 비용,
  통제, 온디바이스 배포다** (4장, p.184).[^huyen2025]

## 축 하나: 데이터 프라이버시

- 원칙 — **조직 밖으로 데이터를 보낼 수 없는 엄격한 데이터 프라이버시 정책을 가진 기업에게 외부 호스팅
  모델 API는 논외다** (4장, p.184).[^huyen2025]
  - 각주의 미묘한 실측 — **흥미롭게도 엄격한 데이터 프라이버시 요건을 가진 어떤 기업들은, 보통은 서드파티
    서비스에 데이터를 보낼 수 없지만 GCP·AWS·Azure에 호스팅된 모델에 데이터를 보내는 것은 괜찮다고
    저자에게 말했다. 이 기업들에게 데이터 프라이버시 정책은 그들이 어떤 서비스를 신뢰할 수 있는가에 더
    가깝다. 그들은 큰 클라우드 제공자는 신뢰하지만 다른 스타트업은 신뢰하지 않는다** (4장, p.184
    각주 14).[^huyen2025]
- 초기의 대표 사건 — **가장 눈에 띄는 초기 사건 하나는 삼성 직원들이 삼성의 독점 정보를 ChatGPT에 넣어
  회사의 기밀을 실수로 유출한 일이었다. 삼성이 이 유출을 어떻게 발견했는지, 유출된 정보가 삼성에 대해
  어떻게 쓰였는지는 분명하지 않다. 그러나 그 사건은 삼성이 2023년 5월 ChatGPT를 금지할 만큼
  심각했다** (4장, pp.184–185).[^huyen2025]
  - 각주 — **이 이야기는 TechRadar를 포함해 여러 매체가 보도했다(루이스 매디슨의 "Samsung Workers Made
    a Major Error by Using ChatGPT", 2023년 4월)** (4장, p.184 각주 15).[^huyen2025]
- 국경 — **어떤 나라는 특정 데이터를 국경 밖으로 보내는 것을 금지하는 법을 갖고 있다. 모델 API 제공자가
  이 유스케이스를 서빙하고 싶다면 그 나라에 서버를 세워야 할 것이다** (4장, p.185).[^huyen2025]
- 정책은 바뀐다 — **모델 API를 쓰면 API 제공자가 당신의 데이터를 자기 모델을 훈련하는 데 쓸 위험이
  있다. 대부분의 모델 API 제공자가 그렇게 하지 않는다고 주장하더라도 그들의 정책은 바뀔 수 있다.
  2023년 8월 Zoom은 제품 사용 데이터와 진단 데이터를 포함해 Zoom 사용자의 서비스 생성 데이터를 자기 AI
  모델 훈련에 쓸 수 있도록 이용 약관을 조용히 바꾼 것이 알려진 뒤 반발에 부딪혔다** (4장,
  p.185).[^huyen2025]
- 왜 문제인가 — **다른 사람이 당신의 데이터를 자기 모델 훈련에 쓰는 것의 무엇이 문제인가? 이 영역의
  연구는 아직 드물지만 몇몇 연구는 AI 모델이 자기 훈련 표본을 기억할 수 있음을 시사한다. 예컨대 허깅
  페이스의 StarCoder 모델이 자기 훈련 집합의 8%를 기억한다는 것이 밝혀졌다. 이 기억된 표본은 사용자에게
  실수로 유출되거나 악의적 행위자에게 의도적으로 악용될 수 있는데, 5장에서 실증한다** (4장,
  p.185).[^huyen2025]

## 축 둘: 데이터 계보와 저작권

- 방향이 갈린다 — **데이터 계보와 저작권 우려는 기업을 여러 방향으로 몰 수 있다: 오픈 소스 모델 쪽으로,
  독점 모델 쪽으로, 또는 둘 다에서 멀어지는 쪽으로** (4장, p.185).[^huyen2025]
- 투명성의 부재 — **대부분의 모델에 대해 그 모델이 어떤 데이터로 훈련되었는지에 대한 투명성은 거의 없다.
  제미나이의 기술 리포트에서 구글은 모델의 성능에 대해 상세히 다뤘지만 모델의 훈련 데이터에 대해서는
  "데이터 보강 작업자들이 최소한 현지 생활 임금을 받는다"는 것 외에는 아무 말도 하지 않았다. OpenAI의
  CTO는 자기 모델을 훈련하는 데 어떤 데이터가 쓰였는지 질문받았을 때 만족스러운 답을 주지 못했다** (4장,
  p.185).[^huyen2025]
- IP 법이 진화 중이다 — **게다가 AI를 둘러싼 IP 법이 활발히 진화하고 있다. 미국 특허상표청(USPTO)은
  2024년 "AI 보조 발명은 범주적으로 특허 불가능하지 않다"고 명확히 하면서도, AI 애플리케이션의 특허
  가능성은 "혁신에 대한 인간의 기여가 특허를 받을 자격이 될 만큼 충분히 유의한지"에 달려 있다고 했다.
  저작권 있는 데이터로 모델이 훈련되었고 당신이 그 모델을 써서 제품을 만들었을 때 당신의 제품 IP를
  방어할 수 있는지도 불분명하다. 게임과 영화 스튜디오처럼 존재가 자기 IP에 달려 있는 많은 기업이,
  최소한 AI를 둘러싼 IP 법이 명확해질 때까지는 제품 창작을 돕는 데 AI를 쓰기를 주저한다(제임스 빈센트,
  The Verge, 2022년 11월 15일)** (4장, p.185).[^huyen2025]
- 완전 오픈 모델 쪽 논리와 그 현실 — **데이터 계보에 대한 우려는 어떤 기업들을 훈련 데이터가 공개된
  완전 오픈 모델 쪽으로 몰았다. 그 논리는 이것이 커뮤니티가 데이터를 검사해 그것이 쓰기에 안전한지
  확인하게 해 준다는 것이다. 이론상으로는 훌륭하게 들리지만 실제로는 어떤 기업이든 파운데이션 모델을
  훈련하는 데 통상 쓰이는 크기의 데이터셋을 철저히 검사하는 것은 어렵다** (4장, pp.185–186).[^huyen2025]
- 반대 방향의 논리 — **같은 우려로 많은 기업이 대신 상용 모델을 택한다. 오픈 소스 모델은 상용 모델에
  비해 법적 자원이 제한적인 경향이 있다. 저작권을 침해하는 오픈 소스 모델을 쓴다면 침해당한 쪽이 모델
  개발자를 쫓을 가능성은 낮고 당신을 쫓을 가능성이 더 높다. 그러나 상용 모델을 쓴다면 모델 제공자와
  맺는 계약이 데이터 계보 위험으로부터 당신을 잠재적으로 보호할 수 있다** (4장, p.186).[^huyen2025]
  - 각주 — **전 세계에서 규제가 진화하면서 모델과 훈련 데이터에 대한 감사 가능 정보의 요구가 늘어날 수
    있다. 상용 모델은 인증을 제공할 수 있어 기업의 수고를 덜어 줄지도 모른다** (4장, p.186
    각주 16).[^huyen2025]

## 축 셋: 성능

- 격차가 좁혀진다 — **여러 벤치마크는 오픈 소스 모델과 독점 모델 사이의 격차가 좁혀지고 있음을 보였다.
  이 추세는 언젠가 가장 강한 독점 모델만큼, 어쩌면 그보다 더 잘 수행하는 오픈 소스 모델이 나올 것이라고
  많은 사람이 믿게 만들었다** (4장, p.186, Figure 4-7).[^huyen2025]
- 저자의 반론 — **오픈 소스 모델이 독점 모델을 따라잡기를 저자가 아무리 바라더라도, 저자는 그것을 위한
  유인이 갖춰져 있다고 보지 않는다. 이용 가능한 가장 강한 모델을 갖고 있다면 다른 사람이 그것으로 돈을
  벌도록 오픈 소스로 공개하겠는가, 아니면 직접 돈을 벌려 하겠는가? 기업이 가장 강한 모델은 API 뒤에 두고
  더 약한 모델을 오픈 소스로 공개하는 것은 흔한 관행이다** (4장, p.186).[^huyen2025]
  - 각주의 유인 분석 — **사용자는 더 많은 정보와 선택지를 뜻하므로 모델이 오픈 소스이기를 원한다. 그러나
    모델 개발자에게는 무엇이 이득인가? 많은 기업이 오픈 소스 모델 위에 추론과 파인 튜닝 서비스를 제공해
    돈을 벌려고 생겨났다. 많은 사람은 오픈 소스 모델을 활용하려면 이 서비스가 필요하다. 그것은 나쁜 일이
    아니다. 그러나 모델 개발자의 관점에서 다른 사람이 돈을 벌게 하려고 수백만, 수십억을 모델 구축에 왜
    투자하는가? 메타가 경쟁자(구글·마이크로소프트/OpenAI)를 견제하려고만 오픈 소스 모델을 지원한다고
    주장할 수도 있다. Mistral과 Cohere 모두 오픈 소스 모델을 갖지만 API도 갖는다. 어느 시점에는 Mistral과
    Cohere 모델 위의 추론 서비스가 그들의 경쟁자가 된다. 오픈 소스가 사회에 더 낫다는 논거가 있고 어쩌면
    그것으로 유인은 충분하다. 사회에 좋은 것을 원하는 사람들은 계속 오픈 소스를 밀 것이고, 어쩌면 오픈
    소스가 이기게 도울 집단적 선의가 충분할 것이다. 저자는 분명 그러기를 바란다** (4장, p.186
    각주 17).[^huyen2025]
- 그래서 남는 결론 — **이 이유로 가장 강한 오픈 소스 모델은 당분간 가장 강한 독점 모델에 뒤처질 가능성이
  높다. 그러나 가장 강한 모델이 필요하지 않은 많은 유스케이스에는 오픈 소스 모델로 충분할 수 있다** (4장,
  p.187).[^huyen2025]
- 또 다른 이유 — **오픈 소스 모델이 뒤처질 수 있는 또 다른 이유는 오픈 소스 모델 개발자가 상용 모델처럼
  사용자로부터 자기 모델을 개선할 피드백을 받지 못한다는 것이다. 모델이 오픈 소스로 공개되고 나면 모델
  개발자는 그 모델이 어떻게 쓰이고 있는지, 야생에서 얼마나 잘 작동하는지 알 수 없다** (4장,
  p.187).[^huyen2025]

## 축 넷: 기능

- 모델 주위에 필요한 것들 — **모델이 유스케이스에 작동하려면 모델 주위에 많은 기능이 필요하다. 그런
  기능의 예다** (4장, p.187):[^huyen2025]
  - **확장성: 바람직한 지연과 비용을 유지하면서 추론 서비스가 애플리케이션의 트래픽을 감당할 수 있게 하는 것.**
  - **함수 호출: 모델에게 외부 도구를 쓸 능력을 주는 것으로, RAG와 에이전트 유스케이스에 필수적이다.**
  - **구조화 출력: 모델에게 JSON 형식으로 출력을 생성하라고 요청하는 것 같은 것.**
  - **출력 가드레일: 응답이 인종차별적이거나 성차별적이지 않게 하는 것처럼 생성된 응답의 위험을 완화하는 것.**
- API로 가게 되는 이유 — **이 기능 다수는 구현하기 어렵고 시간이 많이 들어, 많은 기업이 원하는 기능을
  기본 제공하는 API 제공자로 향하게 만든다** (4장, p.188).[^huyen2025]
- logprobs 제약 — **모델 API를 쓰는 것의 단점은 그 API가 제공하는 기능에 제약된다는 것이다. 많은
  유스케이스가 필요로 하는 기능 하나는 logprobs인데, 분류 과제·평가·해석 가능성에 매우 유용하다. 그러나
  상용 모델 제공자는 다른 사람이 logprobs를 써서 자기 모델을 복제할 것을 우려해 logprobs 노출을 주저할 수
  있다. 실제로 많은 모델 API가 logprobs를 노출하지 않거나 제한된 logprobs만 노출한다** (4장,
  p.188).[^huyen2025]
- 파인 튜닝 제약 — **상용 모델은 모델 제공자가 허용할 때만 파인 튜닝할 수 있다. 프롬프팅으로 모델의
  성능을 최대치까지 끌어올렸고 그 모델을 파인 튜닝하고 싶다고 상상해 보라. 이 모델이 독점이고 모델
  제공자에게 파인 튜닝 API가 없다면 그렇게 할 수 없을 것이다. 그러나 오픈 소스 모델이라면 그 모델에 대한
  파인 튜닝을 제공하는 서비스를 찾거나 직접 파인 튜닝할 수 있다. 부분 파인 튜닝과 전체 파인 튜닝처럼 여러
  유형의 파인 튜닝이 있고, 상용 모델 제공자는 그중 일부 유형만 지원할 수 있다는 것을 유념하라** (4장,
  p.188).[^huyen2025]

## 축 다섯: API 비용 대 엔지니어링 비용

- 양쪽 다 비싸다 — **모델 API는 사용량에 따라 과금하는데, 이는 사용이 많으면 감당 못 할 만큼 비쌀 수
  있다는 뜻이다. 어느 규모에 이르면 API로 자원이 출혈하는 기업은 자기 모델을 호스팅하는 것을 고려할 수
  있다. 그러나 모델을 직접 호스팅하려면 사소하지 않은 시간·인재·엔지니어링 노력이 필요하다. 모델을
  최적화하고, 필요에 따라 추론 서비스를 확장하고 유지보수하고, 모델 주위에 가드레일을 제공해야 할 것이다.
  API는 비싸지만 엔지니어링은 더 비쌀 수도 있다** (4장, p.188).[^huyen2025]
  - 각주 — **API 비용에 가장 크게 타격받는 기업은 아마 가장 큰 기업들이 아닐 것이다. 가장 큰 기업은
    서비스 제공자에게 충분히 중요해서 유리한 조건을 협상할 수 있을지 모른다** (4장, p.188
    각주 18).[^huyen2025]
- SLA 의존 — **다른 한편 다른 사람의 API를 쓴다는 것은 그들의 SLA(서비스 수준 협약)에 의존하게 된다는
  뜻이다. 이 API가 신뢰할 만하지 않다면 — 초기 스타트업에서 흔히 그렇듯 — 당신은 그 주위의 가드레일에
  엔지니어링 노력을 써야 할 것이다** (4장, p.188).[^huyen2025]
- 사용 편의 — **일반적으로 당신은 쓰고 조작하기 쉬운 모델을 원한다. 통상 독점 모델은 시작하고 확장하기가
  더 쉽지만, 오픈 모델은 그 구성 요소가 더 접근 가능하므로 조작하기가 더 쉬울 수 있다** (4장,
  p.188).[^huyen2025]
- 표준 API를 따르는 것 — **오픈 모델로 가든 독점 모델로 가든 당신은 이 모델이 표준 API를 따르기를 원하는데,
  이것이 모델 교체를 더 쉽게 만들기 때문이다. 많은 모델 개발자가 자기 모델을 가장 인기 있는 모델의 API를
  흉내 내도록 만들려 한다. 집필 시점 기준 많은 API 제공자가 OpenAI의 API를 흉내 낸다** (4장,
  p.188).[^huyen2025]
- 커뮤니티 지원 — **커뮤니티 지원이 좋은 모델을 선호할 수도 있다. 모델이 가진 역량이 많을수록 그 기벽도
  많다. 사용자 커뮤니티가 큰 모델은 당신이 마주치는 어떤 문제든 이미 다른 사람들이 겪었을 수 있고 그들이
  온라인에 해법을 공유했을 수 있다는 뜻이다** (4장, p.189).[^huyen2025]
  - 각주 — **이는 커뮤니티가 광범위하게 시험한 가장 인기 있는 도구를 늘 쓰라는 소프트웨어 인프라의
    철학과 비슷하다** (4장, p.189 각주 19).[^huyen2025]

## 축 여섯: 통제·접근·투명성

- a16z 조사 — **2024년 a16z의 연구는 기업이 오픈 소스 모델에 신경 쓰는 두 핵심 이유가 통제와 커스터마이즈
  가능성임을 보인다** (4장, p.189, Figure 4-8).[^huyen2025] 도판이 표시한 비율이다 (4장, p.189,
  Figure 4-8):[^huyen2025]

  | 이유 | All reasons cited | Primary reason cited |
  |---|---|---|
  | Control | 37% | 60% |
  | Customizability | 37% | 30% |
  | Cost | 26% | 10% |

- 통제 — **당신의 비즈니스가 어떤 모델에 의존한다면 그것에 어느 정도 통제권을 원하는 것이 이해할 만하고,
  API 제공자는 당신이 원하는 수준의 통제를 늘 주지는 않을 수 있다. 다른 사람이 제공하는 서비스를 쓸 때
  당신은 그들의 이용 약관과 요율 한도에 종속된다. 이 제공자가 당신에게 이용 가능하게 만든 것에만 접근할
  수 있고, 따라서 필요에 따라 모델을 손볼 수 없을 수 있다** (4장, p.189).[^huyen2025]
- 안전성 가드레일이 제약이 되는 자리 — **모델 제공자는 잠재적 소송으로부터 사용자와 자신을 보호하려고,
  인종차별적 농담을 하라거나 실제 사람의 사진을 생성하라는 요청을 차단하는 것 같은 안전성 가드레일을 쓴다.
  이 안전성 가드레일은 압도적 다수의 유스케이스에는 좋지만 특정 유스케이스에는 제약 요인일 수 있다. 예컨대
  당신의 애플리케이션이 실제 얼굴을 생성해야 한다면(뮤직 비디오 제작을 돕는 등) 실제 얼굴 생성을 거부하는
  모델은 작동하지 않을 것이다. 저자가 자문하는 기업 Convai는 물체를 집는 것을 포함해 3D 환경에서 상호작용할
  수 있는 3D AI 캐릭터를 만드는데, 상용 모델과 작업할 때 모델이 계속 "AI 모델로서 저는 물리적 능력이
  없습니다(As an AI model, I don't have physical abilities)"라고 응답하는 문제에 부딪혔다. Convai는 결국
  오픈 소스 모델을 파인 튜닝했다** (4장, pp.189–190).[^huyen2025]
- 접근을 잃을 위험 — **상용 모델에 대한 접근을 잃을 위험도 있는데, 그 주위에 시스템을 지었다면 고통스러울
  수 있다. 오픈 소스 모델에서 할 수 있는 것처럼 상용 모델을 동결할 수는 없다. 역사적으로 상용 모델은 모델
  변경·버전·로드맵에서 투명성이 부족했다. 모델은 자주 갱신되지만 모든 변경이 사전에 공지되거나 아예
  공지되는 것은 아니다. 당신의 프롬프트가 기대대로 작동하지 않게 되어도 당신은 이유를 모른다. 예측 불가능한
  변경은 상용 모델을 엄격히 규제되는 애플리케이션에 쓸 수 없게 만들기도 한다. 그러나 저자는 이 역사적
  투명성 부족이 빠르게 성장하는 산업의 의도치 않은 부작용일 뿐일지 모른다고 짐작하며, 산업이 성숙하면서
  이것이 바뀌기를 바란다** (4장, p.190).[^huyen2025]
- 더 드물지만 존재하는 상황 — **덜 흔하지만 안타깝게도 존재하는 상황은, 모델 제공자가 당신의 유스케이스·
  산업·국가에 대한 지원을 중단할 수 있고, 당신의 나라가 당신의 모델 제공자를 금지할 수 있다는 것이다
  — 이탈리아가 2023년에 잠시 OpenAI를 금지한 것처럼. 모델 제공자가 아예 폐업할 수도 있다** (4장,
  p.190).[^huyen2025]

## 축 일곱: 온디바이스 배포

- **모델을 기기에서 돌리고 싶다면 서드파티 API는 논외다. 많은 유스케이스에서 모델을 로컬로 돌리는 것이
  바람직하다. 유스케이스가 신뢰할 만한 인터넷 접속이 없는 지역을 겨냥하기 때문일 수도 있다. 프라이버시
  때문일 수도 있다 — AI 조수에게 당신의 모든 데이터에 대한 접근을 주고 싶지만 당신의 데이터가 기기를
  떠나기를 원하지 않을 때처럼** (4장, p.190).[^huyen2025]

## 장단점 표

- 모델 API 사용과 모델 자체 호스팅의 장단점이다 — **단점은 기울임꼴이다** (4장, pp.190–191,
  Table 4-4):[^huyen2025]

  | | Using model APIs | Self-hosting models |
  |---|---|---|
  | Data | *Have to send your data to model providers, which means your team can accidentally leak confidential info* | Don't have to send your data externally / *Fewer checks and balances for data lineage/training data copyright* |
  | Performance | Best-performing model will likely be closed source | *The best open source models will likely be a bit behind commercial models* |
  | Functionality | More likely to support scaling, function calling, structured outputs / *Less likely to expose logprobs* | *No/limited support for function calling and structured outputs* / Can access logprobs and intermediate outputs, which are helpful for classification tasks, evaluation, and interpretability |
  | Cost | *API cost* | *Talent, time, engineering effort to optimize, host, maintain* (can be mitigated by using model hosting services) |
  | Finetuning | *Can only finetune models that model providers let you* | Can finetune, quantize, and optimize models (if their licenses allow), *but it can be hard to do so* |
  | Control, access, and transparency | *Rate limits* / *Risk of losing access to the model* / *Lack of transparency in model changes and versioning* | Easier to inspect changes in open source models / You can freeze a model to maintain its access, *but you're responsible for building and maintaining model APIs* |
  | Edge use cases | *Can't run on device without internet access* | Can run on device, *but again, might be hard to do so* |

- 이 결정이 좁히는 것 — **각 접근의 장단점이 상용 API를 쓸지 모델을 직접 호스팅할지 결정하는 데 도움이 되기를
  바란다. 이 결정은 당신의 선택지를 상당히 좁혀야 한다. 다음으로 공개적으로 이용 가능한 모델 성능 데이터를
  써서 선택을 더 다듬을 수 있다** (4장, p.191).[^huyen2025]
