이 페이지의 질문: **스레드를 더 만들면 처리량이 더 나온다는 추론은 어디서 미끄러지는가.**

## 요청당 스레드 모델

- 오늘날 많은 웹 애플리케이션은 요청당 스레드(thread-per-request) 모델로 돈다 — 요청마다 스레드
  하나가 배정되고, 그 스레드가 요청과 응답의 수명 주기 전체를 맡는다 (1장, p.9).[^rahman2025]
- 그 자리에 있는 소프트웨어가 서블릿 컨테이너(servlet container)다. 웹 애플리케이션으로 들어오는
  요청의 처리를 맡는 소프트웨어이며, 아파치 톰캣이나 제티 같은 것이 그 예다. 요청이 도착하면
  컨테이너가 자기 스레드 풀의 스레드 하나에 그 요청을 넘긴다 (1장, p.9).[^rahman2025]
- 동시 연결이 많을 때 이 모델이 유리하다 — 동시성이 늘면 처리량도 늘고, 그 성질이 현대 웹
  애플리케이션이 늘어나는 요청량을 감당하며 확장하게 해 준다 (1장, p.9).[^rahman2025]
- 이 모델의 실물을 저자가 뒤에서 이름으로 짚는다 — 스프링 부트 웹 애플리케이션이 역사적으로 이
  모델을 주로 따랐고, 요청마다 전용 플랫폼 스레드 하나가 붙었다. 중간 부하에서는 잘 돌지만 I/O
  바운드 요청이 동시에 많이 들어오면 확장성 문제에 부딪힌다 (7장, p.297).[^rahman2025]
  그 프레임워크가 지금 그 자리를 어떻게 바꾸는지는
  [프레임워크가 가상 스레드를 켜는 방식](../concepts/enabling-virtual-threads-in-frameworks.md)에
  있다.
- 그래서 자연스러운 추론이 나온다 — 대부분의 현대 운영 체제가 수백만 동시 연결을 감당하니 스레드를
  더 만들면 처리량이 더 나오리라는 것이고, 리틀의 법칙(Little's Law)도 그렇게 읽힌다. 저자는 이
  추론이 그럴듯해 보이지만 미끄러운 데가 있어 늘 기대한 결과를 내지는 않는다고 못박는다 (1장,
  p.9).[^rahman2025]
  - 리틀의 법칙은 각주에서 지연과 동시성과 처리량을 잇는 큐잉 시스템의 원리로 소개되고, 상세한
    논의와 동시성이 높아지면 처리량이 높아진다는 실증은 다음 장으로 미뤄진다 (1장, p.9
    각주 1).[^rahman2025]

## 처리량이라는 지표

- 웹 애플리케이션에서 처리량(throughput)은 요청이 처리되고 서버가 응답을 내주는 속도이며, 보통 초당
  요청 수(requests per second, RPS)나 초당 트랜잭션 수(transactions per second, TPS)로 잰다. 부하를
  감당하는 능력을 나타내므로 성능과 확장성과 자원 활용의 핵심 지표가 된다 (1장,
  p.10).[^rahman2025]
- 계산은 처리한 총 요청 수를 총 시간으로 나눈 값이다 (1장, p.10).[^rahman2025]

  ```math
  \text{Throughput} = \frac{\text{Total Request Processed}}{\text{Total Time}}
  ```

## 메모리 발자국과 페이징

- 스레드 하나의 메모리 발자국이 약 2 MiB이고 이것은 힙 밖에서 스레드마다 드는 값이다. 수천 동시
  연결을 도는 대규모 애플리케이션에서는 스레드들의 메모리 합이 실제로 돌릴 수 있는 연결 수를
  좌우한다 (1장, p.10).[^rahman2025]
  - 이 값은 대부분의 리눅스 환경 기본값이며 운영 체제에 따라 다르고 조정할 수 있다 (1장, p.10
    각주 2).[^rahman2025]
  - 같은 값을 자바 가상 머신 쪽에서 잰 수치가
    [가상 스레드와 코루틴](../concepts/virtual-threads-and-coroutines.md)에 있다. 그쪽은 64비트
    리눅스 핫스팟의 스레드 스택을 1MB로 적는다 — 재는 자리가 다르므로 두 수치를 같은 것으로 읽지
    않는다. #hypothesis 두 수치의 차이가 무엇을 포함하고 무엇을 뺀 결과인지는 두 소스 모두
    밝히지 않는다.
- 애플리케이션이 물리 메모리를 다 쓰면 디스크로 페이징이 일어나고, 이것은 램에 닿는 것보다도
  훨씬 느리다. 디스크에서 읽는 시간과 램에서 읽는 시간의 차이가 1,000배이며, 이것만으로도 성능이
  크게 무너진다 (1장, p.10).[^rahman2025]

## 상한은 운영 체제가 정한다

- 자바 스레드는 실제로는 호스트 운영 체제가 주는 네이티브 스레드(native thread)를 얇게 감싼
  껍데기다. 그래서 애플리케이션이 만들 수 있는 스레드의 최대 개수가 사실상 호스트 운영 체제의
  네이티브 스레드 생성 한계에 묶인다 (1장, p.10).[^rahman2025]
- 거의 모든 운영 체제가 만들 수 있는 스레드 수에 상한을 두므로, 애플리케이션의 확장 가능성도 이
  병목에 묶인다 (1장, p.10).[^rahman2025]
  - 이 껍데기 관계가 어떤 스레드 구현 모델의 귀결인지는
    [스레드 구현 모델](../concepts/thread-implementation-models.md)이 답한다.

## 문맥 전환은 CPU 비용이다

- 스레드 생성은 메모리 부담만이 아니라 CPU 부담이기도 하다. 스레드 사이를 오갈 때 일어나는 것이
  문맥 전환(context switch)이며, 지금 스레드의 문맥을 저장하고 새 스레드의 문맥을 되불러 와야
  한다 (1장, p.10).[^rahman2025]
- 그 저장과 복원이 CPU 사이클을 먹고, 부하가 높은 시스템에서는 이 부담이 성능에 큰 차이를 만든다.
  저자는 이것을 애플리케이션에서 제대로 인정받지 못하는 무게의 원천이라고 부른다 (1장,
  p.10).[^rahman2025]
  - 문맥이 무엇인지를 개발자와 스레드와 운영 체제의 세 관점으로 갈라 본 서술이
    [가상 스레드와 코루틴](../concepts/virtual-threads-and-coroutines.md)에 있다.

## 몇 개까지 만들 수 있는가

- 저자는 상한을 재는 골격 코드를 싣는다 — 스레드를 계속 만들어 각각을 주차시켜 두고
  `OutOfMemoryError`가 날 때까지 세는 프로그램이다 (1장, p.11).[^rahman2025]

  ```java
  public class ThreadLimitTest {
      public static void main(String[] args) {
          var threadCount = new AtomicInteger(0);
          try {
              while (true) {
                  var thread = new Thread(() -> {
                      threadCount.incrementAndGet();
                      LockSupport.park();
                  });
                  thread.start();
              }
          } catch (OutOfMemoryError error) {
              System.out.println("Reached thread limit: " + threadCount);
              error.printStackTrace();
          }
      }
  }
  ```

- 저자 기계의 실측은 16,363개다 — 그만큼 만든 뒤 `OutOfMemoryError`가 났다. 저자는 이것을 스레드
  개수에 유한한 한계가 있다는 사실의 실물로 읽고, 그 한계가 대체로 밑의 운영 체제와 하드웨어가
  정하는 것이라 기계마다 다르다고 덧붙인다 (1장, p.11).[^rahman2025]
- 그래서 이 절의 결론은 균형이다 — 스레드는 웹 애플리케이션의 확장성에 큰 이득을 주지만 비용이
  따라오고, 그 비용은 때로 눈에 잘 띄지 않으므로 성능을 지키려면 신중히 따져야 한다 (1장,
  p.11).[^rahman2025]
