하나의 질문: **데이터가 들어와서 사람이 보기까지의 일 중 어디까지를 미리 하고 어디부터를
물어볼 때 할 것인가.**

## 두 경로

- **추상 수준에서 앞 절에서 논한 데이터플로 시스템은 파생 데이터셋(검색 색인·구체화 뷰·예측
  모델 같은)을 만들고 최신으로 유지하는 프로세스를 준다. 그 프로세스를 쓰기 경로(write path)라
  부르자. 정보 조각이 시스템에 쓰일 때마다 그것은 여러 단계의 배치·스트림 처리를 거칠 수 있고,
  결국 모든 파생 데이터셋이 쓰인 데이터를 반영하도록 갱신된다** (13장,
  p.555).[^kleppmann2026]
- **그런데 애초에 왜 파생 데이터셋을 만드는가? 아마 나중에 그것을 다시 질의하고 싶기 때문일
  것이다. 이것이 읽기 경로(read path)다: 사용자 요청을 서빙할 때 파생 데이터셋에서 읽고, 어쩌면
  결과에 더 많은 처리를 수행하고, 사용자에 대한 응답을 구성한다** (13장,
  p.556).[^kleppmann2026]
- 둘을 합치면 — **쓰기 경로와 읽기 경로를 합치면 데이터가 수집되는 지점부터 (아마 다른 사람에게)
  소비되는 지점까지 데이터의 전체 여정을 아우른다. 쓰기 경로는 미리 계산되는 여정의 부분이다;
  그것은 아무도 보여 달라고 요청하지 않았더라도 데이터가 들어오는 즉시 열심히(eagerly) 수행된다.
  읽기 경로는 누군가 요청할 때에만 일어나는 여정의 부분이다. 함수형 프로그래밍 언어에 익숙하다면
  쓰기 경로가 즉시 평가(eager evaluation)와 비슷하고 읽기 경로가 지연 평가(lazy evaluation)와
  비슷하다는 것을 알아챌 것이다** (13장, p.556).[^kleppmann2026]
- **파생 데이터셋은 쓰기 경로와 읽기 경로가 만나는 자리다. 그것은 쓰기 시점에 수행돼야 하는
  일의 양과 읽기 시점에 수행돼야 하는 일의 양 사이의 트레이드오프를 나타낸다** (13장,
  p.556).[^kleppmann2026]

## 경계를 옮기는 것이 전부다

- 저자들의 예 — **전문 검색 색인이 좋은 예다: 쓰기 경로는 색인을 갱신하고 읽기 경로는 키워드로
  색인을 검색한다. 읽기와 쓰기 둘 다 어떤 일을 해야 한다. 쓰기는 문서에 나타나는 모든 텀에 대한
  색인 엔트리를 갱신해야 한다. 읽기는 질의의 각 단어를 검색하고 불리언 논리를 적용해 질의의 단어를
  전부 담은 문서(AND 연산자)나 각 단어의 동의어 중 아무거나 담은 문서(OR 연산자)를 찾아야 한다**
  (13장, p.556).[^kleppmann2026]
- 색인이 없으면 — **색인이 없으면 검색 질의는 (grep처럼) 모든 문서를 훑어야 하고, 문서 수가
  많으면 매우 비싸질 것이다. 색인이 없다는 것은 쓰기 경로의 일이 적고(갱신할 색인이 없다) 읽기
  경로의 일이 훨씬 많다는 뜻이다** (13장, pp.556–557).[^kleppmann2026]
- 반대 극단은 불가능하다 — **다른 한편 모든 가능한 질의에 대한 검색 결과를 미리 계산하는 것을
  상상할 수 있다. 그 경우 읽기 경로에서 할 일이 적다: 불리언 논리 없이 그냥 질의의 결과를 찾아
  반환하면 된다. 그러나 쓰기 경로가 훨씬 더 비쌀 것이다. 물어볼 수 있는 검색 질의의 집합은
  무한하거나(적어도 코퍼스의 텀 수에 지수적이거나) 하므로 가능한 모든 검색 결과를 미리 계산하는
  것은 가능하지 않을 것이다** (13장, p.557).[^kleppmann2026]
- 중간 지대 — **또 다른 선택지는 가장 흔한 질의의 고정된 집합에 대해서만 검색 결과를 미리 계산해
  색인에 가지 않고도 빠르게 서빙할 수 있게 하는 것이다. 드문 질의는 여전히 색인에서 서빙할 수
  있다. 이는 일반적으로 흔한 질의의 캐시라 불리지만, 흔한 질의 중 하나의 결과에 포함돼야 할 새
  문서가 나타날 때 갱신돼야 하므로 구체화 뷰라 부를 수도 있다** (13장,
  p.557).[^kleppmann2026]
- 그래서 정리가 하나 나온다 — **이 예에서 색인이 쓰기 경로와 읽기 경로 사이의 유일한 가능한
  경계가 아님을 볼 수 있다. 흔한 검색 결과의 캐싱도 가능하고, 적은 수의 문서에 대해서는 색인
  없이 grep 같은 스캔도 가능하다. 이렇게 보면 캐시·색인·구체화 뷰의 역할은 단순하다: 그것들은
  읽기 경로와 쓰기 경로 사이의 경계를 옮긴다. 그것들은 결과를 미리 계산함으로써 쓰기 경로에서
  더 많은 일을 하고 읽기 경로의 수고를 아끼게 해 준다** (13장, p.557).[^kleppmann2026]
- 이 책의 첫 사례가 바로 그것이었다 — **쓰기 경로와 읽기 경로에서 하는 일 사이의 경계를 옮기는
  것이 사실 "사례 연구: 소셜 네트워크 홈 타임라인"의 소셜 네트워킹 예의 주제였다. 그 예에서 우리는
  또한 쓰기 경로와 읽기 경로 사이의 경계가 유명인과 일반 사용자에 대해 다르게 그어질 수 있음을
  보았다. 500쪽을 지나 우리는 한 바퀴를 돌아 제자리로 왔다!** (13장,
  p.557).[^kleppmann2026] 그 사례는
  [소셜 네트워크 홈 타임라인 사례](../concepts/social-network-home-timelines.md)에 있다.

## 상태를 가진 오프라인 클라이언트

- 경계를 다른 곳으로 옮겨 보면 — **과거에 웹 브라우저는 인터넷 연결이 있을 때에만 쓸모 있는 일을
  할 수 있는 무상태 클라이언트였다(오프라인에서 할 수 있는 거의 유일한 일은 온라인일 때 미리
  불러 둔 페이지를 위아래로 스크롤하는 것이었다). 그러나 단일 페이지 자바스크립트 웹 앱은 이제
  클라이언트 측 UI 상호작용과 웹 브라우저의 영속 로컬 저장을 포함해 상태를 다루는 능력을 많이
  갖고 있다. 모바일 앱도 비슷하게 기기에 상태를 많이 저장할 수 있고 대부분의 사용자 상호작용에
  서버 왕복을 요구하지 않는다** (13장, p.557).[^kleppmann2026]
- **"싱크 엔진과 로컬 우선 소프트웨어"에서 영속적 로컬 상태가 사용자가 인터넷 연결 없이 오프라인
  으로 작업하고 네트워크 연결이 가능할 때 백그라운드에서 원격 서버와 동기화하는 부류의 애플리케이션을
  가능하게 하는 것을 보았다. 모바일 기기는 때때로 느리고 신뢰할 수 없는 셀룰러 인터넷 연결을
  가지므로, UI가 동기 네트워크 요청을 기다리지 않아도 되고 앱이 대체로 오프라인에서 동작하는 것은
  사용자에게 큰 장점이다** (13장, p.558).[^kleppmann2026] 그 계열은
  [싱크 엔진과 로컬 우선 소프트웨어](../concepts/sync-engines-and-local-first.md)에 있다.
- 관점의 전환 — **중앙 데이터베이스와 대화하는 무상태 클라이언트라는 가정에서 벗어나 최종 사용자
  기기에서 유지되는 상태 쪽으로 옮겨 가면 새로운 기회의 세계가 열린다. 특히 기기 위의 상태를
  서버 상태의 캐시로 생각할 수 있다. 화면의 픽셀은 클라이언트 앱에 있는 모델 객체의 구체화 뷰다;
  모델 객체는 원격 데이터센터에 있는 상태의 로컬 레플리카다** (13장,
  p.558).[^kleppmann2026]

## 상태 변화를 클라이언트로 밀기

- 지금의 기본값 — **웹 브라우저에서 전형적인 웹 페이지를 불러오고 나서 데이터가 서버에서 바뀌면,
  브라우저는 페이지를 다시 불러올 때까지 그 변경을 알지 못한다. 브라우저는 데이터를 한 시점에만
  읽으며 그것이 정적이라고 가정한다; 브라우저는 서버의 갱신을 구독하지 않는다. 따라서 브라우저의
  상태는 명시적으로 변경을 폴링하지 않는 한 갱신되지 않는 낡은 캐시다. (RSS 같은 HTTP 기반 피드
  구독 프로토콜은 사실 폴링의 기본 형태일 뿐이다.)** (13장, p.558).[^kleppmann2026]
- 바뀐 것 — **2026년 저술 시점 기준 더 최근의 프로토콜은 HTTP의 기본 요청/응답 패턴을 넘어섰다. 서버 전송
  이벤트(server-sent events, EventSource API)와 웹소켓(WebSockets)은 웹 브라우저가 서버로의 열린
  TCP 연결을 유지하고 서버가 연결돼 있는 한 브라우저에 능동적으로 메시지를 밀어 넣을 수 있는 통신
  채널을 제공한다. 이는 서버가 로컬에 저장한 상태의 어떤 변경이든 최종 사용자 클라이언트에게
  능동적으로 알려 클라이언트 측 상태의 낡음을 줄일 기회를 준다** (13장,
  p.558).[^kleppmann2026]
- 우리 모델로 옮기면 — **쓰기 경로와 읽기 경로라는 우리 모델의 용어로, 상태 변화를 클라이언트
  기기까지 능동적으로 미는 것은 쓰기 경로를 최종 사용자까지 끝까지 확장하는 것을 뜻한다. 클라이언트가
  처음 초기화될 때는 여전히 초기 상태를 얻기 위해 읽기 경로를 써야 하지만, 그 뒤로는 서버가 보내는
  상태 변화의 스트림에 의존할 수 있다. 스트림 처리와 메시징을 둘러싸고 논의한 발상은 따라서
  데이터센터 안에서 도는 것에 국한되지 않는다; 우리는 그것을 더 밀고 나가 최종 사용자 기기까지
  확장할 수 있다** (13장, p.558).[^kleppmann2026]
- 오프라인 구간은 이미 푼 문제다 — **기기는 때때로 오프라인일 것이고 그동안 서버로부터 상태 변화의
  어떤 통지도 받을 수 없을 것이다. 그러나 우리는 이미 그 문제를 풀었다; "컨슈머 오프셋"에서 로그
  기반 메시지 브로커의 컨슈머가 실패하거나 연결이 끊긴 뒤 재연결해 연결이 끊긴 동안 도착한 메시지를
  하나도 놓치지 않도록 보장하는 방법을 논했다. 같은 기법이 개별 사용자에게도 동작하는데, 각 기기가
  작은 이벤트 스트림의 작은 구독자다** (13장, pp.558–559).[^kleppmann2026] 그 오프셋 기제는
  [로그 기반 메시지 브로커](../concepts/log-based-message-brokers.md)에 있다.

## 종단 간 이벤트 스트림

- **React나 Elm처럼 상태 있는 클라이언트와 UI를 개발하는 도구는 이미 기저 상태의 변경에 응답해
  렌더된 UI를 갱신하는 능력을 갖고 있다. 이 프로그래밍 모델을 확장해 서버가 이 클라이언트 측 이벤트
  파이프라인에 상태 변경 이벤트를 밀어 넣을 수 있게 하는 것은 매우 자연스러울 것이다** (13장,
  p.559).[^kleppmann2026]
- 그 결과 — **그러면 상태 변화가 종단 간 쓰기 경로를 통해 흐를 수 있다: 변경을 촉발하는 한 기기의
  상호작용에서, 이벤트 로그와 다양한 파생 데이터 시스템과 스트림 프로세서를 거쳐, 다른 기기의
  사용자 인터페이스까지. 이 상태 변화는 꽤 낮은 지연으로 — 이를테면 종단 간 1초 미만으로 — 전파될
  수 있다** (13장, p.559).[^kleppmann2026]
- 이미 그런 것도 있다 — **인스턴트 메시징이나 온라인 게임 같은 어떤 애플리케이션은 이미 그런
  "실시간" 아키텍처를 갖고 있다(응답 시간 보장이라는 의미가 아니라 낮은 지연의 상호작용이라는
  의미에서). 왜 우리는 모든 애플리케이션을 이렇게 짓지 않는가?** (13장,
  p.559).[^kleppmann2026]
- 막는 것 — **도전은 무상태 클라이언트와 요청/응답 상호작용이라는 가정이 우리의 데이터베이스·
  라이브러리·프레임워크·프로토콜에 깊이 배어 있다는 점이다. 많은 데이터스토어는 요청이 단일 응답을
  반환하는 읽기·쓰기 연산을 지원하지만, 요청이 시간에 걸쳐 응답의 스트림을 반환하는 연산(즉 변경을
  구독하는 능력)을 지원하는 것은 훨씬 적다** (13장, p.559).[^kleppmann2026]
- 저자들의 결론 — **쓰기 경로를 최종 사용자까지 끝까지 확장하려면 이런 시스템 다수를 짓는 방식을
  근본적으로 재고해 요청/응답 상호작용에서 발행/구독 데이터플로 쪽으로 옮겨 가야 할 것이다. 이는
  노력을 요구하겠지만 UI를 더 반응적으로 만들고 더 나은 오프라인 지원을 제공한다는 장점을 가질
  것이다** (13장, p.559).[^kleppmann2026]
