## 하나의 질문

**데이터 메시로 옮겨 가면 누가 무엇을 하게 되는가.**

- 저자가 다룰 범위를 좁힌다 — **사람에 관한 조직 설계 결정에는 그들의 역할·역량·개발과 훈련·
  채용이 포함된다. 이 절에서 나는 데이터 메시가 영향을 주는 핵심적으로 구별되는 영역만 다룰
  것이다: 새롭고 변화하는 역할과 책임, 그리고 데이터 메시를 구현하는 데 필요한 재능·기술·
  마음가짐을 생성할 새로운 개발 경로다** (16장, p.324).[^dehghani2022]
- 어느 원칙이 어느 역할을 만드는지가 짝지어 적힌다 — **제품으로서의 데이터 원칙과 도메인 소유권
  원칙의 도입은 각 도메인 팀 안에 데이터 프로덕트 소유자 같은 새 역할을 도입한다. (…) 셀프서브
  데이터 플랫폼은 플랫폼 제품 소유자 역할을 강조한다. (…) 거버넌스 의사 결정의 도메인 연합은
  데이터 거버넌스 책임자·데이터 스튜어드·데이터 커스터디언 같은 기존 거버넌스 역할을 바꾼다.
  궁극적으로 교차 기능 도메인 지향 팀으로의 데이터 소유권 탈중앙화는 조직의 데이터 총괄 — 예:
  최고 데이터·분석 책임자 — 의 책임과 역할을 옮긴다** (16장, pp.324–325).[^dehghani2022]

## 새로 생기는 역할 셋

- **① 데이터 프로덕트 소유자(data product owner)** — **특정 도메인 안에서 일하고 그 도메인의
  데이터 프로덕트에 책임진다. 하위 도메인과 데이터 프로덕트의 수·복잡도에 따라 한 명이거나 여러
  명일 수 있다. 데이터 프로덕트 소유자는 데이터 프로덕트의 비전과 로드맵을 둘러싼 의사 결정을
  촉진하고, 데이터 소비자의 만족을 지속적으로 측정하고 소통하는 데 관심을 두며, 데이터 프로덕트
  팀이 데이터의 품질과 풍부함을 개선하도록 돕는다. **그들은 도메인 데이터 프로덕트의 수명 주기를
  관리하고 소통한다 — 언제 바꾸고·개정하고·데이터와 스키마를 퇴역시킬지다. 그들은 경쟁하는 데이터
  소비자의 필요 사이에서 균형을 잡는다**** (16장, p.325).[^dehghani2022]
  - 측정이 역할의 일부다 — **데이터 프로덕트 소유자는 자기 데이터 프로덕트의 성공 기준과
    비즈니스 정렬 KPI — 성능과 성공을 재는 객관적 지표 집합 — 를 정의하고·지속적으로 모니터링하고·
    정제한다. 그들은 이 지표를 써서 데이터 프로덕트의 상태에 대한 관측 가능성을 얻고 팀이 데이터
    프로덕트를 개선하도록 돕는다** (16장, p.325).[^dehghani2022]
  - 성공의 정의 — **데이터 프로덕트의 성공은 다른 어떤 제품과도 같이 데이터 소비자의 만족에
    정렬된다. 예컨대 데이터 소비자 만족은 순추천지수 — 소비자가 그 데이터 프로덕트를 남에게
    추천하는 정도 — 로, 데이터 소비자가 데이터 프로덕트를 발견하고 성공적으로 쓰는 데 걸리는
    줄어든 리드 타임으로, 그리고 사용자의 성장으로 측정될 수 있다** (16장,
    p.325).[^dehghani2022] 같은 지표가
    [데이터 메시의 적합성 함수](../concepts/data-mesh-fitness-functions.md)에 있다.
- **② 도메인 데이터 프로덕트 개발자(domain data product developer)** — **도메인의 데이터
  프로덕트를 짓고 운영하려면 앱 개발 팀의 역할이 데이터 프로덕트 개발자를 포함하도록 확장되어야
  한다. 데이터 프로덕트 개발자는 협업하는 애플리케이션 개발자와 긴밀히 일하며 도메인 데이터
  의미론을 정의하고, **애플리케이션 맥락의 데이터(안쪽의 데이터)를 데이터 프로덕트 맥락(바깥쪽의
  분석 데이터)으로 매핑한다.** 그들은 원하는 데이터를 생성하는 변환 로직과, 자기 데이터
  프로덕트의 사용성 특질·보증을 짓고 유지한다** (16장, p.325).[^dehghani2022]
  - 부수 효과가 명시된다 — **그런 교차 기능 협업의 훌륭한 부작용은 서로 다른 기술 집합의 교차
    수분(cross pollination)이며, 기존 개발자를 교차 숙련시켜 데이터 프로덕트 개발자가 되게 하는
    능력이다** (16장, p.325).[^dehghani2022]
- **③ 플랫폼 제품 소유자(platform product owner)** — **이 역할은 데이터 메시 플랫폼에 고유하지
  않으며 어떤 내부 기술 플랫폼에도 필수다. 멀티플레인 플랫폼 서비스는 단순히 제품이며, 내부
  사용자·데이터 프로덕트 개발자·소비자가 자기 일을 하려 쓰는 제품이다. **플랫폼 서비스의 성공은
  사용 편의·만족, 그리고 솔직히 말해 강제 없는 플랫폼 서비스의 채택에 달려 있다**** (16장,
  p.326).[^dehghani2022]
  - 요구되는 배경 — **플랫폼 제품 소유자는 사용자 — 이 경우 데이터 개발자·데이터 프로덕트 소유자
    등 — 에 대한 깊은 지식을 가져야 한다. 흔히 플랫폼 제품 소유자는 과거에 파워 유저였고 데이터
    생산자나 소비자의 여정을 직접 경험한 사람이다. 그들은 플랫폼의 일부로 쓰거나·짓거나·살
    기술 지형에 대한 합리적 이해를 갖는다. 사용자 리서치·제품 검증·피드백 수집·A/B 테스팅 같은
    제품 소유권 기술이 필요하다** (16장, p.326).[^dehghani2022]
  - 이 역할이 밟는 여정이
    [데이터 플랫폼 사용자 여정](../concepts/data-platform-user-journeys.md)이다.

## 옮겨 가는 기존 역할

저자는 데이터 거버넌스 사무국의 역할별로 행선지를 지정한다 (16장, p.326):[^dehghani2022]

| 오늘의 역할 | 오늘 하는 일 | 데이터 메시에서의 행선지 |
|---|---|---|
| 데이터 스튜어드(data steward) | **중앙 거버넌스 팀에서 운영하며 하나 이상 도메인의 데이터 품질 이슈를 관리·조사·해결한다** | **도메인으로 옮겨 그 도메인의 일부가 되어 데이터 프로덕트 소유자가 된다.** 또는 **플랫폼으로 옮겨 데이터 품질 테스트·관측 가능성·복구를 자동화하는 전문가가 된다** |
| 데이터 커스터디언(data custodian) | **데이터 소스와의 일상 업무와 데이터 유지를 직접 손으로 맡는다** | **이 역할은 폐지(deprecated)되고 도메인의 데이터 프로덕트 개발자 역할로 옮겨진다** |
| 데이터 협의회(data council) | **정책에 대해 책임지는 최상위 의사 결정 기구** | **도메인의 대표가 참여하는 연합 모델로 옮겨진다** |

- 이 이동들이 겨냥하는 것 — **이 예들은 거버넌스의 자동화와 연합으로 나아가고, **동기적 통제와
  병목을 제거하며, 변경을 만들 권한을 가진 사람에게 책임을 주는** 출발점이다** (16장,
  p.327).[^dehghani2022]
- "폐지"라는 낱말이 실제로 쓰인다는 점이 중요하다 — 저자는 역할의 재배치와 소멸을 구분한다.

## 최고 데이터·분석 책임자의 변화

- 오늘의 CDAO — **오늘 기술 조직은 최고 데이터·분석 책임자(CDAO)·최고 기술 책임자·최고 디지털
  책임자 같은 기능 임원이 운영한다. 전통적으로 CDAO의 역할은 데이터에 관한 모든 것 — 비즈니스
  가치를 이끌 데이터의 전사적 창출·활용·거버넌스에 대한 책임 — 에 관계해 왔다. 내가 함께 일한
  많은 CDAO는 데이터 플랫폼을 짓고, 분석 데이터를 수확하고 수집하고, 비즈니스가 요구하는 분석
  솔루션 다수 — 대시보드와 ML 모델 — 를 짓는 데 책임진다** (16장, p.327).[^dehghani2022]
- 이동의 방향 — **데이터를 전문화된 관심사에서 일반화된 관심사로 옮기는 것, 데이터 책임을 교차
  기능 도메인 팀에 분배하는 것, 데이터 전문성을 확산시키는 것 모두가 CDAO의 역할을 **인에이블먼트
  (enablement) 역할**로 옮기는 데 영향을 주며, 최고 디지털·기술 책임자와 긴밀히 협업하는 관계를
  갖게 한다** (16장, p.327).[^dehghani2022]
- 남는 것과 남지 않는 것 — **CDAO는 고도로 전문화된 영역에 대해서는 남을 것이다. 어떤 고도
  전문 영역이 진화할지, 그 역할이 정확히 어떻게 생길지 말하기는 너무 이르다** (16장,
  p.327).[^dehghani2022] #hypothesis
- 그리고 미해결 과제로 남긴다 — **그럼에도 조직은 **데이터 책임의 탈중앙화와 CDAO 아래 데이터
  책무의 중앙집중 사이의 충돌을 해소해야 한다**** (16장, p.327).[^dehghani2022]

## 교육이 민주화를 이끈다

- 전략이 요구하는 것 — **데이터 메시 전략은 디지털 솔루션 개발 — 애플리케이션·서비스·제품 — 에
  관여하는 모두에게 요구되는 최소 기술 집합의 확산을 요구한다. 데이터를 감상하고·이해하고·쓰기
  위해서다. 데이터 전문가와 나머지 모두 사이의 조직적 사일로 벽을 제거하는 것이 기술·언어·이해의
  유기적 교차 수분을 위한 촉매다** (16장, p.327).[^dehghani2022]
- 그러나 구조만으로는 부족하다 — **삼투로 새 기술을 배우기에 유리한 조직 구조를 만드는 것이 좋은
  출발점이지만, 조직은 전반에 걸친 **의도적으로 설계된 데이터 리터러시(data literacy)
  프로그램**을 만들고 실행하는 데 투자해야 한다** (16장, p.327).[^dehghani2022]
- 낱말의 어원을 짚으며 교육과 참여를 잇는다 — **"민주화(democratization)"의 어근을 따라가면
  "dēmos" — 사람 — 에 도달한다. 교육은 사람들의 인식과 참여 수준을 높인다. 사실 연구는 사람들의
  교육 수준이 사회 규모에서 민주주의 수준에 직접 영향을 준다는 것을 보여 준다** (16장,
  p.328).[^dehghani2022] 각주는 Eduardo Alemán·Yeaji Kim, "The Democratizing Effect of
  Education", *Research & Politics*(2015)을 든다 (16장, p.328, 각주 11).[^dehghani2022]
- 무엇을 가정하는가 — **데이터 메시의 성공적 구현은 이전 패러다임이 기대했던 것 이상의 데이터
  공유 참여에 달려 있다. 그것은 **제너럴리스트 기술자**가 데이터를 제공하고 쓰이게 하는 데
  참여한다고 가정한다. 제품 관리자·애플리케이션 개발자·시스템 설계자가 더 이상 데이터의 지식과
  책임을 외부화하지 않는다고 가정한다** (16장, p.328).[^dehghani2022]
- **기대치의 상한도 명시된다** — **데이터 메시는 사람들이 데이터 전문가가 되기를 기대하지 않지만,
  **자기 데이터의 전문가**가 되기를 기대한다. 플랫폼이 요구되는 전문화 정도를 낮춘다. 협업적
  교차 기능 팀을 기대하고, 제너럴리스트가 데이터와 데이터 유스케이스에 대한 언어·심성 모델·감상·
  공감을 확립하기를 기대한다. 비슷하게 **데이터 전문가가 소프트웨어 엔지니어와 나란히, 그리고
  흐름 안에서 일하며** 데이터를 관리하고·적용하고·공유할 때 소프트웨어 공학의 에버그린 실무를
  익히기를 기대한다** (16장, p.328).[^dehghani2022]

## 교육의 다섯 대상

저자가 대상별로 목표를 다르게 잡는다 (16장, pp.328–329):[^dehghani2022]

- **모두(Everyone)** — **디지털 솔루션을 짓거나·지원하거나·관리하는 데 관여하는 모두는 좋은
  데이터가 무엇이고 어떻게 활용될 수 있는지에 대한 인식을 가져야 한다. 조직의 특정 산업에 적용된
  ML의 응용 — 생성 애플리케이션·최적화 솔루션·추천 시스템·이상 탐지 서비스 — 을 배우는 것이
  창의성과 참여 욕구를 높인다. (…) **이 교육의 기대 결과는 데이터에 대한 인식·감상·공감·호기심을
  만드는 것이다**.**
- **임원과 의사 결정자** — **임원은 데이터 메시가 왜 조직에 관련되는지를 깊이 이해하고 그
  뒷받침 원칙을 알아야 한다. 데이터 메시 실행 동안 그들은 **단기 전술적 필요와 전략적 필요
  사이에서 균형을 잡아야 하는 많은 결정적 결정**에 직면할 것이다.**
- **제너럴리스트 기술자** — **데이터 공유의 기여자 인구를, 데이터 프로덕트 개발자로든 데이터
  사용자로든 규모 확장하려면 새 도구 집합에 대한 숙달이 필요하다. 기술적으로 개발자는 플랫폼
  인터페이스·서비스와, 데이터 프로덕트를 규율하는 표준·정책에 대해 교육받아야 한다. (…) 플랫폼과
  거버넌스에 대한 교육은 지속적인 인에이블먼트 활동이 될 수 있다.**
- **데이터 전문가** — **데이터 전문가 — 데이터 엔지니어나 데이터 과학자 — 다수가 도메인 교차
  기능 팀에 합류할 것이다. 그들은 종단 결과를 전달하는 스트림 정렬 팀에서 일할 것이다.
  **그들은 더 이상 하나의 고립된 단계에서 일하지 않는다.** 이것은 소프트웨어 공학 실무·기술을
  써서 더 긴밀한 협업과 통합을 뜻한다. 교육 프로그램은 데이터 전문가가 코딩·테스팅·지속적 전달
  같은 소프트웨어 공학 실무를 배우도록 도와야 한다.**
- **플랫폼 엔지니어** — **데이터 인프라 엔지니어는 연산·운영 인프라 — 애플리케이션을 짓고
  호스팅하는 — 에 더 가까이 가야 하고, 연산 인프라 엔지니어는 데이터 인프라 지형을 더 잘 이해해야
  한다. 데이터 메시는 데이터 플랫폼과 애플리케이션 플랫폼의 매끄러운 통합을 요구한다.**

## 두 강제 함수

- **데이터 메시는 전문화되고 고립된 팀에서 교차 기능적이고 협업적인 팀으로의 이동을 껴안는다.
  그것은 또한 두 강제 함수(forcing functions)에 의존한다 — **플랫폼을 통해 데이터 전문화의
  수준을 낮추는 것**과 **데이터 리터러시의 수준을 높이는 것**이다. 이것은 다수인 제너럴리스트
  기술자 인구가 데이터 프로덕트와 솔루션에 능동적으로 기여하게 하려는 것이다. **조직은 이 두
  집단 사이의 지식 격차를 닫을 경력 경로를 설계해야 한다**** (16장, p.329).[^dehghani2022]
- 절의 제목이 그 요지다 — **유연한 조직은 유연한 사람을 요구한다(Flexible organizations
  require flexible people)** (16장, p.329).[^dehghani2022]
