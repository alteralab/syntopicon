KEY: cocoindex
--- SUMMARY ---
CocoIndex는 ex-Google 인프라 리드 Linghua Jin이 2024년 세운 2인 규모 SF 스타트업(Tracxn 기준 펀딩 없음)의 Apache-2.0 오픈소스로, Rust 코어 + Python SDK, 2025-03 공개 후 17개월간 stars 11.2k·릴리스 1–2주 주기로 매우 활발하다. 핵심 가치는 선언형 dataflow('Target = F(Source)')와 증분 처리(소스별 변경 감지 + 함수 memoization + 타깃 reconciliation)다. 사용자 결정에 중요한 사실 셋: (1) PostgreSQL 필수 의존은 옛말 — 2026-04 v1부터 내부 상태가 임베디드 LMDB로 바뀌어 pip 설치 + 로컬 파일만으로 돌고, live mode(상주)도 선택이라 배치 `cocoindex update`만으로 증분이 동작한다. 노트북 1인 운영 부담은 낮다. (2) 그러나 웹/URL 크롤러 소스가 없다 — dbt 문서 사이트를 직접 끌어오는 경로가 없어 git clone된 md/커스텀 소스를 직접 붙여야 하므로, 'docs 색인 레이어'의 어려운 절반(수집)은 cocoindex가 해결해주지 않는다. (3) v1이 출시 13개월 만의 breaking 재설계였고 회사가 2인·무펀딩이라, 10–20년 지평의 KB가 의존하기엔 API·존속 리스크가 있다. 결정 관점 정리: cocoindex의 강점(임베딩 재계산 절약형 증분 색인)은 '수백~수천 파일을 주기 재색인하며 임베딩 비용이 아플 때' 의미가 있는데, 사용자의 별도 레이어가 소량 문서라면 qmd 재색인이나 llms.txt/온디맨드 조회 대비 이득이 작다. 미확인 항목: 비공개 펀딩 여부(Tracxn 부재가 증명은 아님), Reddit의 실사용 불만(검색으로 유의미한 스레드 미발견), 대규모 프로덕션 채택 사례(자사 블로그 외 독립 후기 미발견), 릴리스 페이지의 v1.0.19 세부 변경 중 'SQLite schema preservation'이 내부 저장소와 어떤 관계인지(타깃 커넥터 버그픽스로 추정).

(3) 그러나 소비 측은 사실상 부재다: Google Mueller의 'no AI system currently uses llms.txt'(2025-06) 발언이 2026년의 서버 로그 실측(Evil Martians: 2개월간 AI 어시스턴트 fetch 37회뿐)과 cats.txt 반증 실험으로 재확인됐고, OpenAI·Anthropic·Google 누구도 프로덕션 소비를 확약하지 않았다. 실제 소비는 크롤러가 아니라 mcpdoc(MCP)·Context7·에이전트의 온디맨드 fetch에서 일어난다. (4) llms-full.txt는 대형 프로젝트에서 컨텍스트에 넣을 수 없는 크기다(직접 실측: Cloudflare 56.7MB≈11~14M 토큰, Anthropic 25.4MB, dbt 10.5MB≈2.6M 토큰) — 발행자인 Cloudflare조차 이를 '오프라인 인덱싱/벡터화 원료'로 규정하고 페이지 단위 Markdown+MCP로 이동 중이다. (5) 버전 구분 메커니즘은 스펙에 없고 확립된 사례도 없다(Expo 요청 이슈는 미구현 종결, Read the Docs는 기본 버전만). 사용자 결정에의 함의: dbt는 이미 llms.txt/llms-full.txt를 제공하므로 '온디맨드 조회(페이지 단위 fetch 또는 mcpdoc류 MCP)'가 별도 ingest 레이어 없이 즉시 가능한 반면, llms-full.txt를 통째로 쓰는 전략은 크기 때문에 성립하지 않으며, 버전 고정이 필요하면 llms.txt 생태계가 해결해주지 않으므로 그 요구가 강할 때만 cocoindex류 자체 인덱싱 레이어가 정당화된다. 미확인 사항: Perplexity가 llms.txt를 우선 참조한다는 주장은 SEO 블로그발 2차 인용만 있고 Perplexity 1차 문서로 확인하지 못했다. 'GPTBot이 llms.txt를 지시문으로 파싱한다'는 일부 SEO 글의 주장도 1차 근거를 찾지 못해 신뢰할 수 없다. 한 기사의 'Cloudflare llms-full.txt ≈ 3.7M 토큰' 수치는 직접 실측(56.7MB)과 모순되어 구식 수치로 판단된다. directory.llmstxt.cloud의 정확한 총 등재 수는 페이지네이션(21페이지, 수백 건 추정)만 확인했고 총계 숫자는 미확인이다. Expo 버전별 llms.txt 이슈의 종결 사유(구현 여부)도 미확인이다.

KEY: dbt-docs
--- SUMMARY ---
dbt 문서는 "빠르게 바뀌는 기술 문서"의 앵커 사례로서, 벤더가 이미 AI 소비 경로를 공식 다중화해 둔 상태다(2026-05 'The devil is in the docs' 블로그가 정본). 실측 확인: (1) llms.txt(222KB 인덱스)·llms-full.txt(10.4MB 전문)·페이지별 .md suffix 모두 라이브이며 매 빌드 재생성. (2) 공식 dbt-mcp는 search_product_docs/get_product_doc_pages로 문서 검색·원문 fetch를 네이티브 제공하고, 그 외 Semantic Layer·Discovery·CLI·Admin까지 노출하는 GA 제품(1.22.x, 2.0-beta 진행 중, 주간 릴리스). (3) 버전 정책상 EOL 버전은 문서 드롭다운에서 제거된다(현재 v2/v1/1.12/1.11만) — 다만 URL 대량 404 사례는 못 찾았고, 구버전 upgrade guide는 리다이렉트로 잔존한다. (4) 소스는 공개 레포(Apache-2.0, Docusaurus, /website 마크다운, default branch 'current')라 클론·로컬 색인이 법적·구조적으로 가능하지만, 최근 30일 커밋 100+건으로 스냅샷은 즉시 낡는다. (5) Context7가 이미 1.2M tokens를 14시간 주기 수준으로 신선하게 색인 중.

아키텍처 시사점: dbt 같은 문서는 KB에 박제할 이유가 약하다 — 공식 llms.txt+.md suffix+MCP 문서 검색이라는 온디맨드 경로가 성숙해 있고, 자체 색인(cocoindex류)을 만들면 100+커밋/월의 갱신을 따라가는 동기화 부채를 떠안는다. 별도 레이어가 필요하다면 "색인 사본"이 아니라 "조회 게이트웨이"(llms.txt 인덱스 → 페이지 .md fetch, 또는 dbt-mcp 원격 도구)로 충분하다는 방향을 지지하는 증거가 우세하다. 단, EOL 버전 문서가 사이트에서 사라지는 정책은 "특정 구버전 기준 지식을 보존해야 한다면 스냅샷이 필요하다"는 반대 방향 근거이기도 하다.

미확인 사항: (a) EOL 시 VersionBlock 콘텐츠가 소스에서 실제 삭제되는 구체 PR/커밋은 특정하지 못함(드롭다운 소멸만 실측). (b) 구버전 문서 URL이 실제 404로 사라진 구체 사례 미발견 — 조사 범위에선 리다이렉트 유지가 관찰됨. (c) dbt-mcp의 최초 릴리스 시점·1.0 도달 시점(릴리스 페이지가 최근 10건만 노출). (d) llms.txt 도입 정확 시점(블로그 발행일 2026-05-15 이전 여부). (e) 커뮤니티의 dbt 전용 .cursorrules 구체 사례는 일반 Cursor rules 관행 외 특정하지 못함. (f) Context7 수치(토큰·갱신 주기)는 자체 표시 기준으로 교차 검증 안 됨.

조사 결론: (1) 조사 대상 6개 중 dbt·React·Spark·Kafka 4개는 문서 소스가 GitHub 공개 저장소의 markdown/MDX로 관리되어 git clone + git pull이 곧 증분 미러가 되고, git diff가 가장 신뢰할 수 있는 변경 감지가 된다. 단 Airflow(rst+Sphinx)와 PostgreSQL(DocBook XML)은 git 미러는 되지만 마크다운화에 변환 단계가 필요하다 — "모든 문서가 markdown"은 성립하지 않는다. (2) dbt는 이미 docs.getdbt.com/llms.txt로 전체 문서 색인을 제공하므로, dbt에 한해서는 로컬 미러 없이 llms.txt+온디맨드 조회로 충분할 가능성이 높다. (3) 크롤이 필요한 소스에는 trafilatura(Apache-2.0, sitemap/피드 크롤+markdown 출력, API 키 불요)가 Firecrawl(AGPL 코어, 클라우드 API 중심)보다 개인 KB에 맞는 단순 대안이다. (4) 증분 색인은 cocoindex 없이도 가능: git 소스는 git pull 자체가 delta이고, 크롤 소스는 content hash 대조(kapa.ai 실무 패턴 — Last-Modified는 신뢰 불가)나 LlamaIndex docstore(doc_id+hash 기반 upsert/skip)로 충분하다. cocoindex는 Δ-only 재처리가 실제 메커니즘이지만 flow 정의 코드+내부 상태 db+타겟 스토리지라는 운영 표면이 생긴다. (5) PKM 관례(Zettelkasten literature/reference vs permanent 분리, Obsidian의 source-material-외부-보관)와 DDIA의 system of record vs derived data 프레임이 모두 같은 방향을 가리킨다: 빠르게 바뀌는 서드파티 문서는 재생성 가능한 cache 레이어(git 미러 + qmd 별도 컬렉션 색인)로 분리하고, 영구 위키(정본)와 백업·검증·보존 정책을 섞지 말 것. 미확인 사항: txtai의 SQLite 지원·증분 upsert 상세와 Haystack DocumentStore 중복 정책은 README 수준에서 확인 불가; cocoindex의 프로덕션 배포에서 Postgres가 필수인지(quickstart는 로컬 db 경로만 확인); Firecrawl/trafilatura로 특정 기술 문서 사이트를 장기 미러링한 구체적 공개 사례기(도구 능력만 확인, 사례 글은 미발견); Kafka KIP-1133의 정확한 채택 시점; "cache vs source of record"를 문서 레이어 설계에 명시적으로 적용한 단독 아키텍처 글(DDIA 일반 프레임 외 직접 사례 미발견).
