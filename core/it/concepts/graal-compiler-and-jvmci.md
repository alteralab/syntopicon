이 페이지의 질문: **자바로 작성된 컴파일러가 어떻게 핫스팟의 JIT 컴파일러 자리에 들어가며, 그
경계는 무엇으로 되어 있는가.**

## 버전 조건

> **버전 조건**: JDK 9 이상 JDK 15 이하 — **핫스팟 가상 머신에는 총 세 가지 JIT 컴파일러가
> 포함되어 있다** (11장, p.564).[^zhou2024] 실습 환경은 OpenJDK 17에 그랄 컴파일러를 따로
> 빌드해 얹은 것이다 (11장, p.567).

## 세 번째 컴파일러가 있던 자리

- 셋 중 마지막이 이 페이지의 주제다 — **지금까지는 그중 전통적인 클라이언트 컴파일러와 서버
  컴파일러를 중심으로 이야기했다. 세 번째는 바로 그랄 컴파일러를 활용한 jaotc 컴파일러다. 비록
  JDK 16부터는 jaotc가 사라졌지만 그랄 컴파일러는 그랄VM이라는 독립 프로젝트에서 발전을 이어 가고
  있다** (11장, p.564).[^zhou2024]
- 그것을 품은 가상 머신의 정체가 한 문장에 정리된다 — **그랄VM은 오라클이 자바 기술을 확장하여
  만든 새로운 가상 머신이다. 핫스팟 가상 머신을 토대로 고성능, 메모리 사용량 감소, 폴리글랏
  프로그래밍, AOT 네이티브 컴파일 등의 프리미엄 특징을 추가했다. 이번 절의 주인공인 그랄
  컴파일러는 JIT 컴파일과 AOT 컴파일을 모두 지원한다** (11장, p.564).[^zhou2024] 제품으로서의
  그랄VM은 [그랄VM과 네이티브 이미지](../concepts/graalvm-and-native-image.md)에 있다.

## 맥신에서 갈라져 나온 내력

- 자바로 쓰인 것이 우연이 아니다 — **초기에 그랄VM과 그랄 컴파일러는 핫스팟을 대체하거나 차세대
  핫스팟 기술의 기초가 되리라는 기대를 받았다. 그랄 컴파일러는 원래 맥신 가상 머신의 C1X
  컴파일러를 대체할 차세대 컴파일러로 설계되었기 때문에 자연스럽게 자바 언어로 작성되었다. 그러다가
  2012년에 맥신 프로젝트에서 분리되어 독립적인 자바 컴파일러 프로젝트가 되었다** (11장,
  p.565).[^zhou2024] **C1X는 핫스팟의 C1 컴파일러에 대응하는 맥신 가상 머신용 컴파일러다**
  (11장, p.565, 각주 23). 맥신 자체는
  [자바 가상 머신 제품군](../concepts/java-virtual-machine-family.md)에 있다.
- 오라클이 건 기대가 네 항목이다 — **오라클은 그랄 컴파일러가 궁극적으로 높은 컴파일 효율과 출력
  품질, AOT와 JIT 컴파일 지원, 핫스팟을 포함한 다양한 가상 머신 지원 등의 특성을 갖춘 컴파일러가
  되기를 희망했다** (11장, p.565).[^zhou2024]
- 자바로 쓰였다는 사실 자체가 이점으로 꼽힌다 — **그랄 컴파일러는 자바로 작성되었기 때문에 코드가
  명확하고 핫스팟 서버 컴파일러의 다양한 고급 최적화 기술을 가져와 쓸 수 있었다. 그래서 수많은
  회사와 연구소에서 이 컴파일러를 기반으로 새로운 컴파일 기술을 개발하고 연구하고 있다** (11장,
  p.565).[^zhou2024]

## C2를 대체하라는 요구

- 증언이 둘 실려 있다 — **핫스팟 서버 컴파일러의 창시자인 클리프 클릭(Cliff Click)은 그랄
  컴파일러를 매우 높게 평가하며 "앞으로 가상 머신과 컴파일러를 구현할 때 C/C++를 다시는 사용하지
  않을 것이다"라고 말했다. 트위터의 자바 가상 머신 팀은 C2는 기능을 추가하거나 개선하기가 너무
  어려워서 시급히 대체되어야 한다고 말하기도 했다** (11장, p.565).[^zhou2024]
- 탑재 경로가 두 단계였다 — **그랄 컴파일러는 'jaotc 고급 컴파일 도구'라는 이름으로 JDK 9에
  최초로 공식 탑재되었다. 그리고 JDK 10부터는 서버 컴파일러 대신 핫스팟의 계층형 컴파일 중 최상위
  JIT 컴파일러로 사용할 수 있었다** (11장, p.565).[^zhou2024] 그 계층 구조는
  [JIT 컴파일러와 계층형 컴파일](../concepts/jit-compilers-and-tiered-compilation.md)에 있다.
- 지금은 다시 돌아오려 하고 있다 — **현재는 jaotc가 JDK에서 제거된 상태지만, 2022년 말에는 그랄
  컴파일러를 다시 OpenJDK로 통합하려는 갤러해드(Galahad) 프로젝트가 제안되었다** (11장,
  p.566).[^zhou2024] 그 제안의 우선순위도 적혀 있다 — **우선은 그랄VM의 JIT 컴파일러를 가져와
  C2 컴파일러를 대체하는 데 중점을 두고, AOT 기술 도입의 우선순위는 그다음이다** (11장, p.566,
  각주 25).

## JVMCI — 컴파일러를 갈아 끼우는 인터페이스

- 교체가 가능해진 이유가 인터페이스에 있다 — **이처럼 JIT 컴파일러를 대체할 수 있던 이유는
  핫스팟의 JIT 컴파일러 인터페이스 덕분이다** (11장, p.565).[^zhou2024]
- 그전에는 붙어 있었다 — **그랄도 초기에는 C1이나 C2와 마찬가지로 핫스팟과 긴밀하게 연결되어
  있어서 그랄을 컴파일할 때마다 핫스팟 전체를 다시 컴파일해야 했다. 하지만 JDK 9에 포함된
  컴파일러 인터페이스(JVMCI) 덕분에 핫스팟 코드로부터 분리할 수 있었다** (11장,
  p.566).[^zhou2024] 근거 문서는 **JEP 243: Java-Level JVM Compiler Interface(JVMCI)** 다
  (11장, p.566, 각주 24).
  - 버전 조건: JDK 9 이상 — JVMCI가 표준 JDK에 들어온 시점이다.
- 제공하는 기능이 셋이다 (11장, p.566):[^zhou2024]

  | 기능 | 무엇 |
  |---|---|
  | 요청 전달 | **핫스팟 가상 머신의 컴파일 요청에 응답하고, 요청을 자바로 구현된 JIT 컴파일러에 전달한다** |
  | 데이터 노출 | **클래스, 메서드, 필드, 성능 모니터링 정보 등 핫스팟 JIT 컴파일 관련 데이터를 자바 언어 수준의 데이터 구조로 제공한다** |
  | 결과 배포 | **핫스팟 코드 캐시를 추상화하여 컴파일러가 컴파일이 끝난 네이티브 코드를 배포할 수 있게 한다** |

  - 셋을 합치면 컴파일러가 통째로 갈린다 — **이상의 세 기능 덕분에 핫스팟 가상 머신 외부에서 자바
    언어로 구현한 JIT 컴파일러를 핫스팟에 통합할 수 있다. 예를 들어 핫스팟에서 발생한 최상위 컴파일
    요청을 받아 컴파일을 수행하고, 그 결과로 나온 네이티브 코드를 핫스팟 코드 캐시에 배포할 수
    있다** (11장, p.566).
  - 셋째 기능만 쓰면 AOT가 된다 — **또한 세 번째 기능만 사용하면 핫스팟의 JIT 컴파일러를 우회하여
    외부 컴파일러가 애플리케이션의 클래스 라이브러리를 네이티브 코드로 직접 컴파일하거나
    (jaotc처럼) AOT 컴파일러로도 사용할 수 있다** (11장, p.566). 그 실물은
    [jaotc로 미리 컴파일해 보기](../concepts/jaotc-ahead-of-time-compilation.md)에 있다.
- 저자가 매기는 이 기술의 값은 실무보다 학습 쪽이다 — **그랄과 JVMCI의 등장이 자바 가상 머신과
  컴파일러 개발에 직접적으로 기여하지는 않지만, 자바 가상 머신 기술이 궁금한 개발자들에게 컴파일러
  기술을 엿보고 사용해 볼 수 있는 멋진 수단을 제공한다** (11장, p.566).[^zhou2024]
  다른 확장 인터페이스들과의 관계는
  [핫스팟의 모듈화와 확장 인터페이스](../concepts/hotspot-modularity-and-interfaces.md)에 있다.

## 빌드와 실행 환경

- 전용 빌드 도구가 있다 — **그랄 컴파일러 실습 환경을 갖추려면 빌드 도구인 mx부터 설치해야 한다.
  그랄 컴파일러는 그랄VM의 다양한 하위 프로젝트뿐 아니라 핫스팟과 맥신 가상 머신의 JIT
  컴파일까지, 지원해야 할 게 너무 많아서 빌드 자동화 도구를 직접 제작했다** (11장,
  pp.566–567).[^zhou2024] **방법은 아주 간단하다. 깃 저장소에서 mx를 가져온 후 어디서든 접근할
  수 있게 `PATH` 환경 변수에 추가하면 끝이다** (11장, p.567).
- 필요한 JDK가 시기마다 달랐다 — **초기 그랄VM 프로젝트는 OpenJDK 8로 개발되었고, JVMCI
  인터페이스는 JDK 9 때 추가되었다. 그래서 그랄 팀은 OpenJDK 8에서 JVMCI 기능을 이용할 수 있는
  버전을 제공했다. 하지만 지금은 엔터프라이즈 버전만이 오라클 JDK 8을 지원하며, 커뮤니티 버전은
  OpenJDK 11 이상의 LTS 버전이나 최신 버전을 요구한다** (11장, p.567).[^zhou2024]
- 전체 절차는 명령 몇 줄이다 (11장, pp.567–568):[^zhou2024]

  ```sh
  git clone https://github.com/graalvm/mx.git
  export PATH=$PWD/mx:$PATH

  export JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64/

  git clone https://github.com/graalvm/graal.git   # 그랄VM 코드 전체, 약 700MB
  cd graal/compiler
  mx build

  mx vm -version   # OpenJDK 64-Bit Server VM GraalVM CE 17.0.6-dev+10.1 (…, mixed mode, sharing)
  ```

  - 수동으로 챙길 의존성이 하나뿐이다 — **컴파일 과정에서 수동으로 처리해야 하는 의존성은 다행히
    이 변수 설정뿐이다** (11장, p.567). **전체 빌드 과정에 필요한 의존성들은 자동으로 처리되므로
    OpenJDK만 수동으로 처리하면 된다. 그 덕분에 컴파일은 일반적으로 몇 분 정도면 완료될 것이다**
    (11장, p.567).
  - 통합 개발 환경 프로젝트도 도구가 만들어 준다 — **mx 도구는 주요 자바 통합 개발 환경인
    이클립스·IntelliJ IDEA·넷빈즈용 프로젝트를 생성할 수 있다** (11장, p.568). 명령은 각각
    `mx eclipseinit`, **`mx intellijinit`**, **`mx netbeansinit`** 이고 **한 번에 세 가지 통합
    개발 환경용 프로젝트를 모두 생성하려면 `mx ideinit` 명령을 이용**한다 (11장, p.568, 옮긴이
    각주 27).

## 인터페이스를 직접 설계해 본다면

- 저자가 독자에게 사고 실험을 시킨다 — **JVMCI는 자바 언어로 만드는 컴파일러 인터페이스를
  추구하기 때문에 우리가 수없이 보아 온 자바 인터페이스들과 다르지 않다** (11장,
  p.570).[^zhou2024] 입력과 출력이 각각 하나로 정해진다 — **JIT 컴파일러가 받아야 할 입력이
  무엇인지 생각해 보자. 답은 물론 컴파일할 메서드의 바이트코드다. (…) JIT 컴파일러는 입력받은
  메서드에 해당하는 네이티브 코드를 출력해야 하며, 이 역시 '바이트 배열로 표현되는 코드'여야
  한다** (11장, p.570). 그래서 최소 형태는 이렇게 된다:

  ```java
  interface JVMCICompiler {
      byte[] compileMethod(byte[] bytecode);
  }
  ```

- 실제는 더 복잡하고, 그 이유가 핫스팟이 주는 정보의 양이다 — **핫스팟은 바이트코드 외에도
  메서드에 대한 다양한 정보를 컴파일러에 제공하기 때문에 실제 JVMCI 인터페이스는 이보다는
  복잡하다. 예를 들어 지역 변수 테이블의 변수 슬롯 수, 피연산자 스택의 최대 깊이, 계층형 컴파일의
  최하단 계층에서 수집한 통계 등을 추가로 알려 준다** (11장, pp.570–571):[^zhou2024]

  ```java
  interface JVMCICompiler {
      void compileMethod(CompilationRequest request);
  }

  interface CompilationRequest {
      JavaMethod getMethod();
  }

  interface JavaMethod {
      byte[] getCode();
      int getMaxLocals();
      int getMaxStackSize();
      ProfilingInfo getProfilingInfo();
      // ... 다른 메서드 생략
  }
  ```

  - 그 두 값이 어디서 오는지는
    [클래스 파일의 Code 속성](../concepts/class-file-code-attribute.md)과
    [런타임 스택 프레임 구조](../concepts/stack-frame-structure.md)에 있다.

## 진입점을 찾아 확인하기

- 구현 클래스가 분석의 출발점이다 — **이클립스에서 `JVMCICompiler` 인터페이스의 계층 구조를
  확인해 보자. 그러면 (…) `HotSpotGraalCompiler` 클래스가 이를 구현했음을 알 수 있다. 이 클래스가
  우리가 분석하려는 코드의 진입점이다** (11장, p.571).[^zhou2024] 위치는
  **`jdk.internal.vm.compiler` 프로젝트의 `org.graalvm.compiler.hotspot` 패키지**다 (11장,
  p.573, 각주 29).
- 컴파일을 촉발시킬 코드도 준비된다 (11장, pp.571–572, 코드 11-11):[^zhou2024]

  ```java
  public class Demo {
      public static void main(String[] args) {
          while (true) {          // JIT 컴파일을 촉발하기 위한 무한 루프
              workload(14, 2);
          }
      }

      private static int workload(int a, int b) {
          return (a + b) / 3;
      }
  }
  ```

  - 대상을 좁히는 이유가 잡음이다 — **이 간단한 코드로 인해 `workload()` 말고도 꽤 많은 메서드가
    컴파일된다. 정말 간단한 자바 클래스 하나를 로딩해 실행하는 데에도 수백 개의 다른 클래스가
    로딩될 수 있기 때문이다. 그러니 너무 많은 정보가 섞여 들어오지 않도록 컴파일 대상을
    `workload()` 메서드로 제한하자. `-XX:CompileOnly` 매개 변수를 이용하면 된다** (11장, p.572).
- 먼저 핫스팟 기본 컴파일러로 확인한다 (11장, p.572):[^zhou2024]

  ```sh
  javac Demo.java
  java -XX:+PrintCompilation -XX:CompileOnly=Demo::workload Demo
  ```

  - 출력이 앞 절의 결론을 재확인해 준다 — **핫스팟 컴파일러는 계층형 구조이기 때문에
    `workload()`가 여러 번 컴파일되고 있음을 알 수 있다. (…) 'made not entrant'는 컴파일된 버전이
    삭제되었다는 뜻이다. 이 정보로부터 계층형 컴파일 메커니즘과 최상위 서버 컴파일러가 제대로
    작동하고 있음을 확인할 수 있다** (11장, p.572). 그 출력의 열 구조는
    [핫스팟 JIT 코드 들여다보기](../concepts/hotspot-jit-inspection-tools.md)에 있다.
- 컴파일러를 그랄로 바꾸면 로그가 넘친다 — **이번에는 메시지가 너무 많이 출력되어 원하는 정보를
  찾기 어려울 것이다. `-XX:-TieredCompilation` 매개 변수로 계층형 컴파일을 끄고, 결과 로그는
  파일로 기록해서 살펴보자** (11장, p.572).[^zhou2024] 계층형을 껐으므로 **컴파일이 한 번만
  되었음을 알 수 있을 것이다. 무언가 바뀐 건 분명하다. 하지만 이것만으로는 그랄 컴파일러가 동작한
  것인지는 확신하기 어렵다** (11장, p.573).
- 그래서 컴파일러 자체를 고쳐 확인한다 — `HotSpotGraalCompiler`의 `compileMethod()`에 컴파일된
  메서드 이름과 소요 시간을 출력하는 코드를 끼워 넣고 `mx build`로 다시 빌드한 뒤 실행하면
  **`compile method: workload`** 와 **`time used: 872`** 가 찍힌다 (11장,
  p.573).[^zhou2024] 자바로 쓰인 컴파일러를 자바 코드 고치듯 고쳐 볼 수 있다는 것이 이 절의
  실질적인 논점이다.
