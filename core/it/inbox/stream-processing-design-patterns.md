하나의 질문: **스트림 처리 애플리케이션을 조립하는 알려진 꼴에는 무엇이 있는가.**

- **모든 스트림 처리 시스템은 서로 다르다** — **컨슈머·처리 로직·프로듀서를 엮은 기본
  조합에서부터 기계 학습 라이브러리를 갖춘 스파크 스트리밍 같은 복잡한 클러스터까지,
  그리고 그 사이의 많은 것들.** **그러나 스트림 처리 아키텍처의 흔한 요구에 대한 알려진
  해법인 기본 설계 패턴이 몇 가지 있다** (14장, p.392).[^shapira2021]

## 단일 이벤트 처리

- **스트림 처리의 가장 기본적인 패턴은 각 이벤트를 고립시켜 처리하는 것**이다. **스트림에서
  불필요한 이벤트를 걸러 내거나 각 이벤트를 변환하는 데 흔히 쓰이므로 맵/필터(map/filter)
  패턴이라고도 불린다.** **맵이라는 용어는 맵 단계가 이벤트를 변환하고 리듀스 단계가 그것을
  집계하는 맵리듀스 패턴에서 온 것**이다 (14장, p.392).[^shapira2021]
- **이 패턴에서 스트림 처리 앱은 스트림에서 이벤트를 소비하고 각 이벤트를 수정한 뒤 다른
  스트림으로 이벤트를 생산**한다. 예로 **스트림에서 로그 메시지를 읽어 ERROR 이벤트는
  고우선순위 스트림에, 나머지는 저우선순위 스트림에 쓰는 앱**과 **스트림에서 이벤트를 읽어
  JSON에서 에이브로로 바꾸는 애플리케이션**을 든다 (14장, p.392).[^shapira2021]
- 이 패턴의 이득 — **각 이벤트가 독립적으로 다뤄질 수 있으므로 애플리케이션 안에 상태를
  유지할 필요가 없다.** 그래서 **앱 장애에서 복구하거나 부하를 분산하는 것이 엄청나게
  쉽다 — 상태를 복구할 필요 없이 그냥 이벤트를 앱의 다른 인스턴스에 넘겨 처리**하면 된다.
  **이 패턴은 단순한 프로듀서와 컨슈머로 쉽게 처리할 수 있다** (14장,
  pp.392–393).[^shapira2021]
  - 커넥트 안에서 코드 없이 같은 일을 하는 자리가
    [단일 메시지 변환(SMT)](../concepts/kafka-single-message-transformations.md)이다.

## 로컬 상태를 쓰는 처리

- **대부분의 스트림 처리 애플리케이션은 정보의 집계, 특히 윈도우 집계에 관심**을 둔다.
  예는 **거래일마다 주식의 최저·최고가를 찾고 이동 평균을 계산하는 것**이다. **이런
  집계는 상태 유지를 요구한다** — 최저가와 평균가를 계산하려면 **최솟값·합계·현재까지 본
  레코드 수를 저장**해야 한다 (14장, p.393).[^shapira2021]
- **이 모든 것이 (공유 상태가 아니라) 로컬 상태로 가능한 이유는 예의 모든 연산이 그룹별
  집계(group by aggregate)이기 때문**이다 — **주식 종목별로 집계하지 전체 주식 시장에
  대해 집계하지 않는다.** **카프카 파티셔너를 써서 같은 종목 기호의 모든 이벤트가 같은
  파티션에 쓰이게** 하면, **애플리케이션의 각 인스턴스는 자기에게 배정된 파티션의 모든
  이벤트를 받으므로(이것이 카프카 컨슈머의 보장이다) 자기 파티션에 쓰인 종목 부분집합에
  대한 상태를 유지할 수 있다** (14장, p.393).[^shapira2021] 키가 파티션을 결정하는 규칙은
  [프로듀서 파티션 배분](../concepts/kafka-producer-partitioning.md).
- 대가가 있다 — **애플리케이션이 로컬 상태를 가지면 스트림 처리 애플리케이션은 상당히 더
  복잡해지고** 메모리·지속성·리밸런싱 세 문제를 다뤄야 한다 (14장,
  pp.394–395).[^shapira2021] 그 셋은
  [스트림 처리의 상태](../concepts/stream-processing-state.md)가 담당한다.

## 다단계 처리와 리파티셔닝

- **로컬 상태는 그룹별 집계에는 훌륭하지만, 가용한 정보 전체를 쓰는 결과가 필요하면
  어떻게 하는가.** 책의 예는 **거래일마다 개장에서 폐장까지 가장 많이 오른 주식 10개를
  발행하는 것**이다. **상위 10개가 모두 다른 인스턴스에 배정된 파티션에 있을 수 있으므로
  각 인스턴스에서 로컬로 하는 어떤 일도 충분하지 않다** (14장, p.395).[^shapira2021]
- **필요한 것은 2단계 접근**이다 — **먼저 종목 기호별 일간 등락을 계산한다. 이것은 각
  인스턴스에서 로컬 상태로 할 수 있다. 그다음 결과를 파티션이 하나뿐인 새 토픽에 쓴다. 이
  파티션은 단일 애플리케이션 인스턴스가 읽고, 그 인스턴스가 그날의 상위 10개 주식을 찾을
  수 있다** (14장, p.395).[^shapira2021]
- 그것이 성립하는 이유 — **종목별 일간 요약만 담는 둘째 토픽은 거래 자체를 담는 토픽보다
  훨씬 작고 트래픽도 훨씬 적으므로 애플리케이션의 단일 인스턴스로 처리할 수 있다.** 때로는
  **결과를 내기 위해 더 많은 단계가 필요**하다 (14장, p.395).[^shapira2021]
- **이런 다단계 처리는 맵리듀스 코드를 쓰는 사람에게 매우 익숙하다** — 거기서는 **흔히
  여러 리듀스 단계에 의지해야 하고 리듀스 단계마다 별도의 앱이 필요했다.** **맵리듀스와
  달리 대부분의 스트림 처리 프레임워크는 모든 단계를 하나의 앱에 포함시킬 수 있게 하고,
  어느 애플리케이션 인스턴스(혹은 워커)가 각 단계를 실행할지는 프레임워크가 처리**한다
  (14장, p.395).[^shapira2021]

## 비순차 이벤트

- **스트림에 잘못된 시각에 도착하는 이벤트를 다루는 것은 스트림 처리만이 아니라 전통적인
  ETL 시스템에서도 도전 과제**다. **비순차(out-of-sequence) 이벤트는 사물 인터넷
  시나리오에서 꽤 자주, 그리고 예상대로 일어난다** — **모바일 기기가 몇 시간 와이파이
  신호를 잃었다가 재접속하며 몇 시간치 이벤트를 보내는 경우**다. **네트워크 장비 모니터링
  (고장 난 스위치가 수리될 때까지 진단 신호를 보내지 않는다)이나 제조(공장의 네트워크
  연결은 특히 개발도상국에서 악명 높게 불안정하다)에서도 일어난다** (14장,
  p.399).[^shapira2021]
  - 웨어하우스 ETL 쪽에서 같은 문제를 어떻게 다루는지는
    [지각 도착 데이터](../concepts/late-arriving-data.md)에 있다 — 거기서는 팩트가 늦으면
    **그때 유효했던 차원 키**를 찾는 것이 규칙이다.
- 스트림 애플리케이션이 해야 하는 일 넷 (14장, pp.399–400):[^shapira2021]
  - **이벤트가 순서에서 벗어났음을 인지한다** — **애플리케이션이 이벤트 시간을 살펴 그것이
    현재 시각보다 오래됐음을 발견해야** 한다.
  - **비순차 이벤트를 화해시키려 시도할 기간을 정의한다** — **세 시간 지연은 화해시키고
    세 주 넘은 이벤트는 버릴 수 있다.**
  - **이 이벤트를 화해시킬 인밴드(in-band) 능력을 갖는다.** 이것이 **스트리밍 앱과 배치
    잡의 주된 차이**다 — **일 단위 배치 잡이 있고 잡이 끝난 뒤 이벤트 몇 개가 도착했다면
    보통 어제 잡을 다시 돌려 이벤트를 갱신하면 된다. 스트림 처리에는 "어제 잡 다시 돌리기"가
    없다 — 같은 연속 프로세스가 언제든 옛 이벤트와 새 이벤트를 모두 다뤄야 한다.**
  - **결과를 갱신할 수 있어야 한다.** **스트림 처리 결과가 데이터베이스에 쓰인다면 put이나
    update로 충분하지만, 스트림 앱이 결과를 메일로 보낸다면 갱신이 더 까다로울 수 있다.**
- **구글의 데이터플로와 카프카 스트림즈를 비롯한 여러 프레임워크는 처리 시간과 독립적인
  이벤트 시간 관념을 내장 지원하고, 현재 처리 시간보다 오래되거나 새로운 이벤트 시간을
  가진 이벤트를 다룰 수 있다.** 구현 방식은 **로컬 상태에 갱신 가능한 집계 윈도우 여럿을
  유지하고 그 윈도우 집계를 얼마나 오래 갱신 가능하게 둘지를 개발자가 설정하게 하는 것**이다.
  **물론 집계 윈도우를 오래 갱신 가능하게 둘수록 로컬 상태 유지에 더 많은 메모리가
  필요**하다 (14장, p.400).[^shapira2021]
- **카프카 스트림즈 API는 언제나 집계 결과를 결과 토픽에 쓴다. 그 토픽들은 대개 압착된
  토픽이라 키별로 최신 값만 보존된다. 늦은 이벤트 때문에 집계 윈도우 결과를 갱신해야 하면
  카프카 스트림즈는 그냥 그 집계 윈도우에 대한 새 결과를 써서 이전 결과를 사실상 대체**한다
  (14장, p.400).[^shapira2021]

## 재처리

- **마지막 중요한 패턴은 이벤트의 재처리**이고 변종이 둘이다 (14장,
  pp.400–401):[^shapira2021]
  - **스트림 처리 애플리케이션의 개선된 버전이 있고, 새 버전을 옛 버전과 같은 이벤트
    스트림에 대해 돌려 첫 버전을 대체하지 않는 새 결과 스트림을 만들고, 두 버전의 결과를
    비교한 뒤 어느 시점에 클라이언트를 새 결과로 옮기고 싶은 경우.**
  - **기존 스트림 처리 앱에 버그가 있어서 버그를 고치고 이벤트 스트림을 재처리해 결과를
    다시 계산하고 싶은 경우.**
- **첫째 유스케이스는 아파치 카프카가 이벤트 스트림 전체를 오랫동안 확장 가능한 데이터
  저장소에 저장한다는 사실 덕분에 단순**해진다. **두 버전의 앱이 두 결과 스트림을 쓰게
  하려면 이것만 하면 된다** (14장, p.400):[^shapira2021]
  - **새 버전의 애플리케이션을 새 컨슈머 그룹으로 띄운다.**
  - **새 버전이 입력 토픽의 첫 오프셋부터 처리를 시작하도록 설정한다**(그래야 입력
    스트림의 모든 이벤트에 대한 자기 사본을 얻는다).
  - **새 애플리케이션이 계속 처리하게 두고, 처리 잡의 새 버전이 따라잡았을 때 클라이언트
    애플리케이션을 새 결과 스트림으로 전환한다.**
- **둘째 유스케이스는 더 까다롭다** — **기존 앱을 "리셋"해 입력 스트림의 처음부터 다시
  처리하게 하고, 로컬 상태를 리셋하고(두 버전의 결과가 섞이지 않도록), 어쩌면 이전 출력
  스트림도 청소해야 한다.** **카프카 스트림즈에 스트림 처리 앱의 상태를 리셋하는 도구가
  있지만, 저자들의 권고는 앱 사본 두 개를 돌리고 결과 스트림 두 개를 만들 용량이 있는
  한 언제나 첫 방법을 쓰라는 것**이다 — **첫 방법이 훨씬 안전하다. 여러 버전 사이를
  오갈 수 있게 해 주고 버전 간 결과 비교를 허용하며, 청소 과정에서 결정적 데이터를 잃거나
  오류를 끌어들일 위험이 없다** (14장, p.401).[^shapira2021]
  - 웨어하우스 쪽에서 로직이 바뀌었을 때 하는 같은 판단이
    [증분 처리와 그 대가](../concepts/incremental-processing-tradeoffs.md)의 전체
    재구축(full refresh)이다. 다만 그쪽은 대상 테이블을 지우고 다시 만드는 쪽이 기본이고,
    이쪽은 **지우지 않고 나란히 돌리는 쪽**을 권한다 — 재생 가능한 원본 스트림이 있기
    때문이다.

## 조인과 대화형 질의는 어디에 있는가

- 책이 이 절에서 함께 다루는 나머지 패턴 넷은 다른 페이지가 갖고 있다. **외부 조회를
  쓰는 처리(스트림-테이블 조인)·테이블-테이블 조인·스트리밍 조인**은
  [스트림-테이블 이중성과 조인](../concepts/stream-table-duality.md)에, **대화형 질의**는
  [스트림 처리의 상태](../concepts/stream-processing-state.md)에 있다 — 각각 이중성과
  상태라는 전제 위에 서기 때문이다.
