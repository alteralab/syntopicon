## 버전 조건

> **버전 조건**: RFC 9110(2022-06, STD 97) 기준. 2026-09-07 시점 이를 갱신하거나 폐기하는
> RFC 없음(datatracker 실측).

## 세 종류의 중개자

- HTTP는 연결의 사슬을 통해 요청을 충족시키도록 중개자(intermediary)의 사용을 허용한다. 흔한
  형태가 셋이다 — 프록시(proxy), 게이트웨이(gateway), 터널(tunnel)
  (§3.7).[^fielding2022-rfc9110]
- **이것은 프로그램의 분류가 아니라 요청마다의 역할이다.** 중개자 하나가 요청의 성질에 따라
  원 서버로도, 프록시로도, 게이트웨이로도, 터널로도 행동을 바꿔 가며 동작할 수 있다
  (§3.7).[^fielding2022-rfc9110]
- 사슬의 모양은 이렇다. 사용자 에이전트와 원 서버 사이에 중개자 셋이 있으면 사슬 전체를 지나는
  메시지 하나가 **네 개의 별도 연결**을 통과한다. 어떤 HTTP 통신 옵션은 가장 가까운 비터널
  이웃과의 연결에만, 어떤 것은 사슬의 양 끝점에만, 어떤 것은 사슬의 모든 연결에 적용된다
  (§3.7).[^fielding2022-rfc9110]
- 그림이 선형이라고 해서 참여자가 한 줄로 서 있는 것은 아니다. 각 참여자가 동시에 여러 통신에
  관여할 수 있고, 이후의 요청은 흔히 부하 분산을 위한 동적 설정에 따라 다른 연결 경로로 갈 수
  있다 (§3.7).[^fielding2022-rfc9110]

## 방향을 가리키는 네 낱말

- 상류(upstream)와 하류(downstream)는 **메시지 흐름**에 대한 방향 요건을 서술한다. 모든 메시지는
  상류에서 하류로 흐른다 (§3.7).[^fielding2022-rfc9110]
- 인바운드(inbound)와 아웃바운드(outbound)는 **요청 경로**에 대한 방향 요건을 서술한다. 인바운드는
  "원 서버 쪽으로", 아웃바운드는 "사용자 에이전트 쪽으로"를 뜻한다 (§3.7).[^fielding2022-rfc9110]
- 두 짝이 다른 축이라는 점이 요건을 읽을 때의 핵심이다. 응답 메시지도 상류에서 하류로 흐르지만
  그 이동은 아웃바운드다.

## 프록시

- 프록시는 **클라이언트가 고른** 메시지 전달 에이전트다. 대개 로컬 설정 규칙으로 골라지고, 어떤
  종류의 절대 URI에 대한 요청을 받아 HTTP 인터페이스를 통한 변환으로 그 요청을 충족시키려 시도한다
  (§3.7).[^fielding2022-rfc9110] **누가 고르는가가 프록시의 정의에 들어 있다.**
- 변환의 폭이 넓다. "http" URI에 대한 프록시 요청처럼 최소한인 것도 있고, 전혀 다른 애플리케이션
  계층 프로토콜과의 상호 변환을 요구하는 것도 있다 (§3.7).[^fielding2022-rfc9110]
- 프록시가 쓰이는 자리는 흔히 한 조직의 HTTP 요청을 공통 중개자로 모으는 것이고, 목적은 보안
  서비스나 주석 서비스나 공유 캐싱이다 (§3.7).[^fielding2022-rfc9110]

## 게이트웨이

- 게이트웨이(리버스 프록시라고도 한다)는 **아웃바운드 연결에서는 원 서버로 행동하지만** 받은 요청을
  변환해 인바운드로 다른 서버 하나 이상에 전달하는 중개자다 (§3.7).[^fielding2022-rfc9110]
- 쓰이는 자리가 셋으로 열거된다 — 레거시나 신뢰할 수 없는 정보 서비스를 감싸는 것, "가속기"
  캐싱으로 서버 성능을 올리는 것, HTTP 서비스를 여러 기계에 분할하거나 부하 분산하는 것
  (§3.7).[^fielding2022-rfc9110]
- 요건의 상속 규칙이 명시된다. **원 서버에 적용되는 모든 HTTP 요건이 게이트웨이의 아웃바운드
  통신에도 적용된다.** 게이트웨이는 인바운드 서버와는 원하는 아무 프로토콜로나 통신할 수 있고
  여기에는 이 명세 밖의 사설 HTTP 확장도 든다. 다만 서드파티 HTTP 서버와 상호운용하려는
  HTTP 대 HTTP 게이트웨이는 자기 인바운드 연결에서 사용자 에이전트 요건을 지켜야 한다
  (§3.7).[^fielding2022-rfc9110]

## 터널

- 터널은 **메시지를 바꾸지 않고 두 연결 사이를 잇는 눈먼 중계**다. 활성화되고 나면 터널은 HTTP
  통신의 당사자로 간주되지 않으며, 다만 그 터널이 HTTP 요청으로 개시됐을 수는 있다
  (§3.7).[^fielding2022-rfc9110]
- 터널은 중계되는 연결의 양 끝이 모두 닫힐 때 존재하기를 멈춘다 (§3.7).[^fielding2022-rfc9110]
- 쓰이는 자리는 중개자를 통과하는 가상 연결을 늘리는 것이다. 원전이 드는 예가 공유된 방화벽
  프록시를 통해 기밀 통신을 세우려고 TLS를 쓰는 경우다 (§3.7).[^fielding2022-rfc9110]

## 프로토콜 참여자가 아닌 중개자

- 위 분류는 **HTTP 통신의 참여자로 행동하는** 것만 다룬다. 그 밖에 네트워크 프로토콜 스택의 더
  낮은 계층에서 행동하며 메시지 송신자의 인지나 허락 없이 HTTP 트래픽을 걸러 내거나 우회시키는
  중개자도 있다 (§3.7).[^fielding2022-rfc9110]
- 이 문서가 그것에 내리는 판정이 강하다. **네트워크 중개자는 프로토콜 수준에서 경로상
  공격자(on-path attacker)와 구분되지 않으며**, HTTP 의미론을 잘못 어김으로써 보안 결함이나
  상호운용성 문제를 들여오는 일이 잦다 (§3.7).[^fielding2022-rfc9110]
- 예로 드는 것이 가로채기 프록시(interception proxy, 흔히 투명 프록시라고도 한다)다. **HTTP
  프록시와 다른 점은 클라이언트가 고르지 않는다는 것**이고, 대신 나가는 TCP 80번 포트 패킷
  (그리고 이따금 다른 흔한 포트의 트래픽)을 걸러 내거나 우회시킨다 (§3.7).[^fielding2022-rfc9110]
- 그것이 흔히 놓이는 자리는 공용 네트워크 접속점(비로컬 인터넷 서비스 사용 전에 계정 가입을
  강제하는 수단)과 회사 방화벽 안(네트워크 사용 정책의 집행)이다 (§3.7).[^fielding2022-rfc9110]

## 그것들이 프로토콜의 진화도 막는다

이 절만 다른 소스에서 왔다. 위 절이 보안과 상호운용성의 해를 적는다면, 여기는 같은 행위자가
프로토콜의 **진화**에 미치는 해를 적는다.

- 이 소스는 더 넓은 범주 이름을 쓴다. **미들박스(middlebox)는 IP 라우터의 기능이 아닌 기능을
  수행하는 모든 중개 장치**이고, 드는 예가 NAT와 방화벽과 로드 밸런서와 침입 탐지·방지 시스템과
  CDN 캐시다 (4장, p.135 각주).[^dynowski2025]
  - 이 범주는 위 세 종류의 분류보다 넓다. RFC 9110이 가르는 프록시·게이트웨이·터널은 HTTP 통신의
    참여자이고, 미들박스에는 참여자가 아닌 것이 대부분 든다.
- 관찰된 해가 둘이다. **어떤 미들박스는 인식하지 못한 트래픽을 막거나 HTTP나 TCP 헤더 같은
  메타데이터를 고쳐서 새 프로토콜 판을 깨뜨린다. 미들박스와 운영체제가 새 프로토콜 판을 채택하는
  데 몇 해가 걸릴 수 있다** (4장, p.135).[^dynowski2025]
- 그래서 붙는 이름이 있다. **미들박스는 최종 사용자 기기와 함께 네트워크 프로토콜의 진화를 제약해
  이른바 프로토콜 경화(protocol ossification)를 낳는다** (4장, p.135).[^dynowski2025]
- 이것이 남긴 설계 자국이 크다. 새 HTTP 판들이 **패킷 구조를 암호화로 미들박스의 눈에서 감추고
  프로토콜을 커널 공간이 아니라 사용자 공간에 구현하는** 길을 고른 이유가 여기 있다
  (4장, p.135).[^dynowski2025] 그 귀결은
  [HTTP/2와 HTTP/3의 다중화와 QUIC](../concepts/http-multiplexing-and-quic.md)에 있다.

## 캐시의 정의와 그 규범이 있는 곳

- 캐시(cache)는 이전 응답 메시지의 로컬 저장소와 그 메시지의 저장·검색·삭제를 제어하는 하위
  시스템이다. 캐시는 앞으로 올 동등한 요청의 응답 시간과 네트워크 대역 소비를 줄이려고 캐시 가능한
  응답을 저장한다 (§3.8).[^fielding2022-rfc9110]
- 누가 캐시를 둘 수 있는가에 제약이 하나 붙는다. **아무 클라이언트나 서버나 캐시를 쓸 수 있으나,
  터널로 행동하는 동안에는 캐시를 쓸 수 없다** (§3.8).[^fielding2022-rfc9110]
- 캐시의 효과는 사슬의 단축이다. 사슬 위의 참여자 하나가 그 요청에 적용 가능한 캐시된 응답을
  가지고 있으면 요청/응답 사슬이 그 지점에서 끊긴다 (§3.8).[^fielding2022-rfc9110]
- 응답이 "캐시 가능"(cacheable)하다는 것은 캐시가 이후 요청에 답하는 데 쓰려고 그 응답 메시지의
  사본을 저장하도록 허용된다는 뜻이다. 다만 캐시 가능하더라도 클라이언트나 원 서버가 그 캐시된
  응답을 특정 요청에 언제 쓸 수 있는지에 추가 제약을 걸 수 있다 (§3.8).[^fielding2022-rfc9110]
- **이 문서가 캐시에 대해 말하는 것은 여기까지다.** 캐시 동작과 캐시 가능한 응답에 대한 HTTP
  요건은 RFC 9111(HTTP Caching)이 정한다 (§3.8).[^fielding2022-rfc9110] 그 분업의 내력은
  [HTTP의 정의와 문서의 범위](../concepts/http-definition-and-scope.md)에 있다.

## 같은 낱말들을 운영 쪽에서 쓰는 소스

**2022년 API 아키텍처 운영서가 프록시와 리버스 프록시를 규정하는데 가르는 축이 위 절들과
다르다. 겨루지 않는다.**

- **그쪽이 가르는 축은 무엇을 지키는 배치인가다** — **프록시 서버, 때로 포워드 프록시(forward
  proxy)라 불리는 것은 여러 클라이언트의 콘텐츠 요청을 인터넷 너머의 여러 서버로 전달하는 중개
  서버**이고 **클라이언트를 지키는 데 쓰인다.** **리버스 프록시 서버는 전형적으로 사설
  네트워크의 방화벽 뒤에 앉아 클라이언트 요청을 알맞은 백엔드 서버로 라우팅하는 프록시 서버의
  한 종류**이고 **서버를 지키도록 설계된다** (3장, p.58).[^gough2022]
  - 저자들이 드는 포워드 프록시의 예가 **직원 트래픽을 공개 인터넷으로 라우팅하고 걸러 내는
    사내 프록시**다 (3장, p.58).[^gough2022]
- **위 [프록시](#프록시)와 [게이트웨이](#게이트웨이)의 축과 대조된다.**
  - 규범 문서는 **누가 고르는가**(프록시는 클라이언트가 고른다)와 **무엇으로 보이는가**
    (게이트웨이는 아웃바운드 연결에서 원 서버로 행동한다)로 가른다. **역할의 정의**다.
  - 이 소스는 **누구를 지키려고 두는가**로 가른다. **배치의 의도**다.
  - **두 축이 같은 칸을 만든다** — 규범 문서가 게이트웨이를 **리버스 프록시라고도 한다**고
    적으므로 그쪽 게이트웨이와 이쪽 리버스 프록시가 같은 것이고, 방향도 같다(둘 다 서버 쪽에
    선다). **더해지는 것은 목적이라는 낱말 하나**이고 그것이 규범 문서에는 없다.
- **API 게이트웨이가 이 위에 얹힌다** — 그 소스는 **네트워크 수준에서 API 게이트웨이가 전형적으로
  리버스 프록시로 행동한다**고 적는다 (3장, p.58).[^gough2022] 그러므로 **API 게이트웨이는 위
  분류의 새 항목이 아니라 게이트웨이 역할 위에 API 관리를 얹은 제품 범주**다.
  - **그 층을 그 소스가 스스로 가른다** — **API 게이트웨이는 애플리케이션 계층(OSI 7계층)에서
    동작하며 API 관리를 제공하고, 엣지 프록시는 네트워크와 전송 계층(OSI 3·4계층)에서 동작하는
    더 범용의 트래픽 프록시나 리버스 프록시로 API 고유 기능을 제공하지 않는 편이며, 인그레스
    컨트롤러는 클러스터로 무엇이 들어오는지를 통제하는 쿠버네티스 고유 기술**이다 (3장,
    p.72).[^gough2022]
  - **이 구별의 축이 OSI 층이라 위 세 종류의 분류와 겹치지 않는다.** 규범 문서의 프록시와
    게이트웨이와 터널은 **전부 HTTP 통신의 역할**이므로 층이 같다. **두 분류를 합치지
    않았다** — 같은 낱말이 두 축에서 쓰인다는 사실만 적는다.
- **전문은 [API 게이트웨이의 규정과 기능과 배치](../concepts/api-gateway-capabilities-and-deployment.md)가
  갖는다.** 이 페이지가 가져온 것은 **위 분류와 맞닿는 대목뿐**이다.
