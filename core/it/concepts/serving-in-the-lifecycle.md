하나의 질문: **애써 모으고 정제하고 저장한 데이터에서 실제로 가치를 얻는 자리는 어디이며,
그 자리마다 요구가 어떻게 갈리는가.**

## 소비되지 않는 데이터는 무기력하다

- 자리 — **데이터 엔지니어링 수명 주기의 마지막 단계다. 데이터가 반입·저장되고 일관되고
  유용한 구조로 변환됐으니 이제 데이터에서 가치를 얻을 때다. "가치를 얻는다"는 것은
  사용자마다 다른 것을 뜻한다** (2장, p.44).[^reis2022]
- 실패 양식 — **데이터는 실용적 목적에 쓰일 때 가치를 갖는다. 소비되거나 질의되지 않는
  데이터는 그저 무기력하다. 데이터 허영 프로젝트(data vanity project)는 회사에 주요
  위험이다. 많은 회사가 빅데이터 시대에 허영 프로젝트를 추구해, 어떤 유용한 방식으로도 결코
  소비되지 않은 방대한 데이터셋을 데이터 레이크에 모았다** (2장, p.44).[^reis2022]
- 반복되고 있다 — **클라우드 시대가 최신 데이터 웨어하우스·객체 저장 시스템·스트리밍 기술
  위에 새로운 허영 프로젝트의 물결을 촉발하고 있다. 데이터 프로젝트는 수명 주기 전반에서
  의도적이어야 한다. 그토록 조심스레 수집·정제·저장된 데이터의 궁극적 업무 목적은
  무엇인가?** (2장, p.44).[^reis2022]

## 서빙의 세 유스케이스

9장이 같은 단계를 한 장 전체로 다시 열며 서빙되는 곳을 셋으로 나눈다.

- **첫째, 분석과 BI를 위해 데이터를 서빙한다. 통계 분석·리포팅·대시보드에 쓸 데이터를 준비한다.
  이것이 데이터 서빙의 가장 전통적인 영역이다. 논쟁의 여지는 있으나 그것은 IT와 데이터베이스보다
  앞서지만, 이해관계자가 업무·조직·재무 프로세스를 볼 수 있게 하는 데 여전히 그 어느 때만큼
  중요하다** (9장, p.337).[^reis2022]
- **둘째, ML 응용을 위해 데이터를 서빙한다. ML은 적절히 준비된 고품질 데이터 없이는 불가능하다.
  데이터 엔지니어는 데이터 과학자·ML 엔지니어와 함께 모델 학습에 필요한 데이터를 획득·변환·전달한다**
  (9장, p.338).[^reis2022]
- **셋째, 역방향 ETL(reverse ETL)로 데이터를 서빙한다. 역방향 ETL은 데이터를 데이터 원천으로
  되돌려 보내는 과정이다. 예컨대 광고 기술 플랫폼에서 데이터를 획득하고, 이 데이터에 통계 프로세스를
  돌려 클릭당 비용 입찰가를 결정한 다음, 이 데이터를 광고 기술 플랫폼으로 되먹일 수 있다. 역방향
  ETL은 BI·ML과 고도로 얽혀 있다** (9장, p.338).[^reis2022]

## 신뢰가 뿌리다

- 저자들이 서빙의 일반 고려 사항 맨 앞에 두는 것 — **무엇보다 먼저 신뢰다. 사람들은 당신이 제공하는
  데이터를 신뢰해야 한다** (9장, p.338).[^reis2022] 장 앞머리에 워런 버핏의 말을 인용한다 (9장,
  p.338, 각주 1):[^reis2022]

> It takes 20 years to build a reputation and five minutes to ruin it. If you think about
> that, you'll do things differently.

- 왜 뿌리인가 — **다른 모든 것에 앞서 신뢰는 데이터 서빙의 근원적 고려 사항이다. 최종 사용자는
  자신이 받는 데이터를 신뢰해야 한다. 가장 화려하고 정교한 데이터 아키텍처와 서빙 계층도 최종
  사용자가 그 데이터를 자기 업무의 믿을 만한 표상이라 믿지 않으면 무의미하다. 신뢰의 상실은 흔히
  데이터 프로젝트의 조용한 사망 선고다 — 프로젝트가 몇 달이나 몇 년 뒤까지 공식적으로 취소되지
  않더라도 그렇다** (9장, p.338).[^reis2022]
- 되찾기가 더 어렵다 — **일단 신뢰가 사라지면 그것을 되찾기는 미치도록 어렵다. 이는 필연적으로
  업무가 데이터로 잠재력을 온전히 발휘하지 못하게 만들고 데이터 팀은 신뢰(그리고 어쩌면 팀 자체)를
  잃는다** (9장, p.339).[^reis2022]
- 처방 둘 — **데이터 품질을 실현하고 이해관계자의 신뢰를 쌓으려면 데이터 검증(data validation)과
  데이터 관측성(data observability) 프로세스를, 이해관계자와 함께 타당성을 눈으로 확인하고 확정하는
  일과 결합해 활용하라. 데이터 검증은 데이터가 재무 정보·고객 상호작용·판매를 정확히 표상하는지
  보장하기 위해 데이터를 분석하는 것이다. 데이터 관측성은 데이터와 데이터 프로세스에 대한 지속적인
  시야를 제공한다. 이 프로세스들은 마지막에 이르러 좋은 결과를 실현하려면 *데이터 엔지니어링 수명
  주기 전반에* 적용돼야 한다** (9장, p.339).[^reis2022]
- 그리고 약속을 문서로 — **데이터 품질에 대한 신뢰를 쌓는 데 더해, 엔지니어는 자신의 SLA와 SLO에
  대한 신뢰를 최종 사용자·상류 이해관계자와 함께 쌓을 책임이 있다. 사용자가 업무 프로세스를 수행하려
  데이터에 의존하게 되면, 그들은 데이터 엔지니어가 한 약속대로 데이터가 일관되게 가용하고 최신이기를
  요구할 것이다. 결정적인 업무 판단을 내려야 할 때 가용하지 않다면 고품질 데이터는 소용이 거의 없다.
  SLA와 SLO는 형식적으로든 비형식적으로든 데이터 계약(data contract)의 형태를 취할 수도 있다는 점에
  유의하라** (9장, p.339).[^reis2022]
- 서빙 맥락에서 다시 정의된 SLA·SLO — **SLA는 다양한 형태로 온다. 형태와 무관하게 SLA는 사용자에게
  당신의 데이터 제품에서 무엇을 기대할지 말해 준다. 그것은 당신과 이해관계자 사이의 계약이다. SLA의
  예는 "데이터가 신뢰할 만하게 가용하고 고품질일 것이다"일 수 있다. SLO는 SLA의 핵심 부분이며 합의한
  것에 대해 성능을 어떻게 측정할지 서술한다. 예컨대 앞의 예시 SLA가 주어졌을 때 SLO는 "당신의
  대시보드나 ML 워크플로로 가는 우리 데이터 파이프라인이 99% 가동률을 가지며 데이터의 95%에 결함이
  없을 것이다"일 수 있다. 기대가 분명하고 합의된 SLA·SLO 매개변수 안에서 운영 중인지 검증할 능력이
  있는지 확인하라** (9장, p.339).[^reis2022] 이 어휘의 본가는
  [서비스 수준 목표](../concepts/service-level-objectives.md)다.
- 합의로 끝나지 않는다 — **단순히 SLA에 합의하는 것으로는 충분하지 않다. 지속적인 소통이 좋은 SLA의
  중심 특징이다. SLA나 SLO 기대에 영향을 줄 수 있는 문제를 소통했는가? 교정과 개선을 위한 당신의
  프로세스는 무엇인가? 신뢰가 전부다. 얻는 데 오래 걸리고 잃기는 쉽다** (9장, p.339).[^reis2022]

## 유스케이스와 사용자가 먼저다

- 서빙 단계의 질문 — **서빙 단계는 행동 중인 데이터에 관한 것이다. 그런데 무엇이 데이터의 *생산적인*
  사용인가? 이 질문에 답하려면 두 가지를 고려해야 한다: 유스케이스가 무엇이고 사용자가 누구인가**
  (9장, p.339).[^reis2022]
- 리포트를 넘어선다 — **데이터의 유스케이스는 리포트와 대시보드를 보는 것을 훨씬 넘어선다. 데이터는
  *행동*으로 이어질 때 최선이다. 임원이 리포트에서 전략적 결정을 내릴 것인가? 모바일 음식 배달 앱의
  사용자가 2분 안에 구매하도록 유인하는 쿠폰을 받을 것인가?** (9장, pp.339–340).[^reis2022]
- 물어야 할 것 — **고품질·고영향 데이터는 본질적으로 많은 흥미로운 유스케이스를 끌어당길 것이다.
  그러나 유스케이스를 찾을 때 언제나 "이 데이터가 어떤 *행동*을 촉발할 것이며 *누가* 이 행동을
  수행할 것인가?"를 묻고, 이어서 "이 행동은 자동화될 수 있는가?"라는 적절한 후속 질문을 던지라**
  (9장, p.340).[^reis2022]
- 엔지니어의 직업병 — **가능하면 언제나 ROI가 가장 높은 유스케이스에 우선순위를 두라. 데이터
  엔지니어는 자기가 짓는 시스템의 기술적 구현 세부에 집착하기를 사랑하면서 목적이라는 기본 질문을
  무시한다. 엔지니어는 자기가 잘하는 일을 하고 싶어 한다 — 엔지니어링. 엔지니어가 가치와 유스케이스에
  집중할 필요를 인식할 때 그들은 자기 역할에서 훨씬 더 가치 있고 유효해진다** (9장,
  p.340).[^reis2022]
- 거꾸로 일하기 — **새 데이터 프로젝트를 시작할 때 거꾸로 일하는 것이 도움이 된다. 도구에 집중하고
  싶은 유혹이 있지만 우리는 유스케이스와 사용자에서 시작할 것을 권한다. 시작할 때 스스로에게 물을
  질문들이다** (9장, p.340):[^reis2022]
  - **누가 데이터를 쓸 것이며 그들은 그것을 어떻게 쓸 것인가?**
  - **이해관계자는 무엇을 기대하는가?**
  - **내가 다루는 데이터가 어떻게 쓰일지 이해하기 위해 데이터 이해관계자(데이터 과학자·분석가·업무
    사용자 등)와 어떻게 협업할 수 있는가?**
- 그 결과물의 이름이 데이터 프로덕트다 — 정의와 셀프서비스 판정은
  [데이터 프로덕트](../concepts/data-products.md)에 있다.

## 데이터 메시가 서빙을 재편한다

- **데이터 메시(data mesh)는 데이터를 서빙할 때 점점 더 고려 사항이 될 것이다. 데이터 메시는 조직
  안에서 데이터가 서빙되는 방식을 근본적으로 바꾼다. 사일로화된 데이터 팀이 자기 내부 고객에게
  서빙하는 대신, 모든 도메인 팀이 탈중앙화된 P2P 데이터 서빙의 두 측면을 떠맡는다** (9장,
  p.343).[^reis2022]
- 두 측면 — **첫째, 팀은 다른 팀에 서빙할 데이터를 소비에 맞게 준비할 책임이 있다. 데이터는 조직
  전반의 데이터 앱·대시보드·분석·BI 도구에서 쓰기 좋아야 한다. 둘째, 각 팀이 잠재적으로 자기
  대시보드와 분석을 셀프서비스로 운영한다. 팀은 자기 도메인의 특정 필요에 근거해 조직 전반에서
  데이터를 소비한다. 다른 팀에서 소비된 데이터는 임베디드 분석이나 ML 기능을 통해 도메인 팀이 설계한
  소프트웨어 안으로 들어갈 수도 있다** (9장, p.343).[^reis2022]
- 판정 — **이는 서빙의 세부와 구조를 극적으로 바꾼다** (9장, p.344).[^reis2022] 메시 자체의 네
  구성 요소는 [데이터 메시](../concepts/data-mesh.md)에 있다.

## 분석 세 갈래

- **분석(analytics)은 대부분의 데이터 활동의 핵심이다. 데이터가 저장·변환되고 나면 리포트나
  대시보드를 생성하고 데이터에 대해 애드혹 분석을 할 준비가 된 것이다. 예전에는 분석의
  대부분이 BI를 아울렀지만, 2022년 저술 시점에는 운영 분석·임베디드 분석 같은 다른 면도 포함한다** (2장,
  pp.44–45).[^reis2022]
- 9장의 정의 — **가장 먼저 만날 데이터 서빙 유스케이스는 분석이며, 이는 데이터 안의 핵심 통찰과
  패턴을 발견·탐색·식별하고 보이게 만드는 것이다. 분석에는 여러 면이 있다. 실무로서 분석은 통계적
  방법·리포팅·BI 도구 등을 써서 수행된다** (9장, p.344).[^reis2022]
- 세 범주를 가르는 질문 — **분석을 위해 데이터를 서빙하기 전에 가장 먼저 해야 할 일은 최종
  유스케이스를 식별하는 것이다. 사용자가 역사적 추세를 보고 있는가? 사용자가 사기 경보 같은 이상에
  즉시 자동으로 통지받아야 하는가? 누군가 모바일 애플리케이션에서 실시간 대시보드를 소비하는가? 이
  예들이 비즈니스 분석(보통 BI)·운영 분석·임베디드 분석의 차이를 부각한다. 이 분석 범주들 각각은
  다른 목표와 고유한 서빙 요구사항을 갖는다** (9장, p.344).[^reis2022]

### 비즈니스 인텔리전스

- **BI는 수집된 데이터를 동원해 사업의 과거와 현재 상태를 서술한다. BI는 원시 데이터를
  처리하기 위해 업무 로직을 쓸 것을 요구한다** (2장, p.45).[^reis2022]
- 여기서도 단계가 엉킨다 — **업무 로직은 흔히 수명 주기의 변환 단계에서 데이터에 적용되지만,
  읽기 시 로직(logic-on-read) 접근이 점점 인기를 얻었다. 데이터는 깨끗하지만 꽤 원시적인
  형태로, 최소한의 후처리 업무 로직만 적용해 저장된다. BI 시스템이 업무 로직과 정의의
  저장소를 유지하고, 이 업무 로직으로 데이터 웨어하우스를 질의해 리포트와 대시보드가 업무
  정의에 맞도록 한다** (2장, p.45).[^reis2022]
- 성숙도에 따른 이동 — **회사가 데이터 성숙도를 키우면 애드혹 데이터 분석에서 셀프서비스
  분석(self-service analytics)으로 옮겨 가, IT의 개입 없이 업무 사용자가 민주화된 데이터
  접근을 갖게 한다** (2장, p.45).[^reis2022]
- 그런데 어렵다 — **셀프서비스 분석은 이론상 단순하지만 실제로 해내기는 어렵다. 주된 이유는
  낮은 데이터 품질, 조직의 사일로, 적절한 데이터 기술의 부재가 흔히 분석의 광범위한 사용을
  가로막기 때문이다** (2장, p.45).[^reis2022]
- 9장이 같은 것을 **비즈니스 분석(business analytics)**이라 부르며 다시 정의한다 — **비즈니스
  분석은 역사적·현재 데이터를 써서 전략적이고 실행 가능한 결정을 내린다. 결정의 유형은 장기 추세를
  고려하는 경향이 있고 흔히 통계·추세 분석에 도메인 전문성과 인간의 판단을 섞는다. 비즈니스 분석은
  과학인 만큼이나 예술이다** (9장, p.344).[^reis2022]
- 세 실무 — **비즈니스 분석은 보통 몇 가지 큰 영역으로 나뉜다 — 대시보드·리포트·애드혹 분석. 비즈니스
  분석가는 이 범주 중 하나나 전부에 집중할 수 있다** (9장, p.344).[^reis2022]
  - **대시보드(dashboard)는 조직이 판매나 고객 유지 같은 소수의 핵심 지표에 대해 어떻게 수행하고
    있는지를 의사결정자에게 간결히 보여 준다. 이 핵심 지표는 시각화(차트나 히트맵 같은)·요약 통계,
    혹은 단일한 수 하나로 제시된다. 이는 차를 운전하는 동안 알아야 할 결정적인 것들을 한 눈에 읽게
    해 주는 자동차 계기판과 비슷하다. 조직은 하나 이상의 대시보드를 가질 수 있으며, C레벨 임원은
    총괄 대시보드를 쓰고 그 직속 보고자들은 자기 지표·KPI·OKR이 담긴 대시보드를 쓴다** (9장,
    p.344).[^reis2022] 저자들이 드는 도구 — **2022년 저술 시점에 대시보드를 만드는 데 Tableau·Looker·Sisense·
    Power BI·Apache Superset/Preset 같은 BI 플랫폼을 쓸 수 있다** (9장, p.345).[^reis2022]
  - **리포트(report)의 목표는 데이터를 써서 통찰과 행동을 이끌어 내는 것이다** (9장,
    p.345).[^reis2022] 저자들의 예에서 온라인 소매사의 분석가가 여성용 러닝 쇼츠의 예상보다 높은
    반품률을 조사해, 반품 코드를 집계하고 원단 품질이 낮아 몇 번 입으면 닳는다는 것을 발견하고,
    제조·품질 관리 이해관계자에게 알리고 대시보드가 있는 같은 BI 도구로 리포트를 배포한다.
  - **애드혹 분석(ad hoc analysis)** — **리포트는 보통 애드혹 요청으로 시작한다. 애드혹 분석의
    결과가 영향력 있으면 흔히 리포트나 대시보드로 끝난다. 리포트와 애드혹 분석에 쓰이는 기술은
    대시보드와 비슷하지만 엑셀·파이썬·R 기반 노트북·SQL 질의 등을 포함할 수 있다** (9장,
    p.345).[^reis2022]
- 분석가와의 되먹임 — **좋은 분석가는 끊임없이 업무와 관여하며 데이터에 뛰어들어 질문에 답하고 숨은,
  직관에 반하는 추세와 통찰을 밝혀낸다. 그들은 또한 데이터 엔지니어와 함께 데이터 품질·신뢰성 문제에
  피드백을 주고 새 데이터셋을 요청한다. 데이터 엔지니어는 이 피드백을 다루고 분석가가 쓸 새 데이터셋을
  제공할 책임이 있다** (9장, p.345).[^reis2022]
- 서빙 방식과 빈도 — **비즈니스 분석용 데이터는 흔히 데이터 웨어하우스나 데이터 레이크에서 배치
  모드로 서빙된다. 이는 회사·부서, 심지어 회사 안 데이터 팀 사이에서도 크게 다르다. 새 데이터가 매
  초, 매 분, 30분마다, 매일, 주 1회 가용할 수 있다** (9장, p.345).[^reis2022]
  - 천장 — **분석 문제를 다루는 엔지니어는 데이터의 다양한 잠재적 활용 — 현재와 미래의 —을 고려해야
    한다. 유스케이스에 적절히 서빙하려고 데이터 갱신 빈도를 섞는 것은 흔하지만, 반입 빈도가 하류
    빈도의 천장을 정한다는 것을 기억하라. 데이터에 스트리밍 애플리케이션이 존재한다면, 일부 하류
    처리와 서빙 단계가 배치로 다뤄지더라도 그것은 스트림으로 반입돼야 한다** (9장,
    pp.345–346).[^reis2022]
- 백엔드 선택 — **물론 데이터 엔지니어는 비즈니스 분석을 서빙할 때 다양한 백엔드 기술 고려 사항을
  다뤄야 한다. 어떤 BI 도구는 데이터를 내부 저장 계층에 저장한다. 다른 도구는 데이터 레이크나
  데이터 웨어하우스에 질의를 돌린다. 이는 OLAP 데이터베이스의 힘을 온전히 활용할 수 있다는 이점이
  있다. 앞 장들에서 논했듯 단점은 비용·접근 통제·지연이다** (9장, p.346).[^reis2022]

### 운영 분석

- **운영 분석(operational analytics)은 운영의 세밀한 세부에 초점을 두며, 리포트 사용자가
  즉시 행동할 수 있는 조치를 촉진한다. 재고의 실시간 뷰나 웹사이트·애플리케이션 상태의
  실시간 대시보드일 수 있다. 이 경우 데이터는 원천 시스템에서 직접이든 스트리밍 데이터
  파이프라인에서든 실시간으로 소비된다** (2장, p.45).[^reis2022]
- BI와의 차이 — **운영 분석에서 나오는 통찰의 유형은 전통적 BI와 다르다. 운영 분석은 현재에
  초점을 두며 역사적 추세를 반드시 다루지는 않기 때문이다** (2장, p.45).[^reis2022]
- 9장이 그 차이를 한 줄로 압축한다 (9장, p.346):[^reis2022]

> Operational analytics versus business analytics =
> immediate action versus actionable insights

- 축은 시간이다 — **운영 분석과 비즈니스 분석의 큰 차이는 *시간*이다. 비즈니스 분석에 쓰이는
  데이터는 고려 중인 질문을 더 긴 시야로 본다. 초 단위 최신 갱신은 알면 좋지만 품질이나 결과에
  실질적 영향을 주지 않는다. 운영 분석은 정반대다. 실시간 갱신이 문제가 일어날 때 그것을 다루는 데
  영향을 줄 수 있기 때문이다** (9장, p.346).[^reis2022]
- 실물 — **운영 분석의 한 예가 실시간 애플리케이션 모니터링이다. 많은 소프트웨어 엔지니어링 팀이
  자기 애플리케이션이 어떻게 수행되는지 알고 싶어 한다. 문제가 생기면 즉시 통지받고 싶어 한다.
  엔지니어링 팀은 초당 요청 수·데이터베이스 I/O 등 핵심 지표를 보여 주는 대시보드를 가질 수 있다.
  특정 조건은 스케일링 이벤트를 촉발해 서버가 과부하되면 용량을 추가할 수 있다. 특정 임계가 넘으면
  모니터링 시스템이 문자·그룹 채팅·이메일로 경보를 보낼 수도 있다** (9장, p.346).[^reis2022]
- 경계가 흐려지는 중이다 — **비즈니스 분석과 운영 분석 사이의 선이 흐려지기 시작했다. 스트리밍과
  저지연 데이터가 더 널리 퍼지면서 운영적 접근을 비즈니스 분석 문제에 적용하는 것이 자연스러워질
  뿐이다. 블랙 프라이데이에 웹사이트 성능을 모니터링하는 것에 더해, 온라인 소매사는 매출·수익·광고
  캠페인의 영향을 실시간으로 분석하고 제시할 수도 있다** (9장, p.346).[^reis2022]
  - 저자들의 전망 — **데이터 아키텍처는 뜨거운 데이터와 따뜻한 데이터를 한 곳에 둘 수 있는 세계에
    맞게 바뀔 것이다. 늘 스스로와 이해관계자에게 물어야 할 중심 질문은 이것이다: 스트리밍 데이터가
    있다면 그것으로 무엇을 할 것인가? 어떤 행동을 취해야 하는가? 올바른 행동이 영향과 가치를 만든다.
    행동 없는 실시간 데이터는 끊임없는 주의 산만이다** (9장, pp.346–347).[^reis2022] #hypothesis
    — **장기적으로 우리는 스트리밍이 배치를 대체하리라 예측한다. 다음 10년 동안 데이터 제품은 역사적
    데이터를 매끄럽게 섞는 능력을 갖춘 스트리밍 우선이 될 가능성이 크다** (9장, p.347).[^reis2022]
    2022년 집필 시점의 저자 예측이다 — 근거는 아래 [라이브 데이터 스택](../concepts/live-data-stack.md)의
    11장 논변이 이어받는다.

### 임베디드 분석

- 왜 따로 떼는가 — **실제로 SaaS 플랫폼에서 고객에게 제공되는 분석(고객 대면 분석)은 별도의
  요구사항과 복잡성 집합을 동반한다. 내부 BI는 제한된 청중을 상대하며 대체로 제한된 수의
  통합된 뷰를 제시한다. 접근 통제는 결정적이지만 특별히 복잡하지는 않다** (2장,
  pp.45–46).[^reis2022]
- 무엇이 달라지는가 — **임베디드 분석(embedded analytics)에서는 리포트 요청률과 그에 따른
  분석 시스템의 부담이 극적으로 올라간다. 접근 통제는 훨씬 더 복잡하고 결정적이다. 기업은
  수천 이상의 고객에게 분리된 분석과 데이터를 서빙할 수 있다. 각 고객은 자기 데이터만,
  오직 자기 데이터만 봐야 한다** (2장, p.46).[^reis2022]
- 실패의 비대칭 — **회사 내부의 데이터 접근 오류는 아마 절차 검토로 이어질 것이다. 고객
  사이의 데이터 유출은 신뢰의 대규모 위반으로 여겨져 언론의 주목과 상당한 고객 이탈을
  낳는다. 데이터 유출과 보안 취약점과 관련한 폭발 반경(blast radius)을 최소화하라. 저장소
  안, 그리고 데이터 유출 가능성이 있는 어디에서든 테넌트 수준 또는 데이터 수준 보안을
  적용하라** (2장, p.46).[^reis2022]
- 멀티테넌시 — **2022년 저술 시점의 많은 저장·분석 시스템이 여러 방식으로 멀티테넌시(multitenancy)를
  지원한다. 데이터 엔지니어는 내부 분석과 ML을 위한 통합된 뷰를 허용하려고 여러 고객의
  데이터를 공통 테이블에 두기로 선택할 수 있다. 이 데이터는 적절히 정의된 통제와 필터를 갖춘
  논리적 뷰를 통해 개별 고객에게 외부로 제시된다** (2장, p.46).[^reis2022] 같은 개념을
  클라우드 아키텍처 쪽에서 다룬 것이
  [클라우드 네이티브 아키텍처](../concepts/cloud-native-architecture.md)다.
- 9장이 붙이는 이름 — **비즈니스 분석과 운영 분석이 내부를 향한다면, 2022년 저술 시점 기준 최근 추세는 외부 대면 혹은
  임베디드 분석이다. 그토록 많은 데이터가 애플리케이션을 구동하면서 기업은 점점 최종 사용자에게
  분석을 제공한다. 이는 보통 데이터 애플리케이션(data application)이라 불리며, 흔히 애플리케이션
  자체에 임베드된 분석 대시보드다** (9장, p.348).[^reis2022] 실물은 실시간 온도와 전력 소비를
  보여 주는 스마트 온도조절기 모바일 앱, 그리고 판매자에게 매출·재고·반품 실시간 대시보드를 주는
  제3자 이커머스 플랫폼이다 (9장, p.348).[^reis2022]
- 데이터 엔지니어가 책임지는 자리 — **데이터 엔지니어로서 당신은 아마 임베디드 분석 프런트엔드를
  만들지 않는다. 애플리케이션 개발자가 그것을 다루기 때문이다. 임베디드 분석을 서빙하는
  데이터베이스에는 당신이 책임이 있으므로 임베디드 분석의 속도와 지연 요구사항을 이해해야 한다**
  (9장, p.348).[^reis2022]
- 성능이 세 문제로 갈린다 — **임베디드 분석의 성능은 세 문제를 아우른다** (9장,
  p.349):[^reis2022]
  - **첫째, 앱 사용자는 사내 분석가만큼 드문 배치 처리에 관대하지 않다. 채용 SaaS 플랫폼의 사용자는
    새 이력서를 업로드하자마자 통계에 변화가 반영되는 것을 기대할 수 있다. 사용자는 낮은 데이터
    지연(data latency)을 원한다.**
  - **둘째, 데이터 앱의 사용자는 빠른 질의 성능(query performance)을 기대한다. 분석 대시보드에서
    매개변수를 조정하면 그들은 갱신된 결과가 몇 초 안에 나타나는 것을 보기를 기대한다.**
  - **셋째, 데이터 앱은 흔히 많은 대시보드와 수많은 고객에 걸쳐 극도로 높은 질의율을 지원해야 한다.
    높은 동시성(concurrency)이 결정적이다.**
- 기술 지형 — **구글과 데이터 앱 공간의 다른 주요 참가자들은 이 도전을 감당할 이색적인 기술을
  개발했다. 새 스타트업의 기본값은 데이터 애플리케이션에 통상적인 트랜잭션 데이터베이스를 쓰는
  것이다. 고객 기반이 커지면 그들은 초기 아키텍처를 넘어선다. 그들에게는 고성능 — 빠른 질의·높은
  동시성·거의 실시간 갱신 —을 상대적으로 쓰기 쉬운 형태(SQL 기반 분석 같은)와 결합한 새 세대의
  데이터베이스가 열려 있다** (9장, p.349).[^reis2022]

## 머신러닝

- 경계가 흐릿하다 — **데이터 엔지니어의 책임은 분석과 ML에서 상당히 겹치며, 데이터
  엔지니어링·ML 엔지니어링·분석 엔지니어링 사이의 경계는 흐릿할 수 있다. 예컨대 데이터
  엔지니어는 분석 파이프라인과 ML 모델 학습을 돕는 스파크 클러스터를 지원해야 할 수 있다.
  팀 사이의 태스크를 오케스트레이션하는 시스템을 제공하고, 데이터 이력과 계보를 추적하는
  메타데이터·카탈로그 시스템을 지원해야 할 수도 있다. 이 책임 영역과 관련 보고 구조를
  정하는 것은 결정적인 조직 결정이다** (2장, p.46).[^reis2022]
- 9장이 그 흐릿함을 조직 배치의 문제로 되짚는다 — **인정하건대 ML·데이터 과학·데이터 엔지니어링·ML
  엔지니어링 사이의 경계는 점점 더 흐릿해지고 있으며 이 경계는 조직마다 극적으로 다르다. 어떤
  조직에서는 ML 엔지니어가 데이터 수집 직후 ML 응용을 위한 데이터 처리를 넘겨받거나, 모든 ML 응용의
  전체 수명 주기를 다루는 완전히 별개의 병렬 데이터 조직을 이루기도 한다. 다른 환경에서는 데이터
  엔지니어가 모든 데이터 처리를 다룬 다음 모델 학습을 위해 ML 엔지니어에게 데이터를 넘긴다. 데이터
  엔지니어가 데이터 피처화 같은 극도로 ML 특유의 태스크를 다루기도 한다** (9장, p.349).[^reis2022]
- 두 분야가 만나는 도구 — **피처 스토어(feature store)는 데이터 엔지니어링과 ML 엔지니어링을
  결합하는 2022년 저술 시점 기준 최근 개발된 도구다. 피처 스토어는 피처 이력과 버전을 유지하고, 팀 사이의 피처
  공유를 지원하며, 백필(backfilling) 같은 기본적 운영·오케스트레이션 능력을 제공해 ML
  엔지니어의 운영 부담을 줄이도록 설계됐다** (2장, p.46).[^reis2022]
- 서빙 단계의 ML 관련 고려 사항 (2장, p.47):[^reis2022]
  - **신뢰할 만한 피처 엔지니어링을 수행하기에 데이터 품질이 충분한가? 품질 요구사항과
    평가는 데이터를 소비하는 팀과 긴밀히 협력해 개발된다.**
  - **데이터가 발견 가능한가? 데이터 과학자와 ML 엔지니어가 가치 있는 데이터를 쉽게 찾을 수
    있는가?**
  - **데이터 엔지니어링과 ML 엔지니어링 사이의 기술적·조직적 경계는 어디인가? 이 조직적
    질문은 상당한 아키텍처적 함의를 갖는다.**
  - **데이터셋이 지상 진실(ground truth)을 제대로 대표하는가? 불공정하게 편향돼 있는가?**
- 순서에 대한 경고 — **ML은 흥미롭지만 우리 경험상 회사들은 흔히 성급하게 뛰어든다. ML에
  많은 자원을 투자하기 전에 견고한 데이터 기반을 짓는 시간을 가져라. 일반적으로 ML로 옮기기
  전에 분석에서 역량을 기르는 것이 최선이다. 많은 회사가 적절한 기반 없이 이니셔티브를
  벌였다가 ML의 꿈을 부쉈다** (2장, p.47).[^reis2022]

### 데이터 엔지니어가 알아야 할 ML

- 범위의 한정 — **데이터 엔지니어는 ML에 대한 깊은 이해를 가질 필요가 없지만, 고전적 ML이 어떻게
  작동하는지의 기초와 딥러닝의 기본을 아는 것은 엄청나게 도움이 된다. ML의 기초를 아는 것은
  데이터 과학자와 나란히 데이터 제품을 짓는 데 크게 기여한다** (9장, p.350).[^reis2022]
- 저자들이 꼽는 친숙해져야 할 영역 (9장, pp.350–351):[^reis2022]
  - **지도·비지도·준지도 학습의 차이. 분류와 회귀 기법의 차이.**
  - **시계열 데이터를 다루는 다양한 기법 — 시계열 분석과 시계열 예측을 포함한다.**
  - **"고전적" 기법(로지스틱 회귀·트리 기반 학습·서포트 벡터 머신)을 언제 쓰고 딥러닝을 언제
    쓰는가. 우리는 데이터 과학자가 과잉일 때조차 곧바로 딥러닝으로 뛰어드는 것을 끊임없이 본다.
    데이터 엔지니어의 기본적인 ML 지식은 ML 기법이 적절한지, 그리고 제공해야 할 데이터의 규모가
    얼마인지 알아채는 데 도움이 된다.**
  - **자동화된 머신러닝(AutoML)을 언제 쓰고 ML 모델을 손수 만드는 것은 언제인가. 쓰이는 데이터에
    관해 각 접근의 트레이드오프는 무엇인가.**
  - **구조화·비구조화 데이터에 쓰이는 데이터 랭글링(data-wrangling) 기법은 무엇인가.**
  - **ML에 쓰이는 모든 데이터는 수로 변환된다. 구조화·반구조화 데이터를 서빙한다면 피처 엔지니어링
    과정에서 데이터가 적절히 변환될 수 있게 하라.**
  - **범주형 데이터와 다양한 데이터 유형의 임베딩을 어떻게 인코딩하는가.**
  - **배치 학습과 온라인 학습의 차이. 당신의 유스케이스에는 어느 접근이 적절한가.**
  - **데이터 엔지니어링 수명 주기가 당신 회사의 ML 수명 주기와 어디서 교차하는가. 피처 스토어나 ML
    관측성 같은 ML 기술과 인터페이스하거나 그것을 지원할 책임이 있는가?**
  - **로컬에서 학습할지, 클러스터에서 할지, 엣지에서 할지 언제가 적절한지 알라. 언제 CPU 대신 GPU를
    쓰겠는가. 쓰는 하드웨어의 유형은 대체로 푸는 ML 문제의 유형·쓰는 기법·데이터셋의 크기에 달렸다.**
  - **ML 모델을 학습시킬 때 배치 데이터와 스트리밍 데이터의 응용 차이를 알라. 예컨대 배치 데이터는
    흔히 오프라인 모델 학습에 잘 맞고 스트리밍 데이터는 온라인 학습에 맞는다.**
  - **데이터 캐스케이드(data cascades)가 무엇이며 그것이 ML 모델에 어떤 영향을 줄 수 있는가.**
    - 그 물음의 답을 담은 원전이 이 KB에 있다 —
      [데이터 캐스케이드](../concepts/data-cascades-in-high-stakes-ai.md). 정의와 유형 넷,
      그리고 상류에서 촉발돼 하류에서 늦게 드러나는 구조가 거기 있다.
  - **결과가 실시간으로 반환되는가 배치로 반환되는가. 예컨대 배치 음성 전사 모델은 API 호출 뒤
    음성 표본을 배치로 처리해 텍스트를 반환할 수 있다. 제품 추천 모델은 고객이 온라인 소매 사이트와
    상호작용하는 동안 실시간으로 작동해야 할 수 있다.**
  - **구조화 데이터와 비구조화 데이터의 사용. 표 형태(구조화) 고객 데이터를 군집화하거나 신경망으로
    이미지(비구조화)를 인식할 수 있다.**

## 역방향 ETL

- 정의와 내력 — **역방향 ETL(reverse ETL)은 오랫동안 데이터에서 실무적 현실이었으나, 우리가
  이야기하거나 이름을 붙여 격을 세워 주고 싶지 않았던 안티패턴으로 여겨졌다. 역방향 ETL은
  데이터 엔지니어링 수명 주기의 출력 쪽에서 처리된 데이터를 가져다 원천 시스템으로 되먹인다**
  (2장, p.47).[^reis2022]
- 판정의 전환 — **실제로 이 흐름은 유익하고 흔히 필요하다. 역방향 ETL은 분석 결과나 점수가
  매겨진 모델 등을 프로덕션 시스템이나 SaaS 플랫폼으로 되먹일 수 있게 해 준다** (2장,
  p.47).[^reis2022]
- 원시적 형태 — **마케팅 분석가가 데이터 웨어하우스의 데이터로 마이크로소프트 엑셀에서
  입찰가를 계산한 다음 그 입찰가를 구글 애즈에 업로드할 수 있다. 이 프로세스는 흔히 전적으로
  수동적이고 원시적이었다** (2장, p.48).[^reis2022]
- 제품이 됐다 — **이 책을 쓰는 동안 여러 벤더가 역방향 ETL 개념을 받아들여 Hightouch·Census
  같은 제품을 만들었다. 역방향 ETL은 실무로서 아직 초기이지만 우리는 그것이 자리 잡으리라
  본다** (2장, p.48).[^reis2022]
- 왜 중요해졌나 — **기업이 SaaS와 외부 플랫폼에 점점 더 의존하면서 역방향 ETL은 특히
  중요해졌다. 예컨대 회사는 데이터 웨어하우스의 특정 지표를 고객 데이터 플랫폼이나 CRM
  시스템으로 밀고 싶어 할 수 있다. 광고 플랫폼이 또 하나의 일상적 유스케이스다** (2장,
  p.48).[^reis2022]
- 이름은 미정 — **역방향 ETL이라는 용어가 남을지는 아직 판결이 나지 않았고 실무 자체가 진화할
  수 있다. 어떤 엔지니어는 데이터 변환을 이벤트 스트림에서 처리하고 그 이벤트를 필요에 따라
  원천 시스템으로 되돌려 보냄으로써 역방향 ETL을 없앨 수 있다고 주장한다. 요지는 변환된
  데이터가 어떤 방식으로든, 이상적으로는 올바른 계보와 원천 시스템에 결부된 업무 프로세스와
  함께 원천 시스템으로 돌아가야 한다는 것이다** (2장, p.48).[^reis2022]
  - 이 대안 주장은 [데이터 통합](../concepts/data-integration.md)이 세운 "모든 입력을 하나의
    순서로 깔때기처럼 모은다"는 원칙과 같은 방향이다. 다만 저자들은 그 패턴이 실제로 널리
    채택되는 것은 별개 문제라고 덧붙인다.

### 9장이 다시 보는 역방향 ETL

- 유행어가 됐다 — **2022년 저술 시점에 역방향 ETL은 OLAP 데이터베이스에서 원천 시스템으로 데이터를 다시 적재해
  서빙하는 것을 서술하는 유행어다. 그렇지만 몇 년 이상 현장에서 일한 데이터 엔지니어라면 아마 역방향
  ETL의 어떤 변종을 이미 해 봤을 것이다. 역방향 ETL은 2010년대 후반·2020년대 초에 인기를 얻었고
  점점 더 공식적인 데이터 엔지니어링 책임으로 인정받고 있다** (9장, p.358).[^reis2022]
- 왜 대안들이 부족한가 — 저자들의 리드 스코어링 예에서 데이터 엔지니어가 CRM의 고객·주문 데이터를
  웨어하우스에 넣고 리드 스코어링 모델을 학습시킨 뒤 결과를 웨어하우스에 되돌린다. **영업팀이 그
  점수를 원한다. 결과를 대시보드에 올리거나 엑셀 파일로 이메일할 수 있다. 이 접근들의 문제는 그것이
  영업사원이 실제로 일하는 CRM에 연결돼 있지 않다는 것이다. 점수 매겨진 리드를 그냥 CRM에 도로 넣지
  않을 이유가 무엇인가? 언급했듯 성공적인 데이터 제품은 최종 사용자와의 마찰을 줄인다** (9장,
  p.359).[^reis2022]
- 저자들이 붙이고 싶어 한 다른 이름 — **역방향 ETL 대신 우리 저자들은 반농담으로 그것을 양방향 적재·
  변환(bidirectional load and transform, BLT)이라 부른다. 역방향 ETL이라는 용어는 이 프로세스에서
  일어나는 일을 꽤 정확히 서술하지 못한다. 그럼에도 이 용어가 대중의 상상과 언론에 고착돼 우리도 책
  전반에서 그것을 쓴다. 더 넓게 보아 역방향 ETL이라는 용어가 남을지는 아무도 모르지만, OLAP
  시스템에서 원천 시스템으로 데이터를 적재하는 실무는 계속 중요할 것이다** (9장,
  p.359).[^reis2022]
- 도구 선택의 조언 — **역방향 ETL 솔루션을 직접 굴릴 수도 있지만 많은 기성 역방향 ETL 선택지가
  있다. 우리는 오픈 소스나 상용 관리형 서비스를 쓸 것을 제안한다. 그렇지만 역방향 ETL 공간은
  극도로 빠르게 바뀌고 있다. 명확한 승자가 나타나지 않았고 많은 역방향 ETL 제품이 주요 클라우드나
  다른 데이터 제품 벤더에 흡수될 것이다. 신중히 고르라** (9장, p.359).[^reis2022]
- 경고 — **역방향 ETL은 본질적으로 피드백 루프를 만든다. 예컨대 구글 애즈 데이터를 내려받아 모델로
  새 입찰가를 계산하고 그 입찰가를 구글 애즈에 되적재한 뒤 프로세스를 다시 시작한다고 상상하라.
  입찰 모델의 오류 때문에 입찰가가 점점 높아지고 광고가 점점 더 많은 클릭을 받는다고 하자. 순식간에
  막대한 돈을 낭비할 수 있다! 조심하고 모니터링과 가드레일을 심으라** (9장, p.360).[^reis2022]
  - 파생 데이터를 원천으로 되돌린다는 점에서, 이는
    [기록 시스템과 파생 데이터](../concepts/system-of-record-and-derived-data.md)가 세운 단방향
    유도(기록 시스템 → 파생)를 순환으로 만드는 조작이다. 위 경고는 그 순환이 스스로를 증폭할 때
    무엇이 일어나는지의 실물이다.

## 함께 일하는 사람들

- 대상 — **논했듯 서빙 단계에서 데이터 엔지니어는 많은 이해관계자와 인터페이스한다. 여기에는 데이터
  분석가, 데이터 과학자, MLOps/ML 엔지니어, 그리고 업무 — 데이터가 아니거나 기술적이지 않은
  이해관계자·관리자·임원 —이 포함된다(이에 국한되지 않는다)** (9장, p.360).[^reis2022]
- 역할의 성격 — **상기하자면 데이터 엔지니어는 이 이해관계자들에 대해 *지원* 역할로 작동하며 데이터의
  최종 사용에 반드시 책임이 있는 것은 아니다. 예컨대 데이터 엔지니어는 분석가가 해석하는 리포트의
  데이터를 공급하지만 데이터 엔지니어가 그 해석에 책임이 있는 것은 아니다. 대신 데이터 엔지니어는
  가능한 한 최고 품질의 데이터 제품을 생산할 책임이 있다** (9장, p.360).[^reis2022]
- 되먹임을 의식하라 — **데이터 엔지니어는 데이터 엔지니어링 수명 주기와, 데이터가 이해관계자의 손에
  들어간 뒤의 더 넓은 사용 사이의 피드백 루프를 알고 있어야 한다. 데이터는 좀처럼 정적이지 않으며,
  바깥 세계가 반입되고 서빙되는 데이터에 영향을 줄 것이고 그 데이터는 다시 반입되고 다시 서빙된다**
  (9장, p.360).[^reis2022]
- 의무의 분리 — **서빙 단계에서 데이터 엔지니어에게 큰 고려 사항은 의무와 관심사의 분리다. 초기
  단계 회사에 있다면 데이터 엔지니어가 ML 엔지니어나 데이터 과학자이기도 할 수 있다. 이는 지속
  가능하지 않다. 회사가 자라면 다른 데이터 팀원과 명확한 의무 분담을 확립해야 한다** (9장,
  p.360).[^reis2022]
- 메시를 도입하면 — **데이터 메시를 채택하면 팀 책임이 극적으로 재조직되고 모든 도메인 팀이 서빙의
  측면들을 떠맡는다. 데이터 메시가 성공하려면 각 팀이 자기 데이터 서빙 책임에서 효과적으로 일해야
  하고, 팀들이 조직적 성공을 보장하기 위해 효과적으로 협업해야 한다** (9장, p.360).[^reis2022]

## 서빙 단계에 걸리는 저류

- 자리 — **저류가 서빙에서 종국에 이른다. 데이터 엔지니어링 수명 주기는 말 그대로 수명 주기임을
  기억하라. 무엇이 돌아가든 돌아온다. 우리는 서빙 데이터가 수명 주기 앞에서 놓친 무언가를 부각하는
  경우를 많이 본다. 저류가 데이터 제품을 개선할 방법을 알아채는 데 어떻게 도움을 줄 수 있을지 늘
  살피라** (9장, pp.360–361).[^reis2022]
- 저자들이 좋아하는 표현 — **"데이터는 조용한 살인자"라 말하기를 우리는 즐기며, 저류는 서빙
  단계에서 정점에 이른다. 서빙은 데이터가 최종 사용자의 손에 들어가기 전에 그것이 훌륭한 상태인지
  확인할 마지막 기회다** (9장, p.361).[^reis2022]
- **보안** — **사람과 공유하든 시스템과 공유하든 같은 보안 원칙이 적용된다. 접근 통제가 거의 없이,
  데이터가 무엇에 쓰일지에 대한 고민도 거의 없이 데이터가 무차별적으로 공유되는 것을 우리는 흔히
  본다. 이는 데이터 침해와 그에 따른 벌금·나쁜 언론·일자리 상실 같은 파국적 결과를 낳을 수 있는 거대한
  실수다. 보안을 진지하게 여기라, 특히 수명 주기의 이 단계에서. 모든 수명 주기 단계 가운데 서빙이
  가장 큰 보안 표면(security surface)을 제시한다** (9장, p.361).[^reis2022] 최소 권한 원칙과
  그 실천은 [데이터 엔지니어링의 저류](../concepts/data-engineering-undercurrents.md)에 있다.
  - 읽기 전용이 기본 — **서빙 데이터는 사람이나 프로세스가 질의되는 시스템의 데이터를 갱신해야 하지
    않는 한 흔히 읽기 전용이다. 사람에게는 역할이 쓰기나 갱신 접근 같은 더 고급의 것을 요구하지 않는
    한 특정 데이터베이스와 데이터셋에 읽기 전용 접근만 주어야 한다** (9장, p.361).[^reis2022]
  - 멀티테넌트에서 — **멀티테넌트 환경에서 데이터를 서빙할 때 접근 통제는 결정적이다. 사용자가
    *자기* 데이터에만 접근할 수 있도록 하라. 좋은 접근은 필터된 뷰(filtered view)를 통해 접근을
    중재해, 공통 테이블에 대한 접근 공유에 내재한 보안 위험을 완화하는 것이다** (9장,
    p.361).[^reis2022]
  - 안 쓰는 것은 끄라 — **데이터 제품이 얼마나 자주 쓰이는지, 특정 데이터 제품 공유를 멈추는 것이
    말이 되는지 점검하라. 임원이 분석가에게 리포트를 급히 요청해 놓고 그 리포트가 아주 빠르게 쓰이지
    않게 되는 일은 극도로 흔하다. 데이터 제품이 쓰이지 않으면 사용자에게 여전히 필요한지 물으라.
    아니라면 그 데이터 제품을 죽이라. 이는 떠다니는 보안 취약점이 하나 줄어든다는 뜻이다** (9장,
    pp.361–362).[^reis2022]
  - 관점의 전환 — **끝으로 접근 통제와 보안을 서빙의 장애물이 아니라 핵심 조력자로 보아야 한다. 우리는
    복잡하고 진보한 데이터 시스템이 지어져 회사에 상당한 영향을 줄 잠재력이 있었는데, 보안이 올바로
    구현되지 않아 데이터에 접근이 허용된 사람이 적었고 그래서 시들어 버린 많은 사례를 안다. 세밀하고
    견고한 접근 통제는 업무와 고객을 보호하면서도 더 흥미로운 데이터 분석과 ML이 이뤄질 수 있음을
    뜻한다** (9장, p.362).[^reis2022]
- **데이터 관리** — **서빙 단계에서 당신은 주로 사람들이 고품질의 신뢰할 만한 데이터에 접근할 수 있게
  하는 데 관심이 있다. 이 장 첫머리에 언급했듯 신뢰는 아마 데이터 서빙에서 가장 결정적인 변수다.
  사람들이 자기 데이터를 신뢰하면 그것을 쓸 것이고, 신뢰받지 못한 데이터는 쓰이지 않을 것이다.
  피드백 루프를 제공해 데이터 신뢰와 데이터 개선을 능동적인 프로세스로 만들라** (9장,
  p.362).[^reis2022]
  - 난독화라는 타협 — **규제와 컴플라이언스 우려가 데이터 팀을 압박할 때 특히, 사람들에게 원시
    데이터 접근을 주는 것은 — 제한된 필드와 행만이더라도 — 데이터를 사람이나 사람 집단 같은 개체로
    역추적하는 문제를 낳는다. 고맙게도 데이터 난독화(data obfuscation)의 진보로 합성·뒤섞인·익명화된
    데이터를 최종 사용자에게 서빙할 수 있다. 이 "가짜" 데이터셋은 분석가나 데이터 과학자가 데이터에서
    필요한 신호를 얻게 하면서도 보호 대상 정보를 식별하기 어렵게 만든다. 완벽한 프로세스는 아니지만 —
    충분한 노력이면 많은 데이터셋이 비익명화되거나 역공학될 수 있다 — 적어도 데이터 유출의 위험을
    줄인다** (9장, p.362).[^reis2022] 재식별의 한계 자체는
    [위험 자산으로서의 데이터](../concepts/data-as-a-hazardous-asset.md)가 다룬다.
  - 그리고 정의를 심으라 — **또한 업무 로직과 정의를 제대로 표현하는 엄격한 데이터 모델링과 함께
    시맨틱·메트릭 계층을 서빙 계층에 통합하라. 이는 분석이든 ML이든 역방향 ETL이든 다른 서빙 용도든
    단일한 진실 원천을 제공한다** (9장, p.362).[^reis2022] 그 계층은
    [시맨틱 계층과 메트릭 계층](../concepts/semantic-and-metrics-layers.md)에 있다.
- **DataOps** — **데이터 관리에서 취하는 단계 — 데이터 품질·거버넌스·보안 —은 DataOps에서
  모니터링된다. 본질적으로 DataOps는 데이터 관리를 운영화한다** (9장, p.362).[^reis2022]
  모니터링할 것 (9장, p.363):[^reis2022]
  - **데이터 건강과 데이터 다운타임(data downtime).**
  - **데이터를 서빙하는 시스템 — 대시보드·데이터베이스 등 —의 지연.**
  - **데이터 품질. 데이터와 시스템 보안·접근. 서빙되는 데이터와 모델의 버전. SLO 달성 가동률.**
  - 도구 지형 — **다양한 새 도구가 여러 모니터링 측면을 다루려 생겨났다. 예컨대 많은 인기 있는 데이터
    관측성 도구가 데이터 다운타임을 최소화하고 데이터 품질을 최대화하는 것을 목표로 한다. 관측성
    도구는 데이터에서 ML로 넘어가 모델과 모델 성능의 모니터링을 지원하기도 한다. 더 통상적인 데브옵스
    모니터링도 DataOps에 결정적이다 — 예컨대 저장·변환·서빙 사이의 연결이 안정적인지 모니터링해야
    한다** (9장, p.363).[^reis2022]
  - 코드도 마찬가지 — **데이터 엔지니어링 수명 주기의 모든 단계에서처럼 코드를 버전 관리하고 배포를
    운영화하라. 이는 분석 코드·데이터 로직 코드·ML 스크립트·오케스트레이션 잡에 적용된다. 리포트와
    모델에 여러 배포 단계(dev·test·prod)를 쓰라** (9장, p.363).[^reis2022]
- **데이터 아키텍처** — **서빙 단계에서 피드백 루프는 빠르고 타이트해야 한다. 사용자는 필요할 때
  필요한 데이터에 가능한 한 빨리 접근할 수 있어야 한다** (9장, p.363).[^reis2022]
  - 로컬에서 끌어내라 — **데이터 과학자는 대부분의 개발을 자기 로컬 머신에서 하는 것으로 악명 높다.
    앞서 논했듯 이 워크플로를 클라우드 환경의 공통 시스템으로 이주하도록 권장하라. 거기서 데이터 팀은
    dev·test·프로덕션 환경에서 협업하고 적절한 프로덕션 아키텍처를 만들 수 있다. 데이터 통찰을
    발행하는 도구를 지원해 분석가와 데이터 과학자가 부담 없이 일하도록 도우라** (9장,
    p.363).[^reis2022]
- **오케스트레이션** — **데이터 서빙은 데이터 엔지니어링 수명 주기의 마지막 단계다. 서빙은 그토록
  많은 프로세스의 하류에 있으므로 극도로 복잡한 중첩 영역이다. 오케스트레이션은 단순히 복잡한 작업을
  조직하고 자동화하는 방법이 아니라, 약속한 시각에 데이터가 소비자에게 가용해지도록 팀에 걸쳐 데이터
  흐름을 조율하는 수단이다** (9장, p.363).[^reis2022]
  - 소유가 조직 결정이다 — **오케스트레이션의 소유는 핵심 조직 결정이다. 오케스트레이션은 중앙집중일
    것인가 탈중앙일 것인가? 탈중앙 접근은 작은 팀이 자기 데이터 흐름을 관리하게 해 주지만 팀 간 조율
    부담을 키울 수 있다. 단일 시스템 안의 흐름을 관리하는 대신 팀들은 다른 팀에 속한 DAG나 태스크의
    완료를 직접 촉발해야 하고, 시스템 사이에 메시지나 질의를 넘겨야 한다** (9장,
    pp.363–364).[^reis2022]
  - 중앙집중의 대가 — **중앙집중 접근은 작업을 조율하기 더 쉽지만, 단일한 프로덕션 자산을 보호하기
    위해 상당한 게이트키핑도 존재해야 한다. 예컨대 잘못 쓰인 DAG 하나가 Airflow를 멈춰 세울 수 있다.
    중앙집중 접근은 조직 전체의 데이터 프로세스와 서빙을 내려앉히는 것을 뜻하게 된다. 중앙집중
    오케스트레이션 관리는 높은 표준·DAG의 자동 테스트·게이트키핑을 요구한다** (9장,
    p.364).[^reis2022] 그 DAG의 실행 모델은
    [배치 워크플로와 DAG](../concepts/batch-workflows-and-dags.md)에 있다.
- **소프트웨어 엔지니어링** — **몇 년 전과 비교해 데이터 서빙은 더 단순해졌다. 코드를 쓸 필요가
  극적으로 단순해졌다. 데이터 서빙의 단순화에 집중한 오픈 소스 프레임워크의 확산으로 데이터도 더
  코드 우선(code-first)이 됐다. 최종 사용자에게 데이터를 서빙하는 많은 방법이 존재하며 데이터
  엔지니어의 초점은 그 시스템들이 어떻게 작동하고 데이터가 어떻게 전달되는지 아는 데 있어야 한다**
  (9장, p.364).[^reis2022]
  - 그럼에도 코드가 남는 자리 — **서빙 데이터의 단순함에도 불구하고 코드가 관여한다면 데이터
    엔지니어는 여전히 주요 서빙 인터페이스가 어떻게 작동하는지 이해해야 한다. 예컨대 데이터 엔지니어는
    데이터 과학자가 노트북에서 로컬로 돌리는 코드를 번역해 리포트나 기본적인 ML 모델이 작동하도록
    변환해야 할 수 있다** (9장, p.364).[^reis2022]
  - 생성된 SQL의 성능 — **데이터 엔지니어가 유용할 또 다른 영역은 코드와 질의가 저장 시스템에 대해
    어떻게 수행될지의 영향을 이해하는 것이다. 분석가는 LookML·dbt를 통한 Jinja·다양한 객체 관계
    매핑(ORM) 도구·메트릭 계층 등 다양한 프로그램적 방식으로 SQL을 생성할 수 있다. 이 프로그램적
    계층이 SQL로 컴파일될 때 그 SQL은 어떻게 수행될 것인가? 데이터 엔지니어는 SQL이 손으로 쓴
    SQL만큼 수행되지 않는 곳에 최적화를 제안할 수 있다** (9장, p.364).[^reis2022]
  - IaC로 옮겨 간다 — **분석·ML IaC의 부상은 코드를 쓰는 역할이 데이터 과학자와 분석가를 지원하는
    시스템을 짓는 쪽으로 옮겨 가고 있음을 뜻한다. 데이터 엔지니어는 데이터 팀을 위한 CI/CD 파이프라인
    설정과 프로세스 구축을 책임질 수 있다. 그들은 또한 자신이 지은 Data/MLOps 인프라를 쓰도록 데이터
    팀을 훈련시키고 지원해 이 팀들이 가능한 한 자족적이 되게 하는 편이 좋다** (9장,
    p.364).[^reis2022]
  - 임베디드 분석에서는 — **임베디드 분석의 경우 데이터 엔지니어는 애플리케이션 개발자와 함께 질의가
    빠르고 비용 효율적으로 반환되도록 해야 할 수 있다. 애플리케이션 개발자는 사용자가 다루는 프런트엔드
    코드를 통제한다. 데이터 엔지니어는 개발자가 요청한 대로 올바른 페이로드를 받도록 보장하기 위해
    거기 있다** (9장, p.364).[^reis2022]

## 이 단계가 끝나는 방식

- **데이터 엔지니어링 수명 주기는 서빙 단계에서 논리적 종결에 이른다. 모든 수명 주기가 그렇듯
  피드백 루프가 일어난다. 서빙 단계를 무엇이 작동하고 무엇이 개선될 수 있는지 배울 기회로 보아야
  한다. 이해관계자의 말을 들으라. 그들이 문제를 제기하면 — 그리고 그들은 필연적으로 그럴 것이다 —
  기분 상해 하지 않으려 노력하라. 대신 이것을 당신이 지은 것을 개선할 기회로 쓰라** (9장,
  p.365).[^reis2022] 저자들이 그리는 고리는 구축(build) → 배움(learn) → 개선(improve)이다
  (9장, p.365, 그림 9-6).[^reis2022]
