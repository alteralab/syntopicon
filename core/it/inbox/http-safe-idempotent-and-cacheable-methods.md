하나의 질문: **메서드마다 따로 적지 않고 공통으로 뽑아 둔 속성 셋은 각각 무엇을 뜻하고, 여덟
메서드는 거기에 어떻게 배정되는가.**

## 버전 조건

> **버전 조건**: RFC 9110(2022-06, STD 97) 기준. 2026-09-07 시점 이를 갱신하거나 폐기하는
> RFC 없음(datatracker 실측).

## 안전이란 무엇인가

- 정의 문장이다 (§9.2.1).[^fielding2022-rfc9110]

  > Request methods are considered "safe" if their defined semantics are essentially
  > read-only; i.e., the client does not request, and does not expect, any state change on the
  > origin server as a result of applying a safe method to a target resource.

  **정의된 의미론이 본질적으로 읽기 전용이면** 그 메서드는 안전(safe)하다. 클라이언트가 원 서버의
  상태 변화를 **요구하지도 기대하지도 않는다**는 뜻이다.
- 정의가 한 겹 더 있다. 안전한 메서드를 합리적으로 쓴다고 해서 **어떤 해나 재산 손실이나 원 서버에
  대한 이례적 부담이 생길 것으로 기대되지 않는다** (§9.2.1).[^fielding2022-rfc9110]
- 이 명세가 정의한 메서드 중 안전한 것은 **GET·HEAD·OPTIONS·TRACE** 넷이다
  (§9.2.1).[^fielding2022-rfc9110]

## 안전이 금지하지 않는 것

- 이 정의는 구현을 구속하지 않는다. **잠재적으로 해로운 동작이나 완전히 읽기 전용이 아닌 동작이나
  부작용을 일으키는 동작을 안전한 메서드를 처리하면서 포함하는 것을 이 정의가 막지 않는다**
  (§9.2.1).[^fielding2022-rfc9110]
- 그래서 안전은 **구현의 성질이 아니라 책임의 배분**이다. 중요한 것은 클라이언트가 그 추가 동작을
  요구하지 않았고 **그것에 대해 책임을 질 수 없다는 것**이다 (§9.2.1).[^fielding2022-rfc9110]
- 원전이 드는 예 둘이 이 배분을 보여 준다 (§9.2.1).[^fielding2022-rfc9110]
  - 대부분의 서버는 메서드와 무관하게 모든 응답이 끝날 때 요청 정보를 접근 로그 파일에 덧붙인다.
    **로그 저장소가 가득 차 서버가 실패할 수 있는데도 그것은 안전한 것으로 친다.**
  - 웹에서 광고를 골라 일어난 안전한 요청이 흔히 광고 계정에 과금하는 부작용을 낳는다.

## 안전을 구분해 두는 값

- 구분의 목적이 명시되어 있다. **자동 수집 프로세스(스파이더)와 캐시 성능 최적화(선인출)가 해를
  끼칠 걱정 없이 동작하게 하려는 것**이다 (§9.2.1).[^fielding2022-rfc9110]
- 두 번째 목적은 사용자 에이전트 쪽이다. 믿을 수 없는 콘텐츠를 처리할 때 **안전하지 않은 메서드의
  자동 사용에 적절한 제약을 걸 수 있게 한다** (§9.2.1).[^fielding2022-rfc9110]
- 사람에게 보이는 자리에도 요건이 걸린다. 사용자 에이전트는 가능한 행위를 사용자에게 제시할 때
  **안전한 메서드와 안전하지 않은 메서드를 구별해야 하고**(SHOULD), 그래야 사용자가 요청되기 전에
  안전하지 않은 행위임을 알 수 있다 (§9.2.1).[^fielding2022-rfc9110]

## 질의 파라미터로 행위를 고르는 자원의 책임

- 대상 URI 안의 파라미터가 행위를 고르는 효과를 갖도록 자원이 구성되어 있으면, **그 행위가 요청
  메서드 의미론과 일관되게 만드는 것은 자원 소유자의 책임**이다 (§9.2.1).[^fielding2022-rfc9110]
  원전이 드는 예가 웹 기반 콘텐츠 편집 소프트웨어가 흔히 쓰는 `page?do=delete` 같은 질의 파라미터
  안의 행위다.
- 요건은 금지 형태로 걸린다. 그런 자원의 목적이 안전하지 않은 행위를 수행하는 것이라면, 자원
  소유자는 **안전한 요청 메서드로 접근했을 때 그 행위를 비활성화하거나 불허해야 한다**(MUST)
  (§9.2.1).[^fielding2022-rfc9110]
- 그러지 않았을 때 무슨 일이 일어나는지도 적혀 있다. 링크 관리나 선인출이나 검색 색인 구축을 위해
  **자동 프로세스가 모든 URI 참조에 GET을 걸 때 불행한 부작용이 생긴다**
  (§9.2.1).[^fielding2022-rfc9110]

## 멱등이란 무엇인가

- 정의 문장이다 (§9.2.2).[^fielding2022-rfc9110]

  > A request method is considered "idempotent" if the intended effect on the server of
  > multiple identical requests with that method is the same as the effect for a single such
  > request.

  같은 요청을 여러 번 보냈을 때 **서버에 대한 의도된 효과(intended effect)** 가 한 번 보냈을 때와
  같으면 그 메서드는 멱등(idempotent)하다.
- 이 명세가 정의한 메서드 중 멱등한 것은 **PUT과 DELETE와 안전한 요청 메서드들**이다
  (§9.2.2).[^fielding2022-rfc9110] 안전한 넷이 멱등에 포함되므로 멱등한 메서드는 여섯이 된다.
- 안전과 같은 단서가 붙는다. 멱등 속성은 **사용자가 요청한 것에만 적용된다.** 서버는 요청마다 따로
  로그를 남기거나 개정 이력을 보관하거나, 멱등한 요청 하나하나에 대해 멱등하지 않은 다른 부작용을
  구현해도 된다 (§9.2.2).[^fielding2022-rfc9110]
- 응답까지 같아진다는 뜻은 아니다. 원전이 재시도 서술에서 이 점을 못 박는다 — 반복해도 의도된
  효과는 같지만 **응답은 다를 수 있다** (§9.2.2).[^fielding2022-rfc9110]

## 캐시 가능이란 무엇인가

- 조건이 메서드 정의 쪽에 걸린다. 캐시가 응답을 저장하고 사용하려면 **연관된 메서드가 캐싱을
  명시적으로 허용하고 어떤 조건에서 그 응답을 이후 요청을 충족하는 데 쓸 수 있는지를 상술해야
  한다.** 그러지 않은 메서드 정의는 캐시될 수 없다 (§9.2.3).[^fielding2022-rfc9110]
- 이 명세가 캐싱 의미론을 정의한 메서드는 **GET과 HEAD와 POST** 셋이다. 다만 원전이 곧바로 덧붙인다
  — **압도적 다수의 캐시 구현은 GET과 HEAD만 지원한다** (§9.2.3).[^fielding2022-rfc9110]
- 이 페이지가 담는 것은 여기까지다. 추가 요건은 캐싱 명세(RFC 9111)가 정본이다
  (§9.2.3).[^fielding2022-rfc9110]

## 세 속성의 분포

- 위 세 절의 배정을 한자리에 모으면 이렇게 된다 (§9.2.1, §9.2.2,
  §9.2.3).[^fielding2022-rfc9110]

  | 메서드 | 안전 | 멱등 | 캐시 의미론이 정의됨 |
  |---|---|---|---|
  | GET | 그렇다 | 그렇다 | 그렇다 |
  | HEAD | 그렇다 | 그렇다 | 그렇다 |
  | OPTIONS | 그렇다 | 그렇다 | 아니다 |
  | TRACE | 그렇다 | 그렇다 | 아니다 |
  | PUT | 아니다 | 그렇다 | 아니다 |
  | DELETE | 아니다 | 그렇다 | 아니다 |
  | POST | 아니다 | 아니다 | 조건부로 그렇다 |
  | CONNECT | 아니다 | 아니다 | 아니다 |

- 표가 보여 주는 포함 관계가 하나 있다. **안전하면 반드시 멱등이지만 그 역은 아니다** — PUT과
  DELETE가 멱등하면서 안전하지 않은 자리다 (§9.2.1, §9.2.2).[^fielding2022-rfc9110]
- POST의 캐시 가능은 조건부다. POST 응답은 **명시적 신선도 정보와, 값이 POST의 대상 URI와 같은
  `Content-Location` 헤더 필드를 함께 담을 때만** 캐시 가능하다
  (§9.3.3).[^fielding2022-rfc9110] 조건의 나머지와 캐시가 실제로 무엇을 하는가는 RFC 9111 영역이다.
