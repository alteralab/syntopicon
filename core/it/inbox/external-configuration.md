하나의 질문: **바뀔 값을 코드 밖 어디에 두고, 코드는 그것을 어떻게 읽어야 하는가.**

## 조문 — 애플리케이션을 매개변수화하라

- 출발 — **코드가 애플리케이션이 가동된 뒤에 바뀔 수 있는 값에 의존한다면 그 값을 앱 바깥에
  유지하라. 애플리케이션이 서로 다른 환경에서, 잠재적으로는 서로 다른 고객을 위해 돌 것이라면
  환경별·고객별 값을 앱 바깥에 유지하라. 이런 식으로 당신은 애플리케이션을 매개변수화하는 것이다;
  코드가 자기가 도는 자리에 적응한다** (Topic 32).[^thomas2020]
- 조문 (Topic 32):[^thomas2020]

> **Tip 55** Parameterize Your App Using External Configuration

- 이 Topic이 5장 안에 있는 이유를 5장 도입이 밝혀 둔다 — **유연한 채로 있는 좋은 방법 하나는 코드를
  **덜** 쓰는 것이다. 코드를 바꾸면 새 버그를 들일 가능성에 노출된다. Topic 32 설정(Configuration)은
  세부를 코드에서 완전히 빼내 더 안전하고 쉽게 바꿀 수 있는 자리로 옮기는 법을 설명한다**
  (5장 도입).[^thomas2020]

## 정적 설정 — 그리고 전역으로 만들지 말라는 처방

- 현황 — **많은 프레임워크와 꽤 많은 맞춤 애플리케이션이 설정을 평문 파일이나 데이터베이스 테이블에
  둔다. 정보가 평문 파일에 있다면 추세는 기성 평문 형식을 쓰는 것이다. 현재는 YAML과 JSON이
  여기에 인기 있다. 때로 스크립팅 언어로 쓰인 애플리케이션은 설정만 담는 데 전용된 특수 목적
  소스 코드 파일을 쓴다** (Topic 32).[^thomas2020]
  - **버전 조건**: YAML·JSON이 인기 있다는 것은 2019년 집필 시점의 관측이고, 조문(설정을 코드
    밖에 두라)은 형식 선택에 의존하지 않는다.
- 어느 쪽에 두는가 — **정보가 구조화돼 있고 고객이 바꿀 가능성이 높다면(예컨대 판매세율) 데이터베이스
  테이블에 저장하는 것이 나을 수 있다. 그리고 물론 둘 다 써서 설정 정보를 용도에 따라 나눌 수도
  있다** (Topic 32).[^thomas2020]
- **그리고 이 Topic의 핵심 처방** — **어떤 형식을 쓰든 설정은 보통 애플리케이션이 시작할 때
  자료 구조로 애플리케이션에 읽힌다. 흔히 이 자료 구조는 전역으로 만들어지는데, 그러면 코드의
  어느 부분에서든 그것이 담은 값에 닿기 쉬워진다는 생각에서다** (Topic 32).[^thomas2020]
  - **우리는 당신이 그러지 않기를 선호한다. 대신 설정 정보를 (얇은) API 뒤로 감싸라. 이것이 당신
    코드를 설정의 표현 세부에서 분리한다** (Topic 32).[^thomas2020]
  - 이것은 새 조문이 아니라 [결합 끊기](decoupling.md)의 Tip 48("전역이 될 만큼 중요하다면 API로
    감싸라")을 설정에 적용한 것이다. 설정이 그 조문의 가장 흔한 위반 사례라서 별도의 절을 받았다.

## 서비스로서의 설정

- 저자들의 선호 — **정적 설정이 흔하지만 우리는 현재 다른 접근을 선호한다. 우리는 여전히 설정
  데이터가 애플리케이션 바깥에 유지되기를 원하지만, 평문 파일이나 데이터베이스가 아니라 서비스 API
  뒤에 저장되기를 바란다** (Topic 32).[^thomas2020]
- 이득 넷 (Topic 32):[^thomas2020]
  - **여러 애플리케이션이 설정 정보를 공유할 수 있고, 인증과 접근 제어가 각자 볼 수 있는 것을
    제한한다**
  - **설정 변경을 전역적으로 할 수 있다**
  - **설정 데이터를 전용 UI로 유지보수할 수 있다**
  - **설정 데이터가 동적이 된다**
- **넷째가 이 절의 무게중심이다** — **마지막 항목, 곧 설정이 동적이어야 한다는 것은 우리가 고가용성
  애플리케이션으로 옮겨 감에 따라 결정적이다. 매개변수 하나를 바꾸려고 애플리케이션을 멈추고
  재시작해야 한다는 발상은 현대의 현실과 절망적으로 동떨어져 있다. 설정 서비스를 쓰면 애플리케이션의
  구성 요소가 자기가 쓰는 매개변수의 갱신 알림에 등록할 수 있고, 서비스는 값이 바뀌면 새 값을 담은
  메시지를 보낼 수 있다** (Topic 32).[^thomas2020]
  - 이 구조는 [현실 세계 다루기](juggling-the-real-world.md)의 발행/구독 그대로다 — 설정 서비스가
    채널이고 구성 요소가 구독자다. 저자들이 그 연결을 명시하지는 않는다.
- 형식과 무관한 정의 — **어떤 형태를 취하든 설정 데이터는 애플리케이션의 런타임 행동을 구동한다.
  설정 값이 바뀔 때 코드를 다시 빌드할 필요가 없다** (Topic 32).[^thomas2020]

## 도도 코드를 쓰지 마라

- 저자들의 맺음 — **외부 설정이 없으면 당신 코드는 될 수 있는 만큼 적응적이거나 유연하지 않다.
  이것이 나쁜 것인가? 음, 여기 현실 세계에서는 적응하지 않는 종은 죽는다** (Topic
  32).[^thomas2020]
- **도도새는 모리셔스 섬에서 인간과 그들의 가축의 존재에 적응하지 못했고 빠르게 멸종했다. 그것은
  인간의 손에 의한 최초의 기록된 종 멸종이었다. 당신의 프로젝트(또는 당신의 경력)가 도도새의 길을
  가게 하지 마라** (Topic 32).[^thomas2020]
  - 딸린 도도 삽화(`dodo.png`)는 **아카이브 판에서 유실됐다** — 직인용 대상에서 제외한다.

## 지나치게 하지 마라 — 저자들 자신의 정정

곁글 "Don't Overdo It"에서 저자들이 초판을 정정한다 (Topic 32).[^thomas2020]

- 정정의 이유 — **이 책의 초판에서 우리는 비슷한 방식으로 코드 대신 설정을 쓰라고 제안했는데,
  아무래도 지시에서 조금 더 구체적이었어야 했던 것 같다. 어떤 조언이든 극단으로 가거나 부적절하게
  쓰일 수 있으므로 여기 몇 가지 주의사항이 있다.**
- **① 지나치게 하지 마라** — **우리의 한 초기 고객은 애플리케이션의 모든 단일 필드가 설정 가능해야
  한다고 결정했다. 그 결과 가장 작은 변경을 하는 데도 몇 주가 걸렸는데, 필드와 그것을 저장하고
  편집하는 모든 관리 코드를 둘 다 구현해야 했기 때문이다. 그들은 **4만 개**의 설정 변수와 코딩의
  악몽을 손에 쥐게 됐다.**
- **② 게을러서 결정을 설정으로 밀지 마라** — **어떤 기능이 이렇게 동작해야 할지 저렇게 동작해야
  할지에 대해 진짜 논쟁이 있다면, 또는 그것이 사용자의 선택이어야 한다면, 한쪽으로 시도해 보고
  그 결정이 좋았는지 피드백을 받아라.**
  - 이 둘째 주의가 첫째보다 무겁다. 설정 항목 하나하나는 **미룬 결정**이고, 미룬 결정은 사라지지
    않고 사용자와 운영자에게 넘어간다. [헤드라이트를 앞지르지 마라](dont-outrun-your-headlights.md)의
    "작은 걸음으로 가고 피드백을 받아라"와 같은 판단이다.

## 자격 증명은 어디까지 설정인가

이 Topic은 **외부 서비스를 위한 자격 증명**을 설정에 담을 것들의 첫 항목으로 든다. 이 KB의 데이터
쪽에는 그보다 한 단계 더 나아간 처방이 있다.

- [세밀한 접근과 자격 증명 패턴](fine-grained-access-and-credential-patterns.md)의 **Secrets
  Pointer**는 설정에 자격 증명의 **값**이 아니라 **참조(이름)** 를 두고 실제 값은 비밀 관리자에서
  실행 시점에 가져오게 한다. 그쪽의 근거는 자격 증명이 코드베이스에 매이지 않고 별도 자산으로
  관리돼야 한다는 것이다.
- **대립이 아니라 겹쳐 쓸 수 있는 두 층이다.** 이 Topic의 요구는 "코드 밖으로 빼라"이고, 그쪽의
  요구는 "설정 밖으로도 빼라"이다. 이 Topic의 configuration-as-a-service(인증과 접근 제어로 각
  애플리케이션이 볼 수 있는 것을 제한한다)가 이미 그 방향을 가리키지만, **이 책은 설정 파일에 담긴
  자격 증명의 유출 경로를 논의하지 않는다.** #hypothesis 두 소스가 서로를 참조한 적은 없다.
- 조건을 붙여 읽으면 — 설정을 평문 파일에 두는 이 Topic의 정적 설정 방식은 **자격 증명이 아닌
  항목**에 대해서만 무조건 성립한다.
