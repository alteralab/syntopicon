## 두 낱말이 겹쳐 읽히는 이유

- [newman2021](../sources/newman2021.md)이 이 절을 여는 진단이 이렇다 — **마이크로서비스에
  결부된 기술 영역 가운데 서비스 메시(service mesh)와 API 게이트웨이(API gateway)만큼 주목과
  과대 선전과 혼란을 받은 곳이 드물다.** 둘 다 자기 자리가 있지만 **혼란스럽게도 책임이 겹칠 수
  있고**, 특히 API 게이트웨이는 **오용되고 잘못 팔리기 쉽다** (5장 §"Service Meshes and API
  Gateways", p.162).[^newman2021]
- **저자가 사정거리를 스스로 좁힌다** — 이 제품들로 무엇을 할 수 있는지 상세히 다루려 하지 않고,
  **어디에 들어맞고 어떻게 도움이 되며 어떤 함정을 피할 것인가의 개관**을 주려 한다고 적는다
  (5장, p.162).[^newman2021] 그러므로 이 페이지도 제품 설명서가 아니다.

## 남북 트래픽과 동서 트래픽

- 어휘가 데이터센터 관행에서 온다 — 전형적인 데이터센터 화법에서 **동서(east-west) 트래픽**은
  데이터센터 안을 오가는 것이고, **남북(north-south) 트래픽**은 바깥 세계에서 데이터센터로
  들어오거나 나가는 상호작용이다 (5장, p.162).[^newman2021]
- **저자가 데이터센터라는 낱말을 바꿔 쓴다** — 네트워크 관점에서 데이터센터가 무엇인지가
  흐릿해졌으므로, 더 넓게 **네트워크로 둘러친 테두리(networked perimeter)**를 말하겠다는
  것이다. 그 테두리는 데이터센터 전체일 수도, 쿠버네티스 클러스터일 수도, 같은 가상 LAN에서
  도는 기계 묶음 같은 가상 네트워크 개념일 수도 있다 (5장, p.162).[^newman2021]
- **책임을 가르는 문장이 이것이다** (5장, p.162):[^newman2021]

  > Speaking generally, an API gateway sits on the perimeter of your system and deals with
  > north-south traffic. Its primary concerns are managing access from the outside world to
  > your internal microservices. A service mesh, on the other hand, deals very narrowly with
  > communication between microservices inside your perimeter—the east-west traffic

- **다만 경계가 깨끗하지 않다고 저자가 곧바로 적는다** — 세상이 늘 그렇게 딱 떨어지지는 않으며,
  **여러 API 게이트웨이가 동서 트래픽을 위한 기능도 제공하려 한다** (5장, p.163).[^newman2021]
  그 시도에 대한 판정은 아래 [게이트웨이에 넣지 말아야 할 것 셋](#게이트웨이에-넣지-말아야-할-것-셋)에 있다.

## 둘의 공통 성질 — 코드 없이 공통 행위를 나눠 쓰는 프록시

- **둘을 한데 묶어 볼 수 있는 이유** — 서비스 메시와 API 게이트웨이는 **새 클라이언트 라이브러리나
  새 마이크로서비스를 만들지 않고도 마이크로서비스들이 코드를 나눠 쓰게 할 수 있다.** 아주 단순하게
  말하면 둘은 **마이크로서비스 사이의 프록시로 일할 수 있고**, 그래서 원래는 코드로 해야 했을
  **마이크로서비스 불가지(microservice-agnostic)의 행위** — 서비스 디스커버리나 로깅 같은 것 —
  를 구현하는 데 쓰일 수 있다 (5장, p.163).[^newman2021]
  - 그 대안이 무엇이었는지는
    [DRY 원칙](../concepts/dry-principle.md)의 마이크로서비스 절에 있다. 공통 행위를 공유
    라이브러리로 나눠 쓰면 **모든 사용처를 동시에 갱신할 수 없다**는 제약이 따라붙고, 프록시는
    그 제약을 피하는 다른 길이다.
- **절대 조건이 하나 붙는다** (5장, p.163):[^newman2021]

  > If you are using an API gateway or a service mesh to implement shared, common behavior for
  > your microservices, it's essential that this behavior is totally generic—in other words,
  > that the behavior in the proxy bears no relation to any specific behavior of an individual
  > microservice.

## API 게이트웨이가 하는 일

- **남북 쪽에 초점을 두므로 주된 관심사는 매핑이다** — 마이크로서비스 환경에서 API 게이트웨이의
  주된 관심사는 **외부 당사자의 요청을 내부 마이크로서비스로 매핑하는 것**이다. 그 책임은
  **단순한 HTTP 프록시로 이룰 수 있는 것과 닮았고**, 실제로 API 게이트웨이는 대개 **기존 HTTP
  프록시 제품 위에 기능을 더해 지어지며 주로 역방향 프록시(reverse proxy)로 기능한다** (5장
  §"API Gateways", p.163).[^newman2021]
- **그 위에 얹히는 정당한 기능들** — 외부 당사자를 위한 **API 키** 같은 기제, **로깅**, **속도
  제한(rate limiting)** 따위다. 일부 제품은 **개발자 포털(developer portal)**도 제공하고 그것은
  흔히 외부 소비자를 겨냥한다 (5장, p.163).[^newman2021]
  - 버전 조건: 2021년 저술 시점. 게이트웨이 제품이 HTTP 프록시 위에 지어지고 역방향 프록시로
    기능한다는 서술과 개발자 포털의 제공 여부는 그 시점의 제품 지형이다.
  - API 키로 클라이언트를 식별하는 것이 **옛 인터페이스의 사용을 추적하는 수단**으로 되불리는
    자리가 [계약을 깨는 변경의 관리](managing-breaking-api-changes.md)에 있다.

## 혼란의 출처 — API 경제라는 역사

- **저자는 혼란의 일부가 역사에서 온다고 적는다.** 한때 **"API 경제(the API economy)"**라 불린
  것에 엄청난 관심이 쏠렸다. 업계가 관리형 솔루션에 API를 제공하는 힘을 이해하기 시작했고
  (Salesforce 같은 SaaS 제품에서 AWS 같은 플랫폼까지), API가 고객에게 소프트웨어 사용 방식의
  훨씬 큰 유연성을 준다는 것이 분명했기 때문이다 (5장, p.163).[^newman2021]
  - 그래서 많은 이가 **이미 가진 소프트웨어의 기능을 GUI뿐 아니라 API로도 고객에게 노출하는
    이득**을 따져 보기 시작했고, 그 기대는 **더 큰 시장 기회를 열어 돈을 더 벌겠다**는 것이었다.
    그 관심 속에서 **API 게이트웨이 제품 무리가 등장했고**, 그 기능 집합은 **서드파티의 API 키
    관리·속도 제한 집행·차지백(chargeback) 목적의 사용 추적**에 크게 기울어 있었다 (5장,
    p.163).[^newman2021]
- **그 뒤에 온 현실이 과잉 기능을 남겼다** — API가 일부 고객에게 서비스를 전달하는 훌륭한 길임은
  확실히 증명됐지만 **API 경제의 크기는 기대만큼 크지 않았고**, 많은 회사가 **실제로는 필요하지
  않았던 기능을 잔뜩 실은 API 게이트웨이 제품을 사 버린 것**을 알게 됐다 (5장,
  pp.163–164).[^newman2021]
- **실제 쓰임은 훨씬 좁다** — 대개 API 게이트웨이가 실제로 하는 일은 **조직 자신의 GUI
  클라이언트**(웹 페이지·네이티브 모바일 앱)가 공개 인터넷을 거쳐 **자기 조직의 마이크로서비스에
  접근하는 것을 관리하는 것**이고, 거기에는 **서드파티가 없다** (5장, p.164).[^newman2021]
- **쿠버네티스에서는 이것이 필수가 된다** — 쿠버네티스는 **클러스터 안의 네트워킹만 기본으로
  다루고 클러스터 자체로 드나드는 통신에 대해서는 아무것도 하지 않으므로** 어떤 형태의 API
  게이트웨이가 필수적이다. 그러나 그 쓰임에서는 **외부 서드파티 접근을 위해 설계된 게이트웨이가
  엄청난 과잉**이다 (5장, p.164).[^newman2021]
  - 버전 조건: 2021년 저술 시점. 쿠버네티스가 클러스터 밖 통신을 다루지 않는다는 서술은 그
    시점의 플랫폼 기능 범위다.
- 그래서 저자의 조문이 이렇다 — **게이트웨이를 원한다면 거기서 무엇을 기대하는지 아주 분명히
  하라**는 것이고, 한 걸음 더 나아가 **너무 많은 일을 하는 API 게이트웨이는 아마 피해야 한다**고
  적는다 (5장, p.164).[^newman2021]

## 어떤 게이트웨이가 필요한가

- **쓰임을 알고 나면 종류가 정해진다** (5장 §"Where to use them", p.164):[^newman2021]
  - 쿠버네티스에서 도는 마이크로서비스를 노출하는 것뿐이라면 **자기 역방향 프록시를 직접 돌리거나**,
    더 낫게는 **그 쓰임을 위해 처음부터 지어진 좁은 초점의 제품**(저자가 드는 예는 Ambassador)을
    보라고 적는다.
  - **API에 접근하는 서드파티 사용자를 많이 관리해야 한다면** 볼 만한 다른 제품들이 있을 것이다.
  - **게이트웨이가 둘 이상이 될 수도 있다** — 관심사 분리를 낫게 하기 위해서이고, 저자는 많은
    상황에서 그것이 합리적일 수 있다고 본다. 다만 **전체 체계의 복잡성이 커지고 네트워크 홉이
    늘어난다는 통상적 단서**가 그대로 적용된다.
  - 버전 조건: 2021년 저술 시점. 제품 이름과 그 초점은 그 시점의 지형이다.
- **저자가 벤더 이름을 일부러 적지 않았다고 밝힌다** — 도구 선정을 돕는 일을 해 오면서 **API
  게이트웨이 영역에서 다른 어느 영역보다 잘못된 판매와 좋지 않거나 냉혹한 행태를 더 많이
  겪었고**, 그래서 **이 장에 일부 벤더 제품에 대한 언급을 두지 않았다**고 적는다 (5장,
  p.164).[^newman2021]
  - 저자가 그 사정을 짚는 방식이 이렇다 — API 경제의 호황기를 겨냥해 제품을 지은 벤처 투자
    회사들이 그 시장이 존재하지 않음을 알고 **두 전선에서 싸우고 있다**는 것이다. 복잡한
    게이트웨이가 제공하는 것을 실제로 필요로 하는 **적은 수의 사용자를 두고 다투면서**, 동시에
    **훨씬 단순한 필요를 위해 지어진 좁은 초점의 제품에 사업을 뺏기고 있다** (5장,
    p.164).[^newman2021]

## 게이트웨이에 넣지 말아야 할 것 셋

**저자가 §"What to avoid"로 따로 세운 절이다.** 오용 셋을 든다 (5장, p.164).[^newman2021]

- **① 호출 집계(call aggregation).** 처음은 순진하게 시작한다 — 호출 둘을 합쳐 적재물 하나를
  돌려준다. 그다음 같은 집계 흐름 안에서 **또 다른 하류 호출**을 하게 되고, 그다음 **조건 로직**을
  더하고 싶어지며, 머지않아 **핵심 업무 프로세스를 그 일에 맞지 않는 서드파티 도구 안에 구워
  넣었다**는 것을 알게 된다 (5장, p.165).[^newman2021]
  - **저자가 대신 갈 자리를 셋 지정한다** — 호출을 집계하고 걸러야 한다면
    [GraphQL](../concepts/graphql.md)이나 BFF 패턴(저자는 14장으로 미룬다)의 가능성을 보라는
    것이고, 그 집계가 **근본적으로 업무 프로세스라면 명시적으로 모델링한 사가(saga)로 하는 편이
    낫다**(저자는 6장으로 미룬다) (5장, p.165).[^newman2021]
- **② 프로토콜 재작성(protocol rewriting).** 저자는 이름을 밝히지 않은 어느 벤더가 자기 제품이
  **"어떤 SOAP API든 REST API로 바꿀 수 있다"**고 아주 공격적으로 밀던 것을 기억한다고 적고 둘로
  반박한다 — 첫째, **REST는 프록시 계층에서 그냥 구현할 수 있는 것이 아니라 아키텍처 사고방식
  전체**다. 둘째, **프로토콜 재작성은 중간 계층에서 할 일이 아니다** — 행위를 잘못된 자리로 너무
  많이 밀어내기 때문이다 (5장, p.165).[^newman2021]
  - REST가 왜 프록시 계층의 기능이 아닌지는
    [웹 서비스와 REST](../concepts/web-services-and-rest.md)의 REST 규정 절에 있다.
- **③ 모든 서비스 사이 호출의 중개.** API 게이트웨이나 보통의 네트워크 프록시를 두 마이크로서비스
  사이에 끼우면 **적어도 네트워크 홉 하나가 늘어난다.** A에서 B로 가는 호출이 A에서 게이트웨이로,
  게이트웨이에서 B로 간다. **그 추가 네트워크 호출의 지연과 프록시가 하는 일의 오버헤드를 따져야
  하고**, 저자는 이 문제를 **서비스 메시가 훨씬 잘 푼다**고 적는다 (5장, pp.165–166).[^newman2021]

## 파이프는 멍청하게 엔드포인트는 똑똑하게

- 위 ①과 ②가 공통으로 어기는 규칙을 저자가 한 문장으로 적는다 (5장, p.165):[^newman2021]

  > The main problem with both the protocol rewriting capability and the implementation of
  > call aggregation inside API gateways is that we are violating the rule of keeping the
  > pipes dumb, and the endpoints smart.

  - 이유가 이어진다 — 체계의 **"똑똑함"은 우리가 온전히 통제할 수 있는 우리 코드 안에 살고
    싶어 한다.** 이 예에서 API 게이트웨이는 **파이프**이고 되도록 단순하기를 바란다 (5장,
    p.165).[^newman2021]
- **조직 쪽 논거가 뒤따르고 이것이 이 절의 실무 판정이다** — 마이크로서비스로 밀고 가는 것은
  독립 배포 가능성을 통해 변경을 더 쉽게 내보내는 모형인데, **중간 계층에서도 변경해야 하면
  일이 어려워진다.** API 게이트웨이는 결정적(critical)이므로 그 변경이 대개 **엄격히 통제되고**,
  개별 팀이 중앙 관리되는 그것을 **셀프서비스로 고치도록 자유를 얻을 것 같지 않다. 그러면 무엇이
  따라오는가 — 티켓이다.** 자기 소프트웨어의 변경을 내보내려고 **API 게이트웨이 팀이 대신 고쳐
  주기를 기다리게 된다** (5장, p.165).[^newman2021]
  - 그래서 조문이 이렇다 — **API 게이트웨이(또는 엔터프라이즈 서비스 버스)로 행위를 많이 흘릴수록
    인수인계와 조율 증가와 느려진 전달의 위험이 커진다** (5장, p.165).[^newman2021]

## 서비스 메시가 떠맡는 것

- **규정** — 서비스 메시에서는 **마이크로서비스 사이 통신에 결부된 공통 기능이 메시로 밀려
  들어간다.** 그래서 마이크로서비스가 내부에 구현해야 할 기능이 줄고, 동시에 **어떤 일들이 어떻게
  이뤄지는가에 일관성이 생긴다** (5장 §"Service Meshes", p.166).[^newman2021]
- **메시가 구현하는 공통 기능의 목록** (5장, p.166):[^newman2021]

  > Common features implemented by service meshes include mutual TLS, correlation IDs, service
  > discovery and load balancing, and more.

  - **그 대안이 공유 라이브러리이고 거기서 문제가 둘 난다** — 이런 기능은 흔히 마이크로서비스마다
    꽤 범용이라 공유 라이브러리로 처리하게 되는데, 그러면 **서로 다른 마이크로서비스가 서로 다른
    판의 라이브러리를 돌릴 때**와 **서로 다른 런타임으로 쓰인 마이크로서비스가 있을 때**를
    감당해야 한다 (5장, p.166).[^newman2021]
  - **그 문제를 조직이 어떻게 풀었는지의 실물이 딸려 있다** — 넷플릭스는 적어도 역사적으로는
    **비지역 네트워크 통신을 전부 JVM 대 JVM으로 하도록 강제했다.** 검증된 공통 라이브러리를
    재사용하기 위해서였다 (5장, p.166).[^newman2021]
  - **메시가 바꾸는 것이 그 자리다** — 메시를 쓰면 **서로 다른 프로그래밍 언어로 쓰인
    마이크로서비스들에 걸쳐 공통 기능을 재사용할 가능성**이 생기고, **서로 다른 팀이 만든
    마이크로서비스에 표준 행위를 구현하는 데도 굉장히 유용하다** (5장, p.166).[^newman2021]
- **가장 큰 이득으로 저자가 꼽는 것은 변경의 전파 방식이다** — 이 공통 기능을 오직 공유
  라이브러리로만 구현했다면 행위를 바꿀 때 **모든 마이크로서비스가 새 판을 끌어와 배포해야**
  변경이 살아난다. 메시가 있으면 **재빌드와 재배포 없이** 서비스 사이 통신의 변경을 내보내는
  유연성이 훨씬 커진다 (5장, p.166).[^newman2021]

## 어떻게 도는가 — 프록시를 같은 기계에 붙인다

- **설계의 출발점이 홉 수다** — 마이크로서비스 아키텍처에서는 일반적으로 **남북 트래픽보다 동서
  트래픽이 많을 것**을 예상한다. 주문 하나를 넣는 남북 호출 하나가 **여러 동서 호출**을 낳을 수
  있다. 그래서 테두리 안쪽 호출에 프록시를 두려 할 때 **그 추가 호출이 부르는 오버헤드를 의식해야
  하고**, 그것이 메시가 지어지는 방식의 핵심 고려 사항이다 (5장 §"How they work",
  p.166).[^newman2021]
- **메시들을 하나로 묶는 성질** — 모양과 크기는 제각각이지만 공통점은 **아키텍처가 프록시를
  드나드는 호출의 영향을 제한하려는 데 바탕을 둔다**는 것이고, 그것은 주로 **프록시 프로세스를
  마이크로서비스 인스턴스와 같은 물리 기계에서 돌게 분산해 원격 네트워크 호출 수를 제한**함으로써
  이뤄진다 (5장, p.167).[^newman2021]
  - 저자가 도판으로 드는 경로는 이렇다 — Order Processor가 Payment 마이크로서비스에 요청을 보내면
    그 호출은 먼저 **같은 기계에서 도는 프록시 인스턴스로 지역 라우팅되고**, 그다음 Payment 쪽의
    지역 프록시를 거쳐 이어진다. **Order Processor는 보통의 네트워크 호출을 한다고 여기며 그
    호출이 기계 안에서 지역 라우팅된다는 것을 알지 못한다.** 그 경로가 **현저히 빠르고 분할
    (partition)에도 덜 취약하다** (5장, p.167).[^newman2021]
- **제어 평면(control plane)이 그 위에 얹힌다** — 지역 메시 프록시들 위에 앉아 **프록시의 행위를
  바꿀 수 있는 자리이자 프록시가 하는 일에 대한 정보를 모으는 자리**가 된다 (5장,
  p.167).[^newman2021] 상호 TLS를 구현할 때는 **제어 평면이 클라이언트와 서버 인증서를 배포하는
  데 쓰인다** (5장, p.168).[^newman2021]
- **쿠버네티스에서의 배치** — 마이크로서비스 인스턴스마다 **자기 지역 프록시와 함께 파드(pod)에
  배포한다.** 파드는 늘 한 단위로 배포되므로 **프록시가 있다는 것을 언제나 알 수 있고**, 프록시
  하나가 죽어도 **그 파드 하나에만 영향이 간다.** 이 배치는 **목적에 따라 프록시마다 다르게 설정할
  수 있게도 한다** (5장, p.167).[^newman2021]
  - 버전 조건: 2021년 저술 시점. 파드 단위 배포와 그것이 프록시 가용성에 주는 보장은 그 시점의
    쿠버네티스 동작이다.
  - **파드가 컨테이너 여럿을 담는 드문 경우로 저자가 드는 예가 바로 이 사이드카 프록시다** (8장
    §"A Simplified View of Kubernetes Concepts", pp.260–261).[^newman2021] 파드가 무엇인지와
    서비스·디플로이먼트와의 관계는
    [컨테이너 오케스트레이션과 쿠버네티스](container-orchestration-and-kubernetes.md)에 있다.
- **구현체들이 공통으로 쓰는 프록시** — 많은 서비스 메시 구현이 이 지역 프로세스의 바탕으로
  **Envoy 프록시**를 쓴다. Envoy는 **가벼운 C++ 프록시**로 서비스 메시와 다른 종류의 프록시 기반
  소프트웨어의 구성 요소로 자주 쓰이며, 예컨대 **Istio와 Ambassador의 중요한 구성 요소**다 (5장,
  pp.167–168).[^newman2021]
  - 버전 조건: 2021년 저술 시점. 제품 이름과 그 구성 요소 관계는 그 시점의 지형이다.

## 메시는 똑똑한 파이프가 아닌가

- **저자가 자기 논의에 스스로 반문한다** — 공통 행위를 메시로 미는 이야기가 누군가에게는 경보음을
  울릴 수 있다. **이 접근은 엔터프라이즈 서비스 버스나 지나치게 비대한 API 게이트웨이와 같은
  종류의 문제에 열려 있지 않은가. 너무 많은 "똑똑함"을 메시로 밀어 넣는 위험이 아닌가** (5장
  §"Aren't service meshes smart pipes?", p.168).[^newman2021]
- **저자의 답은 범용성이다** — 기억할 핵심은 **메시에 넣는 공통 행위가 어느 한 마이크로서비스에도
  특정되지 않는다**는 것이다. **업무 기능은 바깥으로 새어 나가지 않았고**, 설정하는 것은 **요청
  타임아웃을 어떻게 다루는가** 같은 범용적인 것들이다 (5장, p.168).[^newman2021]
- **마이크로서비스마다 조정하고 싶은 공통 행위**에 대해서도 대개 잘 마련돼 있어서 **중앙 플랫폼에
  작업이 필요하지 않다.** 저자가 드는 예는 Istio에서 **서비스 정의를 바꾸는 것만으로 타임아웃
  요구를 셀프서비스로 정의**하는 것이다 (5장, p.168).[^newman2021]
  - 버전 조건: 2021년 저술 시점. 셀프서비스 설정이라는 제품 기능의 예다.
  - **이것이 위 게이트웨이 절의 티켓 논거와 짝이 되는 자리다.** 게이트웨이를 기각한 이유가
    중앙 통제와 티켓이었으므로, 메시가 그 비판을 피하는 근거도 **셀프서비스가 되는가**로
    제시된다.

## 하나 들여야 하는가

- **저자가 자기 판단의 이력을 그대로 적는다** (5장 §"Do you need one?", p.168):[^newman2021]
  서비스 메시가 인기를 얻기 시작한 것은 이 책 초판이 나온 직후였고, 저자는 발상의 값어치를 크게
  보면서도 **이 영역의 잦은 변동(churn)**을 보았다. 서로 다른 배치 모형이 제안되고 지어지고
  버려졌으며, 솔루션을 내놓는 회사 수가 급격히 늘었는데 **오래된 도구들조차 안정성이 뚜렷이
  부족했다.**
  - 실물 둘이 든다 — **Linkerd**는 이 영역을 개척하는 데 누구 못지않게 기여했으나 **v1에서 v2로
    가면서 제품을 처음부터 완전히 다시 지었고**, **Istio**는 구글이 낙점한 메시였으나 **첫 1.0
    릴리스까지 몇 해가 걸렸고** 그 뒤로도 아키텍처에 큰 변경이 있었다(제어 평면을 다소 역설적이지만
    합리적으로 **더 모놀리식한 배치 모형**으로 옮겼다) (5장, p.168).[^newman2021]
  - 버전 조건: 2021년 저술 시점. 여기 든 제품 판본의 이력과 안정성 판정은 그 시점까지의 관찰이다.
- **그래서 저자의 조언이 지난 5년 대부분 동안 이랬다** — "서비스 메시를 들여야 하는가"라는 물음에
  **"선택을 6개월 미룰 여유가 있다면 6개월 미루라"**고 답했다는 것이다. 발상에는 설득됐지만
  **안정성이 걱정이었고**, 메시 같은 것은 **개인적으로 위험을 많이 지고 싶은 자리가 아니다** —
  모든 것이 잘 도는 데 너무 결정적이고 **임계 경로(critical path)에 올려 두는 것**이다. 저자는
  이것을 **메시지 브로커나 클라우드 제공자를 고르는 것과 같은 급으로 진지하게** 다룬다고 적는다
  (5장, p.168).[^newman2021]
- **저술 시점의 채점은 완화된다** — 그 뒤로 이 영역이 성숙했고 변동이 어느 정도 느려졌으며,
  여전히 **(건강한) 벤더의 복수성**이 남아 있다고 적는다 (5장, p.169).[^newman2021]
- **그럼에도 모두를 위한 것은 아니다** (5장, p.169):[^newman2021]
  - **쿠버네티스 위가 아니면 선택지가 제한된다.**
  - **복잡성이 더해진다.** 마이크로서비스가 다섯이라면 서비스 메시를 정당화하기 어렵다고 저자는
    본다(그리고 다섯뿐이라면 쿠버네티스 자체를 정당화할 수 있는지도 논쟁적이라고 덧붙인다).
  - **마이크로서비스가 더 많은 조직**, 특히 그것들을 **서로 다른 프로그래밍 언어로 쓰고 싶은**
    조직이라면 볼 값어치가 충분하다.
  - **다만 숙제를 하라** — **메시 사이를 갈아타는 일은 고통스럽다.**
  - 버전 조건: 2021년 저술 시점. 쿠버네티스 밖에서 선택지가 제한된다는 관찰은 그 시점의 지형이다.
  - **메시가 다른 것의 전제가 되는 자리도 있다** — 버전 조건: 2021년 저술 시점에 쿠버네티스에
    FaaS식 개발자 경험을 얹으려는 Knative는 **서비스 메시를 필수로 요구하고 안정적이라 여겨지는
    것이 Istio뿐**이라, **Knative를 채택하면 Istio까지 받아들이게 된다** (8장 §"And Knative",
    p.267).[^newman2021] 곧 위 "메시 사이를 갈아타는 일은 고통스럽다"는 단서가 **메시 위에 얹는
    것을 고를 때도 걸린다.**
- **실물 하나가 그 판정을 예시한다** — Monzo는 서비스 메시 사용이 자기 아키텍처를 그 규모로 돌리는
  데 **필수적이었다**고 공개적으로 말한 조직이다. Linkerd v1로 마이크로서비스 사이 RPC 호출을
  관리한 것이 크게 이로웠다. 흥미로운 것은 **Monzo가 필요한 규모에 이르기 위해 메시 이전의 고통을
  겪어야 했다**는 것이다 — Linkerd v1의 옛 아키텍처가 요구를 더는 만족시키지 못하자, 결국
  **Envoy 프록시를 쓰는 사내 서비스 메시로 옮겼다** (5장, p.169).[^newman2021]

## HTTP 밖의 프로토콜

- **사정거리의 한계가 명시된다** — API 게이트웨이와 서비스 메시는 **주로 HTTP 관련 호출을 다루는
  데 쓰인다.** 그래서 REST·SOAP·gRPC 따위는 이 제품들로 관리할 수 있다 (5장 §"What About Other
  Protocols?", p.169).[^newman2021]
- **다른 프로토콜로 가면 흐릿해진다** — 카프카 같은 메시지 브로커를 쓰는 통신을 보기 시작하면
  사정이 더 애매해지고, **전형적으로 이 지점에서 서비스 메시는 우회된다** — 통신이 **브로커와 직접**
  이뤄진다. 그러므로 **서비스 메시가 마이크로서비스 사이 모든 호출의 중개자로 일할 수 있다고
  가정할 수 없다** (5장, p.169).[^newman2021]
  - 브로커를 거치는 쪽의 기제는
    [발행/구독 메시징](../concepts/publish-subscribe-messaging.md)과
    [로그 기반 메시지 브로커](../concepts/log-based-message-brokers.md)에 있다.

## 11장 — 이 두 중개자가 지는 보안 책임

**11장이 이 두 층에 일을 셋 얹는다.** 전문은 보안 페이지들이 갖고 여기에는 **이 중개자에
무엇이 들어오며 그것이 위 조문과 어떻게 만나는가**만 둔다.

- **① 메시가 상호 TLS의 구현 수단이다.** 버전 조건: 2021년 저술 시점. 저자는 **상호 TLS
  구현의 과제가 역사적으로 도구였고 지금은 덜한 문제**라고 적으며, **상호 TLS 사용을 단순하게
  만들고 싶다는 것이 사람들이 서비스 메시를 구현하는 주된 이유 중 하나**라고 못박는다 (11장,
  p.371).[^newman2021]
  - 위 §"서비스 메시가 떠맡는 것"의 공통 기능 목록 첫 항목이 그것이었다. **11장이 그 항목에
    왜라는 답을 붙인다.**
  - 그 기제와 넷 중 어느 관심사를 다루는지는
    [전송 중 데이터와 정지 데이터의 보호](securing-data-in-transit-and-at-rest.md)에 있다.
- **② 게이트웨이가 단일 사인온의 핸드셰이크를 모으는 자리다.** 신원 제공자로의 리다이렉션과
  핸드셰이크를 마이크로서비스마다 처리하면 기능이 크게 중복되고 공유 라이브러리로는 기술 스택이
  갈릴 때 풀리지 않는다. **그래서 더 흔한 방식이 서비스와 바깥 세계 사이에 앉은 게이트웨이로
  그 행위를 한 자리에 모으는 것**이다 (11장, pp.377–378).[^newman2021]
  - **저자가 권하는 것이므로 위 §"게이트웨이에 넣지 말아야 할 것 셋"의 반례가 아니다.**
    거기서 기각된 것은 호출 집계와 프로토콜 재작성과 동서 호출의 중개였고, 인증 핸드셰이크는
    **바깥 테두리를 넘는 남북 트래픽의 공통 관심사**라 게이트웨이의 정당한 일에 든다.
  - **다만 인가는 갈린다.** 게이트웨이가 하는 것은 **굵은 입도의 판정**까지이고(로그인하지
    않은 사용자를 막는 것, 역할로 애플리케이션 접근을 가르는 것), **어떤 연산을 허용할지의
    세밀한 판정은 마이크로서비스 자신에게 지역적이어야 한다** (11장, p.379).[^newman2021]
    그 논거가 **독립 배포 가능성**이다 — 배포가 마이크로서비스 배포와 상류 게이트웨이 설정 적용
    둘 다를 포함하면 독립적이지 않다 (11장, pp.381–382).[^newman2021]
    - **이것이 위 §"파이프는 멍청하게 엔드포인트는 똑똑하게"와 같은 조문의 인가 판이다.**
      전문은 [서비스 사이 인증과 인가](service-to-service-authentication-and-authorization.md)에
      있다.
- **③ 게이트웨이가 비대해지는 위험이 보안 쪽에서 되풀이된다.** 게이트웨이로 HTTPS를 종단하고
  침입 탐지를 돌릴 수도 있으나, **게이트웨이 계층은 점점 더 많은 기능을 떠맡는 경향이 있고
  그 자체가 거대한 결합 지점이 될 수 있으며 기능이 많을수록 공격 표면도 커진다** (11장,
  p.379).[^newman2021]
  - **11장이 더하는 논거 둘** — 인증을 게이트웨이에 떠넘기면 **마이크로서비스 하나를 격리해
    두고 그 행동을 따지기가 더 어려워지고**, **게이트웨이가 모든 단계를 처리해 주리라 믿는 것이
    거짓 보안감을 낳아 단일 장애점을 만든다** (11장, pp.378–379).[^newman2021]
- **클라이언트 신원 확인에 대한 경고 하나도 이 층을 겨눈다** — 저자는 **서버가 클라이언트 신원을
  확인하려고 중앙 서비스에 호출을 거는 해법들**을 봤다고 적고 **API 게이트웨이 벤더가 미는
  것들이 거기 든다**고 밝히며, **지연의 함의를 생각하면 꽤 정신 나간 일**이라고 적는다 (11장,
  p.371).[^newman2021] 위 §"게이트웨이에 넣지 말아야 할 것 셋"의 셋째와 같은 계열의 경계다.

## 14장 — 게이트웨이가 아니라 BFF

**위 §"게이트웨이에 넣지 말아야 할 것 셋"의 첫째 항이 14장에서 해소된다.** 5장은 호출 집계를
게이트웨이에서 기각하면서 대신 갈 자리로 GraphQL과 BFF 패턴을 가리키고 그 비교를 14장으로
미뤘다. 14장이 그 자리를 채운다.

- **14장이 권하는 배치는 집계를 없애는 것이 아니라 옮기는 것이다** — **프런트엔드를 위한
  백엔드(backend for frontend, BFF)**는 **사용자 인터페이스 하나를 위해 개발된 단일 목적의
  집계 층**이고, 전형적으로 **그 UI와 같은 팀이 유지보수한다** (14장 §"Pattern: Backend for
  Frontend (BFF)", pp.480–481).[^newman2021]
- **5장의 금지가 14장에서 되풀이된다.** 14장은 API 키 관리·사용자 인증·호출 라우팅 같은 일반
  관심사를 API 게이트웨이 제품에 맡기는 것은 합당할 수 있다고 적으면서도, **그 제품으로 호출
  집계와 걸러 내기까지 하려는 것은 경계하라**고 다시 못 박는다 (14장 §"Multiple Concerns",
  p.479):[^newman2021]

  > So if you want to make use of a dedicated API gateway, go ahead—but strongly consider
  > having your filtering and aggregation logic elsewhere.

  - 14장이 더하는 논거 하나가 위 §"게이트웨이에 넣지 말아야 할 것 셋"의 첫째 항과 같은 기제다 —
    **집계 패턴이 실은 그 자체로 마이크로서비스가 될 만한 도메인 기능임을 깨닫는 일이 흔한데**,
    그 행동이 **벤더 고유 설정 안에 있으면 옮기기가 더 곤란하고 다시 발명해야 할 가능성이
    높다** (14장, p.479).[^newman2021]
- **모순이 아니라 경계가 둘로 갈린다.**
  - **무엇인가** — 5장이 금지한 것은 **테두리에 놓인 범용 중개자 안에 업무 로직과 집계를 구워
    넣는 것**이다. BFF는 **우리가 소유한 별개의 배포 단위**이므로 위
    §"파이프는 멍청하게 엔드포인트는 똑똑하게"의 규칙을 어기지 않는다 — 파이프가 아니라
    엔드포인트 쪽이다.
  - **몇 개인가** — 이 페이지의 게이트웨이는 **체계의 테두리에 놓여 남북 트래픽 전체를 본다.**
    BFF는 **사용자 경험 하나마다 하나**다. 위 §"어떤 게이트웨이가 필요한가"가 게이트웨이를 둘
    이상 두는 경우를 관심사 분리로 적어 두었지만, 그것과 BFF는 **재는 대상이 다르다** — 그쪽은
    테두리의 분할이고 이쪽은 UI별 집계 층이다.
- 전문은 [프런트엔드를 위한 백엔드](backend-for-frontend.md)가 갖는다 — 중앙 집약 게이트웨이가
  앓는 문제 셋과 BFF를 몇 개 둘 것인가, 그리고 GraphQL을 그 구현으로 쓰는 판정이 거기 있다.

## 이 KB의 다른 자리에서 온 같은 낱말들

**"서비스 메시"와 "사이드카"는 이 KB에 이미 두 자리에서 들어와 있었다. 대상이 갈리므로 적어
둔다.**

- [서비스 디스커버리와 로드 밸런싱](../concepts/service-discovery-and-load-balancing.md)은
  서비스 메시를 **로드 밸런싱의 정교한 형태**로 규정한다 — 소프트웨어 로드 밸런서와 서비스
  디스커버리를 결합해 사이드카로 배포하고, 클라이언트와 서버가 지역 연결로만 오가므로 **연결
  암호화를 로드 밸런서 수준에서 처리**할 수 있고 관측 가능성도 얻는다는 것이다.
  - **이 페이지의 서술과 같은 대상이고 같은 방향이다.** 이 페이지가 더하는 것은 **왜 프록시를
    같은 기계에 붙이는가**(동서 호출이 남북보다 많아 홉 오버헤드가 곱해진다)라는 설계 근거와,
    **제어 평면**이라는 둘째 구성 요소와, **똑똑한 파이프가 되지 않는 조건**이다.
- [데이터 프로덕트의 포트와 사이드카](../concepts/data-product-ports-and-sidecar.md)의
  사이드카는 **데이터 프로덕트의 정책 실행과 표준 API를 맡는 프로세스**다. **낱말이 같고 계열도
  같다** — 그쪽 원전 스스로 이 패턴이 운영 시스템 아키텍처의 사이드카 패턴에서 왔고 서비스
  메시가 그것을 쓴다고 적는다. **갈리는 것은 무엇을 사이드카에 넣는가다** — 그쪽은 데이터
  프로덕트의 거버넌스 정책이고 이 페이지는 마이크로서비스 사이 통신의 공통 관심사다. 합치지
  않는다.
- [모델 게이트웨이](../concepts/model-gateway.md)는 **같은 낱말의 다른 것**이다. 그쪽 관문이
  중개하는 것은 모델 제공자 API이고, 여기 게이트웨이가 중개하는 것은 체계의 테두리를 넘는
  트래픽이다.
- [안정성 패턴](stability-patterns.md)의 기제 여럿이 **이 층에 얹힐 수 있는 같은 행위**다.
  같은 책이 9장에서 **회로 차단을 서비스 메시 구현에 맡기는 경우**를 공유 기능의 예로 들고
  (9장, p.302), 12장은 시간 초과와 서킷 브레이커를 **애플리케이션이 지는 책임**으로
  적는다.[^newman2021]
  - **어느 층에 둘 것인가를 이 책이 판정하지 않는다.** 5장의 메시 기능 목록에 시간
    초과·재시도·서킷 브레이커는 들어 있지 않고(목록은 상호 TLS·상관 ID·서비스 디스커버리와
    로드 밸런싱이다), 12장은 어느 층에서 구현할지를 말하지 않는다. **두 자리를 잇는 것은 이
    KB의 읽기이고 이 책의 조문이 아니다** #hypothesis.
  - 다만 위 [서비스 메시가 떠맡는 것](#서비스-메시가-떠맡는-것)의 판정은 그대로 걸린다 —
    공유 라이브러리로만 구현하면 행위를 바꿀 때 모든 마이크로서비스가 새 판을 끌어와 배포해야
    한다는 것이고, 안정성 패턴의 설정값(시간 초과 문턱·브레이커 문턱)은 바로 그렇게 자주
    바뀌는 종류다 #hypothesis.

## 사이드카와 메시를 직교 운영 결합으로 다시 읽는 소스

**다른 소스가 같은 두 구조물에 결합의 이름을 붙인다.** 포드 외는 사이드카와 서비스 메시를
편의 기능이 아니라 **직교 결합(orthogonal coupling)을 다루는 재사용 패턴**으로 규정한다 (5장
§"Sidecars and Service Mesh: Orthogonal Operational Coupling", pp.114–118).[^ford2022-evolutionary]

- **직교 결합의 정의** — 수학에서 두 직선이 직각으로 만나면 직교이고 그것이 독립을 함축하듯,
  아키텍처의 두 부분이 **서로 구별되는 목적을 갖되 완전한 해법을 이루려면 만나야 할 때** 직교
  결합이라 부른다. 이 장의 명백한 예가 **도메인 행동과 독립이면서도 필요한 운영 관심사**(모니터링
  같은 것)다. 직교 결합을 알아보면 **관심사 사이에 얽힘이 가장 적은 교차점**을 찾을 수 있다는
  것이 저자들의 주장이다 (5장 옆글 "Orthogonal Coupling", p.118).[^ford2022-evolutionary]
- **문제 설정이 이 페이지와 같다.** 마이크로서비스는 중복을 선호해 결합을 피하는데, **높은 결합이
  오히려 이로운 능력**이 있다 — 모니터링, 로깅, 인증과 인가, 서킷 브레이커 같은 것이다. 팀마다
  알아서 하게 두면 혼돈이 된다 (5장, p.114).[^ford2022-evolutionary] 저자들이 던지는 두 물음이
  구체적이다 — **팀마다 모니터링을 구현한다면 운영 팀은 그것을 했는지 어떻게 확신하는가**, 그리고
  **도구를 조직 전체에서 올려야 할 때 팀들이 어떻게 보조를 맞추는가**.
  - 위 [서비스 메시가 떠맡는 것](#서비스-메시가-떠맡는-것)이 같은 목록을 뉴먼 쪽 서술로 담고
    있다. **두 소스가 같은 문제를 같은 구조물로 푼다.**
- **계보를 더 멀리 잡는다.** 저자들은 사이드카 패턴이 앨리스터 코오번(Alistair Cockburn)의
  **육각형 아키텍처(Hexagonal architecture)**, 달리 **포트와 어댑터 패턴(Ports and Adapters
  pattern)**이라 불리는 훨씬 이른 패턴에 기반한다고 적는다. 도메인 로직이 육각형 가운데 있고
  생태계의 다른 부분으로 가는 포트와 어댑터가 그것을 둘러싼다 (5장, pp.114–115).[^ford2022-evolutionary]
  - **한 가지가 다르다고 명시한다** — 데이터 충실도다. 육각형 아키텍처는 데이터베이스를 갈아 끼울
    수 있는 또 하나의 어댑터로 다뤘는데, 도메인 주도 설계의 통찰은 **데이터 스키마와 트랜잭션성이
    안쪽에 있어야 한다**고 본다. 마이크로서비스가 그쪽이다 (5장, p.115).[^ford2022-evolutionary]
  - **이 KB가 확인한 원전이 아니다** — 귀속은 이 책이 그렇게 귀속한다까지로 둔다.
- **메시가 서는 조건이 적합도 함수다.** 모든 서비스가 사이드카 구성 요소를 포함한다고 아키텍트와
  운영이 **안전하게 가정할 수 있으면**(적합도 함수가 그것을 거버넌스한다) 그것이 메시를 이룬다
  (5장, p.117).[^ford2022-evolutionary] 위 [하나 들여야 하는가](#하나-들여야-하는가)의 판단
  기준에 이 조건이 더해진다. 그 기제는
  [자동화된 아키텍처 거버넌스](automated-architectural-governance.md)에 있다.
- **거버넌스 쪽 쓰임을 하나 더 든다.** 사이드카 패턴은 엔터프라이즈 아키텍트 같은 거버넌스
  집단에게 **너무 많은 다중 언어 환경에 대한 합리적 제동**을 준다. 마이크로서비스의 이점 하나가
  공통 플랫폼 대신 통합에 기대는 것이라 팀마다 복잡도와 능력 수준을 고를 수 있는데, **플랫폼이
  늘어나면 통일된 거버넌스가 어려워진다.** 그래서 메시의 일관성을 이종 플랫폼에 걸친 인프라와
  횡단 관심사의 동력으로 쓴다 — 메시가 없으면 **그 해법을 떠받치는 플랫폼마다 사이드카를 하나씩**
  지어야 한다 (5장, p.117).[^ford2022-evolutionary]
- **디자인 패턴 하나에 빗댄다** — 사이드카와 메시가 분산 아키텍처에 횡단 관심사를 퍼뜨리는 깔끔한
  방법이고, 이것이 **데코레이터 패턴의 아키텍처판**이라는 것이다. 보통의 연결과 독립적으로 분산
  아키텍처를 가로질러 행동을 "장식"하게 해 준다 (5장, p.118).[^ford2022-evolutionary]
- **같은 낱말의 셋째 용법이 이 KB에 이미 있다.**
  [데이터 프로덕트의 포트와 사이드카](data-product-ports-and-sidecar.md)가 데이터 메시 쪽
  사이드카를 갖는다. 포드 외는 그 둘을 **같은 직교 재사용 패턴의 두 적용**으로 잇는다 — 운영
  결합과 데이터 결합이다. 그 절은 아래 데이터 쪽 페이지에 적었다.
- **넷째 용법이 이벤트 기반 쪽에서 들어온다.** 벨마어는 사이드카 패턴을 **레거시 코드베이스를
  안전하게 고칠 수 없을 때 원본 코드를 건드리지 않고 이벤트 기반 기능을 얻는 길**로 쓴다 — 기본
  프로듀서/컨슈머 하나가 이벤트 스트림을 소비해 그 체계의 데이터 저장소에 업서트하고, 사이드카는
  **자기 컨테이너 안에 살되 그 서비스의 단일 배포 단위의 일부**다 (11장 §"Integration with
  Existing Systems Using the Sidecar Pattern", pp.248–249).[^bellemare2025]
  - **위 세 용법과 실어 나르는 것이 다르다** — 뉴먼과 포드 쪽 사이드카는 **운영 관심사**(모니터링·
    로깅·인증)를 담고, 데이터 메시 쪽은 **데이터 결합**을 담으며, 이쪽은 **업무 데이터 자체를
    스트림에서 저장소로 옮긴다.** 같은 배치 구조(같은 배포 단위 안의 별도 컨테이너)를 쓰되
    **책임의 종류가 넷째 칸이다.** **이 대비는 이 KB가 네 원문을 맞대어 세운 것이고 벨마어는 앞의
    셋을 호명하지 않는다.** #hypothesis
  - **대가도 같은 자리에 적힌다** — **복잡도와 조율의 증가**이고, 특히 **두 구성 요소를 함께
    배포하고 함께 되돌릴 수 있어야** 한다는 것이다 (11장, p.249).[^bellemare2025] 위
    [하나 들여야 하는가](#하나-들여야-하는가)의 비용 목록과 같은 종류다.
  - **같은 저자가 14장에서 이 넷째 용법을 한 번 더 쓴다. 다섯째 칸이 아니라 같은 칸의 변종이다.**
    **SQL은 마이크로서비스 안에서는 하기 너무 어려운 일을 맡는 사이드카 능력을 줄 수 있고, 많은
    기본 프로듀서/컨슈머 프레임워크에 없는 조인과 복잡한 집계를 SQL이 메운다.** 저자 자신이
    그 자리에서 11장의 사이드카 절을 명시로 가리킨다 (14장 §"SQL as a Sidecar",
    pp.293–294).[^bellemare2025]
    - **판정 — 실어 나르는 것이 다르되 넷째 칸 안이다.** 11장의 사이드카는 **업무 데이터를
      스트림에서 저장소로 옮기고**, 14장의 SQL 사이드카는 **조인·윈도잉·집계·복잡한 상태 기계라는
      처리 능력을 떠맡는다.** 둘 다 **레거시나 빈약한 프레임워크의 결핍을 바깥에서 메우는 이벤트
      기반 능력**이라는 점이 같고, **배치 구조도 생명 주기 결합 조항도 같다**(마이크로서비스를
      끝낼 때 SQL 잡도 끝나게 해 좀비 프로세스가 남지 않게 하라는 조항이 11장의 함께 배포하고
      함께 되돌리라는 조항과 같은 종류다). 그래서 **다섯째 칸을 세우지 않았다. 이 판정은 이 KB의
      것이다.** #hypothesis
    - 14장 쪽의 나머지는
      [이벤트 기반 마이크로서비스의 네 모양](event-driven-microservice-shapes.md)이 갖는다 —
      그 출력 스트림이 **하류 마이크로서비스만 쓰라고 지어진 사적 스트림**이고 **조이너와
      서비스가 하나의 경계 컨텍스트 안에** 있다는 배치가 거기 있다.

## 같은 읽기의 먼저 나온 판과 거기에만 있는 것

**위 절의 내용이 같은 저자 무리의 2021년 책 8장에 먼저 실려 있다.** 그쪽은 이 논증을 **재사용
패턴 넷 가운데 하나**로 놓고, 직교 결합 곁상자와 육각형 계보와 거버넌스 쪽 쓰임과 데코레이터
비유가 **낱말 수준에서 같다** (8장 §"Sidecars and Service Mesh", pp.234–239, 곁상자
"Orthogonal Coupling"(p.238) 포함).[^ford2021-hard-parts]

- **선후는 서지 사실로 정해진다** — 2021년 책이 2021년 10월, 2022년 책이 그 이듬해의 2판이다.
  저자 구성이 겹치나 같지 않고(2021년은 Ford·Richards·Sadalage·Dehghani, 2022년은
  Ford·Parsons·Kua·Sadalage) 겹치는 사람은 Ford와 Sadalage 둘이다. **두 책 어느 쪽도 이
  자리에서 상대를 가리키지 않는다.** 방향은 이 KB가 서지 사실로 세운 것이다. #hypothesis
- **대리 회사 이름이 다르다** — 같은 모니터링 표준화 논증에서 2021년 책은
  `Penultimate Electronics`를, 2022년 책은 `PenultimateWidgets`를 쓴다. 둘 다 저자들의 대리
  회사다.
- **2021년 판에만 있는 것 넷이다.**

  **하나 — 절충표.** 2022년 판에는 없고 2021년 판에만 있다 (8장, 표 8-4,
  p.239):[^ford2021-hard-parts]

  | Advantages | Disadvantages |
  |---|---|
  | Offers a consistent way to create isolated coupling | Must implement a sidecar per platform |
  | Allows consistent infrastructure coordination | Sidecar component may grow large/complex |
  | Ownership per team, centralized, or some combination | |

  - **이 표가 위 [하나 들여야 하는가](#하나-들여야-하는가)의 판단 재료를 늘린다.** 뉴먼 쪽 판단
    기준이 **얼마나 많은 마이크로서비스를 운영하는가**였다면, 이 표는 **플랫폼마다 사이드카를
    하나씩 지어야 한다**는 비용과 **사이드카가 커지거나 복잡해질 수 있다**는 비용을 더한다.

  **둘 — 도메인 결합을 사이드카에 넣지 말라는 규칙.** 2021년 책의 사가가 그것을 조문으로 만든다 —
  **서비스 메시와 사이드카의 의도는 도메인 결합이 아니라 운영 결합을 한데 모으는 것**이고,
  **`Address`나 `Customer` 클래스 같은 도메인 공유 컴포넌트를 사이드카에 절대 넣지 말아야 한다**
  (8장, p.240, 사가).[^ford2021-hard-parts]
  - **이유가 결합의 정의로 적힌다** — `Address` 클래스가 바뀌고 두 서비스가 그것에 기대면 **둘 다
    바뀌어야 하고 그것이 결합의 정의**다 (8장, p.241, 사가).[^ford2021-hard-parts]
  - **그런데 저자들이 곧바로 그 규칙을 무르게 만든다** — 아키텍트가 그 공유 라이브러리를
    사이드카에 넣기로 결정할 수도 있고 **어쨌든 그것은 기술적 능력**이며, **어느 답도 명백히 옳지
    않아 절충 분석의 값어치가 있는 아키텍트의 결정**이라는 것이다 (8장, p.241,
    사가).[^ford2021-hard-parts]
  - **위 [게이트웨이에 넣지 말아야 할 것 셋](#게이트웨이에-넣지-말아야-할-것-셋)과 같은 종류의
    금지이고 대상만 다르다.** 뉴먼은 게이트웨이에 업무 로직을 넣지 말라 하고, 이쪽은 사이드카에
    도메인 클래스를 넣지 말라 한다. **두 소스가 서로를 호명하지 않는다.** #hypothesis

  **셋 — 사이드카 크기를 가르는 어림.** 공유 유틸리티 코드의 **핵심 절충은 몇 팀이 그것을
  필요로 하는가 대 그것이 모든 서비스에(특히 필요 없는 서비스에도) 얼마나 많은 부담을 더하는가**
  이고, **절반에 못 미치는 팀이 쓴다면 아마 그 부담의 값어치가 없다** (8장, p.241,
  사가).[^ford2021-hard-parts]
  - 그 장면의 수는 **팀 16~17개 가운데 5개**가 JSONtoXML 라이브러리를 쓴다는 것이고, 그래서
    사이드카에 넣지 않고 **나중에 다시 평가**하기로 한다 (8장, p.241,
    사가).[^ford2021-hard-parts]
  - **그 눈금의 근거를 저자들이 대지 않는다.** 등장인물이 대화 중에 내놓고 아키텍트가
    동의한다. #hypothesis

  **넷 — 소유권을 조직으로 답한다.** 사이드카를 팀들이 함께 지는 책임으로 둘 수도 있었으나,
  팀이 충분히 많아져서 **공유 인프라 팀(shared infrastructure team)**을 만들어 사이드카를 관리하고
  유지하게 했고, 그 팀이 **사이드카가 서비스에 묶인 뒤 자동으로 시험하는 배포 파이프라인을 적합도
  함수 묶음과 함께** 지었다. **서비스 팀이 그 팀의 고객이 된다** (8장, pp.240–241, 사가·ADR).[^ford2021-hard-parts]
  - **그 배치가 이 KB의 다른 페이지와 맞닿는다** —
    [플랫폼 팀과 포장된 길](platform-team-and-paved-road.md)의 "플랫폼 팀의 사용자는 다른
    개발자다"라는 재규정과 같은 자리다. **두 소스가 서로를 호명하지 않는다.** #hypothesis
- **그 장의 사가와 ADR과 나머지 세 재사용 패턴은
  [코드 재사용 패턴 넷](code-reuse-patterns.md)이 소유한다.** 이 페이지가 가져온 것은 사이드카와
  메시에 걸리는 대목뿐이다.

## REST 프록시는 게이트웨이인가

[bellemare2025](../sources/bellemare2025.md) 17장이 **REST 프록시(REST proxy)** 라는 중개자를
하나 더 놓는다. **이 페이지의 두 중개자와 축이 다른 셋째 칸으로 판정했다.**

- **규정부터 다르다** — REST 프록시는 **클라이언트가 이벤트 브로커와 통신하도록 REST API를
  노출하는 서비스**다. 쓸 수 있는 스트림 목록 보기, 새 스트림 만들기, 이벤트 발행하기,
  스트림에서 소비하기 같은 **미리 정해진 명령 집합**을 준다 (17장, p.336).[^bellemare2025]

| | API 게이트웨이(이 페이지) | 서비스 메시(이 페이지) | REST 프록시(17장) |
|---|---|---|---|
| 무엇의 앞에 서는가 | **마이크로서비스들**(남북) | **마이크로서비스들**(동서) | **이벤트 브로커** |
| 무엇을 번역하는가 | 대체로 번역하지 않는다(프로토콜 재작성은 금지 항목이다) | 번역하지 않는다 | **HTTP 요청 ↔ 브로커 프로토콜** |
| 업무 로직을 갖는가 | **갖지 말아야 한다** | 갖지 않는다 | **갖지 않는다** — 발행·소비·목록의 명령 집합뿐이다 |
| 성능 자리매김 | 테두리의 필수 경로 | 호스트마다 붙는 사이드카 | **고성능 부품이 아니다** — 웬만한 부하에도 여럿을 두어야 할 수 있다 (17장, p.338)[^bellemare2025] |

- **뉴먼의 금지 셋에 걸리는가 — 걸리지 않는다.** ① 호출 집계를 하지 않고, ③ 모든 서비스 사이
  호출을 중개하지도 않는다(브로커에 붙는 클라이언트만 지난다). **② 프로토콜 재작성이 문제인데,
  이것은 걸리지 않는다고 판정했다** — 뉴먼이 금지한 것은 **SOAP를 REST로 바꾼다는 식으로
  아키텍처 사고방식 자체를 프록시 계층에 구현하려는 시도**이고, REST 프록시가 하는 것은
  **이미 정해진 브로커 명령 집합을 HTTP로 노출하는 것**이라 옮기는 행위가 없다. #hypothesis 두
  소스는 이 자리에서 서로를 호명하지 않고 이 판정은 이 KB의 것이다.
- **한 기능은 경계에 걸린다 — 스키마 검증이다.** REST 프록시에 레코드와 스키마를 함께 보내면
  **프록시가 스키마 레지스트리에 대고 자동으로 검증하고, 호환되지 않으면 예외를 던지고 쓰기를
  거부해 불량 데이터가 스트림에 들어가는 것을 막아 낸다** (17장, p.338).[^bellemare2025]
  **이것을 업무 로직으로 읽지 않았다** — 계약 강제이지 도메인 판단이 아니고, 이 페이지가 세는
  게이트웨이의 정당한 일(인증·부하 분산·차단)과 같은 갈래다. #hypothesis
- **위 §"이 KB의 다른 자리에서 온 같은 낱말들"이 적어 둔 한계가 여기서 한 번 뒤집힌다** —
  브로커를 쓰는 통신은 게이트웨이와 메시의 중개를 우회한다는 것이 그 한계였는데, **REST 프록시는
  바로 그 브로커 트래픽을 HTTP 중개자 하나에 태우는 구성**이다. 다만 그 중개자는 게이트웨이가
  아니라 브로커의 프런트엔드다.
- 전문은 [요청-응답과 이벤트 기반의 통합](request-response-and-event-driven-integration.md)에
  있다 — 같은 claim을 두 페이지에 흩지 않는다.
