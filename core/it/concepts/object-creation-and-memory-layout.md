이 페이지의 질문: **`new` 한 줄이 핫스팟 안에서 무슨 일을 시키고, 만들어진 객체는 힙에
어떤 모양으로 놓이며, 그 객체에 어떻게 닿는가.**

## 객체 하나가 만들어지는 절차

- 가상 머신이 `new` 명령에 해당하는 바이트코드를 만나면 **매개 변수가 상수 풀 안의
  클래스를 가리키는 심벌 참조인지 확인하고, 그 클래스가 로딩·해석(resolve)·초기화
  (initialize)되었는지 확인한다.** 준비되지 않았다면 로딩부터 한다 (2장,
  pp.67–68).[^zhou2024]
- 로딩이 끝났으면 새 객체를 담을 메모리를 할당한다. **객체에 필요한 메모리 크기는 클래스를
  로딩하고 나면 완벽히 알 수 있으므로**, 할당은 자바 힙에서 특정 크기의 블록을 잘라 주는
  일이라 할 수 있다 (2장, p.68).[^zhou2024]
- 할당이 끝나면 가상 머신은 **할당받은 공간을 0으로 초기화한다**(객체 헤더는 제외). 스레드
  로컬 할당 버퍼를 쓴다면 버퍼를 할당할 때 미리 수행한다. **자바 코드에서 인스턴스 필드를
  초기화하지 않고도 쓸 수 있는 이유가 이 단계 덕분**이다 (2장, p.69).[^zhou2024]
- 다음으로 '각 객체에 필요한 설정'을 한다 — **어느 클래스의 인스턴스인지, 클래스 메타
  정보는 어떻게 찾는지, 해시 코드는 무엇인지, GC 세대 나이(age)는 얼마인지** 등이며 이
  정보는 객체 헤더에 저장된다 (2장, pp.69–70).[^zhou2024]
  - 해시 코드는 사실 `Object::hashCode()`가 처음 호출될 때 계산된다.
- 여기까지가 **가상 머신 관점의 객체 생성**이다. 자바 프로그램 관점에서는 이제부터가
  시작으로, **생성자(`<init>()` 메서드)가 실행되어 개발자 의도대로 초기화돼야 비로소 쓸 수
  있는 진짜 객체가 완성된다** (2장, p.70).[^zhou2024]
  - 자바 컴파일러는 `new` 키워드를 바이트코드 `new`(메모리 할당)와 `invokespecial`
    (`<init>()` 호출) 둘로 변환한다. 다만 **`new`가 아닌 다른 방식으로 객체를 생성하면
    `invokespecial`이 연이어 나오지 않을 수 있다.**

## 공간을 자르는 두 방식

- 자바 힙이 완벽히 규칙적이라면, 사용 중인 메모리가 한쪽에 여유 메모리가 반대쪽에 있고
  포인터가 그 경계를 가리킬 것이다. 이때 할당은 **포인터를 정확히 객체 크기만큼 여유 공간
  쪽으로 옮기는 일**이며 이를 **포인터 밀치기(bump the pointer)** 라 한다 (2장,
  p.68).[^zhou2024]
- 하지만 힙은 규칙적이지 않다. 그래서 가상 머신은 **가용 메모리 블록들을 목록으로 따로
  관리하고, 인스턴스를 담기에 충분한 공간을 찾아 할당한 뒤 목록을 갱신한다.** 이 방식이
  **여유 목록(free list)** 이다 (2장, p.68).[^zhou2024]
- 어느 쪽을 쓸지는 **힙이 규칙적이냐**에 달렸고, 그것은 다시 **쓰는 가비지 컬렉터가
  컴팩트(compact: 모으기)를 할 수 있느냐**에 달렸다 (2장, p.68):[^zhou2024]
  - 시리얼·파뉴(ParNew)처럼 모으기가 가능한 컬렉터를 쓰는 시스템이면 단순하고 효율적인
    **포인터 밀치기**를 채택한다.
  - 이론상 CMS처럼 **스윕(sweep: 쓸기)** 알고리즘을 적용한 컬렉터를 쓰면 더 복잡한 **여유
    목록**을 채택한다.
  - '이론상'이라고 한 이유가 있다 — **대다수 상황에서 할당 속도를 높이려고 CMS 구현 시
    여유 목록에 기대한 할당 버퍼를 두고 그 안에서는 포인터 밀치기를 쓰기 때문**이다. 이
    버퍼를 **선형 할당 버퍼(linear allocation buffer)** 라 한다.

## 동시에 할당할 때

- 객체 생성은 매우 빈번하고, **여유 메모리의 시작 포인터를 수정하는 단순한 일도 스레드
  안전하지 않다** — 한 스레드가 포인터 값을 아직 수정하기 전에 다른 스레드가 메모리를
  요청할 수 있다 (2장, p.69).[^zhou2024]
- 해법은 두 가지다 (2장, p.69):[^zhou2024]
  - **메모리 할당을 동기화한다.** 실제로 가상 머신은 **비교 및 교환(CAS)과 실패 시 재시도**
    방식으로 갱신을 원자적으로 수행한다.
  - **스레드마다 다른 공간을 할당한다.** 각 스레드가 자바 힙 안에 작은 전용 메모리를 미리
    받아 두는 것으로, 이를 **스레드 로컬 할당 버퍼(TLAB, thread-local allocation buffer)**
    라 한다. 스레드는 로컬 버퍼에서 할당받다가 버퍼가 부족해지면 그때 동기화를 해 새
    버퍼를 받는다. 사용 여부는 `-XX:+/-UseTLAB`으로 설정한다.

## 객체의 메모리 레이아웃

- 핫스팟은 객체를 세 부분으로 나눠 힙에 저장한다 — **객체 헤더(object header), 인스턴스
  데이터, 정렬 패딩(alignment padding)** (2장, p.72).[^zhou2024]

### 객체 헤더

- 객체 헤더는 두 유형의 정보를 담는다. 첫째는 **객체 자체의 런타임 데이터**로 해시 코드,
  GC 세대 나이, 락 상태 플래그, 점유 락, 편향된 스레드의 아이디, 편향된 시각의 타임스탬프
  등이며, 이 부분을 **마크 워드(mark word)** 라 한다. 크기는 (참조 압축을 켜지 않으면)
  32비트 가상 머신에서 32비트, 64비트 가상 머신에서 64비트다 (2장, p.72).[^zhou2024]
  - 편향된 스레드의 아이디와 편향 시각의 타임스탬프는 편향 락(biased lock) 관련
    사항이며, 편향 락은 JDK 15에서 폐기 대상이 되었고 JDK 18에서 완전히 제거됐다
    (2장, pp.70·72, 옮긴이 주).
    - 버전 조건: 이 두 필드는 JDK 17 이하 — 18 이상에는 존재하지 않는다.
- 마크 워드가 특이한 것은 **데이터 구조의 의미가 동적으로 달라진다**는 점이다. 한정된
  공간에 가능한 한 많은 정보를 담고, **객체 상태에 따라 공간을 재활용할 수 있게 하기
  위해서다** (2장, pp.72–73).[^zhou2024]
  - 예로 32비트 핫스팟에서 객체가 잠겨 있지 않다면 32비트 중 25비트는 해시 코드,
    4비트는 세대 나이, 1비트는 0 고정, 마지막 2비트는 **락 플래그**에 쓰인다.
  - 락 플래그가 나타내는 상태는 `01`(잠기지 않음 또는 편향 가능), `00`(경량 락),
    `10`(확장, 중량 락), `11`(GC 마크)이다 (2장, p.73, 표 2-1).
- 두 번째는 **클래스 워드(klass word)** 로, 객체의 클래스 관련 메타데이터를 가리키는
  **클래스 포인터**가 저장된다. 가상 머신은 이 포인터로 객체가 어느 클래스의 인스턴스인지
  런타임에 알아낸다. 다만 **모든 구현이 클래스 포인터를 객체 헤더에 저장하지는 않는다**
  (2장, p.73).[^zhou2024]
  - 여기서 `klass`는 오타가 아니다 — **자바 클래스를 다루는 데 필요한 정보(정의된 필드와
    메서드 등)를 담은 데이터 구조**를 가리키며, **JDK 7까지는 영구 세대에, JDK 8부터는
    메타스페이스에 저장된다** (2장, p.73, 옮긴이 주).
- 자바 배열이라면 **배열 길이**도 객체 헤더에 저장한다. 위치는 클래스 워드 다음이다.
  **객체 헤더의 메타데이터로 크기를 얻지만 거기 담긴 타입은 배열 '원소'의 타입이므로,
  원소 개수까지 알아야 배열이 차지하는 크기를 제대로 계산할 수 있기 때문**이다 (2장,
  p.73).[^zhou2024]

### 인스턴스 데이터와 정렬 패딩

- 인스턴스 데이터는 **객체가 실제로 담고 있는 정보**다 — 프로그램 코드에서 정의한 필드,
  부모 클래스가 정의한 모든 필드가 여기 기록된다 (2장, p.74).[^zhou2024]
- 저장 순서는 **할당 전략 매개 변수(`-XX:FieldsAllocationStyle`)와 소스 코드의 필드 정의
  순서**에 따라 달라진다. 핫스팟의 기본 순서는 `long`·`double`, `int`, `short`·`char`,
  `byte`·`boolean`, 일반 객체 포인터(ordinary object pointer)다 (2장, p.74).[^zhou2024]
  - 기본 전략에서는 **길이가 같은 필드들이 항상 같이 할당·저장되며, 길이가 같다면 부모
    클래스에서 정의된 필드가 자식 클래스의 필드보다 앞에 배치된다.**
  - `+XX:CompactFields`를 `true`(기본값)로 두면 **하위 클래스의 짧은 필드가 상위 클래스의
    변수 사이사이에 끼워 넣어져 공간이 절약된다.**
- 정렬 패딩은 존재하지 않을 수도 있으며 **특별한 의미 없이 자리를 확보하는 역할**만 한다.
  핫스팟의 자동 메모리 관리 시스템에서 **객체의 시작 주소는 반드시 8바이트의 정수배여야
  하고, 달리 말하면 모든 객체의 크기가 8바이트의 정수배여야 한다.** 객체 헤더는 정확히
  8바이트의 정수배(1배 또는 2배)로 설계돼 있으므로 **인스턴스 데이터가 조건을 못 채울
  때만 패딩으로 채운다** (2장, pp.74–75).[^zhou2024]

## 객체에 접근하는 두 방식

- 자바 프로그램은 스택의 참조 데이터를 통해 힙의 객체를 조작한다. **명세는 참조 타입을
  '객체를 가리키는 참조'라고만 정했을 뿐, 힙에서 객체의 정확한 위치를 알아내는 구체적
  방법은 규정하지 않았다.** 그래서 접근 방식도 구현마다이며 주로 **핸들(handle)** 이나
  **다이렉트 포인터(direct pointer)** 를 쓴다 (2장, p.75).[^zhou2024]
- 핸들 방식에서는 자바 힙에 **핸들 저장용 풀**이 따로 존재한다. 참조에는 객체의 핸들
  주소가 저장되고, 핸들에는 다시 해당 객체의 **인스턴스 데이터와 타입 데이터의 정확한 주소
  정보**가 담긴다 (2장, p.75).[^zhou2024]
  - 가장 큰 장점은 **참조에 '안정적인' 핸들 주소가 저장된다**는 것이다. 가비지 컬렉션
    과정에서 객체가 이동하는 일은 아주 흔한데, **핸들을 쓰면 참조 자체는 손댈 필요가 없고
    핸들 내의 인스턴스 데이터 포인터만 바꾸면 된다.**
- 다이렉트 포인터 방식에서는 **스택의 참조에 객체의 실제 주소가 바로 저장되고**, 힙에
  위치한 객체가 인스턴스 데이터뿐 아니라 타입 데이터에 접근하는 길도 제공해야 한다 (2장,
  pp.75–76).[^zhou2024]
  - 가장 큰 장점은 **속도**다. 핸들을 경유하는 오버헤드가 없기 때문이며, 자바에서는 다른
    객체에 접근할 일이 아주 많으므로 실행 시간에 큰 영향을 준다.
- **핫스팟은 주로 다이렉트 포인터 방식을 쓴다.** 예외적으로 셰넌도어(Shenandoah)
  컬렉터를 쓰면 추가적인 포워딩을 거친다 (2장, p.76).[^zhou2024]
