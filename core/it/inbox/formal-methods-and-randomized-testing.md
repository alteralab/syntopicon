하나의 질문: **분산 알고리즘과 그 구현이 요구된 성질을 모든 상태에서 만족한다는 것을 어떻게
확인할 수 있는가.**

## 왜 테스트만으로는 부족한가

- 상태 공간이 문제다 — **알고리즘이 요구된 성질을 만족한다는 것을 우리는 어떻게 아는가? 동시성,
  부분 실패, 네트워크 지연 때문에 잠재적 상태의 수가 엄청나다. 우리는 그 성질들이 가능한 모든
  상태에서 성립함을 보장하고 어떤 엣지 케이스도 잊지 않았음을 확실히 해야 한다** (9장,
  p.384).[^kleppmann2026] 여기서 말하는 "요구된 성질"의 형식화는
  [장애 모델과 시스템 동기성](../concepts/failure-models-and-synchrony.md)에 있다.

## 형식 증명이 하는 일

- 첫 번째 접근 — **한 가지 접근은 알고리즘을 수학적으로 서술하고 증명 기법을 써서 그것이 시스템
  모델이 허용하는 모든 상황에서 요구된 성질을 만족함을 보이는, 형식 검증(formally verify)이다**
  (9장, p.384).[^kleppmann2026]
- 그 한계와 값어치 — **알고리즘이 올바름을 증명하는 것이 실제 시스템에서의 구현이 반드시 항상
  올바르게 동작한다는 뜻은 아니다. 그러나 그것은 매우 좋은 첫걸음이다. 이론적 분석이, 실제
  시스템에서는 오랫동안 숨어 있다가 (예컨대 타이밍에 관한) 가정이 이례적인 상황에 의해 깨질 때에야
  물어뜯는 알고리즘의 문제를 드러낼 수 있기 때문이다** (9장, p.384).[^kleppmann2026]
- 그래서 둘을 섞는다 — **구현이 기대대로 동작하는지 확인하려고 이론적 분석과 경험적 테스트를
  결합하는 것이 신중하다. 속성 기반 테스트(property-based testing), 퍼징(fuzzing), 결정적
  시뮬레이션 테스트(deterministic simulation testing) 같은 기법은 무작위화를 써서 시스템을 넓은
  범위의 상황에서 테스트한다. 아마존 웹 서비스, FoundationDB, TigerBeetle 같은 조직이 이 기법들의
  조합을 여러 제품에 성공적으로 써 왔다** (9장, p.384).[^kleppmann2026]

## 모델 체킹과 명세 언어

- 정체 — **모델 체커(model checker)는 알고리즘이나 시스템이 기대대로 동작하는지 검증하는 것을
  돕는 도구다. 알고리즘 명세는 TLA+, Gallina, FizzBee 같은 목적 특화 언어로 쓰인다. 이 언어들은
  코드 구현 세부를 걱정하지 않고 알고리즘의 동작에 집중하기 쉽게 해 준다. 그러면 모델 체커는 이
  모델을 써서, 일어날 수 있는 모든 것을 체계적으로 시도함으로써 알고리즘의 모든 상태에 걸쳐 불변식이
  성립하는지 검증한다** (9장, p.384).[^kleppmann2026]
- 무엇을 증명하지 못하는가 — **모델 체킹은 알고리즘의 불변식이 가능한 모든 상태에 대해 성립함을
  실제로 증명할 수는 없다. 대부분의 실세계 알고리즘이 무한한 상태 공간을 갖기 때문이다. 모든 상태의
  진정한 검증에는 형식 증명이 필요한데, 그것도 할 수는 있지만 보통 모델 체커를 돌리는 것보다 더
  어렵다. 대신 모델 체커는 완전히 검증할 수 있는 근사로 알고리즘 모델을 줄이거나, 실행에 상한을
  두도록(예컨대 보낼 수 있는 메시지 수의 최댓값을 설정해) 권한다. 그러면 더 긴 실행에서만 나타나는
  버그는 발견되지 않을 것이다** (9장, pp.384–385).[^kleppmann2026]
- 그럼에도 값어치가 있다 — **그래도 모델 체커는 쓰기 쉬움과 자명하지 않은 버그를 찾아내는 능력
  사이에서 좋은 균형을 이룬다. CockroachDB, TiDB, 카프카를 비롯한 많은 분산 시스템이 버그를 찾고
  고치는 데 모델 명세를 쓴다. 예컨대 TLA+를 써서 연구자들은 알고리즘의 산문 서술의 모호성이 일으킨
  뷰스탬프 복제(viewstamped replication, VR)의 잠재적 데이터 유실을 실증할 수 있었다** (9장,
  p.385).[^kleppmann2026] 뷰스탬프 복제는
  [복제 상태 기계와 합의](../concepts/replicated-state-machine.md)가 세는 합의 알고리즘 넷 중
  하나다.
- 그 대신 치르는 것 — **설계상 모델 체커는 실제 코드가 아니라 프로토콜의 핵심 발상만 명세하는
  단순화된 모델을 돌린다. 이는 상태 공간을 체계적으로 탐색하는 것을 더 다루기 쉽게 만들지만, 명세와
  구현이 서로 어긋나 버릴 위험을 안는다. 모델과 실제 구현이 동등한 동작을 하는지 검사하는 것은
  가능하지만, 실제 구현에 계측(instrumentation)이 필요하다** (9장,
  p.385).[^kleppmann2026]

## 결함 주입

- 정체 — **많은 버그는 기계와 네트워크 장애가 일어날 때 촉발된다. 결함 주입(fault injection)은
  일이 잘못될 때 시스템 구현이 기대대로 동작하는지 검증하는, 효과적이고 (때로는 무서운) 기법이다.
  발상은 단순하다 — 돌고 있는 시스템의 환경에 결함을 주입하고 그것이 어떻게 행동하는지 본다. 결함은
  네트워크 장애, 기계 크래시, 디스크 손상, 멈춘 프로세스 등 컴퓨터에 잘못될 수 있다고 상상할 수
  있는 무엇이든 될 수 있다** (9장, p.385).[^kleppmann2026]
- 어디서 도는가 — **결함 주입 테스트는 보통 시스템이 돌 프로덕션 환경과 매우 비슷한 환경에서
  수행된다. 어떤 곳은 프로덕션 환경에 직접 결함을 주입하기도 한다. 넷플릭스가 자사 Chaos Monkey
  도구로 이 접근을 대중화했다. 프로덕션 결함 주입은 흔히 카오스 엔지니어링(chaos engineering)이라
  불린다** (9장, p.385).[^kleppmann2026]
- 구성 — **결함 주입 테스트를 돌리려면 테스트 대상 시스템을 결함 주입 코디네이터·스크립트와 함께
  먼저 배치한다. 코디네이터는 어떤 결함을 언제 실행할지 결정할 책임을 진다. 로컬 또는 원격 스크립트는
  개별 노드나 프로세스에 장애를 주입할 책임을 진다. 주입 스크립트는 결함을 촉발하는 데 여러 도구를
  쓴다. 리눅스 프로세스는 리눅스의 `kill` 명령으로 멈추거나 죽일 수 있고, 디스크는 `umount`로
  마운트 해제할 수 있으며, 네트워크 연결은 방화벽 설정으로 끊을 수 있다. 결함이 주입되는 동안과
  그 후에 시스템 동작을 살펴 일이 기대대로 되는지 확인할 수 있다** (9장,
  p.385).[^kleppmann2026]
- 프레임워크가 필요한 이유 — **장애를 촉발하는 데 필요한 무수한 도구는 결함 주입 테스트를 작성하기
  성가시게 만든다. 과정을 단순화하려고 Jepsen 같은 결함 주입 프레임워크를 채택하는 것이 흔하다.
  그런 프레임워크는 다양한 운영체제 통합과 많은 미리 만들어진 결함 주입기를 함께 제공한다. Jepsen은
  널리 쓰이는 많은 시스템에서 결정적인 버그를 찾아내는 데 놀랄 만큼 효과적이었다** (9장,
  p.386).[^kleppmann2026] 다른 소스가 세는 결함 주입 도구 목록(Toxiproxy·CharybdeFS·CrashMonkey)은
  [분산 컴퓨팅의 오류](../concepts/fallacies-of-distributed-computing.md)에 있다.

## 결정적 시뮬레이션 테스트

- 정체 — **모델 체킹과 결함 주입의 인기 있는 보완물이 된 또 다른 형식화 기법이 결정적 시뮬레이션
  테스트(deterministic simulation testing, DST)다. 모델 체커와 비슷한 상태 공간 탐색 과정을 쓰지만
  모델이 아니라 실제 코드를 테스트한다** (9장, p.386).[^kleppmann2026]
- 동작 — **DST에서 시뮬레이션은 시스템의 무작위화된 실행을 많이 자동으로 돌린다. 시뮬레이션 중의
  네트워크 통신·I/O·시계 타이밍은 전부 목(mock)으로 대체되어, 시뮬레이터가 여러 타이밍과 장애
  시나리오를 포함해 일이 일어나는 정확한 순서를 통제할 수 있게 한다. 이는 시뮬레이터가 손으로 쓴
  테스트나 결함 주입이 할 수 있는 것보다 훨씬 많은 상황을 탐색하게 해 준다. 테스트가 실패하면
  시뮬레이터가 장애를 촉발한 연산의 정확한 순서를 알고 있으므로 다시 돌릴 수 있다 — 시스템에 대해
  그런 세밀한 통제를 갖지 못하는 결함 주입과 대비된다** (9장,
  p.386).[^kleppmann2026]
- 코드를 결정적으로 만드는 세 전략 — **DST는 시뮬레이터가 네트워크 지연이나 다중 스레드 코드의
  스레드 스케줄링 같은 모든 비결정성의 원천을 통제할 수 있을 것을 요구한다. 보통 세 전략 중 하나가
  채택된다** (9장, pp.386–387):[^kleppmann2026]
  - **애플리케이션 수준** — **어떤 시스템은 코드를 결정적으로 실행하기 쉽게 만들도록 밑바닥부터
    지어진다. 예컨대 DST 공간의 개척자 중 하나인 FoundationDB는 Flow라는 비동기 통신 라이브러리로
    지어졌다. Flow는 개발자가 결정적 네트워크 시뮬레이션을 시스템에 주입할 지점을 제공한다.
    비슷하게 TigerBeetle은 일급 DST 지원을 갖춘 OLTP 데이터베이스다. 시스템 상태가 상태 기계로
    모델링되고 모든 변경이 단일 이벤트 루프 안에서 일어난다. 시계 같은 목 결정적 프리미티브와
    결합하면 그런 아키텍처는 결정적으로 돌 수 있다.**
  - **런타임 수준** — **비동기 런타임과 흔히 쓰이는 라이브러리를 가진 언어는 결정성을 도입할
    삽입 지점을 제공한다. 단일 스레드 런타임을 써서 모든 비동기 코드가 순차적으로 돌게 강제한다.
    예컨대 FrostDB는 고루틴을 순차적으로 실행하도록 Go의 런타임을 패치한다. Rust의 MadSim
    라이브러리도 비슷한 방식으로 동작한다. 그것은 Tokio의 비동기 런타임 API, 아마존의 S3
    라이브러리, 카프카의 Rust 라이브러리를 비롯한 여러 가지의 결정적 구현을 제공한다.
    애플리케이션은 코드를 바꾸지 않고 결정적 라이브러리와 런타임을 갈아 끼워 결정적 테스트 실행을
    얻을 수 있다.**
  - **기계 수준** — **런타임에 코드를 패치하는 대신 기계 전체를 결정적으로 만들 수 있다. 이는
    보통 비결정적인 모든 호출에 기계가 결정적 응답을 하도록 요구하는 섬세한 과정이다. Antithesis
    같은 도구는 보통 비결정적인 연산을 결정적인 것으로 대체하는 맞춤 하이퍼바이저를 지어 이것을
    한다. 시계에서 네트워크와 저장까지 모든 것이 고려돼야 한다. 그러나 일단 그것이 끝나면 개발자는
    하이퍼바이저 안의 컨테이너 모음에서 분산 시스템 전체를 돌려 완전히 결정적인 분산 시스템을 얻을
    수 있다.**
- 재생 말고도 얻는 것 — **DST는 재생 가능성 말고도 여러 이점을 제공한다. 예컨대 Antithesis는
  덜 흔한 동작을 발견하면 테스트 실행을 여러 하위 실행으로 분기해 애플리케이션 코드의 많은 경로를
  탐색하려 시도한다. 그리고 결정적 테스트는 흔히 목 시계와 네트워크 호출을 쓰므로 그런 테스트는
  벽시계 시간보다 빠르게 돌 수 있다. 예컨대 TigerBeetle의 시간 추상은 타임아웃을 촉발하는 데 실제로
  그만한 시간을 다 쓰지 않고도 시뮬레이션이 네트워크 지연과 타임아웃을 흉내 내게 해 준다. 그런
  기법은 시뮬레이터가 더 많은 코드 경로를 더 빠르게 탐색하게 해 준다** (9장,
  p.387).[^kleppmann2026]

## 결정성의 힘

- 저자가 상자로 이 장을 관통하는 발상을 정리한다 — **비결정성은 이 장에서 논한 모든 분산 시스템
  도전의 핵심에 있다. 동시성, 네트워크 지연, 프로세스 중단, 시계 점프, 크래시는 전부 예측할 수 없는
  방식으로, 시스템의 실행마다 다르게 일어난다. 반대로 시스템을 결정적으로 만들 수 있다면 그것은
  일을 엄청나게 단순화할 수 있다. 사실 무언가를 결정적으로 만드는 것은 분산 시스템 설계에서 몇 번이고
  다시 나타나는 단순하지만 강력한 발상이다** (9장, p.387).[^kleppmann2026] 저자가 세는 자리는
  셋이다 (9장, p.387):[^kleppmann2026]
  - **이벤트 소싱의 핵심 이점은 파생된 구체화 뷰를 재구성하려고 사건 로그를 결정적으로 재생할 수
    있다는 것이다.**
  - **워크플로 엔진은 내구성 있는 실행 의미론을 제공하기 위해 워크플로 정의가 결정적일 것에 기댄다.**
  - **상태 기계 복제는 각 레플리카에서 같은 결정적 트랜잭션 계열을 독립적으로 실행함으로써 데이터를
    복제한다. 우리는 이미 그 발상의 두 변형을 봤다 — 문장 기반 복제와 저장 프로시저를 쓰는 직렬
    트랜잭션 실행이다.**
- 그러나 완전한 결정성은 쉽지 않다 — **코드를 완전히 결정적으로 만드는 데는 주의가 필요하다. 모든
  동시성을 없애고 I/O·네트워크 통신·시계·난수 생성기를 결정적 시뮬레이션으로 대체하고 나서도 비결정성의
  요소가 남을 수 있다. 예컨대 어떤 프로그래밍 언어에서는 해시 테이블의 원소를 순회하는 순서가
  비결정적일 수 있다. 자원 한계(메모리 할당 실패, 스택 오버플로)에 부딪히는지 여부도 비결정적이다**
  (9장, p.388).[^kleppmann2026]

## 같은 기법이 한 함수 수준에서 쓰일 때

이 페이지가 첫 절에서 한 줄로 센 **속성 기반 테스트(property-based testing)** 를 다른 소스가 정면
주제로 다룬다. 같은 도구인데 **왜 쓰는지가 다르고, 그 차이가 처방을 가른다.**

- **이 페이지의 진단은 규모다** — **동시성, 부분 실패, 네트워크 지연 때문에 잠재적 상태의 수가
  엄청나다** (9장, p.384).[^kleppmann2026] 사람이 열거할 수 없으므로 기계가 훑는다.
- **저쪽의 진단은 편향이다** — **원래 코드를 당신이 쓰고 테스트도 당신이 쓴다면, 틀린 가정 하나가
  양쪽에 표현될 수 있지 않은가? 코드는 테스트를 통과한다 — 당신의 이해에 근거해 그것이 해야 할 일을
  하기 때문이다** (Topic 42).[^thomas2020] 그래서 해법이 **당신의 선입견을 공유하지 않는 컴퓨터**가
  된다 (Topic 42).[^thomas2020] 전문은 [속성 기반 테스트](property-based-testing.md)에 있다.
- **그래서 속성을 어디서 얻는지도 다르다.** 저쪽은 계약과 불변식에서 끌어낸다 — **일단 계약과
  불변식(우리는 이것들을 한데 묶어 *속성*(properties)이라 부를 것이다)을 알아내면 우리는 그것을 써서
  테스팅을 자동화할 수 있다** (Topic 42).[^thomas2020] 이 페이지의 모델 체킹은 같은 것을 명세
  언어의 불변식으로 쓴다. **두 층에서 검사하는 술어의 출처가 계약/명세로 나뉜다.**
- **저쪽이 남긴 좌절이 이 페이지의 DST가 푸는 문제와 정확히 같다.** 저쪽의 진단 — **좌절인 이유는
  무엇이 실패했는지 짚어 내기가 까다로울 수 있다는 것이다** (Topic 42).[^thomas2020] 그리고 그
  대응이 실패 값을 별도의 결정적 단위 테스트로 굳히는 것인데, 이 페이지의 DST가 하는 일이 그것을
  실행 순서 전체로 확대한 것이다 — **테스트가 실패하면 시뮬레이터가 장애를 촉발한 연산의 정확한
  순서를 알고 있으므로 다시 돌릴 수 있다** (9장, p.386).[^kleppmann2026] **무작위화가 발견을 주고
  결정성이 재현을 준다**는 분업이 두 층에 똑같이 있다. #hypothesis 두 소스가 서로를 언급한 적은
  없다.
- 어긋나는 자리는 없다. 다만 저쪽이 이 페이지의 규모에서 통할 것이라고 주장하지도 않는다 — 저쪽의
  생성기는 함수 인자를 만들고, 이 페이지의 시뮬레이터는 이벤트 순서와 장애를 만든다.
