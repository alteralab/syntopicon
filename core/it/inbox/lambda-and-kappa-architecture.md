# 람다 아키텍처와 카파 아키텍처

하나의 질문: **이력 데이터의 재처리와 방금 도착한 이벤트의 처리를 같은 시스템에서 하려면
무엇이 필요한가.**

## 두 제안

- **배치와 스트림 처리를 통합하려는 초기 제안이 람다 아키텍처(lambda architecture)였는데,
  여러 문제가 있었고 쓰이지 않게 됐다** (13장, p.546).[^kleppmann2026]
- **더 최근의 시스템은 배치 계산(이력 데이터 재처리)과 스트림 계산(도착하는 대로 이벤트를
  처리하는 것)이 같은 시스템에서 구현되게 하며, 이 접근은 때때로 카파 아키텍처(kappa
  architecture)로 알려져 있다** (13장, p.546).[^kleppmann2026]

## 통합이 요구하는 세 기능

- **배치와 스트림 처리를 한 시스템에서 통합하려면 다음 기능이 필요하다** (13장,
  p.546):[^kleppmann2026]
  - **최근 이벤트의 스트림을 다루는 같은 처리 엔진을 통해 이력 이벤트를 재생(replay)할 수 있는
    능력. 예컨대 로그 기반 메시지 브로커는 메시지를 재생할 수 있고, 어떤 스트림 프로세서는
    분산 파일시스템이나 객체 저장소에서 입력을 읽을 수 있다.**
  - **스트림 프로세서를 위한 정확히 한 번 의미론 — 즉 결함이 실제로 일어났더라도 출력이 결함이
    없었을 때와 같도록 보장하는 것. 배치 처리와 마찬가지로 이는 실패한 태스크의 부분 출력을
    버리는 것을 요구한다.**
  - **처리 시간이 아니라 이벤트 시간으로 윈도잉하는 도구. 이력 이벤트를 재처리할 때 처리 시간은
    무의미하기 때문이다. 예컨대 Apache Beam이 그런 계산을 표현하는 API를 제공하며, 이는 Apache
    Flink나 Google Cloud Dataflow로 실행될 수 있다.**

## 람다의 세 계층

데이터 엔지니어링 쪽 소스는 같은 두 아키텍처를 **왜 그것이 나왔는지**의 역사와 함께 적는다.

- 배경 — **"옛날"(2010년대 초·중반)에 카프카가 고도로 확장 가능한 메시지 큐로 등장하고 스톰·
  삼자 같은 스트리밍/실시간 분석 프레임워크가 나오면서 스트리밍 데이터로 작업하는 것의 인기가
  폭발했다. 이 기술들은 회사가 대량의 데이터에 대해 집계·사용자 랭킹·제품 추천 같은 새로운 종류의
  분석과 모델링을 수행하게 해 줬다. 데이터 엔지니어는 배치와 스트리밍 데이터를 하나의 아키텍처로
  조정할 방법을 알아내야 했다. 람다 아키텍처(Lambda architecture)가 이 문제에 대한 초기의 인기
  있는 응답 중 하나였다** (3장, p.104).[^reis2022]
- 구조 — **람다 아키텍처에서는 서로 독립적으로 동작하는 시스템들 — 배치·스트리밍·서빙 — 을 갖는다.
  원천 시스템은 이상적으로 불변이고 추가 전용이며, 처리를 위해 데이터를 스트림과 배치 두 목적지로
  보낸다. 인스트림 처리는 통상 NoSQL 데이터베이스인 "속도(speed)" 계층에서 가능한 한 낮은 지연으로
  데이터를 서빙하려 한다. 배치 계층에서는 데이터 웨어하우스 같은 시스템에서 데이터가 처리·변환돼
  미리 계산되고 집계된 데이터 뷰를 만든다. 서빙 계층은 두 계층의 질의 결과를 집계해 결합된 뷰를
  제공한다** (3장, p.104).[^reis2022]
- 판정 — **람다 아키텍처에는 그 몫의 난제와 비판이 있다. 서로 다른 코드베이스를 가진 여러 시스템을
  관리하는 것은 들리는 만큼 어려워, 조정하기 극히 어려운 코드와 데이터를 가진 오류 나기 쉬운
  시스템을 만든다** (3장, p.105).[^reis2022] 위 [두 제안](#두-제안)이 "여러 문제가 있었고 쓰이지
  않게 됐다"고 요약한 그 문제들이다.
- 그럼에도 언급하는 이유 — **람다 아키텍처가 여전히 주목을 받고 데이터 아키텍처 검색 엔진 결과에서
  인기가 있기 때문에 언급한다. 분석을 위해 스트리밍과 배치 데이터를 결합하려 한다면 람다는 저자들의
  첫 권고가 아니다. 기술과 실무는 앞으로 나아갔다** (3장, p.105).[^reis2022]

## 카파 — 스트림을 유일한 백본으로

- **람다 아키텍처의 결점에 대한 응답으로 제이 크렙스가 카파 아키텍처(Kappa architecture)라는
  대안을 제안했다. 중심 논지는 이것이다 — 반입·저장·서빙 전부에 대해 스트림 처리 플랫폼을 백본으로
  쓰면 안 되는가? 이는 진정한 이벤트 기반 아키텍처를 촉진한다. 라이브 이벤트 스트림을 직접 읽고
  배치 처리를 위해 큰 데이터 덩어리를 재생함으로써 실시간과 배치 처리가 같은 데이터에 매끄럽게
  적용될 수 있다** (3장, p.105).[^reis2022] 그 재생 능력의 근거는 위
  [통합이 요구하는 세 기능](#통합이-요구하는-세-기능)의 첫째와 같다.
- 채택되지 않은 두 이유 — **원래의 카파 아키텍처 글이 2014년에 나왔지만 널리 채택된 것을 보지
  못했다. 여기에는 몇 가지 이유가 있을 수 있다. 첫째, 스트리밍 자체가 많은 회사에게 여전히
  다소 미스터리다 — 말하기는 쉽지만 실행하기는 예상보다 어렵다. 둘째, 카파 아키텍처는 실무에서
  복잡하고 비싼 것으로 드러난다. 어떤 스트리밍 시스템은 방대한 데이터 양으로 확장할 수 있지만
  복잡하고 비싸며, 배치 저장과 처리는 거대한 이력 데이터셋에 대해 훨씬 효율적이고 비용
  효과적으로 남아 있다** (3장, p.105).[^reis2022]

## 데이터플로 모델이 이어받은 것

- 두 제안의 공통 배경 — **람다와 카파 둘 다 2010년대 하둡 생태계가 애초에 잘 맞지 않았을 복잡한
  도구들을 덕트 테이프로 붙이려 함으로써 생긴 한계를 다루려 했다. 배치와 스트리밍 데이터를
  통합한다는 중심 난제는 남았고, 람다와 카파 둘 다 이 추구에서 계속된 진전에 영감과 토대를
  제공했다** (3장, p.105).[^reis2022]
- 남은 문제 — **배치와 스트림 처리를 관리하는 중심 문제 중 하나는 여러 코드 경로를 통합하는
  것이다. 카파 아키텍처는 통합된 큐잉·저장 계층에 기대지만, 실시간 통계를 모으거나 배치 집계
  잡을 돌리려면 여전히 서로 다른 도구를 마주해야 한다. 오늘날 엔지니어는 이를 여러 방식으로 풀려
  하며, 구글은 데이터플로 모델(Dataflow model)과 그것을 구현하는 Apache Beam 프레임워크를 개발해
  자기 자취를 남겼다** (3장, p.106).[^reis2022]
- 그 핵심 발상 — **데이터플로 모델의 핵심 발상은 모든 데이터를 이벤트로 보고, 집계는 다양한 종류의
  윈도우에 대해 수행되는 것으로 보는 것이다. 진행 중인 실시간 이벤트 스트림은 무경계 데이터
  (unbounded data)다. 데이터 배치는 그냥 경계가 있는 이벤트 스트림이고, 그 경계가 자연스러운 윈도우를
  제공한다. 엔지니어는 실시간 집계를 위해 슬라이딩·텀블링 같은 다양한 윈도우 중에서 고를 수 있다.
  실시간과 배치 처리가 거의 동일한 코드를 써서 같은 시스템에서 일어난다** (3장, p.106).[^reis2022]
  그 윈도우들은 [스트림 처리의 시간 윈도우](../concepts/stream-processing-time-windows.md)에 있다.
- **"스트리밍의 특수한 경우로서의 배치"라는 철학이 이제 더 널리 퍼졌다. 플링크·스파크 같은 다양한
  프레임워크가 비슷한 접근을 채택했다** (3장, p.106).[^reis2022]
