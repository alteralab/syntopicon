하나의 질문: **한 활동에 속하는 이벤트들이 여러 파티션과 여러 실행에 흩어져 있을 때 그것들을 어떻게
하나의 세션으로 닫는가.**

## 세션은 특별한 집계다

- 저자의 자리매김 — **세션은 같은 활동에 관련된 이벤트를 결합하므로 특별한 종류의 집계기다. 세션은
  인기도 있다. 스트리밍 비디오를 보거나 운동하거나 심지어 요리할 때마다 일상에서 세션을 생성한다.
  그 각 활동에서 시작점·세션 이벤트·종료점으로 구성된 세션을 만든다. 데이터 엔지니어링 맥락에서는
  정지 상태일 수도 이동 중일 수도 있는 데이터의 성격에 따라 두 세션화 패턴 중에서 고를 수 있다**
  (5장, p.141).[^konieczny2025] 그 집계 쪽 계열은
  [배치 조인과 그룹핑](batch-joins-and-grouping.md)에 있다.
- 배치 쪽이 먼저인 이유 — **세션은 실시간 컴포넌트처럼 들린다. 실제로 대부분의 경우 실시간
  데이터에서 나오지만 생성 방법은 배치 처리도 지원한다** (5장, p.141).[^konieczny2025]

## Incremental Sessionizer — 세 저장 공간

- 문제 — 시간 단위로 파티션된 위치에 방문 이벤트가 있고, **첫 방문으로 시작해 주어진 사용자의 새
  방문이 두 시간 안에 없으면 끝나는 세션으로 집계**하고 싶다. **방문 세션의 전형적 지속은 수 분에서
  세 시간 사이다. 결과적으로 한 방문이 최대 세 개의 다른 파티션에 걸칠 수 있다. 팀의 데이터
  분석가들은 세션을 곧바로 얻는 데 애를 먹고 있는데, 주어진 사용자에 대해 여러 연속 파티션을 처리해야
  하기 때문이다** (5장, pp.141–142).[^konieczny2025]
- 그래서 문제의 계열이 정해진다 — **한 세션의 레코드가 여러 연속 파티션에 있을 수 있으므로 문제는
  증분 처리 계열에 속한다** (5장, p.142).[^konieczny2025]
- 구현이 요구하는 세 저장 공간 (5장, p.142):[^konieczny2025]
  - **입력 데이터셋 저장** — **세션화 파이프라인에서 상관 지어야 할 원시 이벤트를 저장한다.**
  - **완료 세션 저장** — **완료된 모든 세션을 쓰는 자리다. 결국 진행 중 세션도 여기 쓸 수 있지만,
    이상적으로는 세션이 아직 살아 있을 때마다 `is_final`을 false로 두는 식의 속성으로 완료된 것과
    구분해야 한다.**
  - **보류 세션 저장** — **여러 파티션에 걸쳐 있으면서 다음 실행 중 하나에서 닫힐 모든 세션을
    저장한다.** 완료 저장과 두 가지가 다르다. 첫째, **이 공간은 당신에게 속하고 내부 로직과 함께
    진화할 것이므로 비공개로 남아야 한다. 최종 사용자는 세부를 알 필요가 없고, 알게 되면 진화
    유연성이 줄어든다.** 둘째, **세션의 데이터 형식이 완료 세션 저장의 형식과 다를 수 있다. 여기에는
    실행 ID 같은 기술·내부 세부를 포함할 수 있다(예컨대 멱등성 보장을 위해 처리 로직을 정의하는 데
    도움이 된다면).**
- 저장만으로는 부족하고 워크플로 로직이 필요하다 — **로직은 입력 데이터셋을 이전 실행에서 생성된
  보류 세션과 결합하는 것으로 시작한다. 그 결합은 사용자·제품·방문 같은 세션 엔티티마다 일어나고
  다음을 생성할 수 있다** (5장, pp.142–143):[^konieczny2025]
  - **주어진 세션 엔티티에 보류 세션이 없으면 새 세션**
  - **읽은 입력에서 온 새 데이터와 함께 복원된 세션**
  - **새 세션 데이터 없이 복원된 세션. 이 세션은 정의한 만료 규칙에 따라 이번 실행이나 다음
    실행에서 만료될 참일 것이다.**

## 세션화 로직의 세 상태

- 결합이 끝나면 **처리할 세션 데이터를 얻는데, 이전 레코드와 새 레코드로 구성될 수 있다. 그 위에
  세 상태를 정의하는 세션화 로직을 적용해야 한다** (5장, p.143):[^konieczny2025]
  - **초기화** — **세션이 시작될 때. 예컨대 블로그 홈페이지 방문 같은 특정 이벤트 유형이 일어날 때
    시작할 수 있다.**
  - **누적** — **세션이 살아 있을 때. 새로 들어오는 데이터로 무엇을 하는가? 예컨대 방문한 페이지를
    순서대로 저장할 수 있다.**
  - **종료** — **세션이 멈출 때. 세션은 특정 이벤트 유형이 일어나거나 비활동 기간 때문에 끝날 수
    있다(예컨대 사용자가 브라우저를 닫거나 세 시간 동안 자리를 뜰 때).**
- 표현 수단 — **`WINDOW` 함수나 `GROUP BY` 표현식 다음에 선택한 프로그래밍 언어의 커스텀 매핑
  함수를 두어 처리 로직을 정의할 수 있다. 로직의 복잡도에 따라 구현이 SQL보다 프로그래매틱 API로
  표현하기 더 쉬울 수 있다** (5장, pp.143–144).[^konieczny2025]
- 입력과 보류 세션을 잇는 `FULL OUTER JOIN`이 이 패턴의 대표 코드다 — **첫 널이 아닌 원소를
  얻고(`COALESCE`), 첫 값이나 마지막 값을 얻고(`LEAST`·`GREATEST`), 두 배열을 잇는
  (`ARRAY_CAT`) 편의 메서드를 쓴다. 끝으로 세션에 새 데이터가 있을 때만 세션 만료 시각을
  계산한다** (5장, p.146):[^konieczny2025]

  ```sql
  CREATE TEMPORARY TABLE sessions_to_classify AS
   SELECT
    COALESCE(p.session_id, n.session_id) AS session_id,
    LEAST(p.start_time, n.start_time) AS start_time,
    GREATEST(p.last_visit_time, n.start_time) AS last_visit_time,
    ARRAY_CAT(p.pages, n.pages) AS pages,
    CASE
     WHEN n.user_id IS NULL THEN p.expiration_batch_id
     ELSE '{{ macros.ds_add(ds, 2) }}'
    END AS expiration_batch_id
   FROM (SELECT ... FROM visits_{{ ds_nodash }}
    WINDOW visits_window AS (PARTITION BY visit_id, user_id ORDER BY event_time)
   ) AS n
   FULL OUTER JOIN (
    SELECT ... FROM dedp.pending_sessions WHERE execution_time_id = '{{ prev_ds }}')
    AS p ON n.session_id = p.session_id;
  ```

  - 멱등성은 파이프라인 앞머리의 두 `DELETE`가 담당한다 — **파이프라인은 이 실행과 모든 후속
    실행에서 생성된 완료·보류 세션을 전부 청소하는 두 동시 태스크로 시작한다. 그것들은 Airflow의
    불변 `ds` 파라미터에 적용된 단순한 `DELETE FROM` 문을 쓴다** (5장,
    p.145).[^konieczny2025]
  - 쓰기도 둘로 갈린다 — **첫 `INSERT`는 만료 시각이 현재 실행과 다른 모든 보류 세션을 쓰고,
    다음이 완료된 모든 세션을 쓴다** (5장, p.146).[^konieczny2025]

## 비활동 기간과 부분 세션

- 대가 ① **비활동 기간** — **비활동 기간은 세션을 얼마나 오래 열어 둘 수 있는지를 정의한다. 길수록
  더 많은 늦은 데이터를 세션에 포함할 수 있다. 반면 늦은 데이터를 다룰 컴퓨트·저장 자원이 더 많이
  필요할 것이다. 컴퓨트 요구와 비즈니스 로직 사이의 올바른 균형을 찾아야 하는데, 둘 다 갖기는
  어렵기 때문이다. 그 균형이 무엇인지는 물론 전적으로 당신의 구체적 비즈니스 요구에 달렸다** (5장,
  p.144).[^konieczny2025]
- 긴 임계값의 부수 효과가 부분 세션을 부른다 — **긴 비활동 임계값은 그만큼 오래 세션을 숨은 공간에
  유지할 것이다. 사용자가 부분 세션 뷰를 받아들일 수 있다면 그것들을 출력 세션 저장으로 방출할 수도
  있다. 그러나 소비자가 알아야 할 일관성 위험이 있다** (5장, p.144).[^konieczny2025]
  - 저자의 실물이 위험을 보인다 — **부분 세션은 완료된 세션이 아니고 후속 버전에서 바뀔 수 있다.
    은행 시스템의 사기 탐지를 위한 부분 세션을 상상해 보라. 첫 파티션을 처리하면 부분 세션이 "위험
    없음"으로 분류되고 다음 파티션에서야 상태가 "위험"으로 바뀔 것이다. 소비자가 부분 세션을 최종으로
    간주하면 첫 인스턴스에 잘못된 로직을 적용할 수 있다** (5장, p.144).[^konieczny2025]
  - 그래서 처방 — **진행 중 세션에 `is_completed: false` 같은 속성으로 플래그를 다는 것이
    중요하다. 완료된 상태에만 관심 있는 하류 소비자가 그것들을 무시하도록 돕기 위해서다** (5장,
    p.144).[^konieczny2025]
- 대가 ② **데이터 신선도** — **Incremental Sessionizer는 배치 파이프라인에서 동작하고, 배치는
  여전히 데이터 팀의 첫 선택 처리 모드다. 결과적으로 통찰이 실시간에 비해 아주 늦게 오는 일이
  흔하다. 이 이슈를 완화하면서도 배치 파이프라인을 계속 쓰려면 앞 절에서 소개한 부분 세션을 만들 수
  있다** (5장, p.144).[^konieczny2025]

## 세션은 앞으로 의존적이다

- 대가 ③이 이 패턴에서 가장 무겁다 — **세션화 로직이 이벤트 시각 파티셔닝에 의존하면 늦은 데이터가
  문제가 될 것이다. 이미 처리된 파티션에 대한 세션을 놓칠 수 있기 때문이다** (5장,
  p.144).[^konieczny2025]
- 그 이유가 이 데이터 자산의 성질이다 — **세션은 앞으로 의존적인(forward dependent) 특정 데이터
  자산이다. 처음에는 이상하게 들리지만 사실이다. 09:00 파티션에 대해 생성된 세션이 10:00의 세션에
  직접 영향을 주고, 10:00의 것이 11:00의 것에 영향을 주고, 그런 식이다. 따라서 한 엔티티에 대해
  늦은 데이터를 통합해 내더라도 이 데이터가 다음 세션들에 영향을 주지 않는다는 보장이 없다** (5장,
  pp.144–145).[^konieczny2025]
- 그 의존이 백필에서 그대로 드러난다 — **한 파티션에 대해 세션 생성 로직을 재실행하면 모든 후속
  파티션에 대해서도 같은 일을 해야 한다. 이는 매우 빠르게 비싸질 수 있다** (5장,
  p.145).[^konieczny2025]
  - 저자의 판정 — **불행히도 코드베이스를 쉽게 유지하면서 비용을 최적화할 은탄환은 없다. 백필된 것
    뒤의 모든 파티션을 재생하는 단순한 해법은 코드에는 쉽지만 비싸다. 반면 백필할 엔티티를 찾는
    똑똑한 탐지 방법을 갖고 전용 백필 파이프라인에서 그것들만 재실행하는 것은 비용을 최적화하지만
    여분의 복잡성을 더한다** (5장, p.145).[^konieczny2025] 같은 갈림이 늦은 데이터 쪽에서 정적
    대 동적 통합으로 나타난 것이 [늦은 데이터 통합](late-data-integration.md)이다.

## Stateful Sessionizer — 상태 저장이 보류 저장을 대신한다

- 문제 — **이해관계자들이 이제 세션 가용성에 꽤 만족하지만, 점점 더 많은 이가 더 낮은 지연으로
  세션에 접근해야 한다. 파티션이 시간 단위이고 제공할 수 있는 최선의 지연이 한 시간이므로 Incremental
  Sessionizer로는 그것을 달성하는 것이 불가능하다. 좋은 소식은 방문이 스트리밍 브로커에서도 수 초
  안에 사용 가능하다는 것이다** (5장, p.147).[^konieczny2025]
- 왜 기본 스트리밍으로 부족한가 — **세션에 대한 "가능한 한 빨리" 보장은 배치 파이프라인으로 얻기
  어렵다. 그러나 기본 스트리밍 파이프라인도 무상태이므로 도움이 되지 않는다. 그런 이유로 더 진보된
  버전을 써서 Stateful Sessionizer 패턴으로 문제를 풀어야 한다** (5장,
  p.147).[^konieczny2025]
- 무엇이 다른가 — **상태 있는 파이프라인은 상태 저장(state store)이라는 여분 컴포넌트를 가져온다.
  세션화 맥락에서 상태 저장은 Incremental Sessionizer의 보류 세션 저장 구역과 같은 역할을 한다.
  즉 진행 중인 모든 세션을 영속화하고 처리 내내 사용 가능하게 유지한다** (5장,
  p.147).[^konieczny2025]
- 워크플로는 배치 쪽과 같다 (5장, p.147):[^konieczny2025]
  - **세션을 생성하는 것으로 시작하거나, 상태 저장에 있다면 재개한다.**
  - **생성되거나 재개된 세션을 새로 들어오는 레코드와 비즈니스 로직에 따라 결합한다. 예컨대 방문한
    페이지를 순서대로 저장할 수 있다.**
  - **끝에서 세션이 완료됐거나 부분 세션이 소비자에게 필요하면 보류 세션 레코드를 최종 출력으로
    변환해 쓴다. 추가로 세션이 완료되지 않았다면 이 단계는 새 상태를 상태 저장에 쓴다.**
- 상태 저장은 두 겹이다 — **프레임워크 위에 구현하면 상태 저장 지원을 기본으로 얻는다.** 그 구조는
  **두 맛의 저장**이다 — **첫째는 빠른 접근용이라 메모리에 살고, 그래서 당연히 휘발성을 수반한다.
  실패나 재시작 시 상태를 잃을 위험을 넘기 위해 잡은 정기적으로 상태를 더 탄력적인 결함 내성 저장에
  동기화한다** (5장, p.148).[^konieczny2025] 그 저장의 유형 분류는
  [스트림 처리의 상태](../concepts/stream-processing-state.md)에 있다.

## 세션 윈도와 임의 상태 처리

- 처리 로직이 기댈 수 있는 추상은 둘이다 (5장, pp.148–149):[^konieczny2025]
  - **세션 윈도**(session window) — **각 세션 키에 대해 생성되는 윈도다. 그 길이는 갭 기간
    (gap duration)으로 지정되는데, 같은 세션 키를 가진 두 이벤트 사이의 최대 허용 비활동 기간이다.
    같은 세션 키를 가진 두 이벤트 사이의 시간 양이 갭 기간보다 크면 새 세션 윈도가 생성될 것이다.
    아니면 새 이벤트는 이미 열린 세션의 일부가 될 것이다.** 저자의 예에서 갭 기간이 20분일 때
    10:00·10:05·10:15는 한 윈도에 들어가고, 30분 뒤인 10:45가 새 윈도를 연다(그림 5-8).
    그 윈도 종류의 자리는 [스트림 처리의 시간 윈도우](../concepts/stream-processing-time-windows.md)다.
  - **임의 상태 처리**(arbitrary stateful processing) — **세션 윈도보다 더 많은 구현 노력을
    요구하지만 더 많은 유연성을 제공한다. 갭 기간 로직을 정의하는 것이 당신에게 달렸는데, 앞 예처럼
    정적 타이머일 수도 있고 각 세션 키마다 다를 수 있는 동적 연산일 수도 있다. Apache Spark
    Structured Streaming·Apache Flink, 심지어 GCP Dataflow 같은 현대 데이터 엔지니어링
    프레임워크가 이 능력을 기본으로 제공한다.**
- Flink의 세션 윈도가 이 패턴의 대표 코드다 — **세션 키를 추출하는 코드로 시작해 10분 갭 기간과
  15분 허용 지각으로 세션 윈도를 설정한다. 마지막 파라미터는 이미 방출된 세션 윈도에 통합될 이벤트가
  얼마나 늦을 수 있는지를 정의한다** (5장, pp.152–153):[^konieczny2025]

  ```java
  sessions: DataStream = (visits_input_data_stream
    .key_by(VisitIdSelector())
    .window(EventTimeSessionWindows.with_gap(Time.minutes(10)))
    .allowed_lateness(Time.minutes(15).to_milliseconds())
    .process(VisitToSessionConverter(), Types.STRING()).uid('sessionizer'))
  ```

## 상태 있는 세션화의 네 가지 대가

- 대가 ① **적어도 한 번 처리** — **결함 내성 저장에 상태를 저장하는 것은 매 상태 갱신마다 일어나지
  않는다. 대신 체크포인팅(checkpointing)이라 불리는 쓰기 프로세스가 불규칙하게 일어난다. 짐작하듯
  멈춘 잡은 마지막 성공 체크포인트에서 재시작하고, 이는 적어도 한 번 처리로 이어진다. 이 의미론 자체는
  나쁘지 않지만, 그것을 알고 세션의 멱등성에 영향을 줄 수 있는 연산의 부작용을 피하는 편이 낫다.
  세션 키를 생성하기 위해 실행 사이에 바뀌는 속성에 의존하는 것이 그런 예다. 그런 속성 유형의 예가
  실시간(real time)인데, 명백히 각 재시작마다 다를 것이다** (5장,
  p.149).[^konieczny2025] 그 체크포인팅은
  [스트림 처리의 결함 내성](stream-processing-fault-tolerance.md)에 있다.
- 대가 ② **스케일링** — **이 상태 있는 맥락에서 컴퓨트 용량을 바꾸는 것은 상태 재균형을 수반할 수
  있다. 특정 상태 키가 새 워커에 배정되지 않는 한 잡이 데이터를 처리할 수 없다는 뜻이다. 그것이
  스케일링을 불가능하게 만들지는 않지만 무상태 잡보다 더 비싸게 만든다** (5장,
  p.149).[^konieczny2025]
- 대가 ③ **비활동 기간 길이** — **Incremental Sessionizer에서와 마찬가지로 여기서도 총 비용을
  받아들일 수 있게 유지하면서 가능한 한 많은 세션을 포함하는 올바른 균형을 잡아야 한다. 더 긴 비활동
  기간을 갖는 것은 더 많은 하드웨어 압력과 출력 신선도를 함의한다** (5장,
  p.149).[^konieczny2025]
- 대가 ④ **어느 시간축으로 만료시킬 것인가** — **출력 저장으로 세션을 방출하는 것 외에 해법은 완료된
  모든 세션에 대한 상태의 만료도 관리해야 한다. 청소는 두 다른 시간 측면에 의존한다. 첫째는 들어오는
  이벤트의 이벤트 시각인데, 더 신뢰할 만하고 대부분의 경우 선호돼야 한다. 그러나 처리 시각 기반
  만료도 있는데 이쪽은 약간 위험하다** (5장, p.150).[^konieczny2025]
  - 왜 위험한가 — **처리 시각 기반 로직은 현재 시각에 의존한다. 예기치 못한 지연(예컨대 쓰기 재시도
    때문에)이 세션을 너무 일찍 만료시킬 수 있다는 뜻이다. 이 예측 불가능성 때문에 상태 있는
    파이프라인에서는 언제나 이벤트 시각으로 추론하는 것이 더 쉽다** (5장,
    p.150).[^konieczny2025]
  - 이벤트 시각보다 한 걸음 더 나은 것이 워터마크다 — **매번 이벤트 시각을 쓰는 것이 왜 최선이
    아닐 수 있는가? 코드 로직을 크게 단순화한다는 사실에도 불구하고 그렇다. 여기서는 워터마크에
    의존하는 것이 더 나은 접근인데, 잡의 진행에 관련되고 따라서
    `.withWatermark('event_time', '1 minute')` 연산에 관련되기 때문이다** (5장,
    p.152).[^konieczny2025] 저자의 표 5-4가 그 차이를 보인다 — 워터마크 1분·상태 만료 10분에서
    키 A는 워터마크 전략으로는 키 B의 첫 원소를 처리한 직후 방출될 수 있지만(10:10 < 10:14),
    이벤트 시각 전략으로는 만료 시각이 새 워터마크 너머라 그렇지 않다(10:18 > 10:14).
