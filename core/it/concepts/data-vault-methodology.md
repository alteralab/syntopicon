# Data Vault 2.0 방법론

이 페이지의 질문: **DV 2.0 방법론은 어떤 표준들을 왜 섞었고, 계획–실행–리뷰를 어떤 구조와 규율로 반복하는가?** [모델링](../concepts/data-vault-modeling.md)이 허브·링크·새틀레이트라는 구조 규약이라면, 방법론은 그 구조를 스프린트마다 반복 생산 가능하게 만드는 프로젝트 실행 규약이다.

## 무엇을 섞었고 왜

- DV 2.0 방법론은 소프트웨어 공학 표준들을 DW용으로 조합한 것이다: Scrum은 팀 조율과 일상 업무, PMP(PMBOK)는 스프린트 내 공식 프로젝트 계획, CMMI는 전체 관리·감독과 리뷰/개선 세션, TQM은 프로세스·데이터의 폐루프(closed loop) 지속 개선, Six Sigma는 측정(추정 대 실적 KPI) 기반 오류 감소를 맡는다 (§3, p.50).[^linstedt2016]
- 반복 주기의 핵심 정의는 원문이 정확하다 (§3, p.50):[^linstedt2016]

  > Within a two- to three-week-long Scrum iteration (sprint), the team executes a mini-waterfall which is based on the software development life cycle (SDLC). The goal is to have completed deliverables after this iteration, which can be put into production.

- 방법론 전체는 세 활동으로 구성된다: ① 프로젝트 계획(관리·정의·추정), ② 프로젝트 실행(스프린트 정의·팀 조직·기술 번호 부여), ③ 리뷰와 개선 (§3, p.50).[^linstedt2016]
- 순수 Scrum과의 차이: 애자일임에도 스프린트 안에 과업–산출물–역할을 명시한 **공식 프로젝트 계획**을 둔다는 점이 강조된다 (§3.1, p.51).[^linstedt2016]
- "애자일 빅뱅은 없다" — 여러 스프린트에 걸쳐 개발만 하다가 2년 뒤 프로젝트 말미에 일괄 배포하는 방식을 명시적으로 배격한다. 표준은 아티팩트를 개발한 그 스프린트 안에서 배포하는 것이다 (§3.1.2.4, p.66).[^linstedt2016]
- CMMI 관점에서 DV 2.0이 성숙도 5(최적화) 도달을 돕는 근거: 추정–실적 비교로 측정 가능(measurable), 패턴 기반 모델링·적재로 반복 가능(repeatable), 표준·템플릿으로 정의됨(defined), 2–3주 배포와 팀 신축으로 유연(flexible), 모델의 유기적 성장으로 확장 가능(scalable) 등이 열거된다 (§3.1.1.4, pp.58–59).[^linstedt2016]
- 성숙도 단계 매핑(표 3.1): 레벨 2 = 사전 정의된 문서 템플릿·구현 표준·패턴 기반 아키텍처, 레벨 3 = 정의된 프로젝트 프로세스, 레벨 4 = 추정·실적 수집과 리드타임·복잡도·결함 측정, 레벨 5 = 자동화 도구·신속 인도·병렬 팀. 병렬 팀은 레벨 4를 달성한 뒤에나 시도하라고 명시한다 — 성숙도 건너뛰기는 역효과다 (§3.1.1, pp.59–60).[^linstedt2016]

## 프로젝트 계획: 역할·변경 흐름·범위

- 책임은 사람이 아니라 **정의된 역할**에 배정한다. 역할이면 사람 교체가 가능하고, 신규 인력이 자기 책임을 빨리 파악한다. 한 사람이 여러 역할(4개 이상도 관찰됨)을 겸할 수 있다 (§3.1, p.52; §3.2.2, p.87).[^linstedt2016]
- 핵심 신설 역할은 기술 비즈니스 분석가(technical business analyst)다. 비즈니스에 보고하지만 SQL·데이터 모델을 다루는 파워 유저로, 비즈니스–IT 사이의 "담 너머 던지기(over-the-fence-throwing)" — 실패 프로젝트의 흔한 근본 원인 — 를 막는 중재자다. 비즈니스와 IT 역할을 분리하지 말고 한 팀으로(가능하면 같은 공간에) 두라고 권한다 (§3.1, pp.52–53).[^linstedt2016]
- 변경 요청은 정해진 채널을 탄다: 비즈니스 사용자 → 스폰서(우선순위 결정) → 기술 비즈니스 분석가(기술 용어로 번역) → IT 관리자·프로젝트 관리자(일정·위험 평가) → 위험 평가 결과를 비즈니스에 반환해 최종 결정 → 다음 스프린트에 편성 → 비즈니스 테스트 후 공식 승인(sign-off)으로 IT의 의무 종료 (§3.1, pp.54–55).[^linstedt2016]
- 릴리스는 도달 범위로 구분한다: 알파(IT팀 + 기술 비즈니스 분석가 3–5명까지, 보통 첫 2–3 스프린트 후 배포), 베타(스폰서·선별된 비즈니스 관리자까지), 감마(프로덕션, 전체 비즈니스 사용자) (§3.1, pp.55–56).[^linstedt2016]
- IT는 운영 이슈에서 상대적으로 격리된 채 스프린트를 돌 수 있어야 한다. 이를 위해 관리형 셀프서비스 BI(managed self-service BI)로 책임을 비즈니스로 이동한다 — 운영계 오류를 보정하려고 IT가 DW의 데이터를 고치는 것은 IT의 책임이 아니며, 오류는 비즈니스가 소스에서 고치게 한다 (§3.1, p.53).[^linstedt2016]

### 수직 인도와 범위 규율

- 레거시 아키텍처(3NF·스타 스키마)는 초기 모델 수정 비용이 커서 전사를 한 번에 모델링하도록 강제했지만, DV 2.0은 변경 흡수가 싸므로 계층별(수평) 구축 대신 **기능(feature) 단위 수직 구축**을 쓴다: 보고서 하나를 스코핑하고, 그 보고서에 필요한 소스 테이블만 스테이징 → Data Vault → 마트로 관통시킨다 (§3.1.3, pp.67–68).[^linstedt2016]
- 규칙: 스코프에 든 소스 테이블은 **전체 컬럼을 한 번에** 적재·모델링한다. 부분 적재는 "무엇이 이미 DW에 있는가" 평가를 복잡하게 만들고 새틀라이트도 복잡해지므로 피한다. 같은 테이블을 여러 번 건드리지 않는다 (§3.1.3, p.68).[^linstedt2016]
- 트레이드오프 두 가지가 명시된다 (§3.1.3, pp.68–69):[^linstedt2016]
  - "소스 시스템의 전 테이블을 한 번에 적재하자"는 반론 → 당장 필요 없는 데이터 적재는 ETL 용량·초기 인프라를 키우고 한 스프린트에 끝나지 않으며, 기능 인도에 쓸 인력을 묶는다.
  - "타깃을 여러 번 건드리면 비싸다"는 반론 → 사실일 수 있으나, 한 스프린트 안에 유용한 기능을 인도해 "비즈니스가 결과물을 거부하는" 실패 위험을 줄이는 이득이 더 크다.
- 모델링은 스프린트 기간 안에 끝나야 한다. 더 걸리면 스프린트 범위가 너무 크다는 신호이며, 이번 기능에 불필요한 것을 스프린트에서 덜어낸다(제거가 아니라 후속 스프린트로 이연임을 비즈니스에 이해시킨다) (§3.1.3, p.69).[^linstedt2016]

### 애자일 요구사항 수집 — Raw Mart 기법

- 요구사항은 프로젝트 초기에 일괄 수집하지 않고 진행하며 수집한다. 핵심 기법: 비즈니스 규칙 없이 원시 데이터를 차원 형태로만 바꾼 **Raw Mart**를 빠르게 만들어 요구사항 회의에 들고 가서 "이 보고서의 무엇이 잘못됐나?"를 묻는다. 사용자가 문제를 짚는 행위 자체가 IT에 필요한 비즈니스 규칙을 제공한다 (§3.1.3.1, p.69).[^linstedt2016]
- 절차 6단계: ① 필요한 데이터 식별(스코프 내 데이터만 적재) → ② Raw Mart 생성(비즈니스 규칙 미적용, 가상 뷰 권장) → ③ Raw Report 생성 → ④ 보고서를 벽에 게시해 참석자가 직접 주석 → ⑤ 비즈니스 규칙·요구사항 수집(문서화) → ⑥ 규칙을 ETL 또는 SQL 뷰 로직으로 번역. ①–③은 IT가, ④–⑤는 비즈니스가 주도한다 (§3.1.3.1, pp.69–70).[^linstedt2016]
- 이후 수정 요구는 전부 변경 요청이 되어 후속 스프린트로 간다. 회의는 녹화해 위키에 공개, 요구사항 투명성을 확보한다 (§3.1.3.1, p.70).[^linstedt2016]

### 추정 — 기능 점수 분석

- 추정은 기능 점수 분석(Function Point Analysis, FPA)에 의존한다. 채택 이유: 기능을 개별 항목으로 분해해 추정하는 방식인데, DV 2.0은 아티팩트가 표준화돼 있어 분해가 쉽다. 또한 FPA는 코드 줄 수(LOC) 같은 기술 종속 지표와 달리 인도되는 기능을 측정한다 (§3.1.4, pp.71–72).[^linstedt2016]
- DW 적응 세 가지 변환: ① 컴포넌트 경계 재정의 — DW의 한 기능은 스테이징·코어 DW·마트 전 계층의 변경 합이다, ② 기능 유형 매핑 — 스테이징 테이블→외부 인터페이스 파일(EIF), 타깃·팩트·차원·룩업 테이블→내부 논리 파일(ILF), 매핑(ETL)→외부 입력(EI), 프로세스 경보→외부 출력(EO), ③ ETL 복잡도 요인 식별(회귀 분석으로 실제 영향 요인 선별) (§3.1.4.4–3.1.4.6, pp.73–75).[^linstedt2016]
- DV 전용 기능 특성이 정의된다: 스테이지 적재·허브 적재·링크 적재·새틀라이트 적재·차원 적재·팩트 적재·보고서 빌드. DV 2.0 적재 루틴은 EtL(소문자 t) 패턴 — 변환이 최소라 기능 점수가 낮고 복잡도가 단순해야 정상이다 (§3.1.4.7, p.76).[^linstedt2016]
- 복잡도의 일반 규칙: 허브가 가장 쉽고(비즈니스 키 크기와 무관하게 점수 동일), 링크는 쉬움–보통(연결 허브 수에 비례), 새틀라이트는 보통–어려움. 새틀라이트는 얇은(thin) 것과 넓은(wide) 것을 구분한다 — 컬럼이 많을수록 적재 로직이 복잡하고 오적재 위험이 커진다 (§3.1.4.7–3.1.4.8, pp.77–78).[^linstedt2016]
- 기능 점수당 소요 시간(person hours per function point)은 프로젝트마다 실측해 보정해야 하며, 조직 간 이식이 안 된다 — 성숙도·인력 경험·내외부 인력 비율이 다르기 때문. 첫 사이클부터 점수당 실제 시간을 추적하는 것이 추정의 전제다 (§3.1.4.7–3.1.4.8, pp.77–78).[^linstedt2016]
- 추정의 목적은 예측 가능성이다: 추정–실적 비교에서 팀이 학습하고, 맞는 추정이 비즈니스의 신뢰와 후속 예산을 만든다. 그래서 추정은 방법론의 중심 요소다 (§3.1.4.7–3.1.4.8, pp.75, 79).[^linstedt2016]

## 프로젝트 실행: 미니 폭포수와 산출물 규율

- 실행 지침 7개: ① 초기 아키텍처를 구상하되 진화 가능하게, ② 모델링은 저스트 인 타임(스프린트 범위만), ③ 아키텍처 결정은 일찍 검증(늦은 변경은 비싸다), ④ 직접적 비즈니스 가치가 있는 기능만 구현, ⑤ "단일 진실" 집착 회피(사실과 데이터에 집중), ⑥ 요구사항 중심으로 작업 조직(요구사항 문서가 구현보다 수정하기 쉽다), ⑦ 일일 스탠드업에 이해관계자 참석 (§3.2, p.79).[^linstedt2016]
- 3주 스프린트의 표준 분할(표 3.5): 1주차 설계·개발, 2주차 관리·테스트, 3주차 배포·수용. 이것이 스프린트 안의 미니 폭포수(mini-waterfall)이며, 전통 SDLC(요구공학→설계→구현·단위테스트→통합·시스템테스트→운영·유지보수)를 스프린트 규모로 축소한 것이다 (§3.2–3.2.1, p.80).[^linstedt2016]
- 조직은 보통 3–4주 주기로 시작해 빠르게 2주로 단축을 시도한다. 예시 프로젝트 플랜은 보고서 1건 인도 = 58시간(2주 스프린트) 규모이며, 자동화 도구 없이는 2주 스프린트 달성이 어렵다고 명시한다. 스코핑 과업은 중요하지만 2시간을 넘기면 안 된다 (§3.2, p.79; §3.2.2, pp.84–85).[^linstedt2016]
- 산출물은 코드·모델만이 아니다. 필수 문서 목록: 비즈니스 용어집, 요구사항 문서(요구사항당 1쪽 내외), 프로젝트 플랜(한 스프린트 과업만), 약어집, 범위 기술서(스프린트 말 승인 절차의 근거), 변경 요청 문서, 인도·승인 문서, 역할·책임 문서, 작업 분해 구조(WBS)·프로세스 분해 구조·데이터 분해 구조·조직 분해 구조, 데이터 모델 표준, ETL 표준 (§3.2.2, pp.85–86).[^linstedt2016]
- **기술 번호 부여(technical numbering)**: 모든 프로젝트·스프린트의 모든 문서와 아티팩트(역할 1개, 변경 요청 1건, 요구사항 1건, 과업 1개, 용어 1개 단위까지)에 계층적 십진 번호를 매긴다. 한 번 부여한 번호는 재부여·재정렬 금지 — 워드프로세서의 자동 번호 매기기를 쓰지 말라는 수준까지 명시한다 (§3.2.4, pp.87–88).[^linstedt2016]
- 번호의 용도는 교차 참조 행렬이다: 요구사항↔소스 테이블, 소스 테이블↔Data Vault 테이블, Data Vault↔정보 마트, 요구사항↔정보 마트. 아티팩트를 유일하게 식별해야 실적을 아티팩트에 귀속시켜 측정할 수 있고, 측정이 안 되면 계획 대비 비교도 프로세스 최적화도 불가능하다 (§3.2.4, pp.88–89).[^linstedt2016]
- 병렬 팀: 역할이 정의돼 있으므로 팀을 추가해 확장할 수 있다. 각 팀은 상호 의존 없는 소규모 스코프를 맡고, 병렬 팀 간 데이터 모델 동기화는 링크 엔터티로 한다. 기존 DV 팀이 있으면 신규 인력에게 요구되는 기술은 낮다(스테이지·허브·링크·새틀라이트 적재는 기본 SQL 수준) (§3.2.3, p.87).[^linstedt2016]

## 리뷰와 개선: 두 미팅과 측정 루프

- 스프린트를 닫기 전 두 미팅을 한다: **스프린트 리뷰**(제품 검토 — 산출물이 문서화된 요구사항을 충족하는지, 이해관계자 폭넓게 참석, 편차는 변경 요청으로) 와 **회고(retrospective)**(프로세스 검토 — 개선할 활동 식별 + 추정 리뷰: 과소/과대 추정의 원인을 찾아 중단). 기능을 최초 요구사항까지 추적하려면 기술 번호가 필수다 (§3.3, pp.89–90).[^linstedt2016]
- Six Sigma의 역할: 추정 대 실적 KPI로 스프린트가 얼마나 어긋났는지, 프로세스를 어떻게 교정할지를 판단한다. 측정 대상은 **팀이지 개인이 아니다** — 개인을 측정하면 측정을 전복하려 들고, 일부 법제에서는 개인 생산성 측정이 불법이다. 지표는 성과의 잠재 지시자로만 취급하고, 실제 원인은 사람에게 물어라 (§3.3.1, p.90).[^linstedt2016]
- Six Sigma는 데이터 자체에도 적용된다: 테스트에서 발견된 "버그" 수가 데이터가 얼마나 나쁜지의 지표이며, 오류가 줄고 프로세스가 간결해질수록 팀은 더 빠르고 싸고 애자일해진다 (§3.3.1, p.90).[^linstedt2016]
- 개선 루프는 DMAIC 5단계다: 정의(define, 문제와 고객 영향) → 측정(measure, 기준선 대비 현재 성능) → 분석(analyze, 근본 원인·개선 기회를 고객 만족 기여와 수익 영향 두 축으로 우선순위화) → 개선(improve, 후보 해법 중 선택; 여러 변수를 통계 설계 실험으로 동시 변화) → 통제(control, 개선 유지; 위험하면 루프 재시작) (§3.3.1.3, pp.96–97).[^linstedt2016]
- 반복 주기 단축(4→3→2주)은 이 두 미팅의 지속 개선 없이는 달성 불가다. 팀이 활동별 소요 시간을 실측해 어디에 시간이 새는지 찾고, 기술(블루그린 배포·ETL 자동화)·스코핑·훈련으로 줄인다 (§3.3.1.4, p.97).[^linstedt2016]
- TQM의 위치: DV 2.0 방법론에서 TQM은 애자일·CMMI·Six Sigma 적용을 묶는 **거버넌스 메커니즘**이다. Total = 전 조직 참여, Quality = 사용자 기대 충족·초과, Management = 시스템·프로세스의 개선·유지 (§3.3.2–3.3.2.4, pp.98, 102).[^linstedt2016]
- TQM의 핵심 규율은 폐루프다: 보고서에서 오류를 발견하면 소스와 프론트엔드 사이 어딘가에서 몰래 고치지 말고, 비즈니스 사용자를 참여시켜 **소스 시스템에서** 고친다. DW 안에서의 보정이 허용되는 유일한 방식은 Raw Data Vault에서 나가는 길(비즈니스 볼트·정보 마트)에 소프트 비즈니스 규칙을 적용하는 것뿐이다. 폐루프 없는 오류 수정은 TQM이 아니라 단순 데이터 품질(DQ) 활동에 불과하다 (§3.3.2.4, p.103).[^linstedt2016]
- 데이터 품질을 다차원으로 평가한다(표 3.10): 접근성·적정량·신뢰성·완전성·간결성·정합성·조작 용이성·무오류·무결성·해석 가능성·객관성·관련성·평판·보안·적시성·이해 가능성·유일성·부가가치. 평가에는 과업 독립적인 것과 조직의 비즈니스 규칙 지식이 필요한 과업 의존적인 것이 있다 (§3.3.2.1, p.100).[^linstedt2016]
- TQM 계열의 순환 방법론 두 가지가 소개된다: TDQM(정의→측정→분석→개선의 4단계 순환)과 유럽 DWQ 프로젝트의 DWQ 방법론(같은 4단계이나 평가 구간과 개선 구간의 연결이 다름) (§3.3.2.2–3.3.2.3, pp.100–102).[^linstedt2016]
