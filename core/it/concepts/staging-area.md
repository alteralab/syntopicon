스테이징 영역(staging area)은 원천 시스템과 데이터 웨어하우스 사이의 일시적
완충 계층이다. 원천에서 최대한 빨리 데이터를 받아내리고, 웨어하우스 적재에
필요한 시스템 열을 계산해 붙인 뒤, [Raw Data Vault 적재](../concepts/data-vault-loading-patterns.md)가
끝나면 비운다.

## 목적

- 1차 목적은 **원천 시스템의 부하 감소**다. 필요한 데이터를 별도 데이터베이스에
  먼저 통째로 적재해, 웨어하우스 적재 과정의 조회(lookup)가 운영계를 반복
  타격하지 않게 한다. 이 수집(ingestion)은 제공되는 어떤 형식이든 가능한 한
  빨리 수행해야 한다 (§11.1, pp.374–375).[^linstedt2016]
- 스테이징된 데이터는 웨어하우스 팀의 기술적 통제 아래 들어온다 — 인덱스·정렬·
  조인 등 관계형 연산을 자유로이 쓸 수 있다. 데이터 타입은 원천 시스템의 의도된
  타입을 따르는 것이 원칙이다(varchar만 쓰지 말 것). 단 추출 편의를 위해 이
  권고를 어기고 문자열로 받은 뒤, Data Vault 적재 시점에 실제 타입으로 변환하는
  실무 타협도 있다 (§11.1, p.375).[^linstedt2016]
- 스테이징은 원천 수집(sourcing)의 문제 — 지연 변동·도착 시점 불일치·네트워크
  오류·접근 권한 만료 — 를 웨어하우징 본연의 문제와 분리하는 장치이기도 하다.
  데이터를 일단 "쏟아 놓고" 각 단계가 자기 문제만 다루게 한다 (12장 서두, p.470).[^linstedt2016]

## 왜 이력을 두지 않나

- 스테이징 영역은 **일시적(transient)** 이다. 제한된 횟수의 적재분만 유지하며,
  그 목적은 다운스트림 ETL(Raw Data Vault 적재)이 실패했을 때 데이터 유실을
  막는 것뿐이다 — 모든 오류가 하루 안에 고쳐지지는 않기 때문이다 (§11.1, p.375).[^linstedt2016]
- 적재 이력의 보관은 엔터프라이즈 데이터 웨어하우스 계층의 몫이다. 스테이징이
  전체 이력을 유지하면 저장·백업 등 관리가 추가돼 **데이터 웨어하우스를 두 개
  관리하는 꼴**이 된다 (§11.1, p.375).[^linstedt2016]
- 스테이징 테이블 간에는 외래 키로 참조 무결성을 걸지 않는다. 들어오는 소스
  (플랫 파일·관계형 테이블)는 각각 독립적으로 수집되기 때문이다. 각 스테이징
  테이블은 들어온 데이터의 직접 복사본에 시스템 생성 열만 더한 것이다
  (§11.1, p.375).[^linstedt2016]
- 참조 데이터를 스테이징에 가상(뷰)으로만 두고 웨어하우스 계층이 거기 의존하게
  만들면 아키텍처 위반이다 — 스테이징은 중앙 저장소가 아니다 (§12.2.1, pp.551–552).[^linstedt2016]

## 적재 템플릿과 계산 열

스테이징 테이블 적재는 표준 패턴을 따른다: 테이블 truncate(한 적재분만 유지할
때) → 인덱스 비활성화(옵션) → 원천 벌크 읽기(청크 단위, ORM 등 복잡한 API 회피)
→ 시스템 값 계산 → 완전 중복(true duplicate) 제거 → insert → 인덱스 재구축
(§11.1, pp.375–376).[^linstedt2016]

- 완전 중복을 스테이징에서 제거하는 이유: 허브·링크에는 추가 작업량만 만들 뿐
  무해하지만, 새틀라이트 적재의 변화 감지 구현에 따라 문제를 일으킬 수 있다
  (§11.1, p.376).[^linstedt2016]
- "시스템 값 계산" 단계가 붙이는 열은 다섯 가지다: 적재 시각(load date)·레코드
  소스(record source)·시퀀스 번호(sequence number)·업무 키마다의 해시 키·
  새틀라이트마다의 hash diff(옵션) (§11.1, pp.376–377).[^linstedt2016]
- 해시 값(해시 키·hash diff)은 CPU를 쓰므로 계산 결과의 재사용이 이득이다.
  80% 이상의 경우에서 스테이징 적재 시점에 계산해 두는 것이 목표다. 입력 결합
  규칙은 [해시 규율](../concepts/hashing-in-data-vault.md) 참조 (§11.2, pp.378–379).[^linstedt2016]
- 스테이징이 웨어하우스와 같은 인프라에 있으면, 타깃 새틀라이트를 미리 들여다보는
  look-ahead 질의로 신규/변경 레코드를 스테이징 단계에서 분리해 적재 성능을 더
  끌어올릴 수 있다 (§12.1.6, p.538).[^linstedt2016]

### 적재 시각

> The **load date** identifies "the date and time at which the data is
> physically inserted directly into the database"

- 적재 시각은 반드시 **웨어하우스가 생성·통제**한다. 원천의 생성일·수정일 등을
  적재 시각으로 쓰면 도착 지연 혼재·시간대 혼재·날짜 없는 원천·원천 시계의
  신뢰성 문제에 부딪히고, 원천이 생성일을 바꾸면 새틀라이트 기본 키의 불변성이
  깨진다 (§11.3, pp.401–402).[^linstedt2016]
- 원천의 생성일·수정일·유효 시작/종료일 같은 날짜들은 적재 시각 자격이 없다.
  대신 업무 가치가 있으므로 기술(descriptive) 데이터로서 새틀라이트에 적재한다
  (§11.3, pp.402–403).[^linstedt2016]
- 한 배치(한 세트로 도착한 모든 데이터)는 같은 적재 시각을 가진다. 도착 시각은
  밀리초 수준까지 식별해야 한다 — 새틀라이트 기본 키(부모 해시 키 + 적재 시각)의
  유일성이 하루 다회 배치에서도 유지되어야 하기 때문이다. 타임스탬프가 안 되는
  DB에서는 유사 밀리초 카운터(서브시퀀스 번호)를 덧붙인다 (§11.3, p.401).[^linstedt2016]

### 레코드 소스

- 레코드 소스는 디버깅·추적 전용의 문자열이다. 시스템명만 쓰지 말고
  `[원천 애플리케이션].[스키마].[테이블]`처럼 필요한 만큼 상세한 계층 표기를
  쓴다. 예: `CRM.Cust.Customers` (§11.4, p.403).[^linstedt2016]
- 여러 소스를 결합·집계해 레코드 소스가 불분명해지면 그 레코드를 만든 업무
  규칙의 기술명을 쓰고, 규칙이 없는 시스템 생성 레코드는 `SYSTEM`으로 둔다
  (§11.4, p.403).[^linstedt2016]
- 특정 적재에 종속된 값은 피한다 — 날짜가 든 파일명, 물리 DB명·서버명은 위치가
  바뀌어도 같은 출처를 가리키지 못하므로 부적격이다 (§11.4, p.403).[^linstedt2016]

### 시퀀스 번호

- 시퀀스 번호는 원천에서의 레코드 순서를 인식하고, 스테이징까지만 적재되는 완전
  중복을 식별하는 용도다. 레코드의 식별자로는 쓰지 않는다 (§11.1, p.377).[^linstedt2016]

## truncate 주기

- 배치가 Raw Data Vault에 적재되면 스테이징을 정리한다. 저장 소비를 최소로
  유지해 관리 부담을 줄이고 후속 적재 성능을 지키기 위해서다. 세 가지 방식이
  있다 (§12.3, pp.566–567):[^linstedt2016]
  - **TRUNCATE TABLE** — 모든 데이터가 Raw Data Vault에 들어갔고 그 사이 새
    데이터가 도착하지 않았음이 보장될 때. 일 1회 배치가 전형.
  - **특정 적재 시각만 DELETE** — 하루 다회 배치라 위 보장이 불가능할 때.
    적재가 끝난 load date의 행만 지워 유실을 막는다.
  - **파티션 삭제** — DELETE는 느리므로, 테이블을 load date로 파티셔닝해 두고
    배치 완료 시 해당 파티션을 통째로 버린다.
- 제한된 이력을 유지하는 구성이라면 truncation은 다음 적재 시작 시점이 아니라
  Raw Data Vault 적재가 끝난 뒤에 수행한다 (§11.1, pp.375–376).[^linstedt2016]

## 관계형이냐 NoSQL이냐

- 스테이지 영역은 관계형 데이터베이스일 수도 NoSQL 저장소일 수도 있다. 들어오는 데이터가
  관계형 원천에서 오고 타입이 온전히 정해져 있으면 관계형이 최선의 선택이다 — 예컨대
  원천 데이터를 운영 데이터베이스에서 직접 추출해 스테이지에 적재하는 경우
  (§8.6.1, p.243).[^linstedt2016]
- 데이터가 플랫 파일이나 비정형 정보로 온다면 Hadoop 같은 NoSQL 저장소가 더 낫다. 나아가
  **볼륨이나 속도가 높을 때는 정형 데이터든 비정형 데이터든 NoSQL 스테이지 영역이 더 나은
  선택인 경우가 많다** — NoSQL에 저장하는 것은 파일 복사 연산만 요구하므로, 도착하는 크기와
  속도 그대로 데이터를 흡수하는 데 유리하기 때문이다. 흡수가 끝나면 거기서 추출해 Raw
  Data Vault로 적재한다 (§8.6.1, p.243).[^linstedt2016]
- 어느 쪽을 고르든 요구는 같다: **원천 시스템에서 가능한 한 빨리 데이터를 빼내** 웨어하우스가
  원천의 CPU·네트워크 자원을 쓰는 시간을 줄이는 것. 이는 네트워크 인터페이스 같은 다른
  요소에도 달렸지만, 우리가 다룰 수 있는 가장 중요한 선택지는 디스크 저장이다
  (§8.6.1, p.243).[^linstedt2016]

## 일시성이 허락하는 물리 설계

스테이징의 무이력·일시성은 규율이면서 동시에 **물리 설계의 예산을 깎아 주는 근거**다.
계층 무관의 하드웨어·데이터베이스 옵션 자체는
[물리 데이터 웨어하우스 설계](../concepts/physical-data-warehouse-design.md)에 있다.

- RAID 0은 데이터를 여러 디스크에 분산해 개별 디스크의 I/O 성능을 합치므로 **읽기·쓰기
  성능에서 다른 모든 RAID 수준보다 우월하다.** 어레이의 디스크 수는 선택한 버스의 성능에
  달렸다 (§8.6.1.1, p.244).[^linstedt2016]
- RAID 0에 결함 내성이 없다는 것이 문제가 될 수 있으나 **스테이지 영역에는 그리 큰 문제가
  아니다 — 일시적이기 때문이다.** 밑의 디스크 스트라이프가 죽어도 최악의 경우는 아직 적재되지
  않은 채 스테이지에 있던 데이터를 잃는 것이고, 그런 경우에도 원본 원천에서 다시 적재할 수
  있는 일이 많다. 재적재 가능성에 따라 RAID 0이 실행 가능한 해법이 된다
  (§8.6.1.1, p.244).[^linstedt2016]
- 스테이지는 소스 데이터의 직접 사본을 한 번 또는 제한된 횟수의 적재분만 담고 이력이 없으므로
  **저장 공간 요구가 웨어하우스의 나머지에 비해 크지 않다.** 그래서 크고 느린 디스크보다
  **빠른 디스크(예: 15,000 rpm SAS)** 를 택하는 편이 낫고, RAID 0 스트라이핑이 용량을 합쳐
  주므로 빠른 디스크의 용량 제약이 완화된다 (§8.6.1.1, p.244).[^linstedt2016]
  - 이 논의는 관계형 스테이지 영역에 한한다. **NoSQL 스테이지 영역을 쓰면 저장·신뢰성 요구가
    훨씬 높아진다** (§8.6.1.1, p.244).[^linstedt2016]
- 인메모리 테이블도 스테이징에 쓸 수 있지만, 들어오는 데이터를 메모리에 스테이징할 만큼의
  RAM을 인프라가 제공해야 하므로 더 비싼 선택지다 (§8.6.1.1, p.244).[^linstedt2016]
  - 버전 조건: Microsoft SQL Server 2014부터 인메모리 테이블이 도입됐다.
- 데이터베이스 설정 (§8.6.1.2, pp.245–247):[^linstedt2016]
  - 파일그룹을 넷으로 나눠 시작한다. 처음부터 물리 디스크 어레이가 넷 있을 필요는 없다 —
    **파일그룹이 나중에 데이터를 여러 디스크로 분산할 여지를 만들어 준다.** PRIMARY는 시스템
    객체만 담아 작게 유지되므로 서버의 직접 연결 디스크에 남기고, 로그 파일은 데이터와
    분리하며, 인덱스도 분리해 SSD 같은 매우 빠른 디스크에 둔다.
  - 초기 크기는 **원천 데이터 크기 × 스테이지에 잠재적으로 유지할 최대 적재 횟수**로 잡는다.
    스테이지가 이력을 두지 않아도 여러 배치를 담을 수 있다 — 유지보수나 다른 이유의 다운타임
    때문에 스테이지가 곧바로 웨어하우스로 적재되지 않는 경우가 있기 때문이다.
  - 자동 증가 기본값(10%)은 거대한 데이터베이스에서 수 기가바이트가 되므로 **파일그룹당
    1–5GB로 제한**하도록 권한다.
  - 복구 모델의 기본은 Full이지만, **웨어하우징에서는 Simple 복구가 권장 관행이다** — 로그
    파일에 기대는 대신 데이터를 수동으로 다시 적재할 수 있기 때문이다. 스테이지 영역의 성능을
    크게 좌우하는 설정이다.
  - 전문 검색(full-text indexing)이 켜져 있으면 색인 생성에 시스템 메모리를 쓴다. 질의에서
    쓰지 않는다면 웨어하우스에서 이 기능을 빼는 것을 고려한다 — 켜져 있으면 테이블 단위로
    꺼야 한다.
  - 모든 데이터베이스에 같은 데이터 정렬(collation)을 선택해 정렬 간 문자 변환 문제를 피한다.
    최선은 웨어하우스 서버의 기본 정렬을 그대로 두는 것이며, 설치 시 제대로 선택됐는지
    확인한다.

## 레이크하우스 쪽에서 같은 자리를 부르는 이름

위 절들이 세우는 스테이징 영역은 **데이터 볼트 웨어하우스의 규약**이다. 같은 자리를 메달리온
아키텍처 원전이 다시 여는데, 이름도 여럿이고 정당화의 근거도 다르다.

- 그쪽 이름은 **랜딩 존(landing zone)** 이고, 정의는 **원시 데이터가 메달리온 아키텍처에 착지하기
  전에 반입되는 예비 영역**이다 (2장 §"Extra Landing Zones").[^strengholt2025]
- **이름이 고정돼 있지 않다** — 어떤 조직은 그 계층을 "tin layer"·"pre-Bronze"·"pre-refinement"·
  "staging"·"landing area"라 부르며 통상의 메달리온 아키텍처 **밖**에 두고, 다른 조직은 Bronze 계층
  설계 안에 포함시킨다. 저자는 그 계층을 Bronze라 부를지는 각자가 정할 일이고 중요한 것은 조직의
  기능·비기능 요건을 충족하는 방식으로 반입·저장하는 것이라고 적는다
  (2장 §"Landing Zones Takeaway" 곁글).[^strengholt2025]
- **정당화의 근거가 다르다.** 위 "목적" 절이 스테이징을 원천 부하 감소와 적재 실패 대비로
  정당화한다면, 이 소스는 **원천의 특성과 팀 경계**로 정당화한다 — 외부 서비스나 SaaS 벤더를
  상대할 때 필요한 안전한 예비 저장, 그리고 추출 과정을 직접 관리하려는 애플리케이션 팀이
  요구하는 전용 랜딩 존이다. 그래서 원천과 레이크하우스 사이에 **랜딩 영역이 여럿** 있는 것이
  드물지 않다 (2장 §"Extra Landing Zones").[^strengholt2025]
- **건너뛰어도 되는 조건도 명시된다** — 원천 시스템이 튼튼한 보안 수단과 안정적인 직접 반입
  기법을 갖췄다면 중간 랜딩 존을 건너뛰고 Bronze 계층으로 곧장 먹이는 쪽이 더 효율적일 수 있고,
  그럴 때는 스테이징할 필요가 없다 (2장 §"Extra Landing Zones").[^strengholt2025]
- 이 소스에는 **비움 규칙이 없다.** 위 [truncate 주기](#truncate-주기) 절이 스테이징의 정의에
  가깝게 두는 "적재 후 비움"이 랜딩 존에는 조항으로 나오지 않는다. 두 규약이 같은 낱말을 다르게
  쓰는 것이라 서로를 부정하지 않는다.
- 이 랜딩 존 결정이 놓이는 더 큰 맥락은
  [메달리온 계층 이전의 결정과 Delta 테이블 관리](../concepts/medallion-groundwork-and-delta-table-management.md)에
  있다.
