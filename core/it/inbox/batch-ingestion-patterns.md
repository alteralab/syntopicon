하나의 질문: **배치로 반입하기로 정하고 나면 무엇이 아직 결정되지 않은 채 남는가.**

- 배치 반입이 무엇인지부터 — **대량으로 데이터를 처리하는 것을 수반하는 배치 반입은 데이터를
  반입하는 편리한 방식인 경우가 많다. 이는 시간 간격이나 누적된 데이터의 크기에 기반해 원천
  시스템에서 데이터의 부분집합을 취함으로써 데이터가 반입된다는 뜻이다** (7장,
  p.244).[^reis2022]
- 저자들이 이 절에서 다루는 다섯 패턴 (7장, p.245):[^reis2022]
  - **스냅샷 또는 차등 추출 / 파일 기반 내보내기와 반입 / ETL 대 ELT / 삽입·갱신·배치 크기 /
    데이터 마이그레이션**

## 배치를 자르는 두 기준

- **시간 간격 배치 반입(time-interval batch ingestion)은 데이터 웨어하우징을 위한 전통적 업무
  ETL에 널리 퍼져 있다. 이 패턴은 흔히 일간 리포팅을 제공하기 위해 비업무 시간 동안 밤새 하루
  한 번 데이터를 처리하는 데 쓰이지만 다른 빈도도 쓸 수 있다** (7장, p.245).[^reis2022]
- **크기 기반 배치 반입(size-based batch ingestion)은 데이터가 스트리밍 기반 시스템에서 오브젝트
  저장으로 옮겨질 때 꽤 흔하다. 궁극적으로 데이터 레이크에서의 미래 처리를 위해 데이터를 이산
  블록으로 잘라야 한다. 어떤 크기 기반 반입 시스템은 총 이벤트 수의 바이트 크기 같은 다양한
  기준으로 데이터를 객체로 쪼갤 수 있다** (7장, p.245).[^reis2022]
- 이 두 기준은 2장이 배치의 발동 조건으로 든 것과 같다 — **배치 데이터는 미리 정해진 시간
  간격으로, 또는 데이터가 미리 설정된 크기 임계에 닿을 때 반입된다** (2장, p.41).[^reis2022]
  7장은 그 둘을 각각 **어디에서 쓰이는가**로 나눠 놓은 것이다: 시간 간격은 웨어하우스 ETL,
  크기 기반은 스트림에서 오브젝트 저장으로 내리는 착지 지점.

## 전체 스냅샷과 증분 추출

- 두 선택지 — **데이터 엔지니어는 원천 시스템의 전체 스냅샷을 포획할지 차등(differential,
  때로 증분(incremental)이라 불리는) 갱신을 포획할지 골라야 한다. 전체 스냅샷(full snapshots)
  으로 엔지니어는 각 갱신 읽기마다 원천 시스템의 현재 상태 전체를 잡는다. 차등 갱신
  (differential update) 패턴으로 엔지니어는 원천 시스템에서 마지막으로 읽은 이후의 갱신과
  변경만 당길 수 있다** (7장, p.246).[^reis2022]
- 그런데 판정이 단순하지 않다 — **차등 갱신이 네트워크 트래픽과 대상 저장 사용을 최소화하는 데
  이상적이지만, 전체 스냅샷 읽기는 그 단순성 때문에 여전히 극히 흔하다** (7장,
  p.246).[^reis2022]
  - 이 판정은 5장에서 원천 시스템 쪽으로 본 서술과 짝을 이룬다 — 원천이 CRUD 패턴이면
    스냅샷 기반 추출을 쓸 수 있지만 CDC를 통한 이벤트 추출은 연산의 완전한 이력을 준다
    (5장, p.162).[^reis2022] 그쪽은
    [CRUD와 삽입 전용 패턴](../concepts/crud-and-insert-only-patterns.md)에 있다.
    **여기서 저자들이 더하는 것은 "단순성"이라는 반대 방향의 힘**이다 — 이력이 필요 없다면
    전체 스냅샷이 여전히 합리적 기본값이라는 것.

## 파일 기반 내보내기와 반입

- **데이터는 파일을 써서 데이터베이스와 시스템 사이에서 옮겨지는 일이 꽤 잦다. 데이터는 교환
  가능한 형식의 파일로 직렬화되고 이 파일이 반입 시스템에 제공된다. 우리는 파일 기반 내보내기를
  푸시 기반(push-based) 반입 패턴으로 본다. 이는 데이터 내보내기와 준비 작업이 원천 시스템 쪽에서
  이뤄지기 때문이다** (7장, p.246).[^reis2022]
- 직접 연결보다 나은 이유가 보안이다 — **파일 기반 반입은 직접 데이터베이스 연결 접근보다 몇
  가지 잠재적 이점을 갖는다. 보안상의 이유로 백엔드 시스템에 직접 접근을 허용하는 것이 바람직하지
  않은 경우가 많다. 파일 기반 반입으로는 내보내기 프로세스가 데이터 원천 쪽에서 돌아 원천 시스템
  엔지니어가 어떤 데이터가 내보내지고 데이터가 어떻게 전처리되는지에 대해 완전한 통제권을 갖는다**
  (7장, p.246).[^reis2022]
- 교환 수단 — **파일이 만들어지고 나면 다양한 방식으로 대상 시스템에 제공될 수 있다. 흔한 파일
  교환 방법은 오브젝트 저장·보안 파일 전송 프로토콜(SFTP)·전자 데이터 교환(EDI)·보안 복사(SCP)다**
  (7장, p.246).[^reis2022] 각각의 실물은
  [데이터를 반입하는 방법들](../concepts/data-ingestion-methods.md)에 있다.

## 반입 관점에서 본 ETL과 ELT

7장은 ETL·ELT 전체를 다시 정의하지 않고 **반입에 해당하는 두 글자 E와 L만** 떼어 낸다.

- **3장은 배치 워크로드에서 만나게 될 극히 흔한 반입·저장·변환 패턴인 ETL과 ELT를 소개했다.
  다음은 ETL과 ELT의 추출·적재 부분에 대한 간단한 정의다** (7장, p.246):[^reis2022]
  - **추출(Extract) — 원천 시스템에서 데이터를 가져오는 것을 뜻한다. 추출이 데이터를 당기는
    것을 함의하는 듯 보이지만 푸시 기반일 수도 있다. 추출은 메타데이터와 스키마 변경을 읽는
    것도 요구할 수 있다.**
  - **적재(Load) — 데이터가 추출되고 나면 저장 목적지에 적재되기 전에 변환되거나(ETL) 미래
    변환을 위해 그냥 저장으로 적재될 수 있다(ELT). 데이터를 적재할 때 적재하는 시스템의 유형,
    데이터의 스키마, 적재의 성능 영향에 유의해야 한다.**
- **추출이 반드시 풀이 아니다**라는 이 단서가 2장의 서술과 나란히 놓인다 — 2장은 **ETL의 추출
  (E) 부분은 우리가 풀 반입 모델을 다루고 있음을 분명히 한다**고 적었다 (2장, p.42).[^reis2022]
  충돌이 아니라 범위의 차이다: 2장은 전통적 ETL의 실제 관행을, 7장은 낱말의 논리적 범위를
  말한다. 실제로 같은 7장이 파일 기반 내보내기를 푸시로 분류한다 (7장, p.246).[^reis2022]
- ETL·ELT의 전문은 이 페이지가 아니라 웨어하우스 쪽에 있다 —
  [엔터프라이즈 데이터 웨어하우스](../concepts/enterprise-data-warehouse.md)의 ETL·ELT 절,
  그리고 같은 판단을 스트리밍 파이프라인 쪽에서 본
  [데이터 파이프라인 설계 고려사항](../concepts/kafka-data-pipeline-considerations.md).

## 삽입·갱신·배치 크기

- 문제의 형태 — **배치 지향 시스템은 사용자가 적은 수의 큰 연산 대신 많은 작은 배치 연산을
  수행하려 할 때 성능이 나쁜 경우가 많다. 예컨대 트랜잭션 데이터베이스에서는 한 번에 한 행을
  삽입하는 것이 흔하지만, 이는 많은 컬럼 데이터베이스에 나쁜 패턴이다. 그것이 작고 최적이지 않은
  파일을 많이 만들게 하고 시스템이 많은 수의 객체 생성(create object) 연산을 돌게 강제하기
  때문이다. 많은 작은 제자리 갱신 연산을 돌리는 것은 더 큰 문제인데, 갱신을 돌리기 위해
  데이터베이스가 기존 컬럼 파일을 각각 스캔하게 만들기 때문이다** (7장, p.247).[^reis2022]
  - 왜 컬럼 저장에서 특히 나쁜지는
    [컬럼 지향 저장](../concepts/column-oriented-storage.md)의 압축·정렬 절이 설명한다 — 컬럼
    파일은 통째로 정렬·압축돼 있어 한 행만 고치는 연산이 성립하지 않는다.
- 저자들의 처방은 도구의 한계를 아는 것이다 — **작업 중인 데이터베이스나 데이터 저장에 적절한
  갱신 패턴을 이해하라. 또한 어떤 기술은 높은 삽입률을 위해 목적에 맞게 지어졌다는 것을 이해하라.
  예컨대 Apache Druid와 Apache Pinot은 높은 삽입률을 감당할 수 있다. SingleStore는 OLAP과 OLTP
  특성을 결합한 하이브리드 워크로드를 관리할 수 있다. BigQuery는 높은 비율의 평범한 SQL 단일 행
  삽입에서는 성능이 나쁘지만 데이터가 그 스트림 버퍼를 통해 들어오면 극히 잘 수행한다. 도구의
  한계와 특성을 알라** (7장, p.247).[^reis2022]

## 데이터 마이그레이션

- 규모 — **새 데이터베이스나 환경으로 데이터를 마이그레이션하는 것은 보통 사소하지 않으며
  데이터를 대량으로 옮겨야 한다. 때로 이는 테라바이트 또는 훨씬 더 큰 데이터 크기를 옮기는
  것을 뜻하며, 흔히 특정 테이블의 마이그레이션과 전체 데이터베이스·시스템의 이동을 수반한다**
  (7장, p.247).[^reis2022]
- 빈도는 낮지만 함정은 스키마에 있다 — **데이터 마이그레이션은 데이터 엔지니어로서 정기적으로
  일어나는 일은 아니겠지만 익숙해져야 한다. 데이터 반입에서 자주 그렇듯 스키마 관리가 결정적
  고려사항이다. 한 데이터베이스 시스템에서 다른 시스템으로(가령 SQL Server에서 Snowflake로)
  데이터를 마이그레이션한다고 하자. 두 데이터베이스가 아무리 닮았어도 스키마를 다루는 방식에
  미묘한 차이가 거의 언제나 존재한다. 다행히 완전한 테이블 마이그레이션을 감행하기 전에 데이터
  표본의 반입을 테스트해 스키마 이슈를 찾는 것은 일반적으로 쉽다** (7장, p.247).[^reis2022]
- 대량으로 옮기고, 진짜 어려움은 데이터가 아니다 — **대부분의 데이터 시스템은 데이터가 개별
  행이나 이벤트가 아니라 대량으로 옮겨질 때 최고 성능을 낸다. 파일 또는 오브젝트 저장은 데이터
  전송을 위한 훌륭한 중간 단계인 경우가 많다. 또한 데이터베이스 마이그레이션의 가장 큰 도전 중
  하나는 데이터 자체의 이동이 아니라 데이터 파이프라인 연결을 옛 시스템에서 새 시스템으로 옮기는
  것이다** (7장, p.247).[^reis2022]
- **다양한 유형의 데이터 마이그레이션을 자동화하는 많은 도구가 있음을 알아 두라. 특히 크고 복잡한
  마이그레이션의 경우 수동으로 하거나 자체 마이그레이션 솔루션을 쓰기 전에 이 선택지들을 살펴볼
  것을 제안한다** (7장, p.247).[^reis2022]
