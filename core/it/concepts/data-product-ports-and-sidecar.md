## 하나의 질문

**데이터 프로덕트는 바깥과 어떤 표준 인터페이스로 만나며, 모든 프로덕트에 똑같이 걸리는 횡단
관심사는 어디서 실행되는가.**

[데이터 퀀텀](../concepts/data-quantum.md)이 무엇으로 이뤄지는가를 정하고 나면 남는 질문이
표면이다. 원전 9장이 그 표면을 네 인터페이스로 고정하고, 그 표면의 표준 부분을 구현하는
프로세스로 사이드카를 도입한다.

## 데이터 공유 상호작용의 모양

- 상호작용의 대다수가 데이터 공유다 — **데이터 프로덕트 상호작용의 다수는 데이터 공유에 관한
  것이다 — 서빙과 소비다** (9장, p.158).[^dehghani2022]
- 한 도메인 안에 여러 데이터 프로덕트가 있을 수 있고, 그 데이터 공유 인터페이스가 곧 도메인의
  분석 인터페이스가 된다 — **각 도메인은 여러 데이터 프로덕트를 가질 수 있다. 이 예에서 listener
  도메인은 두 데이터 프로덕트를 갖는다: subscriptions와 listener demographics다. 이 데이터
  프로덕트들과 그 데이터 공유 인터페이스 — 곧 출력 데이터 포트(output data ports) — 가 도메인이
  드러내는 분석 인터페이스가 된다** (9장, p.158, 그림 9-10).[^dehghani2022]
- 소비의 상대는 둘이다 — **데이터 프로덕트는 자기와 협력하는 운영 시스템에서, 또는 상류 데이터
  프로덕트에서 데이터를 소비할 수 있다. 이 예에서 podcast demographics 데이터 프로덕트는 협력
  운영 애플리케이션 podcast service에서 podcast events를, 그리고 상류 데이터 프로덕트인 listener
  demographics를 소비한다. 그 입력 인터페이스 — 곧 입력 데이터 포트(input data port) — 가 소스와의
  통합과 그로부터 데이터를 받는 것을 구현한다** (9장, pp.158–159).[^dehghani2022]
- 기저 기술은 고정되지 않는다 — **데이터 프로덕트의 입력 데이터 포트와 출력 데이터 포트를
  구현하는 기저 기술은 데이터 메시의 구현마다 다를 수 있지만, 다음의 공통 성질을 공유한다**
  (9장, p.159).[^dehghani2022]

## 입력 데이터 포트

- 정의 — **이것들은 데이터 프로덕트가 하나 또는 여러 소스에서 데이터를 소비하기 위해 구현하는
  내부(internal) 통합 기제다** (9장, p.159).[^dehghani2022] 앞 절의 인터페이스 세 갈래 중
  **데이터 프로덕트가 내부적으로 쓰는 사설 API**로 분류된 것이 이것이다 (9장, p.155,
  그림 9-9).[^dehghani2022]
- 두 가지 모양이 예로 든다 (9장, p.159):[^dehghani2022]
  - **협력하는 마이크로서비스에서 준실시간 도메인 이벤트를 소비하고 그것을 역사적 장기 보존
    분석 데이터로 변환**하는 것.
  - **상류 데이터 프로덕트에 시간 유발(time-triggered) 질의를 실행해 그 결과를 받아 집계
    데이터로 변환**하는 것.
- 입력 데이터의 도착이 곧 실행 신호다 — **입력 데이터의 도착이 변환 코드를 촉발한다(triggers)**
  (9장, p.155).[^dehghani2022] 구현 양식은 **상류 출력 데이터 API에 대한 구독으로 구현되어
  데이터가 가용해질 때 비동기적으로 받는** 것일 수도, **상류 소스에서 실행되어 데이터 프레임으로
  읽히는 질의**일 수도 있다 (9장, p.155).[^dehghani2022]

## 출력 데이터 포트

- 정의 — **이것들은 데이터 프로덕트의 기저 데이터를 공유하는 외부에서 주소 지정 가능한(externally
  addressable) API다. 각 데이터 프로덕트는 하나 또는 여러 출력 데이터 포트를 가질 수 있다**
  (9장, p.159).[^dehghani2022]
- 여기에 정책 실행이 얹힌다 — **데이터 메시는 모든 소비자가 데이터에 접근하기 전에 호출하는
  출력 데이터 포트용 표준화된 API를 두기를 제안한다. 이 API들은 소비자를 기저 데이터로 재유도하기
  전에 접근 통제 같은 정책을 실행한다** (9장, p.159).[^dehghani2022]
- 재유도의 대상은 다양하다 — **분석 데이터 공유의 경우 API는 접근 정책이 실행되고 나면 클라이언트를
  데이터의 기저 스토리지로 재유도하기를 택할 수 있다. 데이터 프로덕트의 구현에 따라 데이터 공유
  인터페이스는 블롭 스토리지(예: AWS S3의 Parquet 파일)나 이벤트 스트림(예: Kafka Topic), 또는
  테이블(예: BigQuery Table)이나 완전히 다른 무언가로 접근을 재유도할 수 있다** (9장,
  p.149).[^dehghani2022]
- 출력 API가 하는 일의 범위 — **출력 데이터 API는 자기 데이터에 대한 원격 질의를 받아 실행할 수
  있다. 예컨대 데이터를 담은 기저 테이블에 SQL 질의를 실행하는 인터페이스다. 출력 API는 여러
  형식으로 데이터를 공유한다. 예컨대 API가 블롭 스토리지에서 반구조화 파일을 읽거나 이벤트
  스트림을 구독한다** (9장, p.155).[^dehghani2022]

## 발견과 관측 가능성 API

- 세 인터페이스 중 나머지 하나 — **데이터 프로덕트는 발견되고·이해되고·디버깅되고·감사되는 데
  필요한 정보를 인터페이스 집합 — 동기적이거나 비동기적인 — 을 통해 제공한다** (9장,
  p.159).[^dehghani2022]
- 두 갈래가 나뉜다 (9장, pp.159–160):[^dehghani2022]
  - **발견 API는 데이터 프로덕트의 식별자, 그것을 소유한 팀, 데이터 의미론, 문서, 검색을 돕는
    태그 등을 공유한다.**
  - **관측 가능성 API는 데이터 공유에 관한 접근 로그·계보(lineage)·메트릭을 제공한다.**
- 이 API들은 표준화 대상이다 — 그림 9-9는 발견·관측 가능성 API와 출력 데이터 API를
  **표준화되고 도메인 불가지(standardized and domain agnostic)**로, 입력 데이터 API를 데이터
  프로덕트가 상류 데이터를 소비하는 데 쓰는 **사설 API**로 표시한다 (9장, p.156,
  그림 9-9).[^dehghani2022]

## 정책을 중앙 관문에서 지역 맥락으로

- 아키텍처 결정이 거버넌스의 효과를 좌우한다 — **정책을 설정·실행하고, 표준을 부과하고, 데이터
  프로덕트를 품질 기대에 부합하게 유지하기 위해 우리가 아키텍처를 어떻게 모델링하는가는 거버넌스
  기능이 얼마나 효과적일지에 직접적 영향을 준다** (9장, p.164).[^dehghani2022]
- 그 실행 자리로 퀀텀이 지목된다 — **데이터 퀀텀은 계산적 정책을 분산된 방식으로 내장하는 강력하고
  확장 가능한 구성물이다. 그것은 코드로서의 정책(policies as code)을 정의하고 실행할 수 있다**
  (9장, p.164).[^dehghani2022]
- 코드로 표현된 정책의 배급 방식 — **코드로 표현된 정책들은 — 메시 전반에 균일하게 — 각 데이터
  프로덕트에 가용해지고, 데이터 프로덕트는 그것을 올바른 시점에 평가하고 적용할 수 있다** (9장,
  p.164).[^dehghani2022]
- 왜 중앙 게이트웨이가 아닌지 — **데이터 메시 같은 분산 아키텍처에서 목표는 우발적인 경합 지점과
  병목을 제거하는 것이다. 이 이유로 정책을 중앙집중 게이트웨이(centralized gateway)와 대조적으로
  각 데이터 프로덕트의 국소화된 실행 맥락 안에서 독립적으로 설정하고 실행하는 것이 최선이다**
  (9장, p.166).[^dehghani2022] 이것이 사이드카가 존재하는 이유다.

## 사이드카

- 9장 도입의 정의 — **데이터 프로덕트 사이드카(sidecar)는 데이터 프로덕트의 실행 맥락을 공유하고
  정책 실행 같은 도메인 불가지의 횡단 관심사만을 책임지는 프로세스다. 정책 실행에 더해 사이드카
  프로세스는 발견 같은 데이터 프로덕트의 다른 표준화된 기능을 구현하도록 확장될 수 있다. 사이드카
  구현은 모든 데이터 프로덕트에 걸쳐 공통이다** (9장, p.146).[^dehghani2022]
- 본절의 정의는 배치 시점을 명시한다 — **사이드카는 각 데이터 프로덕트의 런타임 맥락을 장식하고
  메시 전반에 표준화될 것으로 기대되는 횡단 관심사를 실행하는 논리적 구성 요소다. 사이드카는 흔히
  데이터 프로덕트와 동적이고 느슨한 결합을 만들기 위해 별도 프로세스로 구현된다. 흔히 배치
  시점(deployment time)에 데이터 프로덕트 컨테이너로 주입된다** (9장, p.165).[^dehghani2022]
- 확장성이 설계 조건이다 — **시간이 지나면 사이드카가 하나 이상이 되거나 추가 교차 기능 능력으로
  사이드카를 확장할 수 있다. 그럼에도 그 설계는 시간이 지나면서 더 많은 정책을 포함할 수 있도록
  확장 가능해야 한다** (9장, p.165).[^dehghani2022]
- 하는 일 ① **정책 실행** — **데이터 프로덕트 사이드카의 책임 하나는 정책을 실행하는 것이다.
  데이터 메시 거버넌스는 데이터 모델링 같은 많은 차원에서 데이터 프로덕트의 다양성을 받아들이지만,
  특정 정책들이 모든 데이터 프로덕트에 일관되게 적용될 것을 요구한다** (9장,
  p.166).[^dehghani2022] 구체적으로 — **각 데이터 프로덕트에 동반하는 사이드카가 출력 포트가
  접근될 때 접근 통제 정책을 평가·적용하거나, 데이터 프로덕트가 새 데이터를 쓸 때 암호화를 적용할
  수 있다** (9장, p.166).[^dehghani2022]
- 하는 일 ② **표준 프로토콜과 인터페이스** — **거버넌스의 중요한 목표 하나는 데이터 프로덕트의
  상호운용 가능한 생태계를 만드는 것이다. 데이터 프로덕트의 데이터와 행위를 드러내는 인터페이스 —
  입력 데이터 포트·발견 포트·출력 데이터 포트·제어 포트 — 는 데이터 프로덕트 사이의 상호운용성에
  근본적이다** (9장, p.166).[^dehghani2022]
  - 사이드카가 그 표준을 구현하는 자리다 — **모든 인바운드·아웃바운드 통신의 흐름에 놓인 사이드카는
    표준화된 API를 제공할 수 있다. 예컨대 사이드카는 각 데이터 프로덕트에서 SLO 메트릭을 노출하는
    표준화된 API를 제공할 수 있다. 데이터 프로덕트의 구현은 이 API들의 표준 구현을 써서 자기
    고유한 내용을 노출한다** (9장, p.166).[^dehghani2022]
- 계열의 출처가 명시된다 — **이 전략은 운영 시스템 아키텍처에서 사이드카 패턴(sidecar pattern)으로
  구현되어 왔다. 사이드카는 애플리케이션 행위를 횡단 관심사로 증강하는 프로세스다. 예컨대 이 패턴은
  서비스 메시(service mesh)가 서비스의 인바운드·아웃바운드 호출에 라우팅·보안·회복력 등의 정책을
  구현하는 데 쓰인다** (9장, p.166).[^dehghani2022]
- 논리 구성 요소이지 물리 하나가 아니다 — **이 논리적 구성 요소 각각은 하나 또는 여럿의 물리
  구성 요소로 구현될 수 있다. 예컨대 사이드카는 서로 다른 종류의 정책 집행 에이전트를 위한 확장
  가능하고 논리적인 자리표시자다** (9장, p.165).[^dehghani2022]
- **같은 낱말이 가리키는 다른 것과 갈라 둔다.** 위 계열 서술이 말하는 그 서비스 메시의
  사이드카는 이 KB에 따로 페이지가 있다 —
  [API 게이트웨이와 서비스 메시](../concepts/api-gateway-and-service-mesh.md)다. **패턴은 같고
  무엇을 넣는지가 다르다.** 그쪽 사이드카에 들어가는 것은 상호 TLS·상관 ID·서비스 디스커버리
  같은 **마이크로서비스 사이 통신의 공통 관심사**이고, 이 페이지의 사이드카에 들어가는 것은
  **데이터 프로덕트의 거버넌스 정책과 표준 API**다. 그래서 위에 적힌 대로 이쪽은 **정책 집행
  에이전트의 자리표시자**다.
  - **배치 근거도 같은 모양이다** — 그쪽 사이드카가 프록시를 같은 기계에 붙이는 이유는 원격
    네트워크 호출을 줄이려는 것이고, 이쪽 사이드카가 실행 맥락을 공유하는 이유는 정책을 중앙
    관문 대신 각 프로덕트의 자리에서 실행하려는 것이다. **둘 다 중앙 집중을 피하려고 실행
    지점을 분산한다.**
  - **셋째 용법이 하나 더 있다** — 컨테이너 하나에 보조 컨테이너를 붙이는 배치 패턴을 가리키는
    쓰임이고, 위 둘은 그 배치 위에서 도는 경우가 많다. 이 페이지는 그 낱말을 쓰지 않는다.

## 계산 컨테이너

- 사이드카와 함께 도입되는 짝 — **데이터 프로덕트 계산 컨테이너(data product computational
  container)는 플랫폼이 실행 정책을 데이터 프로덕트와 함께 하나의 배포 가능 단위로 캡슐화하는
  방법이다. 간결함을 위해 나는 이것을 때때로 데이터 컨테이너(data container)라 부른다** (9장,
  p.164).[^dehghani2022]
- 무엇이 묶이는가 — **자율적으로 사용 가능한 데이터 프로덕트를 만들기 위해 꽤 많은 구조 구성
  요소가 함께 묶인다: 사이드카, 정책 설정, 데이터 프로덕트 변환 코드, 데이터 프로덕트 데이터,
  그 데이터 공유 인터페이스 등이다** (9장, p.166).[^dehghani2022]
- 이것이 연합 거버넌스를 성립시키는 요소로 규정된다 — **연합 거버넌스를 효과적으로 만드는 또 다른
  요소는 아키텍처 퀀텀으로서 데이터 프로덕트의 모든 구조 요소를 감싸는 컨테이너다** (9장,
  p.167).[^dehghani2022] 그 구현의 공급자는 플랫폼이다 — **데이터 프로덕트 경험 플레인이 모든
  데이터 프로덕트에 대해 컨테이너의 구현을 일관되게 제공한다** (9장, p.167).[^dehghani2022]

## 제어 포트

- 넷째 인터페이스이고, 거버넌스가 도입한다 — **계산적 거버넌스는 모든 데이터 프로덕트에 새
  인터페이스, 제어 포트(control port)를 도입한다. 제어 포트는 (1) 각 데이터 프로덕트에 대해
  정책을 설정하고, (2) 거버넌스 요구를 충족하기 위해 아주 높은 권한을 가진 소수의 연산을 실행하는
  API 집합을 노출한다** (9장, p.167).[^dehghani2022]
- **① 정책 설정** — 정책의 저작 주체가 둘로 갈린다 — **이 정책들은 데이터 프로덕트 자신에 의해
  지역적으로 저작·통제될 수도, 메시 경험 플레인에 의해 중앙에서 저작·통제될 수도 있다** (9장,
  p.167).[^dehghani2022]
  - 어느 쪽이 어느 정책에 맞는지도 예로 갈라 둔다 — **데이터 익명화에 관한 정책은 데이터
    프로덕트의 PII 속성을 선언함으로써 지역적으로 저작되는 것이 가장 좋다. 도메인 데이터 프로덕트
    소유자가 데이터 프로덕트에 PII가 있는지 알고 설정하는 데 가장 관련 있는 정보를 갖고 있다.
    대조적으로 역할의 정의와 그 접근 통제는 흔히 중앙에서 저작되고 각 데이터 프로덕트에서
    지역적으로 실행된다** (9장, p.167).[^dehghani2022]
  - 둘은 배타적이지 않다 — **두 형태의 정책 저작 — 지역 설정과 중앙 설정 — 은 단일 데이터
    프로덕트에 대해 공존할 수 있다** (9장, p.167).[^dehghani2022]
  - 설계 조건은 확장성이다 — **제어 포트의 설계는 메시에 새 타입의 정책이 도입될 때 그것을
    지원하도록 확장 가능해야 한다** (9장, p.167).[^dehghani2022]
- **② 특권 연산** — **거버넌스 기능은 모든 데이터 프로덕트에 대해 아주 높은 권한을 가진 소수의
  연산을 실행할 방법이 필요하다. 예컨대 GDPR의 잊힐 권리(right to be forgotten) — 어떤 조직이
  수집한 자기 데이터 전부를 지울 개인의 권리 — 를 실행하는 연산이다** (9장,
  p.167).[^dehghani2022]
  - 그것이 필요한 이유는 전역 전파다 — **전역 거버넌스 기능은 이것을 메시의 모든 데이터 프로덕트에
    알릴 방법이 필요하다. 제어 포트는 한 개인에 대한 잊힐 권리를 구현하는 특정한 고특권 인터페이스를
    노출할 수 있다** (9장, p.167).[^dehghani2022]
- 표준화의 주체 — **플랫폼이 모든 데이터 프로덕트에 대해 제어 포트를 표준화한다** (9장,
  p.167).[^dehghani2022]
- 성숙도는 낮게 매겨져 있다 — 표 9-1은 제어 포트를 **집필 시점 실험적(experimental)**으로
  분류한다 (9장, p.169).[^dehghani2022]
