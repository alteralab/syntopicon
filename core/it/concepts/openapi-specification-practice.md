하나의 질문: **API의 모양을 적은 문서 하나로 실무에서 무엇을 할 수 있는가.**

## 버전 조건

> **버전 조건**: 2022년 저술 시점. 아래 도구 이름(OpenAPI Generator ·
> swagger-request-validator · openapi-examples-validator · openapi-diff · openapi2proto ·
> grpc-gateway)과 **OpenAPI 명세의 판 2와 판 3이 함께 쓰이던 상황**이 그 시점의 것이다. 명세를
> 무엇에 쓰는가라는 분류 자체는 도구와 무관하다.

## 왜 명세가 필요해졌는가

- **순서가 먼저 있다** — 저자들은 **API의 설계가 API 플랫폼의 성공에 근본적**이고, 그다음 고려가
  **API를 소비하는 개발자와 그 API를 나누는 일**이라고 적는다 (1장 §"Specifying REST APIs Using
  OpenAPI", p.12).[^gough2022]
- **API 마켓플레이스가 그 나눔의 자리다** — **소비자가 쓸 수 있는 API의 공개 또는 비공개 목록을
  제공하고, 개발자가 문서를 훑어보고 브라우저에서 빠르게 API를 시험해 그 동작과 기능을 탐색할
  수 있다** (1장, p.12).[^gough2022]
- **저자들이 REST API의 성공을 두 가지로 돌린다** — **기술 지형**과 **클라이언트와 서버 양쪽의
  낮은 진입 장벽**이다 (1장, p.12).[^gough2022]
- **API의 수가 늘자 API의 모양(shape)과 구조를 소비자와 나눌 기제가 빠르게 필요해졌다.** 그래서
  **API 업계의 선도자들이 OpenAPI 이니셔티브(OpenAPI Initiative)를 결성해 OpenAPI 명세(OpenAPI
  Specification, OAS)를 구성했다** (1장, p.12).[^gough2022]
- **스웨거(Swagger)가 OpenAPI 명세의 원래 참조 구현이었으나 대부분의 도구가 이제 OpenAPI를 쓰는
  쪽으로 수렴했다** (1장, p.12).[^gough2022]
  - 버전 조건: 2022년 저술 시점. 도구 생태계의 수렴 상태가 그 시점의 관찰이다.

## 명세가 담는 것

- **OAS는 API의 JSON 또는 YAML 기반 표현**이고 담는 것이 셋이다 — **구조**, **교환되는 도메인
  객체**, 그리고 **API의 보안 요건**이다 (1장, p.12).[^gough2022]
- **구조에 더해 메타데이터도 나른다** — **법적 요건이나 라이선스 요건을 포함한 API의 메타데이터**,
  그리고 **API를 소비하는 개발자에게 유용한 문서와 예제**다 (1장, p.12).[^gough2022]
- **저자들의 위상 판정** — **OAS는 현대 REST API를 둘러싼 중요한 개념이고, 많은 도구와 제품이 그
  쓰임을 중심으로 지어졌다** (1장, pp.12–13).[^gough2022]
- **명세가 공유되고 나서야 그 힘이 드러나기 시작한다**고 저자들이 적는다. 아래 넷이 그 힘이
  드러나는 자리다 (1장 §"Practical Application of OpenAPI Specifications",
  p.13).[^gough2022]
  - 사례 연구에서는 **CFP 팀이 소비자인 상황에서 OAS를 나누면 그 팀이 API의 구조를 이해할 수
    있게 된다**고 적는다 (1장, p.13).[^gough2022]

## 코드 생성

- **저자들이 꼽는 아마도 가장 유용한 기능 하나가 API를 소비하는 클라이언트 쪽 코드의 생성**이다
  (1장 §"Code Generation", p.13).[^gough2022]
- **무엇이 있어서 생성이 가능한가** — 명세가 **서버와 보안과 API 구조 자체의 온전한 상세**를 담기
  때문에, 그 정보로 **API를 표현하고 호출하는 모델 객체와 서비스 객체의 묶음을 생성할 수 있다**
  (1장, p.13).[^gough2022]
- **도구는 넓은 범위의 언어와 툴체인을 지원한다** — 저자들이 드는 것이 **OpenAPI Generator
  프로젝트**이고, 예로 **자바에서 스프링이나 JAX-RS를 고를 수 있고 타입스크립트에서는
  타입스크립트와 좋아하는 프레임워크의 조합을 고를 수 있다**고 적는다 (1장,
  p.13).[^gough2022]
  - 버전 조건: 2022년 저술 시점. 생성기 이름과 지원 툴체인 목록이 그 시점의 것이다.
- **클라이언트만이 아니다** — **OAS에서 API 구현 스텁(implementation stub)을 생성하는 것도
  가능하다** (1장, p.13).[^gough2022]

## 명세가 먼저인가 코드가 먼저인가

- **코드 생성이 곧바로 물음 하나를 세운다** — **무엇이 먼저 와야 하는가, 명세인가 서버 쪽
  코드인가** (1장, p.13).[^gough2022]
- **저자들이 앞서 그 방향의 이름을 규정해 두었다** — **API 우선(API-First) 설계는 개발자와
  아키텍트가 자기 서비스의 기능을 고려하고 API를 소비자 중심(consumer-centric)으로 설계하는
  접근**이다. **그 API 소비자는 모바일 애플리케이션일 수도, 다른 서비스일 수도, 외부 고객일
  수도 있다** (서론, p.xxiv).[^gough2022]
- **이 KB가 이미 갖고 있는 규정과 축이 다르다.** [API 수명 주기](../concepts/api-lifecycle.md)의
  API 우선 절은 같은 이름을 **명세를 먼저 만들고 구현이 뒤따른다**는 **순서**로 규정한다. 이 책은
  같은 이름을 **누구의 관점에서 설계하는가**로 규정한다. **둘은 겨루지 않는다** — 순서의 규정과
  관점의 규정이고, 이 책의 서술은 순서 쪽을 물음으로 열어 둔 채 관점 쪽을 단정한다.
- **답 대신 저자들이 가리키는 것은 2장**이다. 거기서 **테스트와 API 구축에 행동 주도(behavior-
  driven) 접근을 제시하는 계약 테스트**를 논한다고 예고한다 (1장, p.13).[^gough2022]
  그 패턴의 정본은 [소비자 주도 계약](../concepts/consumer-driven-contracts.md)이다.

## 명세는 모양만 전한다

- **저자들이 OpenAPI 명세의 도전을 한 문장으로 적는다** — **명세만으로는 API의 모양만 전달한다**
  (1장, p.13).[^gough2022]
- **더 정확히는 이렇다** — **OpenAPI 명세는 여러 조건 아래에서의 API의 의미론(semantics, 곧 기대
  동작)을 온전히 모델링하지 않는다** (1장, p.13).[^gough2022]
- **그래서 따라오는 요구** — **외부 사용자에게 API를 내놓을 것이라면 동작의 범위가 모델링되고
  테스트되어야 하고, 그래야 나중에 API를 급격히 바꿔야 하는 일을 피할 수 있다** (1장,
  p.13).[^gough2022]
- **같은 자리에서 설계 원칙 하나가 따라 나온다** — **API는 소비자의 관점에서 설계되어야 하고,
  결합을 줄이기 위해 밑에 깔린 표현을 추상화할 필요를 고려해야 한다. API 호환성을 깨지 않고 뒤의
  컴포넌트를 자유롭게 리팩터링할 수 있어야 하며, 그러지 못하면 API 추상화가 가치를 잃는다**
  (1장, p.13).[^gough2022]

## 검증 — 명세를 관문에 세운다

- **OpenAPI 명세는 교환의 내용을 검증해 요청과 응답이 명세의 기대와 맞는지 확인하는 데도
  쓸모가 있다** (1장 §"OpenAPI Validation", pp.13–14).[^gough2022]
- **저자들이 독자의 의문을 먼저 적는다** — **처음에는 이것이 어디에 쓸모가 있을지 분명하지 않을
  수 있다. 코드가 생성됐다면 교환은 언제나 맞지 않겠는가** (1장, pp.13–14).[^gough2022]
- **실무 적용 하나는 API와 API 인프라를 지키는 일이다** (1장, p.14):[^gough2022]
  - **많은 조직에서 존(zonal) 아키텍처가 흔하고, 인바운드 트래픽으로부터 네트워크를 가리는
    DMZ(demilitarized zone)라는 개념이 있다.**
  - **유용한 기능은 DMZ에서 메시지를 심문하고 명세와 맞지 않으면 그 트래픽을 끊는 것이다.**
  - 저자들이 보안의 상세는 6장으로 미룬다고 적는다.
- **도구의 실물 하나** — **아틀라시안이 swagger-request-validator라는 도구를 오픈소스로
  냈고 JSON REST 콘텐츠를 검증할 수 있다** (1장, p.14).[^gough2022]
  - 버전 조건: 2022년 저술 시점. 도구 이름과 그 기능 범위가 그 시점의 것이다.
  - **그 프로젝트에는 여러 모킹·테스트 프레임워크와 통합되는 어댑터도 있어서, 테스트의 일부로
    API 명세가 지켜지는지 보장하는 데 도움을 준다** (1장, p.14).[^gough2022]
  - **도구에 `OpenApiInteractionValidator`가 있고 교환에 대한 `ValidationReport`를 만드는 데
    쓰인다** (1장, p.14).[^gough2022]
  - **검증기를 명세의 위치로 만들 때 `basePathOverride`를 함께 줄 수 있다** — **경로를 바꾸는
    인프라(게이트웨이나 프록시) 뒤에 API를 배포한다면 필요할 수 있다** (1장,
    p.14).[^gough2022]
  - **검증 보고서는 검증이 실행되는 시점의 요청과 응답을 분석해 생성된다** (1장,
    p.14).[^gough2022]

## 예제와 모킹

- **OAS는 명세의 경로마다 예제 응답을 줄 수 있다** (1장 §"Examples and Mocking",
  p.14).[^gough2022]
- **쓰임이 셋이다** (1장, p.14):[^gough2022]
  - **문서화** — **예제는 개발자가 기대되는 API 동작을 이해하도록 돕는 문서로서 유용하다.**
  - **모의 응답** — **일부 제품은 예제를 써서 사용자가 API를 질의하면 모의 서비스가 예제 응답을
    돌려주게 하기 시작했다.** 저자들은 이것이 **개발자 포털처럼 개발자가 문서를 탐색하고 API를
    호출해 보게 하는 기능에서 정말 유용할 수 있다**고 적는다.
  - **짓기 전에 나누기** — **서비스를 짓기로 확약하기 전에 프로듀서와 소비자 사이에 아이디어를
    나눌 수 있다.** 저자들의 판정이 붙는다: **API를 "시험해 보는" 것이 명세가 요건을 충족할지를
    검토해 보려는 것보다 흔히 더 가치 있다.**
- **예제가 들여오는 문제 하나** — **명세의 이 부분은 본질적으로 문자열이다.** XML이나 JSON 같은
  것을 모델링해야 하기 때문이다 (1장, p.15).[^gough2022]
  - **그래서 따로 검증돼야 한다** — **openapi-examples-validator가 예제가 API의 해당 요청/응답
    컴포넌트의 OAS와 맞는지 검증한다** (1장, p.15).[^gough2022]
    - 버전 조건: 2022년 저술 시점. 도구 이름이 그 시점의 것이다.

## 변경 탐지

- **OpenAPI 명세는 API의 변경을 탐지하는 데도 도움이 되고, 그것이 데브옵스 파이프라인의 일부로
  엄청나게 유용할 수 있다** (1장 §"Detecting Changes", p.15).[^gough2022]
- **명세를 맞대는 도구가 여럿이고 저자들이 고른 것이 OpenAPITools의 openapi-diff**다 (1장
  §"OpenAPI Specification and Versioning", p.16).[^gough2022]
- **저자들이 참석자 API 명세로 두 방향을 실제로 돌려 보인다** (1장,
  p.17):[^gough2022]
  - **깨는 쪽** — **`givenName` 필드의 이름을 `firstName`으로 바꾼다. 소비자가 `firstName`이
    아니라 `givenName`을 파싱할 것을 기대하고 있으므로 이것은 깨는 변경이다.** 도구의 출력이
    **호환성 깨짐(Broken compatibility)**과 **빠진 속성**을 짚고 결론을 낸다.

    > API changes broke backward compatibility

  - **안 깨는 쪽** — **`/attendees`의 반환 타입에 `age`라는 새 속성을 더한다. 새 필드를 더하는
    것은 기존 동작을 깨지 않으므로 호환성을 깨지 않는다.** 도구가 **후진 호환(Backward
    compatible)**으로 판정한다.

    > API changes are backward compatible

- **저자들의 권고** — **어떤 변경이 호환되고 어떤 것이 아닌지 직접 시험해 볼 값이 있다. 이런
  종류의 도구를 API 파이프라인의 일부로 들이면 소비자에게 예상 못 한 비호환 변경이 가는 것을
  피하는 데 도움이 된다** (1장, p.17).[^gough2022]
- **한 문장 판정** — **OpenAPI 명세는 API 프로그램의 중요한 부분이고, 도구와 버저닝과 수명 주기와
  결합되면 값을 매길 수 없다** (1장, p.17).[^gough2022]
- **단서가 붙는다** — **도구는 흔히 OpenAPI 판에 특정적이므로, 다루고 있는 명세를 그 도구가
  지원하는지 확인하는 것이 중요하다.** 저자들이 실제로 겪은 것을 적는다: **더 이른 판의 명세로
  같은 diff 도구를 돌렸더니 깨는 변경이 하나도 탐지되지 않았다** (1장, p.18).[^gough2022]
  - 버전 조건: 2022년 저술 시점. **판 2와 판 3이 함께 쓰이던 상황**의 관찰이다.

## 명세끼리 변환할 수 있는가

- **1장의 마지막 물음이 이것이다** — **모든 형식을 다 제공할 수 있는가.** 저자들의 답은
  **그렇다**이다. **RESTful 표현과 gRPC 서비스와 GraphQL 스키마로의 연결을 함께 가진 API를
  지원할 수 있다.** 다만 곧바로 단서가 붙는다 — **쉽지 않을 것이고, 옳은 일이 아닐 수도 있다**
  (1장 §"Multiple Specifications", p.22).[^gough2022]
- **출발은 닮음이다** — **참석자의 `.proto` 파일과 OpenAPI 명세는 그리 달라 보이지 않는다. 같은
  필드를 담고 둘 다 데이터 타입을 갖는다** (1장 §"Does the Golden Specification Exist?",
  p.22).[^gough2022]
- **그래서 변환 도구를 시험한다** — **openapi2proto 도구로 OAS에서 `.proto` 파일을 생성할 수
  있고, 기본으로 필드가 알파벳순으로 정렬된 `.proto` 파일을 출력한다** (1장,
  p.22).[^gough2022]
  - 버전 조건: 2022년 저술 시점. 도구 이름과 기본 동작이 그 시점의 것이다.
- **함정이 거기 있다** — **OAS에 후진 호환되는 새 필드를 더하는 순간 모든 필드의 ID가 바뀌어
  후진 호환성이 깨진다** (1장, p.22).[^gough2022]
  - **저자들이 실물로 보인다** — **`a_new_field`를 더하면 알파벳순으로 맨 앞에 놓이고, 그것이
    이진 형식을 바꿔 기존 서비스를 깬다** (1장, p.23).[^gough2022]
  - **왜 필드 번호가 바뀌면 깨지는가**의 규범 쪽 정본은
    [프로토콜 버퍼와 필드 태그](../concepts/protocol-buffers-encoding.md)이다.
- **다른 도구들의 단서** — **명세 변환 문제를 푸는 다른 도구도 있으나, 일부 도구는 OpenAPI 명세
  판 2만 지원한다는 점을 적어 둘 만하다.** 저자들이 그 이유를 덧붙인다 — **OpenAPI를 둘러싸고
  지어진 도구들이 판 2에서 판 3으로 옮겨 가는 데 걸린 시간 때문에 많은 제품이 OAS의 두 판을 모두
  지원해야 했다** (1장, p.23).[^gough2022]
  - 버전 조건: 2022년 저술 시점.
- **다른 길 하나** — **grpc-gateway는 gRPC 서비스 앞에 REST 파사드를 제공하는 리버스 프록시를
  생성한다. 그 리버스 프록시는 `.proto` 파일에 대해 빌드 시점에 생성되고, openapi2proto와
  비슷하게 REST로의 최선 노력(best-effort) 매핑을 만든다** (1장, p.23).[^gough2022]
  - **`.proto` 파일 안에 확장을 공급해 RPC 메서드를 OAS의 보기 좋은 표현으로 매핑할 수도 있다**
    (1장, p.23).[^gough2022]
  - **대가가 붙는다** — **grpc-gateway는 여러 명령과 설정을 수반하고, 그것은 고(Go) 언어나 그
    빌드 환경으로 일하는 개발자에게만 익숙할 것이다** (1장, p.23).[^gough2022]

## 결합된 명세가 지는 것

- **저자들이 한 걸음 물러서서 무엇을 하려는 것인지 묻는다** (1장 §"Challenges of Combined
  Specifications", p.23):[^gough2022]
  - **OpenAPI에서 변환할 때 우리는 사실상 RESTful 표현을 gRPC 호출의 묶음으로 변환하려는
    것이다. 확장된 하이퍼미디어 도메인 모델을 더 낮은 수준의 함수 대 함수 호출로 변환하려는
    것이다.**
  - **이것은 RPC와 API의 차이를 뒤섞는 것일 수 있고, 호환성과 씨름하는 결과를 낳을 가능성이
    크다.**
  - **반대 방향도 같다** — **gRPC를 OpenAPI로 변환할 때의 목적은 gRPC를 가져다 REST API처럼
    보이게 하려는 것이고, 서비스를 진화시킬 때 어려운 문제의 연쇄를 만들 가능성이 크다** (1장,
    p.24).[^gough2022]
- **버저닝이 그 위에 얹힌다** — **명세가 결합되거나 서로에게서 생성되면 버저닝이 도전이 된다.
  gRPC와 OpenAPI 명세가 각자의 호환성 요건을 어떻게 유지하는지를 유념해야 한다** (1장,
  p.24).[^gough2022]
- **저자들이 요구하는 것은 능동적 결정이다** — **REST 도메인을 RPC 도메인에 결합하는 것이 말이
  되고 전체적으로 가치를 더하는지에 대해 능동적 결정이 내려져야 한다** (1장,
  p.24).[^gough2022]
- **저자들 자신의 결론** — **남북에서 동서용 RPC를 생성하기보다 더 말이 되는 것은,
  마이크로서비스 기반 아키텍처의 통신(RPC)을 REST 표현과 독립적으로 신중히 설계해 두 API가
  자유롭게 진화하게 하는 것이다.** 그리고 **그것이 회의 사례 연구에서 고른 선택이고 프로젝트에서
  ADR로 기록될 것**이라고 적는다 (1장, p.24).[^gough2022]
- **장의 요약이 그 태도를 한 줄로 되풀이한다** — **OpenAPI 기능을 능동적으로 골라야 하고, 어떤
  도구나 생성 기능을 프로젝트에 적용할지 선택해야 한다** (1장 §"Summary",
  p.24).[^gough2022]

## 명세와 계약은 다른 물음이다

**위 [명세는 모양만 전한다](#명세는-모양만-전한다)가 남긴 공백을 같은 책의 2장이 이어받는다.**
거기서 저자들이 명세와 계약을 갈라 놓는다.

- **명세 준수를 먼저 요구한다** — API는 명세를 가져야 하고 **API 응답이 내가 깔아 둔 명세에
  부합하는 것이 중요하다**고 적으며 위 절을 가리킨다 (2장 §"Why Contract Testing Is Often
  Preferable", p.34).[^gough2022]
- **그러나 계약 테스트는 명세 적합과 같은 것이 아니라고 못 박는다** (2장, p.35):[^gough2022]

  > It is important to note that contract testing is not the same as saying that an API
  > conforms to a schema. A system is either compatible with a schema (like OpenAPI Spec) or
  > it is not; a contract is about a defined interaction between parties and provides
  > examples.

  - **곧 명세는 참·거짓의 적합 판정을 주고, 계약은 두 편 사이의 정의된 상호작용과 예를 준다.**
    위 절이 적은 한계(**명세가 조건별 의미론을 온전히 모델링하지 않는다**)를 메우는 것이
    계약이라는 배치이고, **이 책이 그 연결을 스스로 적는다.** 계약 쪽 전문은
    [소비자 주도 계약](../concepts/consumer-driven-contracts.md)에 있다.
- **명세를 계약의 입력으로 쓰는 길이 있으나 도구가 서 있지 않다** — 계약을 들이는 비용을 적은
  자리에서 **OpenAPI 명세를 바탕으로 계약을 만들어 주는 도구를 찾아볼 만하다**고 적되, 각주에
  **저술 시점에 몇몇 프로젝트가 있으나 활발히 유지되는 것이 없어 어느 것도 추천하기
  어렵다**고 단다 (2장 §"Contracts methodology overview", p.39 · 각주 9).[^gough2022]
  - 버전 조건: 2022년 저술 시점의 관찰이다. 위 [버전 조건](#버전-조건)이 이 페이지 전체에
    걸리는 것과 같은 조건이다.

## 이 KB의 다른 OpenAPI 서술과 나란히

- **이 페이지가 들어오기 전 이 KB의 OpenAPI 서술은 둘이었고 둘 다 다른 것을 묻는다.**
  - [REST API 구현 결정](../concepts/rest-api-implementation-decisions.md)이 옮긴 2025년 스타일
    비교서는 **명세 문서 안에 무엇이 적히는가**(`openapi`·`info`·`tags`·`paths`·`parameters`·
    `responses` 필드)와 **명세를 만드는 세 접근**(자동 생성·수동·반수동)을 갖는다.
  - [웹 서비스와 REST](../concepts/web-services-and-rest.md)가 옮긴 2021년 마이크로서비스 실무서는
    같은 명세를 **문서화 수단**으로 놓는다.
  - **이 책이 더하는 것은 명세를 공유한 다음에 무엇을 하는가**다. 앞의 둘 가운데 어느 것도 코드
    생성과 관문 검증과 모의 응답과 변경 탐지를 한 묶음으로 세지 않았다.
- **모순으로 세운 쌍은 없다.** 맞대 본 자리를 적는다.
  - **이 책의 "명세는 모양만 전한다" 대 세 접근의 완전성·일치 맞바꿈** — 겨루지 않고 **층이
    다르다.** 세 접근은 **명세가 구현과 어긋날 수 있다**는 문제이고, 이 책의 한계는 **명세가
    구현과 정확히 맞아도 조건별 동작은 담기지 않는다**는 문제다. **어긋남을 없애도 남는 공백**이
    이 책이 짚는 것이다. #hypothesis
  - **이 책의 코드 생성 권장 대 세 접근의 "자동 생성은 불완전하다"** — 겨루지 않는다. 방향이
    반대다. 이 책이 말하는 생성은 **명세에서 코드를 낳는 것**이고, 세 접근의 자동 생성은
    **코드에서 명세를 낳는 것**이다. 같은 낱말이 두 방향을 가리킨다.
