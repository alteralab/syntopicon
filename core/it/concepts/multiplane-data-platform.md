## 하나의 질문

**셀프서브 데이터 플랫폼 원칙을 아키텍처로 옮기면 플랫폼은 어떤 구조가 되며, 그 구조의 조각은
무엇을 기준으로 갈리는가.**

[셀프서브 데이터 플랫폼 원칙](../concepts/self-serve-data-platform-principle.md)이 **왜·무엇을**
담당하는 4장이라면, 이 페이지는 그 원칙의 **구조**를 정하는 원전 9장의 한 절과 10장 전부다.
플랫폼의 인터페이스를 무엇으로 정하는지는
[데이터 플랫폼 사용자 여정](../concepts/data-platform-user-journeys.md)이 받는다.

## 단일 통합 플랫폼이 아니라 느슨한 서비스 조합

- 설계의 갈림이 둘로 제시된다 — **그런 플랫폼을 설계하는 데는 두 가지 일반적 접근이 있다.
  하나는 단일하고 긴밀히 통합된 플랫폼 — 흔히 주 벤더에게서 사는 — 을 채택하는 것이고, 다른
  하나는 표준적이고 열린 인터페이스를 노출하는 느슨히 통합된 서비스 집합을 쓰는 것이다. 후자는
  흔히 여러 벤더로부터의 짓기와 사기의 조합으로 구현된다** (9장, p.160).[^dehghani2022]
- 데이터 메시가 고르는 쪽이 명시된다 — **데이터 메시 플랫폼 설계는 둘째 진영에 든다. 복잡한
  플랫폼을 그 능력들로 쪼개고, API를 통해 서빙하고, 협력하는 다른 능력과 통합할 열린
  인터페이스를 두는 것을 선호한다** (9장, p.160).[^dehghani2022]
- 단일 플랫폼의 매력과 한계를 나란히 적는다 — **단일 플랫폼이라는 발상은 매력적이지만 — 곧
  벤더 하나만 상대하면 되므로 더 단순하다 — 규모에 한계가 있다. 예컨대 단일 플랫폼은 서비스와
  데이터가 어디에 호스팅될 수 있는지를 제한하고 벤더에 대한 락인(lock-in)을 만든다** (9장,
  p.160).[^dehghani2022]
- 그럼에도 여러 플랫폼이 생기는 것은 필연으로 진단된다 — **그럼에도 시간이 지나면 조직의
  복잡성이 여러 플랫폼의 채택으로 이어진다. 그런데 이 플랫폼들은 각자 자기가 데이터나
  애플리케이션의 유일한 통제자라고 상상하기 때문에 서로 잘 어울리지 못한다. 이는 임기응변적이고
  비싼 통합, 그리고 플랫폼을 가로지르는 값비싼 데이터 복사로 이어진다** (9장,
  p.160).[^dehghani2022]
- 그래서 데이터 메시는 그 복잡성을 전제로 삼는다 — **데이터 메시는 기본적으로 조직의 복잡성이
  다중 플랫폼·다중 호스팅 환경으로 이어진다는 사실을 받아들인다. 이 모델을 지원하기 위해 데이터
  메시는 표준 인터페이스로 서비스를 조합하는 플랫폼 아키텍처 접근을 제시한다. 그래서 데이터가
  서로 다른 서비스와 호스팅 환경에 걸쳐 공유될 수 있다** (9장, p.160).[^dehghani2022]
- API 주도를 고르는 이유는 진화 가능성이다 — **API 주도 접근은 커지는 복잡성 앞에서 유연성을
  허용한다. 시간이 지나면서 데이터 프로덕트 관리의 경험을 새 능력으로 확장하거나, 메시 사용자의
  중단 없이 데이터 프로덕트 관리를 다른 인프라로 옮기는 것을 가능하게 한다** (9장,
  p.160).[^dehghani2022]

## 플레인이라는 낱말 — layer를 피한 이유

- 정의 — **데이터 메시 플랫폼 능력의 논리 설계에서 나는 플레인(plane)이라는 개념을 쓴다.
  플레인은 서로 보완적인 목표와, 종단 간 결과를 만족시키는 데서의 높은 기능적 응집을 갖는
  능력들의 논리적 집합이다** (9장, p.161).[^dehghani2022]
- 표면이라는 은유가 붙는다 — **각 플레인은 표면(surface)처럼 인프라 복잡성을 추상하고, 자기가
  구현하는 능력들에 대한 인터페이스(API) 집합을 제공한다. 플레인 능력은 그 인터페이스를 통해
  접근된다** (9장, p.161).[^dehghani2022]
- **낱말 선택이 의도적 기각이다** — **나는 플랫폼 플레인에 대해 계층(layer)이라는 용어를 쓰는
  것을 의도적으로 피했다. 계층은 흔히 엄격한 계층적 접근으로, 정보와 통제의 흐름이 한 계층에서
  다음 계층으로 옮겨 가는 것으로 상상된다. 예컨대 계층형 애플리케이션 아키텍처 개념은 데이터베이스
  접근을 가장 낮은 계층에 감추고 상위 계층의 매핑된 객체를 통해서만 데이터에 접근하게 한다**
  (9장, p.161).[^dehghani2022]
  - 플레인에서는 그 제약이 없다 — **플랫폼 플레인의 경우 메시 사용자는 자기 필요에 따라 더 높은
    추상 플레인 서비스를 쓸지 더 낮은 것을 쓸지 선택할 수 있다** (9장, p.161).[^dehghani2022]
- 그래서 플레인 사이 관계는 느슨한 의존이다 — **데이터 프로덕트 개발자 같은 최종 사용자는 플랫폼의
  여러 플레인과 직접 상호작용할 수 있다. 플레인 사이에는 느슨한 의존이 있지만 계층화나 계층적
  접근 모델이라는 강한 관념은 없다. 플레인은 강한 계층화 제약 없이 관심사의 분리(separation of
  concerns)를 받아들인다** (9장, p.161).[^dehghani2022]
- 10장이 그 비강제를 다시 확인한다 — **데이터 메시 플레인은 서비스 접근에서 엄격한 계층화를
  부과하지 않는다. 데이터 프로덕트 경험 플레인은 데이터 프로덕트에 대한 연산 집합을 제공하고 그
  기저 인프라 프로비저닝의 복잡성을 관리한다. 그러나 플랫폼 사용자가 인프라 플레인에 접근하는
  것을 엄격히 막으려는 의도는 아니다. 데이터 프로덕트와 일하는 것을 아주 쉽게 만들어서 도메인
  팀이 인프라 서비스와 직접 일할 유인을 갖지 않게 하려는 것일 뿐이다** (10장,
  p.173).[^dehghani2022]
- 논리 설계의 범위도 좁혀 둔다 — **데이터 메시 플랫폼의 논리 아키텍처는 플레인의 인터페이스에만
  집중한다. (…) 아키텍처 모델링에서 나는 논리 인터페이스만 불러낸다. 인터페이스의 물리적 구현이
  명령줄 인터페이스(CLI)인지 API인지 GUI인지, 그리고 각 논리 인터페이스에 대한 실제 물리 호출의
  수는 아키텍처 설계의 범위 밖이다** (9장, p.161).[^dehghani2022]

## 세 플레인

- 저자가 식별한 플레인은 셋이다 — **데이터 메시 플랫폼의 복잡성과 그 광범위한 능력을 감안하면 그
  논리 아키텍처는 여러 플레인으로 구성된다. 지금까지 나는 데이터 메시 인프라에 대해 세 개의 다른
  플레인을 식별했다** (9장, p.162).[^dehghani2022]

| 플레인 | 원어 | 무엇을 담는가 |
|---|---|---|
| 데이터 인프라(유틸리티) 플레인 | data infrastructure (utility) plane | 스토리지·파이프라인 오케스트레이션·컴퓨트 같은 물리 자원을 프로비저닝·관리하는 원자적 서비스 |
| 데이터 프로덕트 경험 플레인 | data product experience plane | 데이터 프로덕트와 직접 작동하는 고수준 추상 서비스 — 생성·접근·보안 등 |
| 메시 경험 플레인 | mesh experience plane | 상호 연결된 데이터 프로덕트의 메시 위에서 작동하는 서비스 — 검색, 메시 전반의 계보 관측 등 |

- 각 플레인의 서술은 9장과 10장이 같은 내용을 두 어투로 적는다 (9장, p.162 · 10장,
  pp.171–172):[^dehghani2022]
  - **데이터 인프라(유틸리티) 플레인은 메시를 짓고 돌리는 저수준 인프라 자원 — 스토리지·컴퓨트·
    아이덴티티 시스템 등 — 을 관리할 책임을 진다. 그것은 운영 시스템을 짓고 돌리는 디지털
    애플리케이션 인프라와 통합되고 겹친다. 예컨대 데이터 인프라는 도메인 팀의 나머지가
    애플리케이션을 개발하는 데 쓰는 것과 같은 CI/CD 엔진을 데이터 프로덕트에 대해 공유할 수
    있다.**
  - **데이터 프로덕트 경험 플레인은 데이터 프로덕트를 짓고·유지하고·소비하는 더 높은 수준의
    추상이며 인프라 플레인을 써서 지어진다. 그 인터페이스는 데이터 프로덕트와 직접 작동한다.**
  - **메시 경험 플레인은 여러 데이터 프로덕트에 걸쳐 작동하는 메시 수준 능력을 추상한다. 예컨대
    메시 위의 데이터 프로덕트를 검색하거나, 여러 데이터 프로덕트를 가로질러 계보 — 입력 데이터
    프로덕트와 출력 데이터 프로덕트 사이의 연결 — 를 순회하는 연산을 지원한다.**
- 플레인 사이에 의존은 있다 — **메시 경험 플레인은 데이터 프로덕트 플레인의 인터페이스에 —
  그것들을 집계하므로 — 의존하고, 데이터 프로덕트 경험 플레인은 더 낮은 수준의 인프라 유틸리티
  플레인의 인터페이스에 — 그것들을 추상하므로 — 의존한다** (9장, p.163, 그림 9-12).[^dehghani2022]
- 그림 9-12가 예로 드는 인터페이스는 플레인마다 다음과 같다. 저자는 이것이 **예시일 뿐 망라가
  아니며, 명령형 어투를 쓴 것은 의도를 분명히 하기 위한 것이고 실제로는 선언적 자원 지향 설계가
  될 가능성이 크다**고 단서를 단다 — 예컨대 "데이터 프로덕트를 한 단위로 배포하는 능력"을 뜻하는
  `/deploy` 대신 실제로는 `HTTP POST /data-product-deployments` 같은 선언적 API가 된다 (9장,
  p.163).[^dehghani2022]

| 플레인 | 그림 9-12의 인터페이스 예 |
|---|---|
| 메시 경험 | `/search`, `/lineage`, `/monitor`, `/global policies` |
| 데이터 프로덕트 경험 | `/create dp`, `/deploy dp`, `/set privacy dp`, `/document dp`, `/read dp` |
| 인프라 유틸리티 | `/polyglot storage`, `/query engine`, `/flow orchestration`, `/compute`, `/identity management`, `/networking addressing`, `/CI/CD engine` |

## 누가 어느 플레인을 쓰는가

- 접근 자체는 열려 있다 — **이 플레인 전부는 플랫폼의 소비자 — 데이터 프로덕트 개발자·소비자·
  소유자·거버넌스 기능 등 — 가 직접 접근할 수 있다** (10장, p.172).[^dehghani2022] 그림 10-1은
  선 굵기로 **특정 인물이 그 플랫폼 플레인을 얼마나 쓰는지의 정도**를 표시한다 (10장, p.172,
  그림 10-1).[^dehghani2022]
- 메시 경험 플레인의 주 사용자 — **메시 경험 플레인은 메시를 전체로서 운영·거버넌스·질의해야 하는
  사람들의 경험을 최적화한다. 예컨대 거버넌스 팀 구성원과 데이터 프로덕트 소유자가 이 플레인의
  서비스와 상호작용해 정책의 현재 상태를 평가하고, 메시의 일반적 운영 건전성을 모니터링하고,
  기존 데이터 프로덕트를 검색한다. 데이터 프로덕트 소비자와 제공자도 데이터 프로덕트의 집합을
  다뤄야 하는 시나리오 — 검색·브라우징, 또는 계보와 로그를 통한 디버깅 — 에서 쓴다** (10장,
  p.173).[^dehghani2022]
- 데이터 프로덕트 경험 플레인의 주 사용자 — **데이터 프로덕트 소비자와 제공자는 주로 데이터
  프로덕트 경험 플레인과 상호작용해 데이터 프로덕트를 발견하고·배우고·이해하고·소비하고·짓고·
  유지한다. 이 플레인은 소비자와 제공자 사이에서 교환되는 가치 단위로서 데이터 프로덕트의 전달과
  소비에 최적화된다** (10장, p.173).[^dehghani2022]
- 그들이 인프라 플레인으로 내려가는 경우도 규정된다 — **더 적은 정도로 그들은 인프라 플레인의
  서비스를 직접 쓸 수 있다. 흔히 데이터 프로덕트 경험 플레인이 아직 그들이 필요로 하는 서비스를
  제공하지 않는 경우다. 예컨대 어떤 데이터 프로덕트가 그래프 질의 언어로 출력을 노출하고 싶은데
  데이터 프로덕트 경험 플레인이 아직 그것을 패키징된 출력 포트 구현으로 지원하지 않는 경우, 데이터
  프로덕트 개발자는 인프라 서비스를 직접 써서 그래프 질의 엔진을 프로비저닝하고 자기 출력 포트
  구현에 연결할 수 있다** (10장, p.173).[^dehghani2022]
  - 그 뒤에 오는 것이 **수확**이다 — **이상적으로는 그들의 그래프 질의 출력 포트 구현이 나중에
    수확되어(harvested) 플랫폼이 지원하는 표준 출력 포트로 되돌려 지어진다** (10장,
    p.173).[^dehghani2022] 4장이 말한 **수확된 프레임워크**가 실제로 어떻게 굴러가는지를 보이는
    유일한 구체 예다.

## 플레인마다 최적화 대상이 다르다

- 두 플레인의 최적화 목표가 대비된다 — **데이터 프로덕트 경험 플레인이 사용자 경험에 최적화하는
  한편, 데이터 인프라 유틸리티 플레인은 자원의 성능과 활용이 최적화되도록 보장한다. 유틸리티
  플레인은 기저 인프라 제공자가 스토리지·컴퓨트·오케스트레이션 등을 두고 제공하는 것에서 최대치를
  뽑아내는 데 최적화한다. 그것은 데이터 프로덕트 경험 플레인을 기저 물리 호스팅 환경에 적응시킨다**
  (10장, p.173).[^dehghani2022]
- 유틸리티 플레인의 사용자는 다른 플랫폼 팀이다 — **그것은 기저 자원과 그 사용자를 중심으로
  조직되며, 그 사용자의 다수는 다른 플레인들을 짓고 있는 플랫폼 엔지니어다. 데이터 인프라 플레인
  서비스의 다수는 운영 시스템과 공유된다** (10장, p.173).[^dehghani2022]
- 이 분리가 마무리에서 원칙으로 승격된다 — **내가 가져가라고 하고 싶은 둘째 요점은 플레인의
  분리를 존중해서 인간 경험과 기계 효율 양쪽에 대해 최적화하기를 선택할 수 있게 하라는 것이다.
  예컨대 데이터 프로덕트 경험 플레인을 써서 단일 데이터 퀀텀과 상호작용하는 논리 수준에서 사용자
  경험을 최적화하라. 별도의 데이터 인프라 플레인을 만들어 기계에 최적화하라 — 예컨대 각각의 독립
  확장을 다루기 위한 컴퓨트와 스토리지의 분리, 또는 데이터 이동을 줄이기 위한 모든 데이터의
  공통 위치화다. 하위 플레인의 최적화 결정이 개발자 경험을 해쳐서는 안 되고, 그 반대도 마찬가지다**
  (10장, p.189).[^dehghani2022] 여기서 말하는 컴퓨트·스토리지 분리는
  [컴퓨트와 스토리지의 분리](../concepts/compute-storage-separation.md)가 다루는 그 선택이고,
  이 문장은 그 선택을 **유틸리티 플레인 안에 가둬야 한다**는 배치 판정이다.

## 제어 플레인·데이터 플레인을 쓰지 않은 판단

- 기존 계열이 있음을 저자가 먼저 인정한다 — **서비스 메시 같은 기존 플랫폼에서는 협력하는 두
  분리된 플레인, 곧 제어 플레인(control)과 데이터 플레인(data)의 개념이 네트워크 라우팅에서
  빌려져 있다** (9장, p.163).[^dehghani2022]
- 그런데도 쓰지 않았다 — **이 관심사의 분리가 데이터 메시 플랫폼에도 적용될 수 있지만 (데이터
  프로덕트가 데이터 플레인을 구성하고 플랫폼이 제어 플레인을 구성한다고 상상할 수 있다) 나는 이
  설계에서 의도적으로 거리를 두었다** (9장, pp.163–164).[^dehghani2022]
- 그 대신 고른 축이 **경험**이다 — **나는 경험(experience)이라는 개념을 써서 플랫폼이 서로 다른
  수준에서 — 개별 데이터 프로덕트의 수준과 메시로서 그것들의 집합의 수준에서 — 제공하는 어포던스
  (affordances)와 경험에 집중했다** (9장, p.164).[^dehghani2022]
- 저자가 드는 예가 그 차이를 보인다 — **예컨대 플랫폼은 서비스 발견(service discovery)과 주소
  지정 가능성(addressability)의 경험을 제공한다: 다른 데이터 프로덕트가 프로그래밍적으로 다른
  데이터 프로덕트를 이름으로 찾고 주소를 지정해 그 데이터를 소비할 수 있는 능력이다. 물론 이는
  동적 레지스트리·주소 지정·라우팅 등을 구현하는 제어 플레인 비슷한 플레인의 구현으로 상상될 수
  있다. 나는 이 구현 세부를 경험 뒤에 따라오는 것으로 간주한다** (9장, p.164).[^dehghani2022]
- 그래서 설계의 계약이 무엇인지 한 줄로 정리된다 — **본질적으로 데이터 메시 아키텍처는 플랫폼을
  그것이 사용자에게 제공하는 경험의 계약으로(by contract of the experience) 설계한다** (9장,
  p.164).[^dehghani2022] 4장의 이행 지침 "메커니즘이 아니라 경험을 짓는다"가 아키텍처 층에서
  구조 결정으로 나타난 자리다.

## 플랫폼이라는 단일 실체는 없다

- 10장 마무리의 첫째 판정 — **이 장에서 한 가지를 가져간다면 나는 이것이기를 바란다: 플랫폼
  같은 단일 실체(single entity)는 없다. 플랫폼 사용자 여정의 한 단계씩을 각각 만족시키는 API·
  서비스·SDK·라이브러리가 있을 뿐이다** (10장, p.189).[^dehghani2022]
- 그 근거가 경계 횡단이다 — **플랫폼 사용자 여정은 사용자가 데이터 프로덕트 개발자든 소비자든
  데이터 메시 플랫폼 서비스에 결코 고립되지 않는다. 그것들은 흔히 운영 시스템을 서빙하는 API와
  경계를 가로지르고 — 예컨대 스트리밍 능력을 써서 마이크로서비스에서 데이터를 소비하는 것 — 또는
  실험 추적이나 GPU 활용 같은 ML 모델 훈련 능력과 경계를 가로지른다** (10장,
  p.189).[^dehghani2022]
- 그래서 플랫폼을 보는 시각이 규정된다 — **따라서 당신의 플랫폼을 사용자에게 매끄러운 경험을
  주기 위해 거기 있는, 잘 통합된 서비스들의 집합으로 보라** (10장, p.189).[^dehghani2022]
  4장이 "단수형 platform은 단일 해법이나 단일 벤더를 뜻하지 않는다"고 미리 못 박은 것과 같은
  판정이 아키텍처 층에서 반복된다.
- 마지막 조언은 순서에 관한 것이다 — **데이터 메시 플랫폼을 만드는 길의 첫걸음으로 마지막 한
  가지를 남기고 싶다: 데이터 프로덕트 개발자와 데이터 프로덕트 소비자 같은 역할에 대해 최소한의
  마찰과 최대한의 기쁨·몰입을 갖는 최적화된 여정을 발견하고 설계하는 데서 시작하라. 그것을 하고
  나면 그들 여정의 여러 단계에 맞는 올바른 도구를 찾는 검색을 계속해도 좋다** (10장,
  p.190).[^dehghani2022]
