이 페이지의 질문: **JDK 9의 모듈 시스템은 무엇을 바꾸었고, 무엇을 의도적으로 하지 않았는가.**

## 모듈은 코드 컨테이너 이상이다

- 출신과 위상이 한 문장에 있다 — **직소 프로젝트의 결과로 JDK 9에 도입된 모듈 시스템(JPMS)은 자바
  기술에 있어 중요한 개선이다. 모듈화라는 '자유롭게 설정 가능한 캡슐화 격리 메커니즘'을 만들기 위해
  자바 가상 머신은 클래스 로딩 아키텍처를 적절히 변형했다** (7장, p.386).[^zhou2024]
- JAR과 다른 점이 정의에 들어 있다 — **JDK 9의 모듈은 JAR 패키지 같은 단순한 코드 컨테이너가
  아니다.** 자바 모듈 정의에는 코드 외에 다음이 포함된다 (7장, p.386):[^zhou2024]
  - **`requires`: 다른 모듈에 대한 의존성 목록**
  - **`exports`: 다른 모듈에서 사용할 수 있는 패키지 목록**
  - **`open`: 다른 모듈에서 리플렉션 API로 접근할 수 있는 패키지**
  - **`uses`: 현재 모듈이 사용할 서비스 목록**
  - **`provides`: 다른 모듈에 제공하는 서비스 목록**
- 이 정의가 클래스 파일로 컴파일되어 저장되는 자리는
  [클래스 파일의 속성 테이블](../concepts/class-file-attributes.md)의 `Module`·`ModulePackages`·
  `ModuleMainClass` 속성이다.

## 고치려 한 두 가지 결함

- 첫째는 의존성 누락이 너무 늦게 터진다는 것이다 — **클래스패스에 기초하던 JDK 8까지의 의존성 관리
  방식은 안정성에 문제가 있었다.** 예전에는 **필요한 타입이 클래스패스에 없더라도 프로그램이 그
  타입을 처음 사용하려 할 때에서야 비로소 예외가 보고되었다** (7장, p.387).[^zhou2024]
  - 버전 조건: JDK 9 이상 — **모듈이 의존하는 다른 모듈들을 명시할 수 있어서, 필요한 의존성이 모두
    갖춰졌는지 애플리케이션 개발 단계에서 확인할 수 있다. 의존성이 누락되었다면 애플리케이션은 시작
    자체를 못하기 때문에 런타임 예외를 상당 부분 피할 수 있다** (7장, p.387).
  - 완전히 사라지지는 않는다 — 각주가 반례를 든다. **모듈화를 적용한다고 해서
    `ClassNotFoundException` 부류의 예외가 완전히 사라진다는 뜻은 아니다. 예를 들어 공개 패키지에서
    일부 타입(클래스·인터페이스)을 제거한 후 모듈의 익스포트 목록에 반영하지 않으면 문제가 된다. 이
    경우 프로그램이 시작은 되지만 런타임에 클래스 로딩 예외가 발생할 수 있다** (7장, p.387,
    각주 24).
- 둘째는 `public`이 너무 넓다는 것이다 — **자바 모듈 시스템은 또한 클래스패스에 존재하는 JAR 파일
  전반의 `public` 타입들에 접근할 수 있던 문제도 해결한다. 이전까지는 `public` 타입이라면 프로그램
  코드 어디서든 이용할 수 있었다. 하지만 JDK 9부터는 다르다. 자바 모듈은 `public` 타입 중에서도
  외부 모듈에 공개할 타입을 따로 명시하게 함으로써 접근 권한을 더 세분화해 관리한다** (7장,
  p.387).[^zhou2024]
- 그 통제가 실제로 걸리는 자리가 클래스 로딩이다 — **이러한 접근 통제는 주로 클래스 로딩 과정에서
  이루어진다** (7장, p.387).[^zhou2024] 구체적인 규칙은
  [심벌 참조의 해석](../concepts/symbolic-reference-resolution.md)에 있다.

## 클래스패스와 모듈패스

- 호환을 위해 대응 개념을 하나 만들었다 — **자바 모듈 시스템이 기존 클래스패스 방식과 호환되도록
  하기 위해 JDK 9에서는 클래스패스에 해당하는 모듈패스 개념을 도입했다** (7장,
  p.387).[^zhou2024]
- 무엇이 모듈인지를 정하는 것은 파일의 내용이 아니라 위치다 — **간단히 말하면, 클래스 라이브러리의
  위치에 따라 모듈인지 아니면 전통적인 JAR 패키지인지 결정된다. JAR 파일을 클래스패스에 배치하면
  모듈 정보(`module-info.class`)를 포함하고 있더라도 JAR 패키지로 취급된다. 반대로 모듈패스에
  배포된 JAR 파일은 JMOD 접미사도 사용하지 않고 `module-info.class` 파일을 포함하지 않더라도
  모듈로 취급된다** (7장, p.387).[^zhou2024]

## 세 가지 호환 규칙

- 목표는 무수정 업그레이드다 — **자바 설계진은 클래스패스 방식의 기존 자바 애플리케이션도 아무런
  수정 없이 JDK 9 이상의 최신 환경에서 실행할 수 있도록 다음 규칙을 적용했다. JDK 자체는 자바 SE의
  표준 클래스 라이브러리 전체를 이미 모듈화해 두었지만, 이 규칙들 덕에 기존 프로그램도 표준 클래스
  라이브러리 모듈들이 익스포트한 패키지에 문제없이 접근할 수 있다** (7장,
  pp.387–388).[^zhou2024]
- 규칙은 셋이다 (7장, pp.387–388):[^zhou2024]
  - **클래스패스상의 JAR 파일용 접근 규칙**: **클래스패스에 있는 모든 JAR 파일과 기타 리소스 파일은
    자동으로 익명 모듈(unnamed module)로 패키징된 것으로 간주한다. 익명 모듈은 격리 효과가 거의
    없어서 클래스패스상의 모든 패키지, JDK의 시스템 모듈들이 익스포트한 모든 패키지, 모듈패스상의
    모듈들에서 익스포트한 모든 패키지를 보고 사용할 수 있다.**
  - **모듈패스상의 모듈용 접근 규칙**: **모듈패스에 존재하는 명명된 모듈(named module)은 자신의
    의존성 정의에서 명시한 모듈과 패키지에만 접근할 수 있다. 익명 모듈의 모든 내용은 명명된
    모듈에서 볼 수 없다. 즉, 명명된 모듈은 기존 방식의 JAR 패키지 내용을 볼 수 없다.**
  - **모듈패스상의 JAR 파일용 접근 규칙**: **모듈 정의가 포함되지 않은 기존 JAR 파일을 모듈패스에
    넣어 두면 자동으로 모듈이 된다. `module-info.class` 파일이 없는 모듈은 기본적으로 자신의 패키지
    모두를 익스포트하며, 모듈패스에 존재하는 다른 모든 모듈에 의존한다. 따라서 기존 방식의 JAR는
    모든 모듈에서 접근할 수 있다.**
- 그래서 업그레이드 비용이 작다 — **이상의 규칙 덕에 옛 클래스패스 방식을 따르는 자바 애플리케이션도
  JDK 9로 매끄럽게 업그레이드할 수 있다. 단, 클래스 로더가 변경되어 몇 가지 사소한 영향이 있을 수
  있다.** 그리고 **프로젝트 설정에서도 JAR로 묶어 배포하는 기존 방식을 유지할 수 있다** (7장,
  p.388).[^zhou2024] 클래스 로더 쪽 변경은
  [클래스 로더와 부모 위임 모델](../concepts/class-loaders-and-parent-delegation.md)에 있다.

## 버전을 지원하지 않는다는 선택

- 요구는 자명한데 지원은 없다 — **일반적으로 잘 관리되는 모듈이라면 버전이 꾸준히 업그레이드되면서
  자연스럽게 여러 가지 릴리스 버전이 생겨난다. 따라서 필요한 의존성을 확실하게 보장받으려면
  컴파일하고 패키징할 때 모듈의 올바른 버전을 개발자가 선택할 수 있어야 한다. 하지만 현시점의 자바
  모듈 시스템은 모듈 정의에 버전 번호를 부여할 수 없다. 따라서 버전이 여러 개일 수 있다는 개념과
  버전 선택 기능을 지원하지 않는다** (7장, p.388).[^zhou2024]
- 버전이라는 낱말 자체는 여기저기 등장한다. `java --list-modules`는 `java.base@17`처럼 **끝에 버전
  번호가 붙어** 있는 목록을 출력하고, **JDK 9에서 클래스 파일 구조에 `Module` 속성이 추가되었고, 그
  안에는 `module_version_index`라는 필드가 있다.** 또한 **모듈 버전은 개발자가
  `javac --module-version` 명령으로 컴파일할 때 지정할 수 있다.** 라이브러리도
  **`java.lang.module.ModuleDescriptor.Version`과 같은 인터페이스를 제공하여 런타임에 특정 모듈의
  버전을 확인할 수 있다** (7장, pp.388–389).[^zhou2024]
- 그런데도 공식 입장은 반복해서 부정이다 — **직소의 공식 명세서는 물론 자바원 콘퍼런스에서의 발표
  내용에서도 "자바 플랫폼 모듈 시스템은 OSGi를 대체하지 않는다", "자바 플랫폼 모듈 시스템은 모듈
  버전을 지원하지 않는다"라며 반복해서 강조하고 있다** (7장, p.389).[^zhou2024]
- 저자는 그 이유를 기술만으로 설명하지 않는다 — **오라클은 모듈 시스템이 기술적으로 너무 복잡해지지
  않기를 원했다. 하지만 직소를 놓고 '오라클 대 IBM·레드햇'이 치열하게 대립한 과거를 감안하면, 현재
  설계가 두 진영이 타협한 결과가 아니라 순전히 기술적인 이유 때문이라고 확신하기는 어렵다. 즉, IBM의
  지원을 이끌어 내기 위해 또는 적어도 반대하지는 않도록 하기 위해 OSGi에 숨 쉴 공간을 제공한 것으로
  보인다** (7장, pp.389–390).[^zhou2024] 이 대립의 경과는
  [JDK 판올림의 역사](../concepts/jdk-release-history.md)에 있다.

## 런타임 교체는 범위 밖이다

- 그 결과가 기능 하나의 부재다 — **자바 모듈 시스템에서는 OSGi와 달리 런타임에 같은 모듈의 여러
  버전이 공존하면서 동적으로 교체, 배포하는 건 거의 불가능하다** (7장, p.390).[^zhou2024]
- 둘을 섞을 수는 있지만 값이 비싸다 — **JDK 9 이후로는 OSGi와 자바 모듈 시스템을 혼합할 수 있지만,
  그러면 의심할 여지없이 매우 복잡해진다. 자바 모듈 시스템과 자바 가상 머신은 기본적으로 모듈의
  런타임 배포와 교체를 지원하지 않는다. 클래스 로더를 이용해 구현할 수는 있지만 매우 불편하다**
  (7장, p.390).[^zhou2024]
- 가상 머신이 제공하는 우회로에는 한계가 명시되어 있다 — **자바 가상 머신에 내장된 JVMTI
  인터페이스(`java.lang.instrument.Instrumentation`)를 이용하면 런타임에 클래스를 어느 정도
  수준까지는 수정할 수 있다(`RedefineClass`, `RetransformClass`). 하지만 제약이 많으며 OSGi와 같은
  핫 스와프를 사용하거나 여러 버전이 공존하도록 하는 데 직접 사용할 수는 없다** (7장,
  p.390).[^zhou2024]
  - 제약이 무엇인지가 각주에 있다 — **기존 메서드의 본문 내용은 수정할 수 있지만, 새로운 메서드를
    추가하거나 기존 메서드의 시그너처를 수정할 수는 없다** (7장, p.390, 각주 28).
  - 그래서 실제 쓰임새가 개발 도구 쪽으로 굳었다 — **IntelliJ IDEA나 이클립스 같은 통합 개발
    환경에서 메서드 본문을 핫 스와프하는 데 잘 활용하고 있다**(통합 개발 환경에서 메서드 본문 코드를
    수정한 다음, 애플리케이션 재시작 없이 바로 반영) (7장, p.390).
- 더 나간 연구도 있었지만 유지되지 못했다 — **런타임 타입 교체를 지원하기 위한 연구 프로젝트인
  DCEVM은 메모리에 로드된 클래스를 성능 손실 없이 임의로 수정할 수 있게 했다. 하지만 안타깝게도 오랜
  기간 업데이트되지 못하고, 최신 버전이 여전히 JDK 11을 지원하는 데 머물러 있다** (7장,
  p.391).[^zhou2024]
