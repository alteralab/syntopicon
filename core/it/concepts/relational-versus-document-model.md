## 관계형 모델과 도전자들

- **오늘날 가장 잘 알려진 데이터 모델은 아마 SQL의 것이며, 이는 1970년 에드거 코드(Edgar
  Codd)가 제안한 관계형 모델(relational model)에 기반한다. 이 모델에서 데이터는
  관계(relations, SQL에서는 테이블tables라 부른다)로 조직되며, 각 관계는 튜플(tuples, SQL에서는
  행rows)의 순서 없는 모음이다** (3장, p.67).[^kleppmann2026]
- **관계형 모델은 원래 이론적 제안이었고 당시 많은 사람이 그것이 효율적으로 구현될 수 있을지
  의심했다. 그러나 1980년대 중반에 이르러 관계형 데이터베이스 관리 시스템(RDBMS)과 SQL은 어떤
  종류든 규칙적인 구조를 가진 데이터를 저장하고 질의해야 하는 대부분의 사람에게 선택 도구가
  됐다. 많은 데이터 관리 유스케이스 — 예컨대 업무 분석 — 는 수십 년이 지난 지금도 여전히
  관계형 데이터가 지배한다** (3장, p.67).[^kleppmann2026]
- 도전자들의 계보 (3장, p.67):[^kleppmann2026]
  - **1970년대와 1980년대 초에는 네트워크 모델(network model)과 계층 모델(hierarchical
    model)이 주요 대안이었지만 관계형 모델이 그들을 지배하게 됐다.**
  - **객체 데이터베이스(object databases)는 1980년대 말과 1990년대 초에 왔다가 다시
    갔다**(오늘날 인기 있는 클라우드 서비스인 대용량 파일용 오브젝트 스토리지와 혼동하지 말
    것).
  - **XML 데이터베이스는 2000년대 초에 나타났지만 틈새 채택에 그쳤다.**
- 그래서 판정이 이렇다 — **관계형 모델의 각 경쟁자는 자기 시대에 많은 과대 선전을 낳았지만
  어느 것도 오래가지 못했다. 대신 SQL이 다른 종류의 데이터를 포함하도록 자라났다 — 예컨대
  XML·JSON·그래프 데이터 지원을 더했다** (3장, p.67).[^kleppmann2026]

## NoSQL이 남긴 것

- **2010년대에는 NoSQL이 관계형 데이터베이스의 지배를 무너뜨리려던 최신 유행어였다. NoSQL은
  단일 기술이 아니라 새로운 데이터 모델·스키마 유연성·확장성, 그리고 오픈 소스 라이선스 모델로의
  이동을 둘러싼 느슨한 발상들의 집합을 가리킨다** (3장, p.67).[^kleppmann2026]
- **어떤 데이터베이스는 스스로를 NewSQL이라 이름 붙였는데, NoSQL 시스템의 확장성과 전통적
  관계형 데이터베이스의 데이터 모델·트랜잭션 보장을 함께 제공하겠다는 목표를 반영한 것이다.
  NoSQL과 NewSQL 발상은 데이터 시스템 설계에 매우 영향력이 컸지만, 그 원리가 널리 채택되면서
  그 용어들의 사용은 시들해졌다** (3장, p.67).[^kleppmann2026]
- **NoSQL 운동의 지속되는 효과 하나가 문서 모델(document model)의 인기이며, 이는 보통 데이터를
  JSON으로 표현한다. 이 모델은 원래 MongoDB·Couchbase 같은 전문 문서 데이터베이스가 대중화했지만,
  이제는 대부분의 관계형 데이터베이스도 JSON 지원을 더했다. 관계형 테이블이 흔히 빡빡하고
  유연하지 않은 스키마를 가졌다고 여겨지는 데 비해, JSON 문서는 더 유연하다고 생각된다** (3장,
  p.67).[^kleppmann2026]

## 객체-관계 임피던스 불일치

- **오늘날 애플리케이션 개발의 상당수가 객체 지향 프로그래밍 언어로 이뤄지며, 이는 SQL 데이터
  모델에 대한 흔한 비판으로 이어진다 — 데이터가 관계형 테이블에 저장되면 애플리케이션 코드의
  객체와 테이블·행·열이라는 데이터베이스 모델 사이에 어색한 번역 계층이 필요하다는 것이다. 두
  모델 사이의 이 단절을 때로 임피던스 불일치(impedance mismatch)라 부른다** (3장,
  p.68).[^kleppmann2026]
- 저자들이 용어의 출처를 상자로 밝힌다 — **임피던스 불일치라는 용어는 전자공학에서 빌려 왔다.
  모든 전기 회로는 입력과 출력에 일정한 임피던스(교류에 대한 저항)를 갖는다. 한 회로의 출력을
  다른 회로의 입력에 연결할 때, 두 회로의 출력 임피던스와 입력 임피던스가 맞으면 연결을 가로지르는
  전력 전달이 최대가 된다. 임피던스 불일치는 신호 반사와 다른 문제로 이어질 수 있다** (3장,
  p.68).[^kleppmann2026]

## ORM의 문제와 값

- **ActiveRecord나 Hibernate 같은 객체-관계 매핑(object-relational mapping, ORM) 프레임워크는
  이 번역 계층에 필요한 상용구 코드의 양을 줄이지만 흔히 비판받는다.** 자주 인용되는 문제들
  (3장, p.68):[^kleppmann2026]
  - **ORM은 복잡하고 두 모델 사이의 차이를 완전히 감추지 못하므로, 개발자는 여전히 데이터의
    관계형 표현과 객체 표현을 둘 다 생각해야 하는 처지에 놓인다.**
  - **ORM은 일반적으로 OLTP 앱 개발에만 쓰인다. 분석 목적으로 데이터를 제공하는 데이터
    엔지니어는 바탕 관계형 표현과 일해야 하므로, ORM을 쓰더라도 관계형 스키마의 설계는 여전히
    중요하다.**
  - **많은 ORM이 관계형 OLTP 데이터베이스와만 동작한다. 검색 엔진·그래프 데이터베이스·NoSQL
    시스템처럼 다양한 데이터 시스템을 가진 조직은 ORM 지원이 부족하다고 느낄 수 있다.**
  - **어떤 ORM은 관계형 스키마를 자동 생성하지만, 그것은 관계형 데이터에 직접 접근하는
    사용자에게 어색할 수 있고 바탕 데이터베이스에서 비효율적일 수 있다. ORM의 스키마·질의 생성을
    커스터마이징하는 일은 복잡할 수 있고 애초에 ORM을 쓰는 이점을 무효로 만들 수 있다.**
  - **ORM은 비효율적인 질의를 실수로 쓰기 쉽게 만든다.** 그 예가 **N+1 질의 문제(N+1 query
    problem)** 다.
- N+1 질의 문제의 설명 — **페이지에 사용자 댓글 목록을 보여 주고 싶어 댓글 N개를 반환하는 질의를
  하나 수행하고, 각 댓글은 작성자의 ID를 담고 있다고 하자. 각 댓글 작성자의 이름을 보여 주려면
  users 테이블에서 그 ID를 조회해야 한다. 손으로 쓴 SQL이라면 아마 질의 안에서 이 조인을 수행해
  각 댓글과 함께 작성자 이름을 반환할 것이다. 그러나 ORM에서는 각 댓글마다 작성자를 조회하려고
  users 테이블에 별도의 질의를 하게 되어 총 N+1개의 데이터베이스 질의가 되고, 이는 데이터베이스에서
  조인을 수행하는 것보다 느리다. 이 문제를 피하려면 ORM에 댓글을 가져올 때 작성자 정보도 함께
  가져오라고 알려 줘야 할 수 있다** (3장, pp.68–69).[^kleppmann2026]
- 그럼에도 **ORM에는 이점도 있다** (3장, p.69):[^kleppmann2026]
  - **관계형 모델에 잘 맞는 데이터라면 영속적 관계형 표현과 인메모리 객체 표현 사이의 번역이
    어떤 형태로든 불가피하며, ORM은 이 번역에 필요한 상용구 코드의 양을 줄인다. 복잡한 질의는
    여전히 ORM 바깥에서 처리해야 할 수 있지만, ORM은 단순하고 반복적인 경우를 도울 수 있다.**
  - **어떤 ORM은 데이터베이스 질의 결과의 캐싱을 도와 데이터베이스 부하를 줄일 수 있다.**
  - **ORM은 스키마 마이그레이션과 그 밖의 관리 활동도 도울 수 있다.**

## 일대다 관계와 문서 표현

- **모든 데이터가 관계형 표현에 잘 맞는 것은 아니다.** 저자들의 예는 이력서다 — **링크드인
  프로필을 관계형 스키마로 표현하면, 프로필 전체는 고유 식별자 user_id로 식별되고 first_name·
  last_name처럼 사용자당 정확히 한 번 나타나는 필드는 users 테이블의 열로 모델링할 수 있다**
  (3장, p.69, 그림 3-1).[^kleppmann2026]
- 그런데 나머지가 문제다 — **대부분의 사람은 경력에서 두 개 이상의 직위(position)를 가졌고,
  교육 기간도 여러 번일 수 있으며 연락처 정보도 여러 개일 수 있다. 그런 일대다(one-to-many)
  관계를 표현하는 한 방법은 직위·교육·연락처 정보를 각각 별도 테이블에 두고 users 테이블에
  대한 외래 키 참조를 갖게 하는 것이다** (3장, p.69).[^kleppmann2026]
- **같은 정보를 표현하는 다른 방법은, 아마 더 자연스럽고 애플리케이션 코드의 객체 구조에 더
  가깝게 대응하는 것으로, JSON 문서다** (3장, p.69, 예제 3-1). 그 문서는 이렇게 생겼다 (3장,
  p.70):[^kleppmann2026]

  ```json
  {
    "user_id":      251,
    "first_name":   "Barack",
    "last_name":    "Obama",
    "headline":     "Former President of the United States of America",
    "region_id":    "us:91",
    "photo_url":    "/p/7/000/253/05b/308dd6e.jpg",
    "positions": [
      {"job_title": "President", "organization": "United States of America"},
      {"job_title": "US Senator (D-IL)", "organization": "United States Senate"}
    ],
    "education": [
      {"school_name": "Harvard University", "start": 1988, "end": 1991},
      {"school_name": "Columbia University", "start": 1981, "end": 1983}
    ],
    "contact_info": {
      "website": "https://barackobama.com",
      "x": "https://x.com/barackobama"
    }
  }
  ```

- **어떤 개발자들은 JSON 모델이 애플리케이션 코드와 저장 계층 사이의 임피던스 불일치를 줄인다고
  느낀다. 스키마의 부재도 이점으로 자주 인용된다** (3장, p.71).[^kleppmann2026] 스키마 쪽
  논의는 [읽기 스키마와 쓰기 스키마](../concepts/schema-on-read-and-schema-on-write.md)에 있다.
- 성능 논거도 붙는다 — **JSON 표현은 다중 테이블 스키마보다 지역성(locality)이 좋다. 관계형
  예에서 프로필을 가져오려면 여러 질의를 수행하거나(테이블마다 user_id로 질의) users 테이블과
  그 하위 테이블들 사이의 지저분한 다중 조인을 수행해야 한다. JSON 표현에서는 관련 정보가 전부
  한곳에 있어 질의가 더 빠르고 단순하다** (3장, p.71).[^kleppmann2026]
- 구조가 드러난다 — **사용자 프로필에서 직위·학력·연락처 정보로 가는 일대다 관계는 데이터에
  트리 구조를 함의하며, JSON 표현은 이 트리 구조를 명시적으로 만든다** (3장, p.71, 그림
  3-2).[^kleppmann2026]
- 다만 경계가 있다 — **일대다 관계를 때로 일대소수(one-to-few)라 부르는데, 이력서는 보통 적은
  수의 직위를 갖기 때문이다. 관련 항목이 정말로 많다면 — 예컨대 유명인의 소셜 미디어 글에 달린
  댓글은 수천 개일 수 있다 — 그것들을 전부 같은 문서에 끼워 넣는 것은 너무 다루기 힘들 수
  있으므로 관계형 접근이 더 낫다** (3장, p.71).[^kleppmann2026]

## 언제 어느 모델을 쓰는가

- 저자들이 논거를 양쪽으로 정리한다 — **문서 데이터 모델을 지지하는 주요 논거는 스키마 유연성,
  지역성으로 인한 더 나은 성능, 그리고 어떤 애플리케이션에서는 그것이 애플리케이션이 쓰는 객체
  모델에 더 가깝다는 것이다. 관계형 모델은 조인, 그리고 다대일·다대다 관계에 대한 더 나은 지원을
  제공함으로써 맞선다** (3장, p.80).[^kleppmann2026]
- 문서 모델이 맞는 자리 — **애플리케이션의 데이터가 문서 같은 구조(즉 일대다 관계의 트리이고
  보통 트리 전체가 한 번에 로드된다)를 가지면 문서 모델을 쓰는 것이 아마 좋은 생각이다. 문서
  같은 구조를 여러 테이블로 쪼개는 관계형 기법인 슈레딩(shredding)은 번거로운 스키마와
  불필요하게 복잡한 애플리케이션 코드로 이어질 수 있다** (3장, p.80).[^kleppmann2026]
- 문서 모델의 한계 둘 (3장, p.80):[^kleppmann2026]
  - **문서 안의 중첩된 항목을 직접 참조할 수 없다. 대신 "사용자 251의 직위 목록 중 두 번째
    항목" 같은 식으로 말해야 한다. 중첩 항목을 참조해야 한다면 관계형 접근이 더 잘 동작하는데,
    어떤 항목이든 그 ID로 직접 참조할 수 있기 때문이다.**
  - 반대로 **어떤 애플리케이션은 사용자가 항목의 순서를 고르게 한다** — 예컨대 **사용자가
    작업을 끌어다 놓아 순서를 바꾸는 할 일 목록이나 이슈 트래커**다. **문서 모델은 그런
    애플리케이션을 잘 지원하는데, 항목(또는 그 ID)을 JSON 배열에 그냥 저장해 순서를 정할 수
    있기 때문이다. 관계형 데이터베이스에는 그런 재정렬 가능한 목록을 표현하는 표준적 방법이
    없어, 정수 열로 정렬하기(중간에 삽입할 때 번호를 다시 매겨야 한다), ID의 연결 리스트
    유지하기, 분수 인덱싱(fractional indexing) 쓰기 같은 여러 요령이 쓰인다.**
- 다대일·다대다 관계 쪽의 판정은
  [정규화와 비정규화](../concepts/normalization-and-denormalization.md)에 있다.

## 읽기와 쓰기의 데이터 지역성

- **문서는 보통 JSON·XML 또는 그 이진 변형(MongoDB의 BSON 같은)으로 인코딩된 하나의 연속된
  문자열로 저장된다. 애플리케이션이 자주 문서 전체에 접근해야 한다면(예컨대 웹 페이지에
  렌더링하기 위해) 이 저장 지역성은 성능 이점을 갖는다. 데이터가 여러 테이블에 나뉘어 있으면
  그것을 전부 가져오는 데 여러 번의 인덱스 조회가 필요하고, 이는 더 많은 디스크 탐색과 더 많은
  시간을 요구할 수 있다** (3장, p.82).[^kleppmann2026]
- 그런데 조건이 붙는다 — **지역성 이점은 문서의 큰 부분을 동시에 필요로 할 때만 적용된다.
  데이터베이스는 보통 문서 전체를 로드해야 하는데, 큰 문서의 작은 부분에만 접근해야 한다면
  이는 낭비일 수 있다. 게다가 문서를 갱신할 때는 보통 문서 전체를 다시 써야 한다. 이런 이유로
  문서를 꽤 작게 유지하고 잦은 작은 갱신을 피하는 것이 일반적으로 권장된다** (3장,
  p.82).[^kleppmann2026]
- 지역성은 문서 모델의 전유물이 아니다 — **관련 데이터를 지역성을 위해 함께 저장하는 것은 문서
  모델에 국한되지 않는다. 예컨대 구글의 Spanner 데이터베이스는 테이블의 행이 부모 테이블 안에
  끼워 넣어져야(중첩돼야) 한다고 스키마가 선언할 수 있게 함으로써 관계형 데이터 모델에서 같은
  지역성 성질을 제공한다. 오라클도 다중 테이블 인덱스 클러스터 테이블(multi-table index cluster
  tables)이라는 기능으로 같은 일을 허용한다. 구글의 Bigtable이 대중화하고 예컨대 HBase와
  Accumulo에서 쓰이는 와이드 칼럼 데이터 모델은 지역성 관리라는 비슷한 목적을 가진 컬럼
  패밀리(column families)를 갖는다** (3장, p.82).[^kleppmann2026]

## 문서를 질의하는 언어

- **관계형 데이터베이스와 문서 데이터베이스의 또 다른 차이는 그것을 질의하는 데 쓰는 언어나
  API다. 대부분의 관계형 데이터베이스는 SQL로 질의되지만 문서 데이터베이스는 더 다양하다. 어떤
  것은 기본 키에 의한 키-값 접근만 허용하고, 어떤 것은 문서 안의 값을 질의하는 2차 인덱스도
  제공하며, 어떤 것은 풍부한 질의 언어를 제공한다** (3장, p.82).[^kleppmann2026]
- 실물들 — **XML 데이터베이스는 흔히 XQuery와 XPath로 질의되며, 이들은 여러 문서에 걸친 조인을
  포함한 복잡한 질의를 허용하고 결과를 XML로 형식화하도록 설계돼 있다. JSON Pointer와 JSONPath는
  JSON에 대해 XPath와 동등한 것을 제공한다. MongoDB의 집계 파이프라인(aggregation pipeline)은
  JSON 문서 모음을 위한 질의 언어의 한 예다** (3장, p.82).[^kleppmann2026]
- 저자들이 집계 예를 든다 — **해양 생물학자가 되어 바다에서 동물을 볼 때마다 관찰 기록을
  데이터베이스에 추가한다고 하자. 이제 월별로 상어를 몇 마리 목격했는지 보고서를 만들고 싶다.**
  PostgreSQL이라면 `date_trunc('month', …)` 으로 그룹화하는 SQL을 쓴다. **같은 질의를 MongoDB의
  집계 파이프라인으로 표현하면 이렇게 된다** (3장, p.83):[^kleppmann2026]

  ```js
  db.observations.aggregate([
      { $match: { family: "Sharks" } },
      { $group: {
          _id: {
              year: { $year: "$observationTimestamp" },
              month: { $month: "$observationTimestamp" }
          },
          totalAnimals: { $sum: "$numAnimals" }
      } }
  ]);
  ```

- 저자들의 평가 — **집계 파이프라인 언어는 표현력 면에서 SQL의 부분집합과 비슷하지만, SQL의
  영어 문장식 구문 대신 JSON 기반 구문을 쓴다. 그 차이는 아마 취향의 문제다** (3장,
  p.83).[^kleppmann2026]

## 두 모델의 수렴

- **문서 데이터베이스와 관계형 데이터베이스는 데이터 관리에 대한 매우 다른 접근으로 출발했지만
  시간이 지나면서 서로 더 비슷해졌다. 관계형 데이터베이스는 JSON 타입과 질의 연산자, 그리고
  문서 안의 속성을 인덱싱하는 능력을 더했다. 어떤 문서 데이터베이스(MongoDB·Couchbase·RethinkDB
  같은)는 조인·2차 인덱스·선언적 질의 언어 지원을 더했다** (3장, p.83).[^kleppmann2026]
- **이 모델들의 수렴은 애플리케이션 개발자에게 좋은 소식인데, 관계형 모델과 문서 모델은 같은
  데이터베이스 안에서 둘을 결합할 수 있을 때 가장 잘 동작하기 때문이다. 많은 문서 데이터베이스가
  다른 문서에 대한 관계형 스타일의 참조를 필요로 하고, 많은 관계형 데이터베이스에 스키마 유연성이
  이로운 구획이 있다. 관계형-문서 하이브리드는 강력한 조합이다** (3장,
  pp.83–84).[^kleppmann2026]
- 저자들이 상자로 덧붙이는 역사적 아이러니 — **코드의 원래 관계형 모델 서술은 관계형 스키마
  안에서 JSON과 비슷한 무언가를 허용했다. 그는 그것을 비단순 도메인(nonsimple domains)이라
  불렀다. 발상은 행 안의 값이 수나 문자열 같은 원시 데이터 타입일 필요가 없다는 것이었다 —
  그것은 중첩된 관계(테이블)일 수도 있어서 임의로 중첩된 트리 구조를 값으로 가질 수 있다. 이
  구성은 30년도 더 지나 SQL에 더해진 JSON·XML 지원에 견줄 만하다** (3장,
  p.84).[^kleppmann2026]
