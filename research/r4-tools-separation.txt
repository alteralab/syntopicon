KEY: architecture-principle
--- SUMMARY ---
판정: 현행 설계(응집도별 — 각 데이터 레이어가 자기 글루를 소유, 공유 엔진만 외부)가 원칙·실증 양쪽에서 우세하다. (1) 사용자 제안 '도구 vs 데이터' 종류별 최상위 분할은 Constantine/Yourdon 위계에서 하위 2등급인 logical cohesion('종류가 같아서 묶음')의 정의 그 자체이고, package-by-layer 논쟁에서 같은 이유(변경이 모든 묶음을 관통, 경계 강제 불가)로 패배한 구도다(Simon Brown, Screaming Architecture). (2) 동거의 적극 근거는 CCP — '같은 이유·같은 시점에 바뀌는 것은 함께': 스키마 마이그레이션이 content+schema+validate 원자 커밋을 요구하는 한 도구는 데이터 곁이 맞고, change coupling 실측 연구(Tornhill/CodeScene)는 co-change 파일을 경계 너머로 벌리면 비용이 거리에 비례해 커짐을 보인다. (3) bounded context(각 컨텍스트가 자기 모델·인프라 소유)와 1인 프로젝트의 Conway 조건(팀 경계 0 → 저장소 경계 추가는 원자성 상실 비용만), 과학 컴퓨팅 실무 표준(Wilson 2017: 단일 프로젝트 루트에 data/+src/ 동거)이 이를 보강한다. — 그러나 사용자 제안은 허수아비가 아니다: Clean Architecture tension diagram이 명시하듯 CCP 우선은 프로젝트 초기 국면의 균형점이고, 성숙하면 REP('재사용 단위=릴리스 단위') 쪽으로 이동한다. 사용자 제안이 옳아지는 실증 조건: (a) 도구가 두 번째~세 번째 소비자(다른 KB, 외부 사용자)를 실제로 얻을 때(REP + rule of three — 그 전의 선제 분리는 premature abstraction), (b) 도구가 독립 릴리스·버전·CI를 필요로 할 때, (c) tools 커밋이 schema/콘텐츠와 co-change하지 않고 단독 변경 비율이 지배적으로 될 때 — 이 (c)는 플랜의 현행 신호('tools 커밋 수가 콘텐츠 상회')보다 정확한 신호이며 git log로 직접 실측 가능하다, (d) 데이터 저장소를 Frictionless Data Package류의 순수 교환 포맷으로 외부에 공개할 때. 요컨대 현행 플랜의 '글루 동거·엔진 외부 + 분리 발동 신호' 구조는 문헌과 정합하며, 개선점은 발동 신호를 커밋 수 비교에서 co-change 비율 계측으로 교체하는 것 하나다.

[LB] Common Closure Principle(CCP, Clean Architecture): '같은 이유로 같은 시점에 바뀌는 것들을 한 컴포넌트에 모으고, 다른 시점·다른 이유로 바뀌는 것들은 분리하라.' 현행 설계의 동거 근거(스키마 마이그레이션 = content+schema+validate 동일 커밋)는 CCP의 교과서적 적용이다.
     src: https://www.oreilly.com/library/view/clean-architecture-a/9780134494272/ch13.xhtml (2017 (Clean Architecture ch.13))
[LB] Constantine/Yourdon의 cohesion 위계에서 logical cohesion(수행 내용의 '종류가 같아서' 묶음)은 coincidental 바로 위의 하위 2등급으로 분류된다. '모든 도구라서 한 폴더'는 정확히 logical cohesion의 정의이며, 원전 계보에서 열등한 묶음 기준으로 판정된 방식이다.
     src: https://en.wikipedia.org/wiki/Cohesion_(computer_science) (원전 1974/1979, 2차 소스 접근 2026-08-08)
[LB] DDD bounded context(Fowler/Evans): 큰 시스템은 각자 통일된 모델을 갖는 컨텍스트로 나뉘고, 각 컨텍스트는 자기 모델·스키마·구현 인프라를 소유한다. core(KB 스키마 컨텍스트)와 docs-mirror(미러 캐시 컨텍스트)가 각자 PLAN·스크립트·스킬을 소유하는 현행안은 이 패턴과 일치하고, 도구를 컨텍스트 밖으로 빼면 두 컨텍스트의 도구가 한 곳에서 뒤섞인다.
     src: https://martinfowler.com/bliki/BoundedContext.html (2014-01-15 (bliki))
[LB] Conway의 법칙 역방향(Inverse Conway Maneuver, ThoughtWorks Tech Radar 등재): 원하는 아키텍처에 맞게 팀 구조를 바꾸라 — 즉 모듈/저장소 경계는 커뮤니케이션 경계와 상호 결정 관계다. 1인 프로젝트에는 팀 경계가 0개이므로, 저장소 경계 추가는 Conway 이득 없이 조정 비용(cross-repo 변경, atomic commit 상실)만 발생시킨다.
     src: https://www.thoughtworks.com/radar/techniques/inverse-conway-maneuver (기원 2010-12, Radar 접근 2026-08-08)
[LB] 실증(마케팅 아님): change coupling(temporal coupling) 연구 — 함께 커밋되는 파일들이 아키텍처 경계를 가로지르면 변경 비용이 커지며, '거리가 멀수록 악화된다.' tools/·schema/·콘텐츠가 실제로 co-change하는 한(스키마 마이그레이션 커밋이 그 증거), 이들을 다른 저장소로 벌리는 것은 실측 데이터가 경고하는 바로 그 패턴이다.
     src: https://codescene.com/blog/software-revolution-part3/ (접근 2026-08-08)

[LB] [사용자 제안이 이기는 조건 1] REP(Reuse/Release Equivalence Principle): '재사용의 단위는 릴리스의 단위'다. 도구가 두 번째 소비자를 얻어 독립 릴리스·버전·호환성 보장이 필요해지는 순간, 분리가 원칙적으로 옳아진다. Clean Architecture의 tension diagram은 이를 명시: 세 원칙(REP·CCP·CRP)은 동시 만족 불가하고, 프로젝트 초기는 CCP(개발 용이) 쪽에서 시작해 성숙하며 REP(재사용) 쪽으로 이동한다.
     src: https://www.oreilly.com/library/view/clean-architecture-a/9780134494272/ch13.xhtml (2017 (Clean Architecture ch.13))
[LB] [사용자 제안이 이기는 조건 2와 그 시점 판정] Rule of Three: 재사용 컴포넌트는 3개 응용에서 검증되기 전에는 충분히 일반적이지 않으며, 소비자 1개 시점의 선제 분리는 premature abstraction으로 유지비만 늘린다. 따라서 '지금 미리 나누자'는 지고, '두 번째(~세 번째) 소비자가 실재할 때 나누자'가 이긴다 — 현행 플랜의 분리 발동 신호와 동일 구조.
     src: https://en.wikipedia.org/wiki/Rule_of_three_(computer_programming) (접근 2026-08-08)
[  ] [사용자 제안이 이기는 조건 3] '데이터 저장소를 순수하게' 진영의 실재 근거: Frictionless Data Package 표준은 데이터+메타데이터만의 순수 패키지가 불특정 다수 도구의 소비·아카이브·FAIR 상호운용에 유리하다고 본다. 단 성립 조건은 '데이터가 자기 전용 글루가 아니라 범용 교환 포맷으로 외부 도구들에 소비될 때'다 — syntopicon의 tools/는 자기 스키마 결합 글루이므로 현재는 해당하지 않는다.
     src: https://specs.frictionlessdata.io/ (접근 2026-08-08)
[LB] [플랜 보완 지점] 현행 플랜의 분리 신호 중 'tools/ 커밋이 콘텐츠 커밋을 지속 상회'는 churn 신호일 뿐 co-change 신호가 아니다. change coupling 실증 기준으로는, tools가 아무리 자주 바뀌어도 schema·콘텐츠와 같은 커밋에서 함께 바뀐다면 CCP가 여전히 동거를 지지한다. 올바른 실측 신호는 'tools 커밋 중 schema/콘텐츠와 무관하게 단독으로 바뀌는 비율'이며, 이는 git log로 직접 계측 가능하다.
     src: https://codescene.com/blog/change-coupling-visualize-the-cost-of-change (접근 2026-08-08)

판정: 현행 설계(응집도별 분리)가 실증 우세이며, 사용자 제안(종류별 분리: 도구 vs 데이터)은 '도구라는 종류' 자체를 분리 축으로 지지하는 실증이 문헌에 존재하지 않는다. 사용자가 분리의 모범으로 삼을 법한 pre-commit·GitHub reusable workflows조차 분리 근거는 종류가 아니라 (1) 복수 소비자의 중복 제거였고("sharing our pre-commit hooks across projects is painful" / "avoid duplication"), pre-commit은 저장소에 결합된 스크립트는 repo: local로 동거하라고 스스로 권고한다 — syntopicon의 tools/는 정확히 이 '결합된 글루'다. 반대 방향의 실증은 두껍다: 스키마와 검증기를 소비자 밖에 두면 version skew·수동 조정으로 퇴화하고(Buf), Google은 원자적 변경과 One-Version Rule로 이를 구조적으로 봉쇄했으며(CACM 2016·SWE at Google ch.16), Notion은 스키마+검증기 동거 덕에 커밋 시점 호환성 게이트를 만들었고, 1인 규모에서는 조기 분리가 조정 비용으로 붕괴한 실무 보고가 반복된다(Losoviz 200-repo → 모노레포 회귀). 분리하면 rev 핀+주간 autoupdate+semver 릴리스 관리라는 상시 비용이 소비자·생산자 양쪽에 생기고(pre-commit.ci의 존재 이유), 스키마 마이그레이션은 원자적 커밋에서 2-PR 조정+호환성 윈도우로 격하된다. 사용자 제안이 이기는 조건(실증 도출): (a) 소비자 수 ≥2 실현 — docs-mirror가 core의 tools를 실제 import하기 시작하면 Rule of Three 경로에 진입하며, 이때는 pre-commit 모델(도구 형제 repo + 소비자 측 rev 핀)이 옳다. 현행 PLAN의 '두 번째 소비자' 발동 신호가 정확히 이 임계다. (b) 독립 라이프사이클 — tools가 KB 콘텐츠와 무관한 자체 릴리스 케이던스·자체 배포(다른 머신, 타인)를 요구할 때. (c) 신뢰·가시성 경계 — 예컨대 tools/스킬을 오픈소스로 공개하되 KB 콘텐츠는 사설로 남길 때(SWE at Google의 유일한 정당 분리 조건이자 Losoviz가 실제 분리한 시점). 결정적 변수의 서열은 실증상 신뢰 경계 > 소비자 수 > 독립 배포 필요이고, '변경 빈도 비율'(tools 커밋이 콘텐츠 커밋 상회)은 정량 실증을 찾지 못해 선행 지표 정도로만 취급해야 한다. 주의할 뉘앙스: 사용자 제안이 '우산 아래 형제 디렉토리(단일 git)'를 뜻한다면 원자적 커밋은 보존되므로 논쟁은 디렉토리 미학 수준으로 축소되지만, '별도 git repo'를 뜻한다면 스키마 마이그레이션의 원자성(content+schema+validate 동일 커밋)을 즉시 상실한다 — 이것이 현행 조항의 핵심 방어선이다.

[LB] pre-commit이 훅을 별도 저장소로 분리한 근거는 '도구라서'가 아니라 복수 소비자였다 — 공식 문서: "As we created more libraries and projects we recognized that sharing our pre-commit hooks across projects is painful. We copied and pasted unwieldy bash scripts from project to project." 즉 분리는 이미 N개 프로젝트가 같은 훅을 복붙하던 고통에 대한 사후 대응이고, 부수 근거는 언어 격리(Ruby 린터를 node 프로젝트에서 Gemfile 없이 쓰기)다.
     src: https://pre-commit.com/ (2026 (현행 문서))
[LB] 분리의 원조인 pre-commit 스스로가 저장소에 결합된 스크립트는 동거하라고 권고한다 — repo: local 훅이 유용한 경우: "The scripts are tightly coupled to the repository and it makes sense to distribute the hook scripts with the repository. Hooks require state that is only present in a built artifact of your repository." syntopicon의 tools/(validate·reindex)는 정확히 이 조건(스키마에 결합, KB 상태 필요)에 해당한다.
     src: https://pre-commit.com/ (2026 (현행 문서))
[LB] 도구를 분리하면 소비자 쪽에 상시 버전 관리 비용이 생긴다: pre-commit은 rev를 불변 참조(tag/SHA)로 핀해야 하고("Using a branch name (or HEAD) for the value of rev is not supported"), 핀을 최신으로 유지하는 일이 상시 작업이라 전용 서비스 pre-commit.ci가 주간(월요일 16:00 UTC) autoupdate PR을 자동 발행하는 것으로 존재 이유를 삼는다.
     src: https://pre-commit.ci/ (2026 (현행 문서))
[LB] GitHub reusable workflows의 공식 추출 근거는 오직 중복 제거("avoid duplication when creating a workflow by reusing existing workflows")이며, 추출 후에는 보안상 SHA 핀("Using the commit SHA is the safest option for stability and security")과 릴리스 관리(semver 태그 발행 + v1/v1.1 이동 태그를 최신 커밋으로 계속 옮기기)가 도구 저장소 쪽의 지속 부담으로 명시된다.
     src: https://docs.github.com/en/actions/sharing-automations/reusing-workflows (2026 (현행 문서))
[LB] Google(SWE at Google 16장)의 One-Version Rule: "Developers must never have a choice of 'What version of this component should I depend upon?'" — 버전 선택을 허용하는 순간 diamond dependency·mismatched linking·lost work가 생긴다. 동시에 이 책은 분리가 정당한 유일 조건도 명시한다: "different sets of authorized developers, visibility, permissions" — 즉 비밀·법무·프라이버시·권한 경계가 다를 때만 저장소를 나눈다("if every project in your organization has the same secrecy, legal, privacy, and security requirements, a true monorepo is a fine way to go").
     src: https://abseil.io/resources/swe-book/html/ch16.html (2020 (서적, 온라인 공개판))
[LB] Google CACM 2016 논문(Potvin & Levenberg)의 원자적 변경 논거: 모노레포에서는 "atomic changes can be applied to many parts of the codebase at the same time"이고 대규모 리팩토링이 단순해지며, 멀티레포의 diamond dependency 문제가 제거된다. 규모: 10억 파일·20억 LOC·86TB·3,500만 커밋. 단 비용도 명시: 대규모 툴링 투자, 코드베이스 복잡화, code health에 추가 노력.
     src: https://dl.acm.org/doi/10.1145/2854146 (2016-07)
[LB] 스키마를 소비자와 다른 저장소에서 공유하는 방식의 실패는 업계에서 반복 보고된다 — Buf: "Protobuf does not have a native way to share dependencies, and teams feel that their only option is to copy/paste (vendor) these schemas manually"(복제 드리프트), 그리고 파괴적 변경 방지가 "code review and communication"이라는 인간 조정에만 의존하게 된다. [LB] Notion은 스키마(~1,300 API 엔드포인트, ~296 큐 태스크 타입)와 그 호환성 검증기를 같은 저장소에 두고, CI가 base 브랜치의 구 스키마와 PR의 신 타입을 TypeScript assignability로 비교해 파괴적 변경을 커밋 전에 잡는다. 스키마와 검증기가 같은 repo·같은 PR에 있어야만 이 게이트가 성립한다 — 검증 기준: "A schema change is backward compatible if and only if new code can handle old data."

[  ] 분리 후 재연결 수단인 git submodule의 고통은 광범위하게 문서화되어 있다: 브랜치 전환 시 잔류 파일, worktree 미지원("support for submodules is incomplete" — Git 공식 문서), 부모보다 먼저 push해야 하는 순서 규율, bad reference 커밋, 서브모듈 코드가 의도치 않은 public API가 되어 소비자를 모른 채 파괴적 변경이 어려워지는 문제, diamond 중복. 저자가 허용하는 예외는 '편집하지 않을 서드파티 코드 수입'뿐이다.

--- SUMMARY ---
판정: 현행 설계(응집도별 분리 — 각 데이터 레이어가 자기 글루(tools·skills·evals)를 소유, 공유 엔진만 외부 설치·버전 핀)가 생태계 실증과 일치한다. 근거의 축은 4개. (1) Claude Code 공식 모델 자체가 종류가 아닌 scope 기반이다: project 스킬은 'This project only', 모노레포 패키지별 nested .claude/skills를 공식 지원하고, cloud/routine 세션은 클론된 repo에 커밋된 스킬만 로드하므로 스킬을 데이터 repo 밖으로 빼면 원격 실행에서 스킬이 사라지는 실측 비용이 있다. (2) 사용자가 선례로 볼 만한 dbt-agent-skills는 '도구 분리'가 아니라 '벤더가 30+ 에이전트 플랫폼이라는 불특정 다수 소비자에게 배포하는 제품' 사례다 — 그리고 그 벤더 스스로 '프로젝트 특화 스킬은 네 프로젝트 안에 추가하라'고 권장하며, dbt-core discussion에서도 실무자들이 'skills should live in repositories, versioned with code / user-level 설치는 복잡성만 추가'라고 증언한다. (3) MCP도 동일 패턴: 프로젝트 결합 서버·설정은 repo에 커밋(VS Code 공식 권장), 범용 서버만 단독 repo·패키지. (4) 단독 스킬 repo(anthropics/skills, dbt-agent-skills)의 공통 특징은 특정 데이터 무결합 + 마켓플레이스 배포 목적 — PLAN의 '두 번째 소비자' 분리 발동 신호와 정확히 같은 조건이다. 다만 사용자 제안이 이기는 조건도 실재한다: (a) 같은 스킬 집합을 core와 docs-mirror 둘 다(또는 제3 프로젝트)가 소비하게 될 때 — 이때 실무 패턴은 중앙 registry + submodule/symlink이고 Claude Code는 스킬 symlink와 --add-dir 로드를 공식 지원한다; (b) 도구가 데이터와 독립된 릴리스 주기·버전 핀을 갖는 배포물이 될 때(dbt deps식 패키지형 스킬); (c) 절충형으로, 세션을 항상 우산 루트에서 시작한다면 '우산 루트 .claude/skills = 크로스 레이어 오케스트레이션 스킬만, 각 레이어는 자기 글루 유지'라는 하이브리드가 nested-skills 공식 기능으로 성립한다. 결론적으로 사용자 제안은 '지금 틀렸다'기보다 'PLAN에 이미 적힌 분리 발동 신호(두 번째 소비자·tools 커밋 상회)가 켜지기 전에 선제 실행하는 것'이며, 그 신호 전 선제 분리를 지지하는 실증은 찾지 못했다. docs-mirror가 자체 검색 스킬을 갖게 되어 두 레이어가 스킬을 '각자' 갖는 것은 분리 신호가 아니고(각자 자기 데이터에 결합), 한 스킬이 두 레이어를 '함께' 다루기 시작하는 순간이 신호다.
