## 하나의 질문

**수백 개의 자율 데이터 프로덕트로 이뤄진 메시에서, 무엇이 잘못되고 있는지를 어떻게 아는가.**

## 정의와 그것이 답하는 질문들

- 절 머리의 제사 — **Don't control, but observe. — Gregor Hohpe** (14장,
  p.262).[^dehghani2022]
- 정의 — **데이터 프로덕트의 마지막이자 필수 불가결한 능력을 보자: 관측 가능성(observability)이다.
  데이터 프로덕트 관측 가능성은 데이터 프로덕트들의 — 그리고 결과적으로 메시의 — **외부 출력을
  관측함으로써 내부 상태를 추론하는 능력**이다** (14장, p.262).[^dehghani2022]
- 답해야 할 질문들 — **관측 가능성은 다음 같은 질문에 답하려 한다: 데이터 프로덕트가 자기 일을
  성공적으로 수행하고 있는가? 자기 보증을 충족하고 있는가? 데이터 프로덕트가 정책을 준수하고
  있는가? 처리된 데이터가 자기 통계적 성질·부피·빈도·범위·분포 등을 충족하는가? 데이터 프로덕트에
  원치 않는 접근이 있었는가? 데이터 프로덕트에 이슈가 있었는가, 그렇다면 근본 원인은 무엇인가?
  지평선에 예상되는 문제가 있는가? 관측 가능성은 이 질문들에 개별 데이터 프로덕트 수준에서도,
  메시로서의 집합 수준에서도 답한다** (14장, p.263).[^dehghani2022]

## 느슨한 결합이 치르는 대가

- **데이터 메시의 분산 아키텍처 — 자기 데이터·데이터 모델·정책으로 서로 연결된 느슨하게 결합된
  데이터 프로덕트의 메시 — 는 관측 가능성에 복잡성을 만든다. 각자 실패할 수 있는 움직이는 부품이
  많고, 모니터링할 데이터 프로덕트와 상호 연결이 다수이며, **실패가 눈에 띄지 않고 지나갈 수
  있다**** (14장, p.263).[^dehghani2022]
- 대조가 날카롭다 — **모놀리식하고 단단히 결합된 시스템에서는 단일 실패가 흔히 전체 시스템의
  실패로 귀결되며 이는 탐지하기 쉽다. 데이터 메시에서는 데이터 프로덕트의 느슨한 결합이 실패를
  가능한 한 국소화한다. 따라서 그런 실패를 탐지하고 디버그하려면 자동화되고 포괄적인 관측 가능성이
  요구된다** (14장, p.263).[^dehghani2022]
  - **격리의 이득과 관측의 비용이 같은 성질에서 나온다**는 정직한 서술이다. 같은 교환이
    [마이크로서비스와 서버리스](../concepts/microservices-and-serverless.md)와
    [모놀리스 대 모듈러](../concepts/monolith-versus-modular.md)에 있다.

## 네 가지 사용처

- **① 메시의 운영 건전성 모니터링** — **데이터 프로덕트가 기대하는 데이터를 받고 있는가, 자기
  변환을 성공적으로 돌리고 있는가, SLO 보증과 기대 통계 성질에 부합하게 데이터를 서빙하고 있는가?
  관측 가능성은 이 프로세스에 중단이 있는지 탐지하고, 자동으로 자기 치유하고 이슈를 고치며, 관련
  있는 사람에게 통지한다** (14장, p.263).[^dehghani2022]
- **② 디버그와 사후 분석 수행** — **무언가 잘못되었을 때, 데이터가 우리 기대에 맞지 않을 때,
  또는 데이터를 받고·변환하고·서빙하는 데 오류가 있을 때, 데이터 프로덕트 관측 가능성은 데이터
  프로덕트 개발자와 소유자가 실패의 영향을 평가하고 근본 원인을 발견하도록 돕는다** (14장,
  p.263).[^dehghani2022]
- **③ 감사 수행** — **데이터 프로덕트는 제3자가 감사 — 규제·리스크·컴플라이언스·보안 — 를
  수행할 수 있게 한다. 예컨대 어떤 서비스가 보안 보증을 위해 접근 로그를 계속 자동으로 감사할
  수 있다 — 누가 어떤 데이터에·언제·어떻게 접근하는가다** (14장, p.263).[^dehghani2022]
  [감사 가능성과 무결성 검사](../concepts/auditing-and-integrity-checking.md)의 접근이 여기서
  **데이터 프로덕트가 스스로 내주는 출력**으로 재배치된다 — 사후 재구성이 아니라 상시 제공이다.
- **④ 데이터 계보 이해** — **데이터 계보 — 데이터가 어디서 발원했고 어떤 변환을 거쳤는지를
  이해하는 것 — 는 데이터를 이해하고 신뢰하는 한 요소로 남으며 데이터 이슈를 디버그하는 데
  필요하다. 이는 모델의 품질이 훈련 데이터의 품질에 크게 달린 기계 학습에서 특히 유용하다.
  훈련 데이터에 대한 더 깊은 이해와 신뢰를 요구하는 데이터 과학자는 흔히 데이터 계보를 평가한다.
  ML 모델 편차의 진짜 이슈를 이해하고 짚어 내려면, 데이터와 모델에 대한 맥락적(런타임) 메트릭과
  결합된 계보가 필수다** (14장, pp.263–264).[^dehghani2022]

## 기존 접근과 갈리는 한 줄

- 설계의 출발점 — **데이터 메시 관측 가능성은 각 데이터 프로덕트가 **설계상** 자기 외부 출력을
  공유하고 자기 상태를 보고하는 데서 시작한다. 각 데이터 프로덕트는 데이터를 소비·변환·공유하면서
  자기 **로그·트레이스·메트릭**을 공유한다. 이 출력들 위에 지어, 메시 경험 플레인이 메시 수준
  상태를 관측하고 모니터링할 수 있다** (14장, p.264).[^dehghani2022]
- **핵심 차이가 한 문장으로 못 박힌다** — **관측 가능성에서 데이터 프로덕트의 구실이 기존 데이터
  관측 가능성과 데이터 메시의 핵심 차이다. 기존 접근은 **외부 당사자 — 데이터 팀 — 가 레이크나
  웨어하우스에서 사후에 데이터를 검사함으로써** 데이터의 상태를 모니터링한다** (14장,
  p.264).[^dehghani2022]
- 그 결과 검사가 이동한다 — **데이터 메시에서는 이 사후 데이터 점검의 다수가 데이터 프로덕트
  변환의 구현 일부가 되며, 테스트와 통제가 **데이터에 대한 계산적 기대(computational
  expectations)**로 표현된다** (14장, p.264).[^dehghani2022]
  - [데이터 품질 관리](../concepts/data-quality-management.md)의 사후 프로파일링·검사 계열과
    갈리는 자리다. 대립은 처방이고, 조건은 **데이터를 만든 팀이 검사를 짤 수 있는가**이다 —
    13장의 "기대(expectations)"가 여기서 관측의 구성 요소로 다시 등장한다.

## 세 기둥 — 로그·트레이스·메트릭

- 계열이 밝혀진다 — **운영 플레인에서 마이크로서비스 같은 분산 아키텍처는 관측 가능성을
  집합적으로 가능하게 하는 세 종류의 외부 출력으로 수렴했다: 로그·트레이스·메트릭이다. 이것들은
  흔히 **관측 가능성 기둥(observability pillars)**이라 불린다** (14장, p.264).[^dehghani2022]

**로그** — **로그는 불변이고·타임스탬프가 찍혔으며·흔히 구조화된 이벤트로, 특정 태스크의 처리와
실행의 결과로 생산된다. 그것들은 흔히 **디버깅**과 **근본 원인 분석**의 훌륭한 정보원이다. 데이터
프로덕트의 경우 데이터를 소비하고·검증하고·변환하고·서빙하는 행위가 로그를 생산할 수 있다. 예컨대
**artist profiles** 데이터 프로덕트의 로그는 **artist onboarding service**에서 입력 포트를 통해
새 데이터를 받았을 때, 일련의 변환을 통해 데이터를 프로덕션화하는 데 취해진 단계의 요약, 그리고
특정 처리 시간의 데이터가 데이터 사용자에게 가용해졌을 때를 포착할 수 있다** (14장,
p.264).[^dehghani2022]

- 조건이 붙는다 — **로그가 유용하고 안전하려면 구조를 표준화하고, 모든 로그가 일관되게 제공해야
  할 필수 요소를 정의하고, 로그에 정보를 과다 노출하지 않도록 올바른 수준의 프라이버시 조치를
  구현하는 것이 중요하다. 이것이 메시의 운영 건전성에 대한 통찰을 위해 로그의 자동·ML 기반 분석을
  가능하게 한다. **자동 분석을 갖추지 않고 로그를 수집하는 것은 흔히 헛수고다** — 분석할 능력
  없이 다른 종류의 대용량 데이터를 모으는 것과 마찬가지다** (14장, p.264).[^dehghani2022]
  [데이터 소스로서의 로그](../concepts/logs-as-a-data-source.md)가 로그를 반입 대상으로 보는
  자리와, 여기서 로그를 **프로덕트가 발행하는 계약된 출력**으로 보는 자리가 갈린다.

**트레이스** — **트레이스는 인과적으로 관련된 분산 이벤트의 기록이다. 트레이스 기록은 행동과
이벤트의 종단 흐름을 인코딩할 수 있는 방식으로 구조화된다. 로그와 비슷하게 트레이스도 불변이고·
타임스탬프가 찍혔으며·구조화된 이벤트다. **분석 데이터 플레인에서 트레이스의 주된 용도는 데이터
계보를 만드는 것이다**: 데이터가 데이터 프로덕트들을 통해 어떻게 흐르고 각 프로덕트에서 어떻게
변환되는가다. 로그와 마찬가지로 데이터 프로덕트는 자기 트레이스의 구조를 모델링하는 단일 표준을
채택한다** (14장, p.265).[^dehghani2022]

- 운영 쪽과 뜻이 다르다 — **운영 플레인의 트레이스는 흔히 요청의 결과로 실행되는 호출과
  트랜잭션의 트리를 포착함에 유의하라. 예컨대 아티스트 목록을 가져오는 웹 요청은 여러
  마이크로서비스로의 호출로 이어질 수 있다. 데이터 메시에서 트레이스는 **입력·출력 포트의
  그래프를 통과하는 데이터 또는 데이터 요청의 흐름**을 표현한다 — 소스 데이터 프로덕트에서
  데이터의 기원으로, 최종 데이터 소비자까지다** (14장, p.265).[^dehghani2022]
  - **계보를 별도 시스템이 수집하는 산물이 아니라 트레이스라는 표준 출력으로 환원**하는 것이
    이 절의 결정이다. 11장이 계보를 "지역 규칙에서 창발한다"고 말한 자리의 구현이 이것이다.
    [메타데이터 관리](../concepts/metadata-management.md)의 계보 수집 계열과 갈린다.

**메트릭** — **메트릭은 데이터 프로덕트의 빌드 시점·런타임 특성을 계속 소통하는 객관적으로
정량화 가능한 파라미터다. 13장 "데이터 보증으로 신뢰를 세운다"에서 나는 각 데이터 프로덕트가
계속 공유하는 메트릭의 몇 범주 — 예: 타임라인·완전성·정확성 등 — 를 도입했다. 로그·트레이스와
비슷하게 메트릭도 불변이고·타임스탬프가 찍힌 (흔히 수치) 이벤트로, 일정 기간에 걸쳐 추적될 수
있다** (14장, p.265).[^dehghani2022]

- 셋의 자리 — **이 기둥들은 분산 관측 가능성 모델을 데이터 프로덕트에 적응시키는 훌륭한
  출발점이다. 9장에서 나는 데이터 프로덕트가 자기 외부 관측 가능성 출력을 공유하는 표준
  인터페이스로 관측 가능성 API를 도입했다** (14장, p.265).[^dehghani2022] 그림 14-3이 로그·
  트레이스(계보)·메트릭 세 출력이 하나의 관측 가능성 API로 나가는 그림이다 (14장, p.265,
  그림 14-3).[^dehghani2022]
- **셋 다 불변·타임스탬프**라는 공통 성질이 반복된다 — 관측 출력도 데이터 프로덕트의 데이터와
  같은 규율을 따른다. [바이템포럴 데이터](../concepts/bitemporal-data.md)의 불변성 논거가
  관측 데이터에도 그대로 적용되는 자리다.

## 운영 플레인까지 이어지는 추적 가능성

- **많은 데이터 프로덕트가 운영 시스템에서 발원한다. 구체적으로 소스 정렬 데이터 프로덕트는 자기
  협력 운영 시스템에서 데이터를 얻는다. 예컨대 **artist profiles** 데이터 프로덕트는 아티스트가
  artist onboarding 마이크로서비스 애플리케이션으로 온보딩하는 행위로 자기 존재를 시작한다**
  (14장, p.266).[^dehghani2022]
- 그래서 경계를 넘어야 한다 — **따라서 데이터 계보의 완전한 그림을 제공하려면, 또는 이슈를
  디버그하고 근본 원인 분석을 수행하려면, 데이터의 관측 가능성은 데이터 프로덕트를 **넘어 운영
  시스템까지** 확장되어야 한다. 관측 가능성 데이터는 운영 시스템까지 추적 가능해야 한다** (14장,
  p.266).[^dehghani2022]
  - 이것이 [데이터 메시](../concepts/data-mesh.md)가 그은 운영/분석 경계를 관측이 다시
    가로지르는 자리다 — 데이터는 갈라 두되 트레이스는 잇는다.

## 구조화되고 표준화된 관측 데이터

- **데이터 프로덕트의 관측 데이터에서 고차 지능과 통찰을 만들기 쉽게 하려면, 메트릭·로그·트레이스가
  구조화된 형식을 갖고 이상적으로 표준화되어야 한다. 그것들은 데이터 프로덕트의 전역 URI, 실제·처리
  타임스탬프, 출력 포트 URI 등 특정 필드를 모델링해야 한다. 구조화된 정보는 자유 형식 메시지를 위한
  평문 같은 비구조 요소를 가질 수 있다. 집필 시점 데이터 프로덕트 메트릭·로그·트레이스를 위한
  **열린 산업 표준을 만들 필요**가 있다** (14장, p.266).[^dehghani2022]
  - 각주 — **집필 시점 OpenLineage는 초기 개발 중이며 데이터 프로덕트의 트레이스에 매핑될 수
    있다** (14장, p.266, 각주 5).[^dehghani2022] 9장 표 9-1이 발견·관측 API의 성숙도를
    "열린 표준을 요구하고 일부가 개발 중"으로 매긴 그 항목이다.
  - 관측 출력에 **처리 시간·실제 시간이 필수 필드로 들어간다**는 것이 중요하다 — 관측 데이터도
    바이템포럴이다.

## 관측 데이터 자체를 데이터 프로덕트로

- 확장 방법 — **시간이 지나며 관측 가능성을 확장하는 한 방법은 **관측 가능성 자체에 도메인 지향
  설계를 적용하는 것**이다 — 예컨대 **데이터 품질**·**데이터 모양**·**데이터 적합성** 같은 관측
  가능성 도메인을 만드는 것이다** (14장, p.266).[^dehghani2022]
- 그리고 재귀가 명시된다 — **메시 수준 관측 가능성 정보 자체가 데이터 프로덕트로 관리될 수 있다고
  상상할 수 있다. 예컨대 **data quality** 데이터 프로덕트가 메시의 데이터 품질에 대한 메트릭과
  보완적 통찰 집합을 제공할 수 있다** (14장, p.266).[^dehghani2022]
  - 데이터 프로덕트 개념이 **자기 자신의 운영 데이터에도 적용되는 재귀**가 여기서 성립한다.
    [멀티플레인 데이터 플랫폼](../concepts/multiplane-data-platform.md)의 메시 경험 플레인이
    이 데이터 프로덕트를 호스팅하는 자리다.

## 저자가 metadata라는 낱말을 끝내 피하는 이유

- 9장의 진술이 여기서 더 강하게 반복된다 — **나는 데이터에 대한 모든 데이터를 **메타데이터라는
  잡동사니 양동이**로 일반화하는 것에 늘 불편함을 느껴 왔다. 이 접근은 서로 다른 메타데이터 부류를
  설계하는 데서 **의도성(intentionality)**을 제거한다. 실제로 나는 글에서 메타데이터라는 용어를
  가능한 한 쓰지 않으려 자제해 왔다. 모든 데이터는 데이터라는 것이 내 개인적 믿음이며, 서로 다른
  타입의 데이터 사이에 상관과 관계가 있고, 모든 데이터는 사업 도메인(예: **artist profiles**)에서
  관측 가능성 도메인(예: **data quality metrics**)에 이르기까지 도메인 개념으로 설계될 수 있다.
  재사용 가능한 데이터 프로덕트 개념이 모든 분석 데이터를 감당한다** (14장,
  p.266).[^dehghani2022]
  - [데이터 퀀텀](../concepts/data-quantum.md)의 같은 주장과 짝을 이룬다. 9장에서는 "그
    낱말이 가리키는 덩어리를 한 시스템이 관리한다는 설계"를 부정했고, 여기서는 **범주 자체를
    없애고 전부 도메인 데이터로 환원**한다. [메타데이터 관리](../concepts/metadata-management.md)가
    메타데이터를 독립 관리 범주로 세우는 서술과 갈리는 최종 진술이다.

## 14장이 뽑은 공통 실 네 가닥

- 절 머리의 제사 — **Man muss immer umkehren. (One must invert, always invert.) — Carl
  Jacobi** (14장, p.267).[^dehghani2022]
- 장 전체의 한 줄 — **이 장에서 한 가지만 남긴다면, 데이터를 관리하고·거버넌스하고·관측하는 것이
  누구의 책임인가에 대한 관점을 **뒤집으라(invert)**는 것이다. 그 책임을 사후에 관여하는 외부
  당사자에서 **데이터 프로덕트 자신**으로 옮겨라** (14장, p.267).[^dehghani2022]
- 무엇이 그것을 가능하게 하는가 — **데이터 퀀텀 안에서 계산 능력·정책과 짝지어진 데이터는 그
  사용자에게 기본 능력들을 어포드할 수 있다: 매니페스트의 도움으로 수명 주기를 관리하고, 내장 정책의
  실행으로 자기 데이터를 거버넌스하고, 로그·메트릭·트레이스 출력으로 자기 상태를 관측하는 것이다**
  (14장, p.267).[^dehghani2022]
- **이 장에서 도입된 모든 데이터 프로덕트 능력의 설계 특성에 공통으로 흐르는 실이 있다** (14장,
  p.267):[^dehghani2022]

| 실 | 저자의 서술 |
|---|---|
| 표준화(standardization) | 메시 수준 상호운용성을 위한 데이터 프로덕트 인터페이스의 표준화 — 예: 로그에 공통 구조를 채택하는 것 |
| 창발(emergence) | 개별 데이터 프로덕트에서 메시 수준 능력이 창발하는 것 — 예: 각 데이터 프로덕트의 입력·변환·출력 트레이스를 관측해 계보를 발견하는 것 |
| 주체성(agency) | 각 데이터 프로덕트가 자기 관측 가능성 출력·오류 로그·메트릭 등을 공유하는 주체성 |
| 확장성(extensibility) | 시간이 지나며 새 역량이 가능해지도록 — 예: 새 정책을 따르는 것 |

- 이 네 낱말이 11장의 복잡 적응계 논의(단순한 지역 규칙 + 표준 + 창발)와 정확히 겹친다 —
  [데이터 프로덕트 어포던스](../concepts/data-product-affordances.md)가 4부 첫머리에 세운 틀이
  4부 끝에서 회수되는 자리다.
- 4부가 닫히는 문장 — **이 장은 데이터 프로덕트의 능력과 어포던스에 관한 데이터 메시 논의를
  마무리한다. 다음으로 나는 데이터 메시를 향한 전략·실행·조직 변화라는 큰 그림으로 줌아웃할
  것이다** (14장, p.267).[^dehghani2022]
