하나의 질문: **품질 말고 무엇이 모델 선택을 실제로 가르는가.**

## 품질만으로는 고를 수 없다

- **고품질 출력을 생성하지만 실행하기에 너무 느리고 비싼 모델은 쓸모가 없을 것이다. 모델을 평가할 때는
  모델 품질·지연·비용의 균형을 잡는 것이 중요하다. 많은 기업이 더 나은 비용과 지연을 제공한다면 더 낮은
  품질의 모델을 택한다. 비용과 지연 최적화는 9장에서 상세히 논의되므로 이 절은 짧다** (4장,
  p.177).[^huyen2025]

## 파레토 최적화와 양보 못 할 것

- **여러 목표를 함께 최적화하는 것은 파레토 최적화(Pareto optimization)라 불리는 활발한 연구 분야다.
  여러 목표를 최적화할 때는 어떤 목표를 타협할 수 있고 어떤 목표를 타협할 수 없는지를 분명히 하는 것이
  중요하다. 예컨대 지연이 타협할 수 없는 것이라면 서로 다른 애플리케이션에 대한 지연 기대치에서 시작해,
  당신의 지연 요건을 충족하지 못하는 모델을 전부 걸러 내고, 나머지 중에서 가장 좋은 것을 고른다** (4장,
  p.177).[^huyen2025]

## 지연 지표는 하나가 아니다

- **파운데이션 모델의 지연에는 여러 지표가 있는데, 첫 토큰까지의 시간(time to first token)·토큰당
  시간(time per token)·토큰 사이 시간(time between tokens)·질의당 시간(time per query) 등이 있으며 이에
  국한되지 않는다. 어떤 지연 지표가 당신에게 중요한지 이해하는 것이 중요하다** (4장,
  p.177).[^huyen2025]

## 지연은 프롬프트로도 통제된다

- **지연은 밑에 깔린 모델뿐 아니라 샘플링 변수에도 달려 있다. 자기회귀 언어 모델은 통상 출력을 토큰
  단위로 생성한다. 생성해야 하는 토큰이 많을수록 총지연이 높아진다. 모델에게 간결하라고 지시하고 생성의
  정지 조건을 설정하는 것 같은 세심한 프롬프팅이나 다른 최적화 기법으로 사용자가 관측하는 총지연을 통제할
  수 있다** (4장, pp.177–178).[^huyen2025]

## 있으면 좋은 것과 없으면 안 되는 것

- 저자의 조언 상자 — **지연에 근거해 모델을 평가할 때는 없으면 안 되는 것(must-have)과 있으면 좋은
  것(nice-to-have)을 구별하는 것이 중요하다. 사용자에게 더 낮은 지연을 원하냐고 물으면 아무도 아니라고
  말하지 않을 것이다. 그러나 높은 지연은 흔히 성가심이지 거래를 깨는 것은 아니다** (4장,
  p.178).[^huyen2025]

## API는 토큰으로, 자체 호스팅은 컴퓨트로

- 모델 API — **모델 API를 쓰면 통상 토큰으로 과금한다. 입력과 출력 토큰을 많이 쓸수록 비싸진다. 그래서
  많은 애플리케이션이 비용을 관리하려고 입력과 출력 토큰 수를 줄이려 한다** (4장, p.178).[^huyen2025]
- 자체 호스팅 — **자기 모델을 호스팅하면 엔지니어링 비용 외의 비용은 컴퓨트다. 가진 기계를 최대한 활용하려고
  많은 사람이 자기 기계에 들어갈 수 있는 가장 큰 모델을 고른다. 예컨대 GPU는 보통 16GB·24GB·48GB·80GB
  메모리로 나온다. 따라서 인기 있는 모델 다수는 이 메모리 구성을 꽉 채우는 것들이다. 오늘날 많은 모델이
  70억 또는 650억 파라미터를 갖는 것은 우연이 아니다** (4장, p.178).[^huyen2025]

## 규모가 커지면 토큰당 비용이 갈린다

- **모델 API를 쓰면 규모를 키워도 토큰당 비용은 대개 크게 변하지 않는다. 그러나 자기 모델을 호스팅하면
  규모를 키울수록 토큰당 비용이 훨씬 싸질 수 있다. 최대 10억 토큰을 서빙할 수 있는 클러스터에 이미
  투자했다면, 하루에 100만 토큰을 서빙하든 10억 토큰을 서빙하든 컴퓨트 비용은 같다. 따라서 서로 다른
  규모에서 기업은 모델 API를 쓰는 것이 더 말이 되는지 자기 모델을 호스팅하는 것이 더 말이 되는지를 다시
  평가해야 한다** (4장, p.178).[^huyen2025]
  - 각주 — **다만 전기 비용은 사용에 따라 다를 수 있다** (4장, p.178 각주 9).[^huyen2025]

## 기준표의 실물

- 가상의 애플리케이션에 대해 모델을 고르는 데 쓰인 기준의 예다. **`scale` 행은 모델 API를 평가할 때 특히
  중요한데, 당신의 규모를 감당할 수 있는 모델 API 서비스가 필요하기 때문이다** (4장, pp.178–179,
  Table 4-3):[^huyen2025]

  | Criteria | Metric | Benchmark | Hard requirement | Ideal |
  |---|---|---|---|---|
  | Cost | Cost per output token | X | < $30.00 / 1M tokens | < $15.00 / 1M tokens |
  | Scale | TPM (tokens per minute) | X | > 1M TPM | > 1M TPM |
  | Latency | Time to first token (P90) | Internal user prompt dataset | < 200ms | < 100ms |
  | Latency | Time per total query (P90) | Internal user prompt dataset | < 1m | < 30s |
  | Overall model quality | Elo score | Chatbot Arena's ranking | > 1200 | > 1250 |
  | Code generation capability | pass@1 | HumanEval | > 90% | > 95% |
  | Factual consistency | Internal GPT metric | Internal hallucination dataset | > 0.8 | > 0.9 |
