하나의 질문: **REST 스타일로 API 하나를 지을 때 설계자가 결정하는 것은 무엇이고, 프레임워크가
대신 결정해 버리는 것은 무엇인가.**

## 버전 조건

> **버전 조건**: 이 페이지의 구현 서술은 **2025년 저술 시점**의 도구 집합을 전제한다. 저자들이
> 이름을 대는 것은 장고 REST 프레임워크(Django REST Framework, DRF)와 그 부속
> 패키지(`djangorestframework-simplejwt`, `drf-spectacular`), 캐시로 쓰는 레디스(Redis),
> 문서 도구인 OpenAPI 명세(OAS)와 Swagger Editor·Swagger UI·ReDoc·Postman, FastAPI,
> AsyncAPI, 그리고 인증서를 내주는 Let's Encrypt다. **저자들은 이 가운데 어느 것의 판 번호도
> 본문에 적지 않는다** — 유일한 예외가 예제에 박힌 OAS 문서의 `openapi: 3.1.0`이다.
> **`stale_after`는 적지 않는다** — 이 장에는 벤더가 공표한 지원 종료일이 없다.
> 설정 키 이름과 기본값(`PAGE_SIZE` 3, `TIMEOUT` 300, `1000/minute`, `cache_page(30)`)은 그
> 시점 예제의 값이고 규범이 아니다. **아래 멱등·안전·캐시 가능의 규범은 시점에 매이지 않되
> 정본은 이 책이 아니라 RFC 9110이다.**

## 프레임워크가 대신 결정하는 것

- 이 장은 **WFS(Weather Forecast Service)라는 예제 체계를 DRF로 구현**하며 나아간다. 저자들이
  밝히는 순서는 **2장에서 서술한 API 설계 패턴을 그대로 따른다**는 것이다 (5장 §"Implementation",
  p.164).[^dynowski2025] 그 패턴들의 정본은 [API 설계 모범 사례](api-design-best-practices.md)
  이하 2장 페이지들이고, **이 페이지는 그 패턴이 REST와 한 프레임워크 위에서 어떤 결정으로
  굳는가만 담는다.**
- **프레임워크가 떠맡아 버리는 자리가 이 절들에서 하나씩 드러난다.** 저자들이 절마다 설정 키
  하나로 넘기는 것을 모으면 이렇게 된다 (5장 §"Implementation",
  pp.164–182).[^dynowski2025]

  | 무엇을 | 어떻게 넘기는가 | 프레임워크가 정한 기본 |
  |---|---|---|
  | 판 고르기 | `DEFAULT_VERSIONING_CLASS` | 질의 파라미터 버저닝으로 지정(`QueryParameterVersioning`) |
  | 직렬화 | `serializer_class`와 `get_serializer_class()` | 모델과 QuerySet을 JSON·XML로 인코딩 가능한 파이썬 타입으로 |
  | 라우팅과 메서드 배치 | 클래스 기반 뷰 | **한 엔드포인트의 모든 HTTP 메서드를 클래스 하나에** 두게 강제 |
  | 페이지네이션 | `DEFAULT_PAGINATION_CLASS`·`PAGE_SIZE` | 페이지 번호 방식, 한 쪽에 세 항목 |
  | 속도 제한 | `DEFAULT_THROTTLE_CLASSES`·`DEFAULT_THROTTLE_RATES` | 익명 클라이언트에 분당 1,000 |
  | 인증 | `DEFAULT_AUTHENTICATION_CLASSES` | 부속 패키지의 JWT 인증 클래스 |
  | 권한 | `permission_classes`와 `get_permissions()` | 뷰 단위로, 메서드별 면제는 손으로 |
  | 오류 로깅 | (설정 없음) | **예외가 일으킨 응답만 로그로 남긴다** |

  - 마지막 줄이 이 표에서 가장 값있는 항목이다 — 저자들이 400(Bad Request) 같은 애플리케이션
    오류를 두고 **DRF가 기본적으로 로그를 남기지 않는다**고 적고, 그 이유를 **DRF가 일으켜진
    예외로 생성된 응답에 대해서만 로그를 만들기 때문**이라고 단다 (5장, p.171).[^dynowski2025]
    **곧 프레임워크의 기본값 하나가 관측 가능성의 구멍을 만든다.**
  - **DRF의 클래스 기반 뷰가 한 엔드포인트의 모든 HTTP 메서드를 클래스 하나에 요구한다**는 것도
    설계자가 고르지 않은 구조다 (5장, p.170).[^dynowski2025] 자원 하나에 메서드 여럿을 두는 RMM
    레벨 2의 배치가 **프레임워크에서는 클래스 하나라는 형태로 나타난다.**
- **저자들은 Update 구현을 일부러 뺐다** — **Create와 비슷하지만 길어서 이 절에 넣지 않았고, 책의
  코드 저장소에 있다**고 적는다 (5장, p.168).[^dynowski2025] 그 저장소는 이 스냅샷에 없다.

## 엔드포인트 이름을 실제로 정할 때

- 출발점이 2장의 두 개념이다 — **API 언어와 이름 짓기**이고, **고른 언어는 미국 영어이며 그
  철자법을 따른다** (5장 §"API Endpoints", p.165).[^dynowski2025] 그 규약의 정본은
  [API 이름과 버저닝](api-naming-and-versioning.md)이다.
- WFS의 엔드포인트 여섯과 각각이 맡는 일 (5장, pp.165–166):[^dynowski2025]
  - `/api/cities` — 일기 예보를 얻을 수 있는 모든 도시를 목록으로 낸다.
  - `/api/cities/<uuid>` — uuid로 식별되는 도시 자원 하나를 돌려준다.
  - `/api/forecasts` — 주어진 도시의 일기 예보를 준다.
  - `/api/geocoding` — 도시 이름을 지리 좌표로, 또 그 반대로 바꾼다.
  - `/api/history` — 도시의 과거 날씨 데이터를 준다.
  - `/api/seed` — WFS 데이터베이스를 날씨 데이터로 채운다.
- **이름마다 판단이 붙어 있다** (5장, p.166).[^dynowski2025]
  - **`cities`는 복수다.** 그리고 **uuid가 부모 컬렉션 `cities/uuid` 안에서 도시 자원을
    식별한다**(그 엔드포인트가 개별 도시 객체를 관리한다).
  - **`history`는 단수로 골랐다.** 이유가 문법이다 — **history는 셀 수 있기도 하고 없기도 하며
    복수형이 histories인데**, 저자들은 **개별 도시의 날씨 이력을 가리키려고 단수형을 골랐다.**
    `histories`로 지었다면 **주어진 도시에 여러 날씨 이력이 있다는 뜻이 되어 상식에 어긋난다.**
  - **`forecasts`는 흔한 어법을 거슬러 복수로 골랐다.** 미국 영어는 **weather forecast라는
    구를 더 흔히 쓰지만**, 단수 `forecast`로 가면 **API가 하루치 예보만 준다는 뜻이 된다.**
    그래서 **앞으로 여러 날의 예보를 얻을 수 있음을 나타내려고 복수를 골랐다.**
  - 곧 이 셋은 **같은 규칙에서 나온 것이 아니라 자원이 실제로 몇 개인가를 각각 따진 결과**다.
    [API 이름과 버저닝](api-naming-and-versioning.md)의 "단수인가 복수인가는 스타일이 정한다"와
    "복수형의 예외" 절이 그 규칙 쪽이고, **이 절은 그 규칙을 한 API에 적용한 기록이다.**

## 중첩하지 않기로 한 이유 셋

- 저자들이 스스로 반론을 세운다 — **왜 `forecast`와 `history` 엔드포인트를 `cities` 아래에
  두지 않는가**(`cities/uuid/forecast`와 `cities/uuid/history`) (5장, p.166).[^dynowski2025]
  이유 셋이 답이다.
  - **① 그렇게 하면 예보가 주어진 도시 하나에 대해서만 반환되고, 여러 도시의 예보를 한꺼번에
    가져오는 시나리오를 미리 막는다.**
  - **② 일기 예보와 이력은 서로 다른 목적에 봉사한다.**
  - **③ 엔드포인트를 평탄하게 유지하면(중첩을 피하면) 일관성과 사용의 편의와 캐싱으로
    이어진다 — 그것들이 바뀔 가능성이 더 낮기 때문이다.**
- **셋째가 이 절의 핵심이다** — 중첩은 자원 사이의 관계를 URL에 새기는 일이고, **관계가 바뀌면
  URL이 바뀐다.** 평탄한 URL이 캐싱에 유리한 것은 **덜 바뀌기 때문**이다. 같은 논리가 위
  [REST 아키텍처 스타일의 제약과 성숙도](rest-architectural-style-and-maturity.md)의 제약
  3(캐시 가능한 자원)에서 값을 매기는 자리다.

## 판을 어디에 두었는가

- 엔드포인트 목록만 보면 **API가 판을 전혀 노출하지 않는 것처럼 보이는데**, 그것은 **질의
  파라미터 버저닝을 쓰기 때문**이다(`/api/cities?version=v1`). **명시하지 않으면 v1과
  통신한다고 가정한다**(저자들이 정한 기본 판) (5장 §"API Versioning",
  p.166).[^dynowski2025]
- 그 결정이 설정에서 넷으로 나뉜다 (5장, p.167):[^dynowski2025]
  - **`DEFAULT_VERSIONING_CLASS`** — 질의 파라미터 버저닝을 켠다.
  - **`DEFAULT_VERSION`** — 기본 판을 v1로 정한다.
  - **`ALLOWED_VERSIONS`** — 서버가 지원하는 판들의 튜플(v1과 v2).
  - **`VERSION_PARAM`** — 버저닝에 쓰는 질의 파라미터의 이름.
- **판이 직렬화기를 고른다** — 뷰의 `get_serializer_class()`가 **요청에 실린 API 판에 따라
  직렬화기를 맞춘다.** 요청의 판이 기본 판(v1)과 맞으면 `CitySerializer`를 돌려주고, 아니면
  **부모 클래스의 구현으로 돌아간다** (5장, p.167).[^dynowski2025]
  - 곧 **판 분기의 단위가 엔드포인트가 아니라 직렬화기**다. 판을 어디에 둘 것인가의 선택지
    넷(URI·헤더·질의 파라미터·미디어 타입)과 그 절충은
    [API 이름과 버저닝](api-naming-and-versioning.md)이 갖고, **이 절이 더하는 것은 고른 뒤에
    코드에서 무엇이 갈리는가**다.

## CRUD라는 낱말과 네 자리의 대응

- 낱말의 유래 — **CRUD라는 용어는 1983년으로 거슬러 올라가 영속 저장소와 그 위에서 수행할 수
  있는 네 작업(Create·Read·Update·Delete)의 맥락에서 나타난다. 그 뒤로 데이터베이스에서 API와
  UI로 채택됐다** (5장 §"CRUD", p.167).[^dynowski2025] 저자들이 각주에 대는 출처가 **제임스
  마틴의 *Managing the Data Base Environment*(Prentice Hall, 1983) 381쪽**이다 (5장, p.167 각주
  17).[^dynowski2025] 이 KB에 그 원전은 없다.
- 표 5-3이 같은 네 작업이 세 자리에서 어떤 낱말이 되는지를 보인다 (5장,
  p.168):[^dynowski2025]

  | CRUD 작업 | SQL | HTTP | UI |
  |---|---|---|---|
  | Create | `INSERT` | `POST` | Add |
  | Read | `SELECT` | `GET` | View, Retrieve, Search |
  | Update | `UPDATE` | `PATCH`, `PUT` | Edit |
  | Delete | `DELETE` | `DELETE` | Remove |

  - **넷 중 Update만 HTTP 쪽이 둘이다.** 이 책은 그 둘을 가르지 않고 나란히 적는다. **무엇이
    둘을 가르는가는 이 책이 아니라 RFC 9110이 답한다** — `PUT`은 대상 자원의 상태를 **주어진
    표현으로 대치**하고, `PATCH`는 부분 수정이다.
    [POST와 PUT](../concepts/http-post-and-put.md)이 그 규범을 갖는다.
  - **같은 CRUD 다섯을 네 API 스타일이 어떻게 이름 짓는가**의 대응표 넷은
    [API 이름과 버저닝](api-naming-and-versioning.md)에 이미 있다. **이 표는 축이 다르다** —
    그쪽은 스타일 사이의 대응이고 이쪽은 **저장소와 프로토콜과 화면 사이의 대응**이다.

## 멱등과 안전과 캐시 가능

- 목차에 없는 곁글 하나가 세 성질을 규정한다 (5장 곁글 §"HTTP Idempotency, Safety, and
  Caching", pp.168–169).[^dynowski2025] **HTTP 메서드는 멱등성·안전성·캐싱이라는 세 성질로
  분류할 수 있다.**
  - **멱등(idempotent) 메서드는 한 번 불리든 여러 번 불리든 서버에 같은 효과를 낸다.** 저자들이
    드는 예가 DELETE다 — **처음 DELETE 요청에 서버가 200(OK)으로 답하고 같은 자원에 대한 이후의
    DELETE 요청은 404(Not Found)를 돌려주는데**, 그래도 멱등인 것은 **멱등성이 서버의 상태만
    고려하기 때문**이다 (5장, p.168).[^dynowski2025]
  - **안전(safe)하다는 것은 서버의 상태를 바꾸지 않는다는 뜻**이다. **POST는 새 자원을 만들므로
    안전하지 않다.** 그러나 **안전한 메서드가 반드시 읽기 전용이어야 하는 것은 아니다** —
    자원을 읽는 일도 **로깅이나 요청의 속도 제한 같은 부작용을 서버에 일으킬 수 있고**,
    **클라이언트가 그 부작용을 일으키지 않는 한 그 메서드는 안전한 것으로 친다** (5장,
    p.168).[^dynowski2025]
  - 저자들이 그 모호함의 출처를 짚는다 — **HTTP의 멱등성과 안전성은 클라이언트 요청의 의도된
    효과로 정의된다. 그래서 안전한 메서드(GET)나 멱등한 메서드(PUT)도 클라이언트에게 최종
    결과가 의도대로인 한 서버에 부작용을 일으킬 수 있다. 이 정의의 모호함은 HTTP 명세가 작업의
    주 효과와 부작용을 구분하지 않기 때문에 생긴다** (5장, p.168).[^dynowski2025]
  - **캐싱은 기존 응답을 이후 요청을 충족하는 데 쓸 수 있는 조건을 서술하는 용어**이고,
    **응답 시간과 네트워크 대역폭 소비를 줄이는 데 쓰이며**, **응답의 저장·회수·삭제를 통제하는
    캐시(로컬 또는 원격 저장소)를 통해 일어난다** (5장, p.169).[^dynowski2025]
- 표 5-4가 표준 메서드 아홉을 세 성질로 가른다 (5장, p.169):[^dynowski2025]

  | 메서드 | 멱등 | 안전 | 캐시 가능 |
  |---|---|---|---|
  | `GET` | 예 | 예 | 예 |
  | `HEAD` | 예 | 예 | 예 |
  | `POST` | 아니오 | 아니오 | 아니오 |
  | `PUT` | 예 | 아니오 | 아니오 |
  | `DELETE` | 예 | 아니오 | 아니오 |
  | `CONNECT` | 아니오 | 아니오 | 아니오 |
  | `OPTIONS` | 예 | 예 | 아니오 |
  | `TRACE` | 예 | 예 | 아니오 |
  | `PATCH` | 아니오 | 아니오 | 아니오 |

  - 표에 각주 둘이 달린다. 하나는 **캐싱이 흔히 읽기 작업에 적용되고 상태를 바꾸는 쓰기
    작업에는 거의 적용될 수 없다**는 것과 **POST는 서버가 응답에 캐시 제어 헤더를 명시적으로
    줄 때만 캐시 가능할 수 있다**는 것이다. 다른 하나는 **API 개발자가 강제하지 않으면 멱등성과
    안전성과 캐시 가능성이 보장되지 않는다**는 것이다 (5장, p.169).[^dynowski2025]

## 그 표가 RFC의 규범과 갈리는 자리

- **이 KB에 같은 분포를 원전으로 갖는 페이지가 있다** —
  [안전·멱등·캐시 가능 메서드](../concepts/http-safe-idempotent-and-cacheable-methods.md)이고
  RFC 9110 §9.2.1–9.2.3에서 온다. **두 표를 맞대면 어긋나는 자리가 둘이다.**
  - **① `PATCH`가 이 책의 표에는 있고 RFC 9110에는 없다.** `PATCH`는 RFC 9110이 정의하는
    메서드가 아니므로 그 표에 자리가 없다. **이 책의 `PATCH` 행은 이 KB가 다른 자리에 갖지 않은
    정보**이고, 출처가 어디인지는 이 책이 밝히지 않는다. #hypothesis
  - **② `POST`의 캐시 가능성을 이 책은 본문에서 "아니오"로, 각주에서 조건부로 적는다.** RFC
    9110의 규범은 **조건부로 그렇다**이고 조건이 둘이다 — **명시적 신선도 정보와, 값이 POST의
    대상 URI와 같은 `Content-Location` 헤더 필드**다. **이 책의 각주는 앞 조건만 말하고 뒤
    조건을 말하지 않는다.** 곧 **이 책이 좁다.**
  - **모순으로 세우지 않았다.** 어긋남의 성격이 **규범 대 요약**이고, 이 책의 표는 실무용
    분류표이지 규범 선언이 아니다. **RFC 9110 쪽 페이지는 고치지 않았다** — 이 책의 요약을 그
    페이지에 얹으면 그 페이지가 "지금 무엇이 규범인가"에 답하지 못하게 된다.
- **한 가지 더** — 이 책의 멱등 설명이 드는 GET 예("몇 번을 회수하든 같은 데이터를 돌려준다")는
  **응답의 동일성**을 말하는데, RFC 9110의 멱등 정의는 **서버에 대한 의도된 효과**를 말한다.
  그리고 이 책 자신이 앞에서 **동적 자원은 개별 클라이언트에 맞춰진다**고 적었다(같은 장 p.152).
  **곧 그 예는 이 책 안에서도 좁다.** 정의 자체는 저자들이 바로 다음 문단에서 "멱등성은 서버의
  상태만 고려한다"로 바로잡으므로 모순이 아니라 **예시의 부정확**으로 읽었다. #hypothesis

## 응답을 부분으로 깎는다

- Read 구현의 목표가 명시된다 — **이 구현의 최종 목표는 API가 부분 응답(partial response)을
  반환할 수 있게 하는 것**이고, **부분 응답은 자원 전체가 아니라 그 부분집합만 돌려준다**
  (5장 §Read, p.173).[^dynowski2025]
  - **저자들이 각주에서 그것이 어느 스타일의 것인가를 밝힌다** — **부분 응답은 GraphQL의 가장
    구별되는 기능**이고, **GraphQL은 그것을 설계상 허용한다**(6장에서 다룬다) (5장, p.173 각주
    21과 p.174 각주 22).[^dynowski2025] 곧 **REST에서 부분 응답은 질의 파라미터로 덧붙이는
    것이고 다른 스타일에서는 스타일 자체의 성질**이다. 그 비교는 [GraphQL](../concepts/graphql.md)이
    맡는다.
- 질의 파라미터 셋이 그 일을 한다 (5장, p.175):[^dynowski2025]
  - **필터링·검색·정렬·부분 응답은 API 서버가 주는 흔한 기능이다. 필터링은 클라이언트가 데이터를
    자기 필요에 맞게 줄이게 하고, 검색은 특정한 일치로 데이터를 찾게 하는 필터링의 한 형태이며,
    정렬은 반환된 데이터의 순서를 바꾸게 한다.**
  - **REST API의 통상적 접근은 필터링 의도를 표현하는 질의 파라미터를 더하는 것**이고, 이 API는
    **`fields`로 반환 데이터를 줄이고, `search`로 특정 데이터를 찾고, `sort`로 순서를 바꾼다.**
    검색 파라미터는 **모델 필드 이름을 접미로 붙인 `search_` 꼴**이다(`search_region` 같은).
  - **`include_deleted`가 소프트 삭제된 자원을 응답에 포함할지를 통제한다** (5장,
    p.174).[^dynowski2025]
- **이 셋의 패턴 쪽 정본은 이 페이지가 아니다** —
  [API 목록 조회 패턴](api-list-query-patterns.md)이 필터 문자열과 필드 기반 필터링과 응답
  모양 깎기를 갖는다. **여기 담은 것은 REST에서 그것이 질의 파라미터라는 형태로 굳는다는 것과
  파라미터 이름의 실제 선택**이다.

## 페이지네이션의 기본값

- 왜 필요한가 — **페이지네이션은 API 서버가 한 번에 클라이언트에 반환하는 항목 수를 제한하게
  한다. 더 큰 데이터셋에 필요하다. 데이터셋을 작은 덩어리로 쪼개면 API 성능이 좋아지고
  메모리 사용량이 줄지만(클라이언트와 서버 양쪽에서), 대신 API 클라이언트가 페이지된 데이터를
  이해하고 파싱하고 다뤄야 하므로 페이지된 요청들 사이의 데이터 불일치 위험이 올라간다** (5장
  §Pagination, p.178).[^dynowski2025]
- **고른 것은 오프셋 기반**이다 (5장, p.178).[^dynowski2025] 응답에 실리는 필드 넷이 무엇을
  하는지가 적힌다 (5장, pp.178–179):[^dynowski2025]
  - **`count`는 이용 가능한 전체 레코드 수를 알려 클라이언트가 데이터셋의 크기를 알게 한다.**
  - **`next`와 `previous`는 다음 쪽과 이전 쪽을 가리키는 URL을 담는다.**
  - **`page_size`가 쪽마다 반환되는 항목 수를 통제한다.**
  - **`results` 배열이 실제 데이터 항목을 담는다.**
- 기본값이 둘이다 — **`PAGE_SIZE` 설정이 쪽마다 보이는 항목 수를 정하고**, 구현에서 **기본
  페이지 크기는 세 항목이며 같은 이름의 질의 파라미터로 통제할 수 있다** (5장,
  pp.179–180).[^dynowski2025]
- **오프셋 기반이 커서 기반에 견주어 무엇을 잃는가**(삭제와 삽입이 오프셋을 어긋나게 한다)는
  이 책의 2장이 이미 다뤘고 그 자리는 [API 목록 조회 패턴](api-list-query-patterns.md)이다.
  **저자들은 REST 구현에서 둘 중 오프셋을 골랐고 그 선택의 근거를 이 절에 적지 않는다.**

## 삭제를 질의 파라미터로 고른다

- 이 API는 **소프트 삭제 패턴을 구현한다** (5장 §Delete, p.175).[^dynowski2025]
- **삭제의 종류를 질의 파라미터가 고른다** — **`soft_delete` 질의 파라미터가 자원을 소프트
  삭제(감추기)할지 하드 삭제(제거)할지를 통제한다** (5장, p.176).[^dynowski2025] 구현에서
  **그 파라미터의 기본값은 참**이다 (5장, p.176).[^dynowski2025]
- 상태 코드 배정이 네 갈래다 (5장, p.177):[^dynowski2025]
  - 데이터베이스 읽기가 실패하면 **500(Internal Server Error)**.
  - 자원이 없으면 **404(Not Found)**.
  - **이미 소프트 삭제된 자원을 다시 소프트 삭제하려 하면 412(Precondition Failed)**.
  - 삭제가 성공하면 **200(OK)**과 함께 자원을 돌려준다.
  - **셋째가 이 절에서 유일하게 2장이 말하지 않은 결정이다.** 삭제의 두 종류와 상태 코드
    선택지는 [API 자원 삭제 패턴](api-resource-deletion-patterns.md)이 갖고, **412를 중복 소프트
    삭제에 배정한 것은 이 구현의 결정**이다. 그 코드가 규범에서 무엇을 뜻하는지는
    [클라이언트 오류 상태 코드](../concepts/http-client-error-status-codes.md)와
    [조건부 요청과 선행 조건](../concepts/http-conditional-requests-and-preconditions.md)에 있다.

## 속도 제한을 스로틀링이라 부른다

- **DRF는 API 속도 제한 도구를 스로틀링(throttling)이라는 다른 이름으로 제공한다** (5장
  §"Rate Limiting", p.180).[^dynowski2025] **같은 것에 프레임워크가 다른 이름을 붙이는 자리**다.
- 사업 쪽 동기가 함께 적힌다 — **속도 제한은 흔히 무료 사용자를 유료 요금제로 밀어 올리는 데
  쓰인다. 회사들이 내놓는 흔한 전략은 공개 API의 전체 능력을 노출하되 초·분·시간·일 같은 단위
  시간당 요청 수를 제한하는 것**이고, **그 목표 가운데 하나가 사용자로 하여금 보통 더 높은 사용
  한도를 주는 유료 구독으로 올라가게 부추기는 것**이다 (5장, p.180).[^dynowski2025]
  - 이것은 **속도 제한을 보호 장치가 아니라 가격 정책의 손잡이로 쓰는 읽기**다.
    [API 요청 수명 패턴](api-request-lifecycle-patterns.md)의 속도 제한 절은 남용 방지와 공정
    사용 쪽을 담는다. **둘은 같은 기제의 두 용도**다.
- 설정과 그 뜻 (5장, p.181):[^dynowski2025]
  - **`DEFAULT_THROTTLE_CLASSES`에 익명 클라이언트의 요청을 제한하는 클래스를 넣는다.**
  - **`DEFAULT_THROTTLE_RATES`가 익명 클라이언트의 제한율을 정의한다** — 예제에서 **분당 1,000
    요청**이다.
  - **클라이언트는 IP 주소로 유일하게 식별된다.**
- **그 식별이 깨지는 자리가 각주에 있다** — **프록시나 로드 밸런서가 클라이언트의 IP 주소를
  감출 수 있다.** 그런 경우 **지속 쿠키나 세션 쿠키를 써서 서버가 생성한 클라이언트 UUID를
  브라우저에 저장할 수 있고**, 클라이언트가 다음 요청을 낼 때 **그 쿠키가 서버로 되돌아와
  서버가 IP 주소와 무관하게 클라이언트를 알아본다** (5장, p.181 각주 23).[^dynowski2025]
  - 중개자가 원래 클라이언트 정보를 감추거나 바꾸는 일 자체의 규범 쪽 자리는
    [HTTP 중개자](../concepts/http-intermediaries.md)와
    [메시지 전달과 홉 단위 필드](../concepts/http-message-forwarding-and-hop-by-hop-fields.md)다.

## 서버 쪽 캐싱이 되사는 것

- 무엇을 구현하는가 — **멱등하고 안전한 HTTP GET 메서드로 데이터를 내주는 엔드포인트에 서버 쪽
  캐싱**을 건다 (5장 §Caching, p.181).[^dynowski2025]
- 기제 — **캐싱은 연속된 API 요청을 캐시 저장소(보통 인메모리 저장소)에 저장함으로써 API의
  응답성을 높인다. 최초 클라이언트 요청은 캐시와 백엔드와 데이터베이스라는 체계 계층을 타고
  퍼져 응답을 만들고, 같은 요청에 대한 이후 응답은 체계를 다시 타지 않고 캐시에서 나온다**
  (5장, p.181).[^dynowski2025]
- **대가가 한 문장으로 적힌다** — **캐싱의 단점은 데이터가 일정 시간 낡은 채로 있다는 것이고,
  그것이 데이터의 신선도를 보장하지 못할 수 있다** (5장, p.181).[^dynowski2025]
- 설정에서 정해지는 것 (5장, p.182):[^dynowski2025]
  - **캐시 백엔드로 레디스를 쓴다고 지정하고, 나머지 옵션이 레디스 서비스의 위치와 데이터베이스
    번호를 정한다.** 캐시 설정에 `TIMEOUT` 값도 들어 있다.
  - **그리고 엔드포인트를 다루는 메서드에 데코레이터를 걸어 응답을 30초 동안 캐시한다.**
  - 곧 **유효 기간이 두 자리에 있다** — 캐시 백엔드 전체의 설정값과 엔드포인트 하나의 데코레이터
    인자다. **저자들은 둘의 관계를 적지 않는다.** #hypothesis
- **이 절은 서버 쪽만 담는다.** 클라이언트 쪽 캐싱과 무효화(TTL·ETag·Last-Modified)는 2장이
  다뤘고 이 KB에서는 [분산 체계에서의 캐싱](../concepts/caching-in-distributed-systems.md)과
  [검증자 ETag와 Last-Modified](../concepts/http-validators-etag-and-last-modified.md)가 갖는다.

## 방어적 프로그래밍

- 목차에 없는 곁글 하나가 구현 절들을 관통하는 순서에 이름을 붙인다 (5장 곁글 §"Defensive
  Programming", p.172).[^dynowski2025]
  - 관찰이 먼저다 — **각 코드 블록이 나타내는 단계의 순서를 보라. 흐름은 요청의 검증에서
    시작해 자원 조작을 거쳐 자원 회수로 끝나고, 그 모든 단계에 걸쳐 프로그램은 각 단계에
    맞게 오류를 처리한다.**
  - 규정 — **이 접근을 방어적 프로그래밍(defensive programming)이라 부르며, 주어진 입력이
    유효하지 않거나 악의적일 수 있다고(그래서 소프트웨어가 오작동할 수 있다고) 예상한다. 그런
    시나리오에 대비함으로써 방어적 프로그래밍은 프로그램이 유효하지 않은 입력을 다룰 수 있고
    소프트웨어가 올바로 작동함을 보장한다.**
  - **검증의 층이 넷이다** — **정제(sanitization)와 입력 검증과 인증과 인가**다.
  - 절충 — **방어적 프로그래밍으로 개발자는 유효하지 않은 입력이 일으키는 예상 밖 행동의 위험을
    줄이고 보안을 높이고 체계 신뢰성을 개선할 수 있다. 그러나 이 접근의 아래쪽은 복잡도를 올릴
    수 있다는 것이다.**
- **넷 중 앞 둘의 정본은 2장이다** — [API 보안 패턴](api-security-patterns.md)의 정제와 검증
  절이 그 구별과 "입력을 신뢰하지 말라"는 조문을 갖는다. **이 곁글이 더하는 것은 그 넷이 한
  요청 처리 안에서 놓이는 순서**다. 같은 태도를 프로그래밍 실천 쪽에서 다루는 자리는
  [단정적 프로그래밍](../concepts/assertive-programming.md)이다.

## API 트래픽의 비중과 보안의 자리

- 관찰 하나로 절을 연다 — **2024년 클라우드플레어가 낸 Application Security Report가 "동적
  (캐시 불가) 트래픽의 60%가 API 관련"이라고 적는다**. 저자들은 그 성장을 **애플리케이션과
  데이터베이스와 IoT와 다른 체계 사이의 주 통신 채널로 API를 채택한 결과**로 읽는다 (5장
  §Security, p.182).[^dynowski2025] 그 보고서는 이 KB가 확인한 원전이 아니다.
- **그런데 문제가 남는다** — **API는 적절한 목록화나 인증이나 감사 없이 프로덕션에 들어갈 수
  있고 그래서 잠재적 보안 위험에 노출된다. 이것은 API 우선 접근(구현 전에 API 명세를 만드는
  것)과 시프트 레프트 실천에도 불구하고 여전히 일어날 수 있다** (5장, p.182).[^dynowski2025]
  - **시프트 레프트는 테스트·보안 조치·QA 같은 개발 실천을 SDLC나 API 수명 주기의 이른
    단계에 통합하는 접근**이다 (5장, p.182).[^dynowski2025] 그 둘의 정본은
    [API 수명 주기](api-lifecycle.md)의 설계·배포 절이다.
- 수단의 목록 (5장, p.182):[^dynowski2025]
  - **TLS를 넘어 REST API는 흔히 업계 표준 인증과 인가로 보호된다.**
  - **JWT(JSON Web Token)는 인증과 인가를 함께 떠받치는 수단 하나**이고 **두 당사자 사이에
    클레임의 표현을 옮기게 해 준다.**
  - **OAuth 2.0(과 OAuth 2.1)은 인가 전용 프로토콜**이고 **웹·데스크톱·모바일 애플리케이션을
    위한 특정 인가 흐름을 준다.**
  - **OIDC(OpenID Connect)는 OAuth 2.0 틀 위에 지어진 또 다른 인증 프로토콜**이고 **사용자
    정보와 신원 검증을 더해 신원 계층을 얹는다. 흔히 단일 사인온 애플리케이션에 쓰인다.**
  - **보안을 높이려고 조직들은 문서화에 OpenAPI, 중앙 집중 통제에 API 관리 플랫폼, 그리고 감사
    실천 같은 도구를 쓴다.**
  - **이 넷의 규정을 이 KB가 새로 얻는 자리는 아니다** — OAuth와 OIDC와 SSO의 배치는
    [서비스 사이 인증과 인가](../concepts/service-to-service-authentication-and-authorization.md)와
    [API 보안 패턴](api-security-patterns.md)이 갖는다. **이 절이 더하는 것은 REST API를
    보호하는 수단의 목록이 그 넷으로 짜인다는 것과 API 트래픽 비중의 수치다.**

## JWT의 세 부분

- 구조 규정 — **JWT는 세 절의 이어붙임이고 각각은 Base64url로 인코딩된 문자열이며, 헤더와
  적재물과 서명이 마침표(".")로 갈린다** (5장 §"JSON Web Token", p.183).[^dynowski2025]
- 각 절이 무엇을 담는가 (5장, p.183):[^dynowski2025]
  - **헤더와 적재물 절은 Base64url로 인코딩된 JSON 객체를 담고, 그 객체는 클레임(토큰에 대한
    정보 조각)과 데이터를 담는다.**
  - **마지막 절은 HMAC 서명이고, Base64url로 인코딩된 헤더와 적재물을 마침표(".")로 이어붙인
    문자열과 비밀(secret)로부터 256비트 길이의 SHA(Secure Hash Algorithm) 함수를 써서
    만든다.**
- 표 5-5가 인코딩된 토큰을 풀어 셋을 나란히 놓는다 (5장, p.183):[^dynowski2025]

  | 헤더 | 적재물 | 서명 |
  |---|---|---|
  | `{"alg": "HS256", "typ": "JWT"}` | `{"sub": "1234567890", "name": "John Doe", "iat": 1516239022}` | `HMAC_SHA256(secret, base64url(header) + "." + base64url(payload))` |

  - **서명 칸이 값이 아니라 식이라는 것이 이 표의 요점**이다 — 서명은 앞 두 칸에서 계산된다.
- **경고 둘이 곁주로 붙는다** (5장, p.183):[^dynowski2025]
  - **토큰을 질의 파라미터로 보내면 브라우저 이력이나 서버 로그에 노출될 수 있다.**
  - **jwt.io 같은 사이트로 JWT를 디코딩할 수 있으나, 인터넷에 사적 정보를 붙여 넣을 때는
    경계하고 믿고 검증된 도구만 쓰라. 그러지 않으면 민감한 정보를 인가되지 않은 제3자에게
    노출할 위험이 있다.**
- **같은 구조를 이 KB가 이미 갖고 있다** —
  [서비스 사이 인증과 인가](../concepts/service-to-service-authentication-and-authorization.md)의
  JWT 절들이 2021년 마이크로서비스 실무서에서 헤더·적재물·서명 셋과 공개 클레임(`exp` 같은)을
  가져왔다. **겹치지 않게 이 페이지가 더하는 것만 적었다** — **Base64url이라는 인코딩의 이름과,
  서명이 어떤 식으로 계산되는가와, 질의 파라미터 노출 경고**다. 클레임의 의미론과 키 관리와
  만료 시각을 정하기 어려운 경우는 **그쪽이 훨씬 두껍게 갖고 있으므로 여기 되풀이하지 않았다.**

## JWT의 성질 다섯

- 저자들이 이점 다섯을 이름으로 센다 (5장, pp.184–185).[^dynowski2025]
  - **안전하다(Secure)** — **JWT의 무결성과 진정성을 보장하려고 암호 알고리즘으로 서명을
    생성한다. 그 알고리즘은 HMAC 같은 대칭일 수도 있고 비공개-공개 키 쌍을 쓰는 RSA나
    ECDSA 같은 비대칭일 수도 있다.** 그리고 **JWT는 `"exp"`(만료) 클레임 같은 클레임을 담고,
    그 클레임은 토큰이 더 이상 유효하지 않게 되는 시각을 지정한다. 만료 시각에 이르면 발급
    체계가 명시적으로 갱신하지 않는 한 그 토큰은 접근에 쓰일 수 없다.**
  - **무상태다(Stateless)** — **JWT는 사용자 데이터를 보관하는 세션 저장소에 기대지 않는다. 이
    성질이 JWT를 크로스 도메인 통신에 API를 쓰는 분산 체계의 인증에 알맞은 선택으로 만든다.**
    - **그런데 저자들이 곧바로 범위를 좁힌다** — **무상태성은 JWT 인증 용례에만 한정된다.
      허용 목록과 거부 목록을 만드는 토큰 접근 통제나 토큰 폐기 같은 기능을 구현할 때는
      저장소 사용을 피할 수 없다** (5장, p.184).[^dynowski2025] **이 한 줄이 "무상태"라는 말을
      마케팅이 아니라 조건부 진술로 만든다.**
  - **자기 완결적이다(Self-contained)** — **JWT는 사용자 ID·역할·권한 같은 클레임을 담아
    서버가 유효한 토큰을 인증의 증거로 취급하게 하고 잦은 데이터베이스 조회의 필요를 줄인다.**
  - **이식 가능하다(Portable)** — **JWT 인코딩은 URL에 안전하고 HTTP 같은 텍스트 기반
    프로토콜과 호환된다. JWT는 HTTP 요청의 질의 파라미터나 본문이나 헤더 안에 실려 보낼 수
    있다.** 저자들이 그 근거로 **URL에 쓰기 안전한 "unreserved characters"가 있다**는 것을
    각주에 단다 (5장, p.184 각주 24).[^dynowski2025]
    - **위 [JWT의 세 부분](#jwt의-세-부분)의 경고와 나란히 읽어야 하는 항목이다** — 질의
      파라미터로 보낼 수 **있다**는 것과 보내도 **된다**는 것이 다르다. 저자들은 둘을 같은
      절에 적고 연결하지 않는다.
  - **맞춤 가능하다(Customizable)** — **JWT는 사용자 역할이나 토큰 만료 시각 같은 클레임을
    담고 그것을 애플리케이션의 필요에 맞게 맞출 수 있다.**
- 구현 쪽 결정 하나 — 저자들은 **DRF와 호환되는 파이썬 패키지 `djangorestframework-simplejwt`를
  찾아 썼고, 그러지 않았다면 JWT 기능을 처음부터 구현해야 했을 것**이라고 적는다 (5장,
  p.184).[^dynowski2025] **부속 패키지를 쓰기로 한 결정이 곧 토큰 클래스와 클레임 이름의 결정**이
  된다 — 설정에서 **인증 클래스로 그 패키지의 JWT 인증을 지정하고, 접근 토큰 클래스를 정하고,
  적재물에서 사용자 ID를 나르는 키 이름을 바꾼다** (5장, p.185).[^dynowski2025]
- 토큰을 관리하는 엔드포인트가 넷이다 — **얻기·갱신·폐기·검증**이다 (5장,
  p.185).[^dynowski2025]

## 짧은 수명 토큰과 남는 위험

- 토큰 둘의 구별 — **응답은 접근 토큰(access token)과 갱신 토큰(refresh token)을 함께 담는다.
  접근 토큰은 보호된 자원에 접근을 허락하고, 갱신 토큰은 현재 접근 토큰이 만료될 때 새 접근
  토큰을 얻는다** (5장, p.186).[^dynowski2025]
- 그것을 어디에 싣는가 — **접근 토큰을 얻으면 그 존재를 요구하는 API 엔드포인트와 상호작용할
  수 있고, 보통 요청의 헤더에 `"Authorization": "Bearer ACCESS_TOKEN"` 꼴의 인가 줄을 담도록
  요청을 구성해야 한다** (5장, p.186).[^dynowski2025] 그 헤더 자체의 문법과 `Bearer` 같은
  스킴이 꽂히는 자리의 규범은 [HTTP 인증 틀](../concepts/http-authentication-framework.md)과
  [HTTP 인증 필드](../concepts/http-authentication-fields.md)에 있다.
- **그리고 저자들이 이 절의 진짜 문제를 적는다** (5장, p.186):[^dynowski2025]
  - **이 경우 JWT는 API와 상호작용하는 사용자의 신원을 확인하는 데 쓰인다. 토큰 자체만 보아서는
    진짜 사용자와 가로챈 토큰을 쓰는 해커를 구별할 방법이 없다.**
  - **이 문제를 다루는 한 방법은 토큰의 유효 시간을 줄여 짧은 수명 접근 토큰(short-lived
    access token)으로 만드는 것**이고, **이 해법은 새 토큰을 얻는(재생성하는) 대가로 보안을
    높인다.**
  - **그러나 짧은 수명 접근 토큰으로도 위험은 남는다.**
  - **이 유보가 이 절의 결론이다** — 저자들은 대안을 제시하지 않고 위험이 남는다고만 적는다.
    자격 증명의 유효 기간을 좁히는 원칙 쪽은
    [자격 증명과 비밀의 수명 주기](../concepts/credentials-and-secrets-lifecycle.md)에, 토큰을
    어디서 만들 것인가의 배치 선택은
    [서비스 사이 인증과 인가](../concepts/service-to-service-authentication-and-authorization.md)에
    있다.

## 자체 서명 인증서와 CA 서명 인증서

- 곁글 하나가 둘을 가른다 (5장 곁글 §"Self-Signed Versus CA-Signed Certificates",
  p.187).[^dynowski2025]
  - **이 절이 보이는 TLS는 자체 서명 인증서(self-signed certificate)를 쓴다. 자체 서명
    인증서에는 기본 웹 브라우저가 신뢰하지 않는다는 단점이 따른다. 그런 인증서로 암호화된
    웹사이트를 방문하는 것은 사용자가 그 방문(인증서)을 승인할 때만 가능하다.**
  - **어림 규칙은 자체 서명 인증서를 피하라는 것이다. 그러나 내부 테스트나 개발 환경처럼 당사자
    사이의 신뢰가 이미 성립한 특정 시나리오에는 알맞을 수 있다. 프로덕션 환경에는 권장되지
    않으므로, 프로덕션에서 애플리케이션 트래픽을 TLS로 암호화할 때는 검증되고 신뢰받는 CA가
    발급한 인증서를 쓰라** — 흔히 **CA 서명 인증서(CA-signed certificate)**라 부른다.
  - **CA 서명 인증서는 인증서의 신원(주체)을 검증하는 신뢰받는 기관이 발급한다. 그 검증은
    인증서 주체의 신원을 얼마나 확인하는가에 따라 네 범주로 분류된다** (5장, p.187).[^dynowski2025]
    저자들은 그 넷의 이름을 본문에 적지 않고 SSL.com의 글을 각주로 넘긴다 (5장, p.187 각주
    26).[^dynowski2025] 그 글은 이 KB가 확인한 원전이 아니다.
  - **CA 서명 인증서를 얻으려면 인증서의 획득과 갱신을 자동화하는 도구를 주는 무료 Let's
    Encrypt 서비스를 쓸 수 있다. 클라우드 제공자의 관리형 인증서를 쓰거나 검증된 제공자에게서
    인증서를 사는 것도 가능하다** (5장, p.187).[^dynowski2025]
- **신뢰 기점을 누가 정하는가**의 규정은 이 책의 3장이 이미 했고 그 자리는
  [전송 중 데이터와 정지 데이터의 보호](../concepts/securing-data-in-transit-and-at-rest.md)다.
  **이 곁글이 더하는 것은 개발과 프로덕션 사이의 실무 경계**다.

## 문서가 없으면 쓰이지 않는다

- 왜 문서인가 — **API를 직관적으로 만들려고 아무리 노력해도 소비자는 여전히 오해할 수 있다.
  그래서 API 문서가 필요하다. 그러지 않으면 API가 쓰이지 않을 수 있다** (5장 §Documentation,
  p.188).[^dynowski2025]
- 명세의 자리 — **API 명세는 API 제공자와 API 소비자 사이의 계약이다. 제공자는 명세를 써서
  API를 서술하고, 소비자는 명세를 읽어 그 API와 어떻게 일할지 이해한다** (5장,
  p.188).[^dynowski2025]
  - **계약이라는 낱말이 이 KB에서 가리키는 다른 것들과 층이 다르다.**
    [소비자 주도 계약](../concepts/consumer-driven-contracts.md)은 **계약이 실제로 깨졌는지를
    누가 어디서 잡는가**를 묻고, [계약의 스펙트럼](../concepts/contract-spectrum.md)은 **계약을
    얼마나 조일 것인가**를 묻는다. **이 절이 말하는 계약은 그 둘의 앞에 있는 문서 하나**다.

## OpenAPI 명세

- 규정과 위상 — **OpenAPI 명세(OAS, 예전 이름 Swagger)는 HTTP 기반 API를 문서화하는 가장 인기
  있는 도구다. OAS는 YAML이나 JSON 같은 사람이 읽을 수 있는 형식을 써서 API의 명세를 담은 텍스트
  문서를 정의한다** (5장 §"OpenAPI Specification", p.189).[^dynowski2025]
- 도구와 채택 (5장, p.189):[^dynowski2025]
  - **OAS 문서는 ReDoc·Postman·Swagger UI 같은 도구로 상호작용하게 만들 수 있다.**
  - **OAS가 개발자에게 인기 있는 것은 넓은 채택과 도구 지원 때문이다. FastAPI 같은 프레임워크는
    OAS를 기본 문서화 표준으로 삼았다.**
  - **OAS는 동기 API를 서술하는 데 인기 있는 선택이지만 비동기 API 지원은 제한적이다. API가
    비동기로 돈다면 AsyncAPI를 고려하라.**
  - **이 KB에 AsyncAPI의 원전은 없다.** 이벤트 기반 인터페이스의 문서화 선택지 둘은
    [웹 서비스와 REST](../concepts/web-services-and-rest.md)의 OpenAPI 절이 2021년 실무서에서
    가져와 갖고 있다.
- 예제 문서에서 claim이 되는 것은 **필드가 무엇을 하는가**다 (5장,
  pp.190–191):[^dynowski2025]
  - **`openapi` 필드가 이 명세가 쓰는 OpenAPI 판을 표시한다**(예제에서 `3.1.0`).
  - **`info` 필드가 제목·판·설명 같은 API 메타데이터를 갖는다.**
  - **`tags`가 작업들을 묶는 데 쓰인다.**
  - **`paths` 필드가 이용 가능한 엔드포인트와 그 작업들을 정의한다.**
  - **`parameters` 필드가 이용 가능한 질의 파라미터를 서술한다** — 이 API에서는 `version`과
    `fields`와 **동적인 `search_{key}`**다.
  - **`responses` 필드가 가능한 API 응답을 정의한다.**
  - **동적 키를 가진 파라미터가 명세에 어떻게 적히는가가 이 예제에서 값있는 자리다** — 이름을
    `search_{key}`로 두고 설명에서 `{key}`를 실제 필드 이름으로 바꾸라고 적는 방식이다.
    **위 [응답을 부분으로 깎는다](#응답을-부분으로-깎는다)의 `search_` 접미가 명세에서는 이
    형태로 나타난다.**

## 명세를 만드는 세 접근

- **일반적으로 API 명세는 세 접근 가운데 하나로 만들 수 있다** (5장 §"Three Approaches to API
  Specification", p.192).[^dynowski2025]
  - **자동 생성(Autogenerated)** — **명세가 소스 코드에서 자동 생성된다.** 저자들이 쓴 것이
    DRF와 함께 동작하도록 설계된 `drf_spectacular` 라이브러리다. **이 접근은 쓰기 쉬워 매력적
    이지만 단점이 있다 — 자동 생성된 명세는 API의 불완전한 개괄을 주고, 그 빈틈을 메우려면 흔히
    소스 코드를 손으로 조정해야 한다.**
  - **수동(Manual)** — **명세를 "상향식"으로, 곧 처음부터 손으로 쓴다. 이 접근은 완전한 통제와
    맞춤을 주지만 시간이 많이 들고 API의 실제 구현과 어긋나기 쉽다.**
  - **반수동(Semi-manual)** — **혼합 접근이다. 자동 생성된 명세가 API 명세의 초기 모양을 주고
    개발자가 빠진 세부를 손으로 채운다. 수동 접근과 마찬가지로 이 방법도 어긋나기 쉽다.**
- **셋 가운데 둘이 같은 위험을 진다** — 수동과 반수동이 **구현과 어긋난다.** 자동 생성은 그
  위험이 없는 대신 **불완전**하다. 곧 **완전성과 일치는 이 세 접근에서 맞바꿔진다.**
  - 그 맞바꿈을 **검증으로 되사는 쪽**이
    [소비자 주도 계약](../concepts/consumer-driven-contracts.md)이다. 명세가 구현과 어긋났는지를
    사람이 읽어 잡는 대신 **소비자가 적은 기대를 제공자 빌드에서 돌린다.** **저자들은 그 연결을
    적지 않는다.** #hypothesis
  - **명세를 구현보다 먼저 쓰는 쪽**은 이 책의 1장이 API 우선 전략으로 다뤘고 그 자리는
    [API 수명 주기](api-lifecycle.md)의 설계 절이다. **위 세 접근과 그 전략은 다른 축이다** —
    세 접근은 **명세를 무엇으로 만드는가**이고 API 우선은 **언제 만드는가**다. 자동 생성은
    정의상 코드가 먼저이므로 **API 우선과 양립하지 않는다.** #hypothesis
- 저자들이 남은 절에서 **자동 생성과 반수동 둘을 실제로 돌려 보인다** — 라이브러리를 설치해
  장고의 앱 목록에 더하고, OAS를 내주는 엔드포인트 셋을 등록한다. 셋은 **Swagger UI를 내주는
  것과 자동 생성 OAS를 내주는 것과 반수동 OAS를 내주는 것**이고, 마지막 것은 **먼저 자동
  생성한 뒤 손으로 갱신한 정적 파일을 읽어 HTTP 응답으로 돌려준다** (5장,
  pp.192–194).[^dynowski2025]

## 이 페이지가 담지 않는 것

- **코드 자체를 담지 않는다.** 이 장의 예제 스물둘은 장고 설정 사전과 뷰 클래스와 curl 호출과
  그 JSON 응답인데, **그것이 뒷받침하는 claim**(프레임워크가 무엇을 대신 결정하는가, 어떤 상태
  코드를 언제 돌려주는가, 어떤 질의 파라미터가 무엇을 통제하는가)**만 산문으로 옮겼다.** 전권
  코드 펜스 예산 셋은 이 장에서도 쓰지 않았다.
- **패턴 자체를 담지 않는다.** 필터링·페이지네이션·속도 제한·삭제·보안 패턴의 정본은 이 책
  2장에서 온 [API 설계 모범 사례](api-design-best-practices.md) 이하 일곱 페이지다. **여기 있는
  것은 그 패턴을 REST와 한 프레임워크 위에서 굳힐 때 실제로 고른 값들**이다.
- **HTTP 의미론을 담지 않는다.** 상태 코드와 메서드와 헤더의 규범 정본은
  [HTTP 의미론](../synthesis/http-semantics.md) 허브 아래에 있다. 위
  [그 표가 RFC의 규범과 갈리는 자리](#그-표가-rfc의-규범과-갈리는-자리)가 두 층이 만나는 유일한
  절이다.
