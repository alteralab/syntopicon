## 재사용은 삶의 사실이다 — 그리고 부채다

- **모놀리스에서는 물음이 아니었다** — 포매터·계산기·검증기·감사 같은 **업무 도메인 공통 기능**과
  보안·로깅·지표 수집 같은 **인프라 공통 기능**은 대개 여러 컴포넌트에 걸쳐 공유되는데, 대부분의
  모놀리식 아키텍처에서 **코드 재사용은 다시 생각할 거리가 거의 되지 않는다** — 공유 클래스 파일을
  임포트하거나 자동 주입하면 되는 문제다. **분산 아키텍처에서는 복잡해진다** (8장,
  p.220).[^ford2021-hard-parts]
  - **도메인 공통과 인프라 공통을 가르는 이 두 낱말이 같은 책 5장의 가름과 같다.** 그쪽 규정은
    [공통 도메인 컴포넌트 모으기](../concepts/gather-common-domain-components.md)에 있고, 이 장은
    **둘을 다 다룬다** — 아래 [사이드카와 서비스 메시](#사이드카와-서비스-메시)가 인프라 쪽을,
    나머지 셋이 도메인 쪽을 주로 맡는다.
- **현장의 구호가 반대쪽으로 기운다** — 마이크로서비스나 서버리스처럼 고도로 분산된 환경에서는
  아키텍트들이 공유 코드의 양을 줄이려고 **"재사용은 남용이다(reuse is abuse!)"**와 **"아무것도
  공유하지 마라(share nothing!)"** 같은 문구를 내세운다. 유명한 DRY 원칙(Don't repeat yourself)에
  맞서 **WET**(Write every time 또는 Write everything twice)이라는 반대 약어로 맞대응하는 조언을
  하는 아키텍트들도 있다 (8장, p.220).[^ford2021-hard-parts]
  - 그 원칙 쪽의 전문과 이 반대 극의 계보는 [DRY 원칙](../concepts/dry-principle.md)에 있다.
- **그러나 저자들은 그 구호에서 멈추지 않는다** — 개발자가 분산 아키텍처 안의 코드 재사용 양을
  제한하려 애써야 하는 것은 맞지만 **그것은 그럼에도 소프트웨어 개발의 삶의 사실이고 다뤄져야
  한다.** 그래서 이 장이 기법 넷을 세운다 — **코드 복제, 공유 라이브러리, 공유 서비스, 서비스 메시
  안의 사이드카**다 (8장, p.221).[^ford2021-hard-parts]
- **부채 쪽 규정은 이 장 뒤쪽에 온다** — **재사용은 가장 남용된 추상 가운데 하나**인데, 조직의
  일반적 시각이 재사용을 **팀이 지향해야 할 칭찬할 만한 목표**로 보기 때문이다. 재사용에 딸린
  절충을 모두 평가하지 못하면 **아키텍처 안에 심각한 문제**가 생긴다 (8장,
  p.242).[^ford2021-hard-parts] 그 판정의 전문이 아래
  [재사용은 언제 값을 하는가](#재사용은-언제-값을-하는가)다.

## 코드 복제

- **규정** — **코드 복제(code replication)에서는 공유 코드가 각 서비스(더 정확히는 각 서비스의
  원시 코드 저장소)로 복사되어**, 코드 공유 자체를 피한다 (8장, p.221).[^ford2021-hard-parts]
- **계보가 오해에서 시작한다** — 저자들은 이 기법이 **미친 소리처럼 들릴 수 있다**고 적으면서도,
  **마이크로서비스 초창기에 경계 컨텍스트(bounded context) 개념을 둘러싼 혼란과 오해가 많았을 때**
  인기를 얻었고 그것이 **"아무것도 공유하지 않는 아키텍처"를 향한 동력**이었다고 적는다. **이론상
  그때는 좋은 접근으로 보였으나 실제로는 빠르게 무너졌다** (8장, p.221).[^ford2021-hard-parts]
  - 그 낱말의 정본은 [경계 컨텍스트](../concepts/bounded-context.md)에 있다.
- **지금은 거의 쓰이지 않지만 유효한 기법으로 남는다** — 다만 **극도로 조심해서** 접근해야 하는데,
  이유가 뻔하다. **코드에서 버그가 발견되거나 중요한 변경이 필요하면 복제된 코드를 담은 모든
  서비스를 갱신하는 일이 매우 어렵고 시간이 든다** (8장, p.221).[^ford2021-hard-parts]
- **그래도 쓸모가 있는 구간이 있다** — **대부분(또는 모든) 서비스가 필요로 하는 고도로 정적인
  일회성 코드**가 그것이다 (8장, p.221).[^ford2021-hard-parts]
  - 저자들이 드는 실물이 **서비스 진입점을 표시하는 애너테이션**이다. 서비스 안에서 진입점을
    나타내는 클래스(대개 서비스 안의 RESTful API 클래스)를 식별한다 (8장, 예제 8-1,
    p.222):[^ford2021-hard-parts]

    ```java
    @Retention(RetentionPolicy.RUNTIME)
    @Target(ElementType.TYPE)
    public @interface ServiceEntrypoint {}

    /* Usage:
    @ServiceEntrypoint
    public class PaymentServiceAPI {
       ...
    }
    */
    ```

  - **이 코드가 복제 후보인 이유를 저자들이 코드 자체로 논증한다** — **예제 8-1의 원시 코드에는
    기능이 전혀 없다.** 애너테이션은 특정 클래스를 서비스 진입점으로 식별하는 **표식(marker)
    또는 태그일 뿐**이다. 다만 그 단순한 애너테이션이 **서비스 종류·도메인·경계 컨텍스트 같은
    다른 메타데이터 애너테이션을 얹을 자리**로는 매우 쓸모 있다 (8장, p.222).[^ford2021-hard-parts]
  - **그래서 판정이 나온다** — 이런 종류의 원시 코드는 **정적이고 버그를 담고 있지 않아(앞으로도
    아마 담지 않을 것이라) 복제의 좋은 후보**다. 유일한 일회성 클래스라면 **공유 라이브러리를
    만드는 대신 각 서비스 저장소에 복사할 값어치가 있을 수 있다.** 그럼에도 저자들은 **복제를
    고르기 전에 이 장의 다른 기법들을 먼저 조사해 보라고 일반적으로 권한다** (8장,
    p.222).[^ford2021-hard-parts]
- **절충표** (8장, 표 8-1, p.223):[^ford2021-hard-parts]

  | Advantages | Disadvantages |
  |---|---|
  | Preserves the bounded context | Difficult to apply code changes |
  | No code sharing | Code inconsistency across services |
  | | No versioning capabilities across services |

## 코드 복제를 언제 쓰는가

- **조건이 둘로 적힌다** — 개발자가 **단순하고 정적인 코드**(애너테이션·어트리뷰트·단순한 공통
  유틸리티 같은 것)를 가졌고 그것이 **일회성 클래스이거나 결함이나 기능 변경으로 바뀔 가능성이
  거의 없는 코드**일 때다 (8장, p.223).[^ford2021-hard-parts]
- **이행 국면의 쓰임이 하나 더 있다** — 모놀리식 아키텍처에서 분산 아키텍처로 옮길 때 **공통 정적
  유틸리티 클래스**에 이 기법이 통할 때가 있다. `Utility.cs` 같은 클래스를 모든 서비스에 복제하면
  **각 서비스가 자기 필요에 맞게 그 클래스를 덜어 내거나 키울 수 있어** 불필요한 코드가 사라지고
  유틸리티 클래스가 **맥락마다 따로 진화**한다. 저자들이 이것을 3장의 **전술적 포크(tactical
  forking)** 기법과 비슷하다고 적는다 (8장, p.223).[^ford2021-hard-parts]
  - 그 기법의 전문은 [분해 접근 둘](../concepts/decomposition-approaches.md)에 있다. **이 책이
    전술적 포크를 3장이라 적는데 이 KB가 반입한 자리는 4장이다** — 4장 §"Tactical Forking"이고,
    3장에는 그 절이 없다. 원문 그대로 두고 표시한다.
  - **위험은 그대로 남는다** — 코드가 서비스마다 복제되므로 **결함이나 변경을 모든 서비스에
    전파하기가 매우 어렵다** (8장, p.223).[^ford2021-hard-parts]

## 공유 라이브러리

- **규정** — 공유 라이브러리(shared library)는 **여러 서비스가 쓰는 원시 코드를 담은 외부
  산출물(JAR 파일·DLL 같은 것)이고 대개 컴파일 시점에 서비스에 묶인다** (8장,
  p.223).[^ford2021-hard-parts]
  - **단순해 보이지만 그렇지 않다고 저자들이 먼저 못 박는다** — 이 기법에는 복잡함과 절충이 있고
    그중에서도 **공유 라이브러리의 세분도와 버저닝**이 가장 크다 (8장, p.223).[^ford2021-hard-parts]

## 세분도를 가르는 두 힘 — 의존 관리와 변경 통제

- **같은 구조가 7장의 서비스 세분도에서 되풀이된다** — 저자들이 스스로 그렇게 적는다. **7장에서
  논한 서비스 세분도와 비슷하게 공유 라이브러리의 세분도에도 절충이 딸리고**, 그 절충을 이루는
  **맞서는 두 힘이 의존 관리(dependency management)와 변경 통제(change control)**다 (8장,
  p.224).[^ford2021-hard-parts] 그 앞 장의 열 요인은
  [서비스 세분도](../concepts/service-granularity.md)에 있다.
- **굵은 쪽의 셈** — 굵은 공유 라이브러리 하나를 두면 **의존 관리는 비교적 단순**하지만(서비스마다
  라이브러리 하나) **변경 통제는 그렇지 않다.** 굵은 공유 라이브러리 안의 어느 클래스 파일이든
  바뀌면 **관심이 있든 없든 모든 서비스가 결국 그 변경을 채택해야 한다** — 공유 라이브러리의 판
  폐기 때문이다. 그것이 **그 라이브러리를 쓰는 모든 서비스의 불필요한 재시험과 재배포**를 강요해
  공유 라이브러리 변경의 전체 시험 범위를 크게 늘린다 (8장, p.224).[^ford2021-hard-parts]
- **가는 쪽의 셈** — 공유 코드를 **기능 단위의 더 작은 공유 라이브러리들**(보안·포매터·애너테이션·
  계산기 같은 것)로 쪼개면 **변경 통제와 전체 유지보수성에는 낫지만 의존 관리가 엉망이 된다.**
  공유 클래스 C7의 변경이 서비스 D와 E에만 영향을 주지만, **공유 라이브러리와 서비스 사이의 의존
  행렬을 관리하는 일이 금세 분산된 진흙 공**처럼 보이기 시작한다 — **분산 모놀리스(distributed
  monolith)**라 부르는 사람도 있다 (8장, p.225).[^ford2021-hard-parts]
  - 도판(그림 8-5)이 서비스 다섯(A~E)과 **`Custom shared libraries`라는 이름이 붙은 공유 클래스
    일곱(C1~C7)** 사이에 점선 의존을 그어 그 행렬을 보인다 (8장, 그림 8-5,
    p.225).[^ford2021-hard-parts]
- **규모가 이 선택을 가른다** — 서비스가 몇 개뿐이면 세분도 선택이 별 문제가 아닐 수 있지만
  **서비스 수가 늘면 변경 통제와 의존 관리에 딸린 문제도 함께 는다.** 저자들이 드는 규모가
  **서비스 200개와 공유 라이브러리 40개**이고, 그러면 **금세 지나치게 복잡해지고 유지보수
  불가능해진다** (8장, p.225).[^ford2021-hard-parts]
  - **그 두 수의 근거를 저자들이 대지 않는다.** 상상해 보라는 예시로 든다. #hypothesis
- **저자들의 조언이 한쪽으로 기운다** — **크고 굵은 공유 라이브러리를 대체로 피하고 가능하면
  더 작고 기능으로 분할된 라이브러리를 지향하라**는 것이고, 곧 **변경 통제를 의존 관리보다 우선**
  하라는 것이다. 예컨대 포매터나 보안(인증과 인가)처럼 **비교적 정적인 기능을 자기 공유
  라이브러리로 떼어 내면** 그 정적 코드가 격리되어 **다른 공유 기능의 시험 범위와 불필요한 판 폐기
  배포가 줄어든다** (8장, p.225).[^ford2021-hard-parts]

## 버저닝 전략

- **조문 한 줄** — 저자들의 일반적 조언은 **언제나 판을 매기라(always use versioning!)**는 것이다.
  공유 라이브러리에 판을 매기면 **후진 호환성만이 아니라 높은 수준의 민첩성 — 변경에 빠르게
  대응하는 능력 — 도 얻는다** (8장, p.225).[^ford2021-hard-parts]
  - **셈이 딸린다** — 서비스 열이 쓰는 공통 필드 검증 규칙 라이브러리 `Validation.jar`가 있고 그중
    한 서비스가 검증 규칙 하나를 즉시 바꿔야 한다고 하자. 판을 매겨 두었으면 **그 서비스만 새
    판을 들여 곧바로 운영에 배포**할 수 있고 **나머지 아홉에는 아무 영향이 없다.** 판이 없으면
    공유 라이브러리를 바꿀 때 **열 전부를 시험하고 재배포**해야 하므로 시간과 조율이 늘고 민첩성이
    준다 (8장, p.226).[^ford2021-hard-parts]
- **그런데 저자들이 곧바로 그 조언을 되친다** — 버저닝에는 절충과 숨은 복잡함이 있고, **사실 저자들은
  버저닝을 분산 컴퓨팅의 아홉째 오류로 자주 생각한다** — **"버저닝은 단순하다"**는 것이다 (8장,
  p.226).[^ford2021-hard-parts]
  - 그 오류 목록의 정본은
    [분산 컴퓨팅의 오류](../concepts/fallacies-of-distributed-computing.md)이고 1994년 Deutsch의
    목록이 원전이다. **이 책은 그 목록의 출처를 이 자리에서 대지 않고, "아홉째"라는 것도 저자들이
    농담조로 붙이는 말이지 그 목록에 실제로 더해진 항목이 아니다.**
- **첫째 복잡함은 소통이다** — 판 변경을 알리는 일이고, 여러 팀이 있는 고도로 분산된 아키텍처에서는
  그것이 어렵다. **`Validation.jar`가 방금 1.5로 올랐다는 것을 다른 팀들이 어떻게 아는가. 무엇이
  바뀌었는가. 어떤 서비스가 영향을 받는가. 어떤 팀이 영향을 받는가.** 공유 라이브러리와 판과 변경
  문서를 관리하는 도구가 많아도(JFrog Artifactory 같은 것) **판 변경은 여전히 알맞은 사람에게
  알맞은 때에 조율되고 전달되어야 한다** (8장, p.226).[^ford2021-hard-parts]
  - 버전 조건: 2021년 저술 시점. 저자들이 도구를 하나만 예로 들고 기능을 적지 않는다.
- **둘째 복잡함이 폐기(deprecation)다** — 어느 날짜 이후로 더는 지원하지 않는 옛 판을 걷어 내는
  일이고, 전략이 **맞춤(custom, 공유 라이브러리마다)**에서 **전역(global, 모든 공유 라이브러리에)**
  까지 걸친다. 둘 다 절충이 딸린다 (8장, p.226).[^ford2021-hard-parts]

  | 전략 | 무엇을 얻는가 | 무엇을 내주는가 |
  |---|---|---|
  | 맞춤(custom) — 라이브러리마다 따로 | **라이브러리마다 변경 속도가 다르므로 대개 이쪽이 바람직하다.** `Security.jar`가 자주 안 바뀌면 두세 판만 유지해도 합리적이고, `Calculators.jar`가 주 단위로 바뀌면 열 판을 유지하는 편이 훨씬 합리적이다 | **누군가가 공유 라이브러리마다 폐기를 유지하고 추적해야 한다.** 저자들의 표현으로 때로 벅찬 일이고 **심약한 사람이 할 일이 결코 아니다** |
  | 전역(global) — 전부에 같은 규칙 | 유지와 거버넌스가 쉽다 | **변경이 라이브러리마다 다르므로 더 못한 접근이다.** 변경 속도와 무관하게 **후진 판을 정해진 수(예컨대 넷) 넘게 지원하지 않는다**는 규칙이라, 자주 바뀌는 라이브러리의 최신 판과 호환을 유지하려고 **끊임없이 재시험하고 재배포하는 처닝(churn)**이 생겨 팀 속도와 생산성을 크게 떨어뜨린다 |

  - 위 표의 열 머리글은 이 KB가 붙였다. 낱말과 수치는 원문 그대로다 (8장,
    pp.226–227).[^ford2021-hard-parts]
- **어떤 전략도 무효로 만드는 사건이 하나 있다** — **심각한 결함이나 공유 코드를 깨는 변경은 어떤
  폐기 전략도 무효로 만들어, 모든 서비스가 한꺼번에(또는 아주 짧은 기간 안에) 공유 라이브러리의
  최신 판을 채택하게 만든다.** 저자들이 이것을 **공유 라이브러리를 알맞은 만큼 가늘게 유지하고
  체계의 공유 기능을 전부 담은 굵은 `SharedStuff.jar` 부류를 피하라고 권하는 또 하나의 이유**로
  든다 (8장, p.227).[^ford2021-hard-parts]
  - **이 문장이 이 페이지 아래
    [갱신의 동시성을 두고 두 소스가 만나는 자리](#갱신의-동시성을-두고-두-소스가-만나는-자리)의
    대질 재료다.**
- **마지막 조언 하나** — **라이브러리의 어느 판이 필요한지 적을 때 `LATEST` 판을 쓰지 마라.**
  저자들의 경험으로 `LATEST`를 쓰는 서비스는 **빠른 수정이나 긴급 핫 배포를 운영에 낼 때 문제를
  겪는다** — `LATEST` 안의 무언가가 그 서비스와 호환되지 않을 수 있고, 그러면 그 서비스를 운영에
  릴리스하려고 팀이 추가 개발과 시험을 해야 한다 (8장, p.227).[^ford2021-hard-parts]

## 공유 라이브러리를 언제 쓰는가

- **절충표** (8장, 표 8-2, p.227):[^ford2021-hard-parts]

  | Advantages | Disadvantages |
  |---|---|
  | Ability to version changes | Dependencies can be difficult to manage |
  | Shared code is compile-based, reducing runtime errors | Code duplication in heterogeneous codebases |
  | Good agility for code shared code changes | Version deprecation can be difficult |
  | | Version communication can be difficult |

  - **세 번째 이점 칸의 `Good agility for code shared code changes`는 원문 그대로다** — `code`가
    두 번 나온다. 두 추출기와 렌더한 그림에서 모두 같다.
- **조건** — **공유 코드 변경이 적거나 보통인 동질(homogeneous) 환경**에 좋은 접근이다. 판을
  매기는 능력이(때로 복잡하더라도) 공유 코드를 바꿀 때 좋은 수준의 민첩성을 준다. **공유
  라이브러리는 대개 컴파일 시점에 서비스에 묶이므로 성능·확장성·내결함성 같은 운영 특성이 영향을
  받지 않고**, 공통 코드 변경으로 다른 서비스를 깨뜨릴 위험도 **버저닝 때문에 낮다** (8장,
  p.227).[^ford2021-hard-parts]
  - **원문의 이 절 제목만 `When To Use`이고 나머지 셋은 `When to Use`다**(대문자 T). 원문 그대로
    적어 둔다.

## 공유 서비스

- **규정** — 공유 라이브러리의 주된 대안이 공유 서비스다. **공유 서비스(shared service) 기법은
  공유 기능을 따로 배포되는 서비스에 놓아 재사용을 피한다** (8장, p.228).[^ford2021-hard-parts]
- **구별되는 성질 하나가 먼저 적힌다** — **공유 서비스 기법에서 공유 코드는 상속(inheritance)이
  아니라 합성(composition)의 형태여야 한다.** 저자들은 원시 코드 **설계** 관점에서 상속보다 합성을
  쓰는 문제에 논쟁이 많다고 인정하면서도(소트웍스의 글 "Composition vs. Inheritance: How to
  Choose"와 마틴 파울러의 글 "Designed Inheritance"를 든다), **아키텍처 관점에서는 코드 재사용
  기법을 고를 때 합성 대 상속이 문제가 되며 특히 공유 서비스 기법에서 그렇다**고 적는다 (8장,
  p.228).[^ford2021-hard-parts]
  - **이 KB가 확인한 원전이 아니다** — 두 글에 대한 귀속은 이 책이 그렇게 귀속한다까지로 둔다.
- **이 기법이 주는 것** — 공유 기능의 변경이 **서비스들의 재배포를 더는 요구하지 않는다.** 변경이
  별도 서비스에 격리되므로 **그 공유 기능이 필요한 다른 서비스를 재배포하지 않고 배포할 수 있다**
  (8장, p.228).[^ford2021-hard-parts]
  - 저자들이 이 기법을 **"그 시절(back in the day)" 분산 아키텍처에서 공유 기능을 다루는 흔한
    접근**이었다고 시제를 붙여 적는다 (8장, p.228).[^ford2021-hard-parts]
- **그리고 절충 넷이 예고된다** — **변경 위험·성능·확장성·내결함성**이다 (8장,
  p.228).[^ford2021-hard-parts]

## 변경 위험 — 런타임 변경이라는 성질

- **양날의 칼이라고 저자들이 적는다** — 앞면은 이렇다. 공유 기능을 바꾸는 일이 **별도 서비스에 담긴
  공유 코드를 고쳐 그 서비스를 재배포하는 문제일 뿐**이고, 그러면 그 공유 기능이 필요한 어떤
  서비스도 재시험·재배포하지 않고 **변경이 모든 서비스에 곧바로 적용된다** (8장,
  p.229).[^ford2021-hard-parts]
- **뒷면이 성질의 차이다** — 공유 서비스의 변경은 **런타임 변경**이고 공유 라이브러리 기법의
  **컴파일 기반 변경**과 다르다. 그래서 공유 서비스의 "단순한" 변경이 **사실상 체계 전체를 내릴 수
  있다** (8장, p.229).[^ford2021-hard-parts]
- **그래서 버저닝이 다시 문제가 되는데 이쪽에서는 어렵다** — 공유 라이브러리에서는 버저닝이 컴파일
  시점 바인딩으로 관리되어 변경 위험을 크게 줄이는데, **공유 서비스의 단순한 변경에는 판을 어떻게
  매기는가** (8장, p.230).[^ford2021-hard-parts]
  - **즉답은 API 엔드포인트 버저닝**이다 — 공유 서비스가 바뀔 때마다 URI에 새 판을 담은 새 API
    엔드포인트를 만드는 것이고, 저자들이 할인 계산기의 예를 든다(`app/1.0/discountcalc?orderid=123`
    부터 `app/1.4/…`까지) (8장, 예제 8-3, p.230).[^ford2021-hard-parts]
  - **문제 셋이 곧바로 따라온다** (8장, p.230):[^ford2021-hard-parts]
    - **부르는 쪽이 바뀌어야 한다** — 할인 계산기 서비스에 접근하는 서비스들(또는 서비스마다의
      설정)이 **올바른 판을 가리키도록 바뀌어야 한다.**
    - **언제 새 엔드포인트를 만드는가가 주관이 된다** — **단순한 오류 메시지 변경에는? 새 계산에는?**
      저자들이 **버저닝이 이 지점에서 대체로 주관적이 되기 시작한다**고 적는다.
    - **프로토콜이 하나가 아니다** — API 엔드포인트 버저닝은 공유 서비스로의 접근이 전부 게이트웨이나
      점대점 통신을 지나는 RESTful API 호출이라고 **가정한다.** 그러나 서비스 사이 통신은 메시징이나
      gRPC 같은 다른 프로토콜로도 흔히 이뤄지고, 그것이 **여러 프로토콜에 걸쳐 판을 조율하기 어렵게**
      만든다.
      - 버전 조건: 2021년 저술 시점. gRPC를 프로토콜의 예로만 든다.
  - **결론이 한 문장으로 적힌다** — 공유 서비스 기법에서 공유 서비스의 변경은 **대체로 런타임의
    성질이라 공유 라이브러리보다 훨씬 큰 위험을 진다.** 버저닝이 그 위험을 줄일 수는 있으나
    **적용하고 관리하기가 공유 라이브러리보다 훨씬 복잡하다** (8장, p.230).[^ford2021-hard-parts]
  - 서비스 계약 쪽의 같은 물음은
    [계약을 깨는 변경의 관리](../concepts/managing-breaking-api-changes.md)에 있다.

## 성능과 확장성과 내결함성

- **성능** — 공유 기능이 필요한 서비스가 공유 서비스로 **서비스 간 호출**을 해야 하므로 **네트워크
  지연 때문에 성능이 영향을 받는다**(엔드포인트가 보안으로 보호된다면 보안 지연도 더해진다). **공유
  라이브러리로 공유 코드에 접근할 때는 이 절충이 존재하지 않는다** (8장, p.231).[^ford2021-hard-parts]
  - **완화 수단 둘을 저자들이 든다** — **gRPC**는 네트워크 지연을 크게 줄여 성능 문제 일부를
    누그러뜨릴 수 있고, **메시징 같은 비동기 프로토콜**도 그렇다. 메시징에서는 공유 기능이 필요한
    서비스가 **요청 큐로 요청을 보내고 다른 일을 하다가 필요할 때 상관 ID(correlation ID)로 별도
    응답 큐에서 결과를 받아 올 수 있다** (8장, p.231).[^ford2021-hard-parts]
    - **저자들이 그 기법의 출처로 자기 책을 든다** — *Java Message Service* 2판(Mark Richards
      외, 오라일리)이다. **이 책의 공저자 한 사람이 자기 앞 책을 대는 자리다.** 이 KB가 확인한
      원전이 아니다.
    - 그 기제의 정본은 [메시징 패턴](../synthesis/messaging-patterns.md)에 있다.
- **확장성** — **공유 서비스를 쓰는 서비스들이 확장하는 만큼 공유 서비스도 확장해야 한다.** 여러
  서비스가 같은 공유 서비스에 동시에 접근할 때 특히 관리가 엉망이 될 수 있다. **공유 라이브러리
  기법에는 이 문제가 없다** — 공유 기능이 컴파일 시점에 서비스 안에 담기기 때문이다 (8장,
  p.232).[^ford2021-hard-parts]
- **내결함성** — 인스턴스를 여럿 두어 대체로 완화할 수 있지만 그래도 고려할 절충이다. **공유
  서비스가 불가용해지면 그 공유 기능이 필요한 서비스들은 공유 서비스가 돌아올 때까지 작동 불능이
  된다.** 공유 라이브러리 기법에는 이 문제가 없다 — 공유 기능이 컴파일 시점에 서비스 안에 담겨
  표준 메서드나 함수 호출로 접근되기 때문이다 (8장, p.232).[^ford2021-hard-parts]
  - **이것이 단일 장애점의 한 실물이다.** 같은 책이 6장에서 공유 데이터베이스에 같은 판정을
    내린다. 그 어휘의 정본은
    [신뢰성과 내결함성](../concepts/reliability-and-fault-tolerance.md)에 있다.
  - 도판(그림 8-11)이 두 기법을 나란히 놓고 공유 라이브러리 쪽에 **`No fault tolerance
    concerns`**라고 적는다 (8장, 그림 8-11, p.233).[^ford2021-hard-parts]

## 공유 서비스를 언제 쓰는가

- **절충표** (8장, 표 8-3, p.233):[^ford2021-hard-parts]

  | Advantages | Disadvantages |
  |---|---|
  | Good for high code volatility | Versioning changes can be difficult |
  | No code duplication in heterogeneous codebases | Performance is impacted due to latency |
  | Preserves the bounded context | Fault tolerance and availability issues due to service dependency |
  | No static code sharing | Scalability and throughput issues due to service dependency |
  | | Increased risk due to runtime changes |

- **조건** — **고도로 다중 언어인 환경**(이종 언어와 플랫폼이 여럿인 환경)과 **공유 기능이 자주
  바뀌는 경우**에 좋다. 공유 서비스의 변경이 전체로 보아 공유 라이브러리보다 훨씬 민첩하되,
  **런타임 부작용과 그 공유 기능이 필요한 서비스들에 가는 위험을 조심하라** (8장,
  p.234).[^ford2021-hard-parts]

## 사이드카와 서비스 메시

- **이 절이 물음을 바꾼다** — 앞의 셋이 **업무 도메인 공통 기능**을 어디에 둘지를 물었다면 이 절은
  **운영 결합(operational coupling)**을 다룬다. 저자들이 **아키텍트가 던지는 어떤 물음에도 가장
  흔한 답이 "때에 따라 다르다!"인데, 분산 아키텍처에서 그 모호함을 운영 결합보다 잘 보여 주는
  문제가 없다**고 적으며 절을 연다 (8장, p.234).[^ford2021-hard-parts]
- **마이크로서비스의 기본 답이 중복이다** — 설계 목표 하나가 높은 수준의 결합 끊기이고, 그것이
  **"중복이 결합보다 낫다(Duplication is preferable to coupling)"**는 조언으로 자주 나타난다.
  두 서비스가 고객 정보를 주고받아야 하는데 DDD의 경계 컨텍스트가 구현 세부를 서비스 안에 가두라고
  요구할 때, 흔한 해법은 **서비스마다 Customer 같은 개체의 내부 표현을 따로 두고 JSON의 이름-값
  쌍처럼 느슨하게 결합된 방식으로 정보를 넘기는 것**이다. 그러면 각 서비스가 **통합을 깨지 않고
  기술 스택까지 포함해 내부 표현을 마음대로 바꿀 수 있다** (8장, p.234).[^ford2021-hard-parts]
  - **저자들이 판정을 양식별로 갈라 적는다** — 아키텍트는 대체로 코드 중복을 못마땅해하지만
    **중복의 문제보다 나쁜 힘이 있을 때가 있고 마이크로서비스의 결합이 자주 그에 해당한다.**
    그래서 **"어떤 능력을 중복할 것인가 결합할 것인가"라는 물음에 마이크로서비스 아키텍처에서는
    중복이, 서비스 기반 아키텍처 같은 다른 양식에서는 결합이 옳은 답일 가능성이 높다. 때에 따라
    다르다** (8장, p.234).[^ford2021-hard-parts]
    - 그 둘째 양식의 규정은 [도메인 서비스 만들기](../concepts/create-domain-services.md)에 있다.
- **그런데 결합이 이로운 능력이 있다** — 모니터링·로깅·인증과 인가·서킷 브레이커처럼 **각 서비스가
  가져야 할 공통 운영 능력**이다. **그것들을 팀마다 알아서 관리하게 두면 혼돈으로 빠진다.** 저자들이
  던지는 두 물음이 구체적이다 — 어느 회사가 공통 모니터링 해법으로 표준화하려 하는데 **팀마다 자기
  서비스의 모니터링을 구현할 책임을 진다면 운영 팀은 그들이 실제로 했는지 어떻게 확신하는가**, 그리고
  **모니터링 도구를 조직 전체에서 올려야 한다면 팀들이 그것을 어떻게 조율하는가** (8장,
  p.234).[^ford2021-hard-parts]
  - **그 회사 이름이 이 책에서는 `Penultimate Electronics`다.** 같은 저자들의 2022년 책이 같은
    논증에서 쓰는 이름은 `PenultimateWidgets`다. 둘 다 이 KB가 확인한 실재 회사가 아니라 저자들의
    대리 회사다.
- **계보를 육각형 아키텍처로 잡는다** — 지난 몇 해 동안 마이크로서비스 생태계에서 떠오른 해법이
  **사이드카 패턴(Sidecar pattern)**이고, 이 패턴은 **앨리스터 코오번(Alistair Cockburn)이 규정한
  훨씬 이른 아키텍처 패턴인 육각형 아키텍처(hexagonal architecture)에 기반한다** (8장,
  p.235).[^ford2021-hard-parts]
  - **육각형 패턴에서는 지금 우리가 도메인 로직이라 부를 것이 육각형 가운데 있고 생태계의 다른
    부분으로 가는 포트와 어댑터가 그것을 둘러싼다**(그래서 **포트와 어댑터 패턴(Ports and Adaptors
    Pattern)**이라고도 불린다). 도판(그림 8-12)이 가운데 `Business logic`을 두고 육각형 위에
    `REST API`·`Command adapter`·`Event adapter`·`Database adapter`를 놓으며 데이터베이스를
    육각형 밖에 둔다 (8장, p.235).[^ford2021-hard-parts]
  - **한 가지가 다르다고 명시한다 — 데이터 충실도(data fidelity)다.** 육각형 아키텍처는
    **데이터베이스를 갈아 끼울 수 있는 또 하나의 어댑터로 다뤘는데**, DDD의 통찰 하나는 **데이터
    스키마와 트랜잭션성이 안쪽에 있어야 한다**고 본다. 마이크로서비스가 그쪽이다 (8장,
    p.235).[^ford2021-hard-parts]
  - **이 KB가 확인한 원전이 아니다** — 귀속은 이 책이 그렇게 귀속한다까지로 둔다.
- **사이드카가 무엇을 가르는가** — 사이드카 패턴은 육각형 아키텍처와 **같은 개념을 활용해 도메인
  로직을 기술(인프라) 로직에서 떼어 낸다.** 서비스 안이 **운영 관심사**와 **도메인 관심사**로
  갈리는데, 아키텍트가 운영 능력의 일관성을 원하면 **떼어 낼 수 있는 부분들이 사이드카
  구성 요소로 들어간다.** 이름은 **오토바이에 붙는 사이드카**에서 온 비유이고, 그 구현은 **팀들이
  함께 지는 책임이거나 중앙 인프라 그룹이 관리한다.** 모든 서비스가 사이드카를 포함한다고 가정할 수
  있으면 **서비스들에 걸친 일관된 운영 인터페이스**가 되고, 대개 **서비스 플레인(service plane)**으로
  이어 붙는다 (8장, p.236).[^ford2021-hard-parts]
- **메시가 서는 조건** — 아키텍트와 운영이 **모든 서비스가 사이드카 구성 요소를 포함한다고 안전하게
  가정할 수 있으면(적합도 함수가 그것을 거버넌스한다) 그것이 서비스 메시(service mesh)를 이룬다.**
  각 서비스 오른쪽의 상자들이 서로 이어져 "메시"를 이룬다 (8장, p.237).[^ford2021-hard-parts]
  - **메시를 가지면 아키텍트와 데브옵스가 대시보드를 만들고 규모 같은 운영 특성을 통제하는 등 여러
    능력을 얻는다** (8장, p.237).[^ford2021-hard-parts]
  - 그 거버넌스 기제는
    [아키텍처 적합도 함수](../concepts/architecture-fitness-functions.md)에 있다.
- **거버넌스 쪽 쓰임이 하나 더 있다** — 사이드카 패턴은 엔터프라이즈 아키텍트 같은 거버넌스 집단에게
  **너무 많은 다중 언어 환경에 대한 합리적 제동**을 준다. 마이크로서비스의 이점 하나가 공통 플랫폼
  대신 통합에 기대어 팀마다 복잡도와 능력 수준을 고를 수 있는 것인데, **플랫폼이 늘어나면 통일된
  거버넌스가 어려워진다.** 그래서 팀들이 **메시의 일관성을 이종 플랫폼에 걸친 인프라와 횡단 관심사를
  떠받치는 동력으로 쓴다** — 메시가 없으면 **그 해법을 떠받치는 플랫폼마다 사이드카를 하나씩** 지어야
  한다 (8장, p.237).[^ford2021-hard-parts]
- **그래서 이것이 재사용 패턴의 한 종류로 규정된다** — 사이드카 패턴은 운영 능력을 도메인에서 떼어
  내는 방법일 뿐 아니라 **특정 종류의 결합을 다루는 직교 재사용 패턴(orthogonal reuse pattern)**이다.
  아키텍처 해법에는 결합의 종류가 여럿 필요할 때가 잦고(도메인 결합 대 운영 결합이 지금의 예다),
  **직교 재사용 패턴은 아키텍처의 이음매 하나 또는 여럿을 거슬러 어떤 측면을 재사용하는 길**을 준다.
  마이크로서비스 아키텍처는 도메인을 중심으로 조직되는데 **운영 결합은 그 도메인들을 가로질러야
  하고**, 사이드카가 아키텍트로 하여금 그 관심사를 **횡단하되 일관된 층**에 격리하게 해 준다 (8장,
  p.238).[^ford2021-hard-parts]

## 직교 결합

- 저자들이 이 낱말을 곁상자로 따로 규정한다 (8장 곁상자 "Orthogonal Coupling",
  p.238):[^ford2021-hard-parts]

  > In mathematics, two lines are *orthogonal* if they intersect at right angles, which also
  > implies independence. In software architecture, two parts of an architecture may be
  > *orthogonally coupled*: two distinct purposes that must still intersect to form a complete
  > solution. The obvious example from this chapter is an operational concern such as
  > monitoring, which is necessary but independent from domain behavior, like catalog
  > checkout. Recognizing orthogonal coupling allows architects to find intersection
  > points that cause the least entanglement between concerns.

- **이 곁상자가 같은 저자들의 2022년 책 5장에 낱말 수준까지 같은 형태로 다시 실린다.** 두 자리의
  관계와 방향은 아래 [이어지는 페이지](#이어지는-페이지)가 가리키는
  [API 게이트웨이와 서비스 메시](../concepts/api-gateway-and-service-mesh.md)가 갖는다.

## 사이드카와 메시를 언제 쓰는가

- **절충표** (8장, 표 8-4, p.239):[^ford2021-hard-parts]

  | Advantages | Disadvantages |
  |---|---|
  | Offers a consistent way to create isolated coupling | Must implement a sidecar per platform |
  | Allows consistent infrastructure coordination | Sidecar component may grow large/complex |
  | Ownership per team, centralized, or some combination | |

  - **이 표만 이점 칸이 셋이고 단점 칸이 둘이다.** 앞 셋은 단점 칸이 더 길거나 같았다.
- **조건** — 사이드카 패턴과 서비스 메시는 **분산 아키텍처에 어떤 횡단 관심사를 퍼뜨리는 깔끔한
  방법**을 주고, **운영 결합 말고도 쓸 수 있다**(저자들이 14장을 가리킨다). **네 사람의 갱
  *Design Patterns* 책에 나오는 데코레이터 디자인 패턴의 아키텍처판**을 준다 — 아키텍트로 하여금
  **보통의 연결과 독립적으로 분산 아키텍처를 가로질러 행동을 "장식"하게** 해 준다 (8장,
  p.239).[^ford2021-hard-parts]
  - **이 KB가 확인한 원전이 아니다** — 데코레이터 패턴에 대한 귀속은 이 책이 그렇게 귀속한다까지로
    둔다.

## 재사용은 언제 값을 하는가

- **이 절이 이 장의 판정을 세운다** — 저자들이 먼저 **많은 아키텍트가 어떤 상황에서 절충을 제대로
  평가하지 못하는데 그것이 반드시 결함은 아니고 많은 절충이 사후에야 뚜렷해진다**고 적는다 (8장,
  p.242).[^ford2021-hard-parts]
- **역사적 교훈을 든다** — 재사용이 지나칠 때의 위험은 많은 아키텍트가 **오케스트레이션 주도
  서비스 지향 아키텍처의 유행**에서 배운 교훈 가운데 하나이고, 그때 많은 조직의 으뜸 목표 하나가
  **재사용의 극대화**였다 (8장, p.242).[^ford2021-hard-parts]
  - **원문이 그 유행의 시기를 `the early 20th century`라 적는다.** 오케스트레이션 주도 서비스 지향
    아키텍처는 20세기가 아니라 21세기 초의 것이다. **원문 그대로 두고 표시한다.**
- **실물이 보험사의 고객 서비스다** — 회사의 부서마다 고객에 대해 신경 쓰는 측면이 따로 있는데,
  예전에 아키텍트들은 **그런 공통성을 찾아내면 조직의 고객 관점을 단일 서비스로 통합하라**고
  배웠다 (8장, pp.242–243).[^ford2021-hard-parts]
- **저자들의 판정은 그것이 아키텍처의 재앙이라는 것이고 이유가 둘이다** (8장,
  p.243):[^ford2021-hard-parts]
  - **첫째, 복잡해진다** — Customer 같은 핵심 개체에 대한 모든 제도적 정보가 한자리에 있어야
    한다면 **그 개체는 어떤 도메인과 시나리오든 감당할 만큼 복잡해져야 하고, 그래서 단순한 일에
    쓰기 어려워진다.**
  - **둘째, 아키텍처에 취약성(brittleness)이 생긴다** — 고객 정보가 필요한 모든 도메인이 한자리에서
    그것을 얻어야 한다면 **그 자리가 바뀔 때 전부가 깨진다.** 고객 서비스가 어느 한 도메인을 위해
    새 능력을 더해야 하면 **그 변경이 다른 모든 도메인에 영향을 줄 수 있어** 변경이 아키텍처
    전체로 "번지지" 않았는지 조율과 시험이 필요해진다.
- **그리고 무엇을 놓쳤는지가 규정된다** — **아키텍트들이 깨닫지 못한 것은 재사용에 중요한 측면이
  둘이라는 것이다. 첫째는 제대로 잡았다 — 추상화(abstraction)다.** 아키텍트와 개발자가 재사용
  후보를 발견하는 길이 추상화다. **그러나 쓸모와 값어치를 결정하는 둘째 고려 사항이 변경률(rate of
  change)이다** (8장, p.243).[^ford2021-hard-parts]
- **되묻는 방식으로 논증한다** — 어떤 재사용은 취약성을 낳는데 **우리가 분명히 이득을 보는 재사용과
  무엇이 다른가.** 모두가 성공적으로 재사용하는 것들 — 운영체제, 오픈 소스 프레임워크와 라이브러리
  — 을 생각해 보라. **프로젝트 팀이 짓는 자산과 그것들을 가르는 답이 느린 변경률이다.** 운영체제나
  외부 프레임워크 같은 기술적 결합에서 이득을 보는 이유는 **그것들의 변경률과 갱신 주기가 잘
  이해되어 있기 때문**이고, **내부 도메인 능력이나 빠르게 바뀌는 기술 프레임워크는 형편없는 결합
  대상**이다 (8장, pp.243–244).[^ford2021-hard-parts]
- **결론이 한 문장으로 조판된다.** 원문은 이 줄을 본문과 떼어 큰 글씨로 놓는다 (8장,
  p.243):[^ford2021-hard-parts]

  > Reuse is derived via abstraction but operationalized by slow rate of change.

  - **이 문장이 같은 저자들의 2022년 책 5장 절 제목 §"Effective Reuse = Abstraction + Low
    Volatility"(p.113)와 같은 주장이다.**[^ford2022-evolutionary] 그 절은 한 문단뿐이고 **왜
    추상화와 낮은 변동성이 효과적 재사용의 조건인지를 논증하지 않는다**는 것이 이 KB의 앞선
    실측이었다. **2021년의 이 절이 그 논증을 갖고 있다** — 취약한 재사용과 성공한 재사용을 맞대어
    변경률을 가름의 축으로 뽑아내는 두 문단이다. 두 책의 대비는
    [DRY 원칙](../concepts/dry-principle.md)이 갖는다.
    - **저자 구성이 겹치나 같지 않다.** 2021년 책은 Ford·Richards·Sadalage·Dehghani, 2022년 책은
      Ford·Parsons·Kua·Sadalage이고 겹치는 사람은 Ford와 Sadalage 둘이다. **두 책 어느 쪽도 이
      자리에서 상대를 가리키지 않는다.** 출판 시점은 2021년이 앞선다. #hypothesis

## 플랫폼을 통한 재사용

- **절 전체가 두 문단이다** — 조직 안 플랫폼의 미덕을 말하는 글이 **의미 확산(semantic diffusion)에
  가까울 만큼** 많은데, 그래도 대부분이 **플랫폼이 조직 안 재사용의 새 대상**이라는 데 동의한다.
  곧 **구별할 수 있는 도메인 능력마다 조직이 잘 규정된 API로 구현 세부를 감추는 플랫폼을 짓는다**는
  뜻이다 (8장, p.244).[^ford2021-hard-parts]
- **그 추론을 이끄는 것이 앞 절의 느린 변경률이다** — 13장에서 논하듯 **API는 호출자에게 꽤 느슨하게
  결합되도록 설계될 수 있어, API를 깨지 않으면서 구현 세부를 공격적으로 바꿀 수 있다.** 물론 이것이
  **도메인 사이에 넘겨야 하는 정보의 의미가 바뀌는 것까지 막아 주지는 않지만**, 캡슐화와 계약을
  주의 깊게 설계하면 아키텍트가 **통합 아키텍처에서 깨는 변경과 취약성의 양을 제한**할 수 있다
  (8장, p.244).[^ford2021-hard-parts]
- **이 플랫폼이 이 KB의 다른 플랫폼과 같은 것인가.** 대질 결과 **가리키는 대상이 다르다.**
  아래 대비는 이 KB가 세운 것이고 두 소스는 서로를 호명하지 않는다. #hypothesis

  | | 이 절(ford2021 8장) | [플랫폼 팀과 포장된 길](../concepts/platform-team-and-paved-road.md)(newman2021 15장) |
  |---|---|---|
  | 플랫폼이 감싸는 것 | **구별할 수 있는 도메인 능력** 하나 | **셀프서비스 도구 묶음** — 원하는 상태 관리, 로그 집계, 서비스 사이 인증과 인가 |
  | 왜 짓는가 | **재사용의 새 대상**. 느린 변경률을 API 뒤에 확보한다 | **스트림 정렬 팀에 밀려든 책임**을 감당하게 한다 |
  | 사용자 | 그 도메인 능력을 부르는 다른 도메인 | **다른 개발자** |
  | 성공 조건 | API가 느슨하게 결합되어 내부 변경률을 감춘다 | **강제하지 않는데도 쓰인다**(포장된 길) |

  - **겨루지 않는다.** 하나는 **도메인 기능을 감싸는 것**이고 다른 하나는 **전달 인프라를 감싸는
    것**이라 같은 낱말이 다른 층에 걸린다. 이 절 자신이 **도메인 능력마다 하나**라고 범위를 적어
    두므로 낱말이 겹치는 자리가 좁다.
  - **그래도 한 조건이 같다** — 양쪽 다 **그 플랫폼이 감추는 것의 변경률이 쓰는 쪽에 새지 않아야**
    선다. 이쪽은 그것을 API 설계로, 저쪽은 채택률로 잰다. #hypothesis

## 책의 사례 — 공통 인프라 로직

- **장면** — 공유 메시지 발송 라이브러리를 쓰기 시작하자 **로그 메시지가 두 번 찍힌다.** 라이브러리도
  로그를 쓰고 서비스도 쓰기 때문이다. 물음이 **누가 로그 메시지를 써야 하는가 — 라이브러리인가
  서비스인가 다른 무엇인가, 그리고 그것을 어떻게 일관되게 만드는가**로 세워진다 (8장, pp.239–240,
  사가).[^ford2021-hard-parts]
- **아키텍트의 진단이 낱말을 준다** — **운영 공유 행위(operational shared behavior)에 부딪힌
  것**이고 로깅은 그중 하나일 뿐이다. 모니터링·서비스 디스커버리·서킷 브레이커, 그리고 **몇 팀이
  나눠 쓰는 JSONtoXML 유틸리티 함수**까지 같은 부류다. 그래서 **공통 행위를 사이드카 구성 요소에
  담는 서비스 메시를 구현하는 중**이라고 답한다 (8장, p.240, 사가).[^ford2021-hard-parts]
- **이 사가가 이 장의 규칙 하나를 명시적으로 만든다** — **서비스 메시와 사이드카의 의도는 도메인
  결합이 아니라 운영 결합을 한데 모으는 것**이고, 그래서 **`Address`나 `Customer` 클래스 같은
  도메인 공유 컴포넌트를 사이드카에 절대 넣지 말아야 한다** (8장, p.240,
  사가).[^ford2021-hard-parts]
  - **이유가 결합의 정의로 적힌다** — 그렇게 하면 **마이크로서비스에서 피하려는 바로 그 방식으로
    결합이 늘어난다.** 대부분의 아키텍처에서는 그 서비스의 단일 구현이 필요한 팀들에 공유되지만,
    마이크로서비스에서는 그것이 **결합 지점을 만들어 여러 서비스를 바람직하지 않게 묶는다** —
    한 팀이 공유 코드를 바꾸면 모든 팀이 그 변경에 맞춰 조율해야 한다. **`Address` 클래스가 바뀌고
    두 서비스가 그것에 기대면 둘 다 바뀌어야 하고 그것이 결합의 정의**다 (8장, p.241,
    사가).[^ford2021-hard-parts]
  - **그런데 저자들이 그 규칙을 곧바로 무르게 만든다** — **아키텍트가 그 공유 라이브러리를
    사이드카에 넣기로 결정할 수도 있다. 어쨌든 그것은 기술적 능력이다. 어느 답도 명백히 옳지 않고,
    그래서 이것이 절충 분석의 값어치가 있는 아키텍트의 결정이다** (8장, p.241,
    사가).[^ford2021-hard-parts]
- **그리고 크기 판정의 어림이 하나 나온다** — 사이드카가 **아키텍처에서 가장 큰 부분이 되기를
  원하지 않는다**는 것이 둘째 문제이고, 저자들이 JSONtoXML 라이브러리를 재료로 절충을 계산하게
  한다. **팀 16~17개 가운데 5개가 쓴다**는 사실이 나오고, 이점은 **모든 팀이 자동으로 그
  라이브러리를 갖고 의존으로 엮을 필요가 없다**는 것이며 대가는 **사이드카가 커진다**는 것이다
  (8장, p.241, 사가).[^ford2021-hard-parts]
  - **어림이 한 문장으로 떨어진다** — **공유 유틸리티 코드의 핵심 절충은 몇 팀이 그것을 필요로
    하는가 대 그것이 모든 서비스에(특히 필요 없는 서비스에도) 얼마나 많은 부담을 더하는가**이고,
    **절반에 못 미치는 팀이 쓴다면 아마 그 부담의 값어치가 없다** (8장, p.241,
    사가).[^ford2021-hard-parts]
    - **그 눈금의 근거를 저자들이 대지 않는다.** 등장인물이 대화 중에 내놓고 아키텍트가
      동의한다. #hypothesis
    - **이 장에서 수치가 붙는 판정은 이것 하나다.** 7장이 공유 도메인 코드 40%라는 눈금을
      주었고([서비스 세분도](../concepts/service-granularity.md)), 이 장은 **사이드카에 넣을지를
      팀 비율 50%로** 가른다. **두 눈금이 재는 대상이 다르다** — 앞은 코드베이스의 비율이고 뒤는
      필요로 하는 팀의 비율이다. #hypothesis
- **소유권이 조직으로 답해진다** — 사이드카를 팀들이 함께 지는 책임으로 둘지 물었을 때, 답은
  **팀이 충분히 많아져서 사이드카 구성 요소를 관리하고 유지할 공유 인프라 팀(shared infrastructure
  team)을 만들었다**는 것이다. 그 팀이 **사이드카가 서비스에 묶인 뒤 자동으로 시험하는 배포
  파이프라인을 적합도 함수 묶음과 함께** 지었다 (8장, p.240, 사가).[^ford2021-hard-parts]
  - **서비스 팀이 그 팀의 고객이 된다** — ADR이 그렇게 적는다.
- **ADR: Using a Sidecar for Operational Coupling** (8장, p.241, ADR):[^ford2021-hard-parts]
  - **맥락** — 마이크로서비스 아키텍처의 각 서비스가 공통되고 일관된 운영 행위를 요구하는데, 그
    책임을 팀마다 맡기면 **불일치와 조율 문제**가 생긴다.
  - **결정** — **서비스 메시와 함께 사이드카 구성 요소를 써서 공유 운영 결합을 한데 모은다.**
    공유 인프라 팀이 서비스 팀을 위해 사이드카를 소유하고 유지하며 **서비스 팀은 그들의 고객으로
    행동한다.** 사이드카가 제공할 것을 다섯으로 나열한다 — `Monitoring`·`Logging`·`Service
    discovery`·`Authentication`·`Authorization`.
  - **귀결** — **팀은 사이드카에 도메인 클래스를 더하지 말아야 한다. 그것이 부적절한 결합을
    조장한다.** 그리고 팀은 **충분히 많은 팀이 필요로 하면** 공유 **운영** 라이브러리를 사이드카에
    놓도록 공유 인프라 팀과 함께 일한다.
  - **이 ADR의 맥락 칸에 대안 목록이 없다.** 1장 p.5가 요구하는 형식의 한 자리다. 같은 어긋남이
    6장 p.184의 ADR에도 있었다. 그 형식의 정본은
    [아키텍처 결정 기록](../concepts/architecture-decision-records.md)에 있다.

## 책의 사례 — 공유 도메인 기능

- **장면의 배치** — 핵심 티켓 기능을 서비스 셋(고객 대면 Ticket Creation·Ticket Assignment·
  Ticket Completion)으로 쪼개기로 했는데 **셋 다 공통 데이터베이스 로직(질의와 갱신)을 쓰고 티켓
  데이터 도메인의 테이블 묶음을 공유한다.** 한쪽은 **공통 데이터베이스 로직을 담아 데이터베이스
  추상 층을 이루는 공유 데이터 서비스**를 원하고, 다른 쪽은 **각 서비스가 빌드와 배포의 일부로
  포함하는 공유 라이브러리(DLL) 하나**를 원한다 (8장, pp.244–245, 사가).[^ford2021-hard-parts]
- **아키텍트가 형식을 교정한다** — **의견의 문제가 아니라 절충을 분석해 가장 알맞은 해법에
  이르는 문제**라고 적고, **가설 기반 접근(hypothesis-based approach)**을 쓰자며 **공유 데이터
  서비스가 가장 알맞은 해법이라고 가설을 세우자**고 한다 (8장, p.245, 사가).[^ford2021-hard-parts]
  - **반대하는 쪽에게 "왜"를 물어 절충의 언어로 생각하게 만드는 것이 이 장면의 방법이다.**
- **절충이 대화에서 하나씩 쌓인다** (8장, pp.245–247, 사가):[^ford2021-hard-parts]

  | 무엇이 나왔나 | 어느 쪽인가 |
  |---|---|
  | 세 서비스가 **모든 데이터베이스 질의와 갱신마다** 서비스 간 호출을 해야 한다 | 성능 손해 |
  | 공유 데이터 서비스가 내려가면 **세 서비스 전부 작동 불능** | 내결함성 손해 |
  | **전부 백엔드 기능이 아니다** — Ticket Creation이 고객 대면이다 | 위 둘의 범위를 넓히는 반론 |
  | 공유 데이터 서비스의 변경은 **런타임 변경**이라 배포하면 무언가 깨질 수 있다 | 변경 위험 |
  | 위험을 줄이려면 **변경마다 티켓 서비스 전부를 시험**해야 해 시험 시간이 크게 는다 | 시험 노력 |
  | Ticket Creation 인스턴스를 늘릴 때마다 **공유 데이터 서비스 인스턴스도 늘려야** 한다 | 확장의 추가 조율 |
  | **데이터 추상** — 서비스들이 데이터베이스 로직을 신경 쓰지 않고 원격 호출만 하면 된다 | 이득 |
  | **중앙 커넥션 풀링** — 다만 고객 티켓 생성을 받치려면 어차피 인스턴스가 여럿이라 **큰 판도를 바꾸지는 않는다** | 이득이되 약함 |
  | **변경 통제** — 데이터베이스 로직 변경에 티켓 서비스를 재배포하지 않아도 된다 | 이득 |

  - 위 표는 원문의 대화를 이 KB가 표로 모은 것이고 낱말은 원문 그대로다.
- **판정을 뒤집은 것이 저장소 이력이다** — 아키텍트가 **그 공유 클래스 파일들이 역사적으로 얼마나
  바뀌었는지 저장소 이력을 보자**고 하고, 셋이 함께 확인한 결과 **생각보다 변경이 훨씬 적었다.**
  그래서 **공유 데이터베이스 로직의 변경이 결국 미미하다**는 사실이 확정되고, 공유 서비스의
  부정적인 면이 긍정적인 면을 넘어선다는 결론에 이른다 (8장, p.247, 사가).[^ford2021-hard-parts]
  - **이 장의 절충표가 공유 서비스의 첫째 이점으로 든 것이 `Good for high code volatility`였다.**
    이 사가는 **그 전제가 실측으로 무너지는 장면**이다. **저자들이 그 대응을 명시하지 않는다.**
    #hypothesis
  - **재료가 앞 사가들과 다르다.** 3장은 업무 근거, 6장 전반은 로그와 지표, 6장 후반은 업무 고통,
    7장은 변경 주기와 처리량의 추정치였다. **이 장면은 저장소 커밋 이력을 증거로 쓴다.** 같은 책이
    쓰는 증거 가운데 유일하게 **과거 실측**이다. #hypothesis
- **ADR: Use of a Shared Library for Common Ticketing Database Logic** (8장, p.247,
  ADR):[^ford2021-hard-parts]
  - **맥락** — 티켓 기능이 서비스 셋으로 나뉘고 셋 다 데이터베이스 질의와 갱신문 대부분에 공통
    코드를 쓴다. **선택지 둘은 공유 라이브러리를 쓰는 것과 공유 데이터 서비스를 만드는 것이다.**
    - **이 ADR의 맥락 칸에는 대안 목록이 있다.** 같은 장의 앞 ADR(p.241)에는 없었다.
  - **결정** — **공통 티켓 데이터베이스 로직에 공유 라이브러리를 쓴다.** 정당화가 셋이다.
    - 공유 라이브러리가 **고객 대면 Ticket Creation 서비스와 Ticket Assignment 서비스의 성능과
      확장성과 내결함성을 개선한다.**
    - **공통 데이터베이스 로직 코드가 많이 바뀌지 않아 상당히 안정적인 코드**임을 확인했다.
      필요하면 **알맞은 자리에 버저닝을 적용해 공통 데이터베이스 로직이 바뀔 때 모든 서비스를
      재배포하지 않아도 되게 한다.**
    - 공유 라이브러리가 **서비스 결합을 줄이고 추가 서비스 의존과 HTTP 트래픽과 전체 대역폭을
      없앤다.**
  - **귀결** — 공유 DLL의 공통 데이터베이스 로직이 바뀌면 **티켓 서비스들을 시험하고 배포해야
    하므로 그 기능의 전체 민첩성이 줄어든다.** 그리고 **서비스 인스턴스마다 자기 데이터베이스
    커넥션 풀을 관리해야 한다.**
    - **둘째 귀결이 같은 책 6장의 커넥션 할당량 논의로 이어진다.** 그 셈은
      [데이터 분해의 구동 요인](../concepts/data-decomposition-drivers.md)에 있다.
  - **결정 칸의 둘째 정당화에 원문이 어긋나는 자리가 하나 있다** — **`change is less risky for the
    common database logic because services would need to be tested and redeployed`**라고 적는데,
    시험과 재배포가 필요하다는 것은 위험이 낮은 **이유**가 아니라 이 ADR 자신이 귀결 칸에 적는
    **대가**다. 원문 그대로 두고 표시한다. #hypothesis
- **두 사가의 날짜가 장 안의 순서와 반대다** — 앞에 놓인 §"Common Infrastructure Logic"이
  **2월 10일 목요일**이고 뒤에 놓인 §"Shared Domain Functionality"가 **2월 8일 화요일**이다.
  장 여는 사가는 **2월 2일 수요일**이다. **저자들이 그 역순을 설명하지 않는다.** #hypothesis

## 넷을 한자리에 놓으면

**아래 대비는 이 KB가 이 장의 네 절에서 뽑아 모은 것이고 원문에 이런 표가 없다.** 낱말은 각 절의
원문 그대로다. #hypothesis

| | 코드 복제 | 공유 라이브러리 | 공유 서비스 | 사이드카와 메시 |
|---|---|---|---|---|
| 공유 코드가 어디에 있는가 | **각 서비스 저장소** | 외부 산출물(JAR·DLL) | **따로 배포되는 서비스** | 서비스마다 붙는 구성 요소 |
| 언제 묶이는가 | 복사 시점 | **컴파일 시점** | **런타임** | 배포 시점(적합도 함수가 확인) |
| 판을 매길 수 있는가 | **없다**(`No versioning capabilities across services`) | **있다**(그러나 폐기와 소통이 어렵다) | 어렵다(엔드포인트 버저닝이 주관적이고 프로토콜마다 갈린다) | 이 장이 다루지 않는다 |
| 운영 특성에 영향이 있는가 | 없다 | **없다**(`not impacted`) | **성능·확장성·내결함성 전부** | 사이드카가 커지면 모든 서비스가 진다 |
| 어떤 코드를 겨냥하는가 | **정적인 일회성 코드** | 변경이 적거나 보통인 공유 코드 | **자주 바뀌는 공유 코드** | **운영 결합**(도메인 결합이 아니다) |
| 어떤 환경을 겨냥하는가 | 이행 국면 | **동질 환경** | **고도로 다중 언어인 환경** | 플랫폼이 여럿인 환경 |

- **넷 가운데 셋이 도메인 공통 기능을 다루고 하나만 인프라 공통 기능을 다룬다.** 그 가름의 낱말이
  이 책 5장의 것과 같다 —
  [공통 도메인 컴포넌트 모으기](../concepts/gather-common-domain-components.md)가 갖는다.
- **변동성이 공유 라이브러리와 공유 서비스를 가르는 축이다.** 라이브러리는 **낮거나 보통**,
  서비스는 **높음**이다. 그리고 아래
  [재사용은 언제 값을 하는가](#재사용은-언제-값을-하는가)가 **느린 변경률이 재사용을 쓸모 있게
  만드는 조건**이라 적으므로, **변동성이 높아 공유 서비스를 고르게 되는 구간은 애초에 재사용이 값을
  덜 하는 구간**이라는 읽기가 가능하다. **저자들이 그 둘을 잇지 않는다.** #speculation

## 갱신의 동시성을 두고 두 소스가 만나는 자리

**같은 판정 규칙을 다른 소스가 다른 낱말로 적는다. 두 소스는 서로를 호명하지 않는다.**

- **뉴먼 쪽 조문** — 라이브러리로 코드를 공유할 때 정말로 중요한 점은 **모든 사용처를 한꺼번에
  갱신할 수 없다**는 것이고, 정말로 모든 사용자에 대해 정확히 같은 시점에 그 코드를 갱신해야
  한다면 실제로 봐야 할 것은 **전용 마이크로서비스를 통한 코드 재사용**이다 (5장,
  p.155).[^newman2021] 전문은 [DRY 원칙](../concepts/dry-principle.md)에 있다.
- **포드 쪽 조문** — **심각한 결함이나 공유 코드를 깨는 변경은 어떤 폐기 전략도 무효로 만들어
  모든 서비스가 한꺼번에 최신 판을 채택하게 만든다** (8장, p.227).[^ford2021-hard-parts]
- **둘이 같은 사실을 반대편에서 적는다.** 뉴먼은 **동시 갱신이 필요하면 서비스로 가라**고 하고,
  포드는 **동시 갱신이 필요한 사건이 실제로 일어나므로 라이브러리를 가늘게 유지하라**고 한다.
  - **겨루지 않는다.** 뉴먼은 그 요구가 **상시적일 때** 서비스를 권하고, 포드는 그것이
    **간헐적 사건일 때** 굵은 라이브러리를 피하라고 한다. **최대 하나만 참일 수 있는가**를 물으면
    답이 아니오다. 둘 다 참일 수 있다. #hypothesis
  - **포드가 하나를 더 준다** — 뉴먼의 조문이 **라이브러리냐 서비스냐**로 끝난다면, 이 장은
    서비스를 골랐을 때 치르는 값을 **변경 위험·성능·확장성·내결함성 넷**으로 갈라 적고 절충표
    셋으로 보존한다. **뉴먼 쪽에는 그 넷을 한자리에 모은 표가 없다.** #hypothesis
- **인프라 횡단 기능에 대해서는 두 소스가 같은 선을 긋는다.** 뉴먼은 **로깅 라이브러리 같은 공통
  코드는 바깥 세계에 보이지 않는 내부 개념이라 괜찮다**고 적고, 이 장은 그것들을 **운영 결합**으로
  묶어 사이드카에 넣으라고 적는다. **긋는 이유가 다르다** — 뉴먼은 **소비자에게 보이는가**로,
  이 장은 **도메인 책임이 있는가**로 가른다. #hypothesis
- **클라이언트 라이브러리는 이 장에 없다.** 뉴먼이 재사용이 결합이 되는 전형으로 드는 그 자리를
  이 장은 다루지 않는다. **두 소스가 같은 물음에 답하되 목록이 어긋나는 자리다.** 그쪽 전문은
  [DRY 원칙](../concepts/dry-principle.md)에 있다.
