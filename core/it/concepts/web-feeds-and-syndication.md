하나의 질문: **갱신되는 콘텐츠를 클라이언트가 스스로 길어 가게 하는 스타일은 무엇으로 되어
있고, 그 선택이 무엇을 되무는가.**

## 버전 조건

> **버전 조건**: 이 페이지의 채택 현황 판정("2000년에 번성했으나 오늘날에는 드물게 쓰인다",
> 쓰는 쪽이 뉴스 매체·기술 회사·블로거·과학자라는 것, 콘텐츠가 로그인으로 보호되는 소셜
> 플랫폼으로 옮겨 갔다는 것)과 피드 리더 제품 이름(Feedly·Inoreader·Newsboat·NewsBlur)과
> 클라우드 벤더·기관의 피드 주소는 **2025년 저술 시점**의 것이다. 명세 사실(RSS 1999년
> 넷스케이프, Atom의 2005년 IETF 표준화 RFC 4287, RSS 판 목록, Atom의 필수 요소와 날짜 형식
> RFC 3339, 미디어 타입 `application/atom+xml`)은 시점에 매이지 않는다. **저자들이 Atom을
> 두고 "거의 삼십 년 전"이라 적은 대목은 이 책 자신의 헐거운 표현이다** — RFC 4287은 2005년이고
> RSS가 1999년이므로 그 셈은 RSS 쪽에나 가깝다. 이 페이지는 연도를 그대로 적고 그 표현을
> 옮기지 않았다.

## 웹 피드의 규정

- **웹 피드(web feed)는 뉴스 피드(news feed)라고도 하며, 웹 페이지 콘텐츠(HTML)나 다른
  웹사이트로 가는 링크 같은 매체를 전형적으로 담은 디지털 문서**이고, 그래서 **사용자가
  웹사이트를 계속 확인하지 않고도 새 콘텐츠를 따라갈 수 있게 한다** (7장, p.227).[^dynowski2025]
- **쓰임이 한 낱말로 적힌다** — **웹 피드는 비동기 정보 방송(asynchronous information
  broadcasting)에 쓰인다.** 그리고 **뉴스·블로그 글·팟캐스트·비디오처럼 정기적인 정보 갱신을
  요구하는 상황에서 활용된다** (7장, p.227).[^dynowski2025]
- **형식은 하나가 아니다** — **웹 피드는 정기적으로 갱신되는 콘텐츠를 관련 정보의 목록을 담은
  문서로 제공해 전달하는 데이터 형식**이고, **JSON 피드와 Media RSS를 포함해 여러 피드 형식이
  있지만 이 장은 가장 널리 쓰이는 RSS와 Atom에 초점을 둔다** (7장
  §"What Is a Web Feed?", pp.227–228).[^dynowski2025]
  - **JSON 피드는 이름만 나온다** — 이 책은 그것의 판이나 규정을 다루지 않는다. 이 KB도 그
    이상을 갖지 않는다.
- 두 형식의 한 줄 규정 (7장, p.228):[^dynowski2025]
  - **RSS는 웹사이트 콘텐츠의 갱신을 표준화된 XML 형식으로 제공하는 웹 피드의 한 종류**이고,
    그래서 **사람과 컴퓨터 양쪽이 읽을 수 있다.**
  - **Atom은 웹 표준으로, 웹 피드를 위해 설계된 XML 기반 언어인 Atom 신디케이션 형식(Atom
    Syndication Format)과, 웹 자원을 발행하고 편집하는 HTTP 기반 애플리케이션 수준 프로토콜인
    Atom 발행 프로토콜(AtomPub)을 아우른다.**

## 풀 기반 API라는 자리

- 저자들이 이 스타일을 책 전체 안에 배치한다 — **이 책이 제시하는 API 대다수가 풀 기반
  API이고 웹 피드도 그 범주에 든다. 풀 기반 API(pull-based API)에서는 클라이언트가 서버에서
  데이터를 요청한다**(클라이언트가 필요할 때 데이터를 얻는다) (7장 §"Why Web Feeds?",
  p.228).[^dynowski2025]
- **그 위에서 피드가 쓸모를 얻는 조건이 적힌다** — **어떤 경우에는 클라이언트가 새 데이터가
  언제 있는지를 자주 알아야 하고, 바로 거기서 웹 피드가 쓸모 있어진다. 그것이 데이터 발견을
  비동기적으로 할 수 있게 한다** (7장, p.228).[^dynowski2025]

## 통지를 시작하는 쪽은 서버가 아니다

- **저자들이 이 대목을 못 박아 적는다** (7장, p.228):[^dynowski2025]

  > Let's be clear: the notification about updated feed content is not initiated by the
  > server; it's the client that periodically fetches feeds.

- **그다음 문장이 절차를 완성한다** — **서버는 웹 피드를 담은 문서를 돌려주고, 클라이언트는 새
  콘텐츠를 자기가 이미 가진 것과 견주어 새로 발행된 것을 더한다** (7장, p.228).[^dynowski2025]
  - **그러므로 "무엇을 이미 보았는가"의 상태는 클라이언트가 들고 있다.** 이것이 아래
    §"구독이라는 낱말이 여기서 뜻하는 것"의 대조가 걸리는 자리이고, 되무는 것 가운데
    §"이용 추적의 어려움"이 나오는 이유이기도 하다 — 서버는 누가 무엇을 읽었는지 모른다.
- **도판에만 있는 것 하나** — 그림 7-1은 구조를 웹 피드 리더(데스크톱의 RSS와 모바일의 Atom)와
  웹 피드 서버(XML 문서 — 글·뉴스·팟캐스트·블로그) 둘로 놓고, **화살표를 리더에서 서버 쪽으로
  긋고 그 위에 "Read feeds periodically"라고 적는다** (7장 그림 7-1, p.228).[^dynowski2025]
  본문에 없는 것은 **한 서버를 리더 여럿이 각자 폴링한다**는 배치이고, 그림은 그것을 화살표
  둘로 보인다.

## 쓸 자리 셋

- **뉴스 웹사이트** — 저자들이 도입에서 든 예다. **뉴스의 소유자가 새 글의 발행을 독자에게
  알리고자 하는 경우**다 (7장, p.228).[^dynowski2025]
- **클라우드 벤더의 상태 고지** — **클라우드 서비스를 쓰는 운영 팀이 벤더의 웹 피드를 따라가
  서비스 변경(새 기능·폐기·장애)을 통지받을 수 있다** (7장, p.228).[^dynowski2025]
- **보안 권고** — **사이버보안 회사들이 웹 피드로 새 위협이나 발견된 취약점을 알릴 수 있고,
  그런 피드를 따라가면 최신 갱신을 받아 대응할 수 있다** (7장, p.228).[^dynowski2025]
- **실물 목록이 표로 온다** — AWS의 상태 피드가 RSS, 애저 클라우드와 구글 클라우드가 Atom,
  미국 사이버보안·인프라 보안국(CISA)이 RSS다 (7장 표 7-1, p.229).[^dynowski2025]
  - 버전 조건: 2025년 저술 시점의 주소와 형식이다. 이 KB는 그 피드들을 스냅샷으로 갖고 있지
    않다.
  - **이 표가 위 §"통지를 시작하는 쪽은 서버가 아니다"와 함께 읽히면 관찰이 하나 나온다** —
    **같은 물음(벤더 서비스의 변경을 어떻게 알 것인가)에 큰 제공자들이 형식을 나눠 쓴다.**
    파편화가 추상이 아니라는 뜻이고, 되무는 것 가운데 파편화 항목이 그것을 다시 적는다.

## RSS — 1999년 넷스케이프

- **RSS는 웹 피드를 위한 XML 1.0 형식의 명세로 1999년 넷스케이프가 발행했다.** **RSS 피드는
  웹사이트에 발행된 콘텐츠(뉴스나 블로그)의 요약을 담고**, **RSS 명세를 따르며 그 명세가 웹
  피드를 어떻게 조직할지를 서술한다** (7장 §"Evolution of Web Feeds", p.229).[^dynowski2025]
- **운용의 모양이 적힌다** (7장, p.229):[^dynowski2025]
  - **콘텐츠 소유자가 웹 서버에 호스팅된 텍스트 파일의 형태로, 또는 HTTP 응답으로 웹 피드를
    유지한다.**
  - **사용자는 웹 피드 리더(집계기, aggregator)로 피드를 읽고 리더가 새로 더해진 콘텐츠를
    보인다.**
  - **웹 피드는 URL로 식별된다.**
  - **피드 리더는 피드 여럿을 집계할 수 있어서, 사이트를 하나씩 찾아가는 대신 여러 원천의
    콘텐츠를 한자리에서 읽기 쉽게 만든다.**

## RSS 문서의 뼈대

**저자들이 RSS 2.0 문서 하나를 예로 들고 요소마다 주를 단다** (7장 예제 7-1과 그 주,
pp.229–230).[^dynowski2025] 이 KB는 그 문서를 펜스로 옮기지 않고 구조만 담는다.

- **문서는 XML 선언으로 시작하고** 그 선언이 **XML 명세의 판과 문서에 쓰인 인코딩**을 가리킨다.
- **뿌리 요소는 `rss`**이고 **피드에 쓰인 RSS 명세의 판을 담는다.**
- **`channel` 요소가 피드의 메타데이터와 그것을 이루는 요소들을 담는다.** **RSS 명세 2.0에
  따르면 `channel`의 필수 요소는 `title`·`description`·`link`이고 `language`는 선택**이다.
- **`item` 요소가 피드의 콘텐츠를 담는다.** 콘텐츠는 **신문 기사·블로그 글·비디오·링크가 달린
  콘텐츠 등**일 수 있고, **2025년 저술 시점의 웹 피드는 전형적으로 짧은 설명과 웹사이트 링크를 담는다.**
  **`item`의 필수 요소는 `title`·`description`·`link`이고 `guid`와 `category`는 선택**이다.
  - `guid`의 중요성에 대해서는 저자들이 바깥 글 하나를 각주로 가리킬 뿐이다 (7장 각주,
    p.230).[^dynowski2025] 이 KB는 그 글을 갖고 있지 않다.

## 신디케이트와 신디케이션

**저자들이 곁글로 낱말의 유래를 푼다** (7장 곁글 §"Syndicate and Syndication",
p.230).[^dynowski2025]

- **출판에서 신디케이트(syndicate)는 개별 역량을 넘어 제공물을 넓히려고 콘텐츠를 나누는
  발행인들의 모임**이다.
- **신디케이션(syndication)은 콘텐츠를 다른 조직에 팔아 여러 곳에서 발행되거나 보이게 하는
  행위**를 가리킨다. 그것이 **콘텐츠 창작자(인쇄·라디오·텔레비전)로 하여금 더 넓은 청중에
  닿게 한다.**
- **웹 피드의 맥락에서 가리키는 것은 웹 신디케이션(web syndication)**이고, 그것은 **블로그
  글·팟캐스트·비디오 같은 콘텐츠를 다른 웹사이트나 플랫폼으로 배포하고 집계하는 과정**이다.

## RSS가 레거시가 된 이유

- **2025년 저술 시점에 RSS 피드는 레거시 기술로 여겨진다**고 저자들이 적고, 새 신디케이션 형식이 나오게 한
  요인 셋을 든다 (7장, p.230):[^dynowski2025]
  - **RSS 피드의 여러 변종이 파편화됐다** — 0.90·0.91·0.92·1.0·1.1·2.0.
  - **그 결과 피드의 검증이 어려워졌고**, **웹 피드 리더가 그것들을 모두 지원하기 어려웠다.**
  - **확장성이 없었다** — 다만 **확장성은 RSS의 나중 판들이 다뤘다**고 단서가 붙는다.

## Atom — 명세가 된 후계

- **Atom 웹 피드는 RSS의 단점을 다루려는 시도로 생겨났다**고 저자들이 적고 고친 것 넷을 든다
  (7장 §"What Is Atom Feed?", p.231):[^dynowski2025]
  - **메타데이터 확장성을 허용한 것.**
  - **콘텐츠 국제화를 위해 유니코드를 지원한 것.**
  - **피드가 여러 콘텐츠 타입(텍스트·HTML·XML)을 피드 요소로 담을 수 있게 한 것.**
  - **가장 중요하게는, 공식 웹 피드 명세가 된 것** — **2005년 IETF가 Atom 신디케이션 형식
    RFC 4287로 표준화했다.**
- **규정** — **Atom은 RSS의 후계다. Atom은 웹 피드를 서술하는 XML 1.0 기반 신디케이션 형식이자
  발행 프로토콜이다. Atom 신디케이션 형식의 피드는 사람과 기계가 모두 읽을 수 있는 형식이며,
  엔티티 요소들로 지어지고 각 엔티티를 서술하는 확장 가능한 메타데이터를 갖는다** (7장,
  p.231).[^dynowski2025]
- **설계 의도와 기원** — **Atom 피드는 웹 콘텐츠(웹 로그·팟캐스트·뉴스 헤드라인 등)를 다른
  웹사이트나 플랫폼으로 배포할 수 있는 방식으로 신디케이트하도록 설계됐고**, 그 기원은 **샘
  루비의 글 "Anatomy of a Well-Formed Log Entry"를 가리킨다** (7장, p.231).[^dynowski2025]
  이 KB는 그 글을 원전으로 갖고 있지 않다.

## Atom 문서의 뼈대

**저자들이 항목 하나짜리 Atom 피드를 예로 들고 주를 단다** (7장 예제 7-2와 그 주,
pp.231–232).[^dynowski2025] 구조만 담는다.

- **문서는 XML 1.0 선언과 인코딩으로 시작한다.**
- **뿌리 요소는 `feed`**이고 **Atom 신디케이션 형식을 쓰는 XML 이름 공간(`xmlns`)을 정의한다.**
  **Atom 피드의 필수 요소는 `id`·`title`·`updated`이고 `link`와 `author`는 권장 요소**다.
- **`entry` 요소가 피드의 콘텐츠를 담는다.** **필수 요소는 `id`·`title`·`updated`이고 권장
  요소는 `link`와 `summary`**다.
- **미디어 타입이 정해져 있다** — **Atom 피드는 `application/atom+xml` 미디어 타입으로
  식별되고 보통 피드 집계기가 읽는다** (7장, p.232).[^dynowski2025] 미디어 타입이 프로토콜
  층에서 무엇을 하는지는
  [표현 메타데이터](../concepts/http-representation-metadata.md)에 있다.
- **피드를 합칠 수 있다** — **새 웹 피드를 다른 피드들로 구성할 수 있고**, 저자들의 예가
  **여러 스포츠 웹사이트의 농구 뉴스를 피드 하나로 합치는 것**이다 (7장,
  p.232).[^dynowski2025]

## Atom이 RSS와 갈리는 넷

- **Atom 문법은 모듈성을 위해 설계됐고 일부 요소는 명세에 따라 필수다** (7장,
  p.232).[^dynowski2025]
- **RSS 피드와 견주어 갈리는 것 셋이 이어서 적힌다** (7장, p.232):[^dynowski2025]
  - **Atom 피드는 항목마다 개별 언어를 지정할 수 있다.**
  - **날짜 형식이 RFC 3339 명세를 따른다**(`YYYY-MM-DDTHH:MM:SSZ`). 날짜 형식이 HTTP 쪽에서
    어떻게 다뤄지는지는 [날짜 형식](../concepts/http-date-formats.md)에 있다.
  - **그 요소들을 Atom 피드 문서의 맥락 밖에서 재사용할 수 있다.**
- **그 재사용의 실물이 AtomPub 쪽 쓰임이다** — 저자들은 앞 예제의 `<author>` 항목을 `<entry>`
  요소를 담은 다른 XML 문서에서 재사용해 보이고, 그런 문서를 **AtomPub 프로토콜을 지원하는
  서버에 HTTP `POST`로 보내 웹 자원을 만들거나 고칠 수 있다**고 적는다 (7장,
  p.232).[^dynowski2025]
  - 그 예제에 붙는 XML 규정 하나 — **CDATA(문자 데이터)는 클라이언트가 `<`·`/`·`&` 같은 특수
    문자를 이스케이프하지 않고도 콘텐츠를 렌더링할 수 있게 하는 특별한 XML 절**이다 (7장,
    p.232).[^dynowski2025]
  - **그래서 이 스타일은 읽기 전용이 아니다** — 피드 형식이 읽는 쪽의 문서 형식이고, AtomPub이
    쓰는 쪽의 프로토콜이다. 다만 이 책은 AtomPub의 구현을 다루지 않는다.

## 둘 다 살아남았다

- **Atom이 공식 표준인데도 둘 다 여전히 쓰인다**고 저자들이 적고 이유를 든다 (7장,
  p.233):[^dynowski2025]
  - **RSS의 옛 판들을 통일하고 폐기할 관장 조직이 없었던 것이 RSS 피드를 개별 개발자들이
    포크하고 갈라지게 했고, 그 결과 판이 둘(v1.\*과 v2.\*)로 남았다.**
  - **RSS 2.0이 모든 RSS 판 가운데 가장 많이 쓰인다.**
  - **RSS의 생존은 첫 웹 피드로서의 이른 지배에 기인할 공산이 크다.**
  - **구글 리더가 중단된 뒤 RSS가 인기를 되찾았고**, 그 중단은 **사용 감소와 중앙화된 소셜
    네트워크로의 더 넓은 이동에 기인한다**고 적힌다.
- **이 장이 열릴 때 이미 판정을 하나 달아 두었다** — **웹 피드는 2000년에 번성했으나 2025년 저술 시점에
  이 기술은 드물게 쓰이고 그 사용자는 뉴스 매체·기술 회사·블로거·과학자다.** 그리고 **콘텐츠가
  메타나 X 같은 로그인으로 보호되는 소셜 플랫폼으로 옮겨 간 뒤로 인기를 잃었다** (7장,
  p.227).[^dynowski2025] 저자들은 **역사적 중요성과 XML의 사용 때문에 교육적 연습으로도
  쓸모 있다**며 그럼에도 한 장을 쓰기로 했다고 적는다.
  - 버전 조건: 2025년 저술 시점의 채택 관찰이다.

## 피드를 내주는 쪽

**이 절은 얇다.** 저자들의 구현은 장고 웹 프레임워크의 피드 클래스에 매여 있고, 이 KB가 담는
것은 **피드 하나를 내주려면 무엇을 정해야 하는가**뿐이다.

- **엔드포인트가 둘 필요하다** — 하나는 **주어진 도시의 일기 예보를 담은 HTML 쪽을 렌더링하고**,
  다른 하나는 **도시들을 열거하고 리더를 첫째 엔드포인트로 보내는 Atom 피드를 렌더링한다**
  (7장 §Implementation, p.234).[^dynowski2025]
  - **곧 피드는 콘텐츠 자체가 아니라 콘텐츠로 가는 링크의 목록이 될 수 있다.** 위
    §"RSS 문서의 뼈대"가 적은 "2025년 저술 시점의 웹 피드는 전형적으로 짧은 설명과 링크를 담는다"가
    구현에서 이 모양으로 나타난다.
- **피드 뷰가 정하는 것이 다섯이다** (7장, pp.234–235):[^dynowski2025]
  - **피드를 유일하게 식별하는 값** — **피드 데이터가 섞이는 것을 막는다**고 저자들이 적는다.
  - **피드 타입** — 이 값이 **Atom 생성기로 지정되면 그 뷰가 Atom 피드를 만들어 낸다.** 곧
    **RSS로 낼 것인가 Atom으로 낼 것인가가 프레임워크의 생성기 선택 한 줄**이다.
  - **언어.**
  - **항목의 목록을 돌려주는 메서드.**
  - **항목마다의 제목·설명·링크·마지막 갱신 시각을 각각 정하는 메서드들.**
- **도판에만 있는 것 하나** — 그림 7-2는 그 구성을 웹 피드 리더가 피드 엔드포인트에
  **`GET /forecast/feed HTTP/1.1`**을 보내고 서비스가 **"Atom 1.0"이라 이름 붙은 문서**를
  내주는 그림으로 그린다 (7장 그림 7-2, p.233).[^dynowski2025] 본문은 그 판 이름을 적지
  않는다.
- 구현에 딸린 조각 하나 — 저자들의 예제에서 **모든 도시는 UUID로 식별되고 그것이 같은 이름의
  도시 사이 충돌을 막는다** (7장, p.233).[^dynowski2025]

## 피드를 읽는 쪽

- **피드 리더(집계기)는 사용자가 웹 피드를 따라가고 그것들을 한자리에 모으게 한다.** 전형적인
  리더는 **피드를 읽음으로 표시하고, 키워드로 검색하고, 범주로 정리하는** 일을 하게 해 준다
  (7장 §"Reading Feeds", p.236).[^dynowski2025]
- **형태가 넷으로 적힌다** — **데스크톱, 모바일, 웹 브라우저 플러그인, 웹 기반 애플리케이션**
  이다. 저자들이 드는 인기 있는 리더가 **Feedly·Inoreader·Newsboat·NewsBlur**다 (7장,
  p.236).[^dynowski2025]
  - 버전 조건: 2025년 저술 시점의 제품 목록이다.
- **고를 때 따질 것 셋** — **클라우드 기반(웹 서비스)인가, 스마트폰을 지원하는가, 자체
  호스팅을 원하는가**다 (7장, p.237).[^dynowski2025]
- **구독한다는 행위의 실체가 한 줄로 적힌다** — **웹 피드에 새로 발행되는 콘텐츠의 갱신을
  받으려면 피드의 제목이나 URL을 피드 리더에 붙여 넣으면 되고, 그러면 리더가 피드를 가져와
  콘텐츠를 사용자에게 보인다** (7장, p.237).[^dynowski2025]
  - **곧 등록은 서버가 아니라 리더 쪽에서 일어난다.** 서버는 누가 자기 피드를 읽는지 모른다.
    아래 §"구독이라는 낱말이 여기서 뜻하는 것"이 걸리는 자리다.
- 저자들이 명령줄 리더 하나로 자기 피드를 읽어 보이고 그 결과가 **읽지 않은 글의 수**다 (7장,
  p.237).[^dynowski2025] **읽음과 읽지 않음의 상태도 리더가 들고 있다.**

## 보안

- **기본 배치부터 적힌다** — **보통 웹 피드는 링크만 있으면 누구나 읽을 수 있도록 일반 대중에
  노출할 의도로 만들어진다. 그러나 피드가 제한되거나 민감한 콘텐츠를 담으면 접근을 통제하려고
  인증 방법을 구현한다** (7장 §Security, p.238).[^dynowski2025]
  - **기본 인증(basic authentication)은 요청마다 사용자 이름과 비밀번호를 주게 하는데 2025년 저술 시점에
    권장되지 않는다** — **요청마다 오래 사는 자격 증명을 담기 때문**이다.
  - **대안이 토큰 기반 인증(token-based authentication)**이고 **자격 증명 노출의 문제를
    다루되 토큰에 만료일이 있으므로 잦은 토큰 재생성을 요구한다.**
  - 그 둘의 프로토콜 쪽 규범은
    [HTTP 인증 프레임워크](../concepts/http-authentication-framework.md)에 있다.
- **HTTP `GET` 엔드포인트라는 사실이 공격면을 정한다** — **웹 피드의 콘텐츠는 HTTP `GET`
  엔드포인트로 실려 나가고, 그것이 피드를 HTTP와 얽힌 여러 공격에 취약하게 만든다(암호화된
  형태에서도 그렇다)** (7장, p.238).[^dynowski2025]
- **예로 드는 것이 DoS 공격**이다 — **공격자가 피드 엔드포인트에 HTTP 요청을 쏟아부어 피드
  서버에 과부하를 걸 수 있다.** 저자들은 완화를 **OSI 모형의 여러 층에서** 다루라고 적는다
  (7장, p.238):[^dynowski2025]
  - **네트워크 계층(3층)** — **단일 IP나 지리적 지역에서 오는 요청을 차단하고(지오블로킹),
    방화벽이나 라우터로 초당 패킷 수·초당 바이트 수·과도한 SYN 패킷 같은 한도를 강제한다.**
  - **애플리케이션 계층(7층)** — **IP에서 오는 과도한 요청을 초·분·시·일 단위 할당량으로
    억누른다.**
  - **그리고 로드 밸런싱으로 서버 하나에 걸리는 부하를 줄이고 요청을 여러 서버에 나누면 단일
    실패 지점의 가능성도 낮아진다.**
  - OSI 층의 대응은
    [네트워크 계층 모형과 패킷 관찰](../concepts/network-layer-models-and-packet-observation.md)에 있다.
- **RSS 피드 주입(RSS feed injection)이 다른 종류의 공격이다** — **공격자가 피드를 담은 문서에
  XSS로 악성 콘텐츠를 주입하거나 기존 콘텐츠를 조작할 수 있다. 공격의 목적은 피드의 콘텐츠를
  고쳐 사용자를 다른 웹사이트로 보내거나 악성 자바스크립트 코드를 넣는 것**이다. **그 공격이
  가능한 이유는 클라이언트도 서버도 피드의 콘텐츠를 검증하지 않기 때문**이고, **결과는 악성
  링크를 누른 사람의 위험과 피드 소유자의 신뢰성 훼손**이다. 방어는 **피드 콘텐츠를 살균하고
  클라이언트와 서버 양쪽의 RSS 소프트웨어를 보안 패치로 최신 상태로 유지하는 것**이다 (7장,
  p.238).[^dynowski2025]
- **마지막 대목이 이 스타일의 비대칭을 드러낸다** — **대부분의 이메일 제공자는 이메일의 악성
  콘텐츠를 잡아내는 도구를 갖추고 있지만(그래서 때로 중요한 메일이 스팸함으로 간다), RSS
  클라이언트에는 그런 도구가 없어서 콘텐츠를 가려 읽고 링크를 누르기 전에 살피는 책임이
  사용자에게 있다.** 같은 책임이 **피드 소유자**에게도 있어서 **악성 콘텐츠가 있는지 피드를
  감시하고 제거해야 한다** (7장, p.239).[^dynowski2025]

## 얻는 것 다섯

**저자들이 절충 절을 한 문장으로 연다** — **웹 피드는 클라이언트(피드 리더나 집계기)가 새
콘텐츠를 얻으려 주기적으로 당기는 API를 짓게 해 준다** (7장 §Trade-Offs,
p.239).[^dynowski2025]

- **방송(Broadcasting)** — **웹 피드 클라이언트가 주기적으로 갱신을 요청한다. 웹 피드의
  콘텐츠가 바뀌면 클라이언트가 그것을 알게 되고, 마치 정보가 그들에게 직접 방송되는 것과
  같다.**
  - **"같다"가 이 항목의 전부다** — 실제 기제는 여전히 폴링이고, 저자들의 표현이 그것을
    감추지 않는다.
- **제때의 갱신(Timely updates)** — **웹 피드의 당기는 주기를 짧은 간격(초)으로 조정할 수
  있어서 발행되자마자 최신 갱신을 얻을 수 있다.**
- **콘텐츠 집계(Content aggregation)** — **웹 피드 리더가 피드 여럿을 모아 주어, 사이트를
  하나씩 찾아가는 대신 여러 원천의 콘텐츠를 한자리에서 읽기 쉽게 한다.**
- **콘텐츠 신디케이션(Content syndication)** — **피드 소유자가 블로그 글·팟캐스트·비디오 같은
  콘텐츠를 다른 웹사이트나 플랫폼으로 신디케이트해 원래 플랫폼 너머로 도달 범위를 넓히게
  한다.**
- **프라이버시(Privacy)** — **로그인 없는 리더는 사용자가 원래 플랫폼과 직접 상호작용하지 않고
  콘텐츠에 닿게 해 익명성을 높일 수 있고, 그래서 수집될 수 있는 개인 데이터의 양을 잠재적으로
  줄인다** (7장, p.239).[^dynowski2025]

## 되무는 것 여섯

- **계약의 부재(Lack of contract)** — **웹 피드는 피드 제공자와 소비자 사이의 계약이 아니다.
  제공자가 피드를 만들거나 갱신하기를 그만두면 소비자는 그 피드가 더 이상 갱신되지 않는지를
  알 수 없다. 그래서 클라이언트는 제공자가 피드를 갱신해 주기를 의지한다** (7장,
  p.239).[^dynowski2025]
  - **이것이 이 스타일과 다른 스타일을 가르는 가장 날카로운 항목**이다. 다른 스타일에서 계약이
    무엇을 뜻하는지는 [계약의 스펙트럼](../concepts/contract-spectrum.md)과
    [API 이름과 버저닝](../concepts/api-naming-and-versioning.md)에 있다 — 그쪽들이 재는 것은 **계약이
    얼마나 엄격한가**인데, 여기서는 **계약이 아예 없다**는 것이 판정이다.
- **온라인에서의 낮은 사용자 참여(Low user engagement online)** — **웹 피드 사용자가 온라인
  플랫폼에서 참여하지 않는 것이 콘텐츠 창작자·발행인·소셜 플랫폼에게, 특히 광고 수익 면에서
  도전이 된다. 웹 피드를 따라간다고 해서 사용자가 플랫폼에서 시간을 보내는 것은 아니다.**
  **플랫폼 소유자에게 이것이 문제인 까닭은 플랫폼이 광고와 데이터 수집을 극대화하려고 사용자의
  긴 체류를 우선하기 때문이고, 웹 피드가 그 노력을 허문다** (7장, p.240).[^dynowski2025]
  - **위 §"얻는 것 다섯"의 프라이버시 항목과 같은 사실의 두 면이다** — 읽는 쪽에 이익인 것이
    플랫폼 쪽에 손해다. 저자들이 그 대칭을 명시하지는 않는다.
- **보안의 도전** — 위 §"보안"의 내용을 되풀이하며, **피드 소프트웨어를 클라이언트와 서버
  양쪽에서 최신으로 유지하라**는 처방을 다시 적는다 (7장, p.240).[^dynowski2025]
- **정보 과부하(Information overload)** — **집계라는 이점이 동시에 단점이 될 수 있다. 너무 많은
  웹 피드를 읽는 사용자는 정보에 압도될 수 있고, 그것이 콘텐츠를 아예 읽지 않는 결과로 이어질
  수 있다** (7장, p.240).[^dynowski2025]
- **파편화(Fragmentation)** — **웹 피드 형식이 여러 판으로 파편화되어 있다. 그것은 피드 리더가
  서로 다른 신디케이션 피드와 그 판들과 확장들을 지원해야 한다는 뜻이다** (7장,
  p.240).[^dynowski2025] 위 §"RSS가 레거시가 된 이유"와 §"둘 다 살아남았다"가 그 역사다.
- **사용자 활동 추적의 부재(Lack of user activity tracking)** — **콘텐츠 창작자로서는 사용자가
  자기 웹 피드와 어떻게 상호작용하는지 알고 싶지만, 누가 피드에 접근하는지, 얼마나 자주 글을
  읽는지, 어디서 들어오는지 같은 지표를 추적하기가 번거롭다.** 가능하기는 하되 기법이
  필요하고, 저자들이 셋을 든다 (7장, p.240):[^dynowski2025]
  - **서버 로그 분석** — **웹 피드 URL로 온 HTTP 호출 수를 세고, 로그에서 시각·사용자 에이전트·
    IP 주소를 파싱한다.**
  - **질의 파라미터** — **`?source=blog` 같은 파라미터를 붙여 클라이언트가 어디서 오는지의
    정보를 얻는다.**
  - **리다이렉트 링크** — **추적에 쓰이는 중간 링크를 사용자에게 주고 그것이 웹 피드 콘텐츠로
    리다이렉트하게 한다.**
  - **이 셋이 전부 서버가 클라이언트의 상태를 모르기 때문에 생기는 우회**다. 위
    §"통지를 시작하는 쪽은 서버가 아니다"의 귀결이다.

## 구독이라는 낱말이 여기서 뜻하는 것

**이 KB에서 "구독"은 적어도 셋을 가리킨다. 이 스타일이 그 가운데 어느 것도 아니라는 것이 이
절의 요지다.** 저자들은 이 대조를 적지 않았고, 이 페이지가 KB 안의 이웃과 맞댄 것이다.

| 무엇을 구독이라 부르는가 | 누가 주도하는가 | 상태를 누가 들고 있는가 | 서버가 구독자를 아는가 |
|---|---|---|---|
| 웹 피드 | 클라이언트가 주기적으로 당긴다 | 리더가 읽음·읽지 않음을 들고 있다 | 모른다 |
| 발행-구독 메시징 | 브로커가 구독자에게 민다 | 브로커가 채널과 구독을 들고 있다 | 안다 |
| 이벤트 스트림의 컨슈머 | 컨슈머가 오프셋으로 읽는다 | 오프셋이 브로커에 기록된다 | 안다 |
| GraphQL 구독 연산 | 원천의 사건에 응답해 밀린다 | 오래 사는 연결이 든다 | 안다 |

- **웹 피드 쪽의 근거는 이 페이지 안에 있다** — 통지를 서버가 시작하지 않는다는 명시,
  클라이언트가 자기가 이미 가진 것과 견주어 새것을 더한다는 절차, 등록이 리더에 URL을 붙여
  넣는 일이라는 서술, 그리고 되무는 것 가운데 이용 추적이 어렵다는 항목이 전부 같은 사실의
  다른 면이다.
- **발행-구독 쪽과 이벤트 스트림 쪽은 [발행/구독 메시징](../concepts/publish-subscribe-messaging.md)과
  [이벤트 스트림과 이벤트 브로커](../concepts/event-streams-and-brokers.md)가 갖는다.**
  **특히 그 첫째 페이지에는 이 스타일과 직접 맞닿는 절이 이미 있다** — 마이크로서비스 실무서가
  **브로커 대신 HTTP 피드(Atom)로 이벤트를 전파하는 선택지**를 적고, 그 대가로 **소비자가 어떤
  메시지를 봤는지 스스로 추적하고 자기 폴링 일정을 관리해야 한다**는 것을 드는 자리다.
  - **두 소스가 같은 방향이다.** 그쪽이 그것을 **대가**로 적고 이쪽은 **규정**으로 적는다 —
    클라이언트가 상태를 든다는 같은 사실이다. 겨루지 않는다.
  - **그쪽에는 이 페이지에 없는 경고가 하나 더 있다** — Atom으로 브로커의 동작(경쟁 소비자
    패턴 같은)을 하나씩 다시 구현하게 되는 경로다. 이 책은 웹 피드를 이벤트 전파 기반으로
    쓰는 물음을 다루지 않으므로 그 경고를 적지 않는다.
- **GraphQL 구독 연산은 같은 책 6장이 규정한다** —
  [GraphQL의 구성 요소와 실행](../concepts/graphql-constructs-and-execution.md) §"연산 셋"에 있다.
  **같은 책이 두 장에서 같은 낱말을 다른 기제에 붙인다는 것이 이 표의 요지**다.
- #hypothesis 이 낱말이 겹치는 이유는 셋 다 **"새것이 생기면 알고 싶다"는 같은 요구**에
  답하기 때문이고, 갈리는 것은 **그 요구를 누구의 자원으로 채우는가**다. 저자들은 이 일반화를
  적지 않았다.
