하나의 질문: **레거시 시스템의 저장소 안에 갇힌 업무 데이터를 어떻게 이벤트 스트림으로
꺼내고, 그 꺼내는 방식마다 무엇을 치르는가.**

## 무엇을 해방이라 부르는가

- 규정이 한 문장이다 (6장 §"What Is Data Liberation?", p.128):[^bellemare2025]

  > Data liberation is the identification and publication of cross-domain data sets to their
  > corresponding event streams and is part of a *migration strategy* for event-driven
  > architectures.

  - **교차 도메인 데이터셋(cross-domain data sets)** 은 **한 데이터 저장소에 저장되어 있으면서
    다른 체계들이 필요로 하는 모든 데이터**다. 기존 서비스와 데이터 저장소 사이의 점대점 의존이
    해방해야 할 교차 도메인 데이터를 짚어 주는 일이 잦다 (6장, p.128).[^bellemare2025]
  - 낱말이 둘로 갈린다 — 기존 체계와 상태 저장소에서 데이터를 **소싱(sourcing)** 하는 것이 해방이고,
    반대로 스트림의 이벤트를 기존 상태 저장소로 **싱킹(sinking)** 하는 것이 그 짝이다. 이벤트 기반이
    아닌 레거시 애플리케이션은 기술과 성능 제약 때문에 스트림을 직접 읽지 못할 수 있어서 싱킹이
    필요해진다 (6장, pp.127–128).[^bellemare2025]
- **해방이 강제하는 것이 둘이다** — **단일 진실 원천(single source of truth)** 과 **체계 사이 직접
  결합의 제거**. 체계들은 더 이상 하부 데이터 저장소나 애플리케이션 API에 직접 결합하지 않고
  **오직 이벤트 스트림에만** 결합한다 (6장, p.128).[^bellemare2025]
- 이 장이 이행 전략의 자리라는 것을 저자가 명시한다. 조직에는 모노리식 관계형 데이터베이스
  애플리케이션이 하나 이상 있을 것이고, 구현들 사이의 점대점 연결이 이미 있을 것이며, 중간 파일
  저장소를 통한 정기 덤프 동기화 같은 **이벤트 비슷한 기제**가 이미 있을 수도 있다. 이 장이 다루는
  것은 그 자리에서 중요한 업무 데이터를 **이벤트 스트림으로 대신 제공하기 시작하는 법**이다 (6장,
  p.127).[^bellemare2025]
- 왜 그것이 필요한가의 근거는 이 KB의 [소통 구조 셋](../concepts/communication-structures.md)에 있다. 이 장의
  맺음이 그 어휘로 돌아온다 — 레거시 체계가 **핵심 업무 도메인 모델의 대부분을 어떤 형태의 중앙화된
  구현 소통 구조 안에** 쥐고 있고, 조직의 다른 영역이 결합되지 않은 새 제품과 서비스를 조립할 수
  있으려면 그 데이터가 거기서 해방되어야 한다 (6장 §Summary, p.155).[^bellemare2025]

## 출발점이 되는 실패 — 이중 쓰기 안티패턴

- 규정 (6장 §"The Dual Write Antipattern", p.129):[^bellemare2025]

  > The dual write antipattern is when a service writes data to two data stores independently of
  > each other.

  - 서비스가 데이터 한 덩이를 **상태 저장소와 이벤트 브로커의 이벤트 스트림 양쪽에** 쓰는 장면이다.
    **두 서비스가 서로 완전히 독립이라 단순한 트랜잭션으로 커밋할 수 없고**, 한쪽 커밋이 성공한 뒤
    다른 쪽 커밋이 실패할 수 있다 (6장, p.129).[^bellemare2025]
- **재시도로 덮이지 않는다** — 원자적으로 쓸 수 없다는 것을 발견한 개발자가 어깨를 으쓱하고 트랜잭션
  없이 그냥 할 수도 있다. 실패하면 재시도하면 된다고 여기지만 커밋이 실패하는 다른 이유가 있다 —
  **유효하지 않은 스키마, 영구히 이전된 서비스, 하드웨어나 설정 문제로 인한 길게 이어지는 대형 장애**.
  결국 생산자 서비스는 포기해야 하고 **그 시점에 두 서비스의 데이터는 영구히 갈라진다** (6장,
  p.129).[^bellemare2025]
- **2PC는 답이 되지 못한다** — 2단계 커밋(two-phase commits, 2PC)을 지원하는 서비스는 여러 참여자가
  드는 분산 트랜잭션에 실제로 낄 수 있다. **그러나 현실은 많은 데이터 저장소가 2PC를 지원하지 않고
  많은 이벤트 브로커도 그렇다** (6장, p.129).[^bellemare2025]
  - 버전 조건: **아파치 카프카에 2PC 프로젝트가 있으나 이 책의 출간 시점에 진행 중으로 남아 있다**
    (6장, p.129).[^bellemare2025] 2025년 저술 시점의 진행 상태에 대한 서술이다.
- **그래서 이 장의 나머지 전부가 "2PC를 쓰지 않고 해방하는 길"이다** — 저자가 절을 그렇게 닫는다
  (6장, p.129).[^bellemare2025]

## 해방 패턴 셋

- 하부 데이터 저장소에서 데이터를 꺼내는 주요 패턴이 셋이다. **해방된 데이터가 새 단일 진실 원천을
  이루도록 되어 있으므로 그것은 데이터 저장소의 데이터 전부를 담아야 하고**, 새 삽입·갱신·삭제로
  계속 최신이어야 한다 (6장 §"Data Liberation Patterns", p.130).[^bellemare2025]
- 셋의 규정을 원문 그대로 둔다 (6장, p.130):[^bellemare2025]

  > *Query-based* You extract data by querying the underlying state store. This can be performed
  > on any data store.

  > *Log-based* You extract data by following the append-only log for changes to the underlying
  > data structures. This option is available only for select data stores that maintain a log of
  > the modifications made to the data.

  > *Outbox table-based* In this pattern, you first push data to a table used as an output queue.
  > Another thread or separate process queries the table, emits the data to the relevant event
  > stream, and then deletes the associated entries. This method requires that the data store
  > support both transactions and an output queue mechanism, usually a standalone table configured
  > for use as a queue.

- 네 번째 수단인 **트리거(trigger)** 는 별도 절로 뒤에 온다. 저자가 그것을 이 셋과 나란히 세우지 않고
  **앞선 절들의 감사·binlog·WAL 패턴보다 앞선 기술**로 소개한다 (6장 §"Capturing Change-Data Using
  Triggers", p.146).[^bellemare2025] 아래 [트리거로 하는 변경 데이터 포착](#트리거로-하는-변경-데이터-포착)이
  그 절이다.

## 셋이 공유하는 조항 하나 — 타임스탬프 순서

- **셋이 각각 고유하지만 공통점이 하나 있다** — 각 패턴은 **정렬된 타임스탬프 순서로 이벤트를 내야
  하고**, 출력 이벤트 레코드 헤더에 **원천 레코드의 가장 최근 `updated_at` 시각**을 써야 한다 (6장,
  p.130).[^bellemare2025]
- 왜인가 — 그래야 **생산자가 이벤트를 발행한 시각이 아니라 이벤트의 발생 시각**에 따라 타임스탬프가
  찍힌 스트림이 나온다. **이것이 데이터 해방에서 특히 중요한 이유는 업무 흐름에서 사건이 실제로 언제
  일어났는지를 정확히 표현하기 때문**이다 (6장, p.130).[^bellemare2025] 타임스탬프 기반 인터리빙의
  전문은 저자가 9장으로 미룬다.

## 중앙 해방 프레임워크

- 해방의 한 방식이 **전용 중앙화 프레임워크**를 써서 데이터를 스트림으로 뽑는 것이다. 예로 드는 것이
  **Kafka Connect(카프카 플랫폼 전용)·Debezium·Apache NiFi** 셋이고, 이들은 기성 연결 옵션으로 온갖
  데이터 저장소·애플리케이션·SaaS 엔드포인트에 붙는다. 일부 커넥터 프레임워크는 **드문 사용례를 위해
  직접 커넥터를 쓰게** 해 준다 (6장 §"Data Liberation Frameworks", p.130).[^bellemare2025]
  - 버전 조건: 2025년 저술 시점의 제품 지형에 대한 서술이다.
- 공통 성질 둘 — 각 프레임워크는 하부 데이터셋에 **질의를 실행해 그 결과를 출력 이벤트 스트림으로
  흘려보내고**, **인스턴스를 더해 변경 데이터 포착 잡의 수용력을 늘릴 수 있게** 확장 가능하다 (6장,
  p.130).[^bellemare2025]
- 스키마 레지스트리와의 통합 수준은 제각각이다 — **컨플루언트(아파치 카프카)가 제공하는 스키마
  레지스트리와의 통합 수준이 다양하게 지원되고, 다른 레지스트리를 받치려면 커스터마이즈가 필요하다**
  (6장, p.131).[^bellemare2025] 커넥터가 사는 자리의 전문은 [카프카 커넥트](../concepts/kafka-connect.md)에
  있다.

## 로그 기반 포착 — 이득 넷과 단점 셋

**기제 자체는 이 KB의 [변경 데이터 캡처](../concepts/change-data-capture.md)가 갖는다.** 이 절이 더하는 것은
그 기제를 **통합 수단으로 골랐을 때의 채점표**다.

- 이 소스의 CDC 규정 (6장 §"Liberating Data Using Change-Data Capture", p.131):[^bellemare2025]

  > Change-data capture is a process that reads (or *tails*) these logs, converts the individual
  > data store changes into events, and writes them to the event stream.

  - 포착 대상에 **개별 레코드의 생성·삭제·갱신**뿐 아니라 **개별 데이터셋과 그 스키마의 생성·삭제·
    변경**도 든다 (6장, p.131).[^bellemare2025] 뒤쪽 [포착 중인 데이터셋의 정의를 바꿀 때](#포착-중인-데이터셋의-정의를-바꿀-때)가
    그 둘째 부류를 다룬다.
- **CDC는 데이터베이스에 가해진 *모든* 변경을 준다** — 어떤 전이도 놓치지 않고 파생 스트림이 모든
  갱신을 담는다. CDC 프레임워크는 **어느 필드를 이벤트에 넣을지 지정하는 설정 파일**을 제공해 내부
  데이터를 바깥세상에서 걸러 낼 수 있게 하고, `serverId`·`transactionId` 같은 메타데이터를 넣을지도
  고를 수 있다 (6장, p.132).[^bellemare2025]
- 보장의 등급이 명시된다 — 체인지로그에서 포착할 때 **진행 상황을 체크포인트해야** 하고(도구에 내장된
  경우도 있다), 포착 기제가 실패하면 체크포인트로 마지막 체인지로그 색인을 복구한다. **이 접근이 줄 수
  있는 것은 최소 한 번(at-least-once) 생산뿐이며, 그것이 해방의 엔티티 중심 성격에는 대체로 알맞다** —
  **엔티티 데이터의 갱신은 멱등이므로 레코드 하나가 더 생산되는 것은 무해하기 때문**이다 (6장,
  p.132).[^bellemare2025]
- **이득 넷** (6장 §"Benefits of Change-Data Capture Using Data Store Logs",
  p.134):[^bellemare2025]

  | 이득 | 저자의 서술 |
  |---|---|
  | **삭제 추적(Delete tracking)** | 데이터 저장소 로그가 삭제를 담으므로 레코드가 언제 지워졌는지 볼 수 있고, 그것을 **툼스톤 이벤트**로 바꿔 하류 삭제와 스트림 압착을 가능하게 한다 |
  | **데이터 저장소 성능에 최소한의 영향** | 로그를 전제로 하는 저장소에서는 저장소 성능에 **아무 영향 없이** 포착할 수 있다. SQL Server처럼 **변경 테이블**을 쓰는 쪽은 영향이 데이터 양에 달렸다 |
  | **낮은 지연의 갱신** | 이벤트가 데이터 저장소 로그에 쓰이는 즉시 전파되어 **상대적으로 낮은 지연**의 스트림이 된다 |
  | **비차단 스냅샷(Nonblocking snapshots)** | 원천 저장소의 정상 운영을 방해하지 않고 스냅샷을 만들 수 있다 |

- **단점 셋** (6장 §"Drawbacks of Change-Data Capture Using Data Store Logs",
  p.134):[^bellemare2025]

  | 단점 | 저자의 서술 |
  |---|---|
  | **내부 데이터 모델의 노출** | **내부 데이터 모델이 체인지로그에 완전히 노출된다.** 하부 모델의 격리를 조심스럽고 선별적으로 관리해야 한다 |
  | **저장소 바깥의 비정규화** | 체인지로그는 이벤트 데이터만 담는다. 일부 기제는 구체화 뷰에서 뽑을 수 있으나 많은 경우 비정규화가 **하류 어딘가에서** 일어나야 하고, 그래서 **고도로 정규화된 이벤트 스트림**이 생겨 하류 마이크로서비스가 외래 키 조인과 비정규화를 떠안게 된다 |
  | **데이터셋 스키마와 출력 이벤트 스키마 사이의 깨지기 쉬운 의존** | 원천 저장소에서 유효한 데이터 모델 변경(데이터셋 변경, 필드 타입 재정의)이 **하류 소비자에게 깨는 변경**을 일으킬 수 있다 |

  - 둘째 단점이 다음 장 전체를 부른다 — 그 비정규화를 어디서 할 것인가가
    [비정규화와 이벤트화](denormalization-and-eventification.md)의 물음이다.

## 초기 상태 스냅샷

- 문제 — **데이터 저장소 로그가 태초부터의 모든 변경을 담고 있을 가능성은 낮다.** 그것은 주로 저장소
  일관성을 보장하는 기제이고, 저장소는 로그 데이터를 하부 모델로 계속 병합해 내리며 **짧은 구간(예:
  수 기가바이트)만 유지**한다 (6장 §"Snapshotting the Initial Data Set State",
  p.132).[^bellemare2025]
- **스냅샷(snapshotting)** 은 **현재** 데이터 전부를 **로그가 아니라 데이터 저장소에서 직접** 스트림으로
  싣는 과정이다. 원천 데이터셋의 모든 엔티티를 질의·반환·복사·이벤트 변환·쓰기해야 하므로 **매우 자원
  집약적**일 수 있다 (6장, p.132).[^bellemare2025]
- 이 질의를 흔히 **부트스트래핑(bootstrapping)** 이라 부르고, 조항이 하나 붙는다 — **부트스트랩 질의
  결과의 레코드와 로그의 레코드 사이에 겹침이 있어야** 라이브 CDC로 넘어갈 때 레코드를 놓치지 않는다
  (6장, p.133).[^bellemare2025]
- **진짜 문제는 크기가 아니라 잠금이다** — 스냅샷은 일관성을 위해 **변하지 않는 데이터 집합**을 요구하고
  그러려면 대개 **질의 대상 테이블을 잠근다.** 중요한 프로덕션 테이블이 스냅샷이 끝날 때까지 **몇 시간
  잠길 수 있다**는 뜻이다 (6장, p.133).[^bellemare2025]
- 선택지 둘이 제시된다 (6장, p.133):[^bellemare2025]
  - **읽기 전용 복제본에서 스냅샷을 뜬다** — 프로덕션 저장소를 건드리지 않는다. 끝나면 테이블 잠금을
    풀고 프로덕션에서 온 복제 갱신으로 채워지게 두었다가 CDC나 주기 질의로 넘어간다.
  - **잠그지 않는 증분 스냅샷** — Debezium 같은 일부 프레임워크가 특정 저장소를 **테이블을 잠그지 않고**
    스냅샷하는 기제를 제공한다. 정상 읽기·쓰기가 방해 없이 계속되고 결과 스냅샷은 현재 테이블 상태와
    **결과적으로 일관**된다.
    - 버전 조건: 2025년 저술 시점의 Debezium 기능에 대한 서술이다.
- 저자가 근거로 인용하는 넷플릭스 논문의 서술 (6장, p.133):[^bellemare2025]

  > DBLog utilizes a watermark based approach that allows us to interleave transaction log events
  > with rows that we directly select from tables to capture the full state. Our solution allows
  > log events to continue progress without stalling while processing selects. Selects can be
  > triggered at any time on all tables, a specific table, or for specific primary keys of a table.
  > DBLog executes selects in chunks and tracks progress, allowing them to pause and resume. The
  > watermark approach does not use locks and has minimum impact on the source.
  >
  > —Andreas Andreakis and Ioannis Papapanagiotou, Netflix

- 병합 규칙이 명시된다 — CDC 체계가 **증분 스냅샷 질의 결과를 로그 레코드와 병합**한다. 스냅샷 질의
  데이터는 스트림에 바로 쓰이되, **그 키에 대해 이미 로그에서 온 *더 새로운* 레코드가 쓰였다면 더 오래된
  쪽을 버린다** — 최신 데이터의 유효한 표현이 아니기 때문이다. 끝나면 CDC는 무기한 로그 테일링을
  계속한다 (6장, pp.133–134).[^bellemare2025]
- 저자의 채점 — **성능을 떨어뜨리거나 프로덕션 사용례를 막지 않는 라이브 테이블 스냅샷은 초기 CDC
  기술에 비하면 막대한 진전**이고, 데이터를 저장소에서 억지로 빼내는 씨름 대신 **데이터를 *쓰는* 일에
  집중하게** 해 준다 (6장, p.133).[^bellemare2025]

## 폴링 질의로 하는 해방

- 질의 기반 해방은 **저장소에 질의해 결과를 받아 이벤트로 바꿔 스트림에 쓴다.** 직접 코드를 쓸 수도
  있으나 **오늘날 커넥터가 풍부하므로 자기 것을 다시 만들기보다 목적에 맞게 지어진 프레임워크로
  시작하기를 저자가 권한다** (6장 §"Liberating Data with a Polling Query", p.135).[^bellemare2025]
- 이 패턴은 **하부 로그를 쓰지 않는다** — 스냅샷과 증분 반복이 **전부 저장소 질의 API를 통해** 소비된다.
  단계가 둘이다: **초기 스냅샷**과 **증분 단계(incremental phase)**. 스냅샷 과정은 위
  [초기 상태 스냅샷](#초기-상태-스냅샷)과 동일하되, **끝난 뒤 넘어갈 저장소 로그가 없다는 것**이 다르다
  (6장, p.135).[^bellemare2025]
- 증분이 딛는 것이 **하이워터 마크(high-water mark)** 다 — 마지막 폴링 이후 어느 레코드가 바뀌었는지
  가려야 하고, 테이블 컬럼에 흔히 들어 있는 `updated_at`이나 `modified_at` 타임스탬프가 **질의가 지난번
  어디서 끝났는지의 훌륭한 하이워터 마크**가 된다. n+1 번째 질의가 n 번째의 하이워터 마크를 써서 그
  사이의 레코드를 고른다 (6장, p.135).[^bellemare2025]
- Kafka Connect JDBC 커넥터가 증분 스냅샷 기능을 기성으로 제공하고, 저자가 그 문서에서 세 모드를 그대로
  옮긴다 (6장, p.135):[^bellemare2025]

  > *Incrementing* Use a strictly incrementing column (as specified by incrementing.column.name) on
  > each table to detect only new rows. Note that this will not detect modifications or deletions of
  > existing rows.

  > *Timestamp* Use a timestamp (as specified by timestamp.column.name) column to detect new and
  > modified rows. This assumes the column is updated with each write, and that values are
  > monotonically incrementing, but not necessarily unique.

  > *Timestamp+incrementing* Use two columns, a timestamp column that detects new and modified rows
  > and a strictly incrementing column that provides a globally unique ID for updates so each row
  > can be assigned a unique stream offset.

  - 버전 조건: 2025년 저술 시점의 Kafka Connect JDBC 커넥터 문서를 인용한 것이다.
- 반환된 행은 자동으로 이벤트로 바뀌며 **질의 결과에서 이벤트 스키마를 추론한다 — 적어도 기성
  프레임워크는 그렇다.** 직접 만든다면 스키마 생성도 자기 몫이다. **어느 쪽이든 상류 저장소 모델이
  바뀌면 이벤트 스키마도 바뀔 위험을 진다** (6장, p.136).[^bellemare2025]
- **저자의 시대 판정이 붙는다** — 질의 기반 폴링은, 특히 직접 만들 때, **일관된 상태를 얻으려고 테이블
  잠금에 크게 기댄다.** 부트스트래핑 방식으로는 **전반적으로 낡은 과정**이고 기술적으로는 여전히
  유효하되 **증분 질의보다 CDC를 쓰는 쪽이 훨씬 흔하다.** 이 책 **초판 이후 CDC가 상당히 개선되어
  질의 기반 폴링은 대체로 하부 로그 접근을 제공하지 않는 저장소와 API로 밀려났다** (6장,
  p.136).[^bellemare2025]
- **증분 갱신의 세 단계** (6장 §"Incremental Updating", p.136):[^bellemare2025]
  - **첫째, 필요한 타임스탬프나 자동 증가 ID가 레코드에 있는지 확보한다.** 이미 처리한 레코드를 거를
    필드가 없으면 데이터셋에 그 필드를 추가하고 저장소가 그것을 채우도록 설정해야 한다. **필드를
    추가할 수 없으면 질의 기반 패턴으로는 증분 갱신이 불가능하다.**
  - **둘째, 폴링 주기와 갱신 지연을 정한다.** 고빈도 갱신은 하류 지연을 낮추지만 **저장소의 총 부하를
    키우고**, 요청 간격이 데이터를 다 싣기에 충분한지도 따져야 한다 — **이전 질의가 끝나기 전에 새
    질의를 시작하면 오래된 데이터가 새 데이터를 덮어쓰는 경쟁 조건**이 생긴다.
  - **셋째, 증분을 켜기 전에 단일 벌크 적재를 한 번 수행한다.** 이 적재가 기존 데이터 전부를 질의해
    생산해야 한다.
- **이득 셋** (6장 §"Benefits of Query-Based Updating", pp.136–137):[^bellemare2025]
  - **커스터마이즈 가능성** — **어떤 데이터 저장소든 질의할 수 있고** 질의 클라이언트 옵션 전체를 쓸 수
    있다.
  - **독립적인 폴링 주기** — 특정 질의는 더 자주 실행해 빡빡한 SLA를 맞추고, 더 비싼 질의는 덜 자주
    실행해 자원을 아낄 수 있다.
  - **내부 데이터 모델의 격리** — 관계형 데이터베이스는 **뷰나 구체화 뷰**를 써서 내부 모델로부터
    격리를 제공할 수 있고, 저장소 밖으로 나가면 안 되는 도메인 모델 정보를 감출 수 있다.
    - 저자가 곧바로 단서를 단다 (6장, p.137):[^bellemare2025]

      > Remember that the liberated data will be the single source of truth. Consider whether any
      > concealed or omitted data should instead be liberated, or if the source data model needs to
      > be refactored. This often occurs during data liberation from legacy systems, where business
      > data and entity data have become intertwined over time.

- **단점 일곱** (6장 §"Drawbacks of Query-Based Updating", pp.137–138):[^bellemare2025]

  | 단점 | 저자의 서술 |
  |---|---|
  | **`updated-at` 타임스탬프가 필수** | 질의 대상 테이블이나 네임스페이스에 갱신 시각 컬럼이 있어야 한다. 마지막 갱신 시각 추적과 증분 갱신의 필수 조건이다 |
  | **소프트 삭제만 감지한다** | 저장소에서 레코드를 완전히 지우면 질의에 아무 이벤트도 나타나지 않는다. 따라서 `is_deleted` 컬럼으로 삭제를 표시하는 **소프트 삭제**를 써야 한다 |
  | **데이터셋 스키마와 출력 이벤트 스키마의 깨지기 쉬운 의존** | 하류 이벤트 형식 스키마 규칙과 맞지 않는 데이터셋 스키마 변경이 일어날 수 있고, **해방 기제가 저장소 애플리케이션의 코드베이스와 분리되어 있을수록 파손 가능성이 커진다** — 질의 기반 체계는 대개 그렇다 |
  | **간헐적 데이터 값을 놓칠 수 있다** | 폴링 간격에만 동기화되므로 같은 레코드에 대한 연속된 변경이 **단 하나의 이벤트로만** 나타날 수 있다 |
  | **프로덕션 자원 소모** | 질의가 하부 체계 자원을 쓰므로 프로덕션에 용납 못 할 지연을 부를 수 있다. 읽기 전용 복제본으로 완화되지만 **추가 금전 비용과 체계 복잡성**이 따른다 |
  | **데이터 크기에 따라 질의 성능이 변한다** | 질의·반환되는 데이터 양이 변경에 따라 달라지고 **최악의 경우 매번 데이터 전체가 바뀐다.** 앞 질의가 끝나기 전에 다음이 시작되면 경쟁 조건이 된다 |
  | **트랜잭션 데이터 불일치** | 기본 키·외래 키로 서로를 참조하는 두 테이블에 쓰는 트랜잭션을 주기 질의로 따라가면, **한 스트림의 레코드가 아직 포착되지 않은 다른 스트림의 값을 참조**할 수 있고 소비자가 데이터를 맞출 때 간헐적 오류가 난다 |

## 트랜잭셔널 아웃박스 테이블로 하는 해방

**패턴 자체의 규정과 알고리즘은 이 KB의 [아웃박스 패턴](../concepts/outbox-pattern.md)이 갖는다.**
이 절이 더하는 것은 **해방 수단으로 썼을 때의 두 자리** — 내부 모델의 격리와 스키마 강제다.

- 이 소스의 규정 (6장 §"Liberating Data Using Transactional Outbox Tables",
  p.138):[^bellemare2025]

  > A transactional outbox table is a dedicated database table that acts as a buffer for data to be
  > written to the event stream.

  - **내부 도메인 모델(internal domain model)** 을 갱신할 때 **바깥세상에 노출하고 싶은 데이터만 골라**
    아웃박스에 쓰고, 전용 CDC 커넥터 같은 **별도 비동기 프로세스**가 그것을 소비해 스트림에 쓴다 (6장,
    p.138).[^bellemare2025]
- 기제의 요지 — 이 패턴은 **저장소의 트랜잭션 능력과 내구성을 활용해 저장소를 선행 기록 로그(write-ahead
  log) 노릇을 하게 만든다.** 내부 테이블 갱신과 아웃박스 갱신이 **단일 트랜잭션**으로 묶여 **전체
  트랜잭션이 성공할 때만** 반영된다. 실패하면 결국 단일 진실 원천인 스트림과 갈라지고 **그 갈라짐은
  발견과 수리가 어렵다** (6장, p.138).[^bellemare2025]
- 커넥터가 출력 스트림에 커밋한 뒤 아웃박스에서 레코드를 지운다. **저장소든 소비자·생산자든 브로커
  자체든 실패가 나도 아웃박스 레코드는 유실 위험 없이 남는다. 이 패턴이 주는 것은 최소 한 번 전달**이다
  (6장, p.139).[^bellemare2025]
- 아웃박스 테이블의 모양이 표로 주어진다 (6장, p.140, 표 6-1 `EcomItem_Outbox` table
  definition):[^bellemare2025]

  | id: INT NOT NULL | name: VARCHAR(255) | price: DECIMAL(13,2) NOT NULL | Datetime: DEFAULT CURRENT_TIMESTAMP | ordering_id INT NOT NULL AUTO_INCREMENT |
  |---|---|---|---|---|
  | 4291 | "Fancy Laptop" | 1299.99 | 2022-06-22 11:33:12 | 1 |

  - 저자가 짚는 것이 둘이다 — **필수 필드마다 `NOT NULL`을 쓰므로 제약을 다 채우지 못하면 아웃박스
    삽입이 실패한다**는 것, 그리고 **`Datetime` 필드가 애플리케이션 코드에서 주어지지 않으면 기본값
    `CURRENT_TIMESTAMP`를 쓴다**는 것이다. 이 타임스탬프는 이벤트 스키마의 일부로 쓰거나 **이벤트가
    언제 만들어졌는지를 가리키는 메타데이터**로 쓸 수 있다 (6장, p.140).[^bellemare2025]
  - 정렬 식별자에 조항이 하나 붙는다 — **아웃박스 테이블의 레코드는 중간 상태가 일어난 순서 그대로
    기록·발행되도록 엄격한 정렬 식별자를 요구한다.** 대안은 **기본 키로 upsert 해 이전 항목을 덮어쓰고
    중간 상태를 포기하는 것**이고, 그 경우 덮어쓰인 레코드는 스트림에 나가지 않는다 (6장,
    p.141).[^bellemare2025]
  - 조항 하나 더 — **아웃박스 테이블 스키마와 이벤트 스키마가 호환되도록 하고 한쪽 필드가 다른 쪽과
    1:1로 대응하게 하라. 배포 전 스크립트로 둘이 맞는지 검증해 쉽게 막을 수 있는 런타임 오류를
    피하라** (6장, p.140).[^bellemare2025]
- **침습성의 대가** — 아웃박스는 **변경 데이터 포착 방식 가운데 상대적으로 침습적**이다. **데이터
  저장소나 애플리케이션 계층 중 하나를 고쳐야 하므로 저장소나 애플리케이션 소유자의 참여가 필요하다**
  (6장, p.140).[^bellemare2025]
- **성능 고려** — 아웃박스 테이블은 저장소와 요청 처리 애플리케이션에 **부하를 더한다.** 부하가 적은 작은
  저장소에서는 전혀 눈에 띄지 않을 수도, **부하가 크고 포착 대상 테이블이 많은 아주 큰 저장소에서는 꽤
  비쌀 수도** 있다. 비용은 사례별로 평가해 **체인지로그 파싱 같은 반응적 전략의 비용과 견주어야** 한다
  (6장 §"Performance Considerations", p.141).[^bellemare2025]

### 내부 데이터 모델의 격리

- **아웃박스는 내부 도메인과 1:1로 대응할 필요가 없다.** 오히려 **아웃박스의 주요 이점 하나가 저장소
  클라이언트가 내부 데이터 모델을 하류 소비자로부터 격리할 수 있다는 것**이다 (6장 §"Isolating Internal
  Data Models", p.141).[^bellemare2025]
- 왜 필요한가 — 내부 모델은 **관계 연산에 최적화된 고도로 정규화된 여러 테이블**일 수 있고 그것은 하류
  소비에 대체로 부적합하다. **단순한 도메인조차 여러 테이블로 이뤄지고, 그것을 독립 스트림으로 노출하면
  하류가 도메인 모델을 재구성해야 한다.** 여러 하류 팀이 각자 재구성하고 관계형 데이터를 스트림에서
  다루게 되므로 **운영 부대 비용이 순식간에 극도로 비싸진다** (6장, p.141).[^bellemare2025]
- 저자가 상자로 못 박는다 (6장, p.141):[^bellemare2025]

  > Exposing the internal data model to downstream consumers is an antipattern. Downstream consumers
  > should only access data formatted with public-facing data contracts, as described in Chapter 4.

  - 그 데이터 계약의 전문은 [이벤트 스키마와 데이터 계약](event-schemas-and-data-contracts.md)에 있다.
- 선택지 둘 — 저장소 클라이언트가 **삽입 시점에 비정규화해 아웃박스가 의도한 공개 데이터 계약을 그대로
  비추게** 하거나(성능과 저장 공간을 더 쓴다), **변경과 출력 스트림의 1:1 대응을 유지하고 그 일만 하는
  전용 하류 이벤트 처리기로 스트림을 비정규화**하거나다. 둘의 비교를 7장으로 넘긴다 (6장,
  p.141).[^bellemare2025] 그 비교의 전문은
  [비정규화와 이벤트화](denormalization-and-eventification.md)에 있다.
- **조직 쪽 판정이 이 절에서 가장 강한 문장이다** — 내부 모델을 외부 소비자로부터 어디까지 격리할
  것인가는 **이벤트 기반 마이크로서비스로 옮겨 가는 조직에서 다툼의 지점이 되는 편**이고, 일부 팀은
  **자원 부족을 이유로** 격리를 유지하지 못하거나 하지 않으려 한다. 그러나 (6장,
  pp.141–142):[^bellemare2025]
  - **그것은 생산자 쪽 상류에서 치르든 데이터의 소비자마다 하류에서 치르든 어차피 치르는 비용**이다.
  - **내부 데이터 모델의 격리는 서비스의 결합 해제와 독립을 보장하고 체계가 오직 새 업무 요구 때문에만
    바뀌게 하는 데 필수**다.

### 스키마 호환의 강제 — 쓰기 전 직렬화와 쓴 뒤 직렬화

- **스키마 직렬화(따라서 검증)를 아웃박스 흐름에 넣을 수 있고**, 검증은 **이벤트를 아웃박스 테이블에
  쓰기 전이나 후** 어느 쪽에서도 할 수 있다. 성공하면 흐름을 진행하고 **실패하면 근본 원인을 가리고
  데이터 손실을 피하기 위해 수동 개입이 필요할 수 있다** (6장 §"Ensuring Schema Compatibility",
  p.142).[^bellemare2025]
- **쓰기 전 직렬화** — **아웃박스 테이블에 트랜잭션을 커밋하기 전에 직렬화하는 것이 데이터 일관성의
  가장 강한 보장**을 준다. 직렬화 실패가 트랜잭션을 실패시켜 내부 테이블의 변경을 롤백하므로 **아웃박스와
  내부 테이블이 동기 상태로 남는다.** 주된 이점은 **내부 상태와 출력 스트림 사이의 불일치가 유의하게
  줄어든다**는 것이고, **이벤트 스트림 데이터가 일급 시민으로 다뤄져 올바른 데이터의 발행이 내부 상태의
  일관성 유지만큼 중요하게 여겨진다** (6장, p.142).[^bellemare2025]
  - 딸려 오는 선택지 하나 — 쓰기 전에 직렬화하면 **모든 트랜잭션에 아웃박스 하나만 쓰는 선택**이 가능해진다.
    내용이 대부분 직렬화된 데이터와 목표 출력 스트림 매핑이라 형식이 단순하기 때문이다 (6장,
    p.142).[^bellemare2025]
  - 대가 — **직렬화 부대 비용 때문에 성능이 나빠질 수 있다.** 가벼운 부하에서는 무시할 만해도 무거운
    부하에서는 함의가 클 수 있고, 서비스가 여전히 성능 요구를 지킬 수 있는지 확인해야 한다 (6장,
    p.143).[^bellemare2025]
- **쓴 뒤 직렬화** — 하류 발행자가 아웃박스에 쓰인 뒤 직렬화한다. 이때는 대개 **도메인 모델마다 독립
  아웃박스**를 두고 각각을 대응하는 출력 스트림의 공개 스키마에 매핑한다. 발행자 프로세스가 직렬화되지
  않은 이벤트를 읽어 연결된 스키마로 직렬화하려 시도한다 (6장, p.143).[^bellemare2025]
  - 실패의 성격이 다르다 — 직렬화 실패는 **이벤트 데이터가 정의된 스키마를 따르지 않아 발행할 수 없다는
    뜻**이고, **이미 완료된 트랜잭션이 호환되지 않는 데이터를 아웃박스에 밀어 넣었으며 그 트랜잭션을
    되돌릴 수 있다는 보장이 없다** (6장, p.144).[^bellemare2025]
  - 현실의 결과 — **직렬화 불가능한 이벤트가 아웃박스에 다량 쌓이는 것으로 끝나는 것이 보통**이다. 일부를
    건지려면 수동 개입이 필요하고 해결은 시간이 오래 걸리며 어렵고 **추가 문제를 막으려 다운타임이 필요할
    수도** 있다. 게다가 **일부 이벤트는 호환되어 이미 발행되었을 수 있어 출력 스트림의 순서가 틀어질 수
    있다** (6장, p.144).[^bellemare2025]
- 저자의 채점과 그 대가 (6장, p.144):[^bellemare2025]
  - **사전 직렬화가 사후보다 호환되지 않는 데이터에 대해 더 강한 보장을 주고 데이터 계약을 위반하는
    이벤트의 전파를 막는다.**
  - **맞교환은 직렬화가 실패하면 트랜잭션이 롤백되므로 업무 프로세스 자체가 완료되지 못한다는 것**이다.
  - 그리고 판정 (6장, p.144):[^bellemare2025]

    > Validating and serializing before writing ensures that the data is being treated as a
    > first-class citizen and offers a guarantee that events in the output event stream are
    > eventually consistent with the data inside the source data store, while also preserving the
    > isolation of the source's internal data model. This is the strongest guarantee that a
    > change-data capture solution can offer.

### 아웃박스의 이득 다섯과 단점 넷

- **이득 다섯** (6장 §"Benefits of event production with outbox tables",
  p.145):[^bellemare2025]
  - **다중 언어 지원** — 트랜잭션 능력을 노출하는 어떤 클라이언트나 프레임워크로도 된다.
  - **정확히 한 번의 아웃박스 의미론(Exactly-once outbox semantics)** — 트랜잭션이 내부 모델과 아웃박스
    데이터를 **원자적으로** 만들게 보장한다. 갱신을 트랜잭션으로 감싸는 한 데이터베이스의 어떤 변경도
    놓치지 않는다.
  - **이른 스키마 강제** — 아웃박스 테이블이 스트림 스키마에 대응하는 잘 정의된 스키마를 제공하고,
    런타임에 이벤트로 직렬화하는 것이 추가 검증이 된다 — 호환되지 않는 데이터는 예외로 드러난다.
  - **내부 데이터 모델 격리** — 저장소 애플리케이션 개발자가 아웃박스에 쓸 필드를 고를 수 있어 내부
    필드를 격리한 채로 둔다.
  - **비정규화** — 서비스가 아웃박스에 쓰기 전에 데이터를 비정규화할 수 있다.
- **단점 넷** (6장 §"Drawbacks of event production with outbox tables",
  p.145):[^bellemare2025]
  - **데이터베이스가 트랜잭션을 지원해야 한다** — 아니면 다른 접근 패턴을 골라야 한다.
  - **애플리케이션 코드 변경** — 이 패턴을 켜려면 코드를 고쳐야 하고 애플리케이션 유지자의 개발·테스트
    자원이 필요하다.
  - **업무 프로세스 성능 영향** — 특히 직렬화로 스키마를 검증할 때 업무 흐름에 대한 성능 영향이 사소하지
    않을 수 있고, **실패한 트랜잭션이 업무 연산의 진행을 막을 수도** 있다.
  - **데이터 저장소 성능 영향** — 특히 아웃박스에 상당량의 레코드가 쓰이고 읽히고 지워질 때 그렇다.
- **비용의 방향을 저자가 다시 못 박는다** — 어떤 조직은 그냥 체인지로그를 파싱해 이벤트를 내고 **사후
  정리를 하류 팀에 맡긴다.** 그것도 나름의 비용을 부른다 — **이벤트 처리·표준화의 컴퓨팅 비용과, 호환되지
  않는 스키마를 해결하고 내부 모델에 대한 강한 결합의 여파를 감당하는 사람의 노동 비용**이다. 그리고
  판정 (6장, p.146):[^bellemare2025]

  > Costs saved at the producer side are often dwarfed by the expenses incurred at the consumer side.

## 트리거로 하는 변경 데이터 포착

- **트리거 지원은 앞 절들이 살핀 감사·binlog·선행 기록 로그 패턴보다 앞선다.** 많은 오래된 관계형
  데이터베이스가 감사 테이블을 만드는 수단으로 트리거를 쓴다. **이름 그대로 특정 조건에 자동으로 일어나고,
  실패하면 트리거를 실행시킨 명령도 함께 실패해 갱신 원자성이 보장된다** (6장 §"Capturing Change-Data
  Using Triggers", p.146).[^bellemare2025]
- **`AFTER` 트리거로 행 수준 변경을 감사 테이블에 포착한다** — `INSERT`·`UPDATE`·`DELETE` 뒤에 트리거가
  변경 데이터 테이블에 대응하는 행을 쓴다 (6장, p.146).[^bellemare2025] 저자의 예에서 트리거는 **삽입
  시각과 이벤트 발행 프로세스가 쓸 자동 증가 시퀀스 ID**도 함께 포착한다 (6장, p.146).[^bellemare2025]
- **약점은 검증이다** — **트리거 실행 중에 변경 데이터를 이벤트 스키마로 검증하는 것은 일반적으로 안
  된다**(불가능하지는 않다). 이유가 셋이다 (6장, p.147):[^bellemare2025]
  - **지원 자체가 없을 수 있다** — 트리거는 데이터베이스 안에서 실행되고 많은 데이터베이스가 쓸 수 있는
    언어 형태가 제한된다. **PostgreSQL은 C·Python·Perl을 지원해 사용자 정의 함수로 스키마 검증을 쓸 수
    있으나 다수는 다중 언어를 제공하지 않는다.**
  - **지원돼도 너무 비쌀 수 있다** — 각 트리거가 독립으로 발화하고 필요한 데이터·스키마·검증 로직을
    저장하는 데 사소하지 않은 부대 비용이 들어 **많은 부하에서는 비용이 너무 높다.**
  - 그래서 검증은 **사후(after-the-fact)** 로 밀린다 — 검증에 성공한 데이터만 출력 스트림으로 생산되고,
    실패한 데이터는 업무 요구에 따른 오류 처리가 필요한데 **사람의 개입을 요구할 가능성이 높다** (6장,
    p.147).[^bellemare2025]
- 스키마 셋이 한 줄로 엮인다 — **변경 데이터 포착 테이블 스키마가 내부 테이블 스키마와 출력 스트림 스키마
  사이의 다리이고, 셋 사이의 호환이 데이터를 출력 스트림에 낼 수 있게 하는 필수 조건**이다. 트리거 실행
  중에 출력 스키마 검증이 대개 수행되지 않으므로 **변경 데이터 테이블을 출력 이벤트 스키마의 형식과
  맞춰 두는 것이 최선**이고, **테스트 때 둘의 형식을 비교하면 프로덕션 배포 전에 비호환을 드러낼 수
  있다** (6장, pp.147–148).[^bellemare2025]
- **레거시에는 잘 맞는다** — 레거시 체계는 정의상 오래된 기술을 쓰고 **트리거는 아주 오래 존재해 왔으므로**
  필요한 포착 기제가 될 수 있다. 접근·부하 패턴이 잘 정의되고 안정적인 편이라 **트리거 추가의 영향을
  정확히 추정할 수 있고**, 스키마 검증이 트리거 과정에서 일어나지 않더라도 **레거시라는 성격 때문에
  스키마 자체가 바뀔 일도 마찬가지로 드물** 수 있다. **사후 검증은 스키마가 자주 바뀔 것으로 기대될 때만
  문제**다 (6장, p.148).[^bellemare2025]
- **그럼에도 저자의 권고는 회피다** (6장, p.148):[^bellemare2025]

  > Avoid the use of triggers whenever possible. Instead, use more modern functionality for
  > generating or accessing change-data, such as a designated CDC system. You should not
  > underestimate the overhead performance and management complexity of a trigger-based solution,
  > particularly when many dozens or hundreds of tables and data models are involved.

- **이득 셋** (6장 §"Benefits of using triggers", p.148):[^bellemare2025] **대부분의 데이터베이스가
  지원**한다 · **작은 데이터셋에는 부대 비용이 낮다**(갱신이 드문 작은 데이터셋이면 유지·설정이 상당히
  쉽다) · **로직을 커스터마이즈할 수 있다**(특정 필드의 부분집합만 노출하도록 트리거 코드를 고칠 수 있어
  하류에 무엇을 내줄지에 어느 정도 격리를 준다).
- **단점 넷** (6장 §"Drawbacks of using triggers", pp.148–149):[^bellemare2025]

  | 단점 | 저자의 서술 |
  |---|---|
  | **성능 부대 비용** | 트리거는 테이블 연산과 **인라인으로 실행**되어 사소하지 않은 처리 자원을 쓴다. 성능 요구와 SLA에 따라 용납 못 할 부하가 될 수 있다 |
  | **변경 관리 복잡성** | 애플리케이션 코드와 데이터셋 정의의 변경이 **대응하는 트리거 수정을 요구**할 수 있고, 유지자가 그것을 놓치면 **해방 결과가 내부 데이터셋과 어긋난다** |
  | **나쁜 확장성** | 필요한 트리거 수가 **포착 대상 데이터셋 수에 선형으로** 는다. 테이블 사이 의존을 강제하는 것 같은 기존 업무 로직 트리거는 여기 포함되지도 않았다 |
  | **사후 스키마 강제** | 출력 이벤트의 스키마 강제가 레코드가 아웃박스 테이블에 발행된 **뒤에만** 일어나고, 그 결과 **발행 불가능한 이벤트가 아웃박스에 남을 수 있다** |

  - 완화책이 하나 적힌다 — 일부 데이터베이스는 **출력 이벤트 스키마와의 호환을 트리거 실행 중에 검증할 수
    있는 언어로 트리거를 실행하게** 해 준다(예: PostgreSQL의 Python). **복잡성과 처리 비용이 늘지만 하류
    스키마 비호환의 위험은 유의하게 줄어든다** (6장, p.149).[^bellemare2025]

## 포착 중인 데이터셋의 정의를 바꿀 때

- **데이터 정의(data definition)** 의 규정 (6장 §"Making Data Definition Changes to Data Sets Under
  Capture", p.149):[^bellemare2025]

  > *Data definition* is the formal description of the data set. For example, a table in a relational
  > database is defined using a *data definition language* (DDL). The resultant table, columns, names,
  > types, and indices are all part of its data definition.

- 문제 — **데이터 마이그레이션은 많은 관계형 애플리케이션에서 흔한 연산**이고 포착도 그것을 받쳐야 한다.
  관계형 데이터베이스의 정의 변경에는 **컬럼 추가·삭제·이름 변경, 컬럼 타입 변경, 기본값 추가·제거**가
  들고, **전부 유효한 데이터셋 변경이지만 해방된 스트림으로의 생산에 문제를 만들 수 있다** (6장,
  p.149).[^bellemare2025]
- **가장 중요한 요소는 기술이 아니라 절차**다 — **원천 데이터셋의 변경 관리 프로세스에 깊이 통합되는
  것**이 정의 변경을 넘기는 데 가장 중요하다. 스트림에 들어가는 데이터가 확립된 스키마와 호환되게
  유지할 책임이 자기에게 있다면 **들어올 변경을 놓치지 않기 위해 할 수 있는 모든 것을 해야 한다** (6장,
  pp.149–150).[^bellemare2025]
- **행동 셋** (6장, p.150):[^bellemare2025]
  - **데이터 저장소 풀 리퀘스트를 관찰한다** — 포착 중인 저장소를 건드리는 코드의 변경 요청 알림을
    등록해, 제안된 변경을 보고 그것이 자기 코드에 영향을 주는지 가린다.
  - **통합 테스트를 만든다** — 이벤트 스트림 스키마를 내려받아 포착 중인 저장소의 스키마와 비교하는
    통합 테스트를 코드베이스에 더한다. **변경을 만드는 개발자에게 개발 시점에 알려 주어 양쪽이 공통 해법을
    찾을 시간을 더 준다.**
  - **배포 검증을 세운다** — 그 통합 테스트를 배포 파이프라인에 넣어 **스키마 검증 단계를 성공(또는
    명시적 무시)하지 않고는 어떤 코드도 배포되지 않게** 한다.
- 저자가 이 자리의 성격을 인정한다 — **한 독립 체계(데이터 저장소)의 스키마를 다른 독립 체계(이벤트
  브로커)로 잇는 일이므로 이 단계는 언제나 다소 아슬아슬하고, 팀 경계가 바로 이 체계 간극에 맞춰지는
  경향이 있어서 특히 그렇다** (6장, p.150).[^bellemare2025]
- **아웃박스의 큰 이점 하나가 여기서 나온다** — **아웃박스를 채우는 코드가 주 애플리케이션과 같은
  코드베이스 안에 있으므로**, 그 코드에 대한 깨는 변경은 **컴파일·테스트 오류로 드러나** 프로덕션에서
  무엇이 깨지기 전에 조치할 수 있다 (6장, p.150).[^bellemare2025]

## 해방의 타협 — 읽고 자기 쓰기와 단방향

- 요구는 분명하다 — **해방된 스트림은 결국, 그리고 정확하게, 원천 데이터셋을 반영해야 한다.** 이벤트 기반
  아키텍처가 이벤트가 실어 나르는 상태 전이(event-carried state transfer)를 위해 그 스트림에 기대고, 그
  데이터를 **원래 테이블의 사본으로 되구체화**할 수 있어야 하기 때문이다 (6장 §"Compromises for Data
  Liberation", p.150).[^bellemare2025]
- **그런데 레거시는 그 스트림에서 자기 데이터셋을 다시 만들지 않는다** — 레거시는 **스냅샷·체크포인트·
  자기 선행 기록 로그 같은 자기 백업·복구 기제**를 갖고 있고, **복구 기제가 무엇이든 복원된 상태가
  스트림을 구체화해 만든 복원과 어긋날 위험이 남는다** (6장, p.150).[^bellemare2025]
- **이상적인 해법이 먼저 제시된다 — 먼저 스트림에 쓰고 되읽는다.** 애플리케이션을 고쳐 **먼저 이벤트
  스트림에 쓰고, 방금 쓴 데이터를 되읽어 자기 내부 상태를 만들게** 하는 것이다 (6장,
  p.151).[^bellemare2025]
  - **이득 둘** (6장, p.151):[^bellemare2025]
    - **단일 진실 원천** — **생산자 서비스가 스트림을 구독하는 다른 모든 서비스와 똑같은 데이터의 완전한
      사본을 갖는다. 구체화 결과들이 서로 완전히 수렴한다.**
    - **스트림에서의 실패 복구** — 생산자 실패는 **스트림을 되읽어 어디까지 했는지의 일관된 시야를 얻는
      것으로** 해결된다. 데이터가 없으면 스트림을 되감아 재생할 수 있다.
  - **단점 셋** (6장, p.151):[^bellemare2025]
    - **지연 증가** — 스트림에 썼다가 되읽는 네트워크 왕복이 지연을 늘려 **아주 낮은 지연을 요구하는
      서비스에는 맞지 않을 수 있다.**
    - **모든 저장소 사용례에 맞지는 않는다** — **앞 단계의 ID와 값을 요구하는 복잡한 다단계 트랜잭션은
      대체로 부적합**하다. 스트림에 먼저 쓴다는 것은 저장소 연산이 대체로 **기본적인 upsert로 제한**된다는
      뜻이다.
    - **리팩터링을 요구한다** — 레거시가 이 패턴을 쓰려면 리팩터링이 필요하고 **아주 단순한 사용례
      바깥에서는 감당하기에 너무 비쌀 수 있다.**
- **그래서 타협이 온다** — 생산자와 소비자 양쪽의 상태를 하나의 스트림으로 만들고 복원하는 것이 이상이지만
  **실무에서는 다른 선택지를 찾아야 하는 일이 잦다.** 레거시가 그런 대규모 변경을 감당하지 못하고 개발
  사이클도 없기 때문이다 (6장, p.152).[^bellemare2025]
  - 타협의 모양 — 해방 패턴으로 데이터를 꺼내 스트림을 만들되 **레거시는 해방된 스트림에서 되읽지 *않는다*.**
    저자가 이것을 **단방향 이벤트 기반 아키텍처(unidirectional event-driven architecture)** 라 부른다 (6장,
    p.152).[^bellemare2025]
  - 그때 목표가 바뀐다 — **근본 목표는 엄격히 통제된 이벤트 데이터 발행을 통해 내부 데이터셋을 외부
    스트림과 동기 상태로 유지하는 것**이고, **스트림은 레거시 애플리케이션의 내부 데이터셋과 결과적으로
    일관**하게 된다 (6장, p.152).[^bellemare2025]

## 싱킹 — 스트림을 저장소로 되돌린다

- **싱킹(sinking)** 은 **이벤트 데이터를 소비해 데이터 저장소에 삽입하는 것**이고, 중앙 프레임워크나
  독립 마이크로서비스가 맡는다. **엔티티든 키 있는 이벤트든 키 없는 이벤트든 어떤 종류의 이벤트 데이터도
  저장소로 싱크할 수 있다** (6장 §"Sinking Event Data to Data Stores", p.152).[^bellemare2025]
- 쓸모의 중심은 통합이다 — **싱킹은 이벤트 기반이 아닌 애플리케이션을 스트림과 통합하는 데 특히
  쓸모 있다.** 싱크 프로세스는 스트림을 읽어 지정된 저장소에 넣고 **자기 소비 오프셋을 스스로 추적하며,
  대상 애플리케이션과 완전히 독립으로 동작한다** (6장, p.152).[^bellemare2025]
- 전형적 용도가 **레거시 사이의 직접 점대점 결합을 대체하는 것**이다. 원천 체계의 데이터가 스트림으로
  해방되고 나면 **다른 변경을 거의 하지 않고도** 목적지 체계로 싱크할 수 있고, **싱크 프로세스는 목적지
  체계의 바깥에서 그것에 보이지 않게 동작한다** (6장, p.152).[^bellemare2025]
- 분석 쪽 고객도 여기 있다 — **배치 기반 빅데이터 분석을 해야 하는 팀도 스트림 데이터의 고객**이고,
  보통 **분산 파일 시스템으로 싱크해** 대규모 병렬 배치 처리를 가능하게 한다. HDFS가 초기 예이고 그
  클라우드 네이티브 후계가 **Amazon S3·Azure Blob Storage·Google Cloud Storage**이며, **Apache Iceberg와
  Delta Lake가 받치는 테이블 형식**도 흔한 목적지다 (6장, pp.152–153).[^bellemare2025]
  - 버전 조건: 2025년 저술 시점의 저장소·테이블 형식 지형에 대한 서술이다.
- 운영 형태 둘 — **Kafka Connect 같은 공통 플랫폼을 쓰면 단순한 설정으로 싱크를 지정하고 공유 인프라에서
  돌릴 수 있고**, **독립 마이크로서비스 싱크**는 개발자가 마이크로서비스 플랫폼에서 만들어 독립으로
  관리하는 대안이다 (6장, p.153).[^bellemare2025]
- **같은 책 11장이 그 독립 마이크로서비스 싱크에 배치 형태 하나를 더 준다** — **사이드카
  패턴(sidecar pattern)** 이다. 레거시 코드베이스를 안전하게 고칠 수 없을 때 기본 프로듀서/컨슈머
  하나가 스트림을 소비해 **그 체계의 저장소에 업서트**하되, **자기 컨테이너 안에 살면서도 그
  서비스의 단일 배포 단위의 일부**로 놓인다. 대가는 **복잡도와 조율의 증가**이고 특히 **두 구성
  요소를 함께 배포하고 함께 되돌릴 수 있어야** 한다는 것이다 (11장 §"Integration with Existing
  Systems Using the Sidecar Pattern", pp.248–249).[^bellemare2025] 그 모양의 전문은
  [스트림 처리 프레임워크의 세 모양](stream-processing-framework-shapes.md)에 있다.

## 싱킹과 소싱이 조직에 주는 영향

- 중앙 프레임워크의 이점 — **한 팀이 규모 있게 운영하며 조직 전역 다른 팀의 해방 필요를 받칠 수 있다.**
  통합하려는 팀은 **커넥터 설정과 설계만 신경 쓰면 되고 운영 임무는 지지 않는다.** 여러 팀의 여러
  저장소에 데이터가 흩어진 **큰 조직에서 가장 잘 듣는다** — 팀마다 자기 해법을 만들지 않고도 해방을 빨리
  시작할 수 있기 때문이다 (6장 §"The Impacts of Sinking and Sourcing on a Business",
  p.153).[^bellemare2025]
- **함정이 둘이다** (6장, p.153):[^bellemare2025]
  - **책임이 두 팀에 나뉜다** — 중앙 프레임워크를 운영하는 팀이 프레임워크와 각 커넥터 인스턴스의 안정성·
    확장·건강을 책임진다. 한편 **포착 대상 체계를 운영하는 팀은 독립이어서 커넥터의 성능과 안정성을 바꾸는
    결정(필드 추가·제거, 전송량에 영향을 주는 로직 변경)을 내릴 수 있다.** 이것이 **두 팀 사이에 직접
    의존**을 만든다. 그런 변경은 커넥터를 깨뜨릴 수 있는데 **커넥터 관리 팀만 그것을 감지하게 되어 팀 간
    의존이 선형으로 늘고**, 변경 수가 늘수록 관리하기 어려운 부담이 된다.
  - **체계가 프레임워크에 기대어 안주한다** — 이벤트 기반 원칙이 부분적으로만 채택된 조직에서 더 널리
    퍼지는 문제다. 데이터가 해방되어 스트림에 발행되고 나면 **조직이 네이티브 이벤트 기반 마이크로서비스로
    나아가는 데 안주**할 수 있다. 팀이 **소싱·싱킹을 커넥터 프레임워크에 과하게 의존해 애플리케이션을
    리팩터링하거나 새 이벤트 기반 서비스를 개발하지 않기로** 고르고, 필요할 때마다 새 소스와 싱크를
    요청하며 **하부 애플리케이션 전체를 이벤트에 무지한 채로** 둔다.
- 저자가 상자로 못 박는다 (6장, p.154):[^bellemare2025]

  > CDC tools are *not* the final destination in moving to an event-driven architecture, but instead
  > are primarily meant to help bootstrap the process. The real value of the event broker as the data
  > communication layer is in providing a robust, reliable, and truthful source of event data
  > decoupled from the implementation layers, and the broker is only as good as the quality and
  > reliability of its data.

- **처방이 직관에 반한다** — 두 문제의 완화는 **CDC 프레임워크의 사용을 최소화하고 팀이 (아웃박스 패턴
  같은) 자기 변경 데이터 포착을 구현하게 하는 것**이다. 앞단 작업이 더 들더라도 그렇게 하면 **팀이 자기
  체계의 이벤트 발행을 단독으로 책임지게 되어 팀 간 의존과 깨지기 쉬운 커넥터 기반 CDC가 사라지고**,
  프레임워크 팀의 일이 줄어 정말 필요한 제품을 받치는 데 집중할 수 있다 (6장, p.154).[^bellemare2025]
- **문화 쪽 효과도 적힌다** — 프레임워크 의존을 줄이면 **"이벤트 우선(event-first)" 사고방식**이 퍼진다.
  스트림을 모노리스 사이에서 데이터를 섞는 수단으로 보는 대신 **각 체계를 이벤트의 직접 발행자이자
  소비자로 보게** 되고, **체계가 *언제* 그리고 *어떻게* 이벤트를 생산해야 하는지, "여기 안"의 데이터가
  아니라 "저 바깥"의 데이터를 생각하기 시작**한다 (6장, p.154).[^bellemare2025]
- 그럼에도 프레임워크가 옳은 자리가 명시된다 — **자원이 제한된 제품과 유지보수만 하는 제품에는 중앙
  소스·싱크 커넥터 체계가 상당한 도움**이고 코드베이스를 크게 리팩터링하지 않고 데이터를 넣고 뺄 수
  있다. **새 제품과 활발히 개발 중인 제품은 네이티브 생산으로 가는 것이 최선**이다 (6장,
  p.154).[^bellemare2025]

## 해방 전략의 스펙트럼

- 맺음이 전략을 **스펙트럼**으로 놓는다 (6장 §Summary, p.155):[^bellemare2025]
  - **한쪽 끝은 원천 체계와의 조심스러운 통합**이다. 이벤트가 구현 저장소에 쓰이는 대로 브로커로
    나가고, **어떤 체계는 스트림에 먼저 생산한 뒤 자기 필요를 위해 되소비해 스트림이 단일 진실 원천임을
    더 강화**하기도 한다. **생산자는 좋은 데이터 생산 시민으로서의 자기 역할을 자각하고 의도치 않은 깨는
    변경을 막을 보호 장치를 둔다.**
  - **반대쪽 끝은 고도로 반응적인 전략**이다. 원천 데이터의 소유자가 **브로커로의 데이터 생산에 거의
    아무 가시성이 없고** 프레임워크가 내부 데이터셋에서 직접 당기거나 체인지로그를 파싱하는 데 전적으로
    기댄다. **하류를 깨뜨리는 스키마 파손이 흔하고 원천 구현의 내부 모델 노출도 마찬가지로 흔하다.**
    저자의 판정 — **이 모형은 장기적으로 지속 불가능하고, 깨끗하고 일관된 도메인 이벤트 생산이라는 데이터
    소유자의 책임을 방치한다.**
- 마지막 판정이 기술이 아니라 문화에 걸린다 — **해방 계획이 이벤트 기반 아키텍처로 나아가는 데 얼마나
  성공할지는 조직의 문화가 정한다. 데이터 소유자가 깨끗하고 믿을 만한 스트림을 생산할 필요를 진지하게
  받아들이고, 데이터 포착 기제가 이벤트 데이터 해방의 최종 목적지로는 불충분하다는 것을 이해해야 한다**
  (6장, p.155).[^bellemare2025]

## 저장소가 아니라 요청에서 꺼낼 때

- **이 페이지의 패턴 셋은 전부 데이터가 *저장소*에 있다고 전제한다. 17장이 그 전제가 서지 않는
  자리를 하나 더 놓는다** — 데이터가 **요청-응답으로 들어올 때**다. 클라이언트가 RPC나 HTTP로
  보낸 것을 이벤트로 포장해 스트림에 쓰는 길이 둘 있고(전용 엔드포인트와 REST 프록시), **백엔드
  서버나 프록시가 그것을 스트림에 쓰는 책임을 진다** (17장, pp.334–338).[^bellemare2025]
  - **이 페이지의 아웃박스와 겹치는 물음이 하나 되풀이된다 — 스키마를 어디서 강제하는가**다.
    17장의 답은 셋이다: 클라이언트가 직렬화하거나, 백엔드가 직렬화하거나, 클라이언트가 평문에
    **스키마 ID를 실어 보내** 백엔드가 그것으로 인코딩한다. **REST 프록시 쪽에는 네 번째 답이
    있다** — 프록시가 스키마 레지스트리에 대고 자동 검증해 **불량 데이터를 스트림 밖으로 막아
    낸다** (17장, p.338).[^bellemare2025] 위
    [스키마 호환의 강제 — 쓰기 전 직렬화와 쓴 뒤 직렬화](#스키마-호환의-강제--쓰기-전-직렬화와-쓴-뒤-직렬화)와
    같은 물음에 대한 다른 자리의 답이다.
  - **조직 밖 제3자 API도 같은 자리에 선다** — 이벤트 기반 마이크로서비스가 제3자 API를 불러 그
    응답을 처리하는 구성인데, 저자가 이것을 해방이라 부르지는 않는다. 값으로 청구되는 것은
    **비결정성과 재처리 때의 요청 폭주**다 (17장, pp.338–341).[^bellemare2025] #hypothesis 이것을
    해방 패턴의 넷째 칸으로 세우지 않았다 — 저자가 그렇게 배치하지 않고, 대상이 조직 밖이라 이
    페이지의 "우리 저장소에서 우리 스트림으로"라는 축과 어긋나기 때문이다.
  - 전문은 [요청-응답과 이벤트 기반의 통합](request-response-and-event-driven-integration.md)에
    있다.

## 이 KB의 다른 자리들과의 분업

이 페이지가 세우는 것은 **해방이라는 이행 전략**이고, 각 패턴의 기제는 이미 이 KB의 다른 자리가 갖는다.

| 자리 | 그쪽이 갖는 것 | 이 페이지가 더하는 것 |
|---|---|---|
| [변경 데이터 캡처](../concepts/change-data-capture.md) | CDC가 **무엇을 하는 기제인가**와 반입 패턴으로서의 판정 조건 | 같은 기제를 **레거시 통합 수단**으로 골랐을 때의 이득 넷·단점 셋, 부트스트래핑의 잠금 문제, 정의 변경 대응 |
| [아웃박스 패턴](../concepts/outbox-pattern.md) | 애그리게이트의 도메인 이벤트를 원자적으로 내보내는 **알고리즘 네 단계** | 같은 패턴을 **해방 수단**으로 썼을 때의 내부 모델 격리와 스키마 강제의 두 자리, 그리고 이득 다섯·단점 넷 |
| [증분 갱신 전략](../concepts/incremental-update-strategies.md) | 대상 테이블에 새 행·바뀐 행을 반영하는 **다섯 의미론** | 같은 문제를 **원천에서 꺼내는 쪽**에서 본 폴링 질의와 하이워터 마크 |
| [정확히 한 번 메시지 처리](../concepts/exactly-once-message-processing.md) | 2PC가 성립할 때와 안 할 때의 길, 카프카 트랜잭션 | 이중 쓰기 안티패턴이라는 **이름**과, 브로커 트랜잭션이 아니라 **아웃박스·CDC**로 우회하는 답 |
| [카프카 커넥트](../concepts/kafka-connect.md) | 커넥트 자체의 기제와 운영 | 커넥트를 **중앙 해방 프레임워크**로 놓았을 때 조직에 걸리는 함정 둘 |
| [기록 시스템과 파생 데이터](system-of-record-and-derived-data.md) | 무엇이 정본이고 무엇이 사본인가의 규정 | 싱킹이 **파생 저장소를 스트림에서 만드는 일**이라는 자리, 그리고 해방 데이터에 한정된 단일 진실 원천 |
