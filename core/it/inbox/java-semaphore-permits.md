이 페이지의 질문: **자바의 세마포어는 무엇을 세고, 어디서 틀어지는가.**

세마포어의 원리는 버전에 매이지 않는다. 가상 스레드가 바꾸는 것은 대가의 크기이고, 그 대목만
아래에서 조건을 달아 구분한다.

## 무엇인가

- 정의가 문지기 비유로 온다 — 세마포어(semaphore)는 공유 자원에 대한 접근을 통제하며 문지기처럼
  구는 동기화 장치이고, 자바에서는 `java.util.concurrent` 패키지의 `Semaphore` 클래스가 그
  접근 통제를 다루는 편한 방법을 준다 (2장, p.54).[^rahman2025]
- 원리는 세는 일이다 — 정해진 수의 퍼밋(permit)을 세고 있다가, 스레드가 특정 코드 구간에
  들어가기 전에 퍼밋을 하나 집어 가게 하고 일이 끝나면 돌려받는다. 남은 퍼밋이 없으면 스레드는
  하나가 풀릴 때까지 기다린다 (2장, p.54).[^rahman2025]
- 저자가 드는 그림이 연결 다섯 개짜리 데이터베이스 풀이다. 세마포어로 다섯 스레드만 그 연결을
  동시에 쓰게 만들 수 있다 (2장, p.54).[^rahman2025]

## 세 메서드

- `acquire()` — 퍼밋을 요청한다. 지금 남은 것이 없으면 스레드가 기다린다 (2장,
  p.54).[^rahman2025]
- `release()` — 퍼밋을 세마포어에 돌려준다. 기다리던 다른 스레드가 나아갈 수 있게 된다 (2장,
  p.54).[^rahman2025]
- `availablePermits()` — 지금 몇 개가 비어 있는지 확인한다 (2장, p.54).[^rahman2025]

## 운영에서 더 필요한 것

- 저자가 운영 시스템에서는 자원 사용을 감시하고 타임아웃을 넣어 무한정 블로킹을 막는 것이 자주
  값어치를 한다고 적고, 예제를 그렇게 보강한다 (2장, p.56).[^rahman2025]
- 타임아웃 — `tryAcquire(5, TimeUnit.SECONDS)`처럼 시간을 준 획득은 무한정 블로킹을 피하고 정해진
  시간이 지나면 제어를 호출자에게 돌려준다. 시간 안에 자원을 얻지 못하면 빈 `Optional`을 돌려주는
  것이 매달려 있는 것보다 나은 저하 방식이다 (2장, p.57).[^rahman2025]
- 공정성 — 생성자의 둘째 인자에 `true`를 넘기면 퍼밋이 요청된 순서, 곧 선입선출로 부여되는 공정한
  세마포어가 되어 경합이 심할 때 스레드 굶주림을 막는다 (2장, p.57).[^rahman2025]
- 계측 — 활성 연결 수와 최대 동시 연결 수를 원자적 정수로 따로 세어 두면 디버깅과 용량 계획에
  쓸 수 있다. 저자는 이 계수가 한도를 강제하는 장치가 아니라 관측용임을 명시한다 (2장,
  p.57).[^rahman2025]
- 저자의 검증 실행에서 요청 50건 가운데 32건이 성공하고 18건이 타임아웃했으며, 최대 동시 연결
  수는 한도인 5를 넘지 않았다 (2장, p.59).[^rahman2025]

## 쓰임새 셋

- 자원 관리 — 네트워크 소켓, 데이터베이스 연결처럼 용량이 유한한 공유 자원의 접근을 제한한다.
  동시 데이터베이스 연결 10개짜리 라이선스라면 퍼밋 10개로 초기화한 세마포어가 그 한도를 넘지 않게
  해 준다 (2장, p.59).[^rahman2025]
- 속도 제한 — 웹 서비스나 API에 대한 요청 속도를 통제해 과부하를 막는다. 외부 API가 분당 100건만
  허용한다면 퍼밋을 다시 채우는 예약 태스크와 세마포어를 함께 써서 그 한도를 지킬 수 있다 (2장,
  p.59).[^rahman2025]
- 일반 동시성 제어 — 특정 코드 구간을 동시에 실행하는 스레드 수를 정밀하게 관리한다 (2장,
  p.59).[^rahman2025]

## 유의할 넷

- 공정성의 값 — 공정한 세마포어는 요청 순서를 유지하는 부담 때문에 비공정한 것보다 성능이 조금
  낮을 수 있다. 스레드 굶주림을 막는 것이 순수한 성능보다 중요할 때 공정성을 고른다 (2장,
  p.59).[^rahman2025]
- 블로킹의 값 — `acquire()`는 퍼밋이 없으면 스레드를 블로킹할 수 있다 (2장,
  p.60).[^rahman2025]
  - 버전 조건: JDK 21 이상 — 가상 스레드가 들어오면서 이 블로킹의 부담이 크게 줄었다. 플랫폼
    스레드와 달리 블로킹된 가상 스레드는 운영 체제 자원을 쓰지 않아 세마포어 기반 동기화가 훨씬
    잘 확장된다 (2장, p.60).
- 오류 처리 — 퍼밋 반납은 반드시 `finally` 블록 안에서 꼼꼼히 한다. 예외가 나더라도 자원 누수를
  막고 제대로 정리하기 위해 필수다 (2장, p.60).[^rahman2025]
- 퍼밋 회계 — 세마포어는 퍼밋을 특정 스레드와 묶지 않는다. 어떤 스레드든 자기가 얻지 않은 퍼밋도
  반납할 수 있다. 이 유연성이 쓸모 있을 때도 있지만, 실효 퍼밋 수가 우연히 늘어나는 일을 피하려면
  설계를 신중히 해야 한다 (2장, p.60).[^rahman2025]

## 퍼밋 회계라는 함정

- 저자가 이것을 위험한 별난 성질이라 부른다 — 세마포어는 어느 스레드가 어느 퍼밋을 얻었는지
  추적하지 않는다 (2장, p.60).[^rahman2025]
- 사고의 모양이 간단하다. 퍼밋 2개로 시작한 세마포어에서 한 스레드가 획득하고 반납을 잊고, 다른
  스레드가 얻지도 않은 채 두 번 반납하면 퍼밋이 2개가 아니라 3개 이상이 된다 (2장,
  p.60).[^rahman2025] 운영에서는 데이터베이스 연결 한도를 넘거나 API를 압도하거나 메모리를
  고갈시키는 일로 이어질 수 있다 (2장, p.60).
- 저자가 방탄 패턴이라 부르는 것은 순서 하나다 — 획득은 `try` 앞에서, 반납은 `finally` 안에서
  한다 (2장, pp.60–61).[^rahman2025]

  ```java
  public <T> T useResource(Callable<T> task) throws Exception {
      semaphore.acquire();   // Acquire before try
      try {
          return task.call();
      } finally {
          semaphore.release();   // ALWAYS releases
      }
  }
  ```

- 같은 결함을 다른 소스가 더 이르게 지적해 두었다 — 예외가 나면 세마포어가 결코 풀리지 않는다는
  경고가 [공유 상태는 잘못된 상태다](../concepts/shared-state-is-incorrect-state.md)에 있다.
  거기서는 그 지적이 세마포어를 버리고 자원 접근 자체를 트랜잭션으로 감싸라는 결론으로 이어진다.
