하나의 질문: **잡을 다시 돌려도 대상 데이터셋이 같아지게 하려면 이전 실행이 남긴 것을 어떻게
치우는가.**

Konieczny의 4장은 그 답을 네 범주로 가른다 — **덮어쓰기**(Overwriting), **갱신**(Updates),
**데이터베이스**(Database), **불변 데이터셋**(Immutable Dataset). 이 페이지는 오케스트레이션과
저장 계층에 손을 대는 세 범주(다섯 패턴)를 다루고, 데이터베이스 범주의 두 패턴
(**Keyed Idempotency**·**Transactional Writer**)은
[정확히 한 번 메시지 처리](../concepts/exactly-once-message-processing.md)에 있다 — 그쪽은 브로커·DB가 주는
보장과 층위를 맞대야 하는 자리이기 때문이다.

## 멱등성이라는 낱말

- 왜 오류 관리만으로 부족한가 — 일시적 실패에서 자동 복구하는 것은 **엔지니어링 관점에서는 훌륭한
  기능이지만 데이터 관점에서는 일관성에 심각한 도전을 가져온다. 재시도된 태스크나 잡이 대상 데이터
  저장에 이미 성공한 쓰기 연산을 재생해 중복으로 이어질 수 있다** (4장, p.79).[^konieczny2025]
  - 저자가 곧바로 못 박는 것 — **중복은 최선의 시나리오다. 중복은 소비자 쪽에서 제거할 수 있기
    때문이다.** 최악은 그 반대다 — **재시도된 항목이 제거할 수 없는 중복을 만드는데, 그것들이 같은
    데이터를 나타내는지 당신이 분간조차 할 수 없기 때문이다** (4장, p.79).[^konieczny2025]
- 정의는 절댓값 함수로 세운다 — **몇 번을 호출하든 언제나 같은 결과를 얻는다. 다르게 말해
  `absolute(-1) == absolute(absolute(absolute(-1)))`** (4장, p.79).[^konieczny2025]
- 데이터 엔지니어링 맥락의 멱등성(idempotency)도 목적이 같다 — **데이터 처리 잡을 몇 번 돌리든
  중복 없는, 또는 명확히 식별 가능한 중복을 가진 일관된 출력을 언제나 얻도록 보장하는 방법이다**
  (4장, p.79).[^konieczny2025]
  - 중복 회피가 늘 가능하지는 않다는 단서가 붙는다 — **트랜잭션적 프로듀서를 지원하지 않는 메시징
    시스템에 데이터를 생성한다면 재시도는 여전히 중복된 항목을 생성할 수 있다. 그러나 멱등적 처리
    덕분에 소비자는 그 레코드들을 그런 것으로 식별할 수 있을 것이다** (4장,
    pp.79–80).[^konieczny2025]
- 계보 한 줄 — 저자는 **2018년 "Functional Data Engineering: A Modern Paradigm for Batch Data
  Processing" 기사로 멱등성을 대중화한 Maxime Beauchemin**을 따로 언급한다 (4장,
  p.80).[^konieczny2025]
  - 그 글의 원문이 이 KB에 있다 —
    [함수형 데이터 엔지니어링](../concepts/functional-data-engineering.md)이 그 페이지다. 이 페이지가
    답하는 것이 **어떻게 치우는가**라면 그쪽은 **왜 그래야 하는가**다. 다만 **정의의 모양이
    다르다** — 위 절댓값 항등식(`absolute(-1) == absolute(absolute(absolute(-1)))`)은
    Konieczny의 것이고 Beauchemin의 글에는 그 항등식이 없다. 그쪽의 규정은
    *"produce the same result every time it runs or re-runs"*, 곧 **재실행 결과의
    동일성**이고, 그것을 얻는 수단으로 **덮어쓰기 강제**를 못 박는다.

## Fast Metadata Cleaner — 데이터 대신 메타데이터를 지운다

- 범주의 전제 — **첫 멱등성 계열은 데이터 제거 시나리오를 다룬다. 새 데이터를 쓰기 전에 기존
  데이터를 제거하는 것이 가장 쉬운 접근이다. 그러나 큰 데이터셋에서 그것을 돌리면 컴퓨트 집약적일
  수 있다** (4장, p.80).[^konieczny2025] 그래서 제거를 데이터 기반으로 할지 메타데이터 기반으로
  할지가 갈린다.
- 문제의 실물 — 일간 배치 잡이 **500GB에서 1.5TB의 방문 데이터 이벤트를 처리**하는데, 멱등성을
  위해 **이전 실행이 더한 모든 행을 `DELETE`로 지우고 처리된 행을 `INSERT`하는 두 단계**를 둔다.
  **3주 동안은 잘 돌았지만 그 뒤 지연 문제를 겪기 시작했다. 테이블이 많이 자라면서 `DELETE`
  태스크의 성능이 상당히 악화됐다** (4장, p.80).[^konieczny2025]
- 왜 `DELETE`가 느린가 — **`DELETE`는 종종 두 단계 액션이다. 먼저 삭제할 행을 식별하고 나중에
  식별된 모든 데이터 파일을 덮어써야 한다** (4장, p.81).[^konieczny2025]
  - 반면 **메타데이터 연산은 데이터 파일과 상호작용할 필요가 없으므로 종종 가장 빠르다. 대신 그
    데이터 파일들을 서술하는 훨씬 작은 계층에서 동작한다. 그래서 메타데이터 부분은 물리적 수준
    대신 논리적 수준에서 동작한다고 흔히 말한다** (4장, p.80).[^konieczny2025]
  - 저자가 상자로 갈라 둔 대비 — **의미론적으로 `TRUNCATE TABLE` 명령은 조건 없는
    `DELETE FROM`과 같은 일을 한다. 두 경우 모두 모든 레코드가 제거된다. 그러나 내부적으로
    `TRUNCATE`는 테이블 스캔을 하지 않는다는 점에서 다르다. 그런 이유로 그것은 메타데이터
    연산으로 분류된다** (4장, p.81).[^konieczny2025]
- 해법의 핵심은 데이터셋을 보는 눈을 바꾸는 것이다 — **데이터셋을 단일한 모놀리식 단위로 보는 대신
  물리적으로 나뉜 여러 데이터셋이 함께 하나의 논리적 데이터 단위를 이룬다고 생각할 수 있다. 다르게
  말해 데이터셋을 여러 테이블에 저장하고 뷰(view) 같은 단일한 자리에서 노출할 수 있다** (4장,
  p.81).[^konieczny2025] 저자의 예는 52개 주간 테이블이 한 해치 방문 데이터셋을 이루는 그림이다.
- 그래서 이 패턴은 두 가지에 의존한다 — **데이터셋 파티셔닝과 데이터 오케스트레이션. 파티셔닝이
  멱등성 입도(idempotency granularity)에 직접 영향을 주므로 신중히 정의해야 한다** (4장,
  p.82).[^konieczny2025] 52개 주간 테이블이면 입도는 한 주다.
- 오케스트레이션에 더해야 하는 세 단계 (4장, p.82):[^konieczny2025]
  - **실행 날짜를 분석해 파이프라인이 새 멱등성 입도를 시작할지 이전 것을 이어 갈지 결정한다.**
    주간 테이블이고 실행일이 월요일이면 초기화 분기로, 아니면 곧장 데이터 삽입부로 간다.
  - **멱등성 환경을 만든다. 여기서 `TRUNCATE TABLE` 또는 `DROP TABLE` 두 메타데이터 연산을
    활용한다. `TRUNCATE`를 쓰는 해법은 흔히 멱등성 컨텍스트 테이블을 만드는 태스크가 앞서고,
    `DROP`을 활용하는 접근은 테이블 생성이 뒤따른다.**
  - **멱등성 컨텍스트 테이블들을 노출하는 단일 추상을 갱신한다. 예컨대 주간 테이블들의 합집합으로
    만든 뷰일 수 있다. 다만 `DROP` 기반 접근은 테이블 하나를 드롭하는 중에 사용자가 뷰에 접근하려
    하면 에러가 날 수 있다. 그것이 문제라면 데이터베이스에서 테이블을 드롭하기 전에 뷰에서 그
    테이블을 제거하는 선택적 단계로 완화할 수 있다.**
- 실행 날짜로 분기하는 태스크가 이 패턴의 대표 코드다 — Airflow의 `BranchPythonOperator`가
  **실행 날짜를 검증하고 그 결과에 따라 데이터 처리로 가거나 주간 테이블 관리를 따른다** (4장,
  p.85):[^konieczny2025]

  ```python
  def retrieve_path_for_table_creation(**context):
    ex_date = context['execution_date']
    should_create_table = ex_date.day_of_week == 1 or ex_date.day_of_year == 1
    return 'create_weekly_table' if should_create_table else "dummy_task"
  ```

- 부분 데이터셋만이 아니라 전체 데이터셋에도 쓸 수 있다 — **증분·파티션 데이터셋 말고도 이 패턴은
  전체 데이터셋에 적용된다. 그 경우 워크플로를 단순화해 매 적재마다 테이블 재생성 단계를 돌리거나
  대안인 Data Overwrite 패턴을 쓸 수 있다** (4장, p.83).[^konieczny2025]

## 멱등성 입도가 백필 입도다

- 이것이 이 패턴의 첫째 결과이자 가장 무거운 것이다 — **패턴이 정의하는 멱등성 입도는 백필 입도
  (backfilling granularity)이기도 하다. 다르게 말해 파이프라인을 재생한다면 파티션 테이블을
  만드는 태스크부터 해야 한다. 그러지 않으면 일관성 없는 데이터셋으로 끝난다** (4장,
  p.84).[^konieczny2025]
  - 실물 — **주 단위로 파티션했는데 하루만 백필해야 한다면 주 전체를 다시 돌리는 것 말고
    선택지가 없다. 다만 다른 날들의 전체 파이프라인을 재처리해야 한다는 뜻은 아니다. 하루치만
    무효한 데이터셋을 생성했다면 나머지 날들에 대해서는 데이터 적재 단계만 재생하면 충분하다**
    (4장, p.84).[^konieczny2025]
  - 그리고 세밀한 백필은 아예 불가능하다 — **한 데이터 제공자, 사용자, 고객 하나에 대한 백필처럼
    세밀한 백필에는 이 패턴이 도움이 되지 않는다. 메타데이터 연산은 언제나 테이블 전체에서 동작하기
    때문이다** (4장, p.84).[^konieczny2025]
- 스키마 진화도 같은 성질에 걸린다 — **멱등성 테이블이 새 선택적 필드를 얻으면 이미 존재하는
  테이블들의 스키마를 갱신하는 별도 파이프라인이 필요하다. Fast Metadata Cleaner 패턴 안에서
  그것을 하면 자동으로 데이터 재처리를 수반하게 되어 덜 효과적이다** (4장, p.85).[^konieczny2025]
  - 반대 방향은 공짜다 — **스키마를 진화시키면서 새 필수 필드를 더하는 시나리오라면 새 필드를
    Fast Metadata Cleaner 패턴에 포함시킬 수 있다. 과거 실행을 재생하는 것이 자동으로 처리를
    촉발해 새 필드를 더하기 때문이다** (4장, p.85).[^konieczny2025]

## 메타데이터 한도와 데이터 노출 계층

- 한도 — **패턴은 전용 파티션이나 테이블 생성에 의존하는데, 불행히도 그것들을 무한정 만드는 것이
  종종 가능하지 않다. 예컨대 2025년 저술 시점의 데이터 웨어하우스인 GCP BigQuery와 AWS Redshift는 각각
  4,000개 파티션과 200,000개 테이블의 한도를 갖는다. 두 수치 모두 크지만, 서로 다른 테이블에서
  동작하는 여러 파이프라인에 이 패턴을 적용해야 한다면 이 높은 할당량에 매우 빠르게 도달할 수
  있다** (4장, p.84).[^konieczny2025]
  - #hypothesis 두 수치는 집필 시점(2024) 값이다 — 클라우드 할당량은 공지 없이 바뀌므로 적용 전
    벤더 문서로 확인해야 한다.
  - 완화책 — **동결(freezing) 단계를 더해 가변 멱등성 테이블을 불변 테이블로 바꿔 파티션 범위를
    줄일 수 있다. 예컨대 동결 기간 이후에 변경 가능성이 없다면 주간 테이블을 월간이나 연간
    테이블로 바꿀 수 있다** (4장, p.84).[^konieczny2025]
- 적용 가능한 저장소가 갈린다 — **Fast Metadata Cleaner 패턴은 메타데이터 연산을 지원하는
  데이터베이스에서만 동작한다. 그중에는 데이터 웨어하우스·레이크하우스·관계형 데이터베이스가 있다.
  반면 객체 저장소 위에서는 구현하기 어려울 수 있고, 거기서는 Data Overwrite 패턴에 의존하게 될
  것이다** (4장, p.84).[^konieczny2025]
- 마지막 결과는 접근이다 — **데이터셋이 더 이상 한 자리에 살지 않는데 최종 사용자는 설계의 내부
  세부를 알고 싶지 않고 단일 진입점에서 데이터에 접근하기를 선호할 수 있다. 그 이슈를 넘으려면
  데이터베이스 뷰와 비슷한 해법, 즉 여러 테이블을 묶어 단일 단위로 노출하는 논리적 구조를 쓸 수
  있다** (4장, pp.84–85).[^konieczny2025]

## Data Overwrite — 데이터 계층을 직접 갈아 끼운다

- 언제 이쪽인가 — **메타데이터 연산을 쓰는 것이 선택지가 아니라면(예컨대 `TRUNCATE`와 `DROP`
  명령이 없는 객체 저장소에서 일한다면) 데이터 연산을 적용하는 것 말고 다른 선택지가 없다** (4장,
  p.86).[^konieczny2025]
- 구현은 기술이 정한다 — **구현은 기술에 달렸지만 전형적으로 네이티브 데이터셋 교체 명령에
  의존한다** (4장, p.86).[^konieczny2025] 저자가 나눈 두 갈래:
  - **데이터 처리 프레임워크를 쓴다면 데이터 라이터를 설정하면서 옵션 하나를 설정하기만 하면 될
    수 있다. Apache Spark는 저장 모드(save mode)를, Apache Flink는 쓰기 모드(write mode)
    속성을 쓴다. 라이터를 설정하고 나면 데이터 처리 프레임워크가 나머지(즉 쓰기 전에 기존 파일
    청소)를 한다. 출력 데이터 저장이 조건을 지원한다면 이 설정 주도 해법을 선택적 덮어쓰기로
    확장할 수 있다. `replaceWhere` 옵션에 지정된 필터 조건에 맞는 데이터셋 일부만 덮어쓸 수 있는
    Delta Lake가 그 경우다** (4장, p.86).[^konieczny2025]
  - SQL로 직접 일한다면 세 선택지가 있다 (4장, pp.86–87):[^konieczny2025]

    | 방법 | 저자가 적은 성질 |
    |---|---|
    | `DELETE FROM` + `INSERT INTO` | **데이터베이스로 일하는 많은 엔지니어에게 알려진 단순한 접근** |
    | `INSERT OVERWRITE` | **더 간결한 대안. 문장의 `INSERT` 부분에 있는 레코드로 테이블 전체를 덮어쓴다.** 간결함 말고 **의미론적 차이**가 있다 — **`INSERT OVERWRITE`는 덮어쓸 행을 고르는 것을 지원하지 않는 반면 `DELETE`와 `INSERT` 조합은 지원한다** |
    | 데이터 적재 명령 | **BigQuery의 `LOAD DATA OVERWRITE`처럼 일부는 데이터 덮어쓰기를 네이티브로 지원한다. 나머지는 `TRUNCATE TABLE` 명령이 앞서야 한다** |

- `INSERT OVERWRITE`가 이 패턴의 대표 코드다 — Databricks·Snowflake 같은 **많은 2025년 저술 시점의 데이터
  엔지니어링 해법이 이 연산으로 패턴의 네이티브 구현을 제공한다. 이 명령은 새 데이터를 삽입하기
  전에 테이블 또는 파티션의 내용을 잘라 낸다** (4장, p.88):[^konieczny2025]

  ```sql
  INSERT OVERWRITE INTO devices SELECT * FROM devices_staging WHERE state = 'valid';
  ```

  - 이 자리에서 저자가 흔한 오해 하나를 상자로 갈라 둔다 — **흔히 공유되는 믿음과 달리 `INSERT`
    명령은 명시적으로 정의된 값을 필요로 하지 않는다. 삽입할 컬럼 목록과 맞는 `SELECT` 문을 내어
    다른 테이블에서 레코드를 삽입할 수도 있다** (4장, p.87).[^konieczny2025]
  - Spark의 `save mode`도 같은 패턴이지만 단서가 붙는다 — **저장 모드 자체는 트랜잭션적이지 않다
    (즉 모든 것이 대상 데이터 형식에 달렸다). 다행히 2025년 저술 시점의 테이블 파일 형식은 그 이슈를 다룬다 —
    삭제가 로그의 새 커밋이고 데이터 파일은 손대지 않은 채로 남기 때문이다** (4장,
    p.88).[^konieczny2025]

## 덮어써도 사라지지 않는다

- 첫째 결과는 성능이다 — **데이터 연산이 개입하므로 덮어쓰이는 데이터셋이 크고 파티션되지 않았다면
  패턴이 나쁘게 수행할 수 있다. 그 경우 처리할 데이터가 점점 많아지므로 덮어쓰기는 날이 갈수록
  느려질 것이다** (4장, p.87).[^konieczny2025] 완화책은 파티셔닝 같은 저장 최적화다.
- 둘째 결과가 이 패턴의 함정이다 — **덮어쓰기 명령을 돌린다고 데이터가 사라진다는 보장은 없다.
  시간 여행(time travel) 기능을 가진 데이터 저장을 쓴다면 데이터셋을 과거 버전 중 하나로 복원하는
  것이 가능해야 하므로, 덮어쓰기를 실행한 뒤에도 데이터 블록은 여전히 거기 있을 것이다. 설정된
  보존 기간이 지난 뒤에, 또는 명령이 지원된다면 미사용 공간을 회수하는 vacuum 연산을 돌린 뒤에야
  삭제될 것이다. 데이터를 즉시 삭제하지 않는 데이터 저장의 예로는 테이블 파일 형식, GCP BigQuery,
  Snowflake가 있다** (4장, p.87).[^konieczny2025]
  - 그래서 결과 절의 이름이 **vacuum 필요**다 — **`DELETE` 연산이 디스크에서 데이터를 즉시
    제거하지 않을 수 있다. 테이블 파일 형식과 관계형 데이터베이스에서 그런 일이 일어나는데, 삭제된
    데이터 블록은 `SELECT` 질의로 사용자가 접근할 수 없더라도 여전히 디스크에 존재한다. 이 죽은
    행들이 차지한 공간을 회수하려면 그것들을 진짜로 제거할 vacuum 프로세스를 돌려야 한다** (4장,
    p.88).[^konieczny2025]

## Merger — 지우는 대신 합친다

- 범주가 바뀌는 이유 — **멱등성을 보장하려고 완전한 데이터셋을 제거하는 것은 쉬운 접근이다.
  불행히도 어떤 유형의 데이터셋은 전면 교체의 좋은 후보가 아니다. 데이터 제공자가 생성한 각 새
  버전이 수정되거나 갱신된 데이터의 부분집합만 담는 증분 데이터셋이 그 경우다** (4장,
  p.89).[^konieczny2025]
- 패턴의 적용 조건 — **데이터셋 정체성이 정적이고(즉 행의 정체성이 수정될 위험이 없고) 데이터셋이
  갱신이나 삽입만 지원한다면 최선의 접근은 변경을 기존 데이터셋과 병합하는 것이다** (4장,
  p.89).[^konieczny2025]
  - 저자가 상자로 선을 긋는다 — **완전히 사용 가능한 데이터셋의 멱등적 처리는 덮어쓰기 패턴 중
    하나가 더 쉽다. 그것들은 그저 데이터셋을 삭제하고 교체하기 때문이다. 반면 Merger 패턴은 새
    행과 기존 행을 결합하기 위해 데이터와 상호작용할 것을 요구한다** (4장,
    p.89).[^konieczny2025]
- 구현의 첫 단계가 가장 중요하다 — **새 데이터셋을 옛 것과 결합하는 데 쓸 속성을 정의하는 때다.
  데이터셋 전체에서 유일성을 보장한다면 사용자 ID 같은 단일 속성을 쓸 수 있다. 그렇지 않다면
  웹사이트 방문 이벤트의 방문 ID와 방문 시각처럼 여러 속성을 쓸 수 있다** (4장,
  pp.89–90).[^konieczny2025]
- 결합 수단 — **2025년 저술 시점에 데이터 처리 프레임워크·테이블 파일 형식·데이터 웨어하우스를 포함한 가장 널리
  쓰이는 해법 대부분이 `MERGE`(일명 `UPSERT`) 명령을 지원하고, 그것이 Merger 패턴을 구현하는 가장
  좋은 방법이다** (4장, p.90).[^konieczny2025] 같은 명령을 다른 소스가 의미론으로 정리한 쪽은
  [증분 갱신 전략](../concepts/incremental-update-strategies.md)이다.
- 정의해야 하는 세 시나리오 (4장, p.90):[^konieczny2025]
  - **삽입** — **새 데이터셋의 항목이 현재 데이터셋에 없다. 따라서 더해야 할 새 레코드다.**
  - **갱신** — **두 데이터셋 모두 주어진 레코드를 저장하지만 새 데이터셋이 갱신된 버전을 제공할
    가능성이 매우 높다.**
  - **삭제** — **가장 까다로운 경우다. Merger 패턴이 삭제를 지원하지 않기 때문이다. 병합하려는
    데이터셋에서 레코드가 빠져 있으면 아무 일도 일어나지 않는다. 그런 이유로 삭제는 소프트
    삭제(soft delete), 즉 주어진 레코드가 제거됐음을 표시하는 속성을 담은 갱신으로 표현될 때만
    가능하다.**
- 소프트 삭제를 포함한 `MERGE` 문이 이 패턴의 대표 코드다 (4장, p.90):[^konieczny2025]

  ```sql
  MERGE INTO dedp.devices_output AS target
  USING dedp.devices_input AS input
  ON target.type = input.type AND target.version = input.version
  WHEN MATCHED AND input.is_deleted = true THEN
  DELETE
  WHEN MATCHED AND input.is_deleted = false THEN
  UPDATE SET full_name = input.full_name
  WHEN NOT MATCHED AND input.is_deleted = false THEN
  INSERT (full_name, version, type) VALUES (input.full_name, input.version, input.type)
  ```

  - `INSERT` 쪽에 `is_deleted` 조건이 붙은 이유가 이 예제의 요점이다 — **그러지 않으면 Merger
    패턴의 첫 실행 중에 제거된 레코드를 삽입하고 결과적으로 결코 그것들을 없애지 못할 수 있기
    때문이다** (4장, pp.90–91).[^konieczny2025]

## 병합의 세 가지 대가

- 대가 ① **유일성** — **첫째이자 가장 중요한 요구다. 데이터 제공자 또는 데이터 생성 잡이 각
  레코드를 안전하게 식별하는 데 쓸 수 있는 불변 속성을 정의해야 한다. 그러지 않으면 병합 로직이
  그냥 동작하지 않는다. 백필의 경우 행을 갱신하는 대신 새 행을 삽입해 일관성 없는 중복으로 이어질
  수 있기 때문이다** (4장, p.91).[^konieczny2025]
- 대가 ② **I/O** — **Fast Metadata Cleaner와 달리 Merger는 데이터 기반 패턴이다. 데이터 블록
  수준에서 직접 동작하므로 더 컴퓨트 집약적이다. 다만 2025년 저술 시점의 데이터베이스와 테이블 파일 형식은 먼저
  메타데이터 계층에서 영향받은 레코드를 찾아 이 읽기 부분을 최적화한다. 이 최적화는 무관한 파일의
  처리를 건너뛰는 데 도움이 된다** (4장, pp.91–92).[^konieczny2025]
- 대가 ③ **증분 데이터셋의 백필** — 이것이 다음 패턴을 부르는 구멍이다. 정상 실행에서는 표 4-1처럼
  갱신과 소프트 삭제가 올바르게 통합되고 **그 시점의 데이터셋은 일관적이다** (4장,
  p.92):[^konieczny2025]

  | 반입 시각 | 새 행 | 출력 테이블 행 |
  |---|---|---|
  | 07:00 | A | A |
  | 08:00 | A–U, B | A–U, B |
  | 09:00 | B–D, C | A–U, C |
  | 10:00 | M, N, O | A–U, C, M, N, O |

  - 그러나 08:00부터 재생하면 달라진다 — **데이터셋이 증분이므로 백필은 가장 최근 버전, 즉
    A–U·C·M·N·O를 담은 것에서 시작한다. 그중 일부는 08:00 이후에 쓰인 테이블 부분에서 빠져
    있다. 결과적으로 백필 동안 당신의 소비자는 정상 실행 때와 같은 데이터를 보지 못한다** (4장,
    p.92).[^konieczny2025] 백필한 마지막 기간이 끝나야 테이블이 천천히 정상으로 돌아온다(표 4-2).
  - 저자의 처방 — **이 이슈를 완화하려면 파이프라인 밖에서 테이블을 첫 재생 실행 시점으로 되돌릴
    복원 메커니즘을 구현해야 할 수 있다. 데이터베이스가 이 버전 관리 능력을 네이티브로 지원한다면,
    예컨대 테이블 파일 형식에서 사용 가능한 시간 여행 기능으로는 비교적 쉽다. 그러나 그것은
    무상태 Merger 패턴을 상태 있는 것으로 바꾼다** (4장, p.92).[^konieczny2025]
  - 백필이 필요 없는 경우도 상자로 갈라 둔다 — **데이터 제공자가 데이터셋에 오류를 넣었다면
    파이프라인을 재생할 필요가 없다. 대신 고쳐진 데이터셋을 요청해 새 데이터셋 증분으로 처리하면
    된다. `MERGE` 연산이 무효한 값에 올바른 값을 적용할 것이다. 이 해법은 행의 정체성이 바뀌지
    않는 한 동작한다** (4장, p.93).[^konieczny2025]

## Stateful Merger — 합치기 전에 되돌린다

- 패턴이 더하는 것은 하나다 — **데이터셋을 복원해야 할 때마다 Merger 패턴은 병합 액션에만
  집중하므로 충분하지 않다. 그러나 Stateful Merger라 불리는 대안이 있는데, 추가 상태 테이블
  (state table)을 통해 데이터 복원 능력을 제공한다** (4장, p.94).[^konieczny2025]
- 워크플로가 세 단계가 된다 — **필요하면 테이블을 복원한다 → 병합 문을 돌린다 → 상태 테이블을
  갱신한다** (4장, p.94).[^konieczny2025]
- 상태 테이블은 실행 시각과 테이블 버전의 대응이다 — **병합 연산이 완료되면 병합된 테이블의 새
  버전을 만든다. 그 완료가 또 다른 태스크를 촉발해 생성된 테이블 버전을 가져와 파이프라인의 실행
  시각과 연관시킨다** (4장, p.94).[^konieczny2025] 그 정의가 이 패턴의 대표 코드다 (4장,
  p.99):[^konieczny2025]

  ```sql
  CREATE TABLE IF NOT EXISTS `default`.`versions`
  (execution_time STRING NOT NULL, delta_table_version INT NOT NULL)
  ```

- 복원 단계의 조건 — **복원 프로세스는 파이프라인이 백필 모드로 돌 때만 일어난다. 그렇지 않으면
  아무 일도 하지 않는다** (4장, p.95).[^konieczny2025]
- 백필 모드를 어떻게 아는가 — **데이터 오케스트레이터가 실행 컨텍스트를 제공한다면 그 컨텍스트에서
  실행 모드(백필인지 정상 실행인지)를 알 수 있고 이 컨텍스트 메타데이터를 분석하기만 하면 된다.
  그렇지 않다면 상태 테이블을 활용하는 로직을 구현해야 한다** (4장, p.95).[^konieczny2025]
  그 로직은 둘로 갈린다 (4장, p.95):[^konieczny2025]
  - **이전 파이프라인 실행이 만든 테이블 버전을 가져온다. 이 버전이 없다면 파이프라인을 처음
    돌리거나 첫 파이프라인 실행을 백필한다는 뜻이다. 그 경우 `TRUNCATE TABLE` 명령으로 테이블을
    청소하고 곧바로 병합 연산으로 넘어갈 수 있다.**
  - **현재 데이터셋 버전을 이전 파이프라인 실행이 만든 데이터셋 버전과 비교한다.** 두 버전이 같으면
    **복원할 것이 없다 — 파이프라인이 정상 모드로 도는 것이다.** 다르면 **파이프라인이 백필
    시나리오에 들어갔다는 뜻이고 병합을 적용하기 전에 테이블을 복원해야 한다.**
- 버전 관리 능력이 없는 저장소를 위한 대안도 제시된다 — **테이블을 버전 관리하는 대신 파이프라인은
  모든 원시 데이터를 실행 시각을 저장하는 컬럼을 가진 전용 원시 데이터 테이블에 적재한다. 백필 탐지
  로직은 원시 데이터 테이블이 미래의 실행 시각에 대한 레코드를 갖는지 검증한다** (4장,
  p.97).[^konieczny2025]
  - 그 다음 **`WHERE execution_time >= '{{ ts }}'` 조건에 맞는 모든 행을 먼저 제거하고, 원시
    데이터 테이블이 마지막 유효 버전에 해당하는 모든 행을 저장하므로,
    `devices_history` 테이블을 질의해 Windowed Deduplicator 패턴의 도움으로 테이블을 다시
    만든다** (4장, p.97).[^konieczny2025] 그 중복 제거 패턴은
    [정확히 한 번 메시지 처리](../concepts/exactly-once-message-processing.md)에 있다.

## 상태 테이블이 거짓말하는 두 자리

- 전제 — **제시된 Stateful Merger 구현은 데이터 저장이 버전 관리될 것을 요구한다(즉 각 쓰기가
  테이블의 새 버전을 만들어야 한다). 그것만이 상태를 추적하고 테이블을 이전 버전으로 복원할 수
  있는 유일한 길이다** (4장, p.96).[^konieczny2025]
- 함정 ① **vacuum 연산** — **Delta Lake나 Apache Iceberg의 테이블처럼 버전 관리된 데이터셋은
  상태 테이블 구현을 가능하게 하지만 함정도 숨긴다. 설정된 보존 기간 뒤에 그것들은 데이터셋이 더
  이상 쓰지 않는 파일을 제거한다. 결과적으로 그 순간 이전 버전 일부가 사용 불가가 된다** (4장,
  p.97).[^konieczny2025]
  - 선택지는 둘 — **보존 기간을 늘려 이슈를 조금 완화할 수 있지만 저장 비용도 늘어난다. 또는
    파이프라인이 보존 기간 너머로는 백필될 수 없다는 사실을 받아들일 수 있다** (4장,
    p.98).[^konieczny2025]
- 함정 ② **메타데이터 연산** — 이쪽이 더 조용하다. **컴팩션(compaction)은 데이터를 덮어쓰지 않고
  더 작은 파일들을 더 큰 것으로 합치기만 한다. 그러나 이 무데이터 액션에도 불구하고 테이블의 새
  버전을 만든다. 결과적으로 복원 액션에서 언제나 상태 테이블의 이전 버전을 쓴다면 두 병합 실행
  사이에 일어난 연산들을 놓치게 된다** (4장, p.98).[^konieczny2025] 그 컴팩션의 패턴 쪽 서술은
  [작은 파일 문제와 컴팩션](small-files-and-compaction.md)에 있다.
  - 처방 — **버전이 1씩 증가한다고 가정하면, 이전 버전을 읽는 대신 현재 실행 시각에 해당하는
    버전을 읽고 1을 빼도록 로직을 바꿀 수 있다** (4장, p.98).[^konieczny2025] 즉
    `version_to_restore = version_for_current_execution_time - 1`이다.

## Proxy — 지우지 않고 한 번만 쓴다

- 마지막 범주의 전제 — **지금까지 본 패턴들은 가변 데이터셋에서 동작했다. 전면 데이터 제거를
  포함해 어떤 식으로든 데이터셋을 바꿀 수 있다는 뜻이다. 그러나 기존 데이터를 삭제하거나 갱신할 수
  없다면 어떻게 하는가** (4장, p.110).[^konieczny2025]
- 이름의 유래 — **"어떤 문제든 간접 계층 하나를 더 넣어 풀 수 있다"는 가장 잘 알려진 엔지니어링
  격언 중 하나에서 영감을 받았다. 그래서 이름이 Proxy다** (4장, p.110).[^konieczny2025]
- 문제 — 배치 잡이 매번 전체 데이터셋을 생성하고 이전 것을 덮어써 왔는데, **법무 부서가 모든 과거
  버전의 사본을 보관할 것을 요구했다. 결과적으로 현재의 가변 접근은 더 이상 유효하지 않다. 각 사본을
  유지하되 가장 최근 테이블만 한 자리에서 노출하도록 파이프라인을 재작업해야 한다** (4장,
  p.110).[^konieczny2025]
- 해법의 두 부분 (4장, pp.110–111):[^konieczny2025]
  - **불변성 보장** — **매번 새 데이터를 다른 위치에 적재해 불변성을 보장해야 한다. 좋고 쉬운
    해법은 타임스탬프가 붙거나 버전이 붙은 테이블을 쓰는 것이다. 중요한 점은 테이블을 만든 뒤 이
    테이블들에서 모든 쓰기 권한을 제거해야 한다는 것이다. 결과적으로 그것들은 한 번만 쓸 수 있게
    된다.**
    - 객체 저장소 위라면 더 쉽다 — **잠금 접근은 WORM(write once read many)으로도 알려져 있고
      모든 주요 객체 저장 서비스가 지원한다. AWS S3에는 Object Lock, Azure Blob에는 불변성 정책,
      GCP에는 객체 홀드 또는 버킷 잠금을 쓴다** (4장, p.111).[^konieczny2025]
  - **단일 데이터 접근점 = 프록시** — **대개는 `SELECT` 문에 어떤 데이터 변환도 없이 가장 최근
    테이블을 노출하는 패스스루 뷰일 것이다. 이 접근은 대부분의 데이터 웨어하우스와 관계형
    데이터베이스, 그리고 OpenSearch(별칭 경유)·Apache Cassandra·ScyllaDB·MongoDB 같은 일부
    NoSQL 저장소에서 동작한다.**
    - 뷰가 없다면 **비슷한 구조를 직접 만들어야 한다. 위치를 참조하거나 소비자가 처리해야 할
      파일을 명시적으로 나열하는 매니페스트 파일(manifest file)일 수 있다. 책임 관점에서는 매니페스트
      생성을 데이터 처리 잡에서 격리하는 것이 낫다. 그래야 어떤 이유로든 매니페스트 생성이 실패해도
      데이터를 재처리할 필요가 없다** (4장, p.111).[^konieczny2025]
- 셋째 구현은 저장소에 맡기는 것이다 — **Delta Lake·Apache Iceberg 같은 테이블 파일 형식과 GCP
  BigQuery 같은 데이터 웨어하우스에 적용된다. 이 데이터 저장들은 쓰기마다 테이블 하나를 만들 수도
  있지만 더 단순한 구현이 가능하다. 테이블을 덮어써도 시간 여행 능력을 보장하려고 데이터가 여전히
  거기 있기 때문이다. 결과적으로 각 쓰기가 내부적으로 테이블의 새 버전을 만들고 질의나 복원을 위해
  디스크의 옛 데이터를 계속 사용 가능하게 둔다. 다만 이 해법은 제한적이고 설정 불가능한 보존 능력을
  가질 수 있다 — 예컨대 집필 시점 BigQuery는 7일이다** (4장, p.111).[^konieczny2025]
  - **네이티브로 버전 관리되는 데이터 저장에서는 쓰기 권한을 제거하는 것이 가능하지 않지만, 기반
    저장 시스템 덕분에 이 해법에는 권한 관리가 필요하지 않다** (4장, p.111).[^konieczny2025]
- 결과 둘 (4장, p.112):[^konieczny2025]
  - **데이터베이스 지원** — **모든 데이터베이스가 이 훌륭한 뷰 기능을 갖지는 않는다. 매니페스트
    파일로 대체할 수 있지만 그러면 읽기 프로세스가 더 번거로워진다.**
  - **불변성 설정** — **데이터 오케스트레이션 수준에서 촉발된 쓰기 태스크의 출력을 설정해 불변성을
    강제할 수 있다. 그러나 그것으로 충분하지 않다. 데이터 저장에서도 불변성을 강제하려면 인프라 팀의
    도움이 필요할 것이다. 객체 저장소에 잠금을 만들고 테이블이 생성되고 나면 그 테이블에서 쓰기
    권한을 제거하면 된다.**
- 매 실행이 자기 테이블에 쓰게 만드는 이름 생성이 이 패턴의 대표 코드다 — **파이프라인 인스턴스가
  재실행되면 이전 데이터셋을 다시 쓸 수 없고 대신 새 데이터셋을 다른 테이블에 써야 한다** (4장,
  p.113):[^konieczny2025]

  ```python
  def get_devices_table_name() -> str:
    context = get_current_context()
    dag_run: DagRun = context['dag_run']
    table_suffix = dag_run.start_date.strftime('%Y%m%d_%H%M%S')
    return f'dedp.devices_internal_{table_suffix}'
  ```

  - 권한이 마지막 조건이다 — **구현은 조작을 수행하는 사용자가 테이블을 생성만 할 수 있도록 보장해야
    한다. 그러지 않으면 사용자가 실수로라도 이전에 생성된 내부 테이블을 삭제해 Proxy 패턴이 제공하는
    불변성 보장을 깰 수 있다** (4장, p.113).[^konieczny2025]

## 레이크하우스 쪽이 같은 병합을 계층 배치의 문제로 세운다

2025년에 나온 레이크하우스 설계서 하나가 같은 `MERGE` 명령을 다루되 **다른 물음에 매단다.** 이
페이지의 물음이 "다시 돌려도 같아지려면 무엇을 치우는가"라면, 그쪽의 물음은 "**증분 변경만 다뤄야
할 때 무엇으로 합치는가**"다. 층위가 달라 겹치지 않고, 그래서 `contradicts`도 걸지 않는다.

- 그쪽이 병합을 부르는 이유는 재실행이 아니라 **증분 적재**다 — 복잡한 필터로 변경분(갱신과 신규
  항목)만 다뤄야 하는 시나리오에서 병합 연산이 결정적이 된다 (5장 §"Implementation of Lakehouse
  Tables" ▸ "Updating Tables with MERGE Operations").[^strengholt2025]
- **조건절의 어휘를 더 넓게 센다** — 이 페이지의 대표 코드가 일치·불일치 둘을 쓴다면, 그쪽은
  `WHEN MATCHED`·`WHEN NOT MATCHED`·`WHEN MATCHED AND`·`WHEN NOT MATCHED BY TARGET`·
  `WHEN NOT MATCHED BY SOURCE` 다섯을 나열하고 이 조건들이 증분 적재 관리의 강력한 도구가 된다고
  적는다 (같은 소절).[^strengholt2025] 마지막 둘은 **원천에 없는 대상 행**을 다루는 자리라, 이
  페이지가 "Merger 패턴이 삭제를 지원하지 않는다"며 소프트 삭제로 우회한 그 구멍과 맞닿는다.
- **그쪽이 더하는 것은 대가의 종류다.** 이 페이지가 유일성·I/O·백필 셋을 세운다면, 그쪽은 **원천
  데이터의 더러움**을 센다 — 원천이 깨끗하지 않거나 조인 조건이 단순하지 않으면 복잡성이 생기고,
  데이터셋에 중복 항목이 있으면 **병합 전에 중복을 제거해야 할 수 있다** (같은
  소절).[^strengholt2025] 이 페이지의 대가 ①(유일성)이 요구하는 것과 같은 전제를 다른 각도에서
  적은 것이다.
- **그 대가에서 나오는 배치 규칙이 이 절에서 가장 옮길 값어치가 있다** — 그래서 **복잡한 병합
  연산은 흔히 메달리온의 다음 계층들에서 수행된다** (같은 소절).[^strengholt2025] 곧 그쪽의 처방은
  패턴을 바꾸는 것이 아니라 **패턴을 돌릴 계층을 옮기는 것**이다. 이 페이지가 Stateful Merger로
  푸는 문제(병합의 전제가 깨지는 자리)를 그쪽은 **아키텍처의 계층 경계로** 푼다.
