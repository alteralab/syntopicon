하나의 질문: **누가 이 데이터에 닿을 수 있는지를 어느 입도로, 어디에 적어 두는가.**

Konieczny의 7장에서 **접근 제어**(Access Control)와 **연결**(Connectivity) 두 범주의 네
패턴이다. 앞의 둘은 **권한을 어디까지 좁힐 수 있는가**를, 뒤의 둘은 **그 권한을 증명하는 자격
증명을 어디에 두는가**를 다룬다. 나머지 범주는 [개인 데이터 제거 패턴](personal-data-removal-patterns.md)과
[암호화와 익명화 패턴](data-encryption-and-anonymization-patterns.md)에 있다.

## 테이블 권한만으로 부족할 때

- 접근 제어 범주의 전제 — **가장 효율적인 데이터 제거 패턴조차 접근 제어와 함께 와야 할 기본 보안을
  제공하기에는 충분하지 않다. 실제로 컴플라이언트한 것에 더해, 인가된 사용자만 데이터의 가장 결정적인
  구획에 접근하게 하고 싶을 것이다. 개인 데이터를 비공개로 유지하는 것이 결정적이지만, 데이터 자체가
  당신이 가진 가장 큰 경쟁 자산일 수 있다** (7장, p.207).[^konieczny2025]
- 장 도입부의 실물 — **데이터셋이 조직 안에서 열려 있는데 다른 팀이 실수로 그것을 덮어쓴다고
  상상해 보라. 당신과 하류 소비자에게 미치는 결과는 클 수 있다** (7장,
  p.197).[^konieczny2025]

## Fine-Grained Accessor for Tables — 열과 행까지 내린다

- 문제의 실물 — HDFS/Hive 작업부하를 클라우드 데이터 웨어하우스로 이전한 뒤 보안 접근 정책이
  필요해졌다. 사용자·그룹 생성은 쉬웠지만 **이해관계자로부터 추가 요구가 있다. 사용자가 주어진
  테이블에 접근할 권한이 있음에도 모든 열과 행을 읽을 권한은 없을 수 있다. 이 저수준 자원에 대한
  인가 기제도 구현해야 한다** (7장, p.207).[^konieczny2025]
- 열 수준 접근의 세 구현 (7장, pp.207–208):[^konieczny2025]
  - **가장 쉬운 구현은 `GRANT` 연산자에 기대는데, 인가된 액션 범위 안의 열을 정의하게 해 준다.
    Amazon Redshift와 PostgreSQL에서 지원된다.** 실물은 `GRANT SELECT(id, login,
    registered_datetime) ON dedp.users TO user_a;`이고, 그 뒤 **`user_a`가 나열되지 않은 열을
    포함하는 질의(`SELECT *` 같은)를 발행하면 데이터베이스는 "ERROR: permission denied for
    table users" 같은 오류를 반환한다** (7장, p.209).[^konieczny2025]
  - **둘째 구현은 데이터 카탈로그와 열에 설정된 태그에 기댄다. GCP BigQuery에서 패턴이 그렇게
    동작한다. 구현은 Data Catalog에 정책 태그를 만들고 그것을 BigQuery 테이블의 보호된 열에
    할당하는 것으로 시작한다. 다음 단계는 각 정책 태그에 대해 Fine-Grained Reader 역할을 할당해
    사용자가 보호된 테이블에 접근하도록 인가하는 것이다.**
  - **셋째 구현은 데이터 마스킹 기능에 기반한다. 여기서 사용자는 보호된 열을 볼 수 있지만 접근
    권한이 없으면 그 내용은 숨겨진다. Unity Catalog를 쓰는 Databricks와 Snowflake가 열 수준 접근
    정책을 그렇게 구현한다.** 실물은 `CREATE FUNCTION ip_mask(ip STRING) RETURN CASE WHEN
    is_member('engineers') THEN ip ELSE '.' END;`을 만들어 열 정의에 `MASK ip_mask`로 다는 것이다.
- 열만으로는 부족하다 — **열 수준 보안은 완전한 세밀 수준 접근 보호를 제공하지 않지만, 행 수준
  보안으로 그것을 완전하게 만들 수 있다. 행 수준 접근은 실행되는 질의에 `WHERE` 조건을 즉석에서
  더하는 다소 동적인 함수에 기대는 일이 잦다. 다만 이름은 다를 수 있다 — Databricks는 그것을 ROW
  FILTER라 부르고, Amazon Redshift는 Row-Level Security라 부르며, GCP BigQuery와 Snowflake는
  행 접근 정책으로 분류한다. 이 구현은 보호된 테이블에 대한 모든 select 요청에 동적 조건을 더할
  별도의 데이터베이스 객체를 정의하는 것으로 이뤄진다** (7장, p.208).[^konieczny2025]
  - **네이티브 지원이 없어도 흉내 낼 수 있다** — **데이터베이스가 행 수준 접근 인가를 네이티브로
    지원하지 않으면, 접근 가드 조건을 가진 뷰에서 테이블을 노출해 그것을 시뮬레이션할 수 있다**
    (7장, p.208).[^konieczny2025] 실물이 `CREATE VIEW users_blogs AS SELECT ... FROM blogs
    WHERE table.blog_author = current_user`이고, **생성된 뷰는 질의를 발행한 사용자가 소유한
    블로그를 반환한다. 그러면 조건이 사용자마다 달라지고, 결과적으로 각 사용자가 뷰의 전용 판을
    갖게 된다** (7장, p.209).[^konieczny2025]
  - PostgreSQL의 네이티브 판이 이 패턴의 대표 코드다 — **정책을 써서 누군가 보호된 테이블을 질의할
    때마다 조건을 더한다** (7장, p.210):[^konieczny2025]

    ```sql
    ALTER TABLE dedp.users ENABLE ROW LEVEL SECURITY;

    CREATE POLICY user_row_access ON dedp.users USING (login = current_user);
    ```

  - 관계형 밖에도 있다 — **AWS DynamoDB가 그런 경우로, 키 기반 접근을 가진 NoSQL 데이터베이스다.
    사용자 로그인에 기반한 행 접근 정책을 시뮬레이션하고 싶다면 아이덴티티·접근 관리(IAM) 정책으로
    할 수 있다.** 그 정책은 **`dynamodb:LeadingKeys` 속성에 기대는데, 각 사용자가 자기 `user_id`
    값으로 시작하는 행만 읽게 해 준다** (7장, p.210).[^konieczny2025]

## 세밀함이 부딪히는 세 벽

- 저자가 먼저 이 패턴을 상대적으로 후하게 평가한다 — **이 기능은 데이터베이스에서 네이티브로
  지원되므로, 지금까지 본 다른 패턴에 견주면 단점의 수가 비교적 적다** (7장,
  p.209).[^konieczny2025]
- **행 수준 보안의 한계** — **대부분의 행 수준 보안 구현은 사용자 이름·사용자 그룹·IP처럼 연결
  세션에서 직접 얻을 수 있는 속성으로 이뤄진 제한된 적용 범위를 갖는다** (7장,
  p.209).[^konieczny2025]
- **데이터 타입** — **열이 중첩 구조 같은 복합 타입이라면 단순한 열 기반 접근 전략을 적용할 수 없을
  수 있다. 열 기반 권한은 이름대로 열을 가리키므로, 그것을 처음에 중첩된 속성에 적용하려면 먼저
  그것들을 펼쳐 다른 테이블에서 노출하거나, 후자가 세밀한 권한을 지원한다면 Dataset Materializer
  패턴을 써야 한다** (7장, p.209).[^konieczny2025]
- **질의 오버헤드** — **행 수준·열 수준 보안 보호가 보안된 테이블에 대해 실행되는 질의에 동적으로
  더해지는 SQL 함수로 표현될 수 있다. 이 오버헤드가 예상치 못한 지연을 일으키면, 사용자나 그룹이
  읽도록 허용된 데이터만 가진 전용 테이블이나 뷰를 Dataset Materializer 패턴으로 만들어 완화할 수
  있다. 물론 이 완화도 데이터 중복이나 많은 접근 그룹에 대한 거버넌스 같은 한계를 갖는다** (7장,
  p.209).[^konieczny2025]
  - **완화책이 두 결과 모두에서 같은 패턴(Dataset Materializer)을 가리킨다** — 그 패턴은 8장
    데이터 저장 범주에 있고 이 KB에는 아직 반입되지 않았다.

## Fine-Grained Accessor for Resources — 클라우드 자원에 최소 권한을 건다

- 문제의 실물은 감사 지적이다 — **보안 감사가 클라우드 계정에서 지나치게 넓은 권한을 탐지했다.
  발견된 위험 중 하나는 한 데이터 처리 잡이 객체 저장소에 있는 모든 데이터셋을 덮어쓸 수 있다는
  가능성이다. 감사인은 시스템의 각 구성 요소에 최소한으로 요구되는 권한을 할당해 데이터 처리 잡이
  자기가 실제로 작업하는 데이터셋만 조작할 수 있게 하는, at-least privilege라 불리는 보안 모범
  사례를 제시했다** (7장, p.211).[^konieczny2025]
  - **원서의 낱말이 통용 표기와 다르다** — 저자는 일관되게 `at-least privilege`라고 쓰지만
    (p.211·p.214), 이 원칙의 확립된 이름은 **최소 권한의 원칙**(principle of least privilege)이다.
    Reis & Housley가 그 이름으로 정의하는 자리는
    [데이터 엔지니어링의 저류](data-engineering-undercurrents.md)에 있다. 저자 자신의 설명
    ("최소한으로 요구되는 권한을 할당")은 통용 정의와 같으므로, 표기 차이지 내용 차이가 아니다.
- **좋은 소식은 AWS·Azure·GCP를 포함한 모든 주요 클라우드 제공자가 at-least privilege 원칙의
  구현을 갖고 있다는 것이고, 그것이 Fine-Grained Accessor for Resources 패턴의 뼈대다** (7장,
  p.211).[^konieczny2025]
- **두 전략이 갈리는 자리는 정책 문서를 어디에 붙이느냐다** (7장, pp.211–212):[^konieczny2025]
  - **첫 접근은 자원 기반(resource based)인데, 접근 범위를 자원 수준에서 직접 정의하기 때문이다.**
    실물은 GCS 버킷에 IAM 정책을 할당하는 것이다.
  - **둘째 접근은 자원 대신 아이덴티티를 쓴다. 여기서 접근 권한은 아이덴티티 수준에서 직접 정의된다
    (예컨대 사람 또는 애플리케이션 사용자). AWS는 서비스가 맡는(assume) IAM 역할로 이 모드를
    지원한다.**
  - 그림이 그 차이를 요약한다 — **자원 기반 접근에서는 접근 통제가 각 자원에 직접 붙고, 아이덴티티
    기반 접근에서는 사용자 수준에 위치한다** (7장, p.212).[^konieczny2025]
- 세밀함의 범위 — **세밀한 권한은 흔히 유연하다. 특정 자원, 같은 접두사로 시작하는 자원 집합, 심지어
  런타임 조건에 기반한 자원을 겨냥할 수 있다. 마지막 구현은 인프라의 가장 낮은 수준에서 접근을
  통제하므로 이전 패턴의 행 수준 접근과 비슷해 보인다** (7장, p.213).[^konieczny2025] 저자의
  실물은 S3의 태그 기반 접근 정책으로, **각 자원에 개별적으로 연관된 커스텀 메타데이터 속성(태그)에
  기댄다.**

## 원칙대로 하면 관리가 안 된다는 맞교환

- 저자가 이 결과에 붙인 이름이 그대로 논지다 — **책대로 하는 보안의 맞교환**(security by the book
  trade-off). **보안 어림규칙은 at-least privilege 원칙으로, 사용자나 그룹이 지금 필요한 자원에만
  접근을 가져야 한다는 것이다. 훌륭한 원칙이지만, 복잡한 환경에서 유지보수하기 어려울 작은 접근 정책
  정의를 많이 만들어 내는 것으로 이어질 수 있다** (7장, p.214).[^konieczny2025]
  - 완화책과 그것이 다시 깨는 것 — **이 문제를 완화하고 자원을 관리 가능한 크기로 유지하려면 와일드카드
    기반 접근을 써서 각 클라우드 자원을 개별적으로 정의하는 대신 `visits*` 같은 접두사를 쓸 수 있다.
    결과적으로 접근 정책이 "visits"로 시작하는 모든 자원에 적용된다. 그러나 이는 at-least privilege
    원칙을 위반할 수 있는데, 사용자가 미래에 생성될 모든 visits 접두 자원에 접근을 가져야 한다고
    보장할 수 없기 때문이다. 그런 이유로 이 단순화 전략을 보안 부서와 논의해야 한다** (7장,
    p.214).[^konieczny2025]
  - **처방이 원칙을 지키라고도, 어기라고도 하지 않는다** — 저자가 내놓는 것은 결정을 다른 부서로
    넘기는 절차다. 위 [개인 데이터 제거 패턴](personal-data-removal-patterns.md)의 보존 기간
    상자(CDO·법무에 재확인하라)와 같은 형태다.
- **복잡성** — **한 프로젝트에서 자원 기반과 아이덴티티 기반 접근을 둘 다 쓰면 무심코 시스템의
  복잡성을 늘리고 있을 수 있다. 가능하면 하나의 해법, 되도록 당신 유스케이스를 더 많이 덮는 쪽을
  선호하는 것이 낫다** (7장, p.214).[^konieczny2025]
- **쿼터** — **다른 어떤 클라우드 자원과 마찬가지로 접근 정책조차 한계를 갖는다. 예컨대 AWS IAM
  서비스는 기본적으로 1,500개의 커스텀 정책을 허용하고, GCP IAM은 프로젝트 안의 커스텀 역할에
  한계(300)를 갖는다. 다만 일부 한계는 유연해서 클라우드 제공자에게 늘려 달라고 요청할 수 있다**
  (7장, p.214).[^konieczny2025]
  - **이 숫자가 위 맞교환을 산수로 만든다** — 최소 권한을 정직하게 지키면 정책 수가 자원 수에
    비례해 늘고, 쿼터는 상수다. 와일드카드는 편의가 아니라 그 산수의 결과다.

## Secrets Pointer — 값 대신 이름을 갖는다

- 연결 범주의 전제 — **지금까지 데이터를 보호하는 법을 배웠다. 이것이 데이터 보안의 핵심이지만
  충분하지 않을 수 있다. 이전 장의 데이터 흐름 패턴을 기억하는가? 데이터는 같은 시스템 안에서 또는
  다른 시스템에 걸쳐 끊임없이 흐르고 있으며, 당신은 그것에 접근해야 할 것이다** (7장,
  p.226).[^konieczny2025]
  - 장 도입부가 위험을 명시한다 — **명백히 Git 저장소에 자격 증명을 저장하는 것은 데이터 유출
    위험을 높이므로 최선의 생각이 아니다. 대신 외부의 더 안전한 곳에 저장해야 한다** (7장,
    p.197).[^konieczny2025]
- 문제의 실물 — 지오로케이션 강화 API의 유일한 인증 수단이 로그인·비밀번호 쌍인데, **과거에 팀이
  다른 API에 쓰던 로그인·비밀번호를 실수로 공유했다. API가 요청 과금이었으므로 그 유출은 청구액
  증가로 이어졌다** (7장, p.226).[^konieczny2025]
- 해법의 발상은 한 문장이다 — **자격 증명은 민감한 파라미터다. 그것을 보안하는 가장 좋은 방법 중
  하나는… 어디에도 저장하지 않는 것이다. 대신 참조(포인터라고도 함)를 쓸 수 있다** (7장,
  p.226).[^konieczny2025]
- 비밀 관리자 서비스(**Google Cloud Secret Manager**·**AWS Secrets Manager**)를 쓸 때 얻는 것
  (7장, p.226):[^konieczny2025]
  - **첫째, 이 민감 데이터를 관리하는 중앙 장소다. 이 중앙화 덕에 접근 모니터링이 더 쉽다.**
  - **둘째, 이 구성 요소는 관리도 촉진한다. 모든 소비자를 갱신할 필요 없이 새 자격 증명 집합을
    그냥 설정할 수 있다.**
  - **소비자는 더 이상 민감 파라미터 값을 참조하지 않는다. 대신 비밀 관리자 서비스에서의 이름을
    참조하게 된다. 결과적으로 각 소비자가 런타임에 서비스에 질의를 발행해 비밀의 값을 가져온다.
    추가로 통신 비용을 아끼려고 소비자는 자격 증명을 얼마간 로컬 캐시에 저장할 수 있다.**
- **접근이 두 수준에서 보호된다 — 첫 수준에서 소비자는 비밀 관리자에 접근이 있어야 한다. 그렇지
  않으면 키를 가져올 수 없다. 이 단계를 보안하려면 세밀한 접근 패턴 중 하나를 쓸 수 있다. 둘째
  보호 수준은 자격 증명 자체에 의해 네이티브로 보장된다. 유효하지 않다면 소비자는 기저 API나
  데이터베이스에 접근할 수 없을 것이다** (7장, p.227).[^konieczny2025]
- 참조로만 연결을 세우는 것이 이 패턴의 대표 코드다 (7장, p.228):[^konieczny2025]

  ```python
  secretsmanager_client = boto3.client('secretsmanager')
  db_user = secretsmanager_client.get_secret_value(SecretId='user')['SecretString']
  db_password = secretsmanager_client.get_secret_value(SecretId='pwd')['SecretString']
  spark_session.read.option('driver', 'org.postgresql.Driver').jdbc(
    url='jdbc:postgresql:dedp', table='dedp.devices',
    properties={'user': db_user, 'password': db_password})
  ```

  - 저자의 해설이 이 패턴의 요지를 정확히 좁힌다 — **연결 설정이 여전히 사용자와 비밀번호를
    참조하지만 코드는 그 값을 모른다. 음, 기술적으로는 알지만 비밀 관리자 데이터 저장 덕분에만
    안다. 달리 말해 자격 증명이 코드베이스에 매이지 않고 별도 자산으로 관리된다** (7장,
    p.228).[^konieczny2025]
  - 덤 하나 — **여러 환경에서의 작업도 단순해진다. IaC로 스크립트화된 프로젝트에서 데이터베이스를
    연결 속성과 함께 만들면 모든 환경에 대해 같은 비밀 이름을 유지하고 IaC가 그 생성을 자동화하게
    할 수 있다. 그러면 코드가 환경마다 다른 연결 파라미터를 저장할 환경별 설정 파일을 다룰 필요가
    없다** (7장, p.228).[^konieczny2025]

## 비밀을 옮겼다고 없어진 것은 아니다

- 저자가 결과 절을 인용으로 연다 — **Phil Karlton의 "컴퓨터 과학에는 어려운 것이 둘뿐이다:
  캐시 무효화와 이름 짓기." 캐시 부분이 Secrets Pointer에도 적용된다** (7장,
  p.227).[^konieczny2025]
- **캐시 무효화와 스트리밍 잡** — **자격 증명을 캐시하면 가장 최신 것을 쓰고 있는지 결코 알 수 없고,
  이는 연결 문제로 이어질 수 있다. 반면 많은 자격 증명 조회 요청을 잠재적으로 피해 비싼 경우 실행
  시간을 최적화할 수 있다. 그것은 좋은 일이지만, 캐시를 구현한다면 자격 증명을 갱신할 수도 있어야
  한다** (7장, p.227).[^konieczny2025]
  - 가장 단순한 답과 그 조건 — **자격 증명 갱신 요청을 보내고 싶지 않다면 가장 단순한 접근은 그냥
    잡을 실패하게 두는 것이다. 정상적으로 재시작되면 새 실행 판이 비밀 관리자에서 자격 증명을 다시
    적재해야 한다. 그렇지만 자격 증명이 매우 자주 바뀐다면 실패 수를 늘릴 것이므로 최적이 아닐 수
    있다. 또한 재시도에도 데이터를 올바르게 유지해야 하므로 멱등성 디자인 패턴 중 하나를 쓰는 것을
    기억하라** (7장, p.227).[^konieczny2025]
  - 비동기 갱신도 안전하지 않다 — **비동기 갱신 프로세스를 쓰려고 할 수도 있지만, 여기서도 출력
    데이터 저장으로 데이터를 보내기 시작한 뒤 연결 파라미터를 갱신하기 전에 자격 증명이 바뀌면 쓰기
    문제를 만날 수 있다** (7장, p.227).[^konieczny2025]
- **로그** — **Secrets Pointer 패턴은 자격 증명이 유출되지 않으리라는 거짓 보안감을 준다. 실제로
  그것들은 이제 인가된 엔티티만 접근할 수 있는 보안된 장소에 저장된다. 이 부분이 뚫리지 않더라도,
  무심코 로그에 포함시키면 여전히 비밀을 유출할 수 있다** (7장, p.227).[^konieczny2025]
- **비밀은 여전히 비밀이다** — **소비자가 자격 증명을 다룰 필요가 없다고 해서 자격 증명이 전혀 없다는
  뜻은 아니다. 실제로 소비자가 비밀 값 대신 참조를 쓸 수 있게 하려면, 비밀 저장소에 비밀 값을 안전하게
  생성해야 하는 비밀 생산자가 있다. 실무에서 이는 저장소에 비밀 값을 넣는 사람 관리자이거나 데이터베이스를
  만들면서 임의 비밀 값을 정의하는 IaC 스택이다** (7장, p.227).[^konieczny2025]
  - **위험이 사라진 것이 아니라 한 자리로 모인 것이다.** 그 자리를 지키는 것이 위
    Fine-Grained Accessor 패턴들의 몫이고, 저자가 두 범주를 잇는 자리도 거기다.

## Secretless Connector — 자격 증명 자체를 없앤다

- **Secrets Pointer 패턴은 자격 증명을 보안하는 법을 보여 준다. 그런데 관리할 자격 증명이 아예
  없는 편이 더 낫다고 말한다면 어떨까? 그것이 다음 패턴이 가능하게 하는 것이다** (7장,
  p.228).[^konieczny2025]
- 두 구현 (7장, pp.229–230):[^konieczny2025]
  - **첫 구현은 클라우드 제공자에서 가용한 IAM 서비스를 쓴다. 여기서 사용자나 관리자가 문서 접근
    정책으로 각 사용자·그룹·역할에 읽기·쓰기 액션을 할당한다. 이 IAM 기반 정책 접근은 데이터 처리
    잡 같은 애플리케이션 사용자에 적용된다. 그들은 당신 같은 사람 사용자와 같은 클라우드 자원에서
    작업할 수 있지만 그 상호작용은 자동화돼 있다. 예컨대 그들의 잡은 하루 중 특정 시각에 돌도록
    스케줄될 수 있다. 그러므로 그들은 로그인하지 않지만 어떻게든 클라우드 자원에 접근하도록 인가돼야
    한다.**
  - 그 흐름 네 단계 — **① 애플리케이션 사용자가 클라우드 서비스와 상호작용하는 요청을 발행한다.
    ② 서비스는 객체를 직접 반환하지 않는다. 대신 IAM 서비스에 연결해 사용자가 요청을 이행하는 데
    요구되는 모든 권한을 갖는지 검증한다. ③ IAM이 권한 범위 목록으로 서비스에 응답한다. ④ 서비스가
    사용자에게 응답을 반환한다. 사용자가 요구되는 모든 권한을 가지면 응답이 요청을 만족시킨다.
    그렇지 않으면 서비스가 오류를 반환한다.**
  - **둘째 구현은 인증서를 쓰며 인증서 기반 인증(certificate-based authentication)으로도 알려져
    있다. 워크플로는 앞의 것과 비슷하지만 IAM 서비스 대신 인증 기관(CA) 구성 요소가 있다. 이 기관은
    워크플로가 진행하도록 인가하기 전에 연결 프로세스에 쓰인 인증서를 검증한다.**
- **무노동의 인상**(workless impression) — **-less 접미사가 노력의 부재를 가리킬 수 있지만
  Secretless Connector 패턴은 약간의 작업을 요구한다. 자격 증명이 관련되지 않더라도 자격 증명 없는
  접근을 활용하도록 엔티티를 설정하는 작업이 여전히 있다. 예컨대 AWS에서는 엔티티가 Security Token
  Service(STS)가 반환하는 임시 자격 증명을 써서 다른 서비스와 상호작용하게 하는 assume role 권한
  설정이 필요하다** (7장, p.230).[^konieczny2025]
- **회전**(rotation) — **이 점은 본질적으로 인증서 기반 인증에 유효하다. 접근 키를 정기적으로
  회전하는 것은 유출 위험을 줄이는 보안 모범 사례로 흔히 여겨진다. 그러나 인증서·로그인·비밀번호에
  대해 그것은 추가 관리 오버헤드를 더한다** (7장, p.230).[^konieczny2025]
  - 무중단 회전의 절차 — **소비자에 영향을 주지 않고 회전하려면 먼저 새 자격 증명을 생성해 소비자와
    공유해야 한다. 그동안 당신 쪽에서는 옛 자격 증명과 새 자격 증명을 둘 다 지원해야, 동시에 이전하지
    못할 수 있는 소비자가 여전히 당신 데이터 저장을 쓸 수 있다. 소비자가 새 자격 증명을 쓰고 있음을
    확인하고 나서야 옛 것을 버릴 수 있다** (7장, p.230).[^konieczny2025]
- 인증서 기반 연결의 실물 — Spark에서 PostgreSQL로 붙을 때 **연결 속성이 비밀번호를 전혀 요구하지
  않고 서버와 공유된 인증서에 기댄다. 연결 파라미터는 서버 호스트 이름이 서버 인증서에 저장된
  이름과 일치하도록 보장하는 verify-full SSL 모드를 쓴다** (7장, p.230).[^konieczny2025]
- 클라우드 판의 실물은 GCP의 서비스 계정이다 — 서비스 계정을 만들고 **그것을 Dataflow 잡이 처리해야
  할 GCS 버킷과 잡 자체에 연결한다. 이렇게 해서 `visits_aggregator` 잡이 아이덴티티를 얻고,
  결과적으로 visits 버킷을 읽는 데 런타임에 제공되는 어떤 자격 증명도 필요하지 않게 된다** (7장,
  p.231).[^konieczny2025]
