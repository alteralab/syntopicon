하나의 질문: **데이터 소유권을 도메인마다 쪼개 놓고 나면 생기는 중복·비용·비호환을 무엇이
되받는가.**

[데이터 메시](../concepts/data-mesh.md)의 넷 중 셋째 원칙이고, 원전이 4장 한 장을 통째로
할당한 자리다. 이 페이지는 그 4장(47p–66p)이 본체다 — 1장 개관 분량은
[데이터 메시](../concepts/data-mesh.md)에 남아 있다.

## 이 원칙이 존재하는 이유

- 앞선 두 원칙이 남기는 청구서를 저자가 먼저 적는다 — **지금까지 나는 데이터 메시를 향한 두
  근본 전환을 제시했다. 업무 도메인을 중심으로 방향 잡힌 분산 데이터 아키텍처와 소유 모델,
  그리고 사용 가능하고 가치 있는 제품으로 공유되는 데이터다. 시간이 지나면 이 겉보기에 단순하고
  꽤 직관적인 두 전환은 바람직하지 않은 결과를 낳을 수 있다 — 각 도메인에서의 노력 중복, 운영
  비용 증가, 그리고 도메인 간의 대규모 비일관성과 비호환일 가능성이 크다** (4장,
  p.47).[^dehghani2022]
- 이 원칙은 그 결과에 대한 답으로 규정된다 — **이 질문들에 답하는 것이 데이터 메시의 셋째
  원칙, 플랫폼으로서의 셀프서브 데이터 인프라(self-serve data infrastructure as a platform)가
  존재하는 이유다. 데이터·분석 플랫폼이 부족해서가 아니라, 그것들이 새로운 제너럴리스트
  기술자(generalist technologists) 인구를 위해 분석 데이터의 공유·접근·사용을 탈중앙적 방식으로
  확장(scale out)할 수 있도록 바꿔야 하기 때문이다. 이것이 데이터 메시 플랫폼의 핵심 차별점이다**
  (4장, pp.47–48).[^dehghani2022]
  - **원칙 명칭이 이 장에서 흔들린다.** 4장 표제는 "Principle of the Self-Serve Data
    Platform"인데, 본문 첫 규정은 옛 이름 **self-serve data infrastructure as a platform**을
    그대로 쓴다 (4장, p.47).[^dehghani2022] [데이터 메시](../concepts/data-mesh.md) 페이지가
    적은 "명칭 판본 차이"는 제3자의 인용 시점 문제만이 아니라 원전 자체가 두 이름을 병용한
    것이다 — 모순이 아니라 같은 원칙의 두 표기다.
- 저자가 그 자리에서 옮겨 적는 것은 지도자와 실무자의 질문 목록이다 — 모든 도메인이 제 데이터를
  짓고 소유해야 한다면 **도메인 데이터 프로덕트 운영 비용을 어떻게 관리하는가**, 이미 구하기 힘든
  **데이터 엔지니어를 도메인마다 어떻게 채용하는가**, 이것은 **각 팀의 과잉 엔지니어링이고 중복
  노력 아닌가**, 사용성 속성을 다 제공하려면 **어떤 기술을 사는가**, **분산된 방식으로 거버넌스를
  어떻게 강제하는가**, **복사된 데이터는 어떻게 관리하는가** (4장, p.47).[^dehghani2022] 도메인
  엔지니어링 팀 쪽 질문은 하나다 — **애플리케이션을 짓는 것을 넘어 데이터까지 공유하도록 우리 팀
  책임을 어떻게 확장할 수 있는가** (4장, p.47).[^dehghani2022]
- 플랫폼이 하는 조작은 추출이다 — 각 도메인에서 **도메인 불가지(domain-agnostic) 능력을 끄집어
  내어 플랫폼으로서의 셀프서브 인프라로 옮기는 것**이고, 그 플랫폼은 **전담 플랫폼 팀(dedicated
  platform team)이 짓고 유지한다** (4장, p.48, 그림 4-1).[^dehghani2022]

## "플랫폼"이라는 낱말이 여기서 뜻하는 것

- 저자가 단수형에 미리 못을 박는다 (4장, p.49):[^dehghani2022]

> In this chapter, I use the phrase *data mesh platform* as shorthand for a set of underlying
> data infrastructure capabilities. A singular form of the term *platform* does not mean a
> single solution or a single vendor with tightly integrated features. It's merely a
> placeholder for a set of technologies that one can use to achieve the objectives mentioned
> in "Data Mesh Platform Thinking", a set of technologies that are independent and yet play
> nicely together.

- 기존 플랫폼 능력의 표본도 열거해 둔다 — **레이크·웨어하우스·레이크하우스 형태의 분석 데이터
  저장, 배치와 스트리밍 양식으로 데이터를 처리하는 데이터 처리 프레임워크와 연산 엔진, 계산적
  데이터 플로 프로그래밍이나 대수적 SQL 유사 문장이라는 두 양식에 기반한 데이터 질의 언어,
  조직 전체 데이터의 거버넌스와 발견을 가능하게 하는 데이터 카탈로그 해법, 복잡한 데이터
  파이프라인 태스크나 ML 모델 배포 워크플로를 오케스트레이션하는 파이프라인 워크플로 관리**
  (4장, p.49).[^dehghani2022]
- 그 능력들이 폐기되는 것은 아니다 — **이 능력 중 다수는 데이터 메시 구현을 가능하게 하는 데
  여전히 필요하다. 그러나 데이터 메시 플랫폼의 접근과 목표에는 전환이 있다** (4장,
  p.49).[^dehghani2022] 바뀌는 것은 능력 목록이 아니라 **사용자와 관리 단위**다.
- 낱말 자체의 어원적 정의를 저자가 인용으로 세운다 (4장, p.54):[^dehghani2022]

> Platform: raised level surface on which people or things can stand.
>
> —Oxford Languages

## 기존 데이터 플랫폼과 갈리는 여섯 특성

- 저자가 그림 하나로 대비시킨 여섯 축이다. 앞이 데이터 메시 플랫폼, 뒤가 기존 플랫폼이다
  (4장, p.50, 그림 4-2):[^dehghani2022]

| # | 데이터 메시 플랫폼 | 기존 플랫폼 |
|---|---|---|
| ① | 자율적 도메인 지향 팀을 서빙한다 | 모든 도메인을 위해 중앙 데이터 팀 하나를 서빙한다 |
| ② | 자율적이고 상호운용 가능한 데이터 프로덕트를 관리한다(코드·데이터·정책을 한 단위로) | 데이터·파이프라인·코드·정책을 따로 관리한다 |
| ③ | 운영계와 분석계 능력이 통합된 플랫폼 | 운영계용·분석계용 두 독립 스택을 점대점으로 통합 |
| ④ | 제너럴리스트 다수를 위해 설계 | 전문가 다수를 위해 설계 |
| ⑤ | 탈중앙 기술을 선호 | 중앙집중 기술을 선호 |
| ⑥ | 도메인 불가지(domain agnostic) | 도메인 인지(domain aware) |

- 이 대비가 기술 교체를 요구하는 것은 아니라고 저자가 단서를 단다 — **데이터 메시 플랫폼은 기존
  기술을 활용하면서도 이 고유한 특성을 제공할 수 있다** (4장, p.49).[^dehghani2022]

## ① 자율적 도메인 지향 팀을 서빙한다

- 플랫폼의 주된 책임 — **기존 또는 새 도메인 엔지니어링 팀이 데이터 프로덕트를 종단 간으로
  짓고·공유하고·사용하는 새로 심긴 책임을 수행할 수 있게 하는 것이다. 운영 시스템과 다른
  원천에서 데이터를 포착하고, 최종 데이터 사용자에게 제품으로서 데이터를 변환하고 공유하는
  일이다** (4장, p.51).[^dehghani2022]
- 자율의 정의가 엄격하다 — **플랫폼은 팀이 이 일을 중앙집중 데이터 팀이나 중개자에 대한 어떤
  의존도 없이 자율적 방식으로 수행할 수 있게 해야 한다** (4장, p.51).[^dehghani2022]
- 기존 벤더 기술이 왜 걸림돌인지를 세 가지 기술적 귀결로 적는다. 이것들은 **중앙집중 데이터
  팀이 모든 도메인을 위해 데이터를 포착·공유한다는 가정**에서 나온다 (4장,
  p.51):[^dehghani2022]
  - **비용이 격리된 도메인 자원별이 아니라 모놀리식으로 추정·관리된다.**
  - **보안·프라이버시 관리가 물리 자원이 같은 계정 아래 공유된다고 가정하고, 데이터 프로덕트별
    격리된 보안 맥락으로 확장되지 않는다.**
  - **중앙 파이프라인(DAG) 오케스트레이션이 모든 데이터 파이프라인의 중앙 관리를 가정한다 —
    중앙 파이프라인 설정 저장소와 중앙 모니터링 포털을 두고서다. 이는 각각 작고 하나의 데이터
    프로덕트 구현에 할당되는 독립 파이프라인들과 충돌한다.**
  - 셋째 항이 [배치 워크플로와 DAG](../concepts/batch-workflows-and-dags.md)의 표준 배치와
    정면으로 갈리는 자리다 — 오케스트레이터를 부정하는 것이 아니라 **오케스트레이션의 단위**를
    중앙 저장소에서 데이터 프로덕트로 옮긴다.

## ② 데이터 프로덕트를 한 단위로 관리한다

- 플랫폼이 다뤄야 하는 새 구성물 — **데이터 메시는 접근의 중심에 새 구성물, 도메인 지향 데이터
  프로덕트(domain-oriented data product)를 놓는다. 이는 자율적으로 가치를 전달하는 새 아키텍처
  구성물이다. 최종 데이터 사용자에게 발견 가능하고 사용 가능하며 신뢰할 만하고 안전한 데이터를
  제공하는 데 필요한 모든 행위와 데이터를 부호화한다** (4장, p.51).[^dehghani2022]
- 그래서 플랫폼에 요구되는 것 — **데이터 메시 플랫폼은 이 새 구성물과 함께 작동해야 하고, 그
  자율적 수명 주기와 그 모든 구성 요소를 관리하는 것을 지원해야 한다** (4장,
  p.51).[^dehghani2022]
- 기존 플랫폼과 갈리는 지점 — **2022년 저술 시점의 기존 플랫폼은 행위(예: 데이터 처리 파이프라인), 데이터와
  그 메타데이터, 그리고 데이터를 규율하는 정책을 독립적인 조각으로 관리한다** (4장,
  p.51).[^dehghani2022]
- 다만 기존 기술 위에 얹는 길을 봉쇄하지는 않는다 — **기존 기술 위에 새 데이터 프로덕트 관리
  추상을 만드는 것은 가능하다. 다만 그리 우아하지는 않다** (4장, p.51).[^dehghani2022]

## ③ 운영계와 분석계가 끊기지 않는 플랫폼

- 요구의 출처는 첫째 원칙이다 — **도메인 소유권 원칙은 자율적 도메인 팀이 데이터를 종단 간으로
  관리할 수 있게 하는 플랫폼을 요구한다. 이는 운영 플레인과 분석 플레인 사이의 간극을 조직적으로
  닫는다** (4장, p.52).[^dehghani2022]
- 그래서 채택의 장벽이 되는 것은 스택의 분열이다 — **플랫폼이 기존 도메인 기술 팀에 성공적으로
  채택되려면, 채택의 장벽인 운영 스택과 분석 스택의 분열(schism)을 제거해야 한다** (4장,
  p.52).[^dehghani2022]
- 저자가 드는 실물 — **2022년 저술 시점에 Spark 같은 데이터 처리 파이프라인을 돌리는 연산 패브릭(computation
  fabric)은 쿠버네티스 같은 운영 서비스를 돌리는 연산 패브릭과 다른 클러스터링 아키텍처에서
  관리되고 흔히 단절되어 있다. 자기 마이크로서비스와 밀접히 협력하는 데이터 프로덕트, 곧 원천
  정렬 데이터 프로덕트를 만들려면 연산 패브릭들의 더 긴밀한 통합이 필요하다** (4장,
  p.52).[^dehghani2022] 그 실현도를 저자가 실측으로 낮춘다 — **두 연산 엔진을 같은 연산 패브릭
  위에서 돌리는 조직은 내가 함께 일해 본 중에 아주 드물었다** (4장, p.52).[^dehghani2022]
- 통합이 곧 동일화는 아니다 — **두 플레인의 본질적 차이 때문에, 운영 시스템용 기술과 분석
  시스템용 기술이 서로 달라야 하는 플랫폼 영역이 많다** (4장, p.52).[^dehghani2022] 저자가
  드는 예가 추적(tracing)이다:
  - **운영 시스템은 분산 애플리케이션에 걸친 (API) 호출 추적에 트리 형태 구조의
    OpenTelemetry 표준을 쓴다. 반면 데이터 처리 워크로드는 분산 데이터 파이프라인에 걸친
    데이터 계보를 추적하는 데 OpenLineage를 쓴다** (4장, p.52).[^dehghani2022]
  - 처방은 통일이 아니라 접합이다 — **두 플레인 사이의 간극을 신경 쓸 만큼 차이가 충분하다.
    그러나 이 두 표준이 잘 통합되는 것이 중요하다. 결국 많은 경우 한 조각 데이터의 여정은
    사용자 행동에 응답하는 애플리케이션 호출에서 시작하기 때문이다** (4장,
    p.52).[^dehghani2022]

## ④ 제너럴리스트 다수를 위해 설계한다

- 진단 — **2022년 저술 시점 데이터 플랫폼 채택의 또 다른 장벽은 각 기술 벤더가 가정하는 독점적 전문화의
  수준이다. 전문 용어와 벤더 특유의 지식 말이다. 이것이 데이터 엔지니어 같은 희소한 전문 역할의
  창출로 이어졌다** (4장, p.52).[^dehghani2022]
- 그 확장 불가능한 전문화의 원인 셋을 저자가 자기 의견으로 명시한다 — **(사실상의) 표준과 관례의
  부재, 기술 상호운용성에 대한 유인의 부재, 제품을 아주 단순하게 쓸 수 있게 만들 유인의 부재**
  (4장, p.52).[^dehghani2022]
  - 그 뿌리를 벤더 유인으로 지목한다 — **나는 이것이 단일 벤더가 처음부터 끝까지의 기능을
    제공해 당신의 데이터를 자기 플랫폼에 저장하게 하고, 데이터와 그 처리를 자기 통제 아래
    붙들어 두려 부가 서비스를 붙이는 거대 모놀리식 플랫폼 사고방식의 잔재라고 믿는다** (4장,
    pp.52–53).[^dehghani2022] #hypothesis — 저자가 "내 의견"·"믿는다"로 표지한 인과 진단이다.
- 처방 — **데이터 메시 플랫폼은 이 패턴을 깨고, 서로 다른 기술 사이의 상호운용성을 촉진하고 한
  전문가가 데이터에서 가치를 내기 위해 배워야 하는 독점 언어와 경험의 수를 줄이는 열린 관례
  집합의 정의에서 시작해야 한다** (4장, p.53).[^dehghani2022]
- 플랫폼의 자리에 대한 강한 규범 — **데이터 메시 플랫폼은 제너럴리스트 기술자에게 적합한 상태를
  유지해야 한다. 그것들은 배경으로 물러나야 하고, 제너럴리스트가 쓰는 네이티브 도구와 프로그래밍
  언어에 자연스럽게 들어맞아야 하며, 그들의 앞길에서 비켜서야 한다** (4장,
  p.53).[^dehghani2022]
- 단서가 붙는다 — **말할 필요도 없이, 이것은 지속 가능한 해법을 낳는 소프트웨어 엔지니어링
  실천을 타협하지 않고 달성되어야 한다. 예컨대 많은 로우코드·노코드 플랫폼은 데이터와 함께
  작동하겠다고 약속하지만 테스팅·버저닝·모듈성 등의 기법에서 타협한다. 시간이 지나면 그것들은
  유지 불가능해진다** (4장, p.53).[^dehghani2022]
- **제너럴리스트 기술자**가 누구인지도 정의한다 — **T자형(T-shaped) 또는 페인트 드립(Paint
  Drip) 사람이라 자주 불리는 기술자 인구를 가리킨다. 소프트웨어 엔지니어링의 넓은 스펙트럼을
  경험했고, 서로 다른 시점에 한두 영역에 집중해 깊은 지식을 얻는 개발자들이다. 요점은 다른
  많은 것을 탐색하면서도 한두 영역에서 깊이 들어가는 것이 가능하다는 것이다** (4장,
  p.53).[^dehghani2022]
  - 대비되는 쪽 — **한 특정 영역에만 전문성을 가진 전문가와 대조된다. 전문화에 집중하기 때문에
    다양한 스펙트럼을 탐색할 수 없다** (4장, p.53).[^dehghani2022]
  - 미래 서술은 추정이다 — **내 생각에 미래의 제너럴리스트는 데이터와 함께 작업하고 데이터
    프로덕트를 통해 데이터를 만들고 공유하거나, 전문 데이터 과학자가 이미 개발한 모델을 피처
    엔지니어링과 ML 훈련에 쓸 수 있게 될 것이다. 본질적으로 그들은 서비스로서의 AI를 쓴다**
    (4장, p.53).[^dehghani2022] #speculation — 저자가 "내 생각에"로 표지한 미래 예측이다.
  - 저술 시점 진단 — **2022년 저술 시점에는 데이터 작업의 다수가 전문화를 요구하고 오랜 기간에 걸친 상당한
    노력을 요구한다. 이것이 제너럴리스트 기술자의 진입을 억제했고 데이터 전문가의 희소성으로
    이어졌다** (4장, p.53).[^dehghani2022]

## ⑤ 탈중앙 기술을 선호한다 — 그리고 그 한계

- 기존 플랫폼의 공통 특성 — **통제의 중앙집중화다. 예로는 중앙집중 파이프라인 오케스트레이션
  도구, 중앙집중 카탈로그, 중앙집중 웨어하우스 스키마, 컴퓨트·스토리지 자원의 중앙집중 할당
  등이 있다** (4장, p.53).[^dehghani2022]
- 탈중앙을 고르는 이유는 조직 속도다 — **도메인 소유권을 통한 탈중앙화에 데이터 메시가 집중하는
  이유는 궁극적으로 변화 속도를 늦추는 조직적 동기화와 병목을 피하기 위해서다** (4장,
  pp.53–54).[^dehghani2022]
- 기술과 조직의 인과가 한 방향이 아니라는 관찰이 붙는다 — **표면적으로 이것은 조직적 관심사지만,
  기저의 기술과 아키텍처가 조직의 소통과 설계에 직접 영향을 준다. 모놀리식이거나 중앙집중적인
  기술 해법은 중앙집중적 통제 지점과 팀으로 이어진다** (4장, p.54).[^dehghani2022] 콘웨이 법칙의
  역방향 진술이다.
- 그래서 플랫폼 설계자의 작업은 감사다 — **데이터 메시 플랫폼은 데이터 공유·통제·거버넌스에서
  조직의 탈중앙화를 설계의 심장에 두어야 한다. 발맞춤 팀 동기화, 통제의 중앙집중화, 자율 팀
  사이의 강한 결합으로 이어질 수 있는 설계의 모든 중앙집중적 측면을 점검한다** (4장,
  p.54).[^dehghani2022]
- **탈중앙이 전부가 아니라는 단서가 같은 절에 붙는다** — **그렇게 말했지만, 각 도메인 팀이
  데이터를 공유하고 사용할 때 수행하는 불필요한 작업을 줄이기 위해 중앙에서 관리되어야 하는
  인프라 측면이 많다. 예컨대 데이터 처리 컴퓨트 클러스터를 세우는 일이다. 여기가 효과적인
  셀프서브 플랫폼이 빛나는 지점이다 — 기저 자원을 중앙에서 관리하면서도 독립 팀이 다른 팀에
  대한 강한 의존 없이 자기 결과를 종단 간으로 달성하게 한다** (4장, p.54).[^dehghani2022]
  이 원칙에서 중앙집중이 허용되는 유일한 축이 **기저 자원 관리**임을 명시한 자리다.

## ⑥ 도메인 불가지

- 책임 분할선 — **데이터 메시는 도메인 팀과 플랫폼 팀 사이에 명확한 책임 구획을 만든다. 도메인
  팀은 이상적으로 데이터 주도인 업무 지향 제품·서비스·데이터 프로덕트를 만드는 데 집중하고,
  플랫폼 팀은 도메인을 위한 기술적 조력자(technical enablers)에 집중한다** (4장,
  p.54).[^dehghani2022]
- 무엇과 다른가 — **이는 데이터 팀이 흔히 분석 용법을 위한 도메인 특유 데이터의 통합과 기저
  기술 인프라 양쪽을 책임지는 기존의 책임 구획과 다르다** (4장, p.54).[^dehghani2022]
- 이 구획이 능력 설계에 거는 조건 — **플랫폼은 도메인 불가지 능력을 제공하는 것과, 조직 전반에
  걸친 도메인 특유의 데이터 모델링·처리·공유를 가능하게 하는 것 사이에서 균형을 잡아야 한다.
  이것은 데이터 개발자에 대한 깊은 이해와 플랫폼에 대한 제품 사고(product thinking)의 적용을
  요구한다** (4장, p.54).[^dehghani2022]

## 플랫폼 사고에서 끌어온 다섯 목표

- 저자는 정의를 셋에서 빌린다 (4장, pp.54–55):[^dehghani2022]
  - Evan Bottcher — **디지털 플랫폼은 매력적인 내부 제품으로 배치된 셀프서비스 API·도구·서비스·
    지식·지원의 기반이다. 자율적 전달 팀은 이 플랫폼을 활용해 더 빠른 속도로, 더 적은 조정으로
    제품 기능을 전달할 수 있다.**
  - Matthew Skelton·Manuel Pais, *Team Topologies* — **플랫폼 팀의 목적은 스트림 정렬 팀이
    상당한 자율성을 갖고 일을 전달할 수 있게 하는 것이다. 스트림 정렬 팀은 자기 애플리케이션을
    짓고·돌리고·고치는 완전한 소유권을 유지한다. 플랫폼 팀은 이 기저 서비스를 개발하는 데
    스트림 정렬 팀에게 요구될 인지 부하를 줄이는 내부 서비스를 제공한다. 플랫폼은 다른 방식으로는
    복잡한 기술을 단순화하고 그것을 쓰는 팀의 인지 부하를 줄인다.**
  - Geoffrey G. Parker 외, *Platform Revolution* — **플랫폼은 한 번에 하나의 상호작용씩
    설계된다. 따라서 모든 플랫폼의 설계는 그것이 생산자와 소비자 사이에 가능하게 하는 핵심
    상호작용의 설계에서 시작해야 한다. 핵심 상호작용은 플랫폼에서 일어나는 가장 중요한 단일
    형태의 활동 — 애초에 대다수 사용자를 플랫폼으로 끌어들이는 가치의 교환 — 이다.**
- 여기서 뽑아 데이터 메시에 적용하는 목표는 다섯이다 (4장, pp.55–56):[^dehghani2022]

| 목표 | 원어 |
|---|---|
| 자율적 팀이 데이터에서 가치를 얻게 한다 | Enable autonomous teams to get value from data |
| 자율적이고 상호운용 가능한 데이터 프로덕트로 가치를 교환한다 | Exchange value with autonomous and interoperable data products |
| 인지 부하를 낮춰 가치 교환을 가속한다 | Accelerate exchange of value by lowering the cognitive load |
| 데이터 공유를 확장한다 | Scale out data sharing |
| 내장된 혁신 문화를 지원한다 | Support a culture of embedded innovation |

## 자율적 팀이 데이터에서 가치를 얻게 한다

- 설계의 출발점은 능력 목록이 아니라 사람의 여정이다 — **플랫폼을 설계할 때 플랫폼 사용자의
  역할과 데이터 프로덕트를 공유·사용하는 그들의 여정(journey)을 고려하는 것이 도움이 된다.
  그러면 플랫폼은 각 여정에 마찰 없는 경험을 만드는 데 집중할 수 있다** (4장,
  p.57).[^dehghani2022]
- 저자가 드는 두 페르소나 — **데이터 프로덕트 개발자(data product developers)와 데이터 프로덕트
  사용자(data product users)** (4장, p.57).[^dehghani2022] 데이터 프로덕트 소유자는 여정이 똑같이
  중요하지만 간결함을 위해 예에서 뺐다고 밝힌다 (4장, p.57).[^dehghani2022]
- **개발자 쪽 여정** — **데이터 프로덕트를 개발하고, 테스트·배포·모니터링·갱신하고, 그 무결성과
  보안을 유지하는 것 — 지속적 전달(continuous delivery)을 염두에 두고서다. 요컨대 개발자는 데이터
  프로덕트의 수명 주기를 관리하며, 그 코드·데이터·정책을 한 단위로 다룬다** (4장,
  p.57).[^dehghani2022]
  - 왜 플랫폼이 필요한가 — **데이터 프로덕트 수명 주기 관리를 위한 기저 인프라의 프로비저닝과
    관리는 2022년 저술 시점 도구에 대한 전문 지식을 요구하고 각 도메인에서 복제하기 어렵다** (4장,
    p.57).[^dehghani2022]
  - 그래서 요구되는 것 — **플랫폼은 데이터 프로덕트 개발자가 기저 인프라 자원 프로비저닝을
    걱정하지 않고 데이터 프로덕트를 짓고·테스트하고·배포하고·보안하고·유지할 수 있게 하는 모든
    필요한 능력을 구현해야 한다** (4장, p.57).[^dehghani2022]
  - 개발자가 남기고 다뤄야 할 것은 도메인 특유의 다섯뿐이다 — **데이터를 생성·유지하는 도메인
    특유 로직인 변환 코드, 도메인의 데이터 무결성을 검증·유지하는 빌드 시점 테스트, 데이터
    프로덕트가 품질 보증을 충족하는지 지속 모니터링하는 런타임 테스트, 스키마·문서 같은 데이터
    프로덕트의 메타데이터 개발, 그리고 필요한 인프라 자원의 선언** (4장, p.57).[^dehghani2022]
  - 나머지는 플랫폼 몫이다 — **셀프서브 접근은 데이터 프로덕트 개발자가 자기 인프라 필요를
    선언하고 나머지는 플랫폼이 처리하게 하는 플랫폼 API 집합을 노출한다** (4장,
    p.58).[^dehghani2022]
- **사용자 쪽 여정** — **통찰을 만들기 위한 분석이든 기계 학습 모델 개발이든, 데이터를 발견하는
  데서 시작한다. 데이터가 발견되면 접근 권한을 얻고, 이해하고, 더 깊이 파고들어야 한다. 적합한
  것으로 판명되면 계속 쓴다. 데이터 사용은 일회성 접근에 그치지 않는다 — 소비자는 자기 기계 학습
  모델이나 통찰을 최신으로 유지하기 위해 새 데이터를 계속 받고 처리한다** (4장,
  p.58).[^dehghani2022]
- 자율의 구체적 뜻이 여기서 접근 승인으로 내려온다 — **플랫폼은 수작업 개입의 필요를 줄여야
  한다. 예컨대 데이터를 만든 팀이나 거버넌스 팀을 쫓아다니며 정당화하고 데이터 접근을 얻어야 할
  필요를 없애야 한다. 플랫폼은 접근 요청을 촉진하는 프로세스를 자동화하고 소비자에 대한 자동화된
  평가에 근거해 접근을 부여한다** (4장, p.58).[^dehghani2022] 이 문장이
  [연합 컴퓨테이셔널 거버넌스 원칙](../concepts/federated-computational-governance-principle.md)과
  맞물리는 지점이다 — 정책이 코드가 되지 않으면 이 자동 승인이 성립하지 않는다.

## 가치 교환 — 다면 플랫폼과 조합 가능성

- 저자가 빌려 오는 렌즈 — **데이터 메시 플랫폼을 보는 흥미로운 렌즈 하나는 그것을 다면
  플랫폼(multisided platform)으로 보는 것이다. 주로 둘 이상의 구별되는 당사자 사이의 직접
  상호작용을 가능하게 함으로써 가치를 창출하는 플랫폼이다. 데이터 메시의 경우 그 당사자는 데이터
  프로덕트 개발자·데이터 프로덕트 소유자·데이터 프로덕트 사용자다** (4장, p.58).[^dehghani2022]
- 교환의 성패 기준이 명시된다 — **성공이 가치 교환, 곧 데이터 프로덕트로 직접 측정되는 플랫폼**
  (4장, p.58).[^dehghani2022] 교환이 일어나는 자리는 둘이다 — **메시 위에서 데이터 프로덕트
  사이, 또는 메시의 가장자리에서 ML 모델·리포트·대시보드 같은 최종 제품과 데이터 프로덕트
  사이** (4장, p.58).[^dehghani2022]
- 그 귀결로 붙는 이름 — **메시는 본질적으로 조직의 데이터 마켓플레이스(organizational data
  marketplace)가 된다** (4장, p.58).[^dehghani2022] 저자는 이것이 **조직 안 문화 변화의
  촉매**가 될 수 있다고 적는다 (4장, p.58).[^dehghani2022] #hypothesis
- **조합으로 고차 가치를 만든다** — 가치 교환은 단일 데이터 프로덕트 사용을 넘어 **여러 데이터
  프로덕트의 조합(composition)으로 확장된다** (4장, p.59).[^dehghani2022] 저자의 예는 리스너
  통찰이 **음악 청취 중 행동·팔로우하는 아티스트·인구통계·소셜 미디어 상호작용·친구 네트워크의
  영향·주변 문화 이벤트를 교차 상관해** 만들어지는 것이고, 그것들은 **상관되고 피처 행렬로
  조합되어야 하는 여러 데이터 프로덕트**다 (4장, p.59).[^dehghani2022]
- 플랫폼이 그 조합을 위해 제공하는 것 — **플랫폼은 데이터 프로덕트 연결(data product linking)을
  가능하게 한다. 한 데이터 프로덕트가 다른 데이터 프로덕트의 데이터와 데이터 타입(스키마)을 쓰는
  경우다. 이것이 매끄럽게 가능하려면 플랫폼이 데이터 프로덕트를 식별하고·주소 지정하고·연결하고·
  읽는 표준화되고 단순한 방식을 제공해야 한다** (4장, p.59).[^dehghani2022]
- 그 결과에 저자가 붙이는 표현 — **이런 단순한 플랫폼 기능이 동질적 인터페이스를 갖는 이질적
  도메인의 메시(a mesh of heterogeneous domains with homogeneous interfaces)를 만든다** (4장,
  p.59).[^dehghani2022] 이 한 줄이 셋째 원칙의 아키텍처적 목표를 압축한다.

## 인지 부하를 낮춘다 — 선언과 자동화

- 개념의 출처를 저자가 밝힌다 — **인지 부하(cognitive load)는 인지과학 분야에서 문제를 풀거나
  학습하기 위해 임시 정보를 붙들고 있는 데 필요한 작업 기억의 양으로 처음 도입되었다** (4장,
  p.59, 각주 2는 John Sweller, "Cognitive Load During Problem Solving: Effects on Learning",
  *Cognitive Science* 12(2), 1988).[^dehghani2022]
- 플랫폼이 그것을 낮추는 방법 — **개발자에게 제시되는 세부와 정보의 양을 감춤으로써, 곧 복잡성을
  추상함으로써(abstracting complexity)다** (4장, p.59).[^dehghani2022]
- 개발자 관점의 규범 — **데이터 프로덕트 개발자로서 나는 내 도메인 불가지 소망이 무엇인지를,
  그것을 정확히 어떻게 구현할지 서술하지 않고 표현할 수 있어야 한다. 예컨대 개발자로서 나는 내
  데이터의 구조·보존 기간·잠재적 크기·기밀성 등급을 선언할 수 있어야 하고, 데이터 구조를 만들고
  스토리지를 프로비저닝하고 자동 암호화를 수행하고 암호화 키를 관리하고 키를 자동 회전하는 것은
  플랫폼에 맡길 수 있어야 한다** (4장, p.59).[^dehghani2022]
- 방법 ① **선언적 모델링을 통한 복잡성 추상** — **지난 몇 년간 컨테이너 오케스트레이터(예:
  쿠버네티스)나 인프라 프로비저닝 도구(예: Terraform) 같은 운영 플랫폼이 목표 상태의 선언적
  모델링(declarative modeling of the target state)을 통해 복잡성을 추상하는 새 모델을 확립했다.
  이는 목표 상태를 어떻게 지을지 명령하는 명령적(imperative) 지시 같은 다른 방법과 대조된다.
  본질적으로 전자는 무엇에, 후자는 어떻게에 집중한다** (4장, p.60).[^dehghani2022]
  - **한계도 같은 자리에 적힌다** — **많은 시나리오에서 선언적 모델링은 아주 빠르게 한계에
    부딪힌다. 예컨대 선언으로 데이터 변환 로직을 정의하는 것은 로직이 복잡해지자마자 수확 체감에
    도달한다** (4장, p.60).[^dehghani2022]
  - 그래서 적용 범위가 좁혀진다 — **그러나 프로비저닝된 인프라처럼 자기 상태로 서술될 수 있는
    시스템은 선언적 양식에 잘 들어맞는다. 데이터 프로덕트의 수명 주기를 관리하는 인프라의 목표
    상태는 선언적으로 정의될 수 있다** (4장, p.60).[^dehghani2022]
- 방법 ② **자동화를 통한 복잡성 추상** — **데이터 프로덕트 개발자 여정에서 사람의 개입과 수작업
  단계를 제거하는 것은 복잡성, 특히 프로세스 전반의 수작업 오류에서 생기는 복잡성을 줄이는 또
  다른 방법이다. 기저 데이터 인프라의 프로비저닝 자체가 코드형 인프라(infrastructure as code)
  기법으로 자동화될 수 있다** (4장, p.60, 각주 3은 Kief Morris, *Infrastructure as Code*,
  O'Reilly 2021).[^dehghani2022]
  - 저자가 지목하는 최대 기회 — **2022년 저술 시점에 데이터 인증 또는 검증 승인 프로세스는 흔히 수작업으로
    이뤄진다. 이는 엄청난 자동화 기회의 영역이다. 플랫폼은 데이터 무결성 검증을 자동화하고,
    데이터의 성질을 테스트하는 데 통계적 방법을 적용하고, 예기치 못한 이상치를 발견하는 데
    기계 학습까지 쓸 수 있다** (4장, p.60).[^dehghani2022] 수작업 인증을 전제하는
    [데이터 품질 관리](../concepts/data-quality-management.md)의 처방과 갈리는 자리다.

## 데이터 공유를 확장한다 — 유닉스 철학의 부재

- 진단은 표준의 부재다 — **기존 빅데이터 기술 지형에서 내가 관찰한 문제 하나는 규모 있는 데이터
  공유로 이어지는 상호운용 가능한 해법을 위한 표준의 부재다. 예컨대 데이터 접근 시 인증·인가의
  통일된 모델의 부재, 데이터와 함께 프라이버시 권리를 표현하고 전송하는 표준의 부재, 데이터의
  시간성(temporality) 측면을 제시하는 표준의 부재다** (4장, p.60).[^dehghani2022]
- 그 결과 — **이 빠진 표준들이 조직 신뢰 경계 너머로 사용 가능한 데이터의 네트워크를 확장하는
  것을 억제한다** (4장, pp.60–61).[^dehghani2022]
- 저자가 가장 중요하다고 적는 결핍 — **무엇보다 데이터 기술 지형에는 유닉스 철학(Unix
  philosophy)이 빠져 있다** (4장, p.61).[^dehghani2022] 그 철학을 직인용한다 (4장,
  p.61):[^dehghani2022]

> This is the Unix philosophy: Write programs that do one thing and do it well. Write
> programs to work together…
>
> —Doug McIlroy

- 운영계와 데이터계의 갈림에 대한 저자의 해석 — **우리는 운영 세계에서 아주 특별한 사람들
  (McIlroy·Ritchie·Thompson 등)과 그 철학, 소프트웨어를 짓는 방식이 씨를 뿌린 덕에 믿을 수
  없을 만큼 운이 좋았다. 그래서 우리는 단순하고 작은 서비스들의 느슨한 통합을 통해 강력하게
  확장되고 복잡한 시스템을 지을 수 있었다. 어떤 이유에선지 빅데이터 시스템에 오면 우리는 이
  철학을 버렸다. 아마도 어느 시점에 우리가 데이터(몸)를 그 코드(영혼)에서 분리하기로 결정했고,
  그것이 그 주위에 다른 철학을 확립하도록 이끌었기 때문일 것이다** (4장, p.61).[^dehghani2022]
  #hypothesis — 저자가 "아마도"로 표지한 원인 추정이다.
- 그래서 플랫폼 설계 규범 — **데이터 메시 플랫폼이 조직 안팎에서 데이터 공유를 현실적으로
  확장하려면, 유닉스 철학을 전면적으로 받아들이되 그것을 데이터 관리와 데이터 공유의 고유한
  필요에 적응시켜야 한다. 플랫폼을 서로 다른 벤더가 서로 다른 구현으로 구현할 수 있으면서도
  나머지 플랫폼 서비스와 잘 어울리는 상호운용 가능한 서비스 집합으로 설계해야 한다** (4장,
  p.61).[^dehghani2022]
- 실물 예는 관측 가능성이다 — 능력 자체는 **메시 위 모든 데이터 프로덕트의 행동을 모니터링하고
  중단·오류·바람직하지 않은 접근을 탐지하고 관련 팀에 알려 데이터 프로덕트를 복구하게 하는
  능력**이고, 이를 위해 협력해야 하는 플랫폼 서비스는 넷이다 — **자기 운영에 대한 정보를 내보내고
  로깅하는 데이터 프로덕트, 내보내진 로그와 메트릭을 포착해 총체적 메시 뷰를 제공하는 서비스,
  그 로그에서 이상과 오류를 검색·분석·탐지하는 서비스, 문제가 생기면 개발자에게 알리는 서비스**
  (4장, p.61).[^dehghani2022]
  - 결합의 열쇠 — **이 서비스들의 단순한 통합의 열쇠는 상호운용성이다. 로그와 메트릭이 표현되고
    공유되는 공통 언어와 API 말이다** (4장, p.61, 각주 4는 OpenLineage를 추적 로그 표준화
    시도로 지목한다).[^dehghani2022]
  - 표준이 없을 때의 대가 — **그런 표준 없이는 우리는 데이터 접근을 단일 호스팅 환경으로 제약하는
    단일 모놀리식(그러나 잘 통합된) 해법으로 되돌아간다. 우리는 환경을 가로질러 데이터를 공유하고
    관측하는 데 실패한다** (4장, p.61).[^dehghani2022]

## 내장된 혁신 문화

- 배경으로 린 계열을 든다 — **Eric Ries가 짧고 빠른 build-measure-learn 주기를 통해 어떻게
  과학적으로 혁신하는지 보이려고 린 스타트업(Lean Startup)을 도입했다. 이 개념은 이후 규모화된
  혁신 방법론인 린 엔터프라이즈(Lean Enterprise)를 통해 더 큰 기업에 적용되었다** (4장,
  p.62).[^dehghani2022]
- 플랫폼이 하는 일 — **데이터 메시 플랫폼은 불필요한 수작업을 제거하고 복잡성을 감추고 데이터
  프로덕트 개발자와 사용자의 워크플로를 간소화해, 그들이 데이터로 혁신할 수 있게 풀어 준다**
  (4장, p.62).[^dehghani2022]
- **성숙도 측정 지표가 여기서 하나 나온다** — **데이터 메시 플랫폼이 그 일을 얼마나 효과적으로
  하는지 평가하는 단순한 리트머스 시험은, 한 팀이 데이터 주도 실험을 구상하고 그 실험을 돌리는
  데 필요한 데이터를 쓰게 되기까지 걸리는 시간을 재는 것이다. 짧을수록 데이터 메시 플랫폼이 더
  성숙한 것이다** (4장, p.62).[^dehghani2022] 원전 전체에서 드물게 조작적 정의를 갖춘 지표다.
- 누가 실험하는가도 규정된다 — **데이터 메시 플랫폼은 도메인 팀이 혁신하고 데이터 주도 실험을
  수행하도록 지원한다. 데이터 주도 혁신은 더 이상 중앙 데이터 팀의 전유물이 아니다. 그것은 각
  도메인 팀이 자기 서비스·제품·프로세스를 개발하는 데 내장(embedded)되어야 한다** (4장,
  p.62).[^dehghani2022]

## 이행 지침 여섯

저자가 4장 마지막에 두는 실행 지침이다 (4장, pp.62–65).[^dehghani2022]

### ① API와 프로토콜을 먼저 설계한다

- **플랫폼 여정을 시작할 때 — 사려는 것이든 지으려는 것이든 아마도 둘 다든 — 플랫폼이 사용자에게
  노출하는 인터페이스를 선택하고 설계하는 데서 시작하라. 프로그래밍 API일 수도, 명령줄이나 그래픽
  인터페이스일 수도 있다. 어느 쪽이든 인터페이스를 먼저 정하고 그다음 그 구현을 여러 기술을 통해
  한다** (4장, p.62).[^dehghani2022] 저자가 드는 선례는 **객체를 post·get·delete하는 REST API를
  노출하는 클라우드 블롭 스토리지 제공자**다 (4장, p.62).[^dehghani2022]
- API만이 아니다 — **API에 더해 상호운용성을 가능하게 하는 통신 프로토콜과 표준을 정하라. 대규모
  분산 아키텍처의 한 사례인 인터넷에서 영감을 받아 좁은 허리(narrow waist) 프로토콜을 정하라**
  (4장, p.63, 각주 8은 Akhshabi·Dovrolis의 SIGCOMM 2011 논문 "The Evolution of Layered Protocol
  Stacks Leads to an Hourglass-Shaped Architecture").[^dehghani2022]
- 정할 프로토콜의 목록이 명시된다 — **데이터 프로덕트가 자기 의미론을 어떻게 표현하는지, 어떤
  형식으로 시변(time-variant) 데이터를 부호화하는지, 각각 어떤 질의 언어를 지원하는지, 각각 어떤
  SLO를 보증하는지를 규율하는 프로토콜** (4장, p.63).[^dehghani2022]

### ② 제너럴리스트 채택을 준비한다

- 기술 평가의 기준을 바꾼다 — **플랫폼 기술을 평가할 때 많은 개발자에게 알려진 자연스러운
  프로그래밍 양식에 더 잘 맞는 것을 선호하라. 예컨대 파이프라인 오케스트레이션 도구를 고른다면,
  YAML이나 XML에 난해한 표기법으로 또 하나의 도메인 특유 언어(DSL)를 만들려는 것보다 제너럴리스트
  개발자에게 익숙한 단순한 파이썬 함수 프로그래밍에 적합한 것을 골라라** (4장,
  p.63).[^dehghani2022]
- 그러나 단일 수준을 가정하지 않는다 — **현실에서는 복잡성 면에서 데이터 프로덕트의 스펙트럼이,
  전문화 수준 면에서 데이터 프로덕트 개발자의 스펙트럼이 있을 것이다. 플랫폼은 규모 있게 데이터
  프로덕트 전달을 동원하기 위해 이 스펙트럼을 만족시켜야 한다. 어느 경우든 회복력 있고 유지 가능한
  데이터 프로덕트를 짓기 위해 상록의(evergreen) 엔지니어링 실천을 적용할 필요는 여전히 남는다**
  (4장, p.63).[^dehghani2022]

### ③ 인벤토리를 만들고 단순화한다

- 정리 대상은 두 벌의 스택이다 — **분석 데이터 플레인과 운영 플레인의 분리는 우리에게 두 개의
  단절된 기술 스택을 남겼다. 하나는 분석 데이터를, 다른 하나는 애플리케이션·서비스를 짓고 돌리는
  것을 다룬다. 데이터 프로덕트가 운영 세계에 통합되고 내장됨에 따라 두 플랫폼을 수렴시키고 중복을
  제거할 기회가 있다** (4장, p.63).[^dehghani2022]
- **가장 날 선 진단이 여기 붙는다** — **지난 몇 년간 업계는 데이터 해법으로 마케팅되는 기술에
  과잉 투자를 겪었다. 많은 경우 그 운영계 대응물이 그 일을 하기에 완벽히 적합하다. 예컨대 나는
  DataOps라는 이름으로 마케팅되는 새로운 부류의 지속적 통합·지속적 전달(CI/CD) 도구를 봤다. 이
  도구들을 더 자세히 평가해 보면, 기존 CI/CD 엔진이 제공할 수 없는 차별화된 능력을 거의 제공하지
  않는다** (4장, pp.63–64).[^dehghani2022] [DataOps](../concepts/dataops.md)를 독립 도구 범주로
  세우는 서술과 정면으로 갈리는 판정이다 — 저자는 DataOps의 실천을 부정하는 것이 아니라 **그
  이름을 단 별도 도구 구매**를 부정한다.
- 실행은 재고 조사다 — **시작할 때, 당신 조직이 채택한 플랫폼 서비스의 인벤토리를 만들고 단순화할
  기회를 찾아라** (4장, p.64).[^dehghani2022]

### ④ 데이터 프로덕트를 관리하는 고수준 API를 만든다

- **데이터 메시 플랫폼은 데이터 프로덕트를 새 추상으로 관리하는 새 API 집합을 도입해야 한다.
  많은 데이터 플랫폼이 — 클라우드 제공자에게서 받는 서비스처럼 — 스토리지·카탈로그·컴퓨트 같은
  저수준 유틸리티 API를 포함하지만, 데이터 메시 플랫폼은 데이터 프로덕트를 하나의 객체로 다루는
  더 높은 수준의 API를 도입해야 한다** (4장, p.64).[^dehghani2022]
- 예로 드는 것 — **데이터 프로덕트를 생성하고·발견하고·연결하고·읽고·보안하는 API** (4장,
  p.64).[^dehghani2022] 착수 순서도 지정된다 — **데이터 메시 플랫폼을 세울 때 데이터 프로덕트라는
  추상과 작동하는 고수준 API에서 시작하라** (4장, p.64).[^dehghani2022]

### ⑤ 메커니즘이 아니라 경험을 짓는다

- 관찰된 실패 양식 — **플랫폼의 표현이 그것이 가능하게 하는 경험(experiences)이 아니라 그것이
  포함하는 메커니즘(mechanisms)에 닻을 내리는 플랫폼 구축·구매 상황을 나는 수없이 만났다. 플랫폼을
  이렇게 정의하는 접근은 흔히 비대한 플랫폼 개발과, 과욕적이고 과잉 가격의 기술 채택으로 이어진다**
  (4장, p.64).[^dehghani2022]
- 저자가 드는 실물이 데이터 카탈로그다 — **거의 모든 플랫폼이 메커니즘 목록에 데이터 카탈로그를
  갖고 있고, 이는 기능 목록이 가장 긴 데이터 카탈로그 제품의 구매로 이어지며, 그다음 팀의 워크플로를
  그 카탈로그의 내부 작동에 맞추도록 과적합시킨다. 이 과정은 흔히 몇 달이 걸린다** (4장,
  p.64).[^dehghani2022] [메타데이터 관리](../concepts/metadata-management.md)가 카탈로그를 중심
  기제로 세우는 서술과 갈리는 자리다.
- 대안 순서 — **대조적으로 당신의 플랫폼은 데이터 프로덕트를 발견한다는 단일 경험의 표현에서
  시작할 수 있다. 그다음 이 경험을 가능하게 하는 가장 단순한 도구와 메커니즘을 짓거나 사라.
  그다음 헹구고, 반복하고, 다음 경험을 위해 리팩터링하라** (4장, p.64).[^dehghani2022]

### ⑥ 가장 단순한 기반에서 시작해 수확하며 진화시킨다

- 선후 관계 질문에 저자가 답한다 — **"내가 데이터 메시를 채택하기 시작할 수나 있는가, 아니면
  플랫폼을 먼저 짓기까지 시간을 기다려야 하는가?" 답은 데이터 메시 플랫폼이 없더라도 오늘 데이터
  메시 전략을 채택하기 시작하라는 것이다** (4장, p.65).[^dehghani2022]
- 시작점 — **가장 단순한 가능한 기반에서 시작할 수 있다. 당신의 가장 작은 가능한 기반 프레임워크
  (foundation framework)는 아마 당신이 이미 채택한 데이터 기술로 구성될 것이다. 특히 이미 클라우드
  위에서 분석을 운영하고 있다면 그렇다. 기반으로 쓸 수 있는 바닥층 유틸리티에는 전형적인 저장 기술,
  데이터 처리 프레임워크, 연합 질의 엔진 등이 포함된다** (4장, p.65).[^dehghani2022]
- 진화 방식이 **수확**이다 — **데이터 프로덕트의 수가 늘면 표준이 개발되고 데이터 프로덕트 전반에
  유사한 문제에 접근하는 공통 방식이 발견된다. 그러면 데이터 프로덕트와 도메인 팀 전반에서 공통
  능력을 수집함으로써 플랫폼을 수확된 프레임워크(harvested framework)로 진화시키게 된다** (4장,
  p.65).[^dehghani2022]
- 플랫폼 자체의 지위 — **데이터 메시 플랫폼 자체가 하나의 제품임을 기억하라. 그것은 내부
  제품이다 — 여러 벤더의 서로 다른 도구와 서비스로 지어졌더라도 그렇다. 그 제품 사용자는 내부
  팀이다. 그것은 기술적 제품 소유권(technical product ownership), 장기 계획, 장기 유지보수를
  요구한다. 계속 진화하고 진화적 성장을 거치지만, 그 삶은 오늘 최소 실행 가능 제품(MVP)으로
  시작한다** (4장, p.65).[^dehghani2022]

## 요약이 남기는 것

- 저자 자신의 요약 — **데이터 메시의 셀프서브 플랫폼 원칙은 다른 두 원칙이 기존 도메인 엔지니어링
  팀에 부과하는 인지 부하를 낮추려 구조에 나선다. 자기 분석 데이터를 소유하고 그것을 제품으로
  공유하라는 부담 말이다** (4장, p.65).[^dehghani2022]
- 무엇을 공유하고 무엇이 다른가 — **그것은 기존 데이터 플랫폼과 공통 능력을 공유한다. 다중 언어
  스토리지·데이터 처리 엔진·질의 엔진·스트리밍 등에 대한 접근 제공이다. 그러나 사용자에서
  차별화된다 — 주로 제너럴리스트 기술자로 이뤄진 자율적 도메인 팀이다. 그것은 데이터·메타데이터·
  코드·정책을 한 단위로 캡슐화하는 데이터 프로덕트라는 더 높은 수준의 구성물을 관리한다** (4장,
  p.65).[^dehghani2022]
- 목적의 한 줄 — **그 목적은 저수준 복잡성을 더 단순한 추상 뒤에 감추고, 데이터 프로덕트를 가치
  단위로 교환한다는 결과를 달성하는 여정에서 마찰을 제거함으로써 도메인 팀에 초능력을 주는
  것이다** (4장, p.66).[^dehghani2022]
- 확장 방향이 기술 선택 기준을 정한다 — **단일 배포 환경이나 조직 단위나 회사를 넘어 데이터
  공유를 확장하기 위해, 그것은 상호운용 가능한 탈중앙 해법을 선호한다** (4장,
  p.66).[^dehghani2022]
