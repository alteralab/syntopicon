# 작은 파일 문제와 컴팩션

- [문제 — 메타데이터가 처리보다 비싸진다](#문제--메타데이터가-처리보다-비싸진다)

- [결과 셋](#결과-셋)
- [이어지는 페이지](#이어지는-페이지)

하나의 질문: **데이터를 자주 반입한 대가를 언제 어떻게 되갚는가.**

> **용어 주의**: 이 페이지의 **컴팩션(compaction)** 은 여러 작은 파일을 큰 파일로 병합하는
> 연산이다. 카프카 토픽의 키별 최신값 보존은 이 KB에서 **압착**으로 옮기고
> ([카프카 로그 압착](../concepts/kafka-log-compaction.md)), LSM 트리의 정렬 테이블 병합은
> [LSM 컴팩션](../concepts/lsm-compaction.md)이 받는다. Konieczny의 Compactor 패턴은 **셋 다를
> 한 이름 아래 묶으므로** 아래 [키 기반 저장에서는 뜻이 달라진다](#키-기반-저장에서는-뜻이-달라진다)
> 절에서 저자 자신이 그 갈림을 짚는 대목을 따로 옮겼다.

## 문제 — 메타데이터가 처리보다 비싸진다

- 문제의 발생 경로 — **완벽한 데이터셋조차 병목이 될 수 있다. 특히 새 데이터 때문에 시간이
  지나며 자랄 때 그렇다. 그 결과 어느 시점에는 파일을 나열하는 것 같은 메타데이터 관련 연산이
  데이터 처리 변환보다도 더 오래 걸릴 수 있다** (2장, p.27).[^konieczny2025]
- 저자의 문제 서술이 그 비율을 수치로 준다 (2장, p.27):[^konieczny2025] 실시간 반입
  파이프라인이 스트리밍 브로커의 이벤트를 오브젝트 저장에 동기화하고 배치 잡이 최대 10분 안에
  데이터를 쓸 수 있게 하는 단순한 패스스루 잡인데, **석 달 뒤 모든 배치 잡이 데이터셋을 구성하는
  너무 많은 작은 파일 때문에 메타데이터 오버헤드(metadata overhead) 문제를 겪는다. 그 결과 잡은
  실행 시간의 70%를 처리할 파일을 나열하는 데, 남은 30%만 데이터를 처리하는 데 쓴다. 이는 종량
  과금(pay-as-you-go) 서비스를 쓸 때 심각한 지연·비용 영향을 갖는다.**
  - **이 70/30이 이 문제의 성격을 규정한다** — 데이터가 커져서가 아니라 **조각이 많아져서**
    느려진다. 그래서 완화책도 컴퓨트 증설이 아니라 조각 수 줄이기다.
- 오래된 문제라는 것도 저자가 못 박는다 — **작은 파일을 갖는 것은 데이터 엔지니어링 공간에서 잘
  알려진 문제다. 하둡 시대부터 있었고 2025년 저술 시점의, 사실상 무제한인 오브젝트 저장 기반 레이크하우스에도
  여전히 존재한다. 많은 작은 파일을 저장하는 것은 더 긴 나열 연산과 파일을 열고 닫는 더 무거운
  I/O를 수반한다. 이 이슈에 대한 자연스러운 해법은 더 적은 파일을 저장하는 것이다** (2장,
  p.27).[^konieczny2025] (저자는 자세한 설명을 Rukmani Gopalan, *The Cloud Data Lake*(O'Reilly,
  2023) 4·5장으로 넘긴다 — 2장, p.27 각주 4.)

## Compactor 패턴

- 하는 일 — **Compactor 패턴은 여러 작은 파일을 더 큰 파일로 결합해 읽기의 전체 I/O 오버헤드를
  줄임으로써 문제를 다룬다** (2장, p.27).[^konieczny2025]
- 구현은 기술마다 다르고, 저자가 셋을 대조한다 (2장, pp.27–28):[^konieczny2025]

  | 저장 | 컴팩션의 실물 |
  |---|---|
  | Apache Iceberg | `rewrite data file` 액션 |
  | Delta Lake | `OPTIMIZE` 명령 |
  | Apache Hudi | 머지-온-리드(merge-on-read, MoR) 테이블 — 데이터셋은 컬럼 형식으로 쓰이고 이후 변경은 행 형식으로 쓰인다 |

  - **오픈 테이블 파일 형식은 전용 컴팩션 명령을 갖고, 그것이 흔히 새 커밋의 일부로 작은 파일을
    큰 파일로 병합하는 트랜잭션 분산 데이터 처리 잡을 내부에서 돌린다** (2장,
    p.27).[^konieczny2025]
  - Hudi가 다른 이유 — **이 접근이 더 빠른 쓰기를 선호하므로, 읽기 프로세스를 최적화하기 위해
    Hudi의 컴팩션 연산은 행 저장의 변경을 컬럼 저장과 병합한다. 이 접근은 동질적 컬럼 형식에서만
    작동하는 Delta Lake·Apache Iceberg와 다르다** (2장, p.28).[^konieczny2025]
  - 행·컬럼 저장의 이 갈림 자체는
    [컬럼 지향 저장](../concepts/column-oriented-storage.md)이 받는다.
- 레이크하우스 쪽 실행은 두 줄로 끝나지만, **컴팩션 하나로는 끝나지 않는다**는 것이 이 패턴의
  핵심 교훈이다 (2장, p.29):[^konieczny2025]

  ```python
  devices_table = DeltaTable.forPath(spark_session, table_dir)
  devices_table.optimize().executeCompaction()
  devices_table.vacuum()
  ```

  - 첫 호출은 **잡이 시작할 때 사용 가능한 파일만 재조직하므로 독자와 기록자 모두에게 안전하고
    비충돌적인 연산**이다 (2장, p.29).[^konieczny2025] 둘째 호출은 이미 컴팩션된, 무관해진
    파일을 청소한다 — **청소 프로세스는 설정된 보존 임계보다 오래된 파일에만 적용된다. 그렇지
    않으면 vacuum이 쓰이는 중이고 아직 커밋되지 않은 파일을 제거해 테이블 상태를 손상시킬 수
    있다** (2장, p.29).[^konieczny2025]

## 키 기반 저장에서는 뜻이 달라진다

- 저자는 Compactor를 레이크 밖으로도 넓힌다 — **Compactor는 레이크 관련 저장 외의 데이터
  저장에서도 작동한다. 그중 하나가 추가 전용 키 기반 로그 시스템인 Apache Kafka다. 이 설정 기반
  구현에서는 컴팩션 빈도만 설정하면 되고, 전체 컴팩션 프로세스는 이후 그 빈도에 따라 데이터
  저장이 관리한다** (2장, p.28).[^konieczny2025]
- 그런데 같은 이름 아래 기제가 갈린다 (2장, p.28):[^konieczny2025]

  > However, in key-based systems, the compaction consists of optimizing the storage by
  > keeping only the most recent entry for a given record key. It still improves the
  > storage footprint, but unlike compaction in table file formats, the operation
  > overwrites the present data.

  - **이것이 이 KB가 낱말을 갈라 두는 이유의 소스 측 근거다.** 테이블 형식의 컴팩션은 **같은
    데이터를 더 적은 파일로 재배치**하고, 키 기반의 것은 **오래된 값을 지운다** — 후자는 정보
    손실이 있다.
- 카프카 설정의 실물 — 토픽을 만들 때 로그 압착 설정을 걸 수 있고, **키 기반 레코드를 쓰며 매
  추가가 상태 갱신일 때 특히 유용하다. 압착을 켜면 Apache Kafka는 각 키의 최신 버전만 남기고
  나머지를 제거하는 청소 프로세스를 돌린다.** 설정은 `log.cleanup.policy`(압착 전략)와
  `log.cleaner.min.compaction.lag.ms`·`log.cleaner.max.compaction.lag.ms`(압착 빈도) 같은
  속성을 지원한다 (2장, pp.29–30).[^konieczny2025]
  - **결정성의 차이도 저자가 짚는다** — **Delta Lake 예제와 달리 카프카의 압착은 비결정적이다.
    정규 일정으로 돌 것을 기대할 수 없고, 그 결과 각 키마다 유일한 레코드를 언제나 보게 될 것을
    보장하지 않는다** (2장, p.30).[^konieczny2025] 압착의 내부 기제는
    [카프카 로그 압착](../concepts/kafka-log-compaction.md)에 있다.
- 트랜잭션 데이터베이스 쪽은 또 다르다 — **PostgreSQL에서 컴팩션은 `VACUUM` 명령만 쓰는데,
  그것은 저장 계층에서 물리적으로 제거되지 않은 삭제된 행인 죽은 튜플(dead tuples)이 차지한
  공간을 회수한다. 명시적 명령으로 촉발할 수 있다** (2장, p.29).[^konieczny2025]
  - 그러므로 **Delta Lake 예제와 비교하면 조금 오해를 부를 수 있다**고 저자 자신이 단서를 단다
    (2장, p.29).[^konieczny2025] 같은 낱말이 세 저장에서 세 가지 일을 한다.

## 결과 셋

- 결과 ① **비용 대 성능 맞교환** — **컴팩션 잡은 큰 테이블에서 컴퓨트 집약적일 수 있는 평범한
  데이터 처리 잡일 뿐이다. 이 측면만 고려하면 드물게, 예컨대 하루 한 번, 이상적으로는 업무 시간
  밖에, 그리고 데이터셋을 생성하는 파이프라인 바깥에서 실행해야 한다** (2장,
  p.28).[^konieczny2025]
  - 반대 방향의 힘 — **반면 드문 실행은 아직 컴팩션되지 않은 데이터를 다루는 잡에는 문제가 될 수
    있다. 그 잡들은 이 최적화 기법의 이득을 그냥 못 받기 때문이다** (2장, p.28).[^konieczny2025]
  - 저자의 판정은 규칙이 아니라 조건이다 — **불행히도 만능 해법은 없다. 때로는 하루 한 번 도는
    것으로 충분해 컴팩션되지 않은 데이터셋이 소비자에게 영향을 줄 만큼 크지 않다. 반대로 때로는
    그것이 받아들일 수 없어서, 소비자에게 벌을 주는 것이 반입 처리량에 영향을 주는 것보다 더 큰
    영향을 갖기 때문에 컴팩션을 데이터 반입 프로세스 안에 포함시키는 쪽을 선호하게 될 것이다**
    (2장, p.28).[^konieczny2025]
- 결과 ② **일관성** — **컴팩션은 이미 존재하는 데이터를 재작성할 뿐임을 기억하라. 그 결과
  소비자는 쓸 데이터와 컴팩션 중인 데이터를 구별하기 어려울 수 있다. 그런 이유로 컴팩션은 원시
  파일 형식(JSON·CSV)보다 ACID 속성을 가진 2025년 저술 시점의 오픈 테이블 파일 형식(Delta Lake·Apache
  Iceberg)에서 구현하는 것이 훨씬 단순하고 안전하다** (2장, p.28).[^konieczny2025]
- 결과 ③ **청소(cleaning)** — **컴팩션 잡은 원천 파일을 보존할 수 있다. 그 결과 작은 파일들이
  여전히 남아 메타데이터 액션에 계속 영향을 준다. 그런 이유로 컴팩션 잡만으로는 충분하지 않다.
  이미 컴팩션된 파일이 차지한 공간을 회수하는 청소 잡으로 그것을 완성해야 한다** (2장,
  p.28).[^konieczny2025]
  - 수단은 `VACUUM` 같은 명령이고 **Delta Lake·Apache Iceberg·PostgreSQL·Redshift 같은 2025년 저술 시점
    데이터 저장 기술에서 쓸 수 있다. 다만 청소 전략은 현명하게 고르라 — 그 삭제된, 이미 컴팩션된
    파일에 기반한 버전으로는 데이터셋을 복구하지 못할 수 있다** (2장, p.29).[^konieczny2025]
  - **이 마지막 문장이 청소와 시간 여행의 충돌**이다. Full Loader의 결과 절이 되돌리기 수단으로
    들었던 시간 여행이 여기서 보존 임계 아래로 잘린다
    ([배치 반입 패턴](../concepts/batch-ingestion-patterns.md)의 Full Loader 절).
