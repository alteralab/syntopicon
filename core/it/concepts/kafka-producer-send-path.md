하나의 질문: **`send()` 한 번을 부르면 메시지는 어떤 부품들을 거쳐 브로커에 닿고,
그 사이의 실패는 누가 다루는가.**

## 요구사항이 먼저 갈린다

- 애플리케이션이 카프카에 쓰는 이유는 다양하다 — 감사·분석용 사용자 활동 기록, 지표
  기록, 로그 메시지 저장, 스마트 기기 정보 수집, 다른 애플리케이션과의 비동기
  통신(asynchronous communication), 데이터베이스에 쓰기 전 버퍼링 (3장,
  p.48).[^shapira2021]
- 용도가 갈리면 요구사항도 갈린다 — **모든 메시지가 치명적인가 유실을 감내할 수
  있는가, 우발적 중복을 허용하는가, 지연·처리량에 엄격한 요구가 있는가** (3장,
  p.48).[^shapira2021]
- 두 예가 대비된다 (3장, p.48):[^shapira2021]
  - 신용카드 거래 처리 — 메시지를 절대 잃거나 중복시키지 말아야 하고, 지연은 500ms
    까지 허용되며, 처리량은 초당 최대 100만 메시지를 기대한다.
  - 웹사이트 클릭 정보 저장 — 약간의 유실과 중복은 감내되고, 사용자 경험에 영향이
    없는 한 지연이 커도 된다.
- 이 갈림이 **프로듀서 API를 쓰는 방식과 설정을 좌우한다** (3장, p.48).[^shapira2021]

## 경로의 부품들

- 시작점은 `ProducerRecord`다. **토픽과 밸류값은 필수**이고, 키·파티션·타임스탬프·헤더
  모음은 선택이다 (3장, p.49).[^shapira2021]
- `send()`를 부르면 프로듀서가 가장 먼저 하는 일은 **키와 밸류 객체를 바이트 배열로
  직렬화(serialize)하는 것**이다 — 네트워크로 보낼 수 있게 하기 위해서다 (3장,
  p.49).[^shapira2021]
- 파티션을 명시하지 않았으면 데이터가 **파티셔너(partitioner)**로 간다. 파티셔너는
  대개 `ProducerRecord`의 키를 근거로 파티션을 고른다 (3장, p.49).[^shapira2021]
- 파티션이 정해지면 프로듀서는 그 레코드가 갈 토픽과 파티션을 알게 되고, **같은
  토픽·파티션으로 갈 레코드들의 배치에 그 레코드를 넣는다.** 그 배치들을 적절한
  브로커로 보내는 것은 **별도의 스레드**다 (3장, p.49).[^shapira2021]
- 브로커가 메시지를 받으면 응답을 돌려준다 (3장, pp.49–50):[^shapira2021]
  - 성공하면 `RecordMetadata` 객체를 돌려주는데 **토픽·파티션·그 파티션 안에서의
    오프셋**이 담긴다.
  - 실패하면 에러를 돌려준다. 프로듀서는 에러를 받으면 **포기하고 에러를 반환하기
    전에 몇 번 더 재시도할 수 있다.**

## 세 가지 전송 방식

- 프로듀서를 만들고 나면 메시지를 보내는 방식은 셋이다 (3장, p.51):[^shapira2021]
  - **fire-and-forget** — 서버로 보내고 성공 여부를 신경 쓰지 않는다. 카프카가 고가용
    이고 프로듀서가 자동 재시도하므로 대개는 성공하지만, **재시도 불가 에러나 타임아웃일
    때는 메시지가 유실되고 애플리케이션은 아무 정보도 받지 못한다.**
  - **동기 전송(synchronous send)** — 기술적으로 카프카 프로듀서는 언제나 비동기다.
    `send()`는 `Future` 객체를 돌려주고, `get()`으로 그 `Future`를 기다려 다음 레코드를
    보내기 전에 성공 여부를 확인하는 것이 동기 전송이다.
  - **비동기 전송(asynchronous send)** — `send()`에 콜백 함수를 함께 넘긴다. 브로커
    응답이 오면 콜백이 호출된다.
- 예제들은 전부 단일 스레드지만, **프로듀서 객체 하나를 여러 스레드가 함께 써서 메시지를
  보낼 수 있다** (3장, p.51).[^shapira2021]
- 가장 단순한 전송은 `producer.send(record)`의 반환값을 무시하는 것이다. `send()`는
  `RecordMetadata`를 담은 `Future`를 돌려주지만 무시하면 **성공 여부를 알 방법이 없고,
  이 방식은 메시지를 조용히 버려도 되는 경우에만 쓸 수 있다 — 프로덕션에서는 통상
  그렇지 않다** (3장, p.52).[^shapira2021]
- 반환값을 무시해도 **카프카에 보내기 전 단계의 예외는 여전히 받는다** — 직렬화 실패의
  `SerializationException`, 버퍼가 찼을 때의 `BufferExhaustedException`이나
  `TimeoutException`, 전송 스레드가 인터럽트됐을 때의 `InterruptException` (3장,
  p.52).[^shapira2021]

## 동기 전송과 에러의 두 종류

- 동기 전송은 단순하지만 **성능이 대가**다. 클러스터가 얼마나 바쁜지에 따라 브로커는
  프로듀스 요청에 **2ms에서 수 초까지** 걸려 응답하는데, 동기 전송이면 전송 스레드가
  그 시간을 아무 일도 하지 않고 기다린다 — 다른 메시지를 보내지도 못한다. 그래서 **동기
  전송은 프로덕션 애플리케이션에서 잘 쓰이지 않는다**(코드 예제에서는 매우 흔하다)
  (3장, pp.52–53).[^shapira2021]
- `KafkaProducer`의 에러는 두 종류다 (3장, p.53):[^shapira2021]
  - **재시도 가능(retriable) 에러** — 메시지를 다시 보내면 해결될 수 있는 것들이다.
    연결 에러는 연결이 다시 맺어지면 해결되고, "not leader for partition" 에러는 그
    파티션의 새 리더가 선출되고 클라이언트 메타데이터가 갱신되면 해결된다.
  - `KafkaProducer`는 이런 에러를 **자동 재시도하도록 설정할 수 있으므로**,
    애플리케이션 코드는 재시도 횟수가 소진되고도 해결되지 않았을 때에만 재시도 가능
    예외를 받는다.
  - **재시도로 해결되지 않는 에러** — 예로 "Message size too large"가 있다. 이 경우
    `KafkaProducer`는 재시도하지 않고 **즉시 예외를 반환한다.**

## 비동기 전송과 콜백

- 비동기가 필요한 이유는 왕복 시간의 산술이다 — 애플리케이션과 클러스터 사이 네트워크
  왕복이 10ms면 **메시지마다 응답을 기다릴 경우 100개를 보내는 데 약 1초**가 걸리지만,
  응답을 기다리지 않고 전부 보내면 거의 시간이 들지 않는다 (3장, p.53).[^shapira2021]
- 그래도 응답을 완전히 버리지는 않는다 — **완전히 실패한 경우는 알아야** 예외를
  던지거나 로그를 남기거나 "errors" 파일에 적어 나중에 분석할 수 있다 (3장,
  p.53).[^shapira2021]
- 그래서 프로듀서는 레코드를 보낼 때 콜백을 붙이는 것을 지원한다 (3장,
  pp.53–54):[^shapira2021]
  - 콜백을 쓰려면 `org.apache.kafka.clients.producer.Callback` 인터페이스를 구현하는
    클래스가 필요하다 — 함수는 `onCompletion()` 하나뿐이다.
  - 카프카가 에러를 돌려주면 `onCompletion()`은 **널이 아닌 예외**를 받는다.

  아래가 그 `Callback` 구현과 그것을 넘기는 `send()` 호출이다 —
  `DemoProducerCallback`·`onCompletion`으로 찾는다.

  ```java
  private class DemoProducerCallback implements Callback {
      @Override
      public void onCompletion(RecordMetadata recordMetadata, Exception e) {
          if (e != null) {
              e.printStackTrace();
          }
      }
  }

  ProducerRecord<String, String> record =
      new ProducerRecord<>("CustomerCountry", "Biomedical Materials", "USA");
  producer.send(record, new DemoProducerCallback());
  ```

- 콜백에는 제약이 붙는다 — **콜백은 프로듀서의 메인 스레드에서 실행된다** (3장,
  p.54):[^shapira2021]
  - 이것이 보장하는 것: 같은 파티션으로 메시지 둘을 연달아 보내면 **콜백도 보낸 순서
    그대로 실행된다.**
  - 이것이 요구하는 것: **콜백은 충분히 빨라야 한다.** 느리면 프로듀서를 지연시키고 다른
    메시지의 전송을 막는다. **콜백 안에서 블로킹 연산을 수행하는 것은 권장되지
    않으며**, 블로킹이 필요하면 다른 스레드에서 동시에 수행해야 한다.

## 경로에 얹는 것 — 헤더

- 레코드는 키·밸류 외에 **헤더(header)**를 가질 수 있다. 레코드 헤더는 **키/밸류 쌍
  자체는 건드리지 않고 카프카 레코드에 메타데이터를 추가하는** 수단이다 (3장,
  p.71).[^shapira2021]
- 대표 용도 둘 (3장, p.71):[^shapira2021]
  - **계보(lineage)** — 레코드 안 데이터의 출처를 표시한다.
  - **라우팅·추적** — 메시지 본문을 파싱하지 않고 헤더 정보만으로 라우팅한다. 메시지가
    암호화돼 있고 라우터에 데이터 접근 권한이 없는 경우가 그 예다.
- 구조는 **키/밸류 쌍의 순서 있는 컬렉션**이다. **키는 항상 `String`**이고 값은 메시지
  밸류처럼 **직렬화된 아무 객체**나 될 수 있다 (3장, p.71).[^shapira2021]
- 추가는 레코드의 `headers()`에 `add`하는 것이다 — 예로 `record.headers().add(...)`에
  `"privacy-level"` 키와 UTF-8로 바이트화한 값을 넘긴다 (3장, p.71).[^shapira2021]

## 경로에 얹는 것 — 인터셉터

- 인터셉터의 존재 이유는 **클라이언트 애플리케이션 코드를 고치지 않고 동작을 바꾸는
  것**이다. 조직의 모든 애플리케이션에 동일한 동작을 넣고 싶거나, 원본 코드에 접근할 수
  없을 때가 그 경우다 (3장, p.71).[^shapira2021]
- `ProducerInterceptor`의 핵심 메서드는 둘이다 (3장, p.71):[^shapira2021]
  - `onSend(ProducerRecord<K, V> record)` — **레코드가 카프카로 보내지기 전, 심지어
    직렬화되기 전에** 호출된다. 여기서 레코드 정보를 캡처하고 수정할 수 있으며, **반드시
    유효한 `ProducerRecord`를 반환해야 한다** — 반환된 레코드가 직렬화돼 전송된다.
  - `onAcknowledgement(RecordMetadata metadata, Exception exception)` — 카프카가 전송에
    대한 응답(ack)을 보내면 호출된다. **응답을 수정할 수는 없고** 정보를 캡처만 한다.
- 일반적인 용도: 모니터링·추적 정보 수집, 표준 헤더 삽입(특히 계보 추적), 민감 정보
  마스킹 (3장, p.72).[^shapira2021]
- 적용은 클라이언트 코드 변경 없이 이뤄진다 — 카프카에 딸려 오는
  `kafka-console-producer`에 인터셉터를 물리는 절차는 셋이다: **jar를 `CLASSPATH`에
  추가**하고, `interceptor.classes=…`와 인터셉터 자체 설정을 담은 설정 파일을 만들고,
  애플리케이션을 평소처럼 실행하되 `--producer.config`로 그 설정을 포함시킨다 (3장,
  p.73).[^shapira2021]
