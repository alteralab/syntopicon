# 데이터베이스 관리 시스템의 구조

이 페이지의 질문: **데이터베이스 관리 시스템은 어떤 구성 요소로 나뉘고, 저장
엔진(storage engine)은 그중 어디에 있는가.**

## 청사진은 없다

- 데이터베이스 관리 시스템 설계에 공통 청사진은 없다. 데이터베이스마다 조금씩 다르게
  지어지고, 구성 요소의 경계는 보기도 정의하기도 어렵다. 문서상 경계가 있어도 코드에서는
  성능 최적화·엣지 케이스 처리·아키텍처 결정 때문에 겉보기에 독립적인 구성 요소들이 서로
  얽혀 있다 (1장, p.8).[^petrov2019]
- 이 책이 제시하는 구조는 여러 표준 문헌에서 공통으로 나타나는 주제를 모은 것이지, 어느 한
  제품의 실제 모듈 구획이 아니다 (1장, p.8).[^petrov2019]
- 데이터베이스 관리 시스템은 클라이언트/서버 모형을 쓴다 — 데이터베이스 시스템 인스턴스
  (노드)가 서버, 애플리케이션 인스턴스가 클라이언트다 (1장, p.8).[^petrov2019]

## 질의가 지나는 경로

- 클라이언트 요청은 **전송 서브시스템(transport subsystem)** 으로 들어온다. 요청은 대개 질의
  언어로 표현된 질의 형태이며, 이 서브시스템은 클러스터의 다른 노드와의 통신도 맡는다
  (1장, p.8).[^petrov2019]
- 전송 서브시스템은 질의를 **질의 처리기(query processor)** 에 넘긴다 — 파싱·해석·검증을
  한다. 접근 제어 검사는 그 뒤에 이뤄지는데, 질의를 해석한 뒤에야 온전히 할 수 있기
  때문이다 (1장, p.9).[^petrov2019]
- 파싱된 질의는 **질의 최적화기(query optimizer)** 로 간다 (1장, p.9):[^petrov2019]
  - 먼저 불가능하거나 중복된 부분을 걷어낸다.
  - 그다음 내부 통계(인덱스 카디널리티, 근사 교집합 크기 등)와 데이터 배치(클러스터의 어느
    노드가 데이터를 갖고 있고 전송 비용이 얼마인가)를 근거로 가장 효율적인 실행 방법을
    찾는다.
  - 질의 해석에 필요한 관계 연산(대개 의존 트리로 표현)과 인덱스 순서·카디널리티 추정·접근
    방법 선택 같은 최적화를 함께 다룬다.
- 결과는 **실행 계획(execution plan, 질의 계획)** 이다 — 결과가 완전하다고 볼 수 있게 되기까지
  수행해야 하는 연산의 순열이다. 같은 질의를 서로 효율이 다른 여러 실행 계획으로 만족시킬
  수 있으므로 최적화기가 그중 가장 나은 것을 고른다 (1장, p.9).[^petrov2019]
- 실행 계획은 **실행 엔진(execution engine)** 이 수행하며, 로컬 연산과 원격 연산의 결과를
  합친다. 원격 실행에는 클러스터의 다른 노드로 데이터를 읽고 쓰는 일과 복제가 포함된다
  (1장, p.10).[^petrov2019]

## 저장 엔진 안쪽

- 로컬 질의(클라이언트에서 직접 오거나 다른 노드에서 온 것)는 **저장 엔진(storage engine)** 이
  실행한다. 저장 엔진은 책임이 나뉜 여러 구성 요소를 갖는다 (1장, p.10):[^petrov2019]
  - **트랜잭션 관리자(transaction manager)** — 트랜잭션을 스케줄링하고, 데이터베이스가 논리적으로
    일관되지 않은 상태에 빠지지 않게 한다.
  - **잠금 관리자(lock manager)** — 실행 중인 트랜잭션을 위해 데이터베이스 객체에 잠금을 걸어,
    동시 연산이 물리적 데이터 무결성을 깨뜨리지 않게 한다.
  - **접근 방법(access method, 저장 구조)** — 디스크의 데이터 접근과 조직을 관리한다. 힙 파일과
    [B-트리](../concepts/b-tree-structure.md)·[LSM 트리](../concepts/lsm-tree.md) 같은 저장 구조가
    여기 속한다.
  - **버퍼 관리자(buffer manager)** — 데이터 페이지를 메모리에 캐시한다.
  - **복구 관리자(recovery manager)** — 연산 로그를 유지하고 장애 시 시스템 상태를 복원한다.
- 트랜잭션 관리자와 잠금 관리자가 함께 **동시성 제어(concurrency control)** 를 맡는다 — 논리적·물리적
  데이터 무결성을 보장하면서 동시 연산이 가능한 한 효율적으로 수행되게 한다 (1장,
  p.10).[^petrov2019]

## 트랜잭션을 굴리는 네 구성 요소

위의 다섯 관리자 목록은 1장의 조감도다. 5장은 같은 것을 트랜잭션 쪽에서 다시 세는데, 이때
호명되는 것은 넷이고 이름도 조금 다르다(접근 방법 대신 페이지 캐시가, 복구 관리자 대신 로그
관리자가 나온다).

- **데이터베이스 시스템에서 트랜잭션을 구현하려면, 디스크에 데이터를 조직하고 영속화하는 저장
  구조에 더해 여러 구성 요소가 함께 일해야 한다. 노드 로컬에서는 트랜잭션 관리자(transaction
  manager)가 트랜잭션을 조율하고 스케줄링하며, 트랜잭션과 그 개별 단계를 추적한다** (5장,
  p.80).[^petrov2019]
- **잠금 관리자(lock manager)는 이 자원에 대한 접근을 지키고 데이터 무결성을 위반할 동시 접근을
  막는다. 잠금이 요청될 때마다 잠금 관리자는 그것이 이미 다른 트랜잭션에 의해 공유 모드나 배타
  모드로 쥐어져 있는지 확인하고, 요청된 접근 수준이 모순을 낳지 않으면 접근을 허가한다. 배타
  잠금은 어느 시점에나 최대 하나의 트랜잭션만 쥘 수 있으므로 그것을 요청하는 다른 트랜잭션은
  잠금이 해제될 때까지 기다리거나, 중단하고 나중에 재시도해야 한다. 잠금이 해제되거나 트랜잭션이
  종료될 때마다 잠금 관리자는 대기 중인 트랜잭션 중 하나에 알려 그것이 잠금을 획득하고 계속하게
  한다** (5장, p.80).[^petrov2019]
- **페이지 캐시(page cache)는 영속 저장(디스크)과 저장 엔진의 나머지 사이의 중개자 역할을 한다.
  메인 메모리에서 상태 변경을 준비하고, 영속 저장과 동기화돼야 하는 페이지의 캐시 역할을 한다.
  데이터베이스 상태에 대한 모든 변경은 먼저 캐시된 페이지에 적용된다** (5장,
  p.80).[^petrov2019]
- **로그 관리자(log manager)는 캐시된 페이지에 적용됐지만 아직 영속 저장과 동기화되지 않은 연산의
  이력(로그 항목)을 보유해, 크래시 시 그것들이 유실되지 않도록 보장한다. 다시 말해 로그는 이
  연산들을 재적용하고 시작 중에 캐시된 상태를 재구성하는 데 쓰인다. 로그 항목은 중단된 트랜잭션이
  한 변경을 언두하는 데도 쓰일 수 있다** (5장, p.80).[^petrov2019]
- 범위가 여기서 끊긴다 — **분산(다중 파티션) 트랜잭션은 추가 조율과 원격 실행을 요구한다.** 그
  프로토콜은 13장이 다룬다 (5장, p.80).[^petrov2019]

## 동시성 제어가 실제로 무엇을 고르는가

- 위에서 한 줄로 정리된 동시성 제어(concurrency control)는 실제로는 선택지가 여럿인 자리다.
  **동시성 제어는 단일 노드 데이터베이스와 분산 데이터베이스 양쪽에 관련된다** (8장,
  p.278).[^kleppmann2026]
- **2026년 저술 시점에 직렬성(serializability)을 제공하는 대부분의 데이터베이스는 세 기법 중 하나를 쓴다 —
  직렬 순서로 문자 그대로 트랜잭션을 실행하기, 2단계 잠금(two-phase locking), 그리고 직렬성
  스냅샷 격리(serializable snapshot isolation) 같은 낙관적 동시성 제어(optimistic concurrency
  control) 기법** (8장, p.309).[^kleppmann2026] 잠금 관리자가 전면에 나서는 것은 그중 둘째
  뿐이다.
- 위의 잠금 관리자와 복구 관리자가 결합하는 지점도 명시된다 — **단일 노드 트랜잭션에서 원자성은
  흔히 저장 엔진이 구현한다. 데이터베이스는 트랜잭션의 쓰기를 내구적으로 만들고(보통 쓰기 전
  로그에) 디스크의 로그에 커밋 레코드를 덧붙인다. 커밋 레코드가 크래시 전에 디스크에 성공적으로
  쓰였으면 트랜잭션은 커밋된 것으로 간주되고, 아니면 그 트랜잭션의 쓰기는 롤백된다** (8장,
  p.323).[^kleppmann2026]

## 왜 이 해부가 필요한가

- 이 책 1부의 관심사는 저장과 인덱싱 구조다. 그래서 상위 수준의 데이터 조직 방식과 데이터
  파일·인덱스 파일의 관계를 먼저 이해해야 한다 (1장, p.8).[^petrov2019]
- 용어가 맥락 없이는 모호하다는 점도 이 장의 동기다 — 예로 서로 거의 관계가 없는 열 지향
  스토어와 와이드 칼럼 스토어의 구분, 또는 클러스터형·비클러스터형 인덱스가 인덱스 구조형
  테이블과 맺는 관계가 그렇다. 이 장의 목표는 그런 용어를 가리지 않고 정확한 정의를 찾는
  것이다 (1장, p.7).[^petrov2019]
- 흔히 쓰이는 다른 분류축도 있다 — OLTP(사용자 대면 요청과 트랜잭션이 많고 질의가 짧다),
  OLAP(복잡한 집계, 길게 도는 애드혹 질의), HTAP(둘의 성질을 결합)이 그것이다. 다만 이 책은
  완전한 분류 체계가 논의에 필요하지 않다고 보고 넘어간다 (1장, pp.7–8).[^petrov2019]
