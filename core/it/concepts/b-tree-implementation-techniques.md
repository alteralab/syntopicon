하나의 질문: **기본 B-트리 알고리즘과 실제로 돌아가는 온디스크 구현 사이에는 무엇이 더
필요한가.**

## 무엇이 더 필요한가

- 앞 장이 다룬 것은 일반 원칙이었다 — **이진 형식 조합의 일반 원칙, 셀을 만들고 계층을 짓고
  포인터로 페이지에 잇는 법. 이 개념들은 인플레이스 갱신 저장 구조와 추가 전용 저장 구조
  양쪽에 적용된다** (4장, p.61).[^petrov2019]
- 이 장이 더하는 것은 셋으로 묶인다 (4장, p.61):[^petrov2019]
  - **조직(organization)** — **키와 포인터 사이의 관계를 세우는 법, 헤더와 페이지 사이의 링크를
    구현하는 법.**
  - **루트-리프 하강 중에 일어나는 일** — **이진 탐색을 수행하는 법, 나중에 노드를 분할하거나
    병합해야 할 경우에 대비해 브레드크럼을 모으고 부모 노드를 추적하는 법.**
  - **최적화 기법과 유지보수** — **재균형·오른쪽 전용 덧붙이기·벌크 로딩, 유지보수 프로세스,
    가비지 컬렉션.**

## 이진 탐색과 삽입 지점

- **B-트리 조회 알고리즘은 이진 탐색(binary search) 알고리즘을 써서 노드 안에서 찾는 키의
  위치를 잡는다. 이진 탐색은 정렬된 데이터에 대해서만 작동한다 — 키가 정렬돼 있지 않으면 이진
  탐색할 수 없다. 이것이 키를 순서대로 유지하고 정렬 불변식을 유지하는 일이 필수인 이유다**
  (4장, p.67).[^petrov2019]
- 반환값의 의미 — **이진 탐색 알고리즘은 정렬된 항목 배열과 찾는 키를 받아 숫자를 돌려준다.
  돌려준 숫자가 양수면 찾는 키가 입력 배열에서 발견됐다는 뜻이고 그 숫자가 배열 안 위치를
  지정한다. 음수 반환값은 찾는 키가 입력 배열에 없다는 뜻이며 삽입 지점(insertion point)을
  준다** (4장, p.67).[^petrov2019]
- **삽입 지점은 주어진 키보다 큰 첫 요소의 인덱스다. 이 수의 절댓값은 순서를 보존하려면 찾는
  키를 삽입해야 하는 인덱스다. 삽입은 삽입 지점부터 요소를 한 자리씩 밀어 삽입될 요소의 공간을
  만드는 식으로 할 수 있다** (4장, p.67).[^petrov2019]
- 상위 레벨에서는 정확한 일치가 목적이 아니다 — **상위 레벨에서의 탐색 대부분은 정확한 일치로
  끝나지 않고, 우리가 관심 있는 것은 탐색 방향이다. 이 경우 찾는 것보다 큰 첫 값을 찾아
  대응하는 자식 링크를 따라 딸린 서브트리로 들어가야 한다** (4장, p.67).[^petrov2019]
- 슬롯 페이지 위에서는 이진 탐색이 한 겹 더 간접적이다 — **B-트리 페이지의 셀은 삽입 순서로
  저장되고 셀 오프셋만이 논리적 요소 순서를 보존한다. 페이지 셀을 이진 탐색하려면 가운데 셀
  오프셋을 고르고, 그 포인터를 따라 셀을 찾고, 이 셀의 키를 찾는 키와 비교해 탐색을 왼쪽으로
  이어갈지 오른쪽으로 이어갈지 정하고, 찾는 요소나 삽입 지점을 찾을 때까지 이 과정을 재귀적으로
  잇는다** (4장, p.67).[^petrov2019]

## 분할과 병합을 위로 전파하기

- **B-트리의 분할과 병합은 상위 레벨로 전파될 수 있다. 그러려면 분할하는 리프 또는 병합하는
  리프 쌍에서 루트 노드로 되짚는 사슬을 순회할 수 있어야 한다** (4장, p.68).[^petrov2019]
- 첫 번째 방법 — **B-트리 노드가 부모 노드 포인터를 포함할 수 있다. 하위 레벨의 페이지는 상위
  레벨에서 참조될 때 언제나 페이지 인(paged in)되므로, 이 정보를 디스크에 영속화할 필요조차
  없다** (4장, p.68).[^petrov2019]
- 그 대가는 형제 포인터와 같다 — **형제 포인터와 마찬가지로 부모 포인터도 부모가 바뀔 때마다
  갱신돼야 한다. 이는 페이지 식별자를 가진 구분 키가 한 노드에서 다른 노드로 옮겨지는 모든
  경우에 일어난다 — 부모 노드의 분할·병합·재균형 중에** (4장, p.68).[^petrov2019]
- 부모 포인터를 다른 데 쓰기도 한다 — **일부 구현(예컨대 WiredTiger)은 교착 상태를 피하려고
  리프 순회에 부모 포인터를 쓴다. 형제 포인터로 리프 노드를 순회하는 대신 알고리즘이 부모
  포인터를 쓴다. 형제를 주소 지정하고 찾으려면 부모 노드에서 포인터를 따라가 하위 레벨로
  재귀적으로 내려간다. 부모를 공유하는 모든 형제를 순회한 뒤 부모 노드의 끝에 닿으면 탐색이
  재귀적으로 위로 계속되어 결국 루트까지 올라갔다가 리프 레벨로 다시 내려온다** (4장,
  p.68).[^petrov2019]
- 두 번째 방법 — **부모 노드 포인터를 저장하고 유지하는 대신, 목표 리프 노드로 가는 경로에서
  순회한 노드를 추적해 두었다가 삽입 중의 연쇄 분할이나 삭제 중의 병합이 생기면 부모 노드
  사슬을 역순으로 따라가는 것이 가능하다** (4장, p.69).[^petrov2019]
- 그것을 브레드크럼이라 부른다 — **구조 변경을 낳을 수 있는 연산(삽입 또는 삭제) 중에는 먼저
  루트에서 리프로 트리를 순회해 목표 노드와 삽입 지점을 찾는다. 연산이 분할이나 병합을 낳을지
  미리 알 수 없으므로(적어도 목표 리프 노드를 찾기 전까지는) 브레드크럼(breadcrumbs)을 모아야
  한다** (4장, p.69).[^petrov2019]
- **브레드크럼은 루트에서 따라간 노드로 가는 참조를 담으며, 분할이나 병합을 전파할 때 그것들을
  역순으로 되짚는 데 쓰인다. 이를 위한 가장 자연스러운 자료 구조는 스택이다. 예컨대
  PostgreSQL은 브레드크럼을 스택에 저장하며 내부적으로 `BTStack`이라 참조한다. 이 스택은
  메모리에 유지된다** (4장, p.69).[^petrov2019]
- **노드가 분할되거나 병합되면 브레드크럼으로 부모로 끌어올려진 키의 삽입 지점을 찾고, 트리를
  되짚어 올라가며 필요하면 상위 레벨 노드로 구조 변경을 전파할 수 있다** (4장,
  p.69).[^petrov2019]
- 예시가 절차를 굳혀 준다 — **루트-리프 순회 중에 방문한 노드와 셀 인덱스를 담은 브레드크럼을
  모은다. 목표 리프 노드가 분할되면 스택 맨 위 항목을 팝해 그 직계 부모를 찾는다. 부모 노드에
  공간이 충분하면 브레드크럼의 셀 인덱스 자리에 새 셀이 덧붙는다**(그 인덱스가 여전히
  유효하다는 가정 아래). **그렇지 않으면 부모 노드도 분할된다. 이 과정은 스택이 비어 루트에
  닿거나 그 레벨에서 분할이 일어나지 않을 때까지 재귀적으로 이어진다** (4장,
  p.69).[^petrov2019]

## 재균형 — 분할을 미루기

- **일부 B-트리 구현은 분할과 병합 연산을 미뤄 그 비용을 상각하려 한다. 레벨 안에서 요소를
  재균형(rebalancing)하거나, 더 점유된 노드에서 덜 점유된 노드로 요소를 옮기며 최대한 미룬 뒤
  마침내 분할이나 병합을 수행한다. 이는 노드 점유율을 개선하는 데 도움이 되고 트리 안의 레벨
  수를 줄일 수 있으나, 재균형의 유지 비용이 잠재적으로 더 든다** (4장, p.70).[^petrov2019]
- **로드 밸런싱은 삽입과 삭제 연산 중에 수행될 수 있다. 공간 활용을 개선하려고 오버플로 시
  노드를 분할하는 대신 요소 일부를 형제 노드 중 하나로 옮겨 삽입 공간을 만든다. 마찬가지로
  삭제 중에도 형제 노드를 병합하는 대신 이웃 노드에서 요소 일부를 옮겨 노드가 최소한 절반은
  차 있도록 할 수 있다** (4장, p.70).[^petrov2019]
- **B\*-트리는 두 형제가 모두 찰 때까지 이웃 노드 사이에 데이터를 계속 분배한다. 그다음
  노드 하나를 반쯤 빈 둘로 분할하는 대신, 알고리즘이 두 노드를 셋으로 분할하며 각각은 3분의 2가
  찬다. SQLite가 구현에서 이 변형을 쓴다** (4장, pp.70–71).[^petrov2019]
- 득실이 명시된다 — **이 접근법은 분할을 미룸으로써 평균 점유율을 개선하지만, 추가적인 추적과
  균형 잡기 로직을 요구한다. 높은 활용률은 더 효율적인 탐색을 뜻하기도 하는데, 트리 높이가 더
  작고 찾는 리프까지의 경로에서 순회할 페이지가 더 적기 때문이다** (4장, p.71).[^petrov2019]
- 부모도 손봐야 한다 — **균형 잡기는 형제 노드의 최소/최대 불변식을 바꾸므로, 그것을 보존하려면
  부모 노드의 키와 포인터를 갱신해야 한다** (4장, p.71).[^petrov2019]
- **로드 밸런싱은 많은 데이터베이스 구현에서 쓰이는 유용한 기법이다. 예컨대 SQLite는
  `balance-siblings` 알고리즘을 구현하는데, 이 절에서 서술한 것과 꽤 가깝다. 균형 잡기는 코드에
  복잡도를 더할 수 있지만 그 사용 사례가 고립돼 있으므로 나중 단계에 최적화로 구현할 수 있다**
  (4장, p.71).[^petrov2019]

## 오른쪽 전용 덧붙이기

- 흔한 워크로드 하나가 최적화의 문을 연다 — **많은 데이터베이스 시스템이 자동 증가하는 단조
  증가 값을 주 인덱스 키로 쓴다. 이 경우는 최적화의 기회를 여는데, 모든 삽입이 인덱스
  끝(가장 오른쪽 리프)에서 일어나므로 대부분의 분할이 각 레벨의 가장 오른쪽 노드에서 일어나기
  때문이다. 게다가 키가 단조 증가하고 덧붙이기 대 갱신·삭제의 비율이 낮다면, 논리프 페이지도
  임의 순서 키의 경우보다 덜 단편화된다** (4장, p.71).[^petrov2019]
- **PostgreSQL은 이 경우를 fastpath라 부른다. 삽입된 키가 가장 오른쪽 페이지의 첫 키보다
  엄격히 크고 그 가장 오른쪽 페이지에 새 항목을 담을 공간이 충분하면, 새 항목이 캐시된 가장
  오른쪽 리프의 적절한 위치에 삽입되고 읽기 경로 전체를 건너뛸 수 있다** (4장,
  p.72).[^petrov2019]
- **SQLite에는 비슷한 개념이 있고 `quickbalance`라 부른다. 항목이 맨 오른쪽 끝에 삽입되고 목표
  노드가 가득 차 있으면**(곧 삽입 시 트리에서 가장 큰 항목이 되면), **재균형이나 노드 분할
  대신 새 가장 오른쪽 노드를 할당하고 그 포인터를 부모에 더한다. 이렇게 하면 새로 만든 페이지가
  거의 비게 되지만**(노드 분할의 반쯤 빈 경우와 달리) **그 노드는 곧 채워질 가능성이 매우 높다**
  (4장, p.72).[^petrov2019]

## 벌크 로딩

- **미리 정렬된 데이터가 있어 그것을 벌크 로드하려 하거나 트리를 재구축해야 한다면**(예컨대
  조각 모음을 위해) **오른쪽 전용 덧붙이기의 착상을 한 걸음 더 밀고 갈 수 있다. 트리 생성에
  필요한 데이터가 이미 정렬돼 있으므로, 벌크 로딩 중에는 트리의 가장 오른쪽 위치에 항목을
  덧붙이기만 하면 된다** (4장, p.72).[^petrov2019]
- **이 경우 분할과 병합을 아예 피하고 아래에서 위로 트리를 구성할 수 있다 — 레벨별로 써 나가거나,
  이미 쓰인 하위 레벨 노드에 대한 포인터가 충분해지는 즉시 상위 레벨 노드를 쓴다** (4장,
  p.72).[^petrov2019]
- 한 구현 방식 — **미리 정렬된 데이터를 리프 레벨에 페이지 단위로 쓰는 것이다**(개별 요소를
  삽입하는 대신). **리프 페이지가 쓰이고 나면 그 첫 키를 부모로 전파하고 상위 B-트리 레벨을
  짓는 일반 알고리즘을 쓴다. 덧붙는 키가 정렬 순서로 주어지므로 이 경우 모든 분할은 가장
  오른쪽 노드에서 일어난다** (4장, p.72).[^petrov2019]
- 아래에서 위로 짓는 것이 왜 이득인가 — **B-트리는 언제나 맨 아래(리프) 레벨부터 지어지므로,
  상위 레벨 노드가 조립되기 전에 완전한 리프 레벨을 다 써 낼 수 있다. 그러면 상위 레벨을 지을
  때 모든 자식 포인터를 손에 쥐고 있게 된다. 이 접근법의 주된 이득은 디스크에서 분할이나
  병합을 수행하지 않아도 된다는 것, 그리고 동시에 구성하는 동안 트리의 최소 부분**(곧 현재
  채우고 있는 리프의 모든 부모)**만 메모리에 유지하면 된다는 것이다** (4장,
  p.72).[^petrov2019]
- **불변 B-트리도 같은 방식으로 만들 수 있지만, 가변 B-트리와 달리 이후 수정을 위한 공간
  오버헤드가 필요 없다 — 트리에 대한 모든 연산이 최종이기 때문이다. 모든 페이지를 완전히 채울
  수 있어 점유율이 좋아지고 결과적으로 성능도 나아진다** (4장, p.72).[^petrov2019]

## 압축

- **원시 비압축 데이터를 저장하는 것은 상당한 오버헤드를 유발할 수 있고, 많은 데이터베이스가
  공간을 아끼려 그것을 압축하는 방법을 제공한다. 여기서 겉보기 트레이드오프는 접근 속도와
  압축률 사이다 — 더 큰 압축률은 데이터 크기를 개선해 한 번의 접근으로 더 많은 데이터를 가져오게
  하지만, 압축과 해제에 더 많은 RAM과 CPU 사이클을 요구할 수 있다** (4장,
  p.73).[^petrov2019]
- **압축은 서로 다른 세분성(granularity) 수준에서 할 수 있다. 파일 전체를 압축하면 더 나은
  압축률을 낼 수 있지만 적용 범위가 제한적이다 — 갱신 때마다 파일 전체를 다시 압축해야 하고,
  더 세분화된 압축이 대개 큰 데이터셋에 더 잘 맞기 때문이다. 인덱스 파일 전체를 압축하는 것은
  비실용적이면서 효율적으로 구현하기도 어렵다 — 특정 페이지를 주소 지정하려면 파일 전체(또는
  압축 메타데이터를 담은 그 섹션)에 접근해 압축된 섹션의 위치를 잡고, 압축을 풀고, 쓸 수 있게
  만들어야 하기 때문이다** (4장, p.73).[^petrov2019]
- **대안은 데이터를 페이지 단위로 압축하는 것이다. 지금까지 논의한 알고리즘이 고정 크기
  페이지를 쓰므로 우리 논의에 잘 맞는다. 페이지는 서로 독립적으로 압축되고 해제될 수 있어
  압축을 페이지 적재와 플러싱에 결합할 수 있다** (4장, p.73).[^petrov2019]
- 다만 블록 경계가 값을 부른다 — **압축된 페이지는 디스크 블록의 일부만 차지할 수 있고 전송이
  대개 디스크 블록 단위로 이뤄지므로 추가 바이트를 채워야 할 수 있다. 압축된 페이지가 디스크
  블록보다 작으면 그 페이지를 적재할 때 다른 페이지에 속하는 추가 바이트도 함께 페이징되고,
  페이지가 여러 디스크 블록에 걸치면 블록을 하나 더 읽어야 한다** (4장, p.73).[^petrov2019]
- **또 다른 접근법은 데이터만 압축하는 것으로, 행 단위**(데이터 레코드 전체를 압축)**로 하거나
  열 단위**(열을 개별적으로 압축)**로 한다. 이 경우 페이지 관리와 압축이 분리된다** (4장,
  p.73).[^petrov2019]
- 실물 — **이 책을 쓰며 검토한 오픈소스 데이터베이스 대부분은 Snappy·zLib·lz4 같은 가용
  라이브러리를 쓰는 플러그 가능한 압축 방법을 갖는다** (4장, p.74).[^petrov2019]
- 저자가 비교를 하지 않는 이유도 밝혀 둔다 — **압축 알고리즘은 데이터셋과 잠재적 목적(압축률·
  성능·메모리 오버헤드 등)에 따라 다른 결과를 내므로 이 책은 비교와 구현 세부를 다루지 않는다.
  서로 다른 블록 크기에 대해 서로 다른 압축 알고리즘을 평가하는 개관이 여럿 있고, 대개 네 지표에
  초점을 맞춘다 — 메모리 오버헤드·압축 성능·해제 성능·압축률. 압축 라이브러리를 고를 때 이
  지표들을 고려해야 한다** (4장, p.74).[^petrov2019]
