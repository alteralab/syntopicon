# 데이터 생태계와 유스케이스

**목차**: [순환계라는 관점](#순환계라는-관점) · [유스케이스 5종](#유스케이스-5종) · [활동 추적](#활동-추적) · [메시지 교환](#메시지-교환) · [지표와 로그 수집](#지표와-로그-수집) · [커밋 로그](#커밋-로그) · [스트림 처리](#스트림-처리) · [이어지는 페이지](#이어지는-페이지)

하나의 질문: **카프카는 여러 시스템이 뒤엉킨 데이터 환경에서 어떤 자리를 차지하며,
실제로 어떤 일에 쓰이는가.**

## 순환계라는 관점

- 데이터 처리를 위해 구축한 환경에는 많은 애플리케이션이 참여한다. 입력은 데이터를
  만들거나 시스템에 들여오는 애플리케이션이고, 출력은 지표·리포트·기타 데이터
  제품이다 (1장, p.12).[^shapira2021]
- 어떤 구성 요소는 시스템에서 데이터를 읽어 다른 원천의 데이터로 변환한 뒤 다시 데이터
  인프라로 넣는 **루프**를 만든다. 이 과정은 내용·크기·용도가 제각각인 여러 유형의
  데이터에 대해 수행된다 (1장, p.12).[^shapira2021]
- 원문 직인용 (1장, p.12):[^shapira2021]

> Apache Kafka provides the circulatory system for the data ecosystem. It
> carries messages between the various members of the infrastructure, providing
> a consistent interface for all clients.

- 메시지 스키마를 제공하는 시스템과 결합하면 **프로듀서와 컨슈머는 더 이상 어떤
  형태의 밀결합이나 직접 연결도 필요로 하지 않는다.** 업무 사례가 생기고 사라지는 대로
  구성 요소를 붙이고 뗄 수 있고, 프로듀서는 누가 데이터를 쓰는지, 소비 애플리케이션이
  몇 개인지 신경 쓸 필요가 없다 (1장, p.12).[^shapira2021]

## 유스케이스 5종

### 활동 추적

- 링크드인에서 설계될 당시 카프카의 **원래** 유스케이스가 사용자 활동 추적(activity
  tracking)이다 (1장, p.12).[^shapira2021]
- 웹사이트 사용자가 프론트엔드 애플리케이션과 상호작용하면 그 행동에 관한 메시지가
  생성된다 — 페이지 뷰나 클릭 추적 같은 수동적 정보일 수도 있고, 프로필에 정보를
  추가하는 것처럼 더 복잡한 행동일 수도 있다 (1장, pp.12–13).[^shapira2021]
- 이 메시지는 하나 이상의 토픽으로 발행되어 백엔드 애플리케이션이 소비한다 — 리포트
  생성, 기계 학습 시스템 공급, 검색 결과 갱신 등 풍부한 사용자 경험에 필요한 작업을
  수행한다 (1장, p.13).[^shapira2021]
- 같은 웹 이벤트를 데이터 웨어하우스의 팩트로 모델링하는 쪽은
  [클릭스트림 팩트](../concepts/clickstream-facts.md)를 참조 — 카프카가 운반 계층이라면
  그쪽은 착지 계층의 grain·차원 설계다.

### 메시지 교환

- 사용자에게 알림(예: 이메일)을 보내야 하는 애플리케이션에서, 애플리케이션들은
  **형식이나 실제 발송 방법을 신경 쓰지 않고** 메시지를 생산할 수 있다 (1장,
  p.13).[^shapira2021]
- 단일 애플리케이션이 보낼 메시지를 모두 읽어 일관되게 처리한다 (1장,
  p.13):[^shapira2021]
  - 공통 룩앤필로 포매팅(데코레이팅)한다.
  - 여러 메시지를 하나의 알림으로 모아 보낸다.
  - 사용자가 원하는 수신 방식 선호를 적용한다.
- 이렇게 하면 여러 애플리케이션에 기능을 중복 구현할 필요가 없고, 다른 방식으로는
  불가능한 집적(aggregation) 같은 작업도 가능해진다 (1장, p.13).[^shapira2021]

### 지표와 로그 수집

- 여러 애플리케이션이 같은 유형의 메시지를 생산하는 능력이 빛나는 대표 사례다 (1장,
  p.13).[^shapira2021]
- 애플리케이션이 주기적으로 지표를 카프카 토픽에 발행하면 모니터링·경보 시스템이
  소비한다. 하둡 같은 오프라인 시스템에서 성장률 예측 같은 더 장기적인 분석에도 쓸 수
  있다 (1장, p.13).[^shapira2021]
- 로그 메시지도 같은 방식으로 발행해 엘라스틱서치 같은 전용 로그 검색 시스템이나 보안
  분석 애플리케이션으로 보낼 수 있다 (1장, p.13).[^shapira2021]
- 추가 이점: **목적 시스템을 바꿔야 할 때(예: 로그 저장 시스템 교체) 프론트엔드
  애플리케이션이나 집적 방식을 고칠 필요가 없다** (1장, p.13).[^shapira2021]

### 커밋 로그

- 카프카가 커밋 로그 개념에 기반하므로 데이터베이스 변경점을 카프카로 발행할 수 있고,
  애플리케이션은 이 스트림을 지켜봄으로써 실시간 갱신을 쉽게 받는다 (1장,
  p.13).[^shapira2021]
- 이 체인지로그(changelog) 스트림은 데이터베이스 갱신을 원격 시스템으로 복제하거나,
  여러 애플리케이션의 변경점을 하나의 데이터베이스 뷰로 통합하는 데도 쓴다 (1장,
  p.13).[^shapira2021]
- 지속성 있는 보존이 체인지로그의 버퍼가 되어, 소비 애플리케이션에 장애가 나면 다시
  재생(replay)할 수 있다. [로그 압착](../concepts/brokers-and-clusters.md) 토픽을 쓰면
  키별 마지막 변경만 남겨 더 긴 보존을 얻는다 (1장, pp.13–14).[^shapira2021]
- 원천 시스템에서 변경분만 뽑아 오는 DW 쪽 문제와 맞닿는다 —
  [ETL 34 서브시스템](../concepts/etl-subsystems.md)의 변경 데이터 캡처(CDC)가 그 자리다.

### 스트림 처리

- 거의 모든 카프카 사용을 스트림 처리로 볼 수 있지만, 이 용어는 대체로 **하둡의
  맵리듀스와 비슷한 기능을 제공하는 애플리케이션**을 가리킨다 (1장,
  p.14).[^shapira2021]
- 대비의 축은 시간 범위다: 하둡은 보통 시간·일 단위의 긴 시간대에 걸친 집적에
  의존하는 반면, **스트림 처리는 메시지가 생산되는 즉시 실시간으로 데이터를 다룬다**
  (1장, p.14).[^shapira2021]
- 스트림 프레임워크는 카프카 메시지 위에서 도는 작은 애플리케이션을 쓰게 해준다 —
  지표 세기, 다른 애플리케이션의 효율적 처리를 위한 메시지 파티셔닝, 여러 원천의
  데이터를 사용한 메시지 변환 등 (1장, p.14).[^shapira2021]
