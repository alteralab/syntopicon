# DV 참조 테이블

하나의 질문: **비즈니스 키가 아닌 코드·분류 데이터를 Data Vault에서 어디에 두나.**

참조 테이블(reference table)은 Data Vault 코어 아키텍처(허브·링크·새틀라이트) 밖의 엔터티 타입이지만 실무에서 자주 쓰인다. 다른 비즈니스 키를 설명하는 맥락 정보 — 표준 코드, 설명, 분류 — 를 담는다 (§6.3, pp.184–185).[^linstedt2016]

## 왜 허브가 아닌가: 참조 데이터의 성질

- 허브는 비즈니스에서 쓰이는 객체를 식별하는 비즈니스 키의 유일 목록이다 (../concepts/data-vault-hub.md, ../concepts/business-key.md). 그런데 기업 데이터에는 **비즈니스 객체를 참조하지 않아서** 비즈니스 키 자격이 없는 키·코드가 더 있다. 예: ISO 국가 코드(USA, DEU) — 업무에서 쓰이는 코드지만, 국가 자체는 그 조직의 비즈니스 객체가 아니다 (§6.3, p.184).[^linstedt2016]
- 이런 데이터는 특정 정보 상태를 서술하는 기술적(descriptive) 참조 데이터로 쓰이며, 조직이 아니라 외부 기관이 통제하는 경우가 많다. 반면 같은 국가 코드가 다른 조직(예: UN)에서는 비즈니스 키일 수 있다 — 허브 여부는 코드의 본성이 아니라 **그 조직에서의 쓰임**이 정한다 (§6.3, pp.184–185).[^linstedt2016]
- 참조 데이터는 순수하게 기술적이지도 않다 — 다른 정보의 맥락 속에서만 산다. 판매 트랜잭션 없이 국가 코드 목록만 있으면 비즈니스 가치는 0이고, 다른 데이터에 쓰일 때 비로소 서술을 보태 가치를 낸다. 비즈니스 객체가 사용하는 키가 아니므로 허브 구조에 넣지 않는다 (§6.3, p.185).[^linstedt2016]

## 참조 규칙: 링크 없이 새틀라이트에서 코드로

- 참조 테이블의 기본 키는 대리 키(surrogate key)나 해시가 아니라 **기술적 비즈니스 키 자체**(예: Date, 주 약어)다. 새틀라이트와 Business Vault 엔터티가 이 키로 데이터를 참조하기 때문인데, 그래야 읽기 쉽고 시간이 지나도 감사 가능성이 보장된다. 켜기로 했다면 참조 무결성이나 ER 모델(디버깅용)에도 쓸 수 있다 (§6.3.1, pp.187–188).[^linstedt2016]
- 통합 방식: 모델의 적절한 곳 어디서든 참조 테이블의 기본 키를 그대로 쓴다. 가장 큰 쓰임새는 새틀라이트이고 Business Vault 엔터티에서도 쓴다 — 허브·링크를 거치지 않는다. 예: Passenger 허브의 Address 새틀라이트가 USPS 주 약어 코드로 State 참조 테이블을 가리킨다 (§6.3.1, pp.188–189).[^linstedt2016] 새틀라이트 쪽 구조는 ../concepts/data-vault-satellite.md 참조.

> That way, the reference indicates that there is more descriptive information for *State* in the reference table. By doing so, we don’t use readability in the satellite and keep the basic usage of Data Vault entities intact. (§6.3.1, p.189)[^linstedt2016]

- 해시 키를 쓰지 않는 이유도 같은 선상이다: 이력형 참조 테이블에서 Date를 해시하면 해시가 기본 키가 되어야 하고, 그것이 참조 테이블의 사용성(가독성)을 해친다 (§6.3.2, p.190).[^linstedt2016]

## 형태 1: 무이력(no-history) 참조 테이블

- 가장 기본형은 그냥 2·3정규형 테이블이다. 변하지 않거나 아주 드물게 변하는 참조 데이터에 쓴다. 예: 의약품 처방 코드, 증권 거래소 심볼, 진단 코드, VIN 제조사 코드, 달력 날짜·시각, 국제 통화 코드, 미국 주 약어 (§6.3.1, p.185).[^linstedt2016] 단, 변경 빈도는 프로젝트마다 다르다 — 미국 밖에서는 진단 코드가 자주 바뀔 수도 있다 (§6.3.1, p.185).[^linstedt2016]
- 변경 이력이 없으므로 시작일·종료일 컬럼이 없다. 예: 달력 참조 테이블 — Date가 기본 키, Year·Month·Day·DayOfWeek가 속성 (§6.3.1, pp.185–187).[^linstedt2016]
- "이력을 안 남긴다"는 "변경이 없다"가 아니다 — 대부분의 변경이 버그 수정이거나(예: DayOfWeek의 번역·축약) 이력 데이터를 포함한 모든 정보 마트에 소급 반영되어야 하는 종류라, 추적할 필요가 없는 것이다 (§6.3.1, p.186).[^linstedt2016]
- 데이터가 마스터 데이터 관리 시스템(예: MDS)에서 오면 LoadDate·RecordSource를 두되, 이력 추적이 없으므로 사용자 변경이 내용을 덮어쓴다. 어디서도 소싱하지 않는 경우엔 두 컬럼이 필요 없다. 다만 분석용 마스터 데이터에서 소싱하는 것이 좋은 관행이다 — IT 없이 비즈니스 사용자가 직접 편집할 수 있게 되고, 이것이 관리형 셀프서비스 BI의 전제다 (§6.3.1, p.188).[^linstedt2016]

## 형태 2: 이력형(history-based) 참조 테이블

- 참조 데이터도 새틀라이트 데이터처럼 이력화가 필요할 때가 있다 — 보고서를 재출력하거나 과거 시점의 참조 데이터를 봐야 하는 경우 (§6.3.2, p.189).[^linstedt2016]
- 해법은 무이력 참조 테이블에 **표준 새틀라이트를 다는 것**이다. 기본 테이블은 무이력 속성만, 새틀라이트는 이력이 필요한 속성만 든다. 예: Calendar 참조 테이블에 Fiscal Calendar 새틀라이트를 달아 Fiscal Year·Fiscal Quarter를 이력화 — 과거에 회계 달력이 다른 두 조직이 합병했고 과거 보고서로 일해야 하는 경우가 그 요건이다 (§6.3.2, pp.189–190).[^linstedt2016]
- 새틀라이트는 참조 테이블의 기본 키(Date)로 붙되 해시하지 않으며, 그 외에는 표준 DV 2.0 새틀라이트와 같다 — 기본 키의 LoadDate, 종료 처리용 LoadEndDate (§6.3.2, p.190).[^linstedt2016] 기본 엔터티들을 조합해 고급 엔터티를 만드는 DV 2.0 방식의 좋은 예다 (§6.3.2, p.190).[^linstedt2016]

## 형태 3: 코드-설명(code and descriptions) 테이블

- 코드+설명 목록(예: FAA 항공기 운용 코드 N=Normal, U=Utility, …)은 업무 전반에 쓰여 보고서·OLAP 차원 같은 사용자 대면 요소에 반드시 나타나고, 설명을 UI에 통합하면 비상용 사용자의 가용성이 크게 오른다 (§6.3.3, p.191).[^linstedt2016]
- 이런 목록은 많다. 목록마다 참조 테이블을 만드는 대신, 여러 목록을 하나의 범주화된 테이블로 묶는다: 기본 키 = **Group + Code** 복합 키, 속성 = Description. Group이 어느 목록인지(예: StdOpCode, RstOpCode) 식별한다 (§6.3.3, pp.191–194).[^linstedt2016]
- 통상 추가하는 속성: 짧은 설명(차트 캡션용), 정렬 순서(차원 정렬은 알파벳순이 아니라 비즈니스가 정한다), 외부 참조 URL, 소유자, 코멘트 (§6.3.3, p.192).[^linstedt2016]
- 적용 한계: 이 묶음은 참조 데이터들이 같은 데이터 타입·같은 서술 속성을 쓸 때만 가능하다. 구조가 다르면 개별 참조 테이블로 간다 (§6.3.3, p.193).[^linstedt2016]
- 새틀라이트에서 참조하는 두 방식 (§6.3.3.1, p.194):[^linstedt2016]
  - Group+Code 복합 키를 외래 키로(참조 무결성은 선택).
  - 새틀라이트에 Code 컬럼만 두고 Group은 속성이 암묵적으로 결정 — 조회 시 WHERE에 하드코딩 필터를 넣는다. 모델이 코드를 "타입 코딩"한 상위 타입 테이블이므로 수용 가능한 관행이지만, 어느 새틀라이트 속성이 어느 Group인지 문서화가 필요하다.
- 이력이 필요하면 형태 2와 같은 방식으로 새틀라이트를 단다: 이력 추적 속성(ShortDescription, LongDescription)은 새틀라이트로, 무이력 속성(SortOrder)은 기본 테이블에 남긴다. 복합 기본 키이므로 새틀라이트도 Group·Code 두 컬럼을 모두 참조한다 (§6.3.3.1, pp.194–195).[^linstedt2016]

[^linstedt2016]: Linstedt & Olschimke 2016, 6장 "Advanced Data Vault Modeling"
