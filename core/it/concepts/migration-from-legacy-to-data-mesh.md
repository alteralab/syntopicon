## 하나의 질문

**웨어하우스와 레이크를 이미 가진 조직은 무엇을 먼저 하고 무엇을 끝내야 하는가.**

- 이 물음이 필수인 이유가 먼저 적힌다 — **레거시를 이야기하지 않고 데이터 메시의 진화적 실행을
  말할 수 없다. 데이터 메시를 채택하는 조직 다수는 데이터 웨어하우스·데이터 레이크·레이크하우스
  같은 과거 데이터 아키텍처의 구현을 하나 이상 갖고 있고, 중앙집중 데이터 팀을 가진 중앙집중
  거버넌스 구조를 갖고 있을 가능성이 크다. 데이터 메시 실행은 그런 레거시 조직 구조·아키텍처·
  기술로부터의 이관을 자기 증분적·진화적 여정에 통합해야 한다** (15장, p.299).[^dehghani2022]

## 일반화가 불가능하다는 선언

- 저자가 범위를 먼저 닫는다 — **그러나 레거시로부터의 이관은 일반화하기 어렵다. 경로가 조직에
  특유한 많은 변수에 크게 의존하기 때문이다: 메시 확립이 새 환경(예: 새 클라우드 제공자)으로의
  이전과 겹칠 경우 새 인프라로 이관하는 시간 제약, 초기 채택자 도메인의 규모와 수, 플랫폼에
  가용한 투자 등등** (15장, p.299).[^dehghani2022]
- 그래서 내놓는 것의 지위 — **특정 상태에서 데이터 메시로 가는 이관 전략을 펼치는 것은 이 책의
  범위 밖이고, 조직과의 긴밀한 협업과 그 고유 맥락에 대한 이해를 요구한다. 그러나 내가 공유할 수
  있는 것은 지금까지의 내 경험에서 나온 고수준 교훈 목록이다. **여기에는 배울 것이 훨씬 더
  많다**** (15장, p.300).[^dehghani2022] 곧 아래 다섯은 방법론이 아니라 경험칙이다.

## ① 중앙집중 데이터 아키텍처는 데이터 메시와 공존하지 않는다 — 과도기가 아니라면

- 자주 받는 질문에 대한 답이 짧다 — **나는 조직이 만들어 온 기존 웨어하우스·레이크·레이크하우스가
  메시와 공존할 수 있는지 자주 질문받는다. 짧은 답은 **과도적으로는 그렇고, 궁극적으로는
  아니다**** (15장, p.300).[^dehghani2022]
- 근거 — **어떤 증분적 이관이든 옛것과 새것이 동시에 공존하는 기간을 요구할 것이다. 그러나
  데이터 메시의 목표는 레이크와 웨어하우스의 병목을 제거하는 것이다. 탈중앙 데이터 프로덕트가
  **중앙집중되고 공유되는** 웨어하우스와 레이크를 대체한다. 따라서 목표 아키텍처는 중앙집중
  병목이 데이터 메시와 공존하도록 의도하지 않는다** (15장, p.300).[^dehghani2022]
- **방향이 판정을 가른다** — 안티패턴 쪽 — **예컨대 중앙집중 데이터 웨어하우스나 레이크를
  유지하고 그 하류에서 데이터 메시에 데이터를 먹이는 것은 안티패턴이다. 이 경우 데이터 메시는
  더해진 복잡성이고, 도메인에서 데이터를 걷는 웨어하우스라는 병목은 남는다** (15장,
  p.300).[^dehghani2022]
- 허용되는 쪽 — **대안으로, 과도적 단계로서 데이터 메시 구현이 웨어하우스에 데이터를 먹이고,
  그 웨어하우스가 여전히 웨어하우스를 쓰는 통제된 소수의 레거시 사용자에게 리포트를 서빙하는
  것은 가능하다. 모든 레거시 웨어하우스 사용자가 메시로 이관될 때까지 메시와 웨어하우스는
  공존한다. 이관은 계속되고, 웨어하우스 병목의 중앙집중 수준을 낮춘다** (15장,
  p.300).[^dehghani2022]
- 최종 판정 — **아키텍처의 궁극적 목표는 전반적 **중앙집중** 수준을 제거하고 줄이는 것이다.
  따라서 궁극적으로 메시 구현과 **중앙** 데이터 웨어하우스나 레이크는 공존해서는 안 된다**
  (15장, p.300).[^dehghani2022]
  - 곧 갈림은 "웨어하우스가 있느냐"가 아니라 **데이터 흐름에서 웨어하우스가 상류인가 하류인가**다.
    [전사 데이터 웨어하우스](../concepts/enterprise-data-warehouse.md)와
    [데이터 레이크](../concepts/data-lake.md)가 상대편이다.

## ② 중앙집중 데이터 기술은 데이터 메시와 함께 쓸 수 있다

- **아키텍처와 기술을 갈라 놓는다** — **이 책을 쓰는 시점에 데이터 메시 네이티브 기술은 만들어진
  것이 없다. 우리는 채택자가 기존 기술을 커스텀 설정과 그 위에 지은 솔루션으로 활용하는 진화
  단계에 있다** (15장, p.300).[^dehghani2022]
  - 버전 조건: 2022년 출간 시점 — 저자는 데이터 메시 네이티브 기술의 부재를 시점 조건으로 명시한다.
- 처방 — **오늘 내 조언은 기존 기술의 요소들을, 그것들이 자율적이고 분산된 데이터 프로덕트를
  짓고 운영하는 데 방해가 되지 않는 방식으로 활용하라는 것이다. 나는 기존 기술을
  **멀티테넌트(multitenant) 방식**으로 설정하고 운영하기를 제안한다. 예컨대 객체 저장소 같은
  레이크 지향 기술의 기본 요소를 쓰되 저장소의 할당과 접근을 각 데이터 프로덕트의 경계를 기준으로
  설정하라. 비슷하게, 데이터 웨어하우징 기술을 기반 저장소와 SQL 접근 양식으로 활용하되 각
  데이터 프로덕트에 별도 스키마를 배정하라** (15장, pp.300–301).[^dehghani2022]
- 그리고 전제를 확인한다 — **모든 기존 기술이 그런 설정에 적합한 것은 아니다. 되는 것을 활용하라**
  (15장, p.301).[^dehghani2022]
  - 이것이 [기술 선택 기준](../concepts/technology-selection-criteria.md)에 걸리는 조건이다 —
    기술을 갈아치우는 것이 아니라 **테넌시 경계를 데이터 프로덕트에 맞출 수 있는가**로 고른다.
  - 앞선 자기 평가 축이 "중앙집중 데이터 모델링·통제·저장을 **강제하는** 기술"을 탈락시킨 것과
    모순이 아니다 — 강제하지 않고 멀티테넌트로 설정 가능한 기술만 남는다는 뜻이다
    ([데이터 메시 실행 프레임워크](../concepts/data-mesh-execution-framework.md)).

## ③ 레이크와 웨어하우스를 우회해 소스로 직행하라

- 최소 저항 경로를 명시적으로 거부한다 — **기존 레이크나 웨어하우스에서 이관할 때 최소 저항의
  경로는 웨어하우스나 레이크를 메시의 상류에 놓고, 기존 웨어하우스 테이블에서 데이터를 소비하는
  입력 포트를 가진 데이터 프로덕트를 구현하는 것이다. **내 조언은 이 경로를 택하지 말라는
  것이다.** 대신 레이크나 웨어하우스의 기존 소비자를 발견하고, 그들의 필요와 유스케이스를 인식하고,
  소스 도메인 시스템에서 데이터를 소비하는 새 데이터 프로덕트에 그들을 직접 연결하라** (15장,
  p.301).[^dehghani2022]
- 실행 순서 — **도메인 소유자를 일찍 발견하고, 데이터에 대한 도메인의 진실한 표현에 따라 데이터
  프로덕트를 개발하고, 필요하면 소비자를 갱신하라** (15장, p.301).[^dehghani2022]
- 우회하지 않을 때 치르는 대가가 넷으로 열거된다 — **레이크 파일이나 웨어하우스 테이블을
  대표하는 인공적 데이터 프로덕트를 만드는 것은 메시의 결과 — 도메인에 의한 소유권을 통한 규모
  확장, 소스와 소비자 사이 간극 좁히기 — 를 달성하지 못한다. 그것은 기술 부채를 더 쌓고, 소스와
  소비자 사이에 또 하나의 층을 만들고, 둘 사이 거리를 늘릴 뿐이다** (15장,
  p.301).[^dehghani2022]
  - 이 처방이 [도메인 소유권 원칙](../concepts/domain-ownership-principle.md)의 상류 소유
    조항과 같은 것이다 — 이관 국면에서도 데이터의 출처는 소스 도메인이지 레이크가 아니다.

## ④ 데이터 웨어하우스를 소비 엣지 노드로 써라

- 위 ③의 예외가 소비자 쪽에 있다 — **기존 웨어하우스의 소비자를 평가하다 보면 일부를 웨어하우스에
  남기고 결코 메시로 이관하지 않기로 결정할 수 있다. 이 결정에는 여러 이유가 있다. 예컨대 자주
  바뀌지 않고, 작고 특정한 테이블 집합에 의존하며, 역공학하고 재생성하기 어려운 복잡한 비즈니스
  로직으로 정의된 재무 리포트 같은 리포트는 웨어하우스에 의존한 채로 남을 수 있다** (15장,
  p.301).[^dehghani2022]
- 그때의 배치 — **이 경우 당신은 웨어하우스가 **메시의 소비자**로 행동하고 **엣지 소비 노드(edge
  consuming node)**가 되기를 원한다. 남은 테이블의 작은 집합에 접근하는 제한된 리포트만 두는
  것이다** (15장, p.301).[^dehghani2022]
- ①과 합치면 규칙이 하나로 정리된다 — **웨어하우스는 메시의 하류 잎(leaf)으로만 살아남는다.**

## ⑤ 원자적 진화 단계로 이관하라

- 시간 규모부터 인정한다 — **데이터 웨어하우스나 레이크로부터의 이관은 조직 규모에 따라 여러 진화
  이터레이션과 아마도 수개월 또는 수년이 걸릴 가능성이 크다** (15장, p.301).[^dehghani2022]
- 단위의 정의 — **나는 **원자적 진화 단계(atomic evolutionary steps)**로 이관을 실행하기를
  강력히 제안한다. 단계가 완료되었을 때 시스템의 상태가 기술 부채와 아키텍처 엔트로피가 **더
  적은** 채로 남는 단계다** (15장, p.301).[^dehghani2022]
- 실제로 무시된다는 관찰 — **논리적이고 자명해 보일지 모르지만 이것은 흔히 무시된다. 팀은 옛
  파이프라인이나 레이크 파일을 뒤에 남긴 채 새 인프라와 데이터 프로덕트를 계속 더하기만 한다.
  시간이 지나면 그들은 새것과 남겨진 옛 시스템을 유지하는 아키텍처 복잡성과 총소유비용을 더할
  뿐이다. 이 공존의 주된 이유는 **우리가 사용자와 소비자를 새 구성 요소로 이관하는 데 자주
  실패한다**는 것이다** (15장, p.301).[^dehghani2022]
- 원자적 단계의 구성이 열거된다 — **예컨대 새 데이터 프로덕트 집합을 만들고 있다면 레이크나
  웨어하우스의 기존 소비자 — 리포트나 ML 모델 — 를 그것들로 이관할 시간을 반드시 확보하라.
  이관의 원자적 단계는 새 소스 정렬·집계·소비자 정렬 데이터 프로덕트를 더하는 것, 소비자를 새
  데이터 프로덕트로 이관하는 것, 그리고 레이크·웨어하우스의 테이블·파일·파이프라인을 폐기하는
  것을 포함한다. **이관 단계는 이 단계들이 모두 일어날 때 완료되며, 일부가 완료되지 않으면
  전부 되돌린다.** 이 원자적 단계의 끝에서 아키텍처 엔트로피가 줄어든다** (15장,
  pp.301–302).[^dehghani2022]
- 미완의 정의를 뒤집어 다시 적는다 — **역으로, 새 데이터 프로덕트를 만든 뒤 소비자를 이관하지
  않거나 기존 파이프라인과 레이크 파일을 폐기하지 않으면 원자적 이관 단계는 완료되지 않은
  것이다. 프로젝트 일정과 자원 배분이 **이관의 원자적 단계**에 헌신하도록 정렬되어 있는지
  확인하라** (15장, p.302).[^dehghani2022]
- **다른 소스의 점진적 이관 처방과 나란히 놓인다** —
  [재처리와 점진적 마이그레이션](../concepts/reprocessing-and-gradual-migration.md)은 옛
  뷰와 새 뷰를 파생 뷰로 나란히 돌리고 사용자 비율을 조금씩 옮기라고 처방한다. 두 처방은
  대립하지 않는다 — Kleppmann 쪽은 **단계 안에서의 안전한 전환 방식**을, 저자는 **단계의
  완료 조건**을 말한다. 조건은 시간 축이다: 이행 중의 공존은 둘 다 허용하고, 이행이 끝났는데
  남은 공존은 저자만 금지한다.

## 15장이 스스로 남기는 요약

저자의 마무리가 그린필드와 브라운필드의 비율을 밝힌다 (15장, p.302):[^dehghani2022]

- **데이터 메시 실행은 더 큰 데이터 전략의 일부이며 사실 그 전략의 주요 구성 요소다. 그것은
  데이터가 비즈니스 목표에 정렬되어 어떻게 가치를 생성하는지의 가설을 정의하는, 비즈니스 지향
  전략적 이니셔티브를 필요로 한다.**
- **점 솔루션으로 데이터 주도 비즈니스 결과를 전달하는 것과 여러 유스케이스에 걸친 장기 공유
  플랫폼을 짓는 것 사이의 균형은 여전히 도전이다. 장기 채택 로드맵에 기반한 진화적 접근과 장기
  목표에 따라 구현의 적합성을 재는 함수 같은 도구가 평형을 세우고 실행을 진화적 방식으로 성숙한
  상태로 안내하도록 돕는다.**
- **드문 경우에 조직은 그린필드 데이터 메시 구현을 만들 기회를 갖는다. **다수의 경우 브라운필드
  실행이 데이터 웨어하우스·레이크·레이크하우스 같은 기존 아키텍처로부터의 이관을 감안해야
  한다.** 이 경우 옛 아키텍처와 조직을 이관하는 것은 데이터 소비자와 제공자, 그리고 그 사이의
  모든 것을 메시 쪽으로 옮기는 원자적 진화 단계를 실행하는 데 달려 있다.**
