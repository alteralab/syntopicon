하나의 질문: **내가 통제하지 못하는 시스템에서 데이터를 받아야 할 때, 무엇을 먼저 알아야
하는가.**

## 소유하지 않는 시스템에서 시작한다

- 정의 — **원천 시스템(source system)은 데이터 엔지니어링 수명 주기에서 쓰이는 데이터의
  기원이다. 예컨대 IoT 장치, 애플리케이션 메시지 큐, 트랜잭션 데이터베이스가 원천
  시스템일 수 있다** (2장, p.35).[^reis2022]
- 이 단계를 규정하는 비대칭 — **데이터 엔지니어는 원천 시스템에서 데이터를 소비하지만
  보통 원천 시스템 자체를 소유하거나 통제하지 않는다** (2장, p.35).[^reis2022]
- 그래서 요구되는 것 — **데이터 엔지니어는 원천 시스템이 작동하는 방식, 데이터를 생성하는
  방식, 데이터의 빈도와 속도(velocity), 그것이 생성하는 데이터의 다양성에 대해 작동 수준의
  이해를 가져야 한다** (2장, p.35).[^reis2022]
- 그리고 통신 채널 — **엔지니어는 파이프라인과 분석을 깨뜨릴 수 있는 변경에 대해 원천 시스템
  소유자와 열린 연락선을 유지해야 한다. 애플리케이션 코드가 어떤 필드의 데이터 구조를 바꿀 수
  있고, 애플리케이션 팀이 백엔드를 완전히 새로운 데이터베이스 기술로 이전하기로 선택할 수도
  있다** (2장, p.35).[^reis2022]
- 난점의 정체 — **데이터 엔지니어링의 주요 도전은 엔지니어가 함께 일하고 이해해야 하는
  데이터 원천 시스템의 현기증 나는 배열이다** (2장, p.35).[^reis2022]
- 한계도 알아야 한다 — **예컨대 원천 애플리케이션 데이터베이스에 대한 분석 질의가 자원
  경합과 성능 문제를 일으키지 않겠는가?** (2장, p.37).[^reis2022]
- 5장이 이 단계를 다시 여는 자리 — **원시 데이터를 얻기 전에 데이터가 어디에 존재하고 그것이
  어떻게 생성되며 그 특성과 기벽이 무엇인지 이해해야 한다** (5장, p.155).[^reis2022]
- 저자들이 내다보는 역할 이동 — **데이터가 확산되면서, 특히 데이터 공유의 부상과 함께, 데이터
  엔지니어의 역할이 데이터 소스와 목적지 사이의 상호작용을 이해하는 쪽으로 크게 옮겨 갈 것으로
  기대한다. A에서 B로 데이터를 옮기는 기본 배관 작업은 극적으로 단순해질 것이다. 반면 원천
  시스템에서 데이터가 생성되는 대로 그 본질을 이해하는 것은 여전히 결정적으로 남을 것이다**
  (5장, p.156).[^reis2022]

## 데이터는 어떻게 만들어지는가 — 아날로그와 디지털

- 데이터 자체의 정의부터 — **데이터는 조직되지 않은 맥락 없는 사실과 수치의 모음이다. 그것은
  아날로그와 디지털 양쪽으로 여러 방식으로 만들어질 수 있다** (5장, p.156).[^reis2022]
- **아날로그 데이터(analog data)** — **실세계에서 생성된다. 음성 발화, 수어, 종이에 쓰기,
  악기 연주 같은 것이다. 이 아날로그 데이터는 흔히 덧없다(transient) — 대화가 끝나고 나면
  내용이 허공으로 사라지는 구두 대화를 얼마나 자주 겪었는가** (5장, p.156).[^reis2022]
- **디지털 데이터(digital data)** — **아날로그 데이터를 디지털 형태로 변환해 만들어지거나
  디지털 시스템의 고유 산물이다. 아날로그를 디지털로 바꾸는 예는 아날로그 음성을 디지털
  텍스트로 변환하는 모바일 문자 앱이다. 디지털 데이터 생성의 예는 전자상거래 플랫폼의 신용카드
  거래다 — 고객이 주문하고, 거래가 신용카드에 청구되고, 그 거래 정보가 여러 데이터베이스에
  저장된다** (5장, p.156).[^reis2022]
- 데이터는 도처에 있다 — **이 장에서는 웹사이트나 모바일 애플리케이션과 상호작용할 때 만들어지는
  데이터처럼 흔한 예를 몇 개 쓴다. 그러나 사실 데이터는 우리 주위 세상 어디에나 있다. 우리는
  IoT 장치, 신용카드 단말기, 망원경 센서, 주식 거래 등에서 데이터를 포착한다** (5장,
  p.156).[^reis2022]
- 그래서 첫 행동은 문서를 읽는 것이다 — **원천 시스템과 그것이 데이터를 생성하는 방식에
  익숙해져라. 원천 시스템 문서를 읽고 그 패턴과 기벽을 이해하는 데 노력을 들여라. 원천
  시스템이 RDBMS라면 그것이 어떻게 작동하는지(쓰기·커밋·질의 등) 배워라. 거기서 반입할
  능력에 영향을 줄 수 있는 원천 시스템의 속속들이를 배워라** (5장, p.156).[^reis2022]

## 파일과 비정형 데이터

- 정의 — **파일(file)은 바이트의 시퀀스이며 보통 디스크에 저장된다. 애플리케이션은 흔히
  데이터를 파일에 쓴다. 파일은 로컬 파라미터·이벤트·로그·이미지·오디오를 저장할 수 있다**
  (5장, p.156).[^reis2022]
- 파일이 사라지지 않는 이유 — **덧붙여 파일은 데이터 교환의 보편적 매체다. 데이터 엔지니어가
  데이터를 프로그래매틱하게 얻기를 아무리 바라도 세상의 많은 부분이 여전히 파일을 주고받는다.
  예컨대 정부 기관에서 데이터를 받는다면 데이터를 Excel이나 CSV 파일로 내려받거나 이메일로
  파일을 받을 가능성이 높다** (5장, p.157).[^reis2022]
- 마주치는 형식과 그 구조 등급 — **데이터 엔지니어로서 마주칠 주요 소스 파일 형식은 —
  수동으로 생기든 원천 시스템 프로세스의 출력으로 생기든 — Excel·CSV·TXT·JSON·XML이다.
  이 파일들은 자기 기벽이 있고 구조화(Excel·CSV)·반구조화(JSON·XML·CSV)·비구조화(TXT·CSV)
  일 수 있다** (5장, p.157).[^reis2022]
  - 분석용 형식은 여기서 다루지 않는다 — **데이터 엔지니어로서 어떤 형식(Parquet·ORC·Avro
    같은)을 많이 쓰겠지만 그것은 나중에 다루고 여기서는 원천 시스템 파일에 초점을 맞춘다**
    (5장, p.157).[^reis2022] 그 나중의 자리가
    [데이터 인코딩 형식](../concepts/data-encoding-formats.md)이다.
- API도 원천 시스템의 표면이다 — **애플리케이션 프로그래밍 인터페이스(APIs)는 시스템 사이에
  데이터를 교환하는 표준적 방법이다. 이론상 API는 데이터 엔지니어의 데이터 반입 작업을
  단순화한다. 실무에서 많은 API는 여전히 엔지니어가 관리해야 할 상당한 데이터 복잡성을
  노출한다. 다양한 서비스·프레임워크와 API 데이터 반입을 자동화하는 서비스가 부상했음에도
  데이터 엔지니어는 흔히 맞춤 API 연결을 유지보수하는 데 상당한 에너지를 투자해야 한다**
  (5장, p.157).[^reis2022] API 각각의 성격은
  [웹 서비스와 REST](../concepts/web-services-and-rest.md)에 있다.

## 두 원형 — 애플리케이션 데이터베이스와 IoT 스웜

- 전통형 — **데이터베이스가 뒷받침하는 여러 애플리케이션 서버. 이 원천 시스템 패턴은
  관계형 데이터베이스 관리 시스템(RDBMS)의 폭발적 성공과 함께 1980년대에 인기를 얻었고,
  소프트웨어 개발 실무의 여러 현대적 진화와 함께 오늘날에도 여전히 인기 있다. 예컨대
  애플리케이션은 흔히 단일 모놀리스가 아니라 마이크로서비스를 갖춘 작은 서비스·데이터베이스
  쌍 여럿으로 이뤄진다** (2장, p.35).[^reis2022]
- 최근형 — **IoT 스웜(swarm): 장치의 무리가 중앙 수집 시스템으로 데이터 메시지를 보낸다.
  센서·스마트 장치 같은 IoT 장치가 야생에서 늘어나면서 이 원천 시스템은 점점 흔해지고
  있다** (2장, p.36).[^reis2022]
- 그 밖의 원천 — **원천은 하류 시스템이 소비할 데이터를 생산하며, 사람이 만든 스프레드시트,
  IoT 센서, 웹·모바일 애플리케이션이 여기 든다. 각 원천은 고유한 데이터 생성 볼륨과
  박자(cadence)를 갖는다** (2장, p.37).[^reis2022]
- 애플리케이션 데이터베이스의 정의 — **애플리케이션 데이터베이스(application database)는
  애플리케이션의 상태를 저장한다. 표준적 예는 은행 계좌의 잔고를 저장하는 데이터베이스다.
  고객 거래와 지불이 일어나면 애플리케이션이 은행 계좌 잔고를 갱신한다** (5장,
  p.157).[^reis2022] 그 시스템 유형의 이름과 성질은
  [트랜잭션과 ACID](../concepts/acid-transactions.md)에 있다.

## 원천 시스템 평가 질문

- 평가의 축 — **원천 시스템이 반입·상태·데이터 생성을 어떻게 다루는지를 포함해 고려할 것이
  많다.** 저자들이 출발점으로 제시하는 질문 목록 (2장, pp.36–37):[^reis2022]
  - **데이터 원천의 본질적 특성은 무엇인가? 애플리케이션인가? IoT 장치의 무리인가?**
  - **데이터는 원천 시스템에서 어떻게 영속화(persisted)되는가? 장기 보존되는가, 아니면
    임시로 두었다가 빠르게 삭제되는가?**
  - **데이터는 어떤 속도로 생성되는가? 초당 몇 이벤트인가? 시간당 몇 기가바이트인가?**
  - **출력 데이터에서 어느 수준의 일관성을 기대할 수 있는가? 데이터 품질 검사를 돌린다면
    불일치 — 기대하지 않은 자리의 널, 형편없는 포매팅 등 — 는 얼마나 자주 일어나는가?**
  - **오류는 얼마나 자주 발생하는가? 데이터에 중복이 들어 있겠는가?**
  - **일부 데이터 값이 늦게, 어쩌면 동시에 생산된 다른 메시지보다 훨씬 늦게 도착하겠는가?**
  - **반입되는 데이터의 스키마는 무엇인가? 데이터의 완전한 그림을 얻으려면 여러 테이블,
    심지어 여러 시스템에 걸쳐 조인해야 하는가?**
  - **스키마가 바뀌면(예컨대 새 컬럼 추가) 그것은 어떻게 처리되고 하류 이해관계자에게
    어떻게 전달되는가?**
  - **원천 시스템에서 데이터를 얼마나 자주 끌어와야 하는가?**
  - **상태를 갖는 시스템(예: 고객 계정 정보를 추적하는 데이터베이스)에서 데이터는 주기적
    스냅샷으로 제공되는가, 변경 데이터 캡처(change data capture, CDC)의 갱신 이벤트로
    제공되는가? 변경이 수행되는 로직은 무엇이고 그것은 원천 데이터베이스에서 어떻게
    추적되는가?**
  - **하류 소비를 위해 데이터를 전송할 데이터 제공자는 누구·무엇인가?**
  - **데이터 원천에서 읽는 것이 그 성능에 영향을 주는가?**
  - **원천 시스템에 상류 데이터 의존이 있는가? 그 상류 시스템의 특성은 무엇인가?**
  - **지각하거나 누락된 데이터를 검사할 데이터 품질 검사가 자리 잡혀 있는가?**

## 스키마 — 가장 까다로운 뉘앙스

- **원천 데이터의 가장 도전적인 뉘앙스 중 하나는 스키마다. 스키마는 데이터의 계층적 조직을
  정의한다. 논리적으로 우리는 데이터를 원천 시스템 전체 수준에서 생각해 개별 테이블로,
  나아가 각 필드의 구조까지 파고들 수 있다** (2장, p.37).[^reis2022]
- 두 갈래 — **원천 시스템에서 실려 오는 데이터의 스키마는 여러 방식으로 다뤄진다. 인기 있는
  두 선택지는 스키마리스(schemaless)와 고정 스키마(fixed schema)다** (2장,
  p.37).[^reis2022]
- **스키마리스는 스키마의 부재를 뜻하지 않는다. 오히려 애플리케이션이 데이터를 쓸 때 —
  메시지 큐든, 평문 파일이든, 블롭이든, 몽고DB 같은 문서 데이터베이스든 — 스키마를 정의한다는
  뜻이다. 관계형 데이터베이스 저장 위에 지은 더 전통적인 모델은 데이터베이스에서 강제되는
  고정 스키마를 쓰고, 애플리케이션 쓰기는 거기에 부합해야 한다** (2장, p.37).[^reis2022]
  이 구분을 저장 층위를 가리지 않는 일반 어휘로 다시 세운 것이
  [읽기 스키마와 쓰기 스키마](../concepts/schema-on-read-and-schema-on-write.md)다.
- 어느 쪽이든 남는 문제 — **두 모델 중 어느 쪽도 데이터 엔지니어에게 도전을 안긴다.
  스키마는 시간에 따라 바뀌고, 실제로 소프트웨어 개발의 애자일 접근에서는 스키마 진화가
  장려된다. 데이터 엔지니어 일의 핵심 부분은 원천 시스템 스키마의 원시 데이터 입력을 받아
  분석에 유용한 출력으로 변환하는 것인데, 원천 스키마가 진화하면서 이 일은 더 어려워진다**
  (2장, p.37).[^reis2022] 그 진화를 형식 층위에서 감당하는 방법은
  [인코딩과 진화](../synthesis/encoding-and-evolution.md)에 있다.

## 원천 데이터베이스를 이해하는 일곱 축

저자들이 원천 시스템 데이터베이스 기술을 이해할 때 가로지르는 주요 고려사항 (5장,
p.166):[^reis2022]

- **데이터베이스 관리 시스템(database management system)** — **데이터를 저장하고 서빙하는 데
  쓰이는 데이터베이스 시스템. DBMS로 줄여 쓰며, 저장 엔진·질의 최적화기·재해 복구, 그리고
  데이터베이스 시스템을 관리하는 다른 핵심 구성 요소로 이뤄진다.** 그 내부 구조는
  [데이터베이스 관리 시스템의 구조](../concepts/dbms-architecture.md)에 있다.
- **조회(lookups)** — **데이터베이스는 데이터를 어떻게 찾고 회수하는가? 인덱스가 조회 속도를
  높이는 데 도움이 될 수 있지만 모든 데이터베이스가 인덱스를 갖지는 않는다. 데이터베이스가
  인덱스를 쓰는지 알아 두고, 쓴다면 그것을 설계·유지하는 최선의 패턴이 무엇인지 알아라.
  효율적 추출을 위해 어떻게 활용할지 이해하라. B-트리와 로그 구조 병합 트리(LSM)를 포함한
  주요 인덱스 유형에 대한 기초 지식도 도움이 된다.**
- **질의 최적화기(query optimizer)** — **데이터베이스가 최적화기를 활용하는가? 그 특성은
  무엇인가?**
- **확장과 분산(scaling and distribution)** — **데이터베이스가 수요에 따라 확장되는가? 어떤
  확장 전략을 배치하는가? 수평으로(데이터베이스 노드를 더) 확장하는가, 수직으로(단일 머신에
  자원을 더) 확장하는가?**
- **모델링 패턴(modeling patterns)** — **어떤 모델링 패턴이 이 데이터베이스와 가장 잘
  작동하는가(예: 데이터 정규화나 와이드 테이블)?**
- **CRUD** — **데이터가 데이터베이스에서 어떻게 질의·생성·갱신·삭제되는가? 모든 유형의
  데이터베이스가 CRUD 연산을 다르게 다룬다.**
- **일관성(consistency)** — **데이터베이스가 완전히 일관적인가, 아니면 완화된 일관성 모델(예:
  최종 일관성)을 지원하는가? 데이터베이스가 읽기와 쓰기에 대해 선택적 일관성 모드를
  지원하는가(예: 강하게 일관적인 읽기)?** 그 모델들의 정의는
  [일관성 모델](../concepts/consistency-models.md)에 있다.

- 갈래는 둘로 시작한다 — **우리는 데이터베이스를 관계형과 비관계형 범주로 나눈다. 사실
  비관계형 범주가 훨씬 더 다양하지만, 관계형 데이터베이스는 여전히 애플리케이션 백엔드에서
  상당한 공간을 차지한다** (5장, p.166).[^reis2022] 그 갈래별 서술은
  [관계형 모델과 문서 모델](../concepts/relational-versus-document-model.md)에 있다.

## 실무 세부는 유통기한이 짧다

- 저자들이 5장 후반부에 붙인 경고 — **이 절은 현대 원천 시스템과 상호작용하는 실무적 세부를
  논한다. 흔히 마주치는 데이터베이스·API와 다른 측면의 세부를 파고들 것이다. 이 정보는 앞서
  논한 주요 아이디어보다 유통기한이 짧을 것이다 — 인기 있는 API 프레임워크·데이터베이스와
  다른 세부는 계속 빠르게 바뀔 것이다** (5장, p.165).[^reis2022]
- 그래도 알아야 하는 이유 — **그럼에도 이 세부는 일하는 데이터 엔지니어에게 결정적인
  지식이다. 이 정보를 기준선 지식으로 공부하되 진행 중인 발전을 따라잡기 위해 폭넓게 읽기를
  제안한다** (5장, p.165).[^reis2022]
  - 이 KB에서 그 대응물이 `stale_after`와 `버전 조건:`이다 — 저자들이 "유통기한"이라 부른
    것을 페이지 단위로 기록한다. #hypothesis

## 함께 일할 사람들 — 두 종류의 이해관계자

- 왜 사람 이야기가 여기 있는가 — **원천 시스템에 접근할 때 함께 일할 사람들을 이해하는 것이
  필수다. 우리 경험상 원천 시스템 이해관계자와의 좋은 외교와 관계는 성공적인 데이터 엔지니어링의
  과소평가된 결정적 부분이다** (5장, pp.181–182).[^reis2022]
- 둘로 갈린다 — **보통 두 범주의 이해관계자를 상대한다: 시스템 이해관계자와 데이터
  이해관계자다. 시스템 이해관계자(systems stakeholder)는 원천 시스템을 짓고 유지한다 —
  소프트웨어 엔지니어, 애플리케이션 개발자, 서드파티일 수 있다. 데이터 이해관계자(data
  stakeholder)는 당신이 원하는 데이터에 대한 접근을 소유하고 통제하며, 일반적으로 IT·데이터
  거버넌스 그룹·서드파티가 담당한다. 시스템 이해관계자와 데이터 이해관계자는 흔히 다른
  사람이나 팀이고, 때로는 같다** (5장, p.182).[^reis2022]
- 그래서 데이터 엔지니어의 처지 — **당신은 흔히 이해관계자가 올바른 소프트웨어 엔지니어링·
  데이터베이스 관리·개발 실무를 따르는 능력에 좌우된다. 이상적으로 이해관계자는 DevOps를 하고
  애자일한 방식으로 일하고 있다. 데이터 엔지니어와 원천 시스템 이해관계자 사이에 피드백 루프를
  만들어 데이터가 어떻게 소비되고 쓰이는지에 대한 인식을 형성하기를 제안한다. 이는 데이터
  엔지니어가 많은 가치를 얻을 수 있는 가장 간과된 영역 중 하나다** (5장, p.182).[^reis2022]

## 데이터 계약과 SLA

- 저자들이 인용하는 정의 — 데이터 계약(data contract)에 대해 James Denmore의 서술을 그대로
  옮긴다 (5장, p.182):[^reis2022]

  > A data contract is a written agreement between the owner of a source system and the
  > team ingesting data from that system for use in a data pipeline. The contract should
  > state what data is being extracted, via what method (full, incremental), how often,
  > as well as who (person, team) are the contacts for both the source system and the
  > ingestion. Data contracts should be stored in a well-known and easy-to-find location
  > such as a GitHub repo or internal documentation site. If possible, format data
  > contracts in a standardized form so they can be integrated into the development
  > process or queried programmatically.

  - 계약이 적어야 할 것은 넷이다 — 무엇을 추출하는가, 어떤 방법으로(전체·증분), 얼마나
    자주, 그리고 원천 쪽과 반입 쪽 각각의 연락 담당자가 누구인가.
  - 두는 자리와 형식도 조건이다 — 잘 알려지고 찾기 쉬운 위치(GitHub 저장소나 사내 문서
    사이트)에, 가능하면 개발 프로세스에 통합되거나 프로그래매틱하게 질의될 수 있는 표준
    형식으로.
- 계약 위에 SLA가 얹힌다 — **덧붙여 상류 제공자와 SLA를 맺는 것을 고려하라. SLA는 의존하는
  원천 시스템에서 무엇을 기대할 수 있는지에 대한 기대를 제공한다. SLA의 예는 "원천 시스템의
  데이터가 신뢰할 수 있게 가용하고 높은 품질일 것이다"일 수 있다** (5장, p.183).[^reis2022]
- SLO는 그것을 재는 눈금이다 — **서비스 수준 목표(service-level objective, SLO)는 SLA에서
  합의한 것에 대해 성능을 측정한다. 예컨대 앞의 SLA가 주어지면 SLO는 "원천 시스템이 99%
  가동 시간을 가질 것"일 수 있다** (5장, p.183).[^reis2022] 두 낱말의 일반 정의는
  [서비스 수준 목표](../concepts/service-level-objectives.md)에 있다.
- 형식이 없어도 기대치는 세운다 — **데이터 계약이나 SLA·SLO가 너무 형식적으로 보인다면 적어도
  가동 시간·데이터 품질, 그리고 당신에게 중요한 다른 무엇이든에 대한 원천 시스템 보증의 기대를
  말로라도 정하라. 원천 시스템의 상류 소유자는 당신이 필요로 하는 데이터를 제공할 수 있도록
  당신의 요구사항을 이해할 필요가 있다** (5장, p.183).[^reis2022]

## 저류가 원천 시스템에 거는 조건

- 전제 — **데이터 엔지니어링 수명 주기의 다른 부분과 달리 원천 시스템은 일반적으로 데이터
  엔지니어의 통제 밖에 있다. 원천 시스템의 이해관계자와 소유자 — 그리고 그들이 생산하는
  데이터 — 가 데이터 관리·DataOps(그리고 DevOps)·DODD·데이터 아키텍처·오케스트레이션·소프트웨어
  엔지니어링에 관한 모범 사례를 따르고 있으리라는 암묵적 가정(어떤 이는 희망이라 부를)이 있다.
  데이터 엔지니어는 원천 시스템에서 데이터가 생성될 때 저류가 적용되도록 가능한 한 많은 상류
  지원을 받아야 한다. 그렇게 하면 데이터 엔지니어링 수명 주기의 나머지 단계가 훨씬 매끄럽게
  진행될 것이다** (5장, p.183).[^reis2022] 저류 여섯의 목록은
  [데이터 엔지니어링의 저류](../concepts/data-engineering-undercurrents.md)에 있다.
- **보안** — **보안은 결정적이고, 원천 시스템에 취약점 지점을 우연히 만드는 것은 가장 원치
  않는 일이다** (5장, p.183). 고려할 영역 (5장, p.183):[^reis2022]
  - **원천 시스템이 저장 중 데이터와 전송 중 데이터 양쪽에서 데이터가 안전하고 암호화되도록
    아키텍처돼 있는가?**
  - **원천 시스템에 공용 인터넷으로 접근해야 하는가, 아니면 가상 사설망(VPN)을 쓰는가?**
  - **원천 시스템의 비밀번호·토큰·자격 증명을 안전하게 잠가 두라. 예컨대 SSH 키를 쓴다면
    키 매니저를 써서 키를 보호하라. 비밀번호도 같은 규칙이다 — 비밀번호 관리자나 단일 로그인
    (SSO) 제공자를 쓰라.**
  - **원천 시스템을 신뢰하는가? 원천 시스템이 정당한지 늘 신뢰하되 검증하라. 악의적 행위자가
    보낸 데이터를 받는 쪽이 되고 싶지는 않을 것이다.**
- **데이터 관리** — **원천 시스템의 데이터 관리는 데이터 엔지니어에게 도전적이다. 대부분의
  경우 원천 시스템과 그것이 생산하는 데이터에 대해 주변적 통제만 — 통제가 있기라도 하다면 —
  갖는다. 가능한 한 원천 시스템에서 데이터가 어떻게 관리되는지 이해해야 하는데, 이것이
  데이터를 반입·저장·변환하는 방식에 직접 영향을 주기 때문이다** (5장, p.184).[^reis2022]
  고려할 영역은 여섯이다 (5장, p.184):[^reis2022]
  - **데이터 거버넌스** — **상류 데이터와 시스템이 신뢰할 수 있고 이해하기 쉬운 방식으로
    거버넌스되고 있는가? 누가 데이터를 관리하는가?**
  - **데이터 품질** — **상류 시스템에서 데이터 품질과 무결성을 어떻게 보장하는가? 원천 시스템
    팀과 함께 일해 데이터와 소통에 대한 기대를 세우라.**
  - **스키마** — **상류 스키마가 바뀔 것을 기대하라. 가능한 곳에서는 원천 시스템 팀과 협업해
    다가오는 스키마 변경을 통지받으라.**
  - **마스터 데이터 관리** — **상류 레코드의 생성이 마스터 데이터 관리 실무나 시스템에 의해
    통제되는가?**
  - **프라이버시와 윤리** — **원시 데이터에 접근할 수 있는가, 아니면 데이터가 난독화될
    것인가? 원천 데이터의 함의는 무엇인가? 얼마나 오래 보존되는가? 보존 정책에 따라 위치가
    바뀌는가?**
  - **규제** — **규제에 따라 그 데이터에 접근하도록 돼 있는가?**
- **DataOps** — **운영 탁월성 — DevOps·DataOps·MLOps·XOps — 은 스택 전체의 위아래로 확장돼
  데이터 엔지니어링과 수명 주기를 지원해야 한다. 이것이 이상적이지만 흔히 온전히 실현되지
  않는다** (5장, p.184).[^reis2022]
  - 왜 상류를 관측해야 하는가 — **원천 시스템과 그것이 생산하는 데이터 양쪽을 통제하는
    이해관계자와 일하고 있으므로, 가동 시간과 사용을 관측·모니터링하고 사건이 일어날 때
    대응할 수 있음을 확실히 해야 한다. 예컨대 CDC를 위해 의존하는 애플리케이션 데이터베이스가
    I/O 용량을 초과해 재조정이 필요할 때 그것이 이 시스템에서 데이터를 받는 능력에 어떤 영향을
    주는가?** (5장, p.184).[^reis2022]
  - 고려사항 셋 (5장, p.185):[^reis2022]
    - **자동화** — **코드 갱신과 새 기능처럼 원천 시스템에 영향을 주는 자동화가 있다. 그리고
      데이터 워크플로를 위해 설정한 DataOps 자동화가 있다. 원천 시스템의 자동화에 생긴 문제가
      데이터 워크플로 자동화에 영향을 주는가? 그렇다면 독립적으로 자동화를 수행할 수 있도록
      이 시스템들을 분리하는 것을 고려하라.**
    - **관측 가능성** — **원천 시스템에 중단이나 데이터 품질 문제 같은 이슈가 있을 때 어떻게
      알 것인가? 원천 시스템 가동 시간에 대한 모니터링을 설정하라(또는 원천 시스템을 소유한
      팀이 만든 모니터링을 쓰라). 원천 시스템의 데이터가 하류 사용을 위한 기대에 부합하는지
      확인하는 검사를 설정하라.**
    - **사건 대응** — **나쁜 일이 일어나면 계획이 무엇인가? 예컨대 원천 시스템이 오프라인이
      되면 데이터 파이프라인이 어떻게 행동할 것인가? 원천 시스템이 다시 온라인이 됐을 때
      "잃어버린" 데이터를 백필할 계획은 무엇인가?**
- **데이터 아키텍처** — **데이터 관리와 비슷하게, 원천 시스템 아키텍처의 설계와 유지보수에
  관여하지 않는 한 상류 원천 시스템 아키텍처에 미치는 영향은 거의 없을 것이다. 상류 아키텍처가
  어떻게 설계됐고 그 강점과 약점이 무엇인지도 이해해야 한다** (5장, p.185).[^reis2022]
  고려할 것 넷 (5장, p.186):[^reis2022]
  - **신뢰성** — **모든 시스템은 어느 시점에 엔트로피를 겪고 출력은 기대에서 표류한다. 버그가
    도입되고 무작위 결함이 일어난다. 시스템이 예측 가능한 출력을 내는가? 시스템이 얼마나 자주
    실패할 것으로 예상할 수 있는가? 시스템을 충분한 신뢰성으로 되돌리는 평균 수리 시간은
    얼마인가?**
  - **내구성** — **모든 것은 실패한다. 서버가 죽을 수도, 클라우드의 존이나 리전이 오프라인이
    될 수도, 다른 문제가 생길 수도 있다. 불가피한 실패나 중단이 관리하는 데이터 시스템에
    어떤 영향을 줄지 고려해야 한다. 원천 시스템은 하드웨어 장애나 네트워크 중단으로 인한 데이터
    손실을 어떻게 다루는가? 장기간의 중단을 다루고 중단의 폭발 반경을 제한할 계획은
    무엇인가?**
  - **가용성** — **원천 시스템이 있어야 할 때 켜져 있고 돌아가고 가용하다는 것을 무엇이
    보증하는가?**
  - **사람** — **원천 시스템 설계를 누가 책임지며, 아키텍처에 깨는 변경이 가해졌는지 어떻게
    알 것인가? 데이터 엔지니어는 이 시스템을 유지하는 팀과 함께 일해 이 시스템이 신뢰할 수
    있게 아키텍처됐음을 보장해야 한다. 잠재적 시스템 실패에 대한 기대를 세우기 위해 원천 시스템
    팀과 SLA를 만들라.**
- **오케스트레이션** — **데이터 엔지니어링 워크플로 안에서 오케스트레이션할 때는 주로
  오케스트레이션이 원천 시스템에 접근할 수 있게 만드는 데 관심을 두게 되며, 이는 올바른
  네트워크 접근·인증·인가를 요구한다** (5장, p.186).[^reis2022] 생각할 것 둘 (5장,
  p.186):[^reis2022]
  - **박자와 빈도** — **데이터가 고정된 일정으로 가용한가, 아니면 원할 때마다 새 데이터에
    접근할 수 있는가?**
  - **공통 프레임워크** — **소프트웨어 엔지니어와 데이터 엔지니어가 같은 컨테이너 관리자,
    예컨대 쿠버네티스를 쓰는가? 애플리케이션과 데이터 워크로드를 같은 쿠버네티스 클러스터에
    통합하는 것이 말이 되는가? Airflow 같은 오케스트레이션 프레임워크를 쓴다면 그것을 상류
    애플리케이션 팀과 통합하는 것이 말이 되는가? 여기에 정답은 없지만 통합의 이득과 강한
    결합의 위험을 저울질할 필요가 있다.**
- **소프트웨어 엔지니어링** — **데이터 지형이 원천 시스템 접근을 단순화하고 자동화하는 도구로
  옮겨 가면서도 코드를 써야 할 가능성이 크다** (5장, p.187).[^reis2022] 코드를 쓸 때 고려할
  것 여섯 (5장, p.187):[^reis2022]
  - **네트워킹** — **코드가 원천 시스템이 있는 네트워크에 접근할 수 있는지 확실히 하라. 또한
    늘 보안 네트워킹을 생각하라. 공용 인터넷을 통한 HTTPS URL로 접근하는가, SSH인가,
    VPN인가?**
  - **인증과 인가** — **원천 시스템에 접근할 적절한 자격 증명(토큰·사용자명/비밀번호)이
    있는가? 그것들이 코드나 버전 관리에 나타나지 않도록 어디에 저장할 것인가? 코드화된 작업을
    수행할 올바른 IAM 역할을 갖고 있는가?**
  - **접근 패턴** — **데이터에 어떻게 접근하는가? API를 쓴다면 REST·GraphQL 요청, 응답 데이터
    볼륨, 페이지네이션을 어떻게 다루는가? 데이터베이스 드라이버로 데이터에 접근한다면 드라이버가
    접근하는 데이터베이스와 호환되는가? 두 접근 패턴 어느 쪽이든 재시도와 타임아웃은 어떻게
    다뤄지는가?**
  - **오케스트레이션** — **코드가 오케스트레이션 프레임워크와 통합되며 오케스트레이션된
    워크플로로 실행될 수 있는가?**
  - **병렬화** — **원천 시스템에 대한 병렬 접근을 어떻게 관리·확장하는가?**
  - **배포** — **원천 코드 변경의 배포를 어떻게 다루는가?**

## 원천 시스템은 "남의 문제"가 아니다

- 장의 결론 — **원천 시스템과 그 데이터는 데이터 엔지니어링 수명 주기에서 필수적이다. 데이터
  엔지니어는 원천 시스템을 "남의 문제"로 취급하는 경향이 있다 — 위험을 무릅쓰고 그렇게 하라!
  원천 시스템을 남용하는 데이터 엔지니어는 프로덕션이 내려갈 때 다른 직장을 찾아야 할지도
  모른다** (5장, p.187).[^reis2022]
- 채찍이 있으면 당근도 있다 — **원천 시스템 팀과의 더 나은 협업은 더 높은 품질의 데이터, 더
  성공적인 결과, 더 나은 데이터 제품으로 이어질 수 있다. 이 팀의 상대역과 양방향 소통 흐름을
  만들라. 분석과 ML에 영향을 주는 스키마·애플리케이션 변경을 통지하는 프로세스를 설정하라**
  (5장, pp.187–188).[^reis2022]
- 경계가 흐려지고 있다 — **데이터 엔지니어와 원천 시스템 팀 사이의 통합이 커지고 있음을
  인식하라. 한 예가 리버스 ETL로, 오랫동안 그늘에서 살았지만 최근 두각을 나타냈다. 또한
  이벤트 스트리밍 플랫폼이 이벤트 기반 아키텍처와 분석 양쪽에서 역할을 할 수 있음을 논했다 —
  원천 시스템은 데이터 엔지니어링 시스템이기도 할 수 있다. 말이 되는 곳에서는 공유 시스템을
  지으라** (5장, p.188).[^reis2022]
