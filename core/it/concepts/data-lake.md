이 페이지의 질문: **관계형 데이터 웨어하우스가 이미 있는데 왜 파일 저장소가 또
필요해졌고, 그 선택이 무엇을 바꾸는가.**

## 웨어하우스가 감당하지 못한 수요

- 데이터 웨어하우스는 보통 SQL로 질의하는 **관계형** 데이터 모델을 쓰고 전용 BI
  소프트웨어를 얹는다. 업무 분석가가 던지는 종류의 질의에는 잘 맞지만, 데이터
  과학자가 하는 작업에는 덜 맞는다 (1장, p.9).[^kleppmann2026]
  - ML 모델 학습용 형태로의 변환: 테이블의 행과 열을 특징(feature)이라 불리는 수치
    벡터·행렬로 바꾸는 일이며, 학습 성능을 최대화하도록 이 변환을 수행하는 과정을
    특징 공학(feature engineering)이라 부른다. SQL로 표현하기 어려운 커스텀 코드가
    흔히 필요하다.
  - 텍스트에 자연어 처리(NLP)를 적용해 구조화된 정보를 뽑는 일(예: 리뷰의 감성,
    언급된 주제), 사진에서 컴퓨터 비전으로 정보를 뽑는 일.
- SQL 데이터 모델에 ML 연산자를 더하려는 시도도, 관계형 기반 위에 효율적 ML
  시스템을 짓는 시도도 있었지만, 많은 데이터 과학자는 데이터 웨어하우스 같은
  관계형 데이터베이스 안에서 일하기를 선호하지 않는다 — Pandas·scikit-learn 같은
  파이썬 라이브러리, R, Spark 같은 분산 분석 프레임워크를 쓴다 (1장,
  p.9).[^kleppmann2026]

## 정의와 웨어하우스와의 차이

- 정의는 원문 그대로 (1장, pp.9–10):[^kleppmann2026]

> The answer is a *data lake*: a centralized data repository that holds a copy
> of any data that might be useful for analysis, obtained from operational
> systems via ETL processes. The difference from a data warehouse is that a data
> lake simply contains files, without imposing any particular file format, data
> model, or schema.

- 레이크 안의 파일은 Avro·Parquet 같은 파일 형식으로 인코딩된 데이터베이스 레코드
  모음일 수도 있지만, 텍스트·이미지·비디오·센서 판독값·희소 행렬·특징 벡터·게놈
  서열 등 **어떤 종류의 데이터든** 똑같이 담을 수 있다 (1장, p.10).[^kleppmann2026]
- 유연성만이 아니라 값도 싸다. 오브젝트 스토어 같은 범용 파일 저장(commoditized
  file storage)을 쓸 수 있기 때문이다 (1장, p.10).[^kleppmann2026] 그 저장 계층의
  성질은 [클라우드 네이티브 아키텍처](../concepts/cloud-native-architecture.md)
  참조.

## 스시 원칙 — 원시 데이터가 낫다

- ETL 프로세스는 **데이터 파이프라인(data pipeline)** 으로 일반화됐고, 어떤 경우에는
  데이터 레이크가 운영계에서 웨어하우스로 가는 경로의 **중간 기착지**가 됐다 (1장,
  p.10).[^kleppmann2026]
- 데이터 레이크는 운영계가 만들어 낸 "원시(raw)" 형태의 데이터를 관계형 웨어하우스
  스키마로 변환하지 않은 채 담는다. 그러면 데이터의 **소비자마다 자기에게 가장 맞는
  형태로** 원시 데이터를 변환할 수 있다는 이점이 생긴다. 이를 스시 원칙(sushi
  principle)이라 부르기도 한다 — "원시 데이터가 낫다(raw data is better)" (1장,
  p.10).[^kleppmann2026]
- 이 원칙은 KB 안에서 정면으로 부딪히는 자리가 있다. Kimball은 ETL의 부가가치가
  **적재 전** 정제·통합에서 나온다고 보고, 정규화 구조를 사용자 질의에서 차단하라고
  요구한다(→ [ETL 34 서브시스템](../concepts/etl-subsystems.md),
  [Kimball DW/BI 아키텍처](../concepts/kimball-dwbi-architecture.md)). 반면 Linstedt의
  Raw Data Vault는 원천 그대로의 보존을 우선한다(→
  [데이터 품질 관리](../concepts/data-quality-management.md)의 "나쁜 데이터의 가치").
  세 관점을 지우지 말고 병기해 둔다.
  - 다만 Kimball 쪽의 대립각은 겉보기보다 좁다. 같은 저자들이 빅데이터를 다룰 때는
    **분석 시점까지 데이터 구조를 선언하지 않는 데 익숙해지라**고 요구하며 그 이점 넷을
    스시 원칙과 같은 논거로 든다 — 적재 시점에 구조를 이해하지 못했을 수 있고, 내용이
    가변적이며, 자원 집약적 단계를 피할 수 있고, **서로 다른 분석가가 같은 데이터를
    정당하게 다르게 볼 수 있다** (21장, p.540).[^kimball2013] 갈리는 것은 원시 보존
    여부가 아니라 **무엇을 언제 붙이는가**다: Kimball은 구조 선언은 미루되 내구 대리 키와
    차원 부착은 최초 추출 단계에서 하라고 요구한다 (21장, pp.535, 539, 541).[^kimball2013]
    전문은 [빅데이터 분석 실무 지침](../concepts/big-data-analytics-practices.md).

## 이 선택의 이름 — 읽기 스키마

같은 책 3장이 이 선택에 이름을 붙인다. 레이크는 저장소 층위의 사례이고, 그 층위를 가리지 않는
일반 어휘가 3장에 있다.

- 두 이름의 정의 — **읽기 스키마(schema-on-read)는 데이터의 구조가 암묵적이며 데이터를 읽을 때만
  해석되는 것이고, 쓰기 스키마(schema-on-write)는 스키마가 명시적이고 데이터가 쓰일 때
  데이터베이스가 모든 데이터가 그것에 부합하도록 보장하는 관계형 데이터베이스의 전통적
  접근이다** (3장, p.80).[^kleppmann2026]
- "스키마가 없다"는 표현에 대한 경고도 그대로 적용된다 — **스키마리스(schemaless)라는 말은
  오해를 부른다. 데이터를 읽는 코드가 대개 어떤 종류의 구조를 가정하기 때문이다 — 즉 암묵적
  스키마가 있으나 강제되지 않을 뿐이다** (3장, p.80).[^kleppmann2026] 레이크에서도 마찬가지로,
  파일 형식을 강제하지 않는다는 것이 소비자가 아무 구조도 가정하지 않는다는 뜻은 아니다.
- 언제 이 쪽이 유리한지에 대한 조건도 레이크의 논거와 겹친다 — **읽기 스키마 접근은 컬렉션의
  항목들이 전부 같은 구조를 갖지 않을 때 유리하다. 객체의 종류가 많아 각 종류를 자기 테이블에
  두는 것이 실용적이지 않을 때, 그리고 데이터의 구조가 내가 통제할 수 없고 언제든 바뀔 수 있는
  외부 시스템에 의해 결정될 때다** (3장, p.81).[^kleppmann2026] 전문은
  [읽기 스키마와 쓰기 스키마](../concepts/schema-on-read-and-schema-on-write.md)에 있다.

## 레이크 다음에 온 것들

- 분석 실무가 성숙하면서 조직은 분석 시스템과 데이터 파이프라인의 **관리·운영**에
  점점 더 주의를 기울이게 됐고, 그것이 예컨대 DataOps 선언(DataOps Manifesto)에
  담겼다. 이 흐름을 민 것은 부분적으로 거버넌스·프라이버시, 그리고 GDPR·CCPA 같은
  규제 준수 문제였다 (1장, p.10).[^kleppmann2026]
- 분석용 데이터가 파일과 관계형 테이블만이 아니라 **이벤트 스트림**으로도 제공되는
  일이 늘고 있다. 파일 기반 분석은 데이터 변화에 대응하려면 분석을 주기적으로(예:
  일 단위) 다시 돌려야 하지만, 스트림 처리는 분석 시스템이 **초 단위**로 이벤트에
  반응하게 해 준다 — 예컨대 사기·악용 활동을 식별하고 차단하는 데 값어치가 있다
  (1장, p.10).[^kleppmann2026] 운반 계층 쪽은
  [데이터 생태계와 유스케이스](../concepts/kafka-data-ecosystem-and-use-cases.md)
  참조.
- 분석 시스템의 산출물을 거꾸로 운영계에 되돌리는 경우도 있고, 이를 리버스
  ETL(reverse ETL)이라 부르기도 한다. 예: 분석 시스템에서 학습한 ML 모델을
  프로덕션에 배포해 최종 사용자에게 추천을 내보내는 것 — TFX·Kubeflow·MLflow 같은
  전용 도구를 쓴다 (1장, p.10).[^kleppmann2026]

## 한 덩어리였던 웨어하우스가 넷으로 쪼개진다

같은 책 4장이 이 흐름의 **구조적 결과**를 적는다. 레이크가 오브젝트 스토리지 위로 옮겨 가면서
예전에 하나의 시스템이던 것이 교체 가능한 구성 요소로 나뉜다.

- 먼저 클라우드 쪽 배경 — **테라데이터·버티카·SAP HANA 같은 기성 데이터 웨어하우스 벤더는 상용
  라이선스의 온프레미스 배포와 클라우드 기반 솔루션을 함께 제공한다. 그러나 더 많은 고객이
  클라우드로 옮겨 가면서 구글 클라우드의 BigQuery, 아마존 Redshift, 스노우플레이크 같은 클라우드
  전용 데이터 웨어하우스도 널리 채택됐다. 전통적 데이터 웨어하우스와 달리 클라우드 데이터
  웨어하우스는 오브젝트 스토리지나 서버리스 계산 플랫폼 같은 확장 가능한 클라우드 인프라를 활용할
  수 있다** (4장, p.135).[^kleppmann2026]
- 그것이 주는 것 — **클라우드 웨어하우스는 다른 클라우드 서비스와 더 잘 통합되는 경향이 있다.
  예컨대 많은 클라우드 웨어하우스가 자동 로그 반입을 지원하고 구글 클라우드 Dataflow나 AWS Kinesis
  같은 데이터 처리 프레임워크와의 쉬운 통합을 제공한다. 이 웨어하우스들은 질의 계산을 저장 계층과
  분리하기 때문에 더 탄력적이기도 하다. 데이터가 로컬 디스크가 아니라 오브젝트 스토리지에
  영속화되므로 저장 용량과 질의용 계산 자원을 독립적으로 조정하기 쉽다** (4장,
  p.135).[^kleppmann2026]
- 오픈 소스 쪽에서 일어난 일 — **Apache Hive·Trino·Apache Spark 같은 오픈 소스 데이터 웨어하우스도
  클라우드와 함께 진화했다. 분석용 데이터 저장이 오브젝트 스토리지의 데이터 레이크로 옮겨 가면서
  오픈 소스 웨어하우스는 쪼개지기 시작했다. 예전에는 Hive 같은 단일 시스템에 통합돼 있던 다음
  구성 요소들이 2026년 저술 시점에는 흔히 별개 구성 요소로 구현된다** (4장, p.135).[^kleppmann2026]
  - **질의 엔진(query engine)** — **Trino·Apache DataFusion·Presto 같은 질의 엔진은 SQL 질의를
    파싱하고, 실행 계획으로 최적화하고, 데이터에 대해 실행한다. 실행은 대개 병렬 분산 데이터 처리
    태스크를 요구한다. 어떤 질의 엔진은 내장 태스크 실행을 제공하고 다른 것들은 Spark나 Flink 같은
    서드파티 실행 프레임워크를 쓰기로 고른다** (4장, pp.135–136).[^kleppmann2026]
  - **저장 형식(storage format)** — **저장 형식은 테이블의 행이 파일에서 어떻게 바이트로
    인코딩되는지를 정하며, 그 파일은 보통 오브젝트 스토리지나 분산 파일시스템에 저장된다. 이
    데이터는 질의 엔진뿐 아니라 데이터 레이크를 쓰는 다른 애플리케이션도 접근할 수 있다.
    Parquet·ORC·Lance·Nimble이 그런 저장 형식의 예다** (4장, p.136).[^kleppmann2026]
  - **테이블 형식(table format)** — **Parquet과 비슷한 저장 형식으로 쓰인 파일은 한 번 쓰이면 보통
    불변이다. 행 삽입과 삭제를 지원하려고 Apache Iceberg나 데이터브릭스의 Delta 형식 같은 테이블
    형식을 쓸 수 있다. 테이블 형식은 어떤 파일이 테이블을 구성하는지를 정의하는 파일 형식을 테이블
    스키마와 함께 명시한다. 그런 형식은 시간 여행(time travel, 테이블을 과거 시점의 모습으로 질의할
    수 있는 능력)·GC·심지어 트랜잭션 같은 고급 기능도 제공한다** (4장, p.136).[^kleppmann2026]
  - **데이터 카탈로그(data catalog)** — **테이블 형식이 어떤 파일이 테이블을 이루는지 정의하듯,
    데이터 카탈로그는 어떤 테이블이 데이터베이스에 담기는지 정의한다. 카탈로그는 테이블을 만들고
    이름을 바꾸고 지우는 데 쓰인다. 저장 형식·테이블 형식과 달리 스노우플레이크의 Polaris나
    데이터브릭스의 Unity Catalog 같은 데이터 카탈로그는 보통 REST 인터페이스로 질의할 수 있는
    독립 서비스로 돈다. Apache Iceberg도 카탈로그를 제공하며 클라이언트 안에서 또는 별도 프로세스로
    돌 수 있다. 질의 엔진은 테이블을 읽고 쓸 때 카탈로그 정보를 쓴다. 전통적으로 카탈로그와 질의
    엔진은 통합돼 있었지만, 그것들을 분리한 덕분에 데이터 발견·데이터 거버넌스 시스템도 카탈로그의
    메타데이터에 접근할 수 있게 됐다** (4장, p.136).[^kleppmann2026]

## 데이터 레이크 1.0과 그 실패

데이터 엔지니어링 쪽 소스는 1세대 데이터 레이크에 별도의 이름("데이터 레이크 1.0")을 붙이고
그것이 약속을 지키지 못한 경위를 따로 적는다 — 위 [정의와 웨어하우스와의 차이](#정의와-웨어하우스와의-차이)가
말하는 원리가 실무에서 어떻게 어긋났는가의 기록이다.

- 발상 자체 — **빅데이터 시대에 나타난 가장 인기 있는 아키텍처 중 하나가 데이터 레이크다.
  데이터에 빡빡한 구조적 제한을 부과하는 대신, 구조화·비구조화를 막론하고 모든 데이터를 중앙
  위치에 그냥 쏟아부으면 어떤가? 데이터 레이크는 업무를 무한한 데이터의 샘에서 마시게 해방하는
  민주화의 힘이 될 것이라 약속했다. 1세대 데이터 레이크 "데이터 레이크 1.0"은 견실한 기여를
  했지만 대체로 그 약속을 이행하는 데 실패했다** (3장, p.101).[^reis2022]
- 저장 기반이 옮겨 갔다 — **데이터 레이크 1.0은 HDFS로 시작했다. 클라우드가 인기를 얻으면서 이
  데이터 레이크들은 극히 싼 저장 비용과 사실상 무한한 저장 용량을 가진 클라우드 기반 객체 저장소로
  옮겨 갔다. 저장과 연산이 단단히 결합된 모놀리식 데이터 웨어하우스에 기대는 대신, 데이터 레이크는
  어떤 크기·유형의 데이터든 막대한 양을 저장하게 해 준다. 이 데이터를 질의하거나 변환해야 할 때는
  수요에 따라 클러스터를 띄워 거의 무제한의 연산 능력에 접근하고, 맵리듀스·스파크·레이·프레스토·
  하이브 등 당면 태스크에 좋아하는 데이터 처리 기술을 고를 수 있다** (3장, pp.101–102).[^reis2022]
- 실제로 벌어진 일 — **약속과 과대 선전에도 불구하고 데이터 레이크 1.0에는 심각한 결점이 있었다.
  데이터 레이크는 쓰레기 하치장이 됐다. 데이터 늪(data swamp)·다크 데이터(dark data)·WORN 같은
  용어가 한때 유망하던 데이터 프로젝트가 실패하면서 생겨났다. 데이터는 스키마 관리·데이터 카탈로깅·
  발견 도구랄 것이 거의 없는 채로 관리 불가능한 크기로 자랐다. 게다가 원래의 데이터 레이크 개념은
  본질적으로 쓰기 전용이어서, 사용자 레코드의 표적 삭제를 요구하는 GDPR 같은 규제의 도래와 함께
  거대한 골칫거리를 만들었다** (3장, p.102).[^reis2022] 그 반대 압력은 아래
  [반대 압력 — 데이터 최소화](#반대-압력--데이터-최소화)가 다룬다.
- 처리도 어려웠다 — **조인처럼 비교적 평범한 데이터 변환도 맵리듀스 잡으로 코딩하기가 큰
  두통거리였다. 피그·하이브 같은 후속 프레임워크가 데이터 처리 상황을 다소 개선했지만 데이터 관리의
  기본 문제를 다루는 데는 거의 기여하지 못했다. SQL에서 흔한 단순한 데이터 조작 언어(DML) 연산 —
  행의 삭제나 갱신 — 은 구현하기 고통스러웠고 대개 완전히 새 테이블을 만들어 달성됐다. 빅데이터
  엔지니어들이 데이터 웨어하우징 쪽 상대에게 특유의 경멸을 내뿜는 동안, 후자는 데이터 웨어하우스가
  기본 데이터 관리 능력을 기본 제공했고 SQL이 복잡하고 성능 좋은 질의·변환을 쓰는 효율적 도구였음을
  지적할 수 있었다** (3장, p.102).[^reis2022]
- 비용의 약속도 어긋났다 — **데이터 레이크 1.0은 빅데이터 운동의 또 다른 핵심 약속을 이행하는
  데도 실패했다. 아파치 생태계의 오픈 소스 소프트웨어는 독점 MPP 시스템에 대한 수백만 달러짜리
  계약을 피할 수단으로 선전됐다. 값싼 기성 하드웨어가 맞춤 벤더 솔루션을 대체할 것이었다. 실제로는
  하둡 클러스터 관리의 복잡성이 회사로 하여금 높은 급여로 대규모 엔지니어 팀을 고용하도록 강제하면서
  빅데이터 비용이 부풀었다. 회사들은 흔히 벤더에게서 라이선스된 맞춤 하둡 판본을 구매해 노출된
  전선과 날카로운 모서리를 피하고 하둡을 더 사용자 친화적으로 만들 발판 도구 집합을 획득하기로
  했다. 클라우드 저장을 써서 하둡 클러스터 관리를 피한 회사조차 맵리듀스 잡을 쓸 인재에 크게 써야
  했다** (3장, p.102).[^reis2022]
- 그럼에도 과소평가하지 말라고 단서를 단다 — **1세대 데이터 레이크의 효용과 힘을 과소진술하지
  않도록 조심해야 한다. 많은 조직이 데이터 레이크에서 유의한 가치를 찾았다 — 특히 넷플릭스·페이스북
  같은 거대하고 데이터 중심적인 실리콘밸리 기술 회사들이다. 이 회사들은 성공적인 데이터 실무를
  세우고 자체 클라우드 기반 도구와 강화를 만들 자원을 갖고 있었다. 그러나 많은 조직에게 데이터
  레이크는 낭비·실망·치솟는 비용의 내부 슈퍼펀드 오염 부지가 됐다** (3장, p.102).[^reis2022]

## 수렴 — 레이크하우스와 데이터 플랫폼

- **1세대 데이터 레이크의 한계에 대응해 여러 참가자가 그 개념을 강화해 약속을 온전히 실현하려
  했다. 예컨대 Databricks가 데이터 레이크하우스(data lakehouse)의 관념을 도입했다. 레이크하우스는
  데이터 웨어하우스에서 발견되는 통제·데이터 관리·데이터 구조를 통합하면서도 객체 저장소에 데이터를
  두고 다양한 질의·변환 엔진을 지원한다. 특히 데이터 레이크하우스는 원자성·일관성·격리성·지속성
  (ACID) 트랜잭션을 지원하는데, 이는 데이터를 그냥 부어 넣고 결코 갱신·삭제하지 않던 원래 데이터
  레이크에서 크게 이탈한 것이다. 데이터 레이크하우스라는 용어는 데이터 레이크와 데이터 웨어하우스
  사이의 수렴을 시사한다** (3장, p.103).[^reis2022] 그 트랜잭션 성질을 실제로 떠받치는 구조는 위
  [한 덩어리였던 웨어하우스가 넷으로 쪼개진다](#한-덩어리였던-웨어하우스가-넷으로-쪼개진다)에 있다.
- 반대 방향의 수렴도 일어났다 — **클라우드 데이터 웨어하우스의 기술 아키텍처는 데이터 레이크
  아키텍처와 매우 유사해지도록 진화했다. 클라우드 데이터 웨어하우스는 연산을 저장에서 분리하고,
  페타바이트 규모 질의를 지원하고, 다양한 비구조화 데이터와 반구조화 객체를 저장하며, 스파크나 빔
  같은 진보된 처리 기술과 통합된다** (3장, p.103).[^reis2022]
- 전망 — **수렴의 추세는 계속되기만 할 것이라 믿는다. 데이터 레이크와 데이터 웨어하우스는 여전히
  서로 다른 아키텍처로 존재할 것이다. 실무에서 그 능력은 수렴해 일상 작업에서 둘 사이의 경계를
  알아채는 사용자가 거의 없을 것이다. 이제 여러 벤더가 데이터 레이크와 데이터 웨어하우스 능력을
  결합한 데이터 플랫폼(data platform)을 제공하는 것을 본다. 데이터 레이크와 데이터 웨어하우스
  아키텍처 중 하나를 고르는 대신, 미래의 데이터 엔지니어는 벤더·생태계·상대적 개방성을 비롯한
  다양한 요인에 근거해 수렴된 데이터 플랫폼을 고를 선택지를 갖게 될 것이다** (3장,
  p.103).[^reis2022]

## 6장이 더한 것 — 레이크하우스의 메타데이터 계층과 상호운용성

같은 저자들이 6장에서 저장 추상 층을 다시 다루며 위 서술에 세 가지를 더한다.

- 데이터 웨어하우스의 계보를 다시 정리한다 — **데이터 웨어하우스는 표준 OLAP 데이터 아키텍처다.
  3장에서 논했듯 데이터 웨어하우스라는 용어는 기술 플랫폼(예: Google BigQuery와 Teradata),
  데이터 중앙집중화를 위한 아키텍처, 그리고 회사 안의 조직 패턴을 가리킨다. 기술 추세 면에서
  우리는 전통적 트랜잭션 데이터베이스 위의 데이터 웨어하우스 구축에서, 행 기반 MPP 시스템(예:
  Teradata와 IBM Netezza), 컬럼 MPP 시스템(예: Vertica와 Teradata Columnar)을 거쳐 클라우드 데이터
  웨어하우스와 데이터 플랫폼으로 진화했다** (6장, p.215).[^reis2022]
- 클라우드 DW가 레이크를 조직하는 데 쓰이지만 한계가 있다 — **실무에서 클라우드 데이터 웨어하우스는
  흔히 데이터를 데이터 레이크 — 원래 James Dixon이 착상한, 방대한 양의 미처리 원시 데이터를 위한
  저장 영역 — 로 조직하는 데 쓰인다. 클라우드 데이터 웨어하우스는 방대한 양의 원시 텍스트와 복잡한
  JSON 문서를 감당할 수 있다. 한계는 클라우드 데이터 웨어하우스가 진정한 데이터 레이크와 달리
  이미지·비디오·오디오 같은 진정한 비정형 데이터를 감당할 수 없다는 것이다. 클라우드 데이터
  웨어하우스는 완전한 데이터 레이크 해법을 제공하기 위해 오브젝트 저장과 짝지어질 수 있다** (6장,
  p.216).[^reis2022]
- 레이크 저장의 2022년 저술 시점 기준 최근 두 발전 — **지난 5년은 데이터 레이크 저장의 진화에서 두 가지 주요 발전을
  보았다. 첫째, 컴퓨트와 저장의 분리로의 주요 이전이 일어났다. 실무에서 이는 데이터의 장기 보존을
  위해 하둡에서 클라우드 오브젝트 저장으로의 이동을 뜻한다. 둘째, 데이터 엔지니어들이 MPP 시스템이
  제공하던 기능의 상당 부분 — 스키마 관리, 갱신·병합·삭제 능력 — 이, 데이터 레이크로 몰려가는
  와중에 처음에는 기각됐지만, 사실 극도로 유용하다는 것을 발견했다. 이것이 데이터 레이크하우스라는
  관념으로 이어졌다** (6장, p.216).[^reis2022]
- 레이크하우스가 더하는 것 — **일반적으로 착상된 대로 레이크하우스는 레이크와 똑같이 오브젝트
  저장에 데이터를 저장한다. 그러나 레이크하우스는 이 배치에 데이터 관리를 매끄럽게 하고 데이터
  웨어하우스와 비슷한 엔지니어링 경험을 만들도록 설계된 기능을 더한다. 이는 견고한 테이블·스키마
  지원과 증분 갱신·삭제 관리 기능을 뜻한다. 레이크하우스는 일반적으로 테이블 이력과 롤백도 지원하며,
  이는 파일과 메타데이터의 옛 버전을 보존함으로써 달성된다** (6장, p.216).[^reis2022]
- 그 정체는 계층이다 — **레이크하우스 시스템은 데이터 관리·변환 도구와 함께 배치되는 메타데이터·
  파일 관리 계층이다. Databricks가 오픈 소스 저장 관리 시스템인 Delta Lake로 레이크하우스 개념을
  강하게 밀었다** (6장, p.216).[^reis2022]
- 상용 데이터 플랫폼과 아키텍처가 같다 — **데이터 레이크하우스의 아키텍처가 BigQuery와 Snowflake를
  포함한 다양한 상용 데이터 플랫폼에서 쓰이는 아키텍처와 비슷하다는 점을 지적하지 않을 수 없다.
  이 시스템들은 데이터를 오브젝트 저장에 저장하고 자동 메타데이터 관리·테이블 이력·갱신/삭제 능력을
  제공한다. 하부 파일과 저장을 관리하는 복잡성은 사용자에게 완전히 숨겨진다** (6장,
  pp.216–217).[^reis2022]
- **레이크하우스의 핵심 이점은 상호운용성이다** — **독점 도구 대비 데이터 레이크하우스의 핵심
  이점은 상호운용성이다. 데이터가 열린 파일 형식으로 저장돼 있으면 도구 사이에 데이터를 교환하기가
  훨씬 쉽다. 독점 데이터베이스 형식에서 데이터를 재직렬화하는 것은 처리·시간·비용에 오버헤드를
  일으킨다. 데이터 레이크하우스 아키텍처에서는 다양한 도구가 메타데이터 계층에 연결해 오브젝트
  저장에서 데이터를 직접 읽을 수 있다** (6장, p.217).[^reis2022]
- 테이블 구조가 강제되지 않는다는 점도 다시 강조된다 — **데이터 레이크하우스의 데이터 상당 부분이
  테이블 구조를 부과받지 않을 수 있다는 점을 강조하는 것이 중요하다. 우리는 레이크하우스에서
  필요한 곳에 데이터 웨어하우스 기능을 부과하고 다른 데이터는 원시 또는 심지어 비정형 형식으로 둘
  수 있다** (6장, p.217).[^reis2022]
- **데이터 플랫폼** — **점점 벤더는 자기 제품을 데이터 플랫폼(data platforms)으로 꾸미고 있다.
  이 벤더들은 핵심 데이터 저장 계층과 긴밀히 통합된 상호운용 가능한 도구의 생태계를 만들었다.
  플랫폼을 평가할 때 엔지니어는 제공되는 도구가 자기 필요를 충족하는지 확인해야 한다. 플랫폼에
  직접 제공되지 않는 도구도 여전히 상호운용될 수 있지만 데이터 교환에 추가 오버헤드가 든다.
  플랫폼은 비정형 유스케이스를 위해 오브젝트 저장과의 긴밀한 통합도 강조한다** (6장,
  p.217).[^reis2022]
  - 저자들의 유보 — **2022년 저술 시점에 데이터 플랫폼이라는 관념은 솔직히 아직 완전히 살이 붙지 않았다.
    그러나 데이터 도구의 담장 친 정원(walled garden)을 만들려는 경주가 벌어지고 있으며, 이는 데이터
    엔지니어링의 작업을 단순화하는 동시에 유의한 벤더 락인을 만든다** (6장, p.217).[^reis2022]

## 스트림 대 배치 저장 아키텍처

- 무엇과 닮았는가 — **스트림 대 배치 저장 아키텍처(stream-to-batch storage architecture)는
  람다 아키텍처와 많은 유사점을 갖는다 — 기술적 세부를 두고 트집을 잡는 사람도 있겠지만. 본질적으로
  스트리밍 저장 시스템의 토픽을 지나 흐르는 데이터가 여러 소비자로 쓰여 나간다** (6장,
  p.217).[^reis2022] 그 아키텍처는
  [람다 아키텍처와 카파 아키텍처](../concepts/lambda-and-kappa-architecture.md)에 있다.
- 소비자가 갈린다 — **이 소비자 중 일부는 스트림에 대한 통계를 생성하는 실시간 처리 시스템일 수
  있다. 덧붙여 배치 저장 소비자가 장기 보존과 배치 질의를 위해 데이터를 쓴다. 배치 소비자는 설정
  가능한 트리거(예: 시간과 배치 크기)에 근거해 S3 객체를 생성할 수 있는 AWS Kinesis Firehose일 수
  있다** (6장, p.217).[^reis2022]
- BigQuery의 실물 — **BigQuery 같은 시스템은 스트리밍 데이터를 스트리밍 버퍼로 반입한다. 이
  스트리밍 버퍼는 자동으로 컬럼 오브젝트 저장으로 재직렬화된다. 질의 엔진은 사용자에게 테이블의
  현재적이고 거의 실시간인 뷰를 제공하기 위해 스트리밍 버퍼와 객체 데이터 양쪽의 매끄러운 질의를
  지원한다** (6장, p.217).[^reis2022]

## 모던 데이터 스택

- **모던 데이터 스택(modern data stack)은 2022년 저술 시점에 유행하는 분석 아키텍처로, 저자들이 앞으로 몇 년
  동안 더 널리 쓰이리라 예상하는 유형의 추상화를 부각한다. 과거의 데이터 스택이 비싸고 모놀리식한
  도구 모음에 의존했다면, 모던 데이터 스택의 주 목표는 클라우드 기반의 플러그 앤 플레이하고 쓰기
  쉬운 기성 구성 요소를 써서 모듈화되고 비용 효율적인 데이터 아키텍처를 만드는 것이다. 이 구성
  요소에는 데이터 파이프라인·저장·변환·데이터 관리/거버넌스·모니터링·시각화·탐색이 포함된다. 도메인은
  여전히 유동적이고 구체적 도구는 빠르게 바뀌고 진화하고 있지만, 핵심 목표는 그대로 남을 것이다 —
  복잡성을 줄이고 모듈화를 늘리는 것이다** (3장, p.103).[^reis2022] 이 관념은 위
  [수렴 — 레이크하우스와 데이터 플랫폼](#수렴--레이크하우스와-데이터-플랫폼)의 수렴된 데이터 플랫폼
  발상과 잘 통합된다 (3장, p.103).[^reis2022]
- 핵심 산출 — **모던 데이터 스택의 핵심 결과는 셀프서비스(분석과 파이프라인), 애자일한 데이터
  관리, 그리고 오픈 소스 도구나 명확한 가격 구조를 가진 단순한 독점 도구의 사용이다. 커뮤니티도
  모던 데이터 스택의 중심 측면이다. 릴리스와 로드맵이 대체로 사용자에게 감춰져 있던 과거의 제품과
  달리, 모던 데이터 스택 공간에서 운영되는 프로젝트와 회사는 통상 강한 사용자 기반과 활발한
  커뮤니티를 가지며, 이들은 제품을 일찍 쓰고 기능을 제안하고 코드를 개선하는 풀 리퀘스트를 제출하며
  개발에 참여한다** (3장, p.104).[^reis2022]
- 판정 — **"모던"이 어디로 가든, 이해하기 쉬운 가격 책정과 구현을 갖춘 플러그 앤 플레이 모듈성이라는
  핵심 개념이 미래의 길이라고 본다. 특히 분석 엔지니어링에서 모던 데이터 스택은 데이터 아키텍처의
  기본 선택지이며 앞으로도 그럴 것이다** (3장, p.104).[^reis2022]

## 반대 압력 — 데이터 최소화

- 우리가 데이터를 저장하는 이유는 그 가치가 저장 비용보다 크다고 보기 때문이다.
  그러나 **저장의 비용은 청구서를 넘어선다** — 데이터가 유출·탈취됐을 때의 책임과
  평판 손상, 저장·처리가 법을 어긴 것으로 판명될 때의 법적 비용과 과징금까지
  비용편익 계산에 넣어야 한다 (1장, p.25).[^kleppmann2026]
- 정부나 경찰이 데이터 제출을 강제할 수도 있다. 데이터가 범죄화된 행위를 드러낼 수
  있는 곳에서는(저자들이 든 예는 여러 중동·아프리카 국가의 동성애, 미국 여러 주의
  낙태) 그런 데이터를 저장하는 것 자체가 사용자에게 실제 안전 위험을 만든다 —
  위치 데이터나 시간에 따른 IP 주소 로그만으로도 드러날 수 있다 (1장,
  p.25).[^kleppmann2026]
- 위험을 다 계산에 넣고 나면 **어떤 데이터는 아예 저장할 가치가 없고 따라서 지워야
  한다**는 판단이 합리적일 수 있다. 이 원칙을 데이터 최소화(data minimization,
  독일어로 Datensparsamkeit)라 부르며, 나중에 쓸모 있을지 모른다는 이유로 데이터를
  투기적으로 잔뜩 쌓는 "빅데이터" 철학과 **정면으로 어긋난다** (1장,
  p.25).[^kleppmann2026]
- 데이터 최소화는 GDPR과는 맞는다: 개인 데이터는 명시된 명확한 목적으로만 수집할 수
  있고, 이후 다른 목적으로 쓸 수 없으며, 수집 목적에 필요한 기간보다 오래 보관해서는
  안 된다 (1장, p.25).[^kleppmann2026]
- **반대편 처방**: [EDW](../concepts/enterprise-data-warehouse.md)의 "단일 사실
  버전"은 컴플라이언스를 근거로 **모든 원시 데이터를 항상 보관**하자고 말한다. 위의
  데이터 최소화는 같은 컴플라이언스를 근거로 **덜 저장하고 지우자**고 말한다. 다만
  두 처방의 대상이 온전히 같지는 않다 — 전자는 감사 가능성을 위한 업무 데이터,
  후자는 GDPR이 규율하는 개인 데이터다. 겹치는 구간(웨어하우스가 개인 데이터를
  담을 때)에서만 실제로 부딪히며, 그때도 어느 쪽이 참인지가 아니라 어떤 데이터에
  어느 정책을 걸지의 설계 판단이다. 사실 주장의 충돌이 아니므로 `contradicts`는
  달지 않는다(PLAN §2.1).
- 같은 책 14장이 이 원칙을 규제 조문으로 되받고 그 대립을 명시한다 — **GDPR은 개인 데이터가
  "구체적이고 명시적이며 정당한 목적을 위해 수집되고 그 목적과 양립할 수 없는 방식으로 추가
  처리되지 않아야" 하며 "처리되는 목적과 관련해 적절하고 관련성 있으며 필요한 것으로 제한되어야"
  한다고 규정한다** (14장, p.596).[^kleppmann2026] 그리고 **이 데이터 최소화 원칙은 빅데이터의
  철학 — 데이터 수집을 최대화하고, 수집된 데이터를 다른 데이터셋과 결합하고, 새로운 통찰을 생성하기
  위해 실험하고 탐색하는 것 — 과 정면으로 어긋난다. 탐색은 예견되지 않은 목적으로 데이터를 쓰는
  것을 뜻하는데, GDPR은 그것이 데이터가 수집됐어야 하는 "구체적이고 명시적인" 목적의 반대라고
  규정한다** (14장, p.596).[^kleppmann2026] 레이크의 "일단 원시 데이터를 다 모아 두고 나중에
  해석한다"는 전제가 바로 그 탐색이다.
- 14장은 실행 지침도 한 줄 더 준다 — **첫걸음으로 우리는 데이터를 영원히 보관하지 말고 더 이상
  필요 없어지는 즉시 파기하며 애초에 수집하는 것을 최소화해야 한다. 여러분이 갖고 있지 않은
  데이터는 유출되거나, 도난당하거나, 정부에 의해 넘기도록 강제될 수 없는 데이터다** (14장,
  p.597).[^kleppmann2026] 그 논거의 전문은
  [위험 자산으로서의 데이터](../concepts/data-as-a-hazardous-asset.md)에 있다.

## 데이터 메시가 보는 레이크

데이터 메시의 제안자는 레이크를 웨어하우스와 **같은 실패 유형**으로 묶는다 — 둘 다 모놀리식
중앙 소유이기 때문이다. 다만 레이크에 대해서는 별도의 진단이 하나 더 붙는다: **모델링의
부재**와 **코드와 데이터의 분리**다.

- DDD의 어휘로 레이크를 분류한다 — Evans의 전략 설계가 기각한 세 양식 중 **의도적 모델링
  없음**(no intentional modeling)에 해당한다 — **원시 데이터를 블롭 저장소에 쏟아붓는 데이터
  레이크와 비슷하다** (2장, p.18).[^dehghani2022] 위
  [스시 원칙](#스시-원칙--원시-데이터가-낫다)이 원칙으로 삼는 그 선택이 여기서는 진단 대상이
  된다.
- 물의 은유 자체가 비판 대상이 된다 — **데이터 아키텍처 명명법은 생명 그 자체의 원천인 물에서
  번성했다. 데이터 레이크, 레이크쇼어 마트, 데이터플로, 레이크하우스, 데이터 파이프라인, 레이크
  하이드레이션 같은 것들이다. 그러나 그 밑에는 위험한 관념이 도사린다 — 데이터가 유용해지고
  의미를 갖고 가치를 지니고 소비할 가치가 있으려면 원천에서 다른 어딘가(예: 중앙 레이크)로
  흘러가야 한다는 관념이다. 상류의 데이터가 하류의 데이터보다 덜 가치 있거나 덜 유용하다는
  가정이 있다** (2장, p.24).[^dehghani2022]
- 데이터 스왐프를 코드와 데이터의 분리로 설명한다 — **이 관점은 코드(연산)와 데이터의 분리를
  낳는다. 이 분리는 시간이 지나며 썩어 가는 고아 데이터셋을 만든다. 규모에 이르면 우리는 이
  분리를 데이터 스왐프(data swamps) — 퇴화한 데이터 레이크 — 로 경험한다** (3장,
  p.44).[^dehghani2022] 위 [데이터 레이크 1.0과 그 실패](#데이터-레이크-10과-그-실패)가
  현상으로 서술하는 것을, 이쪽은 **원인 진단**으로 옮긴다.
  - 그 진단에서 나오는 처방 — **데이터 대 코드라는 이중 양식에서 데이터와 코드를 하나의 아키텍처
    단위, 곧 단일 배포 단위로 옮긴다. 하나는 다른 하나 없이 존재하지 않는다** (3장,
    p.44).[^dehghani2022]
- 품질 책임의 위치도 웨어하우스와 함께 묶어 판정한다 — **데이터 레이크나 데이터 웨어하우징
  아키텍처에서는 품질과 무결성을 갖춘 데이터를 만드는 책무가 원천의 하류에 있고 중앙 데이터
  팀에 남는다** (3장, p.30).[^dehghani2022]

**8장이 레이크를 세대로 세어 놓는 자리.** 2부 8장은 분석 데이터 아키텍처의 역사를 셋으로 끊고
레이크를 **2세대**로 놓는다 — 1세대는 웨어하우스, 3세대는 멀티모달 클라우드다. 세대론 전체는
[분석 데이터 아키텍처 세대론](../concepts/analytical-data-architecture-generations.md)에 있고,
여기서는 레이크에 직접 걸리는 것만 옮긴다.

- 도입 시점과 동기를 한 문장으로 못 박는다 — **데이터 레이크 아키텍처는 데이터 웨어하우징
  아키텍처의 난제에 대응해 2010년에 도입되었다: 기계 학습 모델 훈련 과정에서 데이터 과학자가
  데이터에 접근하는 것이다. 데이터 과학자는 사업의 현실에 가능한 한 가까운 원래 형태의 데이터를
  필요로 한다. 데이터 과학자는 데이터가 정확히 어떻게 모델링되어야 하는지 예측할 수 없으므로
  원시 데이터에 대한 접근을 선호한다. 더해서 기계 학습 훈련은 대규모로 병렬화된 데이터 읽기를
  요구했다** (8장, p.123).[^dehghani2022] 위
  [스시 원칙](#스시-원칙--원시-데이터가-낫다)이 미각의 은유로 말하는 것을 이쪽은 **ML 훈련의
  요구**로 근거 짓는다 — 같은 선택의 다른 정당화다.
- 사전 변환이 왜 해로운지에 대해서는 레이크 편을 든다 — **사전 변환은 블로커이며 모델 훈련의
  더 느린 반복으로 이어진다. 더해서 그것은 운영 시스템 데이터의 본성을 바꾸고, 변환된 데이터로
  훈련된 모델이 실제 프로덕션 질의에 대해 성능을 내지 못하는 방식으로 데이터를 변이시킨다**
  (8장, p.124).[^dehghani2022] 사례는 음악 추천기다 — **웨어하우스에서 변환·모델링된 데이터로
  훈련되었을 때, 로그인한 청취자의 세션 정보로 추천 서비스가 호출되는 운영 맥락에서 성능을 내지
  못한다. 심하게 변환된 데이터는 청취자 속성 일부를 놓치거나 다른 표현으로 인코딩했다** (8장,
  p.124).[^dehghani2022]
- **판정은 reis의 "데이터 레이크 1.0 실패"와 같은 현상을 가리키되 원인을 다르게 짚는다** —
  **데이터 레이크 아키텍처는 복잡성과 퇴화(complexity and deterioration)로 고통받는다. 그것은
  초전문화된 데이터 엔지니어의 중앙 팀이 운영하는 배치나 스트리밍 잡의 복잡하고 다루기 힘든
  파이프라인을 만든다. 그것은 시간이 지나며 퇴화한다. 관리되지 않는 데이터셋들은 흔히 신뢰받지
  못하고 접근 불가능하며 가치를 거의 제공하지 못한다. 데이터 계보와 의존성은 가려져 추적하기
  어렵다** (8장, p.125).[^dehghani2022]
  - **나란히 놓으면**: 위 [데이터 레이크 1.0과 그 실패](#데이터-레이크-10과-그-실패)의
    reis 서술은 실패를 **도구의 미비**로 설명한다 — 스키마 관리·카탈로깅·발견 도구가 없었고,
    맵리듀스 잡 작성이 두통거리였고, 쓰기 전용 설계가 GDPR과 충돌했다. Dehghani의 서술은 같은
    증상(늪·불신·추적 불가)에서 **소유 구조**를 원인으로 지목한다 — 초전문화된 중앙 팀이
    도메인 바깥에서 운영한다는 것. **모순이 아니라 설명 층위가 다르다**: 전자가 맞다면 처방은
    도구 보강(레이크하우스·카탈로그·테이블 형식)이고, 후자가 맞다면 도구를 보강해도 남는다.
    그리고 실제로 3세대(레이크하우스 포함)에 대한 Dehghani의 판정이 그것이다 — **그것들은
    이전 세대의 한계로 이어진 기저 특성 다수를 여전히 앓는다** (8장, p.126).[^dehghani2022]
    위 [수렴 — 레이크하우스와 데이터 플랫폼](#수렴--레이크하우스와-데이터-플랫폼)이 해법으로
    적는 것이 여기서는 **미해결 판정**을 받는다. #hypothesis — 어느 층위가 옳은지는 이 두
    소스만으로 판정되지 않는다. 레이크하우스 채택 이후의 실측이 나와야 갈린다.
- 저자가 꼽는 레이크 아키텍처의 특성 아홉 항(추출·원형 보존·최소 변환·오브젝트 스토리지 적재·
  파일 또는 데이터프레임 접근·데이터 과학자 주 사용·레이크쇼어 마트·마트의 용도·피처 스토어)은
  세대론 페이지에 전문이 있다 (8장, p.124).[^dehghani2022]

**두 처방은 어떤 문제에 답하는가.** 레이크는 스키마를 미리 정할 수 없는 상태에서 원시 데이터를
잃지 않는 문제에 답하고, 데이터 메시는 그 원시 데이터의 의미를 아는 사람과 그것을 관리하는
사람이 갈라지는 문제에 답한다. 데이터 메시도 **원천 정렬 데이터를 고해상도로 보존하라**고
말한다는 점에서 스시 원칙과 목적을 공유한다 — 갈리는 것은 그 보존을 **어디서 누가** 하느냐다.
정본은 [데이터 메시 원칙](../synthesis/data-mesh-principles.md) 허브가 받는다.

## 분산 아키텍처 쪽에서 본 같은 양식

**분산 아키텍처의 트레이드오프를 다루는 2021년 책이 이 양식을 한 절로 요약하고 절충표를
붙인다.** 그 책의 공저자 가운데 한 사람이 데이터 메시의 제안자라 위
[데이터 메시가 보는 레이크](#데이터-메시가-보는-레이크)와 계보가 같다 (14장 §"The Data Lake",
pp.386–388).[^ford2021-hard-parts]

- **이 양식의 성립을 진자의 반대극으로 적는다** — 데이터 웨어하우스의 복잡성과 비용과 실패에
  대한 반동으로 **설계의 진자가 반대극으로 흔들린 것**이고, **의도적으로 데이터 웨어하우스
  패턴의 역**이다. 중앙집중 모델과 파이프라인은 유지하되 웨어하우스의 **"변환하고 적재하는"
  모델을 "적재하고 변환하는" 모델로 뒤집는다** (14장, p.386).[^ford2021-hard-parts]
  - **그 철학이 한 문장으로 적힌다** — 막대한 변환 작업을 하는 대신, **쓰이지 않을지도 모르는
    쓸모없는 변환을 하느니 아무 변환도 하지 말고 업무 사용자가 자연 형태의 분석 데이터에
    접근하게 하라**는 것이다. 그래서 **작업의 부담이 선제적(proactive)이 아니라 반응적
    (reactive)으로 옮겨진다** — 필요 없을지도 모르는 일을 하지 말고 **요구가 있을 때만
    변환한다** (14장, p.386).[^ford2021-hard-parts] 위
    [이 선택의 이름 — 읽기 스키마](#이-선택의-이름--읽기-스키마)가 같은 선택을 스키마 쪽
    어휘로 부르는 자리다.
  - **아키텍트가 이 관찰에 이른 근거 둘** — 웨어하우스에 미리 지어 둔 스키마가 **사용자가
    요구하는 리포트나 조회의 종류에 맞지 않는 일이 잦아** 해법을 짜려면 웨어하우스 스키마를
    이해하는 추가 작업이 필요했다는 것, 그리고 **많은 기계 학습 모델이 변환된 판보다 반쯤
    날것에 "가까운" 데이터로 더 잘 돈다**는 것이다 (14장, p.386).[^ford2021-hard-parts]
- **이 페이지가 갖지 않은 진단 하나** — 도메인 전문가에게 이 상황이 **견디기 힘든 시련**이었다는
  서술이다. 데이터가 웨어하우스로 변환되느라 **도메인 분리와 맥락이 벗겨졌는데, 새 스키마에
  자연스럽게 맞지도 않는 질의를 짜려면 결국 도메인 지식이 다시 필요했다**는 것이다 (14장,
  pp.386–387).[^ford2021-hard-parts]
- **저자들이 꼽는 레이크의 한계 셋** (14장, pp.387–388):[^ford2021-hard-parts]
  - **알맞은 자산을 발견하기 어렵다** — 도메인 안의 데이터 관계에 대한 이해 상당 부분이
    **데이터가 구조 없는 레이크로 흘러 들어가며 증발한다.** 그래서 도메인 전문가가 여전히 분석을
    짜는 데 끼어들어야 한다.
  - **PII와 그 밖의 민감 데이터** — 데이터 과학자가 흩어진 정보 조각들을 모아 **사생활을
    침해하는 지식을 알아내는 능력**과 나란히 PII 우려가 커졌다. 많은 나라가 사적 정보뿐 아니라
    **결합하면 학습해 식별할 수 있는 정보**까지 제한한다. **구조 없는 데이터를 레이크에
    쏟아붓는 것은 꿰맞추면 사생활을 침해할 수 있는 정보를 노출할 위험**을 안고, 발견 과정과
    마찬가지로 **그 사고를 피할 지식을 가진 것은 도메인 전문가**라서 그들이 레이크의 데이터를
    다시 분석해야 하게 만든다. 최소 수집 쪽 처방은 위
    [반대 압력 — 데이터 최소화](#반대-압력--데이터-최소화)에 있다.
  - **여전히 도메인이 아니라 기술로 분할된다** — 소프트웨어 아키텍처의 2021년 저술 시점 추세는 기술 능력
    기반 분할에서 **도메인 기반 분할**로 초점을 옮기는 것인데, **웨어하우스와 레이크 둘 다
    기술적 분할에 초점을 둔다.** 아키텍트는 그 해법을 대개 **주입·변환·적재·서빙이라는 구별되는
    분할**로 설계하고 각각이 하나의 기술 능력에 집중한다. **그러나 둘 다 데이터를 별도 실체로
    분리하려 하다가 그 과정에서 PII 데이터 같은 중요한 도메인 관점을 잃거나 흐린다.**
    - **저자들이 이 셋째를 결정적이라 부른다** — 아키텍트가 점점 **기술이 아니라 도메인**을
      중심으로 설계하는데 **이전 두 접근이 모두 데이터를 그 맥락에서 떼어 놓는 예**라는 것이다
      (14장, p.388).[^ford2021-hard-parts] 그 판정이 데이터 메시로 가는 다리다.
- **표 14-2의 열 머리글과 값을 그대로 옮긴다** (14장, p.388):[^ford2021-hard-parts]

| Advantage | Disadvantage |
|---|---|
| Less structured than data warehouse | Sometimes difficult to understand relationships |
| Less up-front transformation | Requires ad hoc transformations |
| Better suited to distributed architectures | |

- **표 뒤에 세 줄이 더 붙는다** (14장, p.388):[^ford2021-hard-parts]
  - **파이프라인의 취약성과 병리적 결합이라는 단점은 그대로 남는다** — 레이크 패턴에서 변환을
    덜 하기는 하지만 변환도 데이터 정화도 여전히 흔하다.
  - **레이크 패턴은 데이터 무결성 검사와 데이터 품질 등의 품질 문제를 하류 레이크 파이프라인으로
    떠민다.** 그것이 **데이터 웨어하우스에서 나타나던 운영 병목의 일부를 똑같이 만들 수 있다.**
    위 [데이터 메시가 보는 레이크](#데이터-메시가-보는-레이크)가 인용하는 품질 책임의 위치
    판정과 같은 것을 파이프라인 쪽에서 적은 것이다.
  - **기술적 분할과 배치 같은 성질 때문에 데이터가 낡을(staleness) 수 있다.** 세심한 조율이
    없으면 아키텍트는 **상류 시스템의 변경을 무시해 낡은 데이터를 갖게 되거나, 결합된
    파이프라인이 깨지게 두거나** 둘 중 하나가 된다.
