하나의 질문: **문서 데이터베이스가 스키마를 강제하지 않는다는 것은 정확히 무엇을 뜻하며,
그 선택이 데이터 형식을 바꿔야 할 때 무엇을 바꾸는가.**

## "스키마 없음"은 오해다

- 사실 관계부터 — **대부분의 문서 데이터베이스, 그리고 관계형 데이터베이스의 JSON 지원은 문서
  안의 데이터에 어떤 스키마도 강제하지 않는다. 관계형 데이터베이스의 XML 지원은 보통 선택적
  스키마 검증을 함께 제공한다. 스키마가 없다는 것은 임의의 키와 값이 문서에 추가될 수 있고,
  읽을 때 클라이언트가 문서에 어떤 필드가 있을지에 대해 아무 보장도 갖지 못한다는 뜻이다**
  (3장, p.80).[^kleppmann2026]
- 그런데 이름이 틀렸다 — **문서 데이터베이스는 때때로 스키마리스(schemaless)라 불리지만 그것은
  오해를 부른다. 데이터를 읽는 코드가 대개 어떤 종류의 구조를 가정하기 때문이다 — 즉 암묵적
  스키마(implicit schema)가 있으나 데이터베이스가 그것을 강제하지 않을 뿐이다** (3장,
  p.80).[^kleppmann2026]

## 두 이름과 그 비유

- **더 정확한 용어는 읽기 스키마(schema-on-read, 데이터의 구조가 암묵적이며 데이터를 읽을 때만
  해석된다)이고, 이는 쓰기 스키마(schema-on-write, 스키마가 명시적이고 데이터가 쓰일 때
  데이터베이스가 모든 데이터가 그것에 부합하도록 보장하는 관계형 데이터베이스의 전통적 접근)와
  대비된다** (3장, p.80).[^kleppmann2026]
- 비유가 하나 붙는다 — **읽기 스키마는 프로그래밍 언어의 동적(런타임) 타입 검사와 비슷하고,
  쓰기 스키마는 정적(컴파일 시점) 타입 검사와 비슷하다. 정적 타입 검사와 동적 타입 검사의
  옹호자들이 그 상대적 장점을 두고 큰 논쟁을 벌이듯, 데이터베이스에서 스키마를 강제하는 것도
  논쟁적인 주제이고 일반적으로 명확한 승자는 없다** (3장, p.81).[^kleppmann2026]

## 형식을 바꿔야 할 때 갈린다

- **두 접근의 차이는 애플리케이션이 데이터의 형식을 바꾸고 싶을 때 특히 두드러진다. 예컨대
  지금은 각 사용자의 전체 이름을 한 필드에 저장하고 있는데 대신 이름과 성을 따로 저장하고
  싶다고 하자** (3장, p.81).[^kleppmann2026]
- **문서 데이터베이스에서는 새 필드를 가진 새 문서를 그냥 쓰기 시작하고, 옛 문서를 읽을 때의
  경우를 처리하는 코드를 애플리케이션에 두면 된다** (3장, p.81):[^kleppmann2026]

  ```js
  if (user && user.name && !user.first_name) {
      // Documents written before Dec 8, 2023 don't have first_name
      user.first_name = user.name.split(" ")[0];
  }
  ```

- 그 대가 — **이 접근의 단점은 데이터베이스에서 읽는 애플리케이션의 모든 부분이 이제 오래전에
  쓰였을 수 있는 옛 형식의 문서를 다뤄야 한다는 것이다** (3장, p.81).[^kleppmann2026]
- **반면 쓰기 스키마 데이터베이스에서는 보통 이런 식의 마이그레이션을 수행한다** (3장,
  p.81):[^kleppmann2026]

  ```sql
  ALTER TABLE users ADD COLUMN first_name text DEFAULT NULL;
  UPDATE users SET first_name = split_part(name, ' ', 1);      -- PostgreSQL
  UPDATE users SET first_name = substring_index(name, ' ', 1); -- MySQL
  ```

- 그 비용의 실제 분포 — **대부분의 관계형 데이터베이스에서 기본값을 가진 열을 추가하는 것은
  큰 테이블에서도 빠르고 문제가 없다. 그러나 UPDATE 문을 실행하는 것은 모든 행을 다시 써야
  하므로 큰 테이블에서 느릴 가능성이 높고, 다른 스키마 연산(열의 데이터 타입 변경 같은)도 보통
  테이블 전체의 복사를 요구한다** (3장, p.81).[^kleppmann2026]
- 도구가 있지만 완전히 풀리지는 않는다 — **이런 종류의 스키마 변경을 다운타임 없이 배경에서
  수행할 수 있게 하는 여러 도구가 존재하지만, 큰 데이터베이스에서 그런 마이그레이션을 수행하는
  것은 여전히 운영상 도전적이다. 복잡한 마이그레이션은 first_name 열을 기본값 NULL로 추가하고
  (이것은 빠르다) 읽을 때 채워 넣음으로써 피할 수 있는데, 이는 문서 데이터베이스에서 하는 것과
  같다** (3장, p.81).[^kleppmann2026]

## 어느 쪽이 유리한 조건

- **읽기 스키마 접근은 컬렉션의 항목들이 전부 같은 구조를 갖지 않을 때(즉 데이터가 이질적일
  때) 유리하다.** 예로 드는 조건 둘 (3장, p.81):[^kleppmann2026]
  - **객체의 종류가 많고, 각 종류의 객체를 자기 테이블에 두는 것이 실용적이지 않다.**
  - **데이터의 구조가 내가 통제할 수 없고 언제든 바뀔 수 있는 외부 시스템에 의해 결정된다.**
- 반대 조건 — **그런 상황에서는 스키마가 도움보다 해가 될 수 있고, 스키마 없는 문서가 훨씬 더
  자연스러운 데이터 모델일 수 있다. 그러나 모든 레코드가 같은 구조를 가질 것으로 기대될 때는
  스키마가 그 구조를 문서화하고 강제하는 유용한 기제다** (3장, p.82).[^kleppmann2026]
- 같은 대립이 분석 저장소 쪽에서도 나타난다 — **데이터 레이크는 파일 형식·데이터 모델·스키마를
  전혀 강요하지 않고 파일을 담을 뿐**이며 (1장, pp.9–10),[^kleppmann2026] 소비자마다 자기에게
  맞는 형태로 원시 데이터를 변환하게 한다. 이는 위의 두 조건 중 첫째와 같은 논거 위에 서
  있다. 전문은 [데이터 레이크](../concepts/data-lake.md)에 있다.

## 스키마 진화가 같은 유연성을 되찾아 온다

같은 책 5장이 이 대립을 다시 열고 셋째 자리를 만든다 — 스키마를 두되 그것이 시간에 따라 바뀌게
하는 쪽이다.

- 두 모델의 대비가 5장 첫머리에 다시 나온다 — **관계형 데이터베이스는 일반적으로 데이터베이스의 모든
  데이터가 하나의 스키마에 부합한다고 가정한다. 그 스키마는 (스키마 마이그레이션, 곧 `ALTER` 문으로)
  바뀔 수 있지만 어느 시점에나 정확히 하나의 스키마가 유효하다. 반면 읽기 스키마("스키마리스")
  데이터베이스는 스키마를 강제하지 않으므로 데이터베이스가 서로 다른 시점에 쓰인 옛 데이터 형식과 새
  데이터 형식의 혼합을 담을 수 있다** (5장, p.161).[^kleppmann2026]
- 관계형 쪽도 실제로는 형식이 뒤섞인다 — **대부분의 관계형 데이터베이스는 null 기본값을 가진 새 열을
  더하는 것 같은 단순한 스키마 변경을 기존 데이터를 다시 쓰지 않고도 허용한다. 옛 행을 읽을 때
  데이터베이스는 디스크의 인코딩된 데이터에 빠져 있는 열에 null을 채워 넣는다. 스키마 진화는 밑에
  깔린 저장소가 스키마의 여러 역사적 버전으로 인코딩된 레코드를 담고 있더라도 데이터베이스 전체가
  하나의 스키마로 인코딩된 것처럼 보이게 해 준다** (5장, p.179).[^kleppmann2026] 곧 "어느 시점에나
  하나의 스키마"는 **논리적 겉모습**이고 물리적으로는 여러 버전이 공존한다.
- 그래서 5장의 결론이 이 페이지의 대립을 재배치한다 — **스키마 진화는 스키마리스/읽기 스키마 JSON
  데이터베이스가 제공하는 것과 같은 종류의 유연성을 허용하면서 데이터에 대한 더 나은 보장과 더 나은
  도구를 제공한다. 그래도 운영을 단순하게 유지하려면 동시에 존재하는 스키마 형식의 수를 최소로 유지하는
  것이 바람직하다** (5장, p.178).[^kleppmann2026]
- 이는 위 [어느 쪽이 유리한 조건](#어느-쪽이-유리한-조건)의 "일반적으로 명확한 승자는 없다"와
  어긋나지 않는다. 3장은 **스키마를 강제할지 말지**를 두고 승자가 없다고 말하고, 5장은 그 축과 다른
  축(스키마가 **버전에 걸쳐 진화할 수 있는가**)에서 스키마 기반 인코딩의 손을 든다. 전문은
  [데이터 인코딩 형식](../concepts/data-encoding-formats.md)에 있다.

## 저장 아키텍처에서 이 선택이 걸리는 자리

- 스키마가 답하는 질문들 — **데이터의 기대되는 형태는 무엇인가? 파일 형식은 무엇인가? 구조화·
  반구조화·비구조화 중 무엇인가? 어떤 데이터 타입이 기대되는가? 데이터는 더 큰 계층에 어떻게
  들어맞는가? 공유 키나 다른 관계를 통해 다른 데이터와 연결돼 있는가?** (6장,
  p.219).[^reis2022]
- 관계형일 필요는 없다 — **스키마가 관계형일 필요는 없다는 데 주의하라. 오히려 데이터는 구조와
  조직에 대한 정보를 많이 가질수록 더 유용해진다. 데이터 레이크에 저장된 이미지의 경우 이 스키마
  정보는 이미지 형식·해상도, 그리고 이미지가 더 큰 계층에 들어맞는 방식을 설명할 수 있다** (6장,
  p.219).[^reis2022]
- 로제타석이라는 비유 — **스키마는 일종의 로제타석, 즉 데이터를 읽는 법을 알려 주는 지시로 기능할
  수 있다. 두 주요 스키마 패턴이 존재한다: 쓰기 스키마와 읽기 스키마** (6장,
  p.219).[^reis2022]
  - **쓰기 스키마(schema on write)는 본질적으로 전통적 데이터 웨어하우스 패턴이다 — 테이블이
    통합 스키마를 갖고 테이블에 대한 어떤 쓰기든 거기에 부합해야 한다. 읽기 스키마를 지원하려면
    데이터 레이크가 스키마 메타스토어를 통합해야 한다** (6장, p.219).[^reis2022]
  - **읽기 스키마(schema on read)로는 스키마가 데이터가 쓰일 때 동적으로 만들어지고, 읽는 쪽이
    데이터를 읽을 때 스키마를 정해야 한다. 이상적으로 읽기 스키마는 Parquet이나 JSON처럼 내장
    스키마 정보를 구현하는 파일 형식으로 구현된다. CSV 파일은 스키마 불일치로 악명 높고 이 환경에서
    권장되지 않는다** (6장, pp.219–220).[^reis2022] 형식별 차이는
    [데이터 인코딩 형식](../concepts/data-encoding-formats.md)에 있다.
- 저자들의 요약 — **쓰기 스키마의 주된 이점은 데이터 표준을 강제해 미래에 데이터를 소비하기 더 쉽게
  만든다는 것이다. 읽기 스키마는 유연성을 강조해 사실상 어떤 데이터든 쓰이도록 허용한다. 이는 미래에
  데이터를 소비하기가 더 어려워지는 대가와 함께 온다** (6장, p.220).[^reis2022]
