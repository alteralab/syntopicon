## 하나의 질문

**데이터 프로덕트가 다른 것들과 얽혀 있으면서도 자기 수명 주기를 독립적으로 관리하려면, 무엇을
선언해야 하는가.**

## 14장이 마무리하는 세 어포던스

- **데이터 프로덕트는 오래 산다(long-lived). 그와 함께 그 상태를 관리하고, 그 수명 동안 거버넌스하고·
  디버그하고·감사할 필요가 따라온다** (14장, p.255).[^dehghani2022]
- 14장이 다루는 셋 — **데이터 프로덕트가 무엇을 어포드하는지의 설계다** (14장,
  p.255):[^dehghani2022]
  - **데이터 프로덕트 개발자가 착상부터 변경·수정·진화의 많은 반복에 걸쳐 그 수명 주기를 관리하는 것**
  - **전역 정책에 거버넌스되고 그것을 준수하는 것**
  - **모니터링되고·디버그되고·감사되는 것**

## 자율적 수명 주기가 규모의 전제다

- 절 머리의 제사 — **Never tell people how to do things. Tell them what to do and they will
  surprise you with their ingenuity. — George S. Patton** (14장, p.255).[^dehghani2022]
  선언적 모델링을 예고하는 인용이다.
- 조건문의 형태로 규정된다 — **데이터 메시의 규모 약속은 데이터 프로덕트의 수명 주기가
  **자율적으로** 관리될 수 있을 때에만 — 곧 데이터 프로덕트가 다른 데이터 프로덕트에 마찰 없이
  제한된 영향만 주며 지어지고·테스트되고·배포되고·돌 수 있을 때에만 — 이행될 수 있다. 이 약속은
  데이터 프로덕트 사이에 입력·출력 데이터 포트를 통한, 데이터나 스키마를 공유하는 상호 연결성이
  있는 동안에도 참으로 남아야 한다** (14장, p.255).[^dehghani2022]
- 이 장이 다루는 몫이 좁혀진다 — **10장에서 우리는 플랫폼 서비스의 사용에 초점을 두고 데이터
  프로덕트 개발자가 수명 주기를 관리하는 여정을 보았다. 그때 명백해진 것은 프로비저닝·인프라 자원
  관리·변경과 개정 관리 같은 복잡한 기제를 둘러싼 작업의 다수를 기저 플랫폼, 곧 **데이터 프로덕트
  경험 플레인**이 한다는 것이었다. 여기서 논할 것으로 남은 것은 **데이터 프로덕트가 자기를 만들고
  진화시키기 위해 제공하는 능력**이다** (14장, p.256).[^dehghani2022]
  [데이터 플랫폼 사용자 여정](../concepts/data-platform-user-journeys.md)이 플랫폼 쪽을 받고,
  이 페이지가 프로덕트 쪽을 받는다.

## 매니페스트 — 목표 상태의 선언

- 정의 — **수명 주기 관리에서 데이터 프로덕트의 핵심 능력 하나는 자기 **목표 상태(target
  state)**의 명세 — 자기 일을 하는 데 요구하는 자원과 설정 — 를 정의하는 것이다. 나는 이 명세를
  **데이터 프로덕트 매니페스트(a data product's manifest)**라 부른다. 데이터 프로덕트 개발자는
  데이터 프로덕트 매니페스트를 설정하고 유지하며, 변환 코드·테스트·시맨틱 정의 같은 다른 아티팩트와
  나란히 플랫폼에 제시한다** (14장, p.256).[^dehghani2022]
- 계열이 밝혀진다 — **데이터 프로덕트 매니페스트라는 이름은 쿠버네티스와 이스티오 같은 다른
  선언적 인프라 프로비저닝·오케스트레이션 시스템에서 영감을 받았다** (14장,
  p.256).[^dehghani2022]
  [클라우드 네이티브 아키텍처](../concepts/cloud-native-architecture.md)의 선언적 배포 모델이
  데이터 프로덕트 쪽으로 옮겨 온 것이다.
- 앞선 원칙과 이어진다 — **4장에서 논한 대로, 데이터 프로덕트의 **선언적 모델링**은 복잡성을
  감춘다. 데이터 프로덕트는 자기 매니페스트에 자기 원하는 목표 상태를 선언한다. 매니페스트는
  데이터 프로덕트의 수명 동안 바뀌고 진화할 수 있다** (14장, p.256).[^dehghani2022]
  [셀프서브 데이터 플랫폼 원칙](../concepts/self-serve-data-platform-principle.md)의 "선언적
  모델링으로 복잡성을 추상화한다"가 여기서 구체적 산출물이 된다.
- 무엇을 얻는가 — **매니페스트 선언을 써서 데이터 프로덕트 개발자는 데이터 프로덕트의 여러 측면과
  성질을 표준 방식으로, 이상적으로는 기저 물리 구현에 불가지하게 소통할 수 있다. 개발자는 시간이
  지나며 선언을 바꾸고, 새 개정판을 만들고, 옛것을 은퇴시킬 수 있다** (14장,
  p.256).[^dehghani2022]
- 설계 관점의 주체가 명시된다 — **데이터 메시는 매니페스트의 정의에 **개발자 경험 중심(developer-
  experience-centric)** 접근을 채택한다. 이는 데이터 프로덕트 개발자가 플랫폼의 내부와 플랫폼이
  데이터 프로덕트를 물리적으로 어떻게 프로비저닝하는지가 아니라 **데이터 프로덕트의 측면들**에
  집중한다는 뜻이다. 추가로 매니페스트는 데이터 프로덕트를 물리 구현에 묶어 두지 않으며, 이상적으로
  기저 플랫폼에 불가지이고 따라서 **이식 가능(portable)**하다** (14장, p.257).[^dehghani2022]

## 두 갈래의 산출물

- 그림 14-1의 서술 — **데이터 프로덕트 팀은 두 그룹의 아티팩트를 개발한다: 변환 코드와 시맨틱
  정의 같은 **소스 아티팩트(source artifacts)**, 그리고 데이터 퀀텀의 목표 (런타임) 상태와 그것이
  요구할 자원의 선언인 **데이터 프로덕트 매니페스트**다. 플랫폼은 이 아티팩트들을 써서 빌드·런타임
  아티팩트를 생성하고, 필요한 자원을 프로비저닝하고, 데이터 프로덕트 컨테이너를 돌린다** (14장,
  p.256).[^dehghani2022]
- 그림 14-1은 데이터 프로덕트 경험 플레인이 `/build`와 `/deploy` 두 인터페이스를 노출하고,
  소스 아티팩트는 빌드·배포로, 매니페스트는 프로비저닝으로 흘러 데이터 프로덕트 컨테이너가 되는
  경로를 그린다 (14장, p.257, 그림 14-1).[^dehghani2022]
  - **선언과 코드가 서로 다른 경로로 흐른다**는 것이 이 그림의 요점이다. 컨테이너의 정의는
    [데이터 프로덕트의 포트와 사이드카](../concepts/data-product-ports-and-sidecar.md)가 받는다.

## 매니페스트의 구성 요소

- 표 14-1이 예를 든다 — **표 14-1은 매니페스트가 정의하는 구성 요소의 몇 예를 열거한다** (14장,
  p.258):[^dehghani2022]

| 구성 요소 | 저자의 정의 |
|---|---|
| 데이터 프로덕트의 URI | 데이터 프로덕트의 전역 고유 식별자. 13장에서 데이터 프로덕트를 발견하고 주소 지정하는 핵심 식별자로 처음 도입되었다 |
| 출력 포트 | 각 출력 포트, 그것이 지원하는 접근 양식, 그리고 요구되는 보증의 선언. 이 선언을 써서 플랫폼이 스토리지와 스트림 토픽 같은 자원을 프로비저닝한다 |
| 출력 포트 SLO | 각 출력 포트가 보증하는 서비스 수준 합의의 선언 |
| 입력 포트 | 각 입력 포트와 그 성질 — 데이터가 어디서 오고 어떻게 회수되는지 — 의 선언 |
| 지역 정책 | 지역성·기밀성·프라이버시·보존 등 지역 정책의 설정 |
| 소스 아티팩트 | 변환 코드와 입력 포트 질의를 포함해, 데이터 프로덕트의 일부인 다른 소스 아티팩트에 대한 서술 |

- **선언이 자원 프로비저닝을 낳는다**는 것이 출력 포트 항의 요점이다 — 스토리지 타입 선택이
  개발자가 아니라 선언에서 파생된다.
- 확장성이 설계 조건이다 — **시간이 지나면서 매니페스트 언어의 설계는 확장 가능해야 하고, 플랫폼이
  새 타입의 자원이나 데이터 프로덕트의 의존과 능력을 지원하도록 진화할 때 새 측면을 추가할 수 있어야
  한다** (14장, p.258).[^dehghani2022]

## 매니페스트에 넣지 않는 것

- 경계가 명시된다 — **코드로 (명령형으로) 정의하는 것이 가장 좋은 데이터 프로덕트의 측면들은
  여기 포함되지 않는다. 예컨대 데이터 변환 로직, 입력 포트 질의, 출력 포트 맞춤 어댑터, 그리고
  정책의 맞춤 측면을 강제하는 코드는 코드로 구현되고 데이터 프로덕트 소스 아티팩트로 유지되는
  것이 가장 좋다** (14장, p.258).[^dehghani2022]
  - **선언형과 명령형의 경계선**이 여기서 그어진다 — 무엇을 원하는가는 매니페스트, 어떻게
    계산하는가는 코드다. 정책조차 이 선을 따라 갈라진다(설정은 매니페스트, 맞춤 강제 로직은
    코드).
