하나의 질문: **흩어진 기법들을 무슨 순서로 하나의 시스템에 얹는가.**

## 기법을 하나의 제품으로 묶는 장

- 장의 자리 — **지금까지 이 책은 파운데이션 모델을 특정 애플리케이션에 적응시키는 폭넓은 기법을
  다뤘다. 이 장은 이 기법들을 한데 가져와 성공적인 제품을 만드는 방법을 논의할 것이다** (10장,
  p.449).[^huyen2025]
- 왜 점진적으로 서술하는가 — **이용 가능한 AI 엔지니어링 기법과 도구의 폭이 넓다는 것을 감안하면
  올바른 것을 고르는 일은 압도적으로 느껴질 수 있다. 이 과정을 단순화하려고 이 장은 점진적 접근을
  취한다. 파운데이션 모델 애플리케이션을 위한 가장 단순한 아키텍처에서 시작해, 그 아키텍처의 난점을
  부각하고, 그것을 다루기 위해 구성 요소를 점차 더해 간다** (10장, p.449).[^huyen2025]
- 절의 전제 — **완전히 갖춰진 AI 아키텍처는 복잡할 수 있다. 이 절은 팀이 프로덕션에서 따를 법한
  과정을 따라가며, 가장 단순한 아키텍처에서 시작해 점차 더 많은 구성 요소를 더한다. AI 애플리케이션의
  다양성에도 불구하고 그것들은 많은 공통 구성 요소를 공유한다. 여기서 제안된 아키텍처는 폭넓은
  애플리케이션에 두루 통하도록 여러 회사에서 검증되었지만, 어떤 애플리케이션은 벗어날 수 있다**
  (10장, pp.449–450).[^huyen2025]

## 가장 단순한 아키텍처

- **가장 단순한 형태에서 당신의 애플리케이션은 질의를 받아 그것을 모델에 보낸다. 모델이 응답을
  생성하고 그것이 사용자에게 반환된다. 맥락 강화도, 가드레일도, 최적화도 없다. 모델 API 상자는
  서드파티 API(예: OpenAI·구글·앤트로픽)와 자체 호스팅 모델을 둘 다 가리킨다. 자체 호스팅 모델을
  위한 추론 서버를 만드는 것은 9장에서 논의한다** (10장, p.450).[^huyen2025] 도판은 사용자와
  모델 API 사이의 왕복(Query·Response) 하나만 그리고, 모델 API 상자 안에 Generation 하나만 둔다
  (10장, p.450, Figure 10-1).[^huyen2025]

## 다섯 단계의 순서

- **이 단순한 아키텍처에서 필요가 생길 때마다 더 많은 구성 요소를 더할 수 있다. 그 과정은 다음과
  같은 모습일 수 있다** (10장, p.450):[^huyen2025]
  1. **모델에 정보 수집을 위한 외부 데이터 소스와 도구 접근을 주어 모델로 들어가는 맥락 입력을
     강화한다.**
  2. **당신의 시스템과 사용자를 보호할 가드레일을 둔다.**
  3. **복잡한 파이프라인을 뒷받침하고 보안을 더하기 위해 모델 라우터와 게이트웨이를 더한다.**
  4. **캐싱으로 지연과 비용을 최적화한다.**
  5. **시스템의 능력을 극대화하기 위해 복잡한 로직과 쓰기 행동을 더한다.**
- 순서는 규범이 아니다 — **이 장은 내가 프로덕션에서 흔히 보는 진행을 따른다. 그러나 저마다 필요가
  다르다. 당신의 애플리케이션에 가장 말이 되는 순서를 따라야 한다** (10장, p.450).[^huyen2025]
- 나머지 둘의 자리 — **품질 통제와 성능 개선을 위해 어떤 애플리케이션에도 필수인 모니터링과 관측성은
  이 과정의 끝에서 논의될 것이다. 이 모든 구성 요소를 하나로 잇는 오케스트레이션은 그 뒤에
  논의된다** (10장, p.450).[^huyen2025]

## 1단계 맥락을 강화한다

- 무엇이 먼저 자라는가 — **플랫폼의 초기 확장은 대개 시스템이 각 질의에 답하는 데 모델이 필요로 하는
  관련 맥락을 구성하게 해 주는 기제를 더하는 일을 수반한다. 6장에서 논의했듯 맥락은 텍스트 검색·이미지
  검색·표 데이터 검색을 포함한 다양한 검색 기제를 통해 구성될 수 있다. 맥락은 모델이 웹 검색·뉴스·
  날씨·이벤트 같은 API를 통해 정보를 자동으로 수집하게 해 주는 도구로도 강화될 수 있다** (10장,
  pp.450–451).[^huyen2025]
- 이 장이 붙이는 비유 (10장, p.451):[^huyen2025]

  > *Context construction is like feature engineering for foundation models.*

  **그것은 모델에게 출력을 만드는 데 필요한 정보를 준다. 시스템의 출력 품질에서 그 중심적 역할 때문에
  맥락 구성은 모델 API 제공자들이 거의 보편적으로 지원한다. 예컨대 OpenAI·Claude·Gemini 같은 제공자는
  사용자가 파일을 올리고 모델이 도구를 쓰게 해 준다** (10장, p.451).[^huyen2025]
- 제공자마다 다르다 — **그러나 모델의 능력이 다르듯 이 제공자들은 맥락 구성 지원에서도 다르다. 예컨대
  어떤 종류의 문서를 몇 개나 올릴 수 있는지에 제한이 있을 수 있다. 특화된 RAG 솔루션은 벡터 데이터베이스가
  수용할 수 있는 만큼 문서를 올리게 해 줄 수 있지만, 일반적인 모델 API는 적은 수의 문서만 올리게 할 수
  있다. 프레임워크마다 검색 알고리즘과 청크 크기 같은 다른 검색 설정도 다르다. 마찬가지로 도구 사용에서도
  솔루션들은 지원하는 도구의 종류와, 병렬 함수 실행이나 오래 도는 작업을 지원하는지 같은 실행 방식에서
  다르다** (10장, p.451).[^huyen2025]
- 아키텍처에 더해지는 상자들 — 도판은 맥락 구성(Context construction — 예: RAG·에이전트·질의
  재작성), 읽기 전용 행동(Read-only actions — 예: 벡터 검색·SQL 질의 실행·웹 검색), 데이터베이스(예:
  문서·표·대화 이력·벡터DB)를 모델 API 앞에 놓는다 (10장, p.451, Figure 10-2).[^huyen2025]

## 5단계 에이전트 패턴을 더한다

- 순차 흐름의 한계 — **지금까지 논의한 애플리케이션은 상당히 단순하다. 각 질의가 순차적 흐름을 따른다.
  그러나 6장에서 논의했듯 애플리케이션 흐름은 루프·병렬 실행·조건 분기와 함께 훨씬 더 복잡해질 수
  있다. 6장에서 논의한 에이전트 패턴(agentic pattern)은 복잡한 애플리케이션을 만드는 데 도움이 될 수
  있다** (10장, p.463).[^huyen2025]
- 루프가 생기는 방식 — **예컨대 시스템이 출력을 생성한 뒤, 그것은 과제를 완수하지 못했으며 더 많은
  정보를 모으기 위해 또 한 번의 검색을 수행해야 한다고 판단할 수 있다. 원래 응답이 새로 검색된 맥락과
  함께 같은 모델이나 다른 모델로 넘겨진다. 이것이 루프를 만든다** (10장, p.463).[^huyen2025] 도판은
  이 되먹임을 출력 가드레일에서 맥락 구성으로 돌아가는 화살표 하나로 그린다 — **노란 화살표는 생성된
  응답이 시스템으로 되먹여져 더 복잡한 애플리케이션 패턴을 가능하게 한다** (10장, p.464, Figure 10-9
  설명).[^huyen2025]

## 쓰기 행동

- **모델의 출력은 이메일 작성·주문 넣기·은행 이체 개시 같은 쓰기 행동(write action)을 호출하는 데도
  쓰일 수 있다. 쓰기 행동은 시스템이 자기 환경을 직접 바꾸게 해 준다. 6장에서 논의했듯 쓰기 행동은
  시스템을 크게 더 유능하게 만들지만 그것을 상당히 더 많은 위험에 노출시키기도 한다. 모델에 쓰기 행동
  접근을 주는 것은 극도의 주의를 기울여 이뤄져야 한다** (10장, p.464).[^huyen2025] 도판은 쓰기
  행동(예: 주문 갱신·이메일 발송) 상자를 더하고 사용자 쪽 화살표를 "Final response"로 바꾼다 (10장,
  p.465, Figure 10-10).[^huyen2025]

## 부품이 늘면 실패 모드가 는다

- **여기까지 모든 단계를 따라왔다면 당신의 아키텍처는 꽤 복잡해졌을 가능성이 높다. 복잡한 시스템은 더
  많은 과제를 풀 수 있지만 더 많은 실패 모드를 들여오기도 해서, 잠재적 실패 지점이 많은 탓에 디버깅을
  더 어렵게 만든다** (10장, p.464).[^huyen2025]
- 요약이 되풀이하는 대가 — **각 추가 구성 요소는 잠재적으로 당신의 시스템을 더 유능하게, 더 안전하게,
  또는 더 빠르게 만들 수 있지만 시스템의 복잡도도 키워 그것을 새로운 실패 모드에 노출시킨다** (10장,
  p.492).[^huyen2025]

## 구성 요소의 경계는 유동적이다

- 요약이 붙이는 단서 — **시스템을 모듈적이고 유지보수 가능하게 유지하려면 구성 요소를 분리하는 것이
  필요하지만, 이 분리는 유동적이다. 구성 요소가 기능에서 겹칠 수 있는 방식은 많다. 예컨대 가드레일은
  추론 서비스에서, 모델 게이트웨이에서, 또는 독립 구성 요소로 구현될 수 있다** (10장,
  p.492).[^huyen2025]
- 이 장이 무엇을 주는가 — **장은 두 부분으로 이뤄졌다. 첫 부분은 AI 애플리케이션을 위한 공통
  아키텍처를 논의했다. 어떤 애플리케이션의 정확한 아키텍처는 다를 수 있지만, 이 고수준 아키텍처는 서로
  다른 구성 요소가 어떻게 맞물리는지 이해하는 틀을 제공한다. 저자는 이 아키텍처를 만드는 데 단계별
  접근을 써서 각 단계의 난점과 그것을 다루는 데 쓸 수 있는 기법을 논의했다** (10장,
  p.492).[^huyen2025]

## 시스템 문제라는 결론

- 장을 닫는 규정 — **많은 AI 난제는 그 핵심에서 시스템 문제다. 그것을 풀려면 흔히 한 걸음 물러나
  시스템을 전체로 살펴볼 필요가 있다. 하나의 문제가 독립적으로 일하는 서로 다른 구성 요소들에 의해
  다뤄질 수도 있고, 어떤 해법은 여러 구성 요소의 협업을 요구할 수도 있다. 시스템에 대한 철저한 이해가
  실제 문제를 풀고, 새 가능성을 열고, 안전을 보장하는 데 필수적이다** (10장, p.493).[^huyen2025]

## 책이 닫히는 자리

- 에필로그가 세는 것 — **당신은 해냈다! 방금 15만 단어가 넘는, 160개의 삽화·250개의 각주·975개의 참조
  링크가 든 기술서를 끝냈다** (에필로그, p.495).[^huyen2025]
- 저자가 남기는 관찰 — **기술 저술의 가장 어려운 부분은 올바른 답을 찾는 것이 아니라 올바른 질문을
  던지는 것이다. 이 책을 쓰면서 저자는 재미있고 유용한 발견으로 이끄는 많은 질문을 던지게 되었다**
  (에필로그, p.495).[^huyen2025]
- 분야에 대한 전망 — **이미 파운데이션 모델 위에 만들어진 놀라운 애플리케이션이 아주 많다. 이 수가
  미래에 지수적으로 자라리라는 데는 의심의 여지가 없다. 이 책이 소개한 것 같은 AI 엔지니어링에 대한 더
  체계적인 접근이 개발 과정을 더 쉽게 만들어 더 많은 애플리케이션을 가능하게 할 것이다** (에필로그,
  p.495).[^huyen2025]
