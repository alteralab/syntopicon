이 페이지의 질문: **클래스 파일은 바이트 수준에서 어떤 모양이며, 그 모양이 왜 그렇게
고정적인가.**

## 왜 이 형식이 안정적이어야 했는가

- 저자가 이 장을 지루하다고 미리 말하면서도 피해 갈 수 없다고 하는 이유는 하나다 —
  **파일 형식과 구조는 '사전 읽기'와 비슷하여 이번 장은 어쩔 수 없이 조금 지루할 것이다.
  그렇더라도 자바 가상 머신에서 가장 중요한 기초이므로 더 깊이 학습하기 위해서는 절대 피해 갈 수
  없는 주제다** (6장, p.290).[^zhou2024]
- 이 형식의 안정성이 자바의 상업적 성공 조건이었다 — **자바 기술은 항상 하위 호환성을 매우 잘
  유지해 왔는데, 클래스 파일 구조가 안정적이지 않았다면 불가능했을 일이다. 옛 버전으로 컴파일한
  제품이라는 이유로 실행할 수 없다면 어떤 프로그래밍 언어든 상업적으로 성공하기는 매우
  어렵다** (6장, p.290).[^zhou2024]
- 그래서 실제로 거의 바뀌지 않았다 — **이번 장에서 설명하는 클래스 파일 구조 대부분은 《자바
  가상 머신 명세》 1판 때 내용 그대로다**(1997년 발행되어 JDK 1.2 시대 가상 머신까지 대응).
  명세가 몇 차례 개정되며 세부는 갱신됐지만 **기본적으로 원래 구조를 유지한 채 내용을 추가하거나
  기능을 확장하는 형태**였다 (6장, p.290).[^zhou2024]

## 파일이 아니어도 되는 '파일 형식'

- 단위는 하나다 — **모든 클래스 파일은 각각 하나의 클래스 또는 인터페이스를 정의한다** (6장,
  p.290).[^zhou2024]
  - 예외가 각주에 적혀 있다 — **`package-info.class`와 `module-info.class`는 특정 클래스나
    인터페이스를 정의하지 않으며, 그 대신 해당 패키지나 모듈에 대한 정보를 기술한다** (6장,
    p.290, 각주 2).
- 이름과 달리 파일일 필요는 없다 — **클래스나 인터페이스를 꼭 파일에 담아 둘 필요는 없다.
  예컨대 동적으로 생성하여 클래스 로더에 직접 제공할 수 있다.** 그래서 저자는 **클래스나
  인터페이스가 반드시 따라야 하는 형식을 '클래스 파일 형식'으로 지칭**하며 **디스크에 파일
  형태로 존재할 필요는 없다** (6장, p.290).[^zhou2024]
- 저장 방식은 극단적으로 조밀하다 — **클래스 파일은 바이트를 하나의 단위로 하는 이진 스트림
  집합체다. 각 데이터 항목이 정해진 순서에 맞게, 구분 기호 없이 조밀하게 나열된다. 그래서 클래스
  파일 전체가 낭비되는 공간 없이 프로그램을 실행하는 데 꼭 필요한 데이터로 채워진다** (6장,
  p.290).[^zhou2024]
- 바이트 순서도 고정이다 — **1바이트가 넘는 데이터 항목은 바이트 단위로 분할되며, 이때 큰 단위의
  바이트가 먼저 저장되는 빅 엔디언 방식으로 표현된다** (6장, pp.290–291).[^zhou2024]
  - 각주가 이 선택의 배경을 정리한다 — **빅 엔디언은 가장 큰 단위의 바이트가 가장 낮은 주소에,
    가장 작은 단위의 바이트가 가장 높은 주소에 저장된다.** 2024년 저술 시점에는 **x86이 리틀 엔디언을
    이용하는 대표적인 아키텍처**이고, **파워(Power), AArch64, RISC-V 등 대부분의 주류
    프로세서는 엔디언 방식을 변환할 수 있는 바이 엔디언(Bi Endian) 명령어 집합 아키텍처**다
    (6장, p.291, 각주 3).

## 런타임에 만들어지는 클래스 — 동적 프락시

'동적으로 생성하여 클래스 로더에 직접 제공한다'는 앞 절의 단서가 실제로 쓰이는 자리다.

- 저자는 이 기술의 문턱부터 낮춘다 — **'바이트코드 생성'은 고급 기술이 아니니 안심하자. (…)
  JDK에 포함된 javac 컴파일러는 바이트코드 생성 기술의 '조상'에 해당하며 이 역시 자바로 작성되었다**
  (9장, p.456).[^zhou2024] 쓰이는 자리는 넓다 — **웹 서버의 JSP 컴파일러, 컴파일타임에 코드를
  변경해 주는 AOP 프레임워크가 있다. 동적 프락시 기술에서도 흔히 쓰인다. 리플렉션을 사용할 때도
  가상 머신은 실행 속도를 개선하기 위해 런타임에 바이트코드를 생성하기도 한다** (9장, pp.456–457).
- 동적 프락시에서 '동적'이 뜻하는 것과 그 이득이 분리되어 있다 — **동적 프락시의 장점은 프락시
  클래스를 작성하는 코드 양을 줄여 주는 게 아니다. 원래의 클래스와 인터페이스가 무엇인지 알 수 없는
  상태에서 프락시가 행위를 대신 결정할 수 있다는 점이 장점이다. 이처럼 프락시 클래스가 원래 클래스와
  직접 연결되어 있지 않다면 다양한 애플리케이션 시나리오에서 유연하게 재사용할 수 있다** (9장,
  p.457).[^zhou2024]
- 사용자 코드가 하는 일은 두 가지뿐이다 — 대신 실행할 인스턴스를 묶고(`bind`), 가로챈 호출을
  처리하는 것이다 (9장, pp.457–458, 코드 9-1 발췌):[^zhou2024]

  ```java
  static class DynamicProxy implements InvocationHandler {
      Object originalObj;

      Object bind(Object originalObj) {
          this.originalObj = originalObj;
          return Proxy.newProxyInstance(
              originalObj.getClass().getClassLoader(),
              originalObj.getClass().getInterfaces(), this);
      }

      @Override
      public Object invoke(Object proxy, Method method, Object[] args)
          throws Throwable {
          System.out.println("Welcome");
          return method.invoke(originalObj, args);
      }
  }
  ```

- 블랙박스는 한 군데뿐이고, 그 안에서 클래스가 만들어진다 — **코드에서 유일한 블랙박스는
  `Proxy::newProxyInstance()` 메서드이며 특별한 것은 없다. (…) 이 메서드의 소스 코드를 추적하면
  프로그램이 검증, 최적화, 캐싱, 동기화, 바이트코드 생성, 명시적 클래스 로딩 같은 작업을 수행했음을
  알 수 있다. (…) 최종적으로 `sun.misc.ProxyGenerator::generateProxyClass()` 메서드를 호출하여
  바이트코드 생성을 완료한다. 이 메서드는 런타임에 프락시 클래스에 해당하는 바이트코드를 생성해
  `byte[]` 배열로 반환한다** (9장, p.458).[^zhou2024]
  - 결과물을 눈으로 볼 수 있다 — `main()` 첫 줄에서
    `System.getProperties().put("sun.misc.ProxyGenerator.saveGeneratedFiles", "true")`를 실행하면
    **`$Proxy0.class` 파일이 생성된다. 바로 프락시 클래스의 클래스 파일이다** (9장, pp.458–459).
    옮긴이 각주는 같은 효과를 내는 가상 머신 매개 변수를 적어 둔다 —
    **`-Djdk.proxy.ProxyGenerator.saveGeneratedFiles=true`** (9장, p.458, 옮긴이 각주 7).
- 만들어진 클래스의 모양은 단순하고 규칙적이다 — 디컴파일하면 **`final class $Proxy0 extends Proxy
  implements DynamicProxyTest$IHello`** 이며, **`Object`에서 상속된 `equals()`, `hashCode()`,
  `toString()` 메서드와 인터페이스에서 정의한 각 메서드에 대응하는 구현이 생성되었다. 그리고 메서드
  본문을 구현할 때는 항상 `InvocationHandler` 객체의 `invoke()` 메서드를 호출한다. (…) 메서드별
  차이점은 전달되는 매개 변수와 메서드 객체가 다르다는 것뿐이다. 따라서 동적 프락시의 어떤 메서드가
  호출되든 실제로는 `InvocationHandler::invoke()`에서 프락시 로직을 실행하게 된다** (9장,
  pp.459–460).[^zhou2024] 메서드 객체들(`m0`~`m3`)은 정적 초기화 블록에서 `Class.forName()`과
  `getMethod()`로 한 번만 얻어 둔다 (9장, p.459, 코드 9-2).
- 그러나 손으로 바이트를 쌓는 것은 실무의 방식이 아니다 — **일반적인 생성 과정은 클래스 파일의 형식
  명세에 맞춰 바이트코드를 구성하면 된다. 하지만 실제 개발에서는 바이트코드를 바이트 단위로 직접
  구성하는 경우는 드물다. 그런 식으로는 일부 고도로 형식화된 코드만 생성할 수 있다. 사용자 프로그램의
  코드는, 특히 생성할 바이트코드양이 많은 경우라면 JDK에 동봉된 바이트코드 클래스 라이브러리를
  사용하는 편이 좋다** (9장, p.460).[^zhou2024]

## 두 가지 데이터 타입뿐인 의사 구조

- 형식을 기술하는 문법 자체가 단순하다 — **《자바 가상 머신 명세》에 따르면 클래스 파일에
  데이터를 저장하는 데는 C 언어의 구조체와 비슷한 의사 구조(pseudo structure)를 이용한다. 이
  의사 구조에는 '부호 없는 숫자'와 '테이블'이라는 두 가지 데이터 타입만 존재한다** (6장,
  p.291).[^zhou2024]
  - **부호 없는 숫자(unsigned number)**: **기본 데이터 타입을 표현한다. `u1`, `u2`, `u4`,
    `u8`은 각각 1바이트, 2바이트, 4바이트, 8바이트를 뜻한다. 숫자, 인덱스 참조, 수량 값을
    기술하거나 UTF-8로 인코딩된 문자열 값을 구성할 수 있다** (6장, p.291).
  - **테이블**: **여러 개의 부호 없는 숫자나 또 다른 테이블로 구성된 복합 데이터 타입을
    표현한다. 구분이 쉽도록 테이블 이름은 관례적으로 `_info`로 끝난다.** 그리고 **클래스 파일
    전체는 본질적으로 테이블**이다 (6장, p.291).
- 개수를 세는 규약도 문법의 일부다 — **같은 타입의 데이터 여러 개를 표현할 때 그 개수가 정해져
  있지 않다면 개수를 알려 주는 타입이 바로 앞에 등장한다. `*_count` 형태의 항목들이 여기
  속한다. 이처럼 '개수 + 개수만큼의 데이터 타입' 형태를 해당 타입의 '컬렉션'이라고 한다** (6장,
  p.292).[^zhou2024]
- 구분자가 없다는 사실이 모든 제약의 근원이다 — **클래스 구조는 XML 같은 언어를 이용하지 않는다.
  구분자가 없기 때문에** 각 데이터 항목의 **바이트 순서(byte ordering), 각 바이트의 의미, 길이,
  순서가 모두 엄격하게 제한되며 변경할 수 없다** (6장, p.292).[^zhou2024]

## ClassFile 구조

- 파일 전체의 뼈대는 이 하나의 표에 다 들어 있다. 이후의 모든 절은 이 항목들을 하나씩 푸는
  것이다 (6장, p.291, 구조 정의 6-1):[^zhou2024]

  ```text
  ClassFile {
      u4             magic;
      u2             minor_version;
      u2             major_version;
      u2             constant_pool_count;
      cp_info        constant_pool[constant_pool_count-1];
      u2             access_flags;
      u2             this_class;
      u2             super_class;
      u2             interfaces_count;
      u2             interfaces[interfaces_count];
      u2             fields_count;
      field_info     fields[fields_count];
      u2             methods_count;
      method_info    methods[methods_count];
      u2             attributes_count;
      attribute_info attributes[attributes_count];
  }
  ```

## 매직 넘버

- 파일의 첫 4바이트가 신원 확인용이다 — **모든 클래스 파일의 처음 4바이트는 매직 넘버로
  시작한다. 매직 넘버는 가상 머신이 허용하는 클래스 파일인지 여부를 빠르게 확인하는 용도로만
  쓰인다** (6장, p.292).[^zhou2024]
- 이 기법은 클래스 파일 고유의 것이 아니다 — **클래스 파일뿐 아니라 다양한 파일 형식에서 파일
  타입 식별용으로 매직 넘버를 즐겨 쓴다. 예컨대 GIF와 JPEG 같은 이미지 파일에도 파일 헤더에
  매직 넘버가 등장한다. 파일 확장자는 사용자가 마음대로 변경할 수 있기 때문에 파일 형식
  식별용으로는 매직 넘버가 더 안정적이다** (6장, p.292).[^zhou2024] 같은 기법을 저장 엔진
  쪽에서 본 서술은 [온디스크 파일 형식](../concepts/on-disk-file-format.md)에 있다.
- 값에는 사연이 있다 — **클래스 파일의 매직 넘버는 '낭만적인' `0xCAFEBABE`다. 이 값은 자바의
  이름이 아직 오크이던 시절에 결정되었다.** 자바 개발 팀의 핵심 멤버인 **패트릭 노튼(Patrick
  Naughton)** 이 전한 뒷이야기는 이렇다 (6장, p.292):[^zhou2024]

  > "우리는 재미있고 기억하기 쉬운 값을 찾고 있었다. 그런데 마침 즐겨 찾는 카페(Peet's
  > Coffee)의 인기 바리스타가 눈에 띄어 `0xCAFEBABE`로 선정했다."

  - 각주에 형제 값도 하나 있다 — **자바의 아버지 제임스 고슬링에 따르면 `CAFEDEAD`도 한때 다른
    객체 저장 형식으로 이용되었다고 한다. 이후 폐기되어 널리 확산되지 못했다** (6장, p.292,
    각주 4).

## 버전 번호가 정하는 호환 범위

- 다음 4바이트가 버전이다 — **매직 넘버 다음의 4바이트는 클래스 파일의 버전 번호다. 5~6번째
  바이트는 마이너 버전을, 7~8번째 바이트는 메이저 버전을 뜻한다. 자바 버전 번호는 45부터
  시작한다. JDK 1.1 이후 주요 JDK 릴리스의 메이저 버전은 1씩 증가**한다 (6장,
  pp.292–293).[^zhou2024]
- 호환은 한 방향으로만 열려 있다 — **상위 버전 JDK는 하위 버전을 인식할 수 있다. 하지만 하위
  버전 JDK에서 상위 버전의 클래스 파일을 실행할 수는 없다.** 이는 임의의 구현 선택이 아니라
  명세의 요구다 — **《자바 가상 머신 명세》의 '클래스 파일 검증' 절에서 "파일 형식이 변경되지
  않았더라도 상위 버전의 클래스 파일을 실행하면 안 된다"라고 규정했기 때문**이다 (6장,
  p.293).[^zhou2024]
  - 구체적으로 **JDK 1.1은 버전 번호 45.0~45.65535 범위의 클래스 파일을 지원한다. 즉, 버전이
    46.0인 클래스 파일은 실행할 수 없다. JDK 1.2는 45.0~46.65535 버전을 지원한다** (6장,
    p.293).
- JDK 버전과 클래스 파일 버전 번호의 대응은 이렇다 (6장, p.294, 표 6-1 발췌):[^zhou2024]

  | JDK 버전 | 클래스 파일 버전 번호 |
  |---|---|
  | JDK 1.1.8 | 45.3 |
  | JDK 1.2.2 (`-target 1.2`) | 46.0 |
  | JDK 1.3.1 (`-target 1.3`) | 47.0 |
  | JDK 1.4.2 (`-target 1.4`) | 48.0 |
  | JDK 5 | 49.0 |
  | JDK 6 | 50.0 |
  | JDK 7 | 51.0 |
  | JDK 8 | 52.0 |
  | JDK 9 | 53.0 |
  | JDK 11 | 55.0 |
  | JDK 17 | 61.0 |
  | JDK 21 | 65.0 |

  - `-source` 매개 변수가 받아 주는 범위도 함께 좁혀져 왔다 — **JDK 12에서 버전 6 지원이,
    JDK 20에서 버전 7 지원이 종료**됐고, **JDK 9부터는 `-source` 매개 변수로 버전 번호 1.5
    이하를 지정할 수 없다** (6장, p.294와 각주 6).
  - JDK 5 이후로는 **기본값이 JDK 버전과 같아진다** (6장, p.294).
- 마이너 버전은 대부분의 기간 동안 죽어 있던 필드다 — **JDK 1.0.2는 45.0~45.3을 지원했다.
  JDK 1.1은 45.0~45.65535를 지원했다. 하지만 JDK 1.2부터는 마이너 버전을 사용하지 않아서 모두
  값이 0으로 고정되어 있다** (6장, p.295).[^zhou2024]
  - 버전 조건: JDK 12 이상 — **일부 복잡한 새 기능을 '공개 베타' 형태로 출시할 때 마이너 버전을
    다시 활용**하기 시작했다. **미리 보기 기능을 사용하는 경우는 마이너 버전을 65535로 지정하여
    자바 가상 머신이 해당 클래스 파일을 로드할 때 인지할 수 있도록** 한다 (6장, p.295).
- 이 장의 모든 실물 예제는 JDK 17로 컴파일한 클래스 파일 기준이며, 실제 바이트를 읽으면
  **첫 4바이트가 `0xCAFEBABE`, 5~6번째가 마이너 버전 `0x0000`, 이어서 메이저 버전 `0x003D`(십진
  61)** 로 나온다 (6장, p.293).[^zhou2024]

## 추가만으로 확장해 온 20년

- 형식의 변화 폭이 언어의 변화 폭보다 훨씬 작았다 — **언어 문법, API, 가상 머신 구현 기술
  측면의 변경과 비교하면 클래스 파일의 구조는 상당히 안정되게 유지되었다. 실제로 주요 구조,
  의미, 바이트코드 명령어 수는 거의 그대로다** (6장, p.351).[^zhou2024]
- 그것을 가능하게 한 것이 설계 선택이다 — **접근 플래그나 속성 테이블 등의 구조가 애초부터
  확장을 고려해 설계된 덕분이다. 그래서 모든 개선이 새로운 내용을 추가하는 형태로 이루어질 수
  있었다** (6장, p.351).[^zhou2024]
- 추가된 양은 이렇다 — **JDK 1.4 이후로 클래스 파일 형식에는 총 5개의 접근 플래그가 추가되었다.
  속성 테이블에는 총 21개의 속성이 추가되었다. 추가된 속성들은 대부분 열거형, 가변 길이 변수,
  제네릭, 동적 애너테이션, 모듈화, 레코드 클래스, 봉인된 클래스 등 새로운 언어 기능을 지원하는 데
  사용된다** (6장, p.351).[^zhou2024]
- 형식의 값어치를 저자가 요약해 둔 문장이 이 페이지의 결론이다 — **특정 하드웨어나 운영 체제에
  종속되지 않는 플랫폼 독립성, 클래스 파일 형식의 간결성·안정성·확장성은 자바 기술 시스템이
  플랫폼 독립과 언어 독립이라는 두 마리 토끼를 모두 잡기 위한 중요한 두 기둥이다** (6장,
  p.351).[^zhou2024]
