# 데이터 통합

- [이어지는 페이지](#이어지는-페이지)

하나의 질문: **한 애플리케이션이 여러 저장 시스템을 쓸 수밖에 없을 때, 그 사이의 데이터를
무엇으로 맞춰 두는가.** 이 문제를 저자들은 데이터 통합(data integration)이라 부른다.

이 장의 성격을 저자들이 먼저 밝힌다 — **이 장은 앞선 장들보다 더 의견이 강하며, 여러 접근을
비교하기보다 하나의 특정한 철학을 깊이 파고든다** (13장, p.539).[^kleppmann2026]

## 해법이 여럿이라는 사실에서 출발한다

- 출발점 — **이 책에 반복해서 나온 주제는 어떤 주어진 문제에도 여러 해법이 있고 각각 자기
  장점·단점·트레이드오프를 갖는다는 것이다. 예컨대 4장에서 저장 엔진을 논할 때 로그 구조화
  저장·B-트리·컬럼 지향 저장을 살폈고, 6장에서 복제를 논할 때 단일 리더·다중 리더·리더리스
  접근을 고려했다** (13장, p.539).[^kleppmann2026]
- **"데이터를 저장하고 나중에 다시 찾고 싶다" 같은 문제가 있으면 하나의 옳은 해법은 없고
  각각 다른 상황에 적절한 여러 접근이 있다. 소프트웨어 구현은 보통 하나의 특정 접근을 골라야
  한다. 코드 경로 하나를 견고하고 성능 좋게 만드는 것만도 충분히 어렵다; 많은 기능으로 너무
  많은 유스케이스를 만족시키려 하면 특화 도구에 비해 그 기능들의 구현이 나빠지기 쉽다** (13장,
  p.540).[^kleppmann2026]
- 그래서 도구 선택도 상황에 달린다 — **모든 소프트웨어 조각은, 이른바 "범용(general-purpose)"
  데이터베이스라 하더라도, 특정한 사용 패턴을 위해 설계돼 있다** (13장,
  p.540).[^kleppmann2026]
- 첫째 과제 — **이 대안의 범람 앞에서 첫 도전은 소프트웨어 제품과 그것이 잘 맞는 상황 사이의
  대응을 알아내는 것이다. 벤더는 자기 소프트웨어가 잘 맞지 않는 워크로드의 종류를 알려 주기를
  당연히 꺼린다** (13장, p.540).[^kleppmann2026]
- 둘째 과제 — **도구와 상황의 대응을 완벽하게 이해하더라도 또 다른 도전이 있다. 복잡한
  애플리케이션에서 데이터는 흔히 여러 방식으로 쓰이고, 하나의 소프트웨어 조각이 그 전부에
  적합할 가능성은 낮다. 따라서 여러분은 결국 애플리케이션의 기능을 제공하기 위해 여러 소프트웨어
  조각을 이어 붙이게 된다** (13장, p.540).[^kleppmann2026]

## 특화 도구를 파생으로 잇기

- 대표 예 — **임의의 키워드 질의를 처리하기 위해 OLTP 데이터베이스와 전문 검색 색인(full-text
  search index)을 통합해야 하는 일이 흔하다. PostgreSQL 같은 어떤 데이터베이스는 단순한
  애플리케이션에는 충분할 수 있는 전문 색인 기능을 포함하지만, 더 정교한 검색 설비는 전문
  정보 검색 도구를 요구한다. 반대로 검색 색인은 일반적으로 내구적인 기록 시스템(system of
  record)으로는 그리
  적합하지 않다. 그래서 많은 애플리케이션이 요구사항 전부를 만족시키려면 두 도구를 결합해야
  한다** (13장, p.540).[^kleppmann2026]
- 문제가 커지는 방향 — **데이터 표현의 수가 늘수록 통합 문제는 더 어려워진다. 데이터베이스와
  검색 색인 말고도 어쩌면 분석 시스템(데이터 웨어하우스, 또는 배치·스트림 처리 시스템)에 데이터
  사본을 유지해야 하고; 원본 데이터에서 유도된 객체의 캐시나 비정규화 버전을 유지해야 하며;
  데이터를 기계 학습·분류·랭킹·추천 시스템에 통과시키거나; 데이터 변경에 기반해 알림을 보내야
  한다** (13장, p.540).[^kleppmann2026]

## 데이터플로를 명시한다

- 무엇을 분명히 해야 하는가 — **여러 접근 패턴을 만족시키려고 같은 데이터의 사본을 여러 저장
  시스템에 유지해야 할 때는 입력과 출력에 대해 아주 분명해야 한다. 데이터는 어디에 먼저 쓰이고
  어느 표현이 어느 원천에서 파생되는가? 데이터를 올바른 형식으로 올바른 자리 전부에 어떻게
  넣는가?** (13장, p.541).[^kleppmann2026]
- 한 가지 배치 — **예컨대 데이터가 먼저 기록 시스템 데이터베이스에 쓰이고, 그 데이터베이스에
  가해진 변경이 포착돼(변경 데이터 캡처, Change Data Capture) 같은 순서로 검색 색인에 적용되도록
  배치할 수 있다.
  CDC가 색인을 갱신하는 유일한 방법이면 색인이 전적으로 기록 시스템에서 파생됐고 따라서 그것과
  일관된다고(소프트웨어의 버그를 빼면) 확신할 수 있다. 데이터베이스에 쓰는 것이 이 시스템에
  새 입력을 공급하는 유일한 방법이다** (13장, p.541).[^kleppmann2026] 그 기제는
  [변경 데이터 캡처](../concepts/change-data-capture.md)에 있다.
- 그러지 않았을 때 — **애플리케이션이 검색 색인과 데이터베이스 양쪽에 직접 쓰도록 허용하면
  두 클라이언트가 동시에 충돌하는 쓰기를 보내고 두 저장 시스템이 그것을 다른 순서로 처리하는
  문제가 생긴다. 이 경우 데이터베이스도 검색 색인도 쓰기의 순서를 결정하는 "책임자"가 아니므로
  둘이 모순되는 결정을 내려 서로 영구적으로 불일치하게 될 수 있다** (13장,
  p.541).[^kleppmann2026]
- 그래서 원칙이 하나 나온다 — **모든 사용자 입력을 모든 쓰기의 순서를 결정하는 단일 시스템으로
  깔때기처럼 모을 수 있다면, 같은 순서로 쓰기를 처리해 데이터의 다른 표현을 유도하기가 훨씬
  쉬워진다. 이는 "실무에서의 합의"에서 본 상태 기계 복제(state machine replication) 접근의
  응용이다. CDC를 쓰는지 이벤트 소싱 로그를 쓰는지는 전체 순서(total order)를 정한다는 원칙보다
  덜 중요하다** (13장, p.541).[^kleppmann2026] 그 접근의 본가는
  [복제 상태 기계](../concepts/replicated-state-machine.md)다.
- 그리고 결함 복구가 쉬워진다 — **이벤트 로그에 기반해 파생 데이터 시스템을 갱신하는 것은 흔히
  결정적(deterministic)이고 멱등적(idempotent)으로 만들 수 있어서 결함에서 복구하기가 꽤
  쉬워진다** (13장, p.541).[^kleppmann2026]

## 파생 데이터와 분산 트랜잭션

- 비교의 자리 — **데이터 시스템을 서로 일관되게 유지하는 고전적 접근은 분산 트랜잭션을 포함한다.
  파생 데이터 시스템을 쓰는 접근은 분산 트랜잭션과 비교해 어떤가?** (13장,
  p.541).[^kleppmann2026]
- **추상 수준에서 그들은 다른 수단으로 비슷한 목표를 달성한다. 분산 트랜잭션은 원자적 커밋
  프로토콜을 써서 변경이 원자적으로 적용되도록 보장하고, 로그 기반 시스템은 결정적 재시도와
  멱등성을 통해 정확성을 달성한다** (13장, p.541).[^kleppmann2026]
- **가장 큰 차이는 트랜잭션 시스템이 보통 값이 쓰인 뒤 즉시 최신 값을 읽을 수 있다고 보장하는
  반면, 파생 데이터 시스템은 흔히 비동기적으로 갱신되므로 기본적으로 읽기가 최신임을 보장하지
  않는다는 것이다** (13장, p.542).[^kleppmann2026] 그 보장의 이름과 구현은
  [복제 지연이 만드는 이상](../concepts/replication-lag-anomalies.md)에 있다.
- 실무 판정 — **분산 트랜잭션은 그 성능·운영 비용을 흡수할 의사가 있는 환경에서 성공적으로
  쓰여 왔다. 그러나 XA는 결함 내성과 성능 특성이 나빠서 그 유용성을 심각하게 제한한다. 분산
  트랜잭션을 위한 더 나은 프로토콜을 만드는 것이 가능할 수도 있지만, 그런 프로토콜이 널리
  채택되고 기존 도구와 통합되게 하는 것은 어려울 것이고 곧 일어날 것 같지 않다** (13장,
  p.542).[^kleppmann2026] XA 쪽 서술은
  [XA 트랜잭션과 이종 분산 트랜잭션](../concepts/xa-transactions.md)에 있다.
- 그럼에도 남는 단서 — **좋은 분산 트랜잭션 프로토콜에 대한 광범위한 지원이 없는 상황에서
  로그 기반 파생 데이터가 서로 다른 데이터 시스템을 통합하는 가장 유망한 접근이다. 그렇지만
  자기 쓰기 읽기 같은 보장은 유용하며, 모두에게 "최종 일관성은 불가피하다 — 받아들이고 다루는
  법을 배워라"라고 말하는 것은(적어도 다루는 법에 대한 좋은 지침 없이는) 생산적이지 않다**
  (13장, p.542).[^kleppmann2026]
