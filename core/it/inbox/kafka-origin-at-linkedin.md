# 카프카의 기원

**목차**: [링크드인의 두 시스템](#링크드인의-두-시스템) · [모니터링 시스템](#모니터링-시스템) · [활동 추적 시스템](#활동-추적-시스템) · [왜 하나로 합칠 수 없었나](#왜-하나로-합칠-수-없었나) · [카프카의 탄생과 설계 목표 4가지](#카프카의-탄생과-설계-목표-4가지) · [오픈소스와 상업적 관여](#오픈소스와-상업적-관여) · [이름](#이름) · [이어지는 페이지](#이어지는-페이지)

하나의 질문: **카프카는 어떤 구체적 실패에서 나왔고, 그 실패가 설계 목표를 어떻게
결정했는가.**

- 카프카는 링크드인(LinkedIn)의 데이터 파이프라인 문제를 풀기 위해 만들어졌다. 여러
  유형의 데이터를 다루면서 사용자 활동과 시스템 지표에 대한 깨끗하고 구조화된 데이터를
  실시간으로 제공하는 고성능 메시징 시스템이 목표였다 (1장, p.14).[^shapira2021]

## 링크드인의 두 시스템

### 모니터링 시스템

- 커스텀 수집기와 오픈소스 도구로 지표를 저장·표시했다. CPU 사용률·애플리케이션 성능
  같은 전통적 지표 외에, 모니터링 시스템을 사용해 **하나의 사용자 요청이 내부
  애플리케이션들로 어떻게 전파되는지 들여다보는** 정교한 요청 추적 기능도 있었다 (1장,
  p.14).[^shapira2021]
- 결함 (1장, p.14):[^shapira2021]
  - 폴링(polling) 기반 지표 수집이었고 수집 간격이 컸다.
  - 애플리케이션 소유자가 자기 지표를 스스로 관리할 방법이 없었다.
  - 단순한 작업 대부분에 사람의 개입이 필요한 고접촉(high-touch) 운영이었다.
  - 비일관적이었다 — 시스템마다 같은 측정에 다른 지표 이름을 썼다.

### 활동 추적 시스템

- 프론트엔드 서버가 주기적으로 접속해 XML 형식 메시지 배치를 발행하는 HTTP 서비스였다.
  배치는 오프라인 처리 플랫폼으로 옮겨져 파싱·대조됐다 (1장, p.14).[^shapira2021]
- 결함 (1장, pp.14–15):[^shapira2021]
  - XML 형식이 비일관적이었고 파싱이 계산적으로 비쌌다.
  - 추적하는 사용자 활동 유형을 바꾸려면 프론트엔드와 오프라인 처리 사이에 상당한
    조율 작업이 필요했고, **그러고도 스키마 변경 때마다 시스템이 계속 깨졌다.**
  - 시간 단위 배치로 만들어져 실시간에 쓸 수 없었다.

### 왜 하나로 합칠 수 없었나

- 모니터링과 활동 추적은 같은 백엔드 서비스를 쓸 수 없었다 — 모니터링 서비스는 너무
  투박했고 데이터 형식이 활동 추적에 맞지 않았으며 폴링 모델이 추적의 푸시 모델과
  호환되지 않았다. 반대로 추적 서비스는 지표용으로 쓰기엔 너무 취약했고 배치 지향
  처리가 실시간 모니터링·경보에 맞는 모델이 아니었다 (1장, p.15).[^shapira2021]
- 그런데 두 데이터는 특성을 많이 공유했고 **상관 분석이 매우 바람직했다** — 특정 유형의
  사용자 활동이 애플리케이션 성능에 어떤 영향을 주는지 같은 질문이다. 특정 사용자 활동의
  감소는 그것을 서비스하는 애플리케이션의 문제를 가리킬 수 있는데, 활동 배치 처리에 몇
  시간이 걸리면 대응이 느려진다 (1장, p.15).[^shapira2021]
- 기성 오픈소스 해법을 철저히 조사해 ActiveMQ로 프로토타입을 세웠지만 **당시로서는
  규모를 감당하지 못했다.** 링크드인의 사용 방식에는 취약한 해법이기도 해서 브로커를
  멈추게 하는 결함이 여럿 발견됐고, 이 정지가 클라이언트 연결을 밀리게 해 애플리케이션의
  사용자 요청 처리를 방해했다. 그래서 커스텀 인프라로 가기로 결정했다 (1장,
  p.15).[^shapira2021]

## 카프카의 탄생과 설계 목표 4가지

- 개발팀은 제이 크렙스(Jay Kreps)가 이끌었다. 분산 키-값 저장소 Voldemort의 개발과
  오픈소스 릴리스를 맡았던 수석 소프트웨어 엔지니어다. 초기 팀에는 네하
  나크헤데(Neha Narkhede)가, 나중에 준 라오(Jun Rao)가 있었다 (1장,
  p.15).[^shapira2021]
- 원문 직인용 — 주요 목표 (1장, p.15):[^shapira2021]

> - Decouple producers and consumers by using a push-pull model
> - Provide persistence for message data within the messaging system to allow
>   multiple consumers
> - Optimize for high throughput of messages
> - Allow for horizontal scaling of the system to grow as the data streams grew

- 결과물은 **메시징 시스템 전형의 인터페이스를 가지되 저장 계층은 로그 집적(log
  aggregation) 시스템에 더 가까운** 발행/구독 메시징 시스템이었다. 메시지 직렬화에
  아파치 에이브로를 채택한 것과 결합해, 지표와 사용자 활동 추적을 하루 수십억 메시지
  규모로 효과적으로 처리했다 (1장, pp.15–16).[^shapira2021]
- 규모 기록: 링크드인의 사용량은 **2020년 2월 기준** 하루 7조 개를 넘는 메시지 생산과
  5페타바이트를 넘는 데이터 소비까지 성장했다 (1장, p.16).[^shapira2021]

## 오픈소스와 상업적 관여

- 연표 (1장, p.16):[^shapira2021]
  - 2010년 말 — GitHub에 오픈소스 프로젝트로 공개
  - 2011년 7월 — 아파치 소프트웨어 재단 인큐베이터 프로젝트로 제안·수락
  - 2012년 10월 — 인큐베이터 졸업
- 이후 링크드인 밖에서 견고한 기여자·커미터 공동체를 얻었고, 넷플릭스·우버를 포함해
  세계 최대 데이터 파이프라인 일부에 쓰인다 (1장, p.16).[^shapira2021]
- 링크드인은 Cruise Control·Kafka Monitor·Burrow를 계속 유지한다. 컨플루언트는 상용
  제공물 외에 ksqlDB·스키마 레지스트리·REST 프록시를 커뮤니티 라이선스로 공개했는데,
  **사용 제한이 포함돼 있어 엄밀한 의미의 오픈소스는 아니다** (1장,
  p.16).[^shapira2021]
- 2014년 가을 크렙스·나크헤데·라오가 링크드인을 떠나 컨플루언트(Confluent)를 세웠다.
  개발·엔터프라이즈 지원·교육 제공이 중심이며, 구글과의 파트너십으로 GCP 관리형 카프카
  클러스터를, AWS·애저에서도 유사 서비스를 제공한다. 2016년 시작한 Kafka Summit
  컨퍼런스 시리즈도 조직한다 (1장, p.16).[^shapira2021]
