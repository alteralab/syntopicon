하나의 질문: **원천에서 데이터를 가져오는 이 한 단계가 왜 파이프라인 전체의 신뢰성을
결정하는가.**

## 최대의 병목

- 자리 — **데이터 원천, 쓰고 있는 원천 시스템의 특성, 데이터가 저장되는 방식을 이해한 뒤에는
  데이터를 모아야 한다. 데이터 엔지니어링 수명 주기의 다음 단계는 원천 시스템으로부터의 데이터
  반입(data ingestion)이다** (2장, p.39).[^reis2022]
- 판정 — **우리 경험상 원천 시스템과 반입은 데이터 엔지니어링 수명 주기의 가장 중대한
  병목을 이룬다. 원천 시스템은 보통 직접 통제 밖에 있고 무작위로 응답 불능이 되거나 낮은
  품질의 데이터를 줄 수 있다. 또는 데이터 반입 서비스가 여러 이유로 알 수 없게 작동을 멈출
  수 있다. 그 결과 데이터 흐름이 멈추거나 저장·처리·서빙에 불충분한 데이터를 전달한다**
  (2장, p.40).[^reis2022]
- 파급 — **신뢰할 수 없는 원천과 반입 시스템은 데이터 엔지니어링 수명 주기 전체에 파문
  효과(ripple effect)를 낳는다** (2장, p.40).[^reis2022]
- 그리고 이 단계가 일을 가장 많이 만든다 — **데이터 엔지니어로 일하는 동안 반입은 에너지와
  노력의 상당 부분을 소모할 것이다. 본질적으로 반입은 배관(plumbing)이다 — 파이프를 다른
  파이프에 연결하고, 데이터가 목적지로 일관되고 안전하게 흐르도록 보장하는 것** (7장,
  p.268).[^reis2022]

## 반입이란 무엇인가 — 통합·내부 반입과의 경계

7장은 2장의 서술을 다시 열고 낱말의 경계부터 긋는다. **같은 데이터 이동인데 이름이 셋으로
갈리는 자리**다.

- 정의 — **데이터 반입(data ingestion)은 데이터를 한 곳에서 다른 곳으로 옮기는 과정이다.
  데이터 반입은 데이터 엔지니어링 수명 주기 안에서 원천 시스템으로부터 저장으로의 데이터
  이동을 함의하며, 반입은 중간 단계다** (7장, p.234).[^reis2022]
- 데이터 통합과 다르다 — **데이터 반입을 데이터 통합(data integration)과 빠르게 대조해 볼
  가치가 있다. 데이터 반입이 A 지점에서 B 지점으로의 데이터 이동인 반면, 데이터 통합은 서로
  다른 원천의 데이터를 새로운 데이터셋으로 결합한다. 예컨대 데이터 통합을 써서 CRM 시스템의
  데이터, 광고 분석 데이터, 웹 분석 데이터를 결합해 사용자 프로필을 만들고 이를 데이터
  웨어하우스에 저장할 수 있다. 나아가 리버스 ETL을 써서 이 새로 만든 사용자 프로필을 CRM으로
  되돌려 보내 영업 담당자가 리드 우선순위를 매기는 데 쓰게 할 수 있다** (7장,
  p.234).[^reis2022]
- 내부 반입과도 다르다 — **데이터 반입은 시스템 내부의 내부 반입(internal ingestion)과도
  다르다는 점을 지적한다. 데이터베이스에 저장된 데이터가 한 테이블에서 다른 테이블로 복사되거나
  스트림의 데이터가 일시적으로 캐시되는 것이 그렇다. 우리는 이것을 8장에서 다루는 일반적 데이터
  변환 과정의 또 다른 부분으로 본다** (7장, p.234).[^reis2022]
  - 즉 **경계선은 "시스템을 건너는가"이지 "데이터가 움직이는가"가 아니다.** 같은 복사라도
    시스템 안에서 일어나면 변환 단계의 소관으로 넘어간다. 그쪽은
    [수명 주기의 변환 단계](../concepts/transformation-in-the-lifecycle.md)에 있다.

## 데이터 파이프라인의 정의

- 왜 정의를 새로 내놓는가 — **데이터 파이프라인은 원천 시스템에서 시작하지만, 반입은 데이터
  엔지니어가 데이터 파이프라인 활동을 능동적으로 설계하기 시작하는 단계다. 데이터 엔지니어링
  공간에서는 데이터 이동과 처리 패턴을 둘러싸고 상당한 의례가 벌어진다 — ETL 같은 확립된
  패턴, ELT 같은 신생 패턴, 오래 확립된 실천에 붙은 새 이름(리버스 ETL)과 데이터 공유가
  그렇다** (7장, p.234).[^reis2022]
- 저자들의 정의 — 직인용한다 (7장, p.235):[^reis2022]

  > A data pipeline is the combination of architecture, systems, and processes that move
  > data through the stages of the data engineering lifecycle.

- 이 정의가 **일부러 모호한** 이유 — **우리 정의는 의도적으로 유동적이고 의도적으로 모호하다 —
  데이터 엔지니어가 당면 과제를 해내는 데 필요한 무엇이든 끼워 넣을 수 있게 하기 위해서다.
  데이터 파이프라인은 온프레미스 트랜잭션 시스템에서 데이터를 반입해 모놀리식 프로세서로
  넘기고 데이터 웨어하우스에 쓰는 전통적 ETL 시스템일 수도 있다. 또는 100개 원천에서 데이터를
  당겨 와 20개 넓은 테이블로 결합하고 다섯 개의 다른 ML 모델을 학습시켜 프로덕션에 배포하고
  진행 중 성능을 모니터링하는 클라우드 기반 데이터 파이프라인일 수도 있다. 데이터 파이프라인은
  데이터 엔지니어링 수명 주기 어디에서든 어떤 필요에도 맞을 만큼 유연해야 한다** (7장,
  p.235).[^reis2022]
- 왜 좁은 철학을 고집하지 않는가 — **이 모든 개념은 데이터 파이프라인이라는 발상에 포괄된다.
  다양한 패턴의 세부를 이해하고 현대적 데이터 파이프라인이 그 전부를 포함한다는 것을 아는 것이
  본질적이다. 세계가 데이터 이동에 대한 엄격한 제약을 가진 전통적 모놀리식 접근에서 벗어나
  제품을 실현하기 위해 레고 블록처럼 조립되는 클라우드 서비스의 열린 생태계로 옮겨 감에 따라,
  데이터 엔지니어는 좁은 데이터 이동 철학을 고수하기보다 원하는 결과를 달성할 올바른 도구를
  쓰는 것을 우선한다** (7장, p.234).[^reis2022]

## 반입 단계의 공학 질문

- 시스템을 설계하거나 짓기 전에 던지는 일차 질문들 (2장, p.40):[^reis2022]
  - **내가 반입하려는 데이터의 유스케이스는 무엇인가? 같은 데이터셋의 여러 버전을 만드는
    대신 이 데이터를 재사용할 수 있는가?**
  - **이 데이터를 생성하고 반입하는 시스템은 신뢰할 만한가, 그리고 데이터는 내가 필요할 때
    가용한가?**
  - **반입 이후 데이터의 목적지는 어디인가?**
  - **데이터에 얼마나 자주 접근해야 하는가? 데이터는 보통 어떤 볼륨으로 도착하는가?**
  - **데이터는 어떤 형식인가? 하류의 저장·변환 시스템이 이 형식을 다룰 수 있는가?**
  - **원천 데이터는 하류에서 즉시 쓰기 좋은 상태인가? 그렇다면 얼마 동안 그런가, 그리고
    무엇이 그것을 못 쓰게 만들 수 있는가?**
  - **데이터가 스트리밍 원천에서 온다면 목적지에 닿기 전에 변환돼야 하는가? 스트림 자체
    안에서 데이터를 변환하는 인플라이트 변환(in-flight transformation)이 적절하겠는가?**
- 7장이 같은 목록을 다시 낸다. **거의 같지만 두 항목이 다르다** (7장, p.235):[^reis2022]
  - **반입하는 데이터의 유스케이스는 무엇인가? / 이 데이터를 재사용하고 같은 데이터셋의 여러
    버전을 반입하는 것을 피할 수 있는가? / 데이터는 어디로 가는가, 목적지는 무엇인가? /
    데이터는 원천에서 얼마나 자주 갱신돼야 하는가? / 예상 데이터 볼륨은 얼마인가? / 데이터는
    어떤 형식인가, 하류 저장과 변환이 이 형식을 받아들이는가? / 원천 데이터가 즉시 하류에서
    쓸 상태인가 — 즉 좋은 품질인가? 서빙하려면 어떤 후처리가 필요한가? 데이터 품질 리스크는
    무엇인가(예: 웹사이트에 대한 봇 트래픽이 데이터를 오염시킬 수 있는가)? / 데이터가 스트리밍
    원천이라면 하류 반입을 위해 인플라이트 처리가 필요한가?**
  - 2장 목록에만 있는 것이 **"이 데이터를 생성하고 반입하는 시스템은 신뢰할 만한가"** 이고,
    7장 목록에만 있는 것이 **데이터 품질 리스크**(봇 트래픽 예시)다. 7장에서 신뢰성은 질문
    목록에서 빠지는 대신 아래 [신뢰성과 내구성](#신뢰성과-내구성)이라는 독립 설계 축으로
    승격된다. 목록의 차이가 곧 7장이 2장에 더한 것이다.

## 설계를 가르는 여덟 축

- **이 질문들은 배치 반입과 스트리밍 반입의 밑을 관통하며 만들고 짓고 유지할 기반 아키텍처에
  적용된다. 데이터를 얼마나 자주 반입하든 반입 아키텍처를 설계할 때 다음 요인들을 고려하고
  싶을 것이다** (7장, pp.235–236):[^reis2022]
  - **유계 대 무계(bounded versus unbounded)**
  - **빈도(frequency)**
  - **동기 대 비동기(synchronous versus asynchronous)**
  - **직렬화와 역직렬화(serialization and deserialization)**
  - **처리량과 확장성(throughput and scalability)**
  - **신뢰성과 내구성(reliability and durability)**
  - **페이로드(payload)**
  - **푸시 대 풀 대 폴 패턴(push versus pull versus poll patterns)**

## 유계 데이터와 무계 데이터

- 정의 — **3장에서 기억하듯 데이터는 두 형태로 온다: 유계와 무계다. 무계 데이터(unbounded
  data)는 이벤트가 일어나는 대로 현실에 존재하는 데이터로, 산발적이든 연속적이든 진행 중이며
  흐른다. 유계 데이터(bounded data)는 시간 같은 어떤 종류의 경계를 가로질러 데이터를 통에
  담는 편리한 방식이다** (7장, p.236).[^reis2022]
- 저자들이 세우는 만트라 — **이 만트라를 채택하자: 모든 데이터는 경계 지어지기 전까지
  무계다(All data is unbounded until it's bounded)** (7장, p.236).[^reis2022]
  - 저자들 스스로 예외를 인정한다 — **많은 만트라가 그렇듯 이것도 100% 시간 내내 정확하지는
    않다. 내가 오늘 오후에 갈겨쓴 장보기 목록은 유계 데이터다. 나는 그것을 의식의 흐름(무계
    데이터)으로 종잇조각에 썼고, 이제 그 생각들은 마트에서 사야 할 것들의 목록(유계 데이터)으로
    존재한다** (7장, pp.236–237).[^reis2022]
  - **그러나 이 발상은 업무 맥락에서 다루게 될 대다수 데이터에 대해 실용적 목적으로 옳다.
    예컨대 온라인 소매업체는 사업이 망하거나 경제가 멈추거나 태양이 폭발할 때까지 하루 24시간
    고객 트랜잭션을 처리할 것이다** (7장, p.237).[^reis2022]
- 그래서 배치는 인공물이다 — **업무 프로세스는 오랫동안 이산 배치를 잘라 냄으로써 데이터에
  인공적 경계를 부과해 왔다. 데이터의 진짜 무계성을 염두에 두라 — 스트리밍 반입 시스템은
  단지 데이터의 무계한 본성을 보존해 수명 주기의 후속 단계들도 그것을 연속적으로 처리할 수
  있게 하는 도구일 뿐이다** (7장, p.237).[^reis2022]

## 빈도 — 배치·마이크로배치·실시간

- **데이터 엔지니어가 데이터 반입 프로세스를 설계할 때 내려야 하는 결정적 결정 중 하나가
  데이터 반입 빈도다. 반입 프로세스는 배치·마이크로배치·실시간일 수 있다** (7장,
  p.237).[^reis2022]
- 스펙트럼의 실물 — **반입 빈도는 느림에서 빠름까지 극적으로 다르다. 느린 쪽 끝에서 업체는
  세금 데이터를 회계 법인에 1년에 한 번 보낼 수 있다. 빠른 쪽에서 CDC 시스템은 원천
  데이터베이스에서 새 로그 갱신을 1분에 한 번 회수할 수 있다. 더 빠르게는 시스템이 IoT
  센서에서 이벤트를 연속적으로 반입해 수 초 안에 처리할 수 있다. 데이터 반입 빈도는 유스케이스와
  기술에 따라 한 회사 안에서도 자주 섞인다** (7장, p.237).[^reis2022]
- **"실시간"에 따옴표가 붙는 이유** — **우리는 "실시간" 반입 패턴이 점점 흔해지고 있음을
  지적한다. 실시간에 따옴표를 붙이는 이유는 진정으로 실시간인 반입 시스템은 없기 때문이다.
  어떤 데이터베이스·큐·파이프라인도 대상 시스템에 데이터를 전달하는 데 내재적 지연을 갖는다.
  준실시간(near real-time)이라 말하는 것이 더 정확하지만, 우리는 간결함을 위해 실시간을 자주
  쓴다. 준실시간 패턴은 일반적으로 명시적 갱신 빈도를 없앤다 — 이벤트가 도착하는 대로 하나씩,
  또는 마이크로배치(micro-batches, 짧은 시간 간격 단위의 배치)로 파이프라인에서 처리된다.
  이 책에서 우리는 실시간과 스트리밍을 서로 바꿔 쓸 것이다** (7장, p.237).[^reis2022]
- 스트리밍을 깔아도 배치는 남는다 — **스트리밍 데이터 반입 프로세스를 쓰더라도 하류의 배치
  처리는 상대적으로 표준이다. 이 글을 쓰는 시점에 ML 모델은 일반적으로 배치 기준으로 학습되며,
  연속 온라인 학습이 점점 널리 퍼지고 있기는 하다. 데이터 엔지니어가 배치 구성 요소 없이 순수
  준실시간 파이프라인을 지을 선택지를 갖는 경우는 드물다. 대신 그들은 배치 경계가 어디에서
  일어날지를 고른다 — 즉 데이터 엔지니어링 수명 주기 데이터가 어디에서 배치로 쪼개질지를**
  (7장, pp.237–238).[^reis2022]
- 그 경계가 병목이 된다 — **데이터가 일단 배치 프로세스에 닿으면 배치 빈도가 모든 하류 처리의
  병목이 된다** (7장, p.238).[^reis2022]
- 반대로 스트리밍이 자연스러운 원천도 있다 — **덧붙여 스트리밍 시스템은 많은 데이터 원천 유형에
  최적이다. IoT 응용에서 전형적 패턴은 각 센서가 일어나는 대로 이벤트나 측정값을 스트리밍
  시스템에 쓰는 것이다. 이 데이터를 데이터베이스에 직접 쓸 수도 있지만 Amazon Kinesis나 Apache
  Kafka 같은 스트리밍 반입 플랫폼이 이 응용에 더 잘 맞는다. 소프트웨어 애플리케이션도 백엔드
  데이터베이스에서 이벤트와 상태 정보를 당겨 오는 추출 프로세스를 기다리는 대신 이벤트가 일어나는
  대로 메시지 큐에 씀으로써 비슷한 패턴을 채택할 수 있다. 이 패턴은 이미 큐를 통해 메시지를
  교환하는 이벤트 기반 아키텍처에 예외적으로 잘 통한다. 그리고 다시, 스트리밍 아키텍처는
  일반적으로 배치 처리와 공존한다** (7장, p.238).[^reis2022]

## 배치는 스트림의 특수한 처리 방식이다

- 이 책이 세우는 관점 — **우리가 다루는 사실상 모든 데이터는 본질적으로 스트리밍이다.
  데이터는 거의 언제나 그 원천에서 연속적으로 생산되고 갱신된다. 배치 반입은 단지 이
  스트림을 큰 덩어리로 처리하는 특화되고 편리한 방식일 뿐이다 — 예컨대 하루치 데이터
  전부를 한 배치로 다루는 것** (2장, p.40).[^reis2022]
  - 이 관점은 Kleppmann이 배치와 스트림을 유한·무한 입력의 차이로 가르는 서술과 층위가
    다르다. 저자들은 **처리 대상의 존재론**(모든 데이터는 스트림)을 말하고, 그쪽은
    **계산의 종료 조건**(입력이 유한한가)을 말한다. 후자의 축은
    [배치 처리](../synthesis/batch-processing.md)와
    [스트림 처리](../synthesis/stream-processing.md)에 있다.
  - 7장의 만트라(**모든 데이터는 경계 지어지기 전까지 무계다**)가 같은 주장의 강한
    판본이다 — 위 [유계 데이터와 무계 데이터](#유계-데이터와-무계-데이터).
- **스트리밍 반입은 하류 시스템 — 다른 애플리케이션이든, 데이터베이스든, 분석 시스템이든 —
  에 연속적이고 실시간인 방식으로 데이터를 제공하게 해 준다. 여기서 실시간(또는 준실시간)은
  데이터가 생산된 뒤 짧은 시간(예: 1초 미만) 안에 하류 시스템에서 가용해진다는 뜻이다.
  실시간이라 부를 자격을 주는 지연은 도메인과 요구사항에 따라 다르다** (2장,
  p.41).[^reis2022]
- 배치의 발동 조건과 그 대가 — **배치 데이터는 미리 정해진 시간 간격으로, 또는 데이터가 미리
  설정된 크기 임계에 닿을 때 반입된다. 배치 반입은 한 방향 문(one-way door)이다 — 데이터가
  일단 배치로 쪼개지고 나면 하류 소비자의 지연은 본질적으로 제약된다** (2장,
  p.41).[^reis2022]
- 왜 배치가 기본이었나 — **레거시 시스템의 한계 때문에 배치는 오랫동안 데이터를 반입하는
  기본 방식이었다. 배치 처리는 특히 분석과 ML에서 하류 소비를 위해 데이터를 반입하는 극히
  인기 있는 방식으로 남아 있다** (2장, p.41).[^reis2022]
- 무엇이 바뀌었나 — **그러나 많은 시스템에서 저장과 연산이 분리된 것, 그리고 이벤트 스트리밍·
  처리 플랫폼이 흔해진 것이 데이터 스트림의 연속 처리를 훨씬 접근 가능하고 점점 더 인기
  있게 만든다. 선택은 대체로 유스케이스와 데이터 적시성에 대한 기대에 달렸다** (2장,
  p.41).[^reis2022]

## 동기 반입과 비동기 반입

- 동기의 정의 — **동기 반입(synchronous ingestion)에서는 원천·반입·목적지가 복잡한 의존을
  가지며 강하게 결합된다. 데이터 엔지니어링 수명 주기의 각 단계가 서로 직접 의존하는 프로세스
  A·B·C를 갖는다. A가 실패하면 B와 C는 시작할 수 없고, B가 실패하면 C가 시작하지 않는다. 이런
  유형의 동기 워크플로는 원천 시스템에서 추출한 데이터가 데이터 웨어하우스로 적재되기 전에
  변환돼야 하는 옛 ETL 시스템에서 흔하다. 반입 하류의 프로세스는 배치의 모든 데이터가 반입될
  때까지 시작할 수 없다. 반입이나 변환 프로세스가 실패하면 전체 프로세스를 다시 돌려야 한다**
  (7장, p.238).[^reis2022]
- 저자들이 드는 실패 사례 — **어느 회사에서 변환 프로세스 자체가 수십 개의 강하게 결합된
  동기 워크플로 연쇄였고 전체 프로세스가 끝나는 데 24시간이 넘게 걸렸다. 그 변환 파이프라인의
  어느 단계라도 실패하면 전체 변환 프로세스를 처음부터 다시 시작해야 했다! 이 사례에서 우리는
  프로세스가 실패한 뒤 또 실패하는 것을 보았고, 존재하지 않거나 알아볼 수 없는 오류 메시지
  때문에 파이프라인을 고치는 것은 진단과 치료에 일주일 넘게 걸린 두더지 잡기 게임이었다.
  그동안 업무는 갱신된 리포트를 받지 못했다. 사람들은 기뻐하지 않았다** (7장,
  p.238).[^reis2022]
- 비동기의 정의 — **비동기 반입(asynchronous ingestion)에서는 의존이 이제 개별 이벤트 수준에서
  작동할 수 있다 — 마이크로서비스로 지은 소프트웨어 백엔드에서와 아주 비슷하다. 개별 이벤트는
  반입되는 즉시 저장에서 가용해진다** (7장, p.239).[^reis2022]
- 저자들이 드는 AWS 예시 — **AWS의 웹 애플리케이션이 Amazon Kinesis Data Streams(여기서
  버퍼 역할)로 이벤트를 방출하는 예를 보자. 스트림은 Apache Beam이 읽어 파싱하고 보강한 뒤
  두 번째 Kinesis 스트림으로 전달한다. Kinesis Data Firehose가 이벤트를 말아 Amazon S3에
  객체로 쓴다** (7장, p.239).[^reis2022]
- 큰 그림 — **큰 아이디어는, 입력 배치가 닫히고 특정 시간 조건이 충족될 때 각 단계마다 배치
  프로세스가 도는 비동기 처리에 의존하는 대신, 비동기 파이프라인의 각 단계가 데이터 항목이
  Beam 클러스터 전역에서 병렬로 가용해지는 대로 처리할 수 있다는 것이다. 처리율은 가용 자원에
  달렸다. Kinesis Data Stream은 충격 흡수재(shock absorber) 역할을 해 부하를 조절하고, 그래서
  이벤트율 급등이 하류 처리를 압도하지 않는다. 이벤트율이 낮고 백로그가 해소되면 이벤트는
  파이프라인을 빠르게 통과한다** (7장, p.239).[^reis2022]
  - 원문이 이 문단에서 "비동기 처리에 의존하는 대신"이라 쓰지만 문맥상 대비되는 것은
    **배치 처리**다 — 바로 이어지는 종속절이 배치 프로세스를 서술하고, 이 절 전체가
    비동기의 이점을 논하는 자리다. 원문 표현을 그대로 옮기되 이 어긋남을 적어 둔다.
    #hypothesis

## 직렬화와 역직렬화

- 왜 반입의 설계 축인가 — **데이터를 원천에서 목적지로 옮기는 것은 직렬화와 역직렬화를
  수반한다. 상기하자면 직렬화(serialization)는 원천의 데이터를 인코딩하고 전송과 중간 저장
  단계를 위해 자료 구조를 준비하는 것을 뜻한다** (7장, p.239).[^reis2022]
- 실패 양상이 조용하다 — **데이터를 반입할 때 목적지가 받는 데이터를 역직렬화할 수 있는지
  확인하라. 우리는 원천에서 반입됐지만 데이터가 제대로 역직렬화될 수 없어 목적지에서 비활성
  상태로 쓸 수 없게 앉아 있는 데이터를 본 적이 있다** (7장, p.239).[^reis2022]
  - 형식의 카탈로그는 [데이터 인코딩 형식](../concepts/data-encoding-formats.md)에,
    같은 재료를 저장 쪽에서 본 것은
    [데이터 저장의 원료](../concepts/storage-raw-ingredients.md)의 직렬화 절에 있다.

## 처리량과 확장성

- **이론상 반입은 결코 병목이어서는 안 된다. 실무에서 반입 병목은 꽤 표준적이다. 데이터
  볼륨이 커지고 요구사항이 바뀌면서 데이터 처리량과 시스템 확장성이 결정적이 된다. 원하는
  데이터 처리량에 유연하게 맞추도록 확장·축소되게 시스템을 설계하라** (7장,
  p.239).[^reis2022]
- 상류가 죽었다 살아나는 순간이 시험대다 — **데이터를 어디에서 반입하는지가 크게 중요하다.
  생성되는 대로 데이터를 받고 있다면 상류 시스템에 하류 반입 파이프라인에 영향을 줄 문제가
  있겠는가? 예컨대 원천 데이터베이스가 내려간다고 하자. 다시 온라인이 되어 밀린 데이터 적재를
  백필하려 할 때, 반입이 이 갑작스러운 밀린 데이터 유입을 따라갈 수 있겠는가?** (7장,
  pp.239–240).[^reis2022]
- 버스티 반입에는 버퍼가 필요하다 — **고려할 또 하나는 급증하는(bursty) 데이터 반입을 다루는
  능력이다. 데이터 생성은 일정한 속도로 일어나는 경우가 드물고 자주 밀물과 썰물을 탄다. 내장
  버퍼링(built-in buffering)은 데이터가 유실되지 않도록 속도 급등 동안 이벤트를 모으는 데
  필요하다. 버퍼링은 시스템이 확장하는 동안의 시간을 잇고 저장 시스템이 동적으로 확장 가능한
  시스템에서도 급증을 수용하게 한다** (7장, p.240).[^reis2022]
- 저자들의 권고 — **가능하면 처리량 확장을 대신 다뤄 주는 관리형 서비스를 쓰라. 서버·샤드·
  워커를 추가해 이 작업을 수동으로 해낼 수 있지만, 이는 흔히 가치를 더하는 일이 아니고 무언가를
  놓칠 좋은 기회다. 이 무거운 일의 상당 부분은 이제 자동화돼 있다. 그럴 필요가 없다면 데이터
  반입 바퀴를 다시 발명하지 마라** (7장, p.240).[^reis2022]

## 신뢰성과 내구성

- 두 낱말의 정의 — **신뢰성과 내구성은 데이터 파이프라인의 반입 단계에서 필수적이다.
  신뢰성(reliability)은 반입 시스템의 높은 가동 시간과 적절한 페일오버를 수반한다.
  내구성(durability)은 데이터가 유실되거나 손상되지 않게 하는 것을 수반한다** (7장,
  p.240).[^reis2022]
- 둘이 연결되는 자리 — **어떤 데이터 원천(예: IoT 장치와 캐시)은 올바로 반입되지 않으면
  데이터를 보유하지 않을 수 있다. 일단 잃으면 영영 사라진다. 이 의미에서 반입 시스템의
  신뢰성이 곧바로 생성된 데이터의 내구성으로 이어진다. 데이터가 반입되고 나면 하류 프로세스는
  일시적으로 고장 나더라도 이론상 늦게 돌 수 있다** (7장, p.240).[^reis2022]
- 비용이 양쪽에 있다 — **우리 조언은 데이터 유실의 영향과 비용에 기반해 리스크를 평가하고
  적절한 수준의 이중화와 자가 치유를 짓는 것이다. 신뢰성과 내구성은 직접비와 간접비를 모두
  갖는다. 예컨대 AWS 영역이 내려가도 반입 프로세스가 계속되겠는가? 리전 전체는? 전력망이나
  인터넷은? 물론 공짜는 없다. 이것이 얼마나 비쌀 것인가? 고도로 이중화된 시스템을 짓고 하루
  24시간 대기 팀을 두어 장애를 처리할 수도 있다. 이는 클라우드와 인건비가 금지적이 되고(직접비)
  진행 중 작업이 팀에 상당한 부담을 준다(간접비)는 뜻이기도 하다. 단일한 정답은 없으며 신뢰성과
  내구성 결정의 비용과 편익을 평가해야 한다** (7장, p.240).[^reis2022]
- 한계의 인정 — **모든 가능한 시나리오에서 신뢰성 있고 내구성 있게 데이터를 반입하는 시스템을
  지을 수 있다고 가정하지 마라. 미국 연방정부의 거의 무한한 예산조차 이를 보장할 수 없다. 많은
  극단적 시나리오에서 데이터를 반입하는 것은 사실 중요하지 않다. 독립 전력을 갖춘 지하 벙커에
  다중 에어갭 데이터센터를 짓더라도 인터넷이 내려가면 반입할 것이 거의 없다. 신뢰성과 내구성의
  트레이드오프와 비용을 지속적으로 평가하라** (7장, p.240).[^reis2022]

## 페이로드

- 정의 — **페이로드(payload)는 반입하고 있는 데이터셋이며 종류·형상·크기·스키마와 데이터
  타입·메타데이터 같은 특성을 갖는다** (7장, p.241).[^reis2022]
- **종류(kind)** — **다루는 데이터의 종류는 데이터 엔지니어링 수명 주기에서 하류에서 어떻게
  다뤄지는지에 직접 영향을 준다. 종류는 타입과 형식으로 이뤄진다. 데이터는 타입을 갖는다 —
  테이블형·이미지·비디오·텍스트 등. 타입은 데이터 형식, 즉 데이터가 바이트·이름·파일 확장자로
  표현되는 방식에 직접 영향을 준다. 예컨대 테이블형 데이터는 CSV나 Parquet 같은 형식일 수
  있고, 각 형식은 직렬화·역직렬화를 위한 다른 바이트 패턴을 갖는다. 또 다른 데이터 종류는
  이미지이며 JPG나 PNG 형식을 갖고 본질적으로 비구조적이다** (7장, p.241).[^reis2022]
- **형상(shape)** — **모든 페이로드는 그 차원을 서술하는 형상을 갖는다. 데이터 형상은 데이터
  엔지니어링 수명 주기 전체에 걸쳐 결정적이다. 예컨대 이미지의 픽셀과 RGB 차원은 딥러닝 모델을
  학습시키는 데 필요하다. 또 다른 예로, CSV 파일을 데이터베이스 테이블로 임포트하려는데 CSV가
  데이터베이스 테이블보다 컬럼이 많으면 임포트 과정에서 오류가 날 가능성이 크다** (7장,
  p.241).[^reis2022] 저자들이 드는 종류별 형상 (7장, p.241):[^reis2022]
  - **테이블형 — 데이터셋의 행과 열의 수, 흔히 M행 N열로 표현된다.**
  - **반구조 JSON — 키-값 쌍, 그리고 하위 요소와 함께 일어나는 중첩 깊이.**
  - **비구조 텍스트 — 본문의 단어·문자·바이트 수.**
  - **이미지 — 너비·높이·RGB 색 깊이(예: 픽셀당 8비트).**
  - **비압축 오디오 — 채널 수(예: 스테레오는 둘), 샘플 깊이(예: 샘플당 16비트), 샘플
    레이트(예: 48kHz), 길이(예: 10,003초).**
- **크기(size)** — **데이터의 크기는 페이로드의 바이트 수를 서술한다. 페이로드는 단일 바이트에서
  테라바이트 이상까지 크기가 다양할 수 있다. 페이로드의 크기를 줄이기 위해 ZIP·TAR 같은 다양한
  형식으로 압축할 수 있다** (7장, pp.241–242).[^reis2022]
  - 청킹 — **거대한 페이로드는 청크로 쪼갤 수도 있는데, 이는 페이로드를 더 작은 부분집합으로
    나눠 효과적으로 크기를 줄인다. 거대한 파일을 클라우드 오브젝트 저장이나 데이터 웨어하우스에
    적재할 때 이는 흔한 실천인데, 작은 개별 파일이 네트워크로 전송하기 더 쉽기 때문이다(특히
    압축돼 있으면). 더 작게 청크된 파일들이 목적지로 보내지고 모든 데이터가 도착한 뒤 재조립된다**
    (7장, p.242).[^reis2022]
- **스키마와 데이터 타입** — **많은 데이터 페이로드가 스키마를 갖는다 — 테이블형과 반구조
  데이터가 그렇다. 이 장에서 앞서 언급했듯 스키마는 필드와 그 필드 안 데이터의 타입을 서술한다.
  비구조 텍스트·이미지·오디오 같은 다른 데이터는 명시적 스키마나 데이터 타입을 갖지 않는다.
  그러나 형상·데이터·파일 형식·인코딩 등에 대한 기술적 파일 설명이 함께 올 수 있다** (7장,
  p.242).[^reis2022]
  - 진짜 어려움은 연결이 아니다 — **다양한 방식(파일 내보내기·CDC·JDBC/ODBC 등)으로
    데이터베이스에 연결할 수 있지만 연결 자체는 쉽다. 위대한 공학적 도전은 기저 스키마를
    이해하는 것이다. 애플리케이션은 데이터를 다양한 방식으로 조직하고, 엔지니어는 데이터를
    이해하기 위해 데이터의 조직과 관련 갱신 패턴에 친숙해져야 한다. 이 문제는 자바나 파이썬
    같은 언어에서 객체 구조에 기반해 스키마를 자동 생성하는 객체 관계 매핑(ORM)의 인기 때문에
    다소 악화됐다. 객체 지향 언어의 자연스러운 구조는 흔히 운영 데이터베이스에서 지저분한
    무언가로 매핑된다. 데이터 엔지니어는 애플리케이션 코드의 클래스 구조에 친숙해질 필요가 있을
    수 있다** (7장, p.242).[^reis2022]
  - API도 마찬가지다 — **스키마는 데이터베이스만의 것이 아니다. 논의했듯 API도 스키마
    복잡성을 제시한다. 많은 벤더 API가 분석용 데이터를 준비해 주는 친절한 리포팅 메서드를
    갖는다. 다른 경우에 엔지니어는 그렇게 운이 좋지 않다. API는 기저 시스템 주위의 얇은 래퍼라
    데이터를 쓰려면 엔지니어가 애플리케이션 내부를 이해해야 한다** (7장, p.242).[^reis2022]
  - 언제부터 봐야 하는가 — **원천 스키마에서 반입하는 것과 관련된 작업의 상당 부분은 데이터
    엔지니어링 수명 주기의 변환 단계에서 일어나며 이는 8장에서 논한다. 우리가 이 논의를 여기에
    둔 이유는 데이터 엔지니어가 새 원천에서 데이터를 반입할 계획을 세우자마자 원천 스키마 연구를
    시작해야 하기 때문이다** (7장, p.242).[^reis2022]
- **스키마 변경의 탐지와 처리** — **스키마의 변경은 원천 시스템에서 자주 일어나며 흔히 데이터
  엔지니어의 통제 밖에 있다. 스키마 변경의 예로는 새 컬럼 추가·컬럼 타입 변경·새 테이블 생성·
  컬럼 이름 변경이 있다** (7장, p.243).[^reis2022]
  - 자동화는 양날이다 — **반입 도구가 스키마 변경 탐지를 자동화하고 심지어 대상 테이블을 자동
    갱신하는 것이 점점 흔해지고 있다. 궁극적으로 이것은 다소 엇갈린 축복이다. 스키마 변경은
    여전히 스테이징과 반입 하류의 파이프라인을 깨뜨릴 수 있다** (7장, p.243).[^reis2022]
  - **엔지니어는 여전히 변경에 자동으로 대응하고 자동으로 수용할 수 없는 변경에 경보를 울리는
    전략을 구현해야 한다. 자동화는 훌륭하지만 이 데이터에 의존하는 분석가와 데이터 과학자도
    기존 가정을 위반하는 스키마 변경을 통보받아야 한다. 자동화가 변경을 수용할 수 있더라도 새
    스키마가 리포트와 모델의 성능에 악영향을 줄 수 있다. 스키마 변경을 하는 사람과 그 변경에
    영향을 받는 사람 사이의 소통은 스키마 변경을 검사하는 신뢰할 만한 자동화만큼 중요하다**
    (7장, p.243).[^reis2022]
- **스키마 레지스트리** — **스트리밍 데이터에서는 모든 메시지가 스키마를 가지며 이 스키마는
  프로듀서와 컨슈머 사이에서 진화할 수 있다. 스키마 레지스트리(schema registry)는 끊임없이
  변하는 스키마 앞에서 스키마와 데이터 타입 무결성을 유지하는 데 쓰이는 메타데이터 저장소다.
  스키마 레지스트리는 스키마 버전과 이력도 추적할 수 있다. 그것은 메시지의 데이터 모델을
  서술해 프로듀서와 컨슈머 사이의 일관된 직렬화·역직렬화를 허용한다. 스키마 레지스트리는 대부분의
  주요 데이터 도구와 클라우드에서 쓰인다** (7장, p.243).[^reis2022]
  - 이 패턴의 구현 실물은
    [카프카 직렬화와 스키마 레지스트리](../concepts/kafka-serialization-and-schema-registry.md)에
    있다. 그쪽은 에이브로 스키마 ID를 레코드에서 떼어 내는 기제까지 내려간다.
- **메타데이터** — **방금 다룬 명백한 특성 외에 페이로드는 흔히 메타데이터를 담는데, 이는
  2장에서 처음 논했다. 메타데이터는 데이터에 관한 데이터다. 메타데이터는 데이터 자체만큼
  결정적일 수 있다. 데이터 레이크에 대한 초기 접근의 — 또는 데이터 슈퍼펀드 부지가 될 수 있었던
  데이터 늪의 — 유의한 한계 중 하나가 메타데이터에 대한 완전한 무관심이었다. 데이터에 대한
  상세한 서술이 없으면 그것은 거의 가치가 없을 수 있다** (7장, p.243).[^reis2022]

## 스트리밍 우선을 고르기 전에

- 저자들이 던지라는 질문들 (2장, pp.41–42):[^reis2022]
  - **실시간으로 반입하면 하류 저장 시스템이 그 데이터 흐름 속도를 감당할 수 있는가?**
  - **밀리초 단위 실시간 반입이 필요한가? 아니면 이를테면 매 분 데이터를 모아 반입하는
    마이크로배치(micro-batch) 접근으로 충분한가?**
  - **스트리밍 반입의 유스케이스는 무엇인가? 스트리밍을 구현해 실현하는 구체적 이득은
    무엇인가? 실시간으로 데이터를 받으면 배치보다 나아지는 어떤 행동을 취할 수 있는가?**
  - **스트리밍 우선 접근이 그냥 배치를 하는 것보다 시간·돈·유지보수·다운타임·기회비용
    면에서 더 비싸지 않겠는가?**
  - **인프라가 실패해도 내 스트리밍 파이프라인과 시스템은 신뢰할 만하고 이중화돼 있는가?**
  - **유스케이스에 가장 적절한 도구는 무엇인가? 관리형 서비스(Amazon Kinesis, Google Cloud
    Pub/Sub, Google Cloud Dataflow)를 써야 하는가, 아니면 카프카·플링크·스파크·펄사 등의
    인스턴스를 직접 세워야 하는가? 후자라면 누가 관리할 것인가? 비용과 트레이드오프는?**
  - **ML 모델을 배포한다면 온라인 예측과 어쩌면 연속 학습으로 어떤 이득을 얻는가?**
  - **살아 있는 프로덕션 인스턴스에서 데이터를 받는가? 그렇다면 반입 프로세스가 이 원천
    시스템에 주는 영향은 무엇인가?**
- 저자들의 권고 — **스트리밍 우선은 좋은 생각처럼 보일 수 있지만 늘 단순하지는 않다. 추가
  비용과 복잡성이 본질적으로 발생한다. 많은 훌륭한 반입 프레임워크가 배치와 마이크로배치
  양식을 모두 다룬다. 우리는 배치가 모델 학습과 주간 리포팅 같은 흔한 유스케이스에 훌륭한
  접근이라고 본다. 배치 대비 트레이드오프를 정당화하는 업무 유스케이스를 식별한 뒤에만
  진짜 실시간 스트리밍을 채택하라** (2장, p.42).[^reis2022]

## 푸시·풀·폴

- 정의 — **데이터 반입의 푸시(push) 모델에서는 원천 시스템이 데이터베이스든 객체 저장소든
  파일시스템이든 타깃으로 데이터를 써 낸다. 풀(pull) 모델에서는 원천 시스템에서 데이터를
  회수해 온다** (2장, p.42).[^reis2022]
- 경계가 흐리다 — **푸시와 풀 패러다임 사이의 선은 꽤 흐릿할 수 있다. 데이터는 데이터
  파이프라인의 여러 단계를 지나가면서 흔히 밀리기도 하고 당겨지기도 한다** (2장,
  p.42).[^reis2022]
- 7장이 셋째 패턴을 더한다 — **당기기와 관련된 또 하나의 패턴이 데이터에 대한 폴링(polling)이다.
  폴링은 변경이 있는지 데이터 원천을 주기적으로 확인하는 것을 수반한다. 변경이 탐지되면 목적지는
  일반적인 풀 상황처럼 데이터를 당겨 온다** (7장, p.244).[^reis2022]
  - 즉 **폴은 풀의 부분집합이 아니라 풀 앞에 붙는 탐지 단계**다. 저자들의 그림에서 목적지가
    먼저 "변경이 있는가"를 묻고, 원천이 "그렇다"고 답한 뒤에 당기기가 일어난다 (7장, p.244,
    그림 7-9).[^reis2022] 아래 [배치 반입 패턴](../concepts/batch-ingestion-patterns.md)의
    타임스탬프 기반 CDC가 이 폴 패턴의 실물이다.
- ETL은 풀이다 — **배치 지향 반입 워크플로에서 흔히 쓰이는 ETL(extract, transform, load)
  프로세스를 보자. ETL의 추출(E) 부분은 우리가 풀 반입 모델을 다루고 있음을 분명히 한다.
  전통적 ETL에서 반입 시스템은 고정된 스케줄로 현재 원천 테이블 스냅샷을 질의한다** (2장,
  p.42).[^reis2022]
  - 다만 7장은 추출이 반드시 풀은 아니라고 단서를 단다 — **추출은 원천 시스템에서 데이터를
    가져오는 것을 뜻한다. 추출이 데이터를 당기는 것을 함의하는 듯 보이지만 푸시 기반일 수도
    있다** (7장, p.246).[^reis2022] 실제로 저자들은 파일 기반 내보내기를 **푸시 기반 반입
    패턴**으로 분류한다 (7장, p.246).[^reis2022] 2장의 "E는 풀이다"라는 서술과 나란히
    읽어야 한다 — 전자는 전통적 ETL의 관행을, 후자는 낱말의 논리적 범위를 말한다.
- CDC는 방식마다 다르다 (2장, p.42):[^reis2022]
  - **한 흔한 방법은 원천 데이터베이스에서 행이 바뀔 때마다 메시지를 촉발한다. 이 메시지는
    큐로 밀리고 반입 시스템이 그것을 집어 간다.**
  - **또 다른 흔한 CDC 방법은 데이터베이스의 모든 커밋을 기록하는 이진 로그(binary log)를
    쓴다. 데이터베이스는 자기 로그로 민다. 반입 시스템은 로그를 읽지만 그 밖에는
    데이터베이스와 직접 상호작용하지 않는다. 이는 원천 데이터베이스에 추가 부하를 거의
    또는 전혀 더하지 않는다.**
  - **배치 CDC의 어떤 판본은 풀 패턴을 쓴다. 예컨대 타임스탬프 기반 CDC에서 반입 시스템은
    원천 데이터베이스를 질의해 이전 갱신 이후 바뀐 행을 당겨 온다.**

  같은 기제를 로그 관점에서 더 깊이 다룬 것이
  [변경 데이터 캡처](../concepts/change-data-capture.md)다.
- 스트리밍은 백엔드를 우회한다 — **스트리밍 반입에서 데이터는 백엔드 데이터베이스를 우회해
  엔드포인트로 직접 밀리며, 보통 이벤트 스트리밍 플랫폼이 데이터를 버퍼링한다. 이 패턴은
  센서 데이터를 뿜는 IoT 센서 무리에 유용하다. 현재 상태를 유지하는 데이터베이스에 의존하는
  대신 기록된 각 판독을 하나의 이벤트로 생각하면 된다** (2장, p.42).[^reis2022]
- **이 패턴은 소프트웨어 애플리케이션에서도 인기가 커지고 있는데, 실시간 처리를 단순화하고,
  앱 개발자가 하류 분석을 위해 메시지를 재단할 수 있게 하며, 데이터 엔지니어의 삶을 크게
  단순화하기 때문이다** (2장, p.42).[^reis2022]

## 반입 단계에 걸리는 저류

**사실상 모든 저류가 반입 단계에 닿지만 여기서는 가장 두드러진 것들을 강조한다** (7장,
p.263).[^reis2022] 저류 여섯의 전문은
[데이터 엔지니어링의 저류](../concepts/data-engineering-undercurrents.md)에 있다.

- **보안** — **데이터를 옮기는 것은 위치 사이에 데이터를 전송해야 하므로 보안 취약점을
  들여온다. 가장 원하지 않는 것은 옮기는 도중에 데이터가 포획되거나 훼손되는 것이다** (7장,
  p.264).[^reis2022]
  - **데이터가 어디 사는지, 어디로 가는지 고려하라. VPC 안에서 움직여야 하는 데이터는 보안
    엔드포인트를 쓰고 절대 VPC 경계를 벗어나면 안 된다. 클라우드와 온프레미스 네트워크 사이에
    데이터를 보내야 하면 VPN이나 전용 사설 연결을 쓰라. 돈이 들 수 있지만 보안은 좋은 투자다.
    데이터가 공용 인터넷을 가로지르면 전송이 암호화되게 하라. 전선 위의 데이터를 암호화하는
    것은 언제나 좋은 실천이다** (7장, p.264).[^reis2022]
- **데이터 관리** — **자연히 데이터 관리는 데이터 반입에서 시작한다. 이것이 계보와 데이터
  카탈로깅의 출발점이며, 이 지점부터 데이터 엔지니어는 스키마 변경·윤리·프라이버시·규정 준수를
  생각해야 한다** (7장, p.264).[^reis2022]
  - 스키마 변경의 두 극단이 다 실패한다 — **스키마 변경(데이터베이스 테이블의 컬럼 추가·변경·
    제거 같은)은 우리 관점에서 데이터 관리의 미해결 쟁점으로 남아 있다. 전통적 접근은 신중한
    명령·통제 검토 절차다. 대기업 고객과 일하면서 우리는 단일 필드 추가에 6개월의 리드 타임을
    들었다. 이는 민첩성에 받아들일 수 없는 장애물이다. 반대편 극단에서는 원천의 어떤 스키마
    변경이든 대상 테이블을 새 스키마로 재생성하게 만든다. 이는 반입 단계의 스키마 문제를
    풀지만 여전히 하류 파이프라인과 목적지 저장 시스템을 깨뜨릴 수 있다** (7장,
    p.264).[^reis2022]
  - 저자들이 내놓는 방향은 Git이다 — **우리 저자들이 한동안 숙고해 온 가능한 해법 하나는 Git
    버전 관리가 개척한 접근이다. Linus Torvalds가 Git을 개발할 때 그의 선택 다수는 동시 버전
    시스템(CVS)의 한계에서 영감을 받았다. CVS는 완전히 중앙집중적이다 — 중앙 프로젝트 서버에
    저장된 코드의 현행 공식 버전 하나만 지원한다. Git을 진정한 분산 시스템으로 만들기 위해
    Torvalds는 트리 개념을 썼다 — 각 개발자가 자신의 처리된 코드 브랜치를 유지하고 다른
    브랜치로 또는 다른 브랜치에서 머지할 수 있다** (7장, p.264).[^reis2022]
  - **몇 년 전만 해도 데이터에 대한 그런 접근은 생각할 수 없었다. 온프레미스 MPP 시스템은
    일반적으로 최대 저장 용량에 가깝게 운영된다. 그러나 빅데이터와 클라우드 데이터 웨어하우스
    환경에서는 저장이 싸다. 서로 다른 스키마와 심지어 서로 다른 상류 변환을 가진 테이블의 여러
    버전을 꽤 쉽게 유지할 수 있다. 팀은 Airflow 같은 오케스트레이션 도구를 써서 테이블의 다양한
    "개발" 버전을 지원할 수 있다 — 스키마 변경·상류 변환·코드 변경이 main 테이블에 대한 공식
    변경 전에 개발 테이블에 나타날 수 있다** (7장, pp.264–265).[^reis2022]
  - 데이터 윤리·프라이버시의 첫 질문 — **고객들은 자주 데이터베이스의 민감 데이터 암호화에
    대해 조언을 구하는데, 이는 일반적으로 우리를 근본적인 질문으로 이끈다: 암호화하려는 그
    민감 데이터가 필요하기는 한가? 알고 보면 이 질문은 요구사항을 만들고 문제를 풀 때 자주
    간과된다** (7장, p.265).[^reis2022]
  - **데이터 엔지니어는 반입 파이프라인을 세울 때 언제나 이 질문을 던지도록 스스로를 훈련해야
    한다. 그들은 필연적으로 민감 데이터를 만날 것이다. 자연스러운 경향은 그것을 반입해 파이프라인의
    다음 단계로 전달하는 것이다. 그러나 이 데이터가 필요하지 않다면 왜 애초에 수집하는가? 데이터가
    저장되기 전에 민감 필드를 그냥 버리면 안 되는가? 절대 수집되지 않은 데이터는 유출될 수 없다**
    (7장, p.265).[^reis2022]
  - 토큰화의 자리 — **민감한 신원을 추적하는 것이 진정으로 필요한 곳에서는 모델 학습과 분석에서
    신원을 익명화하기 위해 토큰화(tokenization)를 적용하는 것이 흔한 실천이다. 그러나 엔지니어는
    이 토큰화가 어디에서 쓰이는지 봐야 한다. 가능하면 반입 시점에 데이터를 해싱하라** (7장,
    p.265).[^reis2022]
  - 무접촉 프로덕션과 유리 깨기 — **가능한 한 민감 데이터가 관련될 때 무접촉
    프로덕션(touchless production)을 목표로 하라. 이는 엔지니어가 개발·스테이징 환경에서
    시뮬레이션되거나 정제된 데이터로 코드를 개발·테스트하되 프로덕션으로는 코드 배포를
    자동화한다는 뜻이다** (7장, p.265).[^reis2022] **무접촉 프로덕션은 엔지니어가 지향해야
    할 이상이지만 개발·스테이징 환경에서 완전히 풀 수 없는 상황이 필연적으로 생긴다. 어떤 버그는
    회귀를 촉발하는 라이브 데이터를 보지 않고는 재현할 수 없다. 이런 경우를 위해 유리 깨기
    프로세스(broken-glass process)를 두라 — 프로덕션 환경의 민감 데이터 접근을 최소 두 사람이
    승인하도록 요구하라. 이 접근은 특정 이슈로 좁게 범위가 정해져야 하고 만료일이 있어야 한다**
    (7장, p.265).[^reis2022]
  - 그리고 기술이 사람 문제를 풀지 않는다 — **민감 데이터에 대한 우리의 마지막 조언: 인간
    문제에 대한 순진한 기술적 해법을 경계하라. 암호화와 토큰화는 둘 다 프라이버시 만병통치약처럼
    다뤄지기 일쑤다. 대부분의 클라우드 기반 저장 시스템과 거의 모든 데이터베이스가 기본으로
    미사용·전송 중 데이터를 암호화한다. 일반적으로 우리는 암호화 문제가 아니라 데이터 접근 문제를
    본다. 해법이 단일 필드에 암호화 층을 하나 더 적용하는 것인가, 아니면 그 필드에 대한 접근을
    통제하는 것인가? 결국 누군가는 암호화 키에 대한 접근을 엄격히 관리해야 한다. 단일 필드
    암호화의 정당한 유스케이스가 존재하지만 의례적 암호화(ritualistic encryption)를 경계하라**
    (7장, p.265).[^reis2022]
  - 해싱도 그렇다 — **토큰화 쪽에서는 상식을 쓰고 데이터 접근 시나리오를 평가하라. 누군가가
    당신 고객 중 한 명의 이메일을 갖고 있다면 그 이메일을 쉽게 해시해서 데이터에서 그 고객을
    찾을 수 있는가? 솔팅 없이 생각 없이 데이터를 해싱하는 것과 다른 전략들은 당신 생각만큼
    프라이버시를 보호하지 못할 수 있다** (7장, p.266).[^reis2022]
- **데이터옵스** — **신뢰할 만한 데이터 파이프라인은 데이터 엔지니어링 수명 주기의 초석이다.
  그것이 실패하면 모든 하류 의존이 끼익 멈춘다. 데이터 웨어하우스와 데이터 레이크가 신선한
  데이터로 채워지지 않고, 데이터 과학자와 분석가가 자기 일을 효과적으로 할 수 없으며, 업무는
  눈을 감고 날게 된다** (7장, p.266).[^reis2022]
  - 모니터링이 가장 결정적인 단계가 여기다 — **데이터 파이프라인이 제대로 모니터링되게 하는
    것은 신뢰성과 효과적 사고 대응을 향한 결정적 단계다. 데이터 엔지니어링 수명 주기에서
    모니터링이 결정적인 한 단계가 있다면 그것은 반입 단계다. 약하거나 존재하지 않는 모니터링은
    파이프라인이 동작할 수도 아닐 수도 있다는 뜻이다. 앞의 시간 논의를 참조해 이벤트 생성·반입·
    프로세스·처리 시간의 다양한 측면을 추적하라. 데이터 파이프라인은 배치나 스트림으로 데이터를
    예측 가능하게 처리해야 한다. 우리는 오래된 데이터로 생성된 리포트와 ML 모델의 사례를 수없이
    봤다. 한 극단적 사례에서는 반입 파이프라인 실패가 여섯 달 동안 탐지되지 않았다. (그 경우
    데이터의 구체적 유용성을 의심할 만하지만 그것은 다른 문제다.) 이것은 제대로 된 모니터링으로
    아주 충분히 피할 수 있었다** (7장, p.266).[^reis2022]
  - 무엇을 모니터링하는가 — **무엇을 모니터링해야 하는가? 가동 시간·지연·처리된 데이터 볼륨이
    시작하기 좋은 지점이다. 반입 잡이 실패하면 어떻게 대응할 것인가? 일반적으로 배포를 기다리기
    보다 처음부터 파이프라인에 모니터링을 넣어라** (7장, p.266).[^reis2022]
  - 상류의 행동도 알아야 한다 — **모니터링이 핵심이며, 의존하는 상류 시스템의 행동과 그것이
    데이터를 생성하는 방식에 대한 지식도 그렇다. 관심 있는 시간 간격당 생성되는 이벤트 수
    (분당 이벤트·초당 이벤트 등)와 각 이벤트의 평균 크기를 알아야 한다. 데이터 파이프라인은
    반입하는 이벤트의 빈도와 크기를 모두 감당해야 한다** (7장, p.266).[^reis2022]
  - 서드파티도 마찬가지다 — **이는 서드파티 서비스에도 적용된다. 이 서비스의 경우, 군살 없는
    운영 효율(줄어든 인원)로 얻은 것이 통제 밖에 있는 의존 시스템으로 대체된다. 서드파티
    서비스(클라우드·데이터 통합 서비스 등)를 쓴다면 장애가 있을 때 어떻게 경보를 받는가?
    의존하는 서비스가 갑자기 오프라인이 되면 대응 계획은 무엇인가?** (7장, p.266).[^reis2022]
    **슬프게도 서드파티 실패에 대한 보편적 대응 계획은 없다. 다른 서버로, 되도록 다른 영역이나
    리전으로 페일오버할 수 있다면 반드시 설정하라** (7장, p.266).[^reis2022]
- **오케스트레이션** — **반입은 일반적으로 크고 복잡한 데이터 그래프의 시작에 앉는다. 반입이
  데이터 엔지니어링 수명 주기의 첫 단계이므로 반입된 데이터는 많은 데이터 처리 단계로 흘러가고
  많은 원천의 데이터가 복잡한 방식으로 섞인다. 이 책 전체에서 강조했듯 오케스트레이션은 이
  단계들을 조율하는 결정적 프로세스다** (7장, p.268).[^reis2022]
  - 크론은 시작점일 뿐이다 — **데이터 성숙도 초기 단계의 조직은 반입 프로세스를 단순한 스케줄
    크론 잡으로 배포하기로 할 수 있다. 그러나 이 접근이 부서지기 쉽고 데이터 엔지니어링 배포와
    개발의 속도를 늦출 수 있다는 것을 인식하는 것이 결정적이다** (7장, p.268).[^reis2022]
  - 진짜 오케스트레이션의 정의 — **데이터 파이프라인 복잡성이 커지면 진짜 오케스트레이션이
    필요하다. 진짜 오케스트레이션이란 개별 태스크가 아니라 완전한 태스크 그래프를 스케줄할 수
    있는 시스템을 뜻한다. 오케스트레이션은 각 반입 태스크를 적절한 스케줄 시각에 시작할 수 있다.
    하류 처리와 변환 단계는 반입 태스크가 완료되는 대로 시작한다. 더 하류에서 처리 단계는 추가
    처리 단계로 이어진다** (7장, p.268).[^reis2022] 이 정의의 전문과 다른 소스와의 대조는
    [배치 워크플로와 DAG](../concepts/batch-workflows-and-dags.md)에 있다.
- **소프트웨어 공학** — **데이터 엔지니어링 수명 주기의 반입 단계는 공학 집약적이다. 이 단계는
  데이터 엔지니어링 영역의 가장자리에 앉아 흔히 외부 시스템과 접하는데, 여기서 소프트웨어
  엔지니어와 데이터 엔지니어가 다양한 커스텀 배관을 지어야 한다** (7장, p.268).[^reis2022]
  - **무대 뒤에서 반입은 믿기 어려울 만큼 복잡하며, 흔히 팀이 카프카나 펄사 같은 오픈소스
    프레임워크를 운영하거나 가장 큰 기술 회사들이 자체 포크하거나 자체 개발한 반입 솔루션을
    돌린다. 이 장에서 논했듯 Fivetran·Matillion·Airbyte 같은 관리형 데이터 커넥터가 반입
    프로세스를 단순화했다. 데이터 엔지니어는 가용한 최선의 도구 — 주로 무거운 일을 대신 해 주는
    관리형 도구와 서비스 — 를 활용하고 중요한 곳에서는 높은 소프트웨어 개발 역량을 길러야 한다.
    반입 관련 코드에도 제대로 된 버전 관리와 코드 리뷰 프로세스를 쓰고 적절한 테스트를 구현하는
    것이 값어치를 한다** (7장, p.268).[^reis2022]
  - **소프트웨어를 쓸 때 코드는 결합이 느슨해야 한다. 원천이나 목적지 시스템에 대한 강한
    의존을 가진 모놀리식 시스템을 쓰지 마라** (7장, p.268).[^reis2022]
