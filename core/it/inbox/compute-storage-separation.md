하나의 질문: **데이터를 처리하는 기계와 데이터를 담는 기계를 떼어 놓으면 무엇을 얻고 무엇을
잃는가.**

## 무엇이 표준이 되었는가

- **이 책 전반에서 다시 찾는 핵심 아이디어가 컴퓨트와 저장의 분리다. 이것은 오늘날 클라우드 시대에
  표준 데이터 접근·질의 패턴으로 부상했다. 데이터 레이크는 논한 대로 데이터를 오브젝트 스토어에
  저장하고 그것을 읽고 처리할 임시 컴퓨트 용량을 띄운다. 이제 대부분의 완전 관리형 OLAP 제품은
  무대 뒤에서 오브젝트 저장에 의존한다** (6장, p.220).[^reis2022]
- 저장 추상을 고를 때의 고려 축 중 하나이기도 하다 — 저자들은 목적·유스케이스, 갱신 패턴, 비용과
  나란히 **저장과 컴퓨트의 분리(separate storage and compute)** 를 넷째 축으로 든다:
  **추세는 저장과 컴퓨트를 분리하는 쪽이지만 대부분의 시스템은 분리와 코로케이션을 혼성화한다.
  이것이 목적·속도·비용에 영향을 주므로 다룬다** (6장, p.215).[^reis2022]
- 그 결과 추상들의 경계가 흐려진다 — **저장과 컴퓨트를 분리하는 것의 인기는 OLAP 데이터베이스와
  데이터 레이크 사이의 선이 점점 흐려진다는 뜻임을 알아야 한다. 주요 클라우드 데이터 웨어하우스와
  데이터 레이크는 충돌 경로에 있다. 미래에 이 둘의 차이는 이름뿐일 수 있다 — 후드 아래에서 기능적·
  기술적으로 매우 비슷할 수 있기 때문이다** (6장, p.215).[^reis2022]

## 코로케이션이 오래 표준이었던 이유

- **컴퓨트와 저장의 코로케이션은 오랫동안 데이터베이스 성능을 개선하는 표준 방법이었다. 트랜잭션
  데이터베이스에서 데이터 코로케이션은 빠르고 낮은 지연의 디스크 읽기와 높은 대역폭을 허용한다.
  저장을 가상화할 때도(예: Amazon EBS를 쓸 때) 데이터는 호스트 머신에 상대적으로 가까이 위치한다**
  (6장, p.220).[^reis2022]
- 분석 쪽도 같았다 — **기계 클러스터에 걸쳐 도는 분석 질의 시스템에도 같은 기본 아이디어가
  적용된다. 예컨대 HDFS와 맵리듀스에서 표준 접근은 클러스터에서 스캔해야 할 데이터 블록을 찾은
  뒤 개별 map 잡을 이 블록으로 밀어내는 것이다. map 단계의 데이터 스캔과 처리는 엄격히 로컬이다.
  reduce 단계는 클러스터에 걸친 데이터 셔플을 수반하지만 map 단계를 로컬로 유지하면 셔플에 더 많은
  대역폭이 효과적으로 보존되어 전체 성능이 나아진다. 강하게 필터링하는 map 단계는 셔플될 데이터
  양도 극적으로 줄인다** (6장, p.220).[^reis2022]

## 분리를 부른 두 동기

- 질문 자체 — **컴퓨트와 저장의 코로케이션이 높은 성능을 인도한다면 왜 컴퓨트와 저장의 분리로
  옮겨 가는가? 몇 가지 동기가 존재한다** (6장, p.220).[^reis2022]
- **덧없음과 확장성** — **클라우드에서 우리는 덧없음(ephemerality)으로의 극적 이동을 봤다.
  일반적으로 서버를 사서 호스팅하는 것이 클라우드 제공자에게서 빌리는 것보다 싸다 — 단, 하루 24시간
  몇 년 동안 쉬지 않고 돌리는 경우에 한해. 실무에서 워크로드는 극적으로 다르고, 서버가 확장·축소할
  수 있다면 종량제 모델로 상당한 효율이 실현된다. 이는 온라인 소매의 웹 서버에도 참이고, 주기적으로만
  돌 수 있는 빅데이터 배치 잡에도 참이다** (6장, p.220).[^reis2022]
  - 그래서 무엇이 가능해지는가 — **덧없는 컴퓨트 자원은 엔지니어가 거대한 클러스터를 띄워 잡을
    제시간에 완료하고 잡이 끝나면 클러스터를 삭제하도록 허용한다. 초고규모로 일시적으로 운영하는
    성능 이득이 오브젝트 저장의 대역폭 한계를 능가할 수 있다** (6장, p.221).[^reis2022]
- **데이터 내구성과 가용성** — **클라우드 오브젝트 스토어는 데이터 손실 위험을 유의하게 완화하고
  일반적으로 극히 높은 가동 시간(가용성)을 제공한다. 예컨대 S3는 데이터를 여러 존에 걸쳐 저장한다.
  자연재해가 한 존을 파괴해도 데이터는 나머지 존에서 여전히 가용하다. 여러 존이 가용한 것은 데이터
  중단의 확률도 줄인다. 한 존의 자원이 내려가면 엔지니어는 다른 존에서 같은 자원을 띄울 수 있다**
  (6장, p.221).[^reis2022]
  - 남는 위험과 그 완화 — **오브젝트 저장의 데이터를 파괴하는 설정 오류의 가능성은 여전히 다소
    무섭지만 배치하기 쉬운 완화책이 이용 가능하다. 데이터를 여러 클라우드 리전으로 복사하는 것은
    이 위험을 줄인다 — 설정 변경은 일반적으로 한 번에 한 리전에만 배포되기 때문이다. 여러 저장
    제공자로 데이터를 복제하면 위험을 더 줄일 수 있다** (6장, p.221).[^reis2022]

## 실무는 다시 섞는다

- **컴퓨트와 저장을 분리하는 실무 현실은 우리가 암시한 것보다 복잡하다. 실무에서 우리는 두 접근의
  이점을 실현하기 위해 코로케이션과 분리를 끊임없이 혼성화한다. 이 혼성화는 일반적으로 두 방식으로
  이뤄진다: 다층 캐싱과 하이브리드 오브젝트 저장** (6장, p.221).[^reis2022]
- **다층 캐싱(multitier caching)** — **장기 데이터 보존과 접근에는 오브젝트 저장을 활용하되 질의와
  데이터 파이프라인의 다양한 단계 동안 쓸 로컬 저장을 띄운다. 구글과 아마존 모두 하이브리드 오브젝트
  저장(컴퓨트와 밀접하게 통합된 오브젝트 저장) 판본을 제공한다** (6장, p.221).[^reis2022]

## 네 가지 사례

- **AWS EMR과 S3·HDFS** — **Amazon EMR 같은 빅데이터 서비스는 데이터를 처리하기 위해 임시 HDFS
  클러스터를 띄운다. 엔지니어는 S3와 HDFS를 둘 다 파일시스템으로 참조할 선택지를 갖는다. 흔한
  패턴은 SSD 드라이브에 HDFS를 세우고, S3에서 끌어오고, 중간 처리 단계의 데이터를 로컬 HDFS에
  저장하는 것이다. 이렇게 하면 S3에서 직접 처리하는 것보다 상당한 성능 이득을 실현할 수 있다.
  클러스터가 단계를 완료하면 전체 결과가 S3에 되쓰이고 클러스터와 HDFS는 삭제된다. 다른 소비자는
  출력 데이터를 S3에서 직접 읽는다** (6장, p.221).[^reis2022]
- **Apache Spark** — **실무에서 Spark는 일반적으로 처리 단계 사이의 성능 좋은 데이터 저장을
  지원하기 위해 HDFS나 다른 덧없는 분산 파일시스템에서 잡을 돌린다. 덧붙여 Spark는 처리를 개선하기
  위해 데이터의 인메모리 저장에 크게 의존한다. Spark를 돌릴 인프라를 소유하는 것의 문제는 동적
  RAM(DRAM)이 극히 비싸다는 것이다 — 클라우드에서 컴퓨트와 저장을 분리함으로써 우리는 큰 양의
  메모리를 빌린 뒤 잡이 완료되면 그 메모리를 놓아줄 수 있다** (6장, pp.221–222).[^reis2022]
- **Apache Druid** — **Druid는 높은 성능을 실현하기 위해 SSD에 크게 의존한다. SSD가 마그네틱
  디스크보다 유의하게 비싸므로 Druid는 클러스터에 데이터 사본을 하나만 유지해 "라이브" 저장 비용을
  3분의 1로 줄인다** (6장, p.222).[^reis2022]
  - 내구성은 어디서 오는가 — **물론 데이터 내구성 유지는 여전히 결정적이므로 Druid는 오브젝트
    스토어를 내구성 계층으로 쓴다. 데이터가 반입되면 처리되고, 압축된 컬럼으로 직렬화되고, 클러스터
    SSD와 오브젝트 저장에 쓰인다. 노드 장애나 클러스터 데이터 손상 시 데이터는 새 노드로 자동
    복구될 수 있다. 덧붙여 클러스터를 내렸다가 SSD 저장에서 완전히 복구할 수 있다** (6장,
    p.222).[^reis2022]
- **하이브리드 오브젝트 저장** — **구글의 Colossus 파일 저장 시스템은 데이터 블록 위치의 세밀한
  통제를 지원하지만 이 기능은 대중에게 직접 노출되지 않는다. BigQuery는 이 기능을 써서 고객 테이블을
  한 위치에 코로케이트해 그 위치에서 초고속 대역폭 질의를 허용한다. 우리는 이것을 하이브리드 오브젝트
  저장(hybrid object storage)이라 부르는데, 오브젝트 저장의 깔끔한 추상과 컴퓨트·저장 코로케이션의
  이점 일부를 결합하기 때문이다. Amazon도 사용자가 데이터가 네트워크 너머로 돌아오기 전에 S3
  클러스터에서 직접 S3 데이터를 필터링하도록 허용하는 S3 Select 기능을 통해 하이브리드 오브젝트
  저장의 어떤 관념을 제공한다** (6장, p.222).[^reis2022]
  - 저자들의 전망 — **퍼블릭 클라우드가 제공물의 성능을 개선하고 가용 네트워크 자원을 더 효율적으로
    쓰기 위해 하이브리드 오브젝트 저장을 더 널리 채택할 것이라고 추측한다. 어떤 곳은 이를 공개적으로
    밝히지 않은 채 이미 하고 있을 수도 있다** (6장, p.222).[^reis2022] #speculation
  - 그리고 무엇을 강조하는가 — **하이브리드 오브젝트 저장의 개념은 남의 퍼블릭 클라우드에 의존하기
    보다 하드웨어에 저수준으로 접근하는 것에 여전히 이점이 있을 수 있음을 강조한다. 퍼블릭 클라우드
    서비스는 하드웨어와 시스템의 저수준 세부(예: Colossus의 데이터 블록 위치)를 노출하지 않지만,
    이 세부는 성능 최적화와 향상에 극히 유용할 수 있다** (6장, p.222).[^reis2022]

## 제로 카피 클로닝

- 정의 — **오브젝트 저장을 중심으로 한 클라우드 기반 시스템은 제로 카피 클로닝(zero-copy cloning)을
  지원한다. 이는 일반적으로 하부 데이터를 반드시 물리적으로 복사하지 않고 객체의 새 가상 사본이
  만들어진다(예: 새 테이블)는 뜻이다. 일반적으로 원시 데이터 파일에 대한 새 포인터가 만들어지고 이
  테이블에 대한 미래의 변경은 옛 테이블에 기록되지 않는다. 파이썬 같은 객체 지향 언어의 내부 작동에
  익숙한 사람에게 이런 유형의 "얕은" 복사는 다른 맥락에서 친숙하다** (6장, p.223).[^reis2022]
- 강점과 한계를 함께 알아야 한다 — **제로 카피 클로닝은 매력적인 기능이지만 엔지니어는 그 강점과
  한계를 이해해야 한다. 예컨대 데이터 레이크 환경에서 객체를 클론한 뒤 원본 객체의 파일을 지우면
  새 객체까지 지워질 수 있다** (6장, p.223).[^reis2022]
- 시스템에 따라 위험이 다르다 — **완전 관리형 오브젝트 스토어 기반 시스템(예: Snowflake와
  BigQuery)에서 엔지니어는 얕은 복사의 정확한 한계에 극도로 익숙해야 한다. 엔지니어는 Databricks
  같은 데이터 레이크 시스템에서는 하부 오브젝트 저장에 더 많은 접근을 갖는다 — 축복이자 저주다.
  데이터 엔지니어는 하부 오브젝트 스토어의 원시 파일을 지우기 전에 큰 주의를 기울여야 한다.
  Databricks와 다른 데이터 레이크 관리 기술은 때때로 딥 카피(deep copying)의 관념도 지원하는데,
  이는 모든 하부 데이터 객체가 복사되는 것이다. 이는 더 비싼 과정이지만 파일이 의도치 않게 손실되거나
  삭제될 때 더 견고하기도 하다** (6장, p.223).[^reis2022]
