이 페이지의 질문: **서버가 아닌 애플리케이션의 구동 시간을 줄이려 할 때, 무엇을 재고 어떤
순서로 손대며, 어디까지가 이제는 의미가 없어진 손질인가.**

> **버전 조건**: 실측은 OpenJDK 11과 17의 핫스팟에서 나왔다. 저자 환경은 64비트 윈도우 10,
> 인텔 i5, 램 24GB 랩톱이며 힙 최대치는 2GB였다. 버전에 매인 개별 claim에는 조건을 따로 적었다.

## 먼저 재고 나서 손댄다

- 전제부터가 규칙이다 — **서버 애플리케이션이 아니라면 시스템을 최적화할 일이 없을 것이라고
  오해하는 개발자가 많다.** 시스템이 클수록 전문 팀이 필요한 것은 맞지만 **다른 분야의
  애플리케이션에도 최적화가 필요한 경우는 많다** (5장, p.269).[^zhou2024]
- 측정 환경을 고정하는 절차가 먼저 나온다. 저자는 이클립스를 대상으로 삼고 **VisualVM과 확장
  플러그인인 비주얼 GC(Visual GC)** 로 실행 데이터를 모았는데, 조건을 이렇게 통제했다 (5장,
  pp.270–271):[^zhou2024]
  - **테스트하는 동안 운영 체제가 디스크 캐싱을 제때 수행하지 못하는 영향을 피하기 위해
    테스트 결과가 안정되게 나올 때까지 이클립스를 여러 번 재시작하여 마지막 결과를 데이터
    샘플로 취했다.**
  - **CPU 과열로 인한 스로틀링 영향을 줄이기 위해 재시작 사이에는 쿨러가 조용해질 때까지
    기다려야** 했다.
- 재려는 값이 도구에 없으면 만든다 — **이클립스를 구동하는 데 소요된 시간은 VisualVM에서 직접
  얻을 수 없다. VisualVM은 이클립스가 어떤 상태에 있는지 알 수 없기 때문**이어서, 저자는
  `IStartup`을 구현해 `eclipse.startTime` 시스템 속성과 현재 시각의 차를 띄우는 플러그인을
  직접 만들었다 (5장, pp.272–273).[^zhou2024] 측정 결과는 **10초 내외에서 안정화**됐다.

## 세 요인으로 나누어 읽기

- 최적화 전 데이터의 해석이 이 페이지의 뼈대다 (5장, p.271):[^zhou2024]
  - **컴파일: 총 1만 8552번 컴파일에 약 1분 6초 소요. 컴파일 시간은 여러 컴파일 스레드가
    동시에 수행한 시간의 총합이므로 이클립스 구동에 이만큼 걸렸다는 뜻은 아니다.**
  - **클래스 로딩: 총 2만 6098개의 클래스 로딩에 18.84초 소요.** 이것 역시 여러 스레드가
    수행한 시간의 총합이다.
  - **가비지 컬렉션: 28번 수행에 396밀리초 소요. 28번 모두 에덴에서 이루어졌다.**
  - 힙 구성은 **에덴 108MB, 생존자 공간 1MB, 구세대 232MB**가 실제 할당량이었다.
- 여기서 흔히 오해하는 지점 하나를 짚어 둔다 — 화면에는 에덴·생존자·구세대의 최대 크기가 모두
  2GB로 찍히는데, 이는 **G1 컬렉터가 힙 메모리를 리전 단위로 관리하며, 각 공간에 필요한
  리전을 동적으로 할당/회수하기 때문**이다. 힙 최대치가 2GB이면 **이 2GB 내에서 어느 영역에
  얼마나 할당할지 가비지 컬렉터가 결정하므로 모두 잠재적 최대 크기를 2GB로 표시**한다 (5장,
  p.272).[^zhou2024]
  - 그래서 값은 계속 움직인다 — **생존자 공간은 구동 초기에는 수십 MB까지 늘어났다가 이클립스의
    초기 백그라운드 작업이 모두 끝나자 안정되어 1MB로 줄어든 것**이다 (5장, p.272).

## JDK 판올림만으로 얻는 몫

- 첫 번째 수단은 코드를 건드리지 않는 쪽이다 — **이클립스 최적화의 첫 번째 단계는 최신 가상
  머신으로 업그레이드해 보는 것**이었다 (5장, p.274).[^zhou2024]
- 근거는 벤더 홍보가 아니라 제삼자 측정이다 — **제삼자가 평가한 데이터를 종합해 판단해 봐도
  JDK 버전이 업그레이드되면 적어도 일부 측면에서는 성능이 확실히 개선된다.** 저자의 SPECjbb2015
  지연 시간 측정에서 **G1 컬렉터 사용 기준으로 JDK 17은 JDK 11보다 10% 정도 개선**되었다 (5장,
  p.274).[^zhou2024]
  - 반대 방향의 경고가 각주에 붙어 있다 — **물론 버전 업그레이드 시 성능이 퇴보하는 경우도
    많다. 프로그램 자체의 한계, 미들웨어나 서드 파티 패키지와의 호환성 등 고려할 게 많으므로
    기업용 애플리케이션에서는 JDK 업그레이드를 신중히 결정해야 한다** (5장, p.274, 각주 5).
- 실측 결과도 비슷한 폭이었다 — JDK 17로 바꾸자 구동 시간이 **평균 8초대 후반까지 단축**되어
  **최신 JDK를 사용하기만 해도 구동 시간을 10% 정도 단축**할 수 있었고, **프로젝트와 설치한
  플러그인이 크고 많을수록 단축되는 정도가 더 커질 것**이다 (5장, p.275).[^zhou2024]

## 클래스 로딩: 검증을 끄는 값

- 클래스 로딩 시간은 jstat으로 따로 잴 수 있다. jps로 프로세스 아이디를 얻은 뒤 `-class`
  옵션을 준다 (5장, p.275):[^zhou2024]

  ```sh
  jstat -class 7216
  ```

  ```text
  Loaded  Bytes     Unloaded  Bytes  Time
   25942  53044.3          0    0.0  16.43
  ```

- 끌 수 있는 근거를 먼저 세운다 — 클래스 로딩은 **로딩 과정에서 안전한 바이트코드인지 검증하는
  단계를 거치는데**, 이클립스는 **사용자가 매우 많고 오랜 기간 검증된 통합 개발 환경이기 때문에
  안전하다고 가정해도 좋을 것**이고, 그렇다면 **이클립스 자체 클래스들을 로딩할 때는 바이트코드
  검증이 굳이 필요 없다** (5장, pp.275–276).[^zhou2024]
- 그래서 `-Xverify:none`으로 **바이트코드 검증을 건너뛰는데, 이를 최적화 수단으로도 활용할 수
  있다.** 실제로 클래스 로딩 시간은 16.43초에서 **14.44초로 2초 남짓 줄었다** (5장,
  p.276).[^zhou2024]
  - 다만 그 절감이 그대로 구동 시간이 되지는 않는다 — **클래스 로딩은 사용자 스레드와 동시에
    수행되기 때문**이며, 실제 전체 구동 시간은 **7초 후반대로, 평균 0.8초 정도** 줄었다 (5장,
    p.276). 총합으로 잰 시간과 벽시계 시간을 혼동하지 말라는 규칙이 여기서 다시 나온다.
  - 버전 조건: 이 실측은 OpenJDK 17에서 `-Xverify:none`이 아직 효력을 갖던 시점의 것이다.
    #hypothesis 검증 생략은 안전성을 자기 책임으로 옮기는 선택이므로, 신뢰할 수 없는 코드를
    로딩하는 애플리케이션에는 이 절감을 적용하지 않는 편이 낫다.

## 컴파일 시간: 양 끝이 모두 나쁘다

- 먼저 '컴파일 시간'이 무엇인지 정의된다 — **여기서 컴파일 시간은 시간이 많이 소요되는
  코드(핫 코드)를 가상 머신의 JIT 컴파일러가 컴파일하는 데 쓴 시간**이다 (5장,
  p.277).[^zhou2024]
- 왜 그 비용을 치르는지도 함께 정리되어 있다 — **핫스팟 가상 머신은 일정 횟수 이상 호출되는
  자바 메서드를 핫 코드로 분류하여 JIT 컴파일러에 넘긴다. 그러면 JIT 컴파일러가 해당 코드를
  런타임에 네이티브 코드로 변환하여 수행 속도를 개선한다. '핫스팟' 가상 머신이라는 이름이
  여기서 기원했다** (5장, p.277).[^zhou2024]
  - 동적 컴파일이 정적 컴파일을 이길 수 있는 이유 — **정적 컴파일러는 알 수 없는 다양한 런타임
    정보를 활용할 수 있어서 더 급진적인 최적화 기법을 적용할 수 있기 때문이다. '대부분의
    경우'를 가정한 최적화 대신 현 상황에만 해당하는 '극단적인 경우'의 최적화를 적용할 수
    있다.** 가정이 어긋나면 **최적화 없이 컴파일한 코드로 돌아갈 수 있고, 또는 심지어 인터프리터
    모드로 돌아가기도 한다** (5장, p.277).
  - 그 대가가 구동 시간이다 — **동적 컴파일은 프로그램의 정상적인 실행 시간에 영향을 준다.
    사용자 프로그램이 실행되는 와중에 컴파일 자체에도 컴퓨팅 자원을 할애해야 하기 때문이다**
    (5장, p.277).
- 그렇다면 컴파일을 끄면 되지 않느냐는 물음에 대한 답이 이 절의 결론이다 (5장,
  pp.277–278):[^zhou2024]
  - `-Xint`로 **가상 머신을 순수한 인터프리트 방식으로 수행**하게 하면 **컴파일 시간은 0으로
    떨어지지만 총 구동 시간은 30초 이상으로 크게 늘어난다. JIT 컴파일러의 혜택이 모두 사라져서
    '전반적인' 실행 속도가 급격히 느려지기 때문**이다.
  - 반대쪽도 마찬가지다 — **가상 머신을 컴파일 모드로 실행하는 `-Xcomp` 매개 변수를 지정하면
    분 단위의 구동 시간을 경험하게 될 것**이다.
  - 버전 조건: JDK 8 이하에는 `-client`라는 선택지가 있어 **가벼운 최적화만 수행하여 애플리케이션
    구동 시간을 줄여** 주고 `-server`는 반대였다. **JDK 9부터는 `-client` 매개 변수를 지정해도
    무시하고 서버 모드로 실행한다. 서버 모드에서도 어차피 계층형 컴파일이 이미 자리를 잡았기
    때문**이다 (5장, p.278).
  - 그래서 남은 결론 — **컴파일 시간 측면에서는 시간을 더 단축할 요인을 찾지 못했다. 자바 기술
    시스템이 발전하여 최적의 방식을 자동으로 찾아 주는 덕분이다** (5장, p.278).

## 메모리 설정: 이제 손댈 것이 적다

- 이 절의 값이 이 사례에서 가장 크다 — 2판과 3판의 차이가 곧 기술 변화의 기록이기 때문이다.
  **2판에서는 32비트 윈도우·32비트 가상 머신·물리 메모리 4GB 환경이었고 같은 작업 환경에
  19번의 전체 GC와 378번의 마이너 GC가 수행되어**, GC 로그를 분석해 에덴·생존자·구세대는 물론
  영구 세대 크기까지 손으로 맞췄다 (5장, p.278).[^zhou2024]
- 지금은 그 여지가 사라졌다 — **대용량 메모리와 64비트 시스템이 보편화된 지금은 메모리 용량
  걱정은 거의 사라졌다. 가비지 컬렉터 기술도 나날이 발전하여 영역별 필요 용량을 가상 머신이
  알아서 동적으로 정해 준다** (5장, pp.278–279).[^zhou2024]
  - 실측이 그것을 뒷받침한다 — **힙의 최대 크기인 2GB 중 사용 중인 용량은 0.5GB도 되지 않았고**
    **구세대에서는 컬렉션이 한 번도 일어나지 않았다.** 일반적으로 **성능에 영향을 많이 주는
    가비지 컬렉션은 구세대를 포함하는 전체 GC**인데 그것이 아예 없었으므로 손댈 값이 없었다
    (5장, p.278).
- 그럼에도 로그를 볼 일은 남는다 — `-Xlog:gc*:gc.log`로 **자세한 GC 로그를 출력해 파일에
  저장**할 수 있고, **GC 로그의 형태와 내용은 가비지 컬렉터마다 다르기 때문에 사용하는 컬렉터의
  특성을 잘 알아 두면 분석하는 데 큰 도움이 된다** (5장, p.279).[^zhou2024]
- 메모리가 넉넉한데 전체 GC가 도는 경우를 잡는 방법도 하나 나온다 — `jstat -gccause`의 **`LGCC`
  열**이 마지막 GC의 원인을 알려 주는데, 여기서 `System.gc()`가 전체 GC를 일으켰음이 드러났다.
  **메모리가 넉넉한 상황에서 굳이 가비지 컬렉션을 수행할 필요가 없다고 판단되면 가상 머신
  차원에서 `System.gc()`의 효력을 없앨 수도 있다** — `-XX:+DisableExplicitGC`가 그것이다 (5장,
  p.279).[^zhou2024]
  - 이 매개 변수는 양날이다. 다이렉트 메모리를 쓰는 프로그램에서 같은 매개 변수가 오버플로를
    막지 못하게 만드는 경우는
    [긴 일시 정지와 프로세스 붕괴 좁혀 가기](../concepts/jvm-pause-and-crash-diagnosis.md)에 있다.

## 컬렉터 교체가 체감으로 이어지지 않을 때

- 구동 시간 말고 사용 중 지연도 볼 값이다 — 프로젝트 재빌드 동안 **신세대는 컬렉션당 약
  37밀리초씩 소요되고 구세대는 컬렉션이 일어나지 않았다. 37밀리초의 일시 정지는 사람이 인지하기
  어렵기 때문**에 전체적으로 만족스러운 상태였다 (5장, p.279).[^zhou2024]
- 컬렉터를 바꿔 볼 근거는 남는 자원이었다 — 빌드 중 **CPU 사용량 평균은 40%를 조금 넘는
  수준이고 가비지 컬렉터 활동량(activity)은 0에 가까웠다. 달리 말하면 CPU 자원은 넉넉하므로
  필요하면 다른 작업에 더 끌어다 쓸 여력이 많다는 뜻**이다 (5장, p.280).[^zhou2024]
  - 그래서 **여유로운 CPU 자원을 일시 정지 시간 단축에 더 투입**해 보기 위해 `-XX:+UseZGC`를
    붙였다 (5장, p.281).
- 결과는 부정적이었고 그 판단 근거가 이 절의 규칙이다 (5장, pp.281–282):[^zhou2024]
  - 도구부터 따라오지 못했다 — **현재의 비주얼 GC는 ZGC를 지원하지 않는다.** CPU 사용량 곡선만
    보면 **사용량은 여전히 40%를 조금 넘어 보이지만 GC 활동량은 눈에 띄게 늘었다.**
  - **이 데이터만으로는 ZGC가 지연 시간을 줄여 주는지 확신할 수 없다.** 더욱이 **G1의 컬렉션당
    지연 시간이 겨우 37밀리초 정도이기 때문에 더 줄였다고 해서 체감하기는 어렵다.** 그래서
    **성능 최적화를 위해 굳이 ZGC를 선택할 필요는 없어 보이고**, 구동 시간에서도 유의미한 차이는
    없었다.
  - 버전 조건: **ZGC는 JDK 11 때 실험 버전으로 처음 소개되었고 JDK 15 때 정식 기능으로
    승격**되었다. 저자의 평가는 **애플리케이션 관점에서 지연 시간은 G1을 따라잡지 못했지만,
    처리량과 일시 정지 시간 기준으로는 이미 가장 우수한 가비지 컬렉터**라는 것이다 (5장, p.282).
- 이 실전 연습 전체가 남기는 결론이 마지막에 있다 — **JDK를 11에서 17로 변경한 것 외에 최종
  설정에 추가한 것은 `-Xverify:none`뿐이다. 2판에서는 11개나 추가했던 것에 비해 최적화할 여지가
  많이 줄었다. 모두 기술 발전 덕분이다. 메모리 공간이 광활해졌고 힙 구성을 가상 머신이 알아서
  최적의 크기로 설정해 준다. 가비지 컬렉터 역시 눈부시게 발전하여 기본 컬렉터의 전반적인 성능이
  매우 좋아졌다** (5장, p.282).[^zhou2024]
  - 그렇다고 끝은 아니다 — **기술을 깊이 이해할수록 최적화할 요소를 많이 발견할 수 있다.**
    저자는 오라클의 자바 SE 문서에서 **핫스팟 가상 머신 가이드와 가비지 컬렉션 최적화 가이드**를
    찾아 자기 프로젝트 특성에 맞춰 시험해 볼 것을 권한다 (5장, p.282).
  - 서버와의 관계도 못박아 둔다 — **데이터베이스, 자원 풀, 디스크 I/O 등 서버단 최적화는 고려해야
    할 요인이 더 많을 것이다. 하지만 가상 머신의 메모리 관련 최적화는 이번 사례에서 살펴본
    아이디어와 크게 다르지 않다** (5장, p.282).
