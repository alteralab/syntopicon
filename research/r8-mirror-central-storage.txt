KEY: size-projection
--- SUMMARY ---
docs-mirror 크기 투영 실측 결과. (1) 계획 5개 문서 저장소의 GitHub API size 합계 = 5.25 GB (dbt docs 1.62, clickhouse-docs 1.23, spark-website 1.00, airflow-site 0.87, kafka-site 0.52 — 전체 git 이력 포함 bare 근사). (2) 20–30개 기술 확장 시 full clone 기준 10–30 GB(11개 표본 중앙값 0.52 GB/repo; 계획 5개는 표본 상위권), blobless(--filter=blob:none) 정책이면 GitLab 실측 사례(웹사이트 repo 2.34 GiB→81 MiB, 97% 절감) 기준 수 GB급으로 압축. 보류 중인 코드 미러 활성화 시 +11.4 GB인데 ClickHouse 단독이 9.8 GB로 86% — 코드 미러 크기는 소수 모노레포가 지배. (3) 맥락: 현행 MacBook Air 기본 SSD가 512GB(M5, 2026)라 최악 투영도 기본 디스크의 10% 미만이고, Xcode·Docker·node_modules 등 기존 재생성 캐시와 같은 급. npm 공식 문서가 명문화하듯 재생성 가능 캐시는 이전·백업 대상이 아니며 기기 교체 시 재클론이 표준 — 옮길 데이터가 0이다. (4) 수백 GB 임계 도달은 '대형 모노레포 코드 미러 수십 개를 full-history로' 같은 좁은 시나리오에서만 발생. 중앙 저장소가 이기는 조건은 크기가 아니라 느린/metered 회선, upstream 소멸 대비(단 이는 archive/의 책무), 다기기 동시 유지 시 중복 다운로드 절약이다. 방법 한계: GitHub API size는 서버측 근사치이며(온디스크 clone 크기와 1:1 아님), 대형 저장소 clone 금지 규칙에 따라 blobless 절감은 문서 근거로 대체했다.

KEY: migration-mechanics
--- SUMMARY ---
3안 비교 결론: '기기 교체 부담'은 이 캐시에 실재하지 않는다. (1) 통째 이동 — Migration Assistant는 사용자 계정 전체(미러 포함)를 자동 이전하므로 아무 조치 없어도 옮겨진다(Apple 공식 문서). 정지 상태 1회 전체 복사라 git 저장소도 안전(git FAQ)하며 유일한 caveat는 worktree 절대 경로 → `git worktree repair` 한 줄. 비용은 수 GB만큼의 이주 시간 증가뿐. (2) 재클론 — 실측 규모가 우려보다 훨씬 작다: 후보 8개 저장소 서버측 총 6.3GB(GitHub API 실측, 최대 dbt 1.6GB), 로컬 ~10GB 추정. GitHub 권장 상한(5GB/repo)이 폭주를 구조적으로 막는다. 10GB 재클론은 100Mbps에서 ~13분, 1Gbps에서 ~1.3분; 상한 가정 50GB도 100Mbps에서 ~67분 — '수 분~수십 분 백그라운드 작업'이 맞고, blobless clone으로 더 줄어든다. KEY: cache-practice
--- SUMMARY ---
결론: "캐시는 기기와 함께 죽고 새 기기에서 재수화한다"는 것이 업계 관행 표준임이 1차 소스로 확인된다. (1) 규모 실측 — 후보 5개 벤더 문서 저장소의 GitHub 서버측 크기 합계는 약 4.8GB로 '대량 데이터' 우려는 현 후보군에서 성립하지 않는다(100Mbps에서 전체 재클론 ~10분). (2) 관행 — npm ci(node_modules 자동 삭제 후 동결 재설치), pnpm store prune("not harmful"), Cargo("you can always remove any part of the cache"), pip·npm cache·brew cleanup·docker prune 모두 캐시를 삭제-재다운로드 대상으로 명문화하고, XDG 스펙은 캐시를 "non-essential data"로 정의하며, CACHEDIR.TAG/restic --exclude-caches/Time Machine(~/Library/Caches 기본 제외, 이 맥북에서 tmutil로 실측)/asimov(1.9k stars)가 캐시의 백업 제외를 1급 기능으로 지원한다. (3) 캐시의 중앙 저장소는 upstream 그 자체(git 미러의 경우 GitHub)이고, 사설 프록시는 air-gap·조직망·대역폭 병목이라는 조직 조건에서만 등장한다(JFrog 문서 명시). (4) git 미러는 SHA content-addressing으로 재클론이 결정적이고 want/have 협상으로 갱신이 증분이며 blobless clone으로 초기 전송도 축소 가능해, 일반 빌드 캐시보다도 재수화 비용이 낮다. (5) 기기 교체 실비용 비교 — 재클론(1커맨드+~10분) ≤ Migration Assistant 통째 이동(로컬 속도, 부담 사실상 없음) < 중앙 저장소(동기화 파이프라인·과금·10–20년 존속 리스크를 새로 만들면서 GitHub이 무료 제공하는 기능을 중복). 중앙 저장소가 이기는 조건은 성실히 찾은 결과 (a) upstream 소멸·이력 재작성으로 재생성 가능성이 깨질 때 — 단 이는 보존 문제로 <kb>/archive/가 담당하는 것이 정합적, (b) air-gap/종량제·극저속 회선, (c) 다수 기기 공유 병목 — 셋 다 개인 맥북 1대 환경에 해당하지 않는다. 실무 권고 도출 가능: mirrors/에 CACHEDIR.TAG를 두면 restic --exclude-caches가 무설정으로 제외한다. 주의: 로컬 mirrors/는 아직 미생성이라 로컬 크기 실측은 불가했고 수치는 GitHub API size 필드 기준이다.
