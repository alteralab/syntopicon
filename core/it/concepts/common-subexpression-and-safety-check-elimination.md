이 페이지의 질문: **이미 계산한 것과 이미 아는 것을 컴파일러는 어떻게 다시 하지 않게 만드는가.**

## 공통 하위 표현식이란

- 위치가 먼저 정해진다 — **공통 하위 표현식 제거는 다양한 컴파일러에서 흔히 사용되는 매우 고전적인
  최적화 기술이다** (11장, p.561).[^zhou2024] 정의는 이렇다:

  > 표현식 E가 이미 평가되었고 E에 등장하는 모든 변숫값이 평가 이후 변하지 않는다면, 뒤에 등장하는
  > E를 공통 하위 표현식이라고 한다.

  - 그래서 할 일이 정해진다 — **공통 하위 표현식은 다시 계산할 필요 없이 이전 계산 결과로 치환하면
    된다** (11장, p.561).
- 적용 범위가 이름을 가른다 — **지역 공통 하위 표현식 제거: 적용 범위가 기본 블록으로 제한. 전역
  공통 하위 표현식 제거: 둘 이상의 기본 블록에 걸쳐 있음** (11장, p.561).[^zhou2024] 기본 블록의
  정의는 [핫스팟 JIT 코드 들여다보기](../concepts/hotspot-jit-inspection-tools.md)에 있다.

## 식 하나가 줄어드는 과정

- 예제는 곱셈이 두 번 나오는 식이다 (11장, p.561):[^zhou2024]

  ```java
  int d = (c * b) * 12 + a + (a + b * c);
  ```

  - 프런트엔드는 이것을 손대지 않는다 — **이 코드를 아무런 최적화 없이 javac 컴파일러에 전달하면
    (…) 자바 소스 코드에서 산술 계산을 우선순위에 맞게 차례로 수행하는 모습**의 바이트코드가
    나온다 (11장, p.562). 곱셈 `b * c`가 두 번 계산되는 그대로다. 프런트엔드가 실행 효율을 손대지
    않는 사정은 [javac의 컴파일 과정](../concepts/javac-compilation-process.md)에 있다.
- JIT는 두 곱셈이 같은 것임을 알아본다 — **컴파일러는 `c * b`와 `b * c`가 같은 표현식이고, `b`와
  `c`의 값은 계산 도중에 변경되지 않음을 알아낸다** (11장, p.562).[^zhou2024] 그러면 식은
  `int d = E * 12 + a + (a + E);` 와 같아진다.
- 거기서 다른 최적화가 이어진다 — **이제 컴파일러는 여러 가지 다른 최적화를 수행할 수 있다. 예를
  들어 (…) 대수식 단순화를 적용할 수 있다** — 결과는 `int d = E * 13 + a + a;` 다 (11장,
  p.562).[^zhou2024] **이처럼 표현식을 변환하면 계산을 반복하는 일을 줄일 수 있다.**

## 배열 경계 검사는 공짜가 아니다

- 자바가 자동으로 끼워 넣는 것이 있다 — **자바는 C/C++보다 상대적으로 안전한 언어다. 예컨대
  `foo[]` 배열의 원소를 얻기 위해 `foo[i]` 코드를 실행하면 시스템이 자동으로 경계(배열 범위의
  상한과 하한)를 확인한다. 즉, `i >= 0 && i < foo.length` 조건을 만족하지 못하면 런타임 예외인
  `ArrayIndexOutOfBoundsException`을 던진다. 그 덕분에 방어 코드를 따로 작성하지 않더라도 오버플로
  공격을 대부분 피할 수 있다** (11장, pp.562–563).[^zhou2024]
- 그 대가가 성능이다 — **하지만 배열 원소를 읽고 쓸 때마다 경계를 확인하므로 배열을 많이 이용하는
  프로그램에서는 성능 부담으로 다가올 수 있다** (11장, p.563).[^zhou2024]

## 검사를 컴파일타임으로 옮기기

- 협상의 여지가 있다 — **배열 경계 검사는 안전을 위해 반드시 필요하지만 잘 협상하면 런타임에
  정확히 한 번만 수행되도록 할 수 있다** (11장, p.563).[^zhou2024]
- 상수 인덱스면 아예 없앨 수 있다 — **`foo[3]`처럼 배열의 인덱스를 상수로 지정했다고 해 보자.
  그리고 컴파일타임에 데이터 흐름을 분석하여 `foo.length`가 3보다 크다는 사실을 알아냈다면 실행 중
  경계 검사를 할 필요가 없다** (11장, p.563).[^zhou2024]
- 더 흔한 쪽은 순환문이다 — **순환문 안에서 루프 변수를 인덱스로 이용하여 배열에 접근하는 코드가
  있다고 가정하자. 컴파일러가 데이터 흐름을 분석하여 루프 변수의 값이 `[0, foo.length)` 범위를
  벗어나지 않는다고 판단하면 순환문 내에서 경계 상한/하한 검사를 완전히 걷어 낼 수 있다** (11장,
  p.563).[^zhou2024]

## '자바는 느리다'의 원죄

- 자동 검사는 배열만이 아니다 — **자바는 이 외에도 다양한 안전 검사를 제공하여 C/C++보다 프로그램을
  훨씬 쉽게 작성할 수 있다. 예를 들어 널 포인터에 접근하려 들면 `NullPointerException`을 던지고,
  0으로 나누면 `ArithmeticException`을 던지는 식이다. C/C++ 프로그램에서는 비슷한 문제가 생기면
  세그멘테이션 오류(segmentation fault)나 (윈도우 프로그래밍에서는) 'memory could not be
  written/read' 오류가 난다. 이를 제대로 처리하지 않으면 프로그램이 곧바로 비정상 종료된다**
  (11장, p.563).[^zhou2024]
- 그 편의가 비용으로 돌아온다 — **자바는 이러한 문제 상황을 인지하고 조치하는 안전 검사 로직을
  자동으로 수행한다. 같은 작업이라도 C/C++보다 더 많은 일을 수행하며 결국 눈에 보이지 않는 부하로
  이어진다. 그래서 적절한 최적화가 이루어지지 못하면 "자바 언어는 본질적으로 느리다"라는 원죄로
  작용할 가능성이 높다** (11장, p.563).[^zhou2024]
- 그래서 목표가 정해진다 — **이러한 보이지 않는 부하를 없애려면 배열 경계 검사를 최대한 최적화하여
  런타임에 수행할 검사를 컴파일타임에 끝마쳐야 한다. 같은 맥락에서 암묵적 예외 처리, 널 포인터
  검사, 0으로 나누기 검사 등도 모두 최적화 대상이다** (11장, p.563).[^zhou2024]

## 암묵적 예외 최적화

- 널 검사가 실제로는 이렇게 생겼다 — 객체 `foo`의 속성 `value`에 접근하는 과정을 저자는 의사
  코드로 이렇게 적는다 (11장, p.563):[^zhou2024]

  ```java
  if (foo != null) {
      return foo.value;
  } else {
      throw new NullPointerException();
  }
  ```

- 최적화는 검사 자체를 없애고 예외 핸들러로 미룬다 (11장, p.564):[^zhou2024]

  ```java
  try {
      return foo.value;
  } catch (segment_fault) {
      uncommon_trap();
  }
  ```

  - 이 코드의 층위에 주의가 붙어 있다 — **가상 머신이 세그멘테이션 오류용 예외 핸들러인
    `uncommon_trap()`을 등록하고 있다. 이 의사 코드는 자바의 `try-catch` 문이 아니라 프로세스
    수준의 예외 핸들러임에 주의하자** (11장, p.564).
- 이득과 손해가 확률로 갈린다 — **이런 식으로 `foo`가 `null`이 아닐 때는 널 검사로 인한 부하 없이
  바로 값에 접근한다. 그 대신 `foo`가 `null`일 때는 `NullPointerException`을 던지기 위해 예외
  핸들러로 이동하는 부담이 더해진다. 예외 핸들러로 진입하면 사용자 모드에서 커널 모드로 전환되고,
  처리를 끝낸 후 다시 사용자 모드로 돌아오는 과정을 거친다. 단순히 `null`을 검사할 때보다 훨씬
  느리다는 뜻이다. 따라서 암묵적 예외 최적화는 `foo`가 `null`일 가능성이 거의 없을 때만 효과가
  있다. 그렇지 않으면 프로그램이 오히려 느려질 것이다** (11장, p.564).[^zhou2024]
- 그 선택을 사람이 하지 않는다 — **다행히 핫스팟 가상 머신은 런타임에 수집하는 성능 모니터링 정보를
  토대로 가장 적절한 방식을 자동으로 선택한다** (11장, p.564).[^zhou2024] 그 정보가 어디서
  모이는지는 [JIT 컴파일러와 계층형 컴파일](../concepts/jit-compilers-and-tiered-compilation.md)에
  있다.
- 같은 계열이 더 있다 — **이 외에도 자바 언어에 특화된 '제거' 최적화 기법으로는 오토박싱 제거,
  안전 지점 제거, 리플렉션 제거 등이 있다** (11장, p.564).[^zhou2024] 오토박싱이 무엇을 끼워
  넣는지는 [자바의 편의 문법 해체](../concepts/java-syntactic-sugar.md)에, 안전 지점은
  [핫스팟의 가비지 컬렉션 구현 상세](../concepts/hotspot-gc-implementation.md)에 있다.
