이 페이지의 질문: **데이터베이스는 레코드를 어떤 파일에 어떻게 놓고, 인덱스는 그 레코드를
어떻게 가리키는가.**

## 왜 그냥 파일이 아닌가

- 데이터베이스 시스템도 데이터 저장에 파일을 쓰지만, 레코드를 찾는 데 파일시스템의 디렉터리·파일
  계층에 기대는 대신 **구현마다 다른 형식으로 파일을 구성한다** (1장, p.17).[^petrov2019]
- 평범한 파일 대신 특수 파일 조직을 쓰는 주된 이유 셋 (1장, p.17):[^petrov2019]
  - **저장 효율** — 저장된 레코드 하나당 저장 오버헤드를 최소화하도록 파일을 구성한다.
  - **접근 효율** — 가능한 한 적은 단계로 레코드를 찾을 수 있다.
  - **갱신 효율** — 디스크의 변경 횟수를 최소화하도록 레코드 갱신이 수행된다.
- 각 테이블은 보통 별도 파일로 표현되고, 테이블의 레코드는 **탐색 키(search key)** 로 조회된다.
  레코드를 찾기 위해 데이터베이스는 인덱스(index)를 쓴다 — **접근할 때마다 테이블 전체를 스캔하지
  않고 레코드를 효율적으로 찾게 해 주는 보조 자료 구조**이며, 레코드를 식별하는 필드의 부분집합으로
  만들어진다 (1장, p.17).[^petrov2019]
- 데이터베이스 시스템은 보통 데이터 파일과 인덱스 파일을 분리한다 — 데이터 파일은 레코드를,
  인덱스 파일은 레코드 메타데이터를 저장하고 그것으로 데이터 파일 안의 레코드를 찾는다. 인덱스
  파일은 대체로 데이터 파일보다 작다. 파일은 페이지로 나뉘며, 페이지 크기는 보통 디스크 블록
  하나 또는 여러 개의 크기다. 페이지는 레코드의 순열로 구성되거나 슬롯 페이지(slotted page)로
  구성될 수 있다 (1장, pp.17–18).[^petrov2019]

## 삭제는 지우지 않는다

- 새 레코드(삽입)와 기존 레코드의 갱신은 키/값 쌍으로 표현된다 (1장, p.18).[^petrov2019]
- **대부분의 2019년 저술 시점 저장 시스템은 페이지에서 데이터를 명시적으로 삭제하지 않는다.** 대신 삭제
  마커(deletion marker, 툼스톤tombstone이라고도 한다)를 쓰는데, 키와 타임스탬프 같은 삭제
  메타데이터를 담는다 (1장, p.18).[^petrov2019]
- 갱신이나 삭제 마커에 의해 가려진(shadowed) 레코드가 차지한 공간은 **가비지 컬렉션** 동안
  회수된다 — 페이지를 읽어 살아 있는(가려지지 않은) 레코드를 새 자리에 쓰고 가려진 것은 버린다
  (1장, p.18).[^petrov2019]
- 이 서술이 뒤에 나올 [LSM 트리](../concepts/lsm-tree.md)의 툼스톤과
  [카프카 로그 압착](../concepts/kafka-log-compaction.md)의 툼스톤을 한 뿌리로 묶는다 — 셋 다 "삭제를
  쓰기로 표현한다"는 같은 착상이지만 회수 기제는 각각 다르다.

## 데이터 파일의 세 형태

- 데이터 파일(주 파일primary file이라고도 한다)은 셋 중 하나로 구현될 수 있다 (1장,
  p.18):[^petrov2019]
  - **힙 구조형 테이블(heap-organized table, 힙 파일)** — 레코드가 특정 순서를 따를 필요가 없고
    대개 쓰기 순서로 놓인다. 그래서 새 페이지를 덧붙일 때 추가 작업이나 파일 재조직이 필요
    없다. 대신 **검색 가능하게 하려면 레코드 위치를 가리키는 별도의 인덱스 구조가 필요하다.**
  - **해시 구조형 테이블(hashed file)** — 레코드가 버킷에 저장되고, 키의 해시 값이 어느 버킷인지를
    정한다. 버킷 안에서는 추가 순서로 저장하거나 조회 속도를 높이려고 키로 정렬해 저장할 수 있다.
  - **인덱스 구조형 테이블(index-organized table, IOT)** — 레코드를 인덱스 자체에 저장한다. 레코드가
    키 순서로 저장되므로 IOT의 범위 스캔은 내용을 순차적으로 훑는 것으로 구현할 수 있다.
- IOT의 이득은 명확하다 — 레코드를 인덱스에 저장하면 **디스크 탐색 횟수를 최소 하나 줄인다.**
  인덱스를 순회해 탐색 키를 찾은 뒤 관련 레코드를 찾으려고 별도 파일을 다시 주소 지정할 필요가
  없기 때문이다 (1장, p.18).[^petrov2019]
- 레코드가 별도 파일에 저장되는 경우, 인덱스 파일은 **데이터 엔트리(data entry)** 를 담는다 —
  레코드를 유일하게 식별하고 데이터 파일에서 찾기에 충분한 정보를 담는 것이다. 예로 파일
  오프셋(행 로케이터row locator라고도 한다)이나 해시 파일의 버킷 ID가 있다. 인덱스 구조형
  테이블에서는 데이터 엔트리가 실제 레코드를 담는다 (1장, p.18).[^petrov2019]

## 인덱스 파일

- 인덱스는 **효율적인 조회 연산을 쉽게 하도록 디스크의 레코드를 조직하는 구조**다. 인덱스 파일은
  키를 데이터 파일 안의 위치로 매핑하는 특수 구조로 구성되는데, 그 위치는 힙 파일이면 키가
  식별하는 레코드의 자리이고 인덱스 구조형 테이블이면 기본 키가 식별하는 자리다 (1장,
  pp.18–19).[^petrov2019]
- 주 데이터 파일에 대한 인덱스를 **주 인덱스(primary index)** 라 하고, 대개 기본 키 또는 기본으로
  지정된 키 집합 위에 만들어졌다고 가정할 수 있다. 나머지 전부가 **보조 인덱스(secondary
  index)** 다 (1장, p.19).[^petrov2019]
- 보조 인덱스는 레코드를 직접 가리킬 수도, 그냥 기본 키를 저장할 수도 있다. 레코드 포인터는 힙
  파일이나 인덱스 구조형 테이블에 대한 오프셋일 수 있다. **여러 보조 인덱스가 같은 레코드를
  가리킬 수 있어, 하나의 레코드가 서로 다른 필드로 식별되고 서로 다른 인덱스를 통해 찾아진다.**
  주 인덱스 파일은 탐색 키당 항목을 하나만 갖지만 보조 인덱스는 탐색 키당 항목을 여럿 가질 수
  있다 (1장, p.19).[^petrov2019]
- 레코드의 순서가 탐색 키 순서를 따르면 그 인덱스를 **클러스터형(clustered, clustering)** 이라
  한다. 이때 레코드는 보통 같은 파일이나 키 순서가 보존된 클러스터 파일에 저장된다. 데이터가
  별도 파일에 저장되고 그 순서가 키 순서를 따르지 않으면 **비클러스터형(nonclustered,
  unclustered)** 이라 한다 (1장, p.19).[^petrov2019]
- 관계는 정의에서 따라 나온다. 원문 직인용 (1장, p.19):[^petrov2019]

> Index-organized tables store information in index order and are clustered by
> definition. Primary indexes are most often clustered. Secondary indexes are
> nonclustered by definition, since they're used to facilitate access by keys other than
> the primary one. Clustered indexes can be both index-organized or have separate index
> and data files.

- 많은 데이터베이스에 레코드를 유일하게 식별하는 명시적 기본 키가 있다. 지정되지 않으면 저장
  엔진이 암시적 기본 키를 만들 수 있다 — 예로 MySQL InnoDB는 자동 증가 열을 새로 넣고 값을
  자동으로 채운다 (1장, p.20).[^petrov2019]
- 이 용어는 여러 계열에서 함께 쓰인다 — MySQL·PostgreSQL 같은 관계형, Apache Cassandra·Riak 같은
  Dynamo 계열 NoSQL, MongoDB 같은 문서 스토어. 프로젝트마다 이름이 조금 다를 수는 있지만 대개
  이 용어로 명확히 대응된다 (1장, p.20).[^petrov2019]

## 주 인덱스를 간접 참조로 쓰기

- 레코드를 (파일 오프셋으로) 직접 참조해야 하는지 주 키 인덱스를 거쳐야 하는지는 **데이터베이스
  커뮤니티에서 의견이 갈리는 문제**다 (1장, p.20).[^petrov2019]
- 득실은 이렇다 (1장, p.20):[^petrov2019]
  - **직접 참조**는 디스크 탐색 횟수를 줄이지만, 레코드가 갱신되거나 유지보수 중에 이동할 때마다
    포인터를 갱신하는 비용을 치러야 한다.
  - **주 인덱스를 통한 간접 참조**는 포인터 갱신 비용을 줄이지만 읽기 경로의 비용이 더 높다.
- 읽기가 대부분인 워크로드라면 인덱스 두엇을 갱신하는 정도로 될 수 있지만, **인덱스가 여럿인
  쓰기 중심 워크로드에서는 직접 참조가 잘 안 먹힌다.** 그래서 일부 구현은 페이로드 오프셋 대신
  기본 키를 간접 참조에 쓴다 — 예로 MySQL InnoDB는 주 인덱스를 두고 조회를 두 번 한다(보조
  인덱스에서 한 번, 주 인덱스에서 한 번). 보조 인덱스에서 오프셋을 바로 따라가는 대신 주 인덱스
  조회의 오버헤드가 더해지는 셈이다 (1장, p.20).[^petrov2019]
- 혼합도 가능하다 — 데이터 파일 오프셋과 기본 키를 **둘 다** 저장하고, 먼저 오프셋이 여전히
  유효한지 확인한 뒤 바뀌었으면 기본 키 인덱스를 거치는 추가 비용을 치르고 새 오프셋을 찾아
  인덱스 파일을 갱신한다 (1장, p.21).[^petrov2019]

## 2차 색인의 값은 유일하지 않다

kleppmann이 같은 구획을 다시 그리되, petrov가 짧게 지나간 **2차 색인의 값 중복** 문제를 두
처방으로 나눠 적는다.

- 기본 키가 무엇인지부터 — **기본 키(primary key)는 관계형 테이블의 한 행, 문서 데이터베이스의 한
  문서, 그래프 데이터베이스의 한 정점을 유일하게 식별한다. 데이터베이스의 다른 레코드는 그
  행·문서·정점을 기본 키(또는 ID)로 참조할 수 있고, 색인이 그런 참조를 해소하는 데 쓰인다** (4장,
  p.132).[^kleppmann2026]
- 2차 색인 — **2차 색인(secondary indexes)을 갖는 것도 매우 흔하다. 관계형 데이터베이스에서는
  `CREATE INDEX` 명령으로 같은 테이블에 여러 2차 색인을 만들 수 있고, 이는 기본 키가 아닌 열로
  검색할 수 있게 한다** (4장, p.132).[^kleppmann2026]
- 무엇이 다른가 — **2차 색인은 키-값 색인에서 쉽게 구성될 수 있다. 주된 차이는 2차 색인에서
  인덱싱된 값이 반드시 유일하지는 않다는 것이다. 즉 같은 색인 항목 아래 여러 행(문서·정점)이 있을
  수 있다** (4장, p.132).[^kleppmann2026]
- 처방이 둘이다 (4장, p.132):[^kleppmann2026]
  - **색인의 각 값을 일치하는 행 식별자의 목록으로 만든다**(전문 색인의 포스팅 리스트처럼).
  - **행 식별자를 덧붙여 각 항목을 유일하게 만든다.**
- 어느 저장 구조를 써도 된다 — **B-트리 같은 인플레이스 갱신 저장 엔진과 로그 구조 저장 둘 다
  색인을 구현하는 데 쓸 수 있다** (4장, p.132).[^kleppmann2026]

## 색인 안에 값을 저장하는 세 배치

- 무엇이 열려 있는 선택인가 — **색인의 키는 질의가 검색하는 대상이다. 색인의 타입에 따라 키 외의
  다른 데이터가 색인에 저장될 수 있다** (4장, p.133).[^kleppmann2026]
- 세 배치가 열거된다 (4장, p.133):[^kleppmann2026]
  - **클러스터드 색인(clustered index)** — **실제 데이터(행·문서·정점)가 색인 구조 안에 직접
    저장되면 클러스터드 색인이라 한다. 예컨대 MySQL의 InnoDB 저장 엔진에서 테이블의 기본 키는 항상
    클러스터드 색인이고, SQL Server에서는 테이블당 하나의 클러스터드 색인을 지정할 수 있다.**
  - **참조를 저장하는 배치** — **대안으로 값이 실제 데이터에 대한 참조일 수 있다: 문제의 행의 기본
    키이거나(InnoDB가 2차 색인에 대해 이렇게 한다) 디스크의 위치에 대한 직접 참조다. 후자의 경우
    행이 저장되는 곳을 힙 파일(heap file)이라 하고, 특정 순서 없이 데이터를 저장한다(추가 전용일
    수도 있고, 나중에 새 데이터로 덮어쓰려고 삭제된 행을 추적할 수도 있다). 예컨대 Postgres는 힙
    파일 접근을 쓴다.**
  - **커버링 색인(covering index) 또는 포함 열을 가진 색인** — **둘 사이의 중간 지대이며, 힙이나
    기본 키 클러스터드 색인에 전체 행을 저장하는 것에 더해 테이블 열 중 일부를 색인 안에 저장한다.
    이는 어떤 질의를 기본 키를 해소하거나 힙 파일을 보지 않고 색인만으로 답할 수 있게 하며, 이때
    그 색인이 질의를 커버(cover)한다고 말한다. 이는 어떤 질의를 더 빠르게 만들 수 있지만 데이터의
    중복은 색인이 더 많은 디스크 공간을 쓰고 쓰기를 느리게 만든다는 뜻이다.**
- 힙 파일에서 값이 커질 때가 까다롭다 — **키를 바꾸지 않고 값을 갱신할 때 힙 파일 접근은 새 값이 옛
  값보다 크지 않은 한 레코드를 제자리에서 덮어쓸 수 있게 한다. 새 값이 더 크면 상황이 더 복잡해지는데,
  아마 공간이 충분한 힙의 새 위치로 옮겨져야 하기 때문이다. 그 경우 모든 색인이 레코드의 새 힙 위치를
  가리키도록 갱신되거나, 옛 힙 위치에 전달 포인터(forwarding pointer)가 남겨져야 한다** (4장,
  p.133).[^kleppmann2026]
- petrov의 "직접 참조 대 주 인덱스 간접 참조" 논의(위 [주 인덱스를 간접 참조로 쓰기](#주-인덱스를-간접-참조로-쓰기))가 이 문단과 같은 문제를 다룬다. 두 서술이 어긋나는 곳은 없고, kleppmann이
  **전달 포인터**라는 셋째 선택지를 추가한다.
