## 버전 조건

> **버전 조건**: OWASP API Security Top 10의 내용과 그 범주 묶음은 **2025년 저술 시점**의
> 판을 따른다. OWASP는 이 목록을 주기적으로 개정하므로 항목의 이름과 순위는 이 책과 현재 판이
> 다를 수 있다. 저자들은 판의 연도를 본문에 적지 않는다. 암호화·인증·인가의 규정과 정제·검증의
> 구별은 시점에 매이지 않는다.

## 공격이 사람 쪽으로 옮겨 갔다

- 관찰에서 시작한다 — **오늘날 조직들이 기성 온라인 소프트웨어로 옮겨 가게 해 주는
  SaaS(software-as-a-service) 모형을 점점 더 채택하고 있고**, 이 이행이 **공격자로 하여금
  기술적 약점만이 아니라 인간 행동의 악용에도 초점을 맞추게 한다** (2장 §"API Security",
  p.68).[^dynowski2025]
- 규정 (2장, p.68).[^dynowski2025]

  > Social engineering, also called human hacking, involves psychological manipulation to
  > gain unauthorized access to IT systems.

- 흔한 방법 셋이 열거된다 (2장, p.68).[^dynowski2025]
  - **피싱(Phishing)** — 공격자가 대상을 속여 민감한 정보를 내놓게 한다.
  - **프리텍스팅(Pretexting)** — 공격자가 데이터를 얻기 위한 구실로 거짓 시나리오를 만든다.
  - **베이팅(Baiting)** — 공격자가 악의적 물건을 남겨 두고 피해자가 그것을 쓰기를 바란다.
    저자들이 드는 실물이 **악성 소프트웨어가 든 USB 스틱을 주차장에 두는 것**이다.

## OWASP와 Top 10

- **OWASP(Open Web Application Security Project)는 웹 애플리케이션 보안에서 글·방법론·문서·
  도구·기술을 만드는 온라인 커뮤니티**이고, **오픈 소스 이니셔티브와 커뮤니티 교육을 통해
  소프트웨어 보안을 개선하는 것**을 목표로 한다 (2장 §"OWASP Top 10 API Security",
  p.69).[^dynowski2025]
- **OWASP에는 여러 프로젝트가 있고 그 가운데 Top 10 프로젝트가 웹 애플리케이션 보안 위험의 참조
  표준이 되었다** (2장, p.69).[^dynowski2025]
- **거기에 더해 OWASP에는 API 보안에 전념하는 API Security Top 10 프로젝트가 있고, 이
  프로젝트가 API 보안 위험과 그 완화 방법을 이해하는 참조로 쓰인다** (2장,
  p.69).[^dynowski2025]

## 세 범주로 묶어 읽기

**저자들은 열 항목을 하나씩 세지 않는다.** 대신 **OWASP API Top 10 위험이 세 주요 범주로 묶일
수 있다**고 적고 그 셋을 서술한다 (2장, pp.69–70).[^dynowski2025]

- **인증과 인가** — 잘못 구현되면 **공격자가 다른 사용자의 신원을 가장하거나 보호된 데이터에
  무단 접근할 수 있게 된다.**
  - **인증 범주의 공격은 손상된 인증 토큰, 잘못 구현된 인증 흐름, 약한 비밀번호에 대한 무차별
    대입 공격 때문에 가능해진다.**
  - **인가 공격은 잘못 설정된 접근 통제 정책이나 관리자 역할과 일반 사용자 역할 사이의 직무
    분리 결여를 악용한다.** 이 범주의 공격 예가 **권한 상승 공격(privilege escalation
    attack)** 이고, **공격자가 인증이나 인가의 약점을 악용해 특권 접근을 얻는 것**이다.
- **인벤토리 관리** — **API와 그 지원 서비스의 잘못된 설정이나 안전하지 않은 프로그래밍 관행이
  공격을 쉽게 만들 수 있다.**
  - 잘못된 설정의 예로 드는 것이 **방화벽 오설정, 소프트웨어 보안 패치 누락, API 로그의 비밀
    누출, 전송 계층 보안(TLS) 누락, 약한 암호화 표준 사용**이다.
  - 이 범주의 공격 예 — **중간자 공격(MITM)**(공격자가 클라이언트와 서버 사이의 통신을 가로챈다),
    **코드 주입 공격**(SQL 주입 같은 여러 경로로 악성 코드를 주입해 체계를 손상시킨다),
    **OS 명령 주입이나 크로스 사이트 스크립팅.**
  - 각주에 실정 하나가 붙는다 — **클라우드 제공자와 SaaS 기업은 현재 자기 서비스의 취약점을
    공개할 의무가 없다. 그 취약점을 완화하는 데 사용자의 조치가 필요한 경우에도 그렇다.**
- **자원 관리** — **API의 사용이 감시되지 않으면 제약 없는 호출이 예상 밖의 비용으로 이어질 수
  있다.**
  - **API 기능이 SMS·이메일·전화 같은 서비스를 제공하는 외부 체계와 통합되어 있고 그것들이
    요청당 과금이면, 공격자가 서비스의 운영 비용을 올릴 수 있다.**
  - 이 범주의 공격 예가 **DoS**이고, **공격자가 요청의 홍수로 API를 압도하는 것**이다.

## 암호화

- 패턴 절의 전제 — **API는 기술적 보안 위험에 취약하다. OWASP 프로젝트는 이 위험들의 분류를
  제공하고 그 역사적 진화를 추적한다.** 이 절은 그 위험을 줄이는 **선별된 패턴**을 서술한다
  (2장 §"Examples of API Security Patterns", p.70).[^dynowski2025]
- 규정 (2장 §"Encryption, Authentication, and Authorization", p.70).[^dynowski2025]
  - **암호화는 API 트래픽을 보호하는 가장 흔한 방법으로, 전송 중 데이터의 기밀성과 무결성과
    진정성을 보장한다.**
  - **암호화는 데이터를 원래 형식인 평문에서 암호화 알고리즘과 암호화 키를 써서 암호문으로
    바꾸는 과정이다. 암호문은 복호화 키 없이는 읽을 수 없다.**
- TLS가 그 셋을 어떻게 나눠 맡는지가 적힌다 (2장, p.70).[^dynowski2025]
  - **API 트래픽 암호화는 보통 TLS에 의존한다.**
  - **거기에 더해 TLS는 신뢰된 인증 기관(CA)이 발급한 디지털 인증서를 써서 클라이언트가 서버를
    인증(신원을 확인)하게 해 준다.** 어떤 경우에는 **상호 TLS 인증(mTLS)** 이 쓰이고, 그때는
    **클라이언트와 서버가 서로를 인증한다.**
  - **마지막으로 TLS는 전송 중에 데이터가 변경되지 않았음을 검증해 데이터 무결성을 보장한다.
    이것은 메시지 인증 코드(MAC)로 달성되며, MAC이 데이터 변조를 탐지하는 것을 돕는다.**

## 인증과 인가

- 규정 둘과 원칙 하나 (2장, p.71).[^dynowski2025]
  - **인증은 엔터티의 신원을 검증하는 과정이다.**
  - **인가는 그 엔터티가 요청된 자원에 접근할 수 있는지를 보장한다.**
  - **API 클라이언트에 데이터를 돌려줄 때는 최소 권한 원칙을 적용하라** — **사용자는 자기
    임무를 수행하는 데 필요한 최소한의 권한만 부여받아야 한다는 원칙**이다.

## 정제와 검증

- 목표가 먼저 적힌다 — **정제와 검증은 입력을 악용하거나 출력 데이터를 조작하는 공격에서 API를
  보호하는 것을 목표로 한다.** 그 공격의 예가 **주입 공격**과 **데이터 누출**이다
  (2장 §"Sanitization and Validation", p.71).[^dynowski2025]
- 둘이 하는 일이 다르다 (2장, p.71).[^dynowski2025]
  - **정제(sanitization)는 데이터가 처리에 안전한 형식임을 보장하는 첫 단계다.** 데이터를
    정제한다는 것은 **예상 밖의 문자 같은 원치 않는 입력을 제거하거나 입력 문자열의 양 끝
    공백을 벗겨 내는 것**을 뜻한다.
  - **검증(validation)은 그와 달리 입력이 검증 제약과 정책을 따르는지를 보장하려는 것이다.**
    예컨대 **검증된 데이터는 올바른 범위에 있을 것으로 기대되고, 문자열은 올바른
    형식일 것으로 기대된다**(올바른 우편번호 같은).
- 조문이 세다 — **안전한 코드를 쓰는 개발자로서 입력 데이터를 절대 신뢰하지 말라. 입력 데이터를
  신뢰하면 공격자가 요청 필드에 악성 코드를 쓸 수 있게 된다. 검증 없이는 데이터 유출이나 무단
  접근 같은 보안 위험으로 이어질 수 있다.** 그리고 단서 하나 — **입력 데이터를 검증할 때는 데이터
  값뿐 아니라 자료형에도 민감하라** (2장, p.71).[^dynowski2025]
- 수단으로 드는 것이 직렬화기다 — **입력 데이터를 다룰 때는 직렬화기(serializer)를 쓰라.
  직렬화기는 많은 프레임워크와 프로그래밍 언어의 흔한 부분이고 종종 데이터 검증 기능을
  포함한다.** 게다가 **대부분의 프레임워크는 모델 수준의 검증(객체 관계 매퍼, ORM)을 지원하는
  내장 검증기를 포함한다** (2장, p.71).[^dynowski2025]

## 출력도 검사 대상이다

- **API의 출력 데이터도 검사되어야 한다. 안전하지 않은 API가 종종 과도한 데이터를, 때로는
  민감한 정보까지 노출하기 때문**이다 (2장, p.71).[^dynowski2025]
- 저자들이 드는 실물 — 차량 대여 서비스의 API를 지으며 차량 위치를 추적하려면 **위치 이력을
  담는 배열인 `location` 필드**를 더해야 하는데, **이 필드는 특권 없는 API 클라이언트에
  노출되어서는 안 된다** (2장, p.71).[^dynowski2025]
- 그래서 같은 원칙이 출력 쪽에서 다시 불린다 — **클라이언트에 데이터를 돌려줄 때 최소 권한
  원칙을 생각하라. API에 최소 권한 원칙을 강제하는 것이 데이터 접근을 통제하고 민감 정보의
  불필요한 노출을 막는 것을 돕는다** (2장, p.71).[^dynowski2025]

## 드라이 런

- **입력과 출력을 검증하는 일의 또 다른 측면이 "드라이 런(dry run)"이라는 개념**이다.
  **드라이 런에서 목표는 애플리케이션 로직을 실행하는 것이 아니라 요청 검증의 효과를 관찰하는
  것**이다 (2장, p.72).[^dynowski2025]
- 수단은 플래그다 — **이를 달성하는 한 방법은 요청 인터페이스에 `validate_only` 플래그를 더하는
  것**이고, **`validate_only`로 요청을 테스트할 때 그 과정은 멱등적이면서 안전해야 한다** (2장,
  p.72).[^dynowski2025]
- 각주에서 그 요구를 예외로 명시한다 — **`POST` 요청은 보통 비멱등이고 안전하지 않은데
  `validate_only` 플래그가 이 규칙에 예외를 만든다. 이 플래그가 있으면 엔드포인트가 그 요청을
  특수한 경우로 다루어 멱등적이고 안전하게 만든다. 이로써 클라이언트가 연산을 실제로 수행하지
  않고 그 유효성을 테스트할 수 있다** (2장, p.72).[^dynowski2025]
  - **이 KB가 이미 갖고 있는 규범과 층이 다르다.** RFC 9110에서 안전함과 멱등성은 **메서드의
    성질**로 규정되고 그 전문은
    [멱등성과 자동 재시도의 규범](../concepts/http-idempotency-and-automatic-retry.md)에 있다.
    이 책이 말하는 것은 그 규정을 고치는 것이 아니라 **특정 엔드포인트가 그 플래그를 보았을 때
    무엇을 하기로 약속하는가**이다. #hypothesis 그래서 두 서술은 겨루지 않는다고 본다 — 다만
    그 약속은 서버 구현이 지키는 것이지 메서드가 보장하는 것이 아니므로, 중개 체계는 여전히
    `POST`로 다룬다.

## 스크래핑 완화

- 앞 절 끝에서 공격의 다른 목적이 소개된다 — **공격자가 체계의 행동을 바꾸는 것이 아니라
  데이터를 뽑아내는 것을 노린다면 데이터 스크래핑(data scraping, 과도한 데이터 수집excessive
  data gathering이라고도 한다)이라는 기법을 쓸 수 있다** (2장, p.72).[^dynowski2025]
- 범위와 동기 (2장 §"Scraping Mitigation", p.72).[^dynowski2025]
  - **데이터 스크래핑은 한 프로그램이 다른 프로그램에서 데이터를 뽑아내게 한다. 가장 널리 퍼진
    형태가 웹사이트에서 데이터를 뽑아내는 웹 스크래핑이고**, 다른 형태는 **API·데스크톱
    애플리케이션·데이터베이스**에서 뽑아내는 것이다.
  - **기업들은 스크레이퍼를 써서 다른 기업의 데이터를 소비해 더 처리하고 분석한다. 경쟁사의
    웹사이트를 스크래핑하는 것은 불공정한 경쟁 우위를 주는 데 쓰일 수 있고, 이것이 법적·윤리적
    우려를 낳을 수 있다.**
- 첫째 완화와 그 한계 — **검색 엔진 크롤러처럼 널리 쓰이고 예의 바른 웹 크롤러로부터 웹사이트를
  보호하려면 API 서버의 루트에 `robots.txt`를 노출하라.** 그러나 **`robots.txt`는 자발적
  표준이고 모든 봇이 그것을 존중하지는 않는다. 이 방법은 악의적 웹 크롤러로부터 조직의 데이터를
  보호하지 못한다** (2장, p.72).[^dynowski2025]
  - 각주에 다음 수단이 적힌다 — **`robots.txt`를 존중하지 않는 악성 봇은 대신 허니팟에 가둬야
    할 수도 있다** (2장, p.72).[^dynowski2025]

## 예측 가능한 식별자를 쓰지 않는다

- 둘째 완화는 식별자에 걸린다 — **공개 API 엔드포인트를 보호하는 데 쓰이는 또 하나의 패턴은
  자원 식별자에 예측 가능한 순열을 쓰지 않는 것**이다 (2장, p.72).[^dynowski2025]
- **사용자 자원 식별자가 정수라면**(`/api/v1/books/1`의 `1` 같은) **스크레이퍼가 식별자를
  증가시키며 자원을 하나씩 긁어 갈 수 있다** (2장, p.72).[^dynowski2025]
- **정수 대신 UUIDv4 식별자를 쓰면 UUIDv4의 방대한 공간 때문에 그런 식별자를 추측하는 데
  스크레이퍼가 너무 오랜 시간을 쓰게 된다.** 저자들이 그 공간을 센다 — **UUIDv4는 128비트
  식별자로 6비트가 미리 정해지고 122비트가 무작위로 생성되어, 총 대략 5.32 × 10^36(5.32
  언데실리언)의 유일한 ID 공간을 준다** (2장, p.72).[^dynowski2025]

## 그 목록의 판 연도를 적는 소스

**위 [버전 조건](#버전-조건)이 "저자들은 판의 연도를 본문에 적지 않는다"고 적어 둔 자리가
다른 소스로 메워진다.** 2022년 API 아키텍처 운영서가 같은 목록을 쓰면서 **그것이 언제 나온
것인지를 본문에 적는다.**

- **조직의 규정이 겹친다** — 그쪽도 **OWASP를 소프트웨어의 보안을 개선하려 일하는 비영리
  재단**으로, **가장 잘 알려진 프로젝트를 OWASP Top 10**으로, 그것을 **웹 애플리케이션이
  마주하는 가장 결정적인 보안 위험의 목록**으로 규정한다 (6장 §"Case Study: Applying OWASP to
  the Attendee API", p.146).[^gough2022] 위 [OWASP와 Top 10](#owasp와-top-10)과 같다.
- **그쪽이 더하는 것이 연도다** — **2019년에 OWASP가 새 top 10 목록을 냈고 그것이 API Security
  Top 10이었다** (6장, p.146).[^gough2022]
  - 이 페이지의 소스는 2025년 책이고 **그 판을 특정하지 않는다.** 그쪽은 2022년 책이고 **2019년
    판을 가리킨다.** **두 페이지가 같은 판을 읽고 있다고 가정할 수 없다** — 이 관찰은 이 KB의
    것이다. #hypothesis
- **그 목록이 어떻게 만들어졌는지도 그쪽이 적는다** — **보안 침해와 버그 바운티 프로그램을 살핀
  보안 전문가들의 작업에 기반하고, 침투 테스터들도 이 top 10에 무엇이 들어야 하는지 의견을
  냈다** (6장, pp.146–147).[^gough2022]
- **그쪽이 붙이는 단서 둘** (6장, p.147):[^gough2022]
  - **이것은 마주하게 될 모든 위협의 철저한 목록이 아니다.** 다만 **자기 API가 어떻게 악용될 수
    있는지 볼 때 염두에 두어야** 한다.
  - **이 목록들은 주기적으로 갱신되므로 바뀌는 대로 변경과 갱신을 찾아보는 것이 중요하다.**
    **이 단서가 위 버전 조건이 요구하던 바로 그 조항이다.**
- **묶는 방식이 두 소스에서 다르다.** 위 [세 범주로 묶어 읽기](#세-범주로-묶어-읽기)는 열
  항목을 **인증과 인가·인벤토리 관리·자원 관리** 셋으로 묶는다. 그쪽은 **위협 모델링 방법론의
  여섯 범주 아래로 항목을 흩어 놓고** 각 자리에서 완화를 함께 적는다 (6장,
  p.154).[^gough2022]
  - **두 묶음이 겨루지 않는다 — 묶는 축이 다르다.** 이쪽은 **무엇이 잘못되는가**로 묶고 그쪽은
    **누가 어떻게 공격하는가**로 묶는다. 그쪽의 배치는
    [STRIDE로 API 위협을 식별하기](stride-threats-for-apis.md)가 갖는다.
  - **그쪽에서 이름으로 확인되는 항목이 다섯이다** — 깨진 사용자 인증, 불충분한 로깅과 모니터링,
    과도한 데이터 노출, 자산 관리 부실, 그리고 인가 붕괴 둘(객체 수준과 기능 수준)이다.
    **주입과 서비스 거부는 항목이 있다고만 적히고 이름이 그대로 인용되지 않는다** (6장,
    pp.154–161).[^gough2022] **이 세는 일은 이 KB의 것이다.** #hypothesis
- **그쪽 7장이 그 목록에 순위 하나를 매긴다** — **이 목록에 오른 인가 관련 보안 문제 가운데 가장
  흔한 둘이 객체 수준 인가의 붕괴와 기능 수준 인가의 붕괴**라는 것이다 (7장 §"Authorization
  Enforcement", p.185).[^gough2022] 두 항목의 규정과 그것을 집행하는 조항은
  [OAuth2 그랜트와 스코프와 신원 계층](oauth2-grants-scopes-and-identity-layer.md)이 갖는다.
  - **위 [인증과 인가](#인증과-인가)가 규정 둘과 최소 권한 원칙까지만 갖고 있던 자리가
    그것으로 메워진다** — 이 페이지의 소스는 인가를 원칙으로 적고, 그쪽은 **인가가 무너질 때
    실제로 무엇이 일어나는가**를 두 항목의 이름으로 적는다. 이 대조는 이 KB의 것이다.
