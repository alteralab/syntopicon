## 데이터 정의와 데이터 로직

- 왜 이것이 서빙의 문제인가 — **강조해 논했듯 조직에서 데이터의 효용은 궁극적으로 그 정확성과
  신뢰성에서 나온다. 결정적으로 데이터의 정확성은 원천 시스템의 이벤트 값을 충실히 재현하는 것을
  넘어선다. 데이터 정확성은 적절한 데이터 정의와 로직도 아우르며, 이것들은 원천 시스템에서 데이터
  파이프라인을 거쳐 BI 도구에 이르기까지 모든 수명 주기 단계에 걸쳐 데이터에 구워져 들어가야 한다**
  (9장, p.342).[^reis2022]
- 두 낱말 — **데이터 정의(data definition)는 조직 전반에서 이해되는 대로의 데이터의 의미를 가리킨다.
  예컨대 *고객*은 회사 안에서, 그리고 부서에 걸쳐 정확한 의미를 갖는다. 고객의 정의가 달라질 때
  그것들은 문서화되어 데이터를 쓰는 모두에게 제공돼야 한다** (9장, pp.342–343).[^reis2022]
- **데이터 로직(data logic)은 총매출이나 고객 생애 가치 같은 데이터에서 지표를 도출하는 공식을
  규정한다. 적절한 데이터 로직은 데이터 정의와 통계 계산의 세부를 인코딩해야 한다. 고객 이탈 지표를
  계산하려면 정의가 필요하다 — 누가 고객인가? 순이익을 계산하려면 총수익에서 어떤 비용을 차감할지
  결정할 논리 규칙의 집합이 필요하다** (9장, p.343).[^reis2022] 이 로직이 실제로 얼마나 복잡해지는지의
  실물은 [수명 주기의 변환 단계](../concepts/transformation-in-the-lifecycle.md)의 업무 로직 절에
  있다.

## 제도적 지식으로 떠돌 때

- 실패 양식 — **우리는 데이터 정의와 로직이 당연시되어, 흔히 제도적 지식(institutional knowledge)의
  형태로 조직 안을 떠도는 것을 자주 본다. 제도적 지식은 그 자체의 생명을 얻으며, 데이터 기반의 통찰·
  결정·행동을 일화가 대체하는 대가를 치른다. 대신 데이터 카탈로그와 데이터 엔지니어링 수명 주기의
  시스템 안에서 데이터 정의와 로직을 형식적으로 선언하는 것이 데이터의 정확성·일관성·신뢰성을
  보장하는 데 크게 기여한다** (9장, p.343).[^reis2022] 카탈로그 쪽 장치는
  [메타데이터 관리](../concepts/metadata-management.md)에 있다.

## 정의는 대부분 암묵적으로 서빙된다

- **데이터 정의는 여러 방식으로 서빙될 수 있으며, 때로는 명시적으로, 그러나 대부분은 암묵적으로
  서빙된다. 암묵적이라는 말은 질의·대시보드·ML 모델을 위해 데이터를 서빙할 때마다 데이터와 파생
  지표가 일관되고 올바르게 제시된다는 뜻이다. SQL 질의를 쓸 때 당신은 이 질의의 입력이 — 상류
  파이프라인 로직과 정의를 포함해 — 올바르다고 암묵적으로 가정하는 것이다. 이 자리가 8장에서 서술한
  데이터 모델링이 데이터 정의와 로직을, 여러 최종 사용자가 이해하고 쓸 수 있는 방식으로 포착하는 데
  엄청나게 유용한 지점이다** (9장, p.343).[^reis2022] 그 모델링은
  [데이터 모델링의 기초](../concepts/data-modeling-fundamentals.md)에 있다.
- 그래서 계층이 필요하다 — **시맨틱 계층(semantic layer)을 쓰면 업무 정의와 로직을 재사용 가능한
  방식으로 통합한다. 한 번 쓰고 어디서나 쓴다. 이 패러다임은 지표·계산·로직에 대한 객체 지향적
  접근이다** (9장, p.343).[^reis2022]

## 데이터 품질과 질의 품질은 다르다

- 저자들이 서빙에서 관측하는 것 — **데이터 엔지니어는 서빙을 생각할 때 자연스럽게 데이터 처리·저장
  기술 쪽으로 끌린다 — 스파크를 쓸 것인가 클라우드 데이터 웨어하우스를 쓸 것인가? 데이터는 오브젝트
  저장에 있는가 SSD 무리에 캐시돼 있는가? 그러나 방대한 데이터셋에 걸쳐 빠른 질의 결과를 내놓는
  강력한 처리 엔진이 본질적으로 좋은 업무 분석을 만들어 주지는 않는다. 저품질 데이터나 저품질 질의를
  먹이면 강력한 질의 엔진은 빠르게 나쁜 결과를 반환한다** (9장, p.355).[^reis2022]
- 두 축의 구분 — **데이터 품질이 데이터 자체의 특성과 나쁜 데이터를 걸러 내거나 개선하는 다양한
  기법에 초점을 둔다면, 질의 품질은 업무 질문에 정확한 답을 반환하는 적절한 로직으로 질의를 짓는
  문제다. 고품질 ETL 질의와 리포팅을 쓰는 것은 시간 집약적이고 세밀한 작업이다. 다양한 도구가 이
  과정의 자동화를 도우면서 일관성·유지보수·지속적 개선을 촉진할 수 있다** (9장,
  p.355).[^reis2022]

## 메트릭 계층이라는 도구

- 정의 — **근본적으로 메트릭 계층(metrics layer)은 업무 로직을 유지하고 계산하는 도구다. (시맨틱
  계층은 개념적으로 극히 비슷하고, 헤드리스 BI(headless BI)는 또 하나의 밀접히 관련된 용어다.) 이
  계층은 BI 도구 안에 살 수도 있고 변환 질의를 짓는 소프트웨어 안에 살 수도 있다. 두 구체적 예가
  Looker와 Data Build Tool(dbt)이다** (9장, p.356).[^reis2022] 저자들은 이 어휘의 출처로 Benn
  Stancil의 "The Missing Piece of the Modern Data Stack"(2021)과 Srini Kadamati의 "Understanding
  the Superset Semantic Layer"(2021)를 각주로 든다 (9장, p.356, 각주 4·5).[^reis2022]
- 무엇을 해결하는가 — **우리는 메트릭 계층 도구가 더 넓은 채택과 더 많은 진입자와 함께 인기를 얻고,
  애플리케이션 쪽으로 상류로 옮겨 가리라 믿는다. 메트릭 계층 도구는 사람들이 데이터를 분석해 온
  이래 조직을 괴롭혀 온 분석의 중심 질문 하나를 푸는 데 도움을 준다: "이 숫자들이 맞습니까?"** (9장,
  p.356).[^reis2022] #hypothesis — 2022년 시점 저자들의 전망이다.

## Looker와 dbt가 사는 자리

- **Looker의 LookML은 사용자가 가상의 복잡한 업무 로직을 정의하게 해 준다. 리포트와 대시보드는 지표를
  계산하기 위해 특정 LookML을 가리킨다. Looker는 사용자가 표준 지표를 정의하고 많은 하류 질의에서
  그것을 참조하게 해 준다. 이는 전통적 ETL 스크립트에서의 반복과 불일치라는 전통적 문제를 풀기 위한
  것이다. Looker는 LookML로 SQL 질의를 생성하고 이 질의는 데이터베이스로 밀어 내려진다. 결과는
  Looker 서버에 영속될 수도 있고 큰 결과 집합의 경우 데이터베이스 자체에 영속될 수도 있다** (9장,
  p.356).[^reis2022] 이 밀어 내림이 질의 푸시다운이며 그 서빙 경로는
  [데이터를 서빙하는 방식](../concepts/data-serving-methods.md)에 있다.
- **dbt는 사용자가 많은 질의와 업무 지표의 표준 정의를 아우르는 복잡한 SQL 데이터 흐름을 정의하게 해
  주며 이는 Looker와 매우 비슷하다. Looker와 달리 dbt는 변환 계층에서만 배타적으로 돌아간다 — 다만
  이는 질의 시점에 계산되는 뷰로 질의를 밀어 넣는 것을 포함할 수 있다. Looker가 서빙 질의와 리포팅에
  초점을 둔다면 dbt는 분석 엔지니어를 위한 견고한 데이터 파이프라인 오케스트레이션 도구로 봉사할 수
  있다** (9장, p.356).[^reis2022]
  - 층위의 대비 — 같은 업무 로직을 Looker는 **읽기 시점**에, dbt는 **변환 시점**에 두는 셈이다.
    2장이 대비시킨 읽기 시 로직(logic-on-read)과 변환 단계 적용의 갈림이 제품 두 개로 실현된
    것이다 — 그 갈림은
    [수명 주기의 서빙 단계](../concepts/serving-in-the-lifecycle.md)의 BI 절에 있다.

## 같은 낱말의 다른 뜻 — 레이크하우스 소비 계층 안의 시맨틱 계층

**같은 낱말이 다른 것을 가리키는 자리가 하나 있다.** 위 절들의 시맨틱 계층은 업무 정의와 로직을
재사용 가능하게 모으는 **도구 계층**이다. 2025년에 나온 레이크하우스 설계서 하나에서 같은 낱말은
소비 계층 안의 **물리 하위 계층**을 가리킨다.

- 그 소스의 출발점은 복잡성의 성장이다 — 팩트와 차원을 가진 스타 스키마 구현이 소비 계층의 인기
  전략이지만 **차원 모델이 커지고 새 데이터 원천이 통합되면서 점점 복잡해질 수 있고**, 이 성장이
  흔히 **비슷하지만 다른 설계 접근을 요구할 만큼 구별되는 겹치는 요구**를 낳는다 (3장 §"Gold
  Layer" ▸ "Curated, Semantic, and Platinum Layers").[^strengholt2025]
- 그래서 **계층 이름이 늘어난다** — 어떤 조직은 **추가 합치(conformed) 계층이나 큐레이션 계층**을
  더하고, 스타 스키마를 쓰는 데이터 마트를 위해 **별도의 (시맨틱) 계층**을 둔다. **때때로 이 추가
  계층들을 플래티넘 계층(Platinum layer)이라 부르며 그 특화되고 고도로 정제된 성격을 강조한다**
  (3장 §"Gold Layer" ▸ "Curated, Semantic, and Platinum Layers").[^strengholt2025]
- 그런 설정에서 조직이 **표준 참조 테이블과 표준 차원을 만드는 전사 데이터 모델링**을 따르는 것이
  흔하고, 그것이 더 큰 레이크하우스 아키텍처 안의 **여러 데이터 마트에 걸쳐 쓰인다.** 복잡하고
  시간이 많이 든다고 여겨지지만 **데이터 재사용성과 표준화를 보장하므로 여전히 인기 있다** (3장
  §"Gold Layer" ▸ "Curated, Semantic, and Platinum Layers").[^strengholt2025]
- 같은 소스의 그림 3-5 캡션이 그 계층을 한 줄로 규정하고, **이 문장은 본문에 없고 그림에만 있다**
  (3장 §"Gold Layer" ▸ "The Gold Layer in Practice", 그림 3-5):[^strengholt2025]

> Data is application-specific, i.e., semantic layers

- 정리하면 **사실 충돌이 아니라 같은 낱말의 다른 지시 대상**이다. 이 페이지의 시맨틱 계층은
  **정의가 어디에 선언되는가**의 문제이고, 저쪽의 시맨틱 계층은 **데이터가 어디에 물리적으로
  놓이는가**의 문제다. 두 뜻이 검색에서 섞이지 않도록 여기 적어 둔다. 계층 쪽 서술은
  [메달리온 Gold 계층](../concepts/medallion-gold-layer.md)에 있다.

## 셋째 자리 — 리포팅 도구가 읽는 시맨틱 모델

**같은 소스의 7장이 위 절과 또 다른 자리를 준다.** 3장의 "시맨틱 계층"이 물리 하위 계층이었다면
7장의 **시맨틱 모델(semantic model)** 은 이 페이지 앞부분의 **도구 계층**에 속한다. 곧 한 책 안에서
낱말이 두 뜻으로 쓰이고, 그 둘째 뜻이 이 페이지의 본류다.

- 규정 — **데이터를 더 이해하고 분석하기 쉽도록 표현·조직하는 방식**이고, 저자의 비유로는 **기술적
  컬럼 이름을 가진 복잡한 데이터 모델을 더 사용자 친화적인 설계로 번역하는 것**이다. 이것이 업무
  사용자의 **셀프서비스 역량을 크게 높인다** — 데이터 처리나 질의 언어의 깊은 기술 전문성 없이
  데이터와 상호작용할 수 있기 때문이다 (7장 §"Design of the Gold Layer" ▸ "Creation of the Semantic
  Model").[^strengholt2025]
- 세우는 개념 단계 — 포함할 테이블을 고르고, **테이블 사이 관계를 만들고**, **카디널리티를
  정의하고**(차원 식별자와 팩트 키는 일대다), **이름을 바꾸고 불필요한 컬럼을 숨겨** 사용자
  친화적으로 만든 뒤 **측정값을 만든다** (같은 소절).[^strengholt2025]
- **계산을 어디에서 할 것인가의 권고가 이 페이지와 맞닿는다** — 리포팅 도구의 수식 언어는 **계산을
  계산 집약적으로 만들 수 있으므로**, **가능한 한 많은 데이터를 원천에서 미리 계산한 뒤 가져오라**는
  것이 저자의 권고다. 더해 **데이터 모델을 제대로 설계하는 것, 특히 스타 스키마를 쓰고 올바른
  카디널리티로 관계를 관리하는 것**이 소비 애플리케이션의 속도와 확장성을 보장한다 (같은
  소절).[^strengholt2025]
  - 위 [Looker와 dbt가 사는 자리](#looker와-dbt가-사는-자리) 절이 **읽기 시점 로직과 변환 시점
    로직**의 갈림으로 두 제품을 대비시켰다면, 이 권고는 그 축에서 **변환 시점 쪽에 무게를 싣는
    판정**이다. 같은 갈림 위의 선택이지 새 축이 아니다.
- **이력 데이터가 이 모델과 부딪히는 자리**(직접 질의 모드가 필터를 지원하지 않아 생기는 선택지
  넷)는 계층 설계의 문제라 [Gold 계층 구현](../concepts/gold-layer-implementation.md)이 받는다.
