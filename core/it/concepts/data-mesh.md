하나의 질문: **중앙집중 데이터 플랫폼이 커질 때 생기는 문제를 도메인 소유권을 뒤집어 푸는
제안은 무엇을 주장하는가.**

이 페이지는 **개관**이다. 정본 소스는 제안자 Zhamak Dehghani 자신의
[*Data Mesh*](../sources/dehghani2022.md)(O'Reilly, 2022)이고, 여기 있는 것은 그 책 1장이
스스로 "요약"이라 부르는 층이다. **네 원칙 각각은 원전이 장 하나씩을 할당한 전용 페이지가
따로 있다** ([도메인 소유권 원칙](../concepts/domain-ownership-principle.md)·
[제품으로서의 데이터 원칙](../concepts/data-as-a-product-principle.md)·
[셀프서브 데이터 플랫폼 원칙](../concepts/self-serve-data-platform-principle.md)·
[연합 컴퓨테이셔널 거버넌스 원칙](../concepts/federated-computational-governance-principle.md)) —
여기 남는 것은 1장·프롤로그가 개관으로 적은 층뿐이다.

## 정의

- 저자가 책 첫 문장에 놓는 정의를 직인용한다 (1장, p.3):[^dehghani2022]

> Data mesh is a decentralized sociotechnical approach to share, access, and manage
> analytical data in complex and large-scale environments—within or across organizations.

- 여기서 말하는 데이터는 **분석 데이터**(analytical data)다 — **이 책에서 한정어 없이 쓰는
  "데이터"는 분석 데이터를 가리킨다. 분석 데이터는 리포팅과 기계 학습 훈련 용법을 서빙한다**
  (1장, p.3).[^dehghani2022]
- 저자는 이것을 아키텍처도 원칙 목록도 운영 모델도 아닌 **사회기술 패러다임**(sociotechnical
  paradigm)으로 분류하기로 결정한다 — 원문을 직인용한다 (1장, p.6):[^dehghani2022]

> Hence, I have decided to classify data mesh as a sociotechnical paradigm: an approach
> that recognizes the interactions between people and the technical architecture and
> solutions in complex organizations.

  - 그렇게 분류한 이유는 최적화 대상이 둘이기 때문이다 — **기술적 탁월성만이 아니라 관련된
    모든 사람(데이터 제공자·사용자·소유자)의 경험도 함께 개선하는 데이터 관리 접근이다**
    (1장, p.6).[^dehghani2022]
- 쓰임의 층위도 저자가 지정한다 — **데이터 메시는 전사 데이터 전략의 한 요소로 활용될 수
  있으며, 엔터프라이즈 아키텍처와 조직 운영 모델의 목표 상태를 반복적 실행 모델과 함께
  서술한다** (1장, p.6).[^dehghani2022]

## 무엇을 얻으려 하는가

- 목표는 셋이다 (1장, p.4):[^dehghani2022]
  - **변화에 우아하게 대응한다** — 사업의 본질적 복잡성·변동성·불확실성에.
  - **성장 앞에서 기민함을 유지한다**(sustain agility in the face of growth).
  - **투자 대비 데이터에서 나오는 가치의 비율을 높인다.**
- 세 목표는 규모가 커질 때 무너지는 것들이다. 저자가 되풀이하는 축은 셋 — **데이터 원천의
  수 증가, 데이터 소비자의 수 증가, 데이터 용법의 다양성 증가**가 조직 성장의 축이고 데이터
  공유가 그 축을 따라 확장(scale out)되어야 한다 (1장, p.6).[^dehghani2022]
- 2부 7장이 같은 세 목표를 한 문장으로 다시 적는다 — **궁극적으로 데이터 메시의 목표는 조직이
  규모에서 데이터로부터 가치를 얻게(get value from data at scale) 하는 것이다. 데이터를 사업을
  개선하고 최적화하는 데만이 아니라 재형성하는 데도 쓰면서** (7장, p.106).[^dehghani2022]
  그 세 목표가 왜 **지금** 위태로운지는
  [분석 데이터 관리의 변곡점](../concepts/data-mesh-inflection-point.md)이 다섯 거시 동인으로
  받고, 무엇이 그것을 만드는지는 아래 [변곡점 이후](#변곡점-이후--세-결과를-무엇이-만드는가)가
  받는다.

## 여섯 축의 이동

- 저자는 데이터 메시가 이전 접근에서 무엇을 옮기는지를 여섯 축으로 나눈다. 각 항의 앞이
  이전, 뒤가 데이터 메시다 (1장, pp.4–5):[^dehghani2022]
  - **조직적으로** — 플랫폼 기술을 운영하는 전문가들이 데이터를 중앙에서 소유하던 것에서,
    데이터가 생산되거나 사용되는 업무 도메인으로 소유권과 책무를 되돌리는 탈중앙 소유 모델로.
  - **아키텍처적으로** — 모놀리식 웨어하우스와 레이크에 데이터를 **모으는**(collecting) 것에서,
    표준 프로토콜로 접근되는 데이터 프로덕트의 분산 메시를 통해 데이터를 **잇는**(connecting)
    것으로.
  - **기술적으로** — 데이터를 파이프라인 코드 실행의 부산물로 다루는 해법에서, 데이터와 그것을
    유지하는 코드를 하나의 살아 있는 자율 단위로 다루는 해법으로.
  - **운영적으로** — 사람의 개입이 있는 하향식 중앙 거버넌스 운영 모델에서, 메시의 노드에
    계산 가능한 정책이 심긴 연합 모델로.
  - **원칙적으로** — 모을 자산으로서의 데이터라는 가치 체계에서, 데이터 사용자(조직 내부와
    외부 모두)를 서빙하고 기쁘게 할 제품으로서의 데이터로.
  - **인프라적으로** — 데이터·분석용과 애플리케이션·운영계용으로 파편화되어 점대점 통합된 두
    벌의 인프라 서비스에서, 운영계와 데이터 시스템 양쪽을 위한 잘 통합된 한 벌로.
- 다섯째 항의 전환("자산이 아니라 제품")이 왜 은유 수준의 문제가 아닌지는
  [제품으로서의 데이터 원칙](../concepts/data-as-a-product-principle.md)에 있다.

## 네 원칙

- 저자는 네 원칙이 **모아서 필요충분하도록**(collectively necessary and sufficient) 의도했다고
  밝힌다 (1장, p.9).[^dehghani2022] 도입 순서도 의미가 있다 — **원칙들이 서로 위에 쌓이기
  때문이다. 데이터 소유권과 아키텍처의 도메인 지향 분산이 이 접근의 심장이고, 나머지 전부가
  거기서 따라 나온다. 데이터 메시는 이 원칙들 전부다** (1부 도입, p.2).[^dehghani2022]

| 원칙 | 원어 | 한 줄 |
|---|---|---|
| 도메인 소유권 | Principle of Domain Ownership | 분석 데이터의 소유권을 데이터에 가장 가까운 업무 도메인으로 탈중앙화한다 |
| 제품으로서의 데이터 | Principle of Data as a Product | 도메인 데이터를 데이터 사용자에게 직접 제품으로 공유한다 |
| 셀프서브 데이터 플랫폼 | Principle of the Self-Serve Data Platform | 도메인 교차 기능 팀이 데이터를 공유할 수 있게 하는 셀프서브 플랫폼 서비스를 둔다 |
| 연합 컴퓨테이셔널 거버넌스 | Principle of Federated Computational Governance | 도메인 대표들의 연합 의사결정 구조를 만들고 정책을 코드로 자동화한다 |

- 첫째 원칙의 요지 — **데이터에 가장 가까운 업무 도메인(데이터의 원천이거나 주 소비자)으로
  분석 데이터의 소유권을 탈중앙화한다. (분석) 데이터를 그것이 대표하는 업무 도메인에 근거해
  논리적으로 분해하고, 도메인 지향 데이터의 수명 주기를 독립적으로 관리한다** (1장,
  p.6).[^dehghani2022] 깊이는
  [도메인 소유권 원칙](../concepts/domain-ownership-principle.md)에 있다.
- 둘째 원칙의 요지 — **도메인 지향 데이터가 데이터 사용자(데이터 분석가·데이터 과학자 등)에게
  직접 제품으로 공유된다** (1장, p.7).[^dehghani2022] 여덟 가지 사용성 속성과 그 근거는
  [제품으로서의 데이터 원칙](../concepts/data-as-a-product-principle.md)에 있다.
- 둘째 원칙은 새 논리 아키텍처 단위도 도입한다 — **제품으로서의 데이터는 데이터 퀀텀(data
  quantum)이라는 새 논리 아키텍처 단위를 도입한다. 이것은 데이터를 제품으로 공유하는 데
  필요한 모든 구조적 구성 요소 — 데이터·메타데이터·코드·정책·인프라 의존성 선언 — 를 자율적으로
  통제하고 캡슐화한다** (1장, p.7).[^dehghani2022] 원전이 9장 한 장으로 이 단위를 정의하므로
  깊이는 [데이터 퀀텀](../concepts/data-quantum.md)이 받는다 — 여기 남는 것은 1장·프롤로그의
  개관뿐이다.
  - 그 단위의 성질은 **아키텍처 퀀텀**(architecture quantum) — **독립적으로 배포될 수 있으면서
    자기 일을 하는 데 필요한 구조적 구성 요소를 전부 갖춘, 아키텍처의 가장 작은 단위**
    (프롤로그, p.xxxv).[^dehghani2022] 확장 방식은 이 정의에서 바로 따라 나온다 — **동등한
    노드(coequal nodes)를 더 추가하고 서로 연결함으로써 무한한 규모를 얻는
    스케일아웃(scale-out) 아키텍처다**
    (프롤로그, p.xxxv).[^dehghani2022]
- 셋째 원칙의 요지 — **도메인의 교차 기능 팀이 데이터를 공유할 수 있게 힘을 주는 새 세대의
  셀프서브 데이터 플랫폼(self-serve data platform) 서비스다. 플랫폼 서비스는 원천에서 소비까지
  데이터 공유의 종단 간 여정에서 마찰을 제거하는 데 중심을 둔다** (1장, p.8).[^dehghani2022]
  깊이는 [셀프서브 데이터 플랫폼 원칙](../concepts/self-serve-data-platform-principle.md)에 있다.
  - 플랫폼이 맡는 층은 둘이다 — **개별 데이터 프로덕트의 전체 수명 주기를 관리하고, 서로 연결된
    데이터 프로덕트의 신뢰할 만한 메시를 관리한다. 메시 전역에 걸친 창발적 지식 그래프와 계보를
    드러내는 것 같은 메시 수준 경험을 제공한다** (1장, p.8).[^dehghani2022]
  - 사용자 최적화가 기계 최적화를 희생하지 않게 하는 분업도 예고된다 — **플랫폼의 경험
    플레인(experience plane)이 자율적이면서 연결된 데이터 프로덕트를 다루는 사용자 경험을
    최적화하는 동안, 플랫폼의 유틸리티 플레인(utility plane)은 물리·기계 수준 성능을
    최적화한다** (프롤로그, p.xxxiv).[^dehghani2022]
- 넷째 원칙의 요지 — **도메인 대표·데이터 플랫폼·주제 전문가(법무·컴플라이언스·보안 등)로 구성된
  팀이 이루는 연합 의사결정과 책무 구조에 기반한 데이터 거버넌스 운영 모델이다. 이 운영 모델은
  도메인의 자율성·기민함과 메시의 전역 상호운용성 사이의 균형을 잡는 유인과 책무 구조를 만든다**
  (1장, p.8).[^dehghani2022] 깊이는
  [연합 컴퓨테이셔널 거버넌스 원칙](../concepts/federated-computational-governance-principle.md)에
  있다.
  - "컴퓨테이셔널"이 붙는 이유 — **거버넌스 실행 모델은 플랫폼 서비스를 통해 모든 데이터
    프로덕트에 대해 세밀한 수준에서 정책을 코드화하고 자동화하는 데 크게 의존한다** (1장,
    p.8).[^dehghani2022]

## 원칙들은 서로를 고친다

- 네 원칙이 서로 보완이라는 말의 뜻은 **각 원칙이 다른 원칙에서 생길 수 있는 새 난제에
  답한다**는 것이다 (1장, p.9).[^dehghani2022] 저자가 드는 연쇄는 둘이다:
  - **탈중앙 도메인 지향 데이터 소유권은 도메인 안에서의 데이터 사일로화를 낳을 수 있고, 이는
    도메인이 자기 데이터를 도메인 안팎으로 제품다운 품질을 갖춰 공유할 조직적 책임을 지도록
    요구하는 제품으로서의 데이터 원칙이 해소한다** (1장, p.10).[^dehghani2022]
  - **도메인이 데이터 프로덕트를 소유하면 노력 중복·소유 비용 증가·데이터 공유 생산성 저하로
    이어질 수 있고, 이 경우 셀프서브 데이터 플랫폼이 도메인 교차 기능 팀에 힘을 준다. 플랫폼의
    목표는 도메인 팀의 인지 부하를 낮추고 불필요한 노력을 줄이고 도메인의 생산성을 높이고 총
    소유 비용을 낮추는 것이다** (1장, p.10).[^dehghani2022]
- 운영 모델로 그리면 이렇다 — **교차 기능 팀을 갖춘 도메인들이 디지털 애플리케이션과 데이터
  프로덕트로 업무 도메인의 목표를 달성한다. 각 도메인은 계약을 통해 자기 데이터와 서비스를
  공유한다. 데이터 프로덕트는 조합될 수 있고 새 도메인이 소유할 수 있다. 전역 정책은 도메인
  대표들로 구성된 연합 그룹이 정의한다. 정책은 다른 플랫폼 서비스와 함께 자동화된 능력으로
  제공된다** (1장, p.11).[^dehghani2022]

## 변곡점 이후 — 세 결과를 무엇이 만드는가

2부 7장 "After the Inflection Point"는 위 세 목표를 **결과**(outcomes)로 다시 부르고, 각 결과를
어떤 실행 축이 만들며 그 축이 어느 원칙에 걸리는지를 하나씩 짚는다. 곧 이 절은
**"왜"에서 "그래서 무엇이 달라지는가"로 넘어가는 다리**다.

- 데이터 메시가 **가정으로 깔고 시작하는 것**부터 명시된다 — **기본값으로 데이터 메시는 데이터의
  편재하는 본성(ubiquitous nature of data)을 가정한다. 데이터는 어떤 기원에서든 올 수 있다.
  조직 안이든 밖이든, 그리고 조직적 신뢰 경계를 가로질러 어떤 시스템에서든 올 수 있다. 어떤
  기저 플랫폼이든 이 클라우드 호스팅 서비스든 저 서비스든 서빙할 수 있다. 데이터 메시는 데이터
  용례의 다양성과 데이터에 대한 그들의 고유한 접근 양식을 가정한다. (…) 마지막으로 데이터
  메시는 사업의 복잡성 — 지속적 성장·변화·다양성 — 을 존재의 자연 상태로 가정한다** (7장,
  p.105).[^dehghani2022] 그 가정의 근거가
  [분석 데이터 관리의 변곡점](../concepts/data-mesh-inflection-point.md)이다.
- 과거에서 무엇을 가져가고 무엇을 버리는지도 한 문단으로 적는다 — **데이터 메시는 과거 해법에서
  배우고 그 단점을 다룬다. 조정 병목으로 작동하는 중앙집중 지점(points of centralization)을
  줄인다. 동기화로 조직을 늦추지 않으면서 데이터 아키텍처를 분해하는 새 방법을 찾는다. 데이터가
  비롯되는 곳과 그것이 사용되는 곳 사이의 간극을 없애고, 두 데이터 플레인 사이에서 일어나는
  우발적 복잡성(accidental complexities) — 일명 파이프라인 — 을 제거한다. 데이터 메시는 단일
  진실 원천이나 하나의 긴밀히 통제된 정규 데이터 모델 같은 데이터 신화에서 떠난다** (7장,
  p.105).[^dehghani2022]

### 결과 하나 — 복잡한 사업에서 변화에 우아하게 대응한다

- 문제 설정 — **사업은 복잡계이며, 각자 고유한 책무 구조와 목표를 갖는 많은 도메인으로
  구성된다. 그들은 각기 다른 속도로 변한다. 사업 전체의 행동은 그 도메인·기능과 그들의 상호작용·
  의존성 사이의 복잡한 관계망의 결과다** (7장, p.106).[^dehghani2022]
- **업무·기술·데이터를 정렬한다** — **첫째 데이터 메시 원칙은 분석 데이터에 대해 같은 분해를
  수행하며, 그 결과가 데이터의 도메인 소유권(domain ownership of data)이다. 각 사업 단위가
  분석 데이터 소유권과 관리의 책임을 진다. 데이터에 가장 가까운 사람들이 어떤 분석 데이터가
  존재하고 그것이 어떻게 가장 잘 해석되어야 하는지 이해하기에 가장 좋은 위치이기 때문이다**
  (7장, p.107).[^dehghani2022]
  - 그 결과 — **도메인 소유권은 분산 데이터 아키텍처를 낳는다. 여기서 데이터 아티팩트 —
    데이터셋·코드·메타데이터·데이터 정책 — 는 각자 대응하는 도메인이 유지한다** (7장,
    p.107).[^dehghani2022]
- **분석 데이터와 운영 데이터의 간극을 좁힌다** — **좋은 결정을 그 순간에 내리려면 분석
  데이터가 업무 진실성(business truthfulness)을 반영해야 한다. 결정이 내려지는 순간의 사업의
  사실과 현실에 가능한 한 가까워야 한다. 서로 멀리 떨어져 부서지기 쉬운 데이터 파이프라인과
  중개 데이터 팀을 통해 연결된 두 개의 분리된 데이터 플레인으로는 이것을 달성하기 어렵다.
  데이터 파이프라인은 해체되어야 하고 분석 데이터와 능력을 원천에 가능한 한 가깝게 제공하는 새
  방식에 자리를 내주어야 한다** (7장, p.108).[^dehghani2022]
  - 그 자리를 무엇이 받는가 — **데이터 메시는 도메인을 중심으로 방향 지어져 제품으로 공유되는
    데이터를 통해 두 플레인 사이의 간극과 피드백 루프를 좁힐 것을 제안한다. 데이터 메시는 두
    플레인을 새 구조 아래 잇는다 — P2P로 연결된 데이터 프로덕트와 애플리케이션의 네트워크, 곧
    분석 데이터를 교환하는 메시다** (7장, p.109).[^dehghani2022]
  - 경계를 지우는 것은 아니다 — **데이터 메시는 운영 데이터와 분석 데이터 사이의 근본적 기술적
    차이를 계속 존중하면서, 이 절에서 보인 대로 간극을 좁히고 둘을 긴밀히 통합한다** (7장,
    p.109).[^dehghani2022] 아래 [어떤 데이터를 말하는가](#어떤-데이터를-말하는가)가 그 차이의
    정본이다.
- **데이터 변경을 업무 도메인 안으로 국소화한다** — **데이터 메시는 하류 데이터 사용자에게
  치명적 영향을 주지 않으면서 데이터 모델이 지속적으로 변할 수 있게 한다. 공유된 전역 정규
  데이터 모델을 제거하고 따라서 변경을 동기화할 필요를 제거함으로써 그렇게 한다** (7장,
  p.110).[^dehghani2022]
  - 그 자유를 가능케 하는 장치 — **데이터 메시는 도메인 데이터를 공유하기 위해 잘 정의되고
    보증된 데이터 계약(data contracts)을 부과한다. 도메인 데이터 계약은 데이터 사용자가 새
    리비전으로 우아하게 이전할 때까지 더 오래된 리비전을 지원한다. 이것이 도메인을 해방해 자기
    데이터 모델을 지속적으로 바꿀 수 있게 한다** (7장, p.110).[^dehghani2022]
- **파이프라인과 데이터 복사의 우발적 복잡성을 줄인다** — 저자는 Fred Brooks의
  "No Silver Bullet—Essence and Accident in Software Engineering"에서 어휘를 가져온다 —
  **소프트웨어 해법을 지을 때 복잡성에는 두 유형이 있다. 첫째, 문제 공간에 본질적이고 내재적인
  본질적 복잡성(essential complexity)이 있다. 이것이 업무·도메인 복잡성이다. 둘째, 우발적
  복잡성(accidental complexity)이 있다: 우리 — 엔지니어·아키텍트·설계자 — 가 우리 해법 안에
  만들어 내는 복잡성이다. 우발적 복잡성은 줄일 수 있고 줄여야 한다** (7장,
  p.111).[^dehghani2022]
  - 제거 대상으로 지목되는 것은 **복사의 여정**이다 — **오늘날 우리는 또 하나의 접근 양식이나
    또 하나의 계산 모델을 위해 데이터가 필요하기 때문에 데이터를 계속 복사해 돌린다. 운영
    시스템에서 랜딩 존으로, 그다음 데이터 레이크로, 그 뒤 데이터 과학자를 위한 피처 스토어로
    복사한다. 데이터 분석가 접근을 위해 레이크에서 레이크쇼어 마트로 다시 복사하고, 마지막
    구간에서는 하류 대시보드나 리포팅 데이터베이스로 복사한다. (…) 오늘날 분석 워크로드를
    돌리려면 어느 클라우드 제공자가 레이크나 웨어하우스에 당신의 모든 데이터를 복사할지를
    가치를 얻기 전에 미리 결정해야 한다** (7장, p.111).[^dehghani2022]
  - 대안으로 제시되는 아키텍처 단위 — **데이터 메시는 도메인 지향 데이터 시맨틱을 캡슐화하면서
    동시에 서로 다른 용례와 사용자에게 적합한 여러 데이터 접근 양식을 제공하는 새 아키텍처
    단위를 만들어 이 문제를 다룬다. 이 아키텍처 단위를 데이터 프로덕트 퀀텀(data product
    quantum, 줄여서 데이터 퀀텀)이라 부른다. 데이터 퀀텀은 자기 네이티브 접근 양식 각각 —
    SQL·파일·이벤트 등 — 에 대해 명시적인 계약과 보증 집합을 갖는다. 외부 데이터 사용자에게
    데이터를 제공하기로 선택하는 경우 인터넷 어디서든 접근될 수 있다. 접근 시점에 자기 인터페이스
    각각에 대해 접근 통제와 정책 시행을 제공한다. 데이터 퀀텀은 자기 데이터를 변환하고 유지하는
    코드를 캡슐화한다. 데이터 파이프라인은 해체되어 데이터 퀀텀 로직의 내부 구현이 된다** (7장,
    p.111).[^dehghani2022] 그 단위의 정의는 위 [네 원칙](#네-원칙) 절에 있다.

### 결과 둘 — 성장 앞에서 기민함을 유지한다

- 요약 — **성장 앞에서 기민함을 유지하는 데이터 메시의 접근은 조직 전반의 병목·조정·동기화를
  줄이는 것을 목표로 하는 몇 가지 기법으로 요약될 수 있다. 기민함은 최소한의 의존성으로 자율적으로
  결과를 달성하는 업무 도메인의 능력에 달려 있다** (7장, p.112).[^dehghani2022]
- **중앙집중·모놀리식 병목을 제거한다** — **모놀리식 데이터 레이크나 웨어하우스를 관리하는
  중앙집중 데이터 팀은 기민함을 제한한다. 특히 태울 원천의 수나 서빙할 용례의 수가 늘 때 그렇다.
  데이터 메시는 중앙집중 병목을 주의 깊게 살핀다. 특히 그것이 아키텍처 관점과 인간 커뮤니케이션
  관점 양쪽에서 다자 동기화의 초점일 때 그렇다. **아키텍처적으로 이 병목은 데이터 레이크와 데이터
  웨어하우스를 포함한다**** (7장, p.112).[^dehghani2022]
  - 대안 — **데이터 메시는 서빙하고 소비할 때 데이터 협업에서의 P2P 접근이라는 대안을 제안한다.
    이 아키텍처는 소비자가 원천 데이터 프로덕트에서 데이터를 직접 발견하고 사용할 수 있게 한다.
    예컨대 ML 훈련 함수나 리포트가 레이크나 웨어하우스 같은 중앙집중 아키텍처 구성 요소의 개입
    없이, 그리고 중개 데이터(파이프라인) 팀의 필요 없이 독립적인 데이터 프로덕트에 직접 접근할 수
    있다** (7장, p.112).[^dehghani2022]
- **데이터 파이프라인의 조정을 줄인다** — 저자가 드는 선례는 넷이다 — **최근 몇십 년간 운영
  규모를 초과 달성한 기술들은 한 가지 공통점이 있다: 그것들은 조정과 동기화를 최소화했다.
  비동기 I/O는 블로킹 I/O 대신 네트워크 애플리케이션의 처리량을 확장했다. 리액티브
  애플리케이션은 메시지의 더 빠른 병렬 처리로 이어졌다. MapReduce 함수형 프로그래밍은
  대용량 데이터 처리를 많은 서버에 분산시켰다. 코레오그래피된 이벤트 주도 마이크로서비스는
  업무 워크플로를 확장했다** (7장, p.112).[^dehghani2022]
  - 그러나 방치된 축이 있다 — **핵심 기술에서 조정과 동기화를 제거하려는 끈질긴 노력에도
    불구하고, 우리는 대체로 조직적·아키텍처적 조정을 방치했다. 그 결과 우리 컴퓨터 시스템이
    아무리 빨리 돌아가도 결과 달성은 팀과 사람의 활동을 조정하는 일에 뒤처졌다** (7장,
    p.113).[^dehghani2022]
  - 분해 축의 교체 — **기존 아키텍처는 구성 요소의 기술적 분해 위에 지어진다 — 곧 반입·정제·
    서빙 같은 파이프라인 작업이다. 이 양식의 아키텍처 분해는 새 데이터 원천이나 새 용례가
    전달될 때마다 이 기능들 사이의 무거운 조정을 낳는다. 데이터 메시는 데이터 관리의 기술적
    분할에서 도메인 지향 분할로 옮겨 간다** (7장, p.113).[^dehghani2022] 그 진단의 전문은
    [분석 데이터 아키텍처 세대론](../concepts/analytical-data-architecture-generations.md)에 있다.
  - 계약이 개발 시점의 조정까지 줄인다 — **새 용례가 도메인 바깥의 새 데이터 프로덕트에 대한
    접근을 요구하는 경우, 소비자는 새 데이터 프로덕트가 이용 가능해질 때까지 그것의 표준 계약·
    목·스텁·합성 데이터 인터페이스를 활용해 진행할 수 있다. 이것이 계약의 아름다움이다. 계약은
    개발 중 소비자와 제공자 사이의 조정을 완화한다** (7장, p.113, 각주 3은 합성 데이터를
    **실제 데이터에서 발견되는 사적 정보를 노출하지 않으면서 실제 데이터와 비슷한 통계적·구조적
    성질을 갖는 데이터**로 정의한다).[^dehghani2022]
- **데이터 거버넌스의 조정을 줄인다** — **또 하나의 주요 조정 병목은 데이터 거버넌스의 중앙
  기능이다. 오늘날 데이터 거버넌스 조정은 데이터 접근을 허가하고, 데이터 품질을 승인하고,
  데이터 변경이 조직 정책에 부합하는지 검증하기 위해 필요하다. 중앙집중되고 심하게 수작업인
  데이터 거버넌스 프로세스는 데이터 공유의 기민함을 억제한다** (7장, p.113).[^dehghani2022]
  - 두 기능으로 마찰을 줄인다 (7장, p.114):[^dehghani2022] **각 데이터 프로덕트 안에 정책을
    코드로(policies as code) 자동화하고 임베드하는 것**, 그리고 **거버넌스의 중앙 책임을 개별
    도메인 데이터 프로덕트 소유자에게 위임하는 것.**
  - 자율의 부작용도 함께 적는다 — **상상할 수 있듯 도메인의 자율은 견제되지 않으면 바람직하지
    않은 결과를 낳을 수 있다: 도메인의 고립, 한 도메인의 데이터 프로덕트가 다른 것들과
    비호환·단절되는 것, 그리고 여러 도메인의 데이터를 소비할 때의 파편화된 경험이다. 데이터 메시
    거버넌스는 도메인의 데이터 프로덕트를 사용하는 일관되고 연결되고 신뢰할 만한 경험을 위해
    거버넌스 관심사의 자동화에 크게 의존한다** (7장, p.114).[^dehghani2022]
- **자율을 가능케 한다** — **팀 자율과 팀 성과의 상관은 팀 관리 연구의 주제였다. 경험적 연구는
  자기 사명을 완수하기 위한 의사결정에서의 팀의 자유가 더 나은 팀 성과로 이어질 수 있음을
  보인다. 다른 한편 너무 많은 자율은 비일관성·중복 노력·팀 고립으로 이어질 수 있다** (7장,
  p.115).[^dehghani2022] #hypothesis — 저자는 "경험적 연구"라 하지만 구체 출처를 각주로 달지
  않는다.
  - 균형의 방법 — **데이터 메시는 팀 자율과 팀 간 상호운용성·협업 사이의 균형을 잡으려 시도한다.
    도메인 팀에 자기 데이터 프로덕트를 위한 최선의 데이터 모델을 고르는 것 같은 국소적 의사결정의
    통제권을 주는 자율을 부여하는 한편, 모든 도메인이 활용하는 데이터 모델링 언어의 표준화 같은
    일관된 경험을 부과하기 위해 계산적 거버넌스 정책을 사용한다** (7장, p.115).[^dehghani2022]

### 결과 셋 — 투자 대비 데이터 가치의 비율을 높인다

- 근거는 6장의 실측이다 — **NewVantage Partners 리포트 같은 산업 리포트와 나 자신의 개인적
  경험은 데이터 관리에 대한 우리 투자에 비해 데이터에서 얻는 가치가 적다는 사실을 가리킨다.
  앱 개발 인프라 같은 다른 기술 투자와 비교해 우리 데이터 팀과 데이터 해법에서 얻는 가치를
  비교하면, 데이터에 관해 우리가 역풍을 맞고 있음이 분명하다** (7장, p.115).[^dehghani2022]
  그 수치는 [분석 데이터 관리의 변곡점](../concepts/data-mesh-inflection-point.md)에 있다.
- **데이터 플랫폼으로 기술적 복잡성을 추상한다** — **기술적 복잡성의 리트머스 시험은 데이터
  엔지니어와 데이터 전문가에 대한 갈수록 커지는 수요다. 우리는 결코 그들을 충분히 갖지 못하는
  것 같다. 또 하나의 리트머스 시험은 데이터 파이프라인 프로젝트의 낮은 가치 대 노력 비율이다.
  많은 노력이 들어가지만 되돌아오는 가치는 적다 — 곧 품질 데이터셋에 대한 마찰 없는 접근을 얻는
  일 말이다** (7장, p.116).[^dehghani2022]
  - 처방 — **데이터 메시는 기존 기술 지형을 비판적으로 바라보고 기술 해법을 데이터 프로덕트
    개발자(또는 사용자) 중심 플랫폼으로 재상상한다. 데이터 전문가의 필요를 없애고 제너럴리스트
    전문가가 데이터 프로덕트를 개발할 수 있게 하는 것을 의도한다** (7장, p.116).[^dehghani2022]
  - 인터페이스 표준화의 목적 — **데이터 메시는 모든 데이터 프로덕트가 공유하는 서로 다른
    어포던스 — 발견·접근 요청·질의·데이터 서빙·데이터 보안 등 — 를 위한 열린 표준 인터페이스
    집합을 정의한다. 이는 더 협업적인 기술 생태계를 가능케 하기 위한 것이다. **벤더 간 통합
    비용을 줄이려는 것이다**** (7장, p.116).[^dehghani2022]
- **제품 사고를 어디에나 심는다** — **데이터 메시는 데이터 사용자가 지각하는 대로의 가치에
  레이저처럼 초점을 맞추게 하는 몇 가지 이동을 도입한다. 자산(asset)으로서의 데이터에서
  제품(product)으로서의 데이터로 사고를 옮긴다. 성공을 측정하는 방식을 **데이터 볼륨에서 데이터
  사용자의 행복으로** 옮긴다** (7장, p.116).[^dehghani2022]
  - 제품 취급 대상은 데이터만이 아니다 — **데이터는 제품으로 취급되는 데이터 메시 생태계의
    유일한 구성 요소가 아니다. 셀프서브 데이터 플랫폼 자체도 제품이다. 이 경우 그것은 데이터
    프로덕트 개발자와 데이터 프로덕트 사용자를 서빙한다. 데이터 메시는 플랫폼의 성공 척도를
    능력의 **수**에서, 데이터 프로덕트 개발 경험을 개선하고 데이터 프로덕트를 전달하거나 발견해
    사용하기까지의 리드 타임을 줄이는 데 대한 능력의 **영향**으로 옮긴다** (7장,
    p.116).[^dehghani2022]
- **경계를 넘어간다** — **업무 기능의 개선은 거의 항상 그 단위의 경계를 넘어서는 통찰을
  요구한다. (…) 다중 도메인·다중 조직 데이터 접근은 데이터 메시에 내장된 가정이다. 데이터 메시의
  데이터 퀀텀 개념은 데이터가 물리적으로 어디에 있든 데이터에 대한 접근을 제공할 수 있다. (…)
  식별 스키마·접근 통제·기타 정책 시행은 인터넷 위에서 활성화되는 열린 프로토콜을 사용한다고
  가정한다** (7장, p.117).[^dehghani2022]

### 결과·실행 축·원칙의 대응표

표 7-1이 이 장 전체를 한 장으로 접는다 (7장, pp.117–118):[^dehghani2022]

| 결과 | 실행 축 | 어느 원칙이 받는가 |
|---|---|---|
| 복잡·변동·불확실한 업무 환경에서 데이터 변경을 우아하게 관리 | 업무·기술·데이터를 정렬 | 도메인 데이터 소유권 |
| 〃 | 운영·분석 데이터 플레인의 간극을 좁힘 (조직 전반 파이프라인과 두 플레인 아키텍처 제거, 멍청한 파이프로 더 긴밀히 통합) | 제품으로서의 데이터 |
| 〃 | 데이터 변경을 업무 도메인으로 국소화 (도메인 지향 데이터 프로덕트 사이의 명확한 계약) | 제품으로서의 데이터 |
| 〃 | 파이프라인과 데이터 복사의 우발적 복잡성 축소 (파이프라인 해체 후 내부 구현으로 추상) | 제품으로서의 데이터 · 데이터 프로덕트 퀀텀 |
| 성장 앞에서 기민함 유지 | 중앙집중 아키텍처 병목 제거 (중앙 웨어하우스·레이크 제거, 데이터 인터페이스로 P2P 공유) | 도메인 소유권 · 제품으로서의 데이터 |
| 〃 | 데이터 파이프라인 조정 축소 (최상위 기능적 분해 → 도메인 지향 분해, 명시적 데이터 계약 도입) | 도메인 소유권 · 제품으로서의 데이터 |
| 〃 | 데이터 거버넌스 조정 축소 (자율 도메인에 책임 위임, 정책을 코드로 자동 검증) | 연합 컴퓨테이셔널 거버넌스 |
| 〃 | 팀 자율 활성화 (계산적 표준으로 자율과 전역 일관성의 균형, 도메인 무관 인프라를 셀프서브로) | 연합 컴퓨테이셔널 거버넌스 · 셀프서브 데이터 플랫폼 |
| 비용 대비 데이터 가치 증대 | 데이터 플랫폼으로 복잡성 추상 (데이터 개발자·사용자 중심 인프라, 열린 표준 인터페이스로 벤더 통합 비용 축소) | 제품으로서의 데이터 · 셀프서브 데이터 플랫폼 |
| 〃 | 제품 사고를 어디에나 (데이터 사용자·개발자 행복으로 성공 측정, 데이터와 플랫폼 둘 다 제품으로) | 셀프서브 데이터 플랫폼 · 제품으로서의 데이터 |
| 〃 | 조직의 경계를 넘어감 (표준·인터넷 기반 데이터 공유 계약으로 물리·논리 경계를 가로질러 공유) | 제품으로서의 데이터 · 셀프서브 데이터 플랫폼 |

- **저자 자신이 만능 해법 주장을 기각한다** — **이 장을 읽고 나면 데이터 메시가 은탄환(silver
  bullet)이라고 가정할지 모른다. 정반대다. 데이터 메시는 해법의 중요한 한 조각이다. 그것은
  우리가 데이터 접근을 진정으로 민주화할 수 있게 한다. 그러나 데이터에서 가치를 끌어내는 루프를
  닫으려면 데이터 공유를 넘어 해야 할 일이 훨씬 많다. 우리는 반복 가능하고 프로덕션 품질인
  분석·ML 기반 해법을 지속적으로 전달해야 한다. 다만 부트스트랩하려면 규모에서의 데이터 공유가
  필요하고, 그것이 데이터 메시가 초점을 두는 것이다** (7장, p.117).[^dehghani2022]

## 어떤 데이터를 말하는가

- 데이터 메시는 분석 데이터에 초점을 두되 둘의 경계를 무시하지 않는다 — **두 데이터 양식의
  흐릿한 구획을 인정하고, 둘을 긴밀히 통합하는 새 모델을 도입하면서도, 둘 사이의 명확한 차이를
  존중한다** (1장, p.11).[^dehghani2022]
- **운영 데이터**(operational data) — **사업을 돌리는 것을 지원하고 트랜잭션 무결성과 함께
  사업의 현재 상태를 유지한다. 이 데이터는 OLTP(online transaction processing) 시스템에 의해
  실시간으로 트랜잭션으로 포착·저장·처리된다** (1장, p.11).[^dehghani2022]
  - 저자가 쓰는 별칭은 **"안쪽의 데이터"(data on the inside)** — **CRUD 연산을 수행하는
    애플리케이션이나 마이크로서비스의 사적 데이터다. 운영 데이터는 REST·GraphQL·이벤트 같은
    API를 통해 의도적으로 바깥에 공유될 수 있다. 바깥의 운영 데이터도 안쪽의 운영 데이터와
    성질이 같다 — 지금 사업에 대해 우리가 아는 것이다** (1장, p.11).[^dehghani2022]
- **분석 데이터**(analytical data) — **사업을 돌린 부산물로 만들어진 역사적·통합적·집계적
  데이터 관점이다. OLAP(online analytical processing) 시스템이 유지하고 사용한다** (1장,
  p.12).[^dehghani2022] 이쪽은 **"바깥의 데이터"(data on the outside)** 범주로, 분석 소비자가
  직접 접근하는 데이터다 (1장, p.12).[^dehghani2022]
- 이 구분에서 저자는 **웨어하우스 진영의 정의를 기각하지 않는다** — **비휘발적·통합적·시변적
  데이터 집합이라는 분석 데이터의 원래 정의는 여전히 유효하다** (1장, p.12, 각주 3은 그 정의를
  "데이터 웨어하우징의 아버지"로 알려진 William H. Inmon의 것으로 밝힌다).[^dehghani2022]
  같은 구분을 웨어하우스 어휘로 서술한 자리는
  [EDW](../concepts/enterprise-data-warehouse.md)에 있다.
- 접근 패턴의 차이도 명시된다 — **분석 접근 양식은 큰 몸집의 데이터를 가로지르는 집중적 읽기
  위주이고 쓰는 쪽은 더 적다** (1장, p.12).[^dehghani2022] 그리고 오늘의 현실을 한 줄로
  적는다 — **오늘날 분석 데이터는 데이터 웨어하우스나 레이크에 저장된다** (1장,
  p.12).[^dehghani2022]

## 기원 — 새 패러다임이라는 자기 규정

- 저자는 토머스 쿤의 『과학혁명의 구조』를 끌어와 자기 위치를 정한다 — **쿤은 패러다임 전환의
  선결 조건이 변칙(anomalies), 즉 기존 규범에 맞지 않는 관측을 식별하는 것과, 새 문제를 푸는 데
  기존 패러다임이 타당한지 의심하는 위기(crisis) 국면에 들어서는 것임을 인식했다. 그는 또한
  사람들이 변칙을 설명하려고 기존 해법에 지탱 불가능한 복잡성을 점점 더 절박하게 밀어 넣는
  것을 관찰했다** (1장, p.13).[^dehghani2022]
  - 그 틀에 자기 분야를 대입한다 — **우리는 데이터를 다루는 접근의 진행에서 쿤적 위기의
    순간에 있다. 따라서 새 패러다임이 필요하다** (1장, p.13).[^dehghani2022]
- 그러면서 원칙의 독창성은 스스로 부인한다 — **데이터 메시의 원칙들은 새롭거나 참신하지 않고,
  지난 20년에 걸쳐 진화하며 우리의 지난 복잡성 난제 — 조직의 대량 디지털화가 이끈 소프트웨어
  복잡성의 규모 — 를 푼 것으로 입증된 실천의 일반화이자 적응이다** (1장, p.13).[^dehghani2022]
  - 그 출처를 넷으로 지목한다 — **소프트웨어에서의 이전 패러다임 전환, 즉 마이크로서비스와
    API 혁명, 플랫폼 기반 Team Topologies, 제로 트러스트 아키텍처(Zero Trust Architecture)
    같은 계산 가능한 거버넌스 모델, 그리고 여러 클라우드와 호스팅 환경에 걸쳐 분산 해법을
    안전하게 운영하는 것의 적응이다** (1장, pp.13–14).[^dehghani2022] 그 원본 계열은
    [마이크로서비스와 서버리스](../concepts/microservices-and-serverless.md)에 있다.
- 책의 서술 지위도 저자가 스스로 좁혀 둔다 — **이 책은 데이터 메시가 혁신 채택 곡선의
  혁신가·얼리어답터 단계에 있다고 말할 수 있는 시점에 쓰이고 있다. 따라서 지금 시점에서
  데이터 메시를 설명할 때 원칙과 아키텍처 양식을 분명히 하고, 구체적 구현 세부와 기술은 시간을
  두고 다듬어 만들어지도록 남기는 것이 적절하다. 어떤 구체적 구현 설계나 도구 제안이든 당신이
  이 책을 읽을 즈음에는 그냥 낡아 있을 것으로 예상한다** (1부 도입, pp.1–2).[^dehghani2022]
  - 성숙 사례가 없다는 것도 명시한다 — **성숙한 데이터 메시를 갖춘 회사의 사례를 서술하기에는
    데이터 메시의 생애에서 너무 이르다. 우리는 지금 첫 데이터 메시들을 짓는 과정에 있기
    때문이다. 그래서 나는 몇 해 뒤에 보게 되리라 예상하는 특성을 보이는 가상 조직을 서술한다**
    (프롤로그, p.xxvi).[^dehghani2022] 프롤로그의 Daff 서사 전체가 이 지위 위에 서 있다 —
    #hypothesis 로 읽어야 하는 미래 서술이다.
- 성과 측정 축도 가상 사례 안에서만 제시된다 — 데이터 접근 리드 타임 감소, 표준 계약으로 인한
  변경 위험 감소, 데이터 프로덕트 간 연결량으로 잰 데이터 활용도, 데이터 주도 해법을 만드는
  팀 수, 데이터 소유 총비용 (프롤로그, p.xxxvi).[^dehghani2022] #hypothesis — 실측이 아니라
  저자가 기대하는 측정 항목이다.

## 2021년의 도메인 주도 설계 실무서가 읽는 같은 아키텍처

**다른 소스 하나가 이 아키텍처를 도메인 주도 설계 쪽에서 읽는다.** 위
[기원 — 새 패러다임이라는 자기 규정](#기원--새-패러다임이라는-자기-규정)이 이 제안의 계보를
스스로 적는 자리라면, 이 절은 **그 계보의 반대편 끝에 선 소스가 같은 것을 무엇이라 부르는가**를
받는다.

- 그쪽의 한 줄 규정 (16장 §"Data Mesh", p.259):[^khononov2021]

> The data mesh architecture is, in a sense, domain-driven design for analytical data.

  - 근거로 그쪽이 드는 것은 **경계를 긋고 그 안을 지킨다는 같은 동작**이다 — 도메인 주도 설계의
    여러 패턴이 경계를 긋고 그 내용을 보호하듯, 이 아키텍처는 **분석 데이터의 모델 경계와
    소유권 경계를 정의하고 보호한다** (16장, p.259).[^khononov2021]
- **원칙 넷의 이름이 양쪽에서 다르다.** 뜻이 갈리는 것이 아니라 강조점이 다르다.

| 위 [네 원칙](#네-원칙)의 이름 | 2021년 실무서가 부르는 이름 |
|---|---|
| 도메인 소유권 | 도메인을 축으로 데이터를 분해한다(decompose data around domains) |
| 제품으로서의 데이터 | 제품으로서의 데이터(data as a product) |
| 셀프서브 데이터 플랫폼 | 자율을 가능하게 한다(enable autonomy) |
| 연합 컴퓨테이셔널 거버넌스 | 생태계를 만든다(build an ecosystem) |

  - 그쪽 이름 넷은 16장 §"Data Mesh" 도입이 나열하는 그대로다 (16장, p.259).[^khononov2021]
    셋째와 넷째의 이름이 특히 다른데, 그쪽은 **플랫폼과 거버넌스 기구를 각각의 목적(자율·생태계)
    으로 부르고** 이 페이지의 원전은 **그 목적을 이루는 수단**으로 부른다.
- **그쪽이 더하는 것은 방법론 쪽 패턴과의 대응이다** (16장 §"Combining Data Mesh and
  Domain-Driven Design", pp.263–264):[^khononov2021]
  - **유비쿼터스 언어와 거기서 나오는 도메인 지식이 분석 모델 설계에 필수적**이라는 것. 그쪽은
    전통적 아키텍처에 빠져 있던 것이 바로 그 도메인 지식이라고 진단한다.
  - **경계 컨텍스트의 데이터를 운영 모델과 다른 모델로 드러내는 것이 열린 호스트 패턴**이고,
    이때 **분석 모델은 또 하나의 공표된 언어**라는 것. 위
    [네 원칙](#네-원칙)의 둘째가 요구하는 출력 포트를 방법론의 이름으로 다시 부른 것이다.
  - **CQRS 패턴이 운영 모델을 분석 모델로 변환하는 데 쓰인다**는 것, 그리고 그 패턴이 모델을
    처음부터 다시 만들 수 있어 **분석 모델의 여러 버전을 동시에 생성해 서빙하기 쉽다**는 것.
    그 패턴은 [CQRS 아키텍처](../concepts/cqrs-architecture.md)에 있다.
  - **경계 컨텍스트 통합 패턴이 분석 모델에도 그대로 적용된다**는 것 — 두 제품 팀이 파트너십으로
    분석 모델을 함께 진화시킬 수도, 한쪽이 부패 방지 계층을 세워 비효율적인 분석 모델로부터
    자신을 보호할 수도, 각자의 길로 가 중복 구현을 낼 수도 있다. 그 관계들은
    [컨텍스트 관계 패턴](../concepts/context-relationship-patterns.md)에 있다.
- **이 읽기가 위 절들의 서술과 겨루는가.** 겨루지 않는다 — 대질하면 **같은 계보를 양쪽이 다
  인정한다.**
  - 이 페이지의 원전도 도메인 지향 분해의 출처로 그 방법론을 직접 지목한다. 위
    [기원](#기원--새-패러다임이라는-자기-규정) 절과
    [도메인 소유권 원칙](../concepts/domain-ownership-principle.md)이 그 자리다.
  - **그쪽이 더하는 것은 방법론 쪽 패턴 이름으로 된 구현 어휘**다 — 열린 호스트 서비스, 공표된
    언어, CQRS, 통합 패턴 넷. 원전이 출력 포트와 계약이라는 일반적 낱말로 적는 자리에 그쪽은
    이미 정의된 패턴 이름을 붙인다.
  - #hypothesis **한 자리는 양쪽이 다르게 읽힐 여지가 있다.** 이 페이지의 원전은 도메인을
    분해의 단위로 삼으면서 분석 데이터의 원형을 셋(원천 정렬·집계·소비자 정렬)으로 나누는데,
    그쪽은 분해 단위를 **경계 컨텍스트**로 못 박고 그 셋에 대응하는 구분을 두지 않는다. 겨루는
    주장은 아니지만 세분성의 물음이 남는다. 어느 소스도 상대를 대질한 적이 없어 가설로 적는다.

## 저자 자신이 아키텍처 책에 먼저 쓴 정의

**이 페이지의 저자가 2021년에 공저자로 참여한 아키텍처 책의 14장에 같은 제안의 정의와 네 원칙이
한 해 먼저 인쇄되어 있다.** 제3자의 소개가 아니라 **같은 사람이 아키텍트 독자를 향해 쓴 판**이고,
그 장 스스로 **전문은 자하마크 데흐가니의 *Data Mesh*가 온전히 다룬다**며 이 페이지의 소스로
넘긴다 (14장, p.390).[^ford2021-hard-parts]

- **정의** (14장, p.389):[^ford2021-hard-parts]

  > Data mesh is a sociotechnical approach to sharing, accessing, and managing analytical
  > data in a decentralized fashion. It satisfies a wide range of analytical use cases, such
  > as reporting, ML model training, and generating insights. Contrary to the previous
  > architecture, it does so by aligning the architecture and ownership of the data with the
  > business domains and enabling a peer-to-peer consumption of data.

  - **위 [정의](#정의)의 2022년 판과 견주면 달라지는 것 셋이다.** 어느 쪽도 사실 주장을 바꾸지
    않는다.

| 항목 | 2021년 14장 p.389 | 2022년 1장 p.3 |
|---|---|---|
| 탈중앙이 놓이는 자리 | **문장 끝의 부사구** — `in a decentralized fashion` | **낱말 앞의 수식어** — `decentralized sociotechnical approach` |
| 범위 한정 | **없다** | `in complex and large-scale environments—within or across organizations` |
| 무엇을 만족시키는가 | **분석 사용 사례를 열거한다** — 보고·기계 학습 모델 훈련·통찰 생성 | 열거하지 않는다 |
| 어떻게 하는가 | **데이터의 아키텍처와 소유권을 업무 도메인에 맞추고 데이터의 P2P 소비를 가능하게 해서** | 정의 문장에 없다(뒤의 원칙들이 맡는다) |

  - **2021년 판이 더 가진 것은 목적과 기제**이고, **2022년 판이 더 가진 것은 적용 범위의
    한정**이다. `sociotechnical`이라는 낱말은 두 판 모두에 있다.
- **네 원칙의 이름 하나가 뒤집혀 있다** (14장, pp.389–390):[^ford2021-hard-parts]

| 2021년 14장의 이름 | 이 페이지(2022년)의 이름 |
|---|---|
| `Domain ownership of data` | `Domain Ownership` |
| `Data as a product` | `Data as a Product` |
| `Self-serve data platform` | `Self-Serve Data Platform` |
| **`Computational federated governance`** | **`Federated Computational Governance`** |

  - **넷째만 낱말 순서가 반대다.** 이 KB의 페이지 슬러그는 2022년 판을 따른다
    ([연합 컴퓨테이셔널 거버넌스 원칙](../concepts/federated-computational-governance-principle.md)).
    **두 이름이 같은 원칙을 가리킨다는 것은 내용으로 확인했고**(연합 의사 결정 모델 + 정책을
    코드로 각 데이터 프로덕트에 심기), 저자가 그 갈림을 적지 않는다. #hypothesis
- **네 원칙의 요지도 이 페이지의 것과 어긋나지 않는다.** 도메인 소유권은 **데이터를 가장 잘 아는
  도메인(데이터를 만들어 내거나 일급 소비자인 도메인)이 소유하고 공유하며, 중간자도 중앙 레이크나
  웨어하우스도 전담 데이터 팀도 없이** P2P로 오간다는 것이고, 제품으로서의 데이터는 **사일로화를
  막으려 조직 역할과 성공 지표를 갖추는 것**이며, 셀프서브 플랫폼은 **선언적 데이터 프로덕트
  생성·검색과 브라우징을 통한 발견·계보와 지식 그래프 관리** 같은 능력을, 거버넌스는 **연합
  의사 결정 모델과 정책의 코드화**를 든다 (14장, pp.389–390).[^ford2021-hard-parts]
- **아키텍처 쪽이 가져가는 것 하나를 그 장이 명시한다** — 둘째 원칙이 **데이터 프로덕트
  퀀텀(data product quantum)이라는 새 아키텍처 퀀텀**을 도입하고, **그 장은 그 퀀텀의 아키텍처
  측면에만 집중한다**고 적는다 (14장, p.390).[^ford2021-hard-parts] 그 단위의 전문은
  [데이터 퀀텀](../concepts/data-quantum.md)이 갖고, 2021년 14장이 더하는 판정(정적·동적 결합의
  분류와 "언제 쓰는가")도 그쪽에 있다.
- **계보를 그 장이 다르게 적는다** — 데이터 메시의 핵심 발상을 **자하마크 데흐가니와 여러
  혁신가들이 마이크로서비스의 도메인 지향 결합 끊김과 서비스 메시와 사이드카에서 끌어내어
  분석 데이터에 수정을 가해 적용한 것**으로 서술하고, 운영 데이터와 분석 데이터의 분리를
  **사이드카 패턴이 다루는 직교 결합의 훌륭한 예**로 놓는다 (14장,
  p.389).[^ford2021-hard-parts]
  - **이 페이지의 위 [기원 — 새 패러다임이라는 자기 규정](#기원--새-패러다임이라는-자기-규정)과
    축이 다르다.** 그쪽은 쿤의 패러다임 전환으로 자기 위치를 잡고, 이쪽은 **마이크로서비스
    계열의 기법 셋에서 파생되었다**고 적는다. **어긋나지 않는다** — 하나는 인식의 지위를,
    다른 하나는 기술의 출처를 말한다. 두 소스가 이 대응을 적지 않으므로 이 읽기는 이 KB의
    것이다. #hypothesis

## 제3자가 보는 데이터 메시

- 데이터 엔지니어링 개론이 아키텍처 유형 목록에서 데이터 메시에 할당한 분량 — **데이터
  메시(data mesh)는 중앙집중 데이터 레이크와 데이터 웨어하우스 같은 뻗어 나가는 모놀리식 데이터
  플랫폼, 그리고 지형이 운영 데이터와 분석 데이터로 갈리는 "데이터의 큰 분열(the great divide
  of data)"에 대한 최근의 응답이다. 데이터 메시는 중앙집중 데이터 아키텍처의 난제를 뒤집으려
  시도하며, 도메인 주도 설계(소프트웨어 아키텍처에서 흔히 쓰이는)의 개념을 가져와 데이터
  아키텍처에 적용한다** (3장, p.109).[^reis2022]
- 그 개론이 인용한 Dehghani의 원문 (3장, p.109):[^reis2022]

> In order to decentralize the monolithic data platform, we need to reverse how we think
> about data, its locality, and ownership. Instead of flowing the data from domains into
> a centrally owned data lake or platform, domains need to host and serve their domain
> datasets in an easily consumable way.

- 저자들이 요약한 대비 — **중앙집중화에서는 한 팀이 모든 도메인에서 데이터를 모으고 조직 전반의
  소비를 위해 그것을 조정하는 책임을 진다(전통적 데이터 웨어하우징의 흔한 접근이다). 데이터
  메시에서는 각 소프트웨어 팀이 조직의 나머지에서 소비될 수 있도록 자기 데이터를 준비하는 책임을
  진다** (3장, p.94).[^reis2022]
- **명칭 판본이 다르다.** 그 개론이 옮긴 네 구성 요소는 "domain-oriented decentralized data
  ownership and architecture"·"data as a product"·"self-serve data infrastructure as a
  platform"·"federated computational governance"이고 (3장, p.109),[^reis2022] 2022년 책의
  원칙 명칭은 위 표대로다. 셋째 원칙이 "self-serve data infrastructure as a platform"에서
  "the Self-Serve Data Platform"으로 바뀌었다 — 같은 원칙의 이른 판본(2019년 블로그 글) 이름을
  인용한 것이므로 모순이 아니라 시점 차이다.

## 같은 낱말을 운영계 이벤트 스트림에 쓰는 소스

- **"데이터 계약"이라는 낱말이 이 KB에서 두 대상에 쓰인다.** 이쪽에서 계약을 지는 것은 **분석용
  데이터 제품**이고, [bellemare2025](../sources/bellemare2025.md) 4장에서 계약을 지는 것은
  **운영계 이벤트 스트림**이다 — 그 소스의 규정은 **데이터 생산자와 그 데이터를 소비하는
  과거·현재·미래의 모든 서비스 사이의 약정**이다 (4장 §"What Is a Data Contract?",
  p.86).[^bellemare2025]
- **그 소스가 겹침을 스스로 인정한다** — 데이터 계약은 **데이터 메시·데이터 레이크·데이터
  웨어하우스를 비롯한 여러 아키텍처와 사고 체계에 등장**했고 **개념적으로는 대체로 같으며 "이
  특정 데이터에 관한 보장이 무엇인가"라는 핵심 물음에 답한다**는 것이다 (4장,
  p.86).[^bellemare2025]
  - 곧 **모순이 아니라 같은 물음의 두 적용 대상이다.** 갈리는 것은 계약이 걸리는 물건이고
    (분석용 데이터 제품인가 운영계 이벤트 스트림인가), **구성 요소 목록은 크게 겹친다** — 소유권,
    서비스 수준 목표, 접근 제한, 스키마와 그 진화 규칙이 양쪽에 다 있다. 이 대조는 이 KB가 세운
    것이다.
