# 데이터베이스를 거치는 데이터플로

하나의 질문: **데이터베이스를 사이에 두고 인코딩과 디코딩이 갈릴 때 무엇이 보장돼야 하는가.**

## 미래의 나에게 보내는 메시지

- 역할 배분부터 — **데이터베이스에서는 쓰기를 하는 프로세스가 데이터를 인코딩하고 읽기를 하는
  프로세스가 그것을 디코딩한다** (5장, p.178).[^kleppmann2026]
- 프로세스가 하나뿐일 때 — **하나의 프로세스만 데이터베이스에 접근할 수도 있는데, 그 경우 독자는 그저
  같은 프로세스의 나중 버전이다. 그런 시나리오에서는 데이터베이스에 무언가를 저장하는 것을 미래의
  나에게 메시지를 보내는 것으로 생각할 수 있다** (5장, p.178).[^kleppmann2026]
- 그러면 한 방향이 필수다 — **여기서 후진 호환은 명백히 필요한데, 그러지 않으면 미래의 내가 과거에
  내가 쓴 것을 디코딩할 수 없기 때문이다** (5장, p.178).[^kleppmann2026]

## 프로세스가 여럿이면 전진 호환도 필요하다

- 실제 상황 — **일반적으로 여러 프로세스가 동시에 데이터베이스에 접근하는 것이 흔하다. 그
  프로세스들은 서로 다른 애플리케이션이나 서비스일 수도 있고, 단순히 같은 서비스의 여러
  인스턴스(확장성이나 내결함성을 위해 병렬로 도는)일 수도 있다** (5장,
  p.178).[^kleppmann2026]
- 그래서 코드 버전이 섞인다 — **어느 쪽이든 그런 환경에서는 데이터베이스에 접근하는 어떤 프로세스는
  더 새로운 코드를 돌리고 어떤 프로세스는 더 오래된 코드를 돌리고 있을 가능성이 높다 — 예컨대 새
  버전이 현재 롤링 업그레이드로 배포되는 중이라 어떤 인스턴스는 갱신됐고 다른 것은 아직 아니기
  때문이다** (5장, pp.178–179).[^kleppmann2026]
- 결론 — **이는 데이터베이스의 값이 더 새로운 버전의 코드로 쓰인 뒤 여전히 돌고 있는 더 오래된
  버전의 코드로 읽힐 수 있다는 뜻이다. 따라서 데이터베이스에도 전진 호환이 흔히 요구된다** (5장,
  p.179).[^kleppmann2026]

## 데이터가 코드보다 오래 산다

- 데이터베이스의 시간 폭 — **데이터베이스는 일반적으로 어떤 값이든 언제든 갱신될 수 있게 한다. 단일
  데이터베이스 안에 5밀리초 전에 쓰인 값과 5년 전에 쓰인 값이 함께 있을 수 있다** (5장,
  p.179).[^kleppmann2026]
- 코드와의 대비 — **애플리케이션의 새 버전을 배포할 때(적어도 서버 쪽 애플리케이션은) 몇 분 안에 옛
  버전을 새 버전으로 완전히 대체할 수 있다. 데이터베이스 내용에는 같은 것이 참이 아니다. 5년 된
  데이터는 그 뒤로 명시적으로 다시 쓰지 않았다면 원래 인코딩으로 여전히 거기 있을 것이다. 이 관찰은
  때때로 데이터가 코드보다 오래 산다(data outlives code)로 요약된다** (5장,
  p.179).[^kleppmann2026]
- 그래서 마이그레이션을 미룬다 — **데이터를 새 스키마로 다시 쓰는(마이그레이션하는) 것이 분명 가능은
  하지만 큰 데이터셋에서는 비싸다. 그러므로 대부분의 데이터베이스는 그 연산을 미루고 비동기로
  최선 노력 기반으로 수행한다** (5장, p.179).[^kleppmann2026]
- 두 가지 실제 경로 (5장, p.179):[^kleppmann2026]
  - **LSM 트리 저장 엔진은 컴팩션 중에 최신 형식으로 데이터를 다시 쓴다.**
  - **대부분의 관계형 데이터베이스는 null 기본값을 가진 새 열을 더하는 것 같은 단순한 스키마 변경을
    기존 데이터를 다시 쓰지 않고도 허용한다. 옛 행을 읽을 때 데이터베이스는 디스크의 인코딩된 데이터에
    빠져 있는 열에 null을 채워 넣는다.**
- 그 결과가 스키마 진화의 값어치다 — **스키마 진화는 밑에 깔린 저장소가 스키마의 여러 역사적 버전으로
  인코딩된 레코드를 담고 있더라도 데이터베이스 전체가 하나의 스키마로 인코딩된 것처럼 보이게 해
  준다** (5장, p.179).[^kleppmann2026]
- 다만 한계가 있다 — **더 복잡한 스키마 변경(예: 단일 값 속성을 다중 값으로 바꾸거나 어떤 데이터를
  별도 테이블로 옮기는 것)은 여전히 데이터를 다시 써야 하며 흔히 애플리케이션 수준에서 그렇게 한다.
  그런 마이그레이션에 걸쳐 전진·후진 호환성을 유지하는 일은 여전히 연구 문제다** (5장,
  p.179).[^kleppmann2026]

## 아카이브 저장

- 언제 생기는가 — **때때로 데이터베이스의 스냅샷을 뜬다고 하자 — 예컨대 백업 목적이나 데이터
  웨어하우스에 적재하기 위해서다. 이 경우 데이터 덤프는 원천 데이터베이스의 원래 인코딩이 서로 다른
  시대의 스키마 버전 혼합을 담고 있더라도 보통 최신 스키마로 인코딩된다. 어차피 데이터를 복사하고
  있으므로 데이터 사본을 일관되게 인코딩하는 편이 낫다** (5장, p.179).[^kleppmann2026]
- 그래서 형식 선택이 정해진다 — **데이터 덤프는 한 번에 쓰이고 그 뒤 불변이므로 Avro 오브젝트
  컨테이너 파일 같은 형식이 잘 맞는다. 이는 또한 데이터를 Parquet 같은 분석 친화적 열 지향 형식으로
  인코딩할 좋은 기회이기도 하다** (5장, p.180).[^kleppmann2026]
