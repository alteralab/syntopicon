하나의 질문: **데이터베이스 트랜잭션으로 묶을 수 없는 여러 서비스 호출을 어떻게 정확히 한 번
수행되게 만드는가.**

## 워크플로와 태스크

- 문제가 생기는 자리 — **정의상 서비스 기반 아키텍처는 애플리케이션의 서로 다른 부분을 각각 책임지는
  여러 서비스를 갖는다.** 저자가 든 예는 신용카드에 청구하고 그 자금을 은행 계좌에 입금하는 결제 처리
  애플리케이션이며, **이 시스템은 사기 탐지·신용카드 통합·은행 통합 등을 책임지는 서로 다른 서비스를
  가질 가능성이 높다** (5장, p.187).[^kleppmann2026]
- 이름이 붙는다 — **결제 하나를 처리하려면 여러 서비스 호출이 필요하다. 결제 처리기 서비스가 사기
  탐지 서비스를 불러 사기를 확인하고, 신용카드 서비스를 불러 카드에서 인출하고, 은행 서비스를 불러
  인출된 자금을 입금할 수 있다. 이 일련의 단계를 워크플로(workflow)라 하고 각 단계를
  태스크(task)라 한다** (5장, p.187).[^kleppmann2026]
- 정의 방식 — **워크플로는 보통 태스크의 그래프로 정의된다. 워크플로 정의는 범용 프로그래밍 언어,
  도메인 특화 언어(DSL), 또는 Business Process Execution Language(BPEL) 같은 마크업 언어로 쓰일 수
  있다** (5장, p.187).[^kleppmann2026]
- 이름이 엔진마다 다르다는 주 — **서로 다른 워크플로 엔진이 태스크에 서로 다른 이름을 쓴다. 예컨대
  Temporal은 액티비티(activity)라는 용어를 쓴다. 어떤 것들은 태스크를 내구 함수(durable functions)라
  부른다. 이름은 다르지만 개념은 같다** (5장, p.187).[^kleppmann2026]

## 워크플로 엔진

- 무엇을 정하는가 — **워크플로는 워크플로 엔진(workflow engine)에 의해 실행된다. 워크플로 엔진은
  각 태스크를 언제 어느 기계에서 돌릴지, 태스크가 실패하면(예: 태스크가 도는 중에 기계가 크래시하면)
  무엇을 할지, 얼마나 많은 태스크가 병렬로 실행되도록 허용할지 등을 정한다** (5장,
  p.187).[^kleppmann2026]
- 두 부분으로 나뉜다 — **워크플로 엔진은 보통 오케스트레이터(orchestrator)와 실행기(executor)로
  구성된다: 오케스트레이터는 실행될 태스크를 스케줄링하는 것을 책임지고, 실행기는 태스크를 실행하는
  것을 책임진다** (5장, p.187).[^kleppmann2026]
- 무엇이 실행을 시작시키는가 — **실행은 워크플로가 촉발될 때 시작된다. 사용자가 시간 기반 스케줄(예:
  시간별 실행)을 정의하면 오케스트레이터가 워크플로 자체를 촉발한다. 웹 서비스나 심지어 사람 같은
  외부 원천도 워크플로 실행을 촉발할 수 있다. 촉발되면 실행기가 호출되어 태스크를 돌린다** (5장,
  pp.187–188).[^kleppmann2026]
- 종류가 셋으로 나뉜다 — **다양한 유스케이스를 다루는 여러 종류의 워크플로 엔진이 있다.
  Airflow·Dagster·Prefect 같은 어떤 것들은 데이터 시스템과 통합해 ETL 태스크를 오케스트레이션한다.
  Camunda·Orkes 같은 다른 것들은 비엔지니어가 워크플로를 더 쉽게 정의·실행할 수 있도록 워크플로에
  대한 그래픽 표기(그림에 쓰인 BPMN 같은)를 제공한다. Temporal·Restate 같은 또 다른 것들은 내구
  실행(durable execution)을 제공한다** (5장, p.188).[^kleppmann2026]

## 내구 실행이 하는 일

- 왜 필요해지는가 — **내구 실행 프레임워크는 트랜잭션성을 요구하는 서비스 기반 아키텍처를 짓는 인기
  있는 방법이 됐다.** 결제 예에서 **우리는 각 결제를 정확히 한 번 처리하고 싶다. 워크플로가 실행되는
  중의 실패는 신용카드 청구는 됐는데 대응하는 은행 계좌 입금은 안 된 결과를 낳을 수 있다. 서비스 기반
  아키텍처에서는 두 태스크를 그냥 데이터베이스 트랜잭션으로 감쌀 수 없다. 게다가 우리가 제한된
  통제권만 갖는 서드파티 결제 게이트웨이와 상호작용하고 있을 수도 있다** (5장,
  p.188).[^kleppmann2026]
- 기제 — **내구 실행 프레임워크는 워크플로에 정확히 한 번 의미론을 제공하는 방법이다. 태스크가
  실패하면 프레임워크가 그 태스크를 다시 실행하되, 실패 전에 그 태스크가 성공적으로 수행한 RPC 호출과
  상태 변화는 건너뛴다. 호출을 하는 척하고 대신 이전 호출의 결과를 반환한다. 이것이 가능한 이유는
  내구 실행 프레임워크가 모든 RPC와 상태 변화를 쓰기 전 로그 같은 내구 저장소에 로깅하기 때문이다**
  (5장, p.188).[^kleppmann2026]
- Temporal로 쓴 결제 워크플로 정의의 조각이다 (5장, p.188):[^kleppmann2026]

  ```python
  @workflow.defn
  class PaymentWorkflow:
      @workflow.run
      async def run(self, payment: PaymentRequest) -> PaymentResult:
          is_fraud = await workflow.execute_activity(
              check_fraud,
              payment,
              start_to_close_timeout=timedelta(seconds=15),
          )
          if is_fraud:
              return PaymentResultFraudulent
          credit_card_response = await workflow.execute_activity(
              debit_credit_card,
              payment,
              start_to_close_timeout=timedelta(seconds=15),
          )
          # ...
  ```

## 그 기제가 코드에 되돌려 거는 제약

- 밖에서는 여전히 멱등성이 필요하다 — **Temporal 같은 프레임워크에 도전이 없는 것은 아니다. 예의
  서드파티 결제 게이트웨이 같은 외부 서비스는 여전히 멱등적 API를 제공해야 한다. 개발자는 중복
  실행을 막기 위해 이 API에 유일한 ID를 쓰는 것을 기억해야 한다** (5장,
  p.189).[^kleppmann2026]
- 코드 변경이 취약해진다 — **그리고 내구 실행 프레임워크가 각 RPC 호출을 순서대로 로깅하기 때문에,
  후속 실행이 같은 RPC 호출을 같은 순서로 하기를 기대한다. 이는 코드 변경을 취약하게 만든다.
  함수 호출을 재배열하는 것만으로 정의되지 않은 동작을 들일 수 있다** (5장,
  p.189).[^kleppmann2026]
- 그래서 배포 방식이 정해진다 — **기존 워크플로의 코드를 수정하는 대신, 코드의 새 버전을 별도로
  배포해 기존 워크플로 호출의 재실행은 옛 버전을 계속 쓰고 새 호출만 새 코드를 쓰게 하는 편이
  안전하다** (5장, p.189).[^kleppmann2026]
- 비결정적 코드가 금지된다 — **비슷하게, 내구 실행 프레임워크는 모든 코드를 결정적으로(같은 입력이
  같은 출력을 낳도록) 재생하기를 기대하므로 난수 생성기나 시스템 시계를 호출하는 것 같은 비결정적
  코드가 문제가 된다. 프레임워크는 흔히 그런 라이브러리 함수의 결정적 구현을 자체적으로 제공하지만
  그것을 쓰는 것을 기억해야 한다. Temporal의 Workflow Check처럼 비결정적 동작이 들어왔는지 판정하는
  정적 분석 도구를 제공하는 것들도 있다** (5장, p.189).[^kleppmann2026]
- 저자가 남긴 주 — **코드를 결정적으로 만드는 것은 강력한 착상이지만 견고하게 하기는 까다롭다**
  (5장, p.189).[^kleppmann2026]
