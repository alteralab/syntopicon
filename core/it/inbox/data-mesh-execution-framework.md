## 하나의 질문

**데이터 메시를 어디서부터, 어떤 리듬으로 시작하는가.**

1~4부가 원칙·아키텍처·설계를 정하고 나면 5부는 그것을 조직 안에서 움직이는 문제로 옮긴다.
5부 도입이 범위를 못 박는다 — **데이터 메시는 규모에서 데이터로부터 가치를 얻는 데이터
주도(data-driven) 조직을 기르는 데이터 전략(data strategy)의 한 요소다. 이 전략의 실행은
여러 면을 갖는다. 그것은 팀·팀의 책임 구조·도메인과 플랫폼 팀 사이의 책임 획정에 영향을 준다.
문화, 곧 조직이 데이터 지향 성공을 어떻게 가치 평가하고 측정하는지에 영향을 준다. 운영
모델과, 데이터 가용성·보안·상호운용성에 관한 지역·전역 결정이 내려지는 방식을 바꾼다.
탈중앙 데이터 공유 모델을 받치는 새 아키텍처를 도입한다** (5부 도입, p.269).[^dehghani2022]

- 저자는 이 부의 지위를 낮춰 잡는다 — **이 책을 쓰는 시점에 우리는 데이터 메시 채택의 초기
  연도에 있다** (5부 도입, p.270).[^dehghani2022] 그리고 **이 장들에서 제안하는 접근은
  도메인 지향 운영 팀과 디지털 플랫폼을 짓는 것 같은 시나리오에 성공적으로 적용되어 온
  진화적·대규모 전환 모델의 적응(adaptation)이다. 나는 데이터 메시에 특유한 장애물과
  촉진자에 대한 내 경험을 공유할 것이다. 이것은 출발점일 뿐이고, 데이터 메시에 고유한 전환
  접근을 다듬는 데는 앞으로 여러 해가 남아 있다** (5부 도입, p.270).[^dehghani2022]

## 먼저: 지금 채택할 조직인가 — 여덟 자기 평가 축

- 15장은 방법론이 아니라 **자격 심사**로 시작한다 — **이 장의 나머지로 넘어가기 전에 스스로
  물어도 좋다. 데이터 메시가 우리 조직에 맞는 선택인가. 더 중요하게는, 데이터 메시가 **지금**
  맞는 선택인가** (15장, p.271).[^dehghani2022]
  - 각주가 "지금"을 정의한다 — **"지금(Now)"은 이 책이 출간된 시점이고, 데이터 메시를
    네이티브로 지원하는 기술이 이른 성숙 상태에 있음을 함의한다** (15장, p.271, 각주
    1).[^dehghani2022] 곧 아래 여덟 축 중 "얼리 어답터" 항은 기술 생태계의 상태에 종속된
    조건이지 영구 조건이 아니다.
- 판정 형식은 거미줄 그래프다 — **그림 15-1은 이 질문들에 대한 내 관점을 그린다. 나는 거미줄
  그래프(spider graph)의 색칠된 구역에 드는 조직 — 평가 축 각각에서 중간 또는 높음을 받는
  조직 — 이 이 시점에 데이터 메시를 성공적으로 채택할 위치에 가장 잘 놓여 있다고 제안한다**
  (15장, pp.271–272).[^dehghani2022]

여덟 축과, 각 축이 명시하는 **탈락 조건**이 같이 적혀 있다 (15장, pp.272–275):[^dehghani2022]

| 축 | 통과 조건 | 저자가 명시한 탈락 조건 |
|---|---|---|
| 조직 복잡성(Organizational complexity) | 데이터·애플리케이션 확산으로 기존 웨어하우스·레이크가 **병목이 된** 규모 | **그런 복잡성 수준에 도달하지 않았고 기존 데이터·분석 아키텍처가 필요를 충족한다면 데이터 메시는 별 가치를 주지 않을 것이다** |
| 데이터 지향 전략(Data-oriented strategy) | ML·분석을 전략적 차별화 요소로 식별 | **데이터 사용에 관한 전략적 비전 없이는 도메인 팀과 비즈니스 도메인이 데이터 공유라는 추가 책임을 지도록 동기 부여하기 어렵다** |
| 임원 지원(Executive support) | C 레벨의 후원과 하향식 관여 | 변화에는 저항이 따르고 **플랫폼의 진척 대 마감을 맞추는 점 솔루션 사이에서 어려운 결정이 필요할 것이다** |
| 핵심에 있는 데이터 기술(Data technology at core) | 데이터·AI를 사업을 확장·재편하는 경쟁 우위로 쓰는 조직 | **기술을 사업의 지원자로 보고 핵심에 두지 않아 기술 능력을 외부 벤더에 위임·외부화하고 기성 솔루션을 사서 꽂기를 기대하는 조직은 아직 데이터 메시를 채택할 위치가 아니다** |
| 얼리 어답터(Early adopter) | 실험·위험 감수·빠른 실패·학습의 기풍, **첫 원리에서 출발해 자기 맥락에 적응시킬 의지** | **위험을 감수하지 않고 잘 검증되고 정제되고 처방된 플레이북만 채택하기를 좋아하는 late adopter 범주의 조직은 당분간 그냥 기다려야 할지 모른다** |
| 현대적 엔지니어링(Modern engineering) | 지속적·자동화된 전달, 데브옵스, 분산 아키텍처, 계산적 정책, 현대적 클라우드 데이터 저장·처리 | **중앙집중 데이터 모델링·중앙집중 데이터 통제·중앙집중 데이터 저장을 강제하는 기술은 성공적 데이터 메시 구현에 맞지 않는다. 그것들은 병목이 되고 데이터 메시의 분산 성질과 충돌한다** |
| 도메인 지향 조직(Domain-oriented organization) | 비즈니스 도메인마다 전담 기술 팀이 있고 기술·비즈니스가 밀착 | **모든 사업 단위에 걸쳐 프로젝트 기준으로 사람(자원)을 공유하는 중앙집중 IT 단위를 가진, 비즈니스 도메인마다의 기술 자산에 대한 지속적·장기적 소유가 없는 조직은 데이터 메시에 좋은 적합이 아니다** |
| 장기 헌신(Long-term commitment) | 전환 여정에 대한 조직적 헌신 | **데이터 메시는 한두 개의 일회성 프로젝트로 구현될 수 없다** |

- 얼리 어답터 축의 근거는 Everett M. Rogers, *Diffusion of Innovations*이고 (15장, p.274,
  각주 2), 현대적 엔지니어링 축은 Martin Fowler의 "Microservice Prerequisites"(2014)를
  전제 목록으로 든다 (15장, p.274, 각주 3).[^dehghani2022] 곧 저자는 **데이터 메시가
  마이크로서비스와 전제를 공유한다**고 명시한다 —
  [마이크로서비스와 서버리스](../concepts/microservices-and-serverless.md)가 그 전제 쪽이다.
- 첫째 축이 다른 일곱을 지배한다 — **데이터 메시 채택의 일차적 기준은 내재적 비즈니스 복잡성과
  데이터 소스·데이터 유스케이스의 확산이다** (15장, p.273).[^dehghani2022]
- 이 심사는 [분석 데이터 관리의 변곡점](../concepts/data-mesh-inflection-point.md)이 거시
  수준에서 말한 것을 조직 하나의 수준으로 내린 것이다 — 변곡점은 산업 전체에 왔더라도, 개별
  조직이 그 지점을 통과했는지는 따로 판정한다.

## 데이터 메시는 데이터 전략의 한 요소다

그림 15-2가 전략에서 플랫폼까지 다섯 층을 세로로 잇고, 왼쪽에 **조직 정렬(구조·프로세스·
문화·성숙도)**을, 오른쪽에 **비즈니스 주도의 반복적 종단 진화 실행(얇은 절편, thin slicing)**을
기둥으로 세운다 (15장, p.276).[^dehghani2022] 저자는 위에서 아래로 읽는다 (15장,
pp.277–278):[^dehghani2022]

- **데이터 전략(data strategy)** — **회사가 데이터를 얼마나 고유하게 활용하는지를 정의하고
  전략적 이니셔티브의 로드맵을 만든다.**
- **전략적 비즈니스 이니셔티브와 유스케이스** — **전략에 따라 데이터와 ML을 활용할 비즈니스
  이니셔티브·유스케이스·실험의 집합이 정의된다.**
- **지능형 애플리케이션과 접점(touchpoints)** — **궁극적으로 사용자의 경험은 그들의 접점과
  그들이 쓰는 애플리케이션을 통해 향상되어야 한다. 각 지능형 비즈니스 이니셔티브는 기존
  애플리케이션의 증강이나 ML을 갖춘 새 애플리케이션으로 이어질 수 있다.**
- **데이터 프로덕트** — **지능형 애플리케이션이 데이터 프로덕트의 식별과 개발을 이끈다.
  실세계 애플리케이션이 데이터 프로덕트 창출을 촉발하지만, 모든 데이터 프로덕트가 그것들에
  직접 쓰이는 것은 아니다. 소비자 정렬(consumer-aligned) 데이터 프로덕트는 애플리케이션이
  직접 쓰고, 집계(aggregate) 또는 소스 정렬(source-aligned) 데이터 프로덕트는 그 데이터
  프로덕트들이 쓸 가능성이 크다. 시간이 지나면서 새롭고 신기한 지능형 애플리케이션에 재사용되는
  데이터 프로덕트의 메시가 만들어진다.**
- **멀티플레인 플랫폼** — **데이터 프로덕트와 지능형 애플리케이션의 창출·소비가 플랫폼 능력의
  우선순위와 개발을 이끈다.** 다만 순서에는 예외를 둔다 — **플랫폼 기능은 병렬로, 때로는
  데이터 프로덕트·지능형 애플리케이션 개발보다 **앞서** 개발된다. 그러나 플랫폼의 가치는
  데이터 프로덕트의 마찰 없고 신뢰할 만한 전달을 통한 **사용**을 기준으로 시연되고 측정된다.**
- **조직 정렬** — **연합 거버넌스 운영 모델의 형성, 교차 기능(비즈니스·개발·데이터·운영) 팀의
  형성, 데이터 프로덕트 소유 역할의 확립이 모두 변화 관리 규율의 보살핌과 주의를 요구하는
  데이터 메시의 조직적 측면이다.** 그리고 시점을 못 박는다 — **조직 정렬은 데이터 비즈니스
  이니셔티브의 전달·실행과 **동시에**, 다만 명시적 의도와 조직 계획을 갖고 일어난다.**
- 이 세로줄이 [멀티플레인 데이터 플랫폼](../concepts/multiplane-data-platform.md)과
  [데이터 퀀텀](../concepts/data-quantum.md)이 무엇을 위해 존재하는지의 위쪽 맥락이다 —
  아키텍처는 비즈니스 이니셔티브에서 유도되지 그 반대가 아니다.

## 실행 프레임워크의 네 성격

- 저자는 "전환(transformation)"이라는 낱말의 무게를 인정하고 그 반대로 간다 — **나는
  transformation이라는 낱말이 꽤 무게를 지닌다는 것을 이해한다. 마치 그것을 움직이게 하려면
  큰 잠재 에너지가 필요한 것처럼. 내가 공유하려는 것은 시작하는 데 도움이 될 수 있는 고수준
  프레임워크다. 이 프레임워크는 한 번에 한 이터레이션씩 나아가고 진척하게 하며, 기반 — 플랫폼·
  정책·운영 방식 — 을 성숙시키면서 가치와 결과를 전달한다. 그것은 **큰 변화를 위한 빅뱅 푸시에
  필요한 모든 의지와 에너지를 모으느라 실행을 미루는 대신, 앞으로 나아가는 운동 에너지(kinetic
  energy)를 써서 계속 나아가게 한다**** (15장, p.279).[^dehghani2022]
- 그림 15-3이 네 성격을 사분면에 둔다 — **비즈니스 주도(business-driven)·종단(end to end)·
  반복적(iterative)·진화적(evolutionary)** (15장, p.279).[^dehghani2022]
- 넷째 성격은 별도 페이지가 받는다 —
  [데이터 메시의 진화적 채택 단계](../concepts/data-mesh-adoption-phases.md)와
  [데이터 메시의 적합성 함수](../concepts/data-mesh-fitness-functions.md)가 그 거시·미시 도구다.

## 비즈니스 주도 실행 — 세 이익

- 정의 — **데이터 메시는 더 큰 데이터 전략의 구성 요소이고, 그림 15-2가 보인 대로 그 실행은
  ML이나 분석을 요구하는 전략적 비즈니스 케이스와 사용자 시나리오가 이끈다. 그것들이 데이터
  프로덕트의 식별·전달과, 그것들을 짓고 관리하고 소비할 플랫폼 구성 요소를 이끈다** (15장,
  p.280).[^dehghani2022]
- 계보를 아마존에 댄다 — **이것은 아마존이 주요 제품과 이니셔티브를 짓는 방식과 비슷하게
  흐른다. "고객에서 시작해 거꾸로 일하라 — 들리는 것보다 어렵지만, 혁신하고 고객을 기쁘게
  하는 명확한 길이다. 유용한 Working Backwards 도구: 제품을 짓기 전에 보도자료와 FAQ를
  쓰는 것."** (15장, p.280, 각주 4).[^dehghani2022]
  - 각주가 든 출처는 *Working Backwards*(New York: St. Martin's Press, 2021), p.98이고,
    저자를 **Colin Bryan and Bill Carr**로 적는다 — 실제 공저자 표기는 Colin Bryar이므로
    원문의 오식으로 보인다. #hypothesis
- 이익 셋 (15장, p.280):[^dehghani2022]
  - **가치와 결과의 지속적 전달과 시연** — **긴 전환 도중에 결과를 보이는 것은 사기에 긍정적
    영향을 주고, 동의를 얻고, 헌신을 높이고, 투자의 지속을 보장한다.** 다만 초기 속도에는
    단서를 단다 — **비즈니스 주도 실행은 지속적으로 비즈니스 가치를 전달하지만, 초기에는 그
    속도가 느리거나 영향 범위가 작을 수 있다. 플랫폼 능력과 운영 모델이 성숙하면서 속도와
    범위가 개선된다.**
  - **소비자로부터의 빠른 피드백** — **내부·외부 사용자와 관여하는 것은 플랫폼과 데이터
    프로덕트의 사용성에 긍정적 영향을 준다. 피드백이 더 일찍, 반복적으로 반영된다.**
  - **낭비 감소** — **실제 비즈니스 유스케이스에 기반해 데이터 프로덕트와 플랫폼을 개발하는
    것은 실제로 필요한 것을 필요할 때 짓게 한다. 기술 투자가 단지 빌드 계획을 따르는 것과
    대조적으로, 비즈니스에 지속 가능하게 가치를 전달하는 데 집중된다.**

## 비즈니스 주도 실행 — 세 병리와 처방

같은 접근이 부르는 부작용이 처방과 짝지어 적혀 있다 (15장, pp.281–282):[^dehghani2022]

- **① 시점 솔루션(point-in-time solutions) 짓기** — **한 번에 하나의 비즈니스 유스케이스에
  솔루션을 전달하는 좁은 초점은 미래 유스케이스를 충족하도록 확장되지 않는 플랫폼 능력과 데이터
  프로덕트를 개발하는 것으로 이어질 수 있다. 이것은 비즈니스 케이스 주도 개발의 가능한 부정적
  결과다.** 특히 위험한 자리를 지목한다 — **이것은 플랫폼 서비스와 소스 정렬·집계 데이터
  프로덕트에 특히 문제가 된다. 메시 위 플랫폼 서비스와 데이터 프로덕트의 목적은 넓은 유스케이스
  집합을 섬기고 가능하게 하는 것이기 때문이다.**
  - 처방 — **제품 사고(product thinking)가 시점 솔루셔닝과 YAGNI 원칙("You Aren't Gonna
    Need It", 미리 짓는 것) 사이의 올바른 균형을 찾는 열쇠다. 데이터 프로덕트 소유자는 분석
    유스케이스의 무한한 성질을 이해한다. 오늘 우리가 인지하지 못하는 미래 유스케이스가 패턴과
    추세를 발견하려 과거 데이터에 손을 뻗을 것이다. 따라서 **데이터 프로덕트는 알려진 유스케이스의
    정확한 필요를 넘어서 데이터를 포착해야 한다**. 이것은 특히 소스 정렬 데이터 프로덕트에
    참이며, 거기서는 비즈니스의 현실과 사실을 가능한 한 가깝게, 일어나는 그대로 포착해야 한다.**
    소스 정렬의 이 성질은 [도메인 소유권 원칙](../concepts/domain-ownership-principle.md)의
    세 원형 서술과 같은 것이다.
- **② 촉박한 비즈니스 마감** — **비즈니스 주도 실행은 플랫폼과 데이터 프로덕트의 개발을
  비즈니스 마감에 종속시킨다. 비즈니스 마감은 흔히 바꾸기 어렵다. 조직 안의 여러 당사자, 때로는
  바깥의 파트너·고객과의 조정을 요구하기 때문이다. 이 마감을 맞추려 플랫폼 서비스 같은 스택의
  아래 층이 비즈니스 케이스의 마감을 맞추려 품질에서 모서리를 잘라 내며 기술 부채(technical
  debt)를 질 수 있다.**
  - 처방 — **플랫폼과 데이터 프로덕트의 장기 제품 소유권과 에버그린 엔지니어링 실무가 새 기능
    전달과 함께 생길 수 있는 기술 부채를 다루는 지속적 개선 과정이 자리 잡게 보장할 수 있다.
    오래 서 있는(long-standing) 플랫폼·데이터 프로덕트 팀은 특정 프로젝트 전달을 넘어서
    자기 시스템과 데이터에 대한 지식과 유인을 갖는다.**
  - 부채에도 등급이 있다 — **예컨대 플랫폼 서비스나 데이터 프로덕트의 장기 제품 소유자는
    시간에 쫓기더라도 API와 인터페이스를 제대로 잡는 것이 우선임을 안다. 흔히 구현 세부에서 진
    기술 부채를 고치는 것이 인터페이스를 바꾸는 것보다 쉽다. API 변경은 다수의 소비자에게 영향을
    주므로 변경 비용이 더 높을 가능성이 크다.**
- **③ 프로젝트 기반 예산(project-based budgeting)** — **비즈니스 이니셔티브의 전달은 흔히
  고정 배정 예산을 가진 기한 있는 프로젝트로 조직된다. 데이터 메시 구현을 비즈니스 이니셔티브를
  통해 실행하는 것은 메시의 오래 서 있는 디지털 구성 요소 — 데이터 프로덕트와 플랫폼 — 에 대한
  예산과 자원 배분에 부정적 영향을 줄 수 있다. 예산이 기한 있는 비즈니스 이니셔티브에 배정되면
  그것이 플랫폼 서비스나 데이터 프로덕트를 짓는 유일한 투자원이 된다. 그 결과 장기 소유권·지속적
  개선·성숙도가 고통받는다.**
  - 처방 — **비즈니스 프로젝트는 오래 서 있는 플랫폼과 데이터 프로덕트를 실행하는 훌륭한
    운반체다. 그러나 그것들의 **유일한** 자금 조달 기제일 수는 없다. 플랫폼과 데이터 프로덕트는
    자기 몫으로 배정된 장기 자원과 예산을 가져야 한다.**
  - 저자가 근본 충돌로 진단한다 — **프로젝트 정신(project mentality)은 제품 팀이 결코 끝나지
    않는 플랫폼·제품 사고와 상충한다. 그들은 새 요구사항 앞에서 계속 제품을 성숙시키고·유지하고·
    진화시키며 많은 프로젝트를 지원한다.**

## 비즈니스 주도 실행 — 네 지침

시작할 때의 실무 지침 넷 (15장, pp.283–284):[^dehghani2022]

- **① 보완적 유스케이스로 시작한다** — **단일 용법 대신 한 번에 두어 개의 보완적 유스케이스를
  고르는 것이 점 솔루션 짓기를 피한다. 보완적이고 동시적인 유스케이스를 통해 메시의 재사용 가능한
  구성 요소를 짓는 것이 점 솔루셔닝의 함정을 피하는 강제 함수(forcing function)가 될 수 있다.**
  예 — **초기 유스케이스를 분석과 리포팅처럼 다르지만 보완적인 영역에서 가져와 ML 기반 솔루션을
  보완할 수 있다. 이것은 데이터 프로덕트의 설계가 두 가지 다른 접근 양식 — ML과 리포팅 — 을
  감당하도록 강제하여, 한 양식에 다른 것으로 확장되지 않는 방식으로 과잉 솔루셔닝하는 것을 막는다.**
- **② 데이터 소비자와 제공자 페르소나를 알고 우선순위를 매긴다** — **두 유형의 데이터 메시
  사용자 페르소나 — 데이터 제공자와 데이터 사용자 — 모두에 초점을 맞추는 것이 플랫폼 능력의
  우선순위를 공정하게, 가장 큰 종단 영향으로 매기게 돕는다.** 저자가 관찰한 실패 양상 —
  **내 경험상 많은 데이터 메시 실행이 데이터 프로덕트 창출에 방점을 두고 시작한다. 그 결과
  데이터 소비자 경험이 고통받고, 종단 결과가 훼손된다.**
- **③ 플랫폼의 결측 기능에 대한 의존이 최소인 유스케이스로 시작한다** — **플랫폼은 사용자에
  응답해 진화한다. 어느 시점에도 모든 유스케이스가 필요로 하는 모든 기능을 그냥 만족시킬 수는
  없다. 실행의 초기 단계에서는 유스케이스가 신중히 선택되는 것이 중요하다. 초기 유스케이스는
  플랫폼에 대한 의존이 **딱 충분히** 있어서, 완전히 막히지 않으면서도 필요한 플랫폼 서비스의
  우선순위와 구축을 이끌어야 한다.** 결측분의 처리 경로도 정해 준다 — **결측 플랫폼 능력에
  대해서는 도메인 팀이 커스텀 개발하고 나중에 플랫폼으로 수확(harvest)되어 일반화될 수 있다.**
  - 이 "수확" 방향이
    [셀프서브 데이터 플랫폼 원칙](../concepts/self-serve-data-platform-principle.md)이 말하는
    플랫폼 기능의 출처다 — 플랫폼이 예견해서 짓는 것이 아니라 도메인이 먼저 짓고 플랫폼이 걷는다.
- **④ 플랫폼 서비스와 데이터 프로덕트에 장기 소유권과 예산을 만든다** — **비즈니스
  이니셔티브와 개별 유스케이스가 메시를 개발할 투자를 제공할 수 있지만, 메시는 오래 서 있는
  디지털 투자이자 회사의 내부 제품으로 간주되어야 한다. 그것은 발족 이후로도 계속 가치를 전달할
  것이 기대된다. 따라서 장기 진화와 운영을 지탱할 자기 몫의 배정된 자원과 투자를 요구한다.**

## 종단·반복 실행

- 이 절은 Martin Fowler의 한 줄로 열린다 — **빅뱅 재아키텍처가 보장하는 유일한 것은
  빅뱅이다!(The only thing a Big Bang re-architecture guarantees is a Big Bang!)** (15장,
  p.285).[^dehghani2022]
- 반복이 무엇을 키우는지가 열거된다 — **지능형 비즈니스 가치의 종단 전달을 지속적으로 반복하는
  것이 메시를 풍요롭게 한다. 그것은 데이터 프로덕트의 수를 쌓아 올린다. 플랫폼 서비스를
  향상시킨다. 자동화된 정책의 커버리지와 효과를 높인다** (15장, p.285).[^dehghani2022]
- 동시성이 전제다 — **어느 시점에도 여러 이터레이션이 동시에 실행되고 있다** (15장,
  p.285).[^dehghani2022] 그리고 반복이 쌓는 것 — **앞서 언급한 것 같은 유스케이스를 전달하는
  이터레이션을 통해 더 많은 데이터 프로덕트가 만들어지고, 더 많은 애플리케이션이 지능적으로
  증강되고, 더 많은 도메인이 메시의 일부가 되고, 플랫폼 서비스가 더 성숙하고, 더 많은 정책이
  계산적으로 가능해진다** (15장, p.285).[^dehghani2022]
- 그림 15-4는 이 종단 이터레이션 하나를 제공자(Listener player events·Listener profiles) →
  소비자(Recommended playlists·Music profiles) 축으로 그리고, 그 위를 계산적 정책(통합 신원·
  프라이버시·암호화)이 가로지르며, 아래는 데이터 프로덕트 창출·검색·모니터링·소비라는 플랫폼
  여정으로 받친다 (15장, p.285).[^dehghani2022] 그 아래층이
  [데이터 플랫폼 사용자 여정](../concepts/data-platform-user-journeys.md)이다.
