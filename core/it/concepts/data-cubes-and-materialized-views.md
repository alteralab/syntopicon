## 구체화 뷰와 가상 뷰

- 정의가 대비로 주어진다 — **관계형 데이터 모델에서 구체화 뷰(materialized view)는 그 내용이
  어떤 질의의 결과인 테이블 비슷한 객체다. 구체화 뷰는 질의 결과의 실제 사본이며 디스크에
  쓰인다. 반면 가상 뷰(virtual view)는 그저 질의를 쓰는 지름길이다. 가상 뷰에서 읽으면 SQL
  엔진이 그것을 뷰의 밑에 깔린 질의로 즉석에서 펼친 뒤 펼쳐진 질의를 처리한다** (4장,
  p.143).[^kleppmann2026]
- 사본이므로 유지 비용이 따라온다 — **밑에 깔린 데이터가 바뀌면 구체화 뷰도 그에 맞게 갱신돼야
  한다. 어떤 데이터베이스는 그것을 자동으로 할 수 있고, Materialize처럼 구체화 뷰 유지에 특화된
  시스템도 있다** (4장, p.143).[^kleppmann2026]
- 거래의 방향이 명시된다 — **그런 갱신을 수행한다는 것은 쓰기에서 더 많은 일을 한다는 뜻이지만,
  구체화 뷰는 같은 질의를 반복해 수행해야 하는 워크로드에서 읽기 성능을 개선할 수 있다** (4장,
  pp.143–144).[^kleppmann2026]

## 구체화 집계

- **구체화 집계(materialized aggregates)는 데이터 웨어하우스에서 유용할 수 있는 구체화 뷰의 한
  유형이다. 데이터 웨어하우스 질의는 흔히 SQL의 `COUNT`·`SUM`·`AVG`·`MIN`·`MAX` 같은 집계 함수를
  포함한다. 같은 집계가 많은 질의에 쓰인다면 매번 원시 데이터를 갈아 대는 것은 낭비일 수
  있다** (4장, p.144).[^kleppmann2026]
- 그래서 나오는 질문이 이것이다 — **질의가 가장 자주 쓰는 카운트나 합계 중 일부를 캐시해 두면
  어떨까** (4장, p.144).[^kleppmann2026]

## 데이터 큐브

- **데이터 큐브(data cube, OLAP 큐브OLAP cube라고도 한다)가 서로 다른 차원으로 묶인 집계의
  격자를 만듦으로써 그 일을 한다** (4장, p.144).[^kleppmann2026]
- 두 차원일 때의 그림 — **각 팩트가 차원 테이블 둘에만 외래 키를 갖는다고 하자. 이제 한 축에
  날짜를, 다른 축에 제품을 둔 2차원 테이블을 그릴 수 있다. 각 칸은 그 날짜–제품 조합을 가진 모든
  팩트의 어떤 속성(예: `net_price`)에 대한 집계(예: `SUM`)를 담는다. 그 뒤 같은 집계를 각 행이나
  열을 따라 적용해 한 차원이 줄어든 요약을 얻을 수 있다** — 날짜와 무관한 제품별 판매, 또는
  제품과 무관한 날짜별 판매다 (4장, p.144).[^kleppmann2026]
- 차원이 늘어도 원리는 같다 — **일반적으로 팩트는 흔히 둘보다 많은 차원을 갖는다.** 예로 든
  스키마에는 날짜·제품·매장·프로모션·고객의 다섯 차원이 있다. **5차원 초입방체가 어떻게 생겼을지
  상상하기는 훨씬 어렵지만 원리는 같다 — 각 칸이 특정 날짜–제품–매장–프로모션–고객 조합의 판매를
  담고, 그 값들을 각 차원을 따라 반복해 요약할 수 있다** (4장, p.144).[^kleppmann2026]
- 이득 — **구체화된 데이터 큐브의 이점은 어떤 질의들이 사실상 미리 계산돼 있어 매우 빨라진다는
  것이다. 예컨대 어제 매장별 총 판매를 알고 싶으면 적절한 차원을 따라 합계만 보면 되고 수백만
  행을 스캔할 필요가 없다** (4장, p.145).[^kleppmann2026]

## 큐브가 못 하는 것

- 대가가 유연성이다 — **단점은 데이터 큐브가 원시 데이터를 질의하는 것과 같은 유연성을 갖지
  못한다는 것이다. 예컨대 100달러가 넘는 품목에서 나온 판매의 비율을 계산할 방법이 없는데,
  가격이 차원 중 하나가 아니기 때문이다** (4장, p.145).[^kleppmann2026]
- 그래서 실무의 배치가 정해진다 — **그러므로 대부분의 데이터 웨어하우스는 가능한 한 많은 원시
  데이터를 유지하려 하고, 데이터 큐브 같은 집계는 특정 질의에 대한 성능 부스트로만 쓴다** (4장,
  p.145).[^kleppmann2026]

## 상용 다차원 데이터베이스가 파는 것

위 절들이 큐브를 저장 기법으로 서술했다면, 이 절은 같은 것을 제품이 어떻게 규정하고
스스로 어디에 부적합하다고 말하는지다. 웨어하우스 계층 안에서의 자리는
[정보 마트](../concepts/information-mart.md)에 있다.

- 자리 규정이 사용자에서 출발한다: 대부분의 일반 업무 사용자는 관계형 웨어하우스를 직접
  다루지 않고 **다차원 데이터베이스(multidimensional database)를 정보 접근의 주 인터페이스로
  선호한다.** 이 데이터베이스들은 온라인 분석 처리(Online Analytic Processing, OLAP)를
  지원하도록 설계되며, 업무 사용자가 질의를 만들고 빠른 응답을 얻게 해 주는 효과적인 소비
  도구다. **최종 사용자가 원시 팩트가 아니라 집계된 정보로 작업하고 싶을 때 가장 적합하다**
  (15장 서두, p.684).[^linstedt2016]
- 상용 OLAP 엔진의 특성 다섯 (15장 서두, pp.684–685):[^linstedt2016]
  - **사용자 정의 메타데이터** — 다차원 데이터베이스는 하나 이상의 OLAP 큐브로 이뤄지고,
    큐브는 정보 마트에서 온 팩트·차원 정의를 그대로 따른다. 계층을 지원하며 여러 큐브의
    팩트를 결합하는 선택지도 있다 — **관계형 토대를 앞 장들의 원칙대로 지었다면 여러 OLAP
    큐브를 가로지르는 질의가 가능해진다.**
  - **질의 성능** — 관계형 데이터베이스에 대고 실행하면 그루핑·집계로 특징지어지는 분석
    질의에서 우월한 성능을 낸다.
  - **집계 관리** — 우월한 성능의 이유 중 하나가 **큐브가 서로 다른 grain 수준에서 데이터를
    미리 계산해 둔다는 것**이며, 이 집계 관리는 업무 사용자에게 투명하다.
  - **계산** — 백분율처럼 큐브에 계산을 더해야 하는 경우를 위해 계산된 측정값을 제공한다.
  - **보안 규정** — 집계된 데이터의 무단 사용을 막는 복잡한 보안 규칙을 제공한다.
- 스스로 그은 경계가 위의 "큐브가 못 하는 것"과 같은 방향을 가리킨다 — **요약하면 이런
  엔진은 집계된 정보를 제공하는 데 가장 좋다. 운영 업무 프로세스에서 통상 다루는 상세
  정보를 제공하기에는 좋은 데이터베이스가 아니며, 그쪽은 관계형 데이터베이스나 NoSQL
  환경이 더 적절하다** (15장 서두, p.685).[^linstedt2016] Kleppmann의 "가능한 한 많은 원시
  데이터를 유지하고 큐브는 성능 부스트로만 쓴다"와 어휘는 달라도 같은 판단이다.
- 큐브 만들기의 실물 순서는 정보 마트의 차원 테이블에서 **차원**을, 팩트 테이블(측정 그룹
  테이블)에서 **큐브**를 정의하는 것이다. 팩트 테이블은 하나만 고르고, 정의가 끝난 큐브는
  **처리(process)와 배포**를 거쳐야 프런트엔드에서 쓸 수 있다
  (§15.2–15.3.1, pp.697, 708, 713–714).[^linstedt2016]
- 계층은 큐브 쪽에서 정의된다: 날짜 차원을 설계 모드로 열어 연도 번호 → 분기 약어 → 월 약어
  → 전체 날짜 순으로 계층 캔버스에 얹는다. **차원마다 여러 계층을 정의할 수 있으므로** 계층에
  이름을 붙여 구별한다 (§15.2.1, p.705).[^linstedt2016] 계층 개념 자체는
  [차원 테이블](../concepts/dimension-table.md)에 있다.
- 접근은 다차원 질의 언어로 한다 — 예시의 MDX 문 하나가 **2003년 10월에 항공사별로 비행한
  거리를 반환한다.** 큐브에서 정보를 꺼내는 한 방법일 뿐이며, 최종 사용자에게 큐브가
  제공하는 측정값과 차원을 애드혹으로 고를 완전한 자유를 준다 (§15.4, p.715).[^linstedt2016]
  - 원문의 MDX 문 자체는 지면에 화면 이미지로만 실려 있어 옮기지 않았다.

## 뷰·연합·질의 가상화 — 결과를 테이블처럼 보이게 하는 기법들

데이터 엔지니어링 개론은 구체화 뷰를 **혼자 다루지 않고** 세 기법을 한 묶음으로 다룬다. 묶는
기준이 이 절의 정보다 — **질의 결과를 테이블 같은 객체로 제시함으로써 가상화하는 것**이다.

- 묶음의 선언 — **이 절에서 우리는 질의 결과를 테이블 같은 객체로 제시함으로써 가상화하는 여러
  기법을 본다. 이 기법들은 변환 파이프라인의 일부가 될 수도 있고 최종 사용자 데이터 소비 바로
  앞에 앉을 수도 있다** (8장, p.323).[^reis2022]
- **뷰** — **먼저 구체화 뷰의 무대를 마련하기 위해 뷰를 복습하자. 뷰(view)는 다른 어떤 테이블처럼
  `SELECT`할 수 있는 데이터베이스 객체다. 실무에서 뷰는 단지 다른 테이블을 참조하는 질의일 뿐이다.
  뷰에서 선택하면 데이터베이스는 뷰 서브질의를 우리 질의와 결합하는 새 질의를 만든다. 그다음 질의
  최적화기가 전체 질의를 최적화하고 돌린다** (8장, p.323).[^reis2022]
  - 위 [구체화 뷰와 가상 뷰](#구체화-뷰와-가상-뷰) 절이 인용하는 정의와 같다. 개론서가 더하는
    것은 **뷰가 하는 세 역할**이다 (8장, p.324):[^reis2022]
    - **첫째, 뷰는 보안 역할을 할 수 있다. 예컨대 뷰는 특정 컬럼만 선택하고 행을 필터해 제한된
      데이터 접근을 제공할 수 있다. 사용자 데이터 접근에 따라 직무 역할별로 다양한 뷰를 만들 수
      있다.**
    - **둘째, 뷰는 데이터의 현재 중복 제거된 그림을 제공하는 데 쓰일 수 있다. 삽입 전용 패턴을
      쓰고 있다면 뷰를 써서 각 레코드의 최신 버전만 보여 주는 중복 제거된 버전의 테이블을 반환할
      수 있다.**
    - **셋째, 뷰는 흔한 데이터 접근 패턴을 제시하는 데 쓰일 수 있다. 마케팅 분석가가 다섯 테이블을
      조인하는 질의를 자주 돌려야 한다고 하자. 이 다섯 테이블을 넓은 테이블로 조인하는 뷰를 만들 수
      있다. 분석가는 그다음 이 뷰 위에서 필터하고 집계하는 질의를 쓸 수 있다.**
- **구체화 뷰** — **비구체화 뷰의 잠재적 단점은 어떤 사전 계산도 하지 않는다는 것이다. 다섯 테이블을
  조인하는 뷰의 예에서, 이 조인은 마케팅 분석가가 이 뷰에 질의를 돌릴 때마다 돌아야 하고 그 조인은
  극도로 비쌀 수 있다** (8장, p.324).[^reis2022]
  - **구체화 뷰(materialized view)는 뷰 계산의 일부 또는 전부를 미리 한다. 우리 예에서 구체화
    뷰는 원천 테이블에 변경이 일어날 때마다 다섯 테이블 조인 결과를 저장할 수 있다. 그다음 사용자가
    뷰를 참조하면 사전 조인된 데이터를 질의하는 것이다. 구체화 뷰는 사실상의 변환 단계이지만
    데이터베이스가 편의를 위해 실행을 관리한다** (8장, p.324).[^reis2022]
  - 최적화기가 알아서 쓰기도 한다 — **구체화 뷰는 데이터베이스에 따라 그것을 직접 참조하지 않는
    질의에 대해서도 유의한 질의 최적화 역할을 할 수 있다. 많은 질의 최적화기가 구체화 뷰처럼
    "생긴" 질의를 식별할 수 있다. 분석가가 구체화 뷰에 나타나는 필터를 쓰는 질의를 돌릴 수 있다.
    최적화기는 사전 계산된 결과에서 선택하도록 질의를 다시 쓸 것이다** (8장, p.324).[^reis2022]
  - **위 [구체화 뷰와 가상 뷰](#구체화-뷰와-가상-뷰) 절이 "쓰기 시 비용, 읽기 시 이득"이라는
    맞교환으로 같은 것을 서술한다.** 개론서가 더하는 각도는 **구체화 뷰가 변환 단계인데 실행
    주체가 데이터베이스**라는 지위 규정이다 —
    [수명 주기의 변환 단계](../concepts/transformation-in-the-lifecycle.md)와 이 페이지가
    만나는 자리다.
- **합성 가능한 구체화 뷰** — **일반적으로 구체화 뷰는 합성을 허용하지 않는다 — 즉 구체화 뷰가
  다른 구체화 뷰에서 선택할 수 없다. 그러나 2022년 저술 시점 기준 최근 이 역량을 지원하는 도구의 출현을 보았다. 예컨대
  Databricks는 라이브 테이블(live tables) 개념을 도입했다. 각 테이블은 원천에서 데이터가 도착하는
  대로 갱신된다. 데이터는 후속 테이블로 비동기적으로 흘러간다** (8장, p.324).[^reis2022]
  - 같은 문제를 이론 쪽에서 다룬 것이
    [증분 뷰 유지](../concepts/incremental-view-maintenance.md)다.
- **연합 질의** — **연합 질의(federated queries)는 OLAP 데이터베이스가 오브젝트 저장이나 RDBMS
  같은 외부 데이터 원천에서 선택할 수 있게 해 주는 데이터베이스 기능이다. 예컨대 오브젝트 저장과
  MySQL·PostgreSQL 데이터베이스의 다양한 테이블에 걸쳐 데이터를 결합해야 한다고 하자. 데이터
  웨어하우스는 이 원천들에 연합 질의를 발행하고 결합된 결과를 반환할 수 있다** (8장,
  p.324).[^reis2022]
  - 외부 테이블 — **또 다른 예로 Snowflake는 S3 버킷에 정의된 외부 테이블(external tables)
    개념을 지원한다. 외부 데이터 위치와 파일 형식은 테이블을 만들 때 정의되지만 데이터는 아직
    테이블로 반입되지 않는다. 외부 테이블이 질의되면 Snowflake는 S3에서 읽고 테이블 생성 시 설정된
    파라미터에 기반해 데이터를 처리한다. S3 데이터를 내부 데이터베이스 테이블에 조인할 수도 있다.
    이는 Snowflake와 비슷한 데이터베이스를 데이터 레이크 환경과 더 호환되게 만든다** (8장,
    p.325).[^reis2022]
  - 구체화 뷰와 만나는 자리 — **어떤 OLAP 시스템은 연합 질의를 구체화 뷰로 변환할 수 있다. 이는
    외부 원천이 바뀔 때마다 데이터를 수동으로 반입할 필요 없이 네이티브 테이블의 성능 상당 부분을
    준다. 구체화 뷰는 외부 데이터가 바뀔 때마다 갱신된다** (8장, p.325).[^reis2022]
- **데이터 가상화** — **데이터 가상화(data virtualization)는 연합 질의와 밀접히 관련되지만,
  이는 일반적으로 데이터를 내부적으로 저장하지 않는 데이터 처리·질의 시스템을 수반한다. 지금으로서는
  Trino(예: Starburst)와 Presto가 탁월한 예다. 외부 테이블을 지원하는 어떤 질의/처리 엔진도 데이터
  가상화 엔진 역할을 할 수 있다. 데이터 가상화에서 가장 유의한 고려사항은 지원되는 외부 원천과
  성능이다** (8장, p.325).[^reis2022]
  - **질의 푸시다운** — **밀접히 관련된 개념이 질의 푸시다운(query pushdown)이다. Snowflake의
    데이터를 질의하고 MySQL 데이터베이스의 데이터를 조인하고 결과를 필터하고 싶다고 하자. 질의
    푸시다운은 가능한 한 많은 작업을 원천 데이터베이스로 옮기는 것을 목표로 한다. 엔진은 필터링
    술어를 원천 시스템의 질의로 밀어 넣을 방법을 찾을 수 있다. 이는 두 목적에 봉사한다: 첫째,
    가상화 계층에서 계산을 덜어 내어 원천의 질의 성능을 활용한다. 둘째, 네트워크로 밀어야 하는
    데이터의 양을 잠재적으로 줄이며, 이는 가상화 성능의 결정적 병목이다** (8장,
    p.325).[^reis2022]
  - 함부로 쓰지 마라 — **데이터 가상화는 다양한 데이터 원천에 데이터가 저장된 조직에 좋은 해법이다.
    그러나 데이터 가상화가 되는대로 쓰여서는 안 된다. 예컨대 프로덕션 MySQL 데이터베이스를 가상화하는
    것은 분석 질의가 프로덕션 시스템에 악영향을 준다는 핵심 문제를 풀지 않는다 — Trino는 데이터를
    내부적으로 저장하지 않으므로 질의를 돌릴 때마다 MySQL에서 당겨 올 것이다** (8장,
    p.325).[^reis2022]
  - 대신 파이프라인의 구성 요소로 — **대안으로 데이터 가상화는 데이터 반입·처리 파이프라인의 구성
    요소로 쓰일 수 있다. 예컨대 Trino가 프로덕션 시스템의 부하가 낮은 자정에 MySQL에서 하루 한 번
    선택하는 데 쓰일 수 있다. 결과는 하류 변환과 일일 질의가 소비하도록 S3에 저장되어 MySQL을 직접
    분석 질의에서 보호할 수 있다** (8장, p.326).[^reis2022]
  - 데이터 메시와의 접점 — **데이터 가상화는 조직 단위 사이에 데이터를 사일로화하는 데 쓰이는 장벽을
    추상화해 데이터 레이크를 훨씬 많은 원천으로 확장하는 도구로 볼 수 있다. 조직은 자주 접근되는
    변환된 데이터를 S3에 저장하고 회사의 다양한 부분 사이의 접근을 가상화할 수 있다. 이는 데이터
    메시 개념과 밀접히 맞는데, 거기서는 작은 팀들이 자기 데이터를 분석용으로 준비하고 회사의 나머지와
    공유할 책임을 진다. 가상화는 실용적 공유를 위한 결정적 접근 계층 역할을 할 수 있다** (8장,
    p.326).[^reis2022] 그 아키텍처는 [데이터 메시](../concepts/data-mesh.md)에 있다.
