있는가.**

## 보편 표준이 없다는 전제

- **저자들이 절 제목에 "(부분적으로) 나열된"이라는 단서를 박는다.** 이 절이 세는 목록이 완결이
  아니라는 것을 제목이 먼저 말한다 (4장, p.59, §"Architectural Characteristics (Partially)
  Listed").[^richards2025]
- **아키텍처 특성은 복잡도의 넓은 스펙트럼 위에 존재한다** — **모듈성 같은 낮은 수준의 코드
  특성부터 확장성과 탄력성(elasticity) 같은 정교한 운영 관심사까지**다 (4장,
  p.59).[^richards2025]
- **진정한 보편 표준은 없다.** 표준을 성문화하려는 시도가 있어 왔지만, **각 조직이 이 낱말들을
  스스로 해석한다** (4장, p.59).[^richards2025]
  - **게다가 소프트웨어 생태계가 빠르게 바뀌므로 새 개념·낱말·측정·검증이 끊임없이 나타나고,
    그것이 아키텍처 특성을 정의할 새 기회를 준다** (4장, p.59).[^richards2025]
- **부피와 너비 때문에 정량화는 어렵지만 아키텍트는 이것들을 범주로 나눈다.** 이어지는 네 절이
  그 넓은 범주 몇과 각각의 실물을 보인다 (4장, p.59).[^richards2025]

## 운영 아키텍처 특성

**성능·확장성·탄력성·가용성·신뢰성 같은 능력을 덮는다** (4장, p.59, 표 4-1).[^richards2025]
표 4-1이 드는 낱말 일곱과 각각이 묻는 것을 압축하면 이렇다.

| 낱말 | 무엇을 묻는가 |
|---|---|
| 가용성(Availability) | 체계가 얼마 동안 가동돼 있어야 하는가. 24/7이면 장애가 나도 빠르게 되살아날 장치가 있어야 한다 |
| 연속성(Continuity) | 재해 복구 능력 |
| 성능(Performance) | 체계가 얼마나 잘 도는가. 스트레스 테스트·피크 분석·기능 사용 빈도 분석·응답 시간이 재는 길이다 |
| 복구 가능성(Recoverability) | 재해가 났을 때 얼마나 빨리 온라인으로 돌아와야 하는가. 백업 전략과 중복 하드웨어 요구가 여기 든다 |
| 신뢰성/안전성(Reliability/safety) | 페일 세이프여야 하는가, 아니면 생명에 영향을 주는 미션 크리티컬인가. **이진이 아니라 스펙트럼인 일이 잦다** |
| 견고성(Robustness) | 도는 동안 오류와 경계 조건을 다루는 능력 — 인터넷 연결이나 전원이 끊기는 따위 |
| 확장성(Scalability) | 사용자나 요청 수가 늘 때 성능을 내며 도는 능력 |

- **이 갈래가 운영(operations)·데브옵스(DevOps) 관심사와 크게 겹친다**고 저자들이 덧붙인다
  (4장, p.59).[^richards2025]

## 구조 아키텍처 특성

**아키텍트는 올바른 코드 구조에 책임이 있고, 많은 경우 코드 품질 — 모듈성, 읽기 쉬움, 컴포넌트
사이 결합이 얼마나 잘 통제되는가, 그 밖의 내부 품질 평가들 — 에 단독 또는 공동 책임을 진다**
(4장, p.60, 표 4-2).[^richards2025] 표 4-2가 드는 낱말 여덟은 다음을 묻는다.

| 낱말 | 무엇을 묻는가 |
|---|---|
| 구성 가능성(Configurability) | 최종 사용자가 인터페이스로 설정을 얼마나 쉽게 바꾸는가 |
| 확장 가능성(Extensibility) | 기존 기능을 넓히는 변경을 아키텍처가 얼마나 잘 받아들이는가 |
| 설치 용이성(Installability) | 필요한 모든 플랫폼에 얼마나 쉽게 설치되는가 |
| 활용 가능성/재사용(Leverageability/reuse) | 공통 컴포넌트를 여러 제품에 걸쳐 얼마나 활용할 수 있는가 |
| 지역화(Localization) | 입력·조회 화면의 데이터 필드가 여러 언어를 받는가 |
| 유지보수성(Maintainability) | 변경과 개선을 얼마나 쉽게 적용하는가 |
| 이식성(Portability) | 둘 이상의 플랫폼에서 돌 수 있는가 |
| 업그레이드 용이성(Upgradeability) | 서버와 클라이언트를 새 버전으로 얼마나 쉽고 빠르게 올리는가 |

## 클라우드 특성 — 2판 신설

- **저자들이 이 갈래를 생태계 변화의 실물로 든다** — **1판이 나온 시점에는 클라우드 기반 컴퓨팅이
  존재했으나 널리 퍼져 있지 않았고, 2025년 저술 시점에는 대부분의 체계가 적어도 어느 정도는
  클라우드 기반 체계와 상호작용한다** (4장, p.60).[^richards2025]
- 표 4-3이 드는 다섯은 **체계 자신의 능력이 아니라 클라우드 제공자의 능력**을 묻는다는 점에서
  위 두 갈래와 다르다 (4장, p.60, 표 4-3):[^richards2025] **요구에 따른 확장성(on-demand
  scalability)**과 **요구에 따른 탄력성(on-demand elasticity)**, 계산 구역으로 자원을 갈라
  더 회복력 있는 체계를 만드는 **구역 기반 가용성(zone-based availability)**, 그리고 여러
  나라·지역의 데이터를 저장할 법적 능력을 묻는 **지역 기반 프라이버시와 보안(region-based
  privacy and security)**이다 — **많은 나라가 자국민의 데이터가 어디에 있어도 되는지를 법으로
  정하고 역외 저장을 제한하는 일이 잦기 때문**이다.
- **2판에서 저자들이 아키텍처 스타일 장마다 절을 하나씩 더해, 그 스타일이 클라우드 고려 사항을
  어떻게 받아들이고 촉진하는지를 서술한다** (4장, p.60).[^richards2025]

## 횡단 아키텍처 특성

**쉽게 알아볼 수 있는 범주에 들지 않거나 범주화를 거부하면서도 중요한 설계 제약이자 고려 사항을
이루는 것들**이다 (4장, p.61, 표 4-4).[^richards2025] 표 4-4가 드는 아홉은 이렇다.

| 낱말 | 무엇을 묻는가 |
|---|---|
| 접근성(Accessibility) | 색맹·청력 손실 같은 장애가 있는 사용자를 포함해 모든 사용자가 얼마나 쉽게 접근하는가 |
| 보존 가능성(Archivability) | 일정 기간 뒤 데이터를 보관하거나 지우는 일에 걸리는 제약 |
| 인증(Authentication) | 사용자가 자기가 말하는 그 사람인지 확인하는 보안 요구 |
| 인가(Authorization) | 사용자가 애플리케이션 안의 특정 기능만 쓰도록 하는 보안 요구 — 유스케이스·서브시스템·웹 페이지·업무 규칙·필드 수준 따위로 |
| 적법성(Legal) | 체계가 도는 입법적 제약 — GDPR 같은 데이터 보호법, 미국의 사베인스-옥슬리 같은 재무 기록법, 그리고 애플리케이션을 짓거나 배포하는 방식에 걸리는 규제 |
| 프라이버시(Privacy) | DBA와 네트워크 아키텍트를 포함한 사내 직원에게조차 트랜잭션을 암호화하고 숨길 수 있는가 |
| 보안(Security) | 데이터베이스나 내부 체계 간 네트워크 통신의 암호화, 원격 사용자 접근의 인증, 그 밖의 보안 조치에 걸리는 규칙과 제약 |
| 지원 가능성(Supportability) | 어느 수준의 기술 지원이 필요한가. 오류를 디버그하려면 로깅 따위를 어디까지 갖춰야 하는가 |
| 사용성/달성 가능성(Usability/achievability) | 사용자가 애플리케이션으로 목표를 이루려면 어느 정도의 훈련이 필요한가 |

## 낱말들이 부정확하고 겹친다

- **어떤 아키텍처 특성 목록도 필연적으로 불완전하다** — **어떤 소프트웨어 프로젝트든 고유한
  요인에 근거해 아키텍처 특성을 발명할 수 있다.** 그리고 **방금 나열한 낱말 다수가 부정확하고
  애매한데, 때로는 미묘한 뉘앙스 때문이고 때로는 객관적 정의가 없기 때문**이다 (4장,
  p.61).[^richards2025]
- **저자들이 드는 애매함 셋** (4장, p.61):[^richards2025]
  - **상호운용성(interoperability)과 호환성(compatibility)** — 같아 보이고 어떤 체계에서는
    실제로 같지만 갈린다. **상호운용성은 다른 체계와의 통합이 쉽다는 것을 함의하고, 그것은 다시
    공표되고 문서화된 API를 함의한다.** 반면 **호환성은 산업 표준과 도메인 표준에 더 관심을
    둔다.**
  - **학습 용이성(learnability)** — 한 정의는 **"사용자가 소프트웨어 쓰는 법을 얼마나 쉽게
    배우는가"**이고, 다른 정의는 **"체계가 자기 환경을 자동으로 학습해 기계 학습 알고리즘으로
    스스로 설정하거나 스스로 최적화하게 되는 수준"**이다. **같은 낱말이 전혀 다른 것을
    가리킨다.**
  - **가용성과 신뢰성** — 정의가 겹친다. **그런데 TCP의 밑에 있는 인터넷 프로토콜 IP를 보라.
    IP는 *가용*하지만 *신뢰할 수 있지는* 않다** — 패킷이 순서를 어겨 도착할 수 있고 수신자가
    빠진 패킷을 다시 요청해야 할 수 있다.

## ISO 목록과 저자들이 고쳐 쓴 판

- **이 범주들을 정의하는 완전한 표준 목록은 없다.** 국제 표준화 기구(ISO)가 능력별로 조직된
  목록을 펴내고 그것이 저자들의 목록과 겹치지만, **주로 불완전한 범주 목록을 세우는 데
  그친다** (4장, p.62).[^richards2025]
- **저자들이 ISO 정의 일부를 2025년 저술 시점의 관심사에 맞게 낱말을 고치고 범주를 더해 다시
  쓴다.** 그 일곱과 각각이 품는 하위 특성을 압축하면 이렇다 (4장,
  pp.62–63):[^richards2025]

| ISO 범주 | 무엇을 재는가 | 품는 하위 특성 |
|---|---|---|
| 성능 효율(Performance efficiency) | 알려진 조건에서 쓰인 자원의 양 대비 성능 | 시간 거동(time behavior) · 자원 활용(resource utilization) · 용량(capacity) |
| 호환성(Compatibility) | 다른 제품·체계·컴포넌트와 정보를 교환하거나 같은 하드웨어·소프트웨어 환경을 공유하며 제 기능을 하는 정도 | 공존(coexistence) · 상호운용성(interoperability) |
| 사용성(Usability) | 사용자가 의도된 목적으로 체계를 효과적·효율적·만족스럽게 쓸 수 있는가 | 적합성 인지 가능성(appropriateness recognizability) · 학습 용이성(learnability) · 사용자 오류 방지(user error protection) · 접근성(accessibility) |
| 신뢰성(Reliability) | 명시된 조건에서 명시된 기간 동안 기능하는 정도 | 성숙도(maturity) · 가용성(availability) · 내결함성(fault tolerance) · 복구 가능성(recoverability) |
| 보안(Security) | 사람이나 다른 제품·체계가 자기 유형과 인가 수준에 맞는 데이터 접근만 갖도록 정보와 데이터를 보호하는 정도 | 기밀성(confidentiality) · 무결성(integrity) · 부인 방지(nonrepudiation) · 책임 추적성(accountability) · 진정성(authenticity) |
| 유지보수성(Maintainability) | 개발자가 소프트웨어를 개선·교정하거나 환경·요구사항 변화에 맞추는 일의 효과성과 효율성의 정도 | 모듈성(modularity) · 재사용성(reusability) · 분석 가능성(analyzability) · 수정 가능성(modifiability) · 테스트 용이성(testability) |
| 이식성(Portability) | 체계·제품·컴포넌트를 한 하드웨어·소프트웨어·운영 환경에서 다른 환경으로 옮기는 정도 | 적응성(adaptability) · 설치 용이성(installability) · 대체 가능성(replaceability) |

- **ISO 목록의 마지막 항목만 소프트웨어의 기능적 측면을 다룬다** — **기능 적합성(functional
  suitability)**이고, **명시된 조건에서 쓰일 때 명시되고 암시된 필요를 충족하는 기능을 제품이나
  체계가 제공하는 정도**다. 하위는 **기능 완전성(functional completeness)**·**기능
  정확성(functional correctness)**·**기능 적절성(functional appropriateness)** 셋이다 (4장,
  p.63).[^richards2025]

## 기능 적합성은 이 목록에 속하지 않는다

- **저자들이 ISO 목록의 마지막 항목을 기각한다** — **기능 적합성이 이 목록에 속한다고 믿지
  않는다. 그것은 아키텍처 특성을 서술하는 것이 아니라 소프트웨어를 지을 동기가 되는 요구사항을
  서술한다** (4장, p.64).[^richards2025]
  - **이 기각이 위 §"보편 표준이 없다는 전제"의 세 기준 가운데 첫째를 그대로 적용한 것이다** —
    기능 적합성은 도메인 밖의 고려 사항이 아니라 도메인 그 자체다.
- **저자들은 이 기각을 시간의 문제로도 읽는다** — **아키텍처 특성과 문제 도메인의 관계에 대한
  생각이 어떻게 진화해 왔는지를 이것이 예시하고, 그 진화를 7장에서 다룬다** (4장,
  p.64).[^richards2025]

## 표준을 강제할 수 없으니 편재 언어를 세우라

- **저자들이 옆글 하나를 여기 둔다** — **아키텍트들 사이의 꾸준한 좌절의 원천이 그토록 많은
  결정적인 것들에 명확한 정의가 없다는 것이고, 거기에는 소프트웨어 아키텍처라는 활동 자체도
  든다** (4장, p.64, 옆글).[^richards2025]
  - **표준이 없으면 회사들이 흔한 것에 자기 낱말을 붙이게 되고, 그것이 업계 전반의 혼란으로
    이어진다** — **아키텍트들이 불투명한 낱말을 쓰거나, 더 나쁘게는 같은 낱말을 전혀 다른 뜻으로
    쓰기 때문**이다 (4장, p.64, 옆글).[^richards2025]
  - **저자들의 처방은 표준의 강제가 아니다** — **소프트웨어 개발 세계에 표준 명명법을 부과할 수는
    없다. 대신 낱말 때문에 생기는 오해를 피하려면 도메인 주도 설계가 권하는 대로 조직이 직원들
    사이에 편재 언어(ubiquitous language)를 세우고 쓰라**는 것이고, 저자들도 그 조언을 따르고
    권한다 (4장, p.64, 옆글).[^richards2025]
  - **같은 처방이 4장 마지막 절에서 다시 나온다** — **업계가 불변의 아키텍처 특성 목록을 만들
    수는 없지만(새것이 끊임없이 나타나므로) 각 조직은 객관적 정의를 갖춘 자기 목록, 곧 편재
    언어를 만들 수 있다**는 것이다 (4장, p.65).[^richards2025]

## 이 KB의 다른 소스들과 맞대어 본 자리

**모순으로 판정한 쌍이 없다.** `contradicts`를 걸지 않았다.

- **이 KB에 이 어휘가 이미 흩어져 있었고, 이 페이지가 그것들을 한 갈래 표로 묶는 첫 자리다.**
  [비기능 요건](../synthesis/nonfunctional-requirements.md) 허브가 성능·신뢰성·보안·확장성·관측
  가능성·유지보수성으로 절을 가르고 각 절에 페이지를 달아 왔는데, **그 절 구성은 이 KB가
  소스별로 쌓아 온 것이고 어느 소스도 갈래 자체를 선언하지 않았다.** 이 소스가 그 선언을 한다.
  **다만 갈래가 서로 어긋난다** — 허브는 **묻는 물음**으로 가르고 이 소스는 **누가 떠받치는가**
  (운영이냐 코드 구조냐 클라우드 제공자냐 어디에도 안 드느냐)로 가른다.
- **같은 ISO 계열 목록을 다른 소스가 다른 축으로 쓴다.**
  [엔터프라이즈 아키텍처 표준과 비기능 요건 다섯 군](../concepts/enterprise-architecture-standards-and-nfrs.md)이
  안정성·릴리스·운영 효율·상호운용성·보안 다섯 군을 세는데, **그쪽의 가름 기준은 한 문서로
  선언할 요건 묶음**이라 이 소스의 네 갈래와 대응하지 않는다. **어느 쪽도 자기 목록을 완결로
  주장하지 않으므로 사실 충돌이 아니다.**
- **"가용성과 신뢰성이 겹친다"는 관찰에 이 KB가 이미 다른 답을 갖고 있다.**
  [신뢰성과 내결함성](../concepts/reliability-and-fault-tolerance.md)이 결함과 장애를 층으로
  갈라 두 낱말을 구분하는데, **이 소스는 그 구분을 IP 프로토콜 하나로 보인다** — 가용하되
  신뢰할 수 없는 것이 실재한다는 반례다. **같은 방향이고 다른 예시다.**
- **"학습 용이성"의 두 뜻 가운데 기계 학습 쪽이 이 KB의 AI 축과 만난다.** 그쪽 뜻이 가리키는
  자기 설정·자기 최적화는 이 KB에서 아키텍처 축이 아니라 AI 축에 있다. **이 소스는 두 뜻이
  있다는 사실만 적고 어느 쪽을 쓰라고 정하지 않는다.**
- **"조직마다 자기 목록을 만들라"는 처방이 이 KB의 표준 선언 페이지와 같은 방향이다.**
  [아키텍처 표준의 활성화와 집행](../concepts/architecture-standard-enablement-and-enforcement.md)이
  언제 무엇을 표준으로 선언할지를 다루는데, **이 소스는 그 선언의 대상 가운데 낱말의 정의가
  먼저 온다**고 적는 셈이다.
