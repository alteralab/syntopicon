하나의 질문: **데브옵스가 소프트웨어에 한 일을 데이터에 하려면 무엇을 옮기고 무엇을 새로
만들어야 하는가.**

## 무엇을 무엇에 옮긴 것인가

- 정의 — **DataOps는 애자일 방법론, 데브옵스, 통계적 공정 관리(statistical process control,
  SPC)의 모범 실무를 데이터에 매핑한다. 데브옵스가 소프트웨어 제품의 릴리스와 품질을 개선하는
  것을 노린다면, DataOps는 데이터 제품에 대해 같은 일을 한다** (2장, p.59).[^reis2022]
- 데이터 제품이 다른 이유 — **데이터 제품은 데이터가 쓰이는 방식 때문에 소프트웨어 제품과
  다르다. 소프트웨어 제품은 최종 사용자에게 특정 기능과 기술적 특징을 제공한다. 대조적으로
  데이터 제품은 건전한 업무 로직과 지표를 중심으로 지어지며, 그 사용자는 결정을 내리거나
  자동화된 행동을 수행하는 모델을 짓는다** (2장, p.60).[^reis2022]
- 그래서 요구되는 것 — **데이터 엔지니어는 소프트웨어 제품을 짓는 기술적 측면과, 훌륭한 데이터
  제품을 만들어 낼 업무 로직·품질·지표를 모두 이해해야 한다** (2장, p.60).[^reis2022]
- 계보 — **데브옵스처럼 DataOps도 린 제조와 공급망 관리에서 많이 빌려 오며, 사람·프로세스·
  기술을 섞어 가치 도달 시간을 줄인다** (2장, p.60).[^reis2022]
- 인용되는 정의 — Data Kitchen에 따르면 **DataOps는 다음을 가능하게 하는 기술적 실무·워크플로·
  문화 규범·아키텍처 패턴의 모음이다** (2장, p.60):[^reis2022]
  - **점점 빨라지는 속도로 고객에게 새 통찰을 전달하는 빠른 혁신과 실험**
  - **극히 높은 데이터 품질과 매우 낮은 오류율**
  - **사람·기술·환경의 복잡한 배열에 걸친 협업**
  - **결과의 명확한 측정·모니터링·투명성**

## 문화 습관이 먼저다

- 순서 — **무엇보다 먼저 DataOps는 문화적 습관의 집합이다. 데이터 엔지니어링 팀은 업무와
  소통하고 협업하며, 사일로를 허물고, 성공과 실수에서 지속적으로 배우고, 빠르게 반복하는
  주기를 채택해야 한다. 이 문화적 습관이 자리 잡을 때에만 팀은 기술과 도구에서 최선의 결과를
  얻을 수 있다** (2장, p.60).[^reis2022]
- 도입 경로가 성숙도에 달렸다 — **회사에 기존 데이터 인프라나 실무가 없다면 DataOps는 첫날부터
  구워 넣을 수 있는 그린필드 기회다. DataOps가 없는 기존 프로젝트나 인프라가 있다면 데이터
  엔지니어는 워크플로에 DataOps를 더하기 시작할 수 있다. 우리는 먼저 관측 가능성과 모니터링에서
  시작해 시스템 성능에 대한 창을 얻은 다음 자동화와 사고 대응을 더할 것을 제안한다** (2장,
  p.60).[^reis2022]
- 세 기둥 — **DataOps는 세 핵심 기술 요소를 갖는다: 자동화, 모니터링과 관측 가능성, 사고
  대응** (2장, p.61).[^reis2022]

## 자동화

- 무엇을 주는가 — **자동화는 DataOps 프로세스의 신뢰성과 일관성을 가능하게 하고, 데이터
  엔지니어가 새 제품 기능과 기존 워크플로의 개선을 빠르게 배포하게 해 준다** (2장,
  p.61).[^reis2022]
- 구성 — **DataOps 자동화는 데브옵스와 비슷한 프레임워크·워크플로를 가지며 변경 관리(환경·코드·
  데이터 버전 관리), 지속적 통합·지속적 배포(CI/CD), 코드로서의 설정으로 이뤄진다. 데브옵스처럼
  DataOps 실무도 기술과 시스템(데이터 파이프라인·오케스트레이션 등)의 신뢰성을 모니터링·
  유지하되, 데이터 품질·데이터/모델 드리프트·메타데이터 무결성 등을 검사하는 차원이 더해진다**
  (2장, p.61).[^reis2022]
- 성숙 곡선의 실물 — cron에서 오케스트레이션 프레임워크로, 다시 자동 배포로 가는 서사는
  [배치 워크플로와 DAG](../concepts/batch-workflows-and-dags.md)에 합류시켰다. 그 다음 단계는
  다음과 같다 — **데이터 과학자가 결국 망가진 DAG를 배포해 Airflow 웹 서버를 내리고 데이터
  팀을 운영상 눈멀게 한다. 충분한 두통 끝에 팀원들은 수동 DAG 배포를 더는 허용하지 말아야
  함을 깨닫는다. 다음 운영 성숙 국면에서 그들은 자동화된 DAG 배포를 채택한다. DAG는 배포 전에
  테스트되고, 모니터링 프로세스가 새 DAG가 제대로 돌기 시작하는지 확인한다. 더해서 데이터
  엔지니어는 설치가 검증될 때까지 새 파이썬 의존성의 배포를 막는다** (2장, pp.61–62).[^reis2022]
- 멈추지 않는다 — **DataOps 선언문의 신조 중 하나는 "변화를 받아들여라(Embrace change)"다.
  이는 변화를 위한 변화가 아니라 목표 지향적 변화를 뜻한다. 자동화 여정의 각 단계마다 운영
  개선의 기회가 존재한다. 요점은 엔지니어가 자기 작업 부하를 줄이고 업무에 전달하는 가치를
  높일 자동화 개선을 끊임없이 구현하려 한다는 것이다** (2장, p.62).[^reis2022]

## 관측 가능성과 모니터링

- 왜 필요한가 — **우리가 고객에게 말하듯 "데이터는 조용한 살인자다." 나쁜 데이터가 몇 달, 몇
  년 동안 리포트에 남아 있는 사례를 수없이 봤다. 임원이 이 나쁜 데이터로 핵심 결정을 내리고
  오류는 한참 뒤에야 발견된다. 결과는 대개 나쁘고 때로 사업에 파국적이다. 이니셔티브가
  훼손되고 파괴되며 수년의 작업이 낭비된다. 최악의 경우 나쁜 데이터가 회사를 재정 파탄으로
  이끌 수 있다** (2장, p.62).[^reis2022]
- 또 다른 실패 서사 — **리포트용 데이터를 만드는 시스템이 무작위로 작동을 멈춰 리포트가 며칠
  지연되는 경우다. 데이터 팀은 이해관계자가 왜 리포트가 늦거나 낡은 정보를 내는지 물을 때까지
  모른다. 결국 여러 이해관계자가 핵심 데이터 팀의 역량에 대한 신뢰를 잃고 자기들만의 분파 팀을
  꾸리기 시작한다. 결과는 불안정한 시스템 여럿, 일관되지 않은 리포트, 사일로다** (2장,
  p.62).[^reis2022]
- 무엇을 갖춰야 하는가 — **관측 가능성(observability)·모니터링·로깅·경보·추적은 전부 데이터
  엔지니어링 수명 주기를 따라 생기는 문제를 앞질러 잡는 데 결정적이다. 모니터링되는 이벤트가
  선을 벗어났는지, 어떤 사고가 대응할 값어치가 있는지 이해하기 위해 SPC를 통합할 것을
  권한다** (2장, p.62).[^reis2022]
- DODD — **Petrella의 DODD 방법은 데이터 관측 가능성을 생각하는 훌륭한 프레임워크를 제공하며,
  소프트웨어 엔지니어링의 테스트 주도 개발(TDD)과 매우 비슷하다** (2장, p.62).[^reis2022]
  인용된 목적 진술은 다음과 같다 (2장, p.63):[^reis2022]

  > The purpose of DODD is to give everyone involved in the data chain visibility into the
  > data and data applications so that everyone involved in the data value chain has the
  > ability to identify changes to the data or data applications at every step—from
  > ingestion to transformation to analysis—to help troubleshoot or prevent data issues.
  > DODD focuses on making data observability a first-class consideration in the data
  > engineering lifecycle.

## 사고 대응

- 전제 — **DataOps를 쓰는 고기능 데이터 팀은 새 데이터 제품을 빠르게 출하할 수 있다. 그러나
  실수는 불가피하게 일어난다. 시스템에 다운타임이 생기거나, 새 데이터 모델이 하류 리포트를
  깨뜨리거나, ML 모델이 낡아 나쁜 예측을 내는 등 수많은 문제가 수명 주기를 끊을 수 있다** (2장,
  p.63).[^reis2022]
- 정의 — **사고 대응(incident response)은 앞서 언급한 자동화와 관측 가능성 능력을 써서 사고의
  근본 원인을 빠르게 식별하고 가능한 한 신뢰할 수 있고 빠르게 해결하는 것이다** (2장,
  p.63).[^reis2022]
- 기술만이 아니다 — **사고 대응은 기술과 도구에 관한 것만이 아니다. 도구가 유익하기는 하지만,
  그것은 데이터 엔지니어링 팀 안에서도 조직 전반에서도 열려 있고 비난하지 않는(blameless)
  소통에 관한 것이기도 하다. AWS CTO Werner Vogels가 남긴 유명한 말처럼 "모든 것은 늘
  깨진다." 데이터 엔지니어는 재난에 대비하고 가능한 한 신속하고 효율적으로 대응할 준비가
  돼 있어야 한다** (2장, p.63).[^reis2022]
- 선제성이 신뢰를 만든다 — **데이터 엔지니어는 업무가 보고하기 전에 문제를 선제적으로 찾아야
  한다. 실패는 일어나고, 이해관계자나 최종 사용자가 문제를 보면 그들이 그것을 제시할 것이다.
  그들은 그렇게 하는 것을 불쾌해할 것이다. 그들이 그 문제를 팀에 제기하러 갔을 때 이미 활발히
  해결 작업이 이뤄지고 있는 것을 보면 느낌이 다르다. 최종 사용자로서 어느 팀의 상태를 더
  신뢰하겠는가? 신뢰는 쌓는 데 오래 걸리고 몇 분 만에 잃을 수 있다** (2장, p.63).[^reis2022]
- **사고 대응은 사고에 사후적으로 대응하는 것인 만큼이나 그것이 일어나기 전에 선제적으로 다루는
  것이기도 하다** (2장, p.63).[^reis2022]

## 현재 상태

- 미완 — **현시점에서 DataOps는 여전히 진행 중인 작업이다. 실무자들은 데브옵스 원칙을 데이터
  도메인에 적응시키고 DataOps 선언문 등을 통해 초기 비전을 그리는 일을 잘 해냈다. 데이터
  엔지니어는 모든 작업에서 DataOps 실무를 높은 우선순위로 두는 것이 좋다. 선행 노력은 제품의
  빠른 전달, 데이터의 더 나은 신뢰성과 정확성, 업무 전반의 더 큰 가치를 통해 상당한 장기
  보상을 볼 것이다** (2장, p.63).[^reis2022]
- 성숙도의 격차 — **데이터 엔지니어링의 운영 상태는 소프트웨어 엔지니어링에 견주면 여전히 꽤
  미성숙하다. 많은 데이터 엔지니어링 도구, 특히 레거시 모놀리스는 자동화 우선이 아니다. 최근
  데이터 엔지니어링 수명 주기 전반에 자동화 모범 실무를 채택하려는 운동이 일어났다. Airflow
  같은 도구가 새 세대의 자동화·데이터 관리 도구를 위한 길을 닦았다** (2장,
  pp.63–64).[^reis2022]
- 자기 규정 — **우리가 DataOps에 대해 서술하는 일반적 실무는 지향적(aspirational)이며, 회사가
  오늘 이용 가능한 도구와 지식을 감안해 가능한 한 최대한 채택해 보기를 제안한다** (2장,
  p.64).[^reis2022]
