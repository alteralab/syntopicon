# 데이터플로 엔진

- [공통점 하나](#공통점-하나)

하나의 질문: **데이터플로 엔진은 MapReduce의 무엇을 바꾸어 더 빨라지는가.**

## 공통점 하나

- **MapReduce의 문제 일부를 고치기 위해 분산 배치 계산을 위한 여러 새 실행 엔진이 개발됐고, 그중
  가장 잘 알려진 것이 Spark와 Flink다. 그들은 다르게 설계됐지만 한 가지 공통점이 있다: 그들은
  워크플로 전체를 독립적인 서브잡으로 쪼개는 대신 하나의 잡으로 다룬다** (11장,
  p.468).[^kleppmann2026]
- 이름의 유래 — **여러 처리 단계를 거치는 데이터의 흐름을 명시적으로 모델링하므로 이 시스템들은
  데이터플로 엔진(dataflow engines)으로 알려져 있다** (11장, p.468).[^kleppmann2026]
- 계보 — **이 스타일의 처리 엔진은 Dryad와 Nephele 같은 연구 시스템에 기반한다** (11장,
  p.469).[^kleppmann2026]

## 무엇이 달라지는가

- **MapReduce처럼 그들도 한 번에 한 레코드를 처리하는 사용자 정의 함수를 반복 호출하는 저수준
  API를 지원하지만, join이나 group by 같은 더 고수준 연산자도 제공한다. 그들은 입력을 샤딩해
  작업을 병렬화하고, 한 태스크의 출력을 네트워크로 복사해 다른 태스크의 입력이 되게 한다.
  MapReduce와 달리 연산자는 map과 reduce가 교대하는 엄격한 역할을 취할 필요가 없고 대신 더 유연한
  방식으로 조립될 수 있다** (11장, p.468).[^kleppmann2026]
- 무엇으로 계산을 표현하는가 — **이 데이터플로 API는 일반적으로 관계형 스타일의 빌딩 블록으로
  계산을 표현한다: 어떤 필드의 값으로 데이터셋을 조인하기, 키로 튜플을 그룹핑하기, 조건으로
  필터링하기, 세기·합하기 등의 함수로 튜플을 집계하기. 내부적으로 이 연산들은 셔플 알고리즘으로
  구현된다** (11장, p.468).[^kleppmann2026] 그 셔플은
  [셔플](../concepts/shuffle-algorithm.md)에 있다.

## MapReduce 대비 여섯 가지 이점

- **그것은 MapReduce 모델에 비해 여러 이점을 제공한다** (11장,
  p.469):[^kleppmann2026]
  - **정렬 같은 비싼 작업이 모든 map과 reduce 단계 사이에서 기본으로 언제나 일어나는 대신, 그것이
    필요한 자리에서만 수행되면 된다.**
  - **데이터셋의 샤딩을 바꾸지 않는 연산자(map이나 filter 같은)가 연달아 여럿 있으면, 그것들이
    하나의 태스크로 합쳐져 데이터 복사 오버헤드를 줄일 수 있다.**
  - **워크플로의 모든 조인과 데이터 의존이 명시적으로 선언되므로 스케줄러는 어느 데이터가 어디에
    필요한지 개관을 갖고, 그래서 지역성 최적화를 할 수 있다. 예컨대 어떤 데이터를 소비하는 태스크를
    그것을 생산하는 태스크와 같은 기계에 놓아, 데이터가 네트워크로 복사되지 않고 공유 메모리 버퍼로
    교환되게 시도할 수 있다.**
  - **연산자 사이의 중간 상태는 메모리에 유지하거나 로컬 디스크에 쓰는 것으로 보통 충분한데, 이는
    그것을 분산 파일시스템이나 오브젝트 스토어에 쓰는 것(거기서는 여러 기계로 복제되고 각 레플리카의
    디스크에 쓰여야 한다)보다 I/O가 적다. MapReduce는 이미 매퍼 출력에 이 최적화를 쓰지만, 데이터플로
    엔진은 그 발상을 모든 중간 상태로 일반화한다.**
  - **연산자는 자기 입력이 준비되는 즉시 실행을 시작할 수 있다; 다음 단계가 시작하기 전에 선행
    단계 전체가 끝나기를 기다릴 필요가 없다.**
  - **기존 프로세스를 재사용해 새 연산자를 돌릴 수 있어, MapReduce(태스크마다 새 JVM을 띄운다)에
    비해 시작 오버헤드가 줄어든다.**
- 결론 — **MapReduce 워크플로와 같은 계산을 데이터플로 엔진으로 구현할 수 있고, 여기 서술된
  최적화 덕분에 그들은 보통 상당히 더 빠르게 실행된다** (11장, p.469).[^kleppmann2026]
