하나의 질문: **네트워크 너머로 노출하는 API를 어떻게 정의하고, 그것을 어떻게 바꿔 나가는가.**

## 서비스란 무엇인가

- 기본 배치 — **네트워크로 통신해야 하는 프로세스가 있을 때 그 통신을 몇 가지 방식으로 배치할 수
  있다. 가장 흔한 배치는 클라이언트와 서버라는 두 역할을 두는 것이다. 서버는 네트워크로 API를
  노출하고 클라이언트는 서버에 연결해 그 API에 요청을 보낼 수 있다. 서버가 노출하는 API를
  서비스(service)라 한다** (5장, p.180).[^kleppmann2026]
- 웹이 그 사례다 — **웹이 이렇게 작동한다: 클라이언트(웹 브라우저)가 웹 서버에 요청을 보내고, HTML·
  CSS·자바스크립트·이미지 등을 내려받는 GET 요청과 서버에 데이터를 제출하는 POST 요청을 한다. API는
  표준화된 프로토콜과 데이터 형식의 집합(HTTP·URL·SSL/TLS·HTML 등)으로 이뤄진다. 웹 브라우저와 웹
  서버와 웹사이트 저자가 대체로 이 표준에 동의하기 때문에 어떤 웹 브라우저로도 어떤 웹사이트든
  접근할 수 있다(적어도 이론상으로는)** (5장, p.180).[^kleppmann2026]
- 브라우저만 클라이언트인 것이 아니다 — **모바일 기기와 데스크톱 컴퓨터에서 도는 네이티브 앱이 흔히
  서버와 통신하고, 웹 브라우저 안에서 도는 클라이언트 쪽 자바스크립트 애플리케이션도 HTTP 요청을 할
  수 있다. 이 경우 서버의 응답은 보통 사람에게 표시할 HTML이 아니라 클라이언트 쪽 애플리케이션 코드가
  더 처리하기 편한 인코딩의 데이터(대개 JSON)다. HTTP가 전송 프로토콜로 쓰이더라도 그 위에 구현된
  API는 애플리케이션별이고, 클라이언트와 서버가 그 API의 세부에 합의해야 한다** (5장,
  p.180).[^kleppmann2026]

## 서비스와 데이터베이스의 차이

- 닮은 곳과 갈리는 곳 — **어떤 면에서 서비스는 데이터베이스와 비슷하다: 보통 클라이언트가 데이터를
  제출하고 질의할 수 있게 한다. 그러나 데이터베이스가 질의 언어로 임의의 질의를 허용하는 반면, 서비스는
  서비스의 업무 로직(애플리케이션 코드)이 미리 정한 입력과 출력만 허용하는 애플리케이션별 API를
  노출한다** (5장, p.180).[^kleppmann2026]
- 그 제약이 값어치다 — **이 제약은 어느 정도의 캡슐화를 제공한다: 서비스는 클라이언트가 무엇을 할 수
  있고 없는지에 세밀한 제약을 부과할 수 있다** (5장, p.180).[^kleppmann2026]
- 설계 목표 — **서비스 지향/마이크로서비스 아키텍처의 핵심 설계 목표는 서비스를 독립적으로 배포
  가능하고 진화 가능하게 만듦으로써 애플리케이션을 바꾸고 유지보수하기 쉽게 만드는 것이다. 흔한
  원칙은 각 서비스가 한 팀에 의해 소유돼야 하고 그 팀이 다른 팀과 조율할 필요 없이 서비스의 새
  버전을 자주 릴리스할 수 있어야 한다는 것이다** (5장, p.180).[^kleppmann2026]
- 그래서 인코딩에 요구가 생긴다 — **따라서 서버와 클라이언트의 옛 버전과 새 버전이 동시에 돌고 있을
  것을 예상해야 하며, 그래서 서버와 클라이언트가 쓰는 데이터 인코딩은 서비스 API의 버전들에 걸쳐
  호환돼야 한다. API가 호환으로 남는 한 팀은 자기 시스템을 원하는 방식으로 수정할 자유가 있다. 이
  성질은 개발자가 데이터·서비스·심지어 시스템 전체의 내부 마이그레이션을 하기 훨씬 쉽게 만든다**
  (5장, pp.180–181).[^kleppmann2026]

## 웹 서비스가 쓰이는 세 맥락

- 이름의 정의와 오해 — **HTTP가 서비스와 이야기하는 밑에 깔린 프로토콜로 쓰이면 그것을 웹
  서비스(web service)라 한다. 이 용어는 아마 약간 잘못된 이름인데, 웹 서비스가 웹에서만이 아니라 여러
  맥락에서 쓰이기 때문이다** (5장, p.181).[^kleppmann2026]
- 세 맥락 (5장, p.181):[^kleppmann2026]
  - **사용자 기기에서 도는 클라이언트 애플리케이션(모바일 기기의 네이티브 앱이나 브라우저의
    자바스크립트 웹 앱 등)이 HTTP로 서비스에 요청하는 것. 이 요청은 보통 공개 인터넷을 지난다.**
  - **한 서비스가 같은 조직이 소유한 다른 서비스에 요청하는 것. 흔히 같은 사설 네트워크 안에 있으며
    서비스 지향/마이크로서비스 아키텍처의 일부다.**
  - **한 서비스가 다른 조직이 소유한 서비스에 요청하는 것. 보통 인터넷을 거친다. 이는 조직들의
    백엔드 시스템 사이 데이터 교환에 쓰인다. 이 범주에는 신용카드 처리 시스템이나 사용자 데이터에
    대한 공유 접근을 위한 OAuth처럼 온라인 서비스가 제공하는 공개 API가 포함된다.**

## REST와 IDL

- **가장 인기 있는 서비스 설계 철학은 REST이며 HTTP의 원칙 위에 세워진다. REST는 단순한 데이터
  형식, 리소스 식별에 URL 쓰기, 캐시 제어·인증·콘텐츠 타입 협상에 HTTP 기능 쓰기를 강조한다. REST의
  원칙에 따라 설계된 API를 RESTful하다고 한다** (5장, p.181).[^kleppmann2026]
- 그것만으로는 부족하다 — **웹 서비스 API를 호출해야 하는 코드는 어떤 HTTP 엔드포인트에 질의할지,
  어떤 데이터 형식을 보내고 응답으로 기대할지를 알아야 한다. 서비스가 RESTful 설계 원칙을 채택하더라도
  클라이언트는 어떻게든 이 세부를 알아내야 한다** (5장, p.181).[^kleppmann2026]
- 그래서 IDL이 온다 — **서비스 개발자는 흔히 IDL을 써서 서비스의 API 엔드포인트와 데이터 모델을
  정의·문서화하고 시간에 걸쳐 진화시킨다. 다른 개발자는 그 서비스 정의를 써서 서비스에 어떻게 질의할지
  정할 수 있다. 가장 인기 있는 서비스 IDL 둘은 JSON을 주고받는 웹 서비스에 쓰이는 OpenAPI(Swagger로도
  알려져 있다)와 gRPC 서비스에 쓰이는 프로토콜 버퍼다** (5장, p.181).[^kleppmann2026]
- **개발자는 보통 OpenAPI 서비스 정의를 JSON이나 YAML로 쓴다. 그 서비스 정의는 개발자가 서비스
  엔드포인트·문서·버전·데이터 모델 등을 정의할 수 있게 한다. 프로토콜 버퍼 서비스 정의는 앞서 본 IDL을
  쓴다** (5장, p.181).[^kleppmann2026] YAML로 쓴 OpenAPI 서비스 정의의 예다 (5장,
  p.182):[^kleppmann2026]

  ```yaml
  openapi: 3.0.0
  info:
    title: Ping, Pong
    version: 1.0.0
  servers:
    - url: http://localhost:8080
  paths:
    /ping:
      get:
         summary: Given a ping, returns a pong message
         responses:
           '200':
             description: A pong
             content:
               application/json:
                  schema:
                    type: object
                    properties:
                      message:
                        type: string
                        example: Pong!
  ```

## 서비스 프레임워크

- 정의를 써도 코드는 남는다 — **설계 철학과 IDL을 채택하더라도 개발자는 여전히 서비스의 API 호출을
  구현하는 코드를 써야 한다. Spring Boot·FastAPI·gRPC 같은 서비스 프레임워크가 이 수고를 단순화하려고
  흔히 채택된다. 서비스 프레임워크는 개발자가 각 API 엔드포인트의 업무 로직을 쓰는 데 집중하게 하고
  프레임워크 코드가 라우팅·지표·캐싱·인증 등을 처리하게 한다** (5장, p.182).[^kleppmann2026]
- 정의와 코드의 선후가 프레임워크마다 갈린다 — **많은 프레임워크가 서비스 정의와 서버 코드를 함께
  묶는다. 인기 있는 파이썬 FastAPI 프레임워크 같은 어떤 경우에는 서버를 코드로 쓰고 IDL이 자동
  생성된다. gRPC 같은 다른 경우에는 서비스 정의를 먼저 쓰고 서버 코드 뼈대가 생성된다. 두 접근 모두
  개발자가 서비스 정의에서 여러 언어의 클라이언트 라이브러리와 SDK를 생성할 수 있게 한다. 코드 생성
  외에도 Swagger 같은 IDL 도구는 문서를 생성하고, 스키마 변경 호환성을 검증하고, 개발자가 서비스를
  질의·테스트할 GUI를 제공할 수 있다** (5장, pp.182–183).[^kleppmann2026]

## RPC 인코딩의 진화와 API 버저닝

- 서비스 쪽 데이터플로에는 단순화 가정이 하나 붙는다 — **진화성을 위해 RPC 클라이언트와 서버가
  독립적으로 바뀌고 배포될 수 있는 것이 중요하다. 데이터베이스를 거치는 데이터 흐름에 비해 서비스를
  거치는 데이터 흐름에서는 단순화 가정을 하나 할 수 있다: 모든 서버가 먼저 갱신되고 모든 클라이언트가
  나중에 갱신된다고 가정하는 것이 합리적이다. 따라서 요청에는 후진 호환만, 응답에는 전진 호환만
  필요하다** (5장, p.186).[^kleppmann2026]
- 호환성은 인코딩에서 상속된다 — **RPC 스킴의 후진·전진 호환 성질은 그것이 쓰는 인코딩이 무엇이든
  그로부터 상속된다** (5장, p.186):[^kleppmann2026]
  - **gRPC(프로토콜 버퍼)와 Avro RPC는 각 인코딩 형식의 호환성 규칙에 따라 진화할 수 있다.**
  - **RESTful API는 응답에 JSON을, 요청에 JSON이나 URI 인코딩/폼 인코딩 요청 파라미터를 쓰는 것이 가장
    흔하다. 선택적 요청 파라미터를 더하는 것과 응답 객체에 새 필드를 더하는 것은 보통 호환성을 유지하는
    변경으로 간주된다.**
- 조직 경계가 문제를 어렵게 만든다 — **서비스 호환성은 RPC가 흔히 조직 경계를 넘는 통신에 쓰인다는
  사실 때문에 더 어려워지는데, 서비스 제공자가 자기 클라이언트를 통제하지 못하고 업그레이드를 강제할
  수 없기 때문이다. 따라서 호환성은 오랫동안, 아마 무기한 유지돼야 한다. 호환성을 깨는 변경이
  필요하면 서비스 제공자는 결국 여러 버전의 서비스 API를 나란히 유지하는 일이 잦다** (5장,
  p.186).[^kleppmann2026]
- 버저닝 방법에는 합의가 없다 — **API 버저닝이 어떻게 작동해야 하는지(곧 클라이언트가 어느 버전의
  API를 쓰고 싶은지 어떻게 나타내는지)에 대한 합의가 없다. RESTful API에서 흔한 접근은 URL이나 HTTP
  `Accept` 헤더에 버전 번호를 쓰는 것이다. 클라이언트를 식별하는 데 API 키를 쓰는 서비스라면 또 하나의
  선택지는 클라이언트가 요청한 API 버전을 서버에 저장하고 별도의 관리 인터페이스로 이 버전 선택을
  갱신하게 하는 것이다** (5장, p.186).[^kleppmann2026]

## 데이터 반입 쪽에서 본 API

앞 절들이 API를 **설계하고 진화시키는 쪽**의 문제로 다룬다면, 데이터 엔지니어링 개론은 같은
것을 **남이 만든 API에서 데이터를 끌어와야 하는 쪽**의 문제로 놓는다.

- API의 현재 위상 — **API는 이제 클라우드에서, SaaS 플랫폼을 위해, 그리고 내부 회사 시스템
  사이에서 데이터를 교환하는 표준적이고 만연한 방법이다. 웹 전반에 여러 유형의 API 인터페이스가
  존재하지만 우리는 주로 HTTP를 중심으로 지어진 것들에 관심이 있다 — 웹과 클라우드에서 가장
  인기 있는 유형이다** (5장, p.174).[^reis2022]
- REST가 지배적인 패러다임이다 — **먼저 현재 지배적인 API 패러다임인 REST를 이야기할 것이다.
  4장에서 언급했듯 REST는 표현 상태 전이(representational state transfer)를 뜻한다. 이 HTTP
  웹 API를 짓기 위한 실무와 철학의 집합은 2000년에 Roy Fielding이 박사 학위 논문에서 제시했다.
  REST는 GET·PUT 같은 HTTP 동사를 중심으로 지어져 있으나, 실무에서 현대 REST는 원래 논문이
  개괄한 동사 매핑 중 소수만 쓴다** (5장, p.174).[^reis2022]
- 무상태성이 핵심 아이디어다 — **REST의 주요 아이디어 중 하나는 상호작용이 무상태(stateless)
  라는 것이다. Linux 터미널 세션과 달리 작업 디렉토리 같은 결부된 상태 변수를 가진 세션의
  관념이 없다. 각 REST 호출은 독립적이다. REST 호출은 시스템의 상태를 바꿀 수 있지만 이
  변경은 전역적이며 현재 세션이 아니라 전체 시스템에 적용된다** (5장, p.174).[^reis2022]
- 그래서 실무 부담이 남는다 — **비판자들은 REST가 결코 완전한 명세가 아니라고 지적한다. REST는
  상호작용의 기본 속성을 규정하지만 API를 활용하는 개발자는 애플리케이션을 짓거나 데이터를
  효과적으로 끌어오기 위해 상당한 양의 도메인 지식을 얻어야 한다** (5장, p.175).[^reis2022]
- 추상화 수준의 편차 — **API 추상화 수준에서 큰 변이를 본다. 어떤 경우 API는 사용자 요청으로부터
  시스템을 보호하는 데 요구되는 최소 기능을 제공하는, 내부에 대한 얇은 래퍼일 뿐이다. 다른
  예에서 REST 데이터 API는 분석 애플리케이션을 위해 데이터를 준비하고 고급 리포팅을 지원하는
  공학의 걸작이다** (5장, p.175).[^reis2022]
- 반입 파이프라인을 단순하게 만든 발전 둘 (5장, p.175):[^reis2022]
  - **첫째, 데이터 제공자가 여러 언어, 특히 파이썬으로 클라이언트 라이브러리를 자주 공급한다.
    클라이언트 라이브러리는 API 상호작용 코드를 짓는 보일러플레이트 노동의 상당 부분을
    제거한다. 클라이언트 라이브러리는 인증 같은 결정적 세부를 다루고 기본 메서드를 접근 가능한
    클래스로 매핑한다.**
  - **둘째, API와 상호작용하고 데이터 동기화를 관리하는 다양한 서비스와 오픈 소스 라이브러리가
    등장했다. 많은 SaaS와 오픈 소스 벤더가 흔한 API용 기성 커넥터를 제공한다. 플랫폼은 또한
    필요에 따라 맞춤 커넥터를 짓는 과정을 단순화한다.**
- 그래도 배관은 남는다 — **클라이언트 라이브러리나 즉시 쓸 수 있는 커넥터 지원이 없는 데이터
  API가 많다. 이 책 전반에서 강조하듯 엔지니어는 기성 도구를 써서 무차별적 중노동을 줄이는 것이
  좋다. 그러나 저수준 배관 작업은 여전히 많은 자원을 소비한다. 사실상 어떤 큰 회사에서든 데이터
  엔지니어는 API에서 데이터를 끌어오는 맞춤 코드를 쓰고 유지보수하는 문제를 다뤄야 하며, 이는
  제공되는 데이터의 구조를 이해하고, 적절한 데이터 추출 코드를 개발하고, 적합한 데이터 동기화
  전략을 결정할 것을 요구한다** (5장, p.175).[^reis2022]

## 웹훅 — 방향이 뒤집힌 API

- 정의 — **웹훅(webhooks)은 단순한 이벤트 기반 데이터 전송 패턴이다. 데이터 원천은 애플리케이션
  백엔드·웹 페이지·모바일 앱일 수 있다. 지정된 이벤트가 원천 시스템에서 일어나면 이것이 데이터
  소비자가 호스팅하는 HTTP 엔드포인트에 대한 호출을 촉발한다** (5장, p.176).[^reis2022]
- 왜 "역 API"인가 — **연결이 원천 시스템에서 데이터 싱크로 간다는 점에 주목하라 — 전형적 API의
  반대다. 이 이유로 웹훅은 흔히 역 API(reverse APIs)라 불린다** (5장, p.176).[^reis2022]
- 엔드포인트가 하는 일 — **엔드포인트는 POST 이벤트 데이터로 다양한 것을 할 수 있다 — 잠재적으로
  하류 프로세스를 촉발하거나 미래 사용을 위해 데이터를 저장한다. 분석 목적에서 우리는 이 이벤트를
  수집하는 데 관심이 있다. 엔지니어는 흔히 메시지 큐를 써서 높은 속도와 볼륨으로 데이터를
  반입한다** (5장, p.176).[^reis2022]

## gRPC

- RPC부터 — **원격 프로시저 호출(remote procedure call, RPC)은 분산 컴퓨팅에서 흔히 쓰인다.
  그것은 원격 시스템에서 프로시저를 돌리도록 허용한다** (5장, p.176).[^reis2022] 그 배치가
  왜 어려운지는 [원격 프로시저 호출의 문제](../concepts/remote-procedure-call-problems.md)에 있다.
- gRPC의 내력 — **gRPC는 2015년 구글에서 내부적으로 개발되고 나중에 오픈 표준으로 공개된 원격
  프로시저 호출 라이브러리다. 구글 안에서의 사용만으로도 우리 논의에 포함될 자격이 충분하다.
  Google Ads와 GCP 같은 많은 구글 서비스가 gRPC API를 제공한다. gRPC는 역시 구글이 개발한
  Protocol Buffers 오픈 데이터 직렬화 표준을 중심으로 지어져 있다** (5장, p.176).[^reis2022]
  그 직렬화 형식은 [프로토콜 버퍼와 필드 태그](../concepts/protocol-buffers-encoding.md)에 있다.
- 무엇을 강조하는가 — **gRPC는 HTTP/2 위에서 효율적인 양방향 데이터 교환을 강조한다.
  효율(efficiency)은 CPU 이용률·전력 소비·배터리 수명·대역폭 같은 측면을 가리킨다. GraphQL처럼
  gRPC는 REST보다 훨씬 구체적인 기술 표준을 부과하며, 따라서 공통 클라이언트 라이브러리의 사용을
  허용하고 엔지니어가 어떤 gRPC 상호작용 코드에도 적용될 기술 집합을 개발하도록 허용한다** (5장,
  p.176).[^reis2022]
