하나의 질문: **브로커를 프로덕션에 올리기 전에 OS·JVM·물리 배치에서 무엇을 맞춰야
하는가.** 대부분의 리눅스 배포판은 기본 커널 설정으로도 대체로 잘 돌지만, 카프카 브로커의
성능을 개선하는 몇 가지 변경이 있다 — 주로 **가상 메모리와 네트워킹 서브시스템, 그리고 로그
세그먼트를 저장하는 디스크 마운트 포인트**에 관한 것이다 (2장, pp.38–39).[^shapira2021]

## 가상 메모리

- 리눅스 가상 메모리 시스템은 워크로드에 맞춰 자동 조정되지만, **스왑 공간과 더티 페이지를
  다루는 방식을 카프카 워크로드에 맞게 조정할 수 있다** (2장, p.39).[^shapira2021]
- 스와핑에 대한 원칙은 단호하다 — **처리량이 중요한 애플리케이션이 대개 그렇듯, 어떤 대가를
  치르더라도 스와핑을 (거의) 피하는 것이 최선이다.** 메모리 페이지가 디스크로 스왑되는
  비용은 카프카 성능의 모든 측면에 눈에 띄는 영향을 준다. 게다가 카프카는 시스템 페이지
  캐시를 많이 쓰는데, **VM 시스템이 디스크로 스와핑하고 있다면 페이지 캐시에 할당된 메모리가
  충분하지 않다는 뜻**이다 (2장, p.39).[^shapira2021]
- 그렇다고 스왑 공간을 없애는 것이 답은 아니다 (2장, p.39):[^shapira2021]
  - 스왑 공간은 필수가 아니지만 **시스템에 치명적인 일이 생겼을 때 안전망 역할**을 한다.
  - 있으면 **메모리 부족 상황에서 OS가 프로세스를 갑자기 죽이는 것을 막을 수 있다.**
  - 그래서 권고는 제거가 아니라 **`vm.swappiness`를 1처럼 아주 낮은 값으로 잡는 것**이다.
    이 값은 VM 서브시스템이 페이지 캐시에서 페이지를 버리는 대신 스왑 공간을 쓸 가능성을
    나타내는 백분율이다. **스왑 메모리를 쓰느니 페이지 캐시용 메모리를 줄이는 편이 낫다.**
- 0이 아니라 1인 이유가 따로 있다 — 예전 권고는 0이었고 "메모리 부족 상황이 아니면 스왑하지
  말라"는 뜻이었다. 그러나 **리눅스 커널 3.5-rc1에서 의미가 바뀌었고 그 변경이 레드햇
  엔터프라이즈 리눅스 2.6.32-303 등 여러 배포판에 백포트되면서 0의 의미가 "어떤 경우에도
  스왑하지 말라"로 바뀌었다.** 그래서 2021년 저술 시점에는 1이 권장된다 (2장,
  p.39).[^shapira2021]
- 더티 페이지 플러시 조정 (2장, pp.39–40):[^shapira2021]
  - 카프카는 프로듀서에 좋은 응답 시간을 주기 위해 디스크 I/O 성능에 의존한다. **로그
    세그먼트를 대개 빠른 디스크(응답이 빠른 SSD, 또는 캐싱용 NVRAM이 충분한 RAID)에 두는
    이유가 이것이다.**
  - `vm.dirty_background_ratio`를 기본 10보다 낮추면 **플러시 백그라운드 프로세스가 시작되기
    전까지 허용되는 더티 페이지 수를 줄일 수 있다.** 값은 전체 시스템 메모리의 백분율이며 5가
    많은 상황에 적절하다.
  - **0으로 두면 안 된다** — 커널이 페이지를 끊임없이 플러시하게 되어 일시적 디스크 쓰기
    급증을 버퍼링하는 능력을 없앤다.
  - `vm.dirty_ratio`(기본 20)는 **커널이 동기 플러시를 강제하기 전까지 허용되는 더티 페이지
    총수**다. 60에서 80 사이가 합리적 범위로 제시된다.
  - 이 설정은 위험을 조금 늘린다 — **플러시되지 않은 디스크 활동량이 늘고, 동기 플러시가
    강제될 때 긴 I/O 멈춤이 생길 수 있다.** 그래서 `vm.dirty_ratio`를 높게 잡는다면
    **시스템 장애에 대비해 클러스터에 복제를 쓰는 것이 강하게 권장된다.**
  - 값을 고를 때는 부하가 걸린 상태에서 시간에 따른 더티 페이지 수를 보는 것이 현명하다 —
    `/proc/vmstat`에서 확인한다.

## 파일 디스크립터와 파일시스템

- 카프카는 로그 세그먼트와 열린 연결에 파일 디스크립터를 쓴다. 파티션이 많은 브로커가
  필요로 하는 최소치는 **(파티션 수) × (파티션 크기 / 세그먼트 크기) + 브로커가 만드는 연결
  수**다. 이 계산을 근거로 `vm.max_map_count`를 아주 크게 올릴 것이 권장되며, 환경에 따라
  **400,000이나 600,000이 대체로 성공적**이었다 (2장, p.40).[^shapira2021]
- `vm.overcommit_memory`는 0으로 두기를 권장한다. 기본값 0은 **커널이 애플리케이션의 가용
  메모리를 판정한다는 뜻**이며, 0이 아닌 값으로 두면 **OS가 메모리를 너무 많이 잡아 카프카가
  최적으로 동작할 메모리를 빼앗을 수 있다.** 유입량이 많은 애플리케이션에서 흔한 일이다
  (2장, p.40).[^shapira2021]
- 파일시스템 선택은 **디스크 하드웨어와 RAID 구성 다음으로 성능에 큰 영향**을 준다. 흔한
  선택지는 Ext4와 XFS다 (2장, p.41):[^shapira2021]
  - **XFS가 많은 리눅스 배포판의 기본 파일시스템이 된 데는 이유가 있다 — 대부분의 워크로드에서
    최소한의 튜닝으로 Ext4를 능가한다.**
  - Ext4도 잘 돌지만 **덜 안전하다고 여겨지는 튜닝 매개변수를 요구한다** — 커밋 간격을 기본
    5보다 길게 잡아 플러시 빈도를 줄이는 것 등이다. Ext4는 블록의 지연 할당도 도입해
    **시스템 장애 시 데이터 손실과 파일시스템 손상 가능성이 커진다.**
  - XFS도 지연 할당 알고리즘을 쓰지만 Ext4의 것보다 일반적으로 안전하다. **파일시스템이
    수행하는 자동 튜닝을 넘어서는 튜닝 없이 카프카 워크로드에서 더 좋은 성능을 낸다.** 디스크
    쓰기를 배치할 때도 더 효율적이어서 전체 I/O 처리량이 좋아진다.
- 파일시스템이 무엇이든 **로그 세그먼트를 담는 마운트에는 `noatime` 마운트 옵션을 잡는 것이
  바람직하다** (2장, p.41):[^shapira2021]
  - 파일 메타데이터는 생성 시각(`ctime`), 마지막 수정 시각(`mtime`), 마지막 접근
    시각(`atime`) 셋을 담는데, **기본적으로 `atime`은 파일을 읽을 때마다 갱신되어 디스크
    쓰기를 대량으로 만든다.**
  - **`atime`은 카프카가 전혀 쓰지 않으므로 끄는 것이 안전하다.** `ctime`과 `mtime`의 처리에는
    영향을 주지 않는다.
  - `largeio` 옵션은 디스크 쓰기가 클 때 카프카의 효율을 높이는 데 도움이 된다.

## 네트워크 커널 설정

- 네트워크 트래픽을 많이 만드는 애플리케이션이 그렇듯, 리눅스 네트워킹 스택의 기본 튜닝을
  조정하는 것이 일반적이다 — **커널이 기본적으로 크고 빠른 데이터 전송에 맞춰져 있지 않기
  때문**이다. 카프카에 권장되는 변경은 대부분의 웹 서버나 네트워킹 애플리케이션에 권장되는
  것과 같다 (2장, p.41).[^shapira2021]
- 첫 조정은 **소켓별 송수신 버퍼에 할당되는 기본·최대 메모리**다 (2장,
  pp.41–42):[^shapira2021]
  - 소켓당 송수신 버퍼 기본 크기는 `net.core.wmem_default`와 `net.core.rmem_default`이며
    **131072(128KiB)가 합리적 설정**이다.
  - 최대 크기는 `net.core.wmem_max`와 `net.core.rmem_max`이며 **2097152(2MiB)가 합리적**이다.
  - **최대 크기는 모든 소켓이 그만큼 버퍼를 할당받는다는 뜻이 아니라, 필요할 때 거기까지
    허용한다는 뜻**이다.
- TCP 소켓 버퍼는 `net.ipv4.tcp_wmem`·`net.ipv4.tcp_rmem`으로 **따로** 설정해야 하며, 최소·
  기본·최대 세 정수를 공백으로 구분해 준다. **최대값은 `net.core.wmem_max`·
  `net.core.rmem_max`가 정한 값보다 클 수 없다.** 예시 설정은 "4096 65536 2048000" — 최소
  4KiB, 기본 64KiB, 최대 2MiB다 (2장, p.42).[^shapira2021]
- 그 밖의 유용한 매개변수 (2장, p.42):[^shapira2021]
  - `net.ipv4.tcp_window_scaling`을 1로 두어 **TCP 윈도 스케일링을 켜면** 클라이언트가 더
    효율적으로 데이터를 전송하고 브로커 쪽에서 버퍼링할 수 있다.
  - `net.ipv4.tcp_max_syn_backlog`를 기본 1024보다 올리면 **동시 연결 수용량이 커진다.**
  - `net.core.netdev_max_backlog`를 기본 1000보다 올리면 **커널이 처리할 패킷을 더 많이
    대기시킬 수 있어 네트워크 트래픽 버스트에 도움이 된다** — 특히 멀티기가비트 연결 속도를
    쓸 때 그렇다.

## 가비지 컬렉터

> **이 절이 왜 그런지의 기제**는 이 페이지 밖에 있다 — G1GC가 힙을 리전으로 나누고 정지
> 시간 목표를 지키려 애쓰는 방식은 [클래식 가비지
> 컬렉터](../concepts/hotspot-classic-collectors.md)에, 아래 두 매개 변수를 포함한 선택
> 기준은 [적합한 가비지 컬렉터 고르기](../concepts/choosing-a-garbage-collector.md)에 있다.
> 여기 적힌 값은 **카프카 브로커라는 특수 사례의 권고**이고 저쪽이 일반형이다.

- 자바 GC 튜닝은 원래 기예에 가까웠지만 **자바 7과 G1GC(Garbage-First) 도입으로 바뀌었다.
  초기에는 불안정하다고 여겨졌으나 JDK8과 JDK11에서 뚜렷이 개선됐고, 2021년 저술 시점에는 카프카의 기본
  가비지 컬렉터로 G1GC를 쓰는 것이 권장된다** (2장, p.42).[^shapira2021]
- G1GC의 성질: **다양한 워크로드에 자동으로 적응해 애플리케이션 수명 동안 일관된 멈춤 시간을
  제공하도록 설계됐다.** 힙을 작은 구역으로 나누고 매 멈춤마다 힙 전체를 수집하지 않아 큰
  힙도 쉽게 다룬다 (2장, p.42).[^shapira2021]
- 조정 옵션은 둘뿐이다 (2장, p.43):[^shapira2021]
  - `MaxGCPauseMillis` — GC 주기마다 선호하는 멈춤 시간이다. **고정 최대치가 아니며 필요하면
    초과할 수 있다.** 기본값은 200밀리초이고, G1GC는 매 주기가 대략 200ms가 되도록 주기 빈도와
    구역 수를 조절한다.
  - `InitiatingHeapOccupancyPercent` — 수집 주기를 시작하기 전 사용 중일 수 있는 전체 힙의
    백분율이다. 기본값 45는 **힙의 45%가 쓰이기 전에는 수집을 시작하지 않는다**는 뜻이다.
- 카프카에 맞춘 값 (2장, p.43):[^shapira2021]
  - **카프카 브로커는 힙 메모리를 효율적으로 쓰고 가비지 객체를 만들므로 두 값을 더 낮게
    잡을 수 있다.**
  - 제시된 값의 전제는 **메모리 64GB 시스템에서 5GB 힙으로 카프카를 돌리는 서버**다. 이때
    `MaxGCPauseMillis`는 20ms, `InitiatingHeapOccupancyPercent`는 35로 잡아 **가비지 컬렉션이
    기본값보다 조금 일찍 돌게 한다.**
- 기본값이 G1GC가 아닌 이유도 기록돼 있다 — **카프카는 G1GC가 나오기 전에 릴리스돼 모든
  JVM과의 호환을 위해 CMS(concurrent mark and sweep)를 기본으로 쓴다. 자바 1.8 이상에서는
  G1GC를 쓰는 것이 새로운 모범 사례**이며, 환경 변수로 쉽게 바꿀 수 있다 (2장,
  p.43).[^shapira2021]

## 데이터센터 배치

- 테스트·개발 환경에서는 브로커의 물리적 위치가 큰 문제가 아니다 — 클러스터가 부분적으로
  또는 완전히 사용 불가가 되어도 영향이 짧다. 그러나 **프로덕션 트래픽을 다룰 때 다운타임은
  대개 돈의 손실**을 뜻한다 (2장, p.43).[^shapira2021]
- 이때 클러스터 안의 복제 설정이 결정적이 되고, **동시에 브로커가 데이터센터의 랙에서 어디에
  놓이는지도 중요해진다.** 데이터센터는 장애 구역(fault zone) 개념을 갖는 것이 바람직하며,
  **카프카를 배포하기 전에 다루지 않으면 서버를 옮기는 비싼 유지 보수가 필요해질 수 있다**
  (2장, p.44).[^shapira2021]
- 랙 인식 할당의 범위와 한계 (2장, p.44):[^shapira2021]
  - 카프카는 새 파티션을 랙 인식 방식으로 배정해 **한 파티션의 레플리카들이 같은 랙을 공유하지
    않게** 할 수 있다. 이를 위해 브로커마다 `broker.rack` 설정을 제대로 잡아야 하며, 클라우드
    환경에서는 장애 도메인으로 설정할 수 있다.
  - **다만 이 설정은 새로 생성되는 파티션에만 적용된다.** 카프카 클러스터는 파티션이 더 이상
    랙 인식 상태가 아닌 경우(예: 파티션 재할당의 결과)를 감시하지 않고 자동으로 교정하지도
    않는다.
  - 그래서 **클러스터의 균형을 유지해 주는 도구(예: Cruise Control)를 쓰는 것이 권장된다.**
- 물리 배치의 모범 사례 (2장, p.44):[^shapira2021]
  - **클러스터의 각 카프카 브로커를 서로 다른 랙에 설치한다.** 최소한 전력과 네트워크 같은
    인프라 서비스의 단일 장애점을 공유하지 않게 한다.
  - 보통 **이중 전원 연결(서로 다른 두 회로)과 이중 네트워크 스위치(서버 쪽에 본딩된 인터페이스로
    매끄럽게 페일오버)** 를 갖춘 서버를 배포한다는 뜻이다.
  - 이중 연결이 있어도 **완전히 분리된 랙에 두는 이점은 남는다** — 때때로 랙이나 캐비닛을
    오프라인으로 내려야 하는 물리적 유지 보수(서버 이동, 전원 배선 재작업)가 필요하기 때문이다.
