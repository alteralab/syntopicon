# 이벤트 루프 스레드를 막지 않는다는 규율

이 페이지의 질문: **이벤트 기반 프레임워크에서 지켜야 하는 규칙은 무엇이고 그것을 어기면 무엇이
무너지는가.**

## 이벤트 기반 프레임워크의 구조

- 저자가 문제를 이렇게 세운다 — 앞의 예제는 잘 확장되고 제 몫을 하지만 현실의 애플리케이션은 훨씬
  복잡하다. 더 크고 더 동적인 시스템을 떠받치려면 코드를 어떻게 구성해야 하는가 (6장
  "Event-Driven Architecture", p.272).[^rahman2025]
- 답이 프레임워크다 — 이벤트 기반 패러다임 위에 지어진 프레임워크가 많고, 그것들이 동시성과
  확장성을 효율적으로 다루기 쉽게 해 준다. 저자가 드는 좋은 예가 Netty와 Vert.x다 (6장,
  p.272).[^rahman2025]
- Vert.x의 바탕이 무엇인지를 저자가 높은 수준에서 정리한다 — 멀티코어 리액터 패턴(multicore reactor
  pattern) 위에 서서 이벤트 루프(event loop) 동시성 모델을 활용한다. 가벼운 이벤트 루프 스레드
  집합이 NIO 같은 논블로킹 연산을 통해 I/O 이벤트를 계속 듣는다 (6장, p.274).[^rahman2025]
  - 버전 조건: 이 예제가 적는 의존 버전은 `vertx-core`와 `vertx-web` 둘 다 5.0.0이며, 저자는
    메이븐 프로젝트를 만들어 그 둘을 더하라고 안내한다 (6장, p.274).[^rahman2025]
- 이벤트가 일어날 때 하는 일이 정해져 있다 — 들어오는 요청 같은 이벤트가 생기면 짧고 논블로킹인
  콜백이 이벤트 루프 안에서 실행되며, 그것이 응답성을 보장한다 (6장, p.274).[^rahman2025]
- 이벤트 루프에서 다룰 수 없는 일도 있다 — 데이터베이스 질의나 파일 시스템 접근처럼 본디 블로킹이거나
  오래 걸리는 연산이 그것이다. Vert.x는 그런 일을 별도의 워커 스레드 풀로 똑똑하게 내보내 이벤트
  루프가 느려지지 않게 한다. 이 설계 덕분에 이벤트 루프는 불필요한 지연 없이 새 요청을 계속 다룰 수
  있게 남는다 (6장, pp.274–275).[^rahman2025]
- 강점 하나가 더 있다 — 이벤트 버스(event bus)가 애플리케이션의 서로 다른 구성 요소들이 비동기로
  통신하게 해 준다. 시스템을 느슨하게 결합된 채로 두면서 부분들 사이의 매끄러운 협력을 보장하는
  방식이다 (6장, p.275).[^rahman2025]

## 층이 셋이다

- 저자가 그림 하나로 층을 갈라 보인다 — 프레임워크가 이벤트 루프를 중심에 두고 동작하며, 클라이언트
  연결 관리와 나가는 요청 처리와 응답 쓰기를 모두 논블로킹으로 맡는다 (6장 그림 6-1,
  p.275).[^rahman2025]
- 그 위에 리액티브 프레임워크가 얹힌다 — 네트워크 연산을 단순하게 만드는 더 높은 수준의 API를 주는
  자리다. 개발자는 날것의 논블로킹 I/O를 직접 다루는 대신 HTTP 요청과 응답과 카프카 메시지 같은
  직관적인 추상을 다루게 된다 (6장, p.275).[^rahman2025]
- 애플리케이션 코드가 가장 위층이다 — 우리 코드는 이벤트 루프와 직접 상호작용하지 않고 이벤트
  핸들러를 통해 동작한다 (6장, p.275).[^rahman2025]

## 규칙 하나

- 여기서 결정적인 대목이 온다 — 애플리케이션의 이벤트 핸들러는 이벤트 루프 스레드에서, 곧 사실상
  I/O 스레드에서 실행된다. 우리 코드가 이 스레드를 막으면 다른 어떤 동시 이벤트도 처리되지 못한다
  (6장, p.276).[^rahman2025]
- 결과가 크다 — 응답성과 동시성이 완전히 무너지며, 저자는 그것이 고도로 리액티브하도록 설계된
  시스템에 재앙이 될 것이라고 적는다 (6장, p.276).[^rahman2025]
- 예제 안에서 그 규율이 드러나는 자리를 저자가 짚는다 — 느린 요청 핸들러가 `Thread.sleep()`이 아니라
  타이머를 쓴다 (6장, pp.274·276).[^rahman2025]

  ```java
  private void handleSlowRequest(RoutingContext ctx) {
      long requestId = requestCounter.incrementAndGet();
      vertx.setTimer(2000, id -> {
          ctx.response()
             .putHeader("content-type", "text/plain")
             .end("Request #" + requestId + ": Slow request processed");
      });
  }
  ```

- 그 차이가 결정적이다 — 타이머는 이벤트 루프 스레드를 막지 않은 채 2초 뒤에 실행될 콜백을
  예약한다. 스레드는 기다리는 동안 곧바로 다른 요청을 다루도록 풀린다 (6장,
  p.276).[^rahman2025]
- 그래서 해법이 단순하게 진술된다 — 우리 코드는 논블로킹이어야 하고, 어떤 상황에서도 I/O 스레드를
  막아서는 안 된다. 막으면 이벤트 루프 전체가 멈춰 서고 애플리케이션의 응답성을 통째로 끌어내린다
  (6장, p.276).[^rahman2025]
- 다만 쉽지 않다는 것을 저자가 인정한다 — 논블로킹 코드를 쓰라고 말하는 것과 실제로 쓰는 것은
  다르고, 진짜 논블로킹 코드를 쓰는 일은 늘 간단하지 않으며 사고방식의 전환을 요구한다 (6장,
  p.276).[^rahman2025]
- 그 자리에서 리액티브 프레임워크가 들어온다 — 블로킹 연산을 피하면서도 복잡한 작업 흐름을 효율적으로
  다루게 돕는 비동기 API를 준다. 작업이 끝나기를 기다리는 대신 콜백을 등록하거나 프로미스를 쓰거나
  리액티브 스트림을 활용해 이벤트 루프를 멈추지 않고 실행을 조율한다 (6장,
  p.276).[^rahman2025]

## 우회로의 값

- 우회로가 있기는 하다 — 블로킹 연산을 별도의 워커 스레드 풀로 내보낼 수 있고, Vert.x 자신도 어느
  정도는 그렇게 한다 (6장, p.276).[^rahman2025]
- 그러나 저자는 그것이 표준이 되어서는 안 된다고 못 박는다. 워커 스레드에 지나치게 기대면 리액티브
  시스템의 목적 자체가 무너진다 (6장, p.276).[^rahman2025]
- 이유가 문맥 전환이다 — I/O 스레드에서 워커 스레드로, 다시 되돌아오는 실행 전환마다 문맥
  전환(context switch)이 들어간다. 그것이 오버헤드를 더해 응답 시간을 늦추고, 애초에 얻으려던 효율
  이득을 깎아 먹는다 (6장, p.276).[^rahman2025] 문맥 전환의 값 자체는
  [스레드의 숨은 비용](../concepts/hidden-costs-of-threads.md)에 있다.
