# 데이터 웨어하우스의 데이터 품질 관리

하나의 질문: **저품질 데이터를 데이터 웨어하우스 어디서, 어떻게 교정하나.**

Data Vault 2.0의 답은 역설적이다 — 일단 나쁜 데이터도 전부 원형 그대로 적재하고, 교정은 하류의 soft rule로 미룬다. 이 페이지는 그 논거(품질 기대의 이원성, 저품질 비용, 나쁜 데이터의 가치)와 교정 기법(표준화, 정정, 매칭·통합, Same-As 링크)을 다룬다.

## 품질 기대: 두 범주와 "사실의 단일 버전"

- Data Vault 2.0 적재의 목표는 품질과 무관하게 모든 데이터를 담는 것이다("the good, the bad, and the ugly"). 피해야 할 관행 셋: 나쁜 데이터를 오류 파일(error mart)로 빼돌리기, 기술적 문제(중복 기본 키·NOT NULL 위반 등)를 이유로 데이터 걸러내기, Raw Data Vault 테이블에 NULL 금지 제약 두기 (13장 도입, p.568).[^linstedt2016]
- 데이터 품질은 주관적 개념이다 — 한 사용자에게 올바른 데이터가 다른 요구 사항을 가진 사용자에게는 틀릴 수 있고, 데이터 웨어하우징에 "황금 사본(golden copy)"이나 "단일 진실 버전(single version of the truth)"은 없다. 그래서 Data Vault 2.0은 "사실의 단일 버전(single version of the facts)"에 집중한다 (§13.1, p.569).[^linstedt2016]
- 품질에 관한 기대는 두 범주로 구분된다 (§13.1, p.569):[^linstedt2016]
  - **데이터 품질 기대**: 값의 유효성을 재는 규칙으로 표현 — 누락·사용 불능 데이터 식별, 충돌 기술, 중복 레코드 판정, 누락 링크 탐색.
  - **비즈니스 기대**: 프로세스의 성능·생산성·효율 측정 — 오류로 인한 처리량 감소, 실패 프로세스 재작업 시간 비율, 잘못된 트랜잭션의 가치 손실.
- 오류 유형별 교정 위치: **데이터 오류**는 원천 애플리케이션·비즈니스 프로세스에서 고치는 것이 최선(아니면 근본 원인이 남아 더 비싼 재교정이 반복된다), **비즈니스 규칙 오류**는 규칙 구현체가 있는 데이터 웨어하우스(Business Vault나 정보 마트 적재 루틴)에서 고쳐야 하고, **인식 오류**는 대개 요구 사항 쪽을 바꿔야 한다 (§13.1, p.569).[^linstedt2016]
- 데이터의 주인은 비즈니스이므로 IT는 비즈니스 규칙 구현 부담을 줄이고 그 책임을 가능한 한 비즈니스 사용자에게 넘겨야 한다 — 관리형 셀프서비스 BI(managed self-service BI). 이 접근에서 IT는 프로세스만 관장하고 원시 데이터를 제공하며, 비즈니스 규칙 오류의 수선 책임은 사실상 비즈니스 사용자에게 이동한다 (§13.1, pp.569–570).[^linstedt2016]

## 저품질의 비용

- 저품질 데이터가 적재되면 비즈니스 사용자가 흔히 간과하는 비용이 발생한다 (§13.2, p.570):[^linstedt2016] 고객·파트너 만족 훼손(예: 외부로 나가는 청구서·재무제표가 틀린 경우), 규제 영향(법정 보고가 틀리면 소송 위험), 재무 비용(품질 개선 비용보다 오판 비용이 몇 배 크다), 조직의 불신(사용자가 시스템을 우회해 운영계 보고서나 사일로 웨어하우스를 따로 만든다), 재설계(고칠 수 없으면 프로젝트를 접고 처음부터 다시), 의사 결정 실기(몇 달 뒤 정정된들 결정 시점은 지나갔다), 비즈니스 전략 저해.
- 저품질 비용은 평가·검사·수선 비용을 몇 배 웃돈다. 개선의 최적 지점은 비즈니스 프로세스와 운영 시스템이고, 그것이 불가능할 때에만 데이터 웨어하우스가 교정 장소가 된다 (§13.2, p.570).[^linstedt2016]

## 나쁜 데이터의 가치: 왜 원천 그대로 보존하나

- 레거시 데이터 웨어하우징은 적재 전에 나쁜 데이터를 고쳤다. 최대 단점은 원본 데이터가 분석에서 사라진다는 것 — 비즈니스 기대와 원천 시스템의 실제 품질 사이 **간극 분석(gap analysis)** 이 불가능해진다 (§13.3, pp.570–571).[^linstedt2016]
- 간극 분석에서 비즈니스는 "일어나야 한다고 믿는 것"을 말하고, 원천 시스템은 "실제로 수집되고 있는 것"을 보여준다. 양쪽 다 옳다 — 이것이 "진실의 두 버전"이고, 그 사이 간극이 닫아야 할 대상이다. 좋은 데이터 웨어하우스는 나쁜 데이터를 보여줌으로써 비즈니스가 자기 애플리케이션의 문제를 발견하고 교정하도록 도와야 한다 (§13.3, p.571).[^linstedt2016]
- 나쁜 데이터를 포함한 원시 데이터 소싱의 가치 (§13.3, p.572):[^linstedt2016] 문제가 (지금이든 미래든) 발견되면 원시 데이터가 있어야 대응할 수 있다; 적재 전에 번역·해석하면 "고쳐진" 데이터가 간극을 가린다; 원시 데이터가 있어야 셀프서비스 BI와 프런트엔드 규칙 이관이 가능하다; IT는 원시 데이터의 해석에 책임지지 않아도 된다.

> Having the bad data in the data warehouse helps to reconcile integrated and altered data with the source systems and with business requirements. This is the reason why bad data, and ugly-looking data, is kept in the data warehouse and not modified, transformed or fixed in any sense on the way into the data warehouse. (§13.3, p.572)[^linstedt2016]

## 아키텍처에서의 위치: 품질 루틴 = soft rule

- 데이터 품질 루틴(오류 교정, 원시 데이터 보완, 가치를 높이는 변환)은 정확히 soft business rule의 목적과 같으므로, Data Vault 2.0 참조 아키텍처에서 soft rule로 취급된다 (§13.4, p.572).[^linstedt2016] 계층 구조는 data-vault-architecture.md 참조.
- soft rule과 마찬가지로 품질 루틴은 자주 바뀐다 — 지식 베이스의 번역 규칙은 진화하고, 데이터 마이닝 기반 교정은 아예 고정 규칙이 없다. Business Vault나 정보 마트 적재 과정에 구현하면 유입 원시 데이터는 전혀 수정되지 않으므로, 규칙이 바뀌어도 **이전 원시 데이터를 재적재하지 않고** 루틴만 고치면 된다 (§13.4, p.573).[^linstedt2016]
- "고품질"의 상이 여럿이면 정보 마트를 여럿 둔다: 전사 합의된 교정을 원하는 소비자, 자기만의 교정 기준을 가진 소비자, 오류 데이터 자체를 분석하려는 소비자를 각각의 마트로 만족시킨다. 이를 위해 교정 루틴은 가능하면 Business Vault에 구현해 여러 마트가 결과를 재사용하게 한다 (§13.4, p.573).[^linstedt2016] business-vault.md 참조.
- 데이터 웨어하우스 안 교정은 어디까지나 차선이다. 최선은 오류를 고치는 것이 아니라 **고칠 필요 자체를 없애는 것** — 정보 프로세스에 품질을 설계해 넣는 것이다. 현실에서는 원천 수정이 범위 밖으로 밀려나 DW 교정이 흔하지만, 그 결과물은 원천의 유효 데이터 + 고쳐진 데이터 + 미탐지 오류 + 새로 유입된 오류의 혼합물임을 인지해야 한다 (§13.5, p.574).[^linstedt2016]
- BI 시스템에서 고칠 수 있는 오류 범주: 파생 데이터 변환·보강·계산, 데이터 표준화, 정정·보완, 매칭·통합, 품질 태깅(하류 사용자에게 품질 정보 제공). 이 "교정"들은 원시 데이터에 대한 UPDATE가 아니라, Raw Data Vault에서 읽어 Business Vault나 정보 마트 계층으로 적재할 때 구체화(materialize)되거나 가상(virtual) 형태로 제공된다 (§13.5, p.574).[^linstedt2016]

## 교정 기법

### 표준화

- 표준화는 원시 데이터를 전사 공유 가능한 표준 형식으로 변환하는 것이다 — 일관된 형식은 다중 소스 통합과 중복 레코드 식별을 돕는다. 사례: 불필요한 문장 부호·공백 제거, 토큰 재배열(성·이름), 요소 재정렬(우편 주소), 단위 불일치 해소(마일 vs km), 형식 불일치(전화번호·우편번호), 운영계 코드를 전사 참조 코드로 매핑 (§13.7, p.578).[^linstedt2016]
- 코드 매핑은 분석용 마스터 데이터를 Data Vault 2.0의 참조 테이블로 적재해 구현하는 것이 자연스럽다 (§13.7, p.578).[^linstedt2016] reference-table.md 참조.

### 정정·보완

- 알려진 오류·누락·의심 데이터를 고치는 규칙 유형: 단일 필드 규칙(형식·범위·도메인), 다중 필드 정합성 규칙(예: 여권 ID와 발급국의 일치), 개연성 규칙(예: 성별과 이름의 조합이 비정상적이면 표시) (§13.8, p.580).[^linstedt2016]
- 교정 방식 셋 (§13.8, p.580):[^linstedt2016]
  - **자동 교정**: 규칙 기반 표준화·정규화·정정. computed satellite가 흔히 담당하며 완전 가상화(뷰)로 구현 가능.
  - **수동 지시 교정(manual directed)**: 자동 교정 결과를 사람이 검토·개입. 신뢰도(confidence) 값을 함께 저장하며, Business Vault에 결과를 **구체화해야 한다**.
  - **수동 교정**: 데이터 스튜어드가 직접 검사·수정. 외부 도구나 MDM 애플리케이션과 결합되는 경우가 많다.
- 교정 불가능한 데이터의 처리 선택지: 기각(집계에 안 쓰이는 데이터라면 마트에서 제외), 무변경 수용, 태그를 달아 수용(오류를 문서화해 사용자에게 제시), 근사값 추정(발생 건수를 보존하는 장점이 있으나 과대·과소 추정 위험). 어떤 선택지를 적용했는지 태그로 남기는 것이 좋다 — 특히 추정값은 실측이 아님을 사용자에게 알려야 한다 (§13.8, p.580).[^linstedt2016]

### 매칭·통합

- 식별자 해소(identity resolution)의 전형적 세 경우와 Data Vault 2.0의 대응 엔터티 (§13.9, p.602):[^linstedt2016]
  - **같은 엔터티**: 같은/다른 소스의 중복 비즈니스 키가 실은 동일한 비즈니스 엔터티 → **Same-As 링크(same-as link, SAL)** 로 해소.
  - **틀린 엔터티**: 서술 데이터의 표기 변형 때문에 기존 레코드를 못 찾는 경우 → computed satellite로 서술 오류 교정.
  - **같은 상위 집단**: 별개 엔터티지만 같은 가구·조직에 속하는 경우 → 계층 링크(hierarchical link)로 집계.
- 중복 후보 식별 기법: 음성(phonetic)·매치 코드·상호 참조·부분 텍스트·패턴·퍼지 로직 등의 매칭 기법, 규칙 대신 근접 매치를 찾는 데이터 마이닝, 교정 소프트웨어 (§13.9, p.602).[^linstedt2016]
- 권장 접근은 SAL이다 — 원시 데이터를 건드리지 않으면서 최대의 유연성을 준다. SAL은 같은 허브를 참조하는 두 해시 키(마스터 레코드, 이후 질의에서 마스터로 대체될 중복 레코드)와 유사도 점수(Score)로 구성된다 (§13.9.1, pp.602–604).[^linstedt2016]
- 유사도 임계값의 트레이드오프: 낮추면 위양성(false positive, 다른 사람을 같다고 판정) 증가, 높이면 위음성(false negative, 같은 사람을 다르다고 판정) 증가. 기본값 0.80이 무난하지만, SAL 방식에서는 오히려 아주 낮은 값(예: 0.05)으로 후보를 넓게 저장하고 **사용 시점에 사용자 정의 임계값으로 거르는** 편이 낫다 — 소비자(정보 마트나 파워 유저)에게 선택권이 넘어가기 때문이다. 원천 허브의 비즈니스 키 볼륨이 클 때만 임계값을 높여 저장량을 억제한다 (§13.9.1, pp.608–609).[^linstedt2016]

## Same-As 링크로 중복 제거된 차원 만들기

- SAL은 중복 제거된 차원 테이블의 토대가 된다. 차원을 허브와 새틀라이트에서 직접 뽑는 대신 **SAL을 소스로** 삼고, 여전히 허브에 매달린 새틀라이트들을 조인해 서술 데이터를 공급한다 (§13.10, pp.618–619).[^linstedt2016] 차원 테이블 일반은 ../concepts/dimension-table.md 참조.
- 저장해 둔 점수를 질의에서 활용한다: 점수가 상수(예: 0.5) 이상인 매핑은 중복을 마스터 해시 키로 접고, 미만인 레코드는 별개 멤버로 남긴다. 파워 유저가 이 상수만 조정하면 차원에 반영되는 매핑의 폭이 달라진다 — 낮출수록 더 많은 비즈니스 키가 마스터로 접히고, 높일수록 알고리즘의 확신이 높은 경우에만 접힌다 (§13.10, p.619).[^linstedt2016]
- SAL 적재 운영은 두 방식이 있다: 점수·매핑 변경을 갱신하는 증분 적재, 매 실행마다 대상을 비우고 다시 채우는 전체 적재. 대부분은 후자가 훨씬 단순하면서 성능도 감당 가능하고, 허브 레코드가 매우 많을 때만 증분이 필요하다 (§13.9.1, p.618).[^linstedt2016] Business Vault 엔터티는 감사 대상이 아니어서 이런 재적재가 허용된다 — business-vault.md 참조.

## 건너뛴 것
