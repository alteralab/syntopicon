하나의 질문: **GraphQL은 다른 그래프 질의 언어들과 무엇이 다르며, 왜 일부러 표현력을
줄였는가.**

## 무엇을 위한 언어인가

- 위치부터 다르다 — **GraphQL은 설계상 이 장에서 본 다른 언어들보다 훨씬 제한적인 질의
  언어다. 그것은 OLTP 질의를 위한 것이며, 그 목적은 사용자 기기에서 도는 클라이언트
  소프트웨어(모바일 앱이나 자바스크립트 웹 앱 프런트엔드 같은)가 UI를 렌더링하는 데 필요한
  필드를 담은, 특정 구조의 JSON 문서를 요청할 수 있게 하는 것이다** (3장,
  pp.98–99).[^kleppmann2026]
- 무엇을 사는가와 그 대가 — **GraphQL 인터페이스는 개발자가 서버 쪽 API를 바꾸지 않고 클라이언트
  코드의 질의를 빠르게 바꿀 수 있게 해 준다. 그러나 그 유연성에는 비용이 따른다. GraphQL을
  채택하는 조직은 흔히 그 질의를 내부 서비스에 대한 요청(보통 REST나 gRPC를 쓴다)으로 변환하는
  도구가 필요하다. 인가(authorization)·속도 제한·성능 문제도 추가적인 걱정거리다** (3장,
  p.99).[^kleppmann2026]

## 의도적으로 제한된 언어

- **이 언어는 의도적으로 제한돼 있는데, GraphQL 질의가 신뢰할 수 없는 출처에서 오기 때문이다.
  그것은 실행이 비쌀 수 있는 어떤 것도 허용하지 않는다. 그러지 않으면 사용자가 (아마 의도치
  않게) 비싼 질의를 많이 돌려 서버에 서비스 거부 상태를 일으킬 수 있기 때문이다** (3장,
  p.99).[^kleppmann2026]
- 구체적으로 두 가지가 막혀 있다 — **특히 GraphQL은 재귀 질의를 허용하지 않으며(Cypher·SPARQL·
  SQL·Datalog와 달리), "미국에서 태어나 지금 유럽에 사는 사람 찾기" 같은 임의의 검색 조건도
  허용하지 않는다 — 서비스 소유자가 그런 검색 기능을 제공하기로 명시적으로 선택하지 않는 한
  그렇다** (3장, p.99).[^kleppmann2026] 그 재귀가 다른 언어에서 어떻게 표현되는지는
  [그래프 질의 언어](../concepts/graph-query-languages.md)에 있다.

## 질의와 응답의 모양

- **그럼에도 GraphQL은 유용하다.** 저자들이 든 예는 **디스코드나 슬랙 같은 그룹 채팅
  애플리케이션**이다. **질의는 사용자가 접근할 수 있는 모든 채널을 요청하며, 채널 이름과 각
  채널의 가장 최근 메시지 50개를 포함한다. 각 메시지에 대해 질의는 타임스탬프, 메시지 내용,
  그리고 발신자의 이름과 프로필 사진 URL을 요청한다. 메시지가 다른 메시지에 대한 답글이면
  질의는 그 메시지의 발신자 이름과 내용도 요청한다**(답글 위에 작은 글씨로 렌더링되어 맥락을
  제공할 수 있다) (3장, p.99, 예제 3-13):[^kleppmann2026]

  ```graphql
  query ChatApp {
    channels {
      name
      recentMessages(latest: 50) {
        timestamp
        content
        sender {
          fullName
          imageUrl
        }
        replyTo {
          content
          sender {
            fullName
          }
        }
      }
    }
  }
  ```

- 응답의 성질 — **응답은 질의의 구조를 그대로 비추는 JSON 문서다. 그것은 요청된 속성을 정확히
  담으며 그 이상도 이하도 아니다. 이 접근은 서버가 사용자 인터페이스를 렌더링하기 위해
  클라이언트가 어떤 속성을 필요로 하는지 알 필요가 없다는 이점을 갖는다 — 클라이언트가 필요한
  것을 그냥 요청할 수 있다** (3장, p.100).[^kleppmann2026]
- 그 이점의 실물 — **예컨대 이 질의는 replyTo 메시지 발신자의 프로필 사진 URL을 요청하지 않지만,
  UI가 그 프로필 사진을 포함하도록 바뀐다면 클라이언트가 필요한 imageUrl 속성을 질의에 더하는
  것만으로 충분하고 서버 쪽 변경은 필요 없다** (3장, p.100).[^kleppmann2026]

## 중복을 받아들이는 선택

- **이 예에서 메시지 발신자의 이름과 이미지 URL은 메시지 객체에 직접 끼워 넣어져 있다. 같은
  사용자가 여러 메시지를 보내면 이 정보가 메시지마다 반복된다. 원칙적으로 이 중복을 줄이는 것이
  가능하겠지만, GraphQL은 요청된 데이터에 기반해 UI를 렌더링하기 더 단순하게 만들기 위해 더 큰
  응답 크기를 받아들이는 설계 선택을 한다** (3장, p.100).[^kleppmann2026]
- **replyTo 필드도 마찬가지다 — 둘째 메시지가 첫째에 대한 답글이라 내용과 발신자 이름이 replyTo
  아래에 중복된다. 대신 답글 대상 메시지의 ID를 반환할 수도 있겠지만, 그러면 그 ID가 반환된 최근
  50개 메시지에 없을 경우 클라이언트가 서버에 추가 요청을 해야 한다. 내용을 중복시키는 것이
  데이터를 다루기 훨씬 단순하게 만든다** (3장, p.100).[^kleppmann2026] 같은 트레이드오프의
  일반형은 [정규화와 비정규화](../concepts/normalization-and-denormalization.md)에 있다.

## 서버 쪽은 정규화돼 있어도 된다

- **서버의 데이터베이스는 데이터를 더 정규화된 형태로 저장하고 질의를 처리하기 위해 필요한
  조인을 수행할 수 있다. 예컨대 서버는 메시지를 발신자의 사용자 ID, 그리고 그것이 답글인 메시지의
  ID와 함께 저장할 수 있다. 앞의 질의 같은 것을 받으면 서버는 그 ID들을 풀어 그것이 가리키는
  레코드를 찾는다. 다만 GraphQL 스키마에 명시적으로 선언된 조인만 클라이언트가 요청할 수 있다**
  (3장, p.101).[^kleppmann2026]
- 마지막 판정 — **GraphQL 질의에 대한 응답이 문서 데이터베이스의 응답과 비슷해 보이고 이름에
  "그래프"가 들어가지만, GraphQL은 어떤 종류의 데이터베이스 — 관계형·문서·그래프 — 위에도 구현될
  수 있다** (3장, p.101).[^kleppmann2026]

## REST와의 관계

- 데이터 엔지니어링 개론이 붙이는 위치 — **GraphQL은 애플리케이션 데이터를 위한 질의 언어이자
  일반 REST API의 대안으로 페이스북에서 만들어졌다. REST API가 일반적으로 질의를 특정 데이터
  모델로 제한하는 반면, GraphQL은 단일 요청에서 여러 데이터 모델을 회수할 가능성을 연다. 이는
  REST보다 더 유연하고 표현적인 질의를 허용한다. GraphQL은 JSON을 중심으로 지어져 있고 JSON
  질의를 닮은 모양으로 데이터를 돌려준다** (5장, p.175).[^reis2022]
- 둘 중 하나를 고르는 문제가 아니다 — **REST와 GraphQL 사이에는 일종의 성전 같은 것이 있어
  어떤 엔지니어링 팀은 한쪽 편이고 어떤 팀은 양쪽을 쓴다. 현실에서 엔지니어는 원천 시스템과
  상호작용하면서 둘 다 마주칠 것이다** (5장, p.175).[^reis2022]
