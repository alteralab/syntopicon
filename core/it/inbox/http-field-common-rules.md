하나의 질문: **필드마다 문법을 새로 정의하지 않으려고 원전이 공유해 둔 부품은 무엇이고, 각
부품이 송신자와 수신자에 무엇을 요구하는가.**

## 버전 조건

> **버전 조건**: RFC 9110(2022-06, STD 97) 기준. 2026-09-07 시점 이를 갱신하거나 폐기하는
> RFC 없음(datatracker 실측).

## 왜 공통 규칙이 따로 있는가

- 많은 HTTP 필드 값이 공백이나 특정 구분 문자로 나뉜 **공통 문법 부품**으로 정의된다
  (§5.6.2).[^fielding2022-rfc9110]
- 구분자는 토큰에 허용되지 않는 US-ASCII 시각 문자 집합에서 고른다
  (§5.6.2).[^fielding2022-rfc9110] 곧 토큰의 정의가 먼저 있고 구분자가 그 여집합에서 나온다.
- 공통 문법을 쓰는 실익은 파서 재사용이다. 수신자가 이미 가진 파서 부품을 다시 쓸 수 있다
  (§5.5).[^fielding2022-rfc9110]

## 리스트 확장 문법

- ABNF 표준에 없는 확장 하나를 이 문서가 쓴다. 리스트 기반 필드 값의 정의를 읽기 쉽게 하려고
  `#` 규칙 확장을 도입한다 (§5.6.1).[^fielding2022-rfc9110]
- `*`와 비슷하게 `#`를 정의하되 뜻이 다르다. 완전한 형태는 `<n>#<m>element`이고 **최소 n개
  최대 m개의 원소를 각각 콤마 하나와 선택적 공백으로 구분해** 적는다는 뜻이다
  (§5.6.1).[^fielding2022-rfc9110]
- 이 확장은 표기의 편의일 뿐이다. 부록 A가 리스트 구성이 펼쳐진 뒤의 송신자용 ABNF 모음을
  보여 준다 (§5.6.1.1).[^fielding2022-rfc9110]

## 송신자와 수신자에 다르게 걸리는 요건

- 송신자 쪽은 금지다. 리스트 구성을 쓰는 어느 생성 규칙에서든 **송신자는 빈 리스트 원소를
  만들어서는 안 된다** (§5.6.1.1).[^fielding2022-rfc9110] 곧 송신자가 지켜야 할 문법은
  `1#element => element *( OWS "," OWS element )`로 펼쳐진다.
- 수신자 쪽은 관용이되 한계가 있다 (§5.6.1.2).[^fielding2022-rfc9110]

  > A recipient MUST parse and ignore a reasonable number of empty list elements: enough to
  > handle common mistakes by senders that merge values, but not so much that they could be
  > used as a denial-of-service mechanism.

  수신자는 적당한 수의 빈 리스트 원소를 파싱해 무시해야 한다. 기준이 두 방향으로 잡혀 있다는
  것이 요점이다. 값을 합치다 저지르는 송신자의 흔한 실수를 감당할 만큼은 참되, **서비스 거부
  수단으로 쓰일 만큼은 참지 않는다.**
- 그 결과 카디널리티가 문법으로 강제되지 않는다. 빈 원소가 있을 수 있으므로 ABNF가 원소 개수를
  강제할 수 없고, 모든 경우가 카디널리티를 적지 않은 것처럼 대응된다
  (§5.6.1.2).[^fielding2022-rfc9110] 빈 원소는 원소 수 계산에 들지 않는다.
- 다만 최소 한 개를 요구하는 생성 규칙에서 값이 통째로 비거나 콤마만 있는 것은 무효다
  (§5.6.1.2).[^fielding2022-rfc9110]

## 토큰

- 토큰(token)은 **공백도 구분자도 포함하지 않는 짧은 텍스트 식별자**다
  (§5.6.2).[^fielding2022-rfc9110]

  ```abnf
  token          = 1*tchar

  tchar          = "!" / "#" / "$" / "%" / "&" / "'" / "*"
                 / "+" / "-" / "." / "^" / "_" / "`" / "|" / "~"
                 / DIGIT / ALPHA
                 ; any VCHAR, except delimiters
  ```

- 필드 이름도 미디어 타입의 type과 subtype도 콘텐츠 코딩 이름도 전부 이 토큰이다
  (§5.1, §8.3.1, §8.4.1).[^fielding2022-rfc9110]

## 공백 세 종류

- 이 명세는 선형 공백의 쓰임을 나타내는 데 규칙 셋을 쓴다. OWS는 선택적 공백, RWS는 필수 공백,
  BWS는 "나쁜" 공백이다 (§5.6.3).[^fielding2022-rfc9110]
- OWS는 선형 공백 옥텟이 없거나 여럿 나올 수 있는 자리에 쓴다. 가독성을 위해 선택적 공백을
  선호하는 프로토콜 요소에서 송신자는 SP 하나로 만들어야 하고, 그 밖에는 제자리 메시지 필터링
  중에 무효하거나 원치 않는 프로토콜 요소를 덮어쓸 때 말고는 만들지 않아야 한다
  (§5.6.3).[^fielding2022-rfc9110]
- RWS는 필드 토큰을 가르는 데 선형 공백 옥텟이 최소 하나 필요할 때 쓴다. 송신자는 SP 하나로
  만들어야 한다 (§5.6.3).[^fielding2022-rfc9110]
- OWS와 RWS는 SP 하나와 같은 의미론을 갖는다. 그렇다고 알려진 내용은 해석하거나 하류로 전달하기
  전에 SP 하나로 바꿔도 된다 (§5.6.3).[^fielding2022-rfc9110]
- BWS는 문법이 **역사적 이유로만** 선택적 공백을 허용하는 자리에 쓴다. 송신자는 메시지에 BWS를
  만들어서는 안 되고, 수신자는 그런 나쁜 공백을 파싱해 프로토콜 요소를 해석하기 전에 제거해야
  한다. BWS는 의미론이 없다 (§5.6.3).[^fielding2022-rfc9110]

## 인용 문자열

- 텍스트 열을 큰따옴표로 감싸면 **값 하나로 파싱된다** (§5.6.4).[^fielding2022-rfc9110]
- 역슬래시 옥텟은 인용 문자열과 코멘트 구성 안에서 한 옥텟짜리 인용 기제로 쓸 수 있다. 인용
  문자열의 값을 처리하는 수신자는 **인용 쌍을 역슬래시 다음 옥텟으로 치환된 것처럼 다뤄야 한다**
  (§5.6.4).[^fielding2022-rfc9110]
- 송신자는 인용 쌍을 남발하지 않아야 한다. 인용 문자열 안에서는 큰따옴표와 역슬래시를 인용할
  때만, 코멘트 안에서는 괄호와 역슬래시를 인용할 때만 만드는 것이 옳다
  (§5.6.4).[^fielding2022-rfc9110]

## 코멘트

- 일부 HTTP 필드에는 코멘트 텍스트를 괄호로 감싸 넣을 수 있다. 다만 아무 데나 되는 것이 아니라
  **필드 값 정의에 `comment`가 들어 있는 필드에서만** 허용된다
  (§5.6.5).[^fielding2022-rfc9110]
- 코멘트는 자기 자신을 중첩할 수 있게 정의되어 있다 (§5.6.5).[^fielding2022-rfc9110]

## 파라미터

- 파라미터(parameter)는 이름과 값 쌍의 인스턴스이고, 어떤 항목에 보조 정보를 덧붙이는 공통
  문법으로 필드 값에 자주 쓰인다. 각 파라미터는 보통 바로 앞의 세미콜론으로 구분된다
  (§5.6.6).[^fielding2022-rfc9110]
- 파라미터 이름은 대소문자를 가리지 않는다. 파라미터 값은 파라미터 이름의 의미론에 따라 대소문자를
  가릴 수도 있고 아닐 수도 있다 (§5.6.6).[^fielding2022-rfc9110]
- 토큰 생성 규칙에 맞는 파라미터 값은 **토큰으로 보내도 인용 문자열 안에 넣어 보내도 되고, 둘은
  동등하다** (§5.6.6).[^fielding2022-rfc9110]
- 원전이 각주로 못을 박는 자리가 하나 있다. 파라미터는 `=` 문자 둘레에 공백을 허용하지 않으며,
  나쁜 공백조차 안 된다 (§5.6.6).[^fielding2022-rfc9110]
