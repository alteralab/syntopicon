이 페이지의 질문: **EDW란 무엇이고, 왜 운영계와 분리하며, 어떤 아키텍처들이
그 요구를 감당해 왔는가.**

- 데이터 웨어하우징의 목표는 지식·지혜의 창출이 아니라, 데이터를 올바른 맥락으로
  옮겨 정보로 집계·통합·요약하는 것이다 — 지식과 지혜는 구조화가 어렵고 암묵적이라
  기계에 담기 힘들기 때문이다 (§1, p.18).[^linstedt2016]

## 왜 운영계와 분리하는가

- 분석 질의(analytical query)는 트랜잭션 질의와 달리 대량의 원시 레코드를
  집계·요약한다. 운영 데이터베이스에 분석 질의를 던지면 RDBMS가 집계를 위해 디스크의
  모든 하위 레코드를 읽어야 하고, 운영·분석 사용자가 한 데이터베이스를 공유하면
  과부하로 양쪽 모두의 사용성이 나빠진다 (§1–1.1, p.19).[^linstedt2016]
- 조직에는 고립된 데이터베이스, 이른바 데이터 섬(data island)이 흔하다. 이들 간의
  유일한 연결 고리는 업무 객체를 식별하는 업무 키(business key)이며, 이질적 소스의
  통합은 결국 업무 키 위에서 이뤄져야 한다 — 이는 보통 분석가 개인의 역량을 넘는다
  (§1, p.19).[^linstedt2016]
- 이 분리의 계보가 의사결정 지원 시스템(decision support system, DSS)이다: 소스
  시스템에서 추출한 데이터를 ETL로 별도의 분석 모델 데이터베이스에 적재해, DSS와의
  상호작용이 운영계를 늦추지 않게 한다 (§1.1.1, pp.19–20).[^linstedt2016] 1990년대에
  도입된 데이터 웨어하우스 시스템이 그 이후 DSS의 데이터 백엔드를 맡아 왔다
  (§1.1.1, p.20).[^linstedt2016]

## 같은 분리를 OLTP와 OLAP로 부르면

Kleppmann은 같은 분리를 방법론이 아니라 **접근 패턴과 사용자**의 언어로 서술한다.
이 절은 그 관점을 나란히 둔 것이다.

### 사람에서 출발한 구분

- 조직의 데이터를 필요로 하는 사람은 셋으로 나뉜다: 읽기·갱신 요청을 처리하는 서비스를
  만드는 백엔드 엔지니어, 경영 판단을 돕는 리포트를 만드는 업무 분석가(비즈니스
  인텔리전스, BI), 그리고 데이터 분석과 기계 학습으로 새 통찰이나 사용자향 제품 기능을
  만드는 데이터 과학자 (1장, pp.3–4).[^kleppmann2026]
- 분석가와 과학자는 도구도 방식도 다르지만 공통점이 둘 있다. 사용자와 백엔드 서비스가
  **생성한 데이터를 들여다본다**는 것, 그리고 (실수 교정을 빼면) 대체로 그 데이터를
  **수정하지 않는다**는 것 — 다만 원본을 가공한 파생 데이터셋은 만들 수 있다 (1장,
  p.4).[^kleppmann2026]
- 여기서 두 시스템 유형의 구분이 나온다 (1장, p.4):[^kleppmann2026]
  - **운영 시스템(operational systems)**: 데이터가 생성되는 백엔드 서비스와 데이터
    인프라. 애플리케이션 코드가 사용자 행동에 따라 데이터베이스의 데이터를 읽고 고친다.
  - **분석 시스템(analytical systems)**: 업무 분석가와 데이터 과학자의 필요를 위한
    시스템. 운영 시스템 데이터의 **읽기 전용 사본**을 담고 분석용 처리에 최적화된다.
- 이 성숙 과정에서 두 전문 역할이 생겼다: 운영계와 분석계를 통합할 줄 알고 조직의 데이터
  인프라를 더 넓게 책임지는 **데이터 엔지니어**, 그리고 분석가·과학자에게 더 쓸모 있도록
  데이터를 모델링·변환하는 **애널리틱스 엔지니어** (1장, p.4).[^kleppmann2026]

### 접근 패턴 — OLTP와 OLAP

- 업무 데이터 처리 초기에는 데이터베이스에 대한 쓰기가 대체로 상거래(판매·주문·급여
  지급 등)에 대응했다. 돈이 오가지 않는 영역으로 데이터베이스가 확장된 뒤에도
  **트랜잭션(transaction)** 이라는 말은 하나의 논리 단위를 이루는 읽기·쓰기 묶음을
  가리키며 남았다 (1장, p.5).[^kleppmann2026]
- 운영 시스템은 보통 키로 적은 수의 레코드를 찾는다 — 이를 점 질의(point query)라
  한다. 사용자 입력에 따라 레코드가 삽입·갱신·삭제되고, 애플리케이션이 대화형이므로
  이 접근 패턴을 **온라인 트랜잭션 처리(online transaction processing, OLTP)** 라
  부르게 됐다 (1장, p.5).[^kleppmann2026]
- 분석은 접근 패턴이 아주 다르다. 대개 **엄청난 수의 레코드를 훑어 개별 레코드가 아니라
  집계 통계(count·sum·average)를 계산한다.** 예: "1월 각 점포의 총매출은 얼마인가",
  "최근 프로모션 기간에 바나나가 평소보다 얼마나 더 팔렸나", "브랜드 X 기저귀와 가장
  자주 함께 구매되는 이유식 브랜드는 무엇인가". 이 사용 패턴을 트랜잭션 처리와 구별해
  **온라인 분석 처리(online analytical processing, OLAP)** 라 부른다 (1장,
  p.5).[^kleppmann2026]
- 두 시스템의 대비 (1장, p.6):[^kleppmann2026]
  - 주 읽기 패턴: 키로 개별 레코드를 가져오는 점 질의 / 많은 레코드에 대한 집계.
  - 주 쓰기 패턴: 개별 레코드의 생성·갱신·삭제 / 벌크 임포트(ETL)나 이벤트 스트림.
  - 사람 사용자: 웹·모바일 앱의 최종 사용자 / 의사결정 지원을 하는 내부 분석가.
  - 기계 사용례: 어떤 동작이 허가됐는지 확인 / 사기·악용 패턴 탐지.
  - 질의의 종류: 애플리케이션이 미리 정의한 고정 질의 / 분석가의 임의 탐색 질의.
  - 질의량: 작은 질의가 아주 많다 / 질의 수는 적고 각각이 복잡하다.
  - 데이터가 표현하는 것: 데이터의 최신 상태(현재 시점) / 시간에 걸쳐 일어난 사건의 이력.
  - 데이터셋 크기: 기가바이트~테라바이트 / 테라바이트~페타바이트.
- OLAP의 "온라인"이 무슨 뜻인지는 불분명하다. 아마 질의가 미리 정의된 리포트만이
  아니라 분석가가 탐색적 질의를 위해 OLAP 시스템을 대화형으로 쓴다는 것을 가리킬
  것이다 (1장, p.6).[^kleppmann2026]
- 운영 시스템에서는 대체로 사용자가 커스텀 SQL을 짜서 돌리도록 허용하지 않는다 —
  권한 없는 데이터를 읽거나 고칠 수 있고, 비싼 질의로 다른 사용자의 성능을 해칠 수
  있기 때문이다. 그래서 OLTP 시스템은 애플리케이션 코드에 박힌 고정 질의 집합을
  주로 돌리고 일회성 커스텀 질의는 유지보수·문제 해결에만 가끔 쓴다. 반면 분석
  데이터베이스는 사용자가 임의 SQL을 직접 쓰거나 Tableau·Looker·Microsoft Power BI
  같은 시각화·대시보드 도구로 질의를 자동 생성하게 해 준다 (1장,
  p.6).[^kleppmann2026]
- 분석 워크로드이면서 사용자향 제품에 임베드되는 부류도 있다. 이런 용도로 설계된
  시스템을 **제품 분석(product analytics)** 또는 **실시간 분석(real-time analytics)**
  이라 하며 Pinot·Druid·ClickHouse가 그 예다. 이들은 데이터를 실시간으로 수집하고 낮은
  지연의 질의 응답에 최적화된 반면, 전통적 OLAP 시스템은 배치로 수집하고 높은 처리량의
  질의 처리에 최적화된다 (1장, p.6).[^kleppmann2026]

### 웨어하우스가 생긴 시점과 이유

- 처음에는 같은 데이터베이스가 트랜잭션 처리와 분석 질의를 모두 맡았다. SQL은 이 점에서
  꽤 유연해서 두 종류 모두에 잘 통했다. **그러다 1980년대 말과 1990년대 초에 분석
  목적으로 OLTP 시스템을 쓰기를 그만두고 별도 데이터베이스에서 분석을 돌리는 흐름이
  생겼고, 그 별도 데이터베이스가 데이터 웨어하우스라 불렸다** (1장,
  p.7).[^kleppmann2026]
- 대기업은 고객향 웹사이트를 떠받치고, 매장 POS를 통제하고, 창고 재고를 추적하고,
  차량 경로를 계획하고, 공급자를 관리하고, 직원을 관리하는 등의 OLTP 시스템을 수십,
  수백 개까지 가진다. 각각이 복잡하고 유지 팀이 따로 필요하므로 **대체로 서로
  독립적으로 운영된다** (1장, p.7).[^kleppmann2026]
- 업무 분석가와 데이터 과학자가 이 OLTP 시스템들을 직접 질의하는 것이 바람직하지 않은
  이유 넷 (1장, p.7):[^kleppmann2026]
  - 관심 데이터가 여러 운영 시스템에 흩어져 있어 한 질의로 결합하기 어렵다(데이터
    사일로, data silo).
  - OLTP에 좋은 스키마와 데이터 레이아웃이 분석에는 덜 맞는다.
  - 분석 질의는 꽤 비쌀 수 있고, OLTP 데이터베이스에서 돌리면 다른 사용자의 성능에
    영향을 준다.
  - OLTP 시스템이 보안·컴플라이언스 때문에 사용자가 직접 접근할 수 없는 별도
    네트워크에 있을 수 있다.
- 데이터 웨어하우스는 그에 대비되는 **별도 데이터베이스**로, 분석가가 OLTP 운영에
  영향을 주지 않고 마음껏 질의할 수 있다. 회사의 온갖 OLTP 시스템에서 온 데이터의
  **읽기 전용 사본**을 담는다 (1장, p.7).[^kleppmann2026]
- 데이터를 가져오는 과정: OLTP 데이터베이스에서 (주기적 덤프나 연속적인 갱신 스트림
  중 하나로) 추출하고, 분석 친화적 스키마로 변환하고, 정제한 뒤 웨어하우스에 적재한다
  — 추출·변환·적재(extract–transform–load, ETL)다. **변환과 적재의 순서를 바꿔 적재
  후 웨어하우스 안에서 변환하면 ELT**가 된다 (1장, p.7).[^kleppmann2026] ETL 내부
  분해는 [ETL 34 서브시스템](../concepts/etl-subsystems.md) 참조.
- 어떤 경우 ETL의 데이터 원천은 CRM·이메일 마케팅·신용카드 처리 같은 외부 SaaS 제품이다.
  원본 데이터베이스에 직접 접근할 수 없고 벤더 API로만 접근할 수 있으므로, 이런 외부
  시스템의 데이터를 자기 웨어하우스로 들이면 SaaS API로는 불가능한 분석이 가능해진다.
  SaaS API용 ETL은 Fivetran·Singer·Airbyte 같은 전문 데이터 커넥터 서비스로 구현되는
  일이 많다 (1장, p.8).[^kleppmann2026]

### HTAP와 특화 추세

- 어떤 데이터베이스는 한 시스템에서 다른 시스템으로 ETL할 필요 없이 OLTP와 분석을
  함께 가능하게 하려는 **하이브리드 트랜잭션/분석 처리(hybrid
  transactional/analytical processing, HTAP)** 를 제공한다. 그러나 **많은 HTAP
  시스템은 내부적으로 OLTP 시스템과 별도의 분석 시스템이 공통 인터페이스 뒤에 감춰져
  결합된 형태**여서, 두 시스템의 구분은 동작을 이해하는 데 여전히 중요하다 (1장,
  p.8).[^kleppmann2026]
- HTAP가 있어도 목표와 요구가 달라 트랜잭션 시스템과 분석 시스템을 분리하는 것이
  흔하다. 특히 운영 시스템마다 자기 데이터베이스를 두는 것이 좋은 관행으로 여겨져
  분리된 운영 데이터베이스가 수백 개까지 생기는 반면, **기업에는 대체로 데이터
  웨어하우스가 하나**여서 분석가가 여러 운영 시스템의 데이터를 한 질의에서 결합할 수
  있다 (1장, pp.8–9).[^kleppmann2026] 서비스별 데이터베이스 규칙은
  [마이크로서비스와 서버리스](../concepts/microservices-and-serverless.md) 참조.
- 따라서 HTAP는 데이터 웨어하우스를 대체하지 않는다. **같은 애플리케이션이 많은 행을
  훑는 분석 질의와 개별 레코드의 낮은 지연 읽기·갱신을 모두 해야 할 때** 쓸모가 있다 —
  사기 탐지가 그런 워크로드일 수 있다 (1장, p.9).[^kleppmann2026]
- 운영계와 분석계의 분리는 더 넓은 추세의 일부다. 워크로드가 까다로워질수록 시스템은
  더 특화되고 특정 워크로드에 최적화됐다. **범용 시스템은 작은 데이터량은 무리 없이
  다루지만, 규모가 커질수록 시스템은 특화되는 경향이 있다** (1장,
  p.9).[^kleppmann2026]

## 워크로드가 인프라를 가른다

위의 OLTP·OLAP 대비가 접근 패턴의 언어라면, 이 절은 같은 대비를 **인프라 조달의
근거**로 다시 쓴 것이다. Linstedt는 물리 설계 장의 출발점을 여기에 둔다.

- 읽기와 쓰기의 비율부터 다르다. OLTP 시나리오에서도 대개 읽기 부하가 쓰기 부하를
  앞선다 — **80% 대 20%가 흔하다.** 그러나 비즈니스 인텔리전스(BI) 애플리케이션에
  비하면 OLTP의 읽기 수는 매우 적다 (§8.1, pp.224–225).[^linstedt2016]
- 부하가 걸리는 시간대도 다르다. 트랜잭션 시스템은 업무 사용자가 일하는 동안 하루
  내내 읽고 쓴다(화면 열기는 SELECT, 거래 수행은 SELECT와 INSERT, 제품 데이터 수정은
  UPDATE). BI는 보통 **이른 아침에 배치로 적재돼 사무실이 열기 전에 끝나며**, 그 배치가
  다루는 데이터셋은 트랜잭션 시스템보다 훨씬 크다. 웨어하우스의 데이터는 빠른 읽기에
  최적화된다 — 하루 워크로드의 대부분이 SELECT이기 때문이다. 응답 시간은 OLTP만큼
  결정적이지 않지만(제품 설명을 여는 데 몇 초를 기다릴 사용자는 없다) 여전히 빠른
  편이 낫다. OLAP은 여기에 더해 읽기 집약적일 뿐 아니라 계산과 집계를 많이 요구하며,
  이쪽 도구는 계산을 위해 데이터셋 전체에 접근하는 일이 잦다
  (§8.1, pp.224–225).[^linstedt2016]
- 인프라에 도전이 되는 워크로드 특성 여섯 (§8.1.1, pp.225–226):[^linstedt2016]
  - **데이터 지연(data latency)** — 데이터 생성과 소비 사이의 시차. 배치 구동
    웨어하우징은 지연 허용치가 크다(밤에 적재해 업무 사용자가 쓰기 한참 전에 준비된다).
    이 여유가 곧 설계의 자유다 — 벌크 데이터 처리와 집합 연산으로 데이터베이스 자원을
    더 효율적으로 쓸 수 있다. 실시간 웨어하우스는 예외이며 이 책의 범위 밖이다.
  - **정합성(consistency)** — OLTP에서는 즉시 정합성이 매우 결정적이다. 웨어하우징도
    같지만, 사용례에 따라서는 **최종 정합성(eventual consistency)으로 충분할 수 있다** —
    데이터를 많은 노드에 대규모로 분산할 때 흔한 선택이다. 저자들은 이것이 완벽한
    해법(모든 변경이 원자적이고 즉시 효력을 갖는 엄격한 정합성)이 아니라 CAP 정리를
    따르는 실용적 접근임을 명시한다. 정합성 모델 자체는
    [정합성 모델](../concepts/consistency-models.md)·[CAP와 PACELC](../concepts/cap-and-pacelc.md)에 있다.
  - **갱신 가능성(updateability)** — OLTP는 기존 데이터를 자주 갱신하지만, BI·OLAP
    애플리케이션은 데이터가 디스크에 **영구적으로** 쓰인다고 가정하는 일이 많다(웹
    서버 로그처럼 결코 바뀌지 않는 데이터). 대부분의 관계형 데이터베이스에서 UPDATE가
    INSERT보다 훨씬 느리다는 사실을 생각하면 이는 큰 이점이며, 수집 절차를 그 성질에
    맞춰 최적화할 수 있다.
  - **데이터 타입(data types)** — 가장 빠른 것은 표(tabular) 형태의 데이터다. 계층형이나
    비정형(텍스트·오디오 파일) 데이터를 관계형 시스템에서 다루려면 평탄화하거나 구조를
    입혀야 하고, 그것이 목표가 아니면 웨어하우스를 NoSQL에 올리거나 일부를 NoSQL에
    맡긴다.
  - **응답 시간(response time)** — 사용자 질의에 답하려면 요약을 위해 대용량을 디스크에서
    읽어야 하는 경우가 잦다. 그래서 많은 OLAP 엔진이 데이터를 **미리 스테이징하고 계산·
    집계를 앞당겨** 예측된 질의에 훨씬 빨리 답한다. 데이터를 웨어하우스에 쓰는 쪽의 응답
    시간도 함께 따져야 한다.
  - **예측 가능성(predictability)** — OLTP는 하루 부하가 예측 가능한 편이고, 웨어하우징에서도
    관계형 리포트와 대시보드는 같은 질의를 반복하므로 예측 가능하다. 반면 애드혹 질의와
    데이터 탐색은 예측 불가능하다.
- 결론이 조달 규칙이 된다: 워크로드 특성이 다르므로 **하드웨어 구성도 OLTP·BI·OLAP마다
  다르게 최적화해야 하며, OLTP와 OLAP에 같은 인프라를 쓰는 것은 권장되지 않는다.**
  웨어하우스 애플리케이션을 담을 인프라와 트랜잭션 시스템을 담을 인프라를 따로 두어야
  각각을 특성에 맞게 최적화할 수 있다 (§8.1.1, p.226).[^linstedt2016] 그 인프라를 실제로
  고르는 자리는 [물리 데이터 웨어하우스 설계](../concepts/physical-data-warehouse-design.md)다.

## 데이터 웨어하우스 시스템의 성격

- 정의는 원문 그대로 (§1.1.2, p.20):[^linstedt2016]

> A data warehouse system (DWH) is a data-driven decision support system that
> supports the decision-making process in a strategic sense and, in addition,
> operational decision-making, for example real-time analytics to detect credit
> card fraud or on-the-fly recommendations of products and services.

- 주제 지향(subject-oriented): ERP·운영계의 기능 지향과 달리 분석용 주제영역(예:
  보험사의 고객·보험계약·보험료·청구)에 초점을 둬, 같은 실세계 사건·객체에 관한
  모든 데이터를 통합 분석할 수 있게 한다 (§1.1.2, p.20).[^linstedt2016]
- 이력 보존: 적재된 데이터는 모두 보관되어 시간 가변(time-variant) 분석이 가능하다.
  소스에는 더 이상 없는 데이터가 많으므로 데이터는 비휘발(nonvolatile)이고, 이는
  정보 시스템의 감사 가능성(auditability) 요건이기도 하다 (§1.1.2, p.21).[^linstedt2016]
- 적재 시 하는 일: 소스마다 다른 업무 키·더티 데이터·데이터 타입과 문자 인코딩
  차이를 정제하고(품질 자체를 보고해야 하는 경우 등 예외 있음), 요구 세분도
  (granularity)에 맞춰 집계한다. 엔지니어는 다층 분석이 가능하도록 가급적 최세분도
  적재를 지향한다 (§1.1.2, p.21).[^linstedt2016]

## EDW: 하나의 주제영역에서 조직 전체로

- EDW는 단일 주제영역이 아니라 조직의 모든 업무 데이터와 업무 규칙을 담으려 하며,
  필요한 모든 주제영역을 업무 사용자가 쓸 수 있는 형태로 제공한다 (§1.2, p.21).[^linstedt2016]
- 접근성(access): 즉시·주문형·고성능 연결만이 아니라, 제시된 정보의 의미를 이해하기
  쉬워야 한다는 뜻까지 포함한다 — 올바른 라벨링과 분석·표현용 애플리케이션의 가용성
  (§1.2.1, pp.21–22).[^linstedt2016]
- 복수 주제영역: 부서마다 데이터 요구가 달라 EDW는 여러 주제영역을 제공하고, 각
  주제영역이 그 사용자가 요구하는 "정보의 정의"를 따른 진실 버전을 내놓는다. 원시
  데이터를 통합·정제해 EDW에 넣고 그 위에 주제영역별 데이터 마트를 짓는데, EDW를
  소스로 삼는 종속(dependent) 데이터 마트가 운영계에서 직접 뽑는 독립(independent)
  마트보다 정제·통합 노력이 덜 든다 (§1.2.2, p.22).[^linstedt2016]
- 단일 진실 버전(single version of truth): 전사 데이터 통합의 목표. 운영계 간
  동기화 지연·수작업 입력 등으로 생기는 복수의 진실을, 선도 시스템 선정·소스 우선순위
  같은 업무 결정으로 정제해 얻는다. 단, 부서마다 "진실이 무엇인가"의 정의가 달라
  복수 주제영역이 필요해진다 (§1.2.3, p.22).[^linstedt2016]
- 단일 사실 버전(single version of facts): 정보가 아니라 **모든 원시 데이터를 항상**
  보관·제공하자는 목표. 컴플라이언스 요구에서 출발한 이 아이디어가 Data Vault 발명으로
  이어졌고, Raw Data Vault에 구현된 핵심 원리다. Data Vault 기반 EDW는 단일 진실
  버전과 단일 사실 버전을 모두 제공한다 (§1.2.4, pp.22–23).[^linstedt2016]
  - **반대편 처방**: Kleppmann은 같은 컴플라이언스를 근거로 반대 방향을 말한다 —
    저장의 비용이 청구서를 넘어 책임·평판·과징금까지 포함하므로 어떤 데이터는 아예
    저장하지 말고 지워야 한다는 데이터 최소화(data minimization)이며, 이는 GDPR과
    맞는다 (1장, p.25).[^kleppmann2026] 단 대상이 온전히 같지는 않다 — 이쪽은
    감사 가능성을 위한 업무 데이터, 저쪽은 개인 데이터다. 어느 쪽이 참인지의 문제가
    아니라 데이터 종류별 정책 판단이라 `contradicts`는 달지 않는다(PLAN §2.1).
    상세는 [데이터 레이크](../concepts/data-lake.md).
- 그 밖의 요구: 사명 수행에 필수(mission-critical)인 자산으로서의 품질 책임
  (§1.2.5, p.23), 데이터량·사용자 증가에 대한 확장성과 MPP(massively parallel
  processing) (§1.2.6, p.23), 볼륨·속도·다양성의 3V로 정의되는 빅데이터 수용
  (§1.2.7, pp.23–24), 야간 적재 시간창과 질의 응답성 같은 성능 (§1.2.8, pp.24–25),
  소스·변환·타깃 3영역에서 오는 복잡성 관리 (§1.2.9, p.25), 비용 통제 (§1.2.11,
  pp.26–27).[^linstedt2016]
- 감사와 컴플라이언스: 데이터의 출처·추출 시점의 추적을 요구한다. 단 Inmon은 감사
  기능을 DW에 넣는 데 반대하는 근거(불필요 데이터 적재 강제, 적재 타이밍 변화,
  백업·복구 요건 급변, 최저 세분도 강제)를 제시했고, 저자들은 감사 가능성을 "어디서
  추출했나·언제·어떤 프로세스로·어디에 쓰였나"에 답하는 수준으로 한정하자는 의견이다
  — 운영계가 데이터를 어떻게 획득했는가는 DW가 답할 질문이 아니다 (§1.2.10,
  p.26).[^linstedt2016]
- 업무 규칙의 위치가 비용·민첩성을 좌우한다: 업무 요구를 DW 적재 사이클(상류)이 아닌
  데이터 마트 적재(하류, 업무 사용자 가까이)로 옮기면 자동 생성으로 유지보수를 통제하고
  요구 변화에 빠르게 반응할 수 있다. 팀의 민첩성은 데이터 처리 과정에 박아 넣은
  복잡성의 양에 정비례한다 (§1.2.11, p.27).[^linstedt2016]

## 아키텍처 지형: 2계층과 3계층

- 흔한 DW 아키텍처는 계층형 접근이다 (§1.4, pp.28–29).[^linstedt2016]
- **Kimball 2계층**: 스테이징 + 데이터 웨어하우스. 스테이지 영역은 소스 테이블을
  본뜬 원시 데이터의 정확한 사본으로, 소스 시스템에 가하는 연산과 추출 시간을 줄이는
  게 주목적이다. DW 계층은 [차원 모델](../concepts/dimensional-modeling.md)로 만들어지며,
  표준 차원(conformed dimension)으로 묶인 데이터 마트들의 논리적 연합이다 — 따라서
  업무 규칙을 DW 계층 **이전에** 구현해 데이터셋을 적합·정렬해야 한다. 장점은 소스에서
  차원 저장소를 만들기 쉽다는 것, 단점은 같은 소스에서 두 번째 차원 모델을 지으려면
  스테이징부터 다시 적재해야 하고 기존 ETL 패키지를 재사용할 수 없다는 것이다
  (§1.4.1, p.29).[^linstedt2016] 전체 수명주기 관점은
  [Kimball DW/BI 아키텍처](../concepts/kimball-dwbi-architecture.md) 참조.
- **Inmon 3계층**: 스테이징과 차원 모델 사이에 원자적(atomic) 데이터 웨어하우스 —
  흔히 정규화된 운영 데이터 스토어(operational data store, ODS) — 를 둔다. DW는
  제3정규형의 원시 데이터로 전사를 통합하되 소스의 물리 테이블에 기반해 거대한 운영
  데이터베이스처럼 동작한다. 데이터가 이미 정제·통합돼 있어 새 데이터 마트를 만들기
  훨씬 쉽다는 게 장점, 전체 구축에 더 많은 처리가 들고 많은 마트가 ODS에 의존하면
  데이터 모델 변경이 부담이 된다는 게 단점이다 (§1.4.2, p.30).[^linstedt2016]
- 두 아키텍처 모두 확장성(특히 변경 흡수) 관점의 한계가 있고, 저자들은 그 대안으로
  [Data Vault 2.0 아키텍처](../concepts/data-vault-architecture.md)를 제시한다 (§1.2.6,
  p.23).[^linstedt2016]
- 여기에 더해, 관계형 스키마를 강제하지 않는 파일 저장소를 분석 계층으로 두는 갈래가
  [데이터 레이크](../concepts/data-lake.md)다 (1장, pp.9–10).[^kleppmann2026]

## 아키텍처 유형으로서의 데이터 웨어하우스

데이터 엔지니어링 쪽 소스는 웨어하우스를 방법론이 아니라 **데이터 아키텍처의 한 유형**으로
목록에 올린다 — 가장 오래되고 가장 잘 확립된 것으로.

- **데이터 웨어하우스(data warehouse)는 보고와 분석에 쓰이는 중앙 데이터 허브다. 데이터
  웨어하우스의 데이터는 통상 분석 유스케이스를 위해 고도로 형식화되고 구조화돼 있다. 그것은
  가장 오래되고 가장 잘 확립된 데이터 아키텍처에 속한다** (3장, p.98).[^reis2022]
- 인몬의 원 정의를 여전히 인정한다 — **1989년 빌 인몬이 데이터 웨어하우스의 관념을 창시하며
  그것을 "경영진의 결정을 지원하는, 주제 지향적이고(subject-oriented) 통합되고(integrated)
  비휘발적이며(nonvolatile) 시간 변이하는(time-variant) 데이터의 모음"으로 서술했다. 데이터
  웨어하우스의 기술적 측면은 유의하게 진화했지만 저자들은 이 원래 정의가 오늘날에도 여전히
  무게를 지닌다고 느낀다** (3장, p.98).[^reis2022] 위
  [EDW: 하나의 주제영역에서 조직 전체로](#edw-하나의-주제영역에서-조직-전체로)와 같은 정의다.
- 경제가 바뀌었다 — **과거에 데이터 웨어하우스는 데이터 시스템을 취득하고 웨어하우스를 유지할
  내부 팀에 비용을 대는 상당한 예산(흔히 수백만 달러)을 가진 엔터프라이즈에서 널리 쓰였다. 이는
  비싸고 노동 집약적이었다. 그 뒤로 확장 가능한 종량제 모델이 클라우드 데이터 웨어하우스를 아주
  작은 회사에도 접근 가능하게 만들었다. 제3자 제공자가 웨어하우스 인프라를 관리하므로 회사는
  데이터의 복잡성이 커지는 와중에도 더 적은 인원으로 훨씬 많은 일을 할 수 있다** (3장,
  p.98).[^reis2022]

## 조직 아키텍처와 기술 아키텍처

- 두 종류를 가른다 — **조직 데이터 웨어하우스 아키텍처(organizational data warehouse
  architecture)는 특정 업무 팀 구조·프로세스에 연관된 데이터를 조직한다. 기술 데이터 웨어하우스
  아키텍처(technical data warehouse architecture)는 MPP처럼 데이터 웨어하우스의 기술적 성질을
  반영한다. 회사는 MPP 시스템 없는 데이터 웨어하우스를 가질 수도 있고 데이터 웨어하우스로 조직되지
  않은 MPP 시스템을 돌릴 수도 있다. 그러나 기술 아키텍처와 조직 아키텍처는 선순환 속에 존재해
  왔고 자주 서로 동일시된다** (3장, p.98).[^reis2022]
- 조직 아키텍처의 두 주요 특성 (3장, p.99):[^reis2022]
  - **온라인 분석 처리(OLAP)를 프로덕션 데이터베이스(온라인 트랜잭션 처리)에서 분리한다** —
    **이 분리는 업무가 성장할 때 결정적이다. 데이터를 별도의 물리 시스템으로 옮기는 것은 부하를
    프로덕션 시스템에서 떨어뜨리고 분석 성능을 개선한다.** 같은 분리를 다른 어휘로 서술한 쪽은
    위 [같은 분리를 OLTP와 OLAP로 부르면](#같은-분리를-oltp와-olap로-부르면)이다.
  - **데이터를 중앙화하고 조직한다** — **전통적으로 데이터 웨어하우스는 ETL을 써서 애플리케이션
    시스템에서 데이터를 끌어온다. 추출 단계는 원천 시스템에서 데이터를 끌어온다. 변환 단계는
    데이터를 정제·표준화하고, 고도로 모델링된 형태로 업무 로직을 조직·부과한다. 적재 단계는
    데이터를 데이터 웨어하우스 대상 데이터베이스 시스템으로 밀어 넣는다. 데이터는 사업 부문이나
    부서의 분석 필요를 섬기는 여러 데이터 마트에 적재된다.**
- 왜 MPP가 붙었는가 — **기술 데이터 웨어하우스 아키텍처에 관해서는, 1970년대 후반 첫 MPP
  시스템이 1980년대에 인기를 얻었다. MPP는 본질적으로 관계형 애플리케이션 데이터베이스에서 쓰이는
  것과 같은 SQL 의미론을 지원한다. 다만 그것들은 방대한 양의 데이터를 병렬로 스캔하도록 최적화돼
  고성능 집계와 통계 계산을 가능하게 한다. 최근 몇 년 사이 MPP 시스템은 특히 클라우드 데이터
  웨어하우스에서 더 큰 데이터와 질의를 촉진하기 위해 행 기반 아키텍처에서 컬럼 기반 아키텍처로
  점점 옮겨 왔다** (3장, p.99).[^reis2022] 컬럼 지향의 기제는
  [컬럼 지향 저장](../concepts/column-oriented-storage.md)에 있다.

## ETL과 ELT

- **ETL의 한 변형이 ELT다. ELT 데이터 웨어하우스 아키텍처에서는 데이터가 프로덕션 시스템에서
  데이터 웨어하우스의 스테이징 영역으로 다소 직접적으로 옮겨진다. 이 맥락에서 스테이징은 데이터가
  원시(raw) 형태임을 가리킨다. 외부 시스템을 쓰는 대신 변환이 데이터 웨어하우스에서 직접 처리된다.
  그 의도는 클라우드 데이터 웨어하우스와 데이터 처리 도구의 막대한 계산 능력을 활용하는 것이다.
  데이터는 배치로 처리되고 변환된 출력은 분석용 테이블과 뷰로 쓰인다** (3장, pp.99–100).[^reis2022]
- 스트리밍에서도 쓰인다 — **ELT는 스트리밍 배치에서도 인기가 있는데, CDC 프로세스에서 이벤트가
  스트리밍돼 스테이징 영역에 저장된 다음 데이터 웨어하우스 안에서 후속 변환된다** (3장,
  p.100).[^reis2022] 그 CDC는
  [변경 데이터 캡처](../concepts/change-data-capture.md)에 있다.
- 이름이 겹치는 두 번째 ELT에 주의한다 — **ELT의 두 번째 판본이 하둡 생태계의 빅데이터 성장기에
  대중화됐다. 이것이 읽기 시점 변환 ELT(transform-on-read ELT)다** (3장, p.100).[^reis2022] 그
  쪽은 [데이터 레이크](../concepts/data-lake.md)의 읽기 스키마 절이 다룬다.

## 클라우드 데이터 웨어하우스

- **클라우드 데이터 웨어하우스는 온프레미스 데이터 웨어하우스 아키텍처의 유의한 진화를 대표하며,
  그 결과 조직 아키텍처에도 유의한 변화를 가져왔다. Amazon Redshift가 클라우드 데이터 웨어하우스
  혁명을 시작했다. 다음 몇 년을 위해 MPP 시스템의 크기를 적절히 산정하고 그것을 조달하기 위해
  수백만 달러짜리 계약에 서명해야 하는 대신, 회사에는 수요에 따라 Redshift 클러스터를 띄우고
  데이터·분석 수요가 자라면 시간에 따라 확장할 선택지가 생겼다. 특정 워크로드를 섬기기 위해 수요에
  따라 새 Redshift 클러스터를 띄우고 더 이상 필요 없을 때 클러스터를 빠르게 지울 수도 있었다**
  (3장, p.100).[^reis2022]
- 다음 단계가 저장과 연산의 분리다 — **Google BigQuery·Snowflake와 다른 경쟁자들이 연산을 저장에서
  분리하는 발상을 대중화했다. 이 아키텍처에서 데이터는 객체 저장소에 담겨 사실상 무한한 저장을
  허용한다. 이는 또한 사용자에게 수천 노드의 장기 비용 없이 애드혹 빅데이터 능력을 제공하면서
  수요에 따라 연산 능력을 띄울 선택지를 준다** (3장, p.100).[^reis2022] 그 계층화는
  [클라우드 네이티브 아키텍처](../concepts/cloud-native-architecture.md)에 있다.
- 경계가 흐려진다 — **클라우드 데이터 웨어하우스는 아주 최근까지 하둡 클러스터를 요구하던 많은
  빅데이터 유스케이스를 감당하도록 MPP 시스템의 능력을 확장한다. 그것들은 단일 질의에서 페타바이트급
  데이터를 쉽게 처리할 수 있다. 통상 행당 수십 메가바이트의 원시 텍스트 데이터나 극히 풍부하고
  복잡한 JSON 문서의 저장을 허용하는 데이터 구조를 지원한다. 클라우드 데이터 웨어하우스(와 데이터
  레이크)가 성숙하면서 데이터 웨어하우스와 데이터 레이크 사이의 선은 계속 흐려질 것이다** (3장,
  p.100).[^reis2022]
- 이름 자체를 버릴 수도 있다는 전망 — **클라우드 데이터 웨어하우스가 제공하는 새 능력의 영향이
  너무 유의해서 데이터 웨어하우스라는 용어를 통째로 버리는 것을 고려할 수도 있다. 대신 이
  서비스들은 전통적 MPP 시스템이 제공하던 것보다 훨씬 넓은 능력을 가진 새 데이터 플랫폼(data
  platform)으로 진화하고 있다** (3장, p.101).[^reis2022]

## 데이터 마트

- **데이터 마트(data mart)는 분석과 보고를 섬기도록 설계된 웨어하우스의 더 정제된 부분집합으로,
  단일 하위 조직·부서·사업 부문에 초점을 둔다. 모든 부서가 자기 필요에 특정한 자기 데이터 마트를
  갖는다. 이는 더 넓은 조직이나 사업을 섬기는 완전한 데이터 웨어하우스와 대조된다** (3장,
  p.101).[^reis2022]
- 존재 이유가 둘이다 — **첫째, 데이터 마트는 분석가와 보고서 개발자가 데이터에 더 쉽게 접근하게
  만든다. 둘째, 데이터 마트는 초기 ETL 또는 ELT 파이프라인이 제공하는 것 너머의 추가 변환 단계를
  제공한다. 보고서나 분석 질의가 복잡한 조인과 집계를 요구하면, 특히 원시 데이터가 클 때, 이는
  성능을 유의하게 개선할 수 있다. 변환 프로세스가 라이브 질의의 성능을 개선하기 위해 조인·집계된
  데이터로 데이터 마트를 채울 수 있다** (3장, p.101).[^reis2022]

[^reis2022]: Reis & Housley 2022, 3장 "Designing Good Data Architecture"

[^linstedt2016]: Linstedt & Olschimke 2016, 1장 "Introduction to Data Warehousing" · 8장 "Physical Data Warehouse Design"
[^kleppmann2026]: Kleppmann & Riccomini 2026, 1장 "Trade-Offs in Data Systems Architecture"
