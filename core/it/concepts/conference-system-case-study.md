## 버전 조건

> **버전 조건**: 2022년 저술 시점. 아래 로드맵이 대는 도구 이름(쿠버네티스·Testcontainers·
> Argo Rollouts)과 C4 모형의 이름은 그 시점의 것이다. 체계의 구조와 도면 세 층의 규정은
> 도구와 무관하다.

## 왜 회의 시스템인가

- 저자들이 도메인 선정 이유를 두 조건으로 적는다 — **알아보기 쉽지만 진화적 아키텍처를
  모델링하기에 충분한 복잡도를 준다** (서론, p.xxv).[^gough2022]
- 체계가 하는 일은 셋이다 — 외부 고객이 **참석자 계정을 만들고, 이용할 수 있는 회의 세션을
  훑어보고, 참석을 예약한다** (서론, p.xxv).[^gough2022]
- **지어낸 체계이되 책 전체를 관통한다** — 저자들은 추상 개념이 실무 적용으로 어떻게 옮겨지는지를
  독자가 탐색하게 하는 것이 목표라고 적고, 사례 연구가 **책이 나아가는 동안 함께 진화한다**고
  밝힌다 (서문, p.xv).[^gough2022]

## 출발점은 삼계층이다

- **사례 연구의 출발점은 전형적인 삼계층(three-tier) 아키텍처**다. UI와 서버 쪽 처리 계층과
  데이터스토어로 되어 있다 (서론, p.xxviii).[^gough2022]
- 그 안을 한 겹 열면 이렇다 — **고객이 웹 애플리케이션과 상호작용하고, 웹 애플리케이션이 회의
  애플리케이션의 API들을 호출하며, 회의 애플리케이션이 SQL로 뒤에 선 데이터스토어를 질의한다**
  (서론, p.xxvi).[^gough2022]

## 컴포넌트 넷과 데이터베이스

- **현재 체계에 관여하는 것은 주요 컴포넌트 넷과 데이터베이스**다 (서론, p.xxvi).[^gough2022]
- **API 컨트롤러(API Controller)** — **UI에서 들어오는 모든 트래픽을 맞고 그 요청을 체계 안
  어디로 보낼지 결정한다.** 그리고 **선 위(on the wire)의 네트워크 수준 표현을 코드 안의 객체나
  표현으로 마셜링하는 책임**도 이 컴포넌트가 진다 (서론, p.xxvi).[^gough2022]
  - **이 컴포넌트가 프로세스 안 라우팅의 관점에서 흥미롭고 접합점 또는 프런트 컨트롤러(front
    controller) 패턴으로 작동한다** — **모든 요청이 컨트롤러를 지나고 컨트롤러가 그 요청을 어디로
    보낼지 결정한다.** 저자들은 이것이 API 요청과 처리에서 중요한 패턴이라고 적는다 (서론,
    p.xxvi).[^gough2022]
  - 그 컨트롤러를 **프로세스 밖으로 내보낼 가능성**을 3장에서 본다고 예고한다 (서론,
    p.xxvi).[^gough2022]
- **참석자(Attendee)·예약(Booking)·세션(Session)** 셋은 **요청을 질의로 번역하고 데이터베이스에
  SQL을 프로세스 밖으로 실행한다** (서론, p.xxvi).[^gough2022]
- **기존 아키텍처에서 데이터베이스가 중요한 컴포넌트다** — **관계를 강제할 수도 있는 자리**이고,
  저자들이 드는 예가 **예약과 세션 사이의 제약**이다 (서론, p.xxvi).[^gough2022]

## 같은 그림에서 프로세스 안과 밖이 갈린다

- **같은 한 장의 컴포넌트 도면 안에서 두 종류의 호출이 나란히 보인다** (서론,
  p.xxvii).[^gough2022]
  - **웹 애플리케이션에서 API 컨트롤러로 가는 화살표는 프로세스 밖(out-of-process) 호출**이다.
  - **API 컨트롤러에서 참석자 컴포넌트로 가는 화살표는 프로세스 안(in-process) 호출**이다.
  - **회의 애플리케이션 경계 안의 상호작용은 전부 프로세스 안 호출**이다.
- **프로세스 안 호출은 잘 정의되어 있고 그 애플리케이션을 구현한 프로그래밍 언어가 제한한다.
  그 호출은 컴파일 시점에 안전하다** — 저자들이 괄호로 그 뜻을 밝힌다: **교환 기제가 지켜야 할
  조건이 코드를 쓰는 시점에 강제된다** (서론, p.xxvii).[^gough2022]
- **프로세스 안 API와 프로세스 밖 API라는 구분 자체의 규정**은
  [API 개념과 스타일 분류](../concepts/api-concepts-and-styles.md)의 해당 절이 갖는다. 여기 있는
  것은 **그 구분이 한 체계의 도면에서 어떻게 보이는가**다.

## 바꾸라는 요구 셋

- **지금의 아키텍처가 여러 해 동안 잘 돌아갔지만 회의 소유자가 개선 셋을 요구했고 그것이
  아키텍처 변경을 몰고 있다** (서론, p.xxviii).[^gough2022]
  - **모바일 애플리케이션을 짓고 싶다.**
  - **체계를 전 세계로 넓혀 한 해 한 번이 아니라 수십 회의를 운영하고 싶다.** 그 확장을 위해
    **발표자와 그들의 세션 신청을 관리하는 외부 CFP(Call for Papers) 체계와 통합**하려 한다.
  - **사설 데이터센터를 없애고 전 세계에 닿는 클라우드 플랫폼 위에서 체계를 돌리고 싶다.**
- **제약이 목표에 붙어 있다** — **기존 프로덕션 체계에 영향을 주지 않고, 모든 것을 한 번에 다시
  쓰지도 않으면서** 새 요건을 받게 이전하는 것이 목표다 (서론, p.xxviii).[^gough2022]

## 계층에서 API로 옮기려면 모델이 필요하다

- **진화적 아키텍처를 논하려면 컴포넌트들이 API 요청을 처리하는 방식을 생각할 모델이 먼저
  필요하다.** 그 모델은 **공개 클라우드와 데이터센터의 가상 머신과 하이브리드 접근 모두에서
  통해야 한다** (서론, p.xxviii).[^gough2022]
- **트래픽을 추상으로 잡으면 API 소비자와 API 서비스(때로 API 프로듀서라 불린다) 사이의 프로세스
  밖 상호작용을 살필 수 있게 된다** (서론, p.xxviii).[^gough2022]
- **SOA나 마이크로서비스 기반 아키텍처 같은 접근에서는 API 상호작용을 모델링하는 일이
  결정적이다.** 저자들이 그 무게를 한 문장으로 적는다 — **API 트래픽과 컴포넌트 사이 통신의
  양식을 배우는 것이 디커플링의 이점을 실현하느냐 유지보수의 악몽을 만드느냐를 가른다** (서론,
  p.xxviii).[^gough2022]
- **그 추상이 실제로 무엇으로 나뉘는가**(남북 트래픽과 동서 트래픽, 그리고 각각을 통제하는
  중개자)는 [API 게이트웨이와 서비스 메시](../concepts/api-gateway-and-service-mesh.md)가 갖는다.

## 진화적 한 걸음

- **트래픽 패턴의 종류를 생각하기 위해 저자들이 사례 연구 아키텍처에 작은 진화적 한 걸음을
  먼저 밟는다** (서론, pp.xxviii–xxix).[^gough2022]
- **참석자 컴포넌트를 레거시 회의 체계 안의 패키지나 모듈이 아니라 독립된 서비스로
  리팩터링한다** (서론, p.xxix).[^gough2022]
- **그 한 걸음으로 회의 체계에 트래픽 흐름이 둘 생긴다** — **고객과 레거시 회의 체계 사이의
  상호작용**, 그리고 **레거시 체계와 참석자 체계 사이의 상호작용**이다 (서론,
  p.xxix).[^gough2022]
- **이 결정이 이 책의 첫 ADR(ADR001)로 기록된다.** 그 기록의 형식과 상태 칸, 그리고 이 책이
  결정을 적는 방식은 [아키텍처 결정 기록](../concepts/architecture-decision-records.md)이 갖는다.
  - **귀결 칸에 적힌 것 셋이 이 사례 연구의 남은 장을 미리 예고한다** — **참석자 서비스 호출이
    지연을 들여올 수 있어 테스트가 필요하다는 것**, **참석자 서비스가 단일 장애점이 될 수 있어
    완화 조치가 필요할 수 있다는 것**, 그리고 **소비자가 여럿인 모형을 계획하고 있으므로 우발적인
    깨는 변경을 줄이려면 좋은 설계와 버저닝과 테스트를 보장해야 한다는 것**이다 (서론 표 I-1,
    p.xxxiv).[^gough2022]
  - 저자들 스스로 **그 귀결 가운데 일부가 꽤 중대해서 더 논의가 필요하고, 일부는 뒤의 장으로
    미룬다**고 적는다 (서론, p.xxxiv).[^gough2022]

## 같은 서비스의 소비자 둘이 다른 결합을 요구한다

- **프로듀서는 참석자 팀이 소유하고, 그 팀이 유지하는 핵심 관계가 둘이다** (1장,
  pp.3–4).[^gough2022]
  - **참석자 팀이 프로듀서이고 레거시 회의 팀이 소비자인 관계** — **두 팀 사이가 가깝고 구조
    변경을 쉽게 조율할 수 있다. 프로듀서와 소비자 서비스 사이에 강한 응집(cohesion)을 이루는
    것이 가능하다** (1장, p.4).[^gough2022]
  - **참석자 팀이 프로듀서이고 외부 CFP 체계 팀이 소비자인 관계** — **팀 사이에 관계가 있기는
    하지만 통합이 깨지지 않게 변경을 조율해야 한다. 느슨한 결합이 요구되고 깨는 변경은 조심스럽게
    관리해야 한다** (1장, p.4).[^gough2022]
- **이 대조가 1장 전체의 설계 선택을 끄는 힘이다** — 저자들은 두 접근을 이 장 내내 맞대어
  비교하겠다고 예고한다 (1장, p.4).[^gough2022] 그 비교가 실제로 도착하는 자리가
  [gRPC와 RPC 스타일](../concepts/grpc-and-rpc-style.md)의 교환 모델링 지침이다.

## 분리가 낳은 상호작용을 무엇으로 검증하는가

**참석자 API를 떼어낸 결정이 2장에서 곧바로 테스트의 물음이 된다.**

- **분리가 새 상호작용을 들여온다** — 참석자 API를 나머지 회의 체계에서 떼어낸 이유는 위
  [진화적 한 걸음](#진화적-한-걸음)에 있고, 그 분리가 **새 상호작용을 들여온다.** 이제 참석자
  API를 **외부 CFP 체계와 레거시 회의 체계 둘이 쓴다** (2장 그림 2-1, p.28).[^gough2022]
- **2장이 하는 일이 둘이다** — **참석자 서비스에 필요한 테스트**와, **레거시 회의 체계와 참석자
  API 사이의 상호작용을 테스트가 어떻게 검증하는가**다 (2장, p.28).[^gough2022]
- **저자들이 그 동기를 자기 경험으로 댄다** — **새 릴리스가 나가면서 일관성을 잃거나 우발적으로
  깨는 변경을 내는 API를 충분히 보았고 그것이 주로 테스트 부족 때문**이라고 적는다. 새 참석자
  API가 그 함정을 피하려면 **올바른 결과가 늘 돌아오리라는 확신**이 있어야 하고 **그것이 생기는
  유일한 길이 알맞은 수준의 테스트에 투자하는 것**이다 (2장, p.28).[^gough2022]
- **네 테스트가 이 체계의 어느 자리에 놓이는가** (2장, pp.38·42·47·49):[^gough2022]
  - **계약 테스트** — 소비자 주도 계약을 적용하면 **레거시 회의 체계에서 참석자 API 서비스로 풀
    리퀘스트가 제출되고** 그 상호작용을 두고 논의가 일어난다.
  - **컴포넌트 테스트** — 참석자 목록 엔드포인트를 대상으로 삼고 **바깥 데이터베이스 의존을
    대신할 목으로 DAO를 세운다.**
  - **통합 테스트** — **아직 개발되지 않은 gRPC 인터페이스를 뼈대 스텁으로 만들어 컨테이너로
    게시**해 개발자들이 경계 너머로 실제 호출을 걸게 하고, **바깥 데이터베이스는 프로덕션과 같은
    판을 컨테이너로 띄워** 경계를 시험한다.
  - **종단 테스트** — **데이터베이스와 참석자 서비스는 띄우되 레거시 회의 체계는 띄우지
    않는다.** 이 테스트에 군더더기라는 것이 저자들의 판단이고, 그래서 **종단 테스트도 때로 경계를
    필요로 한다**고 적는다.
- **이 넷의 규정과 경계를 긋는 규칙은 [API 테스트의 유형과 경계](../concepts/api-test-types-and-boundaries.md)가
  갖고, 계약을 누가 쓰고 어디에 두는가는 [소비자 주도 계약](consumer-driven-contracts.md)이
  갖는다.** 이 절은 **그 기법들이 이 체계의 어디에 떨어지는가**의 색인이다.

## 참석자 서비스를 소비자에게 노출하기

**위 로드맵 표의 3장 칸이 여기서 펼쳐진다.** 3장은 이 체계에 사례 연구를 둘 건다 — 노출을
결정하는 자리와 게이트웨이를 실제로 얹는 자리다.

- **새 요구가 하나 온다** — **회의 체계가 출시 이후 상당한 호응을 얻어서 소유자들이 참석자가
  새 모바일 애플리케이션으로 자기 상세 정보를 볼 수 있게 하고 싶어 한다.** 그러려면 **모바일
  앱이 이 데이터를 질의할 수 있도록 참석자 서비스 API가 바깥으로 노출되어야 한다** (3장
  §"Case Study: Exposing the Attendee Service to Consumers", p.57).[^gough2022]
  - 위 [바꾸라는 요구 셋](#바꾸라는-요구-셋)의 첫째가 모바일이었다. **3장이 그 요구를 집어
    든다.**
- **그 노출에 따라오는 제약** — **참석자 서비스가 개인 식별 정보(PII)를 담으므로 API가
  신뢰할 수 있고 관측 가능해야 할 뿐 아니라 안전해야 한다** (3장, p.57).[^gough2022]
  - PII를 URL에 두지 말라는 조문은 같은 책 1장에서 왔고 그 자리는
    [API 설계 모범 사례](../concepts/api-design-best-practices.md)다.
- **저자들이 가장 단순한 길을 먼저 세우고 그것을 물음으로 되돌린다** — **프록시나 로드
  밸런서로 API를 그냥 노출하고 추가 요구는 언어나 프레임워크 고유 기능으로 구현할 수도
  있다.** 그러나 스스로에게 물어야 한다 — **이 해법이 확장되는가, 재사용 가능한가**(잠재적으로
  다른 언어와 프레임워크를 쓰는 추가 API를 떠받치는 것), **이 과제들이 기존 기술이나 제품
  안에서 이미 풀려 있지는 않은가** (3장, p.57).[^gough2022]
- **그 물음에 이 사례의 답이 정해져 있다** — **추가 API가 앞으로 노출될 계획이고 그 구현에
  추가 언어와 프레임워크가 쓰일 수 있다는 것을 안다. 그러므로 API 게이트웨이 기반 해법을
  구현하는 것이 합당하다** (3장, p.57).[^gough2022]
  - **이것이 판정의 근거가 무엇인지 보이는 자리다.** 게이트웨이를 고르게 만든 것은 **지금의
    요구**가 아니라 **알려진 미래의 요구**다. 같은 논리가 이 책의 선택 지침에도 들어 있다 —
    가까운 미래와 이미 아는 요구를 함께 보라는 것이다. 그 지침은
    [API 게이트웨이의 규정과 기능과 배치](../concepts/api-gateway-capabilities-and-deployment.md)에 있다.
- **그림 3-1과 그림 3-9가 같은 도면이다.** 둘 다 이 페이지의 맥락 다이어그램에 **API
  Gateway** 상자를 하나 끼운 것이고, 캡션만 "참석자 서비스"와 "새 참석자 서비스"로 갈린다
  (3장, 그림 3-1 p.57 · 그림 3-9 p.76).[^gough2022] 저자들은 같은 그림을 두 번 싣는 것에
  대해 아무 말도 하지 않는다.
  - **그 상자의 C4 요소 유형이 `[Software Infrastructure]`다.** 이 페이지의 다른 상자들이
    `[Person]`과 `[Software System]`인 것과 갈린다. **본문은 이 유형 이름을 적지 않는다.**
    C4 세 층의 규정은 아래 [맥락 다이어그램](#맥락-다이어그램)에 있다.
  - **화살표가 바뀐다** — 고객의 `UI requests to new gateway`가 게이트웨이로 들어가고,
    게이트웨이에서 레거시 회의 체계로 `Reviews sessions and creates bookings`가, 참석자
    서비스로 `Creates and retrieves attendees`가 나간다. **레거시 회의 체계에서 참석자
    서비스로 가는 `API call to retrieve attendee details` 화살표는 그대로 남는다** (3장,
    그림 3-1, p.57).[^gough2022] 그 남은 화살표가 아래
    [그 배치가 곧바로 낳는 문제 하나](#그-배치가-곧바로-낳는-문제-하나)의 씨앗이다.

## 모놀리스가 라우팅을 맡는 배치를 기각한다

- **저자들이 흔한 출발점을 먼저 적는다** — **많은 조직이 서비스를 뽑아내는 것으로 이런 이주를
  시작하면서도, 바깥에서 도는 서비스를 위한 라우팅과 다른 횡단 관심사를 모놀리식 애플리케이션이
  수행하게 한다.** 이것이 **흔히 쉬운 선택**인 이유는 **모놀리스가 이미 내부 기능을 위해 그
  기능을 제공해야 하기 때문**이다 (3장, p.76).[^gough2022]
- **그런데 그것이 무엇을 낳는가가 넷으로 적힌다** (3장, p.76):[^gough2022]
  - **모놀리스와 서비스 사이의 단단한 결합**이 생기고, **모든 트래픽이 모놀리식 애플리케이션을
    흐르며**, **설정의 주기가 모놀리스의 배포 빈도에 의해 정해진다.**
  - **트래픽 관리 관점에서 모놀리식 애플리케이션의 부하가 늘고**, **그것이 실패할 때의 폭발
    반경이 커져** 운영 비용이 높아질 수 있다.
  - **느린 릴리스 열차나 실패한 배포 때문에 라우팅 정보나 횡단 설정의 갱신이 제한되면 빠르게
    반복하지 못한다.**
  - 그래서 조문이 이렇다 — **이런 식으로 모놀리스가 트래픽을 라우팅하게 하는 것을 일반적으로
    권하지 않으며, 특히 비교적 짧은 기간에 서비스를 여럿 뽑아낼 계획이라면 그렇다.**
- **대신 갈 자리의 조건이 둘 붙는다** — **게이트웨이가 고가용으로 배포되고 개발자가 라우팅과
  설정을 관리할 직접(셀프서비스) 접근을 가지는 한, 애플리케이션 라우팅과 횡단 관심사를 뽑아
  API 게이트웨이로 모으는 일이 안전성과 속도를 둘 다 준다** (3장, p.76).[^gough2022]
  - **셀프서비스라는 조건이 이 KB의 다른 소스와 같은 자리를 짚는다.**
    [API 게이트웨이와 서비스 메시](../concepts/api-gateway-and-service-mesh.md)가 게이트웨이의 중앙 통제가
    **티켓**을 낳는다는 논거로 기능 추가를 기각하는데, **이 책은 같은 위험을 조건으로 바꿔
    단다** — 셀프서비스가 되면 괜찮다는 것이다. 겨루지 않는다.
- **이 배치가 이 책의 역사 절에도 나온다** — 1세대 게이트웨이 시기에 **모놀리스 일부가 API
  게이트웨이로 행동하거나 게이트웨이 같은 기능을 제공했다**는 서술이다. 그 자리는
  [API 게이트웨이의 규정과 기능과 배치](../concepts/api-gateway-capabilities-and-deployment.md)에 있다.
- **저자들이 이 이주를 부르는 이름이 있다** — **"교살자 무화과(strangler fig)" 패턴**이고,
  **기존 체계의 조각을 독립 배포와 실행이 가능한 서비스로 점진적으로 뽑아냄으로써 모놀리스에서
  마이크로서비스 기반 아키텍처로 시간에 걸쳐 진화시키는 것**이다. 저자들은 그 상세를 이 책
  8장으로 미룬다 (3장 §"Case Study: Evolving the Conference System Using an API Gateway",
  p.75).[^gough2022] 그 패턴의 정본은
  [모놀리스 분해 패턴](../concepts/monolith-decomposition-patterns.md)이다.

## 게이트웨이를 얹고 경로를 매핑한다

**저자들이 쿠버네티스 클러스터 위에서 시연한다. 제품 이름과 설정 문법은 2022년 저술 시점의
것이고 이 페이지는 그 설정을 옮기지 않는다.**

- **설치** — 회의 체계를 쿠버네티스 클러스터에 배포하고 있으므로 **YAML 설정 적용이나 Helm
  같은 표준 쿠버네티스 고유 접근과 명령줄 유틸리티로 API 게이트웨이를 쉽게 설치할 수 있다**
  (3장 §"Installing Ambassador Edge Stack in Kubernetes", pp.76–77).[^gough2022]
- **설치가 애플리케이션에서 덜어 내는 것이 셋이다** — 게이트웨이가 HTTPS 연결을 제공하면
  **회의 체계 애플리케이션이 더는 TLS 연결 종단이나 여러 포트 수신을 신경 쓸 필요가 없다.**
  마찬가지로 **인증과 속도 제한도 애플리케이션을 다시 설정하거나 배포하지 않고 쉽게 설정할 수
  있다** (3장, p.77).[^gough2022]
  - **이것이 이 사례에서 게이트웨이가 실제로 사 준 것이다.** 위
    [참석자 서비스를 소비자에게 노출하기](#참석자-서비스를-소비자에게-노출하기)가 요구한
    안전성이 여기서 채워진다.
- **매핑 둘을 건다** (3장 §"Configuring Mappings from URL Paths to Backend Services",
  pp.77–78):[^gough2022]
  - **첫째 매핑은 도메인의 루트(`/`)를 레거시 네임스페이스에서 도는 기존 회의 체계 서비스로
    보낸다.** 저자들은 이 매핑이 **웹 애플리케이션이나 리버스 프록시를 설정해 본 사람에게는
    익숙할 것**이라고 적는다. 설정이 담는 것은 **이름과, 대상 서비스로 매핑되는 경로**다.
  - **둘째 매핑은 `/attendees` 경로로 보내진 트래픽을 모놀리스에서 뽑아낸 새 참석자
    마이크로서비스로 보낸다.** 여기에는 **재작성(rewrite)이 지정되어 대상 서비스를 부르기 전에
    URL의 맞는 접두 경로를 다시 쓴다.** 그러면 **참석자 서비스에게는 요청이 `/` 경로에서 온
    것처럼 보이고, 사실상 `/attendees` 부분이 벗겨진다.**
  - **이 패턴이 이주의 엔진이다** — **레거시 애플리케이션에서 마이크로서비스를 뽑아낼 때마다
    매핑을 하나씩 더하는 이 패턴을 계속할 수 있다.** 맞는 접두는 **중첩될 수도 있고 정규
    표현식을 쓸 수도 있다.** 그래서 **결국 레거시 애플리케이션은 기능 몇 개만 남은 작은 껍데기가
    되고 나머지 기능은 저마다 매핑을 가진 마이크로서비스들이 처리한다** (3장,
    p.78).[^gough2022]
- **호스트 기반 라우팅이라는 다른 길** — **대부분의 API 게이트웨이가 호스트 기반 라우팅도
  수행하게 해 준다**(예컨대 참석자용 하위 도메인 하나). 이것은 **새 서비스를 담을 새 도메인이나
  하위 도메인을 만들어야 할 때 쓸모 있을 수 있다** (3장 §"Configuring Mappings Using
  Host-based Routing", p.78).[^gough2022]
  - **무엇으로 라우팅하지 말아야 하는가**(요청 적재물)는
    [API 게이트웨이의 함정과 선택](../concepts/api-gateway-pitfalls-and-selection.md)에 있다.

## 그 배치가 곧바로 낳는 문제 하나

- **저자들이 자기 시연의 결과를 함정의 실물로 되쓴다** — **매핑 둘을 설정한 지금의 회의 체계를
  보면 이 문제가 고개를 드는 것이 보인다.** 사용자 요청 같은 **외부 트래픽은 게이트웨이가 대상
  서비스로 올바르게 라우팅하고 있다. 그런데 레거시 애플리케이션은 참석자 서비스의 위치를 어떻게
  발견하는가** (3장, p.82).[^gough2022]
  - 위 [참석자 서비스를 소비자에게 노출하기](#참석자-서비스를-소비자에게-노출하기)가 적어 둔
    **남은 화살표**가 이것이다. 도면에서 레거시 체계가 참석자 서비스를 직접 부른다.
- **흔한 첫 접근이 틀린 답이다** — **모든 요청을 공개적으로 주소 지정 가능한 게이트웨이로
  되돌려 보내는 것**(레거시 애플리케이션이 공개 도메인의 `/attendees` 경로를 부르는 것)이다.
  **대신 레거시 애플리케이션은 어떤 형태의 내부 서비스 디스커버리 기제를 써서 모든 내부 요청을
  내부 네트워크 안에 두어야 한다** (3장, p.82).[^gough2022]
  - **이것이 게이트웨이 루프백 함정이고** 그 전문은
    [API 게이트웨이의 함정과 선택](../concepts/api-gateway-pitfalls-and-selection.md)에 있다. 이 책은
    그것을 **서비스 메시로 어떻게 구현하는지는 다음 장에서 배운다**고 미룬다.
  - 위 로드맵 표의 4장 칸이 그 자리다.

## 세션 기능을 떼어내라는 요구와 ADR501

- **다음 진화를 부르는 요구 한 줄** — **회의 소유자들이 핵심 신기능 하나를 지원해 달라고
  요청한다. 모바일 애플리케이션으로 참석자의 회의 세션을 보고 관리하는 것**이다 (4장 §"Case
  Study: Extracting Sessions Functionality to a Service", p.88).[^gough2022]
- **저자들이 이것을 ADR을 낳을 만한 큰 변경으로 판정하고 예시 ADR을 싣는다** (4장, 표 4-2,
  p.89).[^gough2022] 표제가 **ADR501 세션을 레거시 회의 체계에서 분리하기**이고 상태 칸이
  **제안됨**이다.
  - **맥락** — 마케팅 팀은 **참석자가 모바일 애플리케이션으로 세션의 상세를 보고 관심을 표시할
    수 있으면 참여가 늘 것**이라 믿고, 또한 **세션마다 몇 명이 관심을 갖는지 보고 싶어 한다.**
  - **결정** — **세션 컴포넌트를 독립 서비스로 갈라내는 진화적 한 걸음을 밟는다.** 그러면
    **세션 서비스를 상대로 API 우선 개발을 할 수 있고 레거시 회의 서비스에서 그 API를 부를 수
    있다.** 또한 **참석자 서비스가 세션 서비스의 API를 직접 불러 모바일 애플리케이션에 세션
    정보를 줄 수 있다.**
  - **결과 다섯** — 레거시 애플리케이션이 **세션 관련 질의 전부를 새 세션 서비스에
    넘긴다.** 사용자가 관심 있는 세션을 보고 더하고 빼려 할 때 **참석자 서비스가 세션 서비스를
    불러야 한다.** 관리자가 세션마다 누가 참석하는지 보려 할 때 **세션 서비스가 참석자 서비스를
    불러야 한다.** **세션 서비스가 아키텍처의 단일 장애점이 될 수 있어 그 영향을 완화할 조치가
    필요할 수 있다.** 그리고 **회의가 열리는 동안 세션 조회와 관리가 극적으로 늘므로 큰 트래픽
    급증과 세션 서비스가 과부하되거나 성능이 깎인 채 도는 경우를 셈에 넣어야 한다.**
  - **호출 방향이 양쪽으로 생긴다는 것이 이 단계의 새로운 점이다.** 위
    [진화적 한 걸음](#진화적-한-걸음)에서 참석자 서비스가 떨어져 나왔을 때는 호출이 한
    방향이었는데, 여기서는 **참석자 서비스와 세션 서비스가 서로를 부른다.**
- 도판에만 있고 본문에 없는 것 하나 — **그림 4-1이 이 변경의 C4 도면인데, 세션 서비스로 가는
  화살표가 전부 점선(프로세스 밖 API 호출)이고 게이트웨이를 거치지 않는다.** 참석자가
  게이트웨이로 들어와 레거시 체계에 닿는 흐름만 바깥에서 오고, **세션 서비스는 레거시 체계와
  참석자 서비스에서만 닿는다.** 본문은 도면을 가리키기만 한다 (4장, 그림 4-1,
  p.89).[^gough2022]

## 게이트웨이로 노출하는 길을 기각한다

- **저자들이 쉬운 길을 먼저 적고 곧바로 기각한다** — **새 세션 서비스가 바깥으로 노출될 필요가
  없는데도, 이 서비스를 API 게이트웨이로 노출하고 레거시 체계와 참석자 서비스가 게이트웨이의
  외부 주소로 이 서비스를 부르게 설정하면 앞의 ADR이 말한 라우팅과 신뢰성 요구를 쉽게 맞출 수
  있다** (4장, p.90).[^gough2022]
- **그런데 그것이 3장에서 배운 게이트웨이 루프백 안티패턴의 예가 된다** — **이 안티패턴은
  내부로 향하는 트래픽이 네트워크를 떠날 수 있게 만들고, 거기에 성능과 보안과 (클라우드 벤더)
  비용의 함의가 딸린다** (4장, p.90).[^gough2022]
  - **이것이 위 [그 배치가 곧바로 낳는 문제 하나](#그-배치가-곧바로-낳는-문제-하나)가 미뤄
    둔 답이다.** 3장은 이 체계에서 루프백이 고개를 드는 장면까지만 보이고 **어떻게 푸는지는
    4장으로 미뤘다.** 함정의 전문은
    [API 게이트웨이의 함정과 선택](../concepts/api-gateway-pitfalls-and-selection.md)에 있다.
- **그래서 저자들이 넘어가는 자리가 서비스 메시다** — **이 안티패턴을 피하면서 새 요구를 맞추는
  데 메시가 어떻게 도울 수 있는지 살펴보자**는 것이다 (4장, p.90).[^gough2022]

## 메시로 라우팅과 관측과 구획을 건다

- **저자들이 시연의 전제를 먼저 적는다** — 예시가 **전부 쿠버네티스를 쓰는데 그것이 메시가
  배치되는 가장 흔한 플랫폼**이기 때문이고, 시연되는 개념은 **각 메시가 떠받치는 모든 플랫폼과
  인프라에 적용된다.** 그리고 **애플리케이션 기술 스택 안에서는 메시 구현 하나만 고르고
  채택하기를 권하면서도, 순전히 교육 목적으로 서로 다른 메시 셋으로 회의 체계의 설정을
  시연한다**고 밝힌다 (4장 §"Case Study: Using a Service Mesh for Routing, Observability, and
  Security", p.111).[^gough2022]
- **라우팅** — Istio를 클러스터에 설치할 때 **주된 전제 조건이 클러스터에서 도는 모든 서비스에
  프록시 사이드카를 자동 주입하도록 켜는 것**이고, 그 뒤 다루게 되는 **주요 커스텀 자원이
  둘**이다 (4장 §"Routing with Istio", p.112):[^gough2022]
  - **VirtualService는 어떤 호스트가 주소로 지정될 때 적용할 트래픽 라우팅 규칙 묶음을
    정의한다.**
  - **DestinationRule은 라우팅이 일어난 뒤 그 서비스로 향하는 트래픽에 적용할 정책을
    정의한다.** 그 규칙이 지정하는 것이 **로드 밸런싱과 사이드카에서 나가는 연결 풀 크기, 그리고
    건강하지 않은 호스트를 로드 밸런싱 풀에서 탐지해 쫓아내는 이상치 탐지 설정**이다.
  - **참석자 서비스 쪽 DestinationRule이 서비스의 판 둘을 지정하고, 그것이 새 v2 판의 카나리
    라우팅을 가능하게 하는 바탕**이라고 저자들이 적는다 (4장, p.113).[^gough2022]
  - **저자들이 자기 시연에 단서를 단다** — **시작하기가 정말 이렇게 쉽지만 프로덕션 환경에서
    Istio를 설정하고 유지하는 일은 더 복잡할 수 있다** (4장, p.113).[^gough2022]
- **관측** — Linkerd는 **원격 측정과 모니터링 기능이 기본 설치에서 설정 변경 없이 자동으로
  켜진다.** 그 기능에 드는 것이 **HTTP와 HTTP/2와 gRPC 트래픽의 최상위("황금") 메트릭(요청량과
  성공률과 지연 분포) 기록**, **그 밖의 TCP 트래픽에 대한 TCP 수준 메트릭 기록**, **서비스별·
  호출자와 피호출자 쌍별·경로별 메트릭 보고**, **서비스 사이 런타임 관계를 보이는 토폴로지 그래프
  생성**, **요청의 실시간 온디맨드 표집**이다 (4장 §"Observing Traffic with Linkerd",
  pp.113–114).[^gough2022]
  - **그 데이터를 소비하는 길이 셋**이다 — **Linkerd CLI**, **Linkerd 대시보드와 미리 만들어진
    Grafana 대시보드**, 그리고 **Linkerd에 내장된 Prometheus 인스턴스에서 직접** 가져오는
    것이다 (4장, p.114).[^gough2022]
  - **쓰임이 개발과 프로덕션 양쪽에 걸린다** — **프로덕션에서 유효하지 않은 서비스 사이 트래픽의
    탐지는 늘 자동화해야 하지만**, 이 관측 도구를 **내부 API나 서비스가 잘못 호출되고 있을 때를
    식별하는 데도 쓸 수 있다** (4장, p.115).[^gough2022]
- **구획** — **마이크로서비스 이전에는 서비스 사이 통신의 인가가 주로 방화벽 규칙과 라우팅
  테이블로 집행됐다.** Consul은 **의도(intentions)로 서비스 이름에 따라 서비스 사이 통신 권한을
  정의하게 해 그 관리를 단순하게 한다** (4장 §"Network Segmentation with Consul",
  p.115).[^gough2022]
  - **집행의 경로** — **의도는 어느 서비스가 서로 통신할 수 있는지를 통제하고 인바운드 연결에서
    사이드카 프록시가 집행한다.** **인바운드 서비스의 신원은 그 TLS 클라이언트 인증서로
    검증**되고, **Consul이 각 서비스에 TLS 인증서로 인코딩된 신원을 준다.** 사이드카 프록시가
    **인바운드 서비스가 목적지 서비스와 통신하도록 인가하는 의도가 있는지 확인**하고, **인가되지
    않았으면 연결을 끊는다** (4장, pp.115–116).[^gough2022] 각주로 **그 신원이 SPIFFE X.509
    신원 문서를 따라 인코딩된다**고 적는다 (4장, p.116 각주 9).[^gough2022]
  - **의도의 네 부분** (4장, p.116):[^gough2022] **출발지 서비스**(통신을 개시하는 쪽. 서비스의
    전체 이름이거나 모든 서비스를 뜻하는 와일드카드) · **목적지 서비스**(통신을 받는 쪽) ·
    **권한**(허용인가 거부인가) · **설명**(의도에 설명을 붙이는 선택적 메타데이터 필드).
  - **첫 의도가 기본 정책을 뒤집는다** — **모든 트래픽이 특정 규칙으로 거부되지 않는 한
    허용되는 "전부 허용" 정책을, 모든 트래픽이 거부되고 특정 연결만 켜지는 "전부 거부" 정책으로
    바꾸는 것**이다. 목적지 필드에 와일드카드를 지정해 **모든 서비스 사이 통신을 막은 뒤**,
    레거시 서비스와 참석자 서비스와 세션 서비스 사이에 **필요한 상호작용마다 의도를 하나씩
    정의해 인가**한다. **그 설정을 적용하면 이 상호작용들만, 오직 이것들만 처리되고 다른
    상호작용은 막혀 API 호출이나 요청이 떨어진다** (4장, pp.116–117).[^gough2022]
  - **대안 하나를 덧붙인다** — **Consul의 의도 말고도 Open Policy Agent(OPA) 프로젝트가 메시
    안에서 비슷한 기능을 구현하는 인기 있는 선택**이다 (4장, p.117).[^gough2022]
  - 그 인가의 소재지 물음은
    [서비스 사이 인증과 인가](../concepts/service-to-service-authentication-and-authorization.md)에
    있다.

## 이 체계가 고르는 메시 구현 양식

- **사이드카를 고른다** — **사이드카 기반 접근이 2022년 저술 시점에 가장 흔한 패턴이고 이 회의 체계에도
  좋은 선택일 법하다.** 그 비용이 **최초 설치와 이어지는 운영 유지, 그리고 모든 사이드카를
  돌리는 데 드는 자원**인데, **확장 요구가 2022년 저술 시점에는 수수하므로 사이드카 프록시를 돌리는 데 큰
  컴퓨팅 파워가 필요하지 않을 것**이라고 적는다 (4장, p.107).[^gough2022]
- **프록시 없는 gRPC는 기각된다** — **회의 체계가 gRPC API에 더해 REST API를 쓰므로 지금으로서는
  이 선택지가 배제된다.** 다만 **내부의 REST API 사용이 폐기되거나 gRPC 라이브러리가 gRPC
  기반이 아닌 통신도 떠받치게 되면 다시 평가할 수 있다** (4장, p.109).[^gough2022]
  - **이 체계가 두 스타일을 함께 쓴다는 것이 여기서 설계 선택의 제약으로 되돌아온다.** 그
    선택의 자리는 [gRPC와 RPC 스타일](../concepts/grpc-and-rpc-style.md)이고, 구현 양식 넷의
    전문은 [서비스 메시의 진화와 선택](service-mesh-evolution-and-selection.md)에 있다.
- **다국어 이득이 이 체계에 걸리는 자리도 적힌다** — 메시가 사이드카로 구현되므로 **참석자
  서비스를 다른 언어로 다시 쓰면서도(예컨대 새 성능 요구를 맞추려고) 서비스 사이 통신의 횡단
  측면이 일관되게 다뤄지는 데 계속 기댈 수 있다** (4장, p.101).[^gough2022]

## 키노트 뒤의 트래픽 급증

- **저자들이 ADR501의 마지막 결과를 장면으로 푼다** — **행사에서 수천 명의 참석자가 아침
  키노트를 막 보고 나서 그날의 일정을 보려 하는 장면**을 상상하라는 것이다. **이 갑작스러운
  트래픽 급증이 세션 서비스의 성능을 깎을 수 있다** (4장, p.98).[^gough2022]
- **대부분의 경우에는 적절한 시간 초과와 재시도를 정의**하겠지만, **애플리케이션 동작을 발동하는
  회로 차단 조치도 정의할 수 있다** (4장, p.98).[^gough2022]
- **구체적인 경로** — **참석자 서비스가 세션 서비스에 거는 API 호출(참석자의 하루 세션 일정을
  가져오는 것)이 되풀이해 실패하면, 메시 안에서 회로 차단기를 발동해 이 서비스로 가는 모든
  호출을 빠르게 실패시킬 수 있다**(서비스가 회복하도록). 그리고 **모바일 애플리케이션에서는 그
  실패를 개인 일정 대신 회의 세션 일정 전체를 그려 주는 것으로 "폴백"해 다루는 것이 가장
  그럴듯하다** (4장, p.98).[^gough2022]
  - **이것이 이 KB의 폴백 서술에 드문 실물 하나를 준다** — **깎인 응답이 무엇인지가 구체적**이다.
    개인화된 것에서 개인화되지 않은 것으로 내려간다. 기제들의 전문은
    [안정성 패턴](stability-patterns.md)에 있다.

- **책이 진행되는 동안 이 체계에 일어나는 변경 또는 기술 적용을 저자들이 미리 늘어놓는다**
  (서론, pp.xxx–xxxi).[^gough2022]

  | 장 | 이 체계에 하는 일 |
  |---|---|
  | 1장 | 참석자 API의 설계와 명세. 버저닝과 성능을 위한 교환 모델링의 중요성 |
  | 2장 | 참석자 서비스의 동작을 검증하는 계약 테스트와 컴포넌트 테스트. Testcontainers가 통합 테스트를 돕는 방식 |
  | 3장 | API 게이트웨이로 참석자 서비스를 소비자에게 노출. 쿠버네티스 위 게이트웨이로 체계를 진화시키는 시연 |
  | 4장 | 서비스 메시로 세션 기능을 레거시 회의 체계에서 떼어내기. 메시가 라우팅과 관측 가능성과 보안을 돕는 방식 |

  | 8장 | 참석자 서비스의 도메인 경계 확립과 서비스 패턴들 |
  | 9장 | 클라우드 채택. 참석자 서비스를 클라우드로 옮기고 리플랫포밍을 고려하기 |

- **사례 연구의 진화를 높은 수준에서 한눈에 보려면 10장을 보라고 저자들이 가리킨다** (서문,
  p.xv).[^gough2022]
- **이 로드맵과 사례 연구가 함께 요구하는 것이 둘**이라고 저자들이 적는다 — **아키텍처의 변경을
  시각화하는 일**과 **결정을 기록하는 일**이다. 그 둘을 각각 **C4 다이어그램**과 **아키텍처 결정
  기록(ADR)**이 맡는다 (서론, p.xxxi).[^gough2022]

## 이 체계를 무엇으로 그리는가

- **저자들의 선택과 그 근거** — **C4가 아키텍처와 맥락과 상호작용을 다양한 이해관계자에게
  전달하는 최고의 문서화 표준이라고 믿는다** (서론, p.xxxi).[^gough2022]
- **UML을 쓰지 않는 이유를 저자들이 직접 답한다** (서론, p.xxxi):[^gough2022]
  - **UML(Unified Modeling Language)은 소프트웨어 아키텍처를 전달하는 방대한 방언을 준다.**
  - **주된 도전은 UML이 주는 것의 대부분을 아키텍트와 개발자가 외우고 있지 않다는 것이고, 그래서
    사람들이 금방 상자와 원과 마름모로 되돌아간다.**
  - **그 결과 논의의 기술적 내용에 들어가기 전에 다이어그램의 구조를 이해하는 일 자체가 진짜
    도전이 된다.**
  - 저자들이 농담 하나를 붙인다 — **많은 다이어그램은 누군가 화이트보드용 마커 대신 유성 마커를
    실수로 집었을 때에만 프로젝트의 이력에 남는다.**
- **C4 모형은 여러 수준의 상세로 프로젝트 아키텍처의 안내가 되는 단순화된 다이어그램 집합을
  준다** (서론, p.xxxi).[^gough2022]
- **이 책이 쓰는 것은 그 가운데 앞의 세 수준**이고, 사례 연구를 소개하며 그 셋을 모두 드러냈다
  (서론, pp.xxxi·xxxv).[^gough2022]

## 맥락 다이어그램

- **의도는 기술 청중과 비기술 청중 모두에게 맥락을 세우는 것**이다 (서론,
  p.xxxi).[^gough2022]
- **이 도면이 막는 실패가 있다** — **많은 아키텍처 대화가 저수준 상세로 곧장 뛰어들어 고수준
  상호작용의 맥락을 세우는 일을 놓친다** (서론, p.xxxi).[^gough2022]
- **저자들이 그 값을 시간으로 센다** — **체계 맥락 다이어그램을 잘못 그렸을 때의 함의를
  생각하라. 접근을 요약해 두는 이점이 오해를 바로잡는 데 드는 몇 달의 작업을 아낄 수 있다**
  (서론, p.xxxi).[^gough2022]

## 컨테이너 다이어그램

- **하는 일은 아키텍처의 주요 참여자들을 기술적으로 갈라 보이는 것**이다 (서론,
  p.xxxii).[^gough2022]
- **컨테이너의 규정은 직인용으로 둔다** (서론, p.xxxii):[^gough2022]

  > A container in C4 is defined as "something that needs to be running in order for the
  > overall system to work"

  저자들이 드는 예가 **회의 데이터베이스**다.
- **성격과 자리** — **컨테이너 다이어그램은 본성상 기술적이고 더 높은 수준의 체계 맥락 다이어그램
  위에 쌓인다** (서론, p.xxxii).[^gough2022]
- **이 책은 일부러 기술 이름을 비웠다** — 회의 애플리케이션 컨테이너를 그냥 **소프트웨어**로
  적어 두었는데, **보통의 C4 컨테이너라면 컨테이너의 종류를 더 상세히 적는다**(저자들이 드는 예가
  **자바 스프링 애플리케이션**이다). 그렇게 하지 않은 이유는 **특정 해법을 보이는 데 도움이 되지
  않는 한 이 책이 기술 특정성을 피하기 때문**이고, 그 근거로 **API와 2022년 저술 시점 애플리케이션의 이점이
  해법 공간에 상당한 유연성이 있다는 것**을 든다 (서론, p.xxxii).[^gough2022]

## 컴포넌트 다이어그램

- **하는 일은 각 컨테이너 안의 역할과 책임, 그리고 내부의 상호작용을 정의하는 것**이다 (서론,
  p.xxxii).[^gough2022]
- **두 자리에서 쓸모가 있다** — **컨테이너의 상세를 누가 물어 왔을 때**, 그리고 **코드베이스로
  가는 아주 유용한 지도로서**다 (서론, p.xxxii).[^gough2022]
- **저자들이 그 지도의 값을 대는 방식** — **새 프로젝트에서 처음 일하기 시작할 때를 생각하라.
  스스로를 문서화하는(self-documenting) 코드베이스를 훑어보는 것도 한 접근이지만, 전부를
  짜맞추기는 어려울 수 있다** (서론, p.xxxii).[^gough2022]
- **이 층에서 기술이 드러난다** — **컴포넌트 다이어그램은 소프트웨어를 짓는 데 쓰는 언어와
  스택의 상세를 드러낸다.** 그래서 이 책은 기술 중립을 지키려고 **패키지/모듈**이라는 용어를
  썼다 (서론, p.xxxii).[^gough2022]
- **저자들이 인정하는 성질 하나** — 프런트 컨트롤러라는 이름이 붙은 API 컨트롤러가 **프로세스 안
  라우팅의 관점에서 흥미롭다**는 관찰은 이 층의 도면이 있어야 나온다 (서론,
  p.xxvi).[^gough2022]

## 기능 플래그로 참석자를 옮긴다

- **5장이 이 체계로 배포와 릴리스의 분리를 시연한다.** 저자들이 여기서 시작하는 까닭은 **진화적
  아키텍처를 곱게 모형화할 수 있어서, 앞서 제시한 새 인프라로의 변경 속도를 통제할 수 있기
  때문**이다 (5장 §"Case Study: Feature Flagging", p.126).[^gough2022]
- **배치가 나란히 놓기다** — **참석자를 다루는 레거시 체계와 그 데이터베이스가 현대화된 API 기반
  서비스와 나란히 산다** (5장, p.126).[^gough2022]
- **결정이 일어나는 자리가 컨트롤러다** — **기능 플래그를 쓰면 컨트롤러가 질의를 내부 API
  서비스에 대고 실행할지 외부 API 서비스에 대고 실행할지를 코드 수준에서 결정할 수 있게 된다**
  (5장, pp.126–127).[^gough2022]
- **이 배치가 사 오는 것** — **사용자 작은 묶음을 새 체계로 옮겨 기능이 그들에게 계속 도는지
  시험할 수 있고, 잘못되면 스위치를 되돌리며, 아니면 100퍼센트 이행에 닿을 때까지 롤아웃을 이어
  간다** (5장, p.128).[^gough2022] 이 장치의 규정과 그것이 지우는 의무 둘은
  [배포와 릴리스의 분리와 릴리스 전략](deployment-and-release-separation.md)에 있다.
- **그림에만 있고 본문에 없는 것 넷** (5장, 그림 5-1, p.127):[^gough2022]
  - **기능 플래그가 이 그림에서 독립된 소프트웨어 구성 요소로 그려진다.** 설명이 **배포와
    릴리스의 분리를 돕도록 기능 플래그를 설정한다**이다.
  - **데이터스토어가 둘이다** — 레거시 참석자 쪽과 리팩터링된 참석자 서비스 쪽이 각각 자기
    데이터스토어를 갖는다. 본문은 데이터베이스가 나란히 산다고만 적는다.
  - **외부로 라우팅되는 API 요청은 프로세스 밖이고 내부로 라우팅되는 것은 프로세스 안이라고
    라벨이 붙는다.** 이 구별은 위
    [같은 그림에서 프로세스 안과 밖이 갈린다](#같은-그림에서-프로세스-안과-밖이-갈린다)가 서론
    그림에서 세운 것과 같은 축이다.
  - **API 컨트롤러에서 기능 플래그로 가는 화살표에 플래그에 기반해 실행 논리를 정한다는 라벨이
    붙고 그것도 프로세스 안**이다.

## 이 체계의 릴리스를 어떻게 모형화하는가

- **5장이 이 체계를 예로 판의 종류와 릴리스 전략을 맞춘다** (5장 §"Case Study: Modeling
  Releases in the Conference System", p.129).[^gough2022] 그 대응의 전문은
  [배포와 릴리스의 분리와 릴리스 전략](deployment-and-release-separation.md)에 있다.
- **이 체계에 특히 걸리는 조항 하나** — **소비자와 생산자가 강하게 결합되어 있고 같은 팀이
  소유하며 언제나 함께 움직인다면 API 판 가르기와 수명 주기는 결정적이지 않고**, 그 상황에서는
  **두 구성 요소를 함께 릴리스하고 트래픽을 인그레스에서 통제하는 전략**이 맞으며 **대체로
  블루그린 모형이 잘 듣는다** (5장, p.130).[^gough2022]
- **그래서 이 체계의 그림 셋이 서로 다른 짝을 보인다** (5장, 그림 5-2·5-3·5-4,
  pp.132–135):[^gough2022]
  - **카나리와 트래픽 미러링의 그림에서는 참석자 서비스만 새 판이 되고 레거시 회의 서비스는 v1.0
    그대로다.**
  - **블루그린의 그림에서는 레거시 회의 서비스와 참석자 서비스가 함께 v1.1이 되어 그린 환경을
    이룬다.** 곧 **강하게 결합된 짝을 함께 내보내는 전략이라는 본문의 조항이 그림에서 두 상자가
    함께 초록이 되는 것으로 표현된다.**

## 롤아웃 도구로 참석자 API를 굴린다

- **5장이 이 체계에 롤아웃 도구를 적용해 보인다** (5장 §"Case Study: Performing Rollouts with
  Argo Rollouts", pp.135–138).[^gough2022]
- **선언의 내용** — **참석자 API의 파드 다섯을 돌리면서 카나리 방식을 지정하고, 롤아웃을
  촉발하면 파드의 20퍼센트가 새 판으로 교체된다** (5장, p.136).[^gough2022]
- **진행의 순서** — **가중치 20퍼센트 뒤에 무기한 정지를 두고 40·60·80퍼센트마다 10초 정지를
  둔다.** 정지 단계에서 **UI나 명령줄에서 수동 승격이 촉발되기를 기다리고**, **문제가 생기면
  카나리 릴리스를 빠르게 되돌릴 수 있다** (5장, pp.136–137).[^gough2022]
- **지표로 승격을 모는 변형** — **지표 수집기의 값으로 카나리 배포의 성공률을 관찰하는 분석
  단계를 롤아웃 정의에 나타내면 성공 기준이 충족될 때 롤아웃이 진행되게 할 수 있다** (5장,
  p.138).[^gough2022]
- **그림에만 있고 본문에 없는 것** — 대시보드 그림 둘에서 **파드가 체크 표시 다섯 개로 그려지고
  카나리 개정에는 체크가 하나**다. 곧 **다섯의 20퍼센트가 하나**라는 산수가 그림에만 있다. 또
  **옛 판만 안정으로 표시되고 그쪽에만 롤백 단추가 붙으며**, 요약 칸에 **설정 가중치와 실제
  가중치가 따로** 있다 (5장, 그림 5-5·5-6, pp.137–138).[^gough2022]

## 이 체계에서 잡을 지표 여섯

- **5장이 이 체계를 예로 중요한 지표의 목록을 든다** (5장, p.141).[^gough2022]
  - **참석자에 대한 분당 요청 수.**
  - **참석자에 대한 서비스 수준 목표(SLO)로서의 응답 평균 지연.** **지연이 크게 벗어나기
    시작하면 문제의 이른 징후일 수 있다.**
  - **CFP 체계에서 오는 401의 수.** **벤더 침해나 도난당한 토큰을 가리킬 수 있다.**
  - **참석자 서비스의 가용성과 가동 시간의 측정.**
  - **애플리케이션의 메모리와 CPU 사용량.**
  - **체계 안의 참석자 총수.**
- **목록의 성격이 갈린다** — **앞의 넷은 운영 지표이고 마지막 하나는 업무 지표**다. 이 구별과
  지표 일반의 규정은 [관측 가능성과 모니터링](observability-versus-monitoring.md)이 갖는다.

## 참석자 API에 OWASP를 적용한다

- **6장이 이 체계를 위협 모델링 연습의 대상으로 삼는다** (6장 §"Case Study: Applying OWASP to
  the Attendee API", p.146).[^gough2022] 연습의 절차 전체는
  [API 위협 모델링](../concepts/api-threat-modeling.md)이 갖는다.
- **이 연습의 목표가 명시된다** — **참석자 서비스에 대한 목표는 API 보안 위험 목록의 항목들이
  완화되도록 함으로써 제삼자의 외부 소비에 대비시키는 것**이다 (6장, p.150).[^gough2022]
- **목표가 직접적이어서 지도가 단순해진다** — **이것이 직접적 목표이므로 데이터 흐름
  다이어그램을 써서 데이터 흐름을 그 목록의 문제와 취약점에 대응시킬 수 있다** (6장,
  p.154).[^gough2022] 저자들은 **전형적인 위협 모델링 목표는 오히려 "개인 식별 정보의 유출을
  막아 규정을 준수한다"거나 "계약 의무를 채우기 위해 99.9퍼센트 가용성을 제공한다" 같은 것**
  이라고 덧붙인다.
- **정보를 모으는 단계에서 이 체계가 요구하는 것** — **모바일, 게이트웨이, 데이터베이스, 참석자
  서비스 등 모든 구성 요소에 걸쳐 일하는 팀원들을 불러들여야** 한다 (6장, p.150).[^gough2022]
- **그림에만 있고 본문에 없는 것** — 그림 6-1은 이 연습에 쓰이는 참석자 API를 **참석자라는
  사람에서 시작해 모바일 앱과 API 게이트웨이와 참석자 서비스와 데이터스토어로 잇는 C4 컨테이너
  그림**으로 그리고, **게이트웨이에 소프트웨어 인프라라는 꼬리표**를 붙인다. **모바일 앱에서
  게이트웨이로 가는 호출에는 HTTP라는 라벨**이 붙고 **참석자 서비스에서 데이터스토어로 가는
  것에는 프로세스 밖의 SQL이라는 라벨**이 붙는다 (6장, 그림 6-1, p.146).[^gough2022]

## 이 체계의 데이터 흐름 다이어그램

- **분해 단계에서 이 체계의 DFD를 만든다** (6장 §"Step 3: Decompose the System",
  p.151).[^gough2022] 저자들은 **그것을 어느 위협 모델링 도구로 만들었고 다른 도구도 있다**고
  적는다.
- **그림에만 있고 본문에 없는 것 넷** (6장, 그림 6-2, p.151):[^gough2022]
  - **흐름마다 프로토콜이 붙는다** — 모바일 애플리케이션과 게이트웨이 사이는 **HTTPS**,
    게이트웨이와 참석자 API 사이는 **상호 TLS**, 참석자 API와 데이터베이스 사이는 **TCP**다.
    각 프로토콜이 양방향으로 한 쌍씩 그려진다.
  - **경계가 둘이다** — 모바일 애플리케이션과 게이트웨이 사이를 가르는 **인터넷 경계**와,
    게이트웨이·참석자 API·데이터베이스를 함께 감싸는 **서비스 메시** 경계다. 본문은 인터넷 경계만
    이름으로 든다.
  - **API 게이트웨이에 자원 서버(Resource Server)라는 꼬리표**가 붙는다. 그 낱말의 규정은 이
    장에 없고 7장 몫이다.
  - **모바일 애플리케이션에 클라이언트 애플리케이션이라는 꼬리표**가 붙는다. 이는 DFD의
    **외부 개체** 구성 요소에 해당한다.
- **C4 그림과 DFD가 이 체계에 대해 서로 다른 것을 보인다.** 위
  [이 체계를 무엇으로 그리는가](#이-체계를-무엇으로-그리는가)의 세 층은 **구조**를 그리고, 이
  DFD는 **데이터의 흐름과 신뢰 수준이 바뀌는 자리**를 그린다. 그 구별을 저자들이 직접 적는다
  (6장, p.148).[^gough2022]

## 도구가 이 체계에서 찾은 위협

- **위협 식별 단계에서 도구가 자동 분석을 돌린다** — **참석자 API 체계에 대해 도구가 잠재적 위협
  27개를 찾았다** (6장, p.151).[^gough2022]
- **그림에만 있고 본문에 없는 것** — 그림 6-3은 그 도구의 위협 목록 화면을 보이고, **제목과
  범주와 상호작용이라는 세 칸**으로 이뤄진다. **범주 칸의 값이 STRIDE의 낱말들**이고 **상호작용
  칸의 값이 그 위협이 걸리는 흐름의 프로토콜**이다. 곧 **요소별 STRIDE라는 적용 단위가 화면에서는
  흐름마다 한 줄씩으로 나타난다** (6장, 그림 6-3, p.152).[^gough2022]

## 이 체계의 위협 하나에 DREAD를 매긴다

- **위험 평가 단계에서 저자들이 이 체계의 위협 하나를 골라 점수를 매긴다** — **속도 제한이 없는
  상태에서 API 게이트웨이에 대한 분산 서비스 거부 공격**이다 (6장, p.163).[^gough2022] DREAD의
  다섯 축과 산식은 [API 위협 모델링](../concepts/api-threat-modeling.md)이 갖는다.
- **매겨진 점수와 근거** (6장, p.164):[^gough2022]

  | 축 | 점수 | 이 체계에서의 근거 |
  |---|---|---|
  | 피해 | 8 | **속도 제한이 없다.** 누구든 원하는 만큼 게이트웨이에 요청을 보내 과부하시켜 쓸 수 없게 만들 수 있다 |
  | 재현성 | 8 | **초당 많은 요청으로 게이트웨이를 되풀이해 호출하면 성능이 깎이다가 결국 멈춘다** |
  | 악용 가능성 | 5 | **공격자가 네트워크 밖에서 시작할 수 있다.** 다만 게이트웨이가 먼저 인증과 인가를 확인하므로 **요청이 체계와 통합된 정당하고 알려진 클라이언트 애플리케이션에서 와야 한다** |
  | 영향받는 사용자 | 10 | **게이트웨이를 쓸 수 없으면 모든 사용자에게 영향이 간다** |
  | 발견 가능성 | 10 | **악용하려는 누구에게나 알아내기가 쉽다** |

- **총점이 8.2다** — 다섯 점수의 합 41을 5로 나눈 값이다 (6장, p.164).[^gough2022]
- **그 결과가 우선순위를 정한다** — **이 체계에서 식별된 모든 위협을 모아 점수를 매기고 우선순위를
  정했을 때 가장 높은 항목이 API 게이트웨이에 대한 분산 서비스 거부 방어의 부재**이고, **그
  완화는 API 게이트웨이 안에 속도 제한과 부하 덜기를 구현하는 것**이다 (6장,
  p.164).[^gough2022]
- **캡션과 그림이 갈리는 자리가 하나 있다.** 그림 6-6의 캡션은 그 위협을 **TCP 위장 위협**이라
  부르는데, 그림 안의 속성 창에 보이는 위협의 제목은 **API 게이트웨이의 프로세스 충돌 또는
  정지 가능성**이고 범주는 **서비스 거부**이며 본문도 **분산 서비스 거부 공격**이라 적는다 (6장,
  그림 6-6, p.163).[^gough2022] **이 KB는 셋을 그대로 적어 둔다** — 저자들은 이 갈림에 대해
  아무 말도 하지 않는다.
  - 같은 그림에만 있는 것 셋 — **위협에 식별자 88이 붙고**, **상태가 시작되지 않음**이며,
    **우선순위가 높음**으로 매겨져 있다. **상태와 우선순위 칸의 존재는 도구가 위협을 추적 가능한
    항목으로 다룬다는 뜻**이고 본문에는 없다.

## 이 체계에 걸리는 6장의 완화들

- **6장이 이 체계를 예로 드는 완화가 여럿이고 각각의 전문은
  [STRIDE로 API 위협을 식별하기](stride-threats-for-apis.md)에 있다.** 여기서는 이 체계에
  걸리는 자리만 적는다 (6장, pp.154–162).[^gough2022]
  - **주입을 앞에서 막는 자리** — **게이트웨이가 참석자 API의 명세로 요청을 검증하되, 참석자
    API도 여전히 입력을 정제하고 데이터베이스에 준비된 구문을 써야** 한다.
  - **게이트웨이에서 풀리지 않는 자리** — **대량 할당**이다. 참석자를 조회하면 돌아오는
    **읽기 전용이어야 할 목록 속성**을 갱신 요청에 끼워 넣는 공격이고, **API 구현 자체 안에서
    막아야** 한다.
  - **과도한 데이터 노출의 실물** — 참석자 서비스가 **여권 번호 같은 개인 식별 정보를 들고
    있다면** 사용자 정보 요청에 그것이 딸려 나가지 않게 해야 한다.
  - **자산 관리 부실의 실물** — **테스트용으로 노출했다가 잊힌 베타 참석자 엔드포인트**다.
  - **서비스 거부의 완화 자리** — **이 체계에서 속도 제한을 구현할 가장 알맞은 위치는 API
    게이트웨이**다.
  - **헤더 강화의 실물** — 공격자가 **역할을 주장하거나 다른 주체를 사칭하게 하는 꼴의 추가 HTTP
    헤더를 참석자 API로 보내는 것**이고, 완화는 **게이트웨이의 헤더 허용 목록**이다.
- **이 체계가 이 장에서 얻는 판정 하나** — **API 게이트웨이가 현관문 노릇을 하므로 그 설정에
  각별한 주의를 기울여야 하고, 여기서의 보안 오설정은 파국적 효과를 낼 수 있다** (6장,
  p.161).[^gough2022]

## 이 체계를 지키는 일이 두 갈래로 갈린다

- **7장이 이 체계의 소비자를 인증의 관점에서 다시 센다** (7장, p.168, 그림 7-1).[^gough2022]
  **모바일 앱은 API 게이트웨이를 거쳐 참석자 API에 질의하고, CFP 체계도 비슷한 길을 따르되
  제3자가 소유한다.**
- **그래서 인증할 대상이 둘로 갈린다** (7장, p.168):[^gough2022]
  - **최종 사용자** — 모바일 앱 사용자와 CFP 체계를 쓰는 발표자들이다.
  - **시스템 대 시스템 상호작용** — CFP 체계 자신이다.
- **이 체계가 지켜야 할 것이 무엇인지도 못박힌다** — **참석자 API는 이름과 이메일 주소 같은
  개인 식별 정보를 담고 사용자는 그것이 보호되기를 기대한다** (7장, p.168).[^gough2022]
  **6장의 과도한 데이터 노출 절이 여권 번호로 든 것과 같은 자산**이다.

## 키만으로 사용자를 대신 주장하는 장면

- **7장이 이 체계로 만드는 반례 하나다** (7장, p.171).[^gough2022] **제3자가 소유한 CFP 체계를
  발표자가 쓰고 있고, CFP가 그 사용자 데이터에 딸린 이메일 주소를 갱신해 달라고 요청한다.**
- **판정** — **CFP 체계가 API 키로 식별된다는 것이 그 체계가 최종 사용자가 누구인지나 누구를
  대신하는지를 단언해도 된다는 뜻은 아니다.** 그렇게 하면 **체계 전체의 신뢰를 제3자의 손에
  놓는 것**이다 (7장, p.171).[^gough2022]
- **한 해법이 곧바로 기각된다** — **CFP가 API 키와 함께 사용자의 이름과 비밀번호를 넘겨 참석자
  서비스가 사용자를 인증하게** 하는 것인데, **사용자가 자기 자격 증명을 CFP에 넘겨야 하므로
  바람직하지 않다** (7장, p.171).[^gough2022]
- **그래서 이 체계가 바라는 장면이 규정된다** — **CFP가 참석자 서비스를 부르되, 사용자를 대신한
  요청은 자격 증명의 공유 없이 사용자의 구체적 승인으로 이뤄지는 것**이다 (7장,
  p.171).[^gough2022] 그 해법의 전문은
  [API 인증과 OAuth2의 역할과 토큰](../concepts/api-authentication-and-oauth2-tokens.md)에 있다.
- **이 체계에서 게이트웨이가 맡는 역할 이름이 하나 는다** — **게이트웨이를 OAuth2의 자원 서버로
  쓰는 것**이고, **게이트웨이 뒤에 서비스가 여럿 있어도 클라이언트에게는 게이트웨이가 자원
  서버**다. **이 사례의 자원 소유자는 둘** — 모바일 앱을 쓰는 참석자들과 CFP 체계를 쓰는
  발표자들이다 (7장, p.172, 그림 7-4).[^gough2022]

## 이 체계가 고르는 그랜트 둘

- **두 클라이언트가 서로 다른 그랜트를 쓴다** (7장, p.180, 그림 7-8):[^gough2022]
  - **외부 CFP 체계는 기밀 클라이언트**다 — **비밀을 유지할 수 있으므로 인가 코드 그랜트를 쓸
    수** 있다.
  - **모바일 애플리케이션은 공개 클라이언트**다 — **비밀을 유지할 수 없으므로 인가 코드 그랜트에
    PKCE를 더해야** 한다.
- **둘 다 사용자(자원 소유자)를 대신해 참석자 API에 접근한다** (7장, p.180).[^gough2022]
- **저자들이 그림으로 확인시키는 것 하나** — **PKCE를 쓴다고 해서 높은 수준의 걸음이나 사용자의
  여정이 달라지지 않는다** (7장, p.180).[^gough2022]

## 분기 보고서와 클라이언트 자격 증명 그랜트

- **사용자를 대신하지 않는 요청이 이 체계에 하나 있다** — **외부 CFP 체계가 석 달마다 보고서를
  만드는 일**이고, **참석자 가운데 몇 명이 발표를 제출해 발표자가 되는지를 보인다** (7장,
  p.182).[^gough2022] **참석자를 대신하는 것이 아니라 CFP 체계 자신을 위해 일어난다.**
- **그래서 미리 마련되는 것이 셋이다** (7장, p.182):[^gough2022]
  - **클라이언트(외부 CFP 체계)가 인가 서버에 등록된다.**
  - **참석자 서비스에서 그 클라이언트가 접근 가능한 클라이언트 목록에 더해진다.**
  - **참석자에 대한 정보를 읽고 어느 사용자가 발표를 제출했는지 질의할 수 있게 설정된다** —
    **이것이 미리 마련된 접근**이다.
- **호출 순서** — **클라이언트가 접근하려 할 때 인가 서버에 액세스 토큰을 요청하고 그 토큰을
  써서 참석자 API를 부른다** (7장, p.182).[^gough2022]

## 이 체계의 스코프

- **7장이 이 체계의 종단점을 스코프로 두 번 깎는다** (7장, pp.183–184).[^gough2022] 출발은
  **참석자 API의 종단점 넷**(목록 조회·개별 조회·등록·갱신)과 **레거시 회의 API의 종단점
  둘**(회의 목록 조회·회의 생성)이다. 레거시 쪽 둘은 **이 예를 위해 노출되어 있다고 가정**한 것이다.
- **첫 깎기는 체계의 경계로 가른다** — **외부 CFP는 참석자 API에만 접근하면 되고 자원 소유자는
  CFP가 회의 정보에 접근하는 것을 원하지 않으므로, 참석자 스코프와 회의 스코프 둘**이 만들어진다
  (7장, p.184).[^gough2022]
- **둘째 깎기는 읽기와 쓰기를 가른다** — **조회 둘은 읽기 스코프로, 등록과 갱신은 계정 스코프로**
  간다 (7장, p.184).[^gough2022]
- **이 체계에서 클라이언트의 권한과 사용자의 권한이 어긋나는 장면도 만들어진다** (7장,
  p.185):[^gough2022] 참석자 서비스에는 **참석자를 관리하는 관리자 권한**과 **보기 전용 권한**이
  있을 수 있는데, **한 참석자는 프로필 설명을 읽는 권한만 가진 채로 클라이언트에게 참석자 정보를
  읽고 관리하는 권한을 줄 수** 있다. **곧 사용자가 자기에게 없는 권한을 클라이언트에 위임하는
  꼴**이고, 그 겹침의 전문은
  [OAuth2 그랜트와 스코프와 신원 계층](oauth2-grants-scopes-and-identity-layer.md)에 있다.
- **이 체계에서 OIDC가 필요해지는 자리도 지목된다** — **외부 CFP 체계가 발표자에 대한 데이터를
  저장해야 하는데 OAuth2 그랜트만으로는 최종 사용자의 신원을 얻을 길이 없다** (7장,
  p.186).[^gough2022]

## 참석자 도메인의 경계를 세운다

- **8장이 이 체계에 하는 일은 도메인 경계를 세우는 것**이고, 그 값어치를 **저장소를 갈아 끼우려
  할 때 생기는 갈림길**로 보여 준다 (8장 §"Case Study: Establishing Attendee Domain Boundaries",
  p.194).[^gough2022]
  - **참석자 서비스가 밑에 깔린 데이터 저장소와 강하게 결합돼 그 스키마의 형식으로 데이터를
    노출한다고 하자.** 그러면 제공자가 저장소를 다른 것으로 갈고 싶을 때 **선택지는 둘뿐**이다 —
    **옛 형식과 새 형식 사이를 오가며 데이터를 적응시키는 새 체계를 구현**하거나(복잡하고 오류가
    나기 쉬운 변환 코드를 요구한다), **외부 API를 고치고 모든 소비자가 그것을 채택하게** 하는
    것이다. 저자들이 단서를 붙인다 — **널리 채택된 서비스에서 그 일의 어려움을 과소평가하지 마라.**
  - **위 [참석자 서비스를 소비자에게 노출하기](#참석자-서비스를-소비자에게-노출하기)가 세운 두
    소비자 관계가 이 대가를 실물로 만든다** — 소비자가 둘이므로 둘째 선택지의 비용이 실재한다.
- **응집 쪽의 반례도 이 체계 위에 놓인다** — **회의 엔티티 전체에 걸쳐 쓸 수 있는 편의 함수
  모음을 노출하는 "utils" API를 만들었다고 상상해 보라.** 그러면 **참석자 API 같은 한 API 뒤의
  코드가 바뀌면 다른 유틸리티 API도 함께 고쳐야 하는 상황**이 쉽게 생기고, **원저자가 아니거나
  문서와 테스트가 아주 좋지 않으면 그것을 놓치고 체계에 일관되지 않거나 호환되지 않는 동작을
  남기기 쉽다** (8장, p.193).[^gough2022]

## 이 체계를 모듈로 가르면 어떻게 되는가

- **8장이 서론에서 시작한 체계에 들일 수 있었을 모듈 분해를 제안한다** — **컨트롤러 · 서비스 ·
  데이터 접근 객체(DAO)** 셋을 각각 모듈로 잡는 안이다 (8장 §"Decomposing a System into
  Modules", p.200).[^gough2022]
  - **컨트롤러가 RESTful 종단점을 노출하고 애플리케이션을 띄우는 웹 서버가 그것을 노출한다.**
  - **서비스 모듈은 컨트롤러 뒤에서 업무 로직이 사는 곳**이고 컨트롤러에 분명한 인터페이스를
    노출한다.
  - **DAO 모듈은 서비스 뒤에서 데이터 접근 객체가 사는 곳**이고 서비스에 분명한 인터페이스를
    노출한다.
  - **모듈 층은 꽤 흔하고, 모듈 사이에 분명한 단방향 의존이 서는 지점에 이르는 것이 모듈성의
    좋은 적용**이다 (8장, p.200).[^gough2022]
- **그림 8-1이 본문에 없는 것을 보여 준다** — 세 모듈 각각이 **참석자·예약·세션 셋으로 다시
  갈리고**(참석자 컨트롤러·예약 컨트롤러·세션 컨트롤러, 같은 식으로 서비스와 DAO), 모든 상자에
  **[Component: Class]** 유형 라벨이 붙으며, 아래에 **"사용의 방향"(Direction of usage)** 화살표가
  컨트롤러에서 DAO 쪽으로 그어져 있다 (8장 그림 8-1, p.200).[^gough2022]
  - **위 [컴포넌트 다이어그램](#컴포넌트-다이어그램)이 쓰는 C4 층과 같은 층의 그림**이다.
- **위 [기능 플래그로 참석자를 옮긴다](#기능-플래그로-참석자를-옮긴다)가 8장에서 패턴 이름을
  얻는다** — 8장이 그 기능 플래그 사례를 되부르며 **교살자 무화과의 한 구현 갈래**로 세우고,
  **전에 프로세스 안 상호작용으로 있던 이음매에 새 API를 들일 때 잘 듣지만 이미 프로세스 밖에서
  그 서비스와 상호작용하는 소비자가 많다면 전부가 플래그를 구현하고 통제하기를 기대하는 것은
  비현실적**이라고 적는다 (8장 §"Strangler Fig", p.203).[^gough2022] 그 패턴의 전문은
  [API 이행 패턴과 고통 지점](../concepts/api-migration-patterns-and-pain-points.md)에 있다.

## 참석자 서비스를 클라우드로 옮긴다

- **동기가 업무 쪽이다** — **회의 체계 소유자들이 결국 자기 데이터 센터를 운영하는 부담을 없애고
  싶어 한다**는 것이고, **그것은 궁극적으로 새 서비스 전부와 모놀리식 애플리케이션과
  미들웨어(API 게이트웨이 같은)와 데이터 저장소를 클라우드로 옮기는 일**을 뜻한다 (9장
  §"Case Study: Moving the Attendee Service to the Cloud", p.210).[^gough2022]
- **참석자 서비스를 먼저 고른 이유 둘** — **가장 새로운 구성 요소**이고 **트래픽을 가장 많이 받는
  서비스 가운데 하나**이기 때문이다 (9장, p.210).[^gough2022]
- **여섯 이전 전략을 이 체계에 하나씩 대 본 결과** (9장 §"Case Study: Replatforming the Attendee
  Service to the Cloud", p.214):[^gough2022]

| 전략 | 이 체계에 대한 판정 |
|---|---|
| 유지 또는 재검토 | **유효하지 않다** — 문제를 미루는 것일 뿐이고 클라우드로 간다는 목표를 뒤로 미룬다 |
| 재호스팅 | **탄탄한 전략일 수 있으나 고르지 않았다** — 자기 MySQL 인스턴스를 그대로 들어 옮기는 대신 클라우드 기반 서비스형 데이터베이스를 쓰고 싶었다 |
| **리플랫폼** | **골랐다** — 큰 재작업을 피하면서 새 클라우드 서비스를 활용한다 |
| 재구매 | **말이 되지 않는다** — 이 체계는 주로 맞춤 애플리케이션과 표준 데이터 저장소다 |
| 리팩터·재아키텍처 | **적절해 보이지 않았다** — 참석자 기능을 책 앞부분에서 이미 서비스로 뽑아내 재아키텍처를 해 두었다. 다만 **앞으로 새 기능을 더할 때는 강하게 고려할 선택지**라고 적는다 |
| 폐기 | **아직 폐기할 부분이 없다** — 다만 전체 목표 하나가 레거시 회의 체계의 폐기이고, 리플랫폼과 리팩터가 끝나면 그쪽으로 갈 수 있다 |

- **게이트웨이도 함께 옮기는 결정과 그 이유** — **참석자 서비스의 리플랫폼에 더해 API 게이트웨이를
  클라우드로 이전하기로 했다.** **게이트웨이를 지금 옮기는 것이 API 트래픽을 기존 온프레미스
  위치에서 클라우드로 점진적으로 라우팅하는 것을 돕는다** (9장, p.214).[^gough2022]
  - **순서에 이름이 붙는다** — **엣지에서 시작해 안쪽으로**다. **기존 게이트웨이를 그대로 돌리면서
    현재 게이트웨이의 복제본을 클라우드에 배포할 수 있고, 그러면 프로덕션 체계를 흐트러뜨리지 않고
    클라우드 기반 게이트웨이를 점진적으로 구성해 위험을 최소화할 수 있다** (9장,
    p.216).[^gough2022]
- **네트워크 정책이 이 체계 위에 걸리는 장면** — 클러스터의 파드를 전부 거부 기본값에 둔 뒤,
  **레거시 회의 체계가 참석자 서비스를 찾을 수 있도록 DNS 조회를 여는 정책**과 **레거시 회의
  체계가 참석자 네임스페이스와 통신하도록 이그레스를 여는 정책**을 차례로 연다 (9장
  §"Augmenting Service Mesh with Network Policies", pp.221–222).[^gough2022]
  - **그 사이의 중간 상태가 이 절의 요점이다** — **DNS만 열면 레거시 회의 서비스는 사이드카를
    통해 참석자가 어디 있는지 발견할 수 있지만 요청 자체는 차단된다** (9장,
    p.222).[^gough2022]
- **하이브리드 최종 상태** — 다중 클러스터 서비스 메시 피어링으로 **온프레미스와 클라우드의 데이터
  평면을 결합된 제어 평면의 앎 아래로** 가져오는 배치다. **온프레미스가 클라우드처럼 동작하게
  만듦으로써 나머지 서비스를 클라우드로 진화시킬 쉬운 길이 생긴다** (9장, p.222).[^gough2022]
  이전 전략과 제로 트러스트 전체는
  [API 인프라로 하는 클라우드 이전](../concepts/cloud-migration-with-api-infrastructure.md)에 있다.

**10장이 이 체계의 진화를 처음부터 다시 훑는다** (10장 §"Case Study: A Look Back on Your
Journey", pp.225–232).[^gough2022] **위 [아홉 장이 이 체계에 하는 일](#아홉-장이-이-체계에-하는-일)의
로드맵이 예고였다면, 이 절은 실제로 일어난 아키텍처 변경만 골라 다시 센다.**

| 걸음 | 무엇이 달라졌나 |
|---|---|
| 출발점 | 원래의 회의 체계 아키텍처 |
| 서론 | 이해관계자의 요구에 근거해 **참석자 기능을 API 기반 서비스로 뽑아내 레거시 회의 체계 밖의 독립 프로세스로 돌리기로** 결정 |
| 1·2장 | **아키텍처는 그대로** — 참석자 API와 서비스를 설계하고 테스트하는 동안 정적이었다 |
| 3장 | **첫 큰 진화적 걸음** — 최종 사용자 고객과 기존 회의 체계·새 서비스 사이에 API 게이트웨이를 들였다. 고객이 게이트웨이를 거쳐 요청하고 게이트웨이가 **추상과 단일 진입점**을 준다. **이 걸음이 파사드 패턴을 들였고 레거시를 부를지 현대 서비스를 부를지 통제하게 했다** |
| 4장 | 레거시 체계에서 **세션 기능을 새 세션 서비스로 뽑아내고** 서비스 간 API 트래픽을 다루는 **서비스 메시**를 들였다 |
| 5장 | 참석자 서비스의 **내부 판과 외부 판**을 만들고 **기능 플래그로 사용자 요청이 어느 쪽으로 가는지** 정했다 |
| 6장 | **아키텍처는 그대로** — 다만 위협 모델링의 현실적 시나리오를 위해 **모바일 애플리케이션**이 회의 체계를 부르는 개념을 들였다 |
| 7장 | **외부 CFP 체계**를 아키텍처에 더했고, 그것이 외부(사용자 대면) 인증과 인가의 구현을 요구했다 |
| 9장 | 참석자 서비스와 API 게이트웨이를 **클라우드 플랫폼으로 이전**했고, 이어서 **다중 클러스터 서비스 메시로 제로 트러스트 아키텍처를 향하는 모델**을 냈다 — 진화가 이어지는 동안의 **하이브리드 아키텍처** 선택지다 |

  바꾸지 않고 바꾸는 방법을 다루는 장**이기 때문으로 읽힌다. **저자들이 그 생략을 설명하지
  않는다.** 이 관찰은 이 KB가 표를 훑어 센 것이다. #hypothesis
- **회고의 초점을 저자들이 밝힌다** — **전형적인 체계가 API 기반 또는 서비스 기반으로 진화할 때
  당신과 당신의 팀이 내려야 할 핵심 결정 지점을 부각하는 데** 있었다 (10장,
  p.232).[^gough2022]
- **맺는 판정 한 문장** — **온프레미스에서 도는 서비스 하나와 데이터베이스라는 소박한 출발점에서

## 이 KB의 다른 사례 연구와 갈리는 자리

- **장마다 같은 체계를 다시 손대며 절충을 비교하는 매체**라는 점에서
  [Sysops Squad 사례](../concepts/sysops-squad-case.md)와 같은 종류다. 갈리는 것은 축이다 —
  Sysops Squad는 **모놀리스를 쪼개는 일과 데이터를 가르는 일**을 축으로 놓고, 이 체계는
  **인터페이스와 그 트래픽**을 축으로 놓는다.
- [화물 운송 예제](../concepts/cargo-shipping-example.md)의 설계 연습이나
  [마켓노버스 사례 연구](../concepts/marketnovus-case-study.md)의 사후 기록과는 성격이 다르다.
  **이 체계는 지어낸 것이고 앞으로 진화시킬 대상**이지 이미 일어난 일의 기록이 아니다.
- **이 페이지는 사례 연구가 무엇인가만 담는다.** 각 장이 그 체계에 적용하는 기법의 정본은 그
  기법의 페이지이고, 위 로드맵 표는 **어느 장이 어디를 손대는가의 색인**이다.
