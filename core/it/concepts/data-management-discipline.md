하나의 질문: **데이터를 자산으로 다룬다는 말이 데이터 엔지니어의 일에서 구체적으로 무엇을
뜻하는가.**

## 왜 "엔터프라이즈스러운" 것이 돌아왔는가

- 내력 — **데이터 관리는 수십 년간 있었지만 최근까지 데이터 엔지니어링에서 큰 견인을 얻지
  못했다. 데이터 도구가 단순해지고 데이터 엔지니어가 관리할 복잡성이 줄고 있다. 그 결과 데이터
  엔지니어는 가치 사슬을 올라 다음 단의 모범 실무로 옮겨 간다. 한때 거대 기업에만 유보됐던
  데이터 모범 실무 — 데이터 거버넌스, 마스터 데이터 관리, 데이터 품질 관리, 메타데이터 관리 —
  가 이제 모든 크기와 성숙도의 회사로 내려오고 있다. 우리 표현대로 데이터 엔지니어링은
  "엔터프라이즈스러워지고" 있다** (2장, p.50).[^reis2022]
- 정의는 DMBOK을 인용한다. 왜곡에 민감한 구간이라 원문을 직인용한다 (2장, p.50):[^reis2022]

  > Data management is the development, execution, and supervision of plans, policies,
  > programs, and practices that deliver, control, protect, and enhance the value of data
  > and information assets throughout their lifecycle.

- 데이터 엔지니어링과의 연결 — **데이터 엔지니어는 데이터 수명 주기를 관리하고, 데이터 관리는
  데이터 엔지니어가 그 과업을 기술적으로도 전략적으로도 완수하는 데 쓸 모범 실무의 집합을
  아우른다. 데이터를 관리하는 프레임워크가 없으면 데이터 엔지니어는 진공 속에서 작동하는
  기술자에 지나지 않는다** (2장, p.50).[^reis2022]
- 왜 중요한가 — **데이터 관리는 기업이 재무 자원·완제품·부동산을 자산으로 보듯 데이터가 일상
  운영에 필수적임을 보여 준다. 데이터 관리 실무는 조직이 데이터에서 가치를 얻고 그것을 적절히
  다루도록 모두가 채택할 수 있는 응집된 프레임워크를 이룬다** (2장, pp.50–51).[^reis2022]

## 데이터 거버넌스

- 정의는 인용된다 — **『Data Governance: The Definitive Guide』에 따르면 "데이터 거버넌스는
  무엇보다 조직이 수집한 데이터의 품질·무결성·보안·사용성을 보장하기 위한 데이터 관리
  기능이다"** (2장, p.51).[^reis2022]
- 저자들의 확장 — **데이터 거버넌스는 사람·프로세스·기술을 관여시켜 조직 전체에서 데이터
  가치를 최대화하면서 적절한 보안 통제로 데이터를 보호한다. 효과적인 데이터 거버넌스는
  의도를 갖고 개발되며 조직의 지지를 받는다. 데이터 거버넌스가 우발적이고 되는대로일 때
  부작용은 신뢰할 수 없는 데이터부터 보안 침해까지 그 사이 전부에 걸칠 수 있다** (2장,
  p.51).[^reis2022]
- 나쁘게 되는 실물 — **업무 분석가가 리포트 요청을 받았는데 질문에 답할 데이터가 무엇인지
  모른다. 트랜잭션 데이터베이스의 수십 개 테이블을 몇 시간 뒤지며 어떤 필드가 유용할지 마구
  추측한다. 분석가는 "방향은 맞는" 리포트를 만들지만 그 기반 데이터가 정확하거나 건전한지
  전혀 확신하지 못한다. 리포트 수신자도 데이터의 유효성을 의심한다. 분석가의 — 그리고 회사
  시스템의 모든 데이터의 — 무결성이 의문에 부쳐진다. 회사는 자기 성과에 혼란스러워하고 업무
  계획은 불가능해진다** (2장, pp.51–52).[^reis2022]
- 핵심 세 범주 — **데이터 거버넌스의 핵심 범주는 발견 가능성(discoverability)·보안·책임
  (accountability)이다. 이 핵심 범주 안에 데이터 품질·메타데이터·프라이버시 같은 하위 범주가
  있다** (2장, p.52).[^reis2022]
- 발견 가능성 — **데이터 주도 회사에서 데이터는 가용하고 발견 가능해야 한다. 최종 사용자는
  자기 일을 하는 데 필요한 데이터에 빠르고 신뢰할 수 있게 접근할 수 있어야 한다. 그들은
  데이터가 어디서 오는지, 다른 데이터와 어떻게 관계되는지, 그 데이터가 무엇을 뜻하는지 알아야
  한다. 발견 가능성의 핵심 영역에는 메타데이터 관리와 마스터 데이터 관리가 든다** (2장,
  p.52).[^reis2022] 각각은 [메타데이터 관리](../concepts/metadata-management.md)와
  [마스터 데이터 관리](../concepts/master-data-management.md)에 있다.
- 데이터 품질과 책임은 [데이터 웨어하우스의 데이터 품질 관리](../concepts/data-quality-management.md)에
  합류시켰다.

## 데이터 모델링과 설계

- **데이터에서 업무 통찰을 끌어내려면 데이터가 쓸 수 있는 형태여야 한다. 데이터를 쓸 수 있는
  형태로 바꾸는 프로세스가 데이터 모델링과 설계다. 전통적으로 데이터 모델링을 DBA와 ETL
  개발자의 문제로 생각하지만, 데이터 모델링은 조직 거의 어디에서나 일어날 수 있다. 펌웨어
  엔지니어가 IoT 장치 레코드의 데이터 형식을 개발하거나, 웹 애플리케이션 개발자가 API 호출에
  대한 JSON 응답이나 MySQL 테이블 스키마를 설계하는 것 — 전부 데이터 모델링과 설계의
  사례다** (2장, p.57).[^reis2022]
- 왜 어려워졌나 — **새 데이터 원천과 유스케이스의 다양성 때문에 데이터 모델링은 더 도전적이
  됐다. 예컨대 엄격한 정규화는 이벤트 데이터와 잘 맞지 않는다** (2장, p.57).[^reis2022]
- 도구가 뒤따랐다 — **다행히 새 세대의 데이터 도구는 측정값·차원·속성·계층의 논리적 분리를
  유지하면서 데이터 모델의 유연성을 높인다. 클라우드 데이터 웨어하우스는 방대한 양의
  비정규화·반정형 데이터의 반입을 지원하면서 Kimball·Inmon·Data Vault 같은 흔한 데이터 모델링
  패턴도 여전히 지원한다. 스파크 같은 데이터 처리 프레임워크는 평평한 정형 관계 레코드부터
  원시 비정형 텍스트까지 데이터의 전 스펙트럼을 반입할 수 있다** (2장, p.57).[^reis2022]
  세 방법론의 내용은 [데이터 웨어하우스 모델링](../synthesis/data-warehouse-modeling.md)에 있다.
- 포기하면 어떻게 되나 — **엔지니어가 감당해야 할 데이터의 폭이 넓다 보니 손을 들고 데이터
  모델링을 포기하고 싶은 유혹이 있다. 이는 끔찍한 생각이며 참담한 결과를 낳는데, 사람들이 한
  번 쓰고 결코 읽지 않는(write once, read never, WORN) 접근 패턴을 중얼거리거나 데이터
  늪(data swamp)을 언급할 때 그것이 드러난다** (2장, p.57).[^reis2022]

## 데이터 계보

- 정의 — **데이터가 수명 주기를 지나갈 때 어떤 시스템이 데이터에 영향을 줬는지, 이리저리
  넘겨지고 변환되는 동안 데이터가 무엇으로 구성돼 있는지 어떻게 아는가? 데이터 계보(data
  lineage)는 데이터를 처리하는 시스템과 그것이 의존하는 상류 데이터 양쪽을 추적하면서 수명
  주기 전반에 걸친 데이터의 감사 추적(audit trail)을 기록하는 것을 서술한다** (2장,
  p.57).[^reis2022]
- 무엇에 쓰나 — **데이터 계보는 오류 추적, 책임 소재, 데이터와 그것을 처리하는 시스템의 디버깅에
  도움이 된다. 데이터 수명 주기에 대한 감사 추적을 제공한다는 명백한 이득이 있고 규제 준수에도
  도움이 된다. 예컨대 어떤 사용자가 자기 데이터를 시스템에서 삭제하기를 원하면, 그 데이터에
  대한 계보가 있어야 그것이 어디에 저장돼 있고 무엇에 의존하는지 알 수 있다** (2장,
  pp.57–58).[^reis2022]
- 확산 — **데이터 계보는 엄격한 컴플라이언스 기준을 가진 큰 회사들에서 오랫동안 있어 왔다.
  그러나 데이터 관리가 주류가 되면서 이제 작은 회사에도 더 널리 채택되고 있다** (2장,
  p.58).[^reis2022]
- 관련 개념 — **Andy Petrella의 데이터 관측 가능성 주도 개발(Data Observability Driven
  Development, DODD) 개념은 데이터 계보와 밀접히 관련된다. DODD는 계보를 따라 내내 데이터를
  관측한다. 이 프로세스는 개발·테스트·최종적으로 프로덕션에 적용돼 품질과 기대 부합성을
  전달한다** (2장, p.58).[^reis2022]

## 데이터 통합과 상호운용성

- 정의 — **데이터 통합과 상호운용성은 도구와 프로세스에 걸쳐 데이터를 통합하는 프로세스다.
  분석에 대한 단일 스택 접근에서 벗어나 여러 도구가 요구에 따라 데이터를 처리하는 이질적
  클라우드 환경으로 옮겨 가면서, 통합과 상호운용성은 데이터 엔지니어 일에서 점점 넓어지는
  부분을 차지한다** (2장, p.58).[^reis2022]
- 방식의 변화 — **점점 더 통합은 커스텀 데이터베이스 연결이 아니라 범용 API를 통해 일어난다.
  예컨대 데이터 파이프라인은 Salesforce API에서 데이터를 당겨 Amazon S3에 저장하고, Snowflake
  API를 호출해 테이블로 적재하고, API를 다시 호출해 질의를 돌린 다음, 결과를 스파크가 소비할 수
  있는 S3로 내보낼 수 있다** (2장, p.58).[^reis2022]
- 그 결과의 역설 — **이 모든 활동은 데이터를 직접 다루는 대신 데이터 시스템과 대화하는 비교적
  단순한 파이썬 코드로 관리될 수 있다. 데이터 시스템과 상호작용하는 복잡성은 줄었지만 시스템의
  수와 파이프라인의 복잡성은 극적으로 늘었다. 처음부터 시작하는 엔지니어는 맞춤 스크립팅의
  능력을 빠르게 넘어서고 오케스트레이션의 필요에 걸려 넘어진다** (2장, p.58).[^reis2022]
  - 같은 문제를 시스템 원리 층위에서 다룬 것이 [데이터 통합](../concepts/data-integration.md)이다.
    그쪽은 **어느 표현이 어디서 파생되는가**를 묻고, 여기는 **무엇이 무엇을 호출하는가**를
    묻는다.

## 데이터 수명 주기 관리

- 무시되던 문제 — **데이터 레이크의 도래는 조직이 데이터 아카이브와 파기를 무시하도록 부추겼다.
  저장을 무한정 더할 수 있는데 왜 데이터를 버리겠는가?** (2장, p.58).[^reis2022]
- 두 변화가 그것을 되돌렸다 (2장, pp.58–59):[^reis2022]
  - **첫째, 데이터가 점점 더 클라우드에 저장된다. 이는 온프레미스 데이터 레이크를 위한 큰
    선행 자본 지출 대신 종량제 저장 비용을 갖는다는 뜻이다. 모든 바이트가 월별 AWS 명세서에
    나타나면 CFO는 절감 기회를 본다. 주요 클라우드 벤더는 매우 드문 접근을 가정해 극히 낮은
    비용으로 장기 데이터 보존을 허용하는 아카이브 전용 객체 저장 클래스를 제공한다. 이
    저장 클래스는 중요한 아카이브의 우발적·의도적 삭제를 막는 추가 정책 통제도 지원한다.**
  - **둘째, GDPR·CCPA 같은 프라이버시·데이터 보존 법이 데이터 엔지니어에게 사용자의 "잊힐
    권리"를 존중하도록 데이터 파기를 능동적으로 관리할 것을 요구한다. 데이터 엔지니어는 어떤
    소비자 데이터를 보유하는지 알아야 하고 요청과 컴플라이언스 요구에 응해 데이터를 파기할
    절차를 가져야 한다.**
- 파기의 난이도가 저장 방식에 달렸다 — **데이터 파기는 클라우드 데이터 웨어하우스에서
  단순하다. SQL 의미론이 `where` 절에 부합하는 행의 삭제를 허용한다. 데이터 파기는 한 번 쓰고
  여러 번 읽는 것이 기본 저장 패턴이던 데이터 레이크에서 더 도전적이었다. Hive ACID나 Delta
  Lake 같은 도구가 규모에서 삭제 트랜잭션을 쉽게 관리하게 해 준다** (2장, p.59).[^reis2022]

## 윤리와 프라이버시

- 지위의 변화 — **지난 몇 년의 데이터 침해·허위 정보·데이터 오용은 한 가지를 분명히 한다:
  데이터는 사람에게 영향을 준다. 데이터는 한때 야생 서부에 살며 야구 카드처럼 자유롭게
  수집되고 거래됐다. 그 시절은 오래전에 갔다. 데이터의 윤리적·프라이버시적 함의는 한때 보안처럼
  있으면 좋은 것으로 여겨졌지만, 이제는 일반 데이터 수명 주기의 중심이다** (2장,
  p.59).[^reis2022]
- 저자들의 규범 — **데이터 엔지니어는 아무도 보고 있지 않을 때 옳은 일을 해야 한다. 언젠가는
  모두가 보고 있을 것이기 때문이다** (2장, p.59).[^reis2022]
- 구체적으로 무엇을 하는가 — **데이터 엔지니어는 데이터셋이 개인 식별 정보(personally
  identifiable information, PII)와 그 밖의 민감 정보를 가리도록 보장해야 하고, 데이터셋이
  변환되는 동안 편향이 식별·추적될 수 있게 해야 한다. 규제 요구사항과 컴플라이언스 처벌은
  커지기만 한다. GDPR·CCPA 같은 늘어나는 데이터 규제에 데이터 자산이 부합하도록 보장하라**
  (2장, p.59).[^reis2022]
