하나의 질문: **분석가·데이터 과학자·ML 엔지니어의 손에 데이터를 실제로 얹는 경로는 무엇이며,
경로마다 무엇을 얻고 무엇을 감수하는가.**

## 네 갈래의 목록

- **분석에서와 마찬가지로 데이터 엔지니어는 데이터 과학자와 ML 엔지니어에게 그들이 일하는 데
  필요한 데이터를 제공한다. 파이프라인과 프로세스가 극도로 비슷하기 때문에 우리는 ML을 위한
  서빙을 분석과 나란히 두었다. 분석과 ML에 데이터를 서빙하는 방법은 많다. 이 데이터를 서빙하는
  흔한 방법에는 파일·데이터베이스·질의 엔진·데이터 공유가 있다** (9장, p.351).[^reis2022]

## 파일 교환

- 왜 어디에나 있는가 — **파일 교환(file exchange)은 데이터 서빙에서 어디에나 있다. 우리는
  데이터를 처리하고 파일을 생성해 데이터 소비자에게 넘긴다** (9장, p.351).[^reis2022]
- 하나의 파일이 여러 목적을 갖는다 — **파일이 많은 목적에 쓰일 수 있음을 유념하라. 데이터
  과학자는 고객 불만의 감성을 분석하기 위해 고객 메시지의 텍스트 파일(비구조화 데이터)을 적재할
  수 있다. 업무 부서는 파트너 회사에서 CSV 모음(구조화 데이터)으로 송장 데이터를 받을 수 있고
  분석가는 이 파일들에 통계 분석을 수행해야 한다. 또는 데이터 벤더가 온라인 소매사에 경쟁사
  웹사이트의 제품 이미지(비구조화 데이터)를 제공해 컴퓨터 비전으로 자동 분류하게 할 수 있다**
  (9장, p.351).[^reis2022]
- 서빙 방식을 정하는 다섯 요인 (9장, p.352):[^reis2022]
  - **유스케이스 — 비즈니스 분석·운영 분석·임베디드 분석.**
  - **데이터 소비자의 데이터 취급 프로세스.**
  - **저장소에 있는 개별 파일의 크기와 개수. 이 파일에 누가 접근하는가.**
  - **데이터 유형 — 구조화·반구조화·비구조화.**
- 왜 둘째 항이 중요한가 — **둘째 항목이 주요 고려 사항 중 하나다. 데이터 소비자가 공유 플랫폼을 쓸
  수 없기 때문에 데이터 공유가 아니라 파일을 통해 데이터를 서빙해야 하는 경우가 흔하다** (9장,
  p.352).[^reis2022]
- 가장 단순한 형태와 그 함정 — **서빙할 가장 단순한 파일은 엑셀 파일 하나를 이메일로 보내는 것과
  같은 부류다. 파일을 협업으로 공유할 수 있는 시대에도 이는 여전히 흔한 워크플로다. 파일을
  이메일로 보내는 문제는 각 수신자가 자기 버전의 파일을 갖는다는 것이다. 수신자가 파일을 편집하면
  이 편집은 그 사용자의 파일에 국한된다. 파일 사이의 어긋남이 필연적으로 생긴다. 그리고 수신자가
  더는 그 파일에 접근하기를 원하지 않는다면 어떻게 되는가? 파일이 이메일로 보내졌다면 그것을 회수할
  수단이 거의 없다. 일관되고 정합적인 단일 버전이 필요하다면 Microsoft 365나 Google Docs 같은 협업
  플랫폼을 쓸 것을 제안한다** (9장, p.352).[^reis2022]
- 규모가 커지면 — **물론 단일 파일을 서빙하는 것은 확장하기 어렵고, 필요는 결국 단순한 클라우드 파일
  저장을 넘어설 것이다. 큰 파일이 몇 개라면, 혹은 파일이 꾸준히 공급되는 데이터 레이크라면 오브젝트
  저장 버킷으로 자라날 것이다. 오브젝트 저장은 어떤 유형의 블롭 파일도 저장할 수 있고 특히 반구조화·
  비구조화 파일에 유용하다** (9장, p.352).[^reis2022]
- 분류의 단서 — **일반적으로 우리는 오브젝트 저장(데이터 레이크)을 통한 파일 교환을 파일 교환보다
  "데이터 공유" 아래에 두는데, 그 프로세스가 애드혹 파일 교환보다 유의하게 확장 가능하고 매끄러울 수
  있기 때문이다** (9장, p.352).[^reis2022] 오브젝트 저장 자체는
  [오브젝트 스토어](../concepts/object-stores.md)에 있다.

## 데이터베이스

- 자리 — **데이터베이스는 분석과 ML을 위한 데이터 서빙에서 결정적인 계층이다. 이 논의에서 우리는
  암묵적으로 OLAP 데이터베이스(데이터 웨어하우스·데이터 레이크 같은)에서 데이터를 서빙하는 데 초점을
  유지한다. 데이터 서빙은 데이터베이스를 질의한 다음 그 결과를 유스케이스에 소비하는 것을 수반한다.
  분석가나 데이터 과학자는 SQL 편집기로 데이터베이스를 질의하고 그 결과를 CSV 파일로 내보내
  하류 애플리케이션이 소비하게 하거나, 노트북에서 결과를 분석할 수 있다** (9장,
  p.352).[^reis2022] 그 질의가 안에서 겪는 것은
  [질의의 생애와 성능](../concepts/query-lifecycle-and-performance.md)에 있다.
- 이점 — **데이터베이스에서 데이터를 서빙하는 것은 다양한 이점을 동반한다. 데이터베이스는 스키마를
  통해 데이터에 순서와 구조를 부과한다. 데이터베이스는 테이블·컬럼·행 수준의 세밀한 권한 통제를
  제공해 데이터베이스 관리자가 다양한 역할을 위한 복잡한 접근 정책을 짤 수 있게 한다. 그리고
  데이터베이스는 크고 계산 집약적인 질의와 높은 질의 동시성에 대해 높은 서빙 성능을 제공할 수 있다**
  (9장, pp.352–353).[^reis2022]
- BI 시스템과의 분담 — **BI 시스템은 보통 데이터 처리 작업부하를 원천 데이터베이스와 나눠 갖지만 두
  시스템 사이의 경계는 다양하다. 예컨대 Tableau 서버는 데이터베이스에서 데이터를 끌어오는 초기 질의를
  돌리고 그것을 로컬에 저장한다. 기본적인 OLAP/BI 슬라이싱과 다이싱(대화식 필터링과 집계)은 로컬
  데이터 사본 위에서 서버에서 직접 돌아간다** (9장, p.353).[^reis2022]
- 질의 푸시다운 — **반면 Looker(와 비슷한 최신 BI 시스템)는 질의 푸시다운(query pushdown)이라 불리는
  계산 모델에 의존한다. Looker는 데이터 처리 로직을 특화 언어(LookML)로 인코딩하고, 이를 동적인 사용자
  입력과 결합해 SQL 질의를 생성하고, 이 질의를 원천 데이터베이스에 대해 돌린 뒤 출력을 제시한다.
  Tableau와 Looker 둘 다 자주 도는 질의의 처리 부담을 줄이기 위한 다양한 결과 캐싱 설정을 갖는다**
  (9장, p.353).[^reis2022] 그 LookML이 놓인 계층은
  [시맨틱 계층과 메트릭 계층](../concepts/semantic-and-metrics-layers.md)이다.
- 데이터 과학 쪽 경로 — **데이터 과학자는 데이터베이스에 연결해 데이터를 추출하고 피처 엔지니어링과
  선택을 수행할 수 있다. 이 변환된 데이터셋이 ML 모델에 먹여지고 오프라인 모델이 학습돼 예측 결과를
  생산한다** (9장, p.353).[^reis2022]
- 서빙 계층 관리 — **데이터 엔지니어는 흔히 데이터베이스 서빙 계층을 관리하는 일을 맡는다. 여기에는
  성능과 비용의 관리가 포함된다. 컴퓨트와 저장을 분리하는 데이터베이스에서 이는 고정된 온프레미스
  인프라 시절보다 다소 미묘한 최적화 문제다. 예컨대 이제는 각 분석·ML 작업부하마다 새 스파크
  클러스터나 Snowflake 웨어하우스를 띄우는 것이 가능하다** (9장, p.353).[^reis2022]
  - 권고 — **일반적으로 유스케이스에 따라 클러스터를 적어도 쪼개는 것이 권장된다 — 예컨대 ETL과
    분석·데이터 과학용 서빙으로. 데이터 팀은 흔히 더 잘게 나누기로 선택해 주요 영역마다 웨어하우스
    하나를 할당한다. 이는 서로 다른 팀이 데이터 엔지니어링 팀의 감독 아래 자기 질의 비용을 예산할 수
    있게 해 준다** (9장, p.353).[^reis2022] 이 분리를 가능하게 한 축은
    [컴퓨트와 저장의 분리](../concepts/compute-storage-separation.md)다.
- 임베디드 분석이 걸리는 자리 — **임베디드 분석에서 논한 세 성능 고려 사항 — 데이터 지연·질의 성능·
  동시성 —을 상기하라. 스트림에서 직접 반입할 수 있는 시스템은 데이터 지연을 낮출 수 있다. 그리고 많은
  데이터베이스 아키텍처가 임베디드 분석에 내재한 도전적인 유스케이스를 서빙하기 위해 질의 성능과
  동시성을 높이려 SSD나 메모리 캐싱에 의존한다** (9장, p.353).[^reis2022]
- 한 지붕 아래 — **점점 더 Snowflake·Databricks 같은 데이터 플랫폼이 분석가와 데이터 과학자가 단일
  환경에서 작동하게 해, SQL 편집기와 데이터 과학 노트북을 한 지붕 아래 제공한다. 컴퓨트와 저장이
  분리돼 있기 때문에 분석가와 데이터 과학자는 서로를 방해하지 않고 다양한 방식으로 기저 데이터를
  소비할 수 있다. 이는 높은 처리량과 이해관계자에게 더 빠른 데이터 제품 전달을 허용할 것이다** (9장,
  p.353).[^reis2022]

## 스트리밍 시스템

- 무엇이 다른가 — **스트리밍 분석은 서빙의 영역에서 점점 더 중요하다. 높은 수준에서 이 유형의 서빙은
  전통적 질의와 다른 방출 지표(emitted metrics)를 수반할 수 있음을 이해하라** (9장,
  p.354).[^reis2022]
- 그리고 운영 분석 데이터베이스 — **또한 우리는 운영 분석 데이터베이스가 이 영역에서 커지는 역할을
  하는 것을 본다. 이 데이터베이스는 역사적 데이터의 넓은 범위에 걸쳐 질의를 돌리게 해 주며 초 단위
  최신 현재 데이터를 포괄한다. 본질적으로 그것들은 OLAP 데이터베이스의 측면과 스트림 처리 시스템을
  결합한다. 점점 더 분석과 ML을 위해 데이터를 서빙하는 데 스트리밍 시스템과 일하게 될 것이므로 이
  패러다임에 익숙해지라** (9장, p.354).[^reis2022] 그 패러다임은
  [스트림 처리 패러다임](../concepts/stream-processing-paradigm.md)에 있다.

## 질의 페더레이션

- 정의 — **8장에서 배웠듯 질의 페더레이션(query federation)은 데이터 레이크·RDBMS·데이터 웨어하우스
  같은 여러 원천에서 데이터를 끌어온다. 분산 질의 가상화 엔진이 인지를 얻으면서, 데이터를 OLAP
  시스템에 중앙화하는 수고를 거치지 않고 질의를 서빙하는 방법으로 페더레이션이 더 인기를 얻고 있다.
  오늘날 Trino·Presto 같은 OSS 선택지와 Starburst 같은 관리형 서비스를 찾을 수 있다. 이 제공물 중
  일부는 스스로를 데이터 메시를 가능하게 하는 방법으로 서술한다. 그것이 어떻게 펼쳐질지는 시간이
  말해 줄 것이다** (9장, p.354).[^reis2022] 페더레이션이 언번들링 논의에서 놓이는 자리는
  [데이터베이스 언번들링](../concepts/unbundling-databases.md)이다.
- 서빙 관점의 부담 — **페더레이션 질의를 위해 데이터를 서빙할 때 최종 사용자가 여러 시스템 —
  OLTP·OLAP·API·파일시스템 등 —을 질의하고 있을 수 있음을 알아야 한다. 단일 시스템에서 데이터를
  서빙하는 대신 이제 여러 시스템에서 서빙하고 있으며 각각은 자기 사용 패턴·특이점·뉘앙스를 갖는다.
  이는 데이터 서빙에 도전을 제기한다. 페더레이션 질의가 살아 있는 프로덕션 원천 시스템을 건드린다면
  그 페더레이션 질의가 원천에서 과도한 자원을 소비하지 않도록 보장해야 한다** (9장,
  p.354).[^reis2022]
- 언제 이상적인가 — **우리 경험상 페더레이션 질의는 데이터 분석에 유연성을 원하거나 원천 데이터를
  엄격히 통제해야 할 때 이상적으로 맞는다. 페더레이션은 애드혹 질의로 탐색적 분석을 수행하게 해
  주며, 데이터 파이프라인이나 ETL을 세우는 복잡성 없이 다양한 시스템의 데이터를 섞는다. 이는
  페더레이션 질의의 성능이 지속적 목적에 충분한지, 아니면 일부나 전체 데이터 원천에 반입을 세우고
  OLAP 데이터베이스나 데이터 레이크에 중앙화해야 하는지 판단하게 해 준다** (9장,
  p.355).[^reis2022]
- 읽기 전용이라는 성질 — **페더레이션 질의는 원천 시스템에 읽기 전용 접근도 제공하는데, 이는 파일·
  데이터베이스 접근·데이터 덤프를 서빙하고 싶지 않을 때 훌륭하다. 최종 사용자는 자신이 접근해야 할
  버전의 데이터만 읽고 그 이상은 읽지 않는다. 질의 페더레이션은 접근과 컴플라이언스가 결정적인
  상황에서 탐색해 볼 훌륭한 선택지다** (9장, p.355).[^reis2022]

## 데이터 공유

- 네 번째 갈래 — **데이터 공유(data sharing)는 일반적으로 데이터 서빙을 보안과 접근 통제의 문제로
  바꾼다** (9장, p.355).[^reis2022] 파이프라인을 짜는 문제가 권한을 짜는 문제로 대체되므로 이 목록의
  다른 셋과 성격이 다르다. 5장·6장·9장의 서술이 모이는 본가는
  [데이터 공유와 서드파티 소스](../concepts/data-sharing-and-third-party-sources.md)이며,
  거기의 "서빙 쪽에서 세 번째로 본 데이터 공유" 절이 이 갈래의 전문이다.

## 노트북으로 서빙하기

- 왜 노트북이 서빙 대상인가 — **데이터 과학자는 일상 업무에서 흔히 노트북을 쓴다. 데이터를 탐색하든
  피처를 엔지니어링하든 모델을 학습시키든 데이터 과학자는 노트북을 쓸 가능성이 크다. 이 글을 쓰는
  시점에 가장 인기 있는 노트북 플랫폼은 Jupyter Notebook과 그 차세대인 JupyterLab이다. Jupyter는
  오픈 소스이며 노트북에서 로컬로, 서버에서, 혹은 다양한 클라우드 관리형 서비스를 통해 호스팅될 수
  있다. Jupyter는 Julia·Python·R을 뜻하며 뒤의 둘이 데이터 과학 응용, 특히 노트북에 인기 있다.
  쓰는 언어와 무관하게 가장 먼저 고려해야 할 것은 노트북에서 데이터에 어떻게 접근할 수 있는가다**
  (9장, p.356).[^reis2022]
- 접근 경로 — **데이터 과학자는 API·데이터베이스·데이터 웨어하우스·데이터 레이크 같은 데이터 원천에
  프로그램적으로 연결할 것이다. 노트북에서 모든 연결은 파일 경로에서 파일을 적재하거나 API 엔드포인트에
  연결하거나 데이터베이스에 ODBC 연결을 맺기 위해 적절한 내장·임포트 라이브러리로 만들어진다. 원격
  연결은 연결을 맺기 위해 올바른 자격증명과 권한을 요구할 수 있다. 연결되고 나면 사용자는 테이블
  (그리고 행·컬럼)이나 오브젝트 저장에 저장된 파일에 대한 올바른 접근이 필요할 수 있다. 데이터
  엔지니어는 흔히 데이터 과학자가 올바른 데이터를 찾도록 돕고 그다음 그들이 필요한 행과 컬럼에 접근할
  올바른 권한을 갖도록 보장한다** (9장, pp.356–357).[^reis2022]
- 전형적 워크플로 — **데이터 과학자에게 극도로 흔한 워크플로 하나는 로컬 노트북을 돌려 데이터를 pandas
  데이터프레임으로 적재하는 것이다. pandas는 데이터 조작과 분석에 쓰이는 널리 퍼진 파이썬 라이브러리이며
  데이터(가령 CSV 파일)를 Jupyter 노트북에 적재하는 데 흔히 쓰인다. pandas가 데이터셋을 적재할 때
  그것은 이 데이터셋을 메모리에 저장한다** (9장, p.357).[^reis2022] 데이터프레임이라는 추상 자체는
  [데이터프레임과 배열](../concepts/dataframes-and-arrays.md)에 있다.
- 메모리를 넘으면 — **데이터셋 크기가 로컬 머신의 가용 메모리를 넘으면 어떻게 되는가? 랩톱과 워크스테이션의
  제한된 메모리를 생각하면 이는 필연적으로 일어난다 — 데이터 과학 프로젝트가 그 자리에서 죽는다. 더
  확장 가능한 선택지를 고려할 때다. 먼저 노트북의 기저 저장과 메모리를 유연하게 확장할 수 있는 클라우드
  기반 노트북으로 옮기라. 이 선택지를 넘어서면 분산 실행 시스템을 보라. 인기 있는 파이썬 기반 선택지에는
  Dask·Ray·Spark가 있다. 완전한 클라우드 관리형 제공물이 매력적이라면 Amazon SageMaker·Google Cloud
  Vertex AI·Microsoft Azure Machine Learning으로 데이터 과학 워크플로를 세우는 것을 고려하라.
  마지막으로 Kubeflow·MLflow 같은 오픈 소스 종단 간 ML 워크플로 선택지는 각각 쿠버네티스와 스파크에서
  ML 작업부하를 확장하기 쉽게 만든다. 요점은 데이터 과학자를 랩톱에서 떼어 내 클라우드의 힘과 확장성을
  활용하게 하는 것이다** (9장, p.358).[^reis2022]
- 누가 그 이동을 돕는가 — **데이터 엔지니어와 ML 엔지니어는 확장 가능한 클라우드 인프라로의 이동을
  촉진하는 데 핵심 역할을 한다. 정확한 분업은 조직의 세부에 크게 달렸다. 그들은 클라우드 인프라를
  세우고 환경 관리를 감독하며 데이터 과학자를 클라우드 기반 도구로 훈련시키는 일을 이끌어야 한다.
  클라우드 환경은 버전과 갱신 관리·접근 통제·SLA 유지 같은 상당한 운영 작업을 요구한다. 다른 운영
  작업과 마찬가지로 "데이터 과학 운영"이 잘 되면 상당한 보상이 뒤따른다** (9장,
  p.358).[^reis2022]
- 프로덕션이 되는 노트북 — **노트북은 프로덕션 데이터 과학의 일부가 되기까지 한다. 넷플릭스에서
  노트북이 널리 배포돼 있다. 이는 장단이 있는 흥미로운 접근이다. 프로덕션화된 노트북은 데이터
  과학자가 자기 작업을 훨씬 빨리 프로덕션에 넣게 해 주지만, 그것은 본질적으로 표준 이하의 프로덕션
  형태이기도 하다. 대안은 ML과 데이터 엔지니어가 노트북을 프로덕션 용도로 변환하는 것인데 이는 이
  팀들에 상당한 부담을 지운다. 이 접근들의 혼합이 이상적일 수 있다 — "가벼운" 프로덕션에는 노트북을,
  고가치 프로젝트에는 완전한 프로덕션화 프로세스를 쓰는 것이다** (9장, p.358).[^reis2022]
- 자격증명이 새는 자리 — **노트북과 데이터 과학 코드에서 잘못 다뤄진 자격증명은 주요 보안 위험이다.
  우리는 이 영역에서 자격증명이 잘못 다뤄지는 것을 끊임없이 본다. 자격증명을 코드에 직접 심는 것이
  흔하며, 거기서 그것은 흔히 버전 관리 저장소로 새어 든다. 자격증명은 메시지와 이메일로 자주
  돌아다니기도 한다** (9장, p.357).[^reis2022]
  - 처방 — **우리는 데이터 엔지니어가 데이터 과학 보안 실무를 감사하고 개선을 위해 협업할 것을
    권장한다. 데이터 과학자는 대안이 주어지면 이 대화에 매우 수용적이다. 데이터 엔지니어는 자격증명
    취급의 표준을 세워야 한다. 자격증명은 결코 코드에 심어져서는 안 되며, 이상적으로 데이터 과학자는
    자격증명 관리자나 CLI 도구로 접근을 관리한다** (9장, p.357).[^reis2022]
