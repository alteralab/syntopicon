하나의 질문: **이벤트 기반 마이크로서비스는 실제로 어떤 모양으로 지어지고, 무엇을 책임지며,
그 플랫폼의 값은 무엇인가.**

## 이벤트가 업무 로직을 민다는 말

- **이벤트 기반 마이크로서비스(event-driven microservice)는 다른 여느 애플리케이션과 크게 다르지
  않다.** 같은 종류의 컴퓨트·저장·네트워크 자원을 요구하고, 소스 코드를 둘 곳과 빌드·배포 도구와
  건강한 운영을 위한 모니터링·로깅을 똑같이 요구한다. 이벤트 기반 애플리케이션으로서 하는 일은
  **스트림에서 이벤트를 읽고, 그 이벤트에 근거해 일을 하고, 결과를 내놓는 것**이다 — 결과의 형태는
  **새 이벤트이거나 API 호출이거나 다른 형태의 작업**이다 (3장, p.49).[^bellemare2025]
- **"이벤트 기반"이라는 낱말의 뜻을 저자가 비유로 규정한다** (3장, p.49).[^bellemare2025]

  > *Event-driven* means that the events *drive* the business logic, just as water from a
  > stream turns the water wheel of a mill.

- **그래서 일하는 시점이 정해진다** — 이벤트 기반 애플리케이션은 마이크로든 매크로든 **이벤트가
  들어올 때에만 일을 하는 편**이다(타이머 만료도 이벤트다). 그 밖의 시간에는 처리할 새 이벤트가
  올 때까지 **놀고 있다** (3장, p.49).[^bellemare2025]

## 공통 기반 — 오프셋과 컨슈머 그룹

- **컨슈머 마이크로서비스가 스트림에서 이벤트를 읽고, 각 컨슈머는 자기가 읽은 위치를 스스로
  갱신할 책임을 진다.** 그 위치 값이 **오프셋(offset)** 이고, **이벤트 스트림의 처음부터 재어
  현재 이벤트가 어디인가를 나타내는 척도**다. 오프셋이 있어서 **여러 컨슈머가 서로 독립으로 소비하고
  진행 상황을 추적**할 수 있다 (3장, p.50).[^bellemare2025]
- **컨슈머 그룹(consumer group)은 여러 컨슈머를 하나의 논리적 실체로 보게 해 주고, 메시지 소비의
  수평 확장을 가능하게 한다.** 새 컨슈머 인스턴스가 그룹에 들어오면 **활성 인스턴스들 사이에서
  파티션이 대개 자동으로 재분배**되는데 이것을 **리밸런싱(rebalancing)** 이라 부른다. 인스턴스는
  **자기에게 배정된 파티션에서만** 이벤트를 받는다. **상태, 특히 로컬 상태(local state)도 리밸런싱을
  요구할 수 있다** (3장, p.50).[^bellemare2025] 로컬 상태의 리밸런싱 상세는 8장으로 미뤄져 있다.

## 네 모양

- **저자는 "이벤트 기반 마이크로서비스를 무엇이 이루는가"를 정의로 답하지 않고 구현 사례 넷을 먼저
  보이고 거꾸로 거슬러 가는 순서를 택한다** (3장, p.51).[^bellemare2025]
- **이 표는 이 KB가 3장의 네 절을 맞대어 만든 것이고 원문에 이런 표는 없다.** 각 칸의 근거는 아래
  네 절에 있다.

  | 모양 | 무엇으로 짓는가 | 기반에 무엇을 요구하는가 | 저자가 드는 제약 |
  |---|---|---|---|
  | 기본 프로듀서/컨슈머 | 브로커 클라이언트 라이브러리 하나. 업무 로직을 잇는 모든 연산을 개발자가 직접 쓴다 | 이벤트 브로커만 | 폭넓은 언어에서 쓸 수 있으나 손으로 써야 할 것이 가장 많다 |
  | 스트림 처리 프레임워크 | 카프카 스트림즈·플링크·스파크 같은 프레임워크 | **별도의 독립 클러스터**(플링크·스파크)이거나 **특정 이벤트 브로커와의 밀착 구현**(카프카 스트림즈) | 지원 아키텍처에 더 큰 선투자. 언어 지원이 대개 제한된다 |
  | 스트리밍 SQL 질의 | 선언형 질의 한 덩어리 | 그 아래에 튼튼한 하위 수준 API 집합 | **표준화되어 있지 않다.** 고른 프레임워크에 크게 의존한다 |
  | 레거시 애플리케이션 | 고치지 않고 **커넥터(connector)** 로 붙인다 | 커넥터가 도는 자리 | 그 애플리케이션 자체는 바꿀 수 없는 굳은 구조로 둔다 |

## 기본 프로듀서/컨슈머

- **기본 프로듀서/컨슈머(basic producer/consumer)라는 이름 그대로다** — 프로듀서가 이벤트를 내고,
  컨슈머가 이벤트를 소비하며, **업무 로직을 이어 붙이는 모든 연산은 소프트웨어 개발자가 직접
  써야 한다** (3장 §"The Basic Producer/Consumer", p.51).[^bellemare2025]
- 저자가 드는 파이썬 예제는 `input_topic`에서 이벤트를 소비해 **키마다 합을 세고, 값이 1000을
  넘으면 갱신된 합계를 새 이벤트 스트림에 낸다** (3장, pp.51–52).[^bellemare2025]
- **상태 저장소는 그 예제에서 메모리 사전 하나지만 저자가 곧바로 경계를 단다** — 실제로는 그것
  말고 다른 것을 쓰고 싶을 것이고, **관계형 데이터베이스나 완전 관리형 키-값 저장소나 다른 내구적
  상태 저장소로 갈아 끼울 수 있다.** 쓰임새에 가장 맞는 상태 저장소를 고르라는 것이 처방이다 —
  어떤 것은 고성능 키-값 저장소가, 다른 것은 관계형·그래프·문서 저장소가 맞는다 (3장,
  pp.52–53).[^bellemare2025]
- **이 단순한 예제가 보이는 것이 이 모양의 골격이다** — 저자는 이것이 **대다수 이벤트 기반
  마이크로서비스에 공통인 핵심 구성 요소**를 보여 준다고 적는다. **이벤트 스트림 컨슈머, 프로듀서,
  상태 저장소, 그리고 입력 스트림에 새 이벤트가 도착하는 것이 미는 연속 처리 루프** 넷이고,
  **업무 로직은 그 처리 루프 안에 박혀 있다** (3장, p.53).[^bellemare2025]
- **같은 책 9장이 이 모양에 빠져 있는 부품 하나를 못박는다** — **이벤트 스케줄링은 많은 스트림 처리
  프레임워크의 기능이지만 기본 컨슈머 구현에는 대체로 없고, 자기 마이크로서비스 구현에 그것이
  필요한지 판별해야 한다.** 판별 기준은 **이벤트가 소비되고 처리되는 순서가 업무 로직에
  중요한가**다 (9장, p.204).[^bellemare2025]
  - **곧 여러 입력 스트림에서 다음에 처리할 이벤트를 시간 순서로 고르는 일이 이 모양에서는 직접
    써야 하는 코드**이고, 아래 [스트림 처리 프레임워크](#스트림-처리-프레임워크)에서는 프레임워크가
    준다. 위 [네 모양](#네-모양)의 가름 축에 이 항목이 없는데, **저자가 3장에서 이 차이를 들지
    않고 9장에 가서야 적기 때문이다.** 이벤트 스케줄링의 규정과 그것이 재처리의 재현 가능성과
    맞물리는 자리는 [결정적 스트림 처리](../concepts/deterministic-stream-processing.md)에 있다.

## 스트림 처리 프레임워크

- **스트림 처리 이벤트 기반 마이크로서비스는 스트림 처리 프레임워크로 짓는다.** 저자가 드는 유력
  후보가 **아파치 카프카 스트림즈·아파치 플링크·아파치 스파크**다 (3장 §"The Stream-Processing
  Event-Driven Microservice", p.53).[^bellemare2025]
  - 버전 조건: 2025년 저술 시점의 채택 지형이다. 저자는 **초판(2020)에서 들었던 아파치 스톰과
    아파치 사자(Samza)는 이제 그만큼 흔하지 않다**고 적어 5년 사이의 이동을 직접 채점한다.
- **프레임워크가 주는 것 둘** — 이벤트 브로커와 **더 밀착된 통합**을 주어 직접 다뤄야 할 부수 작업을
  줄이고, **더 높은 수준의 구성물로 더 강력한 계산**을 준다. 저자가 드는 예가 **스트림과 구체화된
  테이블을 아주 적은 수고로 조인**하게 해 주는 것이다 (3장, p.53).[^bellemare2025]
- **기본 프로듀서/컨슈머와 가르는 핵심 차이를 저자가 못 박는다** — 스트림 처리기는 **별도의 독립
  클러스터를 *요구*하거나**(예: 플링크·스파크) **특정 이벤트 브로커와의 밀착 구현을 요구한다**
  (예: 카프카 스트림즈) (3장, p.53).[^bellemare2025]
  - **그 요구가 갈리는 방식까지 적힌다** — 플링크와 스파크(그리고 그와 같은 것들)는 **자체 독점
    처리 클러스터**를 써서 상태·확장·내구성·데이터의 내부 라우팅을 관리한다. 반면 **카프카
    스트림즈는 카프카 클러스터만으로** 애플리케이션 상태의 내구적 저장, 토픽 재파티셔닝, 애플리케이션
    확장 기능을 얻는다 (3장, p.53).[^bellemare2025]
- **프로그래밍 양식도 갈린다** — 스트림 처리 프레임워크는 **맵리듀스 프로그래밍(함수형 프로그래밍의
  한 형태)** 을 쓰는 편이고, `map`·`reduce`·`aggregate`·`join`·`filter` 같은 함수로 데이터에 대한
  변환을 **선언**한다 (3장, p.54).[^bellemare2025]
- **저자가 드는 플링크 예제에서 넘어가는 대목 하나가 4장으로 이어진다** — 조인 결과를 합치는 함수
  자리가 **출력 이벤트 스키마를 선언하는 자리**이고, 저자는 그것이 **4장에서 다루는 데이터 계약의
  일부**라고 적는다 (3장, p.55).[^bellemare2025]
- **대가가 명시된다** — 스트리밍 프레임워크는 매우 강력한 능력을 주지만 **지원 아키텍처에 대개 더
  큰 선투자를 요구**하고, **언어 지원이 대개 제한된다**(파이썬과 JVM이 가장 흔하다). 다만 초판
  이후 다른 언어 지원을 더한 것도 있다 (3장, p.55).[^bellemare2025]

## 스트리밍 SQL 질의

- **저자가 절을 물음으로 연다** — "내 마이크로서비스는 사실 그냥 SQL 질의여야 하는 것 아닌가"
  (3장 §"The Streaming SQL Query", p.55).[^bellemare2025]
- **데이터베이스 세계에서 SQL을 인기 있게 만든 바로 그것이 스트리밍 세계에서도 통한다** — **선언적
  성질** 때문이다. 원하는 결과를 선언할 뿐 **어떻게 얻을지는 지정하지 않고**, 그것은 아래에 있는
  처리 엔진의 일이다 (3장, p.55).[^bellemare2025]
- **결과물의 성질은 다른 마이크로서비스와 같다** — 이런 스트리밍 SQL 질의는 **업무 로직을 계속
  실행하는 장기 실행 프로세스**가 되고, **무기한 돌면서 필요에 따라 확장·축소**한다 (3장,
  p.56).[^bellemare2025]
- **가장 큰 경계가 표준의 부재다** — **스트리밍 SQL은 표준화되어 있지 않고**, 마이크로서비스를 지을
  때 고른 프레임워크에 크게 의존한다. 그리고 **장난감 예제를 넘어서려면 그 아래에 튼튼한 하위 수준
  API 집합**이 필요하다 (3장, p.56).[^bellemare2025]
  - 저자가 예로 드는 플링크 프로젝트의 API 층이 넷이고 **각 층이 아래 층에 의존한다**. 이 표는
    그림 3-3을 렌더해 눈으로 읽은 것이고 원문 도판의 라벨을 그대로 옮겼다 (3장,
    p.56).[^bellemare2025]

    | 층 (위에서 아래로) | 원문 라벨 |
    |---|---|
    | SQL | High-level language |
    | Table API | Declarative DSL |
    | DataStream | Core APIs |
    | Stateful stream processing | Low-level building block (streams, state, [event] time) |

  - 버전 조건: 2025년 저술 시점의 아파치 플링크 API 층 구성이다. 저자가 출처로 적는 것은 아파치
    플링크 문서다.
- **판정은 "찾아보라"에 가깝다** — 스트리밍 SQL을 쓸 기회를 계속 살피라는 것이고, **시간과 수고를
  크게 아껴 줄 수 있다**는 것이다. 다만 **갈래와 종류가 여럿이라 프레임워크마다 무엇이 지원되고
  무엇이 안 되는지는 직접 확인해야 한다** (3장, p.56).[^bellemare2025]

## 레거시 애플리케이션과 커넥터

- **레거시 애플리케이션(legacy application)은 애초에 이벤트 기반 처리를 염두에 두고 쓰이지 않은
  것**이다. 대개 **낡았지만 중요한** 체계로 결정적인 업무 기능을 맡고 있으나 **더는 활발히 개발되지
  않는다.** 변경은 드물고 꼭 필요할 때만 이뤄진다. 그리고 **중요한 업무 데이터의 문지기인 경우가
  잦다** — 그 체계의 데이터베이스나 파일 저장소 안에 갇혀 있는 것이다 (3장 §"The Legacy
  Application", p.57).[^bellemare2025]
- **저자의 처방은 고치지 말고 붙이라는 것이다** — 레거시 애플리케이션은 **바꾸기 어려운 굳은
  구조**지만, **커넥터(connector)** 를 써서 전체 이벤트 기반 아키텍처 안으로 통합할 수는 있다
  (3장, p.57).[^bellemare2025]
- **커넥터는 양방향이다** — 원본 체계나 데이터베이스에서 이벤트를 읽어 **데이터를 이벤트로 바꿔
  이벤트 스트림에 쓰고**, 반대로 스트림에서 이벤트를 읽어 **알맞은 형식으로 바꿔 레거시 체계의
  API나 데이터베이스에 쓴다.** 그래서 **전체 체계를 네이티브 이벤트 기반 아키텍처로 다시 설계하지
  않고도** 기존 애플리케이션을 통합할 수 있다 (3장, p.57).[^bellemare2025]
  - 그림 3-4를 렌더해 눈으로 확인한 것이 이 양방향이다 — 위쪽 "Producing to stream"에서
    서비스와 그 데이터베이스가 커넥터에 데이터를 읽히고 커넥터가 이벤트 스트림에 쓰며, 아래쪽
    "Consuming from stream"에서 커넥터가 스트림을 읽어 서비스의 데이터베이스에 쓴다.
- **값어치는 시작 비용에 있다** — 커넥터는 **아키텍처 전체를 다시 발명하지 않고도 이벤트 스트림을
  시작**하게 해 주고, 데이터를 스트림에 넣기 쉽게 만들어 **이벤트 기반 마이크로서비스에서 값을
  빨리 얻게** 해 준다 (3장, p.57).[^bellemare2025] 커넥터의 상세는 6장으로 미뤄져 있다.

## 어느 모양이 어디에 맞는가 — 뒤쪽 세 장의 답

**위 [네 모양](#네-모양)이 무엇으로 짓는가를 가른다면, 같은 책 11~13장이 각 모양이 어디에
맞는가를 답한다.** 세 장이 답하는 것은 셋뿐이다 — 기본 프로듀서/컨슈머(11장), 중량
프레임워크(12장), 경량 프레임워크(13장). 위 표의 둘째 칸이 뒤에서 **중량과 경량 둘로 갈린다.**

- **기본 프로듀서/컨슈머가 잘 듣는 자리 넷을 11장이 든다** (11장 §"Where Do BPCs Work Well?",
  pp.248–252):[^bellemare2025] **사이드카로 레거시 체계에 붙일 때** · **순서에 기대지 않는 상태
  있는 로직**(저자가 게이팅 패턴(gating pattern)이라 부르는 것) · **아래의 데이터 저장소가 업무
  로직 대부분을 할 때** · **처리와 저장소를 따로 확장하고 싶을 때**.
  - **한계도 같은 장이 못 박는다** — **스트림 사이의 관계를 다루는 능력이 없어** 조인하려면
    전부 데이터베이스에 적재해 거기서 조인해야 하고, **상태 구체화·이벤트 스케줄링·타임스탬프
    기반 판단** 같은 기성 기제가 없다 (11장, p.252).[^bellemare2025]
- **중량 프레임워크의 맺음이 그 대가를 적는다** — 중량은 **중앙 집중 자원 클러스터로 돌아** 추가
  운영 부담과 모니터링과 조율을 요구하고, **일부 상태 있는 이벤트 기반 마이크로서비스 패턴의
  요구에는 충분하지 않을 수 있다**. 2025년 저술 시점 기준 최근의 배포 모델 혁신이 **쿠버네티스 같은 컨테이너 관리
  해법과의 통합**을 개선해 **완전 독립 마이크로서비스에 가까운 세분도의 배포**를 가능하게 했다
  (12장 §"Summary", p.276).[^bellemare2025]
- **경량 프레임워크의 맺음이 그 자리를 적는다** — 경량은 **자기 독립 자원 클러스터를 요구하지
  않고** 확장·셔플링·데이터 내구성을 **이벤트 브로커와 컨테이너 관리 체계에 기댄다** (13장
  §"Summary", p.284).[^bellemare2025]
- **세 모양의 런타임 내부는 이 페이지가 갖지 않는다** — 클러스터의 두 역할, 체크포인트와
  체인지로그, 드라이버 모드와 클러스터 모드, 확장의 두 길, 멀티테넌시, 그리고 프레임워크를 고르는
  기준은 [스트림 처리 프레임워크의 세 모양](stream-processing-framework-shapes.md)에 있다.
  **이 페이지는 "어느 모양인가"의 주인으로 남는다.**

## 스트리밍 SQL이라는 모양

**위 [스트리밍 SQL 질의](#스트리밍-sql-질의)가 3장이 이 모양을 소개하는 자리라면, 14장이 그 모양의
개념 알맹이를 채운다.** 문법과 제품은 이 소스 메타가 L3로 배치한 층이라 여기 담지 않는다 — 담는
것은 **이 모양이 무엇으로 이뤄지고 어디에 놓이는가**다.

- **바탕이 되는 규정** — **스트리밍 SQL은 마이크로서비스 같은 질의를 짓는 선언적 기제**이고,
  **어떤 엔진이나 프레임워크를 고르든 원리는 대체로 같다** (14장, p.285).[^bellemare2025]
  - **표준이 없다는 것을 저자가 다시 못 박는다** — **지금 확정된 스트리밍 SQL 표준은 없다
    (ANSI든 다른 것이든).** 프레임워크마다 문법과 의미가 달라서 스트리밍 SQL을 말할 때는
    **일반적인 방언(dialects)** 을 말하는 것이다 (14장, p.285).[^bellemare2025]
  - 버전 조건: 2025년 저술 시점의 제품 지형이다. 이 장이 다루는 실물은 **아파치 플링크의 Flink
    SQL과 아파치 스파크의 Spark SQL** 둘이고, **둘 다 자기 하위 수준 API 위에 얹은 층**이다
    (14장, p.285).[^bellemare2025]
- **연속 질의(continuous query)가 이 모양을 다른 SQL과 가른다** (14장, p.286):[^bellemare2025]

  > Streaming SQL queries run indefinitely on the stream of data, applying the query logic to
  > each event as it's received. In contrast, a query on a conventional relational database
  > operates on the data that was present at the time it was executed.

  - 곧 **관습적 질의는 유계 데이터셋을 다 훑으면 끝나지만 스트리밍 질의는 끝나지 않는다.**
    유계와 무계의 가름은 [결정적 스트림 처리](../concepts/deterministic-stream-processing.md)에 있다.
- **스트림을 테이블로 선언하는 것이 첫 단계다** — **스트림을 테이블로 보는 것(streams-as-tables)이
  기본 데이터 추상**이고, 질의를 쓰기 전에 **스트리밍 데이터 위에 테이블 정의를 선언**해야 한다
  (14장, pp.286–287).[^bellemare2025] 이 변환의 기제는
  [스트림-테이블 이중성](stream-table-duality.md)에 있다.
  - **프레임워크에서 볼 수 있는 테이블이 셋**이다 (14장, pp.286–287). 원문 정의 목록을 표로 모은
    것은 이 KB다.[^bellemare2025]

    | 테이블 | 기본 키 | 무엇을 하는가 |
    |---|---|---|
    | **업서트 테이블**(upsert tables) | 요구한다 | 각 이벤트가 업서트이거나 삭제다. **같은 키의 새 레코드가 옛 레코드를 덮어쓴다.** 2장의 구체화된 테이블과 동일하다 |
    | **추가 전용 테이블**(append-only tables) | 요구하지 않는다 | 모든 레코드를 삽입해 **이전 데이터의 완전한 이력을 유지**한다. 모든 레코드가 불변이고 삭제할 수 없어 **스트림을 받치는 추가 전용 로그와 아주 비슷**하다 |
    | **철회 테이블**(retraction tables) | 행 전체가 키다 | 삽입·갱신·삭제를 지원하되 **행 전체가 키 노릇**을 한다. 조금 더 앞선 형이라 **모든 프레임워크에 있지는 않고**, 주로 **상류 계산의 결과를 반영**한다 |

  - **확인할 것 하나를 곁상자가 적는다** — **최소한 추가 전용과 업서트 둘 다 지원하는지 문서를
    확인하라. 추가 전용만 지원하는 프레임워크도 있고 그러면 처리 선택지가 크게 좁아진다** (14장,
    p.287).[^bellemare2025]
- **코드를 어디서 돌릴 것인가가 넷으로 갈린다.** 저자는 이것을 문법이 아니라 **실행 방식**의
  문제로 세운다 (14장 §"Executing Streaming SQL Code", pp.290–293). 아래 표는 네 절을 이 KB가
  모은 것이고 원문에 이런 표는 없다.[^bellemare2025]

  | 실행 자리 | 무엇인가 | 저자가 두는 자리 |
  |---|---|---|
  | **명령줄 인터페이스**(CLI) | 프롬프트에 SQL을 쓰거나 붙여 넣는다 | **시험과 로컬 개발이 가장 흔한 쓰임**이다. **CLI를 끝내면 잡도 끝나므로** 프로덕션에는 다른 방식이 낫다 |
  | **애플리케이션 안에 심기** | 네이티브 애플리케이션 코드에 SQL 질의를 박는다 | **프레임워크가 지원하는 언어에 매이되**, 업무 로직 대부분을 내장 SQL로 짜므로 **코드가 훨씬 적다.** **마이크로서비스 배포 파이프라인과 시험·확장·모니터링에 잘 맞물린다** |
  | **노트북**(notebook) | 실행 가능한 코드와 서식 있는 글과 시각화를 섞는 브라우저 기반 도구 | **탐색과 분석에 가장 좋다.** **프로덕션 쓰임에는 전용 마이크로서비스를 만들고 노트북 코드를 옮기라**는 것이 처방이다 |
  | **SQL 게이트웨이**(SQL gateway) | 여러 클라이언트가 SQL 코드를 동시에 원격으로 실행하게 하는 서비스. 제출된 잡이 **각자의 세션 안에서** 돌고 처리 클러스터에 기댄다 | **서비스를 짓는 애플리케이션을 만드는 간접비를 없앤다.** 이상적 후보는 **시간이 지나도 바뀌지 않는 단순한 질의**이고, 관계형 데이터를 비정규화하는 조이너 서비스가 그 예다 |

  - 노트북의 이득 다섯은 **대화형 개발 · 시각화와 문서화 · 컨테이너 같은 격리 · 다중 언어 지원 ·
    공유 가능성**이고, 단점 넷은 **버전 관리의 복잡함 · 성능 한계 · 시험의 한계 · 승격과 롤백의
    한계**다 (14장, pp.291–292).[^bellemare2025] 버전 조건: 2025년 저술 시점의 도구 이름이다.
    저자가 드는 무료 오픈 소스 노트북이 **아파치 제플린과 주피터**이고, 노트북과 처리 엔진을
    잇는 것이 **인터프리터(interpreter)** 다.
- **다섯째 자리가 사이드카다** — **SQL은 마이크로서비스 안에서는 하기 너무 어려운 일을 맡는
  사이드카 능력을 줄 수 있다.** **많은 기본 프로듀서/컨슈머 프레임워크에 조인과 복잡한 집계를 할
  능력이 없는데 SQL이 그 틈을 쉽게 메운다** (14장 §"SQL as a Sidecar", pp.293–294).[^bellemare2025]
  - **조인·윈도잉·집계·복잡한 이벤트 기반 상태 기계를 SQL 엔진에 떠넘기고 남은 업무 로직은
    마이크로서비스 안에 둔다.** 출력 스트림은 **그 하류 마이크로서비스만 쓰라고 지어진 사적
    스트림**이고, **SQL 조이너와 마이크로서비스가 하나의 경계 컨텍스트 안에 있어** 그 스트림과
    조이너와 서비스의 내부 경계가 **바깥 세계에는 사적으로 남는다** (14장,
    p.294).[^bellemare2025]
  - **생명 주기를 묶으라는 조항이 붙는다** — **마이크로서비스를 끝낼 때 SQL 잡도 함께 끝나게 해
    좀비 프로세스가 남지 않게 하라. SQL 질의와 마이크로서비스 구성 요소를 생명 주기 내내 단단히
    결합해 두는 것이 중요하다** (14장, p.294).[^bellemare2025] 사이드카라는 낱말이 이 KB에서
    갖는 네 용법의 대조는
    [API 게이트웨이와 서비스 메시](../concepts/api-gateway-and-service-mesh.md)에 있다.
- **선언형이 막히는 자리의 탈출구가 UDF다** — **사용자 정의 함수(user-defined function, UDF)는
  SQL 문법으로는 쉽게 되지 않는 연산을 주는 커스텀 함수**이고 **아래 SQL 프레임워크의 네이티브
  언어로 쓴다** (14장 §"User-Defined Function Calls", p.294).[^bellemare2025]
  - **들어오고 나가는 레코드의 관계로 셋으로 갈린다** — **레코드 하나를 넣어 하나를 받는 것** ·
    **여러 레코드를 넣어 집계된 하나를 받는 것** · **하나를 넣어 여러 개를 받는 것** (14장,
    p.295).[^bellemare2025]
  - **UDF로 값을 고치는 데 그치지 않고 집계와 복잡한 상태 기계를 지을 수 있으며, 외부 시스템을
    호출해 제3자 서비스나 생성형 AI 모델 같은 것과 통합할 수도 있다** (14장,
    p.295).[^bellemare2025] **곧 UDF가 이 모양의 선언성을 깨고 나가는 문**이고, 외부 호출이
    결정성에 거는 값은 [결정적 스트림 처리](../concepts/deterministic-stream-processing.md)에 있다.

## 넷 밖의 다섯째 — 함수로 짓기

- **15장이 이 분류에 칸을 하나 더 붙인다** — **FaaS(functions as a service)는 마이크로서비스를 짓는
  또 하나의 길**이고 **비교적 단순한 것부터 적당히 복잡한 것까지의 이벤트 기반 해법을 구현하는
  수단**이다 (15장, p.297).[^bellemare2025]
  - **3장의 넷과 나란히 놓이지 않는다** — 3장은 네 모양을 한자리에서 견주는데 **15장의 FaaS는
    그 목록에 들어가지 않고 별도의 장으로 온다.** 저자가 그것을 **기본 프로듀서/컨슈머의 변형**으로
    소개하기 때문이다(정기적으로 멈추는 기본 프로듀서/컨슈머). **이 읽기는 이 KB의 것이고 저자가
    "다섯째 모양"이라고 적지는 않는다.** #hypothesis
  - 그 모양의 전문은 [FaaS로 짓는 이벤트 기반 마이크로서비스](faas-event-driven-microservices.md)가
    갖는다 — 촉발 다섯, 콜드 스타트와 웜 스타트, 로컬 상태 금지, 함수가 함수를 부르는 두 패턴,
    그리고 지속 함수 오케스트레이터.

## 토폴로지 — 두 층위

- **토폴로지(topology)라는 낱말이 두 층위에 쓰인다고 저자가 먼저 경고한다** — 하나는 **개별
  마이크로서비스의 처리 로직을 이루는 논리적 단계들**을 서술할 때이고, 다른 하나는 한 단 위에서
  **개별 마이크로서비스와 이벤트 스트림과 요청-응답 API 사이의 그래프 같은 관계**를 가리킬 때다
  (3장 §"Topologies and Event-Driven Microservices", p.58).[^bellemare2025]
- **마이크로서비스 토폴로지의 규정** (3장, p.58).[^bellemare2025]

  > A microservice topology is the event-driven business logic internal to a single
  > microservice. It defines the data-driven operations that the service performs on
  > events, including transformation, storage, and the production of new events.

- **업무 토폴로지의 규정** (3장, p.58).[^bellemare2025]

  > A business topology is like a microservice topology, but zoomed out one level
  > further. It is the set of microservices, event streams, and APIs that fulfill complex
  > business functions.

  - **업무 토폴로지는 임의의 묶음**이다 — 한 팀이나 부서가 소유한 서비스들일 수도 있고, 복잡한
    업무 기능의 상위 집합을 채우는 서비스들일 수도 있다 (3장, p.58).[^bellemare2025]
  - **1장의 소통 구조와 이어진다** — 저자는 **업무 소통 구조(business communication structures)가
    업무 토폴로지를 구성한다**고 적고, **마이크로서비스가 업무 경계 컨텍스트를 구현하며 이벤트
    스트림이 컨텍스트를 가로지르는 도메인 데이터를 나누는 데이터 소통 기제를 제공한다**고 잇는다
    (3장, p.58).[^bellemare2025] 소통 구조 셋의 전문은
    [소통 구조 셋](../concepts/communication-structures.md)에 있다.
- **둘을 가르는 한 문장이 곁글로 박혀 있다** (3장, p.59).[^bellemare2025]

  > A *microservice topology* details the inner workings of a single microservice. A
  > *business topology*, on the other hand, details the relationships *between* services.

- **업무 토폴로지 도판이 이 KB에 더하는 관찰 하나가 있다** — 그림 3-6을 렌더해 보면 본문이 적는
  마이크로서비스 셋과 이벤트 스트림 셋 말고 **모놀리스(Monolith) 상자 하나가 더 있고, 그것이
  마이크로서비스 2의 REST API와 요청·응답으로 이어져 있다.** 본문은 그 모놀리스를 언급하지
  않는다 — 도판만이 보이는 배치다. 곧 **이벤트로 이어진 그래프 안에 요청-응답 변이 하나가 섞여
  있는 그림**이고, 저자가 1장에서 적는 "섞어 쓰는 것이 표준"이라는 판정과 같은 방향이다.

## 1장이 먼저 세운 규정 — 책임 여섯과 이득 일곱

3장이 이 페이지의 본체를 주지만 **1장이 같은 것을 한 번 더 짧게 세운다.** 두 목록의 수가 다르므로
따로 적는다.

- **계보를 먼저 세운다** — 마이크로서비스와 마이크로서비스식 아키텍처는 **여러 해 동안 여러 형태와
  여러 이름으로 있어 왔다**. **서비스 지향 아키텍처(SOA)**는 흔히 **여러 마이크로서비스가 서로 직접
  동기적으로 통신하는 것**으로 이뤄지고, **메시지 전달 아키텍처**는 **소비되는 이벤트를 써서 비동기로
  통신**한다 (1장 §"What Are Event-Driven Microservices?", p.3).[^bellemare2025]
  - **그래서 무엇이 새로운가의 답이 기술이 아니라 요구다** — **이벤트 기반 아키텍처는 분명 새롭지
    않되**, **큰 데이터 집합을 규모에서 실시간으로 다뤄야 하는 필요가 새롭고** 그것이 **옛 아키텍처
    양식으로부터의 변화를 필요하게 만든다** (1장, p.3).[^bellemare2025]
  - **이벤트가 소비될 때 파괴되지 않는다는 것이 메시지 전달과 갈리는 자리**이고, 저자는 그 구분이
    **이 책이 다루는 정말 강력한 패턴들을 가능하게 하므로 중요하다**고 적는다 (1장,
    p.4).[^bellemare2025] 세 양식의 전문은
    [이벤트 스트림과 이벤트 브로커](event-streams-and-brokers.md)에 있다.
- **규정이 한 문장이다** (1장 §"What Are Event-Driven Microservices?", p.4):[^bellemare2025]

  > In its simplest form, an event-driven microservice is a purpose-built service that consumes
  > and/or produces events.

  - 저자가 같은 절 끝에서 한 번 더 조인다 (1장, p.5):[^bellemare2025]

    > an event-driven microservice, by definition, is driven by an event loop of consuming and/or
    > producing events

- **작다는 것의 기준이 여기서 두 겹으로 적힌다** — **작다의 정의는 다양할 수 있으나 서비스는
  (개념적으로) 한 사람의 머리 안에 들어가야 하고**, 소유 팀은 **비교적 작은 팀, 혹은 피자 두 판이면
  먹일 수 있는 팀**이어야 한다. 저자가 뒤엣것을 **아마존의 마이크로서비스 채택이 유행시킨 기준**이라
  적는다 (1장, p.4).[^bellemare2025] 아래 [얼마나 작아야 하는가](#얼마나-작아야-하는가)가 3장의 더
  긴 답을 갖고, 같은 규칙의 다른 출처는 [콘웨이의 법칙](../concepts/conways-law.md)에 있다.
- **마이크로서비스가 전적으로 책임지는 것이 여섯이다** (1장, p.4).[^bellemare2025]
  - **고른 입력 스트림에서 이벤트를 소비하기.**
  - **고른 출력 스트림으로 데이터를 생산하기.**
  - **자기 상태 저장소에 자기 상태를 저장하고 관리하기.**
  - **자기 업무 로직에 따라 이벤트를 처리하고 저장하고 그에 반응하기.**
  - **확장성 유지** — **처리 능력과 상태 저장 양쪽에서**.
  - **모니터링 솔루션과의 통합.**
  - **아래 3장의 책임 여덟이 이 여섯의 상위집합이 아니다.** 여섯 가운데 "저장하고 관리하기"와
    "처리하고 반응하기"가 여덟에서는 더 잘게 갈리고, 반대로 여덟에만 있는 **스트림당 단일 기록자
    원칙**은 1장에 없다. 두 목록이 같은 것의 두 판이라는 것은 이 KB의 읽기다. `#hypothesis`
- **생산자와 소비자라는 이름이 여기서 붙는다** — **소비자 마이크로서비스**는 입력 스트림 하나
  이상에서 이벤트를 소비해 처리하고, **생산자 마이크로서비스**는 다른 서비스가 소비하도록 이벤트
  스트림에 이벤트를 생산한다. **이벤트 기반 마이크로서비스가 둘 다인 것이 흔하다** (1장,
  p.5).[^bellemare2025]
- **주된 이득으로 저자가 드는 것이 일곱**이다 (1장, pp.5–6).[^bellemare2025]

  | 이득 | 저자가 적는 것 |
  |---|---|
  | **기술적 유연성** | 서비스가 **가장 알맞은 언어와 기술**을 쓴다. **선구적 기술로 쉽게 프로토타이핑**하는 것도 가능해진다 |
  | **업무 요구의 유연성** | **잘게 나뉜 마이크로서비스의 소유권은 재편하기 쉽다.** 큰 서비스에 견줘 **팀 사이 의존이 적고**, 조직이 **데이터 접근의 장벽에 막혔을 업무 요구 변화에 더 빨리 반응**할 수 있다 |
  | **느슨한 결합** | 이벤트 기반 마이크로서비스는 **특정 구현 API가 아니라 도메인 데이터에 결합**한다. **스키마로 데이터 변경 관리를 크게 개선**할 수 있다 |
  | **지속적 통합과 전달** | **작고 모듈적인 마이크로서비스는 내보내기 쉽고 필요하면 되돌리기도 쉽다** |
  | **높은 시험 가능성** | 마이크로서비스는 **큰 모놀리스보다 의존이 적은 편이라 필요한 테스트 엔드포인트를 모의로 만들고 적절한 코드 커버리지를 확보하기 쉽다** |
  | **확장성** | **개별 서비스를 필요에 따라 늘리고 줄인다** |
  | **세분도** | **서비스가 경계 컨텍스트에 깔끔히 대응**하고 **업무 요구가 바뀌면 쉽게 다시 쓸 수 있다** |

  - **다섯째 이득이 20장의 출발 전제와 같은 것**이다 —
    [이벤트 기반 마이크로서비스의 테스트](testing-event-driven-microservices.md)가 그 전제를 다시
    편다.

## 마이크로서비스가 지는 책임 여덟

- **모든 마이크로서비스가 어떻게 짓든 어떤 기술을 쓰든 공통으로 지는 책임의 집합이 있고, 자기
  서비스를 지을 때 그것을 셈에 넣어야 한다** (3장 §"Event-Driven Microservice Responsibilities",
  p.59).[^bellemare2025]
- **여덟 항목의 이름과 각 규정을 원문 정의 목록에서 그대로 옮겼고 표 형식은 이 KB가 만든 것이다**
  (3장, pp.59–61).[^bellemare2025]

  | 책임 | 저자가 적는 것 |
  |---|---|
  | **서비스 경계와 범위** (service boundaries and scope) | 잘 정의된 경계 집합을 강제할 책임. 이 애플리케이션이 무엇을 책임지고 **무엇을 책임지지 않는가**. 뒤쪽이 더 중요해지는 것은 여러 마이크로서비스가 함께 복잡한 워크플로를 채울 때다. **마이크로서비스를 경계 컨텍스트에 가능한 한 깔끔하게 대응**시키면 짐작과 모호함을 크게 피할 수 있다 |
  | **확장성** (scalability) | 자기 확장성을 보장할 책임. **수평(인스턴스를 늘리는 것)이든 수직(더 강한 인스턴스)이든** 확장되도록 쓰여야 한다. 확장을 기본으로 제공하는 프레임워크가 훨씬 매력적인 편이다. 아래의 처리 능력은 서비스마다 따로 대 줄 수도 있고 **공유 컴퓨트 자원 풀**로 댈 수도 있다 |
  | **상태 관리** (state management) | 자기 데이터 저장소에 대한 **생성·읽기·갱신·삭제의 유일한 책임자**. 상태를 바꾸는 연산은 전부 그 통제 경계 안에 남는다. 디스크가 차거나 애플리케이션 변경을 시험하지 못한 것 같은 상태 저장소의 문제도 그 서비스의 문제 공간이다 |
  | **스트림 진행 상황의 추적** (keep track of stream progress) | 입력 이벤트 스트림을 어디까지 읽었는지 스스로 추적해야 한다. 예컨대 아파치 카프카는 **논리적 마이크로서비스마다 하나씩인 컨슈머 그룹**으로 이 진행을 추적한다. 컨슈머 그룹은 다른 주요 이벤트 브로커도 쓰지만, 컨슈머가 **자기 오프셋을 손으로 조작**하거나(레코드를 다시 재생하려는 것처럼) **자기 데이터 저장소 같은 다른 곳에 저장**하기를 고를 수도 있다 |
  | **장애 복구** (failure recovery) | 장애 뒤에 스스로 건강한 상태로 돌아올 수 있음을 보장할 책임. 저장된 상태를 스트림 입력 진행 상황과의 관계 속에서 고려해야 한다. **크래시가 나면 소비 서비스는 마지막으로 알려진 좋은 오프셋에서 재개**하는데, 그것이 **중복 처리와 중복 상태 갱신**을 뜻할 수 있다. 데이터베이스 스냅샷, 이벤트 스트림으로부터의 복원, 데이터 재생이 흔히 쓰이는 보존·복원 기법이다 |
  | **스트림당 단일 기록자 원칙** (the single writer per stream principle) | **각 이벤트 스트림에는 생산하는 마이크로서비스가 하나, 오직 하나만 있다.** 그 마이크로서비스가 그 스트림에 낸 각 이벤트의 소유자다. 이것이 **어떤 이벤트에 대해서도 권위 있는 진실의 원천을 늘 알 수 있게** 해 주고, 체계 전체를 가로지르는 **데이터 리니지 추적**을 가능하게 한다. 소유권과 쓰기 경계의 강제에는 접근 통제 기제를 써야 한다 |
  | **이벤트 키와 파티셔닝** (event keys and partitioning) | **출력 레코드의 기본 키를 고를 책임**과 **그 레코드를 어느 파티션으로 보낼지 정할 책임**. 같은 키의 레코드는 대개 같은 파티션으로 가지만 라운드 로빈·무작위·커스텀 같은 다른 전략을 고를 수도 있다. **결국 어느 파티션에 쓸지를 정하는 것은 당신의 마이크로서비스다** |
  | **이벤트 스키마와 데이터 계약** (event schemas and data contracts) | 이벤트의 데이터 내용을 스키마로 정의해 **소비자가 분명한 필드 이름·타입·기본값을 갖게** 할 것. 저자가 드는 물음이 "`product_id`를 문자열로 쓰는가 정수로 쓰는가"다. 지금으로서는 **잘 정의된 Avro·Protobuf·JSON 스키마**로 레코드를 쓸 계획을 세우라는 것이 처방이다 |

- **단일 기록자 원칙이 이 목록에서 가장 규범적인 항목이다.** 그것이 무엇을 사는지를 저자가 함께
  적는다 — **권위 있는 진실의 원천을 늘 알 수 있게 되는 것**과 **데이터 리니지의 추적 가능성**
  둘이다 (3장, p.60).[^bellemare2025] 이 원칙이 2장의 "이벤트 브로커가 단일 진실 원천"이라는
  주장과 이어지는 자리는 [기록 시스템과 파생 데이터](system-of-record-and-derived-data.md)에 있다.

## 얼마나 작아야 하는가

- **저자가 먼저 오답을 지운다** — 마이크로서비스 아키텍처의 목표는 **가능한 한 많이 만드는 것이
  아니다.** 서비스 수가 가장 많다고 상을 받지 않고 그 경험이 보람 있지도 않을 것이며, 저자는
  **"마이크로서비스 1,000개를 만들었고 모든 것이 끔찍했다"는 블로그를 쓰게 될 것**이라고 적는다
  (3장 §"How Small Should a Microservice Be?", p.61).[^bellemare2025]
- **균형을 묻는 이유가 양쪽에 비용이 있어서다** — **마이크로든 아니든 짓는 모든 서비스가 부수
  비용을 유발**하되 **단일 모놀리스가 주는 고통도 피하고 싶다**는 것이 저자가 세우는 대립이다
  (3장, p.61).[^bellemare2025]
- **저자가 재는 잣대 셋이 전부 사람 쪽이다** (3장, p.61).[^bellemare2025]

  | 잣대 | 저자가 적는 것 |
  |---|---|
  | 팀 하나가 감당할 수 있는가 | 마이크로서비스는 **한 팀이 관리할 수 있어야** 하고, 그 팀 안의 다른 사람도 필요하면 그 서비스를 손볼 수 있어야 한다 |
  | 그 팀은 얼마나 큰가 | **투 피자 팀(two-pizza team)** 이 인기 있는 척도이나 저자는 **개발자가 얼마나 배고픈지에 따라 달라지는 미덥지 않은 안내**일 수 있다고 단서를 단다 |
  | 한 사람의 머리에 들어가는가 | 그 팀의 **개발자 한 사람이 그 서비스가 지는 임무의 공간을 자기 머리에 담을 수 있어야** 하고, **새로 온 개발자가 그 서비스가 무슨 임무를 지고 어떻게 그것을 해내는지 하루나 이틀이면 알아낼 수 있어야** 한다 |

- **그리고 저자는 크기 자체를 부차로 밀어낸다** (3장, p.61).[^bellemare2025]

  > Ultimately, the real concern is that the service *serves a particular bounded context*
  > and satisfies a business need. The size, or how *micro* it really is, comes as a
  > secondary concern.

  - 그래서 **여기 적은 상한을 밀어붙이는 마이크로서비스가 나와도 괜찮다**는 것이 저자의 허용이고,
    중요한 것은 **그 서비스가 채우는 구체적 업무 관심사와 서비스의 경계를 짚어낼 수 있고, 그
    서비스가 무엇을 *해야 하고* 무엇을 *하지 말아야 하는지*의 목록을 머릿속에 잘 유지할 수 있는
    것**이다 (3장, pp.61–62).[^bellemare2025]
- **빠른 조언 다섯을 목록으로 적는다** (3장, p.62).[^bellemare2025]

  | 조언 | 저자가 다는 근거 |
  |---|---|
  | 필요한 만큼만 서비스를 짓는다 | **많다고 더 나은 것이 아니다** |
  | 한 사람이 서비스 전체를 이해할 수 있어야 한다 | 위 잣대 셋의 셋째와 같은 것 |
  | 팀이 그 서비스와 그 출력 이벤트 스트림을 소유·유지할 책임을 져야 한다 | 소유권이 서비스 하나에 붙는다 |
  | **먼저 기존 서비스에 기능을 더할 길을 찾는다** | **애플리케이션당 부수 비용이 줄어든다** — 다음 절의 마이크로서비스 세금으로 이어진다 |
  | 짓기로 한 것은 **모듈형 구성 요소(modular components)** 로 짓는 데 집중한다 | 업무가 자라면 **모듈 하나를 떼어 독립 마이크로서비스로 바꿔야 할 수도** 있다 |

- **이 KB에는 같은 물음에 답하는 소스가 이미 넷 있다.** 이 소스가 다섯째이고, 맞댄 결과는
  [마이크로서비스 경계 어림법](microservice-boundary-heuristics.md)에 있다.

## 규모에서 관리하기 — 컨테이너와 가상 머신

> **버전 조건**: 2025년 저술 시점의 제품 지형이다. 이 절에 나오는 제품 이름과 채택 판정은 그
> 시점의 것이고, 이 KB에서 이 축의 전문은 뉴먼의
> [마이크로서비스 배포 선택지](microservice-deployment-options.md)와
> [컨테이너 오케스트레이션과 쿠버네티스](../concepts/container-orchestration-and-kubernetes.md)가 갖는다.
> 여기는 이 소스가 더하는 것만 얇게 적는다.

- **서비스 수가 자라면 관리가 점점 어려워진다** — 각 마이크로서비스가 고유한 컴퓨트 자원·데이터
  저장소·설정·환경 변수와 그 밖의 서비스별 속성을 요구하고, **그것을 소유한 팀이 관리하고 배포할
  수 있어야** 하므로 개발자 운영(DevOps)의 간소화가 요구된다 (3장 §"Managing Microservices at
  Scale", p.62).[^bellemare2025]
- **저자가 이 자리를 바꾼 것으로 드는 셋이 컨테이너화·컨테이너 관리·코드형 인프라(IaC)** 이고,
  기술 선택의 인기 있는 예로 **도커·쿠버네티스·테라폼**을 든다 (3장, p.62).[^bellemare2025]
- **컨테이너와 가상 머신의 절충을 이 소스가 적는 대로만 옮긴다** (3장, pp.63–64).[^bellemare2025]

  | 격리 수단 | 저자가 적는 성질 |
  |---|---|
  | **컨테이너** | 호스트 운영체제를 **공유 커널 모델**로 쓴다. 컨테이너 사이의 기본 분리를 주면서 환경 변수·라이브러리·의존성을 격리한다. 가상 머신의 이점 대부분을 **훨씬 적은 값에** 주고 시작이 빠르며 자원 부수 비용이 낮다. **대가 둘** — 컨테이너화된 애플리케이션이 호스트 운영체제에서 돌 수 있어야 하고, **커널의 취약점 하나가 그 호스트의 모든 컨테이너를 위험에 빠뜨린다**(클라우드의 공유 테넌시 모델에서 특히 중요하다) |
  | **가상 머신(VM)** | **자체 운영체제와 가상화된 하드웨어**로 완전한 격리를 준다. 컨테이너보다 보안이 높지만 **역사적으로 훨씬 비쌌고**, 시작이 느리고 시스템 발자국이 크다. 저자가 드는 경량 VM 프레임워크가 **구글 gVisor·아마존 Firecracker·Kata Containers**다 |
  | **마이크로VM(microVM)** | 운용과 취급이 컨테이너에 훨씬 가깝다. 메모리·CPU 부수 비용이 아주 낮고 **고전 VM보다 훨씬 빨리(1초 미만) 시작**한다. 멀티테넌트 서비스에 **하드웨어 수준 격리**를 준다 |

- **저자의 판정은 컨테이너 쪽이다** — 초판 이후 5년 동안 선택지와 프레임워크가 나아졌지만
  **VM은 마이크로든 아니든 컨테이너에 비하면 여전히 상대적으로 드물다.** 컨테이너 격리가
  개선되고 보안 위험이 줄었기 때문이고, **아주 엄격한 격리 요구가 없다면 컨테이너를 쓸 공산이
  훨씬 크다** (3장, pp.63–64).[^bellemare2025]
  - 저자는 **결말을 열어 둔다** — 마이크로VM이 컨테이너를 대체할지, 컨테이너가 마이크로VM의 기능을
    전부 흡수할지, 둘이 이중성으로 공존할지는 **시간이 말해 줄 것**이라고 적는다 (3장,
    p.64).[^bellemare2025]
- **둘을 관리하는 것이 컨테이너 관리 시스템(container management systems, CMS)** 이고, 컨테이너
  배포·자원 할당·아래 컴퓨트 자원과의 통합을 통제한다. 저자가 드는 것이 **쿠버네티스·도커
  엔진·아마존 ECS·Nomad**다 (3장, p.64).[^bellemare2025]
- **CMS에 요구되는 것이 수직 확장과 수평 확장 둘 다**이고, **각 마이크로서비스는 하나의 단위로
  배포되어야 한다.** 많은 경우 실행 파일 하나로 충분해 컨테이너 하나에 담기지만, 더 복잡한 것은
  **여러 컨테이너와 외부 데이터 저장소 사이의 협응**을 요구한다 — 저자가 드는 예가 **쿠버네티스의
  파드(pod) 개념**이고, 여러 컨테이너를 **하나의 동작으로 배포하고 되돌릴 수 있게** 해 준다
  (3장, p.64).[^bellemare2025]
  - **VM 관리는 컨테이너 관리보다 아직 제한적**이라고 저자가 적는다 — 쿠버네티스와 도커 엔진이
    gVisor와 Kata Containers를, 아마존 플랫폼이 Firecracker를 지원한다. **고른 CMS가 요구하는
    컨테이너와 VM을 다룰 수 있는지 확인하라**는 것이 처방이다 (3장, p.64).[^bellemare2025]

## 마이크로서비스 세금

- **저자가 플랫폼 비용 전체에 이름을 붙인다** (3장 §"Paying the Microservice Tax",
  p.65).[^bellemare2025]

  > The *microservice tax* is the sum of costs, including financial, manpower, and
  > opportunity, associated with implementing the tools, platforms, and components of a
  > microservice architecture.

- **세금에 드는 것이 이벤트 브로커·CMS·배포 파이프라인·모니터링 솔루션·로깅 서비스의 관리와
  배포와 운영 비용**이다. 이 지출은 **피할 수 없고**, **조직이 중앙에서 내거나 마이크로서비스를
  쓰는 각 팀이 따로 낸다** (3장, p.65).[^bellemare2025]
  - **누가 내는가로 결과가 갈린다** — 중앙이 내면 **확장 가능하고 단순하고 통일된 개발 틀**이
    되고, 팀마다 따로 내면 **과도한 부수 비용·중복 해법·파편화된 도구·지속 불가능한 성장**이
    된다 (3장, p.65).[^bellemare2025]
- **세금에는 학습 비용도 든다** — 개발자가 마이크로서비스를 짓고 관리하고 유지하는 새 기술을
  배우는 동안의 **생산성 저하**다. 비동기를 다루는 법, 장애에서 복구하는 법, 서비스 모듈화가 전부
  시간이 들고 **이벤트 기반 아키텍처 경험이 적은 주니어 개발자에게 특히** 그렇다 (3장,
  p.65).[^bellemare2025]
  - 버전 조건: 2025년 저술 시점. 저자는 학습 비용을 낮추는 것으로 블로그·영상·책·글·안내서·개발
    환경 플러그인과 함께 **효과적인 AI 코파일럿의 등장**을 든다.
- **판정이 명시적으로 규모에 걸린다** — 마이크로서비스 세금을 내는 것은 사소하지 않고 **이벤트
  기반 마이크로서비스를 시작하는 데 가장 큰 장애의 하나**다. **작은 조직은 모듈형 모놀리스처럼
  업무 요구에 더 맞는 아키텍처를 고수하고, 업무가 확장과 성장 문제에 부딪힌 뒤에야 마이크로서비스로
  넓히는 것이 좋다** (3장, p.65).[^bellemare2025]
- **완화 셋을 저자가 든다** (3장, p.65).[^bellemare2025]

  | 완화 | 저자가 적는 것 |
  |---|---|
  | 전부 아니면 전무가 아니다 | 이벤트 기반 마이크로서비스 플랫폼에 **점진적으로 투자**할 수 있고, 필요가 요구하는 대로 기능을 더해 갈 수 있다 |
  | 세금 자체가 줄고 있다 | CMS와 이벤트 브로커와 그 밖의 흔히 필요한 도구 사이의 **새 통합**으로 꾸준히 내려가고 있다 |
  | 클라우드 서비스 | **명시적으로 언급할 값어치가 있다**고 저자가 적는다. 완전 관리형 CMS·이벤트 브로커·모니터링 솔루션·데이터 카탈로그·통합/배포 파이프라인을 **직접 돌리지 않고** 구할 수 있다. 자원을 크게 들이기 전에 **실험하고 시험**할 수 있어 시작하기 훨씬 쉽다 |

  - 버전 조건: 2025년 저술 시점. 저자는 클라우드 서비스와 완전 관리형 제공이 **초판이 나온
    2020년 이후 크게 개선되었고 채택이 수그러들 기미가 없다**고 적는다.
- **요약이 세금의 경계를 인정한다** — 마이크로서비스 세금은 **마이크로서비스를 쓸 만한 선택으로
  만들기 위해 해야 하는 업무 아닌 일의 총합**이고, **무엇이 그 안에 들고 들지 않는지에 분명한
  조리법은 없다.** 조직마다 기술 스택이 다르므로 **한 조직에 좋은 조언이 다른 조직에는 나쁜 선택**일
  수 있다. 처방은 **새것을 사기 전에 이미 가진 것을 쓰고 점진적으로 일하라**는 것이다 (3장,
  p.67).[^bellemare2025]
- **맺음 장이 그 "분명한 조리법 없음"에 목록 하나를 붙인다.** 3장이 항목을 열거하되 경계가 없다고
  적은 자리에, 22장이 **세금을 이루는 필수 서비스**를 여섯으로 못 박는다 (22장 §"Tooling,
  Infrastructure, and the Microservice Tax", pp.440–441):[^bellemare2025]
  **이벤트 브로커와 이벤트 스트림** · **스키마 레지스트리와 메타데이터 관리** · **접근 통제 관리** ·
  **자원 관리를 포함한 컨테이너 관리 체계** · **지속적 통합·전달·배포 서비스** ·
  **모니터링·로깅 서비스**.
  - 22장이 세금을 다시 규정하는 문장도 3장과 미묘하게 다르다 (22장, p.440):[^bellemare2025]

    > Event-driven microservices require an investment in the systems and tools that permit its
    > operation at scale, known as the microservice tax.

    3장이 **비용의 합**으로 규정한 것을 22장은 **투자**로 적는다. 같은 것의 두 면이라고 읽었다.
    `#hypothesis`
  - **시작점까지 적는다** — 세금을 내는 것은 **전부 아니면 전무가 아니고**, 조직은 흔히 **이벤트
    브로커 서비스나 컨테이너 관리 체계 하나로 시작해** 필요에 따라 나머지를 더해 간다 (22장,
    p.441).[^bellemare2025] 위 완화 표의 첫 칸이 "점진적으로 투자할 수 있다"까지만 적는데, **어느
    것으로 시작하는지를 대는 것은 22장뿐**이다.
  - **맺음이 규모 판정도 한 번 더 부드럽게 적는다** — **모든 마이크로서비스가 *마이크로*일 필요는
    없고**, 조직이 **세금을 전부 혹은 일부 내지 않았다면 더 큰 서비스 몇 개를 쓰는 것이 합리적**이다
    (22장 §"Microservices", p.443):[^bellemare2025]

    > There is no award for building the most microservices, nor is there an award for having just a
    > single massive service.

    이어서 **자기 조직에 맞는 균형을 찾아야 한다**고 적고, 큰 서비스에서 떼어 낸 잘게 나뉜 새
    서비스를 짓기 쉽게 하는 **핵심 원칙 셋**을 든다 (22장, pp.443–444):[^bellemare2025]
    **흔히 쓰이고 중요한 업무 엔티티와 이벤트를 이벤트 브로커에 게시할 것** ·
    **이벤트 브로커를 마이크로서비스를 구동하는 단일 진실 원천으로 쓸 것** ·
    **자기 마이크로서비스를 세우고 쓰고 관리하기 쉽게 만들 것**.
    둘째 조문이 6장이 범위를 좁혀 둔 그 진술이다 — 정본은
    [기록 시스템과 파생 데이터](system-of-record-and-derived-data.md)에 있다.

## 서비스 계약

- **서비스 계약(service contract)은 분명하고 간결한 마이크로서비스 경계를 세우는 중요한 구성
  요소**이고, **형식 문서화·API 관리·어느 서비스에 접근할 수 있고 어느 것에 못 하는지를 세우는
  데 결정적**이다 (3장 §"Service Contracts", p.66).[^bellemare2025]
  - 버전 조건: 2025년 저술 시점. 저자가 가장 인기 있는 선택으로 드는 것은 **OpenAPI 같은 명세나
    Swagger 같은 구현**이다.
- **서비스 계약이 세우는 것 여덟을 원문 정의 목록에서 옮겼고 표 형식은 이 KB가 만든 것이다**
  (3장, p.66).[^bellemare2025]

  | 세우는 것 | 저자가 적는 것 |
  |---|---|
  | 서비스 API | 그 서비스가 지원하는 API 호출 — 이름, 필수·선택 매개변수, 반환 타입, 지원 프로토콜 |
  | 코드 생성 | 명세에 근거해 **뼈대만 있는 함수**를 만들고, 그것을 고쳐 계약을 채우는 업무 로직을 담는다 |
  | 문서화 | 명세에서 문서를 생성할 수 있어 손으로 갱신하는 시간과 수고를 아낀다. **코드와 문서를 함께 생성하면 문서가 실제 가능한 호출과 일치함을 보장**할 수 있다 |
  | 네임스페이싱 | 서비스의 네임스페이스를 지정해 조직 정보를 주고 **이름이 비슷한 서비스 사이의 모호함을 없앤다** |
  | 버저닝 | 서비스 계약의 판과 **계약 변경의 내력** |
  | 소유권 | 그 서비스를 소유한 팀이나 사람을 지정한다 |
  | 서비스 수준 목표(또는 합의) | 소유자가 적절한 서비스 수준의 유지를 책임진다. **사이트 신뢰성 엔지니어(SRE)가 서비스 인스턴스를 살려 두는 책임을 질 수는 있어도 나머지 전부는 소유자의 책임**이다 |
  | 깨는 변경의 관리 | 서비스 API는 시간이 지나면 바뀔 수 있다. 계약이 **API를 폐기 예정으로 표시**하게 해 주어, 곧 삭제될 API에서 어떻게 옮겨 갈지를 사용자에게 알린다 |

- **그런데 저자가 곧바로 이 틀이 이벤트 기반에 그대로 오지 않는다고 적는다** — 이벤트 기반
  마이크로서비스는 직접 API 호출로 통신하는 요청-응답 마이크로서비스와 좀 다르다. **통신이
  점대점이 아니라 이벤트 스트림으로 일어나므로 서비스 계약 관념의 상당수가 아예 적용되지 않을 수
  있다.** 그 자리를 4장의 **데이터 계약(data contract)** 이 맡고, 서비스 계약과 비슷하되 **몇
  가지 핵심에서 다르다** (3장, p.67).[^bellemare2025]
- **다만 둘 다 필요한 경우가 명시된다** — **요청-응답 기반 API와 이벤트 스트림 데이터를 섞어
  제공하는 마이크로서비스는 서비스 계약과 데이터 계약을 둘 다 요구한다** (3장,
  p.67).[^bellemare2025] 데이터 계약의 전문은
  [이벤트 스키마와 데이터 계약](event-schemas-and-data-contracts.md)에 있다.

## 이 KB의 다른 자리들과의 분업

- **네 모양 가운데 셋은 이 소스의 뒤쪽 장들이 전문으로 다룬다** — 기본 프로듀서/컨슈머는 11장,
  중량·경량 프레임워크는 12~13장, 스트리밍 SQL은 14장, 커넥터는 6장이다. 이 페이지는 **3장이
  네 모양을 나란히 놓고 가르는 축**과 **11~13장이 답하는 "어느 모양이 어디에 맞는가"**와
  **14장이 채우는 스트리밍 SQL의 알맹이**를 담고, 프레임워크 셋의 런타임 내부는
  [스트림 처리 프레임워크의 세 모양](stream-processing-framework-shapes.md)이,
  15장의 함수 기반 모양은
  [FaaS로 짓는 이벤트 기반 마이크로서비스](faas-event-driven-microservices.md)가 갖는다.
  **스트리밍 SQL만 전용 페이지 없이 이 페이지 안에 절로 남는다** — 14장이 열두 쪽이고 그 가운데
  개념으로 살아남는 것이 위 한 절 분량이라, 나누면 이 페이지를 가리키기만 하는 스텁이 되기
  때문이다.
- **컨테이너와 가상 머신의 축은 이 페이지가 정본이 아니다.** 뉴먼 쪽이 같은 물음에 훨씬 두껍게
  답하고, 이 소스가 더하는 것은 **마이크로VM이라는 셋째 칸**과 **2025년 시점의 채택 판정**이다.
- **마이크로서비스 세금은 뉴먼이 같은 이름을 남의 말로 옮겨 쓰는 자리가 이미 있다.** 이 소스는
  그 이름에 **규정과 항목 목록을 붙이는 쪽**이고, 맞댄 결과는
  [마이크로서비스의 고통과 채택 판단](microservice-pain-points-and-adoption.md)에 있다.
