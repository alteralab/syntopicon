하나의 질문: **쪼개기로 했을 때 모놀리식 데이터베이스를 어떤 순서로 어떻게 가르는가.**

쪼갤 것인가의 **판정**은 [데이터 분해의 구동 요인](../concepts/data-decomposition-drivers.md)이 갖고,
이 페이지는 그 판정을 통과한 뒤의 **절차**를 갖는다.

- **절차의 전제가 협업이다** — 모놀리식 데이터베이스를 분해하는 일은 어렵고 **아키텍트가
  데이터베이스 팀과 긴밀히 협업할 것을 요구한다.** 특히 효과적인 기법 하나가 **다섯 단계
  절차(five-step process)로 알려진 것을 쓰는 것**이고, 이 **진화적이고 반복적인 절차는 데이터
  도메인이라는 개념을 매개로 데이터를 별도 스키마로, 따라서 서로 다른 물리 데이터베이스로 체계적으로
  옮긴다** (6장, p.151).[^ford2021-hard-parts]

## 데이터 도메인이란 무엇인가

- **규정** (6장, p.152):[^ford2021-hard-parts]

  > A *data domain* is a collection of coupled database artifacts—tables, views, foreign keys,
  > and triggers—that are all related to a particular domain and frequently used together within
  > a limited functional scope.

  - **네 조건이 들어 있다** — 결합된 데이터베이스 아티팩트의 모음이고, 그 아티팩트는
    테이블·뷰·외래 키·트리거이며, 전부 **한 도메인에 관계되고**, **제한된 기능 범위 안에서
    자주 함께 쓰인다.**

## 축구공 비유

- **데이터베이스를 축구공으로 본다** — 데이터 도메인을 개념적으로 생각하는 한 방법이 **데이터베이스를
  축구공으로 보고 각 흰 육각형을 별개의 데이터 도메인으로 보는 것**이다. 각 흰 육각형은 **도메인에
  관계된 테이블의 모음과 외래 키·뷰·저장 프로시저 같은 결합 아티팩트 전부**를 담는다 (6장,
  p.153).[^ford2021-hard-parts]
- **이 그림이 무엇을 보게 하는가** — 이렇게 시각화하면 아키텍트와 데이터베이스 팀이 **데이터 도메인
  경계**와 **끊어야 할 도메인 사이 의존**을 뚜렷이 볼 수 있다 (6장,
  p.153).[^ford2021-hard-parts]
- **보존과 제거의 선이 육각형이다** — 각 흰 육각형 **안에서는** 모든 테이블 의존과 관계가 **보존될
  수 있지만** 육각형 **사이에서는** 그렇지 않다. 도판에서 **실선은 데이터 도메인 안에 갇힌
  의존**이고 **점선은 데이터 도메인을 가로질러 데이터 도메인이 별도 스키마로 뽑혀 나갈 때 제거되어야
  하는 의존**이다 (6장, p.153, 그림 6-18).[^ford2021-hard-parts] 도판은 재현하지 않는다.

## 도메인을 가로지르는 의존을 걷어 내기

- **무엇을 제거하는가** — 데이터 도메인을 뽑아낼 때 도메인 사이 의존은 제거되어야 하고, 그것은
  데이터 도메인 사이의 **외래 키 제약·뷰·트리거·함수·저장 프로시저를 제거하는 것**을 뜻한다
  (6장, p.154).[^ford2021-hard-parts]
- **저자들이 그 작업의 방법론을 다른 책으로 넘긴다** — 데이터베이스 팀은 스콧 앰블러와 프라모드
  사달게이의 *Refactoring Databases: Evolutionary Database Design*에 있는 **리팩터링 패턴을 써서
  이 데이터 의존들을 안전하고 반복적으로 제거할 수 있다** (6장,
  p.154).[^ford2021-hard-parts] **이 KB는 그 책을 원전으로 들이지 않았다** — 귀속은 이 책이
  그렇게 귀속한다까지로 둔다. 같은 저자가 참여한 2022년 책의 데이터 진화 서술은
  [진화적 데이터베이스 설계](evolutionary-database-design.md)에 있다.
- **책의 예가 뷰 하나를 고친다.** Payment 데이터 도메인을 만들 때 **customer 테이블이 다른 데이터
  도메인에 속하므로 Payment 도메인의 `v_customer_contract` 뷰에서 그 테이블을 빼야 한다** (6장,
  p.154).[^ford2021-hard-parts]
  - **데이터 도메인을 정의하기 전의 뷰**가 이것이다 (6장, p.155, 예제
    6-1).[^ford2021-hard-parts] 도메인을 가로지르는 조인이 뷰라는 아티팩트 안에 어떻게 박혀
    있는지를 이 목록이 보인다.

    ```sql
    CREATE VIEW [payment].[v_customer_contract]
      AS
    SELECT
         customer.customer_id, customer.customer_name,
         contract.contract_start_date, contract.contract_duration,
         billing.billing_date, billing.billing_amount
    FROM payment.contract AS contract
    INNER JOIN customer.customer AS customer
         ON ( contract.customer_id = customer.customer_id )
    INNER JOIN payment.billing AS billing
         ON ( contract.contract_id = billing.contract_id )
    WHERE contract.auto_renewal = 0
    ```

  - **고친 뒤에 달라지는 것이 둘이다** — **customer 테이블과 payment 테이블 사이의 조인이
    제거되고**, **고객 이름 열(`customer.customer_name`)도 함께 제거된다.** 남은 뷰는
    `payment.contract`와 `payment.billing`만 조인하고 고객 식별자를 `billing.customer_id`에서
    가져온다 (6장, p.155, 예제 6-2).[^ford2021-hard-parts]
- **그 제거가 강제하는 규칙이 뒤따른다** (6장, p.155):[^ford2021-hard-parts]

  > The bounded context rules for data domains apply just the same as individual tables—a
  > service cannot talk to multiple data domains.

  - **그래서 값을 잃는 것이 아니라 호출이 생긴다** — 뷰에서 그 테이블을 제거함으로써 **Payment
    서비스는 원래 뷰에서 얻던 고객 이름을 이제 Customer 서비스를 호출해 얻어야 한다** (6장,
    p.155).[^ford2021-hard-parts] 같은 값을 잃는 대가는
    [데이터 분해가 부르는 문제들](../concepts/data-decomposition-concerns.md)이 성능 항목으로 센다.
  - **두 예제의 제목이 내용과 어긋난다** — 원문이 둘 다 `Database view to get open tickets`로
    시작하는데 이 뷰가 돌려주는 것은 계약과 청구 정보다. 원문 그대로 두었다.

## 다섯 단계

- **데이터 도메인 개념을 이해하고 나면 절차를 적용할 수 있다** (6장, p.155).[^ford2021-hard-parts]
  그림 6-17의 띠가 절차 전체의 목적을 한 줄로 적는다 — **독립 서버 위에 데이터 도메인을 만드는
  다섯 단계 절차**다 (6장, p.151, 그림 6-17).[^ford2021-hard-parts] 상자 다섯의 이름은
  아래와 같다.

  | 단계 | 그림 6-17의 상자 | 쪽 |
  |---|---|---|
  | 1 | Analyze database and create data domains | p.156 |
  | 2 | Assign tables to data domains, move tables | p.156 |
  | 3 | Separate database connections to data domains | p.158 |
  | 4 | Move schemas to separate database servers | p.159 |
  | 5 | Switch over to independent database servers | p.161 |

  - **상자의 문구와 절 제목이 한 자리에서 다르다** — 둘째 상자는 `Assign tables to data domains,
    move tables`인데 절 제목은 `Step 2: Assign Tables to Data Domains`다. 원문 그대로 두었다.

## 1단계 — 데이터베이스를 분석하고 데이터 도메인을 만든다

- **출발 상태에 이름이 있다** — 모든 서비스가 데이터베이스의 모든 데이터에 접근하는 이 실천은
  **그레거 호페와 보비 울프의 *Enterprise Integration Patterns*에 서술된 공유 데이터베이스 통합
  양식(shared database integration style)으로 알려져 있고**, 데이터와 그 데이터에 접근하는 서비스
  사이에 **단단한 결합**을 만든다 (6장, p.156).[^ford2021-hard-parts]
  - **그 결합이 무엇을 망가뜨리는지가 앞 절과 이어진다** — 데이터베이스 안의 이 단단한 결합이
    **변경 관리를 아주 어렵게 만든다** (6장, p.156).[^ford2021-hard-parts] 그 논거는
    [데이터 분해의 구동 요인](../concepts/data-decomposition-drivers.md) §"변경 통제"에 있다.
  - 같은 통합 양식의 카탈로그 쪽 서술은
    [애플리케이션 통합의 네 가지 스타일](application-integration-styles.md)에 있다.
- **이 단계가 하는 일** — 데이터베이스를 쪼개는 첫 단계는 **데이터베이스 안의 구체적인 도메인
  묶음을 식별하는 것**이고, 그 결과가 위 표 6-5처럼 **관련 테이블을 묶어 가능한 데이터 도메인을
  식별하는 것**이다 (6장, p.156).[^ford2021-hard-parts]
  - **이 단계에는 물리적 이동이 없다.** 옮기는 것은 다음 단계다.

## 2단계 — 테이블을 데이터 도메인에 배정한다

- **이 단계가 하는 일** — 다음 단계는 **구체적인 경계 컨텍스트를 따라 테이블을 묶어, 특정 데이터
  도메인에 속하는 테이블을 자기 스키마로 배정하는 것**이다 (6장, p.156).[^ford2021-hard-parts]
- **스키마의 규정** — **스키마(schema)는 데이터베이스 서버 안의 논리적 구성물**이고 테이블·뷰·함수
  같은 객체를 담는다. **오라클처럼 어떤 데이터베이스 서버에서는 스키마가 사용자와 같고**, SQL
  서버처럼 다른 데이터베이스에서는 **사용자가 접근 권한을 갖는 데이터베이스 객체의 논리
  공간**이다 (6장, p.156).[^ford2021-hard-parts]
  - 버전 조건: 2021년 저술 시점의 제품 동작이다 — 저자들이 판을 대지 않는다.
- **도메인이 합쳐져야 하는 경우가 있다** — 서로 다른 데이터 도메인에 속한 테이블들이 **단단히
  결합되어 서로 관계될 때 데이터 도메인은 필연적으로 합쳐져야 하고**, 그러면 **여러 서비스가 한
  데이터 도메인을 소유하는 더 넓은 경계 컨텍스트**가 생긴다 (6장,
  p.157).[^ford2021-hard-parts] 저자들이 그 합치기의 상세를 9장으로 넘긴다.
  - **이것이 이 절차가 서비스별 데이터베이스와 같지 않은 자리다** — 한 데이터 도메인을 **여러
    서비스가 소유할 수 있다**고 저자들이 명시한다.
- **실제 이동은 한 줄이다** — 사례에서 `billing` 테이블을 원래 스키마에서 `payment`라는 데이터
  도메인 스키마로 옮기는 명령이 `ALTER SCHEMA payment TRANSFER sysops.billing;`이다 (6장,
  p.157).[^ford2021-hard-parts]

## 곁상자 — 데이터 도메인과 데이터베이스 스키마

- **두 낱말의 격이 다르다는 것을 저자들이 곁상자로 못 박는다** (6장,
  p.157, 곁상자):[^ford2021-hard-parts]

  > A *data domain* is an architectural concept, whereas a *schema* is a database construct that
  > holds the database objects belonging to a particular data domain. While the relationship
  > between a data domain and a schema is usually one to one, data domains can be mapped to one
  > or more schemas, particularly when combining data domains because of tightly coupled data
  > relationships. We will be referring to a data domain and schema to mean the same thing, and
  > will be using the terms interchangeably.

  - **대응이 보통 일대일이지만 언제나 그런 것은 아니다** — 단단히 결합된 데이터 관계 때문에 데이터
    도메인을 합칠 때는 **한 데이터 도메인이 여러 스키마에 대응할 수 있다.**
  - **그리고 저자들이 이 책의 나머지에서 두 낱말을 바꿔 쓰겠다고 선언한다.** 이 KB는 그 선언을
    그대로 옮기되 **두 낱말을 구분해 쓴다** — 아키텍처 개념과 데이터베이스 구성물이 섞이면 위
    일대다 경우가 보이지 않기 때문이다.

## 동의어 — 임시 장치와 그 대가

- **다른 길이 하나 있다** — 데이터베이스 팀은 자기 스키마에 속하지 않는 테이블에 대해
  **동의어(synonyms)를 만들 수 있다.** 동의어는 **심볼릭 링크(symlink)와 비슷한 데이터베이스
  구성물**로, 같은 서버나 다른 서버, 같은 스키마나 다른 스키마에 있을 수 있는 **다른 데이터베이스
  객체에 대한 대체 이름**을 준다 (6장, p.157).[^ford2021-hard-parts]
  - **의도와 조건** — 동의어의 취지는 **스키마를 가로지르는 질의를 없애는 것**이지만, 그것에
    접근하려면 **읽기나 쓰기 권한이 필요하다** (6장, p.157).[^ford2021-hard-parts]
- **책의 예** — 티켓 이력과 담당자 프로필을 가로질러 조인하던 질의를 두고,
  `CREATE SYNONYM ticketing.sysops_user FOR profile.sysops_user;`로 동의어를 만든 뒤 질의가
  **도메인을 가로지르는 테이블 대신 동의어를 쓰게 한다** (6장, p.158).[^ford2021-hard-parts]
  - **원문이 만든 동의어 이름과 고친 질의가 쓰는 이름이 다르다** — 동의어는
    `ticketing.sysops_user`로 만들어지는데 고친 질의는 `ticket.sysops_user`를 조인한다. 원문
    그대로 두었다.
- **대가가 명시된다** — 스키마를 가로질러 접근되는 테이블에 이렇게 동의어를 만드는 것은
  **애플리케이션 개발자에게 결합 지점을 준다.** 제대로 된 데이터 도메인을 이루려면 **그 결합
  지점들은 나중에 끊어져야 하고**, 그럼으로써 **통합 지점이 데이터베이스 계층에서 애플리케이션
  계층으로 옮겨 간다** (6장, p.158).[^ford2021-hard-parts]
- **그래도 얻는 것이 있다** — 동의어가 **스키마를 가로지르는 질의를 실제로 없애 주지는 않지만**,
  **의존 확인과 코드 분석을 더 쉽게 해 주어 나중에 쪼개기를 쉽게 만든다** (6장,
  p.158).[^ford2021-hard-parts]
  - **그래서 동의어는 목적지가 아니라 발판이다** — 저자들이 3단계에서 이것을 전부 제거한다.

## 3단계 — 커넥션을 데이터 도메인별로 가른다

- **이 단계가 하는 일** — 각 서비스 안의 **데이터베이스 커넥션 로직이 리팩터링되어** 서비스가
  **특정 스키마에 연결하고 자기 데이터 도메인에 속한 테이블에만 읽기와 쓰기 권한을 갖도록**
  보장한다 (6장, p.158).[^ford2021-hard-parts]
- **저자들이 이 단계를 가장 어렵다고 못 박는다** — 이 이행은 **모든 스키마 교차 접근이 서비스
  수준에서 해소되어야 하므로 가장 어렵다** (6장, p.158).[^ford2021-hard-parts]
  - **완료 상태가 뚜렷하다** — 데이터 접근이 **엄격히 서비스와 그 서비스가 연결된 스키마를 통해서만**
    이루어지도록 설정이 바뀌고, **스키마 교차 접근이 없으며 2단계에서 만든 동의어는 전부
    제거된다.** 다른 스키마의 데이터가 필요한 서비스는 **그 스키마가 아니라 그것을 소유한 서비스와
    말한다** (6장, p.158).[^ford2021-hard-parts]
- **조문이 상자로 따로 인쇄된다** (6장, p.159):[^ford2021-hard-parts]

  > When data from other domains is needed, do not reach into their databases. Instead, access it
  > using the service that owns the data domain.

## 서비스별 데이터 주권

- **3단계를 마치면 데이터베이스가 어떤 상태가 되는지에 이름이 붙는다** (6장,
  p.159):[^ford2021-hard-parts]

  > Upon completion of this step, the database is in a state of *data sovereignty per service*,
  > which occurs when each service owns its own data. Data sovereignty per service is the nirvana
  > state for a distributed architecture.

  - **그런데도 저자들이 곧바로 저울을 단다** — **아키텍처의 모든 실천이 그렇듯 이것에도 이점과
    단점이 있다** (6장, p.159).[^ford2021-hard-parts]
- **이점 둘과 대가 셋** (6장, p.159):[^ford2021-hard-parts]

  | | 항목 |
  |---|---|
  | 이점 | 팀이 다른 도메인에 변경이 미칠지 걱정하지 않고 데이터베이스 스키마를 바꿀 수 있다 |
  | 이점 | 각 서비스가 자기 사용 사례에 가장 알맞은 데이터베이스 기술과 데이터베이스 종류를 쓸 수 있다 |
  | 대가 | 서비스가 대량의 데이터에 접근해야 할 때 성능 문제가 생긴다 |
  | 대가 | 참조 무결성을 데이터베이스에서 유지할 수 없어 나쁜 데이터 품질의 가능성이 생긴다 |
  | 대가 | 다른 도메인에 속한 테이블에 접근하는 모든 데이터베이스 코드(저장 프로시저·함수)를 서비스 계층으로 옮겨야 한다 |

  - **이 셋이 다른 소스의 목록과 그대로 겹친다** — 성능과 참조 무결성은
    [데이터 분해가 부르는 문제들](../concepts/data-decomposition-concerns.md)의 첫 두 항목이고, 셋째는
    [진화적 데이터베이스 설계](evolutionary-database-design.md)가 **데이터베이스 네이티브 기능을
    적합도 함수로 갈아 끼운다**고 적는 자리다. **세 소스가 같은 청구서를 적는다.**
  - **이 목록에 트랜잭션이 없다.** 같은 장의 통합 요인 절이 그것을 따로 세우므로 여기서는
    빠진 것으로 보이고, 저자들이 그 이유를 적지 않는다. #hypothesis

## 4단계 — 스키마를 별도 데이터베이스 서버로 옮긴다

- **이 단계의 전제** — 데이터베이스 팀이 데이터 도메인을 만들어 가르고 서비스가 자기 데이터에만
  접근하도록 격리하고 나면 **데이터 도메인을 별도의 물리 데이터베이스로 옮길 수 있다** (6장,
  p.159).[^ford2021-hard-parts]
- **왜 필요한가** — 서비스가 자기 스키마에만 접근하더라도 **단일 데이터베이스에 접근하는 것은 단일
  아키텍처 퀀텀을 만들고**, 그것은 **확장성·내결함성·성능 같은 운영 특성에 나쁜 영향을 줄 수
  있다** (6장, p.160).[^ford2021-hard-parts] 그 셈법은
  [아키텍처 퀀텀](../concepts/architectural-quantum.md)에 있다.
  - **그래서 3단계와 4단계의 성격이 다르다** — 3단계는 **논리적 격리**를 끝내고 4단계가 **물리적
    분리**를 한다. 위 분해 요인 가운데 퀀텀은 4단계까지 가야 해소된다.
- **선택지가 둘이고 대가가 갈린다** (6장, p.160):[^ford2021-hard-parts]

  | 선택지 | 순서 | 대가 |
  |---|---|---|
  | 백업과 복원(backup and restore) | 데이터 도메인이 든 각 스키마를 백업하고, 데이터 도메인마다 데이터베이스 서버를 세우고, 스키마를 복원하고, 서비스를 새 서버의 스키마에 연결하고, 마지막으로 원래 서버에서 스키마를 제거한다 | 이 접근은 대개 이행에 다운타임을 요구한다 |
  | 복제(replicate) | 데이터 도메인마다 데이터베이스 서버를 먼저 세우고, 스키마를 복제하고, 커넥션을 새 서버로 전환하고, 원래 서버에서 스키마를 제거한다 | 다운타임은 피하지만 복제를 세우는 데 더 많은 작업과 늘어난 조율을 요구한다 |

  - **책의 그림이 보이는 것은 복제 쪽이다** — 데이터베이스 팀이 **데이터 도메인마다 데이터베이스
    서버 하나씩** 여러 서버를 세운다 (6장, p.160, 그림 6-23).[^ford2021-hard-parts]

## 5단계 — 독립 데이터베이스 서버로 전환한다

- **이 단계가 하는 일** — 스키마가 완전히 복제되고 나면 **서비스 커넥션을 전환할 수 있다.**
  데이터 도메인과 서비스가 자기 독립 배포 단위로 행동하게 만드는 마지막 단계는 **옛 데이터베이스
  서버로 가는 커넥션을 제거하고 옛 서버에서 스키마도 제거하는 것**이다 (6장,
  p.161).[^ford2021-hard-parts]
  - **최종 상태는 데이터 도메인마다 독립된 데이터베이스 서버**다 (6장, p.161, 그림
    6-24).[^ford2021-hard-parts]
- **절차가 끝난 뒤에 열리는 문이 둘이다** — 데이터 도메인을 가르고 커넥션을 격리하고 데이터
  도메인을 자기 데이터베이스 서버로 옮기고 나면 팀은 **개별 데이터베이스 서버를 가용성과 확장성에
  맞게 최적화할 수 있고**, **데이터를 분석해 가장 알맞은 데이터베이스 종류를 판정해 생태계 안에
  폴리글랏 데이터베이스 사용을 들일 수 있다** (6장, p.161).[^ford2021-hard-parts]
  - **둘째 문이 이 장의 다음 절이다** — 위 분해 요인의 여섯째(데이터베이스 종류 최적화)가 그
    자리에서 상세해진다.

## 데이터 도메인은 경계 컨텍스트인가

**저자들이 두 낱말을 나란히 쓴다. 그러나 같다고 적지는 않는다.** 아래 판정은 **이 KB가 세운
것**이다.

- **저자들이 잇는 자리는 셋이다** (6장, pp.135·156·157):[^ford2021-hard-parts]
  - 변경 통제의 해법을 **잘 정의된 경계 컨텍스트로 쪼개는 것**이라 적는다.
  - 2단계를 **구체적인 경계 컨텍스트를 따라 테이블을 묶는 것**이라 적는다.
  - 데이터 도메인이 합쳐질 때 **더 넓은 경계 컨텍스트**가 생긴다고 적는다.
- **그래도 두 낱말이 같은 것을 가리키지는 않는다.**

  | | 데이터 도메인(포드 외) | 경계 컨텍스트(에반스·크호노프) |
  |---|---|---|
  | 무엇으로 묶는가 | 결합된 데이터베이스 아티팩트 — 테이블·뷰·외래 키·트리거 | 한 모델이 통용되는 범위. 소스 코드와 업무 로직까지 든다 |
  | 무엇이 판정의 증거인가 | 아티팩트가 **자주 함께 쓰이는가**와 제한된 기능 범위 안에 있는가 | 같은 낱말이 같은 뜻으로 통하는가 |
  | 소유자가 몇인가 | **여럿일 수 있다** — 저자들이 합쳐진 도메인을 여러 서비스가 소유한다고 적는다 | 팀 하나에 컨텍스트 하나가 원전의 규칙이다 |
  | 물리적 대응물 | 스키마. 보통 일대일이되 일대다일 수 있다 | 크호노프 쪽에서는 컨텍스트마다 별도 서비스라는 물리 경계가 붙는다 |

  - **겹치는 점이 하나 분명하다** — **서비스가 여러 데이터 도메인과 말할 수 없다**는 규칙이
    경계 컨텍스트 규칙의 데이터판이라고 저자들 스스로 적는다 (6장,
    p.155).[^ford2021-hard-parts]
  - **갈리는 점은 소유자의 수다.** 크호노프의 경계 컨텍스트는 **팀 하나가 소유하는 단위**이고
    포드 외의 데이터 도메인은 **여러 서비스가 소유할 수 있는 스키마 묶음**이다 (14장,
    pp.225–229).[^khononov2021] **모순이 아니라 재는 것이 다르다** — 한쪽은 모델의 일관성
    경계이고 다른 쪽은 데이터 아티팩트의 결합 경계다. #hypothesis
  - **뉴먼의 서비스별 데이터베이스와도 같지 않다.** 위 3단계가 도달하는 **서비스별 데이터 주권**은
    그 처방과 같은 자리이지만, **2단계가 허용하는 합쳐진 데이터 도메인**은 한 스키마를 여러
    서비스가 소유하는 상태라 그 처방 밖이다. 저자들이 그 상태를 **중간 단계가 아니라 정당한 결과**로
    적는다는 점이 이 절차의 특징이다.
  - 경계 컨텍스트의 원전 쪽 전문은 [경계 컨텍스트](../concepts/bounded-context.md)에 있다.

## 이 절차와 확장 수축 패턴

**같은 저자 무리의 2022년 책이 같은 이행을 패턴으로 적는다.** 아래 배치는 **이 KB가 세운
것**이고 두 책 어느 쪽도 이 자리에서 상대를 호명하지 않는다.

- **2022년 책의 확장/수축(expand/contract) 패턴**은 **옛 상태와 새 상태를 잠시 함께 두었다가 옛
  것을 걷어 내는** 꼴이고, 그 전문은
  [진화적 데이터베이스 설계](evolutionary-database-design.md)에 있다.[^ford2022-evolutionary]
- **2021년 책의 3단계에서 5단계가 그 꼴을 그대로 밟는다.**

  | 국면 | 이 절차의 어디 | 무엇이 둘이 되는가 |
  |---|---|---|
  | 확장 | 2단계의 동의어 | 같은 테이블에 이름이 둘 — 원래 이름과 동의어 |
  | 확장 | 4단계의 복제 | 같은 스키마가 옛 서버와 새 서버 양쪽에 |
  | 수축 | 3단계의 동의어 제거 | 이름 하나만 남는다 |
  | 수축 | 5단계의 옛 커넥션과 옛 스키마 제거 | 새 서버만 남는다 |

  - **두 책의 격이 다르다** — 2021년 책은 **절차**(어느 순서로 무엇을 하는가)를 주고 2022년 책은
    **패턴**(왜 둘을 잠시 함께 두는가)을 준다. **겨루지 않는다.**
  - **다만 2021년 쪽이 되돌리기를 적지 않는다.** 2022년 책은 한번 돌린 마이그레이션을 불변으로
    두라는 규약과 되돌리기를 팀들이 버린 이유를 적는데, 이 다섯 단계에는 **어느 단계에서 되돌릴
    수 있고 어디가 돌아올 수 없는 지점인지에 대한 서술이 없다.** 3단계가 **가장 어렵다**고만 적힌다.

## 코드 쪽 분해 패턴과 나란히 놓기

- **이 다섯 단계는 코드 쪽 여섯 패턴의 데이터판이다.** 저자들이 장 도입부에서 그 대응을 직접
  적는다(컴포넌트는 데이터 도메인으로, 클래스 파일은 테이블로, 클래스 사이 결합 지점은 외래 키와
  뷰와 트리거와 저장 프로시저로) (6장, p.132).[^ford2021-hard-parts]
- **그러나 순서가 반대다.** 아래 대비는 **이 KB가 세운 것**이다.

  | | 코드 쪽 여섯 패턴 | 데이터 쪽 다섯 단계 |
  |---|---|---|
  | 무엇이 먼저 갈라지는가 | 논리 구조(네임스페이스)를 다 정리한 뒤 마지막 패턴에서 배포 단위가 갈라진다 | 논리 구조(스키마)를 2단계에서 가르고 3단계에서 접근을 가른 뒤 4단계에서 물리 서버가 갈라진다 |
  | 언제 시작하는가 | 모놀리스 상태에서 | **코드 쪽이 끝난 뒤에** — 여는 사가가 도메인 서비스로 쪼갠 다음이라고 적는다 |
  | 되돌릴 수 있는가 | 네임스페이스 이동이라 되돌리기 쉽다 | 4단계 이후는 물리 이동이다 |

  - **코드 쪽 여섯 패턴의 마지막이 남겨 둔 것이 바로 이 장의 대상이다** —
    [도메인 서비스 만들기](../concepts/create-domain-services.md)가 만드는 서비스 기반 아키텍처는 **단일
    관계형 데이터베이스를 그대로 남긴다.** 이 장이 그것을 가른다.
  - 코드 쪽 절차 전체는
    [컴포넌트 기반 분해 패턴 여섯](../concepts/component-based-decomposition-patterns.md)에 있고, 모놀리스를
    뽑아내는 장치들은 [모놀리스 분해 패턴](monolith-decomposition-patterns.md)에 있다.

## 9장이 같은 도메인을 공동 소유권의 기법으로 다시 쓴다

**같은 책 9장에 `data domain technique`이라는 이름의 기법이 있다.** 가리키는 것은 이 페이지의
데이터 도메인과 같은 구성물이되, **쓰이는 국면이 다르다.**

- **9장의 규정은 이렇다** — 공동 소유권(여러 서비스가 같은 테이블에 쓰는 상황)을 푸는 네 기법
  가운데 하나로, **같은 서비스들이 공유하는 테이블을 같은 스키마나 같은 데이터베이스에 넣어
  서비스와 데이터 사이에 더 넓은 경계 컨텍스트를 이룬다** (9장 §"Data Domain Technique",
  p.256).[^ford2021-hard-parts]
- **두 국면을 나란히 놓으면 이렇다.**

| | 이 페이지(6장) | 9장의 데이터 도메인 기법 |
|---|---|---|
| 언제 쓰는가 | **쪼개는 동안** — 모놀리식 데이터베이스를 가를 매개 | **쪼갠 뒤** — 테이블에 주인을 배정하다 여럿이 쓰는 자리를 만났을 때 |
| 무엇을 정하는가 | 테이블을 어느 도메인에 넣을 것인가(1~2단계) | 이 테이블을 한쪽에 주지 말고 **공유로 둘 것인가** |
| 선택지 가운데 몇 번째인가 | 절차의 **기본 뼈대**다 | **네 기법 중 하나**다. 나머지 셋은 테이블 쪼개기·위임·서비스 통합이다 |
| 대가를 어디에 적는가 | 위 §"서비스별 데이터 주권"과 §"동의어 — 임시 장치와 그 대가" | 절충표(표 9-2) — 스키마 변경이 여러 서비스에 걸리고 쓰기 책임의 거버넌스가 따로 필요하다 |

- **같은 제약이 두 장을 잇는다** — 위 §"도메인을 가로지르는 의존을 걷어 내기"가 적는 **서비스는
  여러 데이터 도메인과 말할 수 없다**는 규칙이 9장에서 그대로 선택지를 좁히는 데 쓰인다. 9장의
  사가에서 설문 테이블을 공유 데이터 도메인에 두자는 제안이 기각되는 근거가 **그 서비스가 이미
  다른 데이터 도메인에 말하고 있다**는 것이다 (9장, p.280, 사가).[^ford2021-hard-parts]
- **9장이 더하는 조문 하나** — 이 기법을 고를 때는 **데이터가 서로에게 공통인데 왜 별도의
  서비스가 필요한지를 언제나 다시 따져 보라**는 곁상자다 (9장, p.257).[^ford2021-hard-parts]
  **이 페이지의 절차에는 그 되물음이 없다** — 여기서는 도메인을 만드는 것이 목표이지 서비스
  경계를 재검토하는 자리가 아니기 때문이다.
- 네 기법의 전문과 절충표 넷은 [서비스의 데이터 소유권](service-data-ownership.md)에 있다.
- **10장이 같은 구성물을 셋째 국면에서 다시 쓴다** — 소유하지 않은 데이터를 **읽는** 네 패턴
  가운데 하나이고, 저자들이 **9장에서 공동 소유권을 풀던 그 패턴을 데이터 접근에도 쓸 수 있다**고
  명시한다 (10장, p.293).[^ford2021-hard-parts] 그 자리에서는 다른 셋(서비스 간 통신·컬럼 스키마
  복제·복제 캐싱)이 전부 막혔을 때의 **마지막 선택지**로 도입되고, 새로 적히는 대가가 둘이다 —
  **테이블 스키마가 계약이 되어** 어느 테이블의 구조가 바뀌면 여러 서비스가 함께 바뀌어야 하고,
  접근하는 서비스가 **데이터 도메인 안의 모든 데이터에 닿는다는 보안 문제**가 열린다 (10장,
  pp.294–295).[^ford2021-hard-parts] 전문은
  [분산 데이터 접근 패턴 넷](distributed-data-access-patterns.md)에 있다.
  - **곧 이 낱말이 같은 책 안에서 세 국면에 쓰인다** — 6장은 **쪼개는 동안의 매개**, 9장은
    **쓰기가 겹칠 때의 기법**, 10장은 **읽기를 얻는 패턴**이다. **세 자리 가운데 어디에도
    저자들이 그 셋을 한자리에 모아 적지 않는다.** #hypothesis
