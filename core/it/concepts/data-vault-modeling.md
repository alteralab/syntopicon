# Data Vault 모델링

- [왜 business key 중심인가](#왜-business-key-중심인가)
- [세 가지 기본 엔티티](#세-가지-기본-엔티티)
- [제3자가 보는 Data Vault — 데이터 엔지니어링 개론의 서술](#제3자가-보는-data-vault--데이터-엔지니어링-개론의-서술)

Data Vault는 1990년대 Dan Linstedt가 만든 데이터 웨어하우스 모델로, 자연에서
관찰되는 척도 없는 네트워크(scale-free network)를 지향한다 — 허브에 새 연결을
더하는 방식으로 확장이 쉬운 구조다 (§4.1, pp.107–108).[^linstedt2016]

## 왜 business key 중심인가

- 모델 전체가 업무 키(business key)를 축으로 선다 — 업무가 일상 운영에서 정보를
  통합·연결·접근하는 방식 그대로를 모델이 물려받기 위해서다 (§4.2, p.108).[^linstedt2016]
- 모델이 지원하려는 업무 특성: 민첩성(agility)·통합(integration)·복잡성 대응·
  유연성·투명성과 감사 가능성(accountability)·맞춤 보고·확장(scale) (§4.2, p.108).[^linstedt2016]

## 세 가지 기본 엔티티

역할 분담이 모델의 뼈대다 (§4.2, pp.108–109):[^linstedt2016]

> the **hub** separates the business keys from the rest of the model; the
> **link** stores relationships between business keys (and/or hubs); and
> **satellites** store the context (the attributes of a business key or
> relationship).

- [Hub](../concepts/data-vault-hub.md) — 업무 키를 모델의 나머지에서 분리해 보관한다.
- [Link](../concepts/data-vault-link.md) — 업무 키(허브)들 사이의 관계·트랜잭션을 담는다.
- [Satellite](../concepts/data-vault-satellite.md) — 업무 키·관계의 맥락(속성)과 그 변경
  이력을 담는다.
- 링크가 트랜잭션을 표현할 때가 많아 [차원 모델](../concepts/dimensional-modeling.md)의
  [팩트(fact)](../concepts/fact-table.md)를 만드는 기반이
  되곤 하지만, 이는 경험칙일 뿐이다 — 비트랜잭션 링크(예: 공항 간 연결 존재)도
  정상적인 모델이다 (§4.2.2, p.109).[^linstedt2016]
- 확장은 기존 모델 무변경으로 이뤄진다: 새 정보가 필요하면 새 허브를 만들고
  링크로 기존 허브에 연결한다. 기존 ETL은 리팩터링이 필요 없다 (§4.4.2, pp.126–127).[^linstedt2016]

이 장의 논리 표기는 Visual Data Vault(visualdatavault.com)를 쓴다 (p.106).[^linstedt2016]

## 제3자가 보는 Data Vault — 데이터 엔지니어링 개론의 서술

위 서술은 Data Vault 창시자 쪽(linstedt2016)의 자기 서술이다. 아래는 **인몬·킴벌과 나란히
셋째 접근으로 소개하는 개론서**의 요약이다. 개론서는 자기 서술이 **겉핥기이며 각각의 복잡성과
뉘앙스를 거의 정당하게 다루지 못한다**고 미리 밝힌다 (8장, p.295).[^reis2022]

- 무엇이 다른가 — **킴벌과 인몬이 데이터 웨어하우스 안의 업무 로직 구조에 초점을 맞추는 반면
  Data Vault는 데이터 모델링에 다른 접근을 제공한다. 1990년대 Dan Linstedt가 만든 Data Vault
  방법론은 원천 시스템 데이터의 구조적 측면을 그 속성에서 분리한다. 업무 로직을 팩트·차원이나
  고도로 정규화된 테이블로 나타내는 대신, Data Vault는 단순히 원천 시스템의 데이터를 소수의 목적
  특화 테이블에 삽입 전용 방식으로 직접 적재한다** (8장, p.301).[^reis2022]
- **그리고 개론서가 이 접근의 가장 날카로운 특징으로 지목하는 것** — **당신이 배운 다른 데이터
  모델링 접근과 달리, Data Vault에는 좋은·나쁜·표준(conformed) 데이터라는 개념이 없다** (8장,
  p.301).[^reis2022]
  - 이것은 위 [왜 business key 중심인가](#왜-business-key-중심인가) 절이 드는 **투명성과
    감사 가능성**의 다른 표현이다 — 적재 시점에 판정하지 않으므로 원천이 준 것이 그대로
    남는다. 창시자 쪽은 이것을 *감사 가능성*이라는 이점으로 서술하고, 개론서는 *판정의 부재*
    라는 구조적 사실로 서술한다. 같은 성질의 두 각도다.
- 왜 그렇게 하는가 — **2022년 저술 시점의 데이터는 빠르게 움직이고 데이터 모델은 민첩하고 유연하고 확장
  가능해야 한다. Data Vault 방법론은 이 필요를 충족하는 것을 목표로 한다. 이 방법론의 목표는
  업무의 데이터가 진화하는 동안에도 데이터를 가능한 한 업무에 밀착시켜 유지하는 것이다** (8장,
  p.301).[^reis2022]
- 세 테이블 — **Data Vault 모델은 세 주요 테이블 유형으로 이뤄진다: 허브·링크·새틀라이트. 요컨대
  허브(hub)는 업무 키를 저장하고, 링크(link)는 업무 키 사이의 관계를 유지하며,
  새틀라이트(satellite)는 업무 키의 속성과 맥락을 나타낸다. 사용자는 허브를 질의하고, 허브는 질의의
  관련 속성을 담은 새틀라이트 테이블로 연결된다** (8장, p.302).[^reis2022]
  - **위 [세 가지 기본 엔티티](#세-가지-기본-엔티티) 절의 원문 인용과 같은 분담**이다. 개론서가
    더한 것은 **질의 경로**의 명시다 — 허브에서 시작해 새틀라이트로 간다.
- 허브의 표준 필드 넷 (8장, p.302):[^reis2022]
  - **해시 키(hash key) — 시스템 사이에서 데이터를 조인하는 데 쓰이는 기본 키. 계산된 해시
    필드(MD5 또는 유사)다.**
  - **적재 날짜(load date) — 데이터가 허브에 적재된 날짜.**
  - **레코드 소스(record source) — 고유 레코드를 얻은 원천.**
  - **업무 키(business key(s)) — 고유 레코드를 식별하는 데 쓰이는 키.**
  - 불변성 — **허브가 삽입 전용이며 허브의 데이터는 변경되지 않는다는 점에 유의하는 것이 중요하다.
    데이터가 일단 허브에 적재되면 그것은 영구적이다** (8장, p.302).[^reis2022]
  - 설계의 첫 질문 — **허브를 설계할 때 업무 키를 식별하는 것이 결정적이다. 스스로 물으라:
    식별 가능한 업무 요소는 무엇인가? 달리 말해 사용자는 흔히 데이터를 어떻게 찾는가? 이상적으로
    이는 조직의 개념 데이터 모델을 지으면서, Data Vault를 짓기 시작하기 전에 발견된다** (8장,
    p.302).[^reis2022] 해시 키의 상세는
    [Data Vault의 해싱](../concepts/hashing-in-data-vault.md)에 있다.
- 링크 — **링크 테이블은 허브 사이 업무 키의 관계를 추적한다. 링크 테이블은 이상적으로 가능한 가장
  낮은 grain에서 허브를 연결한다. 링크 테이블이 다양한 허브의 데이터를 연결하므로 그것들은 다대다다.
  Data Vault 모델의 관계는 직관적이며 링크의 변경을 통해 다뤄진다. 이는 기저 데이터가 바뀌는 필연적
  사건에 훌륭한 유연성을 제공한다. 새 관계를 나타내기 위해 업무 개념(또는 허브)을 잇는 새 링크를
  만들기만 하면 된다. 그게 다다** (8장, p.303).[^reis2022]
- 새틀라이트 — **키·적재 날짜·레코드 소스를 수반하는 허브와 링크 사이의 관계를 서술했다. 이 관계가
  무엇을 뜻하는지 어떻게 감을 잡는가? 새틀라이트는 의미와 맥락을 주는 서술적 속성이다. 새틀라이트는
  허브나 링크 어느 쪽에도 연결될 수 있다. 새틀라이트에 요구되는 유일한 필드는 부모 허브의 업무 키와
  적재 날짜로 이뤄진 기본 키다. 그 너머로 새틀라이트는 말이 되는 만큼의 속성을 담을 수 있다** (8장,
  p.304).[^reis2022]
- 다른 테이블 유형과 조합 — **PIT(point-in-time)와 브리지 테이블을 포함한 다른 유형의 Data Vault
  테이블이 존재한다. 여기서 다루지는 않지만 Data Vault가 꽤 포괄적이기 때문에 언급한다. 우리 목표는
  단순히 Data Vault의 힘에 대한 개관을 주는 것이다** (8장, p.305).[^reis2022]
- **업무 로직이 놓이는 시점이 다르다** — **논한 다른 데이터 모델링 기법과 달리 Data Vault에서는
  이 테이블들의 데이터가 질의될 때 업무 로직이 만들어지고 해석된다. Data Vault 모델이 다른 데이터
  모델링 기법과 함께 쓰일 수 있음을 알아 두라. Data Vault가 분석 데이터의 착륙 지대가 되고, 그 뒤
  데이터 웨어하우스에서 별도로 — 흔히 스타 스키마를 써서 — 모델링되는 것은 드문 일이 아니다.
  Data Vault 모델은 NoSQL과 스트리밍 데이터 원천에도 적응될 수 있다. Data Vault는 거대한 주제이며
  이 절은 단순히 그 존재를 알리기 위한 것이다** (8장, p.305).[^reis2022]
  - **"착륙 지대 + 하류 스타 스키마"라는 이 조합**은 창시자 쪽이
    [Data Vault 아키텍처](../concepts/data-vault-architecture.md)에서 *인포메이션 마트*로
    부르는 계층과 같은 배치다. 낱말만 다르다 — 개론서는 그것을 "데이터 웨어하우스에서 별도로
    모델링"이라 부른다.
  - 스트리밍 적응 가능성은 같은 장의 다른 자리에서 다시 나온다 — **몇몇은 스트리밍 데이터
    모델링의 선택지로 Data Vault를 제안했다** (8장, p.308).[^reis2022] 이 서술은 개론서가
    킴벌 모델에 대해 **배치에만 적절하고 스트리밍에는 적절하지 않다**고 판정한 것 (8장,
    p.301)[^reis2022]과 짝을 이룬다 — **세 접근 중 스트리밍 후보로 지목된 것은 Data Vault
    하나다.**

[^reis2022]: Reis & Housley 2022, 8장 "Queries, Modeling, and Transformation"

[^linstedt2016]: Linstedt & Olschimke 2016, 4장 "Data Vault 2.0 Modeling"
