## 버전 조건

> **버전 조건**: 아래 도구와 패키지 이름은 **2025년 저술 시점**의 것이다 — protoc,
> grpcio-tools와 그것이 노출하는 `grpc_tools.protoc` 모듈, Bazel, buf, ghz, Protovalidate,
> grpcurl이다. 생성되는 파일의 이름과 위치가 언어마다 다르다는 것도 그 시점의 사정이고,
> 이 KB는 어느 것에 대해서도 공표된 지원 종료일을 갖고 있지 않으므로 `stale_after`를 적지
> 않는다.

> **버전 조건**: 저자들은 `syntax = "proto3"`을 두고 **"이 프로토버프는 최신 프로토콜 버퍼
> 판을 쓴다"**고 적는다 (8장, p.246).[^dynowski2025] **이 KB의
> [프로토콜 버퍼와 필드 태그](../concepts/protocol-buffers-encoding.md)에는 다른 소스가 적은
> 사실이 함께 있다** — 2024년에 나온 Protobuf Editions가 `syntax="proto2"`·`syntax="proto3"`
> 대신 `edition="2023"`처럼 적게 하며 이후의 판 번호 매김을 대체한다는 것이다. 둘 다 2025년에
> 나온 책이다. **이 페이지는 이 책이 적은 대로 옮기고, 판 표기 쪽의 정본은 그 페이지로
> 둔다.**

## 형식이 다를 때 누가 맞추는가

- **문제부터** — **데이터 형식은 엔디언(바이트가 메모리에 저장되는 순서)·데이터 크기(예: 32비트
  또는 64비트)·문자 인코딩(예: ASCII 또는 유니코드) 같은 속성에서 갈릴 수 있다** (8장
  §"Protobuf Serialization", p.245).[^dynowski2025]
- **내부적으로 서로 다른 형식을 쓰는 네트워크 서비스를 다룰 때 접근이 셋 있다** (8장,
  p.245):[^dynowski2025]
  - **보내는 쪽이 맞추기(sender-makes-right)** — **보내는 서비스마다 받는 서비스가 쓰는 모든
    형식을 알게 하는 것**이고, **보내는 쪽이 받는 쪽이 쓸 올바른 형식으로 메시지를 보내야**
    한다.
  - **받는 쪽이 맞추기(receiver-makes-right)** — 반대다. **보내는 쪽의 내부 형식 그대로 보내고
    받는 쪽이 자기 내부 형식으로 변환하게 하는 것**이고, **받는 쪽이 보내는 쪽들이 쓰는 모든
    형식을 알아야** 한다.
  - **정준 중간형(canonical intermediate)** — **보내는 쪽과 받는 쪽이 모두 하나의 공통 형식을
    쓰게 하는 것**이다. **변환의 과업을 보내는 쪽과 받는 쪽 양쪽에 지우되 지원해야 할 변환
    형식의 수를 하나로 줄인다.** 이 접근의 실무적 실현이 **직렬화와 역직렬화**다.
- 그 실현이 무엇인지의 규정은 이 책 2장이 갖는다 — 인코딩과 직렬화를 가르는 자리이고
  [데이터 인코딩 형식](../concepts/data-encoding-formats.md)에 있다.

## gRPC가 고른 것

- **gRPC는 정준 중간형 접근을 채택하고 기본 직렬화 형식으로 프로토콜 버퍼(줄여서
  프로토버프)를 쓴다** (8장, p.245).[^dynowski2025]
  - 각주가 경계를 그어 준다 — **독립된 기술로서 프로토콜 버퍼의 주된 목표는 데이터 직렬화
    기제를 제공하는 것**이고, **gRPC는 JSON을 비롯한 다른 직렬화 형식도 떠받치도록 설계돼
    있다** (8장, p.245).[^dynowski2025] 곧 **둘의 묶임은 기본값이지 강제가 아니다.**
- **프로토콜 버퍼가 노릇을 하나 더 한다** — **gRPC는 프로토콜 버퍼를 IDL로도 써서, RPC
  메서드와 그 요청·응답 메시지를 정의함으로써 API를 서술한다** (8장,
  p.245).[^dynowski2025]
- **파일에서 바이트까지의 경로** — **프로토버프 정의는 사람이 읽을 수 있는 `.proto` 파일에
  저장된다. 이 파일들 안의 자료 구조는 이진 형식으로 컴파일되며, 그것이 텍스트와 견주어 저장
  크기와 파싱 성능을 개선한다. 네트워크로 메시지를 주고받는 데 이 촘촘한 형식을 쓰는 것이
  gRPC의 높은 성능에 기여한다** (8장, p.245).[^dynowski2025]

## proto 파일이 정하는 것

**예제 8-1이 단항 RPC 하나짜리 정의이고, 저자들이 그 파일의 각 줄이 무엇을 정하는지 하나씩
짚는다** (8장, pp.246–247).[^dynowski2025]

- **판 표기** — 첫 줄의 `syntax`가 프로토콜 버퍼의 판을 정한다 (8장, p.246).[^dynowski2025]
  위 [버전 조건](#버전-조건) 참조.
- **패키지에 판이 붙는다** — **프로토버프 정의에 가해진 변경을 전하는 데 도움이 되도록 프로토콜
  버퍼는 버저닝을 기본 지원한다.** 예제에서는 **`echo` 패키지에 판 `v1`이 배정된다** (8장,
  p.246).[^dynowski2025] 같은 책 2장이 **gRPC가 패키지와 서비스 이름을 버저닝하는 쪽을
  선호한다**고 적고, 그 전문은 [API 이름과 버저닝](api-naming-and-versioning.md)에 있다.
- **요청과 응답을 따로 둔다** — **프로토버프는 진화를 염두에 두고 설계됐으므로, 앞으로 수정할
  유연성을 위해 RPC마다 요청 메시지와 응답 메시지를 따로 정의할 것이 권장된다. 흔한 이름 규약은
  RPC 이름 뒤에 `Request`와 `Response` 접미를 붙이는 것이다** (8장,
  p.247).[^dynowski2025]
  - **권장되지 않는 대안도 명시된다** — **gRPC 튜토리얼에서 가끔 보이지만 프로토버프 진화의
    관점에서는 말리는 방식이 요청·응답을 따로 두는 대신 메시지 하나만 정의하는 것**이다 (8장,
    p.247).[^dynowski2025]
  - 각주에 권장이 하나 더 있다 — **메시지마다 파일을 따로 두는 것도 권장되나, 이 책은 읽기
    쉬움을 위해 그 권장을 따르지 않는다** (8장, p.247).[^dynowski2025]
- **주석이 문서다** — **`//`로 시작하는 줄을 프로토버프는 주석으로 다룬다. 프로토버프 파일은
  주석으로 쓰인 나의 API 문서 노릇을 한다** (8장, p.247).[^dynowski2025] 그리고 **서비스와
  RPC 메서드 정의 위에 놓인 주석 줄은 자동 생성된 서비스 문서에 포함된다** (8장,
  p.247).[^dynowski2025]
- **필드 번호가 규칙을 하나 진다** — **필드 번호는, 여기의 1처럼, 주어진 메시지 안에서 다시
  쓰여서는 안 된다** (8장, p.247).[^dynowski2025] 그 번호가 인코딩에서 무슨 일을 하는지는
  [프로토콜 버퍼와 필드 태그](../concepts/protocol-buffers-encoding.md)가 갖는다.
- **서비스와 rpc** — **`service` 블록이 gRPC 서비스를 정의하고 서비스는 여러 RPC를 담을 수
  있다. `rpc`로 시작하는 줄이 RPC 메서드를 정의한다. RPC는 행위를 나타내고 그 이름은 보통
  동사로 시작한다** (8장, p.247).[^dynowski2025]
- **인자가 하나뿐이라는 제약** — **어떤 RPC 메서드도 인자(메시지) 하나만 받고 하나만 돌려준다.
  다만 메시지는 필드를 여럿 담을 수 있고, 메시지는 중첩될 수 있으며 다른 메시지 타입을 필드로
  쓸 수 있다** (8장, p.247).[^dynowski2025] 이 제약이 아래
  [메시지를 메시지의 필드로 쓰기](#메시지를-메시지의-필드로-쓰기)를 부른다.
- **gRPC 서비스는 RPC 정의 하나 이상을 담는다** (8장, p.246).[^dynowski2025]

## 네 유형이 한 파일에서 보이는 모양

**예제 8-8이 단항짜리 정의를 늘려 RPC 유형 넷을 모두 담은 것이고, 저자들이 그것을 프로토버프의
확장성을 보이는 예로 든다** (8장, p.258).[^dynowski2025] **스트리밍 쪽은 `stream` 키워드로
표시된다.**

```proto
// src/grpc/src/echo/echo/proto/echo/v1/echo.proto

syntax = "proto3";

package echo.v1;

message DemoUnaryRequest {
  string content = 1;
}

message DemoUnaryResponse {
  string content = 1;
}

message DemoServerStreamingRequest {
  string content = 1;
}

message DemoServerStreamingResponse {
  string content = 1;
}

// Analogous Request and Response messages follow for the remaining RPC types,
// which we skipped for readability ...

// The service echoes back the content received from the client.
service EchoService {
  // This method demonstrates unary RPC.
  rpc DemoUnary(DemoUnaryRequest) returns (DemoUnaryResponse);

  // This method demonstrates server streaming RPC.
  rpc DemoServerStreaming(DemoServerStreamingRequest)
      returns (stream DemoServerStreamingResponse);

  // This method demonstrates client streaming RPC.
  rpc DemoClientStreaming(stream DemoClientStreamingRequest)
      returns (DemoClientStreamingResponse);

  // This method demonstrates bidirectional streaming RPC.
  rpc DemoBidirectionalStreaming(stream DemoBidirectionalStreamingRequest)
      returns (stream DemoBidirectionalStreamingResponse);
}
```

- **키워드가 붙는 자리가 곧 유형이다** — `stream`이 **반환 쪽에만** 붙으면 서버 스트리밍,
  **인자 쪽에만** 붙으면 클라이언트 스트리밍, **양쪽에** 붙으면 양방향이다. 어느 쪽에도 없으면
  단항이다. 네 유형이 무엇을 뜻하는지는
  [gRPC와 RPC 스타일](grpc-and-rpc-style.md)에 있다.
- 위 주석 두 줄이 **원문 그대로**다 — 저자들이 나머지 유형의 요청·응답 메시지를 읽기 쉬움을
  위해 생략했다고 파일 안에 적어 두었다.

## 메시지를 메시지의 필드로 쓰기

**enricher 서비스의 프로토버프가 합성을 보인다** (8장, pp.268–269).[^dynowski2025]

- **import가 재사용을 준다** — 정의를 **`google/protobuf/timestamp.proto`에서 가져오고**, 그
  파일은 **프로토버프 소스 저장소에서 왔으나 파이썬에서는 grpcio-tools 패키지의 일부로
  배포된다.** 저자들의 판정이 한 줄이다 — **import 기능이 프로토버프의 합성 가능성(결합과
  재사용)을 가능하게 한다** (8장, p.269).[^dynowski2025]
- **직접 정의한 메시지도 필드 타입이 된다** — 예제에서 **City 메시지가 WeatherForecast 메시지의
  필드로 쓰인다** (8장, p.269).[^dynowski2025]
- **내장 Timestamp의 구성이 명시된다** — **Timestamp 메시지 자신은 `int64 seconds = 1;`과
  `int32 nanos = 2;` 두 필드로 이뤄져 있고, 그것이 나노초 해상도를 갖는다는 것을 보인다** (8장,
  p.269).[^dynowski2025]
- **기본값 규칙이 여기서 쓰인다** — **프로토버프 필드에는 기본값이 있고 int64와 int32 모두
  기본값이 0이다.** 그래서 예제는 **nanos 필드를 기본값에 두고, 그 결과 timestamp 필드는 유닉스
  기원 1970-01-01T00:00:00Z 이래의 UTC 초를 나타낸다** (8장, p.269).[^dynowski2025]
  - 그 기본값은 리플렉션이 내놓는 메시지 틀에서 눈으로 확인된다 —
    [gRPC와 RPC 스타일](grpc-and-rpc-style.md)의 문서화 절에 있다.

## 진화 규칙은 여기서 얇다

**저자들 자신이 이 장에서 진화를 깊이 다루지 않겠다고 밝힌다** — **후진 호환이나 전진 호환이
되는 프로토버프 변경의 세부는 들어가지 않는다**고 적고 규칙 셋만 적는다 (8장,
p.248).[^dynowski2025]

- **요청에 새 필드를 더해도 서버가 실패하지 않는다. 서버는 알 수 없는 필드를 무시한다.**
- **요청에 있어야 할 필드가 빠지면 그 필드에는 기본값이 배정된다.**
- **프로토버프 메시지에서 필드를 없애려면 먼저 그 필드를 폐기 예정(deprecated)으로 표시할 수
  있다. 클라이언트 코드가 더 이상 그것을 쓰지 않게 되면 프로토버프에서 없앨 수 있으나, 없앤
  필드의 번호는 재사용을 막기 위해 예약되어야 한다.**
- **이 KB의 정본은 이 페이지가 아니다.** 같은 규칙을 더 두껍게 적는 자리가
  [프로토콜 버퍼와 필드 태그](../concepts/protocol-buffers-encoding.md)이고, 그 두 방향의 규정은
  [후진 호환과 전진 호환](../concepts/backward-and-forward-compatibility.md)이 갖는다. **여기서
  되풀이하지 않는다.**
- 저자들이 더 알고 싶으면 보라고 가리키는 것이 프로토버프의 "Language Guide"와 "API Best
  Practices" 문서, 에릭 앤더슨의 강연, 그리고 **buf가 제공하는 서식기와 린터와 깨는 변경
  검출기**다 (8장, p.248).[^dynowski2025]

## 코드 생성은 API 우선의 얼굴이다

- **분류부터** — **기존 API 명세에서 코드를 생성하는 것(자동으로든 손으로든)이 API 우선 접근을
  특징짓는다. gRPC API의 경우 프로토버프가 API 인터페이스 명세다** (8장 §"Code Generation",
  p.250).[^dynowski2025] API 우선이라는 낱말의 규정은 같은 책 1장의 것이고
  [API 수명 주기](api-lifecycle.md)에 있다.
- **생성된 코드의 지위가 규약으로 정해진다** — **프로토버프에서 생성된 코드는 개발자가 고칠
  것이 아니다. 대신 실제 애플리케이션 기능을 구현하려고 확장하는 바탕으로 개발자가 쓴다** (8장,
  p.250).[^dynowski2025]
- **컴파일러와 그 감싸개** — **프로토버프 컴파일러는 protoc이라 불린다.** 그리고 **프로그래밍
  언어마다 자기 protoc 감싸개를 가질 수 있고**, 파이썬의 grpcio-tools 패키지가 그 예로
  **`grpc_tools.protoc` 모듈을 통해 protoc을 노출한다.** 없으면 **일반 protoc 컴파일러를 쓸 수
  있다** (8장, p.250).[^dynowski2025]
  - 저자들이 각주에 보안 주의를 하나 붙인다 — **패키지 이름과 모듈 이름이 다르다는 점에
    유의하고, 인터넷에서 소프트웨어를 설치할 때 타이포스쿼팅 보안 공격을 피하도록 경계하라**
    (8장, p.250).[^dynowski2025]
  - 다른 각주는 정적 생성이 유일한 길은 아니라고 적는다 — **여러 언어에서 정적 코드 생성을
    피하고 애플리케이션 클라이언트와 서버에서 프로토버프 파일을 직접 쓰는 것도 가능하되, 이런
    쓰임은 덜 흔하다** (8장, p.250).[^dynowski2025]

## 생성되는 파일 둘

**파이썬에서 코드 생성이 파일 둘을 만든다** (8장, p.251).[^dynowski2025]

- **`echo_pb2.py`** — **메시지와 서비스와 RPC 메서드를 위한 이진 자료 구조와 메타데이터를
  담는다.**
- **`echo_pb2_grpc.py`** — **gRPC 클라이언트와 서버 양쪽을 위한 이른바 스텁 코드와, gRPC 서버
  생성을 쉽게 하는 추가 코드를 담는다.**
- **이름과 위치가 언어마다 다르다** — **생성되는 파일의 이름과 위치는 프로그래밍 언어마다
  다르다** (8장, p.250).[^dynowski2025]

## 스텁이 하는 일

- **규정 한 줄** — **gRPC 스텁은 메시지를 직렬화하고 역직렬화하며 RPC를 부를 인터페이스를
  제공한다** (8장, p.251).[^dynowski2025]
- **이름에 그 노릇이 드러난다** — 클라이언트 스텁을 만드는 클래스는 **`Stub` 접미**를 쓰고,
  **gRPC가 떠받치는 대부분의 언어가 생성된 클라이언트 스텁 코드에 stub이라는 낱말을 넣는다**
  (8장, p.252).[^dynowski2025] 서버 쪽 스텁은 **일반적으로 핸들러(handler)라 불리고**, 들어오는
  요청을 역직렬화하고 나가는 응답을 직렬화한다 (8장, p.252).[^dynowski2025]
- **경로가 코드에 박힌다** — **주어진 RPC 서비스의 URI 경로는 gRPC 서버가 서비스하는, 클라이언트
  스텁이 부를 메서드를 담는다. gRPC는 자동 생성된 코드에 URI를 하드코딩함으로써 네트워크 호출의
  세부를 개발자에게서 감춘다** (8장, p.252).[^dynowski2025] **이 문장이 이 KB의
  [원격 프로시저 호출의 문제](../concepts/remote-procedure-call-problems.md)가 경고하는 자리와
  같은 곳을 가리킨다** — 대조는 그 페이지에 있다.
- **직렬화의 단위가 메시지 전체다** — `SerializeToString()`과 `FromString()`이 **요청과 응답
  메시지 전체에 대해 동작하고 메시지의 개별 필드에 대해서는 동작하지 않는다.** 그리고 **String이라는
  이름이 시사하는 것과 달리 그것은 바이트 열을 뜻한다** — 파이썬의 `bytes`이지 `str`이 아니다
  (8장, p.252).[^dynowski2025] 같은 주의가 인터셉터 절에서 한 번 더 되풀이된다 (8장,
  p.270).[^dynowski2025]
- **서비서(servicer)가 서비스 하나의 단위다** — **서비서 클래스는 하나의 gRPC 서비스에 속한 RPC
  메서드 전부를 담고, gRPC 서버 하나가 여러 서비서를 서비스할 수 있다** (8장,
  p.252).[^dynowski2025]

## 생성 코드를 버전 관리에 둘 것인가

**저자들이 권고 둘을 나란히 놓고 조건을 갈라 준다** (8장, p.250).[^dynowski2025]

- **구글의 gRPC 개발자들의 권고**는 **생성된 파일을 빌드 산출물로 다루고, 별도의 디렉터리에
  두며, 버전 관리 아래 저장하지 않는 것**이다. **구글의 Bazel 도구가 하는 일이 그것이다.**
- **그러나 더 작은 파이썬 gRPC 프로젝트에서는** 생성된 파일을 **애플리케이션 코드의 나머지와
  함께 버전 관리 아래 저장하고 파이썬 고유의 방식으로 패키징하는 것이 프로젝트 유지보수를 쉽게
  할 수도 있다.**
  - 각주가 그 근거를 적는다 — 이 접근은 **추가 빌드 도구를 들여오는 데서 오는 운영상의 부담을
    피한다** (8장, p.250).[^dynowski2025] 그 부담을 그리는 강연 인용이 각주에 붙어 있으나
    이 페이지는 옮기지 않았다.
- **`--proto_path` 인자**는 **생성된 파일을 프로토버프 파일이 있는 디렉터리에 놓는 데 쓸 수
  있다** (8장, p.250).[^dynowski2025]

## 계약이 사 주는 것

**절충 절의 장점 가운데 계약 쪽 항목이다** (8장 §Trade-Offs, p.279).[^dynowski2025]

- **프로토콜 버퍼의 메시지와 서비스가 클라이언트와 서버 사이에 타입 붙은 API 계약을 정의하고,
  그 계약은 맞춤 애플리케이션 로직 구현의 바탕으로 자동 생성된 코드를 쓰게 함으로써 강제된다.**
- **프로토버프 파일은 protoc 플러그인으로 확장될 수 있다** — 필드 검증 로직을 넣는 데 쓰이는
  **Protovalidate**가 그 예다.
- **gRPC로 일한다는 것은 API 우선 접근이고, 깨는 변경을 만들기 전에 계획을 요구한다.**
- 이 KB의 계약 층과 맞닿는다 — 계약을 얼마나 조일 것인가의 눈금은
  [계약의 스펙트럼](../concepts/contract-spectrum.md)이 갖고, 계약이 깨질 때 무엇을 할
  것인가는 [계약을 깨는 변경의 관리](../concepts/managing-breaking-api-changes.md)가 갖는다.

## 코드 생성이 청구하는 것

**같은 절의 단점 쪽이다** (8장 §Trade-Offs, pp.279–280).[^dynowski2025]

- **판을 맞추는 일** — **맞는 판의 protoc으로 코드를 생성하거나(구글의 gRPC 개발자들이 권하는
  접근) 생성된 코드를 클라이언트와 서버에 배포하는 데서 운영상의 도전이 생긴다.**
- **구조를 미리 잡는 일** — **어느 쪽이든 프로젝트의 진화를 떠받치려면 프로토버프 디렉터리
  구조와 메시지·서비스 정의가 조직돼야 한다.**
- **배포 파이프라인** — **gRPC 프로젝트의 배포에는 전용 CI/CD 프로세스가 필요하다.**
- **관례가 딸려 온다** — **생성된 코드가 내 프로젝트라면 쓰지 않았을 프로그래밍 관례를 들여올
  수 있다.**
- **도구 쪽 청구서도 함께 적힌다** — **권장되는 프로토버프 쓰임은 Bazel 같은 전용 코드 의존
  관리 도구를 요구하고, 편집기와 IDE는 gRPC 지원이 없는 경향이 있으며, 생산 환경 관련 기능은
  서드파티 도구가 제공한다**(서식·린팅·깨는 변경 검출은 buf, 부하 시험은 ghz) (8장,
  p.280).[^dynowski2025]
- **이 청구서가 이 KB의 앞선 판정과 같은 방향이다.** 생성된 이진 스텁이 클라이언트와 서버의
  배포를 묶는다는 진단이
  [원격 프로시저 호출의 문제](../concepts/remote-procedure-call-problems.md)에 이미 있다. **이
  책은 그 묶임을 "배포와 조직의 문제"로 적고 그쪽은 "타입이 확장만 가능해진다"로 적는다.
  겨루지 않고 같은 사태의 두 면이다.** #hypothesis 두 소스가 이 대응을 적지 않는다.
