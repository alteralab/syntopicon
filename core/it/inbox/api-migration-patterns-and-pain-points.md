## 이 페이지가 담는 것과 담지 않는 것

- **담는 것** — 이 책 8장 "Redesigning Applications to API-Driven Architectures"의 뒤
  절반(pp.202–207)이다. **이행 패턴 셋과 고통 지점 셋**이다.
- **담지 않는 것** — 같은 장의 앞부분(왜 API가 지렛대인가, 응집과 결합, 최종 상태 선택지 넷,
  진화 과정을 관리하는 여섯 걸음)은 [API 주도 재설계와 이음매](api-driven-redesign-and-seams.md)가
  갖는다. **인프라를 클라우드로 옮기는 쪽**은
  [API 인프라로 하는 클라우드 이전](cloud-migration-with-api-infrastructure.md)이 갖는다.

## API로 체계를 진화시키는 패턴 셋

- **이 절이 서는 자리** — **API는 체계를 현대적 아키텍처로 진화시키고 새 기능과 변경을 들이는 데
  강력한 추상을 제공한다.** 3장과 4장에서 본 **게이트웨이와 서비스 메시 기반 구성물이 게이트웨이를
  쓴 운영상의 이주(operational migration)를 가능하게 한다.** **진화적 변경을 만들 때 진화 기간의
  일차 고려는 진화의 위험을 완화하고 이득을 가능한 한 이르게 최대화하는 것**이다 (8장
  §"Architectural Patterns for Evolving Systems with APIs", p.202).[^gough2022]

### 교살자 무화과

- **이름의 유래를 생물 쪽으로 푼다** — **교살자 무화과(strangler fig)는 기존 나무 둘레에서 자라는
  열대 무화과 여러 종 가운데 하나**다. **교살자 무화과가 숙주를 질식시키고 경쟁에서 이기는 일이
  잦지만, 교살자 무화과에 싸인 나무가 열대 폭풍을 견딜 가능성이 더 크다는 증거도 있어 그 관계가
  다소 상리공생적일 수 있음을 시사한다** (8장 §"Strangler Fig", p.203).[^gough2022]
  - **저자들이 그 비유를 진화적 아키텍처의 목표에 붙인다** — **궁극적으로 그것이 진화적 아키텍처의
    목표, 곧 바뀌는 체계를 지탱하는 것이고, 그 결과가 앞서 있던 것을 완전히 걷어 내는 일일 수
    있다** (8장, p.203).[^gough2022]
  - **이 KB가 이 패턴의 정본으로 갖는 페이지가 따로 있다** —
    [모놀리스 분해 패턴](monolith-decomposition-patterns.md)이다. **이 책이 더하는 것은 위 생물학적
    단서(상리공생)와 아래 두 구현 갈래**다.
- **기제** — **옛 기제가 여전히 자리에 있는 동안 애플리케이션의 새 컴포넌트를 들이는 것**으로
  이루고, **목표는 새 API 기반 접근으로 점차 이주하는 것**이다 (8장, p.203).[^gough2022]
- **구현 갈래 둘을 이 책이 가른다** (8장, pp.203–204):[^gough2022]
  - **기능 플래그로 가르는 것** — 5장의 기능 플래그 사례(§"Case Study: Feature Flagging", p.126)를 가리키며 **플래그로 레거시 서비스를
    부를지 새 API 기반 서비스를 부를지 정할 수 있다**고 적는다. **이것은 전에 프로세스 안
    상호작용으로 있던 이음매에 새 API를 들일 때 잘 듣는다.** **그러나 이미 프로세스 밖에서 그
    서비스와 상호작용하는 소비자가 많다면 전부가 기능 플래그를 구현하고 통제하기를 기대하는 것은
    비현실적이다.**
  - **프록시나 게이트웨이를 앞에 두는 것** — **API 상호작용 앞에 프록시나 게이트웨이를 두어 레거시
    구현이나 새 구현으로 라우팅한다. 이것은 프록시를 쓴 파사드의 일종이고, API 소비자는 같은 API를
    쓰면서 뒤에서 한 서비스에서 다른 서비스로 이주가 일어나는 것을 알지 못한다.**
- **이 패턴을 뒤에서 관리하는 일의 어려움 넷** (8장, p.204):[^gough2022]
  - **새 컴포넌트를 들이는 것 자체가 단일 장애점이나 병목이 될 수 있다** — 완화하지 않으면 그렇다.
  - **프록시가 업무 로직을 떠맡아서는 안 된다** — 그러면 **이주가 끝났을 때 걷어 내기 어려워진다.**
  - **레거시와 현대 프로세스를 나란히 운영하는 것**은 **두 서비스 사이의 데이터 정합성을 보장하는
    도전**이다.
  - **그 도전들을 넘는 더 많은 지침은 *Monolith to Microservices*에 있다**고 넘긴다.
- **그림 8-2가 본문에 없는 것을 보여 준다** — 기능 플래그 배치에서 **레거시 쪽 참석자 모듈과
  새 참석자 서비스가 각자 별도의 데이터 저장소를 갖는 것으로 그려진다**(위 "데이터 정합성"의 그림
  쪽 근거다). 그리고 **캡션은 "컨테이너 다이어그램"(container diagram)이라 적는데 상자의 C4 유형
  라벨은 전부 `[Component: Package/Module]`과 `[Component: Software]`**다 (8장 그림 8-2,
  p.203).[^gough2022] 본문은 그 그림을 **"C4 다이어그램"**이라고만 부른다.

### 파사드와 어댑터

- **둘의 자리** — **파사드와 어댑터는 현대적 서비스로 이주하는 것을 도울 수 있는 잘 알려진
  패턴**이고, **교살자 무화과 패턴은 파사드의 일종으로 API 호출을 가로채고 뒤의 복잡성을 감춘다**
  (8장 §"Facade and Adapter", p.204).[^gough2022]
- **어댑터가 필요해지는 흔한 상황** — **이미 어떤 형태의 API를 쓰고 있는 기존 대규모 분산
  애플리케이션**이다. **서비스 간 통신이 SOAP-RCP나 다른 구식 프로토콜로 돌고 있을 수 있고**,
  **어댑터가 주어진 SOAP 요청을 새 RESTful API 호출로 변환하는 컴포넌트를 들여 아키텍처의 진화를
  도울 수 있다** (8장, p.204).[^gough2022]
  - **단서 둘** — **프로토콜 재작성은 올바르게 구현하기 어려울 수 있고**, **응집을 줄이거나 결합을
    들이지 않도록 조심해야** 한다 (8장, p.204).[^gough2022]
  - **원문에 오식이 하나 있다** — 본문이 **"SOAP-RCP"**라 적는다 (8장, p.204).[^gough2022] 이
    KB는 철자를 고치지 않고 그대로 옮긴다.
- **레거시만의 이야기가 아니다** — **1장에서 동서 통신에 인기 있고 효과적인 기술로 gRPC를 봤는데,
  grpc-gateway 프로젝트를 쓰면 뒤에서 gRPC 표현으로 변환되는 RESTful JSON 종단점을 내보일 수
  있다** (8장, p.204).[^gough2022] 그 도구가 명세 쪽에 지우는 대가는
  [OpenAPI 명세 실무](openapi-specification-practice.md)에 있다.
- **둘을 가르는 선이 이 절의 실질이다** (8장, p.204):[^gough2022]
  - **파사드와 어댑터는 *끼어든다*는 점에서 아주 비슷하다.**
  - **파사드는 대개 어댑터보다 덜 복잡하다** — **전통적인 API 게이트웨이는 단순히 API 요청을
    라우팅하는 반면, 어댑터는 대상 애플리케이션이 이해하는 표현으로 변환하는 책임을 진다.**
  - **목차에 없는 상자가 그 선을 조문으로 적는다** — **API 게이트웨이가 파사드 패턴으로 행동하다가
    어댑터 패턴 쪽으로 선을 넘으면 결합이 즉시 늘어난다. 이 과업에 여전히 맞는 구성 요소를 쓰고
    있는지 꼭 물어라** (8장, p.204).[^gough2022]
  - 게이트웨이가 파사드·어댑터로 결합을 줄이는 쓰임의 정본은
    [API 게이트웨이의 규정과 기능과 배치](api-gateway-capabilities-and-deployment.md)다.

### API 층 케이크 — 피하라고 권하는 패턴

- **이름과 계보** — **엔터프라이즈 맥락에서 많이 이야기되는 API 이주 패턴이 "계층화된 API" 또는
  "API 층 케이크"(API Layer Cake)이고, 전통적 엔터프라이즈 모놀리식 애플리케이션에서 보이던
  "관심사의 분리" 계층화 패턴 위에 세워진다** (8장 §"API Layer Cake", p.205).[^gough2022]
- **원래 모양** — **2000년대에 자바나 .NET 엔터프라이즈 애플리케이션에서 애플리케이션 기능을 일련의
  계층화된 티어(예: 프레젠테이션·애플리케이션·도메인·데이터 저장소 티어)로 구현하는 것이 모범
  사례로 여겨졌다.** **핵심 착상은 애플리케이션에 들어오는 각 사용자 요청이 각 티어/층을 차례로
  내려갔다가 올라온다는 것**이었다 (8장, p.205).[^gough2022]
  - **그 패턴의 대가를 한 문장으로 적는다** — **각 티어에 특유한 기능의 추상과 재사용을 허용하되,
    기능의 종단 한 조각이 흔히 여러 층을 고치게 만드는 대가가 따랐다 — 곧 각 티어 층 안의 응집이
    업무 기능 한 단위를 내기 위한 티어들 사이의 높은 결합을 대가로 왔다** (8장,
    p.205).[^gough2022]
  - 이 KB가 그 계층 패턴 자체를 다루는 자리는 [계층 아키텍처](layered-architecture.md)다.
- **현대적 판** — **가트너의 *Pace-Layered Application Strategy*에서 보이고**, **각 API 또는
  마이크로서비스 층에 새 이름이 쓰인다 — 프레젠테이션이 대략 참여 체계(SoE), 애플리케이션이 차별화
  체계(SoD), 데이터 저장소가 기록 체계(SoR)로 옮겨진다** (8장, p.205).[^gough2022] **이 KB는 그
  가트너 문서를 원전으로 확인하지 않았다** — 이 책을 통한 2차 경유다.
- **판정이 분명하다** (8장, p.205):[^gough2022]
  - **시간이 지나며 이 패턴은 나쁜 평판을 얻었고, 특히 그것을 구현한 레거시 체계들이 점점 더
    진화시키기 어려워지면서 그랬다.**
  - **이 패턴은 아키텍트와 개발자가 지름길을 택하도록 부추긴다** — **층을 하나 더 부르지 않으려고
    여러 층 사이에 기능을 중복시키거나**, **요청을 다룰 때 층을 우회하는 것(예: 프레젠테이션 티어가
    데이터 저장소 티어와 직접 통신하는 것)**이다.
  - **우리는 일반적으로 이 패턴을 쓰지 않기를 권한다.**

## 고통 지점과 기회를 찾기

- **어디를 먼저 손댈 것인가의 절이다** — **평판이 나쁜 체계나 코드베이스 부분을 건드리지 않고
  피하고 싶은 유혹이 흔하고, 어떤 고통 지점은 심각한 장애를 해결하기 전까지는 늘 명백하지 않다**
  (8장 §"Identifying Pain Points and Opportunities", p.205).[^gough2022]
- **저자들의 조문** — **좋은 위기를 낭비하지 마라. 체계 안의 문제적 컴포넌트를 식별하고 목록으로
  정리하는 것이 알려진 문제를 추적하고 개선하는 데 도움이 된다** (8장, p.205).[^gough2022]

### 업그레이드와 유지보수 문제

- **업그레이드와 보고된 버그가 어디서 일어나는지 식별하면 "우선 처리 목록"(hit list)을 만들 수
  있다** (8장 §"Upgrade and Maintenance Issues", p.205).[^gough2022] **지켜볼 신호 다섯**은 이것이다
  (8장, p.206):[^gough2022]
  - **특정 서브시스템의 높은 변경 실패율.**
  - **한 체계에 대해 제기되는 높은 지원 이슈 건수.**
  - **체계나 코드베이스의 특정 부분에 걸린 많은 양의 요동(churn).**
  - **높은 복잡도** — 정적 분석과 순환 복잡도로 식별한다.
  - **필요한 변경이 얼마나 쉬운지 물었을 때 개발 팀이 내보이는 낮은 수준의 확신.**
- **그 신호가 가리키는 기회** — **코드 품질 지표를 더하는 것**이 밑에 깔린 문제의 대략적 안내가
  될 수 있고, **유지보수 이슈나 서브시스템 이슈는 기능을 끄집어낼 API 추상을 들이고 교살자 무화과로
  개선을 밀어붙일 좋은 기회일 수 있다.** 다만 **좋은 코딩 원칙을 따르지 않는다는 코드 냄새일
  수도 있다** (8장, p.206).[^gough2022]

### 성능 문제

- **상한선의 자리** — **서비스 수준 협약(SLA)은 성능을 추적하고 감시할 훌륭한 상한선**이다 (8장
  §"Performance Issues", p.206).[^gough2022]
- **저자들이 짚는 실태** — **많은 애플리케이션이 문제의 유입에 대한 선제적 보호를 짓지 않는다.**
  **팀이 성능 문제를 처음 듣는 것이 직접적인 고객 피드백이거나 프로덕션 모니터링(예: 사용자
  요청-응답 지연 예산을 소진한 엣지 체계)이라면 팀은 반응하는 시점에 이미 불리하다** (8장,
  p.206).[^gough2022]
- **성능 문제가 아키텍처적일 수 있다** — 저자들이 드는 예는 **다른 리전에 있거나 인터넷을 건너야
  하는 서비스를 부르는 서비스**다 (8장, p.206).[^gough2022]
- **처방은 측정과 객관적 계획이다** (8장, p.206):[^gough2022]
  - **기존 체계를 측정하고 · 성능을 어디서 개선할 수 있을지 가설을 세우고 · 시험하고 검증하라.**
  - **특정 컴포넌트를 격리해 최적화하려 하지 말고 체계를 전체로 볼 것.**
  - **측정 과정을 자동화하면 성능 측정을 빌드 과정의 일부로 들일 수 있다.** 그것이 같은 장의
    적합도 함수 절에서 성능 분류가 가리키던 자리다([API 주도 재설계와 이음매](api-driven-redesign-and-seams.md)).

### 의존 끊기 — 강하게 결합된 API

- **전제** — **분산 아키텍처로 옮기는 것은 아키텍처의 부분들이 독립적으로 진화할 수 있을 때에만
  배당을 준다** (8장 §"Breaking Dependencies: Highly Coupled APIs", p.206).[^gough2022]
- **지켜볼 안티패턴 하나** — **체계의 서로 다른 부분에 걸쳐 릴리스를 동기화해 조율하는 것**이다.
  **이것은 API들이 강하게 결합돼 있을 가능성의 신호이고, 그것을 깨는 것이 재사용을 늘리고 릴리스
  마찰을 줄일 기회일 수 있다** (8장, p.206).[^gough2022] 같은 성질을 정의로 세우는 페이지는
  [독립 배포 가능성](independent-deployability.md)이다.
- **저자들이 짚는 기량의 공백** — **레거시 코드와 효과적으로 일하는 것은 교육 과정과 팀에서 흔히
  간과되는 기량 하나**이고, **개발자들은 의존을 떼는 데 도움이 되는 종류의 변경을 어떻게 들일지
  확신하지 못할 때가 많다** (8장, p.207).[^gough2022]
- **기법 둘을 든다** (8장, p.207):[^gough2022]
  - **새싹(sprout) 기법** — 마이클 페더스의 2004년 *Working Effectively with Legacy Code*에 실린
    것이다. **테스트를 염두에 두지 않고 지어진 코드를 단위 테스트하기는 아주 어려울 때가 많은데**,
    **새싹은 새 기능을 다른 곳에 만들어 테스트한 뒤 삽입 지점(insertion point)이라 불리는 레거시
    메서드에 그것을 더하는 것**이다.
  - **감싸기(wrap)** — **옛 메서드와 같은 이름과 시그니처로 새 메서드를 만들어 기존 기능을 감싼다.
    옛 메서드는 이름을 바꾸어 새 메서드에서 부르고, 레거시 메서드가 불리기 전에 추가 로직을 둔다.**
- **팀 차원의 처방** — **서비스가 주로 레거시라면 레거시 코드와 일하는 것이 길러야 할 핵심
  기량**이고, **코딩 카타를 하거나 코드베이스의 복잡한 영역에서 짝 프로그래밍을 하는 것이 팀 전역의
  이해를 북돋는다** (8장, p.207).[^gough2022] 저자들은 산드로 만쿠소(Sandro Mancuso)의 유튜브
  영상 하나를 **우리 가운데 여럿이 레거시 코드를 다루는 실용적 접근을 이해하는 데 썼다**고 든다
  (8장, p.207).[^gough2022] **이 KB는 그 영상을 확인하지 않았다.**

## 이 KB의 다른 이행 서술과 나란히

- **교살자 무화과** — 이 KB는 이 패턴을 **여러 소스로 이미 갖고 있다**
  ([모놀리스 분해 패턴](monolith-decomposition-patterns.md)). **이 책의 서술이 그것들과 겨루지
  않는다** — 기제(옛것을 두고 새것을 들여 점차 옮긴다)가 같고, 이 책만 **프록시·게이트웨이 갈래와
  기능 플래그 갈래를 나란히 두고 각각이 듣는 조건**(프로세스 안 이음매인가, 프로세스 밖 소비자가
  많은가)을 적는다. **생물학적 단서(상리공생)도 이 책에만 있다.**
- **API 층 케이크와 게이트웨이 층 쌓기** — **둘은 다른 것을 금지한다.** 위 절은
  **책임을 티어로 갈라 요청이 티어를 차례로 통과하게 만드는 것**을 금지하고,
  [API 게이트웨이의 함정과 선택](api-gateway-pitfalls-and-selection.md)의 ESB 함정은 **한 요청
  경로에 같은 종류의 중개자를 여러 겹 두는 것**을 금지한다. **모순이 아니라 같은 방향의 서로 다른
  금지다.**
- **파사드와 어댑터** — 이 책 3장이 게이트웨이를 쓸 이유 여섯 가운데 첫째로 **파사드와 어댑터로
  결합을 줄이는 것**을 든다([API 게이트웨이의 규정과 기능과 배치](api-gateway-capabilities-and-deployment.md)).
  **이 절은 그 쓰임에 선을 그어 준다** — 게이트웨이가 변환까지 떠맡으면 어댑터가 되고 결합이
  즉시 늘어난다는 것이다.
- **고통 지점의 신호 다섯** — **변경 실패율과 요동은 이 KB의 다른 소스들이 배포 성과 지표와
  코드 요동으로 따로 갖고 있는 것**이고([지속적 통합과 지속적 전달](continuous-integration-and-delivery.md)),
  이 책은 그것들을 **어디를 먼저 리팩터링할지 고르는 선별 기준**으로 묶어 쓴다. **겨루지 않는다 —
  같은 지표의 다른 쓰임이다.**
