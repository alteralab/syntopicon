하나의 질문: **배치 잡이 만든 파생 데이터셋을 실서비스 트래픽을 받는 저장소로 어떻게 옮기는가.**

## 문제

- **배치 잡은 흔히 제품 추천, 사용자 대면 리포트, ML 모델용 특징 같은 사전 계산되거나 유도된 데이터셋을
  만드는 데 쓰인다. 이 데이터셋은 통상 프로덕션 데이터베이스·키-값 저장소·검색 엔진에서 서빙된다. 어떤
  시스템을 쓰든, 사전 계산된 데이터는 배치 처리기의 분산 파일시스템이나 오브젝트 스토어에서 살아 있는
  트래픽을 서빙하는 데이터베이스로 되돌아가야 한다** (11장, p.479).[^kleppmann2026]

## 직접 쓰지 마라

- 유혹 — **배치 잡 안에서 좋아하는 데이터베이스의 클라이언트 라이브러리를 그냥 써서 데이터베이스
  서버에 한 번에 한 레코드씩 직접 쓰고 싶어질 수 있다. 이는 (배치 처리 환경에서 프로덕션 데이터베이스로의
  직접 접근을 방화벽 규칙이 허용한다고 가정하면) 동작하겠지만 여러 이유로 나쁜 생각이다** (11장,
  p.479):[^kleppmann2026]
  - **레코드 하나하나마다 네트워크 요청을 하는 것은 배치 태스크의 정상 처리량보다 몇 자릿수 느리다.
    클라이언트 라이브러리가 배칭을 지원하더라도 성능은 나쁠 가능성이 높다.**
  - **배치 처리 프레임워크는 흔히 많은 태스크를 병렬로 돌린다. 모든 태스크가 배치 프로세스에서 기대되는
    속도로 같은 출력 데이터베이스에 동시에 쓰면 그 데이터베이스는 쉽게 압도될 수 있고, 질의에 대한 성능이
    나빠질 가능성이 높다. 이는 다시 시스템의 다른 부분에 운영 문제를 일으킬 수 있다.**
  - **보통 배치 잡은 잡 출력에 대해 깔끔한 전부-아니면-전무(all-or-nothing) 보장을 제공한다. 잡이
    성공하면 그 결과는 도중에 일부 태스크가 실패해 재시도됐더라도 모든 태스크를 정확히 한 번 실행한
    출력이다; 잡 전체가 실패하면 아무 출력도 만들어지지 않는다. 그러나 잡 안에서 외부 시스템에 쓰는 것은
    그런 식으로 숨길 수 없는, 외부에서 보이는 부수 효과를 만든다. 따라서 부분적으로 완료된 잡의 결과가
    다른 시스템에 보이는 것을 걱정해야 한다. 태스크가 실패하고 재시작되면 실패한 실행의 출력이 중복될 수
    있다.**

## 스트림을 사이에 두기

- **더 나은 해법은 배치 잡이 사전 계산된 데이터셋을 카프카 토픽 같은 스트림으로 밀게 하는 것이다.
  Elasticsearch 같은 검색 엔진, Apache Pinot과 Apache Druid 같은 실시간 OLAP 시스템, Venice 같은 파생
  데이터 저장소, ClickHouse 같은 클라우드 데이터 웨어하우스 모두가 카프카에서 자기 시스템으로 데이터를
  적재하는 내장 능력을 갖고 있다** (11장, p.480).[^kleppmann2026]
- **스트리밍 시스템을 통해 데이터를 미는 것은 앞의 문제 몇 가지를 고친다** (11장,
  p.480):[^kleppmann2026]
  - **스트리밍 시스템은 순차 쓰기에 최적화돼 있어 배치 잡의 대량 쓰기 워크로드에 더 적합하다.**
  - **스트리밍 시스템은 배치 잡과 프로덕션 데이터베이스 사이의 버퍼 역할을 할 수 있다. 하류 시스템은
    자기 읽기 속도를 조절해 프로덕션 트래픽을 계속 편안하게 서빙할 수 있게 보장할 수 있다.**
  - **하나의 배치 잡 출력이 여러 하류 시스템에 소비될 수 있다.**
  - **스트리밍 시스템은 배치 처리 환경과 프로덕션 네트워크 사이의 보안 경계 역할을 할 수 있다. 그것은
    배치 처리 네트워크와 프로덕션 네트워크 사이에 놓이는 이른바 비무장 지대(demilitarized zone, DMZ)
    네트워크에 배치될 수 있다.**

## 남는 문제 — 전부 아니면 전무

- **스트리밍이 본질적으로 풀지 못하는 문제 하나는 전부-아니면-전무 보장이다. 이것이 되게 하려면 배치
  잡은 완료 시 하류 시스템에 자기 잡이 끝났고 이제 데이터를 서빙해도 된다는 통지를 보내야 한다. 스트림의
  소비자는 잡이 완료됐다고 통지받을 때까지, 받은 데이터를 read committed 격리의 커밋되지 않은 트랜잭션처럼
  질의에 보이지 않게 유지할 수 있어야 한다** (11장, p.480).[^kleppmann2026] 그 격리 수준의 정의는
  [격리 수준과 이상 현상](../concepts/isolation-levels-and-anomalies.md)에 있다.

## 반대편 — 데이터베이스를 통째로 만들기

- **데이터베이스를 부트스트랩할 때 더 흔한 또 다른 패턴은 배치 잡 안에서 완전히 새로운 데이터베이스를
  만들고 그 파일을 분산 파일시스템·오브젝트 스토어·로컬 파일시스템에서 데이터베이스로 직접 벌크
  로드하는 것이다. 많은 데이터 시스템이 TiDB의 Lightning과 Apache Pinot의 Hadoop 임포트 잡 같은 벌크
  임포트 도구를 제공한다. RocksDB도 배치 잡에서 정렬 문자열 테이블(Sorted String Table, SST) 파일을
  벌크 임포트하는 API를 제공한다** (11장, p.481).[^kleppmann2026] SSTable이 무엇인지는
  [LSM 트리](../concepts/lsm-tree.md)에 있다.
- 그 맞교환 — **배치에서 데이터베이스를 만들고 데이터를 벌크 임포트하는 것은 매우 빠르고, 시스템이
  데이터셋 버전 사이를 원자적으로 전환하기 쉽게 만든다. 반면 완전히 새로운 데이터베이스를 만드는 배치
  잡에서 데이터셋을 증분으로 갱신하기는 어려울 수 있다. 부트스트랩과 증분 적재가 둘 다 필요할 때는
  하이브리드 접근을 취하는 것이 흔하다. 예컨대 Venice는 배치 행 단위 갱신과 전체 데이터셋 교체를 둘 다
  허용하는 하이브리드 스토어를 지원한다** (11장, p.481).[^kleppmann2026]
