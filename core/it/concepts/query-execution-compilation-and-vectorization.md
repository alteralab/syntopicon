하나의 질문: **열로 적재한 데이터를 CPU가 훑을 때 무엇이 병목이고, 그것을 어떻게 없애는가.**

## 연산자와 질의 계획

- **분석용 복잡한 SQL 질의는 연산자(operators)라 불리는 여러 단계로 이뤄진 질의 계획(query
  plan)으로 쪼개지며, 그 단계들은 병렬 실행을 위해 여러 기계에 분산될 수 있다. 질의 계획기는
  어떤 연산자를 쓸지, 어떤 순서로 실행할지, 각 연산자를 어디서 돌릴지를 고름으로써 많은 최적화를
  수행할 수 있다** (4장, p.142).[^kleppmann2026]
- 연산자 안에서 하는 일은 이렇다 — **각 연산자 안에서 질의 엔진은 열의 값들로 여러 가지를 해야
  할 수 있다. 값이 특정 값 집합에 속하는 행을 전부 찾는다든가(아마 조인의 일부로), 값이 예컨대
  15보다 큰지 확인한다든가. 질의 엔진은 같은 행의 여러 열을 봐야 할 가능성도 높다** — 예컨대
  제품이 "바나나"이고 매장이 특정 관심 매장인 판매 거래를 전부 찾는 경우다 (4장,
  p.142).[^kleppmann2026]

## 왜 인터프리터로는 모자라는가

- 걱정거리가 둘이다 — **수백만 행을 스캔해야 하는 데이터 웨어하우스 질의에서는 디스크에서 읽어야
  하는 데이터의 양뿐 아니라 복잡한 연산자를 실행하는 데 필요한 CPU 시간까지 걱정해야 한다**
  (4장, p.142).[^kleppmann2026]
- 가장 단순한 구현이 왜 느린지가 명시된다 — **가장 단순한 종류의 연산자는 프로그래밍 언어의
  인터프리터와 같다. 각 행을 순회하면서 질의를 나타내는 자료 구조를 확인해 어느 열에 어떤
  비교나 계산을 수행해야 하는지 알아낸다. 불행히도 이것은 많은 분석 목적에 너무 느리다** (4장,
  p.142).[^kleppmann2026]
- **효율적인 질의 실행을 위한 대안적 접근 둘이 등장했다** — 질의 컴파일과 벡터화 처리다 (4장,
  p.142).[^kleppmann2026]

## 질의 컴파일

- **질의 컴파일(query compilation)** — **질의 엔진이 SQL 질의를 받아 그것을 실행하는 코드를
  생성한다. 그 코드는 행을 하나씩 순회하고, 관심 있는 열의 값을 보고, 필요한 비교나 계산을
  수행하고, 요구된 조건이 만족되면 필요한 값을 출력 버퍼로 복사한다. 그 뒤 질의 엔진은 생성된
  코드를 기계어로 컴파일하고(흔히 LLVM 같은 기존 컴파일러를 쓴다) 메모리에 적재된 열 인코딩
  데이터에 대해 그것을 돌린다** (4장, p.142).[^kleppmann2026]
- 낯익은 기법이다 — **이 코드 생성 접근법은 자바 가상 머신(JVM)과 비슷한 런타임들에서 쓰이는
  JIT(just-in-time) 컴파일 접근법과 비슷하다** (4장, p.142).[^kleppmann2026]

## 벡터화 처리

- **벡터화 처리(vectorized processing)** — **질의가 컴파일되지 않고 해석되지만, 행을 하나씩
  순회하는 대신 한 열의 많은 값을 배치(batch)로 처리함으로써 빨라진다. 미리 정의된 연산자의 고정
  집합이 데이터베이스에 내장돼 있고, 우리는 거기에 인자를 넘기고 결과 배치를 돌려받을 수 있다**
  (4장, p.142).[^kleppmann2026]
- 저자가 든 예 — **`product_sk` 열과 제품 ID(가령 "바나나")를 동등성 연산자에 넘기면 비트맵을
  돌려받는다(입력 열의 값마다 비트 하나이고, 그 ID와 일치하면 1이다). 그 뒤 `store_sk` 열과 관심
  매장의 ID를 같은 동등성 연산자에 넘겨 또 하나의 비트맵을 돌려받는다. 마지막으로 두 비트맵을
  비트별 AND 연산자에 넘기면, 결과는 특정 매장의 모든 바나나 판매에 대해 1을 담은 비트맵이다**
  (4장, pp.142–143).[^kleppmann2026]
- 둘 다 살아남았다 — **두 접근법은 구현 면에서 매우 다르지만 둘 다 실무에서 쓰인다** (4장,
  p.143).[^kleppmann2026]

## 둘이 공유하는 네 가지 수단

- **둘 다 현대 CPU의 특성을 이용함으로써 매우 좋은 성능을 낼 수 있다** (4장,
  p.143):[^kleppmann2026]
  - **캐시 미스를 줄이기 위해 임의 접근보다 순차 메모리 접근을 선호한다.**
  - **CPU 명령어 처리 파이프라인을 바쁘게 유지하고 분기 예측 실패(branch mispredictions)를 피하기
    위해 대부분의 일을 빡빡한 안쪽 루프(곧 명령어 수가 적고 함수 호출이 없는 루프)에서 한다.**
  - **여러 스레드와 SIMD(single-instruction, multiple data) 명령어 같은 병렬성을 활용한다.**
  - **압축된 데이터를 별도의 인메모리 표현으로 디코딩하지 않고 그 위에서 직접 연산해, 메모리
    할당과 복사 비용을 아낀다.**
- 낱말 하나가 다른 곳에서 다른 뜻으로 쓰인다는 주가 붙는다 — **의미 검색에서의 벡터는 다른
  뜻이다. 벡터화 처리에서 벡터는 특별히 최적화된 코드로 처리할 수 있는 비트의 배치를 가리키고,
  임베딩 모델에서 벡터는 다차원 공간의 한 위치를 나타내는 부동소수점 수의 배열이다** (4장,
  p.148).[^kleppmann2026]
