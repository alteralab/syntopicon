## 하나의 질문

**데이터 프로덕트는 어디서 무엇을 어떻게 들여오고, 그 안에서 무엇으로 바꾸는가.**

[서빙 쪽](../concepts/data-product-serving-design.md)이 출력 표면의 보장을 정했다면 이쪽은
입구와 내부다. 12장이 다루는 세 기본 기능 중 나머지 둘이다.

## 입력 데이터 포트가 하는 일

- 데이터의 출처 — **대다수의 경우 조직의 데이터는 사람이나 장치 같은 다른 운영 에이전트와의
  상호작용 속에서 내부 또는 외부 운영 시스템에서 발원한다. 어떤 경우 데이터는 구매되거나 자유롭게
  내려받은 아카이브로 받는다** (12장, p.217).[^dehghani2022]
- 아키텍처적 정의 — **아키텍처적으로 입력 데이터 포트는 데이터 프로덕트가 자기 소스 데이터의
  소비를 정의하고 실행하는 데 필요한 기제를 구현한다. 입력 데이터 포트는 데이터 프로덕트가
  **데이터 소스에 접속하고, 질의를 실행하고, 데이터 — 이벤트나 스냅샷 — 를 연속 스트림이나
  일회성 페이로드로 받게** 하는 논리적 아키텍처 구성물이다. 기저 기술의 선택은 구현 특유의
  관심사이고 데이터 플랫폼에 맡겨진다** (12장, p.218).[^dehghani2022]
- 원형별 기본 소스가 갈린다 — **소스 정렬(source-aligned) 데이터 프로덕트는 대개 운영
  시스템에서 데이터를 소비한다. 집계 데이터 프로덕트로 가면 다른 데이터 프로덕트가 소스가 되고,
  소비자 정렬(consumer-aligned) 데이터 프로덕트는 흔히 특정 사용 사례를 위한 지역 소스 데이터를
  제공하기 위해 스마트 로직이나 기계 학습 모델을 포함한다** (12장, p.219).[^dehghani2022]
  세 원형의 정의는 [도메인 소유권 원칙](../concepts/domain-ownership-principle.md)이 받는다.

## 소스의 세 원형

- **데이터 입력 능력의 설계는 여러 소스 원형(archetypes)을 지원해야 한다. 다음이 최상위
  범주들이다** (12장, p.219):[^dehghani2022]
  - **협력하는 운영 시스템(collaborating operational systems)**
  - **다른 데이터 프로덕트(other data products)**
  - **자기 자신(self)**

## 원형 ① 협력하는 운영 시스템

- 무엇을 하는가 — **소스 정렬 데이터 프로덕트는 자기 협력 운영 시스템 — 도메인 사업을 운영한
  부산물로 데이터를 생성하는 하나 또는 여러 애플리케이션 — 에서 데이터를 소비한다. 그것들은
  운영 시스템에 최적화된 데이터를 소비해 분석 사용에 적합한 형식으로 변환한다. 그것들은 하류
  분석 사용 사례를 운영 애플리케이션의 내부 세부에서 분리한다** (12장, p.219).[^dehghani2022]
- **협력**이라는 낱말이 결합의 세기를 뜻한다 — **여기서 협력한다(collaborating)는 어구는 데이터
  프로덕트와 그 소스 운영 시스템 사이의 **단단한 결합(tight coupling)**을 함의한다. 둘 다 같은
  도메인에 속해야 한다. 소스 애플리케이션과 데이터 프로덕트 사이의 운영 데이터 계약은 흔히
  단단히 결합된다. 운영 시스템의 데이터와 모델의 변경이 데이터 프로덕트의 데이터와 모델에 영향을
  준다** (12장, p.219).[^dehghani2022]
- 그래서 조직 배치가 따라온다 — **그래서 나는 협력 운영 시스템 소스와 그 협력 데이터 프로덕트를
  같은 도메인에 두기를 강력히 권장한다. 이는 운영 시스템 변경을 책임지는 도메인 팀이 데이터
  프로덕트 개발자와 긴밀히 협업해 둘을 동기화 상태로 유지할 수 있게 한다** (12장,
  p.219).[^dehghani2022]
  - **단단한 결합을 없애지 않고 조직 경계 안으로 넣는다**는 것이 요점이다. 결합 자체가 아니라
    결합이 **팀 경계를 넘는 것**이 문제라는 판단이다.
- 소스가 단일 도메인에 정렬되지 않는 경우 — **운영 시스템이 단일 도메인에 정렬되지 않은 경우가
  있다. 예컨대 CRM COTS(상용 기성품 고객 관계 관리) 제품은 제품·고객·판매 등 여러 도메인을 하나로
  캡슐화한다. 이 경우 COTS 시스템은 여러 도메인 정렬 인터페이스를 노출할 수 있고, 각각은 특정
  소스 정렬 데이터 프로덕트를 위한 것이다** (12장, p.220).[^dehghani2022]
- 저자의 예 — **listener subscriptions** 데이터 프로덕트가 같은 도메인의 마이크로서비스
  **listener subscription service**에서 데이터를 소비한다. **그것은 이벤트 로그에 발행된 준실시간
  이벤트로 청취자 구독의 변경을 받는다. subscription events 로그는 운영 시스템이 통제·유지하며
  단기 보존(short-retention) 매체다. 데이터 프로덕트는 그 이벤트를 소비해 변환을 수행하고
  궁극적으로 청취자 구독 정보의 장기 보존 시간적 뷰로 서빙한다** (12장,
  p.220).[^dehghani2022]
  - **단기 보존 운영 로그 → 장기 보존 분석 뷰**라는 이 한 줄이 운영/분석 경계의 실제 모양이다.
- **구현 기제에 저자가 순위를 매긴다** — **협력 운영 시스템에서 데이터를 소비하는 입력 포트를
  구현하는 흔한 기제로는 현대적 시스템의 경우 비동기 **이벤트 주도(event-driven)** 데이터 공유,
  그리고 바꾸기 어려운 레거시 시스템의 경우 **변경 데이터 캡처(change data capture)**가 있다.
  자기 도메인 이벤트를 공유하는 현대적 운영 시스템은 점점 흔한 관행이 되고 있으며 협력 데이터
  프로덕트에 데이터를 먹이는 훌륭한 모델이다** (12장, p.220).[^dehghani2022]
  - **CDC는 최후 수단으로 강등된다** — **변경 데이터 캡처는 애플리케이션 데이터베이스의 변경을
    발견하고 추적하는 통합 패턴 집합이고, 그것이 데이터 프로덕트의 입력으로 소싱될 수 있다.
    이것은 협력 운영 시스템에서 데이터를 받는 **가장 바람직하지 않은 방식**이다. 그것은
    데이터베이스 트랜잭션의 내부 구현을 노출하고 사업 도메인에 대응하지 않는다. 그러나 때로는
    레거시 시스템의 경우 유일하게 가용한 선택지다** (12장, pp.220–221).[^dehghani2022]
  - [변경 데이터 캡처](../concepts/change-data-capture.md)가 CDC를 **반입의 일급 방법**으로
    두는 서술과 정면으로 갈린다. 대립은 처방이고, 조건은 **소스 팀이 도메인 이벤트를 발행할
    수 있는가**이다 — 저자도 레거시에는 CDC를 허용하므로 사실 충돌은 아니다. 갈리는 것은
    **기본값**이다.
  - [수명 주기의 반입 단계](../concepts/ingestion-in-the-lifecycle.md)의 푸시·풀 논의와도
    축이 다르다 — 저자의 판정 기준은 전송 방향이 아니라 **노출되는 것이 도메인 개념인가
    DB 내부 구현인가**이다.
- 최종 판단은 조직이 한다 — **데이터 프로덕트가 운영 시스템에서 데이터를 소비하는 방식은 팀이
  운영 시스템을 확장할 수 있는 능력에 크게 영향받는다. 설계는 궁극적으로 도메인 팀 안에서
  운영 시스템을 자기 데이터 프로덕트와 어떻게 통합할지에 대한 합의에 달렸다** (12장,
  p.221).[^dehghani2022]

## 원형 ② 다른 데이터 프로덕트

- **데이터 프로덕트는 메시의 다른 데이터 프로덕트에서 데이터를 소비할 수 있다. 예컨대
  **podcast demographics** 데이터 프로덕트는 **listener profiles**와 **podcast listeners**
  데이터 프로덕트에서 청취자에 대한 속성을 받는다. 그것은 청취자 프로필 정보를 팟캐스트 청취자와
  상관시키고 이 소스들에 분류 변환을 적용한다** (12장, p.221).[^dehghani2022]
- 도메인을 넘는 것이 허용된다 — **이 경우 입력 포트는 다른 데이터 프로덕트의 출력 포트에서
  데이터를 소비한다. 소스 데이터 프로덕트는 같은 도메인에 속할 수도 다른 도메인에 속할 수도
  있다. 그럼에도 입력 데이터 포트의 구현과 그것들이 다른 데이터 프로덕트의 출력 포트에서
  데이터를 소비하는 방식은 **표준화된다**** (12장, p.222).[^dehghani2022]
  - 원형 ①의 단단한 결합과 대조하라 — 도메인을 넘는 통합은 **표준 인터페이스로만** 허용된다.
    그림 12-9는 도메인 내 상류(intra-domain)와 도메인 간 상류(inter-domain)를 다른 선으로
    구분해 그린다 (12장, p.221, 그림 12-9).[^dehghani2022]
- 시간 축이 선택 기제가 된다 — **데이터 프로덕트는 상류 출력의 실제 시간과 처리 시간을 활용해
  원하는 데이터를 선택한다. 스트리밍 입력의 경우 입력 포트 기제는 새 데이터가 도착할 때 처리하기
  위해 소스 데이터의 처리 시간을 추적한다** (12장, p.222).[^dehghani2022]
  [바이템포럴 데이터](../concepts/bitemporal-data.md)의 처리 시간 포인터가 소비 쪽에서 하는
  구실이 이것이다 — **오프셋에 해당하는 것이 처리 시간**이다.

## 원형 ③ 자기 자신

- **어떤 경우 데이터 프로덕트의 지역 계산이 데이터의 소스가 될 수 있다. 예컨대 기계 학습 모델
  추론 같은 지역 변환이 새 데이터를 생성한다. **artists** 데이터 프로덕트를 생각해 보라. 그
  변환은 **artist onboarding** 마이크로서비스에서 받은 정보에 아티스트 분류를 위한 "emerging"이나
  "declining" 같은 새 데이터를 더하는 기계 학습 모델을 돌린다. 추가로 그 데이터 프로덕트는 가능한
  분류 목록 같은 지역 저장 데이터를 자기 입력으로 쓴다** (12장, p.222).[^dehghani2022]
  - 곧 **참조 데이터(lookup)와 모델 출력도 입력으로 센다**. 소스를 외부로만 보지 않는 것이
    이 원형의 요점이다.

## 소비의 지역성 — 물리 위치를 감추면 이관이 된다

- 전제 — **데이터 메시는 많은 구현 결정을 기저 기술에 맡긴다. 데이터 메시 아키텍처는 가능한 한
  기저 기술과 인프라에 불가지다** (12장, p.223).[^dehghani2022]
- 무엇이 구현 세부로 내려가는가 — **예컨대 데이터가 물리적으로 어디에 있는지, 소비하는 데이터
  프로덕트가 데이터를 한 위치에서 다른 위치로 물리적으로 복사하는지는 플랫폼이 짓는 구현
  세부다. 그러나 입력·출력 포트 같은 데이터 메시 아키텍처 구성 요소는 물리 경계를 넘는 데이터나
  처리 이동의 내부 구현을 추상화하는 훌륭한 인터페이스다. 한 데이터 프로덕트의 입력 포트를
  다른 것의 출력 포트에 잇는 단순한 API 집합이 한 물리 스토리지·신뢰 경계에서 다른 곳으로의
  물리적 데이터 이동을 감출 수 있다. 마찬가지로 데이터 소비 요청의 실행은 한 계산 환경에서 다른
  곳으로 발행된 원격 질의를 실행할 수 있다** (12장, p.223).[^dehghani2022]
- 그 귀결이 크다 — **이 설계의 함의는 메시가 **하나 또는 여러 물리 인프라, 여러 클라우드,
  온프레미스 호스팅 환경에 걸칠 수 있다**는 것이다. 이는 데이터 프로덕트가 자기 소스에서 데이터를
  소비할 때 그 과정에서 데이터를 한 기저 호스팅 환경에서 다른 곳으로 물리적으로 옮길 수 있다는
  뜻이다. 이 겉보기에 단순한 능력은 **클라우드로의 데이터 이관**과 **멀티클라우드 데이터
  플랫폼**에 심대한 영향을 줄 수 있다** (12장, p.223).[^dehghani2022]
- 저자의 예 — Daff가 분석 데이터·처리를 클라우드로 옮기는 중이고 **podcast service는 그
  기저 운영 데이터베이스와 함께 온프레미스에서 돌지만 podcast listeners 데이터 프로덕트는
  클라우드에서 돈다. 그것은 비동기 입력 데이터 포트 인터페이스로 데이터를 소비한다. 새 팟캐스트
  청취자가 등록되면 podcast listeners 데이터 프로덕트는 본질적으로 그 정보를 온프레미스
  스트림에서 자기 클라우드 스토리지로 복사하고 자기 클라우드 기반 출력 데이터 인터페이스를 통해
  가용하게 만든다** (12장, p.223).[^dehghani2022]
- 그래서 이관 전략이 바뀐다 — **이것은 빅뱅 데이터 이관 전략 없이 데이터 프로덕트를 통한 한
  환경에서 다른 환경으로의 **연속적 데이터 이관(continuous data migration)**을 구현한다. 같은
  기제가 데이터를 한 클라우드 제공자에서 다른 곳으로 옮길 수 있다** (12장,
  p.223).[^dehghani2022]
- 다만 인프라 전제가 붙는다 — **이것이 현실이 되려면 기저 플랫폼 인프라가 몇 가지 핵심 기능을
  지원해야 한다: 데이터 프로덕트의 인터넷 호환 주소 지정 가능성, 신뢰 경계를 넘는 신원 인증과
  인가, 그리고 출력 데이터 포트를 위한 인터넷 접근 가능 엔드포인트다** (12장,
  p.223).[^dehghani2022]
  - [클라우드 대 자체 호스팅](../concepts/cloud-versus-self-hosting.md)의 이관 논의에 대해
    이것은 **제3의 경로**다 — 리프트 앤 시프트도 재구축도 아니고, 소비 관계 자체가 이관
    파이프가 된다. #hypothesis — 저자는 이 방식의 대역폭·이그레스 비용을 논하지 않는다.

## 소비를 선언하는 쪽이 소비자다

- **데이터 프로덕트는 어떤 데이터를, 어떤 소스에서, 어떻게 소비할지를 **의도적으로 명세한다**.
  데이터 프로덕트가 데이터를 소비하는 능력을 구체적으로 정의하고 통제한다. 이는 소스가 데이터가
  어디로 어떻게 가는지에 대한 지식 없이 처리기(processor)에 데이터를 쏟아붓는 다른 데이터
  아키텍처와 상반된다. 예컨대 이전 아키텍처에서는 외부 유향 비순환 그래프(DAG) 명세가 처리기들이
  서로 어떻게 연결되는지를 **중앙에서** 정의했지, 각 처리기가 데이터를 어떻게 받고 서빙하는지를
  정의하지 않았다** (12장, p.224).[^dehghani2022]
  - 11장의 "중앙 오케스트레이터 없음"이 소비 설계에서 갖는 구체적 모양이다 — **DAG의 간선을
    누가 선언하는가**가 뒤집힌다.
  - [배치 워크플로와 DAG](../concepts/batch-workflows-and-dags.md)와
    [반입 방법](../concepts/data-ingestion-methods.md)이 전제하는 파이프라인 소유 구조와
    갈리는 자리다.

## 소비 설계의 구성 요소

- 표 12-2가 정리한다 (12장, pp.225–226):[^dehghani2022]

| 구성 요소 | 저자의 정의 |
|---|---|
| 입력 데이터 포트 | 데이터 프로덕트가 자기 소스 데이터를 받아 내부 변환에 쓸 수 있게 만드는 기제 |
| 입력 데이터 포트 명세 | 데이터가 **어디서 어떻게** 소비되는지를 설정하는 입력 데이터 포트의 선언적 명세 |
| 비동기 입력 데이터 포트 | 필요한 소스 데이터가 가용해지면 변환 코드를 반응적으로 호출한다. 이벤트 스트림 구독이나 파일에 대한 비동기 I/O 읽기가 예다. 소스 데이터 프로덕트의 **처리 시간 포인터를 추적**하고 새 처리 시간의 데이터를 받으면 반응적으로 변환을 실행한다 |
| 동기 입력 데이터 포트 | 소스에서 데이터를 당겨 오고, 데이터를 가져오면 변환 코드를 호출한다. 예: "Daily podcasts summary"가 podcast listeners에서 동기적으로 데이터를 당겨 매일 자정에 카운트와 요약을 계산한다 |
| 원격 질의(remote query) | 입력 포트 명세는 원하는 데이터를 받기 위해 소스에서 실행되는 질의를 포함할 수 있다. 이 능력은 그러지 않으면 중복해서 가져올 데이터의 양을 줄인다. 질의는 SQL·GraphQL·Flux 등 소스가 이해하는 질의 언어로 표현되고 입력 포트 명세로 정의된다 |
| 입력 포트 동기화기와 임시 스토리지 | 입력 포트는 흔히 **상호 의존적으로** 데이터를 소비한다. 예컨대 artist classification 변환 코드는 artists와 listeners라는 두 독립 소스의 데이터가 가용해지기 전에는 실행을 시작할 수 없다. 임시 스토리지는 필요한 관측이 전부 처리에 가용해질 때까지 관측되었으나 미처리인 데이터를 추적하는 데 필요하다 |

- 원격 질의 항목이 조용히 큰 결정을 담고 있다 — **연산을 데이터가 있는 곳으로 밀어 보낸다**.
  같은 발상이 [질의 수명 주기와 성능](../concepts/query-lifecycle-and-performance.md)의 술어
  푸시다운이다.

## 변환은 내부 구현이다

- 보편성 — **거의 모든 데이터 프로덕트가 아무리 최소한이라도 변환을 수행한다. 우리가 데이터
  프로덕트를 만드는 이유는 기존 데이터의 새 분석 모델을 공유하는 데서 가치를 보기 때문이다. 이
  새 모델을 만드는 데는 변환이 필요하다. 변환 코드를 만들고 유지하는 것이 데이터 프로덕트
  개발자가 가장 많은 주의를 쏟는 일이다** (12장, p.226).[^dehghani2022]
- 자리가 옮겨진다 — **전통적으로 이 변환은 입력 소스에서 출력 싱크로 데이터를 옮기는 데이터
  파이프라인에서 일어났다. 데이터 메시 설계에서 변환은 — 파이프라인으로 구현되든 아니든 —
  데이터 프로덕트 안에 인코딩되고 그것에 의해 추상화된다** (12장, p.226).[^dehghani2022]
- 그리고 저자가 여기서 규정을 멈춘다 — **변환은 데이터 프로덕트의 **내부 구현**이고 그것에 의해
  통제된다. 내부 관심사이므로 나는 그것이 어떻게 설계되어야 하는지에 대해 구체적으로 말할
  의도가 없다. 내 견해로는 변환을 어떻게 구현할지를 고르는 것은 데이터 프로덕트 개발자의
  취향·능력·필요에 달렸다** (12장, p.226).[^dehghani2022]
  - **캡슐화가 서술의 침묵으로 나타나는 자리**다. [데이터 퀀텀](../concepts/data-quantum.md)이
    변환 코드를 내부로 넣은 결정의 논리적 귀결이다.

## 변환 ① 비프로그램적 대 프로그램적

- 두 진영 — **데이터 처리와 변환은 두 주요 진영으로 나뉜다: 비프로그램적
  변환(nonprogrammatic transformations, 예: SQL·Flux·GraphQL)과 프로그램적 데이터
  처리(programmatic data processing, 예: Apache Beam·Apache Spark·Metaflow)다** (12장,
  p.226).[^dehghani2022]
- 비프로그램적 쪽의 장단 — **비프로그램적 접근은 SQL처럼 집합 연산을 수행하는 관계 대수를
  쓰거나 Flux처럼 흐름 기반 함수를 쓴다. 어느 쪽이든 발상은 데이터가 한 집합에서 다른 집합으로
  어떻게 변환되는지의 의도를 하나의 문장으로 포착할 수 있다는 것이다. 그것은 단순하고 많은 데이터
  프로덕트 개발자에게 접근 가능하지만, 그 문장의 기능에 제한된다. 더 복잡한 변환에서는 문장이
  이해하기 어렵고·모듈화하기 힘들고·자동으로 테스트하기 까다로워진다** (12장,
  p.226).[^dehghani2022]
- 저자가 곧바로 경계한다 — **실무에서 우리는 단순히 비프로그램적 변환만 수행하는 데이터
  프로덕트를 많이 발견해서는 안 된다. 다른 어떤 하류 데이터 프로덕트든 같은 원격 질의를 스스로
  돌릴 수 있고, 중간(intermediary) 데이터 프로덕트가 필요 없다** (12장,
  p.227).[^dehghani2022]
  - **얇은 데이터 프로덕트를 만들지 말라**는 이 조항은 [메달리온 계열의 중간
    레이어](../concepts/transformation-in-the-lifecycle.md) 관행과 갈린다 — 조건은 그 층이
    질의 하나로 대체 가능한가이다.
- 프로그램적 쪽 — **프로그램적 데이터 처리는 코드 로직·조건·문장을 써서 데이터를 변환한다.
  Apache Beam이나 Apache Spark 같은 프로그램적 데이터 처리 라이브러리는 Python·Java 등 다른
  프로그래밍 언어에서 쓸 수 있다. 변환 코드는 호스팅 프로그래밍 언어의 온전한 힘 — 명령형이든
  선언형이든 — 에 접근할 수 있다. 모듈화되고 테스트될 수 있다. 이 접근은 코딩하지 않는 데이터
  프로덕트 개발자에게 더 복잡하지만 더 확장 가능하다** (12장, pp.227–228).[^dehghani2022]
  증분 계산의 이점도 든다 — **이 접근의 장점은 played songs에 대한 레코드가 더 도착하면서 통계를
  증분적으로 계산할 수 있다는 것이다** (12장, p.228).[^dehghani2022]
- 판정 — **데이터 메시는 데이터 프로덕트가 자기 변환에 어떤 접근을 채택하는지에 대해 입장을
  취하지 않고 상식에 의존한다: 더 복잡한 사용 사례에는 프로그램적 접근을, 변환이 사소하고
  단순할 때는 비프로그램적 접근을 쓰라. 더 좋게는, 변환이 사소하고 비프로그램적이라면 아무것도
  하지 말고 중간 데이터 프로덕트를 만들지 마라. 최종 소비자가 스스로 질의를 돌리게 두라. 프로그램적
  변환의 경우에도 입력 포트가 처리 전에 소스에 비프로그램적 질의를 불러낼 수 있음에 유의하라.
  이는 변환 코드로 옮겨지는 데이터의 양을 줄이고 처리를 상류 데이터가 있는 곳으로 민다** (12장,
  p.228).[^dehghani2022]

## 변환 ② 데이터플로 기반 — 파이프라인이 허용되는 조건

- 계열 — **데이터플로 프로그래밍 패러다임은 1960년대에 도입되었고, 컴퓨터 프로그램을 연산 사이를
  흐르는 데이터의 유향 그래프로 정의한다. 이 프로그래밍 패러다임은 많은 현대 데이터 파이프라인
  설계에 영감을 주었다** (12장, p.228).[^dehghani2022]
- 무엇을 거부하는가 — **데이터 파이프라인은 데이터가 한 단계에서 다음으로 흐르면서 실행되는
  일련의 변환 단계(함수)다. 데이터 메시는 파이프라인을 **최상위 아키텍처 패러다임**으로 쓰는 것을
  삼가고, 데이터 프로덕트 **사이**에 쓰는 것을 삼간다. 현재 쓰이는 파이프라인의 문제는 파이프라인
  복잡성이 커질 때 쉽게 유지할 수 있는 명확한 인터페이스·계약·추상을 만들지 않는다는 것이다.
  추상의 결여 때문에 파이프라인의 단일 실패가 연쇄 실패를 일으킨다** (12장,
  p.228).[^dehghani2022]
- 무엇을 허용하는가 — **데이터 프로덕트 **경계 안**의 파이프라인 — 또는 일반적으로 데이터플로
  기반 프로그래밍 모델 — 은 변환 코드를 구현하는 자연스러운 패러다임이다. 이 시나리오에서
  파이프라인은 단일 데이터 프로덕트의 맥락과 변환에 의해 경계 지어지므로 덜 복잡해지는 경향이
  있다. 또한 데이터 프로덕트와 함께 단일 단위로 업그레이드되고·테스트되고·배포된다. 따라서
  파이프라인 단계의 단단한 결합은 덜 문제된다** (12장, p.228).[^dehghani2022]
- 그리고 원칙 이름이 여기서 붙는다 — **요컨대, 변환을 위해 데이터 프로덕트 경계 안에서 데이터
  파이프라인을 쓰는 것은 괜찮다. 파이프라인 단계가 데이터 프로덕트의 경계를 넘어 확장되지 않는
  한에서다. 데이터 프로덕트 사이에는, 읽기 전용 출력·입력 데이터 포트를 통해 데이터를 제공하고
  소비하는 것 너머의 변환이 일어나지 않는다. 나는 이것을 **dumb pipes and smart filters**의
  원칙이라 부른다** (12장, p.228).[^dehghani2022]
  - 4부 도입은 같은 원칙을 `dump pipes and smart filters`로 적고 마이크로서비스의
    `dumb pipes and smart endpoints`와 등가라고 밝힌다 (4부 도입, p.192).[^dehghani2022] —
    [데이터 프로덕트 어포던스](../concepts/data-product-affordances.md)에 그 대목이 있다.
  - [데이터플로 엔진](../concepts/dataflow-engines.md)과
    [배치 워크플로와 DAG](../concepts/batch-workflows-and-dags.md)를 **부정하지 않고 경계를
    긋는다**는 것이 정확한 독법이다 — 기술은 그대로 쓰되 그래프가 프로덕트 경계를 넘지 못한다.
- 그림 12-14는 파이프라인 단계들과 **중간 데이터를 위한 선택적 임시 스토리지**를 데이터 프로덕트
  안쪽에 그린다 (12장, p.229).[^dehghani2022]

## 변환 ③ ML을 변환으로

- **세 번째 변환 범주는 모델 기반이다. 기계 학습이나 통계 모델을 데이터 프로덕트의 변환으로
  배포하고 돌리는 것이다. 예컨대 Daff가 TensorFlow 추천기를 써서 청취자의 기존 재생 목록을 확장할
  곡을 추천한다고 상상해 보라. TensorFlow 모델은 직렬화되어 **playlist recommender** 데이터
  프로덕트로 배포될 수 있다. 그 데이터 프로덕트는 청취자의 재생 목록을 소비하고 어떤 곡이 다음에
  추천되는지 예측하며, 그것을 청취자가 재생 목록을 재생할 때 읽히고 쓰이는 재생 목록 확장 추천으로
  저장한다. 추천 모델은 프로그램과 원하는 프로그래밍 언어 안에서 실행되지만 그 계산은 주로
  모델이 수행한다** (12장, p.229).[^dehghani2022]
- 배치 자리가 여럿 열려 있다 — **ML 모델은 마이크로서비스와 애플리케이션뿐 아니라 데이터
  프로덕트 등 여러 다른 맥락에 배포될 수 있다** (12장, p.229).[^dehghani2022]
  [데이터 플랫폼 사용자 여정](../concepts/data-platform-user-journeys.md)의 "ML 모델을 데이터
  프로덕트로 배포하는 여정"이 이것의 플랫폼 쪽 서술이다.

## 변환 ④ 시간 가변 변환

- 세 갈래 전부에 걸리는 공통 성질 — **모든 변환의 공통 특징은 시간 축 — 처리 시간과 실제 시간 —
  을 존중하는 것이다. 변환 코드는 입력을 처리할 때와 각각의 시간을 가진 출력을 생성할 때 시간
  파라미터를 인지한다** (12장, p.229).[^dehghani2022]
- 두 시간이 각각 어디서 온다 — **입력 포트 기제가 각 소스의 처리 시간을 추적한다. 변환 코드는
  소스 데이터에 수행된 계산에 근거해 자기 출력의 **실제 시간**을 생성한다. 출력 포트는 변환된
  데이터를 데이터 프로덕트의 내부 처리 시간 카운트와 함께 서빙한다** (12장,
  p.230).[^dehghani2022]
  - 곧 **실제 시간은 변환 로직이 계산하고, 처리 시간은 런타임이 찍는다**. 이 분업이
    [바이템포럴 데이터](../concepts/bitemporal-data.md)의 두 축이 실제로 만들어지는 자리다.

## 변환 설계의 구성 요소

- 저자가 프레임워크 의존을 먼저 인정한다 — **변환의 설계 — 빌드 시점 정의·배포·실행 — 는 선택한
  프레임워크와 기저 기술에 크게 의존한다. 변환이 선언적 문장으로 구현되든 프로그래밍 코드로
  구현되든, 변환을 빌드하고·테스트하고·배포하고·돌리는 데는 플랫폼 능력이 필요하다** (12장,
  p.230).[^dehghani2022]
- 표 12-3 (12장, p.231):[^dehghani2022]

| 구성 요소 | 저자의 정의 |
|---|---|
| 변환 아티팩트(transformation artifacts) | 변환을 정의하는 코드·설정·문장 또는 모델. 이 아티팩트는 특정 **기록 시간(record time)**에 대해 출력을 생성하기 위해 입력 데이터 위에서 실행된다 |
| 변환 런타임 환경 | 변환은 그 설정에 근거해, 예컨대 정기적으로 또는 필요한 입력 데이터의 가용성에 따라 호출된다. 호출되면 실행할 계산 환경 — 데이터 프로덕트 컨테이너로 경계 지어진 — 을 요구한다. 기저 플랫폼이 이 환경을 제공한다 |
| 임시 스토리지 | 변환 코드의 단계들은 변환의 여러 국면에 걸쳐 상태를 유지하는 임시 스토리지에 대한 접근을 요구할 수 있다. 기저 플랫폼이 제공한다 |

- 그림 12-15는 이 셋을 **데이터 프로덕트 컨테이너** 안에 두고, 도메인 데이터를 그 옆에 그린다
  (12장, p.230).[^dehghani2022] 컨테이너의 정의는
  [데이터 프로덕트의 포트와 사이드카](../concepts/data-product-ports-and-sidecar.md)가 받는다.

## 12장이 스스로 정리한 것

- 서빙 쪽 제약이 어디서 나왔는지를 저자가 되짚는다 — **분산 메시 아키텍처에서 데이터를 서빙하기
  위해 나는 데이터 프로덕트 출력 포트의 몇 가지 성질을 식별했다: **읽기 전용**과 **다중 양식
  API**를 통해 **바이템포럴·불변** 데이터를 서빙하는 것이다. 이 제약들은 데이터 메시의 목표와
  가정에서 나왔다** (12장, p.231).[^dehghani2022] 네 줄로 그 대응이 적힌다 (12장,
  p.231):[^dehghani2022]
  - **데이터 프로덕트는 자기 도메인 지향 데이터를 넓은 데이터 사용자 집합에 네이티브하게 서빙한다
    (다중 양식 접근).**
  - **데이터 프로덕트는 시간적 분석 사용 사례에 쓰일 수 있다 (바이템포럴).**
  - **데이터 프로덕트는 다른 데이터 프로덕트에서 안전하게 데이터를 소비하고, 변환하고, 서빙하면서
    한 시점의 최종적 일관성이라는 전역 상태를 유지할 수 있다 (바이템포럴).**
  - **데이터 프로덕트 사용자는 분석과 ML을 위해 데이터를 처리한다 (읽기 전용).**
- 소비 쪽 요약 — **데이터 프로덕트는 자기 상류 데이터를 어디서 어떻게 받는지에 대한 통제권을
  갖는다. 자기 입력 포트를 써서 같은 도메인의 협력 운영 시스템이나 상류 데이터 프로덕트에서
  데이터를 얻는다. 입력 포트는 멀티클라우드 배포나 점진적 클라우드 이관을 뒷받침하는 서로 다른
  호스팅 환경 사이의 데이터 이동을 구현할 수 있다** (12장, p.231).[^dehghani2022]
- 변환 쪽 요약 — **데이터 프로덕트는 더 높은 가치의 데이터를 서빙하기 위해 거의 늘 어떤 종류의
  변환을 수행한다. 변환 구현은 데이터 파이프라인 함수·정교한 질의·ML 모델 추론 등 여러 형태를
  가질 수 있다** (12장, p.231).[^dehghani2022]
- 그리고 저자가 이 장의 지위를 스스로 낮춘다 — **이 장은 데이터 공유라는 핵심 기능에서 데이터
  프로덕트 설계에 대한 고수준의 사고 틀과 접근을 설정한다. 나는 미래의 데이터 메시 구현들이
  이것을 평가하고 정련하기를 기대한다** (12장, p.231).[^dehghani2022]
