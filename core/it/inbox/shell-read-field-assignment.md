하나의 질문: **표준 입력의 한 줄은 어떤 규칙으로 `var` 피연산자들에 나눠 담기는가.**

[필드 분리와 IFS](shell-field-splitting.md)는 확장 결과가 **몇 개로 쪼개지는가**만 정한다. 쪼갠
것을 **어느 변수에 넣는가**는 그 절이 답하지 않는 질문이고, 규범은 `read` 유틸리티 페이지에 따로
있다. 둘을 한 덩어리로 알면 사고를 절반만 설명하게 된다 — 값이 사라지는 것은 분리의 규범이고,
남은 값이 앞으로 밀려 다른 변수로 들어가는 것은 여기 배분의 규범이다.

## 무엇을 읽는가

- `read`는 표준 입력에서 **논리적 줄(logical line) 하나**를 읽어 하나 이상의 셸 변수에 넣는다
  (DESCRIPTION):[^opengroup2024-shell]

> The `read` utility shall read a single logical line from standard input into one or more shell
> variables.

- 문법은 `read [-r] [-d delim] var...`다 (SYNOPSIS).[^opengroup2024-shell] `-d`는 Issue 8에서
  들어왔다 — 변경 이력이 `Austin Group Defect 243 is applied, adding the -d option`이라 적는다
  (CHANGE HISTORY).[^opengroup2024-shell]
- 읽은 뒤 맨 앞에 오는 처리는 하나다: 끝의 논리적 줄 구분자가 있으면 제거한다
  (DESCRIPTION).[^opengroup2024-shell] 그다음이 아래 두 갈래(빈 `IFS`냐 아니냐)로 나뉜다.

## 배분 전에 필드가 만들어진다

- `IFS`가 unset이거나 비어 있지 않으면 §2.6.5 필드 분리의 **수정판**이 적용된다
  (DESCRIPTION):[^opengroup2024-shell]

> If `IFS` is unset, or is set to any non-empty value, then a modified version of the field
> splitting algorithm specified in 2.6.5 Field Splitting shall be applied, with the modifications as
> follows:

- 첫째 수정은 **입력 전체를 확장 결과 취급**하는 것이다 (DESCRIPTION):[^opengroup2024-shell]

> The input to the algorithm shall be the logical line (minus terminating delimiter) that was read
> from standard input, and shall be considered as a single initial field, all of which resulted from
> expansions, with any escaped byte and the preceding `<backslash>` escape character treated as if
> they were the result of a quoted expansion, and all other bytes treated as if they were the
> results of unquoted expansions.

  - 읽어 들인 바이트는 **전부 "인용하지 않은 확장의 결과"**로 간주된다. 그러므로 필드 분리
    페이지의 규칙이 그대로 걸린다 — IFS 공백류는 연달아 와도 필드를 하나만 끊고, IFS 비공백류는
    빈 필드를 만들어 낸다.
  - 예외는 백슬래시로 이스케이프된 바이트뿐이다. 그것만 "인용된 확장" 취급이라 분리 대상에서
    빠진다.

## 필드는 변수 개수보다 하나 적게 만들어진다

- 둘째 수정이 이 페이지의 중심 규정이다 (DESCRIPTION):[^opengroup2024-shell]

> The loop over the contents of that initial field shall cease when either the input is empty or
> `n` output fields have been generated, where `n` is one less than the number of `var` operands
> passed to the `read` utility. Any remaining input in the original field being processed shall be
> returned to the `read` utility "unsplit"; that is, unmodified except that any leading or trailing
> `IFS` white space, as defined in 2.6.5 Field Splitting, shall be removed.

- 상한이 **n = 변수 개수 − 1**이다. 변수가 셋이면 출력 필드는 최대 둘까지만 만들어지고, 남은
  입력은 쪼개지 않은 채(unsplit) 돌아온다. 그 남은 입력에서 떨어지는 것은 앞뒤의 IFS 공백류뿐이고
  가운데는 손대지 않는다.
- 그래서 **마지막 변수는 "남은 것 전부"를 받는다.** 구분자가 몇 개 더 들어 있어도 마지막 변수
  안에서는 쪼개지지 않는다.
- 변수가 하나뿐이면 상한이 0이라 필드가 아예 안 만들어진다 (DESCRIPTION):[^opengroup2024-shell]

> Note that in the case where just one `var` operand is given on the `read` command line, the
> modified field splitting algorithm ceases after producing zero output fields and simply returns
> the original input field, with any leading and trailing `IFS` white space removed, as unsplit
> input. This unsplit input is assigned to the variable named by the `var` operand.

  - `read line` 꼴이 줄을 통째로 담는 근거가 이것이다. 다만 **앞뒤 IFS 공백류는 잘린다** —
    통째라고 해서 원문 그대로는 아니다.
- 스펙의 예제가 이 상한을 그대로 보여준다. 첫 필드가 `xx`로, 나머지 줄 전체가 `yy`로 간다
  (EXAMPLES):[^opengroup2024-shell]

  ```sh
  while read -r xx yy
  do
      printf "%s %s\n" "$yy" "$xx"
  done < input_file
  ```

  - 원문은 이 명령이 "prints a file with the first field of each line moved to the end of the line"
    이라고 적는다 (EXAMPLES).[^opengroup2024-shell]

## 배분 규칙 세 줄

- 순서 계약과 두 검사 (DESCRIPTION):[^opengroup2024-shell]

> The specified `var` operands shall be processed in the order they appear on the command line, and
> the output fields generated by the field splitting algorithm shall be used in the order they were
> generated, by repeating the following checks until neither is true:
>
> - If more than one `var` operand is yet to be processed and one or more output fields are yet to
>   be used, the variable named by the first unprocessed `var` operand shall be assigned the value
>   of the first unused output field.
> - If exactly one `var` operand is yet to be processed and there was some remaining unsplit input
>   returned from the modified field splitting algorithm, the variable named by the unprocessed
>   `var` operand shall be assigned the unsplit input.

- 그리고 그러고도 변수가 남았을 때 (DESCRIPTION):[^opengroup2024-shell]

> If there are still one or more unprocessed `var` operands, each of the variables names by those
> operands shall be assigned an empty string.

  - 원문의 `variables names by`는 스펙의 오식이다(문맥상 `named by`). 직인용이므로 고치지 않는다.
- 세 줄을 합치면 배분은 이렇다: **앞에서부터 짝을 맞추고, 마지막 변수는 나머지를 통째로 받고,
  그래도 남은 변수는 빈 문자열이 된다.** 마지막 조항이 중요한 이유는 남은 변수가 unset으로
  남는 것이 아니라 **빈 문자열이 대입**되기 때문이다 — 그 변수에 이전 값이 있었다면 지워진다.
- 검사에 **자리(위치) 개념이 없다.** "첫 미처리 변수에 첫 미사용 필드"일 뿐이라, 입력에서 몇
  번째 칸이었는지는 이 단계가 알지 못한다.
- 같은 변수 이름을 두 번 적으면 마지막 대입이 이긴다 (APPLICATION USAGE):[^opengroup2024-shell]

> Since the `var` operands are processed in the order specified on the command line, if any variable
> name is specified more than once as a `var` operand, the last assignment made is the one that is
> in effect when `read` returns, including when an empty string is assigned because no field data
> was available.

## 뒤 칸이 당겨 읽힌다

칸을 갈라 읽는 코드의 사고는 **두 규범이 이어 붙어서** 일어난다. 그래서 한쪽만 알면 설명이
절반에서 끊긴다.

- **1단계 — 분리가 빈 칸을 지운다.** 구분자가 IFS 공백류면 연달아 와도 필드를 하나만 끊으므로,
  값이 비어 있던 칸은 출력 필드로 나오지 않는다 (§2.6.5, [필드 분리와
  IFS](shell-field-splitting.md)).[^opengroup2024-shell]
- **2단계 — 배분이 남은 것을 앞에서부터 채운다.** 위 검사에 자리 개념이 없으므로 세 번째 칸의
  값이 두 번째 변수로 들어간다. 사라진 것은 한 칸인데 **틀리는 것은 그 뒤 전부**다.
- **3단계 — 남은 변수가 빈 문자열이 된다.** 필드가 하나 모자라므로 마지막 변수에 빈 문자열이
  대입된다. 원래 값이 있던 자리인데도 그렇다.
- **종료 상태는 0이다.** 0이 아닌 값은 EOF(1)와 오류(1 초과)뿐이고 이 경우는 둘 다 아니다
  (EXIT STATUS).[^opengroup2024-shell] 즉 이 사고는 어떤 게이트에도 걸리지 않고 통과한다.

막는 방법은 배분 쪽이 아니라 **분리 쪽**에 있는데, 스펙이 그 길을 좁혀 놓았다.

- `<space>`·`<tab>`·`<newline>`은 `IFS` 값에 들어 있는 한 **언제나** IFS 공백류다 (§2.6.5,
  [필드 분리와 IFS](shell-field-splitting.md)).[^opengroup2024-shell] 그러므로 탭으로 칸을 가른
  자료를 `IFS`에 탭만 넣어 읽어도 **빈 칸은 여전히 사라진다.** "구분자를 좁히면 되겠지"가
  듣지 않는 자리다.
- 빈 칸이 살아남으려면 구분자가 애초에 공백류가 아닌 문자여야 한다. 그때는 분리 알고리즘이
  빈 후보도 필드로 끊으므로 자리가 밀리지 않는다 (§2.6.5).[^opengroup2024-shell]
- #hypothesis 자리를 지켜야 하는 자료를 `read`로 읽는 한, 공백류 구분자를 피하는 것 말고
  스펙 안에 다른 길은 없어 보인다 — 스펙이 "유일하다"고 말하지는 않으므로 단정하지 않는다.

여기서 말할 수 있는 것은 **표준이 요구하는 것**까지다. 특정 셸이 실제로 무엇을 하는지는 그 셸의
문서가 답한다.

## IFS가 빈 문자열이면 배분이 없다

- 배분 규칙이 통째로 건너뛰어지는 갈래가 하나 있다 (DESCRIPTION):[^opengroup2024-shell]

> The terminating logical line delimiter (if any) shall be removed from the input. Then, if the
> shell variable `IFS` (see 2.5.3 Shell Variables) is set, and its value is an empty string, the
> resulting data shall be assigned to the variable named by the first `var` operand, and the
> variables named by other `var` operands (if any) shall be set to the empty string. No other
> processing shall be performed in this case.

- 첫 변수가 줄 전체를 받고 나머지 변수는 전부 빈 문자열이 된다.
- **앞뒤 IFS 공백류 제거도 일어나지 않는다** — `No other processing`이 그것까지 막는다. 줄을
  한 바이트도 손대지 않고 받는 자리는 여기뿐이고, 변수 하나만 준 경우와도 다르다(그쪽은 앞뒤
  공백류가 잘린다).
- `var` 피연산자로 `IFS`를 지정하면 동작은 미지정(unspecified)이다. `LANG`·`LC_CTYPE`·`LC_ALL`을
  지정해서 `IFS`의 바이트가 문자를 이루는 방식이나 무엇이 IFS 공백류인지가 바뀌는 경우도, 그
  변경이 그 `read`의 필드 분리에 어떤 영향을 주는지 미지정이다 (OPERANDS).[^opengroup2024-shell]

## 백슬래시와 논리적 줄

- `-r`이 없으면 백슬래시가 이스케이프 문자다 (DESCRIPTION):[^opengroup2024-shell]

> If the `-r` option is not specified, `<backslash>` shall act as an escape character. An unescaped
> `<backslash>` shall preserve the literal value of a following `<backslash>` and shall prevent a
> following byte (if any) from being used to split fields, with the exception of either `<newline>`
> or the logical line delimiter specified with the `-d delim` option (if it is used and `delim` is
> not `<newline>`); it is unspecified which.

- 백슬래시가 제거되는 시점이 두 갈래다 (DESCRIPTION):[^opengroup2024-shell]

> The `<backslash>` and the excepted character shall be removed before splitting the input into
> fields. All other unescaped `<backslash>` characters shall be removed after splitting the input
> into fields.

  - 줄 이음(line continuation)을 이루는 백슬래시만 **분리 전에** 사라지고, 나머지는 **분리 후에**
    사라진다. 순서가 다르므로 결과도 다르다 — 후자는 사라지기 전에 이미 "분리하지 말 것"이라는
    표시로 쓰였다.
- `-r`은 이 전부를 끈다: `Do not treat a <backslash> character in any special way. Consider each
  <backslash> to be part of the input line.` (OPTIONS)[^opengroup2024-shell]

## 종료 상태와 실행 환경

- 종료 상태는 셋이다 (EXIT STATUS):[^opengroup2024-shell]

| 값 | 원문 |
|---|---|
| 0 | `Successful completion.` |
| 1 | `End-of-file was detected.` |
| 1 초과 | `An error occurred.` |

  - EOF와 오류를 가르게 된 것이 Issue 8이다 — `Austin Group Defect 367 is applied, requiring that
    read distinguishes between detecting end-of-file and an error occurring` (CHANGE
    HISTORY).[^opengroup2024-shell]
- 구분자를 만나기 전에 EOF가 오면 **변수는 위 규칙대로 세팅되고 종료 상태만 1이 된다**
  (DESCRIPTION).[^opengroup2024-shell] 반쯤 읽힌 값이 변수에 남아 있다는 뜻이다.
- 변수 대입은 현재 셸 실행 환경에 영향을 준다 (§2.13, [셸 실행 환경과
  서브셸](shell-execution-environment.md)). `readonly`로 표시된 변수처럼 대입이 실패하면 `read`
  처리의 오류로 쳐서 1 초과를 낸다. 오류를 낸 변수보다 **앞의** 변수는 세팅되고, **뒤의** 변수도
  세팅되는지 아니면 거기서 처리가 멈추는지는 미지정이다 (DESCRIPTION).[^opengroup2024-shell]
- 서브셸이나 별도 유틸리티 실행 환경에서 부르면 호출자의 변수는 바뀌지 않는다 — 스펙이 든 예가
  `(read foo)`, `nohup read ...`, `find . -exec read ... \;` 셋이다
  (DESCRIPTION).[^opengroup2024-shell]
- 그래서 이 판본은 `read`를 intrinsic 유틸리티로 요구한다 (APPLICATION USAGE,
  §1.7).[^opengroup2024-shell] 원래 셸 내장이던 것을 서술을 풍부하게 하려고 독립 유틸리티로
  떼어낸 내력이 RATIONALE에 적혀 있다.[^opengroup2024-shell]

## 이식성에 걸리는 자리

- `-d`를 쓰면 `-r`도 같이 써야 한다 (APPLICATION USAGE):[^opengroup2024-shell]

> Implementations differ in their handling of `<backslash>` for line continuation when `-d delim` is
> specified (and `delim` is not `<newline>`); some treat `<backslash>delim` (or
> `<backslash><NUL>` if `delim` is the null string) as a line continuation, whereas others still
> treat `<backslash><newline>` as a line continuation. Consequently, portable applications need to
> specify `-r` whenever they specify `-d delim` (and `delim` is not `<newline>`).

- `-d`에 빈 문자열을 주면 구분자가 널 바이트가 되어 `find -print0`이 낸 목록을 처리할 수 있다.
  개행이 든 경로 이름도 옳게 다뤄진다. 다만 **`-d`와 빈 문자열을 별개 인자 둘로** 적어야 한다
  (APPLICATION USAGE).[^opengroup2024-shell]
- 종료 상태가 1일 때 첫 변수의 값이 비어 있지 않더라도 쓰지 말라는 권고가 붙어 있다 — 목록을
  내던 명령이 경로 이름을 반만 쓰고 끝난 결과일 수 있어서다 (APPLICATION
  USAGE).[^opengroup2024-shell]
- `delim`이 한 바이트 문자도 빈 문자열도 아니면 동작은 미지정이다 (OPTIONS).[^opengroup2024-shell]
