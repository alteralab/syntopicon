KEY: catalog-prerequisites
--- SUMMARY ---
판정 재료 요약.

(a) Polaris류 카탈로그의 실체: Apache Polaris는 Iceberg REST protocol 구현 서비스로, 존재 이유가 '다수 query engine이 같은 테이블을 안전하게 동시 read/write'하게 하는 것이다. 핵심 기능 3종 — (1) 동시 다중 writer의 원자적 metadata pointer swap(Iceberg 스펙: "An atomic swap... provides the basis for serializable isolation" + optimistic concurrency retry), (2) RBAC(다수 service principal 전제), (3) credential vending(STS 단기 자격증명을 엔진에 위임) — 은 전부 '신뢰 경계를 넘는 다수 행위자'를 전제한다. 운영 풋프린트는 Java 21+/Quarkus 상시 서버 + 프로덕션 필수 PostgreSQL. Hive Metastore·Glue·Unity Catalog도 공통 전제가 동일하다(다수 엔진·다수 사용자·동시 쓰기·접근 제어·감사).

(b) 항목별 대조 — sources.yaml(1인 작성·소비자 2개·5~30항목)이 카탈로그 서비스의 전제를 공유하는가: [멀티 엔진 상호운용] 불공유 — 소비자 2개가 같은 리포의 자작 도구라 프로토콜 경계가 없다. [동시 다중 writer CAS] 불공유 — writer 1인이며 git commit이 이미 원자적·이력 보존 쓰기다(Iceberg가 catalog를 요구하는 유일한 hard 이유가 바로 이 CAS인데, 여기선 성립 조건 자체가 없음). [멀티테넌트 RBAC·감사] 불공유 — 1인, git log가 감사 이력. [credential vending] 불공유 — 미러 대상은 공개 벤더 문서 리포. 4개 전제 중 공유하는 것이 0개다.

(c) 사용자 직관이 옳은 부분과 그 관행적 실현 형태: '계약의 명확성'과 '조작의 정형화'는 실재하는 요구이고 업계 표준이 있다 — 다만 CRUD API가 아니라 (1) 스키마: sources.yaml에 JSON Schema를 정의해 구조·필수 필드·타입을 선언(input 계약; SchemaStore가 보여주듯 설정 파일 스키마 검증은 에디터 통합 수준의 관행), (2) 검증 게이트: tools/validate에 스키마 검증을 편입해 커밋 게이트로(이 프로젝트의 기존 패턴과 동형), (3) 단일 소비 경로: tools/pull만 파일을 읽게 하면 output 계약은 그 도구의 인터페이스가 된다, (4) git = versioned·immutable·원자적 저장(OpenGitOps 4원칙이 이 정식화 자체). Backstage처럼 '카탈로그'를 표방하는 시스템조차 source of truth는 git 내 YAML이고 서비스는 파생 조회 레이어다.

(d) 파일→서비스 승격의 실측 임계: crates.io는 index 176MiB·전 클라이언트 전량 다운로드 지경(수만 항목×수백만 소비자)에서 sparse HTTP index로, Homebrew는 수백만 사용자의 git fetch 비용 때문에 2023년에야 JSON API로 — 그마저 읽기 경로만 서비스화했고 쓰기는 여전히 git 파일+CI다. 5~30항목·소비자 2개는 이 임계의 수천~수만분의 1 규모다.

결론적 판정 재료: 카탈로그 서비스의 존재 이유(동시성 CAS·다중 신뢰 경계·credential 위임)는 이 레지스트리에 하나도 성립하지 않으므로 Polaris형 승격은 전제 불일치이고, 사용자가 원하는 '확실한 input/output'은 schema + validate 커밋 게이트 + 단일 pull 소비자 + git 이력이라는 파일 기반 정식화로 얻는 것이 업계 관행이다.
--- FINDINGS ---
[LB] Apache Polaris는 Apache Iceberg 테이블용 catalog 구현체로, Iceberg REST protocol을 구현해 '여러 REST 호환 query engine(Spark, Flink, Trino, Doris, StarRocks, Snowflake 등)이 같은 Iceberg 테이블에 중앙화·보안 read/write 접근'을 제공하는 것이 존재 이유다. 즉 멀티 엔진 상호운용이 전제이자 목적이다.
     src: https://polaris.apache.org/ (2026-08-08 확인 (main 브랜치 문서))
[LB] Polaris의 핵심 기능 집합은 (1) catalog/namespace/table 계층 엔티티 관리, (2) RBAC — "Polaris uses a role-based access control (RBAC) model that lets you centrally configure access for Polaris service principals to catalogs, namespaces, and tables", (3) credential vending — 테이블 로드 시 해당 테이블 위치·연산으로 스코프된 단기 스토리지 자격증명(AWS STS AssumeRole + inline session policy)을 엔진에 발급. 전부 '다수 principal·다수 엔진·클라우드 스토리지 권한 위임'을 전제로 하는 기능이다.
     src: https://raw.githubusercontent.com/apache/polaris/main/site/content/in-dev/unreleased/_index.md (2026-08-08 확인)
[LB] Polaris의 운영 풋프린트: Java 21+ / Quarkus 기반 상시 서버로, Docker·Kubernetes(Helm) 배포를 상정하며, 프로덕션에는 관계형 DB(JDBC, PostgreSQL 권장)가 영속 metastore로 필수다. 기본 in-memory 백엔드는 "not suitable for production. Data will be lost when the server restarts!"라고 명시된다. 즉 '카탈로그 서비스 도입' = 상시 프로세스 + DB 운영이라는 고정비를 진다.
     src: https://raw.githubusercontent.com/apache/polaris/main/site/content/in-dev/unreleased/metastores/_index.md (2026-08-08 확인)
[LB] Iceberg가 catalog를 요구하는 공식 이유는 '동시 다중 writer 간 원자적 metadata pointer 교체(compare-and-swap)'다. 스펙 원문: "An atomic swap of one table metadata file for another provides the basis for serializable isolation." Writer는 optimistic concurrency로 커밋하며, 커밋 = "swapping the table's metadata file pointer from the base version to the new version"이고 stale이면 "retry the update based on the new current version". 이 CAS 지점을 제공하는 것이 catalog의 존재 이유다.
     src: https://raw.githubusercontent.com/apache/iceberg/main/format/spec.md (2026-08-08 확인 (main))
[LB] Iceberg reliability 문서는 catalog가 푸는 문제를 명시한다: Hive 테이블은 metastore+파일시스템 리스팅 혼합 추적이라 "This makes atomic changes to a table's contents impossible"이고, S3 같은 eventually consistent 스토어에서 파일 리스팅으로 상태를 재구성하면 "may return incorrect results". Iceberg는 "Commits replace the path of the current table metadata file using an atomic operation"으로 해결한다. 즉 서비스형 catalog의 본질 기능은 '분산 환경에서의 원자적 커밋 지점'이지 '레지스트리 CRUD 편의'가 아니다.
     src: https://raw.githubusercontent.com/apache/iceberg/main/docs/docs/reliability.md (2026-08-08 확인 (main))
[  ] Hive Metastore가 파일이 아닌 RDBMS 백엔드 서비스인 이유: 메타데이터에 대한 효율적 질의(queriability)와, HDFS 파일은 random update가 불가능해 "no clear way to implement an object store on top of HDFS due to lack of random updates to files"이기 때문. 배포 모드도 remote Thrift service / embedded / local 3종 — 즉 '서비스화'는 다수 클라이언트의 저지연 동시 메타데이터 접근이 전제다.
     src: https://cwiki.apache.org/confluence/display/Hive/Design (2026-08-08 확인)
[  ] AWS Glue Data Catalog는 "your persistent technical metadata store"인 계정/리전 단위 관리형 서비스로, 콘솔·API·CLI·CloudFormation·crawler 등 다수 경로의 다수 소비자(ETL job, Athena 등)가 전제다. Unity Catalog는 "the unified governance layer for data and AI built into Databricks"로 access control·audit log·lineage·discovery를 워크스페이스 전반에 제공 — 두 제품 모두 다수 사용자·다수 엔진·감사가 공통 전제다.
     src: https://docs.aws.amazon.com/glue/latest/dg/start-data-catalog.html (2026-08-08 확인)
[LB] 선언적 레지스트리 파일이 'input 확실성'을 얻는 업계 표준은 스키마 언어 + 자동 검증이다: "JSON Schema is a declarative language for defining structure and constraints for JSON data"(YAML 포함 도구 생태계), 그리고 SchemaStore는 "schemas for all commonly known JSON file formats"를 모아 VS Code·IntelliJ 등 에디터가 설정 파일을 실시간 검증하게 하며 하루 1TB 이상의 스키마를 서빙한다. 즉 '계약의 명확성'은 API endpoint가 아니라 schema+validator로 실현되는 것이 관행이다.
     src: https://json-schema.org/overview/what-is-jsonschema (2026-08-08 확인)
[LB] 대규모 조직조차 소프트웨어 카탈로그의 source of truth를 git 내 YAML 파일로 둔다: Backstage(Spotify 발, CNCF) Software Catalog는 "The source of truth for the components in your software catalog are metadata YAML files stored in source control"이며 "built around the concept of metadata YAML files stored together with the code". 서비스(DB·UI)는 이 파일들을 수확(harvest)해 보여주는 파생 레이어일 뿐이다. 즉 '카탈로그'라는 개념 자체가 파일-레지스트리와 양립하며, 서비스는 다수 팀·다수 리포 규모에서 파일 위에 얹는 조회 레이어다.
     src: https://backstage.io/docs/features/software-catalog/ (2026-08-08 확인)
[  ] 파일 레지스트리의 '조작의 정형화'는 GitOps 원칙(CNCF OpenGitOps v1.0)으로 표준화돼 있다: (1) Declarative — "desired state expressed declaratively", (2) Versioned and Immutable, (3) Pulled Automatically, (4) Continuously Reconciled. 쓰기 = git commit(원자적·이력 보존), 읽기 = 도구의 pull — 이것이 'input/output이 확실한 조작'의 파일 기반 정식화다.
     src: https://opengitops.dev/ (2026-08-08 확인)
[LB] 파일/git 레지스트리가 HTTP 서비스로 승격된 실측 임계 (1) crates.io: git 기반 index가 비압축 176MiB, clone 시 215MiB에 달하고 "the full crate index is relatively big and slow to download... will keep growing as crates.io grows", CI가 "download the full index, use only a tiny fraction of it, and throw it away" 하는 지경이 되어서야 sparse HTTP index로 이전(RFC 2789, 2020). 수만 개 항목 × 수백만 소비자 규모의 문제다.
     src: https://rust-lang.github.io/rfcs/2789-sparse-index.html (RFC 2020년, 2026-08-08 확인)
[LB] 실측 임계 (2) Homebrew: 2023년 4.0에서야 "the slow git fetch of the huge homebrew/core and homebrew/cask taps' Git repositories"를 없애려 formulae.brew.sh JSON API 다운로드로 전환 — "the largest change we have made to our update process since we split Homebrew/brew and Homebrew/homebrew-core". 수천 개 formula × 수백만 사용자 규모에서, 그것도 '읽기 배포 경로'만 API화했고 쓰기(formula 정의)는 여전히 git 리포의 파일 + CI 검증이다.
     src: https://brew.sh/2023/02/16/homebrew-4.0.0/ (2023-02-16)
--- UNRESOLVED ---
 - WebSearch 세션 예산(200회)이 소진돼 모든 검증을 알려진 URL의 WebFetch로 수행했다. 교차 검증용 2차 소스(예: Snowflake의 Polaris 발표 블로그, Netflix의 Iceberg 설계 배경 발표)는 확인하지 못했다.
 - Iceberg terms 페이지의 'catalog must support atomic operations to update the current metadata pointer' 축자 문구는 페이지가 내비게이션만 렌더링돼 직접 확인 실패 — 대신 스펙(format/spec.md)의 Optimistic Concurrency 절 원문으로 동일 내용을 확보했다.
 - crates.io RFC 시점의 정확한 crate 수와 Homebrew formula 수는 1차 소스에서 숫자로 확인하지 못했다(index 크기 176MiB만 확보). '수만 항목·수백만 소비자'는 규모 추정이다.
 - Polaris 버전 릴리스 문서(releases/1.x)가 404라 main 브랜치 in-dev(unreleased) 문서를 사용했다 — 릴리스판과 세부 표현이 다를 수 있으나 기능 집합 자체는 안정적이다.
 - Unity Catalog 문서는 멀티 유저·멀티 워크스페이스 전제를 명시적 문장으로 선언하지 않는다 — 기능 구성(workspace binding, audit log, cross-workspace governance)에서 구조적으로 함의될 뿐이다.

KEY: declarative-registry-practice
--- SUMMARY ---
사용자 직관 중 옳은 부분 — "input/output이 확실한 계약과 정형화된 조작이 필요하다" — 은 업계에서 실제로 실현되고 있으나, 그 표준 실현형은 Polaris류 카탈로그 서비스가 아니라 3요소 패턴이다: 선언 파일(상태) + JSON Schema(계약) + 결정적 CLI 동사(연산). 실증: (1) pre-commit의 .pre-commit-config.yaml은 sources.yaml과 동형의 '외부 repo+rev 핀 레지스트리'인데 validate-config(검증)·autoupdate(update 연산)·sample-config(생성)라는 CLI 동사로 관리되고 SchemaStore에 스키마가 등재돼 있다. (2) dbt packages.yml은 git URL·revision 핀·private provider·로컬 폴백까지 sources.yaml과 항목 구성이 거의 일치하며, 공식적으로 파일+`dbt deps`+package-lock.yml로만 관리되고 API 서비스가 없다. (3) kubectl/terraform은 API 서버·원격 인프라가 실재하는 경우조차 인간 인터페이스가 선언 파일+diff/plan/apply 동사임을 보여준다(kubectl --validate 기본값 strict). (4) SchemaStore 카탈로그 실측 1,414개 스키마 + check-jsonschema의 vendored 검증 훅 16종+는 '파일+스키마=타입 있는 계약'이 생태계 표준 상용구임을 입증한다. KEY: file-to-service-threshold
--- SUMMARY ---
파일 레지스트리→서비스 승격의 실측 임계를 1차 소스로 조사했다. 승격을 일으킨 변수는 사례 전반에서 4개로 수렴한다: 동시 writer >1 (Terraform remote state의 유일한 명시 근거 = 팀 동기화+락), 신뢰 경계를 넘는 다수 클라이언트 (Hive remote metastore — 커넥션 부하·DB 권한 문제), 전량 복사 불가능한 규모의 질의 (Hive queriability — 단 crates.io는 176MiB 인덱스에서도 동적 API를 '유지비가 정적 파일보다 훨씬 비싸다'며 기각하고 sparse 정적 파일을 택함), 네트워크 분리 (SQLite 공식 체크리스트). 항목 수·변경 빈도 단독은 어느 사례에서도 승격 사유가 아니었다. 역방향으로 Iceberg는 Hive 중앙 metastore를 버리고 메타데이터를 파일 트리로 되돌렸으며 서비스는 '원자적 포인터 스왑 1개'로 축소했고, PyPI(PEP 503)의 읽기 경로는 정적 파일 규격이며, GitOps는 계약 명확성을 API가 아닌 '버전 관리되는 선언 파일'로 명문화했다. 판정: 항목 5~30·writer 1인·로컬 소비자 2개인 sources.yaml은 4개 변수 전부 미충족으로 확정적 파일 측이다. 사용자 직관(계약 명확성·조작 정형화)이 옳은 부분은 실재하나, 관행상 그 실현 형태는 CRUD 서비스가 아니라 '스키마 정의 + 선언 파일 + 커밋 게이트 검증(validate)'이고, 원자성·이력은 git이 이미 제공한다. Polaris류 catalog 서비스가 전제하는 조건(다수 엔진·다수 조직·신뢰 경계)은 이 레지스트리에 부재한다.
