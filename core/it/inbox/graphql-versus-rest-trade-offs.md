## 버전 조건

> **버전 조건**: 이 페이지의 채점은 **2025년 저술 시점**의 것이다. 인기 순위(포스트맨 보고서를
> 근거로 든 "REST 다음"), 명세의 상태(2024년 초안이 언제나 200을 쓰는 것에서 벗어나려 한다는
> 것), 그리고 제품 관찰(깃허브의 GraphQL API가 필드를 이따금 버저닝한다는 것)이 그 시점에
> 매인다. 과다 조회와 과소 조회의 규정, 단일 엔드포인트가 공격면과 캐싱에 무엇을 하는가,
> 공격 넷의 기제 자체는 시점에 매이지 않는다.

## REST가 남긴 문제 셋

**이 장은 REST의 부족한 자리에서 시작한다.** 저자들이 **가장 널리 채택됐음에도 REST API에는
단점이 따른다**고 적고 셋을 든다 (6장 §"Problems with REST", p.198).[^dynowski2025]

- **노출하는 데이터 구조와 단단히 결합되는 경향** — REST API의 자원은 전형적으로 엔드포인트가
  드러내는 데이터 모델을 나타내고, **그 결합 때문에 API를 고치지 않고서는 데이터를 바꾸기가
  어렵다.** 데이터가 API로 노출되는 방식을 고치려면 **새 API 판을 내야 할 수 있고 그러면 옛
  클라이언트를 유지하는 어려움으로 이어질 수 있다** (6장, p.198).[^dynowski2025]
- **과다 조회 또는 과소 조회** — 아래 절에서 규정된다.
- **자원 사이의 관계를 다루기 어렵다** — 구현에 따라, **HATEOAS를 쓰지 않거나 관련 데이터를
  응답에 직접 끼워 넣지 않는 REST API는 자원 사이 관계의 관리에 애를 먹을 수 있다.** 저자들의
  예가 **사용자와 그 사용자의 글과 그 글에 달린 댓글을 함께 필요로 하는 클라이언트**다 — 흔히
  API 호출이 여러 번 필요하고 **그 정확한 형식은 API 문서에서 유추해야 한다.** 대안으로
  **그 데이터를 모으는 맞춤 엔드포인트를 구현할 수 있지만 그 접근은 복잡도를 늘리고 클라이언트를
  서버의 API 구조에 결합시킨다** (6장, p.198).[^dynowski2025]
  - 저자들이 REST 쪽 완화책 둘을 함께 적는다 — **HATEOAS는 관련 자원을 찾을 링크를 제공하므로
    자원 사이의 이동을 단순하게 만들 수 있고, 데이터를 끼워 넣는 것은 더 큰 적재물을 대가로
    API 호출 수를 줄일 수 있다** (6장, p.198).[^dynowski2025] HATEOAS의 규정과 실무에서의
    채택 여부는 [REST 아키텍처 스타일의 제약과 성숙도](rest-architectural-style-and-maturity.md)에
    있다.
- **판정** — **GraphQL은 클라이언트가 필요한 특정 데이터만 가져오게 함으로써, 그리고 자원 사이의
  관계를 그래프 기반 모델로 나타냄으로써 REST API의 문제 여럿을 다룬다** (6장,
  p.198).[^dynowski2025]

## 과다 조회와 과소 조회

- 두 낱말이 규정된다 — **API 서비스가 과다 조회(over-fetching)되면 클라이언트가 요구하는 것보다
  더 많은 데이터를 돌려준다. 거꾸로 과소 조회(under-fetching)된 API는 충분한 데이터를 주지 않아
  API 클라이언트가 API 서비스에 추가 요청을 하게 만든다** (6장, p.198).[^dynowski2025]
- **저자들이 곧바로 단서를 단다** — **REST와 마찬가지로 GraphQL도 과다 조회와 과소 조회를 겪을
  수 있다. 다만 GraphQL의 설계는 클라이언트가 정확한 데이터 요구를 명세하게 함으로써 그 위험을
  줄인다** (6장, p.198).[^dynowski2025]
  - **이 단서가 중요하다** — 이 스타일이 두 문제를 없애는 것이 아니라 **위험을 줄인다**는 것이
    저자들의 표현이다. 이 KB의 [GraphQL](../concepts/graphql.md) 페이지가 다른 소스를 근거로
    "응답은 요청된 속성을 정확히 담으며 그 이상도 이하도 아니다"라고 적는 것은 **기제의 서술**이고,
    이쪽은 **그 기제를 쓰는 실무에 남는 위험**을 적는다. 겨루지 않는다.
  - 두 낱말이 공격 이름으로도 돌아온다 — 아래 §"되무는 것 다섯"의 보안 항목을 보라.

## 어디서 왔는가 — 2012년의 모바일

- 저자들은 유래를 **만들어진 시점의 눈으로 보라**고 적는다. **GraphQL은 모바일 기기가 폭발하던
  시기에 나왔다. 2012년 무렵 모바일 웹 브라우저와 HTML5의 기술 스택은 웹 기반 애플리케이션의
  빠른 렌더링과 상호작용성을 제공하기에 충분하지 않았다.** 그리고 **GraphQL은 페이스북이 자사
  iOS·안드로이드 애플리케이션을 다시 쓰려던 노력에서 태어났다.** 그 일이 페이스북(현 메타)으로
  하여금 **그래프 같은 대량의 데이터를 네트워크 너머로 회수할 때 REST API가 요구하는 계산량을
  재평가하게 했다** (6장 §"Origins of GraphQL", p.200).[^dynowski2025]
- **설계를 이끈 관심사가 이어진다** — 사용자가 콘텐츠 소비를 데스크톱에서 모바일로 옮긴 것이
  설계를 이끌었고, **모바일 기기의 두 주된 관심사는 네트워크 효율과 에너지 소비**다. **데이터를
  원하는 모양으로 만들 수 있으면 네트워크로 옮기는 데이터의 양이 줄고 배터리 수명이 보존된다**
  (6장, p.200).[^dynowski2025]
- **동기가 둘 더 있다** (6장, p.200):[^dynowski2025]
  - **클라이언트 플랫폼의 증가** — **REST API 하나로 아주 다양한 클라이언트를 지원하는 것이
    도전이 됐고**, 모든 플랫폼과 클라이언트 판에 걸쳐 호환성과 효율을 보장하는 데 노력이 든다.
  - **REST API의 느린 개발 과정이 빠른 기능 개발의 기대와 맞지 않았다** — REST API에서는
    **서비스가 데이터를 노출하는 방식이 클라이언트 쪽의 구체적 요구와 설계 변경에 맞춰 자주
    고쳐져야 하고**, 달리 말하면 **서비스가 API 엔드포인트에서 돌아오는 데이터의 모양을
    제한한다.** 그것이 반복과 빠른 개발을 가로막았다. **GraphQL은 클라이언트가 API에서 돌아오는
    데이터의 모양을 정하는 방식으로 더 넓은 범위의 애플리케이션을 더 빠르게 개발하도록
    설계됐다** (6장, p.200).[^dynowski2025]

## 무엇이 갈리는가

- 대조가 두 축으로 적힌다 — **REST API는 데이터를 노출하는 데 엔드포인트를 여럿 쓰고 자원
  지향이다. 반면 GraphQL API는 엔드포인트 하나로 노출된다. GraphQL은 흔히 의도 지향이어서 그
  인터페이스가 자원에 실행되는 행위를 서술한다** (6장 §"GraphQL Versus REST",
  p.200).[^dynowski2025]
  - 자원 지향과 의도 지향이라는 낱말 쌍의 규정은 같은 책 2장이 갖고, 이 KB에서는
    [API 이름과 버저닝](api-naming-and-versioning.md)에 있다. 그쪽은 같은 책이 **GraphQL을
    선언적 질의와 명령적 뮤테이션이 섞인 것**으로 적는다고 기록한다 — 이 절의 "흔히 의도 지향"과
    함께 읽어야 할 자리다.

## 식당 비유

**저자들이 차이를 식당 주문에 빗댄다** (6장, p.201).[^dynowski2025] 손님(클라이언트)이 메뉴를
읽고 식사(데이터)를 주문하면 웨이터(API)가 주방(서버)에 주문을 넘기고, 주방이 요청을 처리해
식사를 만들어 웨이터에게 주면 웨이터가 손님에게 낸다.

- **REST에서는 식당의 메뉴가 고정된 API 엔드포인트**이고 **엔드포인트마다 특정한 식사 하나를
  낸다.** 손님이 특별한 식사를 원하면 **먼저 메뉴에 그것을 올려야 하고, 그것은 메뉴를 고치고
  인쇄하고 다시 돌리는 일**을 뜻한다. **잦은 갱신이 필요하다면 특히 자원을 잡아먹는다**
  (6장, p.201).[^dynowski2025]
- **GraphQL에서는 메뉴가 더 유연하다** — **고정된 메뉴 항목을 두는 대신 손님이 원하는 재료를
  정확히 지정할 수 있다.** 주방은 **손님이 요청한 것만 만들어 내므로 낭비(과다 조회)나 추가
  주문의 필요(과소 조회)가 줄어든다.** 그 유연함이 **복잡한 데이터 요구를 맞춤 가능한 질의
  하나로 다루게 한다** (6장, p.201).[^dynowski2025]

## 얻는 것 다섯

**저자들이 절충 절을 장점부터 연다** (6장 §Trade-Offs, pp.222–223).[^dynowski2025]

- **맞춤 가능한 응답 데이터** — **GraphQL API에서 돌아오는 데이터는 그것을 가져오는 데 쓰인
  연산의 모양과 일치한다.** 그 맞춤 가능한 형식이 **과다 조회와 과소 조회를 피하게 돕고 네트워크
  이용을 줄인다.** 나아가 **데이터 맞춤은 클라이언트가 돌아온 데이터를 다시 모양 잡거나
  정규화하지 않고 그대로 다루게 해 준다.**
- **REST보다 덜 수다스럽다** — **API에 데이터를 넣고 빼는 데 API 엔드포인트 하나가 쓰인다.**
  **GraphQL 별칭(alias)과 여러 필드를 한 번에 요청하는 능력이 GraphQL API를 덜 수다스럽게
  (요청 수를 적게) 만들어 여러 번의 왕복을 아낀다.**
- **스키마 인트로스펙션** — **클라이언트가 스키마로부터 API 구성물을 들여다볼 수 있다.**
  스키마를 보면 **연산·필드·스칼라 같은 타입 체계의 정보를 얻을 수 있고**, **타입 이름이 밑줄
  둘(`__`)로 시작하면 인트로스펙션 체계의 일부라는 표시**다.
- **스스로 문서가 된다** — **문서가 상자 밖에서 주어지고 스키마에서 파생된다.** 도구 이야기와
  그 기제는 [GraphQL의 구성 요소와 실행](graphql-constructs-and-execution.md)
  §"인트로스펙션이 문서를 대신한다"에 있다.
- **다른 API의 파사드** — **마이크로서비스 아키텍처에서 게이트웨이 노릇을 하며 개별
  마이크로서비스의 REST·GraphQL·그 밖의 API를 전역 GraphQL 스키마 하나로 통합할 수 있다.**
  **각 마이크로서비스가 자기 엔드포인트를 노출하고 전역 스키마가 클라이언트로 하여금 서비스를
  가로질러 질의하게 한다** (6장, p.223).[^dynowski2025]
  - **그 위에 얹히는 아키텍처 패턴 둘이 이름으로 적힌다** — **BFF 패턴에서는 개별 프런트엔드
    클라이언트(웹·모바일 등)가 자기 필요에 맞춘 GraphQL API와 상호작용하고**, **페더레이션
    (federated) GraphQL 서비스는 여러 GraphQL 체계의 데이터를 질의 가능한 그래프 하나로
    합친다.** 그러면 **서로 다른 원천에서 데이터를 가져와 적재물 하나로 합쳐 응답 하나로
    돌려주는 질의**를 짤 수 있다 (6장, p.223).[^dynowski2025]
  - BFF 쪽 전문은 [프런트엔드를 위한 백엔드](../concepts/backend-for-frontend.md)가, 게이트웨이
    쪽은 [API 게이트웨이와 서비스 메시](../concepts/api-gateway-and-service-mesh.md)가 갖는다.
    **페더레이션은 이 KB가 이 소스로 처음 이름만 얻은 것이고 원전이 없다.**

## 버저닝을 아예 피한다는 주장

- 장점 목록의 마지막 항목이다 — **GraphQL은 연속적인 스키마 진화를 강조하고 버저닝을 아예
  피하는 것을 목표로 한다. 새 API 판을 만드는 대신, 질의가 유연하고 맞춤 가능한 데이터를
  돌려주므로 판 없는(versionless) API를 권한다. 새 능력으로 스키마를 넓히는 일은 새 필드나
  타입을 더해서 이루어지며 그것은 깨는 변경을 들이지 않는다.** 그래서 **클라이언트가 필요한
  데이터만 요청하게 되고 API가 진화하는 동안 후진 호환이 보장된다** (6장, p.223).[^dynowski2025]
- **그 문장 끝에 저자들 자신이 붙인 각주가 주장을 되돌린다** (6장 각주,
  p.223):[^dynowski2025]

  > Even though GraphQL avoids versioning, the ultimate decision on versioning is up to the
  > API designers. For example, GitHub's GraphQL API occasionally versions its fields.

- **그 각주가 같은 책 2장과 이어진다.** 2장은 **GraphQL 같은 의도 지향 API에서는 판이 필드
  이름의 개명으로 표현된다**(`updateOrderV2`)고 적는다 — 이 KB에서는
  [API 이름과 버저닝](api-naming-and-versioning.md)에 있다. **그러므로 두 서술은 겨루지
  않는다** — 6장이 말하는 것은 **스타일의 지향**이고, 2장이 말하는 것은 **그럼에도 판을 매기기로
  했을 때의 관례**이며, 각주의 깃허브 예가 바로 그 관례가 실제로 쓰이는 실물이다.
  - 같은 물음을 "번호 체계"가 아니라 "계약 변경을 어떻게 다루는가"로 고쳐 쓰는 쪽은
    [계약을 깨는 변경의 관리](../concepts/managing-breaking-api-changes.md)에 있다. 필드를
    더하는 것이 왜 깨지 않는가의 일반형은
    [후진 호환과 전진 호환](../concepts/backward-and-forward-compatibility.md)이 갖는다.

## 되무는 것 다섯

**같은 절이 단점으로 이어진다** (6장, pp.223–224).[^dynowski2025]

- **보안의 도전** — **인트로스펙션은 클라이언트가 API 스키마를 질의해 쓸 수 있는 모든 타입을
  보게 함으로써 문서를 제공한다. 개발 중에는 도움이 되지만 동시에 GraphQL API의 타입 체계를
  노출하고 공격자가 그것을 악용할 수 있다.** 공격자는 **그 정보로 공개될 의도가 없던 자원을
  찾아 접근하려 할 수 있다** (6장, p.223).[^dynowski2025]
  - 공격면의 대조가 이어진다 — 아래 §"공격면이 옮겨 간다"를 보라.
  - **과다 조회 공격과 과소 조회 공격**이라는 이름도 여기서 나온다 — **막대한 양의 데이터를
    회수하는 과다 조회 공격과 API에 요청을 여러 번 보내는 과소 조회 공격에 취약하고, 그 둘을
    섞을 수도 있다** (6장, p.223).[^dynowski2025]
- **무거운 질의** — **GraphQL이 과다 조회를 줄이기는 하지만 복잡한 질의는 여전히 성능
  페널티로 이어질 수 있다.** 예로 **재귀적이거나 깊이 중첩된 데이터를 요청하는 질의, 필드를
  많이 가져오는 질의, 별칭 기능을 쓰는 질의**가 **질의 해소를 느리게 만들 수 있다.** 처방은
  **API 설계자가 질의의 복잡도를 고려하고 그 실행에 제한을 두는 것**이다 (6장,
  p.224).[^dynowski2025]
- **캐싱의 도전** — **동적이고 유연한 성질 때문에 캐싱이 복잡하다. 모든 요청이 GraphQL API
  엔드포인트 하나로 깔때기처럼 모이기 때문에 개별 질의를 구별하기가 어렵다. GraphQL에는 HTTP
  캐싱 헤더에 대한 내장 지원이 없어서 캐싱을 다르게 다뤄야 한다.** 표준 권고는 **전역 유일
  식별자(GUID)를 쓰는 질의를 짜는 것**이다 (6장, p.224).[^dynowski2025]
  - **이 KB의 [GraphQL](../concepts/graphql.md) 페이지가 다른 소스에서 같은 판정을 이미
    갖는다** — 캐싱이 REST보다 복잡하고, 조언이 자원마다 ID를 붙이는 것이며, 그러면 CDN이나
    캐싱 리버스 프록시를 쓰는 일이 어려워진다는 것이다. **두 소스가 같은 방향이고 이쪽이 원인을
    한 줄 더 단다** — 엔드포인트가 하나라 질의를 구별할 수 없다는 것과 HTTP 캐싱 헤더의 내장
    지원이 없다는 것이다. 겨루지 않는다. 그 헤더가 무엇을 하는지의 규범은
    [안전·멱등·캐시 가능 메서드](../concepts/http-safe-idempotent-and-cacheable-methods.md)와
    [검증자 — ETag와 Last-Modified](../concepts/http-validators-etag-and-last-modified.md)에,
    캐시 일반은 [분산 시스템의 캐싱](../concepts/caching-in-distributed-systems.md)에 있다.
- **`multipart/form-data`를 기본으로 지원하지 않는다** — **GraphQL 명세는 파일 업로드에 흔히
  쓰이는 그 미디어 타입을 지원하지 않는다.** 파일 업로드 기능을 두려면 **맞춤 REST 엔드포인트를
  따로 구현하거나, 더 큰 요청을 대가로 파일을 Base64 문자열로 인코딩하거나, 아폴로 업로드
  클라이언트를 쓰는 길**이 있다. 게다가 **그 미디어 타입을 켜는 것이 CSRF 공격으로 이어지는
  보안 문제의 문을 열 수 있다** (6장, p.224).[^dynowski2025]
- **HTTP 상태 코드를 거의 쓰지 않는다** — **GraphQL은 오류를 내부에서 다뤄 HTTP 상태 코드에
  기대는 대신 응답 적재물의 일부로 돌려준다. GraphQL에서는 응답이 데이터를 담든 오류를 담든
  둘 다 담든 상관없이 모든 응답에 HTTP 200(OK)이 쓰이고**, 그래서 **200이 실제로는 오류
  응답인 상황으로 이어진다.** `4xx`나 `5xx`가 여전히 돌아올 수는 있지만 **전형적으로 GraphQL
  API 바깥의 문제를 가리킨다** (6장, p.224).[^dynowski2025]
  - **저자들이 이 항목에 각주로 시점을 단다** — **2024년의 명세 초안은 GraphQL이 언제나 200을
    쓰는 데서 벗어나려 한다는 것을 가리킨다** (6장 각주, p.224).[^dynowski2025]
  - 버전 조건: 2025년 저술 시점. 그 초안의 귀결은 이 KB가 확인하지 않았다.
  - 상태 코드가 무엇을 뜻하기로 되어 있는지의 규범은
    [상태 코드와 등급](../concepts/http-status-codes-and-classes.md)에 있다.

## 공격면이 옮겨 간다

- 저자들이 대조를 한 문장으로 적는다 — **GraphQL API와 REST API의 차이는 공격면이다. REST
  API에서는 공격자가 고정된 API 엔드포인트들을 노리는 반면, GraphQL에서는 전형적으로 엔드포인트가
  하나뿐이다.** 그리고 덧붙인다 — **GraphQL API는 효과적인 요청 속도 제한의 구현에서 어려움을
  보인다** (6장, p.223).[^dynowski2025]
- 보안 절이 그 자리를 나누는 방식도 명시된다 — **여러 API 스타일을 가로지르는 보안의 측면은
  같은 책 2장의 OWASP API 보안 상위 열이 다루고**, 이 장의 보안 절은 **GraphQL 특유의 공격과
  사용자 인증의 구현에 초점을 둔다** (6장 §Security, p.216).[^dynowski2025] 가로지르는 쪽은
  이 KB의 [API 보안 패턴](api-security-patterns.md)에 있다.
- 저자들이 밖을 가리키는 것 하나 — **흔한 공격과 그 대응책은 OWASP의 GraphQL 치트 시트를
  보라** (6장, p.216).[^dynowski2025] 이 KB는 그 문서를 반입하지 않았다.

## 인트로스펙션 남용

- **인트로스펙션 남용(introspection abuse) 공격에서 공격자는 GraphQL 인트로스펙션 기능을
  악용해 스키마를 빼낸다.** 공격은 **GraphiQL이나 GraphQL 질의를 보낼 수 있는 다른 도구로
  수행될 수 있다** (6장 §"Attacking GraphQL", p.216).[^dynowski2025]
- **방어는 인트로스펙션을 제한하거나 끄는 것**이다. 그런데 **끄면 문서를 자동 생성하는 능력도
  함께 잃는다.** 저자들의 절충안은 **개발 환경에서는 켜고 생산 환경에서는 끄는 것**이고,
  끈다면 **문서를 미리 만들어 바깥에 호스팅해야 한다** (6장, p.216).[^dynowski2025]
- **끄는 것이 완전한 방어가 아니라는 단서가 각주로 붙는다** — **인트로스펙션이 꺼져 있어도
  스키마를 여전히 빼낼 수 있는 도구(Clairvoyance 같은)가 있다** (6장 각주,
  p.216).[^dynowski2025]
- 저자들이 방법도 적어 둔다 — **자기 API를 인트로스펙트하려면 전체 인트로스펙션 질의를
  엔드포인트에 실행하면 되고 그 질의가 스키마의 모든 정보를 열거한다** (6장,
  p.217).[^dynowski2025]

## 바람직하지 않은 질의와 허용 목록

- **바람직하지 않은 질의(undesirable query)는 GraphQL 서비스가 계산이 무거운 작업을 수행하게
  하거나 민감한 정보를 노출하게 하는 질의**다. **깊이 중첩된 질의, 큰 결과 집합을 요청하는
  질의, 또는 걸러 내기와 정렬을 수행하는 질의**가 거기 든다 (6장, p.217).[^dynowski2025]
- **방어 하나가 승인된 질의의 허용 목록(allowlist)**이다 — **GraphQL 서버가 미리 정의된 안전한
  질의의 목록을 유지하고 들어오는 클라이언트 질의마다 그 목록과 대조한다. 목록에 있으면 서버가
  실행하고, 없으면 HTTP 403(Forbidden)으로 거절해 서버가 그 요청을 다루기를 거부한다는 것을
  알린다** (6장, p.217).[^dynowski2025]
  - 미디어 타입 권고가 하나 붙는다 — **GraphQL에서 `4xx`와 `5xx` 오류를 돌려줄 때는 미디어
    타입 `application/graphql-response+json`을 쓰는 것이 권장된다** (6장,
    p.217).[^dynowski2025] 위 §"되무는 것 다섯"의 마지막 항목(모든 응답에 200)과 함께 읽을
    자리다 — **오류를 HTTP 층으로 올리는 길이 아예 없는 것이 아니라 관례가 그렇지 않을 뿐이다.**
- **허용 목록의 통상 관행이 정규화 질의(normalized queries)**다 — **공백을 없애고 구조를
  알파벳 순서로 따르게 만든 질의**이고, **정규화는 백엔드가 맡으므로 클라이언트는 구체적인
  정규화 규칙을 걱정하지 않고 어떤 형식으로든 질의를 보낼 수 있다** (6장,
  p.217).[^dynowski2025]
- **적용 환경이 갈린다** — **전형적으로 허용 목록은 개발 환경에서 꺼 두어 개발자가 새 질의를
  자유롭게 시험하고 반복하게 하고**, **생산 환경에서는 신뢰된 질의만 실행되게 해 성능 문제와
  데이터 유출의 위험을 줄인다** (6장, p.217).[^dynowski2025]

## 재귀 질의와 깊이 제한

- 기제가 먼저 적힌다 — **GraphQL에서 관계는 스키마에 정의되고 클라이언트가 문서에서 필드 중첩으로
  서술한다. 모델에 순환 관계가 있으면** 같은 관계를 번갈아 되풀이해 중첩한 질의를 짤 수 있다 —
  저자들의 예가 학생과 강좌를 몇 겹이고 번갈아 중첩한 질의다 (6장, p.217).[^dynowski2025]
- **판정이 두 문장으로 나온다** (6장, p.217):[^dynowski2025]
  - **어떻게 보아도 그것은 적법한 GraphQL 질의다.**
  - **문제는 서비스가 돌려주는 객체의 수가 중첩의 수준에 따라 곱셈으로 늘어나 자원을 많이
    잡아먹을 수 있다는 것이다.**
- **방어는 질의의 중첩 깊이를 제한하는 것**이다 (6장, p.218).[^dynowski2025]
- **이 KB의 [GraphQL](../concepts/graphql.md) 페이지는 다른 소스를 근거로 "GraphQL은 재귀
  질의를 허용하지 않는다"고 적는다.** 그 문장과 이 절이 같은 낱말의 다른 뜻을 쓴다는 것,
  그래서 모순 쌍이 아니라는 것은
  [GraphQL의 구성 요소와 실행](graphql-constructs-and-execution.md)
  §"이 KB의 다른 GraphQL 서술과 나란히"에 적어 두었다.

## 배치 질의와 별칭

- **배치 질의 공격(batch query attack)은 문서 하나에 연산 여럿을 담을 수 있는 GraphQL의 능력을
  악용한다.** **공격자가 질의를 많이 합쳐 GraphQL 문서 하나로 보내면 그런 요청이 서비스를
  압도해 자원 고갈이나 서비스 중단으로 이어질 수 있다** (6장, p.218).[^dynowski2025]
  - 그 능력 자체는 정당한 기능이고, 저자들이 앞서 뮤테이션 셋을 한 문서로 보내는 예로 보인
  바로 그것이다 — [GraphQL의 구성 요소와 실행](graphql-constructs-and-execution.md)
  §"한 문서에 연산 여럿"에 있다.
- **방어가 넷으로 적힌다** (6장, p.218):[^dynowski2025]
  - **질의나 뮤테이션 하나에 허용되는 배치 연산의 수를 제한한다** — 저자들의 예가 요청당 연산
    **최대 셋**이라는 상한이다.
  - **실행이 너무 오래 걸리는 질의를 끝내도록 시간 제한을 둔다.**
  - **자원을 많이 쓰는 질의를 보내는 클라이언트를 차단한다.**
- **별칭이 같은 공격의 다른 통로다** — **GraphQL 별칭(alias)에서는 필드에 이름을 줄 수 있고,
  그렇게 하면 요청 하나로 질의를 여럿 돌릴 수 있다** (6장, p.218).[^dynowski2025] 저자들의 예가
  같은 도시 필드에 서로 다른 필터를 걸고 두 별칭으로 부르는 질의다.
  - 같은 별칭이 위 §"얻는 것 다섯"에서는 **덜 수다스럽게 만드는 능력**으로 적힌다. **하나의
    기능이 장점 목록과 공격 목록에 함께 오른 자리**이고, 이 장의 절충 절도 별칭을 무거운 질의의
    원인으로 다시 든다.
- 속도 제한 일반은 [API 요청 수명 패턴](api-request-lifecycle-patterns.md)에 있고, 저자들이
  위에서 적은 대로 **이 스타일에서는 그 구현이 어렵다**는 단서가 붙는다.

## 인증은 스타일 밖에서 온다

**이 절은 얇다.** 저자들의 인증 구현은 장고와 Strawberry에 매인 것이고, 이 KB가 담는 것은
**어디에서 결정이 내려지는가**뿐이다.

- **뮤테이션은 인증된 사용자만 수행할 수 있게 되어 있고**, 그 흐름은 **JWT 통합 라이브러리가
  주는 뮤테이션들을 스키마에 끌어다 붙이는 방식**으로 구현된다 — **토큰을 얻고·갱신하고·
  폐기하고·검증하는 네 뮤테이션**이 그것이다 (6장 §Authentication, p.219).[^dynowski2025]
- **토큰 검증은 권한 클래스가 맡는다** — 권한 클래스가 **요청이 인증됐는지를 불리언으로
  돌려주는 메서드를 덮어쓰고**, 그 안에서 **HTTP `Authorization` 헤더에서 JWT를 꺼내 서명을
  검증하고 적재물 객체로 바꾸며, 만료 시각을 꺼내 만료 여부를 검사하고, 통과하면 인증된
  사용자를 요청 맥락에 끼워 넣는다** (6장, pp.220–221).[^dynowski2025]
- **그래서 인증은 GraphQL 명세가 정하는 것이 아니라 구현이 얹는 것**이다. JWT 자체의 규정과
  성질은 [REST API 구현 결정](rest-api-implementation-decisions.md)이 같은 책 5장에서 이미
  갖고 있다 — **같은 예제 서비스가 두 스타일에서 같은 토큰 기제를 쓴다**는 것이 저자들이 명시한
  사실이다 (6장, p.207).[^dynowski2025]
  - 보호된 자원과 상호작용할 때 **`Authorization` 헤더를 붙여야 한다**는 것도 명시된다 —
    값의 모양은 `Bearer <토큰>`이다 (6장, p.207).[^dynowski2025] 그 헤더의 규범은
    [인증 필드](../concepts/http-authentication-fields.md)에 있다.
- 구현에 딸린 조각 하나 — 저자들의 예제는 **CSRF 보호 기제 때문에 토큰과 쿠키를 함께 실어야
  하고**, 개발용 화면에서는 그 보호를 꺼 두어 다루기 쉽게 만든다 (6장,
  pp.207·209).[^dynowski2025]

## 어디에 쓸 것인가

- **저자들이 쓸 자리를 넷으로 적는다** (6장 §"When to Use GraphQL", p.225):[^dynowski2025]
  - **네트워크 발자국과 에너지 사용이 낮아야 하는 애플리케이션** — 예가 **스마트폰·스마트워치·
    IoT 기기**다. 위 §"어디서 왔는가"의 유래가 그대로 쓸 자리가 된 것이다.
  - **여러 외부 원천의 데이터를 합치는 자리** — **데이터베이스·로깅 서비스·레거시 체계·제3자
    데이터 제공자**를 든다.
  - **중첩된 데이터 구조를 가진 애플리케이션** — 그러지 않으면 **API 호출을 여러 번 해야 할**
    자리이고, **클라이언트가 원하는 데이터를 요청 하나로 회수하게 해 서버 요청 수를 줄일 수
    있다.**
  - **빠른 시제품이나 개념 증명이 필요할 때** — **REST API를 구현하는 데 견줘 개발 시간을 줄일
    수 있다.**
- 이 KB의 [GraphQL](../concepts/graphql.md) 페이지는 다른 소스에서 **체계의 경계에서 외부
  클라이언트에 기능을 노출하는 것**을 이 언어의 단맛 나는 지점으로 적고, **마이크로서비스 사이
  통신을 대체하지 않는다**고 명시한다. **이 절의 넷은 그 배치와 겨루지 않는다** — 넷 모두
  클라이언트가 경계 바깥에 있는 경우이거나(모바일·IoT) 경계에서 여러 뒤쪽을 합치는 경우다.
