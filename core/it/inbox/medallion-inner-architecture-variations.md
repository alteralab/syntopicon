가른 까닭은 물음이 다르기 때문이다 — 앞은 **경계를 몇 개로 긋는가**를 묻고, 여기는 **한 경계 안의
계층을 어떻게 다시 짜는가**를 묻는다.

> [Bronze를 반입 경로로 쪼갠다](#bronze를-반입-경로로-쪼갠다)의 Lakehouse 엔티티·바로가기·미러링)
> 그 시점 제품의 예시로 표시해 두었다. 이 소스에 공표된 만료 날짜가 없어 `stale_after`는 걸지 않는다.

## 이 축이 앞 축과 갈리는 자리

- 저자가 이 절을 여는 문장에 축의 순서가 적혀 있다 — 데이터 제품 관리 전용 계층을 두는 것으로
  시작해, **제공자 정렬·소비자 정렬 모델과 Bronze 복합체 모델과 특정 시나리오·소비자를 위한 추가
  Gold 계층**을 포함한 메달리온 변형을 살피고, **전사 데이터 모델링과 MDM으로 메달리온을 관리하는
  것**까지 간다 (11장 §"Medallion Inner Architecture Variations" 도입).[^strengholt2025]
- 그리고 이 절 전체의 판정이 그 도입에 먼저 나온다 — **확장은 아키텍처나 계층을 더 보태는 일이
  아니라 올바른 뉘앙스를 찾는 일이다** (같은 도입).[^strengholt2025]

## 데이터 제품 전용 계층

- 탈중앙 모델은 데이터 모델 자체의 성격을 바꾼다 — **탈중앙 모델은 데이터 모델을 인터페이스 모델로
  바꾸고, 그것이 데이터 제품이라 불리는 것**이다. 그래서 **데이터 모델링·데이터 품질·데이터
  거버넌스에 각별히 주의**해야 한다 (11장 §"Medallion Inner Architecture Variations" ▸ "Separate
  Data Product Layers").[^strengholt2025]
- 확장 방법의 첫째가 계층을 하나 더 두는 것이다 — 여러 도메인 팀이 각자 운영 애플리케이션과 분석
  데이터를 소유하고 반입·처리·데이터 제품 큐레이션을 맡는 설정에서 **데이터 제품 설계와 배포에
  전용인 계층을 추가로 도입**할 수 있다. 이 여분의 계층은 **팀 내부 소비와 다른 팀에 공유하는 것을
  구별**하게 하고, 그 구별이 결정적인 이유는 **재사용 가능한 일반적 데이터 제품이 특정 유스케이스
  요건을 맞추지 못하는 일이 잦기** 때문이다 (같은 소절).[^strengholt2025]
- 그림 11-3의 배치 (같은 소절, 그림 11-3):[^strengholt2025]

  > 위쪽 *Microsoft Fabric Workspace* 안에 *Synapse data engineering* · *Silver* · *Gold* ·
  > *Separate layer for data products*. 아래쪽 *Workspace* 둘이 각각 *Bronze* · *Silver* ·
  > (왼쪽만) *Gold*와 *Separate layer for data products*를 갖고, 오른쪽 워크스페이스에는
  > *No gold, because no internal consumers*라는 주석이 붙는다. 아래 워크스페이스의 데이터 제품
  > 계층에서 위 워크스페이스로 올라가는 선에 *Data product layer acts as Bronze*,
  > 왼쪽 워크스페이스의 *Gold* 옆에 *For internal consumers*

- 실무로 옮기면 **Silver나 Gold 가운데 하나를 둘로 가르는 것**이다 — 한쪽은 **보통 정성껏 카탈로그에
  등재되고 다른 팀에 승격되며 늘 분명한 소유권이 붙는 안정된 "데이터 제품" 데이터**를, 다른 쪽은
  **팀의 애플리케이션이 쓰는 동적인 "도메인·유스케이스 특정" 데이터**를 맡는다. 이 갈림은 **더 성숙한
  조직에서 흔히 보이며** 팀이 **메달리온의 핵심 원칙에 정렬한 채로 자기 데이터 제품을 독립적으로
  관리**하게 한다 (같은 소절).[^strengholt2025]
- 대규모 배포의 전제가 표준이라는 점을 곁줄이 못 박는다 — **개방 테이블 형식의 촉진을 포함한 메타데이터
  및 상호운용성 표준은 대규모로 데이터를 배포하는 데 필수**이고, 그것을 효과적으로 달성하려면 **견고한
  데이터 거버넌스 관행이 필요**하며 그 관행이 **조직의 모든 도메인이 확립된 데이터 표준을 따르도록
  보장**한다 (같은 소절 곁줄(tip)).[^strengholt2025]
- 절의 맺음이 앞 축과 이 축을 한 문장에 묶는다 — **메달리온 아키텍처를 효과적으로 확장하는 일은
  데이터 메시 원칙을 채택하고 데이터 소유권과 거버넌스를 탈중앙화하는 데 달려 있다** (같은
  소절).[^strengholt2025]

## 맞춤 메달리온과 해법 패턴 일곱

- 전제 — **모든 도메인이 같은 계층 구성을 필요로 하지는 않는다.** 특히 여러 메달리온을 쓰는 데이터
  메시 설정에서는 **도메인마다 요건이 크게 다를 수 있고**, 복잡한 통합·배포 요구부터 단순한 데이터
  소비까지 범위가 넓다 (11장 §"Medallion Inner Architecture Variations" ▸ "Tailored Medallions
  Architectures").[^strengholt2025]
- 자주 만나는 시나리오 하나는 **다른 팀이 관리하는 데이터에 접근해 활용해야 하는 팀·업무 단위를 위한
  격리 환경**을 만드는 것이다. 예컨대 한 팀이 **계층 하나(레이크하우스 하나)로만 이루어진 워크스페이스에서
  다른 팀이 관리하는 데이터로의 읽기 전용 바로가기**를 갖고 일할 수 있다 (같은
  소절).[^strengholt2025]
- 둘을 이어 붙이는 이음이 이 절의 핵심 배치다 — **원천 시스템에 맞춘 것과 소비에 맞춘 것, 두 메달리온
  아키텍처를 다루는 시나리오**에서는 **계층 사이의 상호작용이 결정적**이 된다. **원천 정렬 아키텍처의
  Gold 또는 데이터 제품 계층이 사실상 소비 정렬 아키텍처의 Bronze 계층 역할을 한다**고 볼 수 있고,
  이 접근이 **소비 쪽 Bronze에 데이터 제품 계층을 복제할 필요를 없애 더 날씬한 아키텍처**를 만든다
  (같은 소절).[^strengholt2025]
- 그림 11-4가 그 변형들을 나란히 놓는다 (같은 소절, 그림 11-4):[^strengholt2025]

  > *Simple data provider*(*Ingest* → *Lakehouse Bronze* → *Lakehouse Silver* → *Lakehouse Gold*
  > → *Shortcuts*) · *Single-use complex data provider*(같은 사슬에 *Warehouse Gold*가 갈라져
  > 붙는다) · *Basic consumer* 둘(하나는 *Lakehouse Gold* → *Report*, 다른 하나는
  > *Lakehouse Silver* → *Lakehouse Gold* → *Report*) · *Distributor consumer*(*Bronze* ·
  > *Silver* · *Gold* · *Shortcuts*에 *Warehouse Gold*가 붙는다). 제공자 쪽 *Shortcuts*에서
  > 나온 선이 소비자 쪽 입구로 들어간다

- 해법 패턴 일곱과 각각이 권하는 계층 수 (같은 소절):[^strengholt2025]
  - **단순 데이터 제공자**(simple data provider) — 원천이 몇 안 되고 자기 데이터를 특정 유스케이스로
    소비하지 않는다면 **계층 둘이나 셋**(예: Bronze와 데이터 제품 계층)이면 족하다.
  - **단일 용도 복합 데이터 제공자**(single-use complex data provider) — 원천은 많으나 그 데이터를
    내부 목적으로만 쓴다면 **계층 셋이나 넷**(예: Bronze·Silver·Gold)으로 충분할 수 있다.
  - **다용도 복합 데이터 제공자**(multi-use complex data provider) — 원천이 많고 그 데이터를 여러
    내부 프로젝트에 쓴다면 **최소 넷이나 다섯**을 고려한다.
  - **기본 소비자**(basic consumer) — 복잡한 처리 없이 소비가 주 역할이면 **계층 하나**로, 어쩌면
    **하나도 없이**(예: 다른 도메인의 계층 위에서 바로 보고) 효과적으로 일할 수 있다.
  - **통합 소비자**(integrated consumer) — 자기 프로젝트를 위해 여러 원천을 통합해야 하는 소비자라면
    **계층 둘이나 셋**이 적절하다.
  - **배포자 소비자**(distributor consumer) — 여러 원천을 통합해 자기가 쓰면서 다른 도메인에 더
    배포까지 한다면 **여러 계층**이 필요할 수 있다(예: Bronze·Silver·Gold와 데이터 제품 계층).
  - **소비자 제공자**(consumer provider) — 자기가 쓰려는 것이 아니라 **남에게 제공하려는 목적으로만
    데이터를 소비**한다면 데이터를 효과적으로 관리하기 위해 **여러 계층의 더 복잡한 구성**이 필요할 수
    있다.
- 목록의 판정 — **확장성은 경직된 설계 패턴 하나를 고수할 것을 요구하지 않는다.** 대신 **조직 고유의
  필요에 맞춰 메달리온 아키텍처를 재단**할 수 있고, **각 패턴은 서로 다른 복잡성과 통합 요구에
  대응**하도록 설계되어 있다 (같은 소절).[^strengholt2025]
- 일곱 가운데 소비자 제공자 패턴이 큰 기업에서 통합 노력을 줄이는 데 특히 자주 쓰인다 — **여러 소비
  도메인이 통합 책임을 한 제공 도메인에 위임**하고, 그 도메인이 **조직 전반의 조화에 책임**을 지며
  **공유 고객·제품 관리 같은 전사 원천을 통합·조화해 소비용 평탄화된 골든 데이터 제품**을 만든다. 이
  접근은 **집계(aggregates)의 사용이라고도 불리며 소비 쪽에 필요한 반복적 통합 과업을 크게 줄인다**
  (같은 소절).[^strengholt2025]
- 위임 모델의 다른 구현도 함께 적힌다 — **원천 시스템에 정렬한 각 도메인이 자기 맥락 안에서 데이터
  제품을 만들어 개별 카탈로그로 승격하고, 그 지역 데이터 제품들을 통합된 뷰로 어떻게 합칠지 적은 중앙
  카탈로그를 따로 둔다.** 이런 틀이 **제공 도메인이 자기 지역 데이터 제품을 중앙에서 관리·조화되는
  데이터 제품에 매핑하는 위임 모델**을 뒷받침한다 (같은 소절).[^strengholt2025]
- 설계 패턴을 그때그때 짜지 말라는 것이 이 절의 마지막 권고다 — **모든 설계에 대해 이 설계 패턴들을
  표준화하고 형식화하는 것이 결정적**이고, 저자는 **각 해법 패턴의 설계와 계층 구성과 데이터 제품
  관리에 대한 지침을 제공할 것을 권한다** (같은 소절).[^strengholt2025] 그 지침에 무엇이 들어가는가는
  [데이터 제품 지침](../concepts/data-product-guidelines.md)이 받는다.

## Bronze를 반입 경로로 쪼갠다

- 계층을 더하거나 빼는 축과 별개로 **계층 안쪽에 변형을 도입해 확장하거나 최적화**하는 축이 있고,
  저자는 그것을 Bronze부터 본다 (11장 §"Medallion Inner Architecture Variations" ▸ "Adaptability of
  the Bronze Layer").[^strengholt2025]
- **Bronze 계층을 나누어 서로 다른 데이터 반입 흐름을 효과적으로 관리**할 수 있다. 예로 **Bronze가
  여러 데이터 풀의 복합체(conglomerate)처럼 작동하는 변형**을 든다 — 2025년 저술 시점의 Microsoft
  Fabric 설정에서 **Bronze 안의 여러 Lakehouse 엔티티가 여러 데이터 풀을 관리**한다 (같은
  소절).[^strengholt2025]
- 그림 11-5의 배치 (같은 소절, 그림 11-5):[^strengholt2025]

  > 왼쪽 원천이 셋으로 묶여 있다 — *Amazon S3* · *Dataverse* · *Other storage locations* /
  > *Operational systems* / *Cosmos DB* · *SQL* · *Snowflake* · *Database or warehouses*.
  > 첫 묶음에서 *Shortcuts*로 표시된 선이 *Bronze layer*와 *Operational reporting and
  > analytics*로 곧장 가고, 둘째 묶음은 *Landing area* → *Ingest data with Data Factory*를 거쳐
  > *Bronze layer*로, 셋째 묶음은 *Real-time data replication*으로 *Bronze layer*로 간다.
  > *Bronze layer* 안에 레이크하우스 상자 셋이 세로로 쌓여 있다. 오른쪽은 *Silver layer* →
  > *Gold layer* → *Shortcuts: Serve data to other domains* → *Reporting* · *Data science*,
  > 아래에 *Orchestration using Data Factory* 띠

- 병렬로 도는 반입 패턴 셋 (같은 소절):[^strengholt2025]
  - **바로가기**(shortcuts) — 광범위한 처리가 필요 없는 데이터에는 Bronze 안에 바로가기를 만들 수
    있다. **이미 호환 형식(예: Delta Lake나 Iceberg)이고 기술적 데이터 변환이 필요 없는 데이터**에
    쓸모 있다.
  - **물리 사본**(physical copies) — 여러 원천에서 Bronze로 반입해 데이터의 물리 사본을 만든다.
    **Silver나 Gold에서 쓰이기 전에 광범위한 처리나 변환이 필요한 데이터**에 적합하다.
  - **복제**(replication) — 미러링이나 CDC 같은 실시간 동기화로, **여러 도메인에 걸쳐 복제되어야
    하는 데이터**의 선택지다. 이 구성이 **데이터가 늘 최신이고 여러 애플리케이션에서 쓸 수 있게**
    보장한다.
- 바로가기를 고를 때의 한계가 각주에만 있다 — **바로가기 같은 가상화된 데이터는 특히 큰 데이터셋에서
  병목에 부딪힐 수 있다. 그런 경우에는 데이터의 물리 사본을 만드는 것이 더 나은 선택이다** (11장 각주
  2).[^strengholt2025] 계층 사이를 바로가기로만 잇는 설계가 어디서 물리 사본으로 되돌아가는지의
  한계선이 이 각주다.
- 쪼개는 축은 반입 방식만이 아니다 — **애플리케이션 팀에 맞춰 쪼개는 것**도 고려할 수 있다. 여러 팀이
  더 큰 도메인의 Bronze로 서로 다른 원천을 반입하고 싶은데 **팀끼리 서로의 데이터를 보면 안 되는**
  경우, Bronze 안에 **팀마다 레이크하우스 엔티티를 더 두어 반입을 따로 관리**한다. 이 구성이 **데이터를
  분리·보호해 민감 정보에 대한 무단 접근을 막는다** (같은 소절).[^strengholt2025]
- 절의 판정 — **계층 하나 안에서도 변형을 도입해 서로 다른 반입 흐름을 관리할 수 있고**, 그것이
  **관심사를 효과적으로 분리**한다 (같은 소절).[^strengholt2025]

## Silver의 변형은 안쪽에 갇힌다

- Silver의 규정을 저자가 여기서 다시 쓴다 — Silver는 **Bronze의 반입 프로세스와 Gold의 소비 패턴을
  분리(decouple)하려고 설계된 필수 중간자**다. 이 분리가 데이터 관리·변환 워크플로를 매끄럽게 하고,
  **Silver의 변형이 원천 시스템에서 외부 소비자로 가는 데이터 제공에 직접 영향을 주지 않도록** 보장한다.
  그래서 이 계층에서는 **변환·처리 워크플로를 최적화하는 변형을 도입**할 수 있다 (11장 §"Medallion
  Inner Architecture Variations" ▸ "Silver Layer Variations").[^strengholt2025]
- 다만 자유에 조건이 붙는다 — **효율을 최대화하고 데이터 소유권·거버넌스의 명료함을 유지하려면 Silver의
  안쪽 구조를 Bronze와 어느 정도 정렬시키는 것을 고려하는 편이 좋다.** 그 정렬이 **두 계층에 걸친 데이터
  처리·변환 규칙의 일관성을 유지**해, 시간이 지나며 파이프라인을 관리하고 진화시키는 일을 단순하게 만든다
  (같은 소절).[^strengholt2025]

## Gold의 변형과 거버넌스 하위 계층

- Gold는 **업무 가치를 전달하는 것이 전부**이고 변형을 도입해 특정 필요에 맞출 수 있다. 어떤 조직은
  **여러 플랫폼이나 팀에 데이터를 배포하려 계층을 더 두고**, 그것은 **특정 시나리오용 데이터를 골라
  미리 걸러 새로 만든 계층에 저장**하는 일이 된다. 저자는 8장 AP Pension 아키텍처에서 이미 그 접근을
  보였다고 되짚는다 (11장 §"Medallion Inner Architecture Variations" ▸ "Gold Layer
  Variations").[^strengholt2025] 그 실물은
  [AP Pension 사례 연구](../concepts/ap-pension-case-study.md)에 있다.
- 쪼개는 둘째 기준이 거버넌스다 — **데이터 종류마다 다른 거버넌스 정책이 필요하다면 Gold를 여러
  하위 계층으로 쪼개고 각각에 자기 정책 집합을 두는 것을 고려**한다. 이것은 **한 엔지니어링·업무 팀이
  더 큰 메달리온 아키텍처를 운영하는 큰 도메인**에서 특히 쓸모 있다. **Gold의 부분마다 분명한 소유권을
  보장하는 방법이 하위 계층으로 나누어 각각에 데이터의 품질·보안·거버넌스를 책임지는 소유자를 지정하는
  것**이다. 이 모델은 **공유 데이터 모델을 유지하면서 사업의 여러 부분을 보고해야 하는 큰 금융 기관에서
  흔히 쓰인다** (같은 소절).[^strengholt2025]
- 팀이 커질 때의 조건도 함께 적힌다 — **더 큰 팀에서는 모두가 정렬해 같은 목표를 향해 효과적으로
  일하도록 분명한 프로세스·소통 경로·교육을 세우는 것이 결정적**이다 (같은 소절).[^strengholt2025]
- 이 계층이 전사 표준과 만나는 자리가 다음 절로 이어진다 — **Gold 계층은 전사 표준을 따른다는 점에서
  특히 두드러진다.** 전사 데이터 모델링이 복잡하고 시간이 많이 드는데도 **많은 조직이 데이터 재사용성과
  표준화를 보장하려 어떤 형태로든 전사 데이터 조화를 받아들인다.** 통합하기 쉽게 데이터를 조직·관리하는
  이 과정을 **데이터 큐레이션(data curation)**이라고도 부른다 (같은 소절).[^strengholt2025]

## 전사 데이터 모델과 도메인 집계

- 메달리온 메시에서 전사 데이터 모델은 **도메인을 하나 더 세우는 것**으로 구현된다 — 기업은 **이 통합
  또는 큐레이션 목적으로 추가 도메인을 세우는 일이 잦고**, 그 도메인들이 **전사 표준에 대한 적합을
  보장하려 복잡하고 큰 데이터 모델을 관리**하며, 거기서 **새로 만들어진 데이터 제품이 다른 도메인으로
  배포**된다. 이 접근은 **집계를 짓는 것**(building aggregates)이라 불리고 **앞의 소비자 제공자 시나리오와
  비슷**하며, 조직이 데이터 관리를 효과적으로 확장하게 돕는다. 덧붙여 **소비자는 자기 필요에 따라 Silver와
  Gold와 집계 계층 사이를 오갈 유연함**을 얻는다 (11장 §"Medallion Inner Architecture Variations" ▸
  "Enterprise Data Models").[^strengholt2025]
- 그림 11-6의 배치 (같은 소절, 그림 11-6):[^strengholt2025]

  > 위에 생산 도메인 둘이 각각 *Ingest* → *Lakehouse Bronze* → *Lakehouse Silver* →
  > *Lakehouse Gold* → *Shortcuts*(와 갈라져 나온 *Warehouse Gold*)를 갖는다. 두 도메인의
  > *Shortcuts*에서 나온 선이 가운데 *Domain aggregate*로 모이는데, 그 상자 안에는
  > *Lakehouse Silver* · *Lakehouse Gold* · *Shortcuts*만 있고 **Bronze가 없다.** 집계의
  > *Shortcuts*와 생산 도메인의 *Shortcuts*가 아래 *Consumer* 둘(*Lakehouse Gold* → *Report*)로
  > 들어간다

- 집계는 **완성품이 아니다** — **보통 중앙 팀이 이 도메인 집계를 관리하거나 감독하며 데이터 품질·
  거버넌스·규제 준수 유지에 초점**을 둔다. **이 집계는 특정 유스케이스용의 바로 쓸 수 있는 데이터 제품이
  아니고, 주 역할은 여러 도메인에 걸쳐 데이터를 선통합(pre-integrate)해 배포하는 것**이다. 그것이
  **모든 팀이 같은 고품질 데이터에 접근**하게 하고, 결과는 **다른 도메인으로 매끄럽게 흘러 들어가는
  잘 정리된 데이터 제품**이다. **소비 도메인이 아키텍처 왼쪽의 생산 도메인 자신일 수도 있다**는 점도
  덧붙는다. 이 전략이 **업무 단위마다 통합 노력을 중복하는 것을 막아 회사 전반의 프로세스를 간소화**한다
  (같은 소절).[^strengholt2025]
- 무엇을 선통합할지 고르는 절차 넷 — 저자는 **연합 아키텍처에서 방대한 데이터 가운데 어느 것이 겹치고
  선통합되어야 하는지 가리는 일이 벅차게 느껴질 수 있다**고 인정한 뒤 접근을 적는다 (같은
  소절):[^strengholt2025]
  - **가장 결정적인 데이터 도메인을 식별**하고 그것들과 바탕 원천 시스템 사이의 관계를 이해한다.
  - **이해관계자와 일찍 만나 어떤 데이터셋을 자주 함께 쓰는지** 알아낸다. 이것이 **결합했을 때 가장 큰
    값어치를 주는 데이터**(예: 여러 원천의 고객 데이터, 부서에 걸친 재무 데이터)를 기준으로 통합의
    우선순위를 매기게 한다.
  - **데이터 카탈로그의 메타데이터로 데이터 사용 패턴을 지도화·추적**한다. 이것이 **공통 교차점과 수요가
    높은 데이터셋**을 드러낸다.
  - **남아 있다면 옛 레거시 데이터 웨어하우스를 탐색**한다. 그 시스템들은 **이미 많은 데이터를 결합하고
    선통합해 두었으므로 데이터 큐레이션의 좋은 출발점**이 된다.
- 판정 — **값어치가 높고 자주 쓰이는 데이터에 집중하고 데이터 관계를 이해할 도구를 활용하면, 엔지니어링
  팀을 압도하지 않으면서 무엇을 선통합할지 효율적으로 결정**할 수 있다 (같은 소절).[^strengholt2025]

**낱말 주의 — 여기의 "집계"는 도메인 주도 설계의 애그리게이트가 아니다.** 이 절의 aggregate는 여러
도메인의 데이터를 미리 통합해 배포하는 **데이터 도메인**을 가리키고,
[애그리게이트와 일관성 경계](../concepts/aggregates-and-consistency-boundaries.md)의 애그리게이트는
**한 트랜잭션의 불변식을 지키는 객체 군집**을 가리킨다. 2026년 KB 작성 시점에 같은 영어 낱말이 두
자리에서 다른 것을 센다는 점만 표시해 둔다.

## 마스터 데이터 관리의 자리

- MDM과 큐레이션은 겹치되 목적이 다르다 — **MDM과 큐레이티드 데이터 생성은 둘 다 큰 조직 안의 데이터
  사용을 간소화하는 것을 목표로 하고 ETL·데이터 정제·데이터 과학·메타데이터 관리 같은 공통 기법**을
  쓰며 여기에는 계보 포착과 데이터 모델 서술이 포함된다. **그러나 MDM에는 고유한 초점이 있다 — 필수
  업무 데이터, 곧 마스터 데이터에 대한 단일하고 정확하며 권위 있는 진실의 원천을 세우려 한다**
  (11장 §"Medallion Inner Architecture Variations" ▸ "Master Data
  Management").[^strengholt2025]
- 규정 — **본질적으로 MDM은 데이터 품질 실무이며, 모두가 여러 시스템과 업무 단위에 걸쳐 일관되고
  최신인 마스터 데이터에 기댈 수 있게 보장한다.** 그리고 **금융이나 의료처럼 규제가 심한 산업에서
  MDM은 규제 준수 유지와 데이터 정확성 보장에 결정적이라 선택이 아니라 필수**다 (같은
  소절).[^strengholt2025]
- 여러 메달리온 맥락에서의 배치가 이 절의 기여다 — **MDM은 특화된 접근을 취한다. 조화된(마스터된)
  엔티티의 관리를 담당할 특정 도메인들을 지정하며 그 도메인은 중앙집중일 수도 탈중앙일 수도 있다.
  다른 도메인들은 그 표준화된 엔티티를 활용하는데, 그것은 보통 Silver와 Gold 계층에서 발견된다**
  (같은 소절).[^strengholt2025]
- 그림 11-7이 원천 시스템과 MDM 시스템 사이의 흐름을 다섯 걸음으로 그린다. 그림 안쪽 라벨 (같은 소절,
  그림 11-7):[^strengholt2025]

  > 왼쪽 *Operational system #1*(*Power apps* · *Dynamic 365* · *Dataverse*)과
  > *Operational system #2*(*Batch*), 위쪽에 *API gateway*와 *Event broker*. 번호 ①이 붙은
  > *Workspace* 둘이 각각 *Bronze* · *Silver* · *Gold*를 갖고, ②가 붙은 *Transform*에
  > *Mapping domain event to MDM input format*, ③이 붙은 *MDM system*, 그 위 *Transform*에
  > *Mapping MDM event to domain event format*이 붙어 ④로 *API gateway*로 돌아간다. ⑤는
  > *Gold*에서 *Downstream analytical consumers*로 나간다

- 다섯 걸음의 본문 서술 (같은 소절):[^strengholt2025]
  - 도메인 데이터가 **Dynamics 같은 여러 원천 시스템에서 추출되어 서로 다른 워크스페이스로 전달**되고,
    그 데이터가 **Bronze·Silver·Gold 단계를 지나며 품질과 무결성을 확보**한다. 큰 아키텍처에서는
    **보통 도메인이 이 과정을 스스로 처리**한다.
  - Dynamics와 Power Apps는 공통 데이터 서비스인 **Dataverse의 데이터를 쓰고 도메인 이벤트를 생성**할
    수 있으며, 그 이벤트는 **MDM 입력 형식에 맞게 변환된 뒤 MDM 시스템으로 보내진다.** 이 패턴이
    **원천 시스템과 MDM 시스템 사이의 실시간 데이터 흐름**을 구현한다.
  - **MDM 시스템이 여러 애플리케이션에서 온 데이터를 저장·처리하고 복잡한 병합·매칭 알고리즘으로 단일
    통합 뷰로 통합**한다. **보통 중앙 팀이 이 시스템을 관리**한다.
  - **MDM 시스템도 필요에 따라 이벤트를 생성**할 수 있고, 그 이벤트는 **도메인 이벤트 형식에 맞게
    변환되어 Dynamics로 되돌아가거나 다른 곳에 쓰인다.**
  - **MDM 시스템이 처리한 고품질 데이터가 여러 도메인에 공유되어 모두가 일관되고 신뢰할 수 있는 데이터에
    접근**하게 된다.
- 되먹임의 이름 — **MDM 도메인이 생성한 마스터 데이터는 여러 방식으로 다른 도메인에 되돌아가고, 효과적인
  방법 하나는 그것을 (마스터된) 데이터 제품으로 배포하는 것**이다. 나아가 **이 정제되고 정확한 데이터를
  원래 원천 시스템으로 되돌려 공유하면 그 시스템의 성능이 크게 개선**되며, 이 재배포는 **공존
  패턴**(coexistence pattern)이라 불리고 **흔히 이벤트나 API 호출로 일어난다.** 이 접근이 **옛 시스템과
  새 시스템의 매끄러운 협업을 보장**한다 (같은 소절).[^strengholt2025]

이 KB의 MDM 원전은 [마스터 데이터 관리](../concepts/master-data-management.md)이고, 위 배치는 그
페이지의 성숙도 단계와 운영적·분석적 구분 위에 **여러 메달리온이라는 조건을 하나 더 얹은 것**이다.

## 참조 데이터 관리

- 마스터 데이터와 갈리는 지점부터 시작한다 — **마스터 데이터와 달리 참조 데이터는 특정 도메인 안에서
  관리할 수 있는데, 여러 도메인에 걸쳐 비교될 필요가 없기 때문**이다 (11장 §"Medallion Inner
  Architecture Variations" ▸ "Reference Data Management").[^strengholt2025]
- 규정 — **참조 데이터는 다른 종류의 데이터를 정의·분류·조직·묶음·범주화하는 데 필수**이고, **제품 유형과
  지리적 위치의 관계 같은 값 계층(value hierarchy)을 담는 일이 잦다.** 그리고 **데이터 보안과 접근
  관리에서도 필수 역할**을 한다 — **사용자 인가 모델이 접근 권한을 정하는 데 참조 데이터에 기대는 일이
  잦기** 때문이다 (같은 소절).[^strengholt2025]
- 도메인 안에서 관리해도 중앙과의 정렬은 필요하다 — **여러 도메인에 걸쳐 참조 데이터가 일관되게
  유지되려면 팀은 각 메달리온 아키텍처 안의 데이터 배포 프로세스를 중앙 관리 참조 데이터와 동기화**해야
  한다. 통화 코드·국가 코드·제품 코드 같은 흔한 예는 **MDM 시스템에서 중앙 발행**될 수 있다. 그리고
  **도메인이 자기 데이터 제품을 남에게 배포할 때 분류나 참조에 MDM 참조 데이터의 식별자를 쓰는 것이
  필수**인데, 그 정렬이 **다른 도메인이 전사 참조 데이터를 빠르게 알아보고 통합**하게 하기 때문이다.
  **이 통합을 메달리온 안에서 자동화하면 참조 데이터가 모든 도메인에 걸쳐 최신이고 일관되게** 유지된다
  (같은 소절).[^strengholt2025]
- 정렬을 강제하는 접근 둘 (같은 소절):[^strengholt2025]
  - **중앙 서비스**를 제공해 도메인이 **전사 참조 값을 발견·이해·선택·통합**하게 한다. 예컨대 참조
    데이터를 도메인에 직접 밀어 넣어 데이터 제품 개발을 돕는다.
  - **중앙 MDM 서비스**를 제공해 지역에서 전사 수준으로의 정렬을 관리하거나, **카탈로그를 써서 도메인이
    자기 데이터 제품 컬럼을 중앙 참조 데이터셋의 컬럼에 매핑**하게 돕는다. 이 경우 **데이터 제품이
    Gold에 발행될 때 데이터 품질 조회 잡 같은 후처리 활동을 걸어 불일치를 찾아 해소**한다.
- 판정 — **참조 데이터를 전사 표준에 정렬시키면 어느 팀에서 나왔든 모든 데이터 제품이 정확하고 최신이며
  일관됨을 보장**하게 된다 (같은 소절).[^strengholt2025]

참조 데이터의 자리를 다루는 이 KB의 다른 페이지는
[DV 참조 테이블](../concepts/reference-table.md)이고, 그쪽은 같은 데이터를 **Data Vault 모델의 어느
엔터티에 둘 것인가**로 묻는다. 위 절은 **여러 도메인 사이에서 그 값을 어떻게 맞출 것인가**로 묻는다 —
2026년 KB 작성 시점에 두 물음은 층이 다르고 서로를 부정하지 않는다.

## 표준화의 눈금을 실례로 보이는 맺음

11장 맺음의 나머지 절반이다. 통제와 점진적 확장 쪽은
[메달리온 메시와 데이터 관리의 탈중앙](../concepts/medallion-mesh-and-decentralization.md)이 받는다.

- 눈금을 실례로 보이는 문장 둘 — **원천 시스템 아키텍처에서는 굵은 도메인을, 소비자 쪽에서는 더 가늘고
  성숙한 도메인을 고를 수 있다.** 그리고 **마스터 데이터에는 중앙집중 MDM 시스템을 두면서 국가·통화 코드
  같은 특정 참조 데이터는 개별 도메인이 관리·매핑하게 할 수 있다** (11장
  §"Conclusion").[^strengholt2025] 앞 문장은 이 페이지의 해법 패턴 일곱이, 뒤 문장은 MDM 절과 참조
  데이터 절이 각각 떠받친다.
- 그 유연함의 목적 — **이 유연함이 끊임없이 변하는 사업 지형에 맞춰 아키텍처를 재단하게** 한다 (같은
  절).[^strengholt2025]
