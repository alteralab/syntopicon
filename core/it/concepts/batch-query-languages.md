하나의 질문: **배치 잡을 무엇으로 쓰고, 그 선택이 사람과 기계에 각각 무엇을 바꾸는가.**

## 초점이 옮겨 갔다

- **세월이 흐르며 분산 배치 처리를 위한 실행 엔진은 성숙했다. 인프라는 이제 만 대가 넘는 기계
  클러스터에서 수 페타바이트의 데이터를 저장하고 처리할 만큼 견고하다. 그런 규모에서 배치 프로세스를
  물리적으로 운영하는 문제가 대체로 풀린 것으로 여겨지면서 관심은 프로그래밍 모델을 개선하는 쪽으로
  돌아섰다** (11장, p.473).[^kleppmann2026]

## SQL이 링구아 프랑카가 된 이유

- **MapReduce·데이터플로 엔진·클라우드 데이터 웨어하우스가 모두 배치 처리의 링구아 프랑카로 SQL을
  받아들였다. 그것은 자연스러운 궁합인데, 레거시 데이터 웨어하우스가 SQL을 썼고, 데이터 분석과 ETL
  도구가 이미 그것을 지원하며, 모든 개발자와 분석가가 그것을 알기 때문이다** (11장,
  p.473).[^kleppmann2026]
- 코드가 줄어드는 것 말고 하나가 더 있다 — **손으로 쓴 MapReduce 잡보다 코드가 덜 필요한 것에 더해,
  이 질의 언어 인터페이스는 대화형 사용도 가능하게 한다. 분석 질의를 쓰고 터미널이나 GUI에서 돌리는
  것이다. 이 스타일의 대화형 질의는 비즈니스 분석가·프로덕트 매니저·영업과 재무 팀 등이 배치 처리
  환경에서 데이터를 탐색하는 효율적이고 자연스러운 방법이다. SQL 지원은 또한 분산 배치 처리 시스템을
  탐색적 질의에 적합하게 만들었다** (11장, p.473).[^kleppmann2026]

## 기계 효율도 올라간다

- **고수준 질의 언어는 시스템을 쓰는 사람의 생산성만 올리는 것이 아니라 기계 수준에서 잡 실행 효율도
  개선한다. 질의 엔진은 SQL 질의를 클러스터에서 실행될 배치 잡으로 변환하는 일을 맡는다. 질의에서
  구문 트리로, 다시 물리 연산자로 가는 이 번역 단계가 엔진이 질의를 최적화할 수 있게 한다.
  Hive·Trino·Spark·Flink 같은 질의 엔진에는 조인 입력의 성질을 분석해 당면한 작업에 어느 알고리즘이
  가장 적합할지 자동으로 결정할 수 있는 비용 기반 질의 최적화기(cost-based query optimizers)가 있다.
  최적화기는 중간 상태의 양이 최소화되도록 조인 순서까지 바꿀 수 있다** (11장,
  pp.473–474).[^kleppmann2026] 그 번역 단계의 실행 쪽 세부는
  [질의 실행 — 컴파일과 벡터화](../concepts/query-execution-compilation-and-vectorization.md)에 있다.

## SQL 말고

- **SQL이 가장 인기 있는 범용 배치 처리 질의 언어이지만 틈새 필요를 위해 다른 언어들도 여전히
  쓰인다. 예컨대 Apache Pig는 데이터 파이프라인을 하나의 큰 SQL 질의가 아니라 단계별로 지정할 수 있게
  하는 관계형 연산자 기반 언어였다. DataFrames도 비슷한 성격을 가지며, Morel은 Pig에 영향받은
  2026년 저술 시점 기준 더 현대적인 언어다. 다른 사용자들은 jq·JMESPath·JSONPath 같은 JSON 질의 언어를 채택했다** (11장,
  p.474).[^kleppmann2026] DataFrame 쪽은
  [데이터프레임과 배열](../concepts/dataframes-and-arrays.md)에 있다.
- 그래프도 배치로 돈다 — **많은 그래프 처리 프레임워크는 Apache TinkerPop의 Gremlin 같은 질의 언어로
  배치 계산도 지원한다** (11장, p.474).[^kleppmann2026] 그 언어들의 지형은
  [그래프 질의 언어](../concepts/graph-query-languages.md)에 있다.
- 표현되지 않는 것들 — **그러나 PageRank 같은 반복적 그래프 알고리즘, 복잡한 ML 작업, 그 밖의 많은
  워크플로를 포함해 모든 배치 잡이 SQL로 쉽게 표현되는 것은 아니다. 이미지·비디오·오디오 같은 비관계형
  다중 모달 데이터를 포함하는 AI 데이터 처리도 SQL로 표현하기 어려울 수 있다** (11장,
  p.475).[^kleppmann2026]

## 배치와 클라우드 웨어하우스의 수렴

- 별도 상자가 두 계열의 역사를 정리한다 — **역사적으로 데이터 웨어하우스는 특수 하드웨어 어플라이언스
  위에서 돌며 관계형 데이터에 대한 SQL 기반 분석 질의를 지원했다. MapReduce 같은 배치 처리 프레임워크는
  범용 프로그래밍 언어로 쓰인 처리 로직을 지원하고 임의의 데이터 형식을 읽고 쓸 수 있게 함으로써 더 큰
  확장성과 유연성을 제공하려 나섰다** (11장, pp.474–475).[^kleppmann2026]
- **시간이 지나며 둘은 훨씬 비슷해졌다. 2026년 저술 시점 배치 처리 프레임워크는 이제 배치 잡을 쓰는 언어로 SQL을
  지원하고, Parquet 같은 열 저장 형식과 최적화된 질의 실행 엔진을 써서 관계형 질의에서 좋은 성능을
  낸다. 한편 데이터 웨어하우스는 클라우드로 옮겨 가고 분산 배치 프레임워크가 하는 것과 같은 많은
  스케줄링·결함 내성·셔플링 기법을 구현하면서 더 확장 가능해졌다. 많은 경우 분산 파일시스템도 쓴다**
  (11장, p.475).[^kleppmann2026]
- 양방향이다 — **배치 처리 시스템이 처리 모델로 SQL을 채택한 것과 마찬가지로, 클라우드 웨어하우스도
  대안적 처리 모델을 채택했다. 예컨대 BigQuery는 DataFrames 라이브러리를 제공하고 Snowflake의
  Snowpark 라이브러리는 Pandas와 통합된다. Airflow·Prefect·Dagster 같은 배치 처리 워크플로
  오케스트레이터도 클라우드 웨어하우스와 통합된다** (11장, p.475).[^kleppmann2026]
- 그래도 웨어하우스가 못 하는 것이 있다 — **클라우드 데이터 웨어하우스도 특정 워크로드에서 고전한다.
  행 단위 계산은 열 지향 저장 형식을 쓸 때 덜 효율적이다; 그런 경우에는 대안적 웨어하우스 API나 배치
  처리 시스템이 낫다. 클라우드 데이터 웨어하우스는 또한 다른 배치 처리 시스템보다 비싼 경향이 있다. 큰
  잡은 Spark나 Flink 같은 배치 처리 시스템에서 돌리는 것이 더 비용 효율적일 수 있다** (11장,
  p.475).[^kleppmann2026]
- 그래서 결정 기준은 기술 바깥에 있다 — **궁극적으로 배치 시스템에서 데이터를 처리할지 데이터
  웨어하우스에서 처리할지의 결정은 비용·편의·구현 용이성·가용성 같은 요인으로 귀결되는 경우가 많다.
  대부분의 큰 기업은 데이터 처리 시스템을 여럿 갖고 있어 이 결정에 유연성을 준다. 더 작은 기업은 흔히
  하나로 그럭저럭 해 나간다** (11장, p.475).[^kleppmann2026]
