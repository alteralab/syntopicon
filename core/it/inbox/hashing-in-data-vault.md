# Data Vault의 해시 규율

**목차**: [왜 시퀀스 대신 해시인가](#왜-시퀀스-대신-해시인가) · [알고리즘 선택: MD5와 SHA](#알고리즘-선택-md5와-sha) · [입력 결합 규칙](#입력-결합-규칙) · [충돌 위험과 태도](#충돌-위험과-태도) · [크로스 플랫폼 재생성](#크로스-플랫폼-재생성)

Data Vault 2.0은 시퀀스 번호 대리 키(surrogate key)를 해시 키로 대체했다.
[허브](../concepts/data-vault-hub.md)의 해시 키 절이 요약한 이유를, 여기서는
계산 규율 — 무엇을 어떻게 결합해 해시하는가 — 수준으로 심화한다. 해시는
가능하면 [스테이징 영역](staging-area.md)에서 계산해 재사용한다.

## 왜 시퀀스 대신 해시인가

- 시퀀스 번호의 한계: 적재 순서 의존(부모 먼저), 링크·새틀라이트 적재가 부모
  조회 캐시를 기다리는 병목, 직렬 생성기의 동기화 병목, 복원 시 번호 보존 제약,
  다중 환경 간 동기화, MPP 분산 열로 부적합(핫스팟), 대량 데이터에서의
  롤오버(roll-over) (§11.2, pp.377–378).[^linstedt2016]
- 해시 키 계산은 업무 키만 있으면 어디서든 독립적으로 가능하다 — I/O가 아니라
  CPU 집약이라 분산이 쉽고, 부모 테이블 조회 자체를 없앤다. 새틀라이트 적재의
  열 비교도 hash diff 한 번 비교로 줄인다 (§11.2.3.5, p.389).[^linstedt2016]
- 웨어하우스의 해시는 암호화·보안 목적이 아니다. 순차 대리 키의 대체가 유일한
  목표다 (§11.2.1, p.379).[^linstedt2016]

## 알고리즘 선택: MD5와 SHA

- 권장 기본값은 **MD5**다. 근거는 보안이 아니라 **도구 호환성** — BI 영역의
  ETL 도구·DB 대부분이 MD5를 기본 지원한다. 같은 이유로 MD6·SHA-256 등 지원이
  넓지 않은 알고리즘은 비권장이다 (§11.2.3.3, p.387).[^linstedt2016]
- 충돌 확률을 더 낮추려면 SHA-1로 간다. SHA를 쓴다면 SHA-256 이상이 아니라
  SHA-1을 권장한다 — SHA-1로 이미 충돌 저항이 충분하고 저장 비용이 덜하다.
  CRC-32는 충돌 위험이 너무 커서 후보가 아니다 (§11.2.3.1–3, pp.385–387).[^linstedt2016]
- 출력 크기: MD5 128비트(hex 32자), SHA-1 160비트(40자), SHA-256 256비트(64자)
  (Table 11.1, p.380).[^linstedt2016]
- 저장은 hex 문자열로 한다. binary(16)/varbinary로 저장 공간을 아끼려는 시도는
  Hadoop 등 외부 시스템과의 상호운용성을 깨므로 비권장. 문자형 중에서도 varchar
  대신 고정 길이 타입을 써야 행이 데이터 페이지에 남아 조인 성능이 보장된다
  (§11.2.3.2–3, p.387).[^linstedt2016]
- **웨어하우스 전체에 해시 함수는 하나만** 쓴다. 엔티티별로 다른 크기를 섞으면
  관리·자동화·메타데이터가 복잡해진다. 관계형과 NoSQL 환경에도 같은 함수를
  적용한다 (§11.2.3.4, p.388).[^linstedt2016]

## 입력 결합 규칙

해시 함수 구현이 표준이어도 결과는 입력 비트에 좌우된다. 재생성 가능한 해시를
위해 모든 원시 타입을 문자열로 변환한 뒤 결합하며, 입력 문자열은 조직 전체
표준을 따라야 한다 (§11.2.2, pp.382–384):[^linstedt2016]

- **문자셋** 고정(예: UTF-8) — 같은 문자가 같은 비트가 되도록.
- **앞뒤 공백 제거**, **제어 문자 제거**(CR·LF 등 의미 없는 삽입 문자).
- **타입·길이·정밀도 표준화** — decimal(5,2)와 decimal(6,2)는 같은 문자라도
  다른 이진 표현이므로, 문자열 변환 규칙을 고정한다.
- **날짜는 ISO8601** 형식으로, **소수점·자릿수 구분자**는 지역 설정을 고정.
- **대소문자** — 업무 키는 대부분 대소문자 무관이므로 대문자로 통일(실제로
  대소문자를 구분하는 키는 예외). 해시 출력 hex도 대문자로 통일.
- **NULL은 빈 문자열로 치환**하고, 복합 입력은 반드시 **구분자**(세미콜론 등)로
  잇는다. 구분자가 없으면 (ABC, NULL, DEF)와 (ABC, DEF, NULL)이 같은 입력
  "ABCDEF"가 되어 다른 행이 같은 해시를 갖는다 (§11.2.4, p.394).[^linstedt2016]
- **필드 순서**는 물리 테이블 정의 순서를 따르고 문서화한다. **엔디언**도 표준에
  포함한다(.NET은 리틀, JVM·Hadoop은 빅 엔디언).
- 이 표준은 조직의 관리 주체(governing body)가 **표준 문서**로 확정해야 한다.
  ETL 도구·DB 내장 함수·외부 도구가 입력 준비를 서로 다르게 하면, 각자 만든
  허브·링크의 해시 키가 어긋나 시스템 간 조인이 실패한다 (§11.2.2, pp.383–384).[^linstedt2016]

### 해시 키 공식

> HashKey = Hash(UpperCase(Trim(BK₁) + d + Trim(BK₂) + ⋯ + Trim(BKₙ)))

- BKᵢ는 복합 [업무 키](../concepts/business-key.md)의 개별 구성 요소, d는
  구분자. 단일 키면 n=1이고 구분자 없이 적용한다 (§11.2.4, p.392).[^linstedt2016]
- [링크](../concepts/data-vault-link.md)의 해시 키도 같은 공식으로 — 참조하는
  허브들의 **업무 키**를 결합해 계산한다. 허브의 해시 키를 다시 해시하지
  않는다(hash-of-hash 금지): 해시의 해시는 계단식 계산을 강제해 불필요한 연산을
  늘린다. degenerated 필드(약한 허브 참조)도 입력에 포함한다 (§11.2.4, pp.391–392).[^linstedt2016]

### hash diff 공식

- hash diff는 새틀라이트 기술 속성의 변화 감지용이다. 열별 비교 대신 해시 값
  하나만 비교한다 (§11.2.5, p.395).[^linstedt2016]
- 계산은 해시 키와 유사하되 두 가지가 다르다: (1) UpperCase를 기술 데이터에는
  기본 적용하지 않는다 — 대소문자 변화도 변화로 감지해야 하는 경우가 많고,
  정책은 새틀라이트·속성 단위로 정한다. (2) 유일성을 높이기 위해 **부모의 업무
  키들을 기술 속성 앞에** 같은 구분자로 붙인다(부모 해시 키가 아니라 업무 키
  자체 — hash-of-hash 회피) (§11.2.5, pp.396–397).[^linstedt2016]
- 해시 키와 달리 hash diff는 해당 새틀라이트 하나에서만 쓰이므로 재사용 가치가
  제한적이다 (§11.2, p.379).[^linstedt2016]
- 새틀라이트 구조 변경에도 기존 hash diff를 영원히 유효하게 유지하는 세 가지
  조건: 열은 추가만 하고 삭제하지 않는다(감사 요건이기도 하다) · 새 열은 테이블
  끝에 추가한다 · 끝의 NULL 열은 해시 입력에서 제외한다(트레일링 구분자 제거).
  이 조건을 지키면 구조 변경 후 전체 hash diff 재계산이 필요 없다
  (§11.2.5.1, pp.400–401).[^linstedt2016]

## 충돌 위험과 태도

- 무한한 입력을 고정 길이로 압축하는 이상 충돌은 **예방 불가능**하다. 초기
  적재에서 충돌이 없었다는 사실은 미래를 보장하지 않는다 — 첫 충돌은 운영 첫날
  우연히 올 수도 있다 (§11.2.3.1, pp.385–386).[^linstedt2016]
- 위험의 크기: 충돌 확률 50%에 도달하는 데 CRC-32는 약 77,163건이면 되지만
  MD5는 5.06×10⁹건, SHA-1은 1.42×10²⁴건이 필요하다. 허브가 ~200개 키라면 MD5
  충돌 확률은 데이터 센터에 운석이 떨어질 확률보다 낮다. 그래도 위험이 0은
  아니라는 것이 요점이다 (§11.2.3.1, pp.385–386).[^linstedt2016]
- 그래서 태도는 "예방"이 아니라 **검출**이다: 허브 적재의 존재 확인은 해시 키가
  아니라 업무 키로 수행한다. 해시 키로 조회하면 충돌한 다른 업무 키를 "이미
  있음"으로 오인해 조용히 버린다. 업무 키로 조회하면 충돌 시 기본 키 위반
  오류가 나는데, 이것이 **의도된 동작**이다 — 통보받는 쪽이 낫다
  (§12.1.1, pp.474–475, 485).[^linstedt2016]
- 링크는 업무 키를 저장하지 않으므로 해시 키로 조회하되, 충돌 시 후속 insert가
  기본 키 위반으로 실패해 같은 방식으로 검출된다 (§12.1.2, p.489).[^linstedt2016]
- 충돌이 실제로 나면 더 큰 해시 함수(예: MD5→SHA-1)로 이행하고 해시 열 길이를
  늘려 재계산한다. 일부만 이행하면 관리 비용이 커지므로 전체를 하나의 함수로
  유지한다 (§11.2.3.4, p.388).[^linstedt2016]

## 크로스 플랫폼 재생성

- 해시 키 도입 이유 중 하나가 플랫폼 간 통합이다: 관계형 웨어하우스와 Hadoop 등
  NoSQL 환경이 **각자 독립적으로** 같은 데이터의 해시를 계산하고, 이후 정보
  마트를 만들 때 해시 값으로 조인한다 (§11.2.3.4, p.388).[^linstedt2016]
- 이것이 성립하는 조건은 단 하나다: 모든 시스템이 같은 해시 함수와 같은 입력
  준비 규칙(위 표준 문서)을 쓸 것 (§11.2.3.4, p.388).[^linstedt2016]
- 참고: 정보 마트(차원 모델)에서는 반대로 시퀀스 번호를 선호한다 — 업무
  사용자에게 해시 키가 노출되면 혼란스럽고, 팩트 테이블의 다중 차원 참조에서
  해시 키의 저장 비용이 커진다 (§11.2.3.2, pp.386–387).[^linstedt2016]

[^linstedt2016]: Linstedt & Olschimke 2016, 11장 "Data Extraction"·12장 "Loading the Data Vault"
