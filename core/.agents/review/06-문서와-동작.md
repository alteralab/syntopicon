# 문서와 동작의 어긋남

점검 계획 2단계의 산출물이다. 문서가 말하는 것과 실제로 도는 것을 다섯 자리에서
대조했다. 아무것도 고치지 않았다.

## 어떻게 확인했는가

세 방법을 썼다.

1. **실행.** 조회성 명령은 그대로 돌렸고, 쓰기가 일어나는 것은 `--dry-run`으로 돌렸다.
2. **격리 사본.** 저장소를 바꾸지 않으려고 `/private/tmp`의 스크래치패드에 저장소를
   복제하고, `it/archive/`는 실물 디렉터리로 이어 붙였다. 일부러 규칙을 어긴 파일은
   전부 그 사본에서 만들었고 확인 뒤 지웠다. 같은 시간에 다른 에이전트가 실작업
   트리에 검사용 파일을 만들고 있어서 섞이면 안 됐다.
3. **이력 조회.** `stats.sqlite`의 lint 런 224회를 읽어 어떤 검사가 실제로 울린 적이
   있는지 셌다.

숫자는 2026-08-12에 직접 센 것이다. 확인하지 못한 것은 `확인 못 함`으로 적었다.

## 1. 스킬이 부르는 명령

### 어긋난 것

**`.agents/skills/README.md`의 설치 반복문이 스킬 넷만 건다.**

```bash
for s in kb-query kb-ingest kb-lint kb-new; do
```

실제 스킬은 여섯이다. `kb-plain`과 `paper-search`가 빠져 있다. lint의
`skill-symlink` 검사는 여섯 전부를 요구하므로, 새 기기를 이 README대로 세우면
바로 error 2건이 뜬다. 지금 이 기기는 여섯 개가 다 걸려 있어서 조용하다.

**kb-ingest 3단계의 citekey 명령에 `--romanized`가 없다.**

문서에 적힌 형태는 이렇다.

```
uv run tools/citekey.py --kb <kb> --author <성> --year <연도> [--slug <말>] --type <CSL타입>
```

한국어 저자 이름을 그대로 넘기면 도구가 멈춘다. 실행 결과는 종료 코드 1과 아래
메시지였다.

> 저자 '홍길동'에서 쓸 수 있는 성을 얻지 못했습니다. 소스에 인쇄된 영문 표기를
> --romanized 로 넘기고 (...)

도구 자신의 독스트링에는 `--romanized` 예시가 있다. 스킬에만 없다. PLAN §6이
수용 검증 항목으로 "한국어 소스 1~2권"을 잡고 있어서 곧 걸린다.

**kb-lint SKILL의 "lint의 종료 코드는 항상 0이다"가 한 갈래에서 거짓이다.**

`derived.sqlite`가 없으면 lint는 리포트를 내지 않고 1을 낸다(`lint.py` 660행).
나머지 경로에서는 오류가 있어도 0을 낸다.

**kb-lint SKILL의 검사별 판단 기준이 결과 41가지 중 17가지를 다루지 않는다.**

안내가 없는 것은 아래와 같다.

```
anchor-broken, code-unsourced, epistemic-token, hub-dangling, hub-grammar,
hubs-section, inbox-age, inline-dollar-math, locator-missing, progress-contents,
progress-invalid, progress-missing, progress-suffix, progress-unit,
skill-symlink, term-drift, wikilink
```

(`heading-h1`, `heading-skip`, `heading-depth` 셋은 `heading-*`로 묶여 있으므로
다룬 것으로 셌다.) 리포트를 읽는 사람이 이 열일곱을 만나면 스킬이 답을 주지 않는다.

**`it/overview.md`의 Tools 절 명령이 실행되지 않는 형태다.**

```
- 검색: `qmd query <질의> -c it` / 형태소 레그 `tools/ksearch`
- 점검: `tools/lint --kb it`
```

실제 호출은 `uv run --group index tools/ksearch.py`와 `uv run tools/lint.py --kb it`다.
그대로 치면 명령을 찾지 못한다.

**kb-ingest 9단계의 되짚기가 틀린 단계를 가리킨다.**

본문은 `_progress.yaml`을 두고 "(4단계 참조)"라고 적는데, 그 설명은 2단계
(스냅샷) 안에 있다. 4단계는 지식 추출이다. `lint.py`의 `_check_progress`
독스트링도 같은 오기를 갖고 있고, 거기에 더해 "SCHEMA"를 가리키는데 `SCHEMA.md`는
`_progress.yaml`을 한 번도 언급하지 않는다. 실제 정본은 `schema/progress.yaml`이다.

### 맞은 것

스킬 여섯의 `uv run` 명령을 전부 뽑아 `argparse` 선언과 대조했다. **옵션이 없는데
문서가 부르는 자리는 하나도 없었다.** 아래는 실제로 돌려 본 것이다.

| 명령 | 결과 |
|---|---|
| `validate.py` | 178개 파일, KB 1개, 오류 0 |
| `ksearch.py "<질의>"` | 형태소 히트 출력 |
| `edges.py backlinks`, `neighbors --depth 2`, `degree` | 셋 다 정상 |
| `lint.py`, `--kb`, `--quiet`, `--incremental`, `--overlap-full` | 넷 다 정상 |
| `reindex.py` | 파일 176, 간선 1437 |
| `plaincheck.py` | 위반 3건 검출, 종료 1 |
| `citekey.py --dry-run` | 키 제안 출력 |
| `merge.py --all --kb it --dry-run` | 승격 대상 없음 |
| `kb-new.py --dry-run` | 생성 계획 출력, 아무것도 쓰지 않음 |
| `rename.py --dry-run` | 링크 재작성 계획 출력 |
| `verify.py --dry-run` | 승급 예정 출력 |

- 커밋 게이트는 실제로 켜져 있다. `core.hooksPath`가
  `core/tools/githooks`를 가리키고, 그 훅이 `validate.py`를 부른다.
- `qmd cleanup` 하위 명령은 실재한다. 다만 벤더 도움말은 그 일을
  "Clear caches, vacuum DB"라고만 적는다. kb-ingest가 말하는 고아 벡터 정리와
  같은 것인지는 **확인 못 함**(스킬은 실측 3회를 근거로 든다).
- `merge.py --all`은 승격할 것이 없을 때 종료 코드 1을 낸다. 스킬이 그 줄을
  체인으로 잇지 않아서 문제가 되지는 않는다.

## 2. 도구가 스스로 밝힌 목적

도구 16개의 독스트링을 전부 뽑아 실제 동작과 대조했다.

### 어긋난 것

**`lint.py`의 "PLAN §4.3 매트릭스 15행 전부 구현됐다"가 세 겹으로 틀렸다.**

- 그 매트릭스는 지금 **21행**이다. 15행은 옛 크기다.
- 21행 중 하나("원어 병기, 직인용")는 매트릭스 자신이 "기계 검사 없음"이라고
  적고 있다. "전부 구현됐다"는 그 자리를 덮는다.
- "inbox 나이, 크기" 행의 **크기 쪽은 구현되어 있지 않다.** `check_inbox`는 나이만
  본다.
- 반대로 lint는 매트릭스에 없는 것을 여럿 낸다. `term-drift`, `hub-split-hint`,
  `skill-symlink`, `progress-missing`, `progress-invalid`, `progress-unit`,
  `progress-suffix`, `progress-contents`가 그것이다.

**`lint.py`가 저장소 밖을 읽고 저장소 밖에 쓴다. 독스트링에 없다.**

`check_skill_symlinks`는 `~/.claude/skills/`를 읽고, `main`은 `stats.sqlite`에
런 기록과 증분 기준선을 쓴다. 쓰기는 kb-lint SKILL이 "이원 기록"으로 밝히지만
도구 자신의 첫 줄은 "리포트"라고만 말한다.

**`kb-new.py`의 독스트링이 저장소 밖 쓰기를 적지 않는다.**

`--dry-run` 출력이 보여 준 대로 이 도구는 전역 qmd 설정
(`~/.config/qmd/index.yml`)에 컬렉션을 등록하고 루트 `overview.md`의 KBs 절을
재생성한다. 독스트링은 "KB의 유일한 생성 경로"까지만 말한다. PLAN §4.3에는 적혀
있다.

**`validate.py`는 오타 경로를 받으면 조용히 통과시킨다.**

```
$ uv run tools/validate.py it/concpets/nope.md
0개 파일 · KB 1개 (it) · 오류 0 · 경고 0    (종료 0)
```

없는 파일 하나를 넘겼는데 "오류 0"과 종료 코드 0이 나온다. 이 저장소의 §3 규약은
"이해 못 하는 입력은 조용히 건너뛰지 말고 실패시킨다"다. 같은 이유로
`validate.py --help`도 도움말 대신 "0개 파일, 오류 0"을 낸다. 저장소 밖 경로를
넘기면 그때는 처리되지 않은 예외로 죽는다. 스킬은 늘 인자 없이 부르므로 지금 이
경로는 사람이 손으로 칠 때만 열린다.

**`citekey.py`의 "여기서 만들어진 빈 파일이 곧 예약이다"가 실제와 다르다.**

만들어지는 것은 빈 파일이 아니라 `type`, `title`, `issued`와 H1이 든 씨앗이다.
예약이라는 성질은 맞고, 빈 파일이라는 서술만 틀렸다.

**`lint.py`의 `_has_toc` 주석이 뒤집힌 결정을 현재로 적는다.**

주석은 "저작 관례는 인라인 문단형인데 검사가 불릿형만 인정해 오검출이었다,
형식을 §2.6에 성문하고 검사를 맞췄다"고 말한다. 그런데 PLAN §2.6은 2026-08-11에
반대로 뒤집혔다. 지금 정본은 링크 불릿 목록이고 인라인 문단형은 폐기됐다.
검사는 여전히 둘 다 통과시킨다. 지금 코퍼스에서 100줄 넘는 페이지 110개가 전부
불릿형이라 잘못된 결과는 안 나오지만, 주석을 믿고 고치는 사람은 틀린 전제로
움직인다.

### 맞은 것

나머지 독스트링은 실제와 맞았다. 특히 좋은 자리가 둘이다.

- `rename.py`는 **자기 결함을 스스로 밝힌다.** citekey 개명이 절반만 되고
  본문 각주와 `sources[].id`는 손으로 고쳐야 한다는 것을 독스트링에 적어 두었다.
- `kb-new.py`는 PLAN이 약속한 restic 태그 등록을 하지 않는데, **왜 안 하는지**를
  코드 주석과 사람용 출력 양쪽에 적는다(태그는 백업 시점에 파일 시스템에서
  산출된다). 약속과 다르지만 침묵이 아니다.

`plaincheck.py`는 독스트링이 적은 종료 코드 규약(위반 1, 입력 문제 2)을 실제로
지켰다.

### 이력이 말한 것

`stats.sqlite`의 lint 런 224회를 훑었다. 결과 종류 41가지 중 **한 번이라도 나온
것은 18가지**다. 나머지 **23가지는 한 번도 0이 아닌 적이 없다.**

| 한 번도 안 나온 검사 23가지 |
|---|
| `code-unsourced`, `contradiction-one-sided`, `cross-kb-link`, `epistemic-token`, `heading-depth`, `heading-h1`, `heading-skip`, `hub-dangling`, `hub-grammar`, `hub-split-hint`, `hubs-section`, `inbox-age`, `inbox-p90`, `ingest-trailer`, `inline-dollar-math`, `page-too-long`, `progress-invalid`, `progress-missing`, `redirect-hop`, `skill-symlink`, `snapshot-missing`, `source-uncited`, `wikilink` |

격리 사본에서 규칙을 어긴 파일을 두 차례에 걸쳐 만들었다. 1차는 페이지 문법과
링크와 스냅샷, 2차는 git 이력과 진행 파일과 허브 절이다.

**스물셋 전부 잡혔다.** 하나도 새지 않았다.

**결론: 늘 0인 이유는 검사가 눈이 먼 것이 아니라 코퍼스가 그 규칙을 안 어겼기
때문이다.** 이것이 이 절의 가장 중요한 답이다.

### 반대 방향의 발견

늘 0인 검사가 아니라, **늘 크게 울리는 검사** 쪽에서 문제가 나왔다.

**`claim-unfootnoted` 769건 중 649건(84%)이 구조적 오검출이다.**

개념 페이지 맨 아래의 "이어지는 페이지" 절은 `- [제목](경로) — 한 줄 설명` 꼴의
링크 불릿이다. 설명이 붙어 있어서 `pointer_only`가 아니고, 각주도 없으니 각주 없는
claim으로 찍힌다. 그런데 그 문법은 §2.6이 허브와 overview에 **요구하는** 문법이고,
`hub-grammar` 검사는 그 설명이 없으면 오히려 경고한다. 같은 모양이 한쪽에서는
필수이고 다른 쪽에서는 위반이다.

셈은 이렇다. 개념 페이지의 불릿 6811개 중 각주가 있는 것 3533개, 포인터만인 것
855개, 부모 각주를 상속하는 것 1654개, 검출된 것 769개다. 그 769개를 갈라 보면
링크로 시작하는 것이 649개, 산문 불릿이 120개다.

**최근 런의 리포트는 사실상 이 한 검사다.** 224번 런의 결과 867건 구성은 아래와 같다.

| 검사 | 등급 | 건수 |
|---|---|---|
| `claim-unfootnoted` | info | 769 |
| `term-drift` | info | 41 |
| `overlap` | info | 34 |
| `field-unused` | info | 12 |
| `morph-fragmentation` | info | 8 |
| `locator-missing` | info | 3 |

`--quiet`를 붙이면 info가 전부 숨으므로 출력이 비게 된다. 즉 정상 상태에서 lint는
"769건짜리 한 덩어리"이거나 "빈 화면"이고, 그 사이가 없다.

**작은 중복 둘도 확인했다.**

- `progress-suffix`는 한 값에서 두 번 나온다. 범위 `1-50`을 하이픈으로 쪼개
  조각마다 결과를 내면서 메시지에는 원래 값을 그대로 적기 때문이다. 실측에서
  값 셋이 결과 다섯이 됐다.
- 스냅샷 디렉터리가 아예 없으면 `snapshot-missing`과 `progress-missing`이 같은
  원인으로 둘 다 나온다. `_check_progress`가 디렉터리 존재를 먼저 보지 않는다.

### 맞은 것

- `overlap`은 **분모를 함께 낸다.** 최근 런은 "비교 13695쌍 중 33건이 임계 0.85
  초과 (0.24%)"였다. 41가지 중 분모를 내는 것은 이 하나다.
- 이력에 error 등급으로 실제 나온 것은 `broken-link`(98런, 3848건)와
  `snapshot-mismatch`(2런, 18건) 둘뿐이다.

## 4. 임계값의 근거

코드에 박힌 숫자를 전부 찾았다.

### 어긋난 것

**오류 50건 경보는 여섯 구간에서 울렸고 여섯 구간 다 정상이었다.**

이미 알고 있던 어긋남을 이력으로 다시 셌다. 세 번이 아니라 여섯 구간, 31개 런이다.

| 런 구간 | 오류 수 | 구성 |
|---|---|---|
| 72, 73 | 54 | `broken-link` 100% |
| 83~86 | 67, 59 | `broken-link` 100% |
| 116~119 | 53 | `broken-link` 100% |
| 166~171 | 97 | `broken-link` 100% |
| 192~198 | 55 | `broken-link` 100% |
| 201~208 | 68 | `broken-link` 100% |

**단 한 번도 다른 검사가 섞이지 않았다.** 승급 직전에 새 페이지를 가리키는 링크가
깨져 있는 것이 정상 상태이므로, 이 경보는 지금 사실상 "승급 대기 중인 링크 수가
50을 넘었다"만 말한다. 근거는 PLAN §6에 있고 "자체 상수로 시작해 운영 데이터로
보정"이라고 적혀 있다. 보정할 데이터가 이제 224런 모였다.

**같은 성격의 임계값이 하나 더 있다. inbox 나이 P90이다.**

```python
p90 = ordered[min(int(len(ordered) * 0.9), len(ordered) - 1)]
```

표본 하한이 없다. 초안이 하나뿐이면 `int(1 * 0.9)`가 0이라 P90은 그 파일의 나이
그대로가 된다. 실측에서 30일 넘은 초안 **한 개**를 두자 error 등급
`inbox-p90` 경보가 울렸다. 경보가 이름 붙인 상태는 "적체 파산"인데 실제 상태는
"묵은 초안 하나"였다. 오류 50건 경보와 같은 종류다.

지금은 inbox가 0건이라 울린 적이 없어서 겉으로 드러나지 않았다.

**search-miss 경보는 코드가 없다.**

PLAN §6과 kb-lint SKILL의 임계 경보 표는 세 경보를 나란히 적는다. 그중
"search-miss가 직전 20회 중 4회 초과"는 **어디서도 계산되지 않는다.**
`stats.sqlite`에 `search_miss` 테이블이 있고 kb-query에 넣는 절차가 있지만 읽는
곳이 없다. 지금 그 테이블의 행은 0건이라 kb-query 쪽 기록도 한 번도 돈 적이 없다.
경보 셋 중 하나가 구현되지 않았는데 표는 셋을 같은 격으로 보여 준다.

**근거가 없는 숫자 넷.**

| 상수 | 값 | 적힌 근거 |
|---|---|---|
| `HUB_DEGREE` | 3 | "자체 상수"라고만 적혀 있다 |
| `FRAGMENT_MIN_HITS` | 2 | "한 번뿐인 파편은 오탐일 확률이 높다" |
| `MAX_HEADING_DEPTH` | 4 | "자체 휴리스틱" |
| `TOP_N` (retrieval_eval) | 10 | 없음 |
| 리포트 표시 상한 | 20 | 없음 |

`HUB_DEGREE`, `FRAGMENT_MIN_HITS`, `MAX_HEADING_DEPTH`는 자체 상수임을 밝히고
있으므로 거짓은 아니다. 표시 상한 20은 아무 설명이 없고, 769건짜리 검사에서
20건만 보이게 만드는 숫자다.

### 맞은 것

## 5. 표류할 수 있는 산문

사람이 손으로 적고 기계가 검사하지 않는 기록을 찾았다.

### 어긋난 것

**소스 메타의 "이번 런 범위" 일곱 중 셋이 어긋나 있다. 아직 그대로다.**

아홉 런 뒤처졌던 사건의 대응은 `_progress.yaml`을 만든 것까지였고, **틀린 산문
자체는 지워지지 않았다.** 실제 진행과 대조하면 이렇다.

| citekey | 메타의 산문 | `_progress.yaml`의 covered | 판정 |
|---|---|---|---|
| shapira2021 | 2장과 6장. 3~5장과 7장 이후는 후속 런 | `1p-419p` 전권 완주 | **어긋남** |
| kimball2013 | 1장. 2장과 3장은 후속 런 | 1~8장, 10장, 15~20장 | **어긋남** |
| linstedt2016 | 4장의 4.1~4.5. 5, 6, 2장은 후속 런 | 1~6장, 9~14장 | **어긋남** |
| petrov2019 | 1, 2, 7장 | `1p-44p`, `129p-164p` (1, 2, 7장) | 맞음 |
| zhou2024 | 2부 2장과 3장 | `59p-196p` | 맞음 |
| kleppmann2026 | 1장 | `1p-32p` | 맞음 |
| ongaro2014-raft | 논문 전문 | `1` (whole) | 맞음 |

kb-ingest는 "소스 메타의 산문은 정본이 아니다"라고 크게 적었지만, 그 산문은
여전히 페이지 위에 남아 사람과 에이전트에게 읽힌다. 기계는 이 셋을 잡지 않는다.
lint의 `progress-*` 검사는 진행 파일의 존재와 형식만 보고 산문과 대조하지 않는다.

**`core/CLAUDE.md`의 현재 상태가 크게 뒤처졌다.**

문서는 이렇게 말한다.

> 현재 상태: 수용 검증 진행 중. KB `it/`에 도서 2권 ingest 완료(concepts 38건)

실제로 센 것은 아래와 같다.

| 항목 | 문서 | 실제 |
|---|---|---|
| 소스 | 도서 2권 | 9건 (도서 6, paper-conference 1, webpage 2) |
| concepts | 38건 | 149건 |
| synthesis | 적혀 있지 않음 | 17건 |
| ingest 커밋 | 적혀 있지 않음 | 23건, citekey 10종 |

같은 문서의 다음 줄은 "논문, docs 타입 커버 필요"라고 적는데 **둘 다 이미
커버됐다.** `ongaro2014-raft`가 paper-conference이고, `dbtlabs2026-materialization`과
`kafka2025-kraft`가 webpage다. 이 문서는 core 레이어 작업의 첫 줄이라 파급이 가장
크다.

**PLAN §6의 진행 상태도 같은 자리에서 멈춰 있다.**

> 실행 계획 (2026-08-10 수립 — 진행 상태: 도서 2권 완료, 38 concepts)

이어지는 "소스 배분 (잔여 28~48)"과 "DW 기존 2권 외 분산 시스템, 스트리밍, DB
내부 (...)"도 같은 시점의 말이다. 그 축들은 이미 들어와 있다.

**점검 자료 자신도 하나 틀렸다.**

`02-도구.md`와 `04-계획.md`가 권하는 재계수 명령은 이렇다.

```sh
rg -o 'Finding\("[a-z-]+"' tools/lint.py | sort -u
```

문자 집합에 숫자가 없어서 `heading-h1`과 `inbox-p90`을 중간에서 잘라 먹는다.
결과 종류는 38이 아니라 **41**이고, 두 결과가 목록에서 통째로 빠져 있다. 이
저장소의 §3 규약("regex 파싱 금지, 구조는 파서로 읽는다")이 문서 자신의 계수
명령에는 적용되지 않았다.

**평가가 규약을 못 지키고 있다.**

- evals README와 PLAN §4.6은 "스킬당 3개 이상"을 규약으로 둔다. 시나리오는 12개인데
  전부 kb-ingest, kb-lint, kb-new, kb-query 넷을 다룬다. **kb-plain과 paper-search는
  0개다.**
- "스킬을 고치면 해당 시나리오를 다시 돌린다"도 규약이다. 마지막 실행은
  2026-08-06이고, 그 뒤 네 스킬이 전부 수정됐다(kb-ingest 08-12, kb-lint 08-11,
  kb-query 08-10, kb-new 08-09). **넷 다 재실행되지 않았다.**

**소비자가 없는 큐 둘.**

- `schema/user-dict.yaml`의 `entries`가 빈 목록이다. `morph-fragmentation` 검사는
  199개 런에서 963건을 냈는데 한 번도 사전으로 옮겨지지 않았다.
- `verified` 필드를 쓰는 페이지가 0개다. `verify.py`가 만드는 기록이 코퍼스에
  존재하지 않는다. `stale_after`, `contradicts`, `superseded_by`도 지금 0건이라
  `field-unused`가 224런 전부에서 이들을 "쓰인 적 없음"으로 낸다.

**`.agents/skills/README.md`의 설치 반복문**은 1절에 적은 그대로다. 사람이 손으로
적고 기계가 검사하지 않는 목록의 전형이다.

### 맞은 것

- **PLAN §4.4의 "적체가 생긴 적이 없다"는 지금도 참이다.** inbox가 0건이고
  `inbox-p90`은 224런에서 한 번도 나오지 않았다. 처방을 미리 두지 않은 규율이
  아직 근거를 유지한다.
- **`it/overview.md`의 Hubs 절이 맞다.** 17개가 걸려 있고 synthesis 페이지도 17개다.
  절 주석이 말하는 "10~30개" 범위 안이고 빠진 것이 없다. `hub-candidate`가 224런에서
  2번밖에 안 나온 이유가 이것이다.
- **`schema/migrations.md`의 결번 대장이 비어 있는데 실제로도 은퇴 키가 없다.**
  validate가 그 표를 파싱해 대조하므로 이 자리는 기계가 지킨다.
- **커밋 게이트가 켜져 있다.** 산문으로만 적힌 절차가 아니라 `core.hooksPath`
  설정으로 실재한다.
- **KB 본문 페이지의 런 상대 산문은 두 파일뿐이다.** "이번 런", "이번 개정" 같은
  말이 `brokers-and-clusters.md`와 한 파일에만 있다. 지식 페이지 쪽으로는 이
  종류가 번지지 않았다.
- 루트 `overview.md`의 KBs 절은 기계 소유이고 실제 KB 목록과 맞았다.
