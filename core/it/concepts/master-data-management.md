## 마스터 데이터란 무엇인가

- 마스터 데이터(master data)는 원천 시스템에 흩어진 참조 데이터의 혼란에 대한 비즈니스 측의 답으로, 조직의 운영 시스템에 구현된 비즈니스 프로세스에 참여하는 비즈니스 엔터티를 기술한다. 언뜻 데이터 웨어하우스의 차원과 비슷해 보이지만 운영 시스템에 훨씬 가깝고, 잘 구축되면 차원의 훌륭한 원천이 된다 (§9.1.1, p.261).[^linstedt2016]
- 데이터 관리(data management)는 전사 정보 수명 주기를 관리하는 데 필요한 아키텍처·관행·절차·정책의 개발과 실행이며, IT의 데이터 관리 전문가와 비즈니스의 데이터 스튜어드(data steward)가 나눠 지는 공동 책임이다 (§9.1.2, p.261).[^linstedt2016]
- 마스터 데이터 관리(master data management, MDM)는 이 둘의 결합이다 — 마스터 데이터와 데이터 관리는 각각 독립된 정의·프로세스·활동의 집합이고, 사람과 프로세스가 두 요소를 묶어 전사적 품질 관리(total quality management, TQM)와 갭 분석을 가능하게 한다 (§9.1.3, p.261).[^linstedt2016]
- MDM이 만들려는 것의 정의는 원문을 직인용한다 (§9.1.3, p.262).[^linstedt2016]

> MDM is the creation of a single, well-defined version of all the data entities in the enterprise, the so-called "golden records" – in other words, a single copy of a record representing a single business concept like customer, or product, or order, or sale and so on.

- MDM이 중앙 관리하는 비즈니스 엔터티는 사람(고객·승객·직원), 장소(공항·국가·도시), 물리적 엔터티(항공기·좌석·제품), 논리적 엔터티(브랜드·조직 단위·부서·프로젝트 역할)이다. 항공편·판매 같은 트랜잭션 데이터는 여기 포함되지 않는다 — 마스터 데이터는 트랜잭션에 맥락 정보를 제공하는 데이터다 (§9.2, p.263).[^linstedt2016]

## MDM의 목표: 데이터 조화와 되먹임

- 진정한 MDM의 마지막 단계는 Six Sigma와 TQM 원칙을 적용해 원천 시스템들을 조정(reconcile)하고 데이터 갭·프로세스 갭을 닫는 것이다. 골든 카피가 선정되면 이를 모든 원천 시스템에 되먹여(feed back) 어긋난 데이터를 덮어쓴다 — TQM에서 이를 데이터 조화(data harmonization)라 부른다 (§9.2, p.262).[^linstedt2016]
- 조화는 첫걸음일 뿐이다. 다음은 어떤 프로세스가 어긋난 데이터를 계속 만들어내는지 찾아, 잘못 적용된 원천 시스템 프로세스를 교정(Six Sigma 오류 감소)해 나쁜 데이터의 흐름을 상류에서 차단하는 것이다. MDM이 제대로 되면 결과는 "단일 진실 버전(single version of the truth)" 즉 골든 카피를 가진 전사 정보 시스템이다 (§9.2, p.262).[^linstedt2016]
- 조화된 마스터 데이터의 이점: 데이터 품질 개선(매핑·비즈니스 규칙 감소), 프로세스 간 정보 수수·검증 용이, 데이터 교환 자동화(수동 중복 제거 불필요), 정보 요구사항 축소(중복 제거용 규칙이 줄어든다) (§9.2, p.262).[^linstedt2016]
- 차원 모델링과의 관계: 정제·통합(conform)은 차원 모델의 요구가 아니라 마스터 데이터가 본질적으로 지향하는 것이며, MDM은 표준 차원(conformed dimension)의 속성 값 집합 정의, 여러 시스템의 고객 레코드 정제·통합, 비즈니스 규칙 계산용 파라미터 설정 등 데이터 웨어하우스 곳곳에 쓰일 참조 데이터를 만들고 유지한다 (pp.260, 263).[^linstedt2016]

## 관리 동기

- 조직이 마스터 데이터를 관리해 얻는 이점 (§9.3, pp.263–264):[^linstedt2016]
  - 일관성: 같은 의미의 속성이 시스템마다 다르게 표현되는 문제(예: 성별을 "Male"/"Female" vs "M"/"F")를 비즈니스가 결정한 하나의 값으로 통일.
  - 완전성: NULL·공백을 허용하는 시스템과 기본값을 계산하는 시스템 사이에서 어떤 값을 쓸지 결정.
  - 올바른 형식: 대문자 전용(메인프레임) 값의 표기 교정 — 알고리즘만으로 어려운 비서구권 이름은 비즈니스가 결과를 재정의(override)한다.
  - 범위 검증: 수치 속성의 타당 범위 확인(예: 항공기 엔진 마력이 200,000 HP를 넘으면 오타).
  - 복합 데이터 처리: 단독으로는 정상이나 다른 속성과 결합하면 틀린 값(예: 터보제트는 추력을 내므로 마력으로 재지 않는다)을 잡는 복합 규칙 검증.
  - 중복 제거: 구독 애플리케이션이 중복 걱정 없이 쓸 수 있는 마스터 데이터 제공.
- 조직 차원의 빠른 도입을 이끄는 외부 동인: 규제 준수(Sarbanes-Oxley·Basel II/III — Enron 등 회계 부정이 배경), 프라이버시·데이터 보호(의료 기록·주민번호·카드 정보), 안전·보안(USA Patriot Act, 자금세탁 방지), 복잡도·속도 증가에 대응한 고객 경험 개선. 대부분의 MDM 이니셔티브는 이런 운영적 이점에 집중하고 분석 영역의 이점은 무시하는 경향이 있다 (§9.3, p.264).[^linstedt2016]

## 데이터 웨어하우스에서 자라나는 MDM: 성숙도 3단계

- MDM이 없는 조직에서는 데이터 웨어하우스가 마스터 데이터의 또 다른 동인이자 원천이 되며, MDM 이니셔티브는 데이터 웨어하우스 프로젝트로부터 성숙해 간다 (§9.3, pp.264–266):[^linstedt2016]
  - 1단계: MDM 시스템이 없다. 마스터 데이터는 운영 시스템에서 조달되거나 데이터 웨어하우스의 일부로 개발·관리되고, 웨어하우스의 정보 마트만 이를 소비한다. 전사 데이터 웨어하우스가 조직의 단일 사실 저장소이므로 사실상 마스터 데이터의 원천 역할을 겸한다.
  - 2단계: 웨어하우스의 마스터 데이터를 별도 정보 마트(예: 3정규형 모델)로 발행해, 다른 운영 시스템이 표준화된 방식으로 접근하게 한다.
  - 3단계: 비즈니스가 마스터 데이터를 직접 수정할 수 있게 된다. 정보 마트는 읽기 전용 뷰가 아니라 MDM 데이터베이스가 되고, 수정된 마스터 데이터는 구독자(운영 시스템·데이터 웨어하우스)에 되먹여진다. 이 시점에 MDM 데이터베이스는 데이터 웨어하우스의 또 다른 원천 시스템이 된다.

## 운영적 MDM vs 분석적 MDM

- 운영적 마스터 데이터: 운영 시스템이 MDM의 참조 데이터를 자기 비즈니스 프로세스의 비즈니스 객체로 사용하고, 프로세스 실행 중 수집한 새 정보로 풍부화하며, MDM이 정의한 비즈니스 키로 트랜잭션 데이터를 참조한다. 이런 운영 시스템을 마스터 데이터 구독자(master data subscriber)라 한다. 어떤 시스템도 트랜잭션 정보를 MDM에 쓰지 않는다 — 트랜잭션 데이터는 운영 시스템에만 남고 ETL이 별도로 수집한다 (§9.4, pp.266–267).[^linstedt2016]
- 어느 부서·기능 단위가 MDM의 마스터 데이터를 변경할 수 있는지는 비즈니스가 결정해야 한다 — 전사에서 쓰이는 참조 데이터에 대한 원치 않는 변경을 막기 위해서다 (§9.4, p.266).[^linstedt2016]
- 데이터 웨어하우스도 마스터 데이터의 구독자다. 운영 시스템이 마스터 데이터를 지역적으로 수정·풍부화하므로, 웨어하우스는 중앙 MDM과 모든 운영 원천 시스템 양쪽에서 마스터 데이터를 적재한다. 마스터 데이터는 주로 차원 엔트리의, 트랜잭션 데이터는 팩트 테이블의 원천이 된다 (§9.4, p.267).[^linstedt2016]
- 분석적 마스터 데이터: 데이터 웨어하우스만을 위해 만들어지고 유지되는 마스터 데이터. 유형 (§9.4, pp.267–268):[^linstedt2016]
  - 비즈니스 규칙 파라미터: 세율, "지연 항공편 = 15분 이상 늦은 편" 같은 정의는 바뀔 수 있으므로 ETL이나 뷰에 하드코딩하지 말고 MDM에 둔다 — 비즈니스 사용자가 IT 개입 없이 수정할 수 있다.
  - 그룹·구간(bin) 정의: 지연 시간을 15분 간격 그룹으로 매핑하는 기준표처럼, 수치 상·하한으로 풍부화해 ETL 매핑에 쓴다.
  - 코드와 설명: IATA 공항 코드처럼 방대한 코드를 읽을 수 있는 캡션·정렬 순서로 풍부화.
  - 계층 정의: 조직 계층, 자재 명세(bill of materials) 등을 IT 개입 없이 수정 가능하게.
  - 날짜·달력 정보: 공휴일·영업 시즌의 이름과 정의, 회계 달력의 시작·종료일.
  - 기술 파라미터: 적재 시 호출할 외부 스크립트, 환경 이름, 원천 시스템 FTP 주소, 시간대, 장애 통보 대상자 등.
- 분석적 마스터 데이터는 웨어하우스 전용이라 운영 시스템에 되먹여지지 않지만, 운영 시스템이 쓰기 시작하면 운영적 마스터 데이터로 전환되기도 한다. 반대로 분석 시스템에만 필요한 속성(예: 승객 분류 태그)을 운영 시스템에 필드를 추가하는 대신 MDM의 새 엔터티에 붙이는 것도 흔한 관행이다 (§9.4, p.269).[^linstedt2016]

## Managed Self-Service BI의 enabler

- 비즈니스 규칙 파라미터를 MDM에 두면, 권한 있는 비즈니스 사용자가 파라미터 값을 바꿔 비즈니스 규칙의 결과에 영향을 줄 수 있다(예: 기대 수익률, 감가상각 방식 선택). 파라미터만 바꿀 수 있고 규칙 자체는 바꿀 수 없으므로 이는 관리형 셀프서비스 BI(managed self-service BI)를 정확히 따른다: IT는 파라미터와 규칙을 관리형으로 구축하고, 비즈니스는 그 경계 안에서 셀프서비스로 값을 조정한다 (§9.5, pp.269–270).[^linstedt2016]
- 파라미터를 MDM에 두는 부가 이점: 투명성(누가 언제 무엇을 바꾸고 승인했는지 추적 — 변경 추적 없는 일반 테이블과 대비), 컴플라이언스(원시 데이터가 어떻게 정보로 변환됐는지 문서화 요구 충족), 보안(내장 접근 통제), 재사용성(정보 마트마다 다른 파라미터 값 집합 제공 가능) (§9.5, pp.269–270).[^linstedt2016]
- 다른 축은 운영 시스템과 마스터 데이터 사이의 닫힌 루프(closed loop)다: 비즈니스 사용자가 수정한 마스터 데이터가 운영 시스템의 프로세스 실행과 트랜잭션 데이터에 영향을 주고, 그 둘이 다시 웨어하우스로 들어와 분석 결과에도 반영된다. 이 루프백은 성공적인 managed self-service BI의 필수 요소다 (§9.5, p.270).[^linstedt2016]
- 참조 데이터가 내부 데이터베이스 테이블에만 있으면 비즈니스 사용자는 IT 지원 없이 수정할 수 없다. 진정한 managed self-service BI를 위해서는 비즈니스가 그 데이터의 통제권을 넘겨받아 수정하고 MDM에 되써서 웨어하우스에 적용할 수 있어야 한다 (§9.5, p.270).[^linstedt2016]

## TQM의 enabler

- 사용자가 리포트에서 오류를 발견하면 웨어하우스 팀에는 두 선택지가 있다: (1) 적재 프로세스를 수정해 잘못된 데이터를 교정 값으로 덮어쓰기 — 원시 데이터는 그대로 두고 원하는 출력을 만들어내는 비즈니스 규칙을 넣는 것, (2) 운영 시스템의 원시 데이터를 직접 수정. 웨어하우스 팀이 운영 시스템을 통제하지 못해 현실에서는 (1)이 많지만, TQM의 목표는 오류를 원천에서 고쳐 잘못된 데이터가 구독 애플리케이션에 퍼지는 것을 막는 것이다 (§9.6, pp.270–271).[^linstedt2016]
- 원천에서 고치려면 갭 분석이 선행돼야 한다: 비즈니스가 원천 시스템에 존재한다고 기대하는 데이터·품질(비즈니스 인식)과 IT가 보는 실제 데이터·품질(IT 현실) 사이의 차이를 평가한다 (§9.6, p.271).[^linstedt2016]
- 갭 분석 접근법 두 가지: 전통적 문서 중심(문서화된 프로세스의 갭은 이해하지만 실제 프로세스는 숨겨짐)과 애자일 인터뷰 중심(사람들이 실제로 따르는 프로세스를 이해하지만 더 많은 노력·분석 필요). 실무에서는 가능하면 둘 다 적용한다 — 문서가 있다고 최신·정확하다는 보장이 없다. 결과는 개선 기회·권고·이익을 담은 평가 보고서로 문서화하고, 이해관계자 검증을 거쳐 갭을 닫는 노력의 방향타로 쓴다 (§9.6, pp.271–272).[^linstedt2016]
- MDM 시스템은 비즈니스 사용자에게 운영·분석 시스템에서 쓰이는 마스터 데이터의 통제권을 주지만, 이 목표를 온전히 달성하려면 마스터 데이터가 분석 용도만이 아니라 운영 시스템에도 통합돼야 한다. 그래야 비즈니스가 IT에 의존하지 않고 스스로 오류를 교정한다 — 갭이 IT 개입 없이 닫힌다 (§9.6, p.272).[^linstedt2016]
- Data Vault 2.0 방법론은 MDM을 전사 BI 팀의 표준 운영 절차의 일부로 규정하며, 거버넌스·데이터 통제·TQM 절차를 SEI/CMMI 원칙 적용에 녹여 넣는다 (§9.2, p.263).[^linstedt2016]

## 분석 마스터 데이터의 실물 — 날짜 차원

위 "분석적 마스터 데이터" 목록의 "날짜·달력 정보" 항목이 마지막 장에서 실제 산출물로
나타난다. 관리형 셀프서비스 BI의 원칙이 도구 기본값을 이기는 장면이라 기록해 둔다.

- 분석 서비스는 마법사에서 날짜 차원(time table)을 스스로 만들어 주는 기능을 제공하지만,
  **저자들은 그 과정을 직접 하기를 권한다.** 도구가 제공하는 시간 데이터를 쓰는 대신,
  **권장되는 관리형 셀프서비스 BI 접근은 날짜 차원에 포함할 날짜들과 그에 대응하는 서술
  필드를 담은 분석 마스터 데이터 테이블을 제공하는 것**이다. 이 접근의 이점은 **업무
  사용자가 서술 필드를 수정할 수 있다는 것** — 예컨대 날짜·월의 약어나 캡션을 바꿀 때다.
  책이 함께 제공하는 마스터 데이터 서비스 모델이 그런 멤버를 공급한다
  (§15.2.1, p.700).[^linstedt2016]
- 이 마스터 데이터는 웨어하우스 계층을 우회하지 않는다: 정보 마트의 날짜 차원 뷰는 **Raw
  Data Vault의 참조 테이블에 직접 기반하고, 그 참조 테이블 자체도 가상 뷰다** — 분석 마스터
  데이터가 웨어하우스의 완전한 통제 아래 있고 참조 데이터를 가상으로 제공하기 위한 다른
  요건도 충족되기 때문이다 (§15.2.1, pp.700–701).[^linstedt2016] 참조 데이터가 허브가 아닌
  자리에 놓이는 규칙은 [참조 테이블](../concepts/reference-table.md) 참조.
- 이 차원의 키만 다르다 — 다른 대부분의 차원이 해시 값을 키로 쓰는 것과 달리 **날짜 차원의
  키는 코드 속성**이다 (§15.2.1, p.703).[^linstedt2016] Kimball 쪽에서도 날짜 차원은 대리
  키 규칙의 유일한 예외였다 — [차원 테이블](../concepts/dimension-table.md) 참조.
- 대가가 명시된다: 마스터 데이터에서 날짜 차원을 소싱하면 업무 사용자가 서술 데이터를 더
  많이 통제하지만 **분석 마스터 데이터가 든 상대적으로 큰 테이블을 만들어야 한다.** 그리고
  이 테이블은 **서술적 날짜 정보를 유지할 줄 아는 파워 유저를 위한 것이지 일반 사용자가
  관리할 것이 아니다** (§15.2.1, p.706).[^linstedt2016]

## 데이터 엔지니어링 쪽에서 본 같은 실무

Reis & Housley는 MDM을 데이터 엔지니어링 수명 주기의 **데이터 관리 저류** 아래, 거버넌스의
발견 가능성 항목에 놓는다. 정의는 위 §9.1.3의 골든 레코드 정의와 같은 것을 가리킨다.

- 무엇이 마스터 데이터인가 — **마스터 데이터는 직원·고객·제품·위치 같은 업무 엔터티에 관한
  데이터다. 조직이 유기적 성장과 인수를 통해 더 크고 복잡해지고 다른 기업과 협업하면서,
  엔터티와 아이덴티티의 일관된 그림을 유지하기가 점점 더 어려워진다** (2장,
  p.56).[^reis2022]
- 정의 — **마스터 데이터 관리(MDM)는 골든 레코드(golden records)라 알려진 일관된 엔터티 정의를
  세우는 실무다. 골든 레코드는 조직 전체에서, 그리고 파트너와 함께 엔터티 데이터를
  조화시킨다** (2장, p.56).[^reis2022]
- 성격 — **MDM은 기술 도구를 만들고 배포함으로써 촉진되는 업무 운영 프로세스다. 예컨대 MDM
  팀이 주소의 표준 형식을 정하고, 데이터 엔지니어와 함께 일관된 주소를 반환하는 API와 주소
  데이터로 회사 부문 사이의 고객 레코드를 매칭하는 시스템을 지을 수 있다** (2장,
  p.56).[^reis2022] 위 §9.1.3이 MDM을 "마스터 데이터와 데이터 관리의 결합"이라 한 것과 같은
  자리를 가리킨다.
- 소유의 문제 — **MDM은 전체 데이터 주기를 가로질러 운영 데이터베이스까지 닿는다. 데이터
  엔지니어링의 관할에 직접 들어올 수도 있지만, 조직 전반에서 일하는 전담 팀의 책임으로
  배정되는 일이 흔하다. MDM을 소유하지 않더라도 데이터 엔지니어는 MDM 이니셔티브에 협업할 수
  있으므로 늘 그것을 인지해야 한다** (2장, p.56).[^reis2022]

## 데이터 메시가 MDM을 반례로 드는 자리

데이터 메시는 MDM을 **실패한 선례**로 명시적으로 지목한다. 이 페이지의 위 서술과 정면으로
어긋나는 자리이므로 무엇이 어긋나는지 갈라 둔다.

- 정의 자체에는 이견이 없다. 저자는 DAMA-DMBOK의 MDM 정의를 각주에 그대로 옮겨 놓는다 —
  **여러 시스템에 걸쳐 일관된 사용을 가능하게 하는 마스터 데이터 값과 식별자에 대한 통제.
  MDM의 목표에는 모호한 식별자와 결부된 위험을 줄이면서 정확하고 현재적인 값의 가용성을
  보장하는 것이 포함된다** (2장, p.23, 각주 5).[^dehghani2022]
- 갈리는 것은 **구현 형태**다 — **과거에 마스터 데이터 관리(Master Data Management, MDM)
  구현은 공유 데이터 자산의 모든 면을 한자리에 한 모델로 집계하려 시도했다. 이는 확장되지 않는
  단일 모놀리식 스키마 모델링으로 되돌아가는 것이다** (2장, p.23).[^dehghani2022]
  - 그 맥락은 야심 찬 집계에 대한 경고다 — **한 개념의 모든 면을 포착하려 드는 야심 찬 집계
    도메인 데이터(예: listener 360)를 만들어 조직 전체의 데이터 사용자를 서빙하려는 것을
    강력히 경계하라고 권한다. 그런 집계는 너무 복잡하고 다루기 어려워지며, 어느 특정 용법에서도
    이해하고 쓰기 어렵고, 최신으로 유지하기 어렵다** (2장, p.23).[^dehghani2022]
- 대안 처방 — **데이터 메시는 최종 소비자가 자기 목적에 맞는 데이터 집계를 스스로 조합하고,
  재사용성 높고 야심 찬 집계의 유혹에 저항할 것을 제안한다** (2장, p.23).[^dehghani2022]
- 같은 개체의 여러 모델을 허용하되 잇는 장치는 따로 둔다 — **다의어(polysemes)는 여러 도메인에
  걸쳐 공유되는 개념이다. 데이터 메시는 한 도메인의 다의어를 다른 도메인으로 매핑하는 것을
  전역 식별 체계(global identification scheme)로 허용한다** (2장, p.25).[^dehghani2022]
  MDM의 골든 레코드가 **하나의 값으로 수렴시키는** 반면, 다의어는 **여러 값을 남기고 매핑만
  보장한다.**

**두 처방은 어떤 문제에 답하는가.** MDM은 같은 개체가 시스템마다 다른 값으로 존재해 트랜잭션이
어긋나는 문제에 답하고 — 그래서 원천으로 되먹이는 조화(harmonization)를 목표로 삼는다. 데이터
메시는 그 하나의 모델을 유지하는 비용이 도메인 수에 따라 폭발하는 문제에 답한다. 되먹임 루프가
성립하는 조직(운영 시스템 통제권이 있고 규제 요구가 값의 통일을 요구하는 곳)에서는 MDM의
전제가 유지되고, 도메인 자율이 우선인 조직에서는 데이터 메시의 전제가 유지된다. 후자의 정본은
[데이터 메시 원칙](../synthesis/data-mesh-principles.md) 허브가 받는다.
