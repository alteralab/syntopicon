# 런타임 데이터 영역과 메모리 오버플로

**목차**: [영역을 나누는 두 축](#영역을-나누는-두-축) · [프로그램 카운터](#프로그램-카운터) · [자바 가상 머신 스택](#자바-가상-머신-스택) · [네이티브 메서드 스택](#네이티브-메서드-스택) · [자바 힙](#자바-힙) · [메서드 영역과 런타임 상수 풀](#메서드-영역과-런타임-상수-풀) · [다이렉트 메모리](#다이렉트-메모리) · [어느 영역이 어떻게 넘치는가](#어느-영역이-어떻게-넘치는가) · [이어지는 페이지](#이어지는-페이지)

이 페이지의 질문: **자바 가상 머신은 실행 중 메모리를 어떤 영역으로 나누고, 각 영역은
무엇을 담다가 어떻게 고갈되는가.**

## 영역을 나누는 두 축

- 자바 가상 머신은 자바 프로그램을 실행하는 동안 필요한 메모리를 몇 개의 **데이터
  영역(runtime data area, 런타임 데이터 영역)** 으로 나눠 관리하며, 영역마다 목적과
  생성·삭제 시점이 다르다 (2장, p.59).[^zhou2024]
  - 어떤 영역은 **가상 머신 프로세스의 시작과 동시에** 만들어지고, 어떤 영역은
    **사용자 스레드의 시작과 종료에 맞춰** 생성·삭제된다.
- 그래서 영역을 가르는 축은 둘이다 — **모든 스레드가 공유하는 영역**(자바 힙, 메서드
  영역)과 **스레드별 영역**(프로그램 카운터, 가상 머신 스택, 네이티브 메서드 스택)이다
  (2장, p.60, 그림 2-1).[^zhou2024]

## 프로그램 카운터

- 프로그램 카운터(program counter) 레지스터는 작은 메모리 영역으로, **현재 실행 중인
  스레드의 '바이트코드 줄 번호 표시기'** 라고 생각하면 쉽다. 개념 모형에서 바이트코드
  인터프리터는 이 카운터의 값을 바꿔 다음에 실행할 명령어를 고른다 — 제어 흐름, 분기,
  순환, 점프, 예외 처리, 스레드 복원이 모두 이 표시기를 쓴다 (2장, p.60).[^zhou2024]
- 멀티스레딩은 CPU 코어를 여러 스레드가 교대로 쓰는 방식으로 구현되므로, **스레드
  전환 후 멈춘 지점을 정확히 복원하려면 스레드마다 고유한 프로그램 카운터가 필요하다.**
  그래서 이 영역은 **스레드 프라이빗(thread-private)** 메모리다 (2장, p.60).[^zhou2024]
- 값의 규칙 (2장, p.61):[^zhou2024]
  - 자바 메서드를 실행 중일 때는 **실행 중인 바이트코드 명령어의 주소**가 기록된다.
  - 네이티브 메서드를 실행 중일 때는 값이 `Undefined`('정의되지 않음')다.
- 이 영역은 《자바 가상 머신 명세》에서 **`OutOfMemoryError` 조건이 명시되지 않은 유일한
  영역**이기도 하다 (2장, p.61).[^zhou2024]

## 자바 가상 머신 스택

- 가상 머신 스택도 스레드 프라이빗이며 **연결된 스레드와 운명을 같이한다**(생성·삭제
  시기가 일치한다). 자바 메서드를 실행하는 스레드의 메모리 모델을 설명해 준다 (2장,
  p.61).[^zhou2024]
- 메서드가 호출될 때마다 가상 머신은 **스택 프레임(stack frame)** 을 만들어 **지역 변수
  테이블(local variable table), 피연산자 스택(operand stack), 동적 링크(dynamic linking),
  메서드 반환값** 등을 저장한 뒤, 프레임을 스택에 푸시(push)하고 메서드가 끝나면
  팝(pop)한다 (2장, p.61).[^zhou2024]
- "자바 메모리는 힙과 스택으로 나뉜다"는 흔한 구분법은 **전통적인 C·C++ 프로그램의 메모리
  구조에서 기인한 것으로 자바를 설명하기에는 무리가 있다.** 그럼에도 널리 쓰이는 이유는
  이 둘이 객체 메모리 할당과 가장 밀접하기 때문이고, 이때 '스택'은 보통 가상 머신 스택,
  그중에서도 지역 변수 테이블을 가리킨다 (2장, p.61).[^zhou2024]
- 지역 변수 테이블은 컴파일타임에 알 수 있는 **기본 데이터 타입, 객체 참조(reference),
  반환 주소 타입**을 저장하며, 저장 공간의 단위를 **지역 변수 슬롯(slot)** 이라 한다
  (2장, pp.61–62):[^zhou2024]
  - 일반적으로 슬롯 하나의 크기는 32비트이므로 `double`처럼 64비트인 데이터는 슬롯 두
    개를 차지하고 나머지 타입은 하나에 저장된다.
  - **필요한 슬롯 개수는 컴파일 과정에서 할당되며 메서드 실행 중에는 절대 변하지 않는다.**
    여기서 말하는 '크기'는 슬롯 개수이지 실제 바이트 수가 아니다 — 슬롯 하나를 몇 비트로
    구현하는지는 가상 머신 구현에 달렸다.
- 명세는 이 영역에서 두 가지 오류를 정의한다 (2장, p.62):[^zhou2024]
  - 스레드가 요청한 스택 깊이가 가상 머신이 허용하는 깊이보다 크면 `StackOverflowError`.
  - 스택 용량을 동적으로 확장할 수 있는 가상 머신에서 확장 시점에 여유 메모리가 부족하면
    `OutOfMemoryError`. 다만 **핫스팟은 스택 용량을 동적으로 늘리지 못하므로 두 번째
    이유로 이 예외를 던질 일은 없다.**

## 네이티브 메서드 스택

- 네이티브 메서드 스택(native method stack)은 가상 머신 스택과 매우 비슷한 역할을 하되,
  가상 머신 스택이 **자바 메서드(바이트코드)** 실행에 쓰이는 반면 이쪽은 **네이티브
  메서드** 실행에 쓰인다 (2장, p.62).[^zhou2024]
- 명세가 이 스택의 구조·표현을 아무것도 규정하지 않았기 때문에 구현자가 자유롭게 정할 수
  있고, **핫스팟은 네이티브 메서드 스택과 가상 머신 스택을 하나로 합쳐 놓았다.** 오류
  조건은 가상 머신 스택과 같다 (2장, p.62).[^zhou2024]

## 자바 힙

- 자바 힙(Java heap)은 자바 애플리케이션이 쓸 수 있는 **가장 큰 메모리**이며, 모든
  스레드가 공유하고 가상 머신이 구동될 때 만들어진다. 유일한 목적은 **객체 인스턴스를
  저장하는 것**이다 (2장, p.62).[^zhou2024]
- 《자바 가상 머신 명세》의 규정은 이렇다 (2장, p.62, 각주 7):[^zhou2024]

  > The heap is the run-time data area from which memory for all class instances and
  > arrays is allocated.

- 그럼에도 '거의 모든'이라는 유보가 붙는다 — **JIT 컴파일 기술, 특히 탈출 분석(escape
  analysis)이 발전하면서 스택 할당과 스칼라 치환 최적화가 달라져** 모든 객체가 힙에
  할당된다는 설명이 절대적 진리는 아니게 됐다 (2장, p.63).[^zhou2024]
- 자바 힙은 가비지 컬렉터가 관리하는 영역이라 **GC 힙**이라고도 부른다. 현대적 컬렉터
  대다수가 **세대별 컬렉션 이론(generational collection theory)** 을 기초로 설계된 탓에
  힙을 설명할 때 다음 용어가 자주 등장한다 (2장, p.63):[^zhou2024]
  - **신세대(new generation), 구세대(old generation), 영구 세대(permanent generation),
    에덴 공간(eden space), 생존자 공간에서부터(from survivor space), 생존자 공간으로(to
    survivor space)**.
  - 다만 **이 영역 구분은 가비지 컬렉터들의 일반적 특성 또는 설계 방식일 뿐, 반드시 이
    형태로 메모리를 구성해야 한다는 뜻은 아니다.** 명세의 자바 힙 절에는 세부 영역 구분에
    관한 이야기 자체가 없다.
  - 그래서 "힙은 신세대·구세대·영구 세대·에덴·생존자 공간으로 나뉜다"는 설명은 G1이
    등장한 **2010년 무렵까지는 크게 틀리지 않았지만**, 지금은 핫스팟에도 세대 단위 설계를
    따르지 않는 컬렉터가 포함돼 있어 따져 볼 게 많다.
- 할당 효율을 높이려고 힙을 **스레드 로컬 할당 버퍼(TLAB, thread-local allocation
  buffer)** 여러 개로 나누기도 하지만, 어떻게 나누든 **저장되는 것은 객체 인스턴스뿐**이며
  세부 구분의 목적은 오직 **회수와 할당을 더 빠르게 하기 위해서다** (2장, p.63).[^zhou2024]
- 자바 힙은 **물리적으로 떨어진 메모리에 위치해도 되지만 논리적으로는 연속돼야 한다.**
  다만 대다수 가상 머신은 큰 객체(주로 배열)를 물리적으로도 연속된 공간에 두도록 구현한다
  (2장, p.64).[^zhou2024]
- 크기는 고정할 수도 확장 가능하게 할 수도 있으며, 요즘 주류 가상 머신은 모두 확장
  가능한 형태다(`-Xmx`·`-Xms`). 새 인스턴스에 줄 공간이 없고 더 확장할 수도 없으면
  `OutOfMemoryError`를 던진다 (2장, p.64).[^zhou2024]

## 메서드 영역과 런타임 상수 풀

- 메서드 영역(method area)도 모든 스레드가 공유하며 **가상 머신이 읽어 들인 타입 정보,
  상수, 정적 변수, JIT 컴파일러가 컴파일한 코드 캐시** 등을 저장한다. 명세는 논리적으로
  힙의 한 부분으로 기술하지만, 자바 힙과 구분하기 위해 **'논힙(non-heap)'** 이라 부르기도
  한다 (2장, p.64).[^zhou2024]
- 메서드 영역과 영구 세대는 **같지 않다.** JDK 7까지 많은 개발자가 둘을 혼동했는데, 그건
  당시 핫스팟 팀이 **가비지 컬렉터의 수집 범위를 메서드 영역까지 확장하기로 하고 메서드
  영역을 영구 세대에 구현했기 때문**이다. 덕분에 메서드 영역 관리 코드를 따로 쓰지 않아도
  됐다 (2장, p.64).[^zhou2024]
  - BEA JRockit이나 IBM J9 등 다른 가상 머신에는 애초부터 영구 세대라는 개념이 없었다.
    명세가 구현 방식을 강제하지 않았으므로 원칙적으로 구현자가 정할 사안이었다.
- 되돌아보면 그 결정은 좋은 생각이 아니었다 — **영구 세대의 최대 크기가
  `-XX:MaxPermSize`로 제한되고 설정하지 않아도 기본값이 정해져 있어서, 자바
  애플리케이션이 메모리 오버플로를 겪을 가능성이 커졌기 때문**이다 (2장,
  p.65).[^zhou2024]
- 그래서 이전(移轉)이 단계적으로 일어났다 (2장, p.65):[^zhou2024]
  - **JDK 7**: 영구 세대에서 관리하던 **문자열 상수와 정적 변수**를 자바 힙으로 옮겼다.
  - **JDK 8**: 영구 세대라는 개념을 완전히 지우고, JRockit·J9처럼 **네이티브 메모리에
    메타스페이스(metaspace)** 를 구현해 남아 있던 타입 정보를 옮겼다(JEP 122).
- 명세는 메서드 영역에 제약을 거의 두지 않는다 — 연속될 필요가 없고, 크기를 고정해도
  되고, **심지어 가비지 컬렉션을 하지 않아도 괜찮다.** 회수 대상이 대부분 상수 풀과
  타입이라 **회수 효과가 상대적으로 매우 작기 때문**이지만, 회수하지 않아 메모리가
  누수되는 심각한 버그가 실제로 있었다 (2장, p.65).[^zhou2024]
- 런타임 상수 풀(runtime constant pool)은 메서드 영역의 일부다. 클래스 파일의 상수 풀
  테이블에는 클래스 버전·필드·메서드·인터페이스 등의 설명 정보와 컴파일타임에 생성된
  리터럴·**심벌 참조(symbolic reference)** 가 저장되며, 클래스를 로드할 때 이 정보가 런타임
  상수 풀로 들어간다 (2장, p.66).[^zhou2024]
  - 클래스 파일의 상수 풀과 다른 중요한 특징이 하나 있다 — **동적이라는 점**이다. 자바는
    상수가 컴파일타임에 생성되어야 한다는 규칙이 없어서 **런타임에도 새 상수가 추가될 수
    있다.** `String::intern()`이 그 특성을 쓴다.
  - 런타임 상수 풀은 메서드 영역에 속하므로 **메서드 영역을 넘어서까지 확장될 수 없다.**

## 다이렉트 메모리

- 다이렉트 메모리(direct memory)는 **가상 머신 런타임에 속하지 않으며 명세에 정의된 영역도
  아니다.** 그럼에도 자주 쓰이고 `OutOfMemoryError`의 원인이 될 수 있다 (2장,
  p.66).[^zhou2024]
- JDK 1.4에 NIO가 도입되면서 채널과 버퍼 기반 I/O가 들어왔다. NIO는 **힙이 아닌 메모리를
  직접 할당하는 네이티브 함수 라이브러리를 이용하고, `DirectByteBuffer` 객체를 통해
  그 메모리를 다룬다** — 자바 힙과 네이티브 힙 사이에서 데이터를 복사하지 않아도 되므로
  일부 시나리오에서 성능이 크게 개선된다 (2장, p.67).[^zhou2024]
- 함정은 여기 있다 — **자바 힙 크기의 제약과는 무관하지만 이 역시 메모리다.** 서버
  관리자들이 `-Xmx` 등을 설정할 때 다이렉트 메모리를 간과하는 경우가 잦고, **사용되는 모든
  메모리 영역의 합이 물리 메모리 한계를 넘어서면 동적 확장 시점에 `OutOfMemoryError`가
  발생한다** (2장, p.67).[^zhou2024]

## 어느 영역이 어떻게 넘치는가

- 예외 메시지는 어느 영역이 넘쳤는지 알려 주는 1차 단서다. 이 절의 예제는 모두 **OpenJDK
  17의 핫스팟**에서 확인한 것이며, **메모리 오버플로는 언제 어떻게 발생하는지가 자바 언어
  차원에서 합의된 동작이 아니므로 버전·업체가 다르면 결과가 달라질 수 있다** (2장,
  p.77).[^zhou2024]
- **자바 힙**: 실제로 `OutOfMemoryError`가 가장 많이 발생하는 영역이며, 메시지 옆에
  `Java heap space`가 붙는다 (2장, p.78).[^zhou2024]
  - 해결 절차는 힙 덤프 스냅숏(`-XX:+HeapDumpOnOutOfMemoryError`)을 분석 도구로 열어
    **먼저 '오버플로를 일으킨 객체가 꼭 필요한 객체인가', 즉 메모리 누수인지
    오버플로인지 확인하는 것**이다 (2장, pp.78–79).
  - 누수라면 누수된 객체로부터 **GC 루트까지의 참조 체인(reference chain, 이 책 2장은
    '참조 사슬'로 옮겼다)** 을 살펴 어느
    루트에 붙어 있어 회수되지 못했는지 찾는다. 대개 이것으로 코드의 정확한 위치를 찾는다.
  - 누수가 아니라면 힙 매개 변수(`-Xmx`·`-Xms`)와 실제 가용 메모리를 비교하고, 수명이 너무
    긴 객체나 공간 낭비가 심한 자료 구조가 없는지 살펴 런타임 소비를 낮춘다.
- **가상 머신 스택과 네이티브 메서드 스택**: 핫스팟은 둘을 구분하지 않으므로 `-Xoss`는
  효과가 없고 **스택 크기는 오직 `-Xss`로만 바꾼다** (2장, p.80).[^zhou2024]
  - 단일 스레드에서는 스택 용량을 줄이든 지역 변수를 잔뜩 늘리든 결과가 모두
    `StackOverflowError`다. **핫스팟은 스택 확장을 지원하지 않으므로 스레드 실행 중에
    스택이 넘치는 일은 없다** (2장, p.80).
  - 최소 스택 크기에는 운영 체제·버전별 하한이 있다 — 64비트 윈도우·JDK 17에서는 180K
    미만으로 줄일 수 없고, **리눅스에서는 228K가 한계**여서 그보다 낮게 잡으면
    `The Java thread stack size specified is too small. Specify at least 228k`가 출력된다
    (2장, pp.81–82).
  - 반대로 **스레드를 계속 만들어 내면 오버플로가 나는데, 이때는 스택 공간이 충분한지와
    무관하고 오히려 스레드별 스택을 크게 잡을수록 쉽게 터진다** — 운영 체제가 프로세스에
    주는 메모리에서 힙·메서드 영역을 뺀 나머지를 스택들이 나눠 쓰기 때문이다. 메시지는
    `unable to create native thread`이고, **해법이 '메모리 용량을 줄이는 것'이라는 점이
    직관에 어긋난다** (2장, pp.84–85).
- **메서드 영역과 런타임 상수 풀**: JDK 6에서는 상수 풀이 영구 세대에 있었으므로 메시지가
  `PermGen space`로 나왔고, 이것이 상수 풀이 메서드 영역의 일부라는 증거였다. **JDK 7부터
  문자열 상수 풀이 자바 힙으로 옮겨져 같은 코드가 더는 멈추지 않는다** (2장,
  pp.86–87).[^zhou2024]
  - `String::intern()`의 반환값도 이때 달라졌다 — 같은 코드가 **JDK 6에서는 `false`,
    JDK 7에서는 `true`** 를 출력한다. JDK 6은 처음 만난 문자열을 영구 세대로 복사하고 그
    참조를 반환했지만, JDK 7 이후는 풀이 힙에 있으므로 **풀에 있는 첫 인스턴스의 참조로
    바꾸면 되기 때문**이다 (2장, p.88).
  - 메서드 영역 자체를 넘치게 하려면 클래스를 계속 만들어야 한다. **CGLib 같은 바이트코드
    조작, 동적 프락시, JSP를 동적 생성하는 웹 애플리케이션, 클래스 로더를 자주 자화하는
    OSGi 환경**이 실제 목격 사례다 (2장, pp.88–90).
  - JDK 8부터는 영구 세대가 사라지고 메타스페이스가 그 자리를 대신하므로 **기본 설정에서는
    이런 시나리오로 오버플로를 일으키기 어렵다.** 대신 보호용 매개 변수가 있다 —
    `-XX:MaxMetaspaceSize`(기본값 -1 = 제한 없음), `-XX:MetaspaceSize`(초기 크기이자 클래스
    언로딩을 시도하는 문턱), `-XX:MinMetaspaceFreeRatio`·`-XX:MaxMetaspaceFreeRatio`
    (2장, p.90).
- **다이렉트 메모리**: 용량은 `-XX:MaxDirectMemorySize`로 설정하며, 지정하지 않으면
  `-Xmx`와 같다 (2장, p.91).[^zhou2024]
  - 두드러진 특징은 **힙 덤프 파일에서는 이상한 점을 찾을 수 없다는 것**이다. 오버플로로
    생성된 덤프 파일이 매우 작고 프로그램이 직간접적으로(보통 NIO를 통해) 다이렉트
    메모리를 썼다면, 원인을 여기서 찾아야 한다 (2장, p.92).
