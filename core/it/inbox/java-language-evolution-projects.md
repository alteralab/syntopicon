이 페이지의 질문: **자바 언어 자체는 지금 어떤 프로젝트를 통해 어디로 가고 있는가.**

## 문법 개선을 마지막에 두는 이유

- 저자는 언어 기능과 문법을 **상대적으로 가장 덜 중요한 개선**으로 본다. 근거로 든 반례가
  둘이다 — **인간 친화적이지 못한 문법을 갖춘 자바스크립트는 결국 엄청난 성공을 거두었고,
  자바보다 문법이 훨씬 우아한 C#은 아직도 자바를 따라오지 못하고 있다** (1장,
  p.41).[^zhou2024]
- 그렇다고 값이 없다는 뜻은 아니다 — **언어가 제공하는 기능과 문법은 생산성과 개발 효율에 많은
  영향을 주는 중요한 요인임은 틀림없다. 여러 가지 언어 기능과 편의 문법이 없더라도 여전히
  프로그램을 작성할 수는 있지만, 필수가 아닌 편의 문법조차도 언어를 날마다 사용하는 개발자에게
  행복한 선물일 수 있다** (1장, p.41).[^zhou2024]

## 앰버: 구문 개선

- **JDK 7의 코인 프로젝트가 완료된 후 자바 커뮤니티는 또 다른 언어 기능 개선 프로젝트인 앰버를
  발족했고, 현재는 앰버 프로젝트에서 새로운 구문 개선 아이디어를 지속적으로 실험하고 표준화하는
  중이다** (1장, p.41).[^zhou2024]
- **JDK 10 이후로 정식 표준이 된 구문 개선**은 이렇다 (1장, pp.41–42):[^zhou2024]

  | JEP | 무엇 | 도입 |
  |---|---|---|
  | 286 | Local-Variable Type Inference — 지역 변수 타입 추론(`var`) | JDK 10 |
  | 323 | Local-Variable Syntax for Lambda Parameters — 람다식 매개 변수로 사용할 수 있도록 지역 변수 구문 개선 | JDK 11 |
  | 361 | Switch Expressions — `switch` 문을 표현식으로 사용할 수 있는 문법 추가 | JDK 14 |
  | 378 | Text Blocks — `+` 없이 문자열 여러 줄을 쉽게 표현할 수 있는 문법 추가 | JDK 15 |
  | 394 | Pattern Matching for instanceof — 패턴 매칭 능력을 부여해 `instanceof` 연산자의 표현력 강화 | JDK 16 |
  | 395 | Records — 데이터 전달용 불변 클래스인 레코드 타입 추가 | JDK 16 |
  | 409 | Sealed Classes — 자신을 확장하거나 구현할 수 있는 클래스와 인터페이스를 제한하는 봉인된 클래스와 봉인 인터페이스 타입 추가 | JDK 17 |
  | 440 | Record Patterns — 레코드 클래스로부터 데이터를 가져올 때 패턴 매칭 제공 | JDK 21 |
  | 441 | Pattern Matching for switch — `switch` 문·표현식의 패턴 매칭 능력 개선 | JDK 21 |

- **여전히 진행 중인 개선안도 많다. 진행 중인 안들은 미리 보기 형태로 JDK에 포함되어
  배포되므로 원하면 사용해 볼 수 있다** (1장, p.42):[^zhou2024]
  - **JEP 430 String Templates** — **리터럴 텍스트를 임베디드 표현식 및 템플릿 프로세서와
    결합하여 특수한 결과를 생성할 수 있게 해서 자바의 기존 문자열 리터럴과 텍스트 블록을
    보완**, JDK 21에 포함.
  - **JEP 443 Unnamed Patterns and Variables** — **언더스코어(`_`)를 이용하여 무명 패턴과 무명
    변수 작성 지원**, JDK 21에 포함.
  - **JEP 445 Unnamed Classes and Instance main methods** — **클래스·패키지·모듈 정의를 생략할
    수 있는 무명 클래스와 단순화한 `main()` 메서드 도입**, JDK 21에 포함.
  - **JEP 447 Statements before super()** — **인스턴스를 참조하지 않는 문장은 `this()`나
    `super()` 호출 전에 작성 가능.**
  - 버전 조건: JDK 21 기준의 미리 보기 상태다 — 이후 판올림에서 정식 표준이 되었는지는 이
    소스가 말하지 않는다.

## 발할라와 파나마

- **발할라 프로젝트**는 **값 타입과 원시 타입을 일반화한 제네릭 타입을 제공하고 불변 타입과
  비참조 타입을 명시적으로 선언할 수 있게 한다** (1장, p.43).[^zhou2024]
  - 얻는 것 둘 — **불변 타입은 동시성 프로그래밍에 수많은 이점을 선사한다. 대표적으로 데이터
    경합이 사라져서 성능이 높아진다.** 그리고 **제네릭 타입들이 원시 타입을 지원한다는 말은 더
    이상 오토박싱/언박싱이 필요하지 않다는 뜻**이다 (1장, p.43).
  - 지금 자바의 한계도 적혀 있다 — **스칼라와 같은 일부 언어는 명시적 불변 타입을 선언할 수
    있는 반면, 자바에서는 모든 필드를 `final`로 선언하는 식으로 간접적으로만 구현할 수 있다**
    (1장, p.43).
- **파나마 프로젝트는 자바 가상 머신과 네이티브 코드의 경계를 허문다.** 문제는 JNI다 — **자바
  코드는 JNI를 이용해 네이티브 코드를 호출할 수 있으며 안드로이드처럼 하드웨어와 자주 상호
  작용하는 분야에서는 매우 흔하게 이용되지만, JNI 방식은 이용하기가 상당히 번거롭고 빈번하게
  호출하면 성능 부하도 크다** (1장, p.43).[^zhou2024]
- 파나마의 하위 프로젝트는 셋이다 (1장, p.43):[^zhou2024]
  - **외부 함수 및 메모리 API** — **힙 바깥의 메모리를 사용하기 위한 API**이며 **JNI의 지루한
    접합 코드(glue code)와 투박함 없이 메서드 핸들을 이용해 네이티브 코드와 자바 코드를
    연결한다.** **`java.base` 모듈의 `java.lang.foreign` 패키지로 통합할 예정**이다.
  - **벡터 API** — **하드웨어로 가속되는 벡터 계산 기능을 제공한다. 값 객체를 써야 해서 발할라
    프로젝트와 연관되어 있다.**
  - **Jextract** — **네이티브 라이브러리 헤더와 자바를 바인딩해 주는 도구**다.
- 저자의 마무리 — **자바는 6개월마다 새로운 버전의 JDK를 배포하면서 다른 언어의 멋진 기능들을
  계속해서 흡수할 것**이며, **배움의 끈을 놓지 않고 있기 때문에 앞으로도 오랫동안 지금과 같은
  생명력을 유지하리라 생각한다** (1장, p.43).[^zhou2024] #speculation
