하나의 질문: **데이터를 어디에 두는가라는 선택이 왜 수명 주기의 나머지 전부를 좌우하는가.**

## 단계이면서 토대다

- 왜 복잡한가 — **저장 해법을 고르는 것은 데이터 수명 주기의 나머지에서 성공하는 열쇠이며,
  여러 이유로 수명 주기에서 가장 복잡한 단계 중 하나이기도 하다** (2장, p.38).[^reis2022]
  저자들이 드는 이유 셋:
  - **첫째, 클라우드의 데이터 아키텍처는 흔히 여러 저장 해법을 활용한다.**
  - **둘째, 순수하게 저장으로만 기능하는 데이터 저장 해법은 드물고, 많은 것이 복잡한 변환
    질의를 지원한다. 객체 저장 해법조차 강력한 질의 능력을 지원할 수 있다 — 예컨대 Amazon
    S3 Select.**
  - **셋째, 저장은 데이터 엔지니어링 수명 주기의 한 단계이지만 반입·변환·서빙 같은 다른
    단계와 자주 맞닿는다.**
- 그래서 도식에서의 자리가 다르다 — **실제로 저장은 데이터가 처음부터 끝까지 흐르는 내내
  수명 주기 전체에 걸쳐 일어난다. 그래서 도식은 저장 "단계"를 다른 단계들을 떠받치는
  토대로 그린다** (2장, p.34).[^reis2022]
- 6장이 같은 말을 다시 하는 방식 — **저장은 데이터 엔지니어링 수명 주기의 초석이며 그 주요
  단계들 — 반입·변환·서빙 — 을 떠받친다. 데이터는 수명 주기를 지나며 여러 번 저장된다. 오래된
  말을 바꿔 말하면 아래까지 죽 저장이다. 데이터가 몇 초 뒤에 필요하든, 몇 분, 며칠, 몇 년 뒤에
  필요하든, 시스템이 추가 처리와 전송을 위해 소비할 준비가 될 때까지 그것은 저장에 영속해야
  한다** (6장, p.189).[^reis2022]
- 그래서 첫 행동이 정해진다 — **데이터의 유스케이스와 미래에 그것을 회수할 방식을 아는 것이
  데이터 아키텍처에 알맞은 저장 해법을 고르는 첫걸음이다** (6장, p.189).[^reis2022]
- 저장 시스템이 다른 단계를 겸하는 실물 — **클라우드 데이터 웨어하우스는 데이터를 저장하고,
  파이프라인에서 처리하고, 분석가에게 서빙할 수 있다. 아파치 카프카와 펄사 같은 스트리밍
  프레임워크는 메시지에 대해 반입·저장·질의 시스템으로 동시에 기능할 수 있고, 객체 저장은
  데이터 전송의 표준 계층이다** (2장, p.38).[^reis2022]
- 층위가 셋이라는 것은 [데이터 저장의 원료](../concepts/storage-raw-ingredients.md)에 있다 —
  원료(HDD·SSD·RAM·네트워킹·직렬화·압축·CPU), 저장 시스템(HDFS·오브젝트 저장·RDBMS·캐시·스트리밍
  저장), 저장 추상(데이터 레이크·레이크하우스·데이터 플랫폼·클라우드 DW) (6장, p.190).[^reis2022]

## 저장 시스템 평가 질문

- 데이터 웨어하우스·데이터 레이크하우스·데이터베이스·객체 저장 중 무엇을 고를 때든 던지는
  질문들 (2장, pp.38–39):[^reis2022]
  - **이 저장 해법은 아키텍처가 요구하는 쓰기·읽기 속도와 양립하는가?**
  - **저장이 하류 프로세스의 병목을 만들겠는가?**
  - **이 저장 기술이 어떻게 작동하는지 이해하고 있는가? 저장 시스템을 최적으로 쓰고 있는가,
    아니면 부자연스러운 짓을 저지르고 있는가? 예컨대 객체 저장 시스템에 높은 비율의 랜덤
    접근 갱신을 가하고 있는가?(이것은 상당한 성능 오버헤드를 낳는 안티패턴이다.)**
  - **이 저장 시스템이 예상되는 미래의 규모를 감당하겠는가? 총 가용 저장, 읽기 연산 속도,
    쓰기 볼륨 등 저장 시스템의 모든 용량 한계를 고려해야 한다.**
  - **하류 사용자와 프로세스가 요구되는 서비스 수준 협약(service-level agreement, SLA) 안에
    데이터를 가져갈 수 있겠는가?**
  - **스키마 진화·데이터 흐름·데이터 계보(data lineage) 등에 관한 메타데이터를 포착하고
    있는가? 메타데이터는 데이터의 유용성에 상당한 영향을 준다. 메타데이터는 미래에 대한
    투자이며, 발견 가능성과 조직 지식을 극적으로 높여 앞으로의 프로젝트와 아키텍처 변경을
    매끄럽게 한다.**
  - **이것은 순수 저장 해법(객체 저장)인가, 아니면 복잡한 질의 패턴을 지원하는가(클라우드
    데이터 웨어하우스)?**
  - **저장 시스템이 스키마에 무관한가(객체 저장)? 유연한 스키마인가(카산드라)? 스키마를
    강제하는가(클라우드 데이터 웨어하우스)?**
  - **데이터 거버넌스를 위해 마스터 데이터·골든 레코드 데이터 품질·데이터 계보를 어떻게
    추적하고 있는가?**
  - **규제 준수와 데이터 주권(data sovereignty)을 어떻게 다루고 있는가? 예컨대 데이터를 어떤
    지리적 위치에는 저장할 수 있고 다른 곳에는 저장할 수 없는가?**

## 저장 추상을 고르는 네 고려사항

- 저장 추상이란 — **데이터 엔지니어링 저장 추상(data engineering storage abstractions)은
  데이터 엔지니어링 수명 주기의 심장에 자리하며 데이터 저장 시스템 위에 지어진 데이터 조직·질의
  패턴이다** (6장, p.215).[^reis2022]
- 다루는 것과 다루지 않는 것 — **우리가 관심을 둘 주요 추상 유형은 데이터 과학·분석·리포팅
  유스케이스를 지원하는 것들이다. 여기에는 데이터 웨어하우스·데이터 레이크·데이터 레이크하우스·
  데이터 플랫폼·데이터 카탈로그가 든다. 원천 시스템은 5장에서 논했으므로 다루지 않는다** (6장,
  p.215).[^reis2022]
- 고르는 축은 넷이다 (6장, p.215):[^reis2022]
  - **목적과 유스케이스(purpose and use case)** — **먼저 데이터를 저장하는 목적을 식별해야
    한다. 그것은 무엇에 쓰이는가?**
  - **갱신 패턴(update patterns)** — **이 추상은 벌크 갱신·스트리밍 삽입·업서트 중 무엇에
    최적화돼 있는가?**
  - **비용(cost)** — **직접·간접 금융 비용은 무엇인가? 가치 실현 시간은? 기회비용은?**
  - **저장과 컴퓨트의 분리(separate storage and compute)** — **추세는 저장과 컴퓨트를 분리하는
    쪽이지만 대부분의 시스템은 분리와 코로케이션을 혼성화한다.** 상세는
    [컴퓨트와 저장의 분리](../concepts/compute-storage-separation.md).

## 스트리밍 저장과 재생

- 요구가 다르다 — **스트리밍 데이터는 비스트리밍 데이터와 다른 저장 요구를 갖는다. 메시지 큐의
  경우 저장된 데이터는 시간적이며 일정 기간 뒤에 사라질 것으로 기대된다. 그러나 Apache Kafka
  같은 분산·확장 가능 스트리밍 프레임워크는 이제 극히 장기의 스트리밍 데이터 보존을 허용한다.
  카프카는 오래되고 자주 접근되지 않는 메시지를 오브젝트 저장으로 밀어내려 무기한 데이터 보존을
  지원한다. 카프카 경쟁자(Amazon Kinesis·Apache Pulsar·Google Cloud Pub/Sub 포함)도 장기 데이터
  보존을 지원한다** (6장, p.212).[^reis2022] 그 기제는
  [로그 기반 메시지 브로커](../concepts/log-based-message-brokers.md)에 있다.
- 보존과 짝을 이루는 개념 — **이 시스템들의 데이터 보존과 밀접하게 관련된 것이 재생(replay)의
  관념이다. 재생은 스트리밍 시스템이 과거에 저장된 데이터의 범위를 돌려주도록 허용한다. 재생은
  스트리밍 저장 시스템의 표준 데이터 회수 기제다. 재생은 시간 범위에 대해 배치 질의를 돌리거나
  스트리밍 파이프라인에서 데이터를 재처리하는 데 쓰일 수 있다** (6장, p.212).[^reis2022]
- 실시간 분석 쪽의 계보 — **실시간 분석 애플리케이션을 위해 다른 저장 엔진이 등장했다. 어떤
  의미에서 트랜잭션 데이터베이스가 최초의 실시간 질의 엔진으로 등장했다 — 데이터가 쓰이자마자
  질의에 보이게 된다. 그러나 이 데이터베이스는, 특히 큰 데이터 볼륨에 걸쳐 도는 분석 질의에 대해
  잘 알려진 확장·잠금 한계를 갖는다. 행 지향 트랜잭션 데이터베이스의 확장 가능한 판본이 이 한계
  일부를 극복했지만 여전히 규모 있는 분석에 진정으로 최적화돼 있지는 않다** (6장,
  pp.212–213).[^reis2022]

## 데이터의 온도

- 왜 온도인가 — **모든 데이터가 같은 방식으로 접근되지는 않는다. 회수 패턴은 저장·질의되는
  데이터에 따라 크게 달라진다. 여기서 데이터의 "온도(temperature)"라는 개념이 나온다.
  데이터 접근 빈도가 데이터의 온도를 결정한다** (2장, p.39).[^reis2022]
- 6장은 이것을 저장 수명 주기의 문제로 다시 세운다 — **데이터를 저장하는 것은 그냥 오브젝트
  저장이나 디스크에 저장하고 잊어버리는 것만큼 단순하지 않다. 데이터 저장 수명 주기와 데이터
  보존을 생각해야 한다. 접근 빈도와 유스케이스를 생각할 때 "이 데이터가 하류 사용자에게 얼마나
  중요하고 그들이 얼마나 자주 그것에 접근해야 하는가?"를 물으라. 이것이 데이터 저장 수명 주기다.
  물어야 할 또 다른 질문은 "이 데이터를 얼마나 오래 보관해야 하는가?"다** (6장,
  p.223).[^reis2022]
- **뜨거운 데이터(hot data)** — **가장 자주 접근되는 데이터. 하루에 여러 번, 어쩌면 초당 몇
  번씩 회수된다 — 예컨대 사용자 요청을 서빙하는 시스템에서. 이 데이터는 빠른 회수를 위해
  저장돼야 하며, 여기서 "빠름"은 유스케이스에 상대적이다** (2장, p.39).[^reis2022]
  - 6장의 확장 — **뜨거운 데이터는 즉각적이거나 잦은 접근 요구를 갖는다. 뜨거운 데이터의 하부
    저장은 SSD나 메모리처럼 빠른 접근과 읽기에 적합하다. 뜨거운 데이터에 관여하는 하드웨어
    유형 때문에 뜨거운 데이터를 저장하는 것은 흔히 가장 비싼 형태의 저장이다. 뜨거운 데이터의
    예시 유스케이스는 제품 추천과 제품 페이지 결과를 회수하는 것이다. 이 세 저장 계층 중 뜨거운
    데이터를 저장하는 비용이 가장 높지만 회수는 흔히 싸다** (6장, p.224).[^reis2022]
  - 또 하나의 실물 — **질의 결과 캐시가 뜨거운 데이터의 또 다른 예다. 질의가 돌면 어떤 질의
    엔진은 질의 결과를 캐시에 영속한다. 제한된 시간 동안, 같은 질의가 돌 때 저장에 대해 같은
    질의를 다시 돌리는 대신 질의 결과 캐시가 캐시된 결과를 서빙한다. 이는 같은 질의를 반복해서
    중복 발행하는 것보다 훨씬 빠른 질의 응답 시간을 허용한다** (6장, p.224).[^reis2022]
- **미지근한 데이터(lukewarm data)** — **이따금 접근된다 — 이를테면 매주 또는 매달** (2장,
  p.39).[^reis2022]
  - 6장은 같은 것을 **웜 데이터(warm data)** 라 부른다 — **웜 데이터는 반정기적으로, 이를테면
    한 달에 한 번 접근된다. 웜 데이터가 얼마나 자주 접근되는지를 가리키는 확고한 규칙은 없지만
    뜨거운 데이터보다는 적고 차가운 데이터보다는 많다. 주요 클라우드 제공자는 웜 데이터를
    수용하는 오브젝트 저장 계층을 제공한다. 예컨대 S3는 Infrequently Accessed Tier를 제공하고
    Google Cloud는 Nearline이라는 비슷한 저장 계층을 갖는다. 벤더는 권장 접근 빈도의 모델을
    제시하고 엔지니어는 자기 비용 모델링과 모니터링도 할 수 있다. 웜 데이터의 저장은 뜨거운
    데이터보다 싸고 회수 비용은 조금 더 비싸다** (6장, p.224).[^reis2022]
  - **낱말이 두 장에서 다르다** — 2장은 `lukewarm`, 6장은 `warm`이다. 같은 계층을 가리키며
    정의(이따금·반정기적 접근)도 일치한다. 이 KB는 두 표기를 모두 남긴다 — 검색 키가 원어이기
    때문이다.
- **차가운 데이터(cold data)** — **거의 질의되지 않으며 아카이브 시스템에 저장하기 적절하다.
  차가운 데이터는 흔히 규제 준수 목적으로, 또는 다른 시스템에 파국적 장애가 났을 경우를
  대비해 보존된다. "옛날에는" 차가운 데이터를 테이프에 저장해 원격 아카이브 시설로
  보냈다. 클라우드 환경에서 벤더는 월 저장 비용은 아주 싸지만 데이터 회수 가격은 비싼
  특화된 저장 계층을 제공한다** (2장, p.39).[^reis2022]
  - 6장의 확장 — **다른 극단에서 차가운 데이터는 자주 접근되지 않는 데이터다. 차가운 데이터를
    아카이브하는 데 쓰이는 하드웨어는 일반적으로 싸고 내구성이 있다 — HDD·테이프 저장·클라우드
    기반 아카이브 시스템 같은 것이다. 차가운 데이터는 주로 장기 아카이브를 위한 것으로, 데이터에
    접근할 의도가 거의 또는 전혀 없을 때다. 차가운 데이터를 저장하는 것은 싸지만 차가운 데이터를
    회수하는 것은 흔히 비싸다** (6장, p.224).[^reis2022]
- 접근 빈도가 세 축을 동시에 움직인다 — 그림 6-9는 접근 빈도에 따라 **접근(매우 잦음 / 드묾 /
  드묾)·저장 비용(높음 / 중간 / 쌈)·회수 비용(쌈 / 중간 / 높음)** 이 반대 방향으로 움직임을
  보인다 (6장, p.224, 그림 6-9).[^reis2022]

## 저장 계층을 고르는 셈

- 양 극단이 각각 틀렸다 — **데이터의 저장 계층을 고려할 때 각 계층의 비용을 고려하라. 모든
  데이터를 뜨거운 저장에 저장하면 모든 데이터에 빠르게 접근할 수 있다. 그러나 이는 엄청난
  가격에 딸려 온다! 반대로 비용을 아끼려고 모든 데이터를 차가운 저장에 저장하면 저장 비용은
  분명 낮아지지만 데이터에 접근해야 할 때 긴 회수 시간과 높은 회수 비용을 치른다. 저장 가격은
  더 빠르고 높은 성능의 저장에서 더 낮은 저장으로 갈수록 내려간다** (6장,
  pp.224–225).[^reis2022]
- 아카이브의 실제 — **차가운 저장은 데이터를 아카이브하는 데 인기 있다. 역사적으로 차가운 저장은
  물리 백업을 수반했고 흔히 이 데이터를 말 그대로 금고에 보관할 제3자에게 우편으로 보냈다.
  차가운 저장은 클라우드에서 점점 인기를 얻고 있다. 모든 클라우드 벤더가 차가운 데이터 해법을
  제공하며, 데이터를 차가운 저장으로 밀어 넣는 비용과 그것을 회수하는 비용·시간을 저울질해야
  한다** (6장, p.225).[^reis2022]
- 넘침(spillover)을 계산에 넣는다 — **데이터 엔지니어는 뜨거운 저장에서 웜/차가운 저장으로의
  넘침을 고려해야 한다. 메모리는 비싸고 유한하다. 예컨대 뜨거운 데이터가 메모리에 저장되면 새
  데이터가 너무 많고 메모리가 부족할 때 디스크로 흘러넘칠 수 있다. 어떤 데이터베이스는 자주
  접근되지 않는 데이터를 웜이나 차가운 계층으로 옮겨 데이터를 HDD나 오브젝트 저장으로 내려보낼
  수 있다. 후자는 오브젝트 저장의 비용 효율성 때문에 점점 흔해진다. 클라우드에 있고 관리형
  서비스를 쓰고 있다면 디스크 넘침은 자동으로 일어날 것이다** (6장, p.225).[^reis2022]
- 그래서 수명 주기 정책을 자동화한다 — **클라우드 기반 오브젝트 저장을 쓰고 있다면 데이터에
  대한 자동 수명 주기 정책을 만들라. 이는 저장 비용을 극적으로 줄일 것이다. 예컨대 데이터에
  한 달에 한 번만 접근하면 된다면 데이터를 드문 접근 저장 계층으로 옮기라. 데이터가 180일
  됐고 현재 질의에 접근되지 않는다면 아카이브 저장 계층으로 옮기라. 두 경우 모두 일반 오브젝트
  저장에서 데이터를 이전하는 것을 자동화할 수 있고 돈을 아낄 것이다. 그렇긴 하나 회수 비용 —
  시간과 돈 양쪽 — 을 고려하라. 접근·회수 시간과 비용은 클라우드 제공자에 따라 다를 수 있다.
  어떤 클라우드 제공자는 데이터를 아카이브 저장으로 이전하는 것을 단순하고 싸게 만들지만
  데이터를 회수하는 것은 비싸고 느리다** (6장, p.225).[^reis2022]

## 데이터 보존 — 얼마나 오래 두는가

- 무엇이 바뀌었는가 — **"빅데이터" 초기에는 유용성과 무관하게 가능한 모든 데이터 조각을
  축적하는 쪽으로 기우는 경향이 있었다. "미래에 이 데이터가 필요할지도 모른다"는 기대였다. 이
  데이터 호딩은 불가피하게 다루기 힘들고 더러워졌고, 다른 결과와 악몽 가운데서도 데이터 늪과
  데이터 보존에 대한 규제 단속을 낳았다. 요즘 데이터 엔지니어는 데이터 보존을 고려해야 한다 —
  어떤 데이터를 보관할 **필요가** 있고 얼마나 **오래** 보관해야 하는가?** (6장,
  p.225).[^reis2022]
- **가치(value)** — **데이터는 자산이므로 저장하고 있는 데이터의 가치를 알아야 한다. 물론 가치는
  주관적이며 당면한 유스케이스와 더 넓은 조직에 얼마나 값진지에 달려 있다. 이 데이터는 재생성이
  불가능한가, 아니면 상류 시스템에 질의해서 쉽게 재생성할 수 있는가? 이 데이터가 가용한 것과
  그렇지 않은 것이 하류 사용자에게 어떤 영향을 주는가?** (6장, p.225).[^reis2022]
- **시간(time)** — **하류 사용자에게의 가치는 데이터의 나이에도 달려 있다. 새 데이터는 일반적으로
  오래된 데이터보다 더 값지고 더 자주 접근된다. 기술적 한계가 데이터를 특정 저장 계층에 얼마나
  오래 저장할 수 있는지를 정할 수 있다. 예컨대 뜨거운 데이터를 캐시나 메모리에 저장한다면 TTL을
  설정해 어느 시점 뒤에 데이터를 만료시키거나 웜이나 차가운 저장으로 영속시켜야 할 가능성이 크다.
  그러지 않으면 뜨거운 저장이 가득 차고 뜨거운 데이터에 대한 질의가 성능 지연을 겪을 것이다**
  (6장, p.226).[^reis2022]
- **규제 준수(compliance)** — **어떤 규제(예: HIPAA와 지불카드산업, PCI)는 데이터를 일정 기간
  보관하도록 요구할 수 있다. 이 상황에서 데이터는 접근 요청의 가능성이 낮더라도 요청 시 접근
  가능하기만 하면 된다. 다른 규제는 데이터를 제한된 기간만 보유하도록 요구할 수 있고, 그러면
  특정 정보를 제때 규제 준수 지침 안에서 삭제할 능력이 필요할 것이다. 준수해야 하는 특정 규제의
  보존 요구에 맞는 저장·아카이브 데이터 프로세스와 데이터를 검색할 능력이 필요할 것이다. 물론
  규제 준수와 비용의 균형을 맞추고 싶을 것이다** (6장, p.226).[^reis2022]
- **비용(cost)** — **데이터는 (바라건대) ROI를 갖는 자산이다. ROI의 비용 쪽에는 명백한 저장
  비용이 데이터와 결부돼 있다. 데이터를 보존해야 하는 기간을 고려하라. 뜨거운·웜·차가운 데이터에
  대한 논의를 감안해 자동 데이터 수명 주기 관리 실무를 구현하고, 요구되는 보존 날짜 이후 데이터가
  필요 없으면 데이터를 차가운 저장으로 옮기라. 또는 정말 필요 없으면 데이터를 삭제하라** (6장,
  p.226).[^reis2022]

## 단일테넌트 저장과 멀티테넌트 저장

- 용어 복습 — **단일테넌트(single-tenant) 아키텍처에서는 각 테넌트 그룹(예: 개별 사용자·사용자
  그룹·계정·고객)이 네트워킹·컴퓨트·저장 같은 자기 전용 자원 집합을 받는다. 멀티테넌트
  (multitenant) 아키텍처는 이것을 뒤집어 이 자원을 사용자 그룹들 사이에서 공유한다. 두 아키텍처
  모두 널리 쓰인다** (6장, p.226).[^reis2022] 그 트레이드오프의 일반형은
  [클라우드 네이티브 아키텍처](../concepts/cloud-native-architecture.md)에 있다.
- 단일테넌트 저장이 뜻하는 것 — **단일테넌트 저장을 채택하는 것은 모든 테넌트가 자기 전용 저장을
  받는다는 뜻이다. 각 테넌트가 데이터베이스를 하나씩 받는다. 이 데이터베이스들 사이에 데이터가
  공유되지 않고 저장이 완전히 격리된다. 단일테넌트 저장을 쓰는 예는 각 고객의 데이터가 격리되어
  저장돼야 하고 다른 어떤 고객의 데이터와도 섞일 수 없는 경우다. 이 경우 각 고객이 자기 데이터베이스를
  받는다** (6장, p.226).[^reis2022]
- 그 귀결 — **별도 데이터 저장은 별도의 독립적인 스키마·버킷 구조, 그리고 저장에 관련된 모든 것을
  함의한다. 이는 각 테넌트의 저장 환경을 균일하게 설계하거나 그들이 마음대로 진화하도록 놔둘 자유가
  있다는 뜻이다. 고객 간 스키마 변이는 이점이자 합병증일 수 있다 — 늘 그렇듯 트레이드오프를
  고려하라. 각 테넌트의 스키마가 모든 테넌트에 걸쳐 균일하지 않으면, 전체 테넌트 데이터의 통합된
  뷰를 만들기 위해 여러 테넌트의 테이블을 질의해야 할 때 이는 큰 결과를 갖는다** (6장,
  p.227).[^reis2022]
- 멀티테넌트 저장 — **멀티테넌트 저장은 하나의 데이터베이스 안에 여러 테넌트의 저장을 허용한다.
  예컨대 고객이 자기 데이터베이스를 받는 단일테넌트 시나리오 대신, 여러 고객이 멀티테넌트
  데이터베이스의 같은 데이터베이스 스키마나 테이블에 상주할 수 있다. 멀티테넌트 데이터를 저장한다는
  것은 각 테넌트의 데이터가 같은 곳에 저장된다는 뜻이다** (6장, p.227).[^reis2022]

## 만능 추천은 없다

- **어떤 유형의 저장 해법을 써야 하는가? 이는 유스케이스, 데이터 볼륨, 반입 빈도, 반입되는
  데이터의 형식과 크기에 달렸다. 모두에게 맞는 보편적 저장 추천은 없다. 모든 저장 기술은
  자기 트레이드오프를 갖는다. 무수한 종류의 저장 기술이 존재하며, 자기 데이터 아키텍처에
  최선인 선택을 정할 때 압도되기 쉽다** (2장, p.39).[^reis2022]
- 장의 결론도 같다 — **저장은 어디에나 있고 데이터 엔지니어링 수명 주기의 많은 단계를 떠받친다.
  이 장에서 저장 시스템 주위의 원료·유형·추상·큰 아이디어를 배웠다. 쓰게 될 저장 시스템의 내부
  작동과 한계에 대한 깊은 지식을 얻으라. 데이터·활동·워크로드의 유형을 알라** (6장,
  p.230).[^reis2022]

## 함께 일할 사람들

- **저장은 데이터 엔지니어링 인프라의 심장에 있다. IT 인프라를 소유한 사람들 — 일반적으로
  DevOps·보안·클라우드 아키텍트 — 과 상호작용할 것이다. 데이터 엔지니어링과 다른 팀 사이의 책임
  영역을 정의하는 것이 결정적이다. 데이터 엔지니어가 AWS 계정에 자기 인프라를 배치할 권한을
  갖는가, 아니면 다른 팀이 이 변경을 처리해야 하는가? 팀들이 효율적이고 빠르게 함께 일할 수 있도록
  다른 팀과 협력해 간소화된 프로세스를 정의하라** (6장, p.227).[^reis2022]
- 조직 성숙도가 분업을 정한다 — **데이터 저장에 대한 책임 분담은 관련된 조직의 성숙도에 크게
  좌우될 것이다. 회사가 데이터 성숙도 초기에 있다면 데이터 엔지니어가 저장 시스템과 워크플로를
  관리할 가능성이 크다. 회사가 데이터 성숙도 후기에 있다면 데이터 엔지니어는 저장 시스템의 한
  구획을 관리할 것이다. 이 데이터 엔지니어는 저장 양쪽 — 반입과 변환 — 의 엔지니어와도 상호작용할
  가능성이 크다** (6장, p.228).[^reis2022]
- 그리고 보장해야 할 것 — **데이터 엔지니어는 하류 사용자가 쓰는 저장 시스템이 안전하게 가용하고,
  높은 품질의 데이터를 담고, 넉넉한 저장 용량을 갖고, 질의와 변환이 돌 때 성능을 내도록 보장해야
  한다** (6장, p.228).[^reis2022]

## 저류가 저장에 거는 조건

- 왜 저장의 저류가 다른가 — **저장의 저류는 저장이 데이터 엔지니어링 수명 주기의 모든 단계에
  결정적 허브이기 때문에 유의미하다. 데이터가 움직이고 있거나(반입) 질의·변환되는 다른 저류와
  달리, 저장의 저류는 저장이 워낙 편재하기 때문에 다르다** (6장, p.228).[^reis2022]
- **보안** — **엔지니어는 흔히 보안을 자기 일의 장애물로 보지만 보안이 핵심 조력자라는 생각을
  껴안아야 한다. 세밀한 데이터 접근 통제와 함께 저장 중·이동 중의 견고한 보안은 업무 안에서
  데이터가 더 널리 공유되고 소비되도록 허용한다. 그것이 가능할 때 데이터의 가치는 유의하게
  올라간다** (6장, p.228).[^reis2022]
  - 실행 규칙 — **늘 그렇듯 최소 권한 원칙을 행사하라. 요구되지 않는 한 누구에게도 전체
    데이터베이스 접근을 주지 말라. 이는 대부분의 데이터 엔지니어가 실무에서 전체 데이터베이스
    접근이 필요 없다는 뜻이다. 또한 데이터베이스의 컬럼·행·셀 수준 접근 통제에 주의를 기울이라.
    사용자에게 필요한 정보만 주고 그 이상은 주지 말라** (6장, p.228).[^reis2022]
- **데이터 관리 — 데이터 카탈로그와 메타데이터 관리** — **데이터는 견고한 메타데이터로 향상된다.
  카탈로깅은 데이터 발견을 가능하게 해 데이터 과학자·분석가·ML 엔지니어를 돕는다. 데이터 계보는
  데이터 문제를 추적하는 시간을 가속하고 소비자가 상류 원시 소스를 찾도록 허용한다. 저장 시스템을
  지어 나가면서 메타데이터에 투자하라. 데이터 사전과 이 다른 도구들의 통합은 사용자가 제도적
  지식을 견고하게 공유하고 기록하도록 허용한다** (6장, p.228).[^reis2022] 그 도구의 전문은
  [메타데이터 관리](../concepts/metadata-management.md)에 있다.
  - **메타데이터 관리는 데이터 거버넌스도 유의하게 향상한다. 수동적 데이터 카탈로깅과 계보를
    가능하게 하는 것을 넘어, 이 시스템들에 대한 분석을 구현해 데이터에 무슨 일이 일어나는지의
    명확하고 능동적인 그림을 얻는 것을 고려하라** (6장, p.229).[^reis2022]
- **데이터 관리 — 오브젝트 저장의 데이터 버저닝** — **주요 클라우드 오브젝트 저장 시스템은 데이터
  버저닝을 가능하게 한다. 데이터 버저닝은 프로세스가 실패하고 데이터가 손상될 때 오류 복구에 도움이
  될 수 있다. 버저닝은 모델을 짓는 데 쓰인 데이터셋의 이력을 추적하는 데도 이롭다. 코드 버전 관리가
  개발자가 버그를 일으킨 커밋을 추적하게 하듯, 데이터 버전 관리는 ML 엔지니어가 모델 성능 저하로
  이어지는 변경을 추적하는 것을 도울 수 있다** (6장, p.229).[^reis2022]
- **데이터 관리 — 프라이버시** — **GDPR과 다른 프라이버시 규제는 저장 시스템 설계에 유의한 영향을
  줬다. 프라이버시 함의가 있는 어떤 데이터든 데이터 엔지니어가 관리해야 할 수명 주기를 갖는다.
  데이터 엔지니어는 데이터 삭제 요청에 대응하고 요구에 따라 데이터를 선택적으로 제거할 준비가 돼
  있어야 한다. 덧붙여 엔지니어는 익명화와 마스킹을 통해 프라이버시와 보안을 수용할 수 있다** (6장,
  p.229).[^reis2022]
- **DataOps** — **DataOps는 데이터 관리와 직교하지 않으며 상당한 중첩 영역이 존재한다. DataOps는
  저장 시스템의 전통적 운영 모니터링과 데이터 자체의 모니터링에 관여하며 이는 메타데이터·품질과
  분리할 수 없다** (6장, p.229).[^reis2022]
  - **시스템 모니터링** — **데이터 엔지니어는 다양한 방식으로 저장을 모니터링해야 한다. 여기에는
    인프라 저장 구성 요소가 존재하는 곳의 모니터링뿐 아니라 오브젝트 저장과 다른 "서버리스"
    시스템의 모니터링도 든다. 데이터 엔지니어는 FinOps(비용 관리)·보안 모니터링·접근 모니터링에서
    앞장서야 한다** (6장, p.229).[^reis2022]
  - **데이터 관측과 모니터링** — **서술한 대로 메타데이터 시스템이 결정적이지만, 좋은 엔지니어링은
    데이터의 엔트로피적 성격을 고려해 그 특성을 이해하려 능동적으로 노력하고 주요 변경을 지켜봐야
    한다. 엔지니어는 데이터 통계를 모니터링하고, 이상 탐지 방법이나 단순한 규칙을 적용하고, 논리적
    불일치를 능동적으로 테스트·검증할 수 있다** (6장, p.229).[^reis2022]
- **데이터 아키텍처** — 저자들이 드는 팁 (6장, p.230):[^reis2022] **요구되는 신뢰성과 내구성을
  위해 설계하라. 상류 원천 시스템과 그 데이터가 일단 반입되면 어떻게 저장·접근될지 이해하라.
  하류에서 일어날 데이터 모델과 질의의 유형을 이해하라.**
  - **데이터가 자랄 것으로 예상되면 클라우드 제공자와 저장을 협상할 수 있는가? FinOps에 능동적
    접근을 취하고 그것을 아키텍처 대화의 중심 부분으로 다루라. 조급하게 최적화하지 말되, 큰 데이터
    볼륨을 운영할 업무 기회가 존재하면 규모에 대비하라** (6장, p.230).[^reis2022]
  - **완전 관리형 시스템 쪽으로 기울고 제공자 SLA를 이해하라. 완전 관리형 시스템은 일반적으로
    당신이 돌봐야 하는 시스템보다 훨씬 견고하고 확장 가능하다** (6장, p.230).[^reis2022]
- **오케스트레이션** — **오케스트레이션은 저장과 고도로 얽혀 있다. 저장은 데이터가 파이프라인을
  통해 흐르도록 허용하고 오케스트레이션은 펌프다. 오케스트레이션은 또한 엔지니어가 데이터 시스템의
  복잡성에 대처하도록 도우며, 잠재적으로 여러 저장 시스템과 질의 엔진을 결합한다** (6장,
  p.230).[^reis2022]
- **소프트웨어 엔지니어링** — **저장의 맥락에서 소프트웨어 엔지니어링을 두 방식으로 생각할 수
  있다. 첫째, 쓰는 코드가 저장 시스템과 함께 잘 수행돼야 한다. 쓰는 코드가 데이터를 올바로 저장하고
  데이터·메모리 누수나 성능 문제를 우발적으로 일으키지 않도록 하라. 둘째, 저장 인프라를 코드로
  정의하고 데이터를 처리할 때가 되면 덧없는 컴퓨트 자원을 쓰라. 저장이 컴퓨트와 점점 구별되므로
  데이터를 오브젝트 저장에 두면서 자원을 자동으로 띄우고 내릴 수 있다. 이는 인프라를 깨끗하게
  유지하고 저장과 질의 층의 결합을 피한다** (6장, p.230).[^reis2022]
