## 하나의 질문

**중앙 카탈로그 없이, 상호 연결된 자율 데이터 프로덕트의 메시에서 데이터를 어떻게 발견하고·
이해하고·신뢰하는가.**

- 13장이 여는 문장이 그 질문 그대로다 — **데이터를 발견하고·이해하고·신뢰하는 것은 데이터 여정의
  필수 단계다. 데이터 메시의 접근을 고유하게 만드는 것은 **중앙집중 병목을 만들지 않고** 상호
  연결된 자율 데이터 프로덕트의 탈중앙 메시에서 데이터를 어떻게 발견하고·이해하고·신뢰하는가다**
  (13장, p.233).[^dehghani2022]
- 네 성질의 출처가 밝혀진다 — **데이터 메시는 발견 가능성(discoverability)·이해
  가능성(understandability)·신뢰성(trustworthiness)·탐색 가능성(explorability)을 데이터
  프로덕트의 내재적 특성 일부로 정의한다. 나는 이것들을 3장에서 데이터 프로덕트의 기본 사용성
  특성으로 간략히 도입했다** (13장, p.233).[^dehghani2022]
  [제품으로서의 데이터 원칙](../concepts/data-as-a-product-principle.md)의 여덟 속성 중 넷이다.
- 이 성질들이 답하는 질문 목록 — **이 성질들은 다음 같은 질문에 답한다: 청취자에 대해 무언가를
  말해 주는 데이터 프로덕트가 있는가? 청취자에 대해 데이터 프로덕트가 실제로 어떤 정보를 제공하는가?
  그것을 신뢰할 수 있는가? 특정한 데이터 요구 집합을 가진 내 구체적 사용 사례에 쓸 수 있는가?
  초기 실험을 위해 어떻게 접근을 얻는가?** (13장, p.234).[^dehghani2022]

## 13장이 스스로 긋는 범위

- **이 장은 데이터 발견 가능성과 조합 가능성의 각 어포던스를 간략히 도입한다. 나는 데이터 메시의
  입장을 서술하고 설계 고려사항을 도입해, 각 개별 데이터 프로덕트가 자기 발견 가능성·이해
  가능성·조합 가능성에서 **지역적으로** 자기 몫을 하게 한다. 나는 데이터 프로덕트의 이 지역
  어포던스들이 단단히 결합된 동기화 지점을 만들지 않고 많은 데이터 프로덕트에 걸친 메시 수준
  능력을 표면화하는 방식을 논한다** (13장, p.233).[^dehghani2022]
- 미완성을 명시한다 — **이 장은 데이터 메시 접근의 경계, 곧 데이터 메시의 목표와 무엇이 양립
  가능하고 무엇이 아닌지를 서술한다. **정확한 명세는 아직 정의되고 테스트되어야 하며 이 책의
  범위 밖이다**** (13장, p.233).[^dehghani2022]

## 기존 두 접근과 그 판정

- 저자가 논쟁 지점을 특정한다 — **여기까지에 대해서는 이견이 없다고 생각한다. 데이터 메시가
  오늘날 데이터 발견 가능성 접근의 다수 — 곧 데이터 카탈로그 서비스 — 와 다른 지점은 **이
  어포던스들을 어떻게 달성하는가**다** (13장, p.234).[^dehghani2022]
- **① 사후 큐레이션과 통합(a posteriori curation and consolidation)** — **이 접근에서 데이터
  스튜어드나 거버넌스 팀 구성원이 도메인에 의해 **이미 생성된** 데이터에 대한 정보를 사후에
  식별·태깅·문서화·통합하는 임무를 맡는다. 그렇게 큐레이션된 정보가 발견의 소스가 된다** (13장,
  p.234).[^dehghani2022]
- **② 사후 조사형 지능(a posteriori investigative intelligence)** — **이 접근은 이미 생성된
  데이터에 사후에 풀어놓은 지능형 기계 관찰을 적용해 메타데이터를 추출한다. 예컨대 대규모 운영
  데이터에 알고리즘을 돌려, 누가 그 테이블에 접근했는지·얼마나 널리 쓰이는지·어떻게 쓰이는지를
  분석해 테이블의 신뢰성을 판정할 수 있다. 이 정보는 발견 가능성에 유용한 데이터에 대한 지식의
  층을 만든다** (13장, p.234).[^dehghani2022]
- 판정 — **지능형·조사형 알고리즘은 데이터 메시 이전에 조직에 어떤 데이터가 있는지 발견하도록
  데이터 메시를 부트스트랩하거나, 각 데이터 프로덕트에 추가 정보를 더해 메시의 관측 가능성을
  돕는 데는 유용하지만, **불충분하다**** (13장, p.234).[^dehghani2022]
  - **부정이 아니라 불충분 판정**이라는 점이 중요하다. [메타데이터 관리](../concepts/metadata-management.md)의
    수집·프로파일링 계열을 저자는 폐기하지 않고 **부트스트랩 단계로 강등**한다.

## 발견 가능성을 왼쪽으로 옮긴다

- 핵심 조작 — **데이터 메시가 두 접근 모두와 다른 주된 점은 그것이 **발견 가능성을 왼쪽으로
  이동(shifts discoverability left)**시킨다는 것이다. 데이터 발견 가능성·이해 가능성 등은
  데이터 프로덕트가 생성될 때 그리고 그 수명 주기 전체에 걸쳐 **데이터 프로덕트 자신에서
  시작한다**. 자기를 발견 가능·이해 가능·신뢰 가능·탐색 가능하게 만드는 데 필요한 정보를
  공유하는 것은 데이터 프로덕트의 책임이다** (13장, p.234).[^dehghani2022]
  - `a posteriori`(사후)와 `shift left`(왼쪽 이동)의 대비가 이 절의 전부다 — 같은 조작을
    [데이터 퀀텀](../concepts/data-quantum.md)이 변환 코드에 대해 했고, 여기서는 발견 정보에
    대해 한다.
- 대상이 둘이다 — **데이터 메시는 발견 가능성을 **기계와 사람의 접근** 양쪽에 대해 설계한다.
  사람은 데이터 프로덕트를 발견하고·이해하고·신뢰하고·탐색할 수 있고, 기계는 이 기능을 자동화해
  그 위에 고차 능력을 지을 수 있다. 예컨대 **메시 경험 플레인**은 각 데이터 프로덕트가 제공하는
  발견 데이터를 써서 데이터 프로덕트 검색을 자동화할 수 있다** (13장, p.234).[^dehghani2022]

## 세 층위의 발견

- 그림 13-1이 발견을 세 층으로 나눈다 (13장, p.235):[^dehghani2022]
  - **메시 수준 발견** — 메시 검색(search mesh)·메시 브라우징(browse mesh)·사용자 생성
    콘텐츠(user-generated content)
  - **데이터 프로덕트 수준 발견** — 시맨틱 스키마(semantic schema)·문서(documents)·접근
    감사(access audit)
  - **출력 포트 수준 발견** — 구문 스키마(syntax schema)·통계(statistics)·품질 메트릭
- 스코프가 갈리는 근거 — **메시 경험 플레인은 검색·브라우즈 같은 메시 수준 발견 가능성을
  표면화하는 데 중요한 구실을 한다. 메시 수준 연산은 데이터 프로덕트가 제공하는 데이터와 API를
  통해 가능해진다. 발견 가능성 정보의 일부는 데이터 프로덕트에 스코프되고(예: 그 시맨틱 명세와
  문서), 일부는 각 출력 포트에 스코프된다(예: 데이터 형식 명세, 데이터의 통계적 성질과 모양,
  품질 메트릭과 SLO)** (13장, p.236).[^dehghani2022]
  - **하나의 데이터 프로덕트가 여러 출력 포트를 가지므로 스키마도 여러 개**라는 것이 여기서
    구조적으로 확정된다 — 아래 시맨틱/구문 모델 절이 그 이유다.

## 자기 등록으로 시작한다

- **엔티티의 발견은 그 존재에 대한 인지, 그리고 그것을 위치 지정하고 주소 지정할 수 있는 능력에서
  시작한다. 데이터 메시에서 발견은 데이터 프로덕트가 자기 존재를 더 넓은 생태계, 특히 검색이나
  브라우즈 같은 데이터 플랫폼의 메시 경험 플레인 서비스에 알리는 것으로 시작한다** (13장,
  p.236).[^dehghani2022]
- 시점은 열려 있다 — **이름·주소·위치 같은 여러 정보 조각의 할당은 데이터 프로덕트의 빌드·배포·
  런타임의 서로 다른 단계에서 이뤄질 수 있다** (13장, p.236).[^dehghani2022]
- 계열이 있다 — **서비스 메시 같은 운영 플랫폼에는 서비스를 등록·주소 지정·위치 지정하는 선행
  기술이 있다. 비슷한 기술과 접근이 배치될 수 있다** (13장, p.236).[^dehghani2022]
  [마이크로서비스와 서버리스](../concepts/microservices-and-serverless.md)의 서비스 디스커버리
  계열이다.
- 최소 요건 — **데이터 프로덕트가 발견을 시동하는 데 필요한 최소 정보는 **주소 지정 가능한
  엔드포인트로서의 고유 이름(식별자)**이며, 이를 통해 더 많은 정보를 질의할 수 있다** (13장,
  p.236).[^dehghani2022]

## 전역 URI

- **이상적으로 모든 데이터 프로덕트는 자기를 서술하는 표준 인터페이스를 갖는다: 데이터 프로덕트의
  다른 모든 발견 측면에 접근하는 루트가 되는 전역적으로 접근 가능한 URI다. 그런 발견 API가
  제공하는 정보는 코어 데이터 시맨틱 명세·전체 문서·접근 로그 같은 데이터 프로덕트 수준 정보와,
  각 출력 포트에 특유한 데이터 구문 및 프라이버시 수준·품질 보증 같은 다른 메타데이터를 포함한다**
  (13장, p.236).[^dehghani2022]
  - 각주 — **이 책에서 나는 익숙함 때문에 URI를 썼지만, 구현은 URI와 비슷하되 확장된 문자
    집합을 갖는 IRI(Internationalized Resource Identifier)를 쓸 것이다** (13장, p.236, 각주
    1).[^dehghani2022]
- 갱신 시점이 정보마다 다르다 — **데이터 프로덕트의 발견 API가 제공하는 정보는 수명 주기의 서로
  다른 단계에서 갱신될 수 있다. 스키마 명세를 포함한 일부는 빌드 시점에 알려지고, 데이터의 모양을
  서술하는 통계 같은 다른 것은 런타임에 만들어진다** (13장, p.236).[^dehghani2022]
- 유지 주체와 제공 주체가 갈린다 — **데이터 프로덕트 개발자가 데이터 프로덕트 발견 가능성 정보를
  그 데이터와 함께 유지한다. 그들은 **데이터 프로덕트 경험 플레인**이 제공하는 표준화된 발견 API
  같은 데이터 플랫폼 구성 요소를 쓴다** (13장, p.236).[^dehghani2022]
- 사용자의 동선 — **데이터 사용자는 흔히 메시 경험 플레인을 통해 발견과 검색을 시작하고, 특정
  데이터 프로덕트의 발견 정보로 빠르게 깊이 들어갈 수 있다** (13장, p.236).[^dehghani2022]

## 시맨틱 모델과 구문 모델

- 절 머리의 제사 — **All models are wrong, but some are useful. — George Box** (13장,
  p.237).[^dehghani2022]
- 전제 — **데이터는 어떤 **모델**에 따라 모아진 사실의 집합이다. 데이터 모델은 현실의 **근사**이며,
  당면한 (분석) 과업에 충분히 좋은 것이다** (13장, p.237).[^dehghani2022]
- 모델링 관행의 지형 — **집필 시점 여러 흔한 관행이 있다: 관계형 테이블(SQL 데이터 저장소),
  중첩 트리 구조로 평탄화된 관계(JSON 구조), 열이나 행으로 저장된 속성 그래프 — 엔티티와 관계
  둘 다 속성을 갖는 것(그래프 데이터베이스), 시맨틱 그래프(시맨틱 웹), 시계열 데이터 모델링 등이다**
  (13장, p.237).[^dehghani2022]
- 저자가 표현력에 등급을 매긴다 — **어떤 모델링 양식은 더 표현적이고 직관적인 인간의 세계 이해에
  가깝고, 어떤 것은 손실이 있으며 기계 처리에 최적화되어 있다. 예컨대 속성 그래프는 엔티티·그
  타입·그 성질·엔티티 사이의 관계를 서술하므로 세계를 더 직관적으로 모델링할 수 있다. 가장
  중요하게는 **관계의 타입과 성질을 명시적으로** 모델링할 수 있다. 이는 중첩 표 구조와 대조된다.
  거기서는 속성 값에 근거해 관계의 성질에 대한 가정을 세워야 한다** (13장,
  p.237).[^dehghani2022]
  - [그래프 데이터 모델](../concepts/graph-data-models.md)이 저자의 선호 표현으로 지목되는
    자리다. 그림 13-2는 playlist 도메인을 Listener–Plays→Tracks, Playlist–Contains→Tracks,
    Listener–Creates→Playlist, Recommends 같은 이름 붙은 간선으로 그린다 (13장, p.237,
    그림 13-2).[^dehghani2022]
- **두 모델이 분리된다** (13장, pp.237–238):[^dehghani2022]
  - **시맨틱 모델(semantic model)** — **이상적으로 데이터 프로덕트는 자기 사업 도메인 데이터를
    사업의 현실에 최대한 가깝게 모델링한다. 나는 이것을 데이터 프로덕트의 시맨틱 모델이라 부른다:
    데이터의 도메인 모델을 포착하는 기계·사람 판독 가능한 모델 정의다 — 데이터 프로덕트가 도메인을
    어떻게 모델링하는지, 데이터가 어떤 타입의 엔티티를 포함하는지, 엔티티의 성질, 엔티티 사이의
    관계 등이다.**
  - **구문 모델(syntax model)** — **시맨틱 모델에 더해, 데이터 프로덕트는 자기 출력 포트가
    지원하는 접근 모델에 따라 자기 시맨틱을 인코딩한다. 나는 이것을 구문 모델이라 부른다.
    **모든 출력 포트는 자기 구문 모델을 갖는다.** 예컨대 playlist 파일 출력 포트는 재생 목록을
    중첩 테이블로 모델링해 열 지향 파일로 저장하고 JSON 스키마에 따라 정의한다. 이 모델링은
    피처(모든 레코드에 걸친 열)를 쓰는 기계 학습 훈련에 최적화된다.**
- 시맨틱 모델이 하는 일 — **시맨틱 모델은 구문 모델만 봐서는 알 수 없는 숨은 가정 없이, 데이터가
  무엇을 포착하려는지에 대한 기계와 사람의 이해 양쪽에 도움이 된다. 그것은 데이터를 의도된 모델에
  대해 자동 검증하는 데 도움이 된다. 또한 **더 큰 지식 그래프의 생성에 참여한다**** (13장,
  p.238).[^dehghani2022]
  - 각주가 한계를 붙인다 — **시맨틱 모델은 데이터 사용자가 데이터에서 의미를 찾도록 돕지만, 그
    자체로 의미를 전달하지는 않는다** (13장, p.238, 각주 2).[^dehghani2022]
  - [시맨틱·메트릭 레이어](../concepts/semantic-and-metrics-layers.md)와 갈리는 자리가 여기다 —
    저자는 시맨틱을 웨어하우스 위 공용 층이 아니라 **데이터 프로덕트마다 하나씩** 두고, 구문은
    **출력 포트마다 하나씩** 둔다.
- 셋째로 기대(expectations)가 더해진다 — **구문과 시맨틱 모델링에 더해, 데이터 프로덕트 사용자와
  개발자가 정의하는 코드화된 데이터 **기대(expectations)** — 데이터의 기대 값과 분포를 표현하는
  테스트 — 는 데이터 이해에 크게 도움이 된다** (13장, p.238).[^dehghani2022] 각주는 도구의 예로
  Great Expectations를 든다 (13장, p.238, 각주 3).[^dehghani2022]
  [데이터 품질 관리](../concepts/data-quality-management.md)의 검증 테스트 계열이 여기서
  **발견 정보의 일부**로 재배치된다.

## 데이터 보증으로 신뢰를 세운다

- **올바른 데이터를 찾는 여정에서 데이터 사용자는 데이터가 자기 특정 사용 사례가 요구하는 보증을
  충족하는지 평가하기 위해 데이터의 특정한 **본질적 특성(essential characteristics)**을 평가해야
  한다** (13장, p.238).[^dehghani2022]
- 데이터 프로덕트가 하는 일 — **데이터 프로덕트는 이 객관적 메트릭들을 계산하고 공유한다. 이
  메트릭 중 일부에 대해서는 보증(SLO)을 정의하고 유지한다. 예컨대 **play events** 데이터
  프로덕트는 자기 이벤트의 적시성을 10–30 ms(지연 범위) 보증을 가진 메트릭으로 정의한다. 데이터를
  처리하면서 최신 적시성 메트릭을 서빙하고 자기 보증을 충족하려 애쓴다. 이 메트릭들은 신뢰를
  알리고 세우는 수단이자, 데이터 사용자와 기대를 설정하는 **계약**이다** (13장,
  p.238).[^dehghani2022]
- 정의 주체가 갈린다 — **이 메트릭들의 정의, 그것을 어떻게 계산하고 제시하는지는 **전역
  거버넌스**의 관심사이며 기저 **데이터 프로덕트 경험 플레인**에 의해 표준화된 방식으로 가능해진다**
  (13장, p.238).[^dehghani2022] [연합 컴퓨테이셔널 거버넌스
  원칙](../concepts/federated-computational-governance-principle.md)의 "결정은 전역, 실행은
  지역"이 다시 적용되는 자리다.
- 메트릭도 시간 가변이다 — **이 측정치들은 데이터 프로덕트가 새 데이터를 처리하면서 계속
  갱신된다. 다른 메타데이터와 마찬가지로 메트릭도 시간적이다 — 곧 데이터 프로덕트의 처리 시간과
  실제 시간(또는 시간 윈도우)에 의존한다** (13장, p.239).[^dehghani2022]

## 보증의 다섯 범주

- 저자가 목록의 지위를 먼저 낮춘다 — **이 목록은 예시일 뿐이며 결코 완전하지 않다** (13장,
  p.239).[^dehghani2022]

**① 데이터 품질 메트릭** — **품질로 묶을 수 있는 특성 집합이 있다. 이 속성들은 데이터
프로덕트가 **좋은지 나쁜지**를 정의하려는 것이 아니다. 그것들은 데이터 프로덕트가 충족하기를
기대하는 보증의 문턱값을 소통할 뿐이며, 그 문턱은 특정 사용 사례에는 충분히 수용 가능한 범위일
수 있다** (13장, p.239).[^dehghani2022]

- 저자의 예 — **player 도메인은 두 개의 다른 데이터 프로덕트를 제공할 수 있다: 준실시간 데이터와
  누락·중복 이벤트를 포함한 더 낮은 수준의 일관성을 가진 **play events**, 그리고 더 긴 지연이지만
  더 높은 데이터 일관성을 가진 **play sessions**다. **각각은 자기 사용 사례에 대해 신뢰할 만하다고
  간주될 수 있다**** (13장, p.239).[^dehghani2022]
  - **품질을 절대 등급이 아니라 사용 사례 상대적 계약으로 두는 것**이 이 항의 핵심이고,
    [데이터 품질 관리](../concepts/data-quality-management.md)가 품질을 조직 전체의 단일 기준
    집합으로 관리하는 서술과 갈리는 자리다. 대립은 처방이고, 조건은 **소비자마다 허용 오차가
    다른가**이다.
- 네 예 (13장, p.239):[^dehghani2022]

| 특성 | 저자의 정의 |
|---|---|
| 정확성(accuracy) | 데이터가 실세계 맥락에서 속성의 참값을 얼마나 가깝게 표현하는가의 정도 |
| 완전성(completeness) | 데이터가 실세계 맥락의 모든 성질과 인스턴스를 표현하는 정도 |
| 일관성(consistency) | 데이터가 모순에서 자유로운 정도 |
| 정밀도(precision) | 속성 충실도의 정도 |

- 각주 — **집필 시점 ISO/IEC 25012가 데이터 품질의 15가지 특성을 표준화한다** (13장, p.239,
  각주 4).[^dehghani2022]

**② 데이터 성숙도 메트릭** — **내 견해로 데이터 성숙도는 조직이 데이터 주도 운영 모델을 향한
자기 로드맵과 포부에 근거해 **주관적으로** 정의한다. 예컨대 조직은 사용 정도(degree of usage,
데이터가 얼마나 널리 쓰이는가), 수명 주기(life cycle, 데이터 프로덕트가 개발 중이고 활발히
진화·최적화되는가 아니면 휴면인가), 다양성(diversity, 지원하는 접근 양식과 사용 사례의 수),
연결도(linkage, 타입과 데이터를 재사용하는 형태로 다른 데이터 프로덕트에 연결된 정도) 같은 몇
요인에 근거해 성숙도 모델을 정의할 수 있다. 데이터 프로덕트는 조직의 표준 모델에 따라 자기
성숙도를 계산하고 공유한다** (13장, p.239).[^dehghani2022]

**③ 데이터 표준 준수** — **데이터 프로덕트가 상호운용성 수준을 높이기 위해 따를 수 있는 기존의
도메인 특유 데이터 모델이 있다. 예컨대 의료 도메인에서 FHIR HL7 자원 정의는 조직 내·외부의 더
많은 데이터 소비자와의 상호운용성 수준을 높일 수 있다. 산업 표준을 따르는 결정은 장점(예: 외부
상호운용성)과 단점(예: 하나의 만능 모델에 맞추는 변환 비용)을 함께 고려해야 한다. 데이터 프로덕트는
자기 데이터 모델이 어떤 표준을 따르는지 표현할 수 있다** (13장, p.240).[^dehghani2022]

**④ 시간성 메트릭** — **데이터 프로덕트는 내재적으로 시간적 데이터를 제공한다. 데이터의 시간적
모양을 나타내는 파라미터는 데이터의 적합성을 평가하는 데 도움이 된다** (13장,
p.240):[^dehghani2022]

| 메트릭 | 저자의 정의 |
|---|---|
| 에폭(epoch, 실제·처리) | 데이터가 가용한 가장 이른 실제 시간과 처리 시간. 데이터 사용자가 얼마나 과거로 시간 여행할 수 있는지를 가리키고 데이터 프로덕트의 데이터 보존 기간을 보여 준다 |
| 처리 구간(processing interval) | 데이터가 얼마나 자주 처리되는지 — 그런 패턴이 있다면. 특정 구간이 없으면 평균·최대·최소 구간 통계를 제공할 수 있다. 소비자가 얼마나 자주 새 데이터를 읽고 처리할 수 있는지 기대를 설정한다 |
| 마지막 처리 시간 | 가장 최근 데이터의 처리 시간 |
| 마지막 실제 시간(윈도우) | 가장 최근 데이터의 실제 시간(또는 윈도우) |
| 실제 윈도우(actual window) | 입력 데이터가 처리되고 새 데이터가 만들어지는 실제 시간의 윈도우 — 데이터가 시간 윈도우로 집계되는 경우 |
| 적시성(timeliness) | 실제 시간과 처리 시간이 벌어진 정도. 데이터가 적시일수록 실제 시간과 기록 시간의 간극이 작다. **앞 장에서 나는 이 성질에 스큐(skew)라는 용어를 썼다** |

- 시간성 메트릭이 [바이템포럴 데이터](../concepts/bitemporal-data.md)의 두 축을 **관측 가능한
  계약값**으로 바꾼 것이다 — 스큐가 여기서 발행되는 수치가 된다.

**⑤ 사용자 주도 메트릭** — **여기까지 언급한 모든 범주는 데이터 제공자인 데이터 프로덕트가
제공한다. 데이터 사용자는 흔히 데이터를 쓰는 동료 데이터 사용자의 경험에 근거해 신뢰를 세운다.
따라서 데이터 프로덕트는 소비자의 인식과 경험을 품질 메트릭 집합으로 포착하고 제시해야 한다.
예컨대 회사는 데이터 사용자가 자기 경험 — 이해와 사용의 리드 타임 단축, 데이터의 지각된 품질,
데이터 프로덕트 개발 팀의 응답성 등 — 에 근거해 데이터 프로덕트에 별점을 할당하는
**인정 시스템(recognition system)**을 개발할 수 있다** (13장, p.241).[^dehghani2022]

- 목록의 취지 — **나는 데이터 프로덕트가 데이터 처리의 흐름 속에서 바로 계산하고 포착해 소비자에게
  자율적으로 제공해 신뢰 수준을 높이기 가장 좋은 정보의 종류에 대한 감을 주려고 앞의 목록을
  제시했다** (13장, p.241).[^dehghani2022]
- 기존 도구 지형에 대한 판정 — **오늘날 지나치게 붐비는 메타데이터 관리 기술 지형이 데이터
  메시가 표면화하는 것을 정의하고 노출하려 시도한다. 데이터 메시 접근은 이 도구들에 불가지이며
  모든 데이터 프로덕트가 신뢰 메트릭을 일관되게 제공하고 관리하기를 기대한다** (13장,
  p.241).[^dehghani2022]
- 참조할 표준 둘 — **일관된 신뢰 메트릭 집합을 세우는 데 참고할 만한 주목할 과거 오픈소스 표준
  둘이 있다: Data on the Web Best Practices: Data Quality Vocabulary와, 관련해서 Data Catalog
  Vocabulary다. 그것들은 웹에서 열린 데이터 생태계를 제공하는 모범 관행을 세운다는 사명으로 일관된
  어휘를 만들려 시도했다** (13장, p.241).[^dehghani2022]

## 데이터의 모양을 탐색한다

- 왜 탐색이 별도 단계인가 — **데이터를 탐색하고 그 통계적으로 유의한 성질을 이해하는 것은 특정
  사용 사례에 대해 데이터를 배우고 신뢰하는 데 결정적이다. 데이터 메시는 데이터 탐색을 데이터
  사용자 여정의 결정적 단계로 인정한다 — **결국 그 데이터를 쓰지 않기로 선택하더라도**다** (13장,
  p.241).[^dehghani2022]
- 두 경우가 갈린다 — **데이터 사용자가 이미 데이터에 접근할 수 있는 시나리오에서는 데이터
  프로덕트의 출력 포트를 써서 개별 레코드를 탐색하는 여러 질의를 돌릴 수 있다. 그러나 개인이
  흔히 접근 부족 때문에 개별 레코드에 접근할 수 없는 많은 시나리오에서는, **데이터의 모양을
  탐색하고** 자기 특정 사용 사례에 적합한지 평가할 수 있어야 한다. 데이터 프로덕트는 소비자가
  개별 레코드를 처리하지 않고 데이터의 모양을 탐색하게 하는 정보를 제공할 책임이 있다** (13장,
  p.241).[^dehghani2022]
- 어떤 정보인가 — **예컨대 데이터 프로덕트의 발견 인터페이스는 데이터 필드의 분포·값 범위·값
  빈도·백분위수 등을 조사하는 함수를 포함할 수 있다. 예컨대 기존 **social media mentions**
  데이터 프로덕트가 추세 식별에 신뢰할 만한 소스인지 평가하려면, 발견 인터페이스가 "개별 언급
  소스의 분포"를 조사할 수 있다. 소수 집단만이 결과를 왜곡하는가, 아니면 신뢰성 있게 쓸 수 있는
  종 모양 분포가 있는가?** (13장, p.241).[^dehghani2022]
- 더 일반적 수단 — **더 일반적으로 데이터 프로덕트는 개별 민감 레코드에 대한 접근을 제공하지 않고
  다수의 탐색을 가능하게 하기 위해 **차등 프라이버시(differential privacy)**를 적용한 자기 데이터에
  대한 접근을 제공할 수 있다. 차등 프라이버시는 프라이버시를 개선하면서도 다량의 데이터에 유용한
  분석을 수행하는 능력을 유지하는 기법으로, 예컨대 데이터에 감내 가능한 잡음을 도입한다. "차등
  프라이버시는 대규모 데이터셋에서 통찰을 얻게 하되, 누구도 한 개인에 대해 알 수 없다는 수학적
  증명과 함께다"** (13장, p.242).[^dehghani2022] 각주는 Cynthia Dwork·Aaron Roth, "The
  Algorithmic Foundations of Differential Privacy" (2014)를 든다 (13장, p.242, 각주
  5).[^dehghani2022]
  - [위험 자산으로서의 데이터](../concepts/data-as-a-hazardous-asset.md)와
    [결정권으로서의 프라이버시](../concepts/privacy-as-a-decision-right.md)가 말하는 최소 노출이
    여기서 **탐색을 막지 않는 방식**으로 구현된다.

## 문서와 계산 노트북

- **사람이 읽을 수 있는 문서는 데이터 사용자가 데이터 프로덕트·그 포트의 구문·그 기저 데이터를
  이해하도록 돕는 놀랍도록 강력한 도구다. 가장 중요하게는 데이터 프로덕트 개발자가 **데이터
  이야기(data story)**를 하도록 돕는다** (13장, p.242).[^dehghani2022]
- 계산 노트북의 계보 — **원래 Wolfram Mathematica가 도입한 계산 노트북(computational notebooks)은
  과학 연구·탐색·교육 과정을 뒷받침하는 과학자들의 믿음직한 동반자였다. 최근에는 데이터 과학에서
  널리 쓰이고 있다. 그것들은 데이터를 탐색하는 단순하고·문서 기반이고·직관적이고·상호작용적인
  인터페이스를 제공한다** (13장, p.242).[^dehghani2022]
- 무엇에 쓰는가 — **데이터 프로덕트는 데이터가 어떻게 쓰일 수 있는지를 본질적으로 소통하고 그
  성질을 실제로 보여 주는 계산 노트북 집합을 제공하고 유지할 수 있다. 그것들은 사람이 읽을 수
  있는 문서·코드·데이터 시각화를 한자리에 결합해 데이터에 대한 설득력 있는 이야기를 한다. 추가로
  기저 플랫폼은 다른 이들이 표현한 데이터의 새로운 사용 방식을 포착하기 위해 데이터 사용자의
  계산 노트북 공유를 촉진할 수 있다** (13장, p.242).[^dehghani2022]
- **그리고 명확한 금지선을 긋는다** — **계산 노트북은 데이터 프로덕트에 대한 사용 사례를 문서화하고·
  교육하고·공유하는 훌륭한 방법이다. 그러나 나는 노트북의 **프로덕션 적용을 옹호하지 않는다**.
  그것들이 커지면 모듈화되고·테스트 가능하고·확장 가능한 코드를 만들 프로그래밍 지원의 결여가
  장수하는 프로덕션 코드로 유지하는 것을 어렵게 만든다** (13장, p.242).[^dehghani2022]

## 이 표면을 누가 구현하는가 — 사이드카

- 표준화가 요구된다 — **내가 이 절에서 나열한 발견 가능성 정보의 거의 전부가 모든 데이터
  프로덕트에 걸쳐 표준화되어야 메시와의 매끄러운 경험, 그리고 서로 다른 데이터 프로덕트 사이의
  공정한 평가와 비교가 가능해진다. 이는 플랫폼이 계산·포착·공유의 표준화된 접근을 제공하는 데
  긴밀히 관여해야 함을 함의한다** (13장, p.242).[^dehghani2022]
- 자리가 지정된다 — **그것을 위해 데이터 프로덕트 **사이드카**가 발견 가능성 능력으로 확장되기에
  가장 좋은 위치에 있다. 9장에서 회상하면, 데이터 프로덕트 사이드카는 데이터 퀀텀의 계산 맥락
  안에서 돌면서 모든 데이터 프로덕트에 걸쳐 표준화되려는 횡단 관심사를 책임지는, 플랫폼이 제공하는
  에이전트다** (13장, pp.242–243).[^dehghani2022]
- 그림 13-3이 사이드카가 노출하는 두 API 집합을 그린다 (13장, p.243):[^dehghani2022]
  - **데이터 프로덕트 발견** — `/documents` · `/explore` · `/metrics` · `/semantic`
  - **출력 포트 발견** — `/syntax` · `/metrics` · `/explore` · `/documents` · …
  - 그리고 데이터 프로덕트에서 **데이터 프로덕트·메시 경험 플레인**으로 향하는 **자기 등록**
    화살표가 그려진다.
  - 9장이 사이드카의 확장 대상으로 "발견 같은 다른 표준화된 기능"을 열어 둔 자리가 여기서
    현실화된다 —
    [데이터 프로덕트의 포트와 사이드카](../concepts/data-product-ports-and-sidecar.md).
- 13장 마무리 — **데이터 프로덕트는 데이터 사용자가 데이터를 신뢰하도록 알려진 것과 알려지지 않은
  것 사이의 간극을 메울 책임이 있다. 데이터의 발견·이해·신뢰·탐색은 데이터 프로덕트에서, 데이터
  프로덕트의 데이터 시맨틱·데이터 형식·사용 문서·통계적 성질·기대 품질·적시성 등의 메트릭에 대한
  정보를 공유하는 인터페이스와 행위의 의도적 설계와 함께 시작한다. 이 기본 기능과 메타데이터 공유가
  각 데이터 프로덕트에 지어지고 나면, 연결된 데이터 프로덕트의 메시를 검색하고·브라우즈하고·조사하고·
  의미를 얻는 더 정교하고 ML 기반인 발견 기능이 지어질 수 있다** (13장, p.252).[^dehghani2022]
