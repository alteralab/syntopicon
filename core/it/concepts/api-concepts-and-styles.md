## 인터페이스라는 낱말

- **application programming interface에서 인터페이스는 개체들이 서로 통신하는 상호작용 점을
  가리킨다.** 여기서 개체는 사람일 수도, 체계일 수도, 조직일 수도 있다
  (1장 §"What Is an API?", p.1).[^dynowski2025]
- **그래서 인터페이스는 소프트웨어만의 말이 아니다** — 저자들이 드는 일상의 예가 다섯이다
  (1장, p.2):[^dynowski2025]
  - **휴먼 인터페이스 장치(human interface device, HID)** — 사람이 다른 장치를 다루게 하는 장치.
    TV 리모컨과 컴퓨터 마우스.
  - **명령줄 인터페이스(command-line interface, CLI)** — 글줄로 명령을 받아 체계에 전달한다.
  - **그래픽 사용자 인터페이스(graphical user interface, GUI)** — 그림 아이콘으로 다루게 한다.
  - **채팅 인터페이스(chat interface)** — 대화하듯 주고받는 자리로 애플리케이션을 노출한다.
  - **뇌-컴퓨터 인터페이스(brain-computer interface, BCI)** — 뇌와 바깥 장치를 직접 잇는다.
    뇌-기계 인터페이스라고도 한다.
- **API가 사는 컴퓨터 체계도 여러 갈래다** (1장, p.3):[^dynowski2025]
  - **소프트웨어 라이브러리와 프레임워크** — 저자들이 드는 예는 자바 플랫폼 스탠더드 에디션과
    JDK, 그리고 파이썬 웹 프레임워크인 Flask다.
  - **운영체제** — POSIX(Portable Operating System Interface)는 IEEE 컴퓨터 학회가 정한 규격
    집합이고, 유닉스 계열을 비롯한 운영체제 사이의 호환을 보장하려고 API를 정의한다.
  - **네트워크 기반 애플리케이션** — 컴퓨터 네트워크 너머로 통신하는 쪽이고, 전형적으로는 웹
    서버가 내주고 웹 브라우저가 소비하는 **웹 API**다. 브라우저 없이도 돈다 — 명령줄 도구,
    모바일 앱, 데스크톱 앱이 그 예다.
- **어느 갈래든 API가 하는 일은 같다 — 체계의 복잡성을 인터페이스 뒤로 감춘다.** 쓰는 쪽은 API를
  **불투명 상자(opaque box)**로 다루고, 문서를 따라 입력을 주고 출력과 그 사이의 부수 효과를
  받는다 (1장, p.3).[^dynowski2025]

## 네트워크 기반 API의 규정

이 책이 다루는 범위를 정하는 한 문장이다 (1장 §"Network-Based APIs", p.3):[^dynowski2025]

> A *network-based API* is an interaction point that allows software to communicate over the
> network (typically, the internet).

- **저자들이 '웹 API'라는 좁은 말 대신 이 말을 고른 이유를 밝힌다.** 이 책이 다루는 API 대부분은
  웹 API 범주에 들고 웹 브라우저와 HTTP 같은 웹 기술을 쓰지만, **웹 API라는 말은 API를 웹 기반
  아키텍처와 기술로 좁힌다.** 그래서 더 넓은 말을 쓰고, 달리 밝히지 않는 한 이 책의 "API"는
  네트워크 기반 API를 뜻한다 (1장, p.3).[^dynowski2025]

## API 세 낱말의 해부

**저자들은 약어를 낱말 단위로 풀면서 두 낱말이 클라이언트와 서버 양쪽에 다 있다는 점을 짚는다**
(1장, pp.4–5).[^dynowski2025]

- **Application(애플리케이션)** — 그림에는 서버 쪽에만 적히지만 애플리케이션은 양쪽에 있다.
  서버 애플리케이션은 불투명 상자로 다룰 수 있다 — 입력이 들어가 바깥에서 대개 보이지 않는 변환을
  거쳐 기대한 출력이 나온다. 웹 API 맥락에서 서버 애플리케이션을 **백엔드**, 클라이언트
  애플리케이션을 **프런트엔드**라 부르고, 백엔드가 데이터를 내주면 프런트엔드가 소비한다.
- **Programming(프로그래밍)** — 컴퓨터에 할 일을 지시하는 것이다. 서버 애플리케이션이 내주는
  기능은 클라이언트 애플리케이션이 **프로그램하는 것**으로 볼 수 있다. 이 낱말도 그림에는 서버
  쪽에만 적히지만 프로그래밍은 양쪽에서 일어난다 — 개발자가 도구와 라이브러리로 프런트엔드와
  백엔드 양쪽에 기능을 구현한다.
- **Interface(인터페이스)** — 체계들이 통신하고 데이터를 주고받게 하는 것이고, **서버
  애플리케이션이 자기 기능을 클라이언트 애플리케이션에 노출하는 상호작용 점**이다.

## 같은 낱말을 넷으로 규정하는 쪽

**2022년 API 아키텍처 운영서가 같은 낱말에 다른 규정을 세운다.** 위 규정이 **어디서 일어나는가**
(네트워크 너머)를 잡는다면 이쪽은 **무엇을 갖춰야 API인가**를 잡는다.

- **저자들이 먼저 어려움을 인정한다** — **소프트웨어 아키텍처 분야에는 정의하기가 엄청나게 어려운
  용어가 한 줌 있고, 애플리케이션 프로그래밍 인터페이스(application programming interface)를
  뜻하는 API가 그 분류에 든다. 그 개념이 무려 80년 전에 처음 표면에 나왔기 때문이다.** 그리고
  일반화한다 — **상당한 기간 존재해 온 용어는 결국 과용되고 서로 다른 문제 공간에서 여러 뜻을
  갖게 된다** (서론 §"A Brief Introduction to APIs", p.xxiv).[^gough2022]
  - **위 [API의 계보](#api의-계보)가 1957년 EDSAC 서브루틴에서 시작한다는 것과 이 책의 "80년
    전"은 겨루지 않는다.** 이 책은 개념이 표면에 나온 시점을 어림으로 대고 근거를 대지 않는다.
    #hypothesis
- **저자들이 API를 뜻하는 것으로 여기는 것이 넷이다** (서론, p.xxv):[^gough2022]
  - **API는 밑에 깔린 구현의 추상을 나타낸다.**
  - **API는 타입을 들여오는 명세(specification)로 표현된다. 개발자는 그 명세를 이해할 수 있고,
    도구를 써서 여러 언어로 코드를 생성해 API 소비자(API를 소비하는 소프트웨어)를 구현할 수 있다.**
  - **API는 정보의 교환을 효과적으로 모델링하기 위해 정의된 의미론 또는 동작을 갖는다.**
  - **효과적인 API 설계는 업무 통합을 위해 고객이나 제3자에게로의 확장을 가능하게 한다.**
- **이 넷이 위 규정과 갈리는 자리** — 위 규정에는 **명세**도 **의미론**도 조건으로 들어 있지
  않다. **겨루지 않는다** — 위쪽은 **무엇을 API라 부를 것인가의 범위 설정**이고, 이쪽은 **잘 된
  API가 갖춘 것의 목록**에 가깝다. 특히 둘째 항목(명세)과 셋째 항목(의미론)은 같은 책이 뒤에서
  **명세가 모양만 전하고 의미론은 담지 않는다**고 적는 자리와 맞물린다 —
  [OpenAPI 명세를 쓰는 실무](openapi-specification-practice.md)가 그 자리다.

## 프로세스 안인가 밖인가

**같은 책이 API를 두 범주로 가르는 축을 세운다.** 위 일곱 스타일의 축과 다른 축이고, 이 KB에
없던 구분이다.

- **가르는 기준이 운영체제다** — **크게 보아 API는 그 호출이 프로세스 안(in process)이냐 프로세스
  밖(out of process)이냐에 따라 두 일반 범주로 나뉜다. 여기서 말하는 프로세스는 운영체제(OS)
  프로세스다** (서론, p.xxv).[^gough2022]
- **저자들이 드는 두 실물** (서론, p.xxv):[^gough2022]
  - **한 클래스에서 다른 클래스로의 자바 메서드 호출은 프로세스 안 API 호출이다** — **그 호출이
    호출이 이뤄진 바로 그 프로세스에 의해 처리되기 때문**이다.
  - **HTTP 라이브러리를 써서 외부의 REST 유사 API를 부르는 .NET 애플리케이션은 프로세스 밖 API
    호출이다** — **그 호출이 호출이 이뤄진 프로세스가 아닌 추가의 외부 프로세스에 의해 처리되기
    때문**이다.
- **프로세스 밖이라는 것의 귀결** — **전형적으로 프로세스 밖 API 호출은 데이터가 네트워크를
  가로지르는 것을 수반하고, 그 네트워크는 로컬 네트워크일 수도, 가상 사설 클라우드(VPC)
  네트워크일 수도, 인터넷일 수도 있다** (서론, p.xxv).[^gough2022]
  - **이 지점에서 위 [네트워크 기반 API의 규정](#네트워크-기반-api의-규정)과 두 규정이 만난다.**
    위 규정이 다루는 것이 이 책의 **프로세스 밖 API**다. **두 책은 서로를 호명하지 않는다.**
- **저자들이 자기 책의 사정거리를 그 축으로 긋는다** — **이 책은 후자 스타일의 API에 집중한다.
  다만 아키텍트는 흔히 프로세스 안 API를 프로세스 밖 API로 다시 모델링해야 하는 요건을 만난다**
  (서론, p.xxv).[^gough2022]
  - 요약에서 같은 말을 되풀이한다 — **API는 구현의 추상이고 프로세스 안이거나 밖일 수 있다.
    아키텍트는 흔히 프로세스 밖 API로 진화시키는 자리에 서게 되고, 그것이 이 책이 앞으로 보는
    곳이다** (서론 §"Summary", p.xxxv).[^gough2022]
- **이 구분이 한 체계의 도면에서 어떻게 보이는가**는
  [회의 시스템 사례 연구](conference-system-case-study.md)가 갖는다.

## 유료 다리 비유

**이 책이 스타일이라는 개념을 어디에 앉히는지가 이 비유에서 드러난다.** 두 도시를 잇는 다차로
유료 다리와 그 위를 지나는 트럭을 떠올리라고 한다 (1장, p.5):[^dynowski2025]

- **양 끝의 두 도시** — 클라이언트 애플리케이션과 서버 애플리케이션.
- **도시를 잇는 다리** — 데이터가 흐르는 네트워크.
- **트럭이 다리로 들어가는 톨게이트** — **API 스타일**이다.
- **화물을 실은 트럭** — 요청 또는 응답. **화물에 적힌 주소**는 API 엔드포인트다.
- **톨게이트의 검사** — 요청과 응답이 올바른 형식인지, 인가된 것인지를 검증한다.
- **다리 위의 교통 규칙** — 네트워크 프로토콜.
- **같은 비유로 동기와 비동기도 말할 수 있다** — 트럭이 화물을 내리고 **수령증을 기다리면 동기**,
  화물을 내리자마자 떠나고 **수령증은 나중에 다른 트럭이 실어 오면 비동기**다
  (1장, p.6).[^dynowski2025]

## 메시지

- **메시지는 보내는 쪽이 하나 또는 여럿의 받는 쪽에 보내는 이산 데이터 단위**(자기 완결
  레코드)이고, 보통 **적재물과 그 메시지를 서술하는 메타데이터**를 담는다. OSI 모델에서 이 낱말은
  응용 계층 프로토콜에 붙는다 (1장 §"Message", p.6).[^dynowski2025]
- **저자들이 드는 응용 계층 메시지 셋** (1장, pp.6–7):[^dynowski2025]
  - **HTTP** — POST 요청 한 건. 요청 줄 하나와 헤더 셋과 본문으로 되어 있다.
  - **XMPP** — XML로 인코딩된 메시지이고 XMPP 스트림의 일부다. **XML 속성이 메시지 메타데이터를
    서술하는 자리**로 쓰인다는 점을 저자들이 짚는다.
  - **MQTT** — 이진 메시지이고, 이 프로토콜에서는 메시지를 **패킷(packet)**이라 부른다. 고정
    헤더와 선택적 가변 헤더와 적재물로 되어 있다.

## 전송 방식 셋

- **전송 방식(transmission mode)은 통신 분야에서 온 말이고, 통신하는 당사자들 사이에서 데이터가
  어떻게 공유되는지를 서술한다.** 각 당사자는 **보냄·받음·동시에 보내고 받음** 셋 중 한 상태에
  있다. 이 어휘는 API의 것이 아니다 — 정보를 주고받아야 하는 체계라면 하드웨어든 소프트웨어든
  맞는 전송 방식을 구현한다 (1장 §"Transmission Modes", p.7).[^dynowski2025]
- **단방향(simplex)** — 데이터가 보내는 쪽에서 받는 쪽으로 한 방향으로만 흐른다. 라디오와 TV가
  그렇다 (1장, p.8).[^dynowski2025]
- **반이중(half-duplex, semi-duplex)** — 양방향이되 **동시에는 아니다**. 한 번에 한 방향으로만
  흐른다. 워키토키가 그 예이고, 그래서 양쪽이 "over"와 "out" 같은 어휘로 된 통신 규약을 지켜야
  한다 (1장, p.8).[^dynowski2025]
- **전이중(full-duplex, duplex)** — 양방향으로 **동시에** 흐른다. 전화가 그 예다 — 말하면서 동시에
  들린다 (1장, p.8).[^dynowski2025]
  - 저자들이 각주로 단서를 단다 — 동시 양방향 전송은 **이중 단방향(dual-simplex)**으로도 된다.
    전이중이 채널 하나를 쓰는 데 비해 이쪽은 **단방향 채널 둘**을 쓴다 (1장, p.8 각주 5).[^dynowski2025]

## 동기와 비동기 — 요청-응답 모델 밖으로

- **낱말의 뿌리에서 시작한다** — synchronous는 그리스어 *syn*("함께")과 *chronos*("시간")에서
  왔고, 그래서 **동기 통신은 조율된 타이밍을 요구하고 비동기 통신은 요구하지 않는다**
  (1장 §"Synchronous and Asynchronous Communication Types", p.9).[^dynowski2025]
- **그리고 저자들은 이 개념이 요청-응답 모델에 갇힌 것이 아니라고 못 박는다.** 통신 분야의 동기
  통신은 **공유 시계**를 끼고 있어서, 받는 쪽이 보내는 쪽이 정한 속도로 신호를 표본화하고 바르게
  해석할 수 있게 한다. 사람 쪽 예로는 전화 통화와 화상 대화가 동기이고 이메일과 게시판 글이
  비동기다 (1장, p.9).[^dynowski2025]
- **동기 요청-응답에서 보내는 쪽은 블록된다** — 응답이 올 때까지 다음 일을 시작할 수 없다. 그리고
  **성공의 선결 조건이 하나 붙는다 — 주고받는 동안 양쪽이 살아 있고 닿을 수 있어야 한다**
  (1장, p.9).[^dynowski2025]
- **비동기 요청-응답에서는 블록되지 않는다** — 보낸 뒤 다른 일을 하고, **통신이 일어나는 동안
  양쪽이 동시에 존재하지 않아도 된다** (1장, p.10).[^dynowski2025]
- **어느 쪽인지는 프로토콜이 정할 수도 있고 보내는 쪽이 고를 수도 있다.** 저자들이 드는 실물이
  HTTP다 — HTTP는 요청마다 응답이 있는 요청-응답 모델을 따르므로 클라이언트가 기본적으로 동기로
  통신한다고 짐작하기 쉽지만, **`fetch()`로 요청을 보내는 자바스크립트 클라이언트는 비동기로
  통신하고 같은 요청을 보내는 curl 클라이언트는 동기로 통신한다** (1장, p.10).[^dynowski2025]
  - **이 KB의 다른 소스들이 같은 갈림을 통신 스타일의 축으로 세운다** —
    [마이크로서비스 통신 스타일](../concepts/microservice-communication-styles.md)이 그 자리다.
    이 책은 그 축을 API 스타일마다 어느 쪽이 통상인가로 쓴다(아래 비교표).

## API의 계보

- **착상은 낱말보다 오래됐다.** API라는 말 자체는 1940년대에 기원하지만 **1960–70년대가 되어서야
  떠올랐다** (1장 §"History of APIs", p.10).[^dynowski2025]
- **1940년대, EDSAC** — 영국의 모리스 윌크스·데이비드 휠러·스탠리 길이 초기 컴퓨터 EDSAC을 위한
  모듈형 소프트웨어 라이브러리를 작업했고, 그 결과물인 **최초의 컴퓨터 프로그래밍 책**에
  **서브루틴을 계산 기계에 대한 표준화된 인터페이스로 쓰는 착상**이 담겼다. 2025년 저술 시점 용어로 옮기면
  그것이 API다 (1장, p.10):[^dynowski2025]

  > In order to be able to use a library subroutine, it is not necessary to have an exact
  > knowledge of how it is constructed or of the precise numerical process which it uses,
  > provided that there is available a concise specification of what it does and how it is to
  > be used…. For a subroutine to be useful for inclusion in a library it must be drafted in
  > a sufficiently general form so that it can be used in different contexts without the user
  > having to carry out internal modifications to it.

- **1968년, 낱말의 첫 등장** — 아이라 코튼과 프랭크 그레이토렉스가 "Data Structures and Techniques
  for Remote Computer Graphics"에서 **application program interface**(*program*에 -ing이 붙지
  않은 형태)를 썼다. 애플리케이션과 컴퓨터 체계 사이의 상호작용을 가리키는 말이었고, 그 체계는
  **하드웨어 독립적으로 설계되어 하드웨어가 바뀌어도 이 인터페이스는 그대로**라는 것이 논지였다
  (1장, p.12).[^dynowski2025]
- **1970–80년대** — 네트워크가 흔해지면서 **내 컴퓨터가 아닌 곳에 있는 라이브러리를 부르고 싶다**는
  요구가 생겼고, 그것이 원격 프로시저 호출이라는 착상으로 자랐다 (1장, p.12).[^dynowski2025]
- **1990년대, CORBA** — Object Management Group(OMG)이 정한 표준이다. **프로그래밍 언어에
  불가지**했고, 여러 체계에 흩어진 객체를 원격으로 부르고 연산할 수 있게 했다. 언어 사이의 객체
  상호작용은 CORBA 바인딩이 맡았고 객체는 **인터페이스 정의 언어(IDL)** 문법으로 서술됐다
  (1장, p.12).[^dynowski2025]
- **1993년, COM과 ABI의 구별** — 마이크로소프트의 Component Object Model은 CORBA와 비슷한 문제를
  다뤘으나 대상이 **애플리케이션 이진 인터페이스(ABI)를 쓰는 이진 프로그램**이었다. 저자들이 여기서
  경계를 하나 긋는다 — **API는 하드웨어 독립이고 소스 코드 수준(고수준)에서 접근을 정의하는 반면,
  ABI는 하드웨어 의존이고 기계어 수준(저수준)에서 루틴과 자료 구조에 어떻게 접근하는지를
  정의한다** (1장, p.12).[^dynowski2025]
- **1998년, SOAP** — 웹 서비스 사이에 XML 형식 메시지를 주고받는 프로토콜이다. 응용 계층
  프로토콜을 썼고 주로 HTTP였으며 SMTP는 드물었다. 받은 비판이 셋이다 — **메시지가 커서 장황하고,
  HTTP의 기능을 쓰지 않아 파싱이 느리고, 클라이언트와 서버가 어떻게 상호작용할지를 강제하는
  표준 상호작용 모델을 정의하지 않았다** (1장, p.12).[^dynowski2025]
- **2000년, REST** — 로이 토머스 필딩이 박사 논문 "Architectural Styles and the Design of
  Network-Based Software Architectures"에서 Representational State Transfer를 내놓으며
  **네트워크 기반 API라는 착상**을 서술했다 (1장, p.13).[^dynowski2025]

## API 명령

- **REST가 공개 인터넷에서 네트워크 기반 API의 채택을 도왔다면, 같은 흐름이 기업 안에도 있었다는
  것을 보여 준 문서가 API 명령(API mandate)이다.** 2002년 무렵 아마존의 제프 베조스가 직원들에게
  보낸 메모로 전해지고, 서비스 지향 아키텍처(SOA)의 맥락에서 쓰였다. 저자들이 2025년 저술 시점 용어로 다시
  적은 다섯 원칙이 이렇다 (1장 §"API Mandate", p.13):[^dynowski2025]
  1. 서비스의 데이터와 기능은 API를 통해 노출된다.
  2. 서비스는 오직 API로만 통신한다.
  3. 네트워크 기반 API 말고 다른 통신 수단은 허용되지 않는다.
  4. API는 맥락에 맞는 기술로 구현한다.
  5. API는 **공개 클라이언트에 외부화할 수 있게** 설계한다.
- **그리고 2010년대를 "API의 시대"로 부를 만하다고 적으며 연표를 하나 내놓는다** — REST(2000),
  웹훅(2007), WebSocket(2011), GraphQL(2015), gRPC(2015) (1장, p.13).[^dynowski2025]

## 왜 API인가

**저자들은 이 물음에 개인·개발자·조직 세 시점으로 답한다** (1장 §"Why APIs?",
pp.13–14).[^dynowski2025]

- **개인** — 조직이 찾는 것은 결국 자기 목표를 이루게 해 줄 특정한 기술이므로, 네트워크 기반
  애플리케이션을 다루는 개발자나 아키텍트라면 **API 기술에 투자할 만하다. 역할과 산업을 넘어
  이전되기 때문**이다 (1장, p.13).[^dynowski2025]
- **아키텍처** — API는 **컴포넌트를 가능한 한 독립적으로 만들고 관리하는 모듈 아키텍처**를
  떠받치고, **표준화된 인터페이스로 통신하게 해서 상호운용성을 돕는다.** 원한다면 이것이 SOA나
  마이크로서비스 아키텍처로의 이행을 가능하게 한다 (1장, p.14).[^dynowski2025]
- **조직** — 저자들이 드는 길이 셋이다 (1장, p.14):[^dynowski2025]
  - **새 수익원** — Skyscanner 같은 사이트는 **API 집계자**로 일한다. 항공사와 호텔의 제안을
    주로 API로 질의해 검색 가능하게 만들고, 그것이 항공사·호텔과 API 제공자 양쪽의 수익이 된다.
    저자들은 **Salesforce·eBay·Expedia 같은 회사가 낸 수익의 절반 이상을 API가 가져왔다고 보고된
    적이 있다**고 적으며 2015년 *Harvard Business Review* 글을 근거로 댄다.
  - **시장 도달** — Zoom은 웹사이트 말고도 스마트폰·태블릿·데스크톱·스마트 TV에서 쓸 수 있다.
    모바일 기기에 API를 여는 회사는 세계 인구의 큰 몫에 닿을 수 있다.
  - **최신 기술 접근** — 2021년 깃허브가 내놓은 GitHub Copilot은 수백만 코드 저장소로 훈련된
    GPT 모델에 기반했고, 코드 완성 도구에서 코딩 조수로 자랐다. **OpenAI가 모델 API를 공개했기
    때문에** 깃허브를 비롯한 회사들이 갱신된 모델에 접근할 수 있다.
  - 버전 조건: 2025년 저술 시점. 매출 비중 근거는 2015년 글이고, 제품과 모델 이름은 그 시점의 것이다.

## 접근 종류 셋

API를 가르는 축 가운데 하나가 **접근 종류(API access type)**다 (1장 §"Private, Public, and
Partner APIs", p.15):[^dynowski2025]

- **사설(private)** — **내부 API**라고도 한다. 조직 안에서 개발되고, 조직 단위들 사이에서 데이터를
  주고받는 것이 쓰임이다.
- **공개(public)** — 조직이 일반에 노출한다. 무료로 줄 수도 있고 소유한 조직이 수익화할 수도 있다.
  저자들이 드는 예는 Open-Meteo의 날씨 API로, **비상업 용도는 무료이고 상업 용도는 유료**다.
- **파트너(partner)** — 만든 조직과 그 조직의 파트너만 접근할 수 있다.

## API 스타일이란 무엇인가

- **저자들은 토목의 건축 양식에서 출발한다.** 건축 양식은 건물의 설계·기능·외관에 영향을 주는
  특성·기법·재료·구조와 지역적·문화적 힘의 집합이고, 대개 한 시기와 엮이며 그 특성을 요약하는
  고유한 이름을 갖는다 — 로마·그리스·르네상스·바로크·빅토리아·향토 같은 것들이다
  (1장 §"What Are API Styles?", p.15).[^dynowski2025]
- **그 사고를 소프트웨어와 API에 그대로 옮겨 정의를 내린다** (1장, p.15):[^dynowski2025]

  > we define an *API style* as a paradigm that uses patterns, practices, and protocols to
  > design, implement, and expose APIs

  - 그리고 건축 양식처럼 **API 스타일도 목적과 기능을 갖고 시간과 함께 왔다가 간다**고 덧붙인다.
- **정의에서 흥미로운 대목은 스타일이 특성들의 혼합이고 그중 일부가 지배한다는 것이다.** 저자들이
  드는 비유는 밴드다 — 드럼·베이스·기타·키보드·보컬 다섯으로 록·팝·레게를 만들 수 있고 팝록·펑크록·
  재즈펑크 같은 융합까지 낼 수 있지만, **밴드는 자기를 악기 구성이 아니라 지배적인 음악 장르로
  규정한다.** API 스타일도 같다 — 여러 스타일이 같은 악기(프로토콜·통신 유형·원칙·설계 제약)를
  쓰더라도 **스타일을 정하는 것은 가장 지배적인 특성들의 집합**이다 (1장, pp.15–16).[^dynowski2025]

## 일곱 스타일과 각각의 지배적 특성

**이 분류가 이 책의 뼈대다** — 이어지는 장들이 이 일곱을 하나씩 맡는다 (1장,
pp.16–17):[^dynowski2025]

- **REST/RESTful** — 필딩의 논문이 밝힌 **여섯 제약**을 따르는 API다. 저자들은 단서를 하나 단다 —
  **많은 API가 RESTful을 자칭하지만 실제로는 RESTful API 설계의 요건인 하이퍼미디어 링크를
  빼놓는다**는 것이고, 근거로 필딩의 2008년 글 "REST APIs Must Be Hypertext-Driven"을 댄다.
- **질의 기반(query-based)** — 지배적 특성은 **클라이언트가 원하는 모양으로 데이터를 돌려 달라고
  질의할 수 있다**는 것이다. 대표 기술은 GraphQL이고, 엔드포인트 하나를 노출하면 클라이언트가
  가져올 필드를 지정한 질의를 보낸다.
- **웹 피드(web feed)** — 지배적 특성은 **계속 갱신되는 콘텐츠를 구조화된 형식으로 전달**하는
  능력이다. 잘 알려진 것이 RSS와 Atom이고, 둘 다 데이터 구조화에 XML을 쓰고 응용 프로토콜로
  HTTP를 쓴다.
- **원격 프로시저 호출(RPC)** — 지배적 특성은 **원격 서버의 함수(프로시저)를 부르되 지역 실행처럼
  보이게 하는 것**이다. 클라이언트가 프로시저를 노출한 서버로 호출을 보내고 계산 결과가 되돌아온다.
  이 스타일에서 앞서 나간 기술(프레임워크)이 gRPC다.
- **콜백(callback)** — 지배적 특성은 **콜백 기제**다. 두 쪽이 있다 — 콜백을 만들고 다루는
  **목적지 체계**(메시지를 받는다)와 그 콜백을 부르는 **원천 체계**(메시지를 보낸다)다. 원천에서
  목적지로 가는 **모든 메시지는 확인 응답을 받을 것으로 기대된다.** 대표 기술은 웹훅이고, 저자들은
  경계를 하나 긋는다 — **웹훅은 콜백을 촉발하는 것이 이벤트라는 점에서 이벤트 기반 스타일을
  닮았으나, 메시지 브로커 같은 중개자를 거치지 않는다는 점이 다르다.** 이벤트가 나면 원천이 HTTP
  POST 요청으로 목적지에 알리기 때문에 흔히 **HTTP 콜백**이라 불린다.
- **양방향(bidirectional)** — 클라이언트와 서버가 **양쪽 방향으로 동시에** 데이터를 주고받게 하는
  스타일이다(위 전이중). WebSocket 프로토콜이나 gRPC 프레임워크로 지은 API가 여기 든다.
- **브로커 기반(broker-based)** — 메시지가 **브로커라는 중개자를 지난다**는 것이 특징이다. 여러
  프로토콜로 메시지를 전달하고, 저자들이 드는 브로커 기반 메시징 체계는 Apache ActiveMQ와
  Apache Kafka와 RabbitMQ다. 이 스타일의 전문은
  [브로커 기반 API 스타일과 RabbitMQ](broker-based-api-style-and-rabbitmq.md)에 있다.
- **gRPC가 두 칸에 걸린다는 점을 저자들이 명시한다** — RPC 스타일의 대표 기술이면서 전이중이라
  양방향 스타일에도 든다 (1장, p.17).[^dynowski2025]

## 여섯 축으로 맞댄 비교

**표 1-1을 옮긴 것이다** — 열이 스타일이고 행이 특성이다 (1장, p.18).[^dynowski2025]

| | RESTful | 질의 | 웹 피드 | RPC | 콜백 | 양방향 | 브로커 기반 |
|---|---|---|---|---|---|---|---|
| 기술 | REST | GraphQL | Atom | gRPC | 웹훅 | WebSocket | RabbitMQ |
| 프로토콜 | HTTP | HTTP | HTTP | HTTP/2 | HTTP | WebSocket | AMQP |
| 통신 유형 | 동기 | 동기 | 비동기 | 동기 | 비동기 | 비동기 | 비동기 |
| 이진 데이터 지원 | 예 | 부분 | 부분 | 예 | 예 | 예 | 예 |
| 응답성 | 중 | 중 | 중 | 고 | 중 | 고 | 고 |
| 개발 노력 | 중 | 중 | 저 | 고 | 저 | 중 | 고 |

- 표의 각주 하나: **GraphQL은 HTTP 말고 WebSocket 프로토콜도 쓸 수 있다** (1장, p.18).[^dynowski2025]
- **여섯 축이 무엇을 뜻하는지를 저자들이 정의한다** (1장, p.18):[^dynowski2025]
  - **기술** — 그 스타일을 구현하는 기술의 **한 예**다.
  - **프로토콜** — 그 기술이 쓰는 **주된** 네트워크 프로토콜이다.
  - **통신 유형** — 그 스타일에서 **가장 흔히 쓰이는** 통신 유형이고 동기와 비동기 둘 중 하나다.
  - **이진 데이터 지원** — 예는 기본 지원, 아니오는 미지원, **부분은 이진 인코딩이 되기는 하되
    이미지를 Base64 문자열로 인코딩하는 식의 애플리케이션 수준 구현이 필요하다**는 뜻이다.
  - **응답성** — "The Reactive Manifesto"가 정의한 대로 **제때 응답하는 능력**이고 저·중·고로 잰다.
  - **개발 노력** — **복잡도가 낮은 최소 기능 API를 짓는 데 드는 주관적 노력**이고 저·중·고로 잰다.
- **저자 자신이 이 표의 지위를 낮춰 적는다** — 기술 칸은 예시이고, 프로토콜 칸은 주된 것이며,
  통신 유형 칸은 가장 흔한 쓰임이고, 개발 노력 칸은 **주관적**이다 (1장, p.18).[^dynowski2025]
  - 버전 조건: 2025년 저술 시점. 기술 이름과 프로토콜 대응이 그 시점의 통상 쓰임이다.

## 같은 물음에 다섯으로 답하는 분류

- **저자들이 자기 분류가 유일하지 않다고 곁상자로 밝힌다** — 네트워크 기반 API를 가르는 다른 길이
  많고, 예로 *Continuous API Management*(O'Reilly, 2021)의 저자들은 API 스타일을 다섯으로 든다:
  **터널(tunnel)·자원(resource)·하이퍼미디어(hypermedia)·질의(query)·이벤트 기반(event-based)**
  이다 (1장, p.17).[^dynowski2025]
  - 이 KB는 그 책을 확인하지 않았다 — 위 다섯은 **이 책을 통한 2차 경유**다.

## 이 KB의 다른 스타일 목록들과 이 분류가 갈리는 자리

**이 KB의 판정이다 — 이 책이 다른 소스들을 인용하지 않으므로 대질은 이 KB가 세운 것이다.**

- **"스타일"이라는 낱말이 이 KB에서 최소 세 가지를 가리킨다.** 가르는 것은 **무엇을 축으로
  삼는가**다.
  - 이 페이지의 **API 스타일**은 **기술과 프로토콜의 지배적 특성**을 축으로 삼는다. 그래서
    RabbitMQ와 WebSocket과 Atom이 나란히 놓인다.
  - [마이크로서비스 통신 스타일](../concepts/microservice-communication-styles.md)의 축은
    **서비스들이 협업하는 방식**(요청-응답인가 이벤트 주도인가)과 **구현**(동기 블로킹인가 비동기
    논블로킹인가)이다. 기술 이름은 그 아래 칸에 놓인다.
  - [애플리케이션 통합의 네 가지 스타일](../concepts/application-integration-styles.md)의 축은
    **애플리케이션 사이로 무엇이 건너가는가**(파일·공유 데이터베이스·프로시저 호출·메시지)다.
- **그래서 세 목록은 경쟁하지 않는다.** 같은 기술이 세 목록에서 다른 칸에 앉는 것이 정상이다 —
  gRPC는 이 책에서 RPC이자 양방향이고, 통신 스타일 쪽에서는 요청-응답이며, 통합 스타일 쪽에서는
  원격 프로시저 호출이다. #hypothesis **세 축을 겹쳐 읽으면 한 기술을 고를 때 물어야 할 것이
  셋이 된다** — 무엇이 건너가는가, 어떻게 협업하는가, 어느 프로토콜 위인가.

## 접착제에서 제품으로

- **API 명령이 디지털 조직의 시각을 바꿨다고 저자들은 적는다** — **서비스를 잇는 접착제(API as
  glue)로 보던 것에서 매출에 영향을 주는 재무적 구성 요소로** 보는 쪽으로다. 그 전환은 조직이
  **API가 제품이라는 것**을 깨달은 뒤에 가능해졌다 (1장 §"API as a Product",
  p.19).[^dynowski2025]

## 수익화 모델 다섯

- **API에서 수익을 내는 것을 API 수익화(API monetization)라 부르고**, 저자들이 드는 모델이
  다섯이다 (1장 §"API Monetization", p.19):[^dynowski2025]
  - **사용량 과금(pay-per-use)** — 호출 수·주고받은 데이터량 같은 사용 지표로 잰다. 정확한
    청구가 되고 자기 필요를 모르는 사용자에게 매력적이지만, **정밀한 호출 추적 도구**가 필요하고
    사용자가 자기 비용을 보고 예측할 수 있어야 한다.
  - **구독(subscription)** — 월·연 단위 고정 요금. 수익이 예측 가능해지고, 월 호출 수 상향이나
    고급 기능 같은 제공과 자주 묶인다.
  - **프리미엄(freemium)** — 기본 기능은 무료, 고급 기능·높은 사용량·프리미엄 지원은 유료.
    **사용자 기반을 키울 수 있다는 가정**과 무료 사용자를 유료로 바꾼다는 전제 위에 선다.
  - **거래 수수료(transaction fee)** — API를 통한 거래마다 수수료를 매긴다. 전자상거래와 금융
    서비스 API에서 흔하다.
  - **수익 배분(revenue sharing)** — 서드파티 개발자와 API 제공자가 수익을 나눈다. 제휴 마케팅과
    마켓플레이스에서 흔하다.

## 제품으로 다룬다는 것

- **저자들이 먼저 진단을 놓는다 — 대부분의 조직은 API를 통합 기술로 취급한다.** 그 사고가 낳는
  것은 **범위와 확장성과 내구성 면에서 값이 제한된 API**, 곧 **과소 설계된 API**다. 문서가 부실하고
  설계 표준과 버저닝과 보안이 없거나 확장성이 뒤늦은 생각이 된다 (1장, p.20).[^dynowski2025]
- **제품처럼 다룬다는 것은 다른 자산과 같은 주의를 준다는 뜻이다.** 그렇게 개발된 API의 성공은
  마케팅이나 설계만이 아니라 **서드파티 개발자의 경험**에 뿌리를 둔다 — 그들의 필요에 답하면 채택이
  늘어난다. 저자들은 2025년 저술 시점 기준 최근 **개발자 포털**(Backstage·Clutch·Cortex를 예로 든다)이 인기를 얻었고 이런
  제품이 내부 API 발견과 관리를 돕는다고 적는다 (1장, p.20).[^dynowski2025]
  - 버전 조건: 2025년 저술 시점. 제품 이름과 그 인기 서술이 그 시점의 것이다.
- **제품 사고는 물음의 목록으로 나타난다** — API의 파워 유저는 누구인가, 요청은 어느 지역에서
  오는가, API가 어떤 오류를 내는가, 오류율은 얼마인가, 응답 시간은 얼마인가. 그래서 **API를
  모니터링하고 사용 보고서를 만드는 도구가 있어야 한다** (1장, p.20).[^dynowski2025]
- **그리고 공개는 유지보수 책임을 낳는다.** 공개 API는 **릴리스와 폐기 절차**(공지와 폐기 일정 같은
  것)를 따라야 하고, **API가 나간 뒤에는 과거의 실수를 되돌리기 어렵다.** 저자들이 드는 실물은
  메타(옛 페이스북)가 서드파티 개발자의 Groups API 접근을 끊기로 계획하고 알린 일이다
  (1장, p.20).[^dynowski2025]
  - 그 절차의 전문은 [API 수명 주기](api-lifecycle.md)의 은퇴 절과
    [계약을 깨는 변경의 관리](../concepts/managing-breaking-api-changes.md)에 있다.

## 저자들이 세는 앞날

- **기기 쪽** — Statista를 근거로 **2024년 연결된 IoT 기기 추정치가 180억**이고 그 안에
  **스마트폰 가입 72억**이 있어 세계 인구의 약 **67.1%**를 잇는다고 적는다. IoT 기기 수는 다음
  몇 해에 늘 것으로 보고, 그 기기들이 여러 기능에 네트워크 기반 API를 요구한다
  (1장 §"Future of APIs", p.37).[^dynowski2025]
- **트래픽 쪽** — CDN 제공자 Cloudflare의 2024년 API 보안 보고서를 근거로 **동적(캐시 불가)
  트래픽의 60%가 API 기반**이고 API가 **가장 빨리 자라는 트래픽 범주**라고 적는다
  (1장, p.38).[^dynowski2025]
- **AI 쪽** — LLM 훈련이 소비하는 텍스트·이미지·오디오·영상 데이터가 **대체로 API에서 오고**,
  회사들이 자기 LLM 기반 서비스를 만들면서 **데이터가 드나드는 깔때기로 기존과 새 API 스타일**이
  쓰인다. 또 AI가 수명 주기 각 단계(설계·문서화·구현·보안)를 도울 수 있어 API 수를 더 늘릴
  것이고, **요청·응답 예를 몇 개 주면 이미 AI가 API를 대강 프로그램해 볼 수 있다**고 적는다
  (1장, p.38).[^dynowski2025]
- **보안 쪽** — Gartner가 2021년에 **API 공격이 기업 웹 애플리케이션에 대한 가장 빈번한 공격
  벡터가 될 것**이라고 예측했고, Kong의 2023년 보고서는 **2027년까지 전 세계 API 공격 수가 두 배
  넘게 늘 것**으로 내다본다 (1장, p.38).[^dynowski2025]
- **프로토콜 쪽** — HTTP가 진화해 **2022년 6월 세 번째 릴리스(HTTP/3)에 이르렀고**,
  **WebTransport**는 WebSocket의 단점을 겨냥하며, **Model Context Protocol(MCP)**은 LLM과 에이전틱
  AI가 자원을 발견하고 쓰게 하는 것을 겨냥한다 (1장, p.38).[^dynowski2025]
  - 버전 조건: 2025년 저술 시점. 위 수치와 예측과 프로토콜 지형이 그 시점의 것이다.

## 둘째 소스 — 비동기 API를 두 범주로 가르고 명세의 공백을 짚는다

한 해 앞선 2022년 API 아키텍처 운영서가 마무리 장에서 **비동기 API를 두 범주로 가르고 그 쪽의
명세 공백을 짚는다** (10장 §"Async Communication", p.234).[^gough2022]

- **범주 둘** — **비동기 API는 아주 인기 있고 대체로 클라이언트-서버와 클라이언트-브로커 둘로
  떨어진다.** **클라이언트-서버 관계의 예는 gRPC 같은 기술로 이루어지고, 클라이언트-브로커 관계는
  카프카 같은 중간 기술로 이루어진다** (10장, p.234).[^gough2022]
  - **위 [전송 방식 셋](#전송-방식-셋)과 축이 다르다.** 그쪽은 **무엇으로 나르는가**를 가르고,
    이쪽은 **중간에 브로커가 있는가**를 가른다. **겨루지 않는다.**
  - **다만 이 소스가 gRPC를 비동기의 예로 드는 것이 위 [일곱 스타일과 각각의 지배적
    특성](#일곱-스타일과-각각의-지배적-특성)의 배치와 어긋나 보인다** — 그쪽은 gRPC를 요청-응답
    계열로 둔다. **모순으로 걸지 않는다**: 이 소스는 gRPC의 **스트리밍 쪽 쓰임**을 가리키는 것으로
    읽히고, 어느 쪽도 상대를 부정하는 문장을 쓰지 않는다. #hypothesis
- **명세의 공백** — **OpenAPI 명세가 REST API를 일관되게 서술하고 명세하는 데 결정적이었던 것과
  달리**, 비동기 쪽에는 **AsyncAPI가 비동기 API의 명세를 제공하는 흥미롭고 발전 중인
  표준**이라고 적는다 (10장, p.234).[^gough2022]
  - **그쪽이 짚는 난점 하나** — **비동기 기반 API의 도전 하나는 다양한 프로토콜 형식과 넓은 범위의
    기술을 지원하는 것**이다 (10장, p.234).[^gough2022]
  - **판정** — **이벤트 주도 아키텍처의 인기와 교환을 정의할 필요가 빠르게 자라는 공간이므로 확실히
    지켜볼 만하다** (10장, p.234).[^gough2022]
  - 버전 조건: 2022년 저술 시점. **이 책은 AsyncAPI의 판 번호도 채택 현황도 적지 않는다.**
