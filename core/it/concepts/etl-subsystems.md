ETL이 DW/BI 구축 노력의 불균형하게 큰 몫을 먹는데도 "그때그때 다르다(it
depends)"는 태도로 접근하면 테이블·스크립트·트리거가 뒤엉킨 스파게티가 된다.
수천 개 데이터 웨어하우스의 사후 경험에서 추출된 결론이, 거의 모든 차원
데이터 웨어하우스 백룸에 34개 서브시스템이 필요하다는 것이다 (19장,
pp.443, 449).[^kimball2013]

## 왜 이 4분류인가

- 34개는 나열 목록이 아니라 4개 국면의 전개다: **추출**(1–3) → **정제·통합**
  (4–8) → **전달**(9–21) → **관리**(22–34) (19장, pp.449–450).[^kimball2013]
- 분류의 축은 "어디서 가치가 더해지는가"다. 추출과 전달은 데이터를 옮기고
  적재할 뿐이고, 데이터 자체를 바꿔 조직의 가치를 높이는 곳은 정제·통합이다
  (19장, p.455).[^kimball2013]

> These are the steps where the ETL system adds value to the data. The other
> activities, extracting and delivering data, are obviously necessary, but
> they simply move and load the data.

- 그런데 개수(13개)와 규율의 중심은 전달에 있다 — 원천 구조와 정제 로직은
  천차만별이지만, 차원 구조로 내보내는 전달 기법은 잘 정의되고 규율돼 있어
  ETL 아키텍처에서 가장 중추적(pivotal)인 서브시스템들이다 (19장,
  p.463).[^kimball2013]
- 관리(13개)는 데이터가 아니라 ETL 환경 자체를 다룬다. 신뢰성(항상 완주)·
  가용성(SLA 준수)·관리 용이성(성장·변화 수용)이라는 운영 기준을 채우지
  못하면 좋은 모델도 의사결정 근거로 신뢰받지 못한다 (19장,
  p.483).[^kimball2013]

## 추출 (1–3): 운영계에서 독립된 사본을 확보

- 존재 이유: 원천 시스템과의 인터페이스를 이 그룹에 격리해, 이후 모든 처리가
  운영계와 무관하게 ETL 환경 안에서 이뤄지게 한다 (19장, p.450).[^kimball2013]
- 데이터 프로파일링(1)은 후보 원천의 go/no-go 판정과 "정제 기계를 얼마나
  동원할지"의 근거다 — 프로젝트 수개월 뒤에야 원천 부적합이 드러나는 사태를
  막는다 (19장, pp.450–451).[^kimball2013]
- 변경 데이터 캡처(change data capture, CDC)(2)는 전체 재적재가 불가능한
  규모에서 변경분만 이동하게 한다. 감사 컬럼·시각 기반 추출·전체 비교(diff)·
  로그 스크래핑·메시지 큐 감시 중 원천별로 골라야 하며, 시각 기반 추출은
  실패 재시작 시 중복·누락을 만들어 신뢰할 수 없다 (19장,
  pp.451–453).[^kimball2013]
  - 같은 판정이 스트리밍 쪽에서 실물로 나온다. 카프카의 JDBC 소스 커넥터는 **타임스탬프
    필드나 증가하는 기본 키로 테이블을 스캔해 새 레코드를 찾는데 이것이 상대적으로
    비효율적이고 때로는 부정확하다**고, 반면 **모든 관계형 데이터베이스가 가진 트랜잭션
    로그(리두 로그·빈로그·WAL)를 외부 시스템이 직접 읽는 쪽이 훨씬 정확하고 효율적이며
    그것이 변경 데이터 캡처**라고 못박는다. **대부분의 현대 ETL 시스템이 변경 데이터
    캡처를 데이터 소스로 쓰며**, 관계형 데이터베이스에서 카프카로 스트리밍한다면
    **디비지움(Debezium) 변경 캡처 커넥터가 강력히 권장**된다 (9장,
    p.220).[^shapira2021] 상세는 [카프카 커넥트](../concepts/kafka-connect.md).
    - #hypothesis 그쪽이 권하는 트랜잭션 로그 직독은 위 다섯 방법 중 **로그 스크래핑**에,
      JDBC 커넥터의 타임스탬프 스캔은 **시각 기반 추출**에 대응한다.
- 원천이 변경 이력을 주지 않을 때 이력을 만들어 내는 도구 쪽 장치가 dbt의
  스냅샷이다. 변경 탐지는 갱신 시각 컬럼을 보는 방식과 지정 컬럼 값을 이력과
  비교하는 방식 둘이다 (snapshots.md, "Detecting row
  changes").[^dbtlabs2026-materialization] 상세는
  [dbt 스냅샷](../concepts/dbt-snapshots.md).
  - #hypothesis 이 둘은 위 다섯 방법 중 감사 컬럼과 전체 비교(diff)에 각각
    대응한다.

## 정제·통합 (4–8): 데이터를 바꿔 가치를 더한다

- 품질 스크린(quality screen)(4)이 이 그룹의 심장이다. 파이프라인 곳곳의
  진단 필터로, 실패 시 중단/격리(suspense)/태깅 중 하나를 택하는데 가급적
  **태깅 후 통과**가 최선이다 — 격리 파일은 언제 복귀할지 불명확해 DB
  무결성을 의심스럽게 만든다 (19장, pp.457–458).[^kimball2013]
  - 스트리밍 쪽의 대응물은 커넥트의 `error.tolerance`다 — 손상 메시지를 **조용히 버리거나
    데드 레터 큐 토픽으로 라우팅**하는 두 선택지를 준다 (9장, p.225).[^shapira2021] 상세는
    [단일 메시지 변환(SMT)](../concepts/kafka-single-message-transformations.md).
    - #hypothesis 데드 레터 큐는 여기서 말하는 중단·격리·태깅 셋 중 **격리**에 해당하고,
      **태깅에 해당하는 선택지는 커넥트 쪽에 없다.**
- 오류 이벤트 스키마(5)는 모든 스크린 오류를 팩트 테이블(입도 = 오류 1건 =
  1행)로 중앙 기록하는 차원 모델이고, 감사 차원(audit dimension)(6)은 팩트
  행이 만들어진 순간의 메타데이터 맥락(품질 등급·ETL 버전 등)을 차원으로
  붙인다 — 메타데이터를 실데이터로 승격시키는 장치다 (19장,
  pp.458–460).[^kimball2013]
- 중복 제거·생존(survivorship)(7)과 통합(conforming)(8)이 여러 원천의
  고객·제품을 conformed dimension으로 합친다. 드릴 어크로스 통합이 여기서
  결정된다 (19장, pp.460–463).[^kimball2013]
  ([Kimball DW/BI 아키텍처](../concepts/kimball-dwbi-architecture.md)의 버스
  아키텍처가 요구하는 바로 그 작업이다.)

## 전달 (9–21): 차원 구조로의 규율된 인도

- 13개 중 다수가 [차원 테이블](../concepts/dimension-table.md) 처리에 몰려
  있다 — 차원이 팩트보다 작아도 팩트로 들어가는 진입점이기 때문이다 (19장,
  p.463).[^kimball2013]
- 핵심만 이름을 남기면:
  - **SCD 처리기**(9): 느리게 변하는 차원(slowly changing dimension) 변경을
    타입 1(덮어쓰기)·타입 2(새 행 추가)·타입 3(새 컬럼) 등으로 체계적으로
    처리하고, 타입 2의 유효 시작/종료 시각 등 하우스키핑 컬럼을 유지한다
    (19장, pp.464–467).[^kimball2013] 이론 지형은
    [완만하게 변하는 차원(SCD)](../concepts/slowly-changing-dimension.md), 도구
    구현 한 사례는 [dbt 스냅샷](../concepts/dbt-snapshots.md).
  - **대리 키 생성기**(10): 의미 없는 정수 키를 차원마다 독립 생성한다. 운영
    키+시각 연결(concatenation) 같은 편법은 확장에서 반드시 무너진다 (19장,
    pp.469–470).[^kimball2013]
  - **팩트 테이블 빌더**(13): 트랜잭션·주기 스냅샷·누적 스냅샷 세 유형별
    적재 로직 (19장, pp.473–475).[^kimball2013]
  - **대리 키 파이프라인**(14): 적재 직전 팩트 행의 자연 키를 현재 대리
    키로 치환한다. 이 치환이 곧 참조 무결성의 보증이다 — 차원을 항상 먼저
    갱신해 차원 테이블이 키의 정본이 되게 한다 (19장,
    pp.475–477).[^kimball2013]
  - **지각 도착 데이터 처리기**(16): [지각 도착 데이터](../concepts/late-arriving-data.md)
    참조 (19장, pp.478–479).[^kimball2013]
  - **차원 관리자·팩트 제공자**(17·18): conformed dimension을 중앙(관리자)이
    발급·버전 관리하고, 각 팩트 테이블 소유자(제공자)가 수신해 키 맵과
    집계를 갱신하는 발행-구독 분업 (19장, pp.479–481).[^kimball2013]
  - **집계 빌더**(19): 집계는 인덱스처럼 성능을 위한 파생 구조이며, 기반
    데이터와 항상 일치해야 한다 — 불일치하면 팩트 제공자가 내려야 한다
    (19장, p.481).[^kimball2013]

## 관리 (22–34): ETL을 운영 시스템으로 만든다

- 잡 스케줄러(22)는 시간표가 아니라 잡 간 의존 관계의 통제이고, 워크플로
  모니터(27)는 병목 분석의 출발점이다 (19장, pp.483–484, 489).[^kimball2013]
- 백업(23)·복구/재시작(24): 팩트 테이블에 순차 부여한 단일 컬럼 대리 키가
  있으면 중단된 적재를 키 범위로 재개하거나 되돌릴 수 있다 (19장,
  p.487).[^kimball2013]
- 계보/의존 분석기(29)와 컴플라이언스 관리자(33): 규제 환경에서는 데이터의
  "관리 연속성(chain of custody)"을 지켜야 하므로 모든 변경이 삽입이 된다 —
  타입 1·3처럼 이력을 지우는 갱신은 쓸 수 없다 (19장,
  pp.490–494).[^kimball2013]
- 버전 관리(25)·버전 이관(26)·메타데이터 저장소(34)가 ETL 로직 자체의
  이력·배포·문서화를 맡는다 (19장, pp.488, 495–496).[^kimball2013]

20장은 이 34개를 실제로 구현하는 10단계 프로세스다: 상위 계획 →
도구 선정 → 기본 전략 → 테이블별 상세 → 차원 이력 적재 → 팩트 이력 적재 →
차원 증분 → 팩트 증분 → 집계/OLAP → 운영 자동화. 이력 적재는 사람이 중간에
멈춰 확인해도 되지만 **증분 처리는 완전 자동화**여야 한다는 것이 두 국면의
경계다 (20장, pp.498–519, 특히 pp.515–516).[^kimball2013]

## ETL이라는 말이 가리키는 범위가 넓어졌다

Kimball의 34 서브시스템은 **차원 웨어하우스 백룸**을 전제한 분해다. 다른 소스는
같은 낱말을 더 넓은 범위에 쓴다.

- 추출한 데이터를 분석 친화적 스키마로 **변환한 뒤 적재**하는 것이 ETL이고,
  **변환과 적재의 순서를 바꿔 적재 후 웨어하우스 안에서 변환**하면 ELT다 (1장,
  p.7).[^kleppmann2026]
  - 세 번째 소스가 같은 두 낱말을 **파이프라인 쪽에서** 정의한다. ETL은 **데이터가
    지나가는 동안 데이터에 대한 수정을 데이터 파이프라인이 책임진다**는 뜻이고, ELT는
    **파이프라인이 최소한의 변환(대부분 데이터 타입 변환)만 해서 타깃에 도착하는 데이터가
    원천 데이터와 가능한 한 비슷하게** 만드는 것이다 (9장, p.207).[^shapira2021] 순서는
    같지만 **판단 근거가 다르다** — 여기 34 서브시스템과 Kleppmann은 웨어하우스 적재의
    순서 문제로 보고, 그쪽은 **파이프라인이 하류에서 무엇을 지워 버리는가**의 문제로 본다.
    ETL의 주된 단점을 **파이프라인에서 일어난 변환이 하류에서 데이터를 더 처리하려는
    사람들의 손을 묶는다**는 데 두고, ELT의 단점으로는 **변환이 타깃의 CPU·저장 자원을
    쓰며 그 시스템이 비싸면 계산을 밖으로 옮기려는 강한 동기가 생긴다**는 비용 항을 든다
    (9장, p.207).[^shapira2021] 상세는
    [데이터 파이프라인 설계 고려사항](../concepts/kafka-data-pipeline-considerations.md).
  - 도구 지형에 대한 판정도 붙는다 — **인포매티카·탈렌드·펜타호·아파치 나이파이·스트림셋
    같은 GUI 기반 ETL 도구는 대개 복잡한 워크플로를 위해 만들어져 있어 단지 데이터를 넣고
    빼려는 것뿐이면 무겁고 번거로운 해법**이며, 저자들은 **데이터 통합이 모든 조건에서
    메시지를 충실히 전달하는 데 집중해야 하는데 대부분의 ETL 도구는 불필요한 복잡성을
    더한다**고 보고 **카프카가 데이터 저장소만 통합하는 ETL 도구의 유효한 대체재가 될 수
    있다**고 말한다 (9장, pp.229–230).[^shapira2021]
- 원천이 사내 데이터베이스가 아니라 CRM·이메일 마케팅·신용카드 처리 같은 외부
  SaaS 제품일 때가 있다. 원본 데이터베이스에 직접 접근할 수 없고 벤더 API로만
  접근할 수 있어서, SaaS API용 ETL은 Fivetran·Singer·Airbyte 같은 전문 데이터
  커넥터 서비스가 구현하는 일이 많다 (1장, p.8).[^kleppmann2026]
- ETL 프로세스는 **데이터 파이프라인(data pipeline)** 으로 일반화됐고, 어떤
  경우에는 [데이터 레이크](../concepts/data-lake.md)가 운영계에서 웨어하우스로
  가는 경로의 중간 기착지가 됐다 (1장, p.10).[^kleppmann2026]
- 방향도 한쪽만은 아니다. 분석 시스템의 산출물을 운영계로 되돌리는 것을 리버스
  ETL(reverse ETL)이라 부르기도 한다 — 분석 시스템에서 학습한 ML 모델을
  프로덕션에 배포해 최종 사용자에게 추천을 내보내는 것이 예이며 TFX·Kubeflow·MLflow
  같은 도구를 쓴다 (1장, p.10).[^kleppmann2026]
- 클라우드에서는 ETL이 통합 문제의 일부일 뿐이다. **운영 쪽 클라우드 서비스들도
  서로 통합돼야 하는데 현재로서는 이를 돕는 표준이 없어 상당한 수작업이 드는
  경우가 많다** (1장, p.18).[^kleppmann2026]
  ([클라우드와 자체 호스팅](../concepts/cloud-versus-self-hosting.md))
- **반대편 처방**: 위의 "가치는 정제·통합에서 더해진다"와 정규화 구조를 사용자
  질의에서 차단하라는 Kimball의 요구는, 원시 데이터를 변환하지 않고 담아 두고
  소비자마다 자기에게 맞게 변환하라는 스시 원칙("raw data is better")과 정면으로
  어긋난다 (1장, p.10).[^kleppmann2026] 변환을 적재 전에 두느냐 후에 두느냐의
  기본값 차이이고, 소비자가 알려져 있고 안정적이면 전자가, 소비자가 다양하고
  요구가 변하면 후자가 유리한 **방법론 트레이드오프**다. 어느 쪽이 참인지의 문제가
  아니라 상황이 고르는 문제라 `contradicts`는 달지 않는다(PLAN §2.1) — 선택
  기준은 [데이터 시스템 아키텍처 트레이드오프](../synthesis/data-systems-architecture-tradeoffs.md)가
  담당한다. 상세는 [데이터 레이크](../concepts/data-lake.md). 참고로
  [데이터 품질 관리](../concepts/data-quality-management.md)의 "나쁜 데이터의
  가치"는 원천 보존 쪽에 선다.

- 변환 도구는 적재 전/후라는 순서만이 아니라 **결과를 어떤 물리 형태로 남길지**도
  선언 항목으로 만든다 — 뷰·테이블·증분·임시·구체화 뷰가 그 축이다
  (materializations.md, "Overview").[^dbtlabs2026-materialization] 상세는
  [구체화 스펙트럼](../concepts/materialization-spectrum.md)과
  [증분 처리와 그 대가](../concepts/incremental-processing-tradeoffs.md).
