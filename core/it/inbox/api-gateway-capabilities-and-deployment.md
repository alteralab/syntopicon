하나의 질문: **API 게이트웨이란 무엇이고 무엇을 해 주며 체계의 어디에 놓이는가.**

## 버전 조건

> **버전 조건**: 2022년 저술 시점. 아래에 이름으로 드는 제품과 회사(F5·Citrix·Cisco·
> Apache Web Server·Netscape Navigator·HAProxy·NGINX·ModSecurity·Twilio·Google Ads API·
> Stripe·PayPal·Mashape·Kong·OpenResty·WSO2·Apigee·3Scale·Zuul·Spring Cloud Gateway·
> Docker·Kubernetes·Envoy·Ambassador Edge Stack·CNCF Emissary-ingress·Contour·Gloo Edge·
> Traefik·Tyk·Axway)와 그 제품이 무엇을 지원하며 누가 무엇을 언제 내놓았는가의 서술은
> 그 시점의 것이고, **이 KB는 어느 제품의 문서도 원전으로 확인하지 않았다.** 게이트웨이의
> 규정과 기능의 갈래와 배치의 모양은 제품과 무관하다.

## 이 페이지가 담는 것과 담지 않는 것

- **이 장이 여는 물음이 셋이라고 저자들이 미리 적는다** — API 게이트웨이의 **왜와 무엇과
  어디**를 배우고, 게이트웨이와 다른 엣지 기술의 역사를 살피고, 게이트웨이의 분류와 그것이
  더 큰 아키텍처와 배포 모형에 어떻게 들어맞는지를 본다는 것이다 (3장, p.55).[^gough2022]
- **이 페이지는 그 셋만 담는다.** 같은 장의 나머지 — 게이트웨이가 무너지는 방식과 함정 셋과
  고르는 절차 — 는 [API 게이트웨이의 함정과 선택](api-gateway-pitfalls-and-selection.md)이
  갖는다. 이 장의 회의 시스템 시연은
  [회의 시스템 사례 연구](conference-system-case-study.md)가 갖는다.
- **남북 트래픽과 동서 트래픽이라는 어휘 자체의 자리는 여기가 아니다.** 같은 책 서론이 그
  어휘를 애플리케이션 층위에서 쓴다고 밝힌 대목을 포함해
  [API 게이트웨이와 서비스 메시](api-gateway-and-service-mesh.md)가 소유한다.

## 게이트웨이만이 답은 아니다

- **저자들이 이 장을 자주 받은 물음으로 연다** — **"사용자 트래픽을 백엔드 체계로 보내는 데
  API 게이트웨이가 유일한 해법인가"**이고, 짧은 답은 **아니오**다 (3장 §"Is an API Gateway
  the Only Solution?", p.55).[^gough2022]
- **인그레스(ingress)라는 문제가 먼저 있다** — 많은 소프트웨어 체계가 **소비자의 API 요청,
  곧 바깥 출처에서 온 인그레스 트래픽을 내부 백엔드 애플리케이션으로 라우팅해야** 한다.
  웹 기반 체계에서 그 요청은 흔히 **최종 사용자가 웹 브라우저나 모바일 앱으로 백엔드와
  상호작용하면서** 생기고, **인터넷 어딘가에 배포된 애플리케이션을 통해 API를 부르는 바깥
  체계(흔히 서드파티)**에서 올 수도 있다 (3장, p.55).[^gough2022]
- **그 해법에 요구되는 것이 라우팅만이 아니다** — URL에서 백엔드 체계로 트래픽을 보내는 기제에
  더해, 인그레스를 제공하는 해법은 전형적으로 **신뢰성과 관측 가능성과 보안**도 제공해야 한다
  (3장, p.55).[^gough2022]
- **그러므로 대안이 있다** — 저자들은 **단순한 프록시나 로드 밸런서 구현을 쓸 수 있다**고
  적는다. 그러면서도 게이트웨이가 **특히 엔터프라이즈 맥락에서 가장 흔히 쓰이는 해법**이라고
  믿으며, **소비자와 제공자의 수가 늘어날수록 흔히 가장 확장 가능하고 유지보수 가능하고
  안전한 선택지**라고 적는다 (3장, p.56).[^gough2022]
  - **이것이 채점이지 측정이 아니다.** 수치가 없고 근거로 드는 것이 저자들의 믿음이다.

## 셋을 맞댄 기능표

**저자들이 리버스 프록시와 로드 밸런서와 API 게이트웨이를 열 기능으로 맞댄다** (3장, 표 3-1,
p.56).[^gough2022] 원문 표의 별표를 이 표에서는 `제공`으로 옮겼고 빈 칸은 그대로 두었다.

| 기능 | 리버스 프록시 | 로드 밸런서 | API 게이트웨이 |
|---|---|---|---|
| 단일 백엔드 | 제공 | 제공 | 제공 |
| TLS/SSL | 제공 | 제공 | 제공 |
| 다중 백엔드 | | 제공 | 제공 |
| 서비스 디스커버리 | | 제공 | 제공 |
| API 조합 | | | 제공 |
| 인가 | | | 제공 |
| 재시도 로직 | | | 제공 |
| 속도 제한 | | | 제공 |
| 로깅과 추적 | | | 제공 |
| 회로 차단 | | | 제공 |

- **표를 읽는 방식이 본문에 적혀 있다** — 현재의 요구를 각 해법의 능력에 맞추라는 것이고,
  저자들은 **요구를 전부 이해하지 못해도 괜찮다**고 덧붙인다. 장 전체가 그것을 가르치기
  때문이다 (3장, p.56).[^gough2022]
- **이 표가 이 KB에 없던 것이다.** 이 KB는 회로 차단과 재시도와 속도 제한을
  [안정성 패턴](../concepts/stability-patterns.md)이 소유하고 서비스 디스커버리를
  [서비스 디스커버리와 로드 밸런싱](../concepts/service-discovery-and-load-balancing.md)이 소유하는데,
  **그 기제들을 어느 인프라 층이 떠맡는가**를 한 표로 가르는 소스가 없었다.
- **표에 딸린 ADR 지침** (3장 §"Guideline: Proxy, Load Balancer, or API Gateway", 표 3-2,
  p.56):[^gough2022]
  - **결정** — 인그레스 트래픽 라우팅에 프록시를 쓸 것인가 로드 밸런서를 쓸 것인가 API
    게이트웨이를 쓸 것인가.
  - **논의할 점** — 단일 엔드포인트에서 단일 백엔드 서비스로 가는 단순 라우팅을 원하는가.
    인증·인가·속도 제한 같은 더 앞선 기능을 요구하는 비기능 요건이 있는가. API 키와 토큰이나
    수익화와 차지백 같은 API 관리 기능이 필요한가. 이미 자리 잡은 해법이 있거나, 모든
    트래픽이 네트워크 테두리의 특정 구성 요소를 지나야 한다는 조직 전체의 명령이 있는가.
  - **권고** — **언제나 요구에 맞는 가장 단순한 해법을 쓰되 가까운 미래와 이미 아는 요구를
    함께 본다.** 앞선 비기능 요건이 있으면 API 게이트웨이가 흔히 최선이다. 조직이
    엔터프라이즈라면 **API 관리(APIM) 기능을 지원하는 게이트웨이**를 권한다. 기존 명령과
    해법과 구성 요소에 대해 언제나 조직 안에서 실사를 수행하라.
  - 이 형식이 무엇이고 이 책이 그것을 어떻게 쓰는지는
    [아키텍처 결정 기록](architecture-decision-records.md)에 있다.

## 무엇인가 — 규정과 두 평면

- **규정 한 문장** (3장 §"What Is an API Gateway?", p.58):[^gough2022]

  > In a nutshell, an API gateway is a management tool that sits at the edge of a system
  > between a consumer and a collection of backend services and acts as a single point of
  > entry for a defined group of APIs.

  - **소비자가 무엇일 수 있는지도 같은 자리에 적힌다** — 단일 페이지 웹 애플리케이션이나
    모바일 앱 같은 **최종 사용자 애플리케이션이나 기기**, **다른 내부 체계**, 또는 **서드파티
    애플리케이션이나 체계**다 (3장, p.58).[^gough2022]
  - **"정해진 API 묶음"이라는 한정이 이 규정의 무게중심이다.** 게이트웨이는 체계 전부의
    입구가 아니라 **경계가 그어진 API 묶음 하나의 입구**다. 아래
    [어디에 놓이는가](#어디에-놓이는가)가 그 묶음이 조직 규모에 따라 어떻게 갈리는지를 적는다.
- **구성 요소가 둘이다** — API 게이트웨이는 **제어 평면(control plane)과 데이터 평면(data
  plane)이라는 두 개의 고수준 기본 구성 요소로 구현된다.** 그 둘은 **함께 묶여 제공될 수도
  있고 따로 배포될 수도 있다** (3장, p.58).[^gough2022]
  - **제어 평면은 운영자가 게이트웨이와 상호작용하며 경로와 정책과 필요한 원격 측정을
    정의하는 자리**다 (3장, p.58).[^gough2022]
  - **데이터 평면은 제어 평면에서 지정된 모든 작업이 실제로 일어나는 자리**다 — 네트워크
    패킷이 라우팅되고 정책이 집행되고 원격 측정이 방출된다 (3장, p.58).[^gough2022]
  - **이 KB에 제어 평면이라는 낱말이 이미 있다.**
    [API 게이트웨이와 서비스 메시](api-gateway-and-service-mesh.md)가 서비스 메시의 제어
    평면을 갖고 있다. **겨루지 않는다** — 그쪽은 지역 프록시들 위에 앉는 층이고 이쪽은 같은
    구조를 게이트웨이에도 적용한 것이며, 양쪽 모두 **설정하는 자리와 트래픽이 지나는 자리를
    가르는** 같은 분할이다. **두 서술을 잇는 것은 이 KB의 읽기이고 이 책이 메시의 제어 평면을
    여기서 호명하지 않는다.** #hypothesis

## 프록시와 포워드 프록시와 리버스 프록시

**이 절은 저자들이 곁상자로 따로 세운 자리이고 목차에 없다** (3장, p.58).[^gough2022]

- **프록시 서버(proxy server), 때로 포워드 프록시(forward proxy)라 불리는 것은 여러
  클라이언트에서 온 콘텐츠 요청을 인터넷 너머의 다른 서버들로 전달하는 중개 서버**다
  (3장, p.58).[^gough2022]
- **리버스 프록시 서버(reverse proxy server)는 전형적으로 사설 네트워크의 방화벽 뒤에 앉아
  클라이언트 요청을 알맞은 백엔드 서버로 라우팅하는 프록시 서버의 한 종류**다 (3장,
  p.58).[^gough2022]
- **둘을 가르는 문장이 목적이다** (3장, p.58):[^gough2022]

  > A forward proxy is used to protect clients. […] A reverse proxy is designed to protect
  > servers.

  - 저자들이 드는 포워드 프록시의 예가 **직원 트래픽을 공개 인터넷으로 라우팅하고 걸러 내는
    사내 프록시**다 (3장, p.58).[^gough2022]
- **이 대비가 이 KB에 없던 것이다.** [HTTP 중개자](../concepts/http-intermediaries.md)는 RFC 9110을 따라
  **누가 고르는가**(프록시는 클라이언트가 고른다)와 **무엇으로 보이는가**(게이트웨이는
  아웃바운드 연결에서 원 서버로 행동한다)로 둘을 가른다. **겨루지 않는다** — 규범 문서는
  프로토콜 역할을 가르고 이 책은 **무엇을 지키려는 배치인가**를 가른다. 그쪽 페이지에 이
  대비를 적어 두었다.

## 무슨 기능을 주는가

- **네트워크 수준의 노릇** — API 게이트웨이는 전형적으로 **리버스 프록시로 행동해** 소비자의
  API 요청을 전부 받고, 그것을 채우는 데 필요한 여러 애플리케이션 수준 백엔드 서비스(그리고
  경우에 따라 외부 서비스)를 **부르고 집계해** 알맞은 결과를 돌려준다 (3장 §"What
  Functionality Does an API Gateway Provide?", p.58).[^gough2022]
- **그 위에 얹히는 횡단 요건** — **사용자 인증, 요청 속도 제한, 시간 초과와 재시도**이고,
  체계 안의 관측 가능성 구현을 떠받치기 위한 **지표와 로그와 추적 데이터**를 줄 수 있다
  (3장, p.58).[^gough2022]
- **많은 게이트웨이가 더 얹는 것** — 개발자가 **API의 수명 주기를 관리**하게 하고, API를 쓰는
  **개발자의 온보딩과 관리**를 돕고(개발자 포털과 그에 딸린 계정 관리와 접근 통제 같은 것),
  **엔터프라이즈 거버넌스**를 제공한다 (3장, p.58).[^gough2022]
  - **이 목록이 이 KB의 기존 게이트웨이 서술과 겹치되 넓다.**
    [API 게이트웨이와 서비스 메시](api-gateway-and-service-mesh.md)는 게이트웨이의 정당한
    일을 **매핑과 API 키와 로깅과 속도 제한과 개발자 포털**로 세고 그보다 많은 것을 과잉으로
    판정한다. **집계가 갈리는 자리인데 그 대조는 아래
    [이 KB의 다른 게이트웨이 서술과 만나는 자리](#이-kb의-다른-게이트웨이-서술과-만나는-자리)에
    있다.**

## 어디에 놓이는가

- **테두리에 놓이되 "체계"의 뜻이 유연하다** — API 게이트웨이는 전형적으로 **체계의 테두리에
  배포되지만, 여기서 "체계"의 정의는 꽤 유연할 수 있다** (3장 §"Where Is an API Gateway
  Deployed?", p.59).[^gough2022]
- **스타트업과 중소기업(SMB)** — 게이트웨이가 흔히 **데이터센터나 클라우드의 테두리**에
  배포된다. 이 상황에서는 **게이트웨이가 하나뿐일 수 있고**(고가용성을 위해 여러 인스턴스로
  배포되고 돌지만), 그 하나가 **백엔드 전체의 현관**으로 행동하며 이 장이 다루는 모든 엣지
  기능을 그 단일 구성 요소로 제공한다 (3장, p.59).[^gough2022]
- **대기업과 엔터프라이즈** — 게이트웨이가 전형적으로 **여러 자리에 배포된다.** 흔히
  **데이터센터 주변부의 최초 엣지 스택의 일부**로 놓이고, **제품마다 또는 사업 부문마다 또는
  조직의 부서마다 추가 게이트웨이**가 배포될 수 있다. 이 맥락에서 그 게이트웨이들은 전형적으로
  **별개의 구현**이고 **지리적 위치(예컨대 요구되는 거버넌스)나 인프라 능력(예컨대 저전력 엣지
  컴퓨트 자원 위에서 도는 것)에 따라 서로 다른 기능을 제공할 수 있다** (3장,
  p.59).[^gough2022]
  - **그림에만 있고 본문에 없는 배치가 있다.** 그림 3-3은 **DMZ에 게이트웨이 하나를 두고 그
    뒤의 부서마다 게이트웨이를 하나씩 더 두는** 이중 구조를 그리고, 부서 A의 백엔드로 SOAP와
    gRPC를, 부서 B의 백엔드로 REST를 단다. 본문은 "여러 자리"라고만 적고 앞뒤 관계를 세지
    않는다 (3장, 그림 3-3, p.60).[^gough2022]
  - **이 다중 게이트웨이 배치가 함정이 되는 자리**가
    [API 게이트웨이의 함정과 선택](api-gateway-pitfalls-and-selection.md)의 "거북이" 절이다.
    **같은 배치를 이 책이 한 번은 전형으로 한 번은 함정으로 적는다** — 갈리는 것은 **변경
    비용이 감당 가능한가**이고 그 판정 기준이 그쪽 절에 있다.
- **저자들이 도판에 단서를 단다** — 게이트웨이 안에서 제공되는 **정의와 정확한 기능이 구현마다
  늘 일관되지는 않으므로**, 앞의 그림들은 **정확한 구현이라기보다 개념적인 것으로 생각해야
  한다** (3장, p.60).[^gough2022]

## 엣지 스택 — 테두리의 다른 구성 요소들

- **테두리에 여럿이 놓이는 이유** — API 기반 체계의 테두리는 **소비자와 사용자가 백엔드와 처음
  상호작용하는 자리**이고, 그래서 **많은 횡단 관심사가 거기서 다뤄지는 것이 가장 낫다** (3장
  §"How Does an API Gateway Integrate with Other Technologies at the Edge?",
  p.60).[^gough2022]
- **그래서 현대의 엣지 기술 스택, 곧 "엣지 스택(edge stack)"이 API 기반 애플리케이션의 핵심
  비기능 요건을 채우는 기능의 묶음을 제공한다.** 어떤 엣지 스택에서는 **기능마다 따로 배포되고
  운영되는 구성 요소**가 제공하고, 다른 엣지 스택에서는 **기능과 구성 요소가 합쳐진다** (3장,
  p.60).[^gough2022]
- **이 층들을 모놀리식 구성 요소로 다루면 안 된다** — 전형적으로 따로 배포되고 **개별 팀이나
  서드파티 서비스 제공자가 소유하고 운영할 수 있다.** 어떤 API 게이트웨이는 엣지 스택 안의
  기능 전부를 제공하고, 다른 것은 **API 게이트웨이 기능과 API 관리에만 집중한다.** 클라우드
  환경에서는 **클라우드 벤더가 API 게이트웨이와 통합될 수 있는 로드 밸런서를 제공하는 것도
  흔하다** (3장, p.60).[^gough2022]
- **층의 목록은 그림에만 있다.** 본문은 그림이 "핵심 층들을 보여 준다"고만 적고 층을 세지
  않는다. 그림 3-4는 위에서 아래로 셋으로 묶는다 (3장, 그림 3-4, p.61):[^gough2022]
  - **외부 제공자(External provider)** — 콘텐츠 전송 네트워크(CDN)와 DNS.
  - **엣지 스택(Edge stack)** — **4계층 로드 밸런서 → 애플리케이션 전송 컨트롤러 → 웹
    애플리케이션 방화벽 → API 게이트웨이** 순서로 트래픽이 내려간다.
  - **앱과 서비스(Apps and services)** — 백엔드 체계.
  - **이 순서가 이 페이지가 담는 유일한 층 순서다.** 아래
    [현대사 다섯 시기](#현대사-다섯-시기)가 각 층이 언제 왜 생겼는지를 적는다.

## 왜 쓰는가 여섯

- **저자들이 이 절을 아키텍트의 노릇으로 연다** — 현대 소프트웨어 아키텍트의 큰 몫이 **설계와
  구현에 대해 어려운 물음을 던지는 것**이고, **단기의 구현과 장기의 유지보수 가능성을 함께
  저울에 올려야 한다.** API에 걸리는 횡단 관심사로 저자들이 드는 것은 **유지보수 가능성,
  확장 가능성, 보안, 관측 가능성, 제품 수명 주기 관리, 수익화**다 (3장 §"Why Use an API
  Gateway?", p.61).[^gough2022]
- **게이트웨이가 다룰 수 있다고 저자들이 세는 핵심 문제가 여섯이다** (3장, p.62):[^gough2022]
  프런트엔드와 백엔드 사이의 어댑터와 파사드로 결합 줄이기, 백엔드 서비스의 집계와 번역으로
  소비 단순하게 하기, 위협 탐지와 완화로 과용과 남용에서 API 지키기, API가 어떻게 소비되는지
  이해하기(관측 가능성), API 수명 주기 관리로 API를 제품으로 관리하기, 계정 관리와 청구와
  결제로 API 수익화하기.
  - **이 여섯이 그대로 선택 기준이 된다** — 게이트웨이를 고를 때의 ADR 지침이 이 여섯을
    권고 칸에 되풀이한다. 그 지침은
    [API 게이트웨이의 함정과 선택](api-gateway-pitfalls-and-selection.md)에 있다.

## 하나 — 파사드와 어댑터로 결합을 줄인다

- **저자들이 기초 개념 셋을 먼저 세운다** — **결합(coupling), 응집(cohesion), 정보
  은닉(information hiding)**이다. 느슨한 결합과 높은 응집을 보이도록 설계된 체계가 **이해하고
  유지보수하고 수정하기 더 쉽다**고 배우며, **정보 은닉은 소프트웨어 체계에서 가장 바뀔 법한
  설계 결정들을 격리하는 원칙**이다 (3장 §"Reduce Coupling: Adapter/Facade Between Frontends
  and Backends", p.62).[^gough2022]
  - 각각이 사 주는 것도 적힌다 — **느슨한 결합은 다른 구현을 쉽게 갈아 끼우게 하고 체계를
    시험할 때 특히 쓸모 있다**(느슨하게 결합된 의존은 목과 스텁으로 세우기 쉽다). **높은
    응집은 이해 가능성을 북돋고**(모듈이나 체계 안의 모든 코드가 하나의 중심 목적을 떠받친다)
    신뢰성과 재사용성도 준다. **정보 은닉은 설계 결정이 바뀔 때 체계의 다른 부분이 광범위하게
    고쳐지는 것을 막는다** (3장, p.62).[^gough2022]
  - 그 어휘의 자리는 [아키텍처 모듈성의 구동 요인](../concepts/modularity-drivers.md)과
    [서비스 결합의 네 종류](../concepts/service-coupling-types.md)다.
- **저자들이 API를 그 이론이 현실과 만나는 자리로 규정한다** — 자기들 경험으로는 **API가 흔히
  아키텍처 이론이 현실과 만나는 체계 안의 자리**이고, API는 **말 그대로도 비유적으로도 다른
  엔지니어가 통합해 들어오는 인터페이스**다 (3장, p.62).[^gough2022]
- **게이트웨이가 단일 진입점이자 파사드 또는 어댑터로 행동해 느슨한 결합과 응집을 북돋는다.**
  저자들이 둘을 가른다 — **파사드는 체계에 새롭고 더 단순한 인터페이스를 정의하는 것**이고,
  **어댑터는 기존 인터페이스 둘 사이의 상호운용을 떠받치는 것을 목표로 옛 인터페이스를
  재사용하는 것**이다 (3장, p.62).[^gough2022]
- **그래서 얻는 것** — 클라이언트는 게이트웨이에 노출된 API와 통합하고, **합의된 계약이
  유지되는 한 백엔드의 구성 요소는 위치와 아키텍처와 구현(언어·프레임워크 따위)을 최소한의
  영향으로 바꿀 수 있다** (3장, p.62).[^gough2022]
  - **그림에만 있는 단서 하나** — 그림 3-5는 게이트웨이 앞에 `Single entry point client API`,
    백엔드 쪽에 `Backend APIs can change location, architecture, implementation`이라는 라벨을
    단다 (3장, 그림 3-5, p.63).[^gough2022]
  - 같은 패턴을 진화의 수단으로 세우는 자리가 이 책 8장이라고 본문이 가리킨다(파사드와
    어댑터). 이 KB의 그 자리는
    [부패 방지 계층](../concepts/anticorruption-layer.md)과 [모델 변환](../concepts/model-translation.md)이다.

## 둘 — 집계와 번역으로 소비를 단순하게 한다

- **문제 설정** — 프런트엔드 체계에 노출하고 싶은 API가 **백엔드 하나 또는 백엔드들의 조합이
  지금 제공하는 인터페이스와 다른 경우가 흔하다.** 저자들이 드는 예가 **소유자가 여럿인 여러
  백엔드 서비스의 API를 소비자를 향한 단일 API로 집계하는 것**이고, 목적은 **프런트엔드
  엔지니어의 심상 모형을 단순하게 하고, 데이터 관리를 매끄럽게 하고, 백엔드 아키텍처를
  숨기는 것**이다. 저자들은 **GraphQL이 바로 이 이유로 자주 쓰인다**고 적는다 (3장 §"Simplify
  Consumption: Aggregating/Translating Backend Services", p.63).[^gough2022]
- **대가가 곧바로 적힌다** — 이런 종류의 기능을 여기 구현하는 데는 절충이 있고, **API
  게이트웨이 안의 로직을 백엔드 서비스의 업무 로직과 높이 결합시키기가 너무나 쉽다** (3장,
  p.63).[^gough2022]
  - **저자들이 대가를 적되 금지하지는 않는다.** 이 자리가 이 KB의 기존 게이트웨이 서술과
    갈리는 지점이고 그 대조는 아래
    [이 KB의 다른 게이트웨이 서술과 만나는 자리](#이-kb의-다른-게이트웨이-서술과-만나는-자리)에
    있다.
- **동시 호출 조율(곁상자, 목차에 없다)** — 게이트웨이에 구현되는 인기 있는 단순화 접근이
  **동시 백엔드 API 호출을 조율하는 것**이다. 게이트웨이가 **여러 독립 백엔드 API를 동시에
  부르는 일을 조율하고 조정한다.** 전형적으로 **독립이고 결합되지 않은 여러 API를 순차가 아니라
  병렬로 불러** 소비자를 위한 결과를 모으는 시간을 아끼려는 것이고, 이것을 게이트웨이에서
  제공하면 **소비자마다 이 기능을 따로 구현할 필요가 없어진다** (3장, p.63).[^gough2022]
  - **대가가 둘 적힌다** — 다시 한번 **업무 로직이 게이트웨이와 백엔드 체계에 흩어질 수
    있다**는 것, 그리고 **연산 결합(operation coupling) 문제**다. **API 호출의 순서를 바꾸는
    게이트웨이 구현 변경이 기대 결과에 영향을 줄 수 있고, 특히 백엔드 호출이 멱등하지 않으면
    그렇다** (3장, p.63).[^gough2022]
  - 멱등성의 정본은 [안정성 패턴](../concepts/stability-patterns.md)의 멱등성 절이다.
- **프로토콜 번역** — 엔터프라이즈 맥락에서 흔한 요구다. 저자들이 드는 예가 **SOAP 기반 API만
  제공하는 "유산(heritage)" 체계 여럿을 두고 소비자에게는 REST 같은 API만 노출하고 싶은
  경우**다. 게이트웨이가 이 집계와 번역을 제공할 수 있으나 **이 쓰임에는 주의해야 한다** (3장,
  p.64).[^gough2022]
  - **비용이 둘 적힌다** — **번역이 올바른 충실도를 갖게 하는 설계와 구현과 테스트 비용**이
    있고, **번역을 구현하는 계산 자원 비용**이 있는데 후자는 **요청 수가 많을 때 비쌀 수
    있다** (3장, p.64).[^gough2022]
  - **이 자리가 이 KB의 기존 게이트웨이 서술과 정면으로 마주 본다.** 그쪽은 프로토콜 재작성을
    금지 항목으로 세운다. 대조는 아래 절에 있다.

## 셋 — 과용과 남용에서 지킨다

- **테두리가 두 종류의 첫 접점이다** — 체계의 테두리는 **사용자가 애플리케이션과 처음
  상호작용하는 자리**이자 **나쁜 행위자와 해커가 체계와 처음 마주치는 자리**이기도 하다
  (3장 §"Protect APIs from Overuse and Abuse: Threat Detection and Mitigation",
  p.64).[^gough2022]
- **규모가 방어의 두께를 정한다** — 엔터프라이즈 조직의 대다수는 **CDN과 웹 애플리케이션
  방화벽(WAF), 나아가 주변부 네트워크와 전용 DMZ 같은 보안 중심 층을 엣지 스택에 여럿**
  두지만, **더 작은 조직에서는 API 게이트웨이가 첫 방어선일 수 있다** (3장, p.64).[^gough2022]
- **그래서 많은 게이트웨이가 담는 보안 기능** — **TLS 종단, 인증과 인가, IP 허용과 차단 목록,
  WAF(내장이거나 외부 통합), 속도 제한과 부하 떨어내기, API 계약 검증**이다 (3장,
  p.64).[^gough2022]
  - **API 계약 검증이 게이트웨이의 기능으로 세어진다.** 그 실무의 정본은
    [OpenAPI 명세를 쓰는 실무](openapi-specification-practice.md)의 인바운드 관문 절이다.
  - 속도 제한을 **어느 자리에 두는가**의 물음은
    [API 요청 수명 패턴](../concepts/api-request-lifecycle-patterns.md)이 소유하고, 이 책이 그 자리에
    구성 요소 이름을 붙이는 대목을 그쪽에 적어 두었다.
  - **그림에만 있는 것 하나** — 그림 3-7은 게이트웨이 안의 상자에 `Allow/deny`로 IP 대역 둘을,
    `Rate limit`으로 사용자별 초당 요청 수 둘을 적어 **허용과 차단이 IP 단위이고 속도 제한이
    사용자 단위**임을 보인다. 본문은 그 단위를 적지 않는다 (3장, 그림 3-7,
    p.65).[^gough2022]
- **이 기능의 큰 몫이 탐지 능력이다** — **우발적이든 고의든 API 남용을 탐지하는 능력**이고,
  그러려면 **포괄적인 관측 전략을 구현해야 한다** (3장, p.65).[^gough2022] 다음 절이 그것이다.

## 넷 — 어떻게 소비되는지를 안다

- **두 렌즈가 갈린다** — **업무 목표는 고객 전환·시간당 수익·초당 스트림 시작 같은 핵심 성과
  지표(KPI)로 재는 것이 점점 흔해지고**, **인프라와 플랫폼은 전형적으로 지연·오류·큐 깊이
  같은 서비스 수준 지표(SLI)의 렌즈로 관측된다** (3장 §"Understand How APIs Are Being
  Consumed: Observability", p.65).[^gough2022]
- **테두리가 관측의 요충지인 이유** — **사용자 요청의 대다수(전부가 아니라면)가 체계의 테두리를
  흐르므로** 여기가 관측에 핵심적인 지점이다. **오류 수와 처리량과 지연 같은 최상위 인그레스
  지표를 포착하기에 이상적인 자리**이고, 체계 안쪽 상류로 흐르는 **요청을 식별하고 주석을 다는
  (경우에 따라 애플리케이션 고유 메타데이터로) 핵심 자리**이기도 하다 (3장, p.65).[^gough2022]
- **상관 식별자(correlation identifier)가 그 기제다** — 전형적으로 **게이트웨이를 통해 요청에
  주입되고 상류 서비스마다 전파될 수 있다.** 그 식별자로 **서비스와 체계에 걸친 로그 항목과
  요청 추적을 상관시킬 수 있다** (3장, pp.65–66).[^gough2022]
  - 그 기제가 무엇을 잇는가는 [로그와 트레이스](../concepts/logs-and-traces.md)에 있다.
- **방출과 수집으로 끝나지 않는다** — 체계 수준에서 관측 데이터를 방출하고 수집하는 것이
  중요하되, **그 데이터를 어떻게 처리하고 분석하고 의사 결정을 이끌 수 있는 실행 가능한
  정보로 해석할지도 신중히 생각해야 한다.** 저자들이 꼽는 것이 **시각 표시와 조작을 위한
  대시보드 만들기**와 **경보 정의하기**이고 둘 다 **성공적인 관측 전략에 핵심**이다 (3장,
  p.66).[^gough2022]
  - 그 구별의 정본은 [관측 가능성과 모니터링](../concepts/observability-versus-monitoring.md)이다.

## 다섯 — API를 제품으로 관리한다

- **전제** — 현대의 API는 흔히 **내부 체계와 서드파티가 함께 소비하는 제품으로 설계되고
  지어지고 운영되며 그렇게 관리되어야 한다.** 많은 대규모 조직이 API를 **결정적이고 전략적인
  구성 요소**로 보고 **API 프로그램 전략을 세워 분명한 업무 목표와 제약과 자원을 정한다**
  (3장 §"Manage APIs as Products: API Lifecycle Management", p.66).[^gough2022]
- **전략이 정해지면 일상의 전술은 API 수명 주기 관리에 집중된다.** **전체 수명 주기 API
  관리(APIM)는 API의 전 생애를 아우르며 계획 단계에서 시작해 API가 은퇴할 때 끝난다.** 수명
  주기의 여러 단계가 **API 게이트웨이가 제공하는 구현에 크게 결합되어 있고**, 그래서 **APIM을
  떠받치려 한다면 알맞은 게이트웨이를 고르는 것이 결정적 결정**이다 (3장,
  p.66).[^gough2022]
- **저자들이 특정 벤더의 구획을 채택한다** — **핵심 요소가 셋(만들기·통제하기·소비하기)이고
  상위 단계가 열이라고 정의한 Axway 팀의 균형이 좋다**고 보고 그것을 따른다 (3장,
  pp.66–67).[^gough2022] 열 단계는 이렇다.
  - **짓기(Building)** — API를 설계하고 짓는다.
  - **테스트(Testing)** — 기능과 성능과 보안 기대를 검증한다.
  - **게시(Publishing)** — API를 개발자에게 노출한다.
  - **보안(Securing)** — 보안 위험과 우려를 완화한다.
  - **관리(Managing)** — API가 기능하고 최신이며 업무 요구를 충족하도록 유지하고 관리한다.
  - **온보딩(Onboarding)** — 개발자가 노출된 API를 어떻게 소비하는지 빨리 익히게 한다. 저자들이
    드는 예가 **OpenAPI나 AsyncAPI 문서를 제공하고 포털과 샌드박스를 두는 것**이다.
  - **분석(Analyzing)** — 관측을 가능하게 하고 모니터링 데이터를 분석해 사용을 이해하고 문제를
    탐지한다.
  - **홍보(Promoting)** — API를 개발자에게 알린다. 예가 **API 마켓플레이스에 등재하는 것**이다.
  - **수익화(Monetizing)** — API 사용에 대한 과금과 수익 징수를 가능하게 한다. 저자들은 이
    측면을 **다음 절에서 별도 단계로 다룬다**고 적는다.
  - **은퇴(Retirement)** — API의 폐기와 제거를 떠받친다. 그 이유로 저자들이 드는 것이 **업무
    우선순위의 이동, 기술 변화, 보안 우려**다.
- **이 열 단계가 이 KB의 수명 주기 목록과 다른 목록이다.** [API 수명 주기](../concepts/api-lifecycle.md)에
  다른 소스의 일곱 단계가 이미 있고, 그 대조를 그쪽 페이지에 적어 두었다.
- **그림에만 있는 것 둘** — 그림 3-8은 ⑴ **만들기와 통제하기와 소비하기를 순환 화살표로 잇고**,
  ⑵ 게이트웨이 뒤에 **`REST v1`과 `REST v2`를 나란히 두어 판이 공존하는 배치**를 그리며 API
  포털 상자에 `v1 Prod`와 `v2 Dev`를 적는다. 본문은 셋을 "핵심 요소"라고만 적고 순환이라
  말하지 않으며, 판의 공존도 적지 않는다 (3장, 그림 3-8, p.67).[^gough2022]
  - 판을 여러 개 세워 두는 일의 정본은
    [계약을 깨는 변경의 관리](managing-breaking-api-changes.md)다.

## 여섯 — 수익화

- **수명 주기 관리와 가깝게 이어지는 주제**다. 고객에게 노출되는 API는 전형적으로 **제품으로
  설계되어야 하고 계정 관리와 결제 선택지도 담은 개발자 포털로 제공된다.** 저자들은 **많은
  엔터프라이즈 API 게이트웨이가 수익화를 담는다**고 적는다 (3장 §"Monetize APIs: Account
  Management, Billing, and Payment", p.68).[^gough2022]
- **그 결제 포털은 흔히 결제 해법과 통합되고**(저자들이 드는 예가 PayPal과 Stripe),
  **개발자 플랜과 속도 제한과 다른 API 소비 선택지의 설정을 가능하게 한다** (3장,
  p.68).[^gough2022]
- **저자들이 수익화를 담는 게이트웨이의 예를 각주로 둘 든다** — Apigee Edge와 3Scale이다
  (3장, 각주 3, p.68).[^gough2022]
  - **이 KB의 기존 게이트웨이 서술이 이 기능의 역사적 배경을 갖고 있다** —
    [API 게이트웨이와 서비스 메시](api-gateway-and-service-mesh.md)의 "API 경제라는 역사" 절이
    **차지백 목적의 사용 추적**을 그 시기의 기능 편향으로 적고, 그 기대가 **실현되지 않아 과잉
    기능이 남았다**고 판정한다. **이 책은 같은 기능을 여섯째 이유로 세면서 그 판정을 하지
    않는다.** 겨루지 않는다 — 한쪽은 기능의 존재를 세고 다른 쪽은 그 기능이 실제로 쓰이는지를
    잰다.

## 현대사 다섯 시기

- **저자들이 역사를 보는 이유를 밝힌다** — 아키텍처 스타일과 패턴이 소프트웨어 개발사 내내
  여러 "주기"로 되풀이되고 운영 접근도 그렇다. **주기 사이에 전형적으로 진전이 있지만, 역사가
  주는 가르침을 놓치지 않도록 다 함께 조심해야 한다.** 뒤를 봄으로써 **단단한 기초 위에 짓고,
  근본 요구를 이해하고, 같은 실수를 되풀이하지 않으려 할 수 있다** (3장 §"A Modern History
  of API Gateways", p.68).[^gough2022]
- **1990년대 — 하드웨어 로드 밸런서** (3장, pp.68–69).[^gough2022]
  - "웹 1.0" 시기가 **웹 브라우저와 웹 서버와 하드웨어 로드 밸런서의 진화를 이끌었다.**
    웹 1.0의 경험은 사용자가 **브라우저로 HTTP 요청을 걸면 대상 페이지의 HTML 문서 전체가
    응답으로 돌아오는 것**이었고, 동적인 부분은 **공용 게이트웨이 인터페이스(CGI)와 Perl이나 C
    같은 언어로 쓴 스크립트의 조합**으로 구현됐다. 저자들은 그것을 **오늘날 "서비스로서의
    함수(FaaS)"라 부를 것의 아마도 첫 화신**이라 적는다.
  - **웹사이트에 접근하는 사용자가 늘면서 바탕의 웹 서버에 부담이 걸렸고**, 그것이 **늘어난
    부하를 분산하고 결함 내성도 제공하는 체계를 설계하라는 요구**를 더했다. **하드웨어 로드
    밸런서가 데이터센터의 테두리에 배포됐고**, 목표는 인프라 엔지니어와 네트워킹 전문가와
    시스템 관리자가 **사용자 요청을 여러 웹 서버 인스턴스에 흩뿌리게 하는 것**이었다.
  - **그 초기 구현이 전형적으로 떠받친 것이 기본 상태 점검(health check)**이고, **웹 서버가
    실패하거나 지연이 늘어난 응답을 하기 시작하면 사용자 요청이 다른 데로 라우팅될 수
    있었다.** 저자들은 **하드웨어 로드 밸런서가 지금도 아주 많이 쓰이며**, 기술은
    트랜지스터와 칩 아키텍처와 함께 나아졌으나 **핵심 기능은 그대로**라고 적는다.
- **2000년대 초 — 소프트웨어 로드 밸런서** (3장, p.69).[^gough2022]
  - 웹사이트의 **고가용성과 확장성 요구가 늘고 있었고, 초기 하드웨어 로드 밸런서의 비용과
    경직성이 제약 요인이 되기 시작했다.** 그래서 **소프트웨어 로드 밸런서와 이 기능을 구현하는
    데 쓸 수 있는 범용 프록시**가 등장했다(HAProxy 2001년, NGINX 2002년 출시).
  - **대상 사용자는 여전히 운영 팀이었으나**, 요구되는 기술 때문에 **소프트웨어 기반 웹 서버
    설정에 익숙한 시스템 관리자들이 예전에 하드웨어의 관심사이던 것을 점점 기꺼이 떠맡게
    됐다.**
  - **곁상자(목차에 없다)** — NGINX와 HAProxy는 둘 다 최초 출시에서 진화했으나 **여전히 널리
    쓰이고, 작은 조직과 단순한 API 게이트웨이 쓰임에 여전히 아주 쓸모 있다**(둘 다 엔터프라이즈
    배포에 더 알맞은 상용판도 제공한다). **클라우드(그리고 가상화)의 부상이 소프트웨어 로드
    밸런서의 자리를 굳혔고**, 저자들은 **이 기술의 기초를 배우기를 권한다** (3장,
    p.69).[^gough2022]
  - **같은 시기에 다른 엣지 기술도 올라왔다** — **CDN이 원 웹 서버의 요청을 덜어 내려고 점점
    채택됐고**(주로 인터넷의 성능 병목을 없애려는 필요가 이끌었다), **WAF도 채택이 늘기
    시작했다**(먼저 전용 하드웨어로, 나중에 소프트웨어로). 저자들은 **오픈소스 ModSecurity
    프로젝트와 그것을 Apache Web Server와 통합한 것이 WAF의 대량 채택을 이끌었다고 볼 만하다**고
    적는다 (3장, p.70).[^gough2022]
- **2000년대 중반 — 애플리케이션 전송 컨트롤러(ADC)** (3장, p.70).[^gough2022]
  - **웹 2.0과 XMLHttpRequest API와 Ajax의 광범위한 채택**이 이 시기를 특징짓는다. **API의
    비동기 성질 덕에 요청마다 HTML 페이지 전체를 돌려받고 파싱하고 화면을 완전히 새로 고칠
    필요가 없어졌고**, **데이터 교환 층을 표현 층에서 떼어 냄으로써 웹 페이지가 전체를 다시
    싣지 않고 콘텐츠를 동적으로 바꿀 수 있게 됐다.**
  - **그 변화가 웹 서버와 로드 밸런서에 새 요구를 걸었다** — 다시 한번 더 많은 부하를 다루는
    것, 그리고 **더 안전한(SSL) 트래픽과 점점 커지는(미디어가 풍부한) 데이터 적재물과 우선순위가
    다른 요청을 떠받치는 것**이다.
  - **그래서 애플리케이션 전송 컨트롤러(ADC)가 등장했다.** 기존 네트워킹 업체들이 만든 낱말이고,
    ADC는 **압축과 캐싱과 연결 다중화와 트래픽 셰이핑과 SSL 오프로드를 로드 밸런싱과 결합해**
    떠받쳤다. **대상 사용자는 다시 한번 인프라 엔지니어와 네트워킹 전문가와 시스템
    관리자였다.**
  - **이 시기 끝의 진단이 이 절의 핵심이다** — 2000년대 중반이면 **현대 트래픽 관리 엣지 스택의
    거의 모든 구성 요소가 업계 전반에 널리 채택돼 있었다.** 그러나 **많은 구성 요소의 구현과
    운영이 점점 팀 사이에 사일로화되고 있었다.** 큰 조직에서 개발자가 새 애플리케이션을 노출하려
    하면 전형적으로 **CDN 벤더와 로드 밸런싱 팀과 InfoSec·WAF 팀과 웹·애플리케이션 서버 팀과
    따로따로 여러 회의**를 해야 했다는 것이고, 저자들은 **데브옵스 같은 운동이 부분적으로 이
    사일로가 부과한 마찰을 없애려는 동기에서 나왔다**고 적는다. 그리고 조문을 단다 — **엣지
    스택에 층이 여전히 많고 클라우드나 새 플랫폼으로 옮기는 중이라면, 지금이 여러 층과 전문
    팀의 절충을 생각해 볼 만한 때다.**
- **2010년대 초 — 1세대 API 게이트웨이** (3장, p.71).[^gough2022]
  - **API 경제와 그에 딸린 기술이 등장했다.** 저자들이 드는 실물이 전기통신을 흔들던 조직과
    콘텐츠 제작자의 수익화를 가능하게 한 광고 API와 서비스 접근 과금을 쉽게 한 결제 회사이고,
    **개발자를 위한 API 마켓플레이스를 만들려던 초기 개척자의 부산물로 Kong API 게이트웨이가
    생겼다**(OpenResty와 오픈소스 NGINX 구현 위에 지었다). 다른 구현으로 WSO2와 Sonoa
    Systems와 Red Hat의 것을 든다.
  - **이것이 플랫폼 팀과 시스템 관리자에 더해 개발자를 겨냥한 첫 엣지 기술이었다.** 큰 초점이
    **API의 소프트웨어 개발 수명 주기(SDLC) 관리**와 **엔드포인트와 프로토콜 커넥터와 번역
    모듈 같은 체계 통합 기능 제공**에 있었다. 제공 기능의 폭 때문에 **1세대 API 게이트웨이의
    대다수가 소프트웨어로 구현됐다.**
  - **개발자 포털이 여러 제품에서 솟아났고**, 엔지니어가 **API를 구조화된 방식으로 문서화하고
    공유하게** 했다. 그 포털은 **접근 통제와 사용자·개발자 계정 관리와 게시 통제와 분석**도
    제공했다. **이론상 이것이 API의 쉬운 수익화와 "제품으로서의 API" 관리를 가능하게 할
    것이었다.**
  - **OSI 계층이 옮겨 갔다** — 개발자 상호작용이 진화하면서 **OSI 네트워킹 모형의 애플리케이션
    계층(7계층) 중 HTTP 부분에 초점이 커졌다.** 이전 세대의 엣지 기술은 **IP 주소와 포트에 자주
    집중했고 그것은 주로 전송 계층(4계층)에서 동작한다.** 개발자가 **경로 기반 라우팅이나 헤더
    기반 라우팅 같은 HTTP 메타데이터에 근거해 게이트웨이에서 라우팅 결정을 내리게 한 것**이 더
    풍부한 기능의 기회를 열었다.
  - **모놀리스가 게이트웨이 노릇을 하던 시기이기도 하다** — 조직들이 **기존 모놀리식
    코드베이스에서 단일 목적의 독립 애플리케이션을 뽑아내고 있었고, 그 모놀리스 일부가 API
    게이트웨이로 행동하거나 라우팅과 인증 같은 게이트웨이 같은 기능을 제공했다.** 1세대에서는
    **라우팅과 보안과 복원력 같은 기능적·비기능적 관심사가 테두리와 애플리케이션·서비스 안
    양쪽에서 수행되는 일이 흔했다.**
    - **그 배치를 이 책이 기각하는 자리**가
      [회의 시스템 사례 연구](conference-system-case-study.md)의 게이트웨이 도입 절이다.
- **2015년 이후 — 2세대 API 게이트웨이** (3장, p.72).[^gough2022]
  - **마이크로서비스가 시대정신에 확고히 들어왔고**, 백엔드가 더 많고 더 작은 서비스로 분해되는
    데 더해 **개발자들이 리눅스 LXC 기반의 컨테이너 기술도 채택하고 있었다.** Docker가 2013년
    3월에, 쿠버네티스가 2015년 7월에 v1.0으로 나왔다. **이 아키텍처 스타일의 이동과 바뀐
    런타임이 테두리에 새 요구를 이끌었다.**
  - **넷플릭스가 2013년 중반에 JVM 기반 게이트웨이 Zuul을 내놓았다.** Zuul은 **동적 백엔드
    서비스를 위한 서비스 디스커버리를 떠받쳤고 런타임에 Groovy 스크립트를 주입해 동작을 동적으로
    고치게 했다.** 이 게이트웨이는 **인증과 테스트(카나리 릴리스)와 속도 제한과 부하 떨어내기와
    관측 가능성 같은 여러 횡단 관심사를 단일 엣지 구성 요소로 통합했다.**
  - **쿠버네티스 채택이 늘고 2016년에 Envoy 프록시가 오픈소스로 공개되면서** 그 기술을 둘러싸고
    **많은 API 게이트웨이가 만들어졌고**, 그것이 **API 게이트웨이 영역 전반의 혁신을 더 밀었다.**
  - **대상 사용자는 1세대와 대체로 같았으나 관심사 분리가 더 뚜렷해졌고 개발자 셀프서비스에
    초점이 더 강해졌다.** 1세대에서 2세대로 오면서 **기능적 요건과 비기능적 요건 양쪽이
    게이트웨이 안에 더 많이 통합됐다.**
  - **저자들이 그 통합에 단서를 붙인다** — **마이크로서비스가 "똑똑한 엔드포인트와 멍청한
    파이프"라는 착상 위에 지어져야 한다는 것이 널리 받아들여졌음에도**, **다중 언어 스택의 채택
    때문에 "마이크로서비스 게이트웨이"가 등장해 횡단 기능을 언어 불가지 방식으로
    제공했다** (3장, p.73).[^gough2022]
    - **이것이 이 KB의 기존 게이트웨이 서술과 같은 격언을 인용하면서 다른 방향으로 가는
      자리다.** 대조는 아래 절에 있다.

## 지금의 분류 셋

- **저자들이 어휘의 불일치를 먼저 인정한다** — 소프트웨어 개발 업계의 용어가 흔히 그렇듯
  **무엇이 API 게이트웨이를 정의하거나 분류하는지에 정확한 합의가 없는 경우가 잦다.** 이
  기술이 제공해야 할 기능에는 **폭넓은 합의**가 있으나 **업계의 부문마다 요구가 다르고 따라서
  게이트웨이에 대한 관점도 다르다.** 그래서 **여러 하위 유형이 등장해 논의되고 있다** (3장
  §"Current API Gateway Taxonomy", p.73).[^gough2022]
- **전통적 엔터프라이즈 게이트웨이** (3장, p.73).[^gough2022]
  - 전형적으로 **업무 중심 API를 노출하고 관리하는 쓰임**을 겨냥한다. 흔히 **전체 API 수명 주기
    관리 해법과 통합**되는데, 그것이 **API를 규모 있게 릴리스하고 운영하고 수익화할 때 핵심
    요건**이기 때문이다.
  - **이 영역 게이트웨이의 대다수가 오픈소스 판을 제공할 수 있으나, 전형적으로 오픈 코어와
    상용판 쪽으로 사용이 강하게 기울어 있다.**
  - **운영 비용의 단서가 붙는다** — 이 게이트웨이들은 전형적으로 **데이터 저장소 같은 의존
    서비스의 배포와 운영을 요구한다.** 그 외부 의존은 **게이트웨이의 올바른 동작을 유지하려면
    고가용성으로 돌아야 하고, 그것이 운영 비용과 재해 복구·업무 연속성 계획에 반영되어야
    한다.**
- **마이크로서비스 게이트웨이 또는 마이크로 게이트웨이** (3장, pp.73–74).[^gough2022]
  - **주 쓰임은 인그레스 트래픽을 백엔드 API와 서비스로 라우팅하는 것**이다. 전통적 엔터프라이즈
    게이트웨이에 견주어 **API 수명 주기 관리를 위한 기능이 전형적으로 많지 않다.** 이 종류는
    흔히 **오픈소스로 온전한 기능을 갖춰 제공되거나 전통적 엔터프라이즈 게이트웨이의 경량판으로
    제공된다.**
  - **독립 구성 요소로 배포되고 운영되는 편이고**, **API 수명 주기 데이터와 속도 제한 카운트와
    API 소비자 계정 관리 같은 내부 상태의 관리에 바탕 플랫폼(예컨대 쿠버네티스)을 자주
    이용한다.**
  - **마이크로서비스 게이트웨이가 전형적으로 Envoy 같은 현대 프록시 기술로 지어지므로 서비스
    메시(특히 같은 프록시 기술로 지어진 메시)와의 통합 능력이 전형적으로 좋다.**
- **서비스 메시 게이트웨이** (3장, p.74).[^gough2022]
  - **서비스 메시에 딸려 오는 인그레스 또는 API 게이트웨이는 전형적으로 외부 트래픽을 메시
    안으로 라우팅하는 핵심 기능만 제공하도록 설계된다.** 그래서 **인증·신원 제공자 해법과의
    포괄적 통합이나 WAF 같은 다른 보안 기능과의 통합 같은 전형적 엔터프라이즈 기능이 자주
    빠져 있다.**
  - **상태를 자체 내부 구현이나 플랫폼(예컨대 쿠버네티스)이 제공하는 것으로 관리한다.**
  - **판정이 하나 붙는다** — 이 종류는 **딸린 서비스 메시(그리고 그 운영 요건)와 암묵적으로
    결합되어 있으므로, 아직 서비스 메시를 배포할 계획이 없다면 이것은 십중팔구 첫 API
    게이트웨이로 좋은 선택이 아니다.**
- **셋을 맞댄 표** (3장, 표 3-3, pp.74–75).[^gough2022] 원문 칸의 문장을 줄여 옮겼고 표 자체를
  재현하지 않았다.

  | 쓰임 | 전통적 엔터프라이즈 | 마이크로서비스 | 서비스 메시 게이트웨이 |
  |---|---|---|---|
  | 주 목적 | 내부 업무 API와 그에 딸린 서비스를 노출하고 조합하고 관리한다 | 내부 업무 서비스를 노출하고 조합하고 관리한다 | 메시 안의 내부 서비스를 노출한다 |
  | 게시 방식 | API 관리 팀이나 서비스 팀이 관리 API로 등록하고 갱신한다(성숙한 조직은 전달 파이프라인으로 한다) | 서비스 팀이 배포 과정의 일부로 선언적 코드로 등록하고 갱신한다 | 서비스 팀이 배포 과정의 일부로 선언적 코드로 메시와 게이트웨이를 등록하고 갱신한다 |
  | 모니터링 | 관리와 운영 중심 — 소비자별 API 호출 계량, 오류 보고 | 개발자 중심 — 지연·트래픽·오류·포화 | 플랫폼 중심 — 사용률·포화·오류 |
  | 문제 처리와 디버깅 | 7계층 오류 처리. 문제 해결은 게이트웨이와 API에 로깅을 더해 돌리고 스테이징 환경에서 디버깅한다 | 7계층 오류 처리. 디버깅은 더 자세한 모니터링을 설정하고 트래픽 섀도잉이나 카나리로 문제를 재현한다 | 7계층 오류 처리. 문제 해결은 더 자세한 모니터링을 설정하거나 트래픽 "태핑"으로 특정 서비스 사이 통신을 보고 디버깅한다 |
  | 테스트 | QA와 스테이징과 프로덕션 환경을 여럿 운영한다. 자동화된 통합 테스트와 게이트를 둔 API 배포. 호환과 안정을 위해 소비자 주도 API 버저닝을 쓴다 | 동적 테스트를 위해 카나리 라우팅과 다크 런칭을 가능하게 한다. 업그레이드 관리에 계약 테스트를 쓴다 | 동적 테스트를 위해 카나리 라우팅을 쉽게 한다 |
  | 로컬 개발 | 게이트웨이를 로컬에 배포하고(설치 스크립트·Vagrant·Docker) 프로덕션과의 인프라 차이를 완화하려 한다. 언어별 게이트웨이 모의와 스텁 프레임워크를 쓴다 | 서비스 오케스트레이션 플랫폼(컨테이너나 쿠버네티스)으로 게이트웨이를 로컬에 배포한다 | 서비스 오케스트레이션 플랫폼(쿠버네티스)으로 서비스 메시를 로컬에 배포한다 |
  | 사용자 경험 | 웹 기반 관리 UI와 개발자 포털과 서비스 카탈로그 | IaC나 CLI 주도이고 단순한 개발자 포털과 서비스 카탈로그 | IaC나 CLI 주도이고 제한된 서비스 카탈로그 |

  - **본문과 표의 수가 갈린다.** 본문은 표가 **여섯 가지 중요한 기준으로** 세 유형을 맞댄다고
    적는데 (3장, p.74),[^gough2022] **표의 행은 일곱**이다(주 목적·게시 방식·모니터링·문제
    처리와 디버깅·테스트·로컬 개발·사용자 경험). 저자들은 이 갈림에 대해 아무 말도 하지 않는다.
    이 페이지는 **일곱을 그대로 두었다.**
  - **이 표의 테스트 칸이 이 책 2장과 이어진다** — 계약 테스트와 소비자 주도 버저닝이
    [소비자 주도 계약](consumer-driven-contracts.md)과
    [API 테스트의 유형과 경계](api-test-types-and-boundaries.md)에 있다. 카나리 라우팅과
    다크 런칭은 이 책이 5장으로 미룬다.

## 게이트웨이와 엣지 프록시와 인그레스 컨트롤러

**저자들이 곁상자로 따로 세운 자리이고 목차에 없다. 같은 낱말이 클라우드 맥락에서 갈리는 것을
셋으로 정리한다** (3장, p.72).[^gough2022] 저자들은 이 혼란의 진단을 다른 사람의 블로그 글에
귀속시킨다.

> Generally speaking, in this context an API gateway enables some form of management of
> APIs, ranging from simple adaptor-style functionality operating at the application layer
> (OSI layer 7) that provides fundamental cross-cutting concerns, all the way to full
> lifecycle API management. Edge proxies are more general-purpose traffic proxies or reverse
> proxies that operate at the network and transport layers (OSI layers 3 and 4,
> respectively), provide basic cross-cutting concerns, and tend not to offer API-specific
> functionality. "Ingress Controllers" are a Kubernetes-specific technology that controls
> what traffic enters a cluster and how this traffic is handled.

- **가르는 축이 둘이다** — **어느 OSI 층에서 동작하는가**(게이트웨이는 7계층, 엣지 프록시는
  3·4계층)와 **API 고유 기능을 제공하는가**(게이트웨이는 그렇고 엣지 프록시는 그렇지 않은
  편이다). 인그레스 컨트롤러는 **플랫폼에 묶인 셋째 칸**이다.
- **이 구별이 이 KB에 없던 것이다.** [HTTP 중개자](../concepts/http-intermediaries.md)는 RFC 9110을 따라
  프록시와 게이트웨이와 터널을 가르는데 그 축은 **프로토콜 역할**이지 OSI 층이 아니다.
  **겨루지 않는다** — 그쪽 게이트웨이(리버스 프록시)는 HTTP 통신의 한 역할이고, 이쪽
  게이트웨이는 **그 역할 위에 API 관리를 얹은 제품 범주**다. 이 책 스스로 **API 게이트웨이가
  네트워크 수준에서는 리버스 프록시로 행동한다**고 적으므로(위
  [무슨 기능을 주는가](#무슨-기능을-주는가)) **같은 낱말의 두 층이지 두 주장이 아니다.**
- **인그레스 컨트롤러가 쿠버네티스 고유 기술이라는 규정이 이 KB의 쿠버네티스 페이지와 만난다** —
  [컨테이너 오케스트레이션과 쿠버네티스](../concepts/container-orchestration-and-kubernetes.md)가 그
  플랫폼의 어휘를 소유한다.

## 이 KB의 다른 게이트웨이 서술과 만나는 자리

**[API 게이트웨이와 서비스 메시](api-gateway-and-service-mesh.md)가 이 KB의 기존 게이트웨이
자리이고 2021년 마이크로서비스 실무서가 그 정본이다. 그쪽은 게이트웨이의 기능을 깎고 이쪽은
늘린다. 겨루는지를 따져 보았고 판정은 모순 아님이다.**

- **① 집계 — 한쪽은 금지하고 한쪽은 대가를 적는다.**
  - 그쪽은 **호출 집계를 게이트웨이에 넣지 말아야 할 것 셋의 첫째**로 세운다. 근거는 그것이
    **미끄러운 비탈**이라는 것이다 — 호출 둘을 합치는 데서 시작해 조건 로직에 이르고 끝내 **핵심
    업무 프로세스를 맞지 않는 서드파티 도구 안에 구워 넣게 된다.**
  - 이 책은 **집계를 여섯 이유의 둘째로 세우면서** 같은 위험을 **"게이트웨이 안의 로직을 백엔드
    업무 로직과 높이 결합시키기가 너무나 쉽다"**로 적는다 (3장, p.63).[^gough2022] 동시 호출
    조율 곁상자에서도 **업무 로직이 흩어질 수 있다**는 같은 대가를 적는다.
  - **판정 — 사실이 충돌하지 않는다.** 두 소스가 **같은 위험을 같은 기제로 진단한다.** 갈리는
    것은 **처방의 세기**다 — 한쪽은 하지 말라 하고 다른 쪽은 대가를 알고 하라 한다. **이것은
    상황이 고르는 설계 절충이므로 `contradicts` 대상이 아니다**(이 KB의 스키마가 사실 주장의
    충돌만 대상으로 삼는다).
- **② 프로토콜 번역 — 여기가 가장 멀다.**
  - 그쪽은 **프로토콜 재작성을 둘째 금지 항목**으로 세우고, 어느 벤더가 **"어떤 SOAP API든 REST
    API로 바꿀 수 있다"**고 밀던 것을 기억한다며 둘로 반박한다 — **REST는 프록시 계층에서 그냥
    구현할 수 있는 것이 아니라 아키텍처 사고방식 전체**이고, **프로토콜 재작성은 중간 계층에서
    할 일이 아니다.**
  - 이 책은 **거의 같은 장면을 들면서**(SOAP만 제공하는 유산 체계, REST 같은 API만 노출하고 싶은
    요구) **게이트웨이가 이 기능을 제공할 수 있다**고 적고 **주의하라**는 단서를 붙인다. 단서의
    내용이 **설계·구현·테스트 비용과 계산 자원 비용**이다 (3장, p.64).[^gough2022]
  - **판정 — 사실 주장은 충돌하지 않고 근거가 다른 층에 있다.** 그쪽의 반박은 **REST가 무엇인가**
    라는 규정 논거이고, 이쪽의 단서는 **비용** 논거다. 이쪽은 **REST를 프록시 계층에서 구현할 수
    있다고 주장하지 않는다** — "REST 같은(REST-like) API"라고 적는다. **`contradicts`를 걸지
    않았다.** 이 판정은 이 KB의 것이고 두 책은 이 자리에서 서로를 호명하지 않는다. #hypothesis
- **③ "똑똑한 엔드포인트와 멍청한 파이프" — 같은 격언을 인용하고 반대편에 선다.**
  - 그쪽은 이 격언을 **게이트웨이에 집계와 재작성을 넣지 말라는 조문의 근거**로 든다.
  - 이 책은 **그 격언이 널리 받아들여졌음에도** 다중 언어 스택 때문에 **횡단 기능을 언어 불가지
    방식으로 제공하는 마이크로서비스 게이트웨이가 등장했다**고 적는다 (3장, p.73).[^gough2022]
  - **판정 — 겨루지 않되 무게중심이 반대다.** 한쪽은 격언을 지키려 기능을 깎고 다른 쪽은 격언을
    인정하면서 **다중 언어 환경이라는 제약이 통합을 밀었다**는 사실을 적는다. **둘 다 옳을 수
    있다** — 격언은 설계 원칙이고 통합은 관찰된 업계 동향이다. 두 소스가 서로를 호명하지 않는다.
    #hypothesis
- **④ 게이트웨이를 여러 개 두는 것 — 양쪽 다 조건부로 허용하되 조건이 다르다.**
  - 그쪽은 **관심사 분리를 낫게 하기 위해** 둘 이상이 합리적일 수 있다고 보되 **복잡성과 네트워크
    홉 증가**라는 단서를 단다.
  - 이 책은 **대기업의 다중 게이트웨이를 전형적 배치로 그리고**(위
    [어디에 놓이는가](#어디에-놓이는가)) 동시에 **"거북이" 함정으로 기각하는 조건**을 따로
    적는다. 그 조건은 [API 게이트웨이의 함정과 선택](api-gateway-pitfalls-and-selection.md)에
    있다.
  - **판정 — 같은 방향이고 이 책이 조건을 더 세밀하게 적는다.** 겨루지 않는다.
- **⑤ 기능 목록이 겹치는 자리는 다 같은 방향이다** — 인증, 속도 제한, 로깅, 개발자 포털, 리버스
  프록시로 행동한다는 것이 양쪽에 다 있다.
