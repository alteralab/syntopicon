## 하나의 질문

**전역 거버넌스 정책을 중앙 관문 없이 모든 데이터 프로덕트에 일관되게 적용하려면, 정책을
무엇으로 표현해야 하는가.**

## 정책을 코드로 바꿔 데이터 프로덕트에 심는다

- 절 머리의 제사 — **I think Computation is destined to be the defining idea of our future.
  — Stephen Wolfram** (14장, p.258).[^dehghani2022]
- 데이터 메시의 입장 — **5장에서 도입한, 거버넌스와 정책 준수에 대한 데이터 메시의 입장은 데이터
  프로덕트를 규율하는 정책을 **코드로** 구현하고 그것을 각각의 모든 데이터 프로덕트에 **심는(embed)**
  것이다. 내장된 정책은 데이터 프로덕트의 수명 주기를 거치며 올바른 시점에, 그리고 바로 데이터의
  흐름 속에서 검증되고 부과된다** (14장, p.258).[^dehghani2022]
- 저자의 예가 하나의 정책이 여러 시점에 걸린다는 것을 보인다 — **정책이 특정 타입 데이터의
  인메모리 암호화를 요구하면, 데이터 프로덕트에 내장된 이 **코드로서의 정책(policy as code)**의
  표현은 데이터 프로덕트가 자기 수명 주기의 여러 다른 지점에서 이 정책을 테스트하고 강제할 수 있게
  한다: 빌드·배포 시점에 데이터 프로덕트가 보안 엔클레이브에 접근할 수 있는지 검증하고, 데이터의
  접근과 변환 동안 그 보안 엔클레이브를 쓰는 식이다** (14장, p.258).[^dehghani2022]
  - 각주 — **신뢰 실행 환경(TEE)은 주 애플리케이션의 실행 맥락보다 높은 수준의 보안으로 환경 —
    프로세서·메모리·스토리지 — 을 격리한다** (14장, p.258, 각주 1).[^dehghani2022]
- 코드로 취급하는 것의 귀결 — **정책을 코드로 취급한다는 발상은 정책이 다른 코드처럼 버저닝되고·
  테스트되고 실행되며·관측된다는 뜻이다. 정책은 데이터·데이터 스키마와 마찬가지로 **시간 가변이며
  시간이 지나면서 바뀐다**** (14장, p.259).[^dehghani2022]
  - 정책이 [바이템포럴 데이터](../concepts/bitemporal-data.md)의 "시간성이 모든 측면을
    버저닝한다"에 포함되는 대상이라는 뜻이다 — "어느 처리 시간에 어떤 정책이 걸려 있었는가"가
    질의 가능해야 한다.

## 실행 자리는 이미 9장이 마련해 두었다

- 저자가 앞 장들의 구성물을 불러 모은다 — **9장에서 나는 각각의 모든 데이터 프로덕트에 내장된
  정책의 **설정**과 **실행**을 가능하게 하는 데이터 프로덕트의 아키텍처 구성 요소들을 도입했다.
  나는 **제어 포트(control port)** 개념 — 데이터 프로덕트에 대한 접근 통제 규칙 설정 같은 정책
  설정과, 잊힐 권리 실행이나 다른 데이터 수정 수행 같은 고특권 거버넌스 함수 호출을 위한 인터페이스
  집합 — 을 도입했다. **데이터 프로덕트 사이드카** 개념은 모든 데이터 프로덕트에 동반하며 정책
  실행 같은 모든 데이터 프로덕트의 교차 기능적 필요를 수행하는 동질적 실행 엔진으로 도입되었다.
  사이드카는 단순히 서로 다른 정책을 위한 잠재적으로 여러 기제를 허용하는 논리적 자리표시자이며,
  시간이 지나면서 데이터 프로덕트를 점진적으로 **장식(decorating)**한다. 마지막으로 나는 데이터
  프로덕트 자원의 런타임 인스턴스화를 캡슐화하는 방법으로 **데이터 프로덕트 컨테이너** 개념을
  도입했다** (14장, p.259).[^dehghani2022]
  - 각주가 계열을 밝힌다 — **객체 지향 프로그래밍에서 데코레이터 패턴은 개별 객체에 시간이
    지나면서 행위를 더할 수 있게 하는 설계 패턴이다** (14장, p.259, 각주 2 — Gamma 외,
    *Design Patterns*, 1994).[^dehghani2022] 사이드카가 프록시가 아니라 **데코레이터**로
    설명되는 자리다.
- 공급 주체 — **거버넌스는 전역 관심사이고 정책은 데이터 프로덕트에 일관되게 적용되어야 하므로,
  나는 플랫폼이 이 구성 요소들 — 컨테이너·사이드카 등 — 을 제공할 것을 제안했다. 이 구성 요소들은
  **메시 경험 플레인**과 협력해 작동한다. 메시 경험 플레인은 정책 설정과 메시 전반 모든 데이터
  프로덕트에 대한 전역 잊힐 권리 같은 거버넌스 프로세스를 위한 능력을 제공한다** (14장,
  p.259).[^dehghani2022]
- 그림 14-2는 메시 경험 플레인이 `/privileged-ops/forget-user`와 `/policies-as-code`를 노출하고,
  각 데이터 프로덕트가 `/control-port`와 **내장 정책**을 갖고 사이드카가 **정책 실행과 설정**을
  맡는 구조를 그린다 (14장, p.260, 그림 14-2).[^dehghani2022]
- 셋째 축이 추가된다 — **설정과 실행에 더해, 정책의 거버넌스는 그 채택 상태에 대한 **관측
  가능성(observability)**을 요구한다** (14장, p.259).[^dehghani2022] 그 몫은
  [데이터 프로덕트의 관측 가능성](../concepts/data-product-observability.md)이 받는다.
- 정책의 두 종류 — **정책은 도메인 특유일 수도 불가지일 수도 있다. 예컨대 의료 도메인 데이터를
  서빙하는 데이터 프로덕트는 환자 건강 기록의 보안과 프라이버시를 보증하기 위해 HIPAA를 따라야
  한다. 도메인 불가지로는 모든 데이터 프로덕트가 자기 보증된 데이터 정확도 수준을 지켜야 한다**
  (14장, p.259).[^dehghani2022]

## 정책 표준화가 왜 필수인가

- **메시 전반 모든 데이터 프로덕트에 대해 정책을 표현하고·설정하고·강제하는 일관된 방법을 갖는
  것이 결정적이다. 정책은 모든 데이터 프로덕트의 요소이자 그 인터페이스 — 예: 제어 포트 — 의
  일부다. 따라서 정책이 무엇이고 어떻게 표현되고 강제되는지를 표준화하는 것이 불필요한 복잡성을
  제거한다** (14장, p.260).[^dehghani2022]
- 저자가 가장 단순한 예로 논증한다 — **단순한 정책 하나를 보자: **접근 통제**, 곧 누가 어떤
  데이터에 접근할 수 있는지를 정의하고 강제하는 것이다. 접근 통제가 작동하는 데 필요한 기본
  구성물은 데이터 사용자의 **신원(identity)** 개념이다: 우리가 사용자 — 사람이든 시스템이든,
  메시 위에 있든 밖에 있든 — 를 어떻게 확신 있게 식별하는가다. 신원을 지정하고 인식하는
  표준화된 방법을 가질 수 없다면 여러 데이터 프로덕트에 걸친 데이터 공유는 거의 불가능하다.
  신원 설계 접근이 다양해질수록 데이터 공유의 마찰과 비용이 높아진다** (14장,
  p.260).[^dehghani2022]
- 그리고 현실을 지적한다 — **이 단순한 예가 자명하고 직관적으로 보이겠지만, 데이터 관리
  시스템들이 **아직 표준화된 신원과 접근 통제에 합의하지 못했다**는 데 놀랄 수도 있다. 많은
  스토리지·데이터 관리 기술이 소비자의 계정을 식별하고 접근 통제를 정의·강제하는 자기만의 독점
  방식을 갖고 있다** (14장, p.260).[^dehghani2022]

## 표준화가 절실한 세 정책

**① 암호화** — **데이터 프로덕트의 보안 정책에 따라 데이터는 전송 중·저장 중, 그리고 최근에는
기밀 컴퓨팅(confidential computing)의 진전과 함께 **메모리 안에서도** 암호화된다. 오늘날 암호화
방법은 꽤 잘 표준화되어 있는데, 자연스럽게도 암호화와 복호화에 둘 이상의 당사자가 관여하고 그들이
프로토콜에 합의해야 하기 때문이다. 데이터 메시 설계는 **무엇이·어느 수준에서·어떤 방법으로
암호화되는지의 표현**을 데이터 프로덕트의 발견 인터페이스와 스키마에 포함시킴으로써 이 표준화를
확장할 수 있다** (14장, p.261).[^dehghani2022]

- **암호화 자체가 아니라 암호화 사실의 선언이 새로 표준화된다**는 것이 요점이다 —
  [데이터 프로덕트의 발견·이해·신뢰 설계](../concepts/data-product-discoverability.md)의
  발견 정보에 보안 속성이 들어간다.

**② 접근 통제와 신원** — **데이터 메시 같은 분산 아키텍처에서 단일 플랫폼이나 조직의 경계를
넘어 데이터를 공유하려면, 신원과 접근 통제 규칙을 어떻게 정의하고 검증할지에 대한 **보편적
합의**가 있어야 한다. 가장 중요하게는, 이것을 기술 불가지 방식으로 어떻게 하는가다. 데이터가
어디에 저장되든 어느 클라우드 제공자가 관리하든 독립적으로, 데이터 사용자를 식별하고 그 접근을
관리하는 표준화된 방법이 필요하다** (14장, p.261).[^dehghani2022]

- **운영계와 분석계의 격차가 진단된다** — **운영 API와 서비스 접근에서는 신원에 대한 합의에
  도달하고 있지만, 분석 데이터 접근에서는 그것과 거리가 멀다. 운영 세계에서 분산 API를 향한
  움직임은 신원의 표준화로 이어졌다 — 최종 사용자 애플리케이션이나 다른 서비스에 대해서는
  OpenID Connect 프로토콜, JSON Web Token(JWT) 검증의 사용, 서비스에 대해서는 X.509 인증서,
  그리고 SPIFFE 같은 더 최근의 표준화 프로토콜이다. **API 공유라는 동기가 신원 표준을 세우는
  큰 동력이었다**** (14장, p.261).[^dehghani2022]
- 그리고 원인을 유인으로 설명한다 — **분석 데이터 공간에서 데이터는 여전히 기술 벤더에 갇혀
  있다. 벤더들에게 데이터를 가로질러 공유할 유인이 많지 않고, 그 결과 접근 통제 표준화를
  만드는 데 관심이 없다. 나는 데이터 메시의 주된 동기인 **기술 사일로를 넘어선 데이터 공유**가
  이것을 바꾸는 촉매가 되기를 바란다** (14장, p.261).[^dehghani2022]
  - **표준의 부재를 기술 문제가 아니라 유인 구조 문제로 진단**하는 자리다. #hypothesis —
    반증 조건은 분석 데이터 접근 통제 표준이 벤더 주도로 나오는가, 아니면 소비자 압력으로
    나오는가이다.
  - [데이터 엔지니어링의 저류](../concepts/data-engineering-undercurrents.md)의 보안 저류가
    이 격차를 다루는 자리다.

**③ 프라이버시와 동의** — **최근 십 년의 지역별 프라이버시 법은 자기 데이터가 조직에 의해
포착·통제되는 개인의 개인 식별 정보를 보호하려 한다. 이 법들은 어느 정도의 표준화로 이어졌으나,
대부분 데이터 관리에 관여하는 운영 모델과 프로세스에서다** (14장, p.261).[^dehghani2022]

- 각주 — 예로 **GDPR(EU)·CCPA(캘리포니아, 미국)·오스트레일리아 프라이버시 원칙**이 열거되고
  (14장, p.261, 각주 3), 표준화의 예로 **ISO/IEC 27701:2019, Security techniques**가 든다
  (14장, p.261, 각주 4).[^dehghani2022]
- 남는 공백 — **그러나 데이터 공유의 표준화와 유인의 결여 때문에 프라이버시와 동의의 표준화
  뒤에는 매우 제한된 노력만 있다. 우리는 어떤 데이터가 사적 정보로 보호되어야 하는지, 데이터
  소유자의 동의가 어떻게 표현되고 그 데이터와 함께 공유되는지, 어떻게 일관되게 동의를 부여하거나
  철회할 수 있는지, 그리고 가장 중요하게는 자기 데이터의 사용을 얼마나 투명하게 볼 수 있는지를
  인식하는 일관된 방법과 거리가 멀다** (14장, p.262).[^dehghani2022]
- 요구 — **분산 데이터 공유·관리 아키텍처로서 데이터 메시는 모든 데이터 프로덕트에 걸쳐
  프라이버시와 동의를 관리하는 일관된 방법을 요구한다. 동의는 각 데이터 프로덕트가 심을 수 있는
  **계산적 정책의 한 종류**다** (14장, p.262).[^dehghani2022]
  - [결정권으로서의 프라이버시](../concepts/privacy-as-a-decision-right.md)가 동의를 사람의
    결정권으로 규정하는 서술이, 여기서 **그 결정을 실행 가능한 코드로 어디에 두는가**로
    이어진다.

## 데이터와 정책의 통합

- 무엇이 풀리는가 — **아키텍처 퀀텀으로서의 데이터 프로덕트 개념은 데이터·코드·정책을 **하나의
  유지 가능한 단위**로 통합하려 시도한다. 이 자기 완결적 단위는 우리를 많은 거버넌스 이슈에서
  해방시키며, 여기에는 특정 기술 스토리지의 경계 **밖에서** 프라이버시와 동의를 관리하려 애쓰는
  것도 포함된다** (14장, p.262).[^dehghani2022]
- 저자가 문제를 구체화한다 — **예컨대 동의 정책이 데이터와 분리되어 있으면, 동의가 관리되는
  특정 기술 시스템의 경계를 넘어 데이터가 공유되고 나면 사용자의 동의를 추적하거나 심지어 존중하는
  것조차 어려워진다. 데이터 메시는 정책과 그 설정을, 그것이 규율하려는 데이터와 **연결한다**
  (14장, p.262).[^dehghani2022]
  - [데이터 퀀텀](../concepts/data-quantum.md)이 정책 코드를 세 구조 구성 요소 중 하나로
    넣은 결정의 최종 근거가 이 문단이다 — 캡슐화가 미학이 아니라 **동의 추적의 성립 조건**이다.

## 정책 연결 — 데이터를 따라가는 정책

- 13장의 링크 발상이 정책으로 확장된다 — **13장에서 논한, 서로 다른 데이터 프로덕트에 걸쳐
  데이터 시맨틱과 데이터 개체를 연결하는 것과 비슷하게, 데이터 프로덕트의 정책은 데이터
  프로덕트들에 걸쳐 서로 연결될 수 있다. 그래서 데이터가 다른 이들에게 처리되기 위해 특정 데이터
  프로덕트를 떠날 때, 그것을 규율하는 원래 정책에 대한 링크를 유지한다** (14장,
  p.262).[^dehghani2022]
- **그리고 그 링크가 끊기는 조건이 명시된다** — **데이터 변환이 데이터를 원래 데이터·스키마에
  대한 링크를 더 이상 갖지 않는 방식으로 변형하면, **정책 링크도 자연스럽게 끊긴다**. 정책 연결은
  여러 데이터 프로덕트가 소스 데이터 프로덕트가 유지하는 정책의 최신 상태에 대한 접근을 유지하는 데
  도움이 된다** (14장, p.262).[^dehghani2022]
  - **정책의 전파 범위가 데이터 계보의 연결성과 같아진다**는 규칙이다. 익명화·집계로 원본
    개체와의 연결이 끊어지면 원본 정책도 따라오지 않는다 — 이것은 결함이 아니라 설계된
    성질로 서술된다. #hypothesis — 저자는 이 경계 판정을 누가 검증하는지는 적지 않는다.
- 미완성을 인정한다 — **이것은 추가 개발이 필요한 영역이다. 그러나 데이터 메시는 데이터와 함께
  분산되고 늘 존재하는 정책 공유를 지을 토대 — 데이터 퀀텀 — 를 가능하게 한다** (14장,
  p.262).[^dehghani2022]
