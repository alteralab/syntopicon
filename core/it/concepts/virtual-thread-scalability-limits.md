이 페이지의 질문: **가상 스레드는 무엇을 좋게 만들고 무엇은 좋게 만들지 못하는가.**

## 버전 조건

> **버전 조건**: JDK 21 이상. 아래 수치와 조건은 가상 스레드가 정식으로 쓸 수 있게 된 릴리스
> 이후의 구현을 두고 한 말이다.

## 만 개를 던져 보는 시연

- 저자가 태스크마다 새 가상 스레드를 만드는 실행자에 10,000개를 던진다. 각 태스크는 1초를 잘 뿐인
  단순한 일이다 (2장, pp.40–41).[^rahman2025]

  ```java
  try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
      IntStream.range(0, 10_000).forEach(i -> {
          executor.submit(() -> {
              Thread.sleep(Duration.ofSeconds(1));
              return i;
          });
      });
  }
  ```

- 인상적인 대목으로 저자가 꼽는 것은 자원 쪽이다 — JDK가 이것을 최소한의 운영 체제 스레드로,
  잠재적으로는 단 하나로도 처리한다 (2장, p.41).[^rahman2025]
- 대비가 둘이다 — 태스크마다 플랫폼 스레드를 만드는 `Executors.newCachedThreadPool()`을 썼다면
  운영 체제 스레드 10,000개를 만드는 부담 때문에 프로그램이 죽을 수 있고,
  `Executors.newFixedThreadPool(200)` 같은 고정 풀을 쓰면 동시성이 크게 제한되어 많은 태스크가
  차례로 돌고 프로그램이 훨씬 오래 걸린다 (2장, p.41).[^rahman2025]
- 규모를 키운 수치도 있다 — 충분한 워밍업 뒤 가상 스레드는 초당 약 10,000 태스크의 처리량을 낼 수
  있고, 태스크를 1,000,000개로 늘려도 프로그램이 무리 없이 돌며 초당 거의 1,000,000 태스크에
  이르는 처리량을 낸다 (2장, p.41).[^rahman2025]

## 빠름이 아니라 확장이다

- **이 페이지에서 가장 중요한 구분이다** — 가상 스레드는 더 빠르도록 설계된 것이 아니라 더 큰
  확장성을 주도록 설계되었다. 리틀의 법칙을 따르며, 태스크를 더 빨리 실행해서가 아니라 더 큰
  동시성을 가능하게 해서 처리량을 높인다 (2장, p.41).[^rahman2025] 그 법칙의 내용은
  [리틀의 법칙과 처리량](../concepts/littles-law-and-throughput.md)에 있다.
- 실무적 함의도 같은 말의 다른 면이다 — 더 큰 처리량을 얻으려고 프로그래밍 모델을 손보거나 아예
  다시 생각해야 하는 부담에서 개발자를 풀어 준다. 대기가 많은 I/O 바운드 태스크가 많은
  애플리케이션이라면 그 태스크를 쓰는 방식을 바꾸지 않고 처리량을 크게 올릴 수 있다 (2장,
  p.45).[^rahman2025]

## 이득이 나는 두 조건

- 동시 태스크가 많을 때 — 애플리케이션에 동시 태스크가 수천 개를 넘으면 판을 바꾸는 수단이 될 수
  있다. 수천 요청을 동시에 감당해야 하는 대용량 웹 서버나, I/O 바운드 연산을 병렬로 많이 하는
  애플리케이션이 이상적이다 (2장, p.41).[^rahman2025]
- 비CPU 바운드 작업일 때 — 태스크가 CPU 바운드 연산을 하는 시간보다 기다리는 시간(예를 들면 I/O
  연산)이 길수록 이득이 크다 (2장, p.41).[^rahman2025]

## 도움이 되지 않는 자리

- 저자가 유보를 명시적으로 단다 — 가상 스레드가 자바 애플리케이션에 새로운 수준의 확장성을
  들이지만 동시성의 만병통치약은 아니다. 동시 태스크가 많고 그 작업이 가볍고 비CPU 바운드일 때
  가장 효과가 클 가능성이 높다 (2장, p.41).[^rahman2025]
- 병목의 종류가 판단 기준이다 — I/O가 병목이면 처리량이 극적으로 좋아질 수 있지만, 병목이 활성
  동시 태스크의 수가 아니라 가용한 연산 처리량이면 가상 스레드가 도움이 되지 않는다 (2장,
  p.46).[^rahman2025]
- 플랫폼 스레드 쪽에도 같은 종류의 벽이 있다 — 풀을 키우면 처리량이 오르기는 하지만 한계가 있고,
  결국 운영 체제 자원이 제약되며 스레드 관리 부담 자체가 병목이 된다 (2장,
  p.45).[^rahman2025] 그 부담의 내역은
  [스레드의 숨은 비용](../concepts/hidden-costs-of-threads.md)에 있다.

## 요청당 스레드 모델의 부활

- 확장성의 정의부터 저자가 다시 세운다 — 자바에서 확장성은 애플리케이션이 늘어나는 작업량을 어떻게
  감당하는가의 문제이고, 전통적으로 스레드가 I/O 연산과 만나는 방식이 확장성의 큰 병목이었다
  (2장, p.88).[^rahman2025] 저자의 비유에서 플랫폼 스레드는 줄 선 사람들을 앞에 두고 정보 처리나
  네트워크 응답을 기다리는 동안 아무것도 하지 않는 은행 창구 직원이다 (2장, p.88).
- 그래서 서버 쪽 프로그래밍의 고전 모델이 되살아난다 — 가상 스레드는 서버 애플리케이션의 고전적
  요청당 스레드(request-per-thread) 모델을 되살릴 것을 약속하며, 전통적인 스레드를 쓸 때보다
  훨씬 잘 확장되게 만든다 (2장, p.88).[^rahman2025] 그 모델이 어디서 막혔는지는
  [스레드의 숨은 비용](../concepts/hidden-costs-of-threads.md)에 있다.
- 저자가 마지막으로 정리한 이점 여섯은 단순해진 동시성, 향상된 확장성, 자원 효율성, 기존 자바
  관용구와의 호환성, 줄어든 CPU 부담, 간소해진 서버 쪽 프로그래밍이다 (2장,
  pp.87–88).[^rahman2025]
