하나의 질문: **여러 이벤트에 걸치는 연산이 들고 있어야 하는 정보를 어디에 두는가.**

## 상태는 언제 생기는가

- **각 이벤트를 개별적으로 처리하기만 하면 되는 동안 스트림 처리는 매우 단순한
  활동**이다. 책의 예 — **카프카에서 온라인 쇼핑 거래 스트림을 읽어 $10,000 넘는 거래를
  찾아 담당 영업사원에게 메일을 보내는 일이라면 카프카 컨슈머와 SMTP 라이브러리로 몇
  줄이면 된다** (14장, p.388).[^shapira2021]
- **스트림 처리가 정말 흥미로워지는 것은 여러 이벤트에 걸친 연산이 있을 때**다 —
  **유형별 이벤트 개수 세기, 이동 평균, 두 스트림을 조인해 정보가 보강된 스트림 만들기**
  따위다. 이 경우 **각 이벤트를 따로 보는 것으로는 부족하고 더 많은 정보를 추적해야
  한다** — **이번 시간에 유형별로 몇 개의 이벤트를 봤는지, 조인이 필요한 모든 이벤트,
  합계, 평균 등.** **이 정보를 상태(state)라 부른다** (14장, p.388).[^shapira2021]
- 상태를 **스트림 처리 앱의 지역 변수(예: 이동 횟수를 담는 단순한 해시 테이블)에 두고
  싶어지고 이 책의 여러 예제에서도 실제로 그렇게 했지만, 이는 스트림 처리에서 상태를
  관리하는 신뢰성 있는 방법이 아니다** — **스트림 처리 애플리케이션이 멈추거나 크래시하면
  상태가 사라지고 결과가 바뀌기** 때문이다. **대개 원치 않는 결과이므로 가장 최근 상태를
  영속화하고 재시작 시 복구하도록 주의를 기울여야 한다** (14장, p.388).[^shapira2021]

## 로컬 상태와 외부 상태

- **로컬(내부) 상태(local or internal state)** — **스트림 처리 애플리케이션의 특정
  인스턴스만 접근할 수 있는 상태**다. **보통 애플리케이션 안에서 도는 내장 인메모리
  데이터베이스로 유지·관리**된다. **장점은 극단적으로 빠르다는 것이고, 단점은 가용
  메모리 양에 제한된다는 것**이다. **그 결과 스트림 처리의 설계 패턴 다수가 제한된 양의
  로컬 상태로 처리할 수 있는 하위 스트림으로 데이터를 분할하는 방법에 초점**을 둔다
  (14장, p.388).[^shapira2021]
- **외부 상태(external state)** — **외부 데이터 저장소에 유지되는 상태이며 흔히 카산드라
  같은 NoSQL 시스템**이다. **장점은 사실상 무제한의 크기와, 애플리케이션의 여러
  인스턴스나 심지어 다른 애플리케이션에서도 접근할 수 있다는 것.** **단점은 시스템이
  하나 더 늘면서 생기는 추가 지연과 복잡도, 그리고 가용성** — **외부 시스템이 사용
  불가능한 가능성을 애플리케이션이 다뤄야** 한다 (14장, p.389).[^shapira2021]
- **대부분의 스트림 처리 앱은 외부 저장소를 다뤄야 하는 상황을 피하려 하거나, 적어도
  로컬 상태에 정보를 캐시하고 외부 저장소와 되도록 드물게 통신해 지연 오버헤드를
  제한**한다. **이는 대개 내부 상태와 외부 상태 사이의 일관성 유지라는 도전을 끌어들인다**
  (14장, p.389).[^shapira2021]

## 로컬 상태가 떠안는 세 문제

- **애플리케이션이 로컬 상태를 가지면 스트림 처리 애플리케이션은 상당히 더 복잡해진다.**
  다뤄야 할 문제가 셋이다 (14장, pp.394–395):[^shapira2021]
  - **메모리 사용량** — **로컬 상태는 이상적으로는 애플리케이션 인스턴스가 쓸 수 있는
    메모리에 들어가야 한다. 어떤 로컬 저장소는 디스크로 흘려보내는 것을 허용하지만 성능에
    상당한 영향**이 있다.
  - **지속성** — **애플리케이션 인스턴스가 종료될 때 상태가 사라지지 않고, 인스턴스가 다시
    시작하거나 다른 인스턴스로 대체될 때 상태를 복구할 수 있어야 한다.** 이것은 **카프카
    스트림즈가 아주 잘 다루는 부분**이다 — **로컬 상태는 내장 RocksDB를 써서 인메모리로
    저장되고, RocksDB가 재시작 후 빠른 복구를 위해 데이터를 디스크에도 영속화**한다.
    - **그러나 로컬 상태에 대한 모든 변경은 카프카 토픽으로도 보내진다.** **스트림의
      노드가 죽어도 로컬 상태는 사라지지 않는다 — 카프카 토픽에서 이벤트를 다시 읽어
      쉽게 재생성할 수 있다.** 예컨대 **로컬 상태가 "IBM의 현재 최솟값 = 167.19"를
      담고 있으면 이것을 카프카에 저장해 두었다가 나중에 그 데이터로 로컬 캐시를 다시
      채운다.**
    - **카프카는 이 토픽들에 로그 압착을 써서 토픽이 끝없이 자라지 않고 상태 재생성이
      언제나 실행 가능하게 만든다** — 그 압착의 동작은
      [카프카 로그 압착](../concepts/kafka-log-compaction.md).
  - **리밸런싱** — **파티션은 때때로 다른 컨슈머로 재배정된다. 그럴 때 파티션을 잃는
    인스턴스는 마지막으로 좋은 상태를 저장해야 하고, 파티션을 받는 인스턴스는 올바른
    상태를 복구할 줄 알아야 한다.** 재배정 절차 자체는
    [컨슈머 그룹과 리밸런스](../concepts/kafka-consumer-groups-and-rebalance.md).
- **스트림 처리 프레임워크들은 개발자가 필요한 로컬 상태를 관리하는 것을 얼마나 도와
  주는지에서 서로 다르다. 애플리케이션이 로컬 상태 유지를 요구한다면 프레임워크와 그
  보장을 반드시 확인**하라고 책이 권한다 (14장, p.395).[^shapira2021] 확인 항목의 목록은
  [스트림 처리 프레임워크 고르기](../concepts/choosing-a-stream-processing-framework.md).

## 상태가 있으면 정확히 한 번이 요구가 된다

- **스트림 처리 애플리케이션의 핵심 요구는 장애와 무관하게 각 레코드를 정확히 한 번 처리하는
  능력이다. 정확히 한 번 보장이 없으면 정확한 결과가 필요한 경우에 스트림 처리를 쓸 수
  없다** (14장, p.392).[^shapira2021]
- 여기서 14장이 하는 말은 **요구의 진술**까지다 — **8장에서 상세히 논의한 대로 아파치 카프카는
  트랜잭션적·멱등적 프로듀서로 정확히 한 번 의미론을 지원하고, 카프카 스트림즈는 스트림 처리
  애플리케이션의 정확히 한 번 보장을 구현하기 위해 카프카의 트랜잭션을 쓴다**고 넘긴다 (14장,
  p.392).[^shapira2021] 기제 전체 —
  원자적 다수 파티션 쓰기·좀비 펜싱·`isolation.level` — 는
  [카프카 트랜잭션](../concepts/kafka-transactions.md)과
  [멱등적 프로듀서](../concepts/kafka-idempotent-producer.md)가 갖고 있다.
- 스트림 처리 쪽에서 실제로 하는 일은 설정 한 줄이다 — **카프카 스트림즈 라이브러리를 쓰는
  모든 애플리케이션은 `processing.guarantee`를 `exactly_once`로 잡아 정확히 한 번 보장을
  켤 수 있다** (14장, p.392).[^shapira2021]
  - 버전 조건: Kafka 2.6 이상(스트림즈)·2.5 이상(브로커) — **더 효율적인 정확히 한 번
    구현이 포함되며 `processing.guarantee`를 `exactly_once_beta`로 잡아 켠다** (14장,
    p.392).[^shapira2021]
- 왜 집계가 있을 때 이 보장이 특히 중요한지는 8장 쪽이 이미 답해 두었다 —
  [카프카 트랜잭션](../concepts/kafka-transactions.md)의 "무엇을 위해 만들어졌나".

## 상태 저장소를 직접 읽기 — 대화형 질의

- **스트림 처리 애플리케이션은 상태를 갖고 그 상태는 애플리케이션의 많은 인스턴스에 걸쳐
  분산될 수 있다. 대부분의 경우 사용자는 출력 토픽에서 읽어 처리 결과를 얻지만, 어떤
  경우에는 지름길을 택해 상태 저장소 자체에서 결과를 읽는 것이 바람직**하다 (14장,
  p.401).[^shapira2021]
- **결과가 테이블일 때(예: 베스트셀러 도서 상위 10권) 흔한 경우**다 — **결과의 스트림이
  실은 이 테이블에 대한 갱신의 스트림이므로, 스트림 처리 애플리케이션 상태에서 테이블을
  직접 읽는 편이 훨씬 빠르고 쉽다.** **카프카 스트림즈는 스트림 처리 애플리케이션의
  상태를 질의하는 유연한 API를 포함**한다 (14장, p.401).[^shapira2021] 결과가 왜 테이블로
  보이는지는 [스트림-테이블 이중성과 조인](../concepts/stream-table-duality.md).

## 마이크로서비스 쪽에서 같은 축을 다시 가르는 소스

**같은 두 갈래를 서비스 소유자의 물음으로 다시 세우는 소스가 들어왔다.**
[bellemare2025](../sources/bellemare2025.md) 8장이 **내부 상태 저장소(internal state store)** 와
**외부 상태 저장소(external state store)** 라는 이름으로 위
[로컬 상태와 외부 상태](#로컬-상태와-외부-상태)와 같은 축을 가른다. **가르는 축이 같고 묻는 물음이
다르다** — 위 절은 **스트림 처리 잡이 여러 이벤트에 걸친 연산을 어떻게 받치는가**를 묻고, 그쪽은
**서비스를 소유한 팀이 무엇을 떠안는가**를 묻는다.

- **규정이 배치로 적힌다** — 내부 상태 저장소는 **마이크로서비스와 같은 컨테이너나 VM에 있고 대개
  메모리나 휘발성 디스크에 할당되며, 마이크로서비스가 멈추거나 재시작하면 상태 저장소도 그렇다**
  (8장 §"Selecting a State Store for Your Microservice", p.175).[^bellemare2025] 외부 상태
  저장소는 **프로세서의 컨테이너나 VM 바깥에 존재하고 마이크로서비스 생애 주기와 대체로 독립이며,
  마이크로서비스가 재시작되거나 종료되어도 온라인으로 남아 있다** (8장, p.176).[^bellemare2025]
  - **위 절의 규정은 접근 주체로 갈랐고**(특정 인스턴스만 접근하는가), **그쪽은 배치와 생애 주기로
    가른다.** 어긋나지 않고 같은 둘을 다른 잣대로 가리킨다. **이 대비는 이 KB가 두 원문을 맞대어
    세운 것이다.**
- **위 [로컬 상태가 떠안는 세 문제](#로컬-상태가-떠안는-세-문제)에 그쪽이 둘을 더한다** (8장
  §"Disadvantages of Internal State Stores", p.180):[^bellemare2025]
  - **런타임에 정의된 디스크만 쓸 수 있다** — 붙은 볼륨의 크기나 개수를 바꾸려면 대개 서비스를
    멈추고 조정한 뒤 다시 시작해야 하고, **많은 컴퓨트 자원 관리 솔루션이 볼륨 크기를 늘리는 것만
    허용**한다.
  - **디스크 공간 낭비** — 주기적인 트래픽 패턴은 **피크에만 큰 디스크를 요구**하므로, **저장한
    바이트당 과금하는 외부 서비스에 견주면 내내 최대 디스크를 잡아 두는 것이 공간과 돈의 낭비**가
    된다.
  - **둘 다 위 세 문제(메모리·지속성·리밸런싱)에 없는 축이다** — 셋이 **정확성과 복구**의 문제라면
    이 둘은 **운영 비용**의 문제다.
- **위 절이 "장점은 극단적으로 빠르다"고만 적은 자리에 그쪽이 수치를 준다** — **RocksDB로 SSD에서
  무작위 접근 읽기 지연이 약 65마이크로초**여서 **단일 스레드의 순차 접근 상한이 약 15.4k 요청/초**
  이고, **인메모리는 초당 수백만 건**이며, **거기에 왕복 1밀리초의 네트워크 지연만 더해도 상한이
  939 요청/초로 떨어진다** (8장 §"Advantages of Internal State Stores", pp.179–180).
  [^bellemare2025] 그 이유도 적힌다 — **이벤트는 시간 순서와 오프셋 순서를 지키려고 대개 하나씩
  처리되어야 하므로** 단일 처리 스레드가 응답을 기다리는 데 시간을 쓴다.
  - 버전 조건: 2025년 저술 시점의 RocksDB와 SSD 지형에 대한 수치다.
- **체인지로그 복구의 조항 하나가 위 절에 없다** — **상태 복구 중에는 아무 업무 로직도 유발되지
  않고**, 복구 중인 인스턴스는 **새 이벤트를 처리해서는 안 된다** — 그러면 **비결정적이고 잘못된
  결과**가 나올 수 있기 때문이다 (8장, pp.178, 184).[^bellemare2025]
- **그쪽에만 있는 것이 조직과 비용이다** — 외부 상태 저장소를 쓰면 **각 팀이 자원 할당과 확장 정책과
  시스템 모니터링을 직접 구현**해야 하고, 저자는 **그 관리를 별도 팀에 위임하지 말라**고 처방한다 —
  **기술적 팀 간 의존이 생기기** 때문이다 (8장 §"Drawbacks of External State",
  p.186).[^bellemare2025] 대신 **허용되는 외부 데이터 서비스 목록을 관리·확장 안내와 함께 작성해
  두라**고 적는다.
- **이 페이지에만 있는 것은 대화형 질의**다. 그쪽은 상태 저장소를 밖에서 질의하는 축을 다루지 않는다.
- 전역 상태 저장소, 핫 레플리카, 외부 상태의 스냅샷 복구와 오프셋 정렬, 마이그레이션 대신 다시
  지으라는 처방은 전부
  [상태 있는 마이크로서비스와 상태 저장소](../concepts/stateful-microservices-and-state-stores.md)에 있다.

## 미해소

- 대화형 질의 API의 실물(어떤 호출로 어떻게 인스턴스를 찾아 질의하는가)을 이 장은 보여
  주지 않는다. 해소하려면 **카프카 스트림즈 공식 문서(Developer Guide의 Interactive
  Queries 절)** 나 **『Kafka Streams in Action』(William P. Bejeck Jr., Manning)** 이
  필요하다.
- 카프카 스트림즈의 캐싱 동작은 **책이 다루지 않는다고 직접 밝힌** 최적화다 (14장,
  p.411).[^shapira2021] 상태 저장소와는 무관하다고만 적혀 있어, 무엇을 캐시하고 언제
  비우는지는 **카프카 스트림즈 공식 문서(Memory Management 절)** 를 봐야 한다.
