하나의 질문: **지금 "데이터 엔지니어"라 불리는 역할은 어디서 왔고, 그 40년 동안 무엇이
바뀌고 무엇이 되돌아왔는가.**

이 절의 성격을 저자들이 먼저 밝힌다 — **이 절은 역사 수업이 아니지만, 과거를 보는 것은
오늘 우리가 어디에 있고 상황이 어디로 가는지를 이해하는 데 값을 매길 수 없다. 하나의
주제가 끊임없이 다시 나타난다: 낡은 것이 다시 새것이 된다(what's old is new again)** (1장,
p.6).[^reis2022]

## 1980–2000 — 웨어하우징에서 웹으로

- 뿌리 — **데이터 엔지니어의 탄생은 논쟁의 여지는 있으나 데이터 웨어하우징에 뿌리를
  두며, 1970년대까지 거슬러 간다. 업무 데이터 웨어하우스(business data warehouse)가
  1980년대에 형태를 갖췄고 Bill Inmon이 1989년에 데이터 웨어하우스라는 용어를
  공식적으로 만들었다** (1장, p.6).[^reis2022]
- **IBM의 엔지니어들이 관계형 데이터베이스와 SQL(Structured Query Language)을 개발한
  뒤 오라클이 그 기술을 대중화했다. 신생 데이터 시스템이 커지면서 기업은 리포팅과
  비즈니스 인텔리전스(BI)를 위한 전용 도구와 데이터 파이프라인을 필요로 했다. 사람들이
  업무 로직을 데이터 웨어하우스에 올바르게 모델링하도록 돕기 위해 Ralph Kimball과
  Inmon이 각자의 이름을 딴 데이터 모델링 기법과 접근을 개발했고, 그것들은 오늘날에도
  널리 쓰인다** (1장, p.6).[^reis2022] 그 두 갈래의 내용은
  [데이터 웨어하우스 모델링](../synthesis/data-warehouse-modeling.md)에 있다.
- 첫 확장 가능 분석 — **데이터 웨어하우징은 확장 가능한 분석의 첫 시대를 열었다. 여러
  프로세서로 대량의 데이터를 처리하는 새로운 대규모 병렬 처리(massively parallel
  processing, MPP) 데이터베이스가 시장에 나와 전례 없는 데이터 볼륨을 지원했다** (1장,
  p.6).[^reis2022]
- 그때 생긴 역할들 — **BI 엔지니어·ETL 개발자·데이터 웨어하우스 엔지니어 같은 역할이
  데이터 웨어하우스의 여러 필요를 감당했다. 데이터 웨어하우스와 BI 엔지니어링은 오늘날
  데이터 엔지니어링의 선구였고 여전히 이 분야에서 중심 역할을 한다** (1장,
  p.6).[^reis2022]
- 웹이 온다 — **인터넷이 1990년대 중반 주류가 되면서 AOL·야후·아마존 같은 웹 우선 회사의
  새 세대가 생겼다. 닷컴 붐은 웹 애플리케이션과 그것을 뒷받침하는 백엔드 시스템 — 서버·
  데이터베이스·저장소 — 에 엄청난 활동을 낳았다. 인프라 상당수는 비싸고, 모놀리식이며,
  라이선스가 무거웠다. 이 백엔드 시스템을 팔던 벤더들은 웹 애플리케이션이 만들어 낼
  데이터의 규모를 예견하지 못했을 것이다** (1장, p.6).[^reis2022]

## 2000년대 초 — 현대 데이터 엔지니어링의 탄생

- 상황 — **닷컴 붕괴 뒤 살아남은 야후·구글·아마존 같은 회사들은 처음에 1990년대의
  전통적이고 모놀리식한 관계형 데이터베이스와 데이터 웨어하우스에 계속 의존하며 그
  시스템을 한계까지 밀어붙였다. 그 시스템들이 휘청이면서 데이터 성장을 감당할 갱신된
  접근이 필요해졌다. 새 세대의 시스템은 비용 효율적이고, 확장 가능하고, 가용하고,
  신뢰할 수 있어야 했다** (1장, pp.6–7).[^reis2022]
- 하드웨어 조건 — **데이터 폭증과 때를 같이해 서버·RAM·디스크·플래시 드라이브 같은
  범용 하드웨어(commodity hardware)도 싸고 흔해졌다. 여러 혁신이 방대한 규모의 거대
  컴퓨팅 클러스터 위에서 분산 연산과 저장을 가능하게 했다. 이 혁신들은 전통적으로
  모놀리식했던 서비스를 탈중앙화하고 쪼개기 시작했다. "빅데이터" 시대가 시작됐다** (1장,
  p.7).[^reis2022]
- 빅데이터의 두 정의 (1장, p.7):[^reis2022]
  - **옥스퍼드 영어사전은 빅데이터(big data)를 "특히 인간의 행동과 상호작용에 관해
    패턴·추세·연관을 드러내기 위해 계산적으로 분석될 수 있는 극히 큰 데이터
    집합"으로 정의한다.**
  - **또 하나의 유명하고 간결한 서술은 데이터의 세 V다 — 속도(velocity)·다양성
    (variety)·볼륨(volume).**
- 빅뱅 — **2003년 구글이 Google File System 논문을, 곧이어 2004년에 초확장 가능한
  데이터 처리 패러다임인 맵리듀스(MapReduce) 논문을 발표했다. 사실 빅데이터에는 MPP
  데이터 웨어하우스와 실험 물리 프로젝트의 데이터 관리라는 더 앞선 선행자가 있지만,
  구글의 발표는 데이터 기술의 "빅뱅"이자 오늘날 우리가 아는 데이터 엔지니어링의 문화적
  뿌리를 이뤘다** (1장, p.7).[^reis2022] 맵리듀스 자체의 기제는
  [맵리듀스](../concepts/mapreduce.md)에 있다.
- 하둡 — **구글의 논문들은 야후의 엔지니어들이 아파치 하둡(Apache Hadoop)을 개발하고
  2006년에 오픈 소스화하도록 자극했다. 하둡의 영향은 과장하기 어렵다. 회사들이 규모를
  가리지 않고 자기 데이터가 수 테라바이트, 심지어 페타바이트로 자라는 것을 보면서
  빅데이터 엔지니어의 시대가 태어났다** (1장, p.7).[^reis2022]
- 공용 클라우드 — **비슷한 시기 아마존은 자기 데이터 수요를 따라잡아야 했고 탄력적
  컴퓨팅 환경(EC2), 무한히 확장 가능한 저장 시스템(S3), 고확장성 NoSQL 데이터베이스
  (DynamoDB)를 비롯한 여러 핵심 데이터 구성 요소를 만들었다. 아마존은 이 서비스들을
  AWS를 통해 내부·외부 소비에 제공하기로 선택해 첫 인기 공용 클라우드가 됐다. AWS는
  방대한 범용 하드웨어 풀을 가상화해 되팔면서 초유연한 종량제 자원 시장을 만들었다**
  (1장, p.7).[^reis2022]
- 판정 — **공용 클라우드는 논쟁의 여지는 있으나 21세기의 가장 중요한 혁신 중 하나이며
  소프트웨어와 데이터 애플리케이션이 개발·배포되는 방식에 혁명을 일으켰다. 초기 빅데이터
  도구와 공용 클라우드가 오늘날 데이터 생태계의 기반을 놓았다** (1장, p.8).[^reis2022]

## 2000–2010년대 — 빅데이터 엔지니어링

- 확산 — **하둡 생태계의 오픈 소스 빅데이터 도구가 빠르게 성숙해 실리콘밸리에서
  전 세계의 기술에 밝은 회사들로 퍼졌다. 처음으로 어떤 기업이든 최상위 기술 기업이 쓰는
  것과 같은 최첨단 데이터 도구에 접근할 수 있게 됐다** (1장, p.8).[^reis2022]
- 또 하나의 전환 — **배치 컴퓨팅에서 이벤트 스트리밍으로의 이행이라는 또 다른 혁명이
  일어나 큰 "실시간" 데이터의 새 시대를 열었다** (1장, p.8).[^reis2022] 두 축의 내용은
  [배치 처리](../synthesis/batch-processing.md)와
  [스트림 처리](../synthesis/stream-processing.md)에 있다.
- 그 시절의 도구 목록 — **하둡·Apache Pig·Apache Hive·Dremel·Apache HBase·Apache
  Storm·Apache Cassandra·Apache Spark·Presto 등. 전통적인 엔터프라이즈 지향·GUI 기반
  데이터 도구가 갑자기 시대에 뒤진 것처럼 느껴졌고, 맵리듀스의 부상과 함께 코드 우선
  엔지니어링이 유행했다** (1장, p.8).[^reis2022]
- 빅데이터 엔지니어라는 역할 — **이 도구와 기법 — 하둡·YARN·HDFS·맵리듀스 — 을 효과적으로
  쓰려면 빅데이터 엔지니어는 소프트웨어 개발과 저수준 인프라 해킹에 능숙해야 했다. 다만
  강조점이 옮겨져 있었다. 빅데이터 엔지니어는 보통 규모에 맞춰 데이터를 전달하기 위해
  범용 하드웨어의 거대한 클러스터를 유지했다. 하둡 코어 코드에 이따금 PR을 보낼 수는
  있었지만 초점은 핵심 기술 개발이 아니라 데이터 전달에 있었다** (1장, p.8).[^reis2022]

## 빅데이터가 힘을 잃은 이유

- 자기 성공의 희생자 — **빅데이터는 빠르게 자기 성공의 희생자가 됐다. 유행어로서
  2000년대 초부터 2010년대 중반까지 인기를 누렸다. 엄청난 과대 선전 때문에 회사들이
  작은 데이터 문제에 빅데이터 도구를 쓰는 것을 흔히 볼 수 있었고, 때로는 겨우 몇
  기가바이트를 처리하려 하둡 클러스터를 세우기도 했다** (1장, p.8).[^reis2022]
- 그때 인용되는 말 — **Dan Ariely는 "빅데이터는 십 대의 섹스와 같다: 모두가 그것에 대해
  말하고, 아무도 실제로 어떻게 하는지 모르며, 모두가 다른 모두는 하고 있다고 생각해서,
  모두가 자기도 하고 있다고 주장한다"고 트윗했다** (1장, pp.8–9).[^reis2022]
- 무슨 일이 있었나 — **한 단어: 단순화(simplification). 오픈 소스 빅데이터 도구의 힘과
  정교함에도 그것을 관리하는 일은 많은 작업이었고 끊임없는 주의를 요구했다. 회사들은
  흔히 이 플랫폼을 돌보게 하려고 연간 수백만 달러를 들여 빅데이터 엔지니어 팀 전체를
  고용했다. 빅데이터 엔지니어는 복잡한 도구를 유지하는 데 과도한 시간을 썼고 사업의
  통찰과 가치를 전달하는 데는 그만큼 쓰지 못했다** (1장, p.9).[^reis2022]
- 그래서 — **오픈 소스 개발자·클라우드·서드파티가 자기 클러스터를 관리하고 오픈 소스
  코드를 설치·설정·업그레이드하는 높은 관리 부담과 비용 없이 빅데이터를 추상화하고
  단순화해 이용 가능하게 만들 길을 찾기 시작했다** (1장, p.9).[^reis2022]
- 남은 것 — **빅데이터라는 용어는 본질적으로 대량의 데이터를 다루는 특정 시기와 접근을
  가리키는 유물(relic)이다. 오늘날 데이터는 어느 때보다 빠르게 움직이고 계속 커지지만,
  빅데이터 처리가 워낙 접근 가능해져 별도의 용어를 붙일 값어치가 없어졌다. 모든 회사가
  실제 데이터 크기와 무관하게 자기 데이터 문제를 풀려 한다. 빅데이터 엔지니어는 이제
  그냥 데이터 엔지니어다** (1장, p.9).[^reis2022]

## 2020년대 — 수명 주기를 위한 엔지니어링

- 방향 — **데이터 엔지니어는 역사적으로 하둡·스파크·인포매티카 같은 모놀리식
  프레임워크의 저수준 세부를 돌봤지만, 추세는 탈중앙화되고, 모듈화되고, 관리형이며,
  고도로 추상화된 도구 쪽으로 옮겨 가고 있다** (1장, p.10).[^reis2022]
- **2020년대 초의 인기 있는 추세로는 모던 데이터 스택(modern data stack)이 있는데,
  분석가의 삶을 편하게 하려고 조립한 기성 오픈 소스·서드파티 제품의 모음을 가리킨다.
  동시에 데이터 원천과 데이터 형식은 다양성과 크기 양쪽에서 자라고 있다. 데이터
  엔지니어링은 점점 더 상호운용(interoperation)의 분야이자, 궁극의 사업 목표를 섬기기
  위해 여러 기술을 레고 블록처럼 잇는 분야가 되고 있다** (1장, p.10).[^reis2022]
- 이 책이 쓰는 이름 — **이 책이 논하는 데이터 엔지니어는 더 정확히는 데이터 수명 주기
  엔지니어(data lifecycle engineer)로 서술될 수 있다. 더 큰 추상과 단순화 덕에 데이터
  수명 주기 엔지니어는 더 이상 어제의 빅데이터 프레임워크의 잔혹한 세부에 매이지
  않는다. 저수준 데이터 프로그래밍 기술은 유지하되 역할의 초점은 가치 사슬의 더 높은
  곳 — 보안·데이터 관리·DataOps·데이터 아키텍처·오케스트레이션·일반적 데이터 수명 주기
  관리 — 으로 옮겨 간다** (1장, p.10).[^reis2022]
- 태도의 변화 — **"누가 가장 큰 데이터를 가졌는가"에 집중하는 대신, 오픈 소스 프로젝트와
  서비스가 데이터를 관리·통치하고, 쓰고 발견하기 쉽게 만들고, 품질을 높이는 데 점점 더
  관심을 둔다. 데이터 엔지니어는 이제 CCPA·GDPR 같은 약어에 능통하며, 파이프라인을
  만들면서 프라이버시·익명화·데이터 가비지 컬렉션·규제 준수를 함께 걱정한다** (1장,
  pp.10–11).[^reis2022]
- 되돌아온 것 — **낡은 것이 다시 새것이 된다. 데이터 품질과 거버넌스를 포함한 데이터
  관리 같은 "엔터프라이즈스러운" 것은 빅데이터 이전 시대에 대기업에서 흔했지만 작은
  회사에는 널리 채택되지 않았다. 어제의 데이터 시스템의 어려운 문제 상당수가 풀리고
  말끔히 제품화·패키징된 지금, 기술자와 창업가는 초점을 다시 그 "엔터프라이즈스러운"
  것으로 옮겼다. 다만 전통적 엔터프라이즈의 명령·통제 접근과 대비되는 탈중앙화와
  민첩성을 강조한다** (1장, p.11).[^reis2022]
- 저자들의 자리매김 — **우리는 현재를 데이터 수명 주기 관리의 황금기로 본다** (1장,
  p.11).[^reis2022]

## 그다음은 — 저자들이 본 역할의 미래

11장의 이 서술은 **관측이 아니라 2022년 시점 저자들의 전망**이다 — 그들 스스로 "야생의 추측"을
포함한다고 밝힌다. 그래서 각 항목에 `#hypothesis`를 붙였다. 기술 전망 쪽은
[라이브 데이터 스택](../concepts/live-data-stack.md)에 있다.

- 수명 주기는 사라지지 않는다 — **데이터 과학이 최근 몇 년 주목의 대부분을 받았지만 데이터
  엔지니어링은 빠르게 뚜렷하고 가시적인 분야로 성숙하고 있다. 그것은 기술에서 가장 빠르게 자라는
  경력 중 하나이며 동력을 잃을 기미가 없다. 회사들이 AI와 ML 같은 "섹시한" 것으로 옮기기 전에
  먼저 데이터 기반을 지어야 함을 깨달으면서 데이터 엔지니어링은 인기와 중요성에서 계속 자랄
  것이다. 이 진보는 데이터 엔지니어링 수명 주기를 중심에 둔다** (11장, p.380).[^reis2022]
  #hypothesis
- "도구가 쉬워지면 직업이 사라지는가"에 대한 반박 — **어떤 이들은 점점 단순해지는 도구와 실무가
  데이터 엔지니어의 소멸로 이어질지 묻는다. 이 생각은 얕고 게으르며 근시안적이다. 조직이 새로운
  방식으로 데이터를 활용하면서 이 필요를 다룰 새 기반·시스템·워크플로가 요구될 것이다. 데이터
  엔지니어는 이 시스템을 설계·아키텍팅·구축·유지하는 중심에 앉는다. 도구 사용이 쉬워지면 데이터
  엔지니어는 더 높은 수준의 일에 집중하기 위해 가치 사슬을 올라갈 것이다. 데이터 엔지니어링 수명
  주기는 조만간 사라지지 않는다** (11장, p.380).[^reis2022] #hypothesis
- 복잡도의 하락 — **단순하고 쓰기 쉬운 도구가 데이터 엔지니어링의 진입 장벽을 계속 낮추고 있다.
  단순성을 향한 추세는 계속될 것이다. 데이터 엔지니어링은 특정 기술이나 데이터 크기에 의존하지
  않는다. 그것은 큰 회사만의 것도 아니다. 2000년대에 "빅데이터" 기술을 배포하려면 큰 팀과 깊은
  주머니가 필요했다. SaaS 관리형 서비스의 부상은 다양한 "빅데이터" 시스템의 내장을 이해해야 하는
  복잡성을 대체로 제거했다. 데이터 엔지니어링은 이제 *모든* 회사가 할 수 있는 것이다** (11장,
  p.380).[^reis2022] #hypothesis
  - 예시 — **빅데이터는 자신의 비범한 성공의 희생자다. 예컨대 GFS와 MapReduce의 후예인 Google
    BigQuery는 페타바이트의 데이터를 질의할 수 있다. 한때 구글 내부용으로만 예약됐던 이 미친
    듯이 강력한 기술이 이제 GCP 계정을 가진 누구에게나 가용하다. 사용자는 방대한 인프라 스택을
    지을 필요 없이 저장하고 질의하는 데이터에 대해 지불하기만 한다** (11장,
    p.380).[^reis2022]
  - 오픈 소스의 위상 변화 — **클라우드는 오픈 소스 도구 사용에서 유의한 전환에 책임이 있다.
    2010년대 초에도 오픈 소스를 쓰는 것은 통상 코드를 내려받아 직접 설정하는 것을 수반했다.
    요즘 많은 오픈 소스 데이터 도구가 독점 서비스와 직접 경쟁하는 관리형 클라우드 서비스로
    가용하다. 이는 오픈 소스 코드를 둘러싼 대화를 근본적으로 바꾼다. 많은 경우 관리형 오픈
    소스는 독점 서비스 경쟁자만큼 쓰기 쉽다** (11장, pp.380–381).[^reis2022]
  - 커넥터도 외주가 된다 — **또 하나 유의한 추세는 기성 데이터 커넥터의 인기 성장이다(이 글을
    쓰는 시점에 인기 있는 것으로 Fivetran·Airbyte가 있다). 데이터 엔지니어는 전통적으로 외부
    데이터 원천에 연결하는 배관을 짓고 유지하는 데 많은 시간과 자원을 썼다. 새 세대의 관리형
    커넥터는 고도로 기술적인 엔지니어에게도 설득력이 있다 — 그들이 다른 프로젝트를 위해 시간과
    정신적 대역폭을 되찾는 가치를 인식하기 시작하면서다. API 커넥터는 외주화된 문제가 되어
    데이터 엔지니어가 자기 업무를 이끄는 고유한 문제에 집중할 수 있게 될 것이다** (11장,
    p.381).[^reis2022] #hypothesis
- "엔터프라이지"해진다 — **데이터 도구의 증가하는 단순화와 모범 실무의 출현·문서화는 데이터
  엔지니어링이 더 "엔터프라이지"해짐을 뜻한다. 이는 많은 독자를 격렬히 움츠러들게 할 것이다.
  어떤 이에게 *엔터프라이즈*라는 용어는 지나치게 빳빳한 파란 셔츠와 카키를 입은 얼굴 없는
  위원회들의 카프카적 악몽, 끝없는 관료주의, 계속 미끄러지는 일정과 부풀어 오르는 예산의
  폭포수식 관리 프로젝트를 불러낸다** (11장, p.383).[^reis2022]
  - 그러나 무엇을 뜻하는가 — **다행히 그것은 우리가 말하는 것이 아니다. 우리는 더 큰 회사가
    데이터로 하는 *좋은* 것들 — 관리·운영·거버넌스와 다른 "지루한" 것 —을 가리킨다. 우리는
    현재 "엔터프라이지"한 데이터 관리 도구의 황금기를 살고 있다. 한때 거대 조직에만 예약됐던
    기술과 실무가 아래로 흘러내리고 있다. 빅데이터와 스트리밍 데이터의 한때 어려웠던 부분들이
    이제 대체로 추상화됐고 초점은 사용 편의성·상호운용성·다른 세련됨으로 옮겨 갔다** (11장,
    p.383).[^reis2022] #hypothesis
- 직함과 책임이 변형된다 — **데이터 엔지니어링 수명 주기가 조만간 어디로 가지 않는 동안,
  소프트웨어 엔지니어링·데이터 엔지니어링·데이터 과학·ML 엔지니어링 사이의 경계는 점점 더
  흐릿하다. 사실 이 책의 저자들처럼 많은 데이터 과학자가 유기적 과정을 통해 데이터 엔지니어로
  변형된다 — "데이터 과학"을 하도록 맡겨졌지만 자기 일을 할 도구가 없어, 데이터 엔지니어링
  수명 주기를 서빙할 시스템을 설계하고 짓는 일을 떠맡는 것이다** (11장, p.384).[^reis2022]
  - 시간 배분이 옮겨 간다 — **단순성이 스택 위로 올라가면서 데이터 과학자는 데이터를 모으고
    다듬는 데 자기 시간의 더 작은 조각을 쓸 것이다. 그러나 이 추세는 데이터 과학자를 넘어
    확장될 것이다. 단순화는 또한 데이터 엔지니어가 데이터 엔지니어링 수명 주기의 저수준
    태스크(서버·설정 관리 등)에 더 적은 시간을 쓴다는 뜻이며, "엔터프라이지" 데이터
    엔지니어링이 더 널리 퍼질 것이다** (11장, p.384).[^reis2022] #hypothesis
  - 새 역할 하나 — **데이터가 모든 사업의 프로세스에 더 단단히 임베드되면서 데이터와 알고리즘의
    영역에 새 역할이 나타날 것이다. 한 가능성은 ML 엔지니어링과 데이터 엔지니어링 사이에 앉는
    역할이다. ML 도구 모음이 쓰기 쉬워지고 관리형 클라우드 ML 서비스가 능력을 키우면서 ML은
    애드혹 탐색과 모델 개발에서 벗어나 운영 분야가 되고 있다** (11장, p.384).[^reis2022]
    #hypothesis
  - 그 역할이 하는 일 — **이 경계를 걸치는 새 ML 지향 엔지니어는 알고리즘·ML 기법·모델 최적화·
    모델 모니터링·데이터 모니터링을 알 것이다. 그러나 그들의 일차 역할은 잘 이해된 모델 유형에
    대해 모델을 자동으로 학습시키고 성능을 모니터링하며 전체 ML 프로세스를 운영화하는 시스템을
    만들거나 활용하는 것이다. 그들은 데이터 파이프라인과 품질도 모니터링해 현재의 데이터
    엔지니어링 영역과 겹칠 것이다. ML 엔지니어는 연구에 더 가깝고 덜 이해된 모델 유형에서 일하도록
    더 특화될 것이다** (11장, p.384).[^reis2022] #hypothesis
  - 소프트웨어 엔지니어링 쪽 경계 — **직함이 변형될 또 한 영역은 소프트웨어 엔지니어링과 데이터
    엔지니어링의 교차점이다. 전통적 소프트웨어 애플리케이션을 분석과 섞는 데이터 애플리케이션이
    이 추세를 이끌 것이다. 소프트웨어 엔지니어는 데이터 엔지니어링을 훨씬 더 깊이 이해해야 할
    것이다. 그들은 스트리밍·데이터 파이프라인·데이터 모델링·데이터 품질 같은 것에 전문성을
    개발할 것이다. 우리는 지금 만연한 "담 너머로 던지기" 접근을 넘어설 것이다. 데이터 엔지니어는
    애플리케이션 개발 팀에 통합될 것이고 소프트웨어 개발자는 데이터 엔지니어링 기술을 획득할
    것이다. 애플리케이션 백엔드 시스템과 데이터 엔지니어링 도구 사이에 존재하는 경계도, 스트리밍과
    이벤트 주도 아키텍처를 통한 깊은 통합으로 낮아질 것이다** (11장, p.384).[^reis2022]
    #hypothesis

## 다른 소스가 같은 역할을 병목으로 읽을 때

- 위 서사가 역할의 **역량 변화**를 추적한다면, 데이터 메시의 제안자는 같은 역할의 **조직적
  위치**를 문제로 본다. 진단의 출발은 콘웨이의 법칙이다 — **조직 관점에서 콘웨이의
  법칙(Conway's law)이 모놀리식 조직 구조 — 비즈니스 인텔리전스 팀·데이터 분석 그룹·데이터
  플랫폼 팀 — 와 함께 완전히 작동해 왔다** (8장, p.130).[^dehghani2022]
- 그 구조 안의 데이터 엔지니어가 어디 서 있는가 — **데이터 플랫폼을 짓고 운영하는 사람들의
  삶을 관찰할 만큼 가까이 줌인하면, 데이터가 비롯되거나 사용되는 조직의 운영 단위에서
  사일로화된 초전문화 데이터 엔지니어 집단을 발견한다. 데이터 엔지니어들은 조직적으로
  사일로화되었을 뿐 아니라 업무·도메인 지식이 대개 부재한 채 데이터 도구에 대한 기술
  전문성에 근거해 한 팀으로 분리·묶음되어 있다** (8장, pp.130–131).[^dehghani2022]
  - 결과로 그려지는 세 자리 — **현실에서 우리가 발견하는 것은 단절된 원천 팀, 데이터 팀의
    백로그 위 자리를 두고 다투는 좌절한 소비자, 그리고 과도하게 늘어나고 저평가된 데이터
    팀이다** (8장, p.131).[^dehghani2022]
- **부분적 대응은 안티패턴으로 명시된다** — **최근 몇 해 사이 중앙 데이터 팀을 도메인 지향
  데이터 팀으로 분해하려는 움직임이 있었다. 그것이 개선이기는 하지만 장기적 데이터 소유권과
  데이터 품질의 문제를 풀지 못한다. 데이터 팀은 실제 도메인에서 여전히 멀고, 도메인 시스템의
  변경 및 그들의 필요와 동기화되지 않은 채로 남는다. 이것은 안티패턴이다** (8장,
  p.136).[^dehghani2022]
- **두 서술은 충돌하지 않고 축이 다르다.** 위
  [그다음은](#그다음은--저자들이-본-역할의-미래)의 예측(데이터 엔지니어가 애플리케이션 개발
  팀에 통합되고 소프트웨어 개발자가 데이터 엔지니어링 기술을 얻는다)과 Dehghani의 처방(도메인
  교차 기능 팀이 분석 데이터를 소유한다)은 **같은 방향을 가리킨다** — 갈리는 것은 그것을
  추세 예측으로 보느냐 설계 원칙으로 보느냐다. 후자의 전문은
  [도메인 소유권 원칙](../concepts/domain-ownership-principle.md)과
  [분석 데이터 아키텍처 세대론](../concepts/analytical-data-architecture-generations.md)에 있다.

### 같은 저자가 16장에서 내놓는 행선지

위 진단이 **어디로 가는가**까지 적히는 것이 이 소스의 마지막 장이다. 예측이 아니라 배치표다.

- 데이터 전문가의 자리 — **데이터 전문가 — 데이터 엔지니어나 데이터 과학자 — 다수가 도메인 교차
  기능 팀에 합류할 것이다. 그들은 종단 결과를 전달하는 스트림 정렬 팀에서 일할 것이다. **그들은
  더 이상 하나의 고립된 단계에서 일하지 않는다.** 이것은 소프트웨어 공학 실무·기술을 써서 더
  긴밀한 협업과 통합을 뜻한다. 교육 프로그램은 데이터 전문가가 코딩·테스팅·지속적 전달 같은
  소프트웨어 공학 실무를 배우도록 도와야 한다** (16장, p.329).[^dehghani2022]
- 기대치의 상한이 양쪽에 명시된다 — **데이터 메시는 사람들이 데이터 전문가가 되기를 기대하지
  않지만, **자기 데이터의 전문가**가 되기를 기대한다. (…) 비슷하게 **데이터 전문가가 소프트웨어
  엔지니어와 나란히, 그리고 흐름 안에서 일하며** 데이터를 관리하고·적용하고·공유할 때 소프트웨어
  공학의 에버그린 실무를 익히기를 기대한다** (16장, p.328).[^dehghani2022]
- **소멸하는 역할도 명시된다** — 데이터 커스터디언(data custodian)에 대해 **이 역할은
  폐지(deprecated)되고 도메인의 데이터 프로덕트 개발자 역할로 옮겨진다**고 적고, 데이터
  스튜어드는 **도메인의 데이터 프로덕트 소유자**가 되거나 **플랫폼으로 옮겨 데이터 품질 테스트·
  관측 가능성·복구를 자동화하는 전문가**가 된다고 적는다 (16장, p.326).[^dehghani2022]
- 위 Reis·Housley의 "데이터 엔지니어가 가치 사슬의 더 높은 곳으로 옮긴다"와 대조하면, Dehghani
  쪽은 **위가 아니라 옆으로** 옮긴다 — 전문성의 계층이 올라가는 것이 아니라 도메인 팀 안으로
  분산된다. 역할 전체의 지도는
  [데이터 메시의 역할과 역량](../concepts/data-mesh-roles-and-skills.md)에 있다.
