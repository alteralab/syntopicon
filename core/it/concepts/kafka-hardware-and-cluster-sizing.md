하나의 질문: **브로커 한 대에 어떤 장비를 쓰고 클러스터를 몇 대로 할지 무엇을 보고
정하는가.**

## 병목 다섯 가지

- 하드웨어 선택의 성격부터 원문 직인용 (2장, p.33):[^shapira2021]

> Selecting an appropriate hardware configuration for a Kafka broker can be more art
> than science. Kafka itself has no strict requirement on a specific hardware
> configuration and will run without issue on most systems.

- 성능을 고려하기 시작하면 병목에 기여하는 요소가 나온다 — **디스크 처리량과 용량, 메모리,
  네트워크, CPU.** 카프카를 아주 크게 확장할 때는 갱신해야 하는 메타데이터 양 때문에
  **브로커 한 대가 다룰 수 있는 파티션 수에도 제약**이 생긴다 (2장,
  p.33).[^shapira2021]
- 순서는 정해져 있다 — **어떤 성능 유형이 가장 중요한지 먼저 판정한 뒤** 그에 맞춰 예산
  안에서 최적화된 구성을 고른다 (2장, p.33).[^shapira2021]

## 디스크 처리량

- 프로듀서 클라이언트의 성능은 **로그 세그먼트를 저장하는 브로커 디스크의 처리량에 가장
  직접적으로 영향받는다** (2장, p.33).[^shapira2021]
  - 이유의 사슬: 메시지는 생산될 때 로컬 저장소에 커밋되어야 하고, 대부분의 클라이언트는
    최소 한 브로커가 커밋을 확인할 때까지 기다린다. **그래서 디스크 쓰기가 빠를수록 생산
    지연이 낮아진다.**
- HDD와 SSD의 판단 기준 (2장, pp.33–34):[^shapira2021]
  - SSD는 탐색·접근 시간이 극적으로 낮아 최고 성능을 낸다.
  - HDD는 더 경제적이고 단위당 용량이 크며, **브로커에 여러 개를 쓰면(데이터 디렉터리를
    여러 개 두거나 RAID로 묶어) 성능을 개선할 수 있다.**
  - 드라이브 기술(SAS/SATA)과 드라이브 컨트롤러 품질도 처리량에 영향을 준다.
  - 일반적 관찰: **저장 요구가 아주 크지만 자주 접근되지 않는 클러스터에는 HDD가 유용하고,
    클라이언트 연결이 아주 많은 경우에는 SSD가 낫다.**

## 디스크 용량

- 필요한 용량은 **어느 시점에나 보존해야 하는 메시지 양**이 결정한다 (2장,
  p.34).[^shapira2021]
- 계산 예시: 하루 1TB 트래픽에 보존 7일이면 로그 세그먼트에 **최소 7TB의 사용 가능
  저장소**가 필요하다. 여기에 **다른 파일을 위한 오버헤드 최소 10%**와 트래픽 변동·성장에
  대비한 버퍼를 더한다 (2장, p.34).[^shapira2021]
- 클러스터 관점에서도 같은 요소가 쓰인다 — **클러스터 크기 산정과 확장 시점 판단**의 근거가
  된다. 토픽마다 파티션을 여럿 두면 클러스터 전체 트래픽이 분산되므로, **브로커 한 대의
  밀도로 부족하면 브로커를 더해 가용 용량을 늘릴 수 있다.** 필요한 용량은 클러스터가 고른
  복제 전략에도 좌우된다 (2장, p.34).[^shapira2021]

## 메모리 — 페이지 캐시가 주인공

- 컨슈머의 정상 동작은 **파티션의 끝에서 읽는 것**이며, 이때 컨슈머는 프로듀서를 거의 따라
  붙어 있다. 이 상황에서 읽히는 메시지는 **시스템의 페이지 캐시에 최적으로 저장돼 있어
  브로커가 디스크에서 다시 읽는 것보다 빠르다.** 그래서 시스템에 페이지 캐시용 메모리가
  많을수록 컨슈머 성능이 좋아진다 (2장, p.34).[^shapira2021]
- 뒤집으면 힙은 클 필요가 없다 — **카프카 자체는 JVM에 많은 힙 메모리를 필요로 하지 않는다.
  초당 15만 메시지와 초당 200메가비트 데이터율을 처리하는 브로커도 5GB 힙으로 돌 수 있다**
  (2장, p.34).[^shapira2021]
- 나머지 시스템 메모리는 페이지 캐시로 쓰여 사용 중인 로그 세그먼트를 캐시해 카프카에 이득이
  된다. **이것이 카프카를 다른 중요 애플리케이션과 같은 시스템에 두지 말라고 권고하는 주된
  이유**다 — 페이지 캐시를 나눠 써야 하므로 컨슈머 성능이 떨어진다 (2장,
  p.34).[^shapira2021]

## 네트워크

- 가용 네트워크 처리량이 카프카가 다룰 수 있는 트래픽의 상한을 정하며, **디스크 저장소와
  더불어 클러스터 크기를 지배하는 요인**이 된다 (2장, p.35).[^shapira2021]
- 복잡하게 만드는 것은 비대칭이다 — **카프카가 다중 컨슈머를 지원하기 때문에 인바운드와
  아웃바운드 네트워크 사용량 사이에 본질적 불균형이 생긴다.** 프로듀서가 특정 토픽에 초당
  1MB를 써도, 그 토픽을 읽는 컨슈머 수만큼 아웃바운드가 배수로 늘어난다 (2장,
  p.35).[^shapira2021]
- 여기에 클러스터 복제와 미러링이 더해져 아웃바운드를 더 키운다. **네트워크 인터페이스가
  포화되면 클러스터 복제가 뒤처지는 일이 드물지 않고, 그러면 클러스터가 취약한 상태에
  놓인다** (2장, p.35).[^shapira2021]
- 권고는 명시적이다 — **최소 10Gb NIC로 운영하라. 1Gb NIC를 쓰는 옛 장비는 쉽게 포화되며
  권장되지 않는다** (2장, p.35).[^shapira2021]

## CPU

- 처리 능력은 **디스크와 메모리만큼 중요하지 않지만, 아주 크게 확장하기 시작하면 브로커의
  전반적 성능에 어느 정도 영향을 준다** (2장, p.35).[^shapira2021]
- CPU 요구가 어디서 오는지가 판단의 근거다 — 클라이언트는 네트워크와 디스크 사용을
  최적화하려고 메시지를 압축하는 것이 이상적인데, **브로커는 개별 메시지의 체크섬을 검증하고
  오프셋을 배정하기 위해 모든 메시지 배치의 압축을 풀어야 한다. 그 뒤 디스크에 저장하려고
  다시 압축한다. 카프카의 처리 능력 요구 대부분이 여기서 나온다** (2장,
  p.35).[^shapira2021]
- 그럼에도 **하드웨어 선택의 주된 요인이 되어서는 안 된다** — 다만 클러스터가 노드 수백
  대와 파티션 수백만 개 규모로 아주 커지면, 성능 좋은 CPU를 골라 클러스터 크기를 줄이는
  데 도움이 된다 (2장, p.35).[^shapira2021]

## 클라우드

- 최근에는 클라우드 컴퓨팅 환경에 설치하는 것이 더 흔한 방식이 됐다. 벤더가 관리해 주는
  선택지도 많지만, **직접 관리한다면 결국 CPU·메모리·IOPS·디스크의 조합이 다른 여러 컴퓨트
  인스턴스 중에서 골라야 한다.** 방법은 앞의 성능 특성들에 **우선순위를 매겨 알맞은 인스턴스
  구성을 고르는 것**이다 (2장, p.35).[^shapira2021]
- 애저의 판단 순서 (2장, p.36):[^shapira2021]
  - **디스크를 VM과 별도로 관리할 수 있으므로 저장소 결정이 VM 유형에 묶이지 않는다.**
  - 좋은 출발점은 **필요한 데이터 보존량에서 시작해 프로듀서가 요구하는 성능으로 넘어가는
    것**이다.
  - 아주 낮은 지연이 필요하면 프리미엄 SSD를 쓰는 I/O 최적화 인스턴스가 필요할 수 있고,
    아니면 관리형 저장소로 충분하다.
  - 가용성 세트로 클러스터를 구성하고 애저 컴퓨트 장애 도메인에 파티션을 분산하라는 권고가
    붙는다.
  - **임시 디스크보다 관리형 디스크가 강하게 권장된다** — VM이 옮겨지면 브로커의 데이터를
    전부 잃을 위험이 있다.
- AWS의 판단 (2장, p.36):[^shapira2021]
  - 아주 낮은 지연이 필요하면 로컬 SSD를 갖춘 I/O 최적화 인스턴스, 아니면 EBS 같은 임시
    저장소로 충분하다.
  - `m4`는 **보존 기간을 길게 가져갈 수 있지만 EBS라 처리량이 떨어지고**, `r3`은 **로컬
    SSD로 처리량이 훨씬 좋지만 보존 가능한 데이터량이 제한된다.**
  - 둘 다 필요하면 `i2`나 `d2`로 올라가야 하지만 비용이 크게 오른다.

## 브로커는 몇 대인가

- 단일 브로커는 로컬 개발이나 개념 증명에는 충분하지만, 클러스터에는 뚜렷한 이득이 있다 —
  **가장 큰 이득은 부하를 여러 서버로 확장하는 능력**이고, 그다음이 단일 시스템 장애로 인한
  데이터 유실을 막는 복제다. 복제는 클라이언트 가용성을 유지한 채 카프카나 하부 시스템을
  유지 보수할 수 있게도 한다 (2장, p.36).[^shapira2021]
- 클러스터 크기를 묶는 핵심 영역 넷 (2장, p.37):[^shapira2021]
  - 디스크 용량
  - 브로커당 레플리카 용량
  - CPU 용량
  - 네트워크 용량
- 첫 번째 계산은 저장 용량이다 — **10TB를 보존해야 하고 브로커 한 대가 2TB를 저장할 수
  있으면 최소 클러스터 크기는 5대**다. 여기에 **복제 팩터를 올리면 저장 요구가 최소 100%
  늘어나므로, 복제 팩터 2인 같은 클러스터는 최소 10대**가 필요하다 (2장,
  p.37).[^shapira2021]
- 두 번째 계산은 레플리카 수다 (2장, p.38):[^shapira2021]
  - 브로커 10대 클러스터에 레플리카가 100만 개를 넘으면(복제 팩터 2에 파티션 50만 개),
    균형이 맞은 상황에서 **브로커당 약 10만 개 레플리카**를 떠안는다. 이는 프로듀스·컨슘·
    컨트롤러 큐에서 병목이 될 수 있다.
  - 과거 공식 권고: **브로커당 파티션 레플리카 4,000개 이하, 클러스터당 20만 개 이하.**
  - 현재 권고: 클러스터 효율이 개선돼 훨씬 크게 확장할 수 있으며, **잘 구성된 환경에서
    브로커당 14,000개, 클러스터당 100만 개를 넘지 않기를 권장한다.**
- CPU는 대개 주 병목이 아니지만, **브로커에 클라이언트 연결과 요청이 과도하면 병목이 될 수
  있다.** 고유 클라이언트와 컨슈머 그룹 수를 기준으로 전체 CPU 사용을 지켜보고 확장하면 큰
  클러스터의 성능을 지키는 데 도움이 된다 (2장, p.38).[^shapira2021]
- 네트워크 판단의 예시 계산: **단일 브로커의 네트워크 인터페이스가 피크에 80%까지 쓰이고 그
  데이터의 컨슈머가 둘이면, 브로커가 두 대가 되기 전까지 컨슈머는 피크 트래픽을 따라잡을 수
  없다.** 클러스터에 복제를 쓰고 있다면 복제도 데이터의 추가 컨슈머로 계산에 넣어야 한다
  (2장, p.38).[^shapira2021]
  - 보존 기간에 트래픽이 고르지 않은 경우(피크 시간대의 버스트)도 인터페이스 용량 판단에
    넣는다.
  - 디스크 처리량이나 시스템 메모리가 모자라 생기는 성능 문제를 다루려고 브로커를 늘리는
    선택지도 있다.
