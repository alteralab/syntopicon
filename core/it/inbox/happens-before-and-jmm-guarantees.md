이 페이지의 질문: **자바 메모리 모델의 복잡한 정의를 매번 펼치지 않고, 두 작업이 동시성 환경에서
충돌하는지를 어떤 규칙으로 판정하는가.**

## 원자성

- 모델의 전체 특징이 셋으로 요약된다 — **자바 메모리 모델은 동시성 처리에서 원자성, 가시성, 실행
  순서를 어떻게 처리하는지로 구성된다** (12장, p.603).[^zhou2024]
- 직접 보장되는 범위가 정해져 있다 — **자바 메모리 모델이 직접 보장하는 원자적 변수 연산은 읽기,
  적재, 할당, 사용, 저장, 쓰기다. 기본 데이터 타입으로의 접근, 즉 읽기와 쓰기는 대체로
  원자적이라고 생각할 수 있다. 물론 long과 double은 비원자적일 수 있다** (12장,
  p.603).[^zhou2024] 그 예외가
  [long과 double 변수의 비원자성](../concepts/nonatomic-treatment-of-long-and-double.md)이다.
- 더 넓은 범위를 원하면 잠금으로 간다 — **애플리케이션 수준에서 원자성을 더 넓은 범위로 보장해야 할
  때를 위해 자바 메모리 모델은 잠금과 잠금 해제 연산을 제공한다. 가상 머신이 사용자에게 잠금과 잠금
  해제 연산을 직접 제공하지는 않고, 그 대신 한 단계 추상화된 바이트코드 명령어인 monitorenter와
  monitorexit를 이용하도록 했다. 이 두 명령어는 자바 코드에서 synchronized 키워드로 동기화한
  블록에 해당한다. 그래서 동기화된 블록 전체가 원자적으로 수행된다** (12장, p.603).[^zhou2024]
  그 두 명령어의 실행 기제는 [락의 구현과 최적화](../concepts/lock-optimization.md)에 있다.

## 가시성 — 키워드가 셋이다

- 정의와 확보 방식 — **가시성이란 공유 변수의 값을 한 스레드가 수정하면 수정 결과를 다른 스레드가
  즉시 알 수 있다는 뜻이다. (…) 자바 메모리 모델은 변숫값이 수정되면 새로운 값을 메인 메모리에 즉시
  동기화하고, 작업 메모리의 변숫값을 읽을 때 메인 메모리로부터 값을 갱신하는 식으로 가시성을
  확보한다. 일반 변수든 volatile 변수든 마찬가지다. 다만 volatile 변수용 특별 규칙에 의해
  volatile 변수는 새로운 값을 즉시 메인 메모리로 동기화하고, 이를 사용할 때마다 즉시 메인
  메모리에서 새로 고치도록 한다. 따라서 volatile 변수는 멀티스레드 환경에서도 가시성을 보장하지만
  일반 변수는 보장하지 않는다고 할 수 있다** (12장, p.603).[^zhou2024] 자세한 것은
  [volatile 변수](../concepts/volatile-variables.md)에 있다.
- **키워드가 `volatile` 하나가 아니라는 점이 이 절의 소득이다** — **자바에는 가시성 확보용 키워드가
  volatile 말고도 두 개 더 있다. 바로 synchronized와 final이다** (12장, p.603).[^zhou2024]
  - `synchronized` — **synchronized 블록의 가시성은 "변수의 잠금을 해제하기 전에 변수의 값을 메인
    메모리로 다시 동기화해야 한다(저장과 쓰기 수행)"라는 규칙으로 확보된다** (12장,
    p.604).[^zhou2024]
  - `final` — **final 필드는 생성자에서 초기화된다. 또한 스레드는 생성이 완벽하게 끝나지 않은
    객체의 참조(this)를 다른 스레드에 전달할 수 없다(this 참조가 탈출하면 다른 스레드가 '반만
    초기화된' 객체에 접근할 수 있으므로 매우 위험하다). 따라서 모든 여타 스레드는 초기화가 완료된
    final 필드의 값을 보게 된다** (12장, p.604).[^zhou2024] 예로 든 `public static final int i`
    (정적 초기화 블록에서 대입)와 `public final int j`(생성자에서 대입)는 **모두 가시성이 확보되어
    다른 스레드에서 동기화 없이 올바르게 접근할 수 있다** (12장, p.604). 여기서 말하는 'this 참조
    탈출'을 판정하는 분석이 [탈출 분석](../concepts/escape-analysis.md)의 전역 탈출이다.

## 실행 순서

- 한 문장으로 요약된다 — **"현재 스레드에서 보면 모든 연산이 순서대로 수행된다. 하지만 다른
  스레드에서 보면 순서가 다를 수 있다."** 그리고 **이 중 두 번째 문장은 '명령어 재정렬'과 '작업
  메모리와 메인 메모리 사이의 동기화 지연' 현상을 의미한다** (12장, p.604).[^zhou2024]
- 순서를 잡는 키워드도 둘이다 — **volatile은 그 자체에 "명령어 재정렬을 금지한다"라는 의미를
  포함하며, synchronized는 "락을 소유한 단 하나의 스레드만이 변수에 접근할 수 있다"라는 규칙에
  의거해 작업 순서를 정한다. 즉, synchronized 블록 두 개가 같은 락을 공유한다면 반드시 순서대로
  수행된다** (12장, pp.604–605).[^zhou2024]
- 세 특징을 다 원하면 답이 하나로 모이고, 거기서 다음 장의 문제가 생긴다 — **세 가지 특성이 모두
  필요하면 synchronized 키워드가 멋진 해결책이 되어 준다. synchronized는 만능으로 보이며 실제로
  대부분의 동시성 제어는 synchronized로 가능하다. 하지만 이러한 다재다능함은 개발자들이
  synchronized를 남용하도록 부추겨서 프로그램 성능을 크게 떨어뜨리기도 한다** (12장,
  p.605).[^zhou2024] 그 남용을 가상 머신이 어떻게 수습하는지가
  [락의 구현과 최적화](../concepts/lock-optimization.md)다.

## 선 발생 원칙이 필요한 이유

- 없으면 코드가 장황해진다 — **자바 메모리 모델에서 모든 실행 순서를 volatile과 synchronized로만
  처리한다면 많은 연산이 매우 장황해진다. 다행히 자바는 선 발생 원칙을 따르기 때문에 동시성 코드를
  작성할 때 이런 장황함을 인식하지 못한다. 선 발생 원칙은 데이터 경합 발생 여부와 스레드 안전성을
  확인하는 데 매우 유용한 수단이다. 이 원칙을 따르면 몇 가지 간단한 규칙만으로 동시성 환경에서 두
  작업의 충돌 가능성 판단 문제를 모두 해결할 수 있다** (12장, p.605).[^zhou2024] 여기서 판정
  대상인 스레드 안전성의 정의는
  [스레드 안전성의 다섯 등급](../concepts/thread-safety-levels.md)에 있다.
- 정의는 관찰 가능성으로 되어 있다 — **'선 발생'이란 자바 메모리 모델에서 정의된 두 작업의 수행 순서
  관계를 말한다. 예를 들어 "작업 A는 작업 B보다 선 발생한다"라고 하면 "작업 B가 수행되기 전에 작업
  A의 영향(수행 결과)을 작업 B에서 관찰할 수 있다"라는 뜻이다. 이때 '영향'은 공유 변수의 값 변경,
  메시지 전송, 메서드 호출 등을 모두 포괄한다** (12장, p.605).[^zhou2024]
- 예제는 세 스레드가 변수 하나를 만지는 형태다 — 스레드 A가 `i = 1`, 스레드 B가 `j = i`, 스레드 C가
  `i = 2`를 수행할 때, A의 연산이 B보다 선 발생한다고 가정하면 B 이후 `j`는 1이다. 근거는 둘이다 —
  **1. 선 발생 원칙에 따라 i = 1의 결과를 관찰할 수 있다. 2. 스레드 C는 아직 등장하지 않았으며
  스레드 A의 작업이 완료된 후 다른 스레드가 변수 i의 값을 수정하지 않았다** (12장,
  pp.605–606).[^zhou2024]
  - C가 끼어들면 답이 무너진다 — **C와 B 사이에 선 발생 관계가 없다면 j의 값은 몇일까? 정답은
    '확실하지 않다'이다. C가 변수 i에 미치는 영향을 B가 관찰할 수도, 못할 수도 있기 때문에 i의 값은
    1 또는 2 모두 될 수 있다. 결국 B는 낡은 데이터를 읽을 위험이 있으므로 멀티스레드 환경에서
    안전하지 못하다** (12장, p.606).[^zhou2024]

## 자연스러운 선 발생 관계 여덟 가지

- 목록의 지위가 먼저 규정된다 — **다음 목록은 '자연스러운' 선 발생 관계다. 동기화 장치의 지원 없이
  이루어지며 코딩에 직접 활용할 수 있다. 한편 두 작업 사이의 관계가 다음 목록에 없고 이 목록으로부터
  추론할 수도 없다면, 실행 순서가 보장되지 않는다는 뜻이다. 즉, 가상 머신이 마음대로 순서를 바꿀 수
  있다** (12장, p.606):[^zhou2024]

  | 규칙 | 내용 |
  |---|---|
  | 프로그램 순서 규칙 | **한 스레드 안에서는 '제어 흐름 순서'에 따라 앞의 연산이 뒤따르는 연산보다 선 발생한다. 분기와 순환문 같은 구조까지 고려되기 때문에 프로그램 코드 순서가 아니라 제어 흐름 순서가 기준이다** |
  | 모니터 락 규칙 | **잠금 해제 연산은 '같은 락'에 대한 잠금 연산보다 선 발생한다. 여기서는 '같은 락'이 중요하며 순서는 '시간 순서'다** |
  | 휘발성 변수 규칙 | **volatile 변수의 쓰기 연산은 같은 변수에 대한 읽기 연산보다 선 발생한다. 여기서 순서는 '시간 순서'다** |
  | 스레드 시작 규칙 | **Thread 객체의 start() 메서드는 해당 스레드의 어떤 작업보다도 선 발생한다** |
  | 스레드 종료 규칙 | **스레드의 모든 작업은 해당 스레드의 종료 감지보다 선 발생한다.** 감지 수단은 `Thread::join()`과 `Thread::isAlive()`다 |
  | 스레드 인터럽트 규칙 | **Thread의 interrupt() 메서드 호출은 인터럽트되는 스레드가 인터럽트 이벤트 발생 감지보다 선 발생한다.** 감지 수단은 `Thread::interrupted()`다 |
  | 종료자 규칙 | **객체 초기화(생성자 수행 완료)는 finalize() 메서드 시작보다 선 발생한다** |
  | 전이성 | **연산 A가 연산 B보다 선 발생하고, 연산 B가 연산 C보다 선 발생한다면, A가 C보다 선 발생한다고 결론지을 수 있다** |

- 보장의 근거는 언어 자체다 — **자바 언어는 어떠한 동기화 수단의 지원 없이도 이상의 선 발생 규칙들을
  보장한다** (12장, p.607).[^zhou2024]

## 게터/세터 한 쌍을 판정해 보기

- 대상은 동기화가 전혀 없는 평범한 코드다 (12장, p.607):[^zhou2024]

  ```java
  private int value = 0;

  public void setValue(int value) {
      this.value = value;
  }

  public int getValue() {
      return value;
  }
  ```

- 스레드 A가 `setValue(1)`을, 이어서 B가 같은 객체의 `getValue()`를 호출할 때 규칙을 하나씩
  대입하면 전부 탈락한다 (12장, p.607):[^zhou2024] 두 메서드는 서로 다른 스레드가 부르므로 프로그램
  순서 규칙이 적용되지 않고, 동기화 블록이 없어 모니터 락 규칙도, `value`가 `volatile`이 아니라
  휘발성 변수 규칙도 적용되지 않으며, 시작·종료·인터럽트·종료자 규칙은 무관하고, **적용 가능한 선
  발생 규칙이 없기 때문에 마지막 전이성도 문제가 되지 않는다.**
- 그래서 판정이 뒤집힌다 — **따라서 스레드 A가 B보다 먼저 수행되더라도 B가 getValue()로 얻는 결과는
  알 수 없다. 결국 이 작업은 멀티스레드 환경에서 안전하지 않다** (12장, p.608).[^zhou2024]
- 고치는 방법이 둘이고, 그중 하나가 더 싸다 — **모니터 락 규칙을 적용할 수 있도록 게터/세터 메서드를
  synchronized 메서드로 만들거나 value를 volatile 변수로 선언하면 된다. 그런데 세터 메서드는
  현재 값에 상관없이 값을 덮어쓰므로 지금 시나리오에서는 volatile 키워드만으로 충분하다** (12장,
  p.608).[^zhou2024] 이 판단 기준이
  [volatile 변수](../concepts/volatile-variables.md)의 "연산 결과가 변수의 현재 값과는 무관하거나"
  조건과 같은 것이다.

## 시간 순서와 선 발생은 인과 관계가 없다

- 한 방향은 앞의 예가 이미 반증했다 — **앞의 예에서 '시간상 먼저 발생'하는 작업이 '선 발생'하는
  작업을 의미하지는 않는다고 결론지을 수 있다** (12장, p.608).[^zhou2024]
- 반대 방향은 재정렬이 반증한다 — 같은 스레드에서 `int i = 1; int j = 2;`를 실행할 때
  **프로그램 순서 규칙에 따르면 int i = 1 연산이 int j = 2보다 선 발생한다. 하지만 CPU에서는
  int j = 2가 먼저 실행될 수 있다. 다행히 이 사실을 스레드가 인식할 방법이 없기 때문에 선 발생
  원칙의 정확성에는 영향을 주지 않는다** (12장, p.608).[^zhou2024]
- 결론이 분석의 규율이 된다 — **기본적으로 시간 순서와 선 발생 원칙 사이에는 인과 관계가 없다.
  따라서 동시성 안전 문제를 분석할 때는 시간 순서에 얽매여서는 안 된다. 모든 것은 선 발생 원칙에
  기초해야 한다** (12장, p.608).[^zhou2024]
