하나의 질문: **컨슈머는 어디까지 읽었는지를 어떻게 기록하고, 그 기록 시점의 선택이
중복과 누락 중 무엇을 남기는가.**

## 커밋이란 무엇을 하는 것인가

- `poll()`을 부를 때마다 **그룹의 컨슈머들이 아직 읽지 않은, 카프카에 쓰인 레코드**가
  반환된다. 즉 **그룹의 컨슈머가 어떤 레코드를 읽었는지 추적할 방법이 있다는 뜻**이다
  (4장, p.94).[^shapira2021]
- 카프카의 독특한 성질이 여기 있다 — **많은 JMS 큐가 하는 방식으로 컨슈머의 확인 응답을
  추적하지 않는다.** 대신 **컨슈머가 각 파티션에서의 자기 위치(오프셋)를 카프카를 이용해
  추적하도록** 한다 (4장, p.94).[^shapira2021]
- **파티션에서의 현재 위치를 갱신하는 행위를 오프셋 커밋(offset commit)**이라 한다. 전통적
  메시지 큐와 달리 **카프카는 레코드를 개별적으로 커밋하지 않는다** — **컨슈머는 파티션에서
  성공적으로 처리한 마지막 메시지를 커밋하며, 그 마지막 메시지 이전의 모든 메시지도
  성공적으로 처리됐다고 암묵적으로 가정**한다 (4장, p.94).[^shapira2021]
- 커밋의 실제 동작은 **`__consumer_offsets`라는 특별한 토픽에 각 파티션의 커밋된 오프셋을
  갱신하는 메시지를 보내는 것**이다. **모든 컨슈머가 살아 돌아가는 동안에는 이것이 아무
  영향을 주지 않는다** (4장, p.94).[^shapira2021]
- 영향이 드러나는 것은 리밸런스 때다 — **컨슈머가 크래시하거나 새 컨슈머가 그룹에 조인하면
  리밸런스가 발동되고, 리밸런스 후 각 컨슈머는 이전과 다른 파티션 집합을 배정받을 수 있다.**
  **어디서부터 일을 이어받을지 알기 위해 컨슈머는 각 파티션의 마지막 커밋 오프셋을 읽고 거기서
  계속한다** (4장, p.94).[^shapira2021]
- 커밋되는 값의 정확한 정의에도 주의가 필요하다 — **자동으로든 의도한 오프셋을 지정하지 않고
  커밋할 때든 기본 동작은 `poll()`이 반환한 마지막 오프셋의 다음 오프셋을 커밋하는
  것**이다. 책은 **"마지막 오프셋을 커밋한다"고 쓰되 수동으로 오프셋을 조작할 때는 이 점을
  기억하라**고 못 박는다 (4장, p.95).[^shapira2021]

## 어긋나면 중복이거나 누락이다

- **커밋된 오프셋이 클라이언트가 처리한 마지막 메시지의 오프셋보다 작으면**, 마지막 처리
  오프셋과 커밋 오프셋 사이의 메시지들이 **두 번 처리된다** (4장, p.94, 그림
  4-8).[^shapira2021]
- **커밋된 오프셋이 클라이언트가 실제로 처리한 마지막 메시지의 오프셋보다 크면**, 그 사이의
  모든 메시지가 **컨슈머 그룹에서 누락된다** (4장, p.95, 그림 4-9).[^shapira2021]
- 그래서 **오프셋 관리는 클라이언트 애플리케이션에 큰 영향을 주며**, `KafkaConsumer` API는
  **오프셋을 커밋하는 여러 방법**을 제공한다 (4장, p.95).[^shapira2021]

## 자동 커밋

- 가장 쉬운 방법은 **컨슈머가 대신 커밋하게 두는 것**이다. `enable.auto.commit=true`로
  설정하면 **5초마다 클라이언트가 `poll()`에서 받은 가장 큰 오프셋을 커밋**한다. 이 5초
  간격은 기본값이며 `auto.commit.interval.ms`로 제어한다 (4장, p.95).[^shapira2021]
- **컨슈머의 다른 모든 것과 마찬가지로 자동 커밋도 폴 루프가 구동한다** — **폴할 때마다
  컨슈머는 커밋할 시간인지 확인하고, 그렇다면 마지막 폴에서 반환한 오프셋을 커밋한다** (4장,
  p.95).[^shapira2021]
- 편리함의 대가 (4장, p.96):[^shapira2021]
  - **기본적으로 자동 커밋은 5초마다 일어난다.** 가장 최근 커밋 3초 뒤에 컨슈머가
    크래시했다고 하자. 리밸런싱 후 살아남은 컨슈머들은 **마지막 커밋 오프셋부터** 소비를
    시작하는데, 그 오프셋은 **3초 전 것이므로 그 3초 동안 도착한 이벤트는 모두 두 번
    처리된다.**
  - **커밋 간격을 더 짧게 잡아 중복 창을 줄이는 것은 가능하지만, 중복을 완전히 없애는 것은
    불가능하다.**
  - 자동 커밋이 켜져 있으면 **커밋할 시간이 됐을 때 다음 폴이 직전 폴에서 반환한 마지막
    오프셋을 커밋한다.** 컨슈머는 **어떤 이벤트가 실제로 처리됐는지 모르므로, `poll()`을 다시
    부르기 전에 이전 `poll()`이 반환한 모든 이벤트를 항상 처리하는 것이 결정적으로
    중요하다.** (`poll()`과 마찬가지로 **`close()`도 오프셋을 자동으로 커밋한다.**) 통상
    문제가 되지 않지만 **예외를 처리하거나 폴 루프를 조기에 빠져나올 때 주의**해야 한다.
  - 요약하면 **자동 커밋은 편리하지만 중복 메시지를 피할 만큼의 제어권을 개발자에게 주지
    않는다.**

## 현재 오프셋 커밋 — commitSync

- 대부분의 개발자는 **커밋 시점을 더 통제**한다 — **메시지 누락 가능성을 없애고 리밸런싱 중
  중복되는 메시지 수를 줄이기 위해서**다. 컨슈머 API는 **타이머가 아니라 애플리케이션
  개발자에게 의미 있는 시점에 현재 오프셋을 커밋하는 선택지**를 제공한다 (4장,
  p.96).[^shapira2021]
- `enable.auto.commit=false`로 두면 **애플리케이션이 명시적으로 선택할 때만 오프셋이
  커밋된다.** 가장 단순하고 신뢰성 있는 커밋 API는 **`commitSync()`**이며, **`poll()`이
  반환한 최신 오프셋을 커밋하고 커밋이 완료되면 반환하며, 커밋이 실패하면 예외를 던진다**
  (4장, p.96).[^shapira2021]
- 호출 시점이 곧 의미론이다 (4장, p.96):[^shapira2021]
  - **`commitSync()`는 `poll()`이 반환한 최신 오프셋을 커밋하므로**, **컬렉션의 모든 레코드
    처리를 끝내기 전에 호출하면** 애플리케이션이 크래시할 경우 **커밋됐지만 처리되지 않은
    메시지를 놓칠 위험**이 있다.
  - 반대로 **컬렉션의 레코드를 처리하는 도중 애플리케이션이 크래시하면 가장 최근 배치의
    처음부터 모든 메시지가 리밸런스 시점까지 두 번 처리된다** — 이것이 메시지 누락보다 나을
    수도 아닐 수도 있다.
- 실무 형태 (4장, p.97):[^shapira2021]
  - **현재 배치의 레코드를 모두 "처리"한 뒤, 추가 메시지를 폴하기 전에 `commitSync`를 불러
    배치의 마지막 오프셋을 커밋한다.**
  - **`commitSync`는 복구 불가능한 에러가 아닌 한 계속 재시도한다.** 그런 일이 일어나면
    **에러를 로깅하는 것 말고 할 수 있는 일이 별로 없다.**

## 비동기 커밋 — commitAsync

- 수동 커밋의 단점은 **브로커가 커밋 요청에 응답할 때까지 애플리케이션이 블록된다**는
  것이며, 이는 **애플리케이션의 처리량을 제한**한다. **커밋 빈도를 낮춰 처리량을 개선할 수
  있지만 그러면 리밸런스가 만들 수 있는 잠재적 중복 수가 늘어난다** (4장,
  p.97).[^shapira2021]
- 다른 선택지가 **비동기 커밋 API**다 — **브로커의 응답을 기다리는 대신 요청만 보내고 계속
  진행한다** (4장, p.97).[^shapira2021]
- 대가는 재시도의 부재다 (4장, p.98):[^shapira2021]
  - **`commitSync()`는 성공하거나 재시도 불가 실패를 만날 때까지 커밋을 재시도하지만
    `commitAsync()`는 재시도하지 않는다.**
  - 재시도하지 않는 이유: **`commitAsync()`가 서버로부터 응답을 받는 시점에는 이미 성공한 더
    나중의 커밋이 있었을 수 있기 때문**이다.
  - 책의 시나리오: **오프셋 2000 커밋 요청을 보냈는데 일시적 통신 문제로 브로커가 요청을
    받지 못해 응답하지 않는다. 그동안 우리는 다른 배치를 처리해 오프셋 3000을 성공적으로
    커밋했다. 이때 `commitAsync()`가 앞서 실패한 커밋을 재시도하면, 오프셋 3000이 이미
    처리·커밋된 뒤에 오프셋 2000을 커밋하는 데 성공할 수 있다.** 리밸런스가 일어나면 **중복이
    더 늘어난다.**
- `commitAsync()`는 **브로커가 응답할 때 발동되는 콜백을 넘길 수 있는 선택지**도 준다.
  **커밋 에러를 로깅하거나 지표로 세는 데 쓰는 것이 흔하지만, 콜백을 재시도에 쓰려면 커밋
  순서 문제를 알고 있어야 한다** (4장, p.98).[^shapira2021]
- 비동기 재시도의 관용 패턴 — **단조 증가하는 시퀀스 번호를 쓴다** (4장,
  p.99):[^shapira2021]
  - **커밋할 때마다 시퀀스 번호를 올리고, 커밋 시점의 시퀀스 번호를 `commitAsync` 콜백에
    넣는다.**
  - **재시도를 보낼 준비가 되면 콜백이 받은 커밋 시퀀스 번호가 인스턴스 변수와 같은지
    확인한다.** 같으면 **더 새로운 커밋이 없다는 뜻이므로 재시도해도 안전**하다. **인스턴스
    시퀀스 번호가 더 크면 더 새로운 커밋이 이미 보내졌으므로 재시도하지 않는다.**

## 둘을 함께 쓰기

- 통상 **재시도 없는 이따금의 커밋 실패는 큰 문제가 아니다** — 문제가 일시적이라면 **뒤따르는
  커밋이 성공할 것**이기 때문이다. **그러나 그것이 컨슈머를 닫기 전 또는 리밸런스 전의 마지막
  커밋이라면 커밋이 성공하는 것을 각별히 확실히 해야 한다** (4장, p.99).[^shapira2021]
- 그래서 **관용적인 패턴은 종료 직전에 `commitAsync()`와 `commitSync()`를 결합하는
  것**이다 (4장, p.99):[^shapira2021]
  - **모든 것이 정상인 동안에는 `commitAsync`를 쓴다.** 더 빠르고, 커밋 하나가 실패해도
    **다음 커밋이 재시도 역할**을 한다.
  - **닫는 중이라면 "다음 커밋"이 없으므로 `commitSync()`를 부른다** — **성공하거나 복구
    불가능한 실패를 겪을 때까지 재시도**하기 때문이다.

  아래가 그 결합 형태다 — `commitAsync`·`finally`의 `commitSync`로 찾는다 (4장,
  p.99):[^shapira2021]

  ```java
  Duration timeout = Duration.ofMillis(100);

  try {
      while (!closing) {
          ConsumerRecords<String, String> records = consumer.poll(timeout);
          for (ConsumerRecord<String, String> record : records) {
              System.out.printf("topic = %s, partition = %s, offset = %d, " +
                      "customer = %s, country = %s\n",
                  record.topic(), record.partition(),
                  record.offset(), record.key(), record.value());
          }
          consumer.commitAsync();
      }
      consumer.commitSync();
  } catch (Exception e) {
      log.error("Unexpected error", e);
  } finally {
      consumer.close();
  }
  ```

## 특정 오프셋 커밋

- 최신 오프셋만 커밋하면 **배치 처리를 끝낼 때마다만 커밋할 수 있다.** 그보다 자주 커밋하고
  싶다면, 예컨대 **`poll()`이 거대한 배치를 반환해서 리밸런스가 일어나도 그 많은 행을 다시
  처리하지 않도록 배치 중간에 커밋하고 싶다면**, `commitSync()`·`commitAsync()`를 그냥 부를
  수는 없다 — **아직 처리하지 않은 마지막 반환 오프셋을 커밋해 버리기 때문**이다 (4장,
  p.100).[^shapira2021]
- 컨슈머 API는 `commitSync()`와 `commitAsync()`에 **커밋하고자 하는 파티션과 오프셋의
  맵**을 넘길 수 있게 한다. **토픽 "customers"의 파티션 3에서 받은 마지막 메시지가 오프셋
  5000이라면 파티션 3에 대해 오프셋 5001을 커밋**할 수 있다 (4장, p.100).[^shapira2021]
  - 대가: **컨슈머가 한 파티션 이상을 소비할 수 있으므로 그 전부에 대해 오프셋을 추적해야
    하고, 이는 코드의 복잡도를 올린다.**
- 예제의 판단들 (4장, pp.100–101):[^shapira2021]
  - **오프셋을 수동으로 추적할 맵**을 둔다.
  - **레코드를 읽을 때마다 처리할 것으로 기대되는 다음 메시지의 오프셋으로 맵을 갱신한다** —
    **커밋되는 오프셋은 항상 애플리케이션이 다음에 읽을 메시지의 오프셋이어야 하기**
    때문이며, 그것이 다음번에 읽기를 시작할 자리다.
  - 예제는 **1,000레코드마다 현재 오프셋을 커밋**하기로 정했다. 실제 애플리케이션에서는
    **시간 기준으로도, 레코드 내용 기준으로도** 커밋할 수 있다.
  - 예제는 **콜백 없이 `commitAsync()`를 골랐지만(그래서 둘째 매개변수가 `null`이다)
    `commitSync()`도 완전히 유효**하다. 물론 **특정 오프셋을 커밋할 때도 앞서 본 에러 처리는
    전부 해야 한다.**

## 신뢰성 관점에서 지킬 것

- **오프셋 커밋을 직접 하기로 했다면 정확성과 성능 양쪽을 신경 써야 한다** (7장,
  p.174).[^shapira2021]
- **항상 메시지를 처리한 뒤에 오프셋을 커밋한다** (7장, p.174):[^shapira2021]
  - **폴 루프 안에서 모든 처리를 하고 폴 루프 사이에 상태를 유지하지 않으면(집계 같은 것이
    없으면) 이것은 쉽다.** **자동 커밋을 쓰거나, 루프 끝에서 커밋하거나, 오버헤드와 중복
    처리량을 저울질하는 빈도로 루프 안에서 커밋**하면 된다.
  - **추가 스레드나 상태를 가진 처리가 끼면 훨씬 복잡해진다.** **컨슈머 객체는 스레드
    안전(thread safe)하지 않기** 때문이다.
- **커밋 빈도는 성능과 크래시 시 중복 개수 사이의 트레이드오프**다 (7장,
  pp.174–175):[^shapira2021]
  - 폴 루프 안에서 모든 처리를 하고 루프 사이 상태도 없는 가장 단순한 경우에도 **루프 안에서
    여러 번 커밋할지, 여러 루프마다 한 번만 커밋할지 고를 수 있다.**
  - **커밋에는 상당한 성능 오버헤드가 있다.** `acks=all`로 생산하는 것과 비슷한데,
    **한 컨슈머 그룹의 모든 오프셋 커밋이 같은 브로커로 생산되므로 그 브로커가 과부하될 수
    있다.**
  - **매 메시지마다 커밋하는 것은 처리량이 아주 낮은 토픽에서만 해야 한다.**
- **올바른 오프셋을 올바른 시점에 커밋한다** (7장, p.175):[^shapira2021]
  - 폴 루프 중간에 커밋할 때 흔한 함정은 **마지막으로 처리한 오프셋이 아니라 폴할 때 읽은
    마지막 오프셋을 실수로 커밋하는 것**이다.
  - **메시지를 처리한 뒤 그 오프셋을 커밋하는 것이 결정적으로 중요하다** — **읽었지만 처리하지
    않은 메시지의 오프셋을 커밋하면 컨슈머가 메시지를 놓치게** 된다.
- **리밸런스는 일어난다** — 애플리케이션을 설계할 때 **컨슈머 리밸런스가 일어날 것을 기억하고
  제대로 다뤄야** 한다. 통상 **파티션이 회수되기 전에 오프셋을 커밋하고, 새 파티션을 배정받을
  때 애플리케이션이 유지하던 상태를 정리하는 일**이 포함된다 (7장, p.175).[^shapira2021]

## 처리하지 못한 레코드와 상태 유지

- **폴을 호출하고 레코드를 처리한 뒤에도 일부 레코드가 완전히 처리되지 않아 나중에 처리해야 할
  때**가 있다. 예컨대 **카프카에서 데이터베이스로 레코드를 쓰려는데 그 순간 데이터베이스를 쓸
  수 없어 나중에 재시도해야** 하는 경우다 (7장, p.175).[^shapira2021]
- 문제는 커밋의 단위에서 온다 — **전통적 발행/구독 메시징 시스템과 달리 카프카 컨슈머는
  오프셋을 커밋하지 개별 메시지를 확인 응답하지 않는다.** **레코드 #30 처리에 실패하고 #31
  처리에 성공했다면 오프셋 #31을 커밋해서는 안 된다** — 그러면 **#30을 포함해 #31까지의 모든
  레코드가 처리된 것으로 표시되고, 이는 대개 원하는 바가 아니다** (7장,
  p.175).[^shapira2021]
- 대신 **두 패턴 중 하나를 따르기를 권한다** (7장, p.175):[^shapira2021]
  - **첫째** — 재시도 가능 에러를 만나면 **성공적으로 처리한 마지막 레코드를 커밋**한다. 그리고
    **아직 처리해야 할 레코드들을 버퍼에 저장**해 두고(다음 폴이 덮어쓰지 않도록),
    **컨슈머의 `pause()` 메서드로 추가 폴이 데이터를 반환하지 않게** 한 뒤 **그 레코드들을 계속
    처리 시도**한다.
  - **둘째** — 재시도 가능 에러를 만나면 **별도의 토픽에 쓰고 계속 나아간다.** **별도 컨슈머
    그룹으로 그 재시도 토픽을 처리**하거나, **컨슈머 하나가 메인 토픽과 재시도 토픽을 모두
    구독하되 재시도 사이에는 재시도 토픽을 일시 정지**시킬 수 있다. 이 패턴은 **많은 메시징
    시스템에서 쓰이는 데드 레터 큐(dead-letter-queue) 시스템과 비슷하다.**
- **폴을 여러 번 호출하는 동안 상태를 유지해야 하는 애플리케이션**도 있다. 예컨대 **이동 평균을
  계산하려면 카프카에서 새 메시지를 폴할 때마다 평균을 갱신해야** 한다. **프로세스가 재시작되면
  마지막 오프셋부터 소비를 시작하는 것만으로는 부족하고 그에 맞는 이동 평균도 복구해야** 한다
  (7장, p.176).[^shapira2021]
  - 한 가지 방법은 **애플리케이션이 오프셋을 커밋하는 것과 동시에 최신 누적 값을 "결과" 토픽에
    쓰는 것**이다. 그러면 **스레드가 시동할 때 최신 누적 값을 집어 들고 멈춘 자리에서 이어 갈
    수 있다.**
  - 8장은 **애플리케이션이 결과 쓰기와 오프셋 커밋을 하나의 트랜잭션으로 수행하는 방법**을
    다룬다 — [카프카 트랜잭션](../concepts/kafka-transactions.md) 참조.
  - 일반적으로 이것은 **꽤 복잡한 문제**이므로, **집계·조인·윈도우 등 복잡한 분석을 위한 고수준
    DSL 형식 API를 제공하는 카프카 스트림즈나 플링크 같은 라이브러리를 살펴볼 것**을 권한다.
    - 그 DSL이 실제로 어떤 것인지는
      [카프카 스트림즈 DSL](../concepts/kafka-streams-dsl.md), 여기서 손으로 복구하려 한
      "이동 평균의 상태"를 프레임워크가 어떻게 맡는지는
      [스트림 처리의 상태](../concepts/stream-processing-state.md)에 있다.

## 특정 오프셋에서 읽기

- 지금까지는 **각 파티션의 마지막 커밋 오프셋부터 소비를 시작해 순서대로 진행**했지만,
  **다른 오프셋에서 읽기를 시작하고 싶을 때**가 있다. 카프카는 **다음 `poll()`이 다른
  오프셋에서 소비를 시작하게 만드는 여러 메서드**를 제공한다 (4장, p.104).[^shapira2021]
- 양 끝으로 가는 API가 따로 있다 — **파티션의 맨 처음부터 모든 메시지를 읽고 싶으면
  `seekToBeginning(Collection<TopicPartition> tp)`, 파티션 끝까지 건너뛰어 새 메시지만
  소비하고 싶으면 `seekToEnd(Collection<TopicPartition> tp)`** 다 (4장,
  p.104).[^shapira2021]
- **특정 오프셋으로 seek**하는 것도 가능하며 쓰임새가 다양하다 — **시간에 민감한
  애플리케이션이 뒤처졌을 때 몇 레코드를 건너뛰거나**, **파일에 데이터를 쓰는 컨슈머가 파일을
  잃었을 때 데이터를 복구하려고 특정 시점으로 되돌리는** 경우다 (4장,
  p.104).[^shapira2021]
- 특정 시점에 생산된 레코드로 모든 파티션의 현재 오프셋을 맞추는 절차는 셋이다 (4장,
  p.104):[^shapira2021]
  - **`consumer.assignment()`로 이 컨슈머에 배정된 모든 파티션을 얻어, 되돌리고 싶은
    타임스탬프로 가는 맵을 만든다.**
  - **`consumer.offsetsForTimes()`로 그 타임스탬프 시점에 유효했던 오프셋을 얻는다.** 이
    메서드는 **브로커에 요청을 보내며, 브로커는 타임스탬프 인덱스를 써서 해당 오프셋을
    반환한다.**
  - **각 파티션의 오프셋을 그렇게 반환된 오프셋으로 `seek`해 재설정한다.**

## 진행 위치를 데이터베이스에 두는 길

- 오프셋을 카프카에 커밋하는 대신 **처리 결과와 같은 데이터베이스 트랜잭션 안에 진행 위치를
  기록하는 길**이 있다. 데이터베이스 문헌은 이것을 메시지 ID로 일반화해 서술한다 — **모든
  메시지가 유일한 ID를 갖는다고 가정하고, 데이터베이스에 이미 처리된 메시지 ID들의 테이블을
  둔다. 메시지 처리를 시작할 때 데이터베이스에서 트랜잭션을 열어 그 ID를 검사하고, 이미
  있으면 브로커에 확인 응답하고 버린다. 없으면 테이블에 추가한 뒤 같은 트랜잭션 안에서
  메시지를 처리하고 커밋한다. 커밋이 성공하면 그때 브로커에 확인 응답하고, 확인 응답이
  성공하면 별도 트랜잭션으로 그 메시지 ID를 삭제한다** (8장,
  p.334).[^kleppmann2026]
- 이 방식이 사는 이유 — **정확히 한 번 처리를 달성하는 데는 데이터베이스 안의 트랜잭션만
  필요하고 데이터베이스와 메시지 브로커에 걸친 원자성은 필요하지 않다. 데이터베이스에 메시지
  ID를 기록하는 것이 메시지 처리를 멱등적(idempotent)으로 만들어, 부수 효과를 중복시키지 않고
  안전하게 재시도할 수 있게 한다** (8장, p.335).[^kleppmann2026]
- 각 지점에서 크래시가 나도 안전한 이유 (8장, p.334):[^kleppmann2026]
  - **데이터베이스 트랜잭션을 커밋하기 전에 크래시하면 트랜잭션이 중단되고 브로커가 처리를
    재시도한다.**
  - **커밋한 뒤 확인 응답 전에 크래시하면 재시도가 일어나지만 그 재시도는 데이터베이스에서
    메시지 ID를 보고 버린다.**
  - **확인 응답한 뒤 메시지 ID를 삭제하기 전에 크래시하면 옛 ID가 남는데, 저장 공간을 조금
    차지하는 것 말고는 해가 없다.**
  - **데이터베이스 트랜잭션이 중단되기 전에 재시도가 일어나면 메시지 ID 테이블의 유일성 제약이
    같은 ID가 두 동시 트랜잭션에 의해 삽입되는 것을 막아야 한다.**
