# 카프카 요청 처리

**목차**: [프로토콜과 순서 보장](#프로토콜과-순서-보장) · [브로커 내부 경로](#브로커-내부-경로) · [리더를 찾는 방법 — 메타데이터 요청](#리더를-찾는-방법--메타데이터-요청) · [프로듀스 요청](#프로듀스-요청) · [페치 요청](#페치-요청) · [프로토콜의 진화](#프로토콜의-진화) · [이어지는 페이지](#이어지는-페이지)

하나의 질문: **클라이언트가 보낸 요청은 브로커 안에서 어떤 경로를 지나고, 어디서
멈추는가.** 브로커가 하는 일의 대부분은 파티션 리더에게 온 요청을 처리하는 것이다 —
클라이언트, 파티션 레플리카, 컨트롤러가 보낸다 (6장, p.142).[^shapira2021]

## 프로토콜과 순서 보장

- 카프카는 TCP 위의 **바이너리 프로토콜**을 갖는다. 요청 형식과 브로커의 응답 방식이
  성공·실패 양쪽에 대해 규정돼 있다 (6장, p.142).[^shapira2021]
- 자바 클라이언트 외에 C·파이썬·Go 등 다른 언어의 클라이언트가 있고, **모두 이 프로토콜로
  브로커와 통신한다** (6장, p.142).[^shapira2021]
- 연결은 항상 클라이언트가 개시하고 브로커가 응답한다 (6장, p.142).[^shapira2021]
- 핵심 보장: **특정 클라이언트가 브로커에 보낸 모든 요청은 수신된 순서대로 처리된다.**
  카프카가 메시지 큐처럼 행동하고 저장 메시지의 순서 보장을 제공하는 근거가 이것이다
  (6장, p.142).[^shapira2021]
- 모든 요청의 표준 헤더 (6장, p.142):[^shapira2021]
  - 요청 유형(API 키)
  - 요청 버전 — 브로커가 서로 다른 버전의 클라이언트를 상대해 알맞게 응답하기 위한 것
  - 상관 ID(correlation ID) — 요청을 유일하게 식별하며 응답과 오류 로그에 함께 나와
    문제 추적에 쓰인다
  - 클라이언트 ID — 요청을 보낸 애플리케이션을 식별한다

## 브로커 내부 경로

- 브로커는 **수신 대기하는 포트마다 억셉터(acceptor) 스레드**를 돌려 연결을 만들고,
  이를 프로세서(processor) 스레드에 넘긴다 (6장, p.143).[^shapira2021]
- 프로세서 스레드는 **네트워크 스레드**라고도 하며 개수를 설정할 수 있다. 하는 일은
  클라이언트 연결에서 요청을 받아 요청 큐(request queue)에 넣고, 응답 큐(response
  queue)에서 응답을 꺼내 클라이언트로 돌려보내는 것이다 (6장, p.143).[^shapira2021]
- 요청 큐에 놓인 요청은 **I/O 스레드**(요청 핸들러 스레드)가 집어 처리한다 (6장,
  p.143).[^shapira2021]
- 응답이 즉시 나가지 않는 경우가 있다 — 컨슈머는 데이터가 있을 때만 응답을 받고,
  어드민 클라이언트는 `DeleteTopic` 요청에 대해 삭제가 진행된 뒤 응답을 받는다. **이렇게
  지연되는 응답은 완료될 때까지 퍼거토리(purgatory)에 보관된다** (6장,
  p.143).[^shapira2021]
- 클라이언트 요청 유형 셋 (6장, p.143):[^shapira2021]
  - 프로듀스 요청(produce request) — 프로듀서가 보내며 브로커에 쓸 메시지를 담는다.
  - 페치 요청(fetch request) — 컨슈머와 팔로워 레플리카가 메시지를 읽을 때 보낸다.
  - 어드민 요청(admin request) — 어드민 클라이언트가 토픽 생성·삭제 같은 메타데이터
    작업을 할 때 보낸다.

## 리더를 찾는 방법 — 메타데이터 요청

- **프로듀스 요청과 페치 요청은 둘 다 파티션의 리더 레플리카로 보내야 한다.** 리더가
  없는 브로커에 보내면 "Not a Leader for Partition" 오류 응답이 돌아온다. 알맞은 브로커로
  요청을 보낼 책임은 클라이언트에 있다 (6장, pp.143–144).[^shapira2021]
- 클라이언트가 리더를 아는 방법이 메타데이터 요청(metadata request)이다 — 관심 토픽
  목록을 담아 보내면, 응답이 **토픽에 어떤 파티션이 있고 파티션마다 레플리카가 무엇이며
  그중 어느 것이 리더인지** 알려 준다 (6장, p.144).[^shapira2021]
- 이 요청은 **아무 브로커에나 보내도 된다** — 모든 브로커가 이 정보를 담은 메타데이터
  캐시를 갖고 있기 때문이다 (6장, p.144).[^shapira2021]
- 클라이언트는 이 정보를 캐시해 요청 라우팅에 쓰고, 주기적으로 갱신한다. 갱신 간격은
  `metadata.max.age.ms`로 정한다 (6장, p.144).[^shapira2021]
- 갱신을 앞당기는 신호도 있다 — **"Not a Leader" 오류를 받으면 클라이언트는 재시도 전에
  메타데이터를 갱신한다.** 그 오류 자체가 캐시가 낡았다는 뜻이기 때문이다 (6장,
  p.144).[^shapira2021]

## 프로듀스 요청

- 리더 레플리카를 가진 브로커는 프로듀스 요청을 받으면 먼저 검증 셋을 돌린다 (6장,
  p.145):[^shapira2021]
  - 데이터를 보낸 사용자가 그 토픽에 쓰기 권한이 있는가.
  - 요청에 지정된 `acks` 값이 유효한가(0·1·all만 허용).
  - `acks=all`이면 메시지를 안전하게 쓸 만큼 인-싱크 레플리카가 충분히 있는가. (인-싱크
    레플리카 수가 설정값 아래로 내려가면 새 메시지를 거부하도록 브로커를 설정할 수 있다.)
- 그다음 로컬 디스크에 쓴다. 여기에 중요한 성질이 있다 — **리눅스에서 메시지는
  파일시스템 캐시에 쓰이며, 언제 디스크에 내려갈지에 대한 보장은 없다. 카프카는 데이터가
  디스크에 영속화되기를 기다리지 않고 메시지 내구성을 복제에 의존한다** (6장,
  p.145).[^shapira2021]
- 응답 시점은 `acks`가 정한다 — 0이나 1이면 즉시 응답하고, **all이면 요청을 퍼거토리에
  보관했다가 팔로워 레플리카들이 메시지를 복제한 것을 리더가 관찰한 시점에 응답한다**
  (6장, p.145).[^shapira2021]

## 페치 요청

- 클라이언트는 토픽·파티션·오프셋 목록을 담아 요청한다 — "토픽 Test 파티션 0의 오프셋
  53부터, 파티션 3의 오프셋 64부터 보내 달라"는 식이다 (6장, p.145).[^shapira2021]
- 파티션마다 **반환량 상한**을 지정하는데, 이는 클라이언트가 응답을 담을 메모리를 미리
  할당해야 하기 때문이다. 상한이 없으면 브로커가 클라이언트를 메모리 부족에 빠뜨릴 만큼
  큰 응답을 보낼 수 있다 (6장, p.145).[^shapira2021]
- 리더는 요청 유효성부터 본다 — 그 오프셋이 파티션에 존재하는가. 너무 오래돼 삭제됐거나
  아직 존재하지 않는 오프셋이면 오류로 응답한다 (6장, p.145).[^shapira2021]
- 존재하면 상한까지 읽어 보내는데, **카프카는 제로카피(zero-copy) 방식으로 보낸다** —
  파일(더 정확히는 리눅스 파일시스템 캐시)에서 네트워크 채널로 중간 버퍼 없이 직접
  보낸다. 대부분의 데이터베이스가 로컬 캐시를 거쳐 보내는 것과 다르며, 바이트 복사와
  메모리 버퍼 관리의 오버헤드가 사라져 성능이 크게 개선된다 (6장,
  pp.145–146).[^shapira2021]
- 상한뿐 아니라 **하한**도 지정할 수 있다. 예를 들어 10K로 두면 "보낼 데이터가 최소 10K
  바이트 모이면 그때 결과를 달라"는 뜻이다 (6장, p.146).[^shapira2021]
  - 효과는 CPU와 네트워크 사용량 절감이다 — 트래픽이 적은 토픽에서 클라이언트가 몇
    밀리초마다 요청을 던지고 빈손으로 돌아오는 대신, 요청 한 번을 보내고 브로커가 데이터가
    쌓일 때까지 기다린다. 오가는 데이터 총량은 같지만 왕복이 훨씬 줄어든다.
  - 무한정 기다릴 수는 없으므로 클라이언트가 타임아웃도 정한다 — "x 밀리초 안에 최소량을
    채우지 못했으면 있는 것만 보내라."
- 리더에 있는 데이터가 전부 읽히지는 않는다 — **대부분의 클라이언트는 모든 인-싱크
  레플리카에 쓰인 메시지만 읽을 수 있다.** 아직 아닌 메시지를 페치하려 하면 오류가 아니라
  빈 응답이 돌아온다. 팔로워 레플리카는 이 제한에서 면제된다 — 그렇지 않으면 복제 자체가
  성립하지 않는다 (6장, p.146).[^shapira2021]
- 이 제한의 이유는 일관성이다 — 충분히 복제되지 않은 메시지는 "안전하지 않은" 것으로
  간주된다. 리더가 죽고 다른 레플리카가 그 자리를 대신하면 그 메시지들은 카프카에서
  사라지는데, 그것을 이미 읽은 컨슈머가 있으면 컨슈머 사이에 불일치가 생긴다 (6장,
  pp.146–147).[^shapira2021]
- 대가는 다시 지연이다 — 복제가 느리면 새 메시지가 컨슈머에 닿는 데 더 오래 걸린다.
  **이 지연은 `replica.lag.time.max.ms`로 제한된다** (6장, p.147).[^shapira2021]
- 파티션을 많이 구독하는 컨슈머를 위한 최적화가 페치 세션 캐시(fetch session cache)다
  (6장, p.147):[^shapira2021]
  - 문제는 요청마다 전 파티션 목록을 보내고 브로커가 전 메타데이터를 돌려주는 비효율이다
    — 파티션 집합도 메타데이터도 거의 바뀌지 않고, 돌려줄 데이터가 별로 없는 경우도 많다.
  - 컨슈머는 소비 중인 파티션 목록과 메타데이터를 담은 세션 생성을 시도할 수 있다. 세션이
    생기면 요청마다 파티션을 다 적을 필요 없이 **증분 페치 요청**을 쓸 수 있고, 브로커는
    변경이 있을 때만 메타데이터를 응답에 포함한다.
  - 세션 캐시는 공간이 제한적이라 만들어지지 못하거나 축출될 수 있다. 카프카는 팔로워
    레플리카와 파티션 수가 많은 컨슈머를 우선한다. 실패 시 브로커가 알맞은 오류를 주고
    **컨슈머는 전체 페치 요청으로 조용히 되돌아간다.**

## 프로토콜의 진화

- 클라이언트가 쓰는 요청은 `Metadata`·`Produce`·`Fetch` 셋이 가장 흔하지만, **프로토콜은
  현재 61종의 요청 유형을 다루며 계속 늘어난다.** 컨슈머만 해도 그룹 구성과 소비 조율,
  컨슈머 그룹 관리에 15종을 쓴다 (6장, p.147).[^shapira2021]
- 같은 프로토콜이 브로커 사이의 통신에도 쓰인다. 이 요청들은 내부용이며 클라이언트가
  쓰면 안 된다 — 예를 들어 컨트롤러는 새 리더에게 `LeaderAndIsr` 요청을 보내 클라이언트
  요청을 받기 시작하라 알리고, 팔로워에게도 보내 새 리더를 따르라 알린다 (6장,
  p.148).[^shapira2021]
- 진화 방식은 둘이다 — **새 요청 유형을 더하거나, 기존 요청을 수정해 능력을 더한다**
  (6장, p.148):[^shapira2021]
  - 토픽 생성은 주키퍼를 직접 갱신하는 CLI가 하던 일이었으나 `CreateTopicRequest` 등이
    추가됐다. 그 덕에 **주키퍼 라이브러리가 없는 언어의 클라이언트도 브로커에 요청해
    토픽을 만들 수 있다.**
  - (앞 항목은 Kafka 3.x 이하 기준 서술 — 4.0 이후에는 주키퍼 자체가 없으므로 "주키퍼를
    직접 갱신하던 CLI"라는 대비가 성립하지 않는다.)
  - 수정의 예는 0.9.0과 0.10.0 사이의 `Metadata` 응답이다. 컨트롤러 정보를 담기 위해
    버전 1이 추가됐고, 0.9.0 클라이언트는 버전 0을 보내며 브로커는 버전에 맞춰 응답한다.
- 여기서 나오는 운영 규칙: **클라이언트보다 브로커를 먼저 업그레이드하라.** 새 브로커는
  옛 요청을 다룰 줄 알지만 그 반대는 성립하지 않는다 — 0.10.0 클라이언트가 버전 1
  `Metadata` 요청을 0.9.0 브로커에 보내면 오류로 응답한다 (6장,
  p.148).[^shapira2021]
- 0.10.0에 추가된 `ApiVersionRequest`는 이 문제를 완화한다 — 클라이언트가 브로커에 각
  요청의 지원 버전을 물어보고 알맞은 버전을 쓴다. **제대로 쓰는 클라이언트는 접속한
  브로커가 지원하는 프로토콜 버전으로 옛 브로커와도 통신할 수 있다** (6장,
  pp.148–149).[^shapira2021]
