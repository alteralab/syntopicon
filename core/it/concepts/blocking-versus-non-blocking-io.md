# 블로킹 I/O와 논블로킹 I/O

이 페이지의 질문: **스레드가 입출력을 기다리지 않게 하려면 무엇이 달라져야 하며, 스레드 수를
늘리는 손쉬운 답은 어디서 멈추는가.**

## 두 모델의 정의

- 블로킹(blocking)의 정의는 짧다 — 입출력(input/output, I/O)이 일어나면 호출한 스레드가 그 연산이
  끝날 때까지 기다린다. 그동안 스레드는 필요한 데이터를 얻을 때까지 사실상 막힌 채로 놀고 있다
  (6장 "Blocking Versus Non-blocking I/O", p.249).[^rahman2025]
- 논블로킹(non-blocking) I/O는 그 반대다 — 스레드가 I/O 연산에 붙들리지 않는다. 기다리는 대신,
  I/O가 배경에서 일어나는 동안 스레드는 다른 작업을 계속 실행할 수 있다 (6장,
  p.249).[^rahman2025]
- 기제의 핵심은 책임의 이동이다 — 논블로킹 시스템에서는 운영 체제가 I/O를 처리할 책임을 넘겨받는다.
  연산이 끝나면 운영 체제가 애플리케이션에 알리며, 보통은 콜백 함수를 부르는 방식이다. 그래서 요청을
  시작한 스레드는 놀고 앉아 있을 필요가 없고 데이터가 준비되면 알림만 받으면 된다 (6장,
  p.249).[^rahman2025]

## 예제가 감당해야 하는 것

- 저자는 개념을 구체로 만들기 위해 HTTP 서버를 짓는다. 요청 파이프라이닝(request pipelining)을
  다뤄야 하는 서버이고, 이것은 클라이언트가 응답을 기다리지 않고 여러 요청을 보낼 수 있는 HTTP/1.1의
  핵심 기능이다 (6장, p.249).[^rahman2025]
- 서버가 해내야 하는 일이 다섯이다 (6장, p.249):[^rahman2025]
  - 여러 클라이언트의 연결을 받아들인다.
  - 복잡도가 제각각인 HTTP 요청을 처리한다. 빠른 연산과 느린 연산이 섞인다.
  - 킵얼라이브(keep-alive) 세션을 위해 연결 상태를 유지한다.
  - 요청 파이프라이닝을 올바르게 다룬다.
  - 수백에서 수천에 이르는 동시 연결까지 확장한다.

## 단일 스레드 블로킹 서버

- 첫 판은 단일 스레드 블로킹 서버다. 받아들인 소켓을 곧바로 처리 메서드에 넘기고, 그 메서드가
  끝나야 다음 연결을 받는다 (6장, pp.249–250).[^rahman2025]

  ```java
  public class BlockingHttpServer {
      private static final int PORT = 8080;
      private static final AtomicInteger requestCounter = new AtomicInteger(0);

      public static void main(String[] args) throws IOException {
          try (ServerSocket serverSocket = new ServerSocket(PORT)) {
              serverSocket.setReuseAddress(true);
              while (true) {
                  Socket clientSocket = serverSocket.accept();
                  handleConnection(clientSocket);
              }
          }
      }
  }
  ```

- 저자가 짚는 요점이 다섯이다 (6장, pp.250–251):[^rahman2025]
  - 주소 재사용을 켜는 것은 개발 중에 주소가 이미 쓰이고 있다는 오류를 피하기 위해서다.
  - `accept()` 메서드는 클라이언트가 연결할 때까지 막는다. 단일 스레드가 새 연결을 기다리며 멈추는
    자리가 여기다.
  - 소켓 타임아웃을 5초로 두는 것은 죽은 연결을 감지하고 서버가 무한정 매달리는 것을 막기 위해서다.
  - `parseRequest()` 메서드는 완전한 HTTP 요청이 도착할 때까지 막는다. 한 클라이언트의 요청을
    기다리는 동안 서버는 새 연결을 받아들일 수 없다.
  - 결정적 한계는 처리 쪽이다 — `processRequest()`가 오래 걸리면, 이를테면 느린 데이터베이스 질의를
    만나면 서버 전체가 막힌다. 다른 어떤 클라이언트도 연결하거나 서비스를 받지 못한다.
- 막힘을 눈에 보이게 하려고 처리 시간을 흉내 낸다 — 경로가 느린 쪽이면 30초, 중간이면 500밀리초,
  나머지는 100밀리초를 잔다. 느린 요청 하나가 서버 전체를 30초 동안 막는다 (6장,
  p.251).[^rahman2025]
- 두 부품의 역할을 저자가 갈라 준다 — `Socket`은 네트워크 위에서 도는 프로그램들 사이 양방향 통신
  링크의 한쪽 끝점이고, `ServerSocket`은 들어오는 연결을 계속 듣고 클라이언트 요청을 그에 맞게
  처리한다 (6장, p.252).[^rahman2025]
- 그래서 동작이 이렇게 된다 — 서버가 클라이언트를 다루는 동안 호출 스레드는 그 클라이언트가 연결을
  끊을 때까지 막힌다. 클라이언트가 데이터를 그만 보내면서 연결은 유지하면 서버는 입력을 기다리며
  붙들려 있다. 단일 스레드 서버이므로 현재 세션이 끝날 때까지 다른 클라이언트는 연결할 수 없다
  (6장, p.253).[^rahman2025]

## 막힘이 무엇을 막는지 잰 실측

- 저자는 `curl`로 세 가지 실험을 돌린다 (6장, pp.253–255).[^rahman2025]
- 첫째, 빠른 경로 요청 하나는 즉시 끝난다. 서버가 처리하고 연결을 닫는다 (6장,
  p.254).[^rahman2025]
- 둘째가 문제를 드러낸다 — 느린 요청이 처리되는 동안 다른 클라이언트로 접속하면, 그 둘째
  클라이언트는 TCP 연결을 성공적으로 맺지만 서버가 그것을 받아들이지 않는다. 연결을 맺는 일은
  운영 체제가 하고, 서버는 여전히 느린 요청을 처리하느라 막혀 있기 때문이다. 저자가 실은 출력에서
  `curl`은 5,006밀리초 뒤에 0바이트를 받은 채 타임아웃한다 (6장, p.254).[^rahman2025]
- 셋째가 가장 잘 드러내는 실험이다 — 빠른 요청과 느린 요청과 빠른 요청을 파이프라인으로 셋 보내고
  시간을 잰다. 셋 중 둘이 빠른 요청인데도 전체 시간이 30초를 넘고, 저자가 실은 출력의 총 시간은
  47.811초다. 모든 요청이 순차로 처리되어야 하므로 가운데의 느린 요청이 전부를 막는다 (6장,
  p.255).[^rahman2025]

## 스레드를 늘리는 답과 그 상한

- 손쉬운 해법이 멀티스레딩이다 — 클라이언트마다 새 스레드를 띄우면 여러 연결을 동시에 다룰 수 있다
  (6장, p.255).[^rahman2025]
- 개정판이 얻는 것이 넷이다 (6장, p.256):[^rahman2025]
  - 연결을 다룰 스레드 10개짜리 고정 스레드 풀을 만든다.
  - 주 스레드는 곧바로 새 연결을 받아들이는 일로 돌아갈 수 있다.
  - 연결마다 자기 스레드에서 돌아 동시 처리가 된다.
  - 개별 연결은 여전히 요청을 순차로 처리하므로 파이프라이닝의 순서가 지켜지고, 그러면서 여러
    연결이 동시에 서비스된다.
- 그 답이 멈추는 자리를 저자가 명시한다 — 스레드 수를 늘려 더 많은 클라이언트를 받을 수는 있지만,
  가상 스레드가 오기 전에는 이 접근에 내재된 한계가 있었다. 플랫폼 스레드는 비싸고, 어느 지점을
  넘어서면 수를 늘려도 더 나은 결과가 나오지 않는다 (6장, p.257).[^rahman2025] 그 지점의 수치는
  [스레드의 숨은 비용](../concepts/hidden-costs-of-threads.md)과
  [가상 스레드의 확장 한계](../concepts/virtual-thread-scalability-limits.md)에 있다.
- 가상 스레드로는 확장이 코드 한 줄을 바꾸는 일이 된다 — 고정 스레드 풀 자리에
  `Executors.newVirtualThreadPerTaskExecutor()`를 놓으면 최소한의 오버헤드로 아주 많은 동시 연결을
  감당하게 된다 (6장, p.257).[^rahman2025]
- 그러나 저자는 곧바로 방향을 튼다 — 지금의 초점은 그것이 아니고, 가상 스레드 이전에 어떤 대안이
  있었는지를 보겠다는 것이다. 그 대안이 NIO다 (6장, p.257).[^rahman2025]
