하나의 질문: **도메인 모델과 돌아가는 코드는 어떤 관계여야 하며, 그 관계가 끊어지면
무엇이 사라지는가.**

## 분석 모델과 설계 모델을 갈라 두면 둘 다 죽는다

- 장을 여는 두 실패담이 같은 결말에 이른다. 하나는 벽 하나를 덮는 클래스 다이어그램을 몇 달
  들여 만들었으나 구현으로 옮겨지지 않은 프로젝트, 다른 하나는 모델링을 아예 하지 않고 기능을
  쌓아 올린 프로젝트다 — **섬뜩한 것은 두 과정의 최종 산물이 매우 비슷했다는 것이다! 둘 다
  기능은 했지만 비대하고 이해하기 매우 어려웠으며 결국 유지 보수가 불가능했다** (3장,
  p.46).[^evans2003]
- 이 소스가 요구하는 것이 무엇인지 먼저 규정된다 — **도메인 주도 설계는 초기 분석을 돕는 데
  그치지 않고 설계의 바로 그 토대가 되는 모델을 요구한다** (3장, p.46).[^evans2003]
- 분석 모델(analysis model)이라는 관행이 정면으로 지목된다 — 그것은 **소프트웨어 시스템에서
  맡을 역할을 전혀 고려하지 않고 업무 도메인을 분석해 그 개념을 조직한 산물**이며
  **이해만을 위한 도구로 의도된다** (3장, p.47).[^evans2003] 그 결과가 이렇다 (3장,
  p.48):[^evans2003]
  - **그런 분석 중에 어느 정도 지식 정련이 일어나지만, 코딩이 시작되고 개발자가 설계를 위한
    새 추상을 짜내야 할 때 대부분이 소실된다.**
  - **순수 분석 모델은 도메인을 이해한다는 그 일차 목표조차 이루지 못하는데, 결정적 발견은
    언제나 설계·구현 노력 중에 나오기 때문이다.**
- **매핑이 없으면 정확성 자체를 물을 수 없다** — **설계나 그 중심부의 일부가 도메인 모델에
  대응하지 않으면 그 모델은 가치가 거의 없고, 소프트웨어의 정확성이 의심스러워진다. 동시에
  모델과 설계 기능 사이의 복잡한 매핑은 이해하기 어렵고, 실제로 설계가 변할 때 유지하기
  불가능하다** (3장, p.48).[^evans2003]
- 개념 없는 소프트웨어에 대한 판정 한 줄 — **원인이 무엇이든, 설계의 토대에 개념이 없는
  소프트웨어는 잘해야 자기 행위를 설명하지 못한 채 쓸모 있는 일을 하는 기계장치다** (3장,
  p.48).[^evans2003]

## 조항

- 모델 주도 설계(model-driven design)는 그 이분법을 폐기하는 것으로 정의된다 — **모델 주도
  설계는 분석 모델과 설계 모델의 이분법을 버리고 두 목적을 다 수행하는 단일 모델을 찾아
  나선다. 순수하게 기술적인 문제를 제쳐 두면, 설계의 각 객체는 모델에 서술된 개념적 역할을
  수행한다** (3장, p.49).[^evans2003]
- 그 요구가 비싸다는 것도 함께 적힌다 — **이것은 우리가 고른 모델에 더 많은 것을 요구하게
  만드는데, 그 모델이 꽤 다른 두 목표를 충족해야 하기 때문이다** (3장, p.49).[^evans2003]
  그리고 어느 쪽으로도 타협하지 말라는 단서가 붙는다 — **이 결속이 약해진 분석의 대가로
  와서는 안 되며, 기술적 고려에 치명적으로 훼손되어서도 안 된다. 도메인 발상을 반영하되
  소프트웨어 설계 원칙을 저버린 서투른 설계를 받아들일 수도 없다** (3장, p.49).[^evans2003]
- 처방 문단 (3장, p.49):[^evans2003]

> Design a portion of the software system to reflect the domain model in a very literal way,
> so that mapping is obvious. Revisit the model and modify it to be implemented more naturally
> in software, even as you seek to make it reflect deeper insight into the domain. Demand a
> single model that serves both purposes well, in addition to supporting a robust UBIQUITOUS
> LANGUAGE.

- 모델이 실용적이지 않거나 도메인을 충실히 표현하지 못하면 **새 모델을 찾아야 한다**는 것이
  이 조항의 반복 규칙이고, 그래서 **모델링과 설계 과정은 하나의 반복 루프가 된다** (3장,
  p.49).[^evans2003]

## 코드를 바꾸는 것이 모델을 바꾸는 것이다

- 조항의 후반부가 이 귀결을 명시한다 (3장, p.49):[^evans2003]

> Draw from the model the terminology used in the design and the basic assignment of
> responsibilities. The code becomes an expression of the model, so a change to the code may
> be a change to the model. Its effect must ripple through the rest of the project's
> activities accordingly.

- [유비쿼터스 언어](ubiquitous-language.md)의 "언어를 바꾸는 것이 모델을 바꾸는 것"과 짝을
  이루는 조항이다. 셋이 한 고리로 묶인다 — **말을 바꾸면 모델이 바뀌고, 코드를 바꿔도 모델이
  바뀐다.** 그래서 이 소스에서 이름 바꾸기와 리팩터링은 모델 갱신 절차의 일부다.
- 단일 모델이 사는 세 가지 이득이 열거된다 — **단일 모델은 오류 가능성을 줄이는데, 설계가
  이제 신중히 고려된 모델의 직접적 산물이기 때문이다. 설계가, 심지어 코드 자체가 모델의
  소통력을 갖는다** (3장, p.50).[^evans2003] 그리고 범위 단서 — **때로는 서브시스템마다 다른
  모델이 있겠지만, 시스템의 특정 부분에는 코드에서 요구사항 분석까지 개발 노력의 모든 측면에
  걸쳐 오직 하나의 모델만 적용되어야 한다** (3장, p.50).[^evans2003]

## 모델링 패러다임을 지원하는 언어가 필요하다

- 조건이 하나 붙는다 — **모델 주도 설계가 값을 하려면 그 대응이 문자 그대로여야 하고, 사람이
  실수할 여지 안에서 정확해야 한다. 그런 긴밀한 모델·설계 대응을 가능하게 하려면 모델의
  개념에 직접 대응하는 것을 만들 수 있게 해 주는 소프트웨어 도구가 지원하는 모델링 패러다임
  안에서 일하는 것이 거의 필수다** (3장, p.50).[^evans2003]
- 객체 지향이 왜 이 조건을 만족하는가 — **객체 지향 프로그래밍이 강력한 것은 그것이 모델링
  패러다임에 기반하고 모델 구성물의 구현을 제공하기 때문이다. 프로그래머에게 객체는 메모리에
  정말로 존재하고, 다른 객체와 연관을 갖고, 클래스로 조직되고, 메시징으로 이용 가능한 행동을
  제공한다** (3장, p.51).[^evans2003] 그리고 **객체 설계의 진짜 돌파는 코드가 모델의 개념을
  표현할 때 온다** (3장, p.51).[^evans2003]
- 절차형 언어가 왜 이 조건을 만족하지 못하는가 — **순수 절차형 언어에 대응하는 모델링
  패러다임이 없기 때문에 C 같은 언어를 쓰면 모델 주도 설계의 적용 가능성이 제한된다. …
  프로그래머가 도메인의 개념을 생각하고 있을지 몰라도 프로그램 자체는 일련의 기술적 데이터
  조작이다** (3장, p.51).[^evans2003]
- **여기서 이 소스의 핵심 구분이 한 줄로 나온다** — 절차형 언어의 복합 자료형에 대한 판정이다
  (3장, p.51):[^evans2003]

> Procedural languages often support complex data types that begin to correspond to more
> natural conceptions of the domain, but these complex types are only organized data, and they
> don't capture the active aspects of the domain.

  - **조직된 데이터와 모델을 가르는 선**이고, 이 KB에서 그 선을 따로 다루는 자리가
    [모델의 개념과 도메인의 사실](../concepts/model-concepts-versus-domain-facts.md)이다. 같은 구분이
    3장 첫머리의 실패담에서도 반복된다 — 두 프로젝트 모두 객체 패러다임을 **"멋진 자료 구조"로
    말고는** 활용하지 못했다는 진단이다 (3장, p.46).[^evans2003]

## 사례 이름 규약으로 개념을 유추하던 스크립트

- 인쇄 회로 기판(printed circuit board, PCB) 설계 도구 사례다. 도구는 전도체 하나하나(net)에
  규칙을 붙일 수 있지만 **버스**(bus)라는 개념을 모른다 — 엔지니어는 넷을 8·16·256개씩 버스로
  묶어 생각하는데 **문제는 레이아웃 도구에 버스 같은 개념이 없다는 것이다. 규칙은 수만 개의
  넷에 하나씩 배정되어야 한다** (3장, pp.52–53).[^evans2003]
- 엔지니어들의 우회책이 이 페이지의 핵심 반례다 — **엔지니어들은 넷에 대해 이름 규약(naming
  convention)을 조심스럽게 써서 데이터 파일을 알파벳순으로 정렬하면 한 버스의 넷들이 정렬된
  파일에서 함께 놓이게 했다. 그러면 스크립트가 파일을 파싱해 각 넷을 그 버스에 따라 수정할 수
  있다** (3장, p.53).[^evans2003]
- **저자의 판정이 이 사례의 결론이다** (3장, p.54):[^evans2003]

> What the script writers were trying to do was to supplement the tool's domain model with the
> concept of "bus." Their implementation infers the bus's existence through sorts and string
> matches, but it does not explicitly deal with the concept.

- 그리고 그 우회책이 무는 값이 세 가지로 계상된다 (3장, p.54):[^evans2003]
  - 스크립트가 수십 개로 늘었고 **여전히 그것들은 그저 파일 조작이다.**
  - **파일 형식이 다르면(그리고 여러 형식이 있다) 버스를 묶고 규칙을 적용한다는 개념이 같은데도
    처음부터 다시 시작해야 한다.**
  - **더 풍부한 기능이나 상호작용을 원하면 한 치마다 값을 치러야 한다.**

## 같은 문제를 모델로 푼 판

- 처방은 개념을 명시하는 것이다 — **앞의 논의는 이미 도메인 전문가가 자기 문제를 생각하는 데
  쓰는 개념을 서술했다. 이제 우리는 그 개념을 소프트웨어의 기반으로 삼을 모델로 명시적으로
  조직할 필요가 있다** (3장, p.54).[^evans2003] 모델은 `Abstract Net`을 부모로 두고 `Net`과
  `Bus`를 그 아래 두며, `Net`이 `Bus`를 참조한다 (Figure 3.3, p.55).[^evans2003]
- 그 모델을 객체 지향 언어로 구현하면 **핵심 기능이 거의 사소해진다**는 것이 저자의 판정이고,
  그 실물이 다음 두 클래스다. `assignedRules()`가 자기 규칙과 자기 버스의 규칙을 합치는 것이
  이 설계의 전부다 (3장, p.55):[^evans2003]

  ```java
  abstract class AbstractNet {
      private Set rules;

      void assignRule(LayoutRule rule) {
          rules.add(rule);
      }

      Set assignedRules() {
          return rules;
      }
  }

  class Net extends AbstractNet {
      private Bus bus;

      Set assignedRules() {
          Set result = new HashSet();
          result.addAll(super.assignedRules());
          result.addAll(bus.assignedRules());
          return result;
      }
  }
  ```

- 이름 규약은 사라지지 않고 **한 자리로 밀려난다.** 파일에서 넷을 읽어 이름 규약으로 버스를
  유추하는 일은 `Inferred Bus Factory`라는 유틸리티 하나가 맡고, 그 책임이
  **"넷의 컬렉션이 주어지면 이름 규약을 써서 버스를 유추하고 인스턴스를 만든다"**로 적힌다
  (3장, p.56).[^evans2003]
- 두 설계의 차이가 테스트에서 계상된다 — **스크립트를 테스트하는 유일한 방법은 파일 입출력
  전 구간 비교뿐**인 반면 모델 쪽은 **서비스와 리포지터리 각각을, 그리고 더 중요하게는 핵심
  도메인 로직을 단위 테스트할 수 있다** (3장, pp.56–57).[^evans2003]
- 마지막 단서 — **그런 설계는 한 걸음에 나오지 않는다는 것을 기억하라. 도메인의 중요한 개념을
  단순하고 예리한 모델로 증류하려면 리팩터링과 지식 정련을 여러 차례 반복해야 한다** (3장,
  p.57).[^evans2003]

## 사용자가 보는 모델과 구현 모델이 어긋날 때

- 저자가 드는 실물은 인터넷 익스플로러의 즐겨찾기다 — 사용자는 그것을 **세션을 넘어 지속되는
  웹 사이트 이름의 목록**으로 생각하지만 구현은 URL을 담은 파일이고 파일명이 목록에 오른다.
  그래서 파일명에 못 쓰는 문자를 넣으면 **"파일 이름에는 다음 문자를 쓸 수 없습니다"**라는
  오류가 나오고, 저자는 **무슨 파일 이름?**이라고 되묻는다 (3장, p.58).[^evans2003]
  더 나쁜 쪽은 웹 페이지 제목에 이미 그 문자가 있으면 **조용히 제거하는** 동작이다 —
  **데이터를 조용히 바꾸는 것은 대부분의 애플리케이션에서 완전히 받아들일 수 없다** (3장,
  p.58).[^evans2003]
- 이것이 앞의 분석·설계 이분법과 다른 짝의 문제로 분류된다 — **여기서 우리는 다른 한 쌍의
  모델에서 일어나는 문제를 본다: 사용자 모델과 설계·구현 모델** (3장, p.58).[^evans2003]
- 처방은 둘 중 하나이고 둘 다 **모델을 하나로 만드는 것**이다 (3장, pp.58–59):[^evans2003]
  - **웹 즐겨찾기가 실제로 바로 가기 파일의 모음이라면 이 사실을 사용자에게 노출하고 혼란스러운
    대체 모델을 제거하라.** 그러면 사용자는 파일 시스템에 대해 아는 것을 여기에 쓸 수 있다.
  - 아니면 **즐겨찾기를 다른 방식으로, 이를테면 데이터 파일에 저장해 그 자신의 규칙을 따르게
    하라.** 그 규칙은 웹 페이지에 적용되는 이름 규칙일 것이다.
- 그리고 이득이 규정된다 — **설계가 사용자와 도메인 전문가의 기본 관심사를 반영하는 모델에
  기반하면, 설계의 뼈대를 다른 설계 접근보다 더 많이 사용자에게 드러낼 수 있다. 모델을 드러내는
  것은 사용자에게 소프트웨어의 잠재력에 대한 더 많은 접근을 주고 일관되고 예측 가능한 행동을
  낳는다** (3장, p.59).[^evans2003]

## 모델링하는 사람과 코드 쓰는 사람을 가르지 마라

- 제조업 비유에 대한 반박으로 시작한다 — 숙련 기술자가 설계하고 덜 숙련된 인력이 조립한다는
  추론이 **단 하나의 단순한 이유로 많은 프로젝트를 망쳤다 — 소프트웨어 개발은 전부가 설계다**
  (3장, p.60).[^evans2003]
- 저자 자신이 모델러로만 배치됐던 프로젝트의 실패 원인 둘 (3장, p.60):[^evans2003]
  - **첫째, 모델의 의도 일부가 인계 과정에서 소실됐다.** 모델의 전체 효과는 세부에 매우
    민감한데 **그 세부가 UML 다이어그램이나 일반적 논의로 늘 전달되지는 않는다.**
  - **다른 문제는 모델과 구현·기술의 상호작용에서 오는 피드백의 간접성이었다.** 모델의 어떤
    측면이 플랫폼에서 몹시 비효율적이라는 사실이 저자에게 도달하기까지 몇 달이 걸렸다.
- 그 프로젝트에서 모델이 최종적으로 무엇이 됐는지가 이 페이지의 앞 절과 이어진다 — 개발자들은
  결국 모델 없이 돌아가는 소프트웨어를 썼고, 모델은 **한낱 자료 구조로 격하됐다**(reduced to a
  mere data structure) (3장, p.60).[^evans2003]
- 진단이 세 갈래로 정리된다 (3장, p.61):[^evans2003]
  - **코드를 쓰는 사람이 모델에 책임감을 느끼지 않거나 모델을 애플리케이션에 어떻게 작동시킬지
    이해하지 못하면 그 모델은 소프트웨어와 아무 상관이 없다.**
  - **개발자가 코드를 바꾸는 것이 모델을 바꾸는 것임을 깨닫지 못하면 그들의 리팩터링은 모델을
    강화하는 대신 약화시킬 것이다.**
  - **모델러가 구현 과정에서 분리되면 그 사람은 구현의 제약에 대한 감각을 결코 얻지 못하거나
    빠르게 잃는다.**
- **한 줄 판정** (3장, p.61):[^evans2003]

> Programmers are modelers, whether anyone likes it or not.

- 처방 (3장, pp.61–62):[^evans2003]

> Any technical person contributing to the model must spend some time touching the code,
> whatever primary role he or she plays on the project. Anyone responsible for changing code
> must learn to express a model through the code. Every developer must be involved in some
> level of discussion about the model and have contact with domain experts.
