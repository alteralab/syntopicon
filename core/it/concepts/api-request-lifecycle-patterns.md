하나의 질문: **요청 하나가 너무 오래 걸리거나, 두 번 오거나, 너무 많이 올 때 API는 무엇을
하는가.**

이 장이 같은 자리에 두는 **재시도**와 **캐싱**은 이 KB에 이미 자리가 있어 거기에 얹었다 —
재시도는 [안정성 패턴](../concepts/stability-patterns.md)의 재시도 절, 캐싱은
[분산 체계에서의 캐싱](../concepts/caching-in-distributed-systems.md)이다.

## 시간 초과를 넘기는 작업

- 문제의 진술이 시간 초과에서 시작한다 — **API 요청은 비디오 파일 처리, 재무 보고서 생성,
  기계학습 모델 훈련 같은 작업을 촉발하는 데 쓰일 수 있다.** 요청-응답 모델로 API와 통신하는
  클라이언트는 보낸 요청마다 응답을 기대하고, **REST API로 보냈다면 그 응답이 제때 오기를
  기대한다** (2장 §"Long-Running Tasks", p.62).[^dynowski2025]
- **보통 클라이언트와 API 서버는 무한한 대기를 피하려고 미리 정한 시간 초과를 쓴다.** 그런데
  **이 시간 초과 기제는 처리 시간이 비교적 짧은 작업에만 효과가 있고, 작업의 계산 시간이 시간
  초과를 넘는 시나리오에서는 실패한다** — 많은 양의 데이터를 갈아 넣거나 비디오를 변환하는
  경우다 (2장, p.62).[^dynowski2025]
- **여기가 긴 작업(long-running task) 패턴 — 긴 실행 연산(long-running operations)이라고도
  하는 — 이 도울 수 있는 자리**다 (2장, p.62).[^dynowski2025]

## 긴 작업 패턴이 하는 일

- 절차가 이렇다 (2장, p.62).[^dynowski2025]
  - **클라이언트가 작업 처리를 촉발하는 요청을 API에 보낸다.** 그 작업은 **보통 API를 서빙하는
    기계가 아닌 다른 기계에서 처리된다.**
  - **API는 처리 결과를 돌려주는 대신 시작된 작업의 유일한 식별자를 돌려주고**, 클라이언트는
    그것으로 작업의 상태(진행)를 조회한다.
  - **REST API가 그 작업을 받아들일 때 응답 상태 코드는 202(Accepted)여야 한다.**
  - **작업을 API로 노출하는 한 방법은 API 최상위에 작업 자원을 정의하는 것**이다
    (`/api/v1/tasks`).
- 대가가 상태 보관에 있다 — **이 접근은 API가 작업의 메타데이터를 영속화하고 추적할 것을
  요구한다.** 메타데이터로 드는 것이 **상태, 진행, 시작과 완료 타임스탬프, 오류**다. 그리고
  **어떤 작업은 메타데이터 같은 결과를 돌려주고, 어떤 작업은 결과가 저장된 위치(예컨대 파일의
  위치)를 담을 수 있다** (2장, p.62).[^dynowski2025]

## 작업의 상태와 맞춤 동작

- **작업은 상태 기계로 서술될 수 있고, 그 상태 기계가 가능한 모든 상태 전이에 대한 작업의
  행동을 포착한다** (2장, p.62).[^dynowski2025]
- 상태 관리가 있는 쪽과 없는 쪽이 갈린다 (2장, p.62).[^dynowski2025]
  - **어떤 긴 작업은 일시 정지·재개·취소를 허용해 상태 관리를 지원한다.**
  - **반면 쏘고 잊는(fire-and-forget) 작업 — 시작되고 나면 클라이언트가 갱신을 받지 않는
    작업 — 에서는 클라이언트 쪽 상태 관리가 아예 없다.**
- **이진이 아닌 작업**, 곧 성공과 실패 말고도 상태를 갖는 작업(취소 가능·일시 정지 가능·재개
  가능)은 **그 상태들을 다루는 맞춤 동작을 API에 구현해야 하고**, 그러면
  `/api/v1/tasks/1?action=resume` 같은 인터페이스가 된다 (2장, p.62).[^dynowski2025]
- 곁주에서 그 모양을 고른 이유를 댄다 — **맞춤 동작이 `/resource/ID/action`이 아니라 질의
  매개변수를 쓴 `/resource/ID?action`으로 구성된 것에 주목하라. 뒤쪽 패턴의 문제는 `action`이
  자원(`action` 자원)으로 해석될 수 있다는 것**이다 (2장, p.62).[^dynowski2025]

## 완료를 아는 두 길

- 물음이 그대로 적힌다 — **긴 작업을 시작한 클라이언트는 그 작업이 언제 끝났는지 어떻게
  아는가** (2장, p.63).[^dynowski2025]
- **폴링** — 클라이언트가 주기적으로 API에 작업 상태를 묻는다. **단점은 클라이언트가 만들어
  내는 요청의 과잉**이다 (2장, p.63).[^dynowski2025]
- **오래 사는 연결** — 폴링의 대안으로 API에 오래 사는 연결을 맺는다. **API는 연결을 열어 둔
  채로 두었다가 작업을 끝내고 메시지를 클라이언트에 보낸 뒤 닫는다.** 맞교환은 **API가 밑에
  깔린 연결들을 관리해야 하고 그것이 API 서버의 자원 사용을 늘릴 수 있다**는 것이다 (2장,
  p.63).[^dynowski2025]

## 요청 중복 제거

- 규정과 원인 (2장 §"Request Deduplication", p.63).[^dynowski2025]
  - **요청 중복(request duplication)은 같은 요청이 한 번보다 많이 보내질 때 일어난다.**
  - 원인으로 드는 것이 **UI 요소를 빠르게 여러 번 클릭하는 것**과 **결함 있는 애플리케이션
    로직**이다.
- 해로운 쪽이 명시된다 — **중복된 비멱등 요청은 바람직하지 않고, 특히 금융 맥락에서 그렇다.
  반복된 요청이 같은 상품에 대해 고객의 신용카드에 두 번 청구되는 결과로 이어질 수 있기
  때문**이다 (2장, p.63).[^dynowski2025]
- 그러나 반복이 필요한 경우가 곧바로 구분된다 — **어떤 경우에는 요청을 반복하는 것이
  필요하다.** 서버·네트워크·검증 오류가 일어나 원래 요청을 재시도해야 할 때다 (2장,
  p.63).[^dynowski2025] 곧 이 패턴이 막는 것은 **의도하지 않은 반복**이지 재시도가 아니다.
- 수단은 식별자다 — **클라이언트가 유일한 요청 ID를 만들어 요청에 담고, API가 같은 요청 ID로
  두 번째 요청을 받으면 그 중복을 알맞게 처리한다.** 알맞은 처리로 드는 것이 **이전의 성공
  응답을 돌려주거나 오류를 돌려주는 것**이다 (2장, p.63).[^dynowski2025]
- 곁주에 단서가 하나 붙는다 — **한 클라이언트가 만드는 요청 ID는 유일해야 한다. UUID는 식별자
  충돌의 위험을 최소화하도록 설계된 것이지 없애도록 설계된 것이 아니다** (2장,
  p.63).[^dynowski2025]

## 속도 제한

- 규정 (2장 §"Rate Limiting", p.65).[^dynowski2025]
  - **속도 제한(rate limiting), 스로틀링(throttling)이라고도 하는 것은 합법적이거나 악의적인
    요청의 유입에서 API를 보호하는 데 쓸 수 있다.**
  - **스로틀링은 한 클라이언트가 같은 엔드포인트에 주어진 시간 구간 안에 보낼 수 있는 요청의
    수를 제한한다.**
- 전제가 하나 달려 있다 — **이것은 클라이언트가 식별될 수 있다는 것을 가정한다.** 저자들이 드는
  예가 **클라이언트 IP 주소를 기준으로 스로틀링을 수행하는 것**이고, 그러면 **API가 요청 처리에
  자원을 쓰는 것을 피한다** (2장, p.65).[^dynowski2025]
- 배치에 대한 조문이 붙는다 — **스로틀링은 이상적으로 요청의 네트워크 경로에서 가능한 한 이르게
  일어나야 한다** (2장, p.65).[^dynowski2025]

## 스로틀링만으로 막히지 않는 것

- 쓰임 하나가 더 있다 — **스로틀링은 전통적인 무차별 대입 공격이나 서비스 거부(DoS) 공격의
  영향을 줄이는 데 쓸 수 있다** (2장, p.65).[^dynowski2025]
- 저자들이 드는 시나리오가 비밀번호 재설정 기능이다. 정상 시나리오는 **그 절차를 밟는 사람이
  이메일 주인이고 재설정 요청을 한 번이나 몇 번만 한다는 것을 가정**하는데, **API를 해치려는
  공격자는 이 기능으로 DoS 공격을 수행할 수 있다** — 무한 루프로 재설정 엔드포인트에 HTTP
  `POST`를 보내는 것이다 (2장, pp.65–66).[^dynowski2025]
- 그리고 판정이 온다 — **공격자의 클라이언트 하나로는 서비스를 압도하기 어렵지만 많은
  클라이언트라면 가능하고**, 그것이 분산 서비스 거부(DDoS)다. **DDoS에 참여하는 클라이언트마다
  요청을 몇 번만 수행할 수 있으므로, 스로틀링만으로는 이 유형의 공격을 완화하기에 불충분하다**
  (2장, p.66).[^dynowski2025]

## 이 KB의 다른 자리에서 속도 제한이 가리키는 것

- **같은 이름이 서로 다른 것을 지킨다.** 겨루지 않지만 겹쳐 읽으면 어긋난다.
  - 여기서 속도 제한은 **클라이언트별 요청 수 상한**이고 지키는 대상이 API 자신이며, 두는
    자리는 네트워크 경로의 앞쪽이다.
  - [가상 스레드 시대의 속도 제한](../concepts/rate-limiting-with-virtual-threads.md)에서
    속도 제한은 **호출하는 쪽이 자기 아래 자원에 거는 동시성 상한**이고, 지키는 대상은 하류
    자원이다.
  - [안정성 패턴](../concepts/stability-patterns.md)의 부하 떨어내기는 **들어온 요청 가운데
    일부를 버리는 것**이고, 기준이 클라이언트가 아니라 남은 용량이다.

## "가능한 한 이르게"가 가리키는 구성 요소

**위 [속도 제한](#속도-제한)이 적은 배치 조문은 자리를 방향으로만 말한다 — 요청의 네트워크
경로에서 가능한 한 이르게 일어나야 한다는 것이다. 2022년 API 아키텍처 운영서가 그 자리에 이름을
붙인다. 겨루지 않고 같은 조문을 구체화한다.**

- **속도 제한이 API 게이트웨이의 기능으로 세어진다** — 그 소스가 리버스 프록시와 로드 밸런서와
  API 게이트웨이를 맞댄 표에서 **속도 제한은 API 게이트웨이 칸에만 붙고** 앞의 둘에는 없다
  (3장, 표 3-1, p.56).[^gough2022] 게이트웨이가 주는 횡단 요건을 세는 자리에도 **요청 속도
  제한**이 든다 (3장, p.58).[^gough2022]
- **왜 그 자리인가가 규모로 갈린다** — 엔터프라이즈 조직의 대다수는 **CDN과 웹 애플리케이션
  방화벽(WAF), 나아가 주변부 네트워크와 전용 DMZ 같은 보안 중심 층을 여럿** 두지만, **더 작은
  조직에서는 API 게이트웨이가 첫 방어선일 수 있다** (3장, p.64).[^gough2022]
  - **그러므로 "가능한 한 이르게"의 답이 조직마다 다르다.** 앞에 CDN과 WAF가 있으면 게이트웨이는
    가장 이른 자리가 아니고, 없으면 그것이 가장 이른 자리다. **이 읽기는 이 KB가 두 소스를
    맞대어 세운 것이고 두 책은 서로를 호명하지 않는다.** #hypothesis
- **그 층에 놓인 속도 제한이 무엇과 함께 서는지**도 적힌다 — **TLS 종단, 인증과 인가, IP 허용과
  차단 목록, WAF, 속도 제한과 부하 떨어내기, API 계약 검증**이다 (3장, p.64).[^gough2022]
  - **위 [속도 제한](#속도-제한)이 전제로 단 것이 클라이언트를 식별할 수 있어야 한다는
    것이었다.** 그 목록에서 **IP 허용과 차단 목록이 바로 옆에 선다** — 같은 식별 축이다.
  - **그림에만 있고 본문에 없는 단서 하나** — 그 소스의 그림 3-7은 게이트웨이 안에 허용·차단을
    **IP 대역**으로, 속도 제한을 **사용자별 초당 요청 수**로 적어 **두 기제의 식별 단위가 다르다는
    것**을 보인다. 본문은 그 단위를 적지 않는다 (3장, 그림 3-7, p.65).[^gough2022]
- **같은 소스가 이 자리의 대가도 적는다** — 게이트웨이가 **사용자 요청 다수의 임계 경로에 있고,
  그 안에서 기대는 기능이 많을수록 관련된 위험이 커지고 장애의 영향도 커진다** (3장,
  p.79).[^gough2022] **속도 제한을 앞으로 미는 일은 공짜가 아니다.**
- 전문은 [API 게이트웨이의 규정과 기능과 배치](../concepts/api-gateway-capabilities-and-deployment.md)와
  [API 게이트웨이의 함정과 선택](../concepts/api-gateway-pitfalls-and-selection.md)이 갖는다.
