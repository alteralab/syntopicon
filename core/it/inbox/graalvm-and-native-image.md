- [이어지는 페이지](#이어지는-페이지)

이 페이지의 질문: **자바가 '언어'와 '핫스팟'이라는 두 경계를 넘으려 할 때 무엇을 만들고 있고,
그것으로 무엇을 얻는가.**

- 문제 인식이 먼저다 — **자바스크립트는 인터넷, 파이썬은 인공 지능, 고 언어는 마이크로서비스
  등의 사례에서 볼 수 있듯이 새로운 시장을 등에 업고 세를 넓혀 가는 언어들이 끊임없이
  등장하고 있다. 모든 분야를 지배할 수 있는 언어는 없다.** 그래서 저자는 **자바가 더 크게
  발전하려면 자바 언어 자체를 잊고 기반 기술 영역으로 돌아가야 할 것**이라고 본다 (1장,
  pp.31–32).[^zhou2024]

## 언어 독립을 향한 그랄VM

- **2018년 4월 오라클 연구소는 그랄VM이라는 새로운 기술을 발표했다.** 구호는 **"어디서든 더
  빠르게 실행한다(Run programs faster anywhere)"** 이며, 저자는 이를 **1995년 자바가 탄생하며
  내건 "한 번 작성하면 어디서든 실행된다"** 와 겹쳐 읽는다 (1장, p.32).[^zhou2024]
- 정체는 이렇다 — **'유니버설 VM' 또는 '폴리글랏 VM'이라고도 하는 그랄VM은 핫스팟 가상 머신
  위에 구축된 크로스 언어(cross-language) 풀 스택 가상 머신**이다 (1장, p.32).[^zhou2024]
  - 지원 범위 — **자바, 코틀린, 스칼라, 그루비 같은 자바 가상 머신 언어들은 물론 LLVM 기반
    컴파일러를 사용하는 C·C++, 러스트 같은 언어들, 그 외 자바스크립트, 루비, 파이썬, R,
    웹어셈블리까지도 지원한다** (1장, p.32).
  - 섞어 쓰는 비용이 없다 — **그랄VM에서는 추가 비용 없이 이 언어들을 혼합해 사용할 수 있다.
    서로 다른 언어들이 데이터를 같은 메모리 공간에서 주고받을 수 있고, 각 언어용으로 작성된
    기존 네이티브 라이브러리들도 사용할 수 있다** (1장, p.32).
- 작동 방식의 핵심은 중간 표현이다 — **각종 언어의 소스 코드나 컴파일된 중간 형식(예: LLVM
  비트코드)을 인터프리터를 통해 그랄VM이 이해할 수 있는 중간 표현(IR)으로 변환하는 식으로
  작동한다** (1장, p.33).[^zhou2024]
  - 그 인터프리터를 만드는 틀이 **트러플(Truffle)** 이다 — **새로운 언어용 인터프리터를 빠르게
    제작할 수 있는 언어 구현 프레임워크**이며, **트러플 위에서 고성능 LLVM 비트코드 인터프리터인
    수롱(Sulong)을 제작했다** (1장, p.33).
- 그래서 위치가 바뀐다 — **좀 더 엄격하게 말하면, 그랄VM은 진정한 의미에서 '물리 머신에
  대응하는 고수준 언어 가상 머신'이다. 물리 머신의 명령어 집합(instruction set)과 같은 역할을
  하면서 머신의 특성과만 관련이 있을 뿐 특정 고수준 언어의 특성과는 관련이 없기 때문**이다
  (1장, p.33).[^zhou2024]
  - 오라클 연구소 연구 책임자 토마스 뷔르팅거의 말이 함께 인용된다 (1장, p.33):[^zhou2024]

    > "그랄VM 1.0 출시로, 우리는 고성능 폴리글랏 가상 머신을 만들 수 있음을 입증했다. 그리고
    > 이 목표를 이루는 가장 좋은 방법은 자바나 마이크로소프트 CLR과 달리 특정 언어에 특화된
    > 바이트코드를 통하지 않는 것이다."

- 성능은 원 런타임을 앞지르기도 한다 — **그랄VM은 입력된 중간 표현을 자동으로 최적화하고
  런타임에 JIT 컴파일까지 해 주기 때문에 때로는 네이티브 컴파일러들보다 실행 성능이 나을 수
  있다.** 예로 **그랄JS는 V8 기반의 Node.js보다 빠르고 그랄Py·TruffleRuby·FastR은 각각
  CPython, 루비 MRI, R 언어보다 빠르다** (1장, p.33).[^zhou2024]
- 자바 쪽에서도 그렇다 — **그랄VM은 애초에 핫스팟을 기반으로 탄생했으며 자바 SE와 완벽하게
  호환되기 때문에 자바 가상 머신으로 활용할 수 있다. 표준 핫스팟과의 차이는 주로 JIT
  컴파일러에서 오며, 현재 실행 효율과 컴파일 품질 모두 표준 핫스팟보다 나은 것으로 평가된다.**
  **르네상스 스위트 벤치마크에서 그랄VM 커뮤니티 버전과 엔터프라이즈 버전이 OpenJDK 17보다
  각각 4%와 30% 정도 앞선다** (1장, pp.33–34).[^zhou2024]
  - 버전 조건: JDK 17 기준의 측정이다 — 벤치마크 대상이 OpenJDK 17과 그랄VM 22.2다.

## 차세대 JIT 컴파일러

- 핫스팟의 실행 메커니즘은 셋이다 — **컴파일 속도가 빠른 대신 최적화를 적게 하는 클라이언트
  컴파일러(C1 컴파일러)와 컴파일 속도는 느리지만 더 많은 최적화를 적용하는 서버 컴파일러(C2
  컴파일러), 여기에 인터프리터까지 포함하여 총 3개의 실행 메커니즘이 협력하여 핫스팟 가상
  머신의 실행 서브시스템을 구성한다** (1장, pp.34–35).[^zhou2024]
- **JDK 10부터는 하나가 더 추가되었다. 바로 그랄 컴파일러다.** **그랄 컴파일러는 C2 컴파일러를
  대체할 목적으로 핫스팟에 도입되었다** (1장, p.35).[^zhou2024]
  - C2를 대체하려는 이유 — **C2의 역사는 클리프 클릭(Cliff Click)의 박사 과정 연구로까지
    거슬러 올라가는데, 현재는 클리프 자신도 더는 지속하기 어렵다고 이야기할 만큼 너무
    복잡해졌다** (1장, p.35).
  - 그랄이 유리한 이유 — **그랄은 자바 언어로 작성되었고, C2와 똑같은 고수준 중간 표현(이하
    HIR)을 사용해서 C2의 이점을 수용하기 쉽다. 등장 시기가 C2보다 20년이나 늦은 만큼 후발
    주자의 이점을 제대로 누리고 있다** (1장, p.35).
  - 비대칭도 명시된다 — **실제로 C2의 최적화 기술을 그랄 컴파일러가 받아들이기는 매우 쉽지만,
    반대로 그랄 컴파일러에서 잘 동작하는 최적화 기술을 C2로 이식하기는 매우 어렵다.** 그
    덕분에 **단 몇 년 만에 C2의 컴파일 품질을 따라잡았고 이제는 대부분 항목에서 앞서 나가기
    시작했다** (1장, p.35).
  - 할 수 있는 최적화도 더 넓다 — **그랄 컴파일러는 부분 탈출 분석(partial escape analysis)처럼
    C2보다 복잡한 최적화도 수행할 수 있고, 맞춤형 가정 등을 추가해 공격적 예측
    최적화(aggressive speculative optimization)를 적용하기에도 더 수월하다** (1장, p.35).
- 위치는 한 번 옮겨졌다가 되돌아오는 중이다 — **JDK 16부터는 개발과 관리 효율을 높이고자 그랄
  컴파일러를 JDK에서 독립시켜 그랄VM으로 터전을 옮겼다.** 그러나 **마침내 그랄 컴파일러가
  OpenJDK로 복귀한다는 소식이 전해졌다 — 그랄VM의 여러 선진 기술 중 JIT 컴파일러와 네이티브
  이미지를 OpenJDK에 우선 반영하기로 한 것**이다 (1장, p.35).[^zhou2024]
  - 버전 조건: JDK 10 이상 JDK 15 이하에서 그랄 컴파일러를 쓰려면
    `-XX:+UnlockExperimentalVMOptions -XX:+UseJVMCICompiler` 매개 변수를 지정한다 (1장, p.35).

## 왜 네이티브인가

- 자바의 구조적 불리함이 아키텍처 변화에서 드러난다 — **애플리케이션 아키텍처의 중심은 거대한
  단일 아키텍처에서 작은 마이크로서비스 아키텍처로 빠르게 옮겨 가고 있는데 자바는 이 추세와 잘
  맞지 않는다** (1장, p.36).[^zhou2024]
  - 이유 — **마이크로서비스 아키텍처에서는 분할된 서비스 각각이 더 이상 수십에서 수백GB의
    메모리를 쓸 일이 없고**, **고가용성 서비스 클러스터를 활용하면 단일 서비스를 24시간 중단
    없이 실행하기 위해 노력할 이유가 줄어든다.** 반면 **자바는 구동 시간이 길고 최고 성능을
    내기까지 예열이 필요하다** (1장, p.36).
  - 서버리스에서 더 심해진다 — **함수는 서비스보다도 크기가 작고 실행 시간이 짧다. 현재 가장
    널리 쓰이는 서버리스 런타임인 AWS 람다는 함수 실행 시간을 최장 15분까지만 허용한다** (1장,
    p.36).
- 자바 쪽 대응 두 가지가 최근 JDK에 들어왔다 (1장, p.36):[^zhou2024]
  - **AppCDS(Application Class Data Sharing)** 는 **로딩한 클래스 정보를 캐시해 두어 다음번 구동
    시간을 줄이는 기술**이며, **초기 CDS는 자바 표준 라이브러리만 지원했지만 JDK 10부터 포함된
    AppCDS는 사용자 프로그램의 코드까지 지원한다.**
  - **엡실론은 메모리를 할당만 해 줄 뿐 회수는 하지 않는 컬렉터로, 간단한 작업을 빠르게 처리한
    후 즉시 종료하는 애플리케이션에 매우 적합하다.** 자세한 사정은
    [적합한 가비지 컬렉터 고르기](../concepts/choosing-a-garbage-collector.md)에 있다.
- 더 급진적인 쪽이 **AOT 컴파일**이다 — **사전(ahead of time)이란 의미의 AOT는 적시(just in
  time)의 상대적인 개념**이며, **컴파일을 미리 해 두면 예열 과정을 건너뛰고 처음부터 네이티브
  코드를 실행할 수 있다는 점이 AOT 컴파일의 최대 강점**이다. **시간 압박 없이 프로그램 전체를
  완벽하게 분석하여 최적화할 수 있다**는 것도 이점이다 (1장, pp.36–37).[^zhou2024]
  - 단점도 명확하다 — **"한 번 작성하면 어디서든 실행된다"라는 자바의 약속을 지킬 수 없다.
    다시 말해 하드웨어와 운영 체제별로 따로 컴파일해 배포해야 한다. 또한 자바의 동적 링크
    특성이 크게 줄어든다** — **컴파일할 코드에 대한 모든 것을 컴파일타임에 알 수 있어야 하고,
    그렇지 않으면 사전 컴파일된 결과를 폐기하고 JIT 컴파일 형태로 되돌아가야 한다** (1장,
    p.37).
  - 유보도 붙는다 — **AOT 컴파일은 런타임 모니터링 정보를 활용할 수 없다. 그래서 시간 압박 없이
    최적화할 수 있더라도 JIT 방식보다 결과가 더 좋다는 보장은 없다** (1장, p.37).
- 첫 시도는 실패로 기록된다 — **JDK 9~15에서는 실험 버전의 AOT 컴파일러 jaotc를 제공했지만
  사용해 본 사람 대부분이 실망했다.** **사람들은 가상 머신 없이 독자적으로 실행되는 네이티브
  코드를 기대했지만 실제로는 JIT 컴파일 기능의 일부를 대체한 것에 불과해서 여전히 핫스팟 가상
  머신에서 실행해야 했다** (1장, p.37).[^zhou2024]

## 서브스트레이트 VM과 네이티브 이미지

- **그랄VM의 한 요소인 서브스트레이트 VM(SubstrateVM)은 사전 컴파일된 네이티브 코드를 핫스팟
  가상 머신 없이 실행하는 기술로 독자적인 예외 처리, 스레드 관리, 메모리 관리, 자바 네이티브
  인터페이스(이하 JNI) 접근 메커니즘 등을 갖춘 극히 작은 런타임 환경**이다 (1장,
  p.37).[^zhou2024]
- 만들어지는 산출물이 **네이티브 이미지**다 — **그랄VM은 서브스트레이트 VM과 사용자 프로그램을
  하나로 묶어 네이티브 이미지를 생성한다. 이때 포인터 분석 기술을 활용하여 사용자 프로그램으로
  부터 도달 가능한 코드만 추려 네이티브 이미지에 담는다. 또한 이 과정에서 초기화까지 수행하여
  최종 실행 파일이 생성되면 초기화된 힙 스냅숏을 저장해 둔다** (1장, p.37).[^zhou2024]
  - 그래서 얻는 것 — **자바 가상 머신이 수행하던 초기화 과정을 건너뛰고 프로그램을 곧바로
    실행하여 초기 구동 시간을 획기적으로 줄였다** (1장, p.37).
  - 전제 조건 — **이 방식이 가능하려면 프로그램이 완결된 형태여야 한다. 컴파일러가 찾을 수 없는
    코드나 클래스 라이브러리를 동적으로 읽어 들일 수 없다는 뜻**이며, **이 조건만 만족한다면
    컴파일타임에 대상 프로그램 전체를 탐색할 수 있기 때문에 정적 분석을 수행하여 모든 가상
    메서드 호출을 직접 호출로 변환할 수 있다** (1장, p.37).
- 메모리도 줄어든다 — **핫스팟 가상 머신은 그 자체로 약 수십MB의 메모리를 사용하는데, 메모리를
  GB 단위로 사용하는 커다란 단일 애플리케이션에서는 문제 될 게 없지만 마이크로서비스에서는
  무시할 수 없는 비용**이다. **오라클이 제공한 데이터에 따르면 서브스트레이트 VM에서 실행되는
  작은 애플리케이션의 경우 핫스팟보다 구동 시간은 최대 50배 빨라지고 메모리 사용량은 최대
  5배까지 줄어든다** (1장, p.38).[^zhou2024]
- 큰 애플리케이션에서도 재 보았다 — **JDK 21용 그랄VM으로 스프링 프레임워크의 공식 예제인
  펫클리닉(Spring Petclinic) 서비스를 네이티브 이미지로 만들어 실험한 결과**다 (1장,
  p.39):[^zhou2024]

  | 지표 | JIT가 탑재된 그랄VM CE | 오라클 그랄VM 네이티브 이미지 | 차이 |
  |---|---|---|---|
  | 메모리 사용(최대 RSS) | 1029MB | 641MB | 38% 감소 |
  | 피크 처리량 | 11066req/s | 11902req/s | 8% 상승 |
  | 단위 메모리당 처리량 | `12488req/(GB*s)` | `18569req/(GB*s)` | 49% 개선 |
  | 테일 지연 시간(P99) | 7.2ms | 5.15ms | 28% 감소 |
  | 구동 시간 | 7090ms | 210ms | 34배 빨라짐 |

  - 버전 조건: JDK 21용 그랄VM 기준의 측정이다.
- 다른 언어에서도 같은 효과가 나온다 — **자바스크립트 애플리케이션을 V8 엔진 기반의 Node.js로
  실행하면 간단한 HelloWorld만 해도 메모리를 약 20MB 소비하지만, 같은 애플리케이션을
  서브스트레이트 VM으로 수행하면 동등한 성능을 내면서도 메모리는 단지 4.2MB면 충분하다**
  (1장, p.39).[^zhou2024]
- 저자의 전망 — **언젠가 자바 언어나 핫스팟 가상 머신이 완벽하게 대체된다면, 현재로서는 가장
  유력한 후보가 바로 그랄VM이다. 이 혁명은 자바 사용자들이 느끼지 못하는 사이에 조용하게
  이루어질 가능성이 크다** (1장, p.34).[^zhou2024] #hypothesis
