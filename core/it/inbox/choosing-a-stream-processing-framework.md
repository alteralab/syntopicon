하나의 질문: **스트림 처리 시스템을 고를 때 무엇을 기준으로 가르는가.**

- 출발점은 프레임워크의 기능 목록이 아니다 — **스트림 처리 프레임워크를 고를 때는 쓰려고
  계획 중인 애플리케이션의 유형을 고려하는 것이 중요하다. 서로 다른 유형의 애플리케이션이
  서로 다른 스트림 처리 해법을 요구**한다 (14장, p.417).[^shapira2021]

## 애플리케이션 유형 넷

- **적재(ingest)** — **목적이 한 시스템에서 다른 시스템으로 데이터를 옮기는 것이되, 대상
  시스템에 맞추기 위한 약간의 수정을 가하는 경우** (14장, p.417).[^shapira2021]
- **저밀리초 반응(low milliseconds actions)** — **거의 즉각적인 응답을 요구하는 모든
  애플리케이션.** 일부 사기 탐지 유스케이스가 여기 든다 (14장, p.417).[^shapira2021]
- **비동기 마이크로서비스** — **더 큰 비즈니스 프로세스를 대신해 단순한 동작 하나를 수행하는
  마이크로서비스**이며 재고 갱신 따위다. **성능 개선을 위해 이벤트를 캐시하는 로컬 상태를
  유지해야 할 수 있다** (14장, p.417).[^shapira2021]
- **준실시간 데이터 분석** — **데이터를 이리저리 잘라 보고 흥미롭고 비즈니스에 유의미한
  통찰을 만들기 위해 복잡한 집계와 조인을 수행하는 스트리밍 애플리케이션** (14장,
  p.417).[^shapira2021]

## 유형별로 무엇을 요구하는가

- **적재 문제를 풀려는 것이라면, 스트림 처리 시스템을 원하는 게 맞는지 아니면 카프카
  커넥트처럼 더 단순한 적재 전용 시스템을 원하는지 다시 생각하라. 스트림 처리 시스템이
  확실히 필요하다면 대상 시스템에 대한 커넥터의 선택지가 좋고 품질도 높은지 확인**해야
  한다 (14장, p.418).[^shapira2021] 그 "더 단순한 시스템" 쪽은
  [카프카 커넥트](../concepts/kafka-connect.md)이고, 애초에 커넥트를 고를 기준은
  [데이터 파이프라인 설계 고려사항](../concepts/kafka-data-pipeline-considerations.md)이 갖고
  있다.
- **저밀리초 반응이 필요한 문제라면 스트림즈라는 선택 자체를 다시 생각해야 한다.
  요청-응답 패턴이 흔히 이 작업에 더 알맞다. 스트림 처리 시스템을 확실히 원한다면
  마이크로배치에 초점을 둔 것이 아니라 이벤트 단위 저지연 모델을 지원하는 것을 골라야**
  한다 (14장, p.418).[^shapira2021] 세 패러다임의 지연 스펙트럼은
  [스트림 처리 패러다임](../concepts/stream-processing-paradigm.md).
- **비동기 마이크로서비스를 만든다면 선택한 메시지 버스(바라건대 카프카)와 잘 통합되고,
  상류 변경을 마이크로서비스 로컬 상태로 쉽게 전달하는 변경 캡처 능력이 있으며, 캐시나
  마이크로서비스 데이터의 구체화 뷰 노릇을 할 수 있는 로컬 저장소를 잘 지원하는 스트림
  처리 시스템이 필요**하다 (14장, p.418).[^shapira2021] 그 변경 캡처와 구체화 뷰가
  무엇인지는 [스트림-테이블 이중성과 조인](../concepts/stream-table-duality.md), 아키텍처
  쪽 맥락은 [마이크로서비스와 서버리스](../concepts/microservices-and-serverless.md).
- **복잡한 분석 엔진을 만든다면 역시 로컬 저장소 지원이 훌륭한 스트림 처리 시스템이
  필요하되, 이번에는 로컬 캐시와 구체화 뷰의 유지를 위해서가 아니라 그러지 않으면 구현이
  어려운 고급 집계·윈도우·조인을 지원하기 위해서다. API는 커스텀 집계, 윈도우 연산, 여러
  조인 유형을 지원해야** 한다 (14장, p.418).[^shapira2021]

## 유형과 무관하게 따지는 것

- **유스케이스별 고려에 더해 감안해야 할 전역 고려사항이 몇 가지 있다** (14장,
  p.419):[^shapira2021]
  - **시스템의 운영성** — **프로덕션에 배포하기 쉬운가? 모니터링과 문제 해결이 쉬운가?
    필요할 때 규모를 키우고 줄이기 쉬운가? 기존 인프라와 잘 통합되는가? 실수가 있어
    데이터를 재처리해야 하면 어떻게 되는가?** 마지막 항목이 가리키는 절차는
    [스트림 처리 설계 패턴](../concepts/stream-processing-design-patterns.md)의 재처리다.
  - **API의 사용성과 디버깅의 용이함** — **같은 프레임워크의 서로 다른 버전 사이에서도
    고품질 애플리케이션을 쓰는 데 걸리는 시간이 자릿수만큼 차이 나는 것을 봤다. 개발 시간과
    출시까지의 시간이 중요하므로 나를 효율적으로 만들어 주는 시스템을 골라야 한다.**
  - **어려운 일을 쉽게 만드는가** — **거의 모든 시스템이 고급 윈도우 집계를 하고 로컬
    저장소를 유지할 수 있다고 주장하지만, 문제는 그것을 쉽게 만들어 주는가다. 규모와 복구에
    관한 지저분한 세부를 시스템이 처리하는가, 아니면 새는 추상을 제공하고 대부분의 뒤처리를
    떠넘기는가. 시스템이 깨끗한 API와 추상을 더 많이 노출하고 지저분한 세부를 스스로 다룰수록
    개발자는 더 생산적이다.**
  - **커뮤니티** — **고려 중인 스트림 처리 애플리케이션 대부분이 오픈소스일 것이고, 활발하고
    생동감 있는 커뮤니티를 대체할 것은 없다. 좋은 커뮤니티는 새롭고 신나는 기능을 정기적으로
    얻고, 품질이 상대적으로 좋고(나쁜 소프트웨어에서 일하고 싶은 사람은 없다), 버그가 빨리
    고쳐지고, 사용자 질문이 제때 답을 얻는다는 뜻이다. 또한 이상한 오류를 만나 검색했을 때
    다른 사람들이 이 시스템을 쓰며 같은 문제를 겪고 있으므로 정보를 찾을 수 있다는 뜻이기도
    하다.**
