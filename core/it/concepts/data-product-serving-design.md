## 하나의 질문

**데이터 프로덕트가 다양한 소비자에게 데이터를 내줄 때, 그 출력 표면이 반드시 가져야 하는
성질은 무엇인가.**

[포트](../concepts/data-product-ports-and-sidecar.md)가 출력 데이터 포트라는 이름과 자리를
정하고 나면, 12장은 그 포트가 **무엇을 보장해야 하는가**로 들어간다.

- 12장이 다루는 셋의 배치 — **데이터 프로덕트의 일차적 일은 자기 입력 데이터 포트를 써서
  상류 소스에서 데이터를 소비하고, 그것을 변환하고, 그 결과를 자기 출력 데이터 포트를 통해
  영구히 접근 가능한 데이터로 서빙하는 것이다** (12장, p.201).[^dehghani2022] 저자는 셋 중
  **데이터 메시적 접근에 가장 고유한 성질을 가진 것**부터 시작한다고 밝히고 서빙을 먼저 놓는다
  (12장, p.201).[^dehghani2022]
- 계약이 먼저다 — **데이터 프로덕트는 도메인 지향 데이터를 다양한 분석 소비자 집합에 서빙한다.
  9장에서 도입한 출력 데이터 포트(인터페이스)를 통해서다. 출력 데이터 포트는 **명시적으로
  정의된 계약(explicitly defined contracts)**과 API를 갖는다** (12장, p.201).[^dehghani2022]

## 데이터 사용자의 세 요구

- 요구가 설계 제약을 낳는다는 순서가 명시된다 — **데이터 사용자가 이끄는 요구사항이 데이터
  프로덕트가 데이터를 서빙하는 방식에 일련의 설계 고려사항을 부과한다** (12장,
  p.203).[^dehghani2022]
- **① 분석 데이터 사용자는 다양한 프로필을 갖는다** — **데이터 사용자 — 데이터에 접근하고
  읽는 클라이언트 — 는 넓은 스펙트럼의 페르소나와 애플리케이션 타입에 걸쳐 있다: 데이터 분석가·
  데이터 과학자·데이터 주도 애플리케이션 개발자 같은 사람, 그리고 리포트·시각화·통계 모델·기계
  학습 모델 같은 시스템이다. 3장을 회상하면, 데이터 프로덕트는 그런 다양한 페르소나에게
  네이티브하게 느껴지는 방식으로 자기 데이터를 서빙한다. 우리는 이 기준선 사용성 특성을
  네이티브하게 접근 가능(natively accessible)이라 불렀다** (12장, p.203).[^dehghani2022]
  - 설계 함의 — **이 요구의 설계 함의는 데이터를 다중 양식 접근(multimodal access)으로
    서빙하는 것이다 — 같은 데이터 의미론을 서로 다른 형식과 접근 양식으로 서빙하는 것이다**
    (12장, p.203).[^dehghani2022]
- **② 분석 데이터 사용자는 종단(longitudinal) 데이터를 필요로 한다** — **메시는 데이터의 전역
  상태를 분석 사용 사례를 위해 온전히 종단적으로 유지한다. 가장 중요하게는 **메시 바깥의**
  데이터 레이크·웨어하우스나 어떤 외부 시스템도 없이 전역 상태를 유지한다** (12장,
  p.203).[^dehghani2022]
  - 그 결과 — **이 끊임없이 변하는 데이터의 전역 상태는 연결된 데이터 프로덕트들의 그래프에
    의해 저장·유지되며, 다른 어떤 아키텍처 요소도 아니다. 이것이 아키텍처의 탈중앙화가 뜻하는
    바다** (12장, p.203).[^dehghani2022] [데이터 레이크](../concepts/data-lake.md)와
    [전사 데이터 웨어하우스](../concepts/enterprise-data-warehouse.md)를 "전역 상태의 보관소"
    자리에서 제거하는 문장이다.
  - 왜 시간이 필요한가 — **회고적이든 미래 지향적이든 통찰은 시간의 경과를 고려할 때 가장
    강력하다. 시간에 따른 연속적 데이터 변화에 접근할 수 있을 때에만 우리는 추세를 정식화하고·
    예측하고·여러 도메인에 걸친 서로 다른 이벤트 사이의 상관을 발견할 수 있다. 데이터 메시는
    데이터를 제시할 때도 질의할 때도 시간을 **늘 존재하는 파라미터(ever-present parameter)**로
    가정한다** (12장, p.203).[^dehghani2022]
  - 설계 함의 — **각 데이터 퀀텀이 바이템포럴 데이터를 서빙하는 것** (12장,
    p.203).[^dehghani2022]
- **③ 분석 데이터 사용자는 한 시점에서 여러 도메인의 일관된 뷰를 필요로 한다** — **분석 사용
  사례의 대다수는 여러 데이터 프로덕트의 데이터를 처리한다. 그런 사용 사례는 여러 데이터
  프로덕트를 **일관된 시점(a consistent point in time)**에서 상관시킨다. 예컨대 Daff가
  2021-07-01에 다음 달 구독자 증가를 예측하는 기계 학습 모델을 훈련할 때, 그것은 지난 3년의
  데이터 중 2021-07-01에 여러 데이터 프로덕트에 의해 **알려지고 처리된** 것에 근거해 그렇게
  한다** (12장, p.203).[^dehghani2022]
  - 재현성의 요구 — **2021-07-21에 처리된 이 버전의 증가 모델의 재현 가능성을 뒷받침하기 위해,
    메시는 2021-07-21에 여러 데이터 프로덕트에 걸친 데이터의 **변경 불가능한 상태**를 유지한다**
    (12장, p.203).[^dehghani2022]
  - 설계 함의가 셋을 한꺼번에 부른다 — **여러 데이터 프로덕트에 걸쳐 시점 일관된 데이터를
    제공하는 것은, 재현 가능성을 위한 데이터의 버저닝과 결합되어, 데이터 서빙에 여러 설계
    고려사항을 도입한다: 바이템포럴리티·불변성·읽기 전용 접근이다** (12장,
    p.203).[^dehghani2022]

## 성질 ① 다중 양식 데이터

- 일과 제약이 한 문장에 들어 있다 — **데이터 프로덕트의 일은 특정 도메인의 분석 데이터를
  구체적이고 고유한 도메인 의미론(semantic)으로 서빙하는 것이다. 그러나 데이터 프로덕트가
  다양한 소비자에게 네이티브하게 서빙하려면, **같은 도메인 의미론을 서로 다른 구문(syntax)으로**
  공유해야 한다. 의미론은 열 지향 파일로, 관계형 데이터베이스 테이블로, 이벤트로, 또는 다른
  형식으로 서빙될 수 있다. 같은 의미론이 데이터 소비자의 경험을 타협하지 않고 서빙된다.
  리포트를 쓰는 사람은 데이터를 관계형 테이블로 소비한다. 기계 학습 모델을 훈련하는 사람은
  데이터를 열 지향 파일로 소비하고, 실시간 앱 개발자는 이벤트를 소비한다** (12장,
  p.204).[^dehghani2022]
- 저자의 비유 — **나는 개인적으로 분석 데이터의 성질을 공간(space)과 시간(time(s))의 차원으로
  시각화하는 것이 도움이 된다고 본다. 나는 공간 차원을 써서 데이터의 서로 다른 구문적
  구체화(syntactic materialization), 곧 데이터의 형식을 나타낸다. 어떤 데이터 프로덕트든 자기
  데이터를 여러 형식으로, 곧 다중 양식(multimodal) 형태로 제시할 수 있다** (12장,
  p.204).[^dehghani2022] 열거되는 것은 넷이다 (12장, p.204):[^dehghani2022]
  - **반구조화 파일 — 예: 열 지향 파일**
  - **엔티티 관계 — 예: 관계형 테이블**
  - **그래프 — 예: 속성 그래프**
  - **이벤트**
- 도판의 예 — **play events** 데이터 프로덕트가 세 접근 양식으로 같은 데이터를 낸다:
  **"play events" 토픽 구독(청취자의 로그인·재생·중지 같은 상태 변화 포착), 같은 play 이벤트에
  대한 SQL 질의(이벤트 속성의 행을 가진 테이블 위), 그리고 열 지향 객체 파일(모든 이벤트의
  각 속성마다 하나의 파일)** (12장, pp.204–205, 그림 12-2).[^dehghani2022]
  - 각 양식이 다른 페르소나를 만난다 — **오류 이벤트를 지켜보며 플레이어 품질을 개선하는
    데이터 집약 앱 개발자, 상위 플레이어 사용 패턴의 일별 리포트를 만드는 데이터 분석가(동기
    SQL 접근 모델), 재생 패턴 분류를 발견하는 ML 모델을 훈련하는 데이터 과학자(파일 접근
    양식)다. 이 모두가 같은 데이터 프로덕트 play events가 자기 개별 출력 데이터 포트를 통해
    가능하게 한다** (12장, p.205).[^dehghani2022]
  - 각주 — **하나의 데이터 토폴로지가 여러 접근 양식을 가질 수 있다. 예컨대 이벤트 스트림으로
    형식화된 데이터는 SQL과 발행/구독 접근 양식 양쪽에서 쓰일 수 있다** (12장, p.205, 각주
    1).[^dehghani2022]
- 저자가 이 성질의 2022년 저술 시점 비용을 정직하게 적는다 — **그 시점에 다중 양식 접근을 지원하는 복잡성은
  데이터를 그 기저 인코딩·형식에 불가지하게 의미론적으로 제시하고 질의하는 고차·추상 API의
  부재가 낳은 증상이다** (12장, p.205).[^dehghani2022] #hypothesis — 곧 이 복잡성은 본질이
  아니라 도구의 공백이라는 주장이고, 반증 조건은 그런 추상 API가 나왔을 때 다중 양식 지원
  비용이 실제로 떨어지는가이다.

## 의미론이 일급, 형식과 접근 양식이 이급

- 접근 순서가 규정된다 — **데이터 사용자가 데이터 프로덕트에 접근할 때, 최상위 데이터 프로덕트
  발견 API를 써서 먼저 데이터 프로덕트의 의미론 — 그 제품이 서빙하는 도메인 정보, 예컨대
  **podcasts**, **podcast listeners** 등 — 을 알게 되고, 그 다음 데이터에 대한 특정 접근 양식을
  위해 데이터 프로덕트의 출력 API 중 하나에 접근한다. 데이터가 어떻게 서빙되는지는 기저 (물리)
  기술에 달렸다: 이벤트 로그 구독, 분산 열 지향 파일 읽기, 관계형 테이블에 대한 SQL 질의
  실행이다** (12장, p.204).[^dehghani2022]
- **그리고 이것이 역전이라고 저자가 명시한다** — **도메인 지향 의미론이 최상위 관심사이고,
  형식과 접근 양식은 이급(second-class) 관심사다. 이것은 기존 아키텍처에 대한 역모델(inverse
  model)이다. 기존에는 스토리지와 인코딩 기술이 데이터가 어떻게 조직되는지를 먼저 지시하고 그
  다음 서빙된다** (12장, p.204).[^dehghani2022]
  - [스키마 온 리드와 스키마 온 라이트](../concepts/schema-on-read-and-schema-on-write.md)의
    갈림이 여기서 한 층 위로 올라간다 — 저자가 뒤집는 것은 읽기냐 쓰기냐가 아니라 **의미론과
    물리 형식 중 무엇이 먼저 결정되는가**다.
  - [시맨틱·메트릭 레이어](../concepts/semantic-and-metrics-layers.md)가 의미론을 웨어하우스
    **위에 얹는 별도 층**으로 두는 서술과 자리가 갈린다 — 저자는 그것을 데이터 프로덕트의
    **코어**로 안쪽에 넣는다(아래 표 12-1의 "코어 데이터 의미론").

## 성질 ② 불변 데이터

- 절 머리의 제사 — **No man can cross the same river twice. — Heraclitus** (12장,
  p.206).[^dehghani2022]
- 정의 — **불변 데이터는 한 번 만들어지면 바뀌지 않는다. 데이터 프로덕트는 데이터 조각이 한 번
  처리되어 데이터 사용자에게 가용해지면 그 특정 데이터 조각은 바뀌지 않는 방식으로 데이터를
  서빙한다. 그것은 삭제되거나 갱신될 수 없다** (12장, p.206).[^dehghani2022]
- 계열이 밝혀진다 — **데이터를 바꾸는 것은 흔히 복잡성과 오류로 이어지며, 이는 경험 있는
  프로그래머라면 아는 사실이다. 함수형 프로그래밍에 상당한 관심이 있는 이유가 이것이고, 그것은
  데이터가 결코 바뀌지 않는다는 것을 핵심 공리로 삼는다** (12장, p.206).[^dehghani2022]
- 분석에서 특히 중요한 이유가 재현성이다 — **불변 데이터가 있으면 데이터 사용자는 분석을 반복
  가능한 방식으로 재실행할 수 있다. 특정 시점 데이터셋에 대해 모델을 재훈련하거나 리포트를
  재생성하면 같은 반복 가능한 결과가 나온다** (12장, p.206).[^dehghani2022]
- 왜 재현성이 필요한가 — **결과가 종종 분석가가 더 파고들어야 할 놀라운 관찰을 낳기 때문이다.
  쓰고 있는 데이터가 바뀐다면 놀라운 결과를 재현하지 못할 수 있고, 그것이 데이터 때문인지
  프로그래밍 오류 때문인지 의아해할 수 있다. 분석에 버그가 있다면, 같은 코드를 반복 실행해도
  같은 답을 얻지 못하는 불안정한 데이터 소스로 작업할 때 추적이 훨씬 어렵다** (12장,
  p.206).[^dehghani2022]
- 데이터 메시에서 이 문제가 더 나빠지는 이유 — **가변 데이터의 혼란과 복잡성은 데이터 메시에서
  더 나빠진다. 소스 데이터가 여러 데이터 프로덕트에 쓰일 수 있고, 여러 데이터 프로덕트가 특정
  분석의 소스가 될 수 있으며, 그 각각이 사업 상태에 대한 더 큰 이해에 기여하는 진실의 한 조각을
  갖기 때문이다. 데이터 메시의 분산적 성질은 데이터 사용자에게 (1) 시점(point-in-time) 데이터
  조각에 대해 여러 데이터 프로덕트 사이에 일관성이 있고, (2) 한 시점의 데이터를 읽고 나면 그
  데이터가 바뀌지 않으므로 읽기와 처리를 신뢰성 있게 반복할 수 있다는 확신을 주기 위해
  불변성을 요구한다** (12장, p.206).[^dehghani2022]
- 튜플의 모양이 예로 나온다 — **listener demographics**는 `{listener_id: '123', location:
  'San Francisco', connection_time: '2021-08-12T14:23:00', processing_time:
  '2021-08-13T01:00'}` 같은 튜플로 데이터를 공유한다. **각 정보 조각은 두 개의 시간 가변
  식별 필드를 갖는다. 이 튜플이 한 번 처리되어 데이터 사용자에게 가용해지면 결코 바뀌지 않는다.
  물론 같은 청취자가 다음 날 다른 위치에서 콘텐츠를 들을 수 있고, 그것은 새 데이터 엔티티
  `{listener_id: '123', location: 'New York', connection_time: '2021-08-13T10:00',
  processing_time: '2021-08-14T01:00'}`의 추가로 자신을 드러낸다. 이것들은 두 개의 서로 다른
  시간 조각이지만 여전히 청취자의 새 위치라는 갱신을 전달한다** (12장,
  p.208).[^dehghani2022]
- 불변성이 사 오는 것 — **더 일반적으로, 데이터의 불변성은 우발적 복잡성의 기회를 줄인다.
  분산된 소비자 메시에 걸친 공유 상태 갱신의 부작용을 다루는 복잡성과, 분산 트랜잭션이라는
  다루기 힘든 컴퓨터 과학 문제를 푸는 복잡성이다. 메시가 이미 소비한 데이터가 계속 바뀌는 것을,
  또는 같은 읽기를 재생하면 다른 결과가 나오는 것을 허용한다면 메시의 각 하류 데이터 독자
  코드에 들어갈 복잡성을 상상해 보라** (12장, p.208).[^dehghani2022]
  - [2단계 커밋](../concepts/two-phase-commit.md)을 **풀지 않고 회피하는** 선택이라는
    점이 요점이다 — 같은 회피가
    [상태·스트림·불변성](../concepts/state-streams-and-immutability.md)과
    [조정 회피](../concepts/coordination-avoidance.md)에 있다.
- 그리고 무엇을 대신 얻는가 — **불변성은 변화를 위한 설계와, 새 처리 시간과 그 불변 상태의
  전파를 통해 메시의 **최종적 일관성(eventual consistency)**을 유지하는 것의 또 다른 핵심
  조력자다** (12장, p.208).[^dehghani2022] 각주가 그 뜻을 좁힌다 — **최종적 일관성은 데이터
  프로덕트의 새로 처리된 데이터가 하류 소비자에게 전파되고 나면 어느 시점에 메시가 일관되게
  된다는 뜻이다** (12장, p.208, 각주 2).[^dehghani2022]
  - [일관성 모델](../concepts/consistency-models.md)의 최종적 일관성이 여기서 **메시 전체의
    설계 목표**로 채택된다 — 강한 일관성은 시도되지 않는다.

## 불일치 상관이라는 실패 — 죽음의 다이아몬드

- 저자가 드는 실패 시나리오 (12장, pp.206–207, 그림 12-3):[^dehghani2022] **listener
  demographics**가 일별로 청취자의 지리적 인구통계를 제공하고, 그 하류에 **artists regional
  popularity**와 **regional market size** 둘이 있으며, 그 둘이 다시 **regional marketing**의
  소스가 된다.
- 무엇이 깨지는가 — **이 데이터 프로덕트들은 각자 데이터를 처리하고 서빙하는 자기 박자를 갖는다.
  따라서 그것들 전부가 같은 시각에 데이터를 갱신한다고 보장할 방법이 없다. 이것은 **죽음의
  다이아몬드(deadly diamond)**로 이어질 수 있다. **listener demographics**가 **regional
  marketing**이 분석을 돌리는 시각에 데이터를 갱신하면, listener demographics는 갱신 전 데이터를,
  regional market size는 갱신 후 데이터를 서빙할 수 있으므로 불일치 데이터를 소비할 수 있다.
  더 나쁜 것은, **regional marketing**은 이 불일치를 알지조차 못한다** (12장,
  p.207).[^dehghani2022]
- 해법의 형태 — **데이터 메시는 갱신된 데이터가 데이터 사용자에게 탐지되지 않고 지나갈 가능성을
  제거함으로써 이 문제를 다룬다. 데이터에 대한 변경은 늘 시간 가변 속성을 식별하는 새 데이터
  조각으로 제시되며, 그래서 데이터 사용자는 각각 다른 데이터 프로덕트에서 온 불일치 데이터
  조각들을 상관시키게 되는 일이 결코 없다. 이를 하는 가장 일반적인 방법은
  [바이템포럴 데이터](../concepts/bitemporal-data.md)를 쓰는 것이다** (12장,
  p.207).[^dehghani2022]
  - **문제를 조정으로 풀지 않고 표현으로 푼다**는 점이 요점이다 — 다이아몬드 의존은 그대로
    두고, 어느 시점의 데이터를 봤는지를 데이터 자신이 들고 다니게 한다.

## 성질 ③ 바이템포럴 데이터

- 이 성질은 분량이 커서 별도 페이지가 받는다 — [바이템포럴 데이터](../concepts/bitemporal-data.md).
  요지만: **모든 데이터 조각이 실제 시간(actual time)과 처리 시간(processing time) 두 타임스탬프를
  기록**하고, 과거의 수정은 새 처리 시간의 **철회(retraction)**로 표현되며, 서빙 API는 그 두
  시간을 파라미터로 받는 함수가 된다 (12장, pp.208–214).[^dehghani2022]

## 성질 ④ 읽기 전용 접근

- 저자가 단일 진실 원천을 다시 기각한다 — **다른 분석 데이터 관리 패러다임과 달리 데이터 메시는
  신화적인 **단일 진실 원천(single source of truth)**이라는 개념을 받아들이지 않는다. 모든 데이터
  프로덕트는 자기 능력껏 현실의 진실한 **부분** — 특정 도메인에 대한 — 을, 곧 **진실의 단일
  조각(a single slice of truth)**을 제공한다** (12장, p.216).[^dehghani2022]
  - [도메인 소유권 원칙](../concepts/domain-ownership-principle.md)의 "단일 진실 기각"이 서빙
    설계에서 다시 진술되는 자리다. [마스터 데이터 관리](../concepts/master-data-management.md)의
    골든 레코드 처방과 정면으로 갈린다 — 대립은 처방이고, 조건은 **조직이 도메인 경계를 데이터
    소유 경계로 받아들이는가**이다.
- 무결성이 유지되는 방식 — **데이터는 한 데이터 프로덕트에서 읽히고, 변형·변환되고, 다음
  프로덕트에 의해 서빙될 수 있다. 메시는 변화를 상류 데이터 프로덕트에서 하류 소비자로
  **바이템포럴 불변 데이터의 추가(appends)**로 전파함으로써 자동으로 자기 무결성을 유지한다.
  그렇게 해서 메시는 새 데이터가 그래프를 통해 전파되는 동안 최종적 일관성 상태를 유지한다**
  (12장, p.216).[^dehghani2022]

## 갱신 함수가 없다 — 그리고 잊힐 권리의 예외

- 결론 — **지금쯤 메시나 개별 데이터 프로덕트가 직접적인 **갱신(update) 함수**를 제시하지 않는다는
  것이 자명해 보일 것이다. 갱신은 데이터 프로덕트가 자기 입력을 처리한 간접적 결과다. 데이터
  프로덕트에 대한 변경은 새로 처리된 데이터의 형태로, 오직 데이터 프로덕트의 변환 코드에 의해서만
  수행된다. 이것이 불변성을 보장하고 또한 메시의 최종적 일관성을 유지한다** (12장,
  p.216).[^dehghani2022]
- 예외는 하나이고, 그것은 출력 포트가 아니라 제어 포트로 간다 — **그러나 GDPR 같은 규정에 따라
  **잊힐 권리(right to be forgotten)**를 실행하는 전역 거버넌스 관리 기능처럼 데이터를 바꾸는
  경우가 있다** (12장, p.216).[^dehghani2022]
- 그 구현이 명시된다 — **이것들을 메시 경험 플레인이 모든 데이터 프로덕트의 제어 포트에서
  촉발하는 특정한 관리 기능으로 생각할 수 있다. 그 명령을 실행하는데, 이 경우는 크립토
  슈레딩(crypto shredding)이다. 데이터 프로덕트는 늘 사용자 정보를 암호화해 인코딩한다. 플랫폼에
  사는 암호화 키를 파괴함으로써 — 데이터 프로덕트가 아니라 — 사용자 정보는 본질적으로 읽을 수
  없게 된다** (12장, p.216).[^dehghani2022]
- 그리고 규칙이 한 줄로 못 박힌다 — **이미 처리된 데이터를 갱신해야 하는 다른 특수 경우 연산이
  있다면, 그 연산은 출력 포트의 함수가 아니라 **전역 제어 포트(global control port) 함수**로
  구현된다. **출력 포트는 데이터 사용자가 데이터를 읽기만 하도록 유지하라**** (12장,
  p.216).[^dehghani2022]
  - [데이터 프로덕트의 포트와 사이드카](../concepts/data-product-ports-and-sidecar.md)의 제어
    포트 "특권 연산"이 서빙 설계 쪽에서 왜 필요했는지가 여기서 완결된다.
  - 키 파기로 삭제를 대신하는 기법은
    [위험 자산으로서의 데이터](../concepts/data-as-a-hazardous-asset.md)와
    [결정권으로서의 프라이버시](../concepts/privacy-as-a-decision-right.md) 계열의 같은 수법이다.

## 서빙 설계의 세 구성 요소

- 논리 아키텍처 — **그림 12-6은 있음직한 논리 아키텍처를 보여 준다. 데이터 프로덕트가 자기
  도메인의 코어 표현을 소유·유지하고 출력 데이터 포트 어댑터라는 개념을 써서 여러 공간
  양식(spatial modalities)으로 서빙한다. 각 포트는 늘 바이템포럴·불변·읽기 전용 양식으로
  데이터를 제공한다. 데이터 보존 기간은 데이터 프로덕트의 정책에 달렸다. 여러 관측(처리
  시간)에 대해 데이터를 보유하고 접근 가능하게 만들 수도, 최신 것만일 수도, 그 사이 어딘가일
  수도 있다** (12장, p.216).[^dehghani2022]
- 표 12-1이 세 구성 요소를 정의한다 (12장, p.217):[^dehghani2022]

| 구성 요소 | 저자의 정의 |
|---|---|
| 출력 데이터 포트(output data port) | 특정 데이터 공간 형식(구문)에 대한 특정 접근 양식에 따라 데이터를 서빙하는 인터페이스(API). 그 구현은 특정 물리 기술에 대한 접근을 재유도하는 API일 수 있다 — 예: 웨어하우스 스토리지의 바이템포럴 테이블, 레이크 스토리지의 파일, 이벤트 로그의 토픽 |
| 출력 (데이터) 포트 어댑터(output port adapter) | 특정 출력 포트를 위해 데이터를 제시하는 책임을 지는 코드. 구현은 단순히 데이터를 특정 구문으로 저장하는 데이터 프로덕트 변환 코드의 한 단계일 수도, 읽기 시점에 코어 데이터를 여러 접근 양식으로 적응시키는 런타임 게이트웨이만큼 정교할 수도 있다 |
| 코어 데이터 의미론(core data semantic) | 데이터 의미론의 표현 — 접근 양식이나 그 공간적 구문에 불가지 |
- 이 세 구성 요소가 위 "의미론이 일급"의 구조적 실현이다: **코어 하나 + 어댑터 N + 포트 N**.
  어댑터의 구현 폭이 빌드 시점(미리 구체화)에서 런타임(읽기 시 변환)까지 열려 있다는 점이
  성능·비용 판단의 자리다.
