하나의 질문: **네트워크 너머로 노출하는 API를 어떻게 정의하고, 그것을 어떻게 바꿔 나가는가.**

## 서비스란 무엇인가

- 기본 배치 — **네트워크로 통신해야 하는 프로세스가 있을 때 그 통신을 몇 가지 방식으로 배치할 수
  있다. 가장 흔한 배치는 클라이언트와 서버라는 두 역할을 두는 것이다. 서버는 네트워크로 API를
  노출하고 클라이언트는 서버에 연결해 그 API에 요청을 보낼 수 있다. 서버가 노출하는 API를
  서비스(service)라 한다** (5장, p.180).[^kleppmann2026]
- 웹이 그 사례다 — **웹이 이렇게 작동한다: 클라이언트(웹 브라우저)가 웹 서버에 요청을 보내고, HTML·
  CSS·자바스크립트·이미지 등을 내려받는 GET 요청과 서버에 데이터를 제출하는 POST 요청을 한다. API는
  표준화된 프로토콜과 데이터 형식의 집합(HTTP·URL·SSL/TLS·HTML 등)으로 이뤄진다. 웹 브라우저와 웹
  서버와 웹사이트 저자가 대체로 이 표준에 동의하기 때문에 어떤 웹 브라우저로도 어떤 웹사이트든
  접근할 수 있다(적어도 이론상으로는)** (5장, p.180).[^kleppmann2026]
- 브라우저만 클라이언트인 것이 아니다 — **모바일 기기와 데스크톱 컴퓨터에서 도는 네이티브 앱이 흔히
  서버와 통신하고, 웹 브라우저 안에서 도는 클라이언트 쪽 자바스크립트 애플리케이션도 HTTP 요청을 할
  수 있다. 이 경우 서버의 응답은 보통 사람에게 표시할 HTML이 아니라 클라이언트 쪽 애플리케이션 코드가
  더 처리하기 편한 인코딩의 데이터(대개 JSON)다. HTTP가 전송 프로토콜로 쓰이더라도 그 위에 구현된
  API는 애플리케이션별이고, 클라이언트와 서버가 그 API의 세부에 합의해야 한다** (5장,
  p.180).[^kleppmann2026]

## 서비스와 데이터베이스의 차이

- 닮은 곳과 갈리는 곳 — **어떤 면에서 서비스는 데이터베이스와 비슷하다: 보통 클라이언트가 데이터를
  제출하고 질의할 수 있게 한다. 그러나 데이터베이스가 질의 언어로 임의의 질의를 허용하는 반면, 서비스는
  서비스의 업무 로직(애플리케이션 코드)이 미리 정한 입력과 출력만 허용하는 애플리케이션별 API를
  노출한다** (5장, p.180).[^kleppmann2026]
- 그 제약이 값어치다 — **이 제약은 어느 정도의 캡슐화를 제공한다: 서비스는 클라이언트가 무엇을 할 수
  있고 없는지에 세밀한 제약을 부과할 수 있다** (5장, p.180).[^kleppmann2026]
- 설계 목표 — **서비스 지향/마이크로서비스 아키텍처의 핵심 설계 목표는 서비스를 독립적으로 배포
  가능하고 진화 가능하게 만듦으로써 애플리케이션을 바꾸고 유지보수하기 쉽게 만드는 것이다. 흔한
  원칙은 각 서비스가 한 팀에 의해 소유돼야 하고 그 팀이 다른 팀과 조율할 필요 없이 서비스의 새
  버전을 자주 릴리스할 수 있어야 한다는 것이다** (5장, p.180).[^kleppmann2026]
- 그래서 인코딩에 요구가 생긴다 — **따라서 서버와 클라이언트의 옛 버전과 새 버전이 동시에 돌고 있을
  것을 예상해야 하며, 그래서 서버와 클라이언트가 쓰는 데이터 인코딩은 서비스 API의 버전들에 걸쳐
  호환돼야 한다. API가 호환으로 남는 한 팀은 자기 시스템을 원하는 방식으로 수정할 자유가 있다. 이
  성질은 개발자가 데이터·서비스·심지어 시스템 전체의 내부 마이그레이션을 하기 훨씬 쉽게 만든다**
  (5장, pp.180–181).[^kleppmann2026]

## 웹 서비스가 쓰이는 세 맥락

- 이름의 정의와 오해 — **HTTP가 서비스와 이야기하는 밑에 깔린 프로토콜로 쓰이면 그것을 웹
  서비스(web service)라 한다. 이 용어는 아마 약간 잘못된 이름인데, 웹 서비스가 웹에서만이 아니라 여러
  맥락에서 쓰이기 때문이다** (5장, p.181).[^kleppmann2026]
- 세 맥락 (5장, p.181):[^kleppmann2026]
  - **사용자 기기에서 도는 클라이언트 애플리케이션(모바일 기기의 네이티브 앱이나 브라우저의
    자바스크립트 웹 앱 등)이 HTTP로 서비스에 요청하는 것. 이 요청은 보통 공개 인터넷을 지난다.**
  - **한 서비스가 같은 조직이 소유한 다른 서비스에 요청하는 것. 흔히 같은 사설 네트워크 안에 있으며
    서비스 지향/마이크로서비스 아키텍처의 일부다.**
  - **한 서비스가 다른 조직이 소유한 서비스에 요청하는 것. 보통 인터넷을 거친다. 이는 조직들의
    백엔드 시스템 사이 데이터 교환에 쓰인다. 이 범주에는 신용카드 처리 시스템이나 사용자 데이터에
    대한 공유 접근을 위한 OAuth처럼 온라인 서비스가 제공하는 공개 API가 포함된다.**

## REST와 IDL

- **가장 인기 있는 서비스 설계 철학은 REST이며 HTTP의 원칙 위에 세워진다. REST는 단순한 데이터
  형식, 리소스 식별에 URL 쓰기, 캐시 제어·인증·콘텐츠 타입 협상에 HTTP 기능 쓰기를 강조한다. REST의
  원칙에 따라 설계된 API를 RESTful하다고 한다** (5장, p.181).[^kleppmann2026]
- 그것만으로는 부족하다 — **웹 서비스 API를 호출해야 하는 코드는 어떤 HTTP 엔드포인트에 질의할지,
  어떤 데이터 형식을 보내고 응답으로 기대할지를 알아야 한다. 서비스가 RESTful 설계 원칙을 채택하더라도
  클라이언트는 어떻게든 이 세부를 알아내야 한다** (5장, p.181).[^kleppmann2026]
- 그래서 IDL이 온다 — **서비스 개발자는 흔히 IDL을 써서 서비스의 API 엔드포인트와 데이터 모델을
  정의·문서화하고 시간에 걸쳐 진화시킨다. 다른 개발자는 그 서비스 정의를 써서 서비스에 어떻게 질의할지
  정할 수 있다. 가장 인기 있는 서비스 IDL 둘은 JSON을 주고받는 웹 서비스에 쓰이는 OpenAPI(Swagger로도
  알려져 있다)와 gRPC 서비스에 쓰이는 프로토콜 버퍼다** (5장, p.181).[^kleppmann2026]
- **개발자는 보통 OpenAPI 서비스 정의를 JSON이나 YAML로 쓴다. 그 서비스 정의는 개발자가 서비스
  엔드포인트·문서·버전·데이터 모델 등을 정의할 수 있게 한다. 프로토콜 버퍼 서비스 정의는 앞서 본 IDL을
  쓴다** (5장, p.181).[^kleppmann2026] YAML로 쓴 OpenAPI 서비스 정의의 예다 (5장,
  p.182):[^kleppmann2026]

  ```yaml
  openapi: 3.0.0
  info:
    title: Ping, Pong
    version: 1.0.0
  servers:
    - url: http://localhost:8080
  paths:
    /ping:
      get:
         summary: Given a ping, returns a pong message
         responses:
           '200':
             description: A pong
             content:
               application/json:
                  schema:
                    type: object
                    properties:
                      message:
                        type: string
                        example: Pong!
  ```

## 서비스 프레임워크

- 정의를 써도 코드는 남는다 — **설계 철학과 IDL을 채택하더라도 개발자는 여전히 서비스의 API 호출을
  구현하는 코드를 써야 한다. Spring Boot·FastAPI·gRPC 같은 서비스 프레임워크가 이 수고를 단순화하려고
  흔히 채택된다. 서비스 프레임워크는 개발자가 각 API 엔드포인트의 업무 로직을 쓰는 데 집중하게 하고
  프레임워크 코드가 라우팅·지표·캐싱·인증 등을 처리하게 한다** (5장, p.182).[^kleppmann2026]
- 정의와 코드의 선후가 프레임워크마다 갈린다 — **많은 프레임워크가 서비스 정의와 서버 코드를 함께
  묶는다. 인기 있는 파이썬 FastAPI 프레임워크 같은 어떤 경우에는 서버를 코드로 쓰고 IDL이 자동
  생성된다. gRPC 같은 다른 경우에는 서비스 정의를 먼저 쓰고 서버 코드 뼈대가 생성된다. 두 접근 모두
  개발자가 서비스 정의에서 여러 언어의 클라이언트 라이브러리와 SDK를 생성할 수 있게 한다. 코드 생성
  외에도 Swagger 같은 IDL 도구는 문서를 생성하고, 스키마 변경 호환성을 검증하고, 개발자가 서비스를
  질의·테스트할 GUI를 제공할 수 있다** (5장, pp.182–183).[^kleppmann2026]

## RPC 인코딩의 진화와 API 버저닝

- 서비스 쪽 데이터플로에는 단순화 가정이 하나 붙는다 — **진화성을 위해 RPC 클라이언트와 서버가
  독립적으로 바뀌고 배포될 수 있는 것이 중요하다. 데이터베이스를 거치는 데이터 흐름에 비해 서비스를
  거치는 데이터 흐름에서는 단순화 가정을 하나 할 수 있다: 모든 서버가 먼저 갱신되고 모든 클라이언트가
  나중에 갱신된다고 가정하는 것이 합리적이다. 따라서 요청에는 후진 호환만, 응답에는 전진 호환만
  필요하다** (5장, p.186).[^kleppmann2026]
- 호환성은 인코딩에서 상속된다 — **RPC 스킴의 후진·전진 호환 성질은 그것이 쓰는 인코딩이 무엇이든
  그로부터 상속된다** (5장, p.186):[^kleppmann2026]
  - **gRPC(프로토콜 버퍼)와 Avro RPC는 각 인코딩 형식의 호환성 규칙에 따라 진화할 수 있다.**
  - **RESTful API는 응답에 JSON을, 요청에 JSON이나 URI 인코딩/폼 인코딩 요청 파라미터를 쓰는 것이 가장
    흔하다. 선택적 요청 파라미터를 더하는 것과 응답 객체에 새 필드를 더하는 것은 보통 호환성을 유지하는
    변경으로 간주된다.**
- 조직 경계가 문제를 어렵게 만든다 — **서비스 호환성은 RPC가 흔히 조직 경계를 넘는 통신에 쓰인다는
  사실 때문에 더 어려워지는데, 서비스 제공자가 자기 클라이언트를 통제하지 못하고 업그레이드를 강제할
  수 없기 때문이다. 따라서 호환성은 오랫동안, 아마 무기한 유지돼야 한다. 호환성을 깨는 변경이
  필요하면 서비스 제공자는 결국 여러 버전의 서비스 API를 나란히 유지하는 일이 잦다** (5장,
  p.186).[^kleppmann2026]
- 버저닝 방법에는 합의가 없다 — **API 버저닝이 어떻게 작동해야 하는지(곧 클라이언트가 어느 버전의
  API를 쓰고 싶은지 어떻게 나타내는지)에 대한 합의가 없다. RESTful API에서 흔한 접근은 URL이나 HTTP
  `Accept` 헤더에 버전 번호를 쓰는 것이다. 클라이언트를 식별하는 데 API 키를 쓰는 서비스라면 또 하나의
  선택지는 클라이언트가 요청한 API 버전을 서버에 저장하고 별도의 관리 인터페이스로 이 버전 선택을
  갱신하게 하는 것이다** (5장, p.186).[^kleppmann2026]

## 데이터 반입 쪽에서 본 API

앞 절들이 API를 **설계하고 진화시키는 쪽**의 문제로 다룬다면, 데이터 엔지니어링 개론은 같은
것을 **남이 만든 API에서 데이터를 끌어와야 하는 쪽**의 문제로 놓는다.

- API의 2022년 저술 시점 위상 — **API는 이제 클라우드에서, SaaS 플랫폼을 위해, 그리고 내부 회사 시스템
  사이에서 데이터를 교환하는 표준적이고 만연한 방법이다. 웹 전반에 여러 유형의 API 인터페이스가
  존재하지만 우리는 주로 HTTP를 중심으로 지어진 것들에 관심이 있다 — 웹과 클라우드에서 가장
  인기 있는 유형이다** (5장, p.174).[^reis2022]
- REST가 지배적인 패러다임이다 — **먼저 2022년 저술 시점에 지배적인 API 패러다임인 REST를 이야기할 것이다.
  4장에서 언급했듯 REST는 표현 상태 전이(representational state transfer)를 뜻한다. 이 HTTP
  웹 API를 짓기 위한 실무와 철학의 집합은 2000년에 Roy Fielding이 박사 학위 논문에서 제시했다.
  REST는 GET·PUT 같은 HTTP 동사를 중심으로 지어져 있으나, 실무에서 2022년 저술 시점 REST는 원래 논문이
  개괄한 동사 매핑 중 소수만 쓴다** (5장, p.174).[^reis2022]
- 무상태성이 핵심 아이디어다 — **REST의 주요 아이디어 중 하나는 상호작용이 무상태(stateless)
  라는 것이다. Linux 터미널 세션과 달리 작업 디렉토리 같은 결부된 상태 변수를 가진 세션의
  관념이 없다. 각 REST 호출은 독립적이다. REST 호출은 시스템의 상태를 바꿀 수 있지만 이
  변경은 전역적이며 현재 세션이 아니라 전체 시스템에 적용된다** (5장, p.174).[^reis2022]
- 그래서 실무 부담이 남는다 — **비판자들은 REST가 결코 완전한 명세가 아니라고 지적한다. REST는
  상호작용의 기본 속성을 규정하지만 API를 활용하는 개발자는 애플리케이션을 짓거나 데이터를
  효과적으로 끌어오기 위해 상당한 양의 도메인 지식을 얻어야 한다** (5장, p.175).[^reis2022]
- 추상화 수준의 편차 — **API 추상화 수준에서 큰 변이를 본다. 어떤 경우 API는 사용자 요청으로부터
  시스템을 보호하는 데 요구되는 최소 기능을 제공하는, 내부에 대한 얇은 래퍼일 뿐이다. 다른
  예에서 REST 데이터 API는 분석 애플리케이션을 위해 데이터를 준비하고 고급 리포팅을 지원하는
  공학의 걸작이다** (5장, p.175).[^reis2022]
- 반입 파이프라인을 단순하게 만든 발전 둘 (5장, p.175):[^reis2022]
  - **첫째, 데이터 제공자가 여러 언어, 특히 파이썬으로 클라이언트 라이브러리를 자주 공급한다.
    클라이언트 라이브러리는 API 상호작용 코드를 짓는 보일러플레이트 노동의 상당 부분을
    제거한다. 클라이언트 라이브러리는 인증 같은 결정적 세부를 다루고 기본 메서드를 접근 가능한
    클래스로 매핑한다.**
  - **둘째, API와 상호작용하고 데이터 동기화를 관리하는 다양한 서비스와 오픈 소스 라이브러리가
    등장했다. 많은 SaaS와 오픈 소스 벤더가 흔한 API용 기성 커넥터를 제공한다. 플랫폼은 또한
    필요에 따라 맞춤 커넥터를 짓는 과정을 단순화한다.**
- 그래도 배관은 남는다 — **클라이언트 라이브러리나 즉시 쓸 수 있는 커넥터 지원이 없는 데이터
  API가 많다. 이 책 전반에서 강조하듯 엔지니어는 기성 도구를 써서 무차별적 중노동을 줄이는 것이
  좋다. 그러나 저수준 배관 작업은 여전히 많은 자원을 소비한다. 사실상 어떤 큰 회사에서든 데이터
  엔지니어는 API에서 데이터를 끌어오는 맞춤 코드를 쓰고 유지보수하는 문제를 다뤄야 하며, 이는
  제공되는 데이터의 구조를 이해하고, 적절한 데이터 추출 코드를 개발하고, 적합한 데이터 동기화
  전략을 결정할 것을 요구한다** (5장, p.175).[^reis2022]

## 웹훅 — 방향이 뒤집힌 API

- 정의 — **웹훅(webhooks)은 단순한 이벤트 기반 데이터 전송 패턴이다. 데이터 원천은 애플리케이션
  백엔드·웹 페이지·모바일 앱일 수 있다. 지정된 이벤트가 원천 시스템에서 일어나면 이것이 데이터
  소비자가 호스팅하는 HTTP 엔드포인트에 대한 호출을 촉발한다** (5장, p.176).[^reis2022]
- 왜 "역 API"인가 — **연결이 원천 시스템에서 데이터 싱크로 간다는 점에 주목하라 — 전형적 API의
  반대다. 이 이유로 웹훅은 흔히 역 API(reverse APIs)라 불린다** (5장, p.176).[^reis2022]
- 엔드포인트가 하는 일 — **엔드포인트는 POST 이벤트 데이터로 다양한 것을 할 수 있다 — 잠재적으로
  하류 프로세스를 촉발하거나 미래 사용을 위해 데이터를 저장한다. 분석 목적에서 우리는 이 이벤트를
  수집하는 데 관심이 있다. 엔지니어는 흔히 메시지 큐를 써서 높은 속도와 볼륨으로 데이터를
  반입한다** (5장, p.176).[^reis2022]

## gRPC

- RPC부터 — **원격 프로시저 호출(remote procedure call, RPC)은 분산 컴퓨팅에서 흔히 쓰인다.
  그것은 원격 시스템에서 프로시저를 돌리도록 허용한다** (5장, p.176).[^reis2022] 그 배치가
  왜 어려운지는 [원격 프로시저 호출의 문제](../concepts/remote-procedure-call-problems.md)에 있다.
- gRPC의 내력 — **gRPC는 2015년 구글에서 내부적으로 개발되고 나중에 오픈 표준으로 공개된 원격
  프로시저 호출 라이브러리다. 구글 안에서의 사용만으로도 우리 논의에 포함될 자격이 충분하다.
  Google Ads와 GCP 같은 많은 구글 서비스가 gRPC API를 제공한다. gRPC는 역시 구글이 개발한
  Protocol Buffers 오픈 데이터 직렬화 표준을 중심으로 지어져 있다** (5장, p.176).[^reis2022]
  그 직렬화 형식은 [프로토콜 버퍼와 필드 태그](../concepts/protocol-buffers-encoding.md)에 있다.
- 무엇을 강조하는가 — **gRPC는 HTTP/2 위에서 효율적인 양방향 데이터 교환을 강조한다.
  효율(efficiency)은 CPU 이용률·전력 소비·배터리 수명·대역폭 같은 측면을 가리킨다. GraphQL처럼
  gRPC는 REST보다 훨씬 구체적인 기술 표준을 부과하며, 따라서 공통 클라이언트 라이브러리의 사용을
  허용하고 엔지니어가 어떤 gRPC 상호작용 코드에도 적용될 기술 집합을 개발하도록 허용한다** (5장,
  p.176).[^reis2022]

## 이 모든 것이 얹히는 HTTP의 정의

이 페이지의 소스들은 HTTP를 이미 있는 것으로 놓고 그 위의 설계를 이야기한다. HTTP 자체의 현행
규범은 RFC 9110(STD 97)이고, 위 서술에 쓰인 낱말들이 거기서 정의된다.

- HTTP의 정의 자체는 프로토콜 하나가 아니라 **가족**으로 내려진다 — 일반 인터페이스와 확장 가능한
  의미론과 자기 서술적 메시지를 공유하는, 무상태이고 애플리케이션 계층인 요청/응답 프로토콜들
  (§1.1).[^fielding2022-rfc9110] 자세한 자리는
  [HTTP의 정의와 문서의 범위](../concepts/http-definition-and-scope.md)에 있다.
- 위 "리소스 식별에 URL 쓰기"에 해당하는 규범은 자원(resource)과 표현(representation)의 정의다.
  요청의 대상이면 자원이고, HTTP는 자원의 성질을 제한하지 않고 상호작용 인터페이스만 정의하며,
  주고받는 것은 자원 자체가 아니라 그 상태를 반영하도록 의도된 표현이다
  (§3.1, §3.2).[^fielding2022-rfc9110] 자세한 자리는
  [자원과 표현](../concepts/http-resources-and-representations.md)에 있다.
- 위 "상호작용이 무상태"에 해당하는 규범 문장도 이 문서에 있다. 무상태(stateless)는 각 요청 메시지의
  의미론이 고립되어 이해되고 연결과 그 위 메시지의 관계가 메시지 해석에 영향을 주지 않는다는 뜻이다
  (§3.3).[^fielding2022-rfc9110] 자세한 자리는
  [HTTP 클라이언트와 서버와 무상태성](../concepts/http-clients-servers-and-statelessness.md)에 있다.
- 위 "캐시 제어에 HTTP 기능 쓰기"의 규범은 이 문서가 아니라 RFC 9111(HTTP Caching)에 있다.
  RFC 9110은 캐시가 무엇인지만 정의하고 캐시 동작과 캐시 가능한 응답의 요건은 그쪽으로 넘긴다
  (§3.8).[^fielding2022-rfc9110]
- REST 자체의 정의는 이 문서가 주지 않는다. RFC 9110은 표현을 설명하면서 REST 논문을 참조할 뿐이다
  (§3.2).[^fielding2022-rfc9110]

## REST를 마이크로서비스 쪽에서 규정하면

앞 절들이 REST를 **한 문장의 설계 철학**으로 놓고 지나간다면, 2021년 마이크로서비스
실무서는 그 스타일 자체를 규정하고 채점한다. **이 KB에 로이 필딩의 학위 논문은 없다**
(2026-09 판정으로 반입 대상에서 뺐다) — RFC 9110은 HTTP를 정의할 뿐 REST를 정의하지 않고
참조만 한다. 그 자리를 **2차 경유로 메우는 소스가 둘**이고, 둘의 물음이 다르다. 이 절의
2021년 실무서는 **자원과 HATEOAS에 사정거리를 좁혀** 그 스타일을 채점하고, 2025년 API 스타일
비교서는 **제약 여섯을 목록으로 세고 그 준수를 재는 눈금(리처드슨 성숙도 모형)까지**
든다 (5장 §"Origins of REST", pp.157–159).[^dynowski2025] 후자의 전문은
[REST 아키텍처 스타일의 제약과 성숙도](../concepts/rest-architectural-style-and-maturity.md)에
있고, **이 페이지는 그것을 되풀이하지 않는다.**

- 규정 (5장 §REST, p.127):[^newman2021]

  > Representational State Transfer (REST) is an architectural style inspired by the web.

  - 저자는 그 스타일 뒤에 **많은 원칙과 제약**이 있음을 밝히면서도, 통합 문제와 RPC의 대안이라는
    두 관심사에 **실제로 도움이 되는 것들에만** 사정거리를 좁힌다고 적는다 (5장,
    p.127).[^newman2021]
- 중심 낱말이 자원이다 (5장, p.127):[^newman2021]

  > Most important when thinking about REST is the concept of resources.

  - 자원은 **서비스 자신이 알고 있는 것**이고, 서버는 요청을 받아 **그 자원의 여러 표현을
    만든다.** 그 결과가 이 절의 핵심 문장이다 (5장, p.128):[^newman2021]

    > How a resource is shown externally is completely decoupled from how it is stored
    > internally.

  - 그래서 클라이언트는 **완전히 다른 형식으로 저장돼 있어도 JSON 표현을 요청할 수 있고**,
    표현을 받은 뒤 그것을 바꾸는 요청을 할 수 있으며 **서버는 그 요청에 응할 수도 응하지
    않을 수도 있다** (5장, p.128).[^newman2021] 같은 두 낱말의 프로토콜 쪽 정의는 위
    [이 모든 것이 얹히는 HTTP의 정의](#이-모든-것이-얹히는-http의-정의) 절과
    [자원과 표현](../concepts/http-resources-and-representations.md)에 있다.
- **REST의 스타일이 하나가 아니다** — 저자는 여러 스타일이 있음을 적고 그것들을 견주는
  리처드슨 성숙도 모형(Richardson Maturity Model)을 보라고 권한다 (5장,
  p.128).[^newman2021] 이 KB는 그 모형의 원전을 반입하지 않았으나,
  **그 모형의 레벨 넷을 2차 경유로 서술하는 자리는 생겼다** —
  [REST 아키텍처 스타일의 제약과 성숙도](../concepts/rest-architectural-style-and-maturity.md)다.
- **프로토콜과의 관계가 느슨하다** (5장, p.128):[^newman2021]

  > REST itself doesn't really talk about underlying protocols, although it is most commonly
  > used over HTTP.

  - 저자는 아주 다른 프로토콜 위의 REST 구현을 본 적이 있으나 **일이 많이 든다**고 적는다.
    HTTP가 명세의 일부로 주는 기능들(동사 같은)이 **REST를 HTTP 위에 구현하기 쉽게** 만들고,
    다른 프로토콜에서는 그 기능을 직접 다뤄야 한다 (5장, p.128).[^newman2021]

### REST와 HTTP가 맞물리는 자리

- 맞물림의 내용 — HTTP 동사는 **자원에 대해 어떻게 작동해야 하는지가 명세에서 이미 잘 이해되어
  있고**, REST 아키텍처 스타일은 그 동사들이 **모든 자원에서 같은 방식으로 행동해야 한다**고
  말한다 (5장, p.128):[^newman2021]

  > The REST architectural style actually tells us that these verbs should behave the same way
  > on all resources

  - **그래서 무엇이 없어지는가** — `createCustomer`·`editCustomer` 같은 메서드를 여럿 두는
    일이 사라지고, 고객 표현을 POST해 서버가 새 자원을 만들게 요청하고 GET으로 표현을 가져오면
    된다. 개념상 **엔드포인트는 자원 하나**이고 할 수 있는 작업은 **HTTP 프로토콜에 구워져
    있다** (5장, p.128).[^newman2021]
  - **메서드 하나하나의 규범을 여기 다시 적지 않는다.** 저자가 되풀이하는 것(GET은 멱등하게
    회수하고 POST는 새 자원을 만든다)의 현행 정본은 RFC 9110이고, 이 KB에서는
    [HTTP 메서드 의미론](../synthesis/http-method-semantics.md) 허브 아래가 그 자리다.
    안전성과 멱등성의 정의 자체는 §9.2.1–9.2.2에 있다.[^fielding2022-rfc9110]
- **딸려 오는 생태계가 이 스타일의 값어치 절반이다** — HTTP 캐싱 프록시(Varnish)와 로드
  밸런서(mod_proxy)를 쓸 수 있고, 많은 모니터링 도구가 HTTP를 기본으로 지원하며, 기본 인증부터
  클라이언트 인증서까지 보안 통제를 쓸 수 있다. 다만 조건이 붙는다 — **그 이득을 보려면 HTTP를
  잘 써야 하고, 잘못 쓰면 다른 어떤 기술만큼이나 불안전하고 확장하기 어렵다** (5장,
  p.128).[^newman2021]
  - 버전 조건: 2021년 저술 시점. 저자가 이름을 대는 제품(Varnish·mod_proxy)은 그 시점의 예시다.
    이 KB는 두 제품의 문서를 반입하지 않았다.
- **HTTP를 쓴다고 REST가 되는 것은 아니다** — SOAP도 HTTP로 라우팅되지만 **명세를 거의 쓰지
  않는다**(동사가 무시되고 HTTP 오류 코드 같은 단순한 것도 무시된다). gRPC는 **HTTP/2의 능력을
  활용하도록 설계됐다**(한 연결로 여러 요청-응답 스트림을 보내는 것 같은). 그리고 저자가 못을
  박는다 (5장, p.129):[^newman2021]

  > But of course, when using gRPC, you're not doing REST just because you're using HTTP!

### HATEOAS — 하이퍼미디어를 애플리케이션 상태의 엔진으로

- 규정 (5장 §"Hypermedia as the engine of application state", p.129):[^newman2021]

  > The idea behind HATEOAS is that clients should perform interactions with the server
  > (potentially leading to state transitions) via these links to other resources.

  - **클라이언트는 고객 자원이 서버의 정확히 어디에 사는지(어느 URI를 칠지) 알 필요가 없고,
    링크를 찾아 따라가 필요한 것에 닿는다** (5장, p.129).[^newman2021]
  - 하이퍼미디어 자체는 **한 조각의 콘텐츠가 여러 형식의 다른 콘텐츠로 가는 링크를 담는다**는
    착상이고, 저자는 그것이 평범한 웹 페이지에서 일어나는 일이라고 적는다 (5장,
    p.129).[^newman2021]
- **사람 쪽 비유가 이 착상의 근거다** — 쇼핑 사이트의 장바구니는 위치도 그림도 링크도 시간이
  지나며 바뀌었지만 사람은 여전히 장바구니를 알아보고 쓴다. 곧 **형태와 밑에 깔린 컨트롤이
  바뀌어도 그것이 무엇을 뜻하는지를 이해**하고 있으며, 그래서 웹 페이지는 조금씩 바뀔 수 있다.
  **암묵적 계약이 지켜지는 한 변경이 깨는 변경일 필요가 없다** (5장, p.129).[^newman2021]
  - **전자적 소비자에게 같은 수준의 똑똑함을 주려는 것**이 하이퍼미디어 컨트롤이다 (5장,
    p.129).[^newman2021]
- 무엇이 실제로 문서에 담기는가 — 앨범 목록 표현에 `artist` 관계를 가진 컨트롤과
  `instantpurchase` 컨트롤이 들어 있고, 그 문서를 읽는 클라이언트는 **아티스트 정보를 얻으려면
  `artist` 관계의 컨트롤로 가야 한다는 것과 `instantpurchase`가 구매 프로토콜의 일부라는 것을
  알아야** 한다. 저자의 정리는 **클라이언트가 API의 의미론을 이해해야 한다**는 것이고, 그것이
  쇼핑 사이트에서 사람이 장바구니의 뜻을 아는 것과 같다 (5장, p.130).[^newman2021]
- **무엇을 사는가** — 클라이언트로서는 **어느 URI 스킴으로 가야 사는지를 알 필요가 없고**
  자원에 접근해 구매 컨트롤을 찾아 따라가면 된다. 그 컨트롤의 위치가 바뀌든 URI가 바뀌든
  **사이트가 아예 다른 서비스로 보내든 클라이언트는 상관하지 않는다.** 저자의 표현으로
  **클라이언트와 서버 사이에 막대한 양의 디커플링**이 생긴다 (5장, p.130).[^newman2021]
  - **깨지는 조건도 명시된다** — 새 컨트롤을 문서에 더하는 것은 자유이고, 소비자가 깨지는 것은
    **어느 컨트롤의 의미론을 근본적으로 바꿔 아주 다르게 행동하게 하거나 컨트롤을 아예 없앨
    때**뿐이다 (5장, p.130).[^newman2021]
- **그리고 저자의 채점이 온다.** 이론은 말이 되지만 (5장, p.130):[^newman2021]

  > I've found that this form of REST is rarely practiced, for reasons I've not entirely come
  > to grips with.

  - 진단이 한 줄 붙는다 — **REST의 착상 다수가 분산 하이퍼미디어 체계를 만드는 것을 전제하는데
    대부분의 사람이 만드는 것은 그것이 아니다** (5장, p.130).[^newman2021]
  - 성능 쪽 대가도 적힌다 — 클라이언트가 **여러 컨트롤을 따라가 알맞은 엔드포인트를 찾아야
    하므로 아주 수다스러운(chatty) 프로토콜**이 될 수 있고 작업마다 여러 왕복이 필요할 수
    있다. 저자의 처방은 **먼저 컨트롤을 따라가게 만들고 필요하면 나중에 최적화하라**는
    것이다 (5장, pp.131–132).[^newman2021]
  - 최종 판정이 경험 진술로 적힌다 (5장, p.132):[^newman2021]

    > Despite intellectually appreciating the goals behind HATEOAS, I haven't seen much
    > evidence that the additional work to implement this style of REST delivers worthwhile
    > benefits in the long run

    저자는 그것이 자기 경험 한 묶음일 뿐임을 덧붙이고, 왜 퍼지지 않았는지의 후보 넷을
    가설로 남긴다 — **개념이 너무 낯설거나, 도구와 표준이 없거나, 우리가 짓게 된 종류의
    체계에 모형이 맞지 않거나, HATEOAS의 착상이 우리가 마이크로서비스를 짓는 방식과 잘
    섞이지 않거나** (5장, p.132).[^newman2021]
- **이 KB의 다른 소스들과 겨루지 않는다.** 위
  [REST와 IDL](#rest와-idl) 절의 REST 규정은 단순한 데이터 형식과 URL과 HTTP 기능을 열거할 뿐
  **하이퍼미디어를 REST의 요건으로 세우지 않고**, 데이터 반입 쪽 서술도 동사와 무상태성만
  든 뒤 **REST가 완전한 명세가 아니라는 비판**을 적는다. 곧 그 두 소스는 HATEOAS를
  권하지도 반대하지도 않았고, 뉴먼의 판정이 **비어 있던 자리에 처음 들어온 평가**다.
  모순 쌍으로 세우지 않았다.
  - **뒤에 들어온 2025년 소스의 평가도 겨루지 않고 겹친다.** 그쪽도 **HATEOAS가 실무에서 거의
    쓰이지 않는다**고 적으며 구글과 메타의 API를 실물로 든다. 다른 것은 **왜인가에 대한 답의
    성격**이다 — 뉴먼은 "이유를 온전히 붙잡지 못했다"며 후보 넷을 가설로 남기고, 그쪽은 서버
    복잡도·클라이언트 복잡도·실용주의·문서화 넷을 단정으로 적는다 (5장 §"Is Being RESTless Good
    Enough?", pp.162–164).[^dynowski2025] 그 넷의 전문은
    [REST 아키텍처 스타일의 제약과 성숙도](../concepts/rest-architectural-style-and-maturity.md)에
    있다.

### 도전과 어디에 쓸 것인가

- **클라이언트 코드 생성이 역사적으로 없었다** — 그래서 REST API를 내면서 소비자용 클라이언트
  라이브러리를 함께 주는 일이 잦았고, 그 라이브러리가 **클라이언트와 서버 사이 결합의 문제를
  일으킨다** (5장 §Challenges, p.131).[^newman2021] 저자는 그 문제를 같은 장의 뒤쪽
  (§"DRY and the Perils of Code Reuse in a Microservice World")으로 미룬다.
- **OpenAPI가 그 자리를 어느 정도 메웠다** — 스웨거(Swagger) 프로젝트에서 자란 OpenAPI 명세가
  REST 엔드포인트에 **여러 언어의 클라이언트 코드를 생성할 만큼의 정보를 정의**할 수 있게
  해 준다. 다만 저자의 관찰은 **문서화에 이미 스웨거를 쓰던 팀조차 그 기능을 실제로 쓰는 것을
  많이 보지 못했다**는 것이고, 원인 추정이 **기존 API에 소급 적용하기 어렵다**는 것이다
  (5장, p.131).[^newman2021]
  - 버전 조건: 2021년 저술 시점. **저자가 유보를 덧붙인다** — 전에는 문서화에만 쓰이던 명세가
    이제 더 명시적인 계약을 정의하는 데 쓰이는 것이 걱정스럽고, 그것이 **훨씬 복잡한 명세**로
    이어질 수 있다는 것이다. 저자가 드는 대비가 **OpenAPI 스키마와 프로토콜 버퍼 스키마를
    견주면 대조가 꽤 뚜렷하다**는 것이다. 그럼에도 **선택지가 생긴 것은 좋은 일**이라고 적는다
    (5장, p.131).[^newman2021]
- **성능** (5장, p.131):[^newman2021] REST over HTTP의 적재물은 SOAP보다 더 간결할 수 있으나
  (JSON이나 이진 형식도 쓸 수 있으므로) **Thrift 같은 이진 프로토콜만큼 날씬하지는 않다.**
  요청마다 드는 HTTP의 오버헤드도 저지연 요구에서는 걱정거리가 될 수 있고, 2021년 저술 시점에 쓰이는 주류
  HTTP 프로토콜은 전부 **TCP를 요구**하는데 TCP에는 다른 네트워크 프로토콜에 비한 비효율이
  있다.
  - 버전 조건: 2021년 저술 시점. 저자는 그 제약이 해소되는 중이라 적으며 **HTTP/3가 최종화
    과정에 있고 QUIC 프로토콜로 옮겨 가려 한다**고 쓴다. QUIC은 TCP와 같은 종류의 능력을
    주면서 지연과 대역폭에서 개선을 보였고, 저자의 예상은 **공개 인터넷에 널리 영향을 주기까지
    몇 해가 걸리겠으나 조직 내부 네트워크에서는 더 일찍 이득을 볼 수 있다**는 것이다 (5장,
    p.131).[^newman2021] 이 KB는 HTTP/3와 QUIC의 명세를 반입하지 않았으므로 이 대목은 그
    시점의 전망으로만 읽는다.
- **총평** (5장, p.131):[^newman2021]

  > Despite these disadvantages, REST over HTTP is a sensible default choice for
  > service-to-service interactions.

  - 저자가 더 깊은 다룸으로 Jim Webber·Savas Parastatidis·Ian Robinson의 *REST in Practice*를
    권한다 (5장, p.131).[^newman2021] 이 KB가 확인한 원전은 아니다.
- **어디에 쓸 것인가** (5장 §"Where to use it", pp.132–133):[^newman2021]
  - 널리 쓰이므로 **가능한 한 다양한 클라이언트의 접근을 허용하려는 동기 요청-응답
    인터페이스**에는 명백한 선택이다. 저자는 REST API를 **"대부분의 것에 그럭저럭 충분한"
    선택으로 생각하는 것은 잘못**이라고 적으면서도 그런 면이 있음을 인정하고, 그 근거를
    **널리 이해되는 스타일이고 아주 다양한 기술에서 상호운용을 보장한다**는 데 둔다.
  - **캐싱이 갈림길이다** — HTTP의 능력과 REST가 그 능력을 (감추지 않고) 그 위에 쌓는
    정도 덕분에 **요청의 대규모 캐싱이 효과적으로 필요한 상황에서 뛰어나고**, 그래서
    **외부 당사자나 클라이언트 인터페이스에 API를 노출하는 데 명백한 선택**이다.
  - 맞지 않는 자리도 적힌다 — 더 효율적인 통신 프로토콜과 견주면 손해를 볼 수 있고,
    REST 기반 API 위에 비동기 상호작용 프로토콜을 지을 수는 있으나 **일반적인 마이크로서비스
    사이 통신에서는 대안들에 비해 잘 맞지 않는다.**
  - 한 줄 요약이 이렇다 — **경계(perimeter)에서 쓰기에는 환상적으로 잘 작동하고,
    마이크로서비스 사이의 동기 요청-응답 통신에도 훌륭하다** (5장, p.133).[^newman2021]

## 계약의 엄격함이라는 축에서 REST가 놓이는 자리

- **분산 아키텍처의 계약을 엄격에서 느슨까지의 스펙트럼으로 놓는 소스가 REST를 그 가운데에
  둔다.** 엄격한 극은 XML·JSON 스키마와 객체 RPC(gRPC 포함)이고 느슨한 극은 값 주도 계약과
  단순 JSON과 키-값 쌍 배열인데, **REST와 GraphQL이 그 사이**다 (13장,
  p.367).[^ford2021-hard-parts]
- **그 소스가 대는 근거가 위 §"REST를 마이크로서비스 쪽에서 규정하면"의 자원 개념과 같다** —
  REST에서는 아키텍트가 **메서드나 프로시저 엔드포인트가 아니라 자원을 모델링**하므로 계약이
  덜 취약하다. 비행기 부품을 기술하는 RESTful 자원에 좌석을 묻는 질의가 있을 때 **누가 엔진
  정보를 더해도 그 질의는 깨지지 않는다** — 정보를 더하는 것은 이미 있는 것을 깨뜨리지 않는다
  (13장, p.368).[^ford2021-hard-parts]
  - **이것이 위 §"RPC 인코딩의 진화와 API 버저닝"이 적는 호환 문제의 형식 쪽 답**이다. 축
    전체와 양 끝의 절충표는 [계약의 스펙트럼](../concepts/contract-spectrum.md)에 있다.

## 이벤트 브로커 앞에 세우는 REST — REST 프록시

- **이 페이지의 REST는 지금까지 서비스의 인터페이스였다. 다른 소스 하나가 같은 인터페이스를
  이벤트 브로커 앞에 세운다** — **REST 프록시(REST proxy)는 클라이언트가 이벤트 브로커와
  통신하도록 REST API를 노출하는 서비스**이고, 쓸 수 있는 스트림 목록 보기·새 스트림 만들기·
  이벤트 발행하기·스트림에서 소비하기 같은 미리 정해진 명령 집합을 준다 (17장,
  p.336).[^bellemare2025]
  - **자원이 무엇인가가 이 페이지의 규정과 어긋나지 않는다** — 노출되는 자원이 스트림과 그 안의
    레코드이고, 저장 방식(브로커의 파티션과 오프셋)과 바깥 표현(JSON 적재물)이 갈려 있다.
    위 [REST를 마이크로서비스 쪽에서 규정하면](#rest를-마이크로서비스-쪽에서-규정하면)이 인용한
    "자원이 바깥에 어떻게 보이는가는 안에 어떻게 저장되는가와 완전히 떼어져 있다"가 그대로
    적용되는 자리다. #hypothesis 저자가 이 대응을 적지는 않는다.
  - **읽기가 상태를 갖는다는 것이 이 쓰임의 특이점이다** — 소비하려면 **오프셋 진행을 저장할
    지속 컨슈머를 만들고, 구독하고, 소비하고, 오프셋을 커밋하고, 컨슈머를 삭제하는** 다섯 단계를
    거쳐야 한다 (17장, p.338).[^bellemare2025] 곧 **무상태 요청의 연쇄가 아니라 서버 쪽에 수명을
    갖는 컨슈머를 만들어 두고 쓰는 구성**이다.
  - **성능 채점이 붙는다** — 저자는 REST 프록시가 **통상 고성능 부품이 아니고** 웬만한 부하에도
    여럿을 두어야 할 수 있으며, 통합을 다시 따져 네이티브 프로듀서와 컨슈머로 바꾸는 편이 이로울
    수 있다고 적는다 (17장, p.338).[^bellemare2025]
  - 전문은 [요청-응답과 이벤트 기반의 통합](../concepts/request-response-and-event-driven-integration.md)에
    있다.

## OpenAPI가 문서로 쓰이는 자리

**위 절들이 OpenAPI를 인터페이스 정의 언어로 다룬다면, 같은 마이크로서비스 실무서의 뒤쪽은 그것을
문서화 수단으로 다시 세운다.** 물음이 다르다 — 앞의 것은 "계약을 무엇으로 적는가"이고 이것은
"그 계약을 사람이 어떻게 읽는가"다.

- 저자는 OpenAPI를 스키마 형식으로 이미 소개했다고 적고 덧붙인다 — **그것은 문서를 제공하는
  데에도 아주 효과적이며, OpenAPI 서술자를 소비해 개발자가 문서를 읽을 유용한 포털을 만들도록
  돕는 오픈 소스·상용 도구가 이제 많이 있다** (5장 §"Explicit Schemas",
  p.170).[^newman2021]
  - 버전 조건: 2021년 저술 시점. **저자 자신이 유보를 단다** — **OpenAPI를 보는 오픈 소스 포털은
    다소 기본적으로 보이고, 검색 기능을 지원하는 것을 찾기 어려웠다**는 관찰이다 (5장,
    p.170).[^newman2021] 도구 지형의 서술이므로 그 시점으로 범위를 좁힌다.
  - **쿠버네티스를 쓰는 쪽에는 Ambassador의 개발자 포털이 특히 흥미롭다**고 적는다. Ambassador는
    이미 쿠버네티스용 API 게이트웨이로 인기 있는 선택지이고, 그 개발자 포털은 **가용한 OpenAPI
    엔드포인트를 자동 발견하는 능력**을 갖는다. **새 마이크로서비스를 배포하면 그 문서가 자동으로
    가용해진다는 발상**이 저자에게 크게 호소력이 있다 (5장, p.170).[^newman2021]
    - 버전 조건: 2021년 저술 시점. 제품 이름과 그 기능은 그 시점의 지형이다. 그 게이트웨이가
      무엇인지는 [API 게이트웨이와 서비스 메시](../concepts/api-gateway-and-service-mesh.md)에 있다.
- **이벤트 기반 인터페이스 쪽은 뒤늦게 선택지가 생겼다** — 저자는 **과거에는 이벤트 기반
  인터페이스를 문서화할 좋은 지원이 없었으나 이제 적어도 선택지가 있다**고 적는다. **AsyncAPI는
  OpenAPI를 각색한 것으로 출발했고**, 그 밖에 **CNCF 프로젝트인 CloudEvents**가 있다 (5장,
  p.170).[^newman2021]
  - **저자의 채점에 조건이 붙는다** — 둘 다 실제 현장에서 써 보지는 않았지만 **CNCF와의 결부
    덕분에 통합과 지원이 풍부해 보인다는 이유만으로 CloudEvents에 더 끌린다**고 적는다. 그리고
    단서가 하나 붙는다 — **역사적으로 CloudEvents는 AsyncAPI에 견주어 이벤트 형식에서 더
    제한적으로 보였고 JSON만 제대로 지원되다가 최근에야 프로토콜 버퍼 지원이 제거됐다가 다시
    들어왔으므로** 그것이 고려 사항일 수 있다 (5장, p.170).[^newman2021]
  - 버전 조건: 2021년 저술 시점. 두 명세의 세력과 형식 지원 범위는 그 시점의 관찰이고, 저자가
    적는 "최근"도 그 시점 기준이다.
- **문서가 답하지 못하는 나머지**는 [서비스 디스커버리와 로드 밸런싱](../concepts/service-discovery-and-load-balancing.md)의
  자기 서술하는 체계 절에 있다 — 체계가 프로그램으로 뿜어내는 정보를 모아 사람이 볼 레지스트리를
  채우는 쪽이다.
