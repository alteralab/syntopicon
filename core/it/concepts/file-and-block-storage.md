하나의 질문: **파일과 블록은 무엇이 다르며, 클라우드에서 각각 어떤 형태로 나타나는가.**

## 파일을 규정하는 세 특성

- 왜 정의를 다시 하는가 — **우리는 매일 파일을 다루지만 파일이라는 관념은 다소 미묘하다.
  파일(file)은 소프트웨어와 운영 체제가 쓰는 특정한 읽기·쓰기·참조 특성을 가진 데이터 엔티티다**
  (6장, p.199).[^reis2022] 저자들이 정의에 넣는 특성은 셋이다 (6장, pp.199–200):[^reis2022]
  - **유한 길이(finite length)** — **파일은 유한 길이의 바이트 스트림이다.**
  - **추가 연산(append operations)** — **호스트 저장 시스템의 한계까지 파일에 바이트를 덧붙일
    수 있다.**
  - **임의 접근(random access)** — **파일의 어느 위치에서든 읽을 수 있고 어느 위치에든 갱신을
    쓸 수 있다.**
- 오브젝트는 그중 하나만 갖는다 — **다른 파일 비슷한 데이터 엔티티가 이 특성을 다 갖지는 않는다는
  점에 주목하라. 예컨대 오브젝트 저장의 객체는 첫 번째 특성인 유한 길이만 지원하지만 여전히 극도로
  유용하다** (6장, p.200).[^reis2022] 그 차이의 전문은
  [오브젝트 스토어](../concepts/object-stores.md)에 있다.
- 오브젝트가 더 중요하다는 예고 — **오브젝트 저장(object storage)은 파일 저장과 아주 비슷하게
  행동하지만 핵심 차이가 있다. 파일 저장을 먼저 논함으로써 오브젝트 저장의 무대를 마련하지만,
  오브젝트 저장은 당신이 하게 될 데이터 엔지니어링 유형에 틀림없이 훨씬 더 중요하다** (6장,
  p.200).[^reis2022]

## 디렉터리 트리라는 조직

- **파일 저장 시스템은 파일을 디렉터리 트리로 조직한다.** 저자들이 드는 참조 예는
  `/Users/matthewhousley/output.txt`다 (6장, p.200).[^reis2022]
- 해석 절차 — **이 파일 참조가 운영 체제에 넘겨지면 루트 디렉터리 `/`에서 시작해 `Users`,
  `matthewhousley`, 마지막으로 `output.txt`를 찾는다. 왼쪽부터 작업하면 각 디렉터리는 최종적으로
  파일 `output.txt`에 도달할 때까지 부모 디렉터리 안에 담겨 있다. 이 예는 Unix 의미론을 쓰지만
  Windows 파일 참조 의미론도 비슷하다** (6장, p.200).[^reis2022]
- 파일시스템이 저장하는 것 — **파일시스템은 각 디렉터리를 그것이 담은 파일과 디렉터리에 대한
  메타데이터로 저장한다. 이 메타데이터는 각 엔티티의 이름, 관련 권한 세부, 실제 엔티티에 대한
  포인터로 이뤄진다. 디스크에서 파일을 찾기 위해 운영 체제는 각 계층 수준의 메타데이터를 보고
  마침내 파일 자체에 도달할 때까지 다음 하위 디렉터리 엔티티에 대한 포인터를 따라간다** (6장,
  p.200).[^reis2022]
- 저자들의 처방 — **파이프라인에 파일 저장 패러다임이 필요한 경우 상태에 주의하고 가능한 한
  덧없는(ephemeral) 환경을 쓰라. 붙어 있는 디스크가 있는 서버에서 파일을 처리해야 하더라도
  처리 단계 사이의 중간 저장에는 오브젝트 저장을 쓰라. 수동 저수준 파일 처리는 일회성 반입
  단계나 파이프라인 개발의 탐색적 단계에만 남겨 두려고 해 보라** (6장, p.200).[^reis2022]

## 로컬 디스크 저장

- **가장 친숙한 유형의 파일 저장은 SSD나 마그네틱 디스크의 로컬 디스크 파티션에 있는 운영 체제
  관리 파일시스템이다. New Technology File System(NTFS)과 ext4가 각각 Windows와 Linux에서 인기
  있는 파일시스템이다. 운영 체제가 디렉터리 엔티티·파일·메타데이터를 저장하는 세부를 다룬다.
  파일시스템은 쓰기 도중 정전이 났을 때 쉬운 복구를 허용하도록 데이터를 쓰게 설계돼 있지만, 쓰이지
  않은 데이터는 여전히 손실될 것이다** (6장, p.200).[^reis2022]
- 일관성 — **로컬 파일시스템은 일반적으로 완전한 쓰기 후 읽기 일관성(read after write
  consistency)을 지원한다 — 쓰기 직후에 읽으면 쓰인 데이터를 돌려준다. 운영 체제는 한 파일에 대한
  동시 쓰기 시도를 관리하기 위해 다양한 잠금 전략도 채용한다** (6장, p.201).[^reis2022]
- 고급 기능 — **로컬 디스크 파일시스템은 저널링·스냅샷·중복성·여러 디스크에 걸친 파일시스템
  확장·전체 디스크 암호화·압축 같은 고급 기능도 지원할 수 있다** (6장, p.201).[^reis2022]

## 네트워크 결합 저장(NAS)

- 정의 — **네트워크 결합 저장(network-attached storage, NAS) 시스템은 네트워크 너머로 클라이언트에
  파일 저장 시스템을 제공한다. NAS는 서버를 위한 널리 퍼진 해법이며 흔히 내장된 전용 NAS 인터페이스
  하드웨어와 함께 출하된다** (6장, p.201).[^reis2022]
- 무엇을 사고파는가 — **네트워크 너머로 파일시스템에 접근하는 데 성능 페널티가 있지만, 저장
  가상화에는 상당한 이점도 존재한다 — 중복성과 신뢰성, 자원에 대한 세밀한 통제, 큰 가상 볼륨을
  위한 여러 디스크에 걸친 저장 풀링, 여러 기계에 걸친 파일 공유가 그것이다. 엔지니어는, 특히
  여러 클라이언트가 잠재적으로 같은 데이터에 접근할 때, 자기 NAS 해법이 제공하는 일관성 모델을
  알고 있어야 한다** (6장, p.201).[^reis2022]
- 대안 — **NAS의 인기 있는 대안은 저장 영역 네트워크(storage area network, SAN)이지만 SAN
  시스템은 파일시스템 추상 없이 블록 수준 접근을 제공한다** (6장, p.201).[^reis2022]

## 클라우드 파일시스템 서비스

- 정의 — **클라우드 파일시스템 서비스는 여러 클라우드 VM과 애플리케이션 — 잠재적으로 클라우드
  환경 밖의 클라이언트를 포함해 — 과 함께 쓸 완전 관리형 파일시스템을 제공한다. 클라우드
  파일시스템은 VM에 붙은 표준 저장 — 일반적으로 VM 운영 체제가 관리하는 파일시스템을 가진 블록
  저장 — 과 혼동해서는 안 된다. 클라우드 파일시스템은 NAS 해법과 비슷하게 행동하지만 네트워킹·
  디스크 클러스터 관리·장애·설정의 세부는 클라우드 벤더가 완전히 처리한다** (6장,
  p.201).[^reis2022]
- 실물과 그 일관성 — **예컨대 Amazon Elastic File System(EFS)은 클라우드 파일시스템 서비스의 극히
  인기 있는 예다. 저장은 NFS 4 프로토콜을 통해 노출되며 이 프로토콜은 NAS 시스템도 쓴다. EFS는
  사전 저장 예약 없이 자동 확장과 저장량당 과금을 제공한다. 이 서비스는 또한 로컬 쓰기 후 읽기
  일관성(local read-after-write consistency, 쓰기를 수행한 기계에서 읽을 때)을 제공한다. 전체
  파일시스템에 걸쳐서는 닫은 뒤 열기 일관성(open-after-close consistency)도 제공한다. 다시 말해
  애플리케이션이 파일을 닫으면 이후 읽는 쪽은 닫힌 파일에 저장된 변경을 볼 것이다** (6장,
  p.201).[^reis2022]

## 블록 저장

- 정의 — **근본적으로 블록 저장(block storage)은 SSD와 마그네틱 디스크가 제공하는 원시 저장
  유형이다. 클라우드에서 가상화된 블록 저장은 VM의 표준이다. 이 블록 저장 추상은 원시 디스크가
  제공하는 것 이상의 저장 크기·확장성·데이터 내구성에 대한 세밀한 통제를 허용한다** (6장,
  p.202).[^reis2022]
- 블록의 정의 — **SSD와 마그네틱 디스크에 대한 앞선 논의에서 우리는 이 임의 접근 장치에서 운영
  체제가 디스크의 어떤 데이터든 탐색·읽기·쓰기할 수 있다고 언급했다. 블록(block)은 디스크가
  지원하는 최소 주소 지정 가능 데이터 단위다. 이는 옛 디스크에서 흔히 사용 가능 데이터 512바이트
  였으나 이제 대부분의 현행 디스크에서 4,096바이트로 커져 쓰기를 덜 세밀하게 만드는 대신 블록
  관리 오버헤드를 극적으로 줄인다. 블록은 일반적으로 오류 검출/정정과 다른 메타데이터를 위한 여분
  비트를 담는다** (6장, p.202).[^reis2022]
- 물리 배치의 귀결 — **마그네틱 디스크의 블록은 물리 플래터 위에 기하학적으로 배열된다. 같은
  트랙의 두 블록은 헤드를 움직이지 않고 읽을 수 있지만 별개 트랙의 두 블록을 읽으려면 탐색이
  필요하다. SSD의 블록 사이에도 탐색 시간이 생길 수 있지만 이는 마그네틱 디스크 트랙의 탐색
  시간에 비하면 무한소다** (6장, p.202).[^reis2022]
- 누가 블록 수준으로 접근하는가 — **트랜잭션 데이터베이스 시스템은 일반적으로 최적 성능을 위해
  데이터를 배치하려고 디스크를 블록 수준에서 접근한다. 행 지향 데이터베이스에서 이는 원래 데이터
  행이 연속 스트림으로 쓰였음을 뜻했다. SSD와 그와 결부된 탐색 시간 성능 개선이 도래하면서 상황은
  더 복잡해졌지만, 트랜잭션 데이터베이스는 여전히 블록 저장 장치에 대한 직접 접근이 제공하는 높은
  임의 접근 성능에 의존한다** (6장, p.202).[^reis2022]
- 부팅 디스크 — **블록 저장은 클라우드 VM의 운영 체제 부팅 디스크의 기본 선택지로도 남아 있다.
  블록 장치는 물리 디스크에 직접 하는 것과 매우 비슷하게 포맷되지만 저장은 보통 가상화된다**
  (6장, p.202).[^reis2022]

## RAID와 SAN

- **RAID** — **RAID는 독립 디스크 중복 배열(redundant array of independent disks)을 뜻한다.
  RAID는 데이터 내구성을 개선하고 성능을 향상하고 여러 드라이브의 용량을 결합하기 위해 여러 디스크를
  동시에 통제한다. 배열은 운영 체제에 단일 블록 장치로 나타날 수 있다. 향상된 실효 대역폭과 더 높은
  내결함성(많은 디스크 장애에 대한 내성) 사이의 원하는 균형에 따라 많은 인코딩·패리티 방식이
  이용 가능하다** (6장, p.202).[^reis2022]
- **저장 영역 네트워크(SAN)** — **SAN 시스템은 네트워크 너머로, 일반적으로 저장 풀에서 가상화된
  블록 저장 장치를 제공한다. SAN 추상은 세밀한 저장 확장을 허용하고 성능·가용성·내구성을 향상할 수
  있다. 온프레미스 저장 시스템으로 일한다면 SAN 시스템을 마주칠 수 있고, 다음 절처럼 SAN의 클라우드
  판본도 마주칠 수 있다** (6장, p.203).[^reis2022]

## 클라우드 가상화 블록 저장

- 정의 — **클라우드 가상화 블록 저장 해법은 SAN과 비슷하지만 엔지니어를 SAN 클러스터와 네트워킹
  세부를 다루는 일에서 해방시킨다. 표준 예로 Amazon Elastic Block Store(EBS)를 볼 것이다. 다른
  퍼블릭 클라우드도 비슷한 제공물을 갖는다. EBS는 Amazon EC2 가상 머신의 기본 저장이다. 다른
  클라우드 제공자도 가상화된 오브젝트 저장을 VM 제공물의 핵심 구성 요소로 다룬다** (6장,
  p.203).[^reis2022]
- 계층 — **EBS는 서로 다른 성능 특성을 가진 여러 서비스 계층을 제공한다. 일반적으로 EBS 성능
  지표는 IOPS와 처리량(전송 속도)으로 주어진다. EBS 저장의 더 높은 성능 계층은 SSD 디스크가
  뒷받침하고 마그네틱 디스크 기반 저장은 더 낮은 IOPS를 제공하지만 기가바이트당 더 싸다** (6장,
  p.203).[^reis2022]
- 어디에 사는가와 그 귀결 — **EBS 볼륨은 인스턴스 호스트 서버와 분리해 데이터를 저장하지만 높은
  성능과 낮은 지연을 지원하기 위해 같은 존에 둔다. 이는 EC2 인스턴스가 종료될 때, 호스트 서버가
  실패할 때, 심지어 인스턴스가 삭제될 때도 EBS 볼륨이 영속하도록 허용한다. EBS 저장은 데이터
  내구성이 높은 우선순위인 데이터베이스 같은 애플리케이션에 적합하다. 덧붙여 EBS는 모든 데이터를
  적어도 두 개의 별개 호스트 기계에 복제해 디스크가 실패하면 데이터를 보호한다** (6장,
  p.203).[^reis2022]
  - 다만 보호 범위에 경계가 있다 — 그림 6-5의 설명은 **EBS 볼륨이 높은 내구성과 가용성을 위해
    여러 호스트와 디스크에 데이터를 복제하지만 가용 영역의 장애에는 복원력이 없다**고 명시한다
    (6장, p.203, 그림 6-5).[^reis2022]
- 스냅샷 — **EBS 저장 가상화는 여러 고급 기능도 지원한다. 예컨대 EBS 볼륨은 드라이브가 쓰이는
  동안 즉각적인 특정 시점 스냅샷을 허용한다. 스냅샷이 S3로 복제되는 데는 여전히 얼마간 시간이
  걸리지만, EBS는 스냅샷을 찍을 때 데이터 블록의 상태를 효과적으로 동결하면서 클라이언트 기계가
  디스크를 계속 쓰도록 허용할 수 있다. 게다가 초기 전체 백업 이후의 스냅샷은 차등적이다 — 저장
  비용과 백업 시간을 최소화하기 위해 바뀐 블록만 S3에 쓰인다** (6장, p.203).[^reis2022]
- 확장 한계 — **EBS 볼륨은 또한 고도로 확장 가능하다. 이 글을 쓰는 시점에 어떤 EBS 볼륨 클래스는
  64TiB, 256,000 IOPS, 4,000MiB/s까지 확장할 수 있다** (6장, p.204).[^reis2022]

## 로컬 인스턴스 볼륨

- 정의 — **클라우드 제공자는 가상 머신을 돌리는 호스트 서버에 물리적으로 붙은 블록 저장 볼륨도
  제공한다. 이 저장 볼륨은 일반적으로 비용이 매우 낮고(Amazon의 EC2 인스턴스 스토어의 경우 VM
  가격에 포함) 낮은 지연과 높은 IOPS를 제공한다** (6장, p.204).[^reis2022]
- 결정적 차이 — **인스턴스 스토어 볼륨은 데이터센터의 서버에 물리적으로 붙은 디스크와 본질적으로
  똑같이 행동한다. 한 가지 핵심 차이는 VM이 종료되거나 삭제될 때 로컬로 붙은 디스크의 내용이
  손실된다는 것이다 — 이 사건이 의도적 사용자 동작으로 일어났든 아니든. 이는 새 가상 머신이 다른
  고객에게 속한 디스크 내용을 읽을 수 없도록 보장한다** (6장, p.204).[^reis2022]
- 없는 것들 — **로컬로 붙은 디스크는 EBS 같은 가상화 저장 서비스가 제공하는 고급 가상화 기능을
  전혀 지원하지 않는다. 로컬로 붙은 디스크는 복제되지 않으므로 호스트 VM이 계속 도는 중에도 물리
  디스크 장애가 데이터를 잃거나 손상할 수 있다. 게다가 로컬로 붙은 볼륨은 스냅샷이나 다른 백업
  기능을 지원하지 않는다** (6장, p.204).[^reis2022]
- 그래서 캐시로 쓴다 — **이 한계에도 불구하고 로컬로 붙은 디스크는 극히 유용하다. 많은 경우 우리는
  디스크를 로컬 캐시로 쓰므로 EBS 같은 서비스의 모든 고급 가상화 기능이 필요하지 않다. 예컨대
  EC2 인스턴스에서 AWS EMR을 돌리고 있다고 하자. S3에서 데이터를 소비하고, 인스턴스에 걸쳐 도는
  분산 파일시스템에 임시로 저장하고, 데이터를 처리하고, 결과를 S3에 되쓰는 덧없는 잡을 돌리고
  있을 수 있다. EMR 파일시스템은 복제와 중복성을 내장하고 있고 영구 저장이 아니라 캐시로 기능하고
  있다. EC2 인스턴스 스토어는 이 경우에 완벽하게 적합한 해법이며, 데이터가 네트워크를 거치지 않고
  로컬에서 읽히고 처리될 수 있으므로 성능을 향상할 수 있다** (6장, p.204).[^reis2022]
- 저자들의 판단 기준 — **엔지니어가 로컬로 붙은 저장을 최악의 시나리오에서 생각해 보기를 권한다.
  로컬 디스크 장애의 결과는 무엇인가? 우발적 VM 또는 클러스터 종료는? 존이나 리전 단위 클라우드
  중단은? 로컬로 붙은 볼륨의 데이터가 손실될 때 이 시나리오 중 어느 것도 파국적 결과를 갖지
  않는다면 로컬 저장은 비용 효율적이고 성능 좋은 선택지일 수 있다. 덧붙여 단순한 완화 전략(S3에
  주기적 체크포인트 백업)이 데이터 손실을 막을 수 있다** (6장, p.205).[^reis2022]
