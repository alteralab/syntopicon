하나의 질문: **티어라는 개념은 아키텍처의 어느 층에서 무엇으로 구현되고, 그 티어링이 제대로 도는지는
무엇으로 아는가.**

## 이 페이지가 답하는 물음

- 형제 페이지 [SaaS 티어링 패턴 일곱](saas-tiering-patterns.md)이 **어떤 유형의 티어를 둘 것인가**를
  맡는다면, 이 페이지는 **그것을 어디에 어떻게 거는가**와 **그 동작을 어떻게 보는가**를 맡는다.
- 저자가 그 전환을 이렇게 적는다 — **티어링이 멀티테넌트 아키텍처의 자취에 유의미한 영향을 줄 수
  있다는 것이 또렷해졌을 테니, 이제 이 티어링 개념이 체계의 아키텍처에 적용되는 모습을 보기 시작하겠다**는
  것이다 (14장 §"Implementing Tiering", p.372).[^golding2024]

## 버전 조건

- **2024년 저술 시점**의 판정이다. **이 장에서 제품 이름이 나오는 자리가 이 절들**이고, 저자 자신이
  그 이름들을 예시로만 든다.
  - **API 관리 도구로 드는 예 셋** — **AWS의 API Gateway, Microsoft의 API Management, Google의
    Apigee**이고 **오픈 소스 도구도 이 공간에 있다**고 덧붙인다. **각각이 티어링 이야기에 자기 나름의
    변형을 더하되, 이 API 관리 도구 대다수가 요청마다 적용할 수 있는 스로틀링 정책을 정의하게 해 주는
    기제를 포함**한다 (14장 §"API Tiering", p.373).[^golding2024]
  - **서버리스 컴퓨트로 드는 예** — **AWS Lambda의 동시성(concurrency) 설정**이다 (14장,
    p.375).[^golding2024]
  - **컨테이너 쪽으로 드는 예** — **쿠버네티스의 쿼터(quotas) 기제**다 (14장, p.376).[^golding2024]
- **그 이름들이 조문을 떠받치지 않는다.** 저자가 **선택지 목록이 너무 길어 모든 가능성을 다룰 수 없으나,
  이 개념을 구체적인 기술에 이어 보는 것이 층마다 이 개념을 살려 낸다는 것이 무엇인지 감을 주는 데 도움이
  될 것 같았다**고 적는다 (14장, p.372).[^golding2024] 이 페이지도 같은 자리에 둔다 — 제품 이름은 이
  절 안에만 있고 조문은 그것에 기대지 않는다.
- `stale_after`를 두지 않는다 — 공표된 지원 종료일이 이 소스에 없다.

## 원칙은 같고 구현은 다르다

- **전제** — **티어링의 핵심 원칙은 어떤 기술에도 적용되되, 그 전략을 구현하는 세부는 환경마다 다를 수**
  있다. **컴퓨트 스택과 저장 서비스와 API 게이트웨이가 모두 티어링이 기술과 서비스에 따라 다르게 실현되는
  영역의 예**다 (14장, p.372).[^golding2024]
- **한 층에만 걸리는 것이 아니다** — **어떤 경우에는 티어링을 멀티테넌트 아키텍처의 여러 층에 걸친 서로
  다른 정책과 기법의 모음으로 구현할 수** 있다 (14장, p.372).[^golding2024]

## API 티어링

- **왜 API가 자연스러운 자리인가** — 애플리케이션의 서비스는 **클라이언트나 개발자 SDK에서 여러 연산을
  부르는 데 쓰이는 API를 떠받치게** 되고, **그 API가 멀티테넌트 아키텍처에 티어링 구성물을 들일 자연스러운
  자리**가 되는 경우가 많다. **테넌트가 애플리케이션의 서비스와 상호작용하는 방식을 빚고 제한하고 전반적으로
  통제하는 정책을 들일 기회가 여기 있다** (14장 §"API Tiering", p.373).[^golding2024]
- **저자가 흔히 본다는 구성** — **트래픽이 서비스로 어떻게 흘러들지 설정하고 기술하는 풍부한 선택지를 주는
  API 관리 도구를 쓰는 것**이고, 그 도구를 받아들이면 **환경으로 들어오는 뚜렷한 진입점 하나를 갖게 되어
  SaaS 환경에 더 보편적으로 적용될 수 있는 정책과 구성물을 들일 수** 있다 (14장, p.373).[^golding2024]
- **구성의 뼈대** (14장, p.373):[^golding2024]
  - **요청을 하는 테넌트마다 티어가 연결되고, 그 티어가 스로틀링 정책을 적용하는 데 쓰인다.**
  - **SaaS 환경의 티어마다 그 티어에서 떠받칠 처리량을 정의하는 고유한 정책이 배정**된다. 저자가 이 자리에
    쓰는 이름이 **사용 계획(usage plan)**이고, 스로틀링 정책과 같은 것으로 적는다.
  - **설정할 수 있는 값으로 드는 것 셋** — **초당 요청 수, 버스트 속도, 그리고 하루 전체 요청 할당량**이다.
  - **이 예가 특정 게이트웨이의 개념을 보이되, 그 경험을 이루는 전략과 기제는 다른 API 관리 도구가
    떠받치는 비슷한 구성물로 대체로 대응**된다. **어떤 것은 선택지를 더 주고 어떤 것은 정책을 주입하는
    방식이 다르되 순효과는 대체로 비슷**하다 (14장, p.373).[^golding2024]
- **요청을 정책에 잇는 방법이 이 절의 알맹이다** (14장, p.374):[^golding2024]
  - 그 게이트웨이에서는 **API 키로 잇는다.** **사용 계획마다 API 키가 연결되고, 주어진 API 키로 요청이
    오면 그 키가 어느 티어링 정책을 적용할지 정하는 데 쓰인다.**
  - **저자가 던지는 물음** — **테넌트마다 자기 API 키를 배정해야 하는가**이다. **그렇게 해도 되되, 그러면
    API의 클라이언트가 요청마다 그 키를 써야 해서 클라이언트 쪽으로 움직이는 부품이 더 밀려난다.**
  - **더 효율적인 길로 드는 것** — **게이트웨이에 함수(커스텀 인가자, custom authorizer)를 붙여 요청마다
    불리게 하는 것**이다. **그 함수가 들어오는 요청에서 테넌트의 티어를 꺼내고, 그 티어에 연결된 API 키가
    무엇인지 정해, 그 함수가 배정한 API 키로 요청을 처리**한다.
  - **얻는 것 둘** — **클라이언트가 API 키에 대해 아무것도 알 필요가 없게** 되고, **티어마다 API 키 하나만
    있으면** 된다.
- **저자가 일반화하는 기준 하나** — **정책을 한곳에서 설정할 수 있게 하고 클라이언트가 스로틀링 컨텍스트를
  주입하거나 적용할 필요를 제한하는 전략을 언제나 찾겠다**는 것이다 (14장, p.374).[^golding2024]
- **그림에만 있음** — 그림 14-3은 사용 계획 셋의 값을 실제 숫자로 적는다. **기본 티어는 초당 50요청·버스트
  50요청·하루 1,000요청, 어드밴스드 티어는 100·100·2,000, 프리미엄 티어는 200·200·3,000**이다. **본문은
  설정할 수 있는 항목 셋의 이름만 말하고 어떤 값도 들지 않는다** (14장, 그림 14-3,
  p.374).[^golding2024]
- **인가자 함수는 이 책의 앞 장에서 다른 목적으로 이미 쓰였다** — 서버리스 라우팅에서 경로를 여닫는 쪽의
  자리는
  [서버리스 위의 테넌트 온보딩 자동화와 격리 넷과 동시성](tenant-onboarding-isolation-and-concurrency-on-serverless.md)이다.
  **같은 기제가 여기서는 티어를 키로 바꾸는 번역기로 쓰인다.**

## 컴퓨트 티어링

- **왜 컴퓨트인가** — **컴퓨트 층에서는 해법의 티어링 요건에 따라 서로 다른 확장·처리량·시끄러운 이웃·격리
  전략을 들일 수** 있다. **선택지는 쓰는 컴퓨트 스택과 해법의 배포 모델을 비롯한 여러 요인에 따라 달라지되,
  컴퓨트가 해법 활동의 상당 부분의 중심에 있는 경우가 많아 티어링 기제를 들일 자연스러운 자리**가 된다
  (14장 §"Compute Tiering", p.375).[^golding2024]
- **서버리스 쪽 — 확장의 단위가 함수다** (14장, p.375):[^golding2024]
  - **함수는 테넌트의 다양한 워크로드를 떠받치려고 확장되어야** 하고, **그 확장이 동시성 설정으로 구성되며
    그 설정이 함수의 동시 실행을 몇 개까지 허용할지 정한다.**
  - **풀 환경만으로는 티어링이 불가능하다** — **모든 테넌트가 해법을 구현하는 서버리스 함수를 전부 공유하는
    풀 환경이라면 어떤 종류의 컴퓨트 기반 티어링 모델도 내줄 방법이 없다.** **모든 테넌트가 같은 함수 묶음을
    두고 다투게** 되고, **기본 티어 테넌트가 함수 동시성을 포화시키는 요청 폭주를 던지면 결국 프리미엄 티어
    테넌트에게 나쁜 영향이 간다.**
  - **해법은 배포를 가르는 것이다** — **서로 다른 동시성 설정으로 함수를 따로 배포**해야 하고, **그러면
    해법의 함수를 세 벌 배포하고 배포 중에 서로 다른 동시성 설정으로 구성**하게 된다 (14장,
    p.376).[^golding2024]
  - **저자가 드는 값** — **기본 티어는 동시성 100**으로 **그 티어의 모든 테넌트를 합쳐 동시 함수 실행이
    100개까지만** 가능하고, **어드밴스드 티어는 300**이며, **프리미엄 티어는 값이 없어 남은 동시성이 전부
    이 티어에 배정**된다. **기본 상한이 1,000이라면 프리미엄 티어 테넌트는 600의 동시성을 가질 수** 있다
    (14장, p.376).[^golding2024]
  - **그림에만 있음** — 그림 14-4는 그 설정의 이름을 **예약 동시성(reserve concurrency)**이라 적고
    프리미엄 티어의 값을 **예약되지 않은 전부**라고 적는다. **본문은 "동시성 설정"이라고만 부르고 프리미엄
    티어에는 값이 없다고 적는다** (14장, 그림 14-4, p.375).[^golding2024]
- **컨테이너 쪽 — 완전히 다른 구성물을 쓴다** (14장, pp.376–377):[^golding2024]
  - 저자가 드는 예에서 **테넌트가 두 네임스페이스에 나뉘어 돈다.** 하나는 **컴퓨트 자원을 모든 테넌트가
    공유하는 풀 컴퓨트 모델**이고, 다른 하나는 **한 테넌트의 컴퓨트 자원 전부가 전용 네임스페이스에서 도는
    사일로 컴퓨트 모델**이다. **그 두 네임스페이스가 서로 다른 티어에 연결**된다 — **기본 티어 테넌트가 풀
    쪽에서 돌고 사일로 네임스페이스가 플래티넘 티어에 연결**된다.
  - **두 티어 또는 네임스페이스가 티어링 요건에 따라 아주 다른 확장 프로필을 요구할 수** 있고, **자원
    쿼터(resource quotas)가 등장하는 자리가 여기**다. **네임스페이스마다 쿼터 설정을 구성해 연결**하고,
    팀은 **그 쿼터를 서로 다른 설정으로 구성해 네임스페이스 안 컴퓨트 자원의 규모와 성능에 영향을 줄 수**
    있다.
  - **그림에만 있음** — 그림 14-5는 쿼터에 든 항목을 **CPU 한도**와 **메모리 한도** 둘로 적는다. **본문은
    "서로 다른 설정"이라고만 하고 어떤 항목인지 말하지 않는다** (14장, 그림 14-5, p.376).[^golding2024]
- **티어가 없어도 이 정책은 둔다** — **사업이 티어링 모델을 받아들이지 않았더라도 예상치 못한 워크로드가
  체계를 넘어뜨리는 것을 막을 정책을 어떻게 들일지는 여전히 보겠다**고 적는다 (14장,
  p.377).[^golding2024] 이 문장이 앞 절 곁주의 **내부 전용 기제**와 같은 말이다.

## 저장 티어링

- **왜 저장소인가** — **저장 서비스, 특히 클라우드 기반 관리형 저장소는 저장 경험의 처리량과 규모를 구성할
  수 있는 여러 손잡이를 만드는 사람에게 주는 편**이고, **그 설정으로 테넌트 페르소나의 요건을 떠받치는 데
  필요한 티어링 모델을 정의할 수** 있다 (14장 §"Storage Tiering", p.377).[^golding2024]
- **실현되는 갈래가 둘이다** (14장, p.377):[^golding2024]
  - **저장소가 풀이라면** — **티어마다 읽기·쓰기 활동을 어떻게 제한하거나 제약할지**를 보게 되고, 그것이
    **공유 저장 구성물에 접근하는 테넌트에게 서로 다른 수준의 성능을 내주게** 한다.
  - **다른 하나는 테넌트에게 사일로 저장소를 내주는 데 초점을 둔 모델**이다.
- **저자가 드는 배치** (14장, pp.377–379):[^golding2024]
  - **기본 티어가 풀 저장 모델**이고 **그 저장소는 많은 테넌트가 공유할 수 있어 기본 티어에 합의된 요건을
    충족하는 설정으로 구성**되어야 한다.
  - **어드밴스드 티어도 풀 저장 모델**을 쓰고 **대부분의 면에서 첫 티어와 같되 더 나은 성능과 규모와
    처리량을 내주는 설정으로 구성**된다.
  - **그다음 테넌트들은 사일로 저장소**를 쓰되 **같은 확장·성능 설정을 받는다.** **데이터가 따로 저장될
    뿐 성능과 규모 설정은 같다**는 것이다.
  - **저자가 본 변형 하나와 그 경고** — **그 사일로 테넌트에게 별도의 정책을 내주는 팀을 본 적이 있다**고
    적으며, **가능하되 일회성 정책을 두면 시간이 가면서 운영 효율을 훼손할 수** 있다고 적는다. **테넌트별
    설정을 따져야 할 때마다 운영 자취에 부담이 더해진다**는 것이다.
- **사일로·풀을 데이터 전체에 걸지 말라는 처방** (14장, p.379):[^golding2024]
  - **어떤 SaaS 제공자는 사일로냐 풀이냐의 티어링 전략을 테넌트의 데이터 전체에 전역으로 적용해 그 테넌트에
    연결된 데이터를 모두 사일로해야 한다고 가정**한다. **타당한 시나리오이되 극단적인 경우여야** 한다.
  - 대신 **체계에 있는 데이터의 계열을 보고, 데이터의 성격과 접근 패턴을 비롯한 것에 따라 어느 범주의
    데이터가 사일로되어야 할지 알아내야** 한다. **데이터의 부분집합만 사일로하면 되는 경우를 발견할 수**
    있다.
  - **얻는 것** — **일부 데이터를 풀 모델로 둘 수 있어 운영 복잡도를 줄이고 환경의 비용 자취를 낮출 수**
    있다.
  - 이 처방은 이 책 8장의 조항과 같은 계열이다 — 저장 기술을 서비스마다 고르라는 쪽의 자리는
    [멀티테넌트 데이터 파티셔닝의 기초와 적정 크기화](multi-tenant-data-partitioning-fundamentals.md)와
    [저장 기술별 파티셔닝과 테넌트 샤딩](storage-technology-partitioning-and-tenant-sharding.md)이다.
- **성능 말고 다른 두 축** (14장, p.379):[^golding2024]
  - **용량** — **티어를 테넌트의 저장 용량을 통제하는 방법으로 쓰는** 조직이 있을 수 있다. **테넌트 데이터의
    자취가 값어치와 강한 상관을 갖는 영역과 환경이 분명히 있고**, 그런 경우 **티어 수준마다 용량 한도를 걸게**
    된다.
  - **보존** — **보존 정책을 티어마다 구별하는 것**이고, **데이터를 남겨 두는 것이 SaaS 환경의 비용 프로필에
    영향을 주는 영역에서 특히** 그렇다.
- **그림에만 있음** — 그림 14-6은 저장 정책에 든 항목을 **읽기 IOPS·쓰기 IOPS·CPU·메모리** 넷으로 적되
  값은 모두 자리표(AAA·BBB 따위)로 둔다. 사일로 쪽 둘에는 같은 자리표 값이 들어가 **본문이 말한 "같은 설정"이
  그림에서도 같다.** 티어 이름은 **기본·어드밴스드·플래티넘**이다 (14장, 그림 14-6,
  p.378).[^golding2024]
  - **본문과 그림이 어긋나는 자리 하나** — 본문은 **다이어그램의 아래쪽을 따라 정책을 정의했다**고 적고
    **왼쪽에서 오른쪽으로 훑어보라**고 적는데, **그림은 두 줄로 배치되어 아래쪽 줄이 사일로 티어 둘**이다.
    사실만 적고 어느 쪽이 맞는지 단정하지 않는다.

## 배포 모델과 티어링

- **이미 나온 주제를 일반화한다** — **컴퓨트와 저장 티어링 논의에서 테넌트를 위해 별도 인프라를 배포하고
  거기에 뚜렷한 확장·성능 정책을 붙이는 것이 이미 나타났고**, 그것은 **환경의 어떤 인프라에도 적용될 수 있는
  고전적 주제**다. 저자가 드는 예가 **테넌트 티어마다 내주고 싶은 메시지 처리량을 떠받치도록 별도의 메시징
  인프라를 배포하고 구성하는 것**이다 (14장 §"Deployment Models and Tiering", p.380).[^golding2024]
- **조문으로 세운다** — **체계의 요소마다 티어링이 그 배포 모델에 어떤 영향을 줄 수 있는지 자문해야** 한다
  (14장, p.380).[^golding2024]
- **마이크로서비스에도 같은 사고방식을 건다** (14장, p.380):[^golding2024]
  - 저자가 드는 예에서 **전자상거래 SaaS 환경의 마이크로서비스 여섯** 가운데 **프리미엄 티어 테넌트의
    요건과 워크로드 기대 때문에 셋을 사일로 모델로 내주기로** 하고 **프리미엄 티어 테넌트마다 그 서비스의
    자기 배포를 갖게** 한다. **기본 티어 테넌트는 그 서비스가 풀 모델로 도는 것을 받아들일 의향이 있고**,
    **그 자원은 기본 티어 테넌트들의 합산 소비에 따라 공유되고 확장**된다.
  - **어느 티어에도 속하지 않는 서비스 묶음이 따로 있다** — **풀 모델로 배포되어 기본 티어와 프리미엄 티어
    테넌트가 함께 공유**한다 (14장, p.381).[^golding2024]
- **저자가 뽑는 요점 둘** (14장, p.381):[^golding2024]
  - **티어링 전략이 특정 인프라 자원과 성능 정책 묶음에 직접 대응되어야 하는 것은 아니다.** 그 마이크로서비스는
    **컴퓨트와 저장소와 메시징을 비롯한 인프라 자원으로 조합될 수** 있고, **이 모드의 티어링은 서비스의 배포
    프로필로 해법의 티어링 경험을 정의하는 더 성긴(coarse-grained) 모델**이다.
  - **그 배포 모델이 전부 아니면 전무의 전략이 아니다.** **티어링 요건에 따라 배포되는 마이크로서비스의 묶음을
    정의하는 티어링 모델을 만들 수** 있고, **어떤 것은 풀이고 어떤 것은 사일로이고 어떤 것은 공유**일 수 있다.
  - 이 배치는 이 책 3장의 혼합 모드와 같은 모양이다 — 그 자리는
    [풀 스택 풀 모델과 배포 변형 셋](full-stack-pool-and-deployment-variations.md)이다.
- **그림에만 있음** — 그림 14-7은 마이크로서비스 여섯의 이름을 적는다. 티어에 걸리는 셋이 **제품·주문·장바구니**
  이고 모든 테넌트가 공유하는 셋이 **평점·세금·배송**이다. 열 제목은 **기본 티어 테넌트 · 모든 테넌트 ·
  프리미엄 티어 테넌트**다. 본문은 여섯의 이름을 모두 부르되 **열 제목의 가운데 칸이 "모든 테넌트"라는 것은
  그림만이 보인다** (14장, 그림 14-7, p.380).[^golding2024]

## 스로틀링과 테넌트 경험

- **저자가 자기 전략에 스스로 이의를 제기한다** — **기본 티어 테넌트가 이 정책들로 일부러 경험이 깎이는
  것**이고, **테넌트의 경험을 제한하는 것이 좋은 생각인지 묻는 것은 정당**하며, **이 접근이 훌륭한 서비스
  경험을 전달한다는 전체 사명을 훼손한다고 쉽게 주장할 수도** 있다 (14장 §"Throttling and Tenant
  Experience", p.381).[^golding2024]
- **답이 둘로 나온다** (14장, p.381):[^golding2024]
  - **하나는 균형의 문제다** — **티어링은 모든 테넌트에게 좋은 경험을 주는 것과, 테넌트가 아무 제약이나 한도
    없이 부하를 지우고 자원을 쓰게 두는 것이 비현실적이라는 것을 인정하는 것 사이의 긴장점을 찾는 일**이다.
  - **다른 하나는 가용성이다** — **어떤 테넌트가 해법에 과도한 부하를 지워 다른 테넌트의 경험에 영향을 주기
    시작할 수 있다고 가정해야** 하고, **실제로 체계의 규모를 늘여 일부나 전부를 내려앉게 만드는 시나리오를
    만들 수도** 있다. 그래서 **어떤 면에서 티어링은 테넌트가 과도하다고 판정된 부하를 지우는 것을 막는 데
    쓰이는 전역 성능·가용성 전략의 일부**이기도 하다.
- **비용 쪽 긴장이 하나 더 있다** — **기본 티어에 명시적인 제약이 있고 새 테넌트가 그 모델을 고른다면, 그
  경험의 한도를 분명히 하는 것이 자기 일**이라는 것이고, **티어드 모델에 정말로 전념한다면 테넌트가 자기가
  고른 티어에 따라 제약을 만날 수 있는 모델에도 전념해야** 한다. **핵심은 테넌트에게 뜻이 통하고 각 티어에
  겨냥한 경험과 맞는 제약을 세우는 것**이다 (14장, p.381).[^golding2024]
- **티어가 없어도 정책은 필요하다** — **순수하게 소비 기반 모델에 기대어 소비 수준에 따른 티어드 가격만 갖는
  제공자**라도 **서로 다른 수준의 처리량을 내주는 한도를 떠받치는 티어링 정책의 적용을 여전히 생각해야** 할 수
  있다. **대체로 어딘가 밑에서, 고객이 볼 수 없더라도, 운영 건강을 유지하는 쪽에 가까운 정책을 두어야 할 수**
  있고 **그 정책은 티어에 아무런 대응이 없을 수도** 있다 (14장, p.382).[^golding2024]

## 티어 관리

- **티어 자체는 단순한 개념이다** — **해법 어딘가에 체계가 떠받치는 티어 목록의 표현이 있을 것**이고,
  **그 티어가 추가 속성을 담을 수는 있으나 이 정보를 저장하고 관리하는 데 복잡한 것은 많지 않다** (14장
  §"Tier Management", p.382).[^golding2024]
- **저자가 자주 받는다는 물음은 거처다** — **이 티어의 관리가 어디에 살아야 하는가**이고, **대부분의 경우
  해법의 컨트롤 플레인의 일부로 관리되는 것이 가장 말이 된다**고 답한다. **결국 체계의 티어 목록을 유지하는
  기본 연산 묶음을 가진 또 하나의 마이크로서비스로 드러나게** 된다 (14장, p.382).[^golding2024]
- **청구 체계와의 연결이 남는다** — **티어가 환경에 자리 잡고 관리되더라도, 티어 관리와 청구 체계 안 티어
  표현 사이에 존재할 수 있는 연결을 어떻게 관리할지 따져야** 한다. **다행히 이 데이터는 많이 바뀌지 않되**,
  **둘 사이의 연결을 어떻게 관리하고 둘이 계속 동기화되게 할지는 정해야** 한다 (14장,
  p.382).[^golding2024]
- 컨트롤 플레인이 테넌트 상태의 단일 거처라는 조항의 자리는
  [테넌트 관리와 테넌트 수명 주기](tenant-management-and-tenant-lifecycle.md)다. **티어 관리는 그
  서비스의 형제로 놓인다.**

## 운영과 티어링

- **티어가 운영의 렌즈가 된다** — **개별 테넌트에게 무슨 일이 일어나는지 운영 화면에서 알고 싶은 것은
  분명하되**, **활동과 규모와 비용을 비롯한 환경의 속성을 티어 기반 렌즈로 분석하고 싶을 때가 있다** (14장
  §"Operations and Tiering", p.382).[^golding2024] 그 판정의 12장 쪽 자리는
  [테넌트 인지 운영 콘솔과 멀티테넌트 배포 자동화](tenant-aware-operations-console-and-deployment-automation.md)다.
- **이 절이 더하는 것은 티어링 자체를 재는 일이다** — **그 티어 경계를 정의하면 티어링 체계가 어떻게 돌고
  있는지에 대한 통찰을 주는 도구와 기제도 가져야** 한다. 저자가 드는 물음이 넷이다 (14장,
  p.382):[^golding2024]
  - **알맞은 때에 테넌트를 스로틀링하고 있는가.**
  - **스로틀링 정책이 효과적인가.**
  - **티어링 정책에 영향을 받는 테넌트가 얼마나 잦은가.**
  - **정책이 너무 공격적이거나 너무 느슨한가.**
- **티어링 모델이 운영 통찰에 따라 진화할 것을 예상하라** — **새 테넌트가 들어오고 테넌트 페르소나와 그
  소비 패턴의 더 풍부한 프로필이 생기면서 티어링 모델을 다듬을 기회를 보게 될 공산이 크다**는 것이고, 이것이
  **티어링 동작을 평가하게 해 줄 운영 지표로 체계를 계측하겠다는 강한 약속의 필요를 더 강조**한다 (14장,
  pp.382–383).[^golding2024]
- **저자가 본 두 단계의 실무** (14장, p.383):[^golding2024]
  - **경보를 들여 테넌트가 티어링 정책에 다가가거나 그것을 건드릴 때 더 즉각적인 가시성을 갖는 팀**이 있다.
  - **단계적 티어링 모델을 쓰는 팀도 있다** — **테넌트가 경계에 닿았을 때 실제로 스로틀링을 적용하지 않고
    알림만 올리고**, **그 위에 실제로 스로틀링을 적용하는 내부 수준의 하드 한도를 따로** 둔다. **테넌트에게
    경계에 다가가고 있음을 알릴 수 있는, 조금 더 통제된 경험**을 갖게 해 준다.
  - **모든 정책에 실용적이지는 않다**고 단서를 붙이되 **고려할 만한 또 하나의 접근**이라 적는다.
  - **핵심은 운영 팀에 티어링 추세의 가시성을 주는 더 선제적인 접근을 취하는 것**이다.
- **티어가 배포의 축이 되는 자리** (14장, p.383):[^golding2024]
  - **티어링 전략의 일부로 테넌트에게 전용 자원을 내주면, 배포 기제가 그 티어링 설정을 써서 자원이 아키텍처의
    어디에 어떻게 놓일지 정해야** 한다.
  - **티어링은 단계적 롤아웃 전략의 일부로도 쓰일 수** 있다. **한 티어의 테넌트에게 새 판을 카나리 릴리스로
    내보내고, 그 릴리스의 성공에 따라 나머지 티어로 내보낼 수** 있다.
  - **두 방향이 다 유효하다고 적는다** — **프리미엄 티어 테넌트로의 롤아웃을 피하는 방어적 전술**로 쓸 수도
    있고, **반대로 프리미엄 티어 테넌트에게 먼저 내보내 풀된 기본 티어 테넌트의 큰 묶음에 배포할 때 따라올
    더 큰 규모의 영향을 피하는 쪽**으로 주장할 수도 있다. **여기서의 전략은 환경의 필요에 따라 크게 달라진다.**
  - **저자가 어느 쪽을 고르라고 하지 않는다.** 이것은 12장이 남긴 미해결 물음과 같은 모양이다 — 공유 인프라에서
    카나리가 무엇을 뜻하는가라는 물음에도 저자가 기준을 세우지 않았다.

## 맺음이 남기는 판정

- **티어링의 자리매김** — **모든 SaaS 환경에 맞지 않을 수 있으나, 많은 경우 사업이 여러 테넌트 페르소나와
  시장 구획을 겨냥하게 해 주는 아키텍처·비용·패키징 구성물을 짓게 해 주는 필수 도구**다 (14장,
  p.383).[^golding2024]
- **아키텍트가 사업 쪽 상대에게 주는 선택지** — **티어링을 아키텍트가 쓸 수 있는 더 값어치 있는 도구 가운데
  하나로 본다**고 적는다. **한편으로는 사업이 테넌트 페르소나의 요구에 대응할 유연성을 주는 일이고, 다른
  한편으로는 테넌트가 환경에 부하를 지우는 방식에 더 단단한 통제를 두는 구성물을 들이는 일**이다 (14장,
  p.384).[^golding2024]
- **확장의 효율에 거는 조건** — **체계를 확장하도록 짓되 그것이 떠받쳐야 할 테넌트 페르소나의 가격·패키징
  프로필에 따라 효율적으로 확장하기를 바란다**는 것이고, **모든 테넌트에게 원하는 만큼 체계를 쓸 자유를 주는
  것이 솔깃하게 들릴 수 있으나 그것이 사업에 지울 운영·비용 효율의 부담을 상상할 수** 있다 (14장,
  p.384).[^golding2024]
- **마지막 조항이 티어 없는 환경에도 걸린다** — **티어링 없이도 테넌트가 체계를 내려앉게 하거나 다른 테넌트의
  경험에 영향을 줄 속도로 자원을 쓸 수 없도록 보장하는 통제를 들이는 것을 여전히 고려하고 싶을 것**이다
  (14장, p.384).[^golding2024]

## 스로틀링을 적는 이 KB의 다른 서술과 맞대기

- **같은 기제가 이 KB에 이미 있되 목적이 다르다.** 어느 쌍도 사실 충돌이 아니다.

| 서술 | 무엇을 가르는가 | 무엇을 막으려는가 |
|---|---|---|
| [API 요청 수명 패턴](../concepts/api-request-lifecycle-patterns.md)의 속도 제한 | 클라이언트(예로 드는 것이 IP 주소) | **남용과 서비스 거부** |
| [API 게이트웨이의 규정과 기능과 배치](../concepts/api-gateway-capabilities-and-deployment.md)의 속도 제한 | 사용자 | **과용과 남용** |
| [카프카 클라이언트 쿼터](../concepts/kafka-client-quotas.md) | 클라이언트 또는 사용자 | **한 클라이언트가 클러스터를 압도하는 것** |
| 이 페이지의 스로틀링 | **테넌트의 티어** | **가격 대비 소비의 어긋남**과 시끄러운 이웃 |

- **그래서 이 소스가 더하는 것이 또렷하다** — 위 셋이 스로틀링을 **방어**로 세우는 반면, 이 소스는 그것을
  **상품 구획의 집행 기제**로 세운다. **같은 문단에서 방어의 목적도 함께 인정**한다는 것이 특징이고, 스로틀링
  절이 그것을 **전역 성능·가용성 전략의 일부**라고 적는 대목이 두 목적이 겹치는 자리다.
- **게이트웨이 쪽 서술과 가장 가깝다.** [API 게이트웨이의 규정과 기능과 배치](../concepts/api-gateway-capabilities-and-deployment.md)가
  게이트웨이의 여섯째 쓰임으로 **개발자 플랜과 속도 제한 설정을 가능하게 하는 결제 포털**을 드는데, **이 소스의
  사용 계획이 그 개발자 플랜과 같은 구성물**이다. 두 소스는 서로를 호명하지 않는다.
- **카프카 쪽 쿼터와 갈리는 자리 하나** — 그쪽은 **스로틀링이 조용해서 에러 코드가 아니라 지표로만 알 수 있다**는
  점을 조문으로 세운다. 이 소스는 반대쪽에서 같은 문제를 만난다 — **테넌트가 경계에 닿았음을 알리는 단계적
  티어링**이 그 답이다. **두 소스가 서로를 모르는 채 같은 빈자리를 가리킨다.**

## 이 페이지의 사각

- **저장 티어링의 값이 자리표로만 있다.** 그림에도 본문에도 실제 IOPS나 용량 값이 없다.
- **정책이 너무 공격적인지 느슨한지를 판정하는 잣대가 없다.** 물음만 세우고 답하는 지표를 세우지 않는다.
- **단계적 티어링의 두 수준을 얼마나 벌릴지가 없다.** 알림 수준과 하드 한도의 간격을 정하는 기준이 없다.
- **카나리의 축으로 어느 티어를 먼저 고를지가 미결로 남는다.** 두 방향 다 유효하다고만 적는다.
- **티어 관리 서비스와 청구 체계를 동기화하는 기제가 없다.** 동기화가 필요하다고만 적는다.
- **티어를 바꿀 때 돌고 있는 테넌트에게 무엇이 일어나는지가 이 장에 없다.** 그 절차는 이 책의 5장이
  테넌트 수명 주기 쪽에서 다룬다.
