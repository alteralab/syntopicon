하나의 질문: **수명 주기의 어느 단계에도 속하지 않으면서 모든 단계에 걸리는 것들을 무엇이라
부르고, 그것이 데이터 엔지니어에게 무엇을 요구하는가.**

## 저류라는 범주

- 정의 — **기반암 노릇을 하는 것이 저류(undercurrents)다. 데이터 엔지니어링 수명 주기의 여러
  단계를 가로지르는 보안·데이터 관리·DataOps·데이터 아키텍처·오케스트레이션·소프트웨어
  엔지니어링이 그것이다. 데이터 엔지니어링 수명 주기의 어느 부분도 이 저류 없이는 적절히
  기능할 수 없다** (2장, p.34).[^reis2022]
- 왜 이 범주가 생겼는가 — **데이터 엔지니어링의 이전 주기가 단순히 기술 계층에 집중했다면,
  도구와 실무의 계속된 추상화와 단순화가 그 초점을 옮겼다. 데이터 엔지니어링은 이제 도구와
  기술보다 훨씬 많은 것을 아우른다. 이 분야는 지금 가치 사슬을 올라가며, 데이터 관리·비용
  최적화 같은 전통적 엔터프라이즈 실무와 DataOps 같은 새 실무를 통합하고 있다** (2장,
  pp.48–49).[^reis2022]

## 보안

- 순서의 의미 — **보안은 데이터 엔지니어에게 최우선이어야 하고, 그것을 무시하는 이는 위험을
  감수하는 것이다. 그래서 보안이 첫 저류다** (2장, p.49).[^reis2022]
- 최소 권한 — **데이터 엔지니어는 데이터 보안과 접근 보안 양쪽을 이해하고 최소 권한의 원칙
  (principle of least privilege)을 실천해야 한다. 최소 권한의 원칙은 사용자나 시스템에 의도된
  기능을 수행하는 데 필수적인 데이터와 자원에만 접근을 주는 것을 뜻한다. 보안 경험이 적은
  데이터 엔지니어에게서 보는 흔한 안티패턴은 모든 사용자에게 관리자 접근을 주는 것이다. 이는
  터지기를 기다리는 재앙이다!** (2장, p.49).[^reis2022]
- 자기 자신에게도 적용한다 — **눈에 보이는 파일을 표준 사용자 접근으로 찾고 있을 뿐이라면 루트
  셸에서 작업하지 마라. 더 낮은 역할로 테이블을 질의할 때 데이터베이스의 슈퍼유저 역할을 쓰지
  마라. 최소 권한의 원칙을 우리 자신에게 부과하는 것은 우발적 손상을 막고 보안 우선 사고를
  유지하게 해 준다** (2장, p.49).[^reis2022]
- 가장 큰 취약점 — **사람과 조직 구조는 어느 회사에서나 늘 가장 큰 보안 취약점이다. 언론에서
  주요 보안 침해 소식을 들을 때 흔히 밝혀지는 것은 회사의 누군가가 기본적인 예방책을
  무시했거나, 피싱 공격의 희생자가 됐거나, 달리 무책임하게 행동했다는 것이다. 데이터 보안의
  첫 방어선은 조직에 스며드는 보안 문화를 만드는 것이다** (2장, p.49).[^reis2022]
- 시점의 문제이기도 하다 — **데이터 보안은 타이밍에 관한 것이기도 하다 — 접근해야 하는 바로
  그 사람과 시스템에, 그들의 일을 수행하는 데 필요한 기간에만 데이터 접근을 제공하는 것이다.
  데이터는 암호화·토큰화·데이터 마스킹·난독화, 그리고 단순하고 견고한 접근 통제를 써서 이동
  중(in flight)과 정지 상태(at rest) 양쪽에서 원치 않는 가시성으로부터 보호돼야 한다** (2장,
  p.50).[^reis2022]
- 요구되는 지식 — **데이터 엔지니어는 유능한 보안 관리자여야 한다. 보안이 그들의 영역에 들기
  때문이다. 사용자·아이덴티티 접근 관리(IAM) 역할, 정책, 그룹, 네트워크 보안, 비밀번호 정책,
  암호화에 대한 지식이 시작하기 좋은 자리다** (2장, p.50).[^reis2022]

## 단단한 경계에서 제로 트러스트로

3장이 같은 저류를 아키텍처 원칙("보안을 우선한다")으로 다시 놓고 두 모델을 든다 — **제로 트러스트
보안(zero-trust security)과 공유 책임 보안 모델(shared responsibility security model)이며, 이
둘은 클라우드 네이티브 아키텍처에 밀접히 정렬된다** (3장, p.84).[^reis2022]

- 먼저 옛 모델을 이해해야 한다 — Google Cloud의 다섯 원칙이 서술하는 전통적 모델의 한계를 인용한다
  (3장, p.84):[^reis2022]

> Traditional architectures place a lot of faith in perimeter security, crudely a hard‐
> ened network perimeter with "trusted things" inside and "untrusted things" outside.
> Unfortunately, this approach has always been vulnerable to insider attacks, as well as
> external threats such as spear phishing.

- 저자들이 드는 비유 — **1996년 영화 〈미션 임파서블〉이 단단한 경계 보안 모델과 그 한계의 완벽한
  예를 보여 준다. 영화에서 CIA는 극도로 엄격한 물리 보안을 갖춘 방 안의 저장 시스템에 고도로 민감한
  데이터를 둔다. 이선 헌트는 CIA 본부에 잠입해 인간 표적을 이용해 저장 시스템에 물리적으로 접근한다.
  일단 보안 구역 안에 들어가면 그는 비교적 쉽게 데이터를 유출한다** (3장, p.84).[^reis2022]
- 그것이 현실의 패턴이다 — **적어도 10년 동안 놀라운 언론 보도들이 강화된 조직 보안 경계 안의 인간
  표적을 악용하는 보안 침해의 커져 가는 위협을 알려 왔다. 직원들이 고도로 안전한 기업 네트워크에서
  일하는 와중에도 그들은 이메일과 모바일 기기를 통해 바깥 세계와 연결된 채로 남는다. 외부 위협이
  사실상 내부 위협이 된다** (3장, p.84).[^reis2022]
- 클라우드에서는 더 무너진다 — **클라우드 네이티브 환경에서 강화된 경계라는 관념은 더욱 침식된다.
  모든 자산이 어느 정도는 바깥 세계에 연결돼 있다. 가상 사설 클라우드(VPC) 네트워크는 외부 연결
  없이 정의될 수 있지만, 엔지니어가 이 네트워크를 정의하는 데 쓰는 API 제어 평면(control plane)은
  여전히 인터넷을 마주한다** (3장, p.84).[^reis2022]

## 공유 책임 모델

- **아마존은 공유 책임 모델을 강조하는데, 이는 보안을 클라우드의(of the cloud) 보안과 클라우드
  안의(in the cloud) 보안으로 나눈다** (3장, p.84).[^reis2022] 양쪽의 분담은 원문을 직인용한다
  (3장, pp.84–85):[^reis2022]

> AWS is responsible for protecting the infrastructure that runs AWS services in the
> AWS Cloud. AWS also provides you with services that you can use securely.
>
> Your responsibility is determined by the AWS service that you use. You are also
> responsible for other factors including the sensitivity of your data, your organization's
> requirements, and applicable laws and regulations.

- 일반화 — **일반적으로 모든 클라우드 제공자는 어떤 형태로든 이 공유 책임 모델로 운영된다. 그들은
  발행된 명세에 따라 자기 서비스를 보안한다. 그럼에도 애플리케이션과 데이터를 위한 보안 모델을
  설계하고 그 모델을 실현하기 위해 클라우드 능력을 활용하는 것은 궁극적으로 사용자의 책임이다**
  (3장, p.85).[^reis2022] 이 모델이 얹히는 계층 구조는
  [클라우드 네이티브 아키텍처](../concepts/cloud-native-architecture.md)에 있다.

## 데이터 엔지니어는 보안 엔지니어다

- 책임이 이동했다 — **2022년 저술 시점 기업 세계에서 보안에 대한 명령-통제식 접근은 꽤 흔하며, 여기서 보안·
  네트워킹 팀이 경계와 일반 보안 실무를 관리한다. 클라우드는 이 책임을 명시적으로 보안 역할에 있지
  않은 엔지니어에게 밀어낸다. 이 책임 때문에, 그리고 단단한 보안 경계의 더 일반적인 침식과 함께,
  모든 데이터 엔지니어는 자신을 보안 엔지니어로 여겨야 한다** (3장, p.85).[^reis2022]
- 결과가 구체적이다 — **이 새로운 암묵적 책임을 떠맡지 못하면 끔찍한 결과로 이어질 수 있다. 수많은
  데이터 침해가 Amazon S3 버킷을 공개 접근으로 설정한 단순한 실수에서 비롯됐다. 데이터를 다루는
  이들은 자신이 궁극적으로 그것을 보안할 책임이 있다고 가정해야 한다** (3장, p.85).[^reis2022] 위
  [보안](#보안) 절의 최소 권한 원칙이 실제로 위반되는 자리다.

## 보안을 사람·프로세스·기술로 다시 놓기

10장이 이 저류 하나만을 한 장으로 다시 열며 순서를 명시한다.

- 왜 다시 다루는가 — **보안은 데이터 엔지니어링 실무에 사활적이다. 이는 눈부시게 자명해야 하지만
  우리는 데이터 엔지니어가 얼마나 자주 보안을 나중 생각으로 여기는지에 끊임없이 놀란다. 우리는
  보안이 데이터 엔지니어가 자기 일의 모든 측면과 데이터 엔지니어링 수명 주기의 모든 단계에서 가장
  먼저 생각해야 할 것이라고 믿는다. 한 번의 보안 침해나 데이터 유출이 당신의 업무를 물에 잠기게
  할 수 있다. 그것이 당신 잘못이라면 당신의 경력과 평판이 망가진다** (10장, p.369).[^reis2022]
- 프라이버시와의 관계 — **보안은 프라이버시의 핵심 재료다. 프라이버시는 오랫동안 기업 정보 기술
  공간에서 신뢰에 결정적이었다. 엔지니어는 직간접적으로 사람들의 사생활과 관련된 데이터를 다룬다.
  여기에는 재무 정보, 사적 통신(이메일·문자·전화)에 관한 데이터, 병력, 교육 기록, 직업 이력이
  포함된다. 이 정보를 유출하거나 오용한 회사는 침해가 드러났을 때 스스로가 기피 대상이 됐음을 알게
  될 수 있다** (10장, p.369).[^reis2022] 프라이버시를 권리의 이전으로 보는 축은
  [결정권으로서의 프라이버시](../concepts/privacy-as-a-decision-right.md)에 있다.
- 법률이 배경이다 — **점점 더 프라이버시는 법적으로 유의한 문제다. 예컨대 가족 교육 권리와 프라이버시
  법(FERPA)이 1970년대에 미국에서 발효됐고, 건강보험 이동성과 책임법(HIPAA)이 1990년대에 뒤따랐으며,
  GDPR이 2010년대 중반 유럽에서 통과됐다. 여러 미국 기반 프라이버시 법안이 통과됐거나 곧 통과될
  것이다. 이는 프라이버시 관련 법령의 아주 작은 표본일 뿐이다(그리고 우리는 이것이 시작에 불과하다고
  믿는다). 그럼에도 이 법 중 어느 것을 위반하든 처벌은 유의할 수 있고 업무에 파괴적이기까지 하다**
  (10장, p.369).[^reis2022] GDPR이 요구하는 동의의 내용은
  [감시와 동의](../concepts/surveillance-and-consent.md)에 있다.
- 책임의 범위는 조직마다 다르다 — **데이터 엔지니어의 정확한 보안·프라이버시 책임은 조직 사이에
  유의하게 다를 것이다. 작은 스타트업에서 데이터 엔지니어는 데이터 보안 엔지니어로 이중 역할을 할 수
  있다. 큰 기술 회사는 보안 엔지니어와 보안 연구자의 군대를 갖는다. 이 상황에서도 데이터 엔지니어는
  흔히 자기 팀과 시스템 안의 보안 실무와 기술 취약점을 식별해 전담 보안 인력과 협업해 보고하고 완화할
  수 있다** (10장, p.370).[^reis2022]
- 이 장의 순서 — **이 장에서 우리는 데이터 엔지니어가 보안을 둘러싸고 고려해야 할 것들을, 특히
  사람·프로세스·기술에서 (그 순서로) 펼친다. 이는 완전한 목록이 아니지만, 우리 경험에 근거해
  개선되기를 바라는 주요한 것들을 펼친다** (10장, p.370).[^reis2022] 이 순서 자체가 주장이다 —
  기술이 아니라 사람이 먼저다.

## 사람 — 가장 약한 고리

- 진단 — **보안과 프라이버시에서 가장 약한 고리는 *당신*이다. 보안은 흔히 인간 수준에서 무너지므로
  당신이 언제나 표적인 것처럼 처신하라. 봇이나 인간 행위자가 어느 순간에든 당신의 민감한 자격증명과
  정보를 침투하려 시도하고 있다. 이것이 우리의 현실이며 사라지지 않는다. 온라인이든 오프라인이든
  당신이 하는 모든 것에 방어적 자세를 취하라. 부정적 사고의 힘을 발휘하고 언제나 편집증적이 되라**
  (10장, p.370).[^reis2022]
- 부정적 사고의 힘 — **긍정적 사고에 집착하는 세상에서 부정적 사고는 불쾌하다. 그러나 미국 외과의사
  아툴 가완디가 2007년 뉴욕 타임스에 정확히 이 주제로 기고를 썼다. 그의 중심 논지는 긍정적 사고가
  테러 공격이나 의료 응급의 가능성을 보지 못하게 만들고 대비를 저해할 수 있다는 것이다. 부정적 사고는
  재난 시나리오를 고려하고 그것을 막기 위해 행동하게 해 준다** (10장, p.370).[^reis2022]
- 그것이 데이터에서 뜻하는 것 — **데이터 엔지니어는 데이터 활용 시나리오를 능동적으로 생각해 보고,
  하류에 실제 필요가 있을 때만 민감한 데이터를 수집해야 한다. 사적이고 민감한 데이터를 보호하는 최선의
  방법은 애초에 이 데이터를 반입하지 않는 것이다** (10장, p.370).[^reis2022] 같은 결론에 다른 경로로
  도달하는 것이 [위험 자산으로서의 데이터](../concepts/data-as-a-hazardous-asset.md)의 데이터
  최소화 논변이다.
- **데이터 엔지니어는 자신이 활용하는 어떤 데이터 파이프라인이나 저장 시스템에 대해서도 공격과 유출
  시나리오를 생각해야 한다. 보안 전략을 결정할 때 당신의 접근이 안전의 환상이 아니라 적절한 보안을
  전달하도록 보장하라** (10장, p.370).[^reis2022]
- 늘 편집증적으로 — **누군가 당신의 자격증명을 요구할 때 언제나 주의를 발휘하라. 의심스러울 때 —
  그리고 자격증명을 요구받을 때는 언제나 극도로 의심해야 한다 — 보류하고 동료와 친구에게 두 번째
  의견을 구하라. 그 요청이 정말 정당한지 다른 사람들과 확인하라. 빠른 채팅이나 전화가 이메일 클릭으로
  촉발된 랜섬웨어 공격보다 싸다. 자격증명·민감 데이터·기밀 정보를 요구받을 때는 동료의 요구를 포함해
  누구도 액면 그대로 믿지 마라** (10장, pp.370–371).[^reis2022]
- 윤리도 여기 있다 — **당신은 프라이버시와 윤리를 존중하는 데서도 첫 방어선이다. 수집하도록 맡겨진
  민감 데이터가 불편한가? 프로젝트에서 데이터가 다뤄지는 방식에 윤리적 질문이 있는가? 당신의 우려를
  동료와 리더십에 제기하라. 당신의 일이 법적으로 준수될 뿐 아니라 윤리적이도록 보장하라** (10장,
  p.371).[^reis2022] 그 제기의 근거는
  [공학 윤리와 책임](../concepts/engineering-ethics-and-responsibility.md)에 있다.

## 프로세스 — 보안 극장이 아니라 습관

- 전제 — **사람들이 정규 보안 프로세스를 따를 때 보안은 업무의 일부가 된다. 보안을 습관으로 만들고,
  실제 보안을 정기적으로 실천하고, 최소 권한의 원칙을 발휘하며, 클라우드의 공유 책임 모델을
  이해하라** (10장, p.371).[^reis2022]
- 보안 극장의 정체 — **우리는 기업 고객에게서 컴플라이언스(내부 규칙·법률·표준 기구의 권고에 대한)에
  대한 만연한 집중을 보지만 잠재적으로 나쁜 시나리오에는 충분한 주의를 두지 않는다. 불행히도 이는
  보안의 환상을 만들지만 몇 분만 생각해 보면 명백해질 구멍을 크게 남긴다** (10장,
  p.371).[^reis2022]
- **보안은 조직 전반에서 습관이 될 만큼 충분히 단순하고 효과적이어야 한다. 우리는 아무도 읽지 않는
  수백 쪽짜리 보안 정책을 가진 회사, 사람들이 즉시 잊어버리는 연례 보안 정책 검토, 이 모두가 보안
  감사의 체크박스에 표시하기 위한 것인 회사가 얼마나 많은지에 놀란다. 이것이 보안 극장(security
  theater)이며, 여기서 보안은 진정한 *커밋먼트* 없이 컴플라이언스(SOC-2·ISO 27001 등)의 문자에서
  이뤄진다** (10장, p.371).[^reis2022]
- 대안 — **대신 진정하고 습관적인 보안의 정신을 추구하라. 보안 사고방식을 문화에 구워 넣으라. 보안은
  복잡할 필요가 없다. 예컨대 우리 회사는 이것을 팀의 DNA에 각인시키고 개선할 수 있는 보안 실무를 서로
  갱신하기 위해 적어도 한 달에 한 번 보안 훈련과 정책 검토를 돌린다. 보안은 데이터 팀에 나중 생각이어서는
  안 된다. 모두가 책임이 있고 각자 역할이 있다. 그것은 당신과 당신이 함께 일하는 모든 이에게 우선순위여야
  한다** (10장, p.371).[^reis2022]
- 능동적 보안 — **부정적 사고 관념으로 돌아가 능동적 보안(active security)은 동적이고 변화하는 세계에서
  보안 위협을 생각하고 연구하는 것을 수반한다. 예정된 모의 피싱 공격을 배포하는 데 그치지 말고, 성공한
  피싱 공격을 연구하고 조직의 보안 취약점을 생각해 봄으로써 능동적 보안 자세를 취할 수 있다. 표준
  컴플라이언스 체크리스트를 채택하는 데 그치지 말고 조직 특유의 내부 취약점과 직원이 사적 정보를 유출하거나
  오용할 유인을 생각해 볼 수 있다** (10장, p.371).[^reis2022]
- 최소 권한의 세부 — **최소 권한의 원칙은 사람이나 시스템에 눈앞의 태스크를 완료하는 데 필요한 권한과
  데이터만 주고 그 이상은 주지 않는 것을 뜻한다. 우리는 흔히 안티패턴을 본다 — 일반 사용자에게 모든 것에
  대한 관리자 접근이 주어지는 것인데, 그 사람은 자기 일을 하는 데 IAM 역할 몇 개만 필요할 수 있다.
  누군가에게 백지 위임식 관리자 접근을 주는 것은 거대한 실수이며 최소 권한의 원칙 아래 결코 일어나서는
  안 된다** (10장, p.372).[^reis2022]
  - 시간도 최소화한다 — **대신 사용자(또는 그가 속한 그룹)에게 필요할 때 필요한 IAM 역할을 제공하라. 이
    역할이 더는 필요 없을 때 그것을 회수하라. 같은 규칙이 서비스 계정에도 적용된다. 인간과 기계를 같은
    방식으로 다루라 — 그들이 일을 하는 데 필요한 권한과 데이터만, 그리고 필요한 기간에만 주라** (10장,
    p.372).[^reis2022]
  - 프라이버시로도 이어진다 — **물론 최소 권한의 원칙은 프라이버시에도 결정적이다. 사용자와 고객은 자기
    민감 데이터를 필요할 때만 사람들이 본다고 기대한다. 민감 데이터 주위에 컬럼·행·셀 수준 접근 통제를
    구현하라. PII와 다른 민감 데이터의 마스킹을 고려하고 열람자가 접근해야 할 정보만 담은 뷰를 만들라.
    어떤 데이터는 보유해야 하지만 비상시에만 접근돼야 한다. 이 데이터를 깨진 유리 프로세스(broken glass
    process) 뒤에 두라 — 사용자는 문제를 고치거나 결정적 이력 정보를 질의하기 위해 비상 승인 프로세스를
    거친 뒤에만 그것에 접근할 수 있다. 작업이 끝나면 접근은 즉시 회수된다** (10장,
    p.372).[^reis2022]
- 클라우드의 공유 책임 — **보안은 클라우드에서 공유된 책임이다. 클라우드 벤더는 자기 데이터 센터와
  하드웨어의 물리적 보안을 보장할 책임이 있다. 동시에 당신은 클라우드에서 짓고 유지하는 애플리케이션과
  시스템의 보안에 책임이 있다. 대부분의 클라우드 보안 침해는 클라우드가 아니라 최종 사용자에 의해 계속
  일어난다. 침해는 의도치 않은 오설정·실수·간과·부주의 때문에 일어난다** (10장,
  p.372).[^reis2022] 이 모델의 원문 인용은 위 [공유 책임 모델](#공유-책임-모델) 절에 있다.
- 백업 — **데이터는 사라진다. 때로는 죽은 하드 드라이브나 서버이고, 다른 경우 누군가 데이터베이스나
  오브젝트 저장 버킷을 실수로 지운다. 나쁜 행위자가 데이터를 잠가 버릴 수도 있다. 2022년 저술 시점에 랜섬웨어 공격이
  널리 퍼져 있다. 어떤 보험사는 공격 시 지급을 줄이고 있어, 데이터를 복구하는 것과 그것을 인질로 잡은
  나쁜 행위자에게 지불하는 것 양쪽을 당신에게 떠넘긴다. 재난 복구와 업무 연속성 양쪽을 위해, 그리고
  랜섬웨어 공격으로 당신 데이터의 한 버전이 훼손됐을 때를 위해 데이터를 정기적으로 백업해야 한다.
  더해서 데이터 백업의 복원을 정기적으로 시험하라** (10장, pp.372–373).[^reis2022]
  - 분류의 단서 — **데이터 백업은 엄밀히는 보안·프라이버시 실무에 들지 않는다. 그것은 재난
    예방(disaster prevention)이라는 더 큰 표제 아래 들지만, 특히 랜섬웨어 시대에는 보안에 인접한다**
    (10장, p.373).[^reis2022]
- 예시 정책이 짧다는 것 — 저자들은 자격증명·기기·민감 정보에 관한 표본 보안 정책을 제시하며 **우리가
  일을 과도하게 복잡하게 만들지 않는다는 데 유의하라. 대신 사람들에게 즉시 취할 수 있는 실무적 행동의
  짧은 목록을 준다**고 밝힌다 (10장, p.373).[^reis2022] 자격증명 항목의 실물은 다음과 같다 (10장,
  p.373):[^reis2022]
  - **모든 것에 단일 사인온(SSO)을 쓰라. 가능하면 비밀번호를 피하고 SSO를 기본값으로 쓰라. SSO에
    다중 인증을 쓰라.**
  - **비밀번호나 자격증명을 공유하지 마라. 여기에는 고객 비밀번호와 자격증명이 포함된다. 의심스러우면
    보고 대상에게 물으라. 그 사람도 의심스러우면 답을 찾을 때까지 계속 파고들라.**
  - **피싱과 사기 전화를 경계하라. 결코 비밀번호를 넘겨주지 마라. (다시, SSO를 우선하라.)**
  - **옛 자격증명을 비활성화하거나 삭제하라. 가급적 후자로.**
  - **자격증명을 코드에 넣지 마라. 비밀은 설정으로 다루고 결코 버전 관리에 커밋하지 마라. 비밀
    관리자를 쓰라.**
  - **언제나 최소 권한의 원칙을 발휘하라. 일을 하는 데 필요한 것 이상의 접근을 결코 주지 마라. 이는
    클라우드와 온프레미스의 모든 자격증명과 권한에 적용된다.**
  - 기기와 소프트웨어 갱신 항목도 같은 결이다 — 기기 관리와 다중 인증, 화면 공유 시 전체 데스크톱이
    아니라 단일 문서·탭·창만 공유하기, 브라우저 갱신 알림 시 재시작, OS 베타 미사용, 주요 OS 새
    버전은 1–2주 기다리기 (10장, pp.373–374).[^reis2022]

## 기술 — 패치·암호화·모니터링·네트워크

- 순서의 확인 — **사람과 프로세스로 보안을 다룬 뒤에야 기술을 활용해 시스템과 데이터 자산을 보안할
  때다** (10장, p.374).[^reis2022]
- 패치와 갱신 — **소프트웨어는 낡고 보안 취약점은 끊임없이 발견된다. 쓰고 있는 도구의 옛 버전에서
  보안 결함을 노출하지 않으려면 새 갱신이 가용해지는 대로 언제나 운영체제와 소프트웨어를 패치하고
  갱신하라. 고맙게도 많은 SaaS와 클라우드 관리형 서비스가 당신의 개입 없이 자동으로 업그레이드와 다른
  유지보수를 수행한다. 당신 자신의 코드와 의존성을 갱신하려면 빌드를 자동화하거나 릴리스와 취약점에
  경보를 걸어 수동 갱신을 촉발받으라** (10장, p.374).[^reis2022]
- 암호화의 한계부터 — **암호화는 마법의 탄환이 아니다. 자격증명에 대한 접근을 허용하는 *인간* 보안
  침해가 일어난 경우 그것은 당신을 지켜 주는 데 거의 도움이 되지 않는다. 암호화는 보안과 프라이버시를
  존중하는 어느 조직에나 기준선 요구사항이다. 그것은 네트워크 트래픽 가로채기 같은 기본적 공격에서
  당신을 보호할 것이다** (10장, p.375).[^reis2022]
  - 정지 상태 — **데이터가 정지 상태(저장 기기에 있을 때)일 때 암호화되도록 하라. 회사 랩톱은 기기가
    도난당했을 때 데이터를 보호하기 위해 전체 디스크 암호화가 켜져 있어야 한다. 서버·파일시스템·
    클라우드 오브젝트 저장에 저장된 모든 데이터에 서버 측 암호화를 구현하라. 보관 목적의 모든 데이터
    백업도 암호화돼야 한다. 마지막으로 해당되는 곳에 애플리케이션 수준 암호화를 통합하라** (10장,
    p.375).[^reis2022]
  - 전송 중 — **선을 넘는 암호화는 2022년 저술 시점 프로토콜의 기본값이다. 예컨대 HTTPS는 보통 그 시점 클라우드
    API에 요구된다. 데이터 엔지니어는 언제나 키가 어떻게 다뤄지는지 알고 있어야 한다. 나쁜 키 취급은
    데이터 유출의 유의한 원천이다. 게다가 버킷 권한이 공중에 열려 있으면 HTTPS는 데이터를 보호하는 데
    아무것도 하지 않으며, 이는 지난 10년 여러 데이터 스캔들의 또 다른 원인이다** (10장,
    p.375).[^reis2022]
  - 옛 프로토콜 — **엔지니어는 옛 프로토콜의 보안 한계도 알아야 한다. 예컨대 FTP는 공중 네트워크에서
    단순히 안전하지 않다. 데이터가 이미 공개돼 있을 때는 문제로 보이지 않을 수 있지만, FTP는 중간자
    공격에 취약해 공격자가 내려받는 데이터를 가로채 클라이언트에 도착하기 전에 바꿀 수 있다. 그냥 FTP를
    피하는 것이 최선이다** (10장, p.375).[^reis2022]
- 로깅·모니터링·경보 — **해커와 나쁜 행위자는 보통 자기가 당신의 시스템에 침투하고 있다고 알리지
  않는다. 대부분의 회사는 사고가 한참 지난 뒤에야 보안 사고를 알게 된다. DataOps의 일부는 사고를
  관측·탐지·조치하는 것이다. 데이터 엔지니어로서 시스템에서 이상한 이벤트가 일어날 때 그것을 알기 위해
  자동화된 모니터링·로깅·경보를 세워야 한다. 가능하면 자동 이상 탐지를 세우라** (10장,
  p.375).[^reis2022] 모니터링할 네 영역 (10장, p.376):[^reis2022]
  - **접근 — 누가 무엇에, 언제, 어디서 접근하는가? 어떤 새 접근이 부여됐는가? 현재 사용자 중 계정이
    탈취됐을 수 있음을 시사하는 이상한 패턴이 있는가 — 평소 접근하지 않거나 접근하면 안 되는 시스템에
    접근하려 시도하는 것 같은? 시스템에 접근하는 인식되지 않는 새 사용자가 보이는가? 접근 로그·사용자·
    역할을 정기적으로 훑으라.**
  - **자원 — 디스크·CPU·메모리·I/O에서 평범하지 않아 보이는 패턴을 모니터링하라. 자원이 갑자기
    바뀌었는가? 그렇다면 보안 침해를 가리킬 수 있다.**
  - **과금 — 특히 SaaS와 클라우드 관리형 서비스에서 비용을 감독해야 한다. 지출이 기대 안에 있는지
    확인하기 위해 예산 경보를 세우라. 과금에 예상치 못한 급증이 생기면 누군가 또는 무언가가 악의적
    목적으로 자원을 활용하고 있음을 가리킬 수 있다.**
  - **초과 권한 — 점점 벤더들은 사용자나 서비스 계정이 일정 기간 *활용하지 않는* 권한을 모니터링하는
    도구를 제공한다. 이 도구는 흔히 지정한 시간이 지나면 관리자에게 자동 경보하거나 권한을 제거하도록
    설정될 수 있다.** 저자들의 예 — **특정 분석가가 6개월간 Redshift에 접근하지 않았다고 하자. 이
    권한은 제거되어 잠재적 보안 구멍을 닫을 수 있다. 분석가가 앞으로 Redshift 접근이 필요하면 권한
    복구 티켓을 낼 수 있다.**
  - 묶어서 보라 — **모니터링에서 이 영역들을 결합해 자원·접근·과금 프로필의 횡단적 시야를 얻는 것이
    최선이다. 데이터 팀의 모두가 모니터링을 보고 무언가 이상해 보일 때 경보를 받도록 대시보드를 세울
    것을 제안한다. 이를 효과적인 사고 대응 계획과 결합해 보안 침해가 일어났을 때 관리하고, 대비를
    위해 그 계획을 정기적으로 훑으라** (10장, p.376).[^reis2022]
- 네트워크 접근 — **우리는 데이터 엔지니어가 네트워크 접근과 관련해 꽤 거친 짓을 하는 것을 자주 본다.
  여러 사례에서 우리는 민감 데이터를 대량으로 담은 공개 접근 가능한 Amazon S3 버킷을 봤다. 우리는
  또한 전 세계 0.0.0.0/0(모든 IP)에 인바운드 SSH 접근이 열린 Amazon EC2 인스턴스나 공중 인터넷의
  모든 인바운드 요청에 열린 접근을 가진 데이터베이스도 목격했다. 이것들은 끔찍한 네트워크 보안 실무의
  몇 예일 뿐이다** (10장, p.376).[^reis2022]
  - 최소한의 실무 — **원칙적으로 네트워크 보안은 회사의 보안 전문가에게 맡겨야 한다. (실무에서는 작은
    회사에서 네트워크 보안에 상당한 책임을 떠맡아야 할 수도 있다.) 데이터 엔지니어로서 데이터베이스·
    오브젝트 저장·서버를 아주 자주 만나므로 좋은 네트워크 접근 실무에 부합하는지 확인하기 위해 취할 수
    있는 단순한 조치를 적어도 알고 있어야 한다. 어떤 IP와 포트가, 누구에게, 왜 열려 있는지 이해하라. 이
    포트에 접근할 시스템과 사용자의 인바운드 IP 주소를 허용하고(일명 IP 화이트리스팅) 어떤 이유로든
    광범위하게 연결을 여는 것을 피하라. 클라우드나 SaaS 도구에 접근할 때 암호화된 연결을 쓰라. 예컨대
    커피숍에서 암호화되지 않은 웹사이트를 쓰지 마라** (10장, p.377).[^reis2022]
  - 온프레미스에 대한 단서 — **이 책이 거의 전적으로 클라우드에서 작업부하를 돌리는 데 집중했지만
    온프레미스 서버 호스팅에 대한 짧은 노트를 덧붙인다. 3장에서 우리는 단단한 경계와 제로 트러스트 보안의
    차이를 논했다. 클라우드는 일반적으로 제로 트러스트 보안에 더 가깝다 — 모든 행동이 인증을 요구한다.
    우리는 클라우드가 대부분의 조직에 더 안전한 선택지라고 믿는데, 그것이 제로 트러스트 실무를 부과하고
    공중 클라우드가 고용한 보안 엔지니어 군대를 회사가 활용하게 해 주기 때문이다** (10장,
    p.377).[^reis2022]
  - 그럼에도 남는 경우 — **그렇지만 때로는 단단한 경계 보안이 여전히 말이 된다. 우리는 핵미사일 격납고가
    에어 갭(어떤 네트워크에도 연결되지 않음)돼 있다는 지식에서 어떤 위안을 얻는다. 에어 갭 서버는 강화된
    보안 경계의 궁극적 예다. 다만 온프레미스에서도 에어 갭 서버가 인간 보안 실패에는 취약하다는 것을
    명심하라** (10장, p.377).[^reis2022]
- 저수준 데이터 엔지니어링의 보안 — **데이터 저장·처리 시스템의 내장에서 일하는 엔지니어에게는 모든
  요소의 보안 함의를 고려하는 것이 결정적이다. 어떤 소프트웨어 라이브러리·저장 시스템·컴퓨트 노드도
  잠재적 보안 취약점이다. 잘 알려지지 않은 로깅 라이브러리의 결함이 공격자에게 접근 통제나 암호화를
  우회하도록 허용할 수 있다. CPU 아키텍처와 마이크로코드조차 잠재적 취약점을 나타낸다 — 민감 데이터는
  메모리나 CPU 캐시에 정지 상태로 있을 때 취약할 수 있다. 사슬의 어느 고리도 당연시될 수 없다**
  (10장, p.377).[^reis2022]
- 내부 보안 연구 — **우리는 기술에 능동적 보안 접근을 채택할 것도 강력히 권한다. 구체적으로 이는 모든
  기술 직원이 보안 문제를 생각해야 한다는 뜻이다. 왜 이것이 중요한가? 모든 기술 기여자는 기술 전문성의
  도메인을 개발한다. 회사가 보안 연구자의 군대를 고용하더라도 데이터 엔지니어는 자기 소관의 특정 데이터
  시스템과 클라우드 서비스에 친밀하게 익숙해질 것이다. 특정 기술의 전문가는 그 기술의 보안 구멍을
  식별하기 좋은 위치에 있다. 모든 데이터 엔지니어가 보안에 능동적으로 관여하도록 격려하라. 자기
  시스템에서 잠재적 보안 위험을 식별하면 그들은 완화책을 생각해 보고 그것을 배포하는 데 능동적 역할을
  맡아야 한다** (10장, pp.377–378).[^reis2022]
- 10장의 결론 — **보안은 마음과 행동의 습관이어야 한다. 데이터를 당신의 지갑이나 스마트폰처럼 다루라.
  당신이 회사의 보안을 책임지고 있지는 않겠지만, 기본적인 보안 실무를 알고 보안을 늘 염두에 두는 것은
  조직의 데이터 보안 침해 위험을 줄이는 데 도움이 될 것이다** (10장, p.378).[^reis2022]

## 데이터 아키텍처

- 3장이 이 저류의 자리를 다시 명시한다 — **데이터 엔지니어링 수명 주기의 저류가 데이터 성숙도의
  어느 단계에 있는 회사에나 좋은 데이터 아키텍처의 토대를 이룬다** (3장, p.77).[^reis2022] 그
  아키텍처의 정의와 원칙은
  [데이터 아키텍처의 정의](../concepts/data-architecture-defined.md)와
  [좋은 데이터 아키텍처의 아홉 원칙](../concepts/good-data-architecture-principles.md)에 있다.
- 정의 — **데이터 아키텍처는 조직의 장기 데이터 필요와 전략을 뒷받침하는 데이터 시스템의 현재와
  미래 상태를 반영한다. 조직의 데이터 요구사항은 빠르게 바뀔 것이고 새 도구와 실무가 거의 매일
  도착하는 것처럼 보이므로, 데이터 엔지니어는 좋은 데이터 아키텍처를 이해해야 한다** (2장,
  p.64).[^reis2022]
- 데이터 엔지니어가 하는 일 — **데이터 엔지니어는 먼저 업무의 필요를 이해하고 새 유스케이스의
  요구사항을 모아야 한다. 다음으로 그 요구사항을 번역해 데이터를 포착하고 서빙하는 새 방법을,
  비용과 운영 단순성 사이에서 균형 잡아 설계해야 한다. 이는 원천 시스템·반입·저장·변환·서빙에서
  설계 패턴·기술·도구의 트레이드오프를 안다는 뜻이다** (2장, p.64).[^reis2022]
- 역할의 구분 — **이것이 데이터 엔지니어가 곧 데이터 아키텍트라는 뜻은 아니다. 보통 이 둘은
  별개의 역할이다. 데이터 엔지니어가 데이터 아키텍트와 나란히 일한다면 데이터 아키텍트의 설계를
  구현해 낼 수 있어야 하고 아키텍처적 피드백을 제공할 수 있어야 한다** (2장,
  p.64).[^reis2022]

## 소프트웨어 엔지니어링

- 계보 — **소프트웨어 엔지니어링은 늘 데이터 엔지니어의 중심 기술이었다. 2022년 저술 시점 데이터
  엔지니어링의 초기(2000–2010)에 데이터 엔지니어는 저수준 프레임워크에서 일하며 C·C++·자바로
  맵리듀스 잡을 썼다. 빅데이터 시대의 정점(2010년대 중반)에 엔지니어들은 이 저수준 세부를
  추상화한 프레임워크를 쓰기 시작했다** (2장, p.66).[^reis2022]
- 추상화는 계속되지만 — **클라우드 데이터 웨어하우스는 SQL 의미론으로 강력한 변환을 지원하고,
  스파크 같은 도구는 저수준 코딩 세부에서 벗어나 쓰기 쉬운 데이터프레임 쪽으로 옮겨 가며 더
  사용자 친화적이 됐다. 이 추상화에도 불구하고 소프트웨어 엔지니어링은 여전히 데이터
  엔지니어링에 결정적이다** (2장, p.66).[^reis2022]
- **핵심 데이터 처리 코드** — **더 추상적이고 관리하기 쉬워졌지만 핵심 데이터 처리 코드는
  여전히 쓰여야 하고 데이터 엔지니어링 수명 주기 전반에 나타난다. 반입이든 변환이든 서빙이든,
  데이터 엔지니어는 스파크·SQL·빔 같은 프레임워크와 언어에 고도로 능숙하고 생산적이어야 한다.
  우리는 SQL이 코드가 아니라는 관념을 거부한다** (2장, p.66).[^reis2022]
  - **데이터 엔지니어가 단위·회귀·통합·엔드투엔드·스모크 같은 적절한 코드 테스트 방법론을
    이해하는 것도 필수다** (2장, p.66).[^reis2022]
- **오픈 소스 프레임워크 개발** — **많은 데이터 엔지니어가 오픈 소스 프레임워크 개발에 깊이
  관여한다. 수명 주기의 특정 문제를 풀려고 이 프레임워크를 채택한 다음, 자기 유스케이스를
  위해 도구를 개선하고 커뮤니티에 되돌려주려고 프레임워크 코드 개발을 계속한다** (2장,
  p.66).[^reis2022]
  - 지형의 변화 — **빅데이터 시대에 우리는 하둡 생태계 안에서 데이터 처리 프레임워크의 캄브리아기
    폭발을 봤다. 이 도구들은 주로 수명 주기의 변환·서빙 부분에 집중했다. 데이터 엔지니어링
    도구의 종 분화는 멈추거나 느려지지 않았지만, 강조점이 직접적인 데이터 처리에서 벗어나
    추상화의 사다리 위로 옮겨 갔다. 이 새 세대의 오픈 소스 도구는 엔지니어가 데이터를 관리·
    강화·연결·최적화·모니터링하도록 돕는다** (2장, p.66).[^reis2022]
  - 만들기 전에 — **데이터 엔지니어는 새 내부 도구를 엔지니어링하기 전에 공개적으로 이용
    가능한 도구의 지형을 조사하는 것이 좋다. 도구 구현에 결부된 총소유비용(TCO)과 기회비용을
    주시하라. 그들이 풀려는 문제를 이미 다루는 오픈 소스 프로젝트가 있을 가능성이 크고,
    바퀴를 다시 발명하기보다 협업하는 편이 낫다** (2장, p.67).[^reis2022]
- **스트리밍** — **스트리밍 데이터 처리는 배치보다 본질적으로 더 복잡하고 도구와 패러다임은
  논쟁의 여지는 있으나 덜 성숙하다. 예컨대 배치 처리 세계에서 당연하게 여기는 조인 같은 데이터
  처리 태스크가 실시간에서는 흔히 더 복잡해져 더 복잡한 소프트웨어 엔지니어링을 요구한다.
  엔지니어는 다양한 윈도잉(windowing) 방법을 적용하는 코드도 써야 한다. 윈도잉은 실시간
  시스템이 추적 통계(trailing statistics) 같은 가치 있는 지표를 계산하게 해 준다** (2장,
  p.67).[^reis2022] 그 시간 의미론의 본가는
  [스트림 처리의 시간 의미론](../concepts/stream-processing-time-semantics.md)이다.
- **코드로서의 인프라(infrastructure as code, IaC)** — **IaC는 소프트웨어 엔지니어링 실무를
  인프라의 설정과 관리에 적용한다. 회사들이 Databricks·Amazon EMR 같은 관리형 빅데이터
  시스템과 클라우드 데이터 웨어하우스로 이주하면서 빅데이터 시대의 인프라 관리 부담은
  줄었다. 데이터 엔지니어가 클라우드 환경에서 인프라를 관리해야 할 때는 수동으로 인스턴스를
  띄우고 소프트웨어를 설치하기보다 점점 더 IaC 프레임워크를 통해 그것을 한다** (2장,
  p.67).[^reis2022]
  - **이 실무는 데브옵스의 핵심 부분이며 배포의 버전 관리와 재현성을 가능하게 한다** (2장,
    p.68).[^reis2022]
- **코드로서의 파이프라인(pipelines as code)** — **2022년 저술 시점 오케스트레이션 시스템의 핵심 개념이며
  데이터 엔지니어링 수명 주기의 모든 단계에 닿는다. 데이터 엔지니어는 코드(통상 파이썬)로
  데이터 태스크와 그 사이의 의존을 선언한다. 오케스트레이션 엔진은 이 지시를 해석해 가용
  자원으로 단계를 실행한다** (2장, p.68).[^reis2022]
- **범용 문제 해결** — **어떤 고수준 도구를 채택하든 실제로 데이터 엔지니어는 수명 주기 전반에서
  선택한 도구의 경계 밖에서 문제를 풀고 커스텀 코드를 써야 하는 코너 케이스를 만난다.
  Fivetran·Airbyte·Matillion 같은 프레임워크를 쓸 때 데이터 엔지니어는 기존 커넥터가 없는
  데이터 원천을 만나 커스텀한 무언가를 써야 한다** (2장, p.68).[^reis2022]
