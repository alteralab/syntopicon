하나의 질문: **서빙 단계가 내놓는 것을 "데이터"가 아니라 "제품"으로 부르면 무엇이 달라지며,
사용자가 스스로 만들게 하는 것은 언제 옳은가.**

## 정의

- 저자들이 인용하는 정의 (9장, p.340, 각주 2):[^reis2022]

> A good definition of a data product is a product that facilitates an end goal through the
> use of data.
>
> —D. J. Patil

## 진공에서 만들어지지 않는다

- **데이터 프로덕트(data product)는 진공에서 만들어지지 않는다. 우리가 논한 다른 많은 조직
  프로세스와 마찬가지로 데이터 제품을 만드는 것은 제품·업무와 기술이 섞인 전면 접촉 스포츠다. 데이터
  제품을 개발할 때 핵심 이해관계자를 참여시키는 것이 중요하다. 대부분의 회사에서 데이터 엔지니어는
  데이터 제품의 최종 사용자와 몇 단계 떨어져 있다. 좋은 데이터 엔지니어는 데이터 분석가·데이터
  과학자 같은 직접 사용자와 회사 외부의 고객을 위한 결과를 온전히 이해하려 애쓸 것이다** (9장,
  p.340).[^reis2022]

## "해야 할 일"로 보기

- **데이터 제품을 만들 때 "해야 할 일(jobs to be done)"을 생각하는 것이 유용하다. 사용자는 "해야
  할 일"을 위해 제품을 "고용"한다. 이는 사용자가 무엇을 원하는지 — 즉 당신의 제품을 "고용"하는 그들의
  동기를 — 알아야 한다는 뜻이다. 고전적인 엔지니어링 실수는 최종 사용자의 요구사항·필요나
  제품/시장 적합을 이해하지 않은 채 그냥 짓는 것이다. 이 재앙은 아무도 쓰고 싶어 하지 않는 데이터
  제품을 지을 때 일어난다** (9장, p.341).[^reis2022]

## 긍정 피드백 루프

- **좋은 데이터 제품은 긍정 피드백 루프를 갖는다. 데이터 제품의 사용이 늘어나면 더 유용한 데이터가
  생성되고, 그것이 데이터 제품을 개선하는 데 쓰인다. 헹구고 반복하라** (9장, p.341).[^reis2022]

## 만들기 전에 묻는 것

- 저자들의 세 질문 (9장, p.341):[^reis2022]
  - **누군가 데이터 제품을 쓸 때 그들은 무엇을 이루기를 바라는가? 너무 자주 데이터 제품은 사용자가
    기대하는 결과에 대한 명확한 이해 없이 만들어진다.**
  - **데이터 제품이 내부 사용자를 서빙할 것인가 외부 사용자를 서빙할 것인가? 2장에서 우리는 내부
    대면과 외부 대면 데이터 엔지니어링을 논했다. 데이터 제품을 만들 때 고객이 내부 대면인지 외부
    대면인지 아는 것은 데이터가 서빙되는 방식에 영향을 준다.**
  - **당신이 짓는 데이터 제품의 결과와 ROI는 무엇인가?**
- 그리고 채택을 지켜보라 — **사람들이 쓰고 사랑할 데이터 제품을 짓는 것이 결정적이다. 원치 않는
  효용과 데이터 출력에 대한 신뢰 상실보다 데이터 제품의 채택을 더 망치는 것은 없다. 데이터 제품의
  채택과 사용에 주의를 기울이고 사용자를 행복하게 만들기 위해 조정할 의지를 가지라** (9장,
  p.341).[^reis2022] 그 신뢰가 왜 뿌리인지는
  [수명 주기의 서빙 단계](../concepts/serving-in-the-lifecycle.md)에 있다.

## 셀프서비스인가 아닌가

- 질문의 형태 — **사용자는 당신의 데이터 제품과 어떻게 인터페이스할 것인가? 업무 이사가 데이터 팀에
  리포트를 요청할 것인가, 아니면 이 이사가 그냥 리포트를 만들 수 있는가? 셀프서비스 데이터 제품 —
  사용자에게 스스로 데이터 제품을 만들 능력을 주는 것 —은 여러 해 동안 데이터 사용자들의 공통된
  열망이었다** (9장, p.341).[^reis2022]
- 현재 상태의 판정 — **오늘날 셀프서비스 BI와 데이터 과학은 여전히 대체로 열망이다. 회사가 데이터로
  셀프서비스를 성공적으로 해내는 것을 이따금 보기는 하지만 이는 드물다. 대부분의 경우 셀프서비스
  데이터 시도는 좋은 의도로 시작하지만 결국 실패한다. 셀프서비스 데이터는 실제로 구현하기 어렵다.
  따라서 애드혹 리포트를 제공하고 대시보드를 유지하는 무거운 짐은 분석가나 데이터 과학자에게 남는다**
  (9장, pp.341–342).[^reis2022]
- 왜 어려운가 — **셀프서비스 데이터가 왜 그렇게 어려운가? 답은 미묘하지만 일반적으로 최종 사용자를
  이해하는 것과 관련된다. 사용자가 사업이 어떻게 돌아가는지 이해해야 하는 임원이라면 그 사람은 아마
  명확하고 실행 가능한 지표의 미리 정의된 대시보드만 원할 것이다. 임원은 커스텀 데이터 뷰를 만드는
  셀프서비스 도구를 무시할 가능성이 크다. 리포트가 추가 질문을 자아내면 그들은 더 깊은 조사를 수행할
  분석가를 마음대로 쓸 수 있을 것이다. 반면 분석가인 사용자는 이미 SQL 같은 더 강력한 도구로
  셀프서비스 분석을 추구하고 있을 수 있다. BI 계층을 통한 셀프서비스 분석은 유용하지 않다. 데이터
  과학에도 같은 고려가 적용된다. "시민 데이터 과학자"에게 셀프서비스 ML을 부여하는 것이 많은 자동화
  ML 벤더의 목표였지만 채택은 셀프서비스 분석과 같은 이유로 여전히 초기다. 이 두 극단적 경우에서
  셀프서비스 데이터 제품은 그 일에 잘못된 도구다** (9장, p.342).[^reis2022]
- 성공의 조건 — **성공적인 셀프서비스 데이터 프로젝트는 올바른 청중을 갖는 것으로 귀결된다.
  셀프서비스 사용자와 그들이 하고 싶어 하는 "일"을 식별하라. 그들은 데이터 분석가와 협업해 일을
  끝내는 것과 비교해 셀프서비스 데이터 제품을 써서 무엇을 이루려 하는가? 데이터 배경을 가진 임원
  집단은 셀프서비스의 이상적 청중이다 — 그들은 아마 녹슬어 가는 SQL 기술을 꺼내 들 필요 없이 스스로
  데이터를 자르고 썰고 싶어 한다. 회사 차원의 이니셔티브와 훈련 프로그램으로 직원이 데이터 기술을
  배우는 데 시간을 투자할 의지가 있는 업무 리더도 셀프서비스에서 상당한 가치를 실현할 수 있다**
  (9장, p.342).[^reis2022]
- 그다음 정해야 할 것 — **이 집단에 데이터를 어떻게 제공할지 결정하라. 새 데이터에 대한 그들의 시간
  요구사항은 무엇인가? 그들이 필연적으로 더 많은 데이터를 원하거나 셀프서비스에 요구되는 범위를
  바꾸면 어떻게 되는가? 더 많은 데이터는 흔히 더 많은 질문을 뜻하고 그것은 더 많은 데이터를 요구한다.
  셀프서비스 사용자의 커져 가는 필요를 예상해야 한다. 또한 청중이 잘못된 결과와 혼란 없이 가치와
  통찰을 찾도록 도울 유연성과 가드레일 사이의 미묘한 균형을 이해해야 한다** (9장,
  p.342).[^reis2022]

## 같은 낱말의 다른 용법 — 데이터 메시 쪽

이 페이지의 "데이터 프로덕트"는 **서빙 단계의 산출물**이다. 데이터 메시에서 같은 낱말은
**메시 위에서 오가는 아키텍처 단위**를 가리킨다. 두 용법은 다투지 않지만 범위가 다르다 —
Dehghani 쪽은 데이터·메타데이터·코드·정책·인프라 의존성을 함께 캡슐화한 배포 단위를 뜻하므로,
"만들어 서빙하는 결과물"보다 넓다. 상세는
[제품으로서의 데이터 원칙](../concepts/data-as-a-product-principle.md)에 있다.

- 낱말의 범위를 좁히는 원전의 주석 — **제품으로서의 데이터는 데이터가 모델링되고 공유되는 방식에
  제품 사고를 적용하는 것이다. 제품을 파는 것(product selling)과 혼동하지 말 것** (3장,
  p.31).[^dehghani2022]
- 그리고 그쪽에서는 "제품"이 은유가 아니라 **측정 축의 교체**다 — **자산으로서의 데이터는 성공을
  허영 지표(vanity metrics)로 재게 만들었다. 레이크나 웨어하우스에 포착된 데이터셋과 테이블의
  수, 또는 데이터의 부피 같은 것이다** (3장, p.43).[^dehghani2022] 대신 제안되는 지표는
  **데이터의 채택, 사용자 수, 그리고 데이터를 쓰는 만족도**다 (3장, p.43).[^dehghani2022] —
  위 "긍정 피드백 루프" 절이 말하는 채택과 같은 축이다.
- 사용자 이해를 강조하는 점에서는 두 소스가 같은 자리에 선다. 다만 원전은 그 이해에 **한계가
  있다**는 것을 설계 전제로 삼는다 — **어느 시점에서든 데이터 프로덕트 소유자는 오늘 알려진
  실행 가능한 용법을 알거나 계획할 수 있지만, 오늘 생산되는 데이터의 미래 용법 중 상당 부분은
  그들의 상상 너머에 미지로 남는다** (3장, p.32).[^dehghani2022] 이것이 위 "해야 할 일"
  절과의 차이다 — 저쪽은 사용자의 고용 동기를 알아내라 하고, 이쪽은 알아낼 수 없는 몫을 위해
  원천의 해상도를 낮추지 말라고 한다.
