하나의 질문: **탐지가 문제를 짚었는데 그것이 내 잘못이 아니라면, 누구에게 물어야 하는지를 어떻게
아는가.**

Konieczny 10장의 둘째 기둥인 **추적**(tracking)은 관측을 데이터 자체에서 **데이터 사이의 관계**로
옮긴다. 탐지 쪽은 [관측 탐지 패턴](observability-detector-patterns.md)이다.

## 왜 추적인가 — 내 잘못이 아닐 때

- 이 범주가 서는 자리를 저자가 앞 패턴에 붙여 세운다 — **지금까지 처리 중인 데이터를 관측하는
  해법을 봤다. 그런데 탐지된 문제가 당신 잘못이 아니라면 어떻게 되는가? SLA Misses Detector
  패턴에서 그것을 봤는데, 늦은 이벤트가 이벤트 시각 기반 SLA를 깰 수 있었다. 이 경우 지연의 이유를
  더 잘 이해하기 위해 누구에게 도움을 청할지 알아야 한다. 그 지식을 얻는 훌륭한 방법은 데이터셋의
  의존을 알게 되는 것이고, 그것은 데이터셋에 일종의 가족 나무(family tree)를 세우는 것이다**
  (10장, p.321).[^konieczny2025]
- 장 도입이 그 쓸모를 조직 규모로 적는다 — 추적 패턴은 **대규모 조직에서 흔히 여러 팀에 걸쳐 있는
  데이터 생성 그래프를 발견하는 것을 돕고, 여러 입력에서 만들어진 열에 관해서라면 개별 열의 변환
  로직을 이해하는 데도 도움이 된다** (10장, p.305).[^konieczny2025]
  - 계보(lineage)라는 개념 자체의 정의와 그것이 데이터 관리의 어느 칸에 속하는지는
    [데이터 관리 규율](data-management-discipline.md)에, 기술 메타데이터의 한 항목으로 놓이는
    자리는 [메타데이터 관리](metadata-management.md)에 있다. **Konieczny가 더하는 것은 그것을
    누가 어떻게 만들어 내는가의 구현 층이다.**

## Dataset Tracker — 데이터셋의 가족 나무

- 두 패턴을 가르는 축이 **입도**다 — **데이터 계보 패턴은 데이터셋 수준과 데이터 항목(data entry)
  수준에서 작동한다. 이름이 말하는 대로 테이블·폴더·토픽·큐 같은 다양한 데이터 용기(data
  container)에 적용되는 데이터셋 추적부터 보자. 결국 그것은 이 용기들 사이의 의존 나무를 만들어
  데이터 제공자와 데이터 소비자를 분명히 표현한다** (10장, p.321).[^konieczny2025]
- 문제의 실물은 **범인을 못 찾는 상황**이다 — 품질이 나쁜 데이터셋을 소비하고 있고 스키마가
  일관되지 않아 배치 잡이 정기적으로 실패한다. 조사해 보니 필드 하나가 시간에 걸쳐 다른 데이터
  타입을 가졌다. **상류 데이터 제공자는 이 변경을 모르는데, 그 데이터셋을 생성하는 주체가 아니기
  때문이다. 당신의 데이터 제공자는 또 다른 팀이 생성한 데이터를 처리하고 있어서, 어느 팀이 타입
  불일치 문제를 들여오는지 더 잘 탐지하려면 데이터셋 의존을 이해하고 싶다** (10장,
  p.321).[^konieczny2025]
  - **곧 이 패턴이 푸는 것은 기술 문제가 아니라 조직 문제다** — 그림 10-3의 예도 세 팀(주문·사용자·
    강화된 주문)이 각자 자기 도메인의 데이터 객체를 책임지는 그림이고, 저자는 각주에서 **데이터
    메시 지향 조직에는 익숙해 보일 것**이라며 Dehghani(2022)와 Perrin·Broda(2024)를 가리킨다
    (10장, p.322 각주 4).[^konieczny2025] 그 조직 축의 정본은 [데이터 메시](data-mesh.md)다.

## 관리형이냐 자체 구현이냐

- **구현에 관해서는 두 가지 가능한 해법이 있다** (10장, p.322).[^konieczny2025]
- 관리형 — **첫째는 완전 관리형 클라우드 서비스를 쓰는 것으로, 당신에게는 아무 할 일이 없으니
  투명할 것이다. 이 구현에서 의존 나무의 구성은 각 데이터셋과 상호작용하는 잡·테이블·대시보드를
  분석하는 서비스나 프레임워크에 위임된다. Databricks가 Unity Catalog에 등록된 테이블의 계보를
  포착하는 방식이 그렇고, GCP의 Dataplex 서비스가 BigQuery·Dataproc 같은 다른 GCP 데이터 서비스에
  대해 추적 정보를 자동 기록하는 방식도 그렇다** (10장, p.322).[^konieczny2025]
- 관리형의 한계가 곧 둘째 해법의 이유다 — **그러나 자동화된 판은 언제나 특정 종류의 잡이나 데이터
  스토어에 한정된다. 예컨대 Dataplex가 BigQuery 데이터 적재 잡의 계보를 지원하더라도 BigQuery Data
  Transfer Service로부터의 데이터 적재는 지원하지 않는다. 그런 이유로 데이터셋 계보를 스스로
  구현하는 둘째 구현이 있다** (10장, p.322).[^konieczny2025]

## 자체 구현이 입출력을 뽑는 두 수준

- 시작점은 같다 — **구현은 각 질의·태스크·파이프라인의 입력과 출력을 식별하는 것에서 시작한다.
  이 단계는 두 수준에서 일어날 수 있다** (10장, p.322).[^konieczny2025]
- **데이터 오케스트레이션 계층** — **데이터셋을 생성하는 각 파이프라인은 외부 데이터 계보 서비스로
  보고될 입력과 출력을 포함해야 한다. OpenLineage에 대한 아파치 에어플로처럼 기존 도구 일부는
  데이터셋 사이의 의존을 자동으로 탐지할 수 있다** (10장, p.323).[^konieczny2025]
- **데이터베이스 계층** — **여기서는 계보 잡이 실행된 질의를 분석해 데이터셋 사이의 의존을 식별하고
  그것을 계보 서비스에 저장한다.** 저자의 예는 그림 10-3의 주문과 사용자 테이블을
  `SELECT ... FROM orders o JOIN users u ON u.id = o.user_id`로 붙이는 질의이고,
  **데이터베이스 계층 식별은 이 질의를 나무로 변환해 참조된 모든 테이블을 뽑아낸다** (10장,
  p.323).[^konieczny2025]
  - **두 수준은 선언과 추론의 대비다** — 오케스트레이션 계층은 파이프라인이 **스스로 신고**하고,
    데이터베이스 계층은 실행된 질의에서 **역으로 읽어 낸다**. 앞은 신고 누락에, 뒤는 파서의 한계에
    각각 약하다.

## 추출만으로 끝나지 않는다

- **수동 판의 계보 구현은 입출력 추출에서 멈추지 않는다. 이 선언적이거나 알고리즘적인 해법에 더해,
  식별된 의존을 해석하고 시각적으로 표현할 계층이 필요하다** (10장, p.323).[^konieczny2025]
- 그림 10-4가 그 전체 그림을 네 조각으로 그린다 (10장, p.323):[^konieczny2025] 데이터 처리 계층
  안의 **계보 추출**(lineage extraction)이 **계보 API**로 보내고, API가 **계보 데이터베이스**에
  쓰며, 사람은 **계보 UI**로 그것을 읽는다.
  - 그 대가 — **이 접근은 유연성을 가져오지만 배포된 서비스의 수와 그 사이의 상호작용을 모니터링해야
    하므로 더 많은 구현 노력도 요구한다** (10장, p.323).[^konieczny2025]
  - **완전 관리형 접근도 같은 그림을 따르며, 다만 계보 추출이 기성품으로 수행된다** (10장, p.323,
    그림 10-4 설명).[^konieczny2025]
- 예제는 OpenLineage API와 Marquez UI다 — 에어플로 쪽은 `OPENLINEAGE_URL` 환경 변수와
  `apache-airflow-providers-openlineage` 패키지를 놓으면 **`PostgresOperator` 같은 여러 오퍼레이터에
  대한 네이티브 지원 덕에 별도 단계 없이 OpenLineage 추출기가 전부 해 준다** (10장,
  p.324).[^konieczny2025] Spark 쪽은 세션을 만들 때 의존을 끼우는 것이 전부다 (10장, p.325, 예제
  10-17):[^konieczny2025]

  ```python
  (SparkSession.builder.master('local[*]')
    .appName(app_name)
    .config('spark.extraListeners',
      'io.openlineage.spark.agent.OpenLineageSparkListener')
    .config('spark.openlineage.transport.type', 'http')
    .config('spark.openlineage.transport.url', 'http://localhost:5000')
    .config('spark.openlineage.namespace', 'visits')
    .config('spark.jars.packages', 'io.openlineage:openlineage-spark_2.12:1.21.1')
  .getOrCreate())
  ```

## 벤더 락인과 커스텀 작업

- **벤더 락인**(vendor lock) — **Databricks와 GCP로 제시한 것 같은 완전 관리형 해법은 흔히 서비스
  범위 안에서만 작동한다. 달리 말해 오픈 소스 데이터 스토어나 다른 클라우드에 있는 데이터베이스와
  함께 쓰면 계보의 부분적인 뷰만 얻을 수 있다** (10장, p.324).[^konieczny2025]
- **커스텀 작업**(custom work) — **때때로 데이터 오케스트레이션 프레임워크는 입출력 선언을
  태스크 설정에서 연역할 수 있으므로 그것을 추상화한다. 그러나 그것은 내장 태스크 타입을 쓸 때만
  작동한다. 어떤 커스텀 태스크 타입에 대해서도 입출력 해석 로직을 직접 정의해야 할 수 있다** (10장,
  p.324).[^konieczny2025]
  - **두 결과가 같은 것을 말한다** — 계보의 완전성은 **표준 경로를 얼마나 벗어났는가**에 반비례한다.
    아래 Fine-Grained Tracker의 커스텀 코드 문제도 같은 모양이다.

## Fine-Grained Tracker — 열과 행까지 내려간다

- 다음 질문이 자동으로 따라온다 — **데이터셋 추적은 데이터셋 의존 문제를 풀지만, 자동으로 또 다른
  질문을 불러온다. 열은 어떻게 추적하는가? 달리 말해 어떤 입력 열들이 각 출력 열을 구성하는지를
  어떻게 정하는가?** (10장, p.325).[^konieczny2025]
- 문제의 실물이 앞 장의 패턴에서 온다 — **값비싼 조인을 피하려고 Denormalizer 패턴을 구현했다.
  그 테이블이 3년 만에 30개 넘는 열로 자랐다. 팀 구성이 꽤 자주 바뀌고 그때마다 새 구성원이 테이블
  의존을 묻는다. 대부분은 Dataset Tracker 패턴으로 답할 수 있지만 한 질문이 남는다. 새 동료들은
  당신의 비정규화된 테이블의 각 열이 상류 테이블의 어느 열을 쓰는지 알고 싶어 한다** (10장,
  p.325).[^konieczny2025] 그 Denormalizer의 정본은
  [정규화와 비정규화](normalization-and-denormalization.md)다.
  - **비정규화의 대가 목록에 한 줄이 추가된 셈이다** — 조인을 없앤 표는 **출처를 잃는다**.
- 해법 — **이 열 수준 추적의 세부는 Fine-Grained Tracker 패턴을 쓰기에 이상적인 시나리오다. 그것은
  데이터 기원에 관한 저수준 세부를 열 또는 행 수준에서 제공한다** (10장, p.325).[^konieczny2025]

## 열 수준은 실행 계획을 읽는다

- 관리형 쪽 — **일부 해법은 제약 아래 Dataset Tracker를 네이티브로 지원한다. Databricks가
  `system.access.column_lineage` 추적 테이블을 가진 Unity Catalog로 그렇게 하는 경우가 여전히
  그렇다. 이 기능은 Azure의 Purview 서비스에도 네이티브로 있다** (10장,
  p.325).[^konieczny2025]
- 자체 구현 — **구현은 질의 실행 계획을 분석하고 각 출력 열에 대한 모든 하류 의존을 추적하는 것으로
  이뤄진다** (10장, p.326).[^konieczny2025] 저자의 예에서
  `SELECT CONCAT(u.first_name, d.delivery_address) AS user_with_address FROM users u JOIN addresses d ON d.user_id = u.id`
  라는 질의에 대해 **`user_with_address`의 하류 의존은 users 테이블의 `first_name` 열과 addresses
  테이블의 `delivery_address` 열**이 된다.
  - 그림 10-6이 그 변환을 보인다 — **계보 코드가 실행 나무를 분석해 출력 열의 모든 의존을 발견한다**
    (10장, p.326).[^konieczny2025] 실행 계획이라는 그 나무 자체의 정본은
    [질의 수명 주기와 성능](query-lifecycle-and-performance.md)이다.
- 도구 쪽 사정은 좋은 편이다 — **아파치 스파크 같은 인기 있는 데이터 처리 해법은 OpenLineage
  프레임워크 같은 데이터 계보 도구에 네이티브 지원을 갖는 경우가 많다** (10장,
  p.326).[^konieczny2025]

## 행 수준은 레코드에 실린다

- **저수준 추적은 행에 관련될 수도 있다. 여기서는 어느 잡이 각 행을 만들었는지 알고 싶을 것이다.
  구현은 이 정보를 여분의 속성이나 추가 열로 더하는 것으로 이뤄지며, 예컨대 데이터 장식 패턴을
  활용한다** (10장, p.326).[^konieczny2025] 그 장식 패턴의 정본은
  [데이터 강화와 장식 패턴](../concepts/data-enrichment-and-decoration-patterns.md)이다.
- 예제가 그 속성 목록을 구체적으로 준다 — 두 잡이 카프카 레코드 헤더에 **`job_version`·`job_name`·
  `batch_version`이라는 같은 속성을 싣고, 유일한 차이는 하류 잡에 있는 `parent_lineage` 속성인데
  거기서 상류 잡의 계보 정보와 따라서 데이터 원천을 찾을 수 있다** (10장, pp.327–328, 예제
  10-18).[^konieczny2025]
  - 그 쓸모 — **이 상류 속성을 갖는 것이 워크플로를 이해하기 쉽게 만들고, 데이터 생산자에게 여분의
    디버깅 세부를 줄 수 있으므로 그들과의 디버깅 논의를 자동으로 더 쉽게 만든다** (10장,
    p.327).[^konieczny2025]
  - **행 수준 계보는 데이터 안에 산다** — 데이터셋·열 수준이 **바깥의 서비스**에 기록되는 것과 달리,
    행 수준은 레코드 자신이 자기 출처를 들고 다닌다. 아래 시각화 공백이 그 배치에서 나온다.

## 행 수준 계보의 원전 — Message History

위의 `parent_lineage` 속성 — **레코드가 자기 상류의 계보 정보를 헤더에 싣고 다닌다** — 은 21년 전
메시징 카탈로그에 이미 이름이 붙어 있었다. Hohpe & Woolf의 *Message History*(551)다. 이름을 같은
문제에 붙인 것이 아니라 **같은 구조를 같은 이유로** 고른 것이라, 그쪽이 왜 그렇게 골랐는지가 이
페이지의 배치 결정을 설명해 준다.

- 문제 진술이 이 페이지의 첫 물음과 같다 — **느슨하게 결합된 시스템에서 메시지의 흐름을 어떻게
  효과적으로 분석하고 디버깅하는가?** (10장, p.551).[^hohpe2004] 그 어려움의 원인도 같다 —
  **메시지 수신자가 메시지 채널에서 메시지를 가져올 때, 그것은 일반적으로 어느 애플리케이션이 그
  메시지를 채널에 놓았는지 알지도 못하고 신경 쓰지도 않는다. (…) 그러나 같은 성질이 디버깅과
  의존성 분석을 아주 어렵게 만들 수 있다. 메시지가 어디로 가는지 확실치 않다면 메시지 형식 변경의
  영향을 어떻게 평가하는가?** (11장, p.551).[^hohpe2004]
  - **결합을 줄인 대가가 계보의 상실**이라는 진단이다. 이 페이지의 Dataset Tracker가 답하는
    "누구에게 물어야 하는가"와 정확히 같은 물음이고, 다만 단위가 데이터셋이 아니라 메시지다.
- 해법 — **메시지에 *Message History*를 붙여라. *Message History*는 메시지가 발생 이후 지나온 모든
  애플리케이션 또는 컴포넌트의 목록이다** (11장, p.552).[^hohpe2004]
- 누가 무엇을 더하는가 — ***Message History*는 메시지가 지나온 모든 컴포넌트의 목록을 유지한다.
  메시지를 처리하는 모든 컴포넌트(발신자를 포함해)가 목록에 항목 하나를 더한다. *Message History*는
  시스템 특유의 제어 정보를 담고 있으므로 **메시지 헤더의 일부여야 한다.** 이 정보를 헤더에 두는
  것은 그것을 애플리케이션 특유 데이터를 담는 메시지 본문으로부터 분리한다** (11장,
  p.552).[^hohpe2004]
  - 위 예제의 카프카 레코드 헤더 배치와 같은 결정이다. **제어 정보는 헤더에, 업무 데이터는 본문에** —
    두 소스가 21년을 사이에 두고 같은 자리에 같은 것을 둔다.

### 중앙 저장소를 기각한 두 이유

이 페이지가 계보를 데이터셋·열 수준에서는 **바깥의 서비스**에, 행 수준에서는 **레코드 안**에 두는
이유를 원전이 명시적으로 논증한다.

- 중앙 데이터베이스 접근이 먼저 검토된다 — **각 컴포넌트를 수정해 자기를 지나가는 각 메시지의 고유
  메시지 식별자를 *Control Bus*(540)에 발행하게 할 수 있다. 이 정보는 공통 데이터베이스, 곧
  *Message Store*(555)에 수집될 수 있다** (11장, p.551).[^hohpe2004]
- 그리고 두 이유로 물러난다 — **이 접근은 별도의 데이터 저장소를 포함해 상당한 양의 인프라를
  요구한다. 또 컴포넌트가 메시지의 이력을 살펴야 한다면 중앙 데이터베이스에 대고 질의를 실행해야 할
  텐데, 이는 데이터베이스를 병목으로 만들 위험을 안는다** (11장, p.551).[^hohpe2004]
  - **처리 중인 컴포넌트가 계보를 읽어야 한다면 계보는 데이터와 함께 있어야 한다.** 이것이 위
    [행 수준 시각화 공백](#불투명-상자와-시각화-공백과-진화-관리)의 근본 원인이기도 하다 — 데이터
    안에 사는 계보는 바깥의 시각화 도구가 볼 수 없다. 배치가 쓸모와 공백을 동시에 정한다.
- 식별자로 경로를 잇는 접근도 기각된다 — **각 메시지와 연관된 고유 메시지 ID를 쓰는 것이 자연스러워
  보일 것이다. 그러나 컴포넌트(예: *Message Router*[78])가 메시지를 처리해 출력 채널에 발행하면,
  결과 메시지는 그 컴포넌트가 소비한 메시지와 연관되지 않은 새 메시지 식별자를 받을 것이다. 따라서
  두 메시지를 나중에 연관 지을 수 있도록 들어오는 메시지에서 나가는 메시지로 복사되는 새 키를
  식별해야 할 것이다** (11장, pp.551–552).[^hohpe2004]
- 그 키마저 부족한 자리가 명시된다 — **이는 컴포넌트가 소비하는 모든 메시지에 대해 정확히 하나의
  메시지를 발행하면 꽤 잘 작동할 수 있다. 그러나 이는 *Recipient List*(249)·*Aggregator*(268)·
  *Process Manager*(312) 같은 많은 컴포넌트에는 해당하지 않는데, 이들은 전형적으로 단일 입력
  메시지에 대해 여러 메시지를 발행한다** (11장, p.552).[^hohpe2004]
  - 곧 **1:1이 아닌 변환이 있으면 식별자 사슬은 끊긴다.** 이 페이지의 Fine-Grained Tracker가
    열 수준에서 실행 계획을 읽어야 하는 이유와 같은 구조의 어려움이다 — 조인·집계·분할이 있는
    변환에서는 출력 하나가 입력 하나에 대응하지 않는다.

### 집계가 만드는 이력의 나무

- 원전이 이 경우에 두 선택지를 준다 — **컴포넌트가 발행하는 모든 메시지가 단일 메시지의 결과인 것은
  아니다. 예컨대 *Aggregator*(268)는 여러 메시지에서 수집한 정보를 나르는 단일 메시지를 발행하고,
  그 각각이 자기 이력을 가질 수 있다. (…) ① 완전한 이력을 추적하고 싶다면 *Message History*를
  계층적 트리 구조로 저장되도록 강화할 수 있다. 트리 구조의 재귀적 성질 덕에 단일 노드 아래에 여러
  메시지 이력을 저장할 수 있다. ② 대안으로 단순한 목록을 유지하고 들어오는 메시지 하나의 이력만
  보관할 수 있다. 이 접근은 하나의 들어오는 메시지가 다른 보조 메시지들보다 결과에 더 중요할 때 잘
  작동할 수 있다** (11장, p.552).[^hohpe2004]
- **이 페이지의 예제가 고른 것은 ②의 변형이다** — `parent_lineage` 속성 하나로 **상류 잡 하나**의
  계보를 잇는다 (10장, pp.327–328).[^konieczny2025] 조인이 여럿을 합치는 잡에서는 원전의 ①,
  곧 나무 구조가 필요해진다.
  - 그리고 그 대가가 원전에 이미 함축되어 있다 — 완전한 나무를 실으면 **메시지가 커진다.** 헤더에
    실리는 계보는 파이프라인 깊이에 비례해 자라므로, 깊은 파이프라인에서는 ②의 절단이 실용적
    타협이 된다. #hypothesis 원전은 이 크기 문제를 명시하지 않는다.

### 계보가 디버깅이 아니라 정확성 장치가 되는 자리

- 이 페이지 전체가 계보를 **사후 디버깅 도구**로 놓는다. 원전은 계보가 **런타임 정확성 장치**로도
  쓰이는 용례를 하나 준다 — 발행-구독으로 주소 변경을 전파하는 시스템에서 **고객 관리 시스템 자신도
  그 채널을 구독해야 하므로 자기가 방금 발행한 메시지를 받게 되고, 그 수신이 데이터베이스 갱신을
  낳고 그것이 또 다른 주소 변경 메시지를 촉발해서 무한 루프에 빠질 수 있다. 그런 무한 루프를 피하기
  위해 구독 애플리케이션은 *Message History*를 검사해 메시지가 바로 그 시스템에서 발생했는지
  판정하고, 그렇다면 들어오는 메시지를 무시할 수 있다** (11장, p.553).[^hohpe2004]
  - **계보가 있으면 사이클을 끊을 수 있다.** 양방향 복제·CDC 파이프라인이 자기가 만든 변경을 다시
    소비하지 않게 하는 장치가 이것과 같고, 그쪽은
    [변경 데이터 캡처](change-data-capture.md)에 있다.
  - 판정: 두 소스는 충돌하지 않는다. 계보를 디버깅에 쓰는 것과 루프 차단에 쓰는 것은 같은 데이터의
    두 용도이고, 다만 **후자는 계보가 신뢰할 수 있어야 한다** — 빠지거나 잘린 이력이 무한 루프를
    낳는다. 위 ②의 절단(하나의 상류만 보관)을 고르면 이 용도에는 못 쓴다.

### 오케스트레이션이 있으면 계보 태깅이 덜 필요하다

- 원전이 이 패턴을 쓰지 **않아도 되는** 조건을 명시한다 — ***Message History*는 일련의 메시지가 특정
  업무 기능이나 프로세스를 함께 수행하는 여러 다른 필터를 통해 흐를 때 가장 유용하다. 메시지가
  취하는 경로를 관리하는 것이 중요하다면 *Process Manager*(312)가 유용할 수 있다.
  *Process Manager*(312)는 들어오는 각 트리거 메시지마다 하나의 프로세스 인스턴스를 만든다. 여러
  컴포넌트를 통한 메시지의 흐름이 이제 중앙에서 관리되므로 각 메시지에 자기 이력을 태깅할 필요가
  줄어든다** (11장, p.553).[^hohpe2004]
  - **이것이 이 페이지의 "자체 구현이 입출력을 뽑는 두 수준" 중 오케스트레이션 계층 추출이 성립하는
    이유다.** 에어플로 같은 오케스트레이터가 흐름을 중앙에서 알고 있으면 계보를 데이터에 실을
    필요가 줄어든다. 반대로 이벤트 기반 코레오그래피 — 중앙 조정자가 없는 구조 — 에서는 계보가
    데이터에 실리는 것 말고 방법이 없다. 배치 결정이 아키텍처 스타일을 따라간다.
  - 그쪽 서술은 [배치 워크플로와 DAG](batch-workflows-and-dags.md)와
    [분산 잡 오케스트레이션](distributed-job-orchestration.md)에 있다.

## 불투명 상자와 시각화 공백과 진화 관리

- **커스텀 코드**(custom code) — **열 수준 계보는 실행 계획 노드를 분석해 의존을 탐지한다. 이
  접근은 네이티브 SQL 함수처럼 데이터 처리 도구의 표준 기제를 쓸 때 완벽히 잘 작동한다. 그러나
  프로그래밍 방식의 매핑 함수 같은 커스텀 로직으로 데이터를 변환하면 계보를 얻기가 쉽지 않을
  것이다. 그런 함수는 불투명 상자여서 계보 프레임워크가 출력만 볼 수 있고 코딩된 변환 로직을
  해석하고 이해할 능력이 없는 경우가 많다** (10장, p.327).[^konieczny2025]
- **행 수준 시각화**(row-level visualization) — **데이터셋 계보와 열 수준 계보는 데이터 계보
  세계의 두 흔한 범주이고 추출 쪽과 시각화 쪽 양쪽에서 널리 지원된다. 그러나 행 수준 정보는
  유용하기는 해도 거기 속하지 않는다. 그것은 데이터 품질 문제를 디버깅하고 잘못된 행을 쓴 잡을
  식별하는 데 유용할 수 있는 부가 가치에 가깝다. 불행히도 행 수준 계보는 고전적인 데이터 계보
  시각화 도구와 통합되지 않는다. 결과적으로 행 수준 계보에는 별도의 질의 계층이 필요할 것이다**
  (10장, p.327).[^konieczny2025]
- **진화 관리**(evolution management) — **오늘 당신의 열을 만드는 변환이 미래에는 바뀔 수 있다.
  따라서 완전 관리형이든 맞춤 제작이든 열 계보 해법이 이 진화 추적을 지원하는지 확인해야 한다.
  그렇지 않으면 상류 열이 바뀐 뒤 열의 기원을 정의할 때 잘못된 뷰를 얻을 수 있다** (10장,
  p.327).[^konieczny2025]
  - **계보는 시점 있는 사실이다** — 스키마가 진화하면 어제의 계보와 오늘의 계보가 다르다. 스키마
    진화 자체를 다루는 쪽은 [후진 호환과 전진 호환](../concepts/backward-and-forward-compatibility.md)이다.
