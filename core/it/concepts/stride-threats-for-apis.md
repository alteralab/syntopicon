하나의 질문: **API 표면에서 실제로 어떤 종류의 위협이 서고 각각을 무엇으로 막는가.**

## 버전 조건

> **버전 조건**: 이 페이지가 API 보안 위험 목록이라 부르는 것은 **2019년에 나온 API 전용
> 목록**이고, **2022년 저술 시점**에 그 판이 쓰였다. **목록은 주기적으로 갱신되므로 항목의
> 이름과 순위는 이 책과 현재 판이 다를 수 있다** — 저자들 자신이 그렇게 적는다 (6장,
> p.147).[^gough2022] 전송 계층 보안의 권장 판에 대한 서술도 저술 시점의 것이다. **이 KB는 그
> 목록이나 규격의 문서를 원전으로 확인하지 않았다.** 여섯 범주의 규정과 완화의 기제는 시점에
> 매이지 않는다. `stale_after`는 적지 않는다 — 이 책에는 벤더가 공표한 지원 종료일이 없다.

## 이 페이지가 담는 것과 담지 않는 것

- **담는 것은 위협 식별 단계가 실제로 세는 것이다.** 여섯 범주의 규정과, 그 각각을 API 표면에
  적용했을 때 서는 공격과 완화다.
- **담지 않는 것 셋.** 하나는 **이 단계를 둘러싼 절차 전체**이고 그 자리는
  [API 위협 모델링](../concepts/api-threat-modeling.md)이다. 둘은 **회의 시스템에 이것을 거는 장면**이고
  그 자리는 [회의 시스템 사례 연구](../concepts/conference-system-case-study.md)다. 셋은 **API 보안 위험
  목록 자체를 세 범주로 묶어 읽는 다른 소스의 서술**이고 그 자리는
  [API 보안 패턴](../concepts/api-security-patterns.md)이다.

## 여섯 글자의 규정

- **저자들은 여섯 범주의 정의를 STRIDE를 만든 두 사람의 1999년 논문에서 그대로 따온다** (6장
  각주 6, p.152).[^gough2022] 아래는 그 정의의 한국어 재서술이다 (6장,
  pp.152–153).[^gough2022]
- **위장(Spoofing)** — **사용자의 인증 정보를 침해하는 것.** 공격자가 **개인 정보나 인증 절차를
  재생할 수 있게 하는 무언가를 얻은 경우**이고, 이 범주의 위협은 **유효한 체계 사용자나 자원을
  사칭해 접근을 얻고 그럼으로써 체계 보안을 침해하는 것**과 얽힌다.
- **변조(Tampering)** — **탐지되든 안 되든 체계 데이터나 사용자 데이터를 수정하는 것.** 저장
  중이거나 전송 중인 정보에 대한 무단 변경, 디스크 포맷, 통신에 탐지 불가능한 네트워크 패킷을
  집어넣는 것, 민감한 파일에 탐지 불가능한 변경을 가하는 것이 모두 여기 든다.
- **부인(Repudiation)** — **신뢰되지 않은 사용자가 추적될 수 없는 채로 불법 연산을 수행하는
  것.** 이 범주의 위협은 **악의적이든 아니든 사용자가 잘못을 저지르고도 그것을 증명할 길 없이
  부인할 수 있는 것**과 얽힌다.
- **정보 노출(Information disclosure)** — **사용자의 사적 정보나 업무상 결정적 정보를 침해하는
  것.** 이 범주의 위협은 **보아서는 안 될 개인에게 정보를 노출한다.** 저자들이 인용하는 정의는
  **이 위협이 위장과 다른 점을 못박는다** — 여기서는 **가해자가 정당한 사용자를 사칭할 필요 없이
  정보에 직접 접근한다.**
- **서비스 거부(Denial of Service)** — **체계를 일시적으로 쓸 수 없거나 사용 불가능하게 만드는
  것.** 공격자가 **처리 시간이나 저장 공간 같은 체계 자원을 일시적으로 쓸 수 없게 만들 수 있을
  때** 이 위협이 있다. 인용된 정의는 **어떤 종류의 서비스 거부 위협은 막기가 매우 어려우므로
  최소한 그런 위협을 식별하고 근거를 세워 두어야 한다**고 적는다.
  - **저자들이 각주에서 갱신을 하나 붙인다** — **그 정의는 개별 기계에 대한 것이지만 서비스 거부
    공격이 무엇인가의 맥락은 2022년 저술 시점에도 여전히 같다. 자원을 오프라인으로 만드는 일이라는
    것**이다 (6장 각주 7, p.153).[^gough2022]
- **권한 상승(Elevation of privilege)** — **특권 없는 사용자가 특권 접근을 얻어 체계 전체를
  침해하거나 파괴하기에 충분한 접근을 갖게 되는 것.** 더 위험한 측면은 **탐지 불가능한 방식으로
  체계를 침해하는 것**이고, 그때 사용자는 **체계 관리자가 모르는 채로 특권을 이용할 수 있다.**
  인용된 정의의 맺음이 **공격자가 사실상 모든 체계 방어를 뚫고 신뢰되는 체계의 일부가 되어 무엇
  이든 할 수 있게 된다**는 것이다.
- **저자들이 붙이는 단서 둘** (6장, p.153):[^gough2022]
  - **이 머리글자를 아키텍처의 각 지점에서 체계를 평가하는 데 쓸 수 있다.**
  - **쓸 수 있는 다른 위협 모델링 방법론도 있고**, 저자들은 각주에서 둘의 이름을 든다 (6장 각주
    8, p.153).[^gough2022] **이 KB에 그 둘의 원전은 없다.**

## 적용의 규칙과 이 장의 배치

- **저자들이 이 장에서 쓰는 배치를 스스로 밝힌다** — **API 보안 위험 목록을 부각하려고 위협들을
  해당하는 STRIDE 값 아래로 묶는다.** 목적은 **STRIDE의 적용과 그 목록을 그 완화와 함께 함께
  보이는 것**이다 (6장, p.154).[^gough2022]
- **그러나 실제 적용에서 권하는 단위는 다르다** — **자기 아키텍처에서 위협을 식별할 때는 각
  프로세스와 각 연결에 STRIDE를 적용하라**는 것이고 그 이름이 **요소별 STRIDE**다 (6장,
  p.154).[^gough2022]
- **경계가 어디에 있는지가 이 적용의 출발점이다** — 저자들은 **클라이언트 애플리케이션과 API
  게이트웨이 사이에 존재하는 경계**를 가리키고, **API 게이트웨이가 흔히 네트워크의 테두리에
  있고 인터넷을 마주할 수도 있다**고 적는다 (6장, p.153).[^gough2022]
  - **테두리에서 막는 것의 값과 한계를 함께 적는다** — **테두리에서 체계를 지키면 위험이 체계
    전반에서 줄어들 수 있으나 언제나 그런 것은 아니다** (6장, p.153).[^gough2022]
  - **구역 아키텍처에서 제로 트러스트로 가는 이동은 이 장이 다루지 않고 9장으로 미룬다** (6장,
    p.153).[^gough2022] 이 KB의 그 자리는
    [암묵적 신뢰와 제로 트러스트](zero-trust-and-implicit-trust.md)다.

## 위장

- **위장은 사람이나 프로그램이 다른 사람이나 프로그램으로 가장할 수 있을 때다** (6장,
  p.154).[^gough2022]
- **완화는 인증이다** — **이뤄지는 모든 요청을 인증하고 그것이 정당한지 확인하려 해야 한다**
  (6장, p.154).[^gough2022]
- **대응하는 위험 목록 항목 하나** — **깨진 사용자 인증(Broken User Authentication)**이다. 저자들은
  **이것이 분명히 위장 범주와 관련되므로 인증 흐름이 깨지지 않게 해야 한다**고 적고, 상세를
  7장으로 미룬다 (6장, p.154).[^gough2022]
  - **그 갈고리가 갚였다** — 7장이 인증의 규정과 수단을 준다.
    [API 인증과 OAuth2의 역할과 토큰](../concepts/api-authentication-and-oauth2-tokens.md)이 그것이고,
    **이 절이 말하는 "인증 흐름"의 구체가 거기 있다** — 토큰 기반 최종 사용자 인증과 그 수명,
    시스템 간 인증의 API 키와 그 생성 규칙, 기본 인증을 API에 허용하지 말라는 권고, 그리고
    제3자가 키만으로 사용자를 대신 주장하지 못하게 하는 OAuth2의 동의 절차다.

## 변조

- **변조의 목표는 사용자나 클라이언트가 체계나 애플리케이션이나 데이터를 의도되지 않은 방식으로
  수정할 수 없게 하는 것이다** (6장, p.154).[^gough2022]
- **저자들이 드는 두 실물** — **참석자 서비스로 향하는 트래픽을 외부 위치로 돌려 참석자 서비스를
  수정하는 것**과 **참석자 사용자 데이터를 부적절하게 갱신하는 것**이다 (6장,
  p.154).[^gough2022]
- **변조가 일어나는 주된 길이 둘이다** — **페이로드 주입과 대량 할당**이다 (6장,
  p.154).[^gough2022]

## 페이로드 주입

- **페이로드 주입(payload injection)은 악의적 행위자가 API나 애플리케이션으로 향하는 요청에 악성
  페이로드를 주입하려 할 때 일어난다** (6장, p.154).[^gough2022]
- **범위가 넓다는 것을 저자들이 못박는다** — 위험 목록에서 이것은 **널리 알려진 SQL 주입만이
  아니라 어떤 사용자 입력에 대한 주입에도 걸린다** (6장, p.154).[^gough2022]
- **앞쪽 완화는 계약 검증이다** — **요청 처리 사슬의 이른 자리에서 주입 공격을 막는 것을 겨냥할
  수 있고**, 그 수단이 **API 게이트웨이로 하여금 이뤄진 요청이 정의된 계약이나 스키마에
  부합하는지 검증하게 하는 것**이다. **계약을 채우지 못하는 요청은 거부되거나 해당 트래픽이
  버려질 수 있다** (6장, p.154).[^gough2022]
  - 저자들은 **API 명세가 HTTP 요청 검증에 점점 더 쓰인다**고 적는다 (6장,
    p.155).[^gough2022] 그 명세로 검증한다는 실천의 전문은
    [OpenAPI 명세의 실무](../concepts/openapi-specification-practice.md)가 갖는다.
- **뒤쪽 완화가 반드시 함께 간다** — **API 게이트웨이에서 수행하는 입력 검증이 값어치 있다고 해서
  백엔드 서비스 안에서의 추가 입력 검증과 정제를 생략해도 된다는 뜻은 아니다.** 저자들이 그
  자리에 붙이는 말이 **믿되 검증하라**다 (6장, p.155).[^gough2022]
  - 저자들의 예에서 **API 명세가 각 필드가 받을 문자의 종류를 정의하고**, **게이트웨이가 입력
    검증을 수행해 성공할 때만 통과시킨다.** 그럼에도 **참석자 API는 공격을 막으려고 여전히 입력을
    정제해야 하고 데이터베이스와 통신할 때 준비된 구문(prepared statements)을 써야** 한다.
    **방어선이 여럿이어야 하나가 실패해도 버틴다** (6장, p.155).[^gough2022]
  - 이 조항은 이 KB의
    [마이크로서비스 보안의 원칙과 기본기](../concepts/microservice-security-principles.md)가 **심층 방어**로
    이미 갖고 있는 것과 같은 결이고, **이 소스는 그것을 API 요청 경로의 두 지점으로 구체화한다.**

## 대량 할당

- **대량 할당(mass assignment)은 데이터베이스 개체에 묶인 수정 가능한 속성이 부적절하게 바뀔 수
  있는 취약점이다** (6장, p.155).[^gough2022]
- **특히 위험한 자리** — **바탕 애플리케이션이 액티브 레코드 패턴이나 객체 관계 매핑 프레임워크가
  흔히 제공하는 자동 개체 직렬화·역직렬화를 쓸 때**다 (6장, p.155).[^gough2022]
  - 저자들은 **액티브 레코드 패턴을 데이터 객체와 그 함수들을 노출하는 관행이고 그것이 대체로
    바탕 데이터베이스 모형에 대응한다**고 각주에 규정한다 (6장 각주 9, p.155).[^gough2022]
- **저자들의 가상 사례가 기제를 보인다** (6장, pp.155–156):[^gough2022] 참석자를 조회하면
  **외부에는 읽기 전용이어야 하고 애플리케이션 코드로만 갱신되어야 할 목록 속성**이 함께
  돌아오고, 악의적 행위자가 **갱신 요청에 그 목록을 끼워 보낸다.** **개체가 데이터베이스에
  저장될 때 그 목록의 데이터는 무시되어야 한다.**
- **일반화된 진단** — **대량 할당은 클라이언트 입력 데이터가 그 파급을 생각하지 않은 채 내부
  객체에 묶일 때 전형적으로 생기고, 그것은 데이터베이스 API를 웹 기반 API로 노출할 때 자주
  따라오는 결과**다 (6장, p.156).[^gough2022] 저자들은 **바탕 데이터 모형을 노출하는 것의
  문제를 1장이 사용성 관점에서 이미 논했고 그것이 그러지 말아야 할 추가 근거를 준다**고
  가리킨다. 이 KB의 그 자리는
  [정보 은닉과 정보 누출](information-hiding-and-leakage.md)과
  [API 설계 모범 사례](../concepts/api-design-best-practices.md)다.
- **판정 하나가 이 범주를 다른 것들과 가른다** — **이 취약점은 전형적으로 API 게이트웨이 수준에서
  풀 수 있는 것이 아니고, 대신 API 구현 자체 안에서 막아야 한다** (6장, p.156).[^gough2022]

## 부인

- **STRIDE에 따르면 부인 공격은 애플리케이션이나 체계가 사용자 행위를 제대로 추적하고 기록하는
  통제를 채택하지 않아 악의적 조작이나 새 행위의 신원 위조를 허용할 때 일어난다** (6장,
  p.156).[^gough2022]
- **왜 API에서 문제가 되는가** — **API로 이뤄지는 많은 요청에 대해 요청과 페이로드와 생성된
  응답과 그에 대응하는 내부 행위의 상세를 이해하는 것이 중요하다.** **어떤 규제나 준수 사례에서는
  교환에 무엇이 있었는지를 임의로 조사해야 할 수도 있다** (6장, p.156).[^gough2022]
- **부인이 성립하면 무엇을 잃는가** — **요청이 부인될 수 있다면, 곧 공격자가 무엇을 했는지에 대한
  증거가 없다면, 공격자는 그런 악의적 행위를 하려 했다는 것을 거부하거나 동의하지 않을 수 있다**
  (6장, p.156).[^gough2022]
- **완화는 로깅과 모니터링이다** — **체계를 지나는 요청을 식별하고 무슨 일이 일어나는지 이해하려면
  로깅과 모니터링을 더해야 한다.** 저자들은 **불충분한 로깅과 모니터링이 API 보안 위험 목록의
  한 항목**이라고 적는다 (6장, p.156).[^gough2022]
- **놓을 자리와 그 뒤의 의무** (6장, pp.156–157):[^gough2022]
  - **사용자의 모든 요청이 API 게이트웨이를 흐르므로 그곳이 트래픽을 감시하고 요청과 응답을
    기록할 명백한 중앙 지점**이다. **많은 API 게이트웨이가 이 기능을 기본으로 제공한다.**
  - **다만 그 정보를 시간에 걸쳐 어떻게 저장하고 검색하고 추출할지를 이해해야 한다.**
  - **재해 복구와 업무 연속성 능력과 마찬가지로 로깅과 모니터링도 기대한 것을 실제로 잡고 있는지
    정기적으로 검증되어야 한다.**
- 이 조항이 요구하는 로그의 종류 구별은
  [로그와 트레이스](../concepts/logs-and-traces.md)가 갖는다.

## 정보 노출

- **정보 노출은 내부에서만 쓰여야 하거나 비밀로 유지되어야 할 정보를 노출하지 않는 데 초점이
  있다** (6장, p.157).[^gough2022]
- **이 범주에 드는 흔한 안티패턴이 둘**이고 **과도한 데이터 노출과 자산 관리 부실**이다 (6장,
  p.157).[^gough2022]

## 과도한 데이터 노출

- **과도한 데이터 노출(excessive data exposure)은 데이터가 부적절하게 노출되지 않게 하는 데 초점이
  있다** (6장, p.157).[^gough2022]
- **왜 생기는가** — **API가 어떻게 호출될 것인가에 대해 순진한 가정을 하기가 너무 쉽고, 체계가
  시간에 걸쳐 진화할수록 특히 그렇다.** **처음에는 내부 소비만을 의도한 API가 (좋은 의도로)
  공개될 수 있고, 신뢰되는 클라이언트 애플리케이션에만 접근 가능하던 이전 API가 공개 소비로
  열릴 수 있다** (6장, p.157).[^gough2022]
- **발견이 쉽다는 것이 위험을 키운다** — **API가 웹 애플리케이션을 통해 호출되면 2022년 저술 시점의 웹
  브라우저에 든 개발자 도구로 요청과 응답과 그에 대응하는 페이로드를 조사하기가 쉽다** (6장,
  p.157).[^gough2022]
- **책임의 자리를 저자들이 못박는다** (6장, pp.157–158):[^gough2022]
  - **API 게이트웨이에서 응답 검증을 수행하는 것은 가능하다.**
  - **그러나 무엇을 노출하고 있는지 알고 사적이어야 할 민감 데이터를 노출하지 않는 것은 API를
    짓는 사람의 책임**이다.
  - **API 게이트웨이에서의 어떤 구현도 최후의 검증으로 보아야** 한다.
- **함께 새지 말아야 할 것 둘** — **쓰이는 웹 서버의 판이나 충돌의 결과로 생성된 애플리케이션
  스택 트레이스** 같은 민감 데이터를 호출하는 클라이언트에 되돌리지 않게 해야 한다 (6장,
  p.158).[^gough2022]

## 자산 관리 부실

- **자산 관리 부실(improper assets management)은 전형적으로 체계가 진화하면서 조직이 어느 API가
  (그리고 어느 판이) 노출되어 있는지, 또는 어느 API가 내부 소비만을 위해 설계되었는지 추적을
  잃을 때 일어난다** (6장, p.158).[^gough2022]
- **저자들의 가상 사례가 기제를 보인다** (6장, p.158):[^gough2022] **프로덕션에 API의 여러 판이
  배포되어 있고 이른 판이 모든 속성을 기본으로 노출한다.** **데이터 모형이 진화하면서 개인
  식별 정보를 담은 사적 필드가 여럿 더해지고 새 판은 질의 시 그 정보를 뺀다.** 그럼에도 **옛
  판이 온전히 기능하지 않더라도 데이터 모형에 담긴 추가 정보를 빼내는 데는 여전히 쓰일 수
  있다.**
  - 또 하나의 사례가 **테스트용으로 노출했다가 잊힌 베타 엔드포인트**이고, **노출된 자산에 대한
    제대로 된 관리가 없으므로 눈에 띄지 않지만 공격자는 그 엔드포인트를 호출해 볼 수 있다**
    (6장, p.158).[^gough2022]
- **완화 둘** (6장, p.158):[^gough2022]
  - **모든 API 트래픽이 게이트웨이를 통해 관리된다면 무엇이 존재하는지 알기 위한 등록이 그 안에
    있어야** 한다. **요청을 조사해 예상치 못한 엔드포인트로 호출된 요청의 이상을 찾아볼 수도**
    있다.
  - **프로덕션에 배포된 모든 API를 목록화하고 추적하는 데 API 관리나 개발자 포털 플랫폼을 쓸 수
    있다.** **많은 API 관리 해법이 이 기능을 표준으로 포함하는데, API의 수명 주기를 관리하는 데
    필수 구성 요소로 여겨지기 때문**이다.
  - 그 플랫폼의 규정은
    [API 게이트웨이의 규정과 기능과 배치](../concepts/api-gateway-capabilities-and-deployment.md)가 갖는다.

## 서비스 거부

- **서비스 거부 공격은 악의적 목적으로 체계나 그 방어 가운데 어느 것이든 압도하려 한다** (6장,
  p.158).[^gough2022]
- **저자들이 드는 두 양상** (6장, p.158):[^gough2022]
  - **과부하된 방화벽이 모든 트래픽을 허용하는 쪽으로 기본 동작할 수 있고**, 그러면 **이전에는
    차단되었을 악의적 호출을 공격자가 할 수 있게 된다.**
  - **악의적 행위자가 그저 결정적 서비스의 가용성을 부인하려 할 수도** 있다. 저자들이 드는 예가
    **투표 사이트**이고, **트래픽으로 체계를 과부하시키면 정당한 요청이 들어갈 수 없어 아무도
    투표할 수 없다.**
- **전문 제공자에게 맡기는 자리** — **악의적 서비스 거부 공격이나 분산 서비스 거부 공격은 전문
  서비스 제공자나 소프트웨어나 하드웨어가 다루는 것이 가장 낫다.** **많은 콘텐츠 전송 네트워크
  제공자가 서비스 거부 방어를 기본으로 포함하고, 대부분의 공개 벤더가 공개 도메인 이름과 IP
  주소에 붙일 수 있는 비슷한 서비스를 제공한다** (6장, p.159).[^gough2022]
- **저자들이 경고 상자로 못박는 것 하나가 악의 없는 서비스 거부다** (6장, p.159, 경고
  상자).[^gough2022]
  - **서비스 거부는 사고로도 일어날 수 있고 저자들은 그것을 아군 오사 서비스 거부(friendly fire
    DoS)라 부른다.**
  - **체계가 진화하면서 순환 의존을 실수로 들이는 일이 드물지 않고, 조건이 맞으면 내부 서비스들이
    서로의 API를 무한 루프로 호출하는 일이 생길 수 있다.**
  - **그래서 내부 API 호출에도 속도 제한과 오류 모니터링을 구현하는 것이 값어치가 크다.**
  - 이 구도는 이 KB의 [안정성 패턴](../concepts/stability-patterns.md)이 다루는 연쇄 장애와 같은 결이고,
    **이 소스는 그것을 위협 범주 안에 놓는다.**

## 속도 제한과 부하 덜기

- **저자들이 참석자 API에 거는 완화 둘이 속도 제한과 부하 덜기다** — **API는 확장 요구를 채우되
  트래픽으로 과부하되는 것도 막아야 한다** (6장, p.158).[^gough2022]
- **둘의 규정이 갈리는 자리를 저자들이 못박는다** (6장, p.159):[^gough2022]
  - **속도 제한(rate limiting)은 일정 기간에 API로 이뤄질 수 있는 요청의 수를 제한한다.** 그
    쓰임은 전형적으로 **개별 요청의 속성에 기반해 트래픽을 거부하는 것**을 가리킨다 — 주어진
    사용자나 클라이언트 애플리케이션이나 위치에서 너무 많이 오는 경우다.
  - **부하 덜기(load shedding)는 체계 전체의 상태에 기반해 요청을 거부하는 것**을 가리킨다 —
    데이터베이스가 용량에 찼거나 더 쓸 작업자 스레드가 없는 경우다.
- **기본값이 위험하다** — **많은 애플리케이션과 웹 서버와 API 게이트웨이가 기본으로 속도 제한이나
  부하 덜기를 구현하지 않고 그에 대응하는 실패 양식이 정의되지 않았을 수 있다.** **부하 테스트를
  수행하면 한계와 파괴점과 눈에 보이는 동작에 대한 통찰을 얻을 수 있다** (6장,
  p.159).[^gough2022]
- **놓을 자리** — 사례 연구에서 **속도 제한을 구현할 가장 알맞은 위치는 API 게이트웨이**다 (6장,
  p.159).[^gough2022]
- **속도 제한을 하려면 먼저 무엇을 세는지 정해야 한다** — **전형적으로 각 요청의 발신자(또는
  집계된 요청 묶음)를 식별하려 하고**, 저자들이 드는 속성의 예가 **IP 주소, 지리적 위치,
  클라이언트가 보내는 클라이언트 ID**다. **들어오는 속성으로 제한하고 싶지 않아 모든 요청을 동등
  하게 다룰 수도** 있다 (6장, pp.159–160).[^gough2022]
- **요청 속성을 고른 다음 적용할 전략 넷** (6장, p.160):[^gough2022]
  - **고정 창(fixed window)** — **한 기간 안의 고정된 제한.** 저자들의 예가 하루에 2,400 요청이다.
  - **슬라이딩 창(sliding window)** — **마지막 기간 안의 제한.** 저자들의 예가 지난 한 시간 안에
    100 요청이다.
  - **토큰 버킷(token bucket)** — **총 요청의 정해진 수가 허용되고(토큰의 버킷) 요청이 이뤄질
    때마다 토큰 하나를 가져간다. 버킷은 주기적으로 다시 채워진다.**
  - **리키 버킷(leaky bucket)** — **토큰 버킷과 같되 요청이 처리되는 속도가 고정 속도이고 그것이
    버킷의 샘이다.**
  - **이 전략 넷은 이 KB에 없던 목록이다.** 이 KB의
    [가상 스레드 시대의 속도 제한](rate-limiting-with-virtual-threads.md)은 같은 이름을 **자원별
    퍼밋의 문**으로 다루고 알고리즘의 분류는 갖지 않았다.
- **그림에만 있고 본문에 없는 것** — 그림 6-4와 6-5는 **속도 제한과 부하 덜기 양쪽에서 게이트웨이가
  클라이언트에 같은 응답 코드(429 too many requests)를 돌려주는 것**을 그린다. 두 그림이 갈리는
  자리는 **하류다** — 속도 제한 쪽에서는 게이트웨이가 요청을 막는 표시만 있고, 부하 덜기 쪽에서는
  게이트웨이와 참석자 서비스 사이의 흐름에 **부분적 성능 저하로 부하를 던다**는 라벨이 붙는다
  (6장, 그림 6-4·6-5, p.160).[^gough2022] 본문은 응답 코드를 적지 않는다. 그 코드의 규범은
  [HTTP 클라이언트 오류 상태 코드](http-client-error-status-codes.md)가 갖는다.

## 실패할 때 열 것인가 닫을 것인가

- **저자들이 경고 상자로 못박는 결정 하나** (6장, p.159, 경고 상자).[^gough2022]
  - **API 게이트웨이와 다른 테두리 보안 도구가 실패 시 여는(fail open) 정책을 갖는지 닫는(fail
    closed) 정책을 갖는지 이해하는 것이 중요하다.**
  - **실패 시 여는 정책은 실패 조건이 있어도 서비스에 대한 접근을 계속 허용한다.** 저자들이 드는
    가상 사례가 **의료 응급 서비스에서는 요청을 인증하는 것보다 환자의 병력 정보를 제공하는 것이
    더 중요하다**는 것이다.
  - **실패 시 닫는 정책은 실패 조건에서 연결이 차단되는 것**이다.
  - **단 하나의 옳은 구현은 없고 기본값이 자기 요구를 채워야 한다.** 저자들이 드는 대비가
    **금융 API의 대다수는 기본으로 실패 시 닫기를 원할 것이고 공개 날씨 서비스는 실패 시 열기를
    구현할 수 있다**는 것이다.
- **이 결정은 이 KB에 없던 것이다.** [안정성 패턴](../concepts/stability-patterns.md)이 회로 차단과 폴백을
  갖지만 **테두리 보안 도구가 스스로 고장 났을 때의 기본값**을 정책으로 세우지는 않았다.

## 권한 상승

- **권한 상승은 사용자나 애플리케이션이 현재 보안 맥락에서 허용되어야 할 범위 밖의 작업을 수행할
  길을 찾아낼 때 일어난다** (6장, pp.160–161).[^gough2022] 저자들이 드는 예가 **관리자만
  실행하게 되어 있는 작업을 일반 사용자가 실행할 수 있게 되는 것**이다.
- **대응하는 위험 목록 항목이 둘이다** — **객체 수준 인가의 붕괴(Broken Object Level
  Authorization)**와 **기능 수준 인가의 붕괴(Broken Function Level Authorization)**다 (6장,
  p.161).[^gough2022]
- **둘의 공통점** — **둘 다 인가를 강제하고 API로 향하는 요청이 그 연산을 수행할 자격이 있는지
  확실히 하는 데 초점이 있다** (6장, p.161).[^gough2022] 저자들은 상세를 7장으로 미룬다.
  - **그 갈고리가 갚였다** — 7장 §"Authorization Enforcement"(p.185)가 둘을 각각 규정한다.
    **객체 수준 인가의 붕괴는 사용자가 접근해서는 안 될 객체의 정보를 요청할 수 있게 되는
    것**이고 **자원 식별자를 만지작거리다 발견되는 경우가 많으며**, **기능 수준 인가의 붕괴는
    사용자가 인가되지 않은 작업을 수행할 수 있게 되는 것**이다.[^gough2022] **뒤엣것의 예가 이
    절이 위에서 든 관리자 전용 작업을 일반 사용자가 실행하는 장면과 같다.** 집행의 조항과
    스코프와의 관계는
    [OAuth2 그랜트와 스코프와 신원 계층](../concepts/oauth2-grants-scopes-and-identity-layer.md)이 갖는다.

## 어느 범주에도 갇히지 않는 보안 오설정

- **보안 오설정(security misconfiguration)은 이 STRIDE 범주 가운데 하나에 국한되지 않는다** —
  **오설정은 여러 자리에서 일어날 수 있기 때문**이다 (6장, p.161).[^gough2022] 저자들이 드는
  예가 **권한이 잘못 할당된 정보 노출**과 **속도 제한 정책이 잘못 실패 시 열기로 설정된 서비스
  거부**다.
- **그래서 이것은 별도 위협이라기보다 STRIDE의 각 요소를 위협에 대해 평가할 때마다 함께 생각해야
  하는 또 하나의 조각**이다 (6장, p.161).[^gough2022]
- **저자들이 세우는 명제 하나** — **오설정된 보안을 갖는 것이 보안이 전혀 없는 것보다 나쁠 수
  있다는 것은 자명한 이치이고, 그 까닭은 사용자가 자기 행위와 데이터가 안전하지 않다고 믿을 때
  아주 다르게 행동하기 때문**이다 (6장, p.161).[^gough2022]
  - **이 명제는 이 KB의 다른 보안 페이지들에 없던 것이다.** 기존 서술은 통제의 강도와 배치를
    다루되 **통제가 있다고 믿게 하는 것 자체의 위험**을 세우지 않았다.
- **분류 하나가 따라온다** — **거의 언제나 원하게 될 보안 기능**(전송 계층 보안 같은 것)과
  **API나 설정에 따라 맞춤인 것**(IP 허용 목록 같은 것)이 갈린다 (6장, p.161).[^gough2022]
  저자들은 각주에서 **IP 허용 목록이 자기 체계에 연결하도록 허용된 IP의 말 그대로의 목록이고
  연결하는 IP가 그 목록에 없으면 요청이 거부된다**고 규정한다 (6장 각주 11,
  p.161).[^gough2022]
- **사례 연구에서의 자리** — **API 게이트웨이가 보안 오설정이 파국적 효과를 낼 수 있는 핵심
  자리이고, 게이트웨이가 현관문 노릇을 하므로 그 설정에 각별한 주의를 기울여야** 한다 (6장,
  p.161).[^gough2022]

## 전송 계층 보안 종단

- **전송 계층 보안은 받는 트래픽이 가로채여 수정되지 않았음을 확실히 해 준다.** 또한 **인증서가
  도메인 소유자에 대한 정보를 제공하므로 누구와 연락하고 있는지 확신할 수 있다** (6장,
  p.161).[^gough2022]
- **게이트웨이에서 끝내는 이유가 관리다** — **API 게이트웨이가 들어오는 모든 트래픽을 다루므로
  여기서 전송 계층 보안을 켤 수 있고**, **들어오는 요청에 대한 외부 인증서를 관리하는 중앙
  위치를 갖는 것도 편리하다.** **게이트웨이를 쓰지 않아 요청 트래픽을 다루는 웹 서버와 프록시와
  애플리케이션 각각에 인증서를 더해야 하는 것과 비교하면 관리하기가 더 어렵고 오류가 나기도 더
  쉽다** (6장, p.161).[^gough2022]
- **버전 조건이 여기 붙는다** — **현대적 프로토콜과 강한 암호화를 쓰는 것이 중요하고, 저술 시점
  기준으로는 이전 판들의 알려진 문제 때문에 TLS 1.2 이상을 쓰기를 권한다** (6장,
  p.161).[^gough2022]
  - 저자들이 각주에 붙이는 실정 하나 — **대부분의 상용 API 게이트웨이는 기본으로 현재 판만
    허용하므로, 알려진 취약점이 있는 약한 판이 필요하면 그것을 따로 켜야 한다** (6장 각주 12,
    p.162).[^gough2022]
  - 전송 보호의 관심사 전체는
    [전송 중 데이터와 정지 데이터의 보호](../concepts/securing-data-in-transit-and-at-rest.md)가 갖는다.

## 교차 출처 요청 공유

- **교차 출처 요청 공유(CORS)는 서버로 하여금 브라우저가 자원을 적재하도록 허용해야 할 자기 것
  이외의 출처(도메인·스킴·포트)를 표시하게 하는 HTTP 헤더 기반 기제다** (6장,
  p.162).[^gough2022]
- **두 조항** (6장, p.162):[^gough2022]
  - **CORS를 지원하는 것은 2022년 저술 시점의 어떤 웹 브라우저에도 핵심 요구이고, 보안상의 이유로 브라우저는
    스크립트에서 시작된 교차 출처 HTTP 요청을 제한한다.**
  - **CORS는 웹 브라우저가 원하는 호출을 해도 되는지 보려고 사전 요청(preflight)을 수행함으로써
    동작한다.**
- **어디서 볼 수 있는가** — 브라우저 개발자 도구의 네트워크 호출 절에서 **HTTP OPTIONS 요청**을
  전형적으로 볼 수 있고 **그것이 흔히 CORS 요청**이다 (6장, p.162).[^gough2022]
- **이 규정은 이 KB에 없던 것이다.** HTTP 의미론 축이 메서드와 헤더를 갖지만 **브라우저의 교차
  출처 정책이라는 층**은 갖지 않았다. OPTIONS 메서드 자체의 규범은
  [DELETE와 CONNECT와 OPTIONS와 TRACE](http-delete-connect-options-and-trace.md)가 갖는다.

## 보안 지시 강화

- **문제 진술** — **API 엔드포인트로 향하는 요청은 헤더와 데이터 페이로드를 포함해 임의의
  페이로드를 담을 수 있다.** **진짜 요청은 전부 기대한 계약에 부합하겠지만 공격자는 접근을 얻거나
  체계를 침해하려고 알려지지 않았거나 부정확하거나 기형인 헤더와 데이터를 더할 수 있다** (6장,
  p.162).[^gough2022]
- **완화 둘** — 사례 연구에서 **API 게이트웨이에 HTTP 헤더 허용 목록을 구현하고 모든 유효하지
  않은 HTTP 헤더를 제거하는 것**을 생각해야 한다 (6장, p.162).[^gough2022]
- **공격자가 노리는 것** — 저자들이 드는 실물이 **역할을 주장하거나 다른 주체를 사칭하게 하는
  꼴의 추가 HTTP 헤더를 참석자 API로 보내는 것**이고, 공격자는 **그 헤더들이 제거되지 않고
  내부적으로 쓰여 추가 특권을 줄 것을 바란다** (6장, p.162).[^gough2022]
  - 이 공격은 이 KB의
    [서비스 사이 인증과 인가](../concepts/service-to-service-authentication-and-authorization.md)가 갖는
    **혼란한 대리인 문제**와 같은 결이고, 5장이 같은 책 안에서 **하류로 무엇을 보낼지에 대한
    의견을 가지라**고 적는 자리와 맞물린다.

## 게이트웨이가 할 수 있는 것과 없는 것

- **저자들이 이 장의 맺음에서 세우는 판정 하나** — **API 기반 체계 안에서 API 게이트웨이는 식별된
  위험에 대해 고수준 완화를 자주 제공할 수 있다. 그러나 체계가 더 분산될수록 개별 서비스 구현과
  서비스 사이 통신을 언제나 함께 고려해야 한다** (6장, p.166).[^gough2022]
- **이 장이 실제로 가른 자리가 그 판정과 맞는다.** 이 페이지가 위에서 옮긴 완화 가운데
  **게이트웨이에서 되는 것**은 계약 검증, 로깅과 모니터링, 응답 검증(최후의 검증으로), 자산
  등록, 속도 제한, 전송 계층 보안 종단, 헤더 허용 목록이고, **게이트웨이에서 안 되는 것**으로
  명시된 것이 **대량 할당**이다.
- **저자들이 이 장의 요약에서 다시 세우는 것 셋** (6장, p.165):[^gough2022] **API 보안 위험
  목록이 마주할 위협을 이해하는 훌륭한 자원이라는 것**, **STRIDE가 여섯 위협에 행동을 집중시킨다는
  것**, **DREAD가 무엇을 먼저 완화할지 우선순위를 정하는 데 도움이 되는 정성적 위험 지표를
  계산하는 데 쓰일 수 있다는 것**이다.
