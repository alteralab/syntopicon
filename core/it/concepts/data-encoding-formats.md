## 언어 내장 직렬화의 네 가지 문제

- 편리하긴 하다 — **많은 프로그래밍 언어가 인메모리 객체를 바이트 열로 인코딩하는 내장 지원을
  제공한다. 예컨대 자바에는 `java.io.Serializable`, 파이썬에는 `pickle`, 루비에는 `Marshal`이 있다.
  자바용 Kryo 같은 서드파티 라이브러리도 많다. 이 인코딩 라이브러리는 추가 코드를 최소한만 써서
  인메모리 객체를 저장하고 복원할 수 있게 하므로 편리하다** (5장, p.164).[^kleppmann2026]
- 그러나 문제가 넷 열거된다 (5장, pp.164–165):[^kleppmann2026]
  - **인코딩이 흔히 특정 프로그래밍 언어에 묶여 있어 다른 언어에서 데이터를 읽기 어렵다. 그런
    인코딩으로 데이터를 저장하거나 전송하면 잠재적으로 오랫동안 현재의 프로그래밍 언어에 스스로를
    묶고, 다른 언어를 쓸 수 있는 다른 조직의 시스템과의 통합을 미리 배제하는 것이다.**
  - **같은 객체 타입으로 데이터를 복원하려면 디코딩 프로세스가 임의의 클래스를 인스턴스화할 수 있어야
    한다. 이는 빈번한 보안 문제의 원천이다 — 공격자가 애플리케이션이 임의의 바이트 열을 디코딩하게
    만들 수 있으면 임의의 클래스를 인스턴스화할 수 있고, 그것은 흔히 원격 임의 코드 실행 같은 끔찍한
    일을 하게 해 준다.**
  - **데이터의 버저닝이 흔히 이 라이브러리들에서 뒤늦게 생각된다. 빠르고 쉬운 인코딩을 의도하므로
    전진·후진 호환성이라는 불편한 문제를 자주 소홀히 한다.**
  - **효율(인코딩·디코딩에 드는 CPU 시간과 인코딩된 구조의 크기)도 흔히 뒤늦게 생각된다. 예컨대
    자바의 내장 직렬화는 나쁜 성능과 부푼 인코딩으로 악명 높다.**
- 결론 — **이런 이유로 매우 일시적인 용도가 아닌 무엇에도 언어 내장 인코딩을 쓰는 것은 일반적으로
  나쁜 생각이다** (5장, p.165).[^kleppmann2026]

## JSON·XML·CSV의 결함

- 표준 인코딩의 후보 — **여러 프로그래밍 언어가 쓰고 읽을 수 있는 표준화된 인코딩으로 옮겨 갈 때
  JSON과 XML이 명백한 경쟁자다: 널리 알려져 있고 널리 지원된다. CSV도 인기 있는 언어 독립 형식이지만
  중첩 없는 표 형식 데이터만 지원한다** (5장, p.165).[^kleppmann2026]
- 결함이 열거된다 (5장, pp.165–166):[^kleppmann2026]
  - **XML은 흔히 너무 장황하고 불필요하게 복잡하다고 비판받는다.**
  - **수의 인코딩을 둘러싼 모호성이 많다. XML과 CSV에서는 (외부 스키마를 참조하지 않는 한) 수와
    숫자로만 이뤄진 문자열을 구별할 수 없다. JSON은 문자열과 수를 구별하지만 정수와 부동소수점 수를
    구별하지 않고 정밀도를 명시하지도 않는다.**
    - 그 결과가 실제 사고로 나타난다 — **큰 수를 다룰 때 문제가 된다. 2⁵³(2의 53제곱)보다 큰
      정수는 IEEE 754 배정밀도 부동소수점 수로 정확히 표현될 수 없으므로 자바스크립트처럼 부동소수점
      수를 쓰는 언어에서 파싱하면 부정확해진다. 2⁵³보다 큰 수의 예가 X에서 나타나는데, 각 포스트를
      식별하는 데 64비트 수를 쓴다. API가 반환하는 JSON은 자바스크립트 애플리케이션의 잘못된 수
      파싱을 우회하려고 포스트 ID를 두 번 담는다 — 한 번은 JSON 수로, 한 번은 십진 문자열로.**
  - **JSON과 XML은 유니코드 문자열(곧 사람이 읽을 수 있는 텍스트)을 잘 지원하지만 이진 문자열(문자
    인코딩 없는 바이트 열)은 지원하지 않는다. 이진 문자열은 유용한 기능이므로 사람들은 이진 데이터를
    Base64로 텍스트로 인코딩해 이 한계를 우회한다. 그 뒤 스키마로 그 값이 Base64 인코딩된 것으로
    해석돼야 함을 표시한다. 이는 작동하지만 다소 편법이고 데이터 크기를 약 3분의 1 늘린다.**
  - **XML Schema와 JSON Schema는 강력하고 따라서 배우고 구현하기 꽤 복잡하다. 데이터의 올바른
    해석(수와 이진 문자열 같은)이 스키마의 정보에 의존하므로, XML/JSON Schema를 쓰지 않는
    애플리케이션은 적절한 인코딩·디코딩 로직을 하드코딩해야 할 수 있다.**
  - **CSV는 아무 스키마도 갖지 않으므로 각 행과 열의 뜻을 정의하는 것은 애플리케이션의 몫이다.
    애플리케이션 변경이 새 행이나 열을 더하면 그 변경을 손으로 처리해야 한다. CSV는 또 꽤 모호한
    형식이다(값이 쉼표나 개행 문자를 담으면 어떻게 되는가). 이스케이핑 규칙이 형식적으로 명세됐지만
    모든 파서가 그것을 올바르게 구현하지는 않는다.**
- 그럼에도 살아남는 이유 — **이런 결함에도 JSON·XML·CSV는 많은 목적에 충분히 좋다. 특히 데이터
  교환 형식으로서(곧 한 조직에서 다른 조직으로 데이터를 보내는 데) 계속 인기 있을 것이다. 이런
  상황에서는 사람들이 형식에 합의하기만 하면 그것이 얼마나 예쁘거나 효율적인지가 흔히 문제되지 않는다.
  서로 다른 조직이 무엇에든 합의하게 만드는 어려움이 다른 대부분의 걱정을 압도한다** (5장,
  p.166).[^kleppmann2026]

## JSON Schema

- 어디에 있는가 — **JSON Schema는 데이터가 시스템 사이에서 교환되거나 저장소에 쓰일 때마다 그것을
  모델링하는 방법으로 널리 채택됐다. JSON Schema는 OpenAPI 웹 서비스 명세의 일부로 웹 서비스에서,
  Confluent의 Schema Registry와 레드햇의 Apicurio Registry 같은 스키마 레지스트리에서, 그리고
  데이터베이스에서(예: PostgreSQL의 `pg_jsonschema` 검증 확장과 MongoDB의 `$jsonSchema` 검증 문법)
  발견된다** (5장, p.166).[^kleppmann2026]
- 무엇을 제공하는가 — **JSON Schema 명세는 여러 기능을 제공한다. 스키마는 `string`·`number`·
  `integer`·`object`·`array`·`boolean`·`null` 같은 표준 원시 타입을 포함한다. 그러나 JSON Schema는
  개발자가 필드에 제약을 덧씌울 수 있게 하는 별도의 검증 명세도 제공한다. 예컨대 포트 필드는 최솟값
  1과 최댓값 65,535를 가질 수 있다** (5장, p.166).[^kleppmann2026]
- 열린 모델과 닫힌 모델 — **JSON Schema는 열린(open) 콘텐츠 모델이나 닫힌(closed) 콘텐츠 모델을 가질
  수 있다. 열린 콘텐츠 모델은 스키마에 정의되지 않은 어떤 필드든 어떤 데이터타입으로든 존재할 수
  있게 허용하고, 닫힌 콘텐츠 모델은 명시적으로 정의된 필드만 허용한다. JSON Schema의 열린 콘텐츠
  모델은 `additionalProperties`가 `true`로 설정될 때 활성화되며 이것이 기본값이다. 따라서 JSON
  Schema는 보통 무엇이 허용되는가가 아니라 무엇이 허용되지 않는가(곧 정의된 필드에 대한 잘못된 값)의
  정의다** (5장, p.166).[^kleppmann2026]
- 그 위력이 복잡함을 부른다 — **열린 콘텐츠 모델은 강력하지만 복잡할 수 있다.** 저자가 든 예 —
  **정수(ID 같은)에서 문자열로 가는 맵을 정의하고 싶다고 하자. JSON에는 정수 키를 허용하는 맵이나
  딕셔너리 타입이 없다. JSON 객체는 항상 문자열을 키로 쓴다. 그 요구를 수용하려면 JSON Schema로 이
  타입을 제약해 키가 숫자만 담을 수 있고 값이 문자열만 될 수 있게 할 수 있는데, `patternProperties`와
  `additionalProperties`를 쓴다** (5장, p.166).[^kleppmann2026] 정수 키와 문자열 값을 가진 JSON
  Schema는 이렇다 (5장, p.167):[^kleppmann2026]

  ```json
  {
      "$schema": "http://json-schema.org/draft-07/schema#",
      "type": "object",
      "patternProperties": {
         "^[0-9]+$": {
           "type": "string"
         }
      },
      "additionalProperties": false
  }
  ```

- 그리고 그 위력의 값 — **열린·닫힌 콘텐츠 모델과 검증자 외에도 JSON Schema는 조건부 if/else 스키마
  로직, 이름 붙인 타입, 원격 스키마에 대한 참조 등 많은 것을 지원한다. 이 모든 것이 매우 강력한 스키마
  언어를 만든다. 그런 기능은 다루기 힘든 정의도 만든다. 원격 스키마를 해소하거나, 조건부 규칙에 대해
  추론하거나, 전진·후진 호환되는 방식으로 스키마를 진화시키는 일이 도전적일 수 있다. 비슷한 우려가
  XML Schema에도 적용된다** (5장, p.167).[^kleppmann2026]

## 이진 인코딩 — JSON의 이진 변형

- 왜 나왔는가 — **JSON은 XML보다 덜 장황하지만 둘 다 이진 형식에 비하면 여전히 공간을 많이 쓴다.
  이 관찰이 JSON용 이진 인코딩(MessagePack·CBOR·BSON·BJSON·UBJSON·BISON·Hessian·Smile 등)과
  XML용 이진 인코딩(WBXML·Fast Infoset 등)의 다량 개발로 이어졌다. 이 형식들은 더 간결하고 때로는
  파싱이 더 빠르므로 여러 틈새에서 채택됐지만, 어느 것도 JSON과 XML의 텍스트 버전만큼 널리 채택되지는
  않았다** (5장, p.167).[^kleppmann2026]
- 결정적 한계 — **이 형식 중 일부는 데이터타입 집합을 확장하지만(예: 정수와 부동소수점 수를
  구별하거나 이진 문자열 지원을 더하는 것) 그 밖에는 JSON/XML 데이터 모델을 바꾸지 않는다. 특히
  스키마를 규정하지 않으므로 인코딩된 데이터 안에 모든 객체 필드 이름을 포함해야 한다** (5장,
  p.167).[^kleppmann2026]
- 이 장이 되풀이해 쓰는 예제 레코드다 (5장, p.167):[^kleppmann2026]

  ```json
  {
       "userName": "Martin",
       "favoriteNumber": 1337,
       "interests": ["daydreaming", "hacking"]
  }
  ```

- MessagePack이 이 레코드를 인코딩할 때 첫 바이트들이 무엇을 뜻하는지 (5장,
  p.168):[^kleppmann2026]
  1. **첫 바이트 `0x83`은 뒤따르는 것이 세 필드를 가진 객체임을 나타낸다(최상위 4비트 = `0x80`,
     최하위 4비트 = `0x03`).** 객체의 필드가 15개를 넘어 필드 수가 4비트에 들어가지 않으면 다른
     타입 지시자를 받고 필드 수가 2바이트나 4바이트로 인코딩된다.
  2. **둘째 바이트 `0xa8`은 뒤따르는 것이 8바이트 길이의 문자열임을 나타낸다(최상위 4비트 = `0xa0`,
     최하위 4비트 = `0x08`).**
  3. **다음 8바이트는 ASCII로 된 필드 이름 `userName`이다. 길이가 앞서 표시됐으므로 문자열이 어디서
     끝나는지 알려 줄 마커나 이스케이핑이 필요 없다.**
  4. **다음 7바이트는 접두사 `0xa6`과 함께 여섯 글자 문자열 값 `Martin`을 인코딩한다.**
- 결과가 실망스럽다 — **이 이진 인코딩은 66바이트 길이인데, 이는 (공백을 제거한) 텍스트 JSON
  인코딩이 차지하는 81바이트보다 조금 적을 뿐이다. JSON의 모든 이진 인코딩이 이 점에서 비슷하다.
  그렇게 작은 공간 감소(그리고 아마 파싱 속도 향상)가 사람이 읽을 수 있음을 잃는 값어치가 있는지는
  분명하지 않다** (5장, p.168).[^kleppmann2026] 같은 레코드를 절반 크기로 인코딩하는 쪽이
  [프로토콜 버퍼](../concepts/protocol-buffers-encoding.md)와
  [Avro](../concepts/avro-writer-and-reader-schema.md)다.

## 스키마가 주는 것

- 오래된 착상이다 — **이 인코딩들이 기반한 착상은 결코 새롭지 않다. 예컨대 그것들은 1984년에 처음
  표준화된 스키마 정의 언어 ASN.1과 공통점이 많다. ASN.1은 여러 네트워크 프로토콜을 정의하는 데
  쓰였고, 그 이진 인코딩(DER)은 여전히 SSL 인증서(X.509)를 인코딩하는 데 쓰인다. ASN.1은 프로토콜
  버퍼와 비슷하게 태그 번호로 스키마 진화를 지원한다. 그러나 그것은 또한 매우 복잡하고 문서화가
  나빠서, 새 애플리케이션에는 아마 좋은 선택이 아닐 것이다** (5장, p.177).[^kleppmann2026]
- 독자 규약도 흔하다 — **많은 데이터 시스템이 자기 데이터를 위한 어떤 종류의 독자적 이진 인코딩을
  구현한다. 예컨대 대부분의 관계형 데이터베이스는 질의를 보내고 응답을 받는 네트워크 프로토콜을
  갖는다. 그 프로토콜은 일반적으로 특정 데이터베이스에 고유하며, 데이터베이스 벤더가 데이터베이스의
  네트워크 프로토콜에서 온 응답을 인메모리 자료 구조로 디코딩하는 드라이버(예: ODBC나 JDBC API를
  쓰는)를 제공한다** (5장, p.177).[^kleppmann2026]
- 스키마 기반 이진 인코딩의 성질 넷 (5장, pp.177–178):[^kleppmann2026]
  - **인코딩된 데이터에서 필드 이름을 생략할 수 있으므로 여러 "이진 JSON" 변형보다 훨씬 간결할 수
    있다.**
  - **스키마는 값진 형태의 문서이고, 디코딩에 스키마가 요구되므로 그것이 최신임을 확신할 수
    있다**(손으로 유지하는 문서는 쉽게 현실과 어긋난다).
  - **스키마의 데이터베이스를 유지하면 무엇이든 배포되기 전에 스키마 변경의 전진·후진 호환성을 확인할
    수 있다.**
  - **정적 타입 프로그래밍 언어 사용자에게는 스키마에서 코드를 생성하는 능력이 유용한데, 컴파일 시점
    타입 검사를 가능하게 하기 때문이다.**
- 요약 문장 — **스키마 진화는 스키마리스/읽기 스키마 JSON 데이터베이스가 제공하는 것과 같은 종류의
  유연성을 허용하면서 데이터에 대한 더 나은 보장과 더 나은 도구를 제공한다. 그래도 운영을 단순하게
  유지하려면 동시에 존재하는 스키마 형식의 수를 최소로 유지하는 것이 바람직하다** (5장,
  p.178).[^kleppmann2026]
