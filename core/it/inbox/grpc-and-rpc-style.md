하나의 질문: **원격 함수 호출을 API 스타일로 세운다는 것은 무엇을 정하는 일이고, gRPC는 그
스타일을 HTTP/2 위에서 어떻게 구현하며 무엇을 되무는가.**

## 버전 조건

> **버전 조건**: 아래 채택 판정과 도구 이름은 **2025년 저술 시점**의 것이다. "가장 널리
> 채택된 RPC 구현"이라는 순위, 공식 HTML 문서 생성 도구가 없다는 사정, HTTP/3 위의 gRPC

## RPC라는 낱말

- 규정 — **RPC는 원격 프로시저 호출(Remote Procedure Call)의 약자이고, 이름이 말하듯 RPC API
  스타일은 원격 프로시저(함수)를 불러 API와 상호작용하는 데 초점을 둔다** (8장,
  p.243).[^dynowski2025]
- **인터페이스의 성격이 의도 지향이다** — RPC API는 **의도 지향 인터페이스로 특징지어지며,
  의도는 "CreateUser"나 "GenerateReport" 같은 특정 행위(연산)를 서술한다** (8장,
  p.243).[^dynowski2025]
- **REST의 반대편에 놓인다** — 이 접근은 **REST와 견주면 스펙트럼의 반대쪽에 있다.** REST는
  **"User"나 "Report" 같은 자원의 회수와 수정에 초점을 두고 GET·POST·PUT·DELETE 같은 표준
  HTTP 메서드를 쓴다** (8장, p.243).[^dynowski2025] 자원 지향과 의도 지향의 구별 자체는 같은
  책 2장의 것이고 [API 이름과 버저닝](api-naming-and-versioning.md)에 있다.
- **gRPC의 자리** — **gRPC는 현재 가장 널리 채택된 RPC 구현일 것**이고, 스스로를 이렇게 부른다
  (8장, p.243):[^dynowski2025]

  > high performance, open source universal RPC framework.

  - **프로젝트는 구글이 만들었고 2017년에 Cloud Native Computing Foundation에 기증됐으며 그
    재단이 `https://grpc.io`에서 호스팅한다** (8장, p.243).[^dynowski2025]
- **RPC 기반 기술이 gRPC만은 아니다** — 저자들이 각주로 Apache Thrift·tRPC·JSON-RPC를 든다
  (8장, p.243).[^dynowski2025] 이 KB는 그 셋의 원전을 갖고 있지 않다.
- 잡지식 하나 — **"g"의 뜻이 릴리스마다 장난스럽게 바뀌고**, 목록은 gRPC 깃허브 저장소의
  `doc/g_stands_for.md` 문서에 있다 (8장, p.243).[^dynowski2025]

## 프로시저가 원격이 되기까지

- 출발점 — **1958년에 나온 포트란 II가 프로시저라는 개념을 도입한 첫 고급 프로그래밍 언어였다**
  (8장, p.244).[^dynowski2025]
- 규정 — **프로시저(서브루틴·함수·메서드라고도 한다)는 특정 과업을 수행하도록 설계된 코드
  덩어리**이고 **개발자가 자기 프로그램을 이해하고 조직하도록 돕는다** (8장,
  p.244).[^dynowski2025]
- **분산 체계로 넘어간 시점** — 개발자의 일을 쉽게 하려던 프로시저의 쓰임이 **1970년대
  ARPANET 같은 이른 네트워크 위에서 동작하는 분산 시스템의 영역으로 확장됐고, 그때 RPC라는
  개념이 도입됐다.** **브루스 제이 넬슨(Bruce Jay Nelson)이 1980년대 초 박사 학위 논문에서
  RPC를 더 상세히 다뤘다** (8장, p.244).[^dynowski2025]
- **RPC가 풀려던 문제가 둘로 명시된다** — 지역(단일 기계) 프로시저 호출을 닮는다는 것 말고,
  RPC의 주된 목표는 분산 체계의 도전 **둘**을 다루는 것이었다 (8장, p.244):[^dynowski2025]
  - **내부적으로 서로 다른 데이터 형식을 쓰는 서비스들 사이의 통신**
  - **신뢰할 수 없는 네트워크 위의 통신**
- **넬슨의 설계가 다루지 않은 것도 함께 적힌다** — **서비스 장애나 전역 시계의 부재 같은 다른
  도전은 다루지 않는다. 그럼에도 현대의 RPC 구현은 그 도전 가운데 일부를 다룰 수 있다 — 예컨대
  호출 타임아웃을 지원함으로써** (8장, p.244).[^dynowski2025]
- **이 목록이 이 KB의 [원격 프로시저 호출의 문제](../concepts/remote-procedure-call-problems.md)와
  겨루지 않는다.** 그쪽은 **원격 호출을 지역 호출처럼 보이게 만드는 것이 왜 잘못된 목표인가**를
  묻고, 여기는 **RPC가 애초에 무엇을 풀려 했는가**를 적는다. 대조는 아래
  [이 KB의 이웃과 맞대는 자리](#이-kb의-이웃과-맞대는-자리)에 있다.

## gRPC의 유래

- **Stubby가 앞에 있다** — **gRPC는 구글이 2000년대 초부터 개발해 써 온 내부 RPC 프레임워크
  Stubby에서 유래한다** (8장, p.244).[^dynowski2025]
- **왜 그것을 그대로 열지 않았는가** — **Stubby는 구글의 이름 해석(name resolution)과 로드
  밸런싱 인프라에 묶여 있었고, 그래서 오픈 소스 RPC 프레임워크를 만들려는 구글의 계획에는 맞지
  않았다. 그래서 gRPC는 2013년에 맨바닥에서 시작됐고, HTTP/2 명세가 확정되던 무렵에 함께
  진화했다. gRPC의 첫 안정 릴리스는 2016년에 나왔다** (8장, p.244).[^dynowski2025]
- **설계 목표가 넬슨의 것보다 넓다** — **gRPC의 설계 목표는 넬슨이 서술한 것과 비슷하되, 분산
  체계 구축을 쉽게 하려고 상태 점검(health-checking)·로드 밸런싱·장애 조치(failover) 같은
  기능도 포함한다** (8장, p.245).[^dynowski2025]

## 데이터 흐름 — 채널과 스텁과 전송

**그림 8-1이 배치하는 것이고 본문이 그 흐름을 문장으로 따라간다** (8장 §"gRPC ECHO Server and
Client", p.253).[^dynowski2025]

- **채널이 클라이언트 런타임의 핵심이다** — **gRPC 클라이언트 런타임의 핵심은 이른바
  채널(Channel)이고 클라이언트 애플리케이션이 그것을 시작한다. 채널은 gRPC 서버로의 연결에 대한
  추상을 나타낸다** (8장, p.253).[^dynowski2025]
- **서버 쪽의 대응물** — **서버는 gRPC 서버 런타임의 주된 구성 요소이고 서버 애플리케이션이
  그것을 시작한다** (8장, p.253).[^dynowski2025]
- **한 왕복의 순서**가 그대로 적힌다 (8장, p.253):[^dynowski2025]
  1. **클라이언트 애플리케이션이 요청 메시지를 클라이언트 스텁에 넘기고, 스텁이 메시지를
     직렬화하고 RPC 호출을 시작한다.**
  2. **채널이 전송(Transport)을 만들고 그 위로 RPC 호출을 적절한 gRPC 서버로 보내는 일을
     맡는다.**
  3. **듣고 있던 gRPC 서버가 최초 연결을 받은 뒤 자기 쪽 전송을 만들고 메시지를 서버
     스텁(핸들러)에 넘긴다.**
  4. **서버 스텁이 메시지를 역직렬화하고 서버 애플리케이션을 지역 호출한다.**
  5. **서버 애플리케이션이 서버 쪽 로직을 수행하고 응답 메시지를 직렬화하라고 서버 스텁에
     넘긴다.**
  6. **응답 메시지가 전송을 건너가 클라이언트 스텁에서 역직렬화되고 클라이언트 애플리케이션으로
     돌아간다.**
- **그림 8-1에만 있고 본문에 없는 것 둘이다.** 하나는 **보내는 길(Send path)과 받는 길(Receive
  path)이 화살표 둘로 갈려 그려진다**는 것이고, 다른 하나는 **"gRPC 런타임"이라 이름 붙은 상자가
  채널과 전송(서버 쪽은 서버와 전송)만 감싸고 스텁은 그 상자 밖에 놓이며 "생성된 코드"라는
  괄호가 붙는다**는 것이다 (8장, 그림 8-1, p.253).[^dynowski2025] 곧 **생성된 코드는 런타임의
  일부가 아니라 애플리케이션과 런타임 사이의 층**으로 그려져 있다.
- 서버가 언제 전송을 완성하는지도 적힌다 — **서버는 배경에서 시작돼 클라이언트 연결을 듣기
  시작하고, 첫 연결이 도착해야만 전송의 생성을 마친다** (8장, p.256).[^dynowski2025]

## 채널이 추상인 이유

- **왜 연결이라 부르지 않는가** — 클라이언트를 만드는 일은 **TCP 포트 50051의 gRPC 서버로의
  연결에 대한 추상인 채널을 정의하는 것에서 시작한다. 그것이 추상인 까닭은 gRPC가 클라이언트 쪽
  로드 밸런싱을 지원해 서버가 여러 IP 주소로 해석될 수 있기 때문이다. 클라이언트와 실제 서버
  사이의 모든 연결은 서브채널(subchannel)이 다루지만 이 책은 그 기능을 더 다루지 않는다** (8장,
  p.257).[^dynowski2025]
- **채널은 아껴 쓰는 자원이다** — **효율을 위해 채널 하나가 여러 클라이언트 스텁을 다룰 수
  있다.** 그리고 더 현실적인 예에서는 **채널을 곧바로 닫지 않고 클라이언트의 수명 동안 재사용해
  여러 호출을 수행함으로써 채널 생성 비용을 되풀이하지 않는다** (8장,
  p.257).[^dynowski2025] 같은 권고가 피드 구현에서도 되풀이된다 — **채널과 스텁을 재사용해 자원
  이용을 줄이라고 권장되므로 그 예제는 둘을 클래스 속성으로 만든다** (8장,
  p.275).[^dynowski2025]
- **그 긴 수명이 되돌려 주는 대가를 저자들이 각주에 적는다** — **gRPC는 지연을 줄이려고 수명이
  긴 TCP 연결을 유지하고, 이것은 로드 밸런서의 백엔드에서 부하 불균형을 낳는 경향이 있다** —
  예로 **쿠버네티스 ClusterIP 서비스 뒤의 파드들**이 든다 (8장, p.253).[^dynowski2025]

## RPC 유형 넷

**gRPC가 지원하는 RPC 유형이 넷이고, 스트리밍 쪽에 `stream` 키워드가 붙는다** (8장 §"The Four
RPC Types", pp.258–259).[^dynowski2025] 그 키워드가 실제로 어디 붙는지는
[프로토버프 계약과 코드 생성](protobuf-contract-and-code-generation.md)의 `.proto` 정의에서
볼 수 있다.

- **단항 RPC(Unary RPC)** — **클라이언트 요청 하나와 그 뒤를 잇는 서버 응답 하나로 이뤄진다.**
  이 유형은 **HTTP 기반 API에서 알려진 요청-응답 모델에 대응한다** (8장,
  p.258).[^dynowski2025] "단항"이라는 말은 **요청과 응답이 각각 메시지 하나로 이뤄진다**는
  뜻이다 (8장, p.246).[^dynowski2025]
- **서버 스트리밍 RPC** — **클라이언트 요청 하나 뒤에 서버가 응답 하나 이상을 보내는 것으로
  이뤄진다.** 전형적인 쓸 자리는 **갱신 통지**다 — 클라이언트가 자원의 변경(예: 설정 변경)을
  지켜보기 시작하라고 요청을 보내면 서버가 갱신의 스트림으로 응답한다 (8장,
  p.258).[^dynowski2025]
  - 파일 예로 더 갈라 준다 — **서버 스트리밍으로는 파일 내려받기를 곧바로 구현할 수 있지만
    이어받기(resume) 지원이 없고, 그러려면 애플리케이션 재시도 로직이 필요하다** (8장,
    p.258).[^dynowski2025]
- **클라이언트 스트리밍 RPC** — **클라이언트 요청 하나 이상 뒤에 서버 응답 하나가 오는 것으로
  이뤄진다.** 쓸 자리의 예가 **로그를 서버로 밀어 넣는 것**이고, **이어받기 없이 파일을 조각으로
  올리는 것**도 곧바로 된다 (8장, p.258).[^dynowski2025]
- **양방향 스트리밍 RPC** — **클라이언트 요청과 서버 응답이 임의의 수만큼 오가는 것으로
  이뤄진다.** **채팅 애플리케이션이나 이어받기가 되는 파일 내려받기·올리기** 같은 쓸 자리를
  쉽게 한다 (8장, p.258).[^dynowski2025]
  - **양방향 스트리밍은 전이중 전송 방식을 따른다** (8장, p.262).[^dynowski2025] 전이중이라는
    낱말의 규정은 같은 책 1장의 것이고 [API 개념과 스타일 분류](api-concepts-and-styles.md)에
    있다.
- **저자들이 스트리밍을 권하지는 않는다.** 각주에 **스트리밍 RPC에는 도전이 따른다**고 적고
  에릭 앤더슨의 강연을 2차 경유로 인용한다 (8장, p.258):[^dynowski2025]

  > most RPCs should be unary RPCs.

  - 같은 각주가 덧붙인다 — **단항 RPC와 마찬가지로 스트리밍 RPC도 동기와 비동기 양쪽으로 구현될
    수 있다** (8장, p.258).[^dynowski2025] 본문은 동기 쪽만 다룬다고 밝힌다 (8장,
    p.255).[^dynowski2025]
- **서버 쪽과 클라이언트 쪽 코드의 전체 구조는 유형과 무관하다** — **단항을 쓰든 스트리밍을
  쓰든 서버와 클라이언트의 전반적 구조는 같다** (8장, p.254).[^dynowski2025]
- 언어에 붙는 조건 하나 — **파이썬에서 gRPC 스트림은 이터레이터를 쓸 것을 요구하고**, 예제는
  `yield`로 만든 제너레이터를 그 방법으로 쓴다 (8장, p.262).[^dynowski2025]

## 네 유형이 실제로 내는 출력

**같은 ECHO 서비스에 네 유형을 다 구현해 "Hello"를 보낸 관찰 기록이다** — 스트리밍 쪽은 그
문자열의 글자 하나하나를 다루도록 설계돼 있다 (8장, pp.259–260).[^dynowski2025]

- **단항** — 요청 `Hello` 하나에 응답 `Hello` 하나.
- **서버 스트리밍** — 요청 `Hello` 하나에 응답이 `H`·`e`·`l`·`l`·`o` 다섯.
- **클라이언트 스트리밍** — 요청이 `H`·`e`·`l`·`l`·`o` 다섯이고 응답이 `Hello` 하나.
- **양방향 스트리밍** — 요청과 응답이 글자마다 번갈아 나온다.
  - **그 번갈아 나오는 모양은 저자들이 만든 것이다** — 클라이언트 스트림의 요청 사이에 1초를
    재우는데, **그 잠의 목적은 클라이언트를 늦춰 클라이언트 스트림과 서버 스트림의 글자가
    잇따라 나타나게 하는 것**이고 **전이중이라서 그렇게 할 수 있다** (8장,
    p.262).[^dynowski2025] 곧 이 출력은 전이중의 증거이지 성능 측정이 아니다.

## 전송은 HTTP/2다

**이 절이 네트워크 수준에서 gRPC를 설명한다.** 저자들이 그 수준을 왜 보는지도 적는다 — **채택을
계획할 때, 다른 RPC 구현과 벤치마크를 돌릴 때, 통신 실패를 디버깅할 때 도움이 된다** (8장
§"Protobuf Wire Format", p.262).[^dynowski2025] 문제 해결의 주된 길은 **로깅의 양을 늘리는
것**이라고 각주가 적는다 (8장, p.262).[^dynowski2025]

- **전송 기제가 HTTP/2다** — **gRPC는 HTTP/2를 전송 기제로 쓴다.** 그리고 **gRPC의 HTTP/2 전송
  기제는 HTTP/2 자신이 쓰는 TCP 전송 프로토콜과 구별돼야 한다** (8장,
  p.264).[^dynowski2025] HTTP/2의 프레임과 스트림과 HPACK이 무엇인지는 같은 책 4장의 것이고
  [HTTP/2와 HTTP/3의 다중화와 QUIC](http-multiplexing-and-quic.md)에 있다. 이 페이지는 그것을
  되풀이하지 않는다.
- **요청은 POST다** — **gRPC 요청은 HTTP POST로 서버에 보내진다** (8장,
  p.264).[^dynowski2025]
- **HTTP/2에서 얻는 것 넷이 열거된다** (8장, p.264):[^dynowski2025]
  - **헤더의 HPACK 압축 형식이 HTTP/1 구현과 견주어 gRPC 요청의 크기를 줄인다.**
  - **gRPC는 HTTP/2 흐름 제어를 쓴다.**
  - **HTTP/2의 독립적인 양방향 스트림이 gRPC 스트리밍을 가능하게 한다.**
  - **HTTP/2 프레임의 이진 부호화가 프로토버프의 이진 형식과 맞물린다.**
- **HTTP/3 쪽은 아직 아니다** — 각주가 **HTTP/3 위의 gRPC 지원 제안은 완료됐으나 저술 시점에
  구현이 많지 않다**고 적는다 (8장, p.264).[^dynowski2025]

## End Stream과 반폐쇄와 트레일러

- **클라이언트가 스트림을 닫는 방식** — **클라이언트는 HTTP/2의 End Stream 플래그로 더 보낼
  데이터가 없음을 서버에 알린다. 클라이언트는 이른바 반폐쇄(half-closed) 상태로 들어가고, 그
  상태에서 서버는 응답을 계속 보내되 클라이언트의 추가 데이터는 거부한다** (8장,
  p.264).[^dynowski2025]
- **유형에 따라 그 시점이 갈린다** — **이 요청이 단항이므로 클라이언트는 End Stream을 곧바로
  보낸다. 클라이언트 스트리밍이나 양방향 스트리밍이라면 클라이언트는 자기 스트림의 끝에서만
  End Stream을 보낼 것이다. 서버도 End Stream을 써서 자기 응답의 끝을 클라이언트에 알린다**
  (8장, p.264).[^dynowski2025]
- **상태는 트레일러가 싣는다** — **서버는 HTTP 트레일러를 써서 gRPC 응답 상태 정보를
  클라이언트에 준다. 트레일러는 HTTP 헤더와 비슷하되 HTTP 메시지 본문 뒤에 보내진다** (8장,
  p.264).[^dynowski2025]
- **이 한 줄이 뒤의 단점 하나를 낳는다** — 각주가 잇는다. **트레일러는 "Hypertext Transfer
  Protocol—HTTP/1.1" 명세의 일부이고, 자바스크립트 fetch API에 그 구현이 없다는 것이 gRPC가 웹
  브라우저에서 지원되지 않는 이유 가운데 하나다** (8장, p.264).[^dynowski2025] 아래
  [되무는 것 다섯](#되무는-것-다섯)의 첫째가 그 귀결이다.

## 그림 8-2가 선 위에서 보여 주는 것

**단항 요청 하나를 와이어샤크로 연 화면이고, 저자들이 번호 넷으로 짚는 자리 말고도 본문에 없는
것이 화면에 남아 있다** (8장, 그림 8-2, p.263).[^dynowski2025] 아래 둘은 **그림에만 있고 본문이
말하지 않는다.**

- **HEADERS 프레임이 실어 나르는 헤더들**이 보인다 — `:path`가
  `/echo.v1.EchoService/DemoUnary`이고 `:method`가 `POST`, `:scheme`이 `http`,
  `content-type`이 `application/grpc`, `te`가 `trailers`,
  `grpc-accept-encoding`이 `identity, deflate, gzip`, `user-agent`가
  `grpc-python/1.67.1 grpc-c/44.0.0 (linux; chttp2)`다. 본문은 경로가 생성된 코드에 박힌다는
  것만 적고 미디어 타입도 `te: trailers`도 적지 않는다.
- **프로토버프 바이트 앞에 다섯 바이트가 더 있다** — 화면의 gRPC 메시지 층이 **압축 플래그가
  "압축되지 않음"이고 메시지 길이가 7**이라고 읽고, 덤프 줄이 `00 00 00 00 07` 뒤에
  `0a 05 48656c6c6f`를 보인다. 곧 **프로토버프 메시지가 그대로 프레임에 실리는 것이 아니라 gRPC의
  길이 접두가 한 겹 더 붙는다.** 본문은 이 다섯 바이트를 설명하지 않는다.
- 응답 쪽도 같은 화면에 있다 — 패킷 목록이 `HEADERS[1]: 200 OK`와
  `DATA[1] (GRPC) (PROTOBUF) echo.v1.DemoUnaryResponse content=Hello`를 보인다.
- **바이트 자체가 무엇으로 되어 있는가는 이 페이지의 물음이 아니다** — 태그와 길이와 값이
  이루는 형식은 [프로토콜 버퍼와 필드 태그](../concepts/protocol-buffers-encoding.md)에 있다.

## 구현이 쓰는 기능들

**저자들이 고른 쓸 자리가 서비스 간 통신이다** — **gRPC의 주된 쓸 자리는 서비스 대 서비스
통신**이고, 이 절은 7장에서 만든 [웹 피드](web-feeds-and-syndication.md)의 Atom 피드를 살찌우는
enricher 서비스를 짓는다 (8장 §Implementation, p.266).[^dynowski2025] 도시의 현재 날씨 요약과
관광객을 위한 권고를 **지역에서 도는 LLM이 생성**해 피드 항목에 넣는다. 아래는 그 과정에서
드러나는 gRPC 기능들이고, 구현 코드 자체는 이 KB의 물음이 아니다.

- **인터셉터(interceptor)** — **미들웨어와 비슷하다. 이름이 말하듯 모든 RPC를 가로채 어떤 기능을
  수행한 다음 인터셉터 사슬의 다음으로 RPC를 넘긴다. 클라이언트(채널 위)와 서버 양쪽에서 구현될
  수 있고, 흔한 쓸 자리는 캐싱·로깅·인증이다** (8장, p.269).[^dynowski2025]
  - 예제의 캐시는 파이썬 사전 하나이고, **저자들 스스로 더 현실적인 캐시라면 크기가 제한되고
    오래된 항목을 비우는 TTL 기능이 있을 것**이라고 적는다 (8장, p.270).[^dynowski2025]
  - 캐시 열쇠가 **직렬화된 요청 바이트열**이다 (8장, p.270).[^dynowski2025]
- **오류 상태가 두 단계다** (8장, pp.272–273):[^dynowski2025]
  - **기본 오류 상태**는 RPC를 중단하며 gRPC 상태 코드(예: `InvalidArgument`)와 메시지를
    돌려준다.
  - **풍부한 오류 상태(rich error status)**는 거기에 **Details 필드를 더 담는다.** 관찰된
    출력에서 그 필드는 어느 필드가 어떤 범위를 어겼는지를 타입 붙은 문서로 싣는다.
- **데드라인(deadline)** — **데드라인은 그 시점 뒤로는 클라이언트가 서버 응답을 기다리지 않고
  `DEADLINE_EXCEEDED` gRPC 상태 코드로 RPC를 끝내는 시점을 정의한다** (8장,
  p.272).[^dynowski2025]
  - **전파가 이 기능의 핵심이다** — **마이크로서비스 아키텍처에서 gRPC 서버가 다른 gRPC 서버의
    클라이언트 노릇을 할 수 있다. 그래서 gRPC는 최초 데드라인의 전파를 지원한다. 최초 RPC 요청이
    도중에 더 많은 RPC를 촉발하더라도 재시도를 포함해 원래 데드라인이 지켜진다. 이 동작은 도착할
    가망이 거의 없는 응답을 기다리며 메모리 같은 자원을 쓸데없이 묶어 두는 것을 피하는 데
    쓸모 있다** (8장, p.272).[^dynowski2025]
- **wait-for-ready** — 피드 쪽 클라이언트는 이 기능으로 **요청을 보내기 전에 gRPC 서버가
  가용해지기를 스텁이 기다리게** 한다. **클라이언트가 데드라인을 쓴다면 그 데드라인은 기다리는
  시간에도 적용된다** (8장, p.276).[^dynowski2025]
- **관찰된 사실 하나** — 첫 호출이 **몇 분 걸릴 수 있고** 그 까닭은 **모델 가중치가 첫 사용 때
  내려받아지기 때문**이며, 지역에서 도는 모델이 프롬프트에 답을 생성하는 데도 시간이 든다 (8장,
  p.274).[^dynowski2025] 그래서 피드 리더의 내려받기 제한 시간을 600초로 올려 설정한다 (8장,
  p.273).[^dynowski2025] **저자들은 어느 모델을 쓰는지 이 장 어디에도 적지 않는다.**
- **저자들이 이 절을 닫는 문장이 이 페이지에서 가장 무거운 판정이다** (8장,
  p.276):[^dynowski2025]

  > This implementation of RPC may give you a flavor of the convenience provided by local
  > calls. With an additional development effort, it may be possible to expand this
  > convenience to operational domains such as creation of API documentation, encryption and
  > authentication, resiliency, or observability, but these features aren't available in gRPC
  > out of the box.

  - 곧 **지역 호출의 편의는 호출 지점에서만 주어지고, 문서·암호화와 인증·회복력·관측 가능성은
    별도의 개발 노력**이라는 것이다. 각주가 드는 실물이 넷플릭스의 강연이고, 거기서 언급된 개선
    다수가 **넷플릭스가 내부적으로 만든 gRPC의 사유 확장으로 존재한다**고 적는다 (8장,
    p.276).[^dynowski2025]

## 보안

- **출발점이 전송에서 온다** — **gRPC는 HTTP/2 프로토콜에 기반하므로 그것에 딸린 보안 위험을
  물려받는다** (8장 §Security, p.276).[^dynowski2025] 그 일반 위험은 같은 책 2장이 세 범주로
  묶은 것(인증과 인가·인벤토리 관리·자원 관리)이고 [API 보안 패턴](api-security-patterns.md)에
  있다.
- **쓰이는 자리가 위험을 부른다** — **가장 흔한 gRPC 쓸 자리가 서비스 대 서비스 통신이고 그것은
  보통 사설 네트워크 안에서 일어난다. 그런 배치에서는 경계 기반 컴퓨터 네트워크 관리에서 알려진
  덜 안전한 관행을 채택할 유인이 생긴다** (8장, p.276).[^dynowski2025]
  - 저자들이 그 낱말을 규정한다 — **경계 기반 컴퓨터 네트워크의 보안은 네트워크 경계에서 접근을
    통제하는 데 기대고 경계 안쪽의 트래픽은 덜 살핀다. 이 접근은 어떤 트래픽도 기본으로 신뢰하지
    않는 제로 트러스트 네트워크와 대비된다** (8장, p.277).[^dynowski2025]
- **구체적으로 무엇이 느슨해지는가** — **인증의 관점에서 경계 모델은 표준 TLS 암호화와 서버
  인증으로 충분하다고 가정할 수 있고 흔히 수명이 긴 인증서와 함께 쓰인다. 그 결과 체계가
  클라이언트 내부자 공격에 열린다** (8장, p.277).[^dynowski2025]
- **mTLS가 한 걸음이되 값이 붙는다** — **mTLS 채택은 한 걸음 나아간 것이지만 추가되는 열쇠와
  인증서 관리 때문에 운영상의 도전을 낳는다. SPIRE 프로젝트가 mTLS를 자동화하는 수단을 제공하되
  그 초점은 주로 클라우드에 호스팅된 체계다. mTLS 말고도 gRPC는 토큰 기반 클라이언트 인증을
  지원하며, 그것은 또 한 겹의 보안을 주지만 마찬가지로 추가 운영 노력을 요구한다** (8장,
  p.277).[^dynowski2025]
  - mTLS가 무엇을 더하는지는 서버 설정 쪽에도 적힌다 — **TLS처럼 암호화와 서버 인증을 주고,
    거기에 더해 클라이언트를 서버에 인증한다** (8장, p.256).[^dynowski2025] 그 구별의 원전 층은
    [전송 중 데이터와 정지 데이터의 보호](../concepts/securing-data-in-transit-and-at-rest.md)에 있다.
- **gRPC 고유의 위험이 리플렉션이다** — **gRPC 서버에서 켤 수 있는 리플렉션 기능에 특유의 보안
  위험이 딸린다. 리플렉션은 클라이언트가 서버가 제공하는 API에 대한 정보를 발견하게 해 준다.
  리플렉션을 켜 둔 채로 두는 것은 서비스와 RPC 메서드와 메시지 타입을 열거할 수 있게 하므로
  보안 위험이고, 이 정보의 노출은 표적 공격으로 이어질 수 있다** (8장,
  p.277).[^dynowski2025]

## 문서화

- **공식 도구가 없다** — **저술 시점에 Swagger UI나 GraphiQL에 준하는, 개발자를 향한 HTML 기반
  문서를 생성하는 공식 gRPC 지원이 없다. 그 목표를 이루려는 도구들은 나타났다 사라지고, 더 큰
  gRPC 프로젝트들은 비공식 도구를 쓰거나 쿠버네티스처럼 맞춤 생성기를 유지한다** (8장
  §Documentation, p.277).[^dynowski2025]
- **그래서 남는 것이 둘이다** (8장, p.277):[^dynowski2025]
  - **작은 프로젝트에서는 프로토버프 파일 자체를 정적 gRPC 문서로 다룰 수 있다.**
  - **리플렉션이 온라인 문서를 제공한다.** 그것은 **서비스와 RPC 메서드와 메시지의 발견**을
    특징으로 한다. **리플렉션은 기본으로 꺼져 있고 서비스마다 켤 수 있다.**
- **리플렉션이 실제로 무엇을 내놓는지가 관찰된다** (8장, p.278):[^dynowski2025]
  - 서비스 목록에 **응용 서비스와 리플렉션 서비스 자신이 함께** 나온다.
  - 서비스를 서술하면 **그 서비스의 rpc 하나와 요청·응답 타입의 전체 이름**이 나온다.
  - 메시지를 서술하면서 **기본값으로 채운 메시지 틀**을 달라고 할 수 있고, 그 틀이 빈 문자열과
    0과 `1970-01-01T00:00:00Z`를 채워 보인다. 곧 **프로토버프의 기본값 규칙이 이 틀에서 눈으로
    확인된다.**
- 리플렉션이 계약을 드러낸다는 바로 그 성질이 위 [보안](#보안)의 위험이다. **문서와 공격면이 같은
  스위치에 달려 있다.** 같은 저울이 같은 책 6장의 인트로스펙션에도 있고
  [GraphQL과 REST의 대조와 그 대가](graphql-versus-rest-trade-offs.md)가 그것을 담는다.

## 얻는 것 다섯

**저자들이 장점으로 드는 것이 다섯이다** (8장 §Trade-Offs, pp.278–279).[^dynowski2025]

- **성능** — **이진 직렬화 형식인 프로토콜 버퍼와 HTTP/2 헤더 압축이 합쳐져 JSON/XML 기반이나
  HTTP/1 기반 API와 견주어 네트워크로 전송되는 적재물이 작아진다. gRPC는 클라이언트 쪽과 서버 쪽
  구현을 모두 통제하고 그것이 최적화를 쉽게 한다. 파이썬 구현이 쓰는 gRPC 핵심 라이브러리는
  C++로 쓰여 있다. 그 덕에 파이썬의 전역 인터프리터 락(GIL)이 낳는 성능 제약을 완화할 수 있고,
  그것이 gRPC가 기계 학습 체계의 백엔드에 쓰이는 이유 가운데 하나다.**
- **분산 체계 지원** — **역사적으로 RPC의 목표 가운데 하나가 네트워크의 신뢰할 수 없음에서
  오는 도전을 다루는 것이었다. gRPC는 요청 데드라인·요청 취소·클라이언트 쪽 로드 밸런싱·흐름
  제어·서버 상태 점검·캐싱·재시도처럼 분산 체계를 짓는 데 쓰이는 개념들의 현대적 구현이다.
  그래서 마이크로서비스 아키텍처처럼 네트워크로 통신하는 서비스가 많은 체계에 알맞다.**
- **API 계약** — **프로토콜 버퍼의 메시지와 서비스가 클라이언트와 서버 사이에 타입 붙은 API
  계약을 정의하고, 그 계약은 맞춤 애플리케이션 로직 구현의 바탕으로 자동 생성된 코드를 쓰게 함으로써
  강제된다.** 그리고 **gRPC로 일한다는 것은 API 우선 접근이고, 깨는 변경을 만들기 전에 계획을
  요구한다.** 계약 쪽 전문은
  [프로토버프 계약과 코드 생성](protobuf-contract-and-code-generation.md)에 있다.
- **스트리밍 지원** — 단항에 더해 서버·클라이언트·양방향 스트리밍 셋을 지원하고, **양방향
  스트리밍은 전이중 전송 방식을 허용해 네트워크로 오가는 메시지에 대한 완전한 통제를 준다.**
  저자들이 거기서 한 걸음 더 나간다 — **이것이 개발자가 gRPC로 맞춤 애플리케이션 계층 프로토콜을
  짓게 해 준다.**
- **다중 언어 지원** — **gRPC는 새 기능을 더할 때 자바와 고 구현에 먼저 초점을 두는 경향이 있다.
  그 기능들이 이어 C++ 구현으로 들어가고, 그것이 C++·파이썬·루비·오브젝티브-C·PHP 같은 다른
  언어를 떠받치는 바탕 라이브러리다. .NET과 Node.js와 몇몇 언어별 구현도 따로 있다. 프로토버프
  덕분에 서로 다른 언어로 쓰인 클라이언트와 서버가 통신할 수 있으나, 기능 차이가 존재하는
  경향이 있다.**

## 되무는 것 다섯

**단점도 다섯이다** (8장 §Trade-Offs, pp.279–280).[^dynowski2025]

- **제한된 브라우저 지원** — **웹 브라우저는 gRPC를 기본으로 지원하지 않는다.** 제한적인 지원이
  **grpc-web이나 프록시를 끼우는 grpc-Gateway를 통해, 또는 HTTP 트레일러를 요구하지 않는 RPC용
  변형 HTTP인 Connect Protocol을 써서** 존재한다. 그 원인은 위
  [End Stream과 반폐쇄와 트레일러](#end-stream과-반폐쇄와-트레일러)에 있다.
- **코드 생성의 도전** — **맞는 판의 protoc으로 코드를 생성하거나(구글의 gRPC 개발자들이 권하는
  접근) 생성된 코드를 클라이언트와 서버에 배포하는 일에서 운영상의 도전이 생긴다. 어느 쪽이든
  프로젝트의 진화를 떠받치려면 프로토버프 디렉터리 구조와 메시지·서비스 정의가 조직돼야 한다.
  gRPC 프로젝트의 배포에는 전용 CI/CD 프로세스가 필요하다. 게다가 생성된 코드가 내 프로젝트라면
  쓰지 않았을 프로그래밍 관례를 들여올 수 있다.**
- **제한된 문서화 지원** — 위 [문서화](#문서화)와 같다. **프로토버프 파일이 정적 문서 노릇을
  하고 리플렉션이 온라인 문서를 준다.**
- **공식 도구의 부재** — **도구 공간의 도전은 프로토콜 버퍼와 gRPC 자신에게서 온다. 권장되는
  프로토버프 쓰임은 Bazel 같은 전용 코드 의존 관리 도구를 요구한다. 편집기와 IDE는 gRPC 지원이
  없는 경향이 있다. 생산 환경 관련 기능은 서드파티 도구가 제공한다** — 프로토버프 서식·린팅·깨는
  변경 검출은 **buf**가, 부하 시험은 **ghz**가 맡는 예로 든다.
- **낯섦(Unfamiliarity)** — **gRPC가 쓰는, API를 짓는 RPC 접근은 REST와 견주어 덜 익숙한
  경향이 있다. 프로토콜 버퍼의 이진 형식은 gRPC 기반 서비스를 짓고 디버깅할 때 새 기술을
  요구한다.**
- 저자들이 절충 논의를 더 보라고 가리키는 글 묶음이 케빈 맥도널드의 "gRPC: The Good and the
  Bad" 연재다 (8장, p.280).[^dynowski2025] 이 KB는 그 글을 갖고 있지 않다.

## 어디에 쓸 것인가

- **한 문장 판정** — **gRPC는 마이크로서비스 아키텍처의 서비스들 사이 같은 서비스 대 서비스
  통신에 알맞다. 다만 gRPC 채택 결정은 그 절충을 평가한 뒤에 내려야 한다** (8장 §"When to Use
  gRPC", p.280).[^dynowski2025]
- **무엇이 무엇을 이기는가** — **효율적인 이진 메시징에서 오는 서비스 간 통신의 성능 이득과
  타입 붙은 API 계약의 이점이 어떤 경우에는 gRPC가 들여오는 운영상의 도전을 능가할 수 있다.
  마이크로서비스 아키텍처를 채택한 팀은 그 도전을 넘는 데 필요한 기술 역량을 이미 갖고 있을 수도
  있다** (8장, p.280).[^dynowski2025]
- **언어가 여럿인 환경** — **여러 프로그래밍 언어로 쓰인 서비스의 사용을 피할 수 없다면 gRPC가
  그것들 사이의 통신 기제를 준다** (8장, pp.280–281).[^dynowski2025]
- **응용의 종류로도 갈린다** — **채팅·데이터 스트리밍·모바일 앱·실시간 시스템 갱신 같은 응용이
  gRPC의 덕을 볼 수 있는데, HTTP/2 프로토콜 덕분에 낮은 지연을 주고 데이터 스트리밍을 기본
  지원하기 때문이다** (8장, p.281).[^dynowski2025]

## 이 KB의 이웃과 맞대는 자리

**이 절의 대조는 이 KB가 세운 것이다** — 이 책은 아래 소스들을 인용하지 않는다.

- **클레프만의 RPC 비판과 이 장은 겨루지 않는다.**
  [원격 프로시저 호출의 문제](../concepts/remote-procedure-call-problems.md)는 **원격 호출을 지역
  호출처럼 보이게 만드는 것이 근본적으로 잘못된 목표**라고 적고, 이 장은 **RPC가 형식 차이와
  네트워크의 불신뢰를 다루려 했다**고 적는다. **둘 중 하나만 참일 수 있는 문장이 아니다** — 앞쪽은
  *위치 투명성*이라는 수단을 치고, 뒤쪽은 *무엇을 풀려 했는가*라는 목표를 적는다. 이 책 자신이
  위 [구현이 쓰는 기능들](#구현이-쓰는-기능들) 끝에서 **편의가 기본으로 주어지지 않는 영역
  넷**을 세므로, 같은 방향의 유보를 스스로 적고 있다.
- **뉴먼의 gRPC 채점과도 겨루지 않는다.** 그쪽은 2021년 시점에 **gRPC를 이 공간의 첫 후보로
  꼽되 클라이언트와 서버 양쪽을 상당히 통제할 수 있는 상황을 조건으로 달고**, 말해야 할 상대가
  다양하면 REST가 낫다고 적는다. 이 장의 [어디에 쓸 것인가](#어디에-쓸-것인가)가 세우는 조건이
  같다 — 서비스 대 서비스, 마이크로서비스 팀의 역량, 언어가 여럿인 환경이다. **두 소스가 같은
  자리를 가리킨다.** 그쪽 전문은 [마이크로서비스 통신 스타일](../concepts/microservice-communication-styles.md)과
  [원격 프로시저 호출의 문제](../concepts/remote-procedure-call-problems.md)에 있다.
- **"스트림"이라는 낱말이 이 KB에서 최소 셋을 가리킨다.** 겨루지 않고 기제가 다르다.
  - 여기의 스트리밍 RPC는 **HTTP/2 스트림 하나 위에서 메시지가 여럿 오가는 것**이고, 끝은 End
    Stream 플래그가 알린다.
  - [이벤트 스트림과 이벤트 브로커](../concepts/event-streams-and-brokers.md)의 스트림은 **보관되는
    이벤트의 로그**이고, 소비자가 자기 위치를 들고 되감을 수 있다.
  - [HTTP/2와 HTTP/3의 다중화와 QUIC](http-multiplexing-and-quic.md)의 스트림은 **한 연결 안에서
    독립적으로 흐르는 프레임의 묶음**이고, 위 두 쓰임이 그 위에 앉거나 앉지 않는다.
  - **셋을 가르는 물음은 "다시 읽을 수 있는가"다.** #hypothesis 저자들은 이 대조를 적지 않는다.
- **브라우저가 못 쓴다는 제약이 이 KB의 HTTP 쪽 페이지와 맞물린다.** 원인이 트레일러의 부재이고,
  그것은 HTTP/2가 아니라 **HTTP/1.1 명세의 기능이 자바스크립트 API에 구현되지 않은 것**이다.
  곧 **전송 판을 올린다고 풀리는 제약이 아니다.**
