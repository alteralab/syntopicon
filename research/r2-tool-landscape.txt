KEY: graphrag
--- SUMMARY ---
GraphRAG 엔진군 9종(지정 8 + 신규 발굴 Graphiti)을 GitHub API 실측과 이슈 추적으로 조사했다. 결론: 빠르게 바뀌는 벤더 문서 미러에 그래프 색인을 얹는 것은 갱신 비용 관점에서 성립하지 않는다. 근거 3축 — (1) 비용: 모든 엔진이 청크당 LLM entity 추출을 요구하며(frontier 모델 ≈ $12–19/MB, mini급 ≈ $1–2/MB), 이 비용이 월 수백 커밋의 변경분마다 재발생한다. 완전 로컬화하려면 30B급 모델이 필요해 맥북 1대 예산(A)과 충돌한다. (2) 증분의 실태: MS GraphRAG update-index는 append 전용(수정·삭제 불가, community 재계산 캐스케이드 위험), LightRAG는 증분·삭제를 지원하나 entity 중복 병합 이슈 이력이 있고 수정 = delete+reinsert 재추출이다. 진짜 실시간 증분은 Graphiti뿐이나 이는 md 코퍼스 검색이 아닌 agent memory 엔진이다. (3) 버전 인지(D): 전 엔진 부재 — VersionRAG 논문이 GraphRAG 64% 정확도로 이 공백을 실증했고, 오히려 버전이 다른 같은 문서를 넣으면 entity가 뒤섞이는 역효과까지 있다. 한국어 형태소 분석(E)도 전무하다. 존속성·활동성으로는 LightRAG·Graphiti·Cognee·RAGFlow가 살아있고 nano-graphrag·fast-graphrag는 휴면, KAG는 둔화 상태다. 종합하면 이 코퍼스에는 qmd류의 lexical+vector 증분 색인이 비용 구조상 우월하며, GraphRAG는 '안정적이고 entity가 풍부한 코퍼스에서 multi-hop 질문'이라는 별도 문제의 도구다. 굳이 그래프가 필요해지면 후보는 LightRAG(경량·활발)나 Graphiti(증분·MCP)로 좁혀지고, 버전 인지는 어느 쪽이든 메타데이터 계층 자작이 필요하다.

### Microsoft GraphRAG  [MIT]  https://github.com/microsoft/graphrag
  - maturity: 35,318 stars, 최근 push 2026-08-05, v3.1.1 릴리스 2026-07-18, 기여자 ~51명, Microsoft Research 주도. 릴리스 케이던스 안정적.
  - footprint: Python CLI + parquet/LanceDB 출력 — 상주 서비스 불필요. 단 색인 파이프라인 자체가 LLM 대량 호출 구조라 API 또는 강력한 로컬 모델 필수.
  - incremental: v1.0부터 `update-index` 존재하나 append 전용 — 문서 삭제·수정 미지원(Issue #741, Discussion #1313). 신규 콘텐츠 병합 시 community summary 재계산 임계치를 넘으면 전체 재색인급 비용으로 퇴행. 색인 = 청크당 entity 추출 + community report 생성으로 LLM 호출 필수.
  - version_support: 버전 라벨 구분 조회 없음. VersionRAG 논문 실측에서 버전 민감 질의 정확도 64%에 그침.
  - korean: 형태소 분석 없음. 추출·요약 언어는 LLM 프롬프트에 위임, 검색은 임베딩 의존. CJK 전용 토크나이저 없음.
  - interface: CLI(index/query: local·global·drift search). 공식 MCP 없음. query 방식이 자체 검색 파이프라인에 묶여 있어 에이전트가 저수준 검색 도구로 조합하기 어려움.
  - strengths: 레퍼런스 구현·최대 인지도, MIT, 문서화 우수, 전역 질문(community 요약 기반 sense-making)에 강함. LazyGraphRAG(색인 비용 0.1%)가 OSS 통합 예고됨(2026 Q1–Q2 예정이었으나 v3.1.1까지 릴리스 노트에 흔적 없음).
  - weaknesses: 색인 비용 최상위(GPT-4.1로 800KB ≈ $10–15, 벤치마크 데이터셋당 $51–389). global search 질의도 토큰 폭식. 수정·삭제 반영 불가 → 월 수백 커밋 미러에 구조적으로 부적합.
  - fit_verdict: 부적합. append 전용 증분과 community 재계산 캐스케이드 때문에 고churn 벤더 문서 미러에서 갱신 비용이 통제되지 않고, 버전 구분 조회도 없다.
### LightRAG (HKUDS)  [MIT]  https://github.com/HKUDS/LightRAG
  - maturity: 38,616 stars, push 2026-08-06, v1.5.6 릴리스 2026-08-06, 기여자 ~277명, HKU 연구실(EMNLP 2025 논문). 후보군 중 가장 활발.
  - footprint: pip 설치, 기본 저장소는 파일 기반(JSON KV + nano-vectordb + networkx) — 맥북 1대 OK. Postgres/Neo4j는 선택. 단 추출용 로컬 LLM 권장 최소가 Qwen3-30B-A3B급이라 맥북 로컬 운영 시 색인이 매우 느리거나 API 의존.
  - incremental: 문서 단위 incremental insert + selective deletion(삭제 시 영향 entity의 KG 자동 재생성) 공식 지원. 그러나 분할 insert 간 entity 중복·병합 실패 이력(#485, #2528)과 custom chunk 미병합 버그(#3352)가 실재. 문서 '수정' = delete+reinsert이므로 변경 문서마다 청크당 1–2회 LLM 추출 재발생.
  - version_support: 버전 라벨 구분 조회 없음. 같은 문서 v1.7/v1.8을 넣으면 entity가 뒤섞여 병합됨 — 오히려 버전 혼선 위험.
  - korean: SUMMARY_LANGUAGE 설정으로 출력 언어 제어. 형태소 분석·CJK 토크나이저 없음 — 한영 혼용 검색은 다국어 임베딩 품질에 전적으로 의존.
  - interface: REST API + WebUI + Ollama 호환 챗 엔드포인트. 공식 MCP는 README에 없음(커뮤니티 구현 존재). 검색은 dual-level(키워드 추출 LLM 1회 + 그래프 탐색)로 질의당 비용 저렴(<100 토큰급).
  - strengths: MS GraphRAG 대비 색인·질의 비용 수십 배 절감(community summary 생략), 증분·삭제 API 보유, 초활발 개발, MIT, 파일 기반 저장으로 데이터 탈출 용이.
  - weaknesses: 증분 병합 품질 이슈 이력, 수정 반영은 결국 재추출, 학술 프로젝트 특유의 빠른 API 변동(1년에 마이너 릴리스 다수), 로컬 추출 모델 요구 사양 높음.
  - fit_verdict: GraphRAG군 중 A·C 기준 최선이지만, 버전 혼선 위험(D)과 변경 문서 재추출 비용이 남아 휘발성 문서 레이어의 기본 엔진으로는 여전히 과함.
### Graphiti (Zep) — 신규 발굴  [Apache-2.0]  https://github.com/getzep/graphiti
  - maturity: 29,656 stars, push 2026-08-05, v0.29.3 릴리스 2026-07-27, 기여자 ~57명, Zep(상용 agent memory 회사)이 개발 — 회사 존속에 연동된 bus factor.
  - footprint: Neo4j 또는 FalkorDB 필요(Kuzu는 deprecated). FalkorDB 'Lite' 임베디드(py3.12+)를 쓰면 상주 서비스 0개 가능. 그 외에는 도커 그래프 DB 상주.
  - incremental: 설계 자체가 증분 — episode 단위 실시간 통합, batch 재계산 없음(README 명시). 후보군 중 유일하게 '지속 갱신'이 1급 시민. 단 episode마다 entity/edge 추출 + 기존 edge invalidation 판단에 LLM 호출 — 갱신량에 비례한 LLM 비용은 그대로.
  - version_support: bi-temporal 엣지(유효 기간)로 시간 기반 버전 추적은 됨 — '버전 라벨'(v1.7/v1.8) 기반 구분 조회는 아니고 시각 기반. 후보군 중 D에 가장 근접하나 의미가 다름.
  - korean: 형태소 분석 없음. 추출은 LLM, 검색은 임베딩+BM25(영문 토크나이저) — 한국어 lexical 매칭 약함.
  - interface: 공식 MCP 서버 동봉(Claude/Cursor 연동), Python SDK. 검색은 hybrid(BM25+임베딩+그래프) 함수 호출형 — 파이프라인 강제 아님.
  - strengths: 실시간 증분 그래프의 최강 구현, temporal 모델, 공식 MCP, 활발한 개발. 구조화 출력만 되면 Ollama/vLLM 로컬 운영 가능.
  - weaknesses: 그래프 DB 의존(임베디드 옵션은 최근 것), 작은 로컬 모델은 구조화 출력 실패 잦음(README 경고), 문서 코퍼스 관리 계층 없음(md 디렉토리 스캔·해시 증분 같은 것 직접 구축해야 함), agent memory 용도로 설계돼 문서 검색 용도와 결이 다름.
  - fit_verdict: 증분(C)은 최선이나 md 코퍼스 미러링 용도가 아니라 agent memory 엔진이다. 문서 레이어로 쓰려면 ingest 오케스트레이션을 자작해야 하고 한국어 lexical 검색이 약하다.

--- SUMMARY ---
시간축·메모리형 지식그래프 6계보(Graphiti·Zep·Mem0·Letta·Cognee·memori)를 GitHub API 실측과 공식 문서로 조사한 결론: 이 지형 전체가 '에이전트 대화/이벤트 메모리' 도메인이며, 벤더 문서 미러의 전문 검색이라는 사용자 용도와는 구조적으로 불일치한다. (1) Graphiti의 bitemporal은 마케팅이 아닌 실구현(tx-time=created_at/expired_at 시스템 기록, valid-time=valid_at/invalid_at LLM 추출)이지만, 그 시간축은 'fact의 세계-유효기간'이지 문서 버전 축이 아니다 — v1.7/v1.8 구분은 검색엔진의 코퍼스 메타데이터 1필드로 끝나는 문제이고, git 미러가 이미 tx-time을 무료로 제공한다. 백엔드는 Neo4j 기본에 임베디드는 FalkorDB Lite 단일 경로(Kuzu deprecated). (2) 전 후보가 색인 시점에 LLM 호출을 강제한다(Graphiti는 episode당 다중 호출, LLM-free ingestion은 미해결 이슈) — 월 수백 커밋 증분에 비용 구조가 성립하지 않아 기준 C에서 전멸. (3) 기준 E(한국어)는 전 후보 미지원(Graphiti 프롬프트 영어 전용, open issue). (4) 존속성 경고 실적 2건 — Zep CE 폐기(2025-04), Mem0 OSS 그래프 메모리 회수(Platform 전용화). 판정: 휘발성 문서 레이어의 검색은 이 축에서 답이 나오지 않으며 qmd류 로컬 검색엔진 구도가 유효하다. 유일한 잔여 가치는 Cognee의 임베디드 스택(SQLite/LanceDB/Kuzu)을 '개념 관계 그래프' 보조 축으로 쓰는 실험이나, 이는 검색 레이어의 대체가 아닌 분담이다.

  - footprint: 그래프 DB 상주 필요: Neo4j 5.26(기본)·FalkorDB 1.1.2·Amazon Neptune. 임베디드 경로는 FalkorDB Lite(Python 3.12+)뿐이고, Kuzu 백엔드는 upstream 미유지로 deprecated. 공식 Docker 이미지가 6개월+ 방치돼 v0.10에 머문 전력(issue #1030) — 셀프호스팅은 라이브러리 직접 운용이 실질 경로.
  - incremental: 증분 자체는 강점(add_episode가 배치 재계산 없이 실시간 갱신). 그러나 episode 1건마다 LLM 다중 호출이 필수 — 노드 추출→dedup(MinHash/LSH 우선, LLM fallback)→엣지 추출→모순 해소→valid_at/invalid_at 타임스탬핑까지 전부 LLM 경유(issue #1193, #1299에서 'LLM 없는 add_episode' 요청이 미해결). 월 수백 커밋 미러에 적용하면 색인 비용이 쓰기 시점에 LLM 요금으로 전가된다.
  - version_support: bitemporal은 실제 구현이다: tx-time = created_at/expired_at(시스템이 기록·무효화한 시각, 항상 존재), valid-time = valid_at/invalid_at(LLM이 텍스트에서 추출하는 optional 필드). 단, 이 시간축은 'LLM이 추출한 fact의 세계-유효기간'이지 문서 버전 축이 아니다. dbt v1.7/v1.8 docs를 시간축으로 모델링한 공개 실사용 사례는 조사에서 발견되지 않았고, 역사 backfill조차 temporal-correctness 결함이 보고돼 있다(issue #1489).
  - korean: 프롬프트가 전부 영어이며 다국어 지원은 미해결 open issue(#1141). BM25 측은 백엔드(Neo4j Lucene/FalkorDB) 분석기에 종속되고 한국어 형태소 지원을 Graphiti가 구성해주지 않음. FalkorDB에서 'stopword-only 토큰 쿼리 short-circuit' 같은 fulltext 땜질이 v0.29.3에도 진행 중.
  - interface: Python 라이브러리 + MCP 서버(mcp_server/, MCP Server v1.0은 2025-11 출시, Claude Desktop/Cursor 호환). CLI는 없음. 에이전트가 도구를 고르는 구도와는 호환되지만 검색 대상이 'LLM이 추출한 fact 그래프'라 원문 md 검색이 아니다.
  - strengths: 후보군 중 유일하게 bitemporal이 마케팅이 아닌 실구현. 증분 갱신 설계가 진지하고, MCP 서버가 공식 지원되며, Apache-2.0 + 상업 서비스 기반이라 단기 존속성은 양호.
  - weaknesses: 색인 = LLM 호출(비용·비결정성), 그래프 DB 상주(임베디드는 FalkorDB Lite 하나), 한국어 미지원, 검색 결과가 원문이 아닌 추출된 fact — 데이터 탈출구 관점에서 색인이 죽으면 그래프는 재구축 비용이 크다(원본 md는 무사하나 그래프는 LLM 재추출 요금).
  - fit_verdict: 용도 불일치. '누가 언제 무엇을 좋아했나'류의 fact 변천 추적용이지 벤더 문서 미러의 전문 검색용이 아니다. v1.7/v1.8 구분은 코퍼스 메타데이터 1개 필드로 끝나는 문제를 LLM 추출 그래프로 푸는 과잉 설계.

(3) 엔진 부품: LanceDB가 embedded+한국어 형태소 FTS+hybrid+증분을 유일하게 동시 만족하는 최강 엔진이지만 CLI/MCP/스캐너 전부 자작이라 유지비 예산과 충돌하고, txtai·SeekStorm은 1인 유지에 한국어 약해 탈락, LEANN은 vector-only+질의 시 재계산으로 부적합, bm25s·sqlite-vec·tantivy는 부품 수준. 신흥 발굴(KINDX·EverOS)에서 qmd 대체 완제품은 없었다. 결론: 휘발성 레이어는 '색인이 죽어도 원본 md 무사'가 성립하는 삭제 가능한 파생물이므로 B 기준을 정본 KB보다 완화해도 되고, 그 전제에서 qmd 유지가 종합 1위다 — 단 (a) 한국어는 기존 kiwipiepy 형태소 질의 전처리를 이 레이어에도 적용하고 임베딩을 Qwen3-Embedding-0.6B로 교체하며, (b) 버전 구분은 버전별 디렉토리+컬렉션으로 모델링하고, (c) qmd 6개월 무활동 또는 sqlite-vec 사망을 재평가 트리거로 문서화한다. 형태소 내장이 양보 불가 요건이 되면 Meilisearch(차선, 글루 자작 전제), 자작 재조립이 필요해지면 LanceDB(엔진 1위)가 승계 경로다.

--- SUMMARY ---
색인 레이어는 이 규모에서 "필수"가 아니라 "정밀도·비용 최적화"다. 실측 지형: (1) Anthropic은 Claude Code의 RAG+벡터DB를 grep 기반 agentic search로 교체했고(Cherny 직접 확인: "generally works better", staleness·보안 문제 소멸), Amazon Science AAAI 2026 논문은 rga/pdfgrep만 가진 ReAct 에이전트가 RAG 대비 faithfulness 94.5%·정답률 91.5%를 달성함을 실측, 독립 연구(arXiv 2605.15184)도 4개 하네스에서 grep이 vector retrieval을 대체로 상회함을 확인했다. 반면 Cursor는 임베딩을 폐기하지 않고 자체 모델을 훈련해 유지 — semantic search 추가가 정확도 +12.5%(6.5–23.5%)였으나 효과는 1,000+파일 대형 코드베이스에 집중(code retention +2.6% vs 전체 +0.3%). (2) grep의 miss는 "단독 사용"의 속성이다: NQ 코퍼스에서 순수 grep은 참담하나 LLM 키워드 확장으로 ~10배 개선되며, 에이전트 루프는 항상 확장을 수행한다. 낭비 읽기 정밀도는 grep 1/5 vs 하이브리드 1/8(벤더 주관 벤치마크). (3) 무색인 관행은 공식화됐다: dbt-labs의 fetching-dbt-docs 스킬은 llms.txt 인덱스→llms-full.txt 24h 캐시 grep→개별 .md fetch로, 색인·임베딩·LLM 색인 호출이 전무하다. (4) 실무 권고는 "얇은 인덱스=라우팅, 정독=파일 직접"(llms.txt 생태계, A-RAG의 도구 병렬 노출, Cursor의 grep+semantic 조합 결론). (5) 규모 경계: 관찰된 breaking point는 1M 파일(원조 grep 4초)·10M 파일 monorepo이고 임베딩 이득은 1,000+파일부터 유의미해지기 시작하나, 사용자의 수만~수십만 라인 md 미러는 ripgrep에 밀리초 영역이며 월 수백 커밋 갱신 비용이 무색인에서는 0이 된다(기준 C 완승, 버전 구분도 디렉토리 glob으로 해결=기준 D). 결론: 휘발성 문서 레이어에 무색인 rg+read는 성립하며 유지비 예산(2–3주당 30–45분)에 가장 부합한다. qmd를 전면 폐기할 근거도, 기본값으로 깔 근거도 없다 — 남는 실증 공백은 한국어 형태소 변형에서의 lexical miss율(연구 부재)로, 이 지점이 qmd(kiwipiepy) 유지의 유일한 잔존 근거이므로 한국어 패러프레이즈 질의 qrels로 rg 루프 vs qmd를 직접 실측해 결정하는 것이 옳다.

  - footprint: 단일 정적 바이너리, 상주 서비스 0, DB 0, 색인 파일 0. 유지비가 구조적으로 0에 수렴 — 기준 A 만점
  - incremental: 색인이 없으므로 증분 색인 문제 자체가 소멸. 월 수백 커밋 갱신 시 git pull 즉시 최신 상태 검색. LLM 호출 불필요 — 기준 C에서 어떤 색인 도구도 이길 수 없는 구조
  - version_support: 경로 glob(-g 'spark/3.5/**')으로 디렉토리=버전 네임스페이스. 미러의 디렉토리 구조가 곧 버전 스키마이므로 색인 스키마 설계 자체가 불필요 — 기준 D를 파일시스템이 해결
  - korean: UTF-8 리터럴/regex 매칭은 완전하나 형태소 분석 없음. 조사·어미 변형('스파크의'/'스파크를')은 에이전트가 어간·영문 원어 변형 질의를 생성해 보완 — 이 보완의 miss율은 미실측
  - interface: CLI. Claude Code의 Grep 도구가 곧 ripgrep. 파이프라인 강제 없음 — 에이전트가 질의를 재구성하며 반복 호출하는 ReAct 구도 자체가 인터페이스
  - strengths: 증분·존속성·설치 발자국에서 구조적 만점. 색인이 죽을 일 자체가 없어 데이터 탈출구 문제 소멸(기준 B). Anthropic이 벡터DB를 버리고 채택한 방식이며 Amazon 실측에서 RAG 대비 91-95% attainment
  - weaknesses: 패러프레이즈·의미 질의에서 단독 성능 낮음(LLM 확장으로 ~10배 보완되나 tool call 수·토큰 비용 증가). 낭비 읽기 1/5 수준(하이브리드 1/8 대비). 한국어 형태소 recall 미검증
  - fit_verdict: 휘발성 문서 레이어의 기본 검색 프리미티브로 적합 — 사용자 규모(수만~수십만 라인 md)는 관찰된 성능 경계(1M+ 파일)보다 수십 배 아래이고, 월 수백 커밋 갱신 코퍼스에서 유지비 0이라는 특성이 기준 A·C와 정확히 맞는다.
### dbt-agent-skills / fetching-dbt-docs (무색인 문서 검색 관행의 공식 표본)  [Apache-2.0]  https://github.com/dbt-labs/dbt-agent-skills
  - maturity: 652 stars, created 2026-01-08, push 2026-08-05 (활발). 개발 주체 dbt Labs(회사) — 벤더 공식이라 해당 벤더 문서에 한해 존속성 양호
  - footprint: SKILL.md + 셸 스크립트 1개. 상주 서비스 0. llms-full.txt를 ~/.cache에 24h 캐시하는 것이 로컬 상태의 전부
  - incremental: 증분 개념 없음 — 24h TTL 캐시 재다운로드. LLM 호출 0. 실측 확인: 스크립트는 curl+grep으로 keyword→매칭 페이지 URL 반환 후 개별 .md를 WebFetch
  - version_support: docs.getdbt.com의 현행 버전만 — 버전별 미러 개념 없음. 사용자가 로컬 미러에 같은 패턴을 적용하면 버전 디렉토리로 해결 가능
  - korean: 미지원 — 영문 벤더 문서 전용. 다만 방식 자체는 언어 중립(grep 한계 동일)
  - interface: Claude Code Skill (에이전트가 절차를 읽고 CLI 도구로 실행). 파이프라인 강제 없음
  - strengths: 벤더가 직접 공식화한 무색인 관행이라는 실증 가치: llms.txt 인덱스(라우팅) → llms-full.txt grep(발견) → .md 정독(에이전트 직접)이라는 3단 구조가 사용자가 만들려는 레이어의 참조 설계도. 스킬 내 prompt-injection 방어 지침까지 포함
  - weaknesses: 그대로 쓰는 도구가 아니라 패턴의 표본. 원격 fetch 의존이라 오프라인 미러 요구와는 어긋남(로컬 미러로 치환 필요). 검색은 단순 키워드 OR
  - fit_verdict: 직접 채택할 도구는 아니고, '로컬 llms.txt식 인덱스 + rg + 파일 정독' 스킬을 자작할 때의 검증된 청사진. dbt 미러에는 이 스킬의 URL 패턴(.md 부착·llms.txt)을 미러링 소스 규약으로 재사용할 수 있다.
### probe (buger/probe — 무색인 AST-aware 검색, 중간 지점)  [Apache-2.0]  https://github.com/buger/probe
  - maturity: 677 stars, push 2026-07-31 (활발). 개인 주도(Leonid Bugaev) — bus factor 리스크 있음
  - footprint: 단일 바이너리, 색인 없음(ripgrep+tree-sitter를 질의 시점에 결합), 상주 서비스 불필요
  - incremental: 무색인이므로 증분 문제 없음. LLM 호출 불필요(선택적 AI 모드는 별도)
  - version_support: 경로 스코프로만 — ripgrep과 동일
  - korean: 형태소 미지원. 코드 토큰화 중심
  - interface: CLI + MCP 서버 동시 제공 — 기준 F 충족
  - strengths: 무색인을 유지하면서 검색 결과를 AST 블록 단위로 잘라 반환 — grep의 '라인 매치→전체 파일 읽기' 낭비를 줄이는 설계
  - weaknesses: 코드 코퍼스 지향이라 md 문서에는 AST 이점이 거의 없음. 커뮤니티 규모 작고 10-20년 존속성 불투명
  - fit_verdict: md 중심 문서 미러에는 이점이 약해 채택 비권장 — 다만 '무색인이되 반환 단위를 구조화'하는 설계 방향의 참고 사례로 가치.
