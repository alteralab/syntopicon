하나의 질문: **반입만으로는 빈약한 레코드에 무엇을 어떻게 더해야 값이 오르는가.**

Konieczny의 5장은 값을 올리는 길을 **정보를 더하는 쪽**과 **정보를 줄이는 쪽** 둘로 가른다. 이
페이지는 앞쪽 — **데이터 강화**(Data Enrichment, 다른 데이터셋을 붙인다)와 **데이터 장식**
(Data Decoration, 계산한 속성을 얹는다) — 네 패턴을 다룬다. 줄이는 쪽은
[배치 조인과 그룹핑](../concepts/batch-joins-and-grouping.md)의 집계 두 패턴과
[세션화 패턴](../concepts/sessionization-patterns.md)이 맡는다.

## 반입된 데이터는 자산이 아니다

- 장의 첫 문장이 좌표다 — **인기 없는 의견일지 모르지만 저장소 어딘가에 앉아 있는 데이터는 진짜
  자산이 아니다. 대개는 시스템에 반입되고 나면 빈약하고 여러 품질 이슈를 가질 것이다** (5장,
  p.115).[^konieczny2025]
- 실물 — 스트리밍 계층의 데이터 생산자가 웹 브라우저이므로 **브라우저 버전·언어·운영체제 같은
  값진 기술 정보는 무엇이든 얻을 수 있다. 각 방문의 기술적 부분을 분석하고 싶다면 그것으로 충분할
  것이다. 그러나 특정 브라우저를 쓰는 방문자들의 공통점처럼 더 알아야 한다면? 각 방문 이벤트는
  명시적 관계 없는 개별 항목으로 반입되므로 여분의 노력 없이 데이터를 상관 짓는 것은 불가능하다**
  (5장, p.115).[^konieczny2025]
- 그래서 이 계열의 목적은 하나다 — **데이터셋을 증강해 최종 사용자에게 유용성을 높이는 것** (5장,
  p.115).[^konieczny2025]
- 강화 범주의 전제 — **아주 흔히 원시 데이터는 기술적 제약 때문에 빈약할 것이다. 이벤트가 여기서
  최고의 예다. 그것들은 시간과 공간 속성의 완벽한 표현이지만 확장된 맥락이 자주 없다. 이벤트의
  작성자를 식별할 수는 있어도 마지막 접속일이나 사용자 프로필 점수 같은 여분 정보를 제공할 수 있는
  경우는 드물다** (5장, p.116).[^konieczny2025]

## Static Joiner — 정지 참조 데이터를 붙인다

- 적용 조건 — **강화 데이터셋이 정적 성격이라면(단연 가장 쉬운 상황이다) Static Joiner 패턴을
  택하게 된다** (5장, p.116).[^konieczny2025]
- 문제 — 등록일과 일상 활동의 의존을 이해하기 쉽게 만드는 데이터셋을 만들어 달라는 요구인데,
  **원시 데이터셋에 사용자 맥락이 없다. 그것은 정적 사용자 참조 데이터셋에서만 찾을 수 있다.
  비즈니스 요구에 답하려면 참조 데이터를 사용자 활동으로 가져올 방법을 찾아야 한다** (5장,
  p.116).[^konieczny2025]
- 해법의 놀라운 지점 — **조인되는 데이터셋의 정지 성격이 Static Joiner를 쓰기에 완벽한 조건이다.
  놀랍게도 이 데이터의 정지 성격에도 불구하고 패턴은 스트리밍 파이프라인에서도 동작한다** (5장,
  p.116).[^konieczny2025]
- 구현이 요구하는 것은 **두 데이터셋을 결합하는 데 쓸 수 있는 속성 목록**이다 — 이 책의 예에서는
  **visits와 users 데이터셋에서 사용자를 식별하는 어떤 필드, 예컨대 `user_id` 필드**다 (5장,
  p.116).[^konieczny2025]
- 표현 수단 — **코드 구현에 관해서는 강화가 흔히 SQL `JOIN` 문으로 표현된다. 현대 데이터 처리
  프레임워크와 더 고전적인 데이터 웨어하우스를 지원하므로 이 해법은 보편적이다** (5장,
  p.117).[^konieczny2025]
  - 다른 갈래는 API다 — **이 선언적 방식 외에 프로그래매틱 API에서 데이터셋을 강화할 수 있다.
    여기서 가장 쉬운 길은 HTTP 라이브러리로 데이터 처리 계층과 외부 API 사이의 통신을 가능하게
    하는 것이다** (5장, p.118).[^konieczny2025]
    - 그러나 **어떤 데이터가 API 뒤에 노출된다는 사실이 그 데이터셋을 테이블 같은 데이터 저장
      계층에서 접근할 수 없다는 뜻은 아니다. 필요하면 이 API 노출 데이터셋을 전처리 단계에서
      테이블로 물질화하고 `JOIN` 문의 일부로 쓸 수도 있다** (5장, p.118).[^konieczny2025]
    - 그리고 그 선택은 멱등성이 정한다 — **멱등성에 신경 쓴다면 API를 물질화하고 SCD 형식 중
      하나를 활용하는 해법을 택해야 한다. 그것이 처리 로직을 재생할 때마다 언제나 같은 데이터셋을
      쓰게 됨을 보장한다** (5장, p.118).[^konieczny2025]
    - API를 직접 부를 때의 권장 — **여기서 우리의 권장 하나는 대량(bulk) 연산을 활용하는 것이다.
      여러 항목에 대한 정보를 한 번에 요청할 수 있고, 이것이 데이터 강화에서 흔히 가장 비싼
      연산인 네트워크 처리량을 최적화한다** (5장, p.121).[^konieczny2025]

## SCD가 조인에 시간을 들여온다

- 키 조건만으로 끝나지 않는다 — **이 키 조건 외에 결합이 어떤 시간 제약을 기대할 수도 있다.
  특히 강화 데이터셋이 어떤 형태의 완만하게 변하는 차원을 구현할 때 그렇다. 그 경우 최초 패턴의
  시간 민감(time-sensitive) 정적 조이너 변형을 구현할 수 있다** (5장,
  p.116).[^konieczny2025] 그 모델링 자체의 정본은
  [완만하게 변하는 차원](../concepts/slowly-changing-dimension.md)이다.
- 저자가 상자로 좁혀 둔 것 — **우리 해법에서 강화 데이터셋은 SCD 타입 2 또는 4를 구현해야 한다.
  이 타입들은 시간에 걸친 행 진화를 추적하고, 둘 사이의 유일한 차이는 기술적 구현이다** (5장,
  p.117).[^konieczny2025]

  | 타입 | 저자가 적은 구현 |
  |---|---|
  | 2 | **유효 날짜로 추적을 관리하고 각 현재 값은 종료 날짜가 비어 있다** |
  | 4 | **두 테이블에 의존한다. 첫 테이블은 각 엔티티의 현재 값을 저장하고, 둘째 테이블은 현재 것을 포함한 모든 이력 값을 저장한다** |

- SCD 타입 2 조인이 이 패턴의 대표 코드다 (5장, p.120):[^konieczny2025]

  ```sql
  SELECT v.visit_id, v.event_time, v.page, u.id, u.login, u.email
  FROM dedp.visits v JOIN dedp.users u ON u.id = v.user_id
    AND NOW() BETWEEN start_date AND end_date;
  ```

  - `NOW()`가 그대로 남으면 안 된다는 것이 이 예제의 요점이다 — **이 조건은 데이터셋의 현재
    상태를 얻기 위해 애드혹 질의의 일부로 `NOW()` 함수를 쓴다. 필요에 맞는 다른 날짜를 쓸 수
    있다. 예컨대 데이터 오케스트레이터가 제공하는 실행 시각일 수 있는데, 그것은 파이프라인 실행에
    관련된 불변 속성이라 멱등성을 강제하는 데 도움이 된다** (5장, p.120).[^konieczny2025]
  - 타입 4는 **타입 2와 같은 질의에 의존하므로** 저자가 생략한다 — **유일한 차이는 타입 4가 현재
    값을 별도 테이블에 저장하는 반면 타입 2에서는 현재 행과 과거 행이 같은 데이터셋에 있다는
    것이다** (5장, p.120).[^konieczny2025]
- 스트림과 배치를 잇는 조인도 같은 패턴이다 — 정적 devices 테이블과 스트리밍 visits를 `left_outer`로
  잇는데 **시간 조건을 전혀 포함하지 않는다. devices 테이블이 삽입 전용 테이블이고, 매치된 레코드가
  없어도 괜찮기(left join을 쓰므로) 때문이다** (5장, p.120).[^konieczny2025]
  - 그 느슨한 조건이 숨긴 함정 — **정적 데이터셋과 스트리밍 잡은 별개의 수명 주기를 갖는다. 다르게
    말해 스트리밍 잡은 정적 데이터셋이 갱신되기를 기다리지 않는다. 따라서 이는 조인 미스뿐 아니라,
    전면 재작성의 경우 빈 참조 테이블과 조인하는 결과로 이어질 수 있다** (5장,
    pp.120–121).[^konieczny2025]
  - 그리고 그 위험은 형식이 정한다 — **정적 데이터셋이 JSON이나 CSV 같은 원시 파일 형식으로
    쓰였다면 그런 일이 일어날 수 있다. 우리 경우 devices 테이블은 원자성과 일관성 보장을 제공하는
    테이블 파일 형식에 의존한다. 소비자가 미커밋 파일을 읽기로 결정하지 않는 한, 동시성 이슈 때문에
    빈 테이블을 처리할 위험은 없다** (5장, p.121).[^konieczny2025]

## 정적 조인의 두 가지 대가

- 대가 ① **늦은 데이터와 일관성** — **이상적인 시나리오라면 사용자는 이벤트가 생성되는 것과 같은
  속도로 진화할 것이다(즉 사용자가 프로필을 바꾸고 곧바로 내비게이션 액션을 하면 처리된 방문은 가장
  최근 변경을 포함해야 한다). 불행히도 이 시나리오는 일어나지 않을 수 있다** (5장,
  p.119).[^konieczny2025] 그 이유는 [늦은 데이터 통합](../concepts/late-data-integration.md)에 있다.
  - 완화책이 갈린다 — **스트리밍 파이프라인의 지연 이슈를 완화하려면 다음에 제시하는 Dynamic
    Joiner 패턴을 쓸 수 있다. 배치 파이프라인에서는 더 단순한데, 강화 데이터셋이 존재하기를
    기다리도록 오케스트레이션에 의존할 수 있기 때문이다(예컨대 Readiness Marker 패턴을 활용해서)**
    (5장, p.119).[^konieczny2025] 그 마커는
    [반입 트리거 패턴](../concepts/ingestion-triggering-patterns.md)에 있다.
- 대가 ② **멱등성** — **일관성 외에 멱등성도 고려해야 한다. 배치 파이프라인을 백필한다면 그 결과가
  강화 데이터셋에 대해 멱등적이어야 하는지 스스로 물어야 한다. 그렇고 데이터 제공자가 시간 기반
  질의를 전혀 허용하지 않는다면, 조인하기 전에 시간 측면을 통제하기 위해 강화 데이터셋을 당신의
  데이터 계층으로 가져와야 할 수 있다** (5장, p.119).[^konieczny2025]
  - **API 뒤에 숨은 외부 데이터셋이라면 상황이 더 까다롭다. 여기서도 이상적으로는 시간 기반 질의를
    낼 수 있어야 하지만 그것이 가능하지 않을 수 있다. 해법은 이 시간성을 내부 데이터 저장에 더하고
    모든 강화 레코드를 거기 쓰는 것일 수 있다. 두 경우 모두 SCD를 쓰는 것이 좋은 선택지일
    것이다** (5장, p.119).[^konieczny2025]

## Dynamic Joiner — 두 스트림의 지연 차를 흡수한다

- 왜 정적 패턴으로 부족한가 — **Static Joiner는 정적 성격 때문에 두 스트리밍 데이터셋을 결합하는
  데 가장 잘 맞지 않는다. 문제는 데이터 인식에 있다. 스트리밍은 가능한 한 빨리 처리하는, 계속
  움직이는 데이터셋을 뜻하는 반면 정적 배치 워크로드는 더 느리게 진화하는 데이터에서 동작한다**
  (5장, pp.121–122).[^konieczny2025]
- 문제 — **매주 수천 명의 새 사용자가 들어오면서 프로필 변경 수가 늘었다. 결과적으로 강화된
  데이터셋은 무관해지고 하류 소비자에게 문제가 된다. 각 사용자 변경이 Change Data Capture
  패턴으로 스트리밍 브로커에 등록되므로 양쪽 이벤트를 결합할 더 나은 방법을 찾고 있다** (5장,
  p.122).[^konieczny2025] 그 캡처 쪽은 [변경 데이터 캡처](../concepts/change-data-capture.md)다.
- 이 패턴이 정적 조이너에 더하는 것은 하나다 — **키의 식별과 조인 방법의 정의라는 점은 공유하지만
  여분 요구가 하나 있다. 시간 경계(time boundaries)다. 이 전용 시간 관리 전략이 없으면 많은
  조인이 비게 될 위험이 있다. 왜? 두 데이터셋이 다른 지연을 가질 수 있기 때문이다. 다르게 말해
  강화 데이터셋이 강화되는 데이터셋에 비해 늦거나 그 반대일 수 있다** (5장,
  p.122).[^konieczny2025]
- 시간 조건의 정체는 버퍼다 — **이 시간 조건을 정의한다는 것은 양쪽 스트림에서 조인될 레코드를 위한
  시간 제한 버퍼를 갖는다는 뜻을 함의한다. 그렇게 하면 더 빠른 데이터 원천이 자기 시간 의미론을 더
  느린 데이터 원천에 맞출 수 있다. 결과적으로 버퍼가 조인이 일어날 여분 시간을 준다. 이 여분 시간은
  데이터 원천 간의 허용 지연 차이다. 예컨대 우리 예의 users가 visits보다 한 시간 늦다면 버퍼는
  사용자 스트림이 따라잡았을 때 매치를 찾기를 바라며 visits를 한 시간 더 저장할 것이다** (5장,
  p.122).[^konieczny2025]
- 버퍼가 부르는 둘째 요소가 **GC 워터마크**다 — **기술적으로는 언제나 양쪽 스트림의 이벤트를
  영원히 보관하기로 결정할 수 있지만, 그것은 상당한 하드웨어 자원을 요구하고 인프라를 무한정 확장할
  수 없다면 조만간 실패할 것이다. 더 나은 접근은 너무 오래된 이벤트가 각 버퍼에서 언제 사라져야
  하는지, 즉 언제 가비지 컬렉션(garbage collection, GC) 워터마크를 정의해야 하는지를 정하는
  것이다. 이는 명백히 레코드 중 하나가 정말 늦게 오면 조인을 잃는다는 뜻이지만, 그것이 관리 가능한
  크기의 버퍼를 갖는 대가다** (5장, p.122).[^konieczny2025]
  - 저자가 그림으로 보인 동작 — 스트림 A가 스트림 B보다 몇 분 빠를 때 **스트림 A는 매치되지 않은
    모든 키를 일정 기간 버퍼링한다. 그 다음 스트림 B가 따라잡으면 스트림 A는 들어오는 데이터에서
    또는 버퍼에서 직접 대응하는 행을 찾으려 한다. 매치가 없으면 GC 워터마크가 스트림 B의 가장
    오래된 이벤트 시각보다 오래된 레코드를 제거한다** (5장, p.123).[^konieczny2025]
  - 다행히 **전체 버퍼링 로직을 직접 다룰 필요는 없다. 데이터 처리 프레임워크에 네이티브로 구현돼
    있기 때문이다** (5장, p.123).[^konieczny2025]
- 시간 조건을 건 스트림-스트림 조인이 이 패턴의 대표 코드다 (5장, p.124):[^konieczny2025]

  ```python
  visits_from_kafka: DataFrame = (visits_data_stream
    .withWatermark('event_time', '10 minutes'))

  ads_from_kafka: DataFrame = (ads_data_stream
    .withWatermark('display_time', '10 minutes'))

  visits_with_ads = visits_from_kafka.join(ads_from_kafka, F.expr('''
      page = visit_page AND
      display_time BETWEEN event_time AND event_time + INTERVAL 2 minutes
    '''), 'left_outer')
  ```

  - 이 조건이 두 언어로 동시에 읽힌다는 것이 요점이다 — **조인 조건은 비즈니스적 의미와 기술적
    의미를 갖는다. 사용자가 페이지를 방문한 뒤 최대 2분 안에 광고가 표시될 수 있다는 비즈니스
    규칙을 명시한다. 기술적 관점에서는 늦은 데이터를 위한 여지가 남아 있다는 뜻이기도 하다.
    `withWatermark` 표현식이 양쪽에서 레코드가 최대 10분까지 늦을 수 있게 허용한다** (5장,
    p.124).[^konieczny2025]
  - Flink에는 더 관리된 대안이 있다 — **시간적 테이블 조인(temporal table joins)**. 그 코드는
    각 토픽의 허용 워터마크를 선언한 뒤 `TemporalTableFunction`을 초기화하는데, 그 함수가
    **각 페이지에 대해 가장 최근 광고를 얻는 중요한 역할을 수행한다. 다르게 말해
    `update_time <= event_time`인 광고를 얻는다** (5장, p.125).[^konieczny2025]

## 공간이냐 정확성이냐

- 대가 ① **공간 대 정확성 맞교환** — **GC 워터마크와 시간 경계 때문에 가능한 모든 조인을 얻지
  못할 수 있다. 버퍼 공간을 늘려 효율을 최적화할 수 있지만 그것은 더 많은 하드웨어 자원을 쓰게
  한다. 반대로 공간을 줄이면 저장이 최적화되지만 지연 차가 너무 크면 매칭 가능성이 줄어들 수 있다.
  그런 이유로 언제나 이 두 요소의 균형을 잡아야 하고, 불행히도 만능 공식은 없다. 각 해법은 당신의
  비즈니스 요구와 조인되는 데이터셋 사이의 통상적 지연 차에 달렸다** (5장,
  pp.123–124).[^konieczny2025]
- 대가 ② **늦은 데이터** — **스트림 처리는 본질적으로 더 낮은 지연 처리 의미론 때문에 파이프라인의
  늦은 데이터 통합에 더 약한 관용을 갖는다. 예컨대 사용자 스트림이 어떤 지역에서 일시적 연결 이슈를
  만나 이벤트 부분집합의 전달이 지연될 수 있다. 결과적으로 GC 워터마크가 앞으로 나아가 버퍼된 상태를
  무효화하고 이 늦은 이벤트들은 무시될 것이다** (5장, p.124).[^konieczny2025]
  - 그래서 저자가 이 범주 전체의 한계를 명시한다 — **여기 제시한 두 데이터 강화 패턴 어느 쪽도 이
    늦은 데이터 도착 이슈 때문에 여분의 노력 없이는 조인 결과를 100% 보장하지 않는다. 이 한계를
    넘으려면 3장에서 설명한 대로 늦은 데이터를 추적하고 통합해야 한다** (5장,
    p.124).[^konieczny2025]

## Wrapper — 계산한 값을 원본과 가른다

- 범주가 바뀌는 자리 — **데이터셋이 데이터 강화 패턴으로 값을 얻고 나면 다음에 물을 질문은 그것으로
  충분한가다. 강화 시나리오에서 데이터는 여전히 원시이거나 비구조적이고, 데이터가 최종 형태인 경우는
  드물다. 추가 준비 작업 없이는 이해하고 붙잡기 어려울 수 있다** (5장,
  p.125).[^konieczny2025]
- 이름의 유래 — **소프트웨어 공학에서 감싸기(wrapping)는 객체에 여분 행동이나 속성을 더하는 것으로
  이뤄진다. 같은 정의가 데이터 세계에서도 유효한데, 여기서 감싸기는 레코드의 원본 부분을 변환된
  부분과 분리하는 데도 도움이 된다** (5장, p.125).[^konieczny2025]
- 문제 — 방문이 여러 데이터 제공자에서 와서 **다른 출력 스키마를 낳는다. 다른 필드들을 추출해 한
  자리에 두어 하류 소비자가 쉬운 처리를 위해 그것에 의존할 수 있게 하는 잡을 써야 한다. 여기 요구는
  처리 로직을 단순화하기 위해 이 계산된 값들을 원본 값들과 명확히 분리하되, 디버깅 필요를 위해 원
  구조를 유지하는 것이다** (5장, pp.125–126).[^konieczny2025]
- 요구가 해법을 좁힌다 — **원 레코드를 손대지 않고 유지해야 한다는 요구가 변환 범위를 줄인다. 행을
  그냥 파싱해 새 구조를 생성할 수 없다. 초기 값들을 잃게 되기 때문이다** (5장,
  p.126).[^konieczny2025]
- 해법 — **레코드 수준에 여분 추상을 더하는 것이다. 그 추상은 원래 값들을 고수준 봉투(envelope)로
  감싼다. 이 초기 속성들에 더해 봉투는 입력 데이터 자체에서 오거나 실행 컨텍스트(예컨대 처리 시각이나
  잡 처리 버전)에서 오는 계산된 속성들을 참조한다. 예컨대 우리 입력 방문 이벤트는 두 절에 각각
  대응하는 원시(raw)와 계산(computed) 필드로 구성된 이벤트로 변환될 수 있다** (5장,
  p.126).[^konieczny2025]
- 형식은 가리지 않는다 — **Apache Avro·Protobuf·JSON 같은 스트리밍에 쓰이는 형식 외에 패턴은
  테이블 같은 구조화 형식에서도 지원된다. 그 맥락에서는 필요하면 원본과 조인할 수 있는 별도 테이블로
  구현하거나 같은 테이블 안의 여분 컬럼으로 구현할 수 있다** (5장, p.126).[^konieczny2025]
  구조화 데이터의 네 구현 (5장, p.126):[^konieczny2025]

  | 구현 | 배치 | 저자가 적은 성질 |
  |---|---|---|
  | 1 | **원 행을 평평한 구조로, 모든 계산 컬럼을 중첩 속성으로 저장** | 비정규화 — **읽기가 더 빠를 수 있다** |
  | 2 | **그 반대. 계산된 행들을 하나의 평평한 구조로 저장** | 비정규화 |
  | 3 | **모든 컬럼을 같은 레벨의 평평한 구조로 저장** | 정규화 — **읽기가 더 느릴 수 있지만 데이터셋을 논리적으로 격리해야 하거나 원 구조를 그냥 바꿀 수 없을 때 더 나은 선택** |
  | 4 | **데이터를 두 개의 분리된 테이블에 저장하고 나중에 유일 키로 조인** | 정규화 |

  - **이 접근들 전부가 스키마 관리를 필요로 한다** (5장, p.126).[^konieczny2025]
  - 저자가 상자로 오해를 막는다 — **봉투가 구조화 형식에서 직접 보이지 않더라도 그것은 여전히 거기
    있다. 사실 봉투는 테이블의 한 행이다. 따라서 정상적인 컬럼 형식을 깨서 예컨대 여러 컬럼의
    필드를 중첩 속성을 가진 한 컬럼에 넣을 필요가 없다** (5장, p.127).[^konieczny2025]
- 계산값을 1급 컬럼으로 올리고 원시 값을 구조체로 내리는 SQL이 이 패턴의 대표 코드다 (5장,
  p.129):[^konieczny2025]

  ```sql
  SELECT
    CASE WHEN context.user.connected_since IS NULL
      THEN false ELSE true END AS is_connected,
    CONCAT_WS('-', page, context.referral) AS page_referral_key,
    STRUCT(visit_id, event_time, user_id, page, context) AS raw
  FROM input_visits
  ```

  - 반대 배치도 가능하지만 조건이 붙는다 — **입력 컬럼과 같은 레벨에 모든 계산 컬럼을 가진 테이블을
    가질 수도 있다. 그러나 그 맥락에서는 이름이 원시와 계산을 명확히 구분하지 않으면 최종 사용자가
    원시 값과 계산 값을 분간하지 못할 수 있음을 알아야 한다** (5장, p.129).[^konieczny2025]

## 감싸기의 두 가지 대가

- 대가 ① **도메인 분할** — **논리적 함의다. 패턴이 주어진 도메인의 속성을 나누기 때문이다. 사용자를
  예로 들면, Wrapper를 구현하면 사용자 관련 필드가 원시와 계산이라는 두 다른 고수준 구조에 있게
  된다. 이 접근은 변환된 값과 변환되지 않은 값 사이의 명확한 구분 같은 이점이 있지만 데이터 검색을
  더 복잡하게 만들기도 한다. 소비자는 사용자 데이터가 이 두 자리에 있음을 알아야 한다** (5장,
  pp.127–128).[^konieczny2025]
  - 맞교환의 형태 — **감싼 데이터를 시스템의 첫 저장 계층, 예컨대 사례 연구의 실버 계층에 속하는
    것으로 보고, 이 분리가 혼란스러울 수 있는 사용자에게 노출되는 최종 데이터로는 보지 않을 수
    있다** (5장, p.128).[^konieczny2025]
- 대가 ② **크기** — **장식된 값은 처리된 레코드의 본질적 부분을 이루므로 전체 크기와 네트워크
  트래픽에 영향을 준다. 이는 다음 절에서 볼 Metadata Decorator 패턴의 행동과 다르다** (5장,
  p.128).[^konieczny2025]
  - 완화책 — **데이터 저장 형식이 데이터 원천 프로젝션을 지원한다면 한계를 완화할 수 있다. 이
    기능으로 관심 있는 컬럼을 골라 데이터 원천에 그것들만 물리적으로 접근하도록 요청할 수 있다. 이
    관행은 AWS Redshift·GCP BigQuery 같은 컬럼 지향 데이터 저장을 활용하는 모든 해법에서 매우
    흔하다** (5장, p.128).[^konieczny2025] 그 저장 방식은
    [컬럼 지향 저장](../concepts/column-oriented-storage.md)에 있다.

## Metadata Decorator — 소비자에게 숨긴다

- 왜 Wrapper로 부족한가 — **Wrapper 패턴은 레코드를 감싸는 것이 언제나 가능하므로 보편적이다.
  그러나 더해진 값들이 최종 사용자에게 직접 노출되면 안 될 때 그것은 소비자를 오도할 수 있다. 결국
  최종 사용자는 레코드가 잡 버전 1로 생성됐는지 2로 생성됐는지 신경 쓰지 않을 것이다. 이 문제를
  넘으려면 데이터 저장의 메타데이터 계층에 여분 레코드를 숨길 수 있다** (5장,
  p.129).[^konieczny2025]
- 문제 — 스트리밍 잡이 **거의 주 1회 새 버전을 릴리스**하는데, **배포 프로세스는 매끄럽지만 릴리스된
  버전이 생성된 데이터에 미치는 영향에 대한 가시성이 부족하다. 유지보수 활동을 단순화하려면 각 생성
  레코드에 잡 버전 같은 기술적 맥락을 더해야 한다. 그러나 이 정보를 최종 사용자에게 보내는 레코드에
  포함하고 싶지는 않다** (5장, pp.129–130).[^konieczny2025]
- 구현은 저장소가 정한다 (5장, p.130):[^konieczny2025]
  - **메타데이터를 기본으로 지원한다면 쓰인 각 레코드를 전용 메타데이터 속성과 연관시킬 수 있다. 이
    속성이 데이터 생산자 능력의 네이티브 부분이므로 구현이 비교적 간단하다. 키와 값 속성 외에 각
    레코드에 대해 선택적 헤더 키-값 쌍 목록을 지원하는 Apache Kafka가 그 경우다.**
  - **객체 저장소로 일하고 메타데이터 장식이 주어진 파일에 있는 모든 행에 적용된다면 메타데이터
    속성을 파일에 연관된 태그로 정의할 수 있다.**
  - **태그를 쓸 수 없다면 다른 데이터 저장은 메타데이터 장식을 네이티브로 지원하지 않을 수 있다.
    관계형이나 NoSQL 데이터베이스가 그 경우다. 그것들에서는 메타데이터를 데이터 부분에 포함하되
    최종 사용자에게 공개적으로 노출하지 않는 식으로 장식을 흉내 낼 수 있다.** 구체적으로는
    **각 레코드마다 메타데이터를 개별 추적하고 싶다면 전용 컬럼에 쓴 뒤 그 기술적 정보 없이 뷰에서
    테이블을 노출하거나, 비기술 사용자가 그 컬럼을 읽지 못하도록 권한을 쓰면 된다.**
  - 둘째 선택지는 정규화다 — **처리 맥락을 데이터셋과 조인될 전용 테이블에 저장할 수도 있다. 여기서는
    구현이 훨씬 단순한데, 이 테이블을 팀의 기술 구성원만 접근 가능한 스키마에 문자 그대로 숨길 수
    있기 때문이다.** 그러면 **메타데이터 맥락이 별도 테이블로 정규화되므로 각 행마다 중복되지
    않는다** (5장, p.131).[^konieczny2025]
- Wrapper와의 차이를 저자가 상자로 못 박는다 — **이 메타데이터 장식은 Wrapper 패턴에서 본 것과
  비슷하다. 유일한 차이는 의미론이다. 메타데이터는 정의상 데이터에 대한 서술이므로 비즈니스 사용자에게
  공개적으로 노출되면 안 된다. Wrapper는 기술 속성에 더해 비즈니스 속성을 장식하려는 의도이므로
  그렇지 않다** (5장, p.131).[^konieczny2025]
- 카프카 헤더를 붙이는 PySpark 쓰기가 이 패턴의 대표 코드다 — **메타데이터는 키-값 쌍의 배열이고,
  `includeHeaders` 옵션이 생성된 레코드에 헤더 컬럼을 포함하도록 Apache Spark에 지시한다** (5장,
  p.132):[^konieczny2025]

  ```python
  visits_with_metadata = (visits_to_save.withColumn('headers', F.array(
    F.struct(F.lit('job_version').alias('key'), F.lit(job_version).alias('value')),
    F.struct(F.lit('batch_version').alias('key'),
    F.lit(str(batch_number)).encode('UTF-8')).alias('value'))))
  (visits_with_metadata.write.format('kafka')
    .option('kafka.bootstrap.servers', 'localhost:9094')
    .option('includeHeaders', True).option('topic', 'visits-decorated')
  .save())
  ```

## 장식의 두 가지 대가

- 대가 ① **구현** — **문제 서술의 스트리밍 브로커조차 네이티브 메타데이터 지원이 없어 그것들에는
  구현이 불가능할 수 있다. 예컨대 Amazon Kinesis Data Streams는 헤더를 지원하지 않는다** (5장,
  p.131).[^konieczny2025]
  - #hypothesis 이 지원 목록은 집필 시점(2024) 기준이다 — 관리형 스트리밍 서비스의 기능 표면은
    이후 릴리스에서 달라졌을 수 있으므로 적용 전 벤더 문서로 확인해야 한다.
  - **테이블 데이터셋에서도 구현이 도전적일 수 있는데, 앞서 보였듯 메타데이터 정보를 다룰 여분
    컬럼이나 테이블을 정의해야 하는 경우가 흔하기 때문이다. 동작하기는 하지만 메타데이터 장식을
    네이티브로 지원하는 데이터 저장보다 더 많은 노력을 요구한다** (5장,
    p.131).[^konieczny2025]
- 대가 ② **무엇을 넣을 것인가** — **메타데이터 계층에 어떤 유형의 정보를 넣을 수 있는지에 기술적
  한계는 없지만, 배송 주소나 청구 금액 같은 비즈니스 관련 속성을 거기 쓰는 것은 피해야 한다.
  그러지 않으면 그것들은 소비자에게 숨겨진 채 남는데, 대부분은 메타데이터 부분을 질의할 생각을 결코
  하지 않을 것이기 때문이다. 정의상 메타데이터는 데이터에 대한 데이터이고, 어떤 외부 데이터셋
  사용자든 주로 그 문장 둘째 부분의 데이터에 관심을 가질 것이다** (5장,
  p.131).[^konieczny2025]

## 이 이름들의 원전 — Content Enricher와 Envelope Wrapper

이 장의 **강화(enrichment)** 와 **감싸기(wrapping)** 는 새 낱말이 아니다. 2004년의 기업 통합 패턴
카탈로그가 *Content Enricher*와 *Envelope Wrapper*라는 이름으로 같은 두 동작을 이미 정의했고,
그때는 데이터 파이프라인이 아니라 메시지 하나가 단위였다. 계열 전체는
[메시지 변환 패턴](message-transformation-patterns.md)에 있고, 여기서는 이 페이지의 네 패턴과
직접 겹치는 대목만 옮긴다.

- *Content Enricher*의 문제 — **메시지 발신자가 요구되는 데이터 항목을 전부 갖고 있지 않다면 다른
  시스템과 어떻게 통신하는가?** (8장, p.336).[^hohpe2004]
- **단순한 형식 변환과 갈리는 지점이 명시된다** — ***Message Translator*(85)의 서술은 수신
  애플리케이션이 필요로 하는 데이터가 형식은 틀렸을지언정 이미 들어오는 메시지에 담겨 있다고
  가정했다. 이 새로운 경우에는 필드를 재배열하는 단순한 문제가 아니다. 우리는 실제로 메시지에 추가
  정보를 주입해야 한다** (8장, p.336).[^hohpe2004]
- 해법 — **특화된 변환기인 *Content Enricher*를 써서 외부 데이터 소스에 접근해 없는 정보로 메시지를
  증강하라** (8장, p.338).[^hohpe2004]
- 기제는 위 Static Joiner·Dynamic Joiner와 같은 구조다 — ***Content Enricher*는 들어오는 메시지
  안의 정보(예: 키 필드)를 써서 외부 소스에서 데이터를 회수한다. *Content Enricher*가 필요한
  데이터를 자원에서 회수한 뒤 그 데이터를 메시지에 덧붙인다. 들어오는 메시지의 원래 정보는 결과
  메시지로 넘어갈 수도 있고 수신 애플리케이션의 구체적 필요에 따라 더 이상 필요 없을 수도 있다**
  (8장, p.339).[^hohpe2004]

### 원전이 세운 세 가지 정보 출처

이 페이지의 두 조이너는 **다른 데이터셋**만을 출처로 다룬다. 원전은 출처를 셋으로 갈랐고, 그중
둘은 이 페이지에 대응 항목이 없다.

- **① 계산(Computation)** — ***Content Enricher*가 없는 정보를 계산할 수 있다. 이 경우 알고리즘이
  추가 정보를 통합한다. (…) 이 형태의 *Content Enricher*는 외부 데이터 소스가 필요 없으므로 기본
  *Message Translator*(85)와 아주 비슷하다** (8장, p.339).[^hohpe2004] 이 페이지에서는 계산 결과를
  붙이는 것이 강화가 아니라 **장식(Wrapper)** 으로 분류된다 — 두 카탈로그의 절단면이 다르다.
- **② 환경(Environment)** — ***Content Enricher*가 운영 환경에서 추가 데이터를 회수할 수 있다.
  가장 흔한 예는 타임스탬프다** (8장, p.339).[^hohpe2004] 이 페이지의 Metadata Decorator가
  잡 버전·배치 번호를 붙이는 것이 정확히 이 갈래다.
- **③ 다른 시스템(Another System)** — **이 선택지가 가장 흔하다. *Content Enricher*는 다른
  시스템에서 없는 데이터를 회수해야 한다. 이 데이터 자원은 데이터베이스·파일·LDAP 디렉터리·
  애플리케이션, 또는 없는 데이터를 수동으로 입력하는 사용자를 포함해 여러 형태를 취할 수 있다**
  (8장, p.339).[^hohpe2004] 위 Static Joiner와 Dynamic Joiner가 이 갈래를 정지/움직이는 참조
  데이터로 다시 나눈 것이다.
- **여기서는 느슨한 결합이 목표가 아니라는 판단이 명시된다** — ***Content Enricher*와 데이터 소스
  사이의 상호작용은 정의상 동기적이므로(*Content Enricher*는 데이터 소스가 요청된 데이터를 반환할
  때까지 강화된 메시지를 보낼 수 없다) 동기 프로토콜(예: HTTP나 데이터베이스로의 ODBC 연결)이 비동기
  메시징을 쓰는 것보다 나은 성능을 낼 수 있다. *Content Enricher*와 데이터 소스는 본질적으로
  단단히 결합돼 있으므로 *Message Channel*(60)을 통해 느슨한 결합을 달성하는 것은 그만큼 중요하지
  않다** (8장, p.340).[^hohpe2004] 이 페이지의 Static Joiner가 참조 데이터셋을 브로드캐스트로
  들고 다니는 선택과 같은 판단이다 — 조회 상대와의 결합은 어차피 끊을 수 없으므로 성능으로 고른다.

### 원전이 기각한 것 — 강화를 어디에 두는가

이 페이지가 "강화를 파이프라인 단계로 둔다"를 전제하고 시작하는 데 반해, 원전은 **그 배치 자체를
논증한다**. 네 대안을 세우고 전부 기각한 뒤에야 별도 컴포넌트에 도달한다.

- **발신 쪽을 고쳐 정보를 저장하게 한다(A)** — 기각 근거는 **우리가 다른 시스템의 구체적 필요에
  기반해 그 시스템을 바꾸고 있다**는 것이다 (8장, p.337).[^hohpe2004]
- **발신 쪽이 보내기 직전에 조회한다(B)** — **느슨하게 결합된 시스템에서 우리는 한 시스템이 다음
  시스템에게 무엇을 하라고 지시하는 것을 원하지 않는다. (…) 게다가 이 해법은 일정 시스템을 고객
  관리 시스템에 더 단단히 결합시킨다 — 일정 시스템이 이제 없는 데이터를 어디서 가져올지 알아야
  하기 때문이다** (8장, p.338).[^hohpe2004]
- **데이터를 가진 쪽을 먼저 거치게 한다(C)** — **이제 우리는 (…) 업무 규칙을 고객 관리 시스템 안에
  구현하게 된다. (…) 어떤 필드가 다른 시스템에서 회수돼야 한다면 우리는 시작한 곳과 비슷한 상황에
  있게 된다** (8장, p.338).[^hohpe2004]
- **수신 쪽이 스스로 회수하게 고친다(D)** — **첫째, 이제 회계 시스템을 고객 관리 시스템에 결합시킨다.
  둘째, 이 선택지는 다시 우리가 회계 시스템에 대한 통제를 갖는다고 전제한다** (8장,
  p.338).[^hohpe2004]
- 남는 판단: **강화를 생산자에도 소비자에도 두지 않고 사이의 별도 단계에 둔다.** 그것이 이 페이지의
  Static/Dynamic Joiner가 파이프라인 안의 독립 단계로 서 있는 이유의 논증이고, 이 페이지 자체는
  그 논증을 생략한 채 결론만 물려받았다.
- 참조로 보내고 나중에 복원하는 맞교환도 원전이 세워 둔다 — **참조의 사용이 성능을 개선하는지는
  얼마나 많은 컴포넌트가 참조만으로 단순히 작동할 수 있는가 대 얼마나 많은 컴포넌트가 원본 메시지
  내용 일부를 복원하기 위해 *Content Enricher*를 써야 하는가에 의존한다. 예컨대 메시지가 최종
  수신자에 도달하기 전에 긴 중개자 목록을 통과하면 객체 참조를 쓰는 것이 메시지 트래픽을 크게 줄일
  수 있다. 우리는 최종 수신자 직전의 마지막 단계로 *Content Enricher*를 삽입해 없는 정보를 메시지에
  적재할 수 있다** (8장, p.341).[^hohpe2004] 강화 단계를 **파이프라인의 어느 지점에 놓을
  것인가**를 성능으로 판단하는 자리다.

### Wrapper라는 낱말이 두 카탈로그에서 다른 것

같은 이름이지만 감싸는 목적이 다르다. 판정은 충돌이 아니라 **다른 대상**이다.

- 원전의 *Envelope Wrapper*가 푸는 문제 — **메시지 헤더 필드나 암호화 같은 구체적 요구를 메시지
  형식에 부과하는 메시징 교환에 기존 시스템이 어떻게 참여할 수 있는가?** (8장,
  p.330).[^hohpe2004] 곧 **인프라 규약에 맞추기 위한** 감싸기다.
- 이 페이지의 Wrapper는 **계산한 비즈니스·기술 속성을 원본과 가르기 위한** 감싸기다. 저자가 스스로
  Metadata Decorator와 대비하며 **Wrapper는 기술 속성에 더해 비즈니스 속성을 장식하려는 의도**라고
  적었다 (5장, p.131).[^konieczny2025]
- 그런데 원전도 봉투가 정보를 더한다는 것을 인정하고, **어디까지가 강화인지의 선을 긋는다** —
  **래퍼가 원시 메시지에 정보를 더하는 것은 전형적이다. (…) 그런 의미에서 래퍼는 *Content
  Enricher*(336)의 어떤 측면을 통합한다. **그러나 래퍼는 실제 정보 내용을 강화하지 않고, 메시지의
  라우팅·추적·처리에 필요한 정보를 더한다**** (8장, p.332).[^hohpe2004] 이 구분선은 이 페이지가
  Metadata Decorator에 그은 선(**메타데이터는 정의상 데이터에 대한 서술이므로 비즈니스 사용자에게
  공개적으로 노출되면 안 된다**, 5장 p.131)과 같은 자리에 있다.
- **승격(promotion)이라는 이름이 여기 있다** — **데이터가 원래 메시지 바디에 담겨 있다가 래퍼에
  의해 메시지 헤더로 갈라질 수도 있다(예: 원시 메시지에 담긴 키 필드). 이 마지막 선택지는 때로
  *승격(promotion)* 이라 불린다 — 특정 필드가 바디 안에 숨어 있던 상태에서 헤더에 두드러지게 보이는
  상태로 "승격"되기 때문이다** (8장, p.332).[^hohpe2004] 이 페이지의 Metadata Decorator가 카프카
  헤더에 값을 쓰는 것이 그 반대 방향(강등)의 실물이다 — 같은 헤더/바디 경계를 양쪽에서 쓴다.
- 정리하면 이름 계보는 이렇다.

  | 이 페이지(2025) | 원전(2004) | 무엇이 달라졌는가 |
  |---|---|---|
  | Static Joiner · Dynamic Joiner | *Content Enricher* | 단위가 메시지에서 데이터셋·스트림으로. 참조 데이터가 정지인가 움직이는가로 갈림 |
  | Wrapper | *Envelope Wrapper* | 감싸는 목적이 인프라 적합에서 계산값 분리로 |
  | Metadata Decorator | *Envelope Wrapper*의 헤더 부분 | 숨기는 것이 목적이 됨. 원전은 라우팅·추적이 목적 |
  | (없음) | *Content Filter* · *Claim Check* | 정보를 덜어 내는 쪽. 이 카탈로그에서는 5장 집계 계열과 4장 보안 계열로 흩어짐 |
