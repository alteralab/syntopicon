# 클릭스트림 팩트

**목차**: [원천 데이터의 세 가지 난점](#원천-데이터의-세-가지-난점) · [세션화 — 방법별 신뢰도 서열](#세션화-방법별-신뢰도-서열) · [클릭스트림 전용 차원 4종](#클릭스트림-전용-차원-4종) · [grain 선택 — 세션 팩트와 페이지 이벤트 팩트 두 벌](#grain-선택-세션-팩트와-페이지-이벤트-팩트-두-벌) · [집계와 외부 서비스](#집계와-외부-서비스)

한 페이지의 질문: **웹 서버가 쏟아내는 페이지 이벤트의 급류(clickstream)를
어떤 grain의 [팩트 테이블](../concepts/fact-table.md)로, 어떤 전용 차원과 함께
설계하나?** (15장)

## 원천 데이터의 세 가지 난점

- 무상태(stateless): HTTP에는 세션 개념이 없다. 로그의 페이지 이벤트는 고립돼
  있어, 별도 장치 없이는 완결된 방문 세션을 신뢰성 있게 식별할 수 없다 (15장,
  pp.354–355).[^kimball2013]
- 익명성: 방문자가 신원을 밝히지 않는 한 누구인지, 재방문인지 알 수 없다.
  쿠키는 사람이 아니라 기계를 식별한다 — 같은 사람이 회사·집·모바일 기기를
  오가면 기기마다 다른 쿠키가 박힌다 (15장, pp.354, 357).[^kimball2013]
- 분산 수집: 여러 물리 서버가 동시에 로그를 남기므로 사후 동기화 문제가
  생긴다. 바쁜 서버는 초당 수백 이벤트를 처리하는데 서버 간 시계는 1/100초
  단위로 맞지 않는다 (15장, p.354).[^kimball2013]

## 세션화 — 방법별 신뢰도 서열

세션 식별(sessionizing) 방법 다섯 가지와 한계 (15장, pp.355–356):[^kimball2013]

- 동일 호스트(IP)의 시간 연속 로그 묶기 — 쿠키 불필요하나, 동적 IP 재사용·
  세션 중 IP 변경·방화벽 뒤 브라우저에서 무너진다. 견고한 후처리 알고리즘과
  "결과를 언제 믿지 말지"의 판단이 필요하다.
- 세션 수준 쿠키 — 훨씬 만족스럽지만 브라우저를 닫으면 사라져 재방문을 못
  잇는다.
- SSL 로그인 — 추적은 되지만 전 구간 SSL 오버헤드와 보안 경고 팝업 부담.
- 동적 페이지의 숨은 필드로 세션 ID 핑퐁 — 페이지 생성을 전면 통제해야 하고,
  ID를 안 나르는 링크 하나로 세션이 여럿으로 쪼개진다.
- **영속 쿠키(persistent cookie) — 가장 신뢰할 만한 방법.** 단, 쿠키 거부·수동
  삭제가 있으므로 절대 보장은 아니다.
- 세션 ID는 웹 서버가 아니라 주문 입력 같은 운영 애플리케이션이 발급한다는
  점에 유의 (15장, p.355).[^kimball2013]

## 클릭스트림 전용 차원 4종

일반 차원(날짜·고객·상품·프로모션 등) 외에 클릭스트림에만 있는 차원은
page·event·session·referral 넷이다 (15장, pp.357–358).[^kimball2013]

- **페이지(page) 차원**: grain은 "구별할 가치가 있는 페이지 유형". 동적
  페이지의 인스턴스마다 행을 만들면 행 수가 천문학적이 되므로, 정적 페이지는
  행 하나씩, 동적 페이지는 기능·유형으로 묶는다. 페이지 개발자가 서술 코드를
  로그의 선택 필드에 심어 주는 것이 이 차원 구현의 토대다 (15장,
  pp.358–359).[^kimball2013]
- **이벤트(event) 차원**: 그 페이지에서 무엇이 일어났나 — Open Page, Refresh
  Page, Click Link, Enter Data 정도의 작은 차원 (15장, p.359).[^kimball2013]
- **세션(session) 차원**: 세션 전체의 진단 — 국지 맥락(예: 상품 정보 요청),
  세션 맥락(예: 상품 주문), 성공 여부, 고객 상태 라벨. 세션 ID보다 높은
  수준으로, 개별 세션이 아니라 세션의 부류를 기술한다. 짧은 주기로 바뀌는
  고객 상태 라벨은 고객 차원이 아니라 여기에 둔다 (15장, pp.359–360, 365).[^kimball2013]
- **유입(referral) 차원**: 어떻게 이 페이지에 왔나 — 유입 유형·URL·검색어.
  원시 검색 스펙은 그대로 넣지 말고 단순화·정제한 스펙을 넣는다 (15장,
  p.360).[^kimball2013]

## grain 선택 — 세션 팩트와 페이지 이벤트 팩트 두 벌

### 세션 grain 팩트 테이블

- 첫 팩트 테이블의 grain은 **완결된 방문 세션 1건 = 1행**. 원천(개별 페이지
  이벤트)보다 높은 grain을 택하는 것은 "가장 원자적인 데이터로 시작하라"는
  표준 관행에서의 **의도적 이탈**이다 — 하루 1억 페이지 페치·10억 마이크로
  이벤트를 2천만 세션으로 줄여 적재량을 관리한다 (15장, p.361).[^kimball2013]
- 차원: 날짜 2역할(국제 동기화용 UTC + 방문자 벽시계 로컬), 고객, 진입
  페이지, 세션, 유입. 시각은 시간대 차원 대신 날짜/시각 스탬프로 둔다 —
  시각 차원은 의미 있는 속성이 없고, 스탬프끼리 직접 산술로 세션 간 간격을
  구할 수 있다 (15장, pp.361–362).[^kimball2013]
- 팩트: 세션 초(session seconds)·방문 페이지 수·주문 수·주문 수량·주문
  금액. 마지막 페이지의 체류 시간은 알 수 없는 경우가 많으므로(브라우저 종료,
  이탈) 추출 단계에서 작은 명목값을 배정해 왜곡을 막는다 (15장, pp.361,
  363).[^kimball2013]
- 상품 단위 인과(causal) 차원은 세션 grain에 넣지 않는다 — 한 세션에 여러
  상품이 얽히는 다중값 문제가 생긴다. 전 상품에 걸친 시장 상황 차원이라면
  세션 grain에도 적절하다 (15장, p.363).[^kimball2013]

### 페이지 이벤트 grain 팩트 테이블

- 둘째 팩트 테이블의 grain은 **개별 페이지 이벤트 1건 = 1행** — DW가 감당할
  수 있는 실질적 최저 grain이다. GIF/JPG 같은 마이크로 이벤트는 버린다 (15장,
  p.363).[^kimball2013] 더 거친 grain으로 집계해 두고 싶은 유혹은 참아야
  한다 — 집계는 반드시 차원을 떨어뜨리며, 세션 grain 테이블이 바로 그런
  집계라서 방문자 행동·개별 페이지 질문에는 답하지 못한다 (15장,
  pp.363–364).[^kimball2013]
- 세션 ID는 조인 상대가 없는 퇴화 차원(degenerate dimension)으로 실어, 한
  세션의 페이지 이벤트들을 묶고 세션 grain 테이블과 잇는 부모 키 역할을
  시킨다 (15장, p.365).[^kimball2013]
- 페이지 체류 초는 session seconds와 구별해 page seconds로 명명한다 — 정확히
  등가가 아닌 측정값에 같은 이름을 주면 부적절하게 합산된다(표준 팩트 명명
  규율) (15장, p.365).[^kimball2013]
- 주문 수량·금액 팩트는 주문 이벤트가 아닌 행에서 0/널이지만 넣는다 — 수익을
  행동에 직접 잇는 가치가 크고, 널 팩트는 저장 비용이 거의 없다 (15장,
  pp.365–366).[^kimball2013]

### 스텝(step) 차원 — 순차 프로세스의 위치

- grain이 페이지 이벤트라서 스텝 차원(step dimension)을 붙일 수 있다: 스텝
  번호 + 끝까지 남은 스텝 수로, 세션 안에서 이 이벤트가 어디쯤인지 표현한다
  (15장, p.366).[^kimball2013]
- 세 역할로 단다: 전체 세션 / 구매 하위 세션(구매로 끝난 경로) / 이탈 하위
  세션(구매 미완 경로). 구매 스텝 = 1로 제약하면 성공 구매 경험의 시작
  페이지만, 이탈 스텝의 남은 수 = 0으로 제약하면 실패 세션의 마지막(아마도
  가장 불만족스러운) 페이지만 나온다 (15장, p.366).[^kimball2013]
- 이 기법은 구매 분석 전용이 아니라 **모든 순차 프로세스 분석에 쓸 수 있다**
  (15장, p.366).[^kimball2013]

## 집계와 외부 서비스

- 자주 도는 요약 질의(예: 월×인구통계군별 방문·매출)는 세션 grain 테이블에서
  축소 롤업 차원(월·인구통계·진입 페이지·세션 결과)으로 묶은 집계 팩트
  테이블을 만든다 — 원본의 1% 미만 크기로 100배 이상의 성능을 기대한다
  (15장, pp.366–367).[^kimball2013]
- Google Analytics는 "외부 데이터 웨어하우스"로서 이 장의 정보 대부분을
  수집해 준다(PII 제외) (15장, p.367).[^kimball2013] #hypothesis 2013년 시점
  기술이라 GA 구현 세부(추적 코드 방식·약관)는 낡았을 가능성이 크다 —
  세션화·grain 선택의 원리만 취하는 것이 안전하다.

[^kimball2013]: Kimball & Ross 2013, 15장 "Electronic Commerce"
