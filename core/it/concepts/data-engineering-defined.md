하나의 질문: **데이터 엔지니어링이라는 이름이 가리키는 일의 경계는 어디인가.**

## 정의가 갈린다는 사실에서 출발한다

- 출발점 — **데이터 엔지니어링이 지금 인기 있음에도 그것이 무엇을 뜻하고 데이터
  엔지니어가 무엇을 하는지에 대한 혼란이 크다. 데이터 엔지니어링은 회사들이 예측
  분석·기술 분석(descriptive analytics)·리포트처럼 데이터로 무언가를 하기
  시작한 이래 어떤 형태로든 존재해 왔고, 2010년대 데이터 과학(data science)의
  부상과 함께 초점이 뚜렷해졌다** (1장, p.3).[^reis2022]
- 정의의 수 — **데이터 엔지니어링의 정의는 끝없이 존재한다. 2022년 초 "what is
  data engineering?"의 구글 정확 일치 검색은 91,000건이 넘는 고유 결과를
  돌려준다** (1장, p.3).[^reis2022]
- 저자들이 인용한 기존 정의 넷은 서로 층위가 다르다 (1장, pp.3–4):[^reis2022]
  - AlexSoft — **데이터 엔지니어링은 정보의 흐름과 접근을 위한 인터페이스와 기제를
    만드는 것을 목표로 하는 일련의 작업이다. 요컨대 데이터 엔지니어는 조직의 데이터
    인프라를 세우고 운영하며, 데이터 분석가와 과학자의 추가 분석을 위해 그것을
    준비한다.**
  - Jesse Anderson — **첫째 유형은 SQL 중심이다. 데이터의 작업과 일차 저장이
    관계형 데이터베이스에 있고 모든 데이터 처리가 SQL이나 SQL 기반 언어로
    이뤄진다. 둘째 유형은 빅데이터(Big Data) 중심이다. 하둡·카산드라·HBase 같은
    빅데이터 기술에 저장하고 맵리듀스·스파크·플링크 같은 빅데이터 프레임워크로
    처리한다.**
  - Maxime Beauchemin — **기존 역할에 견주면 데이터 엔지니어링 분야는 비즈니스
    인텔리전스(business intelligence)와 데이터 웨어하우징의 상위집합(superset)에
    소프트웨어 엔지니어링 요소를 더 많이 들여온 것으로 생각할 수 있다.**
  - Lewis Gavin — **데이터 엔지니어링은 데이터의 이동·조작·관리에 관한 전부다.**
- 저자들의 평 — **이것은 정의 몇 개일 뿐이지만 데이터 엔지니어링의 의미에 대한
  엄청난 범위의 의견을 담고 있다** (1장, p.4).[^reis2022]

## 이 책의 정의

- 공통 실을 풀면 패턴이 드러난다 — **데이터 엔지니어는 데이터를 얻고, 저장하고,
  데이터 과학자·분석가 등의 소비를 위해 준비한다** (1장, p.4).[^reis2022]
- 이 책이 세우는 정의는 왜곡에 민감한 구간이라 원문을 그대로 옮긴다 (1장,
  p.4):[^reis2022]

  > Data engineering is the development, implementation, and maintenance of systems
  > and processes that take in raw data and produce high-quality, consistent
  > information that supports downstream use cases, such as analysis and machine
  > learning. Data engineering is the intersection of security, data management,
  > DataOps, data architecture, orchestration, and software engineering. A data
  > engineer manages the data engineering lifecycle, beginning with getting data from
  > source systems and ending with serving data for use cases, such as analysis or
  > machine learning.

  이 정의는 두 축으로 이뤄져 있다 — **수명 주기**(원천 시스템에서 데이터를 얻는 데서
  시작해 유스케이스에 데이터를 서빙하는 데서 끝난다)와 **여섯의 교차점**(보안·데이터
  관리·DataOps·데이터 아키텍처·오케스트레이션·소프트웨어 엔지니어링). 그 두 축의
  전개는 [데이터 엔지니어링 수명 주기](../synthesis/data-engineering-lifecycle.md)에 있다.
- 이 프레임의 의도 — **기술에 고착해 큰 그림을 근시안적으로 놓치기가 너무 쉽다. 이
  책은 데이터 엔지니어링 수명 주기(data engineering lifecycle)라는 큰 아이디어를
  중심에 두며, 그것이 데이터 엔지니어에게 자기 역할을 보는 총체적 맥락을 준다고
  믿는다** (1장, p.5).[^reis2022]
- **수명 주기는 대화를 기술에서 데이터 자체와 그것이 섬겨야 할 최종 목표 쪽으로
  옮긴다** (1장, p.5).[^reis2022]

## 데이터 과학의 상류

- 자리 — **데이터 엔지니어링은 데이터 과학·분석과 별개다. 서로를 보완하지만 뚜렷이
  다르다. 데이터 엔지니어링은 데이터 과학의 상류(upstream)에 앉는다 — 데이터
  엔지니어가 데이터 과학자(데이터 엔지니어링의 하류)가 쓰는 입력을 공급하고,
  데이터 과학자는 그 입력을 유용한 것으로 바꾼다** (1장, p.11).[^reis2022]
- 근거로 드는 계층 — Monica Rogati의 **데이터 과학 욕구 단계(Data Science Hierarchy
  of Needs, 2017)**. **많은 데이터 과학자가 ML 모델을 만들고 튜닝하고 싶어 하지만,
  현실은 그들 시간의 70%에서 80%가 계층의 아래 세 부분 — 데이터 수집·정제·처리 —
  에서 소모되고 분석과 ML에는 아주 작은 조각만 쓰인다는 것이다** (1장,
  p.12).[^reis2022]
- 그래서 나오는 처방 — **회사는 AI·ML 같은 영역을 다루기 전에 견고한 데이터 기반
  (계층의 아래 세 층)을 지어야 한다. 이상적인 세계라면 데이터 과학자는 시간의 90%
  이상을 피라미드 위층 — 분석·실험·ML — 에 써야 한다** (1장, p.12).[^reis2022]
- 이유 — **데이터 과학자는 보통 프로덕션 등급 데이터 시스템을 엔지니어링하도록
  훈련받지 않았고, 데이터 엔지니어의 지원과 자원이 없기 때문에 그 일을 임기응변으로
  하게 된다** (1장, p.12).[^reis2022]

## 무엇을 하지 않는가

- 경계 — **데이터 엔지니어는 보통 ML 모델을 직접 만들거나, 리포트·대시보드를
  만들거나, 데이터 분석을 수행하거나, 핵심성과지표(KPI)를 세우거나, 소프트웨어
  애플리케이션을 개발하지 않는다. 다만 이해관계자를 가장 잘 섬기려면 이 영역들에
  대한 작동 수준의 이해는 갖춰야 한다** (1장, p.13).[^reis2022]
- 반대로 놓지 않는 것 — **데이터 엔지니어는 프로덕션 등급의 소프트웨어 엔지니어링
  실력을 갖춰야 한다. 프로덕션 등급 코드를 쓸 수 없는 데이터 엔지니어는 심각하게
  발목이 잡힐 것이고, 그것이 곧 바뀔 것 같지도 않다. 데이터 엔지니어는 그 많은 다른
  역할에 더해 여전히 소프트웨어 엔지니어다** (1장, pp.19–20).[^reis2022]
- 다만 그 소프트웨어 작업의 성격이 바뀌었다 — **완전 관리형 서비스가 이전에
  엔지니어에게 기대되던 저수준 프로그래밍 노력의 상당 부분을 대체한다. 예컨대 데이터
  엔지니어는 이제 고수준 추상에 집중하거나 오케스트레이션 프레임워크 안에서
  파이프라인을 코드로 쓴다** (1장, p.19).[^reis2022]
- 최적화 축 — **데이터 엔지니어는 복잡한 움직이는 부품을 여럿 저글링하며 비용·민첩성
  ·확장성·단순성·재사용·상호운용성이라는 축을 따라 끊임없이 최적화해야 한다** (1장,
  p.13).[^reis2022]

## 역할의 연속체 — A형과 B형

- 왜 나누는가 — **직무 기술서는 데이터 엔지니어를 상상 가능한 모든 데이터 기술을
  갖춘 "유니콘"으로 그리지만, 데이터 엔지니어가 전부 같은 종류의 일을 하거나 같은
  기술 집합을 갖지는 않는다** (1장, pp.21–22).[^reis2022]
- 빌려 온 구분 — **데이터 과학에는 A형·B형 데이터 과학자라는 개념이 있다. A형(A는
  분석 analysis)은 데이터를 이해하고 통찰을 끌어내는 데 집중한다. B형(B는 구축
  building)은 비슷한 배경에 강한 프로그래밍 능력을 갖추고, 데이터 과학이 프로덕션에서
  작동하게 하는 시스템을 짓는다** (1장, p.22).[^reis2022]
- **A형 데이터 엔지니어 — A는 추상(abstraction)이다. 차별화되지 않는 무거운 작업을
  피하고, 데이터 아키텍처를 가능한 한 추상적이고 단순하게 유지하며, 바퀴를 다시
  발명하지 않는다. 전적으로 기성 제품·관리형 서비스·도구를 써서 데이터 엔지니어링
  수명 주기를 관리한다. 모든 산업, 모든 데이터 성숙도 수준의 회사에서 일한다** (1장,
  p.22).[^reis2022]
- **B형 데이터 엔지니어 — B는 구축(build)이다. 회사의 핵심 역량과 경쟁 우위를
  확장하고 활용하는 데이터 도구와 시스템을 짓는다. 데이터 성숙도 범위에서는 2·3단계
  (데이터로 확장·데이터로 선도) 회사에서, 또는 초기 유스케이스가 너무 독특하고
  미션 크리티컬해서 커스텀 도구가 필요할 때 더 흔히 보인다** (1장, p.22).[^reis2022]
- 둘의 관계 — **A형과 B형은 같은 회사에서 일할 수 있고 심지어 같은 사람일 수도
  있다. 더 흔하게는 A형이 먼저 고용돼 기반을 놓고, 필요가 생기면서 B형 기술이
  학습되거나 채용된다** (1장, p.22).[^reis2022]

## 일차 언어 넷

- **집필 시점 데이터 엔지니어링의 일차(primary) 언어는 SQL·파이썬·JVM 언어(보통
  자바나 스칼라)·bash 넷이다** (1장, p.20).[^reis2022]
  - **SQL** — **데이터베이스와 데이터 레이크의 가장 흔한 인터페이스. 빅데이터 처리에
    커스텀 맵리듀스 코드를 써야 했던 시기에 잠시 밀려났다가, 여러 형태로 데이터의
    링구아 프랑카로 재부상했다.**
  - **파이썬** — **데이터 엔지니어링과 데이터 과학 사이의 다리 언어. "모든 것에서 두
    번째로 좋은 언어"로 알려져 있다. pandas·NumPy·Airflow·sci-kit learn·TensorFlow·
    PyTorch·PySpark가 그 위에 있다.**
  - **JVM 언어(자바·스칼라)** — **스파크·하이브·드루이드 같은 아파치 오픈 소스
    프로젝트에서 우세하다. JVM은 대체로 파이썬보다 성능이 좋고 파이썬 API보다 저수준
    기능에 접근할 수 있다(스파크와 빔이 그 경우다).**
  - **bash** — **리눅스의 명령 줄 인터페이스. 오늘날에도 데이터 엔지니어는 파이프라인에서
    파일을 처리하려 `awk`·`sed` 같은 명령 줄 도구를 자주 쓰거나 오케스트레이션
    프레임워크에서 bash 명령을 호출한다.**
- SQL의 재부상에 대한 판정 — **맵리듀스와 빅데이터 시대의 도래는 SQL을 한물간 지위로
  밀어냈다. 그 이후 여러 발전이 데이터 엔지니어링 수명 주기에서 SQL의 유용성을 극적으로
  끌어올렸다. Spark SQL·BigQuery·Snowflake·Hive를 비롯한 많은 도구가 선언적이고
  집합론적인 SQL 의미론으로 방대한 데이터를 처리할 수 있고, 플링크·빔·카프카 같은
  스트리밍 프레임워크도 SQL을 지원한다** (1장, p.20).[^reis2022]
- 다만 만능은 아니다 — **유능한 데이터 엔지니어는 SQL이 그 일에 맞는 도구가 아닐 때를
  알아보고 적절한 대안을 골라 코딩할 수 있다** (1장, p.21).[^reis2022]
- 이차(secondary) 언어 — **R·자바스크립트·Go·러스트·C/C++·C#·줄리아. 회사 전반에서
  널리 쓰이거나 도메인 특화 도구와 함께 쓰일 때 필요해진다** (1장, p.21).[^reis2022]
- 학습 태도 — **바뀌지 않을 것을 이해하려면 기본기에 집중하고, 분야가 어디로 가는지
  알려면 진행 중인 발전에 주의하라** (1장, p.21).[^reis2022]
