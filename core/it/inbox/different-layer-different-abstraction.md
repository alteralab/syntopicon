하나의 질문: **어떤 클래스가 자기 계층의 값을 하고 있는지를 무엇으로 판정하는가.**

## 규칙

- 전제 — **소프트웨어 시스템은 계층으로 구성되며, 상위 계층은 하위 계층이 제공하는 설비를
  쓴다. 잘 설계된 시스템에서 각 계층은 그 위아래 계층과 다른 추상을 제공한다. 하나의 연산이
  메서드 호출로 계층을 오르내리는 것을 따라가면 메서드 호출마다 추상이 바뀐다** (7장 도입,
  p.51).[^ousterhout2021]
- 저자의 예 둘 (7장 도입, p.51):[^ousterhout2021]
  - **파일 시스템에서 최상위 계층은 파일 추상을 구현한다. 파일은 가변 길이 바이트 배열이며
    가변 길이 바이트 범위를 읽고 씀으로써 갱신될 수 있다. 그다음 하위 계층은 고정 크기 디스크
    블록의 메모리 캐시를 구현한다. 호출자는 자주 쓰는 블록이 메모리에 남아 빠르게 접근된다고
    가정할 수 있다. 최하위 계층은 장치 드라이버로 이뤄지며 보조 저장 장치와 메모리 사이로
    블록을 옮긴다.**
  - **TCP 같은 네트워크 전송 프로토콜에서 최상위 계층이 제공하는 추상은 한 기계에서 다른
    기계로 신뢰성 있게 전달되는 바이트 스트림이다. 이 수준은 기계 사이에 유계 크기 패킷을
    최선 노력으로 전송하는 하위 수준 위에 지어진다: 대부분의 패킷은 성공적으로 전달되지만
    일부는 손실되거나 순서가 뒤바뀌어 전달될 수 있다.**
- 조문 — **시스템에 비슷한 추상을 가진 이웃 계층이 있다면 이것은 클래스 분해에 문제가 있음을
  시사하는 붉은 깃발이다** (7장 도입, p.51).[^ousterhout2021]

## 통과 메서드

- 정의 — **이웃 계층이 비슷한 추상을 가지면 그 문제는 흔히 통과 메서드(pass-through method)의
  형태로 드러난다. 통과 메서드는 호출하는 메서드와 비슷하거나 동일한 시그니처를 가진 다른
  메서드를 부르는 것 말고는 거의 아무것도 하지 않는 메서드다** (7장 §7.1,
  p.52).[^ousterhout2021]
- 실물의 규모 — GUI 텍스트 편집기를 구현한 학생 프로젝트의 `TextDocument` 클래스는 거의
  전부가 통과 메서드였다. **그 클래스의 공개 메서드 15개 중 13개가 통과 메서드였다** (7장
  §7.1, p.53).[^ousterhout2021]
- **붉은 깃발: 통과 메서드(Pass-Through Method)** (7장 §7.1, pp.52–53):[^ousterhout2021]

> A pass-through method is one that does nothing except pass its arguments to another
> method, usually with the same API as the pass-through method. This typically indicates
> that there is not a clean division of responsibility between the classes.

- 두 가지 해악 — **통과 메서드는 클래스를 더 얕게 만든다: 클래스의 인터페이스 복잡성을 올려
  복잡성을 더하지만 시스템의 총 기능은 늘리지 않는다. (…) 통과 메서드는 클래스 사이에 의존도
  만든다: `TextArea`의 `insertString` 메서드 시그니처가 바뀌면 `TextDocument`의
  `insertString` 메서드도 맞춰 바뀌어야 한다** (7장 §7.1, p.53).[^ousterhout2021]
- 무엇의 증상인가 — **통과 메서드는 클래스 사이의 책임 분할에 혼란이 있음을 나타낸다. 위
  예에서 `TextDocument` 클래스는 `insertString` 메서드를 제공하지만 텍스트 삽입 기능은
  전적으로 `TextArea`에 구현돼 있다. 이것은 보통 나쁜 생각이다: 어떤 기능으로의 인터페이스는
  그 기능을 구현하는 바로 그 클래스에 있어야 한다** (7장 §7.1, p.53).[^ousterhout2021]
- 발견했을 때 물을 것 — **한 클래스에서 다른 클래스로 가는 통과 메서드를 보면 두 클래스를
  놓고 자문하라 "정확히 어떤 기능과 추상에 이 클래스들이 각각 책임을 지는가?" 아마 클래스
  사이 책임의 겹침을 알아채게 될 것이다** (7장 §7.1, p.53).[^ousterhout2021]
- 해소 경로 넷 — **해법은 각 클래스가 뚜렷하고 일관된 책임 집합을 갖도록 클래스를 리팩터링하는
  것이다.** Figure 7.1이 여러 방법을 보인다 (7장 §7.1, p.53):[^ousterhout2021]
  - **(b) 하위 클래스를 상위 클래스의 호출자에게 직접 노출해, 그 기능에 대한 책임을 상위
    클래스에서 완전히 없앤다.**
  - **(c) 클래스 사이에서 기능을 재분배해 클래스 사이 호출을 피한다.**
  - **(d) 클래스들을 풀어낼 수 없다면 최선의 해법은 그것들을 합치는 것일 수 있다.**
  - 실제 학생의 선택 — **위 예에서는 책임이 얽힌 세 클래스가 있었다: `TextDocument`,
    `TextArea`, `TextDocumentListener`. 학생은 클래스 사이로 메서드를 옮기고 세 클래스를
    책임이 더 명확히 구분되는 둘로 접어 통과 메서드를 없앴다** (7장 §7.1,
    p.53).[^ousterhout2021]

## 인터페이스 중복이 괜찮은 두 경우

- 판정 기준 — **같은 시그니처를 가진 메서드가 있는 것이 언제나 나쁜 것은 아니다. 중요한 것은
  각 새 메서드가 유의미한 기능에 기여해야 한다는 것이다. 통과 메서드가 나쁜 이유는 새
  기능에 기여하지 않기 때문이다** (7장 §7.2, p.53).[^ousterhout2021]
- **① 디스패처(dispatcher)** — **디스패처는 인수를 써서 여러 다른 메서드 중 하나를 골라
  호출하는 메서드다. 그다음 인수의 대부분이나 전부를 고른 메서드에 넘긴다. 디스패처의
  시그니처는 흔히 그것이 부르는 메서드들의 시그니처와 같다. 그렇더라도 디스패처는 쓸모 있는
  기능을 제공한다: 여러 메서드 중 어느 것이 각 과제를 수행할지 고르는 것이다** (7장 §7.2,
  pp.53–54).[^ousterhout2021]
  - 실물 — **웹 서버가 브라우저에서 들어오는 HTTP 요청을 받으면 디스패처를 부르는데, 그것은
    들어오는 요청의 URL을 살펴 그 URL을 처리할 특정 메서드를 고른다. 어떤 URL은 디스크의
    파일 내용을 반환해 처리될 수 있고, 다른 URL은 PHP나 JavaScript 같은 언어의 프로시저를
    불러 처리될 수 있다. 디스패치 과정은 꽤 복잡할 수 있고, 보통 들어오는 URL에 대조되는
    규칙 집합으로 구동된다** (7장 §7.2, p.54).[^ousterhout2021]
- **② 같은 인터페이스의 여러 구현** — **운영체제의 디스크 드라이버 같은, 다중 구현을 가진
  인터페이스다. 각 드라이버는 다른 종류의 디스크를 지원하지만 전부 같은 인터페이스를 갖는다.
  여러 메서드가 같은 인터페이스의 다른 구현을 제공할 때 그것은 인지 부하를 줄인다. 이 메서드
  중 하나로 작업해 본 적이 있으면 새 인터페이스를 익힐 필요가 없으므로 다른 것들로 작업하기가
  더 쉽다. 이런 메서드는 보통 같은 계층에 있고 서로를 호출하지 않는다** (7장 §7.2,
  pp.54–55).[^ousterhout2021]

## 데코레이터

- 정의 — **데코레이터(decorator) 디자인 패턴("래퍼wrapper"로도 알려진)은 계층에 걸친 API
  중복을 조장하는 패턴이다. 데코레이터 객체는 기존 객체를 받아 그 기능을 확장한다. 그것은
  바탕 객체와 비슷하거나 동일한 API를 제공하고, 그 메서드는 바탕 객체의 메서드를 호출한다**
  (7장 §7.3, p.55).[^ousterhout2021]
- 예 둘 — **4장의 자바 I/O 예에서 `BufferedInputStream` 클래스는 데코레이터다: `InputStream`
  객체가 주어지면 같은 API를 제공하되 버퍼링을 도입한다. 예컨대 문자 하나를 읽으려고 `read`
  메서드가 호출되면 바탕 `InputStream`의 `read`를 불러 훨씬 큰 블록을 읽고 남는 문자를
  미래의 `read` 호출을 만족시키려 저장한다. 다른 예가 윈도잉 시스템에 있다: `Window` 클래스가
  스크롤되지 않는 단순한 형태의 창을 구현하고, `ScrollableWindow` 클래스가 수평·수직 스크롤바를
  더해 `Window` 클래스를 장식한다** (7장 §7.3, p.55).[^ousterhout2021]
- 판정 — **데코레이터의 동기는 클래스의 특수 목적 확장을 더 일반적인 핵에서 분리하는 것이다.
  그러나 데코레이터 클래스는 얕은 경향이 있다: 적은 양의 새 기능을 위해 많은 양의 상용구를
  들인다. 데코레이터 클래스는 흔히 많은 통과 메서드를 담는다. 데코레이터 패턴을 남용해 작은
  새 기능마다 새 클래스를 만들기 쉽다. 이것이 자바 I/O 예 같은 얕은 클래스의 폭발을 낳는다**
  (7장 §7.3, p.55).[^ousterhout2021]
- **데코레이터 클래스를 만들기 전에 검토할 대안 넷** (7장 §7.3, pp.55–56):[^ousterhout2021]
  - **데코레이터 클래스를 만드는 대신 새 기능을 바탕 클래스에 직접 더할 수 있는가?** —
    **새 기능이 비교적 범용적이거나, 바탕 클래스와 논리적으로 관련되거나, 바탕 클래스의
    대부분의 용도가 새 기능도 쓸 것이라면 말이 된다. 예컨대 자바 `InputStream`을 만드는
    사람은 사실상 모두 `BufferedInputStream`도 만들고 버퍼링은 I/O의 자연스러운 부분이므로,
    이 클래스들은 합쳐졌어야 했다.**
  - **새 기능이 특정 사용 사례에 특화돼 있다면 별도 클래스를 만드는 대신 그 사용 사례와
    합치는 것이 말이 되겠는가?**
  - **새 데코레이터를 만드는 대신 새 기능을 기존 데코레이터와 합칠 수 있는가?** — **이것은
    여러 개의 얕은 데코레이터 클래스 대신 하나의 더 깊은 데코레이터 클래스를 낳을 것이다.**
  - **마지막으로, 새 기능이 정말로 기존 기능을 감싸야 하는지 자문하라: 그것을 바탕 클래스와
    독립적인 독립형 클래스로 구현할 수 있는가?** — **윈도잉 예에서 스크롤바는 아마 기존
    기능 전부를 감싸지 않고 주 창과 별도로 구현될 수 있었다.**
- 래퍼가 정당한 자리 — **래퍼가 말이 되는 상황이 가끔 있다. 한 예는 시스템이 인터페이스를
  수정할 수 없는 외부 클래스를 쓰지만 그 클래스가 쓰이는 애플리케이션에서 다른 인터페이스를
  따라야 할 때다. 이 경우 래퍼 클래스가 인터페이스 사이를 번역하는 데 쓰일 수 있다. 그러나
  이런 상황은 드물다. 보통 래퍼 클래스를 쓰는 것보다 나은 대안이 있다** (7장 §7.3,
  p.56).[^ousterhout2021]

## 인터페이스와 구현

- 같은 규칙의 다른 적용 — **"계층이 다르면 추상도 다르다" 규칙의 또 다른 적용은 클래스의
  인터페이스가 보통 그 구현과 달라야 한다는 것이다: 내부에서 쓰는 표현은 인터페이스에
  나타나는 추상과 달라야 한다. 둘이 비슷한 추상을 가지면 그 클래스는 아마 그리 깊지 않다**
  (7장 §7.4, p.56).[^ousterhout2021]
- 실물 — **6장에서 논의한 텍스트 편집기 프로젝트에서 대부분의 팀은 텍스트 모듈을 텍스트 줄의
  관점에서 각 줄을 따로 저장해 구현했다. 어떤 팀은 텍스트 클래스의 API도 줄을 중심으로
  `getLine`·`putLine` 같은 메서드로 설계했다. 그러나 이것은 텍스트 클래스를 얕고 쓰기
  어색하게 만들었다. 상위 사용자 인터페이스 코드에서는 줄 중간에 텍스트를 삽입하거나(사용자가
  타이핑할 때) 여러 줄에 걸친 텍스트 범위를 지우는 것이 흔하다. 줄 지향 API로는 호출자가
  사용자 인터페이스 연산을 구현하려고 줄을 나누고 합쳐야 했다. 이 코드는 사소하지 않았고
  사용자 인터페이스 구현 전반에 중복되고 흩어져 있었다** (7장 §7.4, p.56).[^ousterhout2021]
- 더 나은 설계와 그 이유 — **텍스트 클래스는 문자 지향 인터페이스를 제공할 때 훨씬 쓰기
  쉬웠다. (…) 내부적으로 텍스트는 여전히 줄의 관점에서 표현됐다. 문자 지향 인터페이스는
  줄 나누기와 합치기의 복잡성을 텍스트 클래스 안에 캡슐화하고, 그것이 텍스트 클래스를 더
  깊게 만들며 그 클래스를 쓰는 상위 코드를 단순화한다. 이 접근으로 텍스트 API는 줄 지향
  저장 기제와 꽤 다르다. 그 차이가 그 클래스가 제공하는 가치 있는 기능을 나타낸다** (7장
  §7.4, p.56).[^ousterhout2021]

## 통과 변수

- 정의 — **계층에 걸친 API 중복의 또 다른 형태가 통과 변수(pass-through variable)인데, 긴
  메서드 사슬을 따라 아래로 넘겨지는 변수다** (7장 §7.5, p.57).[^ousterhout2021]
- 실물 — **데이터센터 서비스의 예다. 명령줄 인수가 보안 통신에 쓸 인증서를 서술한다. 이
  정보는 소켓을 여는 라이브러리 메서드를 부르는 저수준 메서드 `m3`에만 필요하지만, `main`과
  `m3` 사이 경로의 모든 메서드를 거쳐 아래로 넘겨진다. `cert` 변수가 각 중간 메서드의
  시그니처에 나타난다** (7장 §7.5, p.57).[^ousterhout2021]
- 두 가지 대가 — **통과 변수는 복잡성을 더하는데, 중간 메서드들이 그 변수를 쓸 일이 없는데도
  전부 그 존재를 알도록 강제하기 때문이다. 더욱이 새 변수가 생기면(예컨대 시스템이 처음에는
  인증서 지원 없이 만들어졌다가 나중에 그 지원을 더하기로 했다면) 관련 경로 전부로 그 변수를
  넘기려고 많은 수의 인터페이스와 메서드를 수정해야 할 수 있다** (7장 §7.5,
  p.57).[^ousterhout2021]
- 해법 후보 셋 (7장 §7.5, p.57):[^ousterhout2021]
  - **① 최상위 메서드와 최하위 메서드 사이에 이미 공유되는 객체가 있는지 본다.** 위 예에서
    **네트워크 통신에 대한 다른 정보를 담은 객체가 `main`과 `m3` 둘 다에 있을 수 있다.
    그렇다면 `main`이 인증서 정보를 그 객체에 저장해 중간 메서드 전부를 거쳐 넘기지 않아도
    된다.** 단서가 붙는다 — **그러나 그런 객체가 있다면 그것 자체가 통과 변수일 수 있다
    (그렇지 않으면 `m3`이 어떻게 그것에 접근하는가?)**
  - **② 정보를 전역 변수에 저장한다.** 그러나 — **전역 변수는 거의 언제나 다른 문제를 만든다.
    예컨대 전역 변수는 같은 프로세스 안에 같은 시스템의 독립적인 인스턴스를 둘 만드는 것을
    불가능하게 하는데, 전역 변수 접근이 충돌하기 때문이다. 프로덕션에서 여러 인스턴스가 필요할
    가능성은 낮아 보일지 몰라도 테스트에서는 흔히 유용하다.**
  - **③ 컨텍스트 객체를 도입한다** — 아래 절이 그것이다.

## 컨텍스트 객체와 그 대가

- 저자의 선택 — **내가 가장 자주 쓰는 해법은 컨텍스트(context) 객체를 도입하는 것이다.
  컨텍스트는 애플리케이션의 모든 전역 상태(그렇지 않았으면 통과 변수나 전역 변수가 됐을
  것 전부)를 저장한다. 대부분의 애플리케이션은 설정 옵션·공유 서브시스템·성능 카운터 같은
  것을 나타내는 여러 변수를 전역 상태에 갖는다. 시스템 인스턴스당 컨텍스트 객체가 하나
  있다. 컨텍스트는 여러 시스템 인스턴스가 하나의 프로세스에 공존하게 해 주며, 각각이 자기
  컨텍스트를 갖는다** (7장 §7.5, p.57).[^ousterhout2021]
- 컨텍스트 자신이 통과 변수가 되는 문제와 그 처리 — **불행히도 컨텍스트는 아마 여러 자리에서
  필요할 것이므로 잠재적으로 통과 변수가 될 수 있다. 그것을 알아야 하는 메서드의 수를 줄이려면
  컨텍스트의 참조를 시스템의 주요 객체 대부분에 저장할 수 있다. (…) `m3`을 담은 클래스는
  컨텍스트 참조를 자기 객체의 인스턴스 변수로 저장한다. 새 객체가 만들어질 때 만드는 메서드가
  자기 객체에서 컨텍스트 참조를 꺼내 새 객체의 생성자에 넘긴다. 이 접근으로 컨텍스트는
  어디서나 쓸 수 있되 생성자에서만 명시적 인수로 나타난다** (7장 §7.5,
  p.59).[^ousterhout2021]
- 얻는 것 넷 — **컨텍스트 객체는 모든 시스템 전역 정보의 처리를 통일하고 통과 변수의 필요를
  없앤다. 새 변수를 더해야 하면 컨텍스트 객체에 더할 수 있고, 컨텍스트의 생성자와 소멸자
  말고는 기존 코드가 영향받지 않는다. 컨텍스트는 시스템의 전역 상태를 식별하고 관리하기 쉽게
  만드는데, 그것이 전부 한 자리에 저장되기 때문이다. 컨텍스트는 테스트에도 편리하다: 테스트
  코드가 컨텍스트의 필드를 수정해 애플리케이션의 전역 설정을 바꿀 수 있다. 시스템이 통과
  변수를 쓴다면 그런 변경을 구현하기가 훨씬 어려울 것이다** (7장 §7.5,
  p.59).[^ousterhout2021]
- 그리고 저자 자신이 붙이는 유보 — **컨텍스트는 이상적인 해법과는 거리가 멀다. 컨텍스트에
  저장된 변수는 전역 변수의 단점 대부분을 갖는다. 예컨대 특정 변수가 왜 있는지, 어디서 쓰이는지가
  뻔하지 않을 수 있다. 규율 없이는 컨텍스트가 시스템 전반에 뻔하지 않은 의존을 만드는 거대한
  잡동사니 자루로 변할 수 있다. 컨텍스트는 스레드 안전성 문제도 만들 수 있다. 문제를 피하는
  최선의 방법은 컨텍스트의 변수를 불변으로 만드는 것이다. 불행히도 나는 컨텍스트보다 나은
  해법을 찾지 못했다** (7장 §7.5, p.59).[^ousterhout2021]

## 설계 요소는 순이득을 내야 한다

- 장의 맺음이 이 장 전체를 하나의 회계 규칙으로 압축한다 — **시스템에 더해지는 설계 기반
  요소 각각은 — 인터페이스·인수·함수·클래스·정의 — 복잡성을 더한다. 개발자가 그 요소에 대해
  익혀야 하기 때문이다. 어떤 요소가 복잡성에 맞서 순이득을 내려면, 그 설계 요소가 없었을 때
  존재했을 복잡성의 일부를 없애야 한다. 그렇지 않다면 그 특정 요소 없이 시스템을 구현하는
  편이 낫다. 예컨대 클래스는 기능을 캡슐화해 그 클래스의 사용자가 그것을 알 필요가 없게
  함으로써 복잡성을 줄일 수 있다** (7장 §7.6, p.59).[^ousterhout2021]
- 그리고 이 장의 규칙이 그 회계의 특수 사례로 놓인다 — **"계층이 다르면 추상도 다르다"
  규칙은 이 발상의 한 적용일 뿐이다: 다른 계층이 통과 메서드나 데코레이터처럼 같은 추상을
  가지면 그것들이 나타내는 추가 기반 요소를 벌충할 만큼의 이득을 제공하지 못했을 가능성이
  높다. 마찬가지로 통과 인수는 여러 메서드 각각이 그 존재를 알도록 요구하되(이것이 복잡성에
  더한다) 추가 기능에 기여하지 않는다** (7장 §7.6, pp.59–60).[^ousterhout2021]
