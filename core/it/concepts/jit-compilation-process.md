# JIT 컴파일러의 컴파일 과정

- [서버 컴파일러 — 무엇을 더 하는가](#서버-컴파일러--무엇을-더-하는가)

이 페이지의 질문: **컴파일 요청을 받은 C1과 C2는 바이트코드에서 네이티브 코드까지 각각 어떤
단계를 밟는가.**

## 컴파일은 뒤에서 돈다

- 기본값이 비동기다 — **기본적으로 JIT 컴파일은 백그라운드에서 별도 스레드가 진행하며, 컴파일이
  완료될 때까지는 인터프리터가 프로그램 실행을 이어 간다. 메서드 호출로 촉발된 컴파일
  요청이든, OSR 컴파일 요청이든 마찬가지다** (11장, p.527).[^zhou2024] 어느 쪽 요청인지는
  [핫스팟 탐지와 온스택 치환](../concepts/hotspot-detection-and-osr.md)이 가른다.
- 끄면 요청자가 기다린다 — **백그라운드 컴파일을 원치 않는다면 `-XX:-BackgroundCompilation`
  매개 변수로 비활성화할 수 있다. 비활성화 상태에서 JIT 컴파일을 요청한 스레드는 컴파일이 완료될
  때까지 일시 정지 상태로 대기했다가, 완료되면 컴파일러가 만들어 낸 네이티브 코드를 실행한다**
  (11장, p.527).[^zhou2024]
- 그 안에서 하는 일은 컴파일러마다 다르다 — **서버 컴파일러와 클라이언트 컴파일러의 컴파일
  절차는 다르다** (11장, p.527).[^zhou2024]

## 클라이언트 컴파일러 — 3단계

- 설계 방침이 먼저 나온다 — **클라이언트 컴파일러는 비교적 간단하고 빠른 3단계 컴파일러다. 오래
  걸리는 전역 최적화는 포기하고 지역 최적화에 집중한다** (11장, p.527).[^zhou2024]
- 단계 1은 플랫폼 독립 프런트엔드가 맡는다 — **플랫폼 독립적 프런트엔드가 바이트코드로부터 타깃
  독립적 중간 표현인 HIR을 생성한다. HIR은 코드 값을 정적 단일 할당(SSA)으로 표현해 주어 몇 가지
  최적화를 더 쉽게 구현할 수 있게 도와준다. 물론 바이트코드를 HIR로 구성하기 앞서 메서드
  인라인이나 상수 전파 등 몇 가지 기본적인 최적화는 수행한다** (11장, p.527).[^zhou2024]
- 단계 2에서 표현이 한 번 더 내려간다 — **플랫폼 의존적 백 엔드가 HIR로부터 LIR을 생성한다. LIR
  생성 전에 HIR을 대상으로 null 검사 제거와 범위 검사 제거 등의 최적화를 수행하여 HIR이 코드를
  더 효율적으로 표현하도록 최적화한다** (11장, p.527).[^zhou2024]
- 단계 3이 레지스터와 네이티브 코드다 — **플랫폼 의존적 백 엔드가 선형 스캔 레지스터 할당(linear
  scan register allocation)을 사용하여 LIR에 레지스터를 할당하고 핍홀 최적화를 수행한 다음,
  네이티브 코드를 생성한다** (11장, p.528).[^zhou2024]
- 그래서 최적화가 두 중간 표현에 나뉘어 걸린다 — 인라인·상수 전파는 HIR 생성 **앞**에, null 검사
  제거·범위 검사 제거는 LIR 생성 **앞**에, 핍홀 최적화는 레지스터 할당 **뒤**에 붙는다 (11장,
  pp.527–528).[^zhou2024] 각 기법의 내용은
  [JIT 컴파일러의 최적화 기법](../concepts/jit-optimization-techniques.md)에 있다.

## 서버 컴파일러 — 무엇을 더 하는가

- 겨냥하는 곳이 다르다 — **서버 컴파일러는 서버용 애플리케이션들의 일반적인 시나리오를 감안하여
  서버 측 성능을 극대화하도록 설정된 컴파일러다. 상당히 복잡한 최적화까지 지원하는 고급
  컴파일러로, `-O2` 매개 변수를 지정한 GNU C++ 컴파일러 수준에 비견된다** (11장,
  p.528).[^zhou2024]
- 수행하는 최적화가 세 갈래로 나뉜다 (11장, p.528):[^zhou2024]

  | 갈래 | 무엇 |
  |---|---|
  | 전통적인 최적화 | **죽은 코드 제거, 순환문 언롤링, 순환문 표현식 호이스팅, 공통 하위 표현 제거, 상수 전파, 기본 블록 재정렬 등** |
  | 자바 특화 최적화 | **범위 검사 제거, null 검사 제거 등** |
  | 예측 최적화 | **인터프리터나 클라이언트 컴파일러가 제공하는 성능 모니터링 정보를 토대로 가이디드 인라인과 분기 예측처럼 안정성이 다소 떨어지는 예측 최적화** |

  - 일부는 컴파일러의 일이 아니다 — **일부 null 검사 제거는 컴파일러 최적화가 아니라 코드 실행
    중에 자동으로 수행된다** (11장, p.528).
- 레지스터 할당기도 다르다 — **서버 컴파일러가 사용하는 레지스터 할당기는 RISC 같은 일부 프로세서
  아키텍처의 커다란 레지스터 집합의 이점을 활용할 수 있는 전역 그래프 채색 할당기다** (11장,
  pp.528–529).[^zhou2024] 같은 장의 최적화 기법 목록에도 **그래프 채색 레지스터
  할당(graph-coloring register allocation)** 이 C1의 선형 스캔과 나란히 실려 있다 (11장,
  p.551).
- 느리다는 단점이 상쇄된다 — **표준 JIT 컴파일에서 서버 컴파일러는 상대적으로 느리지만 전통적인
  정적 최적화 컴파일러보다는 훨씬 빠르다. 또한 만들어 낸 네이티브 코드의 성능이 클라이언트
  컴파일러의 결과물보다 훨씬 좋아서 컴파일이 오래 걸린다는 단점은 거의 상쇄된다** (11장,
  p.529).[^zhou2024]
  - 버전 조건: JDK 9 이상 — **그래서 JDK 9부터는 서버 모드가 JDK의 기본 모드가 되었다** (11장,
    p.529).

## 저자가 이 절에 붙인 유보

- 분량의 한계를 스스로 밝힌다 — **이번 절에서는 컴파일 원칙과 코드 최적화 용어가 많이 등장해서
  관련 기초가 부족한 독자에게는 다소 추상적이고 이론적으로 느껴졌을 것이다. 무리도 아니다. JIT
  컴파일 과정은 원래 가상 머신에서 가장 기술적이고 복잡한 영역이라서 단 몇 쪽에 모든 내용을
  담기에는 무리가 따른다** (11장, p.529).[^zhou2024]
- 그럼에도 볼 방법은 있다 — **반면에 이 과정은 자바 개발자들이 전혀 모르게 진행되어 존재조차
  인식할 수 없는 게 일반적이다. 핫스팟 가상 머신은 다행히도 JIT 컴파일러의 최적화 과정을
  시각화해 주는 도구를 제공한다** (11장, p.529).[^zhou2024] 그 도구들은
  [핫스팟 JIT 코드 들여다보기](../concepts/hotspot-jit-inspection-tools.md)에 있다.
